# Story Extension 1.9.1 发布说明

Story Extension 面向需求开发与评审，提供材料整理、范围确认、规格与评审文档生成、评审意见回流，以及工程知识在开发各阶段的应用能力。

**1.9.1 重点是让「已经做过的判断」在交付前真的被看见，并让成文先有整篇设计**：Story 交给独立审查时带上完整正文，交付按审查的实际结论放行；写 Story 之前先形成一份可恢复、可调整的整篇写作设计，按它写章、再从原材料核实际全文；评审记录按「请人选方案」与「请人复核结论」分别给填写位；材料里的每张图各自成为一件要处理的事，上游原件与本轮提取稿分开保存；文档里由机器生成的区块被人改过时会被指出来并给出撤销出口。

本版基于 **Framework 3.0.0**，支持有人参与的交互式流程。本文说明发布能力与版本变化；命令、操作步骤和常见问题见[《story 使用指南》](story使用指南.md)，整体协作方式见[《需求交付流程》](需求交付流程.md)。上一版见 [1.9.0](1.9.0.md)，本版在它之上做增量。

## 本版新增与优化

### 1. 独立审查拿到完整正文，交付按结论放行

送去做语义审查的不再只是章节标题与要点，而是当前 Story 的完整正文一次给全，连同规格、决策、范围、留存的上游原件与图片清单一并指明位置。审查方法与输出要求在一处维护，作者面与审查面各取所需，不再各留一份说法。

交付门据此改判：审查判的不是通过就不交付；本工程没有登记审查员时，如实记一笔「未经读者语义审查即交付」，不再静默放行。报告结构齐备与审查结论通过是两件事，前者不再顶替后者。

### 2. 图片各自成为一件要处理的事

材料里的每一张图在作者任务里单独成条：它是什么、在哪里、本次用不用、不用的理由记在哪。清单形状不对（比如材料项不是预期结构）会作为缺口报出来，不再与「本需求确实没有图」同形。

图的引用与说明只按内容存：换个落点、改个名字，说明与取舍都跟着这张图走。

### 3. 上游原件与本轮提取稿分开

S4 提交时被覆盖的那份上游 AR 按轮次留存，并作为一份独立材料进入材料清单与来源检查。作者与审查者回查上游原话时有确定的位置，不必从已被覆盖的输入件里找。

### 4. 生成的内容被手改不会被悄悄盖掉，也不会被悄悄留下

两处的做法按各自的风险不同：

- **附录的契约投影**：全篇检查时逐行与当前真源比对，被人改过就报出差在哪一行，并给出重新
  生成的出口。必需的来源缺失不再被当成一份合法的空投影——那两件事此前同形，而它们的处置相反。
- **评审记录**：渲染时按摘要判这一段有没有被人动过，动过就**拒绝重新渲染**并说明怎么撤销，
  不做全文逐行比对；评审人写在「审核结果：」之后的内容逐字节保留，任何一次渲染都不碰。

### 5. 成文与整稿的失败语义收紧

章提交先核后写：候选正文不合格时不落盘，正文之外的字节原样保留；已经写成功的一章不会再被报成失败。整稿、编号与投影的顺序固定，登记前重跑检查，检查不过不登记。

### 6. 材料事实与验收条目各取一次

同一条命令里，材料现状只取一份快照，路由、提示与输出读的是同一个时点；验收条目一次验证并分组，各阶段只选择需要的集合。

### 7. 命令不变，公共脚本按功能归位

对外命令、参数与产物路径与上一版一致。公共脚本内部按职责分到子目录（流程、材料、成文、知识应用各自成组），单个脚本规模收敛。升级仍是「公共机制整份换掉」；业务对接实现**看来源**：从 Demo 装过来时它那三个替身不给也不
覆盖（目标自己按合同实现），从另一个业务仓复刻时整份换成来源版本（两边对的是同一个需求系统）。

### 8. 写 Story 之前先有整篇写作设计

初析阶段的来源初筛保存每份材料对本需求的作用、仍要核实的矛盾与不适用的依据，后续阶段沿用这些判断。成文起手时，脚本只建一份写作设计空壳（`AR/story-src/story-template.md`），作者对照初筛、原材料、规格与决策登记写出阅读主线、每章的主线与分工、拟用形式，以及已选定要脚本落实的表与图；再次起手时脚本读取这份设计，把选定的表头与作图位铺进章草稿，章提交与全篇检查按同一份选择核对。设计是当前解释安排，不是业务真源、也不是正文上限：写作中发现更好的表达可以直接更新它，业务结论仍回规格与决策登记。

写作设计随成文登记一起冻结，重开后可改；缺失或坏件时起手命令给出具体缺口，不回填历史答案。

### 9. 按设计写章，十章齐后从来源核实际全文

写一章先读本章的设计安排、相关原材料与已写正文，回答本章要增加什么独有解释，再动笔；跨方调用与返回是理解重点时用时序图，改画上游时序图须保留调用方、被调方、返回与失败补偿。结构选择可以指明「这一处要的是时序图」，章提交时普通流程图不能顶替它。

十章齐后的核对从来源出发：初筛与写作设计识别的义务是否在成品有可读解释，承诺的行为从前置到结果是否成立，未决是否被写成已定；问题回最早出错的真源改。独立审查同样先按原材料独立判完整性，再用写作设计定位作者的取舍，最后核实际正文；「未决方案冒充已定」「同一验收编号在两处含义不同」按阻断处理，合法的表达差异不机械处罚。

### 10. 评审记录分「选方案」与「复核结论」两种填写位

决策登记新增 `review_mode`：`choice` 表示请人从方案中选用，评审记录给「方案选择：」填写位，「可选的做法」必须是真正的有序列表，建议先写选哪一项再写理由；`confirm` 表示请人复核已有结论，给「审核结果：」的确认/不同意两框，不同意时写原因与调整结论。两类填写位默认都未选，推荐不等于人已选择。议题正文统一用「决策点」「依据」标题。人工区起点按生成摘要认，评审人引用标签或改动机器正文都不会丢掉已写意见。

发现两份原文冲突时，作者可以分析、推荐，但改变明确验收或范围口径要由人裁决；裁决未取得时保留原文与冲突、正文写明待决边界。plan 阶段的审查按每条义务的实际含义核对它指向的规约原条目，借编号挂载不算知识传递。

### 11. 处置台账归过程目录，测量读数修正

评审回流的处置台账落在 `AR/story-src/review-disposition.json`，AR 根目录只保留交付件；在途需求若旧路径下有台账，回流时原样迁入。实跑测量对工具入参取真实字符串并归一路径分隔符，规则与源码读取次数不再因转义被记成 0。

## 1.9.1 功能清单

以下为本版包含的完整功能，涵盖既有能力及上述优化。

| 功能 | 提供的能力 |
|---|---|
| 需求系统取材 | 获取 AR 及其上游 RR、SR 材料，建立本次需求的输入基础 |
| 本地需求接入 | 支持问题单、工单等非 AR 需求，使用本地提供的材料形成规格与评审文档 |
| 补充材料导入 | 接收 DOCX、文本与界面图片，保留原件，登记材料与图片来源；不支持的格式明确报出 |
| 材料身份与取舍 | 每份正文、每张图各有身份与说明；本次不用的图登记理由，换名换位置仍跟着这张图 |
| 上游原件留存 | 提交提取稿时按轮次留下被覆盖的上游原件，作为独立材料供作者与审查回查 |
| 范围分析与拆分 | 提出整体承载或拆分方案，记录用户选择、各方责任、交接依赖与决定依据 |
| 规格与验收生成 | 形成需求范围、功能行为、业务规则、技术契约及可观察的验收条件，供后续设计实现使用 |
| 来源初筛与整篇写作设计 | 初析保存每份材料的作用与疑点；成文前作者写出阅读主线、每章安排与选定结构，脚本据此铺章草稿并按同一份选择核对；设计可恢复、可调整，随登记冻结 |
| Story 成文 | 按设计逐章编写、落盘，十章齐后从原材料核实际全文；跨方调用用时序图并可指明该处只认时序图；附录契约从规格与知识判断中投影 |
| 生成内容的手改保护 | 附录投影逐行比对报出差在哪一行；评审记录按摘要判动没动过、动过就拒绝重渲染并说明怎么撤销，人工填写区逐字节保留 |
| 决策与评审记录 | 呈现已定判断和待定事项，说明决策点、依据、建议与影响；按「选方案」或「复核结论」给填写位，推荐不预填为人已选择 |
| 冲突裁决边界 | 两份原文冲突时作者只分析与推荐，改变明确验收或范围口径须由人裁决，未裁决前正文写待决边界 |
| 独立语义审查 | 把完整 Story 与它的依据交给独立审查，结论可机读；交付按结论放行，缺审查员时如实披露 |
| 归档与恢复 | 将需求叙事及评审记录送入需求系统，备份被覆盖的正文，支持恢复上次归档前的内容 |
| 评审意见回流 | 获取评审意见，逐条处置并修订相关规格；保留评审时点文档，处置台账记在需求过程目录 |
| 工程知识应用 | 使用项目事实、工程规约和设计模式，支持适用判断、设计落点、验证分派及后续阶段检查 |
| 开发阶段协作 | 向规格、计划、编码、代码检视、单元测试、实机测试提供对应的作者要求与扩展检查；阶段执行由 Framework 承接 |
| 中断恢复 | 根据需求目录中的流程记录恢复进度，支持更换会话后接续 |
| 跨工程安装与升级 | 公共机制整份更新；对接实现按来源处理（Demo 来源不给不覆盖，业务仓之间整份换）；目标的知识、工程身份与自己的说明保留 |

## 主要产物

| 产物 | 职责 |
|---|---|
| `AR/design.md` | 经范围确认形成的需求输入 |
| `spec/spec.md` 与验收材料 | 后续设计、实现和验证的依据 |
| `AR/story.md` | 面向评审者解释完整需求、方案、行为与交付安排 |
| `AR/review.md` | 承载需要审核的判断、待定事项及人工意见 |
| `AR/story-src/story-template.md` | 本次需求的整篇写作设计：阅读主线、各章安排与选定结构 |
| 需求过程记录 | 保存材料、范围决定、初筛判断、成文过程、上游原件与评审处置（`review-disposition.json`）的可追溯信息 |

Story 正文由 AI 根据材料、规格、写作设计与已确认判断编写，附录的部分内容由脚本投影；整篇文档并非规格的确定性转换。评审回流保留评审时点的 Story，规格变更通过处置记录追溯。

## 依赖与发布范围

- **Framework**：基于 3.0.0 的扩展能力接入，安装本扩展无需修改 Framework。
- **需求系统**：业务工程需具备真实对接实现与访问配置；Demo 对接脚本用于本地模拟。
- **知识维护**：项目事实、规约与设计模式由目标工程核实并维护，公共机制按激活清单使用。
- **运行范围**：交互式需求开发；本地非 AR 需求保留仓内产物，不执行 AR 的系统归档与恢复。
- **能力边界**：本版不包含会议转写的专门语义纠偏与结论提取。上面这些改动改变的是**信息送达、写作组织与放行判据**，文档写得好不好仍由独立审查与人来判；结构检查不证明表达质量。规格正文与验收文件之间同一验收编号的机械一致性属 Framework 能力，本版由独立审查按语义核对。
