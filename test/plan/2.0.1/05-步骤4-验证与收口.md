# 步骤 4：回归迁移、验证与收口

依据 [总览](01-实施总览与协作合同.md)、[协作 spec 验收矩阵](../../spec/2.0.1/03-Framework协作与验收.md#5-能力验收矩阵)、[维护预算](../../AGENTS.md#5-维护预算与分级复核)和 [TEST](../../TEST.md)。前置为步骤 1–3 评审通过，实际 framework 发布件及补充 A/B 已交付。

## 1. 验证资产动作

- 将现有 tests/、fixtures/、regression/ 中有效的材料、人签、成文、知识、更新、安装和恢复覆盖迁移到新入口；只服务已退出机制的断言一起删除。
- 更新 run_case/run_multi_case 的需求交付观测、设计关联、独立审查和实际施工终点识别。使用 1.9.8 的隔离 template 装配，不另建 runner。
- Case 保留系统单、本地单、更新和冲突；增加直接 Framework 入口、无新 Spec/Plan、多 CU 的必要验证安排，复用现有装置及材料方法。
- 更新当前 TEST、入口帮助和升级演进说明；历史日志和金样的历史证据不改写成新版本结果。

## 2. 分层验收

| 组 | 场景和预期 | 对应 spec |
|---|---|---|
| T1 来源与人工决定 | 两类来源、缺料、摘要冲突、会议和范围；真实原话与对象对应 | V1、V3 |
| T2 人读交付 | 已准入、零 CU、无新 Spec/Plan；一套 Story 讲清业务与当前设计，图文及精确来源完整 | V2、V7 |
| T3 知识送达与应用 | 直接设计和 Story 路径、四种形态、空/坏登记；作者和质询方实际取得原文、应用到真实对象 | V4 |
| T4 施工承接 | 原生派生/复用后实体义务、模式角色、验收桥仍在；局部和共享义务责任可查 | V5 |
| T5 更新与恢复 | 四类反馈、过期对象、人工编辑、范围变化、未完成更新；只恢复自有可编辑面 | V3、V6、V8 |
| T6 发布 | 请求终点、实际授权、失败、外部冲突及远程恢复；本地单无远程动作 | V7 |
| T7 安装 | 首次/升级/重复、缺能力、脏路径、两类对接来源；目标知识保留、原生入口可用 | V9 |
| T8 组合及退出 | 单/多 CU、当前对象审查、实际成本、旧入口/字段/状态消费者全部退出 | V8、V10 |

每组按特性树叶节点逐项核，记录输入、预期、实际与证据路径。构造反例只证明确定性检查；语义以正常需求、实际模型输入、产物及独立审查判定。

先运行改动相关离线测试，全部实施完成后运行现有全量 pytest、失效形态、机制预算及修改脚本语法检查。检查命令以 1.9.8 后 TEST 和实际 CLI 为准；不得照历史路径或凭示例命令改产品。

真实 CLI 在用户启动的里程碑按 TEST 运行，证据留在 output/story/，不进入消费模型上下文。保留现有宿主、模型与配置记录。实际需求上限为 Plan；可复用阶段不强制重跑。Coding、实机、事件和整体施工证据没有取得时明确未验证。

修改 mjs 逐个 node --check；修改 Python 用 `python -m compileall -q -j 0 <明确改动目录>`。源静态检查与实际消费目标分开。上游补充 A/B 测试必须取实际发布件，不能只 mock 下游结果声称其能力就绪。

正常需求验证仍使用现有 Case 协议：系统单和本地单各保留一条完整前段；选实际有多 CU 义务的需求观察共同知识与分工；直接入口和输入复用场景在授权里程碑中单列。用户从归档件评价业务结果，维护者不把结构夹具的答案注入消费上下文。机械反例不证明模型理解/审查能力。
