## 2. F1 / P2：登记上下文没有正确序列化文件路径

位置：doc/extensions/hooks/shared/knowledge.mjs:611，declarationContext。

当前拼接 flow YAML 时 file 值直接插入，其余复杂值才 JSON.stringify。文件名含合法逗号时，模型读到的路径会改变。

设计者直接调用现行 declarationContext，再将围栏内容交给现行 parseYaml：输入 file 为 `knowledge/facts/a, b.md`，结果变成 `{file: 'knowledge/facts/a', 'b.md': null, ...}`。其他登记字段保留，因此这不是显眼的整体解析失败，而是来源路径被悄悄改写。目标自定义文件名不能被当前 Demo 简单路径限制。

修法：序列化整条声明，例如每行 `'- ' + JSON.stringify(d)`，而非手拼部分字段；JSON 对象是合法的 YAML flow 对象，继续使用现有围栏即可。保证实际文件、protocol、capabilities、capability_decisions 的值原样交付。

验证：普通路径、含逗号及括号等合法文件名，渲染后按 YAML 读回，与原声明逐字段相等。无需新增路径规则或要求目标改文件名。

## 3. F2 / P2：多文件错误仍会被首个读取错误截断

位置：knowledge.mjs:470–476。文件读不到、缺 kind 仍直接 fail；metadata 的 bad 汇总尚未覆盖这些分支。

设计者在 output 下独立临时工作区登记两份文件：第一份缺失，第二份存在但 protocol=99。调用 activeKnowledge 只得到第一份缺失错误，第二份协议问题没有送达。S3 设计明确要求可读文件继续检查、一次汇总，因此目前仍会让维护模型一轮修一个文件后才看到下一个错误。

修法：每文件可定位的读取/类型错误追加 bad 并继续其他文件；本文件前置不足的解析跳过并说明原因。manifest 本身读不到、无法取得文件列表时仍直接报告前置失败。最终有 bad 统一抛 KnowledgeError，不返回部分成功对象。保持现有错误类型与调用者接口。

验证：缺失文件、缺 kind、协议不兼容和合法文件混合时，一次包含全部可确定错误；合法文件的存在不掩盖错误；不返回可误当完整结果的部分知识。

## 4. F3 / P2：适配后的知识验证依赖一个不存在的 feature

位置：skills/story-adaptation/reference/knowledge-adaptation.md:38，第7步“用任一阶段任务包确认知识能加载”。

首次安装目标尚无业务需求是正常情况；spec/plan author 入口都要求 --feature，并承担业务阶段任务。按当前方法，适配模型需要自行发明需求编号或另找实现来确认知识可读。安装和知识迁移应能独立完成，不以存在一份业务需求为前提。

修法：方法页给出从目标工程根直接调用既有 activeKnowledge 与 selfCheck 的只读命令，模块路径按目标 framework.config.json 的 paths.extension_dir 解析。检查只读激活知识并打印结构结论，错误保留具体位置；不创建 feature、不进入阶段，也不新增检查器。已有业务需求的任务包检查留给阶段消费验证。

设计责任：先前设计只写了“通过现有知识加载路径复核”，未交付无 feature 的可用调用方式，执行者选择阶段任务包具有原因。本次已在 S3 设计补齐命令输入与输出合同。

验证：已首装、合法知识已激活、features 目录没有任何需求时，验证可独立通过，未创建业务产物；知识非法时非零退出并给明确信息。
