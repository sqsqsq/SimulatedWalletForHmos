# S3：知识能力适配实现

知识如何叙述、各阶段怎样应用以及 adapt 如何生成知识，按 [08-机制与知识的消费协作设计](08-机制与知识的消费协作设计.md) 落实；本分册已有确定性接口和验证职责保留。

**前置：S2 遗留收口已通过独立评审。** 输入是 S2 记录的真实基线、当前知识与阶段要求；本步不与遗留修复并行。预算、保护项见 [总览](00-整体设计与实施顺序.md)。本设计落实知识能力适配 AC01–AC14 的实现，AC15 留内网交回。

## 1. 交付内容与位置

复用现有 Skill、参考文档、frontmatter、manifest 和加载器。新增的三份说明各有现有消费者，不新增工具命令、生成器或状态框架。

| 交付路径（相对 doc/extensions） | 职责与消费者 |
|---|---|
| skills/story/reference/knowledge/protocol.md | 唯一通用读写规则；接替四份知识 README 中的通用规则。目标适配模型、阶段作者、审查任务在读取对应知识前取得 |
| skills/story/reference/knowledge/capabilities.md | 当前完整能力台账及必要迁移说明；adapt 模型逐项识别，阶段模型按当前需求核适用缺口。人工可读 Markdown，不建立脚本解析台账的要求 |
| skills/story-adaptation/reference/knowledge-adaptation.md | 识别→人定→改写→走查→交回的方法，含一个完整中性例子；由适配 Skill 在机制安装前读取，安装后按目标材料执行 |
| knowledge/ 现有内容文件的 frontmatter | 目标自身的能力关联与要求版本；manifest 仍是唯一激活清单 |
| hooks/shared/knowledge.mjs | 复用既有 YAML 解析工具读取新登记、检查格式、输出原始登记；不判断覆盖程度、内容正确性或业务适用性 |

protocol 与台账同处，互相引用但不复写。通用协议解释 kinds、事实确认、规约列义、模式输入输出结构、登记含义；每项业务能力只在台账说明需要回答什么，目标知识只回答本项目具体是什么。SDK 依赖及目标具体模式内容留在模式文件。

把原 README 里的消费者坐标、候选与组合步骤分别放在协议的对应类型段，模式具体命中条件留原文件。原模式清单由激活文件派生，不在新协议里再手列一份。

## 2. 台账内容

每项使用稳定标题锚点，包含：ID、知识类型、要求修订号、适用条件、消费阶段、当前完整要求、取证位置类别、走查条件、缺失影响、Demo 组织参考链接。通用读写规则、业务相关能力、可选模式分组。

首次登记覆盖部件画像、通用工程事实、上报事实、当前各规约域及两种模式；采用当前 name/pattern_id 作为初始能力 ID，来源从本次激活内容核实，通用脚本不硬编码这些 ID。模式条目明确其 SDK 条件与可不用；规约域参考不等于强制目标继承 Demo 条目。目标自有 ID 可以不存在于包台账，模型照常说明其来源与用途。

要求修订号按能力单独递增，首次为 1；它不是包版本，也不是读写协议版本。上调时说明增删或语义变化；文案整理无需强迫目标改号。提供完整现行要求；涉及更名、拆分或合并时在相关条目保留旧 ID 到新 ID 的迁移依据，直到支持的既有登记均能关联，不要求保存每版全文。跳版本模型从实际旧 ID 和内容出发，不从目标安装版本猜历史。

台账可以点名自己声明的能力与样例路径；阶段实现代码、通用 author、overlay 不据某个能力 ID 分支。包的具体参考能力由台账提供，不在 hooks 复制清单。

## 3. 目标登记的最小协议

使用现有知识文件 frontmatter 的 YAML；kind 仍只有 facts、constraints、patterns。新登记是可选元数据，旧内容无登记依然可被读取并列为待识别；不把“无登记”误认为已满足，也不单凭缺字段拒绝进入适配。

```yaml
---
name: target-service-facts
kind: facts
protocol: 1
capabilities:
  - id: sample-service
    revision: 1
    covers: [identity, result]
---
```

上例 ID 和面名只演示形态。实际取台账条目及目标内容；covers 是该文件真实承载的面标识，正文须能定位其含义。允许一个文件多条绑定、同项能力由多文件覆盖；写入时将同一文件相同 ID 合为一条；读取时发现重复给结构错误，多文件同一 ID 保持合法。业务内容冲突由模型判断，不把两文件均覆盖某面当作错误。

`protocol` 表示本机制能读取的结构版本；初版沿现行 1，不因移出 README 改写全部内容协议。声明缺席时按当前实际结构检查并报告未声明，不能凭空断定版本；显式不兼容的值与字段结构错误报出位置和修法。`revision` 为正整数，仅提供原始版本事实；加载器不比较台账、不据 revision 新旧阻断。未知能力 ID 可以是目标自有，不能校验成非法业务域。

### 不适用与待办

在目标既有部件画像的 frontmatter 使用 `capability_decisions`，这是同一知识文件的一部分，不新建台账或安装状态文件。适配方法依据部件画像内容识别文件，不凭文件名指定唯一所有者。首装部件画像本来必做，不再为决定新增一份文件。

```yaml
capability_decisions:
  - id: sample-service
    revision: 1
    scope: [operation]
    decision: not_applicable
    reason: 本部件不承担该业务，交互方提供此能力
    basis: 架构说明中的责任边界及本次用户确认
```

scope 用能力面标识列表；整项用单元素 `['*']`，不得与面列表混用。decision 只取 not_applicable 或 deferred。deferred 除 reason、basis 外写 impact，说明可能影响哪些任务。它们是用户已作选择的记录，不是模型自动打的完成状态。能力接入由文件的 capabilities 和实际内容表达，不再记 completed。

所有被激活文件的这些登记都由加载器原样交付，方法要求决定集中在部件画像，避免各文件自行豁免。冲突决定或旧不适用与当前新范围相撞，由模型只询问受影响部分；完成适配时删除对应已失效的 deferred 或缩小范围，不能让接入和整项不适用同时有效。保留与本次无关的目标选择。

## 4. 模型怎样执行一次 adapt

### 安装前取输入

适配 Skill 主干增加明确指针：处理首次安装、升级或知识适配时先读方法、协议和台账，检查包/目标路径与现行所有权。命令仍使用现有 adapt-scan --apply / --check；不加第二个 scanner。版本相同、机制无变化时脚本可无写入返回，但模型仍继续核知识状况，不能以 exit 0 结束整个任务。

脚本安装前置、脏工作区规则、目标身份与 adapters 来源策略保持。模型知识编辑也保留目标在途内容；相互冲突的编辑点给具体差异后让人决定，不自动 stash 或覆盖。

### 识别与给人选择

模型读目标激活文件、相关代码和协议，按当前完整要求识别已有内容。无登记先识别再补关联；已有登记先看变化再核真实内容。相同内容多个文件出现时定位权威来源，不合并成新副本。

差异说明按需一项一行：能力/受影响面、当前证据、需要补什么、对当前任务的影响、建议本次适配/不适用/待办。无差异明确说明依据；不是生成一个固定总表再让用户全量签字。向用户一次展示本次真正需要选择的范围，已有有效选择沿用。

### 人定后改写

按已选范围读定义和实际调用，结合业务协议写知识。相同编程语言或类名不能作为直接复制 Demo 的依据；示例只参考信息组织。新建规范与现有能力分开，缺事实标未确认；遇新业务决定、事实冲突或超范围，再问具体问题。

同一能力由多份文件承担时只改相关部分；拆分合并同步引用、登记和激活清单，退出被替换内容。不存在的文件先写成完整可读文件再激活；移动先保留新位置有效、修引用后删旧位置。使用原有文件编辑与 Git diff 保留可检查变化，不建备份状态框架。

每项以一段正常业务使用走查：阶段是否能取得所需定义、哪些设计现在能写出、哪些仍待核。用户已授权的成品不逐项重复确认；需要新的业务裁决时例外。

### 无需求编号时验证知识可读

适配完成后，在目标工程根执行下列只读 Node 程序。模型使用宿主支持的方式把代码传给 `node --input-type=module`；输入是当前工程配置与激活知识，不需要 --feature。与 adapt-scan --check 分开执行、分开报告。

```js
import fs from 'node:fs';
import path from 'node:path';
import { pathToFileURL } from 'node:url';
const root = process.cwd();
const config = JSON.parse(fs.readFileSync(path.join(root, 'framework.config.json'), 'utf8'));
const ext = path.resolve(root, config.paths?.extension_dir ?? 'doc/extensions');
const api = await import(pathToFileURL(path.join(ext, 'hooks/shared/knowledge.mjs')).href);
const knowledge = api.activeKnowledge(root);
const problems = api.selfCheck(root, knowledge);
if (problems.length) throw new Error(problems.join('\n'));
console.log(JSON.stringify({ status: 'PASS', files: knowledge.declarations.length }));
```

异常由 Node 非零退出并保留位置与错误文本；PASS 仅证明加载及已有结构检查，不证明内容正确。命令不创建需求目录或阶段产物，不作为新的脚本文件维护。运行环境缺现有 YAML 依赖时，按原依赖提示处理；不将依赖失败称为知识缺失。

### 中断与失败

脚本未完成机制安装则按错误恢复机制；机制成功但知识待办，分别交回，不回滚成功机制伪造原状态。模型中断后重读当前文件和未决，不凭会话记忆重写全仓。文件激活破损先修链接/格式，语义未知不伪造；目标未选的适配不擅自执行。

交回包括机制安装检查、知识实际改动与证据、用户不适用决定、未完成及影响。没有变化不重写内容；无实际冲突时无需新增确认。

### 方法页的完整中性例子

用“后台任务通知”描述一个非钱包仓：已有通知发送封装与重试，但知识未登记；维护模型查定义及两处真实使用，确认已知返回语义，发现取消时是否通知没有业务依据；用户选择接入已有发送事实、取消策略暂缓；模型复用原文件，补登记和证据，将暂缓范围及影响记入部件画像；走查说明常规发送设计可用、取消策略仍未决。例子中的路径和值标为示意，不变为脚本约定，也不作为真实验收证据。

## 5. README 和消费者的交接

先发布新协议入口与台账，再改首装脚本停止生成/激活 README；manifest 首装知识列表为空，按现行必做部件画像流程补第一份内容。机制 --check 继续只查机制一致性，不借本次扩大为语义适配检查。

升级脚本仍保留目标知识及其激活清单。模型以文件读取工具直接读旧 README、内容文件和 manifest，安装后的人定范围分成两类：必要的协议迁移、可分批完成的知识能力适配。协议迁移恢复当前知识可读；能力适配补业务定义与登记。两类放在同一次范围选择中说明，避免用户选择暂缓某项业务能力时被误当作拒绝基础迁移。

模型执行最小协议迁移的顺序：读取旧索引及实际内容→将目标自有说明迁入正常知识文件→把格式改到当前可解析形态（已有合法正文保持）→更新 manifest 激活清单和相关引用→删除原索引→通过现有知识加载路径复核。未选的业务能力保留原有合法内容和原有登记；未登记的仍可读，不在迁移时自动标成已适配。

| 机制与知识的实际状态 | 模型交回与下一步 |
|---|---|
| 机制未装成功 | 沿 adapt-scan 的具体失败修机制，知识编辑尚未开始 |
| 机制成功、仍激活旧 index，用户同意基础迁移 | 执行上述迁移后核可读，再做已选业务适配 |
| 机制成功、用户暂缓基础迁移 | 明确“机制已安装，知识格式迁移待办，依赖该知识的阶段当前不能完成加载”；保留现场和原文件，等待该项授权，不自动回滚或宣称升级可用 |
| 协议迁移成功，部分能力留待以后 | 已有合法知识正常消费；待办的业务影响按 §6 判断，不因版本差异整体阻断 |
| 协议迁移中断 | 从实际文件重新识别；优先恢复激活清单引用的可读性，再完成既定迁移；已完成内容保持 |

机制 --check 与知识可读性分开报告。旧 index 分支退出后遇到 index 给明确迁移提示，用户可找到方法页；空激活清单保持正常，已激活但缺失的文件按具体错误处理。

Demo 同步迁移四份 README、自有 manifest 和入口引用；kind:index 的解析分支与输出 consumers 随迁移退出。保留通用的缺失错误，不能通过跳过未识别 kind 使旧文件悄悄消失。

全仓核消费者：knowledge.mjs 的 indexes、knowledge-use 的 schema/任务骨架、spec/plan author、pre_verifier、各阶段 author.md、adapt Skill、manifest 注释、使用指南和旧 README 链接。逐处替换为当前协议入口或真实内容来源；历史 release 和测试历史原件不改写。现行 1.9.5 内网指南保留历史意义，新 1.9.6 指南引用新协议和方法。

## 6. 加载器与阶段任务实现

knowledge.mjs 保持 activeKnowledge 返回 facts/constraints/patterns、entries、prefixes、patternIds 等现有业务字段；退出 indexes。用现有 parseYaml 仅解析新元数据，并保留原字段解析行为，避免为改 frontmatter 顺带重写整个解析器。格式错误一次汇总；metadata 错误带文件、字段与修法。

### activeKnowledge 的返回合同

现有 facts/constraints/patterns 的对象内容保持，增加一个顶层 declarations，按 manifest 的激活文件顺序逐份输出。唯一字段命名如下，不再使用 bindings 或 decisions 别名：

```js
{
  facts: [...], constraints: [...], patterns: [...],
  entries: [...], prefixes: [...], patternIds: [...],
  declarations: [{
    file: 'knowledge/facts/project-services.md',
    protocol: 1,
    capabilities: [{ id: 'sample-service', revision: 1, covers: ['identity'] }],
    capability_decisions: []
  }]
}
```

file 与现有文件对象同为相对扩展根的路径。protocol 未声明时返回 null，两个列表未声明时返回 []；metadata 缺失不会丢掉该文件的正常 facts/constraints/patterns 输出。空激活清单返回现有各空集合加 declarations:[]。

不生成 satisfied、coverage_percent 或 needs_upgrade 等语义结论。模型对照完整能力要求和真实内容决定下一步。

### 解析与错误处理

在 activeKnowledge 已经读取每份文件的位置调用本文件内的 parseDeclaration(rel, frontmatterText, bad)，复用 splitFrontmatter 与 parseYaml；返回上面的单文件声明对象。原有 frontmatterPairs 保留给 name、kind、pattern roles 等现行字段使用，登记解析不改动这些字段的既有含义。

| 输入字段 | 结构检查及结果 |
|---|---|
| protocol | 缺席→null；显式值须为当前支持的整数1。其他值报读写协议不兼容 |
| capabilities | 缺席→[]；存在须为数组，每项有非空字符串 id、正整数 revision、非空字符串数组 covers |
| capabilities 的同文件重复 id | 报文件及重复 id，由模型合并实际覆盖面；不同文件相同 id 合法 |
| capability_decisions | 缺席→[]；每项 id/revision、scope、decision、reason、basis 按 §3 类型；deferred 另须非空 impact |
| scope | 非空字符串数组；单独 ['*'] 表示整项；与其他面混写报结构错误 |
| 未登记在包台账的 id、面 | 原样返回，由模型判断目标自有或拼写/语义问题 |
| YAML 不能解析、显式字段类型错误 | 向 bad 追加“文件 + 字段 + 实际问题 + 正确结构”，该文件其他错误能读到的继续收集 |

显式不兼容协议、非法 kind、已激活文件读取失败和现有条目错误进入同一个 bad 汇总，最终沿 KnowledgeError 抛出；单个文件读不到时继续核其他可读文件。函数在有错误时不返回看似完整的部分知识对象。顶层 manifest 不可读时无法枚举文件，直接报该前置错误。保留原条目/角色/编号校验，不扩大为业务内容检查。

parseDeclaration 是 activeKnowledge 的内部实现细节，消费者只使用 declarations；不会为它增加独立命令。revision 大于或小于包条目的值都作为原始事实交给模型，加载器只核数字类型。

### 作者与审查怎样取得信息

在 knowledge.mjs 导出一个小型纯渲染函数 declarationContext(projectRoot, knowledge)，给既有 spec/plan author 与 pre_verifier 共用，返回 Markdown 行数组：当前 protocol.md 与 capabilities.md 的实际路径；每份声明的 file、protocol、capabilities、capability_decisions。使用 extensionRoot 与 relDisplay，登记内容以 YAML 围栏完整输出，空清单如实说明。该函数只渲染已有对象，不读取代码或推导能力差异。

- spec/author.mjs：knowledgeSection 的 activeKnowledge 成功后，在现有文件入口与知识判断说明之间插入这段。空知识分支也给协议/台账入口，让模型按本需求判断是否需要取证；不创建空 knowledge-use 来装登记。
- plan/author.mjs：knowledgeSection 同样插入；承接 Spec 已判定的业务义务，再按实现所需字段读取相应知识。下游需要的值仍缺依据时提出精确待决。
- pre_verifier.mjs：activeKnowledge 成功后，在知识审查片段正文之前加入同一段，使审查者拿到作者使用的登记来源；审查者独立核实际内容。activeKnowledge 失败时保留具体错误，说明哪些检查缺依据，不转述为零条知识或不适用。
- 其他阶段 author.md：在现有知识输入处指向 protocol.md 中本类型规则；沿已定 Spec/Plan 工作。读取清单和生成骨架的现有消费者保持原调用接口，移除 indexes 使用并补 declarations 的空值处理。

protocol.md 的入口顺序是“先读本次用到的类型规则，再读相应已激活知识”；台账只在确认所需能力、修订变化或缺口时展开相关条目。静态提示不重复台账内容，且不按 Demo 的能力名分支。
