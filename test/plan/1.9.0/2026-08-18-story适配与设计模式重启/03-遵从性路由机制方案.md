# 03 · 规约与设计模式的遵从性路由机制方案

> 读者：本方案的评审者与实施者。议题：规约与设计模式数量增长后，如何让模型在需求的
> **合适功能位置、合适阶段**真正应用对应内容，而不是碎片化地全量重读或干脆漏掉。
> 已吸收 [06-Codex-方案检视意见](06-Codex-方案检视意见.md) 的 B2 形态贡献（裁决记录见 00 §6）。

## 1. 问题定义

- 规约已有 6 域，设计模式即将有 2 份且都会增长。「每阶段把所有知识全量读一遍」不可持续：指令密度被稀释，恰是 `test/story/AGENTS.md` §1.0 警告的失效模式。
- 一个需求含多个功能单元，各单元适用的模式/规约不同；同一单元在不同阶段（story-spec-plan-coding-review-ut）关注的维度也不同。
- 需要的不是新知识，而是**路由**：什么单元、什么阶段、读哪份、把结论落在哪、下游怎么无歧义地找回来。

## 2. 事实底座：注入通路的到达性（已核实）

| 通路 | 机理 | 到达谁 | 依据 |
|---|---|---|---|
| lifecycle hook 的 `on_context_load` fragment | harness 收集 → 写 `ai-prompt.md` →「发送给 AI 模型执行**语义验证**」 | **verifier**，不是撰写模型 | `framework/harness/harness-runner.ts:662-676,819,952` |
| spec 阶段撰写模型读到注入件 | `framework/skills/feature/spec/SKILL.md:22` 概述明文点名宿主扩展叠加 → 撰写模型按 SKILL 主动读 | 撰写模型（实跑证实） | spec SKILL.md:22 |
| plan/coding 阶段 | 两份 SKILL.md **零引用** doc/extensions；framework 只读，不能补 | 撰写期**无可靠 hook 通路**，仅 verifier 经 overlay 兜底 | grep 零命中 |

**结论**：spec 是 story 拥有可靠撰写期注入的唯一阶段;plan/coding/review 的撰写期到达必须走
**上游产物**——spec 的产物 plan 必读、plan 的产物 coding 必读（framework 自身的流水线契约），
**登记和指令随产物走**就天然到达。

## 3. 机制：三层路由，登记随产物走

不建新台账、不新增脚本编排（产物即证据的既有纪律）；不侵入 framework 契约资产
（`context/facts.md` 是 framework 的 Code Facts 契约，story 扩展不往里写自定义语义）。

### 3.1 知识层——每份知识自带「何时看我」与稳定身份

- 规约：`constraints/README.md` 适用矩阵（域 × 阶段，已有）；
- 设计模式：`design-patterns/README.md` **路由表**（信号 → `pattern_id`），`pattern_id` 即模式文档
  frontmatter 的 `name`（如 `decision-tree` / `page-interaction`），全链引用同一 id；
  路由信号沿用 framework 已有的 UseCase 复杂度四条件（`framework/skills/reference/plan-workflow-detail.md:44`），不自造判据。

### 3.2 注入层——阶段入口被指到知识（辅通路）

- spec：`story_on_context_load.md` 点名机制（已验证可靠）；
- plan/coding/review：共享指路件（`constraint-application.md` 已挂五阶段；`design-pattern-application.md` 新增挂三阶段）——verifier 一定读到，撰写模型读到与否取决于宿主 CLI 行为，**不依赖它兜正确性**。

### 3.3 产物层——登记与指令随产物走（主通路）

**登记原则：谁有判定权，谁在自己的权威产物里登记；上游登记处同时写明下游的消费义务;
下游读上游产物，不回头读全量知识。**

| 阶段 | 做什么 | 落点与形态 |
|---|---|---|
| **spec** | **识别编排信号,不替 plan 选型**:按功能单元登记「信号/证据/候选 `pattern_id`」,并写明「plan 须按路由表选型并产出模式应用表」的义务 | spec 的**宿主扩展产物**(§9 技术契约同款机制:story 注入件指令 + 模板承载;具体为 §9 后新增小节或功能清单扩展,实施定形态)——story 自己的地盘,首跳由「plan 必读 spec」保证 |
| **plan** | **最终选型**,产出**模式应用表**:每行 `use_case ID / pattern_id / 实例名 / 选型理由 / 知识文件 / contracts 锚点`;零命中显式写「无」,多模式叠加多行;同时完成契约投影(对外可观察状态进 `use-cases.yaml`,内部结构进 `contracts.yaml`——边界见 02 §4) | plan 产物;规约侧沿用既有出口(§7/§9 展开的要求) |
| **coding** | 按应用表读取命中模式的下篇落码 | 源码 + UT(`contracts.yaml` 是只读强契约,harness 已校验文件存在性) |
| **review / ut** | 按同一应用表核对 diff 与使用约定 | 各自报告内的核查结论 |

**三真源边界**（各自只回答一件事，不互相复述）：

| 真源 | 只回答什么 |
|---|---|
| spec 宿主扩展产物的信号登记 | 哪个功能单元出现了什么信号、证据在哪、下游义务是什么 |
| plan 的模式应用表 | 选了哪个 `pattern_id`/实例、为什么、知识与契约锚点在哪 |
| `use-cases.yaml` / `contracts.yaml` | 可观察业务行为 / 具体代码文件与接口，不重复登记选型理由 |

**为什么这就够了**：当年盲测的杠杆结论——模式要落地，杠杆在 plan 把模式展开进契约字段。
规约侧同构：spec 把命中约束展开成 §7/§9 的具体要求，coding 读的是要求不是规约原文。
**遵从性 = 上游把知识翻译成本单元的具体登记，下游只对登记负责**；全量知识只在
「有判定权的那个阶段」被读一次。

### 3.4 阶段 × 内容矩阵（汇总）

| 阶段 | 读知识 | 读登记 | 写登记 | 门禁 |
|---|---|---|---|---|
| spec | 规约矩阵+条目;模式路由表的信号定义（hook 点名，已有通路） | — | §7/§9（规约，已有）+ 信号登记（新增） | post_check + spec overlay |
| plan | 命中模式的上篇（按信号按需读） | spec 信号登记 | 模式应用表 + 契约投影 | `plan_pattern_selection_projected`（查应用表存在与信号一致）+ `plan_constraint_coverage`（已有） |
| coding | 命中模式的下篇（按应用表按需读） | plan 应用表 | 源码+UT | `coding_pattern_invariants_held` + `coding_constraint_landing`（已有） |
| review | 下篇使用约定节 | plan 应用表 + diff | 核查结论 | review overlay 新增核查项 |

## 4. 门禁与看护

- **登记存在性与一致性**：overlay 三条新 semantic_check——信号登记了却无应用表、应用表与信号/契约投影不符、「登记了 `decision-tree` 却手写 if/else 链」均 FAIL；
- **声明↔挂载对齐**：路由表/矩阵声明的每个消费阶段，manifest 必须有对应 hook 或 overlay 挂载（`test_constraint_consumption.py` 纪律延伸至 design-patterns）；
- 全部自带「未走 story 流程 / 无信号登记」的 SKIP 条件,实施时反向验证不恒 SKIP。

## 5. 待实证清单（实施轮）

1. spec 信号登记的形态落定后实跑一次，确认 plan 撰写模型按登记产出应用表（判据：应用表行与信号行可对齐）；
2. 「命中决策树」的全流程案例（test/story 承载，域口径修订见 02 §7）：信号 → 应用表 → 落码 → 核查，四环各自门禁结论；
3. 指路件新增后 `--phase extensions` 校验与六阶段 hook 执行无回归。

## 6. 边界

- 不改 framework；不往 `context/facts.md` 写 story 自定义语义（它是 framework 契约资产）；
- 不用脚本编排模型工作流（路由靠知识元数据 + 产物登记，判断权在模型；脚本只做存在性/一致性机械校验）；
- 不建独立「遵从性台账」文件——同款信息第二处落点就是漂移源。
