> **签名第二条在交付件里不得点名文件**（Step 0 实测）：冻结 04 C12 修订段与本文原写「`knowledge/component-profile.md` 在根」，而该文件名至今仍在激活清单里，写进 `story-adaptation/SKILL.md` 被台账 **M01 判 FAIL**（机制层硬编码知识标识）。改用等价且更准确的结构特征「知识文件平铺在根、没有按类分目录」。维护件（本文与冻结件）不在 M01 扫描面内，原表述留档不改，但交付件一律用结构特征版本。

## 2. 执行 AI 的操作顺序（= `skills/story-adaptation/SKILL.md` 正文，≤ 120 行，示例中性题材，不写具体 hook/知识文件名）

```
0 前置：目标根有 framework/ 与 framework.config.json；framework/package.json.version ≥ 包声明；两处热修文件在位（§5 F7）
1 判态（§1 末）
2 读两棵树：node <包>/skills/story-adaptation/scripts/adapt-scan.mjs --scan --target <目标> → 列清单；你逐文件按 §1 表判
3 写方案 <目标 extension_dir>/adapt/plan.md，四段固定标题：
   一、机制与跳板：新增 / 删除 / 覆盖逐文件；目标本地改动的迁回建议
   二、知识：facts 逐文件 保留 / 移动到 / 补键；包内同名规约与模式换版本清单；目标自加保留清单
   三、待核实：facts 六面、可观测性三渠道、两模式 SDK 与案例——已核实写证据（文件:行），核实不了写证据缺口；包新增字段待填；manifest 与 README 合成说明；三键提议
   四、执行：写入顺序；写完跑哪些校验
4 确认：1=按方案执行  2=修改方案  3=放弃适配（widget + 编号菜单同轮；选 1 后决策复述再动手）
5 写入：机制 → 知识 → 数据对接 → README → manifest → 三键
6 校验：--phase extensions；adapt-scan.mjs --check --target <目标>；任一 FAIL → 照报出的项改，重跑
7 收口：写 adapt/installed.md；报告三态、动作计数、未确认清单与证据缺口、下一步
8 取证顺序（填 facts 用）：目标源码 > 目标配置/依赖 > 目标既有业务案例 > 用户口述；核实不了不写
```

四跳板命令表各加一行 `adapt [<目标工程>]` → 读本 SKILL；`skills/story/SKILL.md` 只加一句指路。

## 3. 辅助脚本 `skills/story-adaptation/scripts/adapt-scan.mjs`（≤ 150 行，零依赖，两个开关）

| 开关 | 做什么 |
|---|---|
| `--scan` | 列两棵树：机制目录逐文件（目标独有 / 包独有 / 同名有差异）、目标 `knowledge/**` 每文件的 frontmatter（首块 `key: value`）与所在目录、`provides.knowledge` 清单、包内 js 是否自述替身；写 `adapt/before.json`：每个目标知识文件的**事实序列**（非空表格单元格与段落按序）+ **自定义文件（目标其它 `skills/*` 与包不认识的文件）的路径与内容指纹**（只记指纹，不记事实序列——它们不参与守恒，只需证明没动过） |
| `--check` | ① 机制目录文件集与内容 == 包；② 目标所有的知识文件（facts + 目标自加规约/模式）旧事实序列仍按序在新文件——**包里有同名的规约/模式不在守恒对象内**（升级时本就换成包的版本；复核 Step 5 修正，此前对全部知识文件核对，内网升级会误报）；③ `provides.knowledge` 无 `confirmed: 未确认` 文件且每条路径存在；④ 自定义文件集与内容指纹 == `before.json`。任一不符 exit 1 点名 |

零字面：不出现 hook / 知识文件名 / 域前缀 / 模式名。替代 2.x 的 `build-release.mjs` + `verify-adaptation.mjs` + `releases/*.json`。

**Step 1 实施登记（与本节的差异，以仓内为准）**：

- **`--backup` / `--restore` 两个开关于 Step 4 整体删除**（用户 2026-08-28 裁定）。
  目标仓的版本管理是执行人的事，adapt 再做一套就是同一职责的第二套实现。
  它们曾在 Step 1–2 制造过四个坑——备份自指（`cpSync` 拒绝复制到自身子目录）、回滚顺序必须先根后目录、
  回滚会抹掉用户确认记录、写入时新增的根文件不被清理——**随能力一起消失，不再登记为待办**。
  交付件里不留任何关于备份与回滚的说明：用一段文档去补一个不提供的能力，仍是打补丁。
- **行数 176（有效约 140），仍未达本节写的「≤ 150 行」的表述口径**（按总行数计）。
  两个开关剩下的都是 `--scan`（两棵树清单 + 事实序列 + 指纹）与 `--check`（四项判据）的必需实现，
  无死代码。不为凑数字挤行删注释（批次 4「< 9000」的教训）。
- **台账扫描面排除 `adapt/`**（`check_failure_modes.py`，常量 `EXCLUDE_KNOWLEDGE` → `NON_MECHANISM_DIRS`）：
  自扫描产物 `before.json` 按定义照录目标工程的知识标识、层名与绝对路径，触发 M01/M03/M04 三条 FAIL。
  工作目录不是机制层，扫它等于把运行产物当交付件判。**这是 M4 的第二面**——我原先只处理了「不入库」，
  而台账扫的是文件系统、不看 git。
