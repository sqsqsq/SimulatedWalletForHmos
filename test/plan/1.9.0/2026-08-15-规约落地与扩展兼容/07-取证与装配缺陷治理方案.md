# W7 取证与装配缺陷治理方案

## 背景

W1–W6 落地后跑第三轮 `split-by-feature`，加上内网实测反馈，暴露出五组问题。它们分散在
规约、脚本与看护三层，但有一条共同的形状：**规则声明了动作，却没定义这个动作的输入与产物**，
于是模型用自己的理解填空，而机械层恰好判不了它填得对不对。

本轮不逐条打补丁，按「缺什么定义就补什么定义、能机械判的下沉到脚本」正向重整。

| 组 | 问题 | 层 |
|---|---|---|
| A | 用户在任务描述里说了拆分，模型判成「无范围指示」 | 规约（取证） |
| B | 跳板缺 `review`；三处规则绑定本工程；「目标无关」无看护 | 规约 + 看护 |
| C | 探针 hook 与 hook-runner 契约冲突 → 门禁 BLOCKER | 脚本（已修）+ 看护 |
| D | 「转写」被理解成写概要；登记表格式错静默变空表 | 规约 + 脚本 |
| E | `initNeeded` 是化石字段 | 契约 |

## A. 范围意图取证：定义输入与产物

### 现象

第三轮 `.positioning.json` 落 `scope_source = sr_related`、`split.decided = "none"`，
而用例 prompt 第三段明写「本次**只做其中一部分**：在范围关卡上按端侧特性把它切开」。

`init_analysis.md` §③ 的四源表**结构是生效的**——模型确实评估了「用户的任务描述」这一行，
写下的结论是：

> 无范围指示（「按 story 技能的规则生成 AR/design.md」未指定拆分）

它引的是 prompt 第一段。**拆分那句在第三段，被概括掉了。**

### 根因

W6 给四源表加了 `user_stated` 这一行，解决的是「有没有这一源」的结构问题。但这一行
只要求给出结论，**没有定义结论从哪来、长什么样**。其余三源天然有物——SR/RR 是文件、
design 预填是文件、兄弟 AR 是查询结果，读了就是读了；唯独任务描述在上下文里，
模型可以「凭印象」作答，而印象是可以丢东西的。

这与 `AGENTS.md` §3「先取证后结论：每条结论必须有可索引证据」同源。任务描述就是证据源，
只是从没被当成证据源对待。

### 方案

把这一行从「给结论」改成「给摘录」，与其余三源同构——都是**有物可核**的判定：

> | **用户的任务描述**（`user_stated`）| **产物是原句摘录，不是概括**：他对本次做多少说过什么，
>   把那句话抄进来；通读全文确无相关表述，写「通读任务描述，无范围表述」。
>   摘录可核对，概括不可核对——这是唯一不在材料里的一源，也是唯一你会凭印象作答的一源 |

配套修 `init_analysis.md` 的 `.positioning.json` 示例：`scope_source` 枚举补 `user_stated`
（W6 改脚本 `SCOPE_SOURCES` 时漏同步文档示例）。

## B. 跳板同步 + 去工程绑定

### B1 三份跳板缺 `review`

W5 给 `story.js` 加了 `review` 子命令，三份跳板（`.claude/commands/story.md`、
`.cac/commands/story.md`、`.opencode/skill/story/SKILL.md`）没同步。

补：用法行、命令转化表（`review <AR>` → 「MCP Token」+「检视」章）、工作流程表
（archive 之后：拉回评审反馈写入 `AR/review.md`，据此修订 spec）。

**同步这件事不该靠人记得**——加机械看护：跳板声明的命令集 == `story.js` 实际分派的命令集，
双向解析、不硬编码清单。此后增删命令忘了同步，测试即红。

### B2 三处规则绑定本工程

`AGENTS.md` §4「目标无关」要求 SKILL.md 与 `rules/` 是通用能力说明，示例不得指向真实目标。
全量排查发现三处违反：

| 位置 | 现状 | 改为 |
|---|---|---|
| `reference/evidence-rules.md:131` | `02-Feature/WalletMain/.../route_map.json` | `<模块目录>/.../route_map.json` |
| `templates/spec-sections.md:56` | 「检索 preferences 于 WalletMain 零命中」 | 「于 `<in_scope 模块>` 零命中」 |
| `rules/scope_gate.md:111` | `AR90098` + 签约入口/扣款对账/运营报表 | `AR900xx` + 中性份描述 |

中性写法照 `init_analysis.md:171` 既有规格（`AR900xx` + 「该份承载什么」），不另创风格。

### B3 补看护

`AGENTS.md` §4 的这条红线此前只写在踩坑表里，没有断言。补：

- 通用规则不得含真实模块名（`WalletMain`/`CommFunc`/`CommUI`/`AccountManager`/`FinancialCard`）、
  工程目录层（`0X-…`）、真实形态单号（`AR9\d{4}`）；
- 范围 `skills/story/{rules,reference,templates,contracts}` + `SKILL.md` + `hooks/spec/`；
- **排除** `mock-data/`（不交付）与 `knowledge/constraints/`（应用专有知识，W2 已裁决
  `WalletLog.*` 就该指真实落点）；
- 只扫标识不扫业务词——「钱包实例扩展」这类标题是合理的；
- 附带：规则里的 `scope_source` 枚举示例与脚本 `SCOPE_SOURCES` 一致（动态取值比对）。

## C. hook 按真实调用形态测

### 现象

第三轮 spec 门禁报：

```
✗ FAIL [MAJOR] lifecycle_hook_on_context_load_extension_error
       hook stdout 非法 JSON：{}{}
```

### 根因

`framework/harness/scripts/hook-runner.mjs` 的契约是：**hook 导出 `default` 函数，
runner 调它、拿返回值、由 runner 负责 `process.stdout.write`**。

W1 新建探针时把它写成了顶层脚本——自己读 stdin、自己 `emit()` 写 stdout。于是模块被
`import` 时写出第一个 `{}`，runner 发现没有 `default` 导出、`out = {}`，又写出第二个 `{}`，
拼成 `{}{}`。

**已修**（改为 `export default`，兼容对象入参与 stdin 两种调用）。

### 看护

离线 414 条全绿没拦住它，因为当时是按顶层脚本形态手工 `echo … | node` 验的——
**验的形态不是真实调用形态**。这与 `test/story/AGENTS.md` 踩坑表里「拿离线全绿当行为正确」
同源，但比那条更可测：hook 的调用形态是确定的，不需要跑模型就能验。

新建 `test/story/tests/test_lifecycle_hooks.py`，对 manifest 声明的每个 `.mjs` hook：

1. `import` 后必须有 `default` 函数；
2. **`import` 本身不得产生 stdout**（顶层自 emit 正是本缺陷的形状）；
3. 以最小 ctx 调 `default`：返回单个可 JSON 序列化的对象；
4. 探针三方向（story 场景注入 / 无 `story-flow.json` 让路 / 非 spec 让路）在 default-调用
   形态下重验。

## D. 装配链：转写定义 + 登记表防静默空

### 现象（内网实测）

1. 转写 story 时被理解为「写一段概要源材料」，`story.md` 内容大量缺失；
2. `ids.json` 格式写错导致装配失败，修复时忘了 `decisions.json`，`review.md` 为空。

### 根因

**三层，且串成一条链。**

第一层，**「转写」这个词承担核心动作，却全篇没有定义**。`rules.md` 只说
「`scaffold` 把源材料原样注入章节文件，你在区块之后写转写正文」。模型读成
「写一段概括源材料的正文」是完全自然的理解。

机械层守得住的只有两样——`可标识事实不丢`（编号/术语/技术契约标识）与
`形态守恒`（图表数量不降级）。概要式转写完全可以引用所有编号、图数够，
**门禁全绿而内容大幅缺失**。「独立可读」是 `[你]` 通道，人判，harness 判不了。

第二层，**登记表格式要模型从零创造**。`rules.md` 只说「登记在 `ids.json`」，
没有形状。而 `story-build.mjs` 的读取是：

```js
function readJson(file, fallback) {
  if (!fs.existsSync(file)) return fallback;
  return JSON.parse(stripBom(fs.readFileSync(file, 'utf-8')));
}
const decisions = readJson(ctx.decisionsPath, { decisions: [] }).decisions ?? [];
const ids = readJson(ctx.idsPath, { ids: [] }).ids ?? [];
```

三种坏输入三种坏结局：文件不存在 → 静默空表；JSON 语法错 → 抛裸异常，不指向修法；
**JSON 合法但结构不对**（顶层是数组、键名写错）→ `?? []` **静默降级成空表**。
第三种最坏——它违反 `story-build.mjs` 自己在头注声明的不变量
「失败模式只有装配失败，不会静默改写作者内容」。

而且有 `validateDecisions`，**没有 `validateIds`**。

第三层，**空表是缺省而不是决定**。`decisions = []` 时 `renderReview` 照常渲染出只有
页眉页脚的 `review.md`，build 成功退出。

**链路**：概要式转写 → 正文没有 `{{DEC-00X}}` 引用 → 悬空引用检查无从触发
（它只拦「引用了但没登记」，拦不住「压根没引用」）→ 空 `decisions.json` 不报错 →
`review.md` 空 → **全绿交付**。所以问题 1 一旦发生，问题 2 必然跟着发生且无人发现。

这是同一个病第三次出现：W1 记过 scaffold「脚本不崩，反而『成功』造空壳」，
本轮的概要式转写与空登记表是它的第二、第三个实例。按 `AGENTS.md` §7
「同类问题第二次出现时停止局部修补」，本轮做跨层裁决而非继续试改。

### 方案

按项目红线「确定性的工作由脚本完成；思考与推理由模型完成」分层。

**D1 「转写」给出判据式定义**（`rules/rules.md` 红线 1 内）

> **转写 = 源材料的完整改写，不是概要。** 判据：源块里的每个事实点（数据、条件、分支、
> 约束、名词）在正文都有落点——可整合、可改序、可换措辞，但删掉源块后正文单独成立、
> 事实一个不少。写成「本章讲了 X 的概况」即为未转写。

不加机械的内容比例判据——那是语义判断，归评价者与 S2/S6 语义层。

**D2 结构由脚本立**

`scaffold` 本来就负责按合同立结构，让它同时生成两份登记表骨架
（`{"decisions": []}` / `{"ids": []}`，带字段说明注释）。

这一步把失败模式从「模型创造格式失败」变成「模型破坏既有结构」——
前者只能靠文档祈祷，后者可机械拦。

**D3 读取恢复「永不静默降级」**

- `readJson` 语法错报**带文件名与修法**的错，不抛裸异常；
- 补 `validateIds`（对照 `validateDecisions` 范式）：结构不对时**大声失败**并给出正确形状，
  不再 `?? []` 静默变空；`validateDecisions` 同样堵住「结构不对 → 静默空」。

**D4 空是决定，不是缺省**

`decisions` 为 0 条时 build 失败，出口是显式声明：

```json
{ "decisions": [], "none_reason": "<为什么这个需求没有任何开放点与须遵守的上游结论>" }
```

`none_reason` 存在才放行，并在 build 输出里醒目打印。`ids` 同理。

沿用 `story_flow.py` 既有哲学——「『没有』和『没查』是两件事」。

**D5 规则补格式示例**

`rules.md` 红线 3/4 处各补一个几行的 json 示例（中性内容）。

### 链路守护对照

| 环节 | 由谁堵 |
|---|---|
| 概要式转写 | D1 定义 |
| 正文无 `{{DEC-00X}}` 引用 | 既有悬空引用检查（覆盖「引用了没登记」）+ D1 |
| 登记表格式错 | D2 骨架 + D3 校验 |
| 空表静默通过 | D4 显式声明 |

## E. 删 `initNeeded`

### 现状

`story.js` 恒发 `initNeeded: true`，`SKILL.md` 只有 `=== true` 一条分支，没有 false 分支。
它原本表达的「要不要初始化 `AR/design.md`」这个判断，职责已被流程接管：

- S4 恒重新生成 `design.md`（`story.js:241` 只在文件不存在时铺空模板，不覆盖已有内容）；
- 已有内容作为 S2b 的预填输入参与分析，不是跳过分析的理由；
- 覆盖前向用户确认由关卡机制承担。

即：**不管拉取到什么，都进入后续需求分析**——这正是当前流程的设计，而 `initNeeded`
是它上一版语义的化石。留着它反而暗示存在「不必分析」的分支，而那个分支并不存在。

### 方案

- `story.js`：docstring init 行删该字段；`emit` 不再输出；
- `SKILL.md:62` 契约示例删字段；`:92` 触发条件改为「init 成功（`success === true`）→
  按固定链条走完四步」；
- 契约测试若断言 init 键集合，同步；
- `export_delivery_patch.py` 的 CAVEATS 补一句：内网现有实现若仍输出 `initNeeded`，
  该字段已不再被消费，忽略即可、无需改内网代码。
