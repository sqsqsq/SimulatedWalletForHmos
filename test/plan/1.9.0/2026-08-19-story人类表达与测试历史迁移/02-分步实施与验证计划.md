# Story 人类表达与工程知识真实生效：分步实施与验证计划

> 日期：2026-08-19  
> 状态：方案已定稿，待用户确认，尚未实施  
> 上位设计：[目标架构与正向优化方案](01-目标架构与正向优化方案.md)

本文件是本轮唯一执行计划。实施按“责任层建设 → 离线验证 → 全量回归 → 正式 CLI → 测试报告”的顺序推进，每一步通过完成门后再进入下一步。

## 1. 执行原则

1. `framework/**` 在实施前后保持字节一致，能力建设落在实例扩展和测试域；
2. 每项能力只有一个真源和一条运行路径；
3. 机械检查验证结构、路径、ID、装配和事务，语义评价验证人读质量、模式适用性和知识实际影响；
4. 当前工作树中的用户修改先记录、后保护，正式 Coding 测试通过源码事务恢复；
5. 离线正反例和回归通过后启动正式 CLI；
6. 正式 CLI 的终点是测试报告，报告中的问题进入下一次用户确认。

## 2. 实施范围

| 能力 | 主要落点 | 验证重点 |
|---|---|---|
| Story 人读模型 | `doc/extensions/skills/story/**`、`doc/extensions/hooks/spec/story/**` | 标题、子章节、表达、内容守恒、图片、Review 边界 |
| Spec 规约与候选信号 | `doc/extensions/hooks/spec/**`、Story 的 Spec 扩展模板、`spec-rules.overlay.yaml` | 命中规约进入规格；模式保留业务单元与候选事实 |
| Plan 知识应用 | `doc/extensions/hooks/plan/**`、共享知识 hook、`plan-rules.overlay.yaml` | 独立选型、主体设计影响、契约冻结与一致性 |
| 下游知识消费 | 共享 hook、coding/review/ut/testing overlays | 同一冻结结果按阶段落地、审查和验证 |
| 模式与规约知识 | `doc/extensions/knowledge/**`、`doc/extensions/ADAPTATION.md` | 运行期知识纯度、内网适配任务链与证据 |
| 实例注册与配置 | `doc/extensions/manifest.yaml`、必要的 `framework.config.json` 实例字段 | canonical event、有效路径、UI Kit 目标 |
| 测试控制器 | `test/story/scripts/run_case.py`、配置和单元测试 | 历史迁移、两分钟观测、源码事务终态 |
| 正式评测 | `test/story/cases/**`、case truth、`output/story/evaluation/**` | 自然正例、自然负例、完整证据与报告 |

`test/story/truth/达标判据.md` 继续作为 Story/Spec 人工评价标准；具体模式命中预期记录在 case truth 中，并与被测模型输入隔离。

### 3.1 动作

1. 记录当前工作树状态、相关文件摘要和上一轮正式 run 的证据索引；
2. 记录 `framework/**` 指纹；
3. 列出当前 Story、knowledge、hook、overlay、manifest 和测试控制器的实际入口；
4. 将目标能力逐项映射到唯一文件责任；
5. 按目标结构整理 `manifest.yaml`，每个注册项使用 canonical event，并指向唯一存在的职责文件；
6. 为后续步骤建立回归命令清单和原有功能保护清单。

### 3.2 完成门

- 每项目标能力有唯一责任文件；
- manifest 注册与实际文件一一对应；
- Story Skill 与各 framework 原生阶段 Skill 的职责边界清晰；
- framework 基线指纹和用户工作树基线已保存。

## 4. 步骤 1：建立 Story 人读生成流程

### 4.1 章节与写作合同

按目标架构整理 Story 章节合同和写作规则：

- `contracts/story-chapters.json` 定义八章正文、三个附录、各章职责和输入归属；
- `reader_question` 作为隐藏写作提示，最终标题由业务语义形成；
- 模型先建立每章标题树，再逐章成文；
- H3/H4 根据页面、场景、状态域、流程分支、接口组和参与方自然拆分；
- 表格、列表、时序图、流程图、状态图和强调块按信息关系选用；
- `story-build.mjs` 与 `merge-story.mjs` 负责章节顺序、标题层级、source block、资产路径和装配一致性。

### 4.2 内容守恒与 Spec 对账

每章 source block 保留本轮原始材料，编辑过程采用“原始材料分章 → 标题树 → 逐章成文 → 最终 Spec 人读信息对账 → 全文语义审视 → 局部修订”。

语义审视逐项覆盖：

- 完整用户旅程与参与方协作；
- 前后 AR/SR 的依赖与阻塞关系；
- 页面信息、按钮状态、隐私说明和结果页下一步；
- 空态、异常、超时、恢复和失败边界；
- 接口、数据和上下文边界；
- 有来源的数值和待决策数值；
- 最终 Spec 中影响人理解和评审的需求事实。

当前原始材料、最终 Spec 和已登记决策是内容对账依据。上一轮 Story 作为回归样本，用于发现表达退化和潜在事实流失。

### 4.3 图片与 Review

- Story 装配保留本地图片、替代文本和图注；
- 最终链接以 `AR/story.md` 所在目录解析；
- 路径检查验证目标存在且位于 feature 允许资产范围；
- Story 提供连续需求正文，`AR/review.md` 提供人工审核对象和结论；
- 术语表位于附录 A，正文首次出现时自然解释。

### 4.4 离线验证

机械用例覆盖：

- 八章与三个附录的装配；
- 合法 H3/H4、标题跳级和空标题；
- source block 保留与最终剥离；
- 图片、普通链接、表格、Mermaid 和代码块的往返；
- 图片目标缺失、越出 feature 资产范围和装配后断链；
- Story 与需求 Review 的读写、归档和恢复。

语义样例至少覆盖 `first-release` 与 `cross-component-rich`：

- 标题符合正常需求文档习惯；
- 读者能够理解背景、价值、范围、方案、场景、体验、系统边界、风险和验收；
- H3/H4 拆分符合真实内容；
- 独有事实有自然落点，语义重复得到归并；
- 异常场景以用户表现、系统处理和验收重点表达；
- 数值与已登记依据一致；
- 最终 Spec 的人读事实在 Story 或需求 Review 中可找到。

### 4.5 完成门

Story 机械测试全部通过，两个人读样例均达到 `test/story/truth/达标判据.md`，本地图片链路具备正反例证据。

## 5. 步骤 2：建立 Spec 信号与 Plan 实际应用

### 5.1 Spec 扩展合同

Spec 扩展形成两类结果：

1. 实际命中的规约转换为实现要求、技术契约、异常、非功能或验收语义，并保留 `rule_id`；
2. 流程段、页面和关键组件形成唯一适用单元，记录动作、状态、等待、自动后继、失败、恢复、候选 `pattern_id` 或“无候选”，以及需求证据。

Spec post-check 校验章节、表头、单元名称唯一性、候选 ID 和证据字段。Spec verifier 评价规约要求与候选事实是否忠于需求。

### 5.2 Plan 阶段指令

重建 `doc/extensions/hooks/plan/on_context_load.md` 的执行顺序：

1. 独立重建适用单元与规约域；
2. 读取路由表和候选模式的 Plan 部分；
3. 形成采用、拒绝和规约义务；
4. 以知识结论设计主体结构和正式契约；
5. 深入设计后复核单元、证据与结论；
6. 生成工程知识决策区和 `project_knowledge`。

### 5.3 Plan 原生产物

Plan 主体形成：

- 模式实例、角色、文件、接口、上下文所有权、动作或节点、等待点、失败收敛、SDK 依赖和组合边界；
- 规约驱动的数据、接口、资源、配置、兼容、隐私、异常、幂等、性能和验证设计；
- acceptance/use-cases 中可观察的状态、事件、分支、恢复和失败；
- contracts 中真实的内部结构和实现义务。

工程知识决策区按“适用单元 + 候选模式”逐项记录事实、结论、理由和主体锚点；应用域约束按约束域记录命中规则、设计义务、实现锚点和验证锚点。`project_knowledge` 冻结采用项与命中项。

### 5.4 Plan 确定性检查

按目标合同整理 `hooks/plan/post_check.mjs`：

- 校验 Spec 显式适用单元的覆盖；
- 校验候选 ID 和规则 ID；
- 校验采用项与 `pattern_applications`、命中规约与 `constraint_obligations` 的一致性；
- 校验 contracts、acceptance 和 use-case 锚点；
- 校验项目根相对路径；
- 校验 Plan 声明的既有资源定义文件；
- 校验实例配置中的唯一 `paths.ui_kit_target_dir`；
- 接受正向命中、部分命中和逐单元零命中三类结构。

### 5.5 Plan 语义评价

Plan verifier 独立完成：

1. 从 Spec 事实和 Plan 主体列出流程段、页面和组件；
2. 根据动作、状态、等待点、后继、分支、失败和恢复重建候选；
3. 对照模式完整 Plan 判据评价采用或拒绝；
4. 检查模式是否改变主体设计和正式契约；
5. 检查规约是否形成需求化设计义务；
6. 检查主体、决策区、contracts、acceptance 和 use-cases 的一致性。

### 5.6 离线正反例

| 样例 | 预期结果 |
|---|---|
| 页面包含多个等待点，业务结果驱动下一动作 | `page-interaction` 改变动作、等待和恢复设计 |
| 多个业务分支各自包含多步云调用与补偿 | `decision-tree` 改变节点、上下文和失败收敛设计 |
| 两类事实自然组合 | 两个模式分别形成实例与交接关系 |
| 独立按钮或一两步线性分支 | 各真实单元形成有证据的拒绝结论 |

规约样例覆盖实际命中、域相关但具体规则零命中、完全不相关三种需求。每个样例同时断言 Plan 主体、决策区和机器契约。

### 5.7 完成门

Spec 与 Plan 的机械用例全部通过；四类模式样例和三类规约样例均通过独立语义评价；Plan 原生架构、文件、接口、use-case 和 visual parity 门禁保持通过。

## 6. 步骤 3：建立下游消费闭环

### 6.1 生命周期 hook

共享知识 hook 按阶段路由：

- Plan 读取适用判断和设计投影；
- Coding 按冻结实例读取 Coding 约定并落实；
- Review 按同一实例读取 Review 约定并审查；
- UT/Testing 按验证锚点读取可观察行为要求。

各知识文件描述阶段事实与约束，各 phase hook 描述当前产物中的写入位置和执行动作。

### 6.2 phase overlays

每个阶段注册一项规约语义检查和一项模式语义检查：

| 阶段 | 规约检查 | 模式检查 |
|---|---|---|
| Coding | 冻结义务在真实 diff 中有实现落点 | 冻结实例的角色、结构和行为已经实现 |
| Review | 逐义务审查真实 diff 并定位责任层 | 逐实例审查使用约定和反模式 |
| UT | 将可观察锚点转成场景和断言 | 覆盖分支、等待、恢复和失败行为 |
| Testing | 形成设备和环境层证据 | 覆盖真机交互和端到端行为 |

每项检查输出 `PASS`、`FAIL` 或 `SKIP`。Plan 合法零命中时，对应检查以 `SKIP` 引用逐单元结论；冻结实例和义务进入实质检查。

### 6.3 Plan 层纠错

下游发现 Plan 设计或冻结结果与阶段事实矛盾时：

1. 当前语义检查以 `FAIL` 保存矛盾证据；
2. 报告记录 `correction.layer=plan`；
3. 主流程使用 framework correction 流程完成修正三问与用户确认；
4. Plan 真源修正后运行 `--correction-check`；
5. Plan 与已闭环下游重验通过后，按正常阶段授权继续。

### 6.4 Coding 逐文件诊断

正式 Coding case 选择已知具备 `ReadLints` 或等价单文件诊断能力的 CLI/profile。测试证据核对每个文件的写入与诊断顺序，最终 Harness 核对全量构建、架构、scope、资源和契约。

### 6.5 离线验证与完成门

使用合成 contracts、acceptance/use-cases 和 diff 验证：

- 冻结实例能够路由到对应阶段知识；
- 规约义务能够解析实现锚点和验证锚点；
- 合法零命中输出带证据的 `SKIP`；
- 冻结结果与阶段事实矛盾时输出 `FAIL` 并定位 Plan；
- Coding、Review、UT、Testing overlay 都符合 verifier 协议；
- manifest 只注册实际使用的 hook 和 overlay。

## 8. 步骤 5：建立 CLI 测试控制器

### 8.1 历史产物迁移

在 `test/story/config/test.yaml` 增加：

```yaml
feature_history:
  backup_root: 'E:\Project\bak'
  action_on_new_chain: move
  timestamp_format: '%Y%m%d-%H%M%S'
```

`run_case.py` 使用 case 既有 `start_phase`：

1. `start_phase == story` 时识别为新链；
2. 解析当前仓根、feature 源目录和备份目标绝对路径；
3. 将存在的 `doc/features/<feature>` 移动到 `<backup_root>/<feature>-<timestamp>`；
4. 目标重名时追加 run-id；
5. 记录源、目标、时间和结果到 run 元数据；
6. `start_phase != story` 时直接继续当前工作区的阶段链。

迁移范围始终是当前 case 的单个 feature 目录。备份产物留在 `E:\Project\bak`，本轮链的新产物留在仓内供下游阶段消费。

### 8.2 观测与非沙箱运行

- 外部观测间隔配置为 120 秒；
- worker 心跳、软超时和进程监测采用各自配置；
- 正式 case 使用非沙箱模式，run 元数据保存启动参数；
- 观察日志记录新事件、状态变化和终态摘要。

### 8.3 源码事务

`run_case.py` 统一自然完成、Harness 失败、软超时和 stop 的收口：

- 单一 finalize 写入 run 最终状态；
- stop 记录停止意图并进入 finalize；
- restore 串行、幂等执行；
- finalize 先完成 restore，再由恢复事实派生 execution、pipeline 和 run 状态；
- `pre_digest`、`restored_digest` 与新增文件清单形成恢复凭证；
- 恢复异常保存错误与人工重试入口。

### 8.4 离线验证与完成门

状态和文件系统用例覆盖：

- 新链迁移、续跑保留、源目录为空、目标重名和路径边界；
- 自然完成、Harness FAIL、软超时、外部 stop、重复 stop；
- restore 首次异常后的人工重试；
- 恢复摘要相等和新增文件清理；
- 两分钟观测配置与独立 worker 心跳；
- `E:\Project\bak` 中历史产物持续保留。

全部用例通过后，测试控制器进入正式 CLI 使用。

## 9. 步骤 6：全量回归与原有功能保护

### 9.1 回归集合

1. Story init、build、merge、import、archive、restore、review 和 help；
2. Story 路径、章节模板、图片与 Markdown 往返；
3. knowledge purity、constraint consumption、design patterns 和 adaptation guide；
4. Spec shape、lifecycle hooks、Plan post-check 与各 phase overlay；
5. `test/story` case、Harness、观察、报告、历史迁移和源码事务；
6. framework 提供的实例扩展完整性检查；
7. 应用工程原生只读 lint/build 前置检查。

### 9.2 完整性审视

回归报告逐项确认：

- Story 只有一个最终真源，需求 Review 只有一个人工决策真源；
- Plan 只有一组知识选择结果，contracts 只有一组下游冻结义务；
- 各阶段沿用 framework 原生 Skills；
- 脚本职责保持在确定性事实；
- manifest 中每个 hook 都有实际阶段职责；
- 每个需求只处理实际涉及的规则、模式和章节；
- case truth 与被测输入保持隔离；
- framework 前后指纹一致；
- 应用业务源码与无关用户修改保持基线状态。

### 9.3 完成门

全量离线回归通过，语义样例通过，framework 指纹一致，应用工程基线完整，正式 CLI 输入和 case truth 完成独立审视。

## 10. 步骤 7：正式 CLI 验证

正式 CLI 使用非沙箱模式，外部观测间隔为两分钟。每条新链先执行当前 feature 的历史迁移，同链阶段连续消费当前工作区产物。

### 10.1 主正例：自然命中两个模式并包含图片

测试输入围绕挂失与补卡的完整用户目标设计：

- 同一主流程依据卡状态、风险判断、身份核验和外部系统结果进入多个有独立业务价值的处置链；
- 关键处置链包含查询、冻结或登记、补卡资格与费用处理、申请提交、状态落地，以及失败恢复、补偿或人工接管；
- 核心页面包含登录/实名、资格等待、风险确认、费用确认、提交等待、失败恢复和结果动作，下一动作由业务结果决定；
- 原始材料包含一张与页面或流程有关的仓内本地图片；
- 业务规则自然触发本轮需要观测的应用域规约。

被测模型可见输入只描述业务事实、用户体验、系统行为和验收结果。两个模式的预期命中、规约预期和图片校验点记录在 case truth。

按 Story → Spec → Plan → Coding → Review 推进：

1. Story：评价专业标题、H3/H4、Markdown、内容守恒、Review 边界和最终图片链接；
2. Spec：评价规约是否改变规格，业务单元与候选事实是否完整；
3. Plan：评价两个模式是否独立命中并改变主体设计、contracts 和 use-cases，规约是否形成设计义务；
4. Coding：评价同一冻结结果是否落到真实代码、资源和配置，逐文件诊断与构建是否完成；
5. Review：评价同一模式实例、规约义务、SDK 约定和反模式是否得到真实审查。

### 10.2 自然负例

使用只有独立按钮、线性处理或一两步简单分支的业务需求，运行 Story → Spec → Plan：

- Spec 保留真实业务单元和事实；
- Plan 为每个单元形成有证据的候选或拒绝结论；
- 主体设计保持与业务复杂度相称；
- 合法零命中完成机械检查和语义评价。

### 10.3 UT 与 Testing 合同验证

本轮通过离线样例验证 UT/Testing 能从同一 `project_knowledge` 和验证锚点取得阶段输入，并形成合规的 `PASS/FAIL/SKIP` 检查结果。真实业务 UT 与真机测试由内网后续执行。

### 10.4 证据与报告

每个 run 保存：

- 输入、case truth 和被测版本指纹；
- 事件流与阶段产物；
- Harness、verifier 和 receipt；
- 源码事务与历史迁移证据；
- Story 人读、内容守恒、图片、规约和模式的语义评价。

正式报告按“现象 → 证据 → 责任层 → 原始诉求达成情况 → 后续建议”成文。报告落盘即结束本轮执行。
