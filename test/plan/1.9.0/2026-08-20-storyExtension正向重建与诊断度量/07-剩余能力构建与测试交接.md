## 5. 多 Case CLI

### 5.1 复用现有 runner

多 Case CLI 是 `test/story/scripts/run_case.py` 的协调层，不是新的 Story runner。必须继续复用现有能力：

- 每次执行的不可变 run 目录与 active/latest 指针；
- worker heartbeat 和 lease；
- Story/Spec/Plan 的阶段门禁、phase result、Trace 和回执；
- Coding 源码事务、最终恢复和 `source_restore_failed`；
- `poll/status/reply/stop`；
- 机械检查、独立语义回执和 `finalize_evaluation.py`；
- `report_data.json`、原始日志和失败证据保留。

协调层只负责选择 Case、排队、启动、轮询、交互状态暴露和汇总，不复制 runner 内部状态，不发明另一套 Case schema，也不修改 `framework/`。

### 5.2 并行边界

| 情况 | 是否允许并行 | 条件 |
|---|---|---|
| 不同 feature 的 Story、Spec、Plan | 条件允许 | feature 工作区、run 目录、CLI/XDG 目录和阶段状态真正隔离 |
| 同一 feature 的任意 Case | 不允许 | 可能读写相同 feature 产物和生命周期状态 |
| 任何执行区间包含 Coding | 不允许 | runner 使用共享仓库源码事务，必须串行 |
| 共用 Framework 当前阶段状态 | 不允许直接并行 | `framework/harness/state/.current-phase.json` 是全局单槽；协调器必须串行安排相关 phase，或先证明运行时已经被正确隔离 |

不能仅因为需求编号不同就假定可以并行。并行资格必须由 feature、阶段区间、工作区和共享状态共同判定；判断不清时串行。

### 5.3 最小功能

- 输入一组现有 Case ID，按上述规则形成可解释的执行批次。
- 每个 Case 仍由现有单 Case `start/poll/reply/stop` 协议驱动。
- 交互 Case 进入 `awaiting_reply` 时单独暴露，不阻塞其他安全批次，但不得自动代替人回答。
- 汇总只聚合各 Case 已发布的执行、机械、语义和 overall 结论；不得把 `pending` 当 PASS。
- 中止后逐一确认 worker、源码事务和指针终态；任一恢复失败使整批不通过。

三个 `narrative-*` Case 的业务事实集合相同、叙述结构不同。三者都必须通过内容守恒和人读评价，才能证明生产能力没有再次依赖一种标题或写法。

## 7. 建议执行顺序

1. 冻结当前实现为可复现提交或隔离快照，记录 clean 状态和新指纹。
2. 先用一个既有代表性 Story/Spec 单 Case 建立基线，完整观察而不是提前停止。
3. 实现并编译 Demo Logger/VOC/Chart，完成它们自己的故障隔离和导出验证。
4. 选择一个包含 Coding/Review 的既有 Case，串行验证冻结的诊断合同能在真实实现和审查中被消费，结束后确认源码完全恢复。
5. 在单 Case 协议稳定后实现多 Case CLI。
6. 先小批验证调度与隔离，再执行全部 15 个 Case；任何包含 Coding 的 Case 串行。
7. 对每个适用 Story/Review 产物完成独立语义评价并执行 `finalize_evaluation.py`，最后形成汇总报告。

单 Case 仍使用现有命令，例如：

```powershell
python test/story/scripts/run_case.py <case-id> start
python test/story/scripts/run_case.py <case-id> poll --cursor 0 --model-cursor 0 --wait-sec 120
python test/story/scripts/run_case.py <case-id> status
python test/story/scripts/run_case.py <case-id> reply --text "<人工回复>"
python test/story/scripts/finalize_evaluation.py <case-id> output/story/evaluation/<case-id>.json
```

执行细节以 `test/story/TEST.md` 和 `test/story/AGENTS.md` 为准。不得给前台命令套外层超时，也不得把长时间静默当作失败或主动 `stop` 的理由。

## 8. 运行中发现问题时

- 不在运行中提交代码、修改生产合同、Framework 或评分规则。
- 保存原始 run 目录、模型流、gate 输出、phase result、源码事务和环境信息。
- 先判断问题属于生产模板/规约、机械门禁、runner，还是被测模型行为。
- 确认根因后回到对应源头修改，再用新的冻结版本重跑；不得在协调器增加特判来掩盖生产缺陷。
- 任何被测模型读取了 `test/story/AGENTS.md`、`TEST.md`、`EVOLUTION.md`、本目录方案、truth 或旧报告的运行都标记为污染，不得证明无提示能力。
