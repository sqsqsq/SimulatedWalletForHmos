# Step2.3 · Fable评审复核

> 2026-09-10。核对用户提供的Fable意见、当前2.3总方案及01–03、template金样和现有代码。此文是独立判断与收敛建议，不是新增实施合同；本轮未改方案、预算、金样或生产代码。

## 1. 结论

“暂不原样交给独立实施会话”成立。问题既有交接接口未定义，也有协议负担本身尚可减少；不能只把18–22作为附件补上，同时让01/02的核心合同继续摇摆。

但不能把Fable的22条逐条叠加执行。A2与A5按字面同时采用会失去预填所需的章节归属；A3的集合并不能证明内容覆盖；D13会把可调整主落点重新变成硬约束。应先确定一套更小且完整的数据流，再把接口与提示落点写进分册，99交接文件只指向唯一入口。

本次重新审视的是整条链：S4输入输出 → 初筛保留何种判断 → Spec内编排时点 → 当前材料视图 → 成文/恢复 → 登记与审查。没有必要重新讨论已接受的“已知依据明确、内容组织可深化”目标。

## 2. 对全部22项的判断

| 项 | 问题判断 | 建议落法与限制 |
|---|---|---|
| A1 短单元ID、文件级版本 | 方向合理，能减少模型反复抄长摘要 | 可用SR#7，但selection/template必须绑定其依据的文件版本；更新源文件后不能把旧SR#7自动解释为新第7节。版本由脚本记录，不让模型手填 |
| A2 sources预填 | 合理，确定性抄写不应交模型 | 只预填初筛已有的明确暂定归属；其余保持公共候选，不允许脚本凭默认use猜归属 |
| A3 合并处理出口、模板只写变化 | 同意避免重复全量登记，不同意简单集合并 | 必须定义同项覆盖顺序：当前template明确处理覆盖初筛旧处理，未改项才继承；default可参考不能算正文已采用。覆盖表仍不能证明业务完整 |
| A4 暂不做子范围引用 | 建议收窄 | 当前无直接使用证据，可只保留整个内容单元和父级前提，作者在表达时区分语义；不用此轮先建复杂边界裁剪 |
| A5 删除Spec前collect、use默认 | 分两部分判断 | 暂定视图不必先生成，可减少一套产物与防覆盖规则；但默认值只能表示“保留供参考”，不能表示“模型已审且采用”。初筛已识别的章节用途与疑点仍须保存，否则削弱用户初筛诉求 |
| B6 S4只用幂等顺序 | 建议减少额外事务逻辑，有条件 | 保留原AR、候选、最终成功才complete；明确每个写入失败后保留何物及如何安全重试。仅写“幂等”不解决覆盖后指纹尚未更新的半提交，也不能把派生稿再备份成原输入 |
| B7 S4先独立提交 | 建议采纳此实施顺序 | 先用正常S1–S4贯通验证自重开消失且真实材料变化仍能发现，再实施切分与编排；不把两个风险捆在一个提交里 |
| B8 status不跨语言起进程 | 简化方向合理 | Python只负责原阶段状态，complete后指向story-build prepare；细写作步骤由MJS判断。这是对现方案明确设计的调整，不是补一个未写字段 |
| C9 ATX优先，不做setext | 建议收窄实现范围 | 未识别标题仍作为当前大块正文保留，不能因此丢内容；setext不专门分段不等于拒绝整个输入文件 |
| C10 verifier内联Story/template，原件定位 | 基本与当前方案一致 | 原件入口必须包含omit/defer，不只是作者选中集合；单列装配与实际收到的字节。路径可读不证明已读，仍核运行证据 |
| C11 INPUT给related目标路径 | 建议采纳 | 从现有related解析当前Story/草稿位置，不再复制邻章原文；正文草稿不存在时如实指出，不能给一条假可读路径 |
| C12 selection金样 | 建议在合同收敛后补 | 与同批原材料配套，演示正常保留、暂定归属、排除、冲突；不变成必须识别固定数量问题的答案 |
| D13 三样唯一硬约束 | 不按原文采用 | 已定业务约束、工具协议与明确选定结构有相应约束；主落点是可调整编排，不重新立为永久硬门禁。“唯一三样”还会漏掉来源身份、范围、人工区等既有保护 |
| D14 保留无独有信息的细分信号 | 建议采纳 | 与“因为模板未列而省略”并列评价。允许深化不等于鼓励拆节凑数；不设置小节数量阈值 |
| D15 content拆known/open | 暂不建议强制拆字段 | “还需解释的关系”不一定是已有结论，也不一定是需人拍板的open决策。强制二分可能迫使模型填答案或过量造议题；保持现有content明确语义，真实未决仍属decisions，避免重复 |
| D16 复用标题包含匹配 | 复用能力合理，不能盲用第一命中 | 复用规范化和查找，明确零匹配/多匹配结果。两个标题都包含目标时不能任取一个作为结构落点；不另建通用Markdown解析器 |
| D17 不报普通标题差异 | 主体合理 | 自由标题的增删改无需逐项提示/拦截；若改变的是已选structure的实际定位目标，仍需提示同步该声明，不可无条件忽略 |
| E18 预算前置 | 需要明确执行责任，但不是没有提案 | 总方案已有10900峰值/10500完成上限提案，并明确开工前核算。应在协议收敛后由维护者给最终数字、用户确认、维护者登记，再开始受该预算约束的实施；不能由方案作者代签或要求用户亲手编辑YAML |
| E19 四个状态谓词 | 缺口成立，必须按使用时点定义 | 区分可读取、可装配、可登记；“JSON+十章+引用”不足以代替字段类型/唯一性/结构声明检查。Spec可供编排不等于Framework spec阶段已经闭环 |
| E20 时点与提示文件表 | 缺口成立，直接影响任务能否送达 | 明确初筛在S4后、Spec前；after-spec在Spec正文/必要输入形成后、story登记和harness之前。指定现有story-write分节承载任务，spec.md阶段说明路由、author.mjs只给入口，不让实施者另造平行story-plan流程 |
| E21 模块语言与摘要 | 需要定依赖方向，文件名不是最大风险 | 建议core/story-sources.mjs负责索引/视图，story-build负责命令与写作判断，Python保留S4/阶段状态。跨语言SHA算法按同一字节口径做一致性测试；它不等于复制两套业务枚举/切分逻辑 |
| E22 六处合同细节 | 均应明确 | 具体建议见第4节；冻结范围依赖A3最终是否继承selection，不能先脱离数据流拍板 |

## 3. 两个需要纠正的事实表述

**预算不是完全没写。** 总方案第7节已有当前值、增删估算、峰值/完成上限提案和开工前核算。缺的是收敛后的最终执行前置及批准记录，不是需要从零再建预算制度。不能因为余量小，就在协议未定前先请用户批准较大的上限。

**Python调Node不是实施者可能自己发明。** 当前02第5节明确写了status调用prepare --status-only。Fable建议移除这次跨语言调用，我认为有简化价值；应把它作为职责变更统一修改，不作为“补充接口”与旧文本并存。

## 4. 六项细节如何定，才不会再扩一套机制

| 对象 | 建议的明确合同 |
|---|---|
| units.context | 同文件中各祖先章节在首个子章节之前的非空正文范围；不包含标题行、当前单元或兄弟内容。标题路径已在heading，不重复当正文复制。无前导正文则空数组 |
| images.source | 来自已索引MD时可记录其单元；独立提供、未被MD引用的登记图允许null，保留materials身份和说明，不能为过门禁虚构来源小节 |
| 源变化/旧引用 | 明确报告哪份文件版本不同、哪些选择或引用受影响，保留旧文件；短ID不能自动重绑。是否用现有报告输出而不加新状态字段，应随A1一次定清楚 |
| sources为空 | 纯组织或附录投影入口允许空数组并由既有投影真源供数据；sources非空不证明内容正确，空也不能豁免业务事实依据。编排/正文自己新增结论仍回Spec/decisions |
| stdout | sources、collect若保留、skeleton、prepare、chapter统一首屏NEXT/INPUT/RESULT责任。失败仍按是否已写入区分退出语义；不只修prepare一条命令 |
| 金样与确定性夹具 | 可以用配套原材料与索引验证切片、范围、链接和引用解析；期望边界须经独立核对，不自动把手工索引当无错算法。不得把selection/template内容注入真实作者证明语义能力 |
| 冻结与reopen | 冻结/绑定最终稿实际依赖的判断文件。template属于当前写作依据；selection若被继承就仍是有效依赖，若已被独立最终编排替代则只是历史初筛。派生视图可重建，不能与判断文件混为一类。reopen保留草稿与原判断，按真实改动更新，不清空重新来过 |

表中“无sources节”与“未采用材料”不是同一件事；前者可能只是结构入口，后者涉及取舍。若把两者都当空集通过，方案又会滑回字段齐备但业务无依据。

## 5. 状态谓词不应合成一个万能有效性检查

建议交接合同分别列出：

- **可读取**：文件存在、编码/JSON可解析；损坏不是缺席，不自动覆盖。
- **可装配**：固定章ID、key唯一、必需字段类型、明确structures及引用可解析；允许尚未写正文。遗漏来源处理是否拦截要与最终简化后的数据模型一致，不以“已经能解析”冒充完整。
- **可登记**：正文及原门禁达到登记条件，当前有效依据版本一致；结构齐备不代替语义审查。
- **Spec输入可用**：指当前Spec草稿具备被编排读取的实际内容；不能写成“Spec阶段已通过harness”，因为Story仍是该阶段产物。应复用现有必要内容/占位检查界定，不另实现一套完整check-spec，不用字数阈值猜内容质量。
- **源变化**：按明确绑定的文件版本比较，不依赖mtime或短编号是否存在；缺文件与内容变化分别报。

这些定义还需与最终A组数据合同一起落实到命令、失败出口和正反用例，不能只在99文件留一段口头说明。

## 6. 推荐的收敛次序

1. 先定01/02的数据流：保留初筛的真实用途判断，减少暂定视图与重复抄写；短ID必须有文件级绑定；默认可参考不冒充已采用；template覆盖初筛的优先级明确。
2. 同时定S4最小幂等提交和Python/MJS责任分界，去掉无必要跨语言状态查询与通用恢复设计；保留原输入及真实失败语义。
3. 将提示词文件/触发时点、谓词、输出与冻结写入分册，配一份selection样例。99只列当前版本和批准状态。
4. 按收敛后的替换清单重新核预算，由用户确认需要变更的额度后实施。不要先签足空间，再把所有可想象的机制装进去。

不建议当前就交Opus自行选择A组。独立实施者可以决定常规函数内部写法，但不能临场改变来源版本绑定、初筛含义、编排覆盖关系或冻结对象。反过来，也无需把每一行代码预先规定好；交接应锁定职责与可观察行为，保留合理实现空间。
