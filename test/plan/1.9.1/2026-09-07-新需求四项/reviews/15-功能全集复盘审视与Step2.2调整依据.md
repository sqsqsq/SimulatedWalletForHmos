# 功能全集复盘审视与 Step2.2 调整依据

> 2026-09-09；评阅 [功能全集与实现方式的历史证据](../steps/02.2-复盘·功能全集与实现方式的历史证据.md)，承接 reviews/14。对重点主张核当前代码和最新一跑 events；未复算全部历史统计，未修改实现或重写步骤方案。

## 1. 本报告增加了什么有效信息

它把讨论从“提示怎么写”扩到“功能由谁完成、产物由谁消费、缺失时如何处理”。这个角度值得纳入 Step2.2：同一个问题可能发生在取材、模型理解、输出、后续消费或闭环处，不能看到最后一条报错就继续加提示或门禁。

值得继续使用的证据包括：跨阶段遗失约束、修好又改坏、后段只替换字面而没有保住业务事实、不同来源路径定义需要协同、部分缺件分支与适用范围需要区分。它们支持把当前任务材料送到执行动作附近、明确局部修改对象、复用确定性生产能力、验证完整的正常路径。

但报告若干“最可靠/最不可靠”“无人核”“上下文衰减”的结论仍过强，有些与原始记录或代码不符。必须先纠正这些判断，再用于定方案；否则会以可靠性为名新增一批无效强制机制。

## 2. 需要先纠正的证据与推断

### 2.1 run_id 变化不等于上下文归零

直接读取最新一跑的 usage 事件，得到：

| run_id 前缀 | 首个 context_total | 末个 context_total |
|---|---:|---:|
| a536d21e | 14060 | 61605 |
| d1107916 | 61858 | 118814 |
| 62af72b4 | 118980 | 161216 |
| 68b2fc75 | 161613 | 241563 |
| e34f3c84 | 242731 | 465744 |

读数连续增长，没有报告 §4.1 所说的“各段归零重来”。这些 usage 的 session_id 也为空，不能仅凭 run_id 判断会话隔离。该数值仍是上下文代理，不应进一步当成模型实际剩余记忆量。

因此不应按“3–6 段新上下文”的假设设计新的会话切换，也不能直接设一个 250k/350k 自动重启阈值。

### 2.2 第 N 次调用失败率含明显的筛选偏差

第 10 次检查只包含前面未结束且继续调用的运行，容易通过的运行已经退出。25%→100% 不能证明同一批内容越修越糟，更不能仅凭与 harness 的相反曲线就把原因排除到模型能力之外。

“某条具体问题已通过，随后因一次修改重新出现”才是更直接的回归证据；应逐例区分：作者改漏了、真源变化使投影重新生成、规则冲突，还是实际知识遗忘。回归发生在高上下文处不自动证明高上下文导致遗忘。

### 2.3 “探针扫描 0 文件只警告”不是当前真实路径

runProbe 在 readable 为空时返回 ok=false、scanned=0；coding/post_check 先处理 !ok，把它放入 problems，最终阻断。后面的 scanned=0 warning 不能脱离前一个分支推导为可放行路径。

这条应从“已证明 fail-open”的实例中删除；若要讨论其他扫描无覆盖场景，应按它的实际返回路径另核。

### 2.4 零代码读取方不等于零消费者

review_reflow 明确将 review-disposition.json 给人复核及下游 plan 参考；测试驱动 run_case.target_reached 也检查它是否存在。后者只证明存在，不证明处置正确，但已经说明“全仓没有任何代码消费”不准确。

日志可以服务诊断、人可以消费报告、模型可以读取说明文件。应检查它们是否实际进入所需任务，而不是为每份文件补一个程序读取方，否则会产生“写一份日志，再写一个脚本证明日志在”的循环。

同样，bridges 配置由 adapt 消费，不代表生成的宿主入口文件运行时无人使用。应分清配置与其物化产物。

### 2.5 “跨章重复无登记、无发现者”不准确

当前台账有 S04-duplicate-paragraph，observed_by 明确要求按“同一件事在两处完整表述”跨章看；读者审查也有重复相关要求。其 scope_note 仍夹着旧的逐字比较描述，说明台账语义需要同步，但不能因此说该问题从未登记。

当前最重要的事实是：已有发现职责，真实执行没有有效发现。再新增一条同义失效形态不会解决它，应检查原发现者的输入与判断动作。

### 2.6 文件留存与阶段发生不能混为一谈

artifact 目录为空可能来自未捕获、回灌/清理或运行中断。单靠事后文件缺失，不能证明当时阶段没有发生；需结合当时 gate 日志、summary、closure 与捕获记录。09-08-step12 已知是外层 Node 无输出异常退出、模型内闭环通过，不能作为“业务 check 判错却照样交付”的同类证据。

用户在 2026-09-07 已明确结束原四批次交付及批次 5/6 的诊断收敛。历史未达指标可以继续作为优化依据，不应由分析件把已作出的交付裁定改成未交付；是否重开需要新的明确决定。

## 3. 对“前置缺失就放行”按完整链路核，不统一加硬门

报告指出 skipped/缺文件分支，值得审视。但应分四种情况：

| 情形 | 正确责任 |
|---|---|
| 当前需求不适用该能力，例如无 must、非 Story 入口、明确离线结构检查 | 如实不适用，不强迫制造产物 |
| 当前阶段还未到达产物生成时点 | 不在早期拦死正常路径，在该产物真正必需的位置验证 |
| 必需文件由另一道有效门负责存在性，本 hook 只审其内容 | 核完整链路是否已有真实阻断；避免相同缺件每层各加一份规则 |
| 到了消费或交付位置，必需文件缺失且无人承担检查 | 应明确失败或未验证，不把缺失解释为通过；在唯一合适的责任位置修正 |

例如 spec/post_check 跳过尚不存在的 spec.md，注释明确将存在性留给 Framework 原生检查；不能只看这个 hook 的 ok=true 就说整条流程可无 Spec 通过。相反，materials.json 在已经登记的 Story 链中若缺失，不能仅以“无图数据”吞掉其来源核查责任，应查明正常生产与交付的必需条件是否闭合。

无 verifier 时，当前 reader 检查确会返回 NOT_APPLICABLE。这里必须明确当前产品支持策略：未审可以作为某宿主的已披露能力状态，但不能用来完成 Step2.2 依赖独立审查的效果验收，更不能声称该份产物已经语义通过。不要绕过 Framework 的配置政策，也不要把未配置与审查成功混称。

--by human 与非空 basis 也只保证记录格式，不能单独证明真实人工授权。现有交互记录才是判断实际确认的依据，不为此在本步新建防伪签名系统。

## 4. 真源复用：共享对象定义，不强求所有集合相同

来源存在性、图来源和材料指纹服务不同目的，三组来源数量不同不必然是重复设计。需要共享的是“同一份源文件的身份和路径”，各消费者再选择其适用集合。

应核一条真实路径调整后所有相关消费者是否一致；不要为了消除列表差异把 Spec、材料原件、派生物全部塞进同一个指纹或图集合，造成自依赖和新的错误。

状态/schema 定义若跨 Python/MJS 共享，优先用已有合同承载；但这个全局问题不能成为 Step2.2 自动重做全部配置的理由。只把本步真实接触、存在不一致的定义纳入直接清理，其余按所属需求处理。

## 5. Step2.2 应吸收的新增重点

### A. 输入按当前动作刷新，而不是要求模型重读整页

报告关于后段不重读规则的观察值得采纳；它支持在实际写作、登记失败与接续位置提供必要材料，不支持继续把原则页加长。

作者当前任务应同时明确：正在编辑哪个产物、需要参考哪些已写内容、要补什么独有信息、哪些约束这次仍有效。相关输入不再依靠模型记住初始任务包，也不按所有章节重复投放整套材料。沿用现有草稿、章节读取与命令输出，不新增逐事实台账。

### B. 返修从一项已定位的编辑任务开始

错误一次列全，但下一步应指到真正拥有错误的草稿/契约/材料；已能定位时直接修，不反复探索 checker 或重写同一修复计划。若出现规则互斥、脚本异常、必须删除业务事实才能通过，应反馈机制问题，不能继续以删事实换绿。

相同问题再次出现时，核这次是否实际编辑了对应对象、是否被真源投影覆盖、前后验证的是不是同一版；不靠增加重试次数解决。局部验证复用原检查，状态接续来自 next_step，不新增另一套返修状态。

### C. 把正常路径的贯通列为实施验收

每项改动同时检查：合法输入依次完成生产与消费是否会被自己的前置条件拦住；修正相关真源后，下游能否一次得到更新；不适用时是否仍有合法出口。不能只有“造一个坏字段会报错”的负向测试。

Step2.2 应验证实际 chapter→登记→既有 harness/verifier→交付路径；步骤 3 和 5 在各自范围做对应贯通，不把它们的全部协议功能提前塞入 2.2。

### D. 判断重复仍由模型做，但必须改变当前工作任务

不采纳“下游只引用上游就让重复不可能”的保证，也不将所有重复降成 advisory。正文需要自包含，必要重现与多视角解释必须保留。

改变的是生成任务：相关已写正文成为眼前比较对象；后续章补齐尚未解释的信息，不再独立生成完整旅程。统稿直接在稿上完成合并和保留独有信息，结果为实际改动而不是一句“已核无冗余”。独立审查按来源和最终稿核同一关系，不根据作者自评判断。效果依真实产物验证，不能用一个新字段证明模型已经比较。

### E. 继续区分任务需要与方法保证

编号、表头、投影等确定性工作继续由脚本做；图种/分支完整性只对可靠的结构事实作机械检查，不能从模型可改的表行数推导真实参与方总数。severity 按交付影响决定，已经是 BLOCKER 却漏报的问题先修判断任务，不通过批量提级掩盖。

## 6. 新发现的落点，不将 Step2.2 扩成全系统重构

| 发现 | 建议归属 |
|---|---|
| 写前/返修时输入、下一步、局部检查、图和重复的实际任务 | Step2.2 |
| 本步关键材料缺失的生产—消费闭合、正常路径被自有条件拦住 | Step2.2 的直接链路检查 |
| 知识 must、适用性、验法、testing 作者要求和证据传播 | 步骤 3；逐条核实际缺口，不能仅凭少一个 overlay 字段就推定任务完全未送达 |
| 评审表态与处置是否落实、处置记录是否被后续任务使用 | 评审回流职责；与步骤 4 的“发现审核点”区分，需明确范围后再修改 |
| 首次画像是否生成与登记、适配合同符合性 | 步骤 2 或后续适配验收，不让成文检查承担 |
| 广泛状态/schema 统一、通用记录体系替换 | 已单独存放的大型重构需求，不自动加入本轮 |

## 7. 对下一版方案的验收要求

下一版 Step2.2 应能回答：

1. 相比原来，模型此刻实际拿到的材料和被要求提交的结果改变了什么？
2. 一个不读初始长规则、但正常使用既有命令与草稿的模型，是否仍能拿到本次必需要求？
3. 某条问题已经定位时，是否能直接完成一次编辑与相关验证，而不先研究门禁？
4. 正常完成、不适用、缺必需输入、真实规则冲突四种情况，分别由谁处理？
5. 真实产物仍有重复或矛盾时，现有记录能否区分未执行、比较做错、源输入问题或机械误判，而不是再统称模型遗忘？

不需要先追加全局检查矩阵、模型评分器或上下文重启阈值。该复盘可以帮助确定工作重点，但尚不能作为“提示均无效、脚本均可靠”的实验结论。保留报告的强问题意识，修正其事实与统计推断后再驱动方案。
