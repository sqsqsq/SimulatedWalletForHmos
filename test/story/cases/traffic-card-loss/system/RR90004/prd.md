# RR90004 交通卡紧急挂失恢复 — 产品需求

> 需求单号：RR90004。钱包端的申请、恢复与结果查看由 AR90004 承载。

## 1. 业务背景

用户发现实体交通卡遗失时，最关心的是尽快阻止原卡继续使用。现有卡包只能展示卡片，用户遇到账号未验证、
卡片状态冲突或网络中断时，需要离开钱包寻找线下渠道，重新进入后也不知道上一轮处理到了哪里。

本需求提供一条可以中断后继续的在线紧急挂失路径。它既要让正常用户快速完成申请，也要让身份未完成、
卡片状态冲突和提交中断的用户看到明确原因、完成必要操作后回到原来的处理位置。

## 2. 用户、目标与边界

| 用户 | 目标 | 本轮提供 | 不提供 |
|---|---|---|---|
| 已登录并实名的交通卡用户 | 立即提交挂失并确认真实冻结结果 | 资格查询、风险说明、申请提交、结果与恢复入口 | 端侧自行宣称冻结成功 |
| 登录或实名未完成的用户 | 完成身份校验后继续原申请 | 保留脱敏卡片上下文、回跳并重新核验资格 | 新建登录或实名能力 |
| 卡片状态冲突的用户 | 看懂冲突并取得最新状态 | 刷新云侧状态、对比申请上下文、给出继续或客服动作 | 修改卡云审核规则 |

本轮修改钱包主应用的页面、状态与数据协作；复用账号能力的登录实名结果和通用 UI 的基础组件，
不修改账号认证流程、卡云冻结规则、线下客服处理或支付能力。

完整需求还包含 AR90005 承担的补卡费用支付、制卡进度、领取通知和客服交接。本单在云侧确认冻结后
交出 `freezeTicketId` 与最终冻结状态；AR90005 没有有效交接结果不得开始。补卡订单确认前不扣费，支付中断后
从既有订单继续，通知失败不撤销冻结或制卡结果。两单共用的挂失上下文保留到补卡完成或取消：完成后清理，
取消只结束补卡办理，旧卡仍保持冻结。

## 3. 用户旅程

1. 用户从卡包选择“紧急挂失”，页面先查询资格并展示冻结影响、当前卡片状态和数据使用说明；
2. 资格可用时，用户勾选确认并提交。提交前再次核对登录、实名和卡片状态；
3. 身份尚未完成时，页面保留脱敏上下文，调用既有身份能力；成功回跳后重新查询资格并回到确认位置；
4. 卡片状态冲突时，页面先刷新云侧状态，再结合已有申请上下文判断：继续既有申请、重新确认或转客服；
5. 云侧受理时，页面保存申请号摘要并查询一次真实冻结结果；尚在处理则展示可恢复的处理中状态；
6. 网络在查询、提交或结果确认任一步中断时，页面保留最近一次安全检查点；用户重试后从该检查点继续，
   已存在申请时复用原申请，不能重复创建；
7. 最终展示“已冻结”“仍在处理”或“处理失败”。只有云侧明确返回已冻结时才展示成功。

## 4. 产品规则

| 规则 | 结论 |
|---|---|
| 资格检查 | 打开页面、身份回跳和状态冲突恢复时重新查询；页面停留期间不轮询。 |
| 身份恢复 | 只保存脱敏卡片标识、入口和页面检查点；回跳账号不同则清空上下文并重新选择卡片。 |
| 重复提交 | 同一卡片存在处理中申请时复用申请，不再次创建。提交按钮在请求期间不可重复触发。 |
| 状态冲突 | 先刷新云侧状态，再根据既有申请、可申请性和失败原因决定下一步，不用端侧缓存覆盖云侧事实。 |
| 用户等待 | 风险说明、身份校验和冲突确认都需要用户操作；等待期间不能自动越过下一步。 |
| 隐私 | 页面、日志和埋点不出现完整卡号、实名信息、完整申请号或认证参数。 |

## 5. 界面设计

申请页在同一页面内承载资格加载、风险确认、身份回跳恢复、冲突处理、提交中和最终结果。业务返回会决定
下一块内容和可操作项；用户尚未确认风险、尚未完成身份或正在阅读冲突说明时，页面停留等待用户操作。

**界面参考没有随本需求归档**：布局、分段、文案与可读性要求写在产品另行提供的界面原型说明里，
本文只写到上一段为止。做界面相关的判断前请先拿到那份说明，不要凭本节推断页面长什么样。

## 6. 验收意图

| 编号 | 场景 | 预期 |
|---|---|---|
| AC-R1 | 正常用户提交 | 资格、风险说明和确认顺序清楚；只创建一次申请并展示云侧结果。 |
| AC-R2 | 登录或实名未完成 | 完成既有身份流程后回到同一卡片和原检查点，再核验后继续。 |
| AC-R3 | 卡片状态冲突 | 刷新状态后给出继续既有申请、重新确认或客服动作，不误报成功。 |
| AC-R4 | 提交响应丢失 | 重试先查询既有申请，不重复创建；能继续确认冻结结果。 |
| AC-R5 | 查询、提交或结果确认失败 | 每个失败阶段都有可读原因、重试入口和安全停留状态。 |
| AC-R6 | 重复点击 | 请求期间重复点击不产生第二次创建请求。 |
| AC-R7 | 页面销毁后重新进入 | 在有效期内恢复安全检查点；账号变化或上下文失效时清空后重新开始。 |
| AC-R8 | 界面参考可查 | 评审能看到本轮依据的界面参考，且从评审件点得开。 |
| AC-R9 | 交接 | 只有有效 `freezeTicketId` 和最终冻结状态才能进入补卡；责任、顺序与共享上下文生命周期讲得清。 |
| AC-R10 | 支付与通知影响 | 付款前不扣费，支付中断不重复创建订单；通知失败不改变云侧业务结果。 |

## 7. 协同成功口径

| 维度 | 成功口径 |
|---|---|
| 风险控制 | 端侧任何分支都不把“已提交”或缓存状态当作“已冻结”。 |
| 连续体验 | 身份校验、冲突确认和网络恢复后，用户能回到有意义的检查点继续。 |
| 防重 | 响应丢失、重复点击和重新进入都不会创建重复申请。 |
| 数据保护 | 页面、日志、缓存与跨模块参数均使用最小化、脱敏数据。 |
| 可审查 | 正常、身份、冲突、响应丢失和失败路径均能从需求追到实现与验证。 |
| 跨单交付 | 挂失先开放并稳定提供交接结果；补卡联调、支付和通知不反向改变挂失状态真源。 |
