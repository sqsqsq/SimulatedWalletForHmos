# Story / Review 金样 · 效果定义（已定稿）

## 状态

**2026-08-30 定稿**（用户逐轮批注后认可）。`story-金样-AR90004.md` 自此是 story.md 的唯一效果定义：

- 判据从金样正推：金样里不存在的要求不设判据；**任何判据若拦金样，错的是判据**；
- 验收拿金样对照：新产物在信息组织、详略、表达形态与评审可用性上同时做到形似、神似；
- 金样不限制业务内容、字数、表格数、图片数或小节数，实际需求决定需要写什么以及写多少；
- 作者面以金样为范本（作业书可引其节选与形态）。

## 为什么先有金样

四轮机制迭代（1.0 / 批次 2 / 批次 3 / 批次 4 首跑）的判据全部从「病」反推，从不存在「期望的 story.md 长什么样」的具体定义，判据冲突无仲裁源。批次 4 CLI 实跑实证：check 报错逐条教被测模型把 token 抄进附录（倾倒区是门禁亲手教出来的）、23 次 check 循环、失败数 35→11→9→1→6→18 修一轴破另一轴。用户裁定（2026-08-29）：停机制优化，先由维护者手写金样、审到满意，再从金样正推判据。

## 定稿过程中的用户批注（效果口径的一部分，后续判据与作业书从这里取「为什么」）

1. 范围：两特性分工用表格，表前后 1–2 句说明；单元格不许塞成压缩袋（一格 8 个分号短语即病）。
2. 业务方案 / 业务流程 / 功能说明是全篇最详细的部分。
3. 验收按「要验的事」分组（不按来源分「原始 / 本轮 / 通用」——那是工程视角），每个编号独立一行 + 可观察条件。
4. 交付与上线要详细：上线路径、开关与兼容、回退设计（含理由）、交付物（给谁做什么用）、与兄弟单的上线顺序。
5. 附录每节开头一句目的（改动边界 = 给评审判影响面；规约判定 = 合规面没有漏检的回显）。
6. 材料清单用列表不用表格；追溯不铺陈各材料职责。
7. 标题：H1 带单号（`# AR90004 …`）；H2/H3 带编号（`## 1.`、`### 4.1`，附录小节 A.–E.）；小节名用常规业务命名——「两单分工 / 支线一 / 调用纪律 / 跨单节奏」这类自造词、编号式、工程味命名都不行。
8. 恢复类小节内容用「时机 / 方案 / 走向」引导的短段，不写一坨散文。
9. 照抄产品原型的「文案要求」不单独成节——有价值的融进页面区域表。
10. 主叙事零工程标识（字段名、配置键、camelCase 落附录表）；术语表不收空转定义，主叙事反复使用的概念（幂等标识、恢复上下文）必须进术语表。

维护者自查另修 7 处：提交「不可用 / 不出现」两说法统一、已有申请去向对齐、AC-R10 改为本特性侧可观察条件、两处强迫对称与工程视角措辞。

11. （2026-08-30 追加，同日二次修订）材料清单每行带可定位文件信息：来源（需求系统 <单号> / 随归档附件）、《文件名》、提供方与提供方式、内容贡献，**且每行带原始引用文件的相对链接**（`原文：[<仓内相对路径>](<相对 story.md 的路径>)`，形态参照 spec「参考资料」节）——用户裁定：原文链接是唯一允许仓内路径出现的位置，此前「仓内路径不写」的口径就材料清单这一处撤销。
12. （2026-08-30 追加）大标题带需求编号（`# AR90004 …`）是「形」的一部分，模板与判据须一致传递。

## 一个供判据设计引用的实证

金样对内容基线（批次 1 的 AR90004 story）跑 `baseline_coverage.py`：**89 条字面 miss，逐条人核语义均有落点**（少数是金样有意不继承的基线毛病：装置事实泄漏、仓内场景编号）。结论：**逐字命中口径的「不丢」工具会把理想文档判成大量丢失**——语义守恒不能建在逐字比对上。
