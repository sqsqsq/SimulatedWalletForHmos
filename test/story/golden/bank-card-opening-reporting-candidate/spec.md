# 银行卡开卡与结果查询 — 需求规格（Spec，专项节选）

本文件仅摘录现有“技术契约”的埋点小节，其他业务章节不在此重复。业务假设与待核协议见[候选说明](README.md)。

## 9. 技术契约

### 9.4 埋点

项目已提供页面、点击等交互的自动运维上报，本例复用其覆盖，不另加同类手工点位。本例没有产品、SE 明确提出的独立运营指标或事件，因此不新增 BI；下列业务步骤结果用于运维统计，不能用自动页面/点击记录代替。

#### 9.4.1 流程与指标

| 业务流程 | 运维指标 | 需要记录的业务事实 |
|---|---|---|
| 开卡办理 | 开卡成功率、各步骤成功率、步骤耗时和失败原因 | 信息校验、短信验证、人脸核验、写卡及结果获取的实际结果 |
| 开卡结果查询 | 查询成功率、查询耗时和失败原因 | 查询请求的执行结果，以及取得的开卡业务状态 |

按流程分别描述点位。同一流程的记录可用于多个指标，无需为成功率、耗时分别重复打点；指标计算由数据使用层处理。本例不增加跨流程联合指标。

#### 9.4.2 开卡办理

**运维点位**

| 步骤 | 需要区分的统计点 | 适用结果与业务触发条件 |
|---|---|---|
| 信息填写与校验 | 卡号规则校验 | 每次用户提交后记录校验通过/不通过；逐字符输入不产生校验终态事件 |
| 同上 | 身份信息校验 | 实际发起校验后，记录通过/拒绝/服务异常；前置卡号不合法而未执行时不虚报 |
| 同上 | 信息校验整体 | 本次提交的所有必要校验通过才记成功；任一必要校验失败记对应失败；校验完成前明确终止本次操作可记取消 |
| 短信验证 | 验证码发送 | 每次发送/重发请求分别记录成功、业务拒绝或服务失败；成功表示发送服务受理，不冒称用户已收到 |
| 同上 | 验证码校验 | 每次实际校验记录通过、错误/过期、服务失败；未提交验证码就退出不伪造校验失败 |
| 同上 | 短信验证整体 | 校验通过记成功；用户明确退出记取消；不可继续的发送/校验失败结束本步并记失败。允许重试的错误仅结束该子尝试 |
| 人脸核验 | 活体检测 | 实际执行后记录通过、不通过或主动中止；未启用摄像头前退出不编造活体结果 |
| 同上 | 身份比对 | 活体通过后实际发起比对，记录一致、不一致或服务异常 |
| 同上 | 人脸核验整体 | 必要检测及比对通过记成功；拒绝授权归普通失败，明确中止归取消；未进入的子步骤不虚报 |
| 写卡 | 开卡申请 | 记录申请受理、业务拒绝或服务异常；请求受理不等同银行卡已开通 |
| 同上 | 本地写入/激活确认 | 按实际结果记录成功、失败或结果待确认；响应超时且不能确定结果时保留待确认过程，查明后再报最终结果 |
| 同上 | 写卡整体 | 权威开卡结果与本地必要步骤均成功才记成功；确定无法完成记失败。动画结束不是完成依据 |
| 结果展示 | 结果数据获取 | 实际获取结果数据后报告成功/失败；页面曝光复用自动上报，获取失败不改写已确认的开卡结果 |
| 全流程 | 一次开卡业务完成 | 写卡整体成功后记全程成功；不可恢复失败或允许取消时的主动终止分别记失败/取消；展示状态另记 |

同一个父步骤可有多个实际统计子点，父步骤与子点是不同统计对象。卡号错误后更正再次提交、短信重发等属于新的尝试；每个点位在同一次尝试中只产生一个终态。所有记录能关联至同一次开卡，避免将合法重试当重复上报。

#### 9.4.3 开卡结果查询

本流程读取既有开卡申请的状态，不承担重新开卡或补发原开卡统计的职责。

| 步骤 | 适用结果与业务触发条件 |
|---|---|
| 查询参数校验 | 实际提交查询后记录校验通过/失败；校验失败不虚报网络请求结果 |
| 查询权威状态 | 请求返回后记录查询成功或业务/服务失败；成功返回的开卡状态单独保留 |
| 查询整体 | 必要校验和状态获取完成为成功，否则失败；页面进入、刷新点击复用自动上报 |

成功查到“开卡失败”或“仍在处理”仍是查询成功；查询本身失败则不能推断开卡失败。查询耗时按本次查询起止计算。

#### 9.4.4 记录要求

需要统计的步骤，成功、失败、主动取消等适用结果均要记录，不只记失败或最终开卡结果。短信重试属于新尝试；重复回调不能重复报告同一点位同一次尝试的终态。用户拒绝授权属于普通失败；只有明确终止该业务才记取消，未执行步骤不补记录。

保留统计所需的流程、步骤、结果、实际耗时及必要维度，不采卡号、证件、验证码或人脸资料。VOC 记录必要过程诊断，不在同一 Chart 终态处双报。若后续产品/SE 明确新增独立运营事件，先补齐业务目的、触发条件和所需维度，再按项目共享事件常量与参数规则设计，不由本例默认生成。
