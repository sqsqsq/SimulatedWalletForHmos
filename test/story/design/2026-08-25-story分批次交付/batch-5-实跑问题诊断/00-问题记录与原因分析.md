## 2. 逐条事实与原因

### P1 · 图片被合法地全部移出

**事实链（按时间）**

1. writer 首次渲染时，四张图引用的是材料里的既有位置：`![分享设置页](../assets/数字车钥匙分享/share-setup.png)`
   （runlog:3708 的替换命令里保留了这一原串）。这是形态守恒要的形态。
2. 00:25:20 首判 276 条里，`[⑩ 语言红线]` 第 273 条：「主叙事出现工程标识 4 处（216 行「share」，224 行「share」，
   232 行「accept」…）——工程标识进附录的那几张表，主叙事写中文业务名」（`events.jsonl` 里该次 check 的完整输出）。
   216 / 224 / 232 三行就是三张图的引用行，被判的词是文件名里的 `share` 与 `accept`。
3. 00:31，作者照红线改：把四张图复制到 `AR/assets/` 并改成中文名，改写引用，注释写「合同允许的第二落点，中文名不带工程标识」
   （runlog:3687、3707–3711）。同一时刻它已把 `PRD:37` 标成 `material_only`，理由为「原图文件名含工程标识不宜进归档正文，
   正文以自有图片目录的中文名副本呈现」（runlog:3802）。
4. 第二次 check 报 `[④ 形态守恒] 4 处`（runlog:4061）：改名副本不在图片登记里，文案要求「引它在仓里的既有落盘位置，不要复制一份到归档目录再改名」。
5. 00:59:02 作者写下「修复策略落定：图片走 material_only」（runlog:4843），四张图的理由统一改成
   「原图文件名含工程标识不宜进归档正文；界面构成已由正文叙述承载，读者可经材料清单查看原件」
   （工作区 `AR/story-src/audit.json:65,79,1577,1596`）。
6. 最终 `AR/story.md` 图片引用 0 条；check 通过。

**最早出错的位置：`share` 这个「工程标识」是判据自己造出来的**

- 语言红线的标识清单从材料单元的 token 派生（`story-build.mjs:2027-2031`），形态判据 `IDENTIFIER_SHAPE = /^[A-Za-z][A-Za-z0-9_]{3,}$/`
  （`:459`）。`AR/design.md:37` 的表格行在括号里写了 `（share-setup.png）`，切 token 时按连字符拆成 `share` 与 `setup.png`
  （工作区 `source-units.json` 里 `DESIGN:37` 的 tokens 为 `['share','setup.png']`，`DESIGN:50` 为 `['accept','page.png','72h']`）。
  `share` 与 `accept` 于是以「材料里出现过的工程标识」身份进入红线词表。
- 红线扫描（`lint-rules.mjs:257-299`）对主叙事每一行做整词匹配，不排除 `![alt](path)` 这个图片引用语法；
  同一文件的另一处扫描（`:565-575`）却专门解析图片行。`share-setup.png` 在连字符处成词边界，`share` 命中。
- 于是两条判据对同一行提出了互斥的要求：⑩ 要求主叙事里不出现 `share`，④ 要求图片引用保留登记里的文件名 `share-setup.png`
  （`story-build.mjs:1642,1665`，按文件名查登记）。改名满足 ⑩ 违反 ④，不改名满足 ④ 违反 ⑩，删掉引用两条都满足。
- 删掉引用之后还需要一个合法落点，作者面给了它：`story-write.md:70` 写 `material_only: <一句理由>`，`:76` 举例
  「界面细节图、同一件事的第二张示意、只为存档的截图」。判据只核两件事：是图片（`story-build.mjs:1495`）、理由 ≥4 字（`:1499`）。
  `material_only` 又是分母的调节阀（`:372-373`），分母归零后「画出数 ≥ 分配数」恒成立。
- 图片位置规则本身也有文本相斥：报错文案说「不要复制一份到归档目录」，合同注释（`story-chapters.json:409`）说归档件自己的 `assets/`
  是合法落点，代码（`:1655-1658`）按合同放行了该目录、只拦改名。作者面（`story-write.md`）通篇没有一句讲图片引用该写什么路径。

**原因归纳**

- 直接原因是判据互斥：一个从材料里切出来的伪标识 `share` 让语言红线去管图片引用行，而形态守恒又要求那一行保持原样。
  作者三次尝试都被拦，最后选了唯一不再被拦的态。报告 §六 把它写成「作者选了逃生门」，事实是判据把门都关上了，只留了逃生门。
- 逃生门本身没有证明义务：分母由被守恒方定，定分母只要一句自由文本。这与 08-29 首跑「判据同时要求改写与逐字命中，倾倒是唯一合法解」
  同型。
- 内网「30 张图不必都进 story」与「一张都不进」之间没有任何判据区分，报告 §六 已指出。

### P3 · spec 结构性闭不了环

**事实**

- `framework/harness/scripts/utils/verifier-plan.ts:158-168`：policy 为 required 且运行模式 interactive 时，adapter 未登记
  interactive 的 verifier 能力即判 `blocked / verifier_provider_unavailable`。
- 登记情况：`framework/agents/claude/adapter.yaml:55-58` 与 `codeagent/adapter.yaml:48-51` 有 `verifier_capability.modes: [interactive]`；
  `opencode/adapter.yaml` 没有这个段。该字段随 framework 3.0.0 同步引入（`a4526d27`）。
- 测试配置 `test/story/config/test.yaml:33-45` 的前两位都是 opencode（GLM5.3-Flash、deepseek），第三位才是 codex。
  `car-key-sharing` 的 `end_phase: plan`。
- 同一报错在 8 月 31 日以来五次运行的 runlog 里都出现过（`story-suite-20260831-165400`、`-220900` 两 Case、
  `story-suite-20260901-121846`、本轮）。三次终态 `gate_failed`、一次 `stopped`、本轮由用户终止。
- 另一件独立的事：工作区 `framework.local.json` 的视觉金丝雀在 15:36Z 判 `none`（「agent 明确声明看不见图片」），
  此前主仓缓存的 `tool_read` 已过期 24h（runlog:1303）。UI 产物因此按盲档工作法产出。这是模型能力事实，与 verifier 无关。

**原因归纳**

- 在 opencode 宿主下，spec 从结构上就闭不了环，plan 永远进不去。这不是本轮才出现的环境故障，是自 08-30 把测试宿主改回 opencode 起
  每一轮都成立的前提。五轮实跑都把它记成「稍后处理」或「环境问题」，没有人把它与「测试终点 plan 是否可达」放在一起看。

### P5 · 初析哈希与轮次边界

**事实**

- `story_flow.py:440-445` 的 docstring：轮次边界按材料指纹，「拿分析件的哈希当轮次边界，等于允许材料没动、重写一遍分析造出一个新轮次」。
  `:474-482` 在 `round` 时把当下的初析哈希盖进轮次条目；`:488-499` 材料未变时重跑 `round` 会刷新这个哈希。
- `flow-check.mjs:86-90`：要求每一轮的 `analysis.sha256` 与上一轮不同，注释写「一轮 = 一次初析：轮次由初析件哈希划界」。
- `SKILL.md:41`：「一轮 = 一次初析。轮次边界由 `AR/init-analysis.md` 的 sha256 判定」。
- `rules/init_analysis.md:19`：「轮次 = 一次材料状态……分析件在同一轮内从盘点版演进到完整版，不算新轮次」。
- `rules/scope_gate.md:80`：补料回 S2a 的顺序是「导入 → 重新盘点材料 → round+1」，没有提初析更新在 `round` 之前还是之后。
- 实跑：第 2 轮的导入与 `round` 在同一条命令里执行（runlog:567），登记完成后才「更新盘点版初析」（runlog:449），
  之后没有再跑 `round`。契约里第 2 轮的哈希因此与第 1 轮相同（`88e4cb8208e93973`）。第 3、4 轮顺序不同，没有撞上。
- 作者在 spec 阶段被 `flow-check` 拦下后手改 JSON，并声称「流程脚本无回修命令」（runlog:7025）。实际重跑 `round`
  即可刷新（`story_flow.py:488-499`），但没有任何文本告诉它这一点。

**原因归纳**

- 三处文本对「轮次边界是什么」说法不一：脚本说材料指纹，检查器与 SKILL 说初析哈希，规则说材料状态。
  这是 AGENTS.md §2「改契约文本时同步它的消费方」的直接违反。
- 哈希在 `round` 时刻采集，而它指纹的对象在那之后才定稿；收口（`complete` / `story`）不复核。
  顺序对了就过，顺序反了就要手改契约。作者被逼去做「书记性修正」，机制层没有给它合法路径。

### P6 · 知识消费链没有被端到端证明

**事实**

- `knowledge/` 在本仓的主要身份是**知识样板**：真正交付到内网代码仓时，facts、规约和模式会按目标仓事实修正、扩展；
  因此 Demo 样板内容是否持续与 Demo 业务代码逐项一致，不是知识能力的核心验收。
- 核心链路应当是：知识在合适阶段被正确执行体看到 → 执行体理解并判断适用性 → 知识改变本阶段产物或设计 →
  已形成的决策与义务传给下游 → 下游按冻结结果落实和验证。
- framework 对 `manifest.yaml > provides.knowledge` 零消费；当前由扩展 `hooks/shared/knowledge.mjs` 自行重读清单。
  这条旁路能枚举知识，不等于阶段作者必然看到了知识正文。
