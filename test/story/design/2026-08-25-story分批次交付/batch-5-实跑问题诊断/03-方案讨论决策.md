# 批次 5 · 方案讨论决策

> 本文件只记录用户与维护者已经明确确认的方案决策，以及实施时必须用证据求解的事实。
> 它不是步骤文件或实施授权；正式顺序和单步边界见 [05-实施方案总览.md](05-实施方案总览.md)。

## D1 · 独立 verifier 先于 Story 重建实施

| 项 | 结论 |
|---|---|
| 状态 | **已确认**（2026-09-02） |
| 决策 | 把 opencode interactive verifier 闭环作为批次 5 的首个基础能力步骤，先于 Story 成文、Knowledge 消费和语义判据重建 |
| 直接解决 | P3：opencode 下 required verifier 不可用，spec 无法闭环 |
| 后续价值 | 为 Story、Knowledge 与后续每个阶段提供独立于作者上下文的语义审查能力 |
| 所有者 | Framework 的 adapter 能力；Story Extension 只提供阶段语义审查内容 |

用户补充口径：D1 是 Framework 已有 verifier 能力对 opencode adapter 的补齐，不计入批次 5 为解决 Extension 问题而新增的
Framework 功能规模；但实施时仍须按完整能力链验收，不能把“能力补齐”降为只加声明。

### 1. 所有权边界

- **Framework** 负责 verifier request、独立执行、报告发布、身份验真、evidence 消费和阶段闭环。
- **opencode adapter** 负责把 OpenCode 的真实 agent/会话能力接入 Framework verifier 协议，并只登记已经实测通过的运行模式。
- **Extension** 只负责提供当前阶段要审查的语义要求；本步骤不修改 Story、Knowledge、overlay 或 `pre_verifier` 内容。
- verifier 是 Framework + Extension 内部执行能力，不是维护者/执行者之外的第三种项目角色。

### 2. 已确认的当前事实

- Framework 已有 `repo_file_request → verifier.report.<subject>.json → receipt/closure` 主链。
- claude 与 codeagent 已物化 verifier agent、使用独立子 agent 执行，并通过 `SubagentStop` 发布报告。
- opencode adapter 当前没有 verifier agent 物化、独立调用、报告发布、身份绑定或 `verifier_capability` 声明。
- adapter schema 当前只登记 `transport=repo_file_request` 与 `publisher=subagent_stop`；不能把 OpenCode 未具备的事件伪装成 `subagent_stop`。
- 本地 `@opencode-ai/plugin` 1.18.x 暴露 agent 与 event 接口，说明存在原生适配可能；当前 Framework 尚未使用这些接口。
- 当前机器直接执行 `opencode --version/--help` 会因用户配置路径 `EEXIST` 失败；这是 smoke 的环境前置，不构成 adapter 已支持或不支持 verifier 的结论。

### 3. 本步骤必须交付的完整能力链

```text
脚本 Harness PASS
→ Framework 生成当前 subject 的 verifier request
→ opencode 启动独立且只读的 verifier 上下文
→ verifier 按 request 读取 prompt_path
→ opencode/Framework 取得可信终稿与独立执行身份
→ 发布当前 subject 的 verifier report
→ 现有 evidence loader、receipt 与 closure 验真并闭环
```

只增加 `adapter.yaml > verifier_capability` 不算实施；能力声明必须是整条链真实通过后的最后一步。

### 4. 正式方案前仍需由 smoke 决定的事实

OpenCode 的报告发布机制不预猜，先用最小实验确认：

1. verifier agent 的原生声明和启动方式；
2. 是否生成独立 session/agent 身份；
3. 能否限制为只读工具；
4. 哪个事件能证明 agent 已完成并提供稳定终稿；
5. 事件字段能否与 request、prompt 和 subject 建立不可混淆的绑定。

若原生 agent 完成事件具备上述证据，Framework 增加对应的机制级 publisher。若不具备，D1 判为 blocked：
“Framework 启动独立 OpenCode 进程并捕获终稿”属于新的 verifier provider 能力，不是 opencode adapter 补齐，
必须另立 Framework 需求并由用户确认，不能作为 D1 的备用分支。publisher 使用机制名称，不使用厂商名，也不复用语义不成立的 `subagent_stop`。

### 5. 范围

本步骤只覆盖 opencode 的 **interactive** verifier：

- 不同时适配 codex、cursor、generic 或其他 adapter；
- 不登记未经实测的 headless/goal；
- 不修改 verifier 的阶段语义问题；
- 不修改 Story 成文、图片、review、Knowledge 或旧 `story-build` 判据；
- 用户已为 D1 单独授权在本工程直接修改 vendored `framework/`；授权只覆盖 OpenCode verifier adapter 补齐所需的精确文件。
  D3 或其他 Framework 改动不继承此授权，到对应步骤前重新决策。
- 本地 D1 通过只证明 Demo 仓可验证，不宣称内网已获得能力。D1 同时交付基于 `RELEASE-MANIFEST.json.source_commit` 的
  上游可复现补丁与变更说明；本地 drift allowlist 只在上游版本尚未包含该变更时有效，后续 UPDATE 覆盖后删除。

### 6. 单步验收与专用 CLI smoke

先用离线正反夹具验证整条 Framework 闭环，再运行一次专用 `opencode-verifier-smoke`。该 smoke 永久保留、显式运行，
不加入 Story `--all`，也不启动现有 2～4 小时的 Story Case。

smoke 只跑 full track 的 Spec，需求为“钱包首页增加隐藏余额开关”：默认关闭；入口位于“我的”页；开启后首页总余额显示
`****`，关闭后立即恢复；本地保存并跨重启保持；清除应用数据恢复默认；不上传服务端，也不改变卡片余额、交易记录和支付功能。
它不经过 `/story`，不使用需求系统、补料、图片、范围选择或人工决策，不生成 Story/Review，不进入 Plan。

正向验收：

- required + interactive + opencode 时生成 request；
- verifier 在独立上下文中只读目标材料并输出报告；
- 报告 subject、request、prompt hash 与当前 summary 一致；
- verifier 前阶段为 INCOMPLETE，合法报告发布后 receipt 与 closure 通过；
- capability 在完整 smoke 通过后才登记 `interactive`。

反向验收：

- 主执行者自行写报告不能入闭环；
- 错 subject、旧报告、篡改 request、错误 prompt hash、缺失终态，或目标材料没有按该 adapter 声明的方式可靠送达，均被拒绝；
- verifier 失败时保持可诊断的 INCOMPLETE，不伪造 PASS；
- policy off/not_applicable 时零 request、零 verifier、零报告要求；
- claude/codeagent 现有 verifier 链保持通过；
- Extension 和当前 Story Case 零修改。

D1 输出两个彼此独立的结论：

1. **Framework 能力结论**：独立执行、身份绑定、request/subject/report/receipt 闭环正确即可通过；
2. **批次 5 继续结论**：smoke 中语义审查若明显无效，D1 能力结论可以通过，但后续退场步骤暂停，先修 verifier 任务。

两个结论都绑定实际 `cli_config_id`。一个模型/配置的通过不能外推到其它配置；后续行为实跑只能使用通过相应资格门的配置。

### 7. 步骤完成边界

实施会话只能声明“opencode verifier 已实施，等待评审”。维护者必须从实际 adapter、调用事件、发布报告和 receipt
重新还原整条链，并确认正反验收均成立后，才能写“步骤通过”并进入 Story/Knowledge 具体方案。

## D2 · 提示词、脚本、verifier 与行为测试共同约束执行者

| 项 | 结论 |
|---|---|
| 状态 | **已确认**（2026-09-02） |
| 决策 | 方案不能假设执行者会 100% 按提示词行动，也不能把语义全部改写成脚本；系统级高风险行为由四类控制层按风险组合保护 |
| 要解决 | 执行者忽略、略写、误解、跳步、编造，以及维护者用更多脚本语义代理进行补救的双向失控 |
| 适用范围 | Story 成文、review、Knowledge 消费、Framework 阶段推进、verifier 与后续所有分步方案 |

### 1. 两个错误极端

- **提示词理想化**：把要求写清后便相信执行者会完整阅读、正确理解并全部落实；遗漏只能到最终产物才被发现。
- **脚本语义化**：因为不信任执行者，使用 token、子串、字数、数量和相似度替模型判断内容是否完整、正确和易读。

批次 5 的目标不是在两个极端之间折中，而是让每种能力只承担自己能可靠完成的责任。

### 2. 四层协作

| 层 | 必须负责 | 不能冒充 |
|---|---|---|
| 提示词 / 作者任务包 | 在行动前给执行者完整目标、输入、步骤、输出合同和失败处置 | 执行保证 |
| 确定性脚本 | 冻结输入、控制步骤与状态、生成骨架、检查结构/引用/精确来源/证据 | 语义理解和人读质量 |
| 独立 verifier | 判断遗漏、略写、矛盾、编造、表达质量和 Knowledge 是否真正应用 | 自己被独立调用及报告身份可信 |
| 隔离行为测试 | 验证未知执行者、未知材料、时间成本和四层协作 | 每个实施步骤的低成本离线检查 |

单一控制层不能证明端到端 Agent 行为。脚本证明可确定事实；verifier 的独立身份与报告由 Framework 验真；
里程碑实跑提供未知执行者与材料上的泛化证据，但有限样本不构成绝对证明。
纯确定性子能力可以只用与它相关的结构证据和独立审查闭环，不强制经过四层中的每一层。

### 3. 提示词与脚本共用任务合同

同一阶段的作者提示、产物骨架、确定性 preflight 与 verifier 审查范围共享事实、结构和状态真源：

```text
必需输入
→ 执行顺序
→ 输出合同
→ 确定性不变量
→ 语义审查目标
→ 失败与恢复条件
```

作者在决策前收到任务包；checker 不再首次披露规则。语义目标以人可读指引进入执行者和 verifier，脚本只消费可确定计算的
结构、状态和引用条件。方案不强制所有提示文字和审查问题都由一个机器 schema 生成；只要求共同事实不出现第二真源。

### 4. 脚本应当接住的失败

- 必需材料、决策、Knowledge 或上游产物缺失；
- 写作期间输入版本发生变化；
- 必需步骤被跳过或状态顺序非法；
- 文件、章节、生成区、图片与链接缺失或损坏；
- 被当前合同声明为必须溯源的精确数字、工程标识或配置声明，既没有权威来源，也没有登记推导过程或 decision；
- 上下游 ID、义务集合、verifier subject 或报告身份不一致；
- 某项检查因前置缺失没有运行，却被表现成通过。

脚本在当前输入允许的范围内尽量一次列出完整问题，并同时报告因前置缺失而无法执行的检查。补齐前置后才可执行的检查
允许在下一轮产生新结果；同类问题反复分层暴露、且本可在上一轮判定时，才属于需要回维护层修正的洋葱式检查。

### 5. verifier 应当接住的失败

- 关键业务目标、范围、流程、异常或验收被忽略；
- 只出现名词或结论，没有解释关系、原因和用户行为；
- 建议、可能性和未决事项被写成确定需求；
- 多条真实事实被拼成材料没有支持的新结论；
- 图片或流程图承载的信息在成品中消失；
- Knowledge 被回显、漏判或没有改变本需求的设计；
- story/review 形式存在但不适合目标读者。

verifier 按问题族聚合结论和代表证据，不按来源单元生成线性增长的逐行裁决表。

报告分为 `blocking_findings` 与 `advisories`。关键遗漏、明显略写、编造、矛盾、范围错误或验收不可判定进入 blocker；
每项须说明具体位置、缺失或错误内容及其影响。标题偏好、同等清楚的表达替换和非必要补充只作 advisory，不能阻止 PASS。

### 6. 有界恢复

运行链的目标形态是：

```text
执行者一次产出
→ 确定性 preflight
→ 一次完整语义审查
→ 执行者按聚合问题针对性修订
→ 确定性复查 + 语义复核
```

一次成文和一次返修是效率目标，不是机制中的固定次数上限。每轮记录问题族、数量、变化和新增原因；问题持续减少且没有重复撞同一规则时，
可以继续完成必要修订。出现同类问题连续重复、错误不减少、修一处引入同族新错或成本持续增长时，返回维护层检查作者任务包、
输入规模、职责分配、verifier 定义或模型能力。停止条件依据是否收敛，不依据写死的轮次数。

### 7. 对后续方案的约束

- 删除逐单元 audit、逐字引文与 token 语义代理，不等于删除输入、步骤、状态、来源和证据控制。
- 每个具体实施步骤必须说明哪些控制层和失败类型适用，以及相应问题由谁发现；不要求纯确定性步骤机械凑齐四层或覆盖无关风险。
- Knowledge 方案须为看到、理解、应用和传递分别提供可观察证据；“理解”只能从判断、产物变化与独立审查中推断，
  不声称脚本能够直接证明模型内部已经理解。任务包已生成或表格已存在不能单独作为应用证据。
- Story 方案必须同时定义作者任务和 verifier 任务，不能只优化提示词或只修改 checker。
- 单步离线验收验证局部协作；真实 Story 由用户与维护者按依赖、风险、成本和证据选择少量里程碑运行。

## D3 · 收紧为 interactive 的 `on_context_load` 作者消费入口

| 项 | 结论 |
|---|---|
| 状态 | **已确认**（2026-09-02） |
| 决策 | 当前只覆盖 interactive；Framework 复用已有 `on_context_load`、extension loader、hook dispatcher 和 `promptFragments`，补一个阶段作者起手的薄消费入口 |
| 目标 | 让 Extension 作者要求在写主产物前进入当前 phase 上下文，不依赖根 AGENTS 的远距离提醒，也不建立影子 Framework |
| 规模判断 | 小型 Framework 既有能力修正；预计 4～6 个文件、约 100～300 行实现和测试，数字只作方案估算，不是验收阈值 |

### 1. 范围前提

- Story Extension 当前设计、实现和验收只覆盖 interactive；该范围已写入 `test/story/AGENTS.md`。
- headless/goal 不进入 D3，不增加兼容、状态、adapter capability 或测试；未覆盖不写成已支持。
- spec、plan、coding、code-review、business-ut 五个 feature Skill 已强制读取 `agent-behavioral-principles.md`；
  device-testing 当前缺少该入口，D3 须补齐，不得把五个误写成六个。
- 当前 Framework/profile 树没有实际 `on_context_load` hook 文件，当前 Extension manifest 也未注册该事件；仓内不存在活跃消费者。
  未知外部 Extension 仍可能依赖现有错误时序，因此 Framework 发布时须写迁移说明并覆盖兼容性测试。

### 2. Framework 最小改动

1. 在共享 `agent-behavioral-principles.md` 增加 phase 写入前的统一动作：解析当前 phase 的 `on_context_load`，把输出作为作者输入。
2. 增加一个只读薄解析器：接收 phase/feature，复用现有 extension loader 与 hook dispatcher，按 Framework → profile → Extension
   顺序执行 `on_context_load`，把 `promptFragments` 直接输出到 interactive 执行者上下文。
3. 从 `harness-runner` 的后置 verifier prompt 装配位置删除当前错误的 `on_context_load` 调用；verifier 专属内容继续只走 `pre_verifier`。
4. 给 device-testing 补上与其余 feature Skill 一致的共享行为规约入口。
5. 校正 lifecycle schema/说明并增加最小单元测试。

解析器不写业务产物，不建立 author-context 状态、receipt、hash 体系或新阶段，也不修改 verifier、closure、track 和 adapter 协议。

### 3. Extension 接入边界

- Extension 使用现有 manifest hook 结构，将各 phase 的 author 内容登记为 `on_context_load`；不增加新 manifest 字段。
- 现有 author 内容只维护一份；根 AGENTS 的 author.md 远距离提醒在新入口稳定后退场。
- Extension 不自建 context loader、不包装六个 phase Skill、不修改生成的 `.opencode/.codex/.claude` phase 跳板。
- 作者内容可继续是 Markdown，也可通过现有 MJS hook 返回 `promptFragments`；执行方式由 Framework 薄解析器统一处理。

### 4. 等价性边界

在 interactive 范围内，该入口须覆盖 `/story → spec`、直接 phase Skill、correction 和跨会话恢复后重新进入 phase 的正常路径。
它保证作者要求在正确动作附近进入上下文，不声称模型内部一定理解；忽略和误用仍由 D2 的确定性检查、独立 verifier 与行为测试发现。

零 Framework 修改的替代方式不接受为等价方案：

- 继续依赖根 AGENTS 已有实跑忽略证据；
- Extension 自建解析器会复制 Framework 配置、loader 和 hook 顺序；
- wrapper Skill 会产生两套 phase 入口；
- 把要求写进上游产物会污染业务真源且覆盖不了首阶段。

### 5. 离线验收

- 无 Extension、无 `on_context_load` 时返回空结果，现有 interactive phase 行为不变；
- Framework/profile/Extension 三层片段顺序与 dispatcher 一致；
- Markdown 与 MJS hook 均能把内容送到作者起手输出；
- hook 缺失为空，hook 失败明确报错，不静默当作无扩展；
- 作者片段不再进入 verifier prompt，`pre_verifier` 行为保持；
- 六个 phase 通过共享行为规约获得同一入口；只补 device-testing 的缺失引用，不在六份 Skill 复制 D3 细则；
- Extension 未接入前不改变既有产物、receipt、closure 或 phase 状态；
- 不运行真实 Story，后续 Extension 接入完成后再按 D9 选择行为里程碑。

## D4 · Story 主叙事与确定性内容分工

| 项 | 结论 |
|---|---|
| 状态 | **已确认**（2026-09-02） |
| 决策 | Story 面向人的主叙事由执行者完成；可由权威数据确定生成的附录、索引和精确结构交给脚本 |
| 目标 | 同时避免模型漏抄精确信息和脚本用 token 代判自然语言语义 |

- 执行者负责背景、范围、业务方案、业务流程、功能、异常、验收和交付等人类叙事。
- 技术契约、材料清单、规约结论等确定性部分从 spec、contracts、materials 和 Knowledge 决策生成，不要求执行者重新抄写。
- Story 保留金样的十章稳定骨架：背景、术语、范围、业务方案、业务流程、功能说明、异常与恢复、验收、交付与上线、附录。
  十章是读者导航和作者任务边界，不形成字数、表格、图片、小节或条目配额。
- 主叙事与生成区有明确所有者，验证者不再要求同一事实同时以模型文本和机器表格维护两份真源。

正向成文路径是：脚本准备完整材料 manifest、材料正文、图片、已定 decisions 与十章作者任务；作者按每章要回答的读者问题
逐章原子落盘并可从缺章续写；全部章节完成后做跨章统稿，脚本再生成确定性区域，独立 verifier 做整体编辑审查。
新链不建立来源单元、章节落点、逐字引文或
“作者声明已覆盖”的证明表。verifier 是安全网，不是成文主机制。执行者只收到从金样正推的通用表达原则，不读取或引用
`test/story/golden`；金样路径只属于维护测试。

Story 文件本身是续写真源：稳定章锚只标识待写/已写，不另建进度表。单章内容完整写入后才原子替换对应待写块；中断恢复只处理
仍待写的章节，已完成章节字节不变。单章完成不按字数、行数或条目数判断；脚本只认空正文与明确模板占位，内容充分性归 verifier。

## D5 · review 在 Story 之后由最终 decisions 渲染

| 项 | 结论 |
|---|---|
| 状态 | **已确认**（2026-09-02） |
| 决策 | decisions 是产品判断的唯一真源；Story 成文中发现的判断先回到 decisions，随后再生成 review |

目标顺序为：

```text
材料与范围决定
→ spec 与初始 decisions
→ Story 成文并登记新发现的判断
→ 最终 decisions
→ 渲染 review
```

- 已成立的结论进入 Story；未决项不写成确定需求。
- review 的机器区由最终 decisions 渲染，人类审核区在重渲染时保持。
- review 不再先于 Story 生成，也不作为 Story 的反向事实来源。
- 成文中新发现的判断不额外制造固定人工停等点；如何进入后续评审按现有产品评审流程处理。
- Plan 不得静默改变 Story 已表达的产品行为、范围或验收。纯技术裁定不回写 Story；若 Plan 发现必须改变产品要求，
  按 correction 返回 Spec，并同步更新 Story/Review 后再继续。

## D7 · Knowledge 以消费链而不是内容样板准确性为目标

| 项 | 结论 |
|---|---|
| 状态 | **已确认**（2026-09-02） |
| 决策 | Knowledge 优化围绕看到、理解、应用、传递；Demo 内容是样板，目标仓由 adapt 修正和扩展 |

- Facts 从 Spec 起直接作为目标仓事实使用；发现错误回 Knowledge 真源修正，不进入“选或不选”。
- Constraints 由 Spec 结合当前需求判断命中并形成产品约束；Plan 决定具体设计落点与验证方式，不能随意否定已命中的约束。
- Design patterns 由 Spec 只登记候选及适用理由，Plan 选择、拒绝或调整并冻结；Spec 不替 Plan 选型。
- Coding、Review、UT、Testing 消费冻结结果，提供落实证据或明确不适用，不重新猜测全部原始 Knowledge。
- 脚本验证清单、身份、引用和上下游集合；verifier 判断漏判、复述和是否真实改变本需求。
- 验收使用机制未知的中性 Knowledge 做穿透：只改 Knowledge/激活内容，不为新条目修改通用机制；各环节提供可观察证据。
- Spec/Plan 的具体章节、文件和表格形态留到方案讨论，不在本决策中冻结。

## D8 · 材料、流程状态和测试状态各有唯一所有者

| 项 | 结论 |
|---|---|
| 状态 | **已确认**（2026-09-02） |
| 决策 | 同一事实和状态只由一个组件写入；其他组件读取或派生，不建立平行状态 |

当前方向：

| 内容 | 所有者 |
|---|---|
| 原始材料、图片与材料版本 | 唯一材料 manifest；README 如保留只能是派生视图 |
| 材料齐备、范围与承载决策 | Story flow |
| Spec～Testing 阶段状态与闭环 | Framework |
| 产品判断与未决项 | decisions |
| Story 确定性附录 | 对应 spec/contracts/materials/Knowledge 决策派生 |
| review 机器区 | decisions 派生 |
| Knowledge 激活 | manifest |
| 测试观测状态 | 测试装置 |

Story flow 不再写 Framework 阶段状态；测试 runner 不用目标阶段 hint 冒充执行者实际到达；图片目录与 README 不再各自登记一份真源。
材料 manifest digest 是材料版本/轮次的唯一边界；`init-analysis.md` 的内容与 hash 只属于同一材料版本内可演进的分析产物，
不再定义轮次。补料改变 manifest digest 后形成新材料版本，执行者不手工修改契约 hash。
唯一 manifest 固定为 `AR/story-src/materials.json`，材料 hash 只由一个共享写入模块计算；导入回执不再单独持久化，
`story-flow.json` 删除逐文件 `inputs`，只引用 manifest path/digest。具体迁移和历史 feature 处理按 D12 不进入当前范围。

Story 的完整性只对“已确认的本 AR 范围 + 已定 decisions + 范围内原始业务事实 + Spec 已成立的产品约束”负责。
兄弟 AR、明确排除项和纯技术候选不进入分母；范围由 Story flow 的权威状态给出，verifier 只能核落实，不能自行扩大范围。

## D10 · 旧质量锚先迁移，新语义链合格后再删除旧发现者

| 项 | 结论 |
|---|---|
| 状态 | **已确认**（2026-09-02） |
| 决策 | D6 退场旧语义判据前，先建立新 verifier 区分力、失效形态责任迁移和新旧产物质量对照；新链跑通不等于质量已守住 |

### 1. verifier 区分力资格门

D1 只证明独立执行和 Framework 闭环，不证明 verifier 会发现内容问题。新 Story verifier 任务定义完成后、D6 删除旧判据前，
使用成对产物验证至少以下问题族：

- 删除关键业务事实；
- 把有效章节替换为空泛或明显略写的内容；
- 写入材料、decision 和 Knowledge 均不支持的确定结论；
- 删除只能由图片或流程图承载的信息；
- 把 Knowledge 应用改成名称回显、原文复述或完全忽略。

验收判断 verifier 是否稳定区分 good/bad 并指向正确问题族，不要求继续生成旧式逐单元表或机械满足“删 N 条报 N 条”。
区分力不足时修 verifier 任务定义和输入，不给 checker 增加语义相似度补丁。

资格结论绑定 `cli_config_id`。对准备承担真实实跑的每个配置分别记录“配置 × 问题族”结果；未具备独立 verifier 能力或未通过
资格门的配置不能用于步骤 11。另以 small/large 合成材料记录上下文、墙钟和报告规模，确认输出仍按问题族而非材料单元增长。

### 2. 73 条失效形态迁移

当前台账 73 条中 69 条 fixed、4 条 pending、0 条 retired。D6 删除旧 checker 前，每条须迁移到一个现行责任：

- `deterministic`：由新确定性检查发现；
- `verifier`：由新语义审查发现；
- `generated_by_construction`：新生成方式使该错误不能从正式入口产生；
- `behavior_test`：由隔离执行行为验证；
- `retired`：旧内部机制已不存在，记录理由和批准。

一项新能力可以承接多条历史形态，不为 73 条各建一个 checker；但旧发现者删除前不得存在无人负责的 fixed 形态。
逐项审查见 [04-失效形态长期要求审计.md](04-失效形态长期要求审计.md)：42 条是跨实现长期不变量，27 条只保留长期目标并重写
旧 form/checker，4 条属于待退场旧实现。特别是“必须用表格/小节/流程图”“图片不能放附录”等批次 4 固定形态不得继续冒充长期要求。

### 3. 内容质量锚

`baseline_coverage.py` 依赖 `source-units.mjs`、token 和片段命中，D6 后不再作为新 Story 守恒工具。新质量对照由三类输入组成：

1. 原始材料：判断事实、关系和业务语义是否遗漏；
2. 已确认金样：判断 Story/Review 的目标效果；
3. 稳定质量维度：背景、范围、流程、功能、异常、验收、决策分离、图文表达和人读质量。

金样保护的是**形似 + 神似**：信息架构、详略分布、内容选择合适的表达形态、主叙事与附录分工、评审可用性和整体人读效果。
金样不限制新需求的业务内容、字数、表格数、图片数或小节数，这些由实际需求决定；不得把“像金样”实现成数量配额。

金样正本只维护在 `test/story/golden/`。design 临时副本删除，测试直接读取正本；输入 fixture 不再保存 story/review 金样副本。
批次 1 Story 只作单向历史参考，不要求逐字、逐片段或数量对齐。维护者对新旧产物做最终语义比较；独立模型可以提供审查证据，
但不能自己证明自己的 verifier 任务有效。`baseline_coverage.py` 在 verifier 资格门建立时完成消费者审计并决定退役或仅作历史诊断，
不拖到最终清理才决定，也不参与新链 PASS/FAIL。
