## 2. 必须改的（blocker）

### B1 · 步骤 9 让作者「直接写十章完整 Story」，是已登记的失败形态回归

**证据**：`steps/09-story-authoring-cutover.md` 「作者直接写十章完整 Story」；`story_flow.py:982-985` docstring：
「曾经……由子 agent 一次写成整篇……一次写成整篇是全有或全无，子 agent 返回空就什么都不剩」；
2026-08-29 D5 实录：writer 一次写 37KB 在 opencode 上 4 次 3 空。当时的修法是「逐章渲染、每章落盘、可续写」，
而分配簿记（audit）是随它一起引入的。步骤 9 退掉分配簿记时把逐章落盘一起退了。

**目标形态**：作者任务包一次给全（材料、范围、decisions、约束、十章读者问题），产出按章**有界落盘、可续写**：
每章写完即追加到 story 文件的对应章锚（步骤 8 已给稳定锚点），中断后重入只写缺的章。不需要任何逐单元分配。

**替代了什么**：替代「整篇一次写成」；不恢复 `audit.json` 与落点表。

**结果判据**：夹具里模拟作者在第 4 章中断，重入后前 3 章字节不变、只补后 7 章；全程不产生 source-units / audit。

### B2 · D1 在本仓 vendored `framework/` 实施，不进上游，内网执行者拿不到

**证据**：`steps/01` 允许范围「`framework.config.json` 仅允许为本步实际修改的 Framework 文件增加真人具名 drift allowlist」，
「不得修改 `framework/RELEASE-MANIFEST*`」；`framework/RELEASE-MANIFEST.json:4` 的 `source_commit` 指向上游 `7401f22`；
CLAUDE.md 红线 9：升级唯一途径 framework-init UPDATE。内网仓的 framework 来自上游发布件，不来自本仓。
结论：步骤 1 做完，只有本仓 demo 的 opencode 能闭环；内网 P3 原样存在；本仓下一次 framework-init UPDATE 还会把它冲掉。

**目标形态**：步骤 1 的完成条件加一条「变更以上游可合入的形式交付」：补丁文件（或上游分支）+ 上游 source_commit 基线 +
本仓 drift allowlist 只作为上游合入前的临时放行，并在 STATUS 写明「本仓实现只服务 demo 验证，内网生效依赖上游发布」。
AGENTS §3「补齐 Framework 能力」补一句路径：改动落上游，经 framework-init UPDATE 回本仓。

**替代了什么**：替代「本地改 vendored + allowlist 永久放行」这条会随下次升级消失的路。

**结果判据**：能从补丁与 source_commit 复现出与本仓相同的 adapter 行为；drift allowlist 条目带失效条件。

### B3 · 步骤 7 的 verifier 资格门没有绑定实跑的宿主与模型

**证据**：`steps/07` 资格夹具通篇未写在哪个 CLI 配置上跑；`test/story/config/test.yaml:37-47` 三个配置
（opencode/GLM5.3-Flash、opencode/deepseek、codex/gpt-5.6-luna）；opencode 的 verifier 子 agent 与主会话同模型。

另外 AGENTS §0 只写了 interactive，没写宿主集合（评审者 2026-09-02 已提，未落）。

**目标形态**：资格门按配置组逐配置跑，逐配置记录 good/bad 命中；未达标的配置不得用作步骤 11 与后续实跑的宿主；
05 §1 或 AGENTS §0 声明本批交付面支持的宿主集合与最低可用模型条件。

**替代了什么**：替代「资格门通过」这个与宿主无关的单一结论。

**结果判据**：`reviews/07-*.md` 里有一张配置 × 问题族的命中表；实跑 Case 的 `cli_config_id` 在达标集合内。

### B4 · 步骤 10 的 `knowledge-use.yaml` 若不删旧手写出口，就是第三真源

**证据**：现状 spec 的知识出口是手写的 §10 规约约束要求 + §11 设计模式候选登记（`skills/story/templates/spec-sections.md:114,141`），

**目标形态**：spec 里知识结论只有一处可编辑（`knowledge-use.yaml`），§10/§11 是生成区；旧三方集合核改为「生成区与 yaml 一致 +
下游分派集合一致」；作者面（`hooks/spec/author.md`、`spec-sections.md`）同步删掉手写要求。

**替代了什么**：替代手写 §10/§11 + 三方 ID 核。

### B5 · 「非占位」若实现成字数或条目阈值，就回到 M13

**证据**：`steps/08` 「脚本只检查章存在、非占位和生成区边界」，`steps/09` 「脚本：十章、非占位……」；04 审计 L 类 M13

**目标形态**：「非占位」的确定性定义写死为：① 模板占位符与 `{{…}}` 残留；② 合法空章只有「本需求不涉及」加依据的固定形态。
其余一律不判。步骤 8 完成条件里「不同长度……的有效夹具均可通过」加一条最短夹具：某章只有一句合法内容也通过。

**替代了什么**：替代任何以字数、行数、条目数为阈值的占位判断。

**结果判据**：grep 步骤 8/9 新增代码不含长度阈值常量；最短夹具 PASS。

### B6 · 步骤 6 的材料状态会有三份记录

**证据**：现有导入回执 `import_sources.py:471-473`（`RECEIPT`），流程契约里的 `inputs` 哈希表 `story_flow.py:474-482`，

**目标形态**：材料状态字段只在 manifest；story-flow 只引用 manifest 的 digest；导入回执改为 manifest 的生成事件或删除。

**替代了什么**：替代回执 + inputs 表 + manifest 并存。

**结果判据**：grep 三个脚本，材料文件的 sha 只在一个模块计算；`story-flow.json` 无 `inputs` 字段。

### 6.2 残余（开工步骤 6、9 之前改；不影响步骤 1–5）

**R1 · 跨章统稿又是一次整篇产出。** `steps/09:20` 与 D4「全部章节完成后做跨章统稿」没有限定统稿的产出形态。
若统稿是让作者重新输出整篇，就回到 B1 要退的「全有或全无」。目标形态：统稿只能以**逐章替换**或**定位编辑**落盘，
每次写入仍以章为原子单位，统稿前后未改动的章字节不变。结果判据：统稿夹具里只改第 5 章，其余九章字节相同；不存在一次写入整篇的路径。

**R2 · manifest 写入者与对接层的边界。** `steps/06` 实施内容 2「需求系统初始化、inbox 导入和补料入口在落盘成功后调用同一 manifest 写入者」。
现状里需求系统取材由执行者直接跑 `story.js init`（`skills/story/SKILL.md:125`），`story.js` 是各部署环境自备的对接层
（`story_flow.py:25`、需求记录 B3-9），不随包交付。若由对接层调用写入者，内网每一份自备 js 都要改，且机制层对它没有约束力。
目标形态：manifest 的（重）计算只由机制层命令承担——`story_flow.py round`（或专门的 `materials` 子命令）在每次被调用时按磁盘现状重算 manifest，
对接层只负责落盘，不知道 manifest 的存在。结果判据：`grep manifest` 在 `story.js` / `review.js` / `token.js` 零命中；
用一份不调用任何写入者的替身 js 取材后跑 `round`，manifest 仍正确生成。

**R3 · 「原子替换待写块」要由脚本承担才可测。** `steps/09` 与 D4 都写了原子替换与字节不变，但没写由谁执行。
若靠作者用编辑工具直接改 story 文件，「原子」与「已完成章字节不变」都只是期望。目标形态：提供一条脚本命令，
输入为章 id 与章内容文件，由脚本校验章锚存在、整块替换、其余字节不动；作者任务包只写「每章写入临时文件后调用它」。
结果判据：第 4 章中断夹具与 R1 统稿夹具都通过这条命令执行，测试直接比对字节。
