## 1. 目标与完成定义

批次 5 完成后应同时成立：

1. OpenCode interactive 能通过 Framework 原生 adapter 完成独立 verifier 闭环；
2. Story/Review 达到金样的形似与神似，内容随真实需求展开，不被数量配额绑住；
3. 执行者在成文前获得完整材料、十章读者任务和适用 Knowledge，不靠 checker 逐轮教学；
4. 脚本只处理确定性事实，独立 verifier 发现遗漏、略写、矛盾和编造；
5. Knowledge 按 Facts、Constraints、Design patterns 的不同生命周期被看到、理解、应用并传给下游；
6. 逐单元分配、逐字引文、token/相似度语义代理和线性裁决表退出正式路径；
7. 73 条失效形态均有现行发现者或获批退役，没有因重构失去质量守门；
8. 典型 Story 耗时持续观测并期望接近半小时，但不作为单次硬门禁。

D1 在本仓的通过只代表 Demo 验证完成；其上游补丁尚未合入发布时，内网 OpenCode verifier 仍未获得该能力，最终状态必须分开报告。

## 2. 不进入本批的内容

- headless、goal 和 OpenCode 外其他未适配 verifier 的 adapter；
- 在途 feature、旧 workspace、旧内部产物的迁移或兼容；
- Demo Knowledge 与 Demo 代码的自动同步；
- 为 Story 新建通用 Agent 编排框架、第二套 phase 状态或第二套 hook loader；
- 用更多词表、阈值、数量和文本相似度继续修旧语义 checker。

## 4. 实施会话只加载当前步骤

每次只把以下内容交给独立实施会话：

1. `test/story/AGENTS.md`；
2. 当前步骤文件；
3. 当前步骤明确指向的源码和测试文件。

不把本文、未来步骤或历史批次全文放入实施上下文。实施者按当前步骤完成后写“已实施，等待评审”，不得自行推进下一步。

## 5. 状态、评审与提交

状态只使用：`未开始`、`实施中`、`已实施，等待评审`、`不通过`、`通过`、`阻塞`。

1. 实施前记录 HEAD、工作区差异和当前步骤允许范围；已有用户改动不纳入本步。
2. 实施者完成本步代码、测试和 STATUS 实施记录，只能标记“已实施，等待评审”。
3. 本维护会话从实际 diff 重建输入、处理、输出、消费者和失败路径，在 `reviews/NN-*.md` 写独立报告。
4. 不通过时重新打开原步骤；下一步骤不得顺手修前序问题。
5. 评审通过后只提交本步骤允许范围、STATUS 和对应评审报告。每步一个可回退提交。

评审报告格式和文件名见 [reviews/README.md](reviews/README.md)。

## 6. 共同保护区

除当前步骤明确列出的文件外，以下内容默认受保护：

- 产品源码与现有业务功能；
- `test/story/golden/` 金样正文、Review 和图片；
- 两个现有真实 Story Case 的输入、对话脚本与期望结果；
- 已通过步骤的实现与评审报告；
- headless/goal 路径及未点名 adapter；
- `framework/RELEASE-MANIFEST*`，不得为迁就本地改动手工重算。

本工程直接修改 vendored Framework 只在步骤 1 已获授权；步骤 4 开始前须重新取得用户授权。Framework 漂移若需本地放行，
只能对本步精确文件使用已有真人审批机制，不得打开全局漂移开关或伪造审批身份。
步骤 1 必须同时产出以上游 `source_commit` 为基线的可复现补丁；本地 allowlist 是发布前临时验证，不是内网交付。

## 7. 质量锚与退场次序

退场次序固定为：

```text
新作者任务可达且可按章中断恢复
→ 新 verifier good/bad 有区分力
→ 准备实跑的 cli_config_id 逐个取得资格
→ 确定性生成与 Knowledge 新责任可用
→ 73 条逐项已有新发现者
→ 真实 Story 里程碑通过
→ 删除旧发现者并批准纯旧实现形态 retired
```

金样是效果的单向否决锚，不是字数和形态配额。`baseline_coverage.py` 在消费者审计前只作历史诊断；若最终没有现行消费者，
步骤 11 删除它，而不是保留一套与新语义链竞争的旧质量口径。
