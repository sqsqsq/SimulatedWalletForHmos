## 2. 设计原则（对照 AGENTS）

- **信息先于决策（§4.1）**：执行者动笔前拿到的是一份**生成的任务包**，不是五处文档的索引。生成物从真源派生，作者读它而不是读脚本。
- **模型与脚本按能力分工（§4.2）**：脚本只做生成骨架、登记、集合一致性；语义判断（图该不该进、要求是不是本需求的设计）归作者与独立审查。
- **单一真源（§5.2）**：图片的身份与语义只在 `materials.json`；知识判断只在 `knowledge-use.yaml`；章节问题与词表只在合同；任务包是它们的投影。
- **交付面通用（§5.3）**：任务包里没有 Case 名、没有维护史；词表与规则来自数据。
- **不构造异常场景**：验收只跑正常需求一次，三轴由用户评。

## 3. 机制设计

### D1 · 作者任务包：生成，不索引

`hooks/spec/author.md` 保留为 ≤40 行的原则页；新增 `hooks/spec/author.mjs`（`on_context_load` 可返回 promptFragments，framework 已支持），
按当前状态**生成**任务包片段，执行者跑 `author-context.ts --phase spec` 一次拿全：

| 任务包段落 | 从哪派生 | 回答 B 里哪条 |
|---|---|---|
| 你现在在哪、下一步跑什么 | `story-flow.json` 状态 + 三份产物在不在（spec.md / knowledge-use.yaml / story 登记 / review 渲染） | B2、B7 |
| 命令序列（含每条产出什么、之后能做什么） | 合同与 `story-build --help` 同一份数据 | B1 |
| `knowledge-use.yaml` 怎么填 | D2 生成的骨架就在磁盘上，任务包只列字段与合法值（「无候选」、`applicable: true/false`、`contract` 引 §9 名） | B1 |
| 决策登记怎么写 | 合同 `decision_categories` + 五个字段名与一条中性示例 | B1 |
| 图片清单：路径 + caption + 「story 里用或不用」的义务 | `materials.json`（D3 带 caption） | B4 |
| 十章各回答读者什么 | 合同 `chapters[].questions` | B4 |
| 客户端词表、数值来源三选一、acceptance 的 knowledge_rule 桥 | 合同数据（D6） | B3 |
| 门禁会判什么（一句一条，不带脚本名） | 合同与 check 的判据清单 | B1 |

体量上限：任务包 ≤ 12 KB。执行者不需要再读 `spec-sections.md` 的注释、`story-write.md` 的输入表、`rules.md` 的 story 段——这三处收缩为原则与形态说明，数据性内容从中移除（替代关系见 §5）。
任务包末尾一句：「门禁要的都在这里；报错会说缺什么、写到哪；不必读脚本。」

### D2 · `knowledge-use.yaml` 骨架由脚本生成

`knowledge-use.mjs init --feature <名>`：从激活清单派生每条约束一行（`id` 已填、`applicable:` 留空）、`constraint_domains` 空段、`facts` 列出激活事实的 id、
`patterns` 一行示例含合法字面「无候选」、`manifest_digest` 已填。作者只填判断。`render` 保持不变。替代：手写整份 YAML、读源码找字段。

### D3 · 图片登记脚本化，语义进材料真源

`import_sources.py register-ux <assets 里的图> --name <语义名> --caption "<这张图是什么>"`：复制到 `ux-reference/` 起名、刷新 `materials.json`。
`materials.json` 的 image 条目加 `caption`；未登记 caption 的图也在清单里（caption 空）。合同里的 `UX` 来源（README）删除——README 不再是任何东西的登记。
`story-write.md` 的义务改为一句：**清单里的每张图，要么在讲它的那一章引用，要么在附录材料清单那一行写明不引用的理由**。
`check ④` 增加一条**集合一致**：清单图片 ⊆ story 引用 ∪ 材料清单里标了「未引用」的行；差集逐张点名（判的是集合，不是该不该用）。
替代：手拷手写 README、`UX` 来源、`warn_if_siblings`。

### D4 · story 审查：留在 framework 的 verifier 协议内做对（12 号方案 B，修订）

**为什么不走独立请求（12 号方案 A）**：framework 的 verifier 协议只认一种请求 `maison_verifier_request`（`verifier-request.ts`），
每次 harness 一个 subject、一份报告；三个有发布器的 adapter（claude、codeagent 走 `subagent_stop` 钩子，opencode 走 `task_tool_result` 插件）都按这一种对账。
加一种「story 审查请求」= 改 framework 协议 + 三个发布器 + 回执的证据规则，是 framework 需求，不是 adapter 的 bug。二跑里 resume 没发布也不是 bug：
resume 用的是自由文本，不带 request JSON，插件按协议拒绝；第三次带正确 request 的调用正常发布了。

所以本步不改 framework、不改任何 adapter，在协议内把四件事做对：

1. **送达**：`pre_verifier.mjs` 把 overlay 里**全部**扩展判据（不只 `knowledge_` 前缀）写进输出要求；story 审查这一项放在片段最前，
   写明「先读 `AR/story.md`、`AR/story-src/materials.json`（图片逐张）、`decisions.json`，再答本项」，输入按路径列出；
2. **一种格式**：结果只按 framework 的 YAML 契约——`checks[]` 里一条 `story_reader_review`，`details` 下 `blocking_findings` 与 `advisories` 两个列表（空列表是结论）；
   overlay 里那段 markdown 块要求删除；
3. **一处真源**：`storyReviewProblems` 只读插件发布的 `verifier.report.<subject>.json` 的 `report_text`，不再匹配任意同名文件；
4. **问对问题**：任务书由合同渲染（`story-build review-task`），含十章读者问题、章级维度、**图片逐张「用了 / 未用及理由是否成立」**、关键事实缺失与编造两问。

一个会话既审 spec 又通读 story 的摊薄风险仍在，第三跑用它的行为读数判：审查者报没报用户找到的问题。若仍漏，再向 framework 提「多 kind 请求」需求，
不在扩展里造旁路。替代：overlay 的 markdown 块要求、`verifier-report.mjs` 的块解析与任意文件名读取、`pre_verifier` 的前缀过滤。

### D5 · 顺序由状态说话

`story_flow.py status` 扩到 spec 阶段内：登记前打印「story 未登记：先 init → skeleton → chapter×10 → 统稿 → story 登记，再跑 harness」，
登记后打印「跑 build → 审查 → harness」。D1 的任务包首段引用同一函数的输出，两处一个真源。关卡顺序同理（「材料先签关卡再导入」由 `status` 在 S3 前打印）。
替代：`phases/spec.md` 里靠散文讲顺序（保留顺序图，删「为什么」以外的操作细节）。

### D6 · 门禁教的东西前移成数据

`lint-rules.mjs` 里写死的客户端语境词表迁到合同 `client_vocabulary`（词 + 改法）；数值来源三选一的标签与 acceptance `knowledge_rule` 桥的形态写进合同；
D1 从合同渲染进任务包，check 与 post_check 从同一份数据判。替代：脚本内词表、只在报错里出现的规则。

### D7 · 装置

- `run_multi_case.py` 改黑名单复制（排除 `.git / output / test / tools / scratch / 构建产物 / doc/features / harness state`），**`node_modules` 不排除**——工作区就是一个能直接跑的工程，被测模型不该花时间装依赖（用户 2026-09-04 裁定）；边界校验不变；
- `measure_run.py`「读 checker 源码」把 bash 里 `readFileSync / cat / sed` 读 `.mjs/.py/.ts` 计入；
- 启动空档 4.5 分钟：记录 opencode 启动到首条会话事件的时间并查因，不在本步修。

### D9 · verifier 只跑一次，且在最后

顺序固定：三份产物定稿 → `story-build check` 与 spec 确定性门全绿 → **story 读者审查（D4）** → spec harness 产出 request → spec verifier 一次 → 回执。
verifier 之后不再改任何产物；改了就等于重来（subject 换代），这句写进任务包。
任务包写明：verifier 的调用只能带 request JSON，不用自由文本 resume——插件按协议只认前者。替代：主模型手写 `verifier-report.md`、resume 补做、二次重审。

### D10 · `chapter` 的输入契约写清并容错

任务包与 `story-write.md` 各一句：章文件只放正文，不带章标题与 H1。`chapter` 命令若发现文件首行是与本章同名的 `## ` 标题（或 H1），剥掉再落盘——这是格式规范化，不是语义。
替代：两跑都发生的「rm story.md 重建骨架重灌」。

### D11 · S1–S4 的侧车形状由 `status` 给

`story_flow.py status` 在需要某个侧车的那一步，打印该侧车的 JSON 骨架（字段与合法值，从代码里的读取函数派生，不另写一份），并在 S3 前打印「先签关卡再导入」。
替代：`init_analysis.md` 里靠散文描述侧车、作者切片读源码。

### D12 · 扩展要求的登记义务进任务包

`context-exploration.md` 的 `key_inputs_read` 要登记作者任务包来源（扩展 overlay 声明的 `phase_input_snippets_extra`），任务包首段直接给出要登记的那一行。
替代：作者在 `context_exploration_inputs_coverage` 上红一轮才知道。

### D8 · 上游观察（不改，登记）

framework 侧本跑合计约 30 分钟，逐条登记回 framework（`AGENTS §3`），性能轴评分时与扩展耗时分开呈现：
- spec 前置：personal-setup 跑三次（脚本路径要 `scripts/` 前缀、要显式 `--project-root`）、视觉自测卷、对两张占位线框做 OCR；
- OCR 没有文档化的入口，作者翻了 `fidelity-shared.ts`、`ocr-toolkit.ts`、`goal-phase-runtime.ts` 才找到 worker；
- `facts.md` 的 frontmatter 字段、`acceptance.yaml` 的 schema 都没随模板送达，作者读源码学；`page_description_completeness` 把非页面小节当页面判；
- `ai-prompt.md` 117 KB，verifier 分三次才读完；任何产物改动都换 subject，verifier 只能整份重跑。

## 4. 三跑的验收（一次 CLI，用户三轴评分）

- **产物结果**：清单里的图逐张有去处（引用或写明不引用）；主流程有图；小节编号干净；`reader-review` 两类结论落盘且图片逐张有答复；用户读 story/review 给分。
- **性能**：从 spec 进入到 story 登记 ≤ 15 分钟；扩展环节（成文 + 审查 + 门禁）合计 ≤ 30 分钟；framework 前置与人工等待单列；上下文 ≤ 150K；读脚本（含 bash 形态）0。
- **Knowledge**：保持二跑水平（YAML 真源、生成区、判定表一致）。
- 审查者区分力：用户在真实产物上找到的问题，`reader-review` 报没报——两跑各一条负面证据（图降级、图缺席）是对照基线。

## 6. 实施与评审方式

作为**步骤 12**，一个方案、四个可回退提交（D1+D2+D5+D6+D10+D11+D12 作者链；D3 图片；D4+D9 审查与顺序；D7 装置），逐个评审但**不跑 CLI**；四个都通过后全量离线、金样、静态测试全绿，再跑一次 CLI。
每个提交的自述附：作者任务包的实际渲染样例（用金样 Case）、`grep` 命令与命中数、预算读数。

## 7. 为什么这是正向设计而不是打补丁（判据与对照）

补丁的形状是：在报错处改一句话、加一个特判、让门禁多认一种格式、加一条夹具证明某个字段出现了。它治的是那一次的症状，下一个需求换个形状照样撞。
正向的判据五条，每条都能在本设计里指认，也能在下一跑的行为上核对：

| 判据 | 本设计怎么满足 | 补丁会怎么做（对照） | 下一跑怎么看 |
|---|---|---|---|
| 从行为链起点找缺失（AGENTS §2、§4.1）：问「执行者做这个决定时手上缺什么」，不问「哪条报错没说清」 | §1 的 B1–B16 每条都写「它当时缺什么」；设计对应到缺失，不对应到报错 | 把 harness 报错文案改得更详细；给 `no_candidate` 加一条纠错 | 作者读脚本次数（含 bash 形态）为 0；同一门禁 FAIL 不超过 1 轮 |
| 信息在决策之前送达，且只送一份 | D1 生成任务包，进 spec 时一次拿全；D2/D11 骨架与侧车形状在写之前就在磁盘上 | 在五处文档各补一段说明，让作者自己拼 | 任务包 ≤12 KB；作者读规则文本 ≤20 次 |
| 真源唯一，提示词是投影（§5.2） | 图片语义只在 `materials.json`；字段与词表只在合同；任务包、任务书、门禁三者从同一份数据派生 | 在 README 和作业书各写一份图片清单 | 改一处合同数据，任务包、check、审查任务书同时变 |
| 每个新增都写替代物，规模不涨 | §5 替代关系表；预算仍在 8350 内 | 只加不减 | 预算门绿；退场项 grep 为零 |
| 用真实行为验收，不造异常场景 | §4 只跑一次正常需求，指标是行为读数与用户三轴 | 为每个新判据造 good/bad 夹具证明它「能拦」 | 一次 CLI 的 `measure_run.py` 读数 + 用户评分 |

一个具体对照：图片两跑都丢。补丁是加一条「材料图片必须出现在 story」的门禁——作者会为过门随手塞图，S01 图降级形态换个样子回来。
正向是：登记时给图一句 caption（真源）→ 任务包逐张列出「这是什么」（送达）→ 作者义务是「用，或写明不用的理由」（判断归作者）→ check 只核集合（脚本兜底）→
读者审查逐张问「用了没有、理由成不成立」（语义归审查者）。四层各担各的，缺哪一层都不靠另一层硬顶。
