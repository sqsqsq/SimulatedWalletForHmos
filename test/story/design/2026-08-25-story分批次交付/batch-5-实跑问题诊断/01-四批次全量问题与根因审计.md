# 批次 5 · 批次 1～4 全量问题与根因审计

> 状态：**原因审计已收口（2026-09-02），具体解决方案尚未制定**。
> 本文回答三件事：四个批次分别出现过什么问题；这些问题最早从哪里产生；跨批次共同根因是什么。
> 本文不把「某次脚本已通过」写成「问题已彻底解决」，也不提出具体实现方案。

## 0. 范围与口径

### 0.1 「四批次」的范围

本文所说的四批次是：

1. 批次 1：知识应用；
2. 批次 2：adapt；
3. 批次 3：extension 机制正向重构；
4. 批次 4：评审载体的内容与表达。

批次 0、1.0/2.0 旧轮次和 2026-08-13～08-24 的设计，只在需要回答「问题最早从哪里来」时作为证据，
不另算第五个审计对象。

### 0.2 两个最终目标

本轮所有问题和根因最终都要回到用户给定的两个目标：

1. `story.md + review.md` 符合要求；典型材料与目标模型的产出耗时期望接近半小时，但该时间只作持续观测和优化目标，
   不作为单次运行的硬性 PASS/FAIL 门槛；
2. 知识在合适时机被正确执行体看到、理解、应用并传给下游，而不是只被声明、抄写或通过门禁。

这里的知识内容是可适配样板。真实内网代码仓会按自身事实修正和扩展知识；批次 5 要保证的是任意适配后的知识都能沿消费链生效，
不是让 Demo 样板与 Demo 业务代码永久自动同步。

### 0.3 证据范围

- `01-全批次需求记录.md` 的 40 条主需求与通用纪律；
- 批次 0～4 的 STATUS、方案、判据、交付与测试报告；
- `test/story/EVOLUTION.md`、冻结 spec、`03-踩坑记录.md`；
- `doc/extensions` 当前实现与 114 个历史提交；
- 8 月 31 日以来的外网实跑，以及内网反馈；
- 批次 5 的 [00-问题记录与原因分析.md](00-问题记录与原因分析.md) P1～P16。

### 0.4 本文中的三个层次

| 层次 | 含义 | 例子 |
|---|---|---|
| 现象 | 使用者直接看到的结果 | check 报 1600+；图片一张没进 story |
| 直接原因 | 直接触发该现象的规则或代码 | 红线扫描图片路径；`material_only` 只核四字理由 |
| 系统根因 | 使同族问题反复出现的设计选择 | 用字符串门禁判断语义；分母由被检查者自己决定 |

同一个系统根因可以在不同批次产生不同现象。审计以「最早形成根因的时间」判归属，不以「最后一次被看见」判归属。

### 0.5 维护视角

Framework + Extension 的本质是指导执行者开发需求的 AI Agent 系统。本文中的作者、writer、被测模型和内网使用模型
都属于**执行者**；分析问题、设计机制、修改实现、调度测试和独立审查属于**维护者**。

维护者掌握的 checker 源码、测试 Case、历史事故和实现坐标不是执行者的可用输入。凡是依赖执行者读取这些维护信息才能成功的机制，
均按 Agent 系统设计失效分析，不把它改写成「再提醒执行者一次」。

## 1. 全量审计结论

四个批次不是四组互相独立的问题，而是一条连续演进链：

1. 批次 1 建立知识链，但 framework 不消费 `provides.knowledge`，知识的送达、理解、应用落点和下游传递没有形成可观察的行为链；
2. 批次 2 为 adapt 增加了超出目标的状态、指纹、备份与归类机制，多次删除后才回到「模型主导、脚本机械核对」；
3. 批次 3 为解决内容遗漏和知识不落地，建立来源单元、三态台账、作者裁决与逐字引文，模型与脚本的职责由此开始倒置；
4. 批次 4 在这套结构上继续增加语言、形态、固定格式、逐问与逐章判据，旧问题没有消失，而是换成判据互斥、规模失控和长时间修门禁。

提交史支持这一判断：

| 类别 | 数量 | 说明 |
|---|---:|---|
| 新能力 | 32 | 真正增加新功能或首次建立能力 |
| 修真实实跑缺陷 | 24 | 修复不是上一笔改动制造的故障 |
| 修上一轮修复引入的问题 | **30** | 新修复直接修前一轮或相邻提交制造的问题 |
| 从 0 重做 / 整体重定义 | 12 | 整文件或整套机制替换 |
| 回退 | 2 | 提交级回退；另有工作区 reset 与整轮作废未计入 |
| 清理与重命名 | 12 | 删除旧机制、死代码与残留 |
| 版本与适配 | 2 | manifest 与 framework 适配 |

「修上一轮修复」已经多于「修真实实跑缺陷」。这说明主要成本不再来自新增需求，而来自机制之间互相制造问题。

复杂度也呈同样趋势：批次 3 收口时 `story-build.mjs` 为 725 行，当前为 2443 行；`lint-rules.mjs`
从 271 行涨到 880 行；非知识层总量从 9764 行涨到 13760 行。同期新增的业务目标没有同比增长。

建立项目知识、规约、设计模式三类知识，以及 spec 识别、plan 冻结、coding/review/ut/testing 落实的完整链路。

### 2.3 本批留下的结构性债务

批次 1 的核心问题不是三类知识样板内容本身，而是「知识如何可靠送达、如何证明理解与应用、如何把已形成的结果传给下游」没有闭环。
后续批次把更多检查叠到 extension 内部，但没有改变 framework 零消费、作者面靠自觉、行为链未被观察这三个前提。

它证明同一个规律：没有先定清模型与脚本的职责时，脚本会自然膨胀成并不理解业务语义的决策器。

### 4.3 本批留下的结构性债务

批次 3 删除了旧逐章取材器，但用「来源单元 → 三态分配 → 作者裁决 → 逐字引文」建立了另一条更重的生产线。
它解决了「有没有登记」的问题，却没有可靠解决「内容是否真正讲清」。模型开始承担枚举、归位和抄录，脚本开始用 token
与子串判断语义，这是批次 4 大规模失控的直接基础。

| B4-P15 | check 回环和上下文失控 | 外网 20 次有读数 check、报告记 24 次；story 1小时41分；上下文增量 572K | 同一模型串行分配、写作、裁决、修复；每次只暴露下一层错误 | RC2 职责倒置；RC4 自我裁决；RC10 线性复杂度 |
| B4-P16 | 内网规模下裁决核实超过 1000 条 | 单元数增大后，引文过短/找不到/无行/回声线性增长 | 一单元一行、一行一引文的证明模型 | RC10 线性复杂度 |
| B4-P17 | framework 3.0.0 后 opencode 无法闭环 spec | adapter 未登记 verifier capability，required 模式直接 blocked | extension 无覆盖入口，测试终点却设为 plan | RC7 协作契约不完整；RC8 测试前提未校验 |
| B4-P18 | 测试装置把 runner hint 记成真实阶段 | `cli_run_started` 用 `next_unclosed_phase or end_phase`；`gates_started` 直接写 `phase=end_phase` | 「准备运行目标阶段门禁」被当成「模型已经到达目标阶段」 | RC8 验证失真；RC5 状态所有权错误 |
| B4-P19 | 批次状态与实际交付不同步 | 批次 4 STATUS 停在 F2，F3～F8 未登记；设计目录被 gitignore | 没有常驻、受版本管理的唯一进度记录 | RC5 多真源；RC9 演进治理缺失 |

### 5.3 本批的性质

批次 4 确实直接引入了图片互斥、`material_only`、部分语言/格式误判和 framework 3.0.0 verifier 阻断，
但 1600+ 报错、长时间成文和脚本膨胀不是独立的新问题。它们是批次 3 的逐单元证明模型，在批次 4 继续叠加判据后的规模结果。

## 6. 根因层级

### 6.1 两个上位维护认知根因

| 根因 | 定义 | 历史表现 | 直接后果 |
|---|---|---|---|
| MRC1 · 把 Agent 系统当作代码产品优化 | 维护决策围绕脚本结构、规则命中和门禁变绿，而不是执行者的输入、理解、决策、产物与成本 | 每次实跑失败优先增加判断、阈值、表格或例外；字段存在与 check PASS 被当作能力成立 | 产生 RC1、RC2、RC8、RC9、RC10，并持续放大复杂度 |
| MRC2 · 维护者与执行者视角混用 | 把维护者掌握的源码、规则、测试和历史默认成执行者能够发现或应该理解的信息 | 要求执行者主动找 author.md、读 checker、从报错学习条件、在同一上下文自我裁决 | 产生 RC3、RC4、RC6、RC7，并使 RC5 难以及时暴露 |

这两个上位根因解释为什么用户反复要求「正向设计」，实际方案仍从当前代码和最后一条 FAIL 出发。它们不替代下面的机制根因：
MRC 说明维护方法为什么持续制造问题，RC 说明系统具体在哪一层失效。

### 6.2 十个机制根因

| 根因 | 定义 | 跨批次证据 | 为什么局部修补无效 |
|---|---|---|---|
| RC1 · 用代理指标替代目标 | 用 token、子串、字数、数量、表格存在性代替语义质量 | 知识「写了名」即应用、`covered_by` 共享 token、12 字引文、图片数量、术语精确子串 | 模型会找到满足代理指标的最省力形态，但真实目标仍可失败 |
| RC2 · 模型与脚本职责倒置 | 脚本做语义决策，模型做枚举、抄录和状态维护 | adapt 归类引擎；story 数百行分配与引文 | 新材料一换，脚本误判；规模一大，模型机械工作爆炸 |
| RC3 · 要求在失败后才送达 | 作者事前拿不到完整、可执行的工作合同 | author.md 靠自觉；真实 token/path 条件只在报错或源码 | 每轮先写错再学习，check 成为教学器而不是验收器 |
| RC4 · 作者与裁决者不独立 | 同一执行体在同一上下文写、判、修 | story 第④步由作者裁决；opencode 无第二执行体 | 裁决容易成为自证，修订又继续污染裁决上下文 |
| RC5 · 多真源、多状态、多契约 | 同一事实由多个文件或状态重复表达 | manifest/扩展自解析、目录/README、story-flow/framework phase、文本/hash/材料状态 | 改一处必然漏另一处，相邻判据开始互相否定 |
| RC6 · 知识消费生命周期未证明 | 没有端到端证明知识在正确时机被看到、理解、应用并传递 | `provides.knowledge` 零消费、作者面靠自觉、内网「只有 spec 生效」、任意新知识未做穿透试验 | 局部增加登记表只能证明声明存在，不能证明实际消费 |
| RC7 · framework/extension 协作契约不完整 | extension 需要的作者送达、知识消费、verifier 能力没有完整宿主协议 | `provides.knowledge` 零消费；opencode verifier blocked；两套状态只单向相接 | extension 只能自建旁路，旁路又形成第二套框架 |
| RC8 · 验证系统不能可靠证明行为 | 离线结构绿、可见 Case 通过或错误读数被当作行为证据 | holdout 未揭盲；度量漏 `tool_output`；runner hint 冒充阶段；原生 gate 被当验收 | 优化围绕已知 Case 和错误仪表进行，内网自然暴露新形态 |
| RC9 · 演进以追加补丁为默认动作 | 每次失败先增加检查、例外或说明，没有同步删除旧职责 | 30 个提交修上一轮修复；21 组 check；非知识层持续增长 | 新旧规则叠层，历史原因消失但代码和文字仍留下 |
| RC10 · 证明模型随输入线性增长 | 每个来源单元都要求人工落点和引文 | 355 单元需 198 行裁决；内网约 2000 单元产生 1000+ 错误 | 调阈值只能改变常数，不能解决规模复杂度 |

当前 Framework 生命周期还有一项必须保留的实现事实：`pre_verifier`、`on_context_load`、`post_verifier` 与 `post_phase`
在真实 verifier 执行之前连续触发；只有 verifier capability enabled 且脚本 PASS 后才装配并执行 verifier。
因此 `post_verifier` 不能读取本轮尚未产生的 verifier 报告。该事实属于批次 5 的设计输入，不作为跨版本常驻规则写入 AGENTS。

## 7. 根因之间的因果链

```text
把 Agent 系统当代码产品（MRC1）+ 维护者/执行者视角混用（MRC2）
        ↓
framework/extension 缺少作者与 verifier 的稳定协作契约（RC7）
        ↓
extension 自建作者面、知识解析、状态和裁决旁路（RC3、RC5）
        ↓
为证明内容与知识生效，引入可机械计算的语义代理（RC1）
        ↓
模型负责填台账和抄引文，脚本负责猜语义（RC2）
        ↓
作者自己裁决，且证明量随来源单元线性增长（RC4、RC10）
        ↓
真实实跑失败后继续追加判据与例外（RC9）
        ↓
可见 Case 逐渐变绿，但测试与度量没有证明泛化（RC8）
        ↓
外网 200+、内网 1600+、图片清零、耗时 1.5 小时集中爆发
```

## 8. 为什么反复强调「正向设计」仍然变成了补丁

### 8.1 每轮以现有实现为起点，而不是以原始目标为起点

方案通常回答「怎样让这次 FAIL 消失」，没有先回答「理想作者、脚本、verifier 各自应该做什么」。
因此上一轮的结构被默认保留，下一轮只能在它外面增加围栏。

### 8.2 完成判据偏向「新检查已通过」

只要新增判据和当前 Case 通过，就容易把它记为完成。旧职责是否删除、总体复杂度是否下降、未知材料是否仍成立，
没有同等强度的完成条件。

### 8.3 正例、反例和 holdout 没有形成固定三联验收

失败 Case 同时参与了设计、调试和验收；holdout 多次登记但没有真正揭盲。机制学会了当前样本的形态，
却没有证明换材料仍成立。

### 8.4 代理判据天然鼓励继续补规则

token 误报就加豁免，图片漏了就加数量，数量仍漏就按章计数，引文无效就加字数、句边界和复用次数。
每一步都能修当前症状，但没有一步改变「脚本正在替代语义判断」这个根因。

### 8.5 没有“删除旧机制”这个强制出口

虽然需求记录要求新增机制说明替代了什么，但批次 4 的实际演进仍以增量修改为主。行数和回环目标只被记录为未达，
没有阻止下一轮继续叠加。

## 10. 进入具体方案前已经确定的边界

以下是原因审计得出的处置方向，不是具体实现方案：

### 10.1 现有能力中有独立价值、应保留的部分

- 材料关卡、范围关卡与流程契约的业务语义；
- docx 转正文、图片抽取和材料导入；
- review 的确定性渲染能力；
- 三类知识的内容边界与 manifest 激活清单；
- adapt 的所有权原则；
- 金样、反例夹具、真实 Case 与隔离测试装置。

### 10.2 必须重新定义职责的部分

- story 作者的输入包和成文流程；
- 内容守恒、人读质量、图片价值与重复判断；
- 作者和语义裁决者之间的上下文边界；
- 适配后知识在各阶段的可见时机、理解任务、应用落点和下游传递；
- opencode verifier 与 framework 阶段闭环；
- story-flow 与 framework phase 的状态所有权。

### 10.3 不能继续作为长期机制保留的部分

- 用 token/子串/字数近似「讲清」的语义门禁；
- 每来源单元一行的人工裁决与逐字引文证明；
- 由被检查者用自由理由调整验证分母；
- 同一事实的第二登记表或第二状态账本；
- 为历史格式静默降级的兼容分支；
- 只为当前两个 Case 增加的例外与阈值。

### 10.4 具体方案尚未确定，但制定与审查方式已冻结

- 具体解决方案由维护者与用户逐项讨论后另起方案文件；本文中的处置边界不等于已经选定实现。
- 实施步骤按一条完整行为链或职责闭环拆分，不按“修改一个文件”拆分；每步写清输入、送达、理解/决策任务、输出、消费者、失败路径和证据。
- 另一个独立会话一次只实施当前步骤，只能声明“已实施，等待评审”；本维护会话从实际 diff 重建行为并决定通过或返修。
- 当前步骤未通过前不读取或实施下一步骤；后续发现前序问题时重新打开原步骤，不在后续步骤顺手修改。
- 单步验收使用冻结范围、结构证据、离线测试和独立语义审查，不把耗时 2～4 小时的真实 Story 作为每步完成条件。
- 真实 Story 由维护者与用户按依赖闭合程度、风险和成本选择少量里程碑运行；完整子链首次接通和最终 holdout 是候选点，
  不是机制写死的次数或固定时点。未经过适用里程碑实跑的步骤不得宣称对应行为已验证。
