## 1. 原则

- **形态来自内容的关系，不来自金样。** 金样是按一个具体需求写的，它有的表不等于每个需求都要有。每一章、每个约定小节都写明**主要用什么表达**——叙述、有序列表、无序列表、图、材料里的图片、引用、标签段、先拆子节——表只是其中一种，只在术语、多方分工与取舍与风险、异常、验收和附录这几处是主形态。机器只核这几处的槽位存在与必有列，不定恰好几列、不定行数、不定表的数量；别处不建表，`story-write.md`「不是鼓励表格」那一段原样保留，而且从此是真的。
- **一个真源、三处消费。** 形态、图片引用串、附录 D/E 的行、acceptance 要接的键，都从合同与登记数据派生，`skeleton` / 任务包 / `check` 读同一份，改一处三处跟着变。
- **规则写进 md，脚本只兜底。** 「verifier 之后做什么」「补料后停不停」先在 SKILL 与 phases 里写清，脚本只把状态答对、把错顺序拦住。
- **交付面不写轮次。** 注释与提示词只讲当前；哪一跑撞到什么留在本目录的 reviews。

## 2. 改动

### F1 · 形态真源：合同定槽位，骨架渲染，check 守存在

**合同**（`contracts/story-chapters.json`）：每章与每个约定小节加 `form` 字段，两部分——

- `primary`：这一段**主要用什么表达**，取值覆盖全部形态：`prose`（叙述）、`ordered`（有序列表）、`list`（无序列表）、`table`、`diagram`（作者画的图）、`image`（材料里的图 + 一句承接）、`quote`（引用材料原话）、`labeled`（「发生 / 处理 / 之后」这类加粗标签段）、`subsections`（先拆子节，形态在子节里定）。可带 `also`（允许的次要形态）与一句 `note`。这一部分是**建议**，进任务包与骨架的注释，`check` 不核。
- `fixed`：少数几个「这种内容天然就是这个形态」的槽位，`check` 核存在；`table` 只写 `columns` = 必有列，`diagram` 只写「至少一张」。条件槽位写 `when`，条件只取已有数据（`split.parts` 有兄弟单据；`decisions` 有 settled 条目；材料清单里有界面图）。

- **附录 A/B/C**：由 spec §9.1–9.5 与 Scope 模块清单生成——A 接口（含入参→出参、错误码）、B 数据·配置·事件（含值结构、有效期）、C 改动边界；作者只补「给评审者看什么」那一句，不重打表。`check ⑫` 核附录三表的行集合 ⊇ spec §9 对应表的行（按第一列的标识对齐）。
- **数据模型总览**：spec §9.2 的值结构就是数据模型；story 不另起「数据架构总览」一节，B 表把值结构列带上即可——评审者在附录一处看全，不在主叙事重复。

### F8 · 图：哪种图讲什么，画一张完整的（用户 2026-09-05 诉求 2）

| 图 | 讲什么 | 什么时候用 |
|---|---|---|
| 流程图 flowchart | 一条业务从触发到终态的走向与分支 | 默认选它：分支多于两条、有决策点；spec §5 就是这种，复用即可 |
| 时序图 sequenceDiagram | 多方之间谁先调谁、回什么 | 参与方三个以上且交互顺序本身是要审的内容（如授权必须在创建签约之前） |
| 状态图 stateDiagram | 一个对象的状态与转移 | 关键状态四个以上且转移条件复杂；状态少于四个用「关键状态」小表 |
| 关系图 erDiagram | 数据实体之间的关系 | 只在附录 B 有多张表互相引用时用；单实体不画 |
| 类图、部署图 | 实现结构 | 不进 story |

必要性与准确性的规则（写进 `story-write.md`「什么内容用什么形态」下面，`check` 只核第一条）：

1. 业务流程章**章首一张完整的图**，覆盖主路径与全部分支去向；分支节里不再各画小图，除非那条分支本身是一段多方交互。零散的三四张小图不如一张全图。
2. 图里的节点用中文业务名，与 §5.1 主路径的步骤一一对应、与 spec §5 一致（复用即一致）；图讲结构，文字讲为什么，两者不互相复述。
3. 材料里的流程图图片可以另引在讲它的那一节（例如服务端触发），但它是材料的视角，不代替本特性的那张图。
