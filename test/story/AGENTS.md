# Story Extension 维护契约

> 本文件约束整个 Story Extension 的维护：Framework 协作、skills、hooks、knowledge、adaptation、测试能力与交付入口。
> 它写给维护者，不进入消费模型上下文。

## 0. 权威入口

- **维护 Extension**：先完整阅读本文件，再按本次任务取得需求、设计和状态记录。
- **运行、修改或评价 Extension 测试**：先读 [TEST.md](TEST.md) 的任务索引，再完整读取对应分支；真实CLI启动前须读完其运行协议。
  测试命令、状态、证据与评分只在那里维护；本文件不复述。
- **追溯历史**：读取 [EVOLUTION.md](EVOLUTION.md)。历史方案只提供演进证据，不直接成为当前实现依据。
- **判定当前需求**：维护任务以用户本次给定的目标、需求、计划和状态为输入；在 `test/story/spec/`、`test/story/design/` 中按该任务查找已有材料。
  无法确定对应任务时补齐歧义，不默认进入某个日期或最新轮次。`doc/features/*` 是历史产物，不是需求真源。
- **运行模式范围**：当前 Story Extension 的设计、实现和验收只覆盖 interactive。headless/goal 不进入当前范围，
  不为它们增加兼容、状态或测试，也不把“未覆盖”写成“已支持”；未来只有用户明确提出时另立需求和验收。
- Framework、Extension 的全部生命周期能力及其 Skill、Hook、Knowledge、Adaptation、Harness、Verifier 和测试都是被维护对象。
  维护者直接检查其源码、配置、测试和产物，
  不调用被维护系统的流程来设计或证明它自身正确。

## 1. 维护与消费的角色

本项目按维护设计者、维护实施者和消费模型分工。前两者属于本项目维护团队，“维护者”是两者的合称，只用于共同义务；
它不是另一种角色，也不表示一个会话可以同时包办方案与实现。历史记录沿用旧称“执行者”，按语境区分，不追溯改名。

### 1.1 维护设计者与维护实施者

| 角色 | 本项目负责 | 交付与边界 |
|---|---|---|
| 维护设计者 | 定位 Extension 的行为问题和最早失效点；澄清需求，为 Framework 协作、Extension 机制、knowledge、adaptation 和测试能力制定正向方案与验收标准；审查实现和真实执行证据，据此决定下一轮修改 | 交方案、判据和评审结论；不代维护实施者修改产品 |
| 维护实施者 | 按有效方案实现或修正上述对象；保证交付给消费模型的内容符合 writing-for-agents：要求在使用前送达，任务边界清楚，完成条件可检查；运行方案确定的验证并提交证据 | 交实际改动、验证结果和未决问题；关键设计受新事实影响时返回维护设计者 |

§7 中的“方案制定者”“reviewer”和评审，均指维护设计者承担的方案与评审职责；各级确认权限按 §7.5。

维护者的共同义务：

- 直接检查被维护对象（§0），维护会话不进入被维护系统的业务管线。
- 按 `TEST.md` 调度 CLI 观察真实执行行为，由本次任务指定的维护角色担任宿主。宿主仍是维护者，只是临时代理人类需求方：
  自然回答需求问题、交付材料、观察过程与结果；不向消费模型提供测试答案、维护历史、脚本命令、文件坐标或实现路径。
  `TEST.md` 中的宿主、观测者和需求方代理，都是维护者在测试模式下的职责。

### 1.2 消费模型

消费模型不属于本项目维护团队。它是使用 Framework + Extension 在目标工程开发真实需求的模型，包括外网隔离 Case
启动的被测模型和内网仓实际使用 Extension 的模型。

消费模型正常完成任务只依赖需求材料、目标仓事实、Framework 与 Extension 上下文。交付内容不要求或引导它读取
`test/story/`、历史方案、失败用例或 checker 源码来学习要求。消费模型读取 checker 只是调查信号：是否属于 Agent 系统问题，
须结合 Story/Review 质量、性能、Knowledge 应用及跨 Case/配置的重复情况判断，不能凭一次读取直接下结论。
明确的工具或脚本内部错误可以读取相关实现定位，但不能据此改业务产物迎合隐藏判据；发现的问题回维护层处理。

被测模型就是消费模型。verifier 是产品内部的独立审查能力，按 Framework + Extension 的使用流程工作。

## 2. 这是 AI Agent 系统

Framework + Extension 的本质是一套指导模型完成需求开发的 **AI Agent 系统**，不是代码产品。
提示词、知识、脚本、门禁、状态文件和报告只是实现载体；系统的评价对象是消费模型在未知需求上的行为。

端到端能力和会影响消费模型行为的机制用同一条行为链描述和验收：

```text
输入事实 → 按时送达 → 正确理解 → 做出决策 → 产生产物 → 传给下游 → 失败恢复 → 留下证据
```

代码通过、字段出现、门禁全绿或报告写了结论，只能证明载体的局部性质。消费模型是否在不接触维护材料的情况下，
以合理成本得到符合目标的结果，才是能力是否成立。

局部确定性能力只需证明它实际承担的输入、输出、失败语义和消费者；不为文件解析、路径检查等 helper 强行增加模型理解、
verifier 或真实 CLI。局部能力组合成用户可见行为时，再沿完整行为链验收。

## 3. Framework、Extension、Knowledge 与测试的所有权

| 部分 | 负责 | 不负责 |
|---|---|---|
| Framework | 通用阶段、上下文装配、工具、宿主能力、verifier 调度、阶段闭环与公共扩展点 | 实例业务知识、Story 专属产物语义 |
| Extension 机制层 | 需求流程、作者任务、阶段扩展、知识路由、产物合同和确定性辅助能力 | 目标仓专名、测试答案、Framework 通用能力的影子实现 |
| Knowledge | 项目事实、规约和设计模式；内容由目标仓维护 | 阶段调度、消费方坐标、测试与维护历史 |
| Adaptation | 按目录所有权安装/升级机制与入口；已有目标知识保持原样，首次建知识骨架并扫描部件画像 | 升级时替目标仓改知识，首次灌入demo具体知识，或按业务改写通用机制 |
| 测试域 | 隔离输入、调度、观测、证据留存、离线回归与真实行为评价 | 替消费模型完成任务、把用例答案注入交付物 |

问题修在最早拥有该职责的位置：通用宿主能力回 Framework，实例行为回 Extension，项目事实回 Knowledge，
适配行为回 Adaptation，观测与测量错误回测试域。缺少 Framework 能力时明确提出或补齐 Framework 能力，
不在 Extension 内复制一套旁路框架。

`.opencode/` 是**本仓 story 分支的 CLI 测试装置**：外网实跑用 opencode，内网用 codex。
它不进 `story-adaptation` 的包，也不为内网适配。opencode 的 `verifier_subagent` 登记与
子代理模板是本仓对 framework 的仅有两处差异，不含逻辑改动，按 drift 具名长期放行、
不交上游；framework 升级时 `init.task_decision` 对这两处选「保留」。

Framework 的正式交付落在其权威源，并由 framework-init UPDATE 进入消费仓。本工程 vendored `framework/` 只有在用户明确授权的
单步验证中可以临时修改；本地验证通过不等于上游或内网已经获得能力，交付时须保留上游基线、可复现补丁和临时放行的失效条件。

## 4. Agent-first 设计

### 4.1 信息先于决策

消费模型做决定之前，所需目标、事实、约束、可用能力和完成条件必须已经进入它的实际上下文。
文件在磁盘上、manifest 有登记、hook 返回了文本，都不等于消费模型已经看到。

报错负责指出哪个既定条件未满足以及如何回到正确路径；它不是首次交付规则的渠道。消费模型依靠连续失败才逐步学会要求，
说明作者输入不完整。

### 4.2 模型与脚本按能力分工

- 模型负责理解语义、判断适用性、处理冲突、作取舍、组织叙事和评价内容是否讲清。
- 脚本负责文件导入、格式转换、枚举、路径解析、结构校验、确定性渲染、状态记录和可复现比较。
- 模型已选择的表头、图语法、引用位置等确定性结果，由脚本生成与检查；选择是否合适、内容是否正确仍由模型判断。
- 能确定计算不等于值得新增机制：先说明实际减少的重复劳动或失败、当前责任为何无法直接修正，以及将替换的旧实现。
- token、子串、字数、数量、相似度和字段存在性只表达它们真实测到的机械事实，不升级成语义结论。
- 语义审查由独立于作者上下文的 verifier 完成；脚本只验证审查对象、证据引用和结果结构真实存在。

### 4.3 不把提示词承诺当作执行保证

消费模型是非确定性模型，可能忽略、略写、误解、跳步或编造；维护者不能假设一条清楚的提示就会被 100% 执行，
也不能因此把语义判断全部改写成脚本规则。系统级高风险行为由以下控制层按实际风险组合保护：

| 层 | 责任 |
|---|---|
| 提示词 / 作者任务包 | 在行动前交付完整目标、输入、步骤、输出合同和失败处置 |
| 确定性脚本 | 冻结输入，控制步骤与状态，生成骨架，检查结构、引用、精确来源和证据完整性 |
| 独立 verifier | 判断遗漏、略写、矛盾、编造、表达质量与知识是否真正应用 |
| 隔离行为测试 | 验证未知消费模型、未知材料、时间成本和整套协作是否成立 |

作者提示与 checker 共享同一份事实、结构和状态真源，避免文字要求和执行条件分叉；语义指引保持人可读，
不为追求“同一合同生成一切”而把它强塞进机器 schema。单一控制层不能证明端到端 Agent 行为：提示词不保证执行，
脚本不证明语义，verifier 自述不代替身份与证据验真，已知 Case 通过不证明泛化。纯确定性子能力按其适用证据闭环，
不强制经过无关的 verifier 或真实行为测试。

确定性门在当前输入允许的范围内尽量一次报告完整问题，并同时列出因前置缺失而未执行的检查。作者机制以高质量完成主要内容为
首要目标，内容按适合当前任务的安全边界可靠落盘；verifier 是纠偏安全网，不代替作者补写主体。运行机制不写死生成或返修次数。
重复出现同类问题、错误不收敛或修订成本持续增长时，回到维护层检查任务包、输入规模、职责分配、verifier 定义或模型能力，
不让消费模型无界撞门禁。

区分已确认业务约束、工具协议和表达/组织建议。模板、编排与来源分配保存已有理解，不构成正文内容上限；允许消费模型补充有依据的关系、条件和合理分节。业务结论变化回相应真源，普通表达深化不增加审批或自证字段。

### 4.4 设计完成条件

一项机制只有同时满足以下条件才算设计闭合：

1. 消费模型的输入、动作、输出、下游消费者和失败路径明确；
2. 指令在对应动作之前送达，不依赖 checker 教学；
3. 脚本没有承担无法确定计算的语义判断；
4. 适用的提示词、脚本、verifier 和行为测试责任明确，消费模型的忽略、略写、编造与跳步都有发现者和恢复路径；
5. 验收能区分正确与错误结果，而不只是检查写了字；
6. 换一个未知业务域，机制仍成立且无需增加特例。

## 5. Extension 结构与不变量

### 5.1 两层与一座桥梁

- **机制层**：`doc/extensions` 中 `knowledge/` 以外的 skills、hooks、overlays、scripts、合同与入口。
  它基于 Framework 公共扩展点运行，对目标仓模块名、SDK、业务名、绝对路径和测试 Case 零强依赖。
- **知识层**：`knowledge/` 下的项目事实、规约和设计模式。本仓内容是可适配样板，目标仓使用前按真实事实核实和扩展。
- **Adaptation 桥梁**：按第3节所有权接入目标仓，知识内容仍由目标维护。它不形成第三套内容所有权。

### 5.2 单一真源

- 同一事实、状态、配置、编号含义、图片登记和决策只维护一个权威来源；其他视图由权威来源生成或解析。
- 随工程变化的约定放在数据合同或配置中；脚本消费数据，不把当前工程的值固化成正则和分支。
- 机制需要域、条目、模式、角色或模块集合时，从权威清单与正文派生；派生失败时明确报错。
- 业务名、契约名、ID 和编号只用于身份、引用和下游追踪，不充当内容语义。Story/Review 的完整性围绕已确认范围内的业务事实、
  关系、流程、异常、验收与决策，由独立语义审查判断。
- 契约修改与直接消费者在同一步同步；写入者、读取者和验证者对同一状态使用同一含义。
- 下游没有动作时给出明确的不适用及理由；缺席不代表不适用。

### 5.3 交付面通用性

- 提示给当前目标、输入、动作、完成条件和恢复方式，直接说明正确位置与做法；禁止性规则保留明确边界，其余用正向表达。
- 注释解释当前职责、理由与边界。维护历史、案例单号、测试业务名、模型名、suite、运行数字与轮次故事留在测试/演进域，不进入交付机制；不带数字的历史叙述同样处理。合法的产品版本/流程概念按语境区别。
- 示例使用与测试Case无关的中性题材，示例与适用条件分开。机制不能按某个案例的原句、表行数、图节点或金样章节增加命中/豁免。
- 过拟合自查覆盖新增、复用和移动的提示、注释、脚本、合同及实际生成内容；同时检查是否提前穷尽了合法业务、强迫固定表达、忽略未预列的关系。只搜专名零命中不算完成。
- 生成内容引用当前需求中的业务名和数字是正常输入；核其来源，不为通过扫描删除业务事实。扫描入口与命中处置见 `TEST.md §7.2–7.3`。

## 6. Knowledge 的内容与消费

### 6.1 知识内容的边界

| 类型 | 回答 | 内容要求 |
|---|---|---|
| 项目事实 | 目标仓有什么、在哪里、通常怎样使用 | 真实路径、类名、API、封装形态和工程惯例；不写阶段路由与维护规则 |
| 规约 | 什么条件下必须做或禁止做什么 | 一条一个可独立判断的要求，写清命中条件、边界与例外；实现专名引用项目事实 |
| 设计模式 | 什么情形适用、由哪些角色协作、怎样验证 | 适用与不适用条件、角色、骨架和验证清单；目标仓是否采用由具体需求决定 |

同一知识只在一个面登记，引用指向真实存在的权威内容。知识正文不给维护者讲如何维护 knowledge，也不写消费阶段坐标。
机制只维护消费时机和产物出口，不复制知识条目、域清单或模式角色。

### 6.2 知识链

Knowledge 能力的验收对象是：

```text
看到 → 理解 → 应用 → 传递
```

- **看到**：当前阶段需要的知识类型和已激活内容实际进入正确执行体的输入；具体条目是否适用于当前需求，由对应阶段读取后判断，
  不要求机制在语义判断前自动过滤。
- **理解**：执行体结合当前需求判断适用、不适用或冲突，不回显知识名称冒充判断。
- **应用**：适用知识改变本阶段的具体产物、设计或契约实体，有可指认的业务落点。
- **传递**：下游读取上游已经形成的知识决策与义务，提供落实证据或明确不适用，不重新猜测原始知识。

三类知识使用不同职责链：

- **项目事实**从 Spec 起作为目标仓事实使用；发现错误回 Knowledge 真源修正，不进入选型。
- **规约**由 Spec 判断是否命中并形成当前需求约束，Plan 决定设计落点和验证方式，不能无理由取消命中项。
- **设计模式**由 Spec 提出候选与适用理由，Plan 选择、拒绝或调整并冻结。

“理解”是从消费模型的判断、产物变化和独立审查中取得的可观察证据，不声称脚本能够直接证明模型内部状态。
知识的适用性与落实决定在受其影响的设计之前形成；排在设计之后的知识总结不构成设计输入。
manifest 是知识激活清单的唯一来源。新增、删除或修改知识时，通用机制无需增加域名、编号、文件名或特例即可完成整条知识链。
Demo 仓维护者保证样板结构有效、类型边界正确并能演示和测试完整知识链，不把 Knowledge 优化改造成自动同步 Demo 业务代码的系统。
CLI 或其它验证一旦发现样板内容、边界或消费结果有真实问题，须按 Knowledge、Extension、Framework 或测试的实际所有权及时修复并
增加回归，不能以“只是 Demo”为由长期挂账。真实目标仓负责把三类知识修正和扩展为自身事实。

## 7. 维护方法

### 7.1 从行为和根因开始

1. 按 `TEST.md §8.1` 还原实际工具入参、返回与读取范围、操作和产物变化。区分“可以生成”“实际送达”“执行了动作”“结果正确”；内部理解没有证据时标未知。
2. 区分产物、行为、指令、Framework、Knowledge与测试观测的问题，定位最早拥有错误职责或错误输入的位置。
3. 同类问题反复出现、优化A损害B、返修或上下文成本持续上涨时，先审视整条流程：思考单位是否合理、输入与派生输出是否混用、哪项判断被多次重做、验证是否只追格式。
4. 比较“修正原职责”和“替换流程/职责”的必要性与代价，不默认保留现有主干，也不自动推倒重写。确需重写遵循用户级确认约定；整体审视本身不是新的审批关卡。

### 7.2 整体修改一项职责

- 一个完整需求或问题可以按风险拆成多个批次和步骤。单步允许交付安全、可验证且有明确后继的中间态；迁移桥须写清所有者、用途、
  删除步骤和退出条件，同一正式入口同时只启用一套职责。
- 整个需求完成时只保留一套现行路径，并删除被替代的指令、状态、门禁、兼容分支、迁移桥和零消费者导出。
- 降级行为必须可观察并有明确适用条件；正常路径不依赖静默降级。
- 没有明确退出步骤的临时路径不得跨轮次沉积；已登记迁移桥按计划退出，不能转成长期兼容层。
- 新增通用框架、状态机、解析器、生成器或评测设施前，证明它是当前目标不可缺少的最小能力，并取得用户确认。

方案给出逐职责的保留/替换/删除清单：点到旧函数、提示或消费者，写清新落点与退出时点；没有旧职责可替换的新增，说明真实缺口。先推演正常路径、相关异常与恢复，再估新增/退出量，不先提高预算容纳未论证的机制。

### 7.3 分步实施与独立审查

- 维护设计者把改动拆成职责闭合的步骤，每步冻结目标、事实、允许范围、保护区、实现要求和验收方法；步骤里写明本步对需求预算的预计增减，
  供维护实施者自检与评审对照，不作为按步骤拦截的门（预算规则见 §7.5）。
- 维护实施者在独立会话中一次只实施当前步骤，记录实际 diff、输入生产者、处理位置、消费者、失败路径和离线结果，
  只能声明“已实施，等待评审”。
- 维护设计者从实际文件重新还原行为；维护实施者自述、字段出现和测试全绿都不能替代审查。
- 当前步骤通过后才能进入下一步。后续发现前序问题时重新打开原步骤，不在当前步骤顺手打补丁。

接受的评审意见须同步当前方案、直接消费者与验收：方案与验收由维护设计者改，直接消费者由维护实施者按方案改；拒绝的给出事实依据。不能只另写一份反馈让维护实施者拼历史。当前实施入口与状态保持一致，历史版本有明确退场标识。生成命令用实际支持的shell执行，验证既覆盖正常路径，也覆盖“已写入后后继失败”等责任边界；不以出现函数名或单例绿代替行为。

### 7.4 分层证据

- 结构证据证明文件、合同、引用、状态和确定性脚本正确。
- 独立语义审查提供任务定义、内容和职责的判断依据；对象绑定、报告结构合格和实际语义结论分别核对，报告PASS不代替对真实缺陷的复核。
- 隔离 CLI 证明消费模型在真实上下文中的行为；它按 `TEST.md` 只在用户启动的里程碑运行，**跑的是正常需求**，结果由用户按评分协议判。
  构造缺陷稿、删事实、造反例只用于确定性脚本的自检与事后诊断，不用来证明模型的判断力——模型的判断力从真实产物上被人找到的问题它报没报来看。
- Extension 测试及行为评价遵循 `TEST.md`；证据须绑定实际宿主、模型与运行配置，不能外推到未验证环境。
- 文档中的“已实施”、原生 gate、离线全绿和一次已知 Case 成功，均不单独构成行为完成。

### 7.5 维护预算与分级复核

本节是Story Extension维护项目的规约，约束方案制定、实现与评审；不作为demo应用仓的全局预算要求。**预算的目的是发现实现走偏、补丁叠加、被替代旧机制未退出、废弃内容残留及其对正常功能的干扰，不是限制功能的正向实现。** 不得删减正常功能、必要测试或说明来凑预算，也不得只改预算把问题变绿。维护侧预算不作为被维护系统中业务执行体的任务要求。

**同一准则在实际动作前送达，不依赖会话开头读过一次**：

| 触点 | 必须带到当前工作中的内容 |
|---|---|
| 制定/修改方案 | 说明本次能力目标、新旧职责替换、退出范围与预算依据；方案质量也要接受复核，不能把预算差异一概归咎实现者 |
| 启动实施/交接新会话 | 当前任务引用本节，并给本包新承担者、被替换旧内容及保留能力；不只下发一个行数上限 |
| 预算报告/超限提示 | 同时给实际差额、所需复核动作与本节入口，明确先查实现/方案，不以裁剪功能或抬数字作为默认修法 |
| 评审/收口 | 核实际diff与消费者：同功能/同语义是否有更简单完整实现、旧内容是否真退、是否造成正常功能干扰；不凭自评、字段存在或预算绿下结论 |

上述要求写入现有方案、交接和评审，不另建运行期“已读/已自查”台账；短提醒可以在动作处重复，阈值和判定原则只在本节维护。预算以内也要检查走偏与残留，超预算也不自动判实现错误。

**制定方案时**，方案制定者同时登记：计量范围与单位、现有基线、本次新/替换实现的预计新增量、旧机制退出清单及预计删除量、实施峰值与完成总量。新增须说明承担什么职责，删除须说明由谁接替；移动、格式变化和重复记账不能算净减。按完整需求管理，阶段分项用于定位，不能通过拆步骤重置预算。

**分级比例** `R = 本次累计实际新增实现量 / 初始批准的新增实现预算`。各指标按同口径分别计算，不将代码行、字符和耗时直接相加；方案指定主要判定指标。这里的新增包括替换旧实现所写的新实现，不是Git新增行的机械合计。旧机制删除量另核，不能用净增量或整个历史仓库规模作分母。纯删除或预算为零时不算百分比；出现未预算的新实现先由reviewer核必要性、确定正预算与适用起点，不由维护实施者自行补数。

| 比例 | 必须采取的动作 | 推进条件 |
|---|---|---|
| R≤100% | 按方案实现并正常评审 | 未超预算不免除功能、质量与退场检查 |
| 100%＜R≤125% | 维护实施者自查重复实现、未退旧机制、范围扩大和方案漏算，记录差额与原因 | 可继续，不逐行停等 |
| 125%＜R≤150% | 自查后交方案制定者或其指定reviewer确认；同时审实现与方案是否错误、遗漏、不清楚或存在更简单完整替代 | reviewer具名确认后继续，不要求人工确认 |
| R＞150% | reviewer整体反思实现与方案，形成具体、可审阅的保留/替换/预算调整建议 | 与人工确认后继续，reviewer不能代替这一级确认 |

超过阈值需确认时，仍允许收敛性修正、删除、必要验证和准备评审材料；未确认前不得继续扩大未获确认的实现、宣告完成或进入下一实施包。确认记录写入该需求既有方案/评审/预算记录，注明范围、额度、理由与确认角色；不另造业务运行期自证台账。已有确认覆盖的范围与额度不重复询问，超出确认范围再升级。

初始预算与累计变化保留；reviewer调整当前执行额度不消除相对初始预算的比例，不能连续小幅改签规避150%人工确认。真实需求范围发生变化时按既有需求确认流程更新基线，并保留前后关系。

完成时同时核功能质量、实际新增、旧机制退出与最终总量。预算以内但旧实现未退出，同样不能完成；超预算但实现必要合理，可按上述角色权限调整，不强迫删功能。

**机械检查的职责**：按预算数据计算比例、报告对应动作，并在交回/阶段推进处检查所需确认是否具备；拦的是未经确认的推进，不应禁止修正与测试。它不替reviewer判断实现合理性，也不证明模型绝不继续写文件。子域复用同一规则，只维护自己的计量口径与脚本接线，不再自定另一套阈值。

**接线边界**：本节确立规约，不代表现有检查器已实现分级。旧检查器的硬超限结果不能成为裁剪功能的理由，应交reviewer按本节处理；机械分级改造需单独验证。已在执行的需求不回退重启、不重置既有额度，也不把历史总量冒充新增预算；由reviewer在下一次预算复核时补齐新增/退出账和适用起点。

**本项目计量与现有接线**：`regression/mechanism-budget.yaml`及`test_mechanism_budget.py`仍维护Extension分类总量、峰值与完成目标，代码行不含注释/空行，完整字符另报。它们尚未接入本节新增实现预算的分级，不能用现有总量比例代替新比例。旧硬失败保留实测交reviewer处理，不改测试绕过，不为换绿删能力。

语义代理不得替模型判断、所有改动须满足有效需求与过拟合边界，继续按§4.2、§5.3及对应检查执行；这些质量要求不能通过增加预算豁免。

## 8. 完成前自检

- 本轮目标与保护项都已检查：改进项是否变好，原有关键能力是否保持，是否通过删事实、改范围或降低要求取得通过。
- 保留/替换/删除清单与实际调用一致，所有接受的评审意见已进入当前方案、直接消费者和验收；入口及状态可供其它维护会话直接接续。
- 原始输入、业务结论、编排建议、工具协议的职责清楚；来源映射或模板没有成为正文上限，必要的确定性工作没有反交给模型。
- 第5.3节过拟合自查与相关验证已完成，命中有语境判断；改动涉及Knowledge时，看到、理解、应用、传递均有消费者和证据。
- 结构通过、语义审查、真实行为与用户验收分别如实记录，未验证的场景/配置不宣称已覆盖；证据入口与判读遵循 `TEST.md`。
- 规模与运行成本按第7.5节核过，净增与净减均可解释；历史指标不冒充当前测量，代码行合规不冒充整体简洁。
- 只运行本次授权和必要的验证，保留测试隔离与Framework边界；测试方法、并行与慢用例纪律以 `TEST.md §7` 为准。
