# Story Extension 维护契约

> 约束 Story Extension 的维护，写给维护者，不进入消费模型上下文。角色定义、方法和交付要求按用户级 AGENTS；
> 本文只写本项目特有的对象、事实、约束和入口。

## 0. 入口

- 维护 Extension 先完整阅读本文件。维护任务以用户本次给定的目标、需求、计划和状态为输入，在 `test/story/spec/`、`test/story/design/`
  中按该任务查找已有材料；无法确定对应任务时补齐歧义，不默认进入某个日期或最新轮次。`doc/features/*` 是历史产物，不是需求真源。
- 运行、修改或评价测试：按 [TEST.md](TEST.md) 任务索引完整读取对应分支，真实 CLI 启动前读完其运行协议；命令、状态、证据与评分
  只在那里维护。
- 追溯历史：[EVOLUTION.md](EVOLUTION.md) 只提供演进证据，不是当前实现依据。历史记录中的“执行者”按语境指维护实施者或消费模型，
  不追溯改名。
- 维护范围只覆盖 interactive 运行模式。framework 具备 headless/goal 能力，Extension 不为它们增加兼容、状态或测试，
  也不把未覆盖写成已支持；用户明确提出时另立需求和验收。

## 1. 本项目的角色职责

| 角色 | 本项目负责 |
|---|---|
| 维护设计者 | 定位 Extension 的行为问题与最早失效点；为 Framework 协作、Extension 机制、knowledge、adaptation 和测试能力制定方案与验收标准；审查实现和真实执行证据 |
| 维护实施者 | 实现或修正上述对象；交付给消费模型的内容满足 writing-for-agents：要求在使用前送达、任务边界清楚、完成条件可检查；运行方案确定的验证并提交证据 |

- “维护者”是前两者的合称。维护者直接检查被维护对象（Framework、Extension 生命周期能力、Skill、Hook、Knowledge、Adaptation、Harness、
  Verifier 和测试）的源码、配置、测试和产物，不调用被维护系统的流程来设计或证明它自身正确。§5 的方案制定者与 reviewer 指维护设计者。
- 维护实施者在独立会话中一次只实施当前步骤，记录实际 diff、输入生产者、处理位置、消费者、失败路径和离线结果，只能声明“已实施，
  等待评审”；生成命令用实际支持的 shell 执行。维护设计者从实际文件重新还原行为；接受的评审意见同步到方案、直接消费者与验收，
  拒绝的给出事实依据。
- 实跑中宿主由本次任务指定的维护角色担任，代理需求方的边界见 TEST §0.2。
- 消费模型是用 Framework + Extension 在目标工程开发真实需求的模型，包括外网隔离 Case 的被测模型和内网仓的使用模型。它只依赖需求材料、
  目标仓事实与 Framework/Extension 上下文；交付内容不引导它读 `test/story/`、历史方案、失败用例或 checker 源码。它读 checker 只是
  调查信号（TEST §8 第 3 项）；为定位明确的工具或脚本内部错误可以读实现，但不能据此改业务产物迎合隐藏判据，问题回维护层处理。
  verifier 是产品内部的独立审查能力，按使用流程工作。

## 2. 产品定位与所有权

Framework + Extension 是指导模型完成需求开发的 AI Agent 系统，不是代码产品；提示词、知识、脚本、门禁、状态文件和报告只是载体，
评价对象是消费模型在未知需求上的行为：

```text
输入事实 → 按时送达 → 正确理解 → 做出决策 → 产生产物 → 传给下游 → 失败恢复 → 留下证据
```

代码通过、字段出现、门禁全绿或报告写了结论，只证明载体的局部性质；消费模型在不接触维护材料的情况下以合理成本得到符合目标的结果，
才是能力成立。局部确定性 helper 只需证明它实际承担的输入、输出、失败语义和消费者；组合成用户可见行为时，再沿行为链验收。

| 部分 | 负责 | 不负责 |
|---|---|---|
| Framework | 通用阶段、上下文装配、工具、宿主能力、verifier 调度、阶段闭环与公共扩展点 | 实例业务知识、Story 专属产物语义 |
| Extension 机制层 | 需求流程、作者任务、阶段扩展、知识路由、产物合同和确定性辅助能力 | 目标仓专名、测试答案、Framework 通用能力的影子实现 |
| Knowledge | 项目事实、规约和设计模式；内容由目标仓维护 | 阶段调度、消费方落点坐标、测试与维护历史 |
| Adaptation | 脚本按目录所有权安装/升级机制与入口，不读写知识；首装由模型写部件定位知识，其余知识由模型按方法页从目标仓自己的代码与需求出发写 | 替目标仓改知识，灌入或对照 Demo 知识，按业务改写通用机制 |
| 测试域 | 隔离输入、调度、观测、证据留存、离线回归与真实行为评价 | 替消费模型完成任务、把用例答案注入交付物 |

问题修在最早拥有该职责的位置；缺 Framework 能力时提出或补齐，不在 Extension 内复制旁路框架。

本仓特殊事实：

- `framework/` 是 AgentMaison 3.0.0 的 vendored 副本（`framework/RELEASE-MANIFEST.json`）。正式交付落在上游，经 framework-init UPDATE
  进入消费仓；本仓副本只在用户明确授权的单步验证中临时修改，交付时保留上游基线、可复现补丁和临时放行的失效条件。
- 本仓对 framework 仅有两处差异：`framework/agents/opencode/adapter.yaml` 的 `verifier_subagent` 登记与
  `framework/agents/opencode/templates/agents/verifier.md` 子代理模板（物化为 `.opencode/agent/verifier.md`），不含逻辑改动，不交上游。
  `framework.config.json` 的 `integrity.drift_allowlist` 在 3.0.0 已退役、读取即忽略；保留靠 UPDATE 时对这两处 `init.task_decision`
  选「保留」。它们不随 story-adaptation 进目标仓；进目标仓的 `.opencode` 内容只有 manifest `provides.bridges`
  登记的跳板。
- `.opencode/` 同时是本仓 story 分支的 CLI 测试装置：外网实跑用 opencode，内网用 codex。

## 3. 不变量

回归台账（`regression/failure-modes.yaml` 的 clause）与评审按下列名字引用。

### 3.1 Agent-first

- **信息先于决策**：消费模型做决定之前，目标、事实、约束、可用能力和完成条件已进入它的实际上下文；文件在磁盘、manifest 有登记、
  hook 返回了文本都不等于送达。报错只指出未满足的条件和回到正确路径的方法，不是首次交付规则的渠道。
- **模型与脚本按能力分工**：模型负责理解语义、判断适用性、处理冲突、取舍、组织叙事和评价内容是否讲清；脚本负责导入、转换、枚举、
  路径解析、结构校验、确定性渲染、状态记录和可复现比较；模型已选的表头、图语法、引用位置由脚本生成与检查。token、子串、字数、
  相似度和字段存在性只表达机械事实，不升级为语义结论；语义审查由独立于作者上下文的 verifier 完成。新增确定性机制前说明减少的重复
  劳动或失败、当前责任为何不能直接修正、将替换的旧实现。
- **提示词不是执行保证**：消费模型可能忽略、略写、误解、跳步或编造。系统级高风险行为由以下控制层按实际风险组合保护：

  | 层 | 责任 |
  |---|---|
  | 提示词 / 作者任务包 | 在行动前交付完整目标、输入、步骤、输出合同和失败处置 |
  | 确定性脚本 | 冻结输入，控制步骤与状态，生成骨架，检查结构、引用、精确来源和证据完整性 |
  | 独立 verifier | 判断遗漏、略写、矛盾、编造、表达质量与知识是否真正应用 |
  | 隔离行为测试 | 验证未知消费模型、未知材料、时间成本和整套协作是否成立 |

  单层不证明端到端：提示词不保证执行，脚本不证明语义，verifier 自述不代替验真，已知 Case 通过不证明
  泛化。纯确定性子能力按其证据闭环，不强制过 verifier 或真实 CLI。作者提示与 checker 共享同一事实、结构和状态真源，语义指引保持人可读。
  确定性门一次报告完整问题并列出因前置缺失未执行的检查。作者机制以高质量完成主体为首要目标，内容按适合当前任务的安全边界可靠落盘；
  verifier 是纠偏安全网，不代替补写；运行机制不写死生成或返修次数。同类问题反复、优化 A 损害 B、错误不收敛或修订成本上涨时回维护层：先审视整条流程
  （思考单位是否合理、输入与派生输出是否混用、哪项判断被多次重做、验证是否只追格式），再检查任务包、输入规模、职责分配、
  verifier 定义或模型能力；比较修正原职责与替换流程的代价，不默认保留现有主干，也不自动推倒重写。
- **区分约束层级**：已确认业务约束、工具协议与表达/组织建议分开。模板、编排与来源分配保存已有理解，不构成正文上限，允许消费模型补充
  有依据的关系、条件和合理分节；业务结论变化回相应真源，表达深化不增加审批或自证字段。

### 3.2 Extension 结构

- **两层一桥**：机制层是 `doc/extensions` 中 `knowledge/` 以外的 `skills/`、`hooks/`、`rules/*.overlay.yaml`、合同、`manifest.yaml`
  与宿主跳板，基于 Framework 公共扩展点运行，对目标仓模块名、SDK、业务名、绝对路径和测试 Case 零强依赖；知识层是 `knowledge/` 的
  项目事实、规约和设计模式，本仓内容是可适配样板；Adaptation 按所有权接入目标仓，知识仍由目标维护，不形成第三套所有权。
- **机制层零测试特征**：机制层与注入件不含测试 Case 的单号、业务名或需求特征，判据是换一个业务域这段文字是否仍成立；示例用与
  Case 无关的中性题材，示例与适用条件分开；不按某个案例的原句、表行数、图节点或金样章节增加命中/豁免。过拟合自查覆盖新增、复用和
  移动的提示、注释、脚本、合同及实际生成内容，同时检查是否提前穷尽了合法业务、强迫固定表达、忽略未预列的关系；只搜专名零命中
  不算完成；生成内容引用当前需求的业务名和数字是正常输入，核来源，不为通过扫描删业务事实。扫描入口见 TEST §7.2–7.3。
- **单一真源**：同一事实、状态、配置、编号含义、图片登记和决策只有一个权威来源，其他视图由它生成或解析；随工程变化的约定放数据合同
  或配置，脚本消费数据，不固化正则与分支；域、条目、模式、角色集合从权威清单与正文派生，派生失败明确报错；业务名、契约名、ID 和编号
  只用于身份与追踪，不充当内容语义；Story/Review 的完整性围绕已确认范围内的业务事实、关系、流程、异常、验收与决策，由独立语义
  审查判断。
- **引用必须真实存在**：跨文件引用的条目、章号、钩子名和字段先确认在目标里存在；改契约文本时同步它的消费方。
- **显式不适用优于静默跳过**：下游无动作时给出不适用及理由，缺席不代表不适用；降级必须可观察并有明确适用条件，正常路径不依赖静默降级。
- **交付面正向表达**：提示给目标、输入、动作、完成条件和恢复方式，直接说明正确做法；禁止性规则保留明确边界，其余正向表达。
  注释解释当前职责、理由与边界。维护历史、案例单号、测试业务名、模型名、suite、运行数字与轮次故事（含不带数字的历史叙述）留在
  测试/演进域，不进交付机制；合法的产品版本/流程概念按语境区别。
- **正向实现，不打补丁**：同一职责不新旧两套并存；导出即须有消费者；`暂时/临时/待迁移/TODO` 不跨轮次留存；迁移桥写清所有者、
  用途、删除步骤和退出条件，整个需求完成时只保留一套现行路径。

### 3.3 Knowledge

- **知识三类与边界**：

  | 类型 | 回答 | 内容要求 |
  |---|---|---|
  | 项目事实 | 目标仓有什么、在哪里、通常怎样使用 | 真实路径、类名、API、封装形态和工程惯例；不写阶段路由与维护规则 |
  | 规约 | 什么条件下必须做或禁止做什么 | 一条一个可独立判断的要求，写清命中条件、边界与例外；实现专名引用项目事实 |
  | 设计模式 | 什么情形适用、由哪些角色协作、怎样验证 | 适用与不适用条件、角色、骨架和验证清单；目标仓是否采用由具体需求决定 |

  同一知识只在一个面登记，引用指向真实存在的权威内容。`manifest.yaml > provides.knowledge` 是知识激活清单的唯一来源，只登记路径；
  每份知识用 frontmatter 的 `kind` 与 `applies_when`（何时读、回答什么）描述自己，机制按它把知识交给当前阶段。框架只读清单
  列出的文件，派生为空即报错。机制只维护消费时机和产物出口，不复制知识条目、域清单、模式角色或知识清单。
- **知识不含维护信息，定位只写一处**：知识正文只写给消费模型，可以讲项目概念、事实、已定规范、项目方法的应用步骤、
  选择依据、参考例子与完成判断；阶段目标、何时读、结果写进哪份产物（章节号、契约字段路径、表名）与命令归机制（作者页、
  模板、任务包）。归属按「什么变了它才变」判，读写规则在机制侧 `skills/story/reference/knowledge/protocol.md`，
  适配方法在 `skills/story-adaptation/reference/knowledge-adaptation.md`，都不进条目正文。
- **知识链**：验收对象是「看到 → 理解 → 应用 → 传递」。看到：当前阶段需要的知识类型和已激活内容实际进入正确执行体的输入，条目
  是否适用由该阶段读取后判断，不要求机制预过滤；理解：执行体结合当前需求判断适用、不适用或冲突，以判断、产物变化和独立审查为
  可观察证据，不回显知识名称冒充判断，不声称脚本能证明模型内部状态；应用：适用知识改变本阶段的具体产物、设计或契约实体，有可指认
  的业务落点；传递：下游读取上游已形成的知识决策与义务，提供落实证据或明确不适用，不重新猜测。三类职责链：项目事实从 Spec 起作为
  目标仓事实使用，发现错误回 Knowledge 真源，不进入选型；规约由 Spec 判断命中并形成当前需求约束，Plan 决定落点与验证方式，不能
  无理由取消命中项；设计模式由 Spec 提出候选与理由，Plan 选择、拒绝或调整并冻结。知识决策在受其影响的设计之前形成，排在设计之后
  的总结不构成设计输入。新增、删除或修改知识时，通用机制无需增加域名、编号、文件名或特例。
- **声明不是应用**：知识冻结须投影为契约实体并有可指认落点，回显名称、anchor 指回声明表自己都不算；只校验「写了字」的门禁测出的
  是拼写，不是知识生效。
- **Demo 样板义务**：本仓维护者保证样板结构有效、类型边界正确并能演示和测试完整知识链，不把 Knowledge 优化改造成自动同步 Demo
  业务代码的系统；验证发现样板内容、边界或消费结果有真实问题时按实际所有权修复并加回归，不以「只是 Demo」挂账；真实目标仓负责把
  三类知识修正和扩展为自身事实。

## 4. 验收

- **设计闭合**：脚本没有承担无法确定计算的语义判断；提示词、脚本、verifier 和行为测试的责任明确，消费模型的忽略、略写、编造与跳步
  都有发现者和恢复路径；验收能区分正确与错误结果，不只检查写了字；换一个未知业务域机制仍成立且无需特例。
- **分层证据**：结构证据证明文件、合同、引用、状态和确定性脚本正确；独立语义审查分别核对对象绑定、报告结构和实际语义结论，报告 PASS
  不代替对真实缺陷的复核；隔离 CLI 只在用户启动的里程碑按 TEST 运行，跑正常需求，结果由用户按评分协议判；构造缺陷稿、删事实、造反例
  只用于确定性脚本自检与事后诊断，不用来证明模型判断力；证据绑定实际宿主、模型与运行配置，不外推到未验证环境。文档中的「已实施」、
  原生 gate、离线全绿和一次已知 Case 成功均不单独构成行为完成。
- 评价范围来自本轮已确认目标及需要保持的原有能力：改进项是否变好、原有关键能力是否保持、是否通过删事实、改范围或降低要求取得
  通过，按 TEST §10 评价。行为还原按 TEST §8.1；只运行本次授权和必要的验证，保留测试隔离与 Framework 边界，测试方法、并行与
  慢用例纪律按 TEST §7。

## 5. 维护预算与分级复核

约束本项目的方案制定、实现与评审，不是 demo 应用仓的全局预算，也不作为被维护系统中业务执行体的任务要求。**预算用于发现实现走偏、
补丁叠加、被替代旧机制未退出、废弃内容残留及其对正常功能的干扰，不限制功能的正向实现。** 不得删减正常功能、必要测试或说明来凑预算，
也不得只改预算把问题变绿。阈值和判定原则只在本节维护，短提醒可在动作处重复，不另建运行期「已读/已自查」台账。

| 触点 | 必须带到当前工作中的内容 |
|---|---|
| 制定/修改方案 | 本次能力目标、新旧职责替换、退出范围与预算依据；登记计量范围与单位、现有基线、预计新增量、旧机制退出清单及预计删除量、实施峰值与完成总量；先推演正常路径、相关异常与恢复，再估新增/退出量，不先提高预算容纳未论证的机制；方案质量同样接受复核，预算差异不能一概归咎实现者 |
| 拆步实施/交接新会话 | 引用本节；给本包新承担者、被替换旧内容及保留能力，不只下发一个行数上限；每步写明对需求预算的预计增减，供自检与评审对照，不作为按步骤拦截的门 |
| 预算报告/超限提示 | 实际差额、所需复核动作与本节入口；先查实现/方案，不以裁剪功能或抬数字作为默认修法 |
| 评审/收口 | 核实际 diff 与消费者：同功能是否有更简单完整实现、旧内容是否真退、是否干扰正常功能；不凭自评、字段存在或预算绿下结论 |

新增须说明承担什么职责，删除须说明由谁接替；移动、格式变化和重复记账不算净减。按完整需求管理，阶段分项只用于定位，不能通过拆步骤
重置预算。

**分级比例** `R = 本次累计实际新增实现量 / 初始批准的新增实现预算`。各指标按同口径分别计算，不将代码行、字符和耗时直接相加，方案指定
主要判定指标。新增包括替换旧实现所写的新实现，不是 Git 新增行的机械合计；旧机制删除量另核，不用净增量或整个历史仓库规模作分母。
纯删除或预算为零时不算百分比；未预算的新实现先由 reviewer 核必要性、确定正预算与适用起点，不由维护实施者自行补数。

| 比例 | 必须采取的动作 | 推进条件 |
|---|---|---|
| R≤100% | 按方案实现并正常评审 | 未超预算不免除功能、质量与退场检查 |
| 100%＜R≤125% | 维护实施者自查重复实现、未退旧机制、范围扩大和方案漏算，记录差额与原因 | 可继续，不逐行停等 |
| 125%＜R≤150% | 自查后交方案制定者或其指定 reviewer 确认；同时审实现与方案是否错误、遗漏、不清楚或有更简单完整替代 | reviewer 具名确认后继续，不要求人工确认 |
| R＞150% | reviewer 整体反思实现与方案，形成具体、可审阅的保留/替换/预算调整建议 | 与人工确认后继续，reviewer 不能代替这一级确认 |

需确认时仍允许收敛性修正、删除、必要验证和准备评审材料；未确认前不得扩大未获确认的实现、宣告完成或进入下一实施包。确认记录写入
该需求既有方案/评审/预算记录，注明范围、额度、理由与确认角色；已有确认覆盖的范围与额度不重复询问，超出再升级。初始预算与累计变化
保留；reviewer 调整当前执行额度不消除相对初始预算的比例，不能连续小幅改签规避 150% 人工确认；需求范围变化时按既有确认流程更新基线
并保留前后关系。

完成时同时核功能质量、实际新增、旧机制退出与最终总量：预算以内但旧实现未退出不能完成；超预算但实现必要合理，按上述角色权限调整，
不强迫删功能。预算以内也查走偏与残留，超预算也不自动判实现错误。§3 的质量要求不能通过增加预算豁免。

机械检查只按预算数据计算比例、报告对应动作，并在交回/阶段推进处检查所需确认是否具备；拦未经确认的推进，不禁止修正与测试；不替
reviewer 判断实现合理性，也不证明模型绝不继续写文件。子域复用同一规则，只维护自己的计量口径与脚本接线，不另定阈值。
