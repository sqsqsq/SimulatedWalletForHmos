# Story 测试域维护规则（维护契约）

> 本文件是维护 Story / Story Extension / 其测试能力时的**跨会话契约**，回答维护者三个问题：
> ①我维护的系统长什么样（§0–§1）②我必须守住什么（§2、§4）③遇到问题去哪定位（§0、§2 末）。
> 被测模型不得读取、注入或转述本文件。

## 0. 角色与文档关系

- 当前执行者是**外层优化者**，Story / Spec / Extension 及其测试能力是被修改对象。
- 不调用 Story、Spec、Framework 的 Skill、阶段流程、Hook、Harness、Verifier 或 Goal 来优化它们自身；可
  直接读取、修改和检查相关源码、配置、测试与产物。
- 真实行为验证只按 [TEST.md](TEST.md) 将能力作为被测对象运行；被测流程自身结果不能代替维护验证。
- 演进背景见 [EVOLUTION.md](EVOLUTION.md)。**TEST.md 是测试执行协议的唯一权威**；AGENTS.md 不复述执行细节。

## 1. 领域心智模型

**定位**：本工程是外网训练 demo 仓，内网才有真实业务代码仓与真实 SDK。demo 验证**机制**，不冒充真实仓内容验证。
本仓 `doc/features/*` 是历史产物，不是需求事实源；真实需求基线以 `test/story/spec/` 冻结澄清为准。

**Extension 两层 + 一座桥梁**（相对通用、又能快速应用到真实仓的组织方式）：

| 结构 | 组成 | 与目标仓的关系 |
|---|---|---|
| **通用机制层**（`knowledge/` 以外全部） | skills、hooks、phase_rules_overlays、scripts、章节合同、releases 清单结构 | 基于 Framework 既有扩展点；**零强依赖**：不引用任何仓模块名 / SDK API / 业务名 / 绝对路径，运行期标识从配置派生 |
| **知识层**（`knowledge/`） | 工程画像、规约、设计模式 | 本仓当作真实仓可核实的事实，但**核心身份是模板**——对另一仓是"该长什么样"的样板 |
| **ADAPTATION 桥梁**（两层主体的唯一接口，非第三层） | `/story adapt` + 插槽 + releases + verify | 把知识层从模板**逐槽替换为目标仓已核实事实**，机制层一字不动；适配即替换，不是重写 |

**测试域**：以隔离 Case + 多 Case 并行 CLI 把上述能力当被测对象验证真实行为。

## 2. 维护不变量（必须成立，跨轮次）

- **机制层零强依赖**：`doc/extensions` 非 `knowledge/` 部分不得出现仓模块名 / SDK API / 业务名 / 绝对路径 /
  架构层名字面（层清单从架构 DSL 派生）。
- **机制层零测试特征（反过拟合）**：机制层与注入件不得出现测试 Case 的单号、业务名或其需求特征——
  **示例一律用与被测 Case 无关的中性题材**。判据很简单：换一个业务域，这段文字还成立吗。
- **约定形态是数据不是代码**：编号形态（场景/功能/异常/验收/非功能编号长什么样）、单号前缀这类
  **随工程而变的约定**，声明在章节合同等数据文件里，不固化进脚本正则；扫描 0 命中时告警
  「形态可能不匹配本工程」，**不得静默通过**——静默失效比报错危险得多。
- **知识只经 manifest 激活清单送达**：框架从不注入知识正文；阶段不扫描目录、不读未启用文件。
- **章节合同安全回退**：词根未命中 → 读整篇；禁止精确标题选择器、primary/supporting、标题匹配门禁。
- **扩展语义判据必须被执行且被证明执行**：`pre_verifier` 注入必答清单，**测试域的回归脚本机械校验
  verifier 报告逐条含全部扩展判据的裁决**——注入 ≠ 执行，只注入不校验实测会漏（曾出现整份清单
  一条没裁而 harness 照收 PASS）。
  收口**不能**放在框架的 `post_verifier` 钩子里：它与 `pre_verifier` 在同一处相邻触发，
  跑在 verifier **之前**，读不到那份还不存在的报告。
- **声明不是应用**：知识冻结必须投影为**契约实体**（模式的每个角色 → 类/模型/文件；规约义务 →
  落点字段/方法/键），并由机械门禁校验实体真实存在；anchor 指回声明表自己不算落点。
  只校验「写了字」的门禁，测出来的是拼写正确，不是知识生效。
- **知识决策先于设计**：阶段附加的知识决策章必须排在它影响的设计章之前。位置即语义——
  排在设计之后只能是事后总结。
- **同一事实一处登记**：正文、附录、评审件、图片、编号含义各只有一个真源。
  附录只有一张条目级表；编号含义从规格件与规约条目表派生，不设手工登记表；同一张图全篇只引一次。
- **出口不枚举域**：规约判定产生的代码要求，落点按**命中条目**派生（spec 的「规约约束要求」章），
  不为任何域预留固定小节——预留小节就是把域清单硬编码换了个地方继续存在。
- **守恒按名不按号**：内容守恒守跨部件契约名（接口/存储键/配置项/事件名/错误码），不守编号。
  代理判据一旦成为门禁，最省力的满足方式就是造一段「场景索引：S1、S2、S3」。
- **显式不适用优于静默跳过**：下游对某条冻结义务无事可做时必须写明理由；
  缺席与「做过但没写」事后完全同形，而只有前者是缺陷。
- **测试判据不绑单一文件名**：闭环凭证认一组命名；阶段预算要落到中止条件上，
  否则「卡住」只能耗到全程预算用尽。
- **原生 gate 只作诊断事实**：被测流程自身 gate 不构成维护判据。
- **回灌不误判漂移**：finalize 三方检查下，前序 Case 合法写入与重复 finalize 不算主工程漂移。
- **正向实现，不打补丁**：改一处能力时把它**整体改到位**，不留下半新半旧的地层。四条判据：
  ① 同一职责**不得新旧两套并存**——旧形态的指令还在、新形态的门禁已上线，模型会读到互相矛盾的要求；
  ② 兼容旧格式的降级分支**不得静默**——要降级就出声，静默降级等于把「没接上」伪装成「正常路径」；
  ③ **导出即须有消费者**——零调用方的导出是死代码，它守着的那份数据也就成了从不生效的第二真源；
  ④ `暂时/临时/待迁移/TODO` 不得跨轮次留存——留过一轮的临时方案就是永久方案，只是没人认领。

  **改契约文本时同步它的消费方**：实测出现过契约里写着某个章号、某条编号、某个钩子名，
  而实现早已改名或根本没注册——文本与实现相斥时，读文本的人（和模型）会照着不存在的东西做。

机制证据与框架运行细节（`knowledgePaths` 行为、`{spec_content}` 注入、hook 返回契约等）见当前轮次
设计文档——本文件只保留不变量，不搬实现细节。

## 2.1 知识与机制的引用边界（谁写什么，谁不写什么）

**一句话**：知识回答「约束是什么、怎么判命中、怎么验」；机制回答「哪个阶段读哪一部分、产出落到哪」。
两边都不复述对方的内容——复述即双真源，双真源必漂移。

| 内容 | 归属 | 反例（曾犯） |
|---|---|---|
| 域清单、条目编号、命中条件、强制力 | **知识**（`knowledge/`） | 机制层脚本正则写死七个域前缀，新增一个域要改代码 |
| 某域在某阶段"该做什么"（布局方案、权限方案、防重入落实…） | **知识**（各域条目/落法附注） | 消费矩阵格子复制域专属动作，与域文件双份维护 |
| 哪个阶段读哪个分区（矩阵格子） | **机制**（消费矩阵） | 知识文件里写消费方的落点坐标（章节号、契约字段路径、表名） |
| 工程实现事实（封装、类名、模块路径、方法） | **项目知识**（`codebase-facts.md` / `component-profile.md`） | 规约的落法附注列工具类名与模块路径；同一封装在两个面各登记一次且互相打架 |

**派生优于枚举**：机制层需要知道"有哪些域/哪些模式"时，运行期从 manifest 激活清单与知识正文派生
（如域前缀取自各域条目编号），不在代码里维护第二份清单。派生不出来要出声，不要退化成空集。

## 2.2 知识编写要求（写什么、怎么写）

- **知识边界（N 类）**：只承载读完代码仓后依然无法可靠得到的判断——隐藏的为什么（决策/取舍/被否方案）、
  全局不变量、例外与边界、约束强制语义、多实现需统一的裁定；**代码可见且写法唯一的一律由模型读仓学习，
  不写入知识**。
- **不穷举**：不列 API 签名、字段清单、调用点、实现形态、工具类名单。判据：这条写下来，
  一次重构会不会让它变成假话？会，就说明它属于代码而不属于知识。
- **落法附注写什么**：平台隐性例外（读代码看不出来的框架行为）、边界、本工程决策的**理由**；
  需要指到具体封装时，**指向项目知识的对应面**，不在规约里复制类名。
- **允许的代码**：规则示意用的伪码判据、写法模板（`static readonly <NAME>: boolean` 这类形态）、
  证否所需的检索项清单（"没有"必须写明查了什么才叫核对过）；**设计模式的代码结构是例外，允许完整骨架**。
- **一面一登记**：同一个事实只在一个面登记；别处需要时写"见 X 面"。
- **引用必须真实存在**：跨文件引用某条目前先确认该条目在目标文件里存在（曾出现三处指向不存在条目的悬空引用）。
- **交付到其它仓的判据**：知识层的每一条都要能在目标仓核实；核实不了的登记为证据缺口，不照抄不虚构。

## 3. 修改纪律

- 先定位最早产生问题的代码或契约，局部修复并同步直接消费者。
- 不把测试答案、维护历史或其他 Case 行为写入初始 prompt。
- 新增或修改运行规则时覆盖成功、失败和恢复路径。
- 完成前运行 Story 单测、Tools CLI 检查、Python 编译和只读 plan 演练；除非用户启动正式测试，不运行真实被测 CLI。

## 4. 维护红线（经验教训）

- 文档状态 ≠ 代码真值：设计/方案文档**禁止写"已实施"**；实施事实与行为验证结论分栏记录。
- 离线全绿 ≠ 行为完成：脚本通过只证明结构，模型行为结论须由隔离 Case / CLI 实跑给出。
- 不引入事实 ID / 平行 contracts 命名空间 / 统一知识解析框架 / 成文状态机。
- 知识层交付到其它仓时，SDK 身份 / API / 案例 / 依赖仍是适配层，必须按目标仓真实事实核实后才能标"已确认"，
  不照抄外部归档的未核实内容。
- 不给模型做"机械保证语义"的承诺：内容守恒、人读质量是语义判断，脚本只守结构与引用完整性。

## 5. 协作与推进约定

- 本领域维护者偏好**确定性的正确结论**，不接受"倾向默认简单选项"的权衡；拿不准机制时先实读框架源码再下结论。
- 历史方案只作**机制形态参考**，源内容逐条比对冻结需求后决定采纳或拒绝，严禁照抄。
- 当前轮次的需求基线、设计与版本映射以轮次 `spec/`、`design/` 为准，新会话先读本节再读轮次文档。
