# Story Extension 维护契约

> 本文件约束整个 Story Extension 的维护：Framework 协作、skills、hooks、knowledge、adaptation、测试能力与交付入口。
> 它写给维护者，不进入执行者上下文。

## 0. 权威入口

- **维护 Extension**：先完整阅读本文件，再读取当前轮次的需求、设计和状态记录。
- **运行、修改或评价 Extension 测试**：完整阅读并遵循 [TEST.md](TEST.md)。测试命令、CLI 协议、状态、观测、评分、
  回灌和清理只在那里维护；本文件不复述。
- **追溯历史**：读取 [EVOLUTION.md](EVOLUTION.md)。历史方案只提供演进证据，不直接成为当前实现依据。
- **判定当前需求**：以 `test/story/spec/` 的冻结澄清和当前 `test/story/design/` 轮次为准。`doc/features/*` 是历史产物，不是需求真源。
- **运行模式范围**：当前 Story Extension 的设计、实现和验收只覆盖 interactive。headless/goal 不进入当前范围，
  不为它们增加兼容、状态或测试，也不把“未覆盖”写成“已支持”；未来只有用户明确提出时另立需求和验收。
- Framework、Extension 的全部生命周期能力及其 Skill、Hook、Knowledge、Adaptation、Harness、Verifier 和测试都是被维护对象。
  维护者直接检查其源码、配置、测试和产物，
  不调用被维护系统的流程来设计或证明它自身正确。

## 1. 只有两种角色

### 1.1 维护者

维护者属于本项目，负责：

- 定位 Extension 的行为问题和最早失效点；
- 澄清需求，制定正向方案与验收标准；
- 实现或审查 Framework 协作、Extension 机制、knowledge、adaptation 和测试能力；
- 保证交付给执行者的内容符合 writing-for-agents：要求在使用前送达，任务边界清楚，完成条件可检查；
- 调度 CLI 观察真实执行行为，并根据真实证据决定下一轮修改。

维护者调度 CLI 实跑时仍是维护者，只是临时代理人类需求方：自然回答需求问题、交付材料、观察过程与结果。
这个模式下按 `TEST.md` 行事，不向执行者提供测试答案、维护历史、脚本命令、文件坐标或实现路径。

### 1.2 执行者

执行者不属于本项目维护团队。它是使用 Framework + Extension 在目标工程开发真实需求的模型，包括外网隔离 Case
启动的被测模型和内网仓实际使用 Extension 的模型。

执行者正常完成任务只依赖需求材料、目标仓事实、Framework 与 Extension 上下文。交付内容不要求或引导它读取
`test/story/`、历史方案、失败用例或 checker 源码来学习要求。执行者读取 checker 只是调查信号：是否属于 Agent 系统问题，
须结合 Story/Review 质量、性能、Knowledge 应用及跨 Case/配置的重复情况判断，不能凭一次读取直接下结论。
明确的工具或脚本内部错误可以读取相关实现定位，但不能据此改业务产物迎合隐藏判据；发现的问题回维护层处理。

`TEST.md` 中的宿主、观测者和需求方代理，都是维护者在测试模式下的职责；被测模型就是执行者。
verifier 是 Framework + Extension 内部用于独立审查的执行能力，不构成第三种项目角色。

## 2. 这是 AI Agent 系统

Framework + Extension 的本质是一套指导模型完成需求开发的 **AI Agent 系统**，不是代码产品。
提示词、知识、脚本、门禁、状态文件和报告只是实现载体；系统的评价对象是执行者在未知需求上的行为。

端到端能力和会影响执行者行为的机制用同一条行为链描述和验收：

```text
输入事实 → 按时送达 → 正确理解 → 做出决策 → 产生产物 → 传给下游 → 失败恢复 → 留下证据
```

代码通过、字段出现、门禁全绿或报告写了结论，只能证明载体的局部性质。执行者是否在不接触维护材料的情况下，
以合理成本得到符合目标的结果，才是能力是否成立。

局部确定性能力只需证明它实际承担的输入、输出、失败语义和消费者；不为文件解析、路径检查等 helper 强行增加模型理解、
verifier 或真实 CLI。局部能力组合成用户可见行为时，再沿完整行为链验收。

## 3. Framework、Extension、Knowledge 与测试的所有权

| 部分 | 负责 | 不负责 |
|---|---|---|
| Framework | 通用阶段、上下文装配、工具、宿主能力、verifier 调度、阶段闭环与公共扩展点 | 实例业务知识、Story 专属产物语义 |
| Extension 机制层 | 需求流程、作者任务、阶段扩展、知识路由、产物合同和确定性辅助能力 | 目标仓专名、测试答案、Framework 通用能力的影子实现 |
| Knowledge | 项目事实、规约和设计模式；内容由目标仓维护 | 阶段调度、消费方坐标、测试与维护历史 |
| Adaptation | 保持机制不变，按目标仓事实修正、扩展 knowledge，并接好实例入口 | 把目标仓知识照抄成 demo 内容，或重写一套通用机制 |
| 测试域 | 隔离输入、调度、观测、证据留存、离线回归与真实行为评价 | 替执行者完成任务、把用例答案注入交付物 |

问题修在最早拥有该职责的位置：通用宿主能力回 Framework，实例行为回 Extension，项目事实回 Knowledge，
适配行为回 Adaptation，观测与测量错误回测试域。缺少 Framework 能力时明确提出或补齐 Framework 能力，
不在 Extension 内复制一套旁路框架。

Framework 的正式交付落在其权威源，并由 framework-init UPDATE 进入消费仓。本工程 vendored `framework/` 只有在用户明确授权的
单步验证中可以临时修改；本地验证通过不等于上游或内网已经获得能力，交付时须保留上游基线、可复现补丁和临时放行的失效条件。

## 4. Agent-first 设计

### 4.1 信息先于决策

执行者做决定之前，所需目标、事实、约束、可用能力和完成条件必须已经进入它的实际上下文。
文件在磁盘上、manifest 有登记、hook 返回了文本，都不等于执行者已经看到。

报错负责指出哪个既定条件未满足以及如何回到正确路径；它不是首次交付规则的渠道。执行者依靠连续失败才逐步学会要求，
说明作者输入不完整。

### 4.2 模型与脚本按能力分工

- 模型负责理解语义、判断适用性、处理冲突、作取舍、组织叙事和评价内容是否讲清。
- 脚本负责文件导入、格式转换、枚举、路径解析、结构校验、确定性渲染、状态记录和可复现比较。
- token、子串、字数、数量、相似度和字段存在性只表达它们真实测到的机械事实，不升级成语义结论。
- 语义审查由独立于作者上下文的 verifier 完成；脚本只验证审查对象、证据引用和结果结构真实存在。

### 4.3 不把提示词承诺当作执行保证

执行者是非确定性模型，可能忽略、略写、误解、跳步或编造；维护者不能假设一条清楚的提示就会被 100% 执行，
也不能因此把语义判断全部改写成脚本规则。系统级高风险行为由以下控制层按实际风险组合保护：

| 层 | 责任 |
|---|---|
| 提示词 / 作者任务包 | 在行动前交付完整目标、输入、步骤、输出合同和失败处置 |
| 确定性脚本 | 冻结输入，控制步骤与状态，生成骨架，检查结构、引用、精确来源和证据完整性 |
| 独立 verifier | 判断遗漏、略写、矛盾、编造、表达质量与知识是否真正应用 |
| 隔离行为测试 | 验证未知执行者、未知材料、时间成本和整套协作是否成立 |

作者提示与 checker 共享同一份事实、结构和状态真源，避免文字要求和执行条件分叉；语义指引保持人可读，
不为追求“同一合同生成一切”而把它强塞进机器 schema。单一控制层不能证明端到端 Agent 行为：提示词不保证执行，
脚本不证明语义，verifier 自述不代替身份与证据验真，已知 Case 通过不证明泛化。纯确定性子能力按其适用证据闭环，
不强制经过无关的 verifier 或真实行为测试。

确定性门在当前输入允许的范围内尽量一次报告完整问题，并同时列出因前置缺失而未执行的检查。作者机制以高质量完成主要内容为
首要目标，内容按适合当前任务的安全边界可靠落盘；verifier 是纠偏安全网，不代替作者补写主体。运行机制不写死生成或返修次数。
重复出现同类问题、错误不收敛或修订成本持续增长时，回到维护层检查任务包、输入规模、职责分配、verifier 定义或模型能力，
不让执行者无界撞门禁。

### 4.4 设计完成条件

一项机制只有同时满足以下条件才算设计闭合：

1. 执行者的输入、动作、输出、下游消费者和失败路径明确；
2. 指令在对应动作之前送达，不依赖 checker 教学；
3. 脚本没有承担无法确定计算的语义判断；
4. 适用的提示词、脚本、verifier 和行为测试责任明确，执行者的忽略、略写、编造与跳步都有发现者和恢复路径；
5. 验收能区分正确与错误结果，而不只是检查写了字；
6. 换一个未知业务域，机制仍成立且无需增加特例。

## 5. Extension 结构与不变量

### 5.1 两层与一座桥梁

- **机制层**：`doc/extensions` 中 `knowledge/` 以外的 skills、hooks、overlays、scripts、合同与入口。
  它基于 Framework 公共扩展点运行，对目标仓模块名、SDK、业务名、绝对路径和测试 Case 零强依赖。
- **知识层**：`knowledge/` 下的项目事实、规约和设计模式。本仓内容是可适配样板，目标仓使用前按真实事实核实和扩展。
- **Adaptation 桥梁**：把机制接入目标仓并替换知识内容。它连接两层，不形成第三套内容所有权。

### 5.2 单一真源

- 同一事实、状态、配置、编号含义、图片登记和决策只维护一个权威来源；其他视图由权威来源生成或解析。
- 随工程变化的约定放在数据合同或配置中；脚本消费数据，不把当前工程的值固化成正则和分支。
- 机制需要域、条目、模式、角色或模块集合时，从权威清单与正文派生；派生失败时明确报错。
- 业务名、契约名、ID 和编号只用于身份、引用和下游追踪，不充当内容语义。Story/Review 的完整性围绕已确认范围内的业务事实、
  关系、流程、异常、验收与决策，由独立语义审查判断。
- 契约修改与直接消费者在同一步同步；写入者、读取者和验证者对同一状态使用同一含义。
- 下游没有动作时给出明确的不适用及理由；缺席不代表不适用。

### 5.3 交付面通用性

- 执行者提示只写正向目标、输入、动作、完成条件和恢复方式；不把维护历史与失败目录带入执行上下文。
- 测试、维护注释和判据可以描述失效形态，但不把具体 Case 单号、测试业务名、某次运行数字、批次编号或维护故事写入交付机制。
- **交付面的注释只说明当前**：这段代码或这条判据现在是什么、为什么这样、边界在哪。不写演进过程——
  「上一版」「曾经」「改动前」「实测一轮」「首跑」「步骤 N」「批次 N」这类叙述一律不进交付面。
  **理由不是篇幅，是过拟合**：执行者会直接打开脚本读，注释里的测试数据（Case 名、需求单号、
  suite 编号、某次运行的计数、模型名）就成了它照着写的样板，测出来的是「照抄那一次」而不是
  「在未知需求上做对」。
  退场理由、失败故事与实测数字留在 `test/story/`（方案、评审、台账）——那里才是它们的家。
  判据「为什么这样定」要留在注释里，但用现在时讲道理，不讲历史：
  写「读不到的来源也要带回来，静默跳过会让一整类材料零信号」，不写「上一版这里是静默跳过，实测……」。
- 示例使用与测试 Case 无关的中性题材，示例与命中条件分开；示例不收窄规则适用范围。
- 交付内容只写执行者完成任务所需的信息。维护方法、测试方法和演进原因留在 `test/story/`。
- 内容对未知业务仍成立才算通用；当前 Case 命中不是通用性的证明。

## 6. Knowledge 的内容与消费

### 6.1 知识内容的边界

| 类型 | 回答 | 内容要求 |
|---|---|---|
| 项目事实 | 目标仓有什么、在哪里、通常怎样使用 | 真实路径、类名、API、封装形态和工程惯例；不写阶段路由与维护规则 |
| 规约 | 什么条件下必须做或禁止做什么 | 一条一个可独立判断的要求，写清命中条件、边界与例外；实现专名引用项目事实 |
| 设计模式 | 什么情形适用、由哪些角色协作、怎样验证 | 适用与不适用条件、角色、骨架和验证清单；目标仓是否采用由具体需求决定 |

同一知识只在一个面登记，引用指向真实存在的权威内容。知识正文不给维护者讲如何维护 knowledge，也不写消费阶段坐标。
机制只维护消费时机和产物出口，不复制知识条目、域清单或模式角色。

### 6.2 知识链

Knowledge 能力的验收对象是：

```text
看到 → 理解 → 应用 → 传递
```

- **看到**：当前阶段需要的知识类型和已激活内容实际进入正确执行体的输入；具体条目是否适用于当前需求，由对应阶段读取后判断，
  不要求机制在语义判断前自动过滤。
- **理解**：执行体结合当前需求判断适用、不适用或冲突，不回显知识名称冒充判断。
- **应用**：适用知识改变本阶段的具体产物、设计或契约实体，有可指认的业务落点。
- **传递**：下游读取上游已经形成的知识决策与义务，提供落实证据或明确不适用，不重新猜测原始知识。

三类知识使用不同职责链：

- **项目事实**从 Spec 起作为目标仓事实使用；发现错误回 Knowledge 真源修正，不进入选型。
- **规约**由 Spec 判断是否命中并形成当前需求约束，Plan 决定设计落点和验证方式，不能无理由取消命中项。
- **设计模式**由 Spec 提出候选与适用理由，Plan 选择、拒绝或调整并冻结。

“理解”是从执行者的判断、产物变化和独立审查中取得的可观察证据，不声称脚本能够直接证明模型内部状态。
知识的适用性与落实决定在受其影响的设计之前形成；排在设计之后的知识总结不构成设计输入。
manifest 是知识激活清单的唯一来源。新增、删除或修改知识时，通用机制无需增加域名、编号、文件名或特例即可完成整条知识链。
Demo 仓维护者保证样板结构有效、类型边界正确并能演示和测试完整知识链，不把 Knowledge 优化改造成自动同步 Demo 业务代码的系统。
CLI 或其它验证一旦发现样板内容、边界或消费结果有真实问题，须按 Knowledge、Extension、Framework 或测试的实际所有权及时修复并
增加回归，不能以“只是 Demo”为由长期挂账。真实目标仓负责把三类知识修正和扩展为自身事实。

## 7. 维护方法

### 7.1 从行为和根因开始

1. 先还原执行者当时实际看到了什么、理解了什么、做了什么以及在哪一步偏离。
2. 区分产物缺陷、执行者行为、Extension 指令、Framework 能力、Knowledge 内容和测试观测。
3. 定位最早拥有错误职责或错误输入的位置，在那里修正；不围绕最后一条报错设计。
4. 从目标行为重新推导方案，明确保留、替换、删除和不做的内容。

### 7.2 整体修改一项职责

- 一个完整需求或问题可以按风险拆成多个批次和步骤。单步允许交付安全、可验证且有明确后继的中间态；迁移桥须写清所有者、用途、
  删除步骤和退出条件，同一正式入口同时只启用一套职责。
- 整个需求完成时只保留一套现行路径，并删除被替代的指令、状态、门禁、兼容分支、迁移桥和零消费者导出。
- 降级行为必须可观察并有明确适用条件；正常路径不依赖静默降级。
- 没有明确退出步骤的临时路径不得跨轮次沉积；已登记迁移桥按计划退出，不能转成长期兼容层。
- 新增通用框架、状态机、解析器、生成器或评测设施前，证明它是当前目标不可缺少的最小能力，并取得用户确认。

### 7.3 分步实施与独立审查

- 方案维护者把改动拆成职责闭合的步骤，每步冻结目标、事实、允许范围、保护区、实现要求和验收方法；步骤里写明本步对需求预算的预计增减，
  供执行者自检与评审对照，不作为按步骤拦截的门（预算规则见 §7.2）。
- 独立实施会话一次只实施当前步骤，记录实际 diff、输入生产者、处理位置、消费者、失败路径和离线结果，
  只能声明“已实施，等待评审”。
- 维护者从实际文件重新还原行为；实施者自述、字段出现和测试全绿都不能替代审查。
- 当前步骤通过后才能进入下一步。后续发现前序问题时重新打开原步骤，不在当前步骤顺手打补丁。

### 7.4 分层证据

- 结构证据证明文件、合同、引用、状态和确定性脚本正确。
- 独立语义审查证明任务定义、内容和职责满足当前需求。
- 隔离 CLI 证明执行者在真实上下文中的行为；它按 `TEST.md` 只在用户启动的里程碑运行，**跑的是正常需求**，结果由用户按评分协议判。
  构造缺陷稿、删事实、造反例只用于确定性脚本的自检与事后诊断，不用来证明模型的判断力——模型的判断力从真实产物上被人找到的问题它报没报来看。
- Extension 测试及行为评价遵循 `TEST.md`；证据须绑定实际宿主、模型与运行配置，不能外推到未验证环境。
- 文档中的“已实施”、原生 gate、离线全绿和一次已知 Case 成功，均不单独构成行为完成。

### 7.5 一次完整需求的规模预算

**为什么有这一条**：机制层的每一次膨胀都不是一次加出来的，而是一步一步各有理由地加出来的；等到一轮结束再看总数，
已经没有人能说清哪一行该退。所以规模是需求级的承诺，随方案一起定，随需求一起收。

**对象**：`doc/extensions` 中 `knowledge/` 以外的全部内容，按类别计（skills 脚本、hooks 脚本、提示词、合同数据）。
**数的是代码行——注释与空行不计**。配额限的是机制的规模，不是文字的长短：把注释算进配额，
省下来的只会是解释，而解释正是下一个维护者判断「这条判据还该不该在」的依据。
逐类怎么剥注释见预算文件头部的「计数口径」。
数字只是围栏，不表达质量；表达质量的判据仍是 §4.2 与已登记的确定性失败清单。

**三个角色各做一件事**：

| 时点 | 谁 | 做什么 |
|---|---|---|
| 定方案 | 维护者 | 与方案同时给出本需求**进行中的峰值**与**完成后的上限**，按类别具名登记进预算文件（位置见 `TEST.md §8` 第 7 项），写清新增脚本行归哪一类确定性失败、退掉什么 |
| 改完自检 | 执行者 | 对照预算自检两向：超出峰值是否合理——方案估错就回方案改预算并写原因，**不砍方案、不拆功能、不少写测试**；远低于预期是否遗漏——该建的没建、该退的没退 |
| 测试后审查 | 评审 | 发现实际与预算的差异，超与不足都申请特别审视其合理性；差异有理由的记入预算文件，没理由的回开对应步骤 |

**判据只有三条**：需求进行中不超过方案声明的峰值；需求完成时回到上限以内（这是完成条件的一部分）；脚本里的语义代理标识
（相似度、复述、最短引文之类）任何时候不得增长——那不是规模，是方向，出现就是又在用字符串近似「讲清没讲清」。

**不按步骤拦中间态**：一个需求在实施途中允许先加后删、允许暂时高于完成后的上限。门只在峰值与完成时点起作用；
红了是提醒回读本节与 §4.2，不是裁剪方案的理由。改预算的任何数字都要具名与理由，和 framework 漂移放行、失效形态退役同一套纪律。

## 8. 完成前自检

- 交付面的注释只讲当前：`grep -rnE "实测|首跑|上一版|曾经|改动前|批次 ?[0-9]|步骤 ?[0-9]" doc/extensions`
  （`knowledge/` 之外）零命中；注释里没有 Case 名、需求单号、suite 编号、运行计数与模型名。
- 两种角色没有混用，测试模式没有向执行者泄漏维护信息。
- 每项改动能追溯到需求、系统所有权或改动直接产生的清理。
- 执行者在行动前已经得到必要信息，正常完成无需阅读 checker 或连续试错。
- 模型与脚本各自承担其可可靠完成的工作；对照需求预算自检过超出与不足，新增脚本行逐段归到确定性失败清单，语义代理标识零新增。
- 改动涉及 Knowledge 时，看到、理解、应用、传递均有消费者和证据。
- 分步实施的中间态符合已登记边界；整个需求完成时迁移桥全部退出，单一真源和直接消费者保持一致。
- 机制对未知业务域成立，交付面没有测试与维护痕迹。
- 测试命令和正式运行授权完全遵循 `TEST.md`。
