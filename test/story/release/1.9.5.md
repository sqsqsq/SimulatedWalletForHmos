# Story Extension 1.9.5 发布说明

> 2026-09-24 收口。上一版见 [1.9.4](1.9.4.md)，本版在它之上做增量。
> 四轮真实 CLI 实跑（两 Case：auto-topup 到 spec、car-key-sharing 到 plan）。第三轮三轴分已由用户确认，第四轮定向实跑的三轴分待用户审视，本文不代填。

## 本版新增与优化

### 1. 上报设计：从指标出发，Spec 讲统计点，Plan 落到实现

- **项目上报知识**：新增 `knowledge/facts/reporting.md`，VOC / Chart / BI 在一处维护——渠道与已有自动采集、身份与 SDK 映射、结果与字段、业务扩展字段、登记与分配规则、从指标反推结果的使用参考。`observability.md` 重写为五条基线义务（定位记录、运维统计点完整、协议字段正确、编码复用与唯一、独立运营采集要有需求依据）。
- **Spec §9.4 以指标为单位**：总述一段之后，每个指标一个 H4，下面是指标定义与依据、统计点表、备注；spec 门禁核「有表必有 H4、每个 H4 至少一行统计点」。
- **Plan 埋点逐统计点落实**：新增 plan 任务包 `hooks/plan/author.mjs`，把 Spec 9.4 的统计点逐条列给作者并附固定几问；Plan 埋点小节对每个统计点写结果、本端何时得知、责任方法、去重与耗时、验证，项目知识定义了协议字段的再给身份与编码。plan 门禁新增三项：每个统计点有对应行、责任方法能在契约里找到、命中统计义务的方法挂了对应 must。
- **审查并列**：plan 审查任务把 Spec 统计点、Plan 埋点行与激活的上报知识并列摆出，按统计点名对齐。

### 2. Story 附录是登记处，全篇一条编号规则

- **附录四节**：技术约定（接口 / 数据 / 配置 / 埋点）、改动边界、规约判定、材料清单。机器区按章节合同的 `projection` 从 Spec 与知识判断投影，作者在机器区之外写说明；每节开头一句业务定位句，只在附录。
- **全篇按深度递归编号**：任何层级的标题都按深度自动编号（10.1、10.1.4.1），附录不再用字母序；正文引用写小节名，不写号。

### 3. 写作心智：向没参与的同事解释业务

- `story-write.md` 开头是读者心智段与一段中性范例（会员开通），重复讲形态的句子退出，留下的每条对应审查维度或机器核点。
- **图三件套**：图前把过程讲一遍、放图、图后逐条讲分支里读者要知道的条件、责任、后果；表达选择表按「读者要判断什么」选载体。
- 写作设计空壳：阅读主线三问（读者是谁、读完要做什么决定、哪几件事最容易误解），每章问读者要能回答什么。
- 草稿章头两行：读完这一章读者要能回答什么；别的章负责什么、这里不重复。
- 读者审查的建议项加上「正文里指着文档说话的句子与章开场白」；验收章有埋点时末尾一段讲上线后观察的指标。

### 4. 作者、审查与交付门

- 规约原文按实际扩展目录送到作者与审查者；作者先判断适用，再完成承载章设计；审查先走业务，再核交接。
- 章号与引用按模板核，附录不带源编号；需求来源统一为「只有 AR 开头走需求系统」。
- **交付门按改动性质分流**：当前报告 PASS 之后的改动只是它的 advisory 或 WARN 修法时，重跑 harness 走历史沿用并在 `notes.md` 记一句；改变业务口径、范围、验收条件或新增实体才重新派审。plan 作者页、spec、update 三处同一句。
- 收尾门禁分清「检查没跑成」与「内容不通过」；开轮时已闭环的阶段，收口时须仍闭环。

### 5. 对接层与内网一致

- **core 与 adapters 隔离**：core 只返回本需求的本地位置 `paths`，不再生成取材命令；SKILL 编排模型调用对接层；对接层不提示 core 的步骤。
- **Demo 对接层按内网的文件划分与导出签名拆分**：`story.js` 入口分发（参数错只写 stderr，命令异常由顶层 catch 写 JSON）；`fetch.js` 导出 `fetchOne`（init 逐级拉 AR → SR → RR）与 `fetchUpstream`（update 只读取材）；`archive.js`、`restore.js`、`mcp.js`（同名替身）、`dirs.js`。
- **需求目录备份统一在 `.backups/`**：`cloud/` 是需求系统拉取内容的备份（归档覆盖系统正文前的那一版，restore 据它恢复系统数据）；`local/` 是本地文档的备份。
- [内网适配指南（1.9.3 → 1.9.5）](内网适配指南-1.9.3升级1.9.5.md)：内网要做的是新建上报知识与改对接脚本，其余由 `/story adapt` 自动完成；另归档 [内网 adapters 架构描述](内网adapters架构描述.md)。

## 未达成与移交 1.9.6

设计者对第四轮的独立评审（`plan/1.9.5/2026-09-24-埋点阶段分工复核/`）结论：**整体目标尚未达成**。

- **埋点的阶段分工**：Spec / Story 提前写了实现协议（结果分类、登记规则），Plan 又重复上游，并把身份与编码推给编码阶段。要按阶段明确完成对象与所用知识，业务统计语义与项目技术实现在 `reporting.md` 内分清。
- **未决业务结论进了正文与验收**、Plan 契约不完整、语义审查没拦住。
- **机制措辞被照写**：附录定位占位 `{{一句：这一节登记什么的精确名称}}` 被写成「这一节登记……」，图指引被写成「图后判断：」小标题；两份 Story 都没写「上线后观察」。
- 代码与上报原始事件的正确性由内网验证，Demo 止于 Plan。
