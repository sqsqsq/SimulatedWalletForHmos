# 内网需求系统对接适配指南

2026-09-23，按用户给出的内网实现职责确认。读者是维护目标工程对接层的模型。本文与上报知识适配分开：本次新增取材命令、删除旧review入口、纠正需求来源判断，不新增对接层help，也不把真实内网的模块结构改造成Demo单文件实现。

## 1. 入口与需求来源

`adapters/story.js` 是需求系统对接的唯一CLI入口，业务命令只有 `init`、`fetch`、`archive`、`restore`。无命令或非法命令给出简短用法/非零退出即可，不实现额外 `help` 命令，不在数据对接层复制需求开发流程。`/story help` 是流程层帮助，可保留；它与对接脚本help不是同一职责。

**本目标项目仅以 AR 开头的需求属于系统支持的需求，其余均为本地需求。** 判断使用项目既有单号规范化方式，不追加数字长度、local前缀等未经确认的规则。编号包含AR但不在开头，不因此成为系统需求。

- AR需求查无此单、缺token、系统故障：按故障返回，不能降级成本地需求。
- ISSUE、DTS、自定义名称、local开头等非AR需求均为本地；不会因没有local字样而访问系统。
- 本地需求走本地材料/产物流程，不取需求系统token、不发MCP请求、不提供系统归档/系统restore动作。若误将本地编号传入系统对接命令，在任何系统访问前明确返回不适用/失败。
- AR/detail.json存在与否是取材结果，不是重新定义来源的依据；本地残留文件也不能把非AR需求升级为系统需求。

这是本项目系统支持范围，不能把它未经确认推广为所有工程的通用单号协议。通用流程和项目对接层须使用同一来源决定，不能各自猜一套关键词；优先复用既有来源记录/合同，确有信息缺口先定位消费者，不为分类新增help、探测命令或业务框架。

## 2. 内网既有模块职责

| 文件 | 当前职责 | 本次动作 |
|---|---|---|
| story.js | 唯一入口，分派命令 | 接入fetch，删除review/help分派和旧用法；保持现有init/archive/restore合同 |
| fetch.js | init命令的实现 | 保留，不因文件名叫fetch就改派到新fetch命令 |
| fetch-upstream.js | fetch命令的实现 | 本次新增：只读取回当前上游与评审材料 |
| archive.js | archive命令的实现 | 保留既有正文/附件归档、备份和校验语义 |
| restore.js | restore命令的实现 | 保留系统归档回退语义，不与本地产物更新恢复混淆 |
| review.js | 旧review命令实现 | 本次删除；共享有效能力移回其真正责任模块后清引用 |
| mcp.js | 内容MCP HTTP调用底层封装 | 复用，不在每个命令重复实现HTTP/token处理 |
| dirs.js | 目录路径、清理、时间戳工具 | 复用既有工程路径规则 |
| post-process.js | HTML转Markdown与图片下载后处理编排 | 新取材需要时复用，输出指向本轮指定目录 |
| html-to-md.js | 富文本转Markdown | 由post-process调用，保留真实转换能力 |
| download-images.js | 在线图片下载替换 | 由post-process调用，保留真实图片能力 |
| image-map.js | 本地图片地址与远端URL映射 | 复用，不维护第二套映射 |
| token.js | 从配置文件读MCP token | 保留；本地需求不触发 |

唯一CLI入口不等于所有业务必须写成一个JS文件。目录中的工具文件不因此成为需要模型直接调用的公共命令。适配/升级保持整个目标对接层的所有权，不用Demo替身覆盖这些真实实现。

## 3. init 与 fetch 的区别

| CLI命令 | 实现模块 | 目的 |
|---|---|---|
| `story.js init <AR> ...` | fetch.js | 首次取该需求及其关联材料，供初始化需求流程使用 |
| `story.js fetch <AR> ... --out <本单收件目录>` | fetch-upstream.js | 取回本次更新所需的最新上游与评审回稿，不覆盖当前业务产物 |

新fetch复用内网的MCP、token、目录和后处理能力。真实系统有HTML/图片时按已有转换/下载链处理；不能因为Demo替身只存Markdown，就要求内网删除这条能力。具体MCP接口、参数与图片归档策略按真实代码取证，不在本指南臆造。

fetch保持当前扩展消费的可观察合同：

- `--out`明确指定本需求的收件目录；`--project-root`用于确定该需求的回执位置，不写到其他工程。
- 当前关联AR/SR/RR正文取到后写入收件目录；评审回稿写入约定的 `AR/story-src/review-feedback.md`，取材回执写 `AR/story-src/fetched.json`。保留既有相同内容不重复落盘的约定。
- `fetched`、`same`、`absent`、`failed`分别表示取到/内容相同/系统不存在/读取失败，不把读取失败当无变更。
- 当前Spec/Story/Review/Plan和已采用需求正文不由fetch覆盖。后处理文件和图片映射也要核写入范围，不借复用工具覆盖当前业务文件。
- stdout最后一行返回既有JSON结果，日志走stderr；任一读取故障如实返回失败，不能写占位件后宣称成功。回执字段沿当前scripts/README和消费方合同核对；其中help与local前缀的旧描述已被本指南的用户确认纠正，需同步删除。

update由流程层指导模型调用 `story.js fetch`，然后读取回执；新模块不替模型理解材料、决定业务变化或触发归档。

## 5. 外网新增能力的适配交付要求

adapters是内外网实现隔离边界。外网新增功能不能仅改core和替身：凡涉及该边界，适配发布必须同时给出对接增量说明，并同步随包交付的scripts/README合同。

| 必须交代 | 内容 |
|---|---|
| 能力变化 | 新增什么、修改什么、删除什么；无变化也明确 |
| 消费者 | 哪个实际流程在什么时机使用，缺失影响哪些功能 |
| 对接合同 | 参数、输出、写盘范围、鉴权需求、不适用与失败结果 |
| 内网动作 | 公共入口如何接线、可复用的现有能力、新实现的责任；不臆造目标内部结构 |
| 退出与保护 | 被替代入口/模块怎样退出，仍有效的原能力怎样保留 |
| 验证与状态 | 正常/失败/本地不适用场景，实际验证证据和未适配事项 |

本次具体增量：story.js新增fetch分派到fetch-upstream.js；init继续由fetch.js实现；review入口与review.js退出；数据对接help退出而流程help保留；仅AR开头进入系统流程。MCP、富文本、图片和token现有模块复用，不用外网替身覆盖。

安装检查通过、外网替身通过、内网真实能力通过分别记录。内网尚未实现fetch时只能说明机制已升级、update上游取材尚未适配，不能笼统宣布update可用。后续每次跨边界变更按同样原则交接，不把具体项目文件名和AR策略固化到通用adapt复制逻辑。
