# 内网上报知识适配指南

适用读者：维护目标工程知识的模型与工程负责人。任务是依据目标仓的真实实现和项目约定，创建或完善 `knowledge/facts/reporting.md`、`knowledge/constraints/observability.md`。这是独立维护任务，不调用或定制 `/story adapt`；日常需求开发模型只消费适配完成后的知识。

本指南可以单独复制到内网，配合目标工程和两份知识样例使用，不依赖外网仓的测试、金样、设计或评审记录。它不进入目标知识激活清单，不要求所有需求都读取。

需求系统对接层（`adapters/`）自 1.9.3 起的改动也要在内网实现一次，见第 9 节；它与知识适配相互独立，可以分开做。

## 1. 可直接交给内网模型的任务

> 请阅读本指南，依据当前工程真实代码、现行上报协议和负责人确认的约定，完善 reporting.md 与 observability.md。先核已有能力和规则，再编辑文件，最后验证激活、引用和语义一致。保留当前有效知识及在途修改；不要照搬样例的类名、编码、参数或强制力。信息缺失时只问会影响结论的具体问题，其余已明确部分继续。交付两份知识、变更说明、依据和未验证项，不修改业务代码、Framework 或 adapt 实现。

## 2. 开始前取得什么

读取目标仓根级与知识目录适用的工作约定，以及知识总索引、facts/constraints/design-patterns 的说明。遵守目标仓现行知识协议；若它与样例格式不同，以目标协议为准，不修改通用加载器来迁就样例。

从工程配置确认扩展目录（如 `framework.config.json > paths.extension_dir`），以下路径均相对该目录，不能假定一定为 doc/extensions：

| 对象 | 用途 |
|---|---|
| `knowledge/facts/reporting.md` | 项目上报能力、协议定义、真实API与使用参考 |
| `knowledge/constraints/observability.md` | 独立、可判断、可落实验证的行为规约 |
| `manifest.yaml > provides.knowledge` | 两份文件的激活入口；未登记时补登记，已有同义文件先确认唯一来源 |

核工作区差异，辨明当前文件由谁修改；基于现稿增量处理，不覆盖其他任务。先查是否已有等价上报知识，避免另建第二份。接口名不同也可以是相同能力，不只按样例名称检索。

最小输入包括：目标仓代码、现行知识和配置、可用的上报协议/编号登记、负责人已确认的约定。适用时再读取真实需求材料和调用样例，不先要求收集所有历史文档。

## 3. 取证：查定义，也查实际调用

| 要查清的事 | 优先看哪里 | 要形成的结论 |
|---|---|---|
| VOC / Chart / BI 的职责和入口 | 管理门面、Builder、公共导出、发送适配与业务调用 | 哪些渠道存在、如何调用、哪些共用行为及差异 |
| 页面/点击自动上报 | 框架/组件埋点、注册/初始化、配置开关、实际页面接入 | 哪些交互覆盖、哪些入口有条件、业务还需报告哪些结果 |
| 完整事件身份 | eventID/funcID/subFuncID 定义、序列化和接收协议、常量登记 | 模板/流程/步骤的真实含义与传输映射；是否与结果字段独立 |
| 内码与结果分类 | 编码表、枚举、正常/失败/取消调用 | 段数/长度、前导零、各段语义、步骤成功与全流程成功的区别 |
| 运营参数 | BI调用与协议、产品/SE材料 | 是否与运维共用身份；必需/可选字段；是否允许借用内外码及其运营语义 |
| 扩展字段 | setter/参数类型、调用赋值、业务协议 | 类型、含义、来源、单位、缺席表示、隐私处理；字段名本身不能证明业务含义 |
| 结果来源与去重 | 业务回调、状态查询、重试/取消、结果收敛处 | 本端实际能观察什么；同点同尝试和新尝试怎样区分 |
| 失败与兼容 | 异常处理、发送失败行为、旧事件消费者 | 上报失败是否影响业务、旧值语义如何保持、谁维护登记 |

优先抽查一条正常路径、一条失败或取消路径，以及必要的重复回调/重试，不遍历所有业务造全量台账。定义与调用冲突时，写清差异，不能任选一方当规范；行为事实由代码证明，业务语义由有效协议或负责人确认。

查不到实现不等于项目没有这项能力：核依赖库和已有声明，无法取得的细节标未知。负责人已明确的项目能力可以作为有效输入，记录其适用工程；不要因为 Demo 没有而否定真实项目能力，也不要把未经核实的 API 签名写成现成接口。

## 4. 改 reporting.md：事实与项目惯例

采用目标现有 frontmatter 和“一节一面”的确认机制。`已确认`/`未确认`按目标知识协议使用；“字段名已核、业务含义未知”应区分，不用整节已确认掩盖猜测。

建议按以下内容组织，可合并很短的面，不强制固定小节数：

- **渠道与自动能力**：实际用途、入口、自动覆盖及接入条件。自动交互上报与手工业务结果上报分清。
- **事件身份与真实映射**：业务身份各部分对应哪些参数/常量/平台字段，VOC等不同协议单独说明。同一业务含义是否共用常量按项目事实。
- **结果与字段**：内码/外码/结果分类的真实含义、对应类型和设置方式，耗时单位与可选性。项目协议不是样例协议的机械翻译。
- **业务扩展字段**：如 channel/source、issueID/issueName、operationType、orderNumber、srcPassType，仅在目标存在时说明；含义和取值不能按名字推测。未定字段列具体待核问题。
- **登记与复用**：真实常量/码表位置、已有分配规则与维护入口；新需求可以依据项目规则建设缺失登记，不假称已分配。
- **短使用参考**：一个关系表或短调用说明步骤身份、子点、结果及字段怎样组合，限必要信息；不复制完整业务服务、状态机或大段测试代码。

协议定义在此唯一维护。例如“这个字段实际表示什么、合法枚举是什么”是事实；要求使用正确字段/保持兼容的义务在规约引用项目定义，不重复一整套码表。

知识正文不写本次维护过程、与Demo对比历史或Spec章节坐标。取证说明另写在本次交付记录，API定位等消费模型需要的信息留在facts。

## 5. 改 observability.md：少量独立义务

按目标仓既有编号与责任迁移，不默认覆盖它的全部规约。可参考五类责任：过程定位、运维覆盖、数据正确、定义兼容、独立运营需求依据。每条写清一个主要要求、命中条件、处置与验法；附注只补真实边界，不复制API、码表和字段手册。

参考样例采用基线：例外须理由、影响、补偿并经评审。目标仓若有明确不可豁免的要求则保留红线及依据，不为同样的外观统一降级；也不因为“上报很重要”就把全域升为红线。原有安全/合规要求由对应规约承担，避免重复定义。

以下是本次钱包项目已确认、适配时应核目标适用范围的约定：

| 项目约定 | 适配时落实 |
|---|---|
| 独立运营事件由产品/SE明确提出，无依据不默认新增 | 区分运营目标与新增BI事件要求；有目标但具体采集不清时澄清，不自行补曝光/点击漏斗 |
| 页面/点击已有自动运维上报 | 核真实覆盖后复用，不重复手工记录；它不替代业务步骤结果 |
| 同语义BI/Chart共用事件身份常量 | 依据真实常量复用，不按渠道再造编号；事件名/流程/步骤字段的具体结构按目标协议 |
| BI不默认带运维结果字段，允许有约定的类似语义复用 | 业务维度按需；借用内外码须明确运营含义、来源和消费约定 |
| 必要步骤成功也上报 | 使用目标的步骤成功分类；覆盖实际适用的失败/主动取消，未执行步骤不虚报 |
| 过程VOC、统计终态Chart | 核业务位置，避免同一统计终态双报；不扩成包括BI的三选一 |

目标工程已有明确不同协议时保留正确的目标规则，并在交付记录说明差异；只有确实与负责人已定要求冲突时请求裁定。不要把规则差异写成Extension分支。

## 6. 三类知识与机制边界

facts回答已有能力、定义和惯例；constraints回答必须履行的条件与结果；design-patterns回答可选实现结构。仅修改前两份知识，不为短调用或点位表新增设计模式。已有模式被业务选择时，在它的真实结果责任方落实上报即可。

Spec/Story/Plan分别何时读取、在哪章写，由现行Extension指引承担；两份知识不写这些坐标。此次适配不改hooks、模板、加载器、Framework、adapt脚本，不建立字段名/渠道枚举专用检查器。

若发现通用机制确实无法读取有效知识，保留最小复现与影响，交机制维护者处理；已能读取的部分照常完成，不能靠改知识含义绕过机制错误。若只是需要实际业务实现，列为对应需求的建设项，不在知识适配任务中擅自开发SDK或上报平台。

## 7. 同步与验证

1. 核manifest仅有一份有效上报facts和对应规约入口；路径存在，编号唯一，无退役条目仍被当前消费者引用。已有目标知识不能被Demo样例覆盖。
2. 规约条目增删/改义时，检查当前在途需求的knowledge-use和contracts引用。仅同步本次授权的活跃消费者；历史已完成报告保持原样，不批量改写所有feature或保留永久旧号别名。
3. 使用目标工程现成知识自检/读取入口验证frontmatter、分面、条目派生、有效引用和已有投影。命令从目标仓现行入口说明取得，不要求为了验证知识跑完整需求流水线。
4. 用该仓一个真实业务做语义走查：材料要求什么、自动覆盖什么、哪些点位需要新增、身份/字段如何对应、结果从哪里获得、谁消费。判定能否指导实现，不以关键词齐全或字段数量作完成证据。
5. 适用时检查无独立BI、有明确BI且仅带业务维度、允许复用内外码、无码外码/无耗时、步骤成功、可恢复子失败、主动取消和旧码复用等合法输入。不存在的业务分支不强造；源码中的实际异常路径优先。

结构自检不证明代码执行正确。此次只交付知识适配，真实业务代码、编译、原始事件捕获在后续获授权的正常需求流程中验证；未执行就列未验证。

## 8. 交回内容与完成条件

交回两份文件及其diff；如修改激活或活跃引用，逐项列明。另给一份简短记录：关键事实的源码/协议位置、目标规则与样例的差异、条目强度依据、检查结果、需负责人确认的问题和未验证项。

完成条件：两份知识各负其责、没有重复定义或猜测充当事实；目标模型能据此形成可实施设计；当前消费者取得新内容；框架与适配器保持通用。若某字段语义仍未知，只将该项标未确认，不能把整体宣称成“全部验证通过”。

## 9. 需求系统对接的独立说明

本指南只指导两份上报知识的维护。需求系统对接是另一项任务，见[内网需求系统对接适配指南](内网需求系统对接适配指南.md)，按真实入口与模块职责实施，不在 adapt 中定制业务逻辑。
