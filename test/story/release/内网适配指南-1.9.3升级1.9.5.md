# 内网适配指南：Story Extension 1.9.3 升级 1.9.5

读者：维护内网业务仓的模型与工程负责人。本指南可以单独带进内网使用。

Demo 包里的知识与对接脚本是**样例**：它们示范职责、信息组织和对外合同，类名、编码、接口参数都是 Demo 自己的。内网照本指南，按真实代码、真实上报协议和真实需求系统写自己的那一份。

## 一、升级做什么

| 块 | 谁做 | 做什么 | 完成条件 |
|---|---|---|---|
| 机制面 | `/story adapt` 自动 | 换掉扩展目录下 `knowledge/` 与 `adapters/` 以外的全部机制文件（含 `core/` 脚本），合成 `manifest.yaml`，刷新入口文件标记区与 `.gitignore` | `--check` 全过 |
| 知识 | 内网维护模型 | 新建 `knowledge/facts/reporting.md`，登记进 `manifest.yaml > provides.knowledge` | 第二节的走查能据它写出 Spec 9.4 与 Plan 埋点的实际值 |
| 对接脚本 | 内网维护模型 | `skills/story/scripts/adapters/story.js` 及其内部模块按第三节实现 | 第三节五项验证通过 |

机制面的命令（在 1.9.5 包仓执行，目标是内网工程根；前置：目标是 git 仓根、要覆盖的路径没有未提交改动）：

```
node <包>/skills/story-adaptation/scripts/adapt-scan.mjs --apply --target <内网工程根> --package <包根>
node <包>/skills/story-adaptation/scripts/adapt-scan.mjs --check --target <内网工程根> --package <包根>
```

adapt 不读写 `knowledge/`，Demo 来源时也不碰 `adapters/`，`provides.knowledge` 由目标自己维护——所以后两块由内网做。路径都相对 `framework.config.json > paths.extension_dir`（缺省 `doc/extensions`）。

## 二、知识：新建 `facts/reporting.md`

### 1.9.5 谁用它

| 消费方 | 用它做什么 |
|---|---|
| Spec §9.4 埋点 | 按指标写统计点：已有自动采集覆盖的不重复列；每个统计点写实际会发生的结果、本端何时得知 |
| Plan 埋点小节（`hooks/plan/author.mjs` 任务包会把激活的 facts 入口列给作者） | 对每个统计点给出身份、编码、分类、外码来源的实际值或候选值，写明登记位置与分配依据 |
| spec / plan 审查 | 把 Spec 统计点、Plan 埋点行与这份知识并列，核值是否落地、是否按项目规则分配 |

所以它要回答两类问题：**项目已经有什么**（渠道、自动采集、身份与字段怎么映射），和**新东西怎么定**（新流程、步骤、编码按什么规则取号，登记在哪）。

### 按面写

格式按内网 `knowledge/facts/README.md` 的现行协议（frontmatter、一节一面、每面 `confirmed`）。Demo 样例 `facts/reporting.md` 分六面，内网按下表逐面取证；很短的面可以合并。

| 面 | 要给出的 | 内网到哪里取证 |
|---|---|---|
| 渠道与已有能力 | VOC / Chart / BI 各服务什么目的、入口是什么；页面进入、点击等**自动采集覆盖什么、接入条件**；上报失败对业务的影响 | 上报门面与 Builder、公共导出、自动埋点的注册与开关、实际页面接入 |
| 身份与 SDK 映射 | 业务身份（模板 / 流程 / 步骤）对应哪些参数、常量和平台字段；各渠道身份的异同 | 身份常量定义、序列化与接收协议 |
| 结果与字段映射 | 内码的段数、各段语义、前导零；结果分类各值的含义（步骤成功与全流程成功的区别）；外码从哪来；耗时单位 | 码表、结果枚举，以及一条正常、一条失败或取消的实际调用 |
| 业务扩展字段 | 内网实际存在的扩展字段、类型、含义与取值；含义未定的列成具体待核问题 | setter 与调用处赋值、业务参数规范 |
| 登记与复用 | **登记文件在哪**；新流程号、步骤号、内码各段**按什么规则取下一个**；同语义按已有定义复用 | 内网现有的编号登记与分配惯例、负责人约定 |
| 使用参考 | 先从一个指标反推要哪些结果，再把一个统计点连成 Plan 深度的一行：身份、内码、外码来源、责任方法、去重键、耗时起止；附一段最短的调用示例 | 内网一条真实业务的上报调用 |

「登记与复用」与「使用参考」两面决定 Plan 能不能写出实际值：只有协议定义、没有分配规则时，Plan 只能写「按知识首次登记」，审查会判没落地。

### 取证与写法

- **查定义，也查实际调用**：抽一条正常路径、一条失败或取消路径，需要时加重复回调或重试。定义与调用不一致时写明差异，不任选一边当规范。
- **能力事实由代码证明，业务语义由协议或负责人确认**。查不到实现不等于没有这项能力：先核依赖库与已有声明；负责人已明确的能力照录并写明适用工程；拿不到的细节标「未确认」，字段名已核、含义未定的分开标。
- **协议定义只在这一份里写**；义务由规约承担，这里不写「必须」。不写维护过程和取证过程——取证记录单独交回。
- 已有同义的上报知识时，先定唯一来源，不另建第二份。

### 登记与验证

1. `manifest.yaml > provides.knowledge` 加 `knowledge/facts/reporting.md`，路径存在、只有一份上报 facts。
2. 用内网现成的知识自检入口核 frontmatter、分面与引用。
3. 拿内网一个真实业务走一遍：材料要求什么指标；自动采集已覆盖什么；需要哪些统计点、每个点的结果本端从哪取得；身份、内码、分类、外码怎么对应；新编码按什么规则取、登记在哪。能据此写出 Spec 9.4 一个指标 H4 与 Plan 埋点一行实际值，才算完成；关键词齐全不算。

## 三、对接脚本：`adapters/story.js` 及内部模块

### 目标形状

- **两个公共入口**：`story.js`（需求系统命令）与 `token.js`（取 token，stdout 即 token）。入口背后按内网实际拆多个内部模块，内部模块不是公共命令。
- **`story.js` 的命令**：`init`、`fetch`、`archive`、`restore`。无命令或命令不认识只给用法并非零退出。`/story help` 是流程层帮助，与对接层无关。
- **需求来源**：只有 **AR 开头**的编号走需求系统；其余（ISSUE、DTS、自定义名、local 开头等）都是本地需求，四条命令在取 token、访问系统之前就失败。AR 单查无此单、缺 token、系统故障都如实报失败，不降级成本地。判断用内网已有的单号规范化方式。
- **输出**：日志走 stderr；stdout 最后一行是单行 JSON；失败非零退出且 JSON 带 `success: false` 与 `error`。各命令的字段以 Demo `story.js` 顶部 docstring 为合同。

### 内网模块怎么对应

按内网真实模块落位（下表是内网已知的模块职责，动手前先核真实分派与调用链）：

| 模块 | 职责 |
|---|---|
| `story.js` | 唯一入口，分派四条命令 |
| `fetch.js` | `init` 的实现：首次取 AR、SR、RR 正文与 detail |
| `fetch-upstream.js`（新建） | `fetch` 的实现：只读取回当前上游与评审回稿 |
| `archive.js` / `restore.js` | 归档与回退系统正文 |
| `mcp.js`、`token.js` | MCP 调用与 token，各命令共用 |
| `post-process.js`、`html-to-md.js`、`download-images.js`、`image-map.js` | 富文本转 Markdown、图片下载与映射；`fetch` 取回的正文照同一条链处理 |
| `dirs.js` | 目录与路径规则 |

`review.js` 与入口里的 `review`、`help` 分派删掉，其中仍被别处用到的能力移回它真正的责任模块。

### `fetch` 的合同

```
node story.js fetch <AR单号> <mcp-token> --project-root <工程根> --out <本单 inbox>
```

- **只读取材**：取回这张单现在关联的 AR / SR / RR 正文与评审回稿，一个业务文件都不写（不碰 `AR/design.md`、`AR/review.md`、Spec、Story、Plan）。
- **写到哪**：三份正文写进 `--out`，与本地对应文件逐字相同的不落盘；评审回稿写 `AR/story-src/review-feedback.md`；取材回执写 `AR/story-src/fetched.json`（`--project-root` 定位本单目录）。回执不能写进 inbox，否则会被当成一份材料导入。
- **四态**：每份材料的 `status` 为 `fetched`（取到）/ `same`（与本地相同）/ `absent`（系统上没有，常态）/ `failed`（读取故障）。读取故障如实记 `failed`，不写占位件、不报成功。
- `--out` 必填，没有默认落点。

`/story update` 的流程：core 的 `update --action status` 返回本单的 `paths`（`project_root`、`inbox` 等绝对路径），模型用它调 `fetch`，core 再读回执。对接层不调用 core 脚本，日志与输出也不提示 core 的下一步命令。

### 参考 Demo，按真实系统实现

Demo 的 `story.js` 用本地目录模拟需求系统，只承载 md，只示范 CLI 合同与写盘落点。内网实现：

- 用真实 MCP 接口取单据与评审回稿，具体接口、参数、分页与鉴权从内网代码与接口文档取证；
- 正文里有富文本与图片时走内网已有的转换与下载链，输出落到 `--out`，并核后处理只写允许的位置；
- 复用内网已有的 MCP、token、目录与后处理模块，不另写一套。

### 验证

1. 分派：`init` → `fetch.js`，`fetch` → `fetch-upstream.js`，`archive` / `restore` 各自原模块；`review`、`help` 不再是命令。
2. 来源：AR 单正常访问系统；AR 查无此单、鉴权失败报失败；非 AR 至少测 ISSUE、自定义名、local 开头三种，都不取 token、不发请求。
3. 四态回执能被 `/story update` 正确读到，`failed` 不被当成无变化。
4. 富文本与图片经后处理后正文与图片引用可用；只写 inbox 与 `AR/story-src/` 下的两个文件。
5. `init`、`archive`、`restore` 的既有行为保持；没有线上写入授权时，`archive` / `restore` 在测试环境核。

## 四、交回

三类结果分开记，不互相代替：

| 结果 | 证据 |
|---|---|
| 机制面 | `adapt-scan --check` 输出 |
| 知识 | `reporting.md` 与 `manifest.yaml` 的 diff；关键事实的源码或协议位置；真实业务走查记录 |
| 对接脚本 | diff；命令到模块的映射；五项验证的实际运行结果 |

另列未验证项与需要负责人确认的问题。某项没做完就单列为未适配，比如 `fetch` 没实现时写明 `/story update` 取材未适配，不笼统宣称升级完成。
