# 内网适配指南：Story Extension 1.9.3 升级 1.9.5

读者：维护内网业务仓的模型与工程负责人。本指南可以单独带进内网使用。

Demo 包里的知识与对接脚本是**样例**：知识示范职责与信息组织；对接脚本的文件划分和导出签名与内网一致，内部用本地目录模拟需求系统。内网照本指南，按真实代码、真实上报协议和真实需求系统写自己的那一份。

## 一、升级做什么

| 块 | 谁做 | 做什么 | 完成条件 |
|---|---|---|---|
| 机制面 | `/story adapt` 自动 | 换掉扩展目录下 `knowledge/` 与 `adapters/` 以外的全部机制文件（含 `core/` 脚本），合成 `manifest.yaml`，刷新入口文件标记区与 `.gitignore`；core 覆盖本地文件前的备份随之落在需求目录的 `.backups/local/` | `--check` 全过 |
| 知识 | 内网维护模型 | 新建 `knowledge/facts/reporting.md`，登记进 `manifest.yaml > provides.knowledge` | 第二节的走查能据它写出 Spec 9.4 与 Plan 埋点的实际值 |
| 对接脚本 | 内网维护模型 | `skills/story/scripts/adapters/` 下改 `story.js`、`fetch.js`、`archive.js`、`restore.js`、`dirs.js`，删 `review.js`（第三节） | 第三节验证通过 |

机制面的命令（在 1.9.5 包仓执行，目标是内网工程根；前置：目标是 git 仓根、要覆盖的路径没有未提交改动）：

```
node <包>/skills/story-adaptation/scripts/adapt-scan.mjs --apply --target <内网工程根> --package <包根>
node <包>/skills/story-adaptation/scripts/adapt-scan.mjs --check --target <内网工程根> --package <包根>
```

adapt 不读写 `knowledge/`，Demo 来源时也不碰 `adapters/`，`provides.knowledge` 由目标自己维护——所以后两块由内网做。路径都相对 `framework.config.json > paths.extension_dir`（缺省 `doc/extensions`）。

## 二、知识：新建 `facts/reporting.md`

### 1.9.5 谁用它

| 消费方 | 用它做什么 |
|---|---|
| Spec §9.4 埋点 | 按指标写统计点：已有自动采集覆盖的不重复列；每个统计点写实际会发生的结果、本端何时得知 |
| Plan 埋点小节（`hooks/plan/author.mjs` 任务包会把激活的 facts 入口列给作者） | 对每个统计点给出身份、编码、分类、外码来源的实际值或候选值，写明登记位置与分配依据 |
| spec / plan 审查 | 把 Spec 统计点、Plan 埋点行与这份知识并列，核值是否落地、是否按项目规则分配 |

所以它要回答两类问题：**项目已经有什么**（渠道、自动采集、身份与字段怎么映射），和**新东西怎么定**（新流程、步骤、编码按什么规则取号，登记在哪）。

### 按面写

格式按内网 `knowledge/facts/README.md` 的现行协议（frontmatter、一节一面、每面 `confirmed`）。Demo 样例 `facts/reporting.md` 分六面，内网按下表逐面取证；很短的面可以合并。

| 面 | 要给出的 | 内网到哪里取证 |
|---|---|---|
| 渠道与已有能力 | VOC / Chart / BI 各服务什么目的、入口是什么；页面进入、点击等**自动采集覆盖什么、接入条件**；上报失败对业务的影响 | 上报门面与 Builder、公共导出、自动埋点的注册与开关、实际页面接入 |
| 身份与 SDK 映射 | 业务身份（模板 / 流程 / 步骤）对应哪些参数、常量和平台字段；各渠道身份的异同 | 身份常量定义、序列化与接收协议 |
| 结果与字段映射 | 内码的段数、各段语义、前导零；结果分类各值的含义（步骤成功与全流程成功的区别）；外码从哪来；耗时单位 | 码表、结果枚举，以及一条正常、一条失败或取消的实际调用 |
| 业务扩展字段 | 内网实际存在的扩展字段、类型、含义与取值；含义未定的列成具体待核问题 | setter 与调用处赋值、业务参数规范 |
| 登记与复用 | **登记文件在哪**；新流程号、步骤号、内码各段**按什么规则取下一个**；同语义按已有定义复用 | 内网现有的编号登记与分配惯例、负责人约定 |
| 使用参考 | 先从一个指标反推要哪些结果，再把一个统计点连成 Plan 深度的一行：身份、内码、外码来源、责任方法、去重键、耗时起止；附一段最短的调用示例 | 内网一条真实业务的上报调用 |

「登记与复用」与「使用参考」两面决定 Plan 能不能写出实际值：只有协议定义、没有分配规则时，Plan 只能写「按知识首次登记」，审查会判没落地。

### 取证与写法

- **查定义，也查实际调用**：抽一条正常路径、一条失败或取消路径，需要时加重复回调或重试。定义与调用不一致时写明差异，不任选一边当规范。
- **能力事实由代码证明，业务语义由协议或负责人确认**。查不到实现不等于没有这项能力：先核依赖库与已有声明；负责人已明确的能力照录并写明适用工程；拿不到的细节标「未确认」，字段名已核、含义未定的分开标。
- **协议定义只在这一份里写**；义务由规约承担，这里不写「必须」。不写维护过程和取证过程——取证记录单独交回。
- 已有同义的上报知识时，先定唯一来源，不另建第二份。

### 登记与验证

1. `manifest.yaml > provides.knowledge` 加 `knowledge/facts/reporting.md`，路径存在、只有一份上报 facts。
2. 用内网现成的知识自检入口核 frontmatter、分面与引用。
3. 拿内网一个真实业务走一遍：材料要求什么指标；自动采集已覆盖什么；需要哪些统计点、每个点的结果本端从哪取得；身份、内码、分类、外码怎么对应；新编码按什么规则取、登记在哪。能据此写出 Spec 9.4 一个指标 H4 与 Plan 埋点一行实际值，才算完成；关键词齐全不算。

## 三、对接脚本：`adapters/`

### 文件与 Demo 一一对应

Demo 的对接层与内网同样分层：入口 `story.js` 分发，一个命令一个文件，命令文件只经 `mcp.js` 访问需求系统，路径统一由 `dirs.js` 给出。文件名与导出签名相同，逐文件对照 Demo 改即可；Demo 的 `mcp.js` 读写本地目录，内网保留真实的 MCP 调用。

| 文件 | 1.9.5 的职责与导出 | 内网要做的 |
|---|---|---|
| `story.js` | 命令 `init` / `archive` / `restore` / `fetch`；参数 `<命令> <AR单号> <mcp-token> [--project-root <abs>] [--out <本单 inbox>]` | 分派表去掉 `review`、加 `fetch`（调 `fetchUpstream`）；`fetch` 缺 `--out` 按参数错处理 |
| `fetch.js` | `fetchOne(reqNo, dirType, mcpToken, backupTimestamp, baseReqNo?) → { parentNo }`；**新增** `fetchUpstream(reqNo, mcpToken, { outDir })`；取单据详情与正文的函数导出供两者共用 | `fetchOne` 不变；加 `fetchUpstream`，复用现有取单据、取正文与 `post-process` 链 |
| `archive.js` | `archiveOne(reqNo, mcpToken, skipBackup?, contentOverride?) → { archived, backupPath, verified, reviewArchived }` | 覆盖系统正文前的备份写到**需求目录** `.backups/cloud/design-<时刻>.md`，`backupPath` 回相对需求目录的路径 |
| `restore.js` | `restoreOne(reqNo, mcpToken) → { restored, verified }` | 从需求目录 `.backups/cloud/` 取最新一份，经 `archiveOne(reqNo, token, true, 内容)` 写回系统 |
| `dirs.js` | 需求目录、`.backups/cloud/` 路径；认 `--project-root` | 加 `.backups/cloud/` 的路径函数；工程根认 `--project-root`（`fetch` 的回执按它定位） |
| `review.js` | — | 删除；它用到的 `post-process` 现由 `fetchUpstream` 调用 |
| `mcp.js`、`token.js`、`post-process.js`、`html-to-md.js`、`download-images.js`、`image-map.js`、`siblings.js`、`system-ca-bootstrap.js` | 不变 | 照旧 |

需求目录下的备份统一在 `.backups/`：`cloud/` 是需求系统拉取内容的备份，由对接层写，restore 据它恢复系统数据；`local/` 是本地文档的备份，由 core 写。

### `story.js` 的入口规则

- **只有 AR 开头的编号走需求系统**；其余（ISSUE、DTS、自定义名、local 开头等）是本地需求，四条命令都在访问系统之前失败。判断用内网已有的单号规范化方式。
- **两层错误**：参数错（缺命令、缺单号、缺 token、非 AR、`fetch` 缺 `--out`）写 stderr 并 `exit(1)`，不写 stdout JSON；命令实现抛异常由顶层 catch 写 `{ mode, reqNo, success: false, error }` 并 `exit(1)`。
- 成功时 stdout 最后一行是 `{ mode, reqNo, success: true, ...命令字段 }`，日志走 stderr。

### `fetchUpstream`：只读取材

- 取回这张单现在关联的 AR / SR / RR 正文与评审回稿，**一个业务文件都不写**（不碰 `AR/design.md`、`AR/review.md`、Spec、Story、Plan）。
- 三份正文写进 `outDir`（本单 inbox），文件名 `AR-design.md` / `SR-design.md` / `RR-prd.md`，与本地对应文件逐字相同的不落盘；评审回稿写 `AR/story-src/review-feedback.md`；回执写 `AR/story-src/fetched.json`，不进 inbox。
- 回执与返回值逐份记 `name`、`label`、`ticket`、`status`、`digest`、`origin`、`bytes`；`status` 四态：`fetched`（取到）/ `same`（与本地相同）/ `absent`（系统上没有，常态）/ `failed`（读取故障）。有 `failed` 时 `success: false`、非零退出。
- 返回 `{ out, fetched, failed, items }`，入口拼成 stdout JSON。

`/story update` 的流程：core 的 `update --action status` 返回本单 `paths`（`project_root`、`inbox` 等绝对路径），模型用它执行 `story.js fetch <AR> <token> --project-root <project_root> --out <inbox>`，core 再读回执。core 不渲染对接命令，也不调用对接层；对接层不调用 core，也不提示 core 的命令。

### 参考 Demo，按真实系统实现

Demo 的 `mcp.js` 用本地目录模拟需求系统、只承载 md，方法名是替身自定的。内网：

- `fetchUpstream` 用真实 MCP 接口取正文与评审回稿，接口、参数与鉴权沿用 `fetchOne` 已在用的那一套；
- 正文有富文本与图片时走现有 `post-process` 链，输出落到 `outDir`，并核后处理只写允许的位置；
- 不另写 MCP、token、目录与后处理能力。

### 验证

1. 分派：`init` → `fetchOne` 逐级，`fetch` → `fetchUpstream`，`archive` / `restore` 各自原模块；`review` 不再是命令，`review.js` 已删。
2. 来源：AR 单正常访问系统；AR 查无此单、鉴权失败走顶层 catch 报失败；非 AR 至少测 ISSUE、自定义名、local 开头三种，都不发请求、不写 stdout JSON。
3. `fetch` 四态回执能被 `/story update` 正确读到，`failed` 不被当成无变化；只写 inbox 与 `AR/story-src/` 下两个文件。
4. `archive` 后需求目录 `.backups/cloud/` 多一份归档前的系统正文；`restore` 用它恢复系统正文，本地业务文件不动。没有线上写入授权时在测试环境核。
5. `init` 的既有行为保持。

## 四、交回

三类结果分开记，不互相代替：

| 结果 | 证据 |
|---|---|
| 机制面 | `adapt-scan --check` 输出 |
| 知识 | `reporting.md` 与 `manifest.yaml` 的 diff；关键事实的源码或协议位置；真实业务走查记录 |
| 对接脚本 | diff；命令到模块的映射；第三节验证的实际运行结果 |

另列未验证项与需要负责人确认的问题。某项没做完就单列为未适配，比如 `fetch` 没实现时写明 `/story update` 取材未适配，不笼统宣称升级完成。
