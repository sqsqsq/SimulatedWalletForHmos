# 内网适配指南：Story Extension 1.9.3 升级 1.9.6

读者：维护内网 wallet 业务仓的模型与工程负责人。本指南可以单独带进内网使用。

Demo 包里的知识与对接脚本都是**样例**：知识示范怎样写给模型用，对接脚本的文件划分与导出签名与内网一致、内部用本地目录模拟需求系统。内网照本指南，按真实代码、真实上报协议与真实需求系统写自己的那一份。

## 一、升级做什么

| 块 | 谁做 | 做什么 | 完成条件 |
|---|---|---|---|
| 机制面 | `/story adapt` 自动 | 换掉扩展目录下 `knowledge/` 与 `adapters/` 以外的机制文件，合成 `manifest.yaml`，刷新入口文件标记区与 `.gitignore` | `--check` 全过 |
| 知识 | 内网维护模型 | 按第二节整理已有知识、新建埋点知识 | 第二节的只读检查 PASS，走查写得出 Spec §9.4 与 Plan 埋点的实际值 |
| 对接脚本 | 内网维护模型 | 按第三节改 `skills/story/scripts/adapters/` | 第三节验证通过 |

机制面命令（在 1.9.6 包仓执行，目标是内网工程根；前置：目标是 git 仓根，要覆盖的路径没有未提交改动）：

```
node <包>/skills/story-adaptation/scripts/adapt-scan.mjs --apply --target <内网工程根> --package <包根>
node <包>/skills/story-adaptation/scripts/adapt-scan.mjs --check --target <内网工程根> --package <包根>
```

路径都相对 `framework.config.json > paths.extension_dir`（缺省 `doc/extensions`）。装完先读包里两份说明：`skills/story/reference/knowledge/protocol.md`（三类知识怎样描述自己、怎样写给模型用）与 `skills/story-adaptation/reference/knowledge-adaptation.md`（写知识的方法）。

## 二、知识

1.9.6 的机制只读 `manifest.yaml > provides.knowledge` 登记的文件，按每份文件 frontmatter 的 `kind` 与 `applies_when` 把它交给当前阶段；知识有几份、叫什么、怎么分都由内网定。

### 1. 并掉四份 README

内网 1.9.3 的 `knowledge/README.md` 与 `knowledge/{facts,constraints,design-patterns}/README.md` 是 `kind: index`，1.9.6 加载时会报「kind 不在封闭集合里」。它们讲的通用规则已由 `protocol.md` 承担：把其中内网自己加的说明并入相应知识文件，从 `provides.knowledge` 删去这四项，再删文件。

### 2. 每份知识写清 `applies_when`

任务包与审查按「路径 —— `applies_when`」列出全部知识，读者据此选读；缺 `applies_when` 加载会报。写成「什么情况下读：它回答什么」，例如：

- 部件定位那份：「判断上游内容是否归本部件时：本部件是谁、职责边界、与哪些交互方怎样交互」——初析与 AR 提取靠它；
- 规约：「所有需求：个人数据、权限与对外暴露面的红线」。

### 3. 面标题只写面名

面标题写 `## <面名>`，去掉 `— \`confirmed: …\``。原先标「未确认」的面改写成确定的陈述：已核的写上依据位置，依据在别人手里的写明向谁取得什么。知识使用记录（`spec/knowledge-use.yaml`）按面名引用，不写 `verified`。

### 4. 新建埋点知识

一份 facts，文件名由内网定，按 Demo 的 `knowledge/facts/event-tracking.md` 分上下篇写：上篇「统计设计」给写统计设计的作者与审查者，下篇（其余三面）给实现、编码、审查与测试；每个面的标题写读者与读完交出什么，上下篇末尾各写完成判断。四面与取证位置：

| 面 | 回答什么 | 内网到哪取证 |
|---|---|---|
| 统计设计 | 指标、流程、事件分类与业务目标的区分；各类上报的目的与现有采集能力（已实现的、只是规范的分开）；应用步骤、边界与一个指标形状的例子 | 上报门面与导出、自动采集的注册与开关、需求规范与负责人约定 |
| 上报实现 | 尝试持有者、结算方法与登记文件三个角色；每个结果的身份与具体候选取值；调用方式与一段结算骨架 | 身份常量、码表与结果枚举，一条正常与一条失败或异常的真实调用 |
| 编号分配与复用 | 已有定义在哪；新身份与编码在哪个父范围取候选、怎样核冲突、登记在哪 | 现有常量与登记文件、分配惯例、负责人约定 |
| 业务扩展字段 | 内网额外提供的字段；各字段的业务含义向谁取得 | 字段写入接口、业务参数规范 |

写法按 `protocol.md`：正向陈述有什么、怎么用；同一事实只写一处，嵌进用到它的那一步；例子一个。上报渠道若仍写在内网别的 facts 里，挪进这一份，原处退出。

### 5. 按共同写法审视其余知识

对照 `protocol.md` 第三至六节看一遍：已有实现类知识写「用哪个、在哪、怎么用」；编码规范与架构配置已写的不再写；设计模式上篇写应用步骤、下篇写约定与完成判断，不重复。内容要改的改，结构已合适的不动。

### 6. 登记与检查

新增、改名、拆分只改知识文件与 `provides.knowledge`。改完在内网工程根执行方法页「确认与交回」一步给出的只读检查（交给 `node --input-type=module`），PASS 后拿一个真实业务走查：初析能据部件定位知识判归属；能据埋点知识写出 Spec §9.4 一个指标与 Plan 埋点一种结果的实际值或候选。

## 三、对接脚本：`adapters/`

### 文件与 Demo 一一对应

入口 `story.js` 分发，一个命令一个文件，命令文件只经 `mcp.js` 访问需求系统，路径统一由 `dirs.js` 给出。文件名与导出签名与 Demo 相同；Demo 的 `mcp.js` 读写本地目录，内网保留真实的 MCP 调用。

| 文件 | 职责与导出 | 内网要做的 |
|---|---|---|
| `story.js` | 命令 `init` / `archive` / `restore` / `fetch`；参数 `<命令> <AR单号> <mcp-token> [--project-root <abs>] [--out <本单 inbox>]` | 分派表去掉 `review`、加 `fetch`（调 `fetchUpstream`）；`fetch` 缺 `--out` 按参数错处理 |
| `fetch.js` | `fetchOne(reqNo, dirType, mcpToken, backupTimestamp, baseReqNo?) → { parentNo }`；`fetchUpstream(reqNo, mcpToken, { outDir })`；取单据详情与正文的函数导出供两者共用 | `fetchOne` 保持；加 `fetchUpstream`，复用现有取单据、取正文与 `post-process` 链 |
| `archive.js` | `archiveOne(reqNo, mcpToken, skipBackup?, contentOverride?) → { archived, backupPath, verified, reviewArchived }` | 覆盖系统正文前把它备份到需求目录 `.backups/cloud/design-<时刻>.md`，`backupPath` 回相对需求目录的路径 |
| `restore.js` | `restoreOne(reqNo, mcpToken) → { restored, verified }` | 取需求目录 `.backups/cloud/` 最新一份，经 `archiveOne(reqNo, token, true, 内容)` 写回系统 |
| `dirs.js` | 需求目录与 `.backups/cloud/` 路径；认 `--project-root` | 加 `.backups/cloud/` 的路径函数；工程根认 `--project-root` |
| `review.js` | — | 删除；它用到的 `post-process` 由 `fetchUpstream` 调用 |
| `mcp.js`、`token.js`、`post-process.js`、`html-to-md.js`、`download-images.js`、`image-map.js`、`siblings.js`、`system-ca-bootstrap.js` | 保持 | 照旧 |

需求目录下的备份都在 `.backups/`：`cloud/` 是需求系统内容的备份，由对接层写，restore 据它恢复系统数据；`local/` 是本地文档的备份，由 core 写。

### `story.js` 的入口规则

- **只有 AR 开头的编号走需求系统**；其余（ISSUE、DTS、自定义名、local 开头等）是本地需求，四条命令都在访问系统之前失败。判断用内网已有的单号规范化方式。
- **两层错误**：参数错（缺命令、缺单号、缺 token、非 AR、`fetch` 缺 `--out`）写 stderr 并 `exit(1)`，stdout 不输出 JSON；命令实现抛异常由顶层 catch 写 `{ mode, reqNo, success: false, error }` 并 `exit(1)`。
- 成功时 stdout 最后一行是 `{ mode, reqNo, success: true, ...命令字段 }`，日志走 stderr。

### `fetchUpstream`：只读取材

- 取回这张单现在关联的 AR / SR / RR 正文与评审回稿；业务文件（`AR/design.md`、`AR/review.md`、Spec、Story、Plan）保持原样。
- 三份正文写进 `outDir`（本单 inbox），文件名 `AR-design.md` / `SR-design.md` / `RR-prd.md`，与本地对应文件逐字相同的不落盘；评审回稿写 `AR/story-src/review-feedback.md`；回执写 `AR/story-src/fetched.json`。
- 回执与返回值逐份记 `name`、`label`、`ticket`、`status`、`digest`、`origin`、`bytes`；`status` 四态：`fetched`（取到）/ `same`（与本地相同）/ `absent`（系统上没有，常态）/ `failed`（读取故障）。有 `failed` 时 `success: false`、非零退出。
- 返回 `{ out, fetched, failed, items }`，入口拼成 stdout JSON。

`/story update` 时，core 的 `update --action status` 返回本单 `paths`（`project_root`、`inbox` 等绝对路径），模型用它执行 `story.js fetch <AR> <token> --project-root <project_root> --out <inbox>`，core 再读回执。core 与对接层互不调用。

`fetchUpstream` 用真实 MCP 接口取正文与评审回稿，接口、参数与鉴权沿用 `fetchOne` 那一套；正文有富文本与图片时走现有 `post-process` 链，输出落到 `outDir`。

### 验证

1. 分派：`init` → `fetchOne` 逐级，`fetch` → `fetchUpstream`，`archive` / `restore` 各自原模块；`review.js` 已删。
2. 来源：AR 单正常访问系统；AR 查无此单、鉴权失败走顶层 catch 报失败；非 AR 至少测 ISSUE、自定义名、local 开头三种，都不发请求、stdout 无 JSON。
3. `fetch` 四态回执能被 `/story update` 正确读到，`failed` 报为失败；写入范围只有 inbox 与 `AR/story-src/` 下两个文件。
4. `archive` 后需求目录 `.backups/cloud/` 多一份归档前的系统正文；`restore` 用它恢复系统正文，本地业务文件保持原样。没有线上写入授权时在测试环境核。
5. `init` 的既有行为保持。

## 四、交回

三类结果分开记：

| 结果 | 证据 |
|---|---|
| 机制面 | `adapt-scan --check` 输出 |
| 知识 | 知识文件与 `manifest.yaml` 的 diff；关键事实的源码或协议位置；只读检查输出；真实业务走查记录 |
| 对接脚本 | diff；命令到模块的映射；第三节验证的实际运行结果 |

另列未验证项与需要负责人确认的问题。没做完的单列为未适配（例如 `fetch` 没实现时写明 `/story update` 取材未适配）。
