# AR90006 交通卡自动充值（钱包端）— 开发需求（AR）

## 1 简介

### 1.1 需求介绍

交通卡余额用尽只有在闸机前才会被发现，用户被迫在人流中完成充值，是当前交通卡投诉量最高的场景。本需求让用户一次签约之后，余额（以服务端记录为准）低于自己设定的门限时由系统自动完成充值，把「想起来充值」这件事从用户身上移走。

判定与扣款全部由服务端完成，钱包端承担签约入口、签约交互、状态展示与记录呈现，不存在「发起自动充值」的端侧动作。目标：签约用户的闸机余额不足发生率下降到万分之五以下；签约转化率不低于交通卡月活的 8%。

### 1.2 本 AR 范围与拆分说明

**本 AR 承载全部需求，无拆分**（同 SR 关联 AR 清单为空）。

本 AR 范围 = 交通卡自动充值（钱包端）的入口、签约、管理与记录展示：交通卡详情页「自动充值」入口、签约页（门限/面额单选、免密协议勾选）、策略查询、免密验证、创建/修改/关闭签约、签约状态与自动充值记录展示、管理页（含停用状态与失败原因）、本件缓存与端侧事件记录。范围经第二级范围关卡由人选定为整体承载。

## 2 需求分析

### 2.1 场景与功能点

| # | 功能点 | 场景 | 交互方类别 |
|---|---|---|---|
| F1 | 详情页「自动充值」入口 | 未实名用户可见入口、点进被引导实名（AC-R1 按情形表口径）；已签约用户直进管理页；开关关闭对已签约用户不隐藏 | 服务器接口 / 账号能力 |
| F2 | 签约页 | 门限四档(5/10/20/30 元)、面额三档(20/50/100 元)单选；协议勾选后「开启」才可点击；协议文案写明单日最多充值 200 元 | 服务器接口 |
| F3 | 策略状态查询 `getAutoTopupPolicy` | 返回可签约性、门限档位、面额档位、单日限额与协议文案；不可签约不拉起免密协议 | 服务器接口 |
| F4 | 免密签约验证 | 用户当场确认免密授权；面额与免密单笔额度同步；失败/取消留在签约页并保留已选门限面额；实名引导后可回来接着签 | 服务器接口 / 其他手机应用（支付） |
| F5 | 创建签约 `createAutoTopupContract` | 收账号、卡片、agreementNo、门限与面额；同卡已有生效签约返回既有 contractNo（转管理页） | 服务器接口 |
| F6 | 签约状态查询 `getAutoTopupStatus` | 返回签约状态、当前门限与面额、最近记录、连续失败次数与停用状态 | 服务器接口 |
| F7 | 管理页 | 顶部签约状态（含停用横幅与失败原因）；最近自动充值记录、失败记录展示失败原因、卡号按现有规则脱敏 | 服务器接口 |
| F8 | 修改签约 `updateAutoTopupContract` | 修改门限或面额，原签约关系不断、不需解约重签；只改门限不动面额不需重新验证 | 服务器接口 |
| F9 | 关闭自动充值 `cancelAutoTopupContract` | 解除后不回滚进行中的订单、不撤销已完成订单 | 服务器接口 |
| F10 | 本件缓存 `wallet_auto_topup_contract` | 缓存 contractNo、门限、面额与状态，仅免网展示；按账号隔离、退出登录清除、不参与备份恢复；缓存缺失以云侧查询为准 | 手机系统接口（本地存储） |
| F11 | 端侧事件记录 | 只记录去标识账号、卡片类型、阶段与结果分类，不记录卡号、金额明细或支付参数 | 服务器接口 |

### 2.2 验收意图

| 编号 | 场景 | 预期 |
|---|---|---|
| AC-R1 | 未实名用户 | 入口可见，点进去被引导去实名；实名完成后回到签约页、此前选择仍在，可继续签约（口径按会议修正：入口能看到） |
| AC-R2 | 签约后自动充值 | 余额低于门限时用户不做任何操作即可完成充值，并能在记录里看到这笔 |
| AC-R3 | 连续失败停用 | 扣款连续失败三次后自动停用，用户打开管理页能看到停用状态与失败原因 |
| AC-R4 | 功能开关关闭 | 新用户看不到签约入口；已签约用户仍能看到入口进管理页，自动充值照常发生 |
| AC-R5 | 记录展示 | 充值记录中的卡号按现有规则脱敏展示 |
| AC-R6 | 修改与关闭 | 签约后可修改门限面额并按新值生效；关闭后不再触发自动充值 |
| AC-R7 | 验证取消后重试 | 用户在支付验证界面取消，回到签约页时刚才选的门限与面额仍在，可直接再次开启 |
| AC-R8 | 实名后续办 | 未实名用户被引导去实名，完成后回到签约页，此前的选择仍在，可继续签约 |
| AC-R9 | 已签约再进入 | 已有生效签约的卡再点入口，进入的是管理页而不是重新签约 |

## 3 SE 方案摘要（本部件相关）

### 3.1 全局方案与部件分工

整体方案：自动充值分签约、触发、扣款、入账与停用五段。判定与扣款全在服务端——触发只能由卡云在余额上报后决定，端侧不监测余额、不存在「发起自动充值」的接口。

| 参与方 | 承担什么 |
|---|---|
| 钱包端（本部件） | 签约入口、签约交互（门限/面额、协议、免密验证拉起）、状态与记录展示、本件缓存、端侧事件；不判断是否该扣款，不保存支付凭据 |
| 账号能力 | 登录与实名结果；未实名不允许签约 |
| 交通卡云（服务端） | 签约关系、触发判定、订单与扣款结论的唯一真源；失败停用决定 |
| 支付部件 | 免密协议与扣款；签约态与单笔额度校验 |
| 运营管理台 | 下发功能开关、门限与面额档位；配置不可用按关闭处理 |

依赖与上线顺序：钱包先后调用策略查询→免密验证→创建签约/修改/关闭签约→状态查询；开关与档位配置与本需求同版本上线；先联调策略与创建签约，再开放状态查询与解约。

### 3.2 本部件方案要点与流程骨架

- 入口判断：`getAutoTopupPolicy` 返回可签约性（未实名不可签约、引导实名；不可签约不拉起免密协议）；已签约场景经 `createAutoTopupContract` 返回既有 `contractNo` 后进管理页 [SR §3/§4]。
- 签约流程骨架：详情页入口 → 签约页选门限面额、勾协议 → 拉起免密验证 → 验证通过带 `agreementNo` 调 `createAutoTopupContract` → 显示已开启（进管理页）。
- 免密授权边界：拿到用户本人验证结果后钱包才调 `createAutoTopupContract`；未拿到（取消/失败）钱包停在签约页，云侧无签约记录，重试即重走验证 [SR §3]。
- 修改与关闭：改门限/面额走 `updateAutoTopupContract`（新增接口，不走解约重签）；关闭走 `cancelAutoTopupContract`（不回滚/不撤销）[会议 T1、SR §3]。
- 失败与恢复：未实名引导实名回来接着签；同卡已有签约返回既有 contractNo 转管理页；中途退出暂存已选门限面额（本账号本卡有效、退出登录清除）；单日达上限当日不触发且不计入失败；连续 3 次失败云侧停用、端侧可见原因；扣款成功写卡未完成时订单保持「充值中」端侧不重试不重复下单；开关关闭只隐藏新签约入口 [SR §4]。
- 数据保护：端侧事件只记录去标识账号、卡片类型、阶段与结果分类；上报失败不改变业务结果 [SR §5]。
