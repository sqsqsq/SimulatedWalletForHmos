# 内容基线：批次 4 判「不丢」的唯一对照物

这三份 story 是批次 1 时代真实实跑产出的，连同它们那一轮的材料一起冻结在这里。
批次 4 要重写 story 的骨架、判据与作业书，**「新写出来的有没有比它少讲」只跟这三份比**
——不跟批次 3 的产物比（那本身是已知劣化的），也不跟上一个子批比（那会让每轮
只需要比上一轮好一点，慢慢滑走）。

## 三份各是什么

每份含 `AR/story.md`（对照物本体）与同轮四份材料：`RR/prd.md`、`SR/design.md`、
`AR/design.md`、`spec/spec.md`。有材料才谈得上「基线里的这个事实来自哪」。

**AR90006 是内容最厚的一份**（17 章、239 表行），用它压「不丢」的上限；
另两份是十章形态，行数适中，用它们看结构。

## 一个值得记下的事实

`AR90004` 与 `ISSUE-410` 的章结构与批次 4 要恢复的十章骨架**几乎逐字一致**：

```
背景 / 术语 / 范围 / 业务方案 / 业务流程 / 功能说明 / 异常与恢复 / 验收 / 交付与上线 / 附录
```

也就是说十章骨架在批次 1 时代真的跑出过完整 story，不是没落过地的假设。
这不构成「十章一定对」的证明——那两份是在当时的机制上写的——但它说明
骨架本身写得出东西，问题出在别处。

## 怎么用

**对照是单向的**：只判「基线有而新 story 无」，不判反向。基线本身有重复、有工程细节
泄漏（那正是批次 4 要治的），把它当满分去对齐会把旧毛病一起抄回来。

具体口径见 `batch-4` 方案 §6：基线 story 作为第五份材料枚举来源单元 → 对新 story 跑
`audit` → 每个基线单元要有落点（机器可核，或 verifier 判「讲清」）；缺失的逐条点名。

## 不要动它

改这里任何一个字节，都等于改了批次 4 全部「不丢」判据的标尺。
指纹由 `tests/test_content_baseline.py` 守着——它变了而冻结清单没更新，
就是有人在悄悄挪标尺。
