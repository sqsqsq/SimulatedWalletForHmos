# AR90004 交通卡紧急挂失恢复 — 开发需求（AR）

## 1 简介

### 1.1 需求介绍

用户遗失实体交通卡后，最关心尽快阻止旧卡继续使用。现有卡包只能展示卡片，用户在账号未验证、
卡片状态冲突或网络中断时只能离开钱包寻找线下渠道，重新进入后也不知道上一轮处理到了哪里。

本需求在钱包内提供一条**可中断后继续的在线紧急挂失路径**：打开挂失页即查询资格并展示冻结影响、
当前卡片状态与数据使用说明；用户确认后提交申请；身份未完成时保留脱敏上下文、走既有身份能力，
回跳后重新核验资格回到确认位置；卡片状态冲突时先刷新云侧状态，再结合已有申请上下文给出
继续、重新确认或转客服；云侧受理后保存申请号摘要并查询一次真实冻结结果。只有云侧明确返回
「已冻结」才展示成功，任何失败阶段都有可读原因、重试入口与安全停留状态。

### 1.2 本 AR 范围与拆分说明

本 SR（SR90004）关联 2 个 AR。本 AR 承载钱包端交通卡紧急挂失的申请、恢复与结果查看
（资格查询、风险确认、身份回跳恢复、冲突处理、创建/复用申请、查询真实冻结结果、上下文保存恢复），
并向兄弟 AR90005 交出 `freezeTicketId` 与最终冻结状态（范围来源：SR90004 分工说明）；
其余归 AR90005（补卡费用支付、制卡进度、领取通知和客服交接）。本 AR 范围内不再切分。

## 3 SE 方案摘要（本部件相关）

### 3.1 全局方案与部件分工

钱包端以云侧资格和申请状态为事实源，把一次挂失处理划为「加载资格、等待风险确认、身份恢复、
冲突恢复、创建或复用申请、确认冻结结果」几个业务阶段；页面根据每一步业务结果决定下一项操作，
需要用户阅读、确认或完成身份时停止自动推进，由新的用户动作继续。资格可用、身份不完整、
状态冲突和已存在申请是不同分支，每条路径都有自己的查询、上下文校验、外部能力调用与失败收敛。

- **本部件（WalletMain）**：组织页面交互与业务路径，保存安全检查点，不绕过身份、不自行认定冻结成功；
- **卡云适配层（本仓）**：模拟本需求所需云侧协议，是资格与冻结结果的唯一事实源，保持幂等；
- **AccountManager**：提供既有登录/实名能力与当前账号范围，失败返回明确结果，不持有挂失申请；
- **AR90005 补卡特性**：承担费用确认、支付恢复、制卡跟踪与客服交接，不复制挂失或改动冻结状态。

上线顺序：先联调资格、创建/复用与冻结结果，收口后开放挂失；AR90005 在拿到有效交接结果后才联调
补卡支付与通知。开关默认关闭，观察错误分类与恢复结果后开放；回退只关闭新入口并保留查询既有
申请的能力，不删除处理中上下文，也不把通知失败解释为冻结失败。

### 3.2 本部件方案要点与流程骨架

| 要点 | 指针 |
|---|---|
| 页面状态机：资格加载 → 等待风险确认 →（等待身份 / 状态冲突）→ 提交中 → 结果确认中 → 已冻结/处理中/失败；内部执行步骤不直接作为 UI 状态 | SR §5 |
| 流程骨架：入口 → 查资格（含身份回跳/冲突刷新重查）→ 风险确认 → 创建或复用申请 → 查真实冻结结果 → 已冻结/处理中/失败 收敛 | SR §3（时序）/ §1 |
| 上下文 `loss_report_recovery_context`：按账号隔离、不随备份恢复，成功/失败/账号变化/超期清理 | SR §5 |
| 接口三件：`queryLossEligibility` / `createOrReuseLossApplication` / `queryFreezeResult` | SR §4 |
| 交接：确认冻结后交 `freezeTicketId` + 最终冻结状态给 AR90005 | SR §2、§5 |
