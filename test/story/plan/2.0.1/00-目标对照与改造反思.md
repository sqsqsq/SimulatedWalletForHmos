# Extension 2.x：对照目标的改造反思

2026-09-22。依据 [目标 spec](../../spec/2.0.1/00-版本需求与结论.md)开展的维护设计分析。先由特性与目标行为决定职责，再判断现有实现能否直接承担。本文不是开工计划：接口缺口、文件级完整动作、实施预算和真实验证计划尚需定案，不授权产品实施。

## 1. 结论

Extension 的产品单位始终是需求，知识能力贯穿实际开发动作。Framework 的 CU 是执行组织，不要求 Extension 转型为 CU 管理系统。旧实现可以保留多少取决于其承担的真实职责，而非代码量、文件名或版本沿革。

现有实现不是整体失效。材料、图、文本操作、人工意见保护、知识清单与实体义务已有明确责任，具备复用价值。真正应替换的是“需求等于一个 Feature、成文等于 spec 附属、知识选择依赖固定阶段”的组织假设。

改造目标是一套按需求职责工作的 Extension，通过 Framework 正式合同协作。不能为每个旧读取器增加“先找 spec，再找 blueprint，再拼所有 CU”的 fallback，也不能另造一份需求级虚拟 spec 给旧逻辑继续使用。

十章组织、固定文件集合、阶段绑定、字段和命令在本分析中按消费者需要判断复用，不作为产品先验约束。默认 Story 请求在准入设计的人读交付处结束；明确完整设计交接或实施请求才要求相应 CU/readiness，实施方案与状态读取须按这些请求终点接线。

## 3. 从零构建推导出的最小职责

若没有旧代码，需要的仍是几项业务能力：可靠取得来源和人工决定；组织需求理解与成文；把知识交给相应动作；把变化交回其责任方；按所有权安装与归档。

Framework 已负责设计权威、执行拆分、运行与完成；Extension 使用其现有协议取得结果。无需再建设需求调度器、CU 仓库、统一 provider 注册机制或第二套运行事件。

职责分离不等于新增软件层。优先在既有入口和消费者处改正责任，复用确定性工具；只有真实重复输入处理无法在现有责任处解决时，才按维护约定提出新增共享机制的必要性、成本和更简单替代方案。

## 4. 现有实现的处置方向

“保留”指保留能力和可直接服务目标的实现；接口处仍须核真实协议。“替换”必须让旧承担者退出，不能运行两套真源。

| 当前对象/范围 | 处置 | 新承担者与使用结果 | 退出判据/保护项 |
|---|---|---|---|
| materials/、import_sources.py、取材 adapters | 优先复用，调整实际交接 | Extension 取得来源、转换、图片、会议，向原生物化入口交材料 | 不丢原件/替代关系，缺席与故障分开；不复制 CU 材料树 |
| flow 的材料/会议/范围决定 | 复用业务规则，剥离阶段路由假设 | 需求级确认及输入准备 | 人签、原话、兄弟需求边界保留；不改为逐 CU 确认 |
| flow/routing、Story SKILL、phases/spec.md | 按目标流程替换 | 需求准备→正式设计交接→人读交付；实施交 Framework | “S4 必进 spec”“spec 三件套即交付”失效路径及专用检查一起退出 |
| story/context、sources、appendix、章节合同 | 修改输入责任，复用写作/呈现工具 | 从当前需求依据与权威设计取得内容，产出一套 Story | 不制造虚拟 spec、不拼 CU spec 当整单设计；精确事实/专项说明仍完整 |
| story/delivery、reader-review-task、审查接入 | 替换资格来源与调度耦合，保留质量要求 | 需求交付检查 + 合法独立读者审查；正式施工状态仍归 Framework | 不固定依赖 spec receipt；无合法审查入口明确缺口，不伪造阶段 |
| knowledge 清单/parser、原文入口与探针 | 优先复用 | 目标知识定义不变，在实际动作前给合适消费者 | 激活语义与空知识保持；脚本不判断语义、不含目标渠道特判 |
| knowledge-use、作者要求、阶段 overlays | 按判断职责重新接线/替换旧生产位置 | 适用判断与选型进入有权作该决定的活动，下游取得有效决定 | spec/plan 唯一判断/选型的旧要求退出；不建立平行蓝图知识设计账 |
| obligationsFromContracts、下游证据检查 | 保留实体义务原则，核实际输入 | Framework 合法施工输入承接实体、角色与验证责任，Extension 核专项语义 | 复用阶段不丢义务；不能依赖不存在的自定义字段自动传递 |
| flow/update 的语义方法与人工保护 | 保留，替换输入/状态/恢复绑定 | 需求级变化理解，设计修订与施工有效性回 Framework | 固定八文件、平铺 phase 路径、覆盖框架历史的恢复范围退出；增量/原话/在途保护保持 |
| review 渲染与人工填写区 | 优先复用，补实际反馈目标绑定 | 需求议题与原生 feedback 的准确映射 | 旧表态不套新问题，候选不当采纳，意见不伪装授权 |
| archive/restore adapters | 保留外部职责，修改交付资格 | 版本对应的人读发布与远端恢复 | 不以 spec 闭环替代交付资格；失败保留本地结果 |
| adaptation 与 manifest | 保留所有权，更换桥接生产者 | Extension 安装业务能力，Framework materialize 宿主入口 | 自有 bridges writer/check 专责退出；目标知识/身份和来源规则保持 |
| 状态帮助、入口、运行说明 | 同步新职责 | 用户看到需求级结果与必要缺口，开发状态引用 Framework | 不残留旧命令与“阶段文件在即完成”的断言 |
| 维护测试与失败经验 | 按能力迁移回归 | V1–V10，环境诊断、报告实际采纳和原有异常保证 | 仅服务已退机制的断言删除；有效业务回归保留；真实起跑另按授权 |

不批量重写历史报告或把正在运行的 1.x 需求转换成 CU。旧版继续使用匹配版本线，不在 2.x 增加永久双轨 fallback。

## 5. 五项关键设计判断

### 5.1 需求上下文不能等同 Feature 路径

Extension 需要定位本次需求依据、人工决定和人读结果；Framework 需要定位演进与施工单位。改造必须让每个读取者取得自己真实负责的对象，不能仅把 feature 参数换成 blueprint_id。具体关联可利用既有身份与原生引用，尚不批准新增通用 registry。

### 5.2 Story 的信息责任独立于它从哪份文件读取

技术附录仍需精确事实，叙事仍需业务语境和权衡。应先明确每类信息的权威，再调整生产/消费；不能为了旧附录正则补一个 spec，也不能把 blueprint 投影当全部 Story。写作设计、章节安全落盘和人工保护若能直接工作则保留。

### 5.3 知识没有“搬完一次就适配完成”

重点是作者及审查者在决定前看到来源，具体义务跟随合法结果进入后续执行。直接 Framework 入口与复用输入是检验点。不能只在 /story 开头补“请读知识”，然后声称所有路径已覆盖；也不能只把 knowledge-use 放进蓝图目录就建立第二真源。

### 5.4 update 仍然是语义工作

变化含义、人工意见和文档影响仍由模型理解；设计和施工变化由 Framework 原权威接手。Extension 提供精确输入并读取结果，不自行维护受影响 CU 列表作为调度依据。保留用户能继续/撤回的体验，但快照权限仅覆盖 Extension 自有工作。

### 5.5 质量证据不能靠沿用旧命令获得

“完整跑一次 harness 才采纳报告”是旧版本的具体观察，不是新产品合同。新合同是独立审查针对当前对象，结果实际被合法消费者接受。需查 3.1 的适用调用面；缺口回 Framework，不造 dummy spec、假 receipt 或额外完成字段。

## 6. 与 Framework 维护者的必要交接

对应 [协作 spec §3](../../spec/2.0.1/03-Framework协作与验收.md#3-已有协议和待定接线)：

1. 蓝图入口与其独立质询能否通过现有公共接入取得完整目标知识，且不依赖先经过 Story。
2. 自定义知识决定和实体义务如何在设计引用、施工输入派生及复用中保留，组合义务由谁在整体完成时消费。
3. 不执行 spec 时，需求级 Story 的读者审查通过哪个合法入口运行，如何绑定对象并消费结果。
4. 设计反馈接受后的 CU、运行恢复及过期结果，Extension 应读取什么原生结果；不向 Extension 下放 Framework 状态写权限。

这些是待核实的实际合同，不预设一定要新增 API。先查真实消费者；已有能力就直接接，缺少通用能力由 Framework 补齐。没有证据前，不宣称只改 Extension 即可完成全部目标。

## 7. 实施设计的组织建议

下列为后续设计的四个交付边界，不是当前开工步骤；前面的合同缺口会影响最终拆分。

| 包 | 独立可检查结果 | 所替换职责与保护能力 |
|---|---|---|
| 1 需求与设计协作 | 一项正式需求的真实来源、知识与设计交接成立，直接入口知识也有合法路径 | 替换单 Feature 阶段路由；保护取材/会议/范围 |
| 2 人读交付与决定回流 | 一套 Story/Review 可独立于新 spec 交付，反馈准确进入设计权威 | 替换 spec 附属成文与交付资格；保护表达、人工区及技术信息 |
| 3 持续知识与变化恢复 | 义务承接、复用、更新、归档及恢复能沿需求责任工作 | 替换固定阶段/快照假设；保护增量处理与所有恢复能力 |
| 4 安装与整体验证 | 所有权升级、旧机制退出和 V1–V10 证据清楚 | 替换自有桥接生产；保护目标知识、对接和历史运行 |

发布件接入作为真实前置处理，包间不人为制造新的运行阶段。每包必要的信息和权限在执行前交给实施者，不能靠施工时重新拼接对话。

## 8. 预算及准入到实施的条件

本轮没有产品新增/删除量，没有批准实现预算。上述复用/替换范围先作为计量边界；在 Framework 合同和文件动作定案后，按 test/story/AGENTS.md §5 分别登记机制、知识、验证装置和必要测试的基线、累计新增、旧内容退出、峰值和完成量。替换写出的新实现计新增，删除另计，不能用净增量掩盖重写成本。

形成可实施方案前须补齐：实际 Framework 发布件身份及用于改造的源码基点；每项输入的唯一生产者/消费者；完整文件及引用动作；合法审查与恢复路径；旧状态/入口/专用检查退出清单；预算依据与必要验证。未确认合同的成本不得以精确行数伪装已经估算。

复核方案是否在打补丁，用四个问题判断：是否重复设计真源或状态；是否为旧文件生产无业务必要的产物；是否用 CU 特例替代需求级行为；是否增加无人使用的通用机制。若答案为是，先修职责与合同。变化规模大小本身不作为好坏标准。

## 9. 本轮反思的证据结论

已经完成：产品特性与目标定义、Framework 已有协议对照、当前关键耦合点定位、复用/替换/退出方向和未决接线清单。尚未完成：所有函数级改造审计、实施工量估算、产品实现、Framework 升级、运行验证。

本轮文档和引用检查只能证明材料结构可用；目标行为成立需实施后按 V1–V10 获取相应证据。现有离线 PASS 不代替 2.x 的行为证据；特性树规定的正常结果与异常保证均须验收。
