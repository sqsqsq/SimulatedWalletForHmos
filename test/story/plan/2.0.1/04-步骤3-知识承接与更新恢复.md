# 步骤 3：知识承接、反馈、更新与恢复

依据 [总览](01-实施总览与协作合同.md)、[步骤 2](03-步骤2-需求设计与人读交付.md)及 [维护预算](../../AGENTS.md#5-维护预算与分级复核)。本步保护既有知识义务、增量更新、人签、归档及恢复能力，替换平铺阶段和全树快照假设。

## 1. 文件动作与生产消费关系

路径相对 `extensions/`。

## 2. 知识承接

项目事实使用依据进入 discovery facts；规约适用和模式选择进入原生 decisions，保留知识来源、理由和实际设计落点。三类知识按真实条件使用，机制不按业务名或固定知识名分支。

作者在设计决定前取得相应完整篇章，后续阶段取得有效决定、原文和当前契约。facts 的错误回知识事实责任方；规约变化回相应设计责任；模式落实到真实角色和接口，不以声明本身作为应用证据。

保留 `must`、`pattern/role`、`knowledge_rule` 的业务语义，验证原生蓝图派生及 prepare-blueprint-design 物化、复用后仍可读取。缺契约先报告原生输入缺口，不能从文本或 touches 猜造接口。施工阶段新形成的具体落点写入该阶段合法输出；共同设计变化交回蓝图。

共享义务对应原生设计对象并经 CU design_refs 传递，组合要求落实到关系/运行时流及原生闭环证据。局部全部通过而组合证据未取得时，进展继续显示缺口。

### 2.1 蓝图内的数据合同（唯一字段定义）

Extension 形态合同放在 `skills/story/contracts/knowledge-application.schema.json`，校验逻辑由现有 knowledge-use/document、validation 消费；schema 只定义下面字段，不另存决定。蓝图完整性、对象寻址和 provenance 继续由原生 checker 判断。

| 对象 | 结构与写入者 | 读取规则 |
|---|---|---|
| 已使用项目事实 | 设计作者写 discovery.facts[] 的原生 fact_id/subject/value/provenance；value.knowledge 为 `{unit,form,source_sha256}`，value.observation 为实际事实及用途 | provenance.source_ref 指知识文件或实际事实来源；需要同时引用工程事实时另写有独立来源的 fact，不用知识覆盖工程证据 |
| 规约/模式决定 | 设计作者写 decisions_and_gaps.decisions[]；原生字段 decision_id/kind/status/owner/provenance/verification_refs/rationale，kind=`knowledge_application` | knowledge 字段按下表；保留稳定 decision_id，不按本轮 hash 重命名 |
| 施工落实 | 当前设计/施工作者写原生契约实体 must、files.pattern/role 和验收 knowledge_rule；新增 must.decision_ref 引用完整原生蓝图 decision ref | 读当前有效契约；字段缺失视本阶段待补，不从名称猜关联 |
| 非 CU 的合法维护 Feature | 其当前原生 contracts.knowledge_applications[] 使用同一决定行结构，来源为当前任务和知识；facts 在该阶段原生事实材料中 | 只服务该 Feature；无 blueprint ref，不作为任何正式需求蓝图的替身或回退来源 |

decision.knowledge 必填：`kind: constraints|patterns`、`form: entries|halves`、`unit`（解析器已有条目/模式身份）、`source_sha256`（原始文件完整 SHA-256）、`outcome`、`target_refs`（蓝图稳定地址数组）。来源路径只在 provenance.source_ref 维护。rationale 为结合本需求的理由。

- constraints 的 outcome 为 applied/not_applicable/waived/pending；applied 必须有 requirement 和非空 target_refs；waived 必须有 waiver `{reason,compensation,authority_ref}`，红线不可豁免；not_applicable 有实际理由、target_refs 可空。
- patterns 的 outcome 为 selected/rejected/adjusted/pending；selected/adjusted 的 target_refs 非空，roles 为 `{role,target_ref}` 数组，角色来自激活模式；rejected 有具体理由；pending 同时有原生 gap，owner、needed_by、unlock_condition 完整。
- 有据的模型判断用 answered_with_evidence；不适用用 not_applicable；人的已接受权威裁决才用 decided_with_authority，provenance/verification_refs 指实际原话与权限。未决按原生 open_decision/blocker 及 gap 处理。上游 closure 对权威结论的知识归位仍按其原规则，不为绕过它改写人的决定类别。
- facts 不要求所有条目逐一登记；约束每条都有判断、模式候选及选择有完整理由。完整性以激活解析集合和语义审查共同核，不按字符串重合率判语义。

### 2.2 消费者接线

| 消费者 | 读取位置和动作 | 异常 |
|---|---|---|
| Story 附录 | 关联蓝图的 knowledge_application 决定；按当前激活条目渲染判定/理由，链接原始对象 | 新增激活条目无判断、来源 hash 变而决定未重判时列缺口 |
| CU 设计准备 | design_refs 必须选择本 CU 真实承担的设计对象及相关决定；作者说明共享义务归属 | 引用解析失败/旧 revision 交原生设计责任方 |
| knowledge-task | 原生有效蓝图决定 + 当前契约；既有决定在角色设计之前送达 | 无相关 Story 合法；需要的输入不可取则退出 1 |
| post_check | knowledge-use validation 校字段/来源/稳定地址；obligationsFromContracts 校实体 must、角色和验收桥 | 坏 shape、来源缺失、决定引用失效集中报告 |
| pre_verifier | 原条目、决定理由、设计对象和当前实体并列；判语义、遗漏和义务偏离 | 不用字段存在冒充知识应用 |
| UT | readAcceptance/knowledgeCriteria 按 verify=ut/both 和实际验收 ID取得实体与测试责任 | 缺必要测试证据显示未完成 |
| Testing | 同源取 verify=device/both 及必要人工/其他验证要求 | 无设备证据如实未验证，不因 UT 通过代替 |

非 CU 路径通过原生 Feature 类型明确分派，不用“蓝图缺失则找局部文件”的 fallback。蓝图派生的 contracts 未包含声明义务属于输入丢失，应失败；没有要求的合法空集通过。保留字段由原生派生/物化正反例核实，最终测试见步骤 4。

## 3. 更新和人工反馈

update 保留材料关卡、人的原话、变化/缺席/故障区分及未完成更新识别。输入变化比较结果交模型判断，用户请求本身可开启更新；不能凭逐文件相同就吞掉请求。

| 变化 | 动作与产物 | 完成依据 |
|---|---|---|
| 纯表达 | 修改 Extension 表达、保持设计和人工内容 | 自有检查与适用读者审查 |
| 需求/范围 | 人决定范围，形成新的有效来源版本 | 实际原话及新的设计输入 |
| 设计反馈 | 按 opinion/fact_supplement/suggestion/authoritative_ruling 形成原生候选 | 原生资格结果；是否接受另读设计处理结果 |
| 原生设计已变 | 读取当前 revision、投影和下游有效性，同步人读件 | 当前对象检查、剩余施工责任如实报告 |
| 人改派生文档 | 保护修改、理解意图并送正确责任方 | 不把派生文档整体升级为设计权威 |

设计相关议题保存被评 revision 和真实 target_ref；需求侧业务意见保留在需求侧。资格缺失报告实际项；过期反馈由裁决方重新确认适用性，不只改 revision 重投。原话、讨论、候选、接受和同步状态分别可查。

update 收口以前完成受影响的人读结果与必要审查，将本轮 decide 原话保留到既有 record.json。Framework 状态只读；已有实施授权可由其原机制续行，update 不创造新的施工授权。

## 4. 恢复和外部发布

恢复仅处理 Extension 自有的可编辑工作件，并沿既有逐文件前后比较保护后来人工工作。蓝图、CU、运行、receipt、审查历史、已引用冻结输入和对外发布记录均不作为覆盖恢复对象。

### 4.1 可编辑集合与保护集合

在既有 `story-chapters.json` 增加 `update_files`，唯一维护以下集合；update 快照、比较、恢复和验收均读取它。所有路径相对需求根，未知文件不因位于同目录就取得恢复权限。

| 集合键 | 精确内容 | 操作 |
|---|---|---|
| editable | AR/story.md；AR/story-src/design-draft.md；AR/story-src/design-input.json；AR/story-src/decisions.json；AR/story-src/story-template.md；AR/story-src/doc-refresh.md；AR/story-src/drafts/** | 保存 before；在 story 登记或 close 的已完成输出点记录 after；按下表恢复 |
| regenerate | AR/review.md；AR/story-src/materials.json | review 保存当前人工区后按恢复后的机器数据渲染，按语义对象/版本核旧表态；materials 按实际来源重算 |
| protected | RR/**、SR/**、AR/design.md、AR/detail.json、inbox/**、assets/**、ux-reference/**、AR/story-src/meetings/**、AR/story-src/inputs/**、AR/story-src/review/**、AR/story-src/updates/**、.backups/**、其他原始/发布记录 | 保持；不属于 editable 的路径默认保护，包括相邻 blueprint/CU |
| field_owned | AR/story-src/story-flow.json | 只由 flow.state/save 改 update 活动指针；rounds、gates、真实人签、binding、input 和归档历史保持，不整文件恢复 |

before/after 仍用现有 updates/<轮次>/，record.json 加 `owned_before`、`owned_after` 的相对路径→SHA-256|null，记录的是实际已完成写入，不按 mtime 猜作者。story 登记/close 时由 flow 唯一写入；未到已完成点的中间修改没有 after 证据，恢复时保留为冲突。此约束保护中断现场，无新增文件监听或动作台账。

本轮说明仍在现有 `AR/story-src/updates/<轮次>/update-notes.md`，随更新历史保存，不新建根级 update-notes。恢复前将当前 Review 人工区原样保存到本轮 protected 历史中；重渲染只在议题语义及被评对象仍匹配时重新关联表态，不匹配的保留在历史并列为需重确认，不能套用或丢弃。

### 4.2 恢复真值表

恢复先把当前差异保存在既有 conflict-<时刻> 目录，保存失败不继续。before 是开轮字节，after 是最后已完成输出，current 是恢复时字节；不存在用 null。

| 条件 | 动作与结果 |
|---|---|
| current == before | 原状，保持 |
| after 已记录且 current == after，before 有文件 | 恢复 before；示例：本轮改写的 story，之后无人改 |
| after 已记录且 current == after，before 为 null | 删除本轮新增文件；示例：本轮新建且未被后来改的草稿 |
| current 与 after 不同，或 after 未记录而 current 与 before 不同 | 保存差异后保持 current，列冲突；示例：登记后人修改 Story，或未登记的中间稿 |
| protected 路径 | 原字节保持；示例：蓝图引用的冻结原文，无论何时新增均不删除 |

有冲突时 record 状态为 restore_conflicted，活动 update 不关闭；恢复明确文件可重复执行。无冲突时为 restored 并关闭本轮 update；人签原话先保留到 record.decisions。恢复后重新计算登记有效性，当前设计不一致则派生 needs_sync，不伪造旧 PASS。

### 4.3 close 的确定性条件

close 依次核：当前材料清单与本轮采用输入一致或已登记有理由的不采用；有效设计引用与本次 Story basis 一致；受影响人读件完成结构检查；原生独立审查 check 可消费；本轮真实人签已归入 record；没有未处理的 restore 冲突。缺一项返回具体缺口，update 保持 open。纯表达更新复用相同设计引用，新设计已接受而人读件未同步时不能 close。Framework 施工是否完成只读展示，不作为文档 close 的额外条件。

发生冲突时保留当前文件和可比较的版本，报告具体路径及前后依据。已接受设计变更保持有效；撤回意图提交原生修订。恢复人读表达后若与当前设计不符，显示待同步而非已交付。

归档检查当前 Story/Review、设计身份、材料和审查依据；先展示差异、未决与验证缺口再按实际授权发布。外部失败保留本地结果；重试检查远端新修改。远程 restore 只恢复其授权外部对象，保留人工新增意见并报告内外差异。本地单没有线上动作。

## 5. 验证与交回

| 编号 | 场景 | 预期 |
|---|---|---|
| S3-01 | 原生派生、物化、复用施工输入 | 实体 must、角色、验收桥完整可读，原生 checker 通过 |
| S3-02 | 无新 Spec/Plan、直接阶段入口、共享义务 | 有效决定持续送达，局部/组合证据责任可追溯 |
| S3-03 | 四类反馈、缺权限、旧 revision、无蓝图目标的业务意见 | 分类和责任正确，资格不冒充接受 |
| S3-04 | 表达/范围/设计更新及未变请求 | 正确层次处理，范围有真实决定，不意外施工 |
| S3-05 | update 收口、撤回及后来人工编辑 | 人签保留，冲突可见，冻结输入和 Framework 文件字节不变 |
| S3-06 | 发布失败、重试时远端新意见、远端恢复、本地单 | 本地结果保持，远端不覆盖新意见，本地无远程调用 |

迁移现有 update、restore、知识义务、对接和失败形态回归，保留合法输入变体。交回当前有效设计→施工输入→验证义务的证据链、更新前后差异、恢复保护结果和退出清单。

运行机制估 +800/−950，累计完成估 B+150。按总览记录累计新增与退出，评审同时核更简单实现和原有业务能力。通过后进入步骤 4。
