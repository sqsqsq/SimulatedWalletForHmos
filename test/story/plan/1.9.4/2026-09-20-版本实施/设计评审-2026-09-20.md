## 3. 需要用户定的三件事

### 3.1 C 需求没有预算数字

`参考/03 §4` 里 C1/C2/C3 三行都是「待核定」，只有 .js 220–340、运行器 240–400、离线回归 700–1100、说明 100–180 四个单列区间。`test/story/AGENTS.md §5` 要求制定方案时登记预计新增量与完成总量。设计把它推到「开工准备」四项之后再签。

C 是本版最大的新增，且 D20 要求越轻量越好，没有数字就没有「走偏」的探测器。建议：C1 开工前先做参考稿 §5 的四项准备，交回函数级清单，由设计评审签一个初始额度，再动 `phases/update.md` 与 `flow/update.py`。A1、B1 不受影响，可以先开工。

### 3.2 update 之后的产物没有独立语义审查

现行链里语义审查只在阶段闭环时由 framework 派一次 verifier；`--revalidate` 只重跑脚本门禁，沿用旧 PASS。update 改了已闭环的 spec/story/plan 之后，新内容只经过模型自己的 §4.6 核对与 T2 的人工后评。设计在 `00 §5`、`03 §8.2`、spec `00 §6` 都如实写了这一点，但没有把它作为一个要用户接受的版本限制列出来。

这是 framework 的缺口，本仓不能改。建议在 `spec/1.9.4/00` §6 明确一句「1.9.4 的 update 产物无独立语义审查，靠模型核对与人工审视；交上游」，并登记到 1.9.3 方案 04 §4 那张 framework 缺口表的同类位置。用户不接受时，唯一的仓内替代是 update 结束时由模型按 `story_reader_review` 判据自审一遍并写进 update-notes，这不是独立审查，只能如实标注。

### 3.3 F2 评审动作擅自已定：只靠 verifier 还是加一条确定性核对

B1 对 F2 的方案是「决策写入前送达表态边界，verifier 对照原文判断，脚本不增字段」。car 第二轮正是 verifier 没拦住的那一次，所以这条方案的可靠性依赖并列依据做得比 1.9.3 好。

有一条不需要语义判断的事实可用：知识条目处置为「（评审动作）」的决策，只能由评审人在 `review.md` 里表态，而 story 登记时 `review.md` 尚未生成，所以这类决策在登记那一刻只能是 open。这是时序核对，不是关键词判语义，也不是按编号特判，`knowledge-use.yaml` 里 `decision:` 键与知识表的处置列已经能对上。建议 B1 把它作为脚本核对项之一，verifier 仍负责其余伪定案。是否加由用户定。

## 8. update 后的独立语义审查：不是版本限制，是 C3 的一个文件动作（15:10）

### 8.1 修正 §3.2 与处置稿 §4 的前提

我在 §3.2 写「这是 framework 的缺口，本仓不能改」，处置稿据此把它列为待用户接受的版本限制。看过 framework 代码后这个前提不成立：派 verifier 从来是主 agent 的动作，`/story update` 就是主 agent 在跑，代码层没有任何东西拦它。

| 事实 | 位置 |
|---|---|
| harness 每跑一次都按当前材料算 subject、写出 `verifier.request.<subject>.json`，并把报告落点写进 `summary.verifier_report`；生成函数不看阶段是否已闭环 | `harness-runner.ts:2014-2050`（issueVerifierRequest）、`:1905-1911` |
| revalidate 逐阶段重跑 harness，所以 update 改完材料再 revalidate，新 subject 的请求已经在盘上 | `revalidate.ts:1-14` 头注 |
| check-receipt 先找当前 subject 的报告；只有 `report_missing` 才退到历史 PASS 并打 `completed_with_prior_review` | `check-receipt.ts:703-719` |
| 已闭环时 NEXT 行只是「停下等待用户指令」，没有拒绝新报告的代码 | `harness-runner.ts:2094、2228-2229` |

也就是说：update 改产物 → `--revalidate` → 对被标 `semantic_not_reverified` 的阶段，把该轮请求整段投给 verifier 子 agent → 回复原样写到 summary 指的路径 → `--sync-closure`。闭环模式就是正常审查，信号消失。verifier FAIL 则回正常返修链，这对材料确实变了的 update 是应有之义。

拦着的是三句指令：NEXT 行「等用户指令」、仓根 CLAUDE.md「verifier 只跑一次」、我们自己 1.9.3 写的 `phases/spec.md:69`「闭环后不手动派 verifier」。前两句是同一次闭环内小修正的口径，framework 的 subject 设计本身就是「材料变了就是新对象」，沿用旧 PASS 被它明确标注为非语义再审；`/story update` 是用户指令，正合 NEXT 行的条件。第三句的理由是「每派一次就是整份再审」，update 本来就该整份再审一次，理由不适用。

| 1 | `03 §8.2` 检查和继续工作 | 加一段：revalidate 之后，对本次 update 实际改了产物且 summary 标 `semantic_not_reverified` 的阶段，用该轮生成的 `verifier.request` 派一次 verifier，报告写回 `summary.verifier_report`，再 `--sync-closure`；一次 update 每个改动阶段最多派一次。无变化退出、「核对后无需修订」、只改过程记录的三条路不派 |

### 8.3 实施时要核实的两点

- revalidate 写出的 summary 与随后 `--sync-closure` 读的是同一份 summary，请求里绑定的 `worktree_digest` 在派审到收报告之间没再变。update 的所有写盘都在 revalidate 之前完成即可满足，交实施者用伪运行证实，可复用 `test_verifier_chain_in_workspace` 的工作区装置。
- 派审用的是 revalidate 那一轮生成的请求，不是旧 subject 的；两个文件名带 subject 哈希，拿错会被 check-receipt 判 `report_missing` 而回到沿用旧 PASS，表面闭环、实际没审。离线用例要覆盖这条错路。

### 8.4 不做的事

不在 Extension 建第二个审查者、不改 verifier 任务书为 update 另写一套判据、不在 B1 提前改 `spec.md:69`。审查内容就是现有 story_reader_review 与知识判据，缺的只是闭环后再派一次的触发点，现在确认触发点在主 agent 手里。
