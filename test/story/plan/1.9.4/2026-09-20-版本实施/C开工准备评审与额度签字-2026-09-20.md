## 3. 三个问题的答复

### 3.1 `flow.schema` 不升

同意不升。`update` 是可选键，旧读者忽略；升了会让在途单的门禁报 schema 不符而流程并没变。`check.mjs` 不为 `update` 键加判据，与它「写入侧已保证的形状不在这里重判」的原则一致；键的形状由 `update.py` 写入侧保证，合同 README 记一段说明。

### 3.2 §2.2 第 3、4 条在 C2 做，但只做确定性那一半

两条是今天就在的缺陷，update 让它高频发生，03 §8.1 明确要求，归 C2。范围划清：

- **议题被删**：渲染前枚举「旧文有、新表无」的 `<!-- decision: X -->`，其人工区原样留存到本次 `updates/<id>/before/`（本来就有完整旧镜像）并在 update-notes 列出；不静默丢，也不在新 review 里保留一个没有议题的孤儿区。
- **id 复用但问题换了**：脚本只判一件事——该议题机器区内容的指纹与人工区表态时记下的指纹是否相同，不同就不自动带过旧勾选，旧区留存同上。「措辞改了」还是「问题换了」是语义判断，归模型：模型认为意义未变时用 decide 的 update 分支明确写「沿用某某在哪一版的表态」，脚本据此带回。指纹算法沿用 `document.mjs:596-606`。
- 45–70 行的估算按上述范围签；超了先查是不是把「意义变没变」写进了脚本。

### 3.3 两条既有事实的处理

- `TERMINAL_STATUS` 不一致归 T1：装置是 T1 的范围，双检查点会更常停在那三个态上。T1 交回时给出统一后的集合与每个态的 finalize 语义。
- 「第二段零件已存在但只在新建 run 时生效」：按 D18 同会话续行，走 3.2 在同一 foreground 里续，不复用 `--continue-case` 另起 run。`events.jsonl` 每次 foreground 启动被截断这条写进 T1 交回，作为「不能靠重启新 session 冒充续行」的机制依据。
