# 支撑工作：测试装置与版本验收

对应用户 D18 与 AC12/AC13。分 T1 装置承接、T2 两 Case 运行与发布两步。它服务整个版本，不作为 Story 表达优化的子功能。读[总览](00-整体设计与实施总览.md)；修改装置按 TEST §7 及相关运行分支，真实启动前读 TEST §0–§6。

## 1. 用户已确定的运行形态

只跑两个 Case，一个到 Spec、一个到 Plan。分别先给初评、回流原结果且不终止，再触发同一会话的 update；第二次评测后终止，回流为 `<需求编号>-update`。不默认增加独立第二轮、第三个 Case 或专项模型测试。

选择复用 auto-topup（AR90006/spec）和 car-key-sharing（ISSUE-206/plan）是设计选型，与当前基线和 case.yaml 相符；用户确认的是两个阶段节点和成本边界，不把具体案例名写入通用运行器。

## 2. T1 要解决的现有缺口

run_case.py 达到目标即 break；run_multi_case.py finalize 拒绝活动 Case，文档回流固定原名；TEST 只在 finalize 后评测。直接执行会在第一次终止或覆盖初稿，必须先改装置，不能靠人工复制活跃目录或重启新 session 冒充续行。

复用现有 lease、awaiting_reply、reply、conclude、闭环事实、事件流和回流冲突检查，不新建运行器、后台观察 Agent 或评测平台。

### 2.1 Case 与状态

Case 增 after_initial: update（不配置仍为普通单终点）；end_phase 仍是首次阶段真源。配置沿 suite→start→worker 穿透并回显。worker 原 state 增 checkpoint_stage=initial/update、initial_snapshot_ref、进入 update 前最近操作 id；不把 update 加入 Framework 的阶段序列。

| 当前情况 | worker 行为 | 宿主动作 |
|---|---|---|
| 初始目标未到 | 原来的阶段驱动与交互 | 正常代理需求方 |
| 初始闭环且 CLI turn 已结束 | 保存 closure/游标，awaiting_reply/checkpoint，保留 session 与租约，不 break | 固定快照、只读初评、首次回流 |
| 初评/回流已完成 | 收到 resume-update，转 update 并续原 session | 先投预登记变更材料，再给正常更新请求 |
| update 处理中 | 旧 spec/plan 回执不能触发自动结束；按原 reply 等待 | 按实际问题回应，不注入初评解法 |
| 本次 update 已结束本轮写入且回合结束 | 核新操作 id、closed 事实、当前摘要和模型结果说明，报告第二检查点，不判语义成功 | 固定快照、后评，再 conclude |
| 宿主 conclude | 原正常终态落证据 | 全部终态后 finalize，另名回流 |

同 session 无法续接时报告 cli_session_lost；不会自动重启新 Case。若模型说完成但必要凭证缺失，记录真实缺口并向用户报告，不自动跳过初评/变更目标。需要额外实跑时单独说明故障与成本。

无变化快速退出不创建新的语义操作记录。此时第二检查点可由本次调用中 prepare 返回 comparison=unchanged 的真实结构化结果、CLI turn 结束及稳定目录摘要触发；绑定当前 session/事件游标，不能拿上次无变化结果或模型一句“没变化”代替。它表示本次检测结束，评测仍核检测范围和是否漏掉续办任务；相关分支离线验证，不增加真实 Case。

### 2.2 新命令与回流合同（待实现）

```text
run_multi_case.py checkpoint --suite-id <suite> --case <case> --point initial|update
run_multi_case.py promote-checkpoint --suite-id <suite> --case <case> --point initial
run_multi_case.py resume-update --suite-id <suite> --case <case> --text <正常业务请求>
```

checkpoint 只在 worker 已等待、无模型写入者时复制 feature、系统侧必要快照、事件游标、闭环事实与版本摘要到 cases/<case>/checkpoints/<point>。复制前后摘要变化则本次快照失败，不能接受混版证据。重入同内容幂等，已有异内容不覆写。

promote-checkpoint 只从固定 initial 快照回流到主仓原 feature 名，不回流源码、不终止 worker。目的目录有异内容时保留双方并报冲突；初次回流记录成功后才允许 resume-update。

resume-update 核初始快照、初评文件和回流记录存在（仅前置齐，不代表评分通过），绑定进入前的操作 id，然后按配置投递业务输入、续原 session。重复调用不重复插意见或修改源材料。

finalize 对 after_initial=update 的终态文档使用 `<原编号>-update` 作为目的目录。复用 promote_case_workspace 的文档复制与冲突保护；其他 Case 行为保持。目录标签改变不改内部需求编号、原始报告或引用；promotion manifest 标 source_feature、destination_dir、point、digest、session_id、event_cursor。初次原编号目录不得被第二次覆盖。

如果第二快照后终态检查产生新报告，finalize 保留 update 检查点指纹和终态报告指纹，明确两者用途，不能把终态后的不同正文冒充已经评测过的正文。主业务文件变了则重新固定快照/更新评测，不启动新 Case。

### 2.3 投递与评测隔离

Case 的 update_inputs 记录测试域 source、destination_kind=system/local_material/review_human_zone、目标内相对 destination、delivery_point=after_initial。初始 seed 真正排除更新材料和旧反馈，不是只延迟一句通知。投递有完整原版/修订版及摘要，禁用随意全局数字替换。

Review 人工区插入仅使用明确 freeform 边界；边界不明时提供独立普通评审材料并记录，不由宿主修复机器产物。对接路径和 copies 解析在实际 features_dir/模拟系统目录内，拒绝越界与目录联接。

checkpoint 等待窗口允许维护者对固定快照做只读评测；恢复驱动后只扮演需求方。不能向被测模型发送评分、维护缺陷清单、脚本路径或修法。评测不代跑其 gate、不改它的产物与全局阶段状态。

## 3. T2 测试输入与执行

### 3.1 更新刺激

auto-topup：第一次快照后，提供预先准备的正常 PRD 修订版，将单日上限从 200 改为 300，并说明界面与协议同步、其他有效决定保持；同时提供既有评审反馈。旧反馈中已落实内容应识别为重复/无变化，旧上限冲突按新决定正常裁决，不能偷偷吞掉。模型收到的是业务材料，不是 Spec 改法。

car-key-sharing：第一次快照后在 Review 人工意见区提供评审决定：撤销宽限改为 36 小时，替代此前 24 小时口径；提示采用“正在收回”；转分享和强制下线保持未决。已有初稿若仍未定时限，则本次是明确裁决，按真实初评解释，不改写历史。应同步已有 Plan 的相关设计/契约/用例，不开始 coding，不访问需求系统。

上述具体刺激属于测试设计，不是产品业务规则或用户已逐项裁定的答案；启动时随实际配置向用户展示。运行中不根据初评结果修改刺激或降低难度；同一输入中的冲突按预定业务立场回应。

### 3.2 执行顺序

1. 核 A1/B1/C1–C3/T1 交回与离线结果。只读 plan 展示两个 Case、配置、更新输入、首次和最终回流目录；用户启动里程碑后 start。
2. 两 Case 到各自 Spec/Plan 初始等待点，分别 checkpoint→初评→promote-checkpoint，不终止；先完成的先处理。
3. 初评与回流完成后投递材料，发送 `/story update <原编号>`；只用产品入口和正常需求方话语，不指内部脚本。
4. 到新 update 等待点，checkpoint→后评→conclude；均终态后 finalize 到 -update 目录并结束观测。

整个版本只这一批两个 Case，各初始/更新后一次评测。失败恢复/无变化/异常组合的剩余覆盖由离线验证承担，不暗增真人模型调用轮数；真实业务交互需要的正常续话不设人为次数上限。

## 4. 评测对象与完成条件

第二检查点是评测时机，不是更新成功标志。closed 只说明本轮操作停止写入；模型可能报告仍待裁决或来源缺口，评测必须按实际结果区分。模型自称结束但没有可信操作/快照事实时由宿主记录缺口并决定是否 conclude，不能只凭说明文件存在判成功。

除文件变化外，评测还要核模型有没有辨清旧版意见、已经落实的重复输入、已有手改、仍未决及隐含下游关系。对第一稿已经正确的地方不强求修改；对摘要相同但上轮遗漏的相关内容，不把它当“没有变化所以正确”。

| 维度 | 初次成品 | update 后成品 |
|---|---|---|
| 产物 | 长段是否混独立问题；H3/H4 是否自然；主语/条件/结果是否具体；图文互补；未决与责任保持 | 变化理解及有效依据正确、隐含关联已同步、有效手改与未变事实保持、旧意见语境与当前可继续范围明确；不能只看修改文件数量 |
| 性能 | 作者、脚本、门禁、审查、返修、上下文；等待单列 | 增量成本与实际影响匹配；独立审查次数/耗时/对象及返修原因单列，无关重跑、重复读源和发布重试可解释 |
| Knowledge | 看到、理解、应用、传递及两条边界定义 | 新变化影响适用性和落实点时准确更新；不以规约名称回显代替应用 |

本版给定更新刺激下，正常预期 auto 的 Spec 审一次，car 的 Spec 和 Plan 各审一次；这是无阻断返修时的成本预期，不是硬上限，不增加 Case 或独立起跑次数。实际无修订或当前材料已有 PASS 不重复派；FAIL 后返修按实际记录。评测核当前 subject 的实际 PASS 及原生闭环，不能只因历史重验日志有/无 semantic_not_reverified 就判断。

每次 scorecard 绑定 checkpoint 内容摘要、机制/知识版本、模型配置、session 和事件区间。按 TEST 三轴给建议分与证据，最终以用户已定的明确行为验收＋成品审视为准；不能把历史 90 分门槛或独立重复次数重新加成版本条件。

成品正确性核当前来源，不要求同源示范的标题、图数、表数或措辞。公开技能效果仅是参考；本次两 Case 前后比较也不证明所有未知需求的成功概率。语义和结构结论分别写。
