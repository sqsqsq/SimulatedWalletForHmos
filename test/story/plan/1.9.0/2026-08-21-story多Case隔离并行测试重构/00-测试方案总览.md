# Story 多 Case 隔离并行测试重构方案

## 1. 本轮目标

本轮只重构多 Case CLI 测试方案，不启动测试，不修改被测产品代码，也不进入 coding skill。

目标是让四个最小覆盖 Case 在同一轮中真正独立运行，并满足以下验收条件：

1. 一轮测试只有一个结果大目录，直接创建在 `output/story/<时间戳-任务名>/` 下。
2. 每个 Case 使用独立临时代码工作区、独立运行状态、独立 AR 和独立产物目录。
3. 临时工作区不复制 `output/`、`test/`、`tools/`、历史 `doc/features/`、`.git` 和运行缓存。
4. 四个 Case 都能同时启动；不再依赖主工作区的共享 Story 阶段槽。
5. 交互 Case 由测试执行器按 Case 脚本承担人工角色；只有出现未预期的人工决策时才暂停报告。
6. 所有交互完成并进入自动化阶段后，才开始每 120 秒一次的正式观测。
7. 结束时先归档证据、校验哈希，再把通过验收的 `doc/features/` 和 Coding 新增代码回灌主工程，最后删除临时工作区。

## 2. 四个最小覆盖 Case

| Case | AR | 阶段范围 | 交互方式 | 覆盖业务场景 |
|---|---|---|---|---|
| `split-two-ar` | AR90005 | Story → Spec → Plan | 自动关卡回复 | 一个 SR 拆多个 AR，本 AR 的范围、兄弟 AR 边界和下游 Plan 传递 |
| `split-interactive` | AR90006 | Story → Spec | 测试执行器按脚本回复 | 材料补录、真人在范围关卡提出拆分要求、范围收窄后的 Spec 闭环 |
| `source-conflict-review` | AR91004 | Story → Spec | 测试执行器按脚本回复 | 同轮来源冲突暴露、人工定源、冲突处置留痕和 Spec 闭环 |
| `pattern-image-review` | AR90004 | Story → Review | 自动关卡回复 | 图片材料保留、Plan 消费设计模式、Coding 真实改动和 Review 审查 |

四个 AR 互不重复。四个 Case 合起来覆盖：自动流程、人工交互、材料补录、来源冲突、多 AR 拆分、图片取材、Plan/Coding/Review 下游消费。

本轮不把 15 个历史 Case 全部混入并行集；其余 Case 作为后续专项回归，不影响这四个业务场景的最小覆盖。

## 3. 运行流程

### 3.1 起跑前

1. 记录本轮非沙箱执行授权及授权范围。
2. 检查旧 suite 的 worker、CLI run 和 lease，确认没有活跃测试。
3. 在本轮结果目录下备份并迁移主工程现有 `doc/features/`，主工程不保留历史同名目录。
4. 加载四个 Case，校验 `case → AR` 一对一；重复 AR 直接拒绝启动。
5. 为每个 Case 准备独立工作区，执行工作区边界检查、路径长度检查和运行目录可写检查。
6. 校验四个工作区的框架状态目录、CLI runtime、临时环境变量和结果路径均不相同。

### 3.2 启动与观测

1. 调度器一次性启动四个 Case，`jobs=4`。
2. Case 之间不共享 `doc/features`、Framework 状态、源码、CLI runtime、模型会话或运行目录。
3. 交互 Case 进入预期关卡时，调度器读取其交互脚本，核对关卡类型和提示指纹后发送对应的人话回复。
4. 交互脚本完成前，状态标记为 `waiting_for_scripted_human`，不计入自动化观测周期，也不因静默判失败。
5. Case 从“最后一次预期交互”转为 `running` 后，记录 `automation_observation_started_at`，随后每 120 秒采集一次状态、模型新增输出、事件、产物快照和质量信号。
6. 预期交互之外的请求必须暂停该 Case 并报告；不得使用推荐项替人工决策，也不得让其他 Case 代答。

### 3.3 结束与回灌

1. 先为每个 Case 固化 run、观测、阶段产物、交互回执、错误分类和哈希清单。
2. 通过验收的 Case 才进入回灌：复制其 `doc/features/<AR>` 和 Coding 阶段产生的受控源码差异。
3. 回灌前再次备份主工程中同名目标，回灌后执行文件哈希校验，并生成 `promotion-manifest.json`。
4. 失败、停止、provider 拒绝或工作区准备失败的 Case 不把半成品回灌主工程，只把完整证据归档到本轮结果目录。
5. 所有证据固化后删除临时工作区；删除前必须确认结果目录已有对应的文档产物、源码差异和清单。

## 4. 当前问题的处理结论

| 已暴露问题 | 本方案的根因修正 |
|---|---|
| 结果实际落在 `output/story/runs/...` | suite 根目录直接使用 `output/story/<时间戳-任务名>/`，Case 数据只放在其下 |
| 临时工程复制范围过大 | 改为白名单复制产品源码、必要配置、`framework/`、`doc/extensions/` 和 Case 输入；明确排除 `output/`、`test/`、`tools/`、历史 `doc/features/`、`.git` 和缓存 |
| “worker 已不在”导致交互无法回复 | 回复写入 suite 的明确 run 目录；进程存活仅作为诊断，不作为正常回复入队的前置条件；由 lease、reply 回执和 worker 消费事件共同确认 |
| AR91004 被 provider 内容检查错误直接判业务失败 | 增加 `provider_rejected` 基础设施分类；不把 provider 拒绝当 Story 语义失败，也不自动改写业务 prompt 绕过检查 |
| AR90004 在启动前因长路径失败 | 源码差异直接在独立工作区比较；源码事务和证据目录使用短临时根，不从长结果路径派生 |
| “等待人工”后无人推进 | 四个已知 Case 的交互动作预先写入脚本，由测试执行器自动承担人工角色；只有未知问题才向用户报告 |

## 5. 本轮不做的事

- 不启动新的 CLI 测试。
- 不执行单 CLI 基线。
- 不把 truth、rubric 或评测答案注入被测模型。
- 不修改 `framework/`、`test/story/truth/` 或产品源码。
- 不把失败或被停止的半成品直接写回主工程。
