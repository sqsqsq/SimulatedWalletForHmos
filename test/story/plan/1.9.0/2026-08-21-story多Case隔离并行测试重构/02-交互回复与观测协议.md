# 交互回复与观测协议

## 1. 交互原则

本轮四个 Case 的交互由测试执行器承担，不再把“等待人工”留给用户自行发现。测试执行器是测试中的人工角色，但不能替模型做业务判断：

1. 只在 Case 已声明的关卡回复。
2. 回复前核对 `awaiting_kind`、关卡标识、选项摘要和提示指纹。
3. 回复使用自然人话，不发送内部选项 key，也不固定发送“按推荐继续”。
4. 回复被 worker 消费后，记录 `reply_accepted` 和 `reply_consumed` 两个事件；只写入 reply 文件不算交互完成。
5. 发现未声明的人工决策、材料缺口或模型询问时，暂停该 Case 并报告，不把另一个 Case 的回复复制过来。

运行器的控制提示不再自动拼接到被测模型的业务 prompt。Case 原始 prompt 保持完整，交互规则放在宿主侧 `interaction-script.json`；这样不会用测试控制语句污染被测模型的行为，也避免把长控制提示截断成模型的首轮任务内容。

## 2. 四个 Case 的交互脚本

### 2.1 AR90005 / `split-two-ar`

- 类型：自动 Case。
- 处理：使用非交互模式既有的关卡自动回复，仅允许对 Case 声明的推荐选项执行自动推进。
- 观察重点：拆分选项是否完整摆出、本 AR 是否只认领一份、兄弟 AR 是否被正确留痕、Plan 是否承接同一边界。
- 不发送人工拆分决定；若模型要求真人重新决定，转为 `unexpected_human_decision`，暂停并报告。

### 2.2 AR90006 / `split-interactive`

按实际出现的关卡顺序执行，不按时间盲回：

1. 材料确认关卡：确认材料已充足，回复“材料充足，开始需求分析。”
2. 范围定法关卡：回复“这个需求本次只做其中一部分：按端侧特性切开，本单先做第一份，其余留给后续单据。”
3. 如果模型没有展示对应材料清单或选项，不发送下一句，先标记 `unexpected_gate_content`。

验收重点是模型是否把人话转成拆分条目、归属和下游范围，而不是是否机械匹配某个编号。

### 2.3 AR91004 / `source-conflict-review`

1. 等模型先展示同轮来源冲突和需要确认的版本，不预先替模型判断。
2. 冲突事实展示完整后回复：

   > 产品已确认离线时也要允许打开已缓存凭证；请把系统说明中的“必须联网”修正为“有可用缓存即可”，保留这次冲突与处置记录，然后继续。

3. 若没有先记录冲突就直接询问采用哪个版本，标记 `conflict_not_recorded_before_reply`，不把它当作正常通过。

### 2.4 AR90004 / `pattern-image-review`

- 类型：自动 Case。
- 不发送人工业务决定；自动关卡只使用既有非交互回复。
- 观测重点：图片链接、Plan 中模式实例、Coding 真实变更、Review 审查是否针对同一份变更。
- Provider 拒绝、工作区失败和编译环境失败均单独分类，不混入 Story 语义结论。

## 3. 观测时钟

每个 Case 单独维护以下字段：

- `interaction_state`: `not_started` / `waiting` / `complete` / `unexpected`
- `last_expected_interaction`
- `automation_observation_started_at`
- `automation_observation_until`
- `next_observation_at`
- `observation_count`

正式观测时钟的唯一启动条件是：

```text
最后一个已声明交互已被 worker 消费
    → Case 状态从 waiting_for_scripted_human 转为 running
    → 写入 observation_started_at
    → 每 120 秒观测一次，直到终态
```

等待交互期间可以实时读取事件和错误，但不产生“第 1 次/第 2 次正式观测”计数。静默不是失败；只要 lease 和 worker 心跳有效，就继续等待或按脚本推进。

## 4. 失败分类

报告必须区分以下结果：

| 分类 | 含义 | 是否可作为业务失败 |
|---|---|---|
| `business_quality_fail` | 模型已完成目标阶段，但产物不满足 Story/Spec/Plan/Review 判据 | 是 |
| `unexpected_human_decision` | 出现未声明的人工决策 | 否，判为测试协议阻塞 |
| `provider_rejected` | CLI/API 被 provider 内容检查、限流或服务错误拒绝 | 否，判为基础设施失败 |
| `workspace_prepare_failed` | 工作区、材料或路径准备失败 | 否，判为测试基础设施失败 |
| `worker_lost` | worker/lease 丢失且无法恢复 | 否，判为执行失败 |
| `stopped` | 用户或测试控制端明确停止 | 否，判为中止 |

AR91004 上一轮的 `400 InternalError.Algo.DataInspectionFailed` 应归入 `provider_rejected`，不能直接得出“来源冲突能力失败”。
