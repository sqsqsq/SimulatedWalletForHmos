# Codex 独立评审意见：Story 分批次交付总纲

> 状态：**独立评审定稿**  
> 日期：2026-08-25  
> 评审者：**Codex，OpenAI 提供的编程代理**。本轮作为 Story / Story Extension 方案之外的外层独立
> 评审者，只读取需求、历史方案、历史测试与本目录方案，不参与被评方案的编写或自证。  
> 评审对象：`00-总方案.md`、`01-全批次需求记录.md`、`02-已验证机制参考.md`、`03-踩坑记录.md`
> 及四个批次 `STATUS.md`。  
> 总体结论：**四批次方向成立，但当前不建议直接批准启动批次 1 设计；须先关闭 2 个阻断问题和 5 个
> 关键执行缺口。**

## 1. 总体评价

新方案比 `2026-08-24-story判据内容化与失效形态回归` 轮更有机会收敛，主要改善真实存在：

1. 把知识应用、内容去重、adapt、人读友好拆成四个交付批次，不再要求一次方案同时解决四类目标；
2. 把需求、已验证机制、踩坑记录分开，需求负责“必须实现什么”，历史机制只证明“某种形态曾经可行”，
   坑册只负责防止已知错误复发；
3. 已把三轮独立评审形成的纪律需求化：冻结后揭盲、全集语义裁决、来源单元覆盖、机械与语义责任分离、
   阶段状态分项和唯一总判定；
4. DTS90006 已正确降为实施前基线，不再冒充 holdout；
5. adapt 被隔离为第三批存量能力守恒，不再挤占本轮 Story 质量优化的主线；
6. 对“十章结构导致内容丢失”的怀疑先调查、后决定是否修改冻结需求，没有把假设直接写成结论。

因此，本评审不反对四批次划分及其优先级。当前问题集中在**批次怎样保持独立、前批验收怎样在后批改动后
继续有效，以及本轮需求到底以谁为准**。

## 2. 阻断问题

### P0-1：没有跨批次验收失效与重验协议，前批“已交付”可能被后批静默改坏

`00-总方案.md` §2 声明“每批把一个子系统从 1.0 升到目标态，批次间系统始终可运行、可独立交付验收”，
但四批并不是互不相交的文件子系统：

- 批次 1 会修改 Story 附录知识出口、写作指令、Spec/Plan 钩子和 verifier；
- 批次 2 会修改 Story scaffold/build/check/audit、review 与同一批写作上下文；
- 批次 4 会再次修改成文指令、章节组织、统稿和全量复核；
- 批次 3 的发布清单又要覆盖四宿主入口与整个 Extension。

后批触碰共享入口时，历史回归只能证明已知形态没有回来，不能自动证明前批的语义验收仍成立。当前只有
“以前一批验收结论为输入”，没有规定：什么改动使前批结论失效、需重跑哪些判据、是否需要新的 holdout，
以及谁更新前批状态。

必须在公共交付协议中增加**跨批次保护与失效规则**。不新增通用框架，直接复用各批 `STATUS.md`，每批收口
固定登记：

1. `protected_requirements`：本批已经验收、后批必须保持的需求编号；
2. `shared_entrypoints`：本批修改并可能被后批再次触碰的 Skill、hook、合同、装配器或报告入口；
3. `permanent_regressions`：后续每批必须重跑的台账项与正反夹具；
4. `behavior_evidence`：本批实际到达的阶段与行为结论，未到达项仍标“行为未验证”；
5. `invalidation_rule`：后批 diff 命中共享入口或改变保护需求的输入输出时，本批结论回到“待重验”；
6. `revalidation_result`：后批收口前重跑受影响的机械、语义和行为判据；若核心语义被修改，后批的新 holdout
   必须同时覆盖受影响的前批能力，旧 holdout 不得复用。

没有这套规则，“分批次”只是把同一大改动按时间切开，不能保证每批交付结果可持续成立。

### P0-2：本轮需求 SSOT 与冻结 spec 的优先级自相矛盾

`01-全批次需求记录.md` 开头同时声明：

- 冻结四份 spec 仍是“唯一真源”；
- `01` 是各批开工时的需求基线；
- `01` 合入了冻结之后的用户新增裁定和三轮评审需求化条目；
- 与冻结 spec 冲突时仍以冻结 spec 为准。

这会导致后来的明确用户决定可能被更早的冻结文本覆盖。例如 G2、B1-13、B1-14、B4-0 都是冻结后的
新增要求，旧 spec 并不能独立推出它们。实现者无法从当前表述唯一判断哪个文件是本轮真正的权威输入。

必须明确唯一顺序：

1. `01-全批次需求记录.md` 是**本轮分批交付的当前需求 SSOT**；
2. 冻结四份 spec 是原始需求基线和条款来源，不因重排而失效；
3. 冻结后的用户明确裁定在 `01` 登记后，作为批准增量优先于旧表述；
4. 评审意见只有在事实核验、被方案采纳并登记为需求条目后才具有约束力；
5. 后续批次若发现必须改变当前需求，先更新 `01`、说明受影响条款并取得用户确认，不能只在批次方案中
   静默覆盖；
6. 未发生明确覆盖时，`01` 中引用的冻结条款继续保持原语义。

如不接受 `01` 成为当前 SSOT，则必须把新增裁定正式更新进冻结需求区并重新冻结；不能继续保持两个文件都
自称最高权威。

## 3. 关键执行缺口

### P1-1：批次 1 仍包含三个可独立实施和验收的目标，存在再次膨胀风险

批次 1 同时包含：

1. 知识内容与激活：三类知识、规约瘦身、模式恢复、manifest；
2. Spec/Plan 应用：三出口、知识决策、义务与模式结构投影、全集语义裁决；
3. 下游传递：Coding、Review、UT、Testing 四阶段账本和真实证据。

这三部分有不同输入、实现入口和行为终点。若仍写成一份大方案、一次实现、最后统一验收，会复现上一轮
“范围虽然改名为一个批次，但内部仍然多特性交织”的问题。

建议保留“批次 1”作为用户交付单位，但开工时使用一份短总览和三份顺序步骤文档：

- 1A：知识内容、瘦身、模式基线与激活；
- 1B：Spec 识别与 Plan 实际应用、冻结；
- 1C：Coding/Review/UT/Testing 传递与行为验证。

每步有独立完成条件，前一步验证通过后才进入下一步；批次 1 的最终交付结论仍在 1C 完成后统一给出。

### P1-2：依赖表、通用说明和 STATUS 模板互相不一致

当前存在三种不同说法：

- 批次表称批次 2 只依赖批次 0、批次 1 结果“可复用”；
- B2 非目标又称知识判定逻辑“批次 1 已交付，本批只消费”，实际形成批次 1 依赖；
- 批次 3 被称为“相对独立”，但 §3 又说批次 2/3/4 均以前一批验收结论为输入；
- `batch-1/STATUS.md` 写“待前置批次验收结论”，但批次 1 没有前置业务批次。

建议固定为：

| 批次 | 实际依赖 |
|---|---|
| 1 | 批次 0 回退与公共设施验收 |
| 2 | 批次 1 验收；消费其知识出口，不重做知识判定 |
| 3 | 批次 0 + 当前累计发布文件树；语义上不依赖批次 2，但按用户优先级顺序启动 |
| 4 | 批次 2 来源单元数据 + 批次 1/2 的保护需求 |

同时分别修正四个 STATUS 的启动条件，不复用“待前置批次验收”这一模板句。

### P1-3：每批只规定“用户手动揭盲”，没有在揭盲前冻结行为终点

holdout 内容必须未知，但**验证能力形态和最低终点必须事先固定**，否则看到 Case 后可以选择较容易的终点，
或者只跑到 Plan 就声称下游四阶段已验证。

每批方案定稿时、holdout 揭盲前，应记录：

- 批次 1：至少一个 Case 实际穿过 Coding、Review、UT、Testing，验证同一冻结义务的四阶段证据；
- 批次 2：实际完成 Story 成文、audit、Spec 归档件与 review 回流处置；
- 批次 3：在隔离目标工程分别验证首次适配、升级、同版本重适配和无法识别 1.0 的确认路径；
- 批次 4：完成 Story 人读改写与来源单元全量复核，且不以长度或标题数量代替质量判断。

若某阶段未到达，可以诚实标“行为未验证”，但该批不能给出覆盖该阶段的完整 PASS。

### P1-4：产品回退到 1.0、测试域保留当前版本，缺少二者兼容验收

批次 0 会把 `doc/extensions` 与四宿主入口回退到 1.0，同时完整保留当前 `test/story/**`。当前测试 runner、
Case、状态识别、truth/夹具和报告能力经历过多轮 2.x 演进，可能读取 1.0 不存在的命令、字段、路径或凭证。

批次 0 除“1.0 命令兼容用例”外，还须增加**测试域 × 1.0 基座兼容矩阵**：

1. 当前 runner 能对 1.0 执行 plan 和隔离 workspace 预检；
2. 公共失效台账能区分“1.0 尚无该能力”与“目标能力回归”，不会在批次 1 开工前全量误报；
3. Case prompt 不调用 1.0 不存在的入口或字段；
4. 阶段状态、verifier 报告名、回灌与清理协议仍可读取；
5. 不兼容项在批次 0 显式登记并局部适配测试域，不能把测试基础设施失败误判为产品失败。

### P1-5：批次 3 的功能验收与最终 2.0 发布收口需要分成两种状态

`B3-4` 把最终 `releases/2.0.json` 指纹延后到批次 4，理由成立，因为后续 managed 内容仍会变化；但这不应
让批次 3 在批次 4 之前始终无法闭环。

建议批次 3 明确两个状态：

- `feature_accepted`：四条适配路径、事务安全、清单归属和独立交付已经通过功能验收；
- `package_finalized`：批次 4 完成后，以最终文件树生成 2.0 清单与指纹，执行整包发布回归。

前者是批次 3 的独立交付结论，后者是全四批完成后的发布动作，不能混为同一个 closure。

## 4. 文字与职责边界建议

`00` 说 `02-已验证机制参考.md` 和 `03-踩坑记录.md` “均非设计依据”，交付协议又说它们是下一批设计输入。
两句话可以统一为：

- `01` 是唯一规范性需求输入；
- `02` 是证据参考，证明哪些机制形态曾经有效及其边界；
- `03` 是负面约束和风险清单，要求方案证明不会复发，但不指定采用哪种实现；
- 后两者是设计时必须读取的证据上下文，不是决定目标或验收范围的需求 SSOT。

另外，`02` 中“DTS90006 明显好转”尚未逐分支计量，宜改成“观察到本需求专名增加，内容质量尚未完成
逐分支验证”，避免参考件在证据不足时提前作语义结论。

## 5. 建议的批准条件

满足以下条件后，建议批准总纲并启动批次 1 设计：

1. 明确 `01-全批次需求记录.md` 与冻结 spec 的权威顺序；
2. 在公共交付协议和 STATUS 中补跨批次保护、失效与重验规则；
3. 修正四批依赖关系与 STATUS 启动条件；
4. 批次 1 确定为一份总览 + 1A/1B/1C 三个可验证步骤；
5. 每批规定 holdout 内容揭盲前必须冻结的最低行为终点；
6. 批次 0 增加当前测试域与 1.0 基座兼容验收；
7. 区分批次 3 功能验收与最终 2.0 整包发布收口。

本文件只提供 Codex 的独立评审与优化建议，不修改当前总纲、需求、参考件或坑册，也不代表用户已经批准
方案重写、启动批次 0/1 或实施任何代码变更。
