### 3.2 作者输入：走扩展自己的入口，不占 `provides.knowledge`

上游给的通道是 `manifest.yaml > provides.knowledge`（原则 1 第 8 条）。**本扩展不用它**，理由是同名不同义：
本扩展的 `provides.knowledge` 同时是**知识激活清单**——`hooks/shared/knowledge.mjs` 第 291–324 行按各文件
frontmatter 的 `kind` 派生域前缀、条目与模式，清单全有全无、`kind` 封闭集合、派生为空 `throw`；上游 1.0 语义还要求
文件在 `knowledge/` 下并带阶段名。把 `hooks/<phase>/author.md` 塞进去会让作者要求参与知识派生。
**后果写明**：作者按第 8 条去 `provides.knowledge` 找作者输入会找不到，扩展自己的指引是唯一通道；goal 模式下没有注入——本仓不跑 goal 模式（`AGENTS.md` §0）。

改法：

- `manifest.yaml` 的 `provides.hooks.<phase>.on_context_load` **六处全部退场**；第 50–57 行「三个事件各有各的消费者」那段注释改写（不再有 `author-context.ts`）；`post_check` 与 `pre_verifier` 不动。
- `hooks/spec/author.mjs` 改成 **CLI**：`node doc/extensions/hooks/spec/author.mjs --feature <名>` 打印任务包正文。`on_context_load` 退场后没有人再调它的默认导出，`{promptFragments}` 那层包装一并删掉——不为「上游将来可能开通道」留接口。
- **指引写在作者一定读得到的三处**：`story_flow.py status` 的 `spec_write` 下一步文本（作者逐步跟的是它）；`SKILL.md` 第 151 行那一段；`skills/story/AGENTS.section.md` 第 5 行（`render-agents-md` 生成 CLAUDE.md 扩展段的真源）——都改成「动笔前跑这一条」，并列出六个阶段 `author.md` 的路径。

### 3.3 读者审查：留在 framework 的 verifier，扩展只改落盘核对

判据、任务书、注入都不动：overlay `story_reader_review` 一份判据；`pre_verifier.mjs` 把 `reader-review-task.mjs` 渲染的任务书注入 ai-prompt；verifier 一次审完。改的是报告的读法、写法、核对时点与严重级：

- **报告形态换了，读法跟着上游**：报告是调用方按 `summary.verifier_report` 原样写出的 MD，不再有插件 JSON；`summary.json` 在 **`<feature>/<phase>/reports/`** 下（`harness-runner.ts` 第 1964 行写在报告目录，`verifier-evidence.ts` 第 116 行同处读），扩展从那里取 `verifier_report` 路径。`hooks/shared/verifier-report.mjs` 的 `REPORT_JSON_RE`、`reportTexts`、`REPORT_TEXT_FIELD` 与文件头「只认发布器落盘的那一份」整段退场——身份锚是 framework 的 subject 校验（`check-receipt` 已核文件在、subject 对、verdict 与计数一致），扩展不重复核。
- **PASS 的写法按上游的输出契约，不设例外**：上游 verifier 定义与 `verify-spec.md` §七都规定「汇总表每项一行（PASS 也列，证据一行），YAML 明细只列 status ≠ PASS 的项」。扩展现在要求 PASS 也带 `blocking_findings: []`，与之冲突，正常 PASS 会被拒。改 overlay 的 `ai_prompt_hint` 与任务书末段：**PASS → 汇总表一行，证据格写「逐章过了什么」，不许空**（空证据与没审同形）；**非 PASS → YAML 明细一条 `id: story_reader_review`，`details` 下 `blocking_findings` 与 `advisories`**。落盘核对相应改成三条：汇总表有 `story_reader_review` 一行且证据格非空；该行 status ≠ PASS 时明细有那两个键；无逐单元裁决表。夹具两条：PASS 只有汇总行能过，FAIL 带明细能过、缺键不过。
- **写作检查与交付检查分开，按动作定要求，不靠文件在不在推断阶段**：`story-build check` 在登记前、返修中、交付前都会被调用，同一实现、两个入口。**普通 `check`**（登记 ⑤、返修）：读者审查那一块恒为 NOT_APPLICABLE——还没到审查。**交付检查 `check --deliver`**：先 spawn framework 的 `check-receipt.ts --feature <名> --phase spec`，退出码非 0 直接 FAIL（闭环没成立，含 verifier 未派、报告缺席、subject 失配、verdict=FAIL——这些都是 framework 的判断，扩展不重判）；退出 0 之后再读 `reports/summary.json` 的 `verifier_report`，按上面三条核报告内容。远程单：归档 ① 改成 `check --deliver`，在 ② 上传之前拦住；③ `archived` 自带的门也是 `--deliver`。本地单没有归档：`phases/spec.md` ⑧ 在 `check-receipt` 之后写「跑 `story-build check --deliver`，这是本地单的交付门」，`story_flow.py status` 在闭环态给同一句。`post_check` 里的 `storyReviewLanding` 删除，`verifier-report.mjs` 只被 `story-build.mjs` 引用。
- **通过的含义**：报告结构完整只说明读得懂，不说明能交付。交付门通过 = framework 回执通过（verdict PASS、blocker_count 0）**且**报告里 `story_reader_review` 一行在、证据非空、非 PASS 时两键在。`story_reader_review` 是 BLOCKER，它 FAIL 时 verdict 必为 FAIL，回执就过不去；夹具里「FAIL 带两键」只证明解析通过，交付门那条夹具要它被拒。
- **严重级与任务书对齐**：任务书写的是「（story_reader_review，BLOCKER）」，overlay 却是 `severity: MAJOR`——按新协议只有 BLOCKER 级 FAIL 才计入 `blocker_count`、才让 verdict=FAIL。改 overlay 为 `BLOCKER`：列了阻断问题就该阻断。
- 任务书与 overlay 里「结论由插件按你的终态发布」「不另写文件」两句删除（`reader-review-task.mjs` 末段、overlay 第 129–132 行）。

**失败怎么恢复**：verifier 对 story 报 blocking → `story_flow.py reopen`（唯一回退出口，撤销成文登记）→ 草稿上改章、`chapter`、`number`、`check` → `story` 重新登记 → harness → verifier 再审（材料变了，subject 换代，这是 framework 的正常返修，不是重复审）。`phases/spec.md` ⑧ 补这一句。

**⑦ 派不派只看 harness 末尾的 `NEXT:` 行**：它说 verifier 启用就派一次；说 `not_reviewed` 就直接 ⑧。`phases/spec.md` 与 `story_flow.py` 的 `SPEC_STAGE_ORDER` 照此改一句，不按宿主名分叉。
