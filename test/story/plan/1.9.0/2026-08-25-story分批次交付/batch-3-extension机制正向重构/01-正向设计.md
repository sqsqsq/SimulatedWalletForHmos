# 01 正向设计：把三个面的通道各归其位

> 状态：**设计稿（2026-08-28），待用户批准后按 [03-实施切分.md](03-实施切分.md) 另开会话实施**。
> 需求基线：冻结四份 spec（`test/story/spec/2026-08-21-story四项需求澄清/`）+ `../01-全批次需求记录.md` 的 G1–G10；本文 §11 逐条对应。
> 诊断依据：[00-机制诊断.md](00-机制诊断.md) C1–C6。本文只写目标形态与替代关系，不写实施步骤。
> 判据：**每个设计项都标注它删掉了什么**——`doc/extensions` 非知识层行数下降是完成判据之一（G7 之外的用户裁定）。

## 0. 一句话

作者只从作者必读的载体拿要求；义务写在下游本来就读的实体上；机器只判机器判得了的事、语义裁决必须附可核实引文；写 story、写 spec、审查各在自己的上下文里做；作者写之前就能看到全部结构判据，报错即指令。

## 1. 三个面与载体分配

| 面 | 谁 | 只从这些载体拿信息 | 不再从这些载体拿 |
|---|---|---|---|
| **作者面** | 阶段主 agent（写产物的那个） | 入口文件 CLAUDE.md/AGENTS.md 的实例扩展节（扩展自供 `AGENTS.section.md`）→ `/story` 作业包、`hooks/<phase>/author.md`、模板、上游产物、post_check 报错文案 | `hooks/*/on_context_load.md`（删除）、checker 源码、`.mjs` 脚本正文 |
| **判据面** | verifier 子 agent + post_check 脚本 | overlay `semantic_checks`（≤5 条/阶段）、`pre_verifier.mjs` 动态清单（≤5KB）、产物 | 作者写作指南、逐单元表 |
| **传递面** | 下游阶段 | 上游产物中的实体（spec §10/§11、contracts 实体 `must`、`files[].pattern`）与派生索引 | 平行账本（`knowledge_freeze`、手写 `knowledge.json`） |

## 2. 原则

1. **送达即义务**：对作者的每条要求，若不在作者必读载体里，视为不存在——不写第二遍到 hook。
2. **产物即接口**：义务写在实体上；机器索引一律派生。
3. **机械只判机器判得了的事，且要有区分力**（对 AR90004 现有产物必须命中已知违规）；语义裁决少而实，证据可核。
4. **分工即分上下文**：每个角色的输入包是明确文件清单，且 story 成文独立于 spec 会话。
5. **首跑即结构通过、报错即指令**：结构判据在模板/author.md 内联；报错文案给「缺什么 / 写到哪 / 示例」，一次报全。
6. 既有不变量保留：通过也留痕、派生为空出声、机制层零业务字面、约定形态是数据。

### 3.2 主 agent 须知 `hooks/<phase>/author.md` 及其送达（用户 2026-08-28 裁定）

术语：「作者」= framework 的主 agent 在某阶段**写产物**的身份（spec 写 spec.md/acceptance/decisions；plan 写 plan.md/contracts；coding 写源码…）；「审查者」= verifier 子 agent。`author.md` = 给写该阶段产物的主 agent 看的一页须知。

- **扩展侧文件**：`hooks/{spec,plan,coding,review,ut,testing}/author.md`，每份 ≤ 60 行，只含四段：读哪几个文件（≤3 个扩展文件）/ 产出形态（指向模板或实体写法，一个中性示例）/ 跑哪条命令 / 门禁会拦什么（一句一条，与报错文案同口径）。**不含**判据推理、示例长文、知识正文。它不是 hook：harness 不执行、manifest 不登记。
- **送达（全宿主一致）**：扩展交付 `doc/extensions/AGENTS.section.md`（≤15 行，机制类，adapt 整体覆盖）；子批 A 把它的内容直接写入本仓 CLAUDE.md 与 AGENTS.md 的「实例扩展」节（两份实例入口文件、同一段）；adapt 写入目标时同样写入目标的两份入口文件（`--check ⑤` 核）。正文三句：
  1. 需求流程入口：`/story <init|archive|restore|review|adapt|help> [AR]`；
  2. **进入 spec / plan / coding / review / ut / testing 任一阶段、动笔之前，若 `doc/extensions/hooks/<phase>/author.md` 存在，先完整读它**（本阶段要读哪几个扩展文件、产物里扩展要求的那几处长什么样、门禁会拦什么）；
  3. 各阶段 harness 会跑 `doc/extensions/hooks/<phase>/post_check.mjs`，报错文案自带修法，不需要读脚本源码。
- **为什么是入口文件而不是 rules 文件或 SKILL**：主 agent 会话开始时自动进入上下文的只有入口文件——claude 读 CLAUDE.md（+ `.claude/rules/*`），**codex 只读 AGENTS(.override).md，不加载任何 rules 目录**（官方文档），opencode/chrys 同。
- **删除**：`hooks/*/on_context_load.md` 六份（作者向内容迁 author.md，判据内容迁 overlay）。
- **与 adapt 的关系**：`AGENTS.section.md` 归机制类；adapt 写入时把它写进目标的两份入口文件，`--check ⑤` 核入口文件含该段（批次 2 已同步）。framework 升级会重渲染入口文件、覆盖这一段——extension 随之升级、adapt 重跑写入，段自然回来，不另设常驻检查（用户 2026-08-28 裁定）。

## 4. D2 传递面：义务落在实体上

### 4.1 `contracts.yaml` 实体级 `must`

```yaml
interfaces:
  - name: CardCloudAdapter
    methods:
      - name: createOrReuseLossApplication
        must:                                # 一条 = 一句可实施要求 · 规则编号 · 验证方式
          - text: 同一幂等键重复调用不得创建第二份申请
            rule: ENV-02
            verify: ut                       # ut | device | probe:<探针名> | review
components:
  - name: LossReportSheet
    must:
      - text: 方向性布局参数只用 start/end，禁止 left/right
        rule: UX-01
        verify: probe:absent_regex
files:
  - path: .../LossFlowOperates.ets
    pattern: decision-tree
    role: 节点表
```

- `must` 只允许挂在 `data_models[].fields[]`、`interfaces[].methods[]`、`components[]`（及其 `state`）、`resource_keys[]`、`files[]` 上；`text` 必须含本需求专名（复述判定沿用 `paraphrase.mjs`）；`rule` 须在册；`verify` 取值封闭。
- 没有实体可挂的规约（评审动作类）不进 contracts，只在 review 记录留痕（既有）。
- **前提核对**：`spec-loader.ts` 对实体级未知键的容忍（`normalizeArrayField` 只归一数组，未见白名单剔除；实施会话 F 条实测）。不容忍时，`must` 放 `plan.md` 各设计章对应实体的小节（固定小标题「必须满足」），coding 亦读 plan.md；派生索引改从 plan.md 解析。
- **删除**：`contracts.yaml.knowledge_freeze` 整块、`hooks/shared/freeze.mjs` 的账本读取、`hooks/plan/on_context_load.md` 的 schema 段、`plan/post_check.mjs` 里针对账本形态的判据（三重锚定、anchor 自指、集合差集）——改为「每条 spec §10 行在 contracts 至少一条 `must` 引用它；每条 `must.rule` 在 §10 命中集内」两条集合判据。

### 4.4 知识送达按阶段最小集

| 阶段 | 读 | 不读 |
|---|---|---|
| spec | 规约各域条目表（判命中）+ facts 画像/惯例 | 模式实现篇、落法附注全文 |
| plan | 命中规约全文（含落法附注与探针列）+ 候选模式选型篇 + facts | 未命中域 |
| coding | contracts（实体 `must`）+ 被选模式实现篇 | 规约文件、facts 全文（`must.text` 已带专名；需要封装名时读 facts 对应面） |
| verifier | overlay 判据 + 派生索引 | 知识正文 |

### 4.5 规约条目表增「探针」列（数据，随知识走）

`| 编号 | 约束 | 强制力 | 命中条件 | 处置 | 验证（执行体） | 探针 |`，探针语法封闭四种：

| 形态 | 语义 | 例 |
|---|---|---|
| `absent_regex:<re>` | `must` 所在实体的文件里不得出现 | UX-01 `absent_regex:\b(left\|right)\s*:` |
| `present_in_method:<re>` | `must` 所在方法体内须出现 | OBS-01 `present_in_method:Logger\.` |
| `referenced_outside_definition` | 实体在定义文件之外被引用 | 模式角色（由验证篇派生，不写在规约） |
| `count_eq:<re>:<n>` | 文件内命中次数恒等 | 模式「唯一 root」 |

无探针的条目 `verify` 只能是 `ut/device/review`。探针表达式是数据，`post_check` 不含任何规则编号；扫描 0 命中告警「形态可能不匹配本工程」。**「探针」列可缺省**（需求 E9）：目标工程的规约表没有这一列时按「无探针」派生，不 throw——否则已适配仓经 adapt 升级后老知识全部派生失败。

### 5.4 hook 自身可靠性

每个 post_check 顶层 try/catch：任何异常 → `{ok:false, severityOverride:'BLOCKER', message:'扩展门禁自身异常：…'}`，绕过 framework 崩栈降级；manifest 路径自检进 `spec` 阶段 post_check 首条（清空即 BLOCKER）。

### 6.5 守恒判据（`story-build check`，整篇）

### 6.6 核对记录三态（`audit.json`，冻结 01-C4）

| 态 | 谁填 | 机器判 |
|---|---|---|
| `at: <标题>` | 机器（token 命中的节）或作者 | 标题在册；作者填的须该节含单元 ≥1 token 或（散文）由 verifier 引文裁 |
| `covered_by: <单元键>` | 作者 | 目标存在、目标 `at` 非空、目标 ≠ 自己、共享 ≥1 token 或同 `also_in` 组 |
| `machine_facing: true` | 机器 | 只能由枚举器打标，作者不得改 |

三态之外 → FAIL；机器已给 `at` 的条目作者不得改成另两态；记录集合 = 单元集合；不进正文、不随归档。

### 6.7 语义与 review

- 语义只留 `story_reader_fitness`（四条，含「同一事实两处讲全」）+ `story_decision_substance`；每条裁决附 story 原文引文（§5.3 核实）。
- `review.md` 由 `decisions.json` 渲染（批次 2 的自解释语法保留：问题/建议或结论/为什么/影响/请谁确认/三勾选）；`decisions.json` 顶层 `scanned_categories` 六键，每键 ≥1 条目或 `none_reason`；`build` 校验。
