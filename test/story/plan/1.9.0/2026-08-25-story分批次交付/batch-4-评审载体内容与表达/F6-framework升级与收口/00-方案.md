## §2 D2 · verifier 报告协议适配（升级的唯一确定断点，维护者已定位）

**新协议事实**（main 版 record-verifier-report.mjs 头注释，维护者已读）：
报告按 subject 分区落盘 `verifier.report.<64位subject>.json`（＋同名 .md），
「**.md 只是人读投影，机器侧不解析**」；投递方式改为「runner 写短 request JSON，
主 agent 投给 verifier，verifier 按 `prompt_path` 自己读原件」；不再写
`.current-phase.json` 的 last_verifier_report。

**断点**：extension 的 `hooks/shared/verifier-report.mjs:23` 按固定名 `^verifier\.report\.md$`
匹配——新文件名带 hash，永远匹配不到 → `adjudicationProblems`（spec/plan 两个 post_check
消费）判「报告缺失」→ spec 闭环第三步必卡。

**改动**：
1. `verifier-report.mjs` 的报告发现逻辑改为：收集 reports 目录下全部
   `verifier.report.<hash>.json`，**机器面读 .json 真源**（不再解析 .md 投影——顺带修掉
   解析 .md 行的脆弱性）；多 subject 文件全收集合并判。裁决表义务（「固定表头逐行裁决」）
   映射到 json 结构：执行时先读 main 版 record-verifier-report.mjs 的 json schema
   （承载 verifier 输出正文的字段），把 `adjudicationProblems` 的行扫描对到该字段；
   json 里没有可扫描正文字段时（两分支处置）——退回解析同名 .md 投影并在差异栏登记
   「机器读投影的原因」。
2. `hooks/shared/pre_verifier.mjs` 与作业书（`phases/story-verify.md`、`phases/spec.md`
   的 verifier 触发段）对新投递协议措辞对齐——描述「短 request JSON＋prompt_path」的
   实际流程，删掉旧「ai-prompt 全文投递」表述。
3. 单测：伪造新格式报告文件（带 hash 文件名＋json 结构）跑 adjudicationProblems 正反各一；
   旧格式文件不再被认（防双轨）。
