## 六、装置：三处缺口在实跑中暴露并当场修复

### ① 凭据失效的真实报文认不出（`199b22b0`）

首跑两个 Case 在 30 秒内双双 `cli_failed`，`failure_kind` 记 `command_failed`，
三个配置只用了第一个，配置组一次没熔断。原因：阿里云返回
`{"code":"invalid_api_key","message":"Incorrect API key provided."}`，
而模式表写的是带空格的 `invalid api key`——两个都不匹配。

补两条签名后重起，**熔断切换当场生效**：bailian 熔断 → 干净基线 → attempt 2 切
volcengine，两个 Case 都自动完成，不用人管。用真实报文（含 request_id 的完整 JSON）
锁了回归。

### ② 挂起没有任何信号（`689607c7`）

auto-topup 的 CLI 请求发出去没回来，**70 分钟零事件产出**：进程活着、租约健康、
状态 running，装置每个指标都正常。配置组的重试等的是失败信号，而**挂起不产生失败信号**。

补 `events_idle_sec`（从最后一次产出算，与已裁掉的运行时限性质不同：时限从开跑算、
拦「跑得久」；这个拦「不再产出」，正常推进时每几秒一个事件，差三个数量级）
与 `stalled` 打标。按用户裁定：**只报警，不自动处置**——停滞是不确定态，自动重启会
把正在进行的工作丢掉。

### ③ 没有单 Case 重启入口（`689607c7`）

`stop` 遍历全部 case，`start` 只能新建 suite——而新建会清 `output/`，那会删掉另一个
正在跑的 Case 的 run 目录。补 `retry --case <id>`：人授权后重启一个 Case，走配置组
同一条链路（干净基线、attempt+1），其它一律不动。

实测处置 auto-topup 一次（重启到 attempt 3 从 story 重跑，全链跑完），**car-key 全程
未受影响**。过程中两处要记：
- 删 workspace 时 `WinError 32`（挂起的 CLI 仍持有文件句柄）——按 `Win32_Process` 的
  `CommandLine` 区分归属后只杀了 auto-topup 那个进程，没有盲杀；
- `command_retry` 首版把 suite 目录当 `suite.json` 传给 `save_suite`，已修。
