## §2 问题清单

### P1（回归）· 流程图被越界放宽，`car-key` 欠画三张

**事实**

`car-key` 的 4 个 diagram 单元全部 `at=业务流程`，story 只画了 1 个：

| 单元 | 来源节 | 内容 | story 里 |
|---|---|---|---|
| `SE:22:2c75dc86` | SR §2 发起分享时序 | `sequenceDiagram`，五方时序 | **压成 1–6 步骤散文** |
| `SE:49:b6046d03` | SR §3 分享状态机 | `flowchart LR`，六态 | ✅ 原样画了 |
| `SPEC:226:89c92a16` | spec §5.1 发起主路径 | `flowchart TD`，含签约失败分支 | **压成同一段散文** |
| `SPEC:245:e69a51f6` | spec §5.2 接受与撤销 | `flowchart TD` | **压成两段散文** |

这正是判据文案自己写的那句「把流程图压成箭头文字算降级」。

**机制原因（两层，缺一不可）**

1. **形态判是每章一个布尔，不是「分了几张画了几张」**：

   ```js
   if (u.kind === 'diagram' && !form.diagram) { …报… }   // 这一章有没有图？
   ```

   业务流程章有 1 张（状态机）→ `form.diagram` 为真 → 4 个单元一个都不报。
   `audit` 的形态欠账当时只报了表行（验收 11 行、范围 2 行），图一条没报。

   **这一层 F8 前后完全相同**，不是本轮改坏的——它本来就这么弱。

2. **F8 删掉了唯一能看见它的那一层**：

   ```js
   const storyDiagrams = (storyText.match(/^\s*(?:```|~~~)\s*\w+/gm) ?? []).length;
   if (sourceForm.diagram && storyDiagrams < sourceForm.diagram) { …报… }
   ```

**决定性实证**：用 F8 之前的脚本（`689607c7`）跑 `car-key` 这份产物（完整工作区，含 `assets/`）：

```
95. 材料里有 4 张图，story 里只有 1 张——数量不该少于源
```

**F8 前拦得住，F8 后拦不住。删的就是这一条。**

**范围判定：这是越界**

内网问题 7 的原文是：

> PRD 里有 **30+ 图片**，模型被逼把所有**图片**往 story 里硬塞。澄清：以 story 的叙述逻辑
> 来正确引用图片，而不能要求所有图片必须在 story 里存在……

**只讲图片，没有一个字提流程图。** F8 却把两条数量判据一起删了：

| 删掉的判据 | 内网 7 要求吗 |
|---|---|
| `imgs.length < sourceForm.image` —— 图片数量不降级 | ✅ 要 |
| `storyDiagrams < sourceForm.diagram` —— **流程图**数量不降级 | ❌ **没有任何内网问题要求** |

**坏掉的恰恰是不该删的那一条。**

流程图与图片在这件事上性质不同：PRD 里图片可以有 30 张（每个界面一张），流程图通常
只有三五张，而且 story 自己重画时早有 `covered_by` 兜着——**它从来没有「硬塞」的压力**。

#### S1c 与 `02-方案-重写.md` §4 的冲突——显式推翻，不含糊过去

`02-方案-重写.md` §4「明确不做的事」里有一行：

> | 任何数量 / 比例 / 上限判据 | 逼引与逼不引同为 Goodhart。3a/3b 是逐单元的结构判，不是计数 |

**S1c 直接与它冲突**：它恢复的正是一条数量判据。这里显式推翻那一行，并写清为什么：

那一行的 Goodhart 论证**只对图片成立**，写它的时候把两类混为一谈了：

| | 图片 | 流程图 |
|---|---|---|
| 材料里的典型数量 | 可达 30+（每界面一张） | 三五张 |
| 「塞满」的代价 | 把 PRD 复刻一遍 —— 内网 7 的原话 | 画三五张图，本来就该画 |
| 有没有实测的硬塞证据 | **有**（内网 7） | **没有，一次都没有** |
| 删掉之后的实测后果 | 图片两个 case 全对 | **`car-key` 4→1** |

Goodhart 的成立条件是「指标压力大到扭曲行为」。30 张图的复刻压力足以扭曲；
三五张流程图的压力不足以扭曲，而**删掉它的代价已经实测到了**。

所以 §4 那一行的正确表述应当是「**图片**不设数量判据」，而不是「任何」。
本轮按这个更正执行；`02` 文件本身不改（它是已实施基线，改它会丢失当时的判断记录）。

**这一条必须写进 `06-交付报告.md`**：否则下一轮读 `02` §4 的人会认为 S1c 违规。

**为什么 F8R 没做**：`02-方案` §4 判定它「不在内网九条里」，且直接降级会让「review 里真·承诺
交付机制」无人接管（反例 N6 证明当前拦得住）。

**正向解法（按结构分区，不降级、不加词表）**

`review-render.mjs` 已经有现成的分区标记：

| 标记 | 语义 |
|---|---|
| `HUMAN_ZONE_MARK = '审核结果：'` | 这一行之后到 `<!-- decision: ID -->` 是人工区，build 一字节不动 |
| `<!-- freeform-zone -->` … `<!-- /freeform-zone -->` | 「其他意见」章，人写 |

**规则一：人工区不判禁用词。** 归档件红线管的是**这份文档对产品的承诺**；评审人写在
「审核结果：」后面的意见、和他写在「其他意见」章里的话，都是**人的表态**，不是产品承诺。
F7 那条「不同意时改什么：文案回退为」正落在这一区。

**规则二：机器区里，属于「上线 / 管控」类别的议题块豁免。** 与 story 的章级豁免
（合同 `banned_terms_exempt`，「交付与上线」章）同构，由 `decision_categories` 数据驱动：
`交付顺序与协同`、`入口与管控` 两类议题的澄清正文里，讲开关放量与回退路径是本职内容。
F7 那条「上游约定：分享功能开关默认关闭，随版本放开」正落在这一类。

**规则三：其余机器区照拦。** 反例 N6（review 正文写「本方案采用灰度发布」而不属上述两类）
必须仍然报——这一条是本项的硬门。

### S6 · 术语消歧参照物（原 D8-2）—— 根因比原以为的更基础

**原判断被推翻**：`04` 初稿写「从 spec §8 功能映射表推导」。实测证明 **§8 是验收标准，
spec 里根本没有「功能映射表」这一章**（章序为 §2 场景 / §3 功能清单 / §4 页面 / §5 流程 /
§6 异常 / §7 非功能 / §8 验收）。这条推导源不存在。

**实测出的真根因**：术语判据拿**整个单元格**去 story 里做子串匹配，而术语单元格普遍带括注：

```
301. spec 术语映射表里的这些业务实体词在 story 里找不到：
     数字车钥匙（车钥匙）、车钥匙分享（分享）、钥匙卡片（卡片详情）、
     配额（剩余可分享数）、权限档（全功能/仅解闭锁）、分享状态…
```

逐个验过（本轮 `car-key` 产物）：

| 术语单元格 | 整串在 story | **去掉括注后** |
|---|---|---|
| 数字车钥匙（车钥匙） | ❌ | ✅ 「数字车钥匙」在 |
| 车钥匙分享（分享） | ❌ | ✅ |
| 钥匙卡片（卡片详情） | ❌ | ✅ |
| 配额（剩余可分享数） | ❌ | ✅ |
| 权限档（全功能/仅解闭锁） | ❌ | ✅ |

**这不是消歧参照物问题，是判据把括注一起拿去匹配。** 一次报 12 个词全是这个成因。

**改动**（`story-build.mjs` 的 `missingGlossaryTerms`）：匹配前把术语单元格的**括注剥掉**，
用主名去核（`数字车钥匙（车钥匙）` → `数字车钥匙`）。括注是给读者的同义提示，不是要求
story 逐字复述的内容。

**消歧参照物那一半**：剥括注之后若仍有「本需求不做、只为对照而列」的词报缺失，
**本轮不再加豁免标记**（那是 F8 首版 D8-2 的补丁形态）。先看剥括注能消掉多少——
按实测这一条就能消掉 12 个里的绝大多数；剩下的记入遗留，等有真实样本再谈。

### S7 · 沉积清理（原 D9）

**诉求**：内网 8 的伴生——「错误激增到 1000+ 然后把台账删了」，洪水本身构成删除激励。

**放宽账（P1 表格）**

## §5 为什么这不是打补丁

### 5.1 改动方向是减，不是加

| | 补丁的形态 | 本方案 |
|---|---|---|
| 动作 | 在出问题的地方**加**一条检查 | 把越界扩大的范围**收**回去 |
| 代码量 | 净增 | **净减**（`IMAGE_KINDS` 少一个成员、落点判少一个条件） |
| 新概念 | 常有 | **零**（不引入任何新状态、新字段、新判据类型） |

S1c 恢复的那条判据是 F7 跑了整整一轮、产出 3 张与 6 张流程图的机制，**有正例基线**，
不是新发明。

### 5.2 它消除的是范围错误，不是症状

P1 的根不是「流程图判据不够强」，而是**内网问题 7 只讲图片，实施时把流程图一起放宽了**。

修法直接对准这个根：**恢复原状**。不是在放宽之后再加一层补救检查——那才是补丁。

### 5.3 图片侧不受影响，两类各自按自己的性质处理

改完之后两类的规则不同，而这个不同**有依据**：

| | 图片 | 流程图 |
|---|---|---|
| 材料里的典型数量 | 可达 30+（每界面一张） | 三五张 |
| 硬塞的压力 | **有**（内网 7 实证） | **无**（从没有人提过） |
| 合法出路 | `at` / `covered_by` / `material_only` | `at` / `covered_by` |
| 数量判据 | 已删（内网 7 诉求） | **恢复** |

「两类规则不同」不是特例，是它们的**材料形态本来就不同**。用同一套规则处理，才是把
不相干的两件事绑在一起——F8 首版正是这么错的。

### 5.4 更通用的方案存在，但不在本轮

审计中识别出一个更通用的形态：把形态判从「每章一个布尔」改成「每章每类，画出数 ≥ 分配数」，
图片、流程图、表格同一套粒度，并且**计数来自作者自己的分配**（`material_only` / `covered_by`
随时可降低它），因此不会退回硬塞。

**它不在本轮**，理由：

1. 它是**新判据形态**，需要新的反例夹具与新的验证面；
2. 本轮的主题是**收回越界**，先回到已验证过的状态，再谈通用化；
3. 我们已经在「一轮里做太多」上栽过一次（F8 首版六处放宽同时上）。

若要做，它应当单独一轮，配自己的 P1 放宽账与反例夹具，记入遗留清单。
