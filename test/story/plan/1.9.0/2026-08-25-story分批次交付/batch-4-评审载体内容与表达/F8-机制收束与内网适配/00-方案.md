## §2 D2 · 知识 README 纯索引化（对内网问题 3）

**失效假设**：README 既当路由又当规则书——同一句判定信号存在于三处（README 路由表、
模式文件 frontmatter `applies_when`、模式文件上篇 §1/§2），是「同一要求出现两处即合并」
（D9-2 纪律）的知识版。内网「README 描述不对」的实证可能基于 F7 前的包版本（F7 已修
零命中行，当前仓 README:27-28 与模式 frontmatter 几乎逐字同源），但**结构病与用户裁定
方向（README 纯索引）不因版本消解**——只要判定语言存在多处，漂移就会再次发生。

**真源指定**：判定唯一真源＝模式文件**上篇**（完整信号、反例、选型）；frontmatter
`applies_when/not_applies_when` 是上篇的**一句话机器投影**（`hooks/shared/knowledge.mjs:202`
消费它做域级命中与必答集派生，保留，不展开）——维护纪律一句写进 README③章：改上篇
时同步 frontmatter 投影。README 路由表的信号描述行退场。

**新形态**（内网模型已验证的结构，采纳）：README 只留四章——
① **设计模式**（定位一段：`pattern_id` 受控声明、粒度切分——「适用单元」表并入此章）；
② **模式清单**（id/文档链接/一句话「解决什么」/依赖——现有清单表保留）；
③ **候选登记规则**（通用规则集中于此：零命中举证要求、「不要复述判定语言」、输入源
口径「信号来自业务流程本身」、双读者说明——这些是 F5/F7 的既有内容，**移位不删义**）；
④ **多模式组合**（通用组合纪律保留，表内不出现具体模式名之外的展开）。
**退场**：路由表里逐模式的信号描述行（「业务流程有多个分支，每个分支自身是多步的…」）
——判定唯一真源＝各模式文件上篇「适用与选型」，README 在③章写一句「逐模式的命中
信号与反例，读对应模式文件上篇」。`spec-sections.md` §11 注释同步指向。
**模式文件不动**（上篇内容本就完整）；`plan/post_check.mjs` 与激活链不涉。

## §3 D3 · 流程推进契约（对内网问题 4、5、9）

**失效假设**：全链推进的授权只存在于 CLI 测试的 prompt 里；交互式使用时，模型在
「extension 说照 next 继续」与「主仓红线 8（BLOCKER）说阶段边界须明示授权」之间
择保守停等——init 后问要不要进 spec、check 报错问要不要修、check 过后问下一步。

**授权分两层，不混为一谈**（framework 的推进门禁是
`framework/harness/scripts/utils/phase-transition-policy.ts`：`resolveTransitionPolicy`
解析**用户消息**命中 `BATCH_PHRASES` 才给批量授权，否则 manual——extension 文本
不进这个解析，SKILL 里写「启动即授权」改变不了 framework 侧的 policy 结果）：

- **extension 流程段与阶段内**（framework policy 管不到的地方——init→spec 入口、
  check 修复循环、check→harness→verifier 衔接）：SKILL 授权文本**有效**，见下三条。
  内网问题 4/5/9 全部发生在这一层。
- **framework phase 之间**（spec 闭环→plan 及之后）：不造与 framework 打架的第二套
  授权。走 framework 认可的途径：story S4 收口时，若用户目标越过 spec（如「做到 plan」），
  提示用户在下一条消息里给出批量授权语（命中 BATCH_PHRASES 的表述），或经
  `phase.next_step` 确认点一次拿到范围授权——一次问代替逐段问。

story SKILL.md 新增「**推进契约**」一节（一处定义，各 author.md 只引用不复述），三条：

1. **授权语义**：用户启动 `/story` 流程即构成红线 8 所称的「明示授权」——授权范围＝
   **story 契约 `next` 覆盖的段**（SKILL 链条图：S1→S4→spec 闭环→S5 归档；`next`
   不驱动 plan 及之后，那属 framework policy 层，见上）。段内推进不逐段询问。
2. **停等点白名单**（此外一律不问）：材料缺口需人补料；范围变更（scope_gate 触发）；
   同一 check 连续 3 次未收敛（报样本与已试修法后停）；归档等破坏性动作的既有确认点。
3. **裁决衔接链**：`story-build check` 通过 → 阶段内「读 author.md → 写产物 →
   主 agent 自跑 harness → 结构级 PASS 后主动触发 verifier」是**同一条义务链**，
   链内无停等点；check FAIL → 按报错文案修复并重跑，直到通过或触发白名单第 3 条。

## §4 D4 · 工程标识 token 的落点改道（对内网问题 6）

  守恒核对范围＝**附录机器面区**；audit 分配时此类 token 从叙事落点剥离、进入附录
