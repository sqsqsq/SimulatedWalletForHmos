# 01 正向方案（知识贯通与评审件精简轮）

> 状态：**设计定稿（待批准实施）**。本文按「从 0 实现需求」写目标契约；不描述被替换实现的细节，废弃做法只在 §9 以「错误 + 教训」留档。
> 用词：本轮是**重写**——凡判为不合理的构件整体重写，不在其上叠判据。

## 0. 本轮纪律

1. 机制层零知识、零业务、零测试特征；派生优于枚举（域、模式角色、编号含义、验证执行体全部从知识数据与 manifest 派生）。
2. **声明不是应用**：任何「知识已应用」的结论都必须投影为契约实体或阶段证据，并被机械校验存在。
3. **显式不适用优于静默跳过**：某阶段对某条义务无事可做，必须写明理由；缺席即 FAIL。
4. **同一事实一处登记**：正文、附录、评审件、图片、编号含义都只有一个真源；其它位置只引用或派生。
5. 不设形态配额（冻结需求 02-C2）；不改 `framework/`。

## 1. 目标契约总览

```
spec ──判命中/登记候选──► story 附录单表 + spec §7 应用域约束要求 + review（派生编号对照）
                                      │
plan ──先冻结后设计──► contracts.yaml > project_knowledge（唯一载体，含 instance/roles/landing）
                                      │
        knowledge-ledger.mjs（从载体 + 规约「验证列」派生每阶段账本）
                                      │
coding / review / ut / testing ──识别账本 → 阶段形态应用 → 同编号留证──► 各自 post_check 机械判
```

## 2. A · review.md

### 2.1 结构（自上而下，固定）

```
# <单号> 决策与评审记录
## 请逐项留下你的结论        （open 议题，机器区 + 人工区）
## 已定决策（请逐条过目）     （settled 议题，同上）
## 计划外意见                 （freeform 区，保持）
## 附录：编号对照            （派生，见 2.2）
## 下一步
请勿删除原结论或覆盖历史意见。
**状态**：草稿（待开发确认）
```

无「怎么填」章。人工区三行选项的括注就是填写说明。

### 2.2 编号对照（派生，不登记）

- `idDictionary(ctx)` 返回 `{id → {title, kind, force?}}`，来源两处：
  - **spec 编号**：按合同 `id_conventions.spec_id_shapes` 扫 `spec/spec.md`；标题取法按出现形态：表格行首格是编号 → 取下一格；`**AC-1** (F1): 文本` → 取冒号后文本；`### S1 标题` / `S1「标题」` → 取标题；截 60 字于标点处。整份 spec 0 命中 → 告警「编号形态可能不匹配本工程，检查合同 id_conventions」。
  - **规约编号**：`knowledge-rules.mjs` 新增 `constraintEntries()`——从 manifest 激活的 `knowledge/constraints/*.md` 的「条目」表取（编号列, 约束列, 强制力列），按表头名定位列，不按位置。
- review 附录行 = 议题 `impact[]` ∪ 机器区文本中出现的编号，逐行「编号 | 标题与含义」；字典查不到 → build 失败并点名议题。
- `ids.json` 取消（scaffold 不再生成；读到时忽略并告警一次）。`{{ID:x}}` 占位符保留，渲染改查字典：表内出「标题」，散文出「“标题（x）”」。
- 决策件质量门：`source` 含「无上游依据」且 `status=settled` → build 失败：「本工程设定的值必须是开放决策，请人表态」。

## 3. B · story：附录单表、图片唯一、守恒按名、去重

### 3.1 附录（合同 `10-appendix` 重写）

- responsibility：「读者核对完备性时来查：每条应用域约束在本需求里是命中还是不涉及，命中的落在哪里。」
- must_answer：「各应用域约束**逐条目**判定：命中/不涉及 + 依据或落点」。
- transcribe_note：「附录只有一张表；『要求』列写 `{{ID:编号}}` 由装配器渲染，不手抄规约原文；正文各章只写中文规约名。」
- 表形态：

```
| 域 | 编号 | 要求 | 命中 | 结论或落点 |
| 可观测性 | DM-01 | {{ID:DM-01}} | 是 | 签约流程带流程标识与步骤标识（见业务流程） |
| 交付物 | 全部条目 | — | 否 | 无新增对外页面与接口；文案翻译已列入… |
```

- build 校验（全部派生）：manifest 激活的每个规约域在表中至少一行（域名取域文件 H1）；编号在字典；「否」行的「结论或落点」非空；不允许出现第二张含规约编号的表或含编号的小节标题。
- 删除四处「两张表 / 兼容性自检」文案：`story_on_context_load.md`、`constraint-usage.md`（整节改写为单表写法）、`evidence-rules.md`「合规判定」节、`ar_design_init.md:110`、`compatibility-checklist.md:8`（改为「本域条目与其它域一样逐条判定」）。

### 3.2 图片全篇唯一

- `assemble()`：同一图片路径（规范化后）引用 >1 → 装配失败，消息列出两处行号，引 rules.md「一个事实一个主叙述位置——图也算」。
- scaffold 视觉清单头注：「每张图全篇只引一次，引在最该回答它的那一章；别处需要时用一句话回指。」
- audit 增列「重复引用」。

### 3.3 守恒扫描改按名不按号

- 守恒对象 = spec 中反引号包裹的技术名（接口、存储键、配置项、事件名、错误码、路由名）+ 功能清单表每行的功能名称；story 全文任意位置出现即守恒。
- 不再要求 S/F/E/AC/BD/NFR 编号出现在 story；`id_conventions.spec_id_shapes` 只服务于 review 字典与标题单号校验。
- 注入件表 D 新增禁止形态「编号清单段」；check 新增 WARN：一段内 ≥3 个 spec 编号且无谓语动词（按「：」后仅编号+顿号判）。
- rules.md §7 改写为「可按名回查的事实不丢」。

### 3.4 决策引用渲染

- 不截断。表内：`值`；散文：`值（待 <decider> 确认，见《决策与评审记录》）` / `值（已定，见《决策与评审记录》）`。
- decider 规整：去尾部「确认」「拍板」；空则渲染「待确认」。
- 同一段落中作者又手写了该决策值里的数值（带单位）→ build 失败：「决策值只由占位符渲染一次」。

### 3.5 去重与人读

- 合同章责任收紧：
  - `06-features`：页面、动作、状态与**正常受限结果**（入口不可见、不可点属此章）；
  - `07-exceptions`：**真正失败**后的用户表现、业务结果、恢复方式；不重述规则；
  - `08-acceptance`：怎样观察到做对了——只写观察方式与通过条件，不复述行为规则。
- check 新增 WARN「跨章重复句」：规范化（去标点空白）后 ≥18 字的句子在 ≥2 章出现，列出位置；只告警不阻断（重复的最终判断按 01-C2 由人/verifier 定）。
- 注入件表 B 加：「一个规则只在一章讲清，其它章一句承接回指；禁止『在两处都写明』。」
- 表 D AI 味清单补：空评价句（「这是…的核心/关键/纪律」）、工作件语言（份 N、本单、走查、命中路径）、括注堆叠；「只引用《决策与评审记录》里实际存在的议题」。
- D3：有序列表/厚度保留 WARN，不加配额。

## 5. D · 下游三段式（coding / review / ut / testing）

### 5.1 账本派生（`hooks/shared/knowledge-ledger.mjs`）

```
ledger(projectRoot, feature) → {
  obligations: [{ rule, obligation, landing[], anchor, verifyBy: {model:boolean, device:boolean} }],
  patterns:    [{ pattern_id, instance, roles{} }],
}
```

- `verifyBy` 从该条目「验证（执行体）」列派生：文本含「模型」→ model；含「实机」→ device；两者皆无 → 两者皆 true 并告警「验证列未声明执行体」。
- 缺 contracts 或缺 `project_knowledge` → 返回 null，下游零注入（保持「宁可不送不送错」）。

### 5.2 识别（`active-knowledge.mjs` 冻结门槛后的注入）

不再只列知识文件名；渲染账本：

```
## 本次冻结的知识义务（唯一入口：plan/contracts.yaml）
### 规约义务
- DM-01 流程标识…  落点：data_models.AutoTopupSignContext.flowId, …  本阶段：<按阶段>
### 设计模式实例
- decision-tree · AutoTopupSignFlow  角色：节点表=…, 步骤枚举=…, …  本阶段：<按阶段>
```

「本阶段」文案按类型 × 阶段取消费语义表；仍附各义务所属域文件的分区（落法附注/结构与落地）供细读。

### 5.3 应用与留证（各阶段 post_check，机械判）

| 阶段 | 产物 | 判据 |
|---|---|---|
| coding | 代码 | 每个 `landing`/`roles` 指向的文件存在，且文件文本含该实体名（类名/字段名/方法名/键名）；缺 → BLOCKER |
| review | `review/review-report.md` | 存在「知识落实审查」节；每条义务编号、每个模式角色各一行，含 PASS/FAIL 裁决词与 diff 位置（文件:行）；缺行 → BLOCKER |
| ut | `use-cases.yaml` / `acceptance.yaml` / `ut/` 报告 | 每条 `verifyBy.model` 义务出现在某 `branches[].linked_acceptance` 或 acceptance BD 的 `knowledge:` 字段；否则 ut 报告「知识用例」节须有「<编号> 不适用于 UT：<理由>」；两者皆无 → BLOCKER |
| testing | `testing/test-report.md` | 每条 `verifyBy.device` 义务一行「结论 + 证据（截图/数值/日志）」；否则「<编号> 待验证：<阻塞原因>」；两者皆无 → BLOCKER |

### 5.4 传递

- 四个 overlay（coding/review/ut/testing）的语义判据改写为「逐条冻结义务与角色核对」，判据来源写「本阶段注入的冻结账本」，不再「逐份知识文件逐域核对」。
- `post_verifier` 不变（保证 overlay 判据被裁决）。
- 义务在下游无法实现 → 报告写「返回 plan 更新冻结」，不静默改（03-C5）。

## 6. E · 测试方法

- `run_case.py::phase_evidence_complete`：verifier 凭证 = `reports/` 下任一匹配 `verifier.report.md` / `verifier-report.yaml` / `verifier-*-result.yaml` / `verifier-*.md`。
- 阶段预算：记录 `(next_phase, 连续次数)`；同一 `next_phase` 连续续话 > `PHASE_TURNS[next_phase]` 且 `highest_phase_reached` 未推进 → 终止，`stop_reason=phase_turn_budget_exhausted`；同一续话指令连续 3 轮且该阶段目录（排除 reports/）内容哈希不变 → `stop_reason=no_progress`。
- `run_multi_case.py poll`：`awaiting_reply` 存在时 `next_interval_sec=15`（无论稳定态）；`adaptive_reply_requests[]` 每项携带 `question`（模型最后输出的等待段原文 ≤1200 字）与 `case_inputs_hint`（本 Case 公开输入文件清单）。
- TEST.md：§3 增「`awaiting_reply` 出现的那次唤醒内必须完成回复；跨唤醒记入观测记录为协调失误」；§5 增「凭证文件组」「stop_reason 语义（phase_turn_budget_exhausted / no_progress / awaiting_reply_timeout）」。
- 单测（`test/story/tests`）：凭证组任一命中即闭环；阶段预算终止；awaiting 间隔 15。

## 7. F · AGENTS.md §2 增补

- 声明不是应用：知识冻结必须投影为契约实体（角色/落点）并机械校验；anchor 自引用不算落点。
- 知识决策先于设计：阶段附加的知识决策章位于其消费的设计章之前。
- 同一事实一处登记，图也算；编号含义派生不登记。
- 出口不枚举域：规约产生的要求按命中条目派生落点。
- 守恒按名不按号：代理判据不得成为门禁。
- 显式不适用优于静默跳过。

## 9. 错误方案留档（只记错误与教训）

| 错误做法 | 教训 |
|---|---|
| 编号含义靠 `ids.json` 人工登记 | 手抄制造第二真源且必然漏；含义能从规格与规约派生就不该登记 |
