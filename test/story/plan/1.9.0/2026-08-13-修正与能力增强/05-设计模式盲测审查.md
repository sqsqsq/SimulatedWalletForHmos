# 设计模式盲测审查与修订 · 记录（已实施）

**问题**：M2 交付的两份模式文档，plan 侧（选型）合格，**coding 侧不合格**——
文档三次强调「引擎/装配器框架已提供、不许重写」，却从未说它们叫什么、怎么调。
**「不许重写 X」而不给 X 的名字，等于逼着违反**：编码模型只有两条路，
手写推进循环（恰是文档自己列的反模式）或编造一个 import（编译失败）。

## 审查方法：盲测

三个无写作记忆的只读 agent，只给指定文档 + 一份现成契约，要求写出可落地代码，
并标注**每一处凭空猜测**、按危害排序。这比作者自查有效——作者读自己的文档时
带着未写下来的记忆，判断不了冷启动模型能不能照做。

| | 场景 | 首测结论 |
|---|---|---|
| A | coding 消费 decision-tree | 「需求侧三个文件的形状能写对，**框架侧那一半完全写不出来**」，14 处发明 |
| B | coding 消费 page-interaction + 叠加 | 「**有等待态的场景下无法正确落地**」，14 处发明 |
| C | plan 消费（拆单元、路由、投影） | 三个单元全判对，投影字段齐整——**上篇有效** |

## 修订

### 1. 写实框架接口（根缺口）

两份下篇各补一段 `interface` / `declare class` 形式的**接口契约**：
节点三型 `root`/`nonLeaf`/`leaf`、`DecisionTreeBuilder`、`fireEvents`、
`PageOperates`、`PageInteractionBuilder`、`operateSequence`。
标注「**符号名与包名以内网框架为准，形状不变**」——名字错了改一行 import，
没有名字则整段代码建立在虚构类型上。骨架同步改为可编译的完整装配示例。

### 2. 动作与状态分离（page-interaction 的核心修正）

原文把「交互项枚举」既当动作表的键、又投影到 `state_model.phases`。
揉在一起时「停下等用户」只能用「链路结束」那个返回值表示，于是同一个 `undefined`
背着终态、挂起、查表落空三种语义——**盲测实证这里会静默跑穿等待态**：
用户没点同意、没输验证码，编排器一路推到创建合约，且不报错。

拆开后：**动作枚举** → `ui_bindings.user_actions`；**状态枚举**（含等待态）
→ `state_model.phases`。等待与恢复的语义随之自然成立：

- **一段推进** = 一次门面方法调用，直到某动作返回 `undefined`；
- **等待** = 本段自然结束、状态停在 `Waiting*`；
- **恢复点就是下一个动作自己**——框架不必记住「停在哪」，没有 `resume` 这回事。

### 3. 等待不进树（叠加的结构性修正）

复测 B 抓到我引入的矛盾：`DecisionTree.fireEvents(ctx)` 无 `from` 参数、
`setRoot` 装配期固定，而当时叠加规则把含等待态的 `phases` 判给了树 →
一条被等待切成多段的流程，树侧表达不出来（写成 `nonLeaf` 跑穿、写成 `leaf` 起不来、
用 root 分派又撞上「自己写 switch」的反模式）。

**正解不是给树加 `from` 参数打补丁，而是把等待从树里彻底排除**：
一棵树表达「一段跑到底、中途不停」的流程；**等待是段的边界**。
一条中途等两次的流程 = 三棵各自跑到底的树，切点由门面的动作决定。
叠加时字段归属随之改为：`coordinator` / `ui_bindings` / `state_model` / `branches`
**全部归交互门面**，树的节点枚举不进契约（退为门面内部实现）。
两份「与…叠加」节改为逐字镜像——首测 B 卡住的原因正是两份不对称、
一份写了 `coordinator` 归属另一份漏了。

### 4. 产出信号：命中模式即产出

framework 侧存在两套阈值（`plan-workflow-detail.md:44` 四条件、
hmos-app `use-cases-schema.md:21-24` 三条件，④在后者无锚点）。
由此可推出死锁：只亮④的单元（单页多次输入、有等待态、无第二 UI 节点、无回滚、
无云调用）命中 page-interaction，但按三条件阈值不产出条目 → 投影无处可落。

framework 只读改不了，实例侧的修法是在 README 列出**五条产出信号**，
第⑤条是「命中本目录任一模式」——模式命中成为独立的产出理由，死锁不再可能。
（`check-ut.ts : usecase_spec_recommended` 仅 MINOR 推荐，多产出不违反任何门禁。）
同时定义「UI 节点」含页面、组件、**模态弹层**——它决定阈值①是否成立。

### 5. 其余（盲测逐条）

`operateSequence` 的写入方与内容、`root` 是否计入、异常穿出 `fireEvents` 的行为、
装配点（页面 `aboutToAppear` 里 `new`）、方法签名的出处（`data_boundaries[].methods`）、
决策点「只判定不执行」界定为「不**写**」、`user_sequence` 写门面方法名、
`coordinator` 写类名、首屏动作也算一条 `user_actions`、
coding hook 路由到 use-cases schema。

**两处 ArkTS 硬伤**（复测抓到，是我写的骨架本身的 bug）：
构造参数属性 `constructor(readonly x: T)` ArkTS 不支持（本工程代码从不这么写）；
计算属性键改为与枚举值同名的标识符键——`Record<E, …>` 的穷尽检查照样把键错与漏项
变成编译错，且不依赖 ArkTS 对计算键的支持。
