## 1. 为什么新增本规格

本轮实跑已经验证 Story 的章节骨架、层级能力和 Markdown 表达形式有所改善，但又暴露出两个独立问题：

1. Story 的信息内容基本正确，章内标题与正文措辞却仍有明显的 AI/契约转写痕迹，不符合正常需求文档的编辑习惯。
2. CLI 重复使用 `doc/features/<feature>` 作为需求产物工作区，历史产物容易被覆盖；若历史产物继续留在工作区，又可能影响下一轮被测模型判断。

## 2. Story 标题与叙述风格诉求

### 2.1 已确认的问题

当前 Story 采用“固定 H2 主线、模型编写 H3/H4”的结构，这个职责划分保留。问题不在内容正确性，也不在标题层级数量，而在模型把隐藏的写作问题或工程术语直接写成了面向人的标题。

典型例子：

| 当前表达 | 正常需求文档表达 |
|---|---|
| 为什么现在要做 | 需求背景 |
| 给谁带来价值 | 需求价值 / 业务价值 |
| 本轮怎样才算成功 | 需求目标 / 成功标准 |
| 本轮边界 | 需求范围 |
| 本 AR 承载什么 | 本期建设内容 |
| 物理改动落在哪里 | 系统影响范围 |
| 依赖谁 | 外部依赖 |
| 方案骨架与关键取舍 | 方案概述 / 设计思路 |
| 谁阻塞谁 | 关键依赖 / 上线前置条件 |
| 验收追溯（功能 → 验收） | 功能验收标准 / 功能与验收要求 |
| 异常 → 验收/处置映射 | 异常场景的处理与验收 / 异常场景验收标准 |

正文中反复出现的“本 AR 承载”“当前处置”“唯一真源”“能力占位”“模拟/契约层交付”“影响范围”等表达，也需要区分是否适合进入面向人的主叙述。工程事实可以保留，但应翻译成读者能自然理解的业务或系统含义；检索、审计和机器契约语言应收敛到系统章节或附录。

标题不得直接描述生成或追溯机制。“箭头 + 斜杠 + 映射”是在解释机器关系，不是在告诉读者本节内容；机器追溯关系可以保留在表格字段或隐藏合同中，面向人的标题应直接说清业务对象及阅读目的。

“异常 → 验收/处置映射”不仅标题不合格，当前用 `E1→AC-1` 一类编号关系压缩正文的内容形态也不合格。若异常处理与验收信息已在正文分别讲清，该节不进入 Story，机器映射留在 `acceptance.yaml` 或契约真源；若确有独有信息必须呈现，则使用“异常场景｜用户表现｜系统处理｜验收重点”的人读表格，不能要求读者来回查编号。

### 2.2 目标表达模型

- H2 主叙述顺序继续由 Story 编辑合同稳定定义。
- H3/H4 继续由模型依据具体需求组织，不把每个子标题写死。
- `reader_question` 只作为模型背后的写作提示，不得直接转写成问答式、口语式标题。
- 章内标题采用正常需求文档中稳定、简洁、可扫描的专业名词性表达。
- 正文按人的理解顺序解释背景、价值、范围、方案、场景、体验、风险和验收，不把 Spec/Plan 字段换序后直接铺陈。
- Story 的信息正确性、完整性、追溯性与人类编辑质量分别评价；结构门禁 PASS 不代表叙述质量 PASS。

### 2.3 编辑模型边界

- H2 由章节合同提供稳定主线，H3/H4 由模型按当前需求组织。
- 子章节是否继续拆分，取决于一个阅读单元中是否存在多个独立主题。
- 标题质量与叙述质量采用人读语义评价，结构脚本负责标题层级和装配完整性。
- Story 和 `review.md` 面向人，其余阶段产物面向 AI。

### 2.4 跨轮内容保真

本轮与上一轮 `cross-component-rich` Story 对比表明，重组和去重之外仍有独有信息被压缩或发生漂移：

- 完整用户旅程由“挂失→冻结→支付→制卡→通知→领取”缩短到“已冻结待支付”，兄弟 AR 的后续链路只剩短引。
- 上轮明确 AR90005 依赖本 AR 产出的 `applicationNo` 与冻结结果；本轮却写成双方互不阻塞，并出现一次 `AR50005` 笔误。
- 支付、通知、客服的参与方责任和失败边界被压缩为“归兄弟 AR，不调用”。
- “无可用卡片”空态、上下文超期后的用户恢复路径缺少等价的人读落点。
- 页面中的卡片信息、隐私说明、主按钮、不可申请禁用态和结果页下一步说明等体验细节被过度概括。
- 本地上下文字段结构与后续接口边界等附录信息有所减少。
- 无上游依据的性能默认值跨轮漂移：上一轮为首屏 2 秒/请求超时 5 秒/交互 300 毫秒，本轮变为资格查询 P95 2 秒/首屏 1 秒/交互 300 毫秒。

后续评价必须区分“删除重复”和“删除独有事实”。允许改序、合并与短引，但每条独有的业务事实、协作关系、用户状态、恢复路径和已登记决策都必须在新 Story 或配套 `review.md` 中保留唯一的人读落点；同一输入下 AI 自设决策值不得无依据漂移。

内容守恒的权威输入是**本轮原始材料、最终 Spec 和已登记决策**。上一轮 Story 只用于回归时发现可能的退化，不能反过来成为需求真源；上一轮写错、漏写或自行增加的内容不得因“历史已有”而继承。

### 2.5 Story 与 Spec 的人读信息对账

`story.md` 不是 `spec.md` 的摘要，但最终 Spec 中影响人理解和评审需求的事实必须在 Story 或 Review 有自然落点，包括：

- 用户行为、业务规则、范围与跨参与方边界；
- 页面、流程、状态、异常、失败恢复和兼容行为；
- 数据、接口、配置、隐私、DFX、上线与外部依赖对人产生的影响；
- 人可以据此判断是否正确的验收口径与风险。

纯机器字段、内部 ID、完整 schema 和只供编码定位的路径可以留在 Spec/契约或 Story 附录。需要人决策的内容进入 `review.md`；已经确定、但影响需求理解的事实仍须在 Story 正文解释。对账复用原始材料、最终 Spec 和已登记决策，由模型和独立语义评价完成；脚本负责确定性的结构与路径。

### 2.6 图片链接能力

- 本轮保证的是**仓内最终 `AR/story.md`** 的本地图片链接：装配、改序和迁移后，相对路径仍能从 Story 所在目录解析到真实文件。
- 图片须保留替代文本；必要时增加简短图注，正文说明图片与当前需求的关系。
- 构建检查只机械验证链接语法、目标存在和路径未越出该 feature 的允许资产范围，不判断图片内容是否正确。
- `archive` 按现有合同处理 Story/Review；本轮图片验收对象为仓内最终 Story。

## 3. 历史需求产物迁移诉求

### 3.1 已确认的简单规则

- 备份根目录固定配置为 `E:\Project\bak`。
- 一条全新 CLI 测试链启动前，只处理该 case 对应的 `doc/features/<feature>` 目录。
- 历史目录存在时，直接迁移到备份根目录，目标目录自动增加时间戳，例如：
  `E:\Project\bak\AR90004-20260819-140305`。
- 历史目录移动后持续保留在备份根目录。
- 本轮新生成的需求产物继续保留在 `doc/features/<feature>`，供同一测试链的下游阶段使用。
- Story→Spec→Plan→Coding→Review 的同一条链内部续跑时不迁移；下一条全新测试链开始时，才把上一轮产物迁走。
- 若时间戳目录重名，追加短序号或 run-id，保证每轮备份唯一。
- 迁移范围固定为当前 case 的单个 feature 目录。

### 3.2 目标效果

1. 被测模型在新一轮开始时看不到上一轮同 feature 的历史产物。
2. 每轮完整需求产物都能在仓外保留，便于人工逐轮对比。
3. 分阶段续跑直接消费本轮工作区中的上游产物。

## 5. 下一轮设计模式命中场景

### 5.1 测试目的

下一轮正式测试需要调整原始业务需求，使功能与场景本身自然具备两类设计模式的适用条件，用于观察
Spec 是否识别信号、Plan 是否完成选型与契约冻结，以及 Coding/Review 是否按真实模式与 SDK 落地和核查。

当前场景中，页面已经包含身份前置、资格判断、确认、结果、重试和客服等由业务结果驱动的交互，
`page-interaction` 存在较强的自然命中信号；但挂失主流程的各业务分支仍以短路或单步处置为主，
尚不足以稳定命中 `decision-tree`。下一轮应通过真实业务复杂度补足后一类信号，并保持前一类信号清晰可见。

### 5.2 原始需求的正向设计原则

- 被测模型可见输入只描述用户目标、业务规则、外部系统行为、失败恢复和验收结果。
- 模式预期、SDK 映射和判定依据保存在 case truth 与评价侧。
- 主业务流程应自然包含多个具有独立业务价值的分支；每个关键分支包含真实的多步云侧调用、状态落库、
  失败收敛，以及必要的撤销、补偿或恢复路径。
- 同一核心页面应自然包含多个用户等待点和后续动作；登录/实名、风险确认、费用确认、提交、失败恢复等
  动作的先后应由业务结果决定。
- 两类复杂度共同服务于挂失与补卡业务的完整用户目标。

### 5.3 观测与判定

- 测试输入只提供业务事实；模式命中预期保留在测试域真值与评价侧。
- Spec 按流程段和页面/组件划分适用单元，登记真实候选证据。
- Plan 中的模式选型实际改变主体设计，包括实例职责、上下文所有权、等待点、交接、失败收敛、
  SDK 依赖和契约骨架；应用表与结构化契约负责汇总和冻结。
- Coding 应能从冻结契约追到真实 SDK 类型和代码结构；Review 应核查模式约定与反模式，而不只检查
  `pattern_id` 是否出现。
- 评价同时审查适用单元划分、业务证据和因果理由。

### 5.4 正式验证范围

- 主正例包含本地图片和两类模式的自然业务事实，运行 Story→Spec→Plan→Coding→Review。
- 自然负例运行 Story→Spec→Plan，验证逐单元拒绝和与需求相称的设计复杂度。
- UT/Testing 在本轮完成同源知识消费的离线合同验证，真实执行由内网后续承担。
- 正式测试完成后提交报告并结束本轮执行。

## 6. 工程知识必须在 Plan 实际生效并向下游传递

### 6.1 本轮暴露的根因

设计模式文档已经按 Plan、Coding、Review 区分了适用判断、结构落地和审查约定，但本轮出现了阶段内容
不可达：Plan 仅依据模式总表提前判定零命中，没有读取具体模式文档的 Plan 部分；随后
`pattern_applications: []` 被冻结，Coding 与 Review 按空集合直接跳过，导致模式文档中已经存在的各阶段
指导全部失效。

同类风险也存在于应用域规约：若 Plan 主体完成后才补写一张处置表，表中结论可能没有改变数据模型、
接口、状态、组件、依赖、恢复策略或验证设计；下游即使读取到 rule_id，也只能自行补设计，破坏阶段边界。

### 6.2 正向阶段链路

目标链路固定为：

`Spec 业务事实与信号 → Plan 独立重建适用单元/适用域 → 读取 Plan 阶段知识 → 改变 Plan 主体设计
→ 一致性复核 → contracts 冻结 → Coding 按冻结实例读取落码指导 → Review 按同一实例读取审查约定`。

应用表和 `project_knowledge` 不是事后“回显”，而是对已经进入 Plan 主体的选择、设计处置与下游义务
进行索引和冻结。若主体没有发生与结论相符的设计变化，不能形成有效冻结。

### 6.3 Plan 生效判据

- Plan 必须在规划文件、接口、组件、状态和依赖之前完成第一轮适用性分析；深入设计发现新事实时再复核，
  最终结论不能直接继承 Spec 的命中或零命中判断。
- 每个真实存在的流程段、页面或组件适用单元都保留独立结论；“存在适用单元但不采用模式”与“没有适用
  单元”必须分开表达，禁止用一行“无适用单元”吞掉 Spec 候选。
- 对每个可能匹配的模式，在最终采用或拒绝前读取其 Plan 部分的 `applies_when`、`not_applies_when`、
  契约投影和适用/不适用说明；不能用总表摘要提前结束判断。
- 采用模式必须实际改变 Plan 主体中的实例职责、角色、上下文所有权、动作/节点、等待点、交接、失败
  收敛、文件与 SDK 依赖；拒绝模式必须基于完整业务事实给出反证。
- 命中规约必须先转化为需求化设计决策，再进入对应的数据、接口、配置、资源、异常恢复或验证设计；
  rule_id 只用于定位来源，不能替代设计。
- Plan 主体、应用表、正式 contracts、acceptance/use-cases 和 `project_knowledge` 必须双向一致；任何一处
  只有编号或文字声明、其它产物没有对应对象或行为，均不视为已生效。

### 6.4 下游传递与纠错

- Coding 以冻结的模式实例和规约义务为执行输入，按实际 ID 读取对应文档的 Coding 部分，并沿锚点落实
  到真实 diff；不能只在注释或回执中声明已遵守。
- Review 读取同一冻结实例的 Review 约定，逐项核对真实代码结构、SDK 行为边界和规约义务，不能只查
  ID 是否出现。
- Coding/Review 发现 Plan 漏选、错选或义务无法落地时，当前阶段的对应语义检查输出 `FAIL`，并把根因说明为
  `correction.layer=plan`。随后复用 framework 既有 `--correction-init`、`.current-correction.json` 和
  `--correction-check`，按现有确认规则完成 Plan 修正与下游重验。
- verifier 必须从 Plan 主体的流程、页面动作、状态与协作关系独立重建适用性，不能引用 Spec/Plan 自己
  的结论作为通过证据。

### 6.5 实施边界

- 阶段闭环使用现有 Plan 原生产物、contracts、framework correction 流程和实例扩展 hook。
- 所需调整落在 `doc/extensions/`、应用工程实例配置与 `test/story/`，`framework/` 保持字节一致。
- 本节记录优化目标与判据，实施以本目录方案经用户确认后为准。
