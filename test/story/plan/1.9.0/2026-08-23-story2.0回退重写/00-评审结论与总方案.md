## 2. 评审结论

### 2.1 骨架判定:方向正确,重建而非推翻

2.0 骨架的每个构件都有冻结条款背书,重写保留骨架、干净重建:

| 构件 | 冻结背书 |
|---|---|
| 固定十章章节合同(含 responsibility) | 需求1 C3(十章各自回答什么问题) |
| 删除每章 form 形态配额 | 需求2 C2 L42(不设 Markdown 类型/数量配额) |
| 四段成文法(全局规划→逐章→统稿→复核) | 需求2 C3 L51-59 |

| decision-tree / page-interaction 两模式原件恢复 | 需求3 C8 |

### 2.2 错误方案记录(只记错误与教训,不记废弃实现细节)

废弃的 2.0 实现处于半途双轨态:已落地门禁与待实施修正互斥并存、离线全绿掩盖行为未验、行为验证无承接台账。逐项教训如下,全部转化为目标契约或负面断言(01 §6):

| # | 错误 | 教训(进入新方案的形式) |
|---|---|---|
| F1 | 机械层"上游守真"检查建立在错误方向假设上(spec 声称的须在上游存在),误伤合法新增接口;报错文案与实际语义相反 | 上游守恒只做语义判据+写入侧指令,不建机械层(G1);报错文案即契约 |
| F2 | review 人工区标记改名未全链兼容,历史产物假失败 | 定位逻辑单源;双标兼容,读旧写新 |
| F3 | 自称 SSOT 的知识消费矩阵无任何代码读取,语义存两份靠人肉同步 | 矩阵必须被机制真实解析;禁止平行硬编码语义 |
| F4 | 机制层硬编码工程路径,工程配置变更时静默失效 | 路径一律读配置;失效必须响亮 |
| F5 | 同一批需求的门禁与写作指令互斥落地(H1 编号、规约编号两处正反打架) | 判据与指令同批同向一次成型 |
| F6 | 章构收敛(14→10)后旧章名坐标残留多处悬空引用 | 结构收敛必须全仓 grep 清零 |
| F7 | review 表单改形后写作指令/回流规则/报错文案仍是旧口径 | 同一契约的全部消费方一次同步 |
| F8 | 矩阵引用的知识分区名在知识文件中并不存在;README 计数与实际不符 | 跨文件引用名以脚本核对 100% 存在 |
| F9 | 注入件形态迁移时静默丢失条款;自写解析器失败时静默漏裁决 | 迁移前后条款清单比对;解析失败必须响亮,禁止静默空结果 |
| F10 | 死代码、矛盾注释、与实现脱节的头注不变量大量堆积 | 注释即契约:与实现不一致即缺陷,验证时走查 |
| F11 | 版本指纹清单两版路径约定不一、基线标注取自开发中间点 | release 路径约定单一;基线注明等价验证点 |

## 3. 重写原则

1. **基座**:`doc/extensions` 与四宿主 story 跳板整体回退到 `19977c98`(D4),在其上按 01 实施计划正向重建;回退前先把现工作区完整临时归档提交(素材保全,含 3 个 untracked 文件)。
2. **正向实现(D5)**:每个重建对象先立目标契约(行为口径,从冻结 C 条款+G 决策推导),实现对契约负责、不对任何废弃实现负责;方案自足,不记录废弃实现细节;F 缺陷以负面契约断言证伪(目标态不得含有),不以"修复项"形式存在。唯一例外:两个设计模式正文按冻结 C8 要求取归档**原件逐字节恢复**(原件早于 2.0,非废弃实现)。
3. **test/story 测试域全保留**(含未提交的 cleanup 软警告改动)——它是测试+demo 能力域,与 extension 版本正交,不在回退范围。
4. **版本语义**:交付物仍是 2.0(manifest `2.0.0`);`releases/2.0.json` 在全部离线验证通过后最后定指纹。
5. **文档纪律**:本轮文档不修改历史轮次设计文档;与历史文档冲突处以本轮为准,冲突点已在 §1/§2 登记。
