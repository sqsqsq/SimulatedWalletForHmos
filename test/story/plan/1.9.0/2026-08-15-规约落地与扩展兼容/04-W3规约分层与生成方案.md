# 规约分层与生成方案

> **性质**：方案，待评审。**未建目录、未写脚本、未改任何现有文件。**
> **要解决的**：① 规约准确性未在真实代码仓验证过；② story 要尽快合入真实仓跑；
> ③ 后续维护如何避免改坏（尤其被消费方引用的条目）。
> **配套**：核查结论见 [`09-规约事实核查台账.md`](../2026-08-14-全流程验证与规约消费/09-规约事实核查台账.md)，25 处修正见 `03-W2规约核查修正方案.md`。

## 1. 结论先说

采用**生成式两层结构**：`constraints-source/` 是唯一真源，`constraints/` 由它生成。
迁移不是复制，是**改一个状态字段 + 重新生成**。先用**首批入驻集**（10 条，已逐条人工确认）
跑通「source → 生成 → 内网跑 story」这条链路，再批量入驻。

原始设想是双层目录 + 人工复制迁移。**一处必改：双份正文手工同步必然分叉。**
本轮已三次实证同类事故——知识文件内嵌消费方用法导致两处各自演化（README 禁 slug、
各文件却要求 slug，无人发现）；design-patterns 的 hook 删除后 README 仍指着它；
COMPAT-04 删除后 `evidence-rules.md` 仍引用。`03-` 方案里的 25 处修正若在双份正文下落地，
每处都要改两遍，漏一遍即分叉。

## 2. 「被引用」不构成最小集的下限

原判断是"被消费方引用的条目必须留在正式目录，否则断链"，因此最小集受引用关系绑架。
**这个判断是错的。**

核查了那 9 处功能依赖（`APP-01/03/07`、`DFX-02/04`、`TEL-04/05/06`、`COMPAT-12`），
它们全是**落点映射**——"这条规约的结论写到产物的哪个位置"。而
`skills/story/reference/constraint-usage.md` 开头已经定义了通用的**三个出口**：
结论回显落 story 两张表、代码要求落规格件 §7、待某方确认落决策件。

于是 `evidence-rules.md:54`「对照 `dfx-baseline:DFX-02`」不过是通用规则的一个**实例**。
把实例枚举进规则文件本身就是多余——与上一轮修掉的「UX-01～06」范围记法是同一个病：
**该说通则的地方去枚举了个例。**

**所以硬引用应当消除，而不是迁就**（步骤 0）。消除后最小集可纯按验证状态划分。
这也解释了"被引用"与"最重要"为何对不上：它反映的是消费方文档当年写得不够抽象，
不反映规约本身的重要性——UX-01 深色红线、SEC-05 权限红线按重要性显然该留，却都不在引用集里
（它们本轮未入驻是另一个原因：内容有已知偏差，等 `03-W2` 修正后再议）。

## 3. 机械约束（设计须绕开）

| 事实 | 对设计的含义 |
|---|---|
| loader 只按 manifest 声明加载 knowledge，绝不扫描目录（`framework/harness/extension-loader.ts:153-174`） | 新目录不登记 manifest 就不会被投喂给模型 |
| `constraint-usage.md:59`「逐个读取 `knowledge/constraints/` 下**全部**约束文件」 | 暂存区**不能**做成 `constraints/full/` 子目录——模型会顺着这句口头指令读进去；同级目录安全 |
| `test_constraint_consumption.py:241` 的过滤是 `"constraints" not in p.parts` | `constraints-source` 这个名字**躲不过**，源文件会被当成"消费方"扫编号——须改过滤 |
| `test_knowledge_purity.py:61` 断言域文件数**恒为 9** | 正式目录缩小即红，须改为断言 source |
| `ConstraintAuditRulingsTest`（`:168-213`）按文件名硬读 5 个域 | 这是**裁决断言**（MODE-04 已删、MaskUtil 非 FormatUtil 等），须改指 source——生成物是影子，对影子做内容体检没有意义 |
| `ReferencedIdsTest.prefix_to_file()` 路径硬拼 `MATRIX.parent` | README 文件清单若保留已移出域的行 → FileNotFoundError |
| `export_delivery_patch.py:78` 的 INCLUDE 只显式列 `doc/extensions/knowledge/constraints` | 同级目录天然不打包；但按该脚本 `test_every_boundary_entry_states_its_reason` 的纪律，仍须在边界表登记理由 |

## 4. 目标结构

```
doc/extensions/knowledge/
├── constraints-source/          ← 自包含的规约维护套件，不登记 manifest
│   ├── AGENTS.md                ← 维护规约（不生成、不投喂）
│   ├── README.md                ← 源版，含全部 9 域
│   ├── <9 个域文件>              ← 条目表加「状态」列 + 新增 `## 档案` 节
│   └── scripts/generate.py      ← 生成器，与源同行
└── constraints/                 ← 生成物，登记 manifest，进交付，勿手改
    ├── README.md
    └── <仅含有 applied 条目的域>
```

### 4.1 三类文件的职责

| 文件 | 读者 | 生成进正式目录 | 投喂给执行模型 |
|---|---|---|---|
| `AGENTS.md` | 改规约的人与 AI | 否 | 否 |
| `README.md` | 执行规约的模型 | 是（删行后） | 是 |
| `<域>.md` | 执行规约的模型 | 是（滤条目后） | 是 |

**判据一句话：执行模型需要知道的进 README，只有维护者需要知道的进 AGENTS.md。**
例如"条目怎么从 `draft` 变成 `applied`"——执行模型永远只看得到已 applied 的条目，
它不需要知道状态机，故归 AGENTS.md。

**source/README 与正式 README 是全集与子集**。README 内容分两类：

- **恒定部分**（条目字段模型、执行体四类、强制力语义、读条目须知）：原样透传；
- **随入驻集变化的部分**（文件清单表、适用矩阵表）：生成器**只删行**。

⚠️ **边界**：「本目录是源、正式目录是生成物」这句话**不写进 source/README**——
它会被生成进正式目录，让规约重新背上维护信息（与删「出处」列同源）。
生成物的"勿手改"头注由**生成器注入**，不在 README 源里。这句话的家是 AGENTS.md。

### 4.2 脚本落位

**原则：脚本跟着它服务的内容走，测试跨目录引用它。**

`test/` 是**评测框架的维护域**（harness、看护测试、交付工具），服务的是"story 这个能力
做得好不好"，与规约体系无关。生成器若放 `test/`，会把源与其工具拆开——
谁拿走 source 而没拿 `test/`，就无法重新生成。

**仓内先例**：`doc/extensions/skills/story/scripts/` 放 skill 运行时脚本，
测试从 test 侧用 `sys.path.insert(0, str(REPO_ROOT / "doc" / "extensions" / "skills" /
"story" / "scripts"))` 引入（`test_story_mock_materials.py:102`）。本方案沿用同一模式。

套件自包含的好处：**交付与否成为一个独立开关**（INCLUDE 加不加这一项），
而不是被目录位置绑死。

⚠️ **生成器纪律**：`export_delivery_patch.py` 的 docstring 声明"只读仓库、只往仓库外写"，
而生成器**要往仓内写**。故生成器须立自己的纪律并写进 docstring——
只写生成目标目录、不碰其他文件、不 commit、不 checkout。

📝 **命名**：原设想为 `constraints-full`，本方案用 `constraints-source`——
"source"表达"唯一真源"这一关键性质，"full"易被读成"另一份全量副本"
（正是要避免的分叉联想）。可改回，不影响设计。

### 4.3 源文件格式

条目表增一列「状态」：

```markdown
| ID | 约束 | 强制力 | 命中条件 | 处置 | 验证（执行体） | 状态 |
|---|---|---|---|---|---|---|
| UX-01 | 深色模式下所有界面元素可读 | 红线 | … | … | … | applied |
| UX-02 | 折叠屏、平板、多窗口下布局不破版 | 基线 | … | … | … | pending-verify |
```

新增 `## 档案` 节（**生成时整节剥离**），承载此前从规约移出的内容：

```markdown
## 档案

### UX-01
- **核实**：官方直证（`ide_color-value`、`ui-dark-light-color-adaptation`）
- **原始诉求**：上游 story 模板规约 §3.2 页面设计
- **真实仓验证**：<待验证>
- **引用情况**：见 AGENTS.md 的查询命令（不维护静态清单）
```

### 4.4 状态阶梯

| 状态 | 含义 | 生成进正式目录 |
|---|---|---|
| `applied` | 已入驻 | 是 |
| `pending-verify` | 内容已核实，等真实仓验证 | 否 |
| `draft` | 有出入 / 无官方出处 / 待修正 | 否 |
| `blocked` | 明确不适用或搁置，编号保留不复用 | 否 |

### 4.5 生成规则

```
for 域文件 in source/*.md:
    applied = [行 for 行 in 条目表 if 行.状态 == 'applied']
    if not applied: 跳过该域（不生成文件）
    输出 = 删「状态」列 → 只留 applied 行
           → 删 `## 档案` 整节
           → 落法/判定附注中属于非 applied 条目的 bullet 按 ID 前缀剔除
           → 头部注入 `<!-- 由 constraints-source 生成，勿手改 -->`
README = source/README 删掉未生成域的「文件清单」行与「适用矩阵」行
```

**防漂移断言（关键）**：重新生成的结果须与仓内文件**逐字相同**，手改生成物即红。

### 4.6 AGENTS.md 承载什么

1. 本目录是唯一真源，`constraints/` 是生成物，勿手改生成物；
2. 状态定义与流转条件（入驻准入：平台条目须官方直证，应用专有条目须业务确认）；
3. **迁移由 AI 执行的步骤**：改状态字段 → 跑生成 → 跑测试 → 导出交付（不是人工复制）；
4. `## 档案` 节的填写要求；
5. **引用不可删的契约 + 查询命令**（不维护静态清单——手工清单会与真实引用漂移，同一个病）：
   ```
   grep -rnE '\b(UX|MODE|SEC|APP|DFX|TEL|COMPAT|ENV|DLV)-[0-9]+' doc/extensions \
     --include=*.md --include=*.yaml | grep -v knowledge/constraints
   ```
6. 防漂移纪律与断言位置。

#### 覆盖面自检

| 维度 | 覆盖 |
|---|---|
| 表制 | 条目表 ✓、场景表 ✓（ENV 两条） |
| 强制力 | 红线 ✓（SEC-06）、基线 ✓ |
| 执行体 | 模型 ✓、实机 ✓（UX-04 切阿语走查）、人工 ✓（DLV-01 回稿跟踪、DLV-05 归档动作） |
| 域 | 6 个域——足以验证 README 文件清单与适用矩阵的**删行逻辑** |

**构建**执行体未覆盖（唯一带构建校验的是暂缓的 `UX-06` 与含已知偏差的 `UX-05`）——
待那两条入驻后补验。

#### 一条选集教训

本方案初稿的候选是 `UX-01` / `SEC-05` / `SEC-06` / `APP-06`，
**其中 3 条（UX-01、SEC-05、APP-06）事后被查出都在「有已知偏差」之列**。
原因是初稿按「跑通链路、覆盖不同执行体」选，**没把内容可靠性放在首位**。

**定则：极小集的首要判据是内容可靠，覆盖面是次要判据。**
覆盖不足可以后补；把有偏差的条目当正式规约发出去，则会直接误导下游。

## 6. 对原设想的两处修正

1. **「复制迁移」改为「改状态 + 重新生成」**——复制会分叉，生成不会。
   这也让"由 AI 执行迁移"更彻底：AI 改一个字段跑一条命令，而不是搬运正文。
2. **「标记被强制引用、不能删除」不手工维护**——`ReferencedIdsTest` 已经在守
   （删了当场红），`test/story/AGENTS.md` §6 记了契约与查询命令。
   手工清单会与真实引用漂移，正是同一个病。

## 7. 未决与风险

- **25 处核查修正应在 source 上做**，不在生成物上做。建议先建 source（步骤 1），
  再把 `10-` 的修正落进 source。
- 极小集之外的条目暂不入驻 → story 的符合性表初期只有 3 行。
  这是真实状态的诚实反映，但内网首跑的合规覆盖面会很窄，须事先知情。
- `ConstraintAuditRulingsTest` 迁指 source 后，正式目录的内容正确性完全依赖
  生成器 + 防漂移断言，故生成器本身须有正反例测试。
- 长期：若内网也要维护规约，source 套件需一并交付——套件自包含，INCLUDE 加一项即可。
