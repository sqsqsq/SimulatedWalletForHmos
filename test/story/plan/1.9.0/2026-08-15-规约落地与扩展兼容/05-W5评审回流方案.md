# W5 评审回流方案

> **性质**：方案，待评审。**未改任何文件。**
>
> ⚠️ **§5.1 与 §5.4 已被 `06-补丁式描述清点与治理方案.md` §5 取代**，以那一节为准。
> 原因：内网所有脚本指令统一走 `story.js` 入口，`review.js` 是 `story.js` 的**内部实现模块**，
> 不是与 `story.js`/`token.js` 并列的第三个对接层替身，也不归档到内网。
> 故 CLI 是 `story.js review <AR> [token]`（形状早已立在 `story.js:5/:19/:334`），
> 契约落点是更新 `story.js:19` 那一行。
>
> §6.1 的风险随之**收窄**——契约本就在 `story.js` docstring 里。
> 但 §6.2 的悬空引用清单**漏了两条**（`export_delivery_patch.py:90/126`），见 `06-` §2 P0-4。

## 1. 范围边界（最重要的一条）

**流程是单轮闭环，不重建 story**：

```
story(init) → spec → review(人) → spec(修订) → plan
```

**没有第二轮评审，没有 story 重新生成。**

由此确定三条语义：

1. **story 是一次性的评审载体**——spec 阶段产出、归档送审，使命即终；
2. **回流只改 spec**，story.md 与系统上的正文保持评审时的样子；
3. **spec 与 story 不一致是本设计接受的结果**，不是缺陷（见 §6 已知限制）。

### 为什么不重建 story

story 承载的是**一次评审**。若每次改 spec 都刷新它，就成了
「改 spec → 刷 story → 要再评审 → 又产生 review → 又改 spec」的循环，
**而这个循环没有终止条件**。收窄为单轮，终止点明确落在「进 plan」。

## 3. 不新增「是否影响 spec」标记的依据

`decisions.json` 的 `impact` 实测内容就是**受影响的 spec 编号清单**
（`output/story/cross-component-rich/.../decisions.json`）：

```json
"impact": ["F1 开关与入口控制", "AC-1", "AC-2"]
"impact": ["F2 登录/实名前置校验与回跳", "AC-5"]
```

它渲染成 review.md 的「**同意或修改后会影响什么**」（`story-build.mjs:329`）。
即「改这条会动 spec 哪里」**在生成时已由 AI 标注**，且给的是编号清单而非布尔值——
**布尔标记是它的退化版本**。

配上人勾的 `verdict`，判据完整：

| verdict | spec 是否要改 | 改哪里 |
|---|---|---|
| `agree` | 否——spec 本就按 proposal 写 | — |
| `revise` | 是 | **impact 直接指出** |
| `defer` | 挂起 | — |

回流时 AI 面对的是「verdict=revise + impact=[F1, AC-1]」——**执行题，不是判断题**。

**新增布尔标记的坏处**：它可能与 verdict **自相矛盾**（人勾「同意」却标「影响 spec」，
以谁为准）。两个字段表达同一件事就会有不一致的可能。

**对两个时点的直接回答**：

- 「生成时 AI 自动标记」——**已经在做**，就是 `impact`；
- 「人反馈时主动标记」——对**议题**不需要，人勾 verdict 已足够，再标一遍是重复劳动。

**真正需要 AI 判断的只有 freeform**（模板外意见）——它没有 verdict、没有 impact，
是需求缺失还是叙述不清只能由 AI 判。判错的代价是需求漏掉，故 §5.3 让 impact 可机检、
§5.2 让分类结果留痕可复核。

## 4. 主流程

```
A spec 阶段（现状）
  产出 spec.md + story.md + review.md（AI 起草议题，人未填）
  story 指纹记录 spec@sha
  └ sha 比对此时为**硬门禁**（.archive/ 不存在 ⇒ 两份要一起送审，必须一致）
  ↓
B /story archive
  story → 系统正文（design.md）；review → 附件
  落 .archive/ 回执 ⇒ sha 比对降为**告警**；
  **review.md 自此归人所有，build 不再碰**
  ↓
C 评审（人）
  在系统上批注，或直接改本地 review.md——**流程不关心来源**
  ↓
D 回流（AI）
  ① 若在系统上评：review.js fetch <AR> → 拉回并**写入 AR/review.md**（先备份）
  ② 模型读 AR/review.md（唯一输入）
  ③ 逐项处置：
       verdict=revise → 按 impact 指出的编号改 spec.md（走 correction 闭环）
       verdict=agree  → 不动
       verdict=defer  → 记台账，标挂起
       freeform       → AI 分类：需求类改 spec；叙述类记台账、不动产物
  ④ 落 AR/review-disposition.json（处置留痕）
  **不重建 story、不重新归档**
  ↓
E 进 plan
```

## 5. 四项改动

### 5.1 review.js（mock 立契约）

**输入唯一就是 review.md**，所以 fetch 的产出不是中间 JSON，而是**直接写回 review.md**。

```
node review.js <fetch|help> <AR> [mcp-token] [--project-root <abs>]

fetch → {"mode":"fetch","reqNo":"AR90003","fetched":true,
         "target":"AR/review.md","backupPath":"AR/.review-backup/<ts>-review.md",
         "status":"confirmed","success":true}
        从需求系统拉回评审后的 review 内容，**写入 AR/review.md**（先备份原文件）
help  → 打印用法（纯文本）
失败  → {"mode":"fetch","reqNo":"…","success":false,"error":"…"}
```

副作用是写文件、stdout 是回执——与 `story.js` 的 `init`（落盘 AR/SR/RR 三套后回执 JSON）
同构，符合既有模式。

**遵循的既有约定**（`story.js:2-27`、`token.js:2`）：

| 要素 | 约定 |
|---|---|
| 定位 | 数据对接层，**部署环境间唯一需替换的实现** |
| 契约真源 | **脚本自身的 docstring**（见下——原「SKILL.md 为真源」的体系已废弃） |
| 输出 | 人类可读日志走 stderr；stdout 最后**单行 JSON** |
| 退出码 | 成功 0 / 失败非 0 |
| token | 第三位置参数；本地不校验不使用，**但缺失时按真实契约报错** |
| mock 手法 | 数据取 `../mock-data/`，系统读写以 stderr 占位打印模拟 |

⚠️ **必须守住的教训**（`test/story/AGENTS.md:165`）：**方向只能是替身向真实契约对齐**，
不允许「文档写这个、本地干那个」——v0.20.0 实证 27 个交付文件全程绿灯却全错。

**契约落点（已随 `d780fec` 调整）**：契约**只写在 `review.js` 自身的 docstring 里**，
照 `token.js` 的做法（它本来就只有 docstring）。**不新增文档章节、不新增契约测试。**

原设计是「SKILL.md 新增 review.js 契约章 + 扩 `test_story_js_contract.py`」，
但 `d780fec` 把这两个落点**双双删除**——`test_story_js_contract.py` 整个文件（-172 行）
与 SKILL.md 的 `## story.js 契约（替换实现时必须保持）` 章。经裁定**按有意废弃处理**。

**删除的中间层**：原设计的 `.review-feedback.json` 与 `review-extract` 本地解析器**都不要**
——两条路径两套解析是多余的；解析复选框与「理解人写的意见」不可分，属判断，归模型。

### 5.2 处置台账 `AR/review-disposition.json`

单轮闭环下它不是「待办队列」而是**处置留痕**——交代每条意见被怎么处理了。
读者是人（想知道意见去向）与下游 plan（参考未处理项）。

```json
{
  "reqNo": "AR90003",
  "at": "2026-08-15",
  "items": [
    { "from": "DEC-003", "verdict": "revise", "disposition": "spec.md F1/AC-1 已改" },
    { "from": "DEC-007", "verdict": "defer",  "disposition": "挂起：等法务确认" },
    { "from": "freeform#1", "kind": "narrative",
      "text": "§5 状态机缺离线分支的图", "disposition": "本轮不处理（story 不重建）" }
  ]
}
```

### 5.3 `impact` 可机检

现状 `impact` 是自由文本数组，不保证元素是 spec 中真实存在的编号。

改法：`story-build.mjs check` 增一项——每个元素须能在 `spec/spec.md` 找到对应编号
（复用 `merge-story.mjs:158` 已有的编号正则 `S\d+|F\d+|E\d+|AC-…|BD-\d+|NFR-\d+`）。

价值：影响面从「描述」变成「锚点」，回流时 AI 有确定落点，不用猜。

### 5.4 spec sha 记录 + 归档后边界

story 指纹尾行扩展（现有正文 sha，`story-build.mjs:609-610`）：

```
<!-- story-fingerprint: body=<sha> spec=<sha> design=<sha> prd=<sha> se=<sha> -->
```

源清单取自 `contracts/story-chapters.json` 的 `sources`，**不硬编码**——新增源自动纳入。

| 阶段 | 判据 | 强度 | 理由 |
|---|---|---|---|
| 归档前 | `.archive/` 不存在 | **硬门禁**（FAIL） | 两份要一起上传送审，不一致会让评审人基于错的叙事判断 |
| 归档后 | `.archive/` 存在 | **告警** | story 已定稿，spec 继续演进正常 |

**它堵的裂缝**：现有 story↔spec 一致性检查是**单向**的（`story-build.mjs:602-608`、
`merge-story.mjs:151-199` 只查「story 缺了 spec 的什么」），故「改 spec 但编号不变」**零检测**。

**同时明确边界**：归档后 review.md 归人所有，`build` 若被调用须拒绝覆盖或强制备份。
这样人可自由编辑本地 review.md，不必担心被重建冲掉。

## 6. 已知限制（本次裁决接受）

**spec 修订后，系统上的正文（story → design.md）不再反映最新 spec。**

- 对下游无影响：plan/coding 看 spec；
- 对后来查阅需求的人是**潜在误导**——系统上的叙事停在评审时点。

缓解（**登记但不实施**）：可在处置台账注明「本轮 spec 已修订 N 处，系统正文未同步」，
需要时由人决定是否手工更新系统正文。

## 6.1 已知风险：替身契约失去机械保障

`test/story/AGENTS.md:165` 记录的教训是 **v0.20.0 实证「27 个交付文件全程绿灯却全错」**，
其防护机制正是 `test_story_js_contract.py`。该测试已随 `d780fec` 废弃，因此：

- **「替身向真实契约对齐」只剩人工纪律，无机械保障**；
- 同笔新增的 `test_flow_contract_gate.py` 守的是 `story-flow.json` **流程契约**，
  不是 story.js **CLI 契约**，**不构成替代**。

**W5 引入 `review.js` 会再增一个替身，风险面因此扩大。**
本方案明确登记此为已知风险，不假装仍有保障。

若日后要恢复保障，最小做法是给每个对接层脚本加一个「docstring 契约 ↔ 实际 stdout 形状」
的自测（不依赖 SKILL.md，避免重蹈被删章节的覆辙）。
