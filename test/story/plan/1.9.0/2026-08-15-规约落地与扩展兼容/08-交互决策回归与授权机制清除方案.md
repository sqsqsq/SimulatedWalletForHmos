# W8 关卡回归讨论与授权机制清除方案

> 状态:**§一–§三 + N6 已实施**(2026-08-15),离线 456 全绿、反例逐条验过;
> §五 checklist 第三组「行为验收」待实跑(交互能力已就绪,可直接跑 `split-interactive`)。上一版(协议式「完成判据」方案)已被否定,本版覆盖。

## 背景:三个证据,一个病根

**证据 1(第 4 轮自动测试)**:prompt 明写「本次只做其中一部分」,模型在 §③ 写
「通读任务描述,无范围表述」,定案 carry_all。W6 加四源行、W7-A 加摘录纪律,两轮修补全部无效。

**证据 2(驱动器源码)**:`run_case.py` 的关卡应答是写死的
`GATE_REPLY = "按你推荐的选项继续,不用再问我"`——人在测试回路里没有说话的位置。
要测「用户选择拆分」只能把答案预塞进初始 prompt,逼出记忆衰减,再为衰减修被测件。

**证据 3(AR90004 手工测试,真人在回路)**:第二级关卡只有 carry_all 一项,
用户口述「本需求先做挂失申请流程」。模型内心写了三段推理纠结这句话的意思
(自认 "needs interpretation"),最后引用「停等点只有第②步」「先做完再问」
说服自己不回问,自行映射 carry_all,记录 `by: human`,直接进 S4。

**病根:用协议管交互。** 从 W6 起给关卡写的东西——四步生命周期、授权两维表、
判定框架——全是交互协议:管模型什么时候停、怎么回话、回答怎么映射。
协议约束形式,约束不出讨论。AR90004 里模型缺的不是更细的协议,
是**该做的分析没人告诉它做**;协议反而成了它拒绝讨论的理由库。

**正确行为(Human 定义)**:人输入特性拆分诉求 → 模型结合需求与诉求**分析**——
拆分是否合理、具体拆分条目是什么、哪些本轮做、哪些留后续(兄弟 AR / 待立项)→
把方案摆出来**与人讨论清楚** → 人确认范围与拆分关系 → 记录、进后续流程。
规约的职责是指导这场讨论的**内容**,不是规定它的**步数与格式**。

## 三、正向重建

### N1 关卡章重写:关卡 = 讨论收敛点(替代四步协议 + 授权节,目标 ≤35 行)

重写后的全部内容:

- **呈现**:分析结论 + 可选方案。有确认组件用组件,没有用编号菜单(能力判据,
  不点名宿主)。选项集仅一项时明说:「没找到可行切法,准备按当前范围整体承载;
  同意就继续,想按某个方向切直接说,我补出该方向的份表再回到这里」;
- **人回应后**:命中既有选项 → 记录(basis 引原话)继续;
  **给出新诉求(切法、范围、条目增减)→ 这是讨论的开始,不是待映射的答案**——
  按 N2 做分析、摆方案、讨论到人确认;
- **底线三条**(仅有的硬约束):
  1. **人确认前不记录、不进后续流程**;`by: human` 记录的必须是人确认过的内容,
     人没说过也没确认过的选项 key 不得以他的名义记录;
  2. **人已确认的事不再重复确认**(执行不另起一轮);
  3. 用户明说「按推荐走,别逐个问」→ 照办,但 **`scope_decision` / `split_carrier`
     的代选永不选拆分**——拆分改变交付边界,须人拍板(Human 裁决):
     用户指明过拆分才拆(指明即定案);只说「别问我」= 不拆;
     SR 清单已切好的是上游既成事实,不算模型代做。

### N2 拆分讨论的内容指导(`rules/scope_gate.md` + `init_analysis.md` §⑤)

人提出拆分诉求(关卡上口述,或任务描述里事先说)时,模型做的是**需求分析**,不是选项映射:

1. **落条目**:他说的那部分对应哪些具体功能条目(对照 §④ 功能清单与 SR 定位),
   剩余部分是哪些条目;
2. **判归属**:本轮做哪些;留后续的归谁——已有兄弟 AR 能承载的写兄弟 AR 单号,
   没有的写「待立项」;
3. **评合理性**:四判据(独立交付/单向依赖/稳定边界/只落一份)用于**标注风险**,
   不用于否决人——卡在哪条就在方案里写明,让人带着信息拍板;
4. **摆方案、讨论**:条目/归属/依据成表呈现,说清自己的理解与建议;
   人修正就更新分析再摆,讨论到收敛;
5. **人确认范围与拆分关系后**:落 `.split-parts.json`、顺序记录两个 gate
   (人一句话已含承载时不再拆成两问)、`split.decided=split`、S4 范围收窄。

§⑤ 维度入口①改为:「用户口述的切法——按上述五步与人讨论收敛,
不要求他的话先长成『维度』」。

## 六、未来路径:批量授权 / 目标模式(不是永远不做,但须系统性设计后再立项)

Human 裁决:这两个方式不是永远不需要,但**当前无系统性设计,已影响正常用户交互**——
本轮删除;需求成立时按独立特性重新设计。设计要件(只记,不实现):

1. **授权的显式来源与解析归属**:用户那句话由谁解析成档位——须有 SSOT 解析器,
   不靠模型猜措辞(当时三连败的根因:三种措辞三种停等,skill 判不出宿主有没有人);
2. **覆盖范围**:哪些关卡可代、哪些永不可代(拆分类永不可代,已裁决);
3. **档位语义定义**:batch 与 goal 的边界、终止条件、失败时的降级路径;
4. **留痕与事后推翻**:代选记录的消费方是谁、人怎么一眼看到并推翻;
5. **与 framework 阶段级 `transition_policy` 的边界**:阶段边界归 framework,
   关卡归 skill,不再错位借用。

在此之前,「无人值守跑通」的需求归**驱动器**(reply / GATE_REPLY)——
这正是 2026-08-13 评测通路文档自己得出的结论(「让驱动器回答,不是逼 skill 别问」)。
