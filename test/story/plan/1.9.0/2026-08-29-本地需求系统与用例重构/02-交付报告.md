### 三个 js 各自变成了什么

| 命令 | 之前 | 现在 |
|---|---|---|
| `init` | 从一个**早已被删的**演示数据目录按模板渲染 RR/SR；走到拉材料就 ENOENT 崩 | 读 `<system>/<单号>/detail.json`，按 `parentNo`/`rrNo` 拉三套正文；**查无此单当场停住**（SKILL:64 那条判据首次可达）；系统缺正文就不写，留给占位件那一步 |
| `archive` | stderr 打印「（占位）上传…」，本地 `.archive/` 抄一份回执 | 系统正文进 `history/` 备份 → 被 story.md 覆盖 → review.md 进 `attachments/`；`verified` = 系统侧与本地字节一致；工作区一字节不动 |
| `restore` | 从本地 `.backup/` 找一份，再「（占位）上传」 | 把该单最新历史版本写回系统正文；无历史即失败 |
| `review` | 找演示目录里的 `<AR>-review-feedback.md`——目录不在，**永远 `unchanged`** | 拉系统上的 `review-feedback.md` 覆盖本地 review.md（先备份）；没有回稿才 `unchanged` |
| `token` | `local-mcp-token-<毫秒时间戳>` | 固定 `local-mcp-token`——带时间戳的 token 每轮都不同，是比对两轮日志时唯一的噪声源，却一次也没帮上忙 |

**SKILL / rules 一字未改**：它们写的是内网契约（查无此单停下问人、材料来自需求系统、
`AR/design.md` 可能预填），旧替身只是没实现到位。三个 js 之外 `doc/extensions` 零改动。

### 材料为什么要分三处

此前四个 Case 把全部材料——含收件箱里的 docx、含图片——在起跑前整棵铺进需求目录。
于是「模型会不会发现材料不够、会不会开口要」**从来没有被测到**：材料一直都够。

| 目录 | 是什么 | 什么时候到 |
|---|---|---|
| `cases/<id>/system/` | 需求系统上挂着的单据 | 起跑时复制到各 workspace **之外**的 `<workspace_root>/.systems/<case>/`，位置只由环境变量告知对接层 |
| `cases/<id>/workspace/` | 起跑那一刻需求目录里就有的东西 | 起跑时 |
| `cases/<id>/supplements/` | 人手上备着、**要来的**那几份 | `on_request`：等它开口，随那句回话一起投 |

每个 Case 一套独立系统：`archive` 会覆盖系统正文、`restore` 会回退它，共用一份两个 Case 会互相改写。
快照放 workspace **之外**，是因为放在里面被测模型一个 `ls` 就看见了——真实环境里需求系统
在远端，看得见就意味着可以绕过对接层直接读（见 §四 差异 2）。
