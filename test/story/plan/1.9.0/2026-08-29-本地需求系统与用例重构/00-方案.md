## 0. 背景与结论
外网 demo 用 token.js / story.js / review.js 三个替身屏蔽内网需求系统。探索实证：`test/story/mock-data/` 早已删除，`story.js init` 走到 `pullMaterials` 会 ENOENT 崩（`story.js:197-198`），`/story review` 永远 `unchanged`；四个 Case 全靠 `run_case.py:1143-1168` 把 `cases/<id>/workspace/` 整棵预铺进 `doc/features/<AR>/`（含 inbox、图片），被测模型从未真正"从系统拉单据"，补料也是启动前摆好的；prompt 把图片可达、兄弟交接、冲突定源等观测点直接写给模型（泄题）。用户要求：①删 mockdata；②token 固定值，story.js 改为从本地目录按单号拉取并模拟内网全部行为（archive/restore/review）；③CLI 测试只在被测模型开口要补料时才投 inbox；④四个 Case 减机械化、每个都支持图片、合成两个。**用户补充：内网系统只支持 md，没有图片；图片只能作为补充材料放 inbox、由 docx 解析得到。**
**只改三个 js 与测试域；`doc/extensions` 其余零改动；不改 framework。**

## 一、本地需求系统（模拟内网）

### 目录契约（数据，不是代码）
```
<system>/                       # 一个目录 = 一套需求系统；单号目录 = 一张单
  RR90004/ detail.json prd.md            # 系统只支持 md，没有图片
  SR90004/ detail.json design.md
  AR90004/ detail.json design.md(可空=系统预填) history/ attachments/review.md review-feedback.md(可选)
  AR90005/ …
```
- `detail.json`：`{reqNo,type:"RR|SR|AR",title,parentNo?,rrNo?}`（沿用现 case 的 `AR/detail.json` 形状）。
- 定位：`story.js` 读环境变量 `STORY_REQUIREMENT_SYSTEM_DIR`，缺省 `<projectRoot>/test/story/requirement-system`（demo 手工跑用）。测试域每个 Case 自带 `cases/<id>/system/`，suite 起跑时复制到 `<workspace>/.requirement-system/` 并设环境变量——系统状态随 Case 隔离、可被 archive 改写、finalize 后作为证据留存。

### story.js 四命令（从 0 重写；docstring 仍是 CLI 契约真源，stdout JSON 形状不变）
| 命令 | 行为 |
|---|---|
| `init <AR>` | 读 `<system>/<AR>/detail.json`（**没有 → `fail` 「查无此单」**，SKILL:64 那条判据首次可达）；按 parentNo/rrNo 拉 `SR/design.md`、`RR/prd.md`、`AR/design.md`（系统预填，`writeIfAbsent`）——**只有 md，系统不承载图片**；写三份 `detail.json`。系统里某份正文缺失 → 不写，由 `story_flow.py init` 落占位件（现行为） |
| `archive <AR>` | 前置 story.md + review.md 在（不跑任何门禁）。系统侧：`<system>/<AR>/design.md` → `history/design-<ts>.md` 备份；story.md 写为系统正文 `design.md`；review.md → `attachments/review.md`；**只上传 md，不上传图片、不改写路径**（内网系统不支持图片）；`verified` = 两份在系统侧字节一致。工作区一字节不动 |
| `restore <AR>` | `history/` 最新 `design-*.md` 写回 `<system>/<AR>/design.md`；无历史 → fail |
| `review <AR>` | `<system>/<AR>/review-feedback.md` 存在 → 备份 `AR/.review-backup/` 后整份写入 `AR/review.md`，`status: confirmed`；否则 `unchanged` |
| `help` | 不变 |
- `review.js` 只保留 `fetchReview`（读系统目录），或并入 story.js（两者留其一，adapt 的「替身自述」头保留）。
- `token.js`：固定输出 `local-mcp-token`。
- **删**：`MOCK_DATA_DIR`、`renderMock`/`{{AR}}` 模板、`materials` 归属回落、`uploadToSystem` 占位打印、`-local-` 死分支、未用的 `spawnSync`。
- **SKILL / rules 一字不改**：它们写的是内网契约（查无此单停下问人、材料来自需求系统、AR/design.md 可能预填），旧 mock 只是没实现到位；新替身是补齐到契约。三个 js 之外 `doc/extensions` 零改动。

## 二、测试域：材料按真实体验投放
- `cases/<id>/system/`：该 Case 的需求系统快照（只有 md）；**图片只能来自 inbox 里的 docx**（`import_sources.py` 抽到 `assets/<stem>/`），所以两个 Case 的图都走 `supplements/` 的 docx；`cases/<id>/workspace/`：人手上本来就有、起跑时已在需求目录里的东西（本地单的初始材料；系统单据通常为空）；`cases/<id>/supplements/`：**按需投放**的补料。
- `case.yaml` 新增：`system: true|false`；`supplements: [{file, deliver: on_request|start}]`。
- `run_multi_case.py`：`create_case_workspace` 复制 `system/` 到 `<workspace>/.requirement-system/`，`suite_environment` 加 `STORY_REQUIREMENT_SYSTEM_DIR`；`_case_seed_manifest`/`seed_case_workspace` 只铺 `workspace/`；`workspace-boundary.json` 记 `system_seeded`/`supplements_pending`。
- **按需投放**：`interaction-script.yaml` 条目加 `deliver: [file…]`；`send_scripted_reply` 与 `run_case.py reply` 在发回复**之前**把指定补料复制进 `doc/features/<AR>/inbox/`（宿主回话形如「我把产品同事给的文档放进需求目录了」）。适配回落（宿主实时回）时 `run_case.py reply --deliver <file>` 同样可用。未被要求前 inbox 只有 README。
- finalize：`.requirement-system/<AR>/` 复制到 `output/.../cases/<case>/system-after/`（归档正文、附件、history 是行为证据）。
- `case_public_inputs` 改为列 `system/` 与 `supplements/` 的 md 名（宿主回话参考）。
