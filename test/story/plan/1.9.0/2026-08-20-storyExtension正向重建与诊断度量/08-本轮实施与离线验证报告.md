## 2. 根因是否被删除

本轮不是给旧 selector 增加 fallback，而是删除职责错位：

- `story-chapters.json` 不再保存输入来源、关键词、标题或优先级；
- Story 脚本机械枚举当前 feature 的 RR、SR、AR、UX、补充材料、Spec 和 Acceptance；
- 脚本只保证路径、结构、编号、图片、决定投影和装配一致性，不判断事实应进入哪一章；
- `lint-rules.mjs` 不再扫描 Constraints 目录，Story 运行时与 Knowledge 完全解耦；
- Knowledge 不再扫描目录或 README；active item 和 `rule_id` 只从 Manifest 与 active 文件精确解析；
- 生产适配器不再读取 `test/story/mock-data`，没有真实系统连接或已落盘材料时如实失败。

因此，父版本来具备的宽容取材能力已经用正向职责恢复，同时保留 Human-First、decisions v2、ids v1、Review、图片、生命周期、模式下游传播和工程知识生效等既有诉求。

## 3. Story 内容守恒边界

本轮已经把内容守恒落到合同、指令和评价方法：

- 固定输入快照中的编号、表行、规则、限定与否定条件、数值、图片和全部业务分支都进入核对范围；
- 同一事实只允许一处完整主叙述，短引用、验收投影和附录精确查询不算重复叙述；
- 当前特性事实完整保留；相关特性保留拆分原因、职责、交接、顺序、生命周期和阻塞，不复制内部实现；
- 被否方案与采用方案、理由相邻；同轮来源冲突进入 Review 并阻止定稿；
- 机械检查不评价文章是否自然、是否完整或是否重复，这些由后续独立语义评价逐项取证。

由于用户明确要求本轮不执行 Story CLI，本报告不能证明模型已经生成了符合上述要求的最终 Story；它只证明生产合同、静态 Case 和离线检查已经为这项验证准备完成。

## 4. 多场景 Case

现有与新增 Case 共 15 个。当前执行者新增或实质补齐的 Story 场景如下：

| 场景 | Case | 当前证据 |
|---|---|---|
| 同事实、简报式 | `narrative-brief` | RR/SR 事实 token 与另外两种风格一致 |
| 同事实、按角色问答 | `narrative-role` | 标题与组织方式独立，事实集合不变 |
| 同事实、按办理顺序 | `narrative-process` | 使用步骤组织，事实集合不变 |
| 同轮来源冲突 | `source-conflict-review` | RR 与 SR 对离线查看给出互斥结论；解决意见只在人工回话区 |
| 非 AR 本地起手 | `local-ticket-start` | `ISSUE-410` 与本地 `detail.json` 明确父子关系，不依赖需求系统 token |
| 跨部件富场景 | `cross-component-rich`、`pattern-image-review` | 独立 RR/SR、图片、兄弟交接、接口、状态与异常材料 |
| 兄弟 AR | `split-two-ar` | Case workspace 自带真实父单关系和共享上下文事实 |
| 补充材料与交互拆分 | `docx-supplement`、`split-by-feature`、`split-interactive` | 每个 Case 都有独立占位输入、SE 和 inbox，不依赖生产 mock 注入 |
| Review 与归档 | `review-reflow` | 继续作为后续人工回流和归档行为载体 |

静态测试验证了 Case schema、阶段值、路径边界、无预期 Story、无判据泄漏、图片引用、叙述变体事实一致性和场景载体完整性。没有调用 `run_case.py`。

## 6. 明确未完成

以下三项仍未实施：

1. Demo 的 Logger/VOC/Chart 真实代码、导出、编译和故障测试；
2. 多 Case CLI 的并行调度、隔离和汇总；
3. 任何 Story CLI Case 实跑，包括现有单 Case、三个叙述变体、冲突 Case 和后续多 Case 执行。

因此不得声称整轮优化已完成，也不得用本报告的离线 PASS 替代最终 Story/Review 的独立人读评价。后续准确入口见 `07-剩余能力构建与测试交接.md`。
