# 步骤 3：扩展生命周期与配置设计

> 前置：[Story 人读信息架构](01-Story人读信息架构.md)、[Story 与 Review 决策合同](02-Story与Review决策合同.md)  
> 本步交付：一致的 phase/event/path 语义、稳定的 Spec 扩展和可被逐项裁决的共享语义检查。

## 1. 一致性的定义

配置一致性体现在三件事：

1. manifest 的阶段键使用 canonical phase id：`spec/plan/coding/review/ut/testing`；
2. lifecycle 入口使用事件原名：`on_context_load`、`post_check`、`pre_verifier`；
3. 每个阶段只注册其职责真实需要的事件和文件。

不同阶段的文件数量无需相同。Spec 有 Story 条件分支，Plan 负责确定性机器交接，因此各自拥有阶段文件；Coding、Review、UT、Testing 通过共享 hook、各阶段 overlay 和原生产物形成完整消费闭环。它们的能力不能省略，只是不为目录对称创建无消费者的阶段文件。

## 2. 目标目录

```text
doc/extensions/hooks/
├── shared/
│   ├── constraint-application.md
│   ├── design-pattern-application.md
│   └── pre_verifier.md
├── spec/
│   ├── on_context_load.md
│   ├── post_check.mjs
│   └── story/
│       ├── on_context_load.mjs
│       └── instructions.md
└── plan/
    ├── on_context_load.md
    └── post_check.mjs
```

命名约定：

- lifecycle 文件名与事件 ID 完全一致，使用下划线；
- 普通知识/指引文件继续使用仓库现有的短横线风格；
- 条件场景用子目录表达，`spec/story/on_context_load.mjs` 表示“Spec 阶段的 Story 条件入口”；
- 输出形态写在必读的阶段入口中，不再拆出 `reference/artifact_contract.md`。

## 4. Spec 保持已验证能力

Spec 已通过真实 CLI 证明以下链路有效：

- framework Spec Skill 明确读取 `hooks/spec/on_context_load.md`；
- `spec-sections.md` 提供 §9 技术契约和 §10 设计模式信号的形态；
- Story 条件入口依据 `AR/story-flow.json` 注入 Story 写作指令；
- `spec/post_check.mjs` 对缺失章节和 Story 产物形成确定性阻断；
- `spec-rules.overlay.yaml` 完成语义评价。

本轮保持这套职责和内容位置。路径迁移只做原子重命名与引用更新：

| 当前路径 | 目标路径 | 语义 |
|---|---|---|
| `hooks/constraint-application.md` | `hooks/shared/constraint-application.md` | 共享规约消费协议 |
| `hooks/design-pattern-application.md` | `hooks/shared/design-pattern-application.md` | 共享模式消费协议 |
| `hooks/spec/story_on_context_load.mjs` | `hooks/spec/story/on_context_load.mjs` | Story 条件 lifecycle 入口 |
| `hooks/spec/story_on_context_load.md` | `hooks/spec/story/instructions.md` | Story 条件写作指令 |

`hooks/spec/on_context_load.md`、`hooks/spec/post_check.mjs` 和 `skills/story/templates/spec-sections.md` 保持原职责，不迁入新的 artifact contract。

## 5. Plan 的阶段闭环

framework Plan Skill 没有实例 hook 的显式作者指针，因此 Plan 采用与 Spec 已验证闭环相同的实例层组合：

1. `hooks/plan/on_context_load.md` 给出完整的阶段任务与输出结构，并进入 harness/verifier 上下文；
2. `hooks/plan/post_check.mjs` 在阶段关闭前检查机器可判的交接事实，失败信息直接指向该阶段合同；
3. `plan-rules.overlay.yaml` 判断选型、规约处置和真实设计效果；
4. 共享 `pre_verifier.md` 要求 verifier 逐项输出合并后的扩展 check。

这个闭环不依赖新增 Skill，也不修改 framework。Plan 的具体产物合同见 [步骤 4](04-Plan工程知识生效设计.md)。

## 6. 共享 pre-verifier 合同

`hooks/shared/design-pattern-application.md` 按阶段明确同一个模式实例的连续职责：Plan 选择并冻结，Coding 落实结构与行为，Review 审查成型 diff，UT 验证可观察行为，Testing 验证真机可观察结果。后两个阶段不重新选型，也不把纯内部结构写成业务断言；某模式没有该阶段可观察义务时，依据 Plan 的行为锚点给出不适用结论。

`hooks/shared/pre_verifier.md` 只规定报告完整性：

1. 从本阶段合并后的 phase rules 动态读取全部 `semantic_checks`；
2. 使用原始 check ID 逐项输出结论和证据；
3. framework 原生检查与实例扩展检查同时保留；
4. 任一 MAJOR 扩展项失败传导到 verifier 总结论；
5. 新增或删除 overlay check 时无需同步维护固定白名单。

它不复述各阶段的语义内容，也不创建第二个 verifier。每个 check 的实际标准仍只在对应 overlay 中维护。

## 7. 兼容迁移

路径调整作为一个原子步骤完成：移动文件、更新 manifest、更新 hook 内相对引用、更新测试与适配指南，然后立即运行生命周期真实调用形态测试。目标目录不保留旧路径别名，避免两套入口长期并存；在提交这一步前，所有仓内在世引用必须已切换到目标路径。

现有 feature 产物不因路径迁移而重写。Story 章节和 decisions 的数据兼容由步骤 1、2 各自负责。

## 8. 完成条件

- manifest 使用 canonical phase/event，并且每个路径真实可解析；
- `story_on_context_load` 已按条件子目录改为 `spec/story/on_context_load`；
- Spec §9/§10、Story 条件注入、post-check 和 overlay 行为无回归；
- Plan 拥有一份自包含阶段合同和一个确定性 post-check；
- Coding、Review、UT、Testing 均装载规约与设计模式共享 hook，并由各自 overlay 定义真实消费证据；
- Coding、Review、UT、Testing 没有新增平行 artifact contract 或知识台账；
- 合并后的每个扩展 check ID 都进入 verifier 输入和输出；
- MJS hook 按真实 hook-runner 契约调用；
- `framework/**` 保持当前字节内容不变。
