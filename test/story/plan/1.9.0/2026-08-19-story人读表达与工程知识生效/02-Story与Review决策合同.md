# 步骤 2：Story 与 Review 决策合同

> 前置：[步骤 1：Story 人读信息架构](01-Story人读信息架构.md)  
> 本步交付：每项决策在 Story 中拥有一个自然上下文，Review 负责表态与结果记录。

## 1. 职责分工

Story 在事实所属章节说明：

- 当前采用的方案或处置；
- 选择依据与影响；
- 方案边界、风险和工作假设。

Review 组织人工表态：

| 字段 | 含义 |
|---|---|
| 审核问题 | 评审会上需要回答的自然语言问题 |
| 当前结论 | Story 已说明的方案、处置或已定规则 |
| Story 上下文 | 理由、影响和边界的唯一阅读位置 |
| 结论来源 | 上游已定、工程设定、规约命中或协作约定 |
| 责任人 | 有权确认或调整结论的具体角色 |
| 影响范围 | 受影响的功能、验收、范围或交付对象 |
| 当前状态 | 开放或已定 |
| 人工结果 | 同意、修改后的结论或暂缓安排 |

开放和已定决策都进入 Review。覆盖范围按本需求实际存在的产品规则、SE 技术约定、工程设定、命中规约、上线协同以及 AR 拆分与承载判断，不要求每个来源类别机械凑数。

## 2. 决策登记保持 schema v2

`AR/story-src/decisions.json` 继续使用当前结构：

```json
{
  "schema_version": 2,
  "decisions": [
    {
      "id": "DEC-001",
      "status": "open",
      "question": "<人类评审问题>",
      "display_text": "<当前方案或已定结论>",
      "rationale": "<选择依据>",
      "source": "<结论来源>",
      "decider": "<责任角色>",
      "impact": ["<受影响对象>"]
    }
  ]
}
```

这些字段已经能够同时生成 Story 上下文和 Review 议题。Story 锚点由决策占位符所在位置确定，避免登记表里的路径与正文位置各自演化。

## 3. Story 唯一投影

作者先在该决策事实自然归属的章节完成上下文，再将 `{{DEC-xxx}}` 作为独立段落放置一次。装配器把该段替换为带稳定锚点的简短人读块：

```markdown
<a id="decision-dec-001"></a>
> **当前处置：** <display_text>。<rationale>。影响范围：<impact>。
```

渲染规则：

- 每项决策在 Story 中恰好投影一次；
- 占位符独占一段，不嵌入句子、表格单元格或另一层括号；
- Story 不渲染 `question`、`status`、`source`、`decider`，也不出现“待确认”“请确认”等会议措辞；
- 同一决策在其它位置需要承接时，使用自然短引或指向该锚点的内部链接；
- 最终 Story 不显示裸 `DEC-*` 编号，稳定 ID 只服务装配与回链。

这使当前方案、依据与影响仍在事实发生处完整可读，同时消除文首清单、机器拼接和多处整句重放。

## 4. Review 决策全景

Review 从同一登记表确定性渲染：

- 审核问题；
- 当前结论或当前方案；
- 状态、来源、责任人和影响范围；
- 指向 `story.md#decision-dec-xxx` 的上下文链接；
- 人工审核结果区。

完整理由由 Story 唯一承载，Review 不再复制 `rationale`。评审者先读结论，需要上下文时一跳回到 Story，再在 Review 表态。

Review 保留现有两类人工内容：

1. 每个议题下的选择、修改意见、暂缓安排、确认人、日期和依据；
2. 计划外意见区。

重新 build 时，机器区可以按登记表更新，人工区按既有决策 ID 逐字节保留。无法映射的旧人工内容明确报错并停止重建，不静默丢失。

## 5. 空集合与状态

- 零开放决策合法；已定决策仍进入 Review 供逐项过目；
- 确实不存在任何决策时，沿用 v2 的 `none_reason` 明确说明事实；
- Story 不因开放决策存在而改变目录或文首结构；
- Review 的状态只描述登记和人工结果，不反向污染 Story 的需求叙事。

## 6. 实施落点

- `story-build.mjs`：移除 Story 决策汇总；限制唯一、独立占位；生成 Story 锚点和人读块；调整 Review 机器区；
- `merge-story.mjs`：检查占位唯一性、锚点存在性、Review 回链和人工内容守恒；
- `rules/rules.md`：说明决策的唯一归属位置和 Story/Review 分工；
- `rules/review_reflow.md`：保持人工表态与计划外意见的回流语义；
- `hooks/spec/story/instructions.md`：按实际决策来源完成登记，不按类别凑数；
- `test_story_build.py` 及 Review 合同测试：覆盖开放、已定、空集合、重复占位、内联占位、断链和人工区守恒。

现有 decisions v2 数据无需迁移；实施不引入 v3 兼容层或双写逻辑。

## 7. 完成条件

- Story 不生成“待确认事项”，也不出现 Review 问题和责任人字段；
- 每项决策只有一个 Story 投影和一个稳定回链锚点；
- Story 的决策块可自然阅读，没有值重复、嵌套括号或机器拼接；
- Review 覆盖本需求实际存在的决策全景，并能回到 Story 阅读完整上下文；
- rebuild 后人工填写内容字节级保持；
- schema v2、空集合、正例和反例测试全部通过。
