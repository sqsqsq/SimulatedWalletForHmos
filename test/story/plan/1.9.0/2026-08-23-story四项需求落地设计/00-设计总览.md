## §2 全局架构判据

### 2.1 层结构（两层 + 一座桥梁）
本工程是**外网训练 demo 仓**；内网才有真实业务代码仓 + 真实 SDK。demo 验证**机制**，不冒充真实仓内容验证。
从「相对通用、又快速应用到真实仓」的诉求出发，Extension 组织为**两层主体 + ADAPTATION 一座桥梁**：

| 结构 | 组成 | 与 Framework 的关系 | 与 demo 仓 / 目标仓的关系 |
|---|---|---|---|
| **通用机制层**（`knowledge/` 以外全部） | skills（story / story-adaptation）、hooks（on_context_load / post_check / pre_verifier）、6 份 phase_rules_overlays、scripts、章节合同、releases 清单结构 | 全部构建在框架既有扩展点（§1.3），不凭空造能力 | **零强依赖**：不引用任何仓模块名、SDK API、业务名、绝对路径；运行期标识从配置派生 |
| **知识层**（`knowledge/`） | component-profile / codebase-facts / constraints（含 diagnostics-metrics）/ design-patterns | manifest `provides.knowledge` 激活（存在性校验 + error 即零污染）；内容经 on_context_load 提示送达 | 本仓当作真实仓核实的事实，但**更核心的身份是模板**——对另一仓是"该长什么样"的样板 |
| **ADAPTATION 桥梁**（两层之间唯一接口，非第三层） | `/story adapt` + 插槽 S1–S5 + verify-adaptation + releases 1.0/2.0 | 通用机制（三态 / 影子树 / 原子写 / 失败恢复） | 把知识层从模板**逐槽替换为目标仓已核实事实**，机制层一字不动；适配即替换，不是重写 |

**可验证不变量**：
1. **机制层依赖禁令**：`doc/extensions` 非 `knowledge/` 部分零仓名/零 SDK/零业务名/零绝对路径引用（S0/S5 各扫一次）。
2. **知识层模板性**：项目知识、模式文档、反模式案例对另一仓是样板，ADAPTATION 插槽按同一结构换内容。
3. **适配即替换、不是重写**：目标仓只迭代知识层身份；通用机制、冻结需求、C8 模式基线、C14/C15 真实取证逐条闭环。

### 2.2 知识层边界（两个判别，正交）
**判别一 · 归哪一类（决定放哪、生命周期走哪）**——对每个候选知识项连问两句：

| 判别句 | 是 → 归哪类 |
|---|---|
| **Q1 描述"当前工程现状"还是施加"必须满足的要求"？** | 描述现状 → **项目知识**；施加要求 → 进 Q2 |
| **Q2 这条"必须"是无条件适用，还是仅当选型后才生效？** | 无条件适用 → **规约**；仅选型后生效的内部纪律 → **设计模式** |

| 类 | 回答的问题 | 判别句 | 生命周期 | 验证 |
|---|---|---|---|---|
| **项目知识** | 当前工程是什么样 | 描述已核实的现状事实（有/没有、长什么样、怎么认） | 核实→引用→影响 | 实扫；"没有"须为核对过的零命中 |
| **规约** | 必须满足什么 | 施加要求，且无条件适用（或在声明的适用面内） | 适用即落实→验证 | 强制力/命中条件/验证执行体 |
| **设计模式** | 可选怎么做 | 方案结构 + **选用该模式后**才生效的工程纪律 | 候选→Plan 选用→冻结→实现→验证 | 契约投影/验证清单 |

**判别二 · 值不值得写（N1–N5，与判别一正交）**——判据：**假设模型已完整读过目标代码仓并按现有代码模仿，若"不写这条也不会写错"，就不写**；知识只承载"读完整个代码仓后依然无法可靠得到"的判断。

| 类 | 一句话 | 例子 |
|---|---|---|
| N1 隐藏的为什么 | 代码只有结果、没有理由：决策、取舍、被否方案 | 模式上篇"解决什么问题/什么时候不该用"；被否方案与取舍理由 |
| N2 全局不变量 | 单点读不出、跨位置才成立的一致性 | `flow_id/step_id` 全链路一致、Chart 每步终态唯一 |
| N3 例外与边界 | 主路径之外、读仓会被主路径吸引而漏的条件 | 秘密字段排除、空态、恢复前提 |
| N4 约束的强制语义 | 红线/基线/建议、命中条件、怎么验——让"易不遵循"可检查 | 上报失败不改业务结果的强制力与验证执行体 |
| N5 多实现需统一 | 几种写法都对，项目选定一种作默认 | 密度"日志>VOC>Chart"、统一命名/统一走封装 |

**边界强制规则（防三类互渗）**：
1. 规约不携带项目事实（C3）：实现事实/代码位置/API 一律移项目知识；规约只留要求/适用/验证。
2. 模式的"必须"是选用后生效的内部纪律，不等于规约（Q2 判）。
3. README/示例/测试夹具/阶段决策/证据不构成知识类型（C2）。
4. 模型读仓可得的代码特征（API 签名/字段清单/调用点/类构成/实现形态）一律不写入知识。
5. 归一类用判别一（语义轴）；条目内部结构仍用 `constraints/README.md` 字段模型（约束/命中条件/处置/验证执行体/强制力）；判别二只裁定值不值得写，不决定归哪一类。

### 2.3 不从框架扩展机制外再造能力
**禁止**（黑名单）：知识正文自动注入框架、目录扫描器、平行 registry、fact-ID/事实合同、成文状态机。

## §3 四项需求设计（逐条映射冻结 C 条款）

### 3.1 需求1+2 — Story 内容守恒与人读成文

**合同（需求1 C1/C3/C5）**
- `story-chapters.json` 14 → **固定十章**：背景/术语/范围/业务方案/业务流程/功能说明/异常与恢复/验收/交付与上线/附录。
- 每章声明：职责（回答读者什么问题）+ 必答问题 + 候选词根（`inputs[].section`）。**词根未命中 → 读取该源整篇，绝不判缺失**；"词根未命中"与"源文件不存在"分开报错（C5）。
- **删除每章 `form` 配额**（需求2 C2 明文：不设 Markdown 类型/数量配额）。不引入 fact-ID / 事实合同 / 成文状态机（黑名单见 §2.3）。

**成文顺序（需求2 C3）**
- `scaffold` 任务书 = 全部同轮材料清单 + 本章职责/必答 + 通用判据；每章读取范围 = 全部材料，**不做预分配**。
- 成文流程：**全局规划 → 逐章成文 → 全文统稿 → 全量事实复核**；统稿只调承接/标题/跨章重复，不整篇重生成。

**内容审计（需求1 C4、需求2 C3）**
- 新增 `story-build.mjs audit`，在最终 `story.md` 定稿后生成 `AR/story-src/content-audit.md`。
- **来源单元级**（段落/列表项/表行/图片/链接/编号数字/明确决定）；每项六字段：来源位置与完整事实 / 是否进入 Story / 完整主叙述位置 / 其它位置独有信息 / 重复合并处置 / 最终处置。
- 审计**不参与**取材、分章、装配、归档（规格 C3 原文：只用于审计）。
- 机械层只验：文件存在、结构含六字段、每条指到真实来源/章节、三个来源文件均被覆盖；事实穷尽/重复成立 = 独立 verifier 语义判据。

**人读规范（需求2，写作指令 + 语义判据，非代码知识，不受 §2.2 约束）**

**表 A 标题 H1–H4**
| 层级 | 规则 |
|---|---|
| H1 | 当前特性真实业务名；拆分时体现本 AR 业务边界；禁 AR/ISSUE/RR/SR 编号、阶段名、"需求评审叙事"等文档类型语 |
| H2 | 固定十章骨架，不增删不改序 |
| H3/H4 | **出现条件**：存在真实从属关系 / 需独立呈现的页面、流程段、接口组、分支或状态时才出现；否则从属 H2 直接写正文。**命名（正向）**：业务对象、读者问题或动作短语（"开通流程""失败处理与恢复""系统分工""上线准备"）；一个标题回答一个主题；从属真实（H4 是 H3 子主题，非平行换名）。**禁用（负向，语义判断非词表）**：模板占位语、提问句、机械分类词、解释性长句、字段拼接/箭头映射、维护术语（`carry_all`、流程契约、`scope_decision`） |

**表 B 叙述逻辑**
- 章内：先给结论/要点一句，再展开原因、参与者、条件、过程、结果。
- 唯一主叙述：事实首次出现处完整呈现；其他章一句承接并指向，不整段重述（对接需求1 C2）。
- 四类关系取舍：因果/解释→正文段落；时间/步骤先后→有序列表或时序图；并列/分类→无序列表或分组小标题；逐项比较/回溯映射→表格。
- 章间：背景为什么→术语定义→范围做什么/不做→方案怎么解决→流程怎么推进→功能当前特性细节→异常恢复失败→验收怎么算对→交付上线→附录查证；每章只推进理解，不复述前文已建立的心智模型。

**表 C 表达取舍（何时用 / 何时不用）**
| 表达 | 何时用 | 何时不用 |
|---|---|---|
| 正文段落 | 连续解释、因果、叙述推进 | 并列多项却写成长段 |
| 有序列表 | 真实先后顺序的步骤 | 顺序无关的并列 |
| 无序列表 | 并列要点/同类列举 | 有因果流程却用圆点打断 |
| 表格 | 多项同维度逐项比较、回溯映射 | 一句话能说清 |
| 流程图 | 流程有分支、交接、返回 | 线性两三步（正文更清楚） |
| 状态图 | 状态流转、停机/恢复语义 | 无状态变化 |
| 时序图 | 跨参与方先后/等待/恢复 | 单一参与方 |
| 图片 | 视觉依据、界面/示意（保留 alt 与图中信息） | 可纯文字表达 |
| 行内代码/代码块 | 展示命令、标识、契约片段 | 业务叙述 |
| 强调/引用 | 关键结论、风险、来源 | 让位给表/正文 |

判据：不设每章数量，只判"该用的形式用了 + 不该用的没滥用"。

**表 D 正文描述**
- 业务语言优先，机器面不出正文（`rule_id`/`pattern_id`/仓内路径/生成机制/检索过程只进附录）。
- 正常受限 vs 真正失败分开（正常受限→功能说明，真正失败→异常与恢复）。
- 数值必标来源（上游约束:`文档名` / 本工程设定,无上游依据 / 平台基线，对齐 evidence-rules §3.2）。
- 一句一意、段落一主题；完整业务过程与当前特性功能分开说明。

> 执行精神：表 C 不设"必须用什么形式"的配额、表 A 不做标题黑名单，只给正向示例与负向类别。

**开放决定与语义验收**
- 开放决定只进 `AR/review.md`，Story 零投影；已定决定唯一投影。
- 语义验收：`story_reader_fitness` 扩展为**九问首读测试**（不看 Spec/RR/SR，仅凭 Story 答：要做什么/为什么/范围/方案/流程/功能/异常/验收/交付），任一答不出即 FAIL。

**统稿检查清单（纳入 01-实施计划 §4 完成判据）**
1. 标题树像正常需求文档目录（逐级可读、从属真实）；
2. 每章推进理解，无"换皮重复"；
3. 机器面只在附录，不出主叙述；
4. 表格/图/列表贴合内容关系（表 C 判据）；
5. 九问首读通过。

### 3.2 需求3 — Knowledge 跨阶段应用

**分类与生命周期（C1/C2/C3/C4）**
- 项目知识 = `component-profile.md` + `codebase-facts.md`（不建 `project-facts/`）；规约 = `constraints/`；设计模式 = `design-patterns/`。归类按 §2.2 判别一。
- `constraints/README.md` **删除"适用矩阵"**，只留索引+字段模型+强制力语义（C4）；路由交给各 overlay/hook。
- 三类各用独立生命周期：项目知识（核实→引用→影响）、规约（适用即落实→验证）、模式（候选→Plan 选择→冻结→实现→验证）。三者不共用"候选/采用/选择"状态（C1）。

**激活与送达（C5，机制层）**
- manifest `provides.knowledge` 是唯一激活真源（framework 已保证：error 即清空）。
- 新增 `hooks/active-knowledge.mjs`（`on_context_load`）：读 manifest → 注入"本阶段激活知识=清单"提示 → 模型打开清单内文件。替换现静态 `constraint-application.md`；清 Story rules 里对知识文件的静态链接（防 PIT-113）。
- 阶段不扫描目录、不读取未启用文件；由"hook 只给清单 + verifier 核引用在清单内"两层守（C5）。

**Spec/Plan/下游（C5/C6，含新增 plan 机制）**
- Spec：识别规约影响 + 模式候选（`spec_pattern_signals` 扩展语义项，候选只能是路由表在册 id 或"无候选"）。
- **Plan（新增 `hooks/plan/on_context_load.md` + `hooks/plan/post_check.mjs`，注册进 manifest）**：固定"工程知识决策"节；`contracts.yaml > project_knowledge`（`pattern_applications`/`constraint_obligations` 带锚点）；post_check 确定性校验受控 ID、锚点可解析、域覆盖、与 Plan 同步——"冻结结果=下游唯一入口"的机械化落点（关 PIT-121）。
- Coding/Review/UT/Testing 只消费冻结结果，对照 `project_knowledge` 验证真实落点（代码/diff/用例/报告）；实现不了回 Plan 更新冻结，不静默重选（C5）。

**规约与知识新增内容（C7/C8）**
- `constraints/diagnostics-metrics.md` — 归类：**规约**（判别一：Q1=施加要求，Q2=无条件适用）。内容仅含必须判据：三方渠道职责、共用 `flow_id|step_id`、密度"日志>VOC>Chart"不设数量配额、Chart 每业务步骤唯一终态、秘密字段排除、上报失败不改业务结果/重试。**不写**事件字段清单、调用点枚举、payload 结构与具体 API 形态——由模型读仓（`Logger.ets`/`WalletHA*`）学习模仿。文件不含任何项目事实。
- `codebase-facts.md` 埋点面 — 归类：**项目知识**（判别一：Q1=描述现状）。存在性登记：`Logger.debug/info/error`、`WalletHAReportForVOC/ChartCBuilder` 已存在并从 CommFunc 导出、非阻塞写入、失败仅 `Logger.error`；只作模型定位真源的索引，不展开方法签名与字段构成。

**设计模式（C8，防 PIT-110/111/112）**
- `design-patterns/README.md` + `decision-tree.md` + `page-interaction.md` 自用户指定原件**逐字节复制**（仅首部最小加载元数据）。**manifest 只登记两个模式正文，不登记 README**。README 只做路由表：受控 pattern_id 全集 / 适用单元粒度（流程段/页面组件）/ 零命中是正常结论。
- 结构/语义（上·适用与选型 / 下·结构与落地、节点表/动作表概念、契约投影边界、分阶段验证清单、反模式→迁移方向）= **通用层基线**，采纳。
- SDK 身份/API/依赖/反模式案例：知识层以本仓（当作真实仓）核实——已比对 `oh_modules/@aspect/WalletMain/oh_modules/framework/{DecisionTree,PageInteraction,StateMachine}.d.ets`，Builder/Manager/Context 签名均吻合。
- SDK 行为事实作为本仓已核实的模式落地形态保留，不作为**强制 API 契约**；交付到其它仓时该身份仍是**适配层**，由 ADAPTATION 插槽 S4 读目标仓真实 SDK 取证替换。
- 删除无消费方元数据 `triggers_usecase_spec`（本仓 framework 与 doc/extensions 均零引用）。
