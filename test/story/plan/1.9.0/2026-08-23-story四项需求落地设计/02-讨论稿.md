## §1 需求来源与基线判定

- 四项需求（内容守恒、人读、Knowledge 跨阶段、ADAPTATION）只采用冻结澄清
  `test/story/spec/2026-08-21-story四项需求澄清/`；不采用历史方案、踩坑记录、EVOLUTION、框架/扩展自身能力作为需求来源。
- "归档 1.0 被证明有效"指**机制链有效**，不指其 SDK 身份对任意目标仓有效；身份归适配层，交给 ADAPTATION 取证。
- 本工程是外网训练 demo 仓，内网才有真实业务代码仓 + 真实 SDK；demo 验证机制，不做真实仓内容验证。

## §2 知识层边界：从"易错三类"到"两轴正交"（本轮关键讨论）

- 初版把知识承载内容列为"易被忽略 / 易不遵循 / 多实现需固化"三类，经审视这三类实际是**从"错误"出发的动机子集**，不完备。
- 正解改为两轴正交：
  - **判别一（归哪类）**：Q1 现状 vs 要求；Q2 无条件 vs 选型后生效。由此导出 项目知识 / 规约 / 设计模式 三类及各生命周期。
  - **判别二（值不值得写）**：假定模型读完代码仓后"不写也会错"才写（N1–N5）。
- 结论：判别二只裁定值不值得写，不决定归哪一类；两者不互相替代。N1–N5 不构成第四类知识。
- observability 曾过度设计为穷举代码特征（事件字段、调用点、payload 结构）；按上述原则收敛为**规约只写必判据、项目知识只做存在性登记**，细节交模型读仓模仿。

## §3 三层 vs 两层 + 桥梁（命名统一过程）

- 曾用"三层结构"，后明确 **ADAPTATION 不是第三层，而是两层主体（机制层 / 知识层）之间的唯一转换接口**。
- 统一命名："两层 + 一座桥梁"，并在 AGENTS.md 维护认知同步表达。

## §4 面向人类（需求2）成文规则讨论

- 人读改写是需求1结果上的表达优化：可调整事实顺序/重组三级四级章节/补承接，但不新增删除改变事实；
  骨架固定，脚本只查结构与引用完整性，表达合理性归语义评价。
- 表达形式不设每章数量配额；取"何时用/何时不用"判据 + 正向示例（非标题黑名单——黑名单只催生另一批机械标题）。

## §5 失败预防要点（对标踩坑记录）

- 文档状态 ≠ 代码真值：方案文档禁止写"已实施"，实施事实与验证结论分栏；离线全绿 ≠ 行为完成。
- 不引入事实 ID / 平行 contracts 命名空间 / 统一知识解析框架 / 成文状态机。
- Story 保持词根未命中回退整篇；模拟稿标题不可成为生产协议（精确标题选择器 / primary/supporting 回退）。
- plan 是"选择与冻结"阶段而非知识终点；Coding/Review/UT/Testing 只消费冻结结果，实现不了回 plan，不静默重选。
