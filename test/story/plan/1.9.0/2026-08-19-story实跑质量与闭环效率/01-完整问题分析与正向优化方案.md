# Story 人读质量、工程知识与可观测性贯通：正向优化方案

> 状态：待确认，尚未实施  
> 日期：2026-08-19  
> 事实依据：[00-实跑事实与问题记录.md](00-实跑事实与问题记录.md)  
> 适用范围：doc/extensions、05-SystemBase/CommFunc、相关工程知识文档与 test/story  
> 实施边界：framework 保持发布件状态；Demo 业务能力只扩展通用日志、VOC 与 Chart 基座

已确认的新增决策：

- 目标仓模式清单为空时完整关闭设计模式能力；
- Chart 以业务步骤为统计粒度；
- Debug 允许未脱敏业务原值和原始结构；
- 凭据、访问令牌、会话秘密和密钥始终排除；
- 本地 Demo 建立正式 Debug、VOC、Chart 能力，CLI 验证推进到 Coding 与 Review。

## 1. 优化目标

本轮把 Story 人读表达和工程知识贯通设计成一条完整链路：

1. Story 与 Review 服务人的理解、评审和决策，内容完整、层次自然、语言符合业务阅读习惯。
2. Spec 准确表达需求、范围、验收和设计模式候选信号。
3. Plan 根据目标代码仓事实完成设计模式选型、规约命中判断和工程设计，并把采用结果写入正式技术合同。
4. Coding、Review、UT、Testing 从同一份合同继续消费设计模式和规约，形成可实现、可审查、可验证的闭环。
5. Story、Spec、Acceptance、Plan 与 contracts 保持阶段所有权和内容一致性。
6. 设计模式能力按目标仓真实情况启用、替换或关闭，不把本仓 demo 模式强加给目标工程。
7. 日志、VOC 定位上报和 Chart 统计埋点形成由密到疏的可观测性设计，并在代码中真实生效。
8. 目标仓适配以真实 Skill、SDK、包元数据和既有业务案例为权威事实，使内网模型能够完成可靠适配。
9. 测试过程保留历史产物，支持不同版本之间的真实效果对比。

最终判断标准不是文档中出现了 pattern_id、rule_id 或事件名，而是这些知识确实改变了设计、实现、审查和验证。

## 2. 总体设计

### 2.1 双表达面

整条链路分为两类产物：

| 表达面 | 产物 | 主要读者 | 成文目标 |
|---|---|---|---|
| 人读面 | AR/story.md、AR/review.md | 产品、研发、评审者 | 读懂价值、范围、方案、风险和待决事项 |
| AI 执行面 | spec.md、acceptance.yaml、plan.md、contracts.yaml、use-cases.yaml | 各阶段模型与校验器 | 精确表达事实、决策、合同、引用和验证分层 |

人读面使用自然语言组织内容；AI 执行面使用稳定结构和可解析引用。两者表达同一需求，但不把机器协议直接复制到 Story 正文。

### 2.2 阶段数据流

~~~mermaid
flowchart LR
    A[原始需求与补充材料] --> B[Story / Review]
    B --> C[Spec / Acceptance]
    C --> D[Plan]
    D --> E[contracts / use-cases]
    E --> F[Coding]
    F --> G[Review]
    E --> H[UT]
    E --> I[Testing]

    K[规约、设计模式与可观测性知识] --> C
    K --> D
    K --> F
    K --> G
    K --> H
    K --> I
~~~

各阶段通过现有 Extension 生命周期完成连接：

- on_context_load 提供本阶段需要理解的知识和成文要求；
- post_check 校验可确定判断的结构、一致性和精确引用；
- pre_verifier 提供语义审查依据；
- phase rules overlay 定义本阶段必须回答的语义问题。

manifest.yaml 继续作为上述阶段配置的统一入口，各阶段统一使用 on_context_load、post_check、pre_verifier 生命周期键。Story 专属逻辑通过 hook 路径和现有 Story Skill 表达，生命周期命名保持阶段一致。

### 2.3 阶段所有权

| 阶段 | 负责作出的决定 | 正式写入位置 | 向下游交付 |
|---|---|---|---|
| Story | 人可理解的需求叙述、开放问题和评审选择 | AR/story.md、AR/review.md | 已澄清的业务语义 |
| Spec | 需求、范围、验收、设计模式候选信号、定位与统计意图 | spec.md、acceptance.yaml | 需求真源与候选集合 |
| Plan | 工程选型、模式实例、规约义务、可观测性、文件与协作设计 | plan.md、contracts.yaml、use-cases.yaml | 可执行工程合同 |
| Coding | 按合同实现模式结构、规约义务和可观测性 | 源码、资源、配置 | 可审查实现 |
| Review | 依据真实 diff 核对模式、规约与观测结果 | review 报告 | 实现、偏差和证据结论 |
| UT | 验证业务级可观察行为 | UT 计划、用例与报告 | 业务验证证据 |
| Testing | 验证真机和环境相关行为 | 测试计划与报告 | 环境验证证据 |

阶段内发现本阶段真源需要修正时，按 AGENTS.md 的修正三问回到对应所有权阶段，再从该阶段继续闭环。

## 3. Story 人读模型

### 3.1 稳定的顶层目录

Story 采用稳定的一级章节，帮助读者快速建立整体认知：

1. 需求概览
2. 范围与协作边界
3. 整体方案
4. 场景与功能设计
5. 体验、流程与状态设计
6. 系统方案与实现边界
7. 风险与当前方案
8. 验收、上线与协作
9. 附录 A：术语
10. 附录 B：详细契约
11. 附录 C：追溯

一级章节表达稳定的信息领域。二级及更深层标题根据本次需求内容自然组织，让读者看到标题就能理解该段在讲什么。

### 3.2 内容驱动的子章节

子章节由业务语义决定，采用正常项目文档中的命名方式。例如：

| 表达意图 | 推荐标题 |
|---|---|
| 说明需求给业务带来的收益 | 业务价值、需求价值 |
| 说明用户在什么情况下使用 | 使用场景、典型场景 |
| 说明一段完整办理过程 | 办理流程、开通流程、支付流程 |
| 说明失败后的用户体验 | 失败处理、异常处理与恢复 |
| 说明系统间职责 | 系统分工、模块协作 |
| 说明上线前关注事项 | 上线准备、发布与回退 |

生成规则：

1. 标题先概括业务对象或读者问题，再组织正文。
2. 一个小节集中回答一个主题；主题包含独立流程、状态、角色或风险时继续拆为三级、四级标题。
3. 标题使用领域语言和业务动作，正文直接说明结论、原因和影响。
4. 机器标识、协议状态和源坐标放在附录或 AI 执行产物中。
5. 同一事实选择一个主要叙述位置，其他章节通过简短引用承接。

### 3.3 人读信息完整性

Story 必须完整承载 Spec 中适合人阅读的七类信息：

| 信息域 | Story 中的主要位置 |
|---|---|
| 业务价值 | 需求概览 |
| 用户与场景 | 需求概览、场景与功能设计 |
| 范围与协作 | 范围与协作边界 |
| 主流程、分支和异常 | 场景与功能设计、体验流程与状态设计 |
| 体验和非功能要求 | 体验、流程与状态设计 |
| 隐私和安全影响 | 系统方案与实现边界、风险与当前方案 |
| 验收、发布和协作要求 | 验收、上线与协作 |

完整性判断采用语义覆盖：允许合并重复内容、改写语言和调整位置，同时保证每个有效事实、约束、边界与验收语义都能在 Story 中找到对应表达。

本轮回归事实集至少覆盖：

- 提交时重新校验登录、实名和绑卡状态；
- 深色模式、大字体、折叠屏和 RTL 适配；
- 本需求对个人信息采集范围的影响；
- 主流程、失败路径、恢复方式和验收结果；
- 需求涉及的系统、模块和外部依赖边界。

这些事实用于测试语义守恒，不作为生产模板中的固定关键词。

### 3.4 规约的人读投影

Story 只表达规约对用户和业务方案造成的实际影响：

- 安全规约转写为用户身份、数据保护和失败处置；
- 体验规约转写为交互反馈、可访问性和多形态适配；
- 兼容性规约转写为支持范围、降级体验和上线条件；
- DFX 规约转写为性能、资源和运行保障；
- 可观测性规约转写为问题定位、运营统计和发布保障。

rule_id、适用矩阵和阶段消费要求保留在 AI 执行面。Story 用业务语言回答“这项要求对用户和方案意味着什么”。

日志级别、VOC 字段和 Chart 事件协议不进入 Story 正文；人在 Story 中看到的是为什么需要定位能力、希望统计什么以及这些能力如何保障业务。

### 3.5 评审决定的人读投影

AR/review.md 是完整的人类决策界面，每个议题包含：

1. 需要决定的问题；
2. 当前建议；
3. 支撑建议的业务事实；
4. 选择不同方案的影响；
5. 人工选择和补充说明区域。

Story 只承载当前建议及其对整体叙述有帮助的原因。议题 ID、协议状态、来源坐标和选择控件由 Review 维护。

### 3.6 Markdown 表达策略

表达形式按内容选择：

| 内容关系 | 推荐形式 |
|---|---|
| 多项同维度比较 | 表格 |
| 有先后、分支、恢复关系的流程 | Mermaid 流程图或状态图 |
| 界面、原型、架构示意 | 图片 |
| 顺序步骤 | 编号列表 |
| 并列要求 | 项目列表 |
| 关键结论或风险 | 简短强调或引用块 |
| 连续解释和因果关系 | 段落 |

每张表、图和图片都应服务于理解，并在相邻正文中说明读者需要关注的结论。

### 3.7 图片导入与引用

图片沿用 Story 的正式导入链：

1. import_sources.py 解析 DOCX 等源材料并提取图片；
2. 路径库确定 feature、AR 和 assets 的统一位置；
3. Story 使用相对链接引用已导入资源；
4. story-build 在装配和检查时验证引用归属与产物一致性；
5. 目标仓适配时通过路径配置迁移资源位置。

paths.py 服务 Python 脚本，paths.cjs 服务 Node.js 脚本；两者表达同一组路径语义，并由路径一致性测试保证结果相同。

## 4. Story、Spec 与 Review 的一致性

### 4.1 统一来源指纹

story-build.mjs 作为 Story 来源指纹和装配一致性的唯一实现，负责：

- 计算 Story 所消费源文件的指纹；
- 把指纹写入 Story 装配元数据；
- 检查上游源变化；
- 检查 Story 装配结果；
- 检查 Review 机器区与决定登记的一致性。

所有生命周期检查调用这项能力，保持相同的文件集合、指纹算法和错误语义。

### 4.2 Spec 闭环

Spec 阶段完成需求和验收成文后，按以下顺序闭环：

1. 完成并校验 spec.md 与 acceptance.yaml；
2. Spec 作者依据最终 Spec、原始材料和决定登记，同步更新 AR/story-src/chapters 与 decisions.json；
3. 运行 Story build，装配最新 Story 和 Review 机器区，并保留 Review 人工区；
4. 运行 Story check 与 Review check；
5. 运行 Spec post_check 和 verifier。

这样，Spec 闭环时 Story 一定对应本次 Spec 的最终内容，人工填写的 Review 区域继续保留。

### 4.3 Plan 入口与闭环

Plan 将 spec.md、acceptance.yaml、上下文事实和工程知识作为设计输入。Story 保持人读投影身份，不承担技术真源职责。

Plan 的 post_check 调用 Story check：

- 指纹一致时继续完成 Plan 校验；
- 指纹变化时把修正落点明确为 Spec，待 Story 重新装配并完成 Spec 闭环后继续 Plan。

Plan 对 Spec、Acceptance、Story 和 Review 按只读上游产物处理。Plan 自己负责 contracts.yaml、use-cases.yaml 和 plan.md。

### 4.4 语义守恒审查

离线测试提供“上游事实域 → Story 章节”的语义回归夹具，覆盖：

- 事实保留；
- 合法合并；
- 冲突处理；
- 决定投影；
- 机器协议隔离；
- 图片引用；
- Spec 改动后的指纹失配。

确定性脚本负责结构与指纹，verifier 负责语义是否完整、准确和适合人阅读。

## 5. Spec 的工程知识职责

### 5.1 设计模式候选登记

设计模式清单存在实际 pattern_id 时，Spec 根据需求事实逐个“适用单元”识别候选。适用单元是可以独立分析的业务流程、页面交互或后台处理单元。

候选集合完全来自目标仓 design-patterns 路由表：目标仓使用其他模式时按真实清单判断；模式清单为空时表示工程级关闭该能力，Spec 省略模式候选章节。

候选表保持以下列：

| 适用单元 | 业务事实 | 候选 pattern_id | 需求/契约证据 |
|---|---|---|---|

判断规则：

1. 从业务事实出发匹配 applies_when 和 not_applies_when；
2. 每个适用单元独立判断；
3. 有候选时登记受控 pattern_id；
4. 单元确实不适用时登记“无候选”并给出事实；
5. Spec 只登记候选，采用决定由 Plan 完成。

### 5.2 规约需求投影

Spec 消费适用于 Story / Spec 的规约域，把会改变需求、体验、边界和验收的要求写入正式章节与 acceptance.yaml。

规约信号以实际需求事实为基础。一次需求只需要覆盖实际命中的条目，命中结果应能在需求或验收中找到具体影响。

### 5.3 验收所有权

Acceptance 属于 Spec 的需求合同。验收标准、边界条件和测试分层在 Spec 阶段形成。

Plan 可以基于这些标准设计 use-cases、接口、状态和文件落点；当工程分析表明验收本身需要变化时，修正回到 Spec。

### 5.4 定位上报与统计埋点

Spec 只描述业务上需要定位和统计什么，不规划具体日志调用点。

原“埋点”契约按用途拆为两部分：

#### VOC 定位上报

| 业务流程 | 定位目的 | 关键路径、状态与控制位 | 结果与异常 | 代码现状 |
|---|---|---|---|---|

VOC 用于拿不到本地日志时的问题定位，因此需求事实必须说明哪些路径选择、业务状态、控制字段、结果码和异常会决定流程或最终结果。

#### Chart 统计埋点

| 业务流程 | 业务步骤 | 指标目的 | 结果字段 | 时延口径 | 代码现状 |
|---|---|---|---|---|---|

Chart 明确属于埋点。统计步骤来自业务流程而非内部函数或状态机节点，每个步骤都具备明确起止、结果和时延口径。

## 6. Plan 的工程知识决策

### 6.1 先应用、后登记

Plan 按以下顺序工作：

1. 读取 Spec 候选、规约适用矩阵和目标代码仓事实；
2. 完成实际模块、SDK、依赖、调用点和既有案例探索；
3. 对候选模式逐项判断适用性与可实施性；
4. 把采用模式的角色、流程、状态、接口和文件落点写入主体设计；
5. 把命中规约转化为接口、数据、资源、配置和验证设计；
6. 以业务流程和步骤为基础完成日志、VOC、Chart 可观测性设计；
7. 生成 plan.md 的工程知识决策区；
8. 将已生效的决定冻结到 contracts.yaml 与 project_knowledge。

工程知识决策区承担选择说明和审查入口；主体设计与正式合同承担实际设计。

### 6.2 设计模式选择表

Plan 中每个 Spec 候选都有一条完整处置记录：

| 适用单元 | 候选模式 | 适用事实 | 反向证据 | 目标仓可实施性 | 结论 | 设计影响 | 合同引用 |
|---|---|---|---|---|---|---|---|

其中：

- 适用事实对应模式的 applies_when；
- 反向证据对应 not_applies_when 及本需求简化条件；
- 目标仓可实施性来自真实 SDK、包元数据、工具链、模块结构和既有业务案例；
- 结论使用“采用”或“不采用”；
- 设计影响说明模式如何改变主体设计；
- 合同引用精确指向 contracts.yaml、acceptance.yaml 或 use-cases.yaml 中的对象。

### 6.3 目标仓可实施性

Plan 采用设计模式前必须确认：

1. SDK 包名、版本和真实导出；
2. 类型、方法、泛型、字段和运行时行为；
3. 最低 SDK、语言和工具链限制；
4. 目标模块中的依赖接入方式；
5. 目标仓已有业务案例的入口、持有者、生命周期和失败路径；
6. 本需求与既有案例之间可复用和需定制的部分；
7. 最小编译骨架成立。

这些证据写入上下文事实和 Plan 选择说明，采用结果再进入正式合同。

### 6.4 模式实例设计

采用模式后，Plan 必须在主体设计和合同中冻结：

- 适用业务单元；
- 唯一实例名；
- 模式角色与各自职责；
- 上下文对象和所有者；
- 入口与调用方边界；
- 节点或动作集合；
- 自动推进关系；
- 用户等待点；
- 停止和恢复方式；
- 成功结果与失败收敛者；
- 与其他模式组合时的交接接口；
- 代码、行为和验证的精确引用。

页面交互编排与流程分支编排组合时，页面交互负责用户动作和等待恢复，流程分支负责后台业务分支；两者通过显式接口或业务状态交接。

### 6.5 规约义务表

Plan 对适用于 Plan 的每个规约域给出一条判断：

| 约束域 | 本需求事实 | 命中 rule_id | 设计义务 | 实现引用 | 验证引用 |
|---|---|---|---|---|---|

命中条目必须改变至少一项正式设计。实际命中的条目进入 project_knowledge.constraint_obligations；其余判断保留在 Plan 说明中。

### 6.6 可观测性设计

Plan 为每条新增或改变的必要业务流程建立统一流程索引，再分别规划日志、VOC 和 Chart：

1. 定义稳定 flow_id、业务步骤和必要的流程实例关联字段；
2. 划分连续必经路径、分支边界、异步边界和异常边界；
3. 规划 Debug 与 Info/Error 日志检查点；
4. 从日志检查点中提炼决定主路径和结果的 VOC 事件；
5. 为每个业务步骤规划一次终态 Chart 埋点；
6. 明确字段、触发时机、合并关系、时延口径和数据策略；
7. 将设计写入 contracts.yaml > observability，并由规约义务精确引用。

同一流程遵守“日志 > VOC > Chart”的信息密度和预期频次：

- 日志覆盖全部必要诊断检查点；
- VOC 覆盖会改变路径或结果的关键节点、状态、控制位和异常；
- Chart 只在业务步骤结束后记录统计结果。

连续且必然执行的路径段使用一条结构化 Info 汇总日志；分支、异步和异常边界分别保留独立日志。内部重试过程进入日志和 VOC，Chart 在重试收敛后只上报该业务步骤的一次终态结果。

## 7. project_knowledge 机器合同

### 7.1 定位

project_knowledge 是 contracts.yaml 中的 Extension 工程知识区，用于把 Plan 已采用的设计模式和实际命中的规约冻结给下游。

它与 contracts.yaml 中的模块、接口、数据、文件和追溯对象组成同一份 Plan 合同。Extension 的 hooks、rules overlays 和 verifier 消费该区。

### 7.2 精确引用模型

引用使用类型明确的对象：

~~~yaml
artifact: contracts
kind: interface
id: WalletPaymentOrchestrator
~~~

字段约束：

| artifact | 允许的 kind | id 含义 |
|---|---|---|
| contracts | module、data_model、interface、component、file、resource_key、navigation、observability_flow、log_point、voc_event、chart_event | contracts.yaml 中对象的唯一 ID 或项目根相对路径 |
| acceptance | criterion、boundary、performance | acceptance.yaml 中对象的唯一 ID |
| use-cases | use_case、branch | use-cases.yaml 中对象的唯一 ID |

四类引用按用途命名：

- contract_refs：模式在正式技术合同中的结构与协作对象；
- behavior_refs：模式影响的可观察业务行为；
- implementation_refs：规约要求对应的实现对象；
- verification_refs：规约要求对应的验收或用例对象。

每条引用必须解析到唯一对象，artifact 与 kind 必须匹配目标产物。

### 7.3 合同结构

~~~yaml
project_knowledge:
  pattern_applications:
    - unit: payment_confirmation
      pattern_id: page-interaction
      knowledge_ref: doc/extensions/knowledge/design-patterns/page-interaction.md
      instance:
        name: PaymentConfirmationInteraction
        owner: PaymentConfirmationPage
        context: PaymentConfirmationContext
        entry: confirmPayment
        roles:
          - id: interaction_manager
            responsibility: 编排页面动作与后继关系
        actions:
          - id: validate_order
            next: request_confirmation
          - id: request_confirmation
            wait_for_user: true
            resume_by: confirmPayment
        success_result: payment_submitted
        failure_owner: PaymentConfirmationPage
      contract_refs:
        - artifact: contracts
          kind: component
          id: PaymentConfirmationInteraction
      behavior_refs:
        - artifact: use-cases
          kind: use_case
          id: UC-PAY-CONFIRM

  constraint_obligations:
    - domain: security-privacy
      rule_ids:
        - SEC-001
      decision: 提交前重新校验账户和绑卡状态
      implementation_refs:
        - artifact: contracts
          kind: interface
          id: PaymentEligibilityGateway
      verification_refs:
        - artifact: acceptance
          kind: criterion
          id: AC-PAY-REVALIDATE

    - domain: observability
      rule_ids:
        - OBS-02
        - OBS-03
        - OBS-04
      decision: 支付提交流程使用分层日志、VOC 定位上报和业务步骤 Chart 埋点
      implementation_refs:
        - artifact: contracts
          kind: log_point
          id: LOG-PAY-RESULT-INFO
        - artifact: contracts
          kind: voc_event
          id: VOC-PAY-DIAGNOSIS
        - artifact: contracts
          kind: chart_event
          id: CHART-PAY-SUBMIT-RESULT
      verification_refs:
        - artifact: acceptance
          kind: criterion
          id: AC-PAY-OBSERVABILITY
~~~

示例只说明结构；正式 pattern_id、rule_id、对象 ID 和字段值均来自目标需求与目标仓事实。

### 7.4 最小完备性

采用模式的机器合同必须满足：

1. unit + pattern_id 唯一；
2. knowledge_ref 指向所采用模式文档；
3. instance 信息足以还原模式的业务结构和运行语义；
4. contract_refs 至少覆盖模式主体；
5. 有外部可观察行为时提供 behavior_refs；
6. Plan 采用项与 pattern_applications 一一对应。

以上模式完备性只在目标仓模式清单启用时执行。模式清单为空时，pattern_applications 字段省略，模式相关 post_check、overlay 和 verifier 统一 SKIP。

规约义务必须满足：

1. domain 属于本阶段适用域；
2. rule_ids 均来自规约知识库；
3. decision 是已经进入主体设计的工程决定；
4. implementation_refs 和 verification_refs 均可唯一解析；
5. Plan 命中项与 constraint_obligations 一一对应。

### 7.5 验证分层

verification_refs 只指向 Acceptance 或 Use Case。具体由 UT 还是 Testing 验证，继续以 acceptance.yaml 中的 ut_layer、ut_focus 和 device_focus 为准。

## 8. 工程对象与可观测性合同

### 8.1 模块、依赖与文件分类

Plan 对工程对象采用统一分类：

| 对象 | 合同位置 | 设计要求 |
|---|---|---|
| 项目源码模块 | contracts.modules | 使用 module catalog 中的权威模块 |
| 源码文件 | contracts.files | 项目根相对路径、职责和所属模块 |
| 资源文件 | contracts.files | 资源路径、用途和 key |
| 路由与配置文件 | contracts.files | 修改位置、字段和影响 |
| 预编译 HAR/HSP/npm 包 | 依赖设计及相应配置文件 | 包身份、版本、导出、接入位置和兼容条件 |
| 跨模块接口 | contracts.interfaces / exports | 调用边界和导出入口 |

contracts.files 覆盖本次计划修改的源码、资源、路由和配置。可编译性检查以这些真实落点为准。

### 8.2 三层可观测性

三类渠道使用同一业务 flow_id 和 step_id，但承担不同职责：

| 渠道 | 目的 | 信息密度 | 触发密度 | 核心内容 |
|---|---|---|---|---|
| Debug / Info / Error 日志 | 本地调测与完整流程还原 | 最高 | 最高 | 出入口、必要节点、控制位、分支、状态、外部结果、异常和原始调测数据 |
| VOC 定位上报 | 无本地日志时远程定位问题 | 中 | 中 | 决定主路径或结果的节点、状态、控制位、结果码与异常 |
| Chart 统计埋点 | 时延、成功率等统计 | 最低 | 最低 | 业务步骤、终态结果、错误码、规范化描述和时延 |

“日志 > VOC > Chart”是合同语义，不用固定数量配额判断。Plan、Review 根据同一条业务路径核对三类触发点是否体现由密到疏。

### 8.3 observability 合同

可观测性写入现有 contracts.yaml，不产生独立文件：

~~~yaml
observability:
  flows:
    - id: payment_submission
      description: 支付确认后的提交与结果处理
      correlation_field: flow_instance_id

      log_points:
        - id: LOG-PAY-ENTRY-DEBUG
          level: debug
          trigger: 进入支付提交
          purpose: 调测提交上下文
          fields: [flow_id, flow_instance_id, request_context]
          payload_policy: raw_business
          excluded_fields: [credential, access_token, session_secret, private_key]
        - id: LOG-PAY-RESULT-INFO
          level: info
          trigger: 连续必经提交路径完成
          purpose: 一条日志还原提交路径及结果
          fields: [flow_id, flow_instance_id, control_state, branch, result_code]
          payload_policy: protected
          merge_group: payment_submit_required_path
        - id: LOG-PAY-ERROR
          level: error
          trigger: 提交或结果处理异常
          purpose: 记录异常点及已积累流程上下文
          fields: [flow_id, flow_instance_id, checkpoint, state, error_code]
          payload_policy: protected

      voc_events:
        - id: VOC-PAY-DIAGNOSIS
          type: diagnosis
          trigger: 关键分支或业务步骤结果确定
          fields: [flow_id, flow_instance_id, checkpoint, path_summary, control_summary, state, result_code, result_description]
        - id: VOC-PAY-EXCEPTION
          type: exception
          trigger: 不可恢复异常
          fields: [flow_id, flow_instance_id, checkpoint, state, error_code, error_description]

      chart_events:
        - id: CHART-PAY-SUBMIT-RESULT
          step_id: submit_payment
          trigger: 业务步骤内部重试收敛后的终态
          fields: [flow_id, step_id, success, error_code, error_description, duration_ms]
~~~

合同约束：

1. 每个 flow、log point、VOC event、Chart event 都有唯一 ID；
2. log_points 覆盖必要业务路径的入口、出口、控制、分支、状态、结果和异常；
3. 同一连续必经路径的 Info 日志通过 merge_group 归并为一次结构化输出；
4. VOC 事件自身包含足够定位信息，不依赖本地日志才能理解；
5. 每个 Chart 业务步骤只有一个终态事件；
6. Chart 在内部重试完成后记录最终结果，重试明细归日志和 VOC；
7. error_description 使用稳定、可统计的规范化描述，原始堆栈留在 Debug 或诊断信息中；
8. 上报失败不改变业务流程、结果、分支或重试。

### 8.4 数据分级

安全与可观测性使用一致的数据分级：

- Debug 可以打印未脱敏业务原值和原始业务数据结构；
- 凭据、访问令牌、会话秘密和密钥在所有渠道中排除；
- Info、Error、VOC、Chart 对受保护业务字段采用省略或脱敏；
- Chart 只携带统计所需的低基数字段；
- VOC 携带定位所需的路径和状态摘要，不复制完整业务对象。

security-privacy 中 SEC-01 按上述规则重写，observability 域负责三类渠道的覆盖、密度和字段语义，二者共同形成唯一一致的执行要求。

### 8.5 Demo 正式能力

为了让本地 CLI 能在 Coding 与 Review 阶段验证真实落地，Demo 在 05-SystemBase/CommFunc 提供正式通用能力：

#### Logger

- 新增 Logger.debug(tag, format, ...args)，调用 hilog.debug；
- 保留 Logger.info 和 Logger.error；
- 业务对象由调用方按合同序列化，Debug 原值与秘密字段排除规则由 Coding 和 Review 核对。

#### VocReporter

- 提供强类型 VocEvent；
- 提供 VocReporter.report(event)；
- 基于 PerformanceAnalysisKit 的 hiAppEvent 写入；
- 正常诊断使用 wallet_voc / flow_diagnosis；
- 不可恢复异常使用 wallet_voc / flow_exception；
- 正常诊断使用 BEHAVIOR，异常使用 FAULT。

VocEvent 至少包含：

- flowId；
- flowInstanceId；
- checkpointId；
- pathSummary；
- controlSummary；
- state；
- resultCode；
- resultDescription；
- exception。

#### ChartReporter

- 提供强类型 ChartEvent；
- 提供 ChartReporter.report(event)；
- 基于 hiAppEvent 写入 wallet_chart / flow_step_result；
- eventType 使用 STATISTIC。

ChartEvent 固定包含：

- flowId；
- stepId；
- success；
- errorCode；
- errorDescription；
- durationMs。

两个 Reporter 都采用非阻塞写入。写入失败只通过 Logger.error 留证，不向业务调用方传播，也不触发业务补偿或重试。

Logger、VocReporter、ChartReporter 通过 CommFunc 的 index.ets 导出，并同步更新 module catalog、glossary、architecture 责任说明与 codebase facts，使 Plan 和 Coding 能从真实代码仓发现能力。

## 9. 下游阶段消费

### 9.1 共享注入

Coding、Review、UT、Testing 继续通过 manifest.yaml 中现有阶段的 on_context_load 注入共享知识：

- hooks/shared/constraint-application.md。
- 模式清单启用时再消费 hooks/shared/design-pattern-application.md；空清单时该能力立即结束，不生成阶段动作或产物要求。

共享提示统一说明：

1. 先读取 project_knowledge；
2. 模式能力启用时，再按 knowledge_ref 读取实际采用的模式文档；
3. 读取 contracts.yaml > observability 和实际命中的可观测性规约；
4. 按本阶段职责消费对应引用；
5. 用真实产物和证据证明执行结果。

### 9.2 Coding

Coding 对每个 pattern_application：

1. 读取 instance、contract_refs 和 behavior_refs；
2. 按模式文档的 coding 约定实现角色、上下文、节点或动作、入口和推进语义；
3. 按 contracts.files 创建或修改源码、资源和配置；
4. 对每个 constraint_obligation 落实 implementation_refs 对应义务；
5. 逐文件完成 lint 与编译闭环；
6. 在交付回执中列出采用项、实现引用和验证证据。

模式的生效表现必须出现在代码结构和运行语义中，而不是仅出现在命名或注释中。

Coding 同时按 contracts.yaml > observability 落实：

1. Debug 覆盖必要调测数据并排除秘密字段；
2. Info 覆盖业务出入口、控制位、分支、状态和结果；
3. 连续必经路径按 merge_group 合并日志；
4. VOC 覆盖关键路径、状态、控制字段、结果码和异常；
5. Chart 在每个业务步骤终态上报成功、失败、错误信息和时延；
6. Reporter 失败与业务执行隔离。

### 9.3 Review

Review 以真实 diff 为审查对象，对每个采用模式和规约义务逐项判断：

| 结论 | 含义 |
|---|---|
| 已实现 | 设计语义、实现引用和行为证据一致 |
| 有偏差 | 代码已经实现，但与合同或模式语义存在差异 |
| 上游合同需修正 | 当前合同与目标仓事实冲突，实施无法按合同成立 |

Review 核对：

- 模式角色是否完整；
- 入口、自动后继、等待、停止、恢复和失败归属是否符合模式；
- 调用方边界是否保持；
- 规约义务是否落实到实际代码、资源或配置；
- 日志是否足以还原流程并避免连续必经路径的重复打印；
- VOC 是否可以独立定位主要路径、状态、控制位、结果和异常；
- Chart 是否以业务步骤为粒度且每步只有一次终态结果；
- 三类观测是否满足“日志 > VOC > Chart”的信息与触发密度；
- Debug 是否排除凭据、令牌、会话秘密和密钥；
- 上报失败是否与业务结果隔离；
- 合同引用是否对应真实 diff；
- 实现是否超出 Scope。

Review 报告面向人阅读，用自然语言说明影响、证据和建议；机器标识用于追溯。

### 9.4 UT 与 Testing

UT 和 Testing 从 verification_refs 找到可观察行为，再依据 acceptance.yaml 的分层执行：

- UT 验证主路径、分支、失败、停止和恢复等业务行为；
- UT 验证业务步骤结果到 Chart 结果的映射、终态唯一性以及异常路径；
- Testing 验证真机、系统能力、设备形态和环境交互；
- Testing 采集实际日志、VOC 与 Chart 事件，核对字段、时机和时延；
- 纯结构性模式通过 Plan、Coding 和 Review 证据闭环；
- 测试结论回指 Acceptance 或 Use Case，不断言内部类名和文件布局。

## 10. 设计模式文档与目标仓适配

### 10.1 设计模式能力结果

目标仓适配先决定实际模式能力，结果只有三类：

#### 模式清单为空

模式清单为空表示工程级关闭设计模式能力：

- design-patterns 目录保留 README 空清单说明；
- manifest knowledge 不登记模式正文；
- Spec 和 Plan 省略模式候选、选择章节；
- project_knowledge 省略 pattern_applications；
- Coding、Review、UT、Testing 的模式消费自然跳过；
- verify-adaptation 输出 disabled，并核对各阶段不存在残留模式要求。

这与“模式能力已启用、单个需求零命中”严格区分：后者仍需按实际单元给出候选或不采用结论。

#### 目标仓使用其他模式

目标仓真实模式替换本仓 decision-tree 与 page-interaction：

- README 路由表登记真实 pattern_id、适用事实和划分粒度；
- 每个模式建立同结构知识文档；
- manifest knowledge 登记真实文档；
- 绑定记录使用真实 Skill、SDK、案例和指纹；
- hooks、post_check、overlays 和测试全部从清单动态读取，不依赖当前两个名称。

#### 目标仓存在对应模式

按真实 Skill、SDK、包元数据和多个业务案例重建当前两份模式文档，demo API、类名和工程结论全部替换为目标仓事实。

### 10.2 设计模式文档结构

每份模式文档统一包含：

1. 解决什么问题；
2. 适用事实；
3. 反向适用事实；
4. Plan 契约投影；
5. Plan 应用步骤；
6. SDK 行为事实；

11. 常见错误形态及迁移方向；

- 入口和调用边界在哪里；
- 失败由谁收敛；
- 模式结构如何进入 contracts 和 use-cases；
- 每个下游阶段如何证明模式生效。

### 10.4 内网目标仓适配顺序

1. 内网真实设计模式 Skill；

3. 目标业务代码仓中的多个既有应用案例；
4. 本仓 demo 模式文档的结构与写法。

模式清单启用时，内网模型对每个 pattern_id 执行：

1. 读取真实 Skill；
2. 检查 SDK 包身份、版本、导出和最低环境；
3. 沿多个既有案例读完入口、持有者、context、节点或动作、停止、恢复和失败路径；
4. 区分 SDK 强制行为与团队工程约定；
5. 把真实事实映射到统一模式文档结构；
6. 写出最小可编译骨架；
7. 回填适配状态、证据和指纹；
8. 运行自包含适配验证；
9. 用自然适用需求和自然非适用需求完成实跑。

### 10.5 模式适配完成标准

每个模式完成适配时应具备：

- 真实 Skill 引用；

## 13. 正式测试场景

### 13.1 自然命中两种模式

原始需求通过功能复杂度自然形成：

- 一个页面具有多个用户动作、异步反馈、等待确认和回调恢复；
- 页面触发的后台业务流程具有多个复杂分支；
- 每个分支包含多步调用、失败收敛或补偿；
- 页面交互与后台分支通过显式业务接口交接；
- 流程包含可影响路径的控制位、状态变化、外部结果、异常和内部重试；
- 每个业务步骤都有明确起止、结果和时延。

需求材料不出现设计模式名称、pattern_id、SDK 类名或“必须使用某模式”的提示。

预期观察：

1. Spec 根据业务事实登记两个候选；
2. Plan 根据真实仓可实施性采用两个模式；
3. 主体设计体现两个模式的职责和组合边界；
4. contracts 与 use-cases 冻结实例、行为和精确引用；
5. Plan 形成日志、VOC、Chart 的完整 observability 合同；
6. Coding 形成相应代码结构、运行语义和观测调用；
7. Review 能逐项核对模式、规约和可观测性生效情况。

### 13.2 自然零命中

选择一个线性、局部、低复杂度需求，验证模型能够基于事实得出无候选或不采用结论，并保持设计简洁。

### 13.3 规约命中组合

测试需求自然包含：

- 提交前状态复核；
- 隐私影响；
- 多形态与可访问性；
- 失败恢复；
- 资源、配置或路由修改；
- 必要业务流程的日志、VOC 和 Chart 观测要求。

预期观察规约从需求影响进入设计义务，再进入代码或验证证据。

### 13.4 图片正式导入

使用包含界面图或流程图的 DOCX 作为正式需求输入：

1. 通过 import_sources.py 导入；
2. 检查资源落点和相对链接；
3. 检查 Story 展示；
4. 检查 build/check 后链接保持；
5. 检查 Spec、Plan、Coding、Review 推进期间图片引用保持有效。

### 13.5 合同边界验证

离线夹具覆盖：

- pattern_id 与 rule_id 的受控集合；
- Spec 候选、Plan 结论与 project_knowledge 的一一对应；
- ref 对象的 artifact、kind、id 唯一解析；
- 模式实例共同字段与模式专属语义；
- 源码模块、预编译依赖、源码、资源和配置的分类；
- Acceptance、Plan 和 Coding 的阶段所有权；
- Story 来源指纹、Review 人工区和归档状态。

### 13.6 设计模式适配结果

离线构造三种目标仓：

1. 当前两个模式的 Demo 仓；
2. design-patterns 清单为空的关闭仓；
3. 只包含不同 pattern_id 和结构的替代模式仓。

验证 Spec、Plan、project_knowledge、共享 hooks、各阶段 overlays 和 verify-adaptation 对三种结果解释一致，且机制代码不依赖 decision-tree 或 page-interaction 名称。

### 13.7 可观测性完整链路

对同一条含正常路径、分支、内部重试和异常的业务流程检查：

1. Spec 分开表达 VOC 定位目的和 Chart 统计口径；
2. Plan 按业务流程与步骤生成 observability 合同；
3. Debug 可以携带未脱敏业务原值，但排除凭据、令牌、会话秘密和密钥；
4. Info 覆盖出入口、控制位、分支、状态、结果和异常；
5. 连续必经路径的 Info 输出按 merge_group 合并；
6. VOC 能在无本地日志时独立还原关键路径与结果；
7. Chart 每个业务步骤只产生一次重试收敛后的终态结果；
8. 三类渠道满足日志 > VOC > Chart 的信息密度和预期频次；
9. VocReporter 或 ChartReporter 写入失败不改变业务执行结果；
10. Review 对每一项给出真实 diff 证据。

## 14. 验收标准

### 14.1 Story 与 Review

- Story 使用约定的一级目录；
- 子章节标题符合业务阅读习惯，并能按复杂度合理拆到三级、四级；
- 七类人读信息域语义完整；
- 正文保持自然叙述，规约与决策经过人读投影；
- 表格、图、图片、列表和强调按内容恰当使用；
- Review 议题能够支持人完成理解和选择；
- 图片经正式导入链后可正常显示；
- Spec 变化会触发一致性检查。

### 14.2 Spec 与 Plan

- 模式清单启用时，Spec 按实际业务单元登记真实模式候选；
- 模式清单为空时，Spec、Plan 和下游完整关闭模式能力；
- 每个候选在 Plan 中完成事实、反证、可实施性和结论判断；
- 采用模式已进入主体设计、contracts 和 use-cases；
- 命中规约已形成具体设计义务；
- project_knowledge 只包含采用模式和实际命中规约；
- Spec 已区分 VOC 定位上报与 Chart 统计埋点；
- Plan 已按业务流程和步骤形成 observability 合同；
- 所有 refs 可唯一解析并与 artifact、kind 匹配；
- 源码模块、预编译依赖、源码、资源和配置分类正确；
- Acceptance 由 Spec 维护，Plan 在其基础上完成设计。

### 14.3 Coding 与 Review

- Coding 能从合同还原模式实例并落实运行语义；
- 代码体现入口、推进、等待、停止、恢复和失败归属；
- 规约义务落实到引用对象；
- Debug、Info/Error、VOC、Chart 使用 Demo 或目标仓真实 API；
- Info 足以还原流程并合并连续必经路径；
- VOC 独立覆盖关键路径、状态、控制位、结果码和异常；
- Chart 以业务步骤为粒度并保持每步一次终态结果；
- 凭据、令牌、会话秘密和密钥未进入任何观测渠道；
- 上报失败不改变业务结果；
- Review 依据真实 diff 对每项模式和规约给出证据结论；
- 结构、行为和 Scope 与 Plan 合同一致。

### 14.4 适配与工程边界

- 内网适配以真实 Skill、SDK、包元数据和业务案例为依据；
- 内网可按真实情况关闭设计模式能力或替换为其他模式；
- Logger、VOC、Chart 绑定均来自目标仓真实能力；
- Extension 通过 manifest、hooks、rules overlays 和现有阶段产物完成能力扩展；
- framework 保持发布件完整性；
- 测试历史迁移到 E:\Project\bak 并可用于版本对比；
- 正式 CLI 报告与产品修改分为两个确认步骤。

用户确认本方案后，按第 12 节顺序实施。实施结束后先完成离线回归，再运行正式 CLI 到 Review。最终提交：
