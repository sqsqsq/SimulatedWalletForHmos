# 03 步骤 1：人的表态、评审载体与流程契约

覆盖 01 的 A、B 域与 G01–G05。只改 extension 的流程脚本、评审渲染与相关规则文档；framework 只读。

## 1. 目标结果

1. 契约里每一笔 `by: human` 都能指回人的原话与当时展示给人的选项；模型不能在问人之前或不问人就落人签。
2. 停等消息由脚本从契约生成，人看到的选项、顺序、推荐与契约记录一致，不带路径与命令。
3. 依据变化只经 `/story update`；update 的状态在所有命令里判定一致，冲突登记为议题并问人，传播与记录完整。
4. 评审记录的人工区只有三态与修改意见；议题形态、决定人、依据都合规，渲染不误报。
5. 流程契约只有一个写入者，手改能被发现并给出恢复路径。

## 2. 现状与证据

- **人签与停等**：A01–A10、A13、A25、A26（代签、编造依据、侧车滞后、裸编号、改写标签、占位未替换、推荐自相矛盾、停等表缺 framework 关卡）。
- **会议**：A11–A14、G01（该问的没问、暂缓写成实现、null 误报、问询规则贴着答案卷）。
- **流程契约与 update**：A15–A24、A27、A28、G02–G05（四命令死锁、手改契约、未取上游、绕过导入、无基准、示例缺参、交付门口头评审入口、冲突被覆盖、传播不全、决定人写成文档、路径不能复制、静默兜底、路由重复文档）。
- **评审载体**：B01–B13。

## 3. 正向设计

### 3.1 停等与人签

**停等表是唯一清单**（`SKILL.md` 停等一节）：
- 列出全部停等点：材料关卡、会议裁决、范围关卡、术语确认、视觉 provider、交付门、update 材料关卡。
- 每行写：谁问、何时问、选项来源、怎样记录。
- 术语确认与视觉 provider 两行写明它们是 framework 的关卡：术语在交互态由人确认后才勾 `[x]`；视觉 provider 的回答用 framework 的 `record-visual-provider` 落盘。

**选项由脚本出**：
- `story_flow.py status` 到了停等点时，除 `next` 之外返回 `ask`：`{gate, ask_id, options:[{no, id, label}], recommend, missing, why}`；同时写侧车。停等之前侧车就已在盘上。
- 固定选项的顺序由契约定，推荐用单独一行「推荐：n（理由）」表示。这替代「推荐项排第一」与「首项固定」两条相互冲突的规则。
- 标签里的占位在生成时替换成实际值。
- 材料关卡的推荐由脚本按 `missing` 算：`missing` 非空就推荐补料。模型把「需求方提到但还没进来的材料」写进 `missing`。
- 停等消息三段：结论与缺口一句、原样的选项块、推荐行。消息里不放路径与命令。

**人签只来自人的回话**：
- `decide --gate <关卡> --ask <ask_id> --reply "<人的原话>"`。脚本核 `ask_id` 与当前侧车一致，把原话映射到选项（编号或标签），记 `{chosen, no, label, reply, by: human, ask_id}`。
- 没有对应 `ask_id` 的 `decide` 一律拒绝，所以「问人之前先签」写不进契约。
- 模型自己的判断用 `decide --propose`，记为 `by: model`。下一次停等时，脚本把未确认的提议列进选项块请人确认。
- 会议话题、术语、update 材料关卡都走同一条路。

### 3.2 会议读取

- **问询判据从原则写**（`phases/meeting-read.md`），替换现在与答案卷逐条对应的写法。下列任一成立就问：
  1. 结论改变本单的范围、接口或验收；
  2. 结论与已归档文档或人已做的决定冲突；
  3. 判不准归属；
  4. 转写存疑且影响结论。
- **暂缓就是未决**：人选「保持待定」的话题登记为 open 议题，产物里写「待定：<谁定、等什么>」，不写任何一种实现。
- **会议停等内容**：要问的话题逐条列出；不问的话题各给一句去向；参会人角色作为一项请人确认。
- `meeting.py` 把缺失与 `null` 都当作「不问」。

### 3.3 流程契约与 update 状态

- **唯一写入者**：`story-flow.json` 由 `story_flow.py` 写，每次写入同时记内容摘要（U19）。命令读到摘要不符时报「契约被手改」并给出 `status` 的恢复路径，然后照常执行，不因此拒绝；摘要只用于发现与恢复，不是门。A16 的根因是 A15 的死锁，由下面的状态函数修。
- **一个状态函数**：`flow/state.py` 提供 `stage_of(contract)`，返回 init 各级、story 成文、已登记、已归档、update 输入、update 进行中、update 已收口。`routing.py`、`submission.py`、`lifecycle.py` 都用它判定，替代各自的判断。update 进行中时：
  - `reopen` 回到当前 update 轮，不开新轮；
  - `complete` 沿用本单已定范围，不再要求范围关卡；
  - 新材料登记进当前 update 轮。
- **取上游**：AR 单的 `update --action inputs` 要求本轮已有取材回执，没有就停下并指明取材那一步；本地单跳过这一项。
- **新原件**：先导入再 `prepare`；收件箱有未并入的原件时，`prepare` 拒绝并列出文件。
- **比较基准**：story 登记即写基准，第一次 update 也能比出「原来怎么写」。
- **报错与读取**：读不到或解析不了的说明、分类、配置、章节一律报错并指明文件；替代现在「读不到当没有」的四处兜底。
- **路径**：导入打印的图片路径就是 `--caption-image` 接受的路径。
- **路由文本**：只给下一步的动作与所在文档章节，规则只在 phase 文档写一次。

### 3.4 update 统一承接依据变化

- **入口**：`SKILL.md` 与 `phases/update.md` 写明 update 承接的四种变化：新材料、评审回流（评审人在 review.md 表态；AR 单经取材取回）、人的新决定、有人直接改过的文档。评审回流不另设流程。
- **交付门**：交付门之后只问「归档送审 / 进入 plan」。删去 `phases/spec.md:85` 与 `routing.py:380` 的交付门评审句。用户开场说「做到评审」时，交付门这一问就是本轮终点的停等。
- **本地单**：`story_flow.py archived` 对本地单只做登记。评审人改本地 review.md 后，update 的比较照常识别。
- **冲突**：新依据与其他仍有效的来源冲突（上游材料、已归档结论、安全口径），或改动已承诺的行为时，登记为 open 议题（两边来源并列），停下问人；不按时间最新覆盖。
- **传播清单**（`update.md`）：spec、acceptance、story、review、plan、contracts、use-cases、AR 提取件与写作设计、`context/facts.md`、会议判断。update-notes 必须有「不变项与理由」表，收口时 `close` 核这张表非空。
- **人的表态**：「通过」这类笼统表态先核针对哪条议题、哪一版，再逐条经决策渠道记原话；决定人只能是人的角色，文档不是决定人。

### 3.5 评审载体

- **人工区**（`review.mjs`）：每条议题只有「评审结论：同意 / 需修改 / 暂缓」与「修改意见：」。choice 议题的选项留在机器区，评审人选别的方案写在修改意见里。这替代勾选框与「不同意原因、调整结论」。
- **议题形态**：open 议题必须是 choice，至少两个可选做法并给建议；settled 议题的依据必须引用人的表态（谁、原话）；形态改变时，人工区为空就按新形态重渲。
- **决定人**：`decider` 只收角色名词（不含「确认」「在…上」等动作词），渲染为「请<角色>评审」。
- **评审人自己给的结论**：记 settled，依据写评审人原话，不再请他人确认。
- **换行归一**：比较人工区前两边都归一成 LF，人没写就不误报。
- **登记什么**：写进 `phases/story-write.md`——
  - 登记：与工程现状矛盾的承诺、降级或模拟承载、自设数值、跨方依赖与确认点、流程性事项；
  - 不登记：实现选型。
- **类别**：`contracts/story-chapters.json` 的决策类别由一张 AR 评审要回答的通用维度推出——范围与交付、业务规则、交互与界面、数据与隐私、依赖与承载、上线与开关、质量指标。替代照评审金样小节名写的类别与「撞的方向」逐行例子。
- **编号**：议题一律用 D 编号；会议话题的 T 编号只在会议判断里用。
- **登记时机**：skeleton 起手前核 `decisions.json` 的结构，不核正文用词——文件要么有议题，要么有一条显式的「本单无待决：<理由>」登记；两者都没有才拒绝起手。有没有漏登记由审查按选项后果核（与 R04 的判法一致，不按「待定」二字判）。
- **依据的写法**：用业务语言，不写关卡号、命令、轮次号。
- **读取**：决策件只认一种顶层形状，形状不对报错并给改法。

## 6. 验收（离线）

| AC | 内容 |
|---|---|
| AC11 | 无 `ask_id` 或 `ask_id` 与侧车不符的 `decide` 被拒；`--reply` 记下原话、编号与标签；`--propose` 记 `by: model` 并出现在下一次 `ask` 的选项块里 |
| AC12 | `status` 在停等点返回的 `ask` 与侧车同源，固定顺序、推荐行、占位已替换；材料关卡 `missing` 非空时推荐补料 |

| AC15 | AR 单缺本轮取材回执时 inputs 停下；本地单跳过；收件箱有未并入原件时 prepare 拒绝；update-notes 缺「不变项与理由」时 close 拒绝 |
