# 步骤 8：废弃机制退出与缺陷修正

2026-09-27，维护设计者。依据用户同日对客户端语境禁用词的问询与裁定，以及 [机制冗余与失效盘点](../2026-09-27-机制冗余与失效盘点.md) 第一批的逐条复核，承接决定 U50–U53。用户定：这些都是废弃机制的退出，合为一步、全部退出、不留残留。在步骤 7 返修提交之后实施，一次提交、一份交回；与步骤 7 合并为一次重跑。本步只删和改，不新增机制。

## 1. 目标结果

1. 实跑里以误拦为主、没有消费者或已失效的机制全部退出：代码、合同、送达、报错、测试、说明零残留。
2. update 期间人的每一句拍板在收口之后仍查得到。
3. 写作指令与代码说同一件事。

## 2. 现状与证据

### 2.1 客户端语境禁用词

- **是什么**：
  - 章节合同 `language_redline.client_vocabulary` 里的七个词（灰度、部署、集群、QPS、TPS、熔断、限流），各配一句改说法，命中即阻断。
  - 豁免有两处：章「交付与上线」、决策类别「上线与开关」的 `banned_terms_exempt`；review.md 上的豁免由 `redactReviewExemptZones` 实现。
  - 在 story 整篇检查、章提交（步骤 7 挪入）、spec 门禁三处判；spec 作者任务包送词表。
- **来由**：8 月 11 日第一版 story 引入（`0304fd23`），目的是不让服务端运维用语进入给端侧评审人看的文档。
- **实跑**：103 份运行记录里 30 份命中。抽样全是误拦：
  - 「解除签约、不回滚进行中的订单」被拦，提示的改法「功能开关关闭」讲不通；
  - 缓存层面的「回退」被拦，不得不另开豁免；
  - 产品稿原词「灰度开关」被拦。

  「回滚」「回退」后来已删出词表，现行七个词在 09-24 之后的实跑里零命中。
- **已有承担者**：写作页规定读者是没参与开发的评审人；读者审查 `story_reader_review` 按「读者能不能读懂」语义判。哪些词会误导读者取决于目标仓自己的产品与习惯，属于目标仓的知识。

### 2.2 其他废弃机制：复核后进本步的

每项都回到实跑报错原文复核过，并核了删掉之后问题会不会挪到更晚的地方暴露。

| 机制 | 复核 |
|---|---|
| spec §9.1 契约小节「表外不许写段落」（`strayProse`） | 命中原文是「现状：检索 `@ohos.net.htt…`」「事件只带车型类别…」这类有依据的契约说明；契约写得是否具体，已由 `spec_ext_conclusion_validity` 按名回查判定 |
| story 附录每节必须一句定位句 | 近期 8 次命中都只让作者补一句说文档自身的话；用户此前的裁定是附录「允许」一句定位，不是「必须」 |
| review 表单禁用行（`reviewFormProblems` 与合同 `review_form_banned_lines`） | 0 命中；review.md 由渲染器生成，表单不再长回来由渲染器测试守；这条正则还会拦评审人在人工区写的「下一步：」 |
| 门禁留痕文件 `ext-post-check.json` | 机制里没有读取方，只有失效形态检查拿它当证据，属于只为测试存在的产品输出；coding 门禁的告警写进这里，审查者看不到（审查提示只含审查前钩子片段） |
| 审查判据 `upstream_inputs_coverage` | 要核的 `spec/context-exploration.md` 不存在；「名字在 SR 中确实存在」已由 `spec_ext_conclusion_validity` 覆盖 |
| 合同死字段 `language_redline.scope`、`sources.*.derived` | 没有读取方（`language.mjs:181` 按每类自己的 scope，默认值在代码里） |

### 2.3 复核后不进本步的

| 机制 | 理由 | 去向 |
|---|---|---|
| spec 门禁「不写文档坐标」 | 删掉后坐标会经规约判定投影进 story 附录，被 ⑩b 在更晚的时点拦下，只是把失败后移 | 随盘点第三节「⑩b 回到真源门禁」重新设计 |
| spec 门禁「带数值的行须标来源」 | 噪声来自逐行粒度，但「数值来源要说清」本身有用（car 的自设 1500 ms 进了验收） | 另立需求重新设计粒度 |
| `decide --propose` | 实跑未用，但它是 1.9.7 步骤 1「人签与模型判断分开」的一部分 | 随人签与推荐两条通道的合并一起看 |
| spec 门禁里的知识自检 `selfCheck` | 目标仓在 adapt 之后改坏知识时，这里是最早发现的地方 | 保留 |
| `AR/story-src/upstream.md` | 实跑只生成过两次，都是归错类；它存在是因为 `AR/design.md` 既是上游原文又会被提取稿覆盖 | 随盘点第三节「上游 AR 正文与提交稿分开」一起退出 |

### 2.4 update 人签收口后丢失（缺陷）

`decide --update` 把人的原话记在契约的 `update.decisions`（`flow/decisions.py:53-60`）；`close` 把 `contract["update"]` 整体改写成 `{"open": None, "last_closed": rid}`（`flow/update.py:599`），`record.json` 也不带它。收口之后原话找不到，与 1.9.7 目标 1 相违。

### 2.5 写作指令与代码不一致

| 位置 | 现状 |
|---|---|
| `phases/update.md` 问人一步 | 把 `<定了哪件事>` 写成议题 id，代码读的是 `--issue` |
| `phases/update.md` 命令表 | `--action status` 报「取材命令」「各阶段有没有产物」，代码没有取材命令，阶段只列有 summary 的 |
| `.claude/commands/story.md` 等跳板的说明 | 「先检测再决定要不要读，取材只写暂存」；`/spec` 列成独立一步 |
| `flow/routing.py`、`flow/rounds.py` | 仍有「冻结」「reopen 作废成文登记」的说法 |
| story 来源括注的报错提示（`story/language.mjs`） | 让作者把来源写进材料清单，而材料清单只许列材料 |

## 3. 正向设计

### 3.1 废弃机制退出（U50、U52）

- 2.1 与 2.2 所列机制整项退出，不设替代机制，也不在 Demo 知识里补同义规约；只为它们存在的部分一并退出。
- 原职责的承担者：

  | 退出 | 由谁承担 |
  |---|---|
  | 客户端语境禁用词 | 读者审查按语义判；用语约定需要时由目标仓写进自己的知识 |
  | §9.1 表外段落门 | 模板引导写法；契约是否具体由 `spec_ext_conclusion_validity` 判 |
  | 附录定位句必需 | 读者审查；写作页与附录骨架里「必须一句定位」改为「可以有一句」 |
  | review 表单禁用行 | 渲染器与它的测试 |
  | 门禁留痕文件 | coding 门禁的告警随门禁返回的消息给作者；审查者按代码与契约自己判，coding overlay 里「告警是审查者的输入」这句失实的说明删掉 |
  | `upstream_inputs_coverage` | `spec_ext_conclusion_validity` |
  | 两个死字段 | 无读取方，无需接替 |

- 语言红线的其余几类不动：工程标识、规约编号、文档坐标、来源括注、仓内路径。它们判的是归档件打不开或看不懂的机械事实。
- 目标仓升级无须动作：这些都是机制退出，演进记录不加条目。

### 3.2 update 人签在收口后可查（U51）

- `close` 把本轮的 `decisions` 原样写进这一轮的 `record.json`，契约只清「开着的那一轮」。
- review 渲染在轮内读契约里的当前记录（`story/review.mjs:570-575`），不受影响。

### 3.3 写作指令与代码对齐（U53）

2.5 各处按代码的实际行为改；跳板只指回 SKILL，不另写流程；来源括注的提示说清规则与机制（来源括注只在主叙事里判），不指向会被另一条判据拦下的位置。
