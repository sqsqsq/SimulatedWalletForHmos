# 04 步骤 2：审查与闭环

覆盖 01 的 C 域与 G05（审查部分）、G06、G09。改 extension 的审查请求、报告采纳、交付门、各阶段门禁与 overlay；framework 只读。

## 1. 目标结果

1. 每阶段 overlay 的全部语义判据都进审查请求，报告逐条有结论；缺一条，门禁点名。
2. WARN 的处置只有一处定义；交付门与这条规则一致；每阶段 verifier 派审一次，业务内容真变了才重审。
3. 审查对象按业务内容计：story 业务章在内，机器区投影不在内；spec 改后投影刷新不需要 reopen。
4. 会让下游重新决定的缺陷判阻断；报告格式在采纳前校验；同一对象的内容结论不能靠重投改写。
5. 能机械核的一致性在脚本层先核；门禁提示一次列全、判得准。

## 2. 现状与证据

- **判据与规则**：C01（判据下发不全）；C02、C03、C04、C19（WARN 规则五处矛盾、交付门不认沿用、WARN 被拦、机械停下条件）。
- **重审与审查对象**：C05、C06、C07（重审循环、审查对象算错、投影刷新要 reopen）。
- **报告与定级**：C08、C09、C17（报告结构未告知、重投覆盖、定级不一、回复未写盘）。
- **可机械核的缺陷**：C10–C14（编号关联漂移、原始编号丢失、图源真假、提示质量、标题）。
- **过程记录与判断**：C15、C16、C18（notes 失实、事实错不回改、为消 WARN 改判断）。
- **示例与重复**：G05、G06、G09。

## 3. 正向设计

### 3.1 判据全量下发

- `hooks/shared/pre_verifier.mjs` 按阶段读 `rules/<phase>-rules.overlay.yaml > semantic_checks`，把全部判据写进请求，不按前缀挑选。
- 请求同时写明报告结构：汇总表每行 `id | status | severity | 证据`；需要细节的判据（如读者审查）写明 `details` 的键与类型。
- `hooks/shared/verifier-report.mjs` 采纳报告时逐一核对判据 id，缺的列成「缺判据：<id>」，按阻断处理。

### 3.2 一条 WARN 规则

规则只写在 `phases/spec.md` 的闭环一节；`phases/update.md`、`hooks/plan/author.md`、`flow/routing.py` 只引用它的章节名。

| 报告结论 | 作者做什么 | 闭环方式 |
|---|---|---|
| 有阻断项 | 按阻断项返修 | 完整 harness → 取新请求再派审 |
| PASS，改动只影响表达（措辞、格式、补说明、补可回查依据） | 修改后跑 `harness-runner --revalidate` | summary 记 `completed_with_prior_review` 与 `script_revalidated`；notes 写「按 <对象> 报告的建议修改，未独立重审」；交付门放行 |
| PASS，改动改变业务口径、范围、验收、契约实体 | 修改后完整 harness | 取新请求再派审 |
| PASS，建议不在本阶段修 | 不改材料 | notes 逐条记建议与去处（下一阶段或评审） |

- **改动属于哪一类由作者判断**，写进 notes；门禁只核记录与 summary 状态是否一致。
- **交付门**（`verifier-report.mjs > withoutCurrentReport`）：去掉「update 进行中一律要求重审」一支，按上表的记录判。update 里哪些阶段改了业务，由 update-notes 声明，`close` 核这些阶段有当前对象的报告。
- **读者审查**（`story/delivery.mjs`）：判 WARN 且没有阻断项时放行，建议项进 notes；只有阻断项才拦，提示指向那一条阻断。
- **停下的条件**（`SKILL.md`）：门禁反复报同一问题、作者判断改不动时，停下向人说明缺什么、需要谁提供；替代「连续三次运行都报了」的机械条件。

### 3.3 审查对象按业务内容计

审查对象的摘要由 framework 计算（`framework/harness/scripts/utils/verifier-material.ts`，只读）：spec 与 acceptance 两份产物，加上扩展注入审查提示的片段的哈希（`lifecycle_hook_fragments`）。扩展只通过自己注入的片段影响它：

- `pre_verifier.mjs` 注入的片段带 story 作者区（各章正文，不含机器区与生成区）的内容摘要。
  - story 业务内容变了，审查对象随之变；
  - 机器区投影刷新时片段不变，审查对象不变。
- 片段里不放随运行变化的内容（时间、轮次、临时路径），同样的材料得到同样的片段。
- 登记后冻结的是作者区。`story-build project` 在登记后可直接刷新机器区，不需要 reopen → complete → story；作者区要改才 reopen。

这是过渡路径：framework 现在只按 spec、acceptance 与注入片段算审查对象，扩展只能借片段传摘要。消费者是交付门与 `withoutCurrentReport`；退出条件是 framework 允许扩展声明审查材料清单（02 §4 已列为上游反馈）。片段里的摘要写成注释形态并标明「审查对象标识，非审查内容」，不让 verifier 把它当材料读。

### 3.4 分级与报告

- **阻断的缺陷类**：让下游必须重新决定的缺陷判阻断（overlay 的 severity 统一为 BLOCKER），包括：
  - 必须设计项缺值；
  - 同一验收编号不同义；
  - 验收不可判定；
  - spec 的现状结论与仓不符；
  - 未决写成已定；
  - plan 义务落地缺行或缺值（`knowledge_obligation_substance`）。
- **报告先校格式**：`verifier-report.mjs` 先校验报告格式，格式不合时原样存为被拒回复并报出改法，不计作一次结论。
- **一个对象一个结论**：同一对象已有格式合规的报告时，新回复被拒，除非材料已变。
- **报告必须落盘**：派审后门禁核报告文件存在；回复只在对话里、没落盘的，点名缺哪一份。
- **notes 如实**：plan 与 spec 的 notes 逐条列出合并报告里的 WARN 行及处置；门禁核 WARN 行都有处置记录。
- **判断改动要有依据**：knowledge-use 的判断在一次审查之后改了，notes 写新依据；overlay 的审查项核「判断变更有新依据」。
- **事实回改**：plan 作者页写明——发现 spec 的现状结论与仓不符，走修正入口改 spec 并登记与现状矛盾的议题，再继续 plan。

### 3.5 机械核前移（脚本层）

- **编号与关联**：spec 门禁核 spec §8 的每个验收编号在 acceptance.yaml 里存在，关联功能一致；同号出现两种含义即报。
- **编号形态一处定义**：AC 编号形态只在 `contracts/story-chapters.json > id_shapes` 定义；spec、ut、testing 门禁都从这里读。
- **原始验收编号**：上游材料里的验收编号（按 `id_shapes.keep`）在 spec §8 或 acceptance.yaml 里都有对应行，或写明不承接的理由。
- **图源标记**：脚本只核来源标记指向的图存在且不是自引用；「是否承接了那张图」是内容判断，交给读者审查已有的图文一致判据，story 作者页写清承接的含义。不用节点文字包含来判同一张图——那会把合法的简化与改措辞报成错。
- **标题**：归档件标题写「编号 需求名」，名称取自需求详情。

### 3.6 门禁提示

- 「一次列全」真列全，不截断；数量多时分组，每组给一个改法。
- 数值来源扫描不把序数（第 N 次、第 N 轮）当数值。
- 图源标记写在围栏外时，报「标记要写在图的围栏里」一条，不分报成两类错。
- 示例一律用中性名：替换与夹具同名、贴着用例的示例（`createBusinessOrder`、「管理台功能开关」「管理台排期」）。
- 合同说明同一件事只写一处（`contracts/README.md`）。

## 8. 实施评审后的决定（2026-09-26）

- **U25**：`reportProblems` 只在格式合规且判据齐时登记 ledger；格式不合的回复不移动，只报（每次运行都报同一问题），「不计作结论」由不登记 ledger 实现；门禁写盘只剩 ledger 一处。拒收文案去掉「放回原处」。审查片段含 story 作者区全文、不含机器区，§3.3 的「摘要」说法改为此；不另带 sha 行。
- **U26**：§3.5 上游原始验收编号以「在 §8 任一行内出现，或在 acceptance.yaml 有 id，或写不承接理由」为承接，不加「沿用编号不重编」规则；关联功能编号形态进 `contracts/story-chapters.json > id_shapes.function`；「同号不同义」只以 §8 第一行为定义，其余行只核编号在册。`hooks/spec/author.md` §8 写一句编号规则与「不承接：<编号> <理由>」写法。
- 金样与 real-run 夹具在测试里各跑一次 spec 门禁（与步骤 4「经生产入口」同口径）。
- `judgement_change_basis`：审查请求给上一份报告路径（`summary.verifier_closure.reviewed_subject_id`），判据以 notes 声明的改动为范围。
- 残留清理：测试删 `updateOpen` 残参；`evidence-rules.md`、`compatibility-checklist.md` 示例换中性。
