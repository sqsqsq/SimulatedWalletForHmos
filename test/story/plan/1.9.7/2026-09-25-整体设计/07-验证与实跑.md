## 3. 实跑

四步全部提交并通过评审后，用户授权起跑；不插中途小实跑（用户 09-25 决定，风险见 00 §5）。

| 项 | 取值 |
|---|---|
| Case | auto-topup（到 spec，第二段：改版 PRD + 系统评审回稿）；car-key-sharing（到 plan，第二段：review.md 评审回流 + 冲突探针） |
| 模型配置 | 与 1.9.6 收口实跑相同（`config/test.yaml` 首项） |
| 宿主 | 按 TEST.md 与各 Case 的测试设计；起跑前读每个 Case 的 `case.yaml`（终点、第二段、`update_inputs`）；每关只答所问、一句；规划条目与提问不相符时按 answered；用 `watch` 做 heartbeat |
| 观测 | 按段记模型时间、工具时间、等人时间、verifier 次数与耗时、首次 harness 与首次 story 登记结果、返工时长 |

### 判据

K 类核结构，J 类核内容与效率；设计者独立读成品与 runlog 判，不以门禁或 verifier 的 PASS 代替。

| # | 判据 | 看什么 |
|---|---|---|
| K1 | spec 扩展章结构 | 「9. 宿主扩展治理项」下 9.1–9.3，附录最后 |
| K2 | story 投影与上线后观察 | 指标标题与 spec 一致；上线后观察按指标写 |
| K3 | plan 结构 | 「9. 宿主扩展」下 9.1 知识决策三节、9.2 埋点 |
| J1 | 人签全部来自人 | 契约每笔 `by: human` 有 `ask_id` 与人的原话；无代签、无编造、无手改契约 |
| J2 | 未决不写成已定 | 会议暂缓、材料冲突、评审未表态的事项，产物都写「待定：谁定、等什么」 |
| J3 | 依据变化由 update 承接 | 交付门不开修订轮；auto 第二段取回评审回稿与改版稿；car 第二段识别 review.md 表态，冲突探针登记并问人 |
| J4 | 必须设计项有值 | plan 9.2 每个统计点每种结果有事件 ID、内码、结果分类的具体候选值；外码写来源或「无」 |
| J5 | 审查判据全量有结论 | spec 与 plan 报告里 overlay 每条判据都有结论；阻断类缺陷被拦在本阶段 |
| J6 | 效率门槛 | 每阶段 verifier 派审一次（材料真变除外，交回写原因）；流程卡死与手改契约 0 次（U20） |
| 观测 | 首次门禁、时长、返工 | 按 [02](02-效率与一次成文质量.md) §5 记录并与 1.9.6 收口实跑对比，写进发布说明；不作通过条件 |

### 判定

- K 与 J 全部成立：
  - 实施者升 manifest version 到 1.9.7；
  - 写 `test/story/release/1.9.7.md`，分开列机制、知识、离线、实跑结果、内网待验证与用户成品评价；
  - 预算台账按实测重签；
  - 同步使用指南与内网指南；
  - 提交带版本号。
- 任一不成立：停在评审，诊断写进本目录 `评审意见/`，按「送达、知识、模型应用、审查、测试资产」五问归因。指向机制或知识的，回到对应分册修改后再谈下一次实跑；只剩模型因素的，如实写入发布说明的未达成项，由用户决定。
