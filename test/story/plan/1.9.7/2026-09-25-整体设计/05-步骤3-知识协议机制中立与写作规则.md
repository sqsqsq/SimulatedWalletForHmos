# 05 步骤 3：知识协议、机制中立与写作规则

覆盖 01 的 E、D 域与 G07、G08；承接原 1.9.7「知识的分类与表达形态」需求 §3–§5（决定 D1–D12 见 [00](00-总览.md) §4）。

## 1. 目标结果

1. 知识增删改只改知识文件与 manifest 的激活清单，extension 的机制、模板、测试零改动。
2. 机制按知识声明的类型与形态消费：加载、登记、送达、门禁、审查只引用协议规定并经加载器校验过的结构名，不点任何知识的名字，不写题材词，不引用未校验的节名。
3. 作者写作时，本阶段要用的知识正文就在任务包里；项目方法的必须设计项写在知识里，作者按它给出具体值。
4. 写作规则从通用原则推出，范例用与用例、金样都不同形的中性题材；规则写成审查能核的句子。
5. 目标仓的模型能按类型、形态与 Demo 示例写出自己的知识；升级时知道协议变了什么、自己的知识哪里不合。

## 2. 现状与证据

- **知识**：E01–E08（形态未声明、机制写死一份知识的结构、示例与金样同形、写作时知识不在眼前、必须设计项没写成列、测试锁 Demo 内容、adapt 缺逐格示例与写死源仓名、shell 写死）。
- **产物内容**：D01–D14（未决写成已定、模拟承载不说明、验收章结构、风险与回退、附录重抄、实现名与文档腔、自设数值、无依据说法、落点借挂、模式单元切分、契约不完整、接口漂移、埋点口径、错字乱码）。
- **过拟合**：G07、G08。

## 3. 正向设计

### 3.1 知识协议（kind × form）

三类知识（`kind`）与三种形态（`form`）构成四个合法组合，每份知识在 frontmatter 同时声明两者。形态指机器读的正文结构，不是读者，也不是题材。

| `kind` \ `form` | `facets`（分面） | `halves`（上下篇） | `entries`（条目表） |
|---|---|---|---|
| `facts` | 查找型：项目已有实现、封装、惯例；首装的部件画像也是它 | 方法型：要多步推导的项目方法 | — |
| `constraints` | — | — | 规约 |
| `patterns` | — | 设计模式 | — |

| | facts × facets | facts × halves | constraints × entries | patterns × halves |
|---|---|---|---|---|
| frontmatter | `name`、`kind: facts`、`form: facets`、`applies_when` | `name`、`kind: facts`、`form: halves`、`applies_when`；不写 roles | `name`、`kind: constraints`、`form: entries`、`applies_when`、可选 `domain`（等于条目前缀） | `name`（模式 id）、`kind: patterns`、`form: halves`、`applies_when`、`roles`（必填）、`optional_roles`、`coordinator_role`；`depends_on` 给模型读，机制不读 |
| 加载器校验的结构 | 至少一个二级标题；正文没有「# 上篇 ·」一级标题 | 两个一级标题「# 上篇 · …」「# 下篇 · …」，各篇至少一个二级标题；不核节名、序号、读者字样 | 表头含「编号」「约束」的表，列按名取（强制力、命中条件、处置、验证；探针列可省，有列时无探针写「无」）；编号「前缀-两位」，一文件一前缀；落法附注以 `**编号**` 起头 | 与 facts × halves 同一解析，另核 `roles` 非空、`coordinator_role` 在 roles 内 |
| 模型读的写法（protocol，不校验） | 一面一能力，每条写用哪个实现、在哪、怎么用 | 篇名后写读者阶段；上篇给设计侧，下篇给实现侧；节按项目方法写 | 一条一个可判定要求，写命中条件、边界、例外、验法 | 上篇适用与选型，下篇结构与落地 |
| knowledge-use 登记单元 | 面名 | 篇名（上篇 / 下篇） | 条目：applicable、requirement、contract 或 impact、waived | 单元、候选、信号 |
| 下游消费 | 任务包按用途与面名列出；作者登记用了哪一面；审查回查；不投影 | spec 登记上篇；plan 任务包附下篇全文（§3.3）；coding 读下篇；不投影 | spec 9.2 投影、验收 `knowledge_rule`、plan `must`、探针、审查并列 | spec 9.3 投影、plan `files[].pattern/role`、coding 读下篇 |
| Demo 示例 | `knowledge/facts/engineering-capabilities.md`、`component-profile.md` | `knowledge/facts/event-tracking.md` | 八份任一；`constraints/observability.md` 示范探针列 | `design-patterns/decision-tree.md`、`page-interaction.md` |

**写法要求**（写进 `reference/knowledge/protocol.md`）：
- **三类共同**：
  - `applies_when` 写清何时读、回答什么；开头一句说它帮读者做什么决定；
  - 正向陈述，只写确定的内容并给依据位置，同一事实只写一处；
  - 写到模型找得到为止：只写模型从代码里找不到或会找错的；
  - 示例只示范形状，一个就够，题材与测试用例、金样都不同形。
- **protocol 与代码一致**：
  - `domain` 写进条目表一节；
  - `depends_on` 标「模型读、机制不读」；
  - 探针列可省，有列而某条无探针写「无」；
  - 读者字样与节号连续是写法约定，机制不核。
- **Demo 知识**：全部显式写 `form`，每格至少一份达到示范质量；protocol 的四格写法各指向对应 Demo 文件。

### 3.2 机制中立

- **加载器**（`hooks/shared/knowledge.mjs`）：
  - `form` 必填、取值封闭，`kind × form` 只认四格；缺 `form`、值不在集合、组合不合法、声明与正文不符，都在同一次加载里按文件报出并给改法；
  - 不从正文推断形态；
  - 解析结果每个对象带 `form` 与登记单元，下游只看解析结果；
  - selfCheck 仍按 kind。
- **登记**（`knowledge-use`）：骨架与校验按登记单元——facets 列面名，halves 列「上篇 / 下篇」，错误信息用对应标签；YAML 键 `facet` 与 `schema: 1` 不变，投影不变。
- **产物出口与知识内容分开**。机制只保留产物出口：
  - spec 9.1.4：每个指标一个小节，小节下先有定义段，再有带「统计点」列的表；
  - plan 9.2：按统计点对齐的行，「责任方法」解析到契约的 `interfaces[].methods[]`；
  - spec 9.2、9.3 的生成区；plan 的 `must`、`files[].pattern/role`。
  
  定义段写什么、表里还有哪些列、共同约定写什么，都由读者含本阶段的那一篇知识定。模板只示出出口的键列，其余写「按知识要求的列」。
- **从机制里移出**：「衡量什么、怎么算、每次上报带什么、在哪打点」四项清单、「所在流程」列、「字段取值」列、`settle` 命名、「角色与登记位置」、「使用约定」「完成判断」「应用步骤」等节名、「以后台数据为分母」等埋点内容句。涉及：
  - `templates/spec-sections.md`、`templates/plan-sections.md`；
  - `hooks/spec/{author.mjs,post_check.mjs}`、`hooks/plan/{author.mjs,post_check.mjs}`；
  - `hooks/shared/{stat-points,pre_verifier}.mjs`；
  - `rules/spec-rules.overlay.yaml:13-17`。
- **任务包与审查的通用句**：
  - 按 `applies_when` 找回答本节问题的知识；
  - form 为 halves 的读读者含本阶段的那一篇；
  - 写完按那一篇自查，审查按那一篇核；
  - 项目规则算得出的字段写成具体值。
- **其他**：coding 作者页把模式写法指到 protocol 的 patterns 一节，写「form 为 halves 的下篇」。

### 3.3 送达（D12）

- plan 任务包读 `spec/knowledge-use.yaml > facts[].used`：凡登记了 `facet: 上篇` 的 halves 知识，把它的下篇全文附进任务包的「本阶段知识」一节（按加载器解析结果取正文，不按内容挑选）。
- 送什么由 spec 阶段的登记决定，机制不判断相关性；spec 没登记的不送，并在任务包里点名「spec 未登记使用的 halves 知识」供作者核对。
- spec 任务包对 halves 知识照旧提示读上篇并登记。

### 3.4 知识：必须设计项（`knowledge/facts/event-tracking.md`）

- **下篇写明**：成功率类运维上报中，事件 ID、内码、结果分类是必须设计项，每个统计点每种结果都给具体候选值并标「候选，待登记：<登记文件>」；外码按实际来源写来源或「无」；耗时只在时延类指标里带。
- **结构骨架拆具名列**：统计点、结果、责任方法、事件 ID、内码、结果分类、外码来源、去重与验证。完成判断同步为「每个统计点、每种结果一行，必须设计项都是具体值」。
- **示例换题材**：换成与测试用例、金样都不同形的中性业务，禁用题材从 `test/story/cases/*/`、`test/story/golden/` 的业务名派生。
- **上篇的衡量口径与业务目标**：
  - 材料里的业务目标翻成要算的率，并写出与指标的关系；
  - 以后台数据为分母的，写需要什么数据、由谁统计；
  - 终态分布不写成指标。

### 3.5 写作规则（`phases/story-write.md`、`hooks/{spec,plan}/author.md`、overlay）

**从原则推出、范例中性**：
- 决策类别表与「撞的方向」换成步骤 1 的通用维度；
- 会员开通、「重复扣款」范例，「本地模拟承载」原句，开关与存量考点，「截止时间」「半小时」例子，都换成与用例、金样不同形的中性范例；
- 图片分类清单只在 story-write 写一处。

**写成审查能核的规则**，overlay 的对应判据由步骤 2 定级：

| 规则 | 对应问题 |
|---|---|
| 待定的事写「待定：谁定、等什么」，不写任何一种实现，不写成本期不做 | D01 |
| 与工程现状矛盾的承诺、降级或模拟承载，正文照实写明，同时登记议题 | D02、B08 |
| 验收章按要验的事分组，每行有可观察的通过条件与主责，上游原始编号独立成行 | D03 |
| 业务方案章写风险与应对；交付章写回退与开关控制边界 | D04 |
| 附录机器区之外只写定位句，不重抄投影 | D05 |
| 正文用业务语言，不出现实现名、仓内路径，不写「本节」「下表」 | D06 |
| 数值有上游依据或登记为自设议题 | D07 |
| 材料里没有的说法不写 | D08 |
| 规约的 requirement 落在真正承担它的接口、存储键、字段或业务步骤上，一条要求覆盖几个实体就列几个落点 | D09 |
| 交互类模式一个页面一个单元，逐页判；结构类模式按流程段判 | D10 |
| 契约声明设计章用到的全部方法；use-cases 只引用契约里的方法；must 挂在真正做这件事的实体上；verify 按规约声明的执行体逐条定 | D11 |
| plan 的接口名与 spec 一致，改名先回 spec | D12 |
| 埋点口径与统计点一致；plan 改了口径先回 spec | D13 |
| 写完通读一遍，找错字与乱码 | D14 |

### 3.6 adapt

- **方法页**（`skills/story-adaptation/reference/knowledge-adaptation.md`）：按四格重排，每格写四要素——何时用这个形态、到哪取证、照哪份 Demo 示例、怎样走查；首装的部件画像是 facets 格的第一小节。只读检查的输出增加按 kind × form 的计数。
- **升级后确认**：不加独立命令字。流程为装机制 → `--check` → 落盘机制交回 → 算两件事 → 停一次问人。两件事是：
  1. 演进记录里晚于目标 `knowledge_adapted_for` 的条目；
  2. 只读检查按当前协议核目标每份知识的结果。
  
  任一非空就把内容摆出来问「现在做知识适配吗」，两者都空只报一句「知识与当前协议一致」；选稍后不写任何东西。
- **演进记录**：`skills/story-adaptation/reference/knowledge-changes.md` 按扩展版本分节，每节写知识协议变了什么、目标仓要做什么。目标 manifest 的 `knowledge_adapted_for` 由模型在知识适配交回时写。加载器只认当前协议，不写迁移脚本、不记进度。
- **内网指南**：新写 `test/story/release/内网适配指南-1.9.3升级1.9.7.md` 替代 1.9.3→1.9.6，写明：
  - 机制部分自动；
  - 知识部分：哪几份落在哪一格、按方法页哪一节写、补 `form`；
  - 取证附表按篇，不按节名。
- **对接层判断**：`adapt-scan.mjs` 由 manifest 的属性判断包里有没有对接层，替代写死的源仓名；检查组连续编号。
- **shell 取自环境**：drafts 与任务包输出的命令围栏按实际 shell 标注，不写死 PowerShell。

## 6. 验收（离线）

| AC | 内容 |
|---|---|
| AC01 | Demo 知识全部加载通过，每个解析对象带 `form`；四格各至少一份 |
| AC02 | 缺 `form`、值不在集合、组合不合法、facets 正文有上篇、halves 缺篇或篇下无二级标题——同一次加载全部点名，含文件与改法 |
| AC03 | 登记单元按形态；校验用对应标签报错；投影两次渲染字节一致 |
| AC04 | hooks、skills、rules 不出现任何激活知识的 name、面名、节名、角色名（词表从知识动态派生） |
| AC05 | 在中性工作区新增一份 facets、一份 halves 事实，改一份 halves 的全部节名，删一份事实——`doc/extensions` 除 `knowledge/` 与 manifest 外零 diff，任务包、骨架、门禁、审查照常 |
| AC06 | protocol 列的 frontmatter 字段集合等于加载器读取集合；方法页四格各含四要素；coding 作者页指向正确；1.9.3→1.9.7 指南存在且只引用方法页 |
| AC07 | adapt 升级后确认：演进条目或检查结果非空时停下问人并列出内容，都空时一句说明不问；选稍后不落盘任何文件 |
| AC26 | spec 登记了 halves 知识的上篇时，plan 任务包含该知识下篇全文；未登记的不附，并在任务包点名 |
| AC27 | 模板与机制文字不含 §3.2 列出的知识结构与内容词；event-tracking 下篇骨架含必须设计项具名列，示例题材不与用例、金样同形 |
