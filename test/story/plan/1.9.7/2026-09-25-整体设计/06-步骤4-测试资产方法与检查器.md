# 06 步骤 4：测试资产、方法与检查器

覆盖 01 的 F 域。改测试域（`test/story/`）与产品代码里只为测试存在的入口；金样与夹具按步骤 1–3 的新载体与形状重做。

## 1. 目标结果

1. 用例的每一关立场只对应一个关卡、一个问题，不替模型说出本该观测的识别，不诱导宿主提前触发流程；声称覆盖的能力都走得到。
2. 上游资料的冲突与歧义要么是有意设置并在 case.yaml 写明预期，要么消除。
3. 测试装置不吞模型的问题、不展示对不上的规划、不在检查点收回话；heartbeat 由驱动器提供；注入不改换行。
4. TEST.md 覆盖本轮出现的全部情形：规划外关卡、双检查点收工、续跑原话、投料规则、分段计时。
5. 金样与夹具与现行载体、合同一致，测试按结构核，不锁旧形态。
6. 检查器能发现本轮漏掉的过拟合、补丁、规则重复与环境写死；产品代码不含只为测试存在的入口。

## 3. 正向设计

### 3.1 用例

**car-key-sharing**（本地单，到 plan，第二段测评审回流）：
- 删 spec 阶段的 `review-comments`。交付门那一关的立场是「进入 plan。」（本 Case 终点是 plan）。
- 每条立场只答一件：交产品稿的立场去掉「按它来」；「材料就这些」「不拆单」拆成材料关卡与范围关卡各一条，顺序按实际停等。
- 24h / 48h 冲突按设计在 spec 登记为 D2 open 议题，不设 init 阶段定源这一关；case.yaml 的覆盖声明改为「材料冲突登记为议题，评审回流定源」。
- **第二段的评审输入**：
  - 写进 D2 与相关议题各自的人工区（三态 + 修改意见），不写进「其他意见」区；
  - 不引用不存在的前序口径；
  - 「正在收回」只在这里出现一次。
- **有意保留一处冲突作探针**：评审意见写「撤销后 36 小时内对方仍可开门」，与 SR、PRD「撤销起车辆侧即拒绝」冲突。
  - case.yaml 写明预期：模型登记冲突并停下问人。
  - 交互立场：「车辆侧撤销即拒绝不变，36 小时是对方设备上卡片收回的期限。」
  - 这一关直接验证 03 §3.4 的冲突规则。

**auto-topup**（AR 单，到 spec，第二段测 update 统一承接）：
- prompt 改为「从这张单开始做，做到规格定稿送审」，与终点一致。
- 交付门立场「归档送审。」：模型执行归档。
- 第二段开始前，装置在需求系统放入评审回稿（模拟评审人在系统上批注），同时投改版 PRD。update 要取上游取回评审回稿，与改版稿一并处理——一轮 update 同时覆盖材料更新与评审回流，并验证 AR 单取材。
- 会议裁决立场按话题拆成独立条目；补参会人角色确认的立场；答案卷修正「单日上限 300」限定第一段、改口描述改为「提议被否决」。

**两个 Case**：头注释、`test_multi_scenario_cases.py` 的能力登记只写走得到的能力（到 spec 或 plan，不写 coding 与真实改码）。

### 3.2 上游资料

- auto 的系统评审回稿不预置，由装置在第二段开始前放入；内容与会议结论、改版稿一致，不重复会上已定的事。
- 改版 PRD 只改单日上限一处，其余与会后结论一致；界面稿如有文字变化同步更新。
- 产品原稿与 RR 的关系在 case.yaml 写明：原稿是含图的草稿，业务以系统里归档的 RR 为准。
- 本地手跑直接读 `cases/*/system/`，删掉过期的 `test/story/requirement-system/` 副本（`bootstrap_local_story.py` 改读源目录）。

### 3.3 测试方法（驱动器与 TEST.md）

- **检查点保留待答问题**（`run_case.py`）：目标闭环时模型最后一句是提问，第一检查点事件带 `pending_question`，poll 照常展示。续跑用 `resume-update --answer "<立场>" --step <id> --text "<业务话>"`：先按规划立场答这一问（记为 planned），再投业务请求。
- **规划条目按相符展示**（`run_multi_case.py`）：规划条目的阶段、关卡类型与当前提问相符时才展示为 planned；不相符时展示「规划里没有对应这一问」，宿主按 answered 只答所问。
- **检查点期间拒收回话**：reply 在检查点等待期间拒收并说明原因。
- **heartbeat 进驱动器**：`run_multi_case.py watch --suite-id <id>` 按间隔零等待 poll，遇到要回话、要收尾或命令连续失败就退出并写明原因，完整 poll 结果存到 `output/story/<suite>/host/last-poll.json`；它不回话。
- **注入保持原换行**：评审输入按目标文件的换行写入对应议题的人工区。
- **检索可靠性**：查明隔离工作区里内置检索工具返回无结果的原因（工作区构建带进了忽略规则等），在工作区构建处修正。
- **TEST.md 补齐**：
  - 规划外关卡：framework 的术语与视觉 provider 询问、模型自开 update 的材料关卡，按 answered 一句作答；
  - 双检查点的收工：第二检查点后评完必须 conclude，与 §3.5 互相引用；
  - 续跑原话：写进 case.yaml 的 `update_request`，按 planned 记账；
  - `update_inputs` 的三种 kind 与自动投放规则；`--deliver` 只收 supplements；
  - 分段计时：见 02 §5；
  - 修正过期的命令示例、字段名 `expected_phase` 与退场的裁决表说法；
  - 本地单的送审件就是工作区里的 review.md 与 story.md。

### 3.6 检查器与产品代码边界

- **`check_failure_modes.py`**：
  - 扫 `.py`；编号正则覆盖三位及以上数字与 `AC-<字母><数字>` 形态；
  - 业务短词与数值从 `cases/*/`、`golden/` 派生，扫 `knowledge/`；
  - 删 6 条失效豁免；历史叙述词表补全；「仲裁锚」等指代金样的词纳入；Python 的 `except` 静默返回纳入。
- **新增判项**：
  1. 同一规则多处定义：定义规则的文档用标题锚点声明，其他文档出现同一规则正文即报；
  2. 机制写死知识结构：词表从激活知识的节名、角色、列名派生；
  3. 环境与源仓写死：固定 shell 名、固定源仓名。
- **`--offline` 仲裁模式**：移到 `test/story/scripts/` 的测试装置里，经生产入口调用。
- **只为测试的导出**：只为测试导出的 8 个符号改为经生产入口（CLI 输出或门禁结果）测试，或并入被生产代码使用的模块导出。
