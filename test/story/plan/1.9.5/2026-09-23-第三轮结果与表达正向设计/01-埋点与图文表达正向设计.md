## 0. 目标与范围

三轮实跑证明的缺口：埋点设计停在事件大类，没有「指标 → 需要的结果 → 统计点」的推导；Plan 埋点只是 Spec 的复制；Story 附录被机制锁成 Spec 投影、渲不出金样形态；图前后说明薄；附录长格集中在规约判定；spec 交付门按审查建议修改后又重审。

本文交付六件事：Spec 9.4 以指标为设计单位；Plan 埋点成为逐统计点的工作单元并有确定性门禁；Story 附录改为登记处（投影表 + 作者说明）并统一为四节；正文图三件套；写作设计空壳与表达选择表重写；交付门分流。附带 Demo 知识与两份金样同步。

不做：不新增图语法；不给产物加自证字段；不建埋点专用检查器；不让作者手抄 Spec 表；不改 Framework；不把金样或测试 Case 的值写进机制；不自动开启第四轮。

## 1. 硬约束

**通用性与解耦**。机制层（模板、作者页、任务包、审查任务、投影、门禁）只认识自己的模板结构：Spec 9.4、Plan 埋点小节、附录 A 四小节、「统计点」这个概念。它不认识知识文件名、渠道名、结果枚举、编码段数、登记文件名、任何专名。凡涉及身份、编码、分类、渠道、自动采集的要求都以「项目知识若有」为前提：有就按它取值并核对，没有就只剩六件与知识无关的事——统计点、业务动作、实际结果、本端何时得知、责任方法、验证。有和没有不是两套分支，是同一条规则。判据：换一份没有上报知识的激活清单，三阶段任务包、模板、审查、投影、门禁照常；机制文本按 TEST §7.2–7.3 扫描零专名。本文样例里的 Demo 值只出现在维护文档与 Demo 知识里。

**正向实现**。同一职责只有一套实现；被替换的旧实现、旧句子、锁旧形态的测试随本需求一并退出（§3 清单）。不在旧实现旁边加分支或补丁。

**责任分工**。模型负责理解需求、选统计点、设计参数与说明；脚本负责送达、投影、对应关系与引用解析、结构核对；verifier 判语义。提示词不是执行保证，凡能用结构或引用核的都进脚本，凡是语义的都不进脚本。

同一流程的多个指标合成一个 H4，标题写全；只有采集目的没有指标名的写成可算的指标名（发起失败分类分布）；项目知识区分采集目的时按那份知识标目的并给依据，没有就不标。作者推导：认出指标 → 反推需要的结果 → 每个结果本端从哪得知（远端拿不到的写备注）→ 项目知识登记了已有采集能力的对照它，已覆盖的不新增 → 剩下的逐点写实际会发生的结果，没有取消能力的点不编取消。H4 不用「全流程（a/b/c/d）」、渠道名、「埋点」「事件」做标题；第一列是可被 §10 引用的统计点名。不涉及时一行「不涉及：<依据>」。

### 2.5 写作心智：向没参与的同事解释业务

这一节替换 story-write 里所有讲「文档怎么写」的形态句；它和下面的范例是作者动笔前读的第一段，也是审查从读者位置判的依据。

> 读这份文档的人是评审人——产品、开发负责人、测试，都没参与开发，手上只有这一份。他们读完要决定：这件事想清楚了没有，能不能开工，怎么验。像向一个没参与的同事解释这件业务那样写：每句的主语是用户、系统、对象、规则，不是文档本身；章不写开场白，第一句就是业务；图前把过程讲一遍，读者不看图也懂，图后讲每条分支里他要知道的条件、责任、后果；表前那一句说的是业务事实。附录是查阅区，节首允许一句定位；正文十章不写「本章 / 本节 / 这张图 / 下表 / 如下」。

中性范例（会员开通，与任何 Case 无关；展示一节的开头、图前后、表前一句、恢复短段）：

```markdown
### 开通流程

用户在会员页选套餐并确认后，先做资格校验，再拉起支付；支付通过才向服务端申请开通，服务端确认后
会员立即生效。资格不符、支付取消、开通失败各有去向，用户不会停在没有出路的页面。

（流程图）

- 资格不符：停在会员页并给出原因，不进入支付。
- 支付取消或失败：回到套餐页，已选套餐保留，可直接再试；不产生开通申请。
- 开通失败：支付已成功时先退款再提示，用户看到的是「已退款、可重试」，不是裸失败。

四类结果对用户的意义不同：

| 结果 | 用户看到什么 | 接下来能做什么 |
|---|---|---|
| 开通成功 | 会员标识与到期日 | 使用会员权益 |
| 资格不符 | 不符原因 | 换套餐或联系客服 |
| 支付取消 | 套餐页 | 直接再试 |
| 开通失败已退款 | 退款说明 | 稍后重试 |

**时机**：支付成功但开通请求超时。**方案**：不显示成功，先向服务端确认；确认已开通就展示，确认未开通则退款。
**走向**：用户在会员页看到最终结果，不需要再次支付。
```

不这样写：「本节介绍开通流程」「如下图所示」「下表列出四类结果」「这张图从用户选套餐开始」。

## 4. 效果怎么保证

前三轮的改动都是模板、提示与审查措辞，证明只靠「告诉它」不够。第三轮 Plan 埋点等于 Spec 的原因：知识没给分配规则，模型拿不到值；Plan 表没有一列是抄 Spec 填不上的；门禁不看埋点内容，审查材料没有逐点对照；埋点是 409 行里的 12 行、一次写完；Spec 只有四行大类。

能不靠模型保证的四层，每层有离线验法；模型是否真能产出金样效果，只能由 §5 第三步的单阶段定向实跑回答，本文不宣称。

| 层 | 要做到 | 不靠模型的验法 |
|---|---|---|
| 决策输入 | 项目知识给出分配规则与 Plan 深度示例；维护者拿着知识能手工推出每个统计点的值 | 按知识手工填一份中性 Plan 埋点表 |
| 工作单元 | 任务包把 9.4 的统计点逐条列给作者，固定几问跟在每条后面；Spec 侧以指标为 H4，每个 H4 至少一行 | 任务包输出里统计点与问题逐条对应 |
| 确定性门禁 | plan post_check 三项；spec post_check 的 H4 与行 | 正反例：复制 Spec 的 Plan FAIL，金样形状 PASS |
| 审查材料 | Spec 统计点、Plan 行、激活 facts 三者并列 | 任务输入里三者并列 |

「同上登记」「按知识首次登记」是语义判断，不进脚本。图前后说明也不设机器判据（会拦金样 AR90004 的旧形态），靠草稿脚手架与审查维度。
