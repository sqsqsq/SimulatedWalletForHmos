# 第二步实施计划：知识描述、作者输入与审查主干整体替换（2026-09-23）

依据：[整体重写方案](00-整体重写方案.md) §3、§5、§6 第二步，以及[步骤1收口评审](步骤1收口评审-2026-09-23.md)「下一步」。基线 `55cbd05f`，工作区干净。按 §5 末条，先列文件动作与替换关系，设计者核过责任再动手。**本文件不改产品。**

## 1. 从两轮复测看，现在的输入把模型引向了哪里

| 复测里的实际产物 | 模型在决定那一刻读到的输入 | 问题出在哪 |
|---|---|---|
| auto 与 car 的 §9.4 都是「事件大类 × 触发 × 归属 × 报表影响」一张表，没有流程、步骤或适用结果 | `spec-sections.md` 的 9.4 示例表，表头正是「事件 / 触发节点 / 归属 / 报表影响 / 代码现状」；注释要求按流程写，但模型照表头填 | 模板示例本身把答案形状定成了事件清单，注释里的要求压不过它 |
| Spec 先写 knowledge-use 的判断，§9.4 与它各写一套 | `hooks/spec/author.md` 的主体是「知识判断怎么填」，业务关系只有一段方法说明；任务包第 2 节也是知识判断 | 作者任务的重心是登记判断，没有要求先完成一份完整的专项设计 |
| car 的 Plan 埋点小节写「新增流程身份（登记 WalletHAEventID）」，must 全部挂在上报入口 | `hooks/plan/author.md` 有逐点位要求，但 `plan-sections.md` 的契约样例里没有「结果由谁决定、上报器只负责发送」的挂法 | 两处说法不一致，样例在后，模型照样例做 |
| verifier 对以上三处都判 PASS | `pre_verifier.mjs` 的知识段写「判的是判断本身」，要求核 requirement 是否落到具体名字；overlay 另写了逐点位的要求 | 两套任务各说各的，审查照注入的主干去做，没有走业务流程 |
| use-cases 引用了不存在的验收编号和方法，verifier 降为 WARN | plan overlay 没有要求核契约绑定 | 第一步已补上验收编号的机械检查；方法绑定的判断还在审查里空着 |

## 2. 文件动作（替换关系）

### 2.1 知识（`reporting.md`、`observability.md`）

两份现稿都是设计者 09-22 直接重写的。对照复测，只改能帮助形成完整设计的地方，不扩写，不加条目：

| 文件 | 改动 | 替换或退出什么 |
|---|---|---|
| `facts/reporting.md` §6 使用参考 | 示例从单个步骤扩成「指标 → 流程 → 步骤 / 子点 → 实际结果 → 本端从哪得知」的一张关系表：一个流程、两个步骤、其中一步有两个子点，每行写出结果从哪个回调或查询得到。仍是短信验证这类中性业务，不用银行卡或本仓 Case 的值 | 替换现有「只有一个步骤」的示例表及其后两段说明。现示例没有流程和指标这一层，与 C 里模型漏掉流程的失败形态对应 |
| `constraints/observability.md` 附注 3 | 「上报方案明确本端通过什么调用、消息或查询取得结果」这一条保留；并入「远端发生的事写本端在什么时机取得」 | 不新增条目；Plan 作者页里同义的那句随 §2.3 退出，这里是唯一来源 |

`reporting` 的渠道、身份映射、结果与字段、未确认字段、登记现状各面不动；OBS 五条基线不动。

### 2.2 Spec 的作者输入

| 文件 | 改动 | 替换或退出什么 |
|---|---|---|
| `templates/spec-sections.md` 9.4 | 示例改成按流程分组：`#### <流程>` 下写一句指标或采集目的及依据，再给一张「步骤 / 子点、业务动作、实际会发生的结果、触发、已有采集或新增、代码现状」的表；没有独立运营需求时写一句不新增 | 退出「事件 / 触发节点 / 归属 / 报表影响」这张事件大类示例表 |
| `hooks/spec/author.md`「写之前：把这次的关系想清楚」 | 改成本阶段的主任务：先沿材料里的业务流程逐段过一遍，把规约原文要求讲清的专项（例如埋点）在它的承载章里写成完整设计，再去填 knowledge-use；knowledge-use 只记本需求怎么适用、责任来源和落点，不另写一份设计 | 退出现在「知识判断怎么填」在前、业务设计在后的顺序；「原文要求讲清的专项方案写在承载它的那一章」那句并入主任务，不再单列 |
| `phases/spec.md` §三 9.4 例外句 | 只保留形式约束（H4、短段、表与列表，不放图）；内容要求指向模板注释一处 | 退出这里对内容的复述 |
| `hooks/spec/author.mjs` 任务包 | 第 2 节标题与导语从「本轮的知识判断」改成「知识原文与本轮判断」：先列原文位置，再说判断是设计之后的登记 | 不改数据与计算，只改导语文字 |

### 2.3 Plan 的作者输入

| 文件 | 改动 | 替换或退出什么 |
|---|---|---|
| `templates/plan-sections.md` 契约样例 | 加一组「结果由业务方法决定、上报器只发送」的挂法：`must` 挂在决定结果的方法上（例如提交方法挂「成功 / 失败 / 取消各报一次，带什么身份与结果」），上报器只挂序列化与发送；并写明 use-cases 的 `linked_acceptance` 取 acceptance 的实际 id，调用写契约里声明过的方法 | 退出样例里「义务挂在任意实体都算」的暗示 |
| `hooks/plan/author.md` 埋点那一条 | 留下逐点位要求，改为指向模板样例与知识附注，不再重复「远端写取得时机」等知识里已有的规则 | 退出与 observability 附注重复的句子 |

### 2.4 审查主干

| 文件 | 改动 | 替换或退出什么 |
|---|---|---|
| `hooks/shared/pre_verifier.mjs` 知识段 | 主干改为两个动作：① 按业务流程走通本阶段产物（spec 看承载章与 §9.4；plan 看设计章、contracts、use-cases），含异常与未执行步骤；② 核本阶段交付够不够下游用（spec→plan 能据以设计；plan→coding 能据以实现：身份、结果、参数来源、调用时机、验证，未知的具体而真实）。原条目与判断并列的那张表保留，作为追溯入口 | 退出「判的是判断本身，不是它有没有被登记」这一主干，以及「要求是不是本需求自己的答案」一类只看措辞的问题清单 |
| `rules/spec-rules.overlay.yaml` `knowledge_spec_exit_substance` | 描述改成与主干一致：先走业务流程，再看判断是否与设计一致；§9.4 那段保留为这一判据的一个例子 | 退出与主干并行的另一套逐条判法 |
| `rules/plan-rules.overlay.yaml` `knowledge_obligation_substance` | 同上；另加一句：use-cases 引用的验收与方法要能在 acceptance、contracts 里找到对应，找不到按实现断链判，不降为措辞问题 | 退出「只核 must 的文字是否属于这条规约」为主的判法 |

## 3. 不做的事

- 不新增 schema、状态、Agent 层级或每条规则的自证字段。
- 不把 Case 或金样里的业务值（银行卡、自动充值、车钥匙）写进模板、作者页、审查主干或知识。
- 不为反例单独调用模型。
- 不启动第三轮真实复测。

## 4. 验证方式

- **机械**：现有 `test_author_task_package`、`test_verifier_report_protocol`、`test_knowledge_use`、`test_neutral_knowledge`、`test_writing_flow` 等照跑，失败模式检查器保持全绿；锁定旧措辞的断言随职责替换一起改。
- **桌面推演**：拿 C 复测的真实产物，按新的审查主干逐项写出审查应当指出的缺口：
  - auto 的 §9.4：没有流程和步骤，页面进入重复采集；
  - car 的 Plan 埋点小节：身份未落、远端事件无观察来源、must 挂在上报器；
  - car 的 use-cases：悬空的验收编号与方法。

  再拿一份按新模板写成的中性细粒度方案，确认它不被误拦。推演写进交回，不宣称模型已经能做到。

## 7. 按《步骤2实施计划评审》修正（2026-09-23）

| 评审项 | 修正后的做法 |
|---|---|
| 知识判断不能排在设计之后 | 作者主任务的顺序定为：取材料与知识 → 判断本需求适用哪些要求、有哪些已有能力、还有什么没定 → 按这些判断完成承载章的设计 → 把已作的决定与实际落点同步进 knowledge-use。设计中发现新事实，回头改原判断，不另起一套。任务包第 2 节不改成「设计之后的登记」 |
| 模板不固化项目策略 | 9.4 模板不写「没有运营需求就不新增」，改为写明采集依据、复用范围与本次动作，具体策略由激活的规约给出。Plan 样例写「所选统计点在各实际适用结果确定时按项目协议记录一次，同一点位同一尝试不重复」，并注明以命中这类义务为前提，不把每个提交方法都变成统计点 |
| 不丢既有审查责任 | 审查主干按「走业务 → 核阶段交接」组织，下面原有的检查都保留：不适用依据、基线豁免、借挂与夹带、项目事实复用、模式候选与角色投影。判断与落点登记仍作为索引，并核它们和设计是否一致 |
| 9.4 表列 | 用「统计点（步骤 / 子点）、业务动作、实际适用结果、触发、已有或新增、代码现状」作示例，可按信息合并调整，不要求每个业务动作都新增点位。目的与依据写在流程小节或点位里。第一列放可引用的统计点名：knowledge-use 的 `contract` 取技术契约章各表的第一列（`validation.mjs::contractNames`）；「代码现状」列名保留，附录投影按它去列 |
| reporting 关系示例 | 紧凑示例，只说明能力怎么用。回调、查询用示例角色写，不编造现成 API；不写成作业步骤，不写章节坐标或规约编号 |
| use-cases 绑定 | plan 审查核调用的接收者或协调者、方法、参数与返回、验收 id 的实际绑定；新增或授权的调用要能追到 contracts，已有外部能力要能追到已核的真实接口。找不到合法绑定按实现断链判。不做按字符串猜语义的检查器 |
| 根因分级 | §1 表里「模型照表头填」「照样例做」是解释性假设，没有决策过程的直接证据；旧 Plan 样例本身并没有「任意实体都算」的规定。加强样例是为了减少歧义 |
| 事实更正 | auto 按页面进入列点位，是**有重复采集风险的设计**，没有编码，所以不能说运行时已重复。car 的义务挂在转发方法 `KeySharingRepository.reportShareEvent` 上，不在 Reporter 类上 |
