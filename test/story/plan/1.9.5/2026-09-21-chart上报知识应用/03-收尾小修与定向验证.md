## 2. 收尾门禁的最小改法

责任位置为 test/story/scripts/run_case.py 的 _run_story_gates、run_gates、第二检查点前后与终态归类；TEST.md 更新其对应运行/证据段。现有调用退出后才统一检查，在进程启动资源失败时把环境问题混成内容失败。调整只针对现有 Story 只读检查，不把 Framework 阶段 harness 前移或多跑一次。

1. 在 update 产物稳定、进入第二检查点等待之前运行现有 Story 只读检查并保存结果/diagnostics。普通单终点在稳定收场时走相同函数。第一检查点的旧结果不能当更新后结果。
2. 复用既有摘要/文件枚举工具，记录这次检查实际读取的产物文件集合及内容摘要，连同 case/run、阶段范围和检查实现版本保存在已有 gate_diagnostics.json 内；不建跨 run 缓存或新状态库。输入集合包含实际读取的 framework.config.json、有效 gates 配置及检查入口，根目录按配置解析；以实际检查器依赖为准，包含其读取的正文、侧车、契约和引用资源；不能只哈希 story.md。
3. conclude 后重新核输入集合及摘要；只有本组门禁均取得有效结论且输入一致才复用本 run 的结果，不再启动同一检查进程。发生新增/删除/内容变化或依赖不全时重新检查，旧 PASS 不沿用。框架闭环读取仍走当前 run_gates 路径。
4. 进程未启动、明确的 OS 启动异常或无有效检查结果时，diagnostics 记录环境/执行失败、退出码和原始输出；总门禁不算通过，终态沿已有 harness_incomplete 表达检查未完成。用户确认 story-build 判据：退出 0 且有“通过”行才通过；退出 1 且有 `[story-build check]` 自身诊断归 gate_failed；其余归检查未完成。该识别仅用于 story-build，其他 gate 沿其真实输出协议。无法判断的非零退出按检查执行失败记录，不猜产品错或机器内存不足。
5. 有效内容 FAIL 仍保留并交宿主判断，检查失败不自动终止当前人工检查点、不自动回复或修改产物。缓存写入失败通过既有日志/事件暴露，未跑成的组在下一次正常调用重查，不能伪造已完成检查；现有 provider 失败跳过门禁的行为保持。

复用的是同一产物版本的确定性结果，不是让宿主替消费模型完成 Framework gate。实现前核现有 fingerprint 的范围：不匹配时只补本函数所需的最小枚举，不推广通用缓存框架。

直接消费者包括 expected_gate_names、build_phase_results、terminal_status_for 及 suite 汇总/回流读取者。实现者沿调用核对：environment/incomplete 能被保留，不被下游重标为内容失败；沿既有终态，不新增需全链兼容的状态字符串。

## 3. 离线用例

在 test_gate_groups、test_update_checkpoints、test_harness 既有测试补：同版本检查只执行一次；等待期改正文/侧车/引用资源使结果失效；第一段结果不用于第二段；有效内容 FAIL；进程启动异常/无结果；conclude 提前到达未有缓存；诊断写入失败；普通单终点与 provider 跳过保持。断言实际调用次数、绑定对象和终态，不能只查新字段存在。

原始 0xC0000142 只作为已观察失败样本，不成为唯一硬编码识别条件。有限资源现场无法稳定重现时，离线注入启动异常验证归类，真实环境效果保留观察；不得标已根治机器资源问题。
