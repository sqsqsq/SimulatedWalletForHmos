## 2. 规约的具体调整

| 条目 | 现行要求 | 验法 |
|---|---|---|
| OBS-01 | 新增/改动日志时，用统一封装保留必要定位上下文，避免组合门面重复记录；不强制每步/分支打日志 | 基线，模型审查；删除 Logger 探针。安全仍归 SEC-01 |
| OBS-02 | 过程关键点 VOC；选定统计节点的终态只 Chart | 保留红线及既有弱探针；探针仅证明调用形态，双报与覆盖由代码审查/事件验证判断 |
| OBS-03 | 涉及指标或影响已有上报时，选择有依据的业务节点，覆盖其全部适用结果；同节点同执行的终态互斥 | 模型设计与实际事件；chartBuilder 探针不是完整性证明 |
| OBS-04 | 内码五段和统计分类准确，主动取消与普通失败区分 | 模型＋实际事件 |
| OBS-05 | 外码、身份/描述、必要维度与计时均有正确语义、来源和单位 | 模型＋运行。标准字段经专用 setter；通用 setter 不拦覆盖，须审查实际调用并核事件 |
| OBS-06 | 查既有定义后决定复用/扩展；相同节点与具体结果可复用，新含义有唯一登记且不冲突 | 旧新定义对照、引用检查和实际旧路径回归 |

模型判断必要节点，不能按函数数量铺点，也不能少选必要节点以回避覆盖。重试、取消后回调、重复通知等只在业务适用时设计；不要求所有需求具备这些分支。

Demo 内码为十位数字字符串，五段各两位，依次是模块、流程、节点/事件、子节点/子事件、具体结果。保持前导零。实际业务采用源码中单一登记位置，注释说明语义；先查分配，再在对应父级选择未占用值，评审核重复及旧含义保持。无定义不得猜已有值，空间不足或语义冲突回知识所有者。知识不预分配一张假业务码表。

内码末段与统计分类独立。中间成功/全程成功/普通失败/主动取消四类中，拒绝授权归普通失败。外码取实际外部返回，无码省略，不伪造零。字段按业务选择，说明类型、单位、来源和隐私；成功率公式归数据使用层。

VOC 定位、Chart 运维统计、BI 运营，二选一只约束 VOC/Chart，不扩成三选一。本地日志仍可按需存在。用户所述真实仓三个 Builder 名称不是 Demo 已实现全部能力的证明。

## 3. facts 写到什么程度

用户确定上报知识按能力域组织，统一文件 reporting.md，标题“上报”，name 为 reporting；applies_when 覆盖新增/修改问题定位上报、运维统计、运营上报及其既有行为。后续 VOC/BI 诉求在本文件各自小节扩展，不因每种渠道另建一份事实文件。

按“渠道与现状→真实入口→渠道特有语义→必要参考骨架”组织。VOC 小节承接 codebase-facts 的 vocBuilder 与组合日志门面，明确一调同时记本地日志并发 VOC。Chart 小节承接当前编码、分类、字段、派生标识与节点结果边界；这些规则不扩大到 VOC/BI。共享发送行为仅在源码确实一致时合并。

BI 小节记录用途及能力边界：真实仓 BIBuilder 名称由用户提供，Demo 尚无已核实现，不给不存在的 API 或假定与 Chart 字段一致；本次不新增 BI 功能。文件扩展职责不增加代码展开程度，各渠道只留实际所需差异。

codebase-facts 仍是其他工程事实的入口，删除其中全部上报内容；本地日志不等同于上报，Logger 与脱敏入口继续保留。上报事实由独立激活的 reporting.md 唯一承载，规约义务继续在 constraints，不将事实与规则合成一份。


API 入口定位到 WalletHAManager.ets、WalletHAReportBaseCBuilder.ets、WalletHAReportForChartCBuilder.ets、WalletFuncResult.ets 及公共 index.ets。只解释容易错用的差异：

- 平台 WalletHA/Wallet_COMMON/STATISTIC 与业务内码不同；VOC 是 BEHAVIOR。
- WalletEventID 由 FuncID_SubFuncID 合成，不是一次执行的唯一标识；专用 setter 保持内部联动。
- SUCCESS、STEP_SUCCESS、STEP_ERROR_BY_ERROR、STEP_ERROR_BY_USER 的实际语义分别对应前述四类。
- 内/外码、描述、渠道、来源、订单等已有 setter，具体签名按源码查；耗时在 Demo 约定毫秒，业务定义起止。
- 新维度复用公开后的 setReportParam，类型沿现有 string/number/boolean；标准字段仍走专用入口。
- report 非阻塞且隔离发送错误，不负责业务去重，也不自动补齐缺失参数。

必要时保留一个短调用片段，仅示意“取得 Builder→设置适用参数→report”，变量来自调用者，不给完整包装函数、类、枚举或异常分支全集。不承诺该示意可独立编译；完整类型签名指向源码。不新增只为承载示例的代码文件。

## 4. 简明参考骨架

新 facts 用一段步骤或一张小表说明：从业务目标选节点→推演适用结果→查已有编码/字段→明确结果决定者与调用位置→确定事件验证。无需强制表头、产物模板或新设计模式登记。

| 需要思考的关系 | 骨架提示 |
|---|---|
| 节点与目的 | 哪个业务结果需要统计；未执行的节点不虚构事件 |
| 结果与数据 | 具体结果、统计分类、外码来源和必要维度分别确定 |
| 业务与 SDK | 业务收敛本次结果，SDK 包装发送；回调/并发去重归真实业务所有者 |
| 设计与验证 | 以场景刺激对应原始事件的时机、参数、次数 |

可用一组中性业务情境解释取消与拒绝的差异，不展开完整业务流程。项目规则、源码事实与示例选择明确区分。样例的节点数量、类名、流程顺序和数据字段不变成通用义务。

目标仓参照该组织方式，查自身 API/编码/结果/参数规则再适配；沿用组织方法，重核具体内容。知识在激活后才进入消费路径；升级保护目标已有知识，不复制 Demo 文件覆盖它。

## 5. 实施与验收

先核 SDK 的唯一可见性改动，再登记未来能力为已有事实。按 .ets 宿主约定读取 pitfalls 并做可用的逐文件 lint；缺原生能力时记录未验证，不为本版启动 Demo 编码/设备真实测试。接口改动的原生编译与执行交内网，不用静态审查冒充通过。

用已有 knowledge selfCheck 及知识协议用例核激活、解析、旧 Logger 探针退出和其他有效探针保留。设计者核知识无完整业务实现、无重复 API 清单、骨架能支持不同合法业务；既不能靠字数证明简洁，也不能为短而删已确认语义。

交回知识 diff、API 改动、定位链接、检查证据及预算；运行正确性按 S4 单列内网待验。

## 6. 在途更名与验收

实施者在当前步骤收口前完成此次局部整理，不重做已完成阶段。替换 manifest 路径和 name 后，核活跃测试夹具 facts 标识、facet 引用及派生预期；分面重组时同步这些直接消费者，不只改文件名。知识加载应仅出现 reporting，一般工程 facts 不再重复上报内容。新事实的选择条件须能覆盖只涉及 VOC 或 BI 的合法需求，不以 Chart 命中作为读取前提。

历史交回、评审与真实运行原件保留当时名称；仅当前设计、现行产品及活跃夹具迁移，不创建旧名兼容文件或别名。沿现有知识协议与相关投影测试验证，不新增固定渠道路由脚本。通用机制仅消费激活清单，不能新增 reporting 文件名/渠道名称特判。迁移与删除单列实账，知识预算不因改名自动增加。
