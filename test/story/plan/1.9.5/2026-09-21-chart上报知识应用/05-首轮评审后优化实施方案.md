# 首轮评审后优化：从业务指标到上报实现

2026-09-22，维护设计者。依据用户本轮明确要求制定，作为当前 1.9.5 的后续优化方案。顺序固定：当前首轮结束并审查→实施本方案及审查发现的必要修正→同组复测。不能在首轮在跑期间改隔离工作区、产物或给模型补本方案答案。

适用前稿的修正点：目标知识不仅描述已有封装，也要给出建设目标工程所需的规则；Spec/Story 先讲业务指标与完整流程覆盖，Plan 再落实技术身份、结果和调用。其他范围保持：统一 reporting、通用机制与 Demo 解耦、知识精简、两个原 Case、Demo 不跑 Coding 及后续真实测试。

## 1. 要达到的效果

读 Spec/Story 能回答：关注哪个业务指标，指标对应哪条完整流程，流程有哪些步骤和需要区分的子步骤，每处适用的成功/失败/取消等结果怎样留下统计记录。不能只给总成功/总失败，也不能只有一张事件名和代码取值表。

读 Plan 能据此实现：每个业务统计点如何映射工程事件身份、内码/外码/结果分类与参数，在真实逻辑的何处取得数据和报告，未发生步骤、重试、重复回调等怎样处理。知识给规则与骨架，当前缺少的实现由本需求的设计/实现阶段建设，不能把“Demo 没有”当作无需设计的理由。

## 2. 第一步：等首轮结束，先审查事实

当前首轮为 output/story/story-suite-20260922-1116，最终以装置实际 run 标识和固定 artifact 为准。执行者完成两个 Case 的既定终点与 finalize，保留实际运行所用的知识/机制版本、输入、交互、产物、轨迹和检查结果。本方案不向本轮模型投放。

设计者审原始 Spec/Story/Review，car 另审 Plan/contracts；核知识是否在决定前取得。逐条区分：已有要求执行失败、原设计未讲清、用户本次新明确的目标、当前材料确有未决。新目标不能倒写成模型当时已知，也不能回改原产物后再评价第一轮。

| 审查问题 | 要取的证据 | 处置位置 |
|---|---|---|
| 只有零散终态，没有指标和全流程关系 | 原需求统计诉求、Spec/Story、点位选择依据 | 知识骨架与 Spec/Story 作者责任 |
| 必要步骤/子步骤遗漏 | 需求流程中的正常、失败、取消、提前退出与协作边界 | 业务覆盖设计，不能只补关键词 |
| 事件身份按结果拆散，或结果只写在事件名里 | 当前事件定义、原始知识、技术设计 | 知识概念及 Plan 映射 |
| Spec 分配代码，Plan 没有落实 | Spec 技术表、Plan 实体义务和实际 API 取证 | 阶段承接/契约，不加新表 schema |
| “暂无接口/码表”被当成不做上报 | facts 当前能力声明、作者理由、需求目标 | 当前事实与目标规范的分工 |
| 其他能力退化或低效返修 | 全部成品与真实轨迹 | 对应原责任位置，不能都归上报 |

完成条件：在本目录形成首轮结果评审，列具体产物位置、根因、已定修正和未决；按 TEST 给三轴建议分并保留用户确认状态。设计者完成该评审后实施者才开始第二步。首轮未结束前允许只读收集与准备，不修改产品/Case。

## 3. 第二步：同时优化目标知识和阶段承接

### 3.1 Demo 知识按目标工程组织

保持两类责任，避免把未来能力伪装成已实现事实：

- reporting.md：现有接口的真实位置与限制；事件身份/结果字段的关系参考；已有实现与待建设能力明确区分。confirmed 只标代码取证，不替目标规则背书。
- observability.md：目标工程的上报协议与完成要求，包括事件结构、流程覆盖、结果语义、编码分配/复用规则。目标规则可以先于代码成立，模型按需求据此设计建设。

用户给出的目标结构在 Demo 知识中作为本项目规范表达：完整业务事件由工程模板 eventID、业务流程 funcID、具体步骤 subFuncID 组成；例如 BankCard_001_002 表示该模板下开卡流程的某个步骤。身份不随成功/失败/取消变化，结果另由内码、外码、结果分类等字段表示。模板与流程/步骤编号按工程登记分配，不把示例值当自动分配结果，不把该结构写到 Extension 通用代码。

十位内码继续五段：业务模块、流程、节点/事件、子节点/子事件、具体结果。内码可表达比事件更细的子步骤与结果；不能把内码结果段混成事件步骤段。事件分段与内码分段不要求逐字符相同，Plan 明确本次映射并查已有定义。样例 1001010101 仅解释结构，不预登记银行卡业务。

当前 Demo 事实仍保留：chartBuilder 接收 WalletHAEventID，现仅 Wallet_COMMON，report 派生 WalletEventID=FuncID_SubFuncID。它尚不能直接证明目标三段完整身份已实现。reporting 用一个简短“目标语义/当前实现/建设差距”表表达这点；不得写目标三段结构已经存在，也不得因当前两段而将目标缩成两段。

当前需求需要该能力时，Plan 明确要新增/调整的模板枚举、完整事件身份映射与业务编码登记位置，区分平台事件 name 与业务标识。已有事件的含义保持或说明迁移影响，不能静默改旧数据。由正常 Coding 在内网落实；本轮维护者不预建银行卡服务、不为制造事实新增演示码表，也不启动 Demo 代码验证链。

缺的是实现时由模型提出具体建设项；缺的是业务语义、工程分配权限或外部协议时提出具体问题，不能任意捏造已分配编号。无现有码表时允许 Plan 依据已定规则提出本需求新登记及唯一源码位置，而非永远写“待定义”。

### 3.2 Spec/Story：先完成业务覆盖

业务方案至少讲清以下关系，表现为简明表格或图文，不强制固定表头/行数：指标及用途→所属完整业务流程→步骤/必要子步骤→各点位适用结果→业务触发条件。

逐流程沿正常路径与异常/取消路径核覆盖。界面可帮助识别步骤，但步骤不等于页面，子步骤不等于所有内部函数。已有业务材料明确的校验、短信、人脸、写入等具体动作不能被“开卡处理”总节点吞掉；纯展示结果页是否产生新统计事件按是否有独立观测意义判断，避免重复报告已完成结果。

Spec 形成业务层统计设计和可观察验收，Story 用读者能理解的语言呈现同一覆盖关系。Spec §9.4 保留既有五列表形，事件列可使用业务点位名；确有已知稳定 ID 可引用，但不得要求作者为了填表提前分配精确编码。需求资料没有编码时如实指出技术映射由 Plan 依据项目规范落实，不能把“Plan 要做”用作省略本阶段业务覆盖的借口。

统计指标名称及用途需要写出；成功率分子/分母等后台公式仍不在客户端实现范围内。VOC 过程定位、Chart 统计节点结果的边界保持，不能为所有过程动作机械双报。

### 3.3 Plan：将覆盖关系映射成可实施方案

Plan 承接每个已定业务点位，并结合真实流程内部逻辑细化必要子步骤。独立上报小节给出事件身份与结果字段的定义来源、已有值复用/新增、参数来源、实际调用位置/时机与异常边界。

按目标知识为本需求确定 eventID/funcID/subFuncID、内码、外码来源和结果分类；区分平台名称、业务事件和一次执行标识。事件身份回答“哪个步骤”，结果字段回答“发生什么”，执行标识回答“哪一次”，三者不能互相代替。同一步骤不同结果通常共享步骤身份；需要区分的子步骤是否独立事件按项目规则与统计用途决定，不把示例节点数变成模板。

必要的基础能力缺口进入真实实体和文件设计，must/description 承接业务责任与字段映射，不全挂公共 Builder；验证能追到每个点位的成功/失败/取消等适用结果及不重复。具体实现边界引出新的业务覆盖变化时同步 Spec/Story，不在 Plan 暗改范围。全部使用既有 contracts/use-cases，禁止新增 reporting 顶层 schema 或固定渠道字段门禁。

生产机制文案使用“专项业务关系/覆盖、项目标识与参数规则、实际能力缺口与建设项”等通用概念；指标、点位、三段编码与四类结果由激活知识提供。换成不同领域/事件协议，通用机制不改。

实施顺序：先修知识责任真源→更新阶段指引和对应审查→迁移必要离线测试。交回时按一次合法新业务推演 Spec/Story→Plan：业务覆盖是否完整、缺失能力是否进入建设方案、已存在能力是否正常复用。无需为此调用额外真实模型。设计者审实际 diff 与证据通过后进入第三步。

## 4. 第三步：同组复测并比较

用户已授权本优化实施且评审通过后复测；沿 TEST 起跑流程核对实际配置，不把授权扩到其他 Case/阶段。两个既有 Case 原材料不变，auto-topup 到 Spec、car-key-sharing 到 Plan，不开 update 第二段，不进 Coding。使用新 suite 和干净隔离工作区，不在首轮会话中喂答案返修。

复测前在已有记录写明：两次的产品/知识版本、Case 输入、模型配置、阶段终点与人工立场。优先保持模型配置一致；不同则披露不可直接归因，不能把所有变化归功于优化。

首轮证据先按现有归档方式留存，确保新 suite 清理不删掉唯一比较原件。第二轮只提供正常业务输入、目标工程知识和正常入口，不把本方案、首轮缺陷清单或正确产物塞给消费模型。

复测评价：指标与流程能对应、必要步骤/子步骤不漏、结果不混入步骤身份；Spec/Story 可读，Plan 可实施；缺失能力进入有依据的建设项；知识与机制解耦；原需求边界/人工结论/图文与性能不退化。两轮各自三轴建议分、扣分证据与用户确认状态保留，不修改首轮评分为新结果。

本轮 auto 无 Plan，不能声称它已验证技术映射；car 的 Plan 可以核设计映射，但代码/真实事件正确性仍交内网。两轮不足以证明广泛稳定性，不为追高分自动增加第三轮；若失败再给具体根因与必要下一步。

## 7. 多流程、多指标及章法要求（用户补充）

Spec/Story/Plan 单处承载的位置与当前规则以[06 裁定](06-埋点单处承载裁定.md)为准：Spec §9.4、Story 附录 B 事件部分、Plan 服务层接口定义下上报小节；不在其他章节重复完整设计。

先列流程与指标对应，再按流程展开步骤/子步骤及运营、运维需求。一个流程可支持多个指标，一个指标可关联多个流程；共享原始事实不按指标数量重复上报，共享组件不丢所属流程。跨流程要说明关联身份、各自成功定义和最终结果唯一责任，不能混淆查询成功与业务办理成功。

金样候选以开卡办理和结果查询说明这些关系，仅供维护者效果审视，不投入当前 Case 或强制其他业务同样拆分。消费机制保持通用，具体上报概念及协议由项目知识承载。

目标项目的运营需求来源、自动运维上报复用、运营/运维共用身份与参数语义、STEP_SUCCESS 覆盖，按[06 的目标项目上报约束](06-埋点单处承载裁定.md)执行。它们属于项目知识，不固化进通用机制；具体文件动作和验收也在该处维护。
