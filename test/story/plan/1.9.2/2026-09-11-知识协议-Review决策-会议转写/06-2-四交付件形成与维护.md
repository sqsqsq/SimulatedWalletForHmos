# 步骤6 · 工作包2：形成并维护四份交付件

状态：随[步骤6总览](06-步骤6-有效结果保真与模型协作收敛.md)定案，待实施。会议输入采用工作包1合同；普通材料走现有流程。本包不新增事实台账、文档生成器、Agent或审查轮次。

## 1. 交付结果与权威来源

四份文件分工协作，既不各抄一遍全部材料，也不靠上下文记忆承接决定。

| 文件 | 读者必须得到什么 | 本阶段依据与现有承载者 |
|---|---|---|
| Spec | 范围、行为条件、例外、验收和未决边界 | 原始材料、实际人工决定、有效会议结果、目标仓事实；knowledge-use记录知识判断，acceptance承载验收 |
| Story | 看懂需求、方案、关键关系、失败恢复及交付 | 当前送审版本Spec与decisions、必要原始依据；story-template只管组织，章节草稿供成文，附录由真源投影 |
| Review | 知道哪些判断需选/确认，依据、推荐与后果 | decisions保留判断与成立状态，Review渲染填写位；人工反馈与review-disposition承接后续处理 |
| Plan | 能实现的输入、数据、调用、状态、恢复与验证设计 | 当前有效Spec与人工处置；plan.md解释设计，contracts.yaml维护实体契约，不各自发明不同接口 |

事实真伪、知识适用性、材料冲突和组织方式由模型判断。脚本保持既有结构、引用、渲染、冻结与阶段状态职责，不判断自然语言是否完整准确。

## 2. 一条关系怎样形成四份正确表达

### 2.1 Spec：先使需求与约束共同成立

作者在设计之前取得原材料及当前决定，对本需求实际涉及的关系逐一想清：谁在什么条件下，用什么输入做什么，结果由谁消费，哪些异常/例外改变去向，哪些尚未决定。它是思考方法，不是每节必填表，不要求另写推演日志。

知识参与这项判断：原条目要求什么，命中哪种实际行为，是否与业务目标冲突；项目事实“没有现成实现”只说明复用结果，不证明不需要该能力。冲突回知识/需求责任方，不能擅自豁免红线、删除功能或用模拟替代真实承诺。明确指标的来源、条件与测量对象；材料没给的数值不能冠以平台/项目基线。

普通业务规则保留在Spec相应行为与验收处；知识判断只保存本需求如何适用，不用编号挂载无关规则。模式允许零命中，事实与规则不强行改成选型。

### 2.2 Story：先设计表达，再完成表达

这是同一流程中的两种工作状态，不新增Agent。`story-write.md`第二节交付“设计表达”的任务，第三节及草稿起头交付“完成表达”的任务；skeleton完成设计读取后指向写章，十章齐后仍进入原整稿回看。不用两段同义提醒假装完成职责分离。

| | 设计表达：产出story-template.md | 完成表达：产出章节草稿与Story |
|---|---|---|
| 输入 | 原材料/初筛、当前Spec与decisions、有效会议结果、章节合同 | 本章模板生成的草稿、对应原文、当前决定、已有正文 |
| 当前要决定 | 章节怎样组织，每处讲什么、用什么形式、解释什么关系及依据在哪里 | 图中具体角色/边/分支，表格列与行，列表项目和叙述内容；使业务条件实际讲成立 |
| 不提前决定 | 正文答案、图节点全集、表格所有列、未确认业务结论 | 不把模板描述复制成正文，不丢模板要解释的关系，也不盲从错误模板 |
| 完成条件 | 作者能从骨架直接着手写该节，必要小节已命名、表达意图明确 | 各节内容真实完整、形式承载了意图；有依据的调整已说明，主体文稿可供人理解和决策 |

**骨架与草稿的边界。** template的阅读主线短写本需求的理解难点及先后，不逐章重复目录。现有章ID继续定位固定章，一级标题和十个二级章节名称仍由章节合同给出，skeleton显示其实际正文标题；模型判定需拆的子章节直接在template写好名称，沿现有####/#####映射到正文H3/H4。各节说明要描述什么、依据及必要条件、关系、未决，不预写完整业务答案。简单内容短写，不强制每节一样深。

**形式协议在原解析器内替换。** 保留阅读主线、骨架、标题、说明行、`- 待核：`与不涉及的结构。将template中的`表头：列…`、`图：类型`统一替换为`形式：<类型>`；类型为`表格`、`有序列表`、`无序列表`、`叙述`或现有DIAGRAM_SYNTAXES的具名图种/通用`图`。一节可声明多种形式，每种一行，重复合并。随后用现有`- 描述：…`说明该形式表达的对象、关系和边界；这是说明行，不新增内容字段或字数检查。例如“此处用时序图解释各方请求、返回与失败责任”，不是预画全部消息。

脚本只认形式与位置，不判说明是否讲得好；未知形式报到该节。旧`表头：`/`图：`声明给当前写法和修正出口，不双读；旧测试随本包迁到新合同。普通说明行仍是自由说明，不从其中猜形式。表格的列在成文时由模型决定，不能把表头决定转移到另一份设计文件。

**复用现有结构能力。** writing-plan派生形式要求供selectedStructure/chapter-contract使用。模板选表格只要求本节有真实表格，不限定列名；图种仍按既有类型核；有序/无序列表仅核对应区域围栏外存在真实列表项，不设条目数；叙述不加字数门。项目原章节合同的必要锚列/附录结构仍保留：那是既有交付合同，不是模板作者提前定列。重合的同一结构只打底/报错一次。任意多个“表格”不表示要求几张表，具体分几张由成文模型决定。

草稿按骨架铺标题及解释任务，以现有可剥除指引给“当前在完成表达”的动作：先读该节依据，再选具体列/节点/项目并写内容。模板所选表格不生成预定表头；固定合同本来要求的表仍按合同生成。已写草稿不覆盖，缺失起点仍由原机制提供。具体类型存在不证明内容成立，最终语义审查核表达意图与原材料。

**成文允许有依据地质疑设计。** 正常填列、画节点、补解释不是偏离，不写记录。改变计划中的分节、形式、内容安排或放弃某项解释时，模型在`AR/story-src/template-adjustments.md`记录该节的原安排、实际调整、原因和可定位依据，再同步本轮template与草稿。一个实质调整一条，返修同一调整更新该条；无调整不建文件，不给每节填“遵循”。未列到但有依据的普通深化仍可直接写，不强迫先修改模板。

该文件是用户要求的过程观测数据，不是业务真源、审批记录或新的状态门；不新增结构schema、签名、冻结协议或强制自证关卡。沿现有story-src保留路径；原始测试记录负责保留形成过程，不能用该文件的作者自述代替实际diff。遇业务结论变化仍回Spec/decisions及既有审批/修正路径，不能用模板调整记录获得改需求权限。已送审快照按§3保持，重新成文时只改当前工作版本。

**整稿仍审实际成品。** 模板中的已知条件也可能错，原材料与有效决定始终优先。沿原回看核关键关系、条件/例外、图文、正文和投影区，再用五类清单定位疑点；有调整文件时把路径交原verifier按需复核原因与实际影响，不新增模板审查轮。正文符合模板并不证明业务正确，偏离合理模板也不能只因给了理由就自动接受。

### 2.3 Review：以需要表态的判断为单位

保留原准入规则和choice/confirm填写位。先确定人表态会改变什么，再写来源中的主张与冲突/缺口、可选做法及后果、推荐与理由。标签、分类和D编号只是组织方式，不能决定议题有没有价值。

open登记在decisions，正文在受影响处写未决边界，不提前确定依赖该结论的行为。“确认继续未定”可以是已定的处置决定，不能误写成业务本身已解决。保持挂起的选项不能暗含一种未批准实现；建议不是人已选。材料明确给定且没有本轮判断的纯事实不增加表态位。

### 2.4 Plan：证明设计能履行需求

起手读取当前Spec、Review和存在的review-disposition，之后从各条实际业务关系确定实体、接口、状态与验证方式。核前一步输出够不够后一步使用，恢复能否找回所需输入，展示值与业务身份能否分别履职，所有约束是否同时成立。不能用实体名字齐全代替可实现性。

每条must与知识原条目的全部要求对应，并挂到实际承担者；普通业务规则写实体说明。反向核已适用的业务步骤是否漏了义务，不只遍历已经挂出的must。终态、状态迁移、事件等按具体业务语义区分，机制不预列案例答案。

收尾核plan.md与contracts.yaml描述同一设计，检查本次是否改变范围、验收、关键承诺及当前来源。纯内部深化不要求回填所有Story细节；实质变化按§3处理。

## 3. 改变与恢复：先判版本，再更新影响面

| 情形 | 动作与完成条件 |
|---|---|
| 未送审的当前产物有真实错误 | 修改责任真源，更新其实际消费者及投影；保持未受影响章节。若已冻结，走现有reopen/登记路径，不直接改冻结件 |
| 送审快照之后形成新决定 | 保持归档Story与Review人工意见；在现有review-disposition及Spec/Plan变更位置说明原结论、当前决定、依据、影响位置与待办。下游实际取得当前依据才算闭合 |
| 用户发起新一轮Story送审 | 用现有reopen、草稿提交、story登记及归档流程形成新版本；不自动覆盖旧评审依据 |
| 仅工程实现深化 | 未改变业务承诺时留在Plan/contracts；不得以同步之名扩Scope或重问已定事项 |
| verifier后发现真实缺陷，包括有内容依据的WARN | 修真实缺陷并按当前Framework规则重验/更新审查绑定；不能为保持旧报告对象回滚正确修正。产物没变化则复用原报告，不无故重跑 |

Story冻结修改使用现有reopen→按当前状态收口→改真源/草稿→chapter→story登记；不建立第二套恢复状态。Framework产物的修正与重验复用现行入口，实施前核实实际命令；无法复用的报告如实重审，不声称旧报告已审新稿。framework只读，确实缺上游能力时记录依赖，不在Extension复制。

同版本自相矛盾是缺陷，已记录并送达下游的快照差异是合法状态。仅有不同文件内容不足以裁定退化，也不能以“历史快照”为由掩盖没有记录的变化。

## 4. 独立审查怎样接住作者偏离

沿原Spec/Plan verifier执行。对象清单由任务书交付，方法在现有overlay维护；不重复整场会议、不增加逐条裁决表。

先从原材料及实际人工决定核本阶段产物的义务、条件、责任、例外和未决；再从产物新增结论回查来源，核是否扩大、降低、编造或引用错位。审查对象包括图文、表、附录投影和当前决策。template是待核的作者理解，不是事实真源。结合实际正文核骨架是否安排了关键理解关系、必要依据与未决去向，是否把答案复述当设计、或因骨架没列而漏掉有效内容；模板长度、待核条数及形式与金样相似均不作为合格条件。

知识审查核实际职责与可实现性：条目究竟要求什么、实际承担者做什么、适用步骤是否遗漏、结果足不足以满足需求。退出“换个需求仍成立即复述”的代理判法；通用要求也可以准确，专门措辞也可能错误。仅报告真实发现及证据，不要求作者逐条自证。

Review审查核推荐、选项后果及成立状态一致；Plan审查核实际数据/接口/恢复链及契约一致。审查结论只绑定本次对象版本，不由PASS推导稳定性。

## 6. 两种写作任务的实施合同

本节把§2.2落到现有函数。数据成员与外部写法按此实施；内部局部函数名可调整，不能自行决定重新引入列契约、新增形式台账或静默接受旧声明。

### 6.1 外部输入：template写什么

固定章节仍用`### <章ID>`定位，章名称来自story-chapters.json，不让作者另维护一份章名表。`writingPlanShell`在每章现有占位说明里显示“正文章名：<合同名称>”，这是写作提示，不增加章名字段。子节由作者用####/#####命名，映射关系不变。

以下为局部中性合同夹具，不是完整十章模板，也不复制进产品作为业务范文：

```markdown
### 05-flow
- 本章主线：让读者理解申请如何被受理，以及不同处理结果怎样返回。
#### 受理协作
形式：时序图
- 描述：用时序图说明发起方、受理方和处理方的调用、返回及失败责任。
- 依据：当前系统设计的受理流程。
#### 结果与后续
形式：表格
- 描述：将各种处理结果与用户下一步对照展示，列在成文时结合实际内容确定。
- 待核：结果未知时能否再次提交；若没有结论，只写当前边界。
#### 用户可继续的操作
形式：无序列表
- 描述：列出已有依据的继续操作及各自前提。
```

作者不需要为时序图预列参与方集合，不需要为表格预定列。成文作者根据来源判断这些内容；来源有缺口时不能为了填满结构造答案。正文可增加合法内容和形式；删改已定安排则按6.5记录实质调整并更新当前模板。

### 6.2 readWritingPlan → selectedStructure合同

保留`readWritingPlan`外层返回`text/chapters/skeletons/structures/rechecks/problems`及原调用者。骨架节点改为`{notes: [], forms: [], sections: []}`，chapter保留id/notApplicable，小节保留title；退出节点tables/diagrams两个平行集合。每项forms为`{kind: 'table'|'diagram'|'list'|'prose', syntax?, ordered?}`，kind决定可用属性：diagram使用现有规范语法键，通用图无syntax；list有ordered布尔；table/prose无额外属性。

`形式：`只匹配整行；具名图从DIAGRAM_SYNTAXES的name/heads派生，不能再造图种表。表格/有序列表/无序列表/叙述是本合同四个协议词，不是业务分类。空值、未知形式、在章或小节之外声明，均记录problems并给位置。`- 形式：…`作为说明时给一次明确写法错误，避免作者以为它被接管；不自动猜正文意图，不遍历自由说明中的“表格”等词。旧`表头：`、旧`图：`一律报当前写法，不解析后继续。

plan.structures由骨架forms派生为`{chapter, at, under?, kind, syntax?, ordered?}`。at为空表示章级；under仅用于H4，父H3仍写at。按章/at/under/kind/规范图种或ordered去重，同位置通用图与具名图重合只留具名要求。prose仅供草稿指引，不进入存在性检查。

selectedStructure的结果：
- h3/h4/skeleton：沿原标题合同；
- tables：仅保留章节合同原tables，不再混入模板columns；
- diagrams：沿原具名图槽位及alsoRequired去重；
- forms：保存模板的table/list存在性要求，带at/under与selected:true；不复制diagram/prose到此数组。

退出addPick中模板列比较、contractTwin、模板列与合同锚列合并。固定章节合同锚列继续由原tableProblem验证，不借此退掉有效合同。

### 6.3 草稿、提交与全稿使用同一解释

在chapter-contract.mjs将选定形式的定位/检查做在同一职责内，由chapterSeedRows、missingPickedSeeds、chapterStructureProblems、pickedStructureNames共用；不得在chapter.mjs和check.mjs各做一次解析。当前入口已经共用chapterStructureProblems，保持调用关系。

定位规则：章级取整章；H3取该节及其子节；H4必须先定位指定父H3，再找该父下的H4，不能借其它父节的同名子节通过。复用document.parseChapter及现有标题规范化；若缺父标题，仅报标题缺失，不继续报该位置的形式缺失。不要保留当前全章搜索H4标题造成的跨父误认。

| 类型 | chapterSeedRows / missingPickedSeeds | chapterStructureProblems |
|---|---|---|
| 模板表格 | 可剥除指引：“本节用表格解释……；按原文决定列与行”；不生成假表头 | 目标范围存在Markdown表即成立，不比列名；固定合同表单独按原规则核 |
| 时序等图 | 原diagramHint按具名图种给起点，不生成业务节点 | 原hasDiagram在正确范围核图种；原合同章级图缺失与选定图去重 |
| 有序/无序列表 | 可剥除指引说明形式与任务，不写无依据项目 | 范围内围栏外存在对应Markdown列表项即可，无序认-/+/*、有序认数字后点或右括号；排除空项与纯横线，不数条目 |
| 叙述 | 原说明行进入guide | 不设字数、段数或关键词门 |

草稿不预填模板自选表头，但固定合同的terms/appendix等种子保持。固定合同同范围已经要求表时，模板的泛表要求由其通过结果接替：没有表或锚列不全只报固定合同错误一次，不能漏掉锚列要求。实际有一张表可同时满足两项，不要求额外造表。H4与H3不同范围不盲目合并。

`drafts.writeDrafts`保留当前未写起点可更新、已动草稿不覆盖的语义：新草稿由新结构生成；已写草稿仅返回缺失标题/形式指引，模型自行调整。缺形式输出“按设计补写，或有依据地调整模板并记录原因”两个出口，不能只有硬塞形式一个出口。章提交仍先剥guide再校验、写Story，正文不遗留操作说明。

“列表/表存在”仅是确定性保护。列是否表达了比较对象、列表是否完整、图是否保持关系由原verifier判断，不向结构checker加入语义词表。

### 6.4 两种任务在什么时候送达

| 时点/生产者 | 模型此刻收到的任务 | 消费者/完成出口 |
|---|---|---|
| 首次skeleton的writingPlanShell及story-write第二节 | 当前在设计表达；取得材料、Spec/decisions；填章/子节、形式、描述/依据/待核 | template可解析后再次skeleton；不在这一步成图或定表列 |
| skeleton铺出的本章草稿头及story-write第三节 | 当前在完成表达；读本节意图与对应原文，确定具体节点/列/内容 | 现有chapter --from草稿；先完成本节再提交，不另交“内容设计”文件 |
| 缺形式/标题的提交反馈 | 指明当前稿缺哪一处；补写或修改设计与说明原因 | 原草稿/模板修正后重提，不自动改模板来使检查变绿 |
| 十章齐的原回看输出 | 核实际完整业务关系及调整影响，清单只负责定位 | 原整稿、登记与Spec闭环 |
| 原verifier任务书 | 当前template全文、实际Story与来源；有调整文件才列真实路径 | 原报告协议；不另出模板评分表或新增模型轮次 |

只有两种任务不同，不要求清空上下文或换Agent。不要在每个小节再重复整份方法，草稿头短写当前动作，细节只在正常写作入口维护。

### 6.5 调整记录如何使用

仅模型对已经用于写章的安排作实质调整时写`AR/story-src/template-adjustments.md`，用普通Markdown，无编号注册器：每项标题为章ID/原小节；正文四项“原安排、实际调整、原因、依据”。首次规划时推敲标题、正常确定表列/图节点、补充已有依据的解释不算偏离。

例如把同一节的表格改成时序图，记录两种形式及为何调用先后比属性对照更能说明问题，依据指当前原文，不写“更好”两个字了事。改节名/合并节/取消原说明任务同理。无调整不建文件；同一调整继续返修更新该项，不把每次措辞编辑记录为新条。

reader-review-task只在文件存在时列路径及用途：核改变是否保留原义务；不将理由自动当真。测试观测将该文件与当时模板、草稿编辑、最终Story对照；它是解释材料，不是证明作者真的先想后写。它不进入STORY_SRC_FROZEN，不添加hash、不成为脚本交付门；原模板/decisions冻结仍保持。

关键事实：现有模型工具允许直接编辑文件，脚本无法在没有旧快照时完美识别每次语义偏离。因此不声称“所有偏离都被机械强制留痕”。本步通过正常作业指引、原verifier与events观测检验执行；发现稳定遗漏再回任务交付分析，不为留痕新建状态系统。

### 6.6 实施先后与保护清单

1. 用下列新协议中性用例改writing-plan解析与selectedStructure，退出columns/contractTwin旧职责；解析失败必须一次列全可确定错误，不能铺半成品草稿。
2. 修改chapter-contract四个消费者及必要的document局部定位，确保打底、补缺和验证同范围；drafts仅改接线，不重建文件恢复逻辑。
3. 一次改齐story-write、空壳/草稿头/下一步输出与verifier对象清单；旧表头协议文字、测试夹具和断言一并退出。
4. 维护侧核完整路径：template→选定结构→草稿→chapter→Story→回看/verifier。保留固定章节合同、附录投影、图片来源、已写稿保护、reopen和人工区回归；不以新形式协议之名重做这些能力。

## 7. 完成条件

新会话只从正常入口能取得各阶段输入与当前决定；作者/审查方法无相互冲突的未决/恢复要求。两种工作状态从原入口明确送达，模板只决定组织与形式，成文确定内容；形式声明与既有固定结构门共同工作，未改变业务的数据深化无需四文档重写；实质变更在现有来源/处置记录闭合。静态检查与对象装配能证明这些机制成立，最终内容及稳定性留工作包3验证。
