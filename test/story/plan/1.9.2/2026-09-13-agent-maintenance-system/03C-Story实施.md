### 三角色在本项目的分工

| 角色 | 承接原职责 | 交付与边界 |
|---|---|---|
| 维护设计者 | 定位 Extension 行为与职责问题，澄清目标，设计 Framework 协作、Extension/Knowledge/Adaptation 的方案与验收，评审真实结果 | 交方案、判据和评审；不代维护实施者修改产品 |
| 维护实施者 | 根据方案实现或修正上述维护对象及测试能力，保证交付内容在使用前可达，运行已确定的验证并提交证据 | 交实际改动、验证和问题；关键设计变化返回设计者 |
| 消费模型 | 使用 Framework + Extension 在目标工程完成业务需求，包括业务侧 spec/plan/coding 等阶段 | 仅使用正常材料与加载链，维护方案和测试答案不进入其上下文 |

原“维护者”列表的每项职责归入上述表，共同的信息隔离、取证和只读边界放表后；维护者是前两者合称，不是第四角色或一个会话可以包办的职责。

保留 CLI 代理需求方的身份和回复边界；按本次任务由已指定的维护角色承担，不新造调度方式。将“verifier 不构成第三种项目角色”改为“verifier 是产品内部独立审查能力，按 Framework + Extension 的使用流程工作”，不再引用旧角色数量。

§7.3 的“方案维护者”写明为维护设计者，“维护者从实际文件重新还原行为”的评审责任也归维护设计者；原实施会话义务归维护实施者。预算中 reviewer 是所指评审职责，原有审批权限保持。

当前维护任务先取得目标、有效决定和项目边界，预算及测试操作在对应动作前读取相关段；脚本、合同和历史证据按实际问题加载。宿主强制加载的根指令继续适用，其成本如实计入。
