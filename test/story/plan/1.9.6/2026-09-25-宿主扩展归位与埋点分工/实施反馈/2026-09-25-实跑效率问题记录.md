# 实跑效率问题记录（2026-09-25，suite story-suite-20260925-191417）

用户 09-25：「模型写完 story+spec 花了 1 个小时，然后又花了 1 个多小时解决问题，而 auto 早就完成了」；要求记录如何提高 extension + framework 的运作效率与一次成文质量。本件只记事实与改进方向，范围与版本由用户定。

## 1. 事实（car-key-sharing，runlog 路径 `output/story/story-suite-20260925-191417/cases/car-key-sharing/20260925-191833-24532-30b3237f/runlog.md`）

| 时段 | 做了什么 | 耗时 |
|---|---|---|
| 19:18–19:55 | 取材（两次补料关）、范围、成文 story + spec、首次 harness | 约 37 分钟 |
| 19:55–20:39 | spec verifier 6 次，首轮闭环前 | 约 44 分钟 |
| 20:40–21:12 | 评审意见落地的修订轮：改 spec、重登记 story、verifier 3 次 | 约 32 分钟 |

对比 auto-topup：两段合计 verifier 4 次。

**8 次 verifier 每次都是 PASS、0 blocker**；重审不是因为产物不合格，而是：

| 次 | 触发重审的原因 |
|---|---|
| 2、3、4、5 | PASS 后模型逐条修 advisory WARN（AC 关联漂移、拼写、API 名对齐、AC 归级），改了 spec/acceptance → 审查对象（subject）变 → 交付门要当前 subject 的原始回复 |
| 6 | 报告格式：`story_reader_review` 的 `details` 下两个键须是列表，写成块标量被交付门拒收，同一请求重投 |
| 7 | 修订轮改了验收描述，模型判定需重审（合理） |
| 8、9 | 修订轮里再修 WARN；改 spec 后 story 附录投影要重登记，story.md 属 spec 审查材料，重登记本身又换 subject（21:05:48 模型自述「这里进入了一个循环」） |

机制出处：`doc/extensions/hooks/shared/verifier-report.mjs > withoutCurrentReport`——沿用历史审查只在「无进行中的 update 且 summary 带 `script_revalidated`」时放行。framework 的 harness 与 check-receipt 已按 `completed_with_prior_review` 接受（21:05:43 summary：`not_reverified` 只剩 `lifecycle_hook_fragments`），拦的只有扩展交付门。这与 CLAUDE.md §五「verifier 只跑一次；材料变了但历史有 PASS 沿用并如实标 `completed_with_prior_review`」和 `phases/update.md` §五「什么时候派」由模型按实际影响判断不一致：门禁用机械条件替掉了模型的判断。

交付门上的口头评审意见（用户 09-25 裁定：这是**未经授权加出来的功能**，测试用例随之扩展）：
- 设计的评审路径只有一条：spec/story 完成后归档送审 review.md，评审人在评审载体上表态，再独立调用 `/story update` 取回并落实——即 auto-topup 规划里「评审意见已写在系统上，拉回来处理」那一关。交付门上不需要口头评审意见，也不需要为它设计 update 流程。
- 机制里的加出处：09-18（1.9.3 步骤 4 裁定，`plan/1.9.3/2026-09-16-Extension机制级替换增强与退场/步骤4补跑评审与裁定-2026-09-18.md:19`）写入「交付门上人给的评审意见走 `/story review` 回流」；09-20（1.9.4 C3，`plan/1.9.4/2026-09-20-版本实施/步骤C3交回-2026-09-20.md:22–23`）随 `/story review` 退场改成 `/story update`，现存 `phases/spec.md:85`、`core/flow/routing.py:380` 两处。
- 用例里的出处：`cases/car-key-sharing/interaction-script.yaml` 的 `review-comments` 标 `expected_phase: spec`、在对话里给评审意见（08-30 `0ba8b13e` 建立，09-04 `c981b01a` 改成短语）；宿主据此在交付门口头给了评审意见，模型按 `spec.md:85` 开 update 20260925-124212，修订轮派了 3 次 verifier。上一轮 story-suite-20260925-114632 同样如此（runlog 9209–9693 行）。
- **修订轮的直接起因是宿主回话**（用户 09-25 指出，宿主认责）：car-key 的 update 测试设计在 plan 完成后的第二段（评审决定写进 review.md 人工区再触发，auto-topup 在 spec 完成后测）。spec 闭环时模型只问「是否进入 plan」，宿主应只答所问，却照规划里的 `review-comments` 在交付门口头给了评审意见，把 update 提前到 spec 阶段触发。20:40–21:12 的修订轮（约 32 分钟、3 次 verifier）记在宿主账上，不计入机制或被测模型；19:55–20:37 首轮闭环前的 6 次重审是机制账，分析见上表。

同一处还有一个规则与门禁的冲突：`phases/spec.md` ⑤ 写「PASS 之后只是 advisory 或 WARN 修法：改完重跑一次完整 harness 走历史沿用，在 notes 记『未独立重审』」，但交付门 `withoutCurrentReport` 只在 summary 带 `script_revalidated`（`--revalidate` 才有）时接受历史沿用，完整 harness 不带这个信号——模型照规则做也过不了交付门，只能重审。

一次成文质量：首轮 verifier 即 PASS。WARN 集中在 spec §8 与 acceptance.yaml 的编号与关联漂移（auto-topup 同样出现 AC-11 同号不同义，verifier 判 MAJOR FAIL）——这类可机械核对的一致性问题留到最贵的语义审查才发现。

## 2. 改进方向（待用户定范围）

| 方向 | 做什么 | 预期效果 |
|---|---|---|
| 退出交付门口头评审（用户已裁定） | 删 `phases/spec.md:85` 与 `routing.py:380` 的交付门评审句；交付门后的下一步只有归档送审 / 进入 plan；`car-key-sharing` 的 `review-comments` 改为归档后评审、独立 `/story update` 取回（本地问题单怎样归档送审需先核对接层对 ISSUE 的支持）；相关测试随改 | 评审只走设计的那一条路；不再出现交付门后自开 update 的修订轮 |
| 交付门与 framework 闭环口径一致 | 交付门接受 `completed_with_prior_review`，在 update 进行中也按「本轮改动是否影响评审依据」由模型判断是否重审，门禁只核判断留痕 | 去掉 2–5、8、9 类重审 |
| PASS 后的 WARN 有去处 | 任务包与作者页写明：PASS 后的 advisory 记入 notes 或随下一阶段处理，修了且只改表达的不重审；需要重审的只有改了验收、契约或业务口径的 | 去掉「修 WARN → 重审 → 新 WARN」的链 |
| 投影刷新不换审查对象 | story 附录机器区是 spec 的投影，刷新它不应算新审查材料；或 spec 改动后投影自动刷新，不需要 reopen → complete → story 三步 | 去掉 8、9 类重审与手工重登记 |
| 报告格式在交付前就对 | verifier 请求里写明 `story_reader_review` 的结构，或由脚本规范化报告格式，不靠重投 | 去掉 6 类重投 |
| 可机械核的一致性前移 | spec §8 与 acceptance.yaml 的编号、功能点关联在 harness 脚本层核，verifier 之前就报 | 提高一次成文质量，减少首轮 WARN |
