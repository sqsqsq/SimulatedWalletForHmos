本文现作为 [08-机制与知识的消费协作设计](08-机制与知识的消费协作设计.md) 的 reporting 样例分册，不再单独代表全部优化范围。职责、实施顺序、验收与预算统一按08；本文件的具体贯穿例子与任务结构供实施使用，预算不重复相加。

## 1. 要取得的结果

消费模型先能用业务语言设计统计，再能把同一组业务结果转成项目的具体上报实现。reporting 不只列出字段和规则，还要像设计模式一样给出应用步骤、完整参考与完成判断，使模型不必自行拼接几节知识来猜实现方法。

本次核对的设计模式确实分上篇“适用与选型（plan）”、下篇“结构与落地（coding/review）”，包含应用步骤、SDK事实、角色骨架和验证。上报借鉴这种围绕读者任务展开的组织，业务设计与实现设计两层分别服务 Spec、Plan；知识仍为 facts，规约义务继续有效，不引入候选选型或第四类知识。

前次设计把“业务语义在前、协议映射在后”当作足够的使用指导，实际仍以字段分类为主；此处由设计者补齐应用方法和贯穿参考，不继续依赖加长阶段 author。

## 2. 文件结构：规则一处，参考两层，同一业务

按读者任务使用四个 H2 面：统计设计（已确认）、上报实现（已确认）、编号分配与复用（已确认）、业务扩展字段（未确认）。前两面把应用步骤、所需语义、同一业务参考与完成判断放在一起；新编号分配为条件读取，未确认字段独立。具体映射与旧需求处理见[面结构裁定](评审意见/2026-09-24-08B实施评审与面结构裁定.md)。

两层应用直接成为前两个事实面的主线：

### 统计设计

说明读者拿到业务目标、流程材料与已核采集能力后，怎样形成业务统计设计：

1. 确定观察对象和范围，区分业务目标与为理解流程质量需要的指标。
2. 沿实际流程识别步骤和子点，区分步骤成功、流程成功、未执行与失败。
3. 对每个点说明适用结果、产生方、本端获知时机以及一次尝试的边界。
4. 核对项目已实现采集能否表达这些事实；需要补采的保留要求，能力尚未实现的列建设差距。
5. 多指标共用同一事实时引用同一采集；独立运营采集按明确需求选择。结果是一份业务读者能核范围与覆盖的方案。

每一步在需要时解释相关项目语义；编号分配和未确认参数给出明确的条件读取入口，保持一处来源。给出后述贯穿例子的业务输出，并用两三句解释为何这样选择点位。

### 上报实现

说明读者拿到已定业务点位与结果后，怎样形成可实施方案：

1. 从真实接口或待建接口设计定位结果在哪个分支、回调或用户动作中确定。
2. 根据项目协议复用身份与值；需新增时给出具体候选和登记位置；确缺分配依据的指出精确待决。
3. 每种适用结果明确字段值或取值表达式、来源、缺席条件以及扩展维度。
4. 决定责任方法和报告时机，用同次尝试处理重复回调，用新尝试表达重试；退出界面与真正取消分别处理。
5. 形成代码责任与简短调用骨架，再列对应原始事件怎样验证。

紧接着展示同一例子的实现映射和短骨架。实际值、候选值、尚未确认的值分别标清；骨架展示角色协作和调用时机，业务类明确为本例待建设计，既有 SDK 调用按真实接口。

完成判断是“业务结果→责任方法/分支→身份与字段来源→调用→预期事件”连得起来；不是表格填满或文件名出现。

## 3. 贯穿例子怎样写

复用现有“服务开通”题材，范围保持小：信息校验、短信验证、开通结果。它只帮助理解组织与应用，消费模型根据当前需求重新设计。

### 业务输出

主指标观察一次服务开通尝试的结果；短信验证步骤的结果用于定位开通受阻原因。验证失败后重新输入可以继续，步骤失败不自动等于整个开通流程已失败。开通受理与最终开通成功是否相同，按本例明确假设说明；远端最终结果通过回调或查询取得。

至少列清以下关系：

| 业务点 | 业务结果 | 获知依据 |
|---|---|---|
| 信息校验 | 通过、条件不满足 | 校验返回 |
| 发送验证码 | 发送成功、发送失败 | 发送响应 |
| 校验验证码 | 校验通过、未通过 | 校验响应 |
| 短信验证步骤 | 验证完成、主动终止 | 子点结果与用户操作 |
| 开通结果 | 开通成功、开通失败 | 开通结果回调或查询 |

这些是示例已声明的适用结果，不是通用必报全集。普通流程退出没有天然对应 SDK 取消能力。业务输出先解释观察目的与覆盖，再呈现点位。

再用短段补多指标/多流程关系：同一验证事实同时用于步骤质量和整段流程分析时复用采集；同名验证出现在不同业务流程时，按真实业务身份区分。独立 BI 只有明确运营需求时才增加；没有需求的例子到此即可，不为展示渠道齐全编造运营诉求。

### 对应的实现输出

将“校验验证码”的通过与未通过完整展开为两行，保留上下游关联。其他点用简短映射说明其责任与结果，不把上篇重抄一遍。

例子可以根据本仓分配规则提出一组完整候选，明确这些数值仅属于演示、未占用真实编号。例如：模板使用已存在的 Wallet_COMMON，流程001、步骤002；假设首次候选模块01、模块内流程01、节点02、子节点02，则通过内码0101020200、失败内码0101020201。前置是本例没有其他已分配值；实际需求必须按全仓定义复用或核冲突。

通过对应 STEP_SUCCESS、未通过对应 STEP_ERROR_BY_ERROR；事件身份保持相同，差异由结果字段表达。外码来自校验响应的实际外部码，没有就省略。每次校验的尝试标识属于执行上下文，业务幂等身份与它分开。耗时只在有观察诉求时取本次请求起止。

新增业务类的示意责任：业务方法校验并处理响应；项目 Builder 组装并发送；尝试上下文确定此次结果是否已结算。用不超过约25行的骨架展示正常分支、失败分支、一次结算与 Builder 调用。代码中的业务响应类型和方法写明是本例假设或拟建设计，SDK 的实际接口带源码依据。

验证短表至少说明：一次通过、一种失败、同次重复回调、重新输入后的新尝试分别应产生怎样的事件；退出验证界面后，已经发出的发送请求仍记录自己的结果。验证的是选定业务对象，不按页面退出统一屏蔽后到结果。

## 4. 阶段机制怎样使用

知识中说明两层内容的读者目的，文档章节坐标留在机制。知识的 SDK、枚举和候选规则不复制到通用 author。

| 实际消费者 | 调整 |
|---|---|
| hooks/spec/author.md | 将现有长段收束为任务：取得项目业务统计语义与业务设计参考，按当前材料完成观察范围、点位、结果和已有覆盖；落 §9.4。完成条件保持已有业务路径走查 |
| hooks/plan/author.md | 承接 Spec 已定结果，读取项目协议与实现参考，完成逐结果责任、字段和验证；落既有单处埋点小节与契约。保留“待登记是已有具体候选”的边界 |
| spec/plan author.mjs | 保持现有事实入口与动态点位数据；不按 reporting 文件名写条件分支，不新增读文件调度脚本 |
| templates/spec-sections.md、plan-sections.md | 保留形状，明确示意行要用当前项目值完成；方法指向各自 author，避免又复制一份长应用步骤 |
| pre_verifier 与现有 overlay | 审查分别核业务语义、技术实现两个完成对象，按实际依据检查；不以参考例子的名称、数值和行数作为答案 |
| capabilities.md 的 reporting 条目 | 走查要求明确同时使用两层参考，把一个已定业务结果落实到具体项目实现；引用原知识内容，不复制示例和码表 |

本次是既有业务语义与实现参考的质量完善，不新增能力类型或协议字段；covers 更新为四个任务面，revision 保持1，并在台账记录旧面到新面的映射。若实施发现实质改变项目协议、适用范围或能力要求，回设计确认相应修订，不为排版自动升级版本。

## 5. 实施顺序与退出

1. **完善知识使用参考**：先形成同一业务的两层完整结果，核现有 SDK 与分配规则。按四个任务面重组正文，把项目定义、应用步骤与参考放在使用它的位置；保留 H2 确认边界、真实事实和用户已定业务规则。
2. **接入并收束阶段任务**：Spec/Plan 各自引用所需参考，撤掉重复的方法句；台账、模板与审查保持同一完成标准。按实际 diff 评审，不增加新 loader、状态或 Agent。
3. **验证与交回**：知识面解析、未确认取证及相关作者/审查交接做必要离线回归；由维护者从当前材料推演业务与实现两层能否接续。实际消费模型效果并入整版最终实跑，不另加一轮业务 CLI。

S3 当前三项已知返修仍独立完成并评审，本方案不能代替它们；最终实跑前两部分均须交齐。执行者反馈与维护者评审继续放本目录的实施反馈/、评审意见/。

## 7. 验收

- 业务设计参考能独立说明指标与流程、步骤、结果及覆盖依据，读者不依赖 SDK 枚举才能理解。
- 实现参考使用同一业务，至少一个点的全部示例结果给出完整候选或来源表达式、责任方法、时机与预期事件；实现者无须自行发明核心映射。
- 示例里的假设、候选和现有 API 事实分清，项目字段含义未确认的仍保持可见。
- 两层任务就地解释所需规则，跨任务共用内容保持一处来源；阶段坐标在机制，业务规范在知识。
- 四个任务面可独立引用，业务扩展字段的未确认验证保持，Spec/Story/Plan 的既定章节及单处埋点范围保持。
- 最终真实产物按用户业务目标审，不按示例表形状、固定值或固定点数审。表达和实现是否真正改善，以整版实际输出为证。

骨架补齐：正常响应与请求异常交给同一结算方法，一次尝试先判断是否已结算再记录；重复回调进入该方法，不重新发送请求。方法假设、通信失败候选与预期事件随之同步，见本轮面结构裁定。
