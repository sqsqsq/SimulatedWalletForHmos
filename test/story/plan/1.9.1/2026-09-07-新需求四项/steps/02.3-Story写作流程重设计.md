## 1. 目标与设计改变

Story面向人解释一项完整业务，章节是表达与保存的单位。先保存已有事实与结论、识别要讲清的关系，给出可调整的阅读主线，再在写作中深化。既不能让十章各自重新决定同一业务，也不能为了避免重复而提前限定全部最终内容。

本步同时追求内容完整准确、整篇关系一致、自适应表达、跨次稳定与合理成本。减少重复不能以删事实为代价；改善流程图不能让验收责任丢失；一次已知案例写得好不构成稳定性证据。

| 当前流程的问题 | 新流程的责任安排 |
|---|---|
| 写每章时重新筛选来源、解释业务 | 进入Spec前保留初步材料判断，Spec后一次形成整篇写作设计 |
| 原始事实、提取稿、Spec转述平权堆叠 | 保留来源身份与性质；Spec只作为本轮设计及约束，不伪装成第二份独立需求证据 |
| 边写边决定归属，减少重复时可能删义务 | 编排给主要解释位置与互补用途的当前建议；写作保留已定依据并允许深化，模板不作为内容白名单 |
| 长指导区随每章刷新，要求又被head截断 | 读者材料与作者正文分开；持久的整篇编排和按章材料视图为工作输入；stdout只给短行动摘要与读取路径 |
| 最后一次统稿兼做理解、发现、编辑和证明 | 写前先审视业务关系与文档组织，写后核对实际保留情况；独立verifier按来源和已定判断再验正文 |
| 局部变好就宣布优化有效 | 每轮同时核所有章节职责、关键事实保留、质量回退和运行成本 |

保留已有效的导入、材料轮次、范围确认、术语与知识能力、编号、附录投影、Review渲染、人工区保护、局部结构检查和Framework闭环。重设计的是上面的写作流程，不另造通用框架或Agent调度器。

## 3. 一条正常路径

```text
现有材料导入与范围确认
  → 模型生成S4候选稿，脚本提交AR/design并完成原流程收口
  → 脚本枚举原材料内容单元，模型保留稀疏初筛判断，不生成Spec前视图
  → 进入原Spec流程，完成需求/设计/知识判断与技术契约
  → 更新材料目录：只增加Spec及已变来源
  → 模型结合初筛、Spec和决策保存关键依据与开放关系，形成当前编排，并反查遗漏、排除与推断
  → 脚本校验引用，按模型已选的表头/图语法建立结构与材料视图
  → 模型沿阅读主线写作并继续深化；脚本逐章检查和落盘
  → 模型从来源核实际正文与编排取舍，保留合理发现并修正必要内容
  → 原story登记、Harness、verifier、回执与交付
```

初筛利用已形成的上下文，但不声称模型已理解所有材料。Spec后增量处理与整篇编排是同一项模型任务，避免“再筛一次、再规划一次、再理解一次”。分段落盘不等于分段重新决策。

各阶段只新增自己的判断：初筛定暂定用途与疑点，不写业务方案；Spec形成需求/工程结论；编排复用已知结论，给当前解释主线和待深化问题；成文可继续发现关系、增加必要解释，不随意重定业务；写后核对实际正文。新增认识若改变业务结论，回原Spec/decisions；只是表达深化则不新增审批或要求先重填模板。不存在新问题时，不重新做一遍相同分析。

新增过程文件全部在AR/story-src下。AR根继续只承担已有交付面。文件合同见步骤01/02：source-index.json是脚本索引，source-selection.json是可由编排覆盖的稀疏初筛，story-template.md是模型形成的当前写作设计，chapters/是可重建输入视图，drafts/是作者正文。编排不是永久内容上限，各自没有第二份同义真源。

## 4. 角色与约束能力

| 承担者 | 必须做 | 不承担 |
|---|---|---|
| 脚本 | 枚举与定位原文、保存源版本、检查引用完整/合法、生成材料视图、落实模型已声明的表头/图语法、固定编号/投影、检查结构、保护文件、给恢复位置 | 不判断来源重要性、业务冲突正确答案、哪种形式最合适、跨章是否属于必要重现、图是否讲清真实关系 |
| 作者模型 | 初筛、处理真实冲突、形成整体编排、选择表达方式、按编排写作与核对 | 不手算原文范围、复制并修复图片路径、重建技术投影或维护海量事实字段 |
| 原独立verifier | 对照原始需求、已定决策与实际正文，检查丢失、矛盾、无依据承诺及表达 | 不把编排或作者自评当答案，不以索引全覆盖证明内容完整 |
| 人 | 范围、真实未决取舍、交付与效果验收 | 不逐文件搬运来源、不代填过程状态 |

物理检查只能约束正常工具路径；模型直接编辑文件、忽略材料或错误判断，不可能由若干字段存在性完全证明。它们由来源核对、独立审查与真实行为评价发现。不能把新初筛表变成新一代七行自证。
