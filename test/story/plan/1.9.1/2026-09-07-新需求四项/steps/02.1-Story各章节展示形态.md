## 1. 问题与用户目标

用户要求平等审视每个章节，从内容职责与阅读目标出发正向优化展示形式，适应未事先列举的场景，同时保证内容不重复、不丢失。内网数据管理功能的纯文字结构说明、流程三标签和单套回退表达是问题线索，不是本步的重点章节或范围边界。

目标是让读者看明白需求、方案、功能行为、设计约束与交付安排。形式服务于读者理解，不以表格数、图数、固定段数或短句数量代替质量。保留现有防遗漏能力，避免再次出现没有流程图、源图没有去向、验收缺失等退化。

本步处理展示方法及其直接机制，不重做知识协议、Review 决策发现、会议解析，也不扩为 Extension 大型重构。当前 CLI 只测试步骤 1，不能当本步效果证据。

## 2. 根因与设计决定

现有 `story-write.md` 已有“按信息关系选形式”的原则，但 `story-chapters.json` 的 form/slots 又把段数、UI 视角、标签和列表写法固定下来。chapterDraft 搭出固定槽位，check 又核其中部分形态，通用写作原则实际让位于固定布局。

本步直接分清现有合同的两种职责，不新增合同层：

- **questions 与 form.note**：本章要回答的问题，以及适合本章的默认组织建议，送达作者与读者审查；默认不表示唯一合法形式。
- **form.slots 与必要固定标题**：只保留有明确交付理由的确定性结构，例如流程图存在、验收表、交付物表及附录投影。移除只代表写作偏好的字段与门禁依赖。

模型读完整体材料后，决定按什么对象分节、采用何种表达。脚本保留术语种子、来源提示、必需结构及附录投影；不猜需求属于哪种业务类型，不生成“页面版／数据版／批处理版”等分支模板，不另存展示计划。

### 共用的形式选择方法

在现有 `story-write.md` 的“什么内容用什么形态”中替换为一套短方法，不另加平行规则页：

1. 明确此处读者要理解或判断的内容，放进负责回答该问题的章节。
2. 按主要关系选择表达：属性/对照/条件组合用表，先后与分支用流程，状态变化用状态图，跨方调用与返回用时序/泳道，对象归属引用用关系图，原因与取舍用叙述。
3. 简单内容短写，复杂内容分层；允许图讲关系、表讲属性、文字讲理由。避免重复相同内容，不禁止互补表达。
4. 检查读者能否直接找到条件、差异、方向、责任、结果；不要求读者从大段散文中自行拼出结构。

取消把 12 步、4 个状态、单列/单行表等数量阈值当作换形式的充分依据；依据是关系复杂度与可读性。不因此放宽用户已确认的流程总览及多方交互图要求。短段与篇幅只作提醒，不保留“每章 2–4KB”“固定四段”等填量目标。

## 3. 十章逐章设计

每个一级章下的二级内容单元、三级拆分对象、默认形式、切换条件与去重边界，详见 [Story 三级章节展示细则](02.1-Story三级章节展示细则.md)。本节保留十章的职责与调整落点，细则给出层级实施依据；二者不生成两套运行期规则。

每章都按“读者目标—组织与形式—内容边界—调整落点”审视。平等看待指采用同一套设计尺度，改动大小由实际问题决定；不为没有问题的章节制造改动，也不以少数反馈章节代替全篇设计。

### 3.1 背景

**读者目标**：理解现状问题、影响对象、为何现在需要改变，以及有依据的目标。

**组织与形式**：按问题及其因果关系组织。简单背景用短文，多类现状或多个可比较目标可用对照表，确有空间或数量关系时可配有依据的示意或数据图；不虚构用户旅程、指标和成本。

**内容边界**：本章说明动机与目标；具体职责分工归范围，方案机制归业务方案，精确通过条件归验收。后文可引用目标，不重新叙述全部背景。

**调整落点**：删除四段占位与禁分节，questions 覆盖实际问题和目标，form.note 给组织原则；保留必要来源和真实性要求。

### 3.2 术语

**读者目标**：掌握理解本需求必需的概念，明确实际存在的歧义。

**组织与形式**：词义映射优先表格；复杂概念的层次或集合关系可辅助配图；没有易混概念时不凑“几组区别”。允许按真实概念关系分组。

**内容边界**：本章解释概念，不承担功能规则、完整字段契约或方案介绍。后文沿用统一名称，在解释实际行为时只补新增信息。

**调整落点**：保留术语表种子和基本词义映射，取消强制易混段占位及禁分节；审查概念是否清楚一致，不核易混组数。

### 3.3 范围

**读者目标**：看清本需求、本特性及相关责任方分别做什么、不做什么，依赖和交接到哪里。

**组织与形式**：按责任边界组织，简单边界用叙述，多对象用责任矩阵或范围图；真实依赖与交接可用列表、表或关系图。是否存在兄弟单据只决定交接内容，不决定能否使用对照表。

**内容边界**：本章说明责任与交付边界；参与方运行时怎样协作归业务方案/流程，各项能力的处理细节归功能说明。依赖责任在本章确定，上线章只补交付顺序和启用条件。

**调整落点**：保留“特性分工”定位及兄弟交接条件，取消固定两段和按工单组织选择表格的限制；实际有依赖才展开依赖节，不生成无依据的承诺。

### 3.4 业务方案

**读者目标**：理解总体解决办法、协作关系、业务真源、关键规则、取舍依据与整体风险。

**组织与形式**：按解决问题的逻辑组织；协作/数据流用图，参与方属性用表，组合规则用决策表，真实备选用对照，原因与依据用叙述。不同形式各承担一部分解释，不全篇重复同一方案。

**内容边界**：本章解释整体机制及为什么这样选；流程展开执行过程，功能说明展开局部规则。风险在此汇总触发、影响和控制方向，具体恢复操作归异常或交付管控章节。

**调整落点**：保留“参与方与分工”定位，参与方表作为默认；取消规则只能列表、有 settled 就必须出现被否方案表的联动。明确要求说明依据，不能为表现“有取舍”虚构备选。

### 3.5 业务流程

**读者目标**：看清从触发到结果的完整过程，谁依据什么处理，分支、状态与交接怎样衔接。

**组织与形式**：按实际过程、并行关系或生命周期组织。简单分支可短文说明，条件组合用表，多方调用用时序/泳道，状态变化用状态图，复杂局部可分层展开。触发、处理、结果与后续作为要回答的问题，不统一打印成标签。

**内容边界**：本章负责能力之间的顺序、条件与连接；第 6 章展开各项能力内部规则，第 7 章展开异常恢复。图上标明必要的异常去向，详细恢复可在第 7 章说明，不完整复制同一段过程。

**调整落点**：保留章首总览图、全部必要分支去向及已确认的多方交互图要求；取消固定“主路径”标题下必须有序列表、每分支各一节及“时机／方案／走向”三标签。总览与局部须有明确连接；上游图仍逐张对应，可等效合并或改画，不以灵活表达取消图或隐藏分支。

### 3.6 功能说明

**读者目标**：理解各项能力在不同输入、条件下怎样工作，处理规则、数据/状态变化和结果是什么。

**组织与形式**：按能力或有业务意义的场景分节。结构属性用表，对象归属用关系图，条件处理用决策表，生命周期用状态图，操作过程用步骤；有界面时使用界面图及交互说明。无需按项目类型套不同模板，也不强制一种功能使用全套图表。

**内容边界**：本章解释局部能力的行为；跨能力过程归第 5 章，精确接口与完整字段契约归附录。正文展示理解行为必需的数据含义，不复刻全部技术清单。

**调整落点**：删除页面专用问题与 image/list/页面状态表通配槽位；移除 ER 图只能放附录 B 的位置限制。按内容所属位置表达实体关系，无关实现代码和类名结构不进入主叙事。

### 3.7 异常与恢复

**读者目标**：区分预期受限与真正异常，理解影响、可观察结果和恢复条件。

**组织与形式**：按实际失败与恢复关系组织。简单情形成表，多步补偿用步骤或图；列名对应真实观察者，可以是用户、调用方、后台任务或运维方。实际没有某类情形时说明依据，不为了两张表制造异常。

**内容边界**：本章负责运行失败后的行为与恢复；整体风险归第 4 章，完整正常过程归第 5 章，特性的交付停用/恢复归第 9 章。同一恢复措施在主要位置讲全，其他位置只补该处需要的条件或联系。

**调整落点**：保留两类语义区分，取消固定“用户看到什么”表头及两类必须同时展开的标题；审查数据与业务结果是否被交代，不只检查提示文案。

### 3.8 验收

**读者目标**：能够根据场景和可观察结果判断需求是否完成，并对应原始要求与主责。

**组织与形式**：按真实验收目标分组，保留编号与通过条件表；复杂输入组合可补参数矩阵、预期数据样例或时序说明。有真实来源的质量目标写清条件与单位，不补编指标或测量值。

**内容边界**：本章验证已经定义的行为，不重新定义一套业务规则。必要地引用关键数值、条件和结果以便独立验收，但不重写功能说明的完整处理过程；如有矛盾先修正权威内容。

**调整落点**：保留验收表与编号追溯，允许必要辅助说明和图表；审查通过条件是否足够、与正文是否一致，不以只有表格或表格更多为合格依据。

### 3.9 交付与上线

**读者目标**：理解交付物、接入与启用依赖、开放顺序、兼容边界，以及各对象如何管控、停用和恢复。

**组织与形式**：按交付关系及可独立控制/恢复的对象组织。顺序用步骤、依赖用图、版本兼容用矩阵、对象管控用表或小节，简单情形短写。回退措施可以有多套，共用措施可合并但须写清作用范围。

**内容边界**：本章说明交付及运行管控，不重复系统内部每项功能和异常处理。每项措施应讲清触发与执行方、作用范围、动作、存量/在途业务及数据影响、恢复条件；关闭入口不能自动代表撤销业务或恢复数据。不可逆结果明确说明，不承诺不存在的开关或回退能力。

**调整落点**：保留交付物表及“回退设计”定位；取消仅交付物可建表、固定四项开关列表、单套回退三标签。对象多时允许多行/多小节，依赖关系明确，不按特性数量机械复制一套段落。

### 3.10 附录

**读者目标**：方便查阅精确契约、知识判断、改动边界与材料依据，支撑正文理解和核查。

**组织与形式**：保留五节与单源投影，结构信息用表，材料贡献用列表；理解精确契约必需的单位说明、格式样例等可放作者区。决定行为理解的关系图放正文相应位置，不把图集中搬到最后。

**内容边界**：机器区只由 spec 和知识判断等真源派生；作者区解释，不维护第二份字段或规则定义。材料清单只解释来源贡献，不容纳无处安放的业务正文。正文不得只剩“见附录”而无法理解需求。

**调整落点**：保留附录节结构、A–D 投影、材料清单；取消表后任何说明和非 Mermaid 围栏一律拒绝的泛化限制。既有语言、自包含与源码倾倒限制继续成立，不放开无关工程细节。

## 4. 内容不重复、不丢失的共同要求

**先确定主要落点，再选择形式。** 一项事实或规则以“主要回答哪个读者问题”确定完整说明的位置。另一章确需使用时只交代它与本章问题的关系，避免再复制整张表或整段流程；不以章节名机械分配同一份材料的每一行。

**必要重现与重复区分。** 验收重现预期值、流程图标示结果、正文说明结果原因，可以同时存在，因为各自回答不同问题；其含义必须一致。图讲关系、表讲属性、文字讲理由属于互补，不能为去重删除其中独有的信息。

**换形式不改变事实。** 来源表的条件、属性、单位、边界与例外，来源图的连接、方向、分支与终态，以及已确认的决定和约束，重组后仍有可识别的去向。缩短、合并或移位之前，先判断有无独有信息；不能以“图里大概有”“其它章应该讲了”代替检查。

**复用既有验证而不新建逐事实台账。** 写章时按本章 questions 核必要内容；现有统稿检查跨章重叠、衔接与矛盾；独立审查同时从来源到产物检查遗漏、从产物到来源检查依据。脚本保留源图、验收编号、投影与引用等确定性保障，不把重复率、字数或相似度当内容完整性的证明。

## 5. 合同、脚本与审查同步

### 5.1 合同和草稿

**运行期边界（98 Q1）**：三级细则只留在维护侧，不由交付脚本或提示词读取、引用或逐行复制。沿用 chapter.questions 说明必答问题、form.note 说明本章必要的默认组织与切换条件，共用方法只维护一份；不限制 note 的句数。slots 只保留本步明确的流程图、术语/验收/交付物表等必要结构，附录保留原有五节与投影；已有必需标题仍由 subsections 管。可选内容单元不得因出现在细则里就变成必填目录、标签或槽位。

在现有 story-chapters.json 按 §3 的十章设计更新 questions/form.note；默认形式只写建议。slots 中删除本步取消的固定形态；保留流程图、术语/验收/交付物表等必要结构。用于形式默认的 prose 数量、UI 通配槽位和固定标签不再生成。

chapterDraft 继续使用现有路径，生成本章标题、简短问题与组织提示、必要标题及有实际来源的种子。柔性正文只留一处填写入口，不把每种可选形式都搭一份空表/空图。这不是空白写作：读者问题、材料、知识、源图和规则已在作者上下文里。

术语种子、材料清单、来源图任务包与附录投影继续复用。只改展示职责，不重新扫描业务生成第二份“展示台账”。旧 slots 渲染分支在没有消费者后删除；仍被必要结构使用的保留。合同版本随变更更新，不维护新旧展示协议分支。

### 5.2 确定性检查

保留十章完整性、已确认必需定位、源图对应与路径、流程图存在、验收编号/表、材料清单、附录五节与投影一致性、写入与冻结边界等既有检查。

撤销仅为旧排版服务的检查：本步已允许的子节、取消的固定标签/列表/页面表，以及附录正常辅助说明不得出现的限制。优先通过删除相应合同槽位让通用检查停止要求，不新增“数据型可跳过”“无 UI 豁免”等分支。

第 5 章图的章首位置、图文关系和细节完整性由作者与独立审查判断，现有图存在/来源检查继续提供结构保障。不追加语义分类器、图表数量配额、文本相似度或“有字段名就必须有表”规则。

附录的机器区仍只由真源投影，作者不能通过增加说明修改或绕过投影内容。允许的辅助说明放作者区；材料清单仍只承担来源与贡献，不成为图文收纳区。不为这一变化重写投影架构。

### 5.3 作者与独立审查

story-write.md 用本步方法替换相应旧段落，避免新旧指令并排；统稿将“同一内容不得用多种形式”修正为避免重复、允许互补。默认篇幅/数量提醒不得与关系选择、章节复杂度冲突。

reader-review-task 从章节 questions 取得新职责，删除依赖旧 label_hints 的三标签提问；复用现有任务装配，不新增一次模型审查。spec-rules.overlay.yaml 的读者审查补齐展示质量的明确判据：

- 形式是否让关键关系、条件、结果、责任直接可见；结构信息是否被压成难以比对的散文；
- UI 与无 UI 都使用真实的观察者和能力对象，未凭空生成页面、开关或回退承诺；
- 逐章完成 §3 的读者目标，实际对象、层次和关系完整，章节间的责任边界与必要衔接清楚；
- 互补图表未造成内容重复或矛盾，必要事实、源图、验收、契约没有因换形式而丢失。

找到问题要点明内容及阅读影响，不以“没用我喜欢的图/标签”判错。审查任务包只提供当前章节问题和输入，具体判据保持在既有规则真源，不两处重复维护。

## 7. 验收与实施顺序

先改合同与作者职责，再同步草稿/确定性检查和审查任务，最后核直接消费者与相关回归。四处修改作为一个完整步骤评审，不只交付提示词。

| 编号 | 完成条件 | 验证方式 |
|---|---|---|
| A1 | 十章的读者问题、组织提示与必要结构均与 §3 一致，不再用排版偏好强迫内容；必要种子仍在 | 逐章核真实 skeleton/draft 输出及直接消费者，不只检查曾暴露问题的几章，也不能只 grep 删除了某个词 |
| A2 | 等义的叙述、条件表、状态/时序表达不因旧排版要求被机械拒绝 | 用现有结构测试夹具改变形式，事实保持，跑真实 check；只验证 checker 接受合法形式，不证明模型会选对 |
| A3 | 各章按内容关系组织，形式让其核心问题易读、易比较；简单与复杂内容均有合适表达 | 按 §3 逐章检查真实产物；结构夹具覆盖实际变更的形式限制，不要求每章造一套业务场景或出现指定标签 |
| A4 | 必需章、流程图、上游图对应、验收编号与附录投影缺失仍被发现 | 复用已有确定性反例；不得以展示灵活为由批量放行原本的内容缺陷 |
| A5 | 不重复写附录契约；辅助说明经过 project/number/check 后保留在正确作者区 | 现有投影测试覆盖一次完整落盘与重投影；机器区被改仍拒绝或重投影纠正 |
| A6 | 无页面数据管理功能没有页面/截图空槽，结构、规则、数据变化和结果易查；UI 功能仍清楚 | 用户真实内网数据管理产物及已有 UI 真实 CLI 产物评审。前者尚未提供时如实待验，不伪造“已通过” |
| A7 | 全篇内容归属清楚，换形式后独有事实及关系不丢失；必要重现含义一致，没有大段跨章复制 | 既有统稿与独立审查双向核对来源/产物，并检查章间衔接；报告指出具体遗漏、重复或矛盾，不用相似度或字数判质量 |
| A8 | 不增加无必要交互、展示决策文件或模型轮次；没有旧新规则并存 | diff 与任务装配检查；一次本轮真实运行记录观察读取/返修成本，不为理论最优额外起对比实验 |
| A9 | 一级至三级分别遵循展示细则，父子不重复、不丢失，简单内容不强拆三级 | 核真实草稿/产物；已有 H4 编号幂等、章落盘与附录投影测试覆盖父子内容和作者说明保留；不以每章都有三级作为通过条件 |
| A10 | 维护细则未变成第二套运行期模板；必答问题、共用方法和必要结构职责单一 | 核交付依赖与实际生成草稿：无 test/story 引用，无可选目录整套预生成，无按细则逐行新增 slots；相同内容的合理表达可通过，必要信息缺失仍由原定检查发现 |

离线验证按 `test/story/TEST.md`：先相关 story-build、材料/投影和作者上下文测试，完成后本轮要求的全量回归、失效形态及自适配检查；framework 保持无新增修改。真实 CLI 仅由用户启动，本步不自动安排或运行。
