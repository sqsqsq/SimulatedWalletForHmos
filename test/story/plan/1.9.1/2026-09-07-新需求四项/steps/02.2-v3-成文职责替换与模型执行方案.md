## 1. 目标、证据与范围

Story 让首次接触需求的人理解需求、方案、设计、实现边界、规约与验收。模型负责组织信息、判断关系和评价质量；脚本负责已有确定性工作、及时提供输入、可靠保存文稿与检查提交条件。

本步解决四个已观察到的偏差：跨章完整复述；图没有讲全实际交接；重组之后指代或后果描述不一致；独立审查没有发现这些问题。依据是 [真实 CLI 效果评审](../reviews/13-Step2.1真实CLI效果评审.md)、[模型遵循探索](02.2-方案分析·模型在什么条件下遵循.md)、[历史证据探索](02.2-复盘·功能全集与实现方式的历史证据.md)，事实边界见 [评审14](../reviews/14-探索报告审视与Step2.2可靠性建议.md)、[评审15](../reviews/15-功能全集复盘审视与Step2.2调整依据.md) 和 [复核17](../reviews/17-Step2.2-new评审意见复核.md)。

现有证据没有证明上述问题由材料版本变化造成。本步不建设逐章输入版本协议。材料轮次、已成文台账冻结、Framework 审查对象绑定继续由原机制承担；这些机制覆盖时点不同，不声称已经防止所有写作期间的输入变化。

跨章重复仍由作者与独立 verifier 判断。及时提供相关正文、在整稿时给明确比较任务，是待验的行为改进；脚本正确生成指导区不代表重复已解决。真实结果仍失败时，按 §9 定位最早失效点，不增加相似度门禁、不无界累加提示。

保持 Step2.1 的十章职责、自适应表达、三级自然组织、源图对应、验收追溯、附录投影、decisions 真源、人工意见保护及过程文件保留。知识协议归步骤3，审核点发现方法归步骤4，会议输入归步骤5。本步只覆盖 interactive，不改 framework、adapt 和业务知识内容，不新增 Agent、任务状态机或评测平台。

## 3. 唯一正常路径

```text
原材料导入、范围确认与 Spec
  → skeleton：保留/补齐草稿，准备首个待写章的指导区
  → 作者读指导区与来源，在同一草稿写正文
  → chapter --from：清理指导区、局部检查、替换目标章
  → 自动准备下一待写章；全章已写则输出整稿动作
  → 作者读当前完整 Story，比较、推演、修改有关章
  → story 登记：原 project → number → build → check → 登记
  → 原 Harness / 独立 verifier / 回执 → 严格交付检查
```

原有作者编辑工具、chapter --from 和 story 登记接口保持。新的 prepare 仅用于刷新当前草稿指导区或重现整稿要求：

```text
node <extensionRoot>/skills/story/scripts/core/story-build.mjs prepare --feature <名>
node <extensionRoot>/skills/story/scripts/core/story-build.mjs prepare --feature <名> --chapter <合同标题>
```

无 --chapter 时，按当前 Story 的 marker 选择合同顺序中首个待写章；全章完成则输出整稿要求，不写文件。指定章用于跳章首次写作和局部返修：只要下一编辑对象不是刚自动准备的章，先执行 prepare --chapter，再读该章指导区。沿用 --project-root 和已有路径配置；NEXT 给实际参数和正确引用的路径，不让模型拼接文件名。

prepare 不创建 Story、不写流程状态、不渲染 Review、不调用材料转换。缺 Story 时指向 skeleton；缺目标草稿时复用现有补稿逻辑：已成文章从当前 Story 补回，未完成章从种子补回，已有草稿正文绝不覆盖。不得由 prepare 顺带重建所有现有草稿。

--offline 继续只允许只读 check；prepare/skeleton --offline 拒绝。原冻结守卫保持。参数缺值、未知章节及必需输入不可读明确退出1，不因“诊断模式”放宽正式写作路径。

skeleton 在任何 Story/草稿写入前读取并核对本次需要的流程范围、章节合同、作者方法及决策输入；缺流程契约、范围未定或输入损坏时 exit1，已有文件逐字节不变，也不生成新骨架。预检复用指导区准备的同一输入函数，不跑完整成文检查，不要求尚未生成的 Review 或审查报告。读取完成后再建立骨架/补稿和写指导区；实际写盘异常明确报告已完成的写入，保留文件，不做跨文件回滚，也不把部分写入称为成功。测试夹具通过共享 helper 提供最小合法契约，不能为维持旧夹具增加“无契约也成功”的生产分支。

## 4. 草稿是唯一逐章工作载体

### 4.1 指导区、作者区和写入边界

继续使用 draftPath 返回的 `AR/story-src/drafts/NN-<章名>.md`。脚本管理的指导区位于文件最前，其后为作者区，包括原章标题、正文、种子表格和作者已填写的内容。

```markdown
<!-- story-author:begin -->
> 本章工作：……
> 当前范围与决策：……
> 相关已写章：……
> 编辑与提交：……
<!-- story-author:end -->
## <本章标题>

<作者正文>
```

指导区非空内容行统一加 `> `，空行输出单独的 `>`，不引入尾随空格；引用原文的 HTML 标记也加前缀。这样源图、机器投影标记及原文中与外层相同的字样不会被误识别为区边界；前缀仅改变展示包装，不改写原文内容。不把多行正文塞进单行 HTML 注释，不用通用 Markdown 解析器。

在 story-build 内用一份指导区定位函数供“刷新”和“提交剥除”共用：仅认文件起始处的精确 begin/end 行，内容行必须符合包装格式。边界缺失、重复或位置异常时退出1并保留原文件，不能扩大删除范围寻找配对；反馈实际文件与修复位置。

新草稿由 chapterDraft 同时生成一次指导区和原有正文种子；其后 prepare 只替换 begin/end 范围。作者区必须逐字节保持，包括换行、表格、未完成内容；不调用 trimEnd、重新播种或全文格式化来刷新指导区。

实现用原文件 Buffer 定位行边界：以 LF 找行尾，识别标记时容许前一字节为 CR，记录 begin 行首至 end 行结束的字节区间；用 Buffer 切片拼接新指导区和原剩余字节。UTF-8 BOM 若存在留在文件起始。不能 split 后 join 整个文件；新增指导区可统一 LF，作者区原有 LF/CRLF 混合保持。无指导区时，在 BOM 后插入完整新指导区及其末尾换行，其余字节不变。现有边界行若无末尾换行，新增区自行带末尾换行，不把作者区首行吞入替换范围。

无指导区的已有草稿按作者区完整保留，在前面添加指导区；不猜测哪些旧注释属于新头部、不做历史批量迁移。这也覆盖现有按 Story 补回草稿的正常路径，不需要版本兼容分支。

提交先剥除整个指导区，再沿用 stripGuidance 对正文中种子提示的现有处理，再 stripOwnHeading。外层指导区要先消失，才可执行保留机器区标记的旧规则。指导区中的引用章标题、待写 marker、图与规约编号不得进入产物或参与候选正文检查；作者区内原有投影标记仍保留。

### 4.2 作者输入的唯一来源

| 指导区内容 | 来源与责任 |
|---|---|
| 当前问题、章边界、必要形式 | story-chapters.json 的 questions、form.note、subsections 与 slots；把 chapterSection 中“必要结构”的有效提示移入当前章渲染，不只删除它 |
| 简短的跨章写作方法 | story-write.md 中单一的章写作要求块：先比较已有解释与本章独有信息，按关系选形式，补足依据。prepare 读取这一块，不在脚本硬编码另一份 |
| 当前范围 | 从 core/flow-check.mjs 提取并导出只读的 currentScope(flow, featureName)，原 flowProblems 与 story-build 共用范围语义；没有可用范围时失败并回原流程，不在 story-build 复制 split 判定 |
| 当前决策 | decisionList 支持的现有 decisions.json，保留完整条目字段及 settled/open 含义；不得凭关键词猜本章适用条目，也不得把未决项写成已决 |
| 相关已写章 | 由 context_chapters 取当前 Story 中已完成章的完整原文，保留来源标题；未完成章标明尚未成文，不把占位稿当事实 |
| 来源定位 | 复用当前材料清单和 Spec/knowledge-use 的入口；缺必需输入与合法无知识分别处理。阶段任务包继续提供图源和知识，不在每章重复全部源文件 |
| 编辑/提交位置 | 当前草稿绝对路径及真实 chapter 命令。指导区明确作者只编辑下方正文 |

章写作方法块与 §6 整稿动作块各在 story-write.md 用固定起止标记定位：`<!-- story-method:chapter:begin -->` / `<!-- story-method:chapter:end -->` 和 `<!-- story-method:whole:begin -->` / `<!-- story-method:whole:end -->`。块内容是人可读说明，无 schema，无状态。脚本仅取两处已知块，缺失或重复明确报错，不新增模板引擎。阶段任务包不再全文渲染十章 questions/form，但保留“进入成文后读当前草稿指导区”的入口说明。

currentScope 返回 `{scope, problems}`，不读写文件、不启动 Python。复用当前轮 accepted 的 scope_decision、split.settled_round 和 parts/carrier 校验：整体承载取末轮 positioning.scope_text；本轮拆分定案取 split.scope_text 并提供已有 parts/兄弟关系，存在 parts 时核本 feature 恰好一份。过期拆分、缺范围、关卡与拆分矛盾返回问题，不能退回旧轮或整个上游范围。flowProblems 保留其它流程检查并消费同份范围问题；调用方只负责文件读取和现有状态/冻结守卫。该提取是 N1 的直接改动，不能另在 story-build 增加第二套范围解释。

context_chapters 写在原章节合同，引用现有章 ID；脚本不复制关系表：

| 当前章 | 默认关联章 |
|---|---|
| 背景 | 无 |
| 术语 | 背景 |
| 范围 | 背景 |
| 业务方案 | 背景、范围 |
| 业务流程 | 范围、业务方案 |
| 功能说明 | 业务方案、业务流程 |
| 异常与恢复 | 业务流程、功能说明 |
| 验收 | 范围、业务流程、功能说明、异常与恢复 |
| 交付与上线 | 范围、业务方案、异常与恢复 |
| 附录 | 无；使用现有投影来源和材料清单 |

关联不是排他范围，作者可依据本需求补读其它章。优先提供原文，不能由脚本摘要或按关键词切掉关系。指导区过长时告知实际范围并用现有读取工具分页，不静默截断。字节成本按 §10 测量，不能把文本从任务文件搬到草稿就算运行成本下降。

### 4.3 准备时点与更新

skeleton 保留现有 Story/草稿的恢复能力，成功后调用同一准备函数；chapter 提交成功后也调用它。首次写作自然得到下一章；修订已完成章后，仍有待写章则回待写章，否则输出整稿动作。

只刷新当前目标章，不在每次提交后批量重写全部待写章。跳章时通过 prepare --chapter 刷新目标后读取；该动作同时写入章方法块和首次/恢复提示。未刷新章的指导区是其上次准备时的输入，不宣称始终最新。批量刷新也不能覆盖来源被直接修改或已完成章的返修，因此不以它代替明确的编辑入口，更不追加逐章版本门禁。

作者更新 decisions、相关章或上游依据后，在继续依赖它们写作前调用 prepare 刷新目标指导区；草稿正文保持，真实新决策不因刷新成本被省略。输入变化不触发任务失效门、不要求重复提交所有已写章。来源本身变化仍走既有材料/范围流程，不由 prepare 重新确认或接受。

指导区只是准备时的可读输入，不是读取证明或完成凭证。chapter 不要求指导区存在，不以它的存在判作者读过；删除指导区不能跳过正文检查。执行中被模型忽略、直接编辑旧稿等语义风险由整稿、独立审查和真实行为验收评价，不宣传为程序强制保证。

## 5. 局部检查在写入之前完成

### 5.1 共用职责

提取 `chapterProblems(ctx, chapter, candidateBody)`，返回问题数组，既不写文件也不退出进程。cmdChapter 与 cmdCheck 共用它及原合同，不另建规则数组或第二套配置。

| 检查 | 单章提交 | 最终检查 |
|---|---|---|
| 空章、现有待填占位 | 对剥除指导区后的候选查 | 每章调用同份函数 |
| 必需小节、表头锚列、流程图 | 沿用 form/slots/slotCondition，查本章；不增表数量和段数要求 | 同份函数 |
| 工作编号 id_shapes.drop | 对排除 Mermaid 围栏的候选文本查 | 同份规则；验收编号集合仍在全篇核 |
| 已有 Markdown 围栏及图片引用 | 查本章可确定的闭合、路径；不提前要求最终图序或跨章锚 | 保留原全篇图序、源图对应及引用检查 |
| 决策字段、规约投影、Spec契约行、源图/验收集合、全局语言与来源检查 | 不搬进本章结构函数；附录先在内存投影，再核候选结构 | 保留原全篇职责 |
| 章顺序、文档总标题、冻结、交付 | 复用章锚与冻结守卫 | 原检查保持 |

局部错误一次列全并指向候选草稿。其它未写章不报缺失；脚本不替作者补业务内容、不按人数或相似度判语义。相同候选在两个入口的局部结果应一致，不以某种代码结构代替行为验证。

### 5.2 写入与失败语义

固定顺序：冻结守卫 → 读目标章与候选 → 剥指导区和种子注释 → 处理本章标题 → 附录条件投影 → chapterProblems → 一次替换目标章 → 准备后继。

候选或指导区格式错误时 exit1，旧 Story 与候选文件不变。通过才写 Story，其余章原文保持。这里只承诺检查后替换，不新增跨文件事务或断电恢复协议。

本章写入后，后继准备失败：本章仍是提交成功，exit0；stderr 报后继错误，末行 NEXT 给 prepare 的实际参数。不能回滚本章或诱导重新生成它。未提交即失败为 exit1。输出始终区分“已写入”和“准备失败”，不能统称流程完成。

### 5.3 两项机械误判回原责任点修

id_shapes.drop 跳过 Mermaid 围栏，避免内部节点名冒充业务工作编号；不新增 Mermaid 语义解析器。正文工作编号、验收 ID 与源图对应保护保留。

“回滚”类词命中只能反映用词事实。沿用现有语境处理，明确的数据/状态恢复不拦；不能可靠确定为客户端发布误用时作为定位提示交语义审查，不以简单词命中要求删掉正确业务承诺。不加本案例原句豁免或更大的语义正则。

## 6. 整稿要求当场送达，恢复时可重现

### 6.1 唯一整稿要求

story-write.md 原七项统稿与重复交回自检归并为下列三个动作，保留独立可读、依据、事实完整和展示质量的目标。三项正文只维护在该文件的整稿要求块，脚本读取后输出，不各写一份。

1. **比较信息归属**：通读当前 Story，对同一事项多处叙述比较独有信息。完整复述合并到主要落点；图讲关系、表讲属性、文字讲理由，以及验收重现条件属于互补，保留且含义一致。正文独立可读，不将必要业务含义移到附录。
2. **推演关系与结果**：从需求范围与依据出发，逐条推演关键流程的触发、参与方交接、分支、异常和终态；核对图、功能说明、异常、验收所述条件与结果。既有能力须有工程依据，新增能力须有需求/设计依据；已决与未决不能混用。
3. **核重组后的表达**：检查指代、单位、因果、可逆后果、表图承接和可查找性。按信息关系用合适形式，不能靠改词或删事实过门禁；没有问题可以不改，不强制制造修改记录。

脚本同时输出当前 Story 路径、所有章草稿路径及合同中的章节职责/关联定位；不再次内联完整 Story 或生成 whole 文件。模型用原读取工具读取当前完整稿，必要时分页。输出要求先读再比较，不能仅指向规则页等模型自行回忆。

### 6.2 正常进入与恢复

最后一章提交成功、全章完成后再次执行 skeleton、无指定章的 prepare，均调用同一个整稿输出函数。未冻结且全部成文时，用户说“继续”由 status 指向 prepare，再输出同样三项动作。status 本身保持只读，不修改指导区，不在 Python 复制整稿文案。

返修某章先 prepare --chapter，再编辑该草稿并 chapter 提交；返回整稿后读取最新 Story。指导区和 stdout 无完成状态，不新增“统稿已做”字段；模型的比较与修订由实际稿件和独立审查评价。

### 6.3 登记与冻结

在 core/story-build.mjs 删除 COPYEDIT_ROWS、copyeditPath 的强制消费者、七行检查和 STORY_SRC_LEDGERS 中的 copyedit；在 core/story_flow.py 的 STORY_SRC_FROZEN 删除 copyedit，并同步相关提示。历史 copyedit 文件保留，不清理过程证据。decisions 的存在、形态、冻结与人工意见保护保持。

`story_flow.py story --feature <名>` 接口不变，仍要求原流程 complete；project → number → build → check 全部通过才登记 story_written。全篇 check 仍核所有章已完成及原完整性条件。失败不登记，保留已完成的确定性投影供幂等重试；不增加整稿票据或登记预检查子命令。

verifier 阻断后的返修沿用已有 reopen 规则撤销成文登记，再刷新对应草稿、修正文、登记和复审。已归档/送审后的保护边界保持；不能为了改稿绕过原人工反馈保护。

## 7. 独立审查和交付

readerReviewTask 在现有 pre_verifier 单个读者审查 fragment 中提供当前完整 Story，附来源路径；story-build review-task 调用同一函数。Framework 的 Spec 输入保持，不能在两个 hook 再各内联一遍 Story。任务装配缺 Story 时明确缺件，不用空串冒充无内容；宿主截断或未读完必须报告缺口，不能直接 PASS。

语义判据仍由 overlay 维护：从已确认范围及来源判断覆盖、交接关系、跨章独有信息与事实依据。作者指导给当前工作输入，不复制一份通用审核规则。审查不要接受“都讲过”等作者自评作为结论，不以图种或表行数代替实际角色和分支完整性。

取消 reader-review-task 中“PASS 到此为止，不写明细”的限制。报告保留当前汇总与 blocking_findings/advisories，可附必要的简短位置与比较依据，不设条数、引文字数或逐事实裁决表。关键遗漏、矛盾或影响判断的重复阻断；纯措辞偏好给建议，不批量调整所有严重度。

storyReviewProblems 的现有 status 是格式检查结果，保留其含义；增加 `reviewVerdict` 表示汇总行实际 story_reader_review 结论，沿原格式清理方式转大写，取不到为 null，各返回分支一致提供。不从 detail 文本倒推，也不重写其它报告协议。

正式交付同时要求：现有 check-receipt 通过、报告结构 status=PASS、reviewVerdict=PASS。缺报告、缺判项、非 PASS 或结构错误均不能正式交付。**本宿主未登记审查员时记一笔放行**——那是如实披露的状态，不是缺件，闭环不因此卡住（用户 2026-09-09 批准保持现状）。普通诊断允许审查尚未产生。adapter 声明能力不证明本次已审；Framework 的其它降级政策不改，也不悄悄增派 Agent。

story_flow.py 的 spec_stage_step 更新成文/恢复提示：进入草稿链，恢复用 prepare，不再笼统把 Story 文件存在当作“十章已经完成”。next_step 的 story_written 分支删除“没有审查员就直接下一步”的放行提示，按当前策略报告审查未完成；保持原阶段状态及人类归档/后续选择。

### 9.2 真实模型行为

用户启动真实 CLI 时，复用原 events、runlog、草稿、Story 与 verifier 报告观察；不向执行者提供维护答案或脚本源码。必须分别取得 UI 与无页面功能的实际证据才能声称覆盖两类，未取得保持待验。

- 首稿：读当前指导区后，本章是否补充独有信息；数据、交互、异常是否选择适合关系的形式；不是只统计图表数量。
- 整稿：实际重复、遗漏、指代和后果错误是否消失，必要事实是否完整；不要求必须产生修改或留下自评清单。
- 审查：人在真实稿件发现的关键缺陷是否被指出，报告依据是否与最终稿相符；不把报告格式通过当语义通过。
- 恢复：中断后从磁盘继续，能重新取得整稿动作或刷新目标指导区，不需要人复述全部上下文。
- 成本：分别记录首次写作、确定性返修、语义返修与人工等待；重点查看本轮指导区最大的三章，不能把章难度差异直接归因于字节。

失败先区分输入没送达、送达但未执行、语义判断错误、上游矛盾、机械误判、宿主能力缺失。没有代理读取轨迹时如实标未知；不以 run_id 变化认定上下文已清空。输入正确而同一配置仍反复漏报时，报告能力边界并讨论人工复核或可用配置，不自动换模型、加 Agent 或无界堆提示。

### 9.3 完成前过拟合自查（必做）

维护者检查本步涉及的提示词、脚本、全部注释、合同数据、示例和错误/NEXT 文案，以及它们实际生成的草稿指导区、整稿输出与 verifier 输入。不能只查新加行或只扫业务专名；复用、移动的旧内容也要检查。该自查留在维护与验收域，不向业务执行模型追加自证清单。

| 自查项 | 可检查的判据 |
|---|---|
| 测试与历史内容泄漏 | 机制中没有案例单号、测试业务名、suite/run 标识、历史批次、某次运行数字、模型名或复盘叙述；注释说明当前职责，不教执行者照某次失败答案写 |
| 特殊业务混入通用机制 | 分支、正则、默认值、示例、提示与合同不依赖本 demo 的模块/API/状态/金额或某个业务的参与方；业务事实来自需求、工程或 knowledge，不硬编码到 extension |
| 对已知样本的隐性适配 | 不因某次稿件的章标题、句式、表行数、图节点名或原句增豁免；错误检查有可说明的结构依据，不能拿字符串、数量或相似度代替语义判断 |
| 表达方式被样本锁死 | 换成无页面、数据处理、多方交接等不同关系时，仍能按真实内容选表达；不强制所有功能套同一页面/流程/恢复模板。固定章节合同与必要结构须能追溯到已确认要求 |
| 生成内容的来源边界 | 指导区引用当前需求中的业务名和数值属于正常输入；逐项确认来自真实来源而非机制模板。不能为通过扫描把业务事实从生成结果删掉 |
| 验证是否只证明已知答案 | 已有夹具用于结构与失败路径，断言对准合同，不锁定某个案例的完整措辞；未知场景的模型效果没有真实证据时标待验，不以一次已知案例全绿声称泛化 |

复用 TEST.md 规定的失效形态检查（含 M02）和针对性文本搜索，命中项逐处读上下文；扫描零命中不等于语义自查通过。不新增业务词黑名单、通用评分器或为自查另跑真实 CLI。

随实施反馈交回检查范围、实际执行的扫描、命中位置及处置、对业务独立性的判断依据和未验证边界。发现过拟合时回原职责修正，复核直接消费者；仅改名、藏进注释或加用例豁免不算解决。最终合并检查无未处理的过拟合问题，才满足本项完成条件。
