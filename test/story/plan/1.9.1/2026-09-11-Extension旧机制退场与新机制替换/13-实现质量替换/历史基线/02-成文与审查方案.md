## 1. 目标与证据

Story 让首次接触需求的人读懂需求、方案、行为、约束与交付。模型负责组织信息、判断关系、评价质量；脚本负责落盘、编号、投影、来源送达、冻结与提交条件。

本方案针对六种已观察到的偏差（2026-09-08 `story-suite-20260908-2115` 一跑），它们也是第三段正常CLI的评价维度：

| # | 偏差 | 当时的现象 |
|---|---|---|
| P1 | 跨章完整复述 | 4.3 / 5.1 / 6.3 三章各讲一遍同一过程 |
| P2 | 图没讲全交接 | 来源标记修好了，五方交互仍未展开 |
| P3 | 重组后语义错 | 「最后两种」错指；可恢复的入口关闭被写成不可逆 |
| P4 | 统稿合理化重复 | copyedit 称「各章必要落点、无冗余」，依据是措辞不同 |
| P5 | 审查漏报 | verifier PASS，声称参与方次序与分支完好 |
| P6 | 返修集中在机械问题 | 编号、引用、禁用词、图源标记 |

2.1 之前另有一类：形式先于内容（无页面功能套页面状态表、流程压成三标签、回退只能一套开关表、附录表后不许有说明）。它由取消固定形态解决（03的C02/C08），既核确定性实现，也在第三段正常CLI中核作者是否正确选择形式，不能只凭取消字段宣称效果达成。

## 2. 唯一正常路径

```text
S1–S4（story_flow.py：材料轮次 → 分析 → 三级关卡人签 → S4候选提交complete，C00修复输入/输出边界）
  → spec 阶段：knowledge-use init → 逐条判断 → 写 spec.md（§10/§11 由投影）
  → story-build skeleton：十章骨架进 story.md（章标题 + 待写标记），每章一份草稿
        drafts/NN-<章名>.md，草稿头是本章读者问题与内容边界（HTML 注释，提交时剥除）
  → 作者动笔前：读全部材料、spec、decisions，形成整篇理解，把各章拟分的小节标题
        直接写进各章草稿（不另落规划文件）
  → 逐章：读本章草稿头 + 已写章（story.md 就在盘上）→ 写正文 → story-build chapter --from <草稿>
        （局部检查 → 单次替换目标章 → 首屏NEXT/INPUT/RESULT：下一章或整稿动作）
  → 写后核对：三个动作（§4.4），改哪章就在它的草稿上改再 chapter 提交
  → story_flow.py story：project → number → build → check 全过才登记 story_written
  → harness → verifier（overlay story_reader_review，拿 Story 全文）→ 回执
  → story-build check --deliver：回执 + 报告结构 + reviewVerdict=PASS → 停下问一次：归档送审 / 进 plan
```

成文侧的主要变化是：草稿头的内容（C01）、`chapter` 的局部检查与 NEXT（C03）、审查拿全文与交付核 reviewVerdict（§6）。其它变化按下文C00–C09闭合，新增与删除都计入终态；不能再按“唯一新增5行”估算。**没有** `prepare`、指导区刷新、`context_chapters`、copyedit 留痕、任务文件、版本协议、tasks 目录。

阶段内「做到哪了」只由 `story_flow.py status` 的 `next_step` 回答（基线的 `spec_stage_step`，按知识判断、Spec、Story及待写章定位），不在 `story-build` 另设查询。

## 3. 十章设计

每章四栏：读者问题进合同 `chapters[].questions`；内容边界进合同新增的一句 `chapters[].boundary`；组织与形式、三级何时出现进 `story-write.md` 的「十章各自怎么组织」一节（每章 4–6 行）。三级细则原表（`02.1-Story三级章节展示细则.md`）留在维护侧作参考，不进交付面。

通用规则先于逐章：

- **形式按主要关系选**：属性/对照/条件组合用表；先后与分支用流程图；状态变化用状态图；跨方调用与返回用时序或泳道；对象归属引用用关系图；原因与取舍用叙述。简单内容短写，复杂内容分层；图讲关系、表讲属性、文字讲理由是互补。
- **不以数量代替判断**：不用表格数、图数、段数、字数、参与方数、状态数决定形式或合格；不设填量目标。
- **三级只在下级内容值得独立定位时出现**：不同对象有不同规则、某局部过程要展开、多个决定各有完整依据。一行表或一段能讲完的对象放在二级下。父级给共同背景或总览，子级只展开差异，父级已列完整明细表就不逐行再建子节。
- **章标题为固定十个H2；H3/H4按业务关系取名，08 §3列出的必要H3锚保留**；编号由 `number` 生成，作者不写编号。

| 章 | 读者问题（`questions`） | 内容边界（`boundary`） | 组织与形式；三级何时出现 |
|---|---|---|---|
| 1 背景 | 现在这件事怎么做，哪里出了问题；问题影响谁，对业务意味着什么；本需求要改变什么，达到什么算成功；本特性在完整需求里承担哪一段 | 讲动机与目标；分工归范围，机制归业务方案，可执行的通过条件归验收 | 因果叙述为默认；多个现状或可比较的目标成「场景/现状/问题/影响」或「现状/目标/口径/依据」表；未知值写未知。简单时不分节。三级只在某问题场景或某目标的口径要独立解释时出现 |
| 2 术语 | 本需求出现的业务与技术术语各是什么意思；实际会被读混的概念，差别与判别条件在哪 | 解释概念；不承担功能规则、完整字段契约、方案介绍；后文沿用同名同义 | 词义表为默认，沿用术语种子；真有易混概念才做「概念/差别/判别条件」对照；真有层次或包含关系才配小图。三级只在一组概念需要独立解释时出现 |
| 3 范围 | 整个需求不做什么；本部件不负责但其他部件仍需完成什么；哪些依赖阻塞本部件，哪些独立排期；本 AR 承载哪部分、兄弟 AR 各承载什么、边界在哪、有无先后依赖 | 讲责任与交付边界；运行时怎样协作归方案与流程，能力细节归功能说明，交付时点归上线 | 责任边界为主线；多对象用「能力/本特性责任/其他责任方/边界」矩阵；依赖用「能力/提供方/使用边界/是否阻塞」表；真有兄弟单才写交接约定。先区分「完整需求不做」与「本特性不负责但别人要做」 |
| 4 业务方案 | 全部参与系统及各自输入、输出、责任与失败影响；业务结果以谁为准、重要业务规则是什么；每个关键取舍选了什么、否了什么、为什么，被否方案的具体缺陷；全篇风险的触发条件、影响、已有控制 | 讲整体机制与为什么这样选；流程展开执行过程，功能说明展开局部规则；风险只在这一章成表 | 参与方「输入/输出/责任/失败影响」表为默认，关系复杂配协作或数据流图；条件组合用决策表；真有备选才做「选项/收益/代价/理由」对照，只有一条路就写依据，不为显得有取舍编备选 |
| 5 业务流程 | 从触发到终态的完整过程与主要阶段；主路径及全部分支去向（开关、登录态、风控、网络、回调等）与交接点；关键状态变化与终态 | 讲能力之间的顺序、条件与连接；能力内部规则归功能说明，详细恢复归异常；异常在总览有去向 | 章前部提供覆盖主路径与全部分支去向的总览图，可置于独立总览小节；不按第一个H3位置机械判定；多方调用用时序或泳道，并行用流程图标同步点，状态用状态图；每条分支讲清触发、处理、结果、后续，不套三标签；局部复杂时在它的节里展开并说清接在总览哪一步 |

| 8 验收 | 完整需求怎样才算完成；每条原始验收编号的场景、可观察通过条件与主责；质量指标是什么，来源是上游约束还是工程设定 | 验证已定义的行为，不重新定义规则；必要地重现关键数值与条件以便独立验收，与正文一致 | 按真实验收目标分组；「编号/场景与前置/可观察通过条件/主责」表保留，编号一条不并；复杂输入组合补参数矩阵或预期样例；质量指标写条件、单位、来源，没有真实测量不画结果图 |

## 4. 作者怎么工作（`story-write.md` 的目标结构）

重写后的 `story-write.md` 只保留下面六节，以完整覆盖本节为准，200行只作起草参照、不代替完成条件；每一句都是方法或事实，不给数字门槛，不重复合同里已有的问题。

### 4.1 写给这样的读者（十条之内）

保留基线里仍成立的读者原则：首次接触者、看得懂业务不看代码、精确契约与业务含义分开放、归档件自包含、叙述不落附录、未定判断只作边界、真实观察者、图片单向。删掉「百字上下」「1–3 项」「三个以上」「绝对只讲一次」一类数字与禁令。

### 4.2 动笔前：先有整篇理解

读全部材料（materials.json 列的每一份）、spec、decisions、本阶段任务包（图、知识、词表、验收落点）。用一句话说清这条业务从触发到终态怎么走、有哪些参与方、哪些是本轮新建；把各章拟分的小节标题直接写进各章草稿的正文区。**不另落规划文件**，不先写十份摘要再各写一遍正文。

### 4.3 写一章

1. 读本章草稿头（读者问题、内容边界）与当前 `story.md` 里已写的章，先回答「这一章相对已写内容要增加什么」；同一事项已在别章讲透的，这里只交代它与本章问题的关系。
2. 按 §3 的通用规则与本章那行选形式；表的条件、单位、例外，图的分支与终态，重组后都要有去向。
3. 图从要解释的过程出发：讲全实际交接、关键状态与全部分支去向；上游画过的图逐张有对应，可等效合并或改画，围栏首行保留来源标记；材料里属于本需求的图在讲它的那一节引用，不属于的登记不用。
4. 决策登记：真实的业务未决当场登记进 `decisions.json`（什么算一条议题、澄清正文怎么写，本节保留基线的定义，不另写）。
5. 写完 `story-build chapter --from <草稿>`；报错照它给的位置改；成功后按 NEXT 走。

### 4.4 写后核对（十章齐了做一次）

三个动作，改哪章在它的草稿上改再提交：

1. **比较信息归属**：通读当前 Story，对同一事项的多处叙述比较独有信息；完整复述合并到主要落点；图讲关系、表讲属性、文字讲理由与验收重现条件是互补，保留且含义一致。
2. **推演关系与结果**：从范围与依据出发逐条推演关键流程的触发、交接、分支、异常、终态；核对图、功能说明、异常、验收所述条件与结果一致；既有能力有工程依据，新建能力有需求或设计依据；已决与未决不混用。
3. **核重组后的表达**：指代、单位、因果、可逆后果、表图承接、可查找性；不靠改词或删事实过门禁；没有问题可以不改，不制造修改记录。

### 4.5 十章各自怎么组织

§3 表的第四栏，每章 4–6 行。

### 4.6 归档件自包含与交回前

保留基线四条红线（仓内路径、悬空引用、断链、工程标识只在附录）的**作者面说明**；确定性作用域与交付检查按08实施，语言/路径保护不再交给已取消的实验裁决。交回前只做一件事：跑 `story_flow.py story`，按它的输出走，不写自评。

不预铺可选业务表图；沿用现有slots的必要表/图和siblings条件子集，不另建结构协议。chapterSeed提供术语、验收/交付最小起始表头，作者按业务补内容；不把默认列数作为合格门。附录现行投影保留，准确字段及H3清单见08 §3。

### C03 章提交与接续

在现有story-build.mjs提取`chapterProblems(ctx,ch,body)`，供cmdChapter与cmdCheck共用：非空/非占位、必要结构、工作编号、围栏闭合，及本章可确定的断链；准确局部/全篇边界见08 §4.1。全篇顺序、源编号全集、投影/冻结、图源对应等仍在全篇check。保持离线只能验证文档自身的边界。

cmdChapter先剥固定自有头注，再剥开头自己的章标题，投影附录候选后再核候选，通过才替换目标章。其它章字节不动。成功后给NEXT/INPUT：下一待写章草稿路径与已写章列表，或当前Story/drafts与写后核对入口；不在尾部重抄整套方法，不新增prepare。

`stripGuidance`只能移除自身定义的头部说明及必要种子提示，不能为保证“逐字节”一概归一全文空白；正文保留与原实现差异须明确测试。Python spec_stage_step保留，明确先取作者要求再写，缺知识判断/Spec/章稿各给正确动作，删纯重复解释不删状态职责。

### C04 写后核对替换copyedit

先按第4节将作者动作与最终NEXT接好，再删除COPYEDIT_ROWS、⑫d、STORY_SRC_LEDGERS/STORY_SRC_FROZEN中copyedit及所有要求七行留痕的指令。保留decisions冻结、实际正文核对、独立verifier和局部返修。

测试改为“没有copyedit也能完成合法登记”和“真的缺正文/决定/审查仍失败”，不能只测旧词零命中。不再要求作者证明自己读过或必须找到几个错误。

### C05 生成与只读保护归一

附录⑦/⑫b旧行核对可以退，但必须先复用当前投影计算形成只读机器区比较。单独check/check --deliver在未先project时仍能发现少行、改非首列、错行和真源变更；作者解释区不参与机器区相等比较。project不变为check，check不写文件。紧接生成后相等不是这条校验的区分力；生成器正确性用独立期望测试。

Review字段核可归review-render的一个共享校验入口，渲染前及只读check共同使用；人工区逐字节保留。H1身份、冻结、生成区保护仍要覆盖生成之后的变化，不能以“只有手改才红”作为删除理由。

### C06 图与引用

图片按内容身份只给一项任务，paths多值是别名。删除未登记AR/assets副本的特殊放行与专属story_image_dir字段；已登记assets仍合法，不删除任何用户图文件。

保留图片登记/采用排除、断链、上游Mermaid对应；它们不是同一职责的五代。按内容可以合图/改画但对应仍可追溯。清单的原件定位、贡献与合法链接保留，取消一段散文配额，倾倒与重复由语义审查按实际效果判断。

### C07 审查对象与真实交付

readerReviewTask内联当前Story全文一次，并给materials/原AR origin/Spec/decisions位置及合同读者目标；不包含不存在的2.3编排。方法与结果分级统一在overlay，任务书只给本次对象与必要读法。读不到全文不得用空串冒充已送达。

storyReviewProblems返回结构status与实际reviewVerdict；取不到结论为null，不能把格式正确的FAIL当PASS。交付按Framework回执、报告结构及真实结论判断；未登记审查能力按已批准政策披露放行，但不能用于声称语义效果已验收。

### C08 全作者面接替

按第3节十章目标、第4节六部分方法和第6节审查完整改写，不能只删到200行就算完成。稿头给本章问题与边界，作业书给方法，任务包给当前材料与操作数据，失败消息给具体位置/修法；这些分工允许必要短文字，不以“脚本里出现作者能读的字”作为废弃标准。

SKILL启动止于spec交付门，归档/Plan由后续用户选择；材料/范围确认保留。失败按真实障碍处置，不要求固定撞三次才报告。同步spec阶段说明、各作者页、帮助、错误与所有直接消费者；既有人工反馈与冻结边界不变。

### C09 本段收口

完成下面的功能与行为检查后进行G2。目录B后续三项仍不在本段。若功能未达或规模增长缺少合理依据，报告具体失败，不把未完成项移到新轮再称本段完成。

## 6. 独立审查的唯一定义

1. 先看有效来源与已确认范围，确认要保留的业务结论与关系，再看实际Story及跨章互补。不给来源打逐条勾，也不拿作者摘要当答案。
2. 合同questions是稳定读者目标，不是写齐条目即可PASS。检查每个最小章节的独有用途与完整事实。
3. blocking_findings指出事实缺失/无依据承诺/矛盾/范围错/验收不可判等；advisories为不影响正确完整的表达建议。每条有位置、问题和影响。
4. 图表文字按关系评价；表数、段数、参与方数不是质量代理。必要重现不当重复，复制整段也不能以措辞不同合理化。
5. 截断或无法读取须披露；报告结构与实际结论分开。PASS也可有简短证据，不设引文字数或发现条数。
6. 范围、数据寿命、控制对象、存量/在途影响、不可逆后果及恢复条件均回到来源和目标核，不因某章没列在模板里就忽略。
