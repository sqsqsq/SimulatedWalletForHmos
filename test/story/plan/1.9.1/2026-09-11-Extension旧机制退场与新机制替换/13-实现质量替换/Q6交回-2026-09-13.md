## 1. 附录：一份计算，两个消费者

`appendixProjection` 是 A–D 机器内容的**唯一计算**。`project` 据它写入；check 据**同一个函数**
与盘上机器区逐区比——新增 `appendixZoneProblems(ctx, storyText)`：

| 报什么 | 怎么判 |
|---|---|
| 缺机器区 | 合同要这一节、投影有行、盘上没有区 → 点名该跑 `project`，并说明旁边的目的句归作者 |
| 多出机器区 | 真源那一节已经没有内容而区还在 → 上一版冒充现状 |
| 重复机器区 | 同名两段 → 投影只认第一段，第二段会一直挂着 |
| 坏标记 | 有起始没结束 → 整段认不出来，连首尾删掉再投 |
| 少行 / 多行 / 行序 / 非首列变化 / 真源变化 | 逐行逐格比，报第一处差异的行号、盘上是什么、真源投出来是什么 |
| 必需真源读不出 | spec 读不到、或 `knowledge-use.yaml` 读不出而激活清单非空 → **不当成期望为空** |

- 输出保留行序、全部单元格与重复行；比较**只归一行尾空白**（编辑器顺手删一个行尾空格不是改动）。
  不用 `Set`、不只比首列。
- **作者解释区在机器标记之外**：不参加比较，也不被生成器重写。
- 这一步**只读**：算的是纯函数 `appendixProjection`，不调会写盘的 `cmdProject`；
  一节的投影在一次运行里只算一次，没有持久缓存。
- `project` 的手改保护、合法真源变化的刷新协议原样不动。
- **离线仲裁锚这一条不判**：那时没有 spec 与激活清单，拿空真源去比会报「盘上多了一整段机器区」——
  判据拦住理想产物时，错的是判据。形态那几条（⑫）照跑。
