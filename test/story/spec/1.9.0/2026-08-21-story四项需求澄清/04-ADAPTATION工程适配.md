# Story Extension 适配与升级

> 状态：已冻结  
> 需求来源：[全量原始需求记录 §4](../../../plan/1.9.0/2026-08-21-story全量需求与踩坑记录/00-全量原始需求记录.md#4-adaptation-面向-ai-的工程适配能力)及本轮用户补充

## 目标

为 Story 新增一个面向目标工程的命令入口。该入口先检查目标工程是否具备 Framework 与 Story
Extension，再根据目标工程的集成状态进入首次适配或版本升级，完成文件同步、工程扫描、适配方案确认和
目标工程修改。

## 已确认需求

### C1：新增 Story 适配命令入口

- 新增命令 `/story adapt [<目标工程>]`。
- 目标工程参数缺省时使用当前工程自身。
- 命令入口只负责路由，实际流程跳转到独立的适配 Skill。

### C2：先检查目标工程是否集成 Framework

- 适配或升级开始前先检查目标工程是否已经集成 Framework。
- 未集成 Framework 时立即中断 Story Extension 适配或升级，提示用户先完成 Framework 集成。
- Story Extension 适配流程不代替 Framework 集成。

### C3：根据 Story Extension 集成状态选择适配或升级

- 检查目标工程是否已经集成 Extension 与 Story。
- 未集成时进入首次适配。
- 已集成时比较目标工程的已安装版本与当前发布版本：版本较旧时进入升级，版本相同时进入重新适配。

### C4：首次适配

- 向目标工程全量复制 Story 跳板和 Extension 的全部内容。
- 扫描目标工程中与适配项有关的真实源码、目录、配置、依赖、Skill、SDK、工具链和既有业务案例。
- 根据扫描结果形成目标工程的适配方案。
- 适配方案必须先交给用户确认；未确认前不修改需要适配的目标工程文件。
- 用户确认后，在目标工程中修改相关文件，形成属于目标工程的正式适配内容。

### C5：版本升级

- Story 与 Extension 建立明确版本号。
- 升级时区分两类内容：目标工程的适配内容，以及由 Story Extension 版本直接维护的内容。
- 适配内容必须保留，并根据来源版本和目标版本重新扫描目标工程，形成需要调整的适配方案；用户确认后
  才更新这些内容。
- Story Extension 直接维护的内容按新版本执行新增、删除和更新，不继续保留旧版本副本。
- 升级流程必须能够识别来源版本、目标版本和两者之间的文件变化。

### C6：版本基线

- 已经归档并在真实项目完成集成的 Story 与 Extension 视为 `1.0` 版本。
- 本轮优化后的 Story 与 Extension 版本定义为 `2.0`。

### C7：Story 跳板与 Extension 共用一个发布版本

- Story 跳板与 Extension 的全部内容作为一个安装、适配和升级单元，共用一个版本号。
- 目标工程只记录一个当前 Story Extension 版本，不维护跳板与 Extension 的版本组合。
- 版本号的唯一真源位于 Extension Manifest；跳板随该版本统一新增、删除和更新。

### C8：版本显式声明直接维护内容和适配内容

- 每个 Story Extension 版本提供明确的升级清单，将交付内容分为直接维护内容和适配内容。
- 直接维护内容归 Story Extension 版本所有，升级时按目标版本清单执行新增、删除和更新。
- 适配内容归目标工程所有，首次复制并适配后保留目标工程结果；升级时重新扫描目标工程，形成适配方案，
  经用户确认后更新。
- 目标工程保存当前安装版本及该版本的升级清单，供后续版本升级使用。
- 内容归属只以版本清单为准，不能根据文件是否修改、文件名关键词或目录扫描结果推断。

### C9：相同版本执行重新适配

- 目标工程已安装当前相同版本时，`/story adapt` 进入重新适配，不直接退出，也不重复执行版本升级。
- 直接维护内容不重复复制或替换，只重新扫描版本清单声明的适配范围。
- 扫描发现变化时生成新的适配方案并等待用户确认；确认后才更新适配内容。
- 没有变化时明确报告当前适配仍然有效，不修改文件。

### C10：升级先形成完整方案，再统一执行

- 升级前先读取来源版本、目标版本和两版升级清单，计算直接维护内容的新增、删除和更新。
- 保留现有适配内容并重新扫描目标工程，形成需要重新调整的适配方案。
- 执行前向用户展示完整版本变化、直接维护内容变化、保留的适配内容以及需要调整的适配内容和依据。
- 直接维护内容不需要逐项选择是否升级，但用户在执行前必须能看到完整变化。
- 用户确认后统一执行直接维护内容变化和适配内容调整；执行失败时恢复升级前状态，不能留下半升级工程。

### C11：首次适配在确认后一次性写入目标工程

- 首次适配先在临时目录准备 Story 跳板和 Extension 的完整目标版本副本，不立即写入目标工程。
- 扫描目标工程，并基于临时副本形成完整适配方案。
- 用户确认后，一次性把完整副本和适配结果写入目标工程。
- 写入失败时目标工程保持适配前状态，不能留下只复制一部分或尚未适配的 Extension。

### C12：通过归档版发布清单识别既有 1.0 安装

- 根据已归档并完成真实项目集成的内容补建 `1.0` 发布清单，记录直接维护内容、适配内容和文件指纹。
- 目标工程没有新版本元数据时，对照 `1.0` 发布清单识别：直接维护内容须能对应归档版，适配内容允许存在
  目标工程差异，Story 跳板与 Extension 入口须完整。
- 能对应时将目标工程认定为 `1.0`，先补写安装记录，再执行 `1.0 → 2.0` 升级。
- 无法对应时不能直接假定为 `1.0`，必须列出差异并让用户确认来源版本后再继续。

### C13：新命令继续满足原始工程适配约束

- 独立适配 Skill 是执行适配的 AI 的集中操作指南，说明检查对象、真实证据来源、修改对象和验证方式。
- 适配必须基于目标工程真实源码、目录、配置、依赖、Skill、SDK、工具链和既有业务案例；文件存在不能
  代表适配完成。
- 未经目标工程核实的项目知识和目标相关规约不能进入正式启用清单；两个随包直接维护的通用模式及其
  索引默认进入知识清单，目标工程证据决定具体需求能否采用，不决定模式文档是否交付或列入清单。
- 目标工程的具体需求允许不采用模式、采用一个或两个既有模式，也允许形成自己的模式；默认列入知识
  清单不等于强制采用。
- 通用 Story Extension 能力、当前工程示例和目标工程正式适配内容必须明确分离。
- 适配后的目标工程不能依赖当前工程的路径、文件或运行环境。
- 适配完成后必须能明确得到目标工程正式启用的项目知识、规约和设计模式。

### C14：可观测性能力随目标工程完成真实适配

- 适配必须分别核实目标工程真实的日志 API、级别、格式语法和运行期开关，VOC SDK、事件模型、字段限制、
  频控和失败语义，Chart SDK、事件命名、字段限制、统计口径和归档流程。
- 适配必须读取目标业务代码中的日志、VOC、Chart 正常案例和异常案例，并核实数据保护规则与秘密字段定义。
- 目标工程真实能力替换 Demo 的 Logger、VOC 和 Chart 身份与示例，同时保留业务流程索引、三层密度、
  业务步骤终态统计和上报失败隔离语义。
- 目标工程缺少任一渠道时，适配方案必须登记能力缺口和权威证据，由用户确认引入真实依赖或调整适用规约；
  确认前不能虚构 API、事件或上报结果。

### C15：两个设计模式默认启用，采用以目标工程证据为准

- 2.0 全量交付 `decision-tree` 和 `page-interaction` 两个通用模式及其索引；通用模式定义属于直接维护内容。
- 两个模式引用的 SDK、依赖、API、代码位置和既有案例属于适配内容，必须通过目标工程真实源码、依赖和
  多个案例核实，不把当前 Demo 或原型工程的身份复制成目标工程事实。
- 两个模式及其索引默认进入目标工程 Knowledge 清单；缺少 SDK、API 或既有案例时登记证据缺口，由 Plan
  据此判断具体需求不能采用或需要先补齐依赖，不从知识清单删除模式原件。
- 具体需求可以形成零个、一个或两个模式候选，并由 Plan 选择采用或不采用；进入清单不表示必须成为候选
  或必须采用。

### C16：Extension 是独立交付包

- `doc/extensions` 内的直接维护内容必须随包自洽，不引用来源工程绝对路径、外部工程文件、
  来源提交或来源工程 Git 历史作为安装、升级或运行依赖。
- `releases/1.0.json` 是随包交付的不可变 1.0 基线；适配器直接读取该清单，不在目标环境
  重建或回溯其来源。
- 历史提交、原始取材位置和复制完整性证据留在 `test/story` 维护记录，不进入交付包。
- 目标适配文件可以承载对目标工程的真实对接；这与直接维护内容不得绑定来源工程是两个边界。
