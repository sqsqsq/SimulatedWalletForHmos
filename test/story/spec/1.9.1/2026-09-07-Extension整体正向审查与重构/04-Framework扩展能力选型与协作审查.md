# Framework 扩展能力选型与协作审查

> 状态：后续正向审查的分析输入，尚未形成最终选型或实施方案。
> 来源：用户 2026-09-06 要求同时评价 Extension 使用 Framework 扩展特性的方式，是否最佳、最高效、最可靠。
> 观察基线：Extension `ffc4d695`，Framework `0143e21` 加本仓 OpenCode 登记；正式讨论以四批次交付后的实际版本复核。
> 关联：[整体诉求](02-Extension整体正向审查与重构诉求.md)、[特性树与当前方案](03-Extension特性树与实现方案审查范围.md)。不启动 Framework 修改或新的运行机制。

## 1. 要回答的问题

整体方案不能只在 Extension 内部比较。需要同时判断：Framework 已提供哪些能力、Extension 为什么选择当前扩展点、还有哪些可用路径、当前自有代码是在补真实缺口还是重复实现已有能力。

“最佳”指在已确认需求、实际宿主、当前协议及必要保护下，能用更少的实现字符与更低的执行/维护成本取得相同或更好效果的方案。高效与可靠需要一起比较，不承诺脱离场景的绝对最优。不能通过取消真实审查提高速度，也不能为假设风险不断增加验证层。

每项接口都沿“声明 → 加载 → 实际调用时点 → 输入接收者 → 输出消费者 → 失败恢复 → 交付证据”检查。接口名、schema 中存在字段、文件被物化，都不足以证明这条链成立。

## 2. 当前协作面与待比较方案

下表覆盖当前使用的扩展点及直接相关的候选能力。未使用能力只作为比较对象，不预设需要接入。

| 编号 | Framework 能力 | Extension 当前用法 | 选型审查要点 |
|---|---|---|---|
| I1 | instance manifest：`provides.skills` 与宿主 skill bridge | 登记 Story、Adaptation，物化多个宿主入口，入口再指向扩展 Skill | 多宿主入口是否是必要薄桥；有无复制主体规则、各宿主是否读到同一版本；能否复用已有物化而减少手工维护 |
| I2 | `provides.knowledge`、作者行为规约 | 清单作为三类知识激活源；作者原则页与动态任务包走扩展自己的指引/CLI | 当前 manifest 1.0 knowledge 是知识路径数组；不能假定它等价于任意作者任务注入。比较官方作者入口与扩展 CLI 的送达时点、信息完整性和实际读取成本 |
| I3 | `on_context_load` | 已取消作者要求对此事件的依赖 | schema 明确只进入 verifier 装配，不进入写前作者上下文。不得因名称像“加载上下文”就重新用来送作者任务；后续上游若改变协议须重新核实际调用 |
| I4 | `post_check` 生命周期钩子 | 六阶段各运行扩展的确定性检查 | 哪些检查补充了 Framework，哪些重复原生检查；错误严重级、超时、缺输入与解析失败如何传播；是否把只在后续时点存在的报告拿到这里提前检查 |
| I5 | `phase_rules_overlays` | 六阶段补充语义判据及部分阶段输入要求 | 合并与覆盖语义是否符合预期；overlay-only 项是否真实进入审查任务；与作者说明及脚本判据有无重复或不同含义 |
| I6 | `pre_verifier` | 从 overlay 提取判据标识，送知识真源位置与 Story 读者任务 | 这份补充是否仍为当前 Framework 必需；是否重复它已装配的判据；扩展自行解析 overlay 的范围与维护成本能否降低。不能仅凭注释中“Framework 不送”就保留全部补充逻辑 |
| I7 | verifier adapter 登记、request/subject、调用方保存 MD | OpenCode 在本仓登记；Framework 派 verifier 一次审 spec/Story；扩展没有另建派发链 | 登记、子代理权限、请求形态、报告格式与宿主实际能力是否对应；相比独立审查链节省了什么；异常与重投由哪一层负责 |
| I8 | `check-receipt` 与报告/阶段证据路径 | `check --deliver` 调原生回执，再检查 Story 审查条目形态 | 是否已经有合适的正式后置点；没有时当前组合是否最小；普通检查、交付检查和归档兜底的重复是否提供新信息；报告读取是否应复用稳定公共接口 |
| I9 | `phase.next_step`、确认策略、修正与重验 | Story 自管材料/范围流程，阶段推进及评审回流接 Framework | 用户授权是否被重复询问；两个状态体系是否各有不同职责；材料修订、成文重开、阶段重验有无重复判定或遗漏失效 |
| I10 | 配置路径、profile、阶段产物与证据合同 | 扩展 paths helper 和作者任务包派生路径；知识义务写入下游契约实体 | 哪些稳定公共能力可直接复用；哪些属于内部实现、不应紧耦合；同一产物路径、状态和字段含义是否多处手写；共享是否减少真实重复 |
| I11 | `provides.skill_assets`（当前未登记） | 扩展自有模板/规则路径由 Skill 或任务包给出 | 当前 schema 支持覆盖 profile 的 skill asset 键。只在确有消费者且能减少重复入口时比较此能力；不是所有作者规则都适合改成 asset |
| I12 | `provides.capabilities`（当前未登记） | 暂未以此注册现有业务 helper | schema 支持 provider 与 severity；须确认实际调用者和失败合同，不能因有字段就把所有脚本包装成 capability 或增加一层调度 |
| I13 | Framework init 物化、完整性与 drift 登记 | Adaptation 接入扩展；本仓 OpenCode 两处登记与目标包分离 | 更新后哪些物化件必须同步、哪些归目标；常驻登记是否容易随升级丢失；包不带补丁后的目标兼容是否有证据，避免另建影子升级器 |

I1–I13 必须与特性树双向对应。例如 I2/I3/I6 共同影响 F2.1、F4、F5.1；I7–I9 共同影响 F2.8、F3.5、F5.4–F5.7；I13 影响 F6。不能逐项宣布“接口用法正确”后就跳过组合审查。

## 3. 已核实的接口事实与证据边界

- [manifest schema](../../../../../framework/specs/instance-extension-manifest.schema.yaml) 中，当前 knowledge 为字符串路径数组；hooks、overlays、skills、capabilities、skill_assets 有不同合同，不可混用。
- [生命周期 schema](../../../../../framework/specs/lifecycle-hooks-schema.yaml) 明确 `on_context_load` 只在 verifier prompt 装配时消费。作者写前送达必须另外确认实际入口。
- [当前 harness](../../../../../framework/harness/harness-runner.ts) 中 `pre_verifier`、`on_context_load`、`post_verifier` 在同一段流程连续发出；不能把 `post_verifier` 的名字理解为独立子代理返回后的交付钩子。正式选型须看调用时序和输入，不只读事件说明。
- [扩展 loader](../../../../../framework/harness/extension-loader.ts) 实际装载各类 provides，并在 manifest 校验失败时停止应用 provides；“没加载要求”和“本需求无要求”应能分辨。
- [当前 pre_verifier](../../../../../doc/extensions/hooks/shared/pre_verifier.mjs) 自行读取 overlay 标识并追加指路与输出要求；其必要范围需要与 Framework 当前真实装配结果对照，尚不能认定可以全部删除或全部必要。

这些是本地版本事实，不是对未来 Framework 版本或所有宿主能力的推断。当前只讨论 interactive；没有用户新需求，不为 headless/goal 增加适配或测试。

## 4. 每个选型需要给出的比较结果

每项至少比较当前用法与一个更简单的可行路径；若没有替代，写明约束和保留理由，不为了比较造新机制。候选可包括直接使用现有扩展点、减少注入内容、合并重复消费者、保留一个轻量适配，或确认确有上游能力缺口。

| 维度 | 必须说清的内容 |
|---|---|
| 需求适配 | 满足特性树的哪项能力；输入和输出是否在正确时点由正确执行体消费 |
| 字符与执行效率 | 静态实现及实际注入字符、重复读取、进程/工具/子代理调用；相较当前路径具体减少什么 |
| 可靠性 | 缺文件、错误配置、加载失败、版本变化、报告缺失或返修时发生什么；谁发现、谁恢复；是否存在静默缺席 |
| 维护与升级成本 | 依赖公共合同还是内部路径；协议变更需同步几处；是否生成额外副本或重复状态 |
| 整体收益 | 是否减少 Extension 字符却把等量规则转移到 Framework、知识或每次运行；局部更短是否导致其它阶段更多工作 |
| 证据 | 官方合同、当前源码实际调用、最小离线对照及所需的实际宿主反馈；缺少的证据如实列出 |

可靠性不以“用了更多门禁”衡量，效率不以“少调用一次审查”衡量。比较的是满足同一目标时的完整行为链；可复用当前检查与已有实跑，不预设增加测试平台。

## 5. 新增的需求与完成条件

**N9：完成 Framework 扩展能力的选型与协作合理性审查。** 整体正向重构必须说明当前使用与相关未使用扩展点的适用性，判断现有接法是否是当前约束下成本更低、可靠性足够且更易维护的选择。

完成条件：

1. I1–I13 与特性树对齐，实际入口、时点、执行体、消费者和失败路径可回查。
2. 每项选型给出保留、改用已有能力、缩减适配、退场或需上游补齐的结论，附更简单路径的比较依据。
3. 对作者送达、审查闭环、恢复推进和工程适配至少各给一条完整链路的组合结论。
4. 不能只因“Framework 提供了”就认定优于现状，也不能只因“扩展已经自己实现”就不比较复用。
5. 最终收益纳入整体字符与效果对照，不能把实现移到另一个层次后虚报缩减；新增上游需求另行明确，不在本记录中授权修改发布件。
