# 在 Framework 3.1 上从零构建 Extension：目标规格

本规格仅依赖 [完整特性树](01-完整特性树.md)与 Framework 的实际职责，不假设已有 Extension 脚本、文件、钩子或状态结构。协议可用性与验证见 [协作分册](03-Framework协作与验收.md)。此处的对象和交接是行为合同，不表示新增数据库、快照、Agent 层级或运行框架。

## 1. 产品责任及权威

Extension 对需求的可理解性、人读交付、人工决定的准确传递、知识应用链与对外归档负责。Framework 对通用设计及其权威、执行拆分、施工推进和开发闭环负责。执行模型在各自职责下分析与行动，人承担真实业务和权限决定。

| 信息/结果 | 权威所在 | 谁消费及何时使用 |
|---|---|---|
| 外部原始材料 | 原提供方，Extension 保存实际取得版本 | 需求理解者、设计者、成文者在有关判断前读取 |
| 需求范围与人工澄清 | 有权决定的人及可追溯原话 | 双方在形成需求解释和设计前使用 |
| 项目事实、规约、模式 | 目标工程维护的知识及真实工程事实 | 当前动作执行者在适用性或设计判断前读取 |
| 部件设计及共同取舍 | Framework 权威蓝图 | 成文者、施工者和验证者读取当前有效设计 |
| 施工细化与运行结果 | Framework 对应执行责任方 | Extension 仅为解释进展、变化和结果而读取 |
| Story 表达 | Extension，设计事实来源仍在蓝图 | 人阅读、评审、归档；不作为新的设计权威 |
| 人工评审意见 | 评审人，保留对象与版本 | Extension 理解并传给正确责任方 |
| 发布记录 | 外部系统结果及 Extension 的实际操作依据 | 人了解外部现状、重试或恢复 |

共同决策只在其权威处成立一次；后续可以引用、落实和提出新事实。不能因读者不同而形成独立可改的第二套设计结论。

## 2. 两种使用路径

**需求协作路径**：人以系统单或本地材料提出需求，Extension 组织取材、澄清、设计、人读交付和后续更新/发布。默认完成到基于有效设计的 Story/Review 与交付选择，施工准备按请求终点启动，具体条件见 §3.3–3.4。用户只请求取材、查看或局部更新时，到该请求终点即可。

**知识应用路径**：人直接使用 Framework 的设计、实施或验证入口，目标工程启用的知识仍按当前动作送达并参与判断。无需创建 Story 流程记录、取材目录或评审件。专项审查、无新 spec/plan 的执行也不能因缺 Story 身份而失去知识。

两条路径使用同一目标知识和同一应用原则；不是两套知识选择器。缺少某项必要来源时回对应责任方，不自动启动无关业务流程。

## 3. 正常需求协作

### 3.1 取得可用于决定的输入（A、G1）

输入是人的请求、来源身份、实际材料及目标工程事实。模型分类、盘点、理解语义；脚本执行确定性获取、转换、来源保存及一致性核对。系统与本地来源进入同一理解过程，远程缺席与故障分别处理。

材料清单包括正文、图表、UX、会议及必要补充。补图不覆盖已有正文，图片说明与采用理由跟随真实图片，会议记录保留讨论性质。取得的版本、采用的版本和待处理版本可区分。

模型先形成材料缺口与建议，再请人确认本轮材料；有待定会议议题时提出裁决；分析业务边界后请人确认本单承担范围。已确认范围以外的依赖、兄弟单责任仍可进入背景，不能成为本次施工义务。

输出是有依据的目标、范围、约束、验收意图、来源及未决。必要未知阻止依赖它的决定；独立且明确的工作可继续。不能用提取摘要代替所有原始输入，也不在提取环节提前建立部件设计权威。

### 3.2 请求设计与知识应用（D、G）

Extension 将确认后的需求依据交给 Framework，并保证设计者及独立质询方在有关决定前取得适当知识。正式需求按 Framework 规则进入设计；是否正式依上游分类和实际语义判断，信息不足问人，不只看编号。

模型在 Framework 设计职责中形成方案，知识改变具体约束、角色、契约、状态与验证安排。独立质询核对知识是否真正影响设计，发现来源冲突或遗漏回正确责任方。

Framework 决定是否拆成一个或多个 CU、如何引用共同设计及何时可施工。Extension 不重新拆分、不逐 CU 重做需求分析，也不为 CU 开出重复的人工评审。

### 3.3 形成需求级说明和人工议题（B、C）

用于正式人读交付的蓝图须通过 Framework 设计准入，投影对应明确的有效 revision。Story 的需求背景和业务语境来自原始需求及有效决定，设计解释来自权威设计。成文所需输入是这些有效依据，不要求先生成施工阶段的 spec/plan。设计尚未准入时可展示草稿和问题，但不能标为正式交付完成。

Story 讲清背景与目标、术语、边界、参与方、场景与行为、方案和取舍、异常恢复、非功能约束、验收、交付上线及精确来源。采用适合读者的组织形式，覆盖这些职责；不按章数、图数或字数判质量。专项知识要求讲清的业务方案可独立定位，技术明细不能在改写叙事时消失。

评审件呈现有后果的议题、依据、建议、待决和人的填写位。已定事项能追溯决定者或权威材料；人的表态不被模型代填。人读成品质量由结构检查和独立语义审查各负其责；设计投影一致不代表 Story 内容完整。

请求终点决定所需结果：

| 请求 | 完成条件 | CU 与施工的关系 |
|---|---|---|
| 默认 Story 请求或仅送审 | 蓝图已准入，Story/Review 与该版设计一致，适用质量检查完成 | 不以 CU 已拆分或 readiness 已就绪作为文档交付前提；已存在的结果可引用 |
| 明确要求完整设计交接 | 上述人读结果，加 Framework 的完整设计交接结果 | Framework 完成或复用 CU、design_refs 与 readiness，到此不启动施工 |
| 授权完整实现 | 按 §3.4 完成施工准备、实施及必要整体闭环 | 可复用有效交接结果，未满足的准备在已有授权内完成 |

送审时可以保留供评审人表态的议题，但当前设计所依赖的事实与权限必须满足准入要求。文档交付、人工批准和施工完成分别报告。

### 3.4 交付选择与实施（F1、D6–D8、G5）

人可选择送审、授权完整实现、先归档再授权或暂不推进；本地需求没有线上归档。已有明确且适用的授权不再询问。业务规约指定的前置审批仍须满足，普通实施授权不代替审批。

完整实现授权包含必要的施工准备。Framework 先完成或复用 CU、design_refs 与 readiness；条件成立后由外层入口创建或恢复 attended 运行，覆盖所需施工与整体闭环，并按有效输入和实际义务安排阶段。准备中若需要修改已定需求或设计，按相应责任处理并同步受影响的人读材料。Extension 继续提供知识与变化输入，读取进展以需求结果向人说明；用户不必逐 CU 授权或理解其内部目录。

实现中需要扩展范围、增加权限或解决人工才能决定的问题，提供事实、选项与影响。质量失败由责任执行者修复，不能由人签字改成通过；环境能力不足据实报告。多个 CU 的局部完成不能替代整体需求的组合证据。

## 4. 知识链的产品合同（D）

知识不是在需求前生成一次清单就完成。它随相关动作被理解和落实，已成立决定传下去，新事实可在原责任处修订。

| 环节 | 必须交付什么 | 成立依据 | 失败处理 |
|---|---|---|---|
| 看到 | 当前动作需要的已激活知识类型、原文及必要事实来源，给作者和相应审查方 | 实际输入可追溯，来源可读 | 来源缺失报告；不能以空知识或报错时首次告知代替 |
| 理解 | 结合当前业务判断适用、不适用、冲突与模式候选 | 理由与业务事实、独立审查；不声称读到模型内部状态 | 回查来源、澄清冲突，不靠关键词自动判语义 |
| 应用 | 要求改变具体设计/实现/验证对象，角色与责任可指认 | 对象、行为和证据要求之间有实际关系 | 漏项回相应设计或执行责任方，不补装饰性声明 |
| 传递 | 已成立决定、相关理由、实体义务、验证责任及需要回查的来源 | 下游实际取得并落实或明确不适用 | 查最早丢失交接，不能让每个 CU 重新猜选型 |

项目事实用于理解真实能力，错误回知识维护者核实；规约结合实际行为判断，设计前考虑设计约束，执行前考虑执行义务；模式在有足够设计事实的负责方完成选择，其他执行者落实角色协作。不能为了统一流程把所有条目提前判死，也不能等设计结束再首次发现设计约束。

共同要求在整体设计中形成，局部义务随 Framework 的真实施工对象承接。需求级完整性核对须能回答：哪些义务已经落实、哪些待后续、哪些需要组合验证，并给出对应的权威结果与依据。取得这些信息的具体接口和覆盖能力由 design 核实；缺少必要信息时明确报告缺口，由所属责任方补齐，Extension 不自行裁定施工完成。

知识应用包括骨架参考、原文附注、专项说明、精确技术定义、真实实体落点和验证分派。探针仅提供可确定的形态证据；运行正确性用相应运行证据。目标只用某种上报渠道、没有专项知识、或换一个业务领域时，通用机制不增加分支。

## 5. 变化处理（E、C4–C5、G）

变化可来自上游改版、人的新决定、评审回稿、直接编辑、知识或工程事实变化，以及 Framework 已接受的设计修订。系统需要在显式 update/继续请求时识别相关变化，不要求后台监控。

先报告本轮输入并完成材料确认，区分未变、未完成更新、缺比较依据和确有变化。无变化且无未完成同步时不改业务结果；来源失败不能当无变化。

模型理解变化影响的目标、行为、责任、异常及验收，说明仍然成立的部分。Extension 修订自己的需求解释和人读表达，将设计变化交给 Framework；施工有效性由 Framework 判断。不能只同步同名词语，也不能替 Framework 在另一份文档重定设计。

| 变化性质 | 去向 |
|---|---|
| 纯表达调整 | Extension 修改表达，保持事实与人工意见，不升设计版本 |
| 新需求或范围改变 | 人裁定业务范围，重新交付有效需求输入 |
| 事实补充或设计裁决 | 按 Framework 反馈协议交候选，取得正式接受/拒绝结果 |
| 无授权的意见或建议 | 保留并说明，不能直接成为设计裁决 |
| 已生效的设计变化 | 读取当前权威结果，同步需求说明，说明下游完成证据是否仍有效 |
| 人直接改了派生文档 | 先保护修改、理解意图，转成适当候选；不将整份 Story 反向当设计源 |

引用旧版本的评审须由裁决方重新评审或确认新版本仍成立，不能只改版本字段重投。需求意见若不涉及蓝图设计对象，应在其业务责任处处理，不伪造技术目标来满足 schema。

update 默认处理受影响的已有文档及必要依据，不自动补完在途阶段或修改产品代码；已存在更广的实施授权由 Framework 按其权限继续，但不得从 update 命令推断新增施工授权。变化超出范围时回范围关卡。

修订后的结果和必要审查须对应当前依据，更新收口不代表整个需求开发完成。报告明确已同步、保留项、未完成及下一责任人，不能通过关闭记录掩盖真实缺口。

## 6. 发布、恢复与续行（F、G2–G4）

归档发布以人审阅的当前内容为对象，展示差异、未决与验证缺口，按实际授权回写。Story 为人读主件，Review 承载表态；图与附件可读，外部读者不需拼接本地施工目录。内容变了就不能沿用不适用的旧确认。

发布失败保留本地正确结果，重试核外部是否有新修改；本地成功不等于外部发布成功。评审未填完可以送审，不能称审批完成。

恢复区分本地工作现场与远端被覆盖内容，保留恢复之后新增的人工工作。已被 Framework 接受的设计或施工变化不由扩展快照撤销；如需撤回设计意图，走原生修订，报告内外版本差异。代码回滚不由文档恢复隐含授权。

跨会话通过真实状态定位未完成工作，查询不触发新设计、拆分或运行。作者和审查方取得当前材料；旧报告不冒充本次审查。对纯机械结果与语义结论分层验证，缺审查能力如实披露；非阻断建议不形成无限返修。

## 7. 跨工程使用（H）

包维护通用机制，目标维护知识与业务身份，业务对接按明确来源所有权处理。首次安装生成知识骨架并核实目标画像，由人确认必要信息；升级保留目标知识，不把 Demo 正文或对接替身带入真实工程。

目标 Framework 及能力不兼容时写入前说明，覆盖面有在途修改时保护并报告；无变化可重复执行。机制退出与新能力交付一起完成，无关内容不进入覆盖面。入口物化由 Framework 负责，跨仓复制和所有权由 Extension 负责。

知识登记格式可以迁移，但不能改变目标激活语义或用包内清单覆盖。损坏配置与明确空知识不同，失败说明完成/未完成范围及恢复动作，不报部分成功为整体可用。

## 8. 产品验收原则

能否完整服务一项需求是验收单位。相同业务要求在单 CU、多 CU、没有新 spec/plan、直接 Framework 入口、设计变化后继续这些合法安排下，Extension 的核心结果与知识义务应一致；无需承诺文档逐字相同。

以真实输入、决定依据、交付物、人工操作及结果证据核对能力。特性树中的异常保证同属产品需求，不能因换了实现而丢失。验证场景与实际接口缺口见协作分册，旧实现映射不参与本规格的功能裁定。
