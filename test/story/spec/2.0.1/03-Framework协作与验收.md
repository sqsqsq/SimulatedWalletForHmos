## 2. 双方交接

| 合同 | 生产者 → 消费者 | 最小有效内容与时机 | 拒绝/恢复责任 |
|---|---|---|---|
| I1 需求依据 | Extension → Framework 设计方 | 设计前给已定目标、范围、验收意图、必要背景/来源、负责人和正式性 | 来源缺失、摘要冲突回取材/采用决定；不凭转述继续 |
| I2 知识输入 | 目标知识经 Extension → 当前作者与独立审查方 | 有关决定前给激活内容、完整来源及相关任务要求，允许执行者判断适用性 | 登记却未送达查接入；知识矛盾回目标维护方 |
| I3 有效设计 | Framework → Extension 成文者 | 设计准入结果、指定 revision 的投影及可追溯设计/缺口；完整交接另含 CU readiness | 未准入不能伪称有效设计；局部结果只作局部交付 |
| I4 人工反馈 | Extension → Framework 设计负责方 | 原话、分类、证据/权限、被评对象和版本；符合 feedback schema 才提交候选 | 资格错误回映射/责任人；采纳由写入负责方判断 |
| I5 知识义务落实 | Framework 有效设计/施工输入 → 后续执行者，经 Extension 专项要求检查 | 已成立决定、真实实体/角色、来源及验证责任；在实施和验证前取得 | 丢失或语义改变回最早责任；不维护影子 CU 义务表 |
| I6 授权与进展 | 人经外层入口 → Framework；Framework → Extension/人 | 实际授权终点和当前设计依据；返回可解释的运行、阻塞与完成结果 | 越权回人；阶段结果和组合完成仍由 Framework 判 |
| I7 外部发布 | Extension ↔ 目标需求系统 | 展示确认过的版本、Story/Review 与素材、实际外部结果 | 失败保留本地结果，外部冲突先解决；Framework 不处理内网凭据 |
| I8 安装与宿主入口 | Extension installer → 目标机制；Framework → 宿主入口 | 按所有权安装已验证版本，再物化、检查实际消费者 | 不兼容/脏覆盖写入前失败；部分安装说明恢复位置 |

知识可以跨 I2/I5 参与所有实际执行环节，这不扩大 Extension 的施工调度职责。CU 身份只在接口追溯、精确定位或解释必要进展时出现，不向用户要求逐 CU 重复业务确认。

## 3. 已有协议和待定接线

| 对象 | 可以依靠的能力 | 尚需定案/验证 | 缺口处理 |
|---|---|---|---|
| I1/I3/I4 | 物化、投影、反馈 schema/checker 及 component-design | 需求身份与真实设计目标映射，材料/意见转换，错误展示 | Extension 的实际适配职责；字段以发布件为准 |
| I2 蓝图知识 | Skill 可显式读材料；Framework 有 conventions 和既有静态输入方式 | component-design 当前正文未显式消费扩展 skill_assets；直接进入 Framework 时的知识送达覆盖尚未证明 | 先核既有公共扩展点；若只有 Story 入口加读指令才能生效，则不满足直接入口目标，缺口交 Framework |
| I5 知识传递 | 蓝图设计引用、施工输入与既有阶段接入 | 自定义实体义务能否跨原生派生/复用保留；接收者是否实际读到，组合义务如何被整体核对 | 不能假设搬 YAML 即可；公共输入/闭环能力不足交上游，业务判据由 Extension 负责 |
| Story 独立语义质量 | Extension 有读者审查要求；Framework 有独立审查能力 | 无新 spec 时通过哪个合法调用面审人读交付、结果如何被采纳 | 优先复用现有审查通道；没有合法入口须列上游依赖，不借假 Feature 或手写 PASS |
| update/恢复 | Framework 有 revision、过期判断和运行恢复职责 | 原生修订与现有 CU 的具体交接、局部文档更新的结果读取 | 同一权威内操作，不用扩展快照回写 Framework 历史 |
| 安装 | materialize、manifest 1.1 | 目标知识登记迁移、旧桥接归属、兼容区间与本地 verifier 差异 | 定向安装验证，不能声明支持所有 3.1+ |

上述“尚需验证”是实施设计的明确输入，不意味着可以删目标或先造兼容层。用公共协议可满足时只实现业务适配；缺公共能力时先说明依赖及验收影响，取得上游能力后再闭合。不得把 hypothetical spec 描述成当前版本已提供全部接线。

## 4. 边界推演

| 场景 | 需求级结果 | Framework 的内部变化 | Extension 必须保持什么 |
|---|---|---|---|
| 一个 CU 变成多个 CU | 同一目标、范围和一套人读交付 | 执行拆分与依赖变化 | 不要求重新建单；共同知识不重复裁决，跨部分义务仍可追溯 |
| 不新跑 spec/plan | 已有有效信息仍满足业务要求 | 复用输入、只补未满足义务 | Story 和知识不以文件新生成作为前提 |
| 直接 /component-design，无 /story | 用户只要设计，不要求归档 | Framework 正式入口执行 | 已激活知识生效，不强制 Story 全链 |
| 已送审后设计修订 | 新旧评审对象可区分 | 蓝图新 revision，旧证据可能过期 | 保护旧表态和发布记录，同步新稿，不把旧批准套新设计 |
| 只有资料要更新 | 资料正确，设计仍待开展 | 无必要创建新设计或 run | 不为了“全链完整”自动补齐所有产物 |
| 仅送审，尚无 CU | 基于准入设计的人读材料可正式交付 | 尚未请求施工准备 | 不因缺 CU 或 readiness 阻止送审，不启动施工 |
| 送审后授权实施 | 人读材料与实际设计仍一致 | 完成或复用 CU/readiness 后进入运行 | 不重复业务确认；新的设计变化按责任回流 |
| 多 CU 各自通过但组合要求未证实 | 需求仍有未完成义务 | Framework 整体核对保留缺口 | 不显示整体完成，不用文档完整代替运行证据 |
| 目标无专项知识或只用一种渠道 | 适用范围被正确理解 | 实际设计按事实形成 | 空知识不强造义务；已登记坏来源不能伪装为空 |

这些场景用于检验责任是否自洽，不新建模拟平台或泛化测试框架。技术反例只验证确定性协议，模型语义能力要用正常需求的真实执行证据评价。

## 5. 能力验收矩阵

特性树各叶节点均落到下面的验收组；组内仍需按叶节点逐项核对，不能只给父组一个 PASS。

| ID | 特性 | 验收场景与结果 | 证据层次 |
|---|---|---|---|
| V1 | A1–A8 | 系统/本地起手、缺料/冲突、会议、图与范围都形成真实可用输入；业务边界不被 CU 改写 | 来源/转换检查、实际输入、语义与交互证据 |
| V2 | B1–B7 | 一套 Story 讲全需求，设计正确、图文完整、技术信息可查；多个 CU 或无新 spec 仍成立 | 结构及来源核对、独立人读审查、用户评价 |
| V3 | C1–C5 | 议题有实际后果，表态不代填；旧版/变义意见受保护，反馈资格与采纳分开 | 人工区检查、反馈协议反例、处理轨迹 |
| V4 | D1–D5 | Story 与直接 Framework 两种入口都在决定前取得完整知识，判断有据并改变真实设计对象 | 作者/审查输入、实际设计差异、独立语义证据 |
| V5 | D6–D9 | 局部与共享义务在后续落实/验证；复用阶段不中断传递；换领域不加机制特判 | 有效引用与实体、执行证据、缺口及中性知识检查 |
| V6 | E1–E6 | 更新四种状态、人工编辑、范围变化、增量同步和本地撤回正确，不授权额外实施 | 定向检查、前后结果、保留项与恢复证据 |
| V7 | F1–F4 | 仅送审不要求 CU 就绪；授权实施后才按需完成施工准备；归档版本准确，失败/冲突可恢复，本地单无远程动作 | 请求终点检查、发布结果与实际授权 |
| V8 | G1–G5 | 中断续行、当前对象审查、能力不足及组合缺口如实呈现；无重复任务或假完成 | 输入、权威状态、报告采纳与实际运行 |
| V9 | H1–H4 | 首次、升级、重复、不兼容、脏路径与两类来源均按所有权工作，目标知识不丢 | 临时目标定向验证、实际文件及入口 |
| V10 | 全体 | 各能力在同一需求协作中组合成立，无影子设计/施工状态、无已退路径干扰 | 合并行为审视、新旧退出核对、实际成本记录 |

命令成功、链接合法、schema 通过各自只证明机械事实。独立语义审查核内容，真实宿主运行核信息是否到达执行者并产生结果。运行配置与模型绑定证据，不外推到未测环境。

## 6. 本版实施验证范围

真实需求止于 Plan，按 [总览](00-版本需求与结论.md)的范围与 TEST 协议起跑；本轮不启动。选择确有施工设计义务的需求观察承接，不为满足检查表强制执行可复用阶段。多 CU、无新 spec/plan、安装、恢复和直接入口须有针对本 Extension 的验证，Framework 自带夹具不独自证明产品能力。

2.0.1 的 Coding 及后续真实行为、上报事件和设备证据未取得时明确标未验证，不削减 D7/D8 的目标，不以“框架支持”声称已验。复用证据须核对材料、版本与环境是否适用；这属于 2.0.1 的验证责任，不改变 Story 1.x 的完整特性基线。

在 design 中将矩阵落实到已有检查、独立审查和必要真实场景，按维护契约说明成本与真实风险。公共接线缺口未解决前，不把整套目标标为可实施完成；可独立完成的准备、分析与确定性验证继续进行。
