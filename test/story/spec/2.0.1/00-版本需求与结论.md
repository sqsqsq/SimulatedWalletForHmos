# Extension 2.0.1：需求级产品目标与 Framework 3.1 协作

2026-09-22，按用户授权，先假设没有 Extension 1.x 的实现，只保留完整产品特性，在 Framework 3.1 上定义目标，再对照现有实现反思改造。本目录是当前唯一有效 spec。它规定产品行为和合作合同，不以旧文件布局、阶段钩子或状态结构限定目标。

## 1. 产品目标

Extension 服务一项需求从材料到开发交付的全过程：让消费模型取得真实输入、理解业务与项目知识，形成供人审阅的完整说明，正确接收决定与变化，保持有效依据一致，并在中断或失败后继续完成任务。

Framework 承担通用设计、施工、验证和闭环。其内部将工作分成一个或多个 CU，不改变 Extension 面向整项需求的职责。双方仍是“需求及知识能力与通用开发能力”的协作关系；交换内容、时机和结果有效性按 3.1 的真实协议确定。

知识的目标始终是“看到、理解、应用、传递”。不把“文件列在清单里”“阶段跑过”“规则名称出现过”当成知识生效，也不要求所有知识只在同一时刻判定。

## 3. 领域词义

| 名称 | 定义与边界 |
|---|---|
| 需求 | 有业务目标、范围、责任人和交付要求的一项工作；是 Extension 对外组织材料与交付的单位 |
| 需求依据 | 原始材料、来源、有效的澄清、范围决定和约束；派生叙述不自动取得原始依据的权威 |
| 设计 | 为满足需求形成的方案、契约和取舍；由 Framework 设计活动承担并形成权威结果 |
| 蓝图 | 当前部件一次演进的权威设计记录；不是新的业务单，也不是作决定的主体 |
| CU | Framework 拆分和推进施工的单位；不要求用户为每个 CU 重建需求、Story 或评审 |
| Story | 让评审者理解整项需求的完整人读说明，设计部分忠实表达有效设计 |
| 人工 Review | 需要人判断的议题、依据与表态；与 Framework 的代码审查不同 |
| 知识 | 目标工程的项目事实、规约、设计模式；由目标维护者维护，由相应执行者结合当前任务判断应用 |
| 交付 | 必须注明对象：需求文档可交付、设计可施工、实施已完成、已发布分别成立，互不替代 |
| 更新与恢复 | 更新使当前结果符合有效变化；恢复明确恢复的是本地工作、外部发布还是设计意图，不混为同一回滚 |

需求具有业务身份，蓝图、CU 和运行具有各自身份。关联用于准确交接与追溯，不要求它们同名或同目录，不在本版推广跨部件自动协调或任意多对多需求平台。

## 4. 范围、决定与非目标

本版包含特性树全部能力：材料与澄清、人读成文、人工评审、知识链、变化处理、发布恢复、续行质量和跨仓安装。普通 Framework 入口也应取得已激活的知识能力，不以先运行 Story 为条件。

保留既有产品决定：材料与范围由人确认，会议有待决话题时请人裁决；文档交付后可选择送审或授权完整实现；本地单不访问需求系统、不线上归档；人的表态不代填。

版本安排保持：story 分支发展 2.x；story-1.0 以 1.9.5 为交付目标，承接 Framework 3.0 的 1.x。2.0.1 使用经验证的 Framework 3.1 发布件，支持范围按实际能力声明，不能推定未来版本均兼容。

范围为 interactive；明确授权完整实现时，衔接 Framework 的 attended 运行。没有新增无人值守产品能力、CU 调度系统、通用状态框架、知识平台或代码生成器；不开发 BI 后台，不借本版扩大 Demo 业务功能。不在本仓就地修改 Framework 发布件，不自动改写全部存量需求。

人读交付须完整表达业务、设计依据、验收与交付要求，保护人工意见，并支持来源追溯及失败恢复。具体文档组织和执行方式由设计依据这些结果确定。

## 6. 交付与验证边界

本次交付是完整特性树、目标 spec、实际协作边界及现有实现反思；不运行被维护产品流程来证明其自身设计，不修改产品代码，不启动真实 CLI。

2.0.1 的真实需求验证上限仍为 Plan，实际 Case 与起跑按 TEST 和用户授权执行。该上限限制本版取得的证据，不删除 Coding、代码审查、UT、设备和整体完成中的知识责任。只取得前段真实证据时，发布必须分别说明接线验证与后段行为未验证，不能称完整需求运行已验收。

设计下一步须解决协作分册中的实际缺口，并依据 [维护契约 §5](../../AGENTS.md#5-维护预算与分级复核)形成新增/退出、峰值和完成预算及 1–4 个实施包；本轮反思不虚构尚未完成的工量估算和授权。
