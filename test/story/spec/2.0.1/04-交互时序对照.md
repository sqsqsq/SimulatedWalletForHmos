# Framework 与 Extension 交互时序对照

本文是 [目标规格](02-目标规格.md) 的图示，协作协议与待核实接线以 [协作分册](03-Framework协作与验收.md) 为准。

图中的“Extension 1.0 / 2.0”表示 1.x / 2.x 产品线。两图以同一套完整产品特性为基础，对照各自与 Framework 的协作方式；后图是 2.0.1 的目标流程，其接线与验证边界见协作分册。

参与者表示职责，不表示独立服务、进程或新增 Agent。执行模型依据相应产品指令完成箭头中的动作；Framework 的独立审查和运行机制合并在其泳道中。两图均以正式需求的完整主路径为例，可选分支按实际请求执行。

## 1. Framework 3.0 + Extension 1.0 产品线

本图展示 Story 1.x 的需求准备、人读交付、知识应用、人工评审、更新和归档如何与 Framework 3.0 配合。

```mermaid
sequenceDiagram
    actor U as 人（需求方与评审者）
    participant S as 需求系统或本地材料
    participant E as Extension 1.x（需求协作）
    participant K as 目标工程知识
    participant F as Framework 3.0（开发流程）

    U->>E: 提出需求，启动 Story
    E->>S: 获取正文、补充材料、图片与会议记录
    S-->>E: 原始材料与来源，或明确缺失/失败
    E->>E: 导入、盘点与缺口分析
    E->>U: 材料关卡：报告已有材料与待补内容
    U-->>E: 补料或确认本轮材料
    opt 会议存在待决话题
        E->>U: 解释话题、建议与依据
        U-->>E: 逐事项裁决
    end
    E->>E: 分析本单、兄弟单与协作方范围
    E->>U: 范围关卡：范围与承载建议
    U-->>E: 确认范围与业务分单
    E->>E: 形成部件需求提取稿
    E->>F: 进入该需求的 spec
    E->>K: 读取激活的事实、规约与模式原文
    K-->>E: 完整来源、适用条件与参考骨架
    E->>F: 交付作者要求和知识输入
    F->>F: 模型形成 spec、验收及知识判断
    Note over E,F: 规约判适用，模式登记候选；典型结构为一需求对应一 Feature
    F-->>E: spec 内容与有效判断，尚未阶段闭环
    E->>E: 编写 Story，登记议题，渲染人工 Review
    E->>F: 三份产物及扩展判据进入检查与独立审查
    F-->>E: spec 阶段闭环结果及读者审查结果
    E->>U: 交付门：Story、Review、缺口与下一步选择
    opt 选择归档送审，或先归档再继续
        U->>E: 授权发布当前版本
        E->>S: 上传 Story 正文、Review 附件与素材
        S-->>E: 实际归档结果
    end
    opt 授权继续开发
        U->>F: 进入 plan 及授权范围内的后续工作
        E->>F: 知识决定、原文及阶段作者要求
        F->>F: Plan 选型，义务落实到契约实体
        loop 按实际授权推进后续阶段
            E->>F: 当前动作的知识义务与审查要求
            F->>F: Coding、代码审查、UT、Testing
            F-->>U: 阶段结果或需要人工决定的问题
        end
    end
    opt 后续材料、评审或人工决定变化
        U->>E: 请求 update
        E->>S: 只读取回上游与评审，不覆盖人工区
        S-->>E: 当前材料和反馈
        E->>U: 本轮材料关卡
        U-->>E: 确认或补料
        E->>E: 理解变化，增量修订已有 Spec/Story/Review/Plan
        E->>F: 受影响的已有阶段重验与适用独立审查
        F-->>E: 当前对象的有效结果
        E->>U: 变化、保留项及可继续边界
    end
```

此结构中，Extension 的目标已经是需求级，但实现将需求交付挂在 spec 闭环上，知识判断与选型分别落在 spec/plan。图中后续阶段并非一次 Story 请求自动授权；更新也不自动改代码或执行设备测试。

## 2. Framework 3.1 + Extension 2.0 产品线

此图从需求级目标推导协作。蓝图知识实际送达、无新 spec 的人读审查及义务跨施工输入传递，仍需按协作分册核实合法接线。

```mermaid
sequenceDiagram
    actor U as 人（需求方与评审者）
    participant S as 需求系统或本地材料
    participant E as Extension 2.x（需求协作）
    participant K as 目标工程知识
    participant F as Framework 3.1（设计与开发）
    participant C as CU 执行（Framework 内部）

    U->>E: 提出需求，启动需求协作
    E->>S: 获取正文、补充材料、图片与会议记录
    S-->>E: 原始材料与来源，或明确缺失/失败
    E->>E: 导入、盘点与缺口分析
    E->>U: 材料关卡：报告已有材料与待补内容
    U-->>E: 补料或确认本轮材料
    opt 会议存在待决话题
        E->>U: 解释话题、建议与依据
        U-->>E: 逐事项裁决
    end
    E->>E: 分析本单、兄弟单与协作方范围
    E->>U: 范围关卡：范围与承载建议
    U-->>E: 确认范围与业务分单
    E->>F: 交需求依据、来源、范围与正式性，请求需求设计
    E->>K: 取得当前动作所需的激活知识原文
    K-->>E: 项目事实、规约、模式及其边界
    E->>F: 在决定前送达作者和独立质询方
    F->>F: 理解需求与知识，形成蓝图设计、质询和调和
    opt 必须由人补充事实、取舍或批准权限
        F->>U: 给出事实、问题、选项与影响
        U-->>F: 作出适用决定
    end
    F->>F: 完成设计准入
    F-->>E: 有效设计投影、revision 与缺口
    Note over E,C: CU 是 Framework 的执行组织；需求级材料与交付不按 CU 复制
    E->>E: 结合需求语境与有效设计，编写一套 Story/Review
    E->>F: 通过合法审查入口提交当前人读材料与业务判据
    F-->>E: 当前对象的独立审查结果
    E->>U: 交付门：完整需求说明、评审议题与实际缺口
    opt 选择归档送审，或先归档再授权
        U->>E: 授权发布当前版本
        E->>S: 上传 Story 正文、Review 附件与素材
        S-->>E: 对应该版本的实际发布结果
    end
    opt 授权完整实现
        U->>F: 经外层入口授权当前需求范围内的完整实现
        F->>F: 完成或复用 CU、design_refs 与 readiness
        F->>F: 创建或恢复 attended 运行
        loop 按依赖和实际义务推进所需 CU
            F->>C: 交付设计引用、有效施工输入和知识义务
            E->>C: 在当前动作前提供相关知识来源与扩展要求
            C->>C: 理解并落实义务，完成所需设计、实现和验证
            Note over F,C: Spec/Plan 按需形成或复用，不机械重跑完整六阶段
            C-->>F: 真实结果、证据及未完成义务
        end
        F->>F: 核对整体需求与必要组合证据
        F-->>E: 权威进展、整体结果或剩余缺口
        E-->>U: 用需求级结果说明完成范围与未验证项
    end
    opt 后续材料、评审、人工决定或设计变化
        U->>E: 请求 update 或继续同步
        E->>S: 取得当前材料与反馈，保护人工修改
        S-->>E: 实际变化或来源缺口
        E->>U: 本轮材料关卡及必要业务裁决
        U-->>E: 确认输入和适用决定
        E->>E: 理解变化，区分表达、需求、设计和范围责任
        opt 变化需要修改有效设计
            E->>F: 提交新需求依据或合格反馈候选
            F->>F: 判断接受；接受后修订蓝图，保留历史
            F->>C: 按原生规则重新判断受影响输入和证据有效性
            C-->>F: 当前状态与后续需要
            F-->>E: 接受结果、当前设计及下游影响
        end
        E->>E: 增量同步 Story/Review，完成适用检查与审查
        E->>U: 当前可用结果、未决、未验证与后续责任
    end
```

此图采用默认 Story 请求：设计准入后形成人读交付，授权实施后按需完成 CU 与施工准备。若用户明确请求完整设计交接，Framework 在该请求内完成 CU、design_refs 与 readiness 后交回，不启动运行；后续授权实施时复用有效结果。

E 到 C 的箭头表示扩展要求经 Framework 的实际执行上下文送达，不代表 Extension 选择或调度 CU。更新中的有效性核对也不表示重新实施；代码修复仍服从实际授权。独立人读审查箭头是目标合同，具体合法入口由 design 核实。

## 3. 两图共同的边界

- 两版都以需求为 Extension 的产品单位；取材、人工决定、人读交付、变化处理与发布职责保持。
- 知识均须看到、理解、应用、传递。旧版依赖 spec/plan 的固定承接；目标版按实际决策和执行责任承接，CU 拆分不能让义务丢失。
- 前图成文在 spec 阶段内完成；后图使用有效设计形成人读交付，不依赖 CU 新生成 spec/plan。蓝图准入、人工批准、实施授权与整体完成分别成立。
- 图示是 Story 完整主路径。直接进入 Framework 时，知识仍应生效，不强制启动取材、成文和归档；这一要求适用于两条产品线。
- 本地单跳过远端获取/发布；纯表达更新不修改蓝图；无变化不创建无用修订。发布失败保留本地结果，本地撤回与远端恢复不回滚 Framework 历史。
- 安装升级属于使用前的独立运维动作，两图未展开；其所有权与失败行为仍按特性 H 和目标规格执行。
