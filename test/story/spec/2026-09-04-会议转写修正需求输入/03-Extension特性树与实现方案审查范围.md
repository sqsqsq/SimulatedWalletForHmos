## 1. 目标与分析方法

目标是保留已确认的用户能力、产物质量和必要保护，以更少的实现字符及更低的使用成本达成相同或更好的效果。不能只问当前实现是否能工作，还要问同一特性是否有更直接的完整实现。

先按用户与执行者能获得的能力列特性树，再映射到当前方案；文件、状态、脚本命令和门禁属于实现手段，不自动成为必须保留的特性。一个支撑模块可服务多个特性，多个文件也可能只是在重复承担一项职责。

以下树覆盖当前 manifest 声明的 Story、Adaptation、三类知识及六阶段扩展。Framework 的编译、通用阶段与回执是依赖；本仓 CLI 测试装置是验证设施。两者进入整体协作分析，但不冒充 Extension 自己实现的用户功能。新提出的会议转写能力不算当前已实现特性。

## 4. 整体组合必须另外审查

局部合理不等于组合合理。需要对下列链条分别还原一遍正常任务和一次实际发生过的恢复，并记录跨特性重复。只画文件依赖图不足以回答这些问题。

| 组合视角 | 需要一起看的特性 | 整体合理性问题 |
|---|---|---|
| 作者完成一次需求 | F1→F2→F3→F5 | 作者是否能沿一条清楚路径完成工作；入口、状态、规则和任务包是否反复解释同一动作；机器自动完成的动作是否还要求作者手动执行 |
| 同一材料的生命周期 | F1.3–F1.5→F2.4–F2.6→F3.3 | 材料身份、版本、路径、引用与不引用理由是否一致；新视图是否引入第二个事实源；不能靠增加别名例外补错误对象模型 |
| 需求变更与失败恢复 | F1.7/F3.5/F5.2–F5.6 | 什么变化需要重签范围、重生成、重登记或重审；是不是每层都独立推断变化；能否避免无关产物与检查重复运行 |
| 知识真正影响开发 | F4.1–F4.9 | 每次读取、判断、冻结、落实和验证分别增加了什么信息；是否只是同一编号在多个文件重复出现；入口变化能否保持全链消费者一致 |
| 一次合法交付 | F2.8/F3.3/F5.5/F5.6 | 结构门、语义审查、回执与交付门各拦什么；是否用同一证据重复证明同一结论；缺省/失效状态是否被一致处理 |
| 换工程仍能工作 | F6 与 F1–F5 | 安装器替换了什么事实、保留了什么能力；运行机制有无目标仓专名或宿主假设；安装期省下的成本是否转嫁到每次运行 |
| 维护一次完整职责 | 全部 | 改一项功能需手改几份相同事实；测试是否只护局部形态；旧路径退场是否连同提示、状态、校验、夹具期望一起完成 |

路径、YAML 读取、材料解析、报告解析、提示装配、原子写入、通用错误输出是共同支撑方案，不另算用户功能。后续对这些支撑方案做反向核对：它们服务树中哪些叶子、是否已有可复用实现、删除或合并会损失什么。共享能够减少真实重复才值得做，不能为了整理目录新建一层框架。

## 5. “更少字符，相同或更好效果”的验收方向

### 5.1 相同目标先固定

重构前按交付后的基线冻结特性树、适用范围与代表性产物。新需求与重构分账，不以减少能力、放宽必要验收或把工作交回用户来实现字符缩减。当前明确要求的固定形态、数据保护和真实恢复能力应保留其效果，实现手段可以比较。

### 5.2 字符减少是明确结果，不只是参考数字

在同一特性范围和同一计数口径下，最终应有可验证的实现字符净减少；具体幅度留待完成特性与方案分析后确定。不能以“每笔都有理由”或“预算允许”代替这个结果。某局部可以增加，但应说明它替代了哪里及整体收益。

至少分开记录两组字符：

- **静态实现字符**：机制脚本、提示词、合同数据及安装适配内容。保留原始字符数和同口径的可执行/有效内容辅助读数；注释、自动生成文本模板不能从总视图中消失。现有预算排除安装器可继续作为其独立管理口径，整体审查必须把安装器单列算清。
- **实际执行输入字符**：一次任务真正送入作者和审查者的提示、动态任务包、规则及重复读取。字符累计量与 token/耗时分别报告，不能用源文件缩短替代上下文成本下降。

Knowledge 样板内容、测试夹具、维护报告和 Framework 自身分别列账，不能用它们的增减抵消机制字符；更不能把机制文字搬进知识、测试或 Framework 后声称减少。目标工程使用所需的生成视图同样应说明其实际读取成本。

只压换行、删必要解释、缩变量名、搬目录或改变统计范围不算正向收益。一个方案若通过取消重复职责降低字符，才算结构性简化；若通过更直接的措辞降低字符，应证明信息仍完整清楚。

### 5.3 效果与成本共同验证

比较产物完整性、正确性、可读性，知识实际应用与传递，输入送达、恢复和交付成功，以及作者工具调用、合理排障之外的源码读取、重复检查和返修成本。正常路径和已发生过的恢复情形都应覆盖；不同宿主证据分别报告。

复用现有测试与运行证据取得最小充分验证，不预设新增评测设施。验证收益时区分模型波动、人工等待和外部服务问题；单次已知 Case 更快或更短不单独证明泛化。

## 6. 正式审查的完成条件

1. 特性树覆盖所有已确认能力，每个叶子有当前方案、入口、直接消费者及可观察结果；待验证能力如实标记。
2. 每个叶子有局部判断：保留、简化、合并、替换、删除或待证，并说明依据；不得只输出问题清单。
3. 每项共同支撑有服务对象；发现的零消费者、重复状态、重复描述与失效路径都有处置，不为完整性制造新设施。
4. 对第 4 节的跨特性链给整体判断，说明局部改动是否减少了全程成本、是否在别处增加了负担。
5. 目标方案能从需求正向推导，并列出它替代的现有内容；确认后的重构有清楚的退出与验证条件。
6. 重构结果在相同目标下展示实际字符净减少和效果对照。若某部分应保留，明确保留，不强迫每个模块都缩短。

## 7. Framework 扩展能力也纳入方案比较

特性方案不能只比较 Extension 内部文件。还须检查使用的 Framework 扩展点、未使用但可能适合的正式能力，以及当前自行实现的内容是否必要。入口、实际时点、输入接收者、失败恢复和升级成本都纳入局部与整体判断；具体清单和验收见 [Framework 扩展能力选型与协作审查](04-Framework扩展能力选型与协作审查.md)。
