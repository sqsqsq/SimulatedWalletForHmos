# Story Extension 1.9.4：整体需求与有效结论

状态：需求范围已由用户在 2026-09-20 本任务的弹框及补充回复确认；本稿按用户随后“制定整体需求、正向重写 spec、编写可实施 design”的指令重写。本文是版本需求与用户决定的唯一入口。设计中的实现取舍由维护设计者负责，不冒充用户裁定。当前没有开始产品实施或真实 CLI 测试。

## 1. 目标与交付顺序

1.9.4 交付三个结果：Story 更容易读、Review 更容易作决定；已有需求发生变化后能自动更新相关产物；修复影响判断与交付正确性的关键缺陷。用户随后明确：表达优化要解决长期存在的长文过多、章节层级不丰富、表达生硬；Markdown 形式、图形与外部实践探索均服务于这些问题。机制残留按实际必要性清理，不以历史清单逐项删除作为版本目标。

用户选择的顺序是：**表达增强与关键缺陷先交付，更新能力随后交付**。这表示分包交回与验收顺序，不要求增加一轮真实 CLI。两个包完成后使用同一批两个 Case 验证，首次结果观察表达与可靠性，继续 update 观察更新效果。

性能目标是减少相关重复工作、防止退化；本版没有全流程半小时的承诺。Framework 所属问题形成具体上游交接，本仓不修改 `framework/`，也不在 Extension 复制通用阶段状态机或审查调度。

## 4. 统一验收条件

| ID | 可检查条件 | 证据层次 |
|---|---|---|
| AC01 | Story 主线清楚，独立问题有自然的小节层级，长段不混装多类问题，表达具体自然；图、表、文互补；Review 能区分待决与已定 | 用户审视成品与来源对照，不以图数/字数/标题数代判 |
| AC02 | 改图、压缩或局部更新后，条件、调用方、返回、失败责任、未决与验收含义保持 | 来源→更新前→更新后的语义核对 |
| AC03 | 无有效人工决定的评审动作不登记为 settled；建议不视为人选 | 真实决定原文与产物；结构验证不能独立证明 |
| AC04 | 用户提到的重要未取得材料被索取或有具体不适用依据；来源不可达不报无变化 | 行为轨迹及读取结果 |
| AC05 | 所有已约定来源有成功检查、无远端适用或明确缺口；不把自己归档的 Story 当新增上游需求 | 对接结果、版本与摘要 |
| AC06 | 模型辨明输入的含义和效力，沿业务关系推演隐含影响；修订最早责任真源并同步已有相关产物，保留有效手改和未变内容，既有 Plan 必要同步 | 变更说明、逐文件 diff、语义核对 |
| AC07 | 冲突、已定结论变化、大幅重组在执行前取得对应人选；不重问仍有效的历史决定 | 输入与交互记录 |
| AC08 | 更新前完整结果可恢复；人工意见保留并保持原议题语境；部分失败不报完成 | 离线异常与恢复验证、产物对照 |
| AC09 | 比较完整且无变化/无未完成更新/无新修订请求时快速报告并清理本次临时副本，不进入完整语义流程、不改业务产物；缺基线/取材失败不误报无变化；不生成新阶段产物或自动改代码/测试 | 比较、清理范围、调用轨迹与产物对照 |
| AC10 | 只有用户确认当前展示结果后才回写；本地单不访问需求系统 | 回写前后系统状态、确认绑定版本 |
| AC11 | 独立 review 入口、专用回流流程及其无消费者状态退出；评审内容处理在 update 内完整承接 | 消费者搜索、入口回归、实际回流 |
| AC12 | 两 Case 各完成一次初始评测/回流与一次 update 后评测/终止/另名回流；同一会话续行 | 会话标识、快照、事件与四份评测 |
| AC13 | 分开报告模型工作、脚本、审查、返修、人工等待与外部故障；没有无依据的全链重复 | 测量及行为解释，不按单个时间阈值自动评分 |

## 5. 实施步骤与依赖

设计入口：[整体实施设计](../../plan/1.9.4/2026-09-20-版本实施/00-整体设计与实施总览.md)。

设计按独立需求组织为七个可交回步骤：

1. A1 Story 表达优化：成文组织、作者送达、源图承接与原功能保护。
2. B1 关键缺陷修复：五类责任问题，含已确认的两条知识定义。
3. C1 识别变化与推演影响：模型取得当前依据与进展，区分变化、决定、冲突和保留项；取材/快照提供支持。
4. C2 关联修订与结果核对：修订相关真源和已有产物，保持人签与未决，说明可继续范围并支持恢复。
5. C3 统一入口与退场：启用 update，替换独立 review，接外部确认回写及适配合同。
6. T1 测试装置：第一次评测/回流后续同 session，最终另名回流。
7. T2 两 Case 验收与发布：按 D18 执行并由用户审视，核旧路径退出与发布一致性。

七步是维护设计拆分，不新增需求或改变 D02 的交付先后；需求 A/B 各一步、C 三步、共同验收支撑两步。各步交回评审后推进，A1/B1 不额外启动真实 CLI。当前授权是设计重写，真实运行待用户启动对应里程碑。

## 6. 待决与已知限制

- DLV-02 与 COMPAT-02 的准确新定义已确认，见 S-FIX §2；目标实际归档位置仍由目标知识所有者补齐，不能编造。
- 真实需求系统的渲染能力及目标仓对接实现不在本次环境中，不能声称已验证。设计安排读取能力合同并提供必要降级，首次目标接入验收要核实。
- 新增实现预算是设计估算，不是用户已签额度；开工前由设计评审核定，按 `test/story/AGENTS.md §5` 管理。
- Framework 的 revalidate 本身只执行脚本重验，但会在适用条件下生成当前材料的 verifier 请求，check-receipt 支持后续提交当前报告。update 由主模型对实际修改的适用阶段使用该请求派既有 verifier，再按原生接口闭环；无需另建审查者或将缺少自动重审作为本版常态限制。无变化/未修订/纯过程记录不派，当前材料已有有效 PASS 不重复派；FAIL 后真实返修按新材料再审，次数与耗时在 T2 单列。
- 目标宿主没有启用 verifier 或没有合法请求时如实报告审查未完成，不以自审、用户回写确认或历史 PASS 替代。本次已核源码和确定性证据读取，完整派审/回写/同步闭环接线仍须 C3 在隔离环境验证。

现有四份需求主稿以本总览的有效决定为准；参考图、历史扫描与归属存档保留作证据，不构成第二套需求。1.9.3 发布版本遗漏的修复不计入本版新增能力。
