## 怎么使用

这是功能目的与目标职责分工的长期清单，也是唯一长期维护的清单。每个父特性说明组合方式，每个子特性说明输入、实现、结果与验收；实现文件不能自行创造功能。功能变更先改本文件，纯实现替换保持功能ID；实现级变化不更新冻结存档——[归属判定](FEATURE-MAP.md)与[全量归属](FEATURE-CONTENT-MAP.md)均为 2026-09-11 轮诊断存档，事实变化由当轮漂移记录或全盘分析承载。

依据优先级：用户最新明确诉求 > 已确认需求/交付保护 > 当前获准的设计；release用于回查已交付能力，旧特性树与历史代码用于查漏，不自动成为现行约束。主要参考：[1.9.0](../../../../release/1.9.0.md)、[原特性树](../../../1.9.1/2026-09-07-Extension整体正向审查与重构/03-Extension特性树与实现方案审查范围.md)、[Step2.3](../../../../plan/1.9.1/2026-09-07-新需求四项/steps/02.3-Story写作流程重设计.md)、[维护约定](../../../../AGENTS.md)。2.3文档中的“待实施”状态落后于提交历史，此处以实际基线区分实施与验收。

“唯一实现”表示同一事实/决策/判据只有一个权威职责，不表示只能有一个文件、一个执行体或只能出现一次。作者指引、确定性脚本、语义审查可以共同承担一个功能，须说明各自新增的作用。直接运行Framework Spec而非/story时，知识功能仍适用，Story取材与归档不强制介入。

## F1 需求取材与范围确定

- **目的**：把外部需求变成经确认的本部件开发输入。
- **输入**：需求单或本地材料、用户决定。
- **目标实现职责**：模型分析充分性和范围；脚本取材导入、保存身份与人决定；子功能F1.1–F1.7顺序协作。
- **结果/消费者**：原始来源、已定范围、AR/design。
- **可检查的完成条件**：材料不丢、输入与派生不混同，范围能追溯。
- **需求依据**：release 1.9.0；用户adapt与2.3诉求。
- **子特性协作**：F1.1, F1.2, F1.3, F1.4, F1.5, F1.6, F1.7；共同使用同一来源/决定，不能各自维护平行真源。

<a id="f1-1"></a>

## F1.1 需求系统与本地起手

- **目的**：两种来源均可进入同一开发流程。
- **输入**：AR编号/本地编号、业务适配器。
- **目标实现职责**：story adapters获取外部记录；story_flow.cmd_init建骨架；本地编号跳过远程动作。
- **结果/消费者**：RR/SR/AR/inbox与单据身份。
- **可检查的完成条件**：本地不碰远程，重跑不覆盖已有输入。
- **需求依据**：release取材/本地接入。

<a id="f1-2"></a>

## F1.2 补充正文与格式转换

- **目的**：已有材料可被模型完整读取。
- **输入**：inbox原件、模型分类。
- **目标实现职责**：import_sources转换DOCX/文本并保留图片关联与原件；模型决定RR/SR/AR/UX归属。
- **结果/消费者**：规范正文、导入记录。
- **可检查的完成条件**：表格图片不丢，不支持格式明确报错。
- **需求依据**：release补料。

<a id="f1-3"></a>

## F1.3 图片身份与用途

- **目的**：图片能引用、能解释不用、改名不变成多张图。
- **输入**：原图、图意、采用决定。
- **目标实现职责**：materials按内容身份登记路径；import_sources注册/说明/used/unused；作者选择使用位置。
- **结果/消费者**：材料图片身份与可读引用。
- **可检查的完成条件**：只补图不覆盖正文，同图多路径一致。
- **需求依据**：release图文；既有图源保护。

<a id="f1-4"></a>

## F1.4 来源盘点与增量变化

- **目的**：知道材料缺什么及何时需重新判断。
- **输入**：材料清单、原件、轮次。
- **目标实现职责**：materials计算身份/摘要/待导入；模型盘点缺口；story_flow保存与确认关联的材料轮次。
- **结果/消费者**：最新输入基准与待处理缺口。
- **可检查的完成条件**：新材料被发现，自身派生写入不误开轮。
- **需求依据**：2.3-01；release中断恢复。

<a id="f1-5"></a>

## F1.5 需求与范围分析

- **目的**：讲清本部件承担什么及外部依赖。
- **输入**：原材料、部件画像、用户意图。
- **目标实现职责**：模型按init_analysis与ar_design规则分析；分析文件供关卡裁决，不成为独立业务真源。
- **结果/消费者**：范围建议、拆分依据、交接关系。
- **可检查的完成条件**：无材料支持的结论不当既定事实。
- **需求依据**：release范围分析。

<a id="f1-6"></a>

## F1.6 人定材料与承载范围

- **目的**：人能对具体结果作决定。
- **输入**：盘点、范围选项、用户回答。
- **目标实现职责**：模型展示结果；flow记录侧车、人选项、依据和承载份表；Framework承接交互工具。
- **结果/消费者**：可恢复的人决定。
- **可检查的完成条件**：不代签、不重复问已确认事项；新诉求回分析。
- **需求依据**：现行范围授权；用户确认结果。

<a id="f1-7"></a>

## F1.7 形成开发需求输入

- **目的**：提取稿可成为Spec输入且原文不丢。
- **输入**：已定范围、原AR、S4候选。
- **目标实现职责**：模型写design-draft；cmd_complete留原输入、提交候选、更新同轮基准；幂等重试。
- **结果/消费者**：AR/design与原始AR定位。
- **可检查的完成条件**：自身输出不冒充原始证据，部分失败可恢复。
- **需求依据**：2.3-01及四项返修。

<a id="f2"></a>

## F2 面向人的Story

- **目的**：一份自包含文档讲清需求、方案、行为与交付。
- **输入**：F1产物、Spec、知识判断、决策。
- **目标实现职责**：先理解与编排，再分章可靠落盘，最后整体核对；确定操作归脚本。
- **结果/消费者**：AR/story.md。
- **可检查的完成条件**：事实准确完整、关系一致、表达自适应。
- **需求依据**：用户金样认可；2.3目标。
- **子特性协作**：F2.1, F2.2, F2.3, F2.4, F2.5, F2.6, F2.7；共同使用同一来源/决定，不能各自维护平行真源。

<a id="f2-1"></a>

## F2.1 成文前原材料定位与初筛

- **目的**：动笔时能拿到来源及前提。
- **输入**：登记正文、原AR、范围。
- **目标实现职责**：sources切ATX及父前导正文；索引短ID/文件版本；模型稀疏记录取舍；不建Spec前视图。
- **结果/消费者**：source-index与source-selection。
- **可检查的完成条件**：保留未分配来源与父级上下文；短ID不静默换义。
- **需求依据**：2.3-01。

<a id="f2-2"></a>

## F2.2 Spec与写作设计衔接

- **目的**：Spec后整合一次本需求阅读主线。
- **输入**：原文、初筛、spec/knowledge-use/decisions。
- **目标实现职责**：Framework生成规格；sources after-spec预填元数据；模型形成story-template并反查来源义务。
- **结果/消费者**：运行时写作设计。
- **可检查的完成条件**：已知/未知区分，模板不成为内容上限。
- **需求依据**：2.3-02。

<a id="f2-3"></a>

## F2.3 按需材料送达

- **目的**：每章看到必要原文、范围与相关章。
- **输入**：编排、有效取舍、索引。
- **目标实现职责**：skeleton唯一写材料视图；显式多处引用共享正文，未分配只列索引；父级前提给位置。
- **结果/消费者**：chapters及精确读取入口。
- **可检查的完成条件**：缺源/过期/缺初筛在写前拒绝；不复制十份全文。
- **需求依据**：2.3-02；四项返修。

<a id="f2-4"></a>

## F2.4 正文表达与可靠落盘

- **目的**：十章协同而不重新决定十遍业务。
- **输入**：当前写作设计、章材料、原文。
- **目标实现职责**：模型自适应分节与表达；drafts保留正文；chapter只替换目标章，失败不覆盖。
- **结果/消费者**：当前正文与可恢复章稿。
- **可检查的完成条件**：正文可深化有依据关系，不因模板未列而删事实。
- **需求依据**：2.3-02。
- **子特性协作**：F2.4.1, F2.4.2, F2.4.3；共同使用同一来源/决定，不能各自维护平行真源。

<a id="f2-4-1"></a>

## F2.4.1 读者问题与章节职责

- **目的**：各级章节有独有阅读价值。
- **输入**：背景/术语/范围/方案/流程/功能/异常/验收/交付/附录。
- **目标实现职责**：稳定十章职责来自合同；模型为子节确定目的与互补关系；不固定下级目录。
- **结果/消费者**：可定位、可理解的叙述。
- **可检查的完成条件**：任一最小节有独有信息；重复整段不冒充完整。
- **需求依据**：1.9.0；2.1–2.3目标。

<a id="f2-4-2"></a>

## F2.4.2 图表与正文协作

- **目的**：用合适形式表达关系。
- **输入**：交互/条件/对象/状态、来源图。
- **目标实现职责**：模型按关系选形式；脚本落实已声明结构与图源引用；保留来源对应但不强制照抄画法。
- **结果/消费者**：表/图/文字互补的正文。
- **可检查的完成条件**：无人数阈值替模型选图；关键图关系完整。
- **需求依据**：用户自适应展示；2.3-02。

<a id="f2-4-3"></a>

## F2.4.3 验收与交付可操作

- **目的**：读者知道如何确认完成及谁接收。
- **输入**：原验收编号、交付要求、风险控制。
- **目标实现职责**：模型说明可观察条件/主责/控制对象及存量影响；脚本保留编号与必要凭据结构。
- **结果/消费者**：验收与交付章节。
- **可检查的完成条件**：不合并掉原验收身份；多种控制措施不压成一个开关。
- **需求依据**：1.9.0；用户9.3诉求。

<a id="f2-5"></a>

## F2.5 契约查阅附录

- **目的**：精确契约可查且不与Spec分叉。
- **输入**：Spec§9、knowledge-use、来源清单。
- **目标实现职责**：project从真源生成接口/数据事件配置/边界/规约投影，作者写必要解释和材料贡献。
- **结果/消费者**：附录五节。
- **可检查的完成条件**：投影保护；解释保留；理解行为不能全挪附录。
- **需求依据**：1.9.0；2.3保护项。

<a id="f2-6"></a>

## F2.6 标题引用与可读整理

- **目的**：归档后可读可追溯。
- **输入**：Story草稿、合同、图源、材料。
- **目标实现职责**：number/headings编号；lint检查具体路径/标识/坏图片等；意义由模型判断。
- **结果/消费者**：规范Story。
- **可检查的完成条件**：机械命中不代替语义；不为消警删业务事实。
- **需求依据**：1.9.0。

<a id="f2-7"></a>

## F2.7 写后整篇核对

- **目的**：发现跨章矛盾遗漏而不重写全部。
- **输入**：实际Story、原材料、编排、决策。
- **目标实现职责**：作者按来源反查、信息归属、关系结果和表达核对；修改回真源或对应草稿。
- **结果/消费者**：修正后的正文。
- **可检查的完成条件**：不是逐项自证台账；不强制找到错误。
- **需求依据**：2.3-03。

<a id="f3"></a>

## F3 决策与评审回流

- **目的**：让人看懂并决定真正影响产物的问题。
- **输入**：需求、设计、知识判断、人反馈。
- **目标实现职责**：模型发现与说明判断，脚本分层渲染保留人工内容，回流修订原责任产物。
- **结果/消费者**：review与处置结果。
- **可检查的完成条件**：人表态不被模型覆盖；未知不伪装已定。
- **需求依据**：release决策与回流。
- **子特性协作**：F3.1, F3.2, F3.3, F3.4；共同使用同一来源/决定，不能各自维护平行真源。

<a id="f3-1"></a>

## F3.1 发现并解释判断

- **目的**：明确问题、依据、建议、影响和未决。
- **输入**：材料冲突/缺口、工程事实、已有决定。
- **目标实现职责**：现行模型提示登记decisions；类别用于整理；新的系统性发现算法属后续步骤4待实现。
- **结果/消费者**：settled/open判断。
- **可检查的完成条件**：分类不代替发现；不为凑议题制造问题。
- **需求依据**：现行release；用户review诉求。

<a id="f3-2"></a>

## F3.2 生成评审件并保护人工区

- **目的**：人看到议题并可表态。
- **输入**：decisions、既有review人工内容。
