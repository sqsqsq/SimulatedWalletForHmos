# 知识能力适配需求审查意见

2026-09-24，维护设计者。审查对象：[需求正文](00-需求.md)及[版本范围](../00-版本范围.md)。本次核对现行 adapt Skill、adapt-scan、knowledge 解析器、三类知识 README、manifest 与作者任务入口；未实施改动、未运行真实 CLI。以下建议尚未替代需求中的已确认决定。

## 1. 结论

**方向正确，需求有必要；当前边界尚未闭合，补齐后再交付实施设计。** 目标是让安装升级的维护模型知道知识需要怎样适配，并让阶段消费模型取得有效知识，不是建设通用知识管理平台。

保留已确认方向：知识协议随机制升级；目标内容由目标维护；包声明能力要求；目标在知识文件登记承担的能力；人选择适配范围后由模型取证适配。无需另建安装状态机、文件指纹库或历史版本推断。

版本范围已经补充两项需求的共用来源与建议顺序，接受这个衔接方向。此前“尚未明确如何衔接”的担忧不再作为当前缺陷；设计时仍需把交付侧权威内容落实到产品文件，不能让消费模型读取维护 spec 的 R01–R03。

## 2. 实施前须补齐的要求

### K01：分清协议、覆盖与内容正确性

对应 §3.2–3.4、AC01/03/05。能力标识与要求版本可以证明登记状态，不能证明知识仍然正确。现行 knowledge 解析器检查结构和条目合法性，也不承担事实正确性判断。

要求分别定义：协议能否被当前机制读取；本项目适用的知识问题是否覆盖；内容是否经实际定义、调用及业务依据核实。脚本比较登记、引用和版本，模型判断内容与适用性。版本一致时不重复要求迁移，但仍允许在真实使用中发现事实漂移并修正。

验收：登记版本正确但关键定义缺失或与代码冲突时，语义走查不能判完成；仅无版本差异不代表内容通过。

### K02：台账全登记不等于目标全部接入

对应 §3.2、§3.6、Q4。保留“现有能力全部补登”的决定，但区分通用读写协议、特定业务涉及的知识能力、可选项目模式。两个模式依赖特定 SDK，不能变成所有工程的默认必备方案。

台账按能力目的和适用条件给出参考；目标按实际项目选择和扩展。Demo 文件拆分、域数量及具体模式不是通用完整性的标准。目录、文件名及模式专名不硬编码到通用分支。

验收：无相关 SDK 的异语言目标可以不采用 Demo 模式，目标自有模式仍被正常消费；不因未复制包内模式判知识不完整。

### K03：旧知识无新登记时，先识别，不直接判缺失

对应 §3.3–3.4、AC04。旧仓知识没有能力及要求版本字段，“拿登记比较即可”尚不能解释如何开始升级。

将无登记作为待识别事实：模型阅读目标已有知识，识别已覆盖内容，补关联后只修真实缺口。不能凭文件名推定，也不能因未登记重建整份知识。支持一份文件承担多项能力、数份文件共同承担一项能力；具体结构交 design 确定，不增加第二份激活清单。

验收：旧仓实际已有完整内容但无元数据时，保留原文和目标扩展，补必要登记；有部分覆盖时仅处理差异。

### K04：不适用决定应有适用范围和复核条件

对应 §3.3、§3.6、AC03。“登记过不再重复报出”应限定为相关要求和适用依据未变。能力增加适用面或项目业务发生相关变化后，需要复核受影响部分。

复用原决定，避免每次升级全部重问；同时保留决定针对的能力或面、依据和要求版本。语义变化由模型识别，不要求新增持续监控或代码指纹系统。能力整体不适用与部分面不适用不能互相覆盖。

验收：无相关变化不重复询问；新增适用面时能够显示差异，不被旧的整项不适用吞掉。

### K05：README 退出必须保护目标自有内容，并接替协议校验

对应 §3.5、AC05。通用规则迁回机制、旧索引退出的方向接受。现行 adapt 明确 knowledge 归目标，目标可能改过 README，不能直接按文件名批量删除。模型先区分通用协议与项目说明，将后者迁到合适知识文件，修正激活清单及引用后退出旧索引。

现行 knowledge.mjs 在 kind:index 分支检查 protocol。删除索引时必须明确新协议声明与校验的承担位置，否则会同时删除有效兼容性检查。机制安装脚本的写入边界与获授权适配模型的知识迁移行为分开描述。

验收：目标自定义说明不丢，旧引用不悬空，新知识仍接受协议检查；不为保留校验长期并存两套索引规则。

### K06：能力缺失、协议错误与业务依据不足分别处理

对应 §3.7、§4、AC05a/06/07。现行解析器对已登记文件缺失、非法协议、重复编号等会报错；这些不能统一降级为“不核值”。

| 情况 | 期望行为 |
|---|---|
| 可选能力不适用 | 按依据正常继续 |
| 当前需求需要知识但未接入 | 按任务取证；仍缺依据时明确影响哪些设计和验证 |
| 激活文件缺失或协议损坏 | 报出具体错误并进入修复，不悄悄忽略 |
| 关键业务决定未形成 | 保留准确未决，不编值，不声明相关设计完整 |

“无知识仓全链照常”应解释为正常进入流程、识别需求和缺口，不是任何需求都能无条件完成。阶段提示说明实际缺什么、下一步取得什么；已具备依据但作者未设计的情况不能借此放行。

### K07：统一适配主体、授权时点与事实来源

对应 §3.4、§4、Q5、AC02/04a。正文同时出现“人选范围后自动适配交回”与“初稿再确认后落盘”；“adapt 不写知识”也混淆脚本和模型。

建议沿 Q5：安装脚本只写机制；模型按人已选定范围取证并修改知识，交回结果和未确认项。遇到新增业务决定、冲突或超出已选范围时再问人，不重复确认已经授权的普通编辑。如果确需每项成品确认，应由用户明确并同步所有段落，不能留给实施者猜。

代码证明当前实现，业务语义由协议、需求或负责人证明；尚未实现但已确定的新能力应能进入设计。知识中分别表述现有事实、已定规范及待核内容，不把拟建能力写成已存在，也不因当前代码没有实现就判为不适用。

## 3. 验收补齐

保留已有首次、部分接入、跨版本及非钱包异语言目标场景。在既有演练中补下列观察，不默认增加长流程或新的测试平台：

| 场景 | 需检查的结果 |
|---|---|
| 有旧知识但无新登记 | 识别并复用，不重复生成，不覆盖目标扩展 |
| 适配中断后再次执行 | 从当前真实文件判断差异，保留已完成内容，不将未完成登记成通过 |
| 能力拆分、合并或文件移动 | 激活清单、能力关联、下游引用同步，旧入口退出；具体迁移关系在包中说明，不靠名称猜 |
| 登记完整但内容缺关键依据 | 走查发现缺口；版本比较不替代内容结论 |
| 机制安装成功、知识只完成部分 | 分别报告结果，说明受影响的流程和剩余动作 |
| 原不适用的相关条件变化 | 只复核受影响面，既不永久忽略也不全量重问 |

脚本离线正反例只证明比较、写入和错误处理；模型自动取证适配的效果需要实际模型演练或真实交回证明，不能把离线测试通过称为模型能力验证。具体演练范围和成本由 design 确定，真实启动另按现有授权流程。

## 4. 设计阶段可以决定的细节

能力台账和协议的具体路径、frontmatter 字段形态、差异报告排版、读取复用方式、具体测试组织均可留给 design；实施前应定清它们的生产者、消费者、版本比较含义和错误处理。比较知识要求的版本与包发布版本分开解释：不要求包每次版本变化都触发目标知识更新。

本审查不要求新增通用调度、状态管理、兼容框架或完整语义版本求解器。按现有激活清单、知识文件与模型工作流完成最小方案即可。

## 5. 处理与收口

需求维护者逐条处理 K01–K07 及验收补齐：接受的同步正文和验收；不接受的给出现有契约或用户决定依据。已确认的目录所有权、台账全登记和由人选适配范围等决定保持，涉及改变这些决定的建议单列确认，不将本审查当作已获新授权。

两项 1.9.6 需求共同验收“取得知识 → 正确理解 → 形成阶段产物 → 下游使用”，分别完成登记和作者提示不能替代整条效果验证。本稿只登记审查意见，未重写需求，未修改产品，未启动实施或测试。
