# 1.9.8 版本范围

2026-09-26 用户授权。**本版无任何功能需求**，解决一个项目结构问题：story 分支的仓根长期是 demo 工程形态，extension 源、维护域与 demo 代码三层混居，extension 的项目级文档只能挤在 `test/story/` 下。方案细化（拆步、逐文件动作、预算计量）另立 `test/story/plan/1.9.8/`，本页登记范围、关键决定与完成条件，不构成实施或真实 CLI 测试的启动授权。

## 背景与问题

| # | 问题 | 依据 |

| 1 | 根目录同时是 demo 工程（`01-Product`…`05-SystemBase`、构建配置、demo 文档）与 extension 开发仓，extension 项目级文档（维护契约、README）与 demo 的 framework 渲染物（根 `AGENTS.md`/`CLAUDE.md`）冲突，只能放 `test/story/` | 根目录清单 |
| 2 | 实跑 workspace 装配按**整仓黑名单拷贝**，demo 代码、维护域、extension 源一起进拷贝决策 | `test/story/scripts/run_multi_case.py:107-129` |
| 3 | 维护代码约 20 处直接依赖根 `framework/`（跑 harness、取 yaml 包、读根 `framework.config.json`），与"framework 本体不在本仓维护"的定位纠缠 | `test/story/scripts/run_case.py:1564,1632`、`test/story/tests/ext_workspace.py:20` 等 |

## 关键决定（用户 2026-09-26 会话确认）

### D1 extension 源落位：根目录 `doc/extensions` 原位保留，目录名不改

- 理由：测试域对 `doc/extensions` 的引用 100+ 处（含代码内字符串常量与 fixture 目录名），原位保留零改动；源码布局与消费仓安装布局一致；单一真源不产生第二份源。
- main 的 `doc/extensions` 是安装物（且为 0.21.0 旧版），story 根的是开发源——本版后两个角色物理分离。

### D2 demo/ 模型：完整业务仓，全部入库

`demo/` 是一个**完整集成了 framework + extension 的业务代码仓**（模拟真实消费仓）：

- 业务代码、构建配置、demo 文档、vendored `framework/`（含 2 处登记差异）、`framework.config.json`、宿主物化（`.opencode/.agents/.cac/.claude/.codex/.cursor` 中 framework 物化与 extension bridge）、demo 自己的 `AGENTS.md/CLAUDE.md/README.md` 全部入库；
- `demo/doc/extensions` 装**已发布版** extension 安装物：本版装当前已发布版 1.9.6（`test/story/release/1.9.6.md`）；后续发布后用发布内容覆盖升级，该过程同时作为 story-adaptation 升级流程的真实验证对象；
- 开发中的 extension 源**不进** demo/；实跑 workspace 仍是「demo/ 整体拷贝 + 根 `doc/extensions` 开发源覆盖」，与现行装配语义一致。

### D3 分支关系：main 与 story 各自演进，仅靠发布件衔接

- 不再互相 merge，无路径映射同步；main 上 app 业务后续演进**不追**入 story 的 demo/（已核实 story 业务代码相对 main 仅 62 文件小差异，以重构时点 story 内容为基）；
- framework 新发布件：main 先接入验证；story 的 demo/ 由「framework 发布件接入协议」（D4）跟进；
- demo/ 的知识样板只需与 demo/ 自身代码一致，不因 main 演进失真。

### D4 framework 发布件接入协议（AI 可自主执行的维护任务）

回答"不是人来操作，AI 如何知道如何做"：

- **触发**：a) 用户发起，告知发布件与版本；b) 维护会话自查——对比 `main:framework/RELEASE-MANIFEST.json` 与 `demo/framework/RELEASE-MANIFEST.json` 版本标识，不一致时**登记报告、不自动升级**，等用户给发布件；
- **执行**：在 `demo/` 内以同一发布件跑 framework-init UPDATE（对目标仓物化，产品自身机制，操作说明即 SKILL 正文）；2 处登记差异按 `framework.config.json` integrity 登记选「保留」；物化刷新后过 framework integrity 检查；
- **验收**：`demo/framework/RELEASE-MANIFEST.json` 版本等于目标；2 处差异在位；test/story 离线回归全绿；
- **登记**：接入完成写一行进 `test/story/EVOLUTION.md`（版本、日期、发布件标识、验证结果）；
- **失败路径**：UPDATE 决策点拿不准→带事实停等用户；离线回归失败→按 TEST.md 诊断，framework 行为变化引起的适配缺口回维护层另立需求，不在接入任务内顺手改。

extension 发布进 demo/ 的协议同构：发布收口（release 说明落地）后，以发布时点源为包对 demo/ 走 story-adaptation 升级，验收 `demo/doc/extensions/manifest.yaml` version 等于发布版。两条协议的完整文本落在根维护契约（D5）。

### D5 维护文档落位：契约上根，测试域留 test/story

- 根 `AGENTS.md` 重写为**维护契约**（由 `test/story/AGENTS.md` 升格：仓定位、目标结构、角色、D4 两条协议、红线指引）；根新增 `README.md`（仓定位与结构图）；
- `TEST.md`、`EVOLUTION.md` 留在 `test/story/`（与 cases/fixtures/scripts 同域，避免相对链接大面积断裂），由根契约索引；
- demo 的 `AGENTS.md/CLAUDE.md/README.md` 随 demo/ 迁移；根 `doc/` 只留 `extensions/`，其余（architecture、glossary、module-catalog、archives、features、业务复盘 md）随 demo/ 走；
- 根宿主目录收缩：`.opencode` 等物化产物进 demo/，根上仅留维护会话所需（verifier 子代理物化件与个人本地设置，后者不入库）；维护会话不再有 `/story` 等跳板，按契约直接读 SKILL.md 正文。
