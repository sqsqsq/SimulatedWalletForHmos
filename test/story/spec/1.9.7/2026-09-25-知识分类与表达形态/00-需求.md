## 2. 目标

1. 知识增删改只改知识文件与 manifest 的激活清单，extension 的机制、模板、测试零改动。
2. 机制按知识声明的类型与形态消费：加载、登记、送达、门禁、审查只引用协议规定并经加载器校验过的结构名，不点任何知识的名字，不写题材词，不引用未校验的节名。
3. 目标仓的模型能按类型、形态与 Demo 示例写出自己的知识，并被同一套机制消费；升级时能知道知识协议变了什么、自己的知识哪里不合。

## 3. 知识的分类与表达形态

### 3.1 形态是什么

形态指**机器读的正文结构**，不是读者，也不是题材。三类知识（`kind`）与三种形态（`form`）构成四个合法组合；每份知识在 frontmatter 同时声明两者。

| `kind` \ `form` | `facets`（分面） | `halves`（上下篇） | `entries`（条目表） |
|---|---|---|---|
| `facts` | 查找型：项目已有实现、封装、惯例；首装的部件画像也是它 | 方法型：要多步推导的项目方法 | — |
| `constraints` | — | — | 规约 |
| `patterns` | — | 设计模式 | — |

不设第四种形态：部件画像与工程能力结构相同（都是分面），差别只在 `applies_when` 与读者；方法型事实与设计模式正文结构相同（两个一级标题分篇），差别在 frontmatter 有没有 `roles` 与下游怎样消费，靠 `kind` 区分。

### 3.2 四格各自怎样描述自己

| | facts × facets | facts × halves | constraints × entries | patterns × halves |
|---|---|---|---|---|
| frontmatter | `name`、`kind: facts`、`form: facets`、`applies_when` | `name`、`kind: facts`、`form: halves`、`applies_when`；不写 roles | `name`、`kind: constraints`、`form: entries`、`applies_when`、可选 `domain`（须等于条目前缀） | `name`（即模式 id）、`kind: patterns`、`form: halves`、`applies_when`、`roles`（必填）、`optional_roles`、`coordinator_role`；`depends_on` 给模型读，机制不读 |
| 机器读的结构（加载器校验） | 至少一个二级标题；正文不得有「# 上篇 ·」一级标题 | 两个一级标题「# 上篇 · …」「# 下篇 · …」，各篇至少一个二级标题；不核节名、序号、读者字样 | 表头含「编号」「约束」的表，列按名取（强制力、命中条件、处置、验证、探针可省）；编号「前缀-两位」，一文件一前缀；落法附注以 `**编号**` 起头 | 与 facts × halves 同一解析，另核 `roles` 非空、`coordinator_role` 在 roles 内 |
| 模型读的写法（protocol，不校验） | 一面一能力，每条写用哪个实现、在哪、怎么用；画像的两面按初析要判的两问组织 | 篇名后写读者阶段；上篇给设计侧、下篇给实现侧；节按项目方法写，Demo 的九节只是示范，不是要求 | 现行 §五：一条一个可判定要求，命中条件、边界、例外、验法 | 现行 §六：上篇适用与选型、下篇结构与落地 |
| knowledge-use 登记单元 | 面名 | 篇名（上篇 / 下篇） | 条目：applicable、requirement、contract 或 impact、waived | 单元、候选、信号 |
| 下游消费 | 任务包按用途与面名列出；作者登记用了哪一面、拿它做了什么；审查回查；不投影 | 任务包对 halves 一律提示「读读者含本阶段的那一篇」；spec 登记上篇、plan 与 coding 读下篇；不投影 | §10 投影、验收的 `knowledge_rule`、plan `must`、探针、审查并列表 | §11 投影、plan `files[].pattern/role`、coding 读下篇 |
| Demo 示例 | `knowledge/facts/engineering-capabilities.md`（能力）、`knowledge/facts/component-profile.md`（首装画像） | `knowledge/facts/event-tracking.md` | 八份任一；`knowledge/constraints/observability.md` 示范探针列 | `knowledge/design-patterns/decision-tree.md`、`page-interaction.md` |

### 3.3 写法要求

- 三类知识共同：`applies_when` 写清何时读、回答什么；开头一句说它帮读者做什么决定；正向陈述、只写确定的内容并给依据位置；同一事实只写一处；**写到模型找得到为止**——只写模型从代码里找不到或会找错的（生效入口、约定、命名、落点），能检索到的签名、全路径、调用链不写；示例只示范形状，一个就够，不写被测材料原句。
- protocol 与代码不一致处在本版收口：`domain` 写入 §五；`depends_on` 标为「模型读、机制不读」；探针列改为「列可省，有列而某条无探针写『无』」；读者字样与节号连续标为写法约定、机制不核。
- Demo 的十三份全部显式写 `form`，每格至少一份达到示范质量；protocol 的四格写法各指向对应 Demo 文件。

## 4. 机制怎样按类型与形态消费

### 4.1 加载器

- `form` 必填，取值封闭（facets / halves / entries），`kind × form` 只认 §3.1 的四格；缺 `form`、值不在集合、组合不合法都按文件报出并给改法。不从正文推断形态。
- 声明与正文不符即报：facets 的正文出现「# 上篇 ·」；halves 缺任一篇或篇下没有二级标题。
- 错误沿现有方式收齐一次报出；解析结果每个对象带 `form` 与登记单元，下游只看解析结果。
- selfCheck 四项不变，仍按 kind。

### 4.2 知识使用登记

- 骨架与校验按登记单元：facets 列面名，halves 列「上篇 / 下篇」，错误信息用对应标签；YAML 键 `facet` 与 `schema: 1` 不变；投影无变化。

### 4.3 任务包、门禁、审查

- 只引用经校验的结构名（kind、form、篇、面、条目列名、roles、applies_when）与机制自己的产物出口（spec §9.4、plan 埋点小节、`must`、`files[].pattern/role`）。不引用节名（应用步骤、使用约定、完成判断、反模式等）、任何知识的角色名、题材词。
- 退出与替代：

| 现文 | 处置 |
|---|---|
| spec 任务包「找用途写到统计设计的那份，重读它读者含 spec 的上篇」「按那一篇的应用步骤逐条回查」「衡量什么率或分布、要算它需要哪几类结果」 | 改为按 form 的通用句：按 `applies_when` 找回答本节问题的知识；form 为 halves 的读读者含本阶段的那一篇；写完按那一篇自查。形状只说「H4 下先一段定义，再放带『统计点』列的表」，不复述定义应含什么 |
| plan 任务包末三句、审查两句里的「使用约定与完成判断」「项目知识点名的角色」 | 改为「按读者含 plan 的那一篇核：项目规则算得出的字段是不是具体值」；角色句删除（facts 无 roles） |
| spec 门禁总述与定义段的内容清单 | 保留结构判据（缺总述、缺定义段），措辞不写内容应含什么 |
| plan 模板示例里的「尝试标识」「结算方法」 | 改为不带角色词的中性叙述或占位 |
| coding 作者页「protocol 第五节」 | 改为 §六，并写「form 为 halves 的下篇」 |
| spec §9.4 形状门禁、统计点解析、plan 埋点小节逐结果核方法与 must | 保留，这是产物出口，归机制 |

### 4.4 测试

- 退出对 Demo 知识内容、面名、节名、与模式同纲的断言；fixture 不写死面名，从加载结果取。
- 机制专名扫描的词表从激活的十三份知识动态派生（name、面名、节名、角色名），不再写死。
- 新增行为测试：在中性工作区新增一份 facets、一份 halves 事实，改一份 halves 的全部节名，删一份事实——`doc/extensions` 除 `knowledge/` 与 manifest 外零 diff，任务包、骨架、门禁、审查照常。

## 5. adapt 怎样指导目标仓

### 5.1 方法页

按四格重排 `skills/story-adaptation/reference/knowledge-adaptation.md`：现有五步是主干，「取证并写」展开为四格，每格四要素——何时用这个形态、到哪取证、照哪份 Demo 示例、怎样走查。首装的部件画像是 facets 格的第一小节（`applies_when` 回答本部件是谁、与谁交互；走查用一份上游材料判归属）。只读检查的输出增加按 kind × form 的计数，作为交回的一部分。

### 5.2 升级后确认

`adapt` 不加独立命令字。流程：装机制 → `--check` → 落盘机制交回 → 算两件事 → 停一次问人。

- 两件事：一是演进记录里晚于目标 `knowledge_adapted_for` 的条目；二是只读检查按当前协议核目标每份知识的结果（缺 form、形态不合、缺 applies_when，按文件列）。
- 任一非空就把内容摆出来问「现在做知识适配吗」：选做，进入方法页流程；选稍后，不写任何东西。两者都空只报一句「知识与当前协议一致」，不问。
- 「根据目标项目情况」只用只读检查结果，不做内容指纹，不猜业务。

### 5.3 演进记录与目标登记

- 演进记录归 adapt：`skills/story-adaptation/reference/knowledge-changes.md`，按扩展版本分节，每节只写知识协议变了什么（新增或改变的类型、形态、字段、结构要求）与目标仓要做什么。只由 adapt 读；知识正文、protocol、story 机制里都不写演进；不另设协议版本号，用扩展版本。
- 目标 manifest 加目标所有的字段 `knowledge_adapted_for: <扩展版本>`，与 `name`、`provides.knowledge` 同归目标；知识适配交回时由模型写，脚本不写。
- 加载器只认当前协议，不按版本分支；不写迁移脚本，不记进度或状态；旧结构直接报当前协议的错误，改法在演进记录与方法页里。

### 5.4 内网指南

新写 `内网适配指南-1.9.3升级1.9.7.md` 替代 1.9.3→1.9.6 指南：机制部分自动；知识部分只写哪几份知识落在哪一格、按方法页哪一节写、补 `form`；内网取证附表按篇不按节名。
