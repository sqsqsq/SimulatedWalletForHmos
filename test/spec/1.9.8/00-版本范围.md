# 1.9.8 版本范围

2026-09-26 建立；2026-09-27 按用户讨论决定修订。本版保持 1.9.7 的需求协作行为，完成 Extension 开发仓、demo 与维护域分离，以及相应安装、装配和维护操作。实施设计见 [总览](../../plan/1.9.8/2026-09-26-整体设计/00-总览.md)。本次授权修改 spec/plan，产品实施与真实 CLI 起跑分别按对应授权执行。

前置为 **1.9.7 最终验收并发布**。P1 已将维护材料从 `test/story/` 迁入 `test/`，开发源/消费工程分别位于 extensions/demo；P1 返修评审结论见当前评审记录。证据路径保留观察时布局，Markdown 链接指向当前材料。

2026-09-28 已确认 R197 为 `c026a70497b511b399c7e15dabd153f852b3a2fe`，见 [发布说明](../../release/1.9.7.md)。开工前两处归属的定案见 [设计裁定](../../plan/1.9.8/2026-09-26-整体设计/评审意见/2026-09-28-开工前疑问设计裁定.md)。

## 1. 问题与事实

| 问题 | 已核事实 |
|---|---|
| 开发源、业务 demo 与维护域混居 | 根为业务工程，开发源在 doc/extensions，维护契约在 test/story |
| workspace 按整仓排除复制 | run_multi_case.py 同时处理业务、维护和运行态目录 |
| 路径角色混用 | run_case.REPO_ROOT 可指隔离 workspace；ext_workspace 的根为维护仓，两者不能统一替换成 demo |
| 源码上提破坏 adapt 定位 | adapt-scan 当前依赖源侧 framework.config.json；配置迁入 demo 后此条件不成立 |
| 发布件及本地定制维护 | framework 为 3.0.0，opencode adapter 登记和 verifier 模板有两处本地差异，依据为 test/story/AGENTS.md §2 |
| 分支职责分化 | main 验证 framework 接入，story 维护 Extension，后续按发布件衔接 |

独立 render-agents-md 默认调用入口生成器并写宿主 bridge（framework/harness/scripts/render-agents-md.ts、utils/instance-skill-bridge.ts）。目前未证明 UPDATE 编排调用这条写入链，因此升级协议按实际差异验收，不规定升级后固定重装 Extension。

## 2. 目标与决定

| 能力 | 结果 |
|---|---|
| A 结构分离 | 根 extensions 开发源、demo 完整消费工程、test 维护域；main 清除 Extension 安装物 |
| B framework 接入 | main/demo 版本漂移可见；实际发布件在 demo 按 framework-init UPDATE 接入并验证 |
| C 安装与测试装配 | 发布版装 demo，开发版装隔离 template/workspace；共用确定性安装动作 |

### D1 开发源上提

`doc/extensions` 用 git mv 上提为根 `extensions/`。本版消费安装位按用户 2026-09-28 裁定固定为 `doc/extensions`；保留既有配置读取，不提供自定义安装位能力。引用按开发仓、demo 消费工程、隔离 workspace 三类角色处理，fixture 消费形态保持。

`story adapt <project_dir>` 不变。源从执行脚本自身位置取得，目标使用传入工程位置；源侧不依赖 framework.config.json，不增加目录搜索、自动猜源或旧布局兼容。

### D2 demo 为完整发布基线

业务代码、配置、文档、framework、本地定制和宿主物化迁入 demo。版本化文件入库，本地依赖和构建运行态按既有忽略规则处理。

本版 demo 初始化采用 **1.9.7 最终发布内容**。机制、知识、原有入口及扩展段绑定同一发布提交，分别与 1.9.8 开发源验收。demo 不要求提前具有 1.9.8 新增的两份入口。

1.9.7 发布时仍为旧布局，首次落位在一次性初始化步骤中按真实发布文件安装并留清单；正常安装工具不保留历史 commit 或旧格式分支。初始化与后续安装共用确定性文件写入动作，见 plan 安装分册。

### D3 分支职责

main 与 story 各自演进，不互相 merge 或进行路径映射同步；main 业务演进不自动追入 demo。main 删除 Extension 安装物及专有入口，保留 framework、业务和其他宿主能力。组合兼容由 story 验证及真实目标仓承担。

### D4 framework 发布件接入

- 用户提供发布件，或漂移脚本比较 main:framework/RELEASE-MANIFEST.json 与 demo/framework/RELEASE-MANIFEST.json，报告版本差及接入指引，不自动升级。
- 按实际发布件的 framework-init UPDATE 在 demo 接入配置和物化产物；两处本地定制按实际 init.task_decision 保留并核结果。退役的 integrity.drift_allowlist 不作为保留依据。
- 按工具实际支持完成发布件/物化校验、维护回归和差异核对；失败回对应责任方。根 verifier 装置由 demo 对应物化件同步，接入结果登记 test/EVOLUTION.md。
- 单独调用入口渲染命令时核实际写入面；不把其行为泛化为全部 UPDATE 的行为。
- 若实际升级/渲染产生入口冲突，按目标已装版本的 manifest 划分所有权：未登记的 Framework 入口核原生物化结果，已登记的入口只对冲突文件恢复同版映射内容并留证。无实际差异不增加动作，不把开发源装进发布基线。

### D5 维护入口与文档

根 AGENTS.md 承担仓定位、操作协议和索引；详细角色、不变量及预算唯一位于 test/AGENTS.md。更新其中随迁移变化的路径和失效事实，保留有效原则。根 CLAUDE.md 指向根契约，README 说明结构。

四份 tracked 消费钩子配置 `.claude/settings.json`、`.cac/settings.json`、`.codex/hooks.json`、`.cursor/hooks.json` 及关联脚本随消费工程进 demo，不按文件名归为根个人设置。Codex 历史 Stop command 的旧机器绝对路径改为消费根相对命令，属于 AC03 的迁移必需例外，其余键与脚本保持。

P1 就位根 AGENTS 最小维护入口及 CLAUDE 指针，P3 完善操作协议。维护者据契约遵守 demo/framework 只读，设计者核本次迁移保持；根不保留失效消费钩子，不声称拥有已迁走的写保护。真正隔离由宿主实际沙箱能力承担，本版不增加维护守卫。

demo 的 AGENTS/CLAUDE/README 随消费工程迁入。安装按 Extension 的 story-ext 标记区处理扩展段，区外保持，源为安装版本自身的 AGENTS.section.md。根 doc 内容分别进入 extensions 或 demo/doc，空容器退出。

### D6 1.9.8 入口分发

原四份 Story bridge 收进 extensions/bridges，补齐 cursor 与 agents 两份。manifest 每项使用 target/source 映射：source 相对扩展源，target 相对目标工程；安装前检查全部源及目标范围。

adapt 按映射分发和自检，宿主无关内容保持。四份既有入口在 doc/extensions 固定布局下保持已发布语义。根 Story bridge 退出，根 verifier 装置不入 bridges。

Framework 独立入口生成器作为已核事实记录，本版不改其实现。2.0.1 的原生入口物化交接由该版承担。

已存在的 `.agents/skills/story/SKILL.md` 与 `.agents/skills/story-adaptation/SKILL.md` 均先随 Framework 生成物迁入 demo，归 R197 物化保持面，不属于 R197 四份 bridge 清单。开发 template 安装 1.9.8 时仅 story 被现有六份映射接管；story-adaptation 保持 Framework 生成入口，不增加第七份映射。main 清理时二者若存在均随 Extension 消费职责退出，实际不存在则登记事实。

### D7 维护域与测试装配

`test/story/` 上提为 `test/`；skill 名、suite 名、output/story 等运行语义保持。历史材料不批量改写；当前入口、命令和配置随迁移更新。1.9.7 已退出的独立内网指南不恢复，升级指引继续由 adapt 演进记录承担。

固定装配顺序：**检查 demo 发布基线 → 复制到隔离 template → 在 template 安装当前开发源 → 校验 → 复制到各 Case workspace**。开发源包括当前未提交修改和新增文件，排除明确运行态；发布源由调用者从指定发布提交导出。demo 装配前后不变，不执行开发版替换或测试后还原。

发布安装中途失败先按安装清单保护人工修改并恢复本次写入面，重新通过预检后才重试；template 失败直接重新装配。共同安装函数、源集合及恢复表的唯一实施定义见 [安装分册 §1](../../plan/1.9.8/2026-09-26-整体设计/04-步骤4-新增脚本与workspace装配重构.md#1-统一安装动作)。

维护目录出现在 demo 顶层时报结构漂移；运行态按既有职责排除，保留 hooks 依赖。失败 template 不启动 Case，修正后重新装配。正式发布时才向 demo 安装发布源并入库。

## 4. 验收条件

- AC01：git mv 迁移且代表文件历史可追溯；迁移和本地文件清单完整。
- AC02：开发源对照 1.9.7 发布基线，业务机制/知识保持；允许改动仅 manifest/bridges、adapt 定位分发、演进及必要入口说明，逐项对应范围 #11。
- AC03：demo 业务、framework/本地定制及消费配置与迁移前一致；安装面、扩展段和迁移必需配置单列核对，其余保持。本地依赖另核 Junction/符号链接目标可达，按新消费根重建缓存链接；字节相同不代替链接有效，不提前要求范围外的 HAP 构建。
- AC04：demo 基线为最终发布的 1.9.7，机制、知识、发布时入口和扩展段对应同一提交；不拿 1.9.8 开发源作相等基准。
- AC05：开发源六份 bridge 与映射齐全；adapt 自身取源，在独立目标安装/自检成功；配置、知识、对接和无关宿主内容按所有权保护。doc/extensions 固定安装位的实际入口命令可执行，规范化路径贯穿脏保护/写入/自检；source 在写入前确认为可读文件，目录误作源零写入失败。
- AC06：demo→template→开发版安装→Case 演练通过，安装面同源、hooks 可加载；失败 template 不起跑；demo 文件及 git 状态前后不变，运行期相对路径正确。
- AC07：引用清点覆盖开发仓、demo、workspace，以及 parents[n]、相对基点、回灌和源码快照；有效消费路径保留，当前失效引用退出。
- AC08：相关离线测试、最终全量 pytest、失效形态、预算和修改脚本语法检查通过；开发版检查使用开发版装配目标，不能用旧 demo 证明新源正确。
- AC09：根维护文档、TEST 与当前契约反映实际结构；路径/链接有效，退役指南不恢复。
- AC10：framework 接入及 Extension 安装发布协议包含输入、动作、验收、登记和失败处理。
- AC11：main 专有安装物/入口/扩展段退出，framework、业务和其余宿主内容保持；按精确文件清点，不删除整个宿主目录。
- AC12：漂移脚本区分同版本、版本差、缺文件/解析失败，并给有效指引。
- AC13：1.9.7 发布身份、首次安装清单、依赖就位、内容核对和 demo 基线入库过程可追溯。

AC06 是离线装配证据，不宣称实跑业务已验。本版不自动启动真实 CLI。预算按 [维护契约 §5](../../AGENTS.md#5-维护预算与分级复核)，各域分别计量，移动不计净减，估算和初始稿对照见 plan 总览。

## 5. 边界

本版不修改 framework 本体，不实施 2.0.1 功能，不增加无人值守能力，不扩展 main 业务。demo 本次以 1.9.7 为安装基线；后续发布覆盖按已建立协议另行执行。hvigor/ohpm 业务构建验证保持原里程碑安排。
