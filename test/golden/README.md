# test/golden：两组金样正本

金样是用户审定过的**目标效果**：拿被测产物与它并排看，需求是否完整准确、关系是否清楚、形式是否适合、责任与交付是否可判断。
它给人对照效果，不当判据的机器否决锚；判据对错按真实依据与中性正反例判。

## 怎样用

- 两组均保留当时审定的 Story、业务 Review、Spec；车钥匙另有 Plan。2.0.5 的 auto 初段终点是 Story 系统送审，第二段是一次 update；car 止于 Plan。当前候选只在实际授权范围内比较，旧载体用来反查议题、依据与后果。依据见[当前评价标准 B7](../regression/extension-acceptance.md#b7-统一story业务交付)。
- 自动充值分两段比：首段按会议保留 200 元；只有第二段实际取得且有权的改版依据才按 300 元核规则、协议、验收与变更说明。两段都填 200，即使表格与金样相同也漏了更新；用正文或验收表准确同步本段协议、规则、验收并留下替换依据，同样可达标。建约明确失败与超时结果未知分别核，不能把结果未知直接当作可再次扣款。
- 车钥匙按车主、接收方、当前钥匙状态和责任方核撤销及断网后果。页面形似金样却把云端撤销写成离线端立即强制下线，缺有权来源时判偏离；用状态表说明车辆侧撤销即拒、实收 48 小时裁定后对方设备卡片的收回期限、车厂强制下线仍待定，可与旅程图等效。没有 48 小时答复仍核 24/48 冲突是否得到处理。关闭应用再打开按实际人答核，不能扩大成设备重启或重装；实有的 D5/D8 未决须评价是否保留。
- 对旧 Review 逐议题反查本版相关 Story 正文、流程/异常、验收、原生决定/gap。业务独审报告与蓝图技术评审投影各按其职责取证。保持历史正文、图、原审定身份及评分；导航更新不构成业务正本再审定。
- 金样与维护分析留在评价域，不进入被测 Case，也不复制进运行工作区。
- Story 材料清单里的链接按消费工程需求目录 `doc/features/<单号>/` 写，在本目录里点不开；仓内可点的权威输入在各组 README 的来源对照里。
- 三张 Mermaid 在正本里保持 Mermaid 形态，不需要 SVG；综合阅读图在 Story 正本里是放置小节末尾的空阅读槽（正式形态），依据写在 SVG 的 `<metadata>`，各组 README 给独立阅读入口。车钥匙 spec §5.3 #1 由表承接，承接位置登记在写作设计里（金样只放目标产物，不含写作设计）。
