# Story Extension 使用说明

Story Extension 是挂在 AgentMaison Framework 上的需求开发流程：从一个需求单号起，取材料、和你确认范围，生成规格（Spec）、面向评审的需求叙事（Story）与评审记录（Review），承接评审意见与材料变化，并把目标工程的知识带进后续设计、编码、检视与测试。

- 用 `/story` 做需求：读第 1、2 部分。
- 把 Story 装到或升级到业务工程：读第 3 部分。
- 想了解规则与机制：读第 4 部分。

## 1. 快速上手

1. 目标工程已接入 Framework 3.0.0 并装好 Story 1.9.8（当前发布版）；没装的见第 3 部分。
2. 在 AI 会话里说 `/story init <编号>`，之后按 AI 的提问作答。
3. 规格与需求文档通过交付门后，系统单选「归档送审」或「进入 plan」，本地单进入 plan。

文中的路径都指目标工程里的位置：每个需求的目录默认是 `doc/features/<编号>/`，实际以 AI 给出的路径为准。本仓 `story-1.0` 分支的 `demo/` 是装好 Framework 3.0.0 与 Story 1.9.8 的示例工程。`story` 分支是 2.0 开发线，它的 `demo/` 已换成 Framework 3.1、仍装 Story 1.9.8，这一组合在适配中、未经验证，不作示例或安装来源。

### 1.1 命令

| 命令 | 什么时候用 |
|---|---|
| `/story init <编号>` | 开始一个需求。`AR` 开头的单从需求系统取材；其他编号（问题单、工单）是本地单，材料由你提供 |
| `/story archive <AR>` | 系统单送审：把 Story 与 Review 上传需求系统 |
| `/story update <编号>` | 已有产物之后，上游材料改版、评审意见回来、你有新决定，或有人直接改过文档 |
| `/story restore <AR>` | 撤回上一次归档对需求系统正文的覆盖 |
| `/story help` | 输出流程说明 |
| `/story adapt <目标工程>` | 把 Story 装到或升级到另一个工程，见第 3 部分 |

### 1.2 一次需求怎么走

1. **起手**：`/story init <编号>`。系统单由 AI 从需求系统逐级取回 AR、SR、RR 三份正文；本地单不连需求系统，没有线上归档，交付终点是仓内的规格、Story 与 Review。
2. **材料**：AI 盘点完材料后问你一次；要补就把文件放进它给出的收件目录。
3. **会议**：交了需求澄清会的转写、且会上有要人定的话题时，逐个话题选一项。
4. **范围**：选整体承载或 AI 给出的某个切法。
5. **生成**：AI 写出本需求的范围输入 `AR/design.md`、规格、Story 与 Review，过门禁与审查。
6. **交付之后**：系统单选归档送审或进入 plan；本地单进入 plan。
7. **评审**：评审人读 Story，在 Review 上表态。
8. **更新**：评审意见回来或材料变了，用 `/story update <编号>`。

### 1.3 AI 在哪停下来问你

| 何时 | 你怎么答 |
|---|---|
| 材料确认：盘点后第一轮一定问，导入后仍缺料会再问；每次 `/story update` 也先问一次要不要补料 | 放好文件后选「材料已放进 doc/features/<单>/inbox/，请导入」；材料齐了选「现有材料就是全部，开始需求分析」 |
| 会议裁决：有要人定的会议话题时 | 每个话题选一项，确认参会人角色 |
| 范围确认：需求分析后一定问 | 见 1.4 |
| 术语确认（Framework）：写规格时 | 逐条核对术语与所属模块 |
| 个人设置（Framework）：阶段入口需要时，如视觉 provider | 从候选里选 |
| 查无此单：系统单的编号查不到 | 确认或更正单号 |
| 交付之后怎么走：交付门通过后问一次 | 系统单：归档送审或进入 plan；本地单：进入 plan |
| 归档、恢复：覆盖线上内容前 | 确认或放弃 |
| update 中新依据与其他仍有效的来源冲突，或要改已经承诺的事 | AI 把两边来源并列、登记成议题；你定用哪一边、怎么改 |

有编号选项时回编号即可；也可以说「按推荐」，它只对当前这一问生效。
门禁反复报同一个问题而 AI 改不动时，它会说明卡在哪一条、缺什么、需要谁提供，请人接手——按它说的补上信息，或找对应的人。

### 1.4 定范围怎么答

- 整体做：选「按当前范围整体承载」。
- 选一个 AI 给出的切法，再选本单承载哪一份。
- 想要的切法不在里面：直接说你的拆法，AI 回到分析补上再摆给你选。

定完之后 AI 写出 `AR/design.md`，后面的规格与代码都以它为界，值得过目它的范围一节。

### 1.5 评审怎么表态

在 Review 的每条议题下，「评审结论」选「同意 / 需修改 / 暂缓」；要改成什么、选别的做法、为什么暂缓写在「修改意见」。填写位不预选任何一项，议题里的建议不等于已选。议题之外的发现写在末尾「其他意见」，一条一个编号。表态回来后跑 `/story update <编号>`。

## 2. 常见问题

**Q1 第一次用系统单，提示要 token？**
把需求系统的访问 token 发给 AI 即可，它写入你的用户级配置，以后不用再配。它会先从目标工程的对接实现和本机配置里找，找不到才向你要。Demo 工程的对接是本地模拟，不需要真实 token。

**Q2 材料能放什么格式？**
`.docx`、`.md` / `.txt` / `.log` 等文本和界面设计图可以直接放。PDF 这类脚本转不了的，AI 读得懂就自己转写，读不了才请你给可读版本。原件都留档。

**Q3 有需求澄清会的录音转写，怎么给？**
把转写 `.docx` 和其他材料一样放进收件目录。会上有要人定的话题时，AI 在定范围之前停一次，逐个话题给推荐与选项；会上没收敛或你选「保持待定」的，登记为未决议题。触发条件见 4.3。

**Q4 中断了、换了会话，怎么继续？**
告诉 AI 要继续的编号。进度记在需求目录的流程契约里，不在对话里，AI 会先查出走到哪、下一步做什么再接着做。

**Q5 已定的范围想调整？**
告诉 AI 你要重新定范围，它会重开范围确认；范围定了再用 `/story update` 更新已有产物。规则见 4.5。

**Q6 Story 能改措辞吗？**
告诉 AI 改哪里，它改那一章并重新登记，别的章不动。附录里派生的几节要改的话改它的来源（规格或知识判断）。你直接改过的文档，下一次 update 会把它当作一项变化读进来。见 4.2。

**Q7 撤回这一轮 update 和 `/story restore` 有什么区别？**
要撤回本地这一轮的修改，告诉 AI 撤回本轮；要撤回上一次归档对需求系统正文的覆盖，用 `/story restore <AR>`。两者的规则见 4.5。

**Q8 规格之后的 plan、编码、检视归谁推进？**
由 Framework 按它的推进策略推进：在你已有的授权范围内往下走，缺少下一阶段的授权时停下来确认。见 4.4。

**Q9 目标工程没有配审查员会怎样？**
照常交付，但交付和更新时会如实写明「没有经过独立语义审查」。见 4.3。

## 3. 安装与升级（移植到业务工程）

在**来源工程**里打开 AI 会话，指定目标工程：

```text
/story adapt <目标工程根目录>
```

- **前置**：目标工程已接入 Framework、是 Git 仓库的根，这次要覆盖的路径上没有未提交的改动。有未提交改动时 AI 会列出路径，由你自己提交或暂存后重试；
  它不替你提交或暂存。
- **首次还是升级**：目标没有扩展的 `manifest.yaml` 就是首次安装，有就是升级。
- **从哪装**：用 `story-1.0` 分支 `demo/` 里的发布版（在该 `demo/` 下打开会话），或另一个已适配的业务仓。`story` 分支的 `demo/` 是 Framework 3.1 接入基线，
  组合尚未验证；维护仓的开发源 `extensions/` 也不是安装来源。
  来源包 `manifest.yaml` 写着 `adapters: stand-in` 的是替身包（Demo 就是），没有这个键的是业务仓，两者对接实现的处理不同（见下表）。

| 部分 | 归谁 | 安装或升级时 |
|---|---|---|
| 流程机制（技能、钩子、规则、合同、核心脚本、宿主入口） | 来源 | 脚本整份替换 |
| 需求系统对接实现（`skills/story/scripts/adapters/`） | 看来源 | 替身包来源：不给也不覆盖，目标用自己的实现（首次接入要自己实现，或从已有业务仓复刻）；业务仓来源：整份换成来源版本 |
| 知识（`knowledge/`） | 目标 | 脚本不读不写；AI 按知识适配方法，从目标工程自己的代码与需求出发写和改，不复制来源工程的业务知识 |
| 工程名称、描述、对接来源、已适配版本、知识激活清单（`manifest.yaml` 里） | 目标 | 保留 |

- **首次安装**你要确认一次：AI 扫描目标工程写出的部件定位知识（本部件是谁、职责边界、和谁交互）、工程名称与描述、扩展配置。
- **升级**：机制写入与自检按这次指令执行，失败时说明缺口。写完如有待跟进的适配条目或知识加载问题，AI 按块列出——知识与对接层列目标已适配版本（`adapted_for`）之后的，
  在途单列目标升级前所装版本之后的，来源是业务仓时对接层已整份换过、不列；另附按当前协议加载目标知识的结果——请你选择现在处理哪几块，再按目标的真实代码逐块做完。
  三块都做完才把目标的已适配版本改成包的版本；只做一部分时不改，交回里列出没做的块与条目；选稍后什么都不写。没有条目时直接交回。
- **写入面**：除上表的扩展目录外，还会更新目标 `AGENTS.md` / `CLAUDE.md` 里的 Story 标记区与 `.gitignore` 的一行；首次安装时在 `framework.config.json` 补上 `paths.extension_dir`。
- **宿主入口**：实际装哪些以来源包 `manifest.yaml` 的 `provides.bridges` 为准，当前登记的形态如下：

  | 宿主 | 入口 |
  |---|---|
  | Claude Code | 命令 `.claude/commands/story.md` |
  | CAC | 命令 `.cac/commands/story.md` |
  | Codex | Skill `.codex/skills/story/SKILL.md` |
  | OpenCode | Skill `.opencode/skill/story/SKILL.md` |
  | Cursor | Skill `.cursor/skills/story/SKILL.md` |
  | 通用 `.agents` | Skill `.agents/skills/story/SKILL.md` |

- 本说明由维护者另行分发，`/story adapt` 不会把它装进目标工程，也不会动目标工程自己的 README。

## 4. 机制与说明

### 4.1 需求目录与产物

扩展装在目标工程的 `doc/extensions/`。需求目录默认是 `doc/features/<编号>/`，由目标工程 `framework.config.json` 的 `paths.features_dir` 决定：

| 位置 | 是什么 | 谁用、何时看 |
|---|---|---|
| `RR/prd.md`、`SR/design.md` | 上游需求与系统方案（外部输入）；取不到时是占位件，按缺料处理 | AI 取材与分析；你核对材料时看 |
| `AR/design.md` | 经范围确认的本部件需求输入 | 规格的输入；范围确认后过目 |
| `spec/spec.md`、`acceptance.yaml` | 规格与验收 | 后续设计、实现和验证的依据 |
| `AR/story.md` | 十章需求叙事 | 评审人阅读；系统单归档的上传正文 |
| `AR/review.md` | 待确认与已定事项、人工表态区 | 评审人表态 |
| `AR/story-src/` | 写作设计 `story-template.md`、材料清单 `materials.json`、流程契约 `story-flow.json`、每轮 update 记录 `updates/<id>/` | AI 的过程记录，排查与追溯时看；流程契约由脚本维护，不要手改 |
| `inbox/` | 收件目录 | 你放补充材料的地方 |
| `.backups/` | `local/` 是本地文档被覆盖前的备份；`cloud/` 是归档覆盖线上正文前的备份（由需求系统对接实现写入） | 恢复时用 |

### 4.2 Story 怎么写成

Story 是十章需求叙事（背景、术语、范围、业务方案、业务流程、功能说明、异常与恢复、验收、交付与上线、附录），由 AI 依据材料、有效决定和规格编写；
附录的技术契约、规约、埋点、改动边界几节从规格与知识判断派生。它不是规格的逐字转换：登记和交付时核查一致性，依据变了要重新核查登记。
改章时 AI 改那一章的草稿并重新登记，连同结构与引用一起核查，别的章不动。`AR/review.md` 的人工表态区在重新生成时一个字都不动。

### 4.3 停下来问你的规则

- 停等点就是 1.3 那张表；门禁报错怎么修、下一步做什么由 AI 自己处理。改不动时说明卡在哪一条、缺什么、需要谁提供，请人接手——这是出口，不是停等点。
- 选项标签由流程脚本给出，AI 原样摆出、不改写。
- 「按推荐」只对当前这一问生效，不会替你答后面的问题；AI 自己的判断记成提议，要你确认后才算数。你的回答连同原话记在流程契约里。
- 会议裁决在这些情况下出现：会上的结论改变范围、接口或验收；与已归档文档或已有决定冲突；判不准是否属于本单；转写存疑且影响结论。
  AI 按原话和你的选择写出当前会议结果，后面的需求文档、规格与 Story 都从它取，结论指回转写原文的行。范围定下之后才到的会议，先重开范围再裁决。
- 交付前过门禁与独立的语义审查：审查判了阻断项才返修，只有建议项时照常交付；宿主没有配审查员时，交付和更新会如实写明没有经过独立语义审查。

### 4.4 授权范围

`/story` 的授权到规格闭环并通过交付门为止。plan 及之后（编码、检视、UT、实机测试）按 Framework 的推进策略，在你已有的授权范围内推进；
缺少下一阶段授权时停下确认。

### 4.5 更新（update）的规则

- 系统单先取回上游；每一轮都先问一次要不要补料。
- AI 比较已有产物、读原文判断变化，按当前有效依据增量修订；改了什么、为什么、哪些没变，记在这一轮的 `update-notes.md`。
- 新依据和其他仍有效的来源冲突、或要改已经承诺的行为时，登记成议题停下问你，不按时间最新覆盖；评审人已表态的议题正文改了，会请评审人确认沿用还是重新看。
- 受影响的阶段按新内容重新核查；业务口径、范围、验收或契约实体变了的，重新过语义审查。
- plan 已在做或已闭环的，改受影响的设计与契约；已到代码或测试的，文档同步到 plan 为止并标明实现与证据可能失效，不自动改源码、不碰设备测试。
- 已归档的先给你看结论与差异，你确认后才用 `/story archive` 回写。
- update 不改范围：要扩或缩时，这一轮收口并记下「范围需重新拍板」；你决定重定后，AI 重开范围确认，范围定了再起一轮 update 更新产物。
- 撤回本轮：需求目录恢复到这一轮开始之前；这之后改过或新建的内容先原样另存，两边都留着，要哪份由你定。
- `/story restore <AR>`：用归档时备份的上一版恢复需求系统上的正文，只在归档之后可用，不动本地这一轮的修改。

### 4.6 工程知识

目标工程在 `doc/extensions/knowledge/` 维护三类知识，由 `manifest.yaml` 的激活清单登记，每份写明何时适用：

| 类型 | 回答什么 | 在流程里怎么用 |
|---|---|---|
| 项目事实 | 工程里有什么、在哪、通常怎么用 | 从规格起作为目标工程的事实使用 |
| 规约 | 什么条件下必须做或禁止做什么 | 规格判断哪些命中、形成本需求的约束；plan 决定落点与验证方式，命中项不能无理由取消 |
| 设计模式 | 什么情形适用、角色怎样协作、怎么验证 | 规格提出候选与理由，plan 选择、拒绝或调整 |

规格、plan、编码、检视、UT、实机测试六个阶段各有作者要求与扩展检查。埋点以指标为单位：规格写指标定义与统计点，plan 对每个统计点的
每种结果落到实现与责任方法，后续阶段据此验证。

### 4.7 当前边界

- 面向有人参与的交互式开发；需求取舍与最终评审由人负责。门禁与语义审查帮助把关，不证明表达质量。
- 已知局限：
  - update 过程中你口头给出的新决定，可能没有记进流程契约；重要决定请在评审记录里写明，或让 AI 复述后记录；
  - 评审意见和系统设计的安全口径冲突时，AI 可能直接采纳而没有停下问你，审查也可能没拦下；
  - 材料里写明还没定的事项，可能没在 Story 与评审记录里露出来；
  - AI 读机制源码的次数仍然偏多，会拖长耗时。
