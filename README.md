# Story Extension 使用说明

Story Extension 是挂在 AgentMaison Framework 上的需求开发流程：从一个需求单号起，取材料、和你确认范围，生成规格（Spec）、面向评审的需求叙事（Story）与评审记录（Review），承接评审意见与材料变化，并把目标工程的知识带进后续设计、编码、检视与测试。
各版改了什么见 [`doc/release/`](doc/release/) 下的版本说明；本仓的维护方式见 [AGENTS.md](AGENTS.md)。

## 1. 产品与适用条件

**使用前提**

- 目标工程已接入 Framework（当前依赖 3.0.0）并装好 Story Extension；没装的先按第 5 节安装。
- 需求系统里的单（`AR` 开头）要目标工程有需求系统的对接实现与访问 token；问题单、工单等本地单不连需求系统，从你给的文件开始。
- 面向有人参与的交互式开发。

**文中的路径**都指目标工程里的位置：扩展装在 `doc/extensions/`；每个需求的目录默认是 `doc/features/<编号>/`，实际以目标工程
`framework.config.json` 的 `paths.features_dir` 和 AI 给出的路径为准。本仓的 `demo/` 是一份装好 Story 的完整示例工程。

## 2. 完成一次需求

### 2.1 起手

```text
/story init <编号>
```

- `AR` 开头：AI 从需求系统逐级取回 AR、SR、RR 三份正文；取不到的会留下占位件，按缺料处理。编号查不到时，AI 请你确认单号后重取。
- 其他编号：不连需求系统，材料由你提供；交付终点是仓内的 Spec、Story 与 Review，没有线上归档。
- 第一次用系统单时要需求系统 token：AI 先从目标工程的对接实现和本机配置里找，找不到才向你要，拿到后写入你的用户级配置，以后不用再配。
  Demo 工程的对接实现是本地模拟，不需要真实 token。

中断或换了会话，告诉 AI 要继续的编号：进度记在需求目录的流程契约里，不在对话里，AI 先查出走到哪、下一步做什么再接着做。

### 2.2 AI 在哪些地方停下来问你

需求开发过程中 AI 在下表这些地方停下来问你（已有需求的更新另有停等，见第 3 节）；门禁报错怎么修、下一步做什么由它自己处理。门禁反复报同一个问题而它改不动时，会停下说明卡在哪一条、缺什么、需要谁提供，请人接手。有编号选项时回编号即可，也可以说「按推荐」——这只对当前这一问生效，
不会替你答后面的问题；AI 自己的判断记成提议，要你确认后才算数。你的回答连同原话记在流程契约里。

| 何时问 | 你提供什么 | 结果 |
|---|---|---|
| **材料确认**：盘点完材料后，第一轮一定问；导入后仍缺料会再问 | 需要补的文件放进 AI 给出的收件目录后回「已放入」对应的选项；材料齐了回「现有材料就是全部」 | AI 导入材料，开始需求分析。能直接放：`.docx`、`.md` / `.txt` / `.log` 等文本、界面设计图；PDF 这类脚本转不了的，AI 读得懂就自己转写，读不了才请你给可读版本。原件留档 |
| **会议裁决**：交了需求澄清会的转写（`.docx`，和其他材料一样放进收件目录），且有话题需要人定时——会上的结论改变范围、接口或验收，与已归档文档或已有决定冲突，判不准是否属于本单，或转写存疑且影响结论 | 每个话题选一项（AI 给推荐）；另外确认参会人角色 | AI 按原话和你的选择写出当前会议结果，后面的需求文档、规格与 Story 都从它取，结论指回转写原文的行；会上没收敛或你选「保持待定」的，登记成未决议题，不替你定。范围定下之后才到的会议，先重开范围再裁决 |
| **范围确认**：需求分析做完后一定问 | 选「整体承载」或 AI 给出的某个切法；选切法后再选本单承载哪一份。想要的切法不在里面，直接说出来，AI 回到分析补上再摆给你 | AI 按定下的范围写出 `AR/design.md`，后面的规格与代码都以它为界，值得过目它的范围一节 |
| **术语确认**（Framework）：写规格时 | 逐条核对术语与所属模块的对应表 | 你确认过的才勾选 |
| **个人设置**（Framework）：阶段入口需要时，如视觉 provider | 从候选里选 | 记进你的个人配置 |
| **查无此单**：系统单取材时编号查不到 | 确认或更正单号 | AI 按你给的单号重取 |
| **交付之后怎么走**：交付门通过后问一次 | 系统单选「归档送审」或「进入 plan」；本地单只有进入 plan | 见 2.4 |
| **归档、恢复**：覆盖线上内容前 | 确认 | 执行或放弃 |

### 2.3 AI 生成什么

范围定下后，AI 形成规格 `spec/spec.md`、验收 `acceptance.yaml`、需求叙事 `AR/story.md` 与评审记录 `AR/review.md`（位置见第 4 节）：

- Story 是十章需求叙事（背景、术语、范围、业务方案、业务流程、功能说明、异常与恢复、验收、交付与上线、附录），由 AI 依据材料、
  有效决定和规格编写；附录的技术契约、规约、埋点、改动边界几节从规格与知识判断派生。它不是规格的逐字转换，登记和交付时会核查一致性，
  依据变了要重新核查登记（见第 3 节）。
- 交付前先过门禁与独立的语义审查：审查判了阻断项才返修，只有建议项时照常交付；目标宿主没有配审查员时，交付和更新都会如实写明
  没有经过独立语义审查。

### 2.4 评审与之后的阶段

- **系统单送审**：`/story archive <AR>`，把 Story 与 Review 上传需求系统。`AR/review.md` 的人工表态区在重新生成时一个字都不动。
- **评审人表态**：读 Story，在 Review 的每条议题下选「同意 / 需修改 / 暂缓」，要改成什么、选别的做法、为什么暂缓写在「修改意见」；
  填写位不预选任何一项，议题里的建议不等于已选。议题之外的发现写在末尾「其他意见」，一条一个编号。
- 表态回来之后用 `/story update` 更新已有产物（第 3 节）。
- **之后的阶段**：`/story` 的授权到规格闭环并通过交付门为止。plan 及之后（编码、检视、UT、实机测试）由 Framework 按它的规则推进，
  每一阶段仍要你授权，不会自动一路往下做。

## 3. 已有需求的变更与恢复

| 场景 | 怎么做 | 会发生什么 |
|---|---|---|
| 上游材料改版、评审意见回来、你有新决定、有人直接改过文档 | `/story update <编号>` | 系统单先取回上游；**每一轮都先问一次要不要补料**；评审人已表态的议题正文改了，会请评审人确认沿用还是重新看；AI 比较已有产物、读原文判断变化，按当前有效依据增量修订，改了什么、为什么、哪些没变记在这一轮的 `update-notes.md`。新依据和其他仍有效的来源冲突、或要改已经承诺的行为时，登记成议题停下问你，不按时间最新覆盖 |
| update 改到哪里 | —— | 受影响的阶段按新内容重新核查；业务口径、范围、验收或契约实体变了的，重新过语义审查。plan 已在做或已闭环的，改受影响的设计与契约；已到代码或测试的，文档同步到 plan 为止并标明实现与证据可能失效，不自动改源码、不碰设备测试；已归档的先给你看结论与差异，你确认后才用 `/story archive` 回写 |
| 范围要扩或缩 | 你决定重新定范围时告诉 AI | update 不改范围：这一轮收口并记下「范围需重新拍板」；你决定重定后，AI 重开范围确认，范围定了再起一轮 update 更新产物 |
| 撤回这一轮 update | 告诉 AI 撤回本轮 | 需求目录恢复到这一轮开始之前；这之后改过或新建的内容先原样另存，两边都留着，要哪份由你定 |
| 撤回线上的归档 | `/story restore <AR>` | 用归档前留在 `.backups/cloud/` 的那一版恢复需求系统上的正文；只在归档之后可用 |
| 想改 Story 的措辞 | 告诉 AI 改哪里 | AI 改那一章并重新登记，会连同结构与引用一起核查，别的章不动。附录里派生的几节要改的话改它的来源（规格或知识判断）。你直接改过的文档，下一次 update 会把它当作一项变化读进来 |

## 4. 产物与工程知识

### 4.1 需求目录里有什么

需求目录默认是 `doc/features/<编号>/`：

| 位置 | 是什么 | 谁用、何时看 |
|---|---|---|
| `RR/prd.md`、`SR/design.md` | 上游需求与系统方案（外部输入） | AI 取材与分析；你核对材料时看 |
| `AR/design.md` | 经范围确认的本部件需求输入 | 规格的输入；范围确认后过目 |
| `spec/spec.md`、`acceptance.yaml` | 规格与验收 | 后续设计、实现和验证的依据 |
| `AR/story.md` | 十章需求叙事 | 评审人阅读；系统单归档的上传正文 |
| `AR/review.md` | 待确认与已定事项、人工表态区 | 评审人表态 |
| `AR/story-src/` | 写作设计 `story-template.md`、材料清单 `materials.json`、流程契约 `story-flow.json`、每轮 update 记录 `updates/<id>/` | AI 的过程记录，排查与追溯时看；流程契约由脚本维护，不要手改 |
| `inbox/` | 收件目录 | 你放补充材料的地方 |
| `.backups/` | `cloud/` 是归档前的线上正文，`local/` 是本地文档备份 | 恢复时用 |

### 4.2 工程知识

目标工程在 `doc/extensions/knowledge/` 维护三类知识，由 `manifest.yaml` 的激活清单登记，每份写明何时适用：

| 类型 | 回答什么 | 在流程里怎么用 |
|---|---|---|
| 项目事实 | 工程里有什么、在哪、通常怎么用 | 从规格起作为目标工程的事实使用 |
| 规约 | 什么条件下必须做或禁止做什么 | 规格判断哪些命中、形成本需求的约束；plan 决定落点与验证方式，命中项不能无理由取消 |
| 设计模式 | 什么情形适用、角色怎样协作、怎么验证 | 规格提出候选与理由，plan 选择、拒绝或调整 |

规格、plan、编码、检视、UT、实机测试六个阶段各有作者要求与扩展检查。埋点以指标为单位：规格写指标定义与统计点，plan 对每个统计点的
每种结果落到实现与责任方法，后续阶段据此验证。

## 5. 安装与升级

在**来源工程**里打开 AI 会话，指定目标工程：

```text
/story adapt <目标工程根目录>
```

- **前置**：目标工程已接入 Framework、是 Git 仓库的根，这次要覆盖的路径上没有未提交的改动。有未提交改动时 AI 会列出路径，由你自己提交或暂存后重试；
  它不替你提交或暂存。
- **首次还是升级**：目标没有扩展的 `manifest.yaml` 就是首次安装，有就是升级。
- **从哪装**：用维护仓发布时装进 `demo/` 的那一份（在 `demo/` 下打开会话），或另一个已适配的业务仓；维护仓的开发源不是安装来源。
  来源包 `manifest.yaml` 写着 `adapters: stand-in` 的是替身包（Demo 就是），没有这个键的是业务仓，两者对接实现的处理不同（见下表）。

| 部分 | 归谁 | 安装或升级时 |
|---|---|---|
| 流程机制（技能、钩子、规则、合同、核心脚本、宿主入口） | 来源 | 脚本整份替换 |
| 需求系统对接实现（`skills/story/scripts/adapters/`） | 看来源 | 替身包来源：不给也不覆盖，目标用自己的实现（首次接入要自己实现，或从已有业务仓复刻）；业务仓来源：整份换成来源版本 |
| 知识（`knowledge/`） | 目标 | 脚本不读不写；AI 按知识适配方法，从目标工程自己的代码与需求出发写和改，不复制来源工程的业务知识 |
| 工程名称、描述、对接来源、已适配版本、知识激活清单（`manifest.yaml` 里） | 目标 | 保留 |

- **首次安装**你要确认一次：AI 扫描目标工程写出的部件定位知识（本部件是谁、职责边界、和谁交互）、工程名称与描述、扩展配置。
- **升级**一次指令完成写入与自检，只在失败时问你；写完按块列出要跟进的条目：知识与对接层列目标已适配版本（`adapted_for`）之后的，在途单列目标升级前所装版本之后的，来源是业务仓时对接层已整份换过、不列。你定范围后 AI 按目标的真实代码逐块做完。
- **写入面**：除上表的扩展目录外，还会更新目标 `AGENTS.md` / `CLAUDE.md` 里的 Story 标记区与 `.gitignore` 的一行；首次安装时在 `framework.config.json` 补上 `paths.extension_dir`。
- **宿主入口**：实际装哪些以来源包 `manifest.yaml` 的 `provides.bridges` 为准，当前登记的形态如下：

  | 宿主 | 入口 |
  |---|---|
  | Claude Code | 命令 `.claude/commands/story.md` |
  | CAC | 命令 `.cac/commands/story.md` |
  | Codex | Skill `.codex/skills/story/SKILL.md` |
  | OpenCode | Skill `.opencode/skill/story/SKILL.md` |
  | Cursor | Skill `.cursor/skills/story/SKILL.md` |
  | 通用 `.agents` | Skill `.agents/skills/story/SKILL.md` |

- 本说明由维护者另行分发，`/story adapt` 不会把它装进目标工程，也不会动目标工程自己的 README。

## 6. 当前边界与帮助

- 需求取舍与最终评审由人负责；门禁与语义审查帮助把关，不证明表达质量，宿主没有审查员时交付会如实标明。
- 已知局限：
  - update 过程中你口头给出的新决定，可能没有记进流程契约；重要决定请在评审记录里写明，或让 AI 复述后记录；
  - 评审意见和系统设计的安全口径冲突时，AI 可能直接采纳而没有停下问你，审查也可能没拦下；
  - 材料里写明还没定的事项，可能没在 Story 与评审记录里露出来；
  - AI 读机制源码的次数仍然偏多，会拖长耗时。
- `/story help` 输出流程说明。
