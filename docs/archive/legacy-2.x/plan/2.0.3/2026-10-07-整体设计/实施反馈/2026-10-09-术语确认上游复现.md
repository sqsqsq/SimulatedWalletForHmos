# 10-09 术语确认上游交接：交互运行里的 headless_assumed 只给 WARN

> 读者：Framework（AgentMaison）原生蓝图负责方，以及维护设计者。依据：[P2](../02-步骤2-产物与独立审查.md)「术语确认的上游交接」与[承接实施复核](../评审意见/2026-10-09-承接实施复核与版本剩余项.md)「上游报告的证据边界」。
> 本文只给已证明的分支事实与行为请求，不改本仓的 vendored 副本，不在 Extension 加术语关卡。报告交付不等于上游已修复。

## 1. 现象

10-03 的 car-key 实跑声明为交互运行（`test/cases/car-key-sharing/case.yaml` 写 `interactive: true`）。作者生成蓝图时把三条 medium 术语直接写成 `extraction_method: headless_assumed`，没有发起确认，随后写下「Zero BLOCKER, only 3 WARN (headless terminology assumptions, expected for automated runs)」。证据见[第三轮交回](2026-10-09-第三轮交回.md)第 51–59 行。

这段只证明作者误用了确认方式。那份工作区本身另有来源指纹不符与缺质询，不能当作「其余条件合法时可整体准入」的验收例。干净对照见第 3 节。

## 2. 实际接入版本与代码位置

- Framework 3.1.0，source commit `074a4c3c4a0591c8ed2162e2a0d048a1fdec081f`（`demo/framework/RELEASE-MANIFEST.json`）。
- `harness/scripts/utils/blueprint-discovery.ts` 的 `validateTerminologyFacts`：`headless_assumed` 一律以 WARN 返回（第 194–196 行）。
- `check-component-blueprint.ts` 的参数里没有运行模式，蓝图里也没有声明运行模式的字段。

## 3. 干净对照：合法中性原生夹具

脚本：`output/scratch/2.0.3-p1/term_clean_repro.py`，原始输出在同名 `.out.json`。

步骤：

1. 夹具用 `test/fixtures/blueprint/wallet-balance-refresh`，原生已准入。
2. 每组从夹具单独建一份工程，并放入 demo 的 `doc/glossary.yaml`。
3. 每组只往 `discovery.facts` 加一条术语事实。远期停放组再加一条字段齐全的 `open_decision` gap（owner、needed_by、unlock_condition、provenance、verification_refs）。
4. 按原生口径重算 `source_fingerprint` 并写回两处。
5. 运行：`npx ts-node scripts/check-component-blueprint.ts --project-root <工程> --blueprint wallet-balance-refresh --json`。

| 对照 | 术语事实 | 整体结果 | `terminology_facts_confirmed` |
|---|---|---|---|
| 0 | 不加（夹具字节原样） | **PASS**，无问题 | — |
| A | 余额刷新 · medium · `headless_assumed` | **PASS**（退出 0） | WARN：「headless 自动继续（headless_assumed），入 must-review…」 |
| B | 余额刷新 · medium · `user_confirmed` | PASS，无问题 | — |
| C | 余额刷新 · medium · 未确认（`model_inference`） | **FAIL** | BLOCKER：「medium 置信度未经用户确认…交互态须当场确认并记 user_confirmed…」；夹具里自报的准入 pass 另被检查器判为不成立（`admission_false_pass`），检查器只报问题、不写回准入状态 |
| D | 同 C，加合法远期 `open_decision` 停放 | PASS | WARN：「已由 gap gap-term-balance-refresh 停放到远期切片…」 |
| E | 钱包主功能 · high · glossary 精确命中 WalletMain | PASS，无问题 | — |

**已证明的分支事实**：在其余条件都合法的蓝图上，同一条没问过人的 medium 术语：
- 记成「未确认」，整体 FAIL（C）；
- 记成 `headless_assumed`，整体 PASS，只有一条 WARN（A）。

检查器拿不到运行模式，所以 A 在交互运行与自动化运行里结果相同。B、D、E 说明合法确认、合法停放和 glossary 直确认都不受影响。

## 4. 请求的行为

1. 让原生检查能知道这次运行是 interactive 还是 headless。运行模式的可靠来源与形态由上游决定。
2. 运行模式为 interactive 时，medium 或 low 术语的 `headless_assumed` 按 C 同样阻断，并提示当场确认。
3. B、D、E 与 headless 运行下的 A 保持现状，不把所有 WARN 一律改成阻断。

## 5. 本仓边界

- 不增设 story_flow 术语关卡，不复制原生置信度算法，不改 vendored 代码。上游交付前，这项自动兜底的保证不签收。
- 这个缺口不妨碍观察正常的交互流程：真实 CLI 观察作者是否按已送达的规则当场提问。规则在 `extensions/skills/story/SKILL.md` 关卡表与 Framework 蓝图工作流里。
- 蓝图里没有 `term:` 事实本身不算缺陷，要按当前材料与工程核有没有需要消歧的映射。
- 结果金样的编写不等待这个接口。
