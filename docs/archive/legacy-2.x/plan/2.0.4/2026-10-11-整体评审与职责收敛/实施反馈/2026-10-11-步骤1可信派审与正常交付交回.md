# 步骤 1 交回：可信派审、返修承接与正常交付

> 读者：维护设计者。依据：[步骤1](../01-可信派审与正常交付.md)，源码基线 `3e880f17`。改动未提交，没有运行模型或 CLI。
> manifest 已按版本纪律升为 2.0.4，没有追加未发布的升级条目。

## 1. 原件直接交接（R01）

**派审路径**：prepare 产出 dispatch → 主执行者原样交给隔离 task → 审查者把报告直接写到回复位置 → check → 消费结果。

| 位置 | 动作 |
|---|---|
| `phases/design.md` 五节第 2 步 | 改写派审要求：<br>· dispatch_text 原样交出，不增删、不改写；<br>· 审查者直接写回复文件，那份就是原件，作者只读；<br>· 向人概述不写回原件；<br>· 宿主只能返回文本时，须用宿主现有的原样存盘动作，外层包装与正文分开保留；<br>· 没有这种动作就停下说明原件交接缺口；作者手写或缩写件不是原件，也不适用未审查授权 |
| 同节结果表 `report_invalid` 行 | 补「你不补表、不改字」 |
| `review-report-contract.mjs::reportFormat` | 原句「宿主原样存下」改为：报告写到派审载体给的回复位置，它是审查原件；格式不合则原件保留、另给新回复 |
| `story-build.mjs` prepare 的提示 | 原句「宿主只返回文本时原样写到那里」改为：原样交出、不增删；审查者直接写到回复位置 |

`reader-review-task.mjs` 的读法与「报告怎么写」现在引用同一个写入职责，没有另写一份相反的文件权限。`dispatchFor` 里本来就写着「只写上面这一份回复」，保留。

check 的职责不变：核材料身份、结构与结论一致，不声称能证明作者真实性；没有新增签名字段。

## 2. 材料变化后的复审参考（R02）

### 2.1 参考的选择顺序

`independent-review.mjs::replyPlace` 按方案的五级顺序选择，命中即停，注释写全了顺序：

1. 当前材料键有可复用的 pass/warn，直接复用。
2. 同一材料键已准备、回复未到，沿用原位置与原上下文。参考原件受损时转 `fresh_review`。
3. 当前材料键有 `report_invalid` 或 `fail`，分别走格式返修或复审。
4. 新增：新材料键、紧前一次准备的 report_file 可读，且字节没有违反已登记原件摘要 → `prior_revision`，只作参考，不继承结论。
5. 其余情况完整审查。

第 4 级的参考记录：

- 字段为 `{kind: prior_revision, material_key: <旧键>, report_file, report_sha256}`。
- 这一份也登记进 `originals`。
- 「前一次」只指紧前那次准备，不往更早找。

第 4 级的派审载体写明：旧报告只是待核的发现与背景，结论不适用于这次；要完整审查，回复只对应新材料键。

第 5 级的派审载体写「这一次没有可信的前轮审查报告作参考」，首审也是这句。

参考原件在准备之后被改动：check 判 `input_invalid`（沿用原有的 `dispatchProblem`）；再 prepare 时走第 2 级转 `fresh_review`。

### 2.2 坏准备记录的预检

新增 `preparedRecord(ctx)`，只服务 prepare 与 check 两个消费者。

| 记录状态 | 结果 |
|---|---|
| 不存在 | 按首次处理 |
| 读不出 | 返回诊断 |
| 不是 JSON 对象 | 返回诊断 |
| 缺必需字段 | 返回诊断 |

必需字段：`material_key`、`project_root`、`report_dir`、`report_file`、`report_dirs`。

诊断里写了路径和恢复动作。两个消费者对诊断的处理：

- `cmdReview` 的 prepare 在 `pendingDisclosure` 及全部定稿写盘之前调用预检，坏记录时 `fail(error)` 非零退出；`prepareReview` 自身也返回 `{error}`。
- check 输出 `{result: input_invalid, detail}`，退出 1。
- 设计页 `input_invalid` 行补一句：准备记录读不出时按诊断恢复原记录，不删掉它重来。

**退出项**：「材料一变就一律不带上下文」的分支，以及只证明这一行为的否定断言（`test_a_failed_review_is_rechecked_with_its_report_and_new_material_starts_clean` 的最后一段）。「材料变了，旧结论失效」的覆盖仍保留。

## 3. 作者与审查动作收敛（R03）

先核了实际送达情况，只改有缺口或冲突的位置：

| 要求 | 核到的现状 | 本轮动作 |
|---|---|---|
| 设计交接：提取稿只是索引，事实取原件 | `design.md` 三节只说「用冻结输入」，没说提取稿的定位 | 在原条目里替换说明：冻结文件直接交设计作者；业务的条件、行为与责任从原件和人签取 |
| 蓝图作者准入前核承接 | `hooks/blueprint/author.md` 没有这条 | 在「承接到设计」段补一句：准入前逐个设计对象回原件与人签核条件、行为、责任；未决写成未决；提取稿只作索引 |
| 写作设计按关系组织 | 五节已有「写作单位是一条业务关系」，但四节写作设计只说「对照初筛写」 | 四节原段替换为：先按当前蓝图与决定认出关系，定在哪处讲完整、哪几处重现，再排进骨架，不按章标题各自重猜 |
| 写作设计的回看 | 六节写死「流程、功能说明、异常与恢复、验收四处」 | 改为「一条关系讲到的各处对着读」；没有新增同义规则，也没有新增台账 |
| 审查严重性 | `story-reader-rules.yaml` 已有阻断类别与两层一致性 | 把「三件事」改为：先写清位置、问题、影响、最早出错的责任位置，再按类别定级；验收没有对应编号、错误源自上游都不降级。措辞偏好仍只是建议 |
| warn 的处置 | 设计页 warn 行写「材料变了按原身份重审」，与新参考机制冲突，也没定「一次处置」 | 替换为：对这组建议只处置一次——事实或范围问题回责任方改；偏好可以保留并写理由；采纳的建议按影响面一次改完再 prepare（新载体带参考），处置写进交付说明或 update-notes；不为清空建议再改再审 |
| 专项内容本身错了 | 设计页只写了「逐字呈现」 | 补：回蓝图修订，不在 Story 补相反解释，也不留给施工单位改共同设计 |

R03 的语义效果（首稿承接、严重性判断、返修收敛）只有步骤 4 的真实评价能证明。本步骤的机械通过不关闭 R03。

## 4. 送审授权（R04）

| 位置 | 动作 |
|---|---|
| `SKILL.md`「推进契约」 | 新增「送审授权」定义：<br>· 选送审或明确要求 archive，即授权把当前展示的三件写入这张单；<br>· 发布前核照常跑并展示，范围没变不再确认第二次；<br>· 外部被改、超出授权范围、附件或目标新增时才停；<br>· 恢复要单独授权 |
| `SKILL.md` 停等表 | 「归档、恢复」拆成两行：<br>· 归档：未授权时问一次，已授权时只在冲突或范围变化时问；<br>· 恢复：人明确要求才做 |
| `SKILL.md` 归档步骤 ② | 「摆给人，人授权了再做 ③」改为：展示；已有送审授权就接着做 ③，没有授权就先请人授权 |
| `flow/publish.py::cmd_publish` | 无冲突时的 action 文本同步上面的规则；冲突时的 `--reply` 处理不变 |
| `phases/update.md` | 第六节、进展表「已归档」行和开头边界句同步：update 本身不授权回写；本轮已有同单同范围的送审或 archive 授权时沿用 |

摘要比对、读回和发布记录不变；没有新增 authorization.json 或签名状态。

## 7. 未验证

真实宿主上的以下行为都没有验证：

- 审查者直接写报告、主执行者不再改写 dispatch；
- 首稿对来源条件与未决的承接；
- 审查者按影响和最早责任定级；
- warn 后一次处置并收敛；
- 已有送审授权时不再二次停等。

这些行为要在步骤 4 的独立评价，或获授权的 CLI 实跑里取证。只有文本返回能力的宿主分支没有具体宿主证据，本轮只写了规则，没有实现存盘动作。
