## 2. 完整问题与忠实反馈（R09）

### 宿主请求

## 3. 合并回复与已答条目（R09）

### 外层 `reply`

| 参数 | 规则 |
|---|---|
| `--step` | 可重复，内部是列表 |
| `--run-id`、`--turn` | 必给 |

预检在发送前完成，失败时不发送、不消费条目。拒绝的情况：

- step 重复或未知；
- planned 不带 step；
- 非 planned 带了 step；
- 条目的等待类型不符，或阶段前提不成立；
- 补料不在声明里、读不到，或重名。

### 发送分支

1. 先查 observations 里这一 run/turn 的成功回复：同样的话、材料、条目重发，返回 `already_sent`、不再发；不同的拒绝。
2. 再要求目标正是当前在等的那一问。
3. 发送失败不消费条目。
4. 没有 payload 时记 `unknown`，提示先核 `events.jsonl`、不自动重发。

### 成功回复的记录

| 位置 | 记录 |
|---|---|
| observations | `run_id / turn / text / deliver / covered_steps / result` |
| `answered_steps` | 按脚本顺序存，相邻两问再确认同一立场不重复计入；新 attempt（`prepare_case_retry`）从空起 |
| `interaction_index` | 只由已答集合派生（第一个未答位置） |

旧的单 step + `max(hit+1)` 推进（`advance_plan`）退出。

### 下层 `run_case.py reply`

- 复用已有的 `--run-id`，新增 `--turn`；
- 写回复文件之前核 `state.run_id` 与 `state.awaiting_turn`，不一致不收；
- poll 给出的 `how` 提示带上两者。

## 4. 人工区意见精确投递（R08）

### 参数传递

外层 `resume-update` 新增 `--review-feedback-file`，解析成绝对路径后传给 `run_case.py resume-update`，再到 `deliver_update_inputs`。

Case 有 `review_human_zone` 时这个参数必给；没有时给了也拒绝。

### 意见文件的核对

`source_item` 按 Case 里各源的声明顺序和条目顺序连续编号。核对项：

- 恰好覆盖每条一次；
- `decision_id` 不重复；
- verdict 与 opinion 等于静态意见（按 YAML 解析后的值比）；
- `decision_id` 为空时报「没投，交维护设计者裁定」；
- 目标 D 标记在工作区 Review 里唯一；
- 工作区 Review 与第一检查点快照的机器区逐字一致（人工区抹去后比较）；
- 人工区的三态行和修改意见行齐全。

### 写入规则

| 人工区现状 | 处理 |
|---|---|
| 空白 | 可写 |
| 已有完全相同的意见 | 幂等，照常通过 |
| 已有不同的人工意见 | 报投递冲突，保留原文 |

全部成立才一次写入：勾目标三态的一项，另两项清空勾选，写修改意见行，原换行与其余文本不动。

### 写前核全部输入

`deliver_update_inputs` 改为先核全部输入，再执行：

- local_material、system 的落点与环境；
- 人工区意见；
- 额外 `--deliver` 的补料源（新 `supplement_sources`，reply 也用它）。

有一项不成立就一项都不写、不排话。执行中途出现 IO 错误时抛 `UpdateDeliveryError`，`cmd_resume_update` 输出已投与未投明细，不写续跑请求。

### 退出项

- 按标题词匹配的 `_write_review_zones`；
- 「匹配不到就记 note、继续算投完」的分支；
- 只证明这些行为的两组测试。

TEST §4.4 第 5 步与 `update_inputs` 表同步，并新增「人工区意见文件」一段和调用示例。

## 5. 异常、等待和容量（R10、E01）

### TEST 的规则改动

- **§4.2**：把正常推进（回 `neutral`），与循环、重复同一个词、没有业务进展的生成分开。异常时保留原话与事件，向用户报告，不机械连发「继续」，宿主也不自行获得停测权限。
- **§3.2**：等待延迟要在观测与成本报告里写明。
- **§1.2 第 0 步**：起跑前把容量事实固定进运行证据，只记非秘密字段。查不清的标未知；上一轮出过输入超限而它仍未知时，不起跑。

### E01 取证

只读取证，脚本是 `output/scratch/2.0.4/e01_facts.py`，只打印模型名、limit 与压缩相关字段，不输出 key 或地址：

| 项 | 事实 |
|---|---|
| CLI 二进制 | opencode 1.18.32（`npm/node_modules/opencode-ai/bin/opencode.EXE`） |
| config 路径 | `%USERPROFILE%\.config\opencode\opencode.jsonc`；runner 经 `OPENCODE_CONFIG` 交给子进程，不预读 |
| 生效模型 | 首选配置 `bailian/deepseek-v4-flash-0731`（`test/config/test.yaml`） |
| 声明的上限 | 该模型 `limit.context = 1048576`、`limit.output = 131072`；配置里其余模型相同 |
| 压缩 | 配置里没有压缩相关字段，即走 opencode 默认，触发条件未核 |
| 服务限制 | 车钥匙 Spec 失败时服务端返回 `Range of input length should be [1, 1000000]`（400，不可重试），没写单位 |
| 计量 | events 里的 token 字段是逐步用量，拿不到发请求那一刻的累计输入 |

**结论：E01 未解决**。声明的上下文 1048576 大于服务允许的 1000000。如果两者单位相同，客户端按声明窗口压缩之前，服务端就会拒绝，这和本轮现象一致。

但以下三件事没有核清，所以不提出具体配置值、不改用户配置、不安排重跑：

- 服务限制的单位；
- opencode 1.18.32 默认压缩触发点的算法；
- 拒绝那一刻的实际输入量。

要定值，需要其中之一：

- 上游或服务方确认限制单位；
- 在获授权的单次验证里，记下压缩触发与请求体积的事实。

模型名和服务限制都没有写进 Extension，也没有以扩大 context 为修复方向。
