# 步骤3：Case、宿主交互与成本可信性

承担 R08–R10、E01。必读 TEST §0–§4/§6、cases/README、两个Case输入和实际立场、[测试调查](调查/03-Case装置与成本调查.md)。本步骤只改测试域与协议，不改Extension业务、不运行新CLI。既有suite原始证据不修订。

## 1. Case只给真实业务事实与要求

自动充值 `update-inputs/review-feedback.md` 第3条改为稳定要求：“停用横幅应提供重新签约入口并有相应验收；当前稿已满足的保留，未满足的补齐具体缺口”。退出“现稿只有原因、没有下一步”的固定断言。其他意见逐项核实际来源，保持200/300冲突及真实业务立场，不删除难点换绿。人工批注若指认当前稿缺陷，宿主必须先读实际送审版本，不能用预制错误评价代替。

车钥匙静态 `car-review-feedback.yaml` 保留三条业务意见与三态，不再含用于机器定位的match词。它供宿主阅读选择实际议题，不直接当最终投递文件。24/48冲突未问到时仍未决定，不把隐藏立场或金样答案提前注入；不拆单与术语确认不扩大成工程范围或设计授权。

`cases/README.md` 明确复杂组合Case的用途及输入版本证据。原稿与归档件的版本冲突可以作为真实冲突保留，但维护注释不能充当消费模型已知的权威规则。材料中图引用在步骤4实际核到目标；引用损坏则作为测试材料问题修真实来源，不让产品特例豁免。不在本轮建立新CLI Case或评分数据库。

## 2. 完整问题与忠实反馈

`TEST.md` §3.2与 `run_multi_case.py::request_host_reply` 统一：`model_prompt` 是完整决策原文，`question` 是展示摘要（当前1200字符），不得把摘要说成完整原话。宿主回答前取得完整选项；脚本候选只说明阶段/类型可能相关，不判断业务语义。

有编号时，仅当整个选项与既定立场等价才选编号。夹带新结论或无等价选项时，一句业务话限定决定；不算污染性的随意发挥，不教脚本/门禁。T6正确立场是建约失败处理待定，不能因选项标题叫“保持待定”批准“可直接重走验证”。术语确认只覆盖需求方能确认的业务含义，工程模块映射归工程事实核定。

## 3. 合并回复与已答条目

在现有 `reply` 命令将 `--step` 设为可重复，内部统一为列表。planned回复必须给至少一个本次确实回答的step；answered/neutral/improvised不带step，不把未问立场注入。一个合并问题可一次登记多个step，不拆成重复业务回复。

**回复目标由宿主提交，不从发送时的最新问题猜。** `request_host_reply`在现有输出给出当前`run_id`和`turn`，外层`reply`增加必填`--run-id <观察到的run>`、`--turn <观察到的turn>`，`command_reply`原样接收。turn按现有等待记录身份比较，不另造计数。调用示例：

```powershell
python test/scripts/run_multi_case.py reply --suite-id <suite> --case <case> --run-id <run> --turn <turn> --reply-mode adaptive --reply-kind planned --step <id1> --step <id2> --text-file <UTF-8回复文件>
```

观测中的成功reply记录保存`run_id/turn/text/deliver/covered_steps`及实际结果；使用已有observations和suite case记录，不增消息账本。比较text按--text或--text-file解码后的实际字符串，deliver与covered_steps按名称/ID去重排序后比较；covered_steps输入重复或未知ID在发送前拒绝。补料名字先按现有Case来源核可读且无重名冲突，不以排序改变实际投递顺序。

发送分支固定：先查询目标run/turn的已有成功回复，再检查当前等待状态。相同请求重入返回既有成功结果，不再投补料或发CLI；该目标已答但内容/材料/覆盖项不同则拒绝。没有成功记录时，目标run/turn必须等于当前等待对象且状态为awaiting_reply，旧回合或新attempt的回复不得落到下一问题。预检失败不消费step；发送失败不消费；发送结果不确定时报告未知并核原事件，不自动重发，不实现跨崩溃exactly-once事务。

case内`answered_steps`为该attempt成功回复所覆盖的step集合，按脚本顺序存；`covered_steps`为本次回复实际集合。两个相邻回合可以再次确认同一立场，但集合不重复增加。新attempt从空集合起，初段转update沿同一attempt保留。`interaction_index`只派生为脚本中首个未答位置，全部已答时为脚本长度，不能用max(hit+1)把前项推成已答。

`candidate_steps`每项固定含`id/text/deliver/expected_kind/expected_phase/phase_ready`。expected_kind匹配后，已知阶段只列本阶段或无阶段限制的未答项；阶段未知时可列候选但phase_ready=false，不认作planned可提交。planned发送须每项当前phase_ready且kind匹配。旧planned_*字段保留为首候选派生展示，无候选置空，plan_note明确“候选，需按完整问题核立场”；候选不是已经识别到真实业务问题。未问项收尾标未发生，不自动判成功/失败。

同步参数解析、`command_reply`、下层实际发信前的目标核对、TEST调用示例、observations、候选展示和现役测试消费者。下层复用run_case已经存在的--run-id参数（不重复定义），给reply增加--turn并由main传给cmd_reply，核现有state.run_id与state.awaiting_turn；目标run只用于与当前活动对象比较，不用于改指旧run目录。实际发信前再核，防两层读取间已换问题；不增加调度层。旧单step/max游标完成推断退出，已有历史suite只作证据，不迁移重放成新attempt。

## 4. 人工区意见精确投递

为既有 `resume-update` 增 `--review-feedback-file <UTF-8 YAML>`。只在Case声明 review_human_zone 时必填；其它Case仍按system/local_material路径。

输入是非空列表，每项固定 `{source_item: 1, decision_id: D1, verdict: 需修改, opinion: <实际意见>}`。source_item按当前Case中所有review_human_zone源的声明顺序、各源YAML条目顺序从1连续编号，只追溯已有输入位置，不是新业务ID。输入必须恰好覆盖每个source_item一次，不能用少交一条跳过意见；目标decision_id不得重复。verdict与opinion分别保持对应静态意见的三态和值，脚本核值与源一致，宿主只负责选真实D身份；其它动态业务反馈另按真实来源，不借此覆盖静态立场。没有真实对应D议题时停止resume-update，指出未投的source_item和意见，交维护设计者裁定其正常承接路径；本轮不新增自由意见投递分支，不伪造D，也不随意塞进相似议题。不能让机器按关键词选择D。

ID由宿主读当前initial Review后按语义选择，属于该份真实Review既有身份；不新增业务ID映射表。命令形态：

```powershell
python test/scripts/run_multi_case.py resume-update --suite-id <suite> --case <case> --review-feedback-file <本次反馈文件>
```

`--review-feedback-file`由外层解析成实际可读的绝对路径，再经现有subprocess参数传入；它是宿主本次准备文件，不受静态Case update-inputs目录来源限制，目标仍由当前Case/初段身份限定。文件只读取、不写入消费workspace作为维护说明。

接线：`command_resume_update`→既有invoke_case转同参数→`run_case.py`解析/`cmd_resume_update`→`deliver_update_inputs`→`_write_review_zones`。先核完整source_item集合、静态意见按YAML解析后的字符串和值对应（不比较YAML缩进和引号写法）、目标Review与其D标记唯一、人工区完整、verdict在现有三态、意见非空；目标必须来自当前待update的初段稿：工作区Review的D身份与机器区应与该initial checkpoint一致，不能只凭另一版也叫D1就投递；人工区允许本次同字节重试的已有意见。全部成立后才一次写人工区，机器区不变；人工区内只将目标三态的一项勾选、其它两项不选，并写现有意见行，保留原换行及其余文本。空白三态是首次可写状态，不算已有不同意见。已有完全相同意见幂等，已有不同人工意见保留并报投递冲突，不自动替人覆盖。

校验失败不写任何输入、不发update请求、不置resumed_update；复用原错误出口报告目标与原因，宿主修输入后重试。混合输入在任何写入前预检全部update_inputs及额外 --deliver 的来源、路径、名字和目标，复用现有只读路径/越界校验。执行期IO失败不启动模型，如实保留已投/未投明细及已写人工区，不伪称零写入；重试按同字节幂等核。不复用源码还原事务处理材料投递，不新建事务平台。

退出match标题词与“没命中记note但继续算投完”的分支、仅证明该行为的用例。测试输入里的opinion是实际业务意见，host不能把实现解法或维护分析写进去。

## 5. 异常、等待和容量

TEST区分普通无提问推进与无业务进展的异常生成。异常时宿主保留原话和事件、向用户报告，按现有stop/retry授权决定处理；不机械发多次“继续”后算正常运行，也不擅自获得自动停测权限。正常awaiting_reply在本次唤醒内处理，延迟在观测与成本报告如实披露。

下次起跑前，维护实施者固定当前CLI二进制版本、请求实际model/config路径、实际生效的输入/上下文/输出limits、压缩触发方法与服务计量约束，只记录脱敏非秘密字段。核查结果记本步骤交回及现有运行证据，不存API key。已有2.0.2阈值算法仅作线索，不当当前程序证据；服务报错1000000未声明单位，不据此填永久常量。

只有上述事实足够才提出具体配置值与离线阈值验证，用户配置修改仍按实际授权。查不到即标E01未解决，不执行盲目重复实跑；步骤1/步骤2/步骤3其它工作可以继续。不得将模型名、服务限制或重复词写进Extension，不以扩大context作为默认修复。

沿 `measure_run.py` 与现有events/state呈现：总历时、人工等待、可确认的异常区间、正常任务/审查、外部错误、实际终点。扣等待不叫纯模型推理，多Case不加成suite历时；失败基线不证明提效。无需新计时平台。

## 6. 验证

复用 `test_multi_case_cli.py`：长问题全文可得；同阶段不同问题只有候选；一次覆盖多个step且未问step保留；非法step或目标run/turn过期发送前失败；running状态的已成功同回合重试返回旧结果；模型已到下一问时旧回复不能落入新问；回复失败不消费；同回合同内容重试不重复发送、不同内容拒绝；零计划neutral正常路径保持。修改这些覆盖的现有fixture而不是向Case塞测试关键词。

反馈投递：不同合法标题同D身份正确写入；空反馈、漏/重复source_item、改写静态立场、未知/重复ID、缺人工区、非三态均不写；已有不同人工意见保留；相同输入重试幂等；机器区逐字不变；初段身份或机器区版本不匹配拒绝；执行期部分IO失败列真实已投/未投且不启动update；所有输入（含额外--deliver）的可预检错误在写前发现。原始意见正确性仍由宿主语义判断，不用脚本判断“符合业务”。
