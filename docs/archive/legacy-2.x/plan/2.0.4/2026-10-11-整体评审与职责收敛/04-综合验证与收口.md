# 步骤4：综合验证与版本收口

前提：步骤1–3分别完成授权内改动与定向检查；上游/环境未决允许先完成本节离线部分，但不冒充真实链验证。通用边界、预算和问题ID见[实施总览](00-实施总览.md)。测试按[test/TEST.md](../../../../../../test/TEST.md)，不新增运行器。

## 1. 确定性收口

| 对象 | 输入与动作 | 可签结果 |
|---|---|---|
| 原件与复审 | 新旧材料、前轮真实报告、重复prepare、坏prepared/报告 | 当前结论绑定新材料、旧报告只作参考、历史原件不改 |
| 原生接缝 | 非默认报告目录、普通Feature/同名不同蓝图CU、坏summary、完整/缺列报告 | 实际原生目录被消费，不以缺读跳过结构检查 |
| 测试交互 | 长问、多话题、无等价选项、同D不同标题、缺人工区/重复ID | 全文可得、已答事实准确、失败不启动update、机器区不改 |
| 有效原能力 | 知识原文/义务、章提交、来源、人工区、update恢复现有回归 | 新行为成立、旧专用断言退出、有效覆盖保持 |
| ADAPT-01 | 未发布升级条目退出后安装当前开发源 | 不强求开发版本升级说明；1.x历史、知识保护和demo复制装配保持 |
| V01 | 同名原件备份→新稿导入/complete→恢复旧表达 | 不混版本；已引用冻结件保留；旧原件能否取得给实际结果 |

V01分两种现有动作验证，不能把complete当close，也不能把restore当原件恢复：

1. 同一开放轮次撤回：以已登记旧稿/输入为起点，open后备份同名旧原件、导入新稿并complete；在close前调用`update --action restore`。此时轮次必须仍为open/restore_conflicted，按当前记录是否已有本轮写入指纹判断能恢复哪些工作件；未登记的改动应保留冲突，不要求无依据强行恢复。核收件箱与冻结输入没有被restore回写、人工意见保持、旧表达与当前依据不一致会报needs_sync。
2. 已收口后回到旧业务表达：新起一轮update；由维护夹具从实际`.backups/local`旧原件取得相同字节，作为本轮明确采用的材料重新导入并complete，再走实际设计/成文同步。闭合旧轮不得直接restore；有真实设计撤销需原生修订，不能以复制旧Story代替。

以上验证材料准备由维护测试夹具完成，不向消费模型注入测试答案；真实业务恢复仍按实际材料与授权。V01复用现有入口和备份，不预先加永久材料库。有原件缺口须明确，不能把报错等同恢复成功；若正常恢复确无合法来源路径，交设计者以复现定最小修正，本步骤不临场扩机制，该项不能宣告完成。

定向检查通过后运行一次 `python test/scripts/verify.py handback`；Case计划检查使用 `python test/scripts/verify.py cases`。保留首次失败及产品/资源/环境分类，只有真实改动或新证据才重复全量。计划装配、门禁绿均不证明语义或真实模型执行。

## 2. 内容与通用性

对原材料/会议/实际人签、首稿写入、当前蓝图、写作设计、章节及附录、原始审查与修复稿、CU与实际Spec/Plan直接读内容。原件不存在或没有生成则注明，不能用最终报告自述补证据。

按当前2.0.3有效目标金样评价读者效果，不按词句、图数、标题或相同CU划分匹配。至少核已暴露的来源条件、超时未知、未决前提、专项共同设计与恢复路径。用中性业务、无相关条件及合法组织变化判断适用性，不往产品加Case词或语义正则。

CU要区分“确无相关Story承诺”和“本来相关却漏登记地址”：以真实来源、原生设计对象和CU结果核责任。过滤没匹配只证明未找到登记关系，不自动证明无义务。事实/知识应进入实际设计与承接实体，名称出现不是应用。

记录最早错误变换：来源→提取/蓝图、蓝图→人读、整体→CU；修回其负责方。已有规则完整送达仍发生误解时，如实报告消费效果，不追加同义提示声称修复。图片没有实际看过就标像素未核，caption与将来真机计划不是视觉证据。

可以完成维护者只读内容走查；新的独立消费模型评价沿相应授权安排，保持与作者上下文隔离。正式金样切换另按用户审定，不通过改金样掩盖遗漏。

## 3. 正常CLI与依赖

新CLI仅在用户启动的里程碑运行。前置为步骤1–3必要检查通过，步骤3的E01有足以避免原容量风险的真实处理证据；车钥匙CU链还需U01完整调用合同可用。上游合同/配置值尚未知时先交证据与阻塞范围，不编造接口、不改vendored框架、不盲重跑。

沿现有两Case：自动充值当前Story/Review实际送审后完成update；车钥匙完成原生认可的适用Spec/Plan或合法复用，再完成update，不编码。Story链与CU链的依赖分别说明，未到终点不以文件存在或一条“继续”代签。直接原生入口/多CU用已授权安排和现有专项覆盖核知识与范围，缺真实行为证据明确未验证，不新增完整CLI Case。

每条实跑保存实际安装身份、输入版本、完整宿主回复、初段/update终点、原始事件、独立审查写入证据、中间与最终产物。审查者直接写文件时核其写入内容；工具最后完成摘要不必等于文件。只有文本返回路径才核原始报告正文逐字落盘。

正式运行还需证明：未决与共同设计不被偷偷定案；建议有采纳/保留理由；已有授权内不重复停等；宿主没有批准夹带结论或投虚假缺陷；未向Framework目录写临时桥。Coding/设备/内网升级保持范围外未验证。

## 4. 成本评价

沿现有measure_run及events/state分列总历时、首次主体成文、必要返修、审查、人工等待、异常恢复与外部错误。字段无法精确区分的部分说明估计口径；不把task完成时刻相减当服务纯耗时，不把扣等待后的余量叫模型推理。

质量、实际输入和终点相同才比较收益；本轮失败或受污染人签只作问题证据。Case整改后的新输入明确版本，不与旧轮混称同条件。既有摘要/去重/同材料复用保留，但不宣称自动解决改变材料引发的全审成本。

不设固定审查轮数或强制一次通过。判断主体是否正确、返修是否有实质原因、建议是否合理收敛；轮数减少本身不是成功。TEST三轴给建议评价，用户确认后才记最终评分。

## 5. 最终交回

在实施反馈提交R01–R10、U01、E01、V01/V02逐项结果：证据、承担者、已解决/待验/阻塞及下一动作。未实施、未发生、未验证分别写明；不能将未完项移版后签完成。原有FW事项附当前影响与真实状态。

同时交本轮与累计G/X、分类/总量、估算差额、已退出路径和保留覆盖。旧target未达到时交设计者复核合理最终目标，不先自改额度或删有效内容。设计者最终分别签功能、内容、交互、退场与成本；结构证据不能互相代签。

本步骤不授权发布、demo更新、用户配置修改、提交或推送。外部条件未满足时保持相应待验，交回本仓已完成范围，不无限等待、不代称整版完成。
