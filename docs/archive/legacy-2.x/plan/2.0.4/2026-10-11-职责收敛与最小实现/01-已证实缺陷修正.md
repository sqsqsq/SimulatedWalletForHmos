# 步骤1：来源、整体设计与 CU 承接

本步承担 R03 的来源到设计部分、V02 的 CU 承接、原生协作和相应退场。预算、全量问题去向及权限以[总览](00-实施总览.md)为准。文件名沿已存在入口保留，正文是本轮完整合同。

## 1. 目标与当前判断

有效需求的条件、知识和责任在设计阶段形成；Story 与每个 CU 消费同一设计。不是将整个 Story 或整份知识表复制进每个 CU，也不是仅交几个链接便认为承接完成。

当前已有 `readBlueprint/readFeature`、`featureKnowledge/unitContext/unitDuties`、原生 stableAddressIndex、来源冻结、相关 Story 片段和生命周期材料绑定。保留这些承担者。缺口是蓝图作者/质询没有明确取得候选采用版本的完整来源索引，现行逐对象回查不能发现根本没有设计对象的条件；CU 内容链已有实现但未获得正常 Plan 终点证据。

必读源码：`extensions/hooks/shared/framework-access.mjs`、`knowledge-task.mjs`、`knowledge-application.mjs`、`pre_verifier.mjs`，`extensions/hooks/blueprint/author.md`、`reviewer.md`，`extensions/hooks/spec/author.md`、`plan/author.md`；Story 侧 `scripts/core/story/design-source.mjs`、`writing-plan.mjs`。原生 API 只读当前 demo 发布件，不修改 Framework。

## 2. 候选采用来源的共同解析

### 唯一读取与调用合同

在现有framework-access中完成以下局部函数，不新增模块、状态、缓存服务或CLI。下列名字固定用于跨文件交接，局部内部拆分由实施者决定。

| 入口 | 输入 | 输出与职责 |
|---|---|---|
| `blueprintSources(projectRoot, blueprint)` | 调用者已读的候选对象 | `{status, sources, requirements, problems}`；从relatedStories抽取currentScopeItems定位、版本冲突与绑定核对。sources保留原生source_ref及声明sha256；requirements返回requirement/root/version/snapshot_ref。此处不读文件正文、不再计算摘要 |
| `readSourceFiles(projectRoot, entries)` | 每项`{path, sha256}`，sha256固定`sha256:<64位原始字节摘要>`；可保留role/provenance供调用方展示 | `{files, excluded, problems}`；files每项保留输入元数据及已核bytes；excluded为路径到失败原因的Map。每项调用原生`resolveCurrentScopeSource`取得bytes/source_sha256并与声明比较；缺少或不合现行格式的声明摘要报问题；失败不给该项bytes，不以现算摘要替声明 |
| `readFrozenInputs(projectRoot, snapshotRef)` | 显式工程相对快照路径，不读flow | `{snapshot, files, excluded, problems}`；读并解析快照，将files行转为实际`<快照目录>/files/<row.path>`和`sha256:<row.sha256>`后只调用readSourceFiles。保留role/provenance/origins，自己不再循环读文件或算hash；缺失/坏JSON/不可解释的files结构报告问题，不当空成功 |

原生`resolveCurrentScopeSource`位于`blueprint-requirement-traceability.ts`，已提供工程路径校验、原字节读取、片段定位和摘要。path带片段时原样交该入口，不先剥片段规避验证；每个成功项明确输出原path引用及无片段的file_path，Markdown Map按file_path定位；excluded保留原path失败身份，不能把带片段字符串当磁盘文件路径。不同声明摘要不得合并；相同引用同摘要可复用同次结果，但多个不同片段必须分别通过原生定位。不存在跨命令缓存。

readFrozenInputs核快照路径与每份文件均处于工程内；冻结files路径还须保持其既定包内相对路径约束，不能靠`../`读到包外。摘要从既有生产合同机械转换：冻结files的64位摘要加前缀，原生声明已有前缀则原样传递，不增加旧格式fallback。snapshot没有整体声明摘要时，本函数不自证快照版本可信；flow的整体摘要检查仍由readSnapshot承担。

### 实际生产者与全部消费者切换

| 消费者 | 切换后做什么 | 同步退出 |
|---|---|---|
| relatedStories | 保留原生CU身份前置，取当前蓝图后调用blueprintSources；返回原有字段并带版本定位 | 内部重复currentScopeItems/需求路径/版本及绑定枚举；抽取移动不计退场收益 |
| blueprintTask | blueprintSources取候选采用版本；所有候选声明（包括冻结来源）均用readSourceFiles核其原引用/片段/声明摘要，再按每个snapshot_ref调用readFrozenInputs取完整包；任一来源问题停在现有任务错误出口，任务渲染真实索引/角色 | 不允许另加候选专用文件读取/hash循环；同冻结包只取一次，声明条目与包内清单分别展示 |
| adoptedInputs | 从当前flow选择snapshot_ref后调readFrozenInputs，保留原`{documents,problems}`返回形态，已核Markdown bytes投影为文本Map | 当前逐files的fs.readFileSync/sha256比较循环；文件失败不进documents，既有调用方无需另算摘要 |
| unitSources | relatedStories取声明来源后调readSourceFiles，投影所需Markdown到documents，并承接excluded/problems；随后仍按storyCurrency取得当前Story | 当前逐related.sources的fs.readFileSync/hash比较分支；不删Story当前性、排除原因和实际文本交付 |

adoptedInputs的现役调用方包括storyCurrency、images的Story图检查、story-inputs的图源列表、reader-review-task的原图对照；unitSources的调用方包括images的CU图检查、knowledge-task的storyExpression。全部沿旧外部返回合同获得同一底层核验结果，不保留新旧开关或兼容分支。UTF-8 BOM只在已有Markdown展示投影时去掉，摘要始终按原字节；非Markdown来源仍校验并可列入蓝图索引，不强行解码为文本。

adoptedInputs在尚未登记snapshot_ref的合法前置阶段保持原有空documents/problems语义（problems为空）；一旦有声明但快照缺失/损坏则不得空成功。blueprintTask不能用readBlueprint草稿返回status=ok掩盖来源issues：所有声明读取与包读取的问题均进入现有缺口/失败出口，stdout不交半份完整任务。

readSnapshot的flow快照整体摘要、scopeConsumption的条目采用关系、Framework准入/来源资格、storyCurrency的成文登记与当前性是不同责任，明确保留；不为减少行数合并掉这些资格。原生checker仍可独立重新核来源，不能用Extension一次读取绕过原生准入。外部原件origins的存活/版本核对继续归externalOriginals，不将当前inbox顶替历史冻结包。

冻结包与声明来源定位是同一套读取的两个调用输入，不是统一内容模型。公共模块不import Story层；design-source已有单向import framework-access，保持无循环。新增三个入口均有上表消费者，未被实际调用的导出不交付。

### 版本与失败

候选引用 v1、flow 已登记 v2时，交付 v1原件并明确候选版本，不能给候选配v2。flow只用于核需求的component/blueprint绑定；本次明确要求设计v2而候选仍v1时回设计负责方同步。声明摘要按原始字节校验，现算摘要不替代声明。没有历史 snapshot 摘要声明时，不拿当前 flow 的摘要套历史快照；按冻结目录内容身份和已登记 files 摘要核，不能声称获得额外的签名保证。

来源缺失、摘要不符、非法路径、绑定冲突、坏快照沿现有任务错误出口列出对象、原因与恢复动作，不输出伪完整任务。来源包坏了由来源生产者恢复或重新 complete；原生设计引用不合法回设计负责方。冻结件不可原地覆盖。

原生直接入口没有 Story 冻结来源时，正常交原生声明来源，不建 Story 登记。discovery 尚无候选时沿 Framework 已收到的需求输入和激活知识起手，不能要求不存在的候选或声称其来源已校验。合法空知识与登记损坏分开。

## 3. 来源、知识与设计的执行动作

knowledge-task 的作者/质询任务按实际采用来源及角色、候选与原生 scope、知识原文组织。替换 author.md 末尾仅“逐设计对象回原件”的单向动作；reviewer.md 的总任务从只核知识效果改为先核来源完整性再核知识效果。完整要求各在其实际读者页维护一处，不在 design.md 再复制一套。

1. 作者从原件的条件、行为、边界、异常和责任反查候选承担位置。init-analysis是定位索引，不是全量设计证明。没有承担者的有效要求进入原生设计缺口或被落实，不能因没有AC而排除。
2. 对每个已形成对象反查出处与工程事实。材料事实、人签和模型推断身份不同；接口未知字段不能被模型转写成来源已确认。
3. 质询者独立读来源后审候选，再沿原生对象scope及app_lens核关系和工程可行性。无对象的遗漏在适用原生整体质询项里给来源、影响、责任与处置，不伪造target_ref，不建立覆盖台账。
4. 设计负责方消费真实回复，补设计或取得真实裁决，再走原生修订与准入。共同设计含混不能移交Story作者改句或推给CU作为局部实现选择。

三类知识沿现有合同：事实保留来源及实际作用；每条激活规约、每个模式保留适用/拒绝/待定的真实理由；适用义务和选中角色落承担对象。不得以“已登记知识名”代替应用。当前漏判检查、实体派生已实现的保持，不重建 knowledge-use 或第二个判断文件。

## 4. 按 CU 范围交付，不丢整体承诺

| 内容 | 权威及当前消费者 | 应看到的结果 |
|---|---|---|
| 整体范围、共享关系及恢复路径 | 原生蓝图和 CU design_refs，原生准备负责分配 | 每个实际责任由承担单位引用，跨单位依赖在原生关系/契约表达 |
| 本 CU 判断与项目事实 | featureKnowledge → unitContext → knowledge-task / pre_verifier | mine交本单位落实；common交公共判断理由；undetermined明确未定，不能当不适用 |
| 规约与模式角色 | unitDuties → Spec acceptance、Plan contracts | must / pattern_roles有真实实体、决定引用和验证责任，下游直接读这些实体 |
| 已交付的人读承诺 | unitSources/storyCurrency → storyExpression | 当前且显式关联的Story片段、来源位置和摘要；不是新的设计权威 |
| Spec/Plan 人读扩展 | 现有spec/plan作者页、post_check和overlay | 技术约定、规约、模式、项目事实与适用埋点讲清本单位实际落实，不复制整份蓝图 |

当前 storyExpression 按 basisSections 与原生对象作用域取片段，其“没有匹配关联”不等于“语义上无承诺”。Spec/Plan作者在范围理解时核原生承担对象和关联Story的整体责任；漏登记由需求作者修写作设计并重新登记，不能靠关键词猜关联。直接入口无Story继续正常施工。不得恢复全需求扫描或自动关系选择层。

本轮必须验证：无mine但有common/undetermined的输入不被局部提前返回丢掉；只保留真实有关事实，不从ID字符形态推归属；同名不同蓝图CU不混用。若检查发现现行decisionTable只因mine为空而返回，改为依据三组实际集合输出，有common/undetermined仍渲染它们，三组都空才输出无判断；身份与问题列表始终保留。现有另一fragment已经交付common/undetermined，本项纠正后续表的错误空结论，不宣称此前知识完全未送达。

保持 lifecycleFragments：作者任务与 pre_verifier 的实际片段及确定性摘要进入原生材料视图；相关内容变化使审查对象变化，无关Story文字变化不为当前CU制造新对象。不新增Extension哈希状态或receipt。合法复用没有新Spec/Plan时，知识和义务仍从实际施工输入交付；不强制造文档证明运行过阶段。

## 5. 上游调用合同与签收边界

U01：Framework有CU准备能力，缺的是动作前可直接使用的完整调用方法。上游应在 component-design / change-unit-progression 给出工程根、蓝图、候选文件、`{providerId, artifact}` 来源及完整示例，串起 `evaluateDesignPreparationEntry`、`acceptChangeUnitDecomposition`、`deriveDesignPreparationReadiness`；说明错误候选不落盘、合法复用和修订后的恢复。辅助脚本只能进目标scratch，不能写framework/harness。

本仓接上游交付的方法入口，不复制consumer、validator或readiness。未交付时本步来源和知识整改可实施；不能签收正常CU准备或Plan终点。FW-04/05、术语interactive确认、直接设计资产与质询合同的既有问题按总览依赖表分别核发布件，不能笼统称全部已解决或全部阻塞。

## 6. 退出与验收

退场：relatedStories的定位实现抽取后只留一处（纯移动不计X）；adoptedInputs和unitSources两段本地文件读取/摘要校验由readSourceFiles接替；来源只有逐对象回查的动作；把当前flow版本当候选来源的拟议路径不实施；如存在只因mine为空而丢公共/未定判断的提前返回退出。保留原生scope、现役过滤、事实引用规则、知识检查和合法无Story路径。

使用现有 `test_knowledge_task.py`、`test_requirement_source.py`、`test_blueprint_case_closure.py`、`test_review_closure.py`、`test_cu_knowledge_chain.py`：

- 对blueprintTask、adoptedInputs、unitSources三入口核同一有效/缺失/坏摘要文件得到一致读取结果；新旧候选选版分别由其调用者控制。核带片段原生来源、非Markdown文件、BOM原字节、坏快照和包内越界，失败副作用均为零。
- 旧候选配新flow仍取旧包；一包多来源、人签和图均真实可读；坏摘要/绑定不输出成功。
- 原生直接入口、无知识、无Story、两个CU、共享责任、拒绝模式、无mine但有公共/未定判断分别得到合法结果。
- 在test_cu_knowledge_chain的既有覆盖中补mine为空但common或undetermined存在的preVerifier实际fragment检查；不能仅核knowledgeTask。三组全空的正常结果保持。
- 实际派生/复用后义务和角色仍读得到，Spec/Plan人读位与契约一致。
- 原生material view核相关片段变化、同字节复用、无关变化不影响。

命令：`python test/scripts/verify.py affected test/tests/test_knowledge_task.py test/tests/test_requirement_source.py test/tests/test_blueprint_case_closure.py test/tests/test_review_closure.py test/tests/test_cu_knowledge_chain.py`。

交回同时给改前/改后的实际任务输出、来源到对象的内容走查、下游消费者和退出diff。机械结果只能签身份与送达；未知业务的首次设计、真正独立质询、CU正常执行由步骤4核。预算按总览P1，不能把共用抽取或历史退场再记收益。
