# 2.0.5重写方案整体审视

2026-10-18（Asia/Shanghai），维护设计者。对象为本版spec与plan 00–04当前本地稿；来源代码观察点为story `8807b401`与story-1.0 `f5972a82`。本次是原方案作者的整体复核，不称独立评审；只记录意见和准备边界，保留方案正文与产品。不执行源码切换、Framework接入、测试实跑、提交或发布。

## 1. 结论

**基于1.9.9正式发布重新适配、保留story历史、按能力选择性复用的方向可保留。当前稿可指导盘点准备，但还不能直接交执行者切换源码。** 本轮发现五项需要补正的方案问题，见§2。新版Framework未知可以阻止接口定案，但不应阻止今天形成能力清单、成果保全清单及测试依赖清单。

今天的准备不要求先取得新版；正式发布身份未锁定时，以固定开发提交作临时盘点，清楚标为开发观察。取得1.9.9发布源后补差额，取得Framework发布件后再定接替落点。不能用等待外部输入代替可完成的现状盘点。

本次通过的是方案方向和可审部分，不是1.9.9发布、旧2.x所有成果完整性、新Framework能力或重写效果。本报告不替代后续实施合同；§2问题须在对应正文修订并核闭合后，才可据方案做产品切换。

## 2. 需要补正的五项

### R1：能力保持仍是类别摘要，缺少继承能力及逐项验收对应（切换前补齐）

位置：总览§4、S2§2“1.9.9新增”、04清单的“1.9.9发布能力与新正本”。现稿主要列R1–R8名称，没有将既有命令、停等/授权、会议、恢复、六阶段知识和新增能力分别落到保持结果。完全按现稿执行，仍可能保住新增功能名却丢掉继承行为。

事实：`f5972a82:extensions/skills/story/SKILL.md:12,47,65`分别登记stats、spec/plan作者任务包及停等真值表；同提交manifest第13行登记story-stats，76行起登记story-view/usage的阶段hook。这些均不只是Story正文内容。材料、归档、恢复、授权及正常失败处理也不能由“R1–R8保持”一语代签。

修订责任在设计者：按§3逐项登记原行为、发布状态、源码/测试/证据、应保持的可观察结果；新落点今天可留待定。发布时未完成的能力不是已成立基线，但仍需明确留在1.x、进入本轮或留后续，不能静默遗失，也不能自动扩入本版。最终发布SHA到位后补差额。

复核方式：从发布README/SKILL/manifest/规格/最新交回和测试两向核清单；每项有效命令、知识出口和用户可见能力至少有去向与验收，不用文件名一致证明行为保持。

### R2：保全与复用定案混在一起，S1的前置可能形成等待循环（今天可明确）

位置：S1§1第11、15行要求每个差异文件给处置、“全文件处置已核”；同时S2才依据新Framework确定接替者和复用位置。部分文件尚无法决定复用或退出，若把“处置已核”解释成最终去向定案，会使S1无法结束，也无法安全开始替换。

应拆清两个结果：S1先证明所有旧文件/行为/证据已覆盖、有可恢复来源和当前状态；S2再决定复用、由Framework接替、由新Extension实现或退出。S1允许“已保全、去向待新版”，但不得把未盘点伪装成待定。最终复用决定不作为今天保全准备的前提。

保全还需区分Git内和Git外：固定提交可保留已提交源码；未提交差异、未跟踪评审、运行原件和本地配置不能仅靠SHA找回。为实际将受覆盖/清理影响的文件确定唯一副本、输出位置、来源与摘要，并检查恢复可读；其余任务文件保持原处且不纳入本任务提交。证据不存在则明确缺失，不补造报告。今天只需盘点与制定保全清单；实际副本写入属于后续准备动作，本次未执行。

复核方式：任选被替换旧文件可从固定提交取回；受影响的Git外文件从登记的副本取回并核摘要；每个候选有目的、依赖、证据成熟度及未解决问题，不能只保存无上下文代码片段。

### R3：测试迁移缺少整套依赖闭合，安装装配不能留到最后（首个实现包前补齐）

位置：S1§3、S3–S4§1–2。现稿知道不能盲换测试，但仍主要按测试文件/Case/金样分类，并把安装和测试装配写在最后收口。旧新manifest、发布安装器、template、harness与公共夹具必须先能配套，才有条件验证首个适配动作。

实际证据：`f5972a82`没有`test/scripts/verify.py`、`test/tests/shared_state.py`、`test/tests/conftest.py`；story有这些文件。`8807b401:test/scripts/run_multi_case.py:241,255`显示template由现役安装函数装入开发源，不是复制extensions即可起跑。1.9.9 manifest为schema 1.0且登记bridges、story-stats及usage hook；story manifest为schema 1.1并使用phase_bindings。未执行安装实验，不能断言某个组合必失败，但已足以否定“只迁用例即可形成可运行基线”。

设计者应按§4先列依赖集合和来源。今天可核现状依赖，实际新版兼容处理等S2。首个适配实现包要含最小可用安装/物化、配套测试装配和定向回归，不等待业务主链全部做完才补安装；完整对外adapt增强仍按版本范围，不借装配修复引入2.1.0新分发能力。

复核方式：发布基线在其原生组合下可复核；新组合能在空白一次性template装入开发源，入口和登记引用完整，随后真实测试可以被收集和执行；不能靠排除装配失败或运行旧发布件取得绿色。

### R4：源码切换提交与可验证交付条件脱节（正式切换前定案）

位置：S1§3第29–33行。现稿提出单独的基线切换加升版提交，同时承认测试迁移在后、checkout是混合环境。根TEST §5要求提交或交回前完成相应离线检查；当前没有说明该提交如何达到一致且可验证的状态。

建议维持用户要求的“先逐字节核1.9.9，再升2.0.5”，但将其先落实为scratch中的完整发布基线和受控本地校验，不承诺提交一个与当前Framework/测试错配的开发树。正式story首个代码包应同时包含获批的最小适配及配套装配/测试；切换前字节同源证明与适配后差异分开保存，首个extensions变更提交仍按项目规则升2.0.5。

如果确需独立提交纯源码基线，设计者应另给能通过适用检查的完整配套或提出明确例外供用户裁定，不能由实施者自行跳过失败。今天可准备路径清单、差异和恢复操作；当前不执行源码替换。

复核方式：明确每个拟提交包的产品/Framework/测试身份及可执行验收；没有“先提交不可验证状态，后续再补”空档。源码恢复仍按精确路径处理，不覆盖其他在途成果。

### R5：金样身份、来源文档与业务决定需一起迁移（测试基线切换前补齐）

位置：S3–S4§2“金样及Case”、04清单。现稿提出采用1.9.9正本，但没有具体指出其审定记录、来源映射、图片资源、模拟前提和未决状态怎样保持可追溯；只复制正文会形成缺链的效果标准。

事实：`f5972a82:test/golden/README.md:17–18`明确两组于10-17获用户认可，列出审定对象/逐文件身份文档，并保留业务未决。正本README中的审批链接指向该分支`doc/plan/1.9.9/`。当前story尚无这套新文档；直接复制正本会产生缺失引用。该分支spec头部部分进度仍早于正本迁移，不能只读一份状态摘要判定当前事实。

设计者应将必要审定/来源文档按固定提交非冲突引入或提供明确可解析的来源记录，连同图源、SVG、界面图、Case立场和README一起核身份。维持金样未决与构造前提；金样获认可不等于真实业务决定已签，也不等于当前产品已经实现选择性SVG。新版产物布局与设计载体变化另审，不改写1.x已审正本冒充新版金样。

复核方式：从每个对照结论可追到原始材料、审定身份、模拟前提和当前决定；资源引用均可读。新版结果不要求相同篇章、图数或文字，但有效事实、关系和读者目标必须保持。比较成本前确认两次输入与终点可比。

## 3. 1.9.9能力保持的最低盘点面

下表是今天可以建立的盘点结构，非全部能力已验证的结论。每行在正式发布身份锁定后补来源、状态及实际验收；源代码是否同名不作为完成条件。

| 能力面 | 保持结果与需要防止的遗漏 |
|---|---|
| 取材与本地单 | 系统材料拉取/缺单处理与本地材料入口各自有效，来源和范围不被蓝图入口取代后丢失 |
| 关卡与授权 | 材料确认、会议裁决、范围/承载选择、推进边界、归档/恢复授权只在适用条件下发生，不重复问也不跳人签 |
| 收件箱/材料清单 | 子目录相对路径身份、同名不同路径、冲突预检、原件集合及材料贡献说明贯通update |
| 人读叙事 | 完整业务、页面/操作连续性、条件/异常/恢复、验收和技术查阅层均有承担者 |
| 图文/SVG | 来源图可定位、合适的表/图承接、选型和资源交付/阅读切换按最终发布合同核；仅金样先改的不视作运行能力 |
| 知识与各阶段 | 项目事实、规约与模式保持有效，作者动笔前送达，蓝图/CU及六阶段适用责任都有出口 |
| Review与独审 | 人工区不被代填，决定与建议分开，原件/格式恢复/warn/视觉限制都有有效处理 |
| archive/restore | 归档内容、附件、覆盖前授权与线上恢复一致；系统二进制资源能力按真实发布限制声明 |
| update/续接/撤回 | 新材料、评审反馈、人新决定、直接改稿、会话中断、同名换版及新轮次可恢复，人工区与历史身份保持 |
| plan至testing | 原有后续阶段的知识义务、验证和闭环保持；不因只验Story就认为全部生命周期已保持 |
| adapt | 首装/升级所有权、知识适配、盘点/独审、状态与ignore保护等按发布实态保持；不自动扩大到新三目录分发 |
| usage/stats | 初始化元信息、自动阶段采集、补采/对账、Git关联、并发及统计成文有真实消费者；新蓝图与多CU不能重复统计或漏阶段 |
| 一次做对/快速恢复 | 公共命令/帮助、写前参数检查、完整诊断与未执行检查、登记顺序、部分成功和可运行恢复入口不退化 |
| 金样与装置 | 新正本、来源与模拟前提保持，忠实宿主输入/幂等/冲突/部分写入恢复覆盖仍在 |
| 安装与宿主发现 | Story、adapt、stats及需要的知识入口可被支持宿主实际找到；原生物化接替旧bridge时核发现和调用 |

判定分别标为已发布且保持、发布前待核、已有缺陷、目标架构待定、明确后续范围；不能把“发布基线”理解为该版本spec所有承诺均已实现。发现缺陷不必因此否定全部1.9.9，但不得用重写消掉欠账。

## 4. 测试基线必须分开的对象

| 对象 | 版本和依赖 | 用途与完成条件 |
|---|---|---|
| 1.9.9参照组合 | 正式发布源码＋原配Framework＋该发布测试/Case/金样/安装器/配置 | 证明拿到的来源自洽，记录其原验收和限制；新Framework未到也能准备，正式复跑需先锁发布身份 |
| 旧2.x证据 | 固定story源码＋当时Framework/Case/输入/报告 | 保留有效反例和未完成事实；不与新组合混用通过数字 |
| 新2.x目标组合 | 1.9.9起点＋新版Framework＋已定适配＋迁移后测试/装置 | 先证明实际装配与定向回归，再验组合行为；等待新版才能定API、引用及期望布局 |

每套组合记录完整源码身份及在途差异、Framework构建、测试装置来源、Case输入/立场/终点、金样身份和非秘密配置。环境/CLI身份不同则说明，不能直接相加测试通过数或拿用例数量相等作覆盖保持证据。

今天盘点测试依赖至少包括：发布安装器与entries、template/workspace复制及排除规则、根配置与pytest入口、公共helper/fixtures、ts转译缓存、Case/本地需求系统及adapters、模型/宿主配置、中央CLI及契约测试、失效形态checker/夹具/条款、金样及来源图/审定文档、预算算法与台账。精确文件清单按实际引用得出，不另造测试框架。

迁移以原业务断言为单位标明保留、换消费者、新合同替代、或已失效并说明依据；旧失败用例不能只删，新测试也不能只核新增字段。正式全量需记录收集失败、跳过、预期失败及未迁完项；“全绿”只能在声明范围内成立。原生Framework测试不能代替Extension业务回归。

## 5. 今天可做与等待边界

以下“今天可做”指不依赖新版的准备范围；本次只执行只读核查和本报告写入，没有实施其余操作。

| 工作 | 今天可推进 | 必须等待的部分 |
