## 1. 起因与判据

用户 10-03 指出，design 页「五」第 90–93 行是补丁式说明：

> 宿主确实没有独立执行能力时，照实告诉人缺什么，不自审顶替……已有不通过的结论、坏报告、没派审或工具失败都不归这一类

这类话是对评审的回应，可以写给设计者；Extension 是给执行模型写需求用的，不能这么写。用户判断不止这一处，要求全量排查。

**排查范围**：`extensions/` 下除 `knowledge/` 外，所有会送到执行模型手上的文字。

| 读者面 | 内容 | 处数 |
|---|---|---|
| Markdown 页 | SKILL、phases、rules、reference、templates、各阶段 author 页 | 224（另有 4 处共用段落） |
| 数据文件 | 判据 yaml、章节合同 json、manifest、SKILL description | 约 60 |
| 脚本输出 | 报错、下一步提示、生成的任务文档 | 55 |
| 真实的不一致或错误 | 见 §3 | 6 |

**三类问题**：

1. **补偿式或反驳式否定**：「确实」「不归这一类」「顶替 / 冒充」「不是 X 而是 Y」「不算……」「如实 / 照实」「真正 / 真实」「不另立 / 不再」。这些读起来像在回应过去的评审或失败。
2. **写给维护者的内容**：设计理由、历史事件、评审口吻、Framework 内部函数与字段、门禁内部机制。
3. **点名过去的错误行为**：写「别再这样做」，而不是写正确做法。

**依据**：
- 根 AGENTS §3.2「正向表达」：交付面写做什么、怎么做；禁止性规则保留明确边界。
- 报错只讲在哪、什么问题与机制，不列修法选项。
- 记忆中的用户裁定：正向写，不写补偿句（09-25）；正文写业务，不写文档自身。

## 2. 改写原则（请确认）

- **写目标形态**：做什么、怎么做、做完是什么样。
- **禁止性规则只留明确边界**：每个边界在一页只说一次，写成范围句，不写「不算 X / 不是 X」的列表。同一意思在几页重复的，只在一页正向写，其余引用。
- **报错**：只讲在哪、什么问题、机制和下一步命令，不辩解、不列修法清单。
- **Framework 内部名**：只留模型实际要调用或要写的；「原生」一词换成它具体指的东西。
- **删掉的理由与历史不丢**：交回时按文件汇总给设计者。
- **判据要求不变**：判据的审查要点（漏、编造、替人定、伪定案、图与关系、跨章矛盾）全部保留，只改写法。
