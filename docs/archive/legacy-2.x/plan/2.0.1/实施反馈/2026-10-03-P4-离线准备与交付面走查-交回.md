## 2. 退场断言核对（分册 §2 末段）

六类维护错误行为是：
- 代码审查格式或无关 JSON；
- 首份报告锁定；
- prompt 暗示补料或禁止命令起手；
- 成文即送审；
- after_initial 即已更新；
- 新来源配旧依据。

逐类检索了 `test/tests`、`tools/cli/tests` 和夹具，没有找到要求这些行为成立的断言。拒绝这些行为的断言都保留了，例如：
- 报告引用非审查材料判 report_invalid；
- 真实复审的新报告不被拒；
- 起手提示恰好是 `/story init <AR>`；
- 登记不等于送审，仅有归档记录不算送审；
- 只有 `after_initial` 不算已更新；
- 材料变了要重新冻结才能收口。

处理了两处边界情况：

| 位置 | 情况 | 处理 |
|---|---|---|
| `flow/routing.py` 登记成文之后的下一步代号 `run_archived` | `status` 把它作为 `next` 送给模型，而这一步实际是交付门和交付选择，代号却暗示「成文即送审」 | 改名为 `run_delivery_gate`。消费者 `check_failure_modes.py:2451`、`test_flow_contract_signs.py`、`test_material_rounds.py` 两处同步改 |
| `test_flow_contract_signs.py` 文件头 docstring | 仍写「交付门之后的问法只有『归档送审 / 进入 plan』」 | 改为现行的五种交付选择 |

其余几处看过后保留：
- 已归档之后旧 archived 标记仍在，同时提示回写；
- `story_written` 之后新料不开新轮；
- 中途续跑的提示里不含 `/story init`；
- Framework 阶段 verifier 的协议字段。

这几处都不要求错误行为成立。

## 4. 交付面走查（裁定 §4「其余旧表述」）

做法：§5–§7 的候选逐条对照现行代码核两点：
- 是否真的送达执行模型。判据 YAML 只有解析后的值送达，manifest 和代码注释都不送达。
