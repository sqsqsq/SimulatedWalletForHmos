# 修复后为什么仍有大量问题：沿真实行为链复核

本稿是 2026-10-04 的深入诊断，承接用户“不要草草下结论”的要求。不把新增提示、扩大 checker、缩短文档作为预设答案；本轮不改产品，不启动模型，不继续堆实施条款。此前 2.0.2 方案是待审稿，本稿指出它尚未充分解决的部分。

## 1. 先纠正前两次分析的不足

“接口投得太多”“提示没送到”“上下文太长”都是现象或部分原因，不能直接推出删接口、再发一次提示、缩小输入就是正确修复。

此前评审正确区分了离线与行为证据，没有签收整版；但评审资源较多投入到格式/路径/摘要、恢复及维护统计的机械完整性，对正常需求里“人如何作决定、设计如何保持一致、审查如何独立”的组合验证不足。这解释了局部返修多轮通过，真实运行仍出现同类失效。责任不能全部推给实施者或消费模型。

本次新增的关键事实：Plan 作者要求完整送达仍执行错误；派审缺少必要身份输入；作者以统一默认理由修“重复”；审查连续多轮修同一业务决定的不同副本。这些事实要求调整归因，而不是重复旧结论。

## 2. 因果链一：机械保真替代了产物职责，导致接口膨胀

**目标：**Story 让评审者理解业务、风险、边界、未决及验收；蓝图与施工契约保存可追溯的精确设计。

**方案变化：**2.0.1 分册 04 §4 将字段、类型/可空、映射、错误、幂等、非功能逐项纳入 Story 投影要求，并将未知结构作为投影适配缺口。此要求原本为修复递归摊平/丢字段，却没有先裁定哪些事实必须在何种交付物中出现。

**实现：**`appendix-readers.mjs::contractRows` 全量遍历契约，`appendix.mjs` 用同一投影作为写入和检查标准。机器可以保证表格与蓝图一致，不能判断这些表格是否服务 Story 读者。

**执行与产物：**补全 SR 字段后，模型新增 DTO/直接映射，投影如实展开。接口数未增长，Story 接口小节却增长约一个数量级。自动充值多个接口重复同一个 create 失败协议号策略；updated 占位响应被放进“必有”字段表。这不仅是字多，也使不确定内容呈现出确定契约的外观。

**为何上轮测试不拦：**`test_story_build.py::TheMachineZoneComesFromTheSource` 检查重投跟随真源、没有模板占位、作者区不损伤。这些是有效测试，但其正确性标准是投影忠实。一个设计占位被完整投出，可以同时通过“没有 {{模板占位}}”而仍不是真实已定接口。测试没有错，签收推论扩大了。

**反事实：**只删 mappings 可以减少字数，但不会解决 updated 是否已定、create NFR 被复制到查询接口、正文与决定冲突。因此“精简附录”不能作为这一链的完整根因修复。

**责任：**维护设计者先定产物职责与精度；实施者按合同投影；设计作者负责源设计语义。不能让渲染器替作者判业务，也不能把全部字段强制展示当成不丢功能。

## 3. 因果链二：决定有登记，但同一决定的含义在多处被重新写

自动充值“改面额是否即时生效”有清晰时间线：

1. 第一轮 Story 审查 `77cd0d15469bf7d1` 指出正文/AC-R6 对 D3 未决替人选边。
2. 作者改正文，第二轮 `7e91a9d422328671` 才发现 decisions D1 与 Review 仍写“改门限或面额即时生效”。
3. 后续正文与决定进一步同步，蓝图 `scenario-update-and-cancel` 的 target 却仍写面额按新值生效。
4. 审查者已看到该矛盾，因“蓝图侧、后续阶段会看 gap”降为 INFO。最终 r2 和更新产物仍保留此差异。

这里不是缺少一条“跨章一致性”提示。`story-reader-rules.yaml` 已要求 Story 与蓝图的含义冲突在交付前阻断；2.0.1 方案也要求回最早责任修。实际处理却以发现所指文件为修复边界，而非以业务决定及其影响为边界。

当前存在两类权威：人的业务决定登记与蓝图的设计决定。两者职责不同是正常的，但“业务结论变了，蓝图哪些具体对象必须同步”仍主要靠作者记忆。materialKey 能发现字节变化，不能发现不同文件自洽地保存了相反含义。原生蓝图 identity 也不能自动证明它忠实于人签。

独立审查并非无效，它抓到了实际错误；失败在于后续处置把总体矛盾拆成各文件的小修，再以“我的正文已对”放行。继续给所有文件各加一个 checker 或让所有产物全文互抄，都只会增加副本和返修面。

**反事实：**如果一次性修完整个决定链，第一轮真实发现本可收敛；如果只把 Story 摘要化，canonical 中错误的场景仍会交给 CU。因此这条根因与接口篇幅无关，必须单列。

## 4. 因果链三：派审的机器事实靠主模型重组，造成格式返修与证据失真

### 已核的实际输入

`independent-review.mjs::prepareReview` 先生成 task，再把 task 纳入 materialKey；为避免自引用，不在 task 内写 key，而通过返回 JSON 单独提供 `material_key/task/report_file`。

对自动充值主会话的 8 次 Story task 调用逐项检查：派遣 prompt 中均无完整 64 位材料键。它们带 task 路径、报告路径，以及主作者自己整理的审查说明。报告目录只有 key 的前 16 位。以 `prt_1025d22d0001ddHKNuqQxmeD1f` 为例，主作者要求第一行写材料身份，却没有给完整身份。

这不证明所有审查者最终都拿不到 key（它可能自行读准备记录），但证明**设计要求的显式交接没有执行**；任务不包含 key，主派遣又漏了 key，必要输入被变成审查者需要自行发现的隐藏依赖。

实际后果与此吻合：`prt_10261782c001eyT5z6pIwprZeH` 主作者把报告的 16 位 key 手改为 64 位。随后 `prt_102637673001fJA065iEBT7CfV` 又用脚本压合判据表，后续再改引用位置。语义结果尚未重新独立判断，机械入口已经给了消费方可通过的报告。

### 另一个冲突

同一派遣 prompt 一方面写“只读材料、不改任何文件”，另一方面又要求把报告写到指定路径。还同时转述 `blocking_findings/advisories` 等语义分类，底层严格要求一张只有真实判据 ID 的表。判据本身只有 `story_reader_review`，任务却包含很多具名维度；审查者把维度当判据行，是可理解但不合法的输出。

此前方案写清了正式合同，但实际交接仍允许主模型在调用时重新组织整套合同：身份漏传、写入职责互相冲突、格式解释漂移。这比“报告解析器太严”更早失效。

### 为什么 check 不阻止作者改原件

check 读的是当前磁盘字节，核格式、材料键、位置与严重性一致；它没有宿主 task 原始回复的独立证据。material_key 绑定的是被审材料，不证明报告是谁写的。目录绑定、历史复用、只读 check 都不能解决这一点。

这不是要求立刻增加防篡改框架。当前应先把已有宿主返回/留存与派审输入责任闭合，实际核独立过程。只再写一句“不准作者改报告”，或仅让审查者自己落盘，都不能证明原件此后未被作者改。

## 5. 因果链四：独立上下文不等于独立判断

本轮真实派过隔离子代理，不能继续归因“没有独立审查”。但后续派遣反复使用“此前 blocker 已全部关闭”“最终轮”“只作机械修正”等作者结论作为开场，要求审查者对既有修复复核。任务也写“旧报告仅供参考”，两种信号同时存在。

自动充值 reviewer 的推理记录 11087 行附近明确辨认出正文与蓝图冲突、想到当前判据要求阻断，随后仍因前轮已列 INFO、属于蓝图侧而维持建议级别。这是已有结论对判断的影响证据；不能证明唯一因果，但足以否定“有隔离子代理就保证独立判准”。

同时审查者须在一轮中核会议、未决、已定来源、十章质量、图文、接口、全部规约、来源清单、蓝图及附录。只有一个总判据字段的报告格式并没有减少这些认知任务。作者区被嵌入任务、机器区再读磁盘、原始来源另读，使审查者还需处理版本与表示差异。

把这些维度拆成更多 agent 不是本稿结论。首先需要恢复明确的审查目标、无预定结论的输入和一致的材料版本，再核当前执行者实际阅读与判断能力；增设 agent 不能替代正确任务设计。

## 6. 因果链五：“要求已送达”被误当成“知道怎样正确落实”

车钥匙 `prt_1026c6bc30018vZ3GeTvwDRoav` 的 read 返回了 plan/author.md 全部 60 行，未截断；第 42 行明确实机规约应写 ut/device/both。随后 `prt_1026d7284001GiQ3n3Z7Nw0UmH` 写 contracts，最终六处仍写 verify: review。

因此这六处不是该规则未送达。错误在实际取知识条目执行体、选实体与填写验证责任的应用动作；post_check 对这六项报错是在履行职责，不能因报错次数多把它删掉。

与此不同，SEC-01 对业务身份的脱敏问题是知识原文边界过宽：要求“任何出口”，模型忠实套用到精确识别收件人的请求字段，就可能让请求无法识别人。完整读知识、挂上 must 并不等于知识应用正确。规约样板需要语义纠正，不能增加一个“账号字段例外”脚本遮盖。

更典型的是自动充值修复规约重复：`prt_102470382001oGCW1Bi9FYGnOW` 把临时生成器的默认 rationale 改为“在下列设计对象上落实该规约要求并承接其实施与审查：<target_refs>”。这消除了与 requirement 的原句重复，却没有提供理由，而且应用到 not_applicable 条目。投影忠实显示了新套话，机械检查仍能通过。

这是**以表述去重替代业务判断**。上一轮只要求“理由不重复/来源可回查”不够；但进一步做相似度去重更错，因为脚本仍不知道本需求为什么适用。

## 7. 因果链六：送审与施工准入的边界没有闭合

真实需求常带业务未决，Story 需要把它摆给人。`design-source.mjs` 却要求先取得 delivery 模式的已准入蓝图，否则成文停下。原生准入又要求当前缺口标 blocker，同时当前一般 blocker 未进入 admission 的派生集合。

于是出现两个实际行为：自动充值推理按 checker 规则保留 blocker 但填写 pass/空 blocker_refs；车钥匙将当前撤销时限冲突改成未来切片 open_decision。前者有已复现原生 helper 缺口，后者是作者对影响范围的错误决定。不能只归为模型不守提示，也不能只修 helper 后宣布整个送审链合理。

深入核了 `change-unit-design-gate.ts`：它会检查实际 design_refs 中对象的 status/disposition，以及契约 authoritative provenance；不是下游完全没有保护。但它的注释又依赖上游完整 admission 派生能反映 BLOCKER。当前已确认的是这一信任前提存在缺口；尚不能未经完整 CU 复现就宣称所有 blocker 都能进入施工。

真正需要定案的是：未决设计可以交人评审到什么程度，哪些受影响范围不能施工，原生状态和引用如何表达。简单增加“所有 blocker 都禁止 Story”会破坏本来合法的送审场景；简单允许 pass 又会夸大设计成熟度。

## 8. 上下文超限是累积结果，不能替代上述归因

车钥匙到 Plan 前已经历材料理解、蓝图构造/质询、Story 多轮审查、CU 准备与 Spec；后段围绕 facts baseline、scope 指纹和首阶段资格反复调查。上下文里既有必要业务资料，也有重复大块 YAML、报告和对 checker 的猜测。

服务输入超限是最终直接故障；是否还有宿主压缩配置不当，当前尚未完成配置来源核实。不能把“增加压缩”作为业务矛盾和审查失真的修复，更不能直接把错误中的 1000000 当 token 单位。

facts 问题也还不能确定全归上游：最终现场已被多次手改。必须以干净的正常 Spec→Plan 重放，区分原生正常派生使 baseline 失效与模型错误改写造成的失效。本稿保留未知，不用模型的推理猜测当 Framework 缺陷证明。

## 9. 为什么一轮修复没有解决：四个验收对象被混用

| 实际证明了什么 | 被误当成什么 | 这轮反例 |
|---|---|---|
| 文件与引用存在、摘要一致 | 决定真实且语义一致 | 同一面额决定在正文、Review、蓝图中不同 |
| 字段被完整投影 | 产物对目标读者完整而合理 | 接口映射占四分之一，埋点设计反而概括 |
| 隔离 task 调用了、报告格式合法 | 结论独立且原件可信 | 作者预先概括修复结论、再手改报告 |
| 知识送到且有实体 must | 知识正确应用并可施工 | verify 写错、身份脱敏破坏接口、理由套话 |

离线测试并非无用或都错。报告协议测试明确使用 `design_kit.write_review` 构造正确回复，它证明协议消费；投影测试证明源跟随；知识测试证明字段/地址/消费者。问题在于缺少与这些证据配套的业务链判断，以及发现后没有把同类问题返回共同设计责任。

对维护过程同样要问：如果修的是表格解析，就只签表格解析；如果修的是权威交接，就必须看原话、实际派遣与全部受影响产物。这比进一步追求测试数量有价值。

## 10. 对当前 2.0.2 草案的影响

现草案的方向中，保持原件、当前来源派生、正常阶段复现仍成立；但不能把它当已完整闭合的实施方案：

- P1 的“保持待定不夹带策略”要与真实人签的权限、决策变化消费一起定案，不能靠选项禁词。
- P2 若只删除内嵌正文改放索引，会把重复输入问题换成漏读/截断问题；需先定实际派审输入与完整阅读路径。完整 material_key 当前已有机械来源，却没有可靠交到接收者，这是必须先解决的接缝。
- P2 的接口粒度尚未定到 Story、现有设计投影及归档附件消费者；不能先删表再考虑读者如何取得设计。
- P3 不能再以“补作者提示”解决已读规则仍错的应用问题；post_check 的有效检查应保留，并验证正常实体落实与错误恢复。
- FW-04 与送审可带未决之间必须协调；不能只要求上游收紧 checker，却不给正常送审留真实可表达状态。

本稿先形成根因与证据，不在尚未闭合处继续新增框架或局部补丁。下一次完善方案应以这些责任合同为单位整体走查，涉及重写时按用户级 AGENTS 单独提议并等待确认；不自行重写现草案。
