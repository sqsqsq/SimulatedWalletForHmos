## 2. 决定怎样成立和变化

模型先读实际来源，列已定、冲突、未知与对当前需求的影响，再组织必要问题。一个选项表达一个可裁定决定；“保持待定”只保留未知、负责人和继续条件。临时实现策略如有必要，单列建议和代价，由有权人明确选择，不藏在推荐的“保持待定”选项中。

已明确且无冲突的授权不重复问。人只确认身份/术语不等于批准业务变化；确认送审不等于准许施工。新临时策略获批准后照实记录为此次决定，不改写成原会议已经决定。

**修改单位是业务决定。** 表达澄清只改人读内容；业务结论变化由作者在现有 update-notes 或设计处置说明列出影响的决定 ID、原生设计对象、Story/Review/验收及施工责任，模型据真实语义判，不建立自动影响图系统。按顺序修决定来源→原生设计及引用→人读件→相应检查。不能先把正文改对就把相反的 canonical 留作 INFO；未受影响的章节和设计不重写。

已有人签但发现题目夹带未告知后果时，不删除人签：向人呈现原问法、实际选项及新增影响，取得必要澄清；此后按新决定继续。历史测试产物仅作证据，不直接改成“正确结果”。

## 3. Framework 设计交接

示例命令按安装后工程执行，`F` 为需求标识，`B` 为显式 blueprint_id：

```text
python doc/extensions/skills/story/scripts/core/story_flow.py bind-design --feature F --component <真实组件> --blueprint B
python doc/extensions/skills/story/scripts/core/story_flow.py complete --feature F --from AR/story-src/design-draft.md --input AR/story-src/design-input.json
```

冻结输出先按原生 materialization 校验（本地来源沿原生本地规则）；然后 `/component-design B` 明确请求“完成可评审设计与独立质询，本次不做 CU 施工准备”。作者取得激活知识、来源和实际人签；主执行者沿宿主隔离能力派质询，交当前候选、原生 scopes、完整必要知识和来源，保存真实回复，设计负责方处理后形成原生结果。直接 `/component-design` 同样消费已登记扩展资产，见 06 FW-01/02。

转写接口的原文字段保持来源事实；类型推导、本地映射、占位响应保留 inferred/未知，不因放进契约表或 source_ref 指自己就成为 authoritative。共同业务缺口的 needed_by 由真实使用范围决定；设计中尚未成立的确定字段不得伪装必有。

设计必须覆盖实际需要修改的业务和宿主模块。只加路由也是修改；发现 CU touches 不覆盖它，回原生设计修订，不在 Plan 私增范围。设计 revision、投影和 CU 有效性均由 Framework 处理，不手填摘要、receipt 或 completion。

## 4. 审阅与施工的原生接缝

定案行为：源可回查、结构/引用有效、实际质询已完成、内部主张一致且未决范围清楚的设计可以供人评审。业务未决进入 Review，Story 只陈述共同成立的行为和条件。当前依赖未解除的 CU 不可施工；真正远期缺口不阻止无关 CU。身份坏、投影过期、质询缺席或源事实矛盾不属于可带着交付的普通未决。

Extension 从原生接口取得“可评审”结果与投影，从原生 readiness 取得施工资格；不由本地列 issue 白名单推断资格。`framework-access.mjs`、`design-source.mjs`、flow 路由统一消费同一结果。具体拟议上游返回合同在 06 FW-04；当前发布件没有该合同，依赖未就绪时继续保留现行边界，明确报告缺口，不用 draft 模式临时放行。该接线必须等上游发布后实施，其他本包修改可独立验收。

## 5. 知识的应用而非回显

修改知识样板 `knowledge/constraints/security-privacy.md` 的 SEC-01：日志、统计、非授权展示应脱敏/排除；业务接口按明确用途、权限和安全传输约定使用必要身份，不可把展示用不可逆掩码传给需要精确识别的接口。无用途/权限约定保持未知，不自动豁免个人数据。目标仓知识不由 adapt 覆盖；样板修正记入既有升级说明。

设计作者对每个激活条目给具体理由：本需求何种事实满足适用条件、实际对象做什么、不适用的边界是什么。requirement、rationale、target_refs 各表达不同职责；不适用条目不写落实义务。模式选型说明角色与协作，不能只有名字。继续使用原生 decisions 与现有 knowledge-application schema，不新增 per-Case 字段，不用相似度/词表判语义。

## 6. 定向验收与交回

`verify.py affected` 运行 `test_meeting_material.py`、`test_requirement_source.py`、`test_knowledge_application.py`、`test_cu_knowledge_chain.py` 的受影响组；按实际文件修改缩小选择，不为改文义无关全跑。

| 输入/动作 | 可检查结果 |
|---|---|
| 中性会议只说等第三方确认 | 推荐保持待定不附带默认重试行为；原话/选项/人签保存；语义由评审者读内容核 |
| 单独批准临时策略 | 记录此次授权与边界，不伪称原会议结论；重复记录按现有幂等合同 |
| 一项决定改变多个产物 | 同步具体原生对象与人读结论；未修 canonical 不以“正文正确”签收 |
| 请求身份与日志显示各有出口 | 业务能识别人，非授权输出不泄露；义务有具体方法，不只是 SEC 编号 |
| 合法未来缺口/当前缺口/坏来源 | 按 06 原生结果区分，不由标签或空 blocker_refs 绕过 |
| 新宿主路由 | 蓝图→CU→施工文件修改范围一致；恢复/重入不私造授权 |

真实独立质询、提问质量与未知需求知识效果留 P4 验，结构正反例只证机械合同。本包交回分别列本仓通过范围与待上游接线，不把全部标为“可施工”。
