## 2. F1：component-design 资产声明没有对应消费链

**输入与复现。** 在合法 1.1 扩展登记以下内容，两页真实存在：

```yaml
provides:
  skill_assets:
    component-design:
      extension_author_requirements: hooks/author.md
      extension_review_requirements: hooks/reviewer.md
```

运行原生 extension inspect/verify；用 `loadInstanceExtensions` 和 `resolveSkillAssetPath` 核路径，并从宿主 component-design 跳板跟到 Skill 及蓝图工作流的实际读取指令。

**实际。** loader 无错误，资产可解析；inspect 两行均为 consumer=/component-design、state=scheduled。component-design 和 app-component-blueprint-workflow 没有读取这两个键或枚举该桶的指令/调用。只有全局知识表、惯例读取等其他来源；不能把这些来源当作 skill_assets 已被消费。

**依据。** `skills/project/extension/SKILL.md` 和 `docs/operations/component-design-host-adaptation.md`、`MIGRATION.md` 明示 component-design 知识走 skill_assets；`harness/scripts/utils/extension-inspect.ts` 对任何 skill/key 直接生成 scheduled 行；`harness/extension-loader.ts` 和 `profile-skill-assets.ts` 只证明登记/解析。

**预期及最小修法。** 明确受支持资产键和读取时机，并把相应内容带到设计作者及其独立质询；或明确真实可用的等价公共输入方式并修正文档/inspect。未知、无消费者的资产只能显示 available/declared，不能仅凭登记标 scheduled。无需新增 provider、phase 或任意脚本执行器。

**验证。** 有/无登记、缺文件、未知键、直接设计与经宿主转入均覆盖；核任务要求实际送达，而非只核清单。未运行模型，因此本报告不声称模型绝不会从 global 索引主动读取知识。

## 3. F2：无 Feature 的独立人读审查能力请求

需求是：宿主已有 Story/Review、真实来源、蓝图和读者判据，希望独立执行者审查当前对象，复用同内容报告，内容改变后拒绝旧报告；不创建虚假 Feature、Spec 或 phase receipt。

已核两个入口：

1. 现有 verifier 的 request/subject/报告检查可用，但正常入口绑定 feature/phase 和相应 summary。适用入口不能由宿主手填一个虚构 feature 来替代。
2. `harness-runner --phase review --request-file <file> --report-dir <dir>` 支持无 Feature 的 review 请求。它准备对象绑定，检查调用方写出的代码审查报告，未沿该路径签发通用独立 verifier 请求。手写结构合法报告即可通过本来承担的结构检查。

**已经排除的误判。** request 可以由另一个 Agent 执行，不能仅因“Agent 自行写报告”就判其必然与作者同上下文；但这还不是原生提供并验证的完整独立审查协议。报告目录禁止与 features_dir 重叠是公开隔离约束，应由宿主遵守，不请求取消它。没有名为 artifact-review.ts 的脚本也不独自证明缺能力。

**需要 Framework 明确或补齐。** 给出合法的无 Feature 独立执行及报告对象验真流程：主调用者交任务/材料，使用现有宿主独立能力，原始报告对应当前对象，报告缺失/非法/过期与审查员不可用可区分。优先复用现有 request/verifier 内核；若已有完整流程，请给真实入口和正反例，无须新增指定名字的 CLI。

**依据。** `harness/scripts/utils/request-phase.ts:runExplicitRequest`、`capability-resolution-entry-input.ts:prepareExplicitRequest`、`harness/scripts/check-review.ts` 的 request 分支、`verifier-request.ts`/`verifier-evidence.ts` 和 `docs/operations/request-harness.md`。

**验证。** 宿主只声明任务和材料，不能手工重绑旧报告为新对象；同内容重复/时间变化复用，正文/设计/判据变化旧报告失效；保留原始回复；缺能力明确未审，不把它写成 PASS。具体安全报告目录使用 Framework 合法位置，不硬要求需求树内目录。

## 4. F3：files 对象中的信息被静默丢弃

最小输入放入任一隔离 Feature 的 contracts.yaml：

```yaml
files:
  - path: src/Example.ts
    must: [{rule: R-1, text: 清除临时内容, verify: ut}]
    pattern: ExamplePattern
    role: storage
```

调用 `new SpecLoader(root, undefined, undefined, frameworkRoot).loadFeatureSpec(feature)`。

**独立实测。** 返回 `contracts.files=["src/Example.ts"]`，`shape_issues=[]`；must/pattern/role 消失。实施者两组命名变体进一步观察到蓝图 derive/物化结果同样丢失，而 files 的原生 schema 明确为 string[]。

**责任判定。** Extension 不应继续写这个不受支持的对象，迁移是宿主责任；但包含语义的非法对象被规范化成看似合法数据且无诊断，是原生输入边界问题。不是要求 Framework 支持旧 Extension 格式。

**最小修法。** 对不可承载的额外字段给出明确 shape issue 并阻止该结果被当作完整有效输入；若保留纯路径旧形态规范化，明确它的允许字段，不静默吞业务字段。平铺、SpecLoader 直读与蓝图派生的失败语义一致。

**依据。** `harness/scripts/utils/spec-loader.ts:normalizeContractsFiles` 的 coerceToPathString；`blueprint-skill-projection.ts` 使用规范后的 parsed.contracts；`specs/artifact-schemas/contracts.schema.yaml`。

## 5. F4：已知集合子树中的未消费文件键漏诊断

以 files=[src/Example.ts] 为授权集合，正常的模型/组件 file 也指向它，比较两个输入：

```text
A: data_models[0].fields[0].must[0].file = src/Unexpected.ts
B: components[0].must[0].file = src/Unexpected.ts
```

调用 `resolveContractFileReferences(root, contracts)` 和 `findUnauthorizedContractFileReferences(result)`。

**独立实测。** A 返回 invalid=[]、unauthorized=[]；B 返回 unconsumed_file_field，准确指向 components[0].must[0].file。实施者的派生例证中也复现同类差异。

**原因。** `contract-reference-closure.ts:rejectUnconsumedFileFields` 遇 allowedFields 直接 continue，fields/state 等已知容器内的新增文件键不再进入拒绝扫描。

**预期。** 对未登记的 file/path 键采用一致的拒绝或明确受支持解析语义；不得仅因置于已知容器就漏掉。同样须保留合法结构字段，不能把任意说明文本误认成写集。

**边界。** 这是未消费引用的漏诊断，未证明实际文件写入越权或目录逃逸。Extension 不使用这个位置绕过授权；不应把本报告描述为已证实安全利用。

## 6. F5：chrys/generic 同目标入口互相覆盖

合法消费 config 的 materialized_adapters 同时包含 chrys 和 generic；扩展 1.1 声明一个 sample Skill。在隔离目录连续调用两次 `materializeExtensions(root, frameworkRoot)`，然后 inspect。

**独立实测。** 第二次两 adapter 仍各报告写入同一 `.agents/skills/sample/SKILL.md`；最终字节可与上次相同，但 inspect 仍报 extension_bridge_stale。ownership 标记包含不同 adapter，造成相互判 stale。`agents/chrys/adapter.yaml` 的说明称可与 generic 幂等共存。

**预期。** 同一公共目标应有一致的共享归属/内容，或在写前明确配置互斥；不应静默轮流重写、最后只因处理顺序决定归属。重复执行应无新增写入和持续 stale。

**依据。** `instance-skill-bridge.ts` 的标记、safeWrite、inspectInstanceSkillBridgeArtifacts；`extension.ts:materializeExtensions` 对 adapter 依次执行。未测实际宿主加载，不声称路由必然失效。

## 7. F6：无 run 交互流程的指令与支持范围不一致

`docs/operations/project-entry.md` 及 goal-mode Skill 明确允许 prepare-scope 后不建 run、按 phase 执行；实际 scope 冻结和 change-unit-completion 也有 Feature 载体。另一方面 component-design、change-unit-progression、skills.index 与共享 framework-agent-execution 规则仍出现“必须真实 attended Goal”或仅 Goal 推进的表述。

**预期。** 同一次请求的入口、被调用 Skill 与生成规则给出一致的运行选择。用户选无 run 时不被另一页强制建 run；明确何时需要 Goal 的预算/恢复能力。

**实现范围待确认。** `change-unit-progress-loop.ts:inspectActiveChangeUnitRuns` 只看 goal-runs。实施者在已有冻结 scope、未有完成投影的样本上得到 active=[]、select_one；这证明该函数不是无 run 在途查询器，不足以证明实际会并发、死锁或选错 CU。请明确无 run 完整 CU 续行的受支持入口，并给单/多 CU 正常与中断证据；若仅支持单 Feature，请修正完整交付声明或补齐原生承接。宿主不自建第二套调度状态。

## 8. F7：宿主适配指南的两处协议描述

**feedback。** `component-design-host-adaptation.md` 声称 --feedback 输出 authoritativeRulingCandidateIds、factSupplementCandidateIds、requiresReconciliation。实际 check-component-blueprint 的 --feedback --json 只返回状态/身份/issues 等，不返回这些字段；函数 validateBlueprintReviewFeedback 有它们，但 checkHostSeamMaterials 只保留 issues。请使 CLI 与文档一致；若函数才是正式入口，明确说明。资格仍不能表示实际接受。

**materialization。** 独立 --materialization 按代码明确在前蓝图模式核来源、hash 和声明 blueprint_id，不加载 canonical；没有参考 component_id 时不能推定不匹配。指南应区分此模式与蓝图存在后的复合检查，不能笼统称两者都会检查 canonical component 一致性。这里优先修文档，不要求前蓝图模式加载尚不存在的蓝图。

评审投影只有 renderBlueprintReviewMarkdown 函数、没有专用 CLI，不列为缺陷；宿主使用该公开函数即可。

## 9. F8：生成入口的人工覆盖提示与预检建议

先在合法隔离工程物化，再在该 adapter **实际选择的入口文件**（如 CLAUDE.md）追加人工段，重复 materialize。

**独立实测。** 人工标记被删除，函数返回成功、entryFilesWritten 含该文件。未被 adapter 选择的另一个入口不改，不能把对未选文件的实验当作保护成功。`extension.ts:materializeEntryFiles` 直接整份重写。

**范围区分。** bridge 的人工漂移保护已有可用；UPDATE planner 已有 drift 和 overwrite/keep 选择，不能称 UPDATE 无任何保护。已退 story-ext 段不要求永久保留，Extension 会把职责迁回自身 Skill 和原生登记。当前不足主要是 extension materialize 直接写整个根入口，与现有覆盖选择的交互不一致。

建议复用既有预检/覆盖政策，在覆盖非规范内容前明确显示差异或给出冲突。也可明确提供受支持的人工规则来源与迁移办法。无需为了本报告创建事务系统或新增指定 dry-run API。原生纯 renderer 已足以供 Extension 组合预检，安装器可在写前停住冲突；因此此项不是整个适配的阻塞前置。

## 10. 不作为 Framework 缺陷上报的事项

- 增加非法 extension_knowledge 质询 scope 被拒是按协议检查。知识应在实际 view/flow/contract 等质询中检查并引用依据；没有新增 scope 不证明无法质询知识。
- createIndependentQuestioningResult 没有仓内调用者不证明质询不存在：原生是模型在隔离上下文执行的工作流。真正需要解决的是 F1 的要求/知识送达。
- 1.0 原生 knowledge formatter 输出空不等于旧 Extension 没有知识能力：1.9.8 自有作者任务/钩子另有消费链。升级 1.1 是宿主接线责任。
- request 的 report-dir 保护、manifest 1.1 拒绝旧非法字段、未知 knowledge_files 被拒、state_management.must 不被原生赋予 Extension 特殊语义，均不能据此要求框架放宽检查。
- 没有 CLI 包装而有可用公共函数，不构成单独缺陷；部分失败没有回滚也不构成必须加事务系统的理由。
- 文件角色迁移到真实实体及知识归位规则的消费先由 Extension 正确实现；本报告不要求 Framework 接受旧 files 对象或新增 knowledge_files。

反馈优先核 F1/F2/F6 的实际接线及支持范围；F3/F4/F5 为确定性行为修正；F7 修协议说明；F8 可复用现有预检改善。请逐项返回适用结论、实际入口/修复提交、验证与发布身份，不需一次为八项新建一套通用框架。
