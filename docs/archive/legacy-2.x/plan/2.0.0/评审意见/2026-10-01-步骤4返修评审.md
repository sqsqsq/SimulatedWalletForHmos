## 2. F1（P1）：已验证报告的只读消费没有绑定被检查字节

位置：independent-review.mjs 的 boundSummary 与 verifiedReviewResult。当前验证 material_key/request_sha256、summary→script-report 摘要，然后要求 working 与 original 字节相同；没有消费原生 input_bindings 对实际 review_report 的绑定。

独立探针得到两种相反错误：

1. 原生实际支持按问题表修正统计数量。一个合法 MINOR 问题（引用真实 JSON 来源，避开已知 Markdown 后缀问题）的报告统计误写 9、实际 1；显式 review check 正常返回 warn，原生修正工作报告。只读查询却返回 report_unchecked，因为工作报告与保留的原回复不同。重跑检查仍产生同样差异，正常恢复路径无法收口。
2. 一次检查通过后，把 original/working 同时换成包含“不通过”结论的新回复而不重验，旧 summary/script-report 未动。只读查询仍返回 pass。两份当前文件相等只说明彼此一致，不说明它们就是那次被检查的版本。

证据：output/story/2.0.0/review-step4-return-1001/binding.json；脚本 output/scratch/r4v/binding.py。第二条是确定性报告绑定反例，不用来评价模型判断能力。

修正合同：

- 原回复保持原样；原生工作报告允许原生已经执行的规范化，二者不要求字节相等。
- 显式 check 时记录实际交入的原回复 SHA-256（写入既有 prepared 记录即可），与本次原生 request、成功返回的检查对象对应；只读时核当前原回复仍为这份。不是新增审查状态中心，也不改变被审业务对象。
- 当前工作报告按 summary/script-report 的原生 input_bindings，用既有 readBoundInput/同源绑定校验核字节与来源；同时保持 summary→script-report 摘要链。不能只给工作报告再写一个自报摘要，替代已经存在的原生绑定。
- 只读不重跑检查、不补登记。原回复换版、工作报告变动、无当前检查结果均指回显式 check；合法原生统计修正后能够直接复用结果。执行检查与只读查询继续共用归类函数。
- 补上述两条小反例及只读前后零写入断言，不增加通用恢复/反篡改系统。
