## 2. 实际做法（与分册对照）

### 2.1 交给设计（分册 §2–4）

- **bind-design**：标识经原生 `assertComponentId`/`assertBlueprintId` 检查。已有蓝图时，核它实际归属的组件；同值重复写入不改字节，不同值拒绝。
- **complete**：
  - 读 `design-input.json`，按 `materials/frozen.py` 冻结到 `AR/story-src/inputs/<hex>/`：
    - 选集是采用原件、它们引用的本地图、候选提取稿和人签导出；
    - 版本号是去掉 `observed_at` 的快照规范 JSON 的 SHA-256；
    - 先写临时目录、复核后改名；同内容复用，损坏报错。
  - 系统单在版本内写 `materialization.json`，本地单把条目交给 builder。两类都先过原生 `validateRequirementSourceMaterialization`，通过才写 `flow.input`。
  - `AR/design.md` 不再被覆盖；`.backups/local/` 退路随之退出。
- **status**：按原生蓝图读取结果派生 gathering … registered，flow 不存准入或 revision 的副本。update 活动态优先显示，同时给主状态。
- **reopen**：初始与 update 中都合法。保留绑定、输入、人签与旧 basis，旧 basis 标为暂不可交付，不关闭 update。

### 2.2 成文来源（分册 §5「附录替换」）

- `story/design-source.mjs` 负责读取来源：
  - 取流程契约的设计关联和冻结输入，原生读已准入蓝图；
  - 核评审投影与当前 revision 对得上，核冻结快照摘要；
  - 任一不成立都给缺口和责任方，skeleton 起手预检就停。
- `story/appendix-readers.mjs` 是章节合同登记的具名读取器，生成与校验共用：

  | 读取器 | 内容 |
  |---|---|
  | contracts | operation、DTO 字段、mapping、错误、幂等、NFR |
  | data_flows | 运行数据流与数据策略 |
  | details | `story_details` 的配置与埋点，逐字 |
  | knowledge_applications | 知识应用决定 |
  | change_boundary | 开发视图与架构影响 |

- `special_design` 必须逐字出现在正文。
- 术语起始行取蓝图的 `term:` 事实，解释由作者写。
- 材料清单按冻结快照标注采用版本，另列派生分析与人签记录。
- 蓝图作者页（`hooks/blueprint/author.md`）补了 `story_details` 写法。

### 2.3 登记、审查与交付（分册 §5「独立审查」及登记）

- **story_basis**：记完整原生 `blueprint_ref`、`input_sha256`（等于 `input.snapshot_sha256`）、`knowledge_sha256`，以及被审文件的路径和原始摘要。`story-build basis` 给出当下的依据，登记、路由、check 和交付门共用它。登记之后任一依据变了，状态即为 needs_sync。
- **交付门**：退出 Spec 回执和 Spec verifier 报告读取，改为核已登记、依据未变。审查未接通时照实写「未经独立审查」，不写通过。交付选择改为送审 / 完整设计交接 / 完整实现 / 暂不推进，本地单没有送审。
- **读者审查**：
  - 判据只在 `rules/story-reader-rules.yaml`；
  - `reader-review-task.mjs` 是唯一任务生成器，判据与章节合同按本模块所在包读取；
  - spec overlay 与 pre_verifier 退出 Story 判据；
  - `story-build review --action prepare` 先过全篇结构检查，再写 `AR/story-src/review/task.md`；`--action check` 在 B 接通前只报 `reviewer_unavailable`，不伪造报告。
- **顺序**：check → 独立审查 → `story_flow.py story` 登记 → `check --deliver` → 交付选择。路由、`phases/design.md` 与 SKILL 一致。

### 2.4 指令面（分册 §1）

- `phases/design.md` 接替 `phases/spec.md` 的 Story 编排：交给设计 → component-design 到准入与投影 → 按蓝图成文 → 审查、登记、交付。
- 原页里 spec/plan 阶段 harness 审查的「闭环」表仍有消费者，迁到 `skills/story/reference/phase-closure.md`，Story 专属行删除。
  - 引用它的有 spec/plan 作者页、update 方法页、`update.py`、`verifier-report.mjs`。
  - 放进 spec 作者页会使该页超过 60 行，被失效形态 A03 拦下。
- SKILL 的改动：
  - 链条、推进契约和停等表：启动语义改为「做到交付门并问一次交付选择」；声明由 status 在进 component-design 那一步打出；交付选择四项；术语取蓝图事实。
  - 本地单终点、归档前置和产物表改为蓝图来源。
- 规则页与成文页：
  - `ar_design_init` 退出覆盖与备份的说法，上游信息类别的消费方由 spec 章节换成蓝图对象；
  - `init_analysis`、`scope_gate`、`inbox_import` 同步；
  - `story-write` 的必读输入与「回真源」出口由 Spec 换成已准入蓝图。

## 4. 局部选择（请评审确认）

1. **材料的 `observed_at`**：
   - 做法：物化件里材料行的 `observed_at` 取冻结时刻，人签行取人签记录时间。冻结时刻写在快照里，不计入版本号；同内容复用时沿用首次的时刻。
   - 原因：分册 §4.3 要「材料原取得时间」，但 `materials.json` 没有逐份记取得时间。
2. **读者判据的措辞**：迁移时只换了输入与对照项（Spec/acceptance.yaml → 蓝图与评审投影、冻结输入、激活知识），其余要求原样。
3. **材料清单形态**：起始行给出采用版本，并另列派生分析与人签记录；每份材料贡献了什么由作者写。
4. **审查排在登记之前**：
   - 做法：`review --action prepare` 不要求已登记，只要求全篇结构检查通过；登记时重核依据。
   - 原因：分册的默认顺序是「结构检查 → 独立审查 → story 登记」。2C 初版要求先登记，2D 已按分册改正。
