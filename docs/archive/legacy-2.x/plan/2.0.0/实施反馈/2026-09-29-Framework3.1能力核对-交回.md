## 2. 基础蓝图

入口与结果（详见 01 报告与 raw-01～raw-22）：
- **蓝图校验**：`check:component-blueprint` 正例通过，准入状态由 checker 推出。发布件中没有写 canonical 蓝图的 CLI，蓝图由 component-design 流程中的模型写。
- **三条接缝**：`--materialization`、`--projection`、`--feedback` 的反例都按原生错误码失败。例如 hash 不符、路径越界、旧版本投影报 `publication_derived_from_mismatch`，旧 revision 的反馈报 `review_feedback_stale_source_revision`。
- **身份与 resolver**：过期 sha 或 revision、错误 component_id、不安全 id、非规范 `cu-` id 都按原生结果失败。蓝图升版后旧 CU 报 `change_unit_blueprint_ref_stale`，经设计准备 readiness 原位升版后复检通过。
- **设计准备**：只有函数入口。0 个 CU 是合法入口，原子接受与整批拒绝都已实跑。
- **施工派生**：CU 引用的节点带有 authoritative acceptance/contracts 时才能派生，否则结果为 absent。物化后重跑不写盘；人工改过的文件拒绝覆盖。
- **component-closure**：因为没有真实施工证据，`--write` 与只读复核的结果都是 FAIL，符合预期。closure 要求每个 `decided_with_authority` 决定带 `knowledge_refs`，并指向 `discovery.inputs.knowledge_assets` 中的精确 `#conclusion-id`（`component-closure-knowledge.ts:39-93`）。蓝图 checker 不查这一点，要到 closure 才会失败。设计步骤 3 的知识决定时需要承接这一约束。

文档与实现不一致之处（按实测，报给设计者判断是否上报）：
1. `--materialization` 单独使用时，component_id 不一致会得到 PASS；要与 `--projection`、`--feedback` 或 `--ref` 同用才报 `materialization_component_mismatch`。宿主适配指南 §3.3 把后者写成了通用行为。
2. `--feedback --json` 只输出 issues，不输出候选列表；宿主适配指南 259–261 行称会输出。候选列表只能从函数 `validateBlueprintReviewFeedback` 取得。
3. 评审投影的 Markdown 只能通过函数 `renderBlueprintReviewMarkdown` 生成，没有 CLI。

随包的 ledger 样例在消费工程中跑不通，因为它引用的需求和蓝图不在发布件内。本次核对在副本中另建了一份薄蓝图来驱动原生 validator，它不代表任何业务设计。

## 3. interactive（无 run）

- `goal-mode-entry --prepare-scope` 只写 `feature.yaml` 候选：同输入重跑不写盘，手改后重跑报 `differs`。acceptance/contracts 已物化时，阶段链为 coding → review → ut → testing，spec/plan 判为可复用。
- 首次 `harness-runner --phase review` 调用即写出 `execution-scope.json`；之后改动候选报 `execution_scope_frozen`。
- CU 推进由 `inspectActiveChangeUnitRuns` 判断，它只扫描 `goal-runs/`，已冻结的无 run feature 不会被识别为进行中。

**确有 Framework 缺口：以下文字只给出 Goal 或 attended run 路径，与 `project-entry.md:30`（两种载体）和 `goal-mode/SKILL.md:14` 不一致。** 路径都相对 `demo/framework`，已抽查：

## 4. A：设计作者与独立质询输入

- **`skill_assets.component-design.*` 没有消费者，属于确有 Framework 缺口。** loader（`extension-loader.ts:460-498`）会合并这一域。但模型只有在 Skill 正文中看到 `profile-skill-asset:<skill>/<key>` 引用时才会读取资产，而 component-design 的 SKILL 与蓝图工作流中这类引用为 0 处（已抽查），profile 的 skill-assets 也没有 component-design 一项。实测登记后 loader、verify 和 inspect 都通过（inspect 显示 scheduled），但各阶段 prompt、goal 作者输入和 AGENTS.md 与不登记时逐字相同。与此相反，`extension/SKILL.md:47`、`component-design-host-adaptation.md:345-346`、`MIGRATION.md:105-106` 都说设计知识应通过 skill_assets 绑定 component-design。
- **设计作者的实际输入。** 模型按 SKILL 自行读取来源、惯例（`SKILL.md:89`）和固定的内置输入（workflow `:22-30`，写明「不得动态加载」）。Extension 唯一能送到设计阶段的原生通道，是 manifest 1.1 中 `audience: global` 的知识：它会渲染进 AGENTS.md 的全局知识表，但只有路径和摘要，而且所有请求都会带上。`formatExtensionPhasePrompt` 只对 Feature 阶段生效（`extension-runtime.ts:22-24`）。把 audience 或 phase_bindings 写成 component-design，loader 会拒绝整份 manifest。
- **两种进入方式。** 直接进入 component-design 和经 Story 转入，在 Framework 侧是同一路径，都不注入扩展输入。经 Story 转入时可以由 Story 自己的 Skill 在调用前送达，属于缺 Extension 接线；直接入口没有承载者，属于确有 Framework 缺口。
- **独立质询没有材料装配，属于确有 Framework 缺口。** 只有 workflow `:28` 的文字要求。`createIndependentQuestioningResult` 在发布件中没有调用者；质询范围只接受 5 种，加 `extension_knowledge` 会报 `blueprint_questioning_scope_invalid`。
- **Feature 阶段的送达已有可用。** 阶段知识与 phase_bindings 经同一函数送进 verifier prompt（`harness-runner.ts:1379`）和 goal 作者 prompt（`goal-phase-runtime.ts:3578-3647`）；交互模式下只有文字指引。demo 当前 manifest 为 1.0，13 份知识的原生消费为零（inspect 显示 declared-unconsumed）。
- **登记了但文件缺失时，整份扩展失效。** 实测报 `skill_assets_missing`，同时 knowledge、hooks、overlays 以及 AGENTS 中的 Skill 表全部清空；verify 与 `--phase extensions` 退出码为 1。

## 5. B：独立人读审查

- **原生 verifier 只认 Feature 阶段。** 报告目录固定为 `<features_dir>/<feature>/<phase>/reports`，subject 中包含 feature 与 phase。`check-receipt` 不带 `--feature` 时退出码为 2；verifier 代理的说明（`verifier.md:3`）禁止自行构造 request。底层纯函数本身可用：subject 与时间无关、随内容变化；报告验真能区分 missing、unparseable、subject_mismatch、verdict_inconsistent。但**没有面向非 Feature 对象的入口，属于确有 Framework 缺口**。登记了 verifier_subagent 的 adapter 是 claude、codeagent、codex、opencode（opencode 为本仓定制）；cursor、chrys、generic 显示 `adapter_has_no_reviewer`。
- **无 Feature 的专项 review request 可以审 Markdown，但不是独立审查。** 实测以 Story/Review 为目标时：
  - `--prepare-request` 退出码 0，同输入得到同一 sha，不建目录；
  - 执行时退出码 0，不产生 `doc/features`，summary 写 `subject=request`。

  但报告由调用方自行写入，没有 verifier 或子代理，也不装配审查任务；它校验的是代码审查报告的结构（六章节、问题表、结论行），不包含 Story 读者判据。Extension 的 review overlay 也会作用到这条请求上：1.9.8 的 overlay 多出一个 `hooks/review/author.md` 必读项。
- **身份与退出码。** `request_sha256` 由规范化后的请求、目标字节、输入字节和 report_dir 共同决定，与报告内容和时间无关。内容变化后若沿用旧目录，会被拒绝。退出码：prepare 为 0；非法请求为 1，输出为文本而非 JSON；PASS 为 0；FAIL 为 1。
- **与步骤 2 合同冲突：report-dir 不能放在 features_dir 内。** `AR/story-src/review` 实测报 `report-dir overlaps protected directory`（`capability-resolution-entry-input.ts:116`，已抽查）。步骤 2 §5 规定的审查目录无法直接使用这条通道。

未验证：verifier 子代理的实际派发、Feature 闭环中 `not_reviewed` 的 WARN 路径、执行中目标字节变化的三个检查码。

## 6. C：施工契约中的知识实体

以下两套命名、路径和规则号不同的变体，结果一致。

| 子项 | 实测 | 分类 |
|---|---|---|
| must 位于 data_models.fields、interfaces.methods、components、components.state、resource_keys | 从 schema 到阶段读回全链保留，二次物化不改写；手改后报 `blueprint projection stale; return to design owner`，且不覆盖人工决定 | 已有可用；Extension 只按平铺路径读取，缺 Extension 接线 |
| 验收中的 knowledge_rule 与 knowledge_decision_id | 全链保留 | 已有可用 / 缺 Extension 接线 |
| knowledge_applications[] | 全链保留 | 已有可用 |
| files[] 上的 must/pattern/role | 蓝图链上被静默收成路径字符串，不报错（`spec-loader.ts:656` 的 `normalizeContractsFiles` 调用 `coerceToPathString`，已抽查）；平铺 Feature 解析时报类型不符并拒绝 | 原生不承载，两条路径的处理不一致 |
| 顶层 `knowledge_files`，或带 `file` 键的角色/must | 报 `unconsumed_file_field`，派生 invalid | 原生按设计拒绝，总览 §3 C 所说的新增登记在 3.1.0 中不存在 |
| `state_management[].must` | 原生放行 | 越位检查只能由 Extension 做，缺 Extension 接线 |

- **可替代载体。** 角色写在承担实体上、并且不带文件键时（例如 `components[].pattern_roles`），可以完整穿过全链。没有承担实体的文件级职责，原生没有载体。
- **原生授权放行口。** `data_models[].fields`、`components[].state` 等白名单字段下嵌套的未授权文件路径不会被扫描，可以通过闭包检查和派生。Extension 不依赖这一点，是否上报由设计者决定。

## 7. D：物化与人工保护

- **1.0 下的 `provides.bridges`。** 3.1 忽略 1.0 manifest 的 bridges、adapters、adapted_for，旧入口保留且不被接管，MIGRATION 的说法实测成立。升级到 1.1 后，这三个字段都会成为 manifest 错误，必须先移除才能物化。
- **正常生成。** 各 adapter 生成带所有权标记的入口，但正文固定为跳板，旧 `/story` 入口里的命令转化表和参数提示无法表达。在 1.1 下，Extension 能控制的 AGENTS 内容只有 skills 表、全局知识表和 phase_bindings 前置行三处。
- **入口级保护已有可用。** 被人工改过或标记损坏的入口会保留，无标记的文件不接管；与保留名冲突时自动加 `ext-` 前缀并告警；1.1 manifest 非法时零写盘拒绝。唯一的例外是：未被改动的孤儿入口会被删除。
- **AGENTS/CLAUDE 人工区没有保护。** 原生 materialize 和 framework-init UPDATE 都整份覆盖这两个文件：story-ext 段和区外人工段被静默删除，退出码仍为 0。在 demo 现状上首次 materialize 会删掉 story-ext 段并新建 5 个 story-adaptation 入口。本次基线接入也遇到了同样的情况，当时手工放回了该段。维护安装器与原生物化会互相覆盖 story-ext 段。
- **只读计算。** materialize 没有 dry-run。组合原生导出的渲染函数与入口核对函数，可以零写盘算出将改写的入口和将丢失的行（在 demo 上是 story-ext 6 行加人工段 2 行），但这只是函数组合，不是现成命令。
- **部分失败。** adapter 名写错或 CLAUDE.md 只读时，已写的入口和 AGENTS.md 不回滚，只给退出码 1 和一行错误，没有已完成清单。
- **Framework 轻微缺陷。** chrys 与 generic 共用 `.agents/skills`，每次物化互相改写，inspect 对 chrys 永远报 stale，但不影响退出码。

未验证：UPDATE 写盘阶段在副本中未跑（本仓基线接入时已实际遇到整份覆盖）、各宿主能否从原生入口路由到 `/story`、带知识字段跑完整阶段门禁。

## 8. 需要设计者裁定的点

1. **A：设计知识送达。** 直接 component-design 入口和独立质询都没有原生承载者。二者择一：
   - 作为 Framework 缺口上报；
   - 或接受「经 Story 转入时由 Story Skill 送达，直接入口只靠 global 知识表」的降级。
2. **B：Story 独立审查。** 原生 verifier 不支持非 Feature 对象；专项 request 不独立，report-dir 也不能放进需求目录。需要确定：上报 Framework 缺口，还是另定审查载体和目录。步骤 2 §5 的审查目录需要随之调整。
3. **C：文件级知识职责。** 没有承担实体的文件级 must/pattern/role 在原生中没有载体，而且在蓝图链上被静默丢弃。需要确定：这类职责是否必须保留，还是改由实体级 must 与 `pattern_roles` 承接。前者需要向 Framework 提出，并同时处理「静默丢弃」这一不一致。
4. **D：AGENTS/CLAUDE 中的 Extension 文字。** 需要确定：story-ext 段的职责能否改由 1.1 的三处渲染项承担；若必须保留任意文字，则属于确有 Framework 缺口，需要人工区保护或 dry-run。
5. **interactive 文字冲突。** §3 表中的几处文字需要向上游报告。
6. **是否上报。** §2 的 3 处文档与实现不一致、§6 的授权放行口、§7 的 chrys/generic 互相改写，是否上报由设计者决定。
