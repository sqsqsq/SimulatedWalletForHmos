# R1 两 Case 金样与质量基线

2026-10-07：原 2.1.0 R1 整项迁入 2.0.3，承接 T7、S1/S2；执行顺序和额度见[总览](../00-版本范围.md)。2026-10-09 按[金样职责修正与执行合同](../../../plan/2.0.3/2026-10-07-整体设计/05-金样职责修正与执行合同.md)统一金样范围。本需求定义期望结果，正式替换由本版 R4 收口；2.0.2 既有能力与正确性修复不重复实施。

## 1. 问题、目标与选择

旧金样集中在早期 Story/Review，跨产物承接及新场景覆盖不足。新整理的 AR90006、ISSUE-206 含两套 Spec/Story/Review 和一份 Plan，但独立审核已发现真实语义与工程缺口。采用它们作为修订基础，可以复用历史探索和表达优点；直接升为正本会把错误变成效果标准。

选择两 Case 共同作为新基线，接替旧 AR90004 等正本的权威地位。AR90006 着重会议、材料更新、未决口径与冲突探针；ISSUE-206 着重端云协作、动态权限、状态、恢复、工程事实缺口及施工承接。不是指定两套固定模板，测试 Case 的专名、数值和答案不进入产品通用规则。

目标是让维护者和评价者能判断正确性、完整性及表达质量。金样定义给定输入下期望的交付结果；专项回归验证确定性机制；真实 CLI 验证消费模型的实际过程与结果。三者共享需求依据、各自交证据，不互相冒充完成。每组金样注明情景终点，不能把待决稿宣称为可实施终稿。

## 2. 输入与决定责任

| 输入 | 取得方式与用途 | 权威边界 |
|---|---|---|
| 产品稿、系统设计、会议和评审原件 | 从现有 Case 取得，锁采用版本；保留原话、版本和定位 | 材料冲突按 Case 设计的处置与宿主立场处理，不取最新日期或多数快照自动定案 |
| 宿主立场 | 交互脚本、答案卷与 `case.yaml` 的探针说明；由维护者为验证 Extension 设计 | 是构造预期的合法输入，不是已发生的人签；测试设计缺的立场由维护者补，并按 cases/README 记账 |
| 目标代码、配置、知识 | 按选定工程基线核实际定义、调用、导出与接入位置 | 工程没有现成能力不等于可以缩小业务目标 |
| 新整理的七份候选与分析档案 | 从[历史参考](../../2.1.0/历史参考/README.md)定位表达与问题线索 | 模型写作物；示范回填不是本 Case 的人签 |
| 实跑产物与过程记录 | 10-03 suite 的会话、输入与产物 | 用于定位缺陷和取表达起点，不反向当需求权威 |

金样修订者按输入取证、组织和同步；独立评价者核内容；用户审定金样的效果；测试维护者负责消费者迁移。消费模型在正常工程中只取得产品输入，不取得金样、分析报告或隐藏判据。

### 2.1 本版采用基线与情景

输入锁到 `15844e09ba1bce07b2ca158adfd63df399cd90be` 的 `test/cases/auto-topup`（tree `6e613a746a2fe92c4f42343aacf5a944383aa18a`）、`test/cases/car-key-sharing`（tree `4cc39a7bac711d8e2f9c4cb43af38cb9f445ca0c`），工程取同提交 demo（tree `6d74bb0b925b45f7e57ee81fe329ea9f9df03a2c`），知识以该提交 extensions/knowledge（tree `0f329be35b34a1af3d428f38d7863a5e7a80eede`）为起点。2026-10-09 补齐的宿主立场按 `test/EVOLUTION.md` §7 记新旧摘要；原始快照保留为历史基底，金样与成本配对都用补齐后的同一版输入。

| 情景 | 目标金样 | 终点 |
|---|---|---|
| 自动充值 initial | Story、Review、必要配图 | 系统送审，零施工单位；调高面额是否重验、授权后建约失败按宿主立场保持待定 |
| 自动充值 update | 更新后的 Story、Review、必要配图 | 承接改版需求与评审回稿；单日上限 300 与会上冲突，识别并问需求方后按立场维持 200 |
| 车钥匙 reviewable | Story、Review、必要配图 | 需求级完整评审；初段各问题按宿主立场定案，上游未定的两件事保持待定 |
| 车钥匙 plan-ready | Story、Review、必要施工单位的 Spec、Plan、必要配图 | 交付门选实现方案，止于 Plan |
| 车钥匙 update | 更新后的 Story、Review，以及本次变更影响的已有 Spec、Plan；必要配图 | 评审意见「36 小时内仍可开门」与车辆侧即拒绝冲突，识别并问需求方后按立场定为卡片收回期限 |

金样只保存目标 Markdown 与配图，不附带蓝图、决定登记、章草稿、流程记录、指纹、准入或质询状态；`design-review.md` 不设独立效果金样，产品照常生成和交付它，由专项回归与真实审查核其同源与内容。

## 3. 修订组织

先执行[审核问题与修订合同](审核问题与修订合同.md)的 G01–G09，再沿其他有效业务关系检查，不能只修列出的样例句子。相同事实和决定的所有落点一并同步。

金样直接根据原始材料、目标工程事实与宿主立场写成：Story/Review 讲清整体需求与争议；止于 Plan 的情景，Spec/Plan 讲清施工范围、实现落点与验证责任。整体规约判断和模式选型在 Story 与 Spec/Plan 里有一致的落点。不要求两个 Case 硬造同样数量的施工单位或每类文档。

- **仍有待决**：正文只陈述已知部分、建议和影响边界，图表、验收、施工不暗选方案。
- **按立场定案**：问到之后按宿主立场形成结论，正文写明结论与依据；README 注明立场来源，不写成已发生的人签。

同一稿不能一处待决、一处已采用、一处已验收。明确的既有业务决定应正确承接，不能为展示更多 open 议题重新打开已经定案的范围。

## 4. 效果定义

| 对象 | 基线应展示什么 |
|---|---|
| 业务事实与决定 | 来源可定位、冲突有处置、建议与定案分开；同一事实跨产物一致 |
| 内容完整性 | 有效范围内的正常/异常/恢复、条件、责任、依赖及验收有实际落点，不靠编号齐全代替内容 |
| 结构与表达 | 同类信息组织稳定；表格能比较，图讲关系，正文解释条件与后果；推荐形态允许有理由地调整 |
| 工程可落地性 | 真实输入输出接得上；身份未因脱敏丢失；页面与依赖有接入动作；文件和验证职责完整 |
| 待决与交付状态 | 读者能判断哪些可继续、哪些等谁决定；局部模拟结果不等于真实联调通过 |

金样只定义效果，通用规则落入现有产品合同并由本版 R2/R3 消费。实跑产物与金样按语义与读者效果比对，允许合理的组织、图形、设计和施工单位划分差异，不要求内部状态或中间路径一致。

### 4.1 最佳结果的编写与评价标准

金样应展示当前需求的最佳结果，不止于修完已知错误。对仍然难读、重复或无法指导实施的内容重新组织，保留正确事实，不受旧稿组织限制。

| 产物 | 应达到的形态 | 不合格表现 |
|---|---|---|
| Story | 背景/范围说明问题与责任；业务方案解释协作与取舍；流程连起条件、交接、分支和终态；功能说明补局部规则；异常、验收、上线完整；附录供精确查阅 | 正文被接口清单占据、只列参与方无协作、关键行为藏附录、重复堆表 |
| Review | 每项独立可决定，依据、选项后果、推荐理由和决定责任明确；已定/待定与正文一致，更新保留原话和当前处置 | 合并不同决定、只有选项号、工程选型都推给人、待定处暗选答案 |
| Spec | 本施工单位行为、边界、数据/状态、恢复、可观察验收和共同设计依赖明确 | 抄Story、只列功能名称、漏恢复入口、含糊验收或改变范围 |
| Plan | 数据来源、状态持有者、接口、页面接入、调用/返回、清理恢复、文件动作及验证责任相互接得上 | 有类名无调用、有页面无入口、状态无来源、只写“补测试” |

图表按阅读任务选：时序讲先后与返回，状态图讲合法迁移，流程图讲分支，表格比较属性；必要条件与业务结果在正文讲明。不定图数、不要求每种图都出现，不把最优的一种合理设计当成唯一合法实现。

五个情景保持。未覆盖但确有必要展示的表达，在同目录README用短例解释并标清适用条件，不增加完整需求或伪造本Case业务。README列重要设计选择、可参考的表达位置及相对旧稿的具体优化，保持简短，不新增评分数据库或逐句对账文件。

## 5. 替换合同与过渡

正式效果正本在用户审定后放 `test/golden/<case>/<情景>/`：Story/Review 在 AR 下，Spec/Plan 保留能明确所属施工单位的目录，配图用情景内相对链接，每组带简短 README（采用输入、终点、宿主立场、必要设计选择、配图来源）。原始输入仍在 `test/cases/`，不复制整套输入到金样。

切换时一并迁移实际消费者（金样文件枚举与指纹、Review 渲染回归、Story 生产检查、唯一副本检查等，以全仓核到的为准）：确定性机制改用专项夹具验证，不从整份业务金样反推登记状态，也不让金样经生产链装配。旧金样独有的有效场景逐项记承接去向；失效的装配、映射与专用断言退出，有效业务覆盖不随旧文件删除。

切换前，现有回归继续读旧正本，修订稿只用于审定；切换后只有新正本承担效果权威，方案候选退为审定证据，不继续双份编辑。

## 6. 验收与失败处理

后续优化按10-10步骤1完善全稿：新增图按实际关系和读者用途评价，不固定图数；完成附录细项、条件式建议、界面参考图元素核对，图渲染/看图未完成就注明。结果金样不要求产品机器图源标记，去掉旧运行标记，以真实材料清单/README追溯；生产单一图源合同由专项夹具与实跑验证，历史原件不改，不为标记或渲染恢复金样现场。


G01–G09 每项有来源、修订后的各处落点及复核结果；其余章节沿同一事实链审查，回原件和工程核对，不以候选之间互相一致自证。

所有目标文档按§4.1达到相应读者目标，业务有据、跨件一致，没有因运行状态造成的内容空缺；交回具体表达优化与完整通读结果，独立评价内容和表达，用户审定效果。这证明的是期望结果已明确，不是产品已能产出它；产品能力由专项回归与授权的真实 CLI 证明。

源材料缺失、立场缺失或规则冲突时报告具体缺口，保持原始材料；由来源、测试设计、Framework、Extension 或测试维护的责任方处理，不删事实、不放宽要求取得通过。
