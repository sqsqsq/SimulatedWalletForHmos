# 知识适配的独立审查

> 读者：执行 `/story adapt` 的适配模型（发起与收回），以及被派来审查的独立执行体。时机：知识写完、走查过、交回知识块与跑 `--mark-adapted` 之前；适配内容改过后对受影响的知识再审一次。

## 为什么要独立

写知识的上下文里已经装着作者的理解，自己核只会看见自己想写的东西。审查由不共享作者上下文的执行体做：宿主有原生的独立只读子代理就用它，没有就交给独立会话或维护者，并在交回里写明「未审」。同一上下文的自查不能代签；阶段 verifier 的 request JSON 协议服务需求阶段，不用它冒充这次审查。

## 发起：把这些交给审查者

| 交什么 | 从哪取 |
|---|---|
| 目标根路径，激活清单与内容摘要 | `adapt-scan --status` 的 `knowledge.digest` |
| 已定的适配范围与按主题的盘点 | 方法页第 2 步、交回里的盘点 |
| 本次处理的演进主题 | `--status` 的 `items.知识`，首次从知识基线起 |
| 每份知识对应的源码、规范位置 | 你取证时用的位置 |
| 一个正常需求作检查输入 | 方法页第 2 步挑的那个 |
| 质量判据 | 方法页「首次知识的质量判据」、`knowledge-topics.md` 对应主题一节、包的 `skills/story/reference/knowledge/protocol.md` |
| 同用途声明候选 | `--status` 的 `knowledge.sameUse`：只按 `applies_when` 原文完全相同分组，为空不说明没有重复 |

审查者自己打开目标仓读事实，不以作者的走查结论为准。

## 审查者：逐份给有依据的结论

先按通用要求核：拿检查需求走一遍，读者能否据知识作出对应阶段的决定；每条事实与规约指得到源码、规范或负责人的位置；不适用的理由查得到；缺口写明缺哪项、影响哪一步。再逐份核四个维度：

| 维度 | 核什么 | 问题回哪里 |
|---|---|---|
| 条目粒度与归类 | 条目是否过多过细、是否先按领域归类再归纳；首批每份最多三项是否遵守。条数符合不代表粒度对 | 这份知识：合并、归类或删到核心项 |
| 项目事实的用途 | 是否讲目标仓有什么、在哪、通常怎么用；是否混进实现推导或代码内部解释，让读者拿它作不了决定 | 这份知识：改写成用法与位置 |
| 跨文件重复 | 同一事实、约束或方法是否在多份里各写一遍；分清有来源的引用、合理互补与内容重复。同用途候选只是线索，异名同义也要找 | 点名权威那一份，其余改为引用或删除 |
| 编码规范边界 | 是否把目标已有的编码规范改写成了项目知识 | 留在编码规范原处，知识里删去 |

结论逐份写：维度、问题、证据位置、建议回到哪份知识怎么改；没问题的也写一句核过什么。

## 收回

审查者的结论原样写进目标扩展目录的 `.adapt/knowledge-review.md`，其中恰好一个 YAML 证据块（作者传输，不改写结论）：

```yaml
knowledge_review:
  digest: <审查时 --status 给的 knowledge.digest>
  executor: <宿主返回的独立执行或会话引用>
  files:                       # 激活清单里每份一项
    - path: knowledge/<类>/<文件>.md
      granularity: {verdict: PASS, evidence: <核过什么、证据位置>}
      fact_use: {verdict: PASS, evidence: …}
      duplication: {verdict: PASS, evidence: …}
      coding_boundary: {verdict: PASS, evidence: …}
  blocking: []                 # 阻断项，没有写空列表
  unreviewed: []               # 没核到的知识或维度及原因
```

`--status` 的 `knowledge.review` 只读派生：缺失、过期（摘要对不上当前知识）、未核完、有 FAIL 或结构有效。本次有知识演进条目时，`--mark-adapted` 要求它结构有效才写 `adapted_for`；知识改过就按新摘要重审受影响的那几份，旧结论不覆盖新内容。结构有效不证明审查真由独立执行体做过：审查执行体、发现与处理照样写进知识块交回。没有独立执行能力时机制照常装好，交回写明知识适配未完成。
