# 取证规则

> 读者：写蓝图时做来源发现与设计的作者；本施工单位有新增工程事实要写的 spec 作者。时机：写任何涉及工程现状的结论之前。

每条涉及工程现状的结论的**唯一合法产出方式**：信息源 → 提取步骤 → 输出规则。
取证失败如实写取不到什么、查过哪里，**任何信息源都取不到时不编造结论**。
取证结果写进当前动作的原生事实对象（蓝图来源发现的 facts、施工阶段的当前事实），不在本页或别处另记一份状态。

## 1. 核心公式

> **事实 = 变更意图 × 代码库现状**

变更意图从本次的真实需求、有效决定与原生当前输入来；**现状先看激活清单里的项目知识**（有什么、叫什么、在哪），
它没登记的面再实扫仓。两者交叉才得出「新增 / 修改 / 废弃 / 复用 / 不涉及」——
只有意图、没有现状比对的条目一律视为**未取证**。

**现状不能用平台常识顶替**：某个 API 在别的工程常见，不等于本工程在用；
项目知识里已核实为「没有」的能力，不要选进新设计。

## 2. 信息源总表

### 变更意图

| 源 | 用途 | 缺失时 |
|---|---|---|
| 本次需求（冻结的交给设计输入、需求材料原文） | 要做什么、边界与验收意图 | 不可缺：没有意图就无从比对 |
| 有效决定（决策登记里已定的议题、人签） | 已定的取舍与口径 | 没有就按材料原文与未决如实写 |
| 原生当前输入（已准入蓝图、施工单位的有效契约与验收） | 已成立的共同设计与本单位承担的部分 | 设计还没成立时只做来源发现，不替设计下结论 |
| `SR/design.md`、`RR/prd.md` | 跨部件交互、云侧接口、业务场景佐证 | 如实标注缺失，相关结论置信度降级 |

### 代码库现状

| 源 | 用途 |
|---|---|
| **激活清单里的项目知识**（`kind: facts`） | **现状的第一落点**：登记了的直接引用；没登记的面才实扫 |
| `doc/module-catalog.yaml` | **定位线索**：`key_exports` / `responsibilities` 指向该去哪个模块找；`NOT_responsible_for` 是负向证据。**catalog 里没有不等于工程里没有**——「无」只能由检索零命中得出 |
| `doc/architecture.md` + `framework.config.json` 的 architecture 段 | 层间依赖规则（`can_depend_on`） |
| `doc/glossary.yaml` | 术语 → 权威模块定位 |
| **激活清单里的规约条目**（`kind: constraints`） | 逐条判定的基准。条目清单由激活清单派生，**本文不列域也不列编号**——列了就是第二份清单，规约一改这里就过期 |
| 代码检索 | 上述都定不下来时的兜底；范围取工程配置与实际模块目录（蓝图涉及的模块、施工单位的授权文件及其所在模块），加全仓工程配置 |

## 3. 现状怎么取

**三步**：① 先查项目知识有没有登记该类能力的既有实现，有就照它写；
② 没登记或存疑，用 catalog 缩定位范围再在范围内检索；③ 与项目知识不符时**以仓为准**，
在结论里登记「项目知识矛盾：<哪一面、哪里不符>」，**知识文件不在本动作改**。
结论里注明依据来自哪一步（项目知识已确认 / 本次实扫），让「查过确实没有」与「没查」可分。

## 4. 结论写法

取证是**生成过程**，产物是一条具体、可回查的结论——不是一条结论加一个出处坐标。

### 4.1 具体到可按名回查

每条结论写全它谈论的那个东西的名字：接口名、存储键、事件名、配置项名、模块名、错误码、路由名。

| 反例（空话，无从核对） | 正例（可按名回查） |
|---|---|
| 新增了一个管理台开关 | `event_signup_enabled`（管理台功能开关，新增）：默认 `false`；关闭态隐藏报名入口及其提示 |
| 新增了报名接口 | 云侧接口 `submitSignup`（新增）：入参 `eventId`/`sessionId`/`contact`，出参 `ticketNo`，新增错误码 `SESSION_FULL` |
| 端侧新增了缓存 | 存储键 `signup_draft`（新增）：值结构 `{ eventId, sessionId, savedAt }`，有效期 30 分钟 |

名字写全了，审查者才能按名搜遍材料、设计与代码去核对。
不涉及的写「不涉及 + 一句判断依据」，依据同样要具体（扫了什么、什么现状）。

### 4.2 三类必须写进结论的信息

| 类别 | 怎么写 |
|---|---|
| **代码库现状** | 仓内文件路径，或检索结论「检索 <该类封装> 于 <模块> 零命中」。**写之前自己确认路径存在**——没有门禁替你查，写错了就是一条查无此物的证据 |
| **约束规约** | 编号（`XXX-01`）与它所在的规约文件 |
| **数值来源类型** | 三选一标在正文：`≤ 1500 ms（本工程设定，无上游依据）` / `30 分钟（上游约束：<文档名>）` / `（平台基线）` |

### 4.3 不写的东西

**文档坐标**（`SR §x` / `RR §x` / `AR §x`）与**小节互指**（`见 A5`）一律不写：
坐标换个文档就失效，名字到哪都成立，且坐标由 AI 自己写、无法自证真假。
改用事物的名字——写「见管理台功能开关 `event_signup_enabled`」，不写「见 A5」。

## 5. 端云接口转写成契约来源

读者：写蓝图契约的设计作者。SE 文档里的接口设计格式不固定，原生契约要一份能逐段比对的结构化来源：由你读懂原文转写，机器只核蓝图与转写一致，转写是否忠实由设计质询对照原文核。

- **协议**：读冻结输入里的 SR 原文（`AR/story-src/inputs/<版本>/files/SR/...`），写 `blueprint/contracts/se-interfaces.yaml`。按原生结构分段写 operations（`operation_id`、`direction`、`version`）、dtos（`dto_id`、`fields[]`：`field_id`、`type`、`required`、`nullable`、`semantics`）、errors（`items`）、idempotency（`rule`）、nfr（`requirements`）。每段带 `provenance`，`source_ref` 写原文所在的冻结文件与章节（`provenance`、`source_ref` 不参与比对）。原文写了什么照写，没写的不补。转写是你从有效来源派生的，权威来自所指的来源，不来自转写文件本身。来源可以是冻结的 SR 原文，也可以是冻结的会议记录或人签里接口负责方逐项确认的内容，按发言者的实际权限、原话与后续人签判断，不按会议还是文档区分：负责方明确确认了的接口与字段，照确认的内容转写，保留它的权威，`source_ref` 指那段记录；只确认了意图、细节未定的，不补成完整协议，未定的类型、版本、响应登记缺口；你自己推导的部分单列，标 `inferred`。
- **映射**：每个 wire 字段落到本部件的哪个字段、怎么换算，是本部件的设计决定，写同目录 `mappings.yaml`（`mapping_id`、`kind`、`source_fields`、`target_field`、`rule`），用不到的字段写 `kind: drop`；`drop` 只表示原文给了而本部件不用，原文没给的响应字段登记缺口，不写成 `drop`。
- **引用**：蓝图 `contracts` 各段的 `source_ref` 写工程根起的路径加段落指针，如 `doc/features/<蓝图 id>/blueprint/contracts/se-interfaces.yaml#/dtos/<DTO>`；内容与所指段落逐项一致，键、取值类型与顺序都算（原生逐段比对）。
- **缺的与冲突的**：原文没给类型、版本、可空性，或前后说法冲突，登记缺口并写明向谁取得；当前施工单位要用的设为 blocker。不知道能不能为空就不写成不可为空，也不拿旧材料里的推测充当 SE 原文。当前设计依赖这个缺口时，补来源、经人授权调整范围，或交含未决的评审草稿；只改 `needed_by` 让它不挡准入不算处理。交互运行中要人定的问人，不用 `headless_assumed` 代替。
- **修订**：被旧 revision 引用的转写与映射文件保留，新版本用新文件名并改 `source_ref`。
