# S2 规则：来源材料导入

> 读者：S2 导入材料的主 agent。时机：收件箱里有还没导入的文件时完整读一遍；没有待导入的件直接去初析，不必读本文。

收件箱 `doc/features/<AR>/inbox/` 是一切上游材料的入口：需求系统取材的结果、人工拿到的文档、界面设计图与会议记录都从这里进来。
原件导入后**留在收件箱**；转换出的正文进 `RR/prd.md`、`SR/design.md` 等当前阅读稿，每一份原件的每个版本登记在材料索引里，
设计、成文、审查与更新都按登记的版本引用它。

## 材料怎么进来

- **需求系统的单据**：取材命令把这张单关联的开发需求、系统设计、产品需求正文取回到收件箱下的一个批次目录
  `inbox/fetch-<时刻>/`，批次里的回执写明每份是哪一类、哪张单——这些件**不用你归类**。
- **人工提供的材料**：请用户放进 `inbox/`（**告知用户这个路径，不要求他记**），整目录放进来也行，
  不用把子目录里的文件挪到顶层。每一层的点文件、点目录与 README 不收，链接不跟随。

**格式**：能不能读由你判断，脚本只负责物化——文本原样并入、`.docx` 转换（它是压缩包，必须脚本转）、图片原样保存。
所以 `.md` / `.txt` / `.log` / 无后缀这类**你直接读得懂的文本，扩展名不限，都可以直接放**。
碰到脚本物化不了的（如 pdf）：**你读得懂就自己转写成 `.md` 放回收件箱**再归类；你也读不了才请用户提供可读版本。

## 归类：这份材料在需求里承担什么

人工放进来的件**由你归类**，六类。按内容主体归，不是按文件名像什么归：

| 类 | 内容判据（回答什么问题） | 谁来消费 | 落点 |
|---|---|---|---|
| `RR` | 要解决的问题、给谁用、业务规则是什么——**用户与业务视角**（问题单、产品需求、运营规则都在此） | 背景、范围、业务流程、交付与上线 | `RR/prd.md` |
| `SR` | 系统怎么分工、接口/时序/数据/异常怎么定——**系统与端云视角** | 业务方案、业务流程、异常与恢复、附录 | `SR/design.md` |
| `AR` | 本部件侧的需求说明、补充说明、历史结论、部件内约束 | 初析与设计 | 需求系统取得的进 `AR/design.md`，人工补录的进 `AR/story-src/upstream.md` |
| `UX` | 界面长什么样（设计图、视觉稿、交互说明） | 页面交互与界面依据 | 图进 `assets/ux/`，文字说明并入 `assets/ux/README.md` |
| `IMAGES` | **这份料是为了补图**：正文系统上已经有了，它是原稿或参考稿，值钱的是里面的图 | 各章按图取用，正文不作依据 | 图抽进 `assets/<主名>.<路径摘要>/`，正文不并入 |
| `MEETING` | **需求澄清会议的记录**：人的讨论，有发言人、时间和来回说的话 | 读会（[phases/meeting-read.md](../phases/meeting-read.md)）；只收原始 `.docx` | `AR/story-src/meetings/` |

**什么时候选 `MEETING`**：内容是人的讨论记录而不是文档——有发言人、时间和来回说的话。
它是讨论态的证据，不是定论；会议原件与转换文本按会议版本留在 `AR/story-src/meetings/<主名>/<版本>/`，同名 docx 换了内容存成新版本。

**什么时候选 `IMAGES`**：已有同一件事的正文，而这份补料版本更早或更粗。把它当正文依据会用草稿盖住定稿，
而人要的只是图。**这一判断由你按材料做，不为它再问人一次**——人已经说过「补图」了。

判断依据按优先级：**用户在申报里的说明**（人说了算）> **读内容判主体**（你能读全文，这是最可靠的依据）>
文件名与首标题（仅作辅助线索）。一份文档混着多类内容时按**主体**归——归类是文件级的，拆不开。

**读 `.docx` 用预览，不要自己写解析**：

```
python doc/extensions/skills/story/scripts/core/import_sources.py --preview <docx 路径>
```

它输出正文与图清单、**不落盘任何东西**，用的是导入那一步同一个解析器——预览看到的正文，就是导入会写进去的正文。

## 落盘：先写判断，再跑脚本

1. 人工放进来的件写进 `doc/features/<AR>/inbox/.classify.json`，内容 `{"<相对收件箱的路径>":"RR|SR|AR|UX|IMAGES|MEETING", ...}`
   （键用 `/` 分隔；平铺在收件箱时就是文件名）；取材批次里回执列着的件不写；
2. `python doc/extensions/skills/story/scripts/core/import_sources.py --feature <AR>`

**为什么写文件而不是当参数传**：JSON 全是引号，而任何 shell 都要对参数再解析一遍——同一条命令在有的宿主下原样送达、
在有的宿主下双引号被吞掉。写文件不过 shell，哪都一样。这条对本 Skill 的所有脚本一致：**结构化数据走文件，参数只放标量**。

**导入的结果**：原件留在收件箱。同类材料各自最新的那一版按所在路径排序拼成当前阅读稿（落点见上表），一份原件占一节，
节标题是它相对收件箱的路径（系统取得的写角色与单号）；`.docx` 里的图按内容起名抽进 `assets/`。
每份原件这一版的字节与转换结果另存在 `.backups/local/`（原件在 `.backups/local/inbox/<原相对目录>/<主名>.<内容摘要><后缀>`，
阅读稿在 `.backups/local/<类>/<名称>-v<N>.md`，当前阅读稿每一版的副本在 `.backups/local/<类>/<主名>-聚合-v<N>.md`），
登记在材料索引 `AR/story-src/materials.json`——版本关系只登记在那里。当前阅读稿与收件箱里的原件给人读、给你定位；
设计引用的是 `.backups/local/` 里那一版（材料索引 `files` 里当前位置那一行的 `reference`），之后材料换版也仍指它。

- 同一来源（同一张单的同一类正文，或收件箱里同一相对路径的件）内容变了，导成**新版本**，旧版本的留存不动，已经引用它的设计与审查仍指得回原字节；
  已经导入过的原样件留在收件箱也不会重复导入。
- 换了位置或名字的件是**新来源**，旧来源仍在索引里可查。它是不是取代了旧来源由你读内容判，在初析或影响分析里写明；
  确是取代时，导入前先退掉旧原件（见下），不退的话两份都还在当前阅读稿里。
- 不同目录下的同名原件各成一个来源，不用请人改名。
- 直接写在 `RR/prd.md`、`SR/design.md`、`AR/design.md` 里的原文也是来源：第一次见到时登记它的字节；之后有人直接改了，
  它算待导入，导入时登记成新版本；正文没变、它引用的图换了也一样。图留在原处，导入按内容另存一份稳定的图给这一版用。
  人写的或人改过的当前阅读稿导入时不覆盖，同类的收件箱原件各自按自己的阅读稿读。

**新原件取代旧原件**：确是取代时，先退掉旧原件，新原件再放进来：

```
python doc/extensions/skills/story/scripts/core/import_sources.py --feature <需求名> --retire <旧原件相对收件箱的路径>
```

它把旧原件移到 `.backups/local/inbox/<原相对目录>/<主名>.<内容摘要><扩展名>` 并删掉它的归类键；路径不对、归类件读不出、
留存冲突时在动手之前停下，一个文件都不动。要恢复某一版，把那份移回收件箱原路径、改回原名、补回归类键再导入。

输入或格式有问题时导入在写盘前一次报全，一个文件都不动；写盘中途出了故障，报告会列出已登记的版本与还没登记的件，原件都还在收件箱，排除故障后重跑即可。

**之后**：归类结果与导入情况随初析摘要在 S3 关卡**一屏带出**（「本批导入：X.docx→RR、首页.png→UX…」）——归类错了用户会当场指出，
改归类件后把那份原件从它的版本目录复制回收件箱重导，按新的类成为新来源。

## 图片的说明与取舍

docx 里的图混着流程图与界面图。判据以**图在正文中的上下文**为准——紧邻「某某页效果如下」的那张就是界面图，
这条线索任何宿主都读得到；能看图时再直接查看导入打印出来的图复核，看不了不影响判断。

**每张图都要有一句说明**——它是什么，界面图、流程图、时序图、状态机都一样：

```
python doc/extensions/skills/story/scripts/core/import_sources.py --feature <需求名>   --caption-image <导入打印的图片路径> --caption "<这张图是什么>"
```

这张图不属于本需求（废弃的对照稿、别的单据的页面）时，在同一处登记不用它的理由；后来又要用它，撤掉理由：

```
python doc/extensions/skills/story/scripts/core/import_sources.py --feature <需求名>   --caption-image <图片路径> --unused "<为什么它不属于本需求>"
python doc/extensions/skills/story/scripts/core/import_sources.py --feature <需求名>   --caption-image <图片路径> --used
```

说明按图片内容记在材料索引里，同一张图出现在几个版本里也只写一次。那句说明不是可选的：成文时作者面上关于这张图的全部信息就是路径与它，
没有它，作者无从知道该在哪一章用它，图就留在材料里没人动。判错了重写覆盖即可。
