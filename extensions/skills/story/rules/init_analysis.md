# S2 规则：材料盘点、需求分析与流程契约

> 读者：S2 做材料盘点与需求分析的主 agent。时机：S2 开始前完整读一遍。
> 在哪停以 [SKILL.md](../SKILL.md)「停等真值表」为准。

## 0. 分两段做，中间隔着材料确认关卡

```
S2a 材料盘点   → 清单 + 一句缺口判断（**不做需求分析**）
S3a 材料关卡   → 材料已放进来源收件箱，请导入 / 现有材料就是全部，开始需求分析
S2b 需求分析   → ①需求概览 ②本部件视角 ③本 AR 定位 ④待实现功能清单 ⑤来源初筛
```

**为什么不能一口气写完**：材料不全时范围判断本身就不可靠——在一个还会变的范围上
做的分析注定作废，材料一变就要重做一遍。先花几分钟盘点材料、问一句还缺什么，
比先写两千字分析再发现缺料便宜得多。

材料确认之后就进设计（有会议先读会）；**不再有范围定法/承载哪份的关卡**：范围由蓝图承载，
「本需求只做 X」或「完整设计先实施 X」写进蓝图的需求条目与边界，不要求额外批准。

**轮次 = 一次材料状态**：料导入 → 材料变 → 新一轮；材料没变，重跑 `round` 幂等。
新一轮照样**重新盘点**，问的是「还缺什么」——够不够由你盘点、由人定，
文件到了不等于内容够了。不缺了就直接进 S2b（`status` 会这么给）；
还缺才把**剩下的**缺口写进缺口文件再停一次，写清还缺什么、为什么现有材料不够。
「材料变没变」由材料清单 `AR/story-src/materials.json` 的 `digest` 说了算——四份正文、
界面参考图、文档内嵌图都在里面，只补图片也换版本。分析件在同一轮内从盘点版演进到
完整版，不算新轮次。

## 1. AR/story-src/init-analysis.md — 决策支撑件

给材料确认与后续设计看的分析。它**不是交付件**：归档不含它，设计的需求条目也**不以它为源**——条目只引
登记的材料版本与人工答复，事实留在原件里一处。
第 ⑥ 节的来源初筛留给后面用：设计从它起步，成文与审查回来对照它和原文。

**S2a 只写第 ⑤ 节的 1、2 两段**（材料清单 + 缺口判断）；材料确认后再补齐 ①–④ 与 ⑥。

### ① 需求概览

这个需求是什么、要解决的问题。

### ② 本部件视角理解 —— 本需求落在本部件的哪一块

本部件的名称与别称、职责范围与交互方类别，在激活知识里自述回答「本部件是谁、与谁交互」的那一份——
按各知识 frontmatter 的 `applies_when` 找到它。对照它核对两项，结论即本节正文：

1. **落在职责范围的哪一块**——按职责范围逐条对需求：哪些在职责内、具体是哪一块；
   落在职责外的写明是哪部分、归谁；
2. **涉及哪几类交互方**——按交互方类别逐类给结论（命中 / 不命中 + 一句依据）；
   全都不命中即本需求与本部件无关，当场提出。

第 ③ 节的「部件在本 SR 下的全量」以本节核对出的职责范围为准。

### ③ 本 AR 定位 —— 本 AR 当前范围是什么

**整条范围链的起点。**三源逐条给结论，再收敛成一句。**按强度排序，先判强的**：

| 源 | 怎么判 |
|---|---|
| **AR 标题**（`title`） | 是否给出特性范围：落到具体特性上就是给了，只有单号加「开发需求」这类通用词就是没给 |
| **开发需求来源的预填**（`design_prefill`） | 需求系统给的开发需求正文已有范围/说明时按它理解，没有就写「无预填说明」 |
| **系统设计来源的关联 AR 清单**（`sr_related`） | 同一 SR 下还有哪些 AR。清单写明各 AR 分工时，**本 AR 那一条就是范围**（上游已经切好了）；只列单号没写分工时它至少是旁证——有兄弟 AR 就说明全量不可能都归本 AR |

→ **收敛一句：「本 AR 当前范围 = ______（来源：标题 / 开发需求预填 /
SR 关联清单 / 三源都没给 → 取部件全量）」**

这一节做的是**材料判读**：范围由上游材料给到哪一步。人对本次做多少有自己的打算是另一回事
——那是决定，在蓝图里与材料/质询后的问答处理，不在这里替他推断。

三源都没给出范围时取部件在本 SR 下的全量，**同样要把全量是什么写出来**，
并且知道这是**待确认的范围**——设计负责方在蓝图里按原件与人的原话定边界。

**不先定下这一句，后面的信号核对就没有施加对象**，只能默默按上游全量判——
那正是「本 AR 承载全部需求」被无声写下的地方：没人决定过它，它只是没有被质疑过。

写完落一份机器面副本到 `AR/story-src/.positioning.json`（格式见下）。

### ④ 待实现功能清单

本 AR 视角下要做的功能点，逐条可数。每条写工程现状：已有能力核到真实定义与调用（写出位置），没有的写缺口；
缺口会改变范围或验收的，在蓝图里连同它的影响写清，必要时按必要问人三条件问一次，不在后续阶段用近似或模拟悄悄顶上。

### ⑤ 材料现状与缺口

1. **材料清单**——人要先知道手上有什么，才谈得上要不要补。三列：**源 / 来源 / 是什么**，
   外加状态：

   | 源 | 来源 | 是什么 | 状态 |
   |---|---|---|---|
   | `RR/prd.md` | 需求系统取得 | 产品需求（业务背景与验收意图） | 已导入 v1 |
   | `SR/design.md` | 需求系统取得 | 系统级设计（分工、接口、时序） | 已导入 v2（v1 留存在 `.backups/local/`） |
   | `AR/design.md` | 需求系统取得 | 上游给进来的开发需求正文（可能已预填） | 已导入，无预填 |
   | `inbox/xxx.docx` | 人工提供 | 待导入材料 | 待导入 |
   | `inbox/<会议记录>.docx` | 人工提供 | 需求澄清会议记录 | 已读会、结论 N 条 / 待导入 |
   | `inbox/fetch-<时刻>/RR-prd.md` | 需求系统取回 | 产品需求新版 | 待导入，导入后成为 RR 来源的新版本 |

   - **只列实际存在的输入源**，状态取自材料索引 `AR/story-src/materials.json`（`sources` 与待导入的 `inbox`）；某一类来源整个没有就不列，
     收进下面那句缺口判断，一句话说清缺的是哪一类；
   - **单份写来源名**；**同类多份写类名 + 件数**（界面图（12 张）），
     **不穷举文件**——十几个文件名铺开，人反而看不出缺的是哪一类；
   - **同一来源的新版本**（update 取回的上游正文、放在同一位置的改版稿）导入后自动成为新版本，状态里写版本号；
     换了名字或位置的改版稿是新来源，是不是取代了旧来源由你读了判，在状态里写明「可能取代 <旧来源>」；
   - **逐项标状态**，光有文件名不算数：`已导入 v<N>` / `空` / `无法解读` / `待导入`。**文件存在 ≠ 有内容**——
     正文是空壳时，只看「文件在」会让整个缺料判断失真；
2. **一句缺口判断**（如「PRD 未归档，正文来自人工补录」；只列文件名等于没说）+ 本轮导入结果。
   **需求方提到但还没进来的材料**另起一小节逐份列：名称、在哪句话里提到、取还是不取、理由。
   取的写进缺口文件 `AR/story-src/.material-gaps.json` 的 `missing`，缺口判断那一句写进 `why`；
   脚本据 `missing` 算材料关卡的推荐：非空推荐请人放料，空的推荐开始分析。
   **不取的理由只能是「本轮范围不依赖它」，而范围依据来自 AR 或需求方的话**；没有就写「无」。

### ⑥ 来源初筛 —— 材料里每一块内容对本需求有什么用

把你读材料时已经形成的判断留下来：设计从这里起步，成文与审查回来对照它和原文，
不必把同一份材料再从头分类一遍。按**能独立判断的主题**逐块写——通常是最小一级标题下的正文；
父级标题自己有正文也算一块，用途相同的相邻几块可以合写一行：

| 来源位置 | 对本需求的作用 | 还要核实的矛盾或缺口 | 不适用的依据 |
|---|---|---|---|

- **来源位置**写文件路径加标题，原文留在原件里，这里不摘抄；
- 第 ④ 节功能清单已经表达清楚的，直接引用，不另写一张同义表；
- **不适用**要写出来源或范围上的理由；说不出理由的，登记到「还要核实」；
- **会议按话题登记**：来源位置写 `AR/story-src/meeting-notes.json` 的 `<主名>@<版本>/T<n>`，
  要指原话就写 `AR/story-src/meetings/<主名>/<版本>/raw.md:L<起>-L<止>`；作用写当前会议结果里
  这个话题的去向（`AR/story-src/doc-refresh.md`），「还要核实」写它仍未决的部分——
  各章写完后的回看清单从这一列取；
- 这不是逐格填满的配额：没有疑点的那一格空着。

**每轮重生成整个文件**（材料变了回到 S2 即 round+1），旧版进 `.backups/local/`。
重生成时，材料没变的那几块初筛判断原样沿用，只重判变了的与新增的。
现行版永远只有这一份，轮次历史查契约——编号累积（init-1、init-2…）会说不清哪份是现行版。

## 2. AR/story-src/story-flow.json — 流程契约

记录每一步的输入、输出与交互：**材料确认了没有**、设计问答里人答了什么原话，
事后可查。范围与业务决定由蓝图承载，契约不再维护第二份决定账。

**它同时是这条流程的状态机**：`status` 读它就回答「现在走到哪、下一步干什么」。
中断后恢复、或不确定该干什么时，**先跑 `status` 看 `next`**，不要靠回忆重建位置。

**你不写这个文件**——[scripts/core/story_flow.py](../scripts/core/story_flow.py) 是它的唯一写入者。
时间戳、轮次边界、收件箱里还有没有没导过的料、本轮并入了哪些文件，都由脚本自己取
（`round` 每次调用都按磁盘现状重算材料清单，答案从清单里读）；
**你只传它无从得知的那部分：材料缺口、本 AR 定位与人的原话。** 问法（选项、顺序、推荐）由 `status` 生成。

| 时机 | 命令 |
|---|---|
| 材料盘点后 / 需求分析后 | `python …/story_flow.py round --feature <AR>`（登记轮次并消费当时的定位侧车；两个时点各跑一次） |
| **任何时候拿不准走到哪** | `python …/story_flow.py status --feature <AR>` → 看 `next` 与 `action` |
| 材料停等点：先取问法 | `python …/story_flow.py status --feature <AR>`，把 `ask.block` 原样摆给人 |
| 材料人回话之后 | `python …/story_flow.py decide --feature <AR> --gate material_scope --ask <ask_id> --reply "<人的原话>"` |
| **材料已确认** | 进 component-design（`phases/design.md`「二、交给设计」）；需求条目写好后 `python …/import_sources.py --feature <AR> --scope <条目文件>` 补齐来源 |
| **设计后必要问答** | 按三条件写问法文件 → `status --questions-file <文件>` 生成一次 `ask` → 人回话后 `decide --ask <ask_id> --item <题号> --reply "<原话>"`；多题用 `--replies-file` |
| **设计开始之后材料又变** | 照常跑 `round`——它不会开新轮，只更新材料指纹并记一笔。补个说明文件、改个错字都属这一类，设计照常进行；要不要采用新版本由设计判断 |
| **设计开始之后真实范围变化** | 走 `/story update`：由蓝图负责方修订需求条目与边界，再同步 Story 与审查；**不再有 `reopen` 或范围关卡** |

### 侧车文件

结构化数据一律走文件——对话里的东西会话一断就丢，脚本也读不到：

| 侧车 | 谁写 | 何时被消费 |
|---|---|---|
| `AR/story-src/.material-gaps.json` | 你（第 ⑤ 节 2 的缺口） | `status` 据它出材料问法；`decide --gate material_scope` 记完销毁 |
| `AR/story-src/.positioning.json` | 你（第 ③ 节的机器面副本） | `round` |
| `AR/story-src/.ask.json` | 脚本（`status` 生成的问法） | `decide` 核对 `--ask`；设计问答答完后由脚本撤下 |

```json
// .material-gaps.json —— 还缺什么与一句缺口判断；不缺时 missing 给空数组
{"missing": ["结果页的界面图（需求方在材料说明里提到）"], "why": "来的原稿只有填写页"}

// .positioning.json
{"scope_text": "本 AR 当前范围一句话",
 "sr_related_ars": [{"ar": "<兄弟 AR 单号>", "scope": "该 AR 承载什么"}]}
```

`sr_related_ars` 只列**同一 SR 下的其它 AR**，没有就给空数组——**不含本 AR 自己**
（本 AR 的范围写在 `scope_text`；把自己列进去会让下游「有兄弟 AR 就不可能承载全部」
这条判断被自己触发）。

**材料选项内容不由你在关卡上写**：两项来自章节合同，脚本按缺口文件算推荐。

### 记录纪律

- **`--reply` 写人的原话**，不写你的转述——它是契约的审计价值所在；
- **签的只能是问过的**：`--ask` 必须是 `status` 当前给出的问法编号，选项集随它一起进契约；
  设计问答的问题与选项从已落盘的问法取，记录时不重填；
- **材料确认只认明确选择**：编号或整句标签；片段命中、模型替人挑一项都不算人的选择；
- **`decide` 的退出码回答「能不能按这个选择往下走」**：`0` 能；`2` 不能——选择已记录，
  但校验没过（如说了料已放进来源收件箱，收件箱里却没有新文件），按 stderr 提示重新与用户确认；`1` 是参数/前置错误。

**防跳步**：材料没确认时路由不进设计，`story` 拒绝登记，即「诊断出缺料却径直交给设计」这种跳步走不通。
没走 /story 的 feature 没有本文件，不适用。
