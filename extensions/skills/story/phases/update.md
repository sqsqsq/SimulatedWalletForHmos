# story update：把已有产物更新到当前有效依据

> 读者：跑 `/story update <需求编号>` 的模型。时机：这个单走过 /story，而上游材料、评审意见、人的新决定或有人直接改过的文档，
> 使现在的需求级产物（材料、提取稿、设计输入、Story、Review）不再与当前依据一致。

**要做的事一句话**：结合最新有效输入、既有决定和当前需求进展，判断哪些内容仍然成立、哪些要改，
使受影响的已有产物成为一致、可继续工作的依据，并说清仍未决或尚未验证的部分。

用户只给编号，不必先替你列出哪些文件要改。**完成对象是这次变化牵动的业务关系，不是某几个文件**——
一条关系含对象、前置、行为、结果、责任、异常、未决与验收，它的落点可能分散在几份产物里，
也可能有一部分在当前阶段还没生成。

**边界**（这几条不由你判断，是给定的）：只更新需求级的已有产物与必要的过程记录；设计由蓝图负责方在 component-design 里改，
施工（CU 的 spec、plan、代码与测试）由 Framework 的阶段推进——update 不授权施工，已有施工结果只查询并说明后续责任。
默认只改这次变化牵动的地方，整篇表达优化由用户明确要求才做，大幅重组先说明再动手；回写到需求系统之前先给人看结果。

## 零、输入阶段：先问要不要补料，再比

一次 update 的入口与 init 同构：**先取输入、报告并问补料，人答了再定最终的材料变化**，然后才是增量修订。
问法、侧车、人签与登记全是 init 第一级关卡那一套，差别只在每次 update 都停一次。

1. **系统需求先取上游**：按 SKILL「更新」② 调用取材，落点用 `update --action status` 返回的 `paths.inbox`。
   这一轮没取过上游，下一步的报输入会停下并指回这里。本地需求没有上游，跳过这一步。
2. **报告输入**：

   ```text
   python doc/extensions/skills/story/scripts/core/story_flow.py update --feature <编号> --action inputs
   ```

   它只报告、不建任何东西：六项里哪几份跟上次已处理的版本不一样、读不到的、收件箱里还没并入正文的原件
   （`pending`）、上次以来新并入正文的原件（`imported`）、最近一次取材的回执（`upstream`：逐份 `fetched` / `same` / `absent` / `failed`）。
3. **材料关卡停一次**：按 `rules/init_analysis.md` S2a 盘点手上的料（不取的理由只能是范围不依赖它），
   缺口写进 `.material-gaps.json`，跑 `status` 取问法；向人报告上游哪几份变了、没变、取不到，本地已有什么，
   一句缺口判断，`ask.block` 原样摆出，问**这一次要不要补料**，停下等他。
4. 他放料进 `inbox/` 或答「不补」→ `decide --gate material_scope --ask <ask_id> --reply "<原话>"` → 有新原件先导入 →
   `round` 登记到本轮（它不开新轮）。新原件是某份旧原件的新版本时，**导入前把 `inbox/` 里那份旧原件本身**
   移到 `.backups/local/<旧原件名>-<时刻>`（不删；`inputs` 的 `superseded_hint` 会列出同类的已归类原件），
   清单里写明取代关系——同一类原件导入时按文件名拼接，不移就是两版拼在一起。
   导入前的目标文件（如 `RR/prd.md`）由导入链自己备份，不用你管。
5. **比较并开这一轮**：`update --action prepare --result <materials|documents>`。`--result` 照人这次的请求记本轮终点：
   只取材与澄清、没有已有人读件受影响的是 `materials`；其余是 `documents`，已有 Story 受影响一律 `documents`。
   续做中的一轮可以从 `materials` 改记成 `documents`，反过来不行——终点不为收口降级。收件箱里还有未并入的原件时它会拒绝并列出文件。

取回的三份正文与人补的料一样在 `inbox/` 里等导入，归类照 init 的做法由你判；本单的系统正文与本地 story
逐字相同的（自己归档上去的那一版）不会落盘。评审回稿不是需求正文，落在 `AR/story-src/review-feedback.md`，
你读它，人的表态照下面的决策渠道记。**缺席与失败是两回事**：系统上没有评审回稿是常态，读不出来是故障——
后者要如实说成缺口。`fetch` 命令失败（包括目标工程的对接实现没有这条命令）时，报出来并停下，不用别的写入方式代替取材：
直接覆盖 `AR/review.md` 会把人刚写的意见吃掉。

## 一、`prepare` 比出的四种情况

比较只看**人和上游会动的六项**：`RR/prd.md`、`SR/design.md`、`AR/design.md`、`inbox/`（按材料事实，
不按文件哈希）、`AR/story.md`、`AR/review.md`。决策登记、写作设计与设计输入是你据它们写出来的中间真源，是结果不是原因，
不进比较。另列上次以来新并入正文的原件（`imported`，含只取图的）：只取图的原件正文不进六项，它带没带来业务变化由你读原件判。

比较结果是事实，不是结论：除了 `resume`，`prepare` 都开这一轮，要不要改、改哪里由你读原文与人这次的要求判。

| `comparison` | 意思 | 你做什么 |
|---|---|---|
| `unchanged` | 六项与上次已处理的版本逐份比过都没变，也没有新并入的原件 | 读人这次的要求与评审回稿判要不要改；没有业务变化时 update-notes 写明比过什么、为什么不用改，照常收口，报告「核对后无需修订」 |
| `resume` | 上一次 update 还开着 | 读它的 `update-notes.md` 与记录接着做完，或按记录撤回。**不要另起一轮** |
| `incomplete` | 比较基准缺席或有来源读不到 | 这不是「没有变化」。说清可查与不可查的范围，按当前材料与产物核一致性，**不补造「原来怎么写」** |
| `changed` | 有文件变了，或有新并入的原件 | 往下走第二节 |

需求目录里的文件按章节合同 `update_files` 分四类：你写的可改件（Story、草稿、写作设计、决策登记、提取稿、设计输入）、
脚本重生的评审记录与材料清单、受保护件（上游正文、收件箱、图、会议原件、冻结输入、独立审查记录、轮次记录与备份，没登记的文件也按它），
以及只由流程命令改字段的流程契约。`prepare` 把可改件与可重生件开轮时的样子留在 `AR/story-src/updates/<id>/before/`，
并记下它们的指纹——那是撤回依据，不是给你读的材料，不要往里写东西。

### 另外四个动作

| 动作 | 什么时候跑 | 它做什么 |
|---|---|---|
| `--action status` | 想知道现在有没有开着的更新、上一轮做到哪 | 报事实：开着的是哪一轮、本轮终点、撤回留下的冲突、说明在不在、本需求的本地位置（`paths.inbox` 是取材落点） |
| `--action feedback` | 评审人对设计议题提了意见 | 核本轮的 `design-feedback.json` 并记进本轮，见第二节 5 |
| `--action close` | 这一轮改完、核完 | 收口，条件见第二节 9 |
| `--action restore` | 这一轮要撤回 | 把可改件与可重生件退回开轮之前，规则见第五节 |

## 二、一条线：从还原依据到收口

这是一次 update 的执行顺序，可以因为补料或拿到裁决回到前面的步骤；**收口永远是最后一步**。
不要求每步一份文件或一次调用，一份 `updates/<id>/update-notes.md` 记住当前判断与去向即可，中断之后靠它和盘上的文件接着做。

### 1 还原当前有效依据

读当前请求、已有的来源说明、有效决定、当前 Story / Review、关联蓝图（评审投影与本需求相关的设计对象）与本轮相关的知识判断。
**把这几样分开**：材料原文、人的结论、你自己的假设、当前产物的表达、历史送审的版本。
同时弄清需求走到哪一步：只有材料、已交给设计、蓝图已准入、Story 已登记或已归档，施工单位（CU）有哪些、各阶段在哪。

先用已有的分析与当前版本建立理解，再回查涉及变化的那几处原文；旧分析可以复用，
但**与原话冲突时以原话为准**。比较基准缺席时明说证据不足，不补造。

### 2 解释变化并分派

对每一项新材料、意见、直接编辑与上一轮没做完的事，回答四问：它说的是哪件业务事；
相对当前依据改了什么；什么没变；是不是已经落实了，或与既有决定冲突。然后按它是哪一类变化分派：

| 变化 | 怎么处理，凭什么算完成 |
|---|---|
| 表达 | 改自有稿（草稿、Story、Review 措辞与结构），重新定稿、独立审查、登记；原设计引用不变 |
| 需求或范围 | 本轮里 `reopen` → 人在范围关卡真实确认 → 改提取稿与设计输入，`complete` 冻结新一版输入 → 蓝图负责方按新输入处理设计 |
| 对设计的意见 | 登记成设计议题、记下人的原话，写成设计反馈交蓝图负责方（第 5 步）；接受之后按新蓝图同步人读件 |
| 蓝图已经改了 | 读当前蓝图与评审投影，同步受影响的 Story 章节与附录，重新定稿、审查、登记 |
| 人直接改了稿子 | 先保存、理解他要表达什么，再把改动送回它的来源责任处（材料、设计或自有稿）；不把派生文档当成整体权威 |

- 看起来被删掉的要求，先核它的去向——是撤销了、挪走了，还是新版本只是没重复说一遍。**依据不足不删下游功能。**
- 「同意」「通过」这类笼统表态，先核它针对的是哪条议题、哪一版，再逐条经决策渠道记原话；不把一句「通过」写成对全部议题的复核。
- 新依据与其他仍有效的来源冲突（上游材料、已归档结论、安全口径），或改动已经承诺的行为时，
  **登记为 `open` 议题，两边来源并列，停下问人**；不按时间最新覆盖，也不替人选一边。

产出按业务主题组织，可以把几条同义输入并成一条，也可以把一段话拆成几件不同影响；**不要求一个文件差异对应一条语义变化**。

### 3 推演影响与保留项

以变化的对象或行为为中心，沿「前置 → 动作 → 结果 → 责任 → 异常 → 验收」查一遍上下文，
再看蓝图怎么实现它、知识判断是否因此适用或不再适用。对新发现的受影响关系继续查，
直到每项变化在已有产物里都有去向，或明确留下待决、不适用、交给设计或施工。

一个数值变化不只是换一个数字：它可能影响什么时候允许操作、提示怎么写、
接口的拒绝条件、异常路径与验收。**只同步现有材料证实存在的关系**——为了「全链完整」虚构一条不存在的能力，
比漏一条更难发现。

依赖靠你读材料判断，**不建通用依赖图、不用同词命中代替**。**列出重要的不变项，每项写出为什么不用改**——
防的是「优化一处、损坏另一处」。已有施工结果（CU 的规格、契约、代码与测试）没改的，也写一句它为什么不受影响，或要谁接着处理。

### 4 只在真的需要人时问

只有现有权限与依据定不了的才问：来源冲突、意见含糊、要改已经承诺过的事、范围扩展、大幅重组。
每项给出原来的解释、新信息、可选的处理及其后果与建议；**能在同一轮说完的集中问一次**。

人的决定限定到具体事项与这一次的输入。来源变化使旧的人签不再适用时明说；
**不因为沿用同一个议题编号就沿用他的勾选**。仍未决的事项继续约束相关内容，但不挡住那些独立且已经明确的修改。

**人答了之后先记下，再照决定改**：先把这件事登记成议题、build 进评审记录，人看过那一条再回话；
他回话后跑 `story_flow.py decide --feature <编号> --update "<定了哪件事>" --issue <议题编号> --reply "<他的原话>"`。
它记的是**原话**：`update-notes.md` 里写「已确认」不算人签，那是你的转述；**不另造「人工已批准 = true」这种自证字段**。
人已表态的议题登记为 settled 时，`review_mode` 怎么写见 `phases/story-write.md`「决策登记」。
议题的决定人只能是人的角色，改版文档不是决定人，也推翻不了人已经做的裁决。

**议题正文改了、而评审人已经在它下面写过意见**时，渲染会停下来：他答的是上一版的问题。
你判定只是改了措辞、问的还是同一件事，请他确认沿用，再跑 `story_flow.py decide --feature <编号> --update "沿用上一版表态" --issue <那条议题的 id> --reply "<他同意沿用的原话>"`，
然后重跑——渲染按 `--issue` 认回那条议题，带回他的表态。判定问的事变了，就让他重新看一眼那一条。

**范围要扩或缩在本轮里做**：跑 `story_flow.py reopen`，update 照旧开着；按 `status` 回到范围关卡问人，
人定了之后改提取稿与设计输入，`complete` 冻结新一版输入交给设计，蓝图负责方按它处理，再同步人读件。

### 5 对设计的意见交给蓝图负责方

评审人对某个设计对象（蓝图里的一处节点、关系、流程或契约）提了意见时，它挂的议题要带 `design_target.target_ref`
（那处设计的稳定地址，取自蓝图评审投影与知识任务），人的原话照第 4 步记下。然后把这些意见写成本轮的设计反馈
`AR/story-src/updates/<id>/design-feedback.json`：

```json
{"artifact": "blueprint-review-feedback@1", "blueprint_id": "<本单关联的蓝图>", "component_id": "<组件>",
 "source_revision": <成文登记时评审的蓝图版本>,
 "items": [{"feedback_id": "D3", "kind": "opinion", "source_revision": <同上>,
            "target_ref": "<议题登记的稳定地址>", "body": "<意见的内容>"}]}
```

- `kind` 按人说的性质选：`opinion`（意见）、`suggestion`（建议）、`fact_supplement`（事实补充，带 `evidence_refs`）、
  `authoritative_ruling`（授权裁决，带 `authority: {owner, role}` 与 `decision: {verdict, rationale}`，只在人确有授权并明确裁决时用）。
- `feedback_id` 是议题编号，同一议题几条写 `D3.1`、`D3.2`；人的原话留在决定记录里，`body` 写这条意见要设计改什么。
- 没有设计目标的业务意见不进这份文件，留在需求侧按议题处理。

跑 `update --action feedback`：它核每条挂在有设计目标、本轮有原话的议题上，并用原生校验判它够不够格进入调和
（缺授权、版本不对、地址不在蓝图里都会报）；资格按提交时的蓝图版本记下，文件没改就不重判。它另报当前蓝图里来源恰好是
「这份反馈的路径#feedback_id」的决定与它们的原生状态——**那只是相关决定，不是接受**。

**接受与否由蓝图负责方在 component-design 里定**：负责方的回复原文记进本轮 `update-notes.md`，你读它与当前蓝图判结果；
没有明确结论就保持待确认，不写成已接受。接受之后蓝图出新版本，按第 2 步「蓝图已经改了」同步人读件。

### 6 修订最早责任内容，再同步关联产物

| 内容层 | 你做什么 | 不能动的 |
|---|---|---|
| 外部原始材料 | 保留取得的版本与来源，更新本地采用的那一版 | 不替上游重写原话来消掉冲突 |
| 初析 / AR 提取稿 / 设计输入 | 修订本需求对来源的理解与承载边界，`complete` 冻结新一版 | 没变的范围与人签复用，没必要不重做初析 |
| 蓝图 | 经设计反馈或新输入交蓝图负责方 | 不在 update 里改蓝图，也不替负责方写接受 |
| Story / Review / 决策登记 | 用当前有效解释更新相关叙事、图与议题，保留人工意见的语境 | 不覆盖有效的手改；旧表态不移植到已经变义的问题上 |
| 已有施工结果 | 说明受影响的 CU、要谁接着做什么 | 不改 CU 的规格、契约、代码与测试，不重跑已完成的阶段 |

原材料与生产真源分开改。附录、编号、评审记录这些确定性投影仍由既有脚本产生，**不手改派生区去迎合检查**。
story 侧的改动：改草稿、`chapter` 提交 → 定稿、独立审查 → `story` 重新登记，做法见 `phases/design.md`「五、独立审查、登记与交付」。
派审期间不动被审的材料；本宿主没有审查员时，如实报告「这次更新没有完成独立审查」，不用自审顶替。新料 `round` 登记进当前轮，不开新轮。

### 7 按关系核对，再说能不能继续

从每项有效变化回查已改的内容，核正常、受限、异常与验收是否一致；从没变的重要关系查有没有误伤；
从待决事项查是不是仍然待决。再核结构、引用、编号与投影。

回查**不要求字面相同**，也不把「旧稿全部保留」当守恒：已经明确取消或被替代的内容应当退出当前版本，
历史留在本轮记录里。没有新增变化但上一轮的同步没做完时接着做，不按文件摘要提前收工。

### 8 写 `update-notes.md`

产出只有一份当前的 `update-notes.md`：当前依据、变化与影响、决定与修订、**不变项与理由**（一张表：
这次变化牵到却不用改的重要内容，每行写为什么不用改）、核对与剩余。
只写这一轮真发生的事，没问过的关卡不写成问过。
向用户展示业务上变了什么与可查的差异，**不要罗列对他决定没帮助的脚本步骤**。

### 9 收口

`update --action close`。它核：说明在、不变项表非空、没有未处理的撤回冲突；本轮终点是 `materials` 的，Story 与 Review 没被这一轮改过；
终点是 `documents` 且已有 Story 的，Story 已按当前内容与当前蓝图重新登记（登记本身核过结构与可消费的独立审查）——
新蓝图已接受而稿未同步的报 `needs_sync`，不收口。施工进展与设计反馈的相关决定只读报告，不挡收口；收口不代表设计反馈已被接受，也不取得施工授权。

## 三、当前做到哪一步，决定这一轮能做什么

| 当前进展 | 默认怎么做 |
|---|---|
| 只有材料或提取稿 | 更新已有的解释与材料，**不顺带交给设计或成文**；终点通常是 `materials` |
| 已交给设计、蓝图未准入 | 更新材料与设计输入，`complete` 冻结新一版；设计由蓝图负责方推进 |
| Story / Review 已登记 | 围绕有效变化核对并同步，重新定稿、审查、登记；本该有却没有的产物，报出这个事实，不用「自动补上」掩盖 |
| 已归档 | 保留旧的送审依据，更新本地工作稿；**人确认之后才回写** |
| 已有 CU 在施工 | 需求级产物同步到当前依据为止，标明哪些 CU 的规格、契约或实现可能失效、接手的人要做什么；**不自动改、不重跑** |

范围由这一轮的请求、实际变化与上一轮没做完的事决定，**不默认开展全需求质量翻修**。
核对时撞见与本轮无关的旧问题，记下来交给它的责任方；确实挡住本轮结果正确性的，纳进来并说明为什么。

## 四、报告什么结果

| 结果 | 什么时候成立 | 用户据此能做什么 |
|---|---|---|
| 已同步，可继续当前工作 | 受影响内容已按当前有效决定一致，适用检查完成，没有挡住当前工作的未知 | 在原进展上继续（**不代表需求自动进入下一阶段**） |
| 已同步，有明确保留项 | 业务未决、待蓝图负责方处理的设计反馈、非阻断建议或施工影响都已说清，没有被写成已完成 | 继续不依赖这些保留项的工作 |
| 尚未完成 | 必要的输入、裁决、同步或验证缺失 | 知道缺什么、影响哪些内容、下一步该谁处理 |
| 核对后无需修订 | 有效变化已经落实过，或只是表达差异、与本单无关 | 保留现稿（**不为留下更新痕迹而重写**） |

本地文件写完了、脚本退出 0、操作记录关闭了，**都不能代替上面这几个判断**。
没有历史版本时可以说「当前无需修订」，但不能说「历史从未发生过变化」。

## 五、撤回这一轮

`update --action restore` 只动可改件与可重生件，逐份按开轮时、本轮完成点（story 登记或收口）与现在的指纹判：

| 这一份 | 撤回时 |
|---|---|
| 现在就是开轮时的样子 | 不动 |
| 本轮完成点登记过它，现在仍是那一版 | 退回开轮时的样子；开轮时没有的删掉 |
| 本轮没到完成点就改过，或完成点之后又改过 | 保留现在的，列成冲突，给出开轮时与现在两版的位置 |
| 受保护件 | 一个字节不动 |

动手之前它把现在与开轮时不同的那几份、连同评审记录（人工区在里面）存进本轮记录目录。有冲突时这一轮照旧开着：
逐份和人定好要哪一版，改成那一版后再跑一次 restore，它只处理满足条件的那几份。人说过的原话、设计关联、冻结输入、
人签、轮次历史与发布记录都不随撤回回退；撤回之后成文登记与当前依据不一致的，它报出来，交付前按当前依据重新定稿登记。

## 六、回写需求系统

先把业务结论、可查的差异、未决与验证缺口**展示给人**，他确认之后才回写；
展示之后版本又变了就重新展示一次。回写走既有的 `/story archive`，不另建发布路径。

外部发布失败时**本地正确的修改留着**，重试之前先看外部有没有被别人改过——
重试的是发布这一步，不是把整轮理解与成文重做一遍。
