# spec 阶段 · 扩展要求（写之前读这一页）

> 读者：spec 阶段的作者。时机：动笔前读一遍；这一次的数据（知识原文、本施工单位承接的判断、缺口）看知识任务
> （story-knowledge Skill，`--action spec`）。

## 你在写什么

spec 是这个施工单位的需求规格：补清本单位的行为、边界与验收。知识应用的判断已经在设计里——CU 在蓝图的知识应用决定，
非 CU 的维护 Feature 在它契约的 `knowledge_applications`。知识任务第 3 块列出本单位承接的那几条与各自的要求、落点；spec 不重判，
把它们要求的行为与验证责任写进验收。判断站不住（不适用的依据回查不到事实、豁免缺理由）时交设计负责方修订，不在 spec 里改判。

知识任务第 2 块的「关联 Story 的已定表达」照录了与本单位相关的 Story 小节：适用的表达可以复用，与原生设计矛盾时按设计写并报出来，Story 的错交回 Story 作者；在已定表达上补本单位的局部细节是合法细化；共同设计或用户可见承诺要变的，交设计负责方经原生修订，不在本阶段改判。

## 验收怎么承接适用判断

本单位承接的每条适用判断（`outcome: applied`；处置以「（评审动作）」开头的不产生代码要求，不建验收），
`acceptance.yaml` 里至少一条 criteria 写出它要求的可观察行为与验证责任，并带上桥：

```yaml
criteria:
  - id: AC-012
    scenario: 处理完成后
    expected: 临时记录已清除，重新打开页面看不到上一次的内容
    knowledge_rule: RET-01
    knowledge_decision_id: knowledge-ret-01
```

- `knowledge_rule` 写判断里的单元，`knowledge_decision_id` 写那条判断的 `decision_id`：同编号的规约可能来自不同文件，下游按两项一起认。
- 一条 criteria 一个编号；同一规约在不同场景（正常、边界、异常恢复）各写一条。
- 验证责任与知识声明的执行体一致：要实机证据的规约，验收写得出实机上怎么判。
- 编号出现不等于承接：条件与结果说不清、只把规约换句话说一遍，都算没承接。

## 宿主扩展治理项怎么写

生成 spec.md 时，模板末尾的「宿主扩展治理项」给评审本单位的人讲：本单位怎样落实设计里的知识判断与技术约定。总表逐项写是否涉及和出处；涉及的，在总表下按小节写：

| 小节 | 写什么 | 从哪取 |
|---|---|---|
| 技术约定 | 本单位接口的新增、复用与变更，工程里现在的实现，数据约束与依赖边界 | 蓝图契约、`blueprint/contracts/` 下的转写与映射、工程事实 |
| 规约 | 逐条写判定、本单位的要求、业务落点与对应验收编号；不适用的写理由 | 知识任务第 2、3 块的判断；`acceptance.yaml` |
| 设计模式 | 每个激活模式的选、不选或待定与理由，本单位承担的范围 | 蓝图的模式判断 |
| 项目事实复用 | 复用了什么、为什么适用、缺什么 | 蓝图事实与工程来源 |

- 每行回答本单位怎么落实；只有来源链接或验收编号不算写完。
- 同一件事只写一处，别处引用它所在的小节；不把整份蓝图的表搬进每个施工单位。
- 判断以蓝图为准，这一章只作解释；判断要改的交设计负责方。
- 本单位不涉及的项在总表写「否」和理由，不建空小节。
- 这一次不生成 spec.md 时不补写，承接仍在验收条目里。

## 写字的几条

- **数值要标来源与测量对象**：阈值、时长、次数写明来自上游约束、本工程设定还是平台基线，条件与量的是什么一并写清；材料没给的数值不冠以上游约束。
- **说「已有」要核到真实的定义与调用**：通用页面、文件或方法签名不证明已有具体业务对象、状态与数据通路；计划中的能力与工程事实分开写。
- **改变外部状态的操作**（创建、修改、关闭、撤销）分别写明确成功、明确拒绝与结果未知：未知不当失败，写清以谁的状态为准、怎样确认、何时允许再操作、怎样避免重复副作用；协议缺查询或幂等依据时写明缺口与责任方，不编造接口。纯本地计算不必套这三种结果。
- **承诺与工程现状不符**（能力没有、页面不存在、字段缺失）时，正文写明差距并交需求或设计负责方，不用模拟或降级悄悄顶替。
- **未决的保持未决**：仍开着的选择，正文只写确定的共同要求，依赖它的行为与验收写成条件，不替人选一边；「占位」「待定」「候选」「先模拟」都不是选边的授权。
- 「验收标准」里一个编号第一次作行首的那一行是它的定义，行内的功能编号与 `acceptance.yaml` 的 `prd_function` 一致。
- 写完通读一遍，找错字、乱码与断句。

## 跑哪条命令

开始本阶段的实际工作之前（读代码、设计、改动之前），先取本阶段的作者知识任务（story-knowledge Skill，`--audience author`）：它同时记下本阶段的开始。第一次开始前在本 Feature 的目录（知识任务第 1 块写的位置）写 `.usage-input.json`：`{"agent": "<宿主>", "model": "<模型>"}`，不知道的写 null。

`cd framework/harness && npx ts-node harness-runner.ts --phase spec --feature <Feature id>`。派审、采纳与报告回来之后的处置见
[phase-closure.md](../../skills/story/reference/phase-closure.md)「闭环」。本单位有设计之外的新增工程事实要写时，取证与结论写法见
[`evidence-rules.md`](../../skills/story/reference/evidence-rules.md)。

## 门禁会拦什么

- 本单位承接的适用判断没有验收条目承接；桥接指回的不是本单位承接的适用判断；写了 `knowledge_rule` 没写 `knowledge_decision_id`，或写成列表。
- 设计里的知识判断本身有缺口（漏判、原文已变、落点失效）：交设计负责方。
- 有 spec.md 时：没有「宿主扩展治理项」章；本单位承接适用规约或选中模式，这一章下却没有对应小节；规约小节写到设计没判断过的编号；引用的验收编号在 `acceptance.yaml` 里没有。
- 「验收标准」里的编号在 `acceptance.yaml` 里没有，或关联功能两处不一致；一个编号在 criteria 与 boundaries 里说两件事。
- verifier 报告里没有本阶段判据的结论，或 WARN、FAIL 没有指向这份报告的处置记录。
