# 部件设计 · 知识要求（独立质询）

读者：在隔离上下文里质询蓝图的审查者。时机有两种：首次质询，你按首读载体答完人读稿正文的八问之后读质询任务核源；
复核修订，你按设计方的复核消息通读当前正文之后，按原问题与修订影响回查。任务由下面的命令生成，给出被评候选、采用来源、原生质询范围与回复要求。

```
node doc/extensions/hooks/shared/knowledge-task.mjs --project-root <工程根> --blueprint <蓝图 id> --action questioning --audience reviewer
```

你只读材料、逐项回复，不改蓝图与任何文件。任务第 3 块列的原生质询范围逐项都要有一条：问题、回答、证据、处置、责任方、验证去向；
未决项与处置建议另列。

首次质询：八问回答在前，核源在后。先独立读任务第 1 块列出的每份采用来源，再看 canonical 候选：来源里的条件、行为、边界、异常与责任都有承担的设计对象；没有承担对象的遗漏写进适用的原生整体质询项，给出来源位置、影响与责任方，不另造目标地址。然后对照知识原文与冻结材料核知识带来的设计效果。

复核修订：核原发现的修法，以及它影响到的设计对象、要求与验收，只对这些回查原件、有效人答与知识原文；未受影响项确认原结论与证据仍适用。

下列判据首次逐条完整核，复核按修订影响核：

- 与本需求相关的规约域都有逐条判断，没有漏读或漏判相关域；整域无关的理由站得住；理由说出本需求的具体事实，能回查到需求材料或仓内事实。
- 适用规约的义务是承担对象在本需求里的具体做法，落在真正承担它的设计对象上，没有曲解条目原意；不适用的，写出的需求条件与材料一致；争议、豁免与待定登记在原生决定或缺口里；登记了豁免不等于可以豁免——核这条规约原文允不允许、授权是否真实有效、理由与补偿是否成立，红线以知识原文与授权为准。
- 业务单元出现候选信号的模式都有判断，该用而没用的点名；选中模式声明的每个必需角色由蓝图里的设计对象承担，可选角色用不用看需求，角色怎样协作、取舍有理由；有信号却不用的写出反证。
- 每项埋点明细是一个指标，标题是指标名；按激活的上报知识核起止、分子与分母、观察窗口、取数责任、谁获知结果、随事件带的字段与去重责任，以及工程里已有覆盖还是新增，本端拿不到的写明由谁统计；没有统计需求的不硬加指标。具体编号与登记文件归施工单位，不因蓝图里没有编号判缺。
- 设计的改动边界覆盖实际要改的每个模块，当前切片用到的缺口挂在当前切片。
- 人的裁决引用了原话；模型的判断保持推断来源。
- 设计对象引的设计记录：核它是不是本次授权内形成、与有效需求和决定相符；外部事实与人的批准回原件与原话核，设计记录与对蓝图自身的定位只说明出处。
- 共同设计的关系按作者页「共同设计要讲清的关系」逐类核，从原材料与人答出发看设计有没有接住：
  - 业务目标与关键规则在设计对象或决定里读得到数值与条件；
  - 身份、状态的维护方与真源清楚，会过期的状态有取得当前状态的去向；
  - 每个被消费的字段有真实生产者与到达路径；
  - 明确失败、结果未知与过期状态分开，重试、新建、撤销的前提与请求身份有真实合同支持；
  - 人答要求等待的动作没有被设计先放行，只属于某个选项的行为没有写成共同设计，原材料冲突登记成了决定；
  - 本次新写的代码、页面、内部登记与取号作为工程落实承担，没有被列成承载缺口；外部不足登记成缺口，写明受影响路径；
  - 评审投影里的图看得到该有的参与方、先后与责任边。
  - 本端不执行的外部动作，它对本部件状态、展示与恢复的影响写进了设计；工程没有现成封装的承诺按材料设计了新写部分，没有被降成更弱的承诺；
  - 某类对象（埋点、配置、数据策略）空着时，核本需求是真不涉及还是漏设计；登记了缺口的义务，当前阶段能设计的部分仍在设计里，缺口只承载真实的外部未决。
  属于外部缺失的与内部漏设计的分开归因。
- 端云接口逐个对照采用的来源（SR 原文、会议记录与人工答复）、`blueprint/contracts/` 下的转写与映射、蓝图契约：字段、类型、必填与可空、版本、错误、幂等有没有改写或遗漏；哪些来自 SE 原文或接口负责方有记录的逐项确认（核发言者的权限与原话）、哪些是本部件的设计或推导；来源没给的有没有登记缺口而不是被补上，只确认了意图的有没有被补成完整协议。原生比对一致只说明蓝图与转写结构相同：转写有没有为迁就蓝图而偏离原文、映射有没有被写成上游已确认的协议，要回原文核。来源说不清的交人决定。

问题写明涉及的设计对象与知识条目。
