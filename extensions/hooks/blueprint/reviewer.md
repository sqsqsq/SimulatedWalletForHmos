# 部件设计 · 知识要求（独立质询）

读者：在隔离上下文里质询蓝图的审查者。时机：你按首读载体答完人读稿正文的八问之后，读质询任务核源时；
任务由下面的命令生成，给出被评候选、采用来源、原生质询范围与回复要求。

```
node doc/extensions/hooks/shared/knowledge-task.mjs --project-root <工程根> --blueprint <蓝图 id> --action questioning --audience reviewer
```

你只读材料、逐项回复，不改蓝图与任何文件。任务第 3 块列的原生质询范围逐项都要有一条：问题、回答、证据、处置、责任方、验证去向；
未决项与处置建议另列。首读的八问回答在前，核源在后：先独立读任务第 1 块列出的每份采用来源，再看 canonical 候选：来源里的条件、行为、边界、异常与责任都有承担的设计对象；没有承担对象的遗漏写进适用的原生整体质询项，给出来源位置、影响与责任方，不另造目标地址。然后对照知识原文与冻结材料核知识带来的设计效果：

- 与本需求相关的规约域都有逐条判断，没有漏读或漏判相关域；整域无关的理由站得住；理由说出本需求的具体事实，能回查到需求材料或仓内事实。
- 适用规约的义务是承担对象在本需求里的具体做法，落在真正承担它的设计对象上，没有曲解条目原意；不适用的，写出的需求条件与材料一致；争议、豁免与待定登记在原生决定或缺口里。
- 业务单元出现候选信号的模式都有判断，该用而没用的点名；选中模式的每个角色由蓝图里的设计对象承担，角色怎样协作、取舍有理由；有信号却不用的写出反证。
- 每项埋点明细是一个指标，标题是指标名；按激活的上报知识核起止、分子与分母、观察窗口、谁获知结果、随事件带的字段与去重责任，本端拿不到的写明由谁统计；没有统计需求的不硬加指标。
- 设计的改动边界覆盖实际要改的每个模块，当前切片用到的缺口挂在当前切片。
- 人的裁决引用了原话；模型的判断保持推断来源。
- 材料承诺的能力与工程现状对过：不实的能力、缺席的外部依赖、只能模拟而影响验收的，登记成了缺口。
- 恢复与兜底路径的发起者、查询身份、对象、状态真源与结果消费者讲得通，挂在真正承担它的一方。
- 端云接口逐个对照采用的来源（SR 原文、会议记录与人工答复）、`blueprint/contracts/` 下的转写与映射、蓝图契约：字段、类型、必填与可空、版本、错误、幂等有没有改写或遗漏；哪些来自 SE 原文或接口负责方有记录的逐项确认（核发言者的权限与原话）、哪些是本部件的设计或推导；来源没给的有没有登记缺口而不是被补上，只确认了意图的有没有被补成完整协议。来源说不清的交人决定。

问题写明涉及的设计对象与知识条目。
