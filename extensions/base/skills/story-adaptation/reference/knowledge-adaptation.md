# 知识适配方法

> 读者：执行 `/story adapt` 的维护模型。四格语法、列定义与下游引用合同见 `base/skills/story/reference/knowledge/protocol.md`；逐主题取证问题见 `reference/knowledge-topics.md`；独审与回流见 `reference/knowledge-review.md`。

## 首次安装作者

先核实安装脚本给出的游标、已有知识和加载问题。现在要为这个项目写起步知识。选一个项目确实处理的常规业务操作，从谁发起追到哪一方给出结果，找出做需求时会判断错的责任、能复用的公共能力和必须遵守的约定。每个候选先开原件：在使用方读调用和依赖，在提供方读接口和限制，约束另查正式规范或有权决定。用主题页核有没有漏掉项目级要求；用现有盘点说清拟写、可排除和缺什么，按一次范围确认接着写。写成别人能拿去圈范围、定设计和做验收的内容。拿刚才的常规操作和一个条件变化的操作走读后，把知识、目标原件与需求交独审。

## 已有知识的升级作者

从脚本给出的已适配版本继续，查看晚于该版本的条目和当前加载错误。先打开已有知识，判断哪个业务结论会改变，保留仍有效的原文、编号和人工决定。无适用变化时交回零新增；无游标但已有知识时从基线核覆盖，沿用已有结论。涉及新增义务而项目依据不足时，说明影响哪个决定、由谁补证。只重审受影响的知识，完成条件具备后按现有脚本记版本。

## 情景分流

| 情景 | 从哪里开始 | 本次交付 |
|---|---|---|
| 首次，正式知识为空 | 从工程配置和产品入口识别部件；有真实需求用它，无需求取仓内一个有实际调用的常规业务操作 | 起步画像；对该操作和项目跨模块决定确有用途的能力、规约及有据适用的方法/模式；卡住首需求的缺口写明影响 |
| 无游标已有知识（有正式知识、缺 `adapted_for`） | 从基线逐主题核已有知识和真实源；保留仍有效的原文、编号与条目引用 | 只补漏项、纠错、消重复并在原位合并登记；作者不自行推测游标 |
| 已适配、收到版本变更 | 读晚于 `adapted_for` 的演进条目、当前加载问题与受影响知识 | 有业务结论变化才定向修订并重审；无适用变化且可读时允许零新增；坏登记先报清缺件 |
| 无依据或资料相冲 | 先查代码能回答什么，再查有权文档或负责人能回答什么 | 已实现行为、已定业务责任、尚待裁决分别陈述；已有通路的部分继续，关键缺口不冒充首装就绪 |

## 作业顺序

1. **画清一笔业务的责任**：读当前需求、架构说明和入口注册，选一个常规操作。沿调用链追到直接决定结果、状态或外部交接的一方，再查相邻模块与失败分支以划清排除边界。只记后文需要的源位置；权威文档的已定责任与已实现行为分开陈述。
2. **定范围前先试证**：对部件归属、公共能力、项目级约束逐项自问「没有这条知识，下游会选错什么」。先开原件核使用方依赖/调用、提供方接口/限制与正式规范；再用 `knowledge-topics.md` 扫单个动作易漏的隐私、兼容、发布等项目约束。剔除单模块私有规则、编码格式/lint 与无助于决策的细节。需要多步推导才选方法型事实；模式只评流程编排与页面交互两个主题及实际使用的承载依赖。不按分类数量或固定文件名决定范围。
3. **一次范围确认定起步集**：按主题给出三态盘点——「适用及拟写内容 / 有据不适用及查过何处 / 缺口、影响及找谁补」。首批每份最多三项高影响内容，规约先按领域归纳合并再选（成熟仓已有超过三项的独立义务不因首次上限删减）。未入首批但会影响下游的重要义务在交回中明示，长期扩充归本仓维护者。不拆文件绕过上限，不要求人重复回答仓内可证事实。
4. **按四格起草**：先写业务判断，再写打开即可核实的源位置与边界；多端协作写清由谁决定结果。文件写完并合协议后才登记进根 `manifest.yaml > provides.knowledge`；同一事实只留一处权威正文，跨主题用引用；正文用项目读者语言，适配过程与待办留交回。
5. **作者自用一次，再交独审**：拿本次正常需求和一个改变命中条件的邻近需求走读——读者应选对责任方、复用入口与验法，条件不成立时停止套用。随后按 `reference/knowledge-review.md` 交独立读者；按问题返修受影响知识并重审，保持 `--check`/`--status`、摘要、部分完成与最终 `--mark-adapted` 边界。

## 四类成品的内容标准与拒收对照

- **项目事实 · 分面（`facts × facets`）**：一个二级标题回答一类查找问题，每项短句给「有什么、项目位置、怎样用、何时不能用」。部件画像先一句边界与上游别称，再列协作方、本端职责与交接结果；能力面只收跨需求公共入口，声称「应复用/已在用」须由使用方依赖或真实调用证明，仅凭应用壳层同名目录推断公共能力属退稿，删去类内部调度过程。
- **项目方法 · 上下篇（`facts × halves`）**：上篇从解决的业务判断与不适用边界推导到下篇可接结论；下篇逐项给项目入口、值来源、取得时机、缺值责任人与验法，且能迁到另一笔业务。拒收仅列 SDK、事件名与成功率的目录式说明；区分本端仅见已受理与权威完成回执，无方法依据时不编编号、渠道或下篇。
- **项目规约 · 条目（`constraints × entries`）**：按同一决策与业务结果聚类归并；权限、例外或验收主体不同会改变下游处置则拆开。按 `protocol.md` 填列，强制力取自正式规范或有权确认，已有实现仅核落差；落法附注只解释易误读边界。拒收按载体重复抄写或把日志脱敏扩大成禁止受权对端接收原始业务标识；人工归档按评审动作表达，不把多条独立义务压成含糊一句来凑首批上限。
- **设计模式 · 上下篇（`patterns × halves`）**：只评流程编排与页面交互两主题。先以目标实际依赖及采用处证明承载能力，再以业务信号与反例定适用；下篇据真实承载库写角色职责、落点、最小协作顺序、库保证与项目纪律及可观察完成条件。已有采用、候选用法与尚无实例分开写；仅有普通代码相似或仅声明依赖未见采用时，不造「项目惯用模式」，也不从单模块自动归纳第三种模式。

## 确认与交回

- 校验命令：`node doc/extensions/base/skills/story-adaptation/scripts/adapt-scan.mjs --check`（知识、入口、使用记录与对接层全量只读核）与 `--status`（读 `knowledge.digest`、`knowledge.sameUse`、`knowledge.review`）。
- 交回必报：本次情景与范围确认结果、按主题三态盘点、新建/修订清单、独审执行体与发现处理、未入首批的重要义务与缺口（含影响及补证方）、对接层真实环境验证结果；仅在机制、知识读回、独审有效与对接全部过关后跑 `--mark-adapted` 落盘 `adapted_for`。
