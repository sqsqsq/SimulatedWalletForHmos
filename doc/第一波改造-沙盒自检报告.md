## 一、两个核心痛点与对应策略

| 痛点 | 现象（用户真实样例） | 第一波策略 |
|------|---------------------|-----------|
| P1 — **Scope creep**（Skill 2 偏离原始诉求） | 只想开发 BankCard，AI 生成 design 时擅自在 `03-CommonBusiness/CardManager` 新增接口 | 引入 **三阶段 Scope 守门**（PRD → design → coding，每阶段有 BLOCKER 校验） |
| P2 — **弱模型 ArkTS 正确率低**（缺即时反馈） | MiniMax/GLM 生成的 .ets 文件频繁踩同类坑，需要大量人工返工 | 引入 **`arkts-pitfalls.md` 15 条易错对照** + **强制逐文件 Lint 门禁**（禁止批量生成后统一 lint） |

两个策略共同遵循的设计原则：**把"软约束"升级为"硬门禁"**——弱模型会"读了不做"，必须有脚本 check 在 `--phase` 链路上兜底。

## 四、试金石实测（BankCard 越界拦截）

1. PRD 声明 `in_scope_modules: [BankCard]`，`out_of_scope_modules` 显式列出 `CardManager` 等。
2. 故意造一份 `design.md`：`inherited_from_prd: false`，`in_scope_modules` 擅自加 `CardManager`，`expansions_with_user_approval: []`。
3. 运行 `--phase design --feature bank-card`，实测输出：

   ```
   ✗ FAIL [BLOCKER] scope_consistency_with_prd
        未经用户批准就扩大到 PRD 之外的模块：CardManager；触碰了 PRD.out_of_scope_modules：CardManager
   ```

4. ✅ **结论**：Scope 越界在脚本 harness 层被精确拦截，不依赖 AI 自觉。试金石文件已清理，`doc/features/bank-card/README.md` 描述了三种玩法（合格 / 拦截 / 合规扩展）供后续内网回归。

## 五、待内网验证的假设与指标

第一波只完成了"框架落地与沙盒自检"，以下假设必须在**内网 MiniMax/GLM + Claude Code CLI** 跑一遍真实需求才能验证：

| 假设 | 验证方式 | 成功标准（建议） |
|------|---------|-----------------|
| Scope 守门能真正减少"CardManager 被乱动" | 用 `/design` 对 BankCard 跑一遍弱模型 | `scope_consistency_with_prd` 在 AI 尝试越界时能触发提议流程或硬拦截，人工介入 ≤ 1 次 |
| `arkts-pitfalls.md` + 逐文件 Lint 能降低 ArkTS 返工 | 与改造前同一需求对比 | 单 .ets 文件首次 lint 通过率 ≥ 70%（当前实际可能在 30-50%） |
| trace.json / gap-notes 能稳定回传 | 内网跑完后人工 review | 每个阶段都有合法 trace.json，且至少一份 gap-notes 能被直接反馈到下一波迭代 |
| CLAUDE.md + slash command + verifier 子 agent 对弱模型可用 | 内网 Claude Code CLI 运行 | 弱模型在无人工提示下能完成一次端到端的 prd → design → code 链路 |

## 六、已知局限 & 下一波改造预告（非本次交付）

1. **`check-design.ts` 的接口签名启发式判定仍有误报**（如 AccountManager 的 callback 类型）——需要在下一波用更精确的 TS AST 解析替换。
2. **`diff_within_scope` 依赖 `git diff HEAD~1`**，对多 commit 特性分支需要 `HARNESS_DIFF_BASE_REF` 环境变量；内网常态化使用前要配套 CI/hook 脚本。
3. **verifier 子 agent 目前是"只读审查员"**，尚未闭环到"FAIL 自动回退到上一 Skill 修复"。下一波可考虑让 verifier 输出可被 `/code` 等 slash command 直接消费的 patch suggestion。
4. **Trace 数据的聚合分析未做**——`harness/reports/` 目前只堆积单次跑动文件，缺少跨时间/跨模型的统计视图，需要一个 `harness-report-aggregator.ts`。
5. **未覆盖的痛点**：资源国际化、HAR 发布版本管理、OHOS_SDK 升级兼容等，目前 skills 里只有经验性约束，尚无门禁。

## 七、给内网实战的最短操作路径

1. 克隆框架骨架到真实钱包工程（只需 `CLAUDE.md`、`.claude/`、`skills/`、`specs/`、`harness/`、`doc/architecture.md` 这几棵树；模块目录按真实项目结构自行适配）。
2. 把真实项目的模块清单同步到 `doc/architecture.md` 的"五层模块架构"小节（这是所有 scope 校验的源头）。
3. 选一个"用户真实遇到过 scope 被乱动"的历史需求作为首个试金石，重复本项目"BankCard 试金石"的三步流程。
4. 每次跑动后填 `gap-notes.md` → 带回 Cursor 侧 → 进入下一波迭代。
