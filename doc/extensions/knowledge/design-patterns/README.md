# 设计模式

**本工程用哪些固定的代码结构，各自在什么情况下用**——工程级事实，不属于任何单个流程阶段。
消费方各自决定怎么用：plan 拿它选型并投影进契约，coding 拿它落码，review 拿它核查。

本文件是**模式清单与路由的唯一真源**。新增或下架模式改这里（与对应模式文档），
消费方的流程规则不动。

`pattern_id` 是全链的**受控标识**：候选登记、知识决策表、各阶段门禁都只认它。
Spec 填候选列时是**查表**——填这里在册的某个 id 原样，或按单元写「无候选」；
路由表里没有的名字（包括通用软件模式名）不是合法值。

## 划分粒度：什么算一个「适用单元」

判断前先把需求切成单元，再逐个单元核对信号。当前各模式的单元粒度：

| 粒度 | 含义 | 用于 |
|---|---|---|
| 流程段 | 一段有独立业务目标、有明确起止的处理过程 | 结构类模式 |
| 页面/组件 | 一个承载用户操作的界面单位 | 交互类模式 |

一个需求通常有多个单元；同一单元可能命中多个模式（叠加使用），也可能一个都不命中。

## 路由：什么信号指向什么模式

| 观察到的信号 | 粒度 | 指向 | `pattern_id` |
|---|---|---|---|
| 业务流程有多个分支，每个分支自身是一段复杂功能（多步云侧调用、回滚或补偿分支） | 流程段 | 流程分支编排 | `decision-tree` |
| 单个页面/组件内用户交互多，且交互之间由业务结果驱动先后顺序 | 页面/组件 | 页面交互编排 | `page-interaction` |
| 单一线性流程、两三个分支且各自只有一两步、无跨步骤状态；或页面只有几个彼此独立的按钮 | — | 不用模式，直接写 | 零命中 |

**零命中是正常结论**，不是遗漏——为不需要的场景套模式，只增加阅读成本。

## 多模式组合

同一需求可以在不同适用单元使用不同模式，也可以在同一业务链中组合；组合不是把两个模式的角色揉成
一套类。plan 先分别完成每个单元的信号判断和契约投影，再声明二者如何衔接：

| 要回答的问题 | plan 落点 | coding / review 判据 |
|---|---|---|
| 每个模式解决哪一个独立问题 | 知识决策表登记适用单元和理由，`project_knowledge` 冻结实例名 | 每个编排对象职责单一，不因组合而跨越自身边界 |
| 上下文所有者是谁 | contracts 的 data_models / interfaces | 上下文只有一个明确所有者；跨模式只传必要结果，不共享可任意改写的全局状态 |
| 先启动谁、何时交接 | use-cases 的 branches / user_sequence | 交接由显式接口或业务状态触发，不靠双方互相持有并递归调用 |
| 用户等待点在哪里 | use-cases 的 user_actions / state_model | 等待用户时当前编排停机，由新的用户动作恢复；后台流程不越过等待点 |
| 失败由谁收敛 | contracts 的 interfaces 与异常映射 | 每个失败只有一个最终处置者，避免两个模式重复提示、重复补偿或重复跳转 |

组合完成的判断不是“两个 `pattern_id` 都出现”，而是各自边界、上下文所有权、交接、等待与失败收敛
都能从契约追到代码。没有组合需求时不创建组合层。

## 模式清单

| `pattern_id` | 文档 | 解决什么 | 依赖 |
|---|---|---|---|
| `decision-tree` | [decision-tree.md](decision-tree.md) | 复杂分支流程：每个分支都是复杂功能，if/else 难以维护 | 编排 SDK（oh 包名 `framework`） |
| `page-interaction` | [page-interaction.md](page-interaction.md) | 页面交互多：把交互与业务逻辑关联，业务结果驱动下一个交互 | 编排 SDK（oh 包名 `framework`） |

编排 SDK 与仓库根 `framework/`（工作流框架）无关，依赖声明在消费模块的 `oh-package.json5`。

## 模式文档的固定结构

每份模式文档按读者分两部分，消费方按需读、不通读：

| 部分 | 读者 | 内容 |
|---|---|---|
| 上篇 | plan | 解决什么问题、什么时候不该用、契约投影（模式概念落到哪些契约字段） |
| 下篇 | coding、review | 框架行为事实、角色与文件落点、结构骨架、使用约定、反模式 |

每份文档还要给出“验证清单”：plan 能据此判断契约是否完整，coding 能据此完成最小编译与关键路径测试，
review 能据此逐条核查 SDK 保证与工程纪律。示例骨架必须使用当前工程真实 SDK 类型并保持内部自洽。

**新增模式时**：写一份同结构的文档，在上面两张表各加一行，并在 `manifest.yaml` 的
`provides.knowledge` 声明——三处齐了，plan/coding/review 才读得到它。
消费方的 hook 与 overlay 不需要改：它们只认路由表与 `pattern_id`。
