# 应用域常驻约束（constraints）

本目录是**跨需求常驻**的应用域约束知识：每个需求在 spec 阶段逐域判定，结论回显进评审叙事件。
七域中除「应用特殊配置」的少数条目外，其余均为 HarmonyOS 应用通用约束，与具体业务无关。

## 使用方法（运行时）

判定在 **spec 阶段**做（那时 SR / PRD 都在手上，取证成本最低），产物分三处落——这三个出口是本目录的全部消费方：

| 判定产出 | 落点 |
|---|---|
| 命中 / 不涉及的**结论** | 叙事件 `AR/story.md`「影响面与风险」章的两张表（兼容性自检 + 应用域约束符合性） |
| 判定中冒出来的**代码要求** | `spec.md` §7 非功能性需求（UX 适配 / 触发频次 / 存储兼容 / 个人数据采集） |
| 判定中得出的**待某方确认** | 决策件 `AR/review.md` 的待定项段 |

1. 判定前按下方「文件清单」逐个读取约束文件，按各文件「回显指引」逐 rule id 判定；
2. 应用域约束符合性表每行给「是/否 + 一句话结论 + 规约编号」；「否」须给一句判定依据。
   编号写**中文规约名 + 编号**（如「安全隐私规约 SEC-03」），**不写 `security-privacy:SEC-03` 这类 slug**
   ——叙事件与决策件都随归档上传，评审者打不开仓内文件；
3. `compatibility-checklist.md` 是**兼容性自检表**的逐项过表数据源（COMPAT-01～11）；
   `telemetry.md` 由 `spec.md` §9.4 埋点 + 本表「资料交付」行共同承载；
4. 条目中的 `<待补充：…>` 表示该基准值/流程尚未录入——判定时写「基准待补充，按条目语义定性评估」，**不得臆造数值**；
5. 「本部件适用性」标**不适用**的条目（目前仅 `compatibility-checklist.md` 有）不参与命中判定，两张表都无需为其单列「不涉及」；
6. 「出处」标**工程增补**的条目仍须判定——它只表示该条目未在上游规约中找到原文，不表示可以跳过。
