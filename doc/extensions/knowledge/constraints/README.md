# 应用域常驻约束（constraints）

**本目录是工程级常驻约束的权威**：写在这里就是规则，条目一律平权，修订走评审改这里。
适用面是 HarmonyOS 应用，与具体业务无关。

## 知识与用法分离

知识只答**「约束是什么、怎么判断命中、怎么验」**；**「哪个阶段怎么用」由消费方各自维护**。
知识文件里不写消费方的落点坐标（章节号、表名、流程环节），也不写其他文档的章节编号——
引用外部规范时只写规范名与主题。

## 条目字段模型

**九域同一张表，列的含义只在这里定义一次**——各域文件不复述。
判定纪律（怎么判、边界在哪）见各域的 `## 判定附注`，那是内容不是列语义。

| 字段 | 回答什么 |
|---|---|
| **约束** | 要求是什么 |
| **命中条件** | 什么需求涉及本条 |
| **处置** | 须声明什么结论 |
| **验证（执行体）** | 怎么确认做到，由谁执行 |
| **强制力** | 红线 / 基线 / 建议 |

落法细节（API、配置字段、代码位置）写在各域的 `## 落法附注`，按条目 ID 列出。

**执行体四类，声明前须能指出它今天在哪运行**：

| 执行体 | 运行位 |
|---|---|
| **模型** | 撰写期自查 + verifier 语义复核，可执行条目内的检索式 |
| **构建** | 编译期校验、CodeLinter 规则 |
| **实机** | ut / testing |
| **人工** | 评审与流程动作，框架只查留痕 |

## 适用矩阵：哪个域在哪个阶段被消费成什么

同一个域在不同阶段消费的维度不一样——COMPAT 在 review 是拿 diff 逐项过，在 ut 是旧缓存
兼容用例。下表是适用总览，格子只写消费维度；怎么消费归各阶段自己的文档
（story/spec 见 [`skills/story/reference/constraint-usage.md`](../../skills/story/reference/constraint-usage.md)，
其余阶段见共享钩子 [`hooks/constraint-application.md`](../../hooks/constraint-application.md)
与各阶段的 `phase_rules_overlays`）。

格子非「—」意味着那个阶段真的会读这一域，其阶段须在 `doc/extensions/manifest.yaml`
有 hook 或 overlay 挂载。

| 域 | story / spec | plan | coding | review | ut | testing |
|---|---|---|---|---|---|---|
| ux-consistency | 命中判定与回显 | 布局方案（折叠屏/深色） | 资源引用与方向性属性 | 检索硬编码色值与文案 | — | 深色/大字体/RTL 实机走查 |
| security-privacy | 命中判定与回显 | 暴露面与权限方案 | 脱敏、权限申请处、调用方校验 | 日志与权限 diff 检查 | — | 抽查 |
| dfx-baseline | 命中判定与回显 | 缓存与频次方案 | 落实 | 调用频次与后台任务检查 | — | 性能测量 |
| compatibility-checklist | 命中判定与回显 | 兼容方案 | 版本/设备/包配套声明落实 | **diff 视角逐项** | 兼容用例（旧缓存/旧接口） | 升级路径验证 |
| env-exceptions | 命中判定与回显 | 恢复策略设计 | 防重入与状态恢复落实 | 检查 | 环境异常用例 | 实机故障注入 |
| deliverables | 命中判定与回显 | — | — | — | — | 交付走查（翻译回稿/归档） |

「—」表示该阶段不消费本域，不是「暂缺」。

## 强制力的含义

| 强制力 | 违反的后果 |
|---|---|
| **红线** | **阻断**：命中而未处置即评审驳回 / 门禁拦截，不得以「后续再补」放行 |
| **基线** | **须给结论**：可以不做，但必须写明为什么不做以及补偿措施，由评审判断是否接受 |
| **建议** | **可不做**：不做时无需理由，做了更好 |

强制力受执行体约束：**只有验证执行体真实存在时才可标红线**；判定基准缺失时，红线范围
收到今天验得了的那一部分，其余登记待补。**执行体是人的条目不标红线**——框架能查的只有
留痕在不在。

## 读条目时须知

- `<待补充：…>` 是**空缺登记**：判定时写「基准待补充，按条目语义定性评估」，
  **不得臆造数值**；补齐的办法是在本目录填上。空缺登记在哪个字段，说明它阻塞的是哪个环节；
- **编号在条目进入本目录时按域内顺序分配，一经分配不复用；条目删除后编号留空**；
- 条目内的检索式（正则、diff 判据、key 比对）是给模型的可操作判据，照此执行。

---

> 修订条目走正常评审：改本目录的文件即可，**这里就是权威**。
> 新增条目须同时给出强制力、命中条件与验证执行体——没有执行体的条目不得标红线。
