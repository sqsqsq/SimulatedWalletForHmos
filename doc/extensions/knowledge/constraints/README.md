# 规约

各域同一张条目表，列义如下；判定边界见各域的「判定附注 / 落法附注」。

| 列 | 含义 |
|---|---|
| **编号** | `<域前缀>-<两位序号>`，全链受控标识 |
| **约束** | 要求是什么 |
| **强制力** | 未满足时怎么处理：**红线** = 阻断，命中就要落实，不许豁免；**基线** = 可本轮豁免，须写理由与补偿，由评审判断；**建议** = 可不做，须写理由 |
| **命中条件** | 什么需求涉及本条 |
| **处置** | 须声明什么结论；以 `（评审动作）` 开头的不产生代码要求——不进 spec 约束出口、不建验收条目，只在评审记录留痕 |
| **验证（执行体）** | 证据从哪来：写成若干段 `<执行体>：<怎么验>`，**各段都要**。执行体取 **模型**（撰写自查 + verifier 复核，可执行条目内的检索式）/ **构建**（编译、CodeLinter）/ **实机**（ut、testing）/ **人工**（评审动作，框架只查留痕；评审动作的条目必须有它） |
| **探针** | 机器能做的局部形态检查，写「无」即没有：`absent_regex:<正则>`（不得出现）/ `present_in_method:<正则>`（方法体内须出现）/ `referenced_outside_definition`（定义文件之外被引用）/ `count_eq:<正则>:<次数>`（命中次数恒等）。前缀 `阻断：` 表示这个形态本身就是要求，不过即那处落点未落实；不带前缀只是取证线索，认不出不等于没做 |

强制力与验证是两件事：红线可以只由模型验，基线也可以有探针。

## 读条目须知

- `<待补充：…>` 是空缺登记：判定时写「基准待补充，按条目语义定性评估」，不得臆造数值。
- 条目内的检索式（正则、diff 判据、key 比对）是可操作判据，照此执行。
- 判「不命中」也要给依据——「不涉及」三个字不构成结论。
- 需要具体封装（类名、路径、API）时看项目知识，规约不写它们。
