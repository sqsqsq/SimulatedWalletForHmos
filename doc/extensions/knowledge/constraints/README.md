# 应用域常驻约束（constraints）

**本目录是工程级常驻约束的权威**：写在这里就是规则，条目一律平权，修订走评审改这里。
适用面是 HarmonyOS 应用，与具体业务无关。

## 知识与用法分离

知识只答**「约束是什么、怎么判断命中、怎么验」**；**「哪个阶段怎么用」由消费方各自维护**。
知识文件里不写消费方的落点坐标（章节号、表名、流程环节），也不写其他文档的章节编号——
引用外部规范时只写规范名与主题。

本目录**不维护阶段消费路由**：哪个阶段读哪一部分、结论落到哪，由各阶段自己的规则声明。
在这里维护一张阶段矩阵就是第二份真源，它和各阶段规则迟早对不上。

## 条目字段模型

**各域同一张表，列的含义只在这里定义一次**——各域文件不复述。
判定纪律（怎么判、边界在哪）见各域的 `## 判定附注`，那是内容不是列语义。

| 列 | 回答什么 |
|---|---|
| **编号** | `<域前缀>-<两位序号>`，全链受控标识；一经分配不复用，条目删除后编号留空 |
| **约束** | 要求是什么 |
| **强制力** | 红线 / 基线 / 建议 |
| **命中条件** | 什么需求涉及本条 |
| **处置** | 须声明什么结论 |
| **验证（执行体）** | 怎么确认做到，由谁执行 |

**处置以 `（评审动作）` 开头**的条目是纯流程动作，不产生代码要求：它们不进 spec 的约束出口，
也不建验收条目，只在评审记录里留痕。

**执行体四类，声明前须能指出它今天在哪运行**：

| 执行体 | 运行位 |
|---|---|
| **模型** | 撰写期自查 + verifier 语义复核，可执行条目内的检索式 |
| **构建** | 编译期校验、CodeLinter 规则 |
| **实机** | ut / testing |
| **人工** | 评审与流程动作，框架只查留痕 |

## 落法附注写什么

各域的 `## 落法附注` 只承载三类内容：

1. **平台隐性例外**——读代码看不出来的框架行为（哪个 API 才镜像、哪个属性对哪种容器不生效）；
2. **边界**——本条管到哪为止，与哪条不重叠；
3. **本工程决策的理由**——为什么这么定，而不是另一种。

**不写目标工程的实现事实**：工具类名、模块路径、API 签名、既有封装一律归项目知识
（[`codebase-facts.md`](../codebase-facts.md)），需要指到具体封装时写
「见项目知识《工程取证事实登记》‹面名›」。规约换个工程不变，封装换个工程就不同——
把封装名复制进规约，等于给同一个事实建了第二份真源。

## 强制力的含义

| 强制力 | 违反的后果 |
|---|---|
| **红线** | **阻断**：命中而未处置即评审驳回 / 门禁拦截，不得以「后续再补」放行 |
| **基线** | **须给结论**：可以不做，但必须写明为什么不做以及补偿措施，由评审判断是否接受 |
| **建议** | **可不做**：不做时无需理由，做了更好 |

强制力受执行体约束：**只有验证执行体真实存在时才可标红线**；判定基准缺失时，红线范围
收到今天验得了的那一部分，其余登记待补。**执行体是人的条目不标红线**——框架能查的只有
留痕在不在。

## 读条目时须知

- `<待补充：…>` 是**空缺登记**：判定时写「基准待补充，按条目语义定性评估」，
  **不得臆造数值**；补齐的办法是在本目录填上。空缺登记在哪个字段，说明它阻塞的是哪个环节；
- 条目内的检索式（正则、diff 判据、key 比对）是给模型的可操作判据，照此执行；
- 判「不命中」也要给依据——「不涉及」三个字不构成结论。

---

> 修订条目走正常评审：改本目录的文件即可，**这里就是权威**。
> 新增条目须同时给出强制力、命中条件与验证执行体——没有执行体的条目不得标红线。
