# 兼容性检查表

叙事件「兼容性自检」表的**直接过表数据源**：判定时对本表逐项过，命中项进表并给分析结论；未命中类别汇总一行「不涉及」。

> 本表逐行取自规约 §11.1，**行序与「涉及范围」列均保持规约原值**。「本部件适用性」列是按 `skills/story/rules/ar_design_init.md §1 本部件申明`（单框架 / 纯鸿蒙钱包 / 手机应用）做的裁剪结论，**不适用的行保留不删**——部件形态变化或回查规约时仍需能找到。

## 条目

| ID | 分类 | 检查项 | 涉及范围（规约原值） | 本部件适用性 |
|---|---|---|---|---|
| COMPAT-01 | API 接口-方法签名 | 是否修改现有方法名称/参数类型/参数顺序/返回值？淘汰方法是否 @Deprecated + 迁移文档？移除是否隔多个主版本并提前通知？ | 单双 | 适用 |
| COMPAT-02 | API 接口-数据结构 | 是否删除服务端或旧版 App 依赖的字段？字段类型变更新旧两端能否处理？新增字段有无默认值/可空？新增字段是否改变现有字段含义或触发服务端新校验？ | 单双 | 适用 |
| COMPAT-03 | API 接口-错误码 | 是否修改/删除已有错误码定义与含义？ | 单双 | 适用 |
| COMPAT-04 | API 接口-依赖兼容 | 升级 SDK 内部第三方库时是否评估与**宿主 App** 已存在版本的兼容性？SDK 支持的 **minSdkVersion** 是否清晰？使用新系统 API 是否加 **@RequiresApi** 注解、低版本有安全回退？新增权限是否经必要性评估？ | 双 | **不适用**——双框架 / SDK 分发形态的检查项，本部件为单框架纯鸿蒙 app，非 SDK 提供方 |

| COMPAT-06 | API 接口-文档沟通 | 每次 **SDK 发布**是否提供详细变更日志？不兼容变更是否提供迁移指南？ | 双 | **不适用**——同 COMPAT-04 |

| COMPAT-08 | 系统权限 | 使用处最小化申请，禁止一次性请求所有权限 | 单双 | 适用（规约同分类下另有一行「不同 **Android** 版本权限请求逻辑差异」标「双」，对本部件不适用，未收录） |
| COMPAT-09 | 渠道 SDK/API 升级 | 升级三方支付渠道 SDK（银联/云闪付/微信支付/支付宝）时变更日志已读？初始化/调用/回调接口变化已关注？不同 OS 版本与设备行为已验证？依赖库与**收银台**或其它 SDK 冲突？最低 OS 版本提升对收银台兼容范围的影响？**收银台**代码是否适配 URL/参数/响应/错误码/签名规则变更？ | 单双 | **按需**——检查主体是收银台与支付渠道 SDK。本部件不集成渠道 SDK，拉起收银台属 `ar_design_init §2` 第 5 类交互方（其他手机应用），收银台自身适配不由本部件承担；仅当本部件直接集成渠道 SDK 时才判定 |
| COMPAT-10 | 端云配套 | 新端是否强制依赖新云（功能依赖新接口）？若是有无应对策略？老端配套新云体验是否符合预期（云侧新增数据结构/端侧版本号规避）？ | 单双 | 适用 |
| COMPAT-11 | 版本配套 | 端侧版本之间是否存在依赖（与周边应用配合，重点看涉及外部调用的地方）？ | 双 | **不适用**——规约标「双」。本部件与周边应用的交互按 `ar_design_init §2` 第 5 类交互方在 spec §7.3 安全性要求登记调用方 |

> 以上均为「有兼容性风险的场景」，命中且有违反时须有分析结论与兼容性方案设计，确保不产生兼容性问题。

## 回显指引

兼容性自检表的生成规则：逐 ID 判定命中与否，**「本部件适用性」为「不适用」的行不参与命中判定**（亦不需为其单列「不涉及」，在末尾汇总行一并说明即可）；命中判定必须能指回**具体变更的名字**（如新增接口 createBusinessOrder 的入参字段 → COMPAT-02 命中）；「检查项」列写 COMPAT-xx 编号；应用域约束符合性表无独立行（兼容性自检表即本表的回显）。
