# 上篇 · 统计设计（读者：写统计设计的作者、审查者）

## 统计设计 — 读完交出：指标、点位、各点的业务结果与本端获知时机、边界

### 1 先分清四个词

**指标**是由采集到的结果算出来的比率、分布或耗时，例如成功率、失败原因分布、步骤耗时。**流程**是一段有起止的业务过程，由步骤组成，步骤下可有子点；一个指标可以汇总几条流程，一条流程可以支撑几个指标。材料里「提交、审核、撤回三类事件」这类**事件分类**是采集对象的分组；「开通率不低于 30%」这类**业务目标**是产品要达到的结果；两者都不是指标。材料只给了事件分类或业务目标时，先写出本需求要算哪几个率或分布，再说明它们与业务目标的关系。

### 2 什么时候不做统计设计

依据写成「不涉及：<事实>」，「不涉及」三个字本身不是依据。三种情形：需求不新增、不改变任何业务流程的结果（纯文案、样式或资源），写出改了什么；要观察的结果已由项目现有采集完整覆盖，写出覆盖它的现有点位；材料明确本需求不做运维观察且无运营诉求，写出材料位置。

### 3 应用步骤

1. **定指标**：一句写它衡量什么，一句写要算它需要哪些结果。
2. **沿流程列点**：步骤、子点、步骤整体、流程整体各是一个统计对象；不同流程里的同名步骤带流程限定。
3. **每点写结果与获知时机**：只写实际适用的业务结果，写明本端在哪个响应、回调或状态查询里得知；远端产生、本端看不到的，写由谁统计或列为待决。
4. **写边界**：一次尝试从发起到终态，重新发起是新尝试；前一步失败而没进入的步骤不记。同一业务事实只在产生它的那一侧、那一条流程下采集一次，别的指标引用它。远端产生的状态在本端是回显，按首次得知状态变化计一次。页面进入与点击说明不了业务结论，统计设计写业务结果。
5. **选渠道**：VOC 定位过程问题、Chart 做运维统计，是当前实现；同一统计终态上两者二选一，过程关键点用 VOC。BI（独立运营采集）与交互自动记录（页面进入、点击）是已定规范、仓内无实现，不算已有覆盖，写成建设差距；独立运营采集只在需求明确要求时加。

### 4 示例

示意：假设开通分三步、最终结果由服务端回调告知、无运营诉求；步骤与结果都不是本项目的答案。

```markdown
#### 服务开通成功率与失败原因（服务开通流程）

衡量用户发起开通后最终开通的比例，以及没开通时卡在哪一步。依据是开通的三步（信息校验、短信验证、开通结果）与运维要求。要算它，需要每一步的结果和一次开通的最终结果。

| 统计点 | 业务动作 | 实际适用结果 | 本端获知时机 | 已有或新增 |
|---|---|---|---|---|
| 短信验证 / 校验验证码 | 用户提交验证码 | 通过 / 未通过 / 请求失败 | 校验响应，或请求发出后通信失败 | 新增 |
| 开通结果 | 服务端告知开通结果 | 开通成功 / 开通失败 | 开通结果回调或查询 | 新增 |
| 开通全流程 | 一次开通收敛 | 成功 / 失败 / 用户取消 | 开通结果确定或用户终止时 | 新增 |

- 验证码重输是新的一次尝试；同一次尝试只有一个结果，重复回调不重复记。
- 开通结果由服务端产生，本端在回调或查询里得知，按首次得知计一次。
```

### 5 完成判断

1. 每个指标标题是指标名加流程名，第一段读得成「这个率或分布由下表的结果算出」。
2. 每个结果写了本端在哪个响应、回调或状态查询里得知；远端结果写了由谁统计或列待决。
3. 同一业务事实只出现在一张表里，别处引用；远端状态按首次得知计。
4. 材料里的事件分类或业务目标已翻成指标，并写明关系。

### 6 反模式

按流程或事件类型分节、每节只写「观察 X 链路」而没有可算的指标；把登记文件、字段接口、编码形态这些上报实现写进统计设计。

# 下篇 · 上报落地（读者：实现作者、编码、审查、测试）

## 上报实现 — 读完交出：每个结果的责任方法、身份与取值候选、去重与验证

### 7 角色与落点

- **尝试持有者**：决定业务结果的业务方法（发起、撤销各一处），持有本次尝试标识，重新发起时新建；公共上报封装只组装发送。
- **结算方法**：一次尝试只结算一个结果，正常响应、业务失败、请求异常与重复回调都调它；它是对外声明的业务方法，写进契约。
- **登记文件**：特性自己 shared 层以 `ChartCodes` 结尾的常量文件，首次使用时新建，写进契约的文件清单。

### 8 SDK 行为事实

- Chart 用 `WalletHAManager.chartBuilder(eventID, funcID, subFuncID)` 链式设字段后 `.report()`：模板 `eventID` 是 hiAppEvent 事件名，流程与步骤写进 `FuncID` / `SubFuncID`，Builder 生成 `WalletEventID` = `FuncID_SubFuncID`（如 `Wallet_COMMON_001_002`），平台类型 STATISTIC。
- VOC 用 `vocBuilder(eventID, desc).report()`，同时记本地日志用 `logAndReport` / `logErrorAndReport` / `logDebugAndReport`。VOC 另用标识：类型 BEHAVIOR，`WalletEventID` 由调用方给，`FuncID` 固定 `VOC`。
- 两者经 `CommFunc/src/main/ets/index.ets` 导出，发送不阻塞业务、失败只记本地日志，不做业务去重。字段 setter 与类型见 `WalletHAReportBaseCBuilder`。

### 9 使用约定（审查逐条核）

1. **候选就是具体值**：按「编号分配与复用」取号，写出流程号、步骤号与十位内码，标「候选，待登记：<登记文件>」；评审确认的是这些值。
2. **结算一次**：结果在决定它的业务方法里报；发请求与结算分开，正常响应、业务失败、请求异常与重复回调都调结算方法，一次尝试记一条；重新发起建新尝试，尝试标识与业务幂等键各管各的；已发出的请求按它自己的最终结果记。
3. **分类按语义**：`setWalletFuncResult` 取 `SUCCESS` 全流程成功、`STEP_SUCCESS` 步骤成功、`STEP_ERROR_BY_ERROR` 普通失败（含拒绝授权）、`STEP_ERROR_BY_USER` 用户主动取消；内码 `setWalletEventInCode` 定位具体结果，与分类独立。
4. **只带拿到的**：外码 `setWalletEventExtCode` 只带实际拿到的外部错误码；耗时 `setDuration` 有诉求且起止明确时带。
5. **身份共用**：同一步骤各结果共用身份，身份不随结果改名；同语义的运维与运营点位引用同组常量；BI 传参走项目 BI 接口，不从 Chart 封装推。
6. **BI 选参**：按运营需求选，不默认带运维内码、外码或分类；项目协议允许时可借内码、外码表达相近的业务含义，同时写明运营侧的含义、取值来源与消费约定，不沿用运维解释；自定义维度 `setReportParam` 只放标准字段之外的维度，扩展参数见「业务扩展字段」。

### 10 示例

把上篇示例落到实现。`OpenFlow`、`SmsVerify` 与其方法是待建设计的示意名，`Wallet_COMMON` 是现有模板；编号按「编号分配与复用」首次候选取号，全部未占号。

| 统计点 | 身份 | 结果 → 内码（候选） | 结果分类 | 外码来源 | 责任方法 | 去重与耗时 | 验证 |
|---|---|---|---|---|---|---|---|
| 短信验证 / 校验验证码 | `Wallet_COMMON` / `001` / `002` | 通过 `0101020200`；未通过 `0101020201`；请求失败 `0101020202` | STEP_SUCCESS / STEP_ERROR_BY_ERROR / STEP_ERROR_BY_ERROR | 响应里的外部错误码；请求失败取错误对象里的码 | SmsVerify.settleCheck | 每次提交验证码一次尝试；重复回调不再报；耗时=请求起止 | 三种结果各一条；重输后再出一条 |
| 开通全流程 | `Wallet_COMMON` / `001` / `000` | 成功 `0101000000`；失败 `0101000001`；用户取消 `0101000010` | SUCCESS / STEP_ERROR_BY_ERROR / STEP_ERROR_BY_USER | 失败那一步的外码 | OpenFlow.finish | 一次开通只记一次；耗时=首次提交到收敛 | 正常、校验失败、取消各一条 |

去重键是「一次尝试＋统计点」，不是身份或结果码；尝试标识由 `OpenFlow` 持有并交给结算方法，与业务幂等键各管各的。登记文件示意为「待登记：<特性>ChartCodes」。

### 11 结构骨架与核对

结算方法先看 `attempt.settled`，已结算直接返回；否则置位，再 `chartBuilder(模板, 流程, 步骤)` 设内码、分类与实际拿到的外码后 `report()`。`attempt` 是尝试持有者交给结算方法的对象。核对：三种结果各一条事件；回调重复到达仍是一条；重新输入后再出一条。

### 12 完成判断

1. 统计设计的每个统计点、每种结果一行，责任方法是契约里声明的「接口.方法」。
2. 每行的流程号、步骤号、内码是具体值并标候选；写不出的行写明缺哪一项依据、影响哪几行。
3. 尝试持有者与结算方法有名字，重复回调、重试、取消都落在结算方法上。
4. 验证列写出每种结果预期的原始事件与次数。

### 13 反模式

用「失败号」「xx」代替值并称待登记；同一方法同一结果写两行；报点写在不发请求的方法上。

## 编号分配与复用 — 读完交出：具体候选号与登记位置

现有定义（当前实现）：模板枚举在 `CommFunc/src/main/ets/shared/ha/WalletHAEventID.ets`，只有 `Wallet_COMMON`；仓内尚无业务流程、步骤、内码登记，也没有 Chart 调用。身份按「模板 → 流程 → 步骤」分配，流程号、步骤号三位；内码十位，按「业务模块 → 模块内流程 → 节点 → 子节点 → 具体结果」分配，每段两位、前导零保留；两处流程段长度不同，不互相截取。本仓采用的分配规范（Demo 拟定；目标仓以自己的登记为准）：

1. 先扫全仓模板、常量与调用，同语义已有值直接复用，跨特性共用模板时先核全部已有定义；身份不是流水号，同一步骤的新结果扩展内码，不复制身份常量。
2. 新值在父范围取未用号作具体候选：首次升序从 `001` / `01` 起；步骤号 `000` 与节点段 `00` 表示流程整体，子节点段 `00` 表示步骤未细分；结果段 `00` 成功、`10` 主动取消，失败取其余未用号。
3. 父范围首次使用时，由本次设计直接给出父范围与子项的具体候选号并写依据；评审确认这些候选；编码前登记并重核冲突，有冲突回设计改号。有外部统一分配的用其结果，拿不到时列出待决项，不自行占号。
4. 登记文件放特性自己的 shared 层，以 `ChartCodes` 结尾，首次使用时新建；设计里在具体值后标「待登记：<登记文件>」，写入前重核冲突，有冲突回设计调整，不自动换号。

## 业务扩展字段 — 读完交出：要用字段的含义、来源与必填条件

`WalletHAReportBaseCBuilder.ets` 另有 `setChannel`、`setSource`、`setIssueID`、`setIssueName`、`setOperationType`、`setSrcPassType`、`setOrderNumber`、`setTransactionId`（string）与 `setHappenedTime`（string | number）。本仓没有这些字段业务含义的依据，要用时先取得项目参数规范或负责人确认，写明：Channel 与 Source 的区分与取值、IssueID / IssueName 指哪个主体、OperationType / SrcPassType 取值集合、OrderNumber 与 TransactionId 的区别、HappenedTime 格式，以及实际用到字段的必填条件、来源与隐私处理。只取要用的。
