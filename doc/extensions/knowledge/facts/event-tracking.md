# 埋点上报

把业务结果变成可算的指标，按项目协议上报。**当前实现**以 `05-SystemBase/CommFunc/src/main/ets/shared/ha/` 为准；**已定规范**是本仓采用、尚未实现的要求。

# 上篇 · 适用与统计设计（读者：spec）

## 1. 解决什么问题

- **指标**：由事件结果算出的比率，如成功率；失败原因、耗时是随每次上报带上的事件字段。
- **流程**：有起止的业务过程，由步骤与子点组成；一个指标可以跨几条流程。
- **事件分类**（「提交、审核、撤回三类事件」）与**业务目标**（「开通率不低于 30%」）都不是指标，先翻成要算的率。

## 2. 什么时候不该用

- 需求不新增、不改变任何业务结果（纯文案、样式或资源）。
- 要观察的结果已由现有采集完整覆盖。
- 材料明确不做运维观察，且无运营诉求。

## 3. 应用步骤

1. **定指标**：一个指标一个小节，标题写指标名；写衡量什么、怎么算（分子分母是本端哪些结果；以后台数据为分母的，写需要什么数据、由谁统计）、每次上报带什么、在哪些流程哪些步骤打点。
2. **列统计点**：步骤、子点、步骤整体、流程整体各是一个点；不同流程的同名步骤带流程限定。
3. **写结果与获知时机**：只写实际会发生的结果和本端在哪个响应、回调或查询里得知；本端看不到的写由谁统计或列待决。
4. **定边界**：重新发起是新尝试；前一步失败而没进入的步骤不记；同一业务事实只在一处采集；远端状态按首次得知计一次；页面进入与点击不进统计设计。
5. **选渠道**：当前实现是 VOC（定位过程问题）与 Chart（运维统计），同一统计终态二选一；已定规范是 BI（运营采集，需求明确要求才加）与交互自动记录（页面进入、点击），仓内无实现，写成建设差距。

示例（假设开通结果由服务端回调告知）：

```markdown
##### 服务开通成功率

- 衡量：发起开通后最终开通的比例。
- 怎么算：开通成功的尝试 / 全部开通尝试。
- 每次上报带：失败原因（回调错误码）、耗时（提交到得知结果）。
- 在哪打点：服务开通流程的校验验证码与开通全流程。

| 统计点 | 所在流程 | 业务动作 | 实际适用结果 | 本端获知时机 | 已有或新增 |
|---|---|---|---|---|---|
| 短信验证 / 校验验证码 | 服务开通 | 提交验证码 | 通过 / 未通过 / 请求失败 | 校验响应或通信失败 | 新增 |
| 开通全流程 | 服务开通 | 一次开通收敛 | 成功 / 失败 / 用户取消 | 回调首次得知或用户终止 | 新增 |
```

# 下篇 · 结构与落地（读者：plan、coding、review）

## 4. SDK 行为事实

- **Chart**：`WalletHAManager.chartBuilder(eventID, funcID, subFuncID)` 链式设字段后 `.report()`；`WalletEventID` = `FuncID_SubFuncID`（如 `Wallet_COMMON_001_002`），平台类型 STATISTIC。
- **VOC**：`vocBuilder(eventID, desc).report()`，记本地日志并上报用 `logAndReport` / `logErrorAndReport` / `logDebugAndReport`。VOC 另用标识：类型 BEHAVIOR，`WalletEventID` 由调用方给，`FuncID` 固定 `VOC`。
- **发送**：经 `CommFunc/src/main/ets/index.ets` 导出；不阻塞业务，失败只记本地日志，不做业务去重。
- **现有定义**：模板枚举 `WalletHAEventID.ets` 只有 `Wallet_COMMON`；仓内没有流程、步骤、内码登记，也没有 Chart 调用。
- **字段**：setter 与类型见 `WalletHAReportBaseCBuilder`；业务扩展字段（`setChannel`、`setSource` 等）的含义本仓无依据。

## 5. 角色与文件落点

| 角色 | 职责 | 命名惯例（拟定） |
|---|---|---|
| 尝试持有者 | 决定业务结果的业务方法，持有本次尝试标识，重新发起时新建 | 业务流程类的提交或查询方法 |
| 结算方法 | 一次尝试只结算一个结果；正常响应、失败、请求异常与重复回调都调它；写进契约 | `settle<结果>` |
| 登记文件 | 流程、步骤、内码常量 | 特性 shared 层 `<特性>ChartCodes` |

## 6. 结构骨架

接上篇示例（`OpenFlow`、`SmsVerify` 为示意名，编号只示范取号形态）。共同约定：身份按步骤共用（校验验证码 `Wallet_COMMON` / `001` / `002`，开通全流程 `Wallet_COMMON` / `001` / `000`），外码取实际拿到的错误码，全流程带耗时。

| 统计点 | 结果 | 责任方法 | 字段取值 | 去重与验证 |
|---|---|---|---|---|
| 短信验证 / 校验验证码 | 未通过 | SmsVerify.settleCheck | 内码 `0101020201`，STEP_ERROR_BY_ERROR，外码取校验响应的码 | 每次提交一次尝试，重复回调不再报 |
| 开通全流程 | 成功 | OpenFlow.finish | 内码 `0101000000`，SUCCESS，耗时从提交到得知结果 | 一次开通只记一次 |

结算方法先看 `attempt.settled`，已结算即返回；否则置位，`chartBuilder(模板, 流程, 步骤)` 设内码、分类与拿到的外码后 `report()`。

## 7. 使用约定 — 人为纪律，SDK 不强制，review 逐条核查

1. **候选就是具体值**：写出流程号、步骤号与十位内码，标「候选，待登记：<登记文件>」。
2. **编号按分配规则**（Demo 拟定，目标仓以自己的登记为准）：身份「模板 → 流程 → 步骤」，流程、步骤号三位；内码十位「业务模块 → 模块内流程 → 节点 → 子节点 → 结果」，每段两位、保留前导零。同语义已有值直接复用，同一步骤的新结果扩展内码；新值在父范围升序取未用号，从 `001` / `01` 起；步骤 `000`、节点 `00` 表示流程整体，子节点 `00` 表示未细分；结果 `00` 成功、`10` 主动取消、其余为失败。有外部统一分配的用其结果，拿不到列待决；编码前写入登记文件并核冲突。
3. **结算一次**：结果在决定它的业务方法里报，一次尝试一条；尝试标识与业务幂等键分开；已发出的请求按它自己的最终结果记。
4. **分类按语义**：`SUCCESS` 只给流程整体成功，步骤成功 `STEP_SUCCESS`，普通失败（含拒绝授权）`STEP_ERROR_BY_ERROR`，用户主动取消 `STEP_ERROR_BY_USER`；内码定位具体结果，与分类独立。
5. **只带拿到的**：外码只带实际拿到的外部错误码；耗时 `setDuration` 在起止明确时带。
6. **BI 与扩展字段**：BI 按运营需求选参、走项目 BI 接口，同语义的运维与运营点位引用同组常量；借内码、外码表达业务含义时写明含义、取值来源与消费约定。业务扩展字段先向项目参数规范或负责人取得含义、取值集合、必填条件与隐私处理；`setReportParam` 只放标准字段之外的维度。

## 8. 设计之外的完成判断

§4、§7 是实现与审查的判据；此外：

| 对象 | 完成判断 |
|---|---|
| plan 埋点小节 | 每个统计点、每种结果一行，按统计点名对齐 spec；责任方法是契约里的「接口.方法」；写不出值的行写明缺哪一项、影响哪几行 |
| 单元测试 | 每种结果预期的原始事件与次数，含重复回调与重新发起 |
| 真机验证 | 只核需要真机的回调时序与远端结果 |

## 9. 反模式

- **按流程或事件类型分节，只写「观察 X」**：没有可算的指标（§3 第 1 步）。
- **把失败原因、耗时单列成指标**：它们是事件字段（§1）。
- **用「失败号」「xx」代替值**：评审无值可确认（§7 第 1、2 条）。
- **同一结果写两行，或报点写在不发请求的方法上**：重复计数，或根本报不出去（§5、§6）。
