# 埋点上报

把业务结果变成可算的指标，并按项目协议报出去。**当前实现**以 `05-SystemBase/CommFunc/src/main/ets/shared/ha/` 的代码为准；**已定规范**是本仓采用、尚未实现的要求。

# 上篇 · 适用与统计设计（读者：spec）

## 1. 解决什么问题

- **指标**：由采集到的结果算出的比率、分布或耗时，如成功率、失败原因分布、步骤耗时。
- **流程**：有起止的业务过程，由步骤组成，步骤下可有子点；指标与流程不一一对应。
- **事件分类**（如「提交、审核、撤回三类事件」）是采集对象的分组，**业务目标**（如「开通率不低于 30%」）是产品要达到的结果，两者都不是指标。
- 材料只给事件分类或业务目标时，先写出要算哪几个率或分布，再写它们与业务目标的关系。

## 2. 什么时候不该用

- 需求不新增、不改变任何业务流程的结果（纯文案、样式或资源）。
- 要观察的结果已由项目现有采集完整覆盖。
- 材料明确本需求不做运维观察，且无运营诉求。

依据写成「不涉及：<上面哪一种的具体事实>」，「不涉及」三个字本身不是依据。

## 3. 应用步骤

1. **定指标**：一个指标一个标题「指标名（流程名）」，第一段写它衡量什么、要算它需要哪些结果。
2. **沿流程列点**：步骤、子点、步骤整体、流程整体各是一个统计点；不同流程里的同名步骤带流程限定。
3. **写结果与获知时机**：每点只写实际适用的业务结果，写明本端在哪个响应、回调或状态查询里得知；远端产生、本端看不到的写由谁统计或列待决。
4. **定边界**：
   - 一次尝试从发起到终态，重新发起是新尝试；
   - 前一步失败而没进入的步骤不记；
   - 同一业务事实只在产生它的一侧、一条流程下采集一次，别处引用；
   - 远端状态在本端是回显，按首次得知计一次；
   - 页面进入与点击说明不了业务结论，不进统计设计。
5. **选渠道**：VOC 定位过程问题、Chart 做运维统计，是当前实现，同一统计终态二选一，过程关键点用 VOC；BI（独立运营采集）与交互自动记录（页面进入、点击）是已定规范、仓内无实现，写成建设差距；BI 只在需求明确要求时加。
6. **回查**：逐个指标、逐个结果按第 1–4 步核一遍；材料里的事件分类与业务目标都已翻成指标。

示例（示意：假设开通分三步、结果由服务端回调告知、无运营诉求）：

```markdown
#### 服务开通成功率与失败原因（服务开通流程）

衡量发起开通后最终开通的比例，以及没开通时卡在哪一步；要算它，需要各步骤的结果与一次开通的最终结果。

| 统计点 | 业务动作 | 实际适用结果 | 本端获知时机 | 已有或新增 |
|---|---|---|---|---|
| 短信验证 / 校验验证码 | 提交验证码 | 通过 / 未通过 / 请求失败 | 校验响应，或请求发出后通信失败 | 新增 |
| 开通结果 | 服务端告知结果 | 开通成功 / 开通失败 | 开通结果回调或查询，按首次得知 | 新增 |
| 开通全流程 | 一次开通收敛 | 成功 / 失败 / 用户取消 | 结果确定或用户终止时 | 新增 |
```

# 下篇 · 结构与落地（读者：plan、coding、review）

## 4. SDK 行为事实

以下是 CommFunc 上报封装的实际运行时行为，不是使用建议：

- **Chart**：`WalletHAManager.chartBuilder(eventID, funcID, subFuncID)` 链式设字段后 `.report()`；模板 `eventID` 是 hiAppEvent 事件名，Builder 生成 `WalletEventID` = `FuncID_SubFuncID`（如 `Wallet_COMMON_001_002`），平台类型 STATISTIC。
- **VOC**：`vocBuilder(eventID, desc).report()`，记本地日志并上报用 `logAndReport` / `logErrorAndReport` / `logDebugAndReport`。VOC 另用标识：类型 BEHAVIOR，`WalletEventID` 由调用方给，`FuncID` 固定 `VOC`。
- **发送**：经 `CommFunc/src/main/ets/index.ets` 导出；不阻塞业务，失败只记本地日志，不做业务去重。
- **现有定义**：模板枚举 `WalletHAEventID.ets` 只有 `Wallet_COMMON`；仓内没有流程、步骤、内码登记，也没有 Chart 调用。
- **字段**：setter 与类型见 `WalletHAReportBaseCBuilder`；其中业务扩展字段（`setChannel`、`setSource` 等）的含义本仓无依据。

## 5. 角色与文件落点

| 角色 | 职责 | 命名惯例 |
|---|---|---|
| 尝试持有者 | 决定业务结果的业务方法，持有本次尝试标识，重新发起时新建 | 业务流程类的提交或查询方法 |
| 结算方法 | 一次尝试只结算一个结果；正常响应、失败、请求异常与重复回调都调它；写进契约 | `settle<结果>` |
| 登记文件 | 流程、步骤、内码常量 | 特性 shared 层 `<特性>ChartCodes` |

## 6. 结构骨架

接上篇示例（`OpenFlow`、`SmsVerify` 为待建设计的示意名，编号只示范取号形态）：

| 统计点 | 身份 | 结果 → 内码 · 分类 | 外码来源 | 责任方法 | 去重与验证 |
|---|---|---|---|---|---|
| 短信验证 / 校验验证码 | `Wallet_COMMON` / `001` / `002` | 通过 `0101020200` STEP_SUCCESS；未通过 `0101020201` STEP_ERROR_BY_ERROR；请求失败 `0101020202` STEP_ERROR_BY_ERROR | 响应或错误对象里的码 | SmsVerify.settleCheck | 每次提交一次尝试，重复回调不再报；三种结果各一条 |
| 开通全流程 | `Wallet_COMMON` / `001` / `000` | 成功 `0101000000` SUCCESS；失败 `0101000001` STEP_ERROR_BY_ERROR；取消 `0101000010` STEP_ERROR_BY_USER | 失败那一步的外码 | OpenFlow.finish | 一次开通只记一次；正常、失败、取消各一条 |

结算方法先看 `attempt.settled`，已结算即返回；否则置位，`chartBuilder(模板, 流程, 步骤)` 设内码、分类与拿到的外码后 `report()`。核对：每种结果一条事件，重复回调仍一条，重新发起再出一条。

## 7. 使用约定 — 人为纪律，SDK 不强制，review 逐条核查

1. **候选就是具体值**：写出流程号、步骤号与十位内码，标「候选，待登记：<登记文件>」；评审确认的是值。
2. **编号按分配规则**（Demo 拟定；目标仓以自己的登记为准）：
   - 先扫全仓，同语义已有值直接复用；身份不是流水号，同一步骤的新结果扩展内码。
   - 身份「模板 → 流程 → 步骤」，流程、步骤号三位；内码十位「业务模块 → 模块内流程 → 节点 → 子节点 → 结果」，每段两位、前导零保留，两处流程段不互相截取。
   - 新值在父范围升序取未用号，从 `001` / `01` 起；步骤 `000` 与节点 `00` 表示流程整体，子节点 `00` 表示未细分；结果 `00` 成功、`10` 主动取消、失败取其余。
   - 父范围首次使用时由本次设计给出候选与依据；有外部统一分配的用其结果，拿不到列待决。
   - 编码前写入登记文件并重核冲突，有冲突回设计改号。
3. **结算一次**：结果在决定它的业务方法里报；发请求与结算分开，一次尝试记一条；尝试标识与业务幂等键各管各的；已发出的请求按它自己的最终结果记。
4. **分类按语义**：`SUCCESS` 只给流程整体成功，步骤成功 `STEP_SUCCESS`，普通失败（含拒绝授权）`STEP_ERROR_BY_ERROR`，用户主动取消 `STEP_ERROR_BY_USER`；内码定位具体结果，与分类独立。
5. **只带拿到的**：外码只带实际拿到的外部错误码；耗时 `setDuration` 有诉求且起止明确时带。
6. **身份共用**：同一步骤各结果共用身份；同语义的运维与运营点位引用同组常量；BI 传参走项目 BI 接口，不从 Chart 封装推。
7. **BI 选参**：按运营需求选，不默认带运维内码、外码或分类；项目协议允许时可借内码、外码表达相近业务含义，写明运营侧含义、取值来源与消费约定。
8. **扩展字段先取得规范**：用业务扩展字段前，向项目参数规范或负责人取得含义、取值集合、必填条件、来源与隐私处理，只取要用的；`setReportParam` 只放标准字段之外的维度。

## 8. 设计之外的完成判断

§4、§7 是实现与审查的判据；此外：

| 对象 | 完成判断 |
|---|---|
| plan 埋点小节 | spec 的每个统计点、每种结果一行，责任方法是契约里的「接口.方法」；写不出值的行写明缺哪一项、影响哪几行 |
| 单元测试 | 每种结果预期的原始事件与次数，含重复回调与重新发起 |
| 真机验证 | 只核需要真机的回调时序与远端结果 |

## 9. 反模式

- **按流程或事件类型分节，只写「观察 X」**：没有可算的指标。正确写法见 §3 第 1 步。
- **用「失败号」「xx」代替值并称待登记**：评审无值可确认。正确写法见 §7 第 1、2 条。
- **同一方法同一结果写两行，或报点写在不发请求的方法上**：同一结果被重复计数，或报点方法根本没被调用。正确写法见 §5、§6。
