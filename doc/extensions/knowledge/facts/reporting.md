# 上报

需求要观察一段业务的质量、要能定位问题、或明确要求运营采集时读这份。它帮你做两件事：先用业务语言说清要观察什么、会有哪些结果、本端何时知道；再把同一组结果落到本仓的上报实现——用什么身份、带什么值、在哪个方法里报、会看到什么事件。

前两面讲业务：[1. 业务统计语义](#1-业务统计语义--confirmed-已确认) 说统计的对象与关系，[2. 渠道与已有能力](#2-渠道与已有能力--confirmed-已确认) 说本仓现在能报什么、哪些只是规范。后四面讲实现：[3. 身份与 SDK 映射](#3-身份与-sdk-映射--confirmed-已确认)、[4. 结果与字段映射](#4-结果与字段映射--confirmed-已确认)、[5. 业务扩展字段](#5-业务扩展字段--confirmed-未确认)、[6. 登记与复用](#6-登记与复用--confirmed-已确认)。[7. 使用参考](#7-使用参考--confirmed-已确认) 用同一个业务把两层走一遍。

依据标注：**当前实现**以 `05-SystemBase/CommFunc/src/main/ets/shared/ha/` 下的代码为准；**已定规范**是本仓采用、尚未实现的要求；例子里的值是示意。

## 1. 业务统计语义 — `confirmed: 已确认`

先分清为什么报。VOC 用来定位过程中的问题；Chart 用来统计流程质量，是运维指标的来源；BI 只在需求明确要求运营数据时才做。同一个业务事实既服务运维又服务运营时，两边用同一个业务步骤身份，不各起一套。

再分清统计对象之间的关系：

- **指标与流程**不是一一对应。一个指标可以观察一条流程，也可以汇总几条相关流程的同类结果；一条流程也可以支撑几个指标。同一事件事实只采集一次，共用于这些指标。观察范围按需求与统计语义定。
- **流程、步骤、子点**：流程由步骤组成，步骤下可以有子点。同一步骤的不同结果属于同一个统计对象，结果不同不改身份。
- **尝试**：一次尝试从发起到这一点得到终态结果。失败后重新输入是新的一次尝试，父步骤仍可能最终成功。步骤成功与流程整体成功是两件事，各有结果。
- **本端何时知道**：结果在远端产生时，本端只能统计实际观察到的那一刻——某个响应、回调或状态查询，要写明是哪一个；本端观察不到的，写清由谁统计或列为待决。
- **交互记录不是业务结论**：页面进入与点击说明不了校验通过、受理成功这类结论，业务结论由业务调用的结果报出。

## 2. 渠道与已有能力 — `confirmed: 已确认`

写设计前先看本仓现在能报什么，已有的直接复用，只是规范的要写成建设差距。

| 渠道 | 用途 | 依据 | 现状 |
|---|---|---|---|
| VOC | 过程问题定位 | 当前实现 | `WalletHAManager.vocBuilder(eventID, desc)`；带本地日志的 `logAndReport` / `logErrorAndReport` / `logDebugAndReport` |
| Chart | 运维统计 | 当前实现 | `WalletHAManager.chartBuilder(eventID, funcID, subFuncID)` |
| BI | 明确需求的独立运营采集 | 已定规范 | 仓内尚无 BI 封装；需求要 BI 时是建设差距 |
| 交互自动记录 | 页面进入、点击 | 已定规范 | 仓内尚无实现，现在不构成已有覆盖；需求要用这些数据时，数据要求与建设差距都写明 |

同一个统计终态上 VOC 与 Chart 二选一；过程中的关键点用 VOC。两者经 `CommFunc/src/main/ets/index.ets` 导出，发送不阻塞业务，失败只记本地日志；SDK 不做业务去重，同次结算由业务代码负责。

## 3. 身份与 SDK 映射 — `confirmed: 已确认`

一个结果报出去，先要有它属于哪一步的身份。Chart 与 BI 共用业务步骤身份：模板 `eventID`、流程 `funcID`、步骤 `subFuncID`。例如 `BankCard_001_002` 表示银行卡模板下某流程的一步；同一步骤的成功与失败共用这个身份，同语义的运营与运维点位引用同一组常量。

在 Chart 里，模板是 hiAppEvent 的事件名，流程与步骤写进 `FuncID` / `SubFuncID`，Builder 生成的 `WalletEventID` 是 `FuncID_SubFuncID`，与事件名一起定位完整身份；平台类型 STATISTIC。BI 的业务身份相同，传参走项目 BI 接口，不从 Chart 封装推它的格式。

VOC 用自己的标识：类型 BEHAVIOR，`WalletEventID` 是调用方给的事件标识，`FuncID` 固定为 `VOC`。三个日志门面先记对应级别的本地日志再发一条 VOC；只上报不记日志用 `vocBuilder(...).report()`。

## 4. 结果与字段映射 — `confirmed: 已确认`

身份说「哪一步」，下面这些说「这一步这次怎样了」。

- **结果分类**（`setWalletFuncResult`）：`SUCCESS` 全流程成功，`STEP_SUCCESS` 步骤成功，`STEP_ERROR_BY_ERROR` 普通失败，`STEP_ERROR_BY_USER` 用户主动取消；拒绝授权归普通失败。
- **内码**（`setWalletEventInCode(string)`）：十位数字字符串，五段各两位——业务模块、业务流程、节点、子节点、具体结果，前导零保留。它定位具体结果；分类表达结果类别，两者独立。子点靠子节点段区分。
- **外码**（`setWalletEventExtCode(string)`）：只带这次结果实际拿到的外部错误码，没有就不设。
- **耗时**（`setDuration(number)`，毫秒）：有统计诉求、起止明确且实际测到时才带。
- **描述**（`setWalletEventDesc(string)`）：点位的可读描述。
- **自定义维度**（`setReportParam(name, value)`，值为 string / number / boolean）：已有标准字段用它自己的入口。

BI 按运营需求选参数，不默认带运维内码、外码或结果分类；项目约定借内外码表达相近含义时，照对应的运营定义取值。

## 5. 业务扩展字段 — `confirmed: 未确认`

`WalletHAReportBaseCBuilder.ets` 还提供 `setChannel`、`setSource`、`setIssueID`、`setIssueName`、`setOperationType`、`setSrcPassType`、`setOrderNumber`、`setTransactionId`（string）与 `setHappenedTime`（string | number）。名称与类型已按代码核实，业务含义还没有依据。

用到时先核：Channel 与 Source 怎么区分、取什么值；IssueID / IssueName 指哪个主体；OperationType / SrcPassType 的取值集合；OrderNumber 与 TransactionId 的区别；HappenedTime 的格式；以及本需求实际用到的字段必填条件、来源与隐私处理。只核本需求要用的，不要求填满。

## 6. 登记与复用 — `confirmed: 已确认`

新点位要编号时读这一面。现有定义（当前实现）：模板枚举在 `CommFunc/src/main/ets/shared/ha/WalletHAEventID.ets`，只有 `Wallet_COMMON`；仓内还没有业务流程、步骤与内码的登记，也没有 Chart 调用。

身份与内码各有命名空间：身份按「模板 → 流程 → 步骤」分配，流程号、步骤号三位；内码按「业务模块 → 模块内流程 → 节点 → 子节点 → 具体结果」分配，每段两位。两处的流程段长度不同，不互相截取。

分配规范（本仓采用；具体编号仍按规范提出并确认）：

1. 先扫全仓的模板、常量定义与调用，同语义的已有值直接复用；同一模板跨特性使用时先核全部已有定义。
2. 新值在父范围里取未用号，给出具体候选：首次按升序从 `001` / `01` 起，节点与子节点段的 `00` 留给未细分；结果段 `00` 成功、`10` 主动取消，失败取其余未用号。
3. 父范围首次使用（例如业务模块段还没有登记）时，父范围与子项的候选及依据一起提出，经项目设计评审确认；候选不称作已有分配。项目有外部统一分配的用其结果，拿不到时列出待决的那一项，不自行占号。
4. 登记文件放在特性自己的 shared 层，文件名以 `ChartCodes` 结尾，首次使用时新建；候选在设计里标「待登记：<登记文件>」，写入前重核冲突，有冲突回到设计调整，不自动换号。

身份定义不是一次执行的流水号。已有定义按语义复用；同一步骤的新结果扩展内码，不复制身份常量。

## 7. 使用参考 — `confirmed: 已确认`

两段参考用同一个业务：先用业务语言把统计设计出来，再把同一组结果落到本仓的上报实现。例子里的业务类、响应类型和编号都是示意，只说明怎样应用；当前需求按自己的材料重新设计，编号按第 6 面提出并核冲突。

### 7.1 业务设计参考

拿到业务目标、流程材料与已核的采集能力后：

1. **定观察对象与范围**：分清材料里的业务目标（例如「开通率提升到多少」）与为看懂流程质量要观察的指标，说明两者的关系。
2. **沿实际流程找点**：列出步骤与子点，分清步骤成功、流程成功、未执行与失败。
3. **每个点写结果与获知时机**：适用的业务结果、结果由谁产生、本端在哪个响应、回调或查询里知道，一次尝试从哪到哪。
4. **核已有覆盖**：第 2 面里当前实现能表达的不再新增；要补的保留要求；只是规范的写成建设差距。
5. **处理共用与运营需求**：几个指标共用同一事实时引用同一采集；独立运营采集只在需求明确要求时加。

例：观察「服务开通」一次开通尝试的结果，短信验证步骤的结果用来定位开通卡在哪。验证码校验失败后重新输入可以继续，步骤失败不等于整次开通失败。本例假设开通受理后，最终结果由服务端回调告知。

| 业务点 | 业务结果 | 本端获知依据 |
|---|---|---|
| 信息校验 | 通过、条件不满足 | 校验返回 |
| 发送验证码 | 发送成功、发送失败 | 发送响应 |
| 校验验证码 | 校验通过、未通过 | 校验响应 |
| 短信验证步骤 | 验证完成、用户主动终止 | 子点结果与用户操作 |
| 开通结果 | 开通成功、开通失败 | 开通结果回调或查询 |

这些是本例的适用结果，不是通用必报全集。选这几个点，是因为开通率要能拆到「卡在哪一步」；页面进入与点击说明不了校验结果，要由业务调用报出。同一验证事实既服务步骤质量、又服务整段开通分析时只采集一次；同名的验证出现在别的业务流程里，按那条流程的业务身份区分。本例没有运营诉求，不加独立运营采集。

### 7.2 实现设计参考

拿到已定的业务点与结果后：

1. **定位结果在哪确定**：在真实接口或待建接口里找到结果成立的分支、回调或用户动作，那个方法就是责任方法。
2. **定取值**：按第 3–6 面复用已有身份与值；需要新值时给具体候选和登记位置；确实缺分配依据时写清缺哪一项。
3. **每种结果写全字段**：值或取值表达式、来源、缺席条件、扩展维度。
4. **定报告时机与同次边界**：同一次尝试的重复回调只结算一次，重试是新尝试；退出界面不等于取消已发出的请求。
5. **形成责任与验证**：写出代码责任和简短调用骨架，再列每种结果应看到的原始事件。

例：「校验验证码」两种结果完整展开（本例假设全仓尚无其他已分配值）：

| 业务结果 | 身份 | 内码（候选） | 结果分类 | 外码 | 责任方法与时机 |
|---|---|---|---|---|---|
| 校验通过 | `Wallet_COMMON`，流程 `001`，步骤 `002` | `0101020200` | `STEP_SUCCESS` | 不带 | 校验方法收到通过响应时 |
| 未通过 | 同上 | `0101020201` | `STEP_ERROR_BY_ERROR` | 取校验响应的外部错误码，没有则不带 | 校验方法收到未通过响应时 |

内码各段：业务模块 `01`、模块内流程 `01`、节点 `02`（短信验证）、子节点 `02`（校验验证码）、结果 `00` 成功 / `01` 未通过，都是按第 6 面首次候选规则提出的示意值，未占用真实编号。两种结果共用同一身份，差异由结果分类与内码表达。尝试标识属于本次执行上下文，与业务幂等身份分开；有观察诉求时耗时取本次请求发出到返回。其余点同样处理：发送验证码由发送方法按发送响应报；开通结果由处理回调的方法报，本端取得时机是回调到达。

```ts
// 示意：SmsVerifyService、VerifyAttempt 为本例待建设计；chartBuilder 与各 setter 为本仓现有接口
async checkCode(attempt: VerifyAttempt, code: string): Promise<boolean> {
  const resp = await this.smsVerifyService.check(code);
  if (attempt.settled) {
    return resp.passed;                       // 同一尝试的重复回调不再报
  }
  attempt.settled = true;
  const builder = WalletHAManager.chartBuilder(WalletHAEventID.Wallet_COMMON, FLOW_OPEN, STEP_SMS_VERIFY)
    .setWalletEventInCode(resp.passed ? IN_CODE_CHECK_PASS : IN_CODE_CHECK_FAIL)
    .setWalletFuncResult(resp.passed ? WalletFuncResult.STEP_SUCCESS : WalletFuncResult.STEP_ERROR_BY_ERROR);
  if (!resp.passed && resp.extCode) {
    builder.setWalletEventExtCode(resp.extCode);
  }
  builder.report();
  return resp.passed;
}
```

| 情形 | 应看到的事件 |
|---|---|
| 一次校验通过 | 一条 `STEP_SUCCESS`，内码结果段 `00` |
| 一次校验未通过 | 一条 `STEP_ERROR_BY_ERROR`，内码结果段 `01`，有外部错误码时带外码 |
| 同一次校验的重复回调 | 仍只有一条 |
| 重新输入后再校验 | 新尝试，再出一条 |
| 退出验证界面时发送请求已发出 | 发送验证码按自己的响应照常记录，不改记取消 |

用对了的判断：每个业务结果都能连成「结果 → 责任方法与分支 → 身份与字段来源 → 调用 → 预期事件」，不是表格填满或出现了某个文件名。
