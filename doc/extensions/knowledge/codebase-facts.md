# 工程惯例与取证导航

**这个工程的东西怎么找、找到之后照什么惯例写。** 工程级知识，不属于任何单个流程阶段。
取证公式「事实 = 变更意图 × **代码库现状**」的现状那一半，第一落点就是本文件。

> **本文件不列清单。** 同类实例在真实工程里成百上千，列了维护不动，一次重构就全部过期；
> 而「去哪找」这件事很少变。所以这里只讲**定位规则**与**少量不易过期的结论**。

## 总则：先找已有实现，再谈新增

任何一类能力——打日志、上报、脱敏、存数据、读配置、跳页面、写界面——这个仓里大概率已经有做法了。
**先去找它，照它写。**

自己引平台 API 或另起一套，会让同一件事在仓里出现两种写法。之后谁也说不清该照哪个：
新人照见到的那个写，评审照记得的那个查，两边都有理。**同一件事只该有一种写法**，
而决定是哪一种的，是仓里已经存在的那个。

## 怎么找

| 要落什么 | 去哪找 | 判据 |
|---|---|---|
| 跨模块公用的技术能力（日志、上报、脱敏、导航、通用工具） | 公共能力层模块的**公开出口文件** | 出口里导出了什么，就用什么；出口里没有的，才谈新增 |
| 本业务域内的能力 | 同一业务模块内对应层的目录 | 同层已有的同类实现就是模板 |
| 数据怎么存 | 业务模块 data 层的既有仓储封装 | 照它的形态加，不自己起一套持久化 |
| 配置开关怎么写 | 各模块存放常量的目录 | 照既有开关的声明形态写，注意区分开关与普通业务常量 |
| 界面怎么写 | 同类页面/组件的既有实现 | 照它的组织方式与命名 |
| 依赖怎么加 | 模块根的依赖声明文件 | 新依赖边的合法性由架构 DSL 的层依赖规则判定 |

**这张表只给「去哪找」，不给「找到的是什么」**——后者随重构变化，看当时的代码为准。

## 找到之后

- **照调用形态用**，不绕过封装直接引平台 API——绕过去就等于在仓里加了第二种写法；
- **照命名与目录惯例**放新文件：同类的东西放在同类的地方，名字用同样的构成方式；
- 既有实现与本需求确实不匹配时，**先说明哪里不匹配再新增**。不说明就新增，
  事后没人分得清这是「有意的第二种做法」还是「没找到就自己写了」。

## 找不到的时候

**「没有」必须是核对过的结论，不是没查到。** 写明查了什么、在哪查的、零命中。

本文件的前身就栽在这上面：凭平台常识写了本仓根本不用的埋点 API，
又漏了实际存在的上报封装——两个错都是「没实扫就下结论」。

## 已核实的结论性事实

只登记「有 / 没有」这类**不易过期**的判断，不登记它长什么样。每条带核实方式，换工程时照此重扫。

| 面 | 结论 | 核实方式 |
|---|---|---|
| 端云接口 | **无端云封装** | 检索平台网络 API 与常见 HTTP 客户端，零命中；数据来自本地仓储层 |
| 可观测性 | **三条渠道齐备**（日志 / 用户问题反馈 / 业务度量），且**上报非阻塞、失败不外传**（只记一条本地日志，不抛、不改返回值） | 读公共能力模块的公开出口看导出了哪些日志与上报类；进实现看失败处置 |
| 业务终态 | **有一个受控枚举**，设计终态集合时从它取，不自造字符串 | 同上，在上报相关实现附近 |
| 远程配置 | **无远程配置封装**（无管理台/云侧下发开关） | 检索配置下发类 API 与相关封装，零命中 |
| 编排 SDK | **随仓存在且被声明依赖，但未找到业务使用先例** | 读模块依赖声明与仓内库目录；再检索业务模块里的使用点 |

**编排 SDK 这条是证据缺口，不是能力背书**：只证实了 SDK 在、被依赖；
设计模式知识里的结构骨架在本工程属「可用但少先例」。具体需求是否采用该模式，
由 plan 结合适用单元与这条证据自行判断——**不得因为模式文档存在就假定工程已具备成熟用法**。

## 换工程复用

本文件的定位规则（「怎么找」「找到之后」「找不到的时候」）**跨工程通用，直接带走**。
「已核实的结论性事实」那张表须由模型实扫目标仓重写，再由人确认——它是唯一与具体工程绑定的部分。
