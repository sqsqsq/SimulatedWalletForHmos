# {{SR}} 交通卡挂失与补卡协同 — 系统设计（SE）

> 关联：AR {{AR}} / PRD {{RR}}。本设计覆盖钱包 app、账号能力、交通卡云、支付部件、通知能力和客户服务。

## 1. 全局方案

在线挂失与补卡分为身份校验、申请创建、冻结状态同步、费用支付、制卡状态跟踪五个阶段。钱包 app 是用户入口和
状态展示方；账号能力只负责既有登录、实名和回跳；交通卡云是卡片状态、费用和申请状态的唯一真源；支付部件
只处理补卡费；通知能力根据卡云事件发送状态变化；客户服务只通过工单号处理异常。

“先在端侧标记已挂失、再异步提交”的方案不采用：端侧状态不能保证原卡冻结，且会让用户把未受理误解为已
冻结。必须以卡云受理结果区分“提交中、已冻结、冻结失败”。

## 2. 责任矩阵

| 参与方 | 输入 | 输出 | 责任 | 失败后的边界 |
|---|---|---|---|---|
| 钱包 app | 用户操作、当前卡片、云侧状态 | 申请请求、支付拉起、进度页与提示 | 收集确认、引导身份校验、展示状态 | 不自行宣称原卡已冻结；保留可恢复的支付意图 |
| 账号能力 | 登录/实名请求、回跳上下文 | 合格身份或失败结果 | 提供既有认证与实名状态 | 未完成校验时不调用挂失接口 |
| 交通卡云 | 卡号、实名账号、申请确认 | 申请号、费用、冻结结果、制卡进度 | 校验资格、冻结原卡、创建补卡工单 | 是卡状态和费用的唯一真源 |
| 支付部件 | 申请号、费用、支付参数 | 支付结果 | 收取补卡费用 | 不改变挂失或制卡状态 |
| 通知能力 | 卡云的状态事件、去标识账号 | 推送消息 | 发送状态变化提醒 | 推送失败不改变云侧申请状态 |
| 客户服务 | 工单号、用户咨询 | 人工处理结论 | 处理审核或制卡异常 | 不直接读取钱包端缓存 |

## 3. 端到端时序

```text
用户 → 钱包 app：选择“挂失与补卡”
钱包 app → 账号能力：检查登录与实名状态
账号能力 → 钱包 app：已验证 / 引导完成后的回跳
钱包 app → 交通卡云：getLossReportEligibility(cardNo)
交通卡云 → 钱包 app：可申请、费用、当前卡状态 / 不可申请原因
用户 → 钱包 app：确认冻结说明和补卡申请
钱包 app → 交通卡云：createLossReport(cardNo, verifiedAccount, channel=wallet)
交通卡云 → 钱包 app：applicationNo、freezeStatus、fee、expiresAt
钱包 app → 支付部件：需要支付时拉起收银台(applicationNo, fee)
支付部件 → 钱包 app：支付结果
钱包 app → 交通卡云：confirmReplacementPayment(applicationNo, paymentRef)
交通卡云 → 通知能力：状态变化事件
交通卡云 → 钱包 app：getReplacementProgress(applicationNo)
通知能力 → 用户：可读状态提醒
```

卡云在支付前可返回“已冻结待支付”；支付成功后进入制卡队列。支付失败、取消或超期不自动重新扣费；
用户从进度页按云侧状态继续操作。卡云最终确认冻结失败时，钱包 app 显示失败状态和客户服务入口。

## 4. 接口约定

### 4.1 `getLossReportEligibility`（新增）

| 字段 | 约定 |
|---|---|
| 请求 | `cardNo`、当前已验证账号标识 |
| 响应 | `eligible`、`reasonCode`、`cardStatus`、`replacementFee`（分）、`policyText` |
| 用途 | 打开申请页前说明可否发起、冻结效果和费用；不可申请时不创建订单。 |
| 错误 | `CARD_NOT_ELIGIBLE`、`IDENTITY_NOT_VERIFIED`、`CARD_STATUS_CONFLICT`。 |

### 4.2 `createLossReport`（新增）

| 字段 | 约定 |
|---|---|
| 请求 | `cardNo`、已验证账号标识、`channel=wallet`、用户确认标记 |
| 响应 | `applicationNo`、`freezeStatus`、`replacementFee`、`expiresAt`、`paymentParams`（需要支付时） |
| 幂等 | 同一张卡存在未完成申请时返回既有 `applicationNo`，端侧不得重复创建。 |
| 错误 | `LOSS_REPORT_REJECTED`、`CARD_ALREADY_FROZEN`、`APPLICATION_IN_PROGRESS`。 |

### 4.3 `confirmReplacementPayment` 与 `getReplacementProgress`

| 接口 | 责任 |
|---|---|
| `confirmReplacementPayment(applicationNo, paymentRef)` | 支付回调后让卡云确认费用状态，返回制卡状态。 |
| `getReplacementProgress(applicationNo)` | 进度页与回到前台时查询，返回冻结、支付、制卡、领取和失败说明。 |

## 5. 数据、状态与恢复

| 数据 | 存储与范围 | 处置 |
|---|---|---|
| `wallet_loss_report_context` | Preferences：`applicationNo`、脱敏卡号尾号、`accountScope`、`createdAt`、`expiresAt` | 与账号隔离；支付完成、申请终止或 24 小时超期后删除；不随备份恢复。 |
| 登录回跳意图 | 内存/短期安全上下文：目标卡片标识和申请页状态 | 登录或实名失败时删除；不能跨账号恢复。 |
| 进度展示 | 以卡云 `getReplacementProgress` 为真源 | 端侧不缓存“已冻结”作为最终事实。 |
| 日志与埋点 | 只记录状态类型、入口和匿名工单阶段 | 脱敏卡号，不记录实名信息、完整申请号、支付参数或证件信息。 |

状态机：`可申请 → 已提交待冻结 → 已冻结待支付 → 制卡中 → 可领取`；任一阶段可以进入`失败`。只有卡云返回
`已冻结待支付`或后续状态时，钱包 app 才能向用户展示原卡已被冻结。

## 6. 配置、质量与安全

| 项目 | 约定 |
|---|---|
| 开关 | `traffic_card_loss_report_enabled` 默认 `false`；关闭或读取失败时隐藏在线入口，旧卡片浏览保持不变。 |
| 兼容 | 旧版本不读取新开关和新缓存；已有线下挂失状态通过卡云状态展示，不迁移端侧数据。 |
| 触发频次 | 资格查询仅在用户打开申请页或回到前台查看进度时触发，无轮询任务。 |
| 可用性 | 卡云不可用时不能创建申请，明确告诉用户稍后重试或联系客服；不假装冻结成功。 |
| 隐私 | 新增页面文案和状态使用资源；不新采集证件数据；账号和卡号显示需脱敏。 |
| 通知 | 推送只含状态摘要和打开进度页的动作，不含完整卡号、费用或实名信息。 |

## 7. 异常与交付协同

| 场景 | 用户可见结果 | 钱包 app 行为 | 责任方 |
|---|---|---|---|
| 未登录/未实名 | 引导完成身份校验 | 保留原卡上下文，完成后回跳 | 账号能力 |
| 卡片不可申请 | 展示可读原因 | 不创建申请或支付单 | 交通卡云 |
| 冻结受理失败 | 明确不是已冻结 | 展示重试/客服入口，不保存成功状态 | 交通卡云 + 客服 |
| 支付取消/失败 | 显示待支付或失败状态 | 从进度页继续，不重复创建申请 | 支付部件 + 交通卡云 |
| 状态查询失败 | 展示上次可读状态和刷新入口 | 不将缓存当最终状态 | 钱包 app |
| 通知投递失败 | 不影响进度页 | 用户仍可主动查看进度 | 通知能力 |

运营负责开关、申请漏斗和失败类型报表；卡云负责状态事件和工单规则；支付部件负责费用支付联调；
钱包 app 负责完整旅程验收及客户服务入口的工单号交接。
