# {{AR}} 交通卡挂失与补卡协同 — 产品需求（PRD）

> 需求单号：{{RR}}（关联 AR：{{AR}} / SR：{{SR}}）

## 1. 业务背景

用户遗失实体交通卡后，当前只能到线下渠道申请处理。在线卡包能看到卡片，却不能立即冻结风险、保留可转移余额或
让用户了解补卡进度。本需求在钱包 app 提供“挂失并申请补卡”入口，把身份校验、云侧冻结、补卡费用支付、
制卡和通知串成一条可追踪的用户旅程。

目标不是替代线下人工审核，而是让已绑定交通卡的用户在发现遗失后尽快阻止继续使用原卡，并获得明确的补卡状态。

## 2. 用户、目标与边界

| 用户 | 目标 | 本需求提供 | 不提供 |
|---|---|---|---|
| 已登录实名交通卡用户 | 尽快冻结遗失卡并补卡 | 在线发起申请、支付补卡费、查看进度 | 绕过实名校验、直接退款 |
| 未实名或游客 | 了解为何不能发起 | 引导完成既有登录与实名流程 | 新建实名或登录能力 |
| 客服人员 | 处理审核异常 | 接收工单编号与状态 | 在钱包 app 内处理工单 |
| 卡服务运营人员 | 观察补卡转化和失败 | 接收匿名化业务事件 | 查看用户完整卡号或身份信息 |

明确不做：卡片余额实时迁移、线下领卡流程改造、原卡恢复、人工审核规则修改、补卡价格制定和退款规则修改。

## 3. 用户旅程

1. 用户在钱包首页或交通卡详情选择“挂失与补卡”；
2. 应用检查登录与实名状态。游客先登录，未实名用户进入既有实名引导；
3. 用户阅读原卡冻结效果、补卡费用和预计进度，确认申请；
4. 云侧校验卡片状态并创建挂失申请，原卡进入冻结中或已冻结状态；
5. 需要支付补卡费时，应用拉起既有收银台；免费或已支付的申请直接进入制卡队列；
6. 云侧通过通知能力推送状态变化；用户在卡包查看“审核中、待支付、制卡中、可领取、失败”等状态；
7. 用户可查看失败原因并按提示联系客户服务或重新提交，不自动重复扣费。

## 4. 产品规则

| 规则 | 结论 |
|---|---|
| 适用卡片 | 仅已绑定、状态为正常或疑似遗失的实体交通卡可发起。 |
| 身份前置 | 挂失申请必须在登录并完成既有实名校验后才能提交。 |
| 冻结效果 | 申请受理后原卡不应继续用于新的交通支付；最终冻结结果以卡云返回为准。 |
| 费用 | 补卡费用由卡云随申请创建结果返回；用户确认支付前不得扣费。 |
| 支付中断 | 保留未过期的申请和支付意图，用户可在进度页继续支付；超期后由云侧决定是否重新申请。 |
| 状态可见 | 进度页必须区分“已提交但未冻结”“已冻结待支付”“制卡中”“可领取”“失败”。 |
| 隐私 | 页面不展示完整卡号或实名证件信息；客服入口只带工单号。 |

## 5. 验收意图

| 编号 | 场景 | 预期 |
|---|---|---|
| AC-L1 | 已登录实名用户提交申请 | 能看到冻结说明、费用和进度；成功创建申请。 |
| AC-L2 | 游客发起 | 完成登录后回到同一张卡的申请页。 |
| AC-L3 | 未实名用户发起 | 进入既有实名引导，不创建挂失申请。 |
| AC-L4 | 卡云拒绝申请 | 清楚展示不可申请原因，不扣费。 |
| AC-L5 | 支付中断 | 能在订单有效期内从进度页继续支付，不重复创建申请。 |
| AC-L6 | 云侧状态变化 | 进度页和通知都能看到最新可读状态。 |
| AC-L7 | 开关关闭 | 不展示在线挂失入口，既有卡片浏览不受影响。 |

## 6. 协同成功口径

| 维度 | 成功口径 |
|---|---|
| 风险控制 | 用户提交申请后，原卡冻结状态可在进度页追踪，失败状态不被伪装为已冻结。 |
| 用户理解 | 每个状态都说明下一步；用户无需到其他文档理解支付、制卡或领取关系。 |
| 数据保护 | 全程不在页面、日志或埋点暴露完整卡号、证件或支付参数。 |
| 协同 | 钱包 app、账号能力、卡云、支付部件和通知能力的责任与失败边界清晰。 |
