# spec 宿主扩展章节取证规则（evidence-rules）

spec §9 技术契约与 story 影响面回显两表生成的**唯一合法方法**：每条结论都由「信息源 → 提取步骤 → 输出规则」产出，取证失败按降级规则处理。**禁止**在任何信息源都取不到时编造结论。

## 0. 核心公式

> **事实 = 变更意图 × 代码库现状**

变更意图从 AR/SR/RR 与 spec 前八章来；**代码库现状从
[`knowledge/codebase-facts.md`](../../../knowledge/codebase-facts.md) 来**——那里登记着这个工程
各能力面「有没有、长什么样、怎么认出来」，未覆盖或存疑的按 §2 三步实扫并回灌。
两者交叉才能得出「新增/修改/废弃/复用/不涉及」。只有意图、没有现状比对的条目一律视为**未取证**。

**现状不能用平台常识顶替**：某个 API 在别的工程常见，不等于本工程在用；facts 里写着
「未使用」的介质，不要选进新设计。

**独立审计原则（人可读红线）**：spec.md 是一份**可独立审计的文件**——读者拿它单看就能读懂并判断，不需要同时翻开 SR / RR / AR。由此有两条推论：

1. **结论自闭环**：事实（接口名、开关默认值、存储键、事件名、模块名）必须写在 spec 本文；禁止「见 SR §x」式转指让读者跳出本文；RR/SR 中与本 AR 弱相关的内容不必赘述。
2. **不写文档坐标**：结论后面**不挂 `spec §x` / `SR §x` / `RR §x` / `AR §x` 这类章节坐标**，小节之间也不用 `见 A5` 互指——改用事物的名字（`见管理台功能开关 feature_entry_enabled`）。理由：坐标换个文档就失效，名字到哪都成立；且坐标由 AI 自己写、无法自证真假。核对由 verifier 按名称回查源文件与开发的证据抽查关卡完成。

> 参照物：`spec.md` 的功能清单/场景/页面/流程/异常各章**零引用**，同样是 AI 从 RR/SR 生成，靠术语映射人工确认、Scope 校验、verifier 与用户确认关卡防幻觉。陈述事实不需要逐句挂出处。

**形式一律表格**：spec 原有各章不管几条都用表格（F1–F6 是表格，只有一条也会是表格），本规则约束的各节同此——每节要么一张表（表头固定、每行一个编号实体），要么一行「不涉及 + 依据」。不按条目数在散文与表格之间切换，那会让同一份文档出现四种形态混排。

## 2. 各节取证规则

每节按四要素执行：**变更意图源 → 现状源 → 输出规则 → 降级**。

**现状怎么取（三步，各节通用）**：

1. **读 [knowledge/codebase-facts.md](../../../knowledge/codebase-facts.md) 对应面**——
   标着 `已确认` 的事实直接用；
2. **未覆盖或存疑**：用 `module-catalog` 缩定位范围，然后**在范围内做代码检索**。
   catalog 只是线索——它只登记关键导出，**「catalog 里没有」不构成「工程里没有」的证据**，
   「无」只能由检索零命中得出；
3. **回灌**：本步查到的事实（含「确无」这个结论）写回 `codebase-facts.md` 对应面，
   并把该面置 `未确认` 交人核对。下一个需求就不必重查。

结论里注明依据来自哪一步（facts 已确认 / 本次实扫），让「查过确实没有」与「没查」在产物上可分。

> **对外暴露面的取证**（不单独成节）：按 facts「对外暴露面」判断有无对外可达入口
> ——平台应用清单里 ability/activity 的对外可达性、路由注册表、catalog `key_exports`。
> 有则进 §9 技术契约表并在 §7.3 安全性要求写调用方校验结论；无对外面时只在 story 应用域约束表的
> 「安全隐私」行写「不涉及 + 现状扫描依据」。调用方从 `SR/design.md` 跨部件交互章节推定。

### 9.1 端云接口

- **意图**：spec 业务流程图中的云侧节点；AR §4/§5（端云接口线索——上游已列清单，按索引直读 SR）；SR 端云声明
- **现状**：网络层封装（按 §2 三步取）
- **输出**：逐接口一行「新增/复用/变更 + 入参出参 + 错误码 + 代码现状」。**请求量四问**（①触发时机是用户点击/定时任务/开机启动？②是否并发？③有无缓存降频？④定时任务是否离散？）是**分析过程，不写进 §9**——只把结论写成 §7.1 性能要求的一行（对照 dfx-baseline 中的高频场景功耗条目）。上线顺序归 review，不在此写。
- **降级**：检索零命中 → 「现状无端云封装（检索零命中），本需求云侧交互为新增域」，或写「不涉及」；SR 缺失 → 接口定义细节标「以云侧接口文档为准（缺 SR 输入）」

### 9.2 数据存储

- **意图**：spec 中的数据持久化需求；AR §4/§5（系统级存储线索，按索引直读 SR）
- **现状**：持久化封装与存储键（按 §2 三步取）
- **输出**：逐存储项一行「键名 + 介质 + 值结构 + 有效期 + 用途 + 代码现状」。**schema 三问**（①DB 版本号是否升级？②旧数据迁移方案？③备份恢复影响？）是**分析过程，不写进 §9**——只把结论写成 §7.2 兼容性要求的一行（对照 app-lifecycle-config 中的数据迁移条目）。加密要求归 §7.3，不在此写。
- **降级**：检索零命中 → 「现状无持久化封装（检索零命中），本需求若引入持久化属新增域，须全新设计声明」

### 9.3 配置项

- **意图**：spec 功能清单/Scope 声明中涉及的开关与配置；AR §5（配置项线索，按 §4 索引直读 SR）
- **现状**：常量开关与远程配置封装（按 §2 三步取）
- **输出**：逐配置项一行「配置名 + 默认值 + 关闭态行为 + 历史版本兼容 + 代码现状」（入口管控对照 app-lifecycle-config 中的功能开关条目）。**必要性论证**（为什么要这个开关而不是硬编码）是决策，归 review 的上线决策，不在此写。
- **降级**：无配置变更 → 「不涉及 + 现状常量清单扫描证据」

### 9.4 埋点

- **意图**：spec 埋点内容；AR §5（打点线索，按 §4 索引直读 SR）
- **现状**：打点封装（按 §2 三步取；**与日志封装区分**——日志不是埋点）；叠加打点规范规约的命名规范与关键节点覆盖要求（TEL-05：核心流程开始/成功/失败节点）
- **输出**：逐事件一行「事件名 + 触发节点 + 归属 + 报表影响 + 代码现状」。通知谁属行动项，归 review 的跨团队协同，不在此写。
- **降级**：检索零命中 → 「现状无埋点封装（仅日志），本需求埋点为新增域」，并仍按 TEL-05 从 spec 流程图列应埋节点

### 9.5 依赖变更（SDK/组件/TA）

- **意图**：spec Scope 模块清单；AR §5（依赖/TA 线索，按 §4 索引直读 SR）
- **现状**：模块依赖声明（按 §2 三步取）；新依赖边的合法性另查 architecture `can_depend_on`
- **输出**：逐依赖一行「依赖 + 变更 + 体积影响 + 兼容风险 + 代码现状」（体积对照 dfx-baseline 中的 ROM 体积条目，兼容对照 compatibility-checklist 中的版本配套条目）；跨层依赖违规直接标红线
- **降级**：无新增依赖 → 「不涉及：Scope 内模块的依赖声明无需变更」

### 合规判定（产物落 story，不落 spec）

判定在 spec 阶段做——那时 SR / PRD / 约束规约都在手上，取证成本最低。但**产物不进 spec**：两张回显表零条代码要求，纯粹是给评审者的完备性证明，与「spec 只装与最终代码有关的内容」相悖。

判定只有三个出口：**产生的代码要求 → spec §7**（UX 适配要求 / 触发频次 / 存储兼容 / 个人数据采集）；**需要人工选择的事项 → 《决策与评审记录》的自然语言问题**；**命中与不涉及的结论 → story 影响面与合规章**。推演过程是工作底稿，三份文档都不写。

**兼容性自检**

- **意图**：§9 技术契约与页面变更的全部结论（推导节，不引入新信息源）
- **现状**：兼容性检查表 **逐条过表**（表里每条都面向本部件，无豁免行）
- **输出**：逐行「条目编号 + 是否命中 + 命中原因或不涉及依据 + 指向」。命中判定必须指回**具体变更的名字**（如「新增下单接口 `createBusinessOrder` 的入参出参字段」），不写小节坐标；一条含多问的，命中时逐问给结论。**本表不产生新要求**——若自检发现需要新增要求，那条要求写进 spec §7 或 §9，本表只做指向。
- **降级**：无（总能产出——全不命中也是结论）

**应用域约束符合性**

- **意图**：spec 全文
- **现状**：`knowledge/constraints/` 除兼容性检查表（由兼容性自检承载）、打点规范规约（由 §9.4 埋点 + 本表「资料交付」行承载）外的 7 个文件逐个过（README.md 有清单与 applies_when）
- **输出**：概览表每行「是/否 + 一句话结论 + 规约编号（逐个列出不用 `~` 范围记法）」；表下按「是」的域给详情，逐条写「中文规约名 + 编号（含义）→ 判定与处置」；小结的数字须与表格一致。**判出「待某方确认」的事项必须逐条登记进 review 的待定项**——那是评审议程的唯一来源。
- **降级**：无

## 3. 结论写法

取证是**生成过程**（§2 各节的四要素），不是**产物形态**。取证的结果是一条具体、可回查的结论——不是一条结论加一个出处坐标。

### 3.1 结论必须具体到可回查

每条结论都要写全它谈论的那个东西的**名字**：接口名、存储键、事件名、配置项名、模块名、错误码、页面路由名。反例与正例：

| 反例（空话，无从核对） | 正例（具体，可按名回查） |
|---|---|
| 新增了一个管理台开关 | `feature_entry_enabled`（管理台功能开关，新增）：默认 `false`；关闭态隐藏新增入口及其相关提示 |
| 新增了下单接口 | 云侧接口 `createBusinessOrder`（新增）：入参 `bizNo`/`amount`(分)/`source`（入口来源），出参 `orderNo`/`payParams`，新增错误码 `ORDER_REJECTED` |
| 端侧新增了缓存 | 存储键 `last_business_context`（Preferences，新增）：值结构 `{ orderNo, bizNo, createdAt }`，有效期 30 分钟 |

名字写全了，verifier 与开发的证据抽查关卡就能按名搜遍 spec / SR / RR / 代码去核对——**这比 AI 自己写的坐标可靠**。

不涉及的小节写「不涉及 + 一句判断依据」，同样要具体（依据是什么现状、扫了什么）。

### 3.2 三类必须写进结论的信息（它们是内容，不是脚注）

**同一条证据在 spec 与 story 里形态不同**——spec 是仓内工作件、story 是归档评审件，两者的读者
和可用引用方式都不一样。所以形态分两列，**三行都必须填**：缺哪一格，写的人就会拿另一个产物的
写法照搬过来。

| 类别 | spec 形态 | story 形态 | 说明 |
|---|---|---|---|
| **代码库现状** | 仓内文件路径 `<模块目录>/.../<工程配置文件>`，或检索结论 `检索 <该类封装> 于 in_scope 模块零命中` | **剥除**——归档件不出现仓内路径 | 核心公式「变更意图 × **代码库现状**」的另一半，本身就是结论的组成部分。**写之前自己确认路径存在**——没有门禁替你查，写错了就是一条查无此物的证据。spec 不归档，路径在仓内有效；story 里这一列由 `--init` 直接剥掉（归档件里裸路径评审者打不开，`--check` 的归档件红线会拦） |
| **约束规约** | 编号：`XXX-01` | 中文域名 + 编号 + 含义括注：`<中文规约名> XXX-01（<该条要求什么>）` | 指向随仓归档的规约，评审者可查。**story 应用域约束表每行必须含本类**。概览表的 rule id 列只写编号（`XXX-01`），含义括注在紧随其后的详情小节给，避免撑爆单元格 |
| **数值来源类型** | 三选一标注在正文：`≤ 1500 ms（本工程设定，无上游依据）` / `30 分钟（上游约束：SE 设计文档）` / `（平台基线）` | **按来源分流**：上游约束 / 平台基线 → 正文直接写数值 + 出处；**本工程设定 → 正文不标注来源，登记 `decisions.json` 后写 `{{DEC-00X}}` 引用** | 凡阈值、时长、次数一类数字，都要能让评审者分辨哪些是硬约束、哪些是可议的默认值。spec 里靠括注即可（spec 没有决策登记机制）；story 有决策件，可议的值就该进那里让人表态——括注只是告知，决策条目才能被投票。标「上游约束」时会被门禁**读上游原文验证该数值真实存在**；story 侧还会被**数值溯源守恒**兜底：上游无、决策也无的数值一律拦下（比对的是值，与你怎么描述无关） |

### 3.3 不写的东西

- **文档坐标**：`spec §3 功能清单`、`SR §4.2 云侧接口定义`、`RR §2`、`AR §4 上游索引`——一律不写（理由见 §0 独立审计原则）。
- **小节互指坐标**：`见 A5`、`指回 A2`——改用事物的名字（`见管理台功能开关 feature_entry_enabled`、`源于新增的下单接口 createBusinessOrder`）。兼容性自检的命中项指回具体变更时同理。

## 4. 上线决策的取证边界

review 的上线决策 B1–B4 是**人的决策**，本规则只约束 AI 的「建议预填」：仅当 spec 事实明确不适用时可预填「建议：不涉及（理由）」；理由同样用名称式，不用小节坐标——写「仅需通知运营（新增了三个打点事件，无对外面与端云接口变更）」，不写「（打点节有新增，接口节无变更）」这类指节不指物的写法。
