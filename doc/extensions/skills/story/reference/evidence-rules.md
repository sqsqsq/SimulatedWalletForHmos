# spec 宿主扩展章节取证规则（evidence-rules）

spec 技术契约章与知识判定结论生成的**唯一合法方法**：每条结论都由「信息源 → 提取步骤 → 输出规则」
产出，取证失败按降级规则处理。**禁止**在任何信息源都取不到时编造结论。

## 0. 核心公式

> **事实 = 变更意图 × 代码库现状**

变更意图从 AR/SR/RR 与 spec 前几章来；**代码库现状按本阶段注入的项目知识去仓里取**——
项目知识给的是「怎么找、找到之后照什么惯例写」的定位规则，不是一份清单。
两者交叉才能得出「新增/修改/废弃/复用/不涉及」。只有意图、没有现状比对的条目一律视为**未取证**。

**现状不能用平台常识顶替**：某个 API 在别的工程常见，不等于本工程在用；
项目知识里已核实为「没有」的能力，不要选进新设计。

**独立审计原则（人可读红线）**：spec.md 是一份**可独立审计的文件**——读者拿它单看就能读懂并判断，
不需要同时翻开 SR / RR / AR。由此有两条推论：

1. **结论自闭环**：事实（接口名、开关默认值、存储键、事件名、模块名）必须写在 spec 本文；
   禁止「见 SR §x」式转指让读者跳出本文；RR/SR 中与本 AR 弱相关的内容不必赘述。
2. **不写文档坐标**：结论后面**不挂 `spec §x` / `SR §x` / `RR §x` / `AR §x` 这类章节坐标**，
   小节之间也不用 `见 A5` 互指——改用事物的名字（`见管理台功能开关 feature_entry_enabled`）。
   理由：坐标换个文档就失效，名字到哪都成立；且坐标由 AI 自己写、无法自证真假。
   核对由 verifier 按名称回查源文件与开发的证据抽查关卡完成。

> 参照物：`spec.md` 的功能清单/场景/页面/流程/异常各章**零引用**，同样是 AI 从 RR/SR 生成，
> 靠术语映射人工确认、Scope 校验、verifier 与用户确认关卡防幻觉。陈述事实不需要逐句挂出处。

**形式一律表格**：spec 原有各章不管几条都用表格，本规则约束的各节同此——
每节要么一张表（表头固定、每行一个编号实体），要么一行「不涉及 + 依据」。
不按条目数在散文与表格之间切换，那会让同一份文档出现几种形态混排。

## 1. 信息源总表

### 外部需求输入（变更意图）

| 源 | 用途 | 缺失时 |
|---|---|---|
| `spec/spec.md`（定稿） | 变更意图 SSOT：Scope/功能清单/流程图/界面描述/配置 | 不可缺（本规则约束的正是 spec 自身的技术契约章与由它派生的判定） |
| `AR/design.md` | 上游已声明的对外依赖/配置线索；链接表与上游索引是 SR/RR 定位索引 | 标注「非 story 流程，仅 spec 单源取证」 |
| `SR/design.md` | 跨部件交互（调用方推定）、云侧接口定义、系统级存储方案 | 调用方 / 端云详情置信度降级并标注 |
| `RR/prd.md` | 业务场景佐证、验收意图 | 标注缺失 |

### 项目知识与工程配置（代码库现状）

| 源 | 用途 |
|---|---|
| **本阶段注入的项目知识** | **现状的第一落点**：给出「这类能力去哪找、找到之后照什么惯例写」的定位规则，以及少量已核实的「有/没有」结论 |
| `doc/module-catalog.yaml` | **定位线索**：`key_exports` / `responsibilities` 指向该去哪个模块找；`NOT_responsible_for` → 负向证据；`layer/format` → 依赖合法性。**`key_exports` 非全量、`responsibilities` 深度不由 schema 保证——catalog 里没有不等于工程里没有，缺席不作否定证据** |
| `doc/architecture.md` + `framework.config.json` architecture 段 | 层间依赖规则（`can_depend_on`） |
| `doc/glossary.yaml` | 术语 → 权威模块定位 |
| **本阶段注入的激活规约条目** | 逐条目判定的基准。条目清单由激活清单派生，**不在本文列举域或编号**——列了就是第二份清单，规约一改这里就过期 |
| 代码检索 | 上述都定不下来时的兜底；范围 = spec Scope 声明的 in_scope_modules 目录 + 全仓工程配置 |

## 2. 各节取证规则

每节按四要素执行：**变更意图源 → 现状源 → 输出规则 → 降级**。

**现状怎么取（三步，各节通用）**：

1. **按项目知识的定位规则去仓里找**该类能力的既有实现——找到就照它写；
2. **找不到或存疑**：用 `module-catalog` 缩定位范围，然后**在范围内做代码检索**。
   catalog 只是线索——它只登记关键导出，**「catalog 里没有」不构成「工程里没有」的证据**，
   「无」只能由检索零命中得出；
3. **回灌**：查到的结论如果属于「有/没有」这类不易过期的判断，写回项目知识的结论表并置未确认交人核对；
   实现细节不回灌——那是清单，会过期。

结论里注明依据来自哪一步（项目知识已确认 / 本次实扫），让「查过确实没有」与「没查」在产物上可分。

> **对外暴露面的取证**（不单独成节）：按项目知识判断有无对外可达入口——
> 平台应用清单里 ability 的对外可达性、路由注册表、catalog `key_exports`。
> 有则进技术契约表并在安全性要求写调用方校验结论；无对外面时在知识判定登记表的对应条目写
> 「不命中 + 现状扫描依据」。调用方从 `SR/design.md` 跨部件交互章节推定。

### 端云接口

- **意图**：spec 业务流程图中的云侧节点；AR 的端云接口线索（上游已列清单，按索引直读 SR）；SR 端云声明
- **现状**：网络层封装（按上面三步取）
- **输出**：逐接口一行「新增/复用/变更 + 入参出参 + 错误码 + 代码现状」。
  **请求量四问**（①触发时机是用户点击/定时任务/开机启动？②是否并发？③有无缓存降频？④定时任务是否离散？）
  是**分析过程，不写进技术契约章**——只把结论写成非功能要求的一行，
  并对照本阶段激活条目里管调用频次的那一条。上线顺序归 review，不在此写。
- **降级**：检索零命中 → 「现状无端云封装（检索零命中），本需求云侧交互为新增域」，或写「不涉及」；
  SR 缺失 → 接口定义细节标「以云侧接口文档为准（缺 SR 输入）」

### 数据存储

- **意图**：spec 中的数据持久化需求；AR 的系统级存储线索（按索引直读 SR）
- **现状**：持久化封装与存储键（按三步取）
- **输出**：逐存储项一行「键名 + 介质 + 值结构 + 有效期 + 用途 + 代码现状」。
  **schema 三问**（①版本号是否升级？②旧数据迁移方案？③备份恢复影响？）是**分析过程，不写进技术契约章**——
  只把结论写成兼容性要求的一行，并对照本阶段激活条目里管数据结构变更的那一条。加密要求归安全性要求。
- **降级**：检索零命中 → 「现状无持久化封装（检索零命中），本需求若引入持久化属新增域，须全新设计声明」

### 配置项

- **意图**：spec 功能清单/Scope 声明中涉及的开关与配置；AR 的配置项线索（按索引直读 SR）
- **现状**：常量开关与远程配置封装（按三步取）
- **输出**：逐配置项一行「配置名 + 默认值 + 关闭态行为 + 历史版本兼容 + 代码现状」。
  **必要性论证**（为什么要这个开关而不是硬编码）是决策，归 review 的上线决策，不在此写。
- **降级**：无配置变更 → 「不涉及 + 现状常量清单扫描证据」

### 埋点

- **意图**：spec 中声明的观测需求
- **现状**：上报封装（按三步取；**与日志封装区分**——日志不是埋点，但两者可能同属一套观测能力）
- **输出**：逐事件一行「事件名 + 触发节点 + 归属 + 报表影响 + 代码现状」。
  记录时机归本阶段激活条目里管可观测性的那些条，此处不复述其判据。
  通知谁属行动项，归 review 的跨团队协同，不在此写。
- **降级**：检索零命中 → 「现状无上报封装，本需求上报为新增域」，并仍按流程图列出应记录的节点

### 依赖变更（SDK/组件/TA）

- **意图**：spec Scope 模块清单；AR 的依赖/TA 线索（按索引直读 SR）
- **现状**：模块依赖声明（按三步取）；新依赖边的合法性另查 architecture `can_depend_on`
- **输出**：逐依赖一行「依赖 + 变更 + 体积影响 + 兼容风险 + 代码现状」，
  体积与兼容分别对照本阶段激活条目里管体积引入与管版本兼容的那些条；跨层依赖违规直接标红线
- **降级**：无新增依赖 → 「不涉及：Scope 内模块的依赖声明无需变更」

### 知识判定（结论落归档件，代码要求落 spec）

判定在 spec 阶段做——那时 SR / PRD / 激活条目都在手上，取证成本最低。但**判定结论不进 spec**：
它零条代码要求，纯粹是给评审者的完备性证明，与「spec 只装与最终代码有关的内容」相悖。

判定只有三个出口：

1. **产生的代码要求 → spec 的规约约束要求章**，**按命中条目逐条派生**——
   不为任何域预留固定小节（预留小节等于把域清单硬编码进流程，新增一个域时它产生的要求就没有落点）；
2. **需要人工选择的事项 → 《决策与评审记录》的自然语言问题**；
3. **逐条目的判定结论 → 知识判定登记表**，由装配器渲染成归档件的附录单表。

推演过程是工作底稿，三份文档都不写。

**逐条目判定**

- **意图**：spec 全文与技术契约章的全部结论
- **现状**：**本阶段注入的每一个激活条目**逐条过。条目清单从激活清单派生——
  不在本文列举有哪些域、哪些编号，也不按名豁免任何域
- **输出**：一张表，逐条目一行「域 + 编号 + 要求 + 命中 + 结论或落点」。
  所有域同表同粒度，**不为任何域另开自检表**——同一件事分两张表登记，两表迟早对不上，
  评审者也说不清该查哪张。命中判定必须指回**具体变更的名字**
  （如「新增下单接口 `createBusinessOrder` 的入参出参字段」），不写小节坐标；
  一条含多问的，命中时逐问给结论。
  **本表不产生新要求**——自检发现需要新增要求时，那条要求写进 spec 的约束要求章或技术契约章，本表只做指向。
  **判出「待某方确认」的事项必须逐条登记进 review 的待定项**——那是评审议程的唯一来源。
- **降级**：无（总能产出——全不命中也是结论，但每条都要给不命中的依据）

## 3. 结论写法

取证是**生成过程**（各节的四要素），不是**产物形态**。取证的结果是一条具体、可回查的结论——
不是一条结论加一个出处坐标。

### 3.1 结论必须具体到可回查

每条结论都要写全它谈论的那个东西的**名字**：接口名、存储键、事件名、配置项名、模块名、错误码、
页面路由名。反例与正例：

| 反例（空话，无从核对） | 正例（具体，可按名回查） |
|---|---|
| 新增了一个管理台开关 | `feature_entry_enabled`（管理台功能开关，新增）：默认 `false`；关闭态隐藏新增入口及其相关提示 |
| 新增了下单接口 | 云侧接口 `createBusinessOrder`（新增）：入参 `bizNo`/`amount`(分)/`source`（入口来源），出参 `orderNo`/`payParams`，新增错误码 `ORDER_REJECTED` |
| 端侧新增了缓存 | 存储键 `last_business_context`（新增）：值结构 `{ orderNo, bizNo, createdAt }`，有效期 30 分钟 |

名字写全了，verifier 与开发的证据抽查关卡就能按名搜遍 spec / SR / RR / 代码去核对——
**这比 AI 自己写的坐标可靠**。

不涉及的小节写「不涉及 + 一句判断依据」，同样要具体（依据是什么现状、扫了什么）。

### 3.2 三类必须写进结论的信息（它们是内容，不是脚注）

**同一条证据在 spec 与归档件里形态不同**——spec 是仓内工作件、归档件面向评审者，
两者的读者和可用引用方式都不一样。所以形态分两列，**三行都必须填**：
缺哪一格，写的人就会拿另一个产物的写法照搬过来。

| 类别 | spec 形态 | 归档件形态 | 说明 |
|---|---|---|---|
| **代码库现状** | 仓内文件路径，或检索结论「检索 <该类封装> 于 in_scope 模块零命中」 | **不写仓内路径**——归档件随需求上传，评审者打不开 | 核心公式「变更意图 × **代码库现状**」的另一半，本身就是结论的组成部分。**写之前自己确认路径存在**——没有门禁替你查，写错了就是一条查无此物的证据。spec 不归档，路径在仓内有效；归档件里出现仓内路径会被归档件红线拦下 |
| **约束规约** | 编号：`XXX-01` | 中文域名 + 编号 + 含义括注：`<中文规约名> XXX-01（<该条要求什么>）` | 指向随仓归档的规约，评审者可查。归档件正文只写中文规约名，编号只出现在附录那张表里 |
| **数值来源类型** | 三选一标注在正文：`≤ 1500 ms（本工程设定，无上游依据）` / `30 分钟（上游约束：SE 设计文档）` / `（平台基线）` | **按来源分流**：上游约束 / 平台基线 → 正文直接写数值 + 出处；**本工程设定 → 正文不标注来源，登记 `decisions.json` 后写 `{{DEC-00X}}` 引用** | 凡阈值、时长、次数一类数字，都要能让评审者分辨哪些是硬约束、哪些是可议的默认值。spec 里靠括注即可（spec 没有决策登记机制）；归档件有决策件，可议的值就该进那里让人表态——括注只是告知，决策条目才能被投票。标「上游约束」时会被门禁**读上游原文验证该数值真实存在**；归档件侧还会被**数值溯源守恒**兜底：上游无、决策也无的数值一律拦下（比对的是值，与你怎么描述无关） |

### 3.3 不写的东西

- **文档坐标**：`spec §3 功能清单`、`SR §4.2 云侧接口定义`、`RR §2`、`AR §4 上游索引`——
  一律不写（理由见 §0 独立审计原则）。
- **小节互指坐标**：`见 A5`、`指回 A2`——改用事物的名字
  （`见管理台功能开关 feature_entry_enabled`、`源于新增的下单接口 createBusinessOrder`）。
  判定命中项指回具体变更时同理。

## 4. 上线决策的取证边界

review 的上线决策是**人的决策**，本规则只约束 AI 的「建议预填」：
仅当 spec 事实明确不适用时可预填「建议：不涉及（理由）」；理由同样用名称式，不用小节坐标——
写「仅需通知运营（新增了三个上报事件，无对外面与端云接口变更）」，
不写「（上报节有新增，接口节无变更）」这类指节不指物的写法。
