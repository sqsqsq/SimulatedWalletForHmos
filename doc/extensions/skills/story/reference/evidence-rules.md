# spec 取证规则

spec 技术契约章每条结论的**唯一合法产出方式**：信息源 → 提取步骤 → 输出规则。
取证失败按各节的降级规则写，**任何信息源都取不到时不编造结论**。

## 1. 核心公式

> **事实 = 变更意图 × 代码库现状**

变更意图从 AR / SR / RR 与 spec 前几章来；**现状先看激活清单里的项目知识**（有什么、叫什么、在哪），
它没登记的面再实扫仓。两者交叉才得出「新增 / 修改 / 废弃 / 复用 / 不涉及」——
只有意图、没有现状比对的条目一律视为**未取证**。

**现状不能用平台常识顶替**：某个 API 在别的工程常见，不等于本工程在用；
项目知识里已核实为「没有」的能力，不要选进新设计。

## 2. 信息源总表

### 变更意图

| 源 | 用途 | 缺失时 |
|---|---|---|
| `spec/spec.md`（定稿） | 意图 SSOT：Scope / 功能清单 / 流程图 / 界面描述 / 配置 | 不可缺（本规则约束的正是它的技术契约章） |
| `AR/design.md` | 上游已声明的对外依赖与配置线索；链接表与上游索引是 SR/RR 的定位索引 | 标注「非 story 流程，仅 spec 单源取证」 |
| `SR/design.md` | 跨部件交互（调用方推定）、云侧接口定义、系统级存储方案 | 调用方 / 端云详情置信度降级并标注 |
| `RR/prd.md` | 业务场景佐证、验收意图 | 标注缺失 |

### 代码库现状

| 源 | 用途 |
|---|---|
| **激活清单里的项目知识**（`kind: facts`） | **现状的第一落点**：登记了的直接引用；没登记的面才实扫 |
| `doc/module-catalog.yaml` | **定位线索**：`key_exports` / `responsibilities` 指向该去哪个模块找；`NOT_responsible_for` 是负向证据。**catalog 里没有不等于工程里没有**——「无」只能由检索零命中得出 |
| `doc/architecture.md` + `framework.config.json` 的 architecture 段 | 层间依赖规则（`can_depend_on`） |
| `doc/glossary.yaml` | 术语 → 权威模块定位 |
| **激活清单里的规约条目**（`kind: constraints`） | 逐条判定的基准。条目清单由激活清单派生，**本文不列域也不列编号**——列了就是第二份清单，规约一改这里就过期 |
| 代码检索 | 上述都定不下来时的兜底；范围 = spec Scope 的 `in_scope_modules` 目录 + 全仓工程配置 |

## 3. 各节取证

**现状怎么取（三步，各节通用）**：① 先查项目知识有没有登记该类能力的既有实现，有就照它写；
② 没登记或存疑，用 catalog 缩定位范围再在范围内检索；③ 与项目知识不符时**以仓为准**，
在结论里登记「项目知识矛盾：<哪一面、哪里不符>」，**知识文件不在本阶段改**。
结论里注明依据来自哪一步（项目知识已确认 / 本次实扫），让「查过确实没有」与「没查」可分。

### 端云接口
意图取 spec 流程图的云侧节点与 SR 端云声明；现状取网络层封装。
逐接口一行「新增/复用/变更 + 入参出参 + 错误码 + 代码现状」。
请求量四问（触发时机 / 并发 / 缓存降频 / 定时是否离散）是分析过程，只把结论写成非功能要求一行。
零命中 → 「现状无端云封装（检索零命中），云侧交互为新增域」。

### 数据存储
意图取 spec 的持久化需求；现状取持久化封装与存储键。
逐存储项一行「键名 + 介质 + 值结构 + 有效期 + 用途 + 代码现状」。
schema 三问（版本号 / 迁移 / 备份恢复）是分析过程，结论写成兼容性要求一行；加密归安全性要求。
零命中 → 「现状无持久化封装，引入持久化属新增域，须全新设计声明」。

### 配置项
意图取 spec 里涉及的开关与配置；现状取常量开关与远程配置封装。
逐项一行「配置名 + 默认值 + 关闭态行为 + 历史版本兼容 + 代码现状」。
「为什么要开关而不是硬编码」是决策，归 review。
无变更 → 「不涉及 + 常量清单扫描证据」。

### 埋点
意图取 spec 声明的观测需求；现状取上报封装（**与日志封装区分**）。
逐事件一行「事件名 + 触发节点 + 归属 + 报表影响 + 代码现状」。
通知谁属行动项，归 review。
零命中 → 「现状无上报封装，上报为新增域」，并仍按流程图列出应记录的节点。

### 依赖变更
意图取 spec Scope 模块清单；现状取模块依赖声明，新依赖边另查 `can_depend_on`。
逐依赖一行「依赖 + 变更 + 体积影响 + 兼容风险 + 代码现状」；跨层依赖违规直接标红线。
无新增 → 「不涉及：Scope 内模块的依赖声明无需变更」。

## 4. 结论写法

取证是**生成过程**，产物是一条具体、可回查的结论——不是一条结论加一个出处坐标。

### 4.1 具体到可按名回查

每条结论写全它谈论的那个东西的名字：接口名、存储键、事件名、配置项名、模块名、错误码、路由名。

| 反例（空话，无从核对） | 正例（可按名回查） |
|---|---|
| 新增了一个管理台开关 | `feature_entry_enabled`（管理台功能开关，新增）：默认 `false`；关闭态隐藏新增入口及其提示 |
| 新增了下单接口 | 云侧接口 `createBusinessOrder`（新增）：入参 `bizNo`/`amount`(分)/`source`，出参 `orderNo`/`payParams`，新增错误码 `ORDER_REJECTED` |
| 端侧新增了缓存 | 存储键 `last_business_context`（新增）：值结构 `{ orderNo, bizNo, createdAt }`，有效期 30 分钟 |

名字写全了，verifier 与证据抽查关卡才能按名搜遍 spec / SR / RR / 代码去核对。
不涉及的小节写「不涉及 + 一句判断依据」，依据同样要具体（扫了什么、什么现状）。

### 4.2 三类必须写进结论的信息

| 类别 | 怎么写 |
|---|---|
| **代码库现状** | 仓内文件路径，或检索结论「检索 <该类封装> 于 in_scope 模块零命中」。**写之前自己确认路径存在**——没有门禁替你查，写错了就是一条查无此物的证据 |
| **约束规约** | 编号（`XXX-01`）。spec 是仓内工作件，读者手上有规约文件 |
| **数值来源类型** | 三选一标在正文：`≤ 1500 ms（本工程设定，无上游依据）` / `30 分钟（上游约束：<文档名>）` / `（平台基线）`。标「上游约束」时门禁会**读上游原文验证该数值真实存在** |

**story 侧不同**：归档件里数值不带来源括注——来源由 spec 承担，可议的值登记决策件后在正文引用。

### 4.3 不写的东西

**文档坐标**（`spec §x` / `SR §x` / `RR §x` / `AR §x`）与**小节互指**（`见 A5`）一律不写：
坐标换个文档就失效，名字到哪都成立，且坐标由 AI 自己写、无法自证真假。
改用事物的名字——写「见管理台功能开关 `feature_entry_enabled`」，不写「见 A5」。
