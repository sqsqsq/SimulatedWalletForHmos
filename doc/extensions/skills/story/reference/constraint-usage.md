# 应用域约束在 spec/story 阶段的用法

规约是什么、怎么读，见激活清单里的知识索引与规约索引。
消费方不止一个——coding 要落实、code-review 要检查、testing 要走查，各自的用法各自维护。

**本文只管 spec/story 这一段**：怎么判定、结论回显到哪里。规约文件不写回显指引，一律在本文。

**条目清单从激活清单来**：本阶段要判的是 `manifest.yaml` 的 `provides.knowledge`
登记、且 `kind: constraints` 的那些文件里的每一个条目。不扫描知识目录、不读未登记的文件；
本文也不列域清单——列了就是第二份真源，新增一个域时它必然过期。

## 判定的三个出口

判定在 **spec 阶段**做（那时 SR / PRD 都在手上，取证成本最低）。判定的推演过程是工作底稿，
三份产物都不写；它只输出三样：

| 判定产出 | 落点 | 为什么在这 |
|---|---|---|
| 逐条目的**判定结论** | 叙事件的附录「规约符合性」单表（由知识判定登记表确定性渲染） | 零条代码要求，纯粹是给评审者的完备性回显 |
| 判定中冒出来的**代码要求** | 规格件的「规约约束要求」章，按**命中条目**逐条派生 | 这类要求只在合规判定时才冒出来，别处没有，漏了就到不了编码 |
| 判定中得出的**待某方确认** | 决策件的开放决策项 | 需要人表态的事项必须有表态位 |

## 符合性表的写法

**一张表，逐条目一行**：域、编号、要求、命中、结论或落点。所有域同表同粒度——
兼容性不另开自检表：同一件事分两张表登记，两张表迟早对不上，评审者也说不清该查哪张。

1. **「命中」只能填 `是` 或 `否`**——填「按需」「视情况」是把判断推给下游，
   而这里的全部价值就是此刻给出判断；
2. **编号逐个列出**（一条目一行），禁止只写域前缀，也禁止用波浪号连写首尾编号的区间记法——
   按前缀判会让整域漏判照样放行；
3. **「要求」列由装配器从规约原文渲染，作者不手抄**：手抄必然与原文分叉，
   而评审者核的正是原文。也因此，这一列**永远不作为「是不是复述」的被检对象**；
4. **判「是」的「结论或落点」要写本需求的设计**——它落在哪个接口、存储键、字段、业务步骤上。
   写规约原文的复制或子串会被装配拦下；同义改写会进评审的必答清单；
5. **判「否」也要给依据**：写「不涉及」不构成依据，写「本需求无新增对外开放页面或接口」才是；
6. 正文里提规约时写**中文规约名**，不写编号——编号是仓内标识，评审者对不上；
   编号只出现在附录那张表里。spec 侧相反：它是仓内工作件，读者手上有规约文件，写裸编号即可
   （两侧形态见 [`evidence-rules.md`](evidence-rules.md) §3.2 证据表）。

## 设计模式候选的写法

**只登记候选，不做选型**。逐个适用单元写候选与命中信号——
**「什么算一个适用单元」由激活清单里的模式索引定义**，此处不复述（复述就是第二份真源）：

- 候选**只能从在册 `pattern_id` 里查表填**，通用软件模式名不是合法值；
- 同一单元可能命中多个模式，也可能一个都不命中；
- **零候选是正常结论**，但要显式登记单元与「为什么都不需要」——
  空着分不清「判过了不需要」与「压根没想这件事」；
- 选或不选是 **plan** 的事：那里才有方案上下文。spec 阶段做选型等于凭空决定。

## 判定纪律

- **条件域先判域，`always` 域逐条**：每个域的 frontmatter 写了 `applies_when`。写 `always` 的域，
  域内条目一律平权逐条判；有命中条件的域，先在 `domains[]` 写一行「适用 / 不适用 + basis」——
  域级不适用是**带依据的判定记录**，不是跳过，判不适用后域内条目不再逐条登记；
  判适用的域，域内条目同样逐条判，判「否」也要给依据；
- 处置标 `（评审动作）` 的条目仍要判定并回显，但**不进规格件的约束要求章**，
  也不建验收条目：它不产生任何代码要求；
- `<待补充：…>` 处写「基准待补充，按条目语义定性评估」，**不得臆造数值**；
- 判定结论是不是「本需求的设计」由 verifier 逐行裁决——这是语义判断，脚本判不了；
  脚本只保证三件事：条目一条不漏、编号在册、结论不是原文的复制。
