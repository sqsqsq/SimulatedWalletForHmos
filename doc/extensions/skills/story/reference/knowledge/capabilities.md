# 知识能力台账

> 读者：适配知识的维护模型；阶段作者与审查者在确认某项能力要求、修订变化或缺口时展开相应条目。写法与登记格式见 [protocol.md](protocol.md)。

一条一项能力。**台账全登记不等于目标都要接入**：业务相关能力按适用条件判，可选模式按目标代码结构选，Demo 的文件拆分、域数量与具体模式都不是完整性标准。目标自有、台账里没有的能力照常消费；与 Demo 同名同号时以目标为准。

每条字段：**类型**、**修订**（本条要求的修订号，按能力单独递增）、**适用**、**谁消费、要得到什么**、**要回答的面与取证**、**走查**（拿一个正常业务，看读者能否用这份知识完成所列消费者要做的那项判断或设计；缺依据补依据，缺应用关系补叙述或例子，真缺决定写待决，不按栏目是否填满判）、**缺失时**、**Demo 参考**（只看组织方式，内容不搬）、**变化**（新增、变更、拆分、合并、迁移的依据，跳版本升级从目标旧 ID 与内容出发对照这里）。

## 一、通用读写规则

### knowledge-protocol

- 类型：机制规则（不登记在目标知识里）；修订 1。
- 适用：所有目标。
- 谁消费：全部读写知识的模型，要得到三类知识的写法、facts 的面、规约表列义与值域、模式的上下篇结构、能力登记格式。
- 走查：激活清单里的文件都能被加载；加载报出的格式错误都已修。
- 缺失时：加载器报具体文件与修法，先修，不走不适用。
- 变化：1.9.6 起规则由机制提供（本目录 `protocol.md`）。目标旧的 `knowledge/README.md` 与 `knowledge/{facts,constraints,design-patterns}/README.md`（`kind: index`）退出：其中的通用规则已由 `protocol.md` 接替；目标自己加的项目说明迁进相应知识文件，改激活清单与引用，再删旧文件。模式 README 的「模式清单」由激活的模式文件派生，依赖写回各模式文件的 `depends_on`。

## 二、业务相关能力

### component-profile

- 类型：facts；修订 1。
- 适用：所有目标，首次安装必做，固定第一份。
- 谁消费：spec 作者判断上游内容与本部件是否相关、界定范围与交互方；故事成文的范围与协作章。
- 面与取证：**部件申明**（部件是什么、职责边界）——架构配置、模块目录与架构说明；**交互方清单**（与谁交互、各自承担什么）——跨模块出口、接口声明与调用方。另在 frontmatter 集中登记本仓的 `capability_decisions`。
- 走查：每条事实带仓内路径或架构配置键名；拿一个真实需求，能据它判出哪些上游内容不归本部件。
- 缺失时：spec 无法判相关性与范围边界，作者只能逐次实扫并在产物里写明依据。
- Demo 参考：`knowledge/facts/component-profile.md`。

### engineering-capabilities

- 类型：facts；修订 1。
- 适用：有代码的目标；设计与编码要用到工程能力时消费。
- 谁消费：spec 写技术契约的「代码现状」、plan 选实现、coding 落地，都要知道本项目已有哪些实现可直接用。
- 面与取证：按能力类别分面（如对外入口与导航、数据与共享状态、开关、日志、脱敏、资源、依赖），每条写本项目已有的实现：用哪个符号、在哪、怎么用。只写模型不容易看到或容易自己另写一套的项目实现；通用写法由编码规范承担。取证看定义与一处实际调用。
- 走查：抽一个真实需求，读者要用到的每项工程能力都能找到本项目的实现与用法。
- 缺失时：作者实扫取证并写检索式；审查按「新增能力未说明复用」判。
- Demo 参考：`knowledge/facts/engineering-capabilities.md`。
- 变化：1.9.6 由 `codebase-facts` 更名为 `engineering-capabilities`，改为只写已有实现与用法；目标旧文件登记的 `codebase-facts` 对应本条。1.9.5 起上报渠道归 `event-tracking`。

### event-tracking

- 类型：facts；修订 1。
- 适用：需求涉及业务定位、运维统计或独立运营采集时。
- 谁消费：spec 写统计设计（观察什么、有哪些业务结果、本端何时知道、哪些已有采集覆盖）；plan 把每种结果落到责任方法与项目要求的字段取值；coding、审查与测试按同一份实现与核对办法落地和取证。
- 面与取证：按读者任务组织——
  - **统计设计**：各类上报目的与现有采集能力；指标、流程、步骤与一次尝试的关系；结果与本端获知时机；应用步骤与一个业务例子。——业务协议、需求规范、负责人约定，上报门面的定义与导出。
  - **上报实现**：一个结果由哪个方法、用什么标识与取值报出，同一次尝试怎样只报一次；应用步骤、例子与调用骨架；落地约定与核对情形。——上报接口与常量定义，一条正常与一条失败或异常的实际调用。
  - **编号分配与复用**：新标识与取值怎样提出、复用与核冲突。——现有常量与登记、分配惯例、负责人约定。
  - **业务扩展字段**：项目额外提供的字段与要取得的依据。——字段写入接口、业务参数规范。
- 走查：拿一个真实业务，读者写得出统计设计，能把其中一个结果接成「责任方法与分支 → 字段取值与来源 → 调用 → 预期事件」，需要新值时按分配规则提出。
- 缺失时：spec 仍按业务写指标与结果；plan 缺取值依据时写明缺哪一项、影响哪几处，提交裁决。
- Demo 参考：`knowledge/facts/event-tracking.md`。
- 变化：1.9.6 由 `reporting` 更名为 `event-tracking`（埋点上报），按读者任务重组为四面：旧「业务统计语义」「渠道与已有能力」与使用参考的业务部分 → 统计设计；旧「身份与 SDK 映射」「结果与字段映射」与使用参考的实现部分 → 上报实现；旧「登记与复用」→ 编号分配与复用；业务扩展字段不变。目标旧登记的 `reporting` 与旧面名对应到这里，继续已有需求时按实际内容重判。1.9.5 由 `chart-reporting` 更名为 `reporting`。

### 规约各域

规约按域一个文件，域前缀即编号前缀。Demo 的八个域只是参考，目标按自身规范建域，不以域数量判完整；目标自有域照三类写法写，机制照常消费。

| ID | 域 | 适用 |
|---|---|---|
| ux-consistency | UX 一致性 | 新页面或 UI 改版 |
| security-privacy | 安全隐私 | 所有需求 |
| dfx-baseline | DFX 基线 | 所有需求 |
| observability | 可观测性 | 新增或修改业务流程的定位、运维统计或独立运营采集 |
| resource-usage | 资源使用 | 界面图片、图标或用户可见文案 |
| compatibility-checklist | 兼容性 | 所有需求 |
| env-exceptions | 环境异常场景 | 所有需求 |
| deliverables | 资料交付 | 所有需求 |

- 谁消费：spec 判命中并写要求与落点；plan 挂 `must`；review、ut、testing 取证；评审动作类条目只在评审记录留痕。

- 类型：constraints；各域修订 1。
- 面与取证：每条条目的约束、强制力、命中条件、处置、验证（执行体）、探针——来源是目标团队已发布的规范、评审清单与历史缺陷；数值无依据写 `<待补充：…>`。
- 走查：拿一个真实需求逐条判命中，命中条目能写出落在哪个实体上、由谁验；不命中能指出命中条件里不成立的事实。
- 缺失时：该域没有要判的条目，spec 的知识判断里不出现；需求确实涉及时审查按「漏判」看材料。
- Demo 参考：`knowledge/constraints/` 下同名文件。
- 变化：1.9.2 起条目表含强制力、验证（执行体）、探针三列；1.9.5 起 `observability` 的逐步日志条目退出，统计点义务写成基线，取值归埋点知识。

## 三、可选模式

目标按自身代码结构选择，可以一个不用；Demo 模式依赖的 SDK 目标没有、或语言不同时判不适用，不因此判知识不完整。目标自有模式照 `protocol.md` 第五节写。

| ID | 解决什么 |
|---|---|
| decision-tree | 复杂分支流程：每个分支都是多步的复杂功能 |
| page-interaction | 页面交互多，由业务结果驱动下一个交互 |

- 类型：patterns；各修订 1。
- 谁消费：spec 按单元登记候选；plan 选型并把角色投影到契约 `files[].pattern` / `role`；coding 读下篇落地；review 核角色投影。
- 面与取证：frontmatter 的 `roles`、`depends_on` 等；上篇适用、选型与应用步骤；下篇 SDK 行为事实、角色、骨架、约定、反模式——依据 SDK 类型声明与实现、仓内一处真实使用。
- 走查：拿一段真实流程或页面，能判出命中或不命中并给出单元与信号；采用时每个角色能指到一个承载实体。
- 缺失时：spec 对该类结构写「无候选」并举证；不影响其他知识。
- Demo 参考：`knowledge/design-patterns/` 下同名文件。
