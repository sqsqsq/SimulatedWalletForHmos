# 知识能力台账

> 读者：适配知识的维护模型；阶段作者与审查者在确认某项能力要求、修订变化或缺口时展开相应条目。写法与登记格式见 [protocol.md](protocol.md)。

一条一项能力。**台账全登记不等于目标都要接入**：业务相关能力按适用条件判，可选模式按目标代码结构选，Demo 的文件拆分、域数量与具体模式都不是完整性标准。目标自有、台账里没有的能力照常消费；与 Demo 同名同号时以目标为准。

每条字段：**类型**、**修订**（本条要求的修订号，按能力单独递增）、**适用**、**谁消费、要得到什么**、**要回答的面与取证**、**走查**（怎样算完成）、**缺失时**、**Demo 参考**（只看组织方式，内容不搬）、**变化**（新增、变更、拆分、合并、迁移的依据，跳版本升级从目标旧 ID 与内容出发对照这里）。

## 一、通用读写规则

### knowledge-protocol

- 类型：机制规则（不登记在目标知识里）；修订 1。
- 适用：所有目标。
- 谁消费：全部读写知识的模型，要得到三类知识的写法、facts 的面与 `confirmed`、规约表列义与值域、模式的上下篇结构、能力登记格式。
- 走查：激活清单里的文件都能被加载；加载报出的格式错误都已修。
- 缺失时：加载器报具体文件与修法，先修，不走不适用。
- 变化：1.9.6 起规则由机制提供（本目录 `protocol.md`）。目标旧的 `knowledge/README.md` 与 `knowledge/{facts,constraints,design-patterns}/README.md`（`kind: index`）退出：其中的通用规则已由 `protocol.md` 接替；目标自己加的项目说明迁进相应知识文件，改激活清单与引用，再删旧文件。模式 README 的「模式清单」由激活的模式文件派生，依赖写回各模式文件的 `depends_on`。

## 二、业务相关能力

### component-profile

- 类型：facts；修订 1。
- 适用：所有目标，首次安装必做，固定第一份。
- 谁消费：spec 作者判断上游内容与本部件是否相关、界定范围与交互方；故事成文的范围与协作章。
- 面与取证：**部件申明**（部件是什么、职责边界）——架构配置、模块目录与架构说明；**交互方清单**（与谁交互、各自承担什么）——跨模块出口、接口声明与调用方。另在 frontmatter 集中登记本仓的 `capability_decisions`。
- 走查：每条事实带仓内路径或架构配置键名；拿一个真实需求，能据它判出哪些上游内容不归本部件。
- 缺失时：spec 无法判相关性与范围边界，作者只能逐次实扫并在产物里写明依据。
- Demo 参考：`knowledge/facts/component-profile.md`。

### codebase-facts

- 类型：facts；修订 1。
- 适用：有代码的目标；需求要写「代码库现状」时消费。
- 谁消费：spec §9 技术契约各表的「代码现状」与已有能力复用；plan 的新增能力先复用登记入口。
- 面与取证：**对外暴露面**、**端云接口**、**数据存储**、**配置项**、**本地日志**、**敏感数据处理**、**资源**、**依赖变更**——各到对应的定义处与一处实际调用取证，写入口名与位置。
- 走查：抽一个真实需求，每个要用到的面都能指到仓内入口；与代码不符之处已登记。
- 缺失时：作者实扫取证并写检索式；复用判断无登记可对照，审查按「新增能力未说明复用」判。
- Demo 参考：`knowledge/facts/codebase-facts.md`。
- 变化：1.9.5 起上报渠道不在这里写，归 `reporting`。

### reporting

- 类型：facts；修订 1。
- 适用：需求涉及业务定位、运维统计或独立运营采集时。
- 谁消费：Spec §9.4 按指标写观察范围、涉及的流程与步骤、实际业务结果与本端获知时机，已实现的采集覆盖不重复列，只是规范、尚未实现的不算覆盖；Plan 埋点对每种结果给出身份、结果与必要参数的实际值或具体候选、责任方法与验证；spec / plan 审查把 Spec 统计点、Plan 结果行与这份知识并列核。
- 面与取证：分两组，业务语义在前、协议映射在后。
  - **业务统计语义**：各类上报的目的（问题定位、运维统计、独立运营采集）；指标与流程的关系（可以一对多、多对一，共用事实只采集一次）；步骤、子点、尝试与结果的关系；同一事实服务多种目的时是否共用身份；远端结果本端何时可知。——业务协议、需求规范与负责人约定。
  - **渠道与已有能力**：各渠道的入口与现状，已实现的交互自动记录（如页面进入、点击）覆盖什么、接入条件；已定而未实现的写成已定规范与建设差距，不算已有覆盖。——上报门面的定义与导出、交互自动记录的注册与开关、实际页面接入。
  - **身份与 SDK 映射**：业务身份的层级与参数、常量、平台字段的对应。——身份常量定义、序列化与接收协议。
  - **结果与字段映射**：结果编码的结构与各段语义、结果分类各值、外码来源、耗时单位。——码表与结果枚举，一条正常与一条失败或取消的实际调用。
  - **业务扩展字段**：实际存在的扩展字段、类型、含义与取值；含义未定的列成具体待核问题。——字段写入接口与调用处赋值、业务参数规范。
  - **登记与复用**：现有定义在哪；身份与结果编码各自的命名空间与段长；新值怎样在父范围里取候选、首次使用父范围时怎样提出、有外部统一分配时用什么；登记文件在哪、登记前怎样核冲突。——现有常量与登记文件、分配惯例、负责人约定；查不到的列为待决，不自行占号。
  - **使用参考**：一个业务语义短例（指标 → 步骤 → 结果 → 获知时机）与对应的实现映射（一种结果连成 Plan 深度的一行）。——本仓一条真实业务的上报调用。
- 走查：拿一个真实业务，能据此写出 Spec §9.4 一个指标的 H4 与 Plan 埋点一种结果的一行实际值或具体候选；关键词齐全不算。
- 缺失时：Spec 仍按业务写指标与结果；Plan 的协议值缺依据时点明缺哪一项、影响哪几行，提交裁决，不把点位留给编码。
- Demo 参考：`knowledge/facts/reporting.md`。
- 变化：1.9.5 由 `chart-reporting` 更名为 `reporting` 并合入其余上报渠道与交互自动记录；`codebase-facts` 的上报渠道一节迁入。本修订把业务统计语义单列一面放在最前，规范与已实现覆盖分开，分配方法写清命名空间与首次候选；知识只讲项目语义与协议，阶段写在哪由机制入口承担。

### 规约各域

规约按域一个文件，域前缀即编号前缀。Demo 的八个域只是参考，目标按自身规范建域，不以域数量判完整；目标自有域照三类写法写，机制照常消费。

| ID | 域（Demo 前缀） | 适用 | 谁消费、要得到什么 |
|---|---|---|---|
| ux-consistency | UX 一致性（UX） | 新页面或 UI 改版 | spec 判命中并写要求与落点；plan 挂 `must`；review、ut、testing 取证 |
| security-privacy | 安全隐私（SEC） | 所有需求 | 同上 |
| dfx-baseline | DFX 基线（DFX） | 所有需求 | 同上 |
| observability | 可观测性（OBS） | 新增或修改业务流程的定位、运维统计或独立运营采集 | 同上；统计点的协议值看 `reporting` |
| resource-usage | 资源使用（RES） | 界面图片、图标或用户可见文案 | 同上 |
| compatibility-checklist | 兼容性（COMPAT） | 所有需求 | 同上 |
| env-exceptions | 环境异常场景（ENV） | 所有需求 | 同上 |
| deliverables | 资料交付（DLV） | 所有需求 | 同上；评审动作类条目只在评审记录留痕 |

- 类型：constraints；各域修订 1。
- 面与取证：每条条目的约束、强制力、命中条件、处置、验证（执行体）、探针——来源是目标团队已发布的规范、评审清单与历史缺陷；数值无依据写 `<待补充：…>`。
- 走查：拿一个真实需求逐条判命中，命中条目能写出落在哪个实体上、由谁验；不命中能指出命中条件里不成立的事实。
- 缺失时：该域没有要判的条目，spec 的知识判断里不出现；需求确实涉及时审查按「漏判」看材料。
- Demo 参考：`knowledge/constraints/` 下同名文件。
- 变化：1.9.2 起条目表含强制力、验证（执行体）、探针三列；1.9.5 起 `observability` 的逐步日志条目退出，统计点义务写成基线，协议值归 `reporting`。

## 三、可选模式

目标按自身代码结构选择，可以一个不用；Demo 模式依赖的 SDK 目标没有、或语言不同时判不适用，不因此判知识不完整。目标自有模式照 `protocol.md` 第五节写。

| ID | 解决什么 | 依赖 |
|---|---|---|
| decision-tree | 复杂分支流程：每个分支都是多步的复杂功能 | 编排 SDK |
| page-interaction | 页面交互多，由业务结果驱动下一个交互 | 编排 SDK |

- 类型：patterns；各修订 1。
- 谁消费：spec 按单元登记候选；plan 选型并把角色投影到契约 `files[].pattern` / `role`；coding 读下篇落地；review 核角色投影。
- 面与取证：frontmatter 的 `roles` 等；上篇适用与选型、契约投影；下篇 SDK 行为事实、角色、骨架、约定、反模式——依据 SDK 类型声明与实现、仓内一处真实使用。
- 走查：拿一段真实流程或页面，能判出命中或不命中并给出单元与信号；采用时每个角色能指到一个承载实体。
- 缺失时：spec 对该类结构写「无候选」并举证；不影响其他知识。
- Demo 参考：`knowledge/design-patterns/` 下同名文件。
