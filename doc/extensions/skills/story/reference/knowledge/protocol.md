# 知识怎么写给模型用

> 读者：写目标仓知识的维护模型，以及各阶段读知识的作者与审查者。时机：写或读某一份知识之前，先读共同写法与它那一格的一节。

知识在扩展根的 `knowledge/` 下，只放目标仓自己的内容：有几份、叫什么、怎么分，都归目标。机制只做两件事——读 `manifest.yaml > provides.knowledge` 登记的文件，按每份文件的自我描述把它交给当前阶段。

## 一、知识怎样描述自己

每份知识在 frontmatter 写四项，这是机制读它的唯一入口：

| 字段 | 写什么 |
|---|---|
| `name` | 文件的标识 |
| `kind` | 类型：`facts`、`constraints` 或 `patterns` |
| `form` | 形态，指机器读的正文结构：`facets`（分面）、`halves`（上下篇）或 `entries`（条目表），必填 |
| `applies_when` | 什么情况下读、它回答什么问题，例如「判断上游内容是否归本部件时：本部件是谁、职责边界、与谁交互」 |

任务包与审查按「路径 —— `applies_when`」列出全部激活知识，读者据此按当前需求选读；所以 `applies_when` 要写清问题，一个「always」说明不了它回答什么。正文开头一句接着说它帮读者做什么决定。登记只在 manifest：新增、改名、拆分一份知识，改知识文件与 `provides.knowledge` 即可。

初析与 AR 提取要读的，是自述回答「本部件是谁、职责边界、与哪些交互方怎样交互」的那一份；首次安装时先写它。

## 二、四个合法格

类型与形态组成四格。加载器按 `form` 分派解析，只核结构，不从正文推断形态；声明与正文不符、组合不在这四格里，载入时按文件报出。

| | facts × facets | facts × halves | constraints × entries | patterns × halves |
|---|---|---|---|---|
| 用在哪 | 查找型：项目已有实现、封装、惯例；首装的部件画像 | 方法型：要多步推导的项目方法 | 规约 | 设计模式 |
| frontmatter | 四项 | 四项，不写 roles | 四项，可选 `domain`（等于条目前缀） | 四项，`name` 即模式 id；`roles` 必填、`optional_roles`、`coordinator_role`；`depends_on` 给模型读，机制不读 |
| 加载器核的结构 | 至少一个二级标题；正文没有「# 上篇 ·」 | 两个一级标题「# 上篇 · …」「# 下篇 · …」，各篇至少一个二级标题 | 表头含「编号」「约束」的条目表（§六） | 同 facts × halves，另核 `roles` 非空、`coordinator_role` 在 roles 里 |
| 登记单元 | 面名 | 篇名（上篇 / 下篇） | 条目编号 | 单元、候选与信号 |
| 下游怎么用 | 任务包列面名，作者登记用了哪一面，审查回查 | spec 读并登记上篇；plan 任务包附下篇全文；coding 读下篇 | spec 9.2 投影、验收 `knowledge_rule`、plan `must`、探针 | spec 9.3 投影、plan `files[].pattern/role`、coding 读下篇 |
| Demo 示例 | `knowledge/facts/` 里 `form: facets` 的各份 | `knowledge/facts/` 里 `form: halves` 的那份 | `knowledge/constraints/` 里带「探针」列的那一份 | `knowledge/design-patterns/` 各份 |

## 三、谁写什么

按「什么变了它才变」判归属：

| 归属 | 写什么 |
|---|---|
| 知识 | 换一个业务仓就不同的东西：项目概念、已有实现与用法、已定规范、项目方法、例子与完成判断 |
| 机制 | 换一套阶段流程才变的东西：阶段目标、何时读知识、结果写进哪份产物哪一节、契约字段位置、命令 |
| 本次产物 | 结合当前需求才能作出的结论：适用判断、具体接口、取值与验证 |

## 四、共同写法

- **正向陈述**：写有什么、怎么用、何时用。依据在别人手里的，写向谁取得什么。
- **只写确定的内容**：每条带依据位置——当前实现写代码或配置位置；已定规范写协议、需求或负责人确认记录；示意写明假设。已定而尚未实现的写成规范与建设差距。同一事实只写一处。
- **按读者任务组织**：有步骤就把要用的事实嵌进那一步，不先列一遍事实再按步骤复述。
- **不复述别处的权威来源**：编码规范、架构配置、模块画像已经写的，不再写。
- **写到模型找得到为止**：只写模型从代码里找不到或会找错的——生效入口、约定、命名与落点；能检索到的签名、路径全名与调用链不写，给一个类名或文件名就够。
- **例子只给一个**：短，标明假设与适用条件；题材与本仓的测试用例、样稿都不同形，例子只示范形状。
- 代码与知识写的「当前实现」矛盾时改知识；代码还没达到已定规范时登记实现差距。

## 五、分面与上下篇

- **分面（facets）**：一个二级标题是一面，标题写 `## <面名>`；知识使用登记（`facts[].used`）按面名引用。按能力分面，每条写用哪个项目实现、在哪、怎么用。
- **上下篇（halves）**：正文两个一级标题，篇名后写读者阶段，如「# 上篇 · 适用与统计设计（读者：spec）」「# 下篇 · 结构与落地（读者：plan、coding、review）」。上篇给设计侧，下篇给实现侧；节按项目方法写，节名、序号与读者字样是写法约定，机制不核。读者按「读者含本阶段的那一篇」读，写完按那一篇自查，审查按那一篇核。
- 项目规则算得出的字段，写成具体值；方法型知识里的必须设计项写成具名列，作者照着给值。

## 六、规约（constraints × entries）

一个文件一个域，条目编号 `<域前缀>-<两位序号>`，编号一经分配不复用；`domain` 可写，写了就等于条目前缀。条目表按列名读：

| 列 | 含义 |
|---|---|
| 编号 | 全链受控标识 |
| 约束 | 要求是什么 |
| 强制力 | **红线** 阻断，命中就落实，不许豁免；**基线** 可本轮豁免，写理由与补偿，由评审判断；**建议** 可不做，写理由 |
| 命中条件 | 什么需求涉及本条 |
| 处置 | 须声明什么结论；以 `（评审动作）` 开头的不产生代码要求——不进 spec 约束出口、不建验收条目，只在评审记录留痕 |
| 验证（执行体） | 写成若干段 `<执行体>：<怎么验>`，各段都要。执行体取 **模型** / **构建** / **实机** / **人工**；评审动作的条目必须有「人工」 |
| 探针 | 可省的列。有这一列时，机器能做的局部形态检查写成 `absent_regex:<正则>` / `present_in_method:<正则>` / `referenced_outside_definition` / `count_eq:<正则>:<次数>`，某条没有写「无」；前缀 `阻断：` 表示形态本身就是要求。表格里的竖线写 `\|` |

一条一个可判定的要求，写命中条件、边界、例外与验法。表后「落法附注」以 `**<编号>**` 起头的列表项是那一条的附注，只解释容易误解的边界；其余列表项是整域通则，同样是要求。规约写义务，项目封装与参数看项目事实。

读条目：`<待补充：…>` 是空缺登记，按条目语义定性评估，数值只用有依据的；条目内的检索式照此执行；判「不命中」写出命中条件里不成立的事实。

## 七、设计模式（patterns × halves）

`name` 就是 `pattern_id`，候选只能填激活清单里在册的 id，或按单元写「无候选」。上篇给判候选与做设计的人：模式解决的问题、不该用它的情形、按步骤应用时各角色承担什么（内部步骤与对外业务状态分开，最后一步回查）；下篇给落地与审查的人：SDK 的行为事实、角色落到哪些文件、结构怎么搭、用它时的约定、设计之外怎样算做完、常见错法。节怎么分、叫什么由知识定。角色投到契约哪个字段是机制的事，见 plan 模板「设计模式选型」。

判候选先把需求切成单元：**流程段**（有独立业务目标与起止的处理过程，用于结构类模式）、**页面/组件**（承载用户操作的界面单位，用于交互类模式；一个页面一个单元，逐页判）。信号来自**业务流程本身**：数分支、数步数、看失败处理时，以需求描述的那个业务过程为准。当前用模拟、演示或简化方式承载某一步，不改变业务信号——承载会换，业务不会。零命中同样举证，反证指向本需求的具体业务事实。

多个模式组合时，先各自完成单元判断与契约投影，再写清每个模式解决哪个独立问题、上下文所有者、先启动谁与交接、用户等待点、失败由谁收敛。
