# 知识的读写规则

> 读者：写或读目标仓知识的模型——适配时的维护模型、各阶段的作者与审查者。时机：先读本次用到的那一类规则，再读相应的已激活知识。每项能力要回答什么，见同目录的 [capabilities.md](capabilities.md)。

知识在扩展根的 `knowledge/` 下，只放目标仓自己的内容；本页是它们共同的写法与读法，随机制升级。

## 一、三类知识与激活

| 类型（frontmatter `kind`） | 回答什么 | 怎么用 |
|---|---|---|
| `facts` 项目事实 | 这个仓的惯例与已有能力：有没有、叫什么、在哪 | 直接复用，不另造；与规约冲突时以规约为准 |
| `constraints` 规约 | 必须做或禁止做的事 | 逐条判命中；命中即义务，落实并验证 |
| `patterns` 设计模式 | 复杂实现的代码结构 | spec 只登记候选，plan 决定用不用；允许一个都不用 |

类型是封闭集合。每份知识文件在 frontmatter 写 `name` 与 `kind`；`applies_when` 是给读者的域级命中摘要。**阶段只读 `manifest.yaml > provides.knowledge` 列出的文件**，目录里未登记的文件没人读到；清单为空是还没配置知识的正常状态。

## 二、项目事实（facts）

一个二级标题是一面（一类能力），标题写 `## <面名> — \`confirmed: 已确认\`` 或 `未确认`：

- `已确认` = 已对仓核实；`未确认` = 用前先核，用到它的阶段要写核实时看的仓内路径。
- 每条事实后面带仓内路径或架构配置的键名；查不到写「未确认」，不写推断。
- 已确认「无 X」的能力不当作已有能力复用；本次确需新建的，作为有依据的方案项登记。
- 已确定但尚未实现的能力写成「已定规范」，不写成已存在。
- 没登记的能力到仓里实扫（构建产物与备份目录不是源码）；与知识不符时以仓为准，并在产物里登记矛盾。
- 面可以按阅读顺序分组，分组靠文件开头的导读，不加包住各面的上级标题。

**部件画像**是 facts 里固定的第一份：这个仓是什么部件、有哪些交互方、职责边界到哪。首次安装时由维护模型写，之后每个需求的作者从它起步。

## 三、规约（constraints）

一个文件一个域，条目编号 `<域前缀>-<两位序号>`，编号一经分配不复用。各域同一张条目表，按列名读：

| 列 | 含义 |
|---|---|
| 编号 | 全链受控标识 |
| 约束 | 要求是什么 |
| 强制力 | **红线** 阻断，命中就落实，不许豁免；**基线** 可本轮豁免，写理由与补偿，由评审判断；**建议** 可不做，写理由 |
| 命中条件 | 什么需求涉及本条 |
| 处置 | 须声明什么结论；以 `（评审动作）` 开头的不产生代码要求——不进 spec 约束出口、不建验收条目，只在评审记录留痕 |
| 验证（执行体） | 写成若干段 `<执行体>：<怎么验>`，各段都要。执行体取 **模型** / **构建** / **实机** / **人工**；评审动作的条目必须有「人工」 |
| 探针 | 机器能做的局部形态检查，没有写「无」：`absent_regex:<正则>` / `present_in_method:<正则>` / `referenced_outside_definition` / `count_eq:<正则>:<次数>`；前缀 `阻断：` 表示形态本身就是要求。表格里的竖线写 `\|` |

强制力与验证是两件事：红线可以只由模型验，基线也可以有探针。表后的「落法附注」以 `**<编号>**` 起头的列表项是那一条的附注，其余列表项是整域通则，同样是要求。

读条目：`<待补充：…>` 是空缺登记，判定时按条目语义定性评估，不臆造数值；条目内的检索式照此执行；判「不命中」要给依据；规约不写类名、路径、API，那些看项目事实。

## 四、设计模式（patterns）

`name` 就是 `pattern_id`，全链受控标识；候选只能填激活清单里在册的 id，或按单元写「无候选」。frontmatter 另写 `roles`（角色，必填）、`optional_roles`、`coordinator_role`，依赖某个 SDK 的写 `depends_on`。正文用两个一级标题分篇：`# 上篇 · …`（适用与选型、契约投影）与 `# 下篇 · …`（SDK 行为事实、角色、骨架、约定、反模式），缺一篇载入即报。

判候选先把需求切成单元：**流程段**（有独立业务目标与起止的处理过程，用于结构类模式）、**页面/组件**（承载用户操作的界面单位，用于交互类模式）。逐单元对照各模式上篇的「解决什么问题」与「什么时候不该用」。信号来自**业务流程本身**：数分支、数步数、看失败处理时，以需求描述的那个业务过程为准。当前用模拟、演示或简化方式承载某一步，不改变业务信号——承载会换，业务不会。零命中同样举证，反证指向本需求的具体业务事实，不复述判定措辞。

多个模式组合时，先各自完成单元判断与契约投影，再在契约里写清：每个模式解决哪个独立问题、上下文所有者、先启动谁与交接、用户等待点、失败由谁收敛；没有组合需求时不建组合层。

## 五、能力登记

知识文件可以在 frontmatter 声明自己承担的能力。它是可选元数据：没有登记的知识照常读取，只是关联尚待核实。

```yaml
protocol: 1
capabilities:
  - id: sample-service
    revision: 1
    covers: [identity, result]
```

- `protocol`：按哪一版读写规则写，当前只有 `1`；写了别的值加载时报不兼容。
- `capabilities`：每项 `id`（台账条目或目标自有的能力）、`revision`（按台账该条的哪一次要求写，正整数）、`covers`（本文件真实承载的面，非空列表，正文能定位其含义）。一个文件可以承担多项，一项也可以由几个文件共同承担；同一文件里同一 `id` 只写一次。

判过不适用或留待以后的，写在部件画像的 frontmatter，集中一处：

```yaml
capability_decisions:
  - id: sample-service
    revision: 1
    scope: [operation]
    decision: not_applicable
    reason: 本部件不承担该业务，交互方提供此能力
    basis: 架构说明中的责任边界及本次用户确认
```

`scope` 是面列表，整项写 `['*']`，两者不混写。`decision` 取 `not_applicable` 或 `deferred`；`deferred` 另写 `impact`：可能影响哪些任务。这些是人作出的选择；接入由 `capabilities` 与实际内容表达，不另记完成状态。

登记只说明状态，不证明内容正确：版本一致也要读内容，关键定义缺失或与代码冲突照样是缺口。
