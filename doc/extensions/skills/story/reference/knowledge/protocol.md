# 知识怎么写给模型用

> 读者：写目标仓知识的维护模型，以及各阶段读知识的作者与审查者。时机：写或读某一类知识之前，先读共同写法与那一类的一节。

知识在扩展根的 `knowledge/` 下，只放目标仓自己的内容：有几份、叫什么、怎么分，都归目标。机制只做两件事——读 `manifest.yaml > provides.knowledge` 登记的文件，按每份文件的自我描述把它交给当前阶段。

## 一、知识怎样描述自己

每份知识在 frontmatter 写三项，这是机制读它的唯一入口：

| 字段 | 写什么 |
|---|---|
| `name` | 文件的标识 |
| `kind` | `facts`、`constraints` 或 `patterns` |
| `applies_when` | 什么情况下读、它回答什么问题，例如「判断上游内容是否归本部件时：本部件是谁、职责边界、与谁交互」 |

任务包与审查按「路径 —— `applies_when`」列出全部激活知识，读者据此按当前需求选读；所以 `applies_when` 要写清问题，一个「always」说明不了它回答什么。正文开头一句接着说它帮读者做什么决定。登记只在 manifest：新增、改名、拆分一份知识，改知识文件与 `provides.knowledge` 即可。

初析与 AR 提取要读的，是自述回答「本部件是谁、职责边界、与哪些交互方怎样交互」的那一份；首次安装时先写它。

## 二、谁写什么

按「什么变了它才变」判归属：

| 归属 | 写什么 |
|---|---|
| 知识 | 换一个业务仓就不同的东西：项目概念、已有实现与用法、已定规范、项目方法的应用步骤、例子与完成判断 |
| 机制 | 换一套阶段流程才变的东西：阶段目标、何时读知识、结果写进哪份产物哪一节、契约字段位置、命令 |
| 本次产物 | 结合当前需求才能作出的结论：适用判断、具体接口、取值与验证 |

## 三、共同写法

- **正向陈述**：写有什么、怎么用、何时用。依据在别人手里的，写向谁取得什么。
- **只写确定的内容**：每条带依据位置——当前实现写代码或配置位置；已定规范写协议、需求或负责人确认记录；示意写明假设。已定而尚未实现的写成规范与建设差距。
- **按读者任务组织**：同一事实只出现一处；有步骤就把要用的事实嵌进那一步，不先列一遍事实再按步骤复述。
- **不复述别处的权威来源**：编码规范、架构配置、模块画像已经写的，不再写。
- **写到模型找得到为止**：只写模型从代码里找不到或会找错的——生效入口、约定、命名与落点；能检索到的签名、路径全名与调用链不写，给一个类名或文件名就够。
- **例子只给一个**：短，标明假设与适用条件。
- 代码与知识写的「当前实现」矛盾时改知识；代码还没达到已定规范时登记实现差距。

## 四、项目事实（facts）

一个二级标题是一面，标题写 `## <面名>`；知识使用登记（`facts[].used`）按面名引用。两种常见形态：

- **已有实现**：按能力分面，每条写用哪个项目实现、在哪、怎么用——写模型不容易看到、容易自己另写一套的东西，通用写法由编码规范承担。
- **项目方法**：要多步推导的能力，照 §六 设计模式的篇与节写——两个一级标题分篇、读者写阶段名，节名与模式同名同序，每节就是一面；不写角色 frontmatter。

## 五、规约（constraints）

一个文件一个域，条目编号 `<域前缀>-<两位序号>`，编号一经分配不复用。条目表按列名读：

| 列 | 含义 |
|---|---|
| 编号 | 全链受控标识 |
| 约束 | 要求是什么 |
| 强制力 | **红线** 阻断，命中就落实，不许豁免；**基线** 可本轮豁免，写理由与补偿，由评审判断；**建议** 可不做，写理由 |
| 命中条件 | 什么需求涉及本条 |
| 处置 | 须声明什么结论；以 `（评审动作）` 开头的不产生代码要求——不进 spec 约束出口、不建验收条目，只在评审记录留痕 |
| 验证（执行体） | 写成若干段 `<执行体>：<怎么验>`，各段都要。执行体取 **模型** / **构建** / **实机** / **人工**；评审动作的条目必须有「人工」 |
| 探针 | 机器能做的局部形态检查，没有写「无」：`absent_regex:<正则>` / `present_in_method:<正则>` / `referenced_outside_definition` / `count_eq:<正则>:<次数>`；前缀 `阻断：` 表示形态本身就是要求。表格里的竖线写 `\|` |

一条一个可判定的要求。表后「落法附注」以 `**<编号>**` 起头的列表项是那一条的附注，只解释容易误解的边界；其余列表项是整域通则，同样是要求。规约写义务，项目封装与参数看项目事实。

读条目：`<待补充：…>` 是空缺登记，按条目语义定性评估，数值只用有依据的；条目内的检索式照此执行；判「不命中」写出命中条件里不成立的事实。

## 六、设计模式（patterns）

`name` 就是 `pattern_id`，候选只能填激活清单里在册的 id，或按单元写「无候选」。frontmatter 另写 `roles`（必填）、`optional_roles`、`coordinator_role`，依赖某个 SDK 的写 `depends_on`。正文两个一级标题，篇名后写读者阶段，如「# 上篇 · 适用与选型（读者：plan）」，节用 `## <序号>. <节名>` 全篇连续编号：

- **上篇**：解决什么问题、什么时候不该用、应用步骤（各角色承担什么、内部步骤与对外业务状态分开，最后一步回查）；
- **下篇**：SDK 行为事实、角色与文件落点、结构骨架、使用约定、设计之外的完成判断、反模式。

缺一篇载入即报。角色投到契约哪个字段是机制的事，见 plan 模板「设计模式选型」。

判候选先把需求切成单元：**流程段**（有独立业务目标与起止的处理过程，用于结构类模式）、**页面/组件**（承载用户操作的界面单位，用于交互类模式），逐单元对照各模式上篇。信号来自**业务流程本身**：数分支、数步数、看失败处理时，以需求描述的那个业务过程为准。当前用模拟、演示或简化方式承载某一步，不改变业务信号——承载会换，业务不会。零命中同样举证，反证指向本需求的具体业务事实。

多个模式组合时，先各自完成单元判断与契约投影，再写清每个模式解决哪个独立问题、上下文所有者、先启动谁与交接、用户等待点、失败由谁收敛。
