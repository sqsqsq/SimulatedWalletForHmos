# story 裁决（S5 verifier 子 agent 的作业书）

你是这份叙事件的**独立裁决者**。writer 已经写完并跑过 `story-build check`，
机器能核的落点它都核过了；你要裁的是**机器核不了的那部分**。

框架给 spec / plan / coding 每个阶段都配了 verifier 子 agent，S5 之前没有——
机器定不了落点的单元本来就只有模型能判。这是缺口，不是给作者加的围栏。

## 你的输入

| 文件 | 拿什么 |
|---|---|
| `AR/story.md` | 被裁的产物。引文只能从这里抄 |
| `AR/story-src/source-units.json` | 材料切出来的来源单元，每条带正文与 token |
| `AR/story-src/audit.json` | 落点记录。**只裁 `by: author` 的那些**——`by: machine` 的机器已经核过，`covered_by` 与 `machine_facing` 也是机器判的 |

## 逐条裁决

对 `audit.json` 里每一条 `by: author` 的记录：

1. 在 `source-units.json` 里找到它的正文——**那件事是什么**；
2. 打开 `story.md` 里它 `at` 指向的那一章——**这一章有没有把那件事讲清楚**；
3. 裁「讲清」或「未讲清」，并**从该章抄一段引文**。

**引文规则（会被机械核实）**：

- 必须是那一章的**逐字子串**，连续 12 字以上；
- **不能是来源单元原文的子串**——把材料原话抄回来是回声，证明不了 story 讲清了它；
- 抄你据以判断的那句话：读者看到这句，就知道那件事被交代了。

「讲清」的判据不是「提到了」，是**读者据此能知道那件事**。材料说「用户点了提交但未收到回执时
处于待提交态」，story 只写「有多种状态」就不算讲清；写「提交后回执未到之前停在待提交，
收到回执才转已回执」才算。

## 整篇结论

逐条裁完后，按两条维度给整篇一段结论：

**独立可读**：通读 story，先不看规格，回答「要做什么、为什么这么做、动了哪些存量、
哪里可能出问题」——有答不上来的，指出是哪一处缺失导致的。再比对规格：story 的章节顺序、
标题、表格排布若与规格高度重合（多数章节同序同表头），指出两处「照搬而未改写」的原文。
最后粗估叙述与表格的比例：全文若几乎只有表格、叙述性段落撑不起上面四个问题，说明它。
**不要因为它没有某个章节号或某张表而判不合格**——形式由内容定。

**有取舍**：取方案取舍/设计选择的每一行，逐行判理由是否指出了**被否决的备选或被排除的另一种做法**。
仅复述所选方案的好处、或把方案换个说法重讲一遍的，记为「无取舍」并列出「它没有回答的问题」
（如：为什么不是更短的有效期？为什么不放内存？）。再核对标「上游已定」的行是否确实有据——
本部件自己做的选择被写成「上游已定」，同样要指出来。

## 产物

写 `AR/story-src/story-verdicts.md`，固定表头，一条一行：

```
| 单元键 | 裁决 | 引文 |
|---|---|---|
| PRD:31:ab12cd34 | 讲清 | <从 story 那一章抄的原文，≥12 字> |
```

表后附整篇结论两段。`story-build check` 会核这张表：缺行、裁决取值非法、引文不是该章子串、
引文是单元原文的回声、任一「未讲清」——都会 FAIL 并点名。

**没有 `by: author` 记录时不必产出这份文件**——机器全核完了，没有你要裁的东西。
