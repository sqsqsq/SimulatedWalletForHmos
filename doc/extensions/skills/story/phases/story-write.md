# story 成文：按章写，最后整篇核对

读者是评审人：他们没参与开发，只有这一份文档，要据此判断
**这件事想清楚了没有、做对了没有**。他不看代码、不翻仓库、不知道内部编号。

动笔之前先写本需求的**写作设计骨架**（第二节）：第一次读的人按什么顺序理解这件事、
正文要有哪些小节、每节要回答什么、依据在哪。然后成文分两步：**一章一章照骨架写**（每章经
`chapter` 命令原子落盘），**十章齐了按回看清单逐条处置一次**（改哪章仍回它的草稿改、再提交）。
不是「一次写完整篇」——整篇是全有或全无，中途断了磁盘上什么都没有；逐章写每步输出有界，
断了知道从哪一章续。写的时候认识深了，回去改设计，再接着写。

## 一、写给这样的读者

- Story 面向**第一次接触需求**的人类评审者，他无需先读规格、产品需求、系统设计或代码。
- 按人的理解顺序说明：为什么做、涉及谁、怎样解决、业务如何推进、当前特性负责什么、
  哪里会失败、怎样验收、怎样交付。先说明背景，再解释理解后文必需的术语。
- 标题用真实业务名，简短、准确概括下文；不用模板占位语、模型提问、机械分类词、
  解释性长句和明显的 AI 式表达。
- **三级只在下级内容值得独立定位时出现**：不同对象有不同规则、某个局部过程要展开、
  几个决定各有完整依据。一行表或一段能讲完的对象放在二级下面；父级给共同背景或总览，
  子级只展开差异——父级已经列了完整明细表，就不再逐行建子节。
- **完整业务过程与当前特性功能分别说明**：业务过程讲需求怎样推进、在哪里交接；
  功能说明展开当前特性承担的能力、动作、状态与分支。
- **正常受限结果与真正异常分开说明**——混在一起，读者分不清哪些要处理、哪些是设计如此。
- 接口、字段、错误码、配置、事件和追溯信息**必须保留，但不能打断面向人的主叙述**：
  它们的落点是附录。
- 验收按真实业务场景或结果组织，**每个原始验收编号独立保留**，并给可观察的通过条件。
- Story 只表达**已经成立**的需求和决定；未确认的事项进决策件，正文里不替它下结论，
  也不生成「待确认事项」「评审导读」。
- 材料里的图**单向**：属于本需求的进正文，不属于的登记为什么不用，不引进来再解释。

### 形式按内容的关系选

| 内容的关系 | 形态 |
|---|---|
| 一组对象各有几个固定属性、要逐项比对 | 表 |
| 先后与分支 | 流程图 |
| 一个对象的状态与转移 | 状态图 |
| 跨方的调用与返回、次序本身要审 | 时序图或泳道 |
| 对象之间的归属与引用 | 关系图 |
| 原因、取舍、一件事为什么这么定 | 叙述，结论先行 |
| 有真实先后的步骤 | 有序列表 |
| 材料里的界面 | 图引用 + 一句说清它画的是什么 |

**图讲关系、表讲属性、文字讲理由，三者互补**：同一件事选它最该待的那一章讲透，
别在两章各写一遍；已经讲透的，别处只交代它与本章问题的关系。**必要的重现不是重复**
——验收要能独立判，就得把关键条件与数值重现一遍，与正文一致即可。

**不以数量代替判断**：不用表格数、图数、段数、字数、参与方数、状态数决定形式或合格，
也不设填量目标。简单内容短写，复杂内容分层；一段里塞进好几件并列的事，读者只能整段重读，
这时**换形态比拆段有用**——并列的改列表、逐项比对的改表、有结构的画成图，
或者提一句结论放段首。

**源材料里是图的，到这里还得是图**：把流程图压成箭头文字是降级——读者要的是那张图
一眼看出的结构，文字复述做不到。**表改成叙述看转得完不完整**：结构、触发条件、单位、
例外有任何一样在文字里落不下来，那是有损转换，留着表；都落得下来、读起来还更顺，就转。

**机器只核这一章的最小必要结构**：章节合同点名要定位的那几个小节在不在、那几张表在不在
（按最低锚列认，列名可以按本需求换说法、可以加列）、业务流程章有没有图。其余一概不核：
小节怎么切、按业务起的节名、行数、措辞、段落多长。**内容讲清没有由读者视角的语义审查判**，
不是数出来的。

## 二、动笔前：先设计表达

写一份 Story 是两种工作，先后做，不换人也不换上下文：

| | **设计表达**（这一节） | **完成表达**（第三节） |
|---|---|---|
| 产出 | `AR/story-src/story-template.md` | 章草稿与 `AR/story.md` |
| 这一步决定 | 章节怎么组织、每处讲什么、用什么形式承载、解释什么关系、依据在哪 | 图里的角色与分支、表格的列与行、列表的项目、正文怎么讲成立 |
| 这一步不定 | 正文答案、图的节点全集、表格的列、还没确认的业务结论 | 不把设计里的描述抄成正文，也不丢掉它要解释的关系；设计错了不照错写 |

分工是这样的：**本章要回答什么、主要职责是什么，在草稿开头**（`skeleton` 按章节合同渲染）；
**成文要用的当前输入**——材料里的图与登记命令、系统设计与 Spec 里的图——在
`story-build skeleton` 的输出里；**知识判断、词表与验收落点**在本阶段任务包里
（`node doc/extensions/hooks/spec/author.mjs --feature <名>`）；**方法在本页**。

动笔前读完：材料清单列的每一份材料、需求分析 `init-analysis.md` 的来源初筛、`spec.md`、
`decisions.json`、有会议材料时的 `doc-refresh.md`、skeleton 给出的当前输入。然后写
`AR/story-src/story-template.md`（skeleton 建好了空壳），两部分：

| 部分 | 写什么 |
|---|---|
| `## 阅读主线` | 本需求最容易被误解的对象与关系是什么、读者先理解哪一件才能理解后文；简短点出依据在哪、哪些未决限制后文。不是再写一份 Spec 摘要，也不按十章重述目录 |
| `## 骨架` | 每章一个 `### <章 ID>`（空壳里已列好），下面是这一章正文将要有的小节，照下表写 |

骨架每一行的写法，脚本按它铺草稿、按它核提交：

| 写法 | 意思 | 脚本怎么用 |
|---|---|---|
| `- 本章主线：…`、`- 答：…`、`- 依据：…`、`- 描述：…` 这类说明行 | 这一章或这一节要解决读者的什么理解问题、依据在哪（文件加标题；会议结果写 `doc-refresh.md` 的话题标题，要指原话就写 `meetings/<主名>/<版本>/raw.md:L<起>-L<止>`）、要解释的关系与先后、受哪些未决限制 | 铺进草稿成为指引行，提交时剥掉 |
| `#### 标题` | 正文里的一个 `###` 小节，标题原样用 | 草稿里建好这一节；提交时正文要有同名的一节 |
| `##### 标题` | 挂在上一个 `####` 下面，正文里的一个 `####` 小节 | 同上；核的时候先定位父节，别的父节下的同名子节顶替不了 |
| `- 待核：…` | 写骨架时还没解决的问题 | 进十章齐后的回看清单 |
| `形式：<类型>` | 这一处用什么承载。类型只有这几个：`表格`、`有序列表`、`无序列表`、`叙述`，或一种图——`图`（任一种）与点名的图种（流程图、时序图、状态图、类图等）。一处要几种就写几行 | 表格只核那个位置真有一张表（**列不由它定**）；列表核有真的列表项，不数条目；点名的图种正文只认那一种，别的图顶替不了；叙述只进草稿指引 |
| `- 描述：…` | 紧跟在 `形式：` 后面：这个形式要表达的对象、关系与边界 | 铺进草稿成为指引行；写得好不好由审查判 |
| `- 不涉及：<理由>` | 这一章不涉及：只写这一行，不留小节与形式 | 草稿里只放「本需求不涉及。」 |

一个中性的例子（局部，不是十章模板）：

```markdown
#### 受理协作
形式：时序图
- 描述：用时序图说明发起方、受理方与处理方的调用、返回及失败责任
- 依据：当前系统设计的受理流程
#### 结果与后续
形式：表格
- 描述：把各种处理结果与用户下一步对照起来，列在写章时按实际内容定
- 待核：结果未知时能否再次提交；没有结论就只写当前边界
```

不为时序图预列参与方，不为表格预定列——那是下一步的事，材料有缺口时更不能为了填满结构造答案。
**形式要单起一行**：写成 `- 形式：…` 的说明行脚本不接管，正文也就没人核。

**骨架写的是要回答的问题，不是答案。** 它的完成条件是：作者据它能直接展开这一节，不必重新猜
这一节为什么存在——不是每节都填满固定字段。它开放地安排理解任务，不替 Plan 提前选存储、接口、
时限或补偿；图要说清它解释的范围与由谁承接，不笼统声称一张图覆盖所有分支。
对照来源初筛与原文写：初筛登记的作用与疑点，已经解决的反映到骨架里，没解决的写成 `- 待核：`
或指向决策登记；原文里还有初筛漏掉的有效内容，一并安排进去。

**骨架是最小集合，不是上限**：已确认的业务结论照它写；它列出的问题，成品里要讲清或写明边界；
骨架没列的有效内容照样写进正文，多出小节、多出表图都合法。写作中要改它（含删掉某一节）按第三节办。
**它不是新的业务事实源**：业务结论变了回 Spec 或 `decisions.json`，再改本轮在用的骨架；
骨架里只引用当前结论，不把 Spec 整份抄进来。
**骨架写错了，正文也不照错写**：当前事实来自原材料与有效决定，「正文符合骨架」不代替正确性。

写好之后再跑一次 skeleton：设计读得了，它把骨架铺进还没动过的草稿、给出第一章的写作动作；读不了，
它说清缺在哪。`chapter` 提交前也核一遍设计。成文登记时写作设计与决策登记一起冻结，登记之后要改先
`story_flow.py reopen`。

**叙述不落附录**。附录是查阅件：读者顺着正文读下来要能读懂这件事，把它塞进附录等于让它
从阅读路径上消失。附录只有那五节，多出来的小节即违规；节里除了投影出来的机器区，
还可以有**理解契约必需的说明**——单位、格式样例、一句这一节给评审者看什么。
它不承担第二份字段表或第二份规则。

## 三、照骨架写一章：完成表达

这一步决定的是内容：图里有哪些角色、哪几条边与分支，表格用哪几列、几行，列表列哪些项目，
正文怎么把这一节要解释的关系讲成立。形式在设计那一步定了，**内容在这里定**。

每章的输入就这几样：

| 输入 | 拿它做什么 |
|---|---|
| 材料里与这一章有关的部分 | 这一章要讲的事实。材料整份在你手上，按读者在这一章会问什么去取 |
| 本章草稿（`AR/story-src/drafts/NN-<章名>.md`） | 骨架已铺在里面：本章的小节标题、每节要答的问题与描述、选定形式的指引（要一张表/一个列表/哪种图）；还有读者问题与主要职责、从 spec 打的底、提交命令 |
| 当前 `story.md` 里已写的章 | 先回答「这一章相对已写内容要增加什么」；已在别章讲透的只交代关系 |
| skeleton 输出的当前输入 | 这一轮有哪几张图、每张的登记命令、上游图的位置 |
| 本阶段任务包 | 知识判断、词表与验收落点 |
| 本页的方法与第六节的四条红线 | 形式怎么选、归档件自包含 |

**照骨架写：先答骨架里的问题，再补骨架没列的。** 读草稿里的骨架、骨架指到的原文与已写的章，
先想清这一章相对已写内容要增加什么独有解释，再动笔；骨架里的关系要在正文里讲成立，不是换个说法
列一遍。已经成立的决定照着用，不在每章重判同一件业务。
范围章讲责任边界，方案讲机制与选择，流程讲跨能力的关系，功能讲能力内部的行为；
验收要独立判所需的条件与数值照样重现。

**写着写着认识变了**：发现更好的讲法或新的关系，就同时改写作设计里受影响的骨架与草稿，接着写，
不用问人（要删骨架里的一节，先删那一行再提交）；改变了业务规则回 Spec 或 `decisions.json` 改，
设计里只引用当前结论。
**实质调整记一条**：已经用来写章的安排被你改了——换掉某处的形式、合并或取消一节、放弃原来要解释的
那件事——在 `AR/story-src/template-adjustments.md` 里按「章 ID / 原小节」写一条：原安排、实际调整、
原因、依据指到哪份原文。一个调整一条，返修同一处就更新那一条；正常填列、画节点、补充有依据的解释
不是调整，不记。没有调整就不建这个文件。它是解释材料，不是改需求的授权。发现来源互相矛盾时，
你可以分析、推荐，但改变明确的验收或范围口径要有人的裁决：没拿到裁决就登记 `open`，保留原文与冲突，
正文写清受影响的待决边界——不为了让两份材料一致而选一边、改验收再写成 `settled`。
术语确认不等于批准了业务改动。
未决的事可以写成明确的边界，但依赖它的行为不能同时写成已定——一个未决也不会让其它确定的内容跟着不能写。

**图从要解释的关系出发**：上游的图可以直接用、合并或改画（保留来源标记）；总览覆盖主线与关键分支
的去向，复杂局部在对应小节展开并接回主线。上游只有一张简单图时，照搬它不等于讲清了；另画了图，
也不省掉那张图原本要讲的事。跨方的调用与返回、结果归谁、失败后谁补救是理解重点时，用时序图或确能
讲清同样关系的形式；流程图讲条件分支，状态图讲对象的生命周期，换了形式不能把调用方、被调方、返回
与失败后的责任丢掉——节点同名、带着来源标记不等于关系还在。不用时序图时，写作设计里说清替代形式
怎样承接这些关系。总览与局部可以互补，不必合成一张大图，也不按参与方个数加图。没有页面的业务按对象、调用方、作业与数据生命周期讲，不硬造页面。

**写给人读，不是把材料列成条目。** 材料是**素材**不是提纲：把与这一章有关的部分组织成
连贯的叙述，该合并的合并，该排序的排序。材料里一句对应正文一个 bullet，那是清单不是叙述。
**表格转成散文时每一列都要有落点**——最容易丢的正是非首列：触发条件、字段名、编号。

**上游画过的图搬进来**：系统设计与 spec 里的图原样放进讲对应内容的那一节，围栏第一行保留
skeleton 输出给的那行来源标记——身份是它在上游的位置，你不用给图起名。**只搬图，不搬文字**：
图周围的话自己写。可以等效合并或按评审者要看的过程改画，改的是画法、讲的是同一件事。
少一张，缺的不是「一张图」，是那张图讲的那件事——先找内容，再搬图。

**材料里的每张图都要有去处**：属于本需求的，在讲它的那一章引用，图前一句承接说清它画的是
什么；不属于本需求的（旧版页面、同页面的另一张截图、同类产品的参考稿、别的部件或别的单
的页面），跑 skeleton 输出里给的那条登记命令写明为什么不用，登记完就不必在正文里交代它。
引用时用它在仓内的**既有落盘路径**：不复制文件、不改名、不另建图片目录、不在归档目录下
造副本——副本没人维护，改了名读者也认不出它就是原来那张。一张图只引一次。
**附录的材料清单不列图**，那一节回答「据哪几份材料写成」。

**验收按材料里的编号逐条给可观察条件**，每个原始编号独立一行；需要细分时沿用上游的编号
体系顺延，**不自造后缀**——编号是评审人和上游对齐用的，自造的他那边查不到。

**激活规约条目一条一行**：附录的「规约判定」小节成表（规约 / 编号 / 命中·不命中·整域不适用
/ 依据）。判「不命中」也要有行、也要依据；整域不适用时给该域一行即可。这张表里写编号是
允许的——主叙事里仍写中文规约名。

**空章**：确实不涉及的章，正文恰好写「本需求不涉及。」一句。不删标题（读者会以为漏写了），
不留空节（分不清「没写」与「不涉及」）。

写完这一章就落盘，再写下一章。**落盘只有这一条路，不要自己去改 `AR/story.md`**——
命令替换的区间就是那一章，别处一个字节都碰不到。正文走文件不走命令行参数：它带换行、
引号与 markdown，任何 shell 都会再解析一遍。中断之后从哪续也由它回答：每次落盘都报还剩
哪几章带着待写标记，**已经写好的章不要重写**。命令在草稿开头，照它给的那一行跑——
它是按本工程的命令行（PowerShell）引好的，换别的 shell 要自己核引用规则。

### 决策登记

**什么算一条议题**：review 是**判断的台账**——已决策的呈现结果供评审人过目，不确定、
矛盾、错误的要人评估。准入判据只有一条：**评审人对这条表态「不同意」，会有产物要改**；
表态没有后果的不占表态位，材料直接给定、没有判断参与的纯事实复述不进。从材料到方案之间
凡发生过一次判断、或还等着人判断的，每处一条——材料没说而本轮定的、材料打架的（定源要有人的裁决）、
材料有错或与工程现状矛盾的、材料明说未决的、需求做不到而降级承载的、关键取舍，以及跨方
依赖的确认点（对方表态变了产物就要改）。已定的登记 `settled`（正文落点是关键取舍），
未定的登记 `open`（去处是评审记录），没有第三种去处。
**把材料里没有的选择写死进正文或附录，就是漏登记。**

**再问这件事该谁定**：改变业务口径或对外承诺的，进评审记录；换一个实现方案结论就会变、又不改对外承诺的
（存储介质、内部结构、用哪个组件），是实现选型，**不登记为议题**——已定的写进 Spec §9 对应那一行，
没定的在 §9 那一行写「由 plan 定」，交给 plan。判不准时问：评审人不表态，这件事能不能上线。
「已定事项」只收来源已定或人已裁、并有取舍位置的；不为填满它造议题，一条都没有时回看清单再问一遍
「材料没说而本轮定的、材料打架时选定的一边」有没有漏登记。

议题从哪里来：十章齐后的回看清单与骨架每一节的关键主张，按第四节的两问撞出来。

**已定的决策写进它的取舍位置**：取舍的理由材料里本来就没有，是起草时判出来的，
所以它只能从 `decisions.json` 里来——`settled` 的那些各写一处取舍：有真实备选的写「选了什么 /
否了什么 / 为什么被否的不行」，只有一条合理路径的直接写依据，不为显得有取舍编备选。
`open` 的议题在正文里写成**受影响处的未决边界**：说清哪一段还没定、依赖它的行为因此写到哪为止，
不把依赖它的做法写成已定。「确认继续保持未定」本身可以是一条已定的处置决定，但那说的是处置，
不是业务已经解决；挂着的选项也不暗示某一种未获批准的实现。

**先定人在评审时要做什么**，写进 `review_mode`——它决定评审记录给评审人什么填写位，
与 `status`（决定成立没有）各管各的：待定的事可能只是请人确认一个缺失的事实，已定的事也可能要人
复核当初的选择。按这件事实际要人做的判断选，不按 status 猜。

**澄清正文**，小标题写成加粗段首（不另起标题行——议题在评审记录里已有三级层次）：

| review_mode | 正文 |
|---|---|
| `choice`：人从几个方案里选一个 | **决策点**（要定什么、影响什么）／**依据**（材料怎么说、还有什么分歧）／**可选的做法**／**建议**／**理由** |
| `confirm`：人复核一个已有结论 | **决策点**／**依据**／**结论与影响**（定了什么、对交付意味着什么）——没有真实备选就不造列表 |

**可选的做法**是真正的有序列表，一个选项一项，每项写成「做法——选它会怎样」：后果说清范围、行为、
验收、交付哪一项会变，并有可指认的事实支撑；写不出后果差别的不是真取舍，改成 `confirm` 或事实陈述。
评审人按这个编号选，别把几个选项塞进一段。**建议**先写「选择方案 N（名称）」，再写**理由**与要接受的代价；
信息确实不够、推荐不出来时，写明缺哪个事实，不为了格式硬选一个，也不编凑数的备选。
推荐不是人已经选了：人没表态之前，它仍是 `open`。

一个中性的 `choice` 正文：

```markdown
**决策点**：受理超时后由谁发起重试，影响用户会不会被重复扣款。

**依据**：Spec 功能说明写「超时后重新提交」，接口说明第 3 节只写了超时按未受理处理，没有说谁负责再次提交。

**可选的做法**：

1. 客户端自动重试——用户无感；前提是受理方保证同一请求只处理一次，验收要加一条「重复提交不重复扣款」。
2. 提示用户手动重试——不依赖受理方去重；用户多一步操作，失败提示与重试入口进功能说明。

**建议**：选择方案 2（提示用户手动重试）。

**理由**：受理方目前没有去重承诺，方案 1 的前提不成立。
```

**「依据」写撞点**：这一条是在哪撞出来的——story 哪一章或 Spec 哪一节的哪个主张，与哪份材料的
哪一节、哪条工程事实或规约相撞。「根据材料和工程现状」这种没有指向的话不算依据：评审人没法复核，
只能凭信任盖章。标题写成陈述句：已定的陈述结论，待定的陈述事项；
写成议题名（「入口问题」）评审人看不出要表什么态。决策结论用人话写，不写工具的档位与
判据名——澄清正文会原样进评审记录，评审者读到的是本需求的事。

**登记时选 `category`**：从下面十一类里挑一个，它决定这条在评审记录里成哪一节。
**每类第三列是撞的方向，不是遍历顺序**：议题从回看清单与骨架里撞出来，不是对着这张表过一遍找出来的；
机器只判类别在不在词表里，这张表不是配额。

| 类型 | 读到什么就检查 | 撞的方向 |
|---|---|---|
| 范围与拆分 | 多段体验、兄弟单迹象、「不做什么」 | 一张单做完还是拆？和谁交接？ |
| 流程顺序与准入 | 步骤先后、资格门槛 | 产品旅程的顺序与现有实现冲突时按哪个？资格挡在哪一步？ |
| 入口与管控 | 新入口或新页面、运营可配置 | 入口放哪？要不要开关？默认值是什么？关掉之后存量怎么办？ |
| 规则与数值 | 阈值、上限、时限、次数 | 材料给了吗？两份材料打架按哪个？没给的谁来定？ |
| 数据与缓存 | 状态、记录、草稿、列表 | 存不存？存哪、存多久？跟账号什么关系？清除之后怎样？ |
| 界面与还原度 | 参考图、没有稿的页面 | 照图到什么程度？没稿的部分按什么做？ |
| 异常与受限体验 | 失败、超时、超限、停用分支 | 每条分支用户看到什么、怎么恢复？受限算不算异常？ |
| 依赖与可用性 | 需求用到的能力、接口、字段 | 工程里现在有吗？没有是近似、模拟还是等待？ |
| 安全隐私与合规落地 | 敏感数据、转授能力、激活规约 | 出口都脱敏了吗？能不能转给第三人？这条规约落到哪、做到什么程度？ |
| 交付顺序与协同 | 多方联调、分阶段开放 | 谁先谁后？模拟什么时候切真实？对方排期变了影响什么？ |
| 验收口径 | 写验收时 | 这一条的通过条件是上游给的还是本轮定的？可观察吗？ |

## 四、回看：十章齐后逐条处置回看清单

逐章写是十次各自有界的小任务，代价是没有一次拿成稿对着来源从头核。十章齐了，**先拿有效的原材料与
当前决定查一遍关键关系有没有漏**——条件、行为、责任、结果、例外与未决，在受影响的位置是不是一致；
再用清单定位疑点。要核的对象是当前的 `spec.md`、`AR/story.md`（含附录投影区）、
`AR/review.md` 与 `decisions.json`；有会议材料时还有 `doc-refresh.md` 与它所引的原话。
还没有 Plan 的阶段不预造 Plan。

`skeleton` 与最后一次 `chapter` 的输出里给出**回看清单**，由脚本从来源枚举——它帮你定位问题，
不是「只审已登记的这几条」的上限：

| 清单里的一类 | 从哪来 | 要确认的去向 |
|---|---|---|
| 初筛疑点 | 需求分析 ⑥ 里「还要核实的矛盾或缺口」非空的行 | 正文讲清、登记 `open`，或有依据地判不适用 |
| 未决 | `decisions.json` 里 `open` 的条目 | 正文里依赖它的行为没有写成已定 |
| 已定取舍 | `settled` 的条目 | 取舍落在哪一章，依据写了没有 |
| 骨架待核 | 骨架里的 `- 待核：` 行 | 在正文或决策登记里有去向 |
| 图 | 正文里每张图所在的节 | 图前声称覆盖的去向，图里有没有 |

对清单里每一条、以及骨架每一节的关键主张，**撞两问**：

1. **这句话材料里有吗？** 有，是搬运，进第二问；没有但说得出依据（工程事实、规约、上游口径），它是决策点，
   依据就是背景；没有也说不出依据，是编的，删掉。
2. **材料给的靠得住吗？** 拿它去撞：更晚的输入（系统设计晚于产品需求、界面稿、当前会议结果）、材料之间、
   工程事实、规约、材料自己声明的目标。「不合适」只认四种：工程没这能力、与既有实现冲突、撞规约、
   材料的目标与做法对不上。「我觉得有更好的设计」不算。

撞出来的东西只有四个出口，**处置回真源，不写台账**：

| 发现 | 出口 |
|---|---|
| 真实未决、跨章矛盾、Spec 与 story 对不上而要人裁 | 登记 `open`，依据写撞点；正文只写受影响的待决边界 |
| 重要的已定取舍正文有依据、登记表里没有 | 补登 `settled`，引既有结论与依据 |
| 已有依据能定的普通说明 | 沿用，不登记 |
| 编造、误读、前后不一致 | 回错误所属的真源改：story 章改草稿再 `chapter` 提交；Spec 改 `spec.md`；验收改 `acceptance.yaml`；知识判断改 `knowledge-use.yaml` 再 render；骨架错了改骨架 |

**材料自己打架时不要选一边照抄**——改变明确验收或范围口径的，有人的裁决才写 `settled`；没有就登记 `open`。
流程、功能说明、异常与恢复、验收对着读，同一种情况四处说的必须是同一件事。同一件事在全篇出现几处，
先问各处还回答了什么别处没回答的：完整复述（后一处没有独有用途）留在最该讲它的位置、其余改成一句承接；
互补（图讲关系、表讲属性、文字讲理由）与验收独立判所必需的条件与数值重现，两处都留着。
每张表前有一句引导，图前那一句说清它画的是什么。

**没有问题不制造改动**，不写「已核对」，也不凑改动数。每一条的去向由独立审查拿同一张清单复核，不由你自报。
每次提交都会把这一章能确定的那几条先核一遍，判不过时盘上什么都不变；**不重新输出整篇**。
改完想再看一次清单就再跑 `skeleton`；全篇改完再跑一次 `check`：跨章的判据（章序、验收编号全集、上游图的落点）
要跟着重核。

## 五、十章各自怎么组织

下面每章四五行，说的是这一章的组织方式，不是又一份配额；通用规则见第一节。

### 背景

因果叙述是默认：现在怎么做 → 哪里出问题 → 影响谁、对业务意味着什么 → 本需求改什么、
什么算成功。多个现状或几个可比较的目标才成表（「场景/现状/问题/影响」或
「现状/目标/口径/依据」），拿不到的值写未知。本特性在完整需求里承担哪一段写在这里，
分工细节归范围。简单时不分节；三级只在某个问题场景或某个目标的口径要独立解释时出现。

### 术语

词义表是默认，草稿里已按规格件的术语映射表打好起始行：改措辞、往下加，纯技术词可以删。
真有会被读混的概念才另做对照（概念/差别/判别条件）——判别条件是读者拿去区分的那一句。
真有层次或包含关系才配一张小图。三级只在一组概念需要独立解释时出现。

### 范围

责任边界是主线：先分清「整个需求不做」与「本特性不负责、但别人要做」。
本特性与其它责任方的分工要讲清楚——多对象时用矩阵（能力/本特性责任/其他责任方/边界）；
依赖成表（能力/提供方/使用边界/是否阻塞）。真有兄弟单据时讲清交接：交接什么、谁先谁后、
按什么对齐，它是说明，不要求成表。运行时怎么协作归业务方案与流程。

### 业务方案

参与方与分工讲全：每一方的输入、输出、责任、失败影响，默认成表，关系复杂时配协作图
或数据流图。业务结果以谁为准、重要业务规则写清楚，条件组合用决策表。
真有备选才做对照（选项/收益/代价/理由），只有一条路就写依据，不为显得有取舍编备选。
全篇的风险只在这一章成表：触发条件、影响、已有控制。

### 业务流程

章前部一张总览图，覆盖主路径与全部分支去向（开关、登录态、风控、网络、回调这些）与
交接点；放在读者一进这一章就找得到的位置——章首那段或一个「总览」小节都行。
多方调用用时序或泳道，并行用流程图标出同步点，关键对象的推进用状态图。
每条分支讲清触发、处理、结果、后续；局部复杂时在它自己的小节里展开，并说清接在总览哪一步。
上游画过的那张讲的是接口与分支：恰好就是这条业务的过程就直接搬过来，不是就自己画一张——
**不为了与上游不同而刻意画不同**，判的是评审者看不看得懂这条业务。
能力内部规则归功能说明，详细恢复归异常——异常在总览里要有去向。

### 功能说明

按能力或有业务意义的场景分节，一节讲一件事：什么输入与条件下工作、按什么规则处理、
数据与状态怎么变、结果是什么、谁看得见。输入与约束用表，条件组合用决策表，
对象归属用关系图，生命周期用状态图，操作用步骤。
有页面就引材料里的界面图并接一句说清它画的是什么；**没有页面就写调用方、后台作业或
管理动作**，不套页面状态表。受限时怎样继续写在这里，真正的异常归下一章。

### 异常与恢复

两类分开写：设计内的受限结果（条件/可观察结果/设计意图/继续条件）与真正的异常
（异常/影响/检测或响应/处理/恢复）。列名对准真实观察者——用户、调用方、后台任务、运维，
谁看得见就写他看见什么。确实没有某一类，说明依据，不留空节也不硬凑。
多步补偿或跨方恢复在它自己的小节里用步骤、流程或时序展开。

### 验收

按真实业务目标分组；「编号/场景与前置/可观察通过条件/主责」那张表的编号一条不并、
不自造后缀。可观察的通过条件是读者拿去判的依据，为此重现关键条件与数值是必要的，
与正文一致就不算重复。复杂输入组合补参数矩阵或预期样例。
质量指标写条件、单位、来源（上游约束还是工程设定）；没有真实测量就不画结果图。

### 交付与上线

上线路径用有序步骤或依赖图：真实依赖接入、相关特性联调、开放顺序。
可独立控制的对象按对象成表（对象/触发/范围/动作/存量与在途影响/恢复条件）；版本或数据
格式差异用兼容矩阵。回退措施可以多套，每项开关与恢复能力要有依据——**关闭入口不等于
撤销业务或恢复数据**，不可逆的结果明说。「交付物」那一节要有一张表：交付物、给谁、
做什么用、什么时候要——评审者要看的是谁在等、拿去做什么、缺了会卡谁；交付时机写在表里
或上线路径里都行，但要写得出来。

### 附录

五节固定，每节开头一句「这一节给评审者看什么」；确实不涉及的写「不涉及：<依据>」一行，
不删标题。接口、数据·配置与事件、改动边界、规约判定四节由脚本从真源投影，你改的是真源；
材料清单里「这份材料贡献了什么」归你。理解契约必需的单位说明与格式样例写在投影之外的
作者区，不维护第二份字段表或第二份规则。决定行为理解的关系图放在正文讲它的那一节，
不搬进附录。

## 六、归档件自包含与交回前

这份文档会被上传到需求系统，读者手上没有这个仓库：

1. 不写仓内路径（需求目录、模块目录名）——读者打不开。**唯一的例外是附录材料清单里的
   原文链接**：那一行本来就是给读者定位原件用的；
2. 不写裸文件名当引用（「见某某文件」）——读者不知道是哪一份；
3. 主叙事不写内部规则编号与仓内标识——改写中文业务名与中文规约名；它们的落点是附录；
4. 不写客户端语境的禁用词——词表与「在哪不算」（整章豁免、决策类别豁免）都在本次任务包，
   `story-build check` 按同一份判。订单、数据、状态的撤销与恢复是正常业务语言，照实写。

**需求不是演示。** 工程当前可能用本地或模拟的方式承载某些能力（云侧还没接、外部服务先用
本地实现顶着），那是交付前的工程状态，不是这个需求的定性。归档件里不得把需求或它的实现
说成演示、示例、样例。模拟承载照实写：**「本地模拟承载，真实服务接入后替换」**。
这一条不设词表——「演示」是常用词，机器拦它会误伤；它由读者视角的语义审查逐问接。

交回前只做一件事：跑 `story_flow.py story --feature <名>`，按它的输出走，不写自评。
它自己会重编号、重投影、重跑 `check`，全过才登记成文。报错说的是**这一类事实的落点长
什么样**，不是一张待抄的字面清单——照着它指的位置去写那件事，不要把报错里的名字原样
搬进附录。

### 交回前自检（两条，只有你看）

**一、独立可读。** 评审者手里只有这份叙事件与《决策与评审记录》——需求规格不随归档。
读完能不能说出：要做什么、为什么这么做、动了哪些存量、哪里可能出问题？出现只有读过规格
才懂的指代（模块内部结构、函数签名、仓内路径、「现状无某某封装」这类扫描结论），就是不达标。
**叙述是你自己的**：顺序服务于人的理解——先为什么 → 再是什么 → 再怎么做 → 再哪里会坏 →
最后怎么算做对。原封不动照搬规格的章节顺序与表格排布即不达标：那说明只做了搬运，没做改写。

**二、有取舍。** 方案取舍与设计选择的每一行都要写清依据；有真实备选的，写清「选了什么、否了什么、
为什么不是另一种」。规格只有结论，story 存在的意义就是补上理由——只复述效果的不算理由：说「因为中断后
可恢复所以存半小时」等于说「做了它因为想要它」，没有回答为什么不是十分钟、为什么不用内存。
**只有一条合理路径时直接写它的依据**，不为显得有取舍编一个备选。
上游已定的方案照实标「上游已定」，不得包装成本部件的取舍——那会让评审者以为这里有得商量。
