# story 成文：先设计表达，再按章写，最后回看

> 读者：spec 阶段写 `AR/story.md` 的作者。时机：`story-build skeleton` 之后动笔前读一遍，写章、登记决策、回看时回到对应一节。

读者是评审人：他们没参与开发，只有这一份文档，要据此判断
**这件事想清楚了没有、做对了没有**。他不看代码、不翻仓库、不知道内部编号。

先写本需求的**写作设计**（第二节）：第一次读的人按什么顺序理解这件事、正文要有哪些小节、
每节要回答什么、依据在哪。然后成文分两步：**一章一章照骨架写**（每章经 `chapter` 命令原子落盘），
**十章齐了按回看清单逐条处置一次**。逐章写每步输出有界，断了知道从哪一章续。

**起手输入**：本章要回答什么、主要职责是什么在每章草稿开头（按章节合同渲染）；
这一轮的图、登记命令与上游图的位置在 `story-build skeleton` 的输出里；
知识判断、词表与验收落点在本阶段任务包（`node doc/extensions/hooks/spec/author.mjs --feature <名>`）；
方法在本页。动笔前读完：材料清单列的每一份材料、需求分析 `init-analysis.md` 的来源初筛、`spec.md`、
`decisions.json`、有会议材料时的 `doc-refresh.md`、skeleton 给出的当前输入。

## 一、写给这样的读者

这一节的每一条都是用户逐条定下的效果口径。
标「机器核」的有判据，其余**由读者视角的语义审查判**。

- 面向**第一次接触需求**的人类评审者，他无需先读规格、产品需求、系统设计或代码。
  按人的理解顺序讲：为什么做、涉及谁、怎样解决、业务如何推进、当前特性负责什么、哪里会失败、
  怎样验收、怎样交付。照搬规格的章节顺序与表格排布，说明只做了搬运没做改写。
- 标题用真实业务名，简短、准确概括下文；不用模板占位语、模型提问、自造词（「两单分工」「支线一」）、
  编号式与工程味命名。章节与小节编号、H1 的单号由登记时的 `number` 统一铺（机器核），你只写业务名。
- **三级只在下级内容值得独立定位时出现**：不同对象有不同规则、某个局部过程要展开、几个决定各有完整依据。
  一行表或一段能讲完的放在二级下面；父级已经列了完整明细表，就不再逐行建子节。
- 业务方案、业务流程、功能说明是全篇最详细的部分。完整业务过程（需求怎样推进、在哪里交接）与
  当前特性功能（能力、动作、状态与分支）分别说明。
- **正常受限结果与真正异常分开说明**。恢复类内容用「时机 / 方案 / 走向」这类短段引导，不写成一坨散文。
- 表前有一句引导、表后需要时一句收束；单元格不塞成压缩袋（一格里一串分号短语就是该拆了）。
- 接口、字段、错误码、配置、事件和追溯信息**必须保留，但不能打断主叙述**：主叙事零工程标识，
  它们落附录（机器核红线见第三节）。术语表不收空转定义，主叙事反复使用的概念必须进术语表。
- 验收按「要验的事」分组，不按来源分；**每个原始验收编号独立一行**（机器核）并给可观察的通过条件。
- 交付与上线要详细：上线路径、开关与兼容、回退设计及理由、交付物给谁做什么用、与兄弟单的上线顺序。
  **关闭入口不等于撤销业务或恢复数据**，不可逆的结果明说。
- 照抄产品原型的「文案要求」不单独成节，有价值的融进讲那个页面的表。
- Story 只表达**已经成立**的需求和决定；未确认的事项进决策件，正文里不替它下结论，
  也不生成「待确认事项」「评审导读」。
- 材料里的图**单向**：属于本需求的进正文，不属于的登记为什么不用，不引进来再解释。
- 附录每节开头一句「这一节给评审者看什么」；材料清单用列表，每行写来源、《文件名》、提供方与方式、
  内容贡献，并带原文的相对链接——这是全篇唯一允许出现仓内路径的地方。

### 形式按内容的关系选

| 内容的关系 | 形态 |
|---|---|
| 一组对象各有几个固定属性、要逐项比对 | 表 |
| 先后与分支 | 流程图 |
| 一个对象的状态与转移 | 状态图 |
| 跨方的调用与返回、次序本身要审 | 时序图或泳道 |
| 对象之间的归属与引用 | 关系图 |
| 原因、取舍、一件事为什么这么定 | 叙述，结论先行 |
| 有真实先后的步骤 | 有序列表 |
| 材料里的界面 | 图引用 + 一句说清它画的是什么 |

**图讲关系、表讲属性、文字讲理由，三者互补**：同一件事选它最该待的那一章讲透，已经讲透的，
别处只交代它与本章问题的关系。**必要的重现不是重复**——验收要能独立判，就得把关键条件与数值重现一遍。

**不以数量代替判断**：不用表格数、图数、段数、字数决定形式或合格，也不设填量目标。
一段里塞进好几件并列的事，**换形态比拆段有用**。

**源材料里是图的，到这里还得是图**：把流程图压成箭头文字是降级。**表改成叙述看转得完不完整**：
结构、触发条件、单位、例外有任何一样在文字里落不下来，那是有损转换，留着表；
表格转成散文时每一列都要有落点——最容易丢的是非首列：触发条件、字段名、编号。

**机器只核这一章的最小必要结构**：章节合同点名要定位的小节与表在不在（按最低锚列认，列名可换说法、可加列）、
业务流程章有没有图。小节怎么切、节名、行数、措辞一概不核，**内容讲清没有由语义审查判**。

## 二、动笔前：先设计表达

设计表达定章节怎么组织、每处讲什么、用什么形式承载、解释什么关系、依据在哪；
不定正文答案、图的节点全集、表格的列，也不定还没确认的业务结论——那些是第三节写章时的事。

写 `AR/story-src/story-template.md`（skeleton 建好了空壳），两部分：

| 部分 | 写什么 |
|---|---|
| `## 阅读主线` | 本需求最容易被误解的对象与关系是什么、读者先理解哪一件才能理解后文；简短点出依据在哪、哪些未决限制后文。不是再写一份 Spec 摘要，也不按十章重述目录 |
| `## 骨架` | 每章一个 `### <章 ID>`（空壳里已列好），下面是这一章正文将要有的小节，照下表写 |

骨架每一行的写法，脚本按它铺草稿、按它核提交：

| 写法 | 意思 | 脚本怎么用 |
|---|---|---|
| `- 本章主线：…`、`- 答：…`、`- 依据：…`、`- 描述：…` 这类说明行 | 这一章或这一节要解决读者的什么理解问题、依据在哪（文件加标题；会议结果写 `doc-refresh.md` 的话题标题，要指原话就写 `meetings/<主名>/<版本>/raw.md:L<起>-L<止>`）、要解释的关系与先后、受哪些未决限制 | 铺进草稿成为指引行，提交时剥掉 |
| `#### 标题` | 正文里的一个 `###` 小节，标题原样用 | 草稿里建好这一节；提交时正文要有同名的一节 |
| `##### 标题` | 挂在上一个 `####` 下面，正文里的一个 `####` 小节 | 同上；核的时候先定位父节，别的父节下的同名子节顶替不了 |
| `- 待核：…` | 写骨架时还没解决的问题 | 进十章齐后的回看清单 |
| `形式：<类型>` | 这一处用什么承载。类型只有这几个：`表格`、`有序列表`、`无序列表`、`叙述`，或一种图——`图`（任一种）与点名的图种（流程图、时序图、状态图、类图等）。一处要几种就写几行 | 表格只核那个位置真有一张表（**列不由它定**）；列表核有真的列表项，不数条目；点名的图种正文只认那一种；叙述只进草稿指引 |
| `- 描述：…` | 紧跟在 `形式：` 后面：这个形式要表达的对象、关系与边界 | 铺进草稿成为指引行；写得好不好由审查判 |
| `- 不涉及：<理由>` | 这一章不涉及：只写这一行，不留小节与形式 | 草稿里只放「本需求不涉及。」 |

一个中性的例子（局部，不是十章模板）：

```markdown
#### 受理协作
形式：时序图
- 描述：用时序图说明发起方、受理方与处理方的调用、返回及失败责任
- 依据：当前系统设计的受理流程
#### 结果与后续
形式：表格
- 描述：把各种处理结果与用户下一步对照起来，列在写章时按实际内容定
- 待核：结果未知时能否再次提交；没有结论就只写当前边界
```

不为时序图预列参与方，不为表格预定列。**形式要单起一行**：写成 `- 形式：…` 的说明行脚本不接管。

**骨架写的是要回答的问题，不是答案。** 完成条件是作者据它能直接展开这一节，不必重新猜这一节为什么存在。
不替 Plan 提前选存储、接口、时限或补偿；图要说清它解释的范围与由谁承接。
对照来源初筛与原文写：初筛登记的作用与疑点，已经解决的反映到骨架里，没解决的写成 `- 待核：`
或指向决策登记；原文里还有初筛漏掉的有效内容，一并安排进去。

**骨架是最小集合，不是上限**：它列出的问题，成品里要讲清或写明边界；骨架没列的有效内容照样写进正文，
多出小节、多出表图都合法。**它不是新的业务事实源**：业务结论变了回 Spec 或 `decisions.json`，
再改骨架；骨架写错了，正文也不照错写。

写好之后再跑一次 skeleton：设计读得了，它把骨架铺进还没动过的草稿、给出第一章的写作动作；读不了，
它说清缺在哪。成文登记时写作设计与决策登记一起冻结，登记之后要改先 `story_flow.py reopen`。

## 三、照骨架写一章：完成表达

这一步定内容：图里有哪些角色、哪几条边与分支，表格用哪几列、几行，列表列哪些项目。
本章草稿（`AR/story-src/drafts/NN-<章名>.md`）里骨架已铺在里面：小节标题、每节要答的问题与描述、
选定形式的指引，以及读者问题、主要职责和提交命令。

**写作单位是一条业务关系，不是一章**：先从当前来源与决定里认出一条完整的关系——条件、行为、责任、结果、
例外、未决——把它讲完整的那一章和需要重现它的章（流程、功能、异常、验收常常共用一条）一起写或改，
再逐章提交。写本章前先读已写的章里与本章共用的关系：这一章相对已写内容要增加什么独有解释，
已在别章讲透的只交代关系。

**照骨架写：先答骨架里的问题，再补骨架没列的。** 骨架里的关系要在正文里讲成立，不是换个说法列一遍。
已经成立的决定照着用，不在每章重判同一件业务。范围章讲责任边界，方案讲机制与选择，流程讲跨能力的关系，
功能讲能力内部的行为；验收要独立判所需的条件与数值照样重现。

**写着写着认识变了**：发现更好的讲法或新的关系，就同时改写作设计里受影响的骨架与草稿，接着写，
不用问人（要删骨架里的一节，先删那一行再提交）；改变了业务规则回 Spec 或 `decisions.json` 改，
设计里只引用当前结论。已经用来写章的安排被你实质改了（换形式、合并或取消一节、放弃原来要解释的事），
在 `AR/story-src/template-adjustments.md` 按「章 ID / 原小节」记一条：原安排、实际调整、原因、依据；
正常填列、画节点不记，没有调整就不建这个文件。
来源互相矛盾时可以分析、推荐，但改变明确的验收或范围口径要有人的裁决：没拿到就登记 `open`，
正文写清受影响的待决边界——不为了让两份材料一致而选一边。术语确认不等于批准了业务改动。
未决的事可以写成明确的边界，但依赖它的行为不能同时写成已定——一个未决也不会让其它确定的内容跟着不能写。

**图从要解释的关系出发**：上游的图可以直接用、合并或改画（保留来源标记）。业务流程章前部一张总览图，
覆盖主路径与全部分支去向（开关、登录态、风控、网络、回调这些）与交接点，复杂局部在对应小节展开并接回主线。
上游画过的那张恰好就是这条业务的过程就直接搬，不是就自己画——**不为了与上游不同而刻意画不同**；
上游只有一张简单图时，照搬它不等于讲清了。跨方的调用与返回、结果归谁、失败后谁补救是理解重点时，
用时序图或确能讲清同样关系的形式；换了形式不能把调用方、被调方、返回与失败后的责任丢掉。
总览与局部可以互补，不必合成一张大图，也不按参与方个数加图。
决定行为理解的关系图放在正文讲它的那一节，不搬进附录。
没有页面的业务按调用方、后台作业与数据生命周期讲，不硬造页面、不套页面状态表。

**写给人读，不是把材料列成条目。** 材料是素材不是提纲：把与这一章有关的部分组织成连贯的叙述。

**上游画过的图搬进来**：系统设计与 spec 里的图原样放进讲对应内容的那一节，围栏第一行保留
skeleton 输出给的那行来源标记。**只搬图，不搬文字**：图周围的话自己写。少一张，缺的不是「一张图」，
是那张图讲的那件事（机器核落点）。

**材料里的每张图都要有去处**：属于本需求的，在讲它的那一章引用，图前一句承接说清它画的是什么；
不属于本需求的（旧版页面、同页面的另一张截图、同类产品的参考稿、别的部件或别的单的页面），
跑 skeleton 输出里给的那条登记命令写明为什么不用。引用时用它在仓内的**既有落盘路径**：
不复制、不改名、不另建图片目录。一张图只引一次。**附录的材料清单不列图**，那一节回答「据哪几份材料写成」。

**验收按材料里的编号逐条给可观察条件**；需要细分时沿用上游的编号体系顺延，**不自造后缀**。
**激活规约条目一条一行**：附录「规约判定」成表（规约 / 编号 / 命中·不命中·整域不适用 / 依据），
判「不命中」也要有行。**空章**：正文恰好写「本需求不涉及。」一句，不删标题、不留空节（机器核）。

**归档件自包含（四条红线，机器核）**——这份文档会上传到需求系统，读者手上没有这个仓库：

1. 不写仓内路径（需求目录、模块目录名）；唯一例外是附录材料清单里的原文链接；
2. 不写裸文件名当引用（「见某某文件」）；
3. 主叙事不写内部规则编号与仓内标识，改写中文业务名与中文规约名，它们的落点是附录；
4. 不写客户端语境的禁用词——词表与「在哪不算」都在本次任务包，`story-build check` 按同一份判。

**需求不是演示**：工程当前用本地或模拟方式承载的能力，照实写「本地模拟承载，真实服务接入后替换」，
不把需求或它的实现说成演示、示例、样例。这一条不设词表（「演示」是常用词），由语义审查判。

**落盘与改章只有两条路**：成文登记**之前**，任何一章写完或要改，都在它的草稿上改、跑草稿开头那条
`chapter` 命令提交——命令原子替换那一章，别处一个字节都碰不到，已写的章同样可以重提；
成文登记**之后** story 冻结，要改先 `story_flow.py reopen`。不要自己去改 `AR/story.md`。
正文走文件不走命令行参数；命令是按本工程的命令行（PowerShell）引好的，换别的 shell 要自己核引用规则。

### 决策登记

**什么算一条议题**：review 是**判断的台账**——已决策的呈现结果供评审人过目，不确定、矛盾、错误的要人评估。准入判据只有一条：**评审人对这条表态「不同意」，会有产物要改**；表态没有后果的不占表态位，材料直接给定、没有判断参与的纯事实复述不进。从材料到方案之间凡发生过一次判断、或还等着人判断的，每处一条——材料没说而本轮定的、材料打架的（定源要有人的裁决）、材料有错或与工程现状矛盾的、材料明说未决的、需求做不到而降级承载的、关键取舍，以及跨方依赖的确认点。已定的登记 `settled`（正文落点是关键取舍），未定的登记 `open`（去处是评审记录），没有第三种去处。**把材料里没有的选择写死进正文或附录，就是漏登记。**

**再问这件事该谁定**：改变业务口径或对外承诺的，进评审记录；换一个实现方案结论就会变、又不改对外承诺的
（存储介质、内部结构、用哪个组件），是实现选型，**不登记为议题**——已定的写进 Spec §9 对应那一行，
没定的在 §9 那一行写「由 plan 定」。判不准时问：评审人不表态，这件事能不能上线。
不为填满「已定事项」造议题；一条都没有时回看清单再问一遍「材料没说而本轮定的、材料打架时选定的一边」有没有漏。

**已定的决策写进它的取舍位置**：取舍的理由只能从 `decisions.json` 里来——`settled` 的各写一处取舍：
有真实备选的写「选了什么 / 否了什么 / 为什么被否的不行」，只有一条合理路径的直接写依据，
不为显得有取舍编备选。只复述效果的不算理由（「因为中断后可恢复所以存半小时」没回答为什么不是十分钟）。
上游已定的方案照实标「上游已定」，不包装成本部件的取舍。
`open` 的议题在正文里写成**受影响处的未决边界**，不把依赖它的做法写成已定。
「确认继续保持未定」本身可以是一条已定的处置决定，但那说的是处置，不是业务已经解决。

**先定人在评审时要做什么**，写进 `review_mode`——它决定评审记录给评审人什么填写位，与 `status` 各管各的：
按这件事实际要人做的判断选，不按 status 猜。

**澄清正文**，小标题写成加粗段首（不另起标题行）：

| review_mode | 正文 |
|---|---|
| `choice`：人从几个方案里选一个 | **决策点**（要定什么、影响什么）／**依据**（材料怎么说、还有什么分歧）／**可选的做法**／**建议**／**理由** |
| `confirm`：人复核一个已有结论 | **决策点**／**依据**／**结论与影响**（定了什么、对交付意味着什么）——没有真实备选就不造列表 |

**可选的做法**是真正的有序列表，一个选项一项，每项写成「做法——选它会怎样」：后果说清范围、行为、
验收、交付哪一项会变；写不出后果差别的不是真取舍，改成 `confirm`。**建议**先写「选择方案 N（名称）」，
再写**理由**与要接受的代价；信息不够推荐不出来时，写明缺哪个事实，不硬选。推荐不是人已经选了：人没表态之前，它仍是 `open`。

一个中性的 `choice` 正文：

```markdown
**决策点**：受理超时后由谁发起重试，影响用户会不会被重复扣款。

**依据**：Spec 功能说明写「超时后重新提交」，接口说明第 3 节只写了超时按未受理处理，没有说谁负责再次提交。

**可选的做法**：

1. 客户端自动重试——用户无感；前提是受理方保证同一请求只处理一次，验收要加一条「重复提交不重复扣款」。
2. 提示用户手动重试——不依赖受理方去重；用户多一步操作，失败提示与重试入口进功能说明。

**建议**：选择方案 2（提示用户手动重试）。

**理由**：受理方目前没有去重承诺，方案 1 的前提不成立。
```

**「依据」写撞点**：story 哪一章或 Spec 哪一节的哪个主张，与哪份材料的哪一节、哪条工程事实或规约相撞。
「根据材料和工程现状」这种没有指向的话不算依据。标题写成陈述句：已定的陈述结论，待定的陈述事项；
决策结论用人话写，不写工具的档位与判据名。

**登记时选 `category`**：从下面十一类里挑一个，它决定这条在评审记录里成哪一节。
**每类第三列是撞的方向，不是遍历顺序**：议题从回看清单与骨架里撞出来；机器只判类别在不在词表里，这张表不是配额。

| 类型 | 读到什么就检查 | 撞的方向 |
|---|---|---|
| 范围与拆分 | 多段体验、兄弟单迹象、「不做什么」 | 一张单做完还是拆？和谁交接？ |
| 流程顺序与准入 | 步骤先后、资格门槛 | 产品旅程的顺序与现有实现冲突时按哪个？资格挡在哪一步？ |
| 入口与管控 | 新入口或新页面、运营可配置 | 入口放哪？要不要开关？默认值是什么？关掉之后存量怎么办？ |
| 规则与数值 | 阈值、上限、时限、次数 | 材料给了吗？两份材料打架按哪个？没给的谁来定？ |
| 数据与缓存 | 状态、记录、草稿、列表 | 存不存？存哪、存多久？跟账号什么关系？清除之后怎样？ |
| 界面与还原度 | 参考图、没有稿的页面 | 照图到什么程度？没稿的部分按什么做？ |
| 异常与受限体验 | 失败、超时、超限、停用分支 | 每条分支用户看到什么、怎么恢复？受限算不算异常？ |
| 依赖与可用性 | 需求用到的能力、接口、字段 | 工程里现在有吗？没有是近似、模拟还是等待？ |
| 安全隐私与合规落地 | 敏感数据、转授能力、激活规约 | 出口都脱敏了吗？能不能转给第三人？这条规约落到哪、做到什么程度？ |
| 交付顺序与协同 | 多方联调、分阶段开放 | 谁先谁后？模拟什么时候切真实？对方排期变了影响什么？ |
| 验收口径 | 写验收时 | 这一条的通过条件是上游给的还是本轮定的？可观察吗？ |

## 四、回看：十章齐后逐条处置回看清单

逐章写是十次各自有界的小任务，代价是没有一次拿成稿对着来源从头核。十章齐了，**先拿有效的原材料与
当前决定查一遍关键关系有没有漏**——条件、行为、责任、结果、例外与未决，在受影响的位置是不是一致；
再用清单定位疑点。要核的对象是当前的 `spec.md`、`AR/story.md`（含附录投影区）、
`AR/review.md` 与 `decisions.json`；有会议材料时还有 `doc-refresh.md` 与它所引的原话。
还没有 Plan 的阶段不预造 Plan。

`skeleton` 与最后一次 `chapter` 的输出里给出**回看清单**，由脚本从来源枚举——它帮你定位问题，
不是「只审已登记的这几条」的上限：

| 清单里的一类 | 从哪来 | 要确认的去向 |
|---|---|---|
| 初筛疑点 | 需求分析 ⑥ 里「还要核实的矛盾或缺口」非空的行 | 正文讲清、登记 `open`，或有依据地判不适用 |
| 未决 | `decisions.json` 里 `open` 的条目 | 正文里依赖它的行为没有写成已定 |
| 已定取舍 | `settled` 的条目 | 取舍落在哪一章，依据写了没有 |
| 骨架待核 | 骨架里的 `- 待核：` 行 | 在正文或决策登记里有去向 |
| 图 | 正文里每张图所在的节 | 图前声称覆盖的去向，图里有没有 |

对清单里每一条、以及骨架每一节的关键主张，**撞两问**：

1. **这句话材料里有吗？** 有，是搬运，进第二问；没有但说得出依据（工程事实、规约、上游口径），它是决策点，
   依据就是背景；没有也说不出依据，是编的，删掉。
2. **材料给的靠得住吗？** 拿它去撞：更晚的输入（系统设计晚于产品需求、界面稿、当前会议结果）、材料之间、
   工程事实、规约、材料自己声明的目标。「不合适」只认四种：工程没这能力、与既有实现冲突、撞规约、
   材料的目标与做法对不上。「我觉得有更好的设计」不算。

撞出来的东西只有四个出口，**处置回真源，不写台账**：

| 发现 | 出口 |
|---|---|
| 真实未决、跨章矛盾、Spec 与 story 对不上而要人裁 | 登记 `open`，依据写撞点；正文只写受影响的待决边界 |
| 重要的已定取舍正文有依据、登记表里没有 | 补登 `settled`，引既有结论与依据 |
| 已有依据能定的普通说明 | 沿用，不登记 |
| 编造、误读、前后不一致 | 回错误所属的真源改：story 章改草稿再 `chapter` 提交；Spec 改 `spec.md`；验收改 `acceptance.yaml`；知识判断改 `knowledge-use.yaml` 再 render；骨架错了改骨架 |

**材料自己打架时不要选一边照抄**——改变明确验收或范围口径的，有人的裁决才写 `settled`；没有就登记 `open`。
流程、功能说明、异常与恢复、验收对着读，同一种情况四处说的必须是同一件事。同一件事在全篇出现几处，
先问各处还回答了什么别处没回答的：完整复述（后一处没有独有用途）留在最该讲它的位置、其余改成一句承接；
互补（图讲关系、表讲属性、文字讲理由）与验收独立判所必需的条件与数值重现，两处都留着。
每张表前有一句引导，图前那一句说清它画的是什么。

**没有问题不制造改动**，不写「已核对」，也不凑改动数。每一条的去向由独立审查拿同一张清单复核，不由你自报。
改哪章就只提交哪章，**不重新输出整篇**。改完想再看一次清单就再跑 `skeleton`；全篇改完再跑一次 `check`：
跨章的判据（章序、验收编号全集、上游图的落点）要跟着重核。

## 五、登记

跑 `story_flow.py story --feature <名>`，按它的输出走，不写自评。它自己会重编号、重投影、重跑 `check`，
全过才登记成文。报错说的是**这一类事实的落点长什么样**，不是一张待抄的字面清单——照它指的位置去写那件事，
不要把报错里的名字原样搬进附录。
