# story 成文（两步：按章写，最后统稿）

读者是评审人：他们没参与开发，只有这一份文档，要据此判断
**这件事想清楚了没有、做对了没有**。他不看代码、不翻仓库、不知道内部编号。

## 写给这样的读者，意味着什么（十三条，写之前读一遍）

- Story 面向**第一次接触需求**的人类评审者，他无需先读规格、产品需求、系统设计或代码。
- 按人的理解顺序说明：为什么做、涉及谁、怎样解决、业务如何推进、当前特性负责什么、
  哪里会失败、怎样验收、怎样交付。
- 先说明背景，再解释理解后文必需的术语。
- 标题使用真实业务名称，简短、自然、准确概括下文。
- 标题不能用模板占位语、模型提问、机械分类词、解释性长句和明显的 AI 式表达。
- 三级、四级标题按真实业务从属关系自然生成，**不为形式对称强行凑出来**。
  **什么算一节**：一条业务支线、一个页面或场景、一个取舍主题、一条恢复路径，各自成节
  ——这不是形式对称，是读者按节回找的单位；把三条支线挤进一段散文才是错。
- **完整业务过程与当前特性功能分别说明**：业务过程讲需求怎样推进、在哪里交接；
  功能说明展开当前特性承担的页面、动作、状态和分支。
- **正常受限结果与真正异常分开说明**——混在一起，读者分不清哪些要处理、哪些是设计如此。
- 连贯的原因、方案、取舍和影响用自然叙述；表格、流程图、状态图、时序图和图片按实际
  表达需要使用。
- 接口、字段、错误码、配置、事件和追溯信息**必须保留，但不能打断面向人的主叙述**
  ——它们的落点是附录。
- 验收按真实业务场景或结果组织，**每个原始验收编号独立保留**，并给可观察的通过条件。
- Story 只表达**已经成立**的需求和决定；未确认的事项进决策件，
  不在 Story 里生成「待确认事项」或「评审导读」。
- 人读改写完成后**再次核对全部事实**，确保叙述优化没有造成内容丢失或重新引入重复。

成文分两步，**一章一章写，最后通读全篇收口**：

```
① 按章写 —— 先建骨架，一次写一章，经 chapter 命令原子落盘
② 统稿   —— 通读全篇一遍，收重复、收承接、收样式；改的那几章仍逐章落盘
```

**为什么不是「一次写完整篇」**：整篇是全有或全无——中途断了，磁盘上什么都没有，
前面读的材料全白读，重试从零开始。逐章写每步输出有界、
写完即落盘，断了知道从哪一章续。

**也没有「先分配」那一步。** 先给材料切出来的每个单元定一个落点、落成一份账再照着写，
那份账的量随材料条数涨而读者拿到的判断不增加；更要紧的是它把「这件事读者在哪一章想知道」
变成一次性的机械分配，写的时候反倒不许回头看材料。
**材料整份给你**，哪一章讲什么由你按读者的理解顺序定。

# 动笔前

材料与图、已确认的范围、已登记的判断、十章各要回答什么——**本阶段任务包一次给全**，
不必边写边找。表达原则在上面「写给这样的读者」十三条与下方「什么内容用什么形态」。

未定的判断只作边界，正文里不替它下结论。

**叙述不落附录**。附录是查阅件：读者顺着正文读下来要能读懂这件事，
把它塞进附录等于让它从阅读路径上消失。附录里只有那五张表和清单。

**同一件事在多份材料里出现，正文只讲一次**——选它最该待的那一章讲透，别在两章各写一遍。

# 决策登记

**什么算一条议题**：review 是**判断的台账**——已决策的呈现结果供评审人过目，
不确定、矛盾、错误的要人评估。准入判据只有一条：**评审人对这条表态「不同意」，
会有产物要改**；表态没有后果的不占表态位，材料直接给定、没有判断参与的纯事实复述不进。
从材料到方案之间凡发生过一次判断、或还等着人判断的，每处一条——材料没说而本轮定的、
材料打架而本轮定源的、材料有错或与工程现状矛盾的、材料明说未决的、需求做不到而降级承载的、
关键取舍，以及跨方依赖的确认点（对方表态变了产物就要改）。已定的登记 `settled`
（正文落点是关键取舍），未定的登记 `open`（去处是评审记录），没有第三种去处。
**把材料里没有的选择写死进正文或附录，就是漏登记。**

**找议题时对着这十一类过一遍**（类型即登记表的 `category`，也决定它在评审记录里成哪一节）。
**这是扫描地图，不是配额**：没有的类不用凑，机器不判每类有没有条目、不判数量、不判空类要解释。

| 类型 | 读到什么就检查 | 对号入座的问题 |
|---|---|---|
| 范围与拆分 | 多段体验、兄弟单迹象、「不做什么」 | 一张单做完还是拆？和谁交接？ |
| 流程顺序与准入 | 步骤先后、资格门槛 | 产品旅程的顺序与现有实现冲突时按哪个？资格挡在哪一步？ |
| 入口与管控 | 新入口或新页面、运营可配置 | 入口放哪？要不要开关？默认值是什么？关掉之后存量怎么办？ |
| 规则与数值 | 门限、上限、时限、次数 | 材料给了吗？两份材料打架按哪个？没给的谁来定？ |
| 数据与缓存 | 状态、记录、草稿、列表 | 存不存？存哪、存多久？跟账号什么关系？清除之后怎样？ |
| 界面与还原度 | 参考图、没有稿的页面 | 照图到什么程度？没稿的部分按什么做？ |
| 异常与受限体验 | 失败、超时、超限、停用分支 | 每条分支用户看到什么、怎么恢复？受限算不算异常？ |
| 依赖与可用性 | 需求用到的能力、接口、字段 | 工程里现在有吗？没有是近似、模拟还是等待？ |
| 安全隐私与合规落地 | 敏感数据、转授能力、激活规约 | 出口都脱敏了吗？能不能转给第三人？这条规约落到哪、做到什么程度？ |
| 交付顺序与协同 | 多方联调、分阶段开放 | 谁先谁后？模拟什么时候切真实？对方排期变了影响什么？ |
| 验收口径 | 写验收时 | 这一条的通过条件是上游给的还是本轮定的？可观察吗？ |


**已定的决策写进它的取舍位置**。取舍的理由材料里本来就没有，是起草时判出来的，
所以它只能从决策登记（`decisions.json`）里来：`settled` 的那些各写一处——
「选了什么 / 否了什么 / 为什么被否的不行」。
`open` 的议题不进正文，它的去处是评审记录，正文里写它等于把未定的事说成定了。

# 第一步 · 按章写

**先建骨架**：`story-build skeleton` 落十个稳定章锚，每章一个待写 marker。
骨架建好之后按合同顺序一次写一章，**每章都经同一条命令原子落盘**：

```bash
node .../story-build.mjs skeleton --feature <名>                      # 只跑一次
node .../story-build.mjs chapter  --feature <名> --chapter <章名> --from <这一章的文件>
```

**落盘只有这一条路，不要自己去改 `AR/story.md`。** 命令替换的区间就是那一章，
别处一个字节都碰不到——「已完成的章没被动过」因此是机械事实，不是期望。
正文走文件不走命令行参数：它带换行、引号与 markdown，任何 shell 都会再解析一遍。

中断之后从哪续也由它回答：每次落盘都报还剩哪几章带着待写 marker，
**已经写好的章不要重写**。

每章的输入就这四样：

| 输入 | 拿它做什么 |
|---|---|
| 材料里与这一章有关的部分 | 这一章要讲的事实。材料整份在你手上，按读者在这一章会问什么去取 |
| 已写好的上一章结尾 | 接得上，不重复交代 |
| 本章草稿（`AR/story-src/drafts/NN-<章名>.md`） | 形态说明、这一章的读者问题、已经搭好的槽位表、从 spec 打的底 |
| 「什么内容用什么形态」那张表（本文下方）与下面的四条红线 | 形式指引与归档件自包含 |
| 草稿里打好底的那几段（术语起始行、spec §5 的图、材料清单的类别与链接） | 改措辞、往下加，别重打 |

**每章 2–4KB**。写完这一章就跑一次 `chapter` 落盘，再写下一章。

## 怎么写一章

**写给人读，不是把材料列成条目。** 材料是**素材**，不是提纲——
把与这一章有关的部分组织成连贯的叙述，该合并的合并，该排序的排序。
材料里一句对应正文一个 bullet，那是清单不是叙述。

- **表格转成散文时，每一列都要有落点**——最容易丢的正是非首列：触发条件、字段名、编号；
- **材料清单里的每张图都要有去处**：要么在讲它的那一章引用（图前一句承接说清它画的是什么），
  要么在附录的材料清单那一行写明为什么不用它。每张图配的那句说明就在清单里，逐张列着；
  引用时用它在仓内的**既有落盘路径**——不复制文件、不改名、不另建图片目录、不在归档目录下造副本：
  副本没人维护，改了名读者也认不出它就是原来那张。一张图只引一次；
- 验收按材料里的编号**逐条给可观察条件**，每个原始编号独立一行（「验收」章）。
  需要细分时沿用上游的编号体系顺延，**不自造后缀**——编号是评审人和上游对齐用的，
  自造的后缀他那边查不到；
- 决策结论用人话写——**不写 framework 的档位与判据名**（`semantic_layout`、`best_effort`
  这类），澄清正文会原样进 review.md，评审者读到的是本需求的事而不是工具的档位；
  开放议题不下结论，交给决策件；
- **激活规约条目一条一行**：附录的「规约判定」小节成表（规约 / 编号 / 命中·不命中·整域不适用 / 依据）。
  判「不命中」也要有行、也要依据；整域不适用时给该域一行即可。**这张表里写编号是允许的**——
  主叙事里仍写中文规约名。

**空章**：确实不涉及的章，正文恰好写「本需求不涉及。」一句。
不删标题（读者会以为漏写了），不留空节（门禁分不清「没写」与「不涉及」）。

## 决策登记的澄清正文

三段式，小标题写成**加粗段首**（不用 `#` 标题行——议题在 review.md 里已有三级层次，
正文里再起标题会把分组压乱）。小标题之下写向同事解释的完整句子；压缩名词串、
维护流程黑话、冒号分号串联的电报体都不合格。

| status | 三段 |
|---|---|
| `settled` | **要定的事**（事项与冲突、疑问所在）／**根据**（材料怎么说、查了什么、问过谁）／**结论与影响**（定了什么、对交付意味着什么） |
| `open` | **要定的事**／**可选的做法**（编号列出每个选项和它的影响）／**建议**——不下结论，下了就不是待定 |

**「根据」必须指名材料或核查**：哪份稿的哪一节怎么说的、查了工程的什么。
说不出依据的判断，评审人没法复核，只能凭信任盖章。

标题写成陈述句：已定的陈述结论（「签约与管理由本单一次交付」），
待定的陈述事项（「入口的最终落点待确认」）。写成议题名（「入口问题」）评审人看不出要表什么态。

## 什么内容用什么形态

**固定形态不等于表格。** 表只是六种之一，哪一节用哪一种由内容的关系定：

| 内容的关系 | 形态 |
|---|---|
| 讲原因、讲取舍的来龙去脉、讲一个页面干什么 | 叙述段，结论先行 |
| 有真实先后的步骤 | 有序列表（超过 12 步拆节） |
| 并列的项、每项一句 | 无序列表（少于三项改叙述） |
| 一件事要回答固定的几个问题 | 加粗标签段，标签就是那几个问题 |
| 走向与分支 | 你画的图（流程图 / 状态图 / 时序图） |
| 材料里的界面 | 图引用 + 一句说清它画的是什么 |
| 一组对象各有几个固定属性 | 表（只有一列的改成列表，只有一行的不成表） |

**每一节固定成哪一种，写在章节合同的 `slots` 里**——草稿已经按它搭好：段落提示、
`1.` 的步骤、`- ` 的项、加粗标签、表头与占位、复制过来的图。你在草稿上填，
不用自己搭。**不设配额**：不要求每一章都出现表或图，能一句话说清的就不建表——
背景、方案叙述、功能行为、交付路径本来就该是叙述，那里一条表格类判据也没有。
把表格当安全牌用，读到的就是「五张表连排、表间只剩引言」，那和把表压成散文是
同一种病的两端。**机器只核机械事实**：固定节在不在、有序列表在不在、标签在不在、
图在不在、表在不在且第一列对不对；行数、措辞、按业务起的节名一概不核。
单元格与段落多长只是写作提醒，作者自查、读者审查看——接口参数、适用条件、
失败处理都可能合理地超过任何一个数字。

**源材料里是图的，到这里还得是图**：把流程图压成「A → B → C」这样的箭头文字、
把表压成散文，都算降级——读者要的是那张图能一眼看出的结构，文字复述它做不到。

### 哪种图讲什么

| 图 | 讲什么 | 什么时候用 |
|---|---|---|
| 流程图 flowchart | 一条业务从触发到终态的走向与分支 | 默认选它：分支多于两条、有决策点。spec §5 就是这种，骨架已经把它复制过来，改节点文字为业务名即可 |
| 时序图 sequenceDiagram | 多方之间谁先调谁、回什么 | 参与方三个以上且交互顺序本身是要审的内容（如授权必须在创建签约之前） |
| 状态图 stateDiagram | 一个对象的状态与转移 | 关键状态四个以上且转移条件复杂；少于四个用一张「关键状态」小表 |
| 关系图 erDiagram | 数据实体之间的关系 | 只在附录 B 有多张表互相引用时用；单实体不画 |
| 类图、部署图 | 实现结构 | 不进 story |

1. 业务流程章**章首一张完整的图**，覆盖主路径与全部分支去向；分支节里不再各画小图，
   除非那条分支本身是一段多方交互。零散的三四张小图不如一张全图。
2. 图里的节点用中文业务名，与主路径那一节的步骤一一对应；图讲结构，文字讲为什么，
   两者不互相复述。
3. 材料里的流程图图片可以另引在讲它的那一节（例如服务端触发），但它是材料的视角，
   不代替本特性走的那张图。

### 机器不判、要你自己把关的几条

- **表**：表前一句引导，说清这张表给你看什么（整章就是一张表的除外）；
  同列头的表连排时各自说明差别；单元格 1–3 个短项，超长改列表或拆行。
- **小节名**：用常规业务名，不口语化、不自造词；同一章里要么分节要么不分，不混着来。
  合同列出的必有节按它的名字找得到就行——「与补卡的交接约定」比「交接约定」更好。
- **位置**：同一件事只占一个结构位置——表、文、图是三种形态，不是三次机会。

## 别写成长文

| 阈值 | 怎么办 |
|---|---|
| 一段超过 160 字 | 拆开、改成列表或表、或者提出一个结论句放段首 |
| 一章正文超过 600 字还没有小标题 | 分 H3，或者把并列部分改成列表 / 表 |
| 有序步骤超过 12 项 | 按阶段拆成几节 |

**段落以百字上下为宜**（红线是 160，那是上限不是目标）。真实分布是段均长 58 字、超过百字的只有 38 段里的 4 段——短段密停顿，读者一眼扫得完一段。

**拆开之后要换形态**：把一个 200 字的长段拆成三个 120 字的段连排，读起来还是一堵墙，
只是墙上多了两道缝。真正管用的是换形式——并列的改列表、逐项比对的改表、
有结构的画成图，或者提一句结论放段首。

**没有句子长度限制**。中文里 45–60 字的完整复句很常见，为了凑短而在逗号处断开，
只会写出半截话和断裂的指代——那比长句更难读。句子啰嗦不啰嗦不设机器判据，归读者视角的语义审查。

## 归档件自包含（四条红线）

这份文档会被上传到需求系统，读者手上没有这个仓库：

1. 不写仓内路径（需求目录、模块目录名）——读者打不开。**唯一的例外是附录材料清单里的
   原文链接**：那一行本来就是给读者定位原件用的，没有链接他只知道「有一份产品需求文档」；
2. 不写裸文件名当引用（「见 design.md」）——读者不知道是哪一份；
3. 主叙事不写内部规则编号与仓内标识——改写中文业务名与中文规约名；
   它们的落点是**附录**（接口 / 数据、配置与事件 / 改动边界 / 规约判定 / 材料清单，
   只有这五节），不是没地方放；
4. 不写客户端语境的禁用词——`story-build check` 会按 lint 规则表拦。

**需求不是演示。** 工程当前可能用本地或模拟的方式承载某些能力（云侧还没接、
外部服务先用本地实现顶着），那是交付前的工程状态，不是这个需求的定性。归档件里
不得把需求或它的实现说成演示、示例、Demo、样例——读者拿到的是一份要做的需求，
不是一份展示品。模拟承载照实写：**「本地模拟承载，真实服务接入后替换」**。

这一条不设词表——「演示」是常用词，机器拦它会误伤（「演示视频」「向客户演示」
本来就该能写）。它由 verifier 逐问接。

# 第二步 · 统稿

逐章渲染是十次各自有界的小任务，这是它的代价：**没有任何一步是通读全篇的**。
各章各写各的，于是同一件事在三章各讲一遍、两句话逐字重复、图连着图没有承接、
图题一章一个样子——每一章单看都对，合起来读才看得出来。

写完最后一章之后，**从头到尾读一遍**，逐条过下面六项。这一步只有你能做：
机器判不了「这两处说的是不是同一件事」，而语义审查看的是读者读不读得懂，
不替你做这一遍通读。

1. **同一件事在全篇出现几处？** 多于一处的，留在最该讲它的位置，
   其余删掉或改写成一句承接。表、文、图是同一件事的三种形态，不是三次机会。
2. **有没有两句逐字或近乎逐字相同的话？** 有就删掉一处。
3. **每张表前有一句引导吗**（这张表给你看什么；整章就是一张表的除外）？
   同列头的表连排时，各自说明了差别吗？
4. **每张图有正文承接吗**（图前一句说清它画的是什么）？图在它内容所属的那一章吗？
5. **样式约定与节奏过一遍**：连续三段以上没有任何停顿（图、表、列表、小标题）的地方，
   考虑换个形式或者分节；单元格一到三个短项、小节命名与颗粒度一致、
   大标题带需求编号（章序、小节序、图题序号由登记步的 `story-build number` 统一铺，
   你只写业务名标题与图题本身）。
6. **读者视角扫一遍**：有没有写给流程或门禁看的话（登记、回写、守恒、
   「按类别可回查」这类）？有没有给实现者的指令混进来？有没有起草过程的痕迹
   （「检索……零命中」这种）？

改的时候仍然一章一章改：要动第五章就把第五章重新写进文件，再跑一次 `chapter --chapter <第五章>`。
**统稿不重新输出整篇**——整篇重出是全有或全无，中途断了磁盘上什么都没有，
而且没被改的那几章会因为重出而字节全变，谁也说不清这一轮到底动了什么。

过完之后在 `AR/story-src/copyedit.md` 写**恰好六行**，六项各一行「查了什么／改了几处或无」。
统稿是唯一一步没有产物的动作，于是跳过它零成本——留一行痕迹，「没做」就藏不住了。
**只写六行，写多不奖励**：把它写成检查报告不加分，`check` 只核行数、不核内容
（写没写到位由语义审查与抽样人核）。

改完重跑一次 `check`——统稿动了正文，确定性判据要跟着重核。

# 交回前

全部章都渲染完之后跑：

```bash
node doc/extensions/skills/story/scripts/story-build.mjs check --feature <名>
```

判据全过才算完。**check 没过就别交。**

报错说的是**这一类事实的落点长什么样**，不是一张待抄的字面清单——
照着它指的位置去写那件事，不要把报错里的名字原样搬进附录。

## 交回前自检（两条，只有你看）

这两条是**整篇印象**，只能由写完全篇的人自己判。语义审查也不替你答——
它读的是成品读不读得懂，答不出「你写的时候手边有什么、少交代了什么」。

**一、独立可读。** 评审者手里只有这份叙事件与《决策与评审记录》——需求规格不随归档，
他打不开，也不关心实现怎么落地。读完能不能说出：要做什么、为什么这么做、动了哪些存量、
哪里可能出问题？出现只有读过规格才懂的指代（模块内部结构、函数签名、仓内路径、
「现状无 X 封装」这类扫描结论），就是不达标。

**叙述是你自己的**：顺序服务于人的理解——先为什么 → 再是什么 → 再怎么做 → 再哪里会坏 →
最后怎么算做对。**原封不动照搬规格的章节顺序与表格排布**即不达标：那说明只做了搬运，没做改写。
**表达贴合内容**：能一句话说清的不建表；并列多项且需逐条比对的才建表；流程用图。
通篇是表、叙述只在表间做连接词，同样不达标。

**二、有取舍。** 方案取舍与设计选择的每一行都要写清「选了什么、否了什么、为什么不是另一种」。
规格只有结论，story 存在的意义就是补上理由——只复述效果的不算理由：
「用某种缓存存 30 分钟，因为中断后可恢复」等于说「做了 X 因为想要 X」，
没有回答为什么不是 10 分钟、为什么不用内存。
**写不出被否决的备选，那一行就不是决策**，删掉或降级成事实陈述，不该占据设计选择的位置。
上游已定的方案照实标「上游已定」，不得包装成本部件的取舍——那会让评审者以为这里有得商量。
