# story 成文（两步：先分配，再逐章渲染）

读者是评审人：他们没参与开发，只有这一份文档，要据此判断
**这件事想清楚了没有、做对了没有**。他不看代码、不翻仓库、不知道内部编号。

成文分两步，**先把每件事分到章，再一章一章写**：

```
① 分配   —— 给每个来源单元定一个落点，落 audit.json；audit 核「没有无家可归的」
② 逐章渲染 —— 按合同顺序，一次写一章，追加到 story.md；写完 audit 一次
```

**为什么不是「一次写完整篇」**：整篇是全有或全无——中途断了，磁盘上什么都没有，
前面读的材料全白读，重试从零开始（实测四次尝试三次空手而归）。逐章写每步输出有界、
写完即落盘，断了知道从哪一章续。

**这不是 1.0 的逐章取材。** 1.0 由章节合同按关键词把材料路由给每一章，同一个事实被四个
章节合同各指一次，于是被强制写四遍。这里**由你分配、机器强制恰好一次**：一个单元一条记录、
一个落点。分完再写，写的时候不再回头翻材料找「这一章该抄什么」。

---

# 第一步 · 分配

**输入**：`AR/story-src/source-units.json`（材料切出来的全部来源单元，每条带正文与 token）
加上你手里的材料——`RR/prd.md`、`SR/design.md`、`AR/design.md`、`AR/upstream.md`（存在时）、
`spec/spec.md`、`AR/story-src/decisions.json`，以及激活清单
（`doc/extensions/manifest.yaml` 的 `provides.knowledge`）所列的规约文件。

**产物**：`AR/story-src/audit.json`，形如

```json
{ "records": [
  { "key": "PRD:31:ab12cd34", "at": "场景与功能" },
  { "key": "SE:88:9f0e1d2c", "covered_by": "PRD:31:ab12cd34" }
] }
```

每个单元**恰好一条记录**，落点只有三种，**没有第四种**：

| 态 | 什么时候用 |
|---|---|
| `at: <章节标题>` | 这件事要写进那一章。标题必须是合同里的 14 个之一 |
| `covered_by: <单元键>` | 它被另一条讲清楚了（同一件事在两份材料各说了一次）。被指的那条自己要有 `at` |
| `machine_facing` | 机器面登记项，**枚举器已经打好，你不要碰**，也不必给它分配 |

分完跑一次：

```bash
node doc/extensions/skills/story/scripts/story-build.mjs audit --feature <名>
```

它会列出**还没有落点的**那些（三态皆空）。清零才算分配完成——
「待处理 0 条」是进入第二步的前提。

**分配的判断标准**：这件事**读者在哪一章会想知道它**。不确定时看章节模板里那一章的
注释（`templates/story-template.md`），它写着这一章回答读者什么问题。

**同一件事在多份材料出现**，选一条写正文、其余标 `covered_by` 指向它——
不要两条都给 `at`，那会让同一件事在两章各写一遍。

# 第二步 · 逐章渲染

按合同顺序，**一次写一章，写完追加到 `AR/story.md`**。每章的输入就这四样：

| 输入 | 拿它做什么 |
|---|---|
| 分给本章的那些单元正文 | 这一章要讲的全部事实。**只看这些，不回头翻材料** |
| 已写好的上一章结尾 | 接得上，不重复交代 |
| 本章在模板里的注释 | 这一章回答读者什么问题 |
| 下面的四条红线 | 归档件自包含 |

**每章 2–4KB**。写完这一章就落盘，再写下一章。

写完一章跑一次 `audit`：分给本章的单元里，token 或 ≥8 字片段能在本章正文里找到的，
机器会标成 `by: machine`（核实了）；找不到的留 `by: author`，交裁决者逐条裁。
`audit` 还会打印**未渲染章**——中途断了看这一行就知道从哪续，**已写好的章不要重写**。

## 怎么写一章

**写给人读，不是把单元列成条目。** 分给这一章的十几条单元是**素材**，
不是提纲——把它们组织成连贯的叙述，该合并的合并，该排序的排序。
一条单元对应一个句子、十条单元十个 bullet，那是清单不是叙述。

- **表格转成散文时，每一列都要有落点**——最容易丢的正是非首列：触发条件、字段名、编号；
- **图片一张不少、一图一引**，引用时说清它画的是什么；
- 验收按材料里的编号**逐条给可观察条件**（「质量与验收」章）；
- 决策结论用人话写；开放议题不下结论，交给决策件；
- **激活规约条目一条一行**：「影响面与合规」章成表（规约 / 编号 / 命中·不命中·整域不适用 / 依据）。
  判「不命中」也要有行、也要依据；整域不适用时给该域一行即可。**这张表里写编号是允许的。**

**空章**：确实不涉及的章，正文恰好写「本需求不涉及。」一句。
不删标题（读者会以为漏写了），不留空节（门禁分不清「没写」与「不涉及」）。

## 归档件自包含（四条红线）

这份文档会被上传到需求系统，读者手上没有这个仓库：

1. 不写仓内路径（需求目录、模块目录名）——读者打不开；
2. 不写裸文件名当引用（「见 design.md」）——读者不知道是哪一份；
3. 不写内部规则编号（那些 `XX-01` 形态的仓内标识）——改写中文规约名；
4. 不写客户端语境的禁用词——`story-build check` 会按 lint 规则表拦。

# 交回前

十四章都渲染完之后跑：

```bash
node doc/extensions/skills/story/scripts/story-build.mjs check --feature <名>
```

九项判据全过才算完。**check 没过就别交。**

## 交回前自检（两条，只有你看）

这两条是**整篇印象**，只能由写完全篇的人自己判。裁决者不看它们——他的任务是
逐条对齐「这个单元 → 那一章讲没讲」，掺进整篇印象题只会稀释掉那件事的注意力。

**一、独立可读。** 评审者手里只有这份叙事件与《决策与评审记录》——需求规格不随归档，
他打不开，也不关心实现怎么落地。读完能不能说出：要做什么、为什么这么做、动了哪些存量、
哪里可能出问题？出现只有读过规格才懂的指代（模块内部结构、函数签名、仓内路径、
「现状无 X 封装」这类扫描结论），就是不达标。

**叙述是你自己的**：顺序服务于人的理解——先为什么 → 再是什么 → 再怎么做 → 再哪里会坏 →
最后怎么算做对。**原封不动照搬规格的章节顺序与表格排布**即不达标：那说明只做了搬运，没做改写。
**表达贴合内容**：能一句话说清的不建表；并列多项且需逐条比对的才建表；流程用图。
通篇是表、叙述只在表间做连接词，同样不达标。

**二、有取舍。** 方案取舍与设计选择的每一行都要写清「选了什么、否了什么、为什么不是另一种」。
规格只有结论，story 存在的意义就是补上理由——只复述效果的不算理由：
「用某种缓存存 30 分钟，因为中断后可恢复」等于说「做了 X 因为想要 X」，
没有回答为什么不是 10 分钟、为什么不用内存。
**写不出被否决的备选，那一行就不是决策**，删掉或降级成事实陈述，不该占据设计选择的位置。
上游已定的方案照实标「上游已定」，不得包装成本部件的取舍——那会让评审者以为这里有得商量。
