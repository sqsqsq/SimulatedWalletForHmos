# story update：把已有产物更新到当前有效依据

> 读者：跑 `/story update <需求编号>` 的模型。时机：这个单已经有产物（Spec / Story / Review / Plan 至少一样），
> 而上游材料、评审意见、人的新决定或有人直接改过的文档，使现在的产物不再与当前依据一致。

**要做的事一句话**：结合最新有效输入、既有决定和当前需求进展，判断哪些内容仍然成立、哪些要改，
使受影响的已有产物成为一致、可继续工作的依据，并说清仍未决或尚未验证的部分。

用户只给编号，不必先替你列出哪些文件要改。**完成对象是这次变化牵动的业务关系，不是某几个文件**——
一条关系含对象、前置、行为、结果、责任、异常、未决与验收，它的落点可能分散在几份产物里，
也可能有一部分在当前阶段还没生成。

**边界**（这几条不由你判断，是给定的）：只更新**已有**的 Spec / Story / Review / Plan 与必要的过程记录；
不自动生成新阶段的产物、不改产品代码与测试；默认只改这次变化牵动的地方，整篇表达优化由用户明确要求才做，
大幅重组先说明再动手；回写到需求系统之前先给人看结果。

## 一、先检测，再决定要不要你读

起手跑一次：

```text
python doc/extensions/skills/story/scripts/core/story_flow.py update --feature <编号> [--request "<人这次明确要求改的事>"]
```

`--request` 只在**人明确要求改一件事**时带上（「把单日上限改成 300」）；只是来看看有没有变化就不带。
带了它就不会走无变化快速退出——文件没变不代表没事做。

它返回 `comparison`，四种去向各走各的：

| `comparison` | 意思 | 你做什么 |
|---|---|---|
| `unchanged` | 与上次已处理的版本逐份比过，真的没变，也没有没做完的更新 | **到此为止**。如实报告「未检测到变化」，不改任何业务文件，不往下读 |
| `resume` | 上一次 update 还开着 | 读它的 `before/` 与 `update-notes.md` 接着做完，或按记录还原现场。**不要另起一轮** |
| `incomplete` | 比较基准缺席或有来源读不到 | 这不是「没有变化」。说清可查与不可查的范围，按当前材料与产物核一致性，**不补造「原来怎么写」** |
| `changed` | 有文件变了、暂存区有新取回的内容，或人明确要求改 | 往下走第二节 |

它同时留下 `AR/story-src/updates/<id>/before/`——**本次执行前的完整现场**。它是还原依据，
不是给你读的材料；这一轮的新内容照常写在原来的位置，不要往 `before/` 里写东西。

取回上游与评审内容用只读取材，它一个业务文件都不写。**命令不要自己拼**——
`update`（任一动作）返回的 `fetch` 字段就是这一次该跑的那一条，落点由脚本定：

```text
python …/story_flow.py update --feature <编号> --action status   # 回执里的 fetch 字段
node   …/adapters/story.js fetch <编号> <token> --out <脚本给的那个目录>
```

取回的东西落在暂存区，`fetched.json` 这份取材回执逐份写清它是什么、摘要、在系统上挂在哪张单下、取到没有。
**缺席与失败是两回事**：系统上没有评审回稿是常态，读不出来是故障——后者要如实说成缺口。
目标工程的对接实现没有 `fetch` 时，报出来并停下，**不要退回用 `review` 顶替**：那条路会覆盖 `AR/review.md`，
把人刚写的意见吃掉。

**暂存区里的东西怎么用完**：读完之后，这一轮真要采用的那几份按**现有导入链**进正文——
放进 `inbox/`，跑 `story_flow.py round` 登记到本轮（它不开新轮）。不采用的，在 `update-notes.md` 里
写清为什么用不上。`close` 时暂存区会被清空（副本已经留在本轮的 `updates/<id>/incoming/` 里）——
**清掉的是暂存，不是依据**；不清的话下一轮永远看见它非空、永远报「有变化」。

### 这一轮的另外三个动作

| 动作 | 什么时候跑 | 它做什么 |
|---|---|---|
| `--action status` | 想知道现在有没有开着的更新、上一轮做到哪 | 报事实：开着的是哪一轮、说明在不在、暂存区有什么、各阶段有没有产物与闭没闭环 |
| `--action close` | 这一轮改完、核完 | 收口：**要先写好 `update-notes.md`**；把此刻的内容留一份作下一轮的比较基准，并清空取材暂存区 |
| `--action restore` | 这一轮要整个撤回 | 还原到这一轮开始之前；**先把这之后改过或新建的原样存起来**，两边都留着，要哪份由人定 |

人在这一轮里拍的板用 `story_flow.py decide --update "<定了哪件事>" --basis "<他的原话>"` 记一笔。
它记的是**原话**：`update-notes.md` 里写「已确认」不算人签，那是你的转述。

**议题正文改了、而评审人已经在它下面写过意见**时，渲染会停下来：他答的是上一版的问题。
你判定只是改了措辞、问的还是同一件事，就用上面这条命令把 `<定了哪件事>` 写成**那条议题的 id**、
`--basis` 写人同意沿用的原话，再重跑——渲染会带回他的表态。判定问的事变了，就让他重新看一眼那一条。

### 阶段事实从哪来

`status` 的 `phases` 逐阶段给「有没有产物、闭没闭环、上次审查判了什么」，读的是 harness 自己写的
`<阶段>/reports/summary.json`（只读投影，不是我们的账）。读不出来它就说读不出来——
**闭没闭环不许猜**，猜错的方向永远是「以为闭了」。

## 二、六个动作

这是一次 update 的认知顺序，可以因为补料或拿到裁决回到前面的动作。**不要求六份文件、六次调用或六个关卡**，
一份 `updates/<id>/update-notes.md` 记住当前判断与去向即可，中断之后靠它和盘上的文件接着做。

### 1 还原当前有效依据

读当前请求、已有的来源说明、有效决定、当前 Story / Review / Spec、已有 Plan 与本轮相关的知识判断。
**把这几样分开**：材料原文、人的结论、你自己的假设、当前产物的表达、历史送审的版本。
同时弄清哪些阶段有产物、哪些已闭环、哪些在途。

先用已有的分析与当前版本建立理解，再回查涉及变化的那几处原文；旧分析可以复用，
但**与原话冲突时以原话为准**。比较基准缺席时明说证据不足，不补造。

产出是一段供后续判断用的工作上下文：这个单做到哪一步、变化之前采用的关键解释是什么、
相关未决与已有的人工修改有哪些。**不是重写一份全量 Spec。**

### 2 解释变化，不是搬运差异

对每一项新材料、意见、直接编辑与上一轮没做完的事，回答四问：它说的是哪件业务事；
相对当前依据改了什么；什么没变；是不是已经落实了，或与既有决定冲突。

- 看起来被删掉的要求，先核它的去向——是撤销了、挪走了，还是新版本只是没重复说一遍。**依据不足不删下游功能。**
- 「同意」「通过」这类话，先核它针对的是哪个议题、哪一版。
- 人直接改过的稿子，先理解他要表达什么，再决定怎么接回真源。
- 多个来源同时变，按来源职责与明确决定定有效解释，**不按时间最新自动压过其他来源**。

产出按业务主题组织，可以把几条同义输入并成一条，也可以把一段话拆成几件不同影响；
**不要求一个文件差异对应一条语义变化**。

### 3 推演影响与保留项

以变化的对象或行为为中心，沿「前置 → 动作 → 结果 → 责任 → 异常 → 验收」查一遍上下文，
再看已有设计怎么实现它、知识要求是否因此命中或不再命中。对新发现的受影响关系继续查，
直到每项变化在已有产物里都有去向，或明确留下待决、不适用、下游交接。

时限从 24 小时改成 36 小时不只是换一个数字：它可能影响什么时候允许操作、提示怎么写、
接口的拒绝条件、异常路径与验收。**只同步现有材料证实存在的关系**——为了「全链完整」虚构一条不存在的能力，
比漏一条更难发现。

依赖靠你读材料判断，**不建通用依赖图、不用同词命中代替**。影响范围可以扩到必要的关联处，
但业务范围的扩展仍要问人。**列出重要的不变项以及为什么不用改**——防的是「优化一处、损坏另一处」。

### 4 只在真的需要人时问

只有现有权限与依据定不了的才问：来源冲突、意见含糊、要改已经承诺过的事、范围扩展、大幅重组。
每项给出原来的解释、新信息、可选的处理及其后果与建议；**能在同一轮说完的集中问一次**。

人的决定限定到具体事项与这一次的输入。来源变化使旧的人签不再适用时明说；
**不因为沿用同一个议题编号就沿用他的勾选**。仍未决的事项继续约束相关内容，
但不挡住那些独立且已经明确的修改。

沿既有的决策渠道记录真实原话，说明里引用这些记录；**不另造「人工已批准 = true」这种自证字段**。

### 5 修订最早责任内容，再同步关联产物

| 内容层 | 你做什么 | 不能动的 |
|---|---|---|
| 外部原始材料 | 保留取得的版本与来源，更新本地采用的那一版 | 不替上游重写原话来消掉冲突 |
| 初析 / AR 提取稿 | 修订本需求对来源的理解与承载边界 | 没变的范围与人签复用，没必要不重做初析 |
| Spec / 验收 / 决定 | 修订需求真义、可观察条件、有效与未决结论 | ID 有语义连续性才保留；**不能只改叙事不改真源** |
| Story / Review | 用当前有效解释更新相关叙事、图与议题，保留人工意见的语境 | 不覆盖有效的手改；旧表态不移植到已经变义的问题上 |
| 已有 Plan / 契约 / 用例 | 调整因本次变化失去依据或需要补齐的设计 | 不重写独立有效的部分，不自动推进 coding |
| 还没生成、或本次无权改的下游 | 说明后续要承担什么、为什么 | 不生成不存在的新阶段产物，不冒充已落实 |

原材料与生产真源分开改。接口、验收、知识这些确定性投影仍由既有脚本产生，
**不手改派生区去迎合检查**。story 侧的改动仍走 `reopen` → 改草稿 → `chapter` → `story` 重新登记。

### 6 按关系核对，再说能不能继续

从每项有效变化回查已改的内容，核正常、受限、异常与验收是否一致；从没变的重要关系查有没有误伤；
从待决事项查是不是仍然待决。再核阶段结构、引用、编号与投影。

回查**不要求字面相同**，也不把「旧稿全部保留」当守恒：已经明确取消或被替代的内容应当退出当前版本，
历史留在 `before/` 里。没有新增变化但上一轮的同步没做完时接着做，不按文件摘要提前收工。

产出只有一份当前的 `update-notes.md`，四段就够：当前依据、变化与影响、决定与修订、核对与剩余。
向用户展示业务上变了什么与可查的差异，**不要罗列对他决定没帮助的脚本步骤**。

## 三、当前做到哪一步，决定这一轮能做什么

| 当前进展 | 默认怎么做 |
|---|---|
| 只有材料或提取稿 | 更新已有的解释与材料，**不顺带把 Spec 生成出来** |
| Spec / Story / Review 已有 | 围绕有效变化核对并同步；本该有却没有的产物，报出这个事实，不用「自动补上」掩盖 |
| Plan 在途 | 改已有的受影响设计，说明其余仍在途；**文件存在不等于那一段已经完成** |
| Plan 已闭环 | 改相关设计、契约、用例与知识落点，再按 framework 的原生修正机制重验 |
| 已归档 | 保留旧的送审依据，更新本地工作稿；**人确认之后才回写** |
| 已到代码或测试 | 文档同步到已有 Plan 为止，标明实现与证据可能失效、接手的人要做什么；**不自动改源码、不碰设备测试** |

范围由这一轮的请求、实际变化与上一轮没做完的事决定，**不默认开展全需求质量翻修**。
核对时撞见与本轮无关的旧问题，记下来交给它的责任方；确实挡住本轮结果正确性的，纳进来并说明为什么。

## 四、报告什么结果

| 结果 | 什么时候成立 | 用户据此能做什么 |
|---|---|---|
| 已同步，可继续当前工作 | 受影响内容已按当前有效决定一致，适用检查完成，没有挡住当前工作的未知 | 在原进展上继续（**不代表需求自动进入下一阶段**） |
| 已同步，有明确保留项 | 业务未决、非阻断建议或代码/测试影响都已说清，没有被写成已完成 | 继续不依赖这些保留项的工作 |
| 尚未完成 | 必要的输入、裁决、同步或验证缺失 | 知道缺什么、影响哪些内容、下一步该谁处理 |
| 核对后无需修订 | 有效变化已经落实过，或只是表达差异、与本单无关 | 保留现稿（**不为留下更新痕迹而重写**） |

本地文件写完了、脚本退出 0、操作记录关闭了，**都不能代替上面这几个判断**。
没有历史版本时可以说「当前无需修订」，但不能说「历史从未发生过变化」。

## 五、与闭环、修正入口的关系

仓根 `CLAUDE.md` 那句「verifier 只跑一次——材料未变复用既有报告，材料变了但历史有 PASS 沿用并如实标
`completed_with_prior_review`」说的是**报告缺席时的兜底路径**（`framework/harness/scripts/check-receipt.ts`
先找当前 subject 的报告，只有 `report_missing` 才退到历史 PASS）。update 改完材料之后重新跑一次门禁，
当前 subject 的请求就在盘上，提交这一轮的报告走的是主路径，不是那条兜底。
`NEXT:` 行说的「停下等待用户指令」，`/story update` 正是那条用户指令。

具体怎么派、怎么回写、怎么确认闭环，等 update 的完整入口开放时在本页补齐（那是 C3 的事）。
**在此之前不要自己拼请求、不要手改回执与 summary。**

普通的局部修正仍按 `phases/spec.md` 的原路走：`--correction-init` 定责任层 → 改真源 →
`--revalidate` 只重跑脚本门禁。两者的区别是**谁发起、材料变了多少**，不是「代码有没有拦着」。
