# story update：把已有产物更新到当前有效依据

> 读者：跑 `/story update <需求编号>` 的模型。时机：这个单已经有产物（Spec / Story / Review / Plan 至少一样），
> 而上游材料、评审意见、人的新决定或有人直接改过的文档，使现在的产物不再与当前依据一致。

**要做的事一句话**：结合最新有效输入、既有决定和当前需求进展，判断哪些内容仍然成立、哪些要改，
使受影响的已有产物成为一致、可继续工作的依据，并说清仍未决或尚未验证的部分。

用户只给编号，不必先替你列出哪些文件要改。**完成对象是这次变化牵动的业务关系，不是某几个文件**——
一条关系含对象、前置、行为、结果、责任、异常、未决与验收，它的落点可能分散在几份产物里，
也可能有一部分在当前阶段还没生成。

**边界**（这几条不由你判断，是给定的）：只更新**已有**的 Spec / Story / Review / Plan 与必要的过程记录；
不自动生成新阶段的产物、不改产品代码与测试；默认只改这次变化牵动的地方，整篇表达优化由用户明确要求才做，
大幅重组先说明再动手；回写到需求系统之前先给人看结果。

## 零、输入阶段：先问要不要补料，再比

一次 update 的入口与 init 同构：**先取输入、报告并问补料，人答了再定最终的材料变化**，然后才是增量修订。
问法、侧车、人签与登记全是 init 第一级关卡那一套，差别只在每次 update 都停一次。

1. **系统需求先取上游**：按 SKILL「更新」② 调用取材，落点用 `update --action status` 返回的 `paths.inbox`。
   这一轮没取过上游，下一步的报输入会停下并指回这里。本地需求没有上游，跳过这一步。
2. **报告输入**：

   ```text
   python doc/extensions/skills/story/scripts/core/story_flow.py update --feature <编号> --action inputs [--request "<人这次明确要求改的事>"]
   ```

   它只报告、不建任何东西：八项里哪几份跟上次已处理的版本不一样、读不到的、收件箱里还没并入正文的原件
   （`pending`）、最近一次取材的回执（`upstream`：逐份 `fetched` / `same` / `absent` / `failed`）。
   `--request` 只在**人明确要求改一件事**时带上（「把默认排序改成按时间」）；只是来看看有没有变化就不带。
3. **材料关卡停一次**：按 `rules/init_analysis.md` S2a 盘点手上的料（不取的理由只能是范围不依赖它），
   缺口写进 `.material-gaps.json`，跑 `status` 取问法；向人报告上游哪几份变了、没变、取不到，本地已有什么，
   一句缺口判断，`ask.block` 原样摆出，问**这一次要不要补料**，停下等他。
4. 他放料进 `inbox/` 或答「不补」→ `decide --gate material_scope --ask <ask_id> --reply "<原话>"` → 有新原件先导入 →
   `round` 登记到本轮（它不开新轮）。新原件是某份旧原件的新版本时，**导入前把 `inbox/` 里那份旧原件本身**
   移到 `.backups/local/<旧原件名>-<时刻>`（不删；`inputs` 的 `superseded_hint` 会列出同类的已归类原件），
   清单里写明取代关系——同一类原件导入时按文件名拼接，不移就是两版拼在一起。
   导入前的目标文件（如 `RR/prd.md`）由导入链自己备份，不用你管。
5. **比较并开这一轮**：`update --action prepare`。收件箱里还有未并入的原件时它会拒绝并列出文件。

取回的三份正文与人补的料一样在 `inbox/` 里等导入，归类照 init 的做法由你判；本单的系统正文与本地 story
逐字相同的（自己归档上去的那一版）不会落盘。评审回稿不是需求正文，落在 `AR/story-src/review-feedback.md`，
你读它，人的表态照下面的决策渠道记。**缺席与失败是两回事**：系统上没有评审回稿是常态，读不出来是故障——
后者要如实说成缺口。`fetch` 命令失败（包括目标工程的对接实现没有这条命令）时，报出来并停下，不用别的写入方式代替取材：
直接覆盖 `AR/review.md` 会把人刚写的意见吃掉。

## 一、`prepare` 的四种去向

判定只看**人和上游会动的八项**：`RR/prd.md`、`SR/design.md`、`AR/design.md`、`inbox/`（按材料事实，
不按文件哈希）、`AR/story.md`、`AR/review.md`、`spec/spec.md`、`plan/plan.md`。决策登记、写作设计、
验收与强契约是你据它们写出来的中间真源，是结果不是原因，不进判定。

| `comparison` | 意思 | 你做什么 |
|---|---|---|
| `unchanged` | 八项与上次已处理的版本逐份比过都没变，收件箱没有未并入的原件，也没有没做完的更新 | **到此为止**。如实报告「未检测到变化」，不改任何业务文件，不往下读 |
| `resume` | 上一次 update 还开着 | 读它的 `before/` 与 `update-notes.md` 接着做完，或按记录还原现场。**不要另起一轮** |
| `incomplete` | 比较基准缺席或有来源读不到 | 这不是「没有变化」。说清可查与不可查的范围，按当前材料与产物核一致性，**不补造「原来怎么写」** |
| `changed` | 有文件变了、收件箱有未并入的原件，或人明确要求改 | 往下走第二节 |

它同时留下 `AR/story-src/updates/<id>/before/`——**本次执行前的现场**（阶段报告与导入备份不在里面）。
它是还原依据，不是给你读的材料；这一轮的新内容照常写在原来的位置，不要往 `before/` 里写东西。

### 另外三个动作

| 动作 | 什么时候跑 | 它做什么 |
|---|---|---|
| `--action status` | 想知道现在有没有开着的更新、上一轮做到哪 | 报事实：开着的是哪一轮、说明在不在、取材命令、各阶段有没有产物与闭没闭环 |
| `--action close` | 这一轮改完、核完 | 收口：**要先写好 `update-notes.md`**；把此刻八项的内容留一份作下一轮的比较基准 |
| `--action restore` | 这一轮要整个撤回 | 还原到这一轮开始之前；**先把这之后改过或新建的原样存起来**，两边都留着，要哪份由人定 |

人在这一轮里拍的板用 `story_flow.py decide --feature <编号> --update "<定了哪件事>" --issue <议题编号> --reply "<他的原话>"` 记一笔：先把这件事登记成议题、build 进评审记录，人看过那一条再回话。
它记的是**原话**：`update-notes.md` 里写「已确认」不算人签，那是你的转述。
人已表态的议题登记为 settled 时，`review_mode` 怎么写见 `phases/story-write.md`「决策登记」。

**议题正文改了、而评审人已经在它下面写过意见**时，渲染会停下来：他答的是上一版的问题。
你判定只是改了措辞、问的还是同一件事，请他确认沿用，用上面这条命令把 `<定了哪件事>` 写成**那条议题的 id**、
`--reply` 写他同意沿用的原话，再重跑——渲染会带回他的表态。判定问的事变了，就让他重新看一眼那一条。

### 阶段事实从哪来

`status` 的 `phases` 逐阶段给「有没有产物、闭没闭环、上次审查判了什么」，读的是 harness 自己写的
`<阶段>/reports/summary.json`（只读投影，不是我们的账）。读不出来它就说读不出来——
**闭没闭环不许猜**，猜错的方向永远是「以为闭了」。

## 二、六个动作

这是一次 update 的认知顺序，可以因为补料或拿到裁决回到前面的动作。**不要求六份文件、六次调用或六个关卡**，
一份 `updates/<id>/update-notes.md` 记住当前判断与去向即可，中断之后靠它和盘上的文件接着做。

### 1 还原当前有效依据

读当前请求、已有的来源说明、有效决定、当前 Story / Review / Spec、已有 Plan 与本轮相关的知识判断。
**把这几样分开**：材料原文、人的结论、你自己的假设、当前产物的表达、历史送审的版本。
同时弄清哪些阶段有产物、哪些已闭环、哪些在途。

先用已有的分析与当前版本建立理解，再回查涉及变化的那几处原文；旧分析可以复用，
但**与原话冲突时以原话为准**。比较基准缺席时明说证据不足，不补造。

产出是一段供后续判断用的工作上下文：这个单做到哪一步、变化之前采用的关键解释是什么、
相关未决与已有的人工修改有哪些。**不是重写一份全量 Spec。**

### 2 解释变化，不是搬运差异

对每一项新材料、意见、直接编辑与上一轮没做完的事，回答四问：它说的是哪件业务事；
相对当前依据改了什么；什么没变；是不是已经落实了，或与既有决定冲突。

- 看起来被删掉的要求，先核它的去向——是撤销了、挪走了，还是新版本只是没重复说一遍。**依据不足不删下游功能。**
- 「同意」「通过」这类笼统表态，先核它针对的是哪条议题、哪一版，再逐条经决策渠道记原话；不把一句「通过」写成对全部议题的复核。
- 人直接改过的稿子，先理解他要表达什么，再决定怎么接回真源。
- 新依据与其他仍有效的来源冲突（上游材料、已归档结论、安全口径），或改动已经承诺的行为时，
  **登记为 `open` 议题，两边来源并列，停下问人**；不按时间最新覆盖，也不替人选一边。

产出按业务主题组织，可以把几条同义输入并成一条，也可以把一段话拆成几件不同影响；
**不要求一个文件差异对应一条语义变化**。

### 3 推演影响与保留项

以变化的对象或行为为中心，沿「前置 → 动作 → 结果 → 责任 → 异常 → 验收」查一遍上下文，
再看已有设计怎么实现它、知识要求是否因此命中或不再命中。对新发现的受影响关系继续查，
直到每项变化在已有产物里都有去向，或明确留下待决、不适用、下游交接。

一个数值变化不只是换一个数字：它可能影响什么时候允许操作、提示怎么写、
接口的拒绝条件、异常路径与验收。**只同步现有材料证实存在的关系**——为了「全链完整」虚构一条不存在的能力，
比漏一条更难发现。

依赖靠你读材料判断，**不建通用依赖图、不用同词命中代替**。影响范围可以扩到必要的关联处，
但业务范围的扩展仍要问人。**列出重要的不变项，每项写出为什么不用改**——防的是「优化一处、损坏另一处」。
已有 Plan 没改的，也要写一句它为什么不受这次变化影响（例如它只跟随某个状态、没写死这次改的值）。

### 4 只在真的需要人时问

只有现有权限与依据定不了的才问：来源冲突、意见含糊、要改已经承诺过的事、范围扩展、大幅重组。
每项给出原来的解释、新信息、可选的处理及其后果与建议；**能在同一轮说完的集中问一次**。

人的决定限定到具体事项与这一次的输入。来源变化使旧的人签不再适用时明说；
**不因为沿用同一个议题编号就沿用他的勾选**。仍未决的事项继续约束相关内容，
但不挡住那些独立且已经明确的修改。

沿既有的决策渠道记录真实原话，说明里引用这些记录；**不另造「人工已批准 = true」这种自证字段**。
议题的决定人只能是人的角色，改版文档不是决定人，也推翻不了人已经做的裁决。

**范围要扩或缩不在这一轮做**：范围由 story 流程的关卡定，update 刻意不进那几级。报「尚未完成：范围需重新拍板」，
写清哪块范围、为什么，`close` 收口并留作保留项；由人走 `reopen` 进范围关卡重拍，范围定了再起一轮 update 更新产物。

### 5 修订最早责任内容，再同步关联产物

| 内容层 | 你做什么 | 不能动的 |
|---|---|---|
| 外部原始材料 | 保留取得的版本与来源，更新本地采用的那一版 | 不替上游重写原话来消掉冲突 |
| 初析 / AR 提取稿 | 修订本需求对来源的理解与承载边界 | 没变的范围与人签复用，没必要不重做初析 |
| Spec / 验收 / 决定 | 修订需求真义、可观察条件、有效与未决结论 | ID 有语义连续性才保留；**不能只改叙事不改真源** |
| Story / Review | 用当前有效解释更新相关叙事、图与议题，保留人工意见的语境 | 不覆盖有效的手改；旧表态不移植到已经变义的问题上 |
| 已有 Plan / 契约 / 用例 | 调整因本次变化失去依据或需要补齐的设计 | 不重写独立有效的部分，不自动推进 coding |
| 还没生成、或本次无权改的下游 | 说明后续要承担什么、为什么 | 不生成不存在的新阶段产物，不冒充已落实 |

原材料与生产真源分开改。接口、验收、知识这些确定性投影仍由既有脚本产生，
**不手改派生区去迎合检查**。story 侧的改动走 `reopen` → `complete` 收口（update 期间沿用本单已定范围）→
改草稿、`chapter` 提交 → `story` 重新登记；update 期间 `reopen` 回到这一轮，新料 `round` 登记进当前轮，不开新轮。

**传播清单**：一项变化逐一核这些位置，改了的与不用改的都要有去向——spec、acceptance、story、review、plan、
contracts、use-cases、AR 提取件与写作设计、`context/facts.md`、会议判断与当前会议结果。

### 6 按关系核对，再说能不能继续

从每项有效变化回查已改的内容，核正常、受限、异常与验收是否一致；从没变的重要关系查有没有误伤；
从待决事项查是不是仍然待决。再核阶段结构、引用、编号与投影。

回查**不要求字面相同**，也不把「旧稿全部保留」当守恒：已经明确取消或被替代的内容应当退出当前版本，
历史留在 `before/` 里。没有新增变化但上一轮的同步没做完时接着做，不按文件摘要提前收工。

产出只有一份当前的 `update-notes.md`：当前依据、变化与影响、决定与修订、**不变项与理由**（一张表：
这次变化牵到却不用改的重要内容，每行写为什么不用改）、核对与剩余。`close` 核不变项表非空，缺了不收口；
只写这一轮真发生的事，没问过的关卡不写成问过。
向用户展示业务上变了什么与可查的差异，**不要罗列对他决定没帮助的脚本步骤**。

## 三、当前做到哪一步，决定这一轮能做什么

| 当前进展 | 默认怎么做 |
|---|---|
| 只有材料或提取稿 | 更新已有的解释与材料，**不顺带把 Spec 生成出来** |
| Spec / Story / Review 已有 | 围绕有效变化核对并同步；本该有却没有的产物，报出这个事实，不用「自动补上」掩盖 |
| Plan 在途 | 改已有的受影响设计，说明其余仍在途；**文件存在不等于那一段已经完成** |
| Plan 已闭环 | 改相关设计、契约、用例与知识落点，再按 framework 的原生修正机制重验 |
| 已归档 | 保留旧的送审依据，更新本地工作稿；**人确认之后才回写** |
| 已到代码或测试 | 文档同步到已有 Plan 为止，标明实现与证据可能失效、接手的人要做什么；**不自动改源码、不碰设备测试** |

范围由这一轮的请求、实际变化与上一轮没做完的事决定，**不默认开展全需求质量翻修**。
核对时撞见与本轮无关的旧问题，记下来交给它的责任方；确实挡住本轮结果正确性的，纳进来并说明为什么。

## 四、报告什么结果

| 结果 | 什么时候成立 | 用户据此能做什么 |
|---|---|---|
| 已同步，可继续当前工作 | 受影响内容已按当前有效决定一致，适用检查完成，没有挡住当前工作的未知 | 在原进展上继续（**不代表需求自动进入下一阶段**） |
| 已同步，有明确保留项 | 业务未决、非阻断建议或代码/测试影响都已说清，没有被写成已完成 | 继续不依赖这些保留项的工作 |
| 尚未完成 | 必要的输入、裁决、同步或验证缺失 | 知道缺什么、影响哪些内容、下一步该谁处理 |
| 核对后无需修订 | 有效变化已经落实过，或只是表达差异、与本单无关 | 保留现稿（**不为留下更新痕迹而重写**） |

本地文件写完了、脚本退出 0、操作记录关闭了，**都不能代替上面这几个判断**。
没有历史版本时可以说「当前无需修订」，但不能说「历史从未发生过变化」。

## 五、与闭环的关系

**哪些阶段要按新的审查对象审一次**：这一轮确实改了该阶段的业务口径、范围、验收或契约实体。
在 update-notes 写一行「业务改动的阶段：spec、plan」（没有写「无」），`close` 核这些阶段有当前对象的 PASS 报告。
只改表达、核对后未修订、只改了过程记录的阶段不派审。按阶段依赖来，先 spec 后 plan；spec 的返修改了 plan 的材料时，
先把 plan 同步好再取它的请求。

派审、采纳与报告回来之后的处置，按 `phases/spec.md`「闭环」一节那张表，本页不另写一份。
派审期间不动被审的材料；本宿主没有 verifier 时，如实报告「这次更新没有完成独立审查」，不用自审顶替。

### 回写需求系统

先把业务结论、可查的差异、未决与验证缺口**展示给人**，他确认之后才回写；
展示之后版本又变了就重新展示一次。回写走既有的 `/story archive`，不另建发布路径。

外部发布失败时**本地正确的修改留着**，重试之前先看外部有没有被别人改过——
重试的是发布这一步，不是把整轮理解与成文重做一遍。
