# S3 规则：材料与范围确认关卡

> [SKILL.md](../SKILL.md)「材料与范围确认关卡」章的展开。**进关卡前完整读一遍**。
> 材料清单、选项集与份表的生成规则在 [init_analysis.md](init_analysis.md) 第 ⑤ 节。

完整提取件 `AR/design.md` 此时**尚未生成**：范围还没定，先生成的完整草稿必然报废。

## 三级，每级只问一件事

```
第一级  材料够不够？     1) 补充材料后继续  2) 材料充足，开始需求分析
第二级  这个范围怎么定？ 1) 按当前范围整体承载  2..n) 分析给出的各具名切法
第三级  本 AR 承载哪份？ 按选定维度的份表逐份列出
```

第二级**有几项取决于分析找出几个可切维度**——分析只找到一个（即「不切」）时就只有一项，
这是正常结果，不是缺漏。

**为什么分开问**：补料问的是材料，定范围问的是范围——挤在一级里，人得同时权衡两件
不相干的事。而它们本有先后：材料不全时范围判断本身就不可靠，在一个还会变的范围上
讨论怎么切，讨论了也白讨论。

**终止条件是「范围已定」**：第二级选了整体承载，或第三级完成定案——都直接进 S4。
补料循环：第一级选 1 就回 S2a（导入 → 重新盘点 → round+1）→ 回第一级，
材料分批到达就多轮补料，循环封闭。

**第一级之前不做需求分析**：那一级只需要材料清单与一句缺口判断。材料不全时做的范围
分析注定作废，每轮补料都要重来——所以分析发生在第一级与第二级**之间**（S2b）。

**选项从哪来**——三级各不相同，这是本关卡最要紧的一条：

| 级 | `--gate` | 选项来源 | 你要做什么 |
|---|---|---|---|
| 一 | `material_scope` | `.gate-options.json` 侧车 | 写侧车（`gate` 写 `material_scope`，key 为 `supplement` / `confirm_scope`），带材料语境的 label |
| 二 | `scope_decision` | **契约 `scope_options`**（来自需求分析的 `.scope-options.json`） | 什么都不用写——**照出契约里的那几项**。分析定几项就摆几项；整体承载项的 key 固定为 `carry_all` |
| 三 | `split_carrier` | **脚本从选定维度的 `parts` 生成** | 什么都不用写——照出各份，key 是 `seq` |

**第二、三级不要现编选项**。分析给几项就摆几项，哪怕只有整体承载一项——
凑数补出来的选项没有份表、没有内容，人看不懂也无从评估，选中之后份表还得接着现编。
脚本从契约取选项，现编的 key 会被直接拒绝。

**人想要分析里没有的切法**：口述修正 → 回 S2b 重做分析（补上该维度、重落
`.scope-options.json`、重跑 `round`），再回到本关卡。这正是「先做完再问」——
分析先行，关卡只负责照出。

**顺序不可跳**：脚本按 `status` 的 `next` 校验——当前这一步不是它说的那一步就直接拒绝。
拿不准走到哪，跑 `story_flow.py status --feature <AR>`。

**怎么呈现**：确认组件（如 AskUserQuestion）可用时**必须用组件**摆选项，同轮消息末尾
再附 portable 编号菜单（`1=… / 2=…`）；组件不可用的宿主才只用编号。
人以编号回复时，`--basis` 记**编号 + 它对应的选项**（`用户回复：2（=按交付阶段切）`）
——光记「2」，离开这次对话就没人知道 2 是什么。

## 第一级：材料够不够

问的时候只给三段（格式见 SKILL「停等消息怎么写」）：**一句盘点结论**、
**一句缺口判断**、**两个选项各一行**。

材料清单四列（源 / 来源 / 是什么 / 状态）写进 `AR/init-analysis.md` 第 ⑤ 节 1，
**不搬进问话里**——人要看清单会去看那份文件，那是它存在的理由。

**这一级不呈现需求分析**——范围、功能清单、切法都还没做，此刻要人回答的只有
「材料够不够」。

**缺口判断必须是结论句**——只列文件名等于没问。

**推荐项由缺口判断决定**：

| 第 ⑤ 节 2 判为 | 推荐 |
|---|---|
| 有缺口（PRD/SE 未归档、关键章节缺失、补录不全） | `1=补充材料`——`inbox/` **路径写全**（`doc/features/<本单号>/inbox/`），不留占位 |
| 无缺口 | `2=材料充足，开始需求分析` |

材料不全时推荐去定范围，是在一个还会变的范围上做决定——**诊断出缺口，推荐就必须跟上**，
否则等于没诊断。**推荐 ≠ 强制**：人照样可以挑另一项。

### 选了补料之后

脚本在选中那一刻校验**料到了没有**，两条路都算数：

- `inbox/` 里除 `README.md` 外有未导入的文件（先签后导：人签完再去放料）；
- 或磁盘材料指纹已经不等于本轮登记的那个（先导后签：料先到了，人再答一句
  「已放进需求目录」）。

两条都不成立 → `rejected`，原地重提；成立 → `accepted`。

**签与导入不分先后**——顺序本来就不该有讲究。不校验就回 S2a 的话，
会拿着同一批材料重新盘点出一模一样的结果，白跑一轮而人以为补过了。

**人回「补充材料」之后，先跑 `decide`，照它打印的下一步走，不要再问一次。**
`accepted` 时它按料的现状告诉你做什么：收件箱里还有原件就直接导入再重跑 `round`；
原件已经进正文、只是材料指纹变了就只重跑 `round`。人已经把料给了，
再问一句「放好了吗」是白等一轮。

### 补料之后什么时候再停

先**用新增的材料重新盘点：上一轮缺的补上了没有**。

- 补上了 → 直接进需求分析，**不再问**。材料够了还把上一轮的选项原样再摆一遍，
  是一次无效的询问：人上一次说的「补充材料」就是对「够不够」的回答。
- 确实还缺 → 写这一级的选项侧车再停一次。第 2 轮起，提出补料请求的那个选项
  （`supplement`）要写 `missing`（还缺什么）与 `why`（为什么现有材料不够）；
  缺了脚本拒收。停等文案按这两个字段写，人看到的就是「还缺什么、为什么」。
  「材料充足，继续」这类不是缺口，不用写。

第 2 轮起，第一级**只在你为这一级摆出选项侧车时停**。判据不看上一轮选了什么——
那样先导后签与先签后导会判出两种结果。侧车要写明 `gate`，
第二级的侧车不会把流程拨回这一级。

## 第二级：范围定法选项集

这一级之前先做完 S2b 需求分析（需求概览 → 本部件视角 → 本 AR 定位 → 待实现功能清单 →
范围定法选项），把定位与选项集落侧车、跑 `round` 登记进契约。

问的时候也是三段：**一句当前范围**（含来源）、**一句要定什么**、
**契约里的选项集原样照出**，每项一行。功能清单与推导写在 `AR/init-analysis.md`，不搬进问话。

**选项集恒定照出**，不因「看着不用切」而省略：人无从推翻一个从未被摆出来的选项。
首项是「按当前范围整体承载」并列出功能点，其余是具名维度的切法（每项写清切成几份、
每份是什么）；推荐项排第一，推导写在选项前的正文里，不写进选项标签。

选整体承载 → 范围就是定位出的那个范围，直接进 S4。
选某个维度 → 进第三级。

**只有整体承载一项时，把出口一起说出来**：分析没找到可行切法，这一问对人来说更像通知
而不是提问——他很可能直接口述一个你没想到的切法。所以问法写成
「分析没找到可行切法，准备按当前范围整体承载；同意就继续，
**想按某个方向切请直接说**，我把那个方向的份表补出来再回到这里」。
出口只写在规则里而不呈现给人，等于没有出口。

### 人提出自己的拆分诉求时

他可能在这一关口述（「本次先做 X」「按 Y 切开」），也可能在任务描述里早就说过。
**那是一次需求讨论的开始，不是一个待映射到选项 key 的答案**——
你需要写一段推理才能把他的话对上某个选项，就说明这件事还没谈清楚。

不要求他的话先长成一个「维度」。按下面五步跟他谈：

1. **落条目**：他说的那部分对应哪些具体功能条目（对照第 ④ 节功能清单与 SR 定位），
   剩下的是哪些条目——**说不清条目，就谈不清范围**；
2. **判归属**：本轮做哪些；留后续的归谁——同 SR 下有兄弟 AR 能承载的写兄弟 AR 单号，
   没有对应单据的写「待立项」；
3. **评合理性**：拿四条判据（独立交付 / 单向依赖 / 稳定边界 / 只落一份）过一遍，
   **卡在哪条就在方案里写明**。判据在这里是**风险标注，不是否决权**——
   他要拆而你觉得切口不干净，就把不干净在哪告诉他，让他带着这个信息拍板；
4. **摆方案、谈**：条目 / 归属 / 依据成表呈现，说清你的理解和建议；
   他改就更新分析再摆，谈到收敛为止；
5. **他确认范围与拆分关系之后**：写 `.split-parts.json`，顺序记录 `scope_decision`
   与 `split_carrier`（他一句话里已经说了承载哪份，就不要再拆成两问），
   `split.decided=split`，S4 按定案的范围收窄。

## 第三级：本 AR 承载哪一份

让人从零描述范围是高成本输入，而你读过全部材料——份表已在初析备好，直接呈现，
人只需认可或改一两句。

按选定维度的份表逐份列出（序、范围一句话、依赖哪几份），取得选择。
**选中的归本 AR，其余份成为关联项**——`carrier` 依次填同 SR 的兄弟 AR 单号
（取初析第 ③ 节的关联清单作建议值），没有对应 AR 的写「待立项」，人可改。

定案后**把整张份表写进侧车文件** `AR/story-src/.split-parts.json`，再跑
`decide --gate split_carrier`：

```json
[{"seq": 1, "carrier": "AR900xx", "scope": "入口与状态展示", "depends_on": []},
 {"seq": 2, "carrier": "<本 feature 名>", "scope": "核心处理链路", "depends_on": [1]},
 {"seq": 3, "carrier": "待立项", "scope": "周边适配", "depends_on": [1]}]
```

- `carrier` 恰有一份是**本 feature 名**——就是人选中的那份，且必须与 `--chosen` 的
  份序号一致（脚本核对：选的与记的对不上就拒绝）；
- 其余写兄弟 AR 单号，没立项的写「待立项」；
- `seq` 是建议执行顺序，`depends_on` 是**须先交付**的那几份（脚本查悬空与成环）；
- 脚本登记后销毁侧车，并从本 AR 那份的 `scope` 推出 `split.scope_text`
  ——**本 AR 的范围只写一次**，两处登记迟早各说各话。

S4 生成时按契约份表转写进 `AR/design.md` 的「本 AR 范围与拆分说明」，并在 spec 阶段照常进
`AR/story-src/decisions.json` 登记 `settled` 决策——**切与不切都要登记**，
评审者必须过目「本 AR 承载哪部分、各兄弟 AR 承载什么」这个结论。
**记文字不记方案编号**——编号离开本次对话就没有意义。

## 用户明说「别逐个问」时，这两级照停

**免不掉。** 材料关卡与范围关卡是本扩展仅有的两处停等点，它们**无条件**——
「别逐个问」免掉的是流程段内其它一切询问（门禁报错要不要修、下一步做什么、
进 harness 还是进 verifier），不包括这两处。

理由不是流程洁癖：这两件事**定错了后面全废**。材料不全时做的范围判断本身不可靠；
范围定错，spec、plan、验收边界跟着一起错。它们值得那两次等待。

**你的判断进推荐项，不进决策。** 缺口判断照做、推荐项照给（见上面的推荐表），
但选哪一项由人回。契约里 `by` 只有 `human` 一个取值，脚本层拦着——
「材料看起来够了就替他确认」这条路不存在。
