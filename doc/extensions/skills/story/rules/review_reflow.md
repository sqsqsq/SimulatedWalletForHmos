# 评审回流规则：按 review.md 修订 spec

> 读者：处置评审意见的主 agent。时机：`/story review` 拉回反馈之后、动手改之前完整读一遍。

评审意见回来之后怎么处置。**输入唯一就是 `AR/review.md`**——人可能在系统上批注、
也可能直接改本地文件，流程不关心来源。

**不重建 story、不重新归档**：story 定稿于评审时点，系统上那份就是评审依据。
重建 story 是人显式发起新一轮评审时的动作，终止权在人，不在流程。

**冻结件登记之后只读。** `AR/story-src/decisions.json` 随 story 登记冻结，
是这份 story 据以成文的判断台账。评审引起的状态变化只记进处置台账 `AR/story-src/review-disposition.json`，
**不回写冻结件**——把评审 status 写回 `decisions.json` 会被门禁拦下，而那是拦对了：
依据一旦可以事后改写，「当时是按什么定的」就查不回来了。

## 1. 逐项处置

每条议题末尾有一处评审人的填写位，形态看议题要人做什么：

| 填写位 | 评审人怎么表态 | 你怎么读 |
|---|---|---|
| 「方案选择：」 | 填上方「可选的做法」里的编号（每项后面写着选它会怎样），或写出另一种方案与理由 | 编号对上哪一项就是选了哪一项；**建议不等于人选了**，没填、或说「通过」而看不出选哪项，都要回去问清 |
| 「审核结果：」带「确认 / 不同意」勾选框 | 勾确认；或勾不同意并写原因与调整结论 | 勾了不同意却没写原因或结论，回去问人要改成什么，不替他补 |
| 只有一行「审核结果：」 | 在后面写自由文字 | 同意、要改成什么、为什么暂缓，由你读那几句话判读 |

评审人不照格式、直接写一句话时，按他实际的意思处理；有歧义就问，不往推荐项上靠。
判读结果落台账（§2），让人复核得到；**提示文字、空框和空着的填写位都不是「同意」**，它们是还没评审。

| 评审人的意思是 | 处置 |
|---|---|
| 同意、确认，或选了与已写方案一致的那项 | 不动 |
| 选了另一项、不同意、要改什么 | 按他说的那件事定位 `spec/spec.md` 里对应的编号或小节，改（走 correction 闭环，见 §3）；待定的议题因此有了人的决定，在台账里记下他选的是什么 |
| 暂缓（写了原因） | 记台账、标挂起，不改产物 |
| 空着或看不出表态 | 记台账标「未评审」，不当作同意 |
| **其他意见**（review.md 末尾那一章） | 判类型：**需求类**→改 spec；**叙述类**→记台账，本轮不动产物 |

其他意见有正式落点：`review.md` 的「其他意见」一章
（`<!-- freeform-zone -->` 区内，`build` 逐字节保留，不会被重建冲掉）。
起草方没登记成议题的事——缺的分支、该复用的既有能力、遗漏的埋点——都写在那里；
人写在别处（如某个议题的表单里）时照样处置，但落台账时要注明它写在哪。

其他意见没有对应的议题，是需求缺失还是叙述不清**只能由你判**。
判错的代价是需求被漏掉，所以**判断结果必须落进台账供人复核**——
这类判断不能只存在于你的推理里。

**「改哪一条」也是你的判读**：登记表里没有指向 spec 编号的字段——那种字段会被填成
泛词，指不准反而误导。评审人说的是业务上的哪件事，你去 spec 里找承载那件事的条目；
找不到唯一落点时，把候选一并写进台账，别自己选一个悄悄改。

## 2. 处置台账 `AR/story-src/review-disposition.json`

交代每条意见的去向。读者是人（想知道意见到哪儿去了）与下游 plan（参考未处理项）。

```json
{
  "reqNo": "<AR>", "at": "<YYYY-MM-DD>",
  "items": [
    { "from": "DEC-003", "verdict": "revise", "disposition": "spec.md F1/AC-1 已改" },
    { "from": "DEC-007", "verdict": "defer",  "disposition": "挂起：等法务确认" },
    { "from": "freeform#1", "kind": "narrative",
      "text": "<原话摘录>", "disposition": "本轮不处理（story 不重建）" }
  ]
}
```

`from` 用议题编号或 `freeform#<序>`；自由意见须带 `kind`（`requirement` / `narrative`）
与 `text` 原话摘录——**分类是你做的判断，原话是人写的事实，两者都要留**。

## 3. spec 改动走 framework 既有的 correction 闭环

`--correction-init --q-requirement y` → 根因判 spec 层 → 级联重验下游已闭环阶段
→ `--correction-check` 收口。**不另造状态机**。

## 4. 归档后的边界

`AR/review.md` 的**人工区**归人所有——每条议题末尾 `方案选择：` 或 `审核结果：` 之后那几行，以及
`<!-- freeform-zone -->` 到 `<!-- /freeform-zone -->` 之间的「其他意见」章。
`story-build.mjs build` 不再重建人工区，只备份；结构（议题标题、澄清正文、请谁确认）
仍由渲染器按 `decisions.json` 生成。人可以自由编辑人工区，不必担心被下一次 build 冲掉。

### 回传意见写到哪

评审人可能把意见给在别处（邮件、聊天、整份带批注的文档）。往回落的时候：

| 意见的形态 | 落到哪 |
|---|---|
| 针对某条议题的表态 | 那条议题的填写位（「方案选择：」或「审核结果：」）后面 |
| 没有对应议题的意见 | 「其他意见」章（`freeform-zone` 之内） |
| 整份带批注的文档 | **不得整份覆盖 `AR/review.md`**——逐条摘回上面两处 |

整份覆盖会把渲染器生成的结构一起替换掉，下一次 `build` 与人手改的正本就对不上了；
原批注件由既有备份机制留在 `.review-backup`，需要溯源时去那里看。

## 5. 快照与修正的边界

**停在评审时点的是送审的那一份，不是当前产物。** 冻结件不回写、人工区不整份覆盖，
说的是「当时按什么定的要查得回」；当前的 `spec.md`、plan 与契约照常按人的新决定改，
真发现的缺陷照常修。记进台账、并且让下游实际取到当前依据，这条意见才算闭合——
同一版产物内部自相矛盾是缺陷，送审快照与当前产物有差异且差异有记录，是合法状态。

spec 修订后，系统上的正文（归档时的 story）停在评审时点，不再反映最新 spec。

- 对下游无影响：plan/coding 看的是 spec；
- 对后来查阅需求的人是**潜在误导**——系统上的叙事停在评审那一刻。

台账里注明「本轮 spec 已修订 N 处，系统正文未同步」，是否手工更新由人决定。

## 已经开工的 plan 怎么办

交付门之后两条路可以并行开始，**这不等于下游可以不管上游变更**。评审回流改了
`spec.md` 而 plan 已经在做时，按 CLAUDE.md 的修正三问定落点，走 framework 的
`--correction-init` 与 `--revalidate`：只改根因层的产物与代码，受影响的 plan 产物
按既有修正流程更新，不重走六阶段、不另建 feature。
