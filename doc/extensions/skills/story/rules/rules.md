# story / review 撰写红线

适用：spec 阶段成文的 `AR/story.md`，与同阶段登记并渲染的 `AR/review.md`。

**每条都标了执行通道**，这决定它对你意味着什么：

| 通道 | 含义 |
|---|---|
| `[机械]` | 由 `story-build check` 检查，违反会被拦下并给出具体位置 |
| `[你]` | 没有任何脚本能替你把关，写得好不好由人和独立评价者判断 |

---

## story

1. `[机械]` **先分配后渲染**：先给每个来源单元定一个落点（哪一章讲它），再按合同顺序
   一次写一章、追加落盘。标题与顺序由 `contracts/story-chapters.json` 定；确实不涉及的章
   正文恰好写「本需求不涉及。」一句，不删标题、不留空节。
   **同一个事实只出现一次**——由「一个单元一条记录一个落点」强制，不靠作者自觉。

2. `[机械]` **材料单元全部有落点**：`story-build init` 把材料切成来源单元，`audit` 给每条一个落点，
   三态之一：`at`（写进了那一章）/ `covered_by`（被另一条已进正文的单元承载）/ `machine_facing`
   （机器面登记项，只能由枚举器打标）。机器定得了的它自己填；定不了的你填章名，
   **由裁决者逐条裁「讲清没讲清」并从 story 抄引文**。三态之外即 FAIL。

3. `[机械]` **表达形态不降级**：材料里的图与流程图单元必须有落点；图片按归档件的相对路径引用，
   全篇唯一、有 alt 文本。不写裸文件名、不写源材料目录名——归档件随需求交出去，
   路径解析不到就是断链，评审者看到的是一个红叉。

4. `[机械]` **编号形态**：`id_shapes.keep` 的验收编号要在「验收」章逐条给出可观察条件，每个原始编号独立一行；
   `drop` 的仓内工作编号不进归档件。标题与含义必须来自权威规格件原文，不得凭记忆编造。

5. `[机械]` **规约逐条判定成表**：激活清单里的每个规约条目，在附录的「规约判定」小节里一行，
   或其整域一行「整域不适用」。表头 `| 规约 | 编号 | 判定 | 依据 |`，判定三选一
   （命中 / 不命中 / 整域不适用），依据非空。**这张表里出现规约编号是允许的**——
   它是给评审者的完备性回显；主叙事里仍写中文规约名，不写编号。
   判「不命中」也要给依据：「不涉及」三个字不是依据，「本需求无新增对外开放页面或接口」才是。

6. `[机械]` **归档件自包含**：不出现仓内路径、裸文件名、内部规则文件名。引用随归档的兄弟文件写
   《决策与评审记录》，不写文件名。上游文档以单号或系统链接引用。
   不用「灰度、回滚、部署、集群、QPS、熔断限流」等服务端发布术语，
   改说功能开关、管理台放量、随版本发布。（词表在 `lint-rules.mjs`。）

7. `[你]` **独立可读**：评审者不打开 spec、PRD、SE，也能说清整个需求由哪些系统完成、各自负责什么、
   用户完整经历、本部件只负责哪一段、**本 AR 又承载其中哪部分**（拆分时还要说清兄弟 AR
   各承载什么、先后与依赖）、边界与风险在哪。三层由粗到细，缺中间一层评审者就接不上；
   第三层怎么写按流程契约判，**三形态见 [`ar_design_init.md`](ar_design_init.md) §3**
   ——「无拆分」不等于「承载全部」。

8. `[你]` **有判断**：写清当前方案、被否方案、取舍理由和风险影响。理由不因篇幅被删——
   合同不设篇幅上限，每章写到足以支撑对应判断为止。

9. `[你]` **只讲产品与方案**：不解释 Skill、模板、生成流程、门禁、归档或 AI 自己。
   读者是评审者，不是这套工具的使用者。

## review

1. `[机械]` **议题由 `decisions.json` 渲染**：状态分章、类型成节、三级编号、陈述句标题、
   分段正文、「请…确认」与「审核结果：」一行，都由 `story-build build` 按登记表生成。
   重跑按登记表重算机器区，**人工已填写的内容一个字节都不会变**。

2. `[你]` **review 是判断的台账，不是待办清单**：已有结论的决策（`status: "settled"`）同样登记、
   同样带表态位。评审者要先知道本需求做了哪些判断、结论各是什么，才谈得上判断对不对。
   准入判据见下面「什么是议题」那一段——三处同一份文字。

3. `[机械]` **议题与登记表一致**：review 里出现未登记的议题、登记的议题没有渲染出来，都会被拦下。

4. `[你]` **议题标题是陈述句**：已定的陈述结论（「界面不做像素级还原」），
   待定的陈述事项（「自动充值入口的摆放位置」）；不用疑问句、反问句，
   也不写「待定项 / 决策队列 / 实现契约」这类分类词。

5. `[你]` **结论要能被直接表态**：结论或建议必须是实质内容而非占位，责任人写到具体角色，
   评审者只需点头或改。

6. `[你]` **AI 只起草，不替人确认**：`AR/review.md` 的表态位——「审核结果：」后面那几句话
   ——只能由评审人填，你只写到机器区为止。人工审核、修改回写与定稿由后续的
   `/story review` 承担。判断「评审做完没有」看的是每条「审核结果：」后面有没有内容，
   不是任何一行状态字。

### 什么是议题（正面定义）

**什么算一条议题**：review 是**判断的台账**——已决策的呈现结果供评审人过目，
不确定、矛盾、错误的要人评估。准入判据只有一条：**评审人对这条表态「不同意」，
会有产物要改**；表态没有后果的不占表态位，材料直接给定、没有判断参与的纯事实复述不进。
从材料到方案之间凡发生过一次判断、或还等着人判断的，每处一条——材料没说而本轮定的、
材料打架而本轮定源的、材料有错或与工程现状矛盾的、材料明说未决的、需求做不到而降级承载的、
关键取舍，以及跨方依赖的确认点（对方表态变了产物就要改）。已定的登记 `settled`
（正文落点是关键取舍），未定的登记 `open`（去处是评审记录），没有第三种去处。
**把材料里没有的选择写死进正文或附录，就是漏登记。**

### 登记字段（`AR/story-src/decisions.json`）

```json
{"id": "DEC-001",
 "status": "open",
 "category": "<十一类扫描表里的一类，见 phases/story-write.md>",
 "title": "<陈述句短标题：已定的陈述结论，待定的陈述事项；不用疑问句、反问句>",
 "clarification": "<带小标题分段的正文，见下>",
 "decider": "<具体角色>"}
```

`clarification` 是**分段的自然叙述**，不是字段拼接：

| status | 三段 |
|---|---|
| `settled` | `**要定的事**`（事项与冲突、疑问所在）／`**根据**`（材料怎么说、查了什么、问过谁）／`**结论与影响**`（定了什么、对交付意味着什么） |
| `open` | `**要定的事**`／`**可选的做法**`（编号列出每个选项和它的影响）／`**建议**` |

小标题之下写向同事解释的完整句子。压缩名词串、维护流程黑话、冒号分号串联的电报体都不合格。
**`**根据**` 必须指名材料或核查**——哪份稿的哪一节怎么说的、查了工程的什么；
说不出依据的判断，评审人没法复核，只能凭信任盖章。

`category` 决定它在评审记录里成哪一节。渲染时分层与编号都由脚本生成：
一级按状态（待确认事项 / 已定事项 / 其他意见），二级按类型成章（有才立，没有不立空章），
三级是评审项本身，编号 `N.M.K` 顺出——登记表里不存序号。
决策有增改时改 `decisions.json` 再 `build`——机器区按登记表重算，人工已填写的内容逐字节保留。

## 完成动作

```bash
node doc/extensions/skills/story/scripts/story-build.mjs build --feature <feature>
node doc/extensions/skills/story/scripts/story-build.mjs check --feature <feature>
```

两条全绿只说明**没有明显缺陷**，不说明这是一份好的评审材料。
后者由人和独立评价者判断——上面标 `[你]` 的那些条正是他们要看的。
