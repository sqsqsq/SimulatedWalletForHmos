# story / review 撰写红线

适用：spec 阶段同批生成 `AR/story.md`、`AR/review.md`。

**每条红线都标注了执行通道**，这决定它对你意味着什么：

| 通道 | 含义 |
|---|---|
| `[结构]` | 由流程与装配器保证，你按流程做就不会违反；试图绕开会装配失败 |
| `[机械]` | 由脚本检查，违反会被门禁拦下并给出具体位置 |
| `[你]` | 没有任何脚本能替你把关，写得好不好由人和独立评价者判断 |

---

## story

1. `[结构]` **章节由合同定义，逐章成文**：不存在「一次写完整篇 story」这个动作。
   每章的取材源、必答问题和强制表达形态由 `contracts/story-chapters.json` 声明，
   `scaffold` 为每章生成**写作任务书**（取材路标 + 必答 + 判据），不复制源材料。

   **写完的判据**：打开任务书列出的每份取材源，其中的每个事实点——数据、条件、
   分支、约束、名词、表格行——都要写进本章；可整合、可改序、可换措辞、
   可换更清楚的表达形态，**不可少一条**。一次只写一章：写完本章，再开下一章。

   装配时会逐章核对源里的表格行、数值参数与反引号标识是否都在正文；
   缺了会指明是哪章缺哪几个，补齐即可。
2. `[结构]` **表达形态与数量不得降级**：源材料用流程图、状态机或表格表达的内容，
   对应章节必须保持同类形态，且图的数量不少于源。把流程图压成 `A → B → C` 箭头文字、
   或三张图只留一张，都会被装配拦下。图画得对不对、分支全不全，仍归你和评价者。
3. `[结构]` **决策先登记再引用**：任何决策性内容——无上游依据的设定值、需要人拍板的问题、
   以及**上游已定但开发必须遵守的结论**——都先在 `decisions.json` 建条目，正文只写 `{{DEC-00X}}`。
   你**没有**「须产品确认」这类措辞可写，也不该在正文直接给出决策结论；引用是唯一出口。
   悬空引用与裸 `DEC-00X` 编号都会装配失败。
   **条目字段照 `scaffold` 建好的骨架里那条 `_example` 填**，不要凭记忆造字段名；
   格式或字段不对时装配会失败并回报正确形状，不会静默当成空表。
   **一条都没有时不能就这么空着**——那和「忘了登记」在产物上长得一模一样：
   确认过确实没有，写 `{"decisions": [], "none_reason": "<为什么没有>"}` 显式声明。
4. `[结构]` **编号含义单源**：被引用的验收、场景、功能编号登记在 `ids.json`，附录由装配器渲染。
   标题与含义**必须**来自权威规格件原文，不得凭记忆编造。`landing`（本需求落点）是可选字段，
   填了 story 附录就多一列、没填就只出两列；review 附录恒为两列、不含落点。
   正文写 `{{ID:编号}}` 引用，装配器按位置渲染——表格里出裸编号（含义查附录），
   散文里出「标题（编号）」，你不必区分写法。
   字段同样照骨架里的 `_example` 填；空表同样要 `none_reason` 显式声明。
   **规约条目不进这张表**——它们走下面第 5 条的知识判定登记表。
5. `[结构]` **知识判定逐条登记**：本阶段要对**激活清单里的每一个规约条目**给判定，
   登记在 `knowledge.json`，附录由装配器渲染成一张「规约符合性」表（所有域同表同粒度）。

   - **条目清单从激活清单来**，你不需要也不应该自己列域：跑一次 `build` 会告诉你漏了哪些条目。
     登记了不在册的编号同样失败——那说明编号写错了，或那条规约已经下架。
   - **判「否」也是判定**，也要写不命中的依据（「不涉及」三个字不是依据；
     写「本需求无新增对外开放页面或接口」才是）。
   - **判「是」的结论要写本需求的设计**：它落在哪个接口、哪个存储键、哪个字段、哪个业务步骤上。
     写之前先自问三句：① 这句话里有没有本需求自己的名字？② 把编号遮住，这句还能指导编码吗？
     ③ 它是不是把规约原文换了个说法？三问任一答错就重写——
     **规约原文的复制或子串会被装配拦下**，同义改写则会进评审的必答清单。
   - **要求列由装配器从规约原文渲染，你不要手抄**：手抄必然与原文分叉，而评审者核的正是原文。
   - **设计模式只登记候选，不做选型**：逐个适用单元写候选与命中信号；
     **单元怎么切由激活的模式索引定义**，照它切；候选只能从在册 `pattern_id` 里查表填。
     **零候选是正常结论**，但要显式登记单元与「为什么都不需要」——
     选型是 plan 的事，那里才有方案上下文。
6. `[结构]` **规约含义写中性事实**：不少规约原文把「是什么」和「谁来拍板」写在一句话里
   （例如「支付类功能默认受限，例外须产品确认」）。写判定结论时只取**中性事实**那半句，
   把「例外由谁定」登记成一条决策。
   照抄整句会把议程措辞带进 story 附录，装配会失败。
   忠实引用指的是不曲解规约要求，不是逐字复制标点。
7. `[机械]` **可标识事实不丢**：spec 的编号、术语与技术契约标识，在 story 全文任意位置有落点即可——
   可整合、可改序、可换措辞，但一条都不能少。
8. `[机械]` **归档件自包含**：不出现仓内路径、裸文件名、内部规则文件名。引用随归档的兄弟文件写
   《决策与评审记录》，不写 `review.md`。上游文档以单号或系统链接引用。
9. `[机械]` **客户端语境用词**：不用「灰度、回滚、部署、集群、QPS、熔断限流」等服务端发布术语，
   改说功能开关、管理台放量、随版本发布。
10. `[你]` **独立可读**：评审者不打开 spec、PRD、SE，也能说清整个需求由哪些系统完成、各自负责什么、
   用户完整经历、本部件只负责哪一段、**本 AR 又承载其中哪部分**（拆分时还要说清兄弟 AR
   各承载什么、先后与依赖）、边界与风险在哪。三层由粗到细，缺中间一层评审者就接不上；
   第三层怎么写按流程契约判，**三形态见 [`ar_design_init.md`](ar_design_init.md) §3**
   ——「无拆分」不等于「承载全部」。术语章给出本需求全部业务与技术术语的
   统一定义（人读两列：术语、含义），机器面字段不带入。
11. `[你]` **有判断**：写清当前方案、被否方案、取舍理由和风险影响。理由不能因为篇幅被删——
   合同不设篇幅上限，每章写到足以支撑对应判断为止。
12. `[你]` **只讲产品与方案**：不解释 Skill、模板、生成流程、门禁、归档或 AI 自己。
    读者是评审者，不是这套工具的使用者。

## review

1. `[结构]` **议题由 `decisions.json` 渲染**：每个议题的问题、结论或建议、理由、影响、来源、
   责任人和三选一表态位都由装配器生成，格式一致、不会漏项。重跑装配按登记表重算机器区，
   **人工已填写的内容一个字节都不会变**。
2. `[你]` **review 是决策全景，不是待办清单**：已经有结论的决策（`status: "settled"`）同样登记、
   同样带表态位。评审者要先知道本需求做了哪些决策、结论各是什么，才谈得上判断对不对。
   准入按实质影响：开发必须理解、遵守或实现的就进，纯事实复述不进。
3. `[结构]` **不承载需求叙事**：review 附录只渲染「编号 / 标题与含义」，落点列不存在——
   评审者要看需求方案就去 story。
4. `[机械]` **议题与登记表一致**：review 里出现未登记的议题、登记的议题没有渲染出来、
   或机器区与登记表对不上，都会被门禁拦下。
5. `[你]` **议题标题是人话**：写评审会上真会说出口的问题或决策句（形如「某指标是否定为 X？」），
   不写「待定项 / 决策队列 / 实现契约」这类分类词。
6. `[你]` **结论要能被直接表态**：结论或建议必须是实质内容而非占位，责任人写到具体角色，
   评审者只需点头或改。
7. `[你]` **AI 只起草，不替人确认**：表态位与状态行由人来填。首版产出后状态保持
   `**状态**：草稿（待开发确认）`，人工审核、修改回写与定稿由后续的 `/story review` 承担，
   不在本流程内。

### 决策从哪找（逐类扫描，六类缺一不可）

准入判据见上面 review 第 2 条（实质影响）；这张表回答的是**去哪找**——
凭印象收集必然只收到最显眼的那几条。

| 来源 | 找什么 |
|---|---|
| PRD 产品规则 | 阈值、默认值、开关策略、边界规则等直接约束实现的产品结论 |
| SE 技术约定 | 接口、存储、有效期、隔离、清理、兼容与恢复策略 |
| 工程设定值 | 无上游依据、由起草方设定的数字与默认值。**装配时会逐个数值回查**：上游原文里没有、又没有决策承载的，一律拦下（比对的是值，与你在正文怎么描述它无关） |
| 约束规约命中项 | 合规判定中命中的规约及其落实方式 |
| 上线与协同 | 上线顺序、依赖是否阻塞、跨团队需知悉或配合的事项 |
| **AR 拆分与承载** | 本 AR 是否需要拆分、承载哪部分、兄弟 AR 各承载什么与先后依赖。**拆与不拆都登记一条 `settled`**——「无需拆分」同样是评审者必须过目的结论，空着分不清「判过了不用拆」与「压根没想这件事」 |

### 登记字段（`AR/story-src/decisions.json`）

```json
{"id": "DEC-001",
 "status": "open",
 "question": "<人在评审会上真会说出口的问题句>",
 "proposal": "<可直接审核的实质结论>",
 "rationale": "<依据：上游文档、约束规约、代码库现状，或说明为何是工程设定>",
 "impact": ["<受影响的验收编号>", "<受影响的章节>"],
 "source": "<上游已定 / AI 设定（无上游依据）/ 约束规约>",
 "decider": "<具体角色>"}
```

`status: "settled"` 的条目把 `proposal` 换成 `conclusion`（已定的结论），其余字段相同；
渲染时开放项排在前、已定项在「已定决策（请逐条过目）」一节。
决策有增改时改 `decisions.json` 再 `build`——机器区按登记表重算，人工已填写的内容逐字节保留。

## 完成动作

```bash
node doc/extensions/skills/story/scripts/story-build.mjs build --feature <feature>
node doc/extensions/skills/story/scripts/story-build.mjs check --feature <feature>
node doc/extensions/skills/story/scripts/merge-story.mjs --feature <feature> --check
```

三条命令全绿只说明**没有明显缺陷**，不说明这是一份好的评审材料。
后者由人和独立评价者判断——上面标 `[你]` 的那些条正是他们要看的。
