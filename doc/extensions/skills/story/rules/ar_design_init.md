# ar_design_init — AR/design.md 生成规则

从 `RR/prd.md`（产品 PRD）+ `SR/design.md`（SE 系统级设计）提取生成 `AR/design.md`，作为 /spec 的输入。

**定位**：AR/design.md 是**部件视角的需求输入件**——只承载「上游要本部件做什么」。开发侧内容（方案、异常、安全、DFX、兼容性、测试）由 spec/review/acceptance 在后续流程中产出，archive 时以评审载体覆盖归档回单据字段。生成前完整阅读本文件四段内容（本部件申明 / 交互方清单 / 提取原则 / 生成规则）。

## 1. 本部件申明（裁剪的第一标尺）

- **部件名称**：单框架钱包 / 纯鸿蒙钱包 / 钱包客户端 / WalletForHMOS（上游文档中出现上述任一称谓，均指本部件）
- **部件职责**：承载手机侧华为钱包应用的功能与需求；**包含**通过蓝牙连接穿戴设备后对其卡片进行远程管理的穿戴卡包功能；**穿戴设备上独立运行的钱包应用不属于本部件**
- **运行形态**：手机应用

职责范围具体化：卡证票券（银行卡、交通卡、门钥匙、证件、票券）在手机上的添加、展示、使用与生命周期管理。凡与之无关的上游内容，不属于本部件需求。

## 2. 交互方清单（裁剪的第二标尺）

判定上游内容「是否与本部件相关」时，按以下六类交互方逐一核对：

| # | 交互方 | 交互方式 | 说明 |
|---|---|---|---|
| 1 | 服务器接口 | HTTP/RPC 请求 | 本部件对钱包云侧服务发起的调用（接口、时序、错误码） |
| 2 | 元服务 | 卡片/轻量化形态 | 元服务卡片承载的入口与展示 |
| 3 | H5 | web 容器 | H5 页面承载的业务流程（活动页、协议页等） |
| 4 | 手机系统接口 | 系统 API/权限 | 系统能力依赖：权限、卡片框架、NFC 控制器、蓝牙等（刷卡、门禁、车钥匙等近场交互经此类能力实现） |
| 5 | 其他手机应用 | 拉起/被拉起 | 收银台、银行 app、deeplink/want |
| 6 | 穿戴设备 | 蓝牙远程管理 | 手机侧对穿戴设备卡片的远程管理（穿戴侧独立运行的钱包 app 不属本部件，见 §1） |

上游内容命中任一交互方 → 与本部件相关，纳入提取；均不命中（如纯云侧内部改造、其他部件独立排期项）→ 不纳入，仅在「上游索引」登记为「不消费」。

## 3. 提取原则

1. 本部件**直接参与**的部分需提取；
2. 本部件**相关场景**需提取；
3. **不涉及的场景不列出**；
4. 对外依赖**只保留与本部件的交互**（对方内部实现不提取）；
5. **交互边界明确**——每项提取内容都要能指出命中 §2 哪一类交互方；
6. **双源互补**：`RR/prd.md`（产品级需求背景与价值描述）与 `SR/design.md`（系统级技术方案）**同等提取，二者平等**——不得只读 SR 而把 RR 当背景略过，也不得只读 RR 而遗漏 SR 的技术约束。

## 4. 生成规则（需求提取五段结构）

通读 `RR/prd.md` + `SR/design.md`（§3 原则 6：双源平等），以 §1、§2 为标尺、§3 为方法做单部件裁剪，按以下固定结构生成（init 产出的空模板即此骨架，补全而非重写）：

```markdown
# <AR> <需求名> — 开发需求（AR）

## 1 简介
### 1.1 需求介绍          ← 一段话（取自 RR 业务背景 + 功能要求主旨）
### 1.2 相关文档链接      ← 表：SR/AR 单号 | PRD | SE 设计 | UX 设计（系统内链接）——必填，
                            归档件 story.md 的上游引用唯一来源

## 2 需求分析
### 2.1 场景与功能点      ← 按 RR 逐场景列功能点（本部件视角），每项标注命中的交互方（§2 六类之一）
### 2.2 验收意图          ← 取自 RR 验收要求

## 3 SE 方案摘要（本部件相关）
### 3.1 全局方案与部件分工  ← 整体怎么做（一段）+ 三方各承担什么（本部件/云侧/其他部件，逐条一句）
                            + 依赖与上线顺序约束（谁先谁后、是否互相阻塞）。
                            这是**评审全局视角的唯一承载点**：评审者据此判断本部件承担的部分是否正确
### 3.2 本部件方案要点与流程骨架
                          ← 每项一句话 + SR 章节指针，不复述细节；
                            上游含流程图/时序图时给**一句话骨架**
                            （入口 → 关键节点 → 终态 → 主要分支去向），不转载不重绘

## 4 上游索引              ← 表前**必须**先写一行「原文位置」说明（见下方「上游原文位置」），
                            再列表：| 信息类别 | SR 章节 | 本流程消费步骤 |
                            信息类别逐类扫描见下方「上游信息类别清单」；
                            均不命中边界的上游章节登记「不消费」

## 5 上游已声明线索        ← 对外依赖/配置项/打点的名称清单，线索级：只列名称+指针（细节看 SR）
```

**上游信息类别清单（§4 逐类扫描 RR/SR，登记命中项）**：

| 信息类别 | 下游消费方 |
|---|---|
| 整体方案与三方分工 | **AR §3.1**（评审全局视角的唯一承载点——评审叙事件的「需求范围与部件分工」全靠它，AR 没写清楚下游补不出来） |
| 业务流程 / 交互时序 | AR §3.2 一句话骨架 + spec 业务流程图（该章节是 spec 强制项，须按 SR 原文建模；AR 只索引不转载） |
| 端云接口（含入参出参字段） | spec §9.1 端云接口 |
| 异常与错误码 | spec 异常处理 + spec §9.1 端云接口 |
| 跨部件交互与**调用方声明** | spec §9 技术契约（对外面）+ §7.3 安全性要求 / 《评审记录》的跨团队协同 |
| 系统级存储 | spec §9.2 数据存储 |
| 配置管控（开关 / 默认值） | spec §9.3 配置项 |
| 打点 | spec §9.4 埋点 |
| 非功能约束（时效 / 频次 / 重试 / 缓存策略） | spec 非功能（§7.1 触发频次行）+ acceptance NFR + story 应用域约束回显（DFX、环境异常） |
| 安全与合规要求（加密 / 敏感数据 / 登录态 / 权限） | spec §7.3 安全性要求 + story 应用域约束回显·安全隐私 |
| 版本与配套约束（历史版本兼容 / 端云上线顺序） | spec §9.3 配置项 + story 兼容性自检 + 《评审记录》的上线时序 B4 |
| 依赖的 SDK / 组件 / TA | spec §9.5 依赖变更 |
| 术语与命名（业务术语 / 字段名 / 事件名） | spec 术语消歧（该步骤是 spec 的强制入口，术语缺失会导致映射错位） |
| 上游已定的方案边界（被否方案 / 明确不做的） | spec（防止下游重新提出已被否决的方案） |

**登记与否的判定（元规则）**：该内容会不会成为下游某产物的**必填输入或硬约束**？会 → 必须登记（正文可只写一句话，细节留在 SR）；纯对方内部实现（云侧微服务拆分、其他部件独立排期）→ 登记「不消费」。本清单是**参考不是穷举**——SR 中清单外的硬约束同样登记。

**上游原文位置（§4 表前必写，一行）**：

```markdown
> 本索引的 SR 章节号指向 `SR/design.md`（与本文件同在 `doc/features/<AR>/` 工作区，PRD 为 `RR/prd.md`）；
> 下游步骤（/spec 及其技术契约与合规判定取证）须按索引直读该文件原文，不得仅凭本文摘要推断。
```

**不做的事**：

1. 不生成开发侧章节——实现方案→plan、页面/异常→spec、安全/配置→spec §7/§9、合规与兼容判定→story 影响面、测试→acceptance.yaml；
2. 不复述 SR 细节——引用替代转载：§3.2/§4/§5 是「一句话 + 指针」粒度（§3.1 全局分工按其自身要求成段）；
3. 不复制或重绘上游的流程图/时序图——图以 SR 为准、以 spec 业务流程图为建模载体；
4. 已有非空 AR/design.md 时不静默覆盖（须经用户确认）。
