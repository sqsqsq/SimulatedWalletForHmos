# ar_design_init — AR/design.md 生成规则

从上游材料提取生成 `AR/design.md`，作为 /spec 的输入。**输入四源**（存在即读，彼此平权）：

| 源 | 是什么 |
|---|---|
| `RR/prd.md` | 产品 PRD |
| `SR/design.md` | SE 系统级设计 |
| `AR/design.md` | 本文件的**现状**（需求系统可能已预填部分内容） |
| `AR/upstream.md` | 人工补录的本部件补充材料（存在时） |

现状与补录材料**与 RR/SR 同等参与提取，无「必须保留原文」义务**——它们是输入，不是需要
逐字守护的既有产物；有价值的内容自然被吸收，如同 RR/SR 里的内容一样。

**定位**：AR/design.md 是**部件视角的需求输入件**——只承载「上游要本部件做什么」。开发侧内容（方案、异常、安全、DFX、兼容性、测试）由 spec/review/acceptance 在后续流程中产出，archive 时以评审载体覆盖归档回单据字段。四段：两把裁剪标尺 / 提取原则 / 生成规则 / 不做的事。**第一段指向部件画像（路径见任务包第 2 节的项目事实清单），须一并读完。**

## 1. 两把裁剪标尺（读部件画像）

「本部件是谁、承担什么、与谁交互」是**工程级事实**，权威在部件画像，本文件不复述——
它换个工程就变，而下面的提取原则不变。生成前完整读一遍画像，取其两节作标尺：

| 标尺 | 画像章节 | 怎么用 |
|---|---|---|
| 第一标尺·部件申明 | 画像 §1 | 上游文档里出现画像列出的任一部件称谓，即指本部件；职责范围之外的上游内容不属本部件需求 |
| 第二标尺·交互方清单 | 画像 §2 | 逐类核对上游内容命中哪类交互方；每个功能点须标注命中的交互方类别 |

上游内容命中任一交互方 → 与本部件相关，纳入提取；均不命中（如纯云侧内部改造、其他部件独立排期项）→ 不纳入，仅在「上游索引」登记为「不消费」。

## 2. 提取原则

1. 本部件**直接参与**的部分需提取；
2. 本部件**相关场景**需提取；
3. **不涉及的场景不列出**；
4. 对外依赖**只保留与本部件的交互**（对方内部实现不提取）；
5. **交互边界明确**——每项提取内容都要能指出命中**画像 §2** 哪一类交互方；
6. **多源互补**：`RR/prd.md`（产品级需求背景与价值描述）与 `SR/design.md`（系统级技术方案）**同等提取，二者平等**——不得只读 SR 而把 RR 当背景略过，也不得只读 RR 而遗漏 SR 的技术约束；`AR/design.md` 现状与 `AR/upstream.md`（存在时）同为输入，一并通读；
7. **AR 范围裁剪**：一个 SR 可能拆成多个 AR。凡本 AR 承载范围之外的内容**不展开提取**，但须在 **design.md §4** 上游索引登记去向（「范围外，归属 ARxxxx / 待立项」）——不展开不等于不交代，评审者要看得到全貌。**只有同 SR 无其它 AR 时范围才等于全集**（§3 形态 ①），本条不触发；
「无拆分」不等于「单 AR」——无拆分但有兄弟 AR（§3 形态 ②）时范围仍是真子集，本条照常触发。

## 3. 生成规则（需求提取五段结构）

通读四源（见文首输入表，本文 §2 原则 6：多源平等），以**画像 §1、§2** 为标尺、
本文 §2 为方法做**单部件 × 本 AR 范围**裁剪（本文 §2 原则 7），按以下固定结构生成（init 产出的空模板即此骨架，
补全而非重写）：

```markdown
# <AR> <需求名> — 开发需求（AR）

## 1 简介
### 1.1 需求介绍          ← 一段话（取自 RR 业务背景 + 功能要求主旨）
### 1.2 本 AR 范围与拆分说明
                          ← 三选一，**按流程契约的 positioning 与 split 判**，不凭印象写。
                            这一节必填，空着评审者分不清「没拆」与「忘了写」。
                            ① **未切分 + 同 SR 无其它 AR**（`sr_related_ars` 为空）：
                              「本 AR 承载全部需求，无拆分」+ 本 AR 范围一句。
                            ② **未切分 + 同 SR 有其它 AR**：不能写「承载全部需求」
                              ——有兄弟 AR 时这句话是假的。写
                              「本 SR 关联 N 个 AR，本 AR 承载 ___（来源：标题/预填/取全量）；
                              其余归 AR900xx（范围）。本 AR 范围内不再切分」。
                              范围来源要写出来：从标题读到的、从预填读到的，还是没有依据
                              而取了部件全量——后者是待确认的范围，评审者有权推翻。
                            ③ **已切分**：一句「本需求切分为 N 份，本 AR 承载第 k 份」+ 拆分表
                              （逐份：序 | 承载 | 范围 | 依赖），内容照抄流程契约 split.parts；
                              表后写本 AR 范围，范围外的去向指向表。
                              兄弟 AR 写单号，尚未立项的写「待立项」——评审者要能看出
                              哪部分有人接、哪部分还悬着
### 1.3 相关文档链接      ← 表：SR/AR 单号 | **同 SR 其它 AR** | PRD | SE 设计 | UX 设计
                            （系统内链接）——必填，归档件 story.md 的上游引用唯一来源。
                            「同 SR 其它 AR」逐个写单号 + 范围，没有就写「无」：
                            下游 spec 要靠它把范围外内容的 out_of_scope 理由写成
                            「归属 AR900xx」而不是笼统的「本需求不做」。
                            **无系统单据时**（问题单/人工提供的原始文档）填来源载体与
                            「无系统链接」，不留空、也不编造链接

## 2 需求分析
### 2.1 场景与功能点      ← 按 RR 逐场景列功能点（本部件视角），每项标注命中的交互方（画像 §2 六类之一）
### 2.2 验收意图          ← 取自 RR 验收要求

## 3 SE 方案摘要（本部件相关）
### 3.1 全局方案与部件分工  ← 整体怎么做（一段）+ 三方各承担什么（本部件/云侧/其他部件，逐条一句）
                            + 依赖与上线顺序约束（谁先谁后、是否互相阻塞）。
                            这是**评审全局视角的唯一承载点**：评审者据此判断本部件承担的部分是否正确
### 3.2 本部件方案要点与流程骨架
                          ← 每项一句话 + SR 章节指针，不复述细节；
                            上游含流程图/时序图时给**一句话骨架**
                            （入口 → 关键节点 → 终态 → 主要分支去向），不转载不重绘

## 4 上游索引              ← 表前**必须**先写一行「原文位置」说明（见下方「上游原文位置」），
                            再列表：| 信息类别 | SR 章节 | 本流程消费步骤 |
                            信息类别逐类扫描见下方「上游信息类别清单」；
                            均不命中边界的上游章节登记「不消费」

## 5 上游已声明线索        ← 对外依赖/配置项/打点的名称清单，线索级：只列名称+指针（细节看 SR）
```

**上游信息类别清单（写 design.md §4 时逐类扫描 RR/SR，登记命中项）**：

| 信息类别 | 下游消费方 |
|---|---|
| 整体方案与三方分工 | **AR §3.1**（评审全局视角的唯一承载点——评审叙事件的「需求范围与部件分工」全靠它，AR 没写清楚下游补不出来） |
| 业务流程 / 交互时序 | AR §3.2 一句话骨架 + spec 业务流程图（该章节是 spec 强制项，须按 SR 原文建模；AR 只索引不转载） |
| 端云接口（含入参出参字段） | spec §9.1 端云接口 |
| 异常与错误码 | spec 异常处理 + spec §9.1 端云接口 |
| 跨部件交互与**调用方声明** | spec §9 技术契约（对外面）+ §7.3 安全性要求 / 《决策与评审记录》的跨团队协同 |
| 系统级存储 | spec §9.2 数据存储 |
| 配置管控（开关 / 默认值） | spec §9.3 配置项 |
| 打点 | spec §9.4 埋点 |
| 非功能约束（时效 / 频次 / 重试 / 缓存策略） | spec 非功能（§7.1 触发频次行）+ acceptance NFR + story 应用域约束回显（DFX、环境异常） |
| 安全与合规要求（加密 / 敏感数据 / 登录态 / 权限） | spec §7.3 安全性要求 + story 应用域约束回显·安全隐私 |
| 版本与配套约束（历史版本兼容 / 端云上线顺序） | spec §9.3 配置项 + story 兼容性自检 + 《决策与评审记录》的上线时序 B4 |
| 依赖的 SDK / 组件 / TA | spec §9.5 依赖变更 |
| 术语与命名（业务术语 / 字段名 / 事件名） | spec 术语消歧（该步骤是 spec 的强制入口，术语缺失会导致映射错位） |
| 上游已定的方案边界（被否方案 / 明确不做的） | spec（防止下游重新提出已被否决的方案） |

**登记与否的判定（元规则）**：该内容会不会成为下游某产物的**必填输入或硬约束**？会 → 必须登记（正文可只写一句话，细节留在 SR）；纯对方内部实现（云侧微服务拆分、其他部件独立排期）→ 登记「不消费」。本清单是**参考不是穷举**——SR 中清单外的硬约束同样登记。

**上游原文位置（design.md §4 表前必写，一行）**：

```markdown
> 本索引的 SR 章节号指向 `SR/design.md`（与本文件同在 `doc/features/<AR>/` 工作区，PRD 为 `RR/prd.md`）；
> 下游步骤（/spec 及其技术契约与合规判定取证）须按索引直读该文件原文，不得仅凭本文摘要推断。
```

## 4. 不做的事

1. 不生成开发侧章节——实现方案→plan、页面/异常→spec、安全/配置→spec §7/§9、合规与兼容判定→story 影响面、测试→acceptance.yaml；
2. 不复述 SR 细节——引用替代转载：design.md §3.2/§4/§5 是「一句话 + 指针」粒度（§3.1 全局分工按其自身要求成段）；
3. 不复制或重绘上游的流程图/时序图——图以 SR 为准、以 spec 业务流程图为建模载体；
4. 不为「要不要覆盖 `AR/design.md`」停下问人——S4 生成提取件本来就是覆盖上游预填版，
   旧版进 `.backup/`。需求系统拉下来的预填版每次都非空，为它设一道确认等于每轮都停，
   而本扩展的停等点只有材料与范围两处（见 SKILL「停等点」）。
