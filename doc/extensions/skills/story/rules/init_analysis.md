# S2 规则：材料盘点、需求分析与流程契约

> 读者：S2 做材料盘点与需求分析的主 agent。时机：S2 开始前完整读一遍。
> 在哪停以 [SKILL.md](../SKILL.md)「停等真值表」为准；关卡怎么摆见 [scope_gate.md](scope_gate.md)。

## 0. 分两段做，中间隔着材料确认关卡

```
S2a 材料盘点   → 清单 + 一句缺口判断（**不做需求分析**）
S3a 第一级关卡 → 材料已放进 inbox，请导入 / 现有材料就是全部，开始需求分析
S2b 需求分析   → ①需求概览 ②本部件视角 ③本 AR 定位 ④待实现功能清单 ⑤范围定法选项 ⑥来源初筛
```

**为什么不能一口气写完**：材料不全时范围判断本身就不可靠——在一个还会变的范围上
做的分析注定作废，材料一变就要重做一遍。先花几分钟盘点材料、问一句还缺什么，
比先写两千字分析再发现缺料便宜得多。

**轮次 = 一次材料状态**：料导入 → 材料变 → 新一轮；材料没变，重跑 `round` 幂等。
新一轮照样**重新盘点**，问的是「还缺什么」——够不够由你盘点、由人定，
文件到了不等于内容够了。不缺了就直接进 S2b（`status` 会这么给）；
还缺才把**剩下的**缺口写进侧车再停一次，每项写清还缺什么、为什么现有材料不够。
「材料变没变」由材料清单 `AR/story-src/materials.json` 的 `digest` 说了算——四份正文、
界面参考图、文档内嵌图都在里面，只补图片也换版本。分析件在同一轮内从盘点版演进到
完整版，不算新轮次。

## 1. AR/story-src/init-analysis.md — 决策支撑件

给 S3 关卡上做决策的人看的分析。它**不是交付件**：归档不含它，生成 design.md 也
**不以它为源**（四源不变）——它与 design.md 大面积重叠，不划死边界就是同一事实两个落点。
第 ⑥ 节的来源初筛留给后面用：Spec 从它起步，成文与审查回来对照它和原文。

**S2a 只写第 ⑤ 节的 1、2 两段**（材料清单 + 缺口判断）；材料确认后再补齐 ①–④、⑤3、⑤4 与 ⑥。
六节最终形态，缺一节不成立：

### ① 需求概览

这个需求是什么、解决什么问题。

### ② 本部件视角理解 —— 本需求落在本部件的哪一块

本部件的申明（名称与别称、职责范围、运行形态）与六类交互方清单，在**项目事实**里——
本次任务包第 2 节逐份列出了它们的路径与各自讲什么，找「部件申明」「交互方清单」那一份。
对照它核对两项，结论即本节正文：

1. **落在职责范围的哪一块**——按画像 §1 逐条对需求：哪些在职责内、具体是哪一块；
   落在职责外的写明是哪部分、归谁；
2. **涉及哪几类交互方**——按画像 §2 的六类逐类给结论（命中 / 不命中 + 一句依据）；
   六类全不命中即本需求与本部件无关，当场提出。

第 ③ 节的「部件在本 SR 下的全量」以本节核对出的职责范围为准。

### ③ 本 AR 定位 —— 本 AR 当前范围是什么

**整条范围链的起点。**三源逐条给结论，再收敛成一句。**按强度排序，先判强的**：

| 源 | 怎么判 |
|---|---|
| **AR 标题**（`title`） | 是否给出特性范围：落到具体特性上就是给了，只有单号加「开发需求」这类通用词就是没给 |
| **`AR/design.md` 预填**（`design_prefill`） | 已有范围/说明时按它理解，没有就写「无预填说明」 |
| **`SR/design.md` 关联 AR 清单**（`sr_related`） | 同一 SR 下还有哪些 AR。清单写明各 AR 分工时，**本 AR 那一条就是范围**（上游已经切好了）；只列单号没写分工时它至少是旁证——有兄弟 AR 就说明全量不可能都归本 AR |

→ **收敛一句：「本 AR 当前范围 = ______（来源：标题 / design.md 预填 /
SR 关联清单 / 三源都没给 → 取部件全量）」**

这一节做的是**材料判读**：范围由上游材料给到哪一步。人对本次做多少有自己的打算是另一回事
——那是决定，在关卡上跟他谈（见 [scope_gate.md](scope_gate.md)「人提出自己的拆分诉求时」），
不在这里替他推断。

三源都没给出范围时取部件在本 SR 下的全量，**同样要把全量是什么写出来**，
并且知道这是**待确认的范围**——评审者有权在关卡上推翻它。

**不先定下这一句，第 5 节的信号核对就没有施加对象**，只能默默按上游全量判——
那正是「本 AR 承载全部需求」被无声写下的地方：没人决定过它，它只是没有被质疑过。

写完落一份机器面副本到 `AR/story-src/.positioning.json`（格式见下）。

### ④ 待实现功能清单

本 AR 视角下要做的功能点，逐条可数。

### ⑤ 材料现状与范围定法

四段，缺一段就不成立：

1. **材料清单**——人要先知道手上有什么，才谈得上要不要补。三列：**源 / 来源 / 是什么**，
   外加状态：

   | 源 | 来源 | 是什么 | 状态 |
   |---|---|---|---|
   | `RR/prd.md`（RR90xxx） | 需求系统拉取 | 产品需求（业务背景与验收意图） | 已归档正文 |
   | `SR/design.md`（SR90xxx） | 需求系统拉取 | 系统级设计（分工、接口、时序） | 已归档正文 |
   | `AR/design.md` | 需求系统拉取 | 本 AR 提取件现状（可能已预填） | 空模板（无预填） |
   | `inbox/xxx.docx` | 人工提供 | 待导入材料 | 待导入 |
   | `inbox/澄清会.docx` | 人工提供 | 需求澄清会议记录 | 已读会、结论 N 条 / 待导入 |
   | `inbox/RR-prd.md` | 需求系统取回 | 产品需求新版 | 待导入，取代 `inbox/产品原稿.docx` |

   - **只列实际存在的输入源**。`AR/story-src/upstream.md` 这类**导入落点产物**不是材料，
     没有就别列——列一行「不存在」只会让人问「这是什么？该有吗？」；
     导入落点产物的有无收进下面那句缺口判断，一句话说清缺的是哪一类；
   - **单份写文件名**；**多份写文件夹名 + 件数**（`ux-reference/`（12 项）），
     **不穷举文件**——十几个文件名铺开，人反而看不出缺的是哪一类；
   - **同一来源的新版本**（update 取回的上游正文、人补的改版稿）在状态里写「取代 `inbox/<旧名>`」。
     导入前把 **`inbox/` 里那份旧原件本身**移到需求目录的 `.backups/local/<旧原件名>-<时刻>`（不删）：
     同一类的原件导入时按文件名拼接，旧的留在 inbox，目标正文就是两版拼在一起。
     导入前的目标文件（如 `RR/prd.md`）由导入链自己备份，不用你管；
   - **逐项标状态**，光有文件名不算数：`已归档正文` / `占位件（未归档）` /
     `空模板（无预填）` / `空` / `无法解读` / `待导入`。**文件存在 ≠ 有内容**——
     PRD 是占位件时，只看「文件在」会让整个缺料判断失真；
2. **一句缺口判断**（如「PRD 未归档，正文来自人工补录」；只列文件名等于没说）+ 本轮导入结果。
   这一句直接决定 S3 第一级推荐哪一项：还缺料就推荐请人放料，不缺就推荐开始分析；
   **需求方提到但还没进来的材料**另起一小节逐份列：名称、在哪句话里提到、取还是不取、理由。
   取的写进 `.gate-options.json` 的 `missing`，停等消息的缺口那一句引用它；不取的说清这一轮为什么用不上它
   ——据上游自判「那份不在本稿」而不向人要，就是没核材料先定了范围。
   **不取的理由只能是「本轮范围不依赖它」，而范围依据来自 AR 或需求方的话**；
   上游材料自己说「另行提供」只说明它现在不在手上，**不构成不取的理由**——范围由谁定，是这两者的分界。
   没有就写「无」；
3. **三类信号逐条核对**（一行一条，写命中与否 + 一句依据），**施加对象是第 ③ 节收敛出的
   那个范围**：本部件内跨多个业务模块 / 超长业务流程 / 大颗粒特性需分层构建
   ——逐条写，不要笼统给一段散文说「不用拆」。
   **信号定的是推荐哪一项，不是要不要给选项**：拆不拆是人的决定，你的活是把选择摆全。
   **信号只在用户没表态时定推荐**——他已经说了要拆或指了切法，就不必再推荐，
   照他说的定（见下条「用户已指明方向时」）；
4. **范围定法选项**——**恒定生成，任何时候都要有**：
   - **首项固定是「按当前范围整体承载」**，并**列出该范围含哪些功能点**
     ——「全部」有多大，人要能看见才谈得上认可；
   - 其余各项是**具名维度**的切法，各附**份表**：序号（建议执行顺序）、
     范围一句话（写到能对照 SR 章节定位）、依赖哪几份（须先交付的）。
     **份表此处不预设承载者**——哪份归本 AR 是人在第三级选的；
   - **维度从哪找**（按序试，找到几个摆几个；本清单是入口不是穷举）：
     ① **用户说过的切法**——他在任务描述里或先前对话里提过怎么切，就把它做成一项；
     不要求他的话已经长成一个「维度」，按 [scope_gate.md](scope_gate.md)
     「人提出自己的拆分诉求时」的五步落成条目与份表；
     ② 端侧业务链路（一条用户旅程一份）；③ 生命周期阶段（建立 / 使用 / 变更注销）；
     ④ 页面组（每份含整页面，不切半页）；⑤ 交付先后（可先行独立上线的最小集 + 增强集）；
   - **切法成立的四条判据**：
     ① 每份**可独立交付、可独立验收**——有自己的完成定义，不是「做一半」；
     ② 份间依赖**单向**——后份依赖前份，互相依赖说明切口选错了；
     ③ 切口沿**稳定边界**（接口、页面、数据主权），不切在一段逻辑中间；
     ④ 同一上游事实**只落一份**——两份都要改同一个接口，那是同一件事被劈开了；
   - **判据怎么用，取决于这个维度是谁提的**：

     | 维度来源 | 判据不满足时 |
     |---|---|
     | 你自己试出来的 | **不摆**，并写明卡在哪条——凑出来的切法比不摆更糟 |
     | **用户指明的** | **照摆**，份表照给，标签后标注「⚠ 卡在判据 X：<一句话>」 |

     用户指的方向即便不完美**也必须出现在选项集里**：判据是给他的参考，不是替他下的否决。
     **人无从推翻一个从未被摆出来的选项**——把它判掉不摆，等于替他做了决定。
     用户已指明时该项排第一且不另设推荐（他已经选过了）；
     整体承载作为固定首项照常并列，让他随时可以改主意。
   - **每一项的标签要让人看得懂选完是什么范围**：切法写清按什么切、切成几份、每份是什么。
     只给一个维度名（「按业务链路切」）而没有内容，人无法评估，等于没摆；
   - **推荐项排第一**，推导写在选项前的正文里，**不写进选项标签**
     （标签只说「选了会得到什么范围」，态度归推导）；默认推荐依赖最少、可先行交付的一份；
   - 举不出任何具名维度时**只有首项一项**，写明「未找到可切维度」及依据
     ——「判过了不用切」与「压根没想这件事」，差别就在这句话在不在。
     **不要为了凑数造切法**：凑出来的切法比不摆更糟——那是把现编的说明书递给做决定的人，
     他看不懂也无从评估，选中之后份表还得接着现编。

   写完把**整个选项集**落 `AR/story-src/.scope-options.json`（格式见下）。
   **关卡只能摆这里定下的选项**——脚本从契约取，不从对话里现编。

### ⑥ 来源初筛 —— 材料里每一块内容对本需求有什么用

把你读材料时已经形成的判断留下来：Spec 从这里起步，成文与审查回来对照它和原文，
不必把同一份材料再从头分类一遍。按**能独立判断的主题**逐块写——通常是最小一级标题下的正文；
父级标题自己有正文也算一块，用途相同的相邻几块可以合写一行：

| 来源位置 | 对本需求的作用 | 还要核实的矛盾或缺口 | 不适用的依据 |
|---|---|---|---|

- **来源位置**写文件路径加标题，原文留在原件里，这里不摘抄；
- 第 ④ 节功能清单、`AR/design.md` 上游索引已经表达清楚的，直接引用，不另写一张同义表；
- **不适用**要写出来源或范围上的理由；说不出理由的，登记到「还要核实」；
- 矛盾已经登记进 `decisions.json` 的，引用那一条；初筛不替未决的事定结论；
- **会议按话题登记**：来源位置写 `AR/story-src/meeting-notes.json` 的 `<主名>@<版本>/T<n>`，
  要指原话就写 `AR/story-src/meetings/<主名>/<版本>/raw.md:L<起>-L<止>`；作用写当前会议结果里
  这个话题的去向（`AR/story-src/doc-refresh.md`），「还要核实」写它仍未决的部分——
  十章齐后的回看清单从这一列取；
- 这不是逐格填满的配额：没有疑点的那一格空着。

**每轮重生成整个文件**（材料变了回到 S2 即 round+1），旧版进 `.backups/local/`。
重生成时，材料没变的那几块初筛判断原样沿用，只重判变了的与新增的。
现行版永远只有这一份，轮次历史查契约——编号累积（init-1、init-2…）会说不清哪份是现行版。

## 2. AR/story-src/story-flow.json — 流程契约

记录每一步的输入、输出与交互：**摆出了哪些选项**、谁在什么依据下选了哪一项，
事后可查、可推翻。

**它同时是这条流程的状态机**：`status` 读它就回答「现在走到哪、下一步干什么」。
中断后恢复、或不确定该干什么时，**先跑 `status` 看 `next`**，不要靠回忆重建位置。

**你不写这个文件**——[scripts/core/story_flow.py](../scripts/core/story_flow.py) 是它的唯一写入者。
时间戳、轮次边界、收件箱里还有没有没导过的料、本轮并入了哪些文件，都由脚本自己取
（`round` 每次调用都按磁盘现状重算材料清单，答案从清单里读）；
**你只传它无从得知的那部分：本 AR 定位、摆了哪些选项、人选了哪一项、依据是什么。**

| 时机 | 命令 |
|---|---|
| 材料盘点后 / 需求分析后 | `python …/story_flow.py round --feature <AR>`（登记轮次并消费当时已有的侧车；两个时点各跑一次） |
| **任何时候拿不准走到哪** | `python …/story_flow.py status --feature <AR>` → 看 `next` 与 `action` |
| S3 每次关卡交互后 | `python …/story_flow.py decide --feature <AR> [--gate material_scope\|scope_decision\|split_carrier] --chosen <选项 key> --basis "<用户原话>"` |
| 会议话题的人裁决（材料确认之后，有要问人的话题时停一次） | `python …/story_flow.py decide --feature <AR> --gate meeting --meeting <主名>@<版本> --item <话题 id> --chosen <选项 key> --basis "<用户原话>"`（选项取自会议判断，不写侧车；读会见 [phases/meeting-read.md](../phases/meeting-read.md)） |
| S4 提取稿写好后 | `python …/story_flow.py complete --feature <AR> --from AR/story-src/design-draft.md`（提交为 AR/design.md 并收口） |
| **收口之后材料又变** | 照常跑 `round`——它不会开新轮，只更新材料指纹并记一笔。补个说明文件、改个错字都属这一类，流程仍是收口的，照常进 spec |
| **收口之后要重新拍板范围** | `python …/story_flow.py reopen --feature <AR>`，然后照常 `round` → `decide` → `complete`。它是唯一的回退出口，会留痕 |

### 侧车文件

结构化数据一律走文件——对话里的东西会话一断就丢，脚本也读不到：

| 侧车 | 谁写 | 何时被消费 |
|---|---|---|
| `AR/story-src/.positioning.json` | 你（第 ③ 节的机器面副本） | `round` |
| `AR/story-src/.scope-options.json` | 你（第 ⑤ 节 4 的**整个**选项集） | `round` |
| `AR/story-src/.gate-options.json` | 你（本次关卡摆出的选项，**文件里写明是哪一级**） | `decide --gate <该级>` |
| `AR/story-src/.split-parts.json` | 你（第三级定案后的份表） | `decide --gate split_carrier` |

```json
// .positioning.json
{"scope_text": "本 AR 当前范围一句话",
 "sr_related_ars": [{"ar": "AR900xx", "scope": "该 AR 承载什么"}]}

// .scope-options.json —— 首项必须是 carry_all；切法必须带 parts（≥2 份）
[{"key": "carry_all",
  "label": "按当前范围整体承载：<列出功能点>"},
 {"key": "<维度名>",
  "label": "按<维度>切：<切成几份、每份是什么>",
  "parts": [{"seq": 1, "scope": "…", "depends_on": []},
            {"seq": 2, "scope": "…", "depends_on": [1]}]}]
```

`sr_related_ars` 只列**同一 SR 下的其它 AR**，没有就给空数组——**不含本 AR 自己**
（本 AR 的范围写在 `scope_text`；把自己列进去会让下游「有兄弟 AR 就不可能承载全部」
这条判断被自己触发）。
```json
// .gate-options.json —— 形如 {"gate": 哪一级, "options": 摆给人的全部选项}
// 第一级只写 key：那两句标签固定，脚本按 key 填；第 2 轮起「我还要料」那一项写 missing / why
{"gate": "material_scope",
 "options": [{"key": "supplied", "missing": "…", "why": "…"}, {"key": "confirm_scope"}]}
```

`gate` 必须写明是给哪一级摆的。三级共用这一个文件名，不写明的话，
你为第二级摆的选项会被第一级读成「材料上又出了新缺口」，把流程拨回上一级。

**选项内容只有第一级由你写**：第二级的选项来自契约里的 `scope_options`，
第三级由脚本从选定维度的 `parts` 生成——分析定几项，关卡就只能摆几项。

### 记录纪律

- **`--basis` 写人的原话**，不写你的转述——它是契约的审计价值所在；
- **选项集必填，且 `--chosen` 必须是其中一项**：选的只能是摆出来的。只记选中项的话，
  「看过选项后选了不拆」与「压根没生成拆分选项」事后完全同形；
- **关卡只认人签**（见 SKILL「停等真值表」）；
- **`decide` 的退出码回答「能不能按这个选择往下走」**：`0` 能；`2` 不能——选择已记录，
  但校验没过（如说了料已放进 inbox，收件箱里却没有新文件），按 stderr 提示重新与用户确认；`1` 是参数/前置错误。

拆分定案的范围文字由份表中本 AR 那一份的 `scope` 推导进契约，S4 从那里逐字抄进
`AR/design.md` 的「本 AR 范围与拆分说明」——写进 §1.2 之后那里是权威，
契约转为历史记录，不构成双落点。

即「诊断出缺料却径直进 /spec」这种跳步走不通。没走 /story 的 feature 没有本文件，不适用。
