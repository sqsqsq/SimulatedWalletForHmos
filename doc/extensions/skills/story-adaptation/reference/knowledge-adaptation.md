# 知识适配方法

> 读者：执行 `/story adapt` 的维护模型。时机：首次安装、升级或单独适配知识时，在跑安装脚本之前读一遍；安装完成后按这里做知识部分。

## 目标

让目标仓的知识回答本版机制需要的问题：看清本仓知识的实际状况，说清与当前要求差在哪，人定范围后依据目标仓的真实代码与业务依据补齐，并如实交回。安装脚本只写机制，知识由你改。

## 输入

| 读什么 | 拿什么 |
|---|---|
| 包的 `skills/story/reference/knowledge/protocol.md` | 三类知识的写法、能力登记与不适用登记的格式 |
| 包的 `skills/story/reference/knowledge/capabilities.md` | 每项能力要回答的面、取证位置、走查条件、修订与迁移依据 |
| 目标的 `manifest.yaml > provides.knowledge` 与其中每个文件 | 现有内容与登记；部件画像里的 `capability_decisions` |
| 目标的代码、架构配置、模块画像与业务说明 | 取证来源 |
| 安装脚本的输出 | 机制装没装成 |

## 步骤

1. **先装机制**：跑 `adapt-scan --apply`，失败按它点名的原因处理，知识编辑尚未开始。版本相同、没有机制要写时脚本退出 0，知识仍按下面继续核，不以此结束任务。
2. **识别现状**：逐项对照台账与目标知识。
   - 新仓：部件画像必做，其余能力全部进差异。
   - 已有登记：先看登记的修订与台账是否一致，再读内容确认实际状况。
   - 有内容无登记：按内容识别它覆盖了哪些能力与面，不凭文件名推定；只补登记与真实缺口，保留原文与目标扩展。
   - 旧版索引件（`kind: index` 的 README）仍在激活清单里：加载会报错，这是必要的协议迁移，见第 5 步。
   - 同一内容出现在多个文件时先定权威来源，不合并成新副本。
3. **形成差异，交人决定**：一项一行——能力或受影响的面、当前证据、要补什么、对当前任务的影响、建议（本次适配 / 不适用 / 留待以后）。没有差异的说明依据。已有有效决定沿用，不全量重问；只把真正要选的一次摆给人。加载器报出的格式错误要修，不能当作不适用；人可以暂缓必要的协议迁移，此时依赖这些知识的阶段不能加载，交回写明这条边界（见第 5 步）。
4. **按人定的范围改写**：读定义也读实际调用，结合业务协议写。
   - 当前实现由代码证明；业务语义由协议、需求或负责人证明；已定而未实现的写「已定规范」；查不到的标「未确认」，不编。
   - 相同编程语言或类名不是照搬 Demo 的理由，Demo 只参考信息组织。
   - 写完在 frontmatter 登记 `capabilities`，新文件先写成完整可读再加进激活清单。
   - 人判的不适用与留待以后，登记在部件画像的 `capability_decisions`；接入后删除已失效的 `deferred` 或缩小其范围。
   - 能力拆分、合并、更名时按台账的变化说明搬内容，保持一处来源，同步激活清单、登记与引用，旧入口退出。
   - 遇到新的业务决定、事实冲突或超出已选范围，停下问具体问题；已选范围内的成品不逐项再确认。
5. **协议迁移（旧 README 退出）**：读旧 README 与实际内容 → 通用规则已由 `protocol.md` 接替，目标自己加的项目说明迁进相应知识文件 → 把格式改到当前可解析形态 → 从激活清单删去 README，修引用 → 删除 README → 重新加载核可读。人暂缓这一步时，交回写明「机制已安装，知识格式迁移待办，依赖知识的阶段当前加载失败」，保留原文件。
6. **走查**：每项已适配能力拿一个正常业务走一遍——阶段能不能取得所需定义、哪些设计现在写得出、哪些仍待核。
7. **确认与交回**：跑 `adapt-scan --check`；再在目标工程根执行下面这段只读检查（交给 `node --input-type=module`），它按目标的 `paths.extension_dir` 加载激活知识并做结构自检，不需要需求编号、不写任何文件。两者分开报告；PASS 只证明能加载、结构成立，不证明内容正确。

   ```js
   import fs from 'node:fs';
   import path from 'node:path';
   import { pathToFileURL } from 'node:url';
   const root = process.cwd();
   const config = JSON.parse(fs.readFileSync(path.join(root, 'framework.config.json'), 'utf8'));
   const ext = path.resolve(root, config.paths?.extension_dir ?? 'doc/extensions');
   const api = await import(pathToFileURL(path.join(ext, 'hooks/shared/knowledge.mjs')).href);
   const knowledge = api.activeKnowledge(root);
   const problems = api.selfCheck(root, knowledge);
   if (problems.length) throw new Error(problems.join('\n'));
   console.log(JSON.stringify({ status: 'PASS', files: knowledge.declarations.length }));
   ```

   出错时非零退出并带文件与原因；缺运行依赖按依赖提示处理，不算知识缺失。

## 完成条件

- 机制 `--check` 通过；激活清单里的知识全部能加载，没有 `kind: index`。
- 人选定的每项能力：内容按台账的面写齐或标明未确认，登记与实际内容一致，走查结论写明。
- 不适用与留待以后都在部件画像登记，理由与依据可回查。

## 失败与中断

- 机制没装成：按脚本报错修机制，不动知识。
- 机制成功、知识部分完成：分开交回，不回滚机制，不笼统称升级完成。
- 中断后再做：从当前文件重新识别，已完成的保留，未完成的不登记；优先恢复激活清单的可读性。
- 你的编辑与目标在途修改冲突：给出具体差异让人定，不自动覆盖或暂存。

## 交回

分别写：机制安装结果；每项已适配能力写了什么、证据位置、走查结论、未确认项；判不适用的依据；留待以后的及其影响到哪些阶段；剩余动作。

## 示例：后台任务通知（中性题材，路径与值均为示意）

目标是一个非钱包的后台服务仓，已装旧版扩展。它有一份项目事实 `knowledge/facts/services.md`，写着通知发送封装 `Notifier.send` 与重试策略，但没有能力登记；台账里对应的能力要求回答「发送入口、返回语义、失败与重试、取消」四面。

- **识别**：读 `services.md` 与两处真实调用。发送入口与重试已写且与代码一致；返回语义没写，代码里 `send` 返回投递回执；取消时是否还发通知，代码和需求都没有依据。
- **差异交人**：一行写「发送入口、重试已覆盖（证据：定义与两处调用）；返回语义缺，可从代码补；取消策略无依据，建议留待以后，影响涉及取消的需求设计」。人选：补返回语义，取消留待以后。
- **改写**：在原文件补「返回语义」一面并带定义位置；frontmatter 登记该能力，`covers` 写三面；在部件画像的 `capability_decisions` 记取消一面 `deferred`，写明理由、依据与影响。
- **走查**：拿「注册成功发通知」这条业务走一遍，Plan 能写出调用入口、成功与失败的判断和重试边界；涉及取消的设计仍待决。
- **交回**：机制 `--check` 通过；本项已适配三面，证据位置；取消一面留待以后及其影响。
