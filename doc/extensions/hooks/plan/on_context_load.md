## 实例扩展：plan 阶段的知识冻结

本阶段是三类知识里**设计模式唯一的选型点**，也是全链唯一的**冻结点**：
coding / code-review / ut / testing 读的不是知识目录，而是你在这里冻结的结果。
冻结缺失或读不出来，下游就零注入——不是「回退到全量」，是**什么都收不到**。

### 一、知识决策是设计的输入，不是设计的总结（BLOCKER）

`plan.md` 里**必须**有一章「知识决策（设计输入）」，且它**必须排在第一个设计章之前**：

```
## 知识决策（设计输入）
### 设计模式选型     —— 逐个候选单元：选或不选 + 理由；选了给唯一实例名
### 规约义务         —— 逐条命中条目：本次要落实成什么 + 落在哪个契约实体 + 哪个业务步骤
### 项目事实影响     —— 复用了什么、缺什么、与已登记事实有无矛盾
## 1. 模块架构图 …（其后是设计各章）
```

位置就是语义。排在设计之后，它只能是「我做完了，顺便声明一下用过哪些知识」；
排在设计之前，后面每一章才有可能按它展开——数据模型里因此多出一个字段，
接口里因此多出一个方法，状态管理里因此多出一个标识。**这正是「应用」与「声明」的差别。**

### 二、冻结写在哪、写成什么（`plan/contracts.yaml`，BLOCKER）

```yaml
knowledge_freeze:
  obligations:
    - rule: <规约条目编号>              # 一条目一行，不要一行塞多条
      criterion: <对应的验收条目编号>    # 见下方「四阶段的验证要求」
      obligation: <本次要落实成什么——可实施的设计结论，不是复述规约原文>
      step: <哪个业务步骤：验收条目的 prd_function，或 use-cases 的 branch>
      anchor: <plan.md 里承载该设计的**设计章**标题>
      review_focus: <review 阶段该核什么>
      landing:
        - <实体引用>                    # 见下方语法，可多条
  patterns:
    - pattern_id: <在册的设计模式标识>   # 见本阶段注入的知识清单
      selected: true                    # 不选时写 false，只需 rationale
      instance: <本方案里的唯一实例名>
      unit: <应用到哪个适用单元>
      rationale: <为什么是它 / 为什么不用它>
      anchor: <设计章标题>
      roles:                            # 键 = 该模式声明的角色，不多不少
        <角色名>: <承载它的类名 / 模型名 / 文件路径>
```

**实体引用语法**：`data_models.<模型>[.<字段>]` / `interfaces.<类>[.<方法>]` /
`components.<组件>[.<状态或属性>]` / `state_management.<环境>.<键>` /
`resource_keys.<键>` / `files.<路径>` / `navigation.<目标页>`。
引用的东西必须在**同一份 contracts.yaml 里真实存在**——门禁按结构解析，不是按文本包含。
集合名对齐 contracts 既有章节，**不自造平行命名空间**。

### 三、四阶段的验证要求写在哪（BLOCKER）

每条义务的 `criterion` 指向 `acceptance.yaml` 里的一条验收条目，那条目**就是**这条义务
在四个阶段的验证要求，不另建第二份分派表：

| 阶段 | 靠什么验 |
|---|---|
| coding | 义务的 `landing` —— 落点实体在代码里必须存在 |
| review | 义务的 `review_focus` —— 复核时核什么 |
| ut / testing | 验收条目的 `ut_layer` —— `unit` 只由 UT 验，`device` 只由实机验，`both` 两边都要 |

所以 spec 阶段提取 `acceptance.yaml` 时，每条约束要求都要有一条对应的 `criteria`：

```yaml
- id: AC-<N>                  # 框架原生形态，下游 ut/testing 认它
  knowledge_rule: <规约条目编号>   # 桥接键：把验收条目认回某条规约
  category: <security|privacy|performance|dfx|compatibility|nfr>
  prd_function: <业务步骤>
  ut_layer: <unit|device|both>     # 谁来验，单源在此
  ut_focus / device_focus: …       # 按框架规则必填
  description / verification_steps / expected_result: …
```

`ut_layer` 同时也是**「显式不适用」的载体**：标 `device` 就等于说「UT 不适用于这一条」，
下游据此报 SKIP 并计数，不必另写一份豁免清单。

### 四、什么叫「真的应用了」（BLOCKER）

三类知识的消费语义不同，冻结时不要混用同一套词：

| 类别 | 本阶段该做的 | 不算数的写法 |
|---|---|---|
| 项目事实 | 用它判断方案可行性与复用（这个工程今天有什么、长什么样） | 罗列事实名称；它**没有**「选用/不选用」这一说 |
| 规约 | 判适用 → 适用的逐条给出**落实设计 + 落点实体** | 只写「已命中 <编号>」；写了义务却给不出承载它的字段/方法 |
| 设计模式 | 选或不选都给结论：选了写实例名与**每个角色的承载实体**，不选写为什么不适用 | 只写模式名；**不选不是缺陷**，不写理由才是 |

**判据一句话：冻结结果必须能指回方案里的实际落点，而那个落点是契约里的一个实体。**

举例说明「有落点」与「没落点」的差别（题材中性，只看形态）：

- ❌ `rule: <某编号>` / `obligation: 流程要带流程标识与步骤标识` / `landing:` 空
  ——读完不知道哪个字段装流程标识；到编码那里，这条义务等于不存在。
- ✅ `obligation: 流程标识在业务入口生成一次并随上下文透传；步骤标识用固定枚举` /
  `landing: [data_models.<上下文模型>.flowId, data_models.<步骤枚举>]`
  ——契约里因此真的多了一个字段和一个枚举，coding 有东西可写，review 有东西可查。

### 五、写每条义务前的三个自问

`obligation` 是你自己写的句子，机械门禁只拦得住「原文照抄」，拦不住「换个说法」：

1. **这句话里有没有本需求自己的名字**（契约实体、业务步骤）？
2. **把编号遮住，这句话还能指导编码吗**？
3. **它是不是把规约的「约束」或「处置」列换了个说法**？

三问任一答错就重写。原文的复制或子串会被门禁拦下；同义改写会进评审的必答清单。

### 六、门禁会拦你的地方（FAIL 判据，逐条对照自查）

1. 缺「知识决策（设计输入）」章，或它排在第一个设计章之后；
2. `contracts.yaml` 缺 `knowledge_freeze`；
3. spec 约束要求章的编号集与 `obligations[].rule` 集对不上（少一条 = 知识在设计阶段丢了）；
4. `criterion` 在 `acceptance.yaml` 里不存在，或那条的 `knowledge_rule` 与本条 `rule` 不一致；
5. 缺 `obligation`，或缺 `landing`（处置标「（评审动作）」的条目除外）；
6. `landing` 的实体引用解析不到契约实体（模型不存在、字段不存在、类里没有那个方法）；
7. `anchor` 在 plan.md 里找不到，或**指回了「知识决策」章自己**——那是声明，不是落点；
8. `step` 在验收条目或 use-cases 里定位不到；
9. 模式不在册；`selected: true` 却缺 `instance`；`roles` 键集与该模式声明的角色集不一致；
   某个角色的值在契约里找不到对应实体；
10. `use-cases.yaml` 存在时 `coordinator` 与模式声明的编排入口角色对不上；
11. `obligation` 是规约原文的复制或子串。

### 七、与 spec 的衔接

spec 的「设计模式候选登记」只登记候选、不做选型（那一步缺少方案上下文）。
本阶段从候选出发：候选里选一个、选多个、或一个都不选，都合法；
**但 spec 全部单元都写「无候选」时，本阶段不应凭空冻结出一个模式**——
那说明选型依据不是从需求来的。真需要时回 spec 补候选登记。

规约方向相反：spec 判命中并把命中结论回显在归档件附录、把产生的代码要求写进 spec；
本阶段把**每一条命中的条目**变成有落点的义务。spec 判了命中而这里没有对应义务，
就是知识在设计阶段丢失——后面编码不可能补回来。
