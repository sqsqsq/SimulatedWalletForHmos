# coding 阶段 · 扩展要求（写之前读这一页）

**冻结结果是本阶段唯一的知识来源**：plan 已经把用到的规约义务与设计模式冻结在
`plan/contracts.yaml` 的 `knowledge_freeze` 里。不回去重读规约、不重新判断该不该适用、
不自行改结论——那些判断在 plan 做过一次了，每阶段各判一次就没人说得清以哪个为准。
冻结与实际对不上时**回 plan 更新冻结**（改了要重跑 plan），不在本阶段绕过。

## 一、读哪几个文件

| 文件 | 拿什么 |
|---|---|
| `plan/contracts.yaml` 的 `knowledge_freeze` | 每条义务的 `landing`（承载实体）与每个模式的 `roles`（角色 → 实体） |
| 被选中的那个设计模式文档（在 `manifest.yaml` 的 `provides.knowledge` 里） | 它的**实现篇**：结构、落点与命名、骨架、约定、反模式 |

规约文件本身不必读——`obligation` 已经带着本需求的专名了。

## 二、产出形态

产出就是代码本身。任务是**让冻结点名的实体在代码里真实存在并承担该义务**：
`landing` 指到模型的字段就真的有那个字段，指到类的方法就真的有那个方法，
指到组件的状态就真的有那个状态。采用的模式同理——`roles` 里每个角色都要有承载它的结构。

每条义务在本阶段都要有个说法，二选一：**真实证据**（它落在哪）或
**显式不适用 + 理由**（为什么本阶段碰不到它）。不能什么都不写——缺席与「做过但没写」
在产物上事后完全同形，而只有前者是缺陷。

## 三、跑哪条命令

```
cd framework/harness && npx ts-node harness-runner.ts --phase coding --feature <需求名>
```

## 四、门禁会拦什么

- 冻结点名的落点实体在代码里找不到（文件建了，但里面没有那个类 / 字段 / 枚举）。
- 采用的模式缺少承载某个角色的结构。

**只在文档里写「已考虑」而代码里没有对应落点的，等于没做**——本阶段的证据是代码本身。

报错会一次列全，每条都写「缺什么 / 写到哪 / 怎么写」。不需要读 `post_check.mjs` 反推判据。
