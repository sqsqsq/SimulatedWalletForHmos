## 实例扩展：coding 阶段的知识账本

## 你读到的是**冻结结果**，不是知识目录

plan 已经把本需求用到的规约义务与设计模式冻结在 `plan/contracts.yaml` 的 `knowledge_freeze` 里。
本阶段**只消费它**：不回去重读规约、不重新判断该不该适用、不自行改动结论。

理由很直接：那些判断在 plan 阶段做过一次了，重新打开它就等于允许每个阶段各判一次——
四个阶段四种理解，最后没人说得清到底以哪个为准。

冻结结果与实际情况对不上（事实变了、义务落不了地）时，**回 plan 更新冻结**，
不在本阶段自行解释。

## 显式不适用优于静默跳过

每条义务在本阶段都要有个说法，二选一：

- **真实证据**——它在本阶段的产物里落在哪；
- **显式不适用 + 理由**——为什么本阶段碰不到它。

不能什么都不写。缺席与「做过但没写」在产物上事后完全同形，而只有前者是缺陷；
静默跳过让两者无法区分，于是所有人都只能假设它做过了。

## 本阶段要落实什么

冻结里的每条义务都带 `landing`——那是它在契约里的承载实体（模型的字段、类的方法、
组件的状态、资源键、文件）。本阶段的任务是**让这些实体在代码里真实存在并承担该义务**。

采用的设计模式同理：`roles` 里每个角色都指向一个实体，实现时该有承载它的结构。

## 门禁会拦你的地方

- 冻结点名的落点实体在代码里找不到（文件建了，但里面没有那个类/字段/枚举）；
- 采用的模式缺少承载某个角色的结构。

**只在文档里写「已考虑」而代码里没有对应落点的，等于没做**——本阶段的证据是代码本身。

义务落不了地时回 plan 修正冻结（改了冻结要重跑 plan 阶段），不要在这里绕过它。
