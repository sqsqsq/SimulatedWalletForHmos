> 读者：spec 阶段的作者。时机：动笔前读一遍。这一页写原则与写法；这一次的数据（你在哪、本轮激活几条、材料里有哪几张图、十章各答什么）看同一钩子生成的**任务包**。

## 先分清你在哪一组

| | 走 `/story` | 直接跑 spec |

**spec 只写与最终代码有关的要求**：规约判定结论进叙事件附录，决策论证进决策件，推演过程与生成流程的说明都不进可见正文。扩展章模板见 [`spec-sections.md`](../../skills/story/templates/spec-sections.md)。

## 本阶段的主任务：从业务关系到完整设计

1. **取输入**：原材料与当前决定（走 `/story` 链时还有 `AR/story-src/doc-refresh.md` 的采纳变化与仍未决），以及命中域规约的整份原文与项目事实（任务包第 2 节列了文件；主表是索引，落法附注同样有效）。各知识先读开头的用途与适用条件，再按本需求读要用的正文，项目方法与参考帮你形成设计，结论写进 spec，不回显知识原文。
2. **沿业务流程走一遍**：谁在什么条件下、用什么输入做什么，结果由谁消费，哪些异常、例外或未执行的步骤改变去向，哪些还没定。这是方法，不是必填表，也不另写推演日志。
3. **判断适用**：哪条规约命中哪个实际行为、项目已有什么能力、还有什么未决。这些判断决定下一步怎么设计；项目事实说「仓里没有现成实现」说的是复用结果，不证明这件事不必做。
4. **在承载章写完整设计**：规约原文要求讲清的专项写在承载它的那一章，同一方案只写一处。某条规约的要求落在某个统计点上时，§10 的落点写那个统计点名。埋点在 §9.4，任务包第 5 节写了这次要交什么、动笔前读哪一份、写完按什么自查；一个指标一个 H4，结果写业务结果，实现层的取值留给 plan；指标口径没定的写需要什么数据，不替人定口径。写完沿正常、失败、主动终止、未执行与结果在远端产生的路径各走一遍：每个结果由谁产生、本端何时可知都说得清，要人定的回到已有决策项；走查直接改设计，不另写推演。
5. **未决的保持未决**：任务包第 3 节照列了当前的决策登记。仍 open 的选择，正文只写确定的共同要求，依赖它的行为与验收写成条件并标出议题编号，不替人选一边；settled 的按它写。
6. **同步登记**：把已作的决定与实际落点写进 `spec/knowledge-use.yaml`。设计中发现新事实，回头改那条判断，不另起一套。冲突回知识或需求的责任方，不擅自豁免红线、删功能，也不用模拟顶替真实承诺。

## 知识判断怎么填

**§10 与 §11 不手写**：它们由 `render` 从 `spec/knowledge-use.yaml` 投影进 spec.md，判断只做一次。

- **命中**：`requirement` 写成**列表，一条要求一句**——把编号遮住还能指导编码吗？换个需求照样成立
  那是复述。**落点二选一**：`contract` 引 §9 登记过的名字（脚本验真），或 `impact` 点名实际影响对象
  （「页面」「资源」这种泛称会被退回）。两个都空或都填，都拦。
- **知识判断只记本需求怎么适用它**：不是这条规约要求的普通业务规则，写在它所属的行为与验收处，
  不挂到编号上。
- **不命中**：写 `reason`——命中条件里哪个事实在本需求不成立，要能回查；「界面沿用现有样式，不新增控件类型」是依据，
  「不涉及」不是，拿处置结果（「调用频次低」）否定命中也不是。值里有英文冒号加空格（`条件: 结果`）时整句加引号。
- **处置是评审动作的条目命中了**：不写要求与契约；走 `/story` 的，先在 `AR/story-src/decisions.json` 登记这件事的议题，
  再把议题 id 写进 `decision`（成文登记之后才判到，先 `reopen`；不为凑 id 提前造空议题）；不走的写 `impact`：谁、在哪份产物里表态。
- **整域都不命中**：登记到 `constraint_domains`；域里只要有一条命中，就改逐条登记。
- **命中但本轮不做**：`applicable: true` 加 `waived` 块（`reason` / `compensation`）。红线不能豁免，基线要写补偿；豁免登记进《决策与评审记录》由评审人表态。
- **项目事实按面记**：`facts[].used` 逐面一项，`facet` 取骨架注释列出的面名、`used_for` 写拿它做什么。
- **模式候选只登记不选型**（选型归 plan）：信号与反证指向真实存在的分支、步骤或交互；允许零命中，没有合适候选写「无候选」加理由。

**知识只读激活清单里的那些**：`manifest.yaml` 的 `provides.knowledge` 是本阶段生效的全部，不扫 `knowledge/` 目录。

## 写字的三条

**数值要标来源与测量对象**。阈值、时长、次数三选一标明 `（上游约束：<文档名>）` / `（本工程设定，无上游依据）` / `（平台基线）`，条件与量的是什么一并写清；标「上游约束」门禁会回 SR/RR 原文核，材料没给的数值不能冠以平台或项目基线，拿不到依据写待补。

**验收要接回规约**。`acceptance.yaml` 里每条命中的规约要有一条带 `knowledge_rule: <编号>` 的条目——编码与真机测试认回规约的唯一桥，命中集与桥接集不一致就是断链；同一验收编号在两处指的功能必须一致。判定推演与规约原文回显不进 spec，它们在归档件附录里。

**上游画过的图搬进 story**，围栏第一行写来源标记，只搬图不搬文字；哪几张以 `story-build skeleton` 的当前输入为准。

**章号照模板**：主章的号以 spec 模板为准，模板里不编号的章（如「Scope 声明」）不计入序号，子节号以父章号开头；扩展追加的几章，号照 `skills/story/templates/spec-sections.md`。

`cd framework/harness && npx ts-node harness-runner.ts --phase spec --feature <需求名>`。走 `/story` 链时，这一段的顺序由 `story_flow.py status` 逐步打印（它也给出这一步要写的文件长什么样）。**harness 放在三份产物齐备之后**——之前跑它一定红。verifier 报告写好后读 summary，当前报告还没被采纳时再完整跑一次这条命令采纳它（采纳的判据见 [update.md](../../skills/story/phases/update.md)「与闭环、修正入口的关系」第 4 步）。取证与结论写法见 [`evidence-rules.md`](../../skills/story/reference/evidence-rules.md)。
