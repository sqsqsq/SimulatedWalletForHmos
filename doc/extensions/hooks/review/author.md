那个实体上。不回去重读规约、不重新判断该不该适用、不自行改结论。与实际对不上时
**回 plan 改 `must`**，不在本阶段自行解释。

## 一、读哪几个文件

| 文件 | 拿什么 |
|---|---|
| `contracts.yaml` | 各实体上的 `must`（`text` 是这条义务在这个实体上要做什么）；标了 `pattern` 的文件 |
| 本轮 diff | 结论要指向 diff 里的**具体位置**，不是指向规约原文 |

## 二、产出形态

审查报告里须有一节 **`## 知识义务复核`**，契约里的每条 `must` 一行：

```
| rule | 落实位置（文件:符号） | 结论 | 依据 |
|---|---|---|---|
| <条目编号> | <文件:类或方法> | 落实 / 未落实 / 不适用 | <据什么这么判> |
```

契约里标了 `pattern` 的模式也要有行：核实现是否按该模式的结构落——角色是否各就各位、
上下文所有者是否唯一、失败是否有单一收敛者。

每条义务二选一：**真实证据**（落在哪）或**显式不适用 + 理由**。不能什么都不写——
缺席与「做过但没写」在产物上事后完全同形，而只有前者是缺陷。

## 三、跑哪条命令

```
cd framework/harness && npx ts-node harness-runner.ts --phase review --feature <需求名>
```

## 四、门禁会拦什么

- 缺 `## 知识义务复核` 节，或表的行集与契约里的 `must` 集对不上。
- 结论指不出 diff 里的位置——写「已按要求处理」而给不出文件与符号的，等于没核。
- 标「不适用」但依据不具体——「不适用」三个字不构成依据，要写清本次变更为什么碰不到它。

**上游阶段声明过、本次变更里却找不到落点的，正是本阶段该抓的。**
照 `must.text` 说的那件事核，不要退回去复述规约原文。
