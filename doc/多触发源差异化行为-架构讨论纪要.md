# 「多触发源 × 差异化行为」架构讨论纪要

> 日期:2026-07-21 · 版本 v3
> 定位:**思路文档**。以「开卡」为贯穿示例说明做法,示例与代码片段均为示意,不绑定任何具体工程的现有实现;落到真实工程时,以当时的 spec/plan 产物为准。

---

## 0. 问题定义

同一个核心业务流程(如开卡),存在 N 个触发源:钱包内入口、三方应用 A 的 deeplink、三方应用 B 的 deeplink……产品要求**按来源在流程的若干位置表现出不同行为**(过程中展示轮播 A/B、结果页是否引导、完成后去向不同等)。

朴素实现是入口传 `source`,过程代码中 `if (source === xxx)` 分支。两个病灶:

1. **知识散落**:「哪个来源对应哪些特殊处理」以控制流形态散落各处,变成需要记忆的部落知识;
2. **改动面扩散**:每新增一个来源,所有分支点都要改一遍;每新增一个差异点,所有来源都要过一遍。

该问题可归入**变体管理(Variability Management)**范畴,软件产品线(SPL)理论与各大厂中台化实践解的都是这类问题。

---

## 1. 核心思想(四条决策原则)

### 1.1 身份与行为分离 ⭐ 红线

> **来源(身份)只允许在系统边界被解释一次,解释产物是一组行为语义;边界之后的所有代码只消费语义,不认识来源。**

病根不是 `if` 本身,而是下游代码认识了上游的**身份**,使每个新身份都成为全链路改动面。正确形态:入口处解析一次 → 得到场景快照 → 下游只问「要不要引导」,不问「你是谁」。快照中保留的场景标识**仅供埋点/日志**,一旦被用于业务分支,等同 `if (source)` 复辟。

### 1.2 变化点显式化(扩展点即契约)

> **哪些位置允许变化,由内核显式声明为扩展点清单,而不是哪里需要就在哪里长 if。**

内核声明「我在这几个点开放定制(过程展示、结果引导、完成去向……),其余不可变」。收益:「哪里可能不同」从隐性知识变成可读契约;对**复用既有能力的**新场景,内核零修改。

### 1.3 维度正交化(场景 = 一行规则)

> **把场景差异分解为相互独立的行为维度,每个场景是一个维度取值向量,即规则表的一行;维度取值的实现可复用、可组合。**

- 防止 N 场景 × M 差异点的实现爆炸:**不为每个来源写一个完整策略类**——`PartnerAScene`、`PartnerBScene` 只是把来源分支换成类爆炸。
- 「记不住哪个场景做什么」的解药:映射关系收敛为**一张有唯一真源的表**,可审计、可 diff、可表驱动测试,不再依赖记忆。
- 维度间存在**合法业务不变量**是正常的(如「回跳调用方」必须同时具备已验证身份与回跳信息),这类约束在解析层校验即可;需要警惕并重切维度的,是说不出业务理由的隐式耦合(「A 开了 B 就必须关」)。

### 1.4 绑定时机与变更主体决定机制层级

> **同一个变体,由谁改、多久改一次,决定它活在哪一层。**

| 变更主体 / 频率 | 承载形态 |
|---|---|
| 开发改,随版本发布 | 类型化规则表 + 策略实现(代码) |
| 产品运营改,不发版生效 | 配置 schema / 规则 / 远端下发 |

演化路径通常是:代码内规则表 → 数据型维度下沉为配置 → 高频部分远端化。不要一步到位,但要知道自己在这条轴的哪个位置。

## 2. 信任边界:先把「参数」验成「事实」 ⭐ 安全红线

**deeplink 携带的任何参数都是外部调用方可控的,一个 `source` 字符串不能证明调用方身份。** 场景解析的输入必须是**宿主校验之后的结构化事实**,而非裸参数:

```
Raw Want / 内部入口事件
      ▼
宿主层:解析、验签、识别可信调用方、协议版本检查
      ▼
LaunchContext(结构化事实)
  ├─ entryType: WALLET_INTERNAL | VERIFIED_PARTNER | UNTRUSTED_EXTERNAL | UNKNOWN
  ├─ verifiedPartnerId?   // 仅在校验通过时由校验过程产生,绝非透传
  ├─ campaignId? / protocolVersion? ...
```

兜底方向必须**保守**:未知或校验失败的外部来源,只能落到能力最少、无内部引导的 `EXTERNAL_DEFAULT` 场景,或直接拒绝;**严禁**兜底为钱包内部场景——那等于向任意伪造方开放内部体验与流程能力。`WALLET_INTERNAL` 只能由内部入口代码构造,不可由外部参数表达。

## 3. 机制选型光谱

按「流程拓扑变不变」选择,从轻到重,**够用即停**:

| 场景特征 | 机制 | 复杂度 |
|---|---|---|
| 差异是纯数据(文案、开关、素材) | 参数化 Profile(声明式) | ★ |
| 差异是行为逻辑,发生在固定点 | 按维度的策略对象 / 钩子 | ★★ |
| 多个行为需按顺序组合、可插拔叠加或短路 | 拦截器 / 中间件管道 | ★★★ |
| 流程结构本身随场景变(多/少步骤) | 状态机 / 流程编排(流程定义即数据) | ★★★★ |
| 变体需独立交付与隔离 | 插件化 / 微内核 | ★★★★★ |

开卡这类「固定流程 + 固定变化点」的问题,取 **Profile(数据)+ 少量维度策略(行为)** 两层即够。多数业务问题停在前两档。

## 4. 参考形态(以开卡为例,示意)

### 4.1 总体链路

```
Want / 内部入口
      ▼
宿主:解析、验签、识别可信调用方        ←—— 信任边界(§2)
      ▼
LaunchContext(结构化事实)
      ▼
ScenarioResolver(唯一的「事实 → 场景」映射点)
      ▼
ScenarioSnapshot(不可变快照)
  ├─ sceneId / matchedRuleId / policyVersion   // 仅埋点、日志、排障
  ├─ profile(数据型维度取值)
  └─ 行为维度取值(如 completionKind,由内核映射到共享策略实现)
      ▼
开卡流程内核(只消费行为语义,不认识来源)
      ▼
CompletionIntent(语义结果:「去哪里」)
      ▼
表现层 / 宿主协调器(「怎么去」:导航、回跳三方)
```

### 4.2 规则表是唯一真源(SSOT)

场景映射以**一份类型化规则表**为唯一真源,文档与测试从它派生,**不维护第二份手工同步的表**:

```typescript
// 示意
interface ScenarioRule {
  ruleId: string;
  match: LaunchContextMatcher;   // 基于结构化事实匹配
  priority: number;              // 多维匹配(partner+campaign+experiment)冲突时按此裁决
  profile: SceneProfile;
}

const RULES: ScenarioRule[] = [
  { ruleId: 'wallet_home',      match: internal(),              priority: 100, profile: {...} },
  { ruleId: 'partner_a',        match: verifiedPartner('appA'), priority: 50,  profile: {...} },
  { ruleId: 'external_default', match: anyExternal(),           priority: 0,   profile: SAFE_MINIMAL },
];
```

配套自动化测试:ruleId 唯一;保守兜底规则存在;**任意合法上下文均有规则覆盖,优先级裁决结果唯一,同优先级的重叠规则视为冲突**(允许多条规则命中,但最终裁决必须确定);维度间业务不变量校验通过。规模化/运营化后,SSOT 迁移为带 schema 校验的配置文件,原则不变。

由规则表**派生**的阅读视图(示意)——它最直接地回应了「记不住哪个来源对应什么处理」的原始痛点:

| 场景事实 | 轮播 | 结果引导 | 完成去向 |
|---|---|---|---|
| 钱包内部入口 | A | 钱包权益 | 卡详情 |
| 已验证三方 A | B | 无 | 返回调用方 |
| 已验证三方 B | B | 活动奖励 | 返回调用方 |
| 未知外部来源 | 无 | 无 | 拒绝或安全退出 |

> 本表仅为阅读而展示的派生视图(可由规则表自动生成),规则表仍是唯一真源。

### 4.3 Profile:按维度组合,而非按来源建类

```typescript
// 示意
interface SceneProfile {
  carouselKind: CarouselKind;         // 数据型维度:过程中展示什么
  resultGuideKind: ResultGuideKind;   // 数据型维度:结果页引导形态
  completionKind: CompletionKind;     // 行为型维度:完成后去向
}
```

数据型差异一律进 Profile,一个场景一行规则;只有确实无法数据化的行为维度才引入策略对象,且**策略实例按维度取值共享**——所有「回跳调用方」的场景共用同一个实现,而不是每个来源一个类。

### 4.4 领域决定「去哪里」,宿主决定「怎么去」

行为策略属于领域层,**不应接触**导航栈、页面栈操作、Ability/进程生命周期(如回跳三方时的 terminateSelf)——那些是表现层与宿主的能力。领域策略只返回语义意图:

```typescript
// 示意
type CompletionIntent = 'CARD_DETAIL' | 'WALLET_HOME' | 'RETURN_VERIFIED_CALLER' | ...;

interface CompletionStrategy {
  decideCompletion(session: Session): CompletionIntent;
}
// 表现层/宿主协调器负责 executeCompletion(intent):栈操作、回跳、关闭页面
```

这样领域逻辑可脱离 UI 单测,宿主行为(各平台导航细节)的变化也不会波及场景规则。

### 4.5 场景快照的生命周期

场景快照一经解析即**不可变**,并与一次业务会话绑定。要点:

- 区分三个操作:**开启会话**(清旧会话 → 写入新快照)、**重置业务进度**(只清用户中途输入,不动快照)、**清理会话**(整体清空)。页面重入(如返回上一步再进来)**不得重新解释来源或改变场景快照**;业务进度保留还是重置,由具体产品流程决定。
- 热启动收到新 deeplink → 视为新会话,完整走一遍「开启会话」;
- 流程进行中收到重复 deeplink → 明确定义为「作废旧会话开新会话」或「忽略」,不得静默混合;
- 冷启动/进程恢复 → 快照随会话状态一起恢复,或整体作废重来,不允许出现「半个会话 + 空场景」的中间态。

## 5. 开发行为守则(Checklist)

**新增一个触发源时:**
- [ ] 只是复用既有行为能力 → 规则表加一行,下游零修改;
- [ ] 引入了新的业务语义 → 允许扩展语义契约(新维度/新意图)及对应实现,但来源身份仍不得泄漏到下游;
- [ ] 外部来源必须先过宿主信任校验;禁止新增「外部来源 → 内部场景」的映射。

**新增一个差异点时:**
- [ ] 先判定:数据型 → Profile 加维度;行为型 → 新维度 + 共享策略实现;
- [ ] 在规则表与维度定义处登记语义;
- [ ] 与既有维度的约束:合法业务不变量 → 解析层加校验;无业务含义的隐式耦合 → 重切维度。

**Code Review 必查项:**
- [ ] 边界之后是否出现来源/场景标识用于业务分支;
- [ ] Resolver 是否仍是唯一映射点;规则表是否仍是唯一真源;
- [ ] 兜底是否落在最保守的外部默认场景,而非任何内部场景;
- [ ] 领域层是否混入导航/生命周期等宿主能力;
- [ ] 场景快照是否不可变、重入是否未重新解释来源或改变快照。

**测试策略:**
- [ ] 规则表:规则覆盖完整 / 裁决结果唯一 / 同优先级无歧义 / 不变量校验,全部自动化;
- [ ] Profile 表驱动测试逐场景断言;策略实现独立单测,不依赖 UI;
- [ ] 生命周期用例:重入、新 deeplink、重复 deeplink、进程恢复。

## 6. 反模式警示

1. **过早搭框架**:两三个场景时,规则表 + 少量策略就是最优解;扩展点框架是几十个场景逼出来的,不是设计出来的。
2. **每来源一个策略类**:只是把来源分支换成类爆炸,违反 §1.3。
3. **双重真源**:文档表与代码表手工同步,会复活「记忆负担」;文档从规则表生成。
4. **信任降级兜底**:未知来源兜底成内部场景,等于向伪造方开放内部能力。
5. **身份泄漏**:场景标识仅供埋点排障,进业务分支即违规。
6. **配置爆炸**:无业务含义的配置耦合出现时重切维度;但不要把合法业务不变量误判为切分错误。
7. **过度抽象一次性差异**:某场景真正一次性的特殊逻辑,以该维度下的一个策略实现承载即可,不为其抽象通用机制。

## 7. 业界参照系

| 实践 | 对应思想 |
|---|---|
| 阿里交易平台 TMF(业务身份 + 扩展点) | §1.1 + §1.2 的工业级形态:请求先识别业务身份,扩展点按身份路由,内核不认识具体业务 |
| COLA 框架 Extension 机制(BizScenario 路由) | 思想相近的公开参考实现,推荐阅读 |
| Linux `file_operations` | 身份在 open 时解析成函数表,之后只调表不问身份 |
| Express / OkHttp 中间件管道 | 多个行为按顺序叠加、短路或包裹执行时的组合形态 |
| 支付宝/微信支付收银台 | 订单由服务端生成并参数签名,客户端行为由验证后的上下文驱动而非透传裸参数——与 §2 信任边界同构 |
| BPMN / Temporal 流程编排 | 流程拓扑本身随场景变时的升级方向 |

## 8. 一句话总结

> **先在信任边界把「参数」验成「事实」;再把「事实」翻译成「语义」且只翻译一次;把「哪里可变」声明成契约;把「谁在哪个点做什么」压成一张有唯一真源的正交规则表;领域决定「去哪里」,宿主决定「怎么去」。**
> 此后,场景的增长是规则表加一行;能力的增长是维度加一列;信任边界保证这一切不被伪造方搭便车。
