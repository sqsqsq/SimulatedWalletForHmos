# 离线测试性能根因：Framework机制与我们的选择

2026-11-04，本会话（维护设计者兼执行者，Claude Opus）。

缘由：用户在2.1.1 E批交回后问：“从1.x到2.x这种性能劣化，究竟是framework机制变化的必然，还是我们选择了看似最简单，但是时间代价很大的方案”。

本报告只给诊断与可行性实验结果，不是施工许可。没有改产品，也没有改仓库测试；实验件全部在`output/`下。

## 1. 结论

两者都有，但把劣化放大的是我们的选择：“一个操作一个进程”。

- **机制的部分（躲不开）**：Framework只发TS源码，靠ts-node现场执行，不出编译产物。任何要用原生语义的进程，都要现场加载几百个TS模块；它真正的计算只有毫秒级。
- **选择的部分（放大成本）**：测试几乎每个断言都起一次产品CLI；产品命令内部又在Python与node之间互相起进程。1.x里进程便宜，这种结构不显眼；2.x把单进程成本抬高5–30倍之后，结构没有跟着改。
- **证据**：三轮提速（10-27、10-28四层改造、11-04 E批）都只减“重复准备”，都停在400–800 s。
- **实验**：让测试在一个常驻进程里调产品命令，同样的断言全部通过，输出逐字节等价，热点类快了约2.1倍（§4）。

## 2. 机制的部分：单进程固定成本

本机空载，在装好Framework与开发版扩展的临时工程（`output/scratch/2.1.1-C02/ws`）里实测：

| 一个node进程里 | 无转译缓存（真实使用） | 有测试转译缓存 |
|---|---|---|
| 空进程 | 70 ms | — |
| 注册ts-node＋`framework-access.mjs` | 170–270 ms | — |
| 加载阶段解析模块（`feature-track.ts` / `capability-resolution.ts`，169个TS模块） | 约2000 ms | 约460 ms |
| 加载之后的实际计算（`loadFrameworkConfig`） | 首次4 ms，之后不到0.1 ms | 同 |

- Framework的`harness/package.json`没有build产物（`dist`不存在），依赖里也没有swc、esbuild；它自己的harness也是每次用ts-node跑。
- 原生重操作（经`goal-mode-entry`准备并冻结范围）一次7–10 s。
- 1.x扩展从不加载Framework的TS，只借`framework/harness`里的`yaml`包（`story-1.0`分支`hooks/shared/yaml.mjs`）。2.x自`43035b62`（2026-09-29，2.0.0步骤1A）起经`framework-access.mjs::loadNative`读原生。

## 3. 选择的部分：一个操作一个进程

E06探针（`output/evidence/2.1.1-impl/E06/process-tree.txt`）记录的一轮全量：

| 项 | 数 |
|---|---|
| 被测侧进程 | 8722（测试直接起4253，产品命令内部嵌套4469） |
| 各自加载一遍Framework的node | 2108 |
| 测试直接起 | `story-build.mjs` 1155次（811次加载Framework）、`node -e`内联探针720次（350次加载）、`story_flow.py` 998次 |
| 产品内部往返 | `story_flow.py → node framework-access --action feature-identity` 2228次，`story-build.mjs → story_flow.py status` 1454次 |

- 4 worker下各类用时合计约2900 worker秒，其中进程启动与Framework加载占七成以上。
- 时间线（全量单跑）：
  - 1.0：1512条，93 s；
  - 2.0初（已读轻量原生）：146–187 s；
  - 反合1.9.9并接入蓝图/CU原生语义之后：505–581 s；
  - 11-04：2030条，600 s（32 worker），E批后434 s。
  
  阶段解析等重模块进入命令、测试逐例经原生入口造冻结态的时候，成本出现跳变。
- **真实使用里这笔账很小**：D04自动充值实跑702分钟，约190次产品命令，额外成本约占全程2%。所以这本质是测试架构的问题；为测试改产品不合算，用户11-04也已经排除。

## 4. 可行性实验：常驻宿主在进程内跑产品命令

做法（`output/evidence/2.1.1-impl/perf-host-probe/`，不改仓库）：
- `host.mjs`：每个pytest进程起一个常驻node。按请求设`argv`、`cwd`、`env`，以不同查询串重新import `story-build.mjs`，让它的入口守卫触发`main()`；拦`process.exit`；收集输出。
- `perf_host_plugin.py`：pytest插件，把测试里的`subprocess.run(["node", ".../story-build.mjs", …])`转给宿主。测试文件一行不改。
- 同一组用例分CLI、宿主两轮跑，每次调用都记下归一化后的输出（工程根换成占位符），然后逐条比对（`compare.py`）。

对象：`test_story_build.py::TheMachineZoneIsCheckedAgainstItsSource`（逐例整篇check）与`test_verifier_report_protocol.py::TheWholeSourceSetIsReviewed`（prepare/check链），共20条用例、60次story-build调用，串行。

| 项 | CLI | 宿主 |
|---|---|---|
| 用例结果 | 20 passed、5 subtests | 20 passed、5 subtests |
| 两个类串行用时 | 70 s | 33 s（约2.1倍） |
| `review --action …` 单次 | 1205 ms | 586 ms |
| `check` 单次 | 953 ms | 360 ms |
| `project` 单次 | 780 ms | 234 ms |
| 输出等价 | — | 60次中59次退出码与stdout/stderr逐字节一致。剩下1次的差别是材料键，这条用例自己导入时会写时刻，CLI连跑两轮也不同（已复核），与宿主无关 |

**实验中发现并修正的保真问题**：第一版宿主拦`process.exit`时只记退出码、不中断执行，失败路径于是落到产品的“脚本自身异常”分支（15次不一致）。改为抛信号截断执行之后，全部等价。这说明这种宿主必须靠“CLI与宿主两轮逐条比对”来守保真，不能只看用例过没过：那15次不一致时，用例照样全过。

**剩余成本**：宿主里单条命令仍要250–600 ms，主要是产品命令内部还会起`story_flow.py`，它又起node算`feature-identity`。按本批约束，产品不改，这部分留着。

## 5. 外推与达标判断（估算，未实测）

- 测试直接起、会加载Framework的进程约1640个（story-build 811、内联探针350、entries 137、framework-access 146、adapt-scan 110、knowledge-task 88）。都改走宿主，空载下每个约省0.4–0.9 s；满负载下争用也会下降。粗估full从745 s（4 worker）降到250–400 s。
- 产品内部的嵌套进程仍在：`feature-identity`约2228次，每次约0.25 s，约560 worker秒，4 worker下约140 s；Python流程脚本的启动也还在。
- 所以只做宿主，120—180 s大概率仍到不了。要达标，还得动产品内部的跨语言往返，这一条用户已排除。

## 6. 需要用户决定

1. **是否放宽Spec R9的“本版不新增runner”**：允许测试侧引入常驻宿主与转发插件（产品不改）。若放宽，由设计者另立批次：
   - 扩到`framework-access`、`knowledge-task`、`entries`、`adapt-scan`与内联探针；
   - 全量做一轮CLI对宿主的逐条比对，作为保真门；
   - 精选一组仍走真实CLI的入口见证；
   - 量化实际用时。
2. **能否接受“产品不改时的下限”**：大约250–400 s，而不是120—180 s。或者把“产品内部跨语言往返”作为产品自身的工程问题另行评估：它在真实使用里只占约2%，单为测试改不合算。
