# maintain Skill 优化方案

2026-11-08，Claude Opus。依据 [maintain 技能反思](2026-11-08-094426-maintain技能反思.md)（下称“反思报告”）、Skill 正文全文、公共 Skill 正文，以及 writing-for-agents 的写作方法。本文是设计方案，不是施工许可：用户选定后，按以往做法在 `doc/project/` 立需求与方案，再修改 `~/.agents/skills/maintain/`。

## 1. 目标与判断标准

**目标**：维护任务第一次就接近人的期望。人工纠正和返修轮次下降；同类问题第二次出现之前能被 Skill 自己发现。

**怎样算改好了**：

| 指标 | 现状（反思报告） | 目标 |
|---|---|---|
| 同一形态的人工纠正复发 | 停等 2 次、投入失衡 2 次、没追到最终消费者 3 次以上 | 第二次出现前由 doctor 或评审报出 |
| 设计错误的发现阶段 | 多数在实施后或用户指出 | 多数在方案评审时 |
| 每个子命令开工前的必读量 | 1.05–2.2 万字 | 约 6 千字以内，参考页按分支读 |
| doctor 主动发现的过程问题 | 0 | 每次报告都有缺陷逃逸表与规则对照 |

## 2. 子命令：问题、原因、解决方案

### help

- **问题**：没有观察到问题。
- **原因**：—
- **方案**：保持现状。命令表改了，help 输出随之改变，无需另维护。

### clarify

- **问题**：
  - 没查清现有设计为什么存在，就下整体结论（“机制过重”）；
  - 用户原意被扩大或缩小。
- **原因**：
  - “查项目现状”只回答“是什么”，不回答“为什么这样”；
  - 澄清结束时没有一个可检查的结果，模型自己判断“已经懂了”就结束了。
- **方案**：clarify 改为 grilling 的轮次（见 §4），maintain 在其上加两项产出：
  1. **现状成因**：每个要改动或批评的现有设计，写出它来自哪次踩坑、评审或 EVOLUTION 条目，以及改掉它会失去什么。查不到就写“未找到成因”，并按未知处理。
  2. **期望锚点**：用户原话、具体样本（好的、坏的、金样）、以及“看到什么人会认为对了”。

  完成判据：grilling 的决定树前沿为空；每条锚点都有原话或样本来源。

### spec

- **问题**：
  - 需求没有具体对象（“像许愿”）；
  - 旧实现被当成必须保留的需求；
  - 保护项与用户原意对不上。
- **原因**：spec.md 要求写“应得到的结果”，但不要求用真实样本说明问题，也不要求逐条对照原话。
- **方案**：以 to-spec 的模板为骨架，maintain 增加三项：
  1. **问题样本**：问题陈述必须指向真实产物的位置，写清人期望看到什么。
  2. **期望锚点**：从 clarify 原样带入。
  3. **保护项对照**：每条保护项对应一条原话或已定约束；“已有实现”不能单独作为保护理由。

  完成判据：每条验收都写了触发、结果、证据类别，并能追溯到一条锚点。

### plan

- **问题**（返修最多的地方）：
  - 方案没追到最终消费者（B01-R02、2.0.2 起草漏判）；
  - 在原生能力旁边另起机制（A03 资格链）；
  - 投入在过重与过简之间摆动；
  - 无必要的前置与停等。
- **原因**：
  - 走查只是一句“要做”，不要求留下结果；
  - 没有“先核原生”这一步；
  - 风险投入表逐项判断，没有用户场景作锚点；
  - 停等判据模糊。
- **方案**：Plan 增加四张必填短表，表本身就是走查的产物：

| 表 | 每行内容 | 评审怎样核 |
|---|---|---|
| 原生能力核对 | 要承担的职责 → 平台或原生是否已有（引用位置）→ 用 / 本层补 / 向上游反馈 | 打开引用位置核实 |
| 消费者追踪 | 变化 → 最终消费者（文件:行或接口名）→ 它实际收到的输入 → 验证入口 | 抽查最终消费者是否真读这个输入 |
| 场景覆盖 | 用户必须覆盖的场景 → 由哪一步承担；删机制时注明场景仍由谁承担 | 场景不能消失 |
| 依赖与停等 | 步骤或问题 → 后续哪一步读取或依赖它 → 停 / 继续 | 只有存在依赖才停 |

  完成判据：四张表没有空行；评审能按表逐行核对。
- **配合**：切片按 to-tickets 的“垂直切片 + 阻塞边”；测试边界按 tdd 的 tests/mocking。阻塞边与「依赖与停等」表是同一份数据，不另写。

### exec

- **问题**：
  - 退场漏掉同一个入口（A04-R01-1）；
  - 方案已写明的项被当成待定（Q1 第 6 项）；
  - 批内选测漏掉全机制守卫。最后一项属于项目问题。
- **原因**：
  - 开工前的“审视方案”没有产出；
  - 方案里写到什么程度算“已写明”，没有判据。
- **方案**：exec 第一步产出**开工核对**：逐行核对 Plan 的「消费者追踪」与「原生能力核对」，标为已核或不成立；不成立的立刻交设计者，其余照做。判断“需要问吗”只看一点：方案是否给出了职责、接口和验证；给了就实现，局部写法自定。
- **保持**：受阻就停下交设计者、无关部分继续、如实交回，这些现在做得好的部分不动。

### handback

- **问题**：
  - 交回字段多、篇幅长；
  - 批末全量之后再修改，最终提交的对象没有一次完整全绿；
  - 约一半提交是文档提交。
- **原因**：handback.md 的八类内容都写成“要写”，没有固定的短格式；它也不区分“全量所测对象”和“最终提交对象”。
- **方案**：
  - 交回改为固定短格式：完成 / 受阻、方案外决定、验证（对象 SHA）、预算、逃逸标记、下一责任人。
  - 全量之后又有改动时，写明“全量对象 X，最终对象 Y，差异与补测”。
  - **逃逸标记**：每个被发现的问题写一行“引入阶段 / 本该在哪发现”。这是 doctor 的原料，见 §5。

### review

- **问题**：
  - 无必要的停等出现两次；
  - 成本问题（同一 Story 被审 8 次）靠用户发现；
  - 首次归因过宽；
  - 报告密度高，人难读。
- **原因**：
  - “验证可信度”的判据可宽可窄，评审默认保守；
  - “成本”只是一个列举词，没有对应动作；
  - 评审只核规则，不核期望锚点。
- **方案**：
  - 停等改用「依赖与停等」表判定；
  - 效果审查加一行**成本读数**：审查次数、返修轮次、耗时与预期对比；
  - 增加**锚点对照**：结果是否达到 spec 的期望锚点；
  - 每个发现带逃逸标记；
  - 评审结论先写给人看的三行：通过什么、阻断什么、下一步。
- **配合**：实现差异审查按 code-review 的 Standards 与 Spec 两轴进行；maintain 只加锚点对照、消费者核对、成本和逃逸标记。

### doctor

- **问题**：从未主动发现过程或方法问题；结论与评审重复；用读取回执代签 Skill 效果；候选不升级。
- **原因**：方法以当前产品状态为中心，没有“收集人工纠正”这一步，也不对照 Skill 正文。
- **方案**：默认 doctor 改为**过程诊断**，四步依次进行：
  1. **缺陷逃逸表**：汇总自上次诊断以来的逃逸标记、Plan/Spec 讨论段里的用户纠正、评审问题编号，每条一行，写明功能、引入阶段、发现者、轮次。
  2. **规则对照**：每类问题定位 Skill 正文中的对应规则，判为缺失、模糊、写了没起作用、或项目侧问题。
  3. **复发识别**：与前次逃逸表比对。复发的形态，或第二次未采纳的候选，列为首要候选。
  4. **Skill 变更候选**：写明改哪一页、改成什么、用哪条历史逃逸回放验证。

  产品与测试状态只记录对过程判断有影响的部分。读取回执保留，只作为“读过”的证据。doctor 的方法页本身也按这个结构重写。

### doctor env

- **问题**：只核链接是否存在；公共 Skill 上游变化了也发现不了；Claude 插件副本与本地副本并存。
- **原因**：没有公共方法的版本基线。
- **方案**：在 dependencies 里记录所采用公共页的 sha 基线；doctor env 比对，变了就提示重新核兼容。并列出各宿主实际可触发的同名副本（见 §4）。

## 3. 结构性优化

### 3.1 现在的结构与问题

```
SKILL.md（路由 + 角色 + 准备，4.4KB）
references/  12 页规则散文：documents（10.9KB，每次必读）、method-use、dependencies……
scripts/read_reference.py   tests/
```

| 结构问题 | 表现 |
|---|---|
| 规则散文代替步骤 | 每页是一串约束，几乎没有编号步骤和完成判据；writing-for-agents 把这叫 sprawl 加 premature completion |
| 共享页一律先读 | documents.md 每个子命令都要读，必读量 1–2 万字 |
| 与公共 Skill 双层重述 | maintain 用否定句改写公共方法（“不默认 TDD”“不发布 tracker”），自己又重写一遍怎么做 |
| 没有回路 | 纠正留在项目文档或 Claude 记忆里；doctor 不收集；Skill 改动没有回归验证 |
| 期望不落地 | 人的期望只在对话里，后续评审核的是规则，不是期望 |

### 3.2 目标结构

```
maintain/
├─ SKILL.md              路由：角色绑定；子命令 → 步骤卡；每个子命令四行（输入、所用公共 Skill、产出、完成判据）
├─ steps/                每个子命令一张步骤卡：编号步骤，每步写完成判据和产出（表或字段）；每张约 3 千字以内
│  clarify spec plan exec handback review doctor
├─ reference/            只在分支命中时读
│  layout.md        落盘结构（原 documents 职责与位置）
│  batches.md       批次、连续推进、依赖与停等判据
│  evidence.md      证据分层、讨论与纠正记录的短格式
│  rewrite.md       方案整体重写的确认规则
│  composition.md   公共 Skill 组合契约（替代 dependencies + method-use 的大部分）
│  tables.md        四张 Plan 表、逃逸标记、锚点的格式与中性例子
├─ lessons.md            经验条目：每条 = 场景、当时行为、期望行为、来源、已改的步骤卡位置；同时是回放集
├─ scripts/read_reference.py（保留）
└─ tests/
```

### 3.3 六项结构动作

| 编号 | 动作 | 替代了什么 | 必要性 / 成本 / 更简单的替代 |
|---|---|---|---|
| S1 | 步骤卡：每个子命令写成编号步骤，每步有完成判据和产出 | 现 12 页规则散文中的同义部分 | 必要：反思报告 G1。成本：重写全部方法页，需要用户确认整体重写。替代：只重写 plan、review、doctor 三页 |
| S2 | 产物驱动：四张 Plan 表、开工核对、锚点、逃逸标记 | “逐段走正常链”“实施者视角走查”等只要求“去做”的句子 | 必要：让做没做可以检查。成本：新增模板，用户规约要求确认；风险是模型机械填表，用“评审抽查引用位置”约束。替代：只加消费者追踪一张表 |
| S3 | 分层加载：SKILL 加一张步骤卡为必读，参考页按分支读 | documents.md 每次必读 | 必要：反思报告 G4。成本：拆页和改指针。替代：只缩减 documents.md |
| S4 | 公共 Skill 当“怎么做”，maintain 只写“做什么、放哪、何时、额外检查” | 各页对公共方法的重述和否定句 | 见 §4 |
| S5 | 正向写法：平衡句改为“遇到某情形就做某事”，每个关键判据配一个中性例子 | 26% 的否定或限制句 | 依据 writing-for-agents 的 Negation 一节。成本低 |
| S6 | 自监测与演进回路：逃逸标记 → doctor → lessons → 步骤卡 → 回放 | 现在没有这条回路 | 见 §5 |

**保持不变**：

- 两种角色与会话绑定；
- 子命令名；
- Spec 与 Plan 的落盘位置、批次、每步自动提交、评审不提交；
- read_reference.py 及其测试；
- 不做兼容层、不搭平台。

## 4. 与公共 Skill 配合

### 4.1 现状问题

| 问题 | 证据 |
|---|---|
| 公共方法只被当成参考材料，它们最强的“步骤 + 完成判据”没被用作骨架 | 例如 grilling 的“前沿为空才结束”、diagnosing-bugs 的“先要一个能变红的回路”、to-tickets 的“垂直切片 + 阻塞边”、code-review 的两轴并行 |
| maintain 页面重述加限制公共方法，适配规则分散在 dependencies、method-use、各方法页、用户级 AGENTS 与 README 五处 | Skill 正文 |
| 回执只证明“读过”，B 批交回没有一处采用落点 | 反思报告 §3.5 |
| Claude 侧同时有插件版（mattpocock-skills:tdd 等）和本地副本，版本不同 | Skill 列表与 README |
| 公共方法与本地政策冲突：code-review 默认并行派子代理，grilling 用子代理查事实，与用户级“子代理须显式选型、未要求不派”的规定冲突，现在只靠零散否定句处理 | 各 SKILL 原文 |

### 4.2 组合契约（composition.md 一张表，唯一来源）

| maintain 步骤 | 用哪个公共 Skill 的哪一步 | maintain 提供的输入 | 公共步骤产出落到哪 | maintain 覆盖的部分 |
|---|---|---|---|---|
| clarify | grilling：决定树、轮次、前沿为空 | 项目事实、现状成因 | Spec 的锚点与决定 | 只问影响目标、范围或验收的问题；查事实不派子代理，除非用户要求 |
| spec | to-spec：问题、方案、用户故事、测试决定、范围外 | 锚点、问题样本 | `doc/spec/<版本>/` | 不发布 tracker；用户故事不求长列表 |
| plan 切片 | to-tickets：垂直切片、阻塞边 | 四张表 | Plan 步骤与「依赖与停等」表 | 不逐票问用户，按批次评审 |
| plan/exec 测试 | tdd：tests.md、mocking.md | 原生契约、独立算例 | 步骤验证与交回 | 不强制完整 TDD 循环 |
| 困难缺陷 | diagnosing-bugs：先建能变红的回路 | 现场证据 | 交回或评审中的定位段 | 实验不越授权 |
| review 实现 | code-review：Standards 与 Spec 两轴 | Spec、项目标准、Plan 表 | 评审意见 | 加锚点对照、消费者核对、成本、逃逸标记；派子代理按用户级选型规定 |
| 写模型指令 | writing-for-agents | 被改页面 | 步骤卡与指令页 | — |
| 概念变化 | domain-modeling | GLOSSARY | 项目术语真源 | 不另建 ADR 目录 |
| doctor | retro：导航、信息访问、工具成本、无效指令 | 逃逸表 | 诊断报告 | 不做无条件门禁 |

配套规则：

- 每张步骤卡只写一行指针，例如“第 2 步按 grilling 做轮次；maintain 另要求：锚点”。不重述公共方法的内容。
- 版本：composition.md 记录所用公共页的 sha，doctor env 比对。Claude 插件版与本地副本不同时，maintain 一律按路径读本地副本；插件版被宿主单独触发时，不算 maintain 的采用。
- 采用证据：交回或评审写“哪一步用了哪个公共步骤，产出在哪”；回执只作留证。

## 5. 对齐人的期望、自我监测与演进

三层回路，各有产物：

| 回路 | 做什么 | 产物 | 谁来消费 |
|---|---|---|---|
| L1 任务内对齐 | clarify 定期望锚点 → spec 带入 → plan 的场景覆盖表 → review 做锚点对照。用户每次纠正，按“需求变化 / 补充事实 / 误解 / 设计错 / 执行偏离”归类后写回锚点 | 锚点、纠正记录 | 同一任务的下一环节 |
| L2 任务间监测 | review 与 handback 给每个问题写逃逸标记；doctor 汇总逃逸表、做规则对照和复发识别 | 逃逸表、复发列表 | doctor、用户 |
| L3 Skill 演进 | 用户选定 doctor 的 Skill 变更候选 → `doc/project/` 立需求与方案 → 改步骤卡 → 写入 lessons.md → 用历史逃逸回放验证 → 下次 doctor 核是否复发 | lessons 条目、回放结果 | Skill 本身、所有宿主 |

**为什么 lessons.md 放在 Skill 仓里**：Codex 和 Claude 都读 `~/.agents`，这样就解决了“教训只在 Claude 记忆里，Codex 看不到”的问题。条目只记已经改进步骤卡的教训，不堆规则；每条注明它改了哪一张卡的哪一步。

**回放验证**有两档，由用户选：

- **纸面回放**：派一个没参与修改的读者，只给新步骤卡和历史场景，判断这一步会不会拦住当时的错误。成本低。
- **真实回放**：在下一次真实维护中观察。自然的首例是 2.0.3 B01-R02 的设计补充：设计者需要交出消费者追踪表。

不建评测平台，也不建状态库。

## 6. 用户级 AGENTS.md 的优化

对象有三份：源文件 `~/.agents/AGENTS.md`（3732 字节）、Codex 副本（逐字节相同）、Claude 副本 `~/.claude/CLAUDE.md`（4406 字节）。这三份在**每个项目、每个会话**都会进入上下文，所以每一行都要求改变行为，否则就是负担。依据：writing-for-agents 的 context load、no-op 与 Negation 三节，以及 retro 的观点：全局 AGENTS 应尽量少写，主要放导航指针。

### 6.1 逐节问题、原因、方案

| 位置 | 问题 | 原因 | 方案 |
|---|---|---|---|

### 6.2 结构方案

用户级 AGENTS 只留四类内容，目标是控制在约 2 千字节以内：

1. 优先级一句；
2. 跨项目都会改变行为的原则（每条是一个动作，配短例）；
3. 导航指针（maintain，以及 Skill 名到项目目录的映射）；
4. 宿主差异。

角色定义、文档规则、诊断说明都归 maintain。三份副本由源文件决定，漂移由 doctor env 用 `git log -S` 比对配置仓找出来源。这也说明 doctor 有信息访问缺口：一条命令就能查到的来源，四次被报成“未知”。这一条并入 §2 doctor env 的方案。

### 6.3 与 maintain 的分工

| 内容 | 归属 |
|---|---|
| 所有项目、所有任务都适用 | 用户级 AGENTS |
| 只在 Agent 产品维护时适用 | maintain |
| 本项目特有 | 项目 AGENTS |
| 从纠正中学到、还没验证是否通用 | maintain 的 lessons.md，在多个项目都观察到后再提升到用户级 |

## 7. 实施路线（供立项时参考）

| 批次 | 内容 | 先做的理由 |
|---|---|---|
| A | doctor 过程诊断 + 逃逸标记 + lessons.md（先用反思报告 §2 的 22 条初始化） | 先能测量，后面每批的效果才看得见 |
| B | plan、review 两张步骤卡，四张表，停等判据，batches.md | 本期复发最多的三类问题都在这里 |
| C | clarify、spec、exec、handback 步骤卡；SKILL 路由；documents 拆页；篇幅收敛 | 依赖 B 的表格式 |
| D | composition.md、版本基线、doctor env；退出 method-use 中的统计部分及各页重述 | 依赖前三批确定的步骤 |
| E | 用户级 AGENTS 精简与宿主差异节；同步三份副本 | 依赖 C、D 确定哪些内容归 maintain；改动影响所有项目，最后做 |

**每批验证**：

- 链接与读取工具测试；
- 必读量读数；
- 纸面回放对应的历史逃逸；
- 首次真实使用的观察（不另启实跑）。

**退出清单**：

- documents.md 中被拆出的部分；
- method-use 里“公共方法使用统计”一节；
- 各方法页对公共 Skill 的重述；
- doctor-analysis 的五类对象结构；
- dependencies 中的适配散文（并入 composition 一张表）。

**风险**：

- 表格变成形式。对策：评审抽查引用位置，回放检查。
- 整体重写丢掉有效规则。对策：改动前逐条映射旧规则的去向，回放全部 lessons。
