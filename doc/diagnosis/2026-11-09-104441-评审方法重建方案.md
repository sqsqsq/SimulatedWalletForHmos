# 评审方法重建方案

2026-11-09，维护设计者（Claude Opus）。用户指出：评审方案和标准也要优化，否则每次 CLI 测试都要用户人工反馈才能发现问题。本方案是 2.0.4 Spec 的输入，现在只写设计与验收，不改标准、脚本或 Skill。配套诊断见 [2.x 适配根因诊断](2026-11-09-104441-2.x适配根因诊断.md)。

- **现状问题**：效果评审围绕 58 项机制条目和当轮挑出的缺陷做，没有固定的效果量具，也不和基线、上一轮对照。Story 内容收缩、跨轮复现、过程异常这几类问题只能靠用户提醒。
- **做法**：在机制评审之前，先用四件固定量具产出一张“效果总表”：金样可达检查表、基线与趋势对照、复现问题探针、过程异常检测。问题由量具找，用户只做确认和取舍。
- **验收**：用这套方法纸面回放 2.0.3 预跑，本轮已知的 13 项问题全部有对应量具，其中 7 项不需要语义判断、可由脚本直接报出。

## 1. 四件量具

### 1.1 金样可达检查表

- 把每份金样拆成三类：A 输入可达、B 维护前提、C 表达形态。A 类按业务关系逐条列出，每条带金样位置与输入依据。初版在 `output/evidence/2.x-adaptation-diagnosis/golden-reachable-checklist.md`：auto 47 条、car 34 条。
- 只有 A 类计入覆盖率；B 类出现时记“额外深化”，不出现不扣分；C 类单列。
- 检查表是评价域的固定量具，不进 Case、不进被测工作区。条目要改动时，按金样修订规则交用户审定。
- 每轮打点由评审者逐条读原文给出（写对、部分、写错、缺失、不可比），并写原文位置。

### 1.2 基线与趋势对照

每轮自动并排四列：金样、1.9.9 基线、上一轮、本轮。内容有两部分：

- **形态**：逐章正文字数、表格行、Mermaid 数、界面图数。复用 `output/evidence/2.0.3-C02-prerun-review/20261109/scripts/story_shape.py`，入库后放到 `test/scripts/`。
- **覆盖**：检查表 A 类的写对、部分、写错、缺失数，以及逐条的变化（新转正、新退步、持续缺失）。

自动列出三类信号：

- 某章字数或表格行比基线低 30% 以上；
- A 类有条目从写对变成部分、写错或缺失；
- 同一条连续三轮缺失或写错，即复现。

阈值只是信号，不是门禁，由评审者解释。基线矩阵要补打 2.0.0–2.0.2 与 1.9.9 早期各轮，一次性完成。

### 1.3 复现问题探针

从 1.9.9 至 2.0.3 的评审里收集反复出现的问题，固定成探针，每轮逐条核，结果写“出现 / 未出现 / 不可判”：

| 探针 | 来源 | 怎么核 |
|---|---|---|
| 写操作结果未知被当成失败或成功 | 1.9.9 起每轮 | 逐个写操作核三种结果是否分开 |
| 待定事项写成可执行（含“可重试”） | 1.9.9 起每轮 | 对每个保持待定的议题，核正文、验收是否承诺了行为 |
| 撤销或删除范围泛称 | 2.0.2、2.0.3 | 核可撤状态是否与状态机一致 |
| 数据有消费者没有生产者 | 2.0.2、2.0.3 | 对每个展示字段核接口来源 |
| 统计空投影写成“不涉及”，或规约判适用却没有落点 | 2.0.2、2.0.3 | 规约判定与 10.3、验收对照 |
| DFX-02 把文案资源排除在外 | 2.0.1 至 2.0.3 | 有新增文案时核结论 |
| 按建议删内容（删承诺、删指认） | 2.0.3 | 对比复核前后稿的删除行 |
| 工程缺失能力的探针没识别（如车钥匙卡片） | 2.0.3 | 按 Case 声明的探针逐条核 |

探针清单放在 `test/regression/`，与标准同管；新增探针要写来源轮次。

### 1.4 过程异常检测

在 `test/scripts/measure_run.py` 的现有读数上增加以下项，结果都写进度量输出：

| 检测项 | 判法 |
|---|---|
| 自建 Goal、`headless_assumed` | 原生会话出现 `create_goal`，或产物出现 `headless_assumed` |
| 产物编码异常 | 需求目录下的文本产物不是 UTF-8（例如 UTF-16 BOM） |
| 审查回复没落盘 | 原生会话里有独审回复，但 `doc/reports/` 下没有对应材料键的保存件 |
| 只因非阻断建议触发的复核 | 复核派审之前的报告结论是 pass/warn，且没有阻断项 |
| 读 checker 源码按文件统计 | 按文件列出次数与首次时刻 |
| 按阶段计时 | 取材、范围、蓝图与质询、成文、独审、登记与交付、CU 准备，各段起止 |
| 续发复核的识别 | 按原生 `send_message` 链认出复核轮及其结论（C02 评审 §5 的度量缺口） |

脚本只报事实；是不是问题，由评审者在效果总表里判断。

## 2. 标准与流程

### 2.1 效果总表放在第一层

在 `test/regression/extension-acceptance.md` 的 58 项之上加“效果总表”。每次效果评审第一页先写这张表，机制条目放第二层：

| 栏 | 内容 |
|---|---|
| 终点 | 请求终点、实际到达、没到达的原因与归属（必然限制、Extension、装置、模型） |
| 覆盖 | 检查表 A 类的四种计数，相对基线与上一轮的变化 |
| 退化与复现 | 1.2 的三类信号与 1.3 的探针结果 |
| 过程异常 | 1.4 的检测结果 |
| 成本 | 总时长、各阶段时长、读 checker 源码、context、独审轮次 |

修改标准时按现有规则写版本递增、保持集合与核对结果。

### 2.2 效果评审的固定顺序

1. 跑形态对比、度量与过程异常检测（脚本）。
2. 用检查表打点、核探针（评审者）。
3. 写效果总表。
4. 再做机制归因与 58 项。

maintain review 步骤卡里“效果”对象的必核范围，补上“基线与趋势对照、探针清单、效果总表先行”。这是用户级 Skill 改动，单独请用户确认。

### 2.3 用户的位置

评分仍由用户确认。所有问题都应在提交评审前由量具和评审者发现；用户的反馈只用于确认、取舍与目标调整。用户事后指出的问题，按评审漏判记逃逸，回到量具里补一条。
