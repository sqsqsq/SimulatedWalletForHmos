### 3.3 项目规则与工具：共享夹具缓存损坏是反复出现的可靠性缺口

**同一症状连续三次出现。** `upstream-sr` 共享树带 `.ready`，内容却残缺：

| 出现 | 键 | 症状 |
|---|---|---|
| A01 | 0b8b5366… | 缺 `doc/extensions` 与 inbox |
| A05 | 33ad907d… | 只剩 `AR/story-src/materials.json` |
| B01 | ddce7b89… | materials.json 的 `origins` 为空 |

三次键都不同，都是新建的树。每次都是删树、同键重建后通过，A01 和 A05 还残留了 `designed/flowed-*.building-*` 目录。三次的处置都是“留证、删树、重跑、交设计者”，测试域一直没有承接。

**代码事实**（`test/tests/shared_state.py:71-103`）：

- `.ready` 只证明构建函数当时没抛错，读者此后不再核内容。
- 锁超时按锁文件 mtime 超过 600 秒判定，之后另一进程会 `rmtree(final, ignore_errors=True)` 再 `os.replace`。
- `_prune` 删除目录 mtime 超过两天的条目；目录 mtime 不随读取更新。不过三次都是新键，这条不能解释本次症状。

**归因的支持程度：** 交回假设的“锁超时重建时在 Windows 上部分删除”与残留的 building 目录相容，但 A05、B01 的症状是内容被定向缺失（只剩一个文件、origins 为空），也相容另一种解释：构建后有人改写或删除了共享树。三种解释都没有排除，原因未知，需要最小复现。每次出现耗一轮定位、删树和重跑，并让失败与产品缺陷混在一起。

**上次报告的冷 builder 问题已修，失效键问题部分仍在：**

- `test_story_update.py` 的 `_registered`/`UpdateCase()._walk` 冷路径已退出：`_walk` 只由 setUp 调用，`self.root` 已先设好。这项可以关闭。
- `WALKED` 键（`test_story_update.py:54`）仍不含本文件，而基类 `before_init`（:116）定义在本文件。只改基类前态时缓存不失效。静态可达，没有动态复现。

**affected 漏掉全机制文本守卫，三次被批末兜住：**

| 步骤 | 漏掉的用例 |
|---|---|
| A05 | handback 后修 3 条预期 |
| B01-R01 | verifier_report_protocol 的旧字面 |
| Q1 批末 | test_knowledge_forms 专名 |

TEST §5 要求 affected 覆盖“直接测试与消费者”，但 test_knowledge_forms、test_negative_guards 这类对整份 extensions 文本做守卫的用例，没有被点名为任何机制文本改动的消费者。代价目前不大（批末一次修正），但每次都让批末最后一个对象缺一次完整全绿。
