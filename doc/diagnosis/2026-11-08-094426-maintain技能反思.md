## 1. 结论

1. **Skill 上线后，10-11 全史分析指出的老问题几乎都还在。** 方案没追到最终消费者、组合行为留白、设计错到实施后才发现、评审漏判效果与成本、过度设计与过度简化来回摆，这些在三个版本里都能找到新案例（见 §2）。
2. **多数人工纠正发生时，Skill 里其实已经写着对应规则。** 规则在，但没有改变行为。原因有三：
   - 规则是要模型“记住去做”的清单，不要求留下可检查的产物；
   - 关键判据写得模糊，模型就默认保守；
   - 每个子命令开工前要读 1–2 万字的规则，关键句被稀释。
3. **教训没有回流到 Skill。** 用户的纠正记在当版的 Plan 讨论段和 Claude 记忆里；下一版设计者（Codex）不读上一版 Plan，也读不到 Claude 记忆。同一条纠正（“没必要停等”）11-03 改过一次，11-07 又出现。三轮 Skill 修改（11-02 加读取回执，11-07 合并、落盘结构）都在改结构，没有一轮针对这些反复出现的失败。
4. **doctor 发现不了这些问题，这是方法本身决定的。**
   - 它以“当前工作的产品状态”为中心，结论与评审大量重叠；
   - 它用读取回执评价 Skill，只证明“读过”，证明不了“读了有用”；
   - 它没有任何一步去收集人工纠正和返修次数，也从不拿失败去对照 Skill 正文。

   用户 11-07 问过“诊断里保留的本 Skill 的问题分析了吗”，当时核实的答案是“没审过 Skill 正文”。我今早的 doctor 报告同样没有：它只诊断了 2.0.3 的产品与测试状态，没有一条关于 Skill 功能的结论。

## 3. 各功能的问题与原因

### 3.1 clarify / spec：先给结论，再被用户纠正

**现象**：设计者在理解现状之前就形成整体判断（“机制过重”“目录调整就是能力保持”“旧实现要保留”），需求写成方向而没有具体对象。三类纠正都要用户逐级对比、举样本才暴露。

**为什么没一次做对**：

- clarify.md 的“查项目现状”只到“现在是什么”，没有要求回答“现在为什么是这样”：哪些踩坑形成了现有设计、改掉它会丢什么。模型于是从当前读到的片段直接外推结论。
- spec.md 要求验收写“触发、结果、证据类别”，但没要求用真实样本说明问题：哪几份产物、哪一处、人期望看到什么。没有样本，需求就只能写成形容词，也就是用户说的“许愿”。
- 用户原意被扩大或缩小时，spec.md 的保护项规则只在成文后的自检里出现一次，没有逐条对照用户原话的步骤。

### 3.2 plan：反复漏掉最终消费者，在原生能力旁边另起机制

**现象**：返修最多的地方。B01-R02、2.0.2 方案复核 9 项、2.0.1 D 批 6 轮，以及 A03 的资格链，归因都是“设计覆盖遗漏”或“设计错误”，不是执行偏离。

**为什么没一次做对**：

- **走查没有产物。** plan.md §2 写了“逐段走正常链：输入取得 → 行动前送达 → 决定 → 产物 → 下游使用”，§4 写了“实施者视角走查”，但都不要求在 Plan 里留下结果，比如每个变化的最终消费者在哪个文件哪一行。模型写完方案后无法自证走到了哪一层，评审也无从检查，只能等实施撞上。B01 的方案分别核了准备、冻结、收口和知识任务，恰好没走到最后那个 verifier request。
- **没有“先核原生”这一步。** 用户级 AGENTS 写“复用现有能力”，项目 AGENTS 写“缺 Framework 能力回其所有者”，但 plan.md §1 的事实核查只说“定位真实生产者、消费者、公共接口”，没有一个动作是“这项职责平台是否已经承担”。A03 的资格链、2.0.1 的“死守旧实现”，都是在没核原生的情况下自建。
- **投入判断两头摆。** 「风险与投入」表逐项判断“某个保护值不值得”，但没有锚点。用户嫌重时，模型连场景一起删（Maison 07）；用户强调可靠时，又加满前置与取证（N2 硬前置）。缺的是在删减或增加之前，先把用户必须覆盖的真实场景列成清单、逐条核对。
- **设计与评审同一方。** 2.0.2 和 2.0.3 的具名 reviewer 就是方案制定者本人（Codex），Plan 的质量主要靠自查。2.0.3 曾另派只读复核，A03 资格链仍然通过，说明光换一个读者不够，还要有可检查的走查产物给读者核对。

### 3.3 review：停等判据模糊，效果与成本靠用户提醒

**现象**：批间无必要停等发生两次（11-03、11-07），每次都由用户追问才撤销。Story 审查 8 次的成本问题由用户发现。首次效果归因过宽，由补评更正。

**为什么没一次做对**：

- documents.md「批次与步骤」写“影响后续契约、设计或验证可信度的问题先修，是否须先复评按依赖说明”。“验证可信度”可以覆盖几乎任何问题。判据可宽可窄时，评审倾向保守地选“先停”，因为停下不会被判错，放行却可能被判错。规则里缺一个可判定的问题：后续步骤是否读取或依赖该问题所在的契约？不依赖就继续。
- review.md §3 效果审查的列举里有“成本”二字，但没有动作：没要求数一数审查次数、返修轮次、耗时，并与预期对比。所以 D02 效果评审写了内容差距，没写“同一 Story 被审 8 次”。
- 第二轮返修反思已经在执行：复评里有“责任反思”段，归因到设计覆盖遗漏，这条规则起了作用。但反思只写进当轮评审，没有去处：没人汇总“哪类设计遗漏在反复出现”。

### 3.4 exec / handback：总体按规矩走，缺口在验证选择

执行者遇到设计缺口时停下交设计者，没有造替身绕过；无关部分继续做；交回如实列出未覆盖项。这些都符合 exec.md，是做得好的部分。

问题集中在两点：

- **affected 选测靠执行者判断。** 跨全机制的文本守卫不在“直接测试”范围内，三次都到批末全量才发现。这是项目 TEST §5 的缺口，不是 Skill 的。
- **方案已写明的项被当成待定（Q1 第 6 项）。** exec.md 写“方案含糊或矛盾时及时问”。执行者遇到实现上需要“猜”的地方，选择问而不是按方案实现。复评认为方案其实给出了可复用的语法（`authorityFile` 的 scheme 前缀）。这一项更像方案表达不够直接，责任在 plan 与 exec 之间。

### 3.5 Skill 正文本身

| 量化项 | 读数 | 含义 |
|---|---|---|
| 每个子命令开工前的必读量（SKILL + documents + method-use + dependencies + 本功能方法页，不含公共方法和项目文件） | clarify 约 1.05 万字；plan、review 约 1.67 万字；exec 约 2.05 万字；doctor 约 2.22 万字 | 动手前就是一两万字的规则，“停等判据”“走到最终消费者”这类关键句被稀释 |
| 含否定或限制的句子占比 | doctor、doctor-analysis、exec 为 26–27%；plan 21%；review 17% | 大量“不……也不……”的平衡句。模型能从中读出禁止什么，读不出遇到具体情形该怎么判 |
| 平均句长 | 29–52 字，dependencies 最长 | 一句话装五到八个约束，难以逐条执行和核对 |
| 规则重复 | “讨论与修订依据”在 8 个方法页各出现 2 次；“不提交”出现在 SKILL 与 4 个页面；“不自动”出现在 10 个文件 | 同一规则多处表述，修改时容易漂移，也增加阅读量 |
| 具体例子 | 全部方法页只有 3 个例子（clarify 的计时、spec 的报告、plan 的风险表） | 按 writing-for-agents 与本项目“示例形状压过规则文字”的观察，没有例子的规则最难迁移成行为 |

这种写法会被模型照搬：Codex 写出的 Plan 与评审（例如 2.0.3 总方案 §8、B01/Q1 复评）是同样的高密度长句，用户读起来吃力。这与记忆 `user-facing-doc-voice`、`reader-voice-not-document-talk` 记录的多次纠正同源。归因强度：推测，但与观察一致。

| 根因 | 说明 | 证据 |
|---|---|---|
| G1 规则不产出可检查的东西 | 走查、原生核对、场景覆盖、停等依赖，都只写成“要做”，不要求在 Plan 或评审里留下结果。做没做无法核对，上下文吃紧时首先被省掉 | B01-R02、11-03 起草漏判、A03 |
| G2 关键判据模糊，模型默认保守 | 停等、投入、阻塞的判据可宽可窄。模型选不会被追责的一边：停下、加保护、要更多证据 | 两次停等、N2 硬前置 |
| G3 纠正不回流 | 用户纠正写进当版 Plan 的讨论段或 Claude 记忆；下一版的设计者（Codex）既不读旧版 Plan，也看不到 Claude 记忆。Skill 的三轮修改（10-25 风险投入与批次规则、11-02 回执、11-07 合并）里，只有 10-25 那轮针对行为失败，之后同类失败复发也没再改 | 停等第二次；过简与过重来回摆 |
| G4 篇幅与密度 | 一两万字的前置阅读，否定平衡句多、例子少 | §3.5 读数 |
| G5 设计者兼任评审者 | Plan 主要靠自查；设计错误到实施后才被发现，代价是一轮实现再加一轮撤回 | 2.0.2、2.0.3 的具名 reviewer 安排 |

G3 是 doctor 本该补上的环节，见 §5。

## 5. doctor 自身反思：为什么它发现不了

### 5.1 实际表现

| 反复问题 | 哪份 doctor 报过 | 实际由谁提出 |
|---|---|---|
| 无依据的批间停等（两次） | 无。doctor-analysis 的检查表里写着“同批是否无据逐步停等”，6 份报告的“停等”命中只有我今早那份 1 次，而且说的是正向安排 | 用户 |
| Story 审查 8 次的成本 | 无（11-07 报告只复述了评审结论） | 用户 |
| 过度设计与过度简化来回摆 | 无（6 份报告“过度/冗余”零命中） | 用户 |
| 测试性能未达标的根因 | 10-27、11-04 两份专项报告 | 用户点名后专项诊断 |
| Skill 正文有没有问题 | 无（11-07 前零命中） | 用户 11-07 口头追问 |
| 公共方法用没用 | 11-02 起按读取回执报告 | 用户 11-02 要求 |
| 入口摘要滞后、测试缓存风险 | 每份都报，四次未采纳 | doctor（发现了，但没推动） |

可以看出：doctor 能可靠发现的是**当前产品与测试的状态问题**，这部分与评审高度重叠；**协作过程与 Skill 方法的问题，它一次都没有主动发现**；被用户点名后，它能做出有效的专项分析。

### 5.2 原因（对照 doctor 正文）

1. **方法以当前工作为中心。** doctor-analysis §1 要求“优先深查当前有效工作、反复问题、未关闭风险和前次候选”。实际执行时，“当前有效工作”吞掉了大部分精力，报告前三节几乎都是产品进度、测试状态和接续入口，与评审重复。
2. **没有“收集人工干预”这一步。** §1 提到要“定位原诉求、当时行为、人的干预与结果”，但这是建立全貌时的一句话，没有要求输出一张“自上次诊断以来的纠正与返修清单”，也没有要求按功能、发现者、引入阶段计数。没有这张表，“同类纠正第二次出现”就无从发现。
3. **用读取回执评价 Skill，是测了一个替代指标。** 11-02 起，§2「公共方法的实际使用」用 read.json 判断“读没读、有没有采用落点”。这只能回答“方法有没有被读”，回答不了“读了以后错误有没有变少”。历次报告的 3.5 节都写“本次分流有效”，评的其实是诊断会话自己的读取行为。
4. **从不拿失败对照 Skill 正文。** §3 的归因候选里有“能力未提供”“已有能力未使用或未送达”，但没有要求对每个反复问题去 Skill 里找那条规则：是缺失、模糊，还是写了没起作用。于是 Skill 永远不是被诊断的对象，只是诊断的工具。
5. **候选不升级。** §4 只复查“前次建议是否采纳”。入口滞后报了四次、缓存问题报了三次，没有规则规定“报到第 N 次怎么办”。doctor 只产候选、不追责任，候选就一直停在报告里。
6. **执行者与被诊断者是同一种模型、同一套盲点。** doctor 由维护模型自己跑，与设计、评审读的是同样的长规则。它在评审里没注意到的过程问题，在 doctor 里同样注意不到；只有给它一个具体关注点（性能、公共方法）时，它才能做好。

今早的 [11-08 维护自检](2026-11-08-092634-维护自检.md)是第 6 点的现成例子：它照着 doctor-analysis 做完了全部五类对象，但只写到 B 批阻断、缓存与入口，没有一条关于 clarify、plan、review 方法本身的发现。

### 5.3 doctor 应该具备的能力

doctor 的核心问题应当是：**自上次诊断以来，哪些工作没有一次做对，错在哪个功能，Skill 为什么没挡住？** 为此它至少要有：

1. **缺陷逃逸表**：每条人工纠正和每轮返修各记一行，列出功能（clarify/spec/plan/exec/review）、引入阶段、发现者（自查/评审/实施/实跑/用户）、轮次。来源是 Plan/Spec 的讨论段、评审的问题编号与反思段、交回的受阻段，都在项目文档里，不用扫描会话。
2. **规则对照**：每类反复问题，在 Skill 正文里定位对应规则，判为缺失、模糊、写了没起作用、或项目侧问题。
3. **复发识别**：与前次报告的逃逸表比对。同一形态第二次出现，或同一候选第二次未采纳，就列为首要候选，并标明责任位置在 Skill 还是项目。
4. **把产品状态降为附带**：产品与测试状态由评审负责；doctor 只记录对过程判断有影响的部分。

## 6. 候选优化（按影响排序）

以下是建议方向，不是施工步骤。第 1 条与第 4 条会新增 doctor 输出表或 Plan 必填项。按用户级规约，新增模板前须说明必要性与更简单替代，由用户确认。

| 优先 | 责任位置 | 建议变化 | 更简单的替代 | 怎样验证 |
|---|---|---|---|---|
| 1 | doctor-analysis.md | 把 §5.3 的“缺陷逃逸表 + 规则对照 + 复发识别”设为默认 doctor 的第一步和主要产出；产品状态退到附带。删除以读取回执代签“Skill 使用效果”的写法，回执只作为留证 | 只在 doctor 里加一句“列出自上次诊断以来的人工纠正” | 用本报告 §2 的事件做回放：新方法在 11-07 时点运行，应能主动报出“批间停等第二次出现” |

## 7. 覆盖、限制与下一步

- **证据边界**：人工纠正只来自文档转录与 Claude 记忆。转录时漏掉的口头纠正、Codex 会话里的原话都没读到。所以 §2 的计数是下限。
- **归因强度**：每一行写的是“对照规则后的判断”。“规则写了没起作用”只说明规则未能阻止，不证明模型当时没读到。篇幅与密度（G4）是否是主因，没有对照实验，属于有观察支持的假设。
- **没做的**：没有用新方法回放验证，没有统计 10-11 以前的数据（引用全史分析），没有评价公共方法 Skill 本身。

**下一步**：请你从 §6 选择要做的项。之后按以往 Skill 优化的做法，在 `doc/project/` 下立一份需求与方案（10-11、11-02、11-07 三轮都在那里），再修改 `~/.agents/skills/maintain/`。我建议第 1、2、3、4 条一起做：第 1 条让 doctor 以后能自己发现这些问题，第 2–4 条针对的是本期重复最多的三类纠正。
