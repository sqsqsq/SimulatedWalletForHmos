# 2.x 适配根因诊断

2026-11-09，维护设计者（Claude Opus）。用户要求：以金样为目标、1.x 为基线、2.x 为全新适配，讲清 1.x 生效的本质与 Framework/Extension 的协作方式；质疑继承的 2.x 适配方案；凡是 Framework 现有机制必然让 Extension 达不到 1.x 效果的，要明确提出。本报告只读取证，没有改产品、测试、金样、标准与运行原件，没有跑 CLI。证据在 `output/evidence/2.x-adaptation-diagnosis/`，评审方法的重建见同目录 [评审方法重建方案](2026-11-09-104441-评审方法重建方案.md)。

- **差距的构成**：
  - 最大的一块是从 1.x 起就没解决的写操作语义：结果未知、待定事项、撤销与恢复。九次实跑、两条线都没达到，2.x 只是没修好。
  - 第二块是 2.x 适配丢掉的知识层：规约落到验收、DFX-02、统计设计。这是我们自己的适配选择造成的，可以改。
  - 第三块是 Framework 3.1 的结构限制：凡是当前切片带未决产品决定的需求，原生流程必然到不了 Plan；蓝图阶段单独就超过半小时期望。
  - 金样本身是按 1.x 模型（Story 与 Spec 同阶段）做的，在 3.1 下有一部分天然够不着。
- **不收敛的主要根因**：
  - 四轮都在用“改指令、改审查组织、补原生接续”去修效果问题，而效果问题集中在两处：一处是规则写了模型也不做的语义层，一处是适配时丢掉的生产环节；两处都没被直接处理。
  - 同时没有固定的效果量具和基线对照，退化只能靠用户人工发现。
- **推荐**：不要把 2.0.4 再开成一轮机制改进。先由用户和 Framework 作者裁定三个结构问题（§5.3），同时换掉评价方法；然后 2.0.4 只做“选项乙”的三件事，先用离线重放证明有效，再跑完整 CLI。

## 1. 1.x 生效机制的本质

1.x 跑在 Framework 3.0.0 上。一个需求就是一个 Feature，Framework 提供 spec/plan/coding 阶段骨架、harness 与 verifier；Extension 在各阶段挂 `pre_phase`（story-view）、`post_check`、`pre_verifier` 与规则覆盖层（1.x `extensions/manifest.yaml:75–121`）。链条是 S1 取材 → S2 导入初析 → S3 关卡 → S4 收口 `AR/design.md` → **Framework spec 阶段内一次 pass 产出 spec.md、AR/review.md、AR/story.md**（1.x `SKILL.md:14–27`）。

| 1.x 产生效果的机制 | 靠什么成立 | 在 3.1 下这个条件还在吗 |
|---|---|---|
| Story 与 Spec 同一作者、同一阶段写，业务与技术同时成形 | Framework 3.0 的需求级产物就是业务形态的 `spec.md`，Extension 把 Story 挂在 spec 阶段 | **不在**。3.1 的需求级产物是组件蓝图（设计形态），业务规格降到 CU 层、排在 Story 之后 |
| Story 有业务形态的真源：`spec.md` 是“意图 SSOT”，Story 是“派生物，零新事实”（1.x `SKILL.md:204–207`） | 真源与 Story 是同一业务语言、同一粒度 | **变了**。Story 的真源换成蓝图，是 4+1 视图、契约、app_lens 这类设计语言 |
| 成文时就有知识判断与验收落点（1.x `story-write.md:52`：“知识判断、词表与验收落点在本阶段任务包 spec/author.mjs”） | spec 阶段知识任务；`knowledge-use.yaml` 逐条判定、`acceptance.yaml` 带规约验收；附录由 spec 扩展章投影 | **丢了**。2.x 知识任务只有蓝图三个动作与 CU 阶段（`knowledge-task.mjs:35–36`），Story 成文没有知识任务 |
| 允许条件 Plan：带未决继续，限制写清（标准 C3） | Framework 3.0 的 plan 阶段不因未决拦截 | **不在**。3.1 CU 门禁不收未决（§2.1） |
| 模型预算花在业务内容上 | 没有设计载体前置 | **不在**。蓝图阶段约 48 分钟（§2.3） |

1.x 达到的水平：1.9.9 发布轮建议分 auto 80/78/86、car 86/74/84（`SimulatedWalletForHmos-Story-1.0/doc/plan/1.9.9/2026-10-24-发布前问题收敛/评审意见/2026-10-25-初段CLI完整评审.md` §6）。但即使在 1.x，“结果未知 / 待定 / 恢复”这一层也从没写对：10-14、10-21、10-22、10-25 每轮都因此扣分。所以 **1.x 的强项是知识层与业务完整度，不是写操作语义**。

逐条对照见 `golden-reachable-checklist.md`：

- auto A 类 39 条：1.9.9 写对 21 条，2.0.3 写对 16 条；
- car A 类 27 条：1.9.9 写错 1 条，2.0.3 写错 6 条。

## 2. Framework 3.1 机制对效果的必然影响

判定分三类：**必然限制**（Extension 怎么做都绕不过）、**成本限制**（做得到，但代价落在 Extension 管不到的地方）、**可由本地解决**。

### 2.1 施工单位门禁不收未决：必然限制

`change-unit-design-gate.ts`（被测 ff111909）的 `dispositionBlocks`（81–85 行）规定：施工单位设计闭包里任何一条记录是 `open_decision`、`blocker` 或 `knowledge_state: unknown`，都以 `change_unit_current_design_unresolved` 拒绝（195 行）。蓝图文档只允许“只被远期切片使用”的未决项停放。

**后果**：

- 凡是当前切片带未决产品决定或工程阻断的需求，原生流程必然到不了 Spec/Plan。1.x 的“条件 Plan”在 3.1 下没有对应物。
- 本轮 car 的实际阻断就是这条：`gap-draft-persistence`（blocker）与 `gap-accept-data-source`（open）都在当前切片，F1 修好后照样会拦。
- **金样本身也到不了**：car 金样的 Plan 带着待定的 D8（待接受能否撤回），D8 就在管理与撤销这个当前切片里；auto 金样止于 Spec，也带着 D3、D4、D8。按 3.1 原生流程，两份金样的终点都不可达。

**要上游改的**：允许 CU 带“声明了条件的未决”进入 Spec/Plan，限制写清后继续，即 1.x 的条件 Plan。否则只能调整目标：凡是带当前切片未决的 Case，终点改为 `design_handoff`。

### 2.2 行为与验收在 CU Spec，送审 Story 排在它之前：成本限制，并受 Extension 选择放大

`docs/concepts/blueprint-design-inputs.md`：

- 蓝图负责共同决策、部件边界、外部契约；
- **spec 负责补清行为、预期、边界和验收分层**，验收 ID 挂在 CU predicate 上；
- 蓝图目标可以携带明确的 `acceptance` 机器内容（`derive.blueprint-acceptance`）。

component-design §5 写明，评审投影“供宿主装配 Story Document”，“零新设计事实”。

**后果**：需求级送审的 Story 写在 CU Spec 之前，按 Framework 分层，行为细节和验收这一层还没成形；只有把它们先写进蓝图（机器形状、过校验器），Story 才有东西可派生。这在 3.1 里做得到，但代价是模型在蓝图里多写一层机器内容，所以属于成本限制。真正把它变成“丢失”的，是 Extension 的两个选择：Story 成文不给知识任务，规约验收只挂 CU（§3）。

### 2.3 蓝图编写成本：对性能目标是必然限制

- 本轮 auto 从范围拍板（21:42）到可以成文（22:31），约 48 分钟花在蓝图与质询上（`stage-2.0.3-auto.md`）。
- 1.9.9 car 从范围拍板到交付，包括 Spec 与 Story，只用了约 50 分钟（`stage-1.9.9-car.md`）。
- 两例写蓝图前都扫了约 20 个 Framework 校验器源码（`checker-files-*.txt`），蓝图 YAML 175–183K 字节，fingerprint 要“先写占位、跑 checker 拿 computed 值回填”。

**后果**：只要蓝图载体与校验方式不变，“半小时到可交付”在 3.1 下必然不可达。这块成本 Extension 管不到，要上游给可直接照用的完整载体形状、指纹计算入口，或减轻编写负担（C02 评审 F3）。

### 2.4 其他各项

| 项 | 判定 | 依据 |
|---|---|---|

## 4. 四轮不收敛的过程原因

### 4.1 投入与结果

| 版本 | 批次 | 评审 | 交回 | 实跑结果（产物/性能/知识） |
|---|---:|---:|---:|---|
| 2.0.0（10-26 至 10-28） | 3 + 2 个专项 | 17 | 18 | 10-27 auto 一次 |
| 2.0.1（10-28 至 11-03） | 5 | 14 | 29 | 82/55/78；car 来源门停住 |
| 2.0.2（11-03 至 11-06） | 6 | 19 | 26 | 80/55/82；74/40/72，未到 Spec |
| 2.0.3（11-06 至 11-08） | 3 | 15 | 15 | 76/60/76；74/52/74，停 design_handoff |

两周 17 个批次、65 份评审、88 份交回（`doc/plan/2.0.x/` 计数）。产品投入的 R 从 2.0.1 的 96% 升到 131%，扩展有效行数从 18579 升到 18917；效果没有回到 1.9.9。

### 4.2 改的是什么

17 个批次里，直接针对 Story 产出的只有 2.0.1-03（业务送审）、2.0.2-02（知识与业务表达）和 2.0.3-01 的一部分；离线测试与测试装置提速占 4 个（2.0.0 提速、2.0.1-05、2.0.2-05、2.0.2-06）；其余都是原生适配、来源、审查组织与观测。

拿 2.0.2 D02 列出的问题，看 2.0.3 实跑后的结果：

| D02 问题 | 2.0.3 处理 | 本轮结果 |
|---|---|---|
| car 来源门失败 | Q1 来源分责 | **关闭**：交付门与准入通过 |
| 独审返工 75%、保存件不原样 | A04 审查组织 | **改善**：轮次 7→4，原样性基本成立 |
| car 接受方数据缺来源 | A01 | **改善**：如实登记缺口 |
| 待定写成可重试、超时当失败 | A01 表达 + A04 审查 | **未变**，独审还认可了一处 |
| 统计上篇后移、空投影写不涉及 | A01 改 `design.md:92` | **auto 退步**（写不涉及），car 有改善 |
| DFX-02 误判 | 无专项处理 | **未变**（第三次） |
| car 到不了 Plan | B01 原生接续 | **未变**，原因从来源门变成 CU 门禁（§2.1） |
| 成本超期望 | C01 观测 | **未变**：auto 157.7→111.1 分钟，car 只到 design_handoff |

机制层面的问题（来源、审查组织、接续）大多修好了；效果层面的问题（语义、知识层、终点、成本）基本没动。

### 4.3 为什么效果问题修不动

1. **规则写了，模型不做。**
   - 2.x 在业务流程章合同里专门加了“有结果未知的环节（超时、回调未到）时，停在什么状态、由谁确认”（`story-chapters.json` 05-flow，1.x 没有这句），作者页、质询页和读者审查任务也都写了未知结果要求（2.0.2 E2/E3 已核送达）。
   - 本轮两例 Story 里“结果未知 / 确认中”出现 0 次。对被测模型 deepseek-v4-flash，靠增加规则文字改变不了这一层。
   - 这是证据最充分的结论，但还不能断定模型“做不到”：从没试过“每个写操作必须逐行填成功、明确失败、结果未知三种结果”这种结构化承载（§5 实验一）。
2. **知识层丢失没人发现。** 2.x 迁移时，“成文时就有规约验收”这个场景没有承担者，场景覆盖表里也没列它。之后三轮评审都没有做相对 1.9.9 的内容对照，直到用户指出。
3. **评价方法不能暴露退化。** 每轮评审围绕 58 项机制条目和当轮挑出的缺陷做，没有固定的效果量具、基线与趋势对照（重建方案见同目录文档）。
4. **反馈回路太长。** 每个效果修复只能靠下一次完整 CLI（约 2 小时）验证，中间没有离线重放；一轮版本两到三天，大部分时间花在机制、测试与文档上。
5. **目标里混着够不着的部分。** 金样按 1.x 模型做，其中有 B 类维护前提，以及 §2.1 的条件 Plan。但对照检查表，B 类在 auto 约 3 条、car 约 3 条，**主要失分仍在 A 类**，所以目标问题是次要原因，不能用它解释大部分差距。

### 4.4 被测模型能力

两条线用的是同一个被测模型；金样由维护者用更强的模型手工做成。语义层九次实跑都没出现，说明在“规则文字”这种送达方式下这是模型的稳定行为。是否在结构化承载下也做不到，**证据不足**，要靠 §5 实验一回答。

## 5. 结论与 2.0.4 选项

### 5.2 可选方向

| 方向 | 做什么 | 代价 | 退出什么 | 前提 |
|---|---|---|---|---|
| **甲** Story 先行 | 回到 1.x 的生产方式：Story 按原件与人答写全业务与验收，蓝图据 Story 设计，质询核一致性 | 改动最大；要处理 Story 与蓝图两份事实的一致性 | “Story 从蓝图派生”的整套约束 | Framework 接受 Story 作为设计输入 |

### 5.3 需要用户与 Framework 作者裁定的三个问题
