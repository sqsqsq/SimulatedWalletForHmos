## 一、本波要解决的真实痛点

延续第一波沙盒自检暴露的新发现：**即使 scope 守门能拦住"写错的模块"，也拦不住"从一开始就读错的模块"**。用户的真实样例：

> PRD 阶段让弱模型处理需求"银行卡模块新增 XX 能力"，它把「卡中心」(业务口径) 误解为「卡管理」(技术模块 `CardManager`)——两个词从自然语言上极像，但归属完全不同。错误从 PRD 的第一行就埋下了，scope 守门在 design 阶段再兜底为时已晚。

根因：**真实工程代码 40-60 万行，LLM 任何一次性探索都啃不下**。弱模型只能在"有限上下文 + 文档检索"下工作，必须把"自然语言 ↔ 模块"的权威映射**落成可机械校验的资产**，而不是每次让模型临场 grep 代码。

本波的策略：

1. **把两份 SSOT 落盘**：`doc/module-catalog.yaml`（每模块画像）+ `doc/glossary.yaml`（业务词 → 模块），所有后续 Skill 都围绕它们做 BLOCKER 校验
2. **自举 Skill**：`skills/0-catalog-bootstrap/`——弱模型也能在大工程里增量建档这两份 SSOT，一次一个模块 / 一条术语，不爆上下文
3. **机械护栏**：10 条"不靠推理、纯字符串 + 正则 + 集合运算"的门禁，专门给 MiniMax 2.5 / GLM 4.5 这种中低端模型兜底

### 2.2 第二波 4 条初代护栏

| 护栏 | 位置 | 触发场景 |
|---|---|---|
| **A：Step 1.5 反扫 NOT_responsible_for** | `infer-glossary-term.md` | 术语 `<T>` 在某模块的 `typical_business_terms` 命中，但同一模块 `NOT_responsible_for` 又排除了 `<T>` → 触发 `typical_term_with_not_responsible_for_conflict`，降级 confidence |
| **B：`typical_vs_not_responsible_conflict` catalog 自相矛盾扫描** | `check-catalog.ts` + `catalog-rules.yaml` | catalog 内同一模块的 typical_business_terms × NOT_responsible_for 字面冲突 → MAJOR WARN，迫使作者修 catalog |
| **C：Step 4.5 alias-merge 分支** | `infer-glossary-term.md` | 新术语与已入库术语同 canonical_module + 字面相似 ≥ 0.5 → 推荐作为 alias 并入现有条目而非新建 |
| **D：module-card `NOT_responsible_for` 反向自检** | `infer-module-card.md` | 草稿落盘前机械扫 typical_business_terms × NOT_responsible_for 子串冲突，强制作者二选一修复（删词 / 加消歧规则） |

### 2.3 第二波实战样例：「账户」term 的 4 护栏联动

> 种子清单里同时有「账号」和「账户」。若没有护栏，弱模型会：Step 1 两条都高置信度命中 `AccountManager.typical_business_terms` → 新建两条独立 term → glossary 被近义词撑爆，Skill 1 消歧时候两条都返回，反而降低命中质量。

启用护栏后的实际轨迹：

1. 第一次跑「账户」：Step 1 命中 → Step 1.5 反扫发现同模块 `NOT_responsible_for[3]` 明文排除"账户"（=钱包业务账户）→ 冲突告警，confidence 从 high 降 medium，hint 里逐字引用原文
2. 用户依据提示改 catalog：在 `AccountManager.NOT_responsible_for[3]` 里加消歧规则（"指华为账号登录身份归本模块；指钱包业务账户归未来 WalletAccount 类模块"）
3. 再跑一次「账户」：Step 1.5 仍识别为冲突，但 hint 清楚了；Step 4.5 进一步发现与已入库「账号」同 canonical + 字面相似度高 → 触发 `alias_merge_candidate`，默认推荐 `e 并入账号`
4. 用户回 `e`，staging 直删，glossary「账号」term 新增 alias"账户"，hint 写入完整消歧规则

**护栏的价值**：即使模型完全不做反思，也能把这类同义词 + 语义二义的组合一路引导到正确终点。**弱模型可以靠机械规则达成 Opus 级的消歧能力**，这是本波第一个强验证点。

## 三、第三波 — P0-1 ~ P0-4 机械守门

### 3.1 四条新护栏

| # | 护栏 | 位置 | 级别 | 机制 |
|---|---|---|---|---|
| **P0-1** | glossary Step 2.5 反向指针扫描 | `infer-glossary-term.md` | prompt 侧 | 对 `NOT_responsible_for[]` 跑 4 条正则（`/属\s*X\s*模块/` / `/归\s*Y\s*类?\s*模块/` / `/在\s*X\s*里/` / `/→\s*X/`），命中即在 candidates_top3 里加一条带"反向指针"的候选；canonical 仍填 TBD（被指向的模块可能尚未建档） |
| **P0-2** | 种子技术词守门 | `check-glossary.ts` + `infer-glossary-term.md` + allowlist 文件 | **BLOCKER** | 扫 `doc/glossary-seed.txt`：`^[A-Z][a-zA-Z0-9]+$` 驼峰、或等于 `catalog.modules[].name`，两项任一命中即 BLOCKER；`doc/glossary-seed-allowlist.txt` 提供逐词豁免 |
| **P0-3** | catalog easily_confused_with 对称性 | `check-catalog.ts` + `catalog-rules.yaml` | MAJOR | A→B 声明混淆时，B→A 也必须声明；`disambiguation` 含关键字 `unidirectional` 可显式豁免 |
| **P0-4** | catalog easily_confused_with 自引用 / 空 module | `check-catalog.ts` + `catalog-rules.yaml` | **BLOCKER** | `ec.module === m.name` 或 `ec.module === ''` 即报错 |

### 3.2 顺带修掉的 2 个潜伏 bug

| bug | 根因 | 修复 |
|---|---|---|
| `readSeedLikeFile` 不支持行内 `#` 尾注 | 原实现只剥整行注释，`SDK  # reason: xxx` 会被整行当成术语 | 截断首个 `#` 后再 trim |
| `toEasilyConfusedArray` 静默丢弃 `module: ""` 条目 | 解析器在源头过滤空串 → P0-4 看不到空 module | 解析器保留原样，由下游各 check 自行决策；`easily_confused_references_exist` 同步加 `if (!target) continue` 避免双报 |

## 五、本波在沙盒内做的"真实 flow"

为了证明"Skill 0 能从零开始搭好 SSOT"，本波在沙盒内用 Skill 0 实际跑了一轮端到端，**用户确认这套流程体感可用**：

### Phase A：module-catalog 自举

1. 用户手动删除 `doc/module-catalog.yaml`（模拟内网移植首日状态）
2. AI 读 skill 后自主创建骨架文件 `{schema_version: 1.0, modules: []}`，harness 变为 `modules_is_list: WARN`（合法中间态，不 BLOCKER）
3. 交互式 `y+` 高置信度批量模式依次建档 5 个沙盒模块：`CommFunc / CommUI / AccountManager / WalletMain / Phone`
4. `CommFunc ↔ CommUI` 走 `easily_confused_with` 对称声明（判定规则统一：「产物是可渲染的 UI → CommUI，否则 CommFunc」）
5. 最终 14/14 PASS

### Phase B：glossary 自举

1. 用户手动删除 `doc/glossary.yaml`
2. AI 创建骨架 + 发现 `glossary-seed.txt` 不存在 → 自动生成带详尽注释的模板，提示用户填种子词
3. 用户填入 13 个真实钱包业务词（含已知易混组「账号 / 账户」「卡包 / 卡中心 / 卡管理」等）
4. AI 交互式处理：
   - **高置信度批量 `y+`**：「首页 / 我的 / 卡包 / 添卡入口 / 设置 / 登录 / 账号」7 条一次合并
   - **「账户」触发 4 护栏联动**（见本报告 2.3 节），用户选 `e 并入账号`
   - **5 条低置信度 `q+` 统一作废**（「钱包账户」「银行卡卡中心」「卡管理」「优惠券」「刷卡」在沙盒里都没有对应模块，留待真实工程移植后再跑）
5. 最终 8 条 term（含 1 条 alias），11/11 PASS

**关键验证**：整个流程没有让用户手动改任何 YAML 文件——AI 在 staging 目录写草稿、对话里问一句 `y/e/s/q`、自己合并、自己删 staging。弱模型移植进内网后按同样流程操作即可。

## 八、已知局限 & 下一波改造预告（非本次交付）

1. **P0-3 对称性豁免关键字 `unidirectional`** 目前只在 `disambiguation` 文本里匹配，没有 `allowed_by: "..."` 之类结构化字段；若真实工程出现大量单向易混，建议升级为 YAML 结构化字段
2. **种子技术词豁免 allowlist 是全局的**，没有模块/业务域粒度；真实钱包工程如果"同一英文词在卡种模块是业务词、在系统层是技术词"的情况频繁出现，需要引入 scope 限定
3. **Step 2.5 反向指针正则是中文强耦合的**（"属 / 归 / 在 / →"），真实项目若用英文写 catalog 需要扩展正则集；目前暂不做，等内网跑一轮看真实比例
4. **Skill 0 Phase A 目前是一次一个模块**，真实钱包 30 模块需要 30 轮对话；未来可以加一个"auto 批量模式"，对高置信度（one_liner + entry_file 都能自动抽出的）模块一次性批处理
5. **glossary 的 `term_covered_by_catalog_typical_terms` 目前是 MAJOR WARN**，真实工程上线后若回补 catalog 跟不上 term 增长速度会噪声很大；可能需要从 WARN 升级为"建议自动回补 catalog"的修复提示
6. **本波没触及的下一块硬骨头**：**架构文档漂移**——`doc/architecture.md` 与真实代码 5 层结构长期不同步是常态；第四波可能需要一个 `check-architecture.ts` 来做"架构 × 代码 × catalog"三向对齐
