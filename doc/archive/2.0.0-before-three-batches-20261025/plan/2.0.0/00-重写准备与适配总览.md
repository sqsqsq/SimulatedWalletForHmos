## 3. 两个执行批次与六个检查单元

本轮是同一产品合同的横向替换，manifest、蓝图真源、Story、update、usage与测试按真实依赖共同交付。步骤描述可检查结果，批次确定连续实施和集中评审边界，均不按数量设限；保留已经展开的A–F，不为技能更新迁目录或重排工程设计。两个批次为：**批次一＝A–E离线适配与集成，批次二＝F真实验收及评审允许合并的非阻塞返修**。六个检查单元如下，细节见03：

1. A：保全、归档映射、测试标准、宿主装配预备；不改产品源，可先检查并提交维护材料。
2. B：启动真实merge，完成安装/DSH装配、来源冻结、蓝图知识与CU初建的闭环。
3. C：完成独立Story、先读正文的审查、送审与归档闭环。
4. D：完成update、CU内容修订、usage/stats及adapt保持，收敛全部替换路径。
5. E：全量迁移核对、离线组合验证、预算复核及第一个产品merge提交。
6. F：取得授权后用DSH验证送审、归档、update与CU到Plan，交效果结论。

B–D在一个集成工作区内连续实现、逐单元检查diff及定向回归，**E之前不提交一个已知错配的产品恢复树**。这是本需求已定的真实merge事务边界：A交回并提交维护材料；B–D作为同一产品merge内的检查点分别交回可还原diff，到E闭合并提交双亲对象。其余后续实施/返修步骤按完成→必要验证→增量交回并提交→前提成立继续，批末集中送审；不能把merge内的例外扩为日常不提交。不是保持新旧两套运行协议的兼容过渡，历史与实际累计继续保留。

编号是文档组织，不是审批轮次。获准实施后，各单元分别写交回，A–E按依赖连续推进，B/C/D不逐项停等；E集中评审与集中返修，获准的F完成后再评效果。只有核心冲突、实际阻塞、预算确认档位或缺授权暂停受影响工作，详见03“执行批次与评审等待点”。项目级指南须按01的现行同步清单落地，不能以历史归档代替有效正文更新。

批次不等于预算包。两个批次共用13已授权范围及原分母，F本身不产生机制增量，合并到后续批次的返修仍累计在原包；评审负责明确哪些问题阻塞后续、是否先复评，哪些可随下一批处理，执行者不自批跨批。旧目录沿用，步骤交回/批末汇总/评审的命名带批次和步骤，历史原件及问题轮次不随跨批迁移或重置。

本轮评审后的集中修订：01固定N/DSH的可提交装配输入并修正祖先核验命令，02将独立Story视觉裁定接到原生纯函数，12/13同步最小回归与原预算内分配；原评审及被审快照保留，来源和决定见11§9。执行者与维护者都优先正常路径、已证缺陷及直接合同失败，不在低频假设或测试能力扩张上追加大量工作；不增加步骤和逐单元审批。
