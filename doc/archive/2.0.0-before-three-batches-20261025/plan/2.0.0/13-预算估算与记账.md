## 3. 来源迁移、整版与实施包三本关系

不新增计量工具，只用源budget_report并在报告中明确适用段：

1. **历史**：保留O旧2.x账与B的1.9.9账和原批准；不把源历史invested6098再加进本轮实际投入。
2. **来源迁移参考**：O→B固定8188/5810只说明替换面。实际在原地保留O模块、直接改写B时，O→最终的diff不等于两段端点相加；不得将8188+5300标成实测新增。
3. **本版交付控制**：`release.baseline_ref=P`，endpoint比较P→当前最终树；已授权control_g=5300。首次merge相对P的新增包含复用O模块，不能免费。删除不冲掉G。
4. **总实施包累计**：`packages[].start_ref=T`（实际merge前目标、first-parent起点），已授权初始approved_g=13488，即来源切换参考8188+适配估算5300的计划包络。实际仍按T→后续first-parent的逐提交G累计；非线性差额交reviewer解释，不能硬凑估算。
5. **适配投入单列**：首次merge为M时，P→M的endpoint作首包适配投入；后续M→当前的first-parent invested追加。此算法在既有报告结果上列算，不造第二meter。首包内未提交反复修改无法从Git恢复投入量，明确记录粒度，不伪造。

为防迁移8188稀释新适配返工，主要适配分级为 `R适配 = [P→M endpoint.G + M→当前 first-parent invested.G] / 初始5300`，按相同100/125/150%动作复核；M未形成时用P→worktree暂估首包并明确不是完整投入。总包13488仍观察完整实施投入，不能替代适配R。初始5300的具名确认和复合起点写本Plan/交回，reviewer汇总两份既有报表，不伪造一个不在first-parent上的package.start_ref，也不新增台账schema或计量算法。

**DAG陷阱**：P/B是正常story merge的第二父链。当前budget_report.chain用 `rev-list --first-parent base..head -- extensions`，不验证base所属链；P→当前的endpoint可用，但该报表series/invested/peak会混入旧story历史。A/E将工具加只读适用性校验：非first-parent基线的endpoint保留，series/invested/churn/peak明确置null，另报 `applicability.first_parent=false` 及reason；build/check/control/markdown中依赖这些字段的守恒和峰值检查显式列未执行，不把null当0。合法T包单独计算，不被全局P不适用连带清空；若无效基线被当package.start_ref请求，报前置不成立。补对应DAG测试，不能静默给误导数字。T在first-parent上才可作本包累计起点。
