## 1. 目标与已确认决定

本版使业务评审者单独阅读 Story 就能理解、确认需求，使开发负责人能用蓝图核查整体设计，使消费模型依据同一有效设计完成 CU 的 Spec/Plan。维护者能追溯反合来源、保全旧成果、辨别能力保持与未验证范围。

用户已确认：

- 原2.0.5讨论与准备结果承接为新2.0.0；旧spec/plan完整迁入doc/archive/legacy-2.x。
- 以已交付的 Framework 3.1 蓝图能力作为设计输入，实际人读文件是 `component-blueprint.review.md`，无需另造名为 `blueprint.md` 的文件。
- 保留独立 Story：蓝图负责完整需求级设计；Story 负责面向产品、开发负责人和测试人员的完整业务叙事与交付。Story 的组织权覆盖全文，不收窄为向蓝图固定章节提供片段。
- 采用送审方案 A：**Story 是完整业务送审正文，蓝图人读稿是设计参考**。业务评审者无需阅读代码、翻仓库或拼读两份文档，便能确认业务范围、流程、异常和验收条件；开发负责人可按需核查蓝图中的契约、职责及 CU 划分。
- 同一设计事实只有一个有效真源。Story 可以按读者理解顺序重述、组织图文和深化表达；发现业务遗漏、矛盾或决定变化时，回到设计责任位置修订并同步。业务确认与 Framework 设计准入分别成立，不能互相代替。

- 采用1.9.9更新后的预算政策与工具，保留历史投入记录；本规格不批准新的增长额度。
- **Extension 的验证使用 DSH，沿用1.9.9方案。** 不把 Codex/OpenCode 全链实跑追加为本版前置条件。

### 2.1 必须保持的1.9.9能力

以下保持的是使用结果，具体接口由Plan按新版合同设计；不要求搬回已退出的旧机制。

| 能力 | 本轮须保持的可观察结果 |
|---|---|
| 来源取得与澄清 | 系统单和本地材料均可进入；目录下同名原件可区分，材料换版保留原件和采用关系；有决定权的人工答复与建议分开，待定事项保持待定 |
| 知识链 | 项目事实、规约和设计模式在受影响决定前送达；适用判断落实到设计对象、义务及角色，传到CU的Spec/Plan；实际不适用有依据，名称回显不算应用 |
| 完整Story | 读者沿业务理解流程、页面交互、条件、异常、责任、结果和验收；技术参考不替代正文，图文之间的关系和来源可核实，不固定沿用旧章节数 |
| 图与资源 | 保留真实来源图片、合法路径与资源交付；正式图使用Mermaid，同一图可选增强阅读SVG，增强不改变业务事实；已制作的增强稿有独立源码审查和有效绑定，零SVG可成立，不强制每图增强或追认视觉审查 |
| 独立审查 | 必审输入含材料、有效人工决定及当前对象；实际独立执行体审查语义并留下原报告，WARN/FAIL有处置。无独立能力明确未审；不能借此把本版DSH独审验收判为通过 |
| 送审与归档 | 正式内容、资源和回执可对应；上传后读回一致才登记归档。远端成功、本地登记失败能只补登记，不重复上传；阶段检查与正式交付保持有效正式图形态，增强SVG继续作为本地阅读能力 |
| update与恢复 | 先核变化来源的决定权，再处理内容；保留原件、人工区和有效决定，区分表达调整与设计变化；范围待决时先做独立工作并明确剩余范围，恢复不丢结果、不重复计入 |
| usage与stats | 真实取材/工作开始前记录开始，成功完成后记完成，多轮累计且重复收尾不重复增加；未知开始不补造耗时。stats保留仅依赖usage记录和Git、无业务目录也可生成、报告不写入工程的能力；多CU不把共同工作重复累计 |
| adapt与所有权 | 按目标仓所有权更新机制、知识及对接层，知识由目标事实形成并独审；升级定向处理真正变化；合法既有usage不被重置，坏记录在写机制前明确失败；不扫描、迁移旧在途需求，不恢复已退出格式兼容 |
| 测试与运行装置 | DSH运行身份、事件、独审原件和结束状态可追溯，隔离工作区不被维护答案污染；实际成功片段及失败/截断证据保留，测试装置问题与产品问题区分 |

原1.10.0评价能力建设已结项，其标准、方法与证据复用，不作为未完成产品重新实现。原发布明确排除的纯故障注入和无真实反馈的异常推演，不因承接遗留扩大成必做矩阵。性能与SVG等效果项须有实际观察、结论和未覆盖边界；若结果仍不足，应交用户裁定，不能沿用1.9.9的接受决定自动判新版本通过。

## 5. 主要场景与异常结果

| 场景与前置 | 应得到的结果 |
|---|---|
| 系统单或本地材料启动，含明确决定与待定问题 | 模型取得真实材料与目标仓事实，厘清权限与范围；有效设计完整承接已知事实和未决，形成可供CU使用的共同设计 |
| 根据有效设计生成并送审Story | 产品和测试只读Story即可评审业务；开发负责人可参考蓝图核设计。材料、正文、图表、附录和验收互相一致，独审原件及处置对应当前稿 |
| 成文发现设计遗漏或前提矛盾 | 由设计责任位置修正真源，刷新受影响视图和CU信息；未解决部分明确阻碍什么，不能在Story中私自补决定或把有缺口的稿签为完整可施工 |
| 仅调整叙事顺序、措辞或同图阅读表达 | 保持有效业务决定、来源与人工确认；依变化性质核所需审查，避免把纯表达改进变成一次新的业务批准 |
| 送审意见或材料换版触发update | 核提出者权限与变化范围，保护原件和人工决定；设计、Story、图、审查和受影响CU一致更新。待定范围与已完成独立部分分别说明，旧结论不冒充新稿证据 |
| 归档上传成功但登记失败，或重复执行收尾 | 明确实际成功位置，从未完成处恢复；不重复上传、不丢回执、不重复增加使用时长；读回不一致时不登记成功 |
