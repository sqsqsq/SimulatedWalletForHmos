## 1. 可行性结论与旧方案缺口

**已有接口支持下面的责任迁移，不需要改产品或新增测试平台；目前没有证据证明180秒不可达，也没有实测证明本方案已经能达标。** 上轮的“缓存接线＋三个局部例组”不足以论证总目标，本页补齐全部工作量、现成接口、保留链、执行依赖及失败后的定位责任。以下预算是实施需要满足的约束，不是把未实现收益写成预测。

旧方案的主要漏项：只关注少数最慢类；将已存在的shared_state再次当成可新增收益；未核failure真实子环境；未核同名测试的责任扩大；未计第二重建的调度和证据保存。修这些问题不能靠测试数量减少、缓存命中率或一次暖跑作结论。

## 3. 时间预算和固定依赖

实际首次装配两轮约48秒，其中复制约9秒、Framework处理约34秒（原生UPDATE约32.5秒）、扩展安装约4.6秒。第二轮入口至装配结束48.018秒，清理3.352秒，完整830.467秒。按这个观察对象，留给并行窗口只有128.63秒；不是每条通道都能再用180秒。

本方案使用以下工作预算：

| 段 | 控制预算 | 事实/条件 |
|---|---:|---|
| 入口、身份取得、首次真实装配 | 60秒 | 48秒实测基础上留余量；计时前不预造 |
| 并行检查窗口 | 110秒 | full、failure、第二重建加轻检查，三者取最大值 |
| 全部消费者结束后的记录与清理 | 10秒 | 已观测清理约3.35秒；日志持久保存也计入 |
| 合计 | 180秒 | 子预算用于定位，最终只按完整总墙时及功能判定 |

固定结构为：

```text
verify计时开始 → 首次装配/身份核对
                  ├─ full（不含第二重建）
                  ├─ failure（同一安装件，正确启用既有TS缓存）
                  └─ 第二次独立重建（触发时）→ runtime → compile → config → node语法
                → 全部结束 → 原始证据持久保存/清理 → 总计时结束
```

仍用现有scenario/run_lane/ThreadPoolExecutor，不新增调度器。总worker预算公式保持；32对应24/7/1。`assembly_steps()`显式pytest `-n 1`，放第三通道首项，**full始终deselect第二类**；无`--assembly`则第三通道与现在相同。预算小于3时仍沿现有顺序执行策略，不能把32核预算外推为任意机器达标承诺。

第二类继续自建第二个空目录、固定树/补丁/原生UPDATE/开发源均真实执行，绝不借首次模板。原生UPDATE继续移除NODE_OPTIONS。第一次verify拥有的模板仅在全部读者结束后清理；第二类拥有自己的目录。第二boundary原件及其原生run-log在teardown前保存到本轮日志下独立子目录，不能覆盖首份boundary；此时生成的新证据才由本轮清理管理。assembly.log/timing/classes沿已有run命名输出，不新增证据格式。

轻检查第二轮合计约31秒，因此在110秒窗口中，第二重建需要控制到约79秒以内。旧99.2/203.3秒是竞争下整类耗时，不能当作独占下限，也不能保证换通道后就能到79秒。该调整保证第二重建从窗口起点开始、不再排在full类队列后面；并发收益仍须实测。

**工作量缺口必须正视：** 第一轮24 worker的11117.1累计秒即使均匀分摊也约463秒。要把full限制在110秒，忽略收集和尾部开销时，累计占用也须不高于2640秒；约76%的工作量削减是这一旧观察尺度下的必要条件，不是承诺的收益。第二重建移出full只是改归属，不算整轮工作消失。两轮负载不同，不能把该比例当固定实现配额。由此排除“补一处缓存、保留其余流程原样即可达标”的说法。

静态调查没有可靠的逐族改后耗时，因此不编造“每组节省80%”或总时长预测。可实施性来自§4已核真实接口；性能可行性必须由§5的有限实施验证建立。没有满足条件前，状态是**方案可实施、达标待证**。
