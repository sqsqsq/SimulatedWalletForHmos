# 1.x 效果可达性与存量退场审计

2026-11-10，维护设计者（Claude Opus）。回答用户两问：新 Framework（main 900c508d）加 Extension 能否达到 1.x 的效果；2.x 多轮修改留下的补丁与废弃机制是否已识别清楚。只读核查，没有改产品代码；证据在 `output/evidence/2.0.4-retirement-audit/20261110/`（脚本、补丁信号、历史退出项残留、与 1.9.9 的逐文件对照）。

- **能达到，主要差距不依赖 Framework**：
  - 退步最多的是知识与验收层；根因是我们没有让蓝图在设计期写原生验收，而 Framework 原生方法本来就要求写。2.0.3 两份蓝图的验收条目都是 0。
  - 依赖 Framework 的只剩两处：当前切片不收条件未决；蓝图成本高。
  - 写操作语义 1.x 本来也没达到，属于“到金样”的差距。
- **上一版 2.0.4 方案把补层放错了位置**：R2、R3 放在 Story 成文，会多出第二份真源；R4、R6 仍是规则文字。本次已改写（§3）。
- **退场没有识别充分**：
  - 2.0.3 承诺净减 460 行，实际只净减 69 行；
  - 历史退出表大体兑现，仍有多处旧格式专用识别分支；
  - 新版原生已经能做的质询结果登记，现在仍由模型手写；
  - 2.x 新增的 update 逻辑（+355 行）从未实跑。
  - 改写后的 2.0.4 新增退场需求 R10，并以整版净增不超过 0 作偏差信号。

### 1.2 为什么说承担位置在蓝图

Framework 原生方法要求蓝图在设计期写出：

- **typed 内容**：被 CU 引用的目标要写 `acceptance`（ID、优先级、步骤与预期、分层）、`contracts`、`use_cases`（`app-component-blueprint-workflow.md` 第 66 行）；
- **失败与中断**：落在 `acceptance.boundaries`、`flow.failure_recovery` 与用例分支（第 83 行）；
- **错误与幂等**：落在 errors / idempotency（第 84 行）；
- **质量**：兼容、安全隐私、UX、打点、性能各有结论，精确阈值写在 acceptance（第 85、145 行）；
- **评审投影**：要有“验收”“失败与恢复”小节，失败与恢复用速查短表写“发生什么、用户看到什么、数据是否保存、如何继续”（第 238、248 行）。材料答不了的单元格明确写未定。

这些要求在旧版 ff111909 已经存在，验收分层也以蓝图提供的等价投影为合法来源（`docs/concepts/acceptance-layering.md` §2）。测试夹具蓝图就带完整验收，原生判 Spec 由蓝图依据复用（`test/tests/test_blueprint_case_closure.py` 第 246 行起）。

但 Extension 送给蓝图作者的指引（`phases/design.md`、`hooks/blueprint/author.md`、`reference/knowledge/protocol.md`）从来没有提过设计期验收。2.0.3 预跑的两份蓝图里，`id: AC` 都是 0 处，实体 `must` 分别有 11 处和 10 处。

### 1.3 结论

| 问题 | 结论 |
|---|---|
| 能否达到 1.x | 能。退步项都由 Extension（指引错层、知识样板）承担，原生字段与方法已经具备 |
| 方案是否已明确 | 上一版没有：R2、R3 放在 Story 成文，错层。本次改到蓝图（§3） |
| Framework 依赖 | 两处：<br>• 当前切片不收条件未决：car 修样板后可能不再触发；真正的未决按切片处理，仍问 Framework 作者；<br>• 蓝图成本：1.9.9 两例全链约 2 小时 45 分（含 Spec 与 Plan），2.0.3 只到 Story 约 1 小时 50 分，把验收写进蓝图还会更长 |
