# 2.0.4 Extension 集中优化方案

2026-11-10，维护设计者 Codex。本轮按203010评审R1–R3原位集中修订，四批职责和成立设计保持。此文件是当前有效实施设计，目录名“优化候选”仅保留历史位置；原六批稿退出施工入口、原评审原样保留。状态：设计安排已明确，产品未实施，增量预算和模型CLI均未授权；FW-F2是已复现且尚未解除的外部接续依赖，不能宣告整版效果就绪。

开工依据：[有效Spec](../../../../spec/2.0.4/2026-11-10-Framework同步与Story效果收敛.md)、[标准变更与对象哈希](../../../../spec/2.0.4/评价标准变更.md)及本方案。本轮先将标准正本更新为extension-acceptance@29，再按其核本方案；A/B/C开工前必须核该组身份，不留给D批或执行者选择。实施仍须授权，标准生效不等于产品通过。

## 1. 目标、已定边界与交付

用户目标是让 Extension 在既有业务工程和测试业务上，恢复 1.x 已证明的有效能力，达到 2.x 金样表达的准确、完整、可读和可施工效果。优化对象是 Extension 与 Framework 的协作，不是补好 demo 或提前交给模型金样答案。

已定：
- 测试业务原件、条件答复和 demo 业务源码保持；模型仍须自行发现、澄清、设计并传递。两仓当前四个主要业务目录 tree 相同，工程缺项本来就是正常输入。
- 未来正式测试：auto 到 Spec、car 到 Plan；不跑 update、Coding、设备或真实云端联调。本轮不启动测试模型。
- 金样是目标、1.x 是已测参照，实际答复按运行记录认定。金样额外选型不是隐藏的必须答案。不能拿历史错误、预备但未发送的人答或维护者细化冒充实际依据。
- 原生承载和职责优先；Extension 不新增 runner、审查层、状态机、通用兼容层、评测平台或恢复能力。
- 不承诺固定篇幅、净减、审查次数或提速百分比。关键语义逐项成立，成本与效果分别结论。

交付为四批方案及两份跨批依据：
1. [需求及标准修订对照](01-需求及标准修订对照.md)：本轮采纳记录与定位；有效目标和标准分别只维护在上述正本，不以本页另立验收规则。
2. [Framework 依赖与核查](02-Framework依赖与核查.md)：区分已确认接口、纯函数发现及尚未验证的公开组合。
3. [A 原生接续与测试装置](01-批次-原生接续/00-批次方案.md)。
4. [B 完整设计与知识承接](02-批次-完整设计与知识承接/00-批次方案.md)。
5. [C 成文、独审与效率](03-批次-成文审查与效率/00-批次方案.md)。

正常链：
原件/有效人答/真实工程 → 原生蓝图设计对象、来源、验收和必要事件 → 原生独立质询 → Story 完整叙事与 Review 真实决定 → Story 独立首读和核源 → 登记/交付 → 已授权 CU 的原生输入与 Spec/Plan → 对应阶段 verifier/receipt/observer。

共同设计缺口由蓝图作者处理；工程没有现成实现时先调查和设计本期应承担的实现，不能直接向业务方索取工程方案。真外部协议缺失才按实际影响澄清或阻断。材料中的普通待定可忠实保留在 Story；是否阻施工按当前 CU 真实依赖决定，不能通过改终点或移标签放行。
