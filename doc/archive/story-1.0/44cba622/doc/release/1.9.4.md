# Story Extension 1.9.4 发布说明

> 2026-09-21 收口，机制版本即本发布提交（C5 之上无机制改动）。上一版见 [1.9.3](1.9.3.md)，本版在它之上做增量。
> 两 Case 双检查点正式实跑一次（初次 + 同会话更新），四份成品的三轴分由用户审视后给出，本文不代填。

## 本版新增与优化

### 1. `/story update`：已有产物跟着新依据走，取代 `/story review`

需求已有 Spec / Story / Review / Plan 之后，上游材料改版、评审意见回来、人有新决定或有人直接改了文档，跑 `/story update <编号>`。

- **入口与 init 同构**：AR 单先从需求系统取回上游正文（落进本单 `inbox/`）；然后报告上游哪几份变了、没变、取不到，本地已有什么，**在材料关卡问一次要不要补料**，人答了才定最终的材料变化。本地单没有上游，直接问补料。关卡、选项、人签与轮次登记全是 init 第一级那一套，记在当前轮，不开新轮、不重走范围。
- **只看人和上游会动的八项**判「有没有变」：`RR/prd.md`、`SR/design.md`、`AR/design.md`、`inbox/`（按材料事实）、`AR/story.md`、`AR/review.md`、`spec/spec.md`、`plan/plan.md`。决策登记、写作设计、验收与强契约是据它们写出来的，随之而变，不进判定。
- **四种去向**：真的没变 → 报「未检测到变化」退出，什么都不建；上一轮没做完 → 接着做；没有可比的基准或来源读不到 → 如实说，不冒充无变化；有变化 → 留一份执行前的现场，交模型读原文判断。
- **模型做判断，脚本管文件**：变化意味着什么、牵动哪些业务关系、哪些不变、哪些要问人，由模型按方法页的六个动作做；增量修订已有产物，不重做全量，不生成新阶段、不改代码。人的新决定用 `decide --update` 记原话。
- **可恢复**：每轮留 `before/` 现场与 `update-notes.md`；`restore` 先保住之后的改动再还原，两边都留；`close` 留下一轮的比较正文。
- **改动过的阶段按新的审查对象审一次，并真正闭环**：重验后派 verifier，报告写好后**完整跑一次** `harness-runner.ts --phase <阶段>` 采纳它（`--sync-closure` 对已闭环阶段不改写）；`close` 收口前逐阶段检查，报告写了、判 PASS 却仍标沿用历史的，拒绝收口并指明命令。PASS 时的建议不改材料、不再派审。
- **同一来源的新版本**：导入前把 `inbox/` 里被取代的旧原件移进 `.backup/`；`inputs` 会列出同类的已归类原件作提示。
- **人写过意见的议题**：正文的决策点换了或议题被删，渲染会停下来，不把旧表态移植到新问题上；只是措辞变了，用 `decide --update <议题 id>` 记下人同意沿用的原话。

`/story review`、`adapters/review.js`、`rules/review_reflow.md` 与处置台账退场；目标工程的对接层要补 `fetch`（合同见 `skills/story/scripts/README.md`），没补时 update 报错停下，不会退回用 `review` 覆盖评审记录。

### 2. Story 成文：先想读者怎么读，再动笔

成文作业书重排为「读者口径 → 成品的阅读组织 → 表达选择 → 动笔前设计 → 写一章 → 回看 → 登记」。业务流程章改为**总览给主线与主要分流入口，复杂分支在对应小节完整展开并接回主线**，审查按总览与局部加起来判；一处要几种形式就各写一行（图讲关系、表讲属性、文字讲理由）。上游图「可以改画」与「原样搬」两条并存指令收成一条：可原样承接，也可改画，改画不能丢参与者与失败责任。评审议题的决策点写「哪个业务对象的哪件事」，用业务名。

### 3. 已定要指得出是谁定的

写 `settled` 之前先问结论是谁给的：要人表态才成立的事，指得出那个人在哪说过；材料明写的写明出处。计划与转述（「已安排」「开发侧确认」）不是表态。审查侧逐条并列 `decider`、`review_mode` 与澄清原文，拿不出人的表态就是伪定案。结论就是评审人自己给的，不再 confirm 同一方。

## 修复

- 规约命中边界：`DLV-02` 定义「对外开放」（交给其他部件、应用或第三方使用的页面入口与 API），`COMPAT-02` 的「改动」包含纯新增——两轮判断摇摆的根源在措辞。
- 会议审查不再要求逐话题一行，改为每个话题的去向与依据可追溯。
- 材料索取：不取需求方提到的材料，理由只能是本轮范围不依赖它；上游自己说「另行提供」不构成不取的理由。
- 成文报错指向的节名与实际作业书对齐；补结构起点按小节归堆，不再把后一节的表印到前一节下面。
- update 的输入阶段按位置认「这一次的回答」，不按秒级时刻（同一秒里的上一次回答曾被当成这一次）。
- 取材命令带 `--project-root`，回执不会落到别的工程；与本地逐字相同的上游正文不落盘，免得每次都报新料。
- 镜像不复制阶段报告、导入备份与重验过程件（64 位哈希文件名套进深目录会超 Windows 路径上限）。

## 退出项

`/story review` 全链（命令、`review.js`、`review_reflow.md`、处置台账、四个宿主桥接里的条目、测试装置的 `story-review` 假阶段）；C1 的取材暂存区 `AR/story-src/incoming/` 及其复制与清空；判定集合里的六项中间真源；方法页里对已闭环阶段无效的 `--sync-closure` 确认步骤。

## 本版验证结果

正式实跑 `story-suite-20260921-1239`（C4 之后起跑），两 Case 各两段、同一会话续行，四份检查点快照与四个回流目录：`AR90006`、`AR90006-update`、`ISSUE-206`、`ISSUE-206-update`。

| | auto-topup（到 spec） | car-key-sharing（到 plan） |
|---|---|---|
| 第一段 | 87.6 分钟 | 83.1 分钟 |
| 第二段（update） | 43.7 分钟 | 24.1 分钟 |
| 第二段刺激 | 产品需求改版，单日上限 200 → 300 | 评审意见：撤销宽限 36 小时、提示语「正在收回」 |

- **更新成立**：两 Case 第二段起手都在材料关卡问了一次补料；auto 的 300 在 spec、验收、story 全部同步、零残留，并自己认出两处冲突（新版推翻澄清会口径；新版旧句与会上的人工裁决相反，保留人的裁决）；car 用评审原话定下 36 小时，同步到 spec、验收、story 与 Plan 的常量和用例，24/48 只留在「原来两份材料打架」的说明里。两 Case 都没重问已定的事，人没定的都保持 open。
- **审查闭环当时没有成立**：四段里三段报告写了、判 PASS，阶段仍标沿用历史——framework 不改写已闭环的 summary，`--sync-closure` 不起作用，而模型据它报了完成。C5 离线实验证实完整跑一次 harness 即采纳，方法页与 `close` 守卫已按此改，**未再真跑验证**。
- auto 第二段因把 PASS 时的建议当返修，审了 4 次（全 PASS）；本版已写明建议不触发再审。
- 两 Case 终态 `gate_failed` 是收尾门禁的 node 进程因机器内存不足没能启动（`0xC0000142`），重跑同一检查均通过。

三轴建议分（产物结果 / 性能 / 知识应用）：待用户审视四份成品后填写。

## 未实证与已知限制

- 无变化快速退出、回写需求系统前的展示与确认、真实 `restore`：离线用例覆盖，真跑未走到。
- update 后「完整跑一次 harness 采纳报告」只在 spec 上离线实验过，plan 同一收口器未单跑。
- 交上游：revalidate 的「已闭环」与 `--sync-closure` 对已闭环阶段的 PASS 输出会让主 agent 以为报告已采纳，建议在输出里点明 `completed_with_prior_review`。
- 测试装置：conclude 之后的收尾门禁在内存紧张时起不来，记为 1.9.5 装置维护。

## 规模

收口实测 12349 有效行（Python 2873 / MJS 3444 / hooks 3394 / prompts 1862 / data 776），1.9.3 收口为 11536。本版新增一整条 update 能力（方法页、文件支持、路由、测试装置），退场旧 review 链。累计新增约 728 行对开工额度 674，约 108%；超出的主要是 update 路由要同时处理收口态与 reopen 之后两种状态、以及 T2 暴露后补的守卫，逐笔记在预算台账。
