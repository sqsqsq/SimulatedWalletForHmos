# Story Extension 1.9.2 发布说明

> 2026-09-16 收口。上一版见 [1.9.1](1.9.1.md)，本版在它之上做增量。收口时两 Case 三轴分未达 90，未闭的机制问题移交 1.9.3（见文末）。

## 本版新增与优化

### 1. 写作设计是一份骨架，草稿照它铺好

写作设计不再是每章一段说明加一段结构选择：作者写阅读主线，再为每章写骨架——正文将要有的小节标题、
每节要回答什么、依据在哪、用哪种形式。起手命令把骨架铺进还没动过的章草稿，章提交与全篇检查
核骨架里的小节、表与图在正文里都有；正文可以多写，要删骨架里的一节就先删骨架那一行。

形式用一行 `形式：<类型>` 声明，类型是表格、有序列表、无序列表、叙述或某一种图；模板不预定表的列，
列与图的内容留给成文；四级小节按它的父节定位，别处同名小节顶替不了。作者写章时改掉已用于写章的安排，
在 `template-adjustments.md` 记原安排、实际调整、原因与依据；没有调整不建文件。旧形态的写作设计会被指出来，按骨架重写。

### 2. 十章齐后按回看清单逐条处置

十章写完，起手命令给出一张回看清单：需求分析里还要核实的疑点、未决与已定的决策、骨架里留着的待核问题、
正文里每张图所在的位置，有会议时还有会议结果与它引的原话。作者先拿有效的原材料与当前决定核关键关系，再对清单每一条问「这句话材料里有吗、材料给的靠得住吗」，有问题回它的真源改；
独立审查拿同一张清单核每一条的去向。

### 3. 评审议题的选项写后果，依据写撞点

「可选的做法」每一项写成「做法——选它会怎样」，缺后果的会被指出来；写不出后果差别的改成请人复核结论。
议题的依据要说清是在哪一章、哪份材料的哪一处撞出来的。verifier 之后发现真实缺陷照改，产物没变才复用结论；不为保住已有报告回滚正确修改。

### 4. 规约声明强制力与验法，各阶段照它执行

规约表里的强制力、验证（执行体）与探针三列由各阶段读取，知识写什么，门禁就照什么执行：

| 阶段 | 现在 |
|---|---|
| 载入知识 | 强制力、执行体、探针写法与协议版本不合的，一次全部列出并说明改哪边；模式文件缺上篇或下篇也会指出 |
| spec | 判断骨架每条带上强制力、要求、命中条件与验法；§10 多出「强制力」「验法」两列。命中但这一轮不做可以登记豁免：红线不许，基线要写补偿，由评审人表态。项目事实按面登记用途，未确认的面要写核实时看的位置 |
| plan | 每处落点的 `verify` 要与规约声明的执行体相符，要实机证据的不能只标 `review`；不是规约要求的业务规则写进实体说明或设计章，不借编号挂。契约里用 `- { … }` 流式写法的字段会被指出（1.9.3 改为与 framework 同一解析器后不再指出） |
| coding | 规约自带的探针对形态匹配的每处落点自动跑：标了「阻断：」的形态不符按强制力处理（红线拦下），其余只记证据缺口；只写在注释里的实体不算；注释里写了规约编号的报到行号 |
| review | 复核表一处落点一行、按列读结论；红线的落点「未落实」会拦下，基线「未落实」要写依据 |

### 5. 会议转写进需求输入

需求澄清会议的语音转写 docx 放进收件箱、归类为 `MEETING`。**内容由模型理解，脚本只做确定的事**：转换、按版本留原件、应用纠偏差异、核引用与结构。

| 环节 | 现在 |
|---|---|
| 导入 | 一个源版本一个目录（`AR/story-src/meetings/<主名>/<sha8>/`），存原件、`raw.md` 与图片；同名文件换了内容存成新版本；转换件丢了按原件重建，重建不出原样就明说 |
| 读会 | 按 `phases/meeting-read.md`：模型只交字面纠偏差异（`corrections.json`，脚本应用成 `evidence.md`，问题一次报全）；再写 `meeting-notes.json`，一个话题一条：归属、原话行范围、判断，要问人的写问题与选项并给推荐。引用一律写 `raw.md` 的行范围 |
| 自检 | 结构与引用：话题编号唯一、原话行范围指得到、遗留有原话、选项键不重复。判断本身脚本不读 |
| 人裁决 | 与第一级材料关卡同一轮，不新增停等点：`status` 机械枚举全部话题，要问的逐条 `decide --gate meeting`，记人选的键与原话 |
| 当前结果 | **模型**按原话与人的裁决写 `AR/story-src/doc-refresh.md`（会议输入绑定行 + 每话题一节 + 原话引用），是下游唯一入口。脚本只核四件：文件在、声明的输入是当前版、每个话题有去向、引用指得到真实行 |
| 下游 | 需求分析 ⑥ 按话题登记，未决进回看清单；提取稿、写作设计、成文依据行都可引它；独立审查逐话题核 |
| 收口之后才到的会议 | 先 `reopen`，一场会一轮 |

## 修复

| 问题 | 现在 |
|---|---|
| 列表项里一句带冒号的话被读成键值，渲染出 `[object Object]` | 按一整句读，原样渲染 |
| 同一章里两个同名小节、只有标题没有正文的小节会进入交付件 | 章提交与全篇检查点名，给出合并、改名或补正文的出口 |
| 还没收口就登记成文时，计算下一步失败会盖掉「还没收口」这句提示 | 先说还没收口，下一步算不出来的原因附在后面 |
| 审查复核表里写「未落实」会被读成「落实」；同一条规约挂在两处时只认最后一行 | 结论按「结论」列的原值读；每处落点各认一行 |
| `* * *` 分隔线被当成无序列表项 | 按 Markdown 分隔线排除 |
| 会议名带空格时标题与引用认不出；围栏里的示例标题被当成真去向；带语言标记的行被当成围栏关闭 | 标题按已知版本与话题认；围栏关闭要同字符、不短于开启、之后只有空白 |
| 六处「引文连续 12 字以上」把长度当依据 | 给得出回查位置或能检索到的原文即可，不按长度计 |

## 移交 1.9.3 的已知缺口

扩展 post_check 一轮只暴露一层；扩展 YAML 读法比 framework 严、`resource_keys` 读法与 framework 不一致；未决在读会理解或决策登记时被写成已定而审查未拦；实现选型进评审待确认区、choice 缺建议；需求方明说手上有的材料不索取就定范围；规约适用判断轮间摇摆（作者判断时看不到处置列）；`acceptance.yaml` 与 spec §8 条目集漂移（归 framework）；`measure_run.py` 管道误计。方案见 `test/story/spec/2026-09-16-Extension机制级替换增强与退场/`。
