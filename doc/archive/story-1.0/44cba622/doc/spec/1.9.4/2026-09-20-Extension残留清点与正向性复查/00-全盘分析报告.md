## 2. 候选残留的处置原则

| 候选 | 需要证实的实际问题 | 本版处置 |
|---|---|---|
| P1 多处读取章节合同 | 路径与失败语义是否分歧；多次读取同一文件本身不是多个事实真源 | 本版触及的读取若需合并，复用已有 context/合同读取能力；不为“六处”单独建通用 loader |
| P2 Markdown 定位并存 | 输入范围是否相同、围栏/表格等合法输入是否判错 | 改动触及处复用 core/story/document.mjs；保留真正不同的窄输入责任并说明，不一律按函数名合并 |
| P3 pending_mark 回退字面 | 合同不可读时是否被错误当成默认成功 | 局部改为与合同读取失败一致的显式错误，避免两处默认值 |
| P4 旧图片形状报错 | 是失效过渡逻辑还是仍有效输入验证 | 删除旧专用分支时由当前清单结构检查承担非法输入报错，不把坏输入变成“没有图片” |
| P5 手抄枚举 | 作者是否取得当前值；新增合法值是否遗漏 | 由当前权威数据生成需要的清单，复用现有作者任务包；指引正文只保留含义，不新增第二份字面枚举 |
| P6 按行禁评审表单腔 | 是否真影响本版合法表达，而非仅形式不同 | 确有合法表达误拒时退对应形态限制，由既有读者审查接语义；保留人工区与投影一致性的确定性保护 |

上述候选并非全部必改。实施者每项交回“实际消费者、具体问题、保留/替换/删除及原因”，设计者从 diff 复核。没有确认真实问题时保留，不为净减行数裁功能。

## 3. 本版必须退出的旧职责

统一 update 交付时退出独立 /story review 路由、story.js review 命令及其专用实现、review_reflow.md 流程、只改 Spec 不刷新 Story 的指令、活跃消费者对 review-disposition.json 的依赖、测试装置 story-review 专用终点。

意见读取、人工区保护、历史快照、归档/恢复能力由 update 与已有归档链承接。历史磁盘文件保持原件，首次更新按显式输入读取一次并保留来源，后续不再持续双写旧台账。

需要同步的生产者/消费者包括 Skill、四宿主跳板、阶段提示、plan 作者输入、overlay、对接合同、适配说明、测试与发布指南。退出检查按职责和消费者核对，不因 review.md 或框架 review 阶段仍出现就判失败。

## 4. 保护项

本任务起始已有两份设计模式正文、EVOLUTION、manifest 的在途修改，均不覆盖。当前 manifest 改到 1.9.3 是发布遗漏修复，1.9.4 发布时再统一更新。Framework、真实目标知识、目标自有 adapters 保持各自所有权；安装器不能用 Demo 替身覆盖业务实现。
