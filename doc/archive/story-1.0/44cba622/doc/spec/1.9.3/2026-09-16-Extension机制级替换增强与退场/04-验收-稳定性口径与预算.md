## 2. 真实 CLI 验收（用户按 TEST 启动）

**完成判据（用户 2026-09-16 定）**：以用户对两 Case 产物的人工审视结果为准，三轴打分只作辅助。人工审视按 §2 的比较单元逐类看：原义是否保持、未决是否仍是未决、关系是否完整、评审载体是否只装该人定的事；过程指标（下表）看方向。打分照 TEST §10 记录，但不以 90 线判本需求完成与否。

**步骤 4 检查点**（步骤 3 末提交的机制版本）：两 Case 各跑一次，到各自现有 `end_phase`；只统计过程指标与「verifier 报告是否引用了并列证据」，不评三轴分、不做两次比较；记录写 `test/story/plan/2026-09-16-Extension机制级替换增强与退场/步骤4检查点-<日期>.md`（交回与评审同目录），作为步骤 8 的对照。

**步骤 4 检查点结果（2026-09-18）**：两 suite 四次运行全部自然闭环；带 FAIL 门禁轮次四次全部低于第二轮基线，`lifecycle_hook_post_check_extension` car 从 8 降到 2–3；verifier 引用了判断表与图并排，会议四栏未被写进结论（责任在 overlay 输出契约，步骤 5 修）；verifier 耗时上升的主因是 FAIL 归零后 harness 与 verifier 被反复重跑。记录见 design 目录两份检查点与评审。

**步骤 8 运行安排**：两 Case（现有 auto-topup 与 car-key-sharing）各跑两次，同机制版本、同材料、同 CLI 配置、同结束阶段；宿主回复沿用各 Case 的 interaction-script 立场。不向被测模型注入历史产物、金样或答案。

**稳定性比较单元**：按类型从每次运行自己的产物派生，两次运行同类集合两两比。不从 `逐项历史对比` 抄内容单元。

| 类型 | 派生来源（脚本枚举） | 比什么（人判） |
|---|---|---|
| 规约适用判断 | `knowledge-use.yaml` 全部 `constraints[]` 的 `applicable` 与 `reason` | T/F 是否一致；reason 引用的事实是否属于命中条件；不一致时哪次对 |
| 决策集合 | `decisions.json` 议题（title、review_mode、settled/open、decider） | 同一业务决定是否两次都登记、状态是否一致；实现选型有没有进待确认区 |
| 未决承接 | 脚本只枚举：open 议题、`doc-refresh.md` 未决话题、以及正文里对它们的显式引用（议题 id、话题 id、图源标记） | 哪些行为依赖这些未决、是否被写成已定，由人或审查按原话判；脚本不派生「依赖行」 |
| 图关系 | 源图（`diagramsOf`）与承接图（图源标记） | 参与者、往返、分支、结果所有者、失败责任是否保持 |
| 章内独有解释 | 骨架每节的问题 → 正文对应节 | 主要机制是否在正文而非只在附录；两次是否落在同类位置 |
| 会议话题去向 | notes 话题 × gate 选项 × doc-refresh 段 | 人选与结果一致；未选建议没有被采用 |

两次一致不推成功概率；同时报最差一轮与关键缺陷。合法差异（分节、措辞、图形、因人工回复不同产生的范围差）单列，不计不稳定。

**步骤 4 检查点的最小规则**：过程指标（harness 轮次、FAIL 轮次、编辑次数）相对第二轮实跑未下降 → 先回看 R1/R2/R3 的实际生效（门禁日志里是否仍逐层暴露、契约是否仍被拒收）修好再进步骤 5；verifier 报告没有引用并列证据 → 回看 E3 装配是否进了 ai-prompt，修好再进步骤 5；两者都成立才进步骤 5（E11）。检查点不评三轴分，不据它改方案顺序。

**步骤 8 的失败路径**：结果按轴分别看。性能轴变差且归因到门禁 → 回看 R3 分组与 R1/R2 读法，不回退提示层；产物或知识轴变差且归因到送达（verifier 报告引用了并列证据却判错，或任务书体积触到 E3 上界）→ 只按 E3 的裁剪顺序缩体积，不回退 E1/E2；变差且只能归因到提示层（作者行为与步骤 4 检查点时明显不同）→ R7/R8 整体回退到**步骤 5 末**的提交（步骤 1–3 的确定性替换与送达、步骤 5 的 E11 保留，步骤 7 退场随之重评）；无法归因 → 记为未验证，不回退，不加提示。所有回退保留 events 与产物副本供下一轮比较。
