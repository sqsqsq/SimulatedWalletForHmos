## 2. 性能分析

### 2.1 A1 量化基线：时间花在哪 **[机械]**

| Case | n | 时长 p50 | p90 | max | 等人 p50/max |
|---|---|---|---|---|---|
| auto-topup | 47 | 64 min | 2.5 h | 15.0 h | 2 min / 1.5 h |
| car-key-sharing | 31 | 2.1 h | 8.0 h | 15.4 h | 6.5 min / 11.4 h |

- auto-topup 时长直方图：**主体 30–90 分钟（29/47）**，>150 min 仅 4 个。car-key-sharing 同理但更重（plan 终点比 spec 终点长）。
- 极值拆解 **[语义]**（`data/analysis-a5-a6.md` §A5.0）：最长 15 h × 2 是 `worker_lost` 基础设施挂死；8 h / 9.6 h 是等人过夜（`human_wait_sec` 41031/25925）；gate_failed 6 例中 3 例是终检进程崩溃（0xC0000142）×3、2 例 API key 失效。
- **结论：模型本体的高效路径是稳定的（30–90 分钟）；波动大头依次为基础设施异常、等人、返修轮数，而不是模型日常推理慢。**

### 2.2 A2 一次成文率与返修轮数 **[机械]**

- verifier 机制 09-04 上线。上线后 spec 审查轮数分布（1 份=一次过）：**28 份一次过（41%）**、2 份 22、3 份 11、≥4 份 8（最多 18 份）；plan：18/26（69%）一次过。
- 确定性门禁失败率低：spec `fail>0` 仅 12/107（11%）、plan 3/41（7%）——**返修大头不在脚本门禁，在 verifier 语义轮次与机制循环**。
- 轮数趋势有欺骗性，必须拆解（`data/analysis-a5-a6.md` §A6）：18 份报告的极端战役中，**20 次派审约九成轮次产物与已审对象逐字节一致**——「写报告→材料变→新审查对象→再派审」的自激循环（framework 按材料哈希寻址 subject，hook 片段引用「上一份报告路径」，写报告这个必需动作本身改变材料）。真正语义返修只占少数轮次（首轮 AC-G3 BLOCKER 一轮修准；后续 PASS 报告携带的真实 WARN 逐条修复）。
- **结论：一次成文率 ≈ 41%（spec）；「修复花大量时间」的第一成分是审查对象漂移循环（机制层），第二成分才是真实语义返修。**

### 2.4 A4 重复犯错与「只修局部再报错」 **[语义]**

- 样本内（10 个失败 run 全程 + 21 轮派审逐轮核对）**未见明确的模型重复犯错**；「同一错误反复报」的三种真实成因：
  1. **机制性重验**：产物每次变更即重触发校验（裁决表引文随 contracts 变更跨 spec/plan/upstream 三次失效重报）；
  2. **告警不收敛**：MINOR 项门禁每轮重报、无清零要求；
  3. **真实残留逐轮带出**：verifier 每轮 PASS 报告带出的 WARN 都是真实问题（漏改数值、口径矛盾，含**模型上轮自己改错的方向**被下轮抓到——这是唯一的模型犯错实例，且被体系发现）。
- 极端任务下的 34–47 分钟卡壳（218 条裁决台账、生成器与检查器互相矛盾）是**任务规模与工具矛盾**，不是模型修不动常规错误。

### 2.5 A5 报错质量 **[语义]**

- 三要素（什么没满足+差在哪+怎么回正路）齐备率在会话内结构性报错中很高；10 样本中所有结构性报错 **1–2 轮修准**。1.9.7 步骤 7「送达与报错」的系统改造与样本后期的报错质量明显相关。
- 短板三类（各 1–2 例）：a) 环境类报错无指引（ts-node 损坏只有堆栈）；b) 形态细节不报（顿号合并路径被判单个路径缺失）；c) 要素分裂多处（期望格式写在 action 文本而非问题清单）。
- **比文案更大的失败源**：送达时机（review-disposition 位置违规在 run 结束后才发现，报错完美但模型永远看不到）与任务规模（218 条逐条裁决无减载路径）。

### 2.6 A6 推理链 **[语义]**

返修战役的模型推理质量本身高（哈希对照自证空转、读框架源码定位循环根因、留下手改痕迹），卡点归纳：

1. 报错难懂：**不是**卡点（21 轮无一误读）；
2. 找不到依据：中度——判据分散在框架层，模型 8 次源码检索拼机制图景；规则页与框架行为有表述缝隙；
3. 规则理解偏差：一处——update 期间 `reopen` 指引与状态机现实冲突，模型两次按文档走入陷阱、手改状态文件恢复（全场唯一越界，有留痕）；
4. 范围不清：verifier WARN「本轮不修」与 advisory「建议落实」的边界由模型裁量，裁量×材料寻址耦合出次生成本；
5. **结构性自激循环（主导）**：合法出口（写报告后走 sync-closure 不重算 subject）存在但**任何规则页都没写明**，模型两次自救找到、一次丢失重找，宿主在其收敛前 4 分钟停止。

## 3. 稳定性分析

### 3.1 B1/B2 结构与字段漂移 **[机械]**

### 3.2 B3/B4 内容差异与归因 **[语义]**（`data/analysis-b3-b4.md`）

五期精读 12 组差异的归因分布是本次分析最重要的修正性发现：

- **c) 规则演进：6 组（一半）**——上游 AC 承接（规则 09-26 才有）、埋点指标化（09-23/25）、扩展章归位（09-25/27）、规约表列与落点串、§8 形态、acceptance schema。「产物不稳定」的大部分是**规则自身高频变更的投影**，不是同一规则下模型行为不稳。
- **b) 门禁盲区：3.5 处现行存在**——① 金额/KB/% 类数值至今不在门禁单位表（latest 仍有未标「200 元」过门禁）；② 来源名粒度无判据（泛称「产品规则」、文件名+§坐标都放行）；③ §0/Scope 的流程说明 blockquote 进正文（规则 09-18 已禁止、判据不及、两轮实跑均出现）；④（已修）中文单位正则 09-26 前扫不中。
- **a) 漏执行：仅 1 处**——v0 轮 knowledge_rule 桥接（规则+门禁+报错全在，终稿 0 条，该轮 FAIL 未闭环）。
- **d) 规则模糊带：5 处**——承接写法两式、指标数量粒度、统计点表列集、术语表列序、来源名形态。
- 数值取值漂移（首屏阈值 1s/1.5s/2s 五期三值）在「本工程设定」自由度内——**这是真源缺位**（没有登记复用机制），不是模型不稳。

### 3.3 B5 理想最佳形态（spec 打样）**[语义]**（`data/analysis-b5-spec-draft.md`）

### 4.2 C2 责任位置（问题修在哪一层）

1. **机制设计层**（最大性能成分）：subject 材料寻址 × hook 引用「上一份报告」→ 写报告自激循环；审查对象无「产物未变不重审」出口；run 结束后才跑的终检无修复回路；218 条裁决级任务无减载。
2. **信息送达层**（规则页/方法页）：sync-closure 合法出口未写明；reopen 适用条件与状态机冲突；处置台账落点无位置约束（#7）；数值取值无真源登记（1s/1.5s/2s 漂移）。
3. **判据层**（门禁盲区 b）：单位表缺金额/KB/%；来源名可定位性；blockquote 说明性文字；H1 标题写法。
4. **规则模糊层**（d）：承接两式、指标粒度、列序——两式都合规造成跨 run 漂移。
5. **模型本体**（样本内占比最小）：唯一实例是上轮改错方向被下轮 verifier 抓到；可疑编造 1 处。**「模型不稳」不是主要矛盾——体系（规则变更频率 + 机制循环 + 判据盲区）才是。**

## 6. 结论（对应诉求的三句话）

1. **性能**：正常路径稳定在 30–90 分钟；时间流失的大头是审查对象自激循环（机制层）、真实语义返修（规则变更高频期的问题密度）、环境异常——模型本体修常规错误的效率高（结构性报错 1–2 轮修准），「模型不稳定」不是主要矛盾。
2. **稳定性**：产物漂移的一半是规则高频演进的投影；现行真实的自由度集中在门禁盲区（3.5 处）与规则模糊带（5 处）；理想最佳形态可以按现行模板逐章拼装（spec 打样已完成），且门禁 PASS 不等于形态最优。
3. **期望路径**（按诉求 P3/S3 的框架归类）：不犯错 → 正向预防（规则页补出口与约束、模糊带定写法、数值真源）；犯错快知道 → 报错三要素已大体成立，补齐盲区判据与告警收敛；不重复犯 → 修「机制性重验」与「写报告即变材料」的循环，而不是归咎模型。
