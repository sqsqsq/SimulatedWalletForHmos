# 需求：Chart 上报方案与可迁移知识样例

版本归属：1.9.5 候选需求。本稿于 2026-09-21 根据用户逐项确认整理，替换此前 GLM 稿中的默认选择和未经确认的结论。**业务目标及用户确认边界已明确；当前设计见[版本范围](../00-版本范围.md)所链接的实施总览。本稿不构成真实测试启动指令。**

Chart 指运维统计上报，与 Story 图形可视化无关。本需求不代表 1.9.5 的全部范围，也不改变正在构建的 1.9.4。[事实核对与确认记录](01-事实核对与待确认.md)保存本次取证和原话依据，本文是当前需求正文。

## 1. 目标

对于涉及指标或影响已有上报的业务需求，模型能够识别需要统计的业务节点，给出完整、正确的 Chart 上报方案，并在实现和验证中落实。知识、Spec、Plan、Story、代码与检视应围绕同一套当前业务要求工作。

**代码实现层负责把所有适用场景的原始事件正确、完整地上报；成功率分子/分母等计算属于数据使用层。** 本轮不设计后台统计公式、不建设统计平台，也不为某种公式提前删掉取消或失败事件。

Demo 提供可参考、可执行验证的样例。迁移到内网或其他代码仓时，按目标仓真实代码与规则适配，不能把 Demo 的类名、字段、编号取值或具体编码表固化为所有项目的协议。

## 3. 上报方案需要讲清楚什么

### 3.1 业务节点、触发与结果

说明该需求哪些业务节点需要统计、为何需要、每个节点何时产生事件，成功、失败和主动取消等适用结果有哪些。只有名称列表或一句“增加 Chart”不能指导正确实现。

四类结果语义为中间步骤成功、全流程成功、普通失败、主动取消；它们与内码的具体结果分别说明。与现有枚举/API 的映射要在样例中清楚呈现，不能仅凭字段名称让消费模型猜。

多步骤、重试、重复回调、提前返回、取消后回调、异常或超时等场景，按具体业务辨明事件产生与去重边界。数据使用层怎样计算成功率不在本轮决定，但代码侧仍须说明它报告的是哪一次实际执行、哪个业务节点及什么结果，避免漏报/误报/重复。

### 3.2 内码与既有定义

内码表示业务场景及具体结果，不应因习惯称“错误码”而只覆盖失败。十位字符串保持前导零；五段语义与实际取值有可查依据。

新增需求先查已有节点、编码与上报；相同含义复用，新增必须区分的含义才扩展。变更不能造成冲突、复用错误含义或使旧消费者误解。编码登记的唯一来源、分配规则及样例取值在设计阶段依据本仓实际补齐，不凭现有 WalletHAEventID 名称推断它就是内码表。

### 3.3 外码

外码承接具体步骤取得的原始外部错误信息中的错误码，与本项目内码分开。说明来源接口及取得方式，不把内码冒充外码，也不为了填字段伪造一个外部错误码。

无外码、多层错误或同场景可能来自不同接口时，样例方案要明确选取来源与缺席表示；具体字段映射由实际接口与设计确定，不能只写“异常时上报”。错误描述及敏感内容继续遵循目标安全要求。

### 3.4 事件身份与扩展参数

用户列出的事件本身信息包括 eventId、funcID、subFuncID、walletEventDesc；其他参数包括 channel、source、issueID、issueName、operationType、orderNumber、srcPassType 等，也允许业务根据需要定义额外维度。这个列表不是封闭全集，也不是每次都必须填满。

每个实际使用的字段说明含义、类型、单位（适用时）、取值/来源、何时必需及隐私处理。当前 SDK 已支持的字段要准确复用，不支持的必要字段在设计中明确差距和最小实现动作，不能伪造 API。

性能类观测需要说清采集的起止点、耗时单位及适用结果；占比等用途需要提供有业务含义的事件分类/维度。它们仍是数据产生要求，不将汇总公式、统计窗口或报表计算实现塞入客户端。

## 4. 日志、VOC、Chart 与 BI 上报

| 类别 | 本需求的职责边界 |
|---|---|
| 日志 | 保留统一封装、必要排障上下文与安全要求；由模型按业务定位需要设计，不再强制每步骤/每分支都有日志 |
| VOC | 问题定位，真实仓对应 VocBuilder；保留关键路径能力，过程关键点使用。Demo 既有 logAndReport 类门面同时产生本地日志，避免重复 |
| Chart | 运维统计，真实仓对应 ChartBuilder；选定统计节点的适用终态事件，覆盖正确分类与参数 |
| BI | 运营打点，真实仓对应 BIBuilder；与 VOC 问题定位、Chart 运维统计分别说明。本次术语澄清不自动扩展为新增 BI 实现或运营采集平台 |

终态只报 Chart、过程关键点只报 VOC 的二选一要求保留。它只约束 VOC/Chart，不扩大为 VOC/Chart/BI 三选一，也不等于终态禁止按排障需要记录本地日志。

VocBuilder、ChartBuilder、BIBuilder 的真实仓命名来自用户确认；接口签名、字段和 Demo 对应能力仍按实际代码取证。知识样例应说明三者用途，不能把真实仓类名直接写成本仓已存在的接口，也不能固化进通用机制。

调整 OBS-01 时，保留的定位、封装与安全责任要有现行承担者；撤销的是过宽的逐步强制及其方法存在性探针，不删除日志 API，不删除其他规则的有效探针能力。安全要求以安全隐私知识真源为准，不复制一套冲突规则。

## 5. 知识与跨阶段产物

### 5.1 各阶段承担的内容

| 阶段/产物 | 要形成的结果 |
|---|---|
| Spec | 独立上报设计小节：需要统计的业务节点、适用场景和结果、数据产生要求、对已有上报/编码的影响及可观察验收 |
| Plan | 独立实现设计小节：具体代码落点、API/字段对应、参数来源、错误/取消/耗时处理、去重及验证方法，落实 Spec 决定 |
| Story | 独立可定位的人读小节：采集哪些业务场景与结果、重要边界及既有上报变化；精确字段/码表按既有附录规则保留，不要求读者先懂 SDK |
| Coding | 在真实业务动作/回调/异常路径正确调用，实现已定上报设计；不能只在注释中声明遵守 |
| Review | 对照需求场景、代码和有效定义，核遗漏、错误分类、字段来源、重复和旧定义影响 |
| UT/适用执行验证 | 通过可复现场景捕获原始事件，核时机、内容、次数；所用模拟/实机范围如实说明 |

只有涉及 Chart 的需求要求这些独立小节。章节的内容应来自本需求的真实设计，不能以统一表头齐全代替设计成立，也不要求三份文档复制同一套明细。

### 5.2 知识与通用机制的边界

用户进一步确定：独立事实知识以“上报”命名并统一承载 VOC、Chart、BI，使用 reporting.md；codebase-facts 的上报内容全部迁入，不保留重复说明。本地日志仍留原工程事实。渠道共用一个知识入口，各自规则与实际能力仍区分；本次不因此扩展为新增 BI 实现，后续上报诉求沿同一知识文件扩充。


用户补充确认：本需求特别关注过拟合，Extension 通用层与 Demo 不得耦合；面向 Demo 的知识层须具备骨架参考能力，让目标仓可以参照组织方法、依据真实代码重新适配。骨架应连接业务节点选择、结果与参数设计、实际调用和验证，明确示例选择不等于通用规则。

- 工程事实记录真实 API、参数/类型、封装行为、定义位置与使用样例；不能把尚未实现或未经核实的能力标为已存在。
- 项目规约承载适用条件、覆盖义务、编码/结果等约定和验证要求；不是所有规则都塞入 codebase-facts，也不是将自然语言要求翻译成关键词检查。
- Demo 样例让使用者看懂如何从业务场景形成上报方案并落到代码/事件证据。目标仓依真实实现适配，既有知识的升级保护沿原有所有权约定。
- Extension 通用部分不写 Wallet 专属类名、五段码值、结果取值表或参数清单。独立小节是用户期望的产物效果，是否复用现有骨架/技术契约或补最小通用承载，在设计阶段核实。
- 知识应用机制是否需要改动取决于实际缺口；既不预设新增机制，也不提前承诺脚本/hooks 零改动。

## 6. 当前已核事实与设计输入

详细位置见[事实核对](01-事实核对与待确认.md)。主要事实：

1. 当前 OBS-03 只有业务步骤终态覆盖要求；OBS-01/02 的现行内容与本轮目标需要按职责修订，不能原样全保留。
2. Demo 已有 WalletFuncResult 四个枚举和内码/外码/结果/耗时等 setter；知识里的 chartBuilder(...).report() 只是简写，封装不会自动补齐未设置的字段。
3. 自定义 setReportParam 为 protected；额外维度不能假定当前调用者已经可任意添加。
4. 当前产品目录字面检索未找到十位内码登记或业务侧 chartBuilder 使用样例；不能由此宣称整个链条没有能力，也不能假定内网有某份权威表。
5. Spec §9.4 已有埋点表，Story 附录有其投影，Plan 有规约义务承接。当前缺的是正确内容与独立可读设计，不是从零没有任何载体。
6. 存在知识消费代码不证明某次实际执行读到并用了这些要求。归因到内容、送达、理解或实现，需要看真实输入与产物，不能仅凭历史总分。

## 7. 验收

用户补充确定验证环境：Demo 真实模型测试止于 Plan，不跑 Coding 及之后的真实测试；代码与原始事件行为在内网真实环境验证。以下目标不降低，按设计/机制证据与运行证据分别记状态，内网未执行时不能将运行项标为已通过。

| ID | 可检查的完成条件 | 证据 |
|---|---|---|
| AC01 | 从具体需求识别必要统计节点，并覆盖各节点全部适用结果，不按内部函数机械铺点 | 来源、Spec/Plan 与场景对照 |
| AC02 | 内码结构/语义、结果分类及外码来源正确；主动取消与拒绝授权等失败分清 | 定义、代码与原始事件 |
| AC03 | 事件身份、描述及所需公共/业务参数有正确值和来源，性能类起止/单位明确 | 参数说明、实现与捕获数据 |
| AC04 | 复用或扩展已有编码/上报有依据，无冲突和旧含义误用 | 现有定义、变更与回归 |
| AC05 | Story/Spec/Plan 的独立小节内容各履职责，并传到 Coding/Review/验证 | 实际阶段输入和产物，不只查标题 |
| AC06 | 可复现执行捕获的原始事件，在正常/失败/取消及相关异常路径中不漏、不误、不重复 | 执行刺激、捕获记录和对应断言 |
| AC07 | 终态 Chart、过程关键点 VOC 的边界保持；日志不按出现次数/方法探针机械判通过 | 代码/事件与规则责任对照 |
| AC08 | Demo 样例可被目标仓按真实代码适配，机制无钱包专属规则依赖 | 知识/通用机制边界及适配说明；目标未实测部分披露 |

本轮不以后台报表公式正确作为客户端验收，不以门禁 PASS 或某段代码出现 chartBuilder 代替事件语义正确。案例选择、次数、捕获方式与原生编译/测试安排由设计提出后按实际授权运行，不沿用 GLM“一次实跑足够”的默认判断。

## 8. 交付与设计依据

交付包含：当前 Demo 的完整知识与可验证样例、各阶段正确承接及独立小节、必要的既有规则替换、正常能力的回归证据、迁移时如何依据目标代码适配的说明。

当前设计负责落实：编码登记与取值的具体位置；事件参数与当前 API 的映射/必要能力补齐；重试/重复回调/取消等具体事件边界；通用产物承载的最小改动；样例与事件捕获方式；新旧职责交接和预算。这些是维护设计职责，不把全部函数级选择转交用户。
