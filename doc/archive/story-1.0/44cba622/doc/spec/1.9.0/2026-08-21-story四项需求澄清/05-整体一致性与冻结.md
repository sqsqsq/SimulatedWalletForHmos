# 四项需求整体一致性与冻结

> 状态：已冻结  
> 检查范围：[需求 1](01-Story内容守恒与去重.md)、[需求 2](02-Story面向人类叙述.md)、
> [需求 3](03-Knowledge跨阶段应用.md)、[需求 4](04-ADAPTATION工程适配.md)

## 整体关系

1. 需求 1 先形成事实完整、重复已合并且主叙述位置明确的 Story 内容结果。
2. 需求 2 以需求 1 的结果和全部同轮材料为成文依据，通过全局规划、逐章成文、全文统稿和全量复核改善
   人读体验，不改变需求 1 已守恒的事实集合。
3. 需求 3 独立负责工程知识的分类、启用、跨阶段应用和验证；Story 不直接读取这些工程知识。
4. 需求 4 负责把 Story 跳板和 Extension 安装、适配或升级到目标工程，并把目标工程真实能力转化为
   需求 3 可正式启用的项目知识、规约和设计模式。
5. 日志、VOC 和 Chart 三层可观测性属于需求 3 的知识内容；需求 4 负责在目标工程中核实并适配它们，
   两处分别回答“怎样应用”和“怎样获得真实目标工程内容”，职责不重复。

## 一致性检查结果

| 检查项 | 结论 | 依据 |
|---|---|---|
| 内容守恒与人类叙述 | 一致 | 需求 2 只改表达、章节组织和阅读逻辑，不增加、删除或改变需求 1 的事实、决定、范围和验收含义。 |
| 去重与逐章成文 | 一致 | 每章读取全部同轮材料，章节职责只指导主要回答的问题；唯一主叙述由全文统稿和成文后审计共同复核。 |
| Story 与 Knowledge 边界 | 一致 | Story 负责需求内容与叙述；三类工程知识从 Spec 开始消费，Story 不直接读取。 |
| Knowledge 分类与可观测性 | 一致 | 可观测性的语义要求属于规约，目标 API、SDK、代码位置和当前实现属于项目知识，不新增第四类知识。 |
| 两个模式与 Knowledge 分类 | 一致 | `decision-tree` 和 `page-interaction` 是两份可选方案；索引不是新类型，目标 SDK 和案例事实仍归项目知识。 |
| Plan 设计与下游执行 | 一致 | Plan 必须先让知识影响真实方案，再冻结具体义务；Coding、Review、UT 和 Testing 只消费冻结结果并以真实产物验证。 |
| Knowledge 激活与 Extension 发布 | 一致 | Knowledge 激活清单声明目标工程启用哪些知识；Extension Manifest 记录 Story Extension 发布版本。两者职责不同。 |
| 首次适配、升级与重新适配 | 一致 | 未集成时首次适配；已安装旧版本时升级；已安装同版本时只重新扫描和调整适配内容。 |
| 直接维护内容与适配内容 | 一致 | 归属由版本发布清单显式声明；直接维护内容随版本替换，适配内容保留并在扫描、方案确认后更新。 |
| Demo 能力与目标工程能力 | 一致 | Demo 只证明当前工程已有实现；目标工程必须重新核实并替换具体身份，不能复制后假定可用。 |
| 修改时机与完整性 | 一致 | 首次适配和升级都先形成完整方案并获得一次确认，再原子写入；失败不留下部分结果。 |

## 检查中清理的残留

- 总览把已经扩展为三项的需求输入误写为“唯一需求输入”，已改为“上面列出的需求输入”。
- 需求 1 的目标和核对证据仍残留已废止的“冲突处理”，已删除，不保留该项设计。
- 需求 3 的已确认问题仍使用“需要确认”措辞，已改为确认恢复完整三层可观测性合同。
- 需求 4 的总分流只写“已集成进入升级”，与同版本重新适配不完整，已按已确认结论补齐版本比较。

以上均为对已确认决定的文字归一，没有新增需求或实现机制。

## 冻结后的四项验收边界

### 需求 1

- 全量盘点来源事实，仅删除已证明重复的表达。
- 每项事实有唯一完整主叙述位置，并有正文外的完整逐项核对证据。

### 需求 2

- 使用固定顶层骨架和自然业务标题，按内容需要使用正文、表格、图和链接。
- 每章读取全部同轮材料，按“全局规划 → 逐章成文 → 全文统稿 → 全量事实复核”成文；成文后再生成
  独立审计记录，优化后的事实集合与需求 1 一致。

### 需求 3

- 项目知识、规约、设计模式职责和生命周期分离，当前版本不增加其它知识类型。
- Plan 在方案中实际应用知识并冻结，下游以代码、diff、UT 和 Testing 结果证明落实。
- 日志、VOC 和 Chart 的完整三层可观测性合同得到设计、实现和验证。
- 恢复 `decision-tree` 和 `page-interaction` 两个模式；它们可以成为候选，但采用与否必须由 Plan 决定并冻结。

### 需求 4

- `/story adapt [<目标工程>]` 在 Framework 前置检查后，确定性进入首次适配、升级或重新适配。
- 版本、内容归属和变化来自显式发布清单；适配只依据目标工程真实证据。
- 两个模式的通用定义及索引直接交付并默认进入知识清单；目标 SDK、依赖和案例经适配核实后，决定具体
  需求形成零个、一个或两个候选，以及 Plan 最终是否采用。
- 用户确认后原子写入，目标工程最终得到可正式启用且不依赖当前工程的 Story Extension 内容。
