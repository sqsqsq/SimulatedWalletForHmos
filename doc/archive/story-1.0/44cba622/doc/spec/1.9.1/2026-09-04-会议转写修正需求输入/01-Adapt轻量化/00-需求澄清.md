# Adapt 轻量化：升级简单、快速

> 状态：原 A1–A11 于 2026-09-07 冻结；**2026-09-08 用户新增内网仓之间复刻场景，覆盖边界已明确，方案已同步到步骤 2 §2–§3；返修二 cdb24f20 已实施**。方案见 [design 步骤 2](../../../../plan/1.9.1/2026-09-07-新需求四项/steps/02-Adapt轻量化.md)。
> 来源：用户 2026-09-07 新需求阶段的第 1 项诉求及后续确认。
> 上级入口：[新需求讨论总览](../00-讨论总览.md)。本需求细化整体正向审查中的 F6 安装与升级职责，不重新打开上一轮交付。

## 1. 用户目标

**升级非常简单、快速。** 支持 Demo 仓向内网业务仓适配，以及已有内网业务仓向其他业务仓复刻。前者保留目标对接实现；后者连同内网共用对接实现一起覆盖。已有目标知识始终保留，不再重复理解业务、逐文件判归属或合并知识。

字符减少应来自取消这些重复职责与历史兼容路径，而不是压缩说明或把工作转交给用户每次手工处理。首次初始化的扫描成本与日常升级成本分别评价。

首次初始化只带 README 的要求与已有目标仓保留知识的要求分别生效：不因交付包去掉 Demo 知识而删除目标已有知识。

## 3. 当前实现为什么重

观察依据为已交付版本的 `story-adaptation/SKILL.md` 与 `adapt-scan.mjs`，用于识别要替代的职责，不作为新方案的合理性依据。

- **知识升级承担语义合并**：当前流程比较包与目标的规约、模式，提出变更提案，重算索引及激活内容。新需求中已有知识全部归目标保留，这些动作不再是日常升级职责。
- **代码所有权没有直接体现在目录里**：当前固定脚本与目标对接脚本同处 `skills/story/scripts`，用后缀、文件自述和特殊排除区分。新需求让目录直接表达哪些可覆盖、哪些需保留。
- **历史兼容持续存在**：无版本的旧目录签名、旧入口段识别、历史工作目录说明、可选 Framework 补丁传递等仍在流程中。需明确退出范围，使未来升级只处理约定结构。
- **普通升级要求完整扫描和方案展开**：当前“读两棵树、逐文件判、写四段方案、确认、写入、校验”的动作中，很多用于知识合并或动态判所有权。目录边界固定后，应取消不再提供信息的环节，不把相同步骤换名称保留。

## 4. 所有权边界与必要连带要求

| 内容 | 首次初始化 | 已集成仓升级 |
|---|---|---|
| Knowledge 目录与 README | 创建说明骨架，无 Demo 具体知识 | 保持目标原样，快速确认即可 |
| 部件画像 `component_profile` | 扫描目标仓初始化 | 保持原样 |
| 其它 facts、规约、设计模式正文 | 不随包填入 | 保持目标原样 |
| Extension 固定机制 | 安装固定目录 | 按目录替换，包括删除已退场的固定文件 |
| `scripts/adapters/` 对接脚本 | Demo 来源不复制替身；内网来源复制其共用实现 | Demo 来源保留目标实现；内网来源整体替换为来源版本 |
| Extension 自有宿主跳板 | 写入指定文件 | 直接覆盖指定文件，宿主其它配置不在覆盖范围 |
| Manifest 中的机制登记与知识激活 | 只登记实际存在的内容 | 机制登记跟随包；目标知识激活与内容保持一致，不因升级重新挑选知识 |

**来源与安装状态是两个独立维度。** 来源决定 adapters 是否随包复制；目标是否首次接入决定知识骨架与部件画像是否初始化。内网仓复制到新业务仓时，也不把来源业务仓的知识正文或画像带过去，仍按 A3/A4 初始化目标自身知识。

“除了 knowledge 都覆盖”限定于 Extension 发布面；manifest 的知识激活清单仍归目标，不得指向来源业务仓的知识。项目源码、目标架构配置和无关宿主配置继续遵守原有覆盖边界。

**只有骨架的知识目录必须是合法起点。** 当前 `activeKnowledge` 要求三类知识都有正文，直接删 Demo 文件会使运行报错。新需求的初始化和直接消费者须同时支持“尚未填充具体知识”，不生成虚构条目、不强制选模式；已配置知识仍正常应用。具体消费形态留到方案设计，不为此另建知识框架。

**目录按职责而非文件后缀划分。** 当前需求系统对接的 `story.js`、`token.js`、`review.js` 是自定义候选；固定的流程、成文和检查脚本属于机制。最终清单需逐项核实，不能简单把所有 `.js` 当业务、所有 `.py` 当机制。

**与会议转写需求对齐。** 会议转写的 docx 解析是公共脚本（04 分册 D4，2026-09-07 按 A11 改），落公共目录，随升级正常更新；本需求不提前实现会议功能。

## 5. 验收方向

1. Demo 向已有业务仓升级，目标知识、对接脚本与无关宿主配置保持不变；内网仓向已有业务仓复刻，目标知识和激活清单保持不变，adapters 与其余机制更新为来源版本。
2. 新仓安装后只有知识说明骨架与扫描生成的目标部件画像，没有 Demo 规约、API、模式实例或业务专名。
3. 固定机制与指定跳板更新到目标版本，已退场机制文件被清除；运行入口能够到达正确的新实现。
4. 相同版本重复执行不损坏目标内容，不启动知识语义合并或业务重新扫描。
5. 日常升级无需逐文件说明业务差异；实际操作、模型读取字符及耗时相较现有流程显著降低。时间上限待当前升级读数及用户期望进一步确认，不先编一个秒数。
6. 必要失败有明确结果；读取失败或安装中断不能标成升级成功。验证使用对应层次的最小检查，不默认把开发阶段全链测试搬进每次升级。
7. Demo 按目标结构交付；新版 adapt 不含历史兼容或迁移实现。内网已有仓由用户手动调整后使用正常升级路径。
8. 内网仓向首次接入的业务仓复刻，目标获得可用的内网对接实现，同时只初始化知识骨架与目标部件画像，不复制来源仓知识正文。
