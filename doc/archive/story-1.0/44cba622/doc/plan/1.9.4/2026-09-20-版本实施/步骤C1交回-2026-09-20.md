## 2. 四种去向各自的判据与失败语义

`prepare` 返回 `comparison`，**全是机械事实，一个业务结论都不下**：

| 去向 | 什么时候 | 脚本做什么 |
|---|---|---|
| `resume` | 上一轮 update 还开着 | **不新建镜像**——新的会把旧的恢复依据盖掉；指回那一轮的 `before/` 与 notes |
| `unchanged` | 与上次已处理版本逐份比过没变、暂存区空、没有读不到的来源、也没有 `--request` | 什么都不建、什么都不删，如实说「比过了，真没变」 |
| `incomplete` | 比较基准缺席，或有来源读不到 | 留镜像，把可查与不可查的范围说清；**不许冒充无变化** |
| `changed` | 有文件变了、暂存区有内容，或人明确要求改 | 留镜像，列出变了哪些、暂存区有什么，指向方法页 |

三条失败语义写进了实现：

1. **「文件不在」与「文件在但读不出来」分开**（`_scan`）。混成一个的话，一次权限错误会被报成「上游把这份材料删了」，而模型据此去删下游功能。
2. **首次没有基准不是无变化**（`_baseline` 只认 `closed` 的记录）。报成无变化的话，第一次 update 会直接退出，而它恰恰最该看一遍。
3. **取不到旧正文就不写差异**（`_write_diffs`）。只说「这几份变了」是事实，编一段 diff 不是。

## 3. 中性场景走查

**这是设计语义审查材料**：逐例写清输入、要判断什么、允许的不同结果。**没有跑过模型**，也没有把这些答案写进生产提示——
写进去就变成了「按这五种情况套」，而真实输入从来不长成样例的样子。

### 场景一：有人手改了部分文档

- **实际输入**：`prepare` 报 `changed`，`changed` 里有 `spec/spec.md`；`before/` 里是他改之前的样子；没有新材料、没有新意见。
- **要判断什么**：他改的是表达还是业务含义；这个意思在真源（Spec / `decisions.json`）里成立吗；与之关联的地方（story 对应章、验收、Plan）同步了没有。
- **应改 / 应留 / 应问**：改的若是业务含义，**回真源改**再让下游一致；只是措辞就保留他的写法、不重生成覆盖回旧稿；改动与已定结论冲突时**问人**。
- **允许的不同结果**：判成「纯表达、无需修订」与判成「要同步三处」都可能对——取决于那几句话的业务含义。**不可接受的是**：重新生成一遍把人的修改抹掉，或只改叙事不改真源。

### 场景二：上游删掉了一段，含义不明

- **实际输入**：`fetched.json` 里 `AR-design.md` 的摘要变了，差异显示少了一段；没有任何说明为什么少。
- **要判断什么**：这是撤销了这个要求、把它挪到别处了，还是新版本只是没重复说一遍。
- **应改 / 应留 / 应问**：先回查去向（同一份的别处、SR、会议）；**依据不足不删下游功能**；问人时问的是「这一段是撤销还是挪走」，不是「要不要删」。
- **允许的不同结果**：找到去向就按去向处理；找不到就保留现状并登记成待决。**不可接受的是**：因为上游没写了就把下游那条能力删掉。

### 场景三：回来的是针对旧版本的评审意见

- **实际输入**：`fetched.json` 取回 `review-feedback.md`，里面有三条意见，其中两条针对的做法在本轮之前已经改过了。
- **要判断什么**：每条意见针对哪个议题、哪一版；它现在是否仍然适用；已经落实的那两条要认出来。
- **应改 / 应留 / 应问**：仍适用的照办；已落实的**说明已落实，不重做一遍**；含糊或与新决定冲突的问人，问的时候要带上「当时那一版是什么样」。
- **允许的不同结果**：把一条意见判成「已落实」或「仍需处理」都可能对。**不可接受的是**：把三条一起当新要求重做，或因为看起来旧就一条都不处理。

### 场景四：新决定改变了隐含关系

- **实际输入**：人在 `--request` 里说「撤销宽限从 24 小时改成 36 小时」；文件可能一个字节都没变。
- **要判断什么**：这个数字牵动哪些关系——什么时候允许撤销、提示怎么写、接口的拒绝条件、异常路径、验收条目，以及 Plan 里已有的相关设计。
- **应改 / 应留 / 应问**：沿完整业务关系推演，**只同步现有材料证实存在的关系**；同时列出重要的不变项与为什么不用改；范围要扩到本单之外时问人。
- **允许的不同结果**：同步三处与同步六处都可能对，取决于这个单实际写到哪。**不可接受的是**：只把数字替换一遍，或者为了「全链完整」虚构一条工程里不存在的能力。

### 场景五：没有新差异，但上一轮没同步完

- **实际输入**：`prepare` 报 `resume`，指向还开着的那一轮；文件摘要与上次比没变。
- **要判断什么**：上一轮的修订清单里哪些做完了、哪些没有；没做完的现在还成不成立。
- **应改 / 应留 / 应问**：读那一轮的 `update-notes.md` 与 `before/` **接着做完**；普通的业务未决如果这次没有新信息，就保持未决、**不反复催问**。
- **允许的不同结果**：接着做完，或按记录还原现场重来。**不可接受的是**：因为「摘要相同」就报无变化退出——那正是上一轮没做完的事被永久丢掉的方式。

## 5. 测试抓到的一处真问题：对接层不许知道「清单」

`test_material_rounds::test_the_data_layer_never_hears_about_the_manifest` 红了：它禁止 `adapters/*.js` 里出现
`manifest` 与 `materials.json`，理由是**对接层各部署环境自备、不随包交付，不能要求它们跟着改**。

我给 `fetch` 的取材清单起名 `manifest.json`，撞了这个词。虽然它与材料清单是两回事，但这个判据守的是
「清单这个口径不扩散到对接层」，**撞名本身就是扩散的开始**。改成 `fetched.json`，正文里叫「取材回执」，
四处引用（story.js、README、update.md、测试）同轮改完。**没有动那条判据。**

顺带发现并修掉：`prepare` 的 id 精确到秒，同一秒跑两次直接报错——这是个没必要的失败路径，改成撞名加序号。
