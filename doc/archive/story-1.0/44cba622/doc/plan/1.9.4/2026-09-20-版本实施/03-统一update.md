# 需求 C：统一 update

对应 S-UPD、D08–D15、AC05–AC11/AC13。先读[总览](00-整体设计与实施总览.md)。本需求由模型理解变化并组织修订，脚本提供取材、保留、差异与确定性检查。实施仍分 C1/C2/C3，但以“取得判断依据→修订关联内容→交付可用结果”组织，而不是以新增命令组织。

## 1. update 的目标与边界

**结合最新有效输入、既有决定和当前需求进展，判断哪些内容仍然成立、哪些需要修订，使受影响的已有产物成为一致、可继续工作的依据，并明确仍未决或尚未验证的部分。**

用户给需求编号，不必先替模型列出哪些文件要改、为什么改。脚本先快速检测实际文件变化并给出差异；无变化且无未完成更新时直接报告退出。有变化、需要续办或比较依据不全时，模型再识别已手改部分、未同步内容、旧意见的适用范围和下游影响。

**轻量优先是本需求的实现约束。** 复杂场景由模型结合原文理解，不逐场景增加脚本状态、分类分支、语义字段或门禁。复用现有文件操作与流程；新增脚本只填真实的确定性缺口。

完成对象是本次变化所涉及的业务关系，而非某几个文件。关系包含对象、前置、行为、结果、责任、异常、未决与验收；其实际落点可能分散在多个产物，也可能在当前阶段尚未生成。

保留已确认边界：只更新已有 Spec/Story/Review/Plan 及必要的输入解释/过程记录；不自动生成新阶段产物、不改产品代码/测试。默认局部及必要关联修订，整篇表达优化由用户明确触发，大幅重组先说明并确认；外部回写在展示后确认。

### 1.1 对用户报告什么结果

| 结果 | 何时成立 | 用户能据此做什么 |
|---|---|---|
| 已同步，可继续当前工作 | 受影响内容按当前有效决定一致，适用检查完成；实际改动的适用阶段已取得当前材料的独立审查 PASS，没有阻止当前工作的未知 | 在原进展上继续，不代表需求自动进入下一阶段 |
| 已同步，有明确保留项 | 当前材料的适用审查通过；业务未决、非阻断建议或代码/测试影响明确，没有被写成已完成；审查缺席/FAIL 不属于可保留的 WARN | 继续不依赖这些保留项的工作，按说明处理剩余事项 |
| 尚未完成 | 必要输入、裁决、同步或验证缺失 | 知道具体缺什么、影响哪些内容、下一步由谁处理 |
| 核对后无需修订 | 有效变化已被落实、只是表达差异或无关；当前关联内容一致 | 保留现稿，不为了留下更新痕迹重写 |

另报外部发布是否发生及实际结果。本地文件写完、脚本退出 0、操作记录已关闭，都不能代替这些判断。没有历史版本时可以判断“当前无需修订”，但不能声称“历史从未发生变化”。

## 2. 先检测，再决定是否需要模型理解

普通启动顺序（prepare 返回 comparison=unchanged/changed/incomplete/resume 及实际比较范围、差异/镜像位置；这些只表示机械检查事实，不表示语义结论）：

1. 保留当前需求目录的临时镜像；已有未完成操作则先恢复其现场，不以新镜像覆盖旧恢复依据。
2. 只读取回约定来源的新内容到暂存位置，不覆盖当前稿；枚举本地约定来源与已有产物。
3. 与上次已处理版本比较，输出新增/修改/删除文件及可取得的正文差异；任何来源失败单列。
4. 无变化、比较完整、没有未完成更新、也没有新的明确重查/修订请求时，报告“未检测到变化”，删除本次临时镜像与暂存内容并退出。目标业务文件、回执和外部系统不写；不进入下述六个模型动作。
5. 有变化时保留本轮镜像不动，将差异、对应原文和当前进展交模型；新工作内容仍在原需求目录正常存放。模型理解后可能判断无需进一步修订，应报告“检测到变化，经分析无需修订”，与“未检测到变化”分开。

没有字节变化但上次已决定的同步没有做完，继续原工作；普通业务未决如果本次没有新信息，只保留未决，不触发反复询问。新增对话决定/明确重查请求也是本轮输入，不能因文件未变而忽略。

缺比较版本或来源不可达不属于无变化。报告可查与不可查范围，让模型处理必要的当前一致性判断；不默认全量重做，也不谎报快速检查通过。

### 2.1 比较基准与恢复镜像分开

| 对象 | 用途 | 保留方式 |
|---|---|---|
| 上次已处理版本 | 识别启动前已经发生的手改、上游变化及重复输入 | 优先复用已有版本；没有可用旧正文时为比较集合保留一份稳定的只读内容/摘要，不引入通用版本平台 |
| 本次启动镜像 | 恢复本次执行前的完整现场 | 无变化删除本次临时副本；有变化保留完整原貌，不混入新内容 |
| 当前需求目录 | 模型修订并继续工作的当前版本 | 新内容正常写在这里；脚本不另建可编辑的完整影子工作目录 |

只保存路径＋哈希能发现哪些文件变了；逐行差异需要旧正文，取不到时如实标明。启动镜像不能替代比较基准：用户在启动前已经修改的内容同样在镜像中，仅将它与当前目录相比会漏检。

只有本轮输入已被模型处理、已决定的修订完成并完成适用检查后，才推进比较基准；失败/中断不推进。已明确暂缓或保持未决但当前无需修订的输入可以记录为已处理，下次没有新信息不重复催问。脚本保存这个执行事实，不替模型判断决定是否合理。

## 3. 必须覆盖的场景与模型判断

下表是设计与验收用的场景，不是脚本枚举表，也不是可能业务变化的全集。模型遇到未列情形仍按目标、实际来源和已确认权限处理。

| 场景 | 要辨清什么 | 应采取的动作与保护 |
|---|---|---|
| 上游新增/修改 | 补充解释、改变要求、纠错，还是新方案替代旧方案 | 确定实际变化及旧结论是否失效，不按新增段落逐字铺到下游 |
| 上游删除/改名/挪位 | 明确撤销、移动内容，还是新版省略了说明 | 找到有效去向/撤销依据；依据不足不删除下游功能 |
| 新会议或新版本 | 谁说了什么，是建议、讨论、决定、否决还是未决 | 读原话和语境，复用会议能力，不能把最后一句或多数意见当决定 |
| 评审意见回流 | 意见类型、针对版本、对象和决定权限 | 只在仍对应当前方案的范围内应用；过期或含糊意见先澄清 |
| 用户已手改部分文档 | 修改意图和依据，哪些部分已经正确、哪些关联未同步 | 保留有效手改并补齐关联；涉及业务的新意思回相应真源，不重生成覆盖回旧稿 |
| 多源同时变化 | 同一件事的互补、重复、矛盾或不同适用范围 | 按来源职责和明确决定定有效解释，不能以时间最新自动压过其他来源 |
| 未决事项得到答案 | 哪些假设、备选分支、风险和验收因裁决改变 | 替换当前相关说明，保留决定来源；不把其他未决顺带定案 |
| 已定规则改变 | 隐含影响，如次数/期限改变对入口、状态、提示、接口、验收的影响 | 沿完整业务关系推演；没有相同词句的下游也要核 |
| Plan 在途或已完成 | 哪些设计有独立依据，哪些依赖已失效要求 | 保留有效设计，更新受影响契约/用例与知识落点；不整体重做 Plan |
| 来源无新差异但上轮没改完 | 变更是否已在全部相关位置落实，旧待办是否仍有效 | 沿原未完成事项续修；不能因摘要相同直接退出 |
| 已到编码/测试 | 哪些实现与证据可能失效，本命令允许处理到哪 | 更新已有文档至 Plan，明确代码/测试影响和修正入口，不宣称整需求重新通过 |
| 只有表达变化 | 改的是措辞、组织还是隐藏地改变了业务含义 | 真正纯表达不改业务决定；保留已有结构保护和人工原话 |
| 部分材料不可达/缺旧基线 | 当前可判断范围与不能证明的历史事实 | 能独立完成的部分继续，依赖缺口的内容明确停在何处，不一律全停或全报成功 |
| 中断、重试、重复意见 | 哪些决定/修改已生效，哪些还没做 | 从实际材料与已有说明恢复，不再重复裁决、覆盖人话或重复归档 |
| 系统正文已经是旧 Story | 这是自己发布的输出、评审改稿还是原始上游 | 先辨来源角色，不能把自己派生的结论重新当权威输入 |

## 4. 模型的工作方法与阶段内输入输出

这六个动作是同一次 update 的认知顺序，可因补料或裁决回到相关动作；不要求六份文件、六次模型调用或六个人工关卡。用一份可恢复的 update-notes.md 保留当前判断和去向。

### 4.1 还原当前有效依据

读取用户当前请求、已有来源说明、有效决定、当前 Story/Review/Spec、已有 Plan 及本轮相关知识决定。区分材料原文、人的结论、模型假设、当前产物表达和历史送审版本；同时确认哪些阶段有产物、哪些已闭环、哪些在途或待处理。

先从已有分析与当前版本取得理解，再回查涉及变化的原文上下文。旧分析可复用，但不能替代有冲突的原话；不要无变化重做全仓探索。比较版本缺席时，明示证据不足，不补造“原来怎么写”。

产出：简短说明当前需求做到哪里、变化前采用的关键解释、相关未决与既有修改。它是供后续判断使用的工作上下文，不重新撰写一份全量 Spec。

### 4.2 解释变化，而非搬运 diff

对新材料、意见、直接编辑和上轮未完成事项，回答：表达的是哪件业务事、相对当前依据改变了什么、有什么没变、是否已经落实、是否与既有决定冲突。

对看似删除的要求先核来源去向；对“同意/通过”先核具体议题和版本；对手改稿先核意图。明确的新用户决定已构成裁决时引用它，不为“改变旧决定”再问一次同样的问题。

产出：按实际业务主题组织的变化解释及依据位置，可以合并同义输入，也可把一段话拆成几件不同影响；不要求一文件差异对应一条语义变化。

### 4.3 推演影响与保留项

以变化的对象或行为为中心，沿前置→动作→结果→责任→异常→验收检查上下文；再看已有设计如何实现它、知识要求是否因此命中/不再命中。对于新发现的受影响关系继续核，直到每项变化在已有相关产物中有去向，或明确留下待决/不适用/下游交接。

依赖由模型结合真实材料判断，不新建通用依赖图、不用同词命中代替。影响范围可以局部扩大到必要关联，但业务 Scope 扩展仍按已确认权限问人。列出重要不变项及为什么不需改，避免“优化一处、损坏另一处”。

示例：时限变化不只替换一个数字，还可能影响何时允许操作、提示、接口拒绝条件、异常路径和验收；只有现有材料证实存在的关系才同步，不能为“全链完整”虚构这些能力。

产出：按业务主题说明要改/保持/待定/交接的内容和真实落点，粒度以执行者能改及读者能核为准，不先冻结一份不许变化的文件白名单。

### 4.4 处理真正需要人的决定

只有现有权限和依据无法确定的事项才问：来源冲突、含糊意见、对既有承诺的新选择、范围扩展或大幅重组。每项给原解释、新信息、可选处理及后果和建议；能在同一轮说明的集中呈现。

人的决定限定到具体事项及当前输入。来源变化使旧人签失去适用性时明示；不因复用同一议题编号就沿用其勾选。仍未决的事项保留对相关内容的约束，不阻止独立且已经明确的修改。

产出：实际人话与落点/未决边界，沿已有决策渠道记录。说明中引用这些记录，不另造“人工已批准=true”自证字段。

### 4.5 修订最早责任内容，并同步关联产物

| 内容层 | 模型动作 | 保护 |
|---|---|---|
| 外部原始材料 | 保留取得的版本及来源，更新本地采用的材料版本 | 不替上游重写原话来消除冲突 |
| 初析/AR 提取稿 | 修订本需求对来源的理解与承载边界 | 未变范围和人签复用；无必要不重做初析 |
| Spec/验收/决定 | 修订需求真义、可观察条件、有效与未决结论 | ID 有语义连续性才保留；不能只改叙事不改真源 |
| Story/Review | 用当前有效解释更新相关叙事/图/议题，保留人工意见语境 | 不覆盖有效手改；旧表态不移植到变义问题；当前稿与历史送审稿分清 |
| 既有 Plan/契约/用例 | 调整因本次变化而失去依据或需要补齐的设计 | 不重写独立有效部分，不自动推进 coding |
| 尚未生成/本次无权修改的下游 | 说明后续需要承担什么及原因 | 不生成不存在的新阶段产物，不冒充已落实 |

原材料与生产真源的修改分开。接口/验收/知识等确定性投影继续由既有脚本产生；不用模型编辑派生区来迎合检查。

### 4.6 按关系核对结果，说明能否继续

从每项有效变化回查已修订内容，核正常/受限/异常及验收是否一致；从未变的重要关系检查是否误伤；从待决事项检查是否仍保持待决。再核阶段结构、引用、编号、投影与必要原生重验。

回查不要求字面相同，也不把旧稿全部保留当守恒；已明确取消或替代的内容应退出当前版本，历史留在备份。没有新增变化但有未完成同步时继续核，不按文件摘要提前判结束。

产出只有一份当前 update-notes.md，说明 §1.1 的实际结果、依据、已修订与保留、未决/缺口、检查与下游影响。向用户展示业务变化及可查差异，不暴露不帮助其决定的脚本步骤。

## 5. 不同进展如何影响工作

| 当前进展 | 默认行为 |
|---|---|
| 只有材料或提取稿 | 更新已有解释与材料，不顺带生成 Spec |
| Spec/Story/Review 已有 | 围绕有效变化核对并同步；缺少本来应有的产物时报告事实，不用自动推进掩盖 |
| Plan 在途 | 修改已有受影响设计，说明其余仍在途；不将文件存在当完成 |
| Plan 已闭环 | 修改相关设计/契约/用例与知识承接，再按原生修正机制重验 |
| 已归档 | 保留旧送审依据，更新本地工作稿；人确认后才回写 |
| 已到代码或测试 | 文档同步至已有 Plan，标明实现/证据可能失效及接手动作，不自动改源码或设备测试 |

update 的范围由本轮请求、实际变化和未完成关联决定，不默认开展全需求质量翻修。若核对发现无关旧问题，记录并交相应责任；确实阻碍本次结果正确性的旧问题纳入本次必要修正并说明原因。

## 6. 交付给模型的最小上下文

入口先交付：当前需求位置、可取得材料与失败项、当前请求、既有决定/未决位置、已有产物与阶段事实、可用的取材/备份/成文/验证操作。仅在需要理解时，由模型按 §4 读取相关原文并决定需要补读什么。

update-notes.md 在原过程目录保存本轮工作说明，使用“当前依据、变化与影响、决定与修订、核对与剩余”四个自然段落主题即可；复杂需求可以按业务主题分节，不强制 JSON、行数、逐差异编号或逐项形式配额。中断后读它和实际文件继续；说明与事实不一致时以原文、真实人签和当前文件核实，不盲从旧摘要。

phases/update.md 承载本章方法；SKILL 只路由入口和权限边界，原始材料/知识不复制进方法。测试、维护设计和同源示范不进入消费模型上下文。

## 7. 脚本只支持可确定的工作

### 7.1 最小职责边界

保留：只读 fetch、完整更新前保留、实际文件差异、既有导入/成文/人工区保护、操作恢复、适用结构检查、归档确认。

变化解释与影响保留为模型的可读工作说明，允许把同义输入合并、把复合事项拆开。脚本不要求语义与文件差异一对一，不把说明冻结成额外接受关卡。初始 Spec/Plan 沿用现有版本与证据，不因 update 新增强制基线动作。文件摘要提供线索与版本绑定，不作为业务影响或无需修订的判定。

### 7.2 文件支持合同

沿 story_flow.py 单一入口新增局部 update 支持，内部只需 prepare/status/close/restore 四个动作；实现集中 core/flow/update.py，不增加独立阶段引擎。

| 对象 | 作用 |
|---|---|
| story-flow.json.update | 定位当前操作及最近关闭记录；不保存另一份需求完成结论 |
| updates/<id>/record.json | 脚本生成的 id、时间、文件清单/摘要、备份位置、操作 open/closed/restored、检查引用与实际发布结果 |
| before/、incoming/、after/、diff/ | 本轮完整旧镜像、暂存外部原件、可复用的比较内容、实际差异。after 只在现有版本不能提供旧内容时保存比较集合，不再复制整份交付目录 |
| updates/<id>/update-notes.md | 模型的当前依据、影响、决定、核对及剩余；下游读它和当前业务真源 |

prepare 负责 §2 的镜像、只读取材和文件差异，返回无变化/有变化/比较不完整/需续办的事实及相关位置；无变化分支由它清理本次临时副本，不新开语义工作记录。status 报已有操作事实及说明位置。close 绑定当前说明、文件摘要与实际检查，只记录本轮处理结果，不判语义正确，也不自动发布；比较基准是否可推进按 §2.1 的已处理条件。restore 先保存当前现场，再恢复本轮修改范围与缺席状态，检测到外部编辑保留双方并报告。

已有原生备份/材料版本、前次 update 的比较内容用于对比；只读比较内容不另设语义基线审批，也不向初始 Spec/Plan 增加必停点。首次没有旧版本时不能判历史无变化，完成当前核对后建立以后可用的比较依据。日志、临时镜像、操作记录与报告不进入业务差异集合，避免每次检查都因自身写入被判有变化。

每个脚本保留必要失败语义：读取不可达不等于无材料，备份失败不开始写正本，写入失败说明已生效部分，关闭前保存实际差异。路径限制在 feature/指定 incoming，拒绝越界和链接；本版单写入者，不承诺自动合并并发编辑。自然语言说明只能支持模型判断，不能替代脚本对真实字节/路径的检查。

### 7.3 只读取材

新增 adapter fetch <编号> ... --out <incoming>，一次取得关联上游与评审内容，保存清单并输出结果；清单标真实来源身份、版本/摘要、原件位置、存在/缺席/失败。只写 incoming，不直接覆盖当前 Review 或 AR/design。本地单明确不适用，不取 token、不访问系统。

原 init 不覆盖已有文件，不能假充刷新；旧 review 会覆写当前稿，不能作为 fetch。业务目标 adapter 按公开合同升级，Demo 不覆盖目标实现，缺能力明确报告。

archive 实际发布摘要与历史版本帮助识别系统 AR 正文是否为自己输出；语义不同或身份不明由模型回查历史/来源，有实质歧义才问人。不能用摘要不同自动升级为新上游，也不能假设全部系统改稿都是有效新要求。

## 8. 与当前生产链衔接

### 8.1 成文与人签

在已备份的 update 上下文中复用 reopen/complete/story；路由不回到 init 的必停材料/范围关卡。模型说明哪些旧决定仍适用、哪些已有新裁决；必要人签通过既有 decide 入口**新增 update 分支**记录真实原话。当前代码没有该分支，新增及接线计入 C2；它不扩大 init 的关卡集合，也不按 update-notes 里的“已确认”字样制造人签。

使用现有骨架/草稿/chapter 修改受影响部分并重新登记，保留 project/number/build/check 的确定性职责。只更新实际已有产物，不为调用 cmd_story 自动创建新阶段。

同一议题意义保持才沿用 ID 和人工区；撤销/变义时旧意见及其原语境可查，新问题不携带旧勾选。对正文手改先理解并接回真源，再渲染合法机器区；不能要求用户删除正确内容才能过门。

### 8.2 检查、独立审查和继续工作

先完成本次要修订的业务产物、决定、图表、投影及既有检查，再按真实修改原因走 correction-init/revalidate。**普通局部 correction 沿用既有不自动重审路径；用户主动启动的 update，对实际修订的阶段使用既有 verifier 审当前材料。** C3 在 update 入口及阶段指令中明确这两个适用场景，不把“代码没有禁止”本身当作用户授权，不新增审查者或另写一套审查判据。

派审条件：本次确实修改了该阶段供评审/后续工作使用的产物或业务依据，原生脚本 PASS，当前宿主/阶段 verifier 启用且本轮 summary 有请求。同一当前 subject 已有有效 PASS 时复用；无变化快速退出、核对后未修订、仅不影响内容结论的过程记录变化不派。不能只按文件名判断“过程记录”：改变有效决定或审查依据时仍要核实际影响。

正常路径按阶段依赖先 spec 后 plan：
1. revalidate 后读取该阶段当前 summary 的 verifier_subject_id、verifier_request、verifier_report；判据是当前证据与 summary.verifier_closure，不是一个假定存在的 summary.semantic_not_reverified 字段。该标记实际在重验账本的 results.flags 中。
2. 当前材料沿用历史 PASS（verifier_closure.mode=completed_with_prior_review）或缺本次有效报告时，把**当前请求 JSON 原文整段**交既有 verifier；保持被审材料不变，等待原样回复。
3. 回复原样写到当前 summary.verifier_report 指定位置，执行既有 --sync-closure --phase <阶段> --feature <编号>（或对应 check-receipt），不手改 summary、回执或历史标记。
4. 确认当前报告 subject 匹配且 verdict=PASS、blocker_count=0，闭环检查成功，当前 verifier_closure 不再沿用历史。仅闭环 exit 0 不足：报告缺席时框架可沿用历史 PASS，update 必须识别这条错路。
5. 再处理下一受影响阶段。若上游返修改变了下游材料，先完成必要同步和原生检查，再用最新请求；不能投先前已经失效的 plan 请求。

正常首次修订稿每个改动阶段一次独立审查；不设“整个 update 最多一次”的硬上限。当前报告 FAIL/无效必须处理，不能回退历史 PASS。BLOCKER 返修导致材料变化时重新生成适用请求再审；同一材料已有 PASS 不重复派，纯风格建议不为追求完美触发新轮。同类错误不收敛按既有维护反馈规则处理，真实新增轮次与原因计入性能。

阶段报告与 receipt 不在通常审前材料中，业务正文、决定及被纳入材料视图的 update-notes 在派审至同步闭环之间不得变化。审查结果直接以既有报告/回执和操作记录引用呈现；不要为写一句“已审”修改刚审过的正文再造成对象漂移。是否被纳入以该轮 material 视图为准，不能只核源码 worktree_digest。

两处标记性质不同：`revalidation.json` 的 `results.flags` 是重验当时的历史账，不手工改绿；summary 的 `readiness_signals` 里的 `semantic_not_reverified` 由 framework 收口器（`phase-closure-finalizer.ts:645-656`）每次收口先清除、仅当闭环仍沿用历史 PASS 时加回，所以 sync-closure 之后它应当消失，没消失就是当前报告没有被采纳。是否已经审查按**当前 subject 的有效报告与当前闭环**判断；这条「信号应消失」同时作为 C3 接线验证的判据。在 update 结果里注明后续审查的实际报告，必要文案改进交上游。

verifier 未启用、缺当前请求或调用失败时，如实报告当前不能完成独立审查；不补造请求、不把自审当独立审查，不宣称当前更新已审查通过。未闭环的已有产物仍按其原生适用流程检查/派审，不因 update 自动推进新阶段。

原生 revalidate 可能延伸至已有代码/测试报告，无限定结束阶段选项。越出文档更新权限时交接原生修正流程，报告当前可继续范围及下游待验证，不能自动开始代码/设备工作或伪造回执。两正式 Case 只有 Spec/Plan，按实际改动的适用阶段核验和审查。

### 8.3 回写

先展示当前业务结论、差异、未决和验证缺口，再确认是否回写当前版本；版本又变则重新展示。仍有明示业务未决的待审稿可以按已有交付门送审，但未完成必要同步或检查的稿件不能以操作 closed 放行。

外部发布结果单列，失败保留本地正确修改，重试前核外部是否被他人改过；不重新执行整套理解/成文。正常 archive/restore 保留，不新增平行发布系统。

## 9. 实施步骤：模型能力先可审，再接生产路径

### C1：交付识别变化与推演影响的方法和输入

在 phases/update.md 写 §1–§6 的快速检测、作者方法与场景边界；入口任务能取得当前请求、有效决定、进展、源材料及失败项。接只读 fetch 和 prepare 快速检测、临时镜像及无变化清理，复用 registry/原版本/普通 diff；公开旧 review 暂保留，update 尚不作为完整交付入口。

交回中性场景走查：手改部分文档、上游删除但含义不明、旧版本评审、新决定改变隐含关系、没有新差异但上次未同步。逐例列“实际输入→模型要判断什么→应改/保留/问什么→允许的不同结果”。这是设计语义审查材料，不伪装已跑模型效果，也不把答案写入生产提示。离线核取材/比较/保留/任务送达，尤其无变化不进入语义流程、启动前手改不漏检、失败不误判无变化、本次临时镜像清理不触及历史备份。

### C2：把模型判断接到关联修订与核对

接 update 上下文中的现有重开/决定/章提交/人工保护/原生检查；实现 status/close/restore 和实际差异。用户修改、已有 Plan、未决和历史意见不因重新渲染丢失；update-notes 为模型恢复与下游提供当前理由，而非新的业务真源。

交回正常与异常文件链、人工区/关系保持的来源对照、未完成结果的明确呈现及恢复证据。不能以脚本验证说明“每个变化已有一行”为语义验收。

### C3：统一入口、回写和退旧

四桥接/SKILL/help 启用 update，plan 作者读取最近更新说明及当前 Spec/决定。删除独立 review 入口、adapter review.js、review_reflow.md 及旧 review-disposition 常驻读写；其有效意见语义完整进入 update。历史原件首次需要时读取并保留，不再维护双台账。

测试消费者同步：test_harness.py:921–931 的 STORY_REVIEW/旧台账终点断言迁移到 T1 新完成事实；test_story_build.py:336–344 以旧台账作例子的两条测试改用当前有效过程文件或中性辅助文件，**保留“AR 根目录只放交付件、过程目录允许辅助件”的通用回归**，不整类删除。run_case.py:467 的旧终点由 T1 退出；C3 交回列明这项仍在测试域的过渡消费者，版本最终交付前必须移除。

核目标 adapter 接入、正常 init/archive/restore/local 行为、外部确认及失败重试。C3 将 phases/spec.md:67–75 的适用范围写清：普通 correction 不自动重审，用户主动 update 按 §8.2 处理实际改动阶段；B1 不提前改这段分流。同步 update 入口、四桥接的动作授权说明及所有会被执行者读到的实例指令；若现行根入口把不重审写成无条件禁令，按其物化来源/既有扩展入口修正适用说明或交上游，不靠下位提示静默盖过。C1/C2 的过渡旧入口在此退出，不留永久 review 别名。实际模型效果由 T2 的同一批两 Case 判断。
