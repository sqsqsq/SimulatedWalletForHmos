## 1. 当前结论

接受 §8 的核心修正：**revalidate 不自动派 verifier，不等于当前材料无法独立审查。** 框架现有请求、报告和闭环接口可以承接；C3 让用户主动 update 对实际改动的适用阶段使用当前请求派既有 verifier。此前“必须接受无独立审查”的判断依据不充分，已从 spec/design 撤回，不再交用户接受这一常态限制。

预算仍须 C 开工前按接线事实核定。F2 的一律 open 判据已被评审者收回，继续按真实来源判结论；A1 可先推进。这里的“可推进”不是本次已经开始实施。

## 2. §8 的源码与离线核验

| 要点 | 实际证据 | 结论边界 |
|---|---|---|
| revalidate 后请求生成 | harness-runner.ts:1830–1841 条件为 verifier enabled 且脚本 PASS；issueVerifierRequest:2014–2050 写请求与报告位置，无“此前闭环即不发”条件 | 不是所有阶段都有请求；不能忽略 adapter/policy 或脚本失败 |
| 当前报告优先 | check-receipt.ts:703 起先 load 当前证据，仅 report_missing 时找历史 PASS；:738 起当前 FAIL 阻断 | 请求/报告错位不能靠历史 PASS 证明当前已审 |
| 当前 PASS 清除沿用模式 | check-receipt.ts:1158 将 verifier_closure 写为当前推导；verifier-evidence.ts::deriveVerifierClosureRecord 当前证据存在时返回 null | 还必须验 verdict=PASS；null 本身不证明通过 |
| 已闭环也会重新核回执 | phase-state.ts::runSyncClosureDetailed 先 tryValidateReceipt，再 finalize；失败分支回写未闭环状态 | 不只读旧 closure_status |
| 字段位置 | revalidate.ts 将 semantic_not_reverified 放在 revalidation.json results.flags；当前 summary 的对应事实是 verifier_closure | 不能按不存在的 summary 顶层字段派发 |
| 历史日志 | revalidation.json 与 summary 的 script_revalidated 消息不会被后续 sync 全部改写 | “信号消失”应限定为当前沿用模式，不手动改历史文案 |
| 材料身份 | verifier-material.ts 读取实际阶段材料及上下文，通常排除报告/回执；worktree_digest 只覆盖配置的产品层 | 除源码摘要外还要保证本轮业务材料不变 |

实际运行了一项临时离线诊断：`scratch/review-194-verifier-evidence.cjs`，只导入真实框架的 evidence loader / closure derivation，在独立 scratch 根创建协议夹具。结果 5 项通过：

1. 缺当前报告、有旧 PASS → report_missing，派生 completed_with_prior_review。
2. 当前 subject PASS → 当前证据有效，沿用记录派生为 null。
3. 当前 subject FAIL → 返回 FAIL，不退到旧 PASS。
4. 在当前路径写旧 subject → subject_mismatch，不退到旧 PASS。
5. 只写旧报告路径、当前路径缺席 → 仍沿用历史，不能当已完成当前审查。

诊断结果文件：`scratch/review194-verifier-rj6Bxk/result.json`。这些用例只证明确定性证据读取/派生，不证明模型判断力；没有运行完整 revalidate→真实派审→sync 闭环。C3 必须在隔离 fixture 补完整接线，不能用 test_verifier_chain_in_workspace 仅检查模板随包的旧用例代替。

## 3. 采纳时补足的边界

- **正常路径一次，不是返修硬上限。** §8.2 的“每次 update 每阶段最多一次”改为正常修订稿各一次；当前 FAIL/材料返修必须按新请求再审。同材料已有 PASS 不重派，风格提醒不触发重复派审。符合既有不写死返修次数约定。
- **原样请求与报告。** 用当前 summary 路径，不能自行拼 subject、复用旧文件名或拼接修改回复。错误路径和当前路径错误回显是两类不同失败，离线分别覆盖。
- **已有授权与指令范围要一致。** C3 明确主动 update 含改动阶段审查，普通 correction 保持原路径；同步执行者实际读取的入口/阶段说明。不能只说“代码没拦”就忽略适用指令，也不改 framework vendored 实现。
- **先完成材料再审，按阶段依赖处理。** spec 返修影响 plan 时，先同步后再取得最新 plan 请求。审查期间不写材料，结果引用现有报告，不为补一句“已审”改刚审过的正文。
- **能力缺席不是通过。** 当前宿主/阶段无合法请求时如实报告审查未完成或原生不适用，不生成影子请求、不以自审替代。正常已登记宿主不再背负“必然无独立审查”的设计限制。
