# 需求 A：Story 表达优化

对应 S-EXP、D04–D07、AC01/AC02。本文是这个需求的完整实施方案；它只是 1.9.4 的一部分。只有一个实施步骤 A1，独立于缺陷需求交回。先读[版本总览](00-整体设计与实施总览.md)，对齐成品时再读[同源示范](参考/02-同源成品示范与保持核对.md)。

## 1. 问题、事实与本次决定

用户指出的问题是长文过多、层级单薄、表达生硬。增加图型数量不能直接解决它们：作者首先需要知道如何分组信息、选择关系的表达、解释前置和例外，再使用对应语法。

已核 writing-plan.mjs 支持父子小节与同位置多个 forms；chapterSeedRows 将骨架的 ####/##### 转成正文 H3/H4，并交付 notes；DIAGRAM_SYNTAXES 已有八类。七项现有离线测试通过，支持复用这一结构链，不能据此声称阅读质量已改善。

本次决定：保留十章职责与必需的表/编号/投影，改作者组织方法和实际任务送达；只有已核实的送达缺口才改脚本。图形按读者问题分类，不以渲染器支持列表作默认菜单。不新建可视化 Agent、事后重写 Skill、Markdown 引擎或第二份事实台账。

## 2. 成品的阅读组织

成品同时提供三个阅读深度：先理解本次改变、参与者和整体方案；再按业务能力/阶段理解行为；最后查验收和精确合同。三层贯穿现有十章，不另增三个固定章节。正文里的关键条件不能通过链接或折叠藏起来。

| 章 | 读者首先得到什么 | 展开方式与保持项 |
|---|---|---|
| 背景 | 当前问题、本次改变及价值 | 具体结果先行；现状/目标确有可比维度才列表，不画装饰图 |
| 术语 | 核心对象的同名同义 | 保留术语表；确有归属关系可画业务关系图，不塞完整功能规则 |
| 范围 | 本需求、协作方和不负责的边界 | 责任表或参与方边界图；保留兄弟需求/跨方交接，不冒充运行流程 |
| 业务方案 | 整体做法、结果权威方和理由 | 角色协作、数据流向、真实方案差异与风险；不按接口顺序抄 Spec |
| 业务流程 | 从触发到主要结果的路线 | 总览给主线和分流入口；局部展开分支与跨方时序，去向用可定位业务名 |
| 功能说明 | 每项能力怎样使用、何时受限 | H3 分能力/对象，H4 分实质子过程；条件组合用表，生命周期用状态图 |
| 异常与恢复 | 失败位置、责任、可观察结果及恢复 | 正常受限与异常分开；复杂补偿局部展开，不重复抄主流程 |
| 验收 | 怎样独立判断已定义行为成立 | 按业务场景分组，上游编号独立一行，条件/单位/结果不丢 |
| 交付与上线 | 依赖、开放、关闭和恢复安排 | 保留交付物表；有顺序用依赖图，有真实日期才做时间排布 |
| 附录 | 精确接口、数据、配置、知识判断及来源 | 真源投影不手工复制；解释查阅方法，不能接收正文漏掉的关系 |

### 分节的执行规则

作者先列本章需要解释的对象、条件、行为与结果，再按同一能力或依赖顺序分组。两组有不同前置、规则、结果，或读者需要单独定位时成为同级小节；只是同一对象的几个属性时用表/列表，不每属性建标题。

H3 使用可识别的业务能力或阶段名；H4 展开其独立条件/过程。标题说实际内容，如“提交后查看进度”，不写“能力承接”“机制闭环”。每节先给结果或核心规则，再解释关系、条件与理由。父节已经完整列出的同一组属性不逐行复制成子节。

完成的可读标准：只看标题能理解路线；读单节知道谁在何种条件下做什么、结果怎样；图表周围文字提供缺少的依据/边界。标题数、字数、图数、固定深度均不是门禁。

## 3. 表达选择：先选用途，再选载体

| 读者需要判断 | 作者应采用的表达 | 当前载体/条件 |
|---|---|---|
| 主路径及条件分流 | 业务流程图 | 既有 flowchart；只画有依据的分支 |
| 谁调用谁、谁返回、谁补偿 | 时序；必要时按责任分泳道 | sequenceDiagram 或 flowchart subgraph；标明箭头含义，保留失败责任 |
| 一个对象的状态与允许动作 | 状态图＋动作/权限表 | 既有 stateDiagram；不能把一个按钮点击虚构为新业务状态 |
| 参与者边界、数据从哪来/到哪去 | 边界图、数据流示意 | 已有 flowchart 分组；数据名与方向有来源，不等于数据库设计 |
| 多条件决定不同结果 | 决策表 | 普通 Markdown 表，不新增图语法 |
| 方案/更新到底差在哪 | 同维度对照表、局部差异图 | 方案说明或更新结果使用；当前 Story 正文仍清楚呈现有效结论 |
| 一组能力怎样分解 | 有层次的标题/列表或浅业务树 | 简单时不用 Mermaid；不搬实现类/文件树进主叙事 |
| 过程里的页面是什么样 | 原型原图、状态对照和简短说明 | 必须有真实素材，沿现有图登记/取舍，不生成虚构 UI |
| 线性步骤、并列要素、取舍依据 | 有序列表、无序列表、短叙述 | 不为每段硬画图；强调只标关键条件/结论 |

类图、数据库 ER、带评分的旅程图、精确甘特与装饰性思维导图不列为常用推荐；确有业务需要和来源时可以使用。这里调整作者选择，不删除既有解析支持、不缩小合法表达空间。Markdown 扩展、HTML/折叠或交互不作为本版新依赖。

### 总览、局部、图文的关系

总览呈现主线和主要分流入口，复杂分支在对应局部完整展开；不能将所有节点挤在一图，也不能为了简洁漏掉分支。总览与局部采用一致业务名，局部结果能接回主线。

图讲最难用线性文字解释的关系；表讲条件/属性；图旁文字补理由、前置和未决。逐箭头复述没有新信息时删去；验收独立成立所需的关键条件、数值重现保留。

上游图可原用、增强、拆分或重组。每张承接图保留相应来源标记，原来的角色、返回、条件、失败归属在全部承接内容中仍可找到。一源多图、多源合图都合法。脚本核真实来源与承接存在；独立审查核内容，不能以字节相等或一对一图数代判。普通原型图片仍执行原图登记规则。

## 4. 如何让模型在正确时间拿到方法

| 时机 | 输入 | 执行与输出 | 失败处理 |
|---|---|---|---|
| skeleton 首次 | 来源、Spec、有效决定；本节方法 | 空壳提示读者主线与各章分工，作者写 story-template | 材料不可读先报具体缺口，不先补想象内容 |
| 作者设计 | 当前完整事实 | 用既有 -答/-依据/-描述/-待核，说明每节要回答什么，图表与文字各承担什么 | 业务未定留在相应边界和决定，不为完成骨架定案 |
| skeleton 再次 | 作者骨架 | notes/forms 铺到各自 H3/H4 草稿；不生成图中业务节点或表格答案 | 结构错误一次指出；合法新节不当上限违规 |
| 写章 | 对应来源、已写关联章、草稿 | 以完整业务关系组织自然说明，提交相关章；可调整骨架表达安排 | 业务变化回真源，表达变化用既有调整记录，不加审批 |
| 原有回看 | 原材料与整篇成品 | 先核内容保持，再按阅读路线处理混段、重复、层级与生硬句子 | 修最早出错处，不新增另一轮全文优化流程 |
| 原有 verifier | 实际正文、依据、决定、写作安排 | 内容错误阻断；纯风格建议指出具体位置和理由 | 按框架既有闭环执行，不为偏好重复派审 |

方法正文唯一放 story-write.md；章节职责仍在 story-chapters.json，脚本消费。维护示范、GitHub 调研、测试答案不进入消费模型上下文。ELI5/show-me 可借鉴的是分层解释与问题驱动选择；不照抄其对话篇幅限制或让 Story 的完整要求等用户再问。

## 5. A1 的文件动作

表中 skills/、hooks/、rules/ 路径相对 doc/extensions；core/ 是 doc/extensions/skills/story/scripts/core/ 的缩写；测试相对 test/story/tests。新方法的唯一正文仍是 story-write.md，不新增另一份生产表达合同。

| 文件/符号 | 动作及退出 | 保留 |
|---|---|---|
| skills/story/phases/story-write.md | 按本方案替换读者/设计/写章/图承接/回看方法；删“可改画”与“一律原样搬入”的并存，删默认所有分支塞总览 | 现有材料读取、决定、章提交、归档自包含边界 |
| skills/story/contracts/story-chapters.json | 05-flow questions 明确总览＋局部承担完整分支 | 十章 ID、职责、structure.diagram、验收/术语/交付表合同 |
| core/story/writing-plan.mjs::writingPlanShell | 用现有语法说明阅读主线、各节解释任务及图文互补 | readWritingPlan、selectedStructure 不扩成语义评分器 |
| core/story/chapter-contract.mjs::chapterSeedRows、drafts.mjs | 核父子 notes 和多 forms 送达，只有实际缺口才修复 | 当前 H3/H4、结构选择与正文可扩展行为 |
| core/story/sources.mjs、hooks/shared/reader-review-task.mjs | 核多图承接的来源枚举；消除与改画规则冲突的提示 | 真来源检查、普通图片登记、源与成品并列 |
| rules/spec-rules.overlay.yaml::story_reader_review | 核事实/关系保持与具体阅读问题，风格 advisory 非阻断 | 独立语义审查、严重错漏阻断 |

Review 同步改善其机器区说明：业务对象明确、选项后果真实、建议依据具体；保留 choice/confirm 填写合同和人工原话。跨更新的人签有效性由需求 C 承接，A1 不提前实现另一套 Review 更新器。

## 6. A1 验证、预算与交回

针对已有 test_writing_plan、test_chapter_view、test_writing_flow、test_story_build、test_evidence_delivery 验证父子位置、同节多形式、必要表只播一次、可补小节、改画承接与人工区保护。已通过的七项现有测试是复用证据，不是新作者方法的效果证明；改动后只补有区分力的测试。

交回 shell→已填骨架→草稿→章提交的实际离线产物，指出每条新方法由谁取得。按同源事实人工核改写内容，证明没有为了图更完整增加规则。示范只对齐预期，最终效果用两个 Case 的初次和 update 后成品观察。

完成条件：上述接线和旧冲突指令退出；合法原能力不回退；离线针对验证通过；实际新增/退出在[预算表](参考/03-职责交接与预算依据.md)登记。A1 可以交回，但不能宣告整个 1.9.4 完成，也不追加真实 CLI。
