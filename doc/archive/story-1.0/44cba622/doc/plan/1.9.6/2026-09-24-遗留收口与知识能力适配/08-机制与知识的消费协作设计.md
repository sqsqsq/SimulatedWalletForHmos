# 机制与知识的消费协作设计

2026-09-24，维护设计者。依据用户对三者关系的纠正，以及已确认选择：知识可以讲项目方法的应用步骤、选择依据、例子与完成判断；机制负责何时交付、当前任务怎样使用、结果进入哪个产物和下游。用户要求选择正确的设计，不以少改文件为目标。

本文为交给维护实施者的方案，维护设计者只修改方案并评审。本文统领知识编写、阶段消费与 adapt 生成的协作；[07](07-上报知识应用组织优化方案.md)作为 reporting 的贯穿样例分册。原 S3 确定性返修继续有效，已通过的实施与历史证据保持。本次没有直接修改 Extension、知识正文或脚本。

## 1. 要解决的根因与完整目标

现有机制能列知识、登记适用、投影义务，但“交付了入口”并不等于模型知道当前怎样应用。现有事实知识多按字段、路径与能力分类，读者仍要自己拼接方法。adapt 的取证和登记可以生成形式完整的知识，却不能据此证明目标仓模型能用它设计与实现需求。

交付目标是一条完整使用过程：适配模型从目标仓形成可消费的知识；机制在任务决策之前交付相关入口和作业要求；消费模型据当前需求正确应用，产出可供下游使用的决定与契约；审查发现具体遗漏或误用，并回到对应责任来源处理。

被测模型不是知识的特殊读者。它与实际业务仓的消费模型遵循同一入口；维护测试只用于观察效果，不向交付内容写入测试答案或案例特征。

## 2. 三者的职责与写作归属

| 对象 | 写什么、做什么 | 完成结果 |
|---|---|---|
| 机制 | 当前阶段的目标、输入、知识读取条件、应用任务、产物出口与下游交接；格式、引用和当前状态的确定性辅助 | 模型知道此时为何需要知识、要借它完成什么、怎样识别还没完成 |
| 知识 | 项目概念与语义、已知事实、已定规范、适用条件、项目方法、依据、参考骨架和应用结果的判断 | 模型能据此在本项目形成判断与设计，能够识别不适用、建设差距和未知 |
| 消费模型 | 结合当前材料选择适用知识、核实必要事实、完成领域判断、权衡与设计，将结果写入当前产物 | 对本需求成立的具体行为、约束、接口、代码或验证，而非知识原文的回显 |

维护实施者负责把本方案落到产品；adapt 的维护模型负责在目标仓生成或优化目标知识，两者不是同一个职责。这里没有新增 Agent 或额外调度层。

内容归属按原因判定：

- 改业务仓就可能变化的概念、封装用法、字段含义、项目分配惯例、模式协作，归知识。
- 改阶段流程或文档布局才变化的执行顺序、命令、章节坐标、契约字段位置、派审与回流，归机制。
- 必须结合本次需求才能作出的节点选择、候选编号、具体接口与适用判断，由消费模型形成，归本次产物。

知识允许说读者和使用目的，也允许描述项目方法的应用步骤。例如“先确定一次业务尝试，再把实际结果映射到项目结果分类”可由知识解释；“在 Plan 哪一章填写、运行什么命令”由机制安排。应用知识的结果可以有完成判断，不能因它含有动词就判为机制内容。

## 3. 三类知识怎样叙述

先在现有 protocol.md 明确下面的编写方法。它是给维护模型的指导，不成为所有文件必须逐项填写的模板。

### 3.1 共同入口

每份知识的开头用短段说明它帮助解决什么问题、什么情况下需要读、能够帮助形成什么判断或设计、具体内容从哪里读。正文按读者的问题与使用过程组织，索引和字段表服务于这种叙述。

简单事实直接讲清即可；多步推导、跨对象协作或易误解的能力才提供应用过程与例子。参考例子需要标明适用条件和假设；完成判断应能指出实际差距，而不靠复述标题、术语或固定字数。

### 3.2 项目事实与能力

读者需要知道“是什么、解决什么、何时可用、怎样使用、结果意味着什么、有什么边界与依据”。按内容需要写：先解释语义与可用条件，再给入口/参数/返回及关系，随后给应用方法与参考，最后说明未知和核实位置。

保留现有 facts 类型。项目方法属于该项目能力的使用知识，不因此变成可选设计模式；可选的结构方案仍按模式管理。只是一条封装位置的事实不扩写成多章教程。

依据分为三种：当前实现由代码和配置证明；已定规范由项目协议、需求或负责人的真实决定证明；示例、候选或拟建设计说明假设和未落实部分。代码与“当前实现事实”矛盾时修事实；代码未达到“已定规范”时登记实现差距。不能统一用现有代码否定未来需求，也不能把规范写成已建能力。

确认与取证的具体接线：protocol 的 confirmed 定义按内容依据类型解释；Spec author 的 verified 提示、knowledge-use/document.mjs 的骨架注释和 validation.mjs 的报错同时接替旧“只写代码路径”的措辞。verified 仍是既有字符串，填写对应代码/配置或协议/需求/负责人确认记录的位置。保持未确认内容须取证的校验，不新增字段；模型与审查判断证据是否真实。部件画像当前代码结构的专项取证继续引用代码/DSL，不与业务规范的依据混用。

### 3.3 规约

保持一条一个可判断的要求：触发条件、义务、例外和验证清楚。读者易误解的边界可以附短例或业务解释，解释服务于判定，不另起一套长篇应用教程。

项目封装和参数规则引用对应事实；通用阶段处置由机制安排。保持约束条目与 must 的追溯，规约不复制实现知识。已撤销的逐步日志红线不恢复，已确认的基线强制力不扩大。

### 3.4 设计模式

以已有上篇/下篇为基础，核选型依据、角色协作、骨架、失效条件与验证是否帮助读者做实际设计。借鉴其围绕任务组织知识的能力，不强迫事实、规约套同样的分篇。

模式自身维护项目角色及协作方法；通用契约字段路径和阶段动作放机制的模式应用说明。迁移相关坐标时在原位置给内容级说明，在对应作者任务提供投影位置，避免删除坐标却无人接替。SDK 和模式本身的符号不是阶段坐标，仍留知识。

### 3.5 结构选择

保留 kind、条目 ID、模式角色、事实面与 confirmed 等有实际消费者的结构。facts 的每个 H2 仍是一面，未确认标记跟着实际内容边界；面内可以按问题用 H3、段落、图表和骨架组织。导读将各面串成阅读路径，不把所有知识固定成同一种栏目。

保留结构的原因是它承担确认和追溯，而不是为了省改动。若实施遇到实际内容无法表达的情况，交出具体内容及消费缺口，由设计者在同一步确定最小协议调整；不先构建任意文档树解析器或更换全部登记格式。

## 4. 机制如何组织一次消费

机制的常驻指令讲当前阶段任务；任务包交本次实际材料、知识入口和上游决定；知识提供项目方法。三处互相引用，不把同一套长作业复制三遍。

### 4.1 进入判断之前

作者取得当前激活知识的文件与类型入口，先阅读用途和适用条件，再按当前业务任务读取必要正文。规约继续按现有域/条目适用流程判断；事实与模式按实际任务选择。脚本不根据文件名、SDK 名或能力 ID 自动判断业务适用。

本次不新增阅读状态台账或机器推断的“已理解”字段。文件存在、路径列出、登记完整只证明这些机械事实；实际读取记录与产物变化用来复核是否发生了正确应用。

### 4.2 各阶段任务与结果

| 阶段 | 行动前交付 | 模型完成的任务 | 交给下游 |
|---|---|---|---|
| Spec | 业务材料、真实决定、知识用途及业务语义/选择依据 | 明确行为与业务结果，识别适用约束、现有能力、模式候选和真实未决；项目方法帮助形成业务设计 | 完整 Spec、知识适用结果、验收与未决；不只登记“用了哪份知识” |
| Plan | Spec 当前决定、已适用知识、项目实现方法/协议/模式参考 | 将已定业务逐项落实为实体、接口、状态、字段、调用责任和验证；候选有具体依据 | 可实施的 Plan/contracts/use-cases，知识义务附着于真实责任实体 |
| Coding | 已定契约及选定知识的实现参考 | 在真实接口与工具链下实现契约；遇契约缺口回责任来源 | 可追到业务决定与知识要求的实现 |
| Review | 本阶段实际产物、原知识、上游已定要求及本次改动 | 核语义是否正确应用、承诺是否成立、下游是否还须补关键设计 | 指向具体责任来源的发现和结论 |
| UT/Testing | 已定验收、契约、实际实现及必要项目验证知识 | 取得适用路径的真实证据，区分行为失败与环境未执行 | 与要求和对象版本相符的结果及未验证项 |

Coding 可以为理解已定契约查原知识，保持不重新改变适用结论和选型的边界。原“must 就是全部知识来源、不回看原规则”的过度限制改为“must 定本次义务，原知识解释方法与语义，代码确认真实接口”。

### 4.3 应用后的传递与异常

沿现有 knowledge-use、Spec/Plan 正文、must、files.pattern/role 传递结果，不另建统一的知识消费合同。项目方法中已形成的具体结论写在本次产物；下游承接这些结论，再读取其实现需要的原知识，不重新猜一遍上游选择。

缺事实时取证；规范与实现不一致时保留建设差距；缺业务决定时问人；知识足够但模型未完成设计时回流当前阶段。已经观察到错误理解时修知识叙述或机制任务的最早责任源，不靠追加“必须认真”等提醒。

## 5. adapt 怎样生成这样的知识

台账回答“本版需要哪些能力、哪些情况适用、缺了影响什么”，作为覆盖索引；它不决定每篇知识的正文目录。目标自有能力按同样编写方法接入，不以 Demo 的知识数量或文件划分判完整。

方法页在人定范围后交付以下写作过程：

1. **确定消费任务**：从目标仓职责、正常需求及现有知识判断读者将要作哪些决定。取一个正常业务作为检查对象，不要求为此新增测试系统。
2. **取证并分类**：查定义、实际调用、配置和业务协议，分清已有事实、已定规范、建设差距及未知。已有知识先识别与复用。
3. **形成叙述**：选择 facts/constraints/patterns 中合适的类型，按第3节说明适用、语义、方法和依据。复杂能力给贯穿参考；简单事实写直接说明。
4. **按消费任务走查**：读者能否完成原先要作的判断？能否给出下一步需要的设计？缺依据就补依据，缺应用关系就补叙述或例子，真缺决定就明确待决。不是按栏目是否填满判完成。
5. **登记与交回**：沿现有 capabilities、capability_decisions 和激活清单记录实际范围；交回知识改了什么、证据、能支持哪些任务及剩余影响。

中断恢复、用户选择、协议迁移与无 feature 校验继续采用 S3 已定设计。模型在目标仓写知识使用新编写方法，而不是复制本仓知识内容或由脚本生成同形正文。

## 7. 三步实施和推进

**A：编写与消费契约。** 先完成通用规则和阶段任务的改动，标清重复内容的接替位置。完成条件：用上报与另一类知识各走一遍输入→判断→产物→下游，读者不必自行决定谁负责解释、谁负责阶段推进。交设计者评审。

**B：知识和 adapt。** 完成 reporting 贯穿样例，修清单中实际存在的其他缺口；按新规则改 adapt 写作方法、台账走查和示例。完成条件：事实、规范与示意来源分清，两层设计能接续，目标仓能够按消费任务生成自己的知识。交设计者评审。

**C：验证和整版交付准备。** 按实际改动运行原有知识/作者/适配离线用例，保留确认状态与追溯。正常模型效果并入用户已定的整版最终实跑；不另外追加一轮业务 CLI。S3 现有 F1–F3 返修可继续，但 S4 效果验证与发布须同时包含本方案的新目标。

07中的三步是 reporting 子任务，计入 B/C，不重复计算流程或另开一轮测试。原00–04中关于知识职责、生成方法与效果判断的概括以本方案为准；既有确定性接口、迁移和测试安全约定继续按对应分册执行。

## 8. 验收与归因

| 验收对象 | 应看到的证据 |
|---|---|
| 知识本身 | 一个正常任务所需的语义、方法、依据和边界可定位；读者能形成具体结果，非只有关键词与字段 |
| 阶段消费 | 动作前取得必要内容，上游结论改变当前设计，下游取得足够信息继续 |
| reporting | Spec 说明指标/流程/结果，Plan 将同一结果落实到责任方法、身份/字段/时机/验证；共同事实可复用 |
| 其他知识类型 | 简单事实可直接用，规约可判，模式可选可落实；不因统一改造变成长篇重复指令 |
| adapt | 正常目标仓的知识来自自身代码与规范，按自身问题组织，并能支持一项实际设计任务 |
| 可迁移性 | 新业务名、其他语言及目标自有知识不要求机制增加专门条件 |

机械检查验证类型、登记、确认状态、引用和上下文交付；内容与效果由维护者及正常任务审查。构造坏格式只能证明脚本处理，不能证明模型理解力。

失败先核四件事：必要知识是否在决策前送达；知识是否足以支持当前判断；模型是否误用或未落实；审查是否漏判。根据证据分别修入口、知识、阶段执行任务或审查，避免每次都归咎模型没听提示。

## 9. 预算与范围控制

已知 S3 交回基线：机制13192有效行、知识616非空行、adapt747非空行；为交回实测，本轮设计未重新运行计量。原机制初始新增预算700及累计台账保留。

本方案相对当前实现的局部估算：机制说明与阶段任务新增约120/退出85有效行；知识新增约90/退出35非空行（包含07原估的 reporting 改动，不与07重复相加）；adapt 方法新增约45/退出20非空行；受影响测试新增约40非空行。对应局部完成估算分别为13227、671、772；先加后删峰值分别为13312、706、792。其他类别及原有运行器不预设新增。
