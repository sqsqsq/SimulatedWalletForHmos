# 1.9.8 首次知识的质量判据与 README 能力介绍

## Context

### 现象

内网首次适配已经跑通，三类知识都有产出，但交给维护者后不可用：
- 规约是一长串未经归纳的条目；
- 有的知识描述的是某个业务模块自己的实现；
- 项目事实写成了实现说明；
- 设计模式是模型自己归纳出来的，项目里并没有对应的承载结构。

### 根因

适配流程只规定了写哪些主题、写成哪种格式，没有规定一份知识「合格」是什么样。模型缺少四个判据，只能按「尽量写全」理解任务：
1. **范围判据**：什么内容够格进项目知识。
2. **初始规模判据**：适配产出的是起步集，不是全集。
3. **形态判据**：规约怎样归纳，项目事实写到什么程度。
4. **模式准入判据**：什么时候可以建立设计模式知识。

维护者评审时也没有同一套判据可依。

更深一层：即使有了通用判据，模型面对某一个主题时（例如安全隐私规约），仍不知道这类知识要替读者作什么判断、先收哪几条、一条写到什么程度、容易错在哪。现有指导只停在「三类知识 + 通用写法」这一层。演进记录的基线条目每条只有一行，不足以指导写作。

README 目前只讲怎样用、有哪些规则，没有一节向潜在使用者介绍它能带来什么。

### 目标

- 模型在动笔前拿到明确的质量判据，首次产出一套小而准的起步知识。
- 维护者用同一套判据评审，并清楚之后的扩充由谁负责。
- README 开头让读者快速判断这套扩展能为自己解决什么。

### 已定决定

- 版本号仍为 1.9.8，改完按根 AGENTS §7 重装 demo。
- **所有权边界**：适配只负责产出起步知识，之后知识的扩充与演进归目标仓维护者。

## 设计

### 1. 四个判据：定义在哪、谁来读

| 判据 | 内容 | 依据 |
|---|---|---|
| 范围 | 只收项目级内容：被多个模块复用的能力，或约束全项目的规范与方法。只属于某个业务模块的实现与规则不进知识，需求涉及时由各阶段直接读那部分代码 | 知识是跨需求复用的上下文；模块私有细节随需求读代码即可，放进知识只会稀释信号 |
| 初始规模 | 首次适配时，每份知识只收覆盖面最广、违反代价最高的少量内容，上限 3 项（规约算条目，分面知识算列表项，上下篇只写方法的核心步骤）；之后由维护者按需求积累补充 | 起步集要能被人逐条核实；规模由人的评审能力决定，不由模型能找到多少决定 |
| 形态 | 规约先按领域归类，再把同类要求归纳成一条可判定的义务，不照搬规范原文；分面知识写成索引式列表，每项只写是什么、在哪、怎么用，不写实现原理与内部流程 | 规约的读者要判断是否命中；事实的读者要找到入口，实现细节从代码里读得到 |
| 模式准入 | 只有目标仓已在使用承载某种结构的 SDK 时，才建立对应的设计模式知识，取证就是该 SDK 的实际使用处；否则交回「不适用」。适配不自行归纳新模式，其余模式由维护者建立 | 机制要求模式能落到具体角色与文件；没有承载结构时，模型归纳出的模式无法落地 |

放置位置按「什么变了它才变」划分：
- **`protocol.md`**（写与读知识的通用规则，阶段作者与审查都读）：放在任何时候写知识都成立的部分，即范围判据与形态判据。分别补在 §三「谁写什么」知识一行、§五 分面、§六 规约。
- **`knowledge-adaptation.md`**：新增「首次知识的质量判据」一节。
  - 四个判据合列一处，范围与形态两条指向 protocol，不复述原文。
  - 初始规模与模式准入属于适配这一动作，写在这一节。
  - 第 2 步「从基线起」的另补主题只限事实与规约。
  - 第 3、4 步（取证并写、走查）指向这一节。
  - 「交回」按判据逐份写自查结论。
  - 读者行补上「整理已有知识」这一时机，已生成的知识照同一节整理。
- **`SKILL.md`**：首次安装的知识一句指向方法页的判据一节和主题写法页，让模型在动笔前读到。
- **根 `AGENTS.md`**：契约随实现同步。
  - §3.3 知识边界写入范围判据；
  - §2 Adaptation 一行改为「适配只产出起步知识，扩充归目标维护者；模式只按准入判据建立；演进记录的知识条目只写主题与它回答的问题，写法在主题写法页」。

### 1.1 按主题的写法：新增 `reference/knowledge-topics.md`

- **定位**：适配时写每个知识主题的具体指导。
  - 与方法页分工：方法页管流程与通用判据，主题页管「这个主题具体怎么写」。
  - 读者：写知识的模型，以及评审知识的维护者。
- **主题范围**：基线 12 个主题，加上 1.9.5 起的上报知识；两个模式主题合为一节「设计模式」，共 12 节。
  - 事实：部件画像、工程能力、上报。
  - 规约：可观测、安全隐私、兼容性、环境异常、性能与资源引入、界面一致性、资源复用、交付事项。
  - 模式：一节「设计模式」，讲怎样写一份模式知识；流程编排、页面交互编排两个基线主题都指向它。
- **每节固定六项**，每项一两行：
  1. **替谁作什么判断**：读者阶段，以及它支撑的决定。
  2. **到哪找**：取证来源，按可信度排序。
  3. **首批收哪几条**：在 3 条上限内，怎样挑出覆盖面最广、违反代价最高的。
  4. **一条写成什么样**：一条示意，用中性题材，标明是示意、按目标仓实际规范改写。
  5. **常见错法**：内网已出现的形态，以及本主题特有的错法。
  6. **怎样核**：拿正常需求走查的方法。
- **与演进记录的分工（单一来源）**：
  - 基线条目只保留「主题（类型）：回答什么；写法见 `knowledge-topics.md`「<主题>」」。
  - 取证与验证挪到主题页，演进记录不再重复。
  - 上报一节中，上下篇各写什么，以演进记录 1.9.5–1.9.7 的上报条目为准；主题页只补判断、挑选、示意与错法，不复述那些条目。
- **设计模式一节**：准入前提——只有目标仓已在使用承载该结构的 SDK 时才写，取证是这个 SDK 的使用处，否则交回「不适用」。同类的以包内对应模式为底稿，沿用上下篇组织与角色划分，把 SDK 行为、文件落点、参照实现换成目标仓的。不写 demo 的 SDK 名、节名与角色名。
- **机制层零测试特征与 M20**：
  - 示意条目的内容用中性题材；编号前缀用主题的通用缩写，与 demo 一致；
  - 不出现 demo 知识的节名、表头以外的专属结构词，也不出现 demo 条目的原文；
  - 规约示意的列沿用 protocol §六 定义的列名。

**示例：「安全隐私规约」一节的样子**（示意，定稿时再推敲措辞）：

> **替谁作什么判断**：spec 判断本需求是否碰到个人数据、权限或对外暴露面，据此形成红线约束；plan 与检视核对落点。
> **到哪找**：公司或产品线的安全隐私规范、隐私评审清单、安全评审的历史结论；代码里已有的脱敏、权限申请与加密封装只用来核「已满足」，不作为规约来源。
> **首批收哪几条**：从规范里挑违反后必须返工或无法上线的红线，优先覆盖面最广的出口类要求（数据往外送的所有渠道）与权限类要求；具体字段清单、各业务的特殊约定不收。
> **一条写成什么样**：`| PRV-01 | 新增的敏感权限在首次使用处申请，并说明用途；用户拒绝后功能可降级使用 | 红线 | 需求新增或扩大权限申请 | 列出权限、申请时机、拒绝后的行为 | 模型：核权限声明与申请调用处；人工：隐私评审确认说明文案 |`（示意：按目标仓实际规范改写）
> **常见错法**：
> - 把规范原文逐条搬成十几条；
> - 把某个业务的加密细节写成全项目规约；
> - 把「用哪个脱敏工具」写进规约（那是项目事实）；
> - 验证只写「检查代码」，没写执行体。
>
> **怎样核**：拿一个新增个人数据字段或新权限的需求逐条判命中，能说出落点与各执行体的验法。

### 2. README

- **新增「1. 功能一览」**，放在快速上手之前，原 1–4 部分顺延为 2–5，文内编号引用同步。
  - 写法：一行一个功能。功能名写成「支持……」；说明写人怎么用（命令、放在哪、能放什么），扩展接着做什么，什么时候会请你确认。
  - 不讲内部机制。每项事实都取自 README 已有章节，不新增能力。

  初稿：

  | 功能 | 说明 |
  |---|---|
  | 支持按需求单号取回上游需求 | 说 `/story init <AR单号>`，自动从需求系统取回这张单关联的 AR、SR、RR 正文。第一次使用时把需求系统的访问 token 发给 AI，之后不用再配 |
  | 支持没有系统单的本地需求 | 问题单、工单或自定义编号也能起需求：`/story init <编号>`，材料由你提供，产出的文档都留在仓内 |
  | 支持添加本地需求文档与会议转写 | 把产品 PRD、系统设计文档、界面设计图等放进 `doc/features/<需求编号>/inbox/`，支持 `.docx`、`.md`、`.txt` 等，PDF 由 AI 尽量转写。需求澄清会的语音转文字稿也放在这里，扩展会识别其中与需求相关的结论；会上没定下来的事，会请你逐个确认 |
  | 支持和你一起确定需求范围 | 读完材料后给出整体承载或拆成几份的建议，你选定后才动笔；想换一种拆法直接告诉它 |
  | 支持生成规格、需求说明与评审记录 | 写出需求规格与验收标准、一份给评审人读的需求说明（按业务讲清来龙去脉），以及供评审人逐条表态的评审记录；交付前经过自动检查与独立审查 |
  | 支持评审意见与需求变更的增量更新 | 评审意见回来、上游需求改版、你有了新决定，或有人直接改了文档，说 `/story update <编号>`，在原文档上增量修订并记下改了什么；与已定内容冲突时先请你裁决；不满意可以撤回这一轮 |
  | 支持送审回写需求系统 | `/story archive <AR单号>` 把需求说明与评审记录上传到需求系统，覆盖前自动备份；`/story restore <AR单号>` 恢复上一版 |
  | 支持从需求一路做到测试 | 规格定稿后接着做方案设计、编码、代码检视、单元测试与实机测试 |
  | 支持沉淀与使用项目知识 | 把项目已有的能力、必须遵守的规范、项目在用的设计模式写成项目知识，各阶段自动引用并检查是否落实 |
  | 支持埋点设计 | 需求要观察业务质量或做运营统计时，从指标定义、统计点到代码落地逐步设计，后续阶段核对落实情况 |
  | 支持中断后继续 | 中断或换了会话，告诉 AI 需求编号，它从上次停下的地方接着做 |
  | 支持装到你的业务工程 | `/story adapt <工程目录>` 一条命令安装或升级；只更新流程部分，不动你的项目知识与需求系统对接；首次安装时 AI 起草项目知识，由你评审定稿 |
  | 支持多种 AI 编程工具 | Claude Code、CAC、Codex、OpenCode、Cursor 等 |
- **「安装与升级」部分新增「评审 AI 起草的知识」小节**：
  - 面向维护者，用日常语言转述四个判据，外加每份知识写清适用时机、每项带出处；
  - 说明发现不合格时怎样让 AI 按判据重整；
  - 说明起步之后的扩充由维护者负责；
  - 注明判据原文在适配方法页，各主题的具体写法在装进工程的 `doc/extensions/skills/story-adaptation/reference/knowledge-topics.md`，评审某一份时对照那一节；README 只作转述、随源同步。

## 验证

- 全量离线回归（TEST §5），含 M20 等失效形态检查。
- 机制层零测试特征自查：新增文字不含内网仓名、模块名、demo 业务名或 SDK 名。
- 两个视角各走查一遍：
  - **模型视角**：首次安装 → SKILL → 方法页与主题页。动笔前能拿到四个判据，以及当前主题的六项写法；对没有编排 SDK 的仓，模式结论是「不适用」。
  - 主题页 12 节逐节自查：示意与 demo 条目原文不重合，题材中性。
  - **维护者视角**：只读 README，就能判断一份知识是否合格、怎样让 AI 重整、之后由谁补充。
- 未验证：内网按判据重整后的知识质量，需要维护者让 AI 重整一次后评审确认。
