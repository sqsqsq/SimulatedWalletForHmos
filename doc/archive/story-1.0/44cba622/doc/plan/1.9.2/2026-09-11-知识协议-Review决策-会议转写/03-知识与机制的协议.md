### 用户定的方向与目标

问题是**知识本身与 extension 机制怎么协作**：知识不在机制里硬编码，机制保证知识按期望被看到、识别、应用、传递。范围是**全部三类知识**。知识侧声明内容、适用边界、依据及结果要求；机制侧及时送达、指导适用判断、保留本需求形成的决定、传给下游、按要求取得证据。双方依赖**稳定的内容协议**，解耦不等于任一方可以任意改协议而另一方无需知晓。准确性分四层验证：知识可信、适用判断正确、实际落实、证据足够。强制力决定未满足时如何处理，验证方式决定证据从何而来，两者独立；三类知识不都是打勾的规则。验收：换业务知识不改机制；改知识要求影响本需求的产物与验证；已确认的约束传到下游不被悄悄降低；机制升级保留目标知识。

### 外部评审纳入的四条

- **F4**：强制力与验法不能混；多执行体是共同必需，不是任选。
- **F5 / N3**：探针命中不是落实证明；探针形态与正确实现的写法无关（`chartBuilder` 分两句写、经封装上报都是对的）。要先分清探针查的是「知识明确要求的强制形态」还是「帮助取证的局部手段」，只有前者才有理由因形态不符阻断。

## 3. 协议总则

**两个签约方**：知识（目标仓所有）在自己的文件里声明；机制（扩展所有）按协议读、按协议执行；三类知识的 README（`kind: index`）是协议正文，`knowledge.mjs` 只按它读。

**协议有版本**：三份 README 的 frontmatter 写 `protocol: 1`；`knowledge.mjs` 声明它实现的版本；不一致就报并指明改哪边。协议只在加字段、改值域时升版。版本号证明的是格式一致，不证明知识可信。

**两个粒度，从头到尾一致**：

| 粒度 | 是什么 | 谁在这个粒度上工作 |
|---|---|---|
| 规约（条目） | 一条知识声明；命中与否、强制力、执行体在这一级 | spec 判命中；acceptance 一条 `knowledge_rule` 对一条规约；UT / testing 按验收条目覆盖 |
| 义务（`must`） | 规约在本需求的一处落点（实体 + 要做什么 + 证据来源） | plan 挂；coding 门禁核实体、跑探针；verifier 逐条判；review 复核表**一处落点一行** |

一条规约可以有多处落点；每处各自要证据，任何一处没证据，这条规约就没落实。

**四层准确性，各有各的验证者**：

| 层 | 问的是 | 谁验、怎么验 |
|---|---|---|
| 知识可信 | 事实是真的吗、依据在吗 | 知识所有者；机制只核结构与 `confirmed` 值域，`selfCheck` 不含机制坐标 |
| 适用判断 | 本需求命中吗、依据可回查吗 | spec 门禁核集合与依据非空；spec verifier 判要求是不是本需求的设计 |
| 落实 | 设计与代码真的做了吗 | plan 门禁核每处落点的证据来源覆盖声明；coding 门禁核实体在、跑探针；coding / review verifier 逐处落点判 |
| 证据足够 | 拿到的证据撑得起「落实」吗 | UT / testing 覆盖门按 `verify` 认领；review 复核表按强制力决定「未落实」的后果 |

**三类知识三种用法**：事实用于定位与核实目标能力；规约产生本需求的约束及处置；模式支持选型与落地，允许一个都不用。

改动两处：`selfCheck` 核 `confirmed` 值域（面级）；`knowledge-use` 的 `facts[].used` 按面（`document.mjs::readUse` 读取、`validation.mjs:82-99` 核字段、`projection.mjs` 投影、`renderSkeleton` 骨架）。

### 4.2 设计模式

看到（候选在骨架）、识别（上篇信号与反例、零命中举证）、应用（`roles` 投影到契约实体）、传递（下篇给 coding / review，角色被引用）都是现状。样板两篇标题已在。改动两处：`parsePatternFile` 载入核 `# 上篇 · …` 与 `# 下篇 · …` 两个一级标题都在（缺一报派生失败）；`coding/author.md:14` 改指「下篇」，删 `sections.implement`。

### 4.3 规约

七列不变、列名不变。三个字段派生出来，含义分开：

| 字段 | 含义 | 值域（README 已定义） | 派生 |
|---|---|---|---|
| 强制力 | **未满足时怎么处理** | `红线` = 阻断，不许豁免；`基线` = 可豁免，须理由与补偿，评审判；`建议` = 可不做，须理由 | `force`，缺列或值不在集合里 → 载入失败 |
| 验证（执行体） | **证据从哪来**；若干段 `<执行体>：<怎么验>`，**各段共同必需** | `模型` / `构建` / `实机` / `人工` | `executors[]`，一段都解析不出 → 载入失败 |
| 探针 | 机器能做的**局部形态检查**；`阻断：` 前缀由知识声明「这个形态本身就是要求」 | `[阻断：]<四形态之一>`（四形态不变） | `probe`（含 `blocking` 标记） |

**探针的职责由知识声明，不由操作符推**（N3、R2）：

| 写法 | 含义 | 不过时 |
|---|---|---|
| `阻断：<形态>` | 知识作者声明**这个形态本身就是要求**（如「方向性参数不得写 left / right」） | 这处落点判「未落实」，后果按强制力：红线 → coding FAIL；基线 → coding 记未落实、review 复核表须有依据；建议 → 记录 |
| `<形态>` | 辅助取证：这处落点里有没有走那个封装 | 只记「证据缺口」交 verifier 与实机验证——分两句写、经封装上报都是正确实现，探针认不出不等于没做 |

同一个操作符可以服务不同的要求：`absent_regex` 可以是要求本身，也可以只是线索；`count_eq` 源码出现次数不等于运行时事件次数。哪一种由写规约的人说，机制照读。

强制力与执行体独立：红线可以只由模型验，独立审查判「未落实」就是阻断；基线可以有探针。不存在「红线必须有可执行验法」。

**载入自检**（`selfCheck` 加四条）：值域三处（强制力、执行体、探针形态）；`人工` 只配「（评审动作）」处置，反之亦然；每条至少一个执行体；协议版本一致。

## 5. 规约合同在各道门上怎么执行

### P1 · 看到：送达，不是指路

- spec：`knowledge-use` 骨架（`document.mjs::renderSkeleton`）每条 `id` 下带一行 `# <强制力> · <约束> · 命中：<命中条件> · 验法：<执行体列表>`。
- plan：spec §10 的表（`projection.mjs::renderConstraints`）加两列**强制力**、**验法**（从知识派生，`render` 写入，作者不填）。
- coding 以后：`must` 不加字段，门禁按 `must.rule` 回查条目取 `force`、`executors`、`probe`。

### P2 · 识别：三种结论，按强制力允许哪几种

| 结论 | 写法 | 红线 | 基线 | 建议 |
|---|---|---|---|---|
| 命中并落实 | `applicable: true` + `requirement` + 落点 | 允许 | 允许 | 允许 |
| 命中但本轮豁免 | `applicable: true` + `waived: {reason, compensation}` | **不允许** | 允许，`compensation` 必填 | 允许，`compensation` 可空 |
| 不命中 | `applicable: false` + `reason` | 允许 | 允许 | 允许 |

spec 门禁（`validation.mjs::coverageProblems`）按 `force` 判组合；`render` 把豁免渲进 §10「命中但本轮豁免（评审判）」小节，附录 D（`appendix.mjs::verdictSkeleton`）同样投影；豁免按决策登记准入登记，评审人表态。`acceptance.knowledge_rule` 只对「命中并落实」要求。

### P3 · 应用：每处落点的证据来源要符合知识声明的执行体；不是规约要求的事不挂 `must`

`must.verify` 的取值改为 **`ut / device / both / review`**——它说的是这处落点的证据由谁取：`ut / device / both` 是实机，`review` 是只由 verifier 判。`probe` 从取值里退场：探针不是作者为某处落点做的选择，它是规约自带的、对该规约每处形态匹配的落点自动跑的局部检查（P4）。

plan 门禁（`hooks/plan/post_check.mjs:263-290` 那一段）按**每条 `must`** 判：

| 该规约声明的执行体 | 对它的每条 `must` |
|---|---|
| 含 `实机` | `verify` ∈ `ut / device / both`——每处落点都要实机证据；一处标 `review` 就是这处没证据 |
| 只有 `模型`（或加 `构建`） | `verify = review` 即可；每条 `must` 都由 verifier 对着代码判，`构建` 由原生门禁判 |
| `人工` | 不挂 `must`（评审动作） |

不再有「同一条目多挂几条 `must` 凑验法集合」：一条 `must` 就是一处落点，它的 `verify` 由规约声明决定，多处落点各自照此。有探针的规约，`present_in_method` 形态要求落点是方法——plan 门禁核该规约至少有一处 `interfaces[].methods[]` 落点，否则探针无处可跑，报出来（不阻断 plan，记为「探针无落点」）。

映射表写在 `obligations.mjs`，plan 作者页印同一张表。

**借挂的作者落点（§1 第 5 条）**：合法业务规则不属于任何命中条目时，它有自己的位置——实体的说明字段（`data_models[].fields[].description`、`components[].props/state` 的说明、`interfaces[].methods[]` 的说明）或 plan.md 对应设计章的一句，**不挂 `must`**。`hooks/plan/author.md` §二 与 `templates/plan-sections.md` 的 `must` 写法处各加一句「不是某条规约要求的规则写在这里」，并给「借挂」的一个中性反例（业务数值上限挂到兼容性条目）。机器不判语义；overlay `knowledge_obligation_substance` 的「借挂即 FAIL」判据不变，它的真实效果在统一 CLI 实跑的 plan 阶段验（用 1.9.1 car 的三处借挂形态作对照）。

**契约读取的核项（步骤 0 评审 §3 第 2 条）**：`yaml-lite` 不认流式映射（`- { name: X, type: string }`），而 framework 的 plan 契约模板用这种写法登记 `data_models[].fields[]`（1.9.1 car `contracts.yaml:35-46` 即是）；带 `must` 的实体必然是块式（`must` 是嵌套列表），所以借挂与落点判据不受影响，但流式字段读成一个字符串后 `resolveEntityRef` 找不到该字段名。`contracts.mjs::readContracts` 加一条：遍历五类实体的成员，遇到以 `{` 开头的字符串项即报「契约里的 `<实体>` 用了流式写法 `{ … }`，扩展只读块式：每个字段一行 `- name:`」，归 plan 结构门禁 `knowledge_obligation_on_entity` 的 problems。不扩 `yaml-lite` 支持流式映射（模块头注的边界不动）。

### P4 · 传递：每道门按粒度、按强制力

| 阶段 | 粒度 | 协议 |
|---|---|---|
| coding | 每条 `must` | 实体在（抹注释后找）；该规约有探针 → 对形态匹配的每处落点自动跑：`阻断：` 的不过 = 该落点未落实，后果按强制力（红线 FAIL）；不带前缀的不过记「证据缺口」（进 verifier 输入） |
| review | **每条 `must` 一行**（`rule` + 落点） | 复核表按 `rule` + 落点定位（`review/post_check.mjs:79-83` 的按编号建 Map 退出），不按 `rule` 建 Map；结论从**结论列**取准确值（`:95` 的整行子串匹配退出；「未落实」不能被读成「落实」）；**红线的落点「未落实」→ FAIL**；基线「未落实」须有依据；建议不拦 |
| ut / testing | 每条规约的验收条目 | `verify` 为 `ut / both`、`device / both` 的义务按 `knowledge_rule` 认领覆盖（现状）；验收条目的 `ut_focus` / `device_focus` 点名各处落点 |

同一规约两处落点，只给一处证据，另一处在 review 表上仍是未覆盖——这是粒度对齐的验收（§7 判据 6）。

## 6. 不做的事

- 不加新列、不改列名、不改目录与 frontmatter 键；本步是 `protocol: 1`。
