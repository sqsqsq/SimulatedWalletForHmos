## 1. 要解决的三件事

| # | 现象（1.9.1 两 Case 实测） | 根因 | 本步的答案 |
|---|---|---|---|
| 1 | 写作设计是每章一段长文（71/123 行），模型写章时只在起手读过一次，`####` 骨架与 `syntax` 两轮无人用；正文分节与设计的对应靠模型记忆 | 设计是「说明」，正文另起炉灶；机器只核表头与图存在，不核骨架 | **骨架直接生成草稿**：作者在写作设计里写的是正文将要有的标题树与每节要答什么，脚本按它建草稿、按它核提交；模板不再是指导文档 |
| 2 | 「写后核对」两 Case 都只修语言红线（auto 5 秒自述完成）；未决写成已定、跨章矛盾、初筛疑点丢失都由 verifier 首轮兜住 | 方法写成三段散文，作者没有可逐条执行的对象；回看没有输入 | **回看清单由脚本枚举**（初筛疑点、open 决策、骨架里的待核项），作者逐条处置到真源，verifier 拿同一张清单复核；不落自证台账 |

## 2. 写作设计：从说明改为骨架

### 2.1 协议（`AR/story-src/story-template.md`）

```markdown
# 写作设计

## 阅读主线
<散文：第一次读的人按什么顺序理解，哪些参与方/对象/关系先讲，已定依据在哪，哪些未决限制叙述>

## 骨架

### 05-flow
- 本章主线：<一句>；与功能说明分工：<一句>
#### 端到端总览
- 答：从发起到失效的主路径与全部分支去向
- 依据：SR/design.md §2、spec §5.1
- 待核：配额满是不是发起前的准入分支，还是只在功能章讲
图：flowchart
#### 发起分享的交互时序
- 答：谁调谁、结果回到谁、签发失败谁回滚
- 依据：SR/design.md §2 时序图
图：sequenceDiagram
##### <再下一级小节，需要时才有>
#### 分享状态机
- 答：六态与转移；「撤销中」时车辆侧已拒绝
表头：状态 | 进入条件 | 退出去向

### 10-appendix
- 五节由投影，材料清单写贡献
```

规则，全部由 `writing-plan.mjs` 一处解析：

| 元素 | 含义 | 机器怎么用 |
|---|---|---|
| `### <章 ID>` | 一章；十章 ID 齐是结构合同 | 定位一章的骨架 |
| `#### 标题` / `##### 标题` | 正文里将出现的 H3 / H4 小节，**标题原样进草稿与正文** | 草稿按此建标题；提交时每个骨架标题都要在正文里（同名，按现有规范化比） |
| `- ` 开头的行 | 骨架说明：答什么、依据、关系、未决、形式理由。`待核：` 开头的行是作者留给回看的问题 | 进草稿时变成 `story-draft:guide` 注释行，提交时剥掉；`待核：` 行进回看清单 |
| `表头：A \| B \| C` | 该标题下要一张表，列即契约 | 复用现有表头种子与提交核对（`selectedStructure` 的表分支） |
| `图：<syntax 或 图>` | 该标题下要一张图；`sequenceDiagram` 等具名语法只认该类 | 复用现有图种子与核对；`图` 表示任一种 |
| 章级结构 | 写在 `### <章 ID>` 直接下方、任何 `####` 之前 | 同现有 `at: ""` |
| 不涉及的章 | `### <章 ID>` 下只有一行 `- 不涉及：<理由>`，没有小节 | 同现有「不涉及」冲突判据：还留着小节或表图就报 |

**退出**：`## 章节安排` 散文段、`## 结构选择` JSON 数组、`FIELDS`/`checkPick`/`readPicks`。旧形态的文件读到即报「按 1.9.2 骨架协议重写这份写作设计」，不双读。

### 2.2 自由度（不变的原则）

骨架是**最小集合，不是上限**：正文可以多出小节、多出表图，不报；要删骨架里的节，先删骨架那一行再提交（机器报的是「骨架有、正文没有」，出口两条都给）。标题级别以骨架为准，标题文字可在提交前改骨架同步。业务结论仍只在 Spec 与 `decisions.json`，骨架里只引用。骨架内容从本需求材料正向形成：`- 答：` 写要回答的问题，不预写答案，不替材料编接口、时限或补偿。

### 2.3 脚本职责变化

| 位置 | 现在 | 改为 |
|---|---|---|
| `writing-plan.mjs::writingPlanShell` | 三部分 + 每章一段占位 | `## 阅读主线`占位 + `## 骨架` 下十个 `### <id>` 各一行占位「写本章的小节标题与每节要答什么」 |
| `readWritingPlan` | 解析三部分与 JSON | 解析骨架树：每章 → `{intro: 说明行[], sections: [{level, title, notes[], table?, diagram?, sections[]}], notApplicable?}`；`待核：` 行单独收集；协议缺口一次报全（章 ID、标题重复、`表头：` 无列、`图：` 未知语法、不涉及却有小节） |
| `selectedStructure` | 由 JSON picks 合并合同结构 | 由骨架树派生同一形状的 picks（`at` = 标题，`kind`、`columns`、`syntax`），合并逻辑不动 |
| `drafts.mjs::chapterDraft` | 章头指引 + 合同种子 | 章头指引 + **骨架标题树**（`####`→`###`，`#####`→`####`）+ 每个标题下的说明注释行 + 表头/作图种子；`- 不涉及：` 的章草稿只放那一句 |
| `writeDrafts` | 未写草稿换成带选定结构的起点 | 同一规则：骨架变了、草稿未动过就重铺；动过的只给缺失起点（现有 `missingPickedSeeds` 扩到标题） |
| `chapter.mjs` 提交 | 核选定表图、不涉及冲突 | 加一条：骨架里本章每个标题在候选正文里都有（剥指引后按规范化标题比）；缺的报标题名与两个出口 |
| `check.mjs` 全篇 | 同上按章 | 同上 |
| `story-write.md` 二、三 | 长文说明三部分 | 改成骨架怎么写（本节 2.1 表）与「照骨架写：先答骨架里的问题，再补骨架没列的」 |

冻结与重开语义不变（写作设计随成文登记冻结）。

## 3. 回看：十章齐后一张清单，处置回真源

### 3.1 时机与入口（R9）

链条：按章写 → 十章齐 → `story-build skeleton` 不再给「写下一章」，而是打印**回看清单** → 作者逐条处置 → `story_flow.py story` 登记。`SKILL.md` 链条那一行的「写后核对」改为「回看」，`phases/spec.md` 与 `story_flow.py status` 的下一步文案同步。回看不新增命令：skeleton 在全部章都不带待写标记时切换输出；作者想再看一次就再跑 skeleton。

### 3.2 清单由脚本枚举（新模块 `core/story/recheck.mjs`，≤ 150 有效行）

| 项 | 来源 | 每条打印什么 |
|---|---|---|
| 初筛疑点 | `init-analysis.md` ⑥ 表「还要核实的矛盾或缺口」非空的行 | 来源位置 + 疑点原文 |
| 未决 | `decisions.json` 里 `status=open` 的条目 | id + 标题；提示「正文里依赖它的行为不能写成已定」 |
| 已定取舍 | `status=settled` 的条目 | id + 标题；提示「取舍落在哪一章，依据写了没有」 |
| 骨架待核 | 写作设计里 `- 待核：` 行 | 章 ID + 那一行 |
| 图与声明 | 现有 ⑫c 已核「图前无承接句」；覆盖声明与图节点是否相符归 verifier | 只列每张图所在节名，提示核「声明覆盖的去向图里有没有」 |

脚本只枚举与定位，不判去向。每条附同一句撞法提示（3.3）。清单同时进读者审查任务书（`reader-review-task.mjs` 追加一节「回看清单」），verifier 用它复核。

### 3.3 撞法（R3、R4、R5）与出口

作者对清单每一条、以及骨架每一节的关键主张，问两件事：

1. **这句话材料里有吗？** 有 → 是搬运，进第二问；没有但有依据（工程事实、规约、上游口径）→ 决策点，依据就是背景；没有也说不出依据 → 编的，删。
2. **材料给的靠得住吗？** 拿它去撞：更晚的输入（SR 晚于 RR、界面稿、会议有效结果）、材料之间、工程事实、规约、材料自己声明的目标。「不合适」只认四种：工程没这能力、与既有实现冲突、撞规约、材料的目标与做法对不上。「我觉得有更好设计」不进。

十一类表留在 `story-write.md`，位置改到「登记时选 category」之后，引导语改为「每类第三列是撞的方向，不是遍历顺序」（R1、R4）。

出口只有四个，处置回真源、不写台账：

| 发现 | 出口 |
|---|---|
| 真实未决、跨章矛盾、spec 与 story 对不上而需人裁 | 登记 `open`（依据写撞点），正文只写待决边界 |
| 重要的已定取舍正文有依据、登记表没有 | 补登 `settled`，引既有结论与依据（R8 分册第二出口，防漏登） |
| 已有依据能定的普通说明 | 沿用，不登记 |
| 编造、误读、不一致 | 回错误所属真源改：story 章 → 草稿重提交；spec → spec.md；验收 → acceptance.yaml；知识判断 → knowledge-use 再 render；骨架错 → 改骨架 |

**没有问题不制造改动**；不写「已核对」。清单里每一条的去向由 verifier 核（§5），不由作者自报。

## 4. Review 议题的表达（R6、R7）

`review_mode` 两类正文形状不变（决策点／依据／可选的做法／建议／理由；决策点／依据／结论与影响）。两处收紧：

- **依据写撞点（R7）**：「依据」段必须指出这条是在哪撞出来的——story 哪一章或 spec 哪一节的哪个主张，与哪份材料的哪一节或哪条工程事实/规约相撞。「根据材料和工程现状」这种没有指向的话不算依据。机器不判（判不出真假），归 verifier；它是稳定性比较的锚（§5 验收 1）。
- **每个选项各带后果（R6）**：「可选的做法」每一项写成 `做法——选它会怎样`，后果说清范围、行为、验收、交付哪一项会变，并有可指认的事实支撑；写不出后果差别的不是真取舍，降级为 confirm 或事实陈述。`review.mjs::choiceListProblems` 加一条形状判据：每个列表项含 `——` 且其后非空；分隔符登记进 `story-chapters.json` 的 `decision_form`（与现有标签同处），`story-write.md` 引它。只判字面，不判后果写得好不好。

`story-write.md` 决策登记节的示例按此改；`review_reflow.md`、使用指南同步一句。

## 5. 审查判据与验收

`spec-rules.overlay.yaml::story_reader_review` 的 `ai_prompt_hint` 加两问（不加检查项）：回看清单里每一条在正文或决策登记里的去向成立吗——初筛疑点被讲清、登记 open、或有依据地判不适用；未决没有被写成已定？每条议题的依据指得出撞点吗？只有「根据材料」的算没写。

| # | 判据 | 怎么验 |
|---|---|---|
| 1 | **稳定性**：同一 Case、同一材料与范围，两次独立运行 | 比撞点集合（决策依据里的撞点 + 回看清单的处置去向），三个维度一起看：分类分布、条目数、语义；措辞/顺序/合并不同不算漂。用 1.9.1 `story-suite-20260914-190900` 作对照基线 |
| 2 | 骨架→草稿→正文 | 夹具：骨架三级标题、表头、具名图各一 → 草稿标题与种子对上；正文缺骨架节 → 提交拒绝并给两个出口；正文多出小节 → 通过；`- 不涉及：` 章留小节 → 报 |
| 3 | 旧形态不双读 | 1.9.1 形态的 template → 报「按骨架协议重写」，不解析 JSON |
| 4 | 回看清单 | 夹具：初筛两条疑点、一条 open、一条 settled、两行 `待核：` → 清单五类各对上；十章未齐时 skeleton 仍给写章动作 |
| 5 | 选项后果 | 夹具：无 `——` 的选项、`——` 后为空 → 拒绝；合法 → 通过；confirm 无列表照过 |
| 6 | 真实运行（用户按 TEST 启动） | 首稿没有 open 决策被写成已定；auto 类初筛疑点（如更新接口缺口）在决策或正文有去向；verifier 首轮 BLOCKER 数下降；三轴建议分较 1.9.1 上升 |
| 7 | 不劣化 | 1.9.1 已通过的结构保护（选定结构冲突、已写章不覆盖、reopen、人工区、处置台账）用例全绿 |

判据 1、6 是核心，需两次完整实跑，起跑前说清成本。
