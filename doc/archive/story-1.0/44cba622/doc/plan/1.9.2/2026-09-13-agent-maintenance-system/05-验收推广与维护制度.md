# S6：维护体系验收

## 目标与前置

S1–S5 已分别交付。验收判断维护者能否基于清楚的目标和依据完成正常工作，以及维护诊断能否发现实际问题并提供完整修复安排。

按当前验收项读取对应步骤。证据放本计划 STATUS 和该维护任务的既有记录；产品正式 Case 不是本次文档整理的默认验证。

先汇总 S1–S5 已有证据，再执行缺少的验收。文件、规则或相关配置未变的通过结果直接引用；发现变化才重验受影响部分。验收不要求重新运行已完成步骤。

## 1. 用户级与项目级依据

| 对象 | 验收结果 | 检查方式 |
|---|---|---|
| 用户级说明 | 覆盖理解目标、设计、实施、评审和交付，角色责任清楚 | 对照 S1 的四节正文和 U1–U6 读正文，检查内容能指导具体决定 |
| 项目文件 | 产品事实、当前依据和特殊要求可定位，通用定义有承接，旧重复退出 | 核对三个项目实际 diff、迁移去向和引用 |
| 用户副本与加载 | AGENTS.md/CLAUDE.md 正文直接包含共同要求，三个既有落点同步，无独立维护文件 | Git 内容标识、新会话读取/注入记录 |
| 维护与消费 | 两类任务取得各自需要的材料，维护历史不进入消费交付；用户级入口也会进入被测模型会话，其内容对消费任务中性 | 检查实际入口与读取记录；逐条核用户级入口不含维护历史、测试答案或项目路径 |
| Story | test/story 文件原位整理，产品边界及其他任务修改保持 | 具名路径 diff 和原修改保护检查 |

S5 的三项用户级局部修订同时核对：交付规模、完整退场、实施/评审适用性分别合并进原条款，三个入口一致；既有角色和授权边界不变。

项目层还必须通过以下目标检查：

| 检查 | 输入与方法 | 不通过条件 |
|---|---|---|
| 长期规范不绑定单次任务 | 阅读各项目 AGENTS/CLAUDE/PROJECT/TEST 的入口；分别以本次维护任务和另一个已有任务的目标/路径推演读取顺序 | 两个任务都被强制送到同一优化轮次，或规范中保留该轮暂存/搬迁动作 |
| 三角色一致 | 将用户级的维护设计者、维护实施者、消费模型逐行对应到项目角色职责，再核测试角色段和维护流程引用 | 缺少某角色的项目职责；把设计、实现都交未区分的单个维护者；旧“第三种角色”等表述重定义了分类 |
| 原有义务完整 | 对照本次重组前职责，核每项在角色表或共同义务段的承接 | 为统一结构删掉事实、产品输入、隔离、迁移或验收条件 |

“维护者”作为前两角色的合称可以保留。状态页与任务索引可说明真实进展，但不能被稳定规范当成替用户选择任务的入口。检查对象是作用和读取路径，不以搜索不到日期或凑齐三个名称判通过。

## 2. 责任人与判定

实施者提供实际文件和检查证据；本方案设计者评审并记录逐项通过、不通过或未验证。设计者会话无法接续时由用户指定接续设计者；产品范围争议由用户裁定。这只定义验收责任，不规定协作工具。

静态项以修正后的 S1 归属表和 S2–S4 文件表核对。每处实际删除须核原句、相同适用对象的完整等义承接、读者在动作前可达的路径；仅指出用户级有概括句不算承接。删除产品条件、隔离或迁移义务，或越过具名范围，判不通过。新会话行为使用 T1。

## 3. T1：Story 称谓整理的真实实施

任务固定为本计划 S4“Story 项目级维护依据与说明注释的角色整理”。在 S1 静态通过后，由新的实施会话完成 S4；只给总览、STATUS 和 S4 路径，不另加本轮错误提醒，不调用 maintenance-agent。S6 汇总这次真实实施的证据，不重新实施 S4。

| 检查项 | 证据 | 不通过条件 |
|---|---|---|
| T1-1 取得依据 | 首次编辑前的文件读取/宿主注入记录，含用户级 AGENTS.md/CLAUDE.md、Story AGENTS、TEST 任务索引及 S4 | 未取得必要入口就改文件；无法提供读取证据则标未验证 |
| T1-2 核实工作区 | 开工 HEAD、AGENTS 和 TEST 各自完整 diff；核 §7.5 预算及 TEST 并行命令/说明、预算判读等在途段落 | 只核 AGENTS 漏核 TEST，按旧报告定位冲突，覆盖/撤回在途内容，或要求先提交无关改动 |
| T1-3 正确迁移 | S4 注释表与实际词级差异 | 将消费模型和维护实施者混换；修改预算值、执行逻辑、断言或历史 reason |
| T1-4 完整交付 | 核 S4 的三角色职责、长期规范与任务分离，以及原义务完整承接 | 只换称谓仍保留二分职责；固定指向单次优化；或用概括句替代产品合同 |
| T1-5 结论有证据 | 实际差异、格式检查、保护项与未验证说明 | 只凭“已自查/全部合理”宣告完成，或把文案核对写成业务行为通过 |

开工 diff 与验收结果留在当次会话或本地实施记录，不归档、不提交。所有 T1 项有证据并通过才标本任务行为通过；未验证项不能当通过，也不使已经通过的 S1 文档部署失效。

## 4. maintenance-agent 的核心功能

T2 固定为 S1–S5 完成后的三次真实调用：Codex 在 Defect、Story 中调用，Claude 在 WalletKit 中调用；输入只有 `$maintenance-agent`。由本方案设计者依据调用时实际材料判定，下表说明诊断应处理的内容，不要求凭空制造每类缺陷。

| 场景 | 输入证据 | 预期诊断与计划 |
|---|---|---|
| 项目方向 | 产品目标与一项当前建设内容不相符 | 说明偏离及影响，修复回到目标或设计决定，不只调整文档措辞 |
| 角色与信息 | 职责定义、计划输入或消费入口有冲突/缺口 | 定位谁应提供何种信息及正确位置，保持维护与消费边界 |
| 规约治理 | 用户/项目定义重复或冲突，状态/说明过时 | 确定权威来源与具体迁移、保留、删除动作，不新增一套平行规则 |
| 实现漂移 | 相关实现已变化，维护材料未同步；或旧机制仍有调用 | 检查真实消费者，合并根因，给出完整替换和同步安排；不能只核对文档互相一致 |
| 交付证据 | 计划留有关键设计，或完成声明只有局部检查支撑 | 明确缺口与责任层，补可实施动作和验收，未验证部分保持未知 |
| 综合修复 | 同一责任问题在多份材料/实现中表现不同 | 按目标组织步骤，覆盖直接影响和旧内容退出；不按文件 diff 或用户例子逐条加补丁 |

在三个项目分别零参数调用，检查当前项目与用户级均有结论。按 04 的诊断内容核对完整性，重点看判断、证据与修复设计；不以文件数量、状态字段或 Git 命令成功代替通过。

每次 T2 必须通过四项：两级实际入口和检查范围明确；每条发现都有可核证据且无错误事实；修复计划包含具体文件动作、依赖、保护项和验收；调用没有修改被诊断材料。任一不满足判该次不通过。没有问题允许给出有检查依据的无修复结论；没有相应样本时，不宣称已证明该类缺陷检出能力。

在已有 T2 产出中核对新增用户要求，不另建测试流程：方案通常为 1–4 步，超过时有独立目标拆分或必要性说明；涉及替换时同时写清旧机制及专用测试的退出、有效回归覆盖的保留；发现过拟合时给出样例依赖与其违背适用范围的证据，修法不扩大为无需要的通用框架。当前材料无此类缺陷时不强凑发现。

Codex、Claude 的实际发现和调用各验证一次；无法运行时标该项待验，不改变核心能力判据。所有调用保持被诊断规约、代码和产品任务状态不变。

## 5. 阅读与表达

从一个实际任务检查整条阅读路径：需要的目标和约束在决定前可得，其他项目、无关分支及历史不默认加载；相同内容的完整定义只有一处。

回复和文档保留有效决定、必要背景、证据与限制。重点按对目标的作用安排，重复提醒、无关背景和失效版本退出。既不以缩短单个文件代替整体简洁，也不以增加记录证明质量。

## 6. 收口

完成条件：S1–S5 交付通过，项目稳定性/角色一致性/义务完整性三项检查通过，T1 全项通过，三次 T2 各四项通过。只完成词语替换和内容保留不能宣告本需求完成。缺宿主或行为证据记未验证。

S1–S5 单步完成与整个体系验收完成分别登记。外部会话或材料尚不可得时，列明哪项验证未做、实际前置和责任人；不回退已完成文档步骤，也不让执行者猜当前应该等待什么。

提交按用户授权限定代码、现行规约及 Skill 交付物；所有设计文档、诊断计划和本地实施记录不归档、不提交。后续会话使用正常维护入口或 maintenance-agent，不需要本计划的历史副本。
