## 关于总量的专项审视

清理之后总量**下降了**（11210 → 11126），但相对基线 `0a177cf2` 的 9942 仍高 **1184 行**。按 §9「不直接按现值重签目标、不为了下降删功能」，这里指出剩余增长集中在哪几件新增职责，以及为什么必要：

| 新增职责 | 为什么必要 |
|---|---|
| 来源索引、内容单元切分、短 ID 与 basis | 「这一段原文在哪、这一版是不是当时那一版」原来没有答案，取舍与漂移都靠人记 |
| 初筛与整篇编排两份工作件、有效取舍合并 | 十章各自重新决定同一项业务，同一件事就会在三章各讲一遍；编排把「读者在哪一章想知道这件事」先想清楚一次 |
| 材料按章分配与视图渲染 | 作者动笔时这一章要用的原文在手边，而不是十章合起来的提要 |
| 已声明结构的生成与在声明位置的检查 | 「说了要画一张时序图」与「那一节真有一张时序图」原来无人对得上 |
| 装配前校验与 `check ⑯` 成文依据 | 依据不成立时**在写之前**停下（四项返修补齐了前一半） |
| 审查输入重组 | 审查者拿到 Story 与写作设计全文、来源只给坐标，而不是一份逐条对账表 |

这几件都能追到 `02.3-01/02/03` 分册的明写条款，没有一件在替模型做判断，也没有第二份同义真源——B5 四部分正是把「第二份」清掉的那一轮。

**仍然证明不了的那一问**：这些新增是否换来更少的重复理解与返修。它是行为问题，静态证明不了，归 CLI 实跑。

## 这一轮里方案被事实推翻的三处

方案质量总体很高（行号与判断我抽查的都命中），但有三处结论与代码事实不符，都在交回里给了证据：

| 处 | 方案说 | 事实 |
|---|---|---|
| B18 | 删 `FLOW_STATES` 第三项「不改变任何现有行为」 | 它核了调用点传什么，没核契约里 `status` 可能是什么；一条用例当场红。结论仍成立（那个值的唯一写入者从不产生它），但要连同那条用例一起处理 |
| C16 | `imported` 与 `materials_changed_after_complete` 零消费者、无文档承诺 | 前者被 `round` 跨轮次使用；后者有 `init_analysis.md` 的明写承诺与用例守着。**两个都不能删** |
| §6 本轮新增 | `viewDrift` 改为结构化比较且「不新增历史状态台账」 | 两条要求互相矛盾：不存快照就没有「上一次的结构化数据」，只有盘上那份渲染产物 |

共同点：**它们都核了「谁调用它」，没核「它的数据从哪来、谁在文档里承诺过它」**。零消费者的判定要从三个方向都问一遍。

## 我自己在这一轮犯的一个错

收敛 `spec/post_check.mjs` 的 `featuresDir` 时，一条 import 替换没加 assert，静默跳过，文件里留下一个没有 import 的 `featureRoot`；随后用 `node -e "await import(...)"` 冒烟，它打印「模块可加载」——**ESM 的未定义标识符只在执行到那一行才报错**。假绿。是下一步 grep 时自己发现的。

两条做成动作：批量替换里每一条都要 assert 命中；「模块能 import」不是「引用都解析得了」，冒烟要跑到真的执行那条路径，否则直接跑全量。
