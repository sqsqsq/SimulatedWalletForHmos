# Step2.3-02 · 整篇编排与成文

> 依赖：[总方案](02.3-Story写作流程重设计.md)、[步骤01](02.3-01-原材料与初筛.md)通过。此步切换正式作者入口，退出v3逐章指导区，不兼容两条正式写作链。

## 1. Spec后做一次增量整理与整篇编排

在Framework的同一次Spec阶段内，spec.md正文、knowledge-use与验收草稿已形成之后、首次Spec harness之前，执行 `story-build sources --feature <名> --stage after-spec`。

它保留未变的原始来源索引，加入Spec的内容单元，并列出与初筛相比新增、变更、失效的来源引用。knowledge-use和decisions是当前判断入口，不能当作独立原始需求重复累加。初筛仍提供未被编排覆盖的默认取舍，不要求模型将同一源再完整分类一次。

模型一次完成下面的工作，输出story-template.md：

1. 对照原材料、初筛、Spec及决策，识别新增结论、冲突与遗漏。原材料里的义务不会因为Spec漏写而自动失效；真正缺失或错误的设计先回Spec/decisions修正。
2. 保存已有可靠结论，识别需要通过理解与写作继续讲清的参与方、对象、规则、交接、状态和失败后果。已有Spec讲清的直接复用；没有答案的明确问题及其影响，不为把模板填满而提前裁定，也不另写同义“业务模型”。
3. 给出整篇阅读主线、主要解释位置和表达形式的当前建议。多方调用优先解释调用/返回，条件组合便于对照，数据对象与寿命保持结构；写作中允许发现新的关系和更合理的组织，不要求此时枚举全部最终小节。

这不是新增人签阶段。已有范围/关键取舍确需用户确认时沿原确认路径；模型不能把来源冲突擅自改成settled。可继续写的已定部分继续写，但不能把尚未决定的内容包装成最终方案。

## 2. story-template.md：一个需求的一份写作设计

**编排调整规则**：有依据的表达深化、分节和措辞可直接改稿；业务结论变化回Spec/decisions，主要信息归属、来源采纳或已声明结构及其定位变化同步相关编排；组织建议不构成正文内容上限。

路径：`AR/story-src/story-template.md`。由模型运行时形成，不提供预填业务内容，不复活旧的固定story-template模板文件。

模板必须区分：已确认的事实/规则需遵守；必须解释的问题与关键关系需解决；内容位置、详略及解释路线是可调整建议。具体性体现在当前依据和真实问题，不体现在提前列定所有答案。未写入template的有效需求仍须解释，正文可以超出其内容清单，但不能违反真实范围或擅改已定业务结论。

文件由标题、人可读的整体阅读主线和**一个JSON编排块**组成。阅读主线不再逐章复述content/form；具体已知依据与待解释问题放相应content，真实未决仍引用decisions，不强行拆成known/open两份字段。

sources after-spec仅在文件不存在时创建十章body起点，content/form留待模型填写；basis由脚本填。初筛有明确chapters的单元，由脚本预填对应body.sources；默认keep但未归章的单元只进入公共参考索引，不猜归属。模型主要写阅读设计和有变化的引用，不手抄全量ID。已存在的template不再整份生成；新增来源及待处理版本通过sources输出送达，保留已写内容。

```json
{
  "schema": 1,
  "feature": "<feature>",
  "title": "<本需求的业务名称>",
  "basis": {"SE": "sha256:<当前文件摘要>", "PRD": "sha256:<当前文件摘要>"},
  "chapters": [
    {
      "id": "04-solution",
      "sections": [
        {
          "key": "rules",
          "title": "业务规则与真源",
          "content": "已有来源明确导出完成前不能下载。需要讲清任务状态与文件有效期的关系，并核对失败后重新发起的业务含义；未知部分不提前定为新建任务。当前建议集中解释这些规则，写作发现其它有效条件时继续补充",
          "form": "当前选用规则对照表；独有例外可以短说明或另作合适展开，不限定为固定节数",
          "structures": [{"kind": "table", "columns": ["条件", "结果", "后续动作"]}],
          "sources": ["SE#7"],
          "related": [{"section": "06-features/operation", "use": "该节说明用户操作和状态表现，需要理解时可重现相关条件，与本节保持同一规则含义"}]
        }
      ]
    }
  ],
  "source_changes": [
    {"unit": "PRD#9", "disposition": "omit", "note": "此单元为已被明确替代的旧交互", "replaced_by": ["PRD#10"]},
    {"unit": "SE#8", "disposition": "defer", "note": "返回条件仍有冲突", "decisions": ["<现有未决ID>"]}
  ]
}
```

示例以虚构的导出业务演示一章；业务内容不进入交付提示，也不是测试答案。实际包含合同十章且顺序一致。字段约定：

- title为本需求的业务名称，脚本将feature与title生成Story总标题，不能只有需求编号；它不是再次生成全文摘要。
- chapter.id取既有章节合同，十章职责保持。sections是当前编排工作项，不是最终正文小节的封闭集合；每章至少一项，可用key为body、title为空给整个章的阅读重点。确实不涉及时说明依据，不删章；没有想定的下级组织不强填。
- key只在本章内唯一，用于编排内引用；title是当前建议的自然业务标题，不含手写编号。只有已形成独立主题时才用children，最多对应H4；不要求正文与所有建议标题一一对应。
- content写已知的具体依据、需要解释的业务问题或关键关系，清楚区分它们；不能只写“讲清规则”等通用职责，也不能为具体而提前编造答案。它不是允许写作的白名单；作者可增加来自有效需求的条件、例子与关系，已定结论引用Spec/decisions，不在此独立重定取值。
- form说明为什么这种形式适合本节的信息关系，不限定业务枚举、不设图表配额。需要脚本落实的具体结构放可选structures；选择本身由模型负责，脚本检查选择后的执行情况。
- structures是本节已选结构的有限声明，合同见§2.2；不是所有节必填，也不是按参与方数自动生成的规则。
- sources为真实来源单元短ID数组，允许多源合并和跨节参考，本期不支持子范围。可为空：纯组织说明、由Spec投影的附录不必伪造来源；空引用不能授权编造业务结论。
- related每项为`{section, use}`：section取其它编排项的`chapter/key[/child]`，use说明当前建议的互补用途，不能只列邻接ID，也不写成永久的“这里只能讲某项”。二者非空、目标在编排中存在；引用body意味着整个章的阅读职责，不要求正文必须有同名小节。无真实关联时省略。
- source_changes为相对初筛的稀疏变更，沿用01的items字段；不变的omit/defer不再抄写。可选replaced_by列有效替代单元，禁止自指和循环；这只核引用，不证明内容等价。单元有独有义务时不能以“派生内容重复”整段排除。

**有效取舍只按一条规则计算**：同一单元以template.source_changes的完整条目优先，其次selection.items，最后默认keep。变更条目整体替换，不逐字段拼接遗留理由。模板内若sources已经明确定位该单元，其正文位置取这些编排项；没有明确定位时，继承有效取舍中的chapters作为章级参考；仍未分配的保留在公共材料入口。

keep/defer都可供写作参考；defer不因sources有引用而自动解决，真实结论看decisions。omit与同一template内显式sources并存属于合同冲突，须先改取舍，不能用简单并集把排除洗成采用。模型重新采用初筛omit的材料时，source_changes显式改keep，再声明位置。replaced_by只是来源主张，不能充当未采用的语义证明。

不再要求每个单元在template重复登记处理出口；脚本只核显式判断、合并结果和引用一致性。默认可参考、已有定位、正文讲清是三件不同的事。来源反查和独立审查必须覆盖未分配、omit与defer材料；不能将“没有未登记ID”当作验收结论。

业务结论仍属于Spec/decisions。content具体说明与本章相关的已知及未知，不另抄问题正文；编排不决定未决变成已定。编排调整统一遵循本节开头的“编排调整规则”。

### 2.1 编排任务内完成“原材料→编排”核对

模型完成编排的最后一个动作是回到原始来源，核对重要业务要求有没有具体解释位置，尤其看混合用途单元、有效omit/replaced_by、defer及decisions未决，以及Spec新增的结论。采用一个小节不能代替检查其中各项独立义务；仅因Spec没有写而排除原始要求不成立。

对跨方接口、对象身份、状态/终态、授权与控制等影响多处正文的关系，核清产生方、使用方、条件、结果及边界；不要求每节填写一组固定分析字段。已有结论正确就复用，来源冲突或设计不满足需求则回Spec/decisions修正，再更新编排。

该动作属于当前编排任务，不新增Agent、检查阶段、签名或“已核对”文件。结果是被修正的具体编排与已有决策，脚本不声称能辨别content是否有深度。独立verifier还会从来源重核，不能只验证作者选中的段落。

### 2.2 已选结构的生成与检查合同

structures仅支持本次已有渲染能力可直接落实的表、图语法及来源图片；其他合理表达保持form自然语言描述，由语义审查评价，不为覆盖所有图种建设通用渲染器。

| 声明 | 首次草稿生成 | 局部与最终检查共用的事实 |
|---|---|---|
| `{"kind":"table","columns":["条件","结果","主责"]}` | 生成声明的表头、分隔行和现有待填占位；模型填业务行 | 在本节正文中存在包含这些列的表，比较复用现有表头规范化；允许额外列，不检查业务行数或内容对错 |
| `{"kind":"diagram","language":"mermaid","type":"sequenceDiagram"}` | 生成对应围栏、类型首行及待填占位，不生成参与方和箭头 | 在本节存在对应语言、类型的闭合围栏；type本步支持sequenceDiagram、flowchart、stateDiagram-v2，检查类型不证明关系完整 |
| `{"kind":"image","image":"image@<既有图片摘要>","caption":"<本节图意>"}` | 从source-index.images解析真实图片，用现有图片路径能力生成本节Markdown引用及模型填写的图意 | 图片ID存在、文件可读、实际引用位于本节；不靠标题文本判断图意准确，也不要求复制废弃/无关图片 |

columns必须为非空字符串数组，type必须是上述已支持类型。声明损坏明确指出编排位置，不能忽略后继续成文。模型可选择其它表达放form中，不冒充已受结构检查保护。

image与caption在图片声明中必需；图片取舍仍归现有materials登记，编排只决定采用图片的正文位置。框架号/单号不进入图意。样例校验要覆盖“图片虽然可读但放在另一节”的情况，不能用全篇含这张图代替本节落实。

声明依所属编排项定位：title为空时作用于整个章，正文可在任意合适子节落实；title非空且确实声明structures时，复用story-chapters已有标题规范化与包含匹配定位，在所属章内必须唯一命中；零命中或多命中报目标及候选位置，由作者消歧，不默认取第一个，不由另一个目标的表或图代为满足。没有结构声明的建议标题不作为提交门禁。同项相同结构要求合并，不借此给表图数量加配额。原章节合同必要结构仍有效；动态声明只落实已经选择的形式，不限制该位置增加其它合理表达。

已有草稿不自动改写。选择改变时先同步编排，脚本提示已有正文与新选择的差异，由模型编辑后提交；不因一次返修就重新生成其它节。来源内容缺失、关系画错、空泛表格等仍由语义核对发现，不追加行数或箭头数门槛。

## 3. 编排后的材料视图与草稿

`story-build skeleton --feature <名>` 改为消费当前source-index与story-template，而非直接播种十份固定写作任务。它先校验编排结构、来源版本、引用目标和原合同必要章节，再更新材料视图和输出草稿。

### 3.1 最终材料视图

本期只有skeleton生成正式材料视图；其输入为索引、selection与template按§2解析的有效取舍。collect不实现，无初筛版/最终版切换或覆盖保护协议。先在内存完成引用、路径与结构校验再写派生视图；失败不改作者草稿，不宣称半套视图已齐。

每个chapters/<章ID>.md包含：该章当前阅读重点与建议组织、content/form、独有原材料全文、公共材料定位、相关输出章读取路径及Spec/knowledge-use/decisions入口。文件头说明这是工作输入而非内容上限；作者可从完整来源目录补读未预分配但实际需要的材料。只有被两个及以上编排项显式引用的单元全文放shared.md一次；仅一个编排项显式引用的全文放所属章。仅有初筛暂定chapters、未分配、未显式引用的defer以及omit只列索引行（标题路径、来源路径:行范围、取舍/问题入口），按需读原件，不自动汇成公共全文。相同单元在同一编排项内重复引用只算一次；上下文随原单元定位读取，不另复制一份祖先正文。

相关已写章节不复制进材料视图，模型需要时直接读当前Story或目标草稿。这样不会把过期已写章作为静态原文反复灌进十个头部，也不会让准备动作批量改输出文件。

正文原文只复制到对应工作视图；不修改源文件。图片与链接沿01的方法定位。模型发现输入有误，应改真源或编排，然后重建视图，不能在视图文件里私改后当成新依据。

### 3.2 输出草稿

继续使用 `AR/story-src/drafts/NN-<章名>.md`，只包含作者正文、章/节标题和现有必要结构种子。大块指导区彻底退出，输入与输出不再在同一文件内通过HTML边界保护。

初次生成时脚本按编排铺标题及structures声明的表头/图语法，保留原有术语和附录机器投影能力，原合同与动态要求合并生成。已有草稿绝不重新播种或覆盖。编排改变后，脚本只列可计算的来源分配、采纳与structures差异，附候选受影响章；普通标题措辞不报，模型自行判断阅读主线是否需调整，作者在现有草稿编辑；不能因为模板更新而重建十章。现有Story已写而草稿缺失时，沿用按现稿补回目标章的恢复能力。

按§2的“编排调整规则”修改受影响内容，不重做其它章。新增小节不因为“模板没列”而被拒，缺失原合同必要结构仍应拦住。

## 4. 写作与提交

作者首次成文先读整份写作设计和公共材料索引，再处理当前章的输入视图；shared正文按该章显式引用的单元范围读取，不要求每章重读整份shared。每章围绕已知依据与真实阅读问题展开；写作也是继续理解的过程，可以发现此前遗漏的条件或更合适的表达。共享原文不是每章都重讲全部过程的理由，模板也不是禁止补充重要内容的理由。

`story-build chapter --feature <名> --chapter <标题> --from <草稿>` 保持接口和局部结构检查。提交前剥必要种子说明，附录先投影，再用共用chapterProblems核候选；失败不改Story、不删除草稿，通过只替换目标章。

增加的检查是原合同确定的章/必要小节、structures中已声明的表头/图语法及其可定位目标、来源/投影保护，不要求正文逐个复现建议目录。模型明确选了sequenceDiagram却交flowchart、或删掉已选主责列，由脚本提示落实或同步已改变的选择；形式是否合适、关系是否正确仍归模型。不检查词数、相似度或按表行数推参与方。

模板可注明“某局部详细过程由下一节解释”，但必须有实际落点。模型不得以相关引用代替每个读者必须在当前章理解的条件或结果。验收重现预期值、图表达关系与表解释属性可以互补，不追求字面零重复。

## 5. prepare与恢复：短输出，持久依据

保留一个 `story-build prepare --feature <名> [--chapter <标题>]` 作为写作恢复入口，语义改为从当前文件给出下一项工作及精确读取位置；不再刷新草稿指导区。

stdout普通成功输出最多保留必要的三类信息，顺序固定：

```text
NEXT: <当前实际动作；需要读的文件先列在这里>
INPUT: <当前编排/章节材料/公共材料及related目标章草稿的实际路径>
RESULT: <本次已保存什么；若只是恢复查询则明确未写入>
```

related逐项解析到实际草稿路径；目标草稿未建立时明确缺失并给该章材料视图路径，不制造已写正文。详细问题写入现有报告/错误输出，不在长日志尾部才首次教下一步。执行提示明确命令输出承载任务，直接运行并保留退出码，不外套head/grep截断；若宿主截断，读取已落盘输入，不能靠开场推断要求全文。不给“已读”字段，不捕获模型内心状态。

磁盘判断与消费者：

| 当前事实 | prepare/status给出的动作 |
|---|---|
| S4未complete | 回原story_flow当前合法步骤，不越过范围确认 |
| 缺索引或selection不可读 | sources before-spec → 模型读取原文、填写稀疏selection；之后进入Spec |
| Spec尚不可用于编排 | 回现有Spec作者入口，保留初筛，不强制生成空Spec凑流程 |
| 缺可装配编排或源版本变化 | sources after-spec → 模型形成/调整story-template，不重做无关来源判断 |
| 有编排而材料视图/草稿未建立 | skeleton，已有草稿保护 |
| 有待写章 | 读整篇设计与目标材料视图，写对应草稿，chapter提交 |
| 所有章有正文 | 进入03的写后核对，读取当前完整Story和编排；不用重复生成草稿 |
| 已登记story_written | 原Harness/verifier/回执路径，不输出必然被冻结守卫拒绝的写命令 |

flow状态仍只有原有状态集合。Python status只给阶段级动作：complete后给“运行story-build prepare”，story_written后给原审查/回执动作；不启动Node，不实现prepare --status-only，也不复制写作子步骤。子步骤只由story-build根据磁盘事实派生。

判定合同分层，不能用一个“有效”替代全部条件：

| 谓词 | 确定性定义与用途 |
|---|---|
| selection可读 | JSON可解析，schema/feature/轮次及字段类型正确，显式unit唯一，ID/章/decisions引用及理由合法；空items合法。basis是否当前另核；可读不证明初筛已执行 |
| Spec可用于编排 | 合同SPEC路径可读，复用specSection取得现有“功能清单”正文，pipeTables能取到至少一行经isPlaceholderRow判为非占位的功能行；knowledge-use与验收输入按现有读取接口可解析。这里只识别正文已开始形成，不能证明Spec完整；其它Spec检查仍留在原harness，不要求它或verifier预先闭环 |
| template可读 | 恰一个可解析JSON块；schema/feature/title正确，章ID按合同齐全且唯一，section key及related引用合法；content/form类型正确。此层允许待填骨架，便于报告定位 |
| template可装配 | 可读且每章有工作项、content/form无空值或现有待填占位，sources及source_changes可解析无冲突，structures合法，selection/index/basis为当前版本。覆盖语义不在该判据内 |
| 源版本变化 | 实际登记来源集合、文件原始字节摘要或当前轮次与index/basis不一致；仅派生视图改写不算源变化。缺文件、新增/删除源分别报告，不用空材料放行 |
| 可登记 | 可装配，加当前Story通过03的原结构/投影/编号/冻结检查；不要求正文照抄建议目录，不把来源分配当语义完整 |

Spec判据只复用story-build.mjs现有specText/specSection/pipeTables/isPlaceholderRow及输入读取能力，不调用整套check-spec或另建完整Spec validator。其尚未满足时直接列缺失输入/正文坐标，回Spec作者，不让模型猜“尚未形成”的含义。

## 6. 修改与退出清单

改动：story-build的sources/skeleton/prepare/chapter及相应帮助；成文专用来源/编排模块；story_flow的Spec内接续；phases/story-write.md、phases/spec.md、SKILL、author.mjs入口；story-chapters合同只保留稳定读者职责与已有必要结构。

提示词接线固定在现有文件，不新增story-plan.md或第二份阶段说明：

| 文件（相对story Skill，author除外） | 保留/改写/删除 | 消费者与触发时点 |
|---|---|---|
| SKILL.md | S4改候选提交；complete后读story-write初筛节，再进入现有Spec入口 | 主执行者，S4收口之后；不在此重复十章写作要求 |
| rules/ar_design_init.md | 保留提取任务，输出改design-draft及带--from的complete | S4作者，写AR之前 |
| phases/spec.md | 保留Framework Spec职责；正文、知识和验收草稿形成后，harness之前接sources after-spec与story-write编排/成文 | Spec作者，同一次Spec pass内，不等阶段闭环后才写Story |
| phases/story-write.md | 主干替换为初筛→整篇编排→成文→写后核对四段；分别列输入、动作、产物和恢复入口，删除v3逐章重新理解与指导区说明；编排调整规则只在编排段定义一次，其它段引用，不逐段转述 | 主执行者按当前工作段读取，prepare指向对应段，不每次读全页 |
| hooks/spec/author.mjs | 保留Spec材料/知识要求；Story仅给当前动作和上述文件对应段入口，删除重复逐章问题表与大块写作方法 | Spec开始的作者任务包；不承担Spec完成后的隐式调度 |
| core/story_flow.py 的next_step与帮助 | 同步S4两处旧提交文案、complete后prepare、已登记后的审查路线 | 恢复会话；只给阶段级路由 |

最后一章提交成功时，stdout首屏给“读取当前Story与template，执行写后核对”及实际路径，后接登记命令位置；完整核对任务已在story-write对应段持久保存。不能只把动作埋在规则页后半段，也不在stdout重抄整套方法。

必须删除：v3指导区边界、引用包装、刷新与剥除协议；guidanceRows/relatedChapters；context_chapters字段及消费者；长stdout整稿分发；写作说明中“逐章重新理解、最后补全局”的旧主干。旧项目历史草稿保留，不做迁移兼容分支；本步真实测试使用新流程的新工作区，内网已有进行中需求的迁移另按用户安排，不擅自批量改历史稿。

现有author.mjs继续负责Spec所需材料与知识要求，Story相关部分只给进入初筛/编排的入口，不再把全部Story章要求展开在那里。图源对应、术语、必要表头继续复用已有能力；来源图可以在保持事实与对应的前提下合并/改画，不能将原图的形状强制作为最终表达。

## 7. 完成条件

1. Spec新增设计进入编排，原始义务不能因Spec省略被自动删除；初筛不重复完整再跑。
2. 动态编排可用不同的合理分节/形式表达同类需求；固定章职责仍有效，不强迫所有章有H4。
3. source-selection与template按同一优先级解析，正式视图只有skeleton一个写入入口；无重复来源身份冒充多份依据。
4. 修改编排不覆盖作者正文；旧引用、失效来源和无法定位的已选结构明确报错；新增合理子节和表达深化无需修改模板即可提交，不触发其它章重写。
5. 单章坏稿不写入、成功只改目标章；全部正常链可到原登记入口。
6. head截断行为作为已知实测风险验证：NEXT在首屏，工作要求可从持久输入读回；不以stdout完整性自证模型已读。
7. v3退出项在生产调用与说明中归零；其原有效职责有当前消费者。归属和规模写回反馈，不能只给删除文件数。
8. 初稿按模型声明产生表头与图语法；缺列/改图类型在当前节提交被拒，修正或有依据地更新编排后通过；另节同形结构不能代替。检查代码共用，不新增图表数量或语义代理门槛。
9. 实际编排保存本需求已有结论，提出具体业务问题并区分未知，不强制填完所有答案；作者能在不改变已定需求的前提下继续发现并深化，不能靠sources齐备或正文完全服从模板宣告语义完成。
10. 根title形成可识别的业务总标题；related能说明实际互补用途；已选图片落在声明节，错节或缺图被定位。材料摘要与ID由脚本产生，不让模型手算。对照template金样评价具体性，不以相同小节数或字段字数判通过。

相关检查复用writing_flow、author_task_package、author_context_entry及新来源/编排测试；不得拿候选金样全文注入真实被测作者。
