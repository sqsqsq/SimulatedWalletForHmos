# Step2.2-new 最新评审意见复核

> 2026-09-09。复核 reviews/16 与当前生产代码；本次未修改实施方案、预算或生产代码，未运行测试或 CLI。

## 1. 结论

reviews/16 的主体判断成立：方案方向可以保留，预算、运行材料成本、恢复入口及直接消费者应在实施前落实。但不能整份原样转成执行清单。L2 会引入不需要的离线写作分支；L5 对共享数组的要求超过实际必要性；“四个宿主都有 verifier，所以不影响现有交付”的结论过强。另有一项交付门的返回值语义遗漏，必须补入 D 段设计。

本次只评议接收哪些意见及如何处理，不重写方案。补齐交接细节不能等同于继续增加机制；每个新增条件仍须证明它解决了实际责任缺口。

## 2. 对 R1–R3 的处理

| 意见 | 复核结论 | 应采取的动作 |
|---|---|---|
| R1 预算 | 接受需要给出分类峰值、完成上限及增删估算。现有余量少是事实；但“必然装不下 A”仍是估算，不能把历史估算倍率当本次已测结果 | 先列准备、校验、失败恢复、删除项的分类估算，再提出需调整的数值。当前未授权改预算，也没有因此要求用户立即签一个尚未给出的数。不得为了旧额度压缩排版或删除必要功能 |
| R2 任务体量 | 接受逐章测量与后段首稿观察；约 75KB 是正文重复装配量，不是新增 token 的完整测量 | A 段记录完整任务文件字节、正文部分、方法与命令部分；真实运行对照各章首稿和返修。保持当前整章关联输入作为待验设计，不凭单例体量先删验收所需来源 |
| R3 重复发现 | 接受在目标处明确待验假设 | 明写：脚本不判跨章语义重复，作者、统稿和独立审查负责判断；任务生成正确仅是结构完成。失败后定位输入送达或语义判断问题，有证据才改责任点，不无界追加提示或相似度规则 |

R2 中 12,288 字节是已有作者任务包的测试约束，不自动成为新章任务的宿主读取上限。应分别报告字节、实际读取范围和可取得的 token 数据，不混为同一度量。材料 build 的 12.9ms 单例也不包括每次启动 Python、任务序列化和模型读取成本，不能据此认定整条准备链便宜。

## 3. 对 L1–L5 的处理

**L1 接受，并补一处直接消费者。** spec_stage_step 的逐章/登记命令要随新参数更新；next_step 的 story_written 分支当前还写“它说没有审查员就直接下一步”（story_flow.py:971）。D 段采用无审查拒交付后，这句必须同步，否则正常恢复提示会把作者引向注定失败的交付门。

status 保持只读。没有有效任务时给 prepare 动作，由 prepare 生成并返回文件路径；不为让 status 显示文件而隐式创建任务，也不按文件时间猜“最新有效任务”。若提供已有任务路径，应由同一输入校验能力确认有效。

**L2 不按原建议接收。** story-build.mjs:2631 已明确 `--offline` 只允许 check；这是诊断边界，不是缺失的 skeleton 功能。保留 `skeleton --offline` 失败。测试正式 skeleton→prepare 链应建立最小合法流程夹具；纯骨架生成可测试现有生成职责，无需给生产命令增加“没有契约也写作成功”的旁路。正常入口缺必需契约应清楚失败，而不是打印未准备任务后当成正式流程成功。

**L3 接受。** 增加只修改 story-write.md 后旧任务失效、草稿保留的确定性验证。恢复输出应明确作者要求已变，刷新后核差异；不让用户重做业务范围确认。

**L4 接受。** D 段必须验证 PASS 汇总后附简短说明仍可解析；保留既有格式和原样报告。是否改解析器以测试及真实返回合同为准，不能仅检查提示词已删除旧句。

**L5 接受共享判据，拒绝指定必须共享数组。** 共享 chapterProblems 及现有合同、由局部与全篇调用同一实现即可。再强制建立规则数组可能引入无必要抽象。验收应验证同一坏章在两入口得到一致结果、全篇独有条件不提前误拦，不以某种代码容器作为正确性证明。

## 4. 新发现：报告格式 PASS 与审查结论 PASS 不是同一个值

当前 hooks/shared/verifier-report.mjs 的 storyReviewProblems：

- 第 204 行在报告判项不是 PASS 时，校验 blocking_findings/advisories 的结构。
- 第 238 行在结构合格后统一返回 `status: 'PASS'`，detail 才保留报告实际判定。

因此方案 §8.4 所说“消费 storyReviewProblems，只有明确 PASS 才放行”，若直接比较现有 status，无法实现新增政策。格式合格的非 PASS 报告也可能返回这个值。这不等于已经证明当前端到端会错误交付：前面还有 Framework 回执和实际语义门禁；此处指出的是新设计不能依赖该返回值表达它并未表达的事实。

D 段的最小改法：保留现有 status 的格式校验含义，返回额外的 `reviewVerdict`，值来自实际 story_reader_review 汇总行，缺行/不可读为 null。交付调用方同时要求现有回执通过、格式结果 PASS、reviewVerdict 为 PASS。现有其它消费者不被改成新的业务含义；不从 detail 文本反向解析结论。

相关确定性验证应覆盖“汇总判项 FAIL、明细结构完整”与“汇总 PASS、附简短说明”两个输入：前者不能仅凭格式结果通过新增交付条件，后者应正常解析。无需重写全部 verifier 协议。

四份 adapter 的 verifier_subagent=true 只证明登记了能力。实际选用哪个 adapter、是否启用、报告是否产生且绑定本轮，仍须从运行证据判断。因此保留无审查拒交付的政策说明及适用范围，不能把它描述为“仅影响离线/夹具”。

## 5. 与后续步骤及整体目标的关系

接受 reviews/16 §5：步骤 4 开工前按 2.2-new C/D 的实际产物核回看位置、读者任务和预算。将此依赖记入总方案即可，不在本步提前实施步骤 4，也不把新 whole 工作与步骤 4 的回看写成两次重复整稿。

本轮优先落实接线、分清报告结论和保留只读边界。任务体量与真实重复改善继续作为行为验收项；不因为设计写得更详细，就宣称模型执行已更可靠。
