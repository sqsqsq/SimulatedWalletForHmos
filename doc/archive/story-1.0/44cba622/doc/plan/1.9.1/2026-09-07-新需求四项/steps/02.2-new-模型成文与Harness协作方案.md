## 1. 目标与设计原则

Extension 的执行者是模型。提示词定义当前思考任务，脚本准备和保存确定性材料，Agent 的读取/编辑工具完成工作，Harness 约束提交和推进。最终质量由模型对内容的理解、判断与审查决定，不能用文件存在或字段齐备代替。

本步目标：

1. 作者在首次写章时得到当前所需事实、已写内容和本章职责，减少重复生成同一过程。
2. 图表达真实过程与交接，来源标记不冒充内容完整性。
3. 统稿实际修正重复、遗漏、矛盾和重组错误，不以自述清单作为完成证明。
4. 确定性问题在正确的提交位置拦住，错误指向可编辑对象，避免查源码、反复改字或删事实换绿。
5. 独立审查取得完整对象并做内容核对，无法验证时如实保留缺口。

确定且复杂的编号、表头、投影、定位、输入版本比对由脚本承担；相关性判断、业务取舍、信息归属、图的语义、重复与互补、事实是否支持结论由模型承担。脚本不根据关键词或相似度替模型做这些判断。

### 2.2 采用的事实与不采用的推断

已经观察到：作者读过本章提示但仍重复；七行统稿自述没有准确反映结果；后续修正多集中于机械问题；独立审查有执行记录但漏报真实内容问题。由此需要改变当前工作材料与提交任务，而不只增加原则说明。

不把“提示全部无效”“脚本 100% 可靠”“verifier 永远查不了重复”作为前提。run_id 变化不代表上下文归零；后几次检查中的失败比例包含难例筛选，不能据此设上下文阈值或自动换会话。保留过程记录用于定位原因，不根据未经验证的相关性增加调度机制。

本步对跨章重复的改善是待验假设：相关正文及时送达、整稿比较和独立审查共同帮助模型发现问题，脚本不承担语义重复检测。A–E 实施及结构检查通过，不能宣布重复问题已解决；效果由 §11.2 的真实首稿、统稿与审查结果判定。仍有重复时按该节定位输入或判断的失效点，不转向相似度门禁，也不无界追加提示。

### 2.3 本步做与不做

做：成文任务准备、按章提交的局部结构检查、整稿修订任务、必要输入缺失处理、接续输出、审查对象送达和对应的验证。

保持：Step2.1 的十章职责与自适应形式，三级自然组织、源图对应、流程总览、验收追溯、附录投影、decisions 真源、人工意见保护、现有归档边界和过程件保留。

不做：业务分类器、逐事实分配台账、相似度门禁、全量裁决表、新 Agent 层级、自动换模型/重启上下文、通用任务框架、框架源码改造。知识协议归步骤 3，审核点发现归步骤 4，会议输入归步骤 5；本步不借功能全集复盘把所有历史问题一起重构。

## 3. 一条成文路径与职责分工

```text
现有材料/范围/Spec/决策 + 章节合同
        ↓ 脚本准备当前任务材料，落盘并给出下一步
模型读取任务 → 思考本章独有内容 → 编辑本章草稿
        ↓ chapter 提交：输入新鲜性 + 局部确定性检查
校验后替换目标章 → 准备下一章任务
        ↓ 全部章完成
脚本准备整稿任务 → 模型对照、推演、修改相关章
        ↓ story 登记：最终投影/编号/渲染/全篇检查
现有 Framework harness → 原有独立 verifier
        ↓ 核对内容，报告真实发现与依据
既有回执与交付检查 → 依用户选择归档或进入后续阶段
```

| 执行者 | 明确职责 | 不承担的判断 |
|---|---|---|
| 作者模型 | 阅读相关依据，决定内容归属与形式，编写/修订正文和实际业务判断 | 不手算编号、复制技术契约表、不自行编造完成凭据 |
| 现有脚本 | 提供当前输入、生成固定部分、验证版本与结构、保存产物、给出接续动作 | 不判语义重复、不按表行数猜完整业务参与方、不自动删事实 |
| 独立 verifier | 对照来源与最终稿，检查覆盖、关系、依据与独有信息 | 不以作者自评或结构 PASS 代替自己的核对 |
| 人 | 范围、未决取舍、最终评审与验收 | 不替模型逐项整理材料或维护内部任务字段 |

本方案中的“任务”是同一个成文模型当前应处理的一项工作，不新增会话或子 Agent。复用现有工具和状态入口，不要求用户增加交互轮次。

## 4. 当前任务材料：及时落盘、直接可读

### 4.1 准备方式

在现有 story-build.mjs 增加成文专用 `prepare` 动作，不新建任务运行器：

```text
story-build prepare --feature <名> --chapter <章名>
story-build prepare --feature <名> --whole
```

前者准备一章，后者准备整稿。skeleton 完成时自动准备第一章；首次 chapter 提交成功后自动准备下一待写章，最后一章提交后准备整稿。正常路径不要求模型额外发现并手工调用 prepare；输入更新、恢复或返修时，NEXT 指向它。

任务材料落在 `AR/story-src/tasks/<章ID或whole>/<输入摘要>.md`。同一输入复用已有文件，输入变化产生新文件，旧材料保留供诊断；文件名与摘要由脚本产生，不让模型维护版本号。不引入全局任务注册表、队列或第三套流程状态。

文件只包含：简短的脚本元信息、本次工作目标、实际输入与来源、编辑对象、提交方式。首行用 `<!-- story-task: <单行JSON> -->` 保存元信息，读取时仅匹配此前缀并用 JSON.parse 解析，不增加 YAML/frontmatter 解析器。字段和版本比较按 §4.4 执行；不记录“已阅读”“已思考”等模型自填状态。

这是必要的有限新增：仅延长提示更便宜，但仍依赖模型回忆初始材料；通用编排或新 Agent 成本更高且无当前实证支持。准备函数只服务现有成文动作，新增复杂度须与删除七行凭据等冗余一并核算。

### 4.2 一章的输入如何组成

| 内容 | 来源与准备方式 |
|---|---|
| 当前该做什么 | 已有待写 marker、当前指定章与章节合同；不是模型填写进度 |
| 本章必答问题和独有职责 | chapter.questions 与短 form.note，复用 Step2.1 定义；共用方法只写一份 |
| 当前范围及已定判断 | 从既有流程契约的有效范围和 decisions 读取；保留未决标记，不将其转成正文结论 |
| 相关已写正文 | 按下表的章节关系取当前 Story 原文，保留标题及来源；不让模型再写摘要 |
| 原始材料与知识依据 | 现有材料清单、Spec、knowledge-use 的当前路径/定位；本章需要查证的直接内容用原有 Read 获取，不把全部上游重复内联进每章 |
| 固定结构与源图入口 | 既有表头/术语种子、来源图任务数据；不任意预选一张图当总览 |
| 编辑与提交 | 实际章草稿路径、对应 chapter 命令及任务文件路径 |

章节关系是阅读职责，不是业务场景分类。以章 ID 在现有章节合同中用一个 `context_chapters` 列表声明，脚本只按该列表提取已完成章；不得另在代码复制一份关系表。

| 当前章 | 默认提供的已写章 |
|---|---|
| 背景 | 无；直接依据需求输入 |
| 术语 | 背景 |
| 范围 | 背景 |
| 业务方案 | 背景、范围 |
| 业务流程 | 范围、业务方案 |
| 功能说明 | 业务方案、业务流程 |
| 异常与恢复 | 业务流程、功能说明 |
| 验收 | 范围、业务流程、功能说明、异常与恢复 |
| 交付与上线 | 范围、业务方案、异常与恢复 |
| 附录 | 无全文重复；使用既有契约投影与材料清单，必要时回查正文 |

这些章给出比较基准，不排除模型依据当前业务补读其他相关内容。提取整章以防脚本按关键词切掉语义；某份原文较长时在任务文件分段保留，明确后续范围，用原有读取工具分页读完。不得静默截断、只保留开头就称输入齐全。

### 4.3 输入摘要只证明材料版本，不证明模型读过

章任务摘要覆盖：有效范围、当前材料版本、Spec、knowledge-use（按现有适用规则）、decisions、章节合同与本任务包含的相关章原文。材料版本按磁盘现状核实，不能只信已经落盘的旧清单；具体算法与依赖集合见 §4.4。排除日志、时间戳、任务文件自身和当前可编辑草稿，避免自依赖。

提交时从权威来源重算，材料变了就拒绝使用旧任务，输出刷新任务的动作；草稿保留。模型不手填摘要，也不要求逐文件向人确认。任务文件可读、版本一致，只能证明有一份与提交匹配的工作输入，不能当作已完成阅读或语义核查。

### 4.4 命令和任务文件合同（实施时直接采用）

本文命令中的 `story-build` 表示 `node <extensionRoot>/skills/story/scripts/core/story-build.mjs`；Python 入口同目录。`extensionRoot` 和 feature 根目录沿用 framework.config.json 的路径配置，NEXT 输出当前工程可执行的完整命令，路径有空格时正确引用。

| 入口 | 新参数与合法组合 | 写入对象 |
|---|---|---|
| `prepare` | `--feature` 必需；`--chapter <合同标题>` 与布尔参数 `--whole` 恰选一项 | 当前任务文件；不改 Story、决策、材料或流程状态 |
| `chapter` | 原参数外，`--task <文件>` 必需 | 局部检查通过后替换目标章，再准备后继任务 |
| `check --task <文件>` | 仅正式 feature 上下文；验证 whole 任务并运行原全篇检查；附加 `--inputs-only` 时只核任务依据和待写 marker；不与 `--offline`、`--deliver` 混用 | 无 |
| `story_flow.py story` | 新增必需的 `--task <whole文件>` | 沿用投影、编号、Review 渲染和最终登记 |
| `check` / `check --offline` / `check --deliver` | 原参数含义保留；普通诊断不要求任务文件，正式交付另按 §8.4 | 无 |

保留 `--project-root`。在 parseArgs/main 中补参数读取和上述互斥检查，缺值或非法组合退出 1，不能把未识别的 `--task` 静默忽略。`--inputs-only` 必须同时有 `check --task`。没有新增 `task-check` 命令；Python 的登记预检查使用 `check --task --inputs-only`，最终检查使用 `check --task`，顺序见 §6.4。

`--offline` 继续仅用于只读 check；skeleton/prepare 携带该参数均退出 1。正式 skeleton 在写入前核必需流程契约，缺件不降级为“骨架成功、无任务”。测试完整写作链应建立最小合法流程夹具，纯骨架生成测试直接验证生成职责，不新增离线写作分支。

任务元信息固定为以下对象。示例中的尖括号由脚本替换，`chapter_id` 对 whole 为 null，所有路径存工程相对路径并统一 `/`：

```json
{
  "schema": 1,
  "feature": "<当前feature>",
  "task_kind": "chapter",
  "chapter_id": "01-background",
  "input_digest": "<64位小写SHA256>",
  "inputs": [
    {"key": "spec", "source": "<feature根>/spec/spec.md", "sha256": "<64位小写SHA256>"}
  ]
}
```

`inputs` 是下表全部依赖的计算结果，不能只写示例中的一项。虚拟输入的 source 使用 `文件路径#字段名` 或 `文件路径#章节ID`。缺少的合法可选文件，其 sha256 为 null；因此后来新增它也会使任务过期。读取时核 schema、feature、kind、章节匹配、摘要及输入字段类型；任务必须位于本 feature 的 tasks 目录。坏 JSON、缺字段、跨 feature 或错误种类均退出 1。任务正文不供模型修改；不增加签名、读取回执或防篡改协议。

| key | 权威输入与计算口径 |
|---|---|
| `scope` | story-flow.json 的 `split` 与 `rounds` 中的 `round`、`gates`。gates 仅保留 gate/chosen/outcome/basis，数组保留原顺序；不含时间戳、操作人、登记时间。prepare 另要求现有流程已 complete，冻结后的写操作继续被原守卫拒绝 |
| `materials` | 调用 materials.py 的只读快照入口，复用 `build(feature_root)`，对返回对象求摘要；它枚举当前正文、图片和收件箱，能发现新增/删除，不仅重算旧清单已有文件 |
| `spec` | 当前 spec/spec.md 完整内容 |
| `knowledge-use` | 当前 spec/knowledge-use.yaml；现有 activeKnowledgeEntries 非空时必需，空知识且文件不存在为 null；存在但损坏仍报错 |
| `knowledge` | activeKnowledge 的 manifest 和已登记文件，逐文件形成有序输入项；复用激活与缺件检查，不按业务名选子集 |
| `decisions` | 当前 decisions.json 完整内容，使用现有 decisionList 核合法形态；合法空数组与缺文件严格区分 |
| `contract` | 当前 story-chapters.json 完整内容 |
| `author-task` | 当前 phases/story-write.md 完整内容，使作者方法调整后旧任务失效；prepare 从中取得章写作或整稿对应的要求块 |
| `chapter:<id>` | 仅 chapter 任务有：context_chapters 中各章的完整原文；尚未完成用 null 表示。目标章草稿和目标章自身不在此集合 |

确定性序列化：JSON 对象键递归按字典序排列，数组保持顺序；文本去 UTF-8 BOM、CRLF 统一 LF，其他字符保留；SHA256 使用 UTF-8。各 inputs 项按 key 排序，input_digest 对 `{schema, feature, task_kind, chapter_id, inputs}` 求完整 SHA256。Python 只返回材料对象，任务摘要仅由 MJS 计算，不复制两份算法。

在已有 materials.py 增加维护内部的 `--snapshot --feature-root <绝对目录>` 只读入口：stdout 仅输出 build 的 JSON，异常 stderr + exit 1；不调用 refresh、不写清单、不推进轮次。MJS 用参数数组启动 Python，复用本工程已有 Python 命令选择方式，不拼 shell。快照与登记清单的 digest 不一致或存在未并入来源时，prepare/提交报告材料流程未更新，NEXT 回现有 round/导入流程；不能自动替人接受新范围。该调用的耗时纳入 §12，不能声称每章校验没有材料扫描成本。

whole 额外保存完整 Story 比较底稿，但底稿不进入 inputs/input_digest。相同输入复用已有 whole 文件，不因正文编辑生成新任务。模型返回 whole 时同时读磁盘当前 Story，旧底稿用于比较，不当作最新稿。

**成文中新增决策的处理选定为刷新，不设计增量豁免。** 发现新判断时先按现有协议更新 decisions，再 prepare 当前章，保留草稿并核新增判断影响后提交；修改旧判断同样处理。整稿期间更新 decisions 后刷新 whole，再核受影响关系。任务会因此变化，但草稿不重建、已完成章不重新生成。不允许略过真实决策登记来维持摘要，也不要求写作开始前穷尽全部决策。

## 5. 作者任务：补齐当前问题，不重新生成整套故事

### 5.1 写一章

模型读取当前任务和章草稿，先比较“相关已写内容已经解释什么、本章还需解释什么”。结果直接进入正文，不生成第二份内容分配表。

相关章已经讲全的过程只作必要承接；本章展开自己的独有信息。需要重现指标、条件、结果以保证独立阅读时可以重现，但不得改变含义。图讲关系、表讲属性、叙述讲理由属于互补，不按字面相似度删除。

没有依据的判断不能写死；已知错误回到权威产物修正；真实未决取舍沿用 decisions/现有确认路径。不能为了通过引用或用词检查删掉真实业务义务。

### 5.2 画图

模型先根据范围、来源和相关正文建立过程：触发、参与方、交接、条件分支、结果与终态；再决定使用、合并或改画上游图，并保留来源对应。

脚本核图存在、可识别的围栏与来源引用等结构事实；多方角色是否完整、交互是否正确由模型核对。当前没有统一可靠的参与方结构真源，本步不从作者表行数自动推出真实角色数量，不新增一张自填人数表。已有多方交互图要求继续送达作者及 verifier，不将图种正确冒充内容完整。

### 5.3 按章提交

```text
story-build chapter --feature <名> --chapter <章名> --from <草稿> --task <当前任务文件>
```

NEXT 生成实际参数，模型不拼接摘要或猜文件名。提交先验证任务种类、章节匹配与输入新鲜性，再检查本章可独立判断的必要结构；失败不替换当前 Story 中的旧章，也不销毁候选草稿。

局部检查从原 cmdCheck 提取可复用函数，最终全篇检查调用同份逻辑。局部只查本章已有条件：非空、待填占位、必要节/表/图、明确可判的引用形状；不把其他未写章报为缺失，不在本章提交时强制全篇图集合和验收集合已经齐备。

输入来源缺失、结构错误均一次列清，定位到实际编辑对象。脚本不为失败稿自动补业务内容；作者修正后重试同一提交。

单章成功是独立落盘。自动准备下一任务失败时，明确输出“本章已提交、后继材料未准备”，只重试 prepare，不回滚或重写本章。该行为须有正常路径和失败恢复测试。

### 5.4 局部检查的提取边界与输出

在 story-build.mjs 内提取 `chapterProblems(ctx, chapter, candidateBody)`，返回问题数组，不写文件、不 process.exit。它由 cmdChapter 和 cmdCheck 共用；不复制一套规则，也不把整份 cmdCheck 套到只含一章的临时 Story 上。

共享合同与检查函数即可，不要求另建规则数组或注册器。验收用同一候选章验证两入口对局部错误的结果一致，并确认全篇独有条件没有提前进入局部检查。

| 当前 cmdCheck 中的职责 | chapter 提交时 | 全篇 check 时 |
|---|---|---|
| ① 空章、⑫a 非占位 | 查候选章；清理指导注释后再判 | 对全部章调用同一函数 |
| form.sections / form.slots / slotCondition | 查本章必要节、锚列、流程图；条件直接复用合同与现有函数 | 对全部章调用同一函数 |
| ③ id_shapes.drop | 对候选章排除 Mermaid 围栏后的文本检查 | 同一规则检查全文；keep 的验收集合仍在全篇核 |
| 图与 Markdown 引用 | 本章已有围栏须闭合，已有图片路径须可解析；跨章锚、图序不在此时要求最终编号 | 原有完整图集合、源图对应、编号和引用检查保留 |
| ⑤ 决策、⑦ 规约投影、⑫b Spec 契约、全局语言/来源守恒 | 不移入局部结构函数；附录先在内存完成 projectAppendix，再查本章结构 | 保留原对应检查，不因单章通过而跳过 |
| ① 标题顺序与 ①b 文档大标题、冻结、交付 | 仅复用已有目标章锚与冻结守卫 | 原全篇职责保留 |

表中的编号是本方案核实基线的定位线索，不成为交付提示或新规则 ID。不增加任意表数量、人物数量、关系完整度的机械门槛。

提交处理顺序固定为：冻结守卫 → 任务校验 → 读候选与目标章 → 清理指导注释 → 附录条件投影 → 局部检查 → 写 Story → 后继 prepare。前六项失败退出 1，Story 原文保持；候选草稿始终保留。这里只承诺校验成功后一次替换目标章，不新增跨文件事务或断电恢复机制。

后继选择按提交前目标章是否有待写 marker 判断：首次写作选择合同顺序中首个未写章，全章已写则 whole；修改已完成章时，尚有未写章则回首个未写章，全部完成则回 whole。whole 复用规则见 §4.4。不保存“当前正在统稿”状态或任务栈。

退出与显示约定：尚未写入而失败为 exit 1；本章已写入为 exit 0，哪怕后继准备失败。后者 stderr 明确报告后继错误，stdout 先写“本章已提交”，末行 NEXT 给实际 prepare 命令。成功准备必须输出任务路径并要求读取，不只输出提交命令，避免模型跳过作者材料。NEXT 是操作提示，不是完成凭证。

## 6. 整稿：有真实工作材料与产物，不用自述凭据

### 6.1 整稿任务

最后一章首次完成后，脚本准备 whole 任务：完整当前 Story、章节关系和范围/决策来源、整稿任务要求、各章草稿位置。模型在同一会话用现有编辑工具处理，不再从记忆中重建一份稿。

任务要求完成三个内容动作：

1. 对同一事项的多处叙述比较独有信息，合并完整重复，保留互补和必要重现。
2. 从触发到终态推演关键过程，核参与方调用/返回、条件分支与后续是否相接。
3. 核重组后的指代、单位、因果与可逆/不可逆后果，避免表格已换但“最后两种”等说明仍指旧对象。

不能以“不同章节都需要”“字面不一样”代替比较。也不要求统稿必须找到错误或产生修改。结果是经过比较的文稿；有真实修改时回对应章草稿，经 chapter 提交，保持其余章不变。

### 6.2 编辑与版本规则

对已写章的修改同样先准备该章当前任务，再提交。它是当前统稿/返修中的局部编辑，不重新启动首次写作流程；成功后 NEXT 提醒回当前整稿任务，不自动改写其他章。

whole 任务的初始 Story 作为比较底稿保留。整稿期间修改 Story 是预期行为，不以 Story 与底稿不同拒绝登记；但范围、材料、Spec、knowledge-use、decisions 或章节合同变化后，应刷新 whole 任务，重新核受影响关系。这样区分“工作对象被正常编辑”与“外部依据已经改变”。

### 6.3 取消七行凭据

新流程不要求生成 copyedit.md，不以行数、存在性或“已核无重复”字段判统稿完成。删除 COPYEDIT_ROWS、copyeditPath 强制消费者、七行检查与 copyedit 冻结登记；decisions 的冻结与人工反馈保护不变。历史 copyedit 留在原地，不清扫或迁移。

```text
story_flow.py story --feature <名> --task <whole任务文件>
```

登记要求全章已提交、whole 输入准备有效，随后执行原有 project→number→build→check，通过才写成文状态。--task 验证由共享的 MJS 输入核对能力完成，Python 传递参数并消费结果，不另实现第二份摘要算法。

whole 任务存在不是统稿思考已发生的证明，它只给正常工具路径一个明确的整稿工作入口。语义缺陷由独立审查与真实结果评价发现，不能再把这个材料版本检查包装成“强制模型认真审过”。

### 6.4 登记与恢复的执行顺序

`cmd_story(feature_root, project_root, task)` 保留原 complete 前置条件，并按以下顺序调用同一个 MJS 入口：

1. `check --task <whole> --inputs-only`：检查本 feature、whole 类型、当前依据、全章无待写 marker；不要求 Review 已生成，不写任何文件。
2. 原 `project` → `number` → `build`，参数继续显式传 feature 和 project-root。
3. `check --task <whole>`：再核输入并执行最终全篇检查；投影、编号和 Review 渲染没有改变外部依据，不应导致 whole 自失效。
4. 全部 exit 0 后登记 story_written，只冻结 decisions。任一失败维持 complete，透传错误与下一步；已经完成的确定性投影保留，重试幂等，不设计全文件回滚。

普通 `check` 仍能做诊断，但不能代替此登记入口写状态。作者直接编辑 Story 可被全篇检查接受，任务文件也不能证明其遵循逐章工具；不得对外声称脚本完全封锁了模型直接写文件。正常工具路径的输入、检查和推进是本步约束范围。

登记后 Story 的冻结/评审回流边界按既有规则处理。本步不授权模型为了 verifier 意见自行取消冻结；执行提示必须给出现有 reopen 或修正路径及其原有适用条件，不能输出冻结状态下必然失败的 chapter 命令。

## 7. 返修：读当前错误对象，执行编辑，不研究如何绕过

所有检查输出区分：输入未就绪、确定性产物错误、工具自身异常。每条尽可能给实际文件/章/规则来源；报错最后的 NEXT 只说明当前最接近的合法动作。

| 情况 | 下一步 |
|---|---|
| 任务输入已旧 | prepare 刷新当前任务，草稿保留，再按新依据核差异 |
| 作者要求变化 | prepare 刷新当前任务，保留草稿，核新的写作要求；不重新询问业务范围 |
| 当前草稿结构不符 | 修改列出的草稿内容，重试原 chapter；不改其他未受影响章 |
| 机器投影与真源不一致 | 回对应 Spec/knowledge-use 真源，重投影；不手改机器区 |
| 内容重复/矛盾由模型发现 | 回主要落点修正文，保留独有事实；相关输入变化按上节刷新 |
| 脚本异常或规则互斥 | 明确未完成及错误证据，反馈维护者；不能删事实或改规则绕过 |
| 正常提交完成 | 按既有待写 marker/流程位置准备下一任务或进入登记/审查 |

复用 next_step 的流程判断，NEXT 不维护第二份阶段枚举。每次给全部当前错误，但不对未知语义伪造一条“照抄即可正确”的替换。归档/进入 plan 等真实人类选择仍保留，不为了唯一 NEXT 取消人的选择。

直接消费者同步：B 段修改 story_flow.py 的 spec_stage_step 逐章提示，C 段修改登记提示，均使用新的 --task 路径；D 段删除 next_step 的 story_written 分支中“没有审查员就直接下一步”的放行说明，改为未完成独立审查时不能正式交付。分别验证 status 的实际输出，不能只改 SKILL 中的示例。

status 保持只读，不生成任务，也不按修改时间挑选所谓最新任务。恢复时给当前章或 whole 的 prepare 命令，由 prepare 复用或生成有效文件并返回其路径；若 status 显示已有任务路径，必须复用同一校验能力确认有效。由此恢复无需猜文件名或继续使用缺 --task 的旧命令。

同一问题反复出现时，模型核：是否实际修改了对应对象、是否改到了真源、是否被重投影恢复、是否正在验证旧输入。没有新信息时不重复相同源码探查或修复计划。不能从工具次数或 context_total 自动推定模型失效，也不增加固定次数重启机制。

### 已知机械误判的处理

工作编号检查限定正文与表格，不把 Mermaid 内部节点 ID 当作读者看到的业务编号；图标签语义仍由既有审查负责，验收编号与源图对应保护不变。不新增 Mermaid 语义解析器。

数据/状态恢复的“回滚”与客户端发布术语分开处理：复用现有语境能力，确定的业务语义不拦；无法可靠区分的词命中给定位提示，交既有语义判断，不要求模型替换正确业务事实。不能按当前案例原句增加豁免，也不扩大禁用词表。

## 8. 独立审查与交付

### 8.1 审查对象与来源

复用 Framework 的 verifier request/subject 和现有 pre_verifier，不新增 reviewer 或捕获链。本基线由 readerReviewTask 读取当前最终 Story 完整原文，随已有 pre_verifier 的单个读者审查 fragment 送入 promptFragments；保持 Framework 原生 Spec 输入。`story-build review-task` 调用同一生产函数，不在 pre_verifier 再拼一遍 Story。当前 Framework 只提供 Story 路径，不能以“宿主可能已经内联”为由省略本步。未来 Framework 若新增同一对象的正式注入能力，再单独调整唯一生产者，本步不做宿主猜测分支。

材料清单、有效范围、decisions 及直接来源仍有明确定位；Spec 按既有 Framework 输入路径取得。不将作者自评、旧 copyedit 或本步探索报告作为审查结论的依据。

检查生成的最终 prompt，确认 Story 全文与被审版本一致，首尾和必要内容没有被截断。若宿主无法承载整份内联内容，保留完整任务文件并明确分页读取路径；未读完的关键内容必须如实标缺口，不能默默截断后 PASS。成本包含实际内联内容，不将其算成免费优化。

### 8.2 模型要完成的核对

verifier 从来源与已确认范围建立应有过程和结果，再对照 Story，不沿作者的章节自述直接接受“都讲过”。

- 查覆盖：关键行为、条件、例外、源图内容和验收有无实际去向。
- 查关系：调用/返回、阶段/分支、状态/终态、操作/后果是否相接且一致。
- 查信息归属：多处出现的同一事项是否各有独有信息，还是完整复述；必要重现不算重复。
- 查依据：既有能力有工程事实，新增能力有确认的需求/设计；不把无页面等同于用户不可观察，也不虚构回退或不可逆承诺。

以上对象从本需求取，不在机制中列具体业务名、金额、接口或案例答案。既有多方图规则仍适用；没有可靠参与方结构源时，不以少填几行表就免除语义核对。

### 8.3 结论与严重度

沿用既有汇总与 blocking_findings/advisories。关键内容缺失、矛盾、无依据承诺、无法支撑交付判断的重复或表达问题应阻断；不影响理解的文字偏好给建议。不会因难以机械判断而把所有重复降级，也不把所有 MAJOR 批量升 BLOCKER。

汇总证据要能支持实际判断，写清核对的关系及位置，不只罗列十章名称。PASS 可在同一报告补充必要的简短对照说明，取消“PASS 不写任何明细”的限制；不设证据条数、最短引文、字数或全量裁决表。无需公开完整思考过程。

脚本只核报告存在、结构与当前闭环绑定，不核“文字像不像认真检查”。发现真实缺陷后按现有修正/subject 更新规则回作者，不强制未改材料重复审查。

### 8.4 没有审查能力时的明确结果

本方案把独立读者审查作为 Story 正式交付的必要条件。当前宿主未启用 verifier 时，可以准备、写作和本地检查，但 check --deliver 不得把 NOT_APPLICABLE 当作正式语义通过；应明确“未完成独立审查，不能按本流程交付”。这属于本方案明确提出的行为变化，待本方案批准后实施。

落点是 cmdCheck 的 `--deliver` 分支：先复用 check-receipt，再消费 storyReviewProblems。该函数现有 status 表示报告结构检查结果，结构完整的非 PASS 判项也可能返回 PASS，不能拿它当语义结论。

在 storyReviewProblems 返回对象中增加 `reviewVerdict`：从 story_reader_review 汇总行取得，去除现有格式符并转大写；无法取得为 null。保留现有 status/problems/detail 的职责，各返回分支都提供 reviewVerdict，不从 detail 反向解析。交付必须同时满足回执通过、status 为 PASS、reviewVerdict 为 PASS。summary 缺失、没有 verifier_report、报告路径不存在、判项缺失、非 PASS 判定或格式错误均退出 1，保留原因。普通 check 不要求尚未产生的独立报告，不重写其它阶段报告协议。

适配器声明 verifier_subagent=true 只表示已登记能力；正式交付仍核本轮实际报告与回执，不宣称该政策只影响离线夹具。

不修改 Framework 对其他流程的降级策略，不悄悄调用新 Agent。用户若选择改变本次交付范围，应明示记录另行决定，不能由模型自行将未审标成已审。

## 9. 必需、可选与验证时机

| 对象 | 本步处理 |
|---|---|
| Story 模式的流程范围、材料清单、Spec 与有效决策文件 | 在实际消费它们的 prepare/登记位置核存在与可读；缺必需输入明确失败，不返回空集冒充没有内容 |
| 源文件是否必需 | 按当前入口与现有材料合同判断；本地需求不能被强制要求不存在的远程单据，不扩大全局 required 集合 |
| knowledge-use | 已配置且本阶段要求产生知识判断时必需；未配置知识的合法路径继续成立 |
| 目标章、任务与草稿 | chapter 提交时必需；未写的其他章不作为局部失败 |
| 全篇与上游对应 | 登记时核最终集合，不因本章结构通过就跳过 |
| 独立审查 | 正式交付前必需；报告缺失、读取失败或未启用均不能算已审 |
| 非 Story 特性与离线检查 | 保持原有适用边界；离线结构检查不能产生正式成文/交付证明 |

先核完整生产—消费链是否已有有效检查，只在真正无人承担的必需条件处补齐。不中途把所有 skipped 分支统一改 FAIL，不让正常首轮还未生成的产物拦住自身生成。

## 11. 实施拆分与验收

同一步可按以下小段实施，前一小段的直接消费者一致后再继续；不允许把新命令孤立交付、让旧调用路径长期并存。

| A 任务准备与输入 | 合同关系、prepare、任务落盘、草稿入口 | 正确输入产生可读任务，相同输入复用，来源变化刷新，未配置知识合法 |

### 11.1 确定性验收

1. 用真实当前产物副本检验 task 生成，引用的章节原文与材料版本准确；缺文件、损坏清单有明确结果，不静默截断。
2. 输入未变时重复 prepare 不制造不同任务；改变相关依据后旧章任务被拒，草稿不丢；专门覆盖只改 story-write.md 的失效；只编辑当前草稿不导致任务自失效。
3. 每章存在性/必要结构使用同一检查函数；故意缺必需表/图时局部拒绝，改正后正常落盘；下一未写章不误拦本章。
4. 整稿期间允许编辑目标文稿；只因文稿与起始底稿不同不阻断；范围/Spec 等外部依据变化要求刷新，不能沿用旧结论。
5. 删除 copyedit 完成凭据不影响 decisions 冻结、人工区保护、源图集合与附录投影；历史过程文件保持。
6. 测实际 Framework 装配链的最终 prompt/报告合同，不能只测一个 helper 返回了字符串；缺 verifier 的 Story 交付明确不通过，非 Story 行为不变。
7. 测正常从 skeleton→逐章提交→整稿→登记→既有审查/回执→交付的贯通。离线使用确定性夹具与已有宿主模拟，只证明连接与状态，不冒充真实语义验证。
8. 两种误判消失后，真实正文工作编号、缺图/缺验收/损坏投影等原有错误仍由对应检查发现。
9. skeleton/prepare --offline 均拒绝；正式 skeleton 缺流程契约时不写入。status 在首次写作、统稿和已登记状态分别输出可执行的恢复路径，运行前后任务目录与流程文件不变。
10. 结构完整但判项 FAIL 的报告不能通过新增交付条件；PASS 汇总后跟简短说明仍能解析且 reviewVerdict 为 PASS。D 段保留这两例的实际解析结果，不能只断言提示词已改。

遵循 TEST.md 的相关测试、离线全量、失效形态与自适配检查；framework 无新增修改。测试只写自己的临时目录。

### 11.2 模型行为验收

真实 CLI 由用户启动。复用现有 events、runlog、草稿、任务文件与 verifier 报告，不建新测评平台。已知案例用于定位旧问题，交付提示中不含答案；至少需要实际取得的 UI 与无页面场景证据才能声称覆盖两者，缺少的保持待验。

| 观察对象 | 达成的依据 | 不能作为达成依据 |
|---|---|---|
| 首次成文 | 首稿能区分章职责，关键关系正确，必要内容有去向；按本轮任务实际字节选最大的三章，单独检查其重复、遗漏和关系错误，结合章职责判断，不能把难度差异直接归因于体量 | task 文件存在、读过规则、表格数量增加 |
| 统稿 | 本轮真实重复/矛盾被正确处理，必要重现有独有价值且同义 | 写“已比较”、强制产生几次 edit、修改了多少字 |
| 图 | 实际参与方、交接、分支与结果可读且完整 | 图种或源标记单独通过 |
| 返修 | 已定位的问题直接修对应对象，原事实保留，正常下一步可执行 | 报错数下降但相关内容被删、生成任务被取消 |
| 独立审查 | 人在真实稿件发现的关键问题有被模型发现，或最终稿经人核确无该缺陷；报告依据与原文相符 | 报告结构完整、十章列名、出现多个引用 |
| 恢复 | 新任务依据磁盘当前事实接续，不要求用户重述全部上下文 | 把新 run_id 当成清空记忆或质量改善 |

首次稿、确定性返修、语义返修、人工等待分别度量。不能把整轮耗时全归本步，也不能忽略新增任务原文带来的读取成本。

失败按“输入准备错误、任务没执行、语义判断错误、真源更新/回归、机械误判、能力不可用”定位；本轮没有子代理读取轨迹时如实说明，不根据其自述推定读完。不再用“模型忘了”概括所有问题。

若同一配置在输入正确、任务明确的情况下仍重复漏报关键缺陷，应向用户报告该能力边界，讨论可用配置或人工复核安排。不得继续无界堆提示、自动换模型、加同质 Agent 或降低内容目标。

## 12. 成本、完成状态与后续

新增的是现有成文动作内的任务材料准备及版本/提交连接，不是通用框架。静态规模增加的核心是准备与核对逻辑；移除七行凭据和重复规则抵消部分成本。原先的净增 50–180 行未包含完整参数、材料快照与失败恢复实现，不能作为可靠估算或承诺。各小段开工前按 §11.3 列实际预计增删，完成后以 diff 测量，不以压缩排版满足预算。

开工前记录当前完整字符数、分类代码行与已签上限，并据实际改动登记峰值和完成预算；不静默抬高已批准边界。另记录生成任务文件及最终审查上下文的实际字符与工具调用，避免静态少了、运行却大幅重复装配。
