# Step2.3-03 · 核对、退出与验收

> 依赖：[总方案](02.3-Story写作流程重设计.md)、[01](02.3-01-原材料与初筛.md)、[02](02.3-02-整篇编排与成文.md)通过。本步闭合写后核对、独立审查与整个流程的质量验收，不新增审查Agent层级。

## 1. 写后核对不是补写前没有想清的方案

全部章节有正文后，prepare给出的第一项动作是读取当前Story、story-template和本次来源/决策。模型核对成品是否讲清有效需求及关系、编排中哪些取舍仍合理，不以“完全服从模板”作为完成标准，也不再凭记忆写一遍“我已检查”。

与02的写前核对分工明确：写前保存已知义务与需要解释的关系；此处从来源、编排和新增认识核实际正文。修改边界统一按02§2的“编排调整规则”；此处核对实际结果。不为两次比较各写一份同义需求理解或完成报告。

核对四类关系：

1. 原始义务与已定判断是否有实际正文落点；不采用的理由是否仍站得住，遗漏不能靠Spec也没写来开脱。
2. 参与方交接、对象身份、规则条件、状态/终态、失败与恢复是否前后相接；图标签、正文与验收含义一致。
3. 多处说明是否有独有用途；必要重现保持，完整复述合并；章节职责清楚且父子层级真实。
4. 读者能否据此理解方案、判断取舍、定位责任和确认交付；不得将未知结论说成已定、将本地模拟说成真实业务已可用。

发现业务根因回Spec或decisions；发现编排不当回story-template；只有措辞/图表表达不好时改对应草稿。三个落点不是三个新阶段或三次全文重写。修订后继续按章提交，保留未受影响内容。

核对结果体现于正文和实际决策，不新增copyedit、已读标记或必须找到若干错误的台账。没有问题可以不改；“做过核对”的自述不构成质量证据。

## 2. 登记与确定性约束

保留 `story_flow.py story --feature <名>` 原入口和complete前置；project → number → build → check通过才写story_written。

最终check增加/接入以下有限条件：

- source-index所指来源版本仍存在、当前引用可读；如变了，回来源更新和受影响编排，不能重算摘要冒充已经重新理解。
- story-template结构有效，原合同十章/必要小节及已声明structures的目标可核对；不要求正文复现全部建议小节。selection与template按02解析出有效取舍，显式引用合法且无冲突；不要求默认可参考单元逐项登记采用出口。表头/图类型校验复用02的同一实现，不能分别在局部与最终check复制规则。
- 原有源图身份、图片引用、验收编号、附录投影、decisions结构及冻结、人工区保护继续检查。

这些条件都不证明语义覆盖。内容只写了一句“这里参考某单元”、草稿没有展开关系，属于语义问题；不能通过增加字数门槛、逐句相似度或强制结论条数伪装为脚本能判。

非Story feature保持不适用；check --offline继续仅查结构，不强求虚构来源/流程。新的成文流程不能通过offline登记为正式完成。

## 3. 原独立verifier的职责重定

复用现有pre_verifier、request/subject、报告与回执机制，不另开一条影子审查链，不改Framework源码。

读者审查输入包含：当前完整Story、当前整篇编排、原始来源目录与版本、decisions及现有Spec/knowledge输入。原始来源目录必须包含已分配、未分配、omit、replaced_by及defer涉及的全部原始单元及可读位置，不得只交chapters中已采用的材料。Story与编排通过已有promptFragments进入被审对象，保证现有subject覆盖当前解释设计；有效selection也作为编排依据进入request，避免继承的排除理由未送达；Spec仍走Framework已有输入，不再额外复制一遍。原材料只内联文件路径、版本、单元位置及有效取舍表，全文按位置读取；不重复内联全部原文，也不把材料摘要当正文。分别记录Story、template、selection/单元表和整份verifier request的实际UTF-8字节及宿主截断情况。

审查任务按以下次序组织，而不是先接受作者的十章解释：

1. 从有效原始来源与已确认范围确认必须保持的业务结论和主要关系，重点核混合用途小节、排除理由和Spec推断。一个小节ID已使用，不代表其中每项独立义务都保留；被替代来源需核替代依据，不能接受作者排除决定作为答案。
2. 对照实际Story核这些结论是否被正确解释；正文是否确实提供了所需关系、条件、结果和可执行责任。新增的解释按来源与价值评价，不能仅因超出template的content或建议目录就判越界。
3. 核跨章/父子内容是否互补，关键图是否与实际参与方和去向一致；再给不影响理解的表达建议。

同一次独立审查完成上述工作，不为每一章各建Agent，也不要求再生成一份完整业务模型。报告沿现有汇总和findings/advisories，关键问题给来源位置、正文位置、影响和修正落点；PASS依据描述实际比较的关系，不只列“逐章已过”。不设条数、引文字数或逐事实裁决表。

只找到原材料和编排却没有读取相关内容时，不声称已经核过。输入被截断/关键材料不可访问须明确缺口；无法支撑判断不能判已确认通过。机制能提供对象、记录版本与报告，不宣称证明模型内部思考。

reviewVerdict与报告结构status继续分开。**交付政策保持用户已批准的现状**：已登记审查能力的宿主要求回执、报告结构及实际PASS；未登记审查员时记提示放行，不在本步擅自改政策。能力缺失必须如实披露，不能拿这条降级路径证明语义目标已验收。

story_written冻结的写作依据包括source-selection、story-template及其basis，沿用现有STORY_SRC_FROZEN与冻结指纹入口，同时保留decisions等原有保护；不能把仍被继承的selection当历史文件漏守。source-index对应版本由来源检查约束；chapters派生视图可按冻结输入重建，不纳入独立冻结台账。reopen解开原有写作冻结，保留上述文件和人工意见，只修受影响内容；重登记更新同一组指纹。sources的basis刷新也受同一冻结守卫约束。

## 4. 失败恢复与影响范围

| 失败 | 回到哪里 | 保留什么 |
|---|---|---|
| 原材料新增/变更 | 更新该源索引，模型重审受影响归属/设计；范围变化走原确认路径 | 原件、已有判断与草稿，不清空整份需求 |
| 初筛分错/遗漏疑点 | 编排尚未形成时修source-selection；形成后在template.source_changes覆盖相应取舍，不倒回重填初筛 | 有效来源和其它判断 |
| Spec或决策错误 | 原Spec/decisions真源，再更新受影响编排与稿件 | 没有受影响的章及人工意见 |
| 主要编排职责错误或已选形式改变 | 更新相关story-template与草稿；普通分节/措辞/有依据的深化直接改稿 | 未受影响内容，技术投影仍由真源生成 |
| 章结构/路径/引用错误 | 当前草稿或相应生成职责 | 提交失败不覆盖旧章 |
| 已登记后语义阻断 | 原reopen→责任真源/编排/草稿→重登记→原审查 | 人工反馈保护与历史证据 |
| 模型多次忽略工作输入 | 核实际工具输出与读取，定位送达/任务/配置 | 不靠多次同样重试、加自证字段或降质量目标收口 |

影响范围先由真实来源/内容关系确定，不能只凭章节编号。例如全局额度规则变化会影响表、验证流程和验收；修改一张图的排版不必重做业务结论。脚本根据来源引用列出候选受影响章，模型判定真实影响并修正；引用集合不能当作完整语义依赖图。

## 5. 整体退出核对

实施者在此步逐项核生产文件与直接调用方：

- 来源与有效取舍只由story-sources的同一解析函数计算；selection的未覆盖项仍被继承，skeleton是材料视图唯一写入入口。
- v3草稿指导区协议、固定context_chapters和逐章重复灌入当前全文的函数已经退出；不存在换名保留的第二套作者输入。
- story-write、spec阶段说明、SKILL、author入口、next_step、post_check与reopen说明全指向新流程；不存在新代码搭旧命令的中间态。
- 保留局部检查、编号、投影、Review人工区、原始图片与验收身份；不得以重构为由削弱原必要保护。
- 已选结构的生成与检查共用原表头/围栏能力，不额外生成一套约束文件；脚本只落实模型选择，不能以人数、关键词或表数替模型选择形式。
- 初筛、Spec、编排、成文的提示各自只要求本阶段新增判断；删除“再读全材料重新定同一结论”的重复工作，不让新流程变成三遍相同分析。
- 原golden与历史测试材料不作为执行者答案输入，不把AR90006专名、数字和方案写进新的枚举/初筛/编排代码。

步骤3开工时按新来源/Spec接口核知识接入，但knowledge仍由目标仓维护。步骤4的“决策回看”接入Spec后整篇编排和写后核对，不能再加一遍同目的统稿；步骤5的会议结论作为新的来源类型接入原材料目录，不复写一条分配管线。

## 6. 确定性验收

按test/story/TEST.md复用现有pytest、失效形态、adapt与Framework只读检查。维护者不运行被维护系统的业务阶段来证明自身正确。相关用例先过，再完成最终离线全量；重复检查只因新改动或未闭合问题而进行。

| 验证目标 | 正反条件 |
|---|---|
| S4正常路径 | 候选提交不自重开；实际来源变化仍阻断；失败不把派生稿登记成原始依据 |
| 内容定位 | 父级前提、表、图、列表与无标题文件保留；不支持的子范围对象/坏引用被拒；同名标题区分 |
| 归属结构 | 空/稀疏初筛合法；模板显式覆盖优先；默认keep不计已采用；未知ID、冲突引用、不合法omit/defer/循环替代被拒；不要求每章有材料；审查输入能定位被排除及未决原文，不仅包含选中集合 |
| Spec增量 | 新设计有入口，未变来源不重新编号；变化源按完整标题路径给重定位候选，重复标题不自动认定；原始义务不因Spec缺失被自动排除；原始与派生来源明显区分 |
| 动态编排 | 两种合理组织、未预列的新增小节或合理拆并都能成文；固定读者职责/必要结构仍检查。已声明结构按02的章/明确目标范围落实，缺列/不符类型/图片错目标被拦；未声明结构的建议标题不成为门禁 |
| 探索空间与事实保护 | 在有效来源范围内补充模板未列的解释可以通过；把未知填成确定结论、或照模板写却遗漏来源义务，仍由语义审查判有问题，不能以结构一致放行 |
| 输入与输出分离 | 重建材料不改作者正文；未分配原文只给索引，多个显式引用才共享全文，作者按范围读；修改编排只列差异；缺稿恢复不覆盖已有稿 |
| 正常成文 | 整篇设计→按章落盘→写后核对→原登记→测试模拟的有效审查/回执→交付可走通 |
| 返修 | 原材料、Spec、编排、表达错误回正确落点；没有无意义地重跑所有章；冻结/人工区保持 |
| 审查接线 | 最终request确实包含本轮对象；报告格式PASS而reviewVerdict FAIL不得当已审通过；能力缺失真实披露 |
| 输出与命令 | NEXT在首屏，材料持久可重新读取；生成命令在实际支持的shell中可执行，引用不因路径字符变化失效 |

确定性反例只验证脚本与连接，不用故意坏稿证明模型语义能力。对模型的判断力，以真实产物里人发现的问题是否被报告为证据。

金样配套原件可以作为切片器的确定性测试输入，索引中的标题/行范围/图片对应可逐项作为期望检查，但先按本期ATX规则核对，不将人工整理索引未经核对直接当算法答案。配套selection示范稀疏取舍与继承，新增中性临时样例覆盖源变化、独立图片、空sources及重复目标标题。维护侧夹具不进入真实运行作者输入，也不以最终金样的语义结论作为切片器测试逻辑。

## 7. 行为验收：质量、稳定性与跨项不退化

真实运行仍需用户按TEST.md启动。复用现有runlog/events/产物/scorecard，不建新评测平台，不往Case提示塞金样答案。设计门槛在这里明确，不自动发起测试。

### 7.1 同条件重复

选定机制版本、宿主/模型配置、输入来源和范围意图，至少3次独立干净运行。交互沿同一需求意图自然回答，材料身份可核；只允许表达措辞变化，实际需求改变则单列，不能混进稳定性样本。不同输入或配置的历史稿只作旁证，不当作本组重复。

三次都按现有三轴评分协议由人评价，逐项保留证据；任何一次关键事实丢失、相互矛盾或未经确认的承诺均记录，不以均分掩盖最差一轮。达到现有90分档仍需用户确认，不由脚本自动判质量。稳定性首先看关键要求与决策是否保持，不要求字句或形式完全相同。

三次全过仅说明这组条件下取得初步可重复证据，不据此估算“成功概率90%”或外推所有需求。未来真实运行仍需保持关键事实与跨项质量观察；未覆盖的来源规模、业务关系和宿主明确保留边界。

### 7.2 场景泛化与A/B相互影响

至少取得一种有界面且跨方协作的需求，以及一种以数据/后台/管理能力为主的需求证据。未取得的场景保持待验，不编造覆盖。原始章节结构改变但语义相同的输入，可作为额外离线定位样例；它不替代真实不同业务。

每次同时核下列面，不只查本轮重点：

| 面 | 通过依据 | 退化信号 |
|---|---|---|
| 需求/规则 | 重要条件、限制、来源和取舍保留；同一来源小节的多项独立义务各有实际去向 | 精简重复时丢规则；Spec遗漏使原义务消失；标记整节已用但遗漏其中关键条件 |
| 流程/对象 | 参与方交接、状态、数据生命期互相一致 | 图更漂亮但回程没了；缓存与业务事实混淆 |
| 表达/层级 | 编排保留具体依据与真实问题，作者可深化并选择合理组织，父子与跨章互补 | 编排只有空泛职责；提前写死答案/全部小节；小节持续增加却没有独有信息；作者因为模板未列而省略新发现的重要内容 |
| 验收/交付 | 原编号可查、主责与开放条件可操作 | 功能写细了却丢验收主责；本地模拟等同上线 |
| 决策/知识 | 已定与未决清楚，知识改变真实设计 | 多一份台账但原歧义未发现；知识只在附录回显 |
| 恢复/效率 | 中断后由当前文件接续，正确动作更直接；前置工作增加与后续返修减少一起核算 | 初筛/Spec/编排三次重复理解同一业务、全量改稿、持续读checker学规则 |

对比金样看同类信息关系是否讲清，不比精确章数/标题/字数。候选金样中的开放业务口径不能自动作为测试答案。旧稿有某个优点，只有当前来源仍支持才要求保留。

同时对照AR90006的story-template金样：运行时编排是否保存已有依据、提出真实业务问题、给可调整的形式与互补建议，并允许后续深化。不能把成品的完备答案和全部小节反向要求模型在写前预定；它不是正向成功的运行证据，不注入Case或要求逐字段逐字复刻。

### 7.3 成本记录与失败归因

记录首次理解/初筛、Spec、编排、正文、机械返修、语义返修、verifier、人工等待与外部故障。统计输入字节、工具实际读取、上下文与被重复发送的原文；不把“没有复制进十个文件”直接当token已减少。

半小时是既有性能期望，不根据一次墙钟自动算得分。新增初筛/编排若只是把原本写作工作做了三次，即使文档正确也不算完整优化。把节省的返修与增加的前置工作一起比较，不能只展示新功能耗时。

行为失败按：输入缺失/角色混用、编排错误、执行偏离、语义能力不足、验证漏报、外部故障分别定位。保留已证实的正确职责；不能继续围绕最后一个症状无界加提示或增脚本分支。

## 8. 完成前过拟合自查

每步交回前查本步改动与直接消费者，最终合并查全部新增/替换提示、注释、脚本、合同、示例、错误/NEXT，以及真实生成的材料视图/编排/正文。

必须说明：规则是否依赖AR90006、某次旧标题、金额/API/状态；是否把金样写成答案；是否仅按关键词/表行数近似语义；是否以固定章模板强迫不适用场景；新增指引是否有当前目标与消费者。引用当前需求的业务名是合法输入，不为过扫描删除它。

复用失效形态检查和针对性搜索，命中逐条核语境；零命中不代替语义自查。交回检查范围、实际命令、命中处置、未验证边界，发现问题回原责任点修。自查记录在维护反馈，不进入业务模型的自证流程。

## 9. 交付结论

实施反馈按01/02/03分别记录：实际diff、职责退出、生产/消费/失败链、按总方案§7比较的新增/删除/净变化与完整字符量、测试结果及行为待验事项。总量未下降必须专项审查职责是否真正替换、是否保留旧链再叠加新分支；不能仅解释新增都有用途便宣布收敛。总方案入口切换完成，旧文档注明历史状态，不宣称旧方案与新方案同时有效。

只有完整实现、结构及过拟合检查闭合，并取得用户确认的稳定性与泛化效果证据，才能关闭Step2.3目标。阶段性允许“实现通过、某场景行为待验”，不把这个状态写成已达全部目标。
