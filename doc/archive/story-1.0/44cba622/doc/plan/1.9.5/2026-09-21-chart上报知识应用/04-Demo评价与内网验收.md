# S4：Demo 到 Plan 的评价与内网验收交接

先读[总览](00-整体设计与实施总览.md)。用户已明确：Coding 及之后的真实测试只在内网，Demo 不跑原生编译/设备事件测试，不为此增加预检、业务源码夹具或注入通道。

## 1. Demo 验证范围

S1–S3 离线结果通过并经设计者接受后，准备两个现有业务 Case，真实模型运行止于 Plan。沿 TEST/cases README 的需求系统、需求材料和交互协议；不用维护方案、隐藏答案或预写 Spec/Plan 作为输入。启动前仍需用户选择 Case 与实际运行配置，本设计不启动模型。

用户已确定复用两个现有 Case，材料一字不改：auto-topup 到 Spec，car-key-sharing 到 Plan；两者原系统设计已有统计诉求。不新建 chart-reporting Case，不增加源码夹具。本轮两者均不开 update 第二段，运行配置按现有入口设置并在起跑前核回显，不能遗留 after_initial 导致额外执行。

两个 Case 的统计节点、字段和编码仍由模型根据各自真实材料与知识判断；不在材料中补标准答案。观察到缺陷先定位责任，再决定必要修正和复测。回写确认、advisory 等未实际经过的分支保留未实证，不为观察追加流程。

## 2. 评价看什么

| 范围 | 可支持的结论 |
|---|---|
| 知识读取轨迹 | 决定前是否取得实际规则/API，缺信息是否如实处理 |
| Spec/Story/Plan | 独立小节各履职责，节点选择、分类/参数/异常边界有依据；非照抄 Demo 示例 |
| contracts 与验收 | 义务落真实计划实体、运行验证可执行，来源与预期明确 |
| 原有能力 | 需求事实、人工结论、业务关系、技术表与附录不因专项设计而丢失 |
| 成本与审查 | PASS advisory 是否触发无效循环；耗时/上下文按 TEST 记录 |

finalize 后评价并提出三轴建议分，用户确认前不写最终达标。结构 PASS、文件路径出现、模型自述均不等于知识被正确应用。Demo 本步不证明代码或原始事件正确。

## 3. 内网交接内容

目标维护者先按真实 VocBuilder/ChartBuilder/BIBuilder、编码登记、结果分类和参数协议适配知识，再按正常业务开发流程实施。不能用 Demo 十位码/四分类覆盖真实仓的不同协议，也不把尚不存在的公开 setter 当成真实 API。

Plan/验证方案至少交代如下场景与可观察预期，由内网实际需求决定哪些适用：

| 场景 | 核对重点 |
|---|---|
| 正常与中间成功 | 实际节点/分类、调用时机和必要字段 |
| 普通失败与授权拒绝 | 不误作主动取消；外码确来自实际返回，无码不伪造 |
| 主动取消与迟到回调 | 结果与业务一致，未执行节点不虚报、既定终态不被改写 |
| 重复通知与重新发起 | 同执行不重复，新执行不被错误去重 |
| 旧定义复用/扩展 | 相同含义复用，新含义不冲突，旧路径不改变含义 |
| 过程 VOC 与终态 Chart | 定位/统计分工，非机械三选一；必要本地日志保留 |
| 维度/耗时/隐私 | 实际来源、类型、计时起止/单位和脱敏准确 |

捕获目标工程实际发送的原始事件，保留刺激、执行标识、载荷与次数。可用目标已有调试/订阅能力；HarmonyOS 可评估 hiAppEvent 订阅，但不是所有仓强制渠道。不创建采集服务，不用手造 payload 代替真实输出，不去重后再断言无重复。关联不足或环境失败应报告未验证。

原生编译与各文件 lint 按目标工具链要求进行。SDK 可见性变化、业务行为与平台送达分别验证；平台事件正确也不证明后台成功率公式，本版不验数据使用层。

## 4. 解耦与发布

中性知识替换、目标已有知识升级保护和空知识路径沿 S2 离线验证，不宣称真实内网已通过。内网结果应按目标仓位置归档，当前版发布说明链接可取得的证据，无法访问的如实列未知。

Demo 发布条件：S1–S3 实施及离线证据接受，S4 到 Plan 的真实结果经用户审视，版本号/使用说明/预算与实际交付一致。manifest 更新为 1.9.5，发布记录放 test/story/release/1.9.5.md；不在机制提示中混入测试历史。

验收逐项列证据等级：AC01/05 可由本次成品评价；AC02/03/04/07 的设计和规则部分可核，代码/事件部分待内网；AC06 原始事件行为待内网；AC08 机制解耦与适配方法可核，真实目标效果待内网。不以本版可发布推定需求所有运行验收均已完成。
