# 交 Framework：SKILL 章序与模板冲突、plan 阶段不核验收引用（本地稿，未发出）

对象：framework 发布件 3.0.0（`framework/package.json`），在 SimulatedWalletForHmos 仓以只读方式集成。本仓不改框架，只准备材料，由有上游联络授权的一方发出。

## 1. spec SKILL 的章序与 profile 模板相矛盾

| 位置 | 原文 |
|---|---|
| `framework/skills/feature/spec/SKILL.md` 第 45 行 | 「填 10 章节（0 术语映射表 / 1 功能概述 / **2 Scope 声明** / 3 目标用户场景 / … / 9 验收标准）」 |
| `framework/profiles/hmos-app/skills/spec/templates/spec-template.md` 第 38、95、236 行 | `## Scope 声明`（不编号）、`## 2. 目标用户与使用场景`、`## 8. 验收标准` |

**实际影响**：2026-09-22 一次真实运行中（Case AR90006，模型 deepseek），作者按 SKILL 的列法把 Scope 编成第 2 章。后面各章整体顺延，扩展追加的「技术契约」变成第 10 章，下面却挂着 9.x 子节；正文里引用「§9」的地方指向了验收标准，不再指向技术契约。

## 2. plan SKILL 的章序与 profile 模板相矛盾

| 位置 | 原文 |
|---|---|
| `framework/skills/feature/plan/SKILL.md` 第 111 行 | 「**1 Scope 声明与继承** / 2 模块架构图 / 3 目录文件结构规划 / 4 数据模型定义 / 5 页面组件树 / …」 |
| `framework/profiles/hmos-app/skills/plan/templates/plan-template.md` 第 16、60、87、95 行 | `## Scope 声明与继承`（不编号）、`## 1. 模块架构图`、`## 3. 数据模型定义`、`## 4. 页面组件树` |

**实际影响**：同一天另一 Case（ISSUE-206）的 plan 标题照模板，而义务表引用设计章时按 SKILL 写「4. 数据模型定义」「5. 页面组件树」。按号去找，找到的是另一章。

## 3. 建议

- 两份 SKILL 的章序列表与 profile 模板统一。以模板为准时，SKILL 写「按模板章序，Scope 不编号」，或者直接不在 SKILL 里列号。这两处以外的 profile 是否有同样冲突，由上游按全部 profile 核。
- 本仓的临时处置：扩展作者页写明「章号以 profile 模板为准」；扩展门禁经 `skill-assets.yaml` 取模板核章号。上游统一后，这条说明保留（它不冲突），门禁可以继续用。

## 4. plan 阶段不核 use-cases 的验收引用

| 现状 | 位置 |
|---|---|
| `linked_acceptance` 只在 UT 阶段核「非空」，并做反查 | `framework/harness/scripts/check-ut.ts` 第 1571、1918 行起 |
| plan 阶段定稿 use-cases 时，不核引用的验收编号是否存在 | check-plan 无对应判据 |

**实际影响**：ISSUE-206 的 use-cases 引用 AC-K1…K11，acceptance.yaml 里只有 AC-1…，到 plan 收口都没人拦；verifier 看到了，但降为 WARN。

**建议**：plan 阶段核 `linked_acceptance` 引用的编号在 acceptance.yaml 中存在，把读取不到与悬空分开报。本仓扩展已在 plan post_check 补上这一条；上游正式接管后，扩展这条退出，不留两份。

## 5. 附带观察（未定性）

同一 plan 的 use-cases 里：
- 协调者 `ShareSetupFlow` 订阅的 `flow.granteePermission`、`flow.quota`、`flow.submitting` 是页面 `ShareSetupPage` 的状态，不是它自己的成员；
- 协调者 `ShareManagePage` 调用的 `flow.onRevoke`、`flow.loadList`、`flow.loadQuota` 在 contracts 中没有声明。

绑定的解析规则由框架定义，这里只列事实，不判定哪一边错。
