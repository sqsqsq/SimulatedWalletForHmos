# 1.9.5 下一轮优化实施方案

依据[首轮结果评审](00-首轮结果评审.md)、用户确认的目标项目约束与单处承载要求。此为首轮后新一轮方案，之前 05/06 提案涉及本轮的动作以本文为实施入口，不要求执行者拼接旧稿。已完成 S1–S3 的有效能力保持，首轮结果不改写。

## 1. 目标、范围与顺序

目标：把必要的埋点配套内容集中讲清，模型能从需求/项目知识形成业务覆盖，在 Plan 落实可实施映射；已有自动能力复用，独立 BI 有需求依据，阶段真实报告能被正确采纳。不是把埋点变成需求主体，也不扩成统计平台。

三步：A 知识与单处承载→B Plan/审查与报告采纳→C 同组复测。每步交差异、针对性证据与预算，设计者接受后下一步；A/B 不起真实模型，C 复用两个原 Case。当前任务制定方案，不启动复测。

## 2. A：项目知识与单处承载

### 2.1 知识先区分规则、事实和目标能力

reporting.md 统一 VOC/Chart/BI，保留短骨架。observability.md 承担约束；通用机制不含模板名、位数、渠道默认策略或固定枚举。

1. 独立运营指标/事件须有产品、SE 的明确材料。只有目标未明细时澄清；没有要求不自行新增 BI，不生成空运营点表。
2. 目标项目有自动页面/点击运维上报（用户确认）。facts 分清该来源与当前 Demo 的源码能力，核覆盖后复用；如 Demo 缺少，只列本需求必要建设差距，不伪装已有、不借此创建无依据 BI。
3. 同流程相同语义的运营/运维身份复用 eventID/funcID/subFuncID 常量；运营不默认需运维内/外码和结果分类，扩展参数按需；有协议依据可以借用内外码表达类似业务含义，不能设一律禁止。
4. 需要统计的 subFuncID 点位覆盖 STEP_SUCCESS、普通失败、主动取消等实际适用结果，不只记全程终态。更细子步骤由项目粒度定义，不能每个函数自动建点。
5. 模板/流程/步骤身份与结果字段分开；具体事件/内码映射由 Plan 查登记后复用或分配。当前缺代码不等于目标不做，缺协议不等于可凭空编造。
6. 增补简短状态判断：自然到期/撤销中等业务状态不自动等于执行失败；按所观察动作与项目结果定义分类。本端无法直接观察的结果需明确消息/查询等权威来源及能力缺口。

生产者位置：knowledge/facts/reporting.md、constraints/observability.md。复用现有条目/附注，不增加通用路由或一张机械结果字典。编码/接口事实以源码为准，目标协议有用户依据；知识说明不比既有设计模式更细。

## 3. B：可实施映射、语义审查与报告采纳

### 3.1 Plan 一个小节完成设计

沿本轮真实 Plan 的“6.服务层接口定义”下上报方案小节。各流程说明每个点位由谁观测、真实触发源、身份与参数、成功/失败/取消语义、编码来源、复用/新增及验证；实现设计更细时补必要子步骤，但不默改业务范围。

要求有实际落实结果：已定协议下不能仅写“在某枚举定义”“同上登记”；没有分配依据则精确列未决，不虚构值。远端发生的接受/失效事件，要明确本端回调/查询/状态通知的取得时机；若需求仅负责本端观察就照此表述，不把远端实际发生时刻当已知。自然到期、待接受作废、撤销中按业务语义分别定义，不一律标普通失败。

contracts 的 must 挂真实业务方法/字段，不能只给枚举一个“覆盖全部结果”泛义务。确缺封装/协议支持时列本需求建设项，Demo 无Coding不意味着Plan可以省略设计；BI无需求则不建设。

文件：hooks/plan/author.md 与 templates/plan-sections.md 按职责各写必要信息；knowledge内容不复制进模板。coding/review/ut作者沿契约，必要时只同步上游定位引用，不新增轮次或要求其重判全部知识。

### 3.2 语义审查回到业务关系

更新 spec/plan-rules.overlay.yaml 的既有知识实义审查项，删除旧“业务章一定有独立节”要求。Spec 核需求依据与流程/步骤/结果覆盖；Story 核单处投影完整与可读；Plan 核业务状态与执行结果、观察责任、字段/编码及建设项，查是否只承诺而没有设计。

使用正常业务原材料核对，而非用银行卡金样作答案。构造“漏步骤成功、无依据BI、自然到期强记失败、无数据来源却声称实时上报”等材料可供维护者离线语义走查；不为每种反例新开模型调用，也不增加会按业务词判失败的脚本。

### 3.3 正常阶段复用当前报告的采纳路径

本轮 auto spec 和 car plan 已有绑定当前 subject 的 PASS 报告，summary仍prior-review；按C5证实的完整 phase 采纳路径处理这类具体情况，不修改Framework收口器。

在 hooks/spec/author.md、hooks/plan/author.md（及 phases/spec.md 对应闭环说明）写明当前报告存在后的动作：报告路径/subject/终态匹配、材料未再变→完整运行对应 phase→核当前summary实际采纳。提取共享说明可复用现有 update 方法页已有段落指针，不建立第二套报告解析或状态库。

材料又变、无当前有效报告或报告FAIL时走Framework实际NEXT/既有修正流程；不把历史PASS冒充当前，不无条件再派审或重跑完整链。纯advisory记录notes，不因偏好循环修改。framework原本允许的历史审查沿用如实披露，不强行全改成“已重审”；只有报告确已产生而尚未采纳时补采纳。

测试域在现有阶段结果中展示闭环模式和当前报告采纳事实，finished只是运行到终点，不与语义内容达标混为一谈。不自动替被测模型跑phase修其产物。

B 完成条件：car式设计缺陷有明确的知识/作者/审查承接；隔离材料验证已存在当前报告的正常spec/plan采纳、错误subject不采纳、FAIL不被历史覆盖。复用已有手工实验和真实报告原件，不复制改subject后宣称真实语义通过；材料未变的证据不重复重跑。

## 4. C：同组复测、成本和保护项

准备相同的两个 Case，材料与业务立场不变，auto 到Spec、car到Plan，无update第二段，无Coding/设备。首轮已结束，实施与评审后按用户此前授权和TEST现有启动流程复测。新suite、干净隔离目录、不投放方案/评审缺陷表/金样答案。

起跑前把首轮实际输入、artifact、events、summary/报告和必要运行状态按现有归档方式保留到仓外，生成文件清单与摘要，并验证可读；仅保留路径指向即将清理的output不算存证。参数/模型尽量相同，差异单列，不能把跨配置变化全部归因于机制。

评价表对照：单处承载；流程与步骤成功不漏；无默认BI；自动能力正确复用/如实列差距；Plan能观察且能实现；身份与结果不混；报告真实采纳；原有人工结论/业务范围/图文不退化。运行过程中不改被测产物或教授解法。

三轴分按TEST由维护者提出、用户确认。当前无完整分项数值则不补编；复测给证据与建议分。耗时按总墙钟/人工等待/外部故障/作者与审查分别解释，不以少跑审查或少写内容换快。两个Case各一轮，失败先定位，不自动第三轮。

代码/实际事件验证仍待内网，不以本轮Plan可实施宣称已实现。真实restore、回写确认、无变化退出等未经过路径保持未实证，勿为清标签加长流程。
