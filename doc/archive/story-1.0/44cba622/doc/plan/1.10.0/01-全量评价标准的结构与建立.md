# 01 全量评价标准：结构、来源与建立

本册展开[总览](00-目标与评审体系实施方案.md)S1。适用于Extension全量能力及后续版本；1.9.9只是首批取证材料，不是清单边界。

## 1. 标准放在哪里、什么是唯一来源

| 内容 | 唯一维护位置 | 不承担什么 |
|---|---|---|
| 用户需求、有效决定与版本范围 | 各版本doc/spec及明确用户决定的来源记录 | 不以测试或实现反推需求 |
| Extension全量、当前有效评价条目 | `test/regression/extension-acceptance.md`（本次建立） | 不复制全部需求正文，不记录每轮测试结果 |
| 标准更新与评审操作、证据和评分规则 | `test/TEST.md`评价章节 | 不在各plan里另维护不同规则 |
| 某版本对标准做了什么改变 | `doc/spec/<版本>/评价标准变更.md` | 不成为第二份全量标准，旧标准正文由Git/固定快照保留 |
| 某轮评价与差距处置 | 该任务已有评审目录及output/evidence；CLI评分卡仍按TEST | 不回写标准让失败自动变通过 |

不再把全量标准长期放在“1.10.0专属06清单”。若建立 `doc/spec/1.10.0/06-有效目标与验收清单.md`，它只导航到上述标准及建立记录，不保存第二份条目正文。AGENTS只放入口与“标准先于实现”的职责要求。

标准开头标明：标准修订号、对应的目标版本、当前状态（待核/可用于实现验收）、已核来源范围和最后一次变更记录。稳定ID与修订号用于引用，不增加运行期状态服务或要求消费模型回显ID。

## 2. 全量范围与粒度

覆盖用户完整使用链，而不是某轮新增功能：取材与转换、来源与会议、范围与决定、人读Story/Review、知识看到/理解/应用/传递、更新与恢复、归档与外部交付、查询续行与错误处置、安装升级与适配、使用记录与统计。

以现有A—H产品结果树作为初始目录，补入已确认usage能力；它们是分类，不是固定48或56条的完成目标。历史F01—F76、50机制叶、15离线组及各版本需求逐条映射。涉及2.x专有实现时保留适用的用户结果，不能借目录分类把CU/蓝图要求引入当前版本。

一个评价条目对应一个可以独立判断的效果或保护条件。若同一条能同时“计时正确但模型身份错误”，就必须分别给结论，不能只给usage一个PASS。一个条目可服务多个阶段/产物；不能按每个标签复制条目以增大覆盖数。

同一能力下至少区分：正常结果、直接相关的重要失败/恢复结果、已有能力保持与退出。只增加有目标或真实风险依据的条件，不为穷尽排列组合制造条目。纯内部函数、字段和文件不是独立用户能力，只在其承担确定性职责或实现保护时作为取证点。

## 3. 每个条目的完整合同

每项使用下面同一结构，可采用Markdown表加短段落，不新建schema工具：

| 项 | 必须写清的内容 |
|---|---|
| 身份 | 稳定ID、条目名称、修订号；所属能力与过程/产物标签 |
| 为什么存在 | 谁要作什么判断或完成什么工作，缺少该能力会有什么影响 |
| 适用范围 | 哪些输入、场景、阶段、对象和目标版本适用；明确的排除条件及来源 |
| 权威依据 | 用户决定/需求正本的准确位置与效力；样例是格式示意、效果参照还是已定业务事实 |
| 预期效果 | 给定输入和前置后，消费者实际得到什么、下一步如何使用；不得只写文件存在或字段齐全 |
| 不应发生的结果 | 与目标直接有关的遗漏、错误、覆盖、越权或多余人工中断；按实际边界列，不套通用异常大全 |
| 完成判断 | 哪些观察结果算符合，哪些算偏离；缺哪些证据只能判未覆盖；哪些条件允许判不适用 |
| 评判方法 | 读取对象、比较步骤、正常及有区分力的反例/边界、结果记录位置；现有可用工具/命令或明确的人工审阅动作 |
| 必需证据 | 结构/确定性、独立语义、真实行为中本条真正需要的层次；证据必须对应哪个对象/版本/输入 |
| 责任 | 谁产出、谁使用、谁评价、问题最早回到哪里；哪些决定只能由用户作出 |
| 保持/替换 | 本次改动保留什么、由谁接替旧职责；旧入口/数据/指令/测试哪些须退出 |

规则不能写成“评审者认为合理即可”：语义判断仍由模型，但应指向可核的业务事实、关系、效果与反例。也不能为了机械可判而将语义换成字数、关键词、图数、固定章节或特定Case答案。

## 4. 三层证据怎样选

| 条目性质 | 最低可支持证据 | 不能替代它的东西 |
|---|---|---|
| 确定性转换、计量、保护、匹配 | 真实输入输出、有效/无效输入能区分、实际消费者读取结果 | 仅检查函数名、字段或脚本退出0 |
| 来源理解、决定、叙事、知识适用/实体化、图义与增益 | 原件与有效决定、完整对应产物、独立于作者结论的逐项核对 | 作者自述、结构PASS、金样字符串相似 |
| 行动前送达、宿主协作、跨步骤消费、真实使用成本 | 正常入口的完整调用输入/返回/读取范围、产物与后续动作、宿主/配置和版本 | 文件已安装、hook能输出、mock已填最终字段 |

组合能力需要沿生产者→实际送达→使用→下游交接核证；局部确定性helper不强制模型和CLI。缺视觉、目标仓、设备或真实权限时保留标准，证据状态写未覆盖及依赖，不从分母移除。Framework导致无法完成时，效果仍未成立，归因单列Framework，不伪称Extension通过，也不擅改Framework。

标准与证据门槛在实现前定义；证据本身可以在实施过程中取得。不得要求先跑完真实CLI才允许写代码；反之也不得把“以后再想怎么验”当作标准已完成。

## 5. 首次建立全量标准的工作顺序

1. 列来源：当前用户有效决定、全部现行能力的需求正本、维护约束、00—04历史索引、现有验收方法。先判效力，再读实现补取证位置。
2. 逐条梳理：从每项需求找正常效果与保护条件，按§3形成条目；来源互相矛盾时明确被替代者。只有真实目标未定才向用户提出具体问题，不把已确认内容反复审批。
3. 做覆盖映射：旧四套清单每条都记录新落点、合并或有据退出；所有当前需求均有标准落点。支撑手段可映射到同一目标，不计成新能力。
4. 核标准能否判对错：至少用一个合法结果和一个有区分力的错误/缺证据结果走查。不调用新模型也可用已保存结果；不能只拿正例证明判据有效。
5. 核消费者：标准在哪一步由设计者/实施者/评审者取得，工具或原件怎样获得，结果交给谁。若方法不可执行，写明缺口并完成必要方法设计，不能空填“CLI验收”。

建立结果不带当前产品“已通过”的默认结论。新标准完成只表示可以按它设计/实施/评审，具体版本效果另行评价。

## 6. 两个标准条目的样例（说明粒度，不是固定答案）

**材料来源独立性**：输入是两个不同子目录的同名原件；目标是两份材料都可导入和追溯，无额外改名确认。应观察分类/转换/资源/registry/update结果互不覆盖，重复导入稳定。错误结果包括只收一份、同名人工中断或来源串线。复用正常导入命令、目录夹具和实际消费者，不只核命名函数。输入真实不可读属于另一失败事实，不伪装成同名冲突。

**使用记录的缺起点处理**：以V5及路径例外为目标来源；已完成且已有累计的步骤，后续某轮缺起点时不抹已有累计，不编造缺失时长。核真实入口、运行态、最终usage及统计facts；“JSON合法”“completed=true”不支持本条。旧last_result实现即使全部旧测通过，也先判目标口径不符。完整R8仍需分别覆盖身份、模型/版本、Git和报告，不能本条通过就代签其余项。

## 7. S1交回与完成条件

交回当前全量标准、来源效力记录、旧清单映射、未定目标/方法缺口及其具体影响。全量是“清单每项都有明确处理”，不等于所有能力已实跑通过。

完成必须满足：当前需求无遗漏映射；条目粒度能分开成功与失败；每项知道怎么评、谁评、证据从哪来；没有由当前代码反推的未经确认目标；1.9.9以外能力也有标准；Framework主模板不混作Extension目标。链接检查和格式检查只是机械部分。
