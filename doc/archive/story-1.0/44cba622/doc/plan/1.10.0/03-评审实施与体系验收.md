# 03 评审实施、结果表达与体系验收

本册展开[总览](00-目标与评审体系实施方案.md)的评审方法和S3验收。评价的是Extension全量能力；不同评价任务只选择不同的执行范围，不重新定义标准。

## 1. 四类任务怎样使用同一套标准

| 任务 | 必须核的范围 | 交回结果 |
|---|---|---|
| 需求/方案评审 | 新目标、变化目标及会受影响的旧能力；目标到标准再到方案 | 目标是否有效、标准是否完整、方案是否必要且能实现目标、关键依赖/决定是否齐备 |
| 实现评审 | 本次实际改动及其全部消费者、声明保留/退出项 | 实现符合哪些条目、哪些偏离、旧机制是否真退、哪些效果还没有证据 |
| 单次真实运行评审 | 授权运行实际覆盖的条目和产生的副作用 | 输入送达/决策/产物/下游消费/恢复/成本；未走到的条目明确未覆盖，不放大成整版结论 |
| 版本或全量评审 | 该目标版本全量适用条目 | 每项状态及证据边界、整体缺口、是否具备阶段/版本收口条件；不能只审本版新增点 |

性能、知识、人工决定、数据保护和升级属于跨阶段能力，不能因没有独立Story章节而被漏掉。Spec/Plan只评价Extension拥有的扩展面和义务链，Framework主设计质量是证据背景；Story/Review整体属于评价范围。

## 2. 评审前取得什么

先取得标准身份及本版标准变更、用户目标来源、实际代码/指令/产物身份、交回范围、声明验证与原始证据。仅定位后再读取具体材料，不预先全仓通读。

明确检查对象是开发源、安装件还是实际运行件；工作区未提交改动必须纳入身份，不能只报HEAD。输入和宿主不同的运行不可直接做版本收益比较；缺失的原件列缺口，不用当前文件假装当时原件。

## 3. 每条如何评价

1. 先读对应目标和标准，核有效决定及样例前提，不先接受执行者的“已完成”。
2. 沿实际生产者到消费者查结果：谁取得输入、谁决定、输出被谁读、失败如何恢复。看正常使用结果，不以抽象函数齐备替代。
3. 按标准要求选证据层次。机械已能计算的交给现有工具；语义由模型读完整相关对象判断；组合行为用真实事件和结果，不用mock代签。
4. 检查未知合法输入与直接相关边界，确认不是按一个Case名称/固定值拼出来；不无限扩损坏协议或提高防御等级。
5. 核更简单完整的实现及旧职责退出。新增有消费者、删除有接替者、必要保护仍在；先核目标必要性，不能只有预算数字和测试总数。
6. 写条目结论及依据，保留不确定性和下一动作。语义问题落回最早责任处，不要求后端脚本靠关键词修正文含义。

## 4. 结论规则

| 结论 | 必须满足 | 常见误用 |
|---|---|---|
| 符合 | 标准适用、对象一致、要求的结果成立、必需证据已取得 | 只有结构通过就声称行为成立；当前字段按旧合同测试通过就算符合新目标 |
| 偏离 | 有可定位事实说明目标、实现或结果不满足标准 | 仅不喜欢措辞或图形形式；把金样额外前提当强制答案 |
| 未覆盖 | 没运行、没读全、无必要原件、无环境或方法尚不能证明 | 填0、标不适用、从分母移除、用作者“已检查”替代 |
| 不适用 | 输入/范围确实不满足适用条件，且有来源依据 | 缺视觉/设备/真实目标仓就标不适用；因为难做而退出目标 |

目标对齐、实现符合性和效果证据分别判。一项包含多个独立条件时逐子条件写结论；不能用“部分通过”掩盖剩余条件。某条证据支持结构不支持语义时，在两个层次分别写，不把局部结论向上覆盖。

有偏离是否阻塞，依据它对已确认目标、正常功能、数据和权限的实际影响；声明依据、责任和最小关闭条件。缺证据影响的是结论范围，不能自动变成扩大实现的理由。允许继续无关工作，但不把受影响目标标完成。

## 5. 报告必须包含的内容

报告沿当前评审目录保存，用以下栏目即可，不建立新的报告平台：

1. 对象、目标版本与标准身份，任务类型和本轮范围；
2. 逐条对照表：目标ID/修订、预期、目标/方案对齐、实现与退场、证据与效果结论、差距责任及动作；
3. 未覆盖与不适用清单及原因，引用全量保持集合和本轮实际覆盖集合；
4. 有价值的差距、根因及修正方向，区分确定事实与解释假设；
5. 结构、独立语义、真实运行、成本、用户确认及发布条件分别总结；
6. 后续动作与授权边界，不用一句“通过”跨越全部层次。

如果报告需要覆盖比例，分母只取该标准修订的适用条目。符合、偏离、未覆盖数量并列；不适用单列依据，不重复计多标签。比例只是覆盖事实，不是质量分。未完成映射前不输出伪精确百分比。

## 6. 评分、成本与历史比较

现有三轴仅在其适用对象上使用，继续建议分→用户确认→基线晋升；全量Extension条目结论不能被三个平均分代替。没有现成数值标准的能力不随意扩评分轴，使用可定位的效果结论。

性能先定义统计区间、人工等待、外部故障和并发口径，再比较。原生工具事件截断时，次数是已观察数；审查对象重验、同步闭环与完整harness不能混成同一种循环。不得通过限正常返修次数、禁止查错或减少业务内容制造效率收益。

比较前逐项核目标修订、材料、有效决定、模型/宿主、工程与机制身份、交互干预、终点及样本范围。可比条件相同才分析版本收益；不相同则明确差异，不推成功率。稳定性必须有同条件重复证据，不能一次成功就写稳定；历史结果按当时标准保存，新标准重评写新记录。

## 7. 体系本身如何验收

这一步同时检查全量、跨版本、判定区分力和实际使用，不只回查1.9.9七个问题。

| 验收面 | 操作 | 预期结果 |
|---|---|---|
| 全量覆盖 | 从原始需求、旧四套清单、现行命令/产物入口反查有效标准 | 每项有去向；安装、update、知识后段、归档恢复等不因本轮未测消失；额外条目均有目标来源 |
| 来源可靠 | 给出旧实现/旧样例与用户最新决定不一致的真实材料 | 先指出目标版本差异，再评价实现；不会选“代码已支持”的那一份当正本 |
| 版本演进 | 按02走一次新增/修改/退出/保持的演练 | 标准先于实施；旧ID/旧证据可追；保留能力有回归；不混用两个修订 |
| 正反区分 | 同一有效标准下，核一个满足结果、一个有关键语义错误、一个缺证据的对象 | 分别符合、偏离、未覆盖；不按格式或关键词归类 |
| 合法变体 | 同义表达、不同图表组织或另一合法输入 | 不因不同于金样的表面形式误判，不为消除误判降低业务要求 |
| 必要性 | 回看清理反例、强制多模态等真实过度设计 | 能区分有实际必要的保护与新增负担，责任回原位置；不据构造边界无限追加机制 |
| 新一轮使用 | 按新方法评审下一份实际交回，列全改变/保持/未覆盖 | 报告能支持具体推进决定；不能只报绿测，也不能只报已知问题 |

现有1.9.9失败记录可用于来源可靠/必要性/部分语义反例；其它维度从原有材料和合法中性输入取得。不能把“命中已知七例”作为全量体系完成的充分条件。

本轮不运行新的真实CLI或外部模型。无独立执行者时，自查标自查；实际方法实施后可由下一次维护评审取得独立使用证据。未取得的可靠性证据要写清，不能把文档建立称为所有未来判断已可靠。

## 8. 实施交回

交付：全量当前标准、历史映射、本版标准变更、TEST/AGENTS实际入口、全量和演进演练记录、正反例与合法变体结果、实际交回使用报告或明确待验证项。维护证据按TEST §0.4，禁止改历史CLI和业务产物补通过。

产品G/X=0。不增加新消费模型任务、扩展状态、网络服务或评分脚本；若现有工具不足，只记录需要核的机械事实和可执行现有替代方法，不借测试域扩建平台。标准内容正确和能用于判断是本轮质量要求，文件数量或篇幅不是验收目标。
