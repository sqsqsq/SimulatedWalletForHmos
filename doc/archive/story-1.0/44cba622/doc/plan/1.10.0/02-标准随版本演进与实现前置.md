# 02 标准随版本演进：先更新标准，再实现

本册展开[总览](00-目标与评审体系实施方案.md)S2的版本过程。适用于每个后续版本及版本内需求实质变化，不限1.9.9，也不限功能新增。

## 1. 固定顺序与责任

**版本需求和目标确定 → 更新全量评价标准及本版变更说明 → 核对目标覆盖与判法 → 开始产品实现 → 按同版标准评审与验收。**

| 时点 | 维护设计者 | 维护实施者 | 评审者/用户 |
|---|---|---|---|
| 定需求 | 取得用户目标、范围、样例效力与保留能力，整理真正未定事项 | 提供环境与实现事实，不据现状缩需求 | 用户裁定需要他决定的目标和范围 |
| 更新标准 | 建立新增/修改/退出/保持条目及证据方法，说明对现有能力影响 | 核方法可执行、所需环境与输入可取得 | 按需求核标准是否能区分正确/错误，是否过拟合或额外设限；不能只查链接 |
| 开工 | 在本版实施方案写清使用的标准修订和变更记录 | 核标准已更新且与任务一致；记录基线，开始实现 | 不增加重复人工审批；只有目标冲突、范围扩大等需用户决定 |
| 中途变化 | 先核是不是目标变化，必要时先更新标准，再改受影响实施 | 实现问题不自行改标准；不受影响部分继续 | 评价变化的依据和影响，不把失败改名成通过 |
| 验收 | 汇总目标实现和未覆盖项 | 提交实际实现/退场/证据 | 按固定标准逐项判；用户确认评分或接受具体缺口 |

标准尚未更新时，可调查、核环境、验证可行性、保留现场；不能将受影响的新目标直接投入产品实现。标准已经定义而实跑环境暂缺，不自动禁止所有实施，须明确后续证据依赖和不能宣称的结果。

## 2. 本版标准变更说明的内容

每个新版本在 `doc/spec/<版本>/评价标准变更.md`记录：目标依据、采用的全量标准修订、变更条目、保持范围、旧条目替代关系、必要证据与回归、目标确认来源和标准核对结论。它是目标到标准的交接，不复制全量条目。

每条变更列：条目ID、原修订→新修订、变更类型、为什么变、预期结果前后差异、受影响阶段/产物/消费者、旧证据能否继续用、验证安排。只有表达修正时写清语义没变；没有变化的条目引用完整保持集合，不逐行重复正文。

本次1.10.0首次建立的版本变更记录以当前Extension全量目标为基线；1.9.9逐项确认用于校准其中受影响条目，不把全部标准命名为“1.9.9评分表”。后续版本沿同一文件结构记录自己的增量。

## 3. 新增、修改、删除、拆分、保持怎样处理

| 类型 | 必须做的事 | 不允许的做法 |
|---|---|---|
| 新增能力 | 先给出目的、效果、判法、证据和边界，再实现；列与旧能力的组合验证 | 代码完成后才用现有结果定义目标 |
| 修改效果/范围/容许输入 | 保留稳定能力ID，增加条目修订；写清有效版本与旧证据失效范围 | 仅改测试期望、不记录目标改变 |
| 退出能力 | 明确用户/有效需求依据、接替者、数据/入口/文档/测试退场与保持项 | 因难验证或缺设备从清单删除 |
| 拆分/合并条目 | 记录旧ID到新ID映射，原要求有去处，覆盖数重新解释 | 借拆分把同一事实重复计为多项成功 |
| 方法改进但目标不变 | 记录新方法的区分力与证据变化；可复核旧对象时给重判记录 | 把方法更新追写成当时已采用/已通过 |
| 完全保持 | 标明依赖未变及可复用证据；组合/共享改动影响到它时做针对性回归 | 因本版没直接改文件就自动认定不受影响 |

被删除的ID不再赋予无关新能力。历史正文由Git保存；当前标准只保留有效要求和必要的退出映射，不并列互相冲突的“当前版本”。

## 4. 标准如何绑定到具体评价对象

开工与评价记录标准修订号、目标版本、源码身份、需求/输入版本、宿主/模型/配置、Case/阶段范围及使用的证据。已提交标准用Git提交定位；未提交标准在该次output/evidence下保存固定文本与摘要，报告指向该副本，不只链接一个未来会变化的工作区文件。

这不是新的签名或防篡改平台；使用现有Git、普通文件与摘要即可。被审对象或标准后来变了，原报告继续绑定原对象；重新评价写新结果并解释差异。不能因同一个版本号没变就借用旧报告。

两个版本并行时，各自在本版变更记录和证据中绑定自己的标准修订。共享当前标准有冲突时先合并已确认的目标增量，不能后一份直接覆盖前一份；不要求每个分支维护第二套全量标准系统。

## 5. 标准核对与开工条件

维护设计者或指定reviewer核四件事：需求每条有标准落点；预期结果确实来自有效决定；判法能区别正确/错误且可执行；保留与退出范围覆盖实际消费者。执行者可以据此自查但不得把自己写的标准自检称独立评审。

核对结论在本版评价标准变更或既有方案评审中记录，不新增审批页面。用户已经确认目标的，不再请用户逐条批准技术验法；若标准选择改变了用户承诺、引入额外人工中断、改变评分量表或扩大范围，才回用户决定。技术实现偏离标准时修实现；标准自身错了回目标来源，不让两者互相证明。

开工前可检查的条件：本版变更记录已存在，当前标准覆盖本版目标及保留项，具体判法/证据依赖已写清，影响关键设计的未决已处理，使用的标准身份可固定。现有目标无法确认时只停止相应依赖，不以一个无关疑点冻结整版。

## 6. 评价标准与样例如何同步

先更新标准含义，再按需同步样例/金样/测试。每个样例标用途：输入示例、数据结构示意、目标效果参照或已确认业务答案；范围和前提明确。样例不是反向制定目标的来源。

格式/编号的机械同步与业务内容修订分开。金样实质业务变化仍按现有审定规则；不能为迎合最新实现改金样，不能把样例中的可选额外前提升级成所有业务必需能力。V5这类用户明确指定的合同不能因为文件名叫候选而被旧实现文档覆盖。

## 7. S2实施文件与验收

- TEST评价章节：写入上述顺序、标准变更与证据绑定规则，原评分/CLI操作规则保持。
- 项目AGENTS设计/实施/评审入口：短句引用TEST和全量标准，明确“需求目标确定后先更新标准，再实现”；不复制完整流程。
- 本版 `doc/spec/1.10.0/评价标准变更.md`：记录第一次建立与替换关系；后续版本按同一规则写自己的文件。
- 当前1.9.9统一接续：引用新标准核对方法，不将1.10.0建设限定为1.9.9专用。

验收必须走一次版本演进演练：从已知旧目标→用户新决定→标准增量→实现开工核对→新对象评价。证明旧报告不会误用于新标准、保留条目不会消失、目标未定不会被代码默认、已确认目标不被重复审批。演练只用现有历史材料或明确标记的中性示例，不制造新的真实产品需求或调用真实CLI。
