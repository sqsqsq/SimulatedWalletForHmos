# 记录端：Extension收尾，归档前写完整

本文件按用户2026-10-22更正更新：采集属于Extension，不依赖Framework修改。原phase_closed上游通知方案撤销，不作为前置或后续待办。当前总入口为[CLI后整改统一接续](../2026-10-22-CLI后整改统一接续.md)。

## 1. 现有职责与收尾动作

Framework继续按原流程产生trace、summary和closure_commit。Extension负责在开发流程中采集并形成usage；消费模型执行Extension的正常收尾作业，脚本负责读原生事实、幂等写入和核结果。用户不手工补点、补数或搬运现场；统计者只读归档结果。

在现有 `story/scripts/core/usage.py` 增加直接可调用的收尾参数：

```text
python doc/extensions/skills/story/scripts/core/usage.py --project-root . --feature <需求编号> --finalize --phase <本阶段>
```

复用现有refresh/结算/写保护，不另建采集器、事件或阶段状态机。原stdin JSON入口继续供已有hook使用；finalize是一项明确的Extension作业，不重跑Framework、不包装或取代它的check-receipt。

- 输入：执行现场的既有身份件、trace、有效summary、Story/update原生记录；phase是本次收尾的阶段，不推断不存在的后续阶段。
- 先核本阶段有原生有效closed及完成时刻，且现有采集身份可对应；未闭环/缺身份/事实不可读如实失败，不造完成状态或新身份掩盖缺口。
- 在同一记录器内结算当前需求已有完成事实，读取实际落盘usage核步骤行/累计与本次可核事实一致。没有起点的已完成轮保留缺耗时语义，不能冒充0秒；其它未完成阶段不加行。
- 返回这次结算的阶段、已记录步骤、耗时缺口及成功/失败；不新建完成回执文件或在usage加完成游标。重复finalize不多记，原生业务closed不被改写。
- 写失败返回非零，明确“业务已闭环，使用记录未完成”；消费模型重试同一收尾动作，成功前不得声称使用记录可归档。不回头重做业务门禁，也不把失败推给stats。

## 2. 如何在实际流程中执行

- `extensions/skills/story/AGENTS.section.md`维护一份统一的“阶段收尾与代码归档”指令：原生闭环成功→执行上述收尾→确认usage写成→再交付/询问下一阶段/正常提交代码。六阶段 `hooks/<phase>/author.md`只在收尾位置引用这一职责；spec/plan动态任务包同步给当前阶段的可执行命令，避免首次在报错时才送达。
- `hooks/shared/usage.mjs`与manifest现有pre_phase保留，负责首次活动与重试起点；不登记phase_closed，不改任何Framework事件。
- Story的 `story-build check --deliver` 已通过现有delivery.mjs调用Framework回执验证：在原生回执成功后直接复用记录器完成spec结算，再交回交付门结果；失败时报告usage未就绪，不进行远端写入。使用现有runPython/客户端调用方式，不另起命令调度层。先查直接消费者，确保归档仍通过这个现有交付门，不复制第二个判断。
- Plan/coding/review/ut/testing及未走Story的Framework需求，由消费模型按已安装的Extension作者入口执行同一收尾命令。到哪个阶段停，就在该阶段收尾，不依赖还有下一阶段。
- Story成文与update关闭仍经现有命令后采集；代码归档前对当前需求再调用同一幂等收尾，是已有结果核对，不另起结算算法。归档仅提交usage及代码，不要求doc/features进Git。

这里的保证是“Extension作业+确定性命令+实际行为验收”，不是后台必然回调。模型可能忽略指令，测试和交回必须核正常收尾真实调用与归档usage，缺调用或漏记录即不通过；不能把这项风险转换成未经用户要求的Framework改造。

usage更新不能自激新业务subject或要求重复语义审查；当前产品工作区摘要排除doc运行产物，仍核实际输入集合。采集不改变Framework的完成判据。

## 3. 临时状态最小内容

| 项目 | 最终做法 |
|---|---|
| 首轮阶段起点 | 直接读trace.started_at，不另写starts副本；保留毫秒，求差后取整。trace缺失且无可信起点就不编耗时 |
| 已完成阶段的重试 | 第一次pre_phase记录该未结算轮起点；同轮再跑门禁不覆盖；收尾结算后清除。原生current-phase会覆盖，不能替代这项 |
| Story | 身份件→首次成文，usage已有story行不重复计；不建Story临时起点 |
| update | 从已有逐轮record派生，已收口再撤回仍保留历史；不建update起点或游标 |
| 空slot/空starts | 不为仅init、版本/身份刷新创建空状态文件；最后一项必要状态消失后在现有锁内清掉空文件，不建清理任务 |
| pending | 只有本次steps发生待提交变化时保存受影响步骤的最终目标值；不复制全部历史steps，不因只改agent/version创建pending；usage成功后清除 |

仍按现有顺序保存必要待写值→原子写usage→清待写，失败后按目标值赋值而非再加一次。阶段起点的清除与usage累计涉及两个文件，不能只删pending却保留这种跨文件累计。新流程既不新增完整结算历史，也不向usage增加游标/状态字段。

`load_state/apply/record/refresh`只按真实需要建立或写slot；统计不调用这些写入函数。身份件和自报输入仍为执行现场辅助件，正常接收后原处理保持；独立stats永远不读取它们。

已存在的合法usage不转换、不清空；旧版本格式按既有不兼容规则报错。运行态以本轮活动状态为准，无消费者的空内容直接退出，不增加历史格式兼容分支。锁、原子替换、坏文件报错、其它需求隔离保留。

## 4. 必验路径

经正常消费模型开发/交付顺序和现有Extension交付入口验证，不只直接调用refresh：

1. 六阶段参数化运行到其中一个终点即结束，没有下一阶段、没有story额外命令、没有stats：usage已含该完成步骤；纯Framework入口也成立。
2. trace首轮、重试轮、重复harness、重复check-receipt/sync-closure：累计符合原口径；重复Extension收尾不多计，不额外造新起点。
3. 起点已有但未完成，不计spent；缺可靠起点的完成行保留而不编耗时；等待/中断只在该已完成可核轮次内计算，不改变V5定义。
4. 注入usage写失败、状态写失败/清理失败，分别重试Extension收尾：业务已闭环事实不回退、usage不丢不重加、最后能收敛；无需调用stats补记。
5. init/Story/update不生成无用途空账；一次仅结算一个步骤时pending不带其它完成历史。并发不同需求、旧usage坏JSON保护保持。

复用现有test_usage、test_usage_entries、test_story_update及预算测试；六阶段及纯Framework用法用隔离安装件验证；直接调用记录器只证明脚本，不代签消费模型已按收尾顺序执行。Framework保持原发布件不动。
