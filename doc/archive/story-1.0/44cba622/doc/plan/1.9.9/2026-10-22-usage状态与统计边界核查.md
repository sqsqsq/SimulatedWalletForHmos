# usage状态与stats输入边界核查

2026-10-22，维护设计者（Codex，本会话）。用户最新决定：用Framework写需求后，随代码归档的使用记录只有doc/usage.json；doc/features整个目录不归档。独立stats只能从usage.json和代码提交记录取得信息，不能假定存在任何需求现场。本轮核源码及隔离复现，不代实施者修改产品。

## 1. 结论

**stats当前确实越界，应删除统计前补结算及其运行态依赖。`.usage-state.json`中也有重复内容，但在保持当前“多轮累计”语义时，不能把整份文件简单删除。** 现有阶段记录不是完整、逐轮不可变的计时历史。

此前将整份临时状态解释为必要过于笼统。正确边界是：记录器负责采集并写usage，stats读取已形成的usage和Git；统计不能为了补记录再次执行记录器。记录时若仍需保存原生系统没有的最小事实，它也不属于统计依赖。

隔离复现：合法usage、可用Git，仅把临时状态写坏，现有stats collect退出1，报“统计前对账没做成”。原usage未变。证据：`output/evidence/1.9.9-usage-state-audit-20261022/probe.json`及同目录scripts。这个失败不应阻止统计已有usage。

## 2. 已有记录实际能提供什么

| 来源 | 已有事实 | 不能据此推断的内容 |
|---|---|---|
| 需求目录 `.usage-id` 与 story-flow | init身份时刻、成文登记时刻 | story_written_at会随后续重登更新，不是所有成文轮次历史；首次已结算值在usage保留 |
| update各轮record.json | 每轮opened_at/closed_at、baseline及撤回状态 | 不需要再维护update起点；当前实现已按原生记录派生，此项保持 |
| 阶段reports/trace.json | 首次阶段起点 | harness-runner的recordStartCommit在已有start_commit时不覆盖，不能提供每轮重试起点 |
| 阶段summary.json | 当前有效闭环及closure_commit.committed_at | 后续harness/闭环会更新当前summary；不是历次闭环时刻集合 |
| Framework `.current-phase.json` | 当前任务/最近一次harness的started_at | phase-state在每次running写入新起点，并在切换任务时覆盖；不等于usage同一未结算轮的首次起点，也不保历史 |

源码位置：`demo/framework/harness/harness-runner.ts` 的 recordStartCommit、running状态写入和生命周期调用；`scripts/utils/phase-state.ts::mergeAndWritePhaseState`；`scripts/utils/phase-closure-finalizer.ts` 的canonical summary发布。仅查interactive现有链路，没有拿headless/goal日志代替产品契约。

例：相同的首次起点、最终重试起点与最终闭环，可以对应不同的首次闭环时刻，因此累计耗时不同。最新trace/summary/current-phase的组合不能逆推出全部过去轮次。直接用“最终完成−首次开始”替换，会把轮次间空档一起算入，改变V5含义。

## 3. 临时文件逐内容取舍

| 当前内容/动作 | 判定与最小处置 |
|---|---|
| 为首次阶段复制trace.started_at到starts | 原生trace有效时重复保存，应直接读原件；保留原毫秒精度，求差时才取整 |
| 未完成的重试轮起点 | 当前原生记录不能稳定替代；维持多轮累计时保留这一最小事实，不能把每次harness调用当新轮 |
| Story/update运行态起点 | 不需要；Story按身份与首次成文，update按原生轮记录。不能为它们重新引入起点/游标 |
| init或普通刷新产生空slot、空starts并写文件 | 无计时或待写内容时没有必要；不为仅创建身份或刷新版本制造空运行态 |
| pending复制该节点全部steps | 范围过宽；仅在有实际结算写入且跨文件失败恢复需要时，保存本次受影响步骤的待写值，成功即清，不长期复制完成历史 |
| pending防重复职责 | 不能在仍用“usage累计+另处清起点”时直接删除，否则一次只写成功一边可能重复加或丢计；若实施改为单源可重复派生，自然随旧结算路径一并退出，不为保文件而保机制 |
| stats调用reconcile | 必须退出；stats不读取/创建/清理该文件，不补写usage，不因其缺失/损坏失败 |

锁、原子替换是正常写保护，不是第二套业务状态，保留；不引入新的事件账本、计时服务或迁移兼容分支。

## 4. stats的明确新边界

- `story-stats/scripts/stats.py::collect` 删除 `usage.record(..., 'reconcile')` 及其失败前置。事实计算只读固定的doc/usage.json字节和固定Git HEAD/历史；不扫描需求目录、summary、trace、story-flow、身份件、自报输入或临时状态来修改数据。
- 需求按usage节点中的编号与启动身份展示，不读取工作区或Git中的doc/features正文找名称，也不从提交说明猜需求名。Git提供提交作者、关联提交与变更量。项目展示名可以用仓目录名，不为补名称往usage加语义字段。
- 合同、解析代码与报告模板属于程序定义，不是第三份运行数据真源；可继续复用，不为“仅两种数据”强拆一套库。统计输出仍沿现有输出安排；无业务提交如实报告，不能拿起跑提交凑数据。
- Skill、模板、入口说明及测试同步退出“统计先对账”。不能把reconcile搬到stats启动包装层或要求用户先手动补账，伪装成stats没有依赖。
- 相同usage字节与Git HEAD应给出相同业务统计事实；允许采集时间/输出目录不同。统计前后usage字节不变。

这是对旧V5“stats前对账、名称从工作区现取”的明确替换，不得同时保留两种有效口径。

## 5. 记录端需要正视的缺口

删除stats补结算后，最后一个已闭环阶段可能还没有进入usage。上一轮车钥匙Plan正是由stats才补出的。**不能为了统计纯读而把缺的最后阶段当作不需要记录。** 这属于记录器生产链的缺口，不应由统计消费者补救。

当前Framework的post_phase名字容易误导：它在harness检查/审查提示生成过程里调用，早于后续closure_commit正式发布；不能把usage挪到这个hook就宣称解决。当前finalizePhaseClosure/check-receipt的正式闭环发布路径没有发现对应的Extension后置通知。

记录端在业务闭环后仍须完成采集，但不要求Framework新增触点。按用户最新更正，Extension提供正常阶段收尾动作，消费模型在交付/代码归档前执行，脚本读原生事实并核usage落盘；Story交付门直接复用。原先把缺少底层通知推成上游改造前置的判断撤销。不能要求用户手工补账，也不能把stats包装成补账入口。

因此分开交回：stats解耦和冗余状态减量可以局部实现/验证；“最后阶段自动进入usage”和“完全删掉所有计时运行态”不能在没有替代证据时宣布完成。当前没有证据支持既删除所有状态、又保持原多轮计时及失败防重语义。

## 6. 必要验收与接续

1. 从已归档代码仓建立独立副本，仅有usage与Git，没有framework/需求目录/临时状态，stats可给完整约定事实与报告；Git历史里也没有doc/features。需求用编号与启动身份呈现，不能因没有需求名称而阻断或把它当异常。
2. 同样usage与Git，增删或改写无关阶段文件不改变业务统计；统计不写usage或运行态。
3. 记录器首次阶段直接用有效原生起止，重复刷新不增加；已有重试累计、等待/中断、缺起点不抹已知值及失败重试保持。
4. Story/update不制造多余运行态，纯init不创建空账；pending只含本次必要待写结果，成功后退出。已有合法使用记录和并发保护不删。
5. 自动闭环最后一阶段写入usage必须取真实生产者触点证据，不能再以stats补写通过。未接好前明确限制，不宣告V5全程完成。

本核查不是扩充前一份“授权与图文审查”方案；两题共享文件有交叉时串行处理并固定真实基线。已形成[当前实施包及预算](2026-10-22-usage归档闭合/00-执行接续与预算.md)，以Extension阶段收尾接替已撤销的上游通知方案；本核查保留事实依据，具体执行以该包为准，产品本轮未修改。
