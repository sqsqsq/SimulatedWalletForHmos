## 2. 各项改动与证据

### Q01 同一块合法性一处判

**改动**（`figure-view.mjs`）：
- 新增 `inspect`：一次读出配对、ID、块体形态、源，以及每块自己的问题。
- `switchView` 与 `readingWork` 都只消费它：
  - 坏块体、重复 ID、孤立标记、源缺失都不能产出「阅读完成」，块体坏时逐图 state 为 `invalid-block`；
  - 只有结构问题、没有合法块时也算「适用」，不算完成；
  - 合法无图仍是「不适用」。
- `readingWork` 直接给出下一动作 `next`，文字从 `routing.reading_todo` 移过来，Python 侧改为照用。
- `switchView` 给出结构化的 `kept: [{id, reason}]`；`restoreView` 按它逐张报，不再用正则从中文 notes 里筛。

**证据**：`test_figure_view.py::OneBlockOneVerdict`。
- 三种坏块（块体不是图、重复 ID、孤立开始标记）在以下入口结论一致：
  - status：未完成，且给出下一动作；
  - `view mermaid` / `svg` / `toggle`：都退出 1；
  - 正式命令 `number`：退出 1；
  - 装置 `run_case.reading_facts`：`pending`。
- 整个过程中 story 字节不变。
- 源缺失时判 `no-source`，mermaid 拒绝。
- 无图时 status 与装置都是「不适用」。

### Q02 阅读进入任务结束决策（`test/scripts/run_case.py`、`run_multi_case.py`）

**`reading_facts`**：
- 完整保留产品的逐图原因、`unmanaged`、`problems`、`next`。
- 状态分四种：complete / not_applicable / pending / unknown。
- 子进程起不来、退出码非 0、输出不是约定形状，都是 `unknown`，不当成「不适用」或空待办。

**worker**：
- 第一段收口（单段直接结束前，或停到第一检查点前）和第二段 update 收口（停到第二检查点前），先调 `reading_followup`。
- 阅读待办在，就把产品的 `next` 原样作为续话交回同一段。状态读不出时，交回读不出的原因和查看入口。不加修法。
- 同一份待办连续 `READING_ATTEMPTS`（2）次续话后仍没有变化，就不再续，记 `reading_stopped`，然后按原逻辑结束或进检查点。

**终态**：
- `closure_facts` 带 `target_complete`：业务阶段闭环，且阅读完成或不适用。
- `pipeline.status` 分三种：`completed_at_requested_end`、`business_closed_reading_incomplete`、`requested_end_not_reached`。
- 进程终态 `finished` 的含义不变。
- suite 摘要带 `target_complete`。

**证据**：新文件 `test_reading_completion.py`，8 项。用替身 CLI 驱动真实的 `foreground`：
- 产品下一动作逐轮转交，阅读做完后整体完成；
- 待办不再变化时只续 2 次，记阅读未完成，进程仍是 finished；
- 读不出时不当成不适用：续话里带原因，读不出到底就记未完成；
- 双检查点：第一检查点在阅读完成后才停；update 改图后，第二检查点也在阅读完成后才停；
- `reading_facts` 保留原因与下一动作；退出码非 0、不是 JSON、缺 complete 三种都是 unknown；
- 整体目标需要两者都成立。

### Q03 报告目录与 framework 同口径

**解析规则**：与 framework 的 `featurePhaseReportsDir` 同口径——`paths.reports_dir_pattern` 是非空字符串就用它，否则用 framework 默认 `doc/features/<feature>/<phase>/reports`，不随 `features_dir` 变。依据：demo/framework/harness/config.ts 第 599 行与第 1993–2016 行。

| 位置 | 改动 |
|---|---|
| `hooks/shared/paths.mjs::phaseReportsDir` | 新增，JS 侧唯一解析 |
| `materials/importer.py::phase_reports_dir`、`project_root_of` | 新增，Python 侧唯一解析，与 `features_dir` 共用读配置 |
| `verifier-report.mjs::reportLocation` | 改用它；summary 在却读不出时判 ERROR / FAIL，不再当「不在」 |
| `flow/update.py::_phase_facts` | 改用它 |
| `flow/routing.py::spec_closed` | 改用它；坏 summary 报错，不拿别处的旧报告顶 |

`ut/reports/ac-coverage.json` 是 framework 按需求目录写的（check-ut 的 `featureFilePath`），不归 pattern 管，保持不动。

**证据**：
- `OneBlockOneVerdict::test_spec_closure_is_read_where_the_project_puts_reports`：
  - 默认布局认得出闭环；
  - 自定义 `audit/<feature>/<phase>` 认得出闭环；
  - 配置了别处时，默认位置的旧 summary 不被读；
  - 坏 summary 报错；
  - 没闭环不误判。
- `test_the_report_check_reads_the_configured_place`：交付门的报告核对在自定义位置找得到 summary，坏 summary 判 ERROR 并说读不出。
- `test_story_update.py::test_phase_facts_follow_the_configured_report_place`：update 读配置位置，不读默认位置。

### Q04 单次只读操作的成本

**改动**：
- figure-check 新增 `--json`，一次给出结构问题与依赖；替换只给局部验收用的 `--deps`。
- `problems_of` 的引用核对复用 `local_deps`（同一份递归），删掉重复实现。
- `figure-reading.mjs::svgFacts`：同一进程内按 SVG 内容复用 figure-check 结果，内容变了就重核，进程结束即失效。
- `cmd_status` 只派生一次阅读事实，路由与输出共用（`next_step` 新增 `reading` 参数）。

**证据**：`output/evidence/1.9.9-20261015-r3-q04/measure.json`（脚本 `output/scratch/1.9.9-r3/q04_measure.py`）。输入是同一份：一张已验图、SVG 形态、已登记成文且无漂移。分别在 38604ccd 和工作区上各跑 3 次 `story_flow.py status`：

| | figure-check 启动 | 耗时（秒） | next / 阅读完成 |
|---|---:|---|---|
| 调整前 | 6, 6, 6 | 0.71, 0.67, 0.67 | run_archived / true |
| 调整后 | 2, 2, 2 | 0.42, 0.37, 0.37 | run_archived / true |

剩下的 2 次：一次是 status 派生阅读事实，一次是退出时恢复视图。二者在不同进程，恢复视图本身要按当前文件重核，属于正确性责任，保留。
