## 4. Case B′ · car-key-sharing（ISSUE-206 重设计）

### 4.1 业务设定（材料的事实基础，成文时以此为准）

**数字车钥匙分享与撤销（钱包端）**。车主的车钥匙已在钱包（已配对车辆），本需求做分享链路：

- **分享**：车主从车钥匙卡片进入分享 → 选联系人 → 选权限档（**全功能**=解闭锁+启动+后备箱 / **受限**=仅解闭锁）→ 设有效期（7 天 / 30 天 / 自定义至多 180 天）→ 发起后**车云与车厂云双确认**（一成一败必须回滚，不得出现半生效）→ 被分享人钱包收到待接受钥匙（**72 小时未接受自动过期**）→ 接受后生效。
- **配额规则**：每辆车同时生效的分享**至多 5 人**；配额满时发起入口置灰并给原因。
- **撤销**：车主随时撤销。被分享设备在线即时失效；**离线时进入「撤销待生效」**，被分享设备回网后本地钥匙自毁，宽限窗内车端黑名单兜底。
- **分享状态机**（六态互斥）：待接受 / 生效 / 已过期（未接受）/ 已到期（有效期满）/ 撤销待生效 / 已撤销。
- **中断续办**：发起分享在双云确认途中退出或断网，回来从检查点继续，不重复发起（同一发起的幂等标识）。
- **埋的冲突（一处，测冲突登记与人工定源）**：离线撤销宽限窗——产品稿写 **24 小时**，SE 稿写 **48 小时**。人工定源答复口径：按产品 24 小时，SE 稿是早期数值。
- **埋的未决项（两处，测 open 议题不进 story）**：① 被分享人能否转移分享（产品倾向禁止，待安全评审拍板）；② 宽限窗到期时车辆本身也一直离线，是否要求车厂云强推失效（待与车厂确认）。两处材料里明写「尚未确定」。
- **无兄弟单据**（本地单）——范围章交接节走「不出现」路径。

### 4.4 口吻红线（BLOCKER，进判据 KM2-2，**两个 Case 的材料都要过检**——用户 2026-08-30 追加裁定：不能与 skill 内容过拟合，必须是真实的需求叙述方式，不能出现任何提示性描述）

材料是需求方与 SE 的正向业务文档，四层检查：

1. **机制概念词零出现**：守恒 / 单元 / 落点 / 探针 / 判据 / 台账 / 章节合同 / 主叙事 / 归档件 / 三态 / 机器面 / 模式名（decision-tree、page-interaction）等；
2. **skill 语言指纹零重合**：从 SKILL.md / 作业书 / 模板 / rules 提取特征短语表（如「可观察的通过条件」「每个原始验收编号独立」「叙事件」「评审件」「合规回显」……执行者建表并入检查脚本），材料 grep 零命中——材料可以有验收表，但表头与措辞用需求方的自然用词（「预期」「通过标准」），不得照抄 skill 措辞；
3. **结构非同构**：材料的章节结构不得照 story 十章骨架或 spec 模板骨架组织——真实 PRD/SE 有自己的自然结构（参照：AR90006 的 SR 结构「整体协作 / 本轮拆分 / 接口与数据 / 失败与恢复 / 数据保护与交付」即自然形态，2026-08-30 初检已过：机制词与 skill 语言零命中）；
4. **无实现指令与引导语**：不出现类名、目录、文件名、代码结构建议（SE 的接口名与字段表是正常 SE 内容，允许）；无「请注意展示」「务必包含」「需在最终文档中体现」这类面向产物形态的提示性句式。

判法：三张词表（机制词 / skill 指纹 / 引导语句式）grep 零命中 + 维护者通读无出戏感——**两 Case 材料（含 AR90006 原件与新写的 car-key-sharing 四份）成文/摆放前都先交维护者评审，过了才进 Case**。AR90006 原件若检出个别语句，修订措辞、不改业务事实。
