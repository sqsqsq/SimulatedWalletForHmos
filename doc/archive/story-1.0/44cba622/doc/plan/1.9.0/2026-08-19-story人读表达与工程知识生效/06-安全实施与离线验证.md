# 步骤 6：安全实施与离线验证

> 前置：步骤 1–5 的目标合同均已确认  
> 本步交付：按最早责任层分批实施，并用真实调用形态证明新旧能力共同成立。

## 1. 实施边界

本轮允许修改：

- `doc/extensions/skills/story/` 中的章节合同、规则、装配与 Review 渲染；
- `doc/extensions/hooks/`、`manifest.yaml` 和相关 phase overlay；
- `doc/extensions/ADAPTATION.md` 与适配自检引用；
- `test/story/` 中对应的离线合同、运行目录实现和评测说明。

本轮保持：

- `framework/**` 当前内容逐字节不变，包括工作树中已经存在的 framework diff；
- 实施完成前不主动修改产品源码、资源和依赖声明；正式 Coding 实跑产生的修改只存在于受控源码事务中，取证后恢复到实跑前字节状态；
- Story/Review 语义达标判据及 rubric 不变；
- 用户和其他会话的无关工作树改动不变。

## 2. 分批实施顺序

### 2.1 建立保护基线

记录目标文件清单、当前 `framework/**` diff/哈希和离线回归结果。确认本轮文件所有权后再编辑。完成条件是能够在实施后证明 framework 和无关工作树没有被覆盖。

### 2.2 原子规范化 hook 路径

一次完成文件移动、manifest、相对引用、适配指南引用和生命周期测试更新。该批只改变路径，不改变 Spec、Story 或阶段语义。立即运行 manifest、hook-runner、extensions 和 Spec 既有合同测试。

### 2.3 实施 Story 人读结构

更新章节合同 v4、写作规则、scaffold 和标题层级检查。先验证旧章节 ID 兼容、新系统章创建、H3/H4 正反例和资产守恒，再进入决策渲染。

### 2.4 实施 Story/Review 决策合同

保持 decisions v2，移除 Story 汇总，实施唯一独立占位、稳定锚点、Review 回链和人工区守恒。该批完成后运行 Story build/merge/post-check 的正例与反例，并逐字审阅生成样例。

### 2.5 实施 Plan 选择与冻结

新增 `hooks/plan/on_context_load.md`、`hooks/plan/post_check.mjs`，扩展 contracts schema 的实例字段，并对齐 plan overlay。覆盖采用、拒绝、Plan 补充候选、部分规约命中、纯结构模式和完全零命中。

### 2.6 实施全链下游消费

更新共享模式/规约 hook 和 Coding、Review、UT、Testing overlay；UT/Testing 新增模式行为检查。用临时 feature 产物验证每个阶段能够读取 Plan 交接、产生本阶段原生证据，并让失败的 MAJOR check 传导为 verifier 失败。

### 2.7 更新目标仓适配

只更新 ADAPTATION 中的路径、Plan 交接和四个下游阶段验证说明。设计模式正文保留叙述骨架；本仓没有的内网事实继续保持“未确认”，不以 demo 推断。

### 2.8 改造正式运行目录

运行基础设施与被测能力分批修改、分批回归，不同时改评价判据。正式 run 使用不可变 run-id 目录：

```text
output/story/
├── runs/<case-id>/<run-id>/
│   ├── state.json
│   ├── live.jsonl
│   ├── events.jsonl
│   ├── runlog.md
│   ├── report_data.json
│   ├── artifact/
│   └── cli-runtime/
└── <case-id>/
    ├── active.json
    └── latest.json
```

- `start` 创建新 run，不递归删除旧 CLI/XDG snapshot；
- `active.json` 指向活动 run，`latest.json` 只在终态原子更新；
- `poll/status/reply/stop` 的命令接口保持不变，由稳定指针解析 run；
- 历史 run 是审计证据，不作为被测模型输入或质量基线；
- 被测模型读取 `test/story/` 或任何历史 run 时，本轮标记为污染、不能作为独立能力证明；
- 保留已有 heartbeat、lease、phase-result 不可变发布和 stop 幂等行为。

这一步解决 Windows 只读 snapshot 回收失败，同时保留正在运行会话的可发现性和审计证据。

### 2.9 建立 Coding 源码事务

凡阶段区间包含 Coding，runner 必须在启动被测 CLI 前对显式 `SOURCE_DIRS` 建立可恢复事务：

1. 记录事务前的 tracked/untracked 文件清单、字节内容和状态指纹；
2. 只在 `SOURCE_DIRS` 内建立干净 Git 基线，任何其它目录都不进入复位集合；
3. Coding 与 Review 共享同一轮源码状态，使 Review 审查的就是本轮 Coding diff；
4. 终态前把源码 patch、变更清单、编译/lint 日志和阶段产物复制到不可变 run 目录；
5. 无论正常、失败或 stop，都在 `finally` 中恢复事务前字节状态，并只删除本轮创建的源码文件；
6. 恢复失败时发布 `source_restore_failed` 终态，保留恢复材料和人工恢复说明，不能把该轮标为有效通过。

该事务保护用户现有修改，不代表在沙箱或隔离工作树中运行；被测 CLI 仍直接作用于当前真实工作区。

## 3. 离线合同覆盖

### 3.1 Story / Review

- 八章正文、三个附录及现有章节 ID 兼容；
- H2→H3→H4 合法，H4 无父级和标题跳级失败；
- 表、列表、图、图片、引用和代码标识可以共同装配；
- 每个决策占位唯一且独占一段；重复、内联、断链失败；
- Review 回链可解析，人工区和计划外意见逐字保留；
- decisions v2 的开放、已定和空集合均合法；
- Story 不含待确认汇总和会议议程措辞。

### 3.2 生命周期与 Spec

- manifest phase/event/path 可解析；
- Spec core 指针仍能读取 `hooks/spec/on_context_load.md`；
- Story 条件 MJS 按真实 hook-runner 形态执行；
- 普通 Spec 不注入 Story 指令，Story flow 正确注入；
- §9/§10、Spec post-check 与现有 overlay 无回归；
- shared pre-verifier 动态覆盖合并后的 check ID。

### 3.3 Plan 与下游

| 阶段 | 正例 | 反例 |
|---|---|---|
| Plan | 候选处置、模式/规约真实投影、部分/零命中 | 漏候选、非法 ID、表与 contracts 漂移、空锚点、只有登记无设计 |
| Coding | 模式结构和规约义务进入 diff | 登记实例不存在、绕开模式、实现锚点落空 |
| Review | 逐实例/义务形成 diff 审查 | 漏审、无证据、静默重选 |
| UT | 模式行为和规约场景进入动作与断言 | 只在用例名写词、断言内部类结构、虚构纯结构模式用例 |
| Testing | device 层行为有操作、观察与证据 | 无证据宣称通过、阻塞写成通过、验证未分配到 device 的内部细节 |

所有用例在临时目录中自建产物，不写真实 feature 路径，不把测试域判据注入被测 prompt。

## 4. 回归顺序

每批先跑其最小正反例，再运行：

1. Story 域全量测试；
2. CLI runtime 合同测试；
3. extensions harness；
4. framework integrity；
5. 与本轮修改相关的 Spec/Plan 生命周期测试；
6. 逐项复核 `git diff`、framework 快照和无关工作树。

离线全绿只证明结构、调用形态和失败传导具备实跑条件，不代表 Story 人读质量或工程知识语义已经达标。

## 5. 失败处置

- 路径迁移失败：停在 2.2，恢复到一套可解析路径后重验，不带着双路径进入后续批次；
- Story 结构或决策测试失败：只修 Story 最早责任层，不同时调整 rubric 或 runner；
- Plan/下游消费失败：先判断是机器交接、共享 hook、阶段 overlay 还是样例产物问题，只改最早责任层；
- runner 基础设施失败：不改被测 Skill、knowledge 或评价判据；
- framework 内容变化：本轮实施无效，恢复 framework 到实施前记录的字节状态后才能继续。

## 6. 离线完成条件

- 所有新增正例、反例、部分命中和零命中用例通过；
- Spec 已有能力和 Story 既有守恒能力无回归；
- Coding、Review、UT、Testing 的模式与规约 check 均能被 verifier 看到并正确传导失败；
- run-id 目录不删除旧 runtime，活动/终态指针和现有 CLI 接口成立；
- Coding 源码事务能在成功、失败和 stop 路径保存 diff 后恢复实跑前状态；
- framework 与无关工作树相对实施前完全不变；
- 当前运行期版本指纹冻结，可以进入正式 Story→Spec→Plan→Coding→Review 实跑。
