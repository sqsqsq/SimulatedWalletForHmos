## 2. 独立评审结论

### P0-1：模式“原件字节一致”与新增 roles frontmatter 不可能同时成立

当前方案同时要求：

- 两个模式与归档原件逐字节一致；
- 模式 frontmatter 承载 `roles`、`optional_roles`、`coordinator_role`，供 Plan 角色投影校验派生；
- C0-3 以整文件 SHA 验证原件一致。

归档原件的 frontmatter 只有 `name`、`applies_when`、`not_applies_when`、`triggers_usecase_spec`，没有上述角色字段。添加角色元数据后整文件 SHA 必然改变，因此 C0-3 与 C3-6 必有一个失败。

**处置建议**：

1. frontmatter 与正文分开读取；
2. 只对原件正文做字节级 SHA 比对；
3. frontmatter 使用明确允许字段白名单；
4. 单独校验 `roles`、`optional_roles`、`coordinator_role` 的结构；
5. 冻结需求 C8 点名的名称、适用与不适用条件、方案结构、契约投影和验证要求仍须保持。

这样既能守住原件正文，又能支持角色派生，不需要建立平行 contracts 命名空间。

### P0-2：回退会删除完整适配能力，但当前方案没有重建需求 4

冻结需求 4 的 C1-C16 包含：四宿主入口、Framework 前置检查、首次适配、版本升级、同版本重新适配、1.0 基线识别、managed/adapted 归属、确认前零写入、失败恢复和独立交付包。

这些能力是在 `19977c98` 之后由 `b6ed75c4` 新增的。回退到 `19977c98` 会删除：

- 四宿主入口的 `adapt` 路由；
- `skills/story-adaptation/SKILL.md`；
- `verify-adaptation.mjs`；
- `build-release.mjs`；
- `releases/1.0.json`、`releases/2.0.json` 及其版本归属语义。

当前方案只在能力守恒表中用一行声明“重建”，但 L1-L7 没有适配目标契约，实施顺序也只在最后重定 `releases/2.0.json`。因此方案可能全部通过自身判据，同时丢失 `/story adapt` 的实质能力。

**处置建议**：新增完整的 L8 适配与发布层，以及对应 C4 系列验收，至少覆盖：

- 四宿主入口与 Extension 共用版本；
- 不可变 `releases/1.0.json`；
- 2.0 managed/adapted 文件及 Manifest 字段归属；
- 首装、1.0→2.0、同版本无变化、同版本有变化；
- Framework 缺失时零写入；
- 中途写入失败后恢复写前指纹；
- Extension 单独交付时不依赖来源仓 Git 或绝对路径。

### P1-1：`ownTerms + isEcho` 仍会被形式满足，并允许产物自证

当前 `ownTerms` 把 plan contracts 的 data model、field、interface、method、component、resource key 名称也作为专名来源；被检查的 Plan 可以自行创造一个实体名，再把该名字插入规约改写文本，从而满足“含专名”。字符级相似度也可以通过同义改写绕过。

这会产生下一种已知模式：

```text
规约原文复述 + 一个自行创造的专名 + 同义改写 = 机械 PASS
```

此外，派生不到专名时判据降级为 WARN，与 L1/L3 声明的 BLOCKER 语义不一致。阈值校准、调试和有效性证明又都使用 AR90004/AR90006，同一批样本只能证明抓住已知问题，不能证明对新需求有效。

**处置建议**：

1. `isEcho` 只作为风险提示或 verifier 的审查线索，不作为“知识已应用”的最终 BLOCKER。
2. 区分可信上游专名与当前产物新引入专名，禁止同一字段为自己提供通过证据。
3. 新引入实体必须同时具备现有 contracts 实体、业务步骤和独立设计落点，不能只靠名字存在。
4. 语义 verifier 必须判断结论是否改变了本需求的结构、行为、失败处置或验证方式。
5. 增加未参与阈值调试的 holdout Case 与对抗夹具：
   - 规约复述中随便插入一个专名；
   - 同义改写规约以绕过相似度；
   - 真设计使用自然语言但没有代码标识；
   - 合法设计同时触发其它可读性 WARN。

### P1-2：实跑终点停在 Plan，不能证明下游四阶段

方案要求 Coding、Review、UT、Testing 按冻结账本逐条留证，C3-10 又标记为“离线构造 + 实跑”。但本轮两个 Case 的终点均为 Plan，当前全部 Case 定义也没有可靠覆盖 Plan 之后的完整终点。

- `story-suite-20260824-130828` 两案均止于 Spec；
- Coding、Review、UT、Testing 目前只有构造夹具证据，没有模型真实行为证据。

**处置建议**：

- AR90004 至少跑到 Review，验证模式结构、代码落地和 Review 逐义务裁决；
- AR90006 跑到 Plan，继续承担复杂规约和内容质量校准；

### P1-3：回退门禁没有覆盖声明的回退范围

方案声明回退 `doc/extensions` 和四宿主 Story 跳板，但 C0-1 只检查：

这不能发现：

四个入口必须显式列为：

**处置建议**：tracked diff、untracked 清单、目标文件树和四入口内容全部纳入回退验收；能力守恒增加 1.0 命令兼容用例，不能只看 `git diff --stat`。

### P1-4：测试报告仍混淆“到达、产出、门禁、闭环”

历史原始 `state.json` 已证明这些状态不能合并成一个“到达阶段”：

- 有 Plan 产物不代表 Plan harness 或 closure 通过；
- `highest_phase_reached` 可能只是 runner hint；
- phase-results 可能仍显示该阶段 `not_reached`；
- verifier 缺失时不能把阶段表述为已完成。

当前报告模板仍只记录“到达阶段 / 中止原因”，可能再次形成过强结论。

**处置建议**：每个阶段分别记录：

```text

execution_status
harness_verdict
verifier_verdict
receipt_status
closure_status
target_reached
```

只有正式 closure 完成，才允许表述为阶段完成。

## 3. 建议的目标实现

### 3.1 总原则

真正可收敛的实现应把三种责任分开：

1. **机械门禁**只证明结构、引用、实体和证据真实存在；
2. **独立 verifier** 判断内容是否真的解决本需求，而不是复述规约；
3. **历史回归 + 新 Case** 分别证明旧问题不回来和机制没有过拟合。

不要让一个字符相似度或专名代理同时承担三种责任。

### 3.2 内容不丢：机械保护 + 独立全量语义审查

机械层只保护可以可靠提取的事实：

- 接口、存储键、配置项、事件、错误码；
- 带量纲数字；
- 图片和链接；
- 表格首列业务键；
- 决策占位符及其单源值；
- 编号含义的派生来源。

其余业务事实由独立 verifier 全量核对。verifier 报告对每个正式来源章节记录：

```text
来源文件 + 行号
事实摘要
Story 落点 + 行号
完整 / 弱化 / 丢失 / 合理归属其它需求
重复位置及是否提供章节独有信息
```

`post_verifier` 机械确认所有正式来源章节都有裁决、三个维度都有结论、FAIL 有证据位置，禁止 0 项裁决却总体 PASS。

现有 `content-audit.md` 可以保留为审查证据，但不再由 Story 作者自己批量填写“完整写入”；应由独立审查过程生成或复核。

### 3.3 内容不重：确定性单源优先，语义重复交给 verifier

以下内容应由装配器确定性渲染，只登记一次：

- 决策值；
- 编号含义；
- 附录“要求”列；
- 图片规范路径；
- review 编号对照。

机械层可硬拦：同一占位值重复、同一图片重复、完全相同长句跨章重复、附录同行要求/结论高度复制。

“同一事实在不同章节是否有独有信息”属于语义判断，由 verifier 按章节责任裁决，不再继续堆形态正则。

### 3.4 知识应用：冻结结论必须落到现有契约实体

建议把规约义务写成可校验的现有 contracts 扩展字段，例如：

```yaml
constraint_obligations:
  - rule: DM-01
    decision: 签约入口生成 flowId，并随创建签约调用传入步骤上下文
    business_step: 创建签约
    landing:
      - data_models.AutoTopupContext.flowId
      - interfaces.AutoTopupGateway.createContract
    verification:
      review: 核对 flowId 只生成一次并贯穿调用
      ut: 两步调用使用相同 flowId
```

机械门禁证明：

- landing 指向的类、字段、接口和方法真实存在；
- anchor 不指回“知识决策”声明表；
- business_step 能在方案或 use-cases 中找到；
- Review/UT/Testing 账本能从冻结结果确定性派生。

verifier 判断：

- decision 是否真的把规约用于本需求；
- decision、landing 与验证义务是否一致；
- 是否只是复制或同义改写规约原文。

模式应用沿用同一原则：`instance + roles → contracts 实体`，coordinator 与 use-cases 一致，未选择的候选给不选理由。

### 3.5 下游传递：从冻结结果派生账本，不回读 Knowledge

Coding、Review、UT、Testing 只读取 Plan 冻结结果。每条义务和模式角色在各阶段必须出现以下二选一：

- 真实证据：文件、diff、用例或设备结果；
- 显式状态：`不适用 / 待验证 + 理由`。

缺席直接失败。下游发现设计无法落实时返回 Plan 更新冻结结果，不自行重解释 Knowledge。

### 3.6 失效形态回归：每条都有坏夹具和好夹具

建议 `failure-modes.yaml` 每项至少包含：

```yaml
id:
dimension:
clause:
bad_fixture:
good_fixture:
checker:
applicable_when:
severity:
variant_of:
status:
```

执行规则：

- 历史坏产物必须失败；
- 对应修正产物必须通过；
- `fixed` 仍永久运行；
- `retired` 必须给理由并经人工批准；
- 新变体保留旧检查，同时新增变体检查；
- AR90004/AR90006 只作历史回归，不同时承担调参与最终证明；
- 最终有效性由 holdout Case 和对抗样本证明。

### 3.7 适配能力：AI 负责内容，事务脚本负责安全写入

适配不应只靠 Skill 文字承诺原子性。建议保留小型事务执行脚本：

```text
plan → shadow tree → diff → user confirmation → apply → verify → rollback
```

AI 负责扫描目标工程、核实知识、生成适配内容和解释方案；脚本只负责路径边界、影子树、指纹、写入、验证和失败恢复。

发布清单必须把 Extension 与四宿主入口视为同一发布单元，而不是只统计 `doc/extensions`。

3. 未参与调参的新 Case 没有出现同族换皮；
4. verifier 对内容去重且不丢、人读友好、知识正确应用三个维度给出带行号的完整裁决；
5. Plan 的每个模式角色和规约义务都落到真实契约实体；
6. 冻结结果真实传递到 Coding、Review、UT、Testing；
7. 未执行阶段明确标记为“行为未验证”，不以离线夹具代替；

10. 全部验证通过后再固定 2.0 发布指纹。

本轮 Story 质量提升。首轮评审指出 L8 缺失，是对回退边界的必要纠错；第二轮不再延伸审查适配机制优化。

SHA 同样不是 Story 质量判据。它只能证明基线未漂移、文件来源一致或装配可复现，不能证明 Story 内容
完整、去重、好读或知识被实际应用。若被锁定对象本身有问题，SHA 只会稳定保存问题。因此 SHA 只应归入
基线完整性门禁，不得计入 Story 质量结论。

### 7.3 阻断问题

#### P0-1：冻结要求“每项有效事实”，方案却只保证“每个来源章节至少一行”

冻结 `01-Story内容守恒与去重.md` C1/C4 要求：原始材料中的全部有效事实逐项反查，每项事实都有独立、
可审查的核对记录。重写版 `01` L1-8 虽称“来源单元级”，但 L3-6 和 `02` C1-8 的实际通过条件只是
“每个正式来源章节有裁决表行”。一个章节包含十项事实时，模型写一行章节摘要即可形式通过，仍然能够
静默漏掉其中九项事实。这正是本轮要消除的“结构存在 ≠ 内容完整”失效形态。

必须改为：

1. 机械枚举全部来源单元，至少覆盖段落、列表项、表格行、图片和链接，并生成稳定 `source_unit_id`；
2. 作者 audit 对每个 `source_unit_id` 拆解事实并记录完整主叙述、独有信息、重复合并与最终处置；
3. verifier 逐 `source_unit_id` 复核事实拆分和处置，而不是每章给一个总判断；
4. post_verifier 校验来源 ID 集合、audit ID 集合和 verifier ID 集合完全一致，缺失、重复或未知 ID 均失败；
5. “哪些事实有效”仍由 verifier 语义判断，机械层只保证没有来源单元被跳过。

#### P0-2：用数量阈值强制标题与段落，重新引入被冻结需求禁止的形式配额

`01` L5-2 规定“一章 ≥3 并列主题或连续散文 ≥约 12 行须切一级小节”，并明确称“判据不是建议”；
`02` C2-2 又把真长段数量不得高于 AR90006/AR90004 的历史数字写成通过条件。这与冻结
`02-Story面向人类叙述.md` C2 直接冲突：三级、四级标题按真实业务从属关系自然生成，不为形式对称强制
出现；Markdown 形态不得设置类型或数量配额，合理性由语义评价判断。

即使 C2-1/C2-2 标成 WARN，L5-2 进入写作指令后的“必须”仍会驱动模型按数字切文。正确做法是保留
主题数、散文行数、长段数作为定位审查对象的诊断信息，但不得形成写作命令或 PASS 条件；verifier 根据
主题从属关系、阅读连续性、章节职责和必要承接判断是否需要切分。

### 7.4 关键缺口

#### P1-1：两个所谓 holdout 都是已知历史 Case，不能证明泛化

`source-conflict-review` 与 `split-two-ar` 已在 2026-08-14、08-20、08-21 多轮方案、实跑与事故分析中
反复出现，历史文档还记录了它们的具体失效形态和产物问题。`02` §2.1 甚至允许使用“既有产物”。它们只能
承担历史回归与调参，不能作为未见样本证明机制没有过拟合。

真正的 holdout 必须在脚本、阈值、提示词和回归夹具全部冻结后，由用户或独立评审者提供此前未参与设计的
新材料。首次揭盲失败即本轮泛化失败；若据此修改实现，下一轮必须更换新的 holdout，不能在同一 Case 上
反复调到通过。

#### P1-2：E1/E2 的 BLOCKER 定义仍不完整，且校准合并计数会掩盖分支失效

`01` L4-2 把阈值和算法参数留给未来 `echo-thresholds.json`，但没有确定相似度算法、归一化方式、比较
字段、窗口和具体阈值。“高相似复制”“逐字搬运级相似”不是可以直接实现且跨实现一致的契约。合法写法
“引用要求 + 紧跟真实设计”仍可能被误判为复制。

`02` §2 又用“E1/E2/E3 合并报 ≥8”校准；即使 E1/E2 完全失效，只靠 E3 WARN 达到八条也能满足表格。
应把 E1、E2、E3、E4 的预期命中行分别冻结，逐分支校准。BLOCKER 只保留规范化后完全相同、且结论字段
没有新增设计内容的确定性纯复制；其余相似情况降为 WARN，由 verifier 裁决。必须增加“要求列合法引用原文，
结论列含真实命名设计”的不误伤夹具。

#### P1-3：Coding 在冻结结构和验收对象中再次消失

冻结 `03-Knowledge跨阶段应用.md` C5 要求 Coding、Review、UT、Testing 四阶段分别按真实代码、diff、
用例、步骤与结果留证。重写版 `01` L3-4 的 `verification` 只有 `review/ut/testing`，`02` C3-10 的观测
对象也只有 `review / ut / testing` 报告。L3-5 文案虽然提到 Coding，结构与判据却无法验证它。

`verification` 必须固定包含 `coding/review/ut/testing` 四个阶段；下游账本对同一 obligation/role 键逐阶段
记录证据或“不适用/待验证 + 理由”。本轮未实际到达的阶段可以标“行为未验证”，但不能从契约结构中省略。

#### P1-4：正文 SHA + frontmatter 白名单仍允许原件字段值被篡改

`02` C0-3 只要求正文 SHA 一致、frontmatter 字段属于白名单、原件字段一个不丢。这能防字段缺失和越界，
却不能防 `name`、`applies_when`、`not_applies_when`、`triggers_usecase_spec` 的值被修改。模式仍可能在机械
PASS 下改变适用语义。

应校验原始四字段的键和值与归档原件一致；新增的 `roles/optional_roles/coordinator_role` 只做独立 schema
和交叉引用校验。该结果只写“模式基线完整”，不得写“Story 质量通过”。

#### P1-5：“模块名 BLOCKER”的作用域不清，可能主动删除合法需求事实

冻结需求允许附录承载接口、数据、配置、事件和工程范围。`01` L1-7 / `02` C2-3 却笼统规定 Story 正文
不得出现模块名，并设为 BLOCKER；同时没有像 C2-4 那样明确“附录外”。如果实现按整份 Story 扫描，来源
材料中合法的工程范围和契约承载信息会被迫删除，与内容守恒冲突。

必须明确检查范围只覆盖面向人类的主叙事章节，并排除附录中有来源依据的工程范围、接口与契约实体；模块名
是否属于不应进入主叙事的实现细节仍需 verifier 结合来源与章节职责裁决，不能仅凭 Catalog 命中一律删除。

#### P1-6：没有从分项结果到最终 PASS/FAIL 的唯一汇总规则

当前已有 BLOCKER、WARN、语义 FAIL、观察项、行为未验证、阶段 closure 等状态，但没有规定它们怎样汇总成
本轮结论。报告者仍可选择性解释 WARN 或未到达阶段，复现“分项事实正确、总评表述过头”的问题。

必须固定：任一机械 BLOCKER 或 verifier 语义 FAIL → 本轮失败；E3/E4 等 WARN 未逐条获得 verifier 裁决
→ 闭环失败；行为未到达的阶段不得宣称其冻结需求已验证；新 holdout 未通过不得宣称泛化通过；只有目标范围
内所有必需项完成，才能给出总 PASS。adapt 只报告守恒回归结果，不计入 Story 质量提升分数。

### 7.5 第二轮建议的最小修订顺序

1. 先把 C1-8 改成来源单元 ID 全集合闭环，补 audit/verifier/post_verifier 三方集合一致性；
2. 删除 L5-2 的强制数字触发和 C2-2 的历史数量通过线，把计数降为诊断；
3. 固定 E1–E4 的算法、范围和逐分支夹具，BLOCKER 只保留可证明的纯复制；
4. 把现有两个 Case 降回历史回归，建立冻结后揭盲的新 holdout；
5. 补齐 Coding/Review/UT/Testing 四阶段冻结结构与账本；
6. 修正 frontmatter 原始值守恒和模块名检查作用域；
7. 最后补唯一总判定规则，再把方案状态恢复为“待批准”。

### 7.6 第二轮批准条件

只有上述 2 个 P0 和 6 个 P1 全部在 `01/02` 中形成可直接实施、无待定算法和无自证漏洞的契约，才建议
批准实施。当前 `01` 的“设计定稿”和 `02` 的“判据定稿”均早于实际闭环，应维持“待修订/待复审”。

### 8.2 阻断问题

#### P0-1：DTS90006 的运行时序与“冻结后揭盲”定义自相矛盾

第三稿 `01` 第 15 行声明 DTS90006 已“进行中”，同文件 §1 又定义 holdout 必须在脚本、阈值、提示词和
回归夹具**全部冻结后**揭盲，并指定 DTS90006 为首个揭盲样本。当前方案仍是“第三稿 · 待复审”，实施步骤
尚未开始，目标脚本、阈值与提示词不可能已经冻结；当前正在运行的 DTS90006 也不可能验证尚未实现的目标态。

即使 DTS90006 尚未用于调参，它最多是**实施前诊断/旧实现基线**，不能同时充当目标实现的泛化证明。
若实施后重跑同一材料，其输入与首次结果又已在实现前暴露，同样不再是未见样本。

必须改为：

1. 将 DTS90006 明确登记为实施前诊断或历史基线，不计入 holdout；
2. 完成实现、回归调参和对抗夹具后，生成冻结清单并记录脚本/阈值/提示词/夹具指纹；
3. 冻结后由用户或独立评审者提供一个此前未向实现者暴露的新 Case；
4. 先登记 holdout 输入指纹，再运行一次；失败即本轮泛化失败；
5. 任何基于该结果的修订都会开启下一轮，并必须更换新的 holdout。

#### P0-2：E4 阈值仍然改变哪些内容必须接受语义裁决，并非“只影响排序”

第三稿 `01` L4-2 声称 E4 的 SequenceMatcher 阈值“只改变提示排序，不改变判定语义”；但 L4-3 与
`02` C3-2/C3-12 只要求 **E3/E4 命中行**进入 verifier 必答并逐行闭环。阈值改变时，E4 命中集合会变化，
哪些行必须接受语义裁决也随之变化，因此阈值实际改变闭环覆盖面。

存在明确逃逸路径：一行规约复述加入可信或半可信专名后不会命中 E3；再通过改写把字符相似度降到 E4
阈值以下，就不会进入 flagged 清单，也无需获得“设计/复述”裁决。该行可以在 E1/E2/E3/E4 全部未命中的
情况下机械通过，第二轮要解决的“复述 + 专名 + 改写”失效形态仍未根除。

必须改为：

1. Story 附录所有判“是”行、Spec 所有应用域约束行、Plan 所有 obligation decision **无条件进入 verifier**；
2. verifier 对上述全集逐行给出“设计/复述 + 证据”，post_verifier 校验输出 ID 集合与输入全集一致；
3. E3/E4 只增加风险标签和审查排序，不决定某行是否接受语义裁决；
4. 这样 E4 阈值才真正只影响阅读顺序，不影响 PASS/FAIL 或语义覆盖；
5. 对抗夹具补“可信专名 + 低字符相似度同义复述”，必须被全集语义裁决判为复述。

### 8.3 定义缺口

#### P1-1：E2 的字段对象与规范化规则仍不足以支持唯一实现

第三稿 L4-2 写“结论/要求文本”与规约原文比较，但 Story 附录同时存在由 `{{ID}}` 确定性渲染的“要求”列，
Spec 又存在“本需求的要求”字段。若实现者把附录原始“要求”列纳入 E2，它天然与规约原文相同，所有合法行
都会被 BLOCKER。当前文字依赖读者自行猜测“要求”到底指哪个字段，和“算法在此定死，无待定项”的声明不符。

“去标点”也不是唯一算法。删除 `-`、`/`、`.`、`_`、`:`、比较符等字符会让不同契约名、编号、路径或条件
折叠为相同字符串，制造误报。

应明确：

1. E1 只比较 Story 附录的 `conclusion_or_landing` 与同行渲染后的 `requirement`；
2. E2 分两个固定入口：Story 只比较 `conclusion_or_landing`，Spec 只比较 `requirement_for_this_feature`；
3. E2 永不比较 Story 附录作为来源引用的原始 `requirement` 列；
4. 子串方向固定为：非空的规范化输出 `normalized_output` 等于或被包含于单个规范化来源字段
   `normalized_source`，反向“来源被包含于带新增设计的输出”不算纯复制；
5. 规范化采用明确步骤，例如 Unicode NFKC、移除 Markdown 展示包装、折叠空白；保留标识符和运算语义所需
   的 `- / . _ : # @ < > =` 等字符，不使用笼统“去标点”；
6. 空字段由结构完整性门禁处理，不借助“空串是任意字符串子串”的语言行为进入 E1/E2。

### 8.4 第三轮最小修订

1. 将 DTS90006 从 holdout 改为实施前诊断，并把真正 holdout 延后到目标实现和判据冻结之后；
2. 把语义 verifier 输入从 E3/E4 flagged 子集扩大为全部适用行/义务，风险判据只负责标记和排序；
3. 固定 E1/E2 的具体字段、子串方向、非空前置与规范化字符规则；
4. 同步修改 `01` L4-2/L4-3/L4-6/§7、`02` C3-2/C3-4/C3-8/C3-12/§2.1 与总判定规则；
5. 增加两条永久回归夹具：实施前运行样本不得冒充 holdout；可信专名 + 低相似度复述不得逃过语义裁决。

只有满足以下条件才建议批准实施：
