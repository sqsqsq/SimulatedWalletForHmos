## 0. 一句话

扩展把「让模型做对」押在两件事上：**写更多指令**（送错了对象）、**写更多门禁**（事后倒逼）。作者在写之前看不到要求，只能靠失败学习；审查者拿到的是作者指南加回声表；下游拿到的是没人读的平行账本。

## 1. framework → extension 的执行保证图谱

### 1.1 一次 `harness-runner.ts --phase X --feature F` 的真实链

```
mergeAndWritePhaseState(running)              harness-runner.ts:645
emitLifecycle('pre_phase') / ('pre_check')    :719-720
runScriptHarness → check-<phase>.ts           :749
emitLifecycle('post_check')   ← 扩展 post_check.mjs   :752
emitLifecycle('on_violation') ×N              :757-763
emitLifecycle('pre_verifier')      ┐
emitLifecycle('on_context_load')   │ 四个连排，同进程同秒   :765-768
emitLifecycle('post_verifier')     │
emitLifecycle('post_phase')        ┘
assembleAIPrompt(..., lifecycleFragments) → ai-prompt.md   :806-818
tryValidateReceipt → finalizePhaseClosure     :860-903
```

**决定性事实**：8 个 hook 事件（`framework/specs/lifecycle-hooks-schema.yaml:15-31`）全部在 harness 同一进程、verifier 子 agent 被调起之前跑完；所有 `promptFragments` 汇入 `lifecycleFragments`（`:676`），**唯一去处**是 `ai-prompt.md` 尾部（`framework/harness/scripts/utils/report-generator.ts:311-318`）。`on_context_load` 在 `post_check` **之后**触发（`:750` vs `:766`）——它不是「阶段上下文加载」，是「verifier 提示词拼装」。

### 1.3 主 agent 与 verifier 互相看不见

- 主 agent 上下文 = `framework/skills/feature/<phase>/SKILL.md` + reference + profile addendum + 用户输入 + 它自己去读的文件。
- verifier 上下文 = `prompts/verify-<phase>.md` 模板 + `{spec_content}`（含扩展 overlay）+ `{script_report}` + `{context_files}`（产物全文）+ 全部 hook 片段。
- 两侧零交集：主 agent 看不到 overlay 判据，verifier 看不到 SKILL 作业指令。
- 更进一步：`.claude/agents/verifier.md:11,27` 让 verifier 读 **raw 模板**，`spec/SKILL.md:64` 让主 agent 传的也是 raw 模板路径；**全仓没有任何指令要求任一方读 `ai-prompt.md`**。扩展为此自建了事后回补：`spec/post_check.mjs:869-872` 在下一次 harness 时核对 verifier 报告文件里有没有裁决表。

### 1.4 扩展能影响主 agent 的全部手段（穷举）

1. `/story` 的 SKILL 文本（用户敲命令进入；覆盖 init→spec 入口）——模型自觉；
2. post_check 的 BLOCKER 报错文案（`severityOverride` + `message`）——机械触发、**事后**；
3. 产物本身（spec.md / contracts.yaml 被下游必读）——事前，但要作者先写对；
4. 脚本当门禁（`story-build check` 等）——得模型自己敲。

**没有一条是「作者写之前、机械送达」的**。`provides.skill_assets` 理论上是，但主 agent 侧的解析协议（`framework/skills/README.md:40-66`）不认它。

### 1.5 这解释了内网结果

| 阶段 | 作者怎么知道扩展要什么 | 结果 |
|---|---|---|
| spec | `/story` 链有一句指路（`skills/story/SKILL.md:299`）+ 937 行 `spec/post_check.mjs` 倒逼（三方 ID 集合、复述判定、逐行裁决核对） | 生效 |
| plan | 无指路；只能从 harness 报错反推 `knowledge_freeze` schema | 填表交差——**仅展示** |
| coding | 无指路；`framework/skills/feature/coding/SKILL.md:38-53` 枚举 contracts 7 个集合，不含 `knowledge_freeze`；`hooks/coding/post_check.mjs:25-38` 只查 `\b名\b` 存在性 | **完全失效** |

「缺少 mjs 探针」是表象：探针再多也是事后；根因是**没有作者面通道**。

### 2.3 回环里发生了什么

- `lifecycle_hook_post_check_extension` **同一 check id 洋葱式 FAIL 5 次**（17:34 / 18:09 / 18:13 / 18:20 / 18:40），每次暴露下一层：缺产物 → §10 与登记源不同文 → story/评审/核对一致性 → verifier 漏裁 → plan 冻结定位不到；`mapping_to_file` 缠斗 4 轮。
- 读 `framework/**` 60 次、`doc/extensions/**` 40 次，合计是读自身产物（36 次）的 **2.8 倍**；`check-spec.ts` 被读 **9 次**；14 条 bash 在 `grep` checker 源码反推判据（`terminology_high_without_glossary -A 40`、`ui_kit_declaration_required` 三连、`resource_integrity -A 30`）。
- 单次整读：`story_flow.py` 42.6KB、`spec/post_check.mjs` 39.3KB、`SKILL.md` 36.9KB、`spec-rules.yaml` 24.1KB（prompt 里本已有全文）。
- 255 次 bash 里 166 次是 `cat/head/sed` 读文件、102 次 grep——bash 被当成第二套 Read。
- 模型自身文本只占 runlog 的 15%，「反复口头确认」不是成本；**成本是机器侧同一份规则、同一条 FAIL 反复入场**。

### 2.4 与历史的对比

同 Case 到 plan 的耗时：08-22 `553928` 67.8 min → 08-27 `b2v3d` ≈108 min（**+59%**）；换来的是该 Case 九次运行里唯一一次 exit 0。质量换时间，单位产出成本翻倍。

## 3. 提示词：七成是框架全文灌注，spec 阶段扩展占 44%

拼装规则 `report-generator.ts:218-321`：模板 → 三个占位符全局替换（`{spec_content}` = phase-rules 全文、`{script_report}` = harness JSON 全文、`{context_files}` = 产物全文）→ profile overlay → hook 片段。

| 阶段 | 总量 | 产物全文 | harness JSON | phase-rules | 扩展注入 |
|---|---|---|---|---|---|
| spec | 205,804 B | 15.0% | 14.4% | 19.1% | **44.3%**（核对记录表 65,986 B = 32.1%；两份 on_context_load.md 19,267 B） |
| plan | 130,628 B | 46.7% | 16.6% | 13.7% | 10.6% |
| coding | 235,907 B | 41.2% | **37.4%**（JSON 塞了两遍） | 11.5% | 2.7% |
| 合计 | 572,339 B | 33.1% | 24.4% | 14.8% | 19.5% |

缺陷：
- **framework bug**：`verify-coding.md` 里 `{script_report}` 出现 2 次（`:24` 行内、`:57` 代码块），`report-generator.ts:257` 用 `/g` 全局替换 → harness JSON 内联两遍，43.3KB / 18.4% 纯浪费。
- `spec.md`（27.4KB）在三阶段各注入一遍、`plan.md`（25.2KB）两遍、`ui-spec.yaml` 三遍 → 跨阶段重复 ≈95KB（16.6%）。
- 扩展：`on_context_load.md` 是给作者的写作规约，30.7KB 原样灌进 verifier；批次 2 新增的 272 行核对记录表使 spec prompt 从 131KB 跳到 206KB（+56.6%）。

## 5. story：去重为什么变成丢失

| 版本 | 守恒放在哪 | 后果 |
|---|---|---|
| 1.0 | 逐章取材 + 逐章守恒（每章把取材节的每行表格/数值/反引号写全） | 同一事实被四个章节合同各指一次 → 强制写四遍（PIT-040/041） |
| 批次 2 第三版 | 删生产线（**方向正确**）；「不丢」交给 `audit.json` 自由文本 `reason` + verifier 逐条裁决 + `audit --verify` | `reason` 只判非空（`story-build.mjs:816`）；verifier 272 行证据只有 14 种字符串、全是回声，表头自述恒真规则（`verifier.report.md:55-57`）；`--verify` 永远 exit 0 却挂 BLOCKER（`:659-681` / `post_check.mjs:445`）→ 161/272 单元「不进」、151 条同一句模板理由、PRD 表格 0 行落点 |

人工对照 221 来源单元：完整 53.8% / 部分 34.8% / 缺失 11.3%。丢失集中在**表格非首列**（9 个页面状态的触发条件整列、接口/上下文字段名、`freezeTicketId`、AC-R 编号）与**两张图**（SE 时序图、spec 流程图）；另有 4 处无源事实（「管理台」「DIcon」「加密…按项目知识」「叙事件」）与 3 组跨章完整重复。

写作条件：指令负向 13 条 / 正向 5 条 / 「材料里每件事都要有落点」0 条；`story_on_context_load.md:84` 把合法理由清单交给被判方；story 在 spec 会话末尾、540K 上下文里写成。

**两版共同根因**：守恒的粒度与位置都错——1.0 按「章 × 数量」，批次 2 按「作者自述」；都不是按**事实 token 整篇**；且作者写之前从未看到「要守的清单」。

## 6. 诊断结论（供设计承接）

| # | 结论 | 设计承接 |
|---|---|---|
| C1 | 作者面无机械通道；hooks 是审查者通道 | 01 §D1 |
| C2 | 平行账本 = 展示；契约传导才生效 | 01 §D2 |
| C3 | 探针恒真、不留痕、verifier 回声 | 01 §D3 |
| C4 | 守恒粒度与位置错，作者写前看不到清单；story 在爆炸的上下文里写 | 01 §D4 |

| C6 | framework 六处执行保证缺口（无作者事件、`{script_report}` 双替换、成功不留痕、崩栈降级、overlay 静默、manifest 静默清空） | 01 §D6 / 04 |
