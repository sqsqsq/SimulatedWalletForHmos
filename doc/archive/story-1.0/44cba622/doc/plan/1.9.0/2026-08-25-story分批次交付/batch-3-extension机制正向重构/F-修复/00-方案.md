## 2. 改四处

### D1 · story 回到 spec 阶段（P1）

- spec 阶段三份产物：`spec/spec.md`、`AR/review.md`、`AR/story.md`。`phases/spec.md` §二 写清阶段内顺序：spec.md 与 `AR/story-src/decisions.json` 定稿 → `story-build init` → 主 agent 用 Task 起 writer（`phases/story-write.md`）→ Task 起 verifier（`phases/story-verify.md`）→ `story_flow.py story` 登记（自带 `story-build check`；前置 `complete`，只登记一次）→ 跑 spec harness。主 agent 不读材料、不写 story。
- spec 门禁（`hooks/spec/post_check.mjs`，仅 `isStory`）：`AR/story-flow.json.status ∈ {story_written, archived}`，否则 BLOCKER「spec 三份产物缺叙事件：起 writer / verifier 后 `story_flow.py story` 登记」。判逻辑放 `flow-check.mjs`，与「须 complete 之后」同一函数。**不记 spec sha、不设重核路径**——story 一次性生成，评审回流只改 spec。
- `SKILL.md` 链条回到 S1–S4 → spec（含成文）→ 归档；删「成文（S5）」节，内容并入 `phases/spec.md`；`story_flow.py next_step`：`complete` 态文案「进 /spec，成文在阶段内」，`story_written` 态「spec 可闭环，之后可归档」。
- **删掉**：独立 S5、SKILL 成文节、`next_step` 的「spec 闭环后回 S5」提示、01 §6.1 位置描述（记差异，不回写 01）。

### D2 · 材料按模板约定定义（P2）

- 合同 `sources` 对 SPEC 这份材料声明 `notes: ["blockquote"]`，含义：按 framework spec 模板约定，`>` 块是文件头登记项与各节作业说明，不是事实；枚举时这类单元打 `machine_facing`（origin: template-notes）。PRD / SE / design 不声明。模板约定变了改这一行数据，机制不改。
- 现有 `machine_facing.unit_kinds` / `table_columns` 保留（按用途声明的登记项）。
- **删掉 / 不做**：`---`、正则之类的形状规则；「与模板同文」比对。

### D3 · 审稿者逐对裁决 + 对抗测试常驻（P3 / P4 / P6）

- `phases/story-verify.md` 的任务改为**逐对裁决**：输入 = `audit.json` 里 `by: author` 的每条「单元正文 → 落点章」；每条输出「讲清 + 抄 story 里陈述这件事的那一句」或「未讲清 + 缺什么」。不给整篇印象题；从 overlay 搬来的两条整体维度（可读、取舍）移到 `phases/story-write.md` 作 writer 自检。
- `check ⑥` 不变（引文在该章、≥12 字、非回声）；**不加**相似度或重叠度判据。
- `TEST.md` 新增常驻行为回归（与效率七项并列，G8 只报数）：对每个到达 spec 的 Case，取 story 副本删 5 个事实（含 ≥2 个纯中文单元），用子 agent 重跑 verifier，须 ≥5 条「未讲清」并点名；不达标即判据面无效，回本节。首轮 AR90004 与 ISSUE-410。
- `measure_run.py` 把「模型裁决 M / 机器核实 N」作为诊断项。

### D5 · 成文 = 分配 → 逐章渲染 → 核对；机制不依赖子 agent

**根因**（见 [问题-writer子agent空返回.md](问题-writer子agent空返回.md)）：C 子批带进一个隐含假设——「story 必须由子 agent 在新鲜上下文里一次写成」。它导致 S5 挪出 spec、一次写 37KB、子 agent 返回空、codex 没有 Task 工具不可移植。假设不成立：spec 作者在 spec 阶段已读完全部材料，需要的不是新鲜上下文，而是**每步输出有界、状态在盘上**；批次 2 的上下文爆炸来自门禁回环与反复重写。1.0 按章写从没有这个问题——它的病是合同路由材料（同一事实四章各指一次），不是按章粒度。

**成文流程**

1. **分配**（作者 = spec 作者，材料已在上下文）：为每个来源单元写 `at: 章` 或 `covered_by: 单元键`，落 `audit.json`；`story-build audit` 核：无三态皆空、`covered_by` 有效。每件事恰好一处在写正文之前成立——**不丢**由「无空态」强制，**不重复**由「一单元一记录一 `at`」强制。
2. **逐章渲染**：按合同顺序每章一次：输入 = 分给本章的单元正文 + 上一章结尾 + 该章读者问题 + 四红线；输出 2–4KB **追加**写入 `AR/story.md`。写完跑 `audit`：token / ≥8 字片段在本章命中 → `by: machine`，否则留 `by: author`（交 verifier）。有界、落盘、可续写（缺哪章补哪章）。**有 Task 工具的宿主每章可起一个小子 agent；没有的（codex）主 agent 自己渲染——机制不依赖子 agent。**
3. **核对与登记不变**：`check` 九项、verifier 逐对（只裁 `by: author`）、`story_flow.py story` 登记、spec 门禁。

**与 1.0 的唯一区别**：1.0 由合同按关键词把材料路由给章；这里由作者分配、机器强制恰好一次。

**改动面**：`phases/story-write.md` 重写为两段作业书（分配 / 单章渲染）；`phases/spec.md` §二 与 `SKILL.md` 改为「分配 → 逐章 → 核对」编排并写明 Task 可选；`story-build audit` 逻辑不改，输出加「未渲染章 / 各章待核单元数」两行。

**删掉**：writer 一次写成作业书、「子 agent 必需」、S5。**不改**：合同、三态、check、verifier、登记、门禁。
