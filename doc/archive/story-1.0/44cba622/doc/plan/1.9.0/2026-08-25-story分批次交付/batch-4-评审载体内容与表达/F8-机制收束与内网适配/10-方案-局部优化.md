## A · UX-only 补料导致的流程死锁

### 事实

`doc/extensions/skills/story/scripts/story_flow.py:85`：

```python
SOURCES = ("RR/prd.md", "SR/design.md", "AR/design.md", "AR/upstream.md")
```

`cmd_round` 用这四份的哈希算轮次指纹（`material_fingerprint`）。**一轮 = 一次材料状态**，
指纹不变就不是新一轮，关卡列表不重置。

补料如果**只有界面图**（落 `ux-reference/`），这四份一个都不变 → 指纹不变 → 轮次不推进
→ 关卡列表永不重置 → 流程卡死在 `import_and_reanalyze`。

**实跑实证**：本仓 CLI 一轮里，`auto-topup` 补的是界面原稿（转换后只落 `ux-reference/`），
被测模型撞上死锁，自己改了这个文件绕过去，并在关卡回话里报备了。

**不是上一轮引入的**：`SOURCES` 那行来自 `0c8ab1dd`。之所以现在才炸，是**第一次出现
「只补图片、不补文字」的补料**。

### 根因

`ux-reference/` 是材料清单里的一行、是初析消费的输入，**却不在「什么算材料变了」的
定义里**。这与上一轮修的「声明的来源不存在时要出声」是同一家族：**把 UX 当二等材料**。

### 改法

把材料输入的定义补全：四份文本源 **+ `ux-reference/` 目录下的文件**，逐文件进指纹。

被测模型给的补丁方向正确（`<scratch>/被测模型的改动-story_flow.diff`），但**不直接采纳**，
理由两条：它没有配回归测试；它把常量名叫 `MATERIAL_INPUTS_EXTRA_DIR`，
「extra」这个词把 UX 说成了附加项，而问题的根就是「UX 被当成附加项」。

**正推的改法**：把 `SOURCES` 从「四份文本」改成「材料输入清单」，UX 目录是其中一员，
名字与注释都不留「额外」的意思。

### 验收

| 编号 | 判什么 | 怎么验 | PASS |
|---|---|---|---|
| A-1 | 只补图片也算新一轮 | 夹具：造一轮，只往 `ux-reference/` 加一个文件，跑 `round` | 指纹变化，轮次推进，关卡列表重置 |
| A-2 | 补文字仍照旧 | 夹具：只改 `RR/prd.md` | 行为与改动前逐字相同 |
| A-3 | 目录不存在时不报错 | 夹具：无 `ux-reference/` | 与只有四源时同一指纹口径，不抛异常 |
| A-4 | **死锁不再复现** | 夹具复刻实跑形状：第 1 轮四源齐、第 2 轮只加一张图 | 第 2 轮 `round` 返回新轮次，`import_and_reanalyze` 不卡 |
| A-5 | 名字不留「额外」 | 读常量与注释 | 不出现 `EXTRA` / 「额外」/「附加」——UX 是材料本身 |

## B · 装置只能在临时仓执行

### 事实

`test/story/scripts/run_multi_case.py:2083` 起：

```python
isolated_workspaces: bool = False,
...
if not isolated_workspaces:
    ensure_no_external_active(plans)
```

隔离是**可选的、缺省关**。不传 `--isolated-workspaces` 时被测 CLI 直接跑在主仓
（`workspace: E:\Project\SimulatedWalletForHmos`）。

**实跑实证**：本轮起测漏了这个开关，后果三条——

1. 被测模型**改了被测对象**（`doc/extensions/skills/story/scripts/story_flow.py`）。
   它下一步完全可能在 `check` 卡住时去改 `story-build.mjs`，那就直接毁掉判据的读数；
2. 产物落进主仓 `doc/features/`（被 gitignore，`git status` 不提示）；
3. 监控按隔离路径找 `story.md`，非隔离下那个路径不存在，**判定线全程失效**。

### 根因

**「测量工具可以在被测对象的仓里跑」本身就是设计错误。** 缺省值是次要的——
真正的问题是这条路存在。上一轮实测里被测模型能改判据，这一条如果不堵，
往后每一轮的读数都得先自证「这轮它没改过机制」。

### 改法

**隔离从可选变成唯一形态**：

1. `--isolated-workspaces` 退场，隔离**无条件生效**；相关分支（`ensure_no_external_active`
   等非隔离专用路径）随之删除，不留「关掉隔离」的入口；
2. 起跑前**物理校验**：case 工作区必须在系统临时目录下、且**不是**主仓路径的子路径，
   不成立即 `SystemExit`；
3. 收尾**物理校验**：suite 结束时核 `git status --porcelain -- doc/extensions` 为空，
   非空即报 `harness_contaminated` 并把 diff 存进 suite 结果目录——
   **哨兵不是为了拦住模型（拦不住），是为了让「机制被改过」永远不会悄悄混进读数**。

`--authorize-non-sandbox` **保留**：它管的是「这不是沙箱、用户知情」，与隔离是两件事。

### 验收

| 编号 | 判什么 | 怎么验 | PASS |
|---|---|---|---|
| B-1 | 开关退场 | `grep -n "isolated.workspaces" run_multi_case.py` | 只剩「恒为真」的实现，没有取值分支、没有命令行开关 |
| B-2 | 工作区必在临时目录 | 单测：构造一个落在主仓下的 case 工作区 | `SystemExit`，报错点名那条路径 |
| B-3 | 非隔离路径已删 | `grep -c "not_isolated\|current_workspace"` | `0` |
| B-4 | **污染哨兵** | 单测：suite 收尾前手工改一个 `doc/extensions` 文件 | suite 状态含 `harness_contaminated`，diff 落盘 |
| B-5 | 干净时不误报 | 正常跑一轮 | 哨兵不出声 |
| B-6 | 既有隔离行为不变 | `pytest test/story/tests -q` | 全绿 |

## C · 扩展包版本号升 1.3.0

### 事实

`doc/extensions/manifest.yaml:3` 仍是 `version: "1.2.0"`；全仓仅此一处写死。
`adapt` 的判态（首次 / 升级 / 重适配）直接比这个值，工作目录也按它命名
（`.adapt-<包 version>/`）。

自 `1.2.0` 之后本仓已实施 F8R 四批与 F8T 五批，机制面改动覆盖判据、作者面、
契约数据与 adapt 自身。**版本号不动，目标工程升上来会被判成「重适配」——
`SKILL.md` §1 写明重适配「机制行不执行」，于是机制改动一条都装不进去。**

### 改法

改成 `1.3.0`。同时在 `manifest.yaml` 里补一句为什么是 minor 而不是 patch：
机制面有判据行为变化（形态判据换粒度、禁用词作用域收窄、术语核主名），
目标工程升上来会看到不同的报错集合。

**不引入 CHANGELOG**：版本历史 git 里有，再立一份就是双真源。

### 验收

## D · 对接层 js 的依赖文件被当成机制内容

### 事实

`adapt-scan.mjs:64` 的分类：

```js
const classOf = (p) =>
  /^skills\/story\/scripts\/[^/]+\.js$/.test(p) ? 'js'
  : ...
  : /^skills\/(story|story-adaptation)\//.test(p) ? 'mech'
  : ...
```

`js` 这一类只认**顶层单个 `.js` 文件**。于是目标工程为自定义对接 js 装的依赖：

| 目标里的路径 | 被判成 | 后果 |
|---|---|---|
| `skills/story/scripts/package.json` | `mech`（不是 `.js`） | 校验 ① 报「机制多出旧文件」 |
| `skills/story/scripts/node_modules/**` | `mech`（有下级目录，不匹配 `[^/]+\.js`） | 同上，逐文件报 |

校验 ① 的判据是「机制目录文件集与内容 == 包」，包里没有这些文件 → 恒 FAIL，**绕不过去**。

### 根因

**分类靠路径长相，而路径长相回答不了「这是谁的东西」。** 对接层不是「几个 .js 文件」，
是**一块归目标所有的地盘**——它的依赖、锁文件、构建产物都在里面。

这与上一轮修 adapt「知识被包覆盖」是同一条：那次的教训写在 SKILL.md §2 里——
「只有模型读得懂哪些内容是这个工程的业务定义，**路径读不懂**」。这一处是同一个错误
在对接层上重犯一次。

### 改法

**判据从「路径长什么样」换成「包里有没有这个文件」**：

1. `skills/story/scripts/` 下，**包内存在同路径**的文件 → 机制（照旧整体复制、逐字核）；
2. `skills/story/scripts/` 下，**包内没有**的文件与目录 → 归目标所有（`custom`），
   **不复制、不校验、不报多出**；
3. 校验 ① 的「机制多出旧文件」只对**包内曾有、现已删除**的路径报——
   那才是「旧文件没清掉」；目标自己加的东西不是旧文件。

**为什么不写死排除 `node_modules` / `package.json`**：那是词表式补丁，下一个依赖形态
（`pnpm-lock.yaml`、`.venv/`、`dist/`）又得加一条。按所有权判，一次到位。

**边界**：这一条只放宽 `skills/story/scripts/` 一个目录。`hooks/`、`rules/`、
`skills/story/` 的其余部分仍是「文件集与内容 == 包」，因为那里没有「目标自己的东西」
这个概念——目标要改机制，走方案页。

### 验收

| 编号 | 判什么 | 怎么验 | PASS |
|---|---|---|---|
| D-1 | 依赖不再被拦 | 夹具：目标 `scripts/` 下放 `package.json` + `node_modules/x/index.js` | `--check` 零报，退出 0 |
| D-2 | **包内机制脚本仍逐字核** | 夹具：改目标的 `scripts/story-build.mjs` 一个字节 | 仍报「机制内容不同于包」 |
| D-3 | **旧文件仍报** | 夹具：目标有一个包内曾有、现已删的机制文件 | 仍报「机制多出旧文件」 |
| D-4 | 对接 js 本身的行为不变 | 夹具：目标 `scripts/story.js` 与包不同 | 仍按 `js` 类处置（看发起方），不按机制核 |
| D-5 | 范围只放宽一个目录 | 夹具：`hooks/` 下放一个包里没有的文件 | **仍报**「机制多出旧文件」 |
| D-6 | 不写死依赖名 | `grep -n "node_modules\|package.json" adapt-scan.mjs` | 除注释举例外，判定逻辑里零命中 |

## E · 停等点收敛成两处，且无条件；其余一律不停

### 目标形态（用户口径）

> 整个 extension 只有 **2 处**新增的等待用户确认：`/story init` 的**材料补齐**与**范围圈定**。
> 两处**固定停**（不由模型判断要不要停）；之后**自动进入 spec**，靠 extension + story 的
> 能力自动走完；spec 阶段自己设计的确认点不受影响。

本项要同时解决两类相反的毛病：**该停的没停**（E1）与**不该停的停了**（E2、E3）。

---

### E1 · 该停的没停：两处关卡改成无条件

**事实**：`skills/story/SKILL.md`「停等点白名单」第 1 条的字面是

> **材料缺口**：**需要**人补料才能继续（占位件、`inbox/` 空、单号查无此单）

**需不需要由模型判**——等于把停等的开关交给了被停的那一方。第 2 条同型
（「`scope_gate` **触发的**三级关卡」）。

**而 `story_flow.py:124` 有 `ACTORS = ("human", "ai")`**，`decide --by ai` 让模型能
**以自己的名义签掉关卡决策**。两件事一叠加就是内网观察到的现象：模型判「材料足够」
→ 条件不成立 → 不停 → `--by ai` 记掉关卡 → **材料补充环节整个被跳过**。

**改法**

| 现在 | 改成 |
|---|---|
| 材料缺口：**需要**人补料才能继续 | 材料关卡：`init` 之后**必停**，无论判断材料够不够。模型的判断只进选项推荐，**定不定由人** |
| 范围变更：`scope_gate` **触发的**三级关卡 | 范围关卡：**必停**。切法与承载哪份是同一次对话里的追问，仍算这一处 |

**物理门禁**：`ACTORS` 收成 `("human",)`，`--by ai` 整个退场（已确认三级关卡里没有
AI 代签的正当用法）。只改文档没用——「记得停下问人」这种话模型会忘，门禁不会。

**材料关卡每轮都停是对的**：补一次料就是一轮新材料状态，重新盘点重新确认。
「两处」说的是**两类停等点**，不是两次。

---

### E2 · 不该停的停了（一）：进入 spec 前的那一问

**事实（本轮实测）**：`auto-topup` 一共停了 4 次，第 4 次是——

> **下一步（一次问清）**：story 契约只管到 spec 闭环……这次要做到哪一步——
> 1. 只做 **spec 阶段** 2. **全链路交付** 3. 其他目标

**它不是模型多问，是契约要求它问的**。`skills/story/SKILL.md:63-66`：

> 所以用户的目标越过 spec 时……**在 S4 收口那一刻一次讲清**：请他在下一条消息里
> 把范围说出来，或者走 framework 的阶段推进确认点一次拿到范围授权。
> **一次问代替逐段问**

**根因**：「一次问代替逐段问」当时解决的是「每闭环一个阶段问一次」，方向对，
但它把**问的次数**从 N 降到 1，而不是降到 0——于是在 S4 收口处**固定长出第三个停等点**。

**做到哪一步这件事，本来就不该在流程中途问。** 它在两个更早的地方已经有答案：
用户发起 `/story` 时说的目标，以及 framework 的阶段推进策略（它解析用户消息，
扩展写什么都改不了它的判定）。中途再问一次，是把一个已经有主的问题重问一遍。

**改法**：删掉 S4 收口那一问。`SKILL.md`「授权分两层」改写为——

- story 契约 `next` 覆盖到 **spec 闭环**，段内一路走完，**S4 之后直接进 spec，不问**；
- spec 闭环之后进不进 plan，**归 framework 的推进策略**，扩展既不问也不判；
- 用户的目标越过 spec 时，那是 framework 阶段边界要处理的事，**不在本扩展的停等点里**。

---

### E3 · 不该停的停了（二）：`story-build check` FAIL 之后停下问人

**事实**：契约已经写明这条链内没有停等点——

> `check` 通过之后，到阶段闭环是**一条义务链，链内没有停等点**……
> `check` FAIL 时按报错文案修，改完重跑，直到通过或触发**白名单第 3 条**。

**而白名单第 3 条是**「同一处连续 3 次修不好」——**又是一句让模型自己判的话**。
与 E1 的第 1 条是同一个缺陷形状：模型试一次就可以宣布「修不好」，然后合法地停下。

**改法：把它从「自述」改成「可核」。**

停等只在**机器可验证**的前提下合法：同一判据类在 `check` 的连续三次运行里**都报了**，
且三次之间产物确有改动。判据类现在有现成的名字（本轮 S8 已给每类打了分类戳），
所以「同一处」是可核的，不再靠模型自述。

不满足这个前提就不是合法停等——**照报错文案修，改完重跑**。

**顺带**：`check` 的报错文案本来就自带「缺什么 / 写到哪 / 怎么写」，
不需要问「该不该修」。这句话已经在契约里，保留。

---

### E4 · 另外两条重新定位，不计入「两处」

| 原第 3 条 | 连续 3 次修不好 → **不是确认点，是失败上报**：它不问人要授权，是报告修不动、请人接手。从「停等点白名单」移到**失败出口**小节，并按 E3 加可核前提 |
| 原第 4 条 | 破坏性动作（归档、恢复）→ **既有确认点**，不是本扩展新增。注明它属于哪一层，不计入这两处 |

改完之后，「新增停等点」名下**只剩两条**：材料关卡、范围关卡。

## 实施顺序

**四批，批间硬门。**

| 批 | 内容 | 门 |
|---|---|---|
| **甲** | A（死锁）+ B（装置隔离） | A-1…A-5、B-1…B-6 全绿；`pytest test/story/tests tools/cli/tests -q` 全绿 |
| **乙** | E（停等收敛） | E-1…E-9 全绿；**E-2/E-3 的物理拒绝是硬门**，破了本项作废 |
| **丙** | C（版本）+ D（对接层归属） | C-1…C-4、D-1…D-6 全绿；**D-2/D-3/D-5 是硬门**（放宽之后机制仍核得住） |
| **丁** | 收口 | 全量回归（单测 / 失效形态 / 金样 / extensions）；adapt 端到端演练重跑一遍；写交付报告 |

**为什么 B 在最前**：B 不落地，后面每一轮实跑的读数都得先自证「这轮机制没被改过」。

**为什么 D 排在 E 之后**：D 是放宽（把一批文件移出机制面），按上一轮定下的纪律，
放宽项排在收紧项之后，且各自配硬门反例。
