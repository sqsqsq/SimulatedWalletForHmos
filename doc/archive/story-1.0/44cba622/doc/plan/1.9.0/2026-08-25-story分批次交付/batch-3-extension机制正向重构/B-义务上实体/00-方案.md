## 0. 一句话

**把规约义务从没人读的平行账本，搬到下游本来就要读的契约实体上；机器只判它判得了、且对已知违规有区分力的事。**

## 1. 现在为什么不行（实测）

`contracts.yaml` 里的 `knowledge_freeze` 是一本**平行账本**：plan 往里写义务，coding / review / ut / testing 从里面读。问题是没人真的读——

- `framework/skills/feature/coding/SKILL.md:38-53` 枚举 contracts 的 **7 个集合**作为本阶段输入，**不含 `knowledge_freeze`**。编码者按 SKILL 走，根本不会打开它。
- `hooks/coding/post_check.mjs` 89 行，判据是 `\b名\b` 跨文件文本存在性——不分声明/调用/注释，末段是容器名时**恒真**。
- AR90004 实测五条规约的衰减：`UX-01` 的处置「用 start/end」+ 5 条落法附注 + 检索式，到 plan 只剩 `landing: components.LossReportSheet`，到 coding **空**；源码 `LossReportSheet.ets:365` 明晃晃写着 `padding({ left, right })`，探针查 `\bLossReportSheet\b` 恒真放行。
- 唯一完整落地的是 `ENV-02`——靠的是 `contracts.components.LossReportSheet.submitting` 这个**编码者本来就读的字段**。把 `knowledge_freeze` 整块删掉，它的结果不变。

**这是反证**：义务写在实体上才生效，写在账本里只是展示。

## 2. 目标形态

### 2.1 义务挂在实体上（`contracts.yaml`）

```yaml
interfaces:
  - name: CardCloudAdapter
    methods:
      - name: createOrReuseLossApplication
        must:
          - text: 同一幂等键重复调用不得创建第二份申请
            rule: <条目编号>
            verify: ut
components:
  - name: LossReportSheet
    must:
      - text: 方向性布局参数只用 start/end，禁止 left/right
        rule: <条目编号>
        verify: probe
files:
  - path: .../LossFlowOperates.ets
    pattern: <在册模式标识>
    role: <该模式声明的角色名>
```

- `must` 只允许挂在 `data_models[].fields[]`、`interfaces[].methods[]`、`components[]`（及其 `state`）、`resource_keys[]`、`files[]` 上。
- `text` 必须含本需求专名（复述判定沿用 `paraphrase.mjs`）；`rule` 须在册。
- `verify` 取值封闭：`ut` / `device` / `both` / `review` / `probe`。
  取 `probe` 时**探针表达式不写在这里**——它在规约条目表的「探针」列，随知识走（见 2.3）。
- 没有实体可挂的规约（处置标「（评审动作）」）不进 contracts，只在 review 记录留痕（既有）。
- **F10 已实测**：`spec-loader.ts:442-478` 的 `normalizeArrayField` 只归一数组、剔非 map 条目，**无键白名单**；`check-plan.ts` 也无未知键校验。实体级 `must` 不会被 framework 剔除，主方案可行，不必退到 `plan.md`。

### 2.2 模式采用 = 结构投影

- 模式文档 frontmatter 增 `sections: { select, implement, verify }`（三篇的标题，现已按读者分篇，只补声明）。
- plan 给每个角色文件标 `files[].pattern` + `files[].role`（`role` 取值须是该模式 frontmatter `roles` / `optional_roles` 里的名字）。
- **删除** `knowledge_freeze.patterns` 与 `roles: {角色: 类名}` 投影——信息由 `files[]` 承载，角色实体 = 文件里的类。

### 2.3 规约条目表增「探针」列（数据，随知识走）

`| 编号 | 约束 | 强制力 | 命中条件 | 处置 | 验证（执行体） | 探针 |`

四种封闭形态：

| 形态 | 语义 |
|---|---|
| `absent_regex:<re>` | `must` 所在实体的文件里**不得**出现 |
| `present_in_method:<re>` | `must` 所在方法体内**须**出现 |
| `referenced_outside_definition` | 实体在定义文件之外被引用（模式角色用） |
| `count_eq:<re>:<n>` | 文件内命中次数恒等于 n |

- **「探针」列可缺省**（E9）：目标工程的规约表没有这一列时按「无探针」派生，**不 throw**——否则已适配仓经 adapt 升级后老知识全部派生失败。
- 无探针的条目 `verify` 只能取 `ut` / `device` / `both` / `review`。
- 探针表达式是**数据**，`post_check` 里不含任何规则编号与正则字面（KB-6）。
- 扫描 0 命中时告警「形态可能不匹配本工程」，不静默。

### 2.4 派生索引（`hooks/shared/knowledge.mjs`）

新增两个纯函数，**运行期从 contracts 派生**，不维护第二份清单：

| 函数 | 返回 |
|---|---|
| `obligationsFromContracts(contracts)` | `[{rule, entityPath, entityKind, text, verify, file}]`——遍历五类实体收集 `must` |
| `patternRolesFromContracts(contracts)` | `[{pattern, role, path}]`——来自 `files[].pattern/role` |

派生为空（spec §10 有命中而 contracts 零 `must`）→ **BLOCKER 指路 plan**（G7）。
`acceptance.yaml` 的 `knowledge_rule` 桥接键保留（framework 原生追溯链不变）。

### 2.5 各阶段改判什么

| 阶段 | 改动 |
|---|---|
| plan | 两条集合判据：① spec §10 每条命中在 contracts 至少一条 `must` 引用 ② 每条 `must.rule` 在 §10 命中集内。**删**三重锚定、anchor 自指、landing 解析等账本形态判据 |

## 6. 风险

1. **AR90004 对照样本用的是旧账本形态**。KB-4 要求新探针对它有区分力（五角色零调用、`padding({left,right})`）——但它的 contracts 里没有 `must`。**处置**：造一份等价的实体 `must` 形态夹具（从 AR90004 的账本机械转写），对**真实源码**跑探针。区分力验的是探针对源码的判别力，不是对 contracts 写法的判别力。
2. **`ut_layer` 退场会丢「显式不适用」的载体**。旧形态里 `device` 就等于「UT 不适用」。新形态 `must.verify: device` 同样表达它——但 `both` 必须保留，否则原来标 `both` 的条目会掉一边。
3. **`freeze.mjs` 拆一半**：账本读取删、实体访问器留。删之前先 grep 每个导出的消费者，避免又出现子批 A 那次「删导出漏了模块自己在用」（坑 #59）。
