## 2. 必修

### B1 · 读者审查写成了两条路，其中一条永远走不到（§3.3）

方案说「一套 adapter 无关的承载」，实际是两条：

1. `phases/spec.md` ⑤ 之后**无条件**派子代理写 `AR/story-src/reader-review.md`；
2. framework 的 verifier 在已登记的宿主上照常渲染 `story_reader_review`——overlay `semantic_checks` 里那一条会进 ai-prompt，`hooks/shared/pre_verifier.mjs` 第 94 行还会把任务书再注入一遍。

内网是 codex，已登记。按方案走，codex 上同一份 story 被审两次：⑤b 一次、⑦ 一次。这与「同一产物不重审」相悖，也与方案自己 §7「不为 opencode 单开一条路径」相悖——它单开的不是 opencode 那条，是 codex 那条。

第二个问题是核对时机。`verifier-report.mjs` 挂在 `post_check`，⑥ 跑 harness 时执行；framework 的报告在 ⑦ 之后才有，而 ⑦ 之后不再跑 harness（`phases/spec.md` ⑧、`story_flow.py` 885–890）。所以「优先读 `summary.verifier_report`」在正常流程里一次也不会命中，是死分支；只有 subject 失配重跑 harness 时才会碰到。「两来源一套判据」实际是一个活来源加一个死来源。

**返修目标**（推荐，只保留一条路）：

- 读者审查由扩展承载，对所有宿主一样：⑤ 登记之后 story 冻结，指纹从此不变，所以 ⑤b 派子代理、⑥ 的 `post_check` 核报告，时机自洽。
- `story_reader_review` 从 overlay 的 `semantic_checks` 里**搬走**（不是复制）：判据正文进任务书的真源（`reader-review-task.mjs` 或它读的一份 md），framework 的 verifier 从此不再碰 story；`pre_verifier.mjs` 第 22、28、94–95 行那一段删除。判据仍只有一份，只是消费者从 framework 换成扩展自己。
- `verifier-report.mjs` 只认一个来源 `AR/story-src/reader-review.md`；JSON 发布件的解析（`REPORT_JSON_RE`、`reportTexts`）整段退场。
- 代价写明：codex 上 spec 阶段要派两个只读子代理（扩展的读者审查、framework 的 spec 审查），各审各的对象，不重叠。

若用户宁可在 codex 上省这一次派发，替代形态是「framework 登记了 `verifier_subagent` 就不派 ⑤b」——那要让作者在 ⑤b 时知道登记状态，多一处对 framework 内部字段的读取，而且核对要挪到归档门。我不推荐。

### B2 · 子代理的输入契约没核：verifier 定义只收 request JSON（§3.3）

方案写「用 Task 派 `subagent_type: verifier`，prompt = 那份任务书」。三处 verifier 定义都写死了输入形态：

- 上游 `framework/agents/claude/templates/agents/verifier.md`（0 改动后原样物化到 `.claude/agents/`）：「你收到的 Task prompt 就是一份 request JSON，别无其它文字……如果不是，写明『未收到合法 verifier request，本次报告不可入闭环』，**不要自行编造 subject_id**」；
- 本仓 `.opencode/agent/verifier.md` 同一段文字（还停在 `schema_version 1.0`）；
- codex 的共享规则（`.codex/rules/framework-agent-execution.mdc` §3）同样要求 prompt = request JSON 整段。

拿任务书去派 verifier，子代理会按定义先声明「不可入闭环」，指纹回显也可能被它当成「编造 subject_id」拒绝。批次 5 的读者审查能跑，是因为它搭在 framework 的 request 上；这次它离开了 request，就得自己把契约说清。

**返修目标**：

- 任务书自足：开头给定 `subject_id`（见 B3 的指纹定义）与只读要求，结尾给终态块形状——**沿用 framework 的终态块**（`<!-- maison-verifier-result:v1 -->` 三行），子代理本来就会写这个块，不另造格式。
- 派发对象写成「宿主的只读子代理」，不指定 `verifier`；本仓装置 `.opencode/agent/verifier.md` 由本仓维护，给它加第二种输入形态（任务书，带 `subject_id:` 首行即回显），同时把 `schema_version` 改 1.1。codex 无 agent 定义文件，任务书自足即可。
- 任务书与 overlay 里「结论由插件按你的终态发布」「不另写文件」两句删除（`reader-review-task.mjs` 末段、overlay 第 129–132 行）——发布器已经没有了。

### 7.2 必修

**R36 · 交付门在 Windows 上从来跑不起来。** `story-build.mjs` 第 1698–1700 行 `spawnSync('npx.cmd', …)` 不带 `shell`。Node 18.20 / 20.12 之后拒绝这样起 `.cmd`，本机 Node 24.18 实测 `r.error.code === 'EINVAL'`、`status === null`。于是 `check --deliver` 在 Windows 上恒走「交付门跑不了：spawnSync npx.cmd EINVAL——自己跑一次」——不是误判通过，但门等于没有，六跑装置正是 Windows。夹具没抓到，因为 `test_verifier_report_protocol.py` 的交付门三条只测「找不到框架」「离线互斥」「普通 check 不碰」，没有一条真的 spawn。

修法：不经 shell、不经 `.cmd`——用 `createRequire(import.meta.url).resolve('ts-node/dist/bin.js', { paths: [harness] })` 解析到 framework/harness 自己的 ts-node，`spawnSync(process.execPath, [bin, 'scripts/check-receipt.ts', …], { cwd: harness })`；解析不到时如实报「framework/harness 没装依赖」。加一条真接线夹具：在本仓对一个不存在的 feature 跑 `check --deliver`，断言 `r.error` 为空、stderr 里是 `check-receipt` 自己的话（feature 不存在）而不是「跑不了」——只 spawn 不写盘，不碰红线 9。

**R37 · 归档 ① 没接上交付门。** 方案 §3.3「远程单：归档 ① 改成 `check --deliver`，在 ② 上传之前拦住」。`SKILL.md` 第 191 行归档块 ① 仍是 `check --feature <AR>`；`--deliver` 只进了第 106 行的衔接链与 `archived`（`story_flow.py` 第 1261 行）。模型照归档块走，① 过了就 ② 上传，`--deliver` 第一次真正跑是 ③ 登记——正是上一轮外部评审指出的「发现问题时内容已上传」。修：第 191 行改 `check --deliver --feature <AR>`，注释写「交付门：回执 + 读者审查形态」。
