# 上游必要信息守恒（需求1 落地强化 · spec 侧）

> 状态：设计定稿（待批准） · 日期：2026-08-23
> 同一批待优化方案之一（与 `00-图片引用`、`01-知识应用`、`02-人读成文闭环`、`03-Review决策项精简` 并列）。
> 本方案处理"2.0 重写时 spec 丢了上游必要信息"的问题：上游（AR/design 的"本 AR 范围与拆分说明"、SR/design、RR/prd）里的
> 必要事实必须落进 spec——因为 **spec 是编码真源**（plan/coding 只看 spec，上游/story 不参与编码）。
> 实施事实与行为验证结论分局记录，禁止写"已实施"。

## 一、背景与根因（已核实的事实）

- 实证（AR90006）：`不保存支付凭据`、`不判断是否该扣款`、`连续失败停用` 三条必要信息，在上游（AR/design.md、SR/design.md、RR/prd.md）和 1.0 归档 spec 都有；当前 2.0 spec **全丢（0 次）**；story 靠重读上游材料才侥幸保留。
- 影响链：spec 是编码真源 → spec 丢了"不保存支付凭据"安全边界 → plan/coding 看不到 → **这条必要信息在应用层丢失**。
- 1.0 的守恒机制（`0c8ab1dd` story-build.mjs L245-275 `findMissingFacts`）是"上游（factSource）→ story"的表格行/数值/标识守恒——**在 2.0 被整体移除**；2.0 的 merge-story 只查"spec → story"的编号/术语/契约标识覆盖，**"上游 → spec"是空档**。
- 结论：2.0 不是把必要信息当"冗余"删掉的——是**写 spec 时没有上游→spec 守恒门禁**，模型把上游必要事实当可优化内容丢掉。

## 二、目标

spec 阶段的必要信息不丢：**上游（AR/design、SR/design、RR/prd）里的必要事实，在 spec 有落点**。spec 是编码真源，这条守恒保护的是"要求到得了编码"。

**方向澄清（非补丁）**：不是恢复 1.0 的"上游→story"严格守恒（那是 1.0 为弥补 story 缺规范而设，且会逼模型逐行搬运、催生冗余——正是 2.0 要消灭的）。本方案是**新建"上游→spec"的必要信息守恒**：只守"必要信息"（业务规则/安全边界/接口/配置/阈值），不守"逐行逐词"（表述可整合改写）。

## 三、"必要信息"的正向定义（判据边界）

| 类别 | 定义 | 例子 | 校验方式 |
|---|---|---|---|
| **可标识事实** | 接口名、配置项名、存储键、事件名、编号、阈值数值 | `getAutoTopupPolicy`、功能开关名、`contractNo`、200 元 | **机械**（名字/编号/数值有落点） |
| **语义事实** | 业务规则、安全边界、失败收敛等**表述性**必要信息 | "不保存支付凭据"、"付款前不扣费"、"不判断是否该扣款" | **语义裁决**（表述可能改写，机械判不了"语义在"） |

**关键判断**：机械层只能可靠守**可标识**（名字/编号/数值）；**语义**（安全边界措辞）必须靠语义裁决（verifier）——这正是"不给模型做机械保证语义"纪律的体现：机械不假装能判"措辞变了但语义在"，语义判据保证被强制裁决。

## 四、方案（三层，全在 `doc/extensions`，零 framework 改动）

### 4.1 写入侧（治根——写 spec 前必须核上游）

`hooks/spec/on_context_load.md`（已注册、已在役）加一条 BLOCKER 指令：
> 写 spec 前必须**逐项核对上游**（AR/design.md 的"本 AR 范围与拆分说明"、SR/design.md、RR/prd.md）中的**必要事实**——业务规则、阈值、安全边界、接口、配置项——逐项确认已落进 spec 对应章节。把上游必要信息当"冗余可删"是错误：spec 是编码真源，上游必要事实必须进 spec（可整合、可改措辞，不能少语义）。

### 4.2 机械门禁（可标识事实）

`hooks/spec/post_check.mjs`（已读上游 L594）扩一个**上游→spec 可标识覆盖检查**：
- 从上游材料提取**可标识事实**：接口名（`getAutoTopupPolicy` 等）、配置项名、存储键、编号、阈值数值（复用现有 `scanNumericSources` 的数值提取模式）；
- 校验 spec 是否有落点（名字/编号/数值在 spec 出现，或已在 decisions 登记——本工程设定值走决策不强制正文）；
- 缺失 → FAIL：`上游必要可标识事实未进 spec：xxx（spec 是编码真源，plan/coding 只看 spec，漏了就到不了编码）`。

### 4.3 语义裁决（语义事实）

`rules/spec-rules.overlay.yaml` 加语义判据 `upstream_semantic_coverage`：
- 描述：上游（AR/design 本 AR 范围、SR/design、RR/prd）里的**语义性必要事实**（业务规则、安全边界、失败收敛）须在 spec 有落点或明确声明"该事实不在本 AR 范围"；表述可改写，语义不能丢。
- 由 `01-知识应用` 的 `pre_verifier.mjs` 强制裁决（进入 verifier 必答清单）。

## 五、改动点

| # | 落点 | 改动 | 类型 |
|---|---|---|---|
| 1 | `hooks/spec/on_context_load.md` | 加"上游必要事实必须进 spec"BLOCKER 指令（§4.1） | 正向 |
| 2 | `hooks/spec/post_check.mjs` | 上游→spec 可标识覆盖检查（§4.2） | 机械门禁 |
| 3 | `rules/spec-rules.overlay.yaml` | 加 `upstream_semantic_coverage` 语义判据（§4.3） | 语义 |
| 4 | 回归 | 依赖禁令、extension-loader、unittest、冒烟 | 回归 |

## 六、不做（越界清单）

- **不恢复 1.0 的"上游→story"逐行/逐词严格守恒**（那是 1.0 为补 story 缺规范而设，催生冗余，正是 2.0 要消灭的）；
- 不要求上游每条事实都进 spec 正文（只守"必要信息"，可整合改写；不相关事实可声明"不在本 AR 范围"）；
- 机械只守**可标识**（名字/编号/数值），语义表述靠语义裁决，不机械伪造；
- 不改 `framework/`、不改 decisions.json schema（本工程设定值走决策登记，不强制正文）。

## 七、与其他方案的关系（防冲突）

- 与 `02-人读成文闭环` 一致：`02 §三` 定义"规约编号合规回显是正文合法内容"——本方案的"必要信息进 spec"与它不冲突（spec 与 story 是两份产物，各自守恒）；
- 与 `01-知识应用` 共享 `pre_verifier.mjs` 强制语义裁决机制（`upstream_semantic_coverage` 进入同一必答清单）；
- 与 `03-Review决策项精简` 无交集。

## 八、验收

- 原生：`node --check` 全 mjs；unittest（story + cli）；extension-loader 0 errors；依赖禁令扫描。
- 冒烟：
  1. 造一个上游有 `getAutoTopupPolicy` 接口名、spec 未写 → post_check FAIL；
  2. 造上游有"不保存支付凭据"语义、spec 未写 → `upstream_semantic_coverage` 在 pre_verifier 必答清单出现；
  3. spec 写了接口名/语义 → PASS；
  4. 本工程设定值（走 decisions 登记）→ 不误报。
- 行为验证（另行）：下一轮四 Case 复查 spec 不再丢上游必要信息（对照 1.0 归档 spec 的"不保存支付凭据/不判断是否该扣款/连续失败停用"类事实）。
