# 2026-08-18 以来需要投建的能力与诉求

## 1. Story 去重且不丢内容

诉求：

- Story 必须完整保留当前需求全部有效事实，不能退化为 Spec 摘要。
- 产品需求、系统设计、当前特性、相关特性、UX、补充材料、Spec、验收和人工确认结果中的有效内容都不能遗漏。
- 当前特性的业务目标、范围、方案、流程、全部有效分支、状态、异常恢复、接口影响、数据、配置、事件、兼容、交付和验收需要完整保留。
- 存在兄弟特性时，需要保留拆分原因、各自职责、交接结果、依赖顺序、阻塞关系和共享状态生命周期，但不复制兄弟特性的内部实现。
- 编号、表格有效行、业务规则、限定条件、否定条件、默认值、固定值、可修改值、数值、图片信息、流程分支、状态终点、错误语义、恢复前提、被否方案和取舍理由都属于需要守恒的内容。
- 同一事实只保留一个完整主叙述，其它位置只作必要承接或补充该位置独有的信息。
- 业务流程、功能说明、异常、验收、图表和追溯不能互相完整复述。
- 去重只能删除重复表达，不能删除唯一事实，不能以文档变短、标题减少或表格减少证明优化成功。
- Story 完成后需要从全文视角统一整理，解决跨部分重复、口径不一致和局部遗漏。
- 同轮材料冲突时不能由模型自行选择，未确认内容不能作为正式事实写入 Story。
- 不能增加来源中不存在的指标、规则、结论和工程事实。
- 内容守恒需要对全部有效事实逐项核对，不能只抽查少量事实。

## 2. Story 面向人类叙述友好

诉求：

- Story 面向第一次接触需求的人类评审者，阅读者无需先读 Spec、产品需求、系统设计或代码。
- 文档按照人的理解顺序说明为什么做、涉及谁、怎样解决、业务如何推进、当前特性负责什么、哪里会失败、怎样验收和怎样交付。
- 先说明背景，再解释理解后文必需的术语。
- 标题使用真实业务名称，简短、自然并准确概括下文。
- 标题不能使用模板占位语、模型提问、机械分类词、解释性长句和明显的 AI 式表达。
- 三级、四级标题根据真实业务从属关系自然生成，不为了形式对称强制出现。
- 完整业务过程与当前特性功能分别说明：业务过程说明需求怎样推进和在哪里交接，功能说明展开当前特性承担的页面、动作、状态和分支。
- 正常受限结果与真正异常分开说明。
- 连贯的原因、方案、取舍和影响使用自然叙述；表格、流程图、状态图、时序图和图片按实际表达需要使用。
- 接口、字段、错误码、配置、事件和追溯信息必须保留，但不能打断面向人的主叙述。
- 验收按照真实业务场景或结果组织，每个原始验收编号独立保留，并提供可观察的通过条件。
- Story 只表达已经成立的需求和决定，未确认事项进入 Review，不在 Story 中生成“待确认事项”或“评审导读”。
- Story 保留以下骨架，后续优化重点是让模型基于真实需求内容写出自然标题、连贯正文和合理层级，而不是继续更换骨架：

## 3. Knowledge 能力重构并在各阶段有效应用

诉求：

- Extension Knowledge 统一分为三类：规约、设计模式和项目知识。
- 三类知识的职责必须清楚且不重叠。
- 规约表达目标工程必须遵守的要求，并明确适用范围和所属领域。
- 设计模式表达可选择、可复用的工程方案，存在模式不代表当前需求必须采用。
- 本轮必须恢复两个曾被删除的设计模式：`decision-tree`（复杂业务分支编排）和
  `page-interaction`（页面交互编排）。两份原型取自
  `E:\Project\AIDefectHelpler\docs\archive\需求开发\extensions\knowledge\design-patterns\`。
- 该目录的 `README.md` 只作为这两个模式的索引、适用单元和组合说明，不形成第三个设计模式。
- 项目知识表达目标工程当前真实存在或明确不存在的能力、依赖、配置和工程事实。
- `project_facts` 与 `codebase_facts` 不再形成两套含义相近的项目事实体系。
- 项目知识来自目标工程源码、依赖、配置、工具链或明确核实，不能来自备份、历史输出、未提交临时文件和测试假设。
- Story 不直接读取三类工程知识，只表达当前需求材料中对人有意义的工程影响。
- Spec 能识别与需求有关的规约影响和设计模式候选，但不能把候选直接当成最终选择。
- Plan 根据目标工程实际情况决定规约如何落实、设计模式采用或不采用，以及项目知识如何影响工程设计。
- Plan 作出的知识决定能够稳定传递给 Coding、Review、UT 和 Testing，后续阶段不能重新选择或静默改变。
- Coding 根据已经确定的知识结果完成真实实现。
- Review 根据真实代码判断规约、设计模式和项目知识是否被正确应用。
- UT 和 Testing 验证各自层次的实际行为，不能只检查知识名称是否出现。
- 必须区分“知识被读取”“知识被识别”“知识被选择”“知识被传递”和“知识被实际应用”，前一步不能证明后一步完成。
- 模式、规约、行为、验证和实现引用必须对应真实对象及正确所属领域，不能使用模糊词命中或文件存在性代替真实应用。
- 支持目标工程没有设计模式、只有一个模式、复用现有两个模式或使用其它模式；有模式时也不强制采用。
- 设计模式知识需要以真实 Skill、SDK、依赖和既有案例为依据，采用后必须对设计和实现产生实际影响。
- README、使用说明、示例、测试夹具和正式运行知识需要明确区分，不能被混合消费。
- 需要保留日志、VOC 定位上报和 Chart 统计埋点组成的三层可观测性知识：日志用于本地调测和完整流程
  还原，VOC 用于无本地日志时远程定位，Chart 用于成功率、时延和终态结果统计。
- 三层渠道使用同一业务 `flow_id` 和 `step_id`，信息与触发密度遵循“日志 > VOC > Chart”，不使用固定
  数量配额判断覆盖质量。
- Spec 说明业务上需要定位和统计什么，不规划具体日志调用点；Plan 必须按业务流程和步骤把三层知识
  实际应用为工程方案和可观测性合同，再冻结实现、Review、UT 和 Testing 义务。
- Coding 必须真实落实日志、VOC 和 Chart；Review 根据真实代码检查覆盖、密度、字段和失败隔离；UT 和
  Testing 验证各自层次的业务结果、事件终态唯一性、实际字段、触发时机和时延。
- Debug 可以承载必要调测信息，但所有渠道都排除凭据、访问令牌、会话秘密和密钥；Info、Error、VOC、
  Chart 中的受保护业务字段需要省略或脱敏。
- 日志或上报失败不能改变业务流程、结果、分支或重试。
- 当前 Demo 已构建 Logger、VOC 和 Chart 正式基础能力。这些 API 和代码位置属于项目知识；三层覆盖、
  密度、数据保护和失败隔离要求属于规约，不能混成新的知识类型。
- Knowledge 保留以下目录结构，后续重构重点是收敛三类知识的职责、消除重复事实，并打通各阶段的真实应用：

## 4. ADAPTATION 面向 AI 的工程适配能力

诉求：

- ADAPTATION 的直接读者是执行工程适配的 AI。
- AI 能根据 ADAPTATION 理解需要检查目标工程的哪些内容、从哪里取得真实证据，以及哪些 Extension 内容需要调整。
- AI 使用目标工程真实的源码、目录、配置、依赖、Skill、SDK、工具链和既有业务案例完成适配。
- AI 能根据目标工程实际情况适配项目知识、规约和设计模式，而不是照搬当前工程内容。
- 目标工程不需要设计模式时，AI 能形成零模式的有效适配结果。
- 目标工程可以复用现有一个或两个模式，也可以引入目标工程自己的模式。
- 未经目标工程核实的知识不能在适配后直接生效。
- 文件存在不能代表适配完成，适配结果必须反映目标工程的真实能力和约束。
- ADAPTATION 需要明确区分通用 Extension 能力、当前工程示例和目标工程正式内容。
- 当前工程不能成为其它工程运行时的隐含依赖。
- 适配说明需要集中、直接、可执行，不能散落在多份互相重复或冲突的文档中。
- 完成适配后，AI 和后续阶段能够清楚知道目标工程实际启用了哪些项目知识、规约和设计模式。
- 可观测性适配必须分别核实目标工程真实的日志 API，VOC SDK、事件模型、字段限制、频控和失败语义，
  Chart SDK、事件命名、统计口径和归档流程，以及正常与异常业务案例和数据保护规则。
- 目标工程的真实能力替换 Demo 的 Logger、VOC 和 Chart 身份及示例，同时保留业务流程索引、三层密度、
  业务步骤终态统计和上报失败隔离语义。
- 目标工程缺少任一渠道时必须登记能力缺口和权威证据，由用户确认引入真实依赖或调整适用规约；确认前
  不能虚构 API、事件或上报结果。
