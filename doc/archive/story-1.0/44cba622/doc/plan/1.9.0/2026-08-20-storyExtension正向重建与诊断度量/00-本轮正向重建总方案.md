## 1. 本轮要解决什么

前三轮优化已经带来了人读 Story、工程知识生效、目标仓适配和测试历史保留等有效能力，但当前实现把一个测试 Case 的材料标题、章节分配方式、Demo Knowledge 和实例路径提升成了生产合同。父提交 Extension 在相同内网链路可以运行，说明问题不是优化诉求本身，而是新机制放错了职责层。

本轮正向完成四项主任务：

1. 重建 Story 的取材、写作、装配和评审链，修复内网致命错误，同时保留有效事实、决定、图片、归档和现有 CLI 能力；
2. 重建 Knowledge 与 ADAPTATION，使 Project Facts、Constraints、Patterns 只有一个运行激活入口，并保持 Spec 候选、Plan 选择、合同冻结和下游消费的完整链路；
3. 落地诊断与业务度量的 Extension 合同，包括知识归属、阶段职责、`observability`、Hook、overlay 和确定性检查；
4. 构造覆盖 Story 全部功能场景的多场景需求 Case，供后续多 Case CLI 验证使用。

## 5. 明确删除的错误或冗余设计

| 删除内容 | 原因 | 正向替代 |
|---|---|---|
| 章节 `sources/inputs`、selector、primary/supporting、标题命中门禁 | 把 Case 的写法变成生产输入协议 | 全量机械枚举材料，模型先完整阅读，再按输出职责归章 |
| 用固定“用户旅程”、机械小标题或业务范文指导模型 | 会把示例语言固化为最终标题，并掩盖真实业务关系 | 固定二级导航，H3/H4 使用当前需求的真实业务名称 |
| 以行数、标题数、表格数或篇幅下降评价人读质量 | 会诱导删除唯一事实 | 用 S2 内容守恒、S3 叙述顺序、S4 取舍、S5 表达形态、S7 单一主叙述评价 |
| 合并不同验收编号来压缩表格 | 丢失来源层级和独立责任 | 每个原始验收编号独立一行，语义相近时使用短引用而不重复理由 |
| `story-sources.json`、`source-inventory.json` 等持久来源台账 | 与现有工作区、导入链和 `context/facts.md` 重复 | 一处纯函数枚举当前实际材料；读取事实仍用现有记录 |
| workspace marker、新 build 状态机、第二套归档 receipt | 与 Story CLI 和 Framework phase 状态重叠 | 命令内临时生成、全部校验后发布；继续使用既有生命周期 |
| Knowledge 目录扫描、README 路由、第二份 registry | 形成多个运行激活真源 | Framework Manifest 是唯一 active 清单 |
| 把本仓默认激活状态等同于所有目标仓都必须激活 | 零模式无法表达，未适配的 SDK/API 还会进入运行期 | 本仓默认同时激活两份模式；其他目标仓的 Manifest 只激活实际采用并完成适配的模式 |
| Story 直接读取 Project Facts、Constraints 或 Patterns | 需求叙述与工程选型职责交叉 | Story 只读需求材料；Spec 起才消费工程 Knowledge |
| 自建 delivery closure、Trace、receipt 或 phase | 绕过 Framework 已有能力 | 复用 Harness、Verifier、`trace.json` 和 `check-receipt` |
| 为每个场景另造 Case schema、runner 状态或答案台账 | Case 反向控制生产实现，形成新的过拟合入口 | 复用现有 `case.yaml`、mock-data、workspace 和评价流程；覆盖关系只写在测试设计与报告中 |

## 6. Framework 复用边界

`framework/` 是已发布平台，本轮不修改、不复制、不替代。

| 需要的能力 | 唯一入口 | Extension 或测试域允许做什么 |
|---|---|---|
| 发布清单 | `doc/extensions/manifest.yaml > provides` | 列出实际 Skill、Knowledge、Hook、overlay，不建平行 registry |
| 阶段上下文与机械检查 | lifecycle hooks | 注入 active Knowledge、检查精确引用和 Story 确定性结构，不定义新 phase |
| 阶段语义 | phase rules overlays | 只表达 Extension 特有义务，不复制 Framework 通用规则 |
| Extension 验收 | Framework `extensions` gate | 先做 Extension 专用检查，再走正式 gate |
| 阶段结构闭环 | Framework Harness | 使用 active workflow，不自建 runner |
| 阶段语义闭环 | 独立 Verifier | 评价语义完整、人读质量和工程合理性，不由脚本替代 |
| 凭证 | `trace.json` 与完成回执 | 保存证据并通过 `check-receipt`，不增加第二张完成凭证 |
| feature 合同 | 现有 `contracts.yaml`、`use-cases.yaml` | 继续承载 `project_knowledge` 和 `observability`，不另建合同文件 |
| Story Case 运行 | `test/story/scripts/run_case.py` 及后续多 Case 入口 | 当前执行者不调用；下一模型执行现有单 Case 并扩展多 Case 编排，不改变 Framework phase |

## 7. 目标职责

| 层 | 只负责什么 | 不负责什么 |
|---|---|---|
| Story | 把完整需求材料组织成人可读、可评审、无重复的需求叙述，并给 Review 提供决定上下文 | 不读取工程 Knowledge，不做模式选型，不规划观测调用点 |
| Review | 收拢已定和开放决定，给人提供表态位置并保留人工结果 | 不成为第二份需求叙事 |
| Extension Knowledge | 保存目标仓事实、跨 feature 规约和正式模式库；Manifest 决定当前目标仓的 active 子集 | 不保存单 feature 采用结果，不保存 Case 答案 |
| Spec | 形成需求、范围、验收、工程知识候选和诊断/度量意图 | 不决定模式采用，不设计具体观测调用点 |
| Plan | 结合代码事实完成工程选择，写主体设计、contracts 和 use-cases | 不重写需求，不从未激活知识中自行选择 |
| Coding/Review/UT/Testing | 消费 Plan 冻结的知识应用和观测合同，实施、审查和验证 | 不重新扫描 Knowledge 后静默换型 |
| ADAPTATION | 在目标仓准备、验证并发布 Extension Knowledge | 不参与正常 feature 运行，不承担 phase 完成状态 |
| test/story Case | 提供多种合法需求输入、交互和生命周期场景 | 不向生产规则提供标题、关键词、章节答案或预期 Story 正文 |
| test/story runner | 驱动、观察、隔离和汇总 Case | 不修改生产合同，不代替 Framework 闭环 |

## 8. 实施顺序

### Gate 0：冻结基线与执行边界

1. 固定父版可运行事实、当前故障、既有能力和现有测试结果；
2. 将第 4 节转成实施验收清单；
3. 冻结第 2 节分工，当前执行者不进入三项后续工作。

完成条件：能够分别指出当前执行者、下一模型和 Framework 各自负责什么。

### Gate 1：重建 Story

按 01、05、06 重写材料枚举、输出合同、模型写作指令、scaffold/build、Review 归并和一次性迁移；删除 selector/primary 和相反测试。

完成条件：父版宽容输入恢复；内容守恒、目标结构、人读表达、决定、Review、图片和 Story/Spec 衔接没有回退；旧输入机制在代码和测试中都不存在。

### Gate 2：重建 Knowledge 与 ADAPTATION

按 02 整理三类 Knowledge 和完整目录；本仓 Manifest 默认同时激活两份模式，其他目标仓只列适配后实际启用并确认的 item；共享解析 active 集；重写 Spec、Plan 和下游消费；让 ADAPTATION 自包含但不进入运行时。

完成条件：Story 与工程知识隔离；零模式、复用默认模式和新增模式均可低成本适配；Spec 候选、Plan 选择、`project_knowledge` 和下游消费只有一条链；Coding 不重新通读 Project Facts。

### Gate 3：落地诊断与业务度量合同

按 03 完成 `diagnostics-metrics`、Project Facts 边界、Spec 意图、Plan `observability`、Coding/Review 消费规则及对应 Extension 检查。不得在 Project Facts 中提前声明尚未构建的 Demo API。

完成条件：规则、目标仓事实和单 feature 设计三层分开；合同可由后续 Demo 实现直接消费；当前范围测试通过。

### Gate 4：构造多场景 Story Case

按 04 先盘点现有 Case，再复用或补建最少的一组需求材料，覆盖标准单特性、跨部件、兄弟 AR、交互拆分、补充材料、来源冲突、图片、Review 生命周期、非 AR 起手和同事实不同叙述风格。

完成条件：覆盖矩阵无缺口；Case 使用现有 schema；测试答案不进入 prompt 或生产 Extension；所有 Case 通过静态装载与路径检查。

### Gate 5：当前范围验证与交接

按 04 执行离线回归、Framework 非 Case gate、clean tracked snapshot 和 Case 静态验收，不启动任何 Story CLI Case。完成当前范围报告后，以实际最终文件、接口和测试结果新建 07。

完成条件：当前执行者范围全部通过或如实列出阻塞；07 可让下一模型不重做分析即可开始三项后续工作。

### Gate 6：下一模型完成剩余能力与测试

下一模型严格按 07 依次完成：Demo Logger/VOC/Chart → 多 Case CLI 并行能力 → 全部多 Case 执行与评价。该 Gate 不属于当前执行者的实施范围，但属于整轮优化最终闭环。

## 9. 当前执行者完成定义

当前执行者只有同时满足以下条件才完成交接：

1. 章节输入选择、文件存在即激活、实例路径或目录猜测三个根因从生产路径退出，而不是被 fallback 掩盖；
2. S-01～A-01、C-01、T-01 和已执行阶段的 F-01 有对应代码、自动检查或语义证据；
3. Story 最终结构与 06 一致，模型写作和语义评价与 05 一致，没有业务范文作为隐含真源；
4. 同一版本材料中的有效事实完整且唯一，开放问题只进入 Review，每个原始验收编号独立保留；
5. Manifest 是 Knowledge 唯一 active 清单，本仓默认同时激活两份模式；只有适配到其他工程时才按真实需要调整为 0、1、2 或新增模式，Story 不直接消费工程 Knowledge；
6. 诊断与业务度量合同已经贯通到可实现边界，但未伪造 Demo API 已存在的 Project Facts；
7. 多场景 Case 覆盖矩阵完整，Case 资产可由现有单 Case runner 独立装载；
8. Extension 专用检查、Framework extensions gate、相关阶段闭环和 clean snapshot 在当前范围内通过；
9. 报告明确标注所有 Story CLI 行为证据尚未执行，不以离线通过代替模型行为结论；
10. 当前范围报告与 07 同时交付，清楚列出未完成的三项以及下一模型的执行顺序。

当前执行者不得把“整轮优化已全部完成”写入报告。只有第 10 节也通过后，整轮优化才完成。

## 10. 整轮优化最终完成定义

下一模型完成以下结果后，整轮优化才最终闭环：

1. Demo `Logger.debug`、`VocReporter`、`ChartReporter` 真实实现、导出并通过 lint、编译、故障注入和数据边界测试；
2. 多 Case CLI 复用现有单 Case runner，Story/Spec/Plan 按不同 feature 隔离并行，包含 Coding 的 Case 串行；
3. 现有正式单 Case 和第 4 节 C-01 对应的全部 Case 实际执行，机械与语义结论分轴，逐 Case 和汇总报告完整；
4. 多 Case 失败不通过修改生产标题、关键词、评分标准或 Case 答案补成 PASS；
5. Demo 工程证据、多 Case 证据和 Framework 阶段凭证均可追溯。

- 不新增 Story CLI 命令、phase、状态机、receipt、Trace 或通用知识协议；
- 不把未适配的目标仓 SDK/API、业务名或固定 Case 关键词写进运行规则；
- 不用关键词、标题样例或长度阈值判断人读质量；
- 不为 Case 创建第二套需求真源、产物答案或运行时台账；
- 当前执行者不修改 Demo 产品代码，不实现多 Case CLI，不执行任何 Story CLI 测试；
- 下一模型不得绕过现有 runner、Framework Harness 或阶段闭环另建平行测试系统；
- 不把污染运行、脏工作区文件存在或文档出现某个 ID 当作完成证据。

## 12. 评审入口

正式实施前只需确认：

1. 当前执行者完成全部生产优化、Extension 合同和多场景 Case 资产；

3. 多场景 Case 现在必须构造，不再等待后续人工决定；
4. 07 必须在当前实施结束后按真实状态编写，不能提前复制方案冒充交接结果。
