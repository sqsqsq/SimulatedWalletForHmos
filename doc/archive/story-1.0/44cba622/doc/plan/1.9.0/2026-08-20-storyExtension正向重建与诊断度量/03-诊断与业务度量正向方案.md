# 诊断与业务度量正向方案

> 状态：Extension 合同已实施并通过离线验证；Demo Logger/VOC/Chart 能力尚未构建
> 本文件承接上一轮已确认但尚未落地的日志、VOC、Chart 和 Demo 通用能力。  
> “埋点”是 Coding 中加入观测调用的动作，不与“可观测性”并列为知识类别。

执行分工固定为：当前执行者完成概念、Knowledge、Spec/Plan 合同、Hook、overlay 和确定性检查；下一模型完成 Demo `Logger.debug`、`VocReporter`、`ChartReporter` 的产品代码、导出和工程测试。当前执行者不得用未实现 API 更新 Project Facts 或宣称 Coding/Review 链已闭环。

## 1. 统一概念

本轮使用“诊断与业务度量”统称这组能力：

| 能力 | 渠道 | 回答的问题 | 信息密度 |
|---|---|---|---|
| 本地诊断 | Debug、Info、Error 日志 | 当时执行到哪里，分支、状态和异常是什么 | 最高 |
| 远程诊断 | VOC | 无法取得本地日志时，关键路径、控制位、结果和异常是什么 | 中等 |
| 业务度量 | Chart | 某个真实业务步骤是否成功、耗时多少、结果如何分布 | 最低 |

三者不是同一个点复制三遍：

- 日志覆盖必要诊断检查点；
- VOC 只提炼会改变路径或结果的关键节点；
- Chart 只在业务步骤收敛时记录一次终态结果；
- 在代码中加入上述调用可称为埋点，但埋点不是第四类 Knowledge，也不是新的阶段。

## 2. 与 Knowledge 的关系

诊断与业务度量不直接放进 Story，也不新增 Knowledge 类别。

| 信息 | 所属位置 |
|---|---|
| 跨 feature 的共同规则 | Constraints：`security-privacy.md` 定义受保护数据底线，`diagnostics-metrics.md` 集中失败隔离、触发、VOC 摘要和 Chart 低基数/单次终态规则 |
| 目标仓真实能力 | Project Facts：Logger、VOC、Chart API、运行时开关和失败语义 |
| 单 feature 的业务意图 | Spec/Acceptance：哪条流程需要定位、哪个业务步骤需要统计 |
| 单 feature 的工程设计 | Plan/contracts：flow、step、日志点、VOC、Chart 及字段 |
| 真实调用 | Coding：在合同指定位置调用目标仓真实 API |
| 生效证据 | Review/UT/Testing：diff、编译、失败隔离和可观察行为 |

设计模式与诊断/度量相互独立。模式可以改变流程、角色和状态边界，Plan 再据此选择观测位置；不能因采用某个模式自动生成固定事件。

## 3. 阶段所有权

### 3.1 Story

只有当需求事实本身提出运营、排障或发布保障目标时，Story 才用业务语言说明“为什么需要定位或统计”以及希望看到什么结果。Story 不出现 Logger/VOC/Chart API、事件名、字段表和 rule_id。

### 3.2 Spec

Spec 只定义业务意图，不规划调用点。

诊断意图至少回答：

- 哪条业务流程或失败路径需要定位；
- 哪些路径选择、状态、控制位、结果码或异常会改变最终结果；
- 需要区分哪些可观察结果。

业务度量意图至少回答：

- 哪些真实业务步骤需要统计；
- 每个步骤的成功和失败结果是什么；
- 时延从哪里开始、在哪里结束；
- 统计结果关联哪条验收或运营目标。

Spec 不创建 event name，不规定函数或类名，不以固定事件数量作为完成标准。

### 3.3 Plan

Plan 先完成业务流程和工程设计，再建立最小 `contracts.yaml > observability` 合同。继续使用现有 Extension 字段，不另建事件注册文件。

| 对象 | 必需信息 |
|---|---|
| Flow | `flow_id`、业务目的、入口和结果 |
| Step | `step_id`、业务语义、开始/结束、成功/失败口径 |
| Log point | 所属 flow/step、级别、触发时机、诊断目的、字段和代码落点 |
| VOC event | 所属 flow/step/checkpoint、触发时机、路径/状态/控制/结果摘要、代码落点 |
| Chart event | 所属 flow/step、唯一终态触发、success/error/duration 口径、代码落点 |
| Policy | 数据分级、秘密字段排除、失败隔离和运行时开关 |

引用使用现有 Acceptance/Use Cases ID、contracts 对象 ID 和安全项目相对路径，不建立 typed-reference DSL。

设计顺序固定为：

1. 建立真实业务 flow 和 step；
2. 找到入口、分支、异步、重试、失败和收敛边界；
3. 布置必要 Debug/Info/Error；
4. 从决定路径或结果的关键点提炼 VOC；
5. 在需要统计的业务 step 收敛处布置一次 Chart 终态；
6. 检查数据和失败策略；
7. 将实际对象写入主体设计和 `observability` 合同。

内部重试进入日志和必要 VOC；Chart 等重试最终收敛后只上报一次业务步骤结果。

### 3.4 Coding

Plan 已根据 active Project Facts 和真实源码选定目标仓 API，并把模块、文件、接口和观测对象冻结到 contracts。Coding 不重新通读 Project Facts；它读取冻结合同、实际源码/依赖/类型定义，以及 `project_knowledge` 中已选模式和命中 Constraints，再完成实现：

- 调用位置、触发条件和字段与合同一致；
- flowId、stepId、checkpointId 身份稳定；
- 不为埋点改变业务控制流、返回值或补偿策略；
- Reporter 失败不向业务层传播；
- 新增 `.ets` 文件继续遵守工程逐文件 lint、ArkTS 和跨模块出口规则。

实际源码与合同不一致时回 Plan 修正；目标仓能力事实本身错误时，再由 Plan/ADAPTATION 更新 Project Facts。Coding 不自行换 API 或重做知识选择。

### 3.5 Review、UT 与 Testing

Review 针对真实 diff 核对：

- 合同对象都有实现；
- 日志、VOC、Chart 的密度逐级降低；
- Chart 按业务步骤且只上报一次终态；
- 字段、数据保护和失败隔离成立；
- 内部函数调用没有被误当成业务步骤。

UT 验证上报失败不改变业务结果、终态次数和可观察分支。Testing 只验证设备、系统服务或真实环境相关行为；纯 SDK 接线和内部结构由编译、UT 或 Review 证明，不虚构真机测试。

## 4. 数据边界

沿用上一轮已确认策略：

- Debug 可以记录排障所需的未脱敏业务原值和原始业务结构；
- 凭据、访问令牌、会话秘密和密钥在所有渠道中始终排除；
- Info、Error、VOC、Chart 对受保护业务字段省略或脱敏；
- VOC 只保留路径、状态、控制位、结果和异常摘要，不复制完整业务对象；
- Chart 只保留低基数字段、结果和时延；
- 目标仓运行时开关、留存、频控和 SDK 限制写入 Project Facts，不能由 Demo 常量冒充。

安全与隐私 Constraints 负责秘密字段和受保护数据底线；`diagnostics-metrics.md` 只负责各观测渠道的触发、摘要、基数、终态次数和失败隔离，不重复定义数据等级。

## 5. 下一模型构建的 Demo 通用能力

Demo 建设只为让正式 Case 能推进到 Coding/Review，并使用真实可编译 API。它不是其他目标仓的默认规范。本节是后续构建目标，不是当前执行者的代码范围。

实施范围限定在 `05-SystemBase/CommFunc` 的通用基座和必要出口。

### 5.1 Logger

- 新增 `Logger.debug(tag, format, ...args)`，调用真实 `hilog.debug`；
- 保留现有 `Logger.info`、`Logger.error`；
- 不在 Logger 内建立业务事件模型或自动序列化完整业务对象；
- 调用方按合同选择字段并排除秘密字段。

### 5.2 VocReporter

- 提供强类型 `VocEvent`；
- 提供 `VocReporter.report(event)`；
- 使用目标工程当前可用的 PerformanceAnalysisKit / `hiAppEvent`；
- 正常诊断写入 `wallet_voc / flow_diagnosis`，类型为 `BEHAVIOR`；
- 不可恢复异常写入 `wallet_voc / flow_exception`，类型为 `FAULT`。

`VocEvent` 至少包含 `flowId`、`flowInstanceId`、`checkpointId`、`pathSummary`、`controlSummary`、`state`、`resultCode`、`resultDescription` 和 `exception`。

### 5.3 ChartReporter

- 提供强类型 `ChartEvent`；
- 提供 `ChartReporter.report(event)`；
- 使用 `hiAppEvent` 写入 `wallet_chart / flow_step_result`；
- event type 使用 `STATISTIC`。

`ChartEvent` 固定包含 `flowId`、`stepId`、`success`、`errorCode`、`errorDescription` 和 `durationMs`。

### 5.4 共同语义

- 两个 Reporter 均为非阻塞写入；
- 写入失败只通过 `Logger.error` 留证；
- 失败不向业务调用方传播，不触发业务补偿或重试；
- 三项能力从 CommFunc 正式跨模块出口导出；
- 不新增事件总线、缓存队列、重试中心、采样平台或业务流程封装。

## 6. 工程知识与 ADAPTATION 同步

Demo 能力只有在下一模型完成代码、导出和编译后，才能写入 `project-facts/codebase-capabilities.md`。当前执行者只能保留现有真实能力或明确记录“不存在”，不能提前登记本节目标。后续记录内容必须来自真实实现：

- API 和类型；
- 模块出口、依赖和最低环境；
- hiAppEvent 类型和字段限制；
- 失败语义；
- 至少一个正常使用和一个失败隔离案例。

同轮新增 `constraints/diagnostics-metrics.md`，只写所有 feature 共用的日志/VOC/Chart 底线。某个 feature 的 flow、step、事件名、字段和代码落点只进入 Spec/Plan/contracts，不写回 Knowledge。

ADAPTATION 指导目标仓分别发现 Logger、VOC 和 Chart 的真实能力：

- 能力不同就重写 Project Facts 和 Plan 使用指导；
- 能力不存在就明确记录不存在，由 Plan 设计合法替代或报告阻塞；
- 不复制本仓包名、事件名和类型作为默认答案；
- 只有确认后的 Project Facts/Constraints 才加入 Manifest。

设计模式适配与观测能力适配使用同一发布原则，但不互相绑定。

## 7. 文档同步边界

- `doc/module-catalog.yaml`：CommFunc 新增通用责任和非责任边界；
- `doc/glossary.yaml`：仅在出现确有歧义的新术语时补充；
- `doc/architecture.md`：只有架构影响非 none 时更新；
- `doc/extensions/knowledge/project-facts/codebase-capabilities.md`：记录已编译能力；
- `doc/extensions/knowledge/constraints/diagnostics-metrics.md`：承载跨 feature 的诊断与度量共同规则；

不建立独立埋点规范库、事件中心文档或 Demo 专用设计模式。

## 8. 验收

### 8.1 合同测试

- Spec 只有业务意图时允许，不要求提前出现 API/event name；
- Plan 每个观测对象关联真实 flow/step、目的、触发和代码落点；
- Plan 把选定 API、模块、文件和接口写入冻结合同，Coding 不需要重新通读 Project Facts；
- 连续必经路径可以合并 Info，分支、异步和异常边界保持可诊断；
- VOC 覆盖关键路径与结果，但少于日志；
- Chart 每个需统计业务 step 只有一次终态；
- 事件名或固定数量本身不能让合同通过。

### 8.2 下一模型执行的通用基座测试

- Logger debug/info/error 使用真实 hilog API；
- VocEvent、ChartEvent 是 ArkTS 可用的强类型结构；
- Reporter 为正常和异常事件选择正确 hiAppEvent 类型；
- SDK 写入抛错或返回失败时业务调用方结果不变；
- 秘密字段不默认进入任何事件；
- CommFunc 出口完整，工程 lint/编译通过。

### 8.3 后续 Coding/Review 正式 Case

下一模型先完成通用基座，再选择一条自然包含正常路径、分支、内部重试和异常的正式 Case，串行推进到 Coding/Review，检查：

1. Spec 先表达定位和统计意图；
2. Plan 形成真实 flow/step 和三类合同；
3. Coding 使用 Demo 真实 API，不虚构接口；
4. 日志大于 VOC 大于 Chart 的信息密度和频次成立；
5. Chart 在业务步骤收敛后一次上报；
6. Reporter 失败不改变业务结果；
7. Review 给出真实 diff、编译或测试证据。

该 Case 是 Demo 能力进入真实代码的正式验收。当前执行者只把 Story/Spec/Plan 和合同推进到可实现边界，不执行本节。
