# 规约精简与结构统一 spec（第二轮优化）

> **性质**：`doc/extensions/knowledge/constraints/` 第二轮优化的设计规约。第一轮（04-方案）
> 解决了定位与字段模型；本轮治理它遗留和引入的问题：补丁式描述、啰嗦、结构不一致、
> 机制侧组织混乱，并为全部内容建立人工确认基线（配套 `07-规约人工确认清单.md`）。
> **执行顺序**：本 spec + 07 清单先交人工评审；07 逐项确认完毕后，才按本 spec §2-§4
> 重写规约文件。机制侧改动（§5）移交 W3 会话，本会话不改。

## 1. 问题定性（探索实证，均已定位到行号）

| # | 问题 | 实证规模 |
|---|---|---|
| 1 | **补丁式描述**：条目正文叙述"改了什么/为什么改"而非陈述规则 | 约 20 处——4 条强制力列长括注（"范围收窄…届时回升""不设红线：…"）、TEL-06 出身说明、"回升条件"、README 密集过程语 |
| 2 | **未经人工确认**：第一轮由模型裁决的语义变化与新增内容 | 17 项语义改写 + 3 条新条目 + 56 个出处判定 + 约 25 个 API 断言 + 6 段 README 元规则 |
| 3 | **啰嗦**：信息密度低、重复陈述 | 全目录 402 行；README 119 行（29.6%）零条目；最长单元格 329 字；README↔域文件三组逐句重复；两条元规则全目录说了 3 遍 |
| 4 | **结构不一致** | 表列三套（7/6/5 列）；域级声明四种形态；表后注四种形态；命中条件写法 5 种；applies_when 双源 3 处不一致；权威归属自相矛盾 1 处 |
| 5 | **机制组织**：spec 一套、其他五阶段一套 | spec 专属 `hooks/spec/`（111 行作业指令 + post_check.mjs）vs 五阶段共享根级 19 行指路件；manifest 同一路径抄 5 遍；**ut/testing 有 hook 无 overlay**——矩阵为其声明的 13 个格子无任何 verifier 核对；消费断言测试 3 盲点 |

三个根因，对应三味药：

- **理由与规则同住一格** → 理由收归 README 唯一住所，条目只留规则（§2 写作规范）；
- **列结构不足导致溢出** → 落法细节迁 `## 落法附注`，单元格限长（§2.3）；
- **模型裁决未过人工闸门** → 07 清单全量确认，建立可信基线（§6）。

## 2. 写作规范（对 9 个域文件一次定死；落地后由机械看护钉住）

### 2.1 统一骨架

```
---
name: <slug>
applies_when: <命中面>          ← applies_when 的单一真源
---
# <域名>

<域界定，恰好一句。>

## <背景节>                      ← 可选，至多一个，紧跟域界定
（承载域级资料：模式定义 / 基线值 / 规范 / 异常三分类 / 两列的读法。
 一律 H2 + 表格；UX 现用 blockquote 的覆盖面说明改为此形态并入域界定或背景节。）

## 条目
                                 ← **表前不写任何域级列声明**：列语义归 README 的
                                   条目字段模型，各域不复述（§2.2）
| 条目表 |

## 落法附注                      ← 可选；API 名/代码路径/配置字段级细节按 ID 列出
- **X-nn**：<落法细节>

## 判定附注                      ← 可选；判定易错点与判定边界，统一 bullet
```

### 2.2 单一表制、列语汇统一

**九域同一张表**：`ID | 约束 | 强制力 | 命中条件 | 处置 | 验证（执行体）`
——「处置与落法」列更名「处置」：落法细节全部迁落法附注，列内只留处置结论要求
与一句落法要点（如「色值一律资源化」）。「出处」列已随溯源信息移出。

**收敛过程（三 → 二 → 一）**：本节初版定了三种表制，检查表（COMPAT）与场景表（ENV）
各缺强制力/验证两列，故用 `## 条目` 开头的**域级声明**补。后来 COMPAT 转成条目表，
ENV 随之。域级声明的存在理由因此消失——**列都在表里了，再写一遍就是重复**。

转 ENV 不只是统一格式：场景表的「典型表现」是**描述性**的（「本地状态丢失、凭证失效」），
模型据此答不出「我这个需求命中没有」；条目表的「命中条件」是**可判定**的
（「需求引入本地状态、缓存或凭证」）。ENV 的 `applies_when: always`——每个需求都要过它，
比任何域都更需要可判定。

**列语义的唯一来源是 `constraints/README.md` 的「条目字段模型」，各域不复述。**
判定纪律（怎么判、边界在哪）归各域的 `## 判定附注`，那是内容不是列语义。
由 `test_constraint_style.py::TableSchemaTest` 机械看护（含反例）。

### 2.2.1 落法附注的表达规范（增量原则 + 一行一规则）

单元格限长把细节赶进了 `## 落法附注`，但附注本身没有约束时会长成 API 教程散文——
实证：UX 域一度 5191 字符，是其余八域均值的三倍，占全目录近四分之一。
病根是没回答**「哪些内容值得占规约的位置」**。规约的读者是有平台知识的编码模型，
它缺的不是 ArkUI 教程，是本工程的决策、平台的陷阱和禁令。

**（1）增量原则**——只写模型默认行为会出错的内容。存在性测试：**删掉它，模型会不会写错？**

| 写 | 不写 |
|---|---|
| 工程决策（断点统一 `WidthBreakpoint`、禁自定义阈值） | 通用平台用法（GridRow/mediaquery 怎么注册、`%1$s` 占位符格式） |
| 平台陷阱（`.direction()` 对 Column 不生效、`windowRect` 单位是 px、裸 `accessibilityGroup(true)` 丢状态） | 常规组合（`maxLines`+`textOverflow`、onConfigurationUpdate→AppStorage） |
| 禁令（禁 `setColorMode`、禁 TS 常量色板） | 模型自己会的 SDK 调用（Intl 用法、`accessibilityRole`） |
| 改变动作选择的机制事实（dark 目录存在即视为支持深色） | 枚举值罗列（FoldStatus 四值、MemoryLevel 三级） |

**（2）一行一规则**——附注写成规则行而非段落：每行一条，祈使句，以「禁」「用」「须」开头
或「场景：动作」结构；API 名保留（可 grep）；机制事实压成触发条件从句，不单独解释。

**（3）正反例优先于解释**——需要示范写法差异时，一对 ❌/✅ 单行代码胜过一段文字；
仅在文字说不清时用。

每个 `## 落法附注` 以一句「只列本工程决策与平台易错点，通用用法不赘述」开头，
既是给读者的读法提示，也是给维护者的收敛纪律。

**（4）不写未经证实的否定断言**——**未找到官方出处时，只能不写或标 `<待补充>`，
不得写成否定断言。**「不存在 X」的举证责任高于「存在 X」：要断言不存在，须有官方的
穷举清单为据；检索无果只能得出「未找到」，不能得出「没有」。

这条是同类错误两次复发后立的机制（`AGENTS.md` §7）：
ENV-02 曾写「开关不在 module.json5 里配」而官方明确要求 `abilities[].recoverable: true`；
SEC-03 曾写「`callerBundleName` 不在 want 默认参数」而官方明文由系统自动填充。
两次都是把「我没查到」写成了「它不存在」。

有穷举清单为据的否定可以写——如「没有 `onRestoreState` 回调」，
依据是官方的生命周期回调列表本身就是穷举的。

### 2.3 单元格限长

目标 ≤120 字符，硬上限 160（含标点，落法附注不受限）。超限的处理次序：先删理由（归
README），再迁落法（归落法附注），最后拆句。直接受治的超长格：COMPAT-12 检查项（329）、
SEC-03 处置（318）、DFX-03 处置（317）、ENV-02 兜底（304）、UX-04 约束（220）及次档 6 处。

### 2.4 禁补丁语（条目只陈述现行规则）

以下形态一律不得出现在域文件正文：

1. **变更叙述**："范围收窄""届时回升""由原 X 拆出""从 X 改为 Y"；
2. **理由内嵌**："不设红线：因为…""——这一点今天就验得了"之类论证；
   理由与元规则的**唯一住所是 README**（强制力-执行体绑定、人工不标红线两条已在
   README，域文件的 3 处复述——dfx-baseline 括注、run-modes 表前段、deliverables/
   telemetry 括注——全删）；
3. **状态语混入结构**：列名不带状态（"运行时判定入口（落法待补）"→列名"运行时判定入口"，
   待补状态由格内 `<待补充>` 自身表达）；
4. 条件性规则用中性句式改写而非补丁句式："回升条件：一旦 X 则转为适用"→
   "转为适用的条件：X"。

**保留**的不算补丁语：`<待补充：…>` 空缺登记（README 定义的正式语义）、判定附注里的
易错点（它是规则的操作指引，不是变更史）、TEL-02 缺号的一行中性登记（压缩为
"TEL-02 编号空缺，保留不复用"，删除"原因不可考""拆开后各按…"两句叙述）。

### 2.5 句式统一

- **命中条件**："需求…"正向陈述开头；例外统一句尾"；X 不命中"；裸 `always` 改"任何需求"；
  括注只允许两种：技术定义（如 exported: true 的坐标）与 `<待补充>`。
- **交叉引用**：统一"详见 <域名> X-nn"（如"详见 security-privacy SEC-05"）；
  "不重复判定/不因本行不适用而遗漏"类免责句每处至多一句，不展开论证。
- **执行体标注**：验证列只写**今天有效**的执行体，可组合，制式"模型：…。实机：…"；
  **禁止时间标签**（"实机（二期）"不合法）——未来才生效的验证不进验证列，随背景节的
  `<待补充>` 登记（DFX-01/05 按此改）。
- **外部规范引用**：规范名 + 主题，不写章节号（README 既有规则，UX-01/05 已合规）。

### 2.6 applies_when 单一真源

frontmatter 为准；README 文件清单列对齐修 3 处不一致（UX 补"交互动效"、TEL 用
"业务流程/页面结构/内部逻辑改动"全称、COMPAT 去掉清单侧括注）。

## 6. 与 07 清单的关系

07 是本 spec 的**前置闸门**：§4 的重写只处理"形"（结构/句式/瘦身），07 处理"实"
（每条规约的语义是否成立）。07 中被驳回的条目按批注回滚或修正后，再进入 §4 重写；
两者合并为一次落地，避免规约文件被改两遍。

07 需用户裁决而本 spec 不代答的三个矛盾：权威归属（README:3 vs security-privacy.md:8）、
TEL-05/ENV-05/APP-07 的出处判定、"工程增补须更强举证"元规则本身是否成立。
