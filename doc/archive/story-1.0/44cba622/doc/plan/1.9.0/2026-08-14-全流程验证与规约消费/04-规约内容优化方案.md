## 1. 定位设计：规约究竟是什么

规约目录存在的唯一理由：**有些工程关切是每个需求都必须过问的，不能指望需求作者（AI）
每次自己想起来**。它是跨需求的常驻工程记忆。

一条规约要完整，必须写全需求生命周期的五个字段。不是按"性质"把条目分成"给人看/给 AI 看/
设计约束/编码规则"四类——同一条约束（如深色主题）天然同时有设计声明、编码落法、验收动作
三个环节，分类是表象；**缺的是把环节写全，并声明每个环节由谁执行**：

| 字段 | 回答什么 | 消费者 |
|---|---|---|
| **约束** | 要求是什么 | 全阶段 |
| **命中条件** | 什么需求涉及本条（正向可判；取代现在反写的"例外条件"） | spec 期 AI 判定、人复核 |
| **处置与落法** | spec/plan 须声明什么结论；代码/配置怎么落（HarmonyOS API 级，可为空） | spec/plan/coding 期 AI |
| **验证（执行体）** | 怎么确认做到，执行体四选一：**脚本**（hook 里跑的确定性校验）、**模型**（verifier 按检索式/语义判）、**实机**（ut/testing）、**人工**（流程确认） | review/ut/testing |
| **强制力** | 红线/基线/建议（重定义见下） | 门禁 |

**执行体不是愿望，是有运行位的实体**——声明某执行体前须能指出它今天在哪运行：

| 执行体 | 今天的运行位 | 可用性 |
|---|---|---|
| 模型 | spec 撰写期（hook 注入指引）+ verifier 子 agent 语义复核（工具集 Read/Glob/Grep，**可执行检索式**） | **现有** |
| 实机 | ut / testing 阶段 | 现有（阶段挂载由 W3 补） |
| 人工 | 评审与流程动作，框架只查留痕 | 现有 |
| 脚本 | phase `post_check` hook（范式见 `doc/extensions/hooks/spec/post_check.mjs` 的数值来源回查） | **仅 spec 有；其余阶段待 W3 建** |

因此本方案**现阶段不声明任何"脚本"执行体**：检索式（正则、diff 判据、key 比对）照写——
它是给模型的可操作判据，verifier 用 Grep 就能执行——但执行体标"模型（按条目内检索式执行）"。
W3 把各阶段 post_check 运行位建好后，确有确定性判据的条目再从"模型"升级为"脚本"：
**升级是加强，不返工。**

**强制力重定义——与验证执行体绑定**（"5 条空红线"的根治）：

- **红线** = 验证不过即阻断。**仅当验证执行体真实存在（有运行位）时才可标红线**；执行体
  缺失的部分要么把红线范围收窄到可执行的半截，要么降档并登记待补。
- **基线** = 须给处置结论：可以不做，但必须写理由与补偿，由评审判断是否接受
  （verifier 判"有没有结论"，执行体天然存在）。
- **建议** = 提示，可不做。
- **人工闭环动作（通知运营、翻译回稿、文档归档）执行体=人，框架只能留痕提醒，一律不得标红线。**

当前"判定方法"一列的病即源于此：不同条目该列装的是**不同环节**的东西——UX-01 装的是
验证方法（正则+key 比对），MODE-01 装的是命中条件（"场景含未登录分支"）。拆开后各归其位。
"给人看还是给 AI 看"由字段天然决定；README 适用矩阵的格子从此由条目字段**推导**，
不再是拍脑袋的设想。

## 2. 全局结构改法

### 2.1 通用域表（UX/MODE/SEC/APP/DFX/TEL/DLV 七域）

新列：`ID | 约束 | 强制力 | 命中条件 | 处置与落法 | 验证（执行体） | 出处`

- "例外条件"列取消，**反转并入命中条件**（UX-01 例外"无 UI 变更" → 命中"需求含 UI 新增/改版"）。
- **「出处」列**（取值 `内网基线`/`工程增补`）兑现两个消费方的悬空契约
  （`rules/spec-rules.overlay.yaml:29`、`skills/story/reference/constraint-usage.md:59`——
  两处都要求按"约束文件的出处列"识别工程增补条目，但现在没有任何表有这列）。
  工程增补条目：TEL-05、ENV-05（AI 新增经裁决转正）+ 本轮新增的 APP-07/TEL-06/COMPAT-12。

### 2.2 checklist 域（COMPAT/ENV 两域）——保持清单形态，补域级强制力

两域各行共享同一强制力与验证方式，逐行重复无信息量，改为**表前域级声明**（这同时补齐
01 §5-1 指出的"整表无等级/判定方法列"）：

- **COMPAT**：列改为 `ID | 分类 | 检查项 | 涉及范围 | 本部件适用性 | 出处`。域级声明：
  强制力=基线（命中项须给分析结论与兼容方案，缺结论即评审驳回）；验证=review 期 diff
  逐项过表（模型）+ ut 兼容用例（旧缓存/旧接口）+ testing 升级路径验证。
  **多问条目新规则**（治"六问一票"）：命中的条目须逐问给结论，不得一票带过。
- **ENV**：列改为 `ID | 场景 | 典型表现 | 兜底要求 | 出处`。域级声明：强制力=基线
  （命中场景须声明兜底策略）；验证=ut 环境异常用例 + testing 实机故障注入。

### 2.3 平台化纪律与指针形态

落法字段写 HarmonyOS API 级内容（这是新结构的主要增量）。API 名（SEC-03/04 调用方校验
键名、DFX-03 后台任务形态等）**须经官方文档核实后写入；查不到权威出处的写 `<待补充>`，
不臆造**——与 README 既有的待补语义一致。

**指针形态（P1 修订）**：落法字段指向外部规范时，**只写规范名 + 主题，不写章节号/行号**。
两条理由：① 与 R-1 立的"不写其他文档的内部编号坐标"原则一致，避免方案自违；
② 被指向的 `framework/profiles/hmos-app/skills/coding/templates/coding-standards.md` 是
framework **vendored 发布件**（升级唯一途径是 framework-init UPDATE），上游改版会让章节号
静默指向别处，而没有任何机械看护发现得了——这正是本轮在根治的"文档描述一个不存在的
消费方"同一个病。
正例："hmos-app coding-standards 的资源管理章（字符串/颜色资源化）"；
反例："coding-standards §6.2"。
规约本就是权威（`README.md:3-4`），必要时**内联一句自包含事实**优于指针。

**结论：适配面很窄，且都是措辞级。** 三条设计使然——① 全部 ID 不变、只增不改号；
② 域数恒为 9、applies_when 不变；③ 消费方引用的是**域清单与 ID 体系**，不是条目内文。

### 8.3 plan/coding/review/ut/testing 五阶段

这五个阶段今天**没有任何消费方**（README 矩阵为它们写了维度，但 hook 已随 design-patterns
删除或从未建过）。W3 正在挂 `hooks/constraint-application.md`（一份文件挂五阶段，正文
零域名零维度，只指向适用矩阵）。**内容侧与机制侧在此处零耦合**：本轮修订矩阵格子后，
挂载一旦就位即被自动消费；矩阵格子若改成"—"，W3 的机械断言（非"—"格子须有真实落点）
自动跟随。**新条目的落法字段（HarmonyOS API 级内容）正是为 coding 阶段准备的增量**——
这是九域里除 UX/SEC 外此前几乎空白的部分。

### 8.4 二期：脚本执行体运行位

W3 承诺按 `doc/extensions/hooks/spec/post_check.mjs` 的范式（数值来源回查：标"上游约束"时
读 SR/RR 原文核对数值真实存在）为各阶段建 post_check 运行位，并把机械断言从"矩阵格子→
挂载"延伸到"**条目声明的验证执行体→真实落点**"（脚本=post_check hook / 模型=overlay 或
hook / 实机、人工=豁免）。运行位就位后，内容侧把确有确定性判据的条目从"模型"升为"脚本"
（首批候选 UX-01 色值检索与 key 成对比对、UX-05 硬编码中文、SEC-05 requestPermissions diff）
——**一次列值修订，不返工**。
