> 状态：待审视，尚未实施  
> 日期：2026-08-19  
> 审计对象：提交 `aad670c02ed109eaade1c5f50fea73fcca67ac78`（`临时本地归档1`）  
> 审计范围：该提交的 38 个文件变更、39 个变更路径，以及它实际依赖但未提交的本地配置、SDK 与测试夹具

## 1. 审计结论

本次内网失败不是单个正则或一个标题漏配，而是一条完整的系统性故障链：

1. 把 RR、SR、AR 等外部输入材料误建模成具有固定 Markdown 目录的结构化协议；
2. 把两个本地 Mock 的章节名固化进运行合同和测试断言；
3. `scaffold` 在确认全部输入可用之前就逐个写入章节文件，失败会留下半成品；
4. Spec 生命周期只检查 `story.md`、`review.md` 是否存在，不检查它们是否由当前输入成功装配、是否非空、是否完整；
5. Plan 与设计模式能力又依赖当前未提交工作区里的 Demo 配置、HAR 和包依赖；
6. 测试在同一个脏工作区、同一组 Mock 上全部通过，掩盖了 clean checkout 和真实内网输入下的失败。

因此，当前提交不能作为可移植的 Extension 交付。应直接重建设计边界，淘汰错误的输入格式合同；不通过增加更多标题别名、缺失时回退分支或 Demo 默认值来延续现有模型。

同时，本次变更并非全部无效。Human-First 的 Story 编辑目标、共享阶段 Hook 的组织方式、不同运行时共用 `features_dir` 配置的路径适配器，以及规约/设计模式向下游传递的总体方向可以保留。需要重做的是它们的输入合同、激活边界、失败原子性和验证体系。

## 2. 已确认的故障事实

### 2.1 Story 输入合同与真实输入不一致

`story-chapters.json` 当前有 11 个输出章节、31 项来源输入：

- 30 项被声明为必需；
- 1 项可选；
- 31 项全部依赖 `heading`、`heading_regex` 或 `heading_path`；
- 没有一项采用整篇材料；
- 标题候选来自本地 RR、SR、AR、Spec Mock 的既有章节名。

`story-build.mjs` 又把这些声明解释为强协议：

- 只解析 ATX 风格 H2-H6，H1 不参与匹配；
- 标题、首尾锚定正则和完整标题路径必须精确命中；
- 文件缺失、只有占位内容、纯文本、H1-only、标题换名、编号方式变化或目录层级变化，都会被判为必需来源缺失；
- 任一章节没有可用 primary source，`scaffold` 整体失败；
- `build` 再次执行同一套严格选择。

真实合同恰好相反：RR、SR、AR 是来源材料，不是本 Extension 拥有的结构化产物。它们可以采用任意格式，可以只有标题和占位说明，也可以不存在。Extension 可以理解其内容，但不能规定其章节名。

### 2.2 旧行为被有意识地改成了 fail-closed

父版本在未命中候选章节时，会把整篇文档交给作者自行筛选。本次变更删除了这一行为，并在规则中明确写入“必需来源未命中就修合同或补材料”。

这说明问题不是偶发实现遗漏，而是设计前提错误：把“防止脚本静默选错章节”推导成“输入必须符合脚本预设章节”。正确边界应是脚本不做语义章节选择，来源理解交给模型和语义评审，而不是让真实材料迁就脚本。

### 2.3 `scaffold` 失败会留下半初始化工作区

当前执行顺序为：

1. 先创建 `AR/story-src/chapters/`；
2. 逐章解析来源；
3. 已满足条件的章节立即写盘；
4. 全部章节循环结束后才统一抛出问题；
5. `decisions.json`、`ids.json` 在失败点之后才创建。

因此一次失败可能同时留下：部分章节任务书已存在、登记表不存在、未写章节缺失。再次运行且不加 `--force` 时，已存在章节先被跳过，形成新旧来源状态混合；使用 `--force` 又可能覆盖已经写入的人工内容。当前没有稳定、可解释的恢复语义。

### 2.4 空 `story.md`、`review.md` 能绕过 Spec 生命周期

需要区分两个事实：

- `story-build.mjs scaffold` 本身只创建 `story-src/chapters` 与登记表，不负责创建最终 `story.md`、`review.md`；
- 内网出现的两个空文件，可能由模型的失败兜底、既有残留或其他调用路径创建，不能无证据归因给 `scaffold`。

但 Extension 确实允许它们逃逸：`hooks/spec/post_check.mjs` 对两份文件只执行存在性检查。它没有验证当前 Story build 指纹、章节是否完整、正文是否非空、Review 机器区与状态结构是否成立，也没有复用 `story-build check` 或 `merge-story --check` 的确定性结果。

于是实际链路是：严格来源合同让 `scaffold` 失败，模型随后留下空文件，而只验存在的 Spec Hook 把它们当作产物齐备，阶段继续推进。内网现象与代码机制一致。

即便人工执行 `merge-story --check`，当前检查也主要验证文件存在与若干标识覆盖；Review 缺状态只会显示“状态行缺失”，不会单独形成失败。`story-build check` 能发现缺少构建指纹，但它目前依赖模型按提示手动执行，并未成为 Spec 生命周期的必经机械条件。

### 2.5 Plan Hook 依赖未提交的 Demo 配置

`hooks/plan/post_check.mjs` 无条件要求 `framework.config.json > paths.ui_kit_target_dir` 是非空、位于项目外层目录之下且真实存在。

但提交 `aad670c` 自身的 `framework.config.json` 没有这个字段。该字段只存在于当前未提交工作区，并且值绑定到：

`02-Feature/WalletMain/src/main/ets/maison_ui_kit`

对应测试也固定写入同一路径，所以没有覆盖字段缺失、其他模块或其他工程布局。结果是：即使 Story 问题修复，clean checkout 或内网工程仍会在 Plan post-check 失败。

同一函数还要求 `prd_to_code_traceability.key_files` 的每个路径都以架构外层目录开头。根目录配置文件、包清单或其他合法工程文件并不满足这个假设。路径安全检查与架构归属检查被混成了一条 Demo 工程形状约束。

### 2.6 已激活的设计模式依赖未提交的 Demo SDK

本次提交在 `manifest.yaml` 中直接激活两份模式知识，并在知识文档中使用包名 `framework` 及具体 Builder API。`codebase-facts.md` 同时宣称根目录 `libs/` 存在对应 HAR。

然而：

- `libs/` 不在该提交的 tracked tree 中；
- WalletMain 对 `framework` HAR 的依赖也只存在于未提交工作区；
- `ADAPTATION.md` 又明确说明 Demo SDK 不随 Extension 复制到目标仓。

因此同一交付同时表达了两个互相冲突的状态：运行时把 Demo 模式当作有效知识激活，交付包却不包含支撑这些 API 的 SDK 与依赖事实。当前本地测试实际上借用了脏工作区，而不是验证了提交本身。

### 2.7 “未确认”只是一条说明，不影响运行时激活

`ADAPTATION.md` 将两个模式标为“未确认”，`verify-adaptation.mjs` 默认仍返回 PASS，仅输出 warning；只有人工额外传入 `--require-confirmed` 才失败。Manifest、阶段 Hook 和规则不会读取这个状态，仍会把两份模式知识注入 Spec、Plan、Coding、Review、UT、Testing。

因此“适配状态”和“运行时是否可消费”彼此脱节。未确认的 Demo API 仍可能影响真实设计与编码。

### 2.8 空模式仓与其他类型模式没有被真正支持

当前验证器要求：

- `design-patterns/README.md` 必须能解析出至少一个模式；
- 每份模式都必须包含 SDK 行为事实、结构骨架、使用约定等固定段落；
- Manifest 固定登记当前两份模式文档；
- Spec 固定要求设计模式信号章节；
- Plan Hook 通过扫描目录内所有 Markdown 文件取得 pattern_id，而不是读取真正激活的知识清单。

这会造成两类错误：

1. 目标仓明确不使用任何设计模式时，无法形成合法关闭状态；
2. 目标仓存在非 SDK 型、非当前两类结构的设计模式时，会被当前模板强行解释成 Builder/API 模式。

目录扫描还意味着：即便某份模式未在 Manifest 激活，只要文件仍在目录中，就可能被 Spec/Plan 的机械检查视为在册模式。知识文件“存在”和“已激活”没有分开。

### 2.9 适配验证器验证了文案形状，没有验证可移植性

`verify-adaptation.mjs` 当前主要检查固定词句、固定表格、固定标题及绑定表字段。它没有验证：

- Manifest 激活的知识是否都已确认；
- SDK 包、版本、导出类型与最低环境是否真实存在；
- 包依赖是否属于 tracked tree；
- 模式文档是否仍残留 Demo 类名、模块名、路径或测试编号；
- clean checkout 是否能够独立运行；
- Story 对任意格式、缺失、空白与占位来源是否可用。

所以它可以在核心交付仍不可移植时给出 PASS。该 PASS 只能证明文档长得像预设模板，不能证明目标仓已经适配完成。

### 2.10 测试把两个 Mock 的特征写成了产品协议

当前 `test_story_build.py` 明确：

- 用与合同完全一致的 RR/SR/AR 标题构造夹具；
- 只验证两组 Mock 文件名和章节名能够命中；
- 明确断言 H1 永远不能匹配；
- 明确断言“内容有效但标题无关”时 `scaffold` 必须失败。

Story/Plan 相关离线测试共 52 项可以全部通过，但这恰好证明测试忠实执行了错误合同。它没有覆盖纯文本、自由标题、H1-only、空文件、占位文件、来源缺失、不同语言、不同目录深度和 clean checkout。

此外，整个 `test/` 当前不在提交 `aad670c` 中，属于未跟踪内容。提交既没有带上支撑改动的回归测试，也没有在独立快照里证明自身可运行。

### 2.11 Demo 业务语义进入了通用 Story 编辑合同

章节合同和写作提示中出现了能力占位、模拟数据、管理台放量、真实服务联调、运营交接等当前测试场景高频概念。这些内容有时适用于钱包 Demo，但不是每个需求的必答事实。

当它们进入 `review_focus`、章节说明或固定模板后，模型容易为了满足提示而生成“不涉及”段落、虚构协作项，或把测试用例的叙述方式复制到真实需求。输出目录可以稳定，具体业务问题必须由当前材料决定，不能由 Demo 场景预置。

### 2.12 工程实例硬编码进入通用脚本

除 `ui_kit_target_dir` 外，还存在以下绑定：

- `merge-story.mjs` 用字面量 `05-SystemBase` 过滤术语；目标仓架构层名变化时会得到不同覆盖结果；
- `codebase-facts.md` 把未提交的 `libs/framework-1.0.0.har` 当作仓库事实；
- `ADAPTATION.md` 把 `AR90004` 写成扩展交付的验证证据；
- `merge-story.mjs` 的运行时代码注释保留 `AR90006` 复盘背景；
- 多个规则和证据示例反复使用管理台开关等单一 Demo 语境。

测试编号和复盘解释应留在 `test/story`，工程实例事实应留在可核验的知识层，通用运行脚本只表达稳定机制。

### 2.13 Plan 锚点检查会产生虚假通过

Plan post-check 将自由文本锚点拆成多个 token，只要其中任一 token 在目标产物中出现，就认为锚点可解析。常见英文词、类型片段或泛化实体名可能轻易命中无关内容。

这会让 `project_knowledge` 看起来具备“可解析锚点”，实际却无法唯一定位合同或行为对象。机械检查的能力边界被表述得比实际更强。

### 2.14 文档契约存在维护性退化

已发现两项确定问题：

- `knowledge/constraints/README.md` 把规约增删改说明指向 `ADAPTATION.md §5`，实际对应内容不在该节；
- `component-profile.md` 删除了“部件事实变化改事实文件、不改消费流程规则”的边界说明，却没有在新位置保留等价原则。

第二项不是本次事故的直接触发点，但它削弱了“实例事实与通用机制分离”的维护约束，与本次过拟合根因方向一致。

## 3. 本次提交中可以保留的设计

以下内容未发现与测试用例或 Demo 路径强绑定，可作为重建时的有效基础：

1. `paths.py` 与 `paths.cjs` 分别服务 Python、Node 两个运行时，共同读取 `framework.config.json > paths.features_dir`；这是跨运行时适配，不是双真源。
2. `import_sources.py`、`story_flow.py` 改用同一 `features_dir` 解析规则，方向正确。
3. `hooks/spec/story/` 的目录化和 `on_context_load` 命名与 Manifest 各阶段配置风格一致。
4. 生命周期名称 `on_context_load`、`post_check`、`pre_verifier` 属于 Framework 已支持能力，没有新造 Framework 行为。
5. 共享规约/设计模式提示向 Plan、Coding、Review、UT、Testing 传递的总体阶段边界正确。
6. 设计模式和规约的 phase overlay 大部分通过动态 `pattern_id`、`rule_id` 表达，没有在下游 Hook 内直接写死当前两个模式名。
7. Story 面向人、Spec/Plan/Coding/UT/Testing 面向 AI、Review 面向人的受众划分，以及 Story 的 Human-First 信息架构目标，应继续保留。
8. 本次提交没有修改 `framework/`，正向治理仍可全部在 Extension、测试域和实例配置范围内完成。

保留这些设计不等于保留当前实现。重建时可以删除错误脚本分支、合同字段和测试断言，只保存正确的职责边界与用户价值。

## 5. 引入原因

### 5.1 把输出可控性扩张成输入可控性

Story 的输出目录、章节顺序、登记表和机器区属于 Extension 自己拥有，可以定义结构合同；RR、SR、AR 属于外部事实材料，不受 Extension 控制。本次设计没有守住这条边界，把输出结构的确定性错误地施加到了输入格式上。

### 5.2 用脚本替代了模型应承担的语义工作

“这段材料应进入 Story 哪一章”是语义编辑判断。为了获得确定性，本次把它转成标题匹配，却没有意识到确定性来自 Mock 格式，不来自业务真相。脚本绿灯因此不代表取材正确，脚本红灯也不代表材料无效。

### 5.3 从一次成功样例归纳生产协议

测试先有两套固定 PRD/SE 示例，再反向生成 selector，最后由测试断言 selector 必须命中这些示例。测试验证的是“当前样例能否被当前实现识别”，没有尝试推翻实现对格式、路径、SDK 和配置的假设。

### 5.4 在脏工作区验证提交

Plan Hook、模式文档和代码库事实所需的 `ui_kit_target_dir`、`libs/`、HAR 依赖与测试目录都未进入提交。测试进程从当前工作区读到了它们，于是错误地把本地环境完整性当成提交完整性。

### 5.5 把“存在”误当成“完成”

Story build/check 被写在给模型的命令清单中，但 Spec post-check 只检查最终文件存在。这相当于把关键闭环寄托在模型自觉执行，同时给机械门禁留了一个空文件捷径。

### 5.6 适配说明、运行激活和测试样例没有分层

Demo 文档既作为适配参考，又直接加入运行时 Manifest；“未确认”只写在说明文档，不参与激活；测试又依赖 Demo SDK。参考模型、目标仓事实和运行知识被当成了同一份东西。

### 5.7 缺少变更级反过拟合审查

评审关注了 Story 表达、规约/模式是否回显、单轮 CLI 是否闭环，却没有在提交前逐项回答：

- 这个判断依赖谁拥有的格式；
- 换一份合法输入是否仍成立；
- clean checkout 是否具备同样事实；
- 缺失、占位和失败路径会留下什么；
- 当前测试是在验证通用能力，还是复述 Demo 特征。

## 6. 正向目标设计

### 6.1 建立唯一的输入材料合同

RR、SR、AR、用户补充材料和图片统一视为“可选、无固定格式的事实材料集合”。输入合同只描述以下机械事实：

- 文件是否存在；
- 文件是否可读；
- 文件大小与摘要；
- 是否为空或明显占位；
- 资产链接是否可解析；
- 材料所属来源角色与物理路径。

脚本不根据标题、章节名、表头或关键词判断材料是否有效，也不把缺失、空白或占位升级为 `scaffold` 失败。模型读取所有可用材料，结合当前 Spec 和代码事实完成语义筛选；证据不足时，在 Story 中如实表达已知边界、假设或决策，不伪造上游内容。

来源角色用于帮助作者理解材料背景，不等于章节路由。单个文件可以为多个 Story 章节提供事实，单个章节也可以在某次需求中没有某类上游材料。

### 6.2 让章节合同只定义输出编辑模型

`story-chapters.json` 只保留 Extension 所拥有的 Story 输出设计：

- 章节 id 与人读章名；
- 读者在本章要理解什么；
- 本章拥有的叙述职责；
- 已在前文解释的主题；
- 表达建议；
- 评审重点；
- 可参考的来源角色，仅作提示。

删除 `heading`、`heading_regex`、`heading_path`、必需来源和 primary 命中要求。输出章节仍按 Human-First 阅读顺序稳定生成，章内 H3/H4 由模型根据当前需求复杂度与业务对象自然命名。

这使“Story 目录可控”与“输入格式自由”同时成立，不需要牺牲人读结构。

### 6.3 重建原子且可恢复的 Scaffold

`scaffold` 的正向职责为：

1. 校验自身章节合同与命令参数；
2. 盘点当前可用材料并生成统一来源清单；
3. 在临时工作目录一次性生成完整章节任务书、`decisions.json`、`ids.json` 与来源清单；
4. 全部成功后再发布为一个完整 `story-src`；
5. 发布失败时不留下可被后续流程误认的半成品。

重跑语义明确区分：首次建立、已有完整工作区继续写作、显式重建。正常重跑不会混用旧任务书与新来源状态，也不会隐式覆盖人工正文。

来源缺失或占位属于合法材料状态，记录在来源清单中，不属于事务失败。真正的失败只包括内部合同损坏、参数错误、不可读文件系统和无法完成原子发布。

### 6.4 建立 Story 完成态，而不是文件存在态

Spec post-check 在 Story 场景下复用一个 Extension 内部的确定性 Story 完成检查。完成态至少要求：

- `story-src` 工作区完整；
- 章节集合与当前章节合同一致；
- 每章存在作者正文；
- `decisions.json`、`ids.json` 形状有效；
- `story.md` 具有当前 build 指纹且正文非空；
- `review.md` 具有合法机器区、人工区和状态行；
- Story、Review 与当前 Spec/来源摘要属于同一次装配；
- 图片和本地链接可解析；
- `merge-story` 的确定性守恒检查通过。

Hook 只负责这些机械事实；叙述是否自然、内容是否完整、材料是否被正确理解仍由独立 Verifier 与人工审视。这样既不会让脚本做语义判断，也不会让空文件通过生命周期。

### 6.5 以 Manifest 作为知识激活边界

设计模式和其他工程知识统一区分三层：

1. **参考材料**：供目标仓适配时阅读，可以包含 Demo 示例，但不自动进入运行时；
2. **已适配知识**：已经依据目标仓 Skill、SDK、包元数据和真实案例重写；
3. **运行时激活知识**：明确登记在 `manifest.yaml > provides.knowledge`，阶段 Hook 才能消费。

Spec/Plan 的 pattern catalog 从 Manifest 的实际激活项得出，不再扫描目录。目录中存在参考文档不代表已启用。

Manifest 中没有激活任何模式文档时，模式能力处于合法关闭状态：Spec 不强制生成模式候选章节，Plan 和下游不生成空台账或虚构判断。激活其他 pattern_id 时，各阶段按实际清单动态消费，不要求它一定具有 SDK Builder 或当前两种模式的文档结构。

### 6.6 让适配完成与激活成为同一个交付事实

目标仓适配按以下顺序建立知识：

1. 读取目标仓已有设计模式 Skill；
2. 核对真实 SDK、包元数据、版本与导出；
3. 阅读多个真实业务应用场景；
4. 区分 SDK 强制行为、团队风格和单一案例偶然写法；
5. 重写目标仓模式知识与最小结构示例；
6. 验证依赖和示例在 clean snapshot 中可用；
7. 最后把确认完成的知识加入 Manifest。

目标仓没有模式、暂不希望使用模式或只有其他模式，均通过 Manifest 的实际激活集合自然表达，不引入额外运行状态文件。

`verify-adaptation.mjs` 改为验证交付事实：Manifest 激活项、适配证据、真实依赖、文档引用和 clean snapshot 一致。激活项未确认即失败；未激活参考文档不参与运行验证；空激活集合是合法结果。

### 6.7 清除 Plan 的实例路径假设

Plan post-check 只检查正式 Plan 契约中可机械判定的结构：

- 路径必须是项目根相对路径，且不得越出项目；
- 受控 pattern_id、rule_id 来自实际激活清单；
- Plan 决定与 `project_knowledge` 数量和身份一致；
- 明确 ID 的行为锚点能在 Acceptance/Use Case 中唯一找到；
- 自由文本的设计合理性和符号关联由语义 Verifier 判断。

删除 `ui_kit_target_dir` 这类单一项目目录的通用强制项。具体 UI Kit、模块、HAR、资源或配置路径由当前代码事实与 Plan 合同登记，不在通用 Hook 预设。

对 `key_files` 只做路径安全与存在性检查；架构归属依赖正式模块字段和架构 DSL 判断，不从路径首段猜测文件类别。

### 6.8 分离实例事实、运行机制和测试证据

三类内容按职责落位：

- `doc/extensions` 运行脚本：只包含可迁移机制；
- `doc/extensions/knowledge`：只登记当前 tracked tree 可核验的工程事实；
- `test/story`：保存需求编号、Mock 标题、故障复盘、Demo 夹具和评测证据。

`AR90004`、`AR90006` 等测试编号从交付文档与运行时代码移出。`05-SystemBase` 等架构事实从 DSL 读取。未提交的 HAR、配置和依赖不得写成代码库事实。

对于本地 Demo 模式验证，测试在隔离夹具中显式提供 SDK、依赖与激活后的 Manifest；不能借用开发者工作区里的未跟踪文件。

### 6.9 保持脚本与语义判断的职责边界

机械脚本负责存在性、可读性、JSON/YAML 形状、路径安全、指纹、唯一 ID、引用完整性、装配一致性和失败原子性。

模型与独立 Verifier 负责来源理解、事实归章、模式是否适用、规约是否命中、设计是否合理、Story 是否自然完整。

任何新增门禁先回答“这一结论是否无需理解业务语义即可确定”。不能确定时，不写进脚本阻断；通过 Prompt、知识、语义检查或人工评审完成。

## 7. AGENTS.md 防复发规则设计

本次治理实施时，将以下内容计入项目根 `AGENTS.md` 的全局红线，并在 `test/story/AGENTS.md` 保留详细评测方法。只在本文记录，尚未修改两份文件。

建议加入的全局红线如下：

| 红线 | 判据 |
|---|---|
| 外部材料无格式契约 | RR、SR、AR、用户补充材料可缺失、为空、占位或采用任意格式；运行脚本不得以标题、章节、表头、关键词命中作为流程成功条件 |
| 输入与输出所有权分离 | Extension 可以约束自己生成的合同和产物结构，不得把同一结构要求施加到外部输入材料 |
| 机制与实例分离 | 通用 Hook/脚本不得硬编码需求编号、测试路径、Demo 模块、工程目录、架构层、SDK 包名或类型；实例事实必须来自可核验知识或当前阶段合同 |
| 脚本不做语义裁决 | 事实归章、模式命中、规约适用和设计合理性由模型/Verifier 判断；脚本仅检查无需业务理解即可确定的机械事实 |
| Clean snapshot 交付 | 改动必须在只含 tracked files 的独立快照通过；所需测试、配置、依赖和 SDK 必须与变更共同交付，脏工作区结果不能作为交付凭证 |
| 初始化失败原子性 | scaffold/init 类命令失败后不得留下可被后续阶段视为有效的半成品；完成门禁验证有效内容与当前版本关系，不只检查文件存在 |
| 反过拟合测试 | 每个输入能力必须覆盖自由标题、H1-only、纯文本、空、占位、缺失和至少一种陌生格式；只覆盖 Demo 样例不得宣称通用能力成立 |

落入 `AGENTS.md` 时保持清单式表达；具体样例、测试矩阵和实现解释留在 `test/story/AGENTS.md` 与本方案，不把全局入口改成大篇教程。由于根 `AGENTS.md` 是 Framework 初始化生成的实例文件，实施后还需验证一次正常的 AGENTS 物化流程不会静默丢失这些实例红线；该验证不得通过修改 `framework/` 完成。

以下步骤只在用户确认本方案后执行。

完成标准：任意合法 RR/SR/AR 形态都能建立 Story 工作区，缺失或占位不会使 scaffold 失败。

### Step 3：重建 Scaffold 与完成态

1. 将 scaffold 改为先完整准备、再原子发布；

5. 确保空 Story、空 Review、旧指纹、部分章节和残留任务书均不能闭环。

完成标准：任何失败都不会留下可被下一阶段误判为有效的半成品；成功产物与当前 Spec/来源版本一致。

### Step 4：重建知识激活与目标仓适配

1. 以 Manifest 实际 knowledge 列表定义激活集合；
2. 让 Spec、Plan 和下游只消费激活模式；
3. 支持空模式、其他模式和当前模式三种真实目标仓状态；
4. 将 Demo 模式文档定位为未激活参考，或连同真实依赖一起形成自包含激活包；
5. 重写适配验证器，使其验证依赖、证据、Manifest 和 clean snapshot 一致性。

完成标准：未确认知识不能影响运行；空模式仓合法；不同类型模式不被强制套入当前 SDK 模板。

### Step 5：重建 Plan 机械合同

1. 移除 `ui_kit_target_dir` 与外层目录首段假设；
2. 从 Manifest 与规约清单取得受控 ID；
3. 收紧有正式 ID 的引用检查；
4. 将自由文本符号关联交给语义 Verifier；
5. 保留模式/规约先影响主体设计、再形成 `project_knowledge` 交接的阶段顺序。

完成标准：Plan Hook 在任意合规工程布局上工作，不依赖 Demo 路径，也不以宽松 token 命中冒充引用可解析。

### Step 6：清理实例泄漏与文档契约

1. 从运行脚本和交付指南移出测试编号、Mock 标题和复盘注释；
2. 从架构 DSL/当前事实读取层级，不保留 `05-SystemBase` 字面量判断；
3. 修正 constraints README 的错误章节引用；
4. 恢复“事实变化改知识、机制保持稳定”的维护边界；
5. 清理 `codebase-facts.md` 中不属于 tracked tree 的事实。

完成标准：生产 Extension 全文扫描不再包含测试需求 ID、测试目录、Demo 专用工程路径和未交付 SDK 断言。

### Step 7：补充 AGENTS 与测试域规则

1. 按第 7 节更新根 `AGENTS.md`；
2. 在 `test/story/AGENTS.md` 加入详细反过拟合与 clean snapshot 评测流程；
3. 验证 AGENTS 物化后实例红线仍存在；
4. 不修改 Framework 模板或其他 `framework/` 文件。

完成标准：后续模型在改 Story/Spec 能力前会先看到输入所有权、脚本边界和 clean snapshot 红线。

### Step 8：离线验证

按以下顺序验证，每组通过后再进入下一组：

1. Story 输入形态矩阵；
2. scaffold 原子性与恢复矩阵；
3. Story/Review 完成态与空文件拦截；
4. 图片导入、相对路径和装配保持；
5. 空模式、替代模式、已确认模式三种激活状态；
6. Plan 路径安全、受控 ID 和引用检查；
7. 生产文件 Demo 泄漏扫描；
8. clean snapshot 全量 `test/story` 回归；
9. 原有 Story archive/restore/review/help 和非 Story Spec 流程回归。

完成标准：测试从“复现当前 Demo”转为“证明能力不依赖当前 Demo”。

### Step 9：正式 CLI 验证与报告

离线验证通过后，使用非沙箱 CLI 跑 Story → Spec → Plan；确认知识激活与 Story 闭环稳定后，再按用户届时授权决定是否推进 Coding/Review。

正式用例至少包含：

1. RR/SR/AR 标题完全不同的材料；
2. 一份纯文本或 H1-only 材料；
3. 一份缺失或占位材料；
4. 一份带图片的正式导入材料；
5. 一个自然零模式需求；
6. 一个由真实业务复杂度自然命中已激活模式的需求。

测试结束只提交报告，不依据报告直接修改实现。

## 9. 验收矩阵

| 目标 | 必须通过的证据 |
|---|---|
| 任意格式来源 | 自由标题、H1-only、纯文本均可 scaffold/build，脚本不要求内容章节名 |
| 缺失与占位合法 | RR/SR/AR 任一或多个缺失、空白、占位时仍可建立工作区，并在成文阶段如实处理证据边界 |
| 失败原子 | 人为制造写入/合同错误后，目标目录没有半初始化有效态；修复后可正常重跑 |
| 空产物不逃逸 | 空 `story.md`、空 `review.md`、缺状态、旧指纹、缺章节任一情况均使 Spec post-check 失败 |
| Story 人读目标保留 | 顶层信息架构、自然标题、合理子章节、图表/图片/列表等表达能力与内容守恒继续成立 |

| Plan 不绑 Demo | clean snapshot 无 `ui_kit_target_dir`、无 WalletMain 特定路径时 Plan Hook 仍能正确运行 |
