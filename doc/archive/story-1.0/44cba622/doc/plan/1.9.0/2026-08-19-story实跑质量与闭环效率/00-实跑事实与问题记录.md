## 1. 本轮要回答的问题

本轮不是只看阶段产物中是否出现设计模式或规约名称，而是验证以下能力是否真实生效：

1. Story 是否成为正常人能顺畅阅读、理解和评审的需求文档；
2. Spec 是否只识别与登记设计模式候选，不提前替 Plan 做采用决定；
3. Plan 是否依据需求事实、代码事实和模式文档完成采用或拒绝，并让结论改变主体设计与契约；
4. Coding 与 Review 是否继续消费 Plan 已冻结的工程知识，而不是只回显名称；
5. 图片是否能从正式材料导入链进入 Story，并在最终归档位置保持可打开；
6. 阶段闭环是否在保证质量的同时保持合理效率。

## 3. 已确认事实

### 3.1 Python 与 Node 路径适配器

`doc/extensions/skills/story/scripts/lib/paths.py` 与 `paths.cjs` 读取同一真源：
`framework.config.json > paths.features_dir`。两份文件分别服务 Python 流程脚本与 Node 脚本/Hook，属于
“一份配置规则、两个运行时适配器”，不是两份配置真源。

跨语言一致性测试覆盖正常值、首尾空白、缺项、空值、错误类型、损坏 JSON 和配置文件缺失，当前通过。

仍需纳入设计审视的边界：可替换的数据对接层 `story.js` 仍保留一份独立路径读取逻辑，现有 parity
测试没有覆盖它。因此目前不能宣称全仓只存在两份路径实现，也不能仅凭 parity 测试证明所有入口永不漂移。

### 3.3 当前 Story 的人读质量

当前成品：`doc/features/AR90004/AR/story.md`。

#### 已取得的进步

- 不再出现“评审导读”“待确认事项”；
- 目录按需求概览、范围、整体方案、场景与功能、体验与状态、系统边界、风险、验收与上线、附录推进；
- “本轮价值”“成功标准”“范围与协作边界”等标题已从模型问句转为正常文档标题；
- 当前共有 11 个二级标题、44 个三级标题，章节拆分明显优于上轮；现有小节普遍较短，没有四级标题本身不构成问题；
- 表格、两张 Mermaid 图、图片、列表、引用块和局部强调均已使用，表达形态比单一段落更丰富；
- 正常、身份未完成、状态冲突、响应丢失、中断恢复等路径可被人顺序理解。

#### 尚未达到 Human-First 目标的表现

1. **机器字段进入主叙事**：范围决策块直接出现 `scope_decision`、`carry_all`、`basis`，并把
   “影响范围”写成 Spec 章节和 AC 编号；这些属于流程契约或查询信息，不应污染给人阅读的结论。
2. **规约原句生硬嵌入正文**：`DFX-01`、`ENV-02`、`COMPAT-02`、`DLV-01` 等完整规约句被括号
   插入配置、风险、上线和运营段落。规约虽然可见，却没有转化为自然的业务/工程影响；编号追溯应集中在附录。
3. **仍有模型化措辞和错词**：如“唯一业务锚”“原子检查点”；“卡云适配层按键交付”是明显错词。
4. **存在可压缩重复**：场景总表之后再逐场景复述；“只有云侧确认才算冻结成功”在概览、方案、风险和验收多次出现。
5. **决策块过长**：当前处置混合结论、依据、机器字段、实现细节与验证坐标，不像供评审者快速表态的决策摘要。

独立人读结论：结构和信息组织已合格，但语言自然度、正文纯度与信息经济性尚未完全达到目标。
本轮 Verifier 对 Story 的判定偏宽——它能检查内容存在、结构、一致性和重复，却没有拦住机器信息污染正文与自然语言质量问题。

### 3.5 Plan 初期的模式选择与上游闭环失真

Plan Research 已解包并读取 `libs/framework-1.0.0.har`，确认其中真实导出
`PageInteractionBuilderV3`、`DecisionTreeBuilderV2` 与 `BaseStateMachine`。这证明被测模型会在采用模式前
核对 SDK，而不是只凭模式名称生成决定。

当前第一版选择为：

- 挂失申请页采用 `page-interaction`：单页多交互、业务结果驱动顺序、存在多个用户等待点；
- 挂失提交与幂等再入不采用 `decision-tree`：被判为顺序幂等步骤，不存在补偿/回滚型多级分支。

该选择已经暴露两个需要在 Plan 成品后继续判断的问题：

1. 测试需求原本自然设计了多分支、恢复与失败收敛场景，但 `decision-tree` 仍未采用；需区分是 Spec 将候选单元
   切得过窄、Plan 判断错误、模式文档的命中边界不清，还是该场景确实不该使用该模式；
2. 采用 `page-interaction` 需要 WalletMain 新增本地 HAR 依赖，与已闭环 Spec 的“无依赖变更”冲突。

被测模型随后直接修改了已闭环的 `spec/spec.md` §9.5，并声称“修正三问 Q2 → spec 落点”。工程入口的真实原文是：

> `AGENTS.md:65`：`Q2 需求没变，接口/契约/设计要变？ | plan（plan.md/contracts.yaml；lite=change.md Scope/关键契约）`

因此这是对现有阶段分层规则的明确误读：模式采用带来的设计与依赖决定应由 Plan 承载，不应先反写 Spec。

更严重的是，上游改写后出现了闭环失真：

- Spec 在 17:46:09 修改；
- 最终 Story 仍是 17:32:38 的旧装配件；
- Verifier 报告仍是 17:36:49 的旧语义验证；
- 模型只重跑 Spec Harness，并在 17:46:34 让 `check-receipt` 判定闭环仍有效。

当前磁盘已经存在可直接观察的矛盾：

- `spec/spec.md` 声明 WalletMain 需要新增 `framework` 本地 HAR 依赖；
- `AR/story.md` 仍写“无新增 / 升级依赖”“依赖声明无需变更”，并在 DFX 结论中写“无新增依赖与资源”。

这说明当前闭环机制至少没有可靠绑定以下新鲜度关系：当前 Spec 内容 ↔ 当前 Verifier 报告 ↔ 当前 Story 派生物。
不能把“Harness 重新 PASS + receipt 可校验”解释为上游语义闭环仍然完整。

### 3.6 Plan 中工程知识的实际影响（Verifier 待确认）

当前稳定版 Plan 已通过结构 Harness（33 项、0 FAIL、0 WARN），语义 Verifier 仍在运行。独立审视可确认：

#### `page-interaction` 不是名称回显

采用决定已经实质改变以下设计：

- WalletMain 新增 `framework` HAR 依赖；
- 目录结构新增 `LossReportContext`、`LossReportActions`、`LossReportPageOperates`、
  `LossReportPageInteraction`；
- 页面被约束为只调用 `LossReportPageInteraction.doOperator`，不在回调中直接串业务；
- `contracts.yaml > project_knowledge.pattern_applications` 冻结唯一实例名与合同/行为锚点；
- `use-cases.yaml` 以 `LossReportPageInteraction` 为 coordinator，登记页面动作、业务状态和数据边界；
- Plan 正文明确用户等待点必须先停机，再由新动作恢复。

因此“模式在 Plan 阶段生效并向 Coding 传递”的主路径已经出现，不再只是附加一张采用表。

#### `decision-tree` 的拒绝当前有充分反证

模式文档要求“多个分支，且每个分支本身是多步云侧调用、回滚或补偿等复杂功能”；明确不适用于线性流程、
只有一两步的分支或纯数据判定。Spec 给它的候选单元是“挂失提交与幂等再入”，该单元实际是
提交 → 创建/复用 → 查询结果的顺序幂等步骤，没有补偿链。因此 Plan 的拒绝符合当前模式边界。

这也意味着本次测试需求虽然自然包含多种用户分支，但仍没有形成真正适用 `decision-tree` 的独立复杂流程段；
本轮不能证明 `decision-tree` 被采用后的下游效果。后续测试应通过业务事实构造“每条分支自身均有多步调用、失败收敛与补偿”
的场景，而不是在需求中点名模式。

#### 当前 Plan 契约仍有实质缺口

1. Plan 服务表把 `start` 写成 `start(cardId: string)`，签名代码块与 `contracts.yaml` 又写成
   `start(entry: LossReportEntryParam)`；`LossReportEntryParam` 没有在数据模型或文件规划中定义。
2. 模式要求动作枚举、动作表和上下文进入正式契约。当前三者虽出现在文件清单与字符串锚点中，
   但 `LossReportActions` 未作为 enum 数据模型登记，`LossReportPageOperates` 与 `LossReportContext`
   也没有可消费的结构/接口合同。
3. `use-cases.yaml` 的 `identity_recheck` 在“身份回跳 → 等待风险确认”之后，未登记新的确认动作，
   却继续期望创建申请并到达冻结结果；`checkpoint_recover` 也只触发页面进入，就期望创建/复用申请并查询冻结结果。
   这疑似越过 `page-interaction` 最关键的“等待用户时必须停机”约束。
4. `use-cases.yaml` 没有按模式文档投影 `branches[].user_sequence`，当前使用 triggers 与 phase sequence，
   但不足以明确哪些后继是自动推进、哪些必须由用户动作重新启动。

#### 规约已影响 Plan，但结构化程度不均

- DFX 频次约束已进入 `queryLossEligibility` 的触发说明；
- 安全隐私已影响卡片字段、日志与恢复上下文；
- 兼容性已影响损坏/旧版上下文的清理语义；
- 环境异常已影响幂等键与清除数据后的恢复路径；
- 不适用于 Plan 的 `deliverables` 域被正确排除，没有机械全量复制。

这些结论已进入 `project_knowledge.constraint_obligations` 并带实现/验证锚点，说明规约不只是回显。
但部分义务目前只存在于说明字符串，尚未全部转化为可由下游直接校验的结构字段。需观察 Plan Verifier、Coding 与 Review
是否能识别并补足，而不是把 `project_knowledge` 的存在本身当作已经实现。

#### Plan Verifier 第一轮结果

Plan Verifier 正确发现一个 BLOCKER：`LossReportEntryParam` 未定义，且 `start()` 在 Plan 服务表、
签名代码块、`contracts.yaml` 与 `use-cases.yaml` 之间不一致。结构 Harness 的 33 项全绿没有发现该问题，
语义 Verifier 在这里发挥了必要作用。

Verifier 另报 3 个规约锚点 WARN。被测模型随后作出两类不同性质的处置：

- 正确收窄 `COMPAT-02`：本需求没有新增或修改错误码，COMPAT-02 的命中条件不成立，
  因此不应进入 `constraint_obligations`；这证明 rule_id 会按需求事实筛选，而不是机械全选。
- UX-01 的验证锚点出现“为可解析而挂编号”：模型明确承认 RTL 方向性应由 Testing 真机走查，
  现有 acceptance 没有对应 AC，却准备把 UX-01 挂到 AC-R1，只因锚点必须在 acceptance/use-cases 中解析。
  AC-R1 的核心语义并不是 RTL，因此该做法只能让结构通过，不能证明规约得到验证。

这表明“验证锚点存在”还不足以证明规约实际生效：锚点契约需要能准确表达阶段归属与验证方式，
不能迫使模型把 Testing 义务伪装成一个不相干的 Acceptance ID。

Verifier 没有指出前述身份回跳/检查点恢复后越过用户确认的问题；若后续复验仍未发现，需判为
`page-interaction` 关键运行语义（用户等待点停机/恢复）尚未被 Plan 语义门禁覆盖。

#### Plan 最终闭环与重复收尾

Plan 最终闭环结果：结构 Harness 33 项（31 PASS、0 FAIL、2 SKIP），语义 Verifier 16/16 PASS、
0 WARN，receipt 与 trace 均通过。

第二次 Verifier 已经是 PASS、0 WARN；被测模型仍主动采纳报告中的非阻断参数 token 对齐与拼写建议，
修改后执行第三次完整 Verifier。这与 Spec 阶段在 PASS 后继续追 WARN 的行为一致，证明额外闭环耗时是稳定的
收尾策略问题，不是单次偶发。产物修改后重新验证是正确的；问题在于 PASS 后是否应主动进入新的修改循环。

最终 16/16 PASS 仍未识别身份回跳与检查点恢复分支越过用户确认的语义矛盾，因此不能把 Verifier 全绿解释为
`page-interaction` 的关键等待点合同已经完整。

Plan 完成回执口头汇报还写了“`use-cases.yaml`（10 分支业务用例）”，磁盘实际只有 9 条 branch id。
这不影响机器契约内容，但说明阶段回执中的自然语言摘要仍可能失真，报告审视不能只读模型自述。

### 3.7 Coding 初期的规约执行情况

Coding 已读取 `coding` Skill、ArkTS 易错点、编码规范、profile addendum 与阶段规则，并在写代码前核对了
资源键、路由、Preferences API 和编排 SDK 类型声明。Research First 在输入读取层面表现正常。

但逐文件工具链红线没有实际生效。被测模型明确写道：

> “Since there's no per-file lint CLI wired to shell, I'll self-check each against arkts-pitfalls and existing patterns, then rely on harness compile.”

随后它连续写入常量、多个数据模型、入口参数与卡云适配器，没有执行“写一个文件 → 立刻 ReadLints → 零 error
才写下一个”。这违反 `AGENTS.md` 的宿主 toolchain 红线，也证明：

- 模型读过规约不等于会遵守；
- 当前宿主没有提供可用 ReadLints 时，提示词没有把行为转化为可执行替代合同；
- Hook/门禁没有在第二个文件写入前物理拦截；
- 最终统一编译即使通过，也不能补回逐文件闭环的过程证据。

后续需观察 Coding Harness/Verifier 与 Review 是否会发现并如实记录该过程违例。若均未发现，说明当前规约
观测只覆盖产物结果，尚未覆盖要求中的执行过程。
