# Story 与知识能力分阶段优化总方案

> 状态：阶段一已完成离线验证，等待人工确认；阶段二、三未开始
>
> 依据：AR90005 的 Story、Review、Spec、Plan 产物与门禁记录，以及当前 Extension、Framework 和评测资产的只读对照。

## 一、本轮评测对象

主评测对象是首版 `AR/story.md` 与 `AR/review.md`。知识链只评价“Extension 登记的知识是否被下游按登记消费”，不评价 Plan 本身的通用写作质量。

本轮分三阶段，严格串行：

1. Story 内容丢失与重复；
2. Story 面向人类友好；
3. Extension 知识应用。

每阶段分别实施、验证和报告。上一阶段未经人工确认，不得开始下一阶段。

## 二、问题归因

| 责任层 | 已确认问题 | 本轮处置 |
|---|---|---|
| Story Extension | 章任务书要求完整取材，却又要求“一次只写一章”，模型没有形成可靠的全文编辑轮；开放决定被当成 Story 当前处置；Review 生成 `story.md#...` 链接后又被归档检查判为悬空；Story 装配失败只按 MAJOR 返回 | 阶段一修正 |
| Story 产物 | AR90005 缺页面链、组件、兼容和诊断数据边界；步骤与流程图、交接标识、共享上下文和主流程重复；正常分支被放进异常章节 | 阶段一修正内容守恒与去重，阶段二再处理人读表达 |
| Knowledge Extension | active 知识已进入 Spec/Plan，但选择依据、约束锚点、备份目录证据和真实 Project Facts 绑定仍有问题 | 阶段三处理 |
| Framework | verifier 模板没有可靠要求执行合并后的 Extension 语义检查；`nfr_quantified` 会在没有上游指标时推动模型编造数字 | 本轮只记录与交接，不修改 `framework/`，不在 Extension 自建替代 Framework |
| 评测资产 | 15 个 Case 多数只承载一个窄场景，同一材料和能力被重复起跑；叙述风格变化也被建成三个正式 Case | 阶段一收敛为 4 个组合 Case；纯输入变形改为离线夹具 |
| 被测模型 | 已有规则明确要求完整取材、唯一主叙述和正常/异常分工，AR90005 仍未完成全文复核 | 通过更清楚的写作动作顺序降低波动，不用语义正则代替模型写作 |

## 三、保持不变

- `story-chapters.json` 继续使用 v5 十章合同和 `reading_focus` 软指导。
- 每章继续获得同一轮全部材料，不恢复 selector、标题匹配、来源优先级、`primary/supporting` 或命中门禁。
- Story 不读取 Project Facts、Constraints 或 Patterns。
- Story CLI 命令和生命周期不变，不新增运行时台账、状态机或平行 verifier。
- 不修改 `framework/`。
- 不执行任何 Story CLI 或 Case 实跑。

正式 Case 只保留 `pattern-image-review`、`split-interactive`、`source-conflict-review`、`split-two-ar`。它们由已完成的多 Case 隔离并行 CLI 直接装载；本轮不重建调度能力。

## 五、最终排除项

以下内容不在三个阶段内实施：

1. Demo 的 Log、VOC、Chart 能力；
2. 多 Case CLI 并行测试能力；
3. 任何多 Case 或单 Case Story CLI 实跑。

三个阶段全部经人工确认后，再编写剩余能力构建与测试交接文档，供后续模型实施。
