## 〇、先纠正一个上轮的错误判断

上轮 constraints 整治时判定「上游 story 模板规约不存在」，据此删除了全部出处标注。
**文档存在**——就是用户此次给出的 `story设计模板-鸿蒙-v1.md`（274 行，14 章）。
上轮错在把「仓内找不到」当成了「不存在」。

但两条结论**不因此翻案**：

1. **「本目录就是权威」原则保持**——真实源是早期人工维护的模板，用户已明确「现在要在
   代码仓里维护」。真实源的角色是**一次性核对基准**，不是长期溯源对象；
2. **不恢复逐条出处标注**——核对结果直接落进条目内容（修正/确认/删除），不留
   `source: §x` 机制。每个事实一个权威落点，核对是动作不是状态。

## 二、阶段适用矩阵（问题 1）

**结论：使用范围确实不一样**——不但域不同，同一个域在不同阶段消费的**维度**也不同
（判定回显 / 方案设计 / 代码落实 / 差分检查 / 用例来源 / 实机走查）。现状 README 的
消费方表只有四行一句话，且**漏了 plan 与 ut**。矩阵定稿如下：

| 域 | story/spec（判定回显） | plan（方案约束） | coding（落实） | review（检查） | ut（用例来源） | testing（走查） |
|---|---|---|---|---|---|---|
| UX | ✓ 命中判定 | UI 布局方案（折叠屏/深色） | 资源引用/start-end/string | 检索硬编码 | — | ✓ 深色/大字体/RTL 实机 |
| MODE | ✓ | 模式分支设计 | 分支落实 | 分支覆盖检查 | ✓ 模式矩阵用例 | 实机切模式 |
| SEC | ✓ | 暴露面/权限方案 | 脱敏/权限申请处 | 日志与权限检查 | — | 抽查 |
| APP | ✓ | 生命周期/配置设计 | 启动落点/清理逻辑 | 落点检查 | 备份恢复/登出用例 | 实机 |
| DFX | ✓ | 缓存与频次方案 | 落实 | 调用频次检查 | — | 性能测量 |
| TEL | ✓ | 埋点表设计 | 埋点落实 | 漏埋检查 | 埋点断言 | 报表核对 |
| COMPAT | ✓ | 兼容方案 | — | **diff 视角逐项**（签名/字段/错误码） | 兼容用例（旧缓存/旧接口） | 升级路径 |
| ENV | ✓ | 恢复策略设计 | 防重入/恢复落实 | 检查 | ✓ 环境异常用例 | 实机故障注入 |
| DLV | ✓ | — | — | — | — | 交付走查（翻译回稿/归档） |

**落点设计（守住知识纯度）**：矩阵放 constraints/README.md 的消费方节（README 写阶段名
是允许的——`test_knowledge_purity` 本就要求列出 coding/testing；禁止的是写消费方的
**坐标细节**）。矩阵格子只写「消费维度」一词，怎么消费仍由各阶段自己的文档承载
（spec/story 已有 constraint-usage.md；plan/coding 的 hook 各加一句指引；ut/testing
的用法待其阶段扩展时再写——**不预写没有消费者的用法**）。

真实源 §12「可测试性设计」当前九域完全未覆盖——它不是约束是**方法**，不进 constraints；
记入本轮「不做」，待 ut 阶段扩展时作为其模板输入。

## 三、安卓内容处置（问题 2）

**建议：声明适用范围，不剔除。** 现状 COMPAT 表已是这个形态（「本部件适用性」列，
04/05/06/11 不适用、09 按需），本轮把它明确为**机制**而非个案：

1. **不剔除的理由**：①COMPAT 表与真实源 §11.1 逐行对应，剔除后与源对不上，未来对照
   维护困难；②「不适用」行记录的是「为什么这条对本部件不成立」，删了会有人重新问
   （现状注释已写明这个理由，实证有效）；③用户确认大部分规则鸿蒙安卓通用——整表可
   平移复用到安卓工程，只需改适用性列，剔除则复用时要回头找源；
2. **补的机制**（现状缺）：
   - README 增加「适用性声明」节：本目录约束的**默认适用面是 HarmonyOS 应用**（现状
     已声明）；含安卓语境的条目不删，逐条标「本部件适用性」，判定维度统一为
     **部件形态**（单框架纯鸿蒙 app / 非 SDK 提供方）——行内只引用维度结论，不各自
     发明理由；
   - 「单双」列语义补一句说明（真实源遗产：单框架/双框架发布形态），现状表头无解释，
     读者只能猜；
   - 安卓专名（AndroidManifest.xml、minSdkVersion、@RequiresApi）**保留在不适用行的
     原文里**（对照与复用价值），适用行内若有安卓专名则补鸿蒙对应物。

## 四、正向设计要点（不打补丁的边界）

1. **核对是一次性动作，不是长期机制**：裁决结果直接改条目正文，不引入
   `origin:/source:` 标注（上轮 frontmatter 键集合 `{name, applies_when}` 与
   「条目平权」原则保持，机械测试不放松）；
2. **矩阵只进 README 一处**，各阶段用法文档引用它，不复述（constraints 上轮的
   「README 与回显指引各自演化」教训）；
3. **适用性判定维度单一来源**：部件形态定义将随 [02-部件画像剥离](02-部件画像剥离.md)
   落到 `knowledge/component-profile.md`——COMPAT 适用性列引用部件画像的形态结论，
   不再在行内重复描述「单框架纯鸿蒙…」（P2 与本主线的衔接点）；
4. **机械断言**（实施时新增/调整于 `test_knowledge_purity.py`）：
   - README 含九域×六阶段矩阵且行齐全（域数=文件数）；矩阵节名**避开「使用方法（运行时）」**
     （既有断言 `test_readme_has_no_runtime_usage_section` 禁此节名，矩阵是适用总览不是用法细则）；
   - COMPAT 每行「本部件适用性」非空，且不适用行必须含理由（防止只标结论）；
   - 「单双」列有语义说明；
   - 经裁决删除/修改的条目按裁决结果断言（MODE-04 不存在、SEC-06 含 MaskUtil、
     APP-02/03 无备份配置扫描表述等）；
   - **同步既有断言的过时理由**：`test_no_reference_to_a_nonexistent_upstream_document`
     的 docstring 写着「那份文档不存在」——已被 §〇 纠正。**断言本身保留**（禁 §x 坐标的
     判据不变），理由改写为「真实源仅作一次性核对基准，仓内即权威、不留长期溯源坐标」；
     AGENTS.md 永久踩坑表同名条目的「并不存在」表述同理待修（评测域回填规则：随本轮
     TEST.md 评测确认后一并回流）。
