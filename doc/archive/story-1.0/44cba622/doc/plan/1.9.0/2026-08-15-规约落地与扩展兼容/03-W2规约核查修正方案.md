## 1. env-exceptions.md（3 处，含 1 处实质错误）

- [ ] **1-1〔实质错误〕ENV-02/05 落法附注**

  改前：
  > - 跨异常重启恢复走 `appRecovery`：`UIAbility.onSaveState` 存状态，重启后在 `onCreate` 判 `launchParam.launchReason === LaunchReason.APP_RECOVERY` 再 `restoreWindowStage`。
  > - 开关是 `context.setRestoreEnabled(true)` 或 `appRecovery.enableAppRecovery`，不在 module.json5 里配。

  改后：
  > - **故障恢复**（崩溃后重启）走 `appRecovery`：`module.json5` 的 `abilities[].recoverable: true` 声明可恢复，`AbilityStage.onCreate` 调 `appRecovery.enableAppRecovery(RestartFlag, SaveOccasionFlag, SaveModeFlag)` 使能；`UIAbility.onSaveState` 存状态，重启后在 `onCreate` 判 `launchParam.launchReason === AbilityConstant.LaunchReason.APP_RECOVERY`，从 `want.parameters` 取回数据塞进 `LocalStorage` 再 `this.context.restoreWindowStage(storage)`。
  > - **备份恢复**（进程被 kill、资源管控退出）是另一套机制：`this.context.setRestoreEnabled(true)`，在 `onCreate` 等初始化阶段调用。两者不要混用。
  > - 没有 `onRestoreState` 回调，恢复逻辑一律写在 `onCreate`。

  *「没有 onRestoreState」保留——它有官方穷举清单（回调列表）为据，符合 0-1 的例外条件。*

- [ ] **1-2 ENV-04 落法附注**

  改前：`单调时钟用 systemDateTime.getUptime(TimeType.STARTUP)——含深度睡眠，不受用户改系统时间影响。`

  改后：`单调时钟用 systemDateTime.getUptime(TimeType.STARTUP)（含深度睡眠；TimeType.ACTIVE 不含）。getRealTime / getRealActiveTime 自 API 12 起废弃。`

  *删「不受用户改系统时间影响」——官方无此表述（台账 C4）。*

- [ ] **2-3 SEC-05 权限范围与 reason 要求**

- [ ] **2-4 SEC-03 验证列**

  改前：`模型：检索 module.json5 中 exported: true 的 ability，逐条核对校验方案；有开放无校验即驳回`

  改后：`模型：检索 module.json5 中 abilities 与 extensionAbilities 下 exported: true 的组件，逐条核对校验方案；有开放无校验即驳回`

- [ ] **2-5 SEC-06 日志工具口径**〔第 25 处，**来源性质与前 24 处不同**〕

  前 24 处来自**官方文档核查**；本条来自**用户提供的真实仓事实**——
  真实代码仓的日志入口是 `WalletLog.*`，不是 demo 仓的 `hilog`/`console`/自研 Logger。

  改前（验证列）：
  > `模型：检索 hilog.*、console.* 与自研 Logger 三类日志调用点，核对敏感字段是否经脱敏`

  改后：
  > `模型：检索 WalletLog.* 调用点核对敏感字段是否脱敏；并检索 hilog.*/console.* 直接调用——业务代码不应绕过统一日志封装`

  **兼查绕过的理由**：只查 `WalletLog.*` 会漏掉「绕过封装直接用 `hilog`/`console`
  打印敏感数据」这种违规，而那正是风险更高的一类（既泄敏感数据、又破坏日志统一）。

  **脱敏工具部分不变**——`MaskUtil`（`05-SystemBase/CommFunc`）与
  `CardNumberMaskUtil`（`02-Feature/FinancialCard`）经确认在真实仓同样正确。

  ⚠️ **这条印证了台账 §5.2 的分类**：仓内代码路径属「只能人工确认」，
  demo 仓事实 ≠ 真实仓事实。本次是该分类第一次被真实验证——
  **其余标为「仓内代码事实」的内容都应比照复核**。

  ⚠️ **副作用**：改后检索式在 demo 仓会零命中（demo 用的是 `hilog`）。
  这是可接受的——规约面向真实仓；但 W3 用 SEC-06 验证链路时不能拿「零命中」当通过依据。

  改前：`启动链路指 UIAbility 的 onCreate、onWindowStageCreate（UI 内容加载在后者）与首页组件的 aboutToAppear。`

## 4. dfx-baseline.md（5 处）

- [ ] **4-1 DFX-03 落法附注整体重写**

  改前：
  > - 后台执行按时长与场景选型：短时任务（有配额上限）、长时任务（`backgroundTaskManager.startBackgroundRunning`）、延迟任务（`workScheduler` + `WorkSchedulerExtensionAbility`）。
  > - 长时任务须在 `module.json5` 的 abilities 下声明 `backgroundModes` 并申请 `ohos.permission.KEEP_BACKGROUND_RUNNING`。
  > - 禁自建常驻循环或定时器长跑。

  改后：
  > - 后台能力统一从 `@kit.BackgroundTasksKit` 导入，按时长与场景选型：
  >   - 短时任务：有当日配额上限，完成后主动取消，配额以 `getTransientTaskInfo()` 实测为准；
  >   - 长时任务：`startBackgroundRunning`，须在 `module.json5` 的 abilities 下声明 `backgroundModes` 并申请 `ohos.permission.KEEP_BACKGROUND_RUNNING`；停止用 `stopContinuousTask(context)`，并注册 `on('continuousTaskCancel', cb)` 处理系统侧取消；调用前用 `canIUse('SystemCapability.ResourceSchedule.BackgroundTaskManager.Core')` 守卫；
  >   - 延迟任务：`workScheduler` + `WorkSchedulerExtensionAbility`（`extensionAbilities` 的 `type` 须为 `workScheduler`），`onWorkStop` 在任务 2 分钟超时或 `stopWork` 时触发。
  > - 禁自建常驻循环或定时器长跑——应用退后台后进程被挂起即失去 CPU、网络、GPS、蓝牙访问权，自建长跑不可靠。

  *停止侧与兜底正好服务 DFX-03 条目要求的"退出条件 + 失败兜底"；2 分钟超时是选型决策点。
  配额不落具体数值（官方正文无条款，示例值不作规范）。*
