# W1 兼容性细化方案：让 story 专有内容对非 story 场景隐形

> **上位方案**：`01-W1兼容性核查与方案.md`（核查结论与总体设计在那里）。
> **本文**：按两条裁决细化到可执行，**未改任何文件**。
> **裁决 1**：规约与 story 功能不绑定——即使从 spec 出发，规约也应正常生效。
> **裁决 2**：目录命名用 `constraints-source`。

## 1. 裁决 1 修正了原方案的一处缺陷

原方案打算把 `hooks/spec/on_context_load.md` **整体** gate 掉。但该文件混装三类内容：

| 行 | 内容 | 性质 |
|---|---|---|
| `:3-15` | 上游输入必读清单（AR/RR/SR，**存在时**） | 半通用，已带"存在时"条件 |
| `:17-49` | 本阶段产出三份文档（BLOCKER）+ 四条 story-build 命令 | **story 专有** |
| `:51-67` | spec 是什么（"与最终代码无关的内容不进 spec"） | 通用写作指导 |
| `:69-83` | §9 技术契约（BLOCKER） | 扩展增强，core 模板无此章 |
| `:85-103` | 合规判定三个出口 | **混装**：规约判定通用，但两个出口（story 回显表、决策件）是 story 专有 |
| `:105-118` | 独立审计原则 / 术语表分工 / 数值来源三选一 | 扩展增强的写作红线 |
| `:120` | 闭环下一步提示（强制） | story 专有，且**与原生 SKILL.md 冲突** |

**整体 gate 会连带关掉规约消费**（`:85-103`），与裁决 1 相反。

## 2. 解法：按内容性质拆两份（v2，取代原「整体 gate」）

> **v1 的错误**：§1 的表已经指出该文件**混装三类内容**，v1 却选择「不拆文件、整体 gate」，
> 并辩解「非 story 用户读不到写作指导与写作红线，是完全隐形的应有之义」。
> **混装是病因，开关是掩盖**——这正是本轮 `06-` §3 要治的补丁式解法（违反 G2）。
> 且辩解不成立：通用写作指导对非 story 用户有价值，一起关掉是净损失，不是「应有之义」。

### 2.1 拆分轴

不是「story vs 通用」，而是「**framework 原生能承接的** vs **依赖 story 产物/章节的**」。

| 原行 | 内容 | 依赖 | 归属 |
|---|---|---|---|
| `:3-14` | 上游输入必读清单 | `AR/design.md`（story S4 产物）、RR/SR（story import） | **story 侧** |
| `:17-47` | 三份产物 + story-build 命令 | `AR/story.md`、`AR/review.md`、`story-src/` | **story 侧** |
| `:51-65` | spec 是什么 | 主体无依赖；`:62/:65` 的"去哪"列指向 story 产物 | **拆**：主体通用，出口改写 |
| `:69-81` | §9 技术契约 | core 模板无此章，是扩展新增的**章节结构** | **story 侧**（见 2.2） |
| `:85-101` | 合规判定三出口 | 出口1→spec §7（通用）；出口2→review.md、出口3→story 章（story） | **拆** |
| `:105-116` | 独立审计原则 / 术语表 / 数值来源 | 纯写作红线，不要求新增结构 | **通用侧**（见 2.3） |
| `:120` | 闭环下一步提示 | story 归档链路，且与原生 `SKILL.md:70/99-101` 冲突 | **story 侧** |

### 2.2 §9 归 story 侧的理由

§9 对任何 spec 都有价值，但它是**扩展新增的章节结构**——core 模板没有。
按 `01-` §裁定「非 story 场景下扩展应完全隐形，体验与扩展不存在时逐字相同」，
新增结构要求必须让路。

这与裁决 1（规约不与 story 绑定）不冲突：**§9 是章节结构，规约是内容要求**，两回事。

### 2.3 写作红线归通用侧 —— 拆开后才能看清的一处细节

`01-` §1.3 指出 post_check ④ 会让老用户失败（习惯写"见 §7.1"这类交叉引用）。
v1 的整体开关把**指导和阻断一起关掉**；拆开后可以分别处理：

| 层 | 处置 | 效果 |
|---|---|---|
| `on_context_load` 注入写作红线 | **保留在通用侧** | 老用户看得到建议 |
| `post_check` ④ 强制阻断 | **gate 掉** | 老用户不被硬拦 |

**注入指导 ≠ 硬阻断。** 这是整体开关做不到的区分，也是拆文件相对补丁的真实收益。

### 2.4 落地形态

`manifest.yaml` 的 `spec.on_context_load` 本就是数组（`hooks-dispatcher.ts:167-176`
确认 `.mjs` 返回 `promptFragments` 可用），注册三条：

```yaml
spec:
  on_context_load:
    - hooks/constraint-application.md      # 不动，规约对所有人生效（裁决 1）
    - hooks/spec/on_context_load.md         # 通用侧，瘦身后无条件注入
    - hooks/spec/story_on_context_load.mjs  # story 侧，探针 gate
```

`constraint-application.md` 保持不动——它是纯指路件，正文已写明
「哪些条目该出现在哪份产物的哪个位置，由本阶段自己的规则决定，本文件不重复」，
与本次拆分自洽。

## 3. 四处改动

### 3.1 拆 `hooks/spec/on_context_load.md` 为两份

**通用侧**（原文件瘦身，仍是 `.md`，无条件注入）保留：
「spec 是什么」的主体 + 独立审计原则 + 术语表分工 + 数值来源三选一
+ 合规判定出口 1（产生代码要求 → spec §7 四处）。
三分表的"去哪"列改写：判定结论与决策论证在非 story 场景下**不写进 spec**，
不再指名 story 产物。

**story 侧** 新建 `hooks/spec/story_on_context_load.mjs`，探针未命中即静默让路：

```js
// 契约已验证：hooks-dispatcher.ts:107-133 stdin JSON → stdout JSON；
// :167-176 取 result.promptFragments；payload 含 projectRoot/phase/feature（:23-31）
const ctx = JSON.parse(readFileSync(0, 'utf-8'));
if (ctx?.phase !== 'spec' || !ctx?.feature || !ctx?.projectRoot) { out({}); }
const featureRoot = path.join(ctx.projectRoot, featuresDir(ctx.projectRoot), ctx.feature);
if (!fs.existsSync(path.join(featureRoot, 'AR', 'story-flow.json'))) out({});  // 静默让路
out({ promptFragments: [fs.readFileSync(storyMdPath, 'utf-8')] });
```

正文放同目录 `story_on_context_load.md`（不进 manifest，只被 `.mjs` 读），承载：
上游输入必读清单 + 三份产物 + §9 技术契约 + 合规判定出口 2/3 + 闭环下一步提示。

`featuresDir()` 直接复用 `post_check.mjs:26-35` 的现成实现。

### 3.2 `hooks/spec/post_check.mjs` 三类检查加 gate

> **行号基线：`d780fec`**。该笔提交使本文件从约 480 行增至约 600 行（+150），
> 但三项关键结构与判据形态**全部未变**，故改法一字不改，仅行号重定位。
> 落地前请再次 grep 定位，不要直接用行号。

照 `storyFlowProblems()`（**`:227`**，调用在 **`:471`**）的现成范式，给以下三处套同一判据：

| 检查 | 定位锚点 | gate 后对非 story 场景 |
|---|---|---|
| ① 三份产物齐备 | `PHASE_ARTIFACTS`（**`:191`**），循环在 **`:464`** | 跳过 |
| ③ §9 技术契约 + 五小节 | `SPEC_SECTIONS`（**`:187`**） | 跳过（core 模板本就无 §9） |
| ④ 术语表解释列 / 禁用词 / 禁文档坐标 / 数值来源 | 循环体内，紧随 ①③ | 跳过（老用户写"见 §7.1"不再失败；数值不再被误判"伪造出处"） |

② 已 gate，不动。硬阻断的 `severityOverride: 'BLOCKER'` 现在 **`:594`**，仍在。

**作者侧佐证**：新版 `post_check.mjs:6` 的文件头注释写着——
「§9 技术契约的结构完整性（**core spec 模板未含**，由 `on_context_load.md` 指令驱动 AI 追加）」。
这正是 W1 核查的核心结论：§9 是扩展加的，对只跑原生 spec 的老用户是破坏性的。

### 3.3 `rules/spec-rules.overlay.yaml` 四条补 SKIP

`spec_constraint_echo`、`spec_ext_conclusion_validity`、`story_reader_fitness`、
`story_decision_substance` 补"`AR/story.md` 不存在时 SKIP"，写法照
`upstream_inputs_coverage:97`。

**注意**：`spec_constraint_echo` 查的是 **story 回显表**，不是规约本身——
给它加 SKIP 与裁决 1 不冲突。规约在非 story 场景仍由 `constraint-application.md` 承载。

### 3.4 `hooks/constraint-application.md`：不动

按裁决 1，规约对所有人生效。**唯一可选微调**（次要，可不做）：
`constraints/README.md` 适用矩阵的 story/spec 列现写"命中判定与回显"，
"回显"对非 story 用户无落点。若要更准确可改为"命中判定与结论落位"——
但 hook 正文已说明"落点由本阶段自己的规则决定"，不改也自洽。

## 4. 探针有效性：已验证成立

`skills/story/scripts/story_flow.py` 是 `AR/story-flow.json` 的**唯一写入者**
（文件头第 1 行自述）。三条命令的调用时机（`skills/story/SKILL.md:258-260`）：

| 时机 | 命令 | 阶段 |
|---|---|---|
| 初析完成后 | `story_flow.py round` | **S2**（导入+初析，`SKILL.md:97`）——**文件首次创建** |
| 每次关卡交互后 | `story_flow.py decide` | S3 |
| 生成 design.md 后 | `story_flow.py complete` | S4，置 `status=complete` |

`SKILL.md:426` 自述其为「init→spec 的流程契约：…spec 阶段 post_check 校验其收口」。

**结论：文件在 story 流程的 init 段创建，远早于 spec 阶段。** 两个方向都成立：

- 走过 `/story` 的 feature → 进 spec 时文件已存在且 `status=complete` → 探针命中；
- 未走 `/story` 的 feature → `story_flow.py` 从未运行 → 文件不存在 → 正确判定为非 story。

**额外确认**：`post_check` 现有的 ② 检查会校验 `status=complete` 与末条决策为
`accepted proceed`，故"走了 story 但流程未收口"的中间态已被现有门禁覆盖，不会漏过探针。

## 5. 验证

必须跑**两个方向**，缺一不可：

| # | 场景 | 期望 |
|---|---|---|
| 1 | 只有 `spec/spec.md`、无 `AR/` 的 feature，跑 `harness --phase spec` | **exit 0**；ai-prompt 中**无** story 指令（三份产物、story-build 命令）；ai-prompt 中**有**规约消费指令（constraint-application 的内容） |
| 2 | 完整 story 流程 | 三份产物检查、§9、全文红线**照常生效**——不能把门禁修没了 |
| 3 | 两场景 verifier 报告对比 | 纯 spec 场景无 story 相关 MAJOR FAIL |
| 4 | `pytest test/story` | 全量绿（当前基线 331） |

场景 1 的第三条是**裁决 1 的专项验证**：规约必须仍然生效。

## 6. 顺带修掉的语义冲突

`on_context_load.md:120` 要求模型自行补写并重排下一步（"人工评审 → 归档"为首选），
与原生 `framework/skills/feature/spec/SKILL.md:70`、`:99-101` 的
"只呈现 harness 的 NEXT_STEP 段落，不自行推导或补写跨阶段建议"**直接冲突**。

随 §3.1 的拆分一并解决——该指令归 story 侧，非 story 场景不注入，原生行为恢复。
story 场景保留（那是 story 流程的一部分，且用户已认可该链路）。

## 7. 不做

- 不改 framework（本方案刻意只改扩展侧）；
- 不碰另一会话正在改的 `run_case.py`、`test_harness.py`；
- 不提交 git。
