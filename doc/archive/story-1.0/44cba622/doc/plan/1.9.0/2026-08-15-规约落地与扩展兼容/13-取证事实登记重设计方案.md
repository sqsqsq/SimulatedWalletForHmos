# W13 方案：工程取证事实集中登记——实扫生成、内网可确认、不散落

> 背景：W12 把 evidence-rules 的平台检索式拆成了 `knowledge/codebase-probes.md`。
> Human 三连问逐层击破了它（见 §一）；随后两版替代方案又被 Human 划界修正（见 §二）。
> 本文是收敛后的方案，**未经确认不实施**。

## 一、探针方案的三个病（逐个查实）

| 质疑 | 查实结果 |
|---|---|
| 「像规约的内容」 | **方法混进了画像**：检索范围、输出规则、调用方推定与 evidence-rules 双真相源；五处降级表述让规则反过来转指数据（「用探针给的现状表述」） |
| 「埋点对不上钱包」 | **清单与哪个仓都对不上**：demo 仓 `hiAnalytics`/`hiAppEvent` 零命中，真实形态是 `05-SystemBase/CommFunc/.../shared/log/Logger.ets` 封装 `hilog`，且全仓无埋点。清单不是扫出来的，是 evidence-rules 里的通用猜测原样平移——**手写 API 清单没有看护，必然腐烂** |
| 「module-catalog 能保证吗」 | 三档：必填字段与库模块 `key_exports` 对账是机械保证；`responsibilities` 深度 schema 不保证（本仓恰好写到 hilog，换个模型可能只写「提供日志能力」）；工程配置文件与模块内部符号完全不在 catalog |

## 二、Human 划定的边界（方案按此收敛）

1. **已有框架能力可以依赖；还没实现的不要假设。**
   `module-catalog.yaml`、`architecture.md` 可依赖；**code-graph 不依赖**——
   本仓一个 `code-graph.yaml` 都没生成，内网已确认也没有（它作为远期可选的机械现状源留档于本文，不进实现）。
2. **基于当前工程的信息，像规约一样集中一份文件，内网模型可确认准确性；不要到处散落。**
   否掉「平台常识不落盘 + catalog 缩范围 + 自由检索」的散落式设计。
3. 内网实情（已确认）：有 `architecture.md`；无 `code-graph.yaml`；
   `module-catalog` **只有关键导出、不全**（`MaskUtil` 未登记）。

## 三、设计：`codebase-facts.md`（探针改名重定位）

改名 `codebase-probes.md` → **`codebase-facts.md`**：probes 是「怎么查」，本文件登记的是
「查到了什么」。模式对齐规约（`constraints/`）：

| 规约模式 | 对应到 facts |
|---|---|
| 集中一份、权威在文件 | 六个取证面（对外暴露面/端云/存储/配置/埋点/依赖）的工程事实全在这一份 |
| 条目可确认、修订走评审 | 每面标 `confirmed: 未确认/已确认`；内网模型对照真实仓逐面核对后置已确认 |
| 有机械看护 | 每面二选一：给出**测试可验存在**的仓内位置，或显式声明「本工程无此封装（已核对）」——「没有」和「没查」分开 |

**内容纪律（修病 ①）**：只登记事实——封装叫什么、在哪个模块/文件、底层用什么。
不写检索范围、输出规则、降级表述、产物落点（方法归 evidence-rules）。

**首版实扫（修病 ②）**：不许沿用通用猜测。已核实的 demo 仓事实：

- 埋点：**无埋点封装**——仅日志 `Logger`（`CommFunc/.../shared/log/Logger.ets`，
  封装 `@kit.PerformanceAnalysisKit` 的 `hilog`，`DOMAIN 0xD001000`）；
- 配置：`shared/constant/*Constants.ets` 布尔常量开关；无远程配置封装；
- 依赖：模块级 `oh-package.json5`；CommFunc `dependencies` 为空；
- 端云 / 存储 / 对外暴露面：实施时逐面实扫填写（存储预计「仅 `AppStorage` 内存态」，以实扫为准）。

**事实回灌（修病 ③ 的另一半）**：取证时发现 facts 与代码不符（重构、换封装），
修订 facts 并把该面退回「未确认」——与 AGENTS §7「事故回灌」同源；facts 是活文件。

**复用**：换工程（安卓）由模型实扫目标仓生成首版，再由人/内网确认——与 component-profile
同款「整篇重写」画像；evidence-rules 与脚本零改。

## 四、evidence-rules 的现状取法（方法收口回规则）

§2 开头替换现指向探针的两段，写成三步：

1. **首选**：读 `codebase-facts.md` 对应面——已确认的事实直接用；
2. **facts 未覆盖或存疑**：`module-catalog` 只作**定位线索** → 必须做范围内代码检索 →
   结果回写 facts（含「确无」结论）。**catalog 缺席不构成「无」的证据**（内网实证
   `MaskUtil` 未登记）——「无」只能由检索零命中得出；
3. 零命中的降级表述**完整写在各节「降级」行**（撤掉「用探针给的…」转指），
   结论注明依据（facts 已确认 / 本次实扫）。

各节「现状」只声明查什么类别：网络封装 / 持久化封装与存储键 / 常量与远程配置开关 /
打点封装（**区别于日志封装**）/ 模块依赖声明；对外暴露面 = 平台应用清单的对外可达性 +
路由注册 + catalog `key_exports`。

§1 信息源表：probes 行改 facts 行（「现状的第一落点，未确认面按 §2 实扫回灌」）；
`module-catalog` 行补注「定位线索用；`key_exports` 非全量、`responsibilities` 深度不保证，
缺席不作否定证据」。
