## 2. 正常机制：一份需求，一条设计与业务交付链

```text
系统/本地材料、原图、会议与有效人答
  → 同一需求根的来源登记与采用版本
  → 原生来源物化＋设计前知识输入
  → canonical蓝图与原生质询 → 原生人读投影
  → Story作者自主成文 → Story独审 → 按原权限交业务送审
  → 需要施工时：原生CU准备 → CU Spec → CU Plan → 获准后Coding等阶段
变化 → 现有update比较 → 回最早责任方 → 同步受影响产物 → 必要复核/交付
```

Story可读取尚未准入设计形成诚实草稿，但不能因此绕过原生交付准入或质询。纯业务请求不强造CU；准备CU不自动开始Coding。完整交付与单阶段请求的分流见§5。

### 2.1 目录、身份与来源版本

采用1.x需求根：`doc/features/<需求标识>/`，保`RR/`、`SR/`、`AR/`、`inbox/`、`assets/`、`ux-reference/`等已有职责；其下`blueprint/`与`<change_unit_id>/`同级。蓝图ID直接取需求标识，不再使用独立`bp-<需求>`编号。CU身份/目录继续由原生编码和路径解析取得；示例`wallet-key-sharing`不是通用命名规则。

Framework的`component_id`保留原生含义。首次进入设计，作者沿既有原生component-design读取组件上下文/catalog，确定真实组件身份；随后在同一次正常交接调用`complete --component <原生组件ID> --input <采用输入>`，蓝图ID由需求根确定，先生成来源物化，再开始完整canonical设计。复用现有`checkBinding`的原生身份检查，改名为只读`design-identity`用途，不写绑定状态。已有同根canonical时直接读取其component，传入值若存在须一致；缺真实组件上下文报原生设计缺口，不能默认猜值或先造空canonical过门。组件选择和来源交接是作者动作，不新增用户技术批准；只有原生确需业务决定才按原权限询问。需求状态不再保存`design_binding`。同根canonical提供蓝图/组件身份；CU由原生`component_blueprint_ref`回到该根。需求材料/Story继续用既有`importer.features_dir`和`paths.featureRoot`定位需求根；蓝图经原生blueprint路径，CU及阶段报告经既有`framework-access.mjs`/`flow/native.py`取得原生Feature身份。不凭字符串拼CU路径或扫描两个根配对，也不为普通需求文件读取新增原生进程。

保留`materials/registry.py`的材料登记、原件/图片与摘要，保留`materials/frozen.py`的版本保护和原子落盘。新`design-input.json`只保现有`adopted`和`scope_items`作为唯一采用输入，退出作者填写`human_decision_ids`；脚本从`effective_human_records`导出完整当前有效人答，原话/时刻/来源保持，scope沿既有`HUMAN_RECORD`引用该导出。被替代人答仍留历史，不让作者选择性遗漏仍有效裁决。脚本从该输入及原件生成版本包、`source_ref/source_sha256/provenance/authority`与原生物化，不让模型重填摘要。

`complete`的前提仍是有效范围、人答、必要材料和来源闭合；退出独立`bind-design`和`complete --from <五段提取稿>`。`design-draft.md`可作初析过程材料，但不再要求“五段齐备”才能进入设计，不必再冻结它的同义副本。原始`AR/design.md`与设计实际使用的有效原件仍保留。相同输入复用版本；选择或scope改变、有效人答改变、原件字节改变都产生新版本，不能仅因材料数量没变而复用旧依据。

`input`只在原生物化成功后登记。失败留原错误与已有原件，不把读取失败当空材料；没有新设计消费证据时保“尚未消费”，不更新成成功。旧来源包与引用它的报告不删；旧在途仍按旧版收口或新任务初始化，安装不自动改旧需求数据。

具体动作与消费者见[退场清单](参考/产品适配-生产消费与退场.md)。

## 3. 知识先改变设计，再向CU传递

### 3.1 输入和判断的唯一承载

继续使用manifest激活清单、`activeKnowledge`、`knowledge-task.mjs`与原生phase bindings。项目事实、规约及模式上篇在蓝图动笔前进入作者/审查所需输入；选中模式下篇在Plan及Coding落实时送达。少展示无关知识不等于少读相关原文。原生阶段任务未实际送达时，修输入接线，不新增作者“已读”签字。

复用现有`knowledge-application.schema.json`及`knowledge-application.mjs`，不建知识台账：

| 类型 | 写在哪里 | 消费方式 |
|---|---|---|
| 项目事实 | 原生`discovery.facts[].value.knowledge`及真实来源 | 区分已有/拟建/模拟；事实错回Knowledge真源；CU只取自己引用的事实 |
| 相关规约条目 | 原生`decisions_and_gaps.decisions[]`的`kind:knowledge_application`；原有unit、来源摘要、outcome、target_refs保留 | 适用结论必须对应真实设计对象；实体`must`与验收消费，不能只落声明表 |
| 整个规约文件不适用 | 同一knowledge合同增加`scope:file`分支，`outcome:not_applicable`、来源摘要、空target_refs，无虚构unit；理由在原生rationale | 现有合法知识合同是一文件一域；同域只要存在命中项就走逐项判断，跨域混装本属非法知识，回知识维护者修正。与该来源逐项记录互斥；不变成每CU必抄的公共正文 |
| 模式选择 | 实际业务单元/信号产生候选，既有selected/adjusted/rejected/pending与roles | 退出“激活即必造一条拒绝”；选中角色仍有实体承担。漏选语义由蓝图独审发现，不用脚本猜适用信号 |

相关规约域仍逐项判断；整体不适用不能豁免真实命中项。知识原文/激活发生变化，沿既有摘要与当前性检查回设计重判受影响内容，不自动把新摘要覆盖旧决定。红线与真实业务规约例外的authority保持，它们不是本版退出的Story免审批准。

**决定文字单一来源**：原生decision已有开放字段，renderer读取`conclusion`等原生结论字段。本版将扩展适用结论统一写入`decision.conclusion`，`rationale`只写本需求选择理由；退出私有`knowledge.requirement`的重复正文，更新schema及任务消费者，不双写或保旧字段fallback。实体`must.text`继续说明该实体怎样承担义务，并非复制一份共同结论。真实取舍才写alternatives，不为常规义务造虚假方案。原生renderer仍可能追加逐条表，这是待实测呈现差距，不能靠手改签名投影掩盖。

### 3.2 跨阶段生产与消费

蓝图作者将实际行为、验收和契约实体放进CU `design_refs`引用的设计对象；`acceptance/contracts/use_cases`由原生本阶段投影承接。只把知识ID放在顶层决定而没有承担实体，不算应用。

| 阶段 | 实现安排与读者结果 | 门禁与语义责任 |
|---|---|---|
| Blueprint | 原生设计结构/reader guide组织整体设计；知识进入接口、状态、数据、安全、资源、指标与角色 | 扩展核来源、合法字段和真实地址；原生质询核设计成立、适用及遗漏 |
| CU Spec | `hooks/spec`作者任务保明确的宿主扩展治理项，说明本单位技术契约、规约、模式范围、埋点验收；主体沿原生模板 | `knowledge_rule/knowledge_decision_id`连接可观察验收，脚本核引用，独审核实际行为而非ID相同 |
| CU Plan | `hooks/plan`把`must`落到现有允许实体，把`pattern_roles`落到真实角色，保复用入口、存储/清理、统计点取值与验证责任 | `obligations.mjs`和统计点检查复用；验法按原规约责任，不能一律both；不追加第二套固定尾章 |
| Coding/Review/UT/Testing | 既有任务消费实体义务、角色和模式下篇，验证真实方法调用、资源/上报与指定证据 | 保后续能力和已有回归；此Plan不默认扩大真实运行终点到编码/设备 |

Spec/Plan保1.9.9章节职责及必要编号，原生标题锚点保文字；不由“模板无编号”推导删编号，不新增固定章数产品规则。三条具体检查链使用当前车钥匙目标：身份/草稿保护、页面交互模式、三个流程统计；再用另一合法题材核机制不依赖本例名称和数字。

## 4. Story、Review与审查各负其责

### 4.1 作者和阅读效果

复用`story-chapters.json`、写作计划、`story-write.md`、有界落盘及局部替换，不新建生成器。原规则已正确的先保留，仅修实际缺失/冲突的输入与消费；章节骨架、图清单和机械lint不冒充阅读质量。

作者任务明确：完整Story保用户视角入口、页面、操作、反馈、去向；同节按场景分组；图＞表格＞列表＞章节＞文字；图前短说明、图、图后补充列表，图外条件才补写，不逐箭头复述。正常、受限、中断、结果未知不可混写。正文＋附录分工、必要技术摘要、真实未决和精确值可查保持。标题含各级及加粗小标题，以主题概括内容，退出写作过程提问；改善不等于任意重编号。

Story从原件/人答/蓝图自主组织，不由蓝图拼贴；需改业务设计回canonical，表达错在Story修。Review保原人答、人工区和真实裁决，不生成“文件齐备”“知识批准”问题；原已决定不再问。当前五稿只是对照，正式作者输入不得包含维护金样答案。

### 4.2 两种独审、未审与必要复核

蓝图质询负责设计成立；Story reviewer首读业务完整可读及与设计一致，有疑问再回查原件/原生设计，不重复整套技术证明。`reader-review-task.mjs`和`story-reader`判据沿现有对象/原报告协议收敛任务，不删除必要事实入口。作者不得改报告结论或代写独审。

`hostReviewer()`读真实adapter声明，`independent-review.mjs`在已有prepare/result链上派审或返回`unreviewed`与能力原因。有审查员必须实际执行；缺审查员由同一结果向Story机器区、登记、update和publish披露。删`review_waiver`、批准/撤回命令及逐版重批，不新建“自动批准”状态。对象过期、输入坏、已知FAIL和报告被改不能被未审覆盖；原生强制质询不降级。业务授权允许的工作可以继续，但未审绝不算独审或DSH验收通过。

非阻断建议由作者采纳或有据保留；设计/业务/验收变更做必要重新审查，纯表达调整按原生revalidate条件处理并披露未独立重审。旧PASS和`closure_status:closed`只说明历史，不证明当前无必修、无待核或可发布；具体统一事实读取见§5.2。

独立Story视觉裁定仍从`framework-access.mjs`的`story-review-visual`接入既有原生视觉能力与判据。`image_input:none`不等于看过图；记录未核轴及影响。软视觉披露不能伪造视觉PASS，也不能豁免用户已定必需审查；不得为通过本版新增视觉代理或免审平台。

## 5. 原生阶段与当前完成语义

### 5.1 阶段准备、运行身份和真实边界

独立CU Spec/Plan动笔前沿原生`prepare-blueprint-design --phase spec|plan`：Spec只导出acceptance，Plan导出contracts及适用use-cases；原生runtime已准备时不重复调用。原生`BlueprintProjectionPreparationError`的owner与conflict/stale/invalid照实交回对应责任，保已有合法增量；不造Extension merge/prepare/归一化器。`framework-access.mjs`与`contracts.mjs`继续通过原生SpecLoader和能力解析读取，合法有序calls列表保顺序和重复，不按旧字符串假设漏掉调用。

完整交付使用原生`goal-mode-entry --prepare-run --run-mode attended`取得或恢复已有run，再消费`--next`和`--report-result`原件；Extension作者指令和阶段访问桥传递原生运行身份，不新存第二份run状态/需求快照、不造调度器。仅Spec/Plan请求停在自身终点；已有有效授权沿原生入口传递，不每个命令重新问人。原生内部Goal运行与CLI配置名字不扩Extension到headless/detached。

`contracts.files/modules`及实现位置是预测；`must`、角色、真实业务边界、公共契约和用户明示限制才决定必须满足什么。调整普通实现文件不自动回蓝图重批；蓝图公共设计改变则回原生owner。修`hooks/plan/author.md`、`post_check.mjs`、`shared/obligations.mjs`及`evidence-rules.md`旧白名单说明/消费者，保实际实体和调用验证。

### 5.2 只读当前事实，不另造完成裁决

在既有`framework-access.mjs`增加一个薄的只读当前处置出口，调用N1的`harness/scripts/utils/verify-feature-completion.ts::readCurrentDispositionInput`及`check-disposition.ts::resolveCurrentDisposition`；沿原生scope/workflow确定chain、endpoint和runId，不固定六阶段全跑，不把Plan-only当整Feature完成。完整交付沿原生完成读者的`CleanPassOptions`（实际feature/chain/workflow/scope/run）。无Feature的独立request复用原生`PreparedRequest`及`CurrentRequestDispositionOptions`，保request_sha256/bindings/reportDir；已有CU的单阶段沿原生阶段入口给定的scope和endpoint。不能只传endpoint/phase/runId拼成PreparedRequest，不能拿summary冒充请求绑定；缺必要身份报缺口，不拼造run/summary。

返回原生`completionBlocking/releaseBlocking/disclosed/completionEligible/releaseReady`及原报告定位。`flow/phase_facts.py`、update、状态展示和usage消费同一只读出口：历史closed保留，当前性与资格单列。update只检查本轮受影响且已授权/已有的阶段，不要求完成尚未开始的Coding。原生checker没执行/抛错按其必需性显示wait/verify，不能自动要求作者返修业务。
