## 1. 章前依据（§2）

**`writing-plan.mjs::basisSections`**：

- 每个章、`####`、`#####` 位置各返回一项 `{chapter, at, under, basis, refs}`。
- `basis` 是 `依据：` 或 `依据:` 开头的原文行。
- `refs` 只对 basis 调现有的 `nativeAddresses`。
- 退出了「只有 refs 非空才 push、只返回地址」的旧形态，没有新增解析器，也不读 Markdown。

消费者有两个，同包切换：

| 消费者 | 改后 |
|---|---|
| `chapter.mjs::nextSteps`（skeleton 与 chapter 共用） | 三个分支的 INPUT 都换成同一句 `designInput`：同次 `designSource` 读到的投影路径、蓝图 id 与 revision、`canonical_path`、流程登记的冻结快照、决策登记。写章分支在 RESULT 之后附本章各处的依据原文，规则见下表 |
| `knowledge-task.mjs::storyExpression` | `basisSections(plan).filter(x => x.refs.length)`：没有地址的依据不进任何 CU 片段；有地址的仍走 stableAddressIndex、scope、storySpan 与区间去重 |

写章分支附依据的规则：

- 有地址的按当前蓝图 `stableAddressIndex` 核，不存在就点名缺口。
- 没有地址的标「未登记机器关联」。
- 整章一处都没写，就如实说「没有登记依据——按当前设计与来源写，不等于本章不涉及」。

`designSource` 只多带一个原生已有的字段 `canonical`。

起手分支保留「材料」一项，因为写作设计还没写时作者需要原材料。写章与回看分支退出了泛指的「来源 <合同来源列表>」，换成当前设计与冻结来源。

改后实际输出（`test_story_build.py::TheChapterTaskCarriesItsBasis`，提交「背景」后的接续）：

```
INPUT: 本章草稿 AR/story-src/drafts/02-术语.md（骨架已铺在里面）；AR/story-src/story-template.md 里「02-terms」的骨架；当前 AR/story.md 里已写的章；当前设计投影 doc/features/bp-REQ-DEMO/blueprint/component-blueprint.review.md（蓝图 bp-REQ-DEMO r3，本体 doc/features/bp-REQ-DEMO/blueprint/component-blueprint.yaml）；冻结来源 doc/features/REQ-DEMO/AR/story-src/inputs/…/snapshot.json；决策登记 AR/story-src/decisions.json；方法见 …story-write.md 的「五、照骨架写一章」

  本章依据 （整章）：依据：蓝图 `view:runtime` 与评审会上对等待态的说法
  本章依据 等待态：依据：人签过的等待时长，见决策登记（未登记机器关联）
```

依据行放在 RESULT 之后，原因是现有合同要求首屏前三行固定为 NEXT / INPUT / RESULT（`test_the_first_three_lines_say_what_to_do_next`）。第一次实现放在 INPUT 后面，被这条用例拦下，已改。

脚本没有展开对象全文、没有反查全部决定，也没有建跨章依赖图。chapter 落盘后接续失败时，「已落盘、不要重交」的兜底保持不变。

## 2. 未知与未决的统一表达（§3）

`story-write.md` 第一节原句「Story 只表达**已经成立**的需求和决定；未确认的事项进决策件」与第五节（:258、:354）冲突。现在原位换成一句加一张三行表：运行结果未知、业务选择或验收前提未定、后续施工细节，每类写明「正文写 / 精确依据与选择在哪 / 不写成」。

## 4. 更新、撤回与历史来源（§6，V01）

新增 `test_story_update.py::ASameNamedOriginalGoesThroughTheRealEntries`。只走真实入口：

```
update inputs → 材料关卡 decide → import_sources → update prepare → round → complete → restore / close
```

旧原件按方法页移进 `.backups/local/<名>-<时刻>`。没有手改快照或 origins。探路脚本是 `output/scratch/2.0.4/v01_chain_explore.py`。

**开放轮换同名材料再撤回：**

1. v1 采用并收口后，把旧原件移进备份，导入 v2，complete 冻结出新一版。
2. 第一次 restore 结果是 `restore_conflicted`：design-draft 与 materials.json 列为冲突（「本轮没到完成点，改动没有登记的那一版可比」），现状保留，轮次仍开着。原因是 **complete 不是完成点**，完成点只由 story 登记或 close 写。
3. 人按冲突给出的开轮版本定回去之后，再 restore 得到 `restored`，轮次关掉。
4. 撤回后各项状态：

   | 项 | 状态 |
   |---|---|
   | 冻结输入登记 | 仍是 v2 |
   | 收件箱 | 仍是 v2 |
   | v1 冻结包 | 字节不变 |
   | 路由 | `design_blueprint`，设计须按当前输入同步，不默认旧设计与来源自动恢复 |

**收口后重新采用旧原件：** v1、v2 各收口一轮之后，把 v2 移进备份，从 `.backups/local` 取回 v1 字节，开新一轮导入并 complete。

- 冻结正文与 v1 逐字节相同；
- `origins` 指向收件箱里的这份原件；
- v2 冻结包没被覆盖；
- 两次换版各留一份备份。

冻结目录按内容寻址。内容与 v1 完全相同时，新登记的快照与 v1 落在同一个目录，现有包不覆盖也不重写。

**未覆盖：**

- restore 输出里的 `needs_sync` 在这个夹具里是空的。原因是夹具的 Story 没有走过真实的 `story` 登记（路由起点是 `register_story`），撤回后的同步需求由路由 `design_blueprint` 体现。带已登记 Story 的 needs_sync 要走完审查与登记，离线夹具没有现成入口，没有手造登记。
- 「旧来源仍被设计引用而暂时不可读」的缺口，由 P1 的 `AdoptedSourcesAreReadThroughOneReader`（删文件、改字节）在读取层覆盖，没有在这条 update 链里另造一次。
