## 4. 正向处理顺序

1. **先处理测试宿主容量风险**：实施者交当前实际生效配置与压缩路径证据，核服务约束后给最小配置修正；在后续重新实跑前验证。异常重复发生时由测试宿主按既有异常处置保留证据、明确停止或恢复，不机械连续发送“继续”。不在 Extension 增加重复词探测器，不以本次单词/次数写生产分支。
2. **修授权唯一真源**：送审选择覆盖已展示范围内的归档上传；预检发现新增覆盖冲突、范围变化才重新请人决定。修 SKILL 的停等表与归档段及相关消费者，移除无条件二次授权。保留发布前比对和读回核对；不改变真实写入保护。
3. **修首次产出与整组返修**：按有效决定追踪本次具体遗漏最早发生在设计、成文输入还是作者消费；修对应位置。审查按业务影响评价，不能因无 AC 降级真实需求。对采纳的问题一次处理其实际影响面，减少补一句又引入重复的局部修补。
4. **落实非阻断建议处置**：消费有效报告后先区分必须修正的事实/范围问题与可选表达改善，沿现有记录交付处置；不把“零建议”作为完成条件。未改材料复用当前报告，采纳并改内容后正常失效重审。禁止设固定最大审查轮数或绕过内容变化绑定。
5. **核 CU 正常接续**：用本轮 12:07–12:10 的真实调用还原入口、候选与报错，判断是漏读、接线缺口还是原生入口合同不全，再把问题交正确责任。暂不另建 CU 调度器或自动补 closure 旁路。

以上为责任与处理方向，不授权修改当前测试或全局配置。完整实施合同、实际文件动作与预算在步骤二核定；正常链性能验收须使用同输入、同质量、同终点证据，分别报告人工等待、模型/工具活动、审查和返修。本轮失败不能当作提效基线。

用户追问后重新核对 2.0.4 spec、当前源码及实际派审。此前专项报告找到直接故障和部分缺陷，没有完成整个 2.x 架构正确性的证明；第 4 节不能直接转成追加提示或门禁的实施清单。

### 已证实的更深接缝问题

- `phases/design.md` 已写 warn 可交付、不因建议反复重审；`rules/story-reader-rules.yaml` 已把遗漏有效范围列为阻断。实际审查仍以“没有对应 AC”降级遗漏。说明不是简单缺少这两条规则；再次追加同义要求不能证明改善。必须核规则实际送达、审查任务负担及模型具体判断，分清合同问题与合同执行失败。
- `independent-review.mjs::replyPlace` 明确对“首审、材料变了”不带上下文，仅同一材料的 fail 带 recheck。正常修复通常改变 material_key，因此机制未稳定承接跨版本的原报告与返修背景。旧结论失效与旧发现失去参考价值是两件事，不应混同。
- 本轮安装件确有上述实现；但实际 task prompt 由主模型自行附加上一轮问题和修复摘要，没有原样使用生成的派审载体。因此不能把九轮审查直接归因于“审查者不知道上一轮”；本轮有背景，但来自作者转述。暴露的是产品合同与实际执行不一致、必要交接靠模型临场补齐。后续修正应复用既有原始报告和准备记录，把历史发现作为待核参考、当前材料作为新结论对象，不新建审查账本或直接复用旧通过结论。
- `reader-review-task.mjs::reading` 每轮要求重新读取来源、人签、蓝图和整套交付；同字节附件去重只能减少一次重复读取。当前复用优化解决材料不变时的重入，并未解决实际材料连续变化时的成本。任何审查范围调整必须先保证完整性，不能未经设计就改为只审 diff。
- `review-object.mjs` 枚举全部会议版本原文，再加入当前冻结集合，文件去重按路径而非来源身份。历史证据与当前采用依据的审查范围值得核定；目前没有证据把这点认作本轮九轮返修或输入溢出的直接原因，不先写防御性代码。

### 架构裁定边界

保留原生蓝图作为设计权威、Story/Review 作为整体人读件、CU Spec/Plan 作为施工细化的方向。此次证据尚不足以推翻它，也不足以签收其正常运行机制。2.0.4 回溯已确认的旧职责退出，不能改口成“旧机制都没退”；真正要查的是新接缝是否完整、当前规则是否相互一致、语义是否在反复转述中丢失，以及审查是否被用作主要成文过程。

后续整体评审按“来源中的业务要求 → 当前蓝图落点 → 作者实际输入 → 首稿 → 审查发现 → 修复 → CU 承担”逐条追踪本轮真实问题。每项只有定位最早错误变换、明确现有责任为何未生效、列出替换而非叠加的实现，并能以其他合法业务验证，才进入实施合同。模型重复生成的底层原因、CU 接续的公开入口充分性仍保留未知；不把现场临时脚本直接产品化。
