# P3 正常需求的执行效率

需求：[R3](../../../spec/2.0.3/03-需求执行效率/需求.md)。不以减少事实、删审查或放松 gate 换性能，不另建统计平台。

## 对照基线

选 P1 审定输入和已验证的实际源版本，固定需求终点与模型/宿主条件；保留已有 2.0.1/2.0.2 实跑作问题证据，不把不同输入/终点的历史耗时直接当性能对照。初段、update、蓝图准备和各 CU 分开；原始事件、子任务回复、实际读取范围及用量记录进入现有 output/story。

## 已定实现动作

**状态检查不返回整份设计正文。** 在现有 `framework-access.mjs` CLI 的 action=blueprint 增加布尔 `--summary`：仍执行同一原生读取与校验，返回同一 status、identity/ref、admitted、issues、projection、units、consumption，省略唯一的大字段 blueprint。默认输出和导出 readBlueprint 函数不变；其他 action 带此参数报参数错误。成功/失败退出码保持原合同，未知/过期不能因摘要变 PASS。`phases/design.md` 的状态核对及帮助示例使用此标志；真正设计/质询/成文继续读权威内容。内部 Python/JS 需要 blueprint 的消费者不得切到摘要，测试核元信息等价和错误保持。

**相同原生投影不要求独立审查者全文读两次。** `reader-review-task.mjs` 的索引保留 canonical、原生投影、设计附件的实际路径；只有原生投影与 design-review 字节一致已由现行定稿核实，才注明它们是同内容的两个位置、完整阅读 design-review 一次即可。canonical 内容不同，仍按必要范围读取；不同正文或来源不做相似度去重。reviewObject/materialKey 仍绑定全部实际文件，任何一个变化继续失效。退出现行读法里“先读原生投影、再通读同一设计附件”的重复指令，不新增读取状态或缓存。

**消除任务中的重复规则。** 与 P2 同步由 chapter questions 与 semantic_checks 各承担自己的事实；同一个判据正文只装配一次，会议/决定/图片的本次数据仍保留，不删必要原文。knowledge-task 的具体义务与相关完整知识保留；已在 2.0.2 实施的排序/verifyChoices 不重写。

**同决定修复不反复逐文件碰撞。** 沿 P2 的当前 update-notes/设计处置与既有差异读取，一次处理已经识别的影响；没有新信息不为跑次数而重审。维持实际对象变化后的必要独立审查，不用固定重试次数截停。

宿主容量处理不纳入产品机制。本版保留实际模型/配置，先核真实压缩规则，需改个人配置时交用户明确决定；不把一次错误上限写入工具或自动切模型。必要配置未成立则对应实跑暂停，其他代码/文档工作继续。

## 首次送达、错误恢复与任务规模

历史reopen冲突、终检过晚、218条裁决、ts-node堆栈是调查入口，不直接成为现行实现需求。当前独立审查结果由independent-review的check、登记、delivery共同消费；reader-review-task已禁止一般逐材料打勾，open议题及会议话题仍逐项核。保持这些现行出口，退出仅讲旧report-disposition落点的指路。

| 当前动作 | 输入与检查位置 | 预期输出和恢复 | 验证 |
|---|---|---|---|
| 成文交付前发现问题 | story-build现有check/prepare/delivery、phases/design与update | 作者实际得到缺口位置、未满足条件和下一动作；返回前不写交付成功。修复后沿同一入口重试，不靠run结束后维护报告提醒 | test_verifier_report_protocol/test_story_update中缺报告、来源漂移、坏报告、未同步更新的现有负例核CLI输出及无错误完成副作用 |
| 输入/依赖不可用 | framework-access CLI、story-build现有入口；缺项目根、读不到来源、原生模块加载失败各取一例 | 输出动作、实际路径/依赖、原始原因及可执行恢复方向；保留非零退出码，不自动安装、不吞异常、不伪装无业务缺口 | test_knowledge_task/test_story_build的入口负例；缺简明诊断才在最外入口补上下文，不给每层套catch |
| 任务过大 | writer逐章入口、reader-review-task和原始材料索引 | 沿现有章级写入、文件范围读取；维护一份任务及完整材料身份。普通材料不增加逐条裁决表，会议/open议题不因数量大丢项 | 用现有任务夹具扩展多个材料/话题和不同长度，核集合完整、规则只装配一次；实际模型是否完整读取在授权CLI事件与报告核 |
| update/reopen | 现有flow及update作者页 | 纯表达不升设计revision；范围变化走现有reopen；恢复只处理自有工作件；同材料复用与变更失效维持 | 复用test_story_update/test_flow_status_client对应场景，不新增平行恢复状态 |

实施者先跑现有输入确认是否已有诊断；若成立，交回位置与结果，不为了历史问题重复实现。仅缺失的入口诊断属于本包局部修正；原生加载器/阶段职责的问题给上游，不新增缓存、分批调度器、固定重试上限或自动压缩机制。新的语义大任务须出现当前证据才另行设计，不能因历史218条直接加分页平台。

历史30–90分钟和41%首轮通过率仅作背景，不用作本版签收门槛。按本轮同一Case输入版本、源版本与终点配对；新立场改变输入后重定对照，不把旧失败运行混作改善基线。

## 实际效率的验证链

交回每项措施的实际消费者与正常路径：首次任务取得必要信息，减少反复找规则/补来源；同决定一次修全已知影响；同材料复用、变化失效；大材料范围读取不漏事实/话题；失败时取得对象、原因和恢复动作。用当前会话事件与产物说明有效调用和重复调用的原因，不新加运行遥测或消费方自证字段。

首次产出质量、独立审查真实效果与重复返修不能由装配测试代签。配对时同时检查R1最佳结果和R4通用性，达到相同质量后才比较成本。P1目标稿应先明确并评审，独立且有证据支持的机制返修可并行，不为等待金样恢复完整运行现场。

## 验收与失败

结构/重复读取的确定性改动先跑实际受影响组；真实性能改善必须在用户授权的正常 Case 中观察。沿 TEST/measure_run 当前可信口径，未知统计不改成零；一份报告不是一次成文，N份报告也不是N−1次返修。

质量仍须符合 P1/P2。给出前后 token、有效处理时间、人工操作、错误与修复内容，提升一项但增加另一项应一并披露。未到相同业务终点、语义不合格、不同环境或样本不足时仅报告事实，不宣告改善。

具体签收采用规格 R3 §3：质量过门后同条件配对，token 与有效处理时间均不增加且至少一项下降、人工操作不增；一升一降只记局部收益。至少一组有效配对且两个 Case 到授权终点才签本版效率目标。

交回新增/退出、对照条件与实际收益；缺原生阶段/宿主能力则停受影响路径，保留其他独立结果。不因追求成本目标硬设最大返修次数或正文长度。
