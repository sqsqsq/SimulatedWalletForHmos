# P1 两 Case 的期望结果金样

需求：[R1](../../../spec/2.0.3/01-两Case金样与质量基线/需求.md)及其 G01–G09 修订合同；金样范围与执行边界按 [05 金样职责修正与执行合同](05-金样职责修正与执行合同.md)。本步不改生产机制或正式金样，交可供人评估的期望结果候选。

## 输入与产出

输入：Case 原始材料与宿主立场（交互脚本、答案卷、`case.yaml` 探针说明）、目标工程与知识、历史候选与 10-03 实跑产物（只作表达起点与缺陷线索）。采用版本见 R1 §2.1；2026-10-09 补齐的宿主立场按 `test/EVOLUTION.md` §7 记账。

候选放 `实施反馈/金样候选/<case>/<情景>/`，五个情景与目标产物：

| 情景 | 目标产物 |
|---|---|
| auto-topup/initial、auto-topup/update、car-key-sharing/reviewable | `AR/story.md`、`AR/review.md`、`assets/` 配图 |
| car-key-sharing/plan-ready | 上述三项，加施工单位的 `spec/spec.md`、`plan/plan.md` |
| car-key-sharing/update | 更新后的 Story、Review，以及本次变更影响的已有 Spec、Plan；配图 |

每组带简短 README：采用输入版本与摘要、情景终点、有效宿主立场、必要设计选择、配图来源。候选只保存目标 Markdown 与配图，不附带蓝图、决定登记、章草稿、流程记录、指纹、准入或质询状态；附录直接写完整期望内容。

## 编写与优化次序

最佳形态按规格R1 §4.1维护，P1消费该标准，不另立一份模板。旧稿是取材起点，不是结构上限；修完G01–G09并不等于达到最佳结果。

1. 核Case原件、工程与立场，校正事实、决定及跨产物关系；完成本轮待接受入口、收回状态、撤销条件等已发现缺口。按真实业务关系检查其他位置，不只修样例句。
2. 优化叙事顺序、段落、表格和图文配合。Story自己讲完整体关系，Spec/Plan把本CU行为与实现接起来；删无信息增量重复，必要验收条件保留。
3. 补完整附录与真实来源链接，配图情景内可读。接口细节不挤占正文，关键业务约束不被摘要藏掉。
4. 独立通读完整产物，以R1的读者目标说明具体前后优化；再交独立内容评价与用户审定。缺点被修正和表达变好分别举实际位置，不用篇幅/表数推定效果。

需要回答的问题按Case立场处理，缺测试输入交设计者；真实仍未定事项保持未决。五个情景不变，必要的额外表达短例只放现有README，标清适用条件，不虚构本Case业务或再建完整需求。

## 交回与推进

交回给出目标产物入口、内容改动及依据、保持项与剩余问题。独立内容评价的输入是原始依据、目标稿与效果判据，不要求先造生产状态；模型调用沿既有授权边界。用户审定具体候选的效果。

P1 完成条件：目标文档达到R1 §4.1的最佳形态与读者目标，业务有据、跨件一致；交具体表达改善及完整通读结论，没有因运行状态造成的内容空缺。这证明期望结果已明确，不证明产品已能产出它；产品能力由专项回归与授权的真实 CLI 证明。

## 正本落点

用户审定后，正式正本按 `test/golden/<case>/<情景>/` 组织：Story/Review 在 AR 下，Spec/Plan 保留能明确所属施工单位的目录，配图用情景内相对链接，带同样的简短 README。原始输入仍在 `test/cases/`，不复制整套输入到金样。切换与消费者迁移见 [P4](04-步骤4-综合验证与切换.md)。
