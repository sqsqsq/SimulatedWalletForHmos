# P2 产物表达与独立审查效果

需求：[R2](../../../spec/2.0.3/02-产物内容与独立审查/需求.md)。输入为 P1 审定差异、当前实际机制与必要预算，不能凭历史样例错误预设产品仍有同一缺陷。

## 处理责任

| 真实差距 | 现有落点 | 应有结果 |
|---|---|---|
| 决定在不同产物变义 | Story 的 design/update 作者流程、蓝图实际决定与审查 | 回最早权威修完整影响面，不只把正文改绿 |
| 人读件难以评估 | story-chapters、story-write、作者写作设计/摘要 | Story 讲清业务全貌，Review 给可决定的争议，技术附件可查，CU 文档能判断局部实现 |
| 审查受作者结论影响 | 当前 reader-review-task / story-reader-rules 与既有 dispatch | 主执行者交真实材料/客观变化，独立审查自行判断；原始回复不由作者加工 |
| 知识只回显或实际链断 | 当前 knowledge 作者任务/决定/义务消费者 | 理由指具体事实，实体承担实际行为，不以 must 存在代替可执行 |

文件动作沿实际生产者/消费者修改；规则在一处维护，其余引用，不新增专属状态或报告协议。正常消费者必须继续用当前 prepare/check，不恢复旧代码审查 request、旧 Spec 知识真源或已退出资格工具。

## 实施前的因果核对

每项改动在现有交回中记录“实际缺口→缺失信息/误解→最早承担者→实际送达→预期输出变化→验证”，不新建运行账本。先核完整任务与原始会话：信息没有进入上下文修装配，已经送达却误解修作者要求或示例，设计错误回蓝图；没有当前缺口则核保持，不追加重复规则。

核Story的章节合同/写作设计在动笔前带出本章读者问题、有效来源及相关决定。核hooks/spec/author.md、hooks/plan/author.md与shared/knowledge-task.mjs的实际任务：本CU行为、条件、恢复与验证义务是否送达。Plan作者页已有前一步输出是否足够后一步使用等要求，优先核其消费，不因候选漏项再写一份。发现遗漏在现有来源装配修，原生设计读取缺口交原生责任方，不改从Story派生。

脚本核机械合同，独立审查核来源对设计、设计对结果及读者效果；不写业务关键词判定器。正常check/prepare返回当前可判断的完整问题和未执行原因，保持现有返回协议；相关测试核信息送达和失败副作用，不能把字符串出现当作语义能力成立。

## 具体文件动作与行为合同

1. 修改 `story-chapters.json` 的范围、业务方案、流程和附录 questions/boundary；`phases/story-write.md` 与 `writing-plan.mjs` 空壳从该合同取得读者目标。阅读主线明确“责任边界→整体协作/关键取舍→状态与分支→验收/待决”，允许作者按真实关系分节；不新增必填自证表、固定图数或全文模板。Story 自身回答整体问题，附件只作精确核对。
2. 修改 `phases/meeting-read.md`、`phases/design.md`、`phases/update.md` 的决定处置：在已有 doc-refresh/update-notes 中写本次决定、实际原话和受影响原生地址/人读位置，按真实权威先修设计再修派生；原文/人签不改。纯表达仅改章稿。有相反 canonical 主张时独立审查仍阻断，不因“属于蓝图侧”降为建议。这是模型语义任务，不建自动影响图或另一个状态表。
3. 修改 `story-reader-rules.yaml`，消除同一条一致性/图文/来源要求在多个段落的重复说明，保留一份可执行判据；`reader-review-task.mjs` 继续从原规则和章合同加载。本轮明确要求核两个不同层次：原始决定与设计是否一致、设计与人读件是否一致。未知结果、真实身份、缓存/云状态与入口接入按具体语义核，不把 G01–G09 名称或数值写进规则。
4. 保持 `review-report-contract.mjs`、prepare/dispatch/check、材料键与原件恢复规则；不换报告格式、不新增判据账本。复审输入沿当前 dispatch，不附作者“已全部关闭”的结论。坏报告按现行独立返修，不能作者手改原文。

变更覆盖上述作者/判据/任务、Spec/Plan实际任务装配缺口、下文数值来源合同及对应测试；原生门改动只交上游。若 2.0.2 已实现完全相同的要求，核其消费者后不重复写一份；该条交回引用实际实现。若实际来源推翻设计则回蓝图负责方，未交付原生能力保持依赖，不由实施者选择新 API。

## 数值、来源与表达的承接合同

本节承接1.x分析中仍有效的内容目标；历史单位表、固定列序和标注格式不恢复。已核事实：story-write.md已有“数值有来处”和自设数值登记；验收节要求上游编号、条件、单位、结果不丢；章节合同允许不适用；reader-review-task从原规则及章节合同装配。实施在这些位置合并同一职责，不再复制一份规则。

| 对象 | 输入、决定与实际文件动作 | 消费者与失败处置 |
|---|---|---|
| 数值与单位 | 在story-write.md现有“数值有来处”段明确金额、比例、容量、时限等都核数值、单位、适用对象/条件；上游要求引用实际来源，合法换算保留原口径。本轮新增工程设定沿decisions记录理由与出处，再落原生设计对象，不新增阈值表 | story-reader-rules.yaml的来源/一致性判据核同一值跨Story、附录和实际施工文档是否同义。无依据的确定承诺、换算错误或改变验收的漂移为阻断；不同适用条件的不同值不误判冲突 |
| 来源定位 | 在同一作者段明确：来源信息放现有材料采用说明、决定依据或附录，指到实际文件及可识别段落/条目；正文自足，不强加逐句括注。泛称“产品规则”而无法回查不算来源 | 审查者实际回原件核语义，不只检查字符串长相；坏路径由现有引用检查发现。不得从金样复制来源坐标或制造冻结现场 |
| 自设数值沿用 | 改动同一业务约束前先读有效决定及原生设计，已有值沿用；需要调整时记录理由并同步消费者。没有上游依据的工程选型保持设计判断身份，涉及业务承诺才交相应权威 | 编码/验证经原生契约取得决定；有新理由可改，不要求跨不同需求的所有阈值相同。无登记或相反值回最早责任修，不新建全项目数值中心 |
| 说明性引用块 | 作者页区分真实业务引文与流程/模板说明。清除对读者无用的“如何填写/当前阶段”残文；保留有必要的原话及其来源 | 独立审查看内容与影响；不以blockquote语法一律拒绝，不恢复1.x禁块正则 |

五类历史“模糊带”按当前职责一次定案：

- **承接写法**：引用用于追溯，正文负责讲清业务；同一事实不整段重复。保留上游验收编号；验收可重现判断必需的条件与数值。合法改述、列表或表格均可，不选一种文字模板排斥其他表达。
- **指标粒度**：指标逐项明确目的、分子/分母（适用时）、观察窗口与数据来源；统计事件是获得证据的动作，不以事件数推定指标数。不涉及统计则明确不涉及，不造指标。
- **统计点表**：既有event设计对象和附录渲染承担字段真源；业务上必须可回答触发时机、承担者、数据与结果。缺语义先补设计；不在作者页另定一组与renderer竞争的表头。核多流程/多指标的实际投影，不因表存在就通过。
- **术语表**：Story按story-chapters.json中术语与含义合同，Spec按Framework原生模板；不强制两者同列序。不为统一顺序修改上游模板。
- **来源名形态**：定位能力按上表，不要求固定“文件名+§编号”的字符串格式，重编号后仍应可追溯。

同步story-reader-rules.yaml仅补当前未表达的上述语义；reader-review-task继续单次加载，已有合同不重述。language.mjs的源码注释仍把归档件说成“两份”，按当前正文/Review/设计附件三件更新事实；这不自动放宽正文工程标识与文档坐标边界。test/golden/README的批注3/4/7/8按当前story-write与章节合同改成正确用途/示例说明，不能成为平行强制模板。

## 术语确认的上游交接

已知事实是interactive作者使用headless_assumed，原生blueprint-discovery.ts对应分支仅WARN；不是Story少一个登记中心。实施者在本包交一份最小复现：声明interactive、同一未确认的medium/low术语、原生checker实测输出、实际接入版本、应拒绝headless来源的行为要求。高置信度有真实glossary依据、实际用户确认、合法远期缺口分别作为对照，不把所有术语或所有WARN一律阻断。

上游负责原生模式与准入合同；未交付时该自动兜底保持未验证，真实CLI观察是否按已送达规则提问。不得增设story_flow术语关卡、复制置信度算法或改vendored代码。auto-topup没有term事实不自动判缺陷：按当前材料和工程核是否有需消歧的映射；无歧义可无，有歧义遗漏交设计发现/质询责任。金样编写不等待这个接口。

## 定向验收

`verify.py affected` 选择 test_story_build、test_writing_plan、test_verifier_report_protocol、test_knowledge_application、test_cu_knowledge_chain 的实际改动组。保留无 Spec/零 CU 成文、合法复用、章节字节保护、人工区、原始报告与当前对象绑定。

语义验收直接读候选：只看 Story/Review 可解释整体责任和主路径，技术附件无相反结论；同一决定变化覆盖其所有实际影响，不在另一件保留旧主张；段落/表/图的合法组织不因形式被误拒。用中性业务的同类输入核通用性，不对 Case 词条或字段个数加规则。

## 交回

每项给原缺口、最早责任、实际变更、旧消费者退出和独立内容结果。P1 的候选可同步修订，但本步不直接切正式金样。不新增 SVG 或安装流程；出现需要新原生能力的事实单列，设计者定合同后再实施，不能临场做旁路。

定向样例在现有test_writing_flow/test_verifier_report_protocol及知识/施工承接夹具内补：原始容量2 MiB与合法2048 KiB换算、比例分母变化导致的假一致、不同条件下不同超时的合法表达、无来源阈值与有据工程决定、真实业务引文与模板残文。脚本测试证明输入与判据送达、引用和原生实体承接；内容对错由模型走查及获授权的独立评价证明，不写正则替代语义，也不因字句存在宣告语义通过。
