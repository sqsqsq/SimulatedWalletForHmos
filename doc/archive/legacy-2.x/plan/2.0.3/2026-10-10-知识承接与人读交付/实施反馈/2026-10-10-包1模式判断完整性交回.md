# 包 1 交回：激活模式有判断，无选中不等于漏判

> 读者：维护设计者。基线 `77002f14`。改动未提交。没有运行模型或 CLI。

## 改动

| 位置 | 改了什么 |
|---|---|
| `hooks/shared/knowledge-application.mjs` | 原有完整性检查补上模式漏项：<br>• 激活清单里每份 `kind=patterns` 的知识，以 `HALVES[0]`（上篇）为唯一选型单元；<br>• 没有任何判断时，报模式文件、单元和补判断的动作（选中、调整、拒绝或待定；没选中也写一条拒绝）；<br>• 下篇不再判；<br>• 原有的 schema、来源摘要、角色、原生地址与一条只判一次的检查不变 |
| `hooks/blueprint/author.md` | 设计模式一条改成：每个激活模式按上篇写一条判断，全都不选也逐个写拒绝的事实 |
| `hooks/blueprint/reviewer.md` | 质询核对项补「每个激活模式都有一条判断；拒绝写出本需求里使它不适用的事实」 |

**消费者**：没有新增入口，都经原有 `problems` 报出。
- **设计侧**：`blueprintKnowledge` 进知识任务第 6 块的缺口，设计作者与质询者都收到，与门禁同一集合；Story 侧经 `appendixSourceProblems` / `designGaps` 停在成文起手。
- **施工侧**：`featureKnowledge` 进 spec、plan 等阶段 post_check 的「设计里的知识判断」组；非 CU 维护 Feature 的契约同样核。
- **脚本边界**：只报缺口，不自动选型、不代写拒绝。

**待定**：判断状态是 `open_decision`，算已判断，不报漏判；是否阻断按原生缺口与切片责任处理，这里不加判断。

## 退出与测试

- **`NoPatternIsSelected` 退出**：它把「模式激活但整份蓝图零决定」当正例，改为 `EveryPatternIsRejected`，即每个激活模式都有据拒绝；不编角色、规约照常送达的断言保留。
- **新增用例**，模式名与单元都从激活清单解析，没有写死 Case 名：

| 用例 | 断言 |
|---|---|
| `test_knowledge_application`：漏判 | 点名模式文件与「上篇」 |
| `test_knowledge_application`：全部有据拒绝 | 通过 |
| `test_knowledge_application`：待定 | 不报漏判 |
| `test_knowledge_application`：无激活模式 | 改清单后零判断合法 |
| `test_cu_knowledge_chain`：`AnUnjudgedPatternIsNamed` | 门禁点名 |
| `test_cu_knowledge_chain`：`APendingPatternIsAJudgement` | 不报漏判、不编角色 |
| `test_cu_knowledge_chain`：原有选中用例 | 角色传递保持 |
| `test_knowledge_task`：`test_unjudged_patterns_reach_the_author_and_the_questioner` | 设计作者与质询者的缺口都点名每个激活模式 |

- **夹具跟随**（测试域）：
  - `design_fixture.judged_rules` 默认对每个激活模式写一条有据拒绝，给定的模式判断照用，`exact` 反例仍可漏判；新增 `pattern_decision`；
  - 中性知识夹具 `judged()` 同样补拒绝；
  - 失效形态 W01 正例契约补一条拒绝；
  - R02 的 `_design.json` 支持带 `file` 的模式判断，正反例都补。
