## 2. R1（P1）：阶段消费者仍走旧的磁盘文件读取

`hooks/shared/contracts.mjs:readContracts/readAcceptance` 仍直接读 featureDir 下的 YAML；spec/plan/coding/ut/testing 与部分审前消费者沿用它们。改对 CU 目录不等于消费了原生有效输入。

独立实际发布件探针：合法 CU 冻结后没有本地 contracts.yaml，`readFeature(...,'plan')` 返回 status=ok、contracts.state=resolved、binding.kind=derive/provider_id=derive.blueprint-contracts；同对象 Extension readContracts 返回 contracts=null、exists=false。正常的蓝图派生输入因此被当作“契约还没建”，义务检查被跳过，用户被引向补文件。S3-01/S3-02 不是复杂异常矩阵，是本版主目标。

同一责任位置另有退路：featureKnowledge 将 `who.status !== ok` 与合法非 CU 合并走平铺契约；featureDir 在无 dir 时自行拼 doc/features。探针中不存在的 CU 被改称平铺 Feature 契约问题，而非保持 change_unit_missing。解析 design_ref 的 catch 也静默少一个承接地址。它们应退出，原生身份/有效引用失败直接交回，不能降为另一种对象或空承接范围。

修正：共用步骤 1 已有 readFeature/原生 resolver 的阶段输入。区分“本阶段刚产出的待核输出”和“承接输入”：当前输出按原生输出要求及 SpecLoader 校验，依赖输入按原生解析结果读取；不能为了复用而拿旧输入代替新输出，也不能自行按文件有无选来源。访问器带明确 phase/用途，同次任务复用解析结果；错误原样报出。不要强制物化出重复 YAML 或补空 Spec/Plan 来迁就旧读法。

本轮补一条真实 CU 的 derive → 原生物化 → 阶段解析 → 门禁/审前任务链，核 must/decision_id/pattern_roles 仍存在并被实际使用。另保留无新 Spec/Plan 的复用正例，以及已存在的过期输入拒绝。可复用当前夹具，不能只给测试手填最终 YAML。

## 3. R2（P1）：知识身份及多 CU 角色责任没有完整交接

- knowledge.mjs 仍强制“激活规约编号全仓唯一”，entryById 按裸编号取第一条；plan/coding 等仍消费它。方案已定按来源路径+unit 区分、通过 decision_id 找真实来源。同编号来自两个合法知识文件时，旧读取机制在新合同之前就拒绝输入。旧全局编号限制及专用断言须退出；先定位决定，再按决定的来源文件和 unit 找条目，验证/探针跟随真实来源。不要给后续编号加业务前缀绕过去。
- carriedBy 只判断决定是否与当前 CU 有任一交集，随后 plan 把该决定的所有 roles 都要求落在每个承接 CU。若模式角色 A 属于 CU-A、B 属于 CU-B，两个 CU 都被要求再实现另一方角色。按角色自己的 target_ref 与当前 CU 有效 design_refs 分派；整体角色完整性在蓝图层检查，CU 只落实它承担的角色。引用父对象时按原生目标关系判范围，不用字符串前缀猜。非法引用保持错误，不静默少算。

知识决定仍保持一份权威；这里只修消费者的身份和承接范围，不增加第二份决定表。补两个同编号不同来源规约正例、两个 CU 分担同一模式不同角色的正例和缺本单位角色的反例。模式角色名称还须对实际模式声明核对，不能仅因作者在决定里自报过就算合法角色。

## 4. R3（P1）：restore 对 Review 仍按整文件恢复

`flow/update.py:cmd_update_restore` 把 regenerate 中的 AR/review.md 与普通文件共用 copy/unlink 真值表。独立探针：本轮新建 Review、填入人工意见、记录完成点后 restore，返回 restored 并将 AR/review.md 删除；原意见只剩受保护历史副本。既有 Review 在同样条件下也走整文件回拷。

保存历史是必要证据，但不等于当前人工区所有权得到保护。更新期间收到并纳入完成点的人工意见不是 Extension 可以随表达撤回删除的内容；这属于正常评审/撤回，不是低概率损坏场景。

修正：Review 人工内容按现有分区能力保留，恢复仅处理自有机器内容。机器内容可由恢复后的决定重生；旧议题与当前人的表态不能确认语义适配时保留当前 Review 并列需处理项，不强行套回旧议题。最简单可先将带人工填写的 Review 保留为冲突，由现有渲染/议题流程处理；不用新建合并系统。无人工填写的纯机器工作件才可按既有恢复规则处理。补新建与既有 Review 各一个正常人工填写正例。

## 5. R4（P1）：锚点相同被当成反馈已处理

framework-access:checkFeedback 只取任意 decision.provenance.source_ref 的 `#` 后缀作为 handled 键；不核反馈文件路径，不核本轮，不核处理结论，open 决定也能命中。update 随后按此输出“已处理”。不同轮次都有 D3 时，上一轮或任意来源的 #D3 就可能让本轮意见虚假闭合。

这是 Extension 自拟规则，不是 Framework 的处理结果接口。原生 validateBlueprintReviewFeedback 只核候选资格，当前 revision 变化后同一旧反馈不能作为新候选再次验证来证明是否已接受。

裁定：删除按片段推导 handled。保留两件独立事实：①首次提交时的候选资格、被评 revision 和完整反馈路径；②当前蓝图中精确引用该反馈完整路径+feedback_id 的相关决定及其原生 status/revision。第二件只能显示“有关联决定”，不等于已接受/已处理。没有负责方明确处理结论时保持待确认，由模型读取 component-design 负责方实际回复及当前设计判断；原回复记录在既有本轮 update-notes.md，接受的设计仍以原生蓝图为权威，不增设处理结果文件或登记中心。旧反馈的资格结果与当前处理观察分开，不因新 revision 自动改投。close 可列仍待处理及责任，不伪报接受，也不自动取得施工授权。

测试移除“任意决定指向 #D3 即已处理”的正例；改为不同文件同锚点不命中、精确引用仍区分决定状态、候选资格不等于接受。

## 6. 三项设计定案与其他局部选择

### 6.1 没有 plan.md 的埋点落实

承载点定在当前有效原生契约的真实方法说明 `interfaces[].methods[].description` 和相关验收条目，那里说明该方法承担的统计点、适用结果及验证方式。原生 ContractsSpec 已有方法 description（harness/scripts/utils/types.ts），不新建统计点状态文件，不伪造规约决定，也不强制产生 plan.md。

有 plan.md 时保留已有逐点表作为人读表达；无 plan.md 时作者/审查任务把蓝图 event 明细、有效契约方法说明和验收并列交付，独立审查逐点核是否落实。脚本核可确定的现有方法/验收引用，语义对应不升级成子串判断。当前“没有 plan.md 所以逐点落实无处可对”的整项跳过退出；可以明确“Markdown 表格一致性不适用”，但实际埋点义务仍必须送达并审查。这用现有输入和审查职责补齐正常路径，不增加通用映射框架。

### 6.2 取证方法页

保留 evidence-rules.md 一份方法，改为设计发现/当前事实核对的共同页；在 blueprint author 的发现动作前引用，spec author 只在本 CU 有新增事实时引用。意图源改为本次真实需求、有效决定、蓝图/原生当前输入；spec/spec.md 不再不可缺。代码目录从配置/实际项目取，不把固定 Spec Scope 作为唯一搜索范围。取证结果归原生 discovery facts 或当前事实载体，页面不写第二份状态。保留原有“不以常识替代本仓事实”的业务能力。

### 6.3 其他局部选择

评审动作类规约不伪造代码验收或 must、Spec 专属 Story 判据退出、schema 失败直接报告、prepare 的显式终点及材料专用 status 入口接受。简单聚合查询减少无关原生调用合理，不能因此减少当前成文所需的独立设计预检。

发布只读预检/外部摘要与既有对接回执口径一致可以保留，本次不新增复杂上传事务。发布和远端恢复的真实成功仍需实际对接结果，纯登记不能自证外部完成。首次基线须按实际采用版本说明，缺已知外部基线明确交人；不将本轮测试用例替身视为真实远端验证。上传失败重试按既有流程和 CLI 场景验证。
