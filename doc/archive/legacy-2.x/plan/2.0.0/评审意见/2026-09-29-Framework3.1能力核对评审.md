# Framework 3.1 能力核对评审与接线裁定

2026-09-29，维护设计者。对象：[实施者交回](../实施反馈/2026-09-29-Framework3.1能力核对-交回.md)，提交 882aeeb0；README 修正 ccf226bd。源码以当前 demo 的 3.1.0/074a4c3c 发布件为准。

## 1. 结论

能力核对的主要机械事实接受，部分“确有 Framework 缺口”的归类需要收窄。核对工作通过，不等于 Story 2.0 接线或完整行为通过。README 已在使用和安装前区分 story-1.0 发布组合与 story 开发 demo，上一轮 P2 关闭。

已另形成[Framework 问题反馈报告](2026-09-29-Framework3.1问题反馈.md)，供用户转交。报告区分实现/文档缺陷、能力增强和支持范围待确认；没有修改 vendored Framework，也未发送外部消息。

## 2. 逐项裁定

| 项 | 裁定 | 本仓动作 |
|---|---|---|
| 基础蓝图 | 原生来源、投影、反馈、identity、准备/派生函数可用；没有专用 CLI 不等于没有能力 | 薄适配器调用真实函数，保持只读/写入边界；反馈候选取实际函数返回，不能假定 CLI 有不存在的字段 |
| A | 文档指向 component-design skill_assets，但无明确消费指令且 inspect 直接报 scheduled，属真实接缝问题 F1 | 报 Framework；保留 Story 前置送达和 Feature 阶段接线，不把仅全局索引降级为已证明的直接设计知识链 |
| 独立质询 | “没有函数调用者”“没有新增 scope”不能证明质询机制缺失。原生设计是模型在隔离上下文履责 | 使用原生 view/relation/flow/app_lens/terminology scope 检查知识产生的实际设计效果，不新增 extension_knowledge 枚举或通用 provider |
| B | 无 Feature request 是合法结构审查通道；缺少直接复用的完整独立产物审查及对象验真合同，是能力请求 F2 | 不用手写 PASS、虚构 Feature 或修改报告目录门禁替代。先按现有合法能力接线，由设计者及时核定调用，独立性及对象绑定进入真实 CLI 观察；只有复现必经能力缺失才要求 Framework 补齐，不以等待上游回复整体阻断 |
| C 实体 | 五处 must、验收桥、knowledge_applications 与真实组件角色的机械承接有证据；尚未跑完整 phase harness/模型语义 | 先实施原生实体读取及下游消费，保持当前合法位置；测试不能把保留字段等同于知识语义成立 |
| C 文件 | 旧 files 对象本来不受当前 schema 支持，必须改 Extension；原生静默丢信息另报 F3 | 不申请 knowledge_files，仅因缺自拟字段不算能力缺口。角色落实际组件/接口/数据模型等承担实体；无实体的文件要求先给真实来源与具体落点，由设计者裁定，不能凭假设要求框架泛化 |
| D 路由/生成 | 原生 skills 表、phase bindings 与桥接已能接替旧机制文字；函数组合的只读渲染可用 | 退出 story-ext 专用段及 bridge writer，命令路由在 Story SKILL，作者要求在已登记入口；安装器薄组合原生预检，不申请新计划 API |
| D 人工保护 | 选中 AGENTS/CLAUDE 被 materialize 整份覆盖属已证事实；UPDATE 已有 overwrite/keep，不能统称无保护 | 安装预检先报冲突再写，不用集合差“少几行”作为安全合并算法；原生改善建议 F8 不阻止本仓安全预检接线 |
| interactive | 无 run 的范围和完成消费已有支持；主入口指令有冲突，CU 连续推进支持范围尚未完全证明 | 报 F6；不称已证明死锁/并发错误，不由 Extension 自建运行状态 |

## 3. 独立复核与证据限制

设计者使用真实发布件的导出函数，在全新临时工程复现：

- 合法 skill_assets 可解析，inspect 两项仍为 scheduled；对照原生 Skill/工作流没有相应读取要求。
- files 对象经 SpecLoader 变成字符串，shape_issues 为空。
- 未知 file 键置于 data_models.fields 子树不报错，置于 components.must 则报 unconsumed_file_field。只证明漏诊断，未证明写入越权。
- 实际选中 CLAUDE.md 的人工标记在 materialize 后消失。对未选 AGENTS.md 的改动保持不变，因此复现必须选择真实 target_path。
- chrys/generic 第二次仍各写同一入口并持续 stale。
- 真实数据模型与接口对象上的 pattern_roles 经 SpecLoader 保留，原生文件引用检查通过；这项补测尚未覆盖完整蓝图/阶段门禁，不扩大为完整行为结论。

实施者 C 探针借用另一源码点的夹具作为输入，被测代码是当前发布件，方法本身可用；但其改动后的整蓝图准入及完整 phase harness 未跑，assurance 的 blocked/degraded 也未因字段保留就消失。交回所称“全链”限于已执行的派生/物化/部分 resolver，不能写成全部执行阶段通过。

原始独立结果：output/story/2.0.0/fw31-review/independent-probe.json；复现脚本：output/scratch/review-fw31-cap/probe.cjs。未运行真实模型、Goal、设备或业务 CLI。

## 4. 对方案的具体修正与后继

1. A 的接收仍需真实原生消费合同；不新增质询 scope，不因 global 可见就声称完整知识链成立。
2. B 的 AR/story-src/review 是宿主原计划落点，不是要求原生取消 report-dir 隔离的依据。正式入口锁定时同步报告路径、原始材料绑定及回流；现有 request 可以由独立 Agent 执行，但还需证明报告绑定和消费者满足要求。
3. C 先采用实体级 must 和 pattern_roles=[{pattern,role,decision_id}]，路径从承担实体的原生 file/path 派生，不在角色行追加文件键。真实组件的角色链已有探针；接口/模型角色再补完整派生/phase 验证。旧 files 对象和 knowledge_files 均不写入新契约。
4. D 的安装器在覆盖前调用原生 renderer/bridge inspection。目标当前入口先与当前安装配置的原生渲染比对，已知旧 story-ext 只按真实旧发布源识别；其余差异保留并报告，不能凭字符串相似度吞掉人工内容。新 manifest/schema/资源预检成立后才写；部分失败通过本次预期写入面和前后字节比较列完成项，不新增持久安装事务。
5. 施工 closure 的知识归位要求需提前交给设计作者：真实 decided_with_authority 决定在整体闭环前要有有效 knowledge_refs 与实际知识资产。模型不能为了过门把人工裁决降格为 inferred，也不能把本次决定自动升级为项目全局规约。来源归位仍由真实设计/知识责任方决定；新增机械消费者在步骤 3 核这条链。

实施者可继续步骤 1 中 manifest/元数据、身份读取、Feature 知识任务、原生安装预检与入口职责迁移，以及步骤 3 已确定实体的接线验证。只读/确定性接线不等待报告全部条目修完；直接设计送达、人读独立审查及无 run 完整 CU 推进分别保留未验证边界，相关正式验收不能提前通过。

Framework 反馈由用户转交；收到对实际合同的回复后，设计者负责具体适配裁定与方案同步，不让实施者自行选择权威、替换载体或弱化产品目标。

## 5. 用户确认的后续推进口径

用户随后确认“先推进适配，再用真实 CLI 判定疑点是否实际阻塞”，并要求写入方案。当前执行依据唯一见[总览 §1.3](../01-实施总览与协作合同.md#13-用户裁定继续适配以真实-cli-判断行为阻塞)，测试观察见步骤 4。已证硬错误及时处理；未验证疑点不作整体开工门；失败先排查 Extension，再判 Framework 责任。源码反馈不撤销，产品目标和证据真实性不降低。
