## 3. 接口转写的确定合同

### 3.1 产物、所有权与时序

用户已选的路线是模拟真实上游材料，不是让脚本按固定 SE 版式提取。

1. SE 的自然语言/表格接口设计仍在现有 SR 正文中，沿现有获取、材料登记和冻结流程送达；不增加 fetch 附件能力或强制 SR/interfaces.yaml。
2. 蓝图设计作者读取本次已登记的冻结 SR 原文，写 `<features_dir>/<blueprint_id>/blueprint/contracts/se-interfaces.yaml`。文件使用原生 operation、request_dto、response_dto、errors、idempotency、nfr 对应结构；每段保留冻结原文路径、实际章节/段落定位及来源摘要。它是模型的转写结果，不能称作未经核实的 SE 原件。
3. 同目录 `mappings.yaml` 由蓝图设计作者形成本部件字段映射。mapping 的选择/转换/默认/丢弃是本部件设计决定，不要求 SE 替本部件给出；来源引用本次设计依据，和协议转写分工明确。
4. canonical 的 source_ref 按实际 YAML/JSON Pointer 引用对应段落，原生 checker 比对蓝图与这些文件。来源转写经核对前，原生结构相等只证明两份结构一致。
5. 设计修订时保留被旧 revision 引用的转写/映射文件，新版本用新文件名并更新当前 source_ref，不覆盖历史有效来源。由现有设计负责方按修订流程管理，不新增 Extension 自动版本调度或恢复机制。
6. 缺类型、版本、可空性或原意冲突时，作者在设计质询前明示 gap 与责任。当前切片必需则阻断准入，后继事项按原生 needed_by/open_decision 处理；不把未知 nullable 当 false，不用旧 Spec 推测值伪称 SE 明示事实。

### 3.2 忠实度由谁核

**主要核对在蓝图准入前的独立设计质询。** 作者转写后，质询方同时取得冻结 SR、转写、映射及 canonical，逐接口核字段、类型、必填/可空、版本、错误、幂等和遗漏；区分 SE 事实与本部件新设计。缺明确来源/权限时交人决定。把首次核对放到 Story 审查太晚，不能采纳实施者此项建议。

Story 独立审查承接已成立设计，仍能发现原材料与人读表达矛盾；不再独立维护一份接口提取结果或重复要求人签。作者/质询要求写在现有 blueprint author/reviewer 页并随知识任务到达；Story 审查材料集合加入实际被 canonical 引用的转写/映射文件，保留原始冻结来源。可直接沿当前原生 source_ref 取实际文件，不扫描全目录猜来源。

文件动作：蓝图作者/质询页、ar_design_init 与 flow.inputs 的交接说明、reader-review-task/review-object 的实际材料接线；不修改 vendored Framework、不扩展取件脚本。

### 3.3 模拟 SE 材料的起草与审定

维护实施者以测试材料作者职责起草当前两个 Case 和 AR90004 金样输入的 SE 接口小节；维护设计者逐接口审定后再纳入基线。用户已授权模拟真实场景，起草新的模拟协议事实是这一步明确的工作，不再按“纯转录现有缺字段文本”停工；但草案须标清本次新增的类型/版本/编码，不冒充旧材料原有内容。

两个活跃 Case 使用不同的自然写法，至少一份非固定编号/表头；不得给消费模型预置转写文件、答案或审查结论。金样没有消费模型运行，可由维护夹具提供与审定 SR 相符的转写和映射，机械比对仍走真实原生 checker；这不证明模型转写忠实度，真实效果由 CLI 证明。

起草范围：auto-topup 的 SR90006、car-key-sharing 的工作区 SR、金样输入 AR90004 的 SR。已退役 traffic-card-loss Case 不同步扩建，其历史数据保留；当前消费者指向活跃输入/金样夹具，不能继续靠两份历史文件必须逐字相同的断言维持关系。金样正本的业务叙事与既定结果保持，新增模拟协议字段只进入已说明的设计/精确附录，旧业务事实不得改变。

采用后更新输入指纹、转写/映射来源、canonical contracts/runtime_data_flows 与 mapping.yaml，核准入和重投后事实保持，最终解除 G01。controlled_fakes 不作为豁免；本路线已有完整模拟协议，应按正常契约校验。

## 4. 同类格式依赖的裁定

### 4.1 上游图与冻结版本

先将 Story 与读者审查的上游读取统一到本次采用的冻结 SR，复用 snapshot 路径；当前工作区新 SR 不得悄悄改变已采用版本的图源。

实施者意见有一点需纠正：diagramsOf 对无数字标题已有业务名回退，所以不能笼统声称中文编号必然失败。真正限制是只解析 Mermaid 与特定层级标题，无法据此枚举所有上游图。

本版保留可解析 Mermaid 的精确引用核对；图片继续走已登记图片的身份/引用检查。对 docx 图片、PlantUML 等未被解析为 Mermaid 的材料，作者与独立审查按实际冻结原文理解图意，机械结果明确“该图格式未作结构解析”，不能写“上游无图”或假装覆盖完整，也不因要求上游改成 Mermaid 而阻断正常需求。生成的 Story 图仍遵守自身明确的产物格式合同。

不新增上游图 JSON 清单或统一转图器。使用现有材料清单、caption、提取稿和章节来源表达回查；图意是否保持由独立审查判。已有可解析来源上的虚假图源标记仍报错。

### 4.2 冻结引用闭合

图像资源与作为本次设计依据的本地文件仍须在采用集合里可解析；冻结不能自动越界复制。普通参考链接不等于采用义务，不能因 SE 引了需求目录外的其他文档而一律拒绝冻结。

在现有 references/closure_problems 中保留图片与普通链接的区别：采用文件和本地图片缺失继续失败；其他未采用的参考链接列明路径与“未纳入本次冻结”，由模型判断是否应补入材料或明确不采用。相关事实不能仅因链接可点击就作为已取得来源。引用目录外的必要图片先沿现有导入入口进入需求材料，不自动搬整个目录，也不更改原件。

复用当前输出的缺口/提示，不另起持久化链接状态文件。测试至少覆盖一条非必要背景链接不拦冻结、一张必要本地图缺失仍拒绝。

### 4.3 验收编号

固定 AC/F/BD 正则只能说明已声明的机器产物格式，不能证明任意上游需求的验收内容被全部保留。保留原生 acceptance 中真实 ID 的引用一致性检查；Story 对上游编号与业务验收的完整承接由模型读冻结原文、独立审查对照。

本版不新增需求验收登记中心。清理把夹具编号习惯当作外部输入要求的作者指令/判据：合法其他编号不能被强制改号，也不能因正则零命中就声称验收已完整。格式不在可解析范围时给出机械覆盖范围说明，语义审查照常覆盖原文。另一合法编号（例如“验收甲/乙”）用于验证正常输入不被旧假设遗漏送达，不靠脚本证明语义完整。

### 4.4 原生 UI/还原度判定

本仓维护 interactive，不能因意见中引用 goal 文件就新增 Goal 模式适配。先沿实际 prepare-scope/Feature 调用链只读核实 requirement 的真实来源（既有 knowledge Skill 已要求真实需求或文件），只把实际命中的还原度判断记为 CLI 观察。原生关键词判定是否构成缺陷须有本版实际调用与输入证据；本轮不改原生、不泛化成新模块。

## 5. 验收与交回顺序

先交模拟 SE 补充草案、字段来源/新增决定对照及消费指引，再由设计者审定具体协议；实现转写方法接线与上述格式边界的局部修正可并行准备，采用基线须在材料审定之后。材料一旦定稿，金样装配走真实冻结、转写引用、契约/flow 准入和投影；Case 消费模型则从原始 SE 自己理解转写。

必要验证限正常链：两种 SE 写法、转写漏字段或误解 nullable 的可发现责任、冻结后当前 SR 改动不影响已采用来源、图片与非必要链接分别处理、非 AC 编号实际送达、金样/G01。机器检查只证明结构/引用；忠实度由设计质询与正常 CLI 审查证据证明，不构造一个脚本声称懂所有 SE。
