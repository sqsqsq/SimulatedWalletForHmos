## 3. 4B 金样迁移

### 3.1 做了什么

正本 `test/golden/story-金样-AR90004.md` 与输入夹具都不改；迁移只在测试的隔离副本里做。

- **`test/scripts/golden_workspace.py`**：用真实流程命令走到交给设计，步骤是：
  1. `init`；
  2. 收件箱原件按 UX 归类导入；
  3. 走材料关卡和范围关卡；
  4. `bind-design wallet-main bp-AR90004`；
  5. 冻结输入，提取稿为 `AR/design.md`。

  1.x 的 `spec/` 不进工作区。之后装 AR90004 的蓝图，迁移正本，用 `story-build project` 重投附录机器区。
- **`test/scripts/golden_design.py`** 与 **`test/fixtures/golden/AR90004-design/`**：
  - 蓝图模板的设计事实逐条取自 SR、spec 与 AR 原文；
  - 知识应用决定由 1.x `knowledge-use.yaml` 逐条转写，来源取金样知识快照，带文件 sha256；
  - 精确明细（数据存储、配置项、埋点）照录正本机器区原文；
  - 需求条目取本次冻结输入推出的原生条目；
  - 来源指纹按原生算法重算。
- **`mapping.yaml` 是迁移唯一依据**，`migrate` 只动其中登记的项，没登记的旧标记、旧机器区、图片链接一律报错：

  | 旧元数据 | 去处 |
  |---|---|
  | `%% 图源 spec §5.1 #1` | 六个分支逐项映射到场景节点 identity-recovery、existing-application、confirm-and-submit、freeze-result、retry-reuse 与运行节点 recovery-context、loss-page-stages，并写明在现有 Story 图里的位置；只删这一行，SR 标记不动 |
  | 依赖变更机器区 | 去掉首尾两行标记，原文保留为作者区；结论由开发视图的五个模块节点承载：WalletMain 改，其余当前与目标同为既有提供方 |
  | 数据存储、配置项、埋点 | 按 `story_details` 原文重投 |
  | 规约 | 按知识应用决定重投 |
  | 改动边界 | 按开发视图节点重投 |
  | 端云接口 | 待核定，见 §3.2 |
  | 正本两处图片链接 | 见 §3.3 第 1 条 |

  1.x 的模式候选与事实使用登记不进蓝图，原因写在 `not_carried`。
- **`verify`**：每条机器派生的旧事实在重投后的新输出里逐字找得到；没重投的 1.x 机器区（起始标记写「由spec」）不算找到。图里业务分支的等价按评审由维护设计者人工对照，映射表已列出逐分支对应。

### 3.2 端云接口：最小字段映射与原生缺口

SR §4 原文能给的，与原生契约（`blueprint-contracts.ts`）要求的逐项对照如下。「未提供」的不按名字猜，也不从 1.x spec 补。

| 接口 | 请求字段（SR §4 原文） | 响应字段（SR §4 原文） | 调用条件与错误行为（SR 原文） |
|---|---|---|---|
| `queryLossEligibility` | `cardId`、`accountScope`（脱敏映射后） | `eligible`、`identityRequired`、`cardState`、`existingApplication`、可读原因 | 打开页面、身份回跳、冲突恢复时调用；无后台轮询 |
| `createOrReuseLossApplication` | 卡片标识、账号范围、用户确认、稳定幂等键（SR 没写字段名） | 有效申请时原 `applicationId`，否则新建并返回 `submitted` 状态 | 响应丢失后再次调用不得创建第二份申请 |
| `queryFreezeResult` | `applicationId` | `frozen` / `processing` / `failed` 及可读原因 | 只有 `frozen` 能驱动成功页面 |

| 原生必填 | SR 是否给出 |
|---|---|
| `operation.operation_id` | 有，即接口名 |
| `operation.direction` | 未提供（只知道钱包调卡云） |
| `operation.version` | 未提供 |
| DTO 的 `dto_id` | 未提供 |
| 字段 `type` | 全部未提供 |
| 可空性 | 全部未提供；缺 nullable 不能当必填 |
| `createOrReuseLossApplication` 的请求字段名 | 未提供；`userConfirmation`、`idempotencyKey` 是 1.x spec 写的，不是 SR 原文 |
| 「可读原因」的字段名 | 未提供；`reason` 出自 1.x spec |
| `mappings`（direct / derivation / default / drop 与 rule） | 未提供 |
| 权威来源 `source_ref` | 要指向一份原生能按 JSON Pointer 加载、与蓝图声明逐项比对的结构化文件；SR 是 Markdown，不能直接作这份来源 |

1.x spec 里另有的本地设计事实——「性质：新增 WalletMain 卡云适配接口」、错误码列——出处是 spec，不是 SR。「新增卡云适配接口」由开发视图 wallet-main-module 的目标状态承载；按评审，不塞进 `nfr` / `errors`。

**缺口不止端云接口这一节，它卡住了蓝图准入。** 运行视图是 changed，原生要求六项触发条件逐条裁决。按 SR 原文，下面四项成立：

| 成立的触发条件 | SR 依据 |
|---|---|
| 远端事实驱动 UI | §2 |
| 冻结结果交给 AR90005 | §5 |
| 重新进入与账号变化 | §7 |
| 不信任旧缓存 | §6 |

这些裁决与依据写在蓝图模板的 `app_lens.runtime_flow_trigger_assessment`。

有一项成立，原生就要求 `runtime_data_flow`；而 runtime flow 的 schema 要求 `external_contract_refs` 与 `logical_contract_refs` 至少各一条，并且都要解析到 `contract:` 对象。所以没有契约就没有 flow，没有 flow 就准入不了。

当前蓝图只剩一个问题 `runtime_flow_required`，另外两条 `blueprint_admission_self_asserted` 和 `blueprint_admission_false_pass` 是它派生出来的。蓝图其余部分已过原生校验：视图、场景交叉引用、关系、知识决定、来源指纹与评审投影。

**请设计者定：**

1. 接口的结构化权威来源从哪里来。评审给的方向是「SR 加接口定义附件」。附件里的 version、type、可空性、mapping 要由 SE/卡云的实际协议提供，迁移不能代填。
2. 来源核定前，金样与 G01 是否继续按「蓝图未准入」保留已知失败。
3. 原生 `current_slice.controlled_fakes` 是否适用：准入允许「当前切片冻结契约和 design refs，或显式声明受控 fake」。我没有用它。原因是 runtime flow 的 contract 引用仍要解析到真实对象，而且这等于替金样声明一个受控替身，属于设计决定。

### 3.3 金样走上真实流程后新暴露的两处冲突

1.x 金样工作区没有 `materials.json`，图片身份与材料清单两条判据从没在金样上执行过（输出里一直写「判据未执行」）。改走真实流程后它们开始执行，并拦住了金样：

1. **图片链接**：正本引用 `assets/image1.png`、`assets/image2.png`（1.x 归档时复制进 AR/assets 的副本）。2.0 的图片按材料登记认，登记的是导入从原件抽出的 `assets/紧急挂失界面原型说明/imageN.png`，两者逐字节相同。
   处理：映射表新增 `image_refs`，迁移时核字节相同后改链接，不同就报错。工作区不再复制归档副本。这是与已裁定三项同一原则的机械迁移，请确认。
2. **材料清单**：判据把原件导入后转换出的 `ux-reference/README.md` 与收件箱原件 `inbox/紧急挂失界面原型说明.docx` 当成两份材料，要求两份都列。金样只列原件。按「拦金样即判据错」改判据：
   - `registry.py` 给已并入正文的收件箱原件记下转换落点 `target`；
   - `sources.mjs` 把原件与它的转换稿算作一份，列任一个就算列到；
   - 新增用例 `test_the_original_and_its_conversion_are_one_material`，旧实现上会失败。

   请确认这个方向。
