2026-10-07，按用户确认的版本重整更新现行范围；2026-10-11 收口性重整：需求文档拍平到版本根层，现行需求按自然顺序重编为 R1–R5（原 R2–R6 顺移一位；原 2.1.0 R1「两 Case 金样」已于 2026-10-07 迁入 2.0.3）。本轮只改规格与方案，不实施产品、改 Framework、切金样、跑新 CLI 或发布。迁移归属见 [版本承接表](../2.0.3/05-版本承接对照.md)。

## 1. 本版目标与有效决定

本版交付四类能力：跨仓安装升级准确、省事（R1）；在有实际效果和成本依据的场景提供 SVG 表达与完整交付（R2）；两项使用诉求——收件箱按子目录收料（R4）与 Story 页面交互流程叙事（R5）。一般成文质量、跨产物语义、独立审查效果及需求执行效率已迁入 [2.0.3](../2.0.3/00-版本范围.md)，本版引用其标准并核保持，不重复建设；R5 是新增的人读叙事能力（沿业务流程读出页面与操作的完整交互），引用 2.0.3 的质量标准与审查判据，不属于上述迁入范围，也不构成迁回。

原已确认的接入流程保持：维护者只发布机制包 xxx/；业务维护者首次另从内网 Wiki 取得 adapters 并放在同级目录；日常只替换 xxx/，保留 adapters、knowledge 与目标信息；随后 AI 执行一次 `/extension materialize` 完成首装或升级，不要求独立 `/story adapt`、状态查询或人工完成标记。

根 extensions/xxx 是机制唯一开发/发布源；Demo 的 knowledge 与本地替身 adapters 各保留唯一维护源，Demo 是示例工程与测试底座，不要求每次机制改动都同步。内网 adapters 独立统一维护，契约未变且无自身修复时不重复分发。R1 统一维护目录所有权和装配要求。

图形方面，用户下载 Markdown 与本地图片后用编辑器阅读。已验证更清楚且日常总成本不增加的场景可直接优先 SVG，不以 Mermaid 先失败为前提，也不要求日常双版试画。没有证据时只声明支持，不宣称 SVG 优势。

资源交付已定为 [R2 §4](02-SVG表达与交付.md#4-图形交付合同) 的同版本三件 Markdown 与资源 zip，系统侧需真实二进制附件能力；SVG 签收按 R2 §6 的六类指导、至少一条完整生产链、优先场景及正式自然选型分别验。正式 Case 未自然选 SVG 不自动失败，但不能用它代替定向端到端证据。

外部依赖明确保留：Framework F1/F2 的实际接口/存储合同，以及系统 adapters 二进制附件能力。未交付时阻塞各自接线/系统完整图形交付，不由实施者猜 API 或用 Markdown-only 路径冒充。具体代码接线待后续 2.1.0 plan；本轮只完善 spec，不写该版本 plan。

R1 依赖 Framework 支持机制与目标内容分离读取，以及原生 extension Skill 消费接入要求。Story 专属独立审查沿 2.0.2 实际合同与 2.0.3 效果核验，不再将旧通用代码审查的 Markdown 引用问题作为本版整体前置；知识适配若有独立审查需求，先核真实对象/现有入口的适用范围，不能伪造 Feature 或新建通用审查平台。

两 Case 修订稿与效果正本切换由 2.0.3 R1/R4 负责，本版仅消费审定结果。未完成或接口未交付按对应工作声明，不从“核心链可运行”推出已全验收。维护范围仍为 interactive。
