## 一、问题诊断（第一波之后新发现）

第一波虽然在 PRD / design / coding 三阶段都加了 Scope BLOCKER，但事故复盘发现：

- 真正的起点错误在 **PRD 阶段的术语映射**：用户原始需求里的"卡中心"（UI 聚合页）被弱模型按字面相似度错映射到 `CardManager`（03 层后端能力）。
- PRD 阶段的 Scope 声明一旦基于错误映射，后面所有 BLOCKER 都会"自洽"通过——因为 design 阶段的 scope 本来就是继承的。
- 弱模型（MiniMax / GLM，200K 上下文）无法全量探索 60 万 LOC 真实代码，**不能指望它靠读代码自行纠错**。

结论：**输出校验不够，必须前置到输入端。**

## 三、术语守门的三道防线

| 防线 | 触发条件 | 实现位置 | 实测结果 |
|------|---------|---------|---------|
| ① 人工确认 | 任意一行「用户确认」≠ `[x]` | `terminology_mapping_table` BLOCKER | 路径 B 实测 FAIL（见下文）|
| ② Catalog 对齐 | 权威模块不在 `module-catalog.yaml` | `terminology_mapping_table` / `scope_matches_catalog` BLOCKER | 自动校验 PASS |
| ③ Glossary 交叉 | 所有行 `[x]` 但与 `glossary.yaml` 权威映射冲突 | `terminology_mapping_table` BLOCKER（第二波 WP6.4 增强）| 路径 C 实测 FAIL（见下文）|

这三道防线合力阻断：
- AI 漏做映射（路径 A 未走完）
- AI 误映射但用户未注意（路径 B）
- AI 误映射且用户漫不经心勾确认（路径 C）

## 五、试金石实测：card-center-litmus

### 5.1 路径 B — AI 把"卡中心"误映射为 `CardManager`（用户未确认）

违规 PRD 片段：
```
| 卡中心 | CardManager | 03-CommonBusiness | high | — | [ ] |
```

实测输出：
```
❌ FAIL [BLOCKER] terminology_mapping_table
   1 条术语映射未获得用户确认（用户确认列不是 [x]）：卡中心
   Verdict: FAIL
```

**结论**：第一道防线成功阻塞。

### 5.2 路径 C — 用户漫不经心勾 `[x]`（最危险场景）

违规 PRD 片段（同上，仅把 `[ ]` 改为 `[x]`）：
```
| 卡中心 | CardManager | 03-CommonBusiness | high | — | [x] |
```

实测输出：
```
❌ FAIL [BLOCKER] terminology_mapping_table
   1 条用户已确认的映射与 doc/glossary.yaml 冲突：
   「卡中心」用户确认了 CardManager，但 glossary 权威映射是 WalletMain
   Suggestion: (1) 按 glossary 修正 PRD 映射；(2) 若确认要覆盖 glossary，
                先显式修改 doc/glossary.yaml 中该术语的 canonical_module 并注明 user-approved
                日期，再跑 check。
```

**结论**：第三道防线兜底成功，即便用户已勾确认也无法放行。

## 六、关键假设与已知边界

### 6.1 假设（将在内网试运行中验证）

1. **glossary / catalog 的维护成本可接受**：真实工程按用户估计 50-200 个业务术语，维护频率低于每周 1 次。
2. **AI 会老实读 glossary 与 catalog**：通过 `/prd` slash command + CLAUDE.md 的强引用保证；trace.json 将记录 AI 是否实际 `Read` 这两个文件。
3. **用户对"每条人工确认"愿意承担**：按用户明确约定，不启用 auto-approve。极端简单需求下会稍有冗余，但远胜于复现事故。

### 6.2 已知限制（第三波可能继续优化）

1. **近义词 / 缩写不在 glossary 里时**：脚本只做子串匹配，弱模型可能漏报。未来可接入 Aider-style Repo Map（WP7）补充。
2. **跨 feature 共享术语演化**：同一术语在不同 feature 的语义漂移需要人工识别，目前靠 `easily_confused_with` 静态维护。
3. **违规 PRD 样例文件本身不会自动跑**：card-center-litmus 的"路径 B/C"需要人工把 PRD-violation-sample.md 里的内容复制到 PRD.md 才能跑，后续可加脚本自动化。

## 七、建议内网试运行路径

1. **Day 1**：直接按 WP6 的资产跑一次"卡中心"类的新需求，观察弱模型是否主动执行 Step 1.5。
2. **Day 2-3**：跑 2-3 个真实需求，每次把 trace.json + gap-notes.md 回传。重点关注：
   - AI 是否在术语未命中时主动停下问用户
   - `terminology_mapping_table` BLOCKER 的真实命中率
   - Glossary 的新增 / 修正频率
3. **Week 2**：基于回传数据决定是否进入 WP7（分层 Repo Map）——如果 BLOCKER 误报率低且 glossary 维护成本可接受，则不急于做 WP7。
