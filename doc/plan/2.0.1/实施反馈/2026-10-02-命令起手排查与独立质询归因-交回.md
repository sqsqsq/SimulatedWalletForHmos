# 实施交回：命令起手排查、原生能力适配复核与独立质询归因

> 读者：维护设计者。时机：重整 2.0.1 方案之前。
> 起点：用户 10-02 看完 [实跑分析](../00-返修与双Case实跑分析.md) 后提了四点：两个 Case 只用命令起手，不给执行模型多余信息；问清 U1、U2 是什么；判断独立质询问题出在哪一层。
> 本页只交事实、分析与建议。2.0.1 用户已定暂不实施，产品、Case、测试都没有改动。

## 1. 总定性：没有查到 Framework 缺陷，问题在适配方案的能力适配核实

逐条复核后，[Framework 协作问题报告](../06-Framework协作问题报告.md)记在上游名下的几项，没有一项是 Framework 的 bug。它们都是 2.x 蓝图适配方案在采用原生能力之前，没有核清楚三件事：

- 这项能力是为什么对象设计的；
- 由谁执行，输入从哪来；
- 执行后留下什么证据。

| 原说法 | 复核后的定性 |
|---|---|
| U1 独立审查不认 Markdown 引用 | 原生 review 是**代码审查**。2.0 拿它审 Story 文档，是选型问题（§3） |
| U2 物化把入口描述写死 | 原生物化的能力边界，Framework 没有承诺带上扩展的描述。2.0 没核「用户靠什么发现 story」（§4） |
| U3 独立质询没有执行路径 | 最接近 Framework 的不完整：有规则、有字段检查，但没有派发、执行与留证。仍应在设计期就核出来，建议改为向上游**确认预期执行方式**的提问，不按缺陷报（§5） |
| F01 首条请求只送到第一行 | 本仓测试工具的问题 |

**根因**：步骤 1–3 用静态接线和 schema 通过作验收，把「接上了」当成了「能用」。实施者也是照这个标准验收并签过的，这是我们两边共同的漏核。

**建议**：重整 2.0.1 时，对方案采用的每一项原生能力先逐项核上面三件事，写进方案。核不通的，在方案里就定好替代或补位，不要等到实跑才暴露。

## 2. 两个 Case 改为只用命令起手：排查结果

### 2.1 执行模型能收到什么

只有四条渠道：

1. case.yaml 的 `prompt`，原样作为第一条消息发出（`test/scripts/run_case.py:1762-1766`）；
2. 宿主的 `reply --text`；
3. `resume-update --text`（也就是 `update_request`），以及可选的 `--answer`；
4. 投放进工作区或需求系统快照的文件。

驱动器自带的自动消息（`GATE_REPLY`、`continuation_reply`、`resume_prompt`，见 `run_case.py:142,317-358`）只在非交互或非 story 起点时才发，这两个 Case 走不到。CLI 配置没有注入系统提示。

### 2.2 多余信息清单

| 渠道 | 位置 | 多余内容 | 建议 |
|---|---|---|---|
| 起手 prompt | `test/cases/auto-topup/case.yaml:53-59` | 终点（定稿送审、不施工）；材料在我手上；透露澄清会；「停下来问我」 | 改为 `/story init AR90006` |
| 起手 prompt | `test/cases/car-key-sharing/case.yaml:43-52` | 不用去系统查；材料在我手上；终点（到方案为止）；「doc/extensions 和 framework 不要动」；「结束时说一下遇到的问题」 | 改为 `/story init ISSUE-206`。framework 只读已是工程 AGENTS 红线；「说一下遇到的问题」是测试诉求，不该发给模型 |

| 交补料时的回话 | auto-topup `interaction-script.yaml:15`；car-key 同文件 `:15` | 点名交的是哪几份材料 | 只回「已放入」那个选项的编号，与 `test/TEST.md:167-168` 一致 |

| 宿主回话 | 本轮实跑，我在车钥匙开头重申了「这轮做什么」 | 多余信息 | 改为命令起手后，起手阶段不会再有需要宿主补充说明的空白 |

下面这些已核过，**没有问题**：

- 系统快照与工作区种子材料都是业务内容；
- 新版产品稿和车钥匙评审意见里没有测试用语；
- case.yaml 里的 `note`、`expected` 字段和注释不会投给模型；
- `meeting-answer-key.md` 不进工作区。

### 2.3 改为命令起手后，要先定的三件事

1. **终点从哪来**：Story 在交付门会问一次交付选择（`extensions/skills/story/SKILL.md:28,49,76-84,100`），宿主在那一关按规划立场回答。现在 prompt 里写了终点，按 `SKILL.md:100`「已有明确授权覆盖的按授权走」，模型可能直接跳过这一问。改为命令起手后，它就必须问。
2. **auto-topup 的「送审」答不出去**：`end_at: story` 在交付门通过时就截停，进入检查点；检查点上 `reply` 被拒（`run_case.py:2354-2358`），TEST §4.4 又规定不传 `--answer`。结果是「归档送审」永远到不了模型，`/story archive` 不会执行。这和实跑分析 §6.1 指出的是同一件事。可以用 2.0.1 P1 的 `delivery: submitted` 终点，也可以允许检查点用 `--answer` 作答，请定。
3. **car-key 没有「只做到实现方案」的选项**：交付门只有完整设计交接、完整实现、暂不推进三项。「完整设计交接」只到施工设计准备（design_handoff），「完整实现」会进写代码。可选做法：
   - 把终点改为 design_handoff；
   - 交付选项里增加「到 Plan 为止」；
   - 宿主在 Framework 阶段边界拒绝进入 coding。

   请定。

## 3. 独立审查：U1 方向纠正

**原生 review 本来就是代码审查**：

- `demo/framework/specs/phase-rules/review-rules.yaml:1-9` 写明「Code Review 阶段规约」，审的是 code-review 产出的 `review-report.md`。
- `demo/framework/docs/operations/request-harness.md:24-28,59`：review 请求的示例是「审查 Repository 查询代码」，targets 是源码；它复用的是代码审查的章节、问题、计数和引用检查。
- 规则本身就面向代码：
  - 问题分类限定为分层违规、接口不一致、资源引用、命名规范等；
  - `issue_to_coding_rule` 要求分类对得上 coding-rules；
  - `review_scope_to_design` 要求审查范围对上 plan 的模块变更表。
- `check-review.ts:652` 的「涉及文件」只认代码后缀，与这个定位一致，不是缺陷。

**Framework 自己的 md 设计产物不走这条路**：

- spec.md、plan.md 由各阶段的脚本检查加 AI verifier 核（`harness/prompts/verify-spec.md`、`verify-plan.md`）；
- 蓝图走 checker 加独立质询（§5）。
- Framework 没有面向「需求说明类文档」的独立审查请求。

**对 2.0 的影响**：

- Story 审查报告被迫套用代码审查的格式和分类，本轮的分类只能选「逻辑错误、异常处理、其他」。
- 问题一指向 md 就过不了文件追溯，审查者只好补无关的 JSON 绕过去（实跑分析 F05）。
- 选用代码审查请求是 2.0 步骤 2 的决定。我和设计者当时都没核它适用于什么对象。

**建议**：U1 不再请上游修后缀，二选一，请定：

1. 向上游提**新功能**：文档或设计产物的独立审查请求；
2. Story 审查改用与文档相符的现有机制。如果现有原生能力都不合适，要在「不另造独立 verifier」的原则下给出补位方案。

## 4. 入口发现：U2 定性

- 宿主（opencode）给模型列可用 Skill 时，每个只带一句描述，模型靠这句选入口。
- 原生物化把扩展 Skill 的描述写成固定的「实例扩展 Skill：story」（`demo/framework/harness/scripts/utils/instance-skill-bridge.ts:338`），没有带上 `story/SKILL.md` 自己的描述。原生 spec 的描述是「spec 撰写」。
- 1.9.8 由扩展自己写入口时，AGENTS 里有一行「需求流程入口：`/story`…」（`demo/AGENTS.md:107`）。2.0 改为原生物化后，这一行没了。

这是原生物化的能力边界，不是缺陷。改为命令起手后，它不再影响 Case 起手，但仍影响真实用户用自然语言提需求。是否要求上游保留描述、Extension 在原生允许的范围里还能做什么，由设计者定。实跑分析 F02 已经说明，入口描述只是车钥匙失败的原因之一。

## 5. 独立质询：U3 归因

**结论**：不是 Case 的问题。Framework 只有规则和字段检查，Extension 也没有设计这一环；被测模型是在这个缺口里照字段要求把内容填上了。

**Framework 3.1.0**（逐文件核过）：

- **规则写了**：`skills/reference/app-component-blueprint-workflow.md:28,93-94` 要求在隔离上下文里质询，编写方不得自证。
- **执行路径没有**：
  - 没有质询用的 agent 定义。phase verifier 只服务 Feature 阶段，没有蓝图阶段，也没有对应的 prompt。
  - 质询者拿到什么输入、交回什么、原始报告存在哪，都没有定义。
  - 没有与蓝图 revision 绑定的请求或回执，无法证明质询真的跑过。
- **检查只核自填字段**：`harness/scripts/utils/blueprint-questioning.ts:77-157` 只核 status、isolated_context、provider_id 与作者不同、各项非空。`frontier_fingerprint` 只要非空就行，没有定义，也不复算。
- **生成函数没人调用**：`createIndependentQuestioningResult` 在发布件里没有调用方。
- **作者只能去读源码**：作者只能读 checker 源码去凑字段，而 `agents-entry-detail.md:87` 又写着「不要读 framework TS 源码反推门禁判词」，两处矛盾。

**Extension 2.0**：

- `extensions/hooks/blueprint/reviewer.md` 是写给「在隔离上下文里质询蓝图的审查者」的。可是 `extensions/skills/story-knowledge/SKILL.md:8,14` 又说质询的知识任务「由发起设计的一方」调用，等于作者自己来做。
- manifest 只能用 `phase_bindings` 绑定 Feature 阶段；Framework 明确没有 `before_component_design`（`docs/operations/component-design-host-adaptation.md:345-346`）。`skill_assets` 要 component-design 引用了才生效，它没有引用。所以**没有任何原生步骤会把质询页交给一个独立执行者**。
- 步骤 2–3 只验收了静态接线和 schema，没有核真实调用，这一项不该签过。

**被测模型**：没有可走的路，就按 checker 的要求让蓝图作者填出了「完整的独立质询」。行为不对，但根因在上面两层。

**建议**：

1. 2.0.1 由设计者补全「谁来执行质询、质询页怎么送到、做不到时如实披露未质询」，用宿主现有的子代理能力，不另造调度。
2. U3 改为向上游确认「独立质询预期由谁、用什么入口执行，结果记在哪里」的提问。上游答复之前，Extension 按披露未质询处理，不写 complete。

## 6. 请设计者定

1. auto-topup 的送审怎么作答：`delivery: submitted` 终点，或检查点 `--answer`。
2. car-key 的「到实现方案为止」怎么表达：改终点、加交付选项，或在阶段边界拒绝。
3. §2.2 各处多余信息的改法，以及 §2.4 的规则与测试同步。
4. U1 改为新功能请求，还是 Story 审查换用其他机制。
5. U2 是否向上游提，以及 Extension 侧能做什么。
6. U3 的 Extension 补位设计，以及向上游提问的措辞。
7. 2.0.1 是否加一节「原生能力适配核实」：逐项写清每项原生能力的设计对象、执行者和留证。
