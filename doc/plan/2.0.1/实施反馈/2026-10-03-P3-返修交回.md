## 2. R1 报告解析

`independent-review.mjs` 的 `table/judge`：

- 表格先核表头下一行是分隔行、列数与表头相同，再逐行核数据列数。读不完整就判 `report_invalid`，不丢行。
- 材料位置先去掉章节定位（`#…`）和行号（`:行`），取出含路径分隔的词，逐个与本次材料集合精确匹配；一个不在集合里就算无效。
- 总体结论只读该节第一个非空行，要以 pass/warn/fail 开头，再写理由（同一行或下一行）。

测试（`test_the_contract_refuses_what_it_cannot_trust`）新增五种情况：
- 发现表缺分隔行，且 MAJOR 被改成 pass：判 `report_invalid`，MAJOR 没被吞掉；
- 发现行少一列：判 `report_invalid`；
- 引用不存在的 `story.md.bak`：判 `report_invalid`；
- 带章节定位的真实路径：判 `warn`；
- 结论不在第一行：判 `report_invalid`。

原有的 YAML 引用、材料键不对、标题只是「含结论」等情况保持。

## 3. R2 未审查交付

| 合同 | 做法 |
|---|---|
| 核实际能力 | `framework-access.hostReviewer`：用原生 `loadFrameworkConfig(...).agent_adapter` 与 `adapter-catalog.resolveVerifierSubagentDeclared` 读当前 adapter 的 `verifier_subagent` 声明。声明能派审查子代理时拒绝授权；记录之后宿主改成能派，授权也不再适用 |
| 授权记录 | 改由 `story_flow.py unreviewed --reason --reply`（`lifecycle.cmd_unreviewed`）写进流程契约 `review_waiver`：原因、原话、`by: human`、adapter、时刻，以及授权所针对那一版的材料键。人签与发布确认都在流程契约里，契约只由 Python 侧保存。准备记录只存 `waiver_at` 引用。`--withdraw` 撤回。`story-build review --action unreviewed` 已退出，换成只读的 `waiver-check` |
| 不撤销已知阻断 | `reviewResult`：当前回复位置还没有回复时，从同一份材料（同一报告目录）里由新到旧取第一份有效结论；之前判 fail 的仍是 fail。授权前要求结果是 `report_missing`，所以「先 fail → 重新准备 → 授权」被拒 |
| 披露进交付件 | 准备开始时由 `pendingDisclosure` 判一次这一版是否沿用授权，条件是：授权给在上一次准备的那一版上，或已随它沿用过；材料没再变；宿主仍不能派审。Review 渲染与 Story 写入都用这个结论。<br>- Review：题头提示之后、议题之前写「审查状态」机器区；<br>- Story：在章节合同 `09-rollout.review_status` 指定的交付章末尾写同名机器区。<br>披露在算材料键之前写入，重跑准备字节不变。<br>原来只写一句「不涉及」的交付章，判空、判不涉及时按去掉机器区后的作者正文算（`document.authoredText`），不因披露变成「缺交付物一节」 |
| 消费 | 交付门 note 写明「已写进 Story 交付章与 Review 题头」；登记照旧接受 unreviewed |

测试（`AnUnreviewedDeliveryNeedsAHuman`）覆盖：
- 没定稿或没原话时拒绝；
- 授权后两件都有披露（Review 的在题头之后、议题之前），重跑准备字节不变，登记与交付通过；
- 宿主声明有能力时拒绝；
- 先 fail 再重新准备，结果仍是 fail，授权被拒；
- 材料变了：先判 `subject_stale`，再准备后是 `report_missing`，Story 里的披露撤掉；撤回授权后真正复审判 pass。
