## 3. R2 Story 门禁：总量与分段共用一份解析

位置：`measure_run.py` 的 `gate_call` 与 `gate_summary`。

- **命令识别**：按段切开命令。认脚本名（`harness-runner`、`story-build.mjs`、`story_flow.py`）后，取脚本后的第一个位置参数作动作；`--feature`、`--action`、`--phase`、`--deliver` 不论顺序。旧的三个正则 `HARNESS_CMD_RE`、`STORY_GATE_RE`、`STORY_REGISTER_RE` 和 `REGISTER_FAIL_RE` 已退出。
- **结果只读该命令的结构化结论**：

  | 门禁 | 通过 | 失败 |
  |---|---|---|
  | `story-build check` | 末行「通过」 | 「N 处未通过」 |
  | `review --action check` | JSON 行的 `result` 为 pass、warn、unreviewed | 其余已知结果 |
  | `story_flow.py story` | JSON 行的 `success` 为 true | `success` 为 false |
  | harness | `Total` 行 FAIL 为 0 | 有 FAIL 检查行，或 `Total` 行 FAIL 大于 0 |

  读不到结论的记 `unknown`，不当作通过或失败。不在任意正文里搜「fail」。
- **`gate_summary` 一份计算，全程与分段共用**，给出：
  - `first_gate`：动作、对象、结果、失败数，涵盖 Story 与原生阶段，替代 `first_harness`；
  - `first_story_register`；
  - `gate_rounds_with_fail` 与 `gate_rounds_unknown`；
  - `rework_min`：按同一动作、同一对象，从失败算到下一次通过；结果未知的那一轮既不开始、也不结束返工；
  - `rework_open`：到最后还没修好的动作与对象。
- **其余字段**：门禁时间（`gap_sec_by_kind.gate`）和 `harness_runs` 也从同一份判定取；同一 check id 跨轮计数只取 harness 门禁。耗时仍注明是事件间隔归属的近似值。

测试（`StoryGatesCountFailuresAndRework`）：

| 情况 | 结果 |
|---|---|
| 同一对象审查先失败、后通过 | 失败 1 轮，首次门禁为 fail，返工 1 分钟 |
| 首次就通过（warn） | 无失败、无返工 |
| 参数换序（`review --feature N --action check`） | 与原顺序结果相同 |

| 两个对象交错（A 失败、B 失败、A 通过、B 仍不通过） | A 返工 2 分钟，B 列为未修好 |
| 结构检查与登记 | 各读自己的结论 |

## 6. 验证并行化（用户 10-03 指示，维护工具）

用户要求全量与失效形态都并行，避免等待。改了三处：

| 改动 | 做法 | 验证 | 耗时 |
|---|---|---|---|
| 失效形态内部并行 | `check_failure_modes.py` 新增 `--jobs`，缺省取 CPU 核数，最多 32。每条形态的夹具自检（正反夹具各一项）和真实目标检查拆成独立任务，放进进程池并行跑。结果先按台账顺序排好位置再回填；`--jobs 1` 为串行，排障时用 | 并行输出与串行逐行比对：207 行完全一致 | 约 380 秒 → 141 秒 |
| handback 三条通道同时跑 | `verify.py` 按「通道」组织：全量、模板加失效形态、其余离线检查三条通道同时起跑，结论按完成先后打印，最后按固定顺序汇总 | 同时跑一轮：全量只有已知的 `test_run_measurement` 失败，失效形态 58 条 FAIL 0，其余都通过，与分开跑一致 | 约 10.5 分钟 → 343 秒 |
| 拆慢类 | 按 `tests/README.md`「用时预算」，把 4 个每条用例各自准备夹具的慢类按主题拆小，辅助方法挪到共同基类：`StoryIsRegisteredAgainAfterChangesPart2` 拆为 2 个；`TheReportIsCheckedReadOnly` 拆为 3 个；`AnUnreviewedDeliveryNeedsAHuman` 拆为 2 个；`TheChapterIsCheckedBeforeItLands` 拆为 2 个。类级共享夹具的 `TheDerivedContractCarriesTheObligations` 不拆，拆开会多造一次 | 拆前拆后都是 364 条，全部通过 | 全量单独跑 243 秒 → 213 秒 |

`test_verify_entry.py` 改为核三件事：三条通道的划分、模板在通道开跑时才建、汇总里有失败时退出码非 0。TEST.md §5 同步，写明同时跑的前提：各步只写自己的位置，共享夹具有锁。

剩下的瓶颈是整机 CPU，不是并行度：
- 拆类之后，最慢的类只要 107 秒，全量却仍要 213 秒；
- 同时跑时全量被拉长到 343 秒，因为两边各起约 32 个进程，机器只有 32 核。

要再提速，得减少总工作量，不能再靠加并行。例如，失效形态的产物类检查每条都要重造一份设计好的夹具，约 17 秒一次，可以改走 `shared_state` 复用。这一步还没做，等用户决定。
