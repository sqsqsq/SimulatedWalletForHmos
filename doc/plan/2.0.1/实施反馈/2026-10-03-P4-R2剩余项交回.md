## 1. 结论

R2 剩余两点已修，只改了 `test/scripts/measure_run.py` 的门禁识别：

- 脚本名只出现在读取或引用里，不算门禁；
- 一次调用执行了多个门禁时，合并输出不归给其中任何一个，按调用单列。

只执行一个门禁的普通调用，统计方式不变。

- 验证（`verify.py handback`，三条通道同时跑，墙钟 323 秒，原始输出在 `output/verify/20261003-211307-handback/`）：
  - 全量 1477 通过，1 失败，失败的仍是 `test_run_measurement`（spec 2.1.0 历史参考里的 png）；
  - 失效形态 58 条 FAIL 0；
  - CLI 测试 29 条通过，compileall、validate_clis、45 个 `.mjs` 都通过。
- 预算：Extension 没有变化，总量 13,875，累计 G 5,236、X 5,354，N = −118，R ≈ −3.8%。

## 2. 改法

- **`executed_gates(command)`：认出实际执行的门禁。** 复用已有的命令分段；每段里，脚本名前面只有解释器（`node`、`python`、`npx`、`ts-node` 等）和开关时，才算执行。前面是 `cat`、`grep` 这类读取动词时只是在读源码，不算。不是门禁的子命令（如 `skeleton`）也不算。没有实现通用的 shell 解释器。
- **`gate_call(event)`：按执行了几个门禁分情况。**
  - 只执行一个门禁：算一轮，结果从输出里该命令的结构化结论读（抽成 `_gate_result`，内容不变），读不到是 unknown。
  - 执行了多个门禁：记为 `unattributed`，列出候选（动作@对象）和调用序号。不算任何对象的通过或失败，不开始、不结束返工，也不推断每条命令各自对应输出的哪一段。
- **`gate_summary`：写明统计单位。**
  - 「门禁轮次」只指只执行了一个门禁的调用；
  - 归属不了的调用单列在 `gate_calls_unattributed`，全程和分段都有，人读输出逐条列出候选；
  - 注释改为：轮次与调用计数分段可相加，返工时长按段各自计算，跨段的返工区间不保证分段相加等于全程。
- **文档**：文件头口径和 TEST.md §6.1 同步。

## 3. 验收

`StoryGatesCountFailuresAndRework` 新增三条：

| 情况 | 结果 |
|---|---|
| `cat` 读 harness 源码、`cat` 读 story-build 源码 | 不计门禁次数、不计门禁时间、不记未知，没有首次门禁 |
| 一次调用先后执行 A、B 两个审查核对，合并输出 fail 又 pass | 失败 0 轮、未知 0 轮；单列一次调用，候选为 `story_review@A`、`story_review@B`；A 没被记成通过 |
| A 单独失败之后，一次调用合并执行 A、B，输出都是 pass | A 仍在 `rework_open`，返工时长为 0 |

已有的单门禁「失败后通过」、参数换序、首次通过、读不到结论、对象交错等测试保持不变，全部通过。

用评审的原始反例（`output/story/2.0.1-p4-rereview-20261003/gate-probes.json`）重放：
- two_reviews：记为 unattributed，候选是 A、B；
- read_source、read_harness：都不是门禁。

拿真实记录核对：car-key 10-02 那一轮原来统计为 harness 运行 3 次、未知 2 轮，其中 2 轮其实是在读 harness 源码。现在统计为运行 1 次、未知 0 轮。自动充值 10-02 的统计不变：没有合并执行门禁的调用。
