# P2：真实设计与知识承接

目标：解决分析 F03/F04/F06，不把 canonical 合法等同于设计成立。

必读：原生 `component-design/SKILL.md` 及其当前引用的发现/设计/质询协议；Extension `reference/evidence-rules.md`、manifest 两项设计资产、`hooks/shared/knowledge-task.mjs`、`knowledge-application.mjs`、`skills/story/contracts/knowledge-application.schema.json`。职责和数据保持在这些已有入口，不新增知识决定文件。

## 1. 设计交接必须交动作，不能只交“写出通过的 YAML”

Story 完成取材后交原生 component-design：项目根、component/blueprint 身份、冻结输入/原生 materialization、真实人签、请求终点为设计准入与评审投影。作者在发现前获得扩展作者要求及知识任务；其任务是形成业务与工程设计，不是读 checker 找到最短通过路径。

原生设计负责方将当前候选、冻结原始需求、SE 转写、设计决定、相关完整知识和扩展质询要求交给**实际独立的质询执行体**。作者不能替质询者填回答、provider 或隔离结果。现有宿主 task/verifier 能力负责派遣；Extension 不写派遣循环。

质询者输出实际问题、引用位置、当前范围影响和结论，保留原始报告。设计负责方处理问题、必要时问人，再按原生协议形成 questioning 与准入结果。保留报告来源/版本关联，用原生现有字段表达；具体公共字段不足时按 U3 提交上游，不能新建 Extension receipt 冒充原生能力。

Reviewer 验收应检查真实调用与输入，而不只看 canonical 的 `isolated_context`。没有独立能力就披露未质询，不能写 complete。这里不是为所有恶意作者建立密码学防伪系统，而是让正常流程的生产者、消费者与交回相符。

## 2. 来源与推断

`evidence-rules.md` 保留 SE 转写职责，进一步固定以下合同；作者页和质询页引用该处：

| 内容 | 谁产生 | 权威及消费 |
|---|---|---|
| SE 明确写出的接口字段/版本/错误 | 模型忠实转写，脚本核路径和字节摘要 | 指向冻结原件及定位；可声明外部确认事实 |
| 本地字段映射/类型选择/缺省策略 | 蓝图作者形成设计决定 | 有据推断或设计选择；不能标作 SE 转写 |
| 材料没有给出的字段 | 保持未知，向负责方澄清 | 不补成必填/不可空/版本号；是否阻断取决于当前采用设计是否依赖 |
| 人工裁定 | 实际人的答复 | 原生 authority 指真实答复，不由角色名或模型推荐推得 |

转写文件是派生物，不因有 `source_ref` 就自动成为外部权威。独立质询逐接口对照原件；不同接口可以具有不同来源完整度。模型推断使用原生允许的证据强度和决定状态，脚本只核字段与关联，不能用词频判断“真的是 SE 原话”。

缺口与范围按实际依赖处理。没有成功响应约定，不能用空字段 `drop` 表示“不需要响应”；`drop` 只在确有来源字段且有丢弃理由时用于真实映射。准入被阻断时，补材料、经授权调整设计范围，或交未决草稿；禁止只移动 `needed_by` 来绕过当前依赖。interactive 不借 `headless_assumed` 代替必要询问。

## 3. 知识从判断到实际设计

复用现有字段，生产者为蓝图作者，独立质询核实际落点：

- 项目事实使用 `discovery.facts[].value.knowledge` 的 unit/form/source_sha256，并保留实际事实内容与 provenance。来源登记为激活知识的事实不得因 value 写成字符串而绕过知识检查；工程文件事实维持原生形态，不强迫全部套知识结构。
- 规约决定沿用 `knowledge_application`、outcome、requirement、target_refs；模型判断使用 `answered_with_evidence`，实际人工裁决才用 `decided_with_authority`。已应用要求指向承担它的实体，不仅指向决定自身或一个宽泛节点。
- 模式的选择、调整、拒绝都给实际理由；selected/adjusted 的 roles 指实际设计对象，下游从对象取角色，不从 Story 反推。
- 配置、事件、数据策略等精确明细使用当前已有 `story_details` 及真实 evidence_refs，或已有对应原生设计对象。需要但未形成时记录 pending，不能在 Story 手工写成已定。
- 设计准入不要求提前编造 Coding 细节；但当前已决定的义务应进入实际 contracts/acceptance 或已有设计明细，CU 派生才能取得。

机械检查补在现有知识加载/验证模块，依据已声明的来源与结构判缺失；不以业务名称推适用性，不以字段存在推定语义合格。

| 消费者 | 必须实际取得的内容 |
|---|---|
| Story | 当前准入设计、决定及精确明细；未知照实展示 |
| 原生 CU 设计引用/物化 | 本 CU 承担的设计对象、具体义务与模式角色 |
| 作者知识任务 | 原文、已成立决定、当前施工输入及缺口 |
| post_check / pre_verifier | 契约实体上的 must/角色与当前阶段证据，缺少实际落点不算通过 |
| UT/Testing | 同一具体义务的验证责任与接受条件，不仅收到知识标题 |

## 4. 验收与退出

定向用现有 `test_knowledge_application.py`、`test_knowledge_task.py`、`test_cu_knowledge_chain.py`、`test_requirement_source.py`：

1. 一个有完整外部协议的接口、一个只有业务意图的接口：前者忠实转写；后者保留缺口/推断，不能从前者借类型成为外部确认事实。
2. 激活知识事实缺结构化值时报告输入不全；普通工程事实可正常消费；空知识清单与损坏登记按现有合同分别处理。
3. 有具体规约/模式落点时，原生派生与复用后仍由实际 CU 消费；无 Story 的直接 Framework 入口一样取得知识。
4. 独立质询输入包含原件、当前设计与完整必要知识；真实调度日志和原始报告支持 complete。作者自填 complete 的构造对象只证明 schema，不能作为独立质询正例。
5. 不适用有真实条件与理由；不强制每条知识生成测试专名、固定行数或同一设计落点。

本包必须退出作者代写质询结果、check 错误反推业务范围、Story 自建精确设计权威的指令；保留合法草稿与明确未决。用结构反例核字段，用正常需求独立质询核语义，二者不能互代。预算引用总览 P2。
