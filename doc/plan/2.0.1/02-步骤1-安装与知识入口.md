## 3. 身份与知识入口

修改 `hooks/shared/paths.mjs` 和调用它的契约、作者、审查读取器。Framework feature 使用其 `feature-identity.js`；Story 上下文仍定位需求目录，并从 flow 读取蓝图关联。非法 CU 身份不回退平铺目录；只读操作不创建目录。

新增 `skills/story-knowledge/SKILL.md`，唯一职责为按本节命令提供当前动作的知识任务。由 phase_bindings 引用；各阶段 author 页继续承担写作责任，动态数据共用 `hooks/shared/knowledge-task.mjs`。入口不创建 Story、不推进阶段、不作适用性判断。

修改 `hooks/shared/knowledge.mjs` 的清单读取以消费 manifest 1.1 路径登记。类型和形态仍从 frontmatter 解析；facts/facets、facts/halves、constraints/entries、patterns/halves 规则保持。明确空清单返回无激活知识；登记文件缺失、坏 frontmatter 和非法形态集中报告。

本步同时实现 knowledge-use 中对步骤 3 §2.1 字段的只读访问及 schema，以供 knowledge-task 消费；步骤 3 负责把设计写作、实体检查和旧生产者退出接上同一访问器，不另写第二套解析。本步验安装与任务输入，步骤 2 验人读交付，步骤 3 验完整承接；全部完成前开发版仅用于对应的隔离验证，不发布给正式需求使用。

设计要求页通过总览补充 A 的两项 skill_assets 登记。作者页在设计发现前交索引与必要原文，独立质询页提供同一真实来源及应用判据；方法篇章在相应决定前完整提供。直接 component-design 与 Story 转入同样消费。

Feature 入口在 `before_phase_work` 取得本阶段任务材料，审查前提供同一知识依据；适用 phase 以实际 workflow 的 Feature phases 为准。直接 Spec/Plan/Coding 等入口不会因缺 Story 身份而失去知识。

### 3.1 唯一入口、参数和失败结果

下面命令中的 `<ext>` 为消费工程配置的 extension_dir，`<root>` 为该工程根，路径含空格时按宿主 shell 的单参数引用传入。

```text
node <ext>/hooks/shared/knowledge-task.mjs --project-root <root> --blueprint <id> --action discovery --audience author
node <ext>/hooks/shared/knowledge-task.mjs --project-root <root> --blueprint <id> --action questioning --audience reviewer
node <ext>/hooks/shared/knowledge-task.mjs --project-root <root> --feature <原生feature-id> --action plan --audience author
node <ext>/hooks/shared/knowledge-task.mjs --project-root <root> --feature <原生feature-id> --action review --audience reviewer
```

project-root、action、audience 必填；blueprint/feature 恰好一个。blueprint 允许 discovery/design/questioning；feature 允许实际 workflow 的 spec/plan/coding/review/ut/testing。audience 为 author/reviewer。非法组合退出 2；输入损坏、登记来源缺失、非法身份或需要的契约缺失退出 1；成功退出 0。失败 stderr 给对象、缺口和责任，stdout 不输出可误用的半份任务包。

discovery/design 可在蓝图尚未创建时取知识，任务包明确“设计尚未形成”；questioning 要有可读且结构合法的当前草稿，不能要求它已经通过依赖本次质询的准入。施工 Feature 通过原生 identity/resolver 获取 CU、蓝图引用及实际输入，过期引用明确失败。合法非 CU 维护 Feature 只读自身原生 facts/acceptance/contracts，按当前动作落实知识；不生成蓝图或 Story。此路径的局部判断随当前原生产物表达，不作整单蓝图决定投影。

成功 stdout 为 Markdown，固定六个顶层内容块：`当前动作与对象`、`激活知识及原文`、`有效事实与决定`、`当前契约与义务`、`本次完成条件`、`缺口与责任`。原文按激活顺序提供，不截断；空清单明确列零项，未登记文件不读。方法知识的上下篇完整列出并指明本动作应使用的部分，由模型判断适用；已成立决定不能因重复读取被重新猜测。

before_phase_work 调用 action=当前 phase、audience=author；before_phase_verify 调用同 phase、audience=reviewer。reviewer 任务输出由调用者随原始输入一起送审，磁盘存在不代替送达。Blueprint 作者要求页 `hooks/blueprint/author.md` 调用 discovery/design；`hooks/blueprint/reviewer.md` 调用 questioning。共同字段定义与示例唯一见 [步骤 3 §2](04-步骤3-知识承接与更新恢复.md#2-知识承接)。

### 3.2 manifest 的完整机制登记

以下为本版机制侧片段，按六个已有 Feature phase 给出全部绑定；YAML 锚点只减少重复文本，展开结果相同。name/description 保留目标身份，knowledge 保留目标清单；示例空清单表示合法空目标，不用于覆盖目标已有登记。包的业务知识路径继续从自身现有 manifest 继承。

```yaml
schema_version: "1.1"
name: sample-extension
version: "2.0.1"
description: 需求与知识协作
provides:
  skills: [story, story-adaptation, story-knowledge]
  knowledge: []
  skill_assets:
    component-design:
      extension_author_requirements: hooks/blueprint/author.md
      extension_review_requirements: hooks/blueprint/reviewer.md
  hooks:
    spec:
      post_check: [hooks/spec/post_check.mjs]
      pre_verifier: [hooks/shared/pre_verifier.mjs]
    plan:
      post_check: [hooks/plan/post_check.mjs]
      pre_verifier: [hooks/shared/pre_verifier.mjs]
    coding:
      post_check: [hooks/coding/post_check.mjs]
      pre_verifier: [hooks/shared/pre_verifier.mjs]
    review:
      post_check: [hooks/review/post_check.mjs]
      pre_verifier: [hooks/shared/pre_verifier.mjs]
    ut:
      post_check: [hooks/ut/post_check.mjs]
      pre_verifier: [hooks/shared/pre_verifier.mjs]
    testing:
      post_check: [hooks/testing/post_check.mjs]
      pre_verifier: [hooks/shared/pre_verifier.mjs]
  phase_rules_overlays:
    spec: rules/spec-rules.overlay.yaml
    plan: rules/plan-rules.overlay.yaml
    coding: rules/coding-rules.overlay.yaml
    review: rules/review-rules.overlay.yaml
    ut: rules/ut-rules.overlay.yaml
    testing: rules/testing-rules.overlay.yaml
phase_bindings:
  spec: &knowledge_binding
    before_phase_work:
      - {kind: skill, ref: story-knowledge}
    before_phase_verify:
      - {kind: skill, ref: story-knowledge}
  plan: *knowledge_binding
  coding: *knowledge_binding
  review: *knowledge_binding
  ut: *knowledge_binding
  testing: *knowledge_binding
```

若实际发布 workflow 缺少这里某 phase，安装在写前报告该具体不匹配，回设计者核发布合同，不静默裁剪绑定。当前原生 parser 支持 YAML 映射和数组；补充 A 的两个资产键只有上游接入后才有送达语义。

### 3.3 安装元数据合同

adaptation.yaml 只保存 `adapters`、`adapted_for` 两项现有值。升级从目标旧 manifest 一次性归位；已有新文件时只读新文件，旧字段同时存在且值冲突则在写前报告。归位属于本次升级操作，运行期不回退旧字段。源对接类型维持现行 `stand-in` 与业务实现来源语义，目标已适配版本仅在知识/对接/在途事项全部交回后更新。目标知识激活登记保留原顺序与内容，加载器支持 1.1 的 string 或 path 对象并归一为实际文件路径。

两键均为可选字符串；新装真实目标生成 `{}`，不继承 Demo 的 stand-in 或已适配版本。adapters 缺席仍沿现行“业务来源”语义，stand-in 明确为替身；adapted_for 缺席按现行未完成适配处理，演进比较起点为 0。新格式要求 adaptation.yaml 文件可读且根为映射，坏文件报错；只有这次升级过程可从旧 manifest 取值。目标对接缺失仍按既有适配缺口报告，不能因元数据归位声称对接已实现。
