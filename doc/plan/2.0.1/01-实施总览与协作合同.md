## 2. 对象与权威

需求保留 `<features_dir>/<需求标识>/{RR,SR,inbox,AR}`；`AR/design.md` 为上游开发需求，`AR/story.md`、`review.md` 为人读件，`AR/story-src/` 保存材料、人工决定、写作和更新记录。Framework 使用 `<features_dir>/<blueprint_id>/blueprint/` 与 `<features_dir>/<blueprint_id>/<change_unit_id>/`。

- 新需求默认以需求标识作为 blueprint_id；接续已有蓝图时显式指定，身份冲突回使用者确认实际对象。
- 关联只存于既有 `story-flow.json`，包含 component_id、blueprint_id。默认同名仍须校验实际归属。
- Story 命令 `--feature` 表示需求目录标识；Framework hook 的 feature 经原生 `feature-identity.js` 解析。两类入口分别取得上下文。
- Extension 只读 Framework 的蓝图、CU、运行和闭环结果。施工授权、调度和完成判断由 Framework 原责任方承担。

| 内容 | 唯一权威 | 生产者及消费者 |
|---|---|---|
| 原始材料、采用关系 | 实际材料与既有材料登记 | 对接/导入生产，理解者、设计者和审查者消费 |
| 范围和人工决定 | 人的原话及对象绑定 | 人决定，flow 记录，双方消费 |
| 蓝图关联 | story-flow.json | flow 写入，Story/更新读取 |
| 设计输入版本 | 本次冻结的项目内来源文件 | 导入交接冻结，Framework 以路径和原始字节 hash 引用 |
| 项目事实使用依据 | 蓝图 discovery facts | 设计者结合真实来源形成，下游回查 |
| 规约适用、模式选择 | 蓝图 decisions | 设计责任方形成，Story 展示、CU 落实 |
| 施工细化 | 原生 contracts/acceptance 及有效引用 | Framework 对应责任方形成，各阶段消费 |
| Story 表达及人工 Review | Extension 人读件 | 成文者表达，评审人作决定 |
| 施工和组合完成 | Framework 原生结果 | Extension 查询并解释 |

知识保留 facts×facets、facts×halves、constraints×entries、patterns×halves。激活清单按目标登记读取，类型与形态来自知识正文。知识应用 decision 使用原生结构及可说明用途的 kind，保留来源、理由和实际落点；模型有据判断与人的权威裁决按真实来源区分。`spec/knowledge-use.yaml` 的独立决策真源职责退出。

## 3. 正常交接

范围确认后，模型形成有来源的目标、约束、验收意图与未决。脚本冻结本次交给 Framework 引用的文件版本，计算原始字节 SHA-256；落在 story-src 下按材料摘要区分的输入目录。冻结件一经引用便保留，新材料形成新版本；恢复不删除这些文件。

系统来源使用原生 `requirement-source-materialization@1`，字段遵循上游 schema：身份、items、source_ref、source_sha256、provenance、authority。脚本计算确定性字段，语义和权威来自实际材料。直接本地来源交项目内文件，由 builder 规范化，保持原始输入可取。

默认链条：**需求确认 → 来源交接 → 蓝图设计及准入 → Story/Review → 独立人读审查 → 交付选择**。component-design 请求明确止于准入和评审投影，零 CU 可交付 Story。Story 不依赖 Spec/Plan；后续施工细节在相应责任阶段形成。

交付选择为送审、完整设计交接、完整实现或暂不推进。本地单无线上归档，已有适用授权直接使用。完整实现由外层入口交 Framework 完成 CU/readiness 及 attended 运行。

### 4.2 上游补充 A：设计动作消费扩展要求

实际缺口：manifest 支持 skill_assets，但 component-design 未完整接入 Extension 作者要求和独立质询要求。

合同如下：

1. 复用 `provides.skill_assets.component-design`，两个资产键分别为 `extension_author_requirements: hooks/blueprint/author.md`、`extension_review_requirements: hooks/blueprint/reviewer.md`，路径相对消费扩展根。
2. 作者要求在 current-facts-discovery 前读取；质询要求随当前蓝图及必要知识输入交给独立质询方。

4. 未登记保留原生行为；登记却不可读时报告缺失路径、影响动作与责任，不记成已消费。
5. 直接入口与经 Story 转入使用同一路径；独立质询的实际上下文须包含要求与必要原文。

### 4.3 上游补充 B：独立产物审查

实际缺口：当前 verifier 请求绑定 Feature phase，无合法的无 Spec Story 审查调用面。

输入：项目根、产物标识、审查任务文件、材料集合、结构检查结果、报告目录。输出：沿既有 verifier 能力生成短 request、原始报告、当前对象绑定及验证结论。

- `prepare` 准备请求；宿主按既有能力派独立审查；`check` 验证原始报告与当前材料并返回结论。
- 独立产物不制造 Feature/phase 或阶段 receipt，不推动 CU/run。
- 相同材料复用有效审查；时间戳、报告登记不改变对象，输入变化后旧报告不作为当前结论。
- 结构检查失败先修确定性问题；报告不合协议时保留原始回复并报告，作者不得补写审查结论。
- 无审查能力沿既有策略披露；Extension 保留已授权的未审查交付披露，不记 PASS。
- Story 判据与业务结论由 Extension 负责；请求、对象绑定和验真复用 Framework。

必要性：无 Spec 的人读交付仍要独立审查。沿用 Spec 审查会保留已决定退出的依赖，在 Extension 复制通用验真则造成双实现，因此由 Framework 补现有能力的调用面。上游交付须提供实际命令和输出协议及正反例；本合同不把建议动作名冒充已经存在的 CLI。

两项上游能力未交付时，步骤 1/2 的相应前置未达成。先完成可独立的设计交接，实际接线依上游发布的协议执行；若发布合同偏离本节，回维护设计者调整直接消费者，不由实施者猜接口。

### 4.4 补充 B 的待上游接受接口合同

以下是提交上游确认的明确接口提案，**当前不可调用、未获上游接受、未实施、未发布**。维护设计者负责取得上游响应并对照本表更新交接证据；本轮未通过工具联系其他任务或代上游作接受决定。步骤 2 的调用者禁止按假定路径实现后宣称已接通。

建议公共入口为 `framework/harness/scripts/artifact-review.ts`，命令候选：

```text
npx ts-node scripts/artifact-review.ts --action prepare --project-root <root> --input <review-input.json> --json
npx ts-node scripts/artifact-review.ts --action check --project-root <root> --request <request.json> --report <raw-report.md> --json
```

输入 descriptor 为 `{artifact_id,task_path,material_paths,structural_results,report_dir}`；路径全部为项目相对路径，artifact_id 是明确需求身份及 story-reader 用途。task_path 为 Extension 生成的读者任务；material_paths 为步骤 2 §4.2 的完整审前材料，structural_results 只含稳定的判据 id/status/severity/details，不带运行时间或命令日志。report_dir 固定为该需求 AR/story-src/review。Framework 验证路径/内容并计算 subject；Extension 不接受外部手填 subject。

| 动作/结果 | stdout JSON 最小合同 | 退出码与调用者行为 |
|---|---|---|
| prepare 成功 | status=prepared/reused，subject_id、request_path、report_path | 0；prepared 原样派 request，reused 仍通过 check 核当前结果 |
| prepare 无审查能力 | status=reviewer_unavailable，reason | 0；明确未审查，不造报告或 PASS |
| 输入/能力协议错误 | status=input_invalid/tool_error，issues[]，reason | 2；交付阻断，回缺失来源或工具责任 |
| check 有效 | status=pass/warn/fail，subject_id、reviewed_subject_id、report_path、blocking_findings[]、advisories[] | pass/无阻断 warn 为0；fail/有阻断为1 |
| check 缺报告 | status=report_missing，request_path、report_path | 1；当前对象未审，不按无能力处理 |
| check 报告非法/对象过期 | status=report_invalid/subject_stale，issues[] | 1；保留原始回复，按当前请求重新派审或修真实协议 |

报告由宿主派审调用方将子代理回复原样写入 report_path；Framework check 验真和判断当前对象，Extension delivery 只消费返回的事实。上游内部 schema 及函数复用由上游维护者实现，不要求复制本提案为第二套 verifier 核心。

接收条件：上述各状态有实际正反例，旧 Feature verifier 行为不受影响；相同材料重入、仅报告时间变化不换对象；正文/原话/设计/知识变更后旧报告失效；缺审查能力与报告坏/缺失分开。上游若提供等价的现有公共调用面，设计者须把它的真实命令/字段逐项映射进此表后交回，不能将未知接线留给 Extension 实施者。

依赖状态登记在本节：A=接口提案已定、未接受交付；B=接口提案已定、未接受交付；实际发布身份=未取得。只有上游回执、接口验证和发布件身份都有可查证据才更新为就绪。
