## 2. 获得授权后的两 Case 正常实跑

起跑条件：无损传输已机械证明；本轮有效上游发布件/输入协议核实；P1–P3 定向通过；用户授权；Case 源的修改与机制修改分开记账。不能边实跑边修改产品或用宿主补答案。

| Case | 需要证明 | 不证明什么 |
|---|---|---|
| 自动充值 | 真实索材、人签、独立设计质询、零 CU Story/Review、按已有授权实际送审；同会话 update 正确处理新稿/200 与 300 冲突、来源版本、反馈和重审 | 不证明 CU、Plan、Coding 或设备行为 |
| 车钥匙 | 完整本地材料交付；正常进入需求设计，Story/Review；按用户 Plan 上限完成原生 CU 准备及相应 Spec/Plan；知识具体义务在下游保持 | 不证明 Coding、UT 执行、设备 Testing 或整体施工闭环 |

两 Case 都重跑。不得只修车钥匙并把本轮自动充值当已通过；原轮保留为诊断证据。必要多 CU 安排按原方案的真实设计决定形成，不为测试强拆业务。直接 Framework 入口先作隔离机械验证，若用户授权专项行为观察再实跑，不擅自增加第三个付费 Case。

首次实际消息按宿主公开记录核完整性。输入没送达时立即把结果归测试基础设施异常，不继续用后半条任务评价产品能力；宿主不向模型讲缺陷答案。过程留存完整会话关系、作者/质询/Story 审查的真实输入、原始报告、当前需求/设计/输入版本，供设计者核实际独立性。

## 3. 后评

设计者逐项对照原始材料与实际产物，检查：业务正常/失败/结果未知、边界和人工决定、来源权威、图文、知识落点、CU 继承。样例、字数、章节行数、通过次数都不作为语义替代判据。

性能使用现有 `measure_run.py`，修复当前对新蓝图/产物审查命令的分类漏项；Task 按实际职责区分作者、质询、Story 审查及报告格式修正，不能全部计作 verifier 次数。时长同时列首段、update、人工等待、工具和子任务，标明上下文计量含缓存。只补现有计量器消费者，不新建评测平台。

三轴建议分与证据写在各 run 的 `evaluation/scorecard.md`，由用户确认；语义错误先修权威来源与流程，不从已知 Case 总结特殊放行条件。没有实际通过的能力单列未验证。

## 4. 完成条件

P1–P3 正常路径与相关反例成立；两 Case 达到真实业务终点；无伪造来源/独立质询和审查绕行；知识链有实际下游证据；旧职责无运行消费者和专用错误断言；预算获相应级别确认；独立语义评测按 TEST 经用户裁定。版本号、demo 发布和 README 当前能力同步另按用户发布决定执行，本计划不自行发布。
