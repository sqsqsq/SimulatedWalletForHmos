# 步骤 2：需求交接、Story 与独立审查

依据 [总览](01-实施总览与协作合同.md)、[步骤 1](02-步骤1-安装与知识入口.md)及 [维护预算](../../../AGENTS.md#5-维护预算与分级复核)。前置为步骤 1 通过评审、Framework 补充 B 已通过实际发布件接入。

## 1. 输入输出与职责

输入是人的请求、实际材料、已确认范围、人工原话、目标知识及有效设计。输出是一套对应明确设计 revision 的 Story/Review 和真实交付选择。Framework 建立与修订设计；Extension 取得来源、保存人签、组织人读表达并调用独立审查。

默认顺序：材料与范围确认 → 冻结设计输入 → 原生来源校验 → component-design 到准入 → 读取投影 → 写作设计与逐章成文 → 结构检查 → 独立审查 → 登记与交付。

## 2. 文件动作

以下路径相对 `extensions/`。

| materials/、import_sources.py | 复用转换、原件、图片和采用关系；增加引用输入的冻结交接 | 不复制整个工作区、不丢原始依据 |

## 3. 身份与来源交接

在既有 flow 中提供 `bind-design`，接收需求标识、component_id、blueprint_id，字段与命令固定如下。新单默认同名仍是调用者显式传值，脚本不按编号猜组件；已有蓝图读取原生身份核对。

完成需求提取后，只冻结本次被采用并交设计引用的文件，保留真实内容及必要相对引用。冻结目录按材料摘要区分；已有相同字节复用，已引用版本保持。SHA-256 使用落盘原始字节，不复用现有换行归一或短指纹作为原生 source_sha256。

系统来源生成原生 materialization；owner、formality、来源语义由实际材料或人工决定给出，脚本仅序列化及计算路径/hash。缺 authority 或来源冲突按上游结构结果报告。本地材料由 builder 规范化，不额外写 provider 文件。

传给 component-design 的请求明确“只完成设计准入与评审投影”。模型可按真实未知提出问题；当前设计缺口先由设计负责方处理。完整设计交接或完整实现授权才要求 CU/readiness。

### 3.1 flow 持久化字段及命令

章节合同 flow.schema 从当前 4 升为 5，旧单按升级演进要求在旧版收口或 init 重起。读写仍唯一由 flow.state/load/save 承担；新字段：

| 字段 | 内容及写入时机 |
|---|---|
| design_binding | `{component_id,blueprint_id}`；bind-design 写一次，重复同值不改文件 |
| input | `{snapshot_ref,snapshot_sha256,materials_digest,candidate_sha256}`；complete 在冻结和原生来源校验成功后写；materials_digest 沿现有材料比较口径，其他为原始完整 SHA-256 |
| story_basis | `{blueprint_ref,input_sha256,knowledge_sha256,files}`；story 成功登记时写。blueprint_ref 使用原生完整引用，files 为 Story、决定登记及写作设计等实际被审输入的路径→摘要 |

准入、当前 revision、CU 状态每次由原生结果读取。story_basis 记录“这份稿使用了什么”，不是当前设计状态副本。归档信息仍沿既有记录保存。

```text
python <ext>/skills/story/scripts/core/story_flow.py bind-design --project-root <root> --feature <需求> --component <组件> --blueprint <蓝图>
python <ext>/skills/story/scripts/core/story_flow.py complete --project-root <root> --feature <需求> --from AR/story-src/design-draft.md --input AR/story-src/design-input.json
python <ext>/skills/story/scripts/core/story_flow.py status --project-root <root> --feature <需求>
```

bind-design 要有 init 后的 flow。标识校验复用原生安全段规则；已有蓝图须 component/blueprint 对应，尚无蓝图允许保存明确的新建关联。不同已有绑定返回冲突，不自动改绑；同绑定退出 0、字节不变。参数错误退出 2，前置/身份冲突退出 1，普通成功 stdout 沿现有单行 JSON。

complete 接口的重要变化：原始 `AR/design.md` 保持，候选提取稿冻结为设计输入，不再覆盖上游 AR；原来 overwrite/backup 的专用提交路径退出，但上游原件保护和幂等能力保留。候选不是原始权威，source provenance 明示 extracted_analysis，并带回原始材料和真实人签。

### 3.2 派生位置与命令合法性

以下表从上到下判定；已有 update 活动优先展示 update_inputs/update_open/restore_conflicted，表中的主流程位置作为更新内实际依据。位置只由 state/routing 派生，不新增可手写状态字段。

| 位置 | 条件 | 下一动作及命令 |
|---|---|---|
| gathering | 材料关卡未确认 | round/decide；complete/story 拒绝 |
| scope_pending | 材料已定但本轮范围或必要会议决定未定 | analysis/decide；complete 拒绝 |
| input_ready | 范围已定，无完整 input | bind-design（如未绑定）→ complete |
| waiting_for_design | input 已冻结有效，蓝图不存在或尚未准入 | component-design 继续；status 只读，story 拒绝 |
| ready_to_write | 原生准入与投影有效，无当前 story_basis | skeleton/chapter/check → 独立审查 → story |
| registered | story_basis、实际文件、当前设计/知识均匹配，交付检查可消费 | 交付选择；重复 story/status 不新增审查 |
| needs_sync | 已有登记但输入/正文/决定/设计引用/知识变更 | update 或当前返修，完成相应责任再重新登记 |

complete 同候选/采用输入返回已有 input；换内容须处于 update，或 reopen 后重新确认范围。reopen 只重开需求范围决定，不清蓝图、人签历史或冻结输入；在新范围确认前登记失效。设计不存在、未准入、引用过期分别报告，不能从文件存在推定可成文。

story 在原生设计有效、当前文件通过结构和独立审查消费后保存 basis；失败不改旧 basis。update close/restore 的条件见 [步骤 3 §4](04-步骤3-知识承接与更新恢复.md#4-恢复和外部发布)。跨会话重新读取 flow、实际文件及原生引用，沿同表续行。

### 3.3 采用清单和冻结算法

新增职责模块 `materials/frozen.py`，只由 complete 调用；快照路径与摘要算法只在此定义。模型写候选 `AR/story-src/design-input.json`，形态：

```json
{
  "adopted": ["RR/prd.md", "SR/design.md", "AR/design.md", "assets/flow.svg"],
  "human_decision_ids": ["ask-1"],
  "scope_items": [
    {"item_id":"requirement-main","kind":"requirement","source_path":"RR/prd.md","authority":{"owner":"需求负责人","formality":"formal_requirement"}},
    {"item_id":"scope-ruling","kind":"invariant","source_path":"AR/story-src/human-decisions.json","authority":{"owner":"需求负责人","formality":"formal_requirement"}}
  ]
}
```

adopted 中每个真实文件必须已在本轮 materials.json 且当前仍与确认基线一致；未采用的材料保持原件并在候选分析中解释，语义完整性由设计和读者审查核。human_decision_ids 必须解析到已有真实 ask/gate 记录；`human-decisions.json` 由脚本按这些记录确定性导出原话、选项、所选项、身份与原记录定位，不由模型编造。候选提取稿自动纳入快照，标为派生分析。

源选集是 adopted 加候选稿及上述原话导出。相关本地图片/链接必须在选集，缺少时报告具体引用，要求补正采用输入；不自动全仓找同名文件。图片按 materials 已登记的实际路径复制，保留相对于需求根的结构和相对链接，不重写原文字节。候选可以引用冻结目录内同样的相对路径。

快照为 `AR/story-src/inputs/<64位sha>/`，内部 `files/<需求相对路径>` 保存字节，`snapshot.json` 保存 `{files:[{path,sha256,role}],scope_items,human_decision_ids,observed_at}`。role 为 original/image/human_record/extracted_analysis，既有 source provenance 随来源保留。files 按 POSIX path 排序，human_decision_ids 按稳定 ID 排序；快照 ID 为除 observed_at 以外上述内容按键排序、UTF-8、无多余空白 JSON 的 SHA-256，不含快照自身路径。observed_at 在首次完整冻结时由脚本记下，复用时保持；有已记录来源观测时间的 provenance 优先用原记录。文件摘要为原始完整 SHA-256，和材料轮次短摘要明确分开。

先在同父目录临时目录完整复制并复核全部字节，再原子改名；同 ID 已存在则核完整内容复用，损坏明确报错。`snapshot.json` 为写入最后的完成标志；临时目录不会被下游读取。系统单在完整快照中生成 materialization.json 并跑原生来源 checker，成功后 flow.input 才指向它；本地单向 builder 交冻结文件和 snapshot 清单，不额外制造 provider manifest。中断重试复用完整快照，未完成文件不被算为有效 input。

### 3.4 materialization 字段来源及多材料例子

| 原生字段 | 唯一生产依据 |
|---|---|
| artifact | 固定原生 requirement-source-materialization@1 |
| component_id/blueprint_id | 已校验的 design_binding |
| item_id/kind | 模型从采用材料提取的稳定语义身份与原生类别；同一含义跨 revision 保持 |
| source_ref | 脚本把 scope_items.source_path 定位到完整快照 files 下，生成项目相对 POSIX 路径 |
| source_sha256 | 对 source_ref 文件的原始字节计算 |
| provenance.source_kind/extraction_method | 原始对接来源、实际转换方式；人工导出明确 recorded_user_reply，分析稿明确 extracted_analysis |
| provenance.source_ref | 与顶层 source_ref 完全相同 |
| provenance.observed_at/source_revision | 已取得来源的实际观测时间/版本，缺 optional 版本则省略 |
| evidence_strength | 真实原始材料/人签的权威事实；模型分析保持 inferred，不升级为 authoritative |
| authority | 原材料权威或已记录的实际人签；不足用 unspecified 交原生正式性确认，不据编号猜 |

例子：`RR/prd.md` 含 `![流程](../assets/flow.svg)`；scope_items 的一项指该正文，另一项指脚本导出的人工范围决定。快照保留 files/RR/prd.md、files/assets/flow.svg、files/AR/story-src/human-decisions.json 和分析稿。图片作为正文的可解析资源，不伪造为独立 requirement。两个 source_ref 分别指冻结正文和原话导出，原生 checker 核路径和真实 SHA；改单字节必须失败，删图片由冻结闭包检查报错。示例的实际构造及机械结果写进验证记录，不以示例证明模型语义。

## 4. 成文与审查

成文前读取关联蓝图，通过原生 checker 核当前设计与投影。业务背景、边界和原话来自需求，设计事实来自 canonical；投影保留原生内容，叙事由模型组织。原生投影未展示但 canonical 已有的精确字段可以派生进附录，并保留可回查来源。

章节草稿、原子提交、图源登记、写作设计和人工区保护继续复用。本章能判的提交时判；整篇检查处理跨章遗漏和一致性。缺设计来源不生成看似完整的占位附录。

结构通过后，读者任务包含当前 Story/Review、有效需求材料与人签、蓝图及知识来源、章级问题、会议和图片对照。调用补充 B prepare，再由宿主使用既有独立能力派审，原样保存回复，check 确认当前对象。Extension 只检查 Story 专属判据与业务结论。

审查输入排除报告登记时间和调用次数；当前对象材料未变时复用有效结论。阻断缺陷回作者/设计责任方修正，建议按现有规则记录；格式不合由真实审查回复解决，不由作者补写报告。无审查员时明确披露未审查，沿既有授权策略交付。

成文登记保存实际原生设计引用与材料指纹；写登记不会改变审查对象。交付门校验登记对应当前来源、结构及审查结果，不要求存在 Spec/Plan/CU。

### 4.1 附录来源替换表

`story-chapters.json` 的 projection 替换旧 from 章号为具名读取器；`appendix.mjs` 生成和 check 共用读取器结果，不在两侧重复解析。原生对象先按本次有效 ref 校验。

| 原来源 | 当前唯一来源 | 渲染位置/缺失处理 |
|---|---|---|
| Spec 术语表 | discovery.facts 中原生 term:<术语> 事实及其 provenance，解释取源材料 | 术语章；缺解释交作者回来源补，不拿模块名冒充业务解释 |
| Spec scope/9.1.5 | development.nodes 的 module、真实改动对象及 architecture_impact 决定，业务分单仍取真实范围决定 | 附录改动边界；合法未改视图表达已核实不变，缺模块按原生缺口 |
| Spec 9.1.1 接口 | contracts[].operation/request_dto/response_dto/mappings/errors/idempotency/nfr | 附录接口；缺已触发契约明细交设计责任，不从施工稿猜 |
| Spec 9.1.2 数据 | runtime flows 的 data_domain_refs/source_of_truth/state_owner/failure_recovery 及相关契约；补充细节使用下述 story_details | 附录数据；不丢有效期、隔离、清理等当前已经形成的设计 |
| Spec 9.1.3 配置 | 承担配置责任的原生设计对象 story_details[kind=configuration] | 附录配置；明确不涉及时有对应有据结论，不造空配置 |
| Spec 9.1.4 埋点 | 实际 runtime flow/contract 的 story_details[kind=event] | 附录埋点；行为与触发条件保持，后续施工才形成的具体值不提前造 |
| Spec 专项说明 | 相关设计对象 story_details[kind=special_design] | 作者在业务章解释，附录派生精确说明及引用 |
| spec/knowledge-use.yaml | 蓝图 knowledge_application 决定，结构定义见步骤 3 | 附录规约判定及模式决定；缺判断/变更未同步报缺口 |
| 材料清单 | 当前实际采用 snapshot 与 materials 原件记录 | 附录材料清单；分别列原件、派生分析及实际采用版本 |

原生字段未承载的已形成精确内容，Extension 在被引用的 node/flow/contract 对象内使用 `story_details: [{id,kind,title,body,evidence_refs}]`，kind 只取 data_policy/configuration/event/special_design；body 是当前设计作者写的完整 Markdown，evidence_refs 为真实来源。定义纳入既有章节合同，和读取器一起验证；只有补充原生未表达的明细时使用，已有字段不重复复制。它属于同一 canonical 设计，由原生修订管理，不建立额外设计文件。

每项 body 在附录确定性渲染并附对象地址，结构检查比对原文；语义审查核遗漏、真实性和知识要求。story_details 缺失是否为问题由需求/知识与设计审查判断，脚本只在已声明该项而字段坏/引用坏时失败。后续施工细节未形成时正文说明范围，不能为满足旧表格强造数据。

### 4.2 独立审查调用和结果消费

Story 判据由 Spec overlay 移到 `rules/story-reader-rules.yaml`，保留 story_reader_review 的完整语义；`reader-review-task.mjs` 是唯一任务生成器。Spec overlay 留本阶段知识/施工输入判据，pre_verifier 不再重复附一份 Story 判据。

新增内部 `story-build review --feature <需求> --project-root <root> --action prepare|check`，作为 Framework 补充 B 的调用者，不自己实现 subject 或报告验真。任务及证据放 `AR/story-src/review/`；prepare 输出上游给出的 request_path/report_path，调用宿主原样提交短 request，原样保存回复到上游指定位置，check 读取上游结构化结果。

审前材料集合：最终 Story、Review 的当前机器区及人工区、决定登记、写作设计、采用快照及图片、当前 canonical/投影、知识原文与应用决定、章节合同、读者判据、结构检查问题的稳定投影。排除审查目录自身、调用日志/时间戳、report ledger、flow 自身 digest 和归档时间。文本/人签/设计/知识/判据变化使旧结果失效；仅重复登记不失效。

| 上游 check 结果 | 交付门 |
|---|---|
| 当前对象 PASS，结构通过 | 允许登记/交付 |
| 当前对象 WARN 且无 blocking_findings | 允许并带 advisories |
| FAIL 或非空 blocking_findings | 阻止交付，回实际责任方修复 |
| report_missing/report_invalid/subject_stale | 不作为当前证据；取当前 request 派审或按诊断修协议，不由作者改报告 |
| reviewer_unavailable | 明确“未审查”，沿既有已授权披露策略放行；缺报告/坏报告不能伪装成无能力 |

check 必须由实际 Framework 返回这些可区分结果，不能依据报告不存在推断能力缺失。尚未交付的接口状态和上游交接见总览 §4.3；在实际契约完成以前，本步标“接口依赖未就绪”。

## 5. 验证与交回

| 编号 | 场景 | 预期 |
|---|---|---|
| S2-01 | 已准入、零 CU、无 Spec/Plan | Story/Review 可完成，交付不制造阶段文件 |
| S2-02 | 缺来源、hash 不符、跨身份、未准入、过期投影 | 定位到实际来源或设计责任，不以占位通过 |
| S2-03 | 相同材料登记/重入；随后修改正文、设计或有效人签 | 前者复用，后者旧审查失效 |
| S2-04 | 一章提交、人工 Review 已编辑、图片重命名 | 其他章和人工内容保留，图源仍可追溯 |
