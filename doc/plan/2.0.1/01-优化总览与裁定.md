## 2. 归因与责任

| 问题 | 裁定 |
|---|---|
| Story 套用无 Feature review | 选型错误：入口复用代码审查规则，补文件后缀不能使其成为 Story 审查 |
| 桥接缺用途 | 原生物化信息表达不足，命令起手不受影响；不是两个 Case 的主要阻塞 |
| 独立质询未执行 | 执行合同缺失，须明确宿主已有子代理的派遣、输入、原件与消费 |
| 作者取 questioning 知识 | 可以准备，不等于可以自审 |
| 首条消息截断 | 本仓 CLI 传输错误，不能用单行命令掩盖 |
| 所有问题均不归 Framework | 不作笼统结论；直接设计的资产消费仍需上游接通 |

Framework 负责蓝图流程/准入、CU/施工输入、阶段审查及完成事实；宿主负责隔离执行；Extension 负责 Story 专属任务、业务报告和当前材料核对；测试装置负责完整请求、真实答复、业务终点和证据。

设计质询与人读审查分别执行。Story 审查使用已有材料清单、指纹和宿主子代理，不新建通用 verifier、调度器或 Feature 替身。

| 包 | 方案 | 交回 |

正常链：完整请求 → 取材/必要澄清 → 范围与有效输入 → 原生设计/独立质询 → Story/Review/人读审查 → 按授权交付或原生施工。直接 Framework 入口不因没有 Story 被强制改道。

P1 可先行；P2 的直接设计完整接线依赖[上游设计资产消费与质询合同](06-Framework协作问题报告.md)。P3 不等待通用文档审查接口，本版不申请该能力。P4 完整签收须有对应发布件与实际调用；新 CLI 单独获用户授权。
