稳定概念与易混区分统一见[GLOSSARY](../../../../../GLOSSARY.md)。本文维护本轮有效行为、职责或接口，历史版本和决定按其对象解释。

2026-10-29。本文是新Plan共享工程决定，不是新增产品协议平台。原生字段以N1发布件schema/入口为准，以下标“扩展”的字段只承担Extension仍缺的责任。字段契约与实际直接消费者同一步切换，无旧格式兼容支路。路径均以消费工程为根，扩展根由Framework配置解析，不写维护仓路径。

## 起步边界与本文“历史”的含义

2.x只从当前版本的新需求初始化，不接续、不转换、不补齐1.x或旧试验2.x的在途需求现场；同一新需求在2.x内部的多轮材料、人答、update、重入和恢复继续支持。本文的“旧采用版/历史update/原人答/恢复”都限定在这个新需求自身的生命周期；归档的1.x和旧试验2.x现场不属于可消费输入，不因格式名字相同就设计接续路径。当前源码可复用，旧数据现场不能因此复用。

| 情况 | 处理 |
|---|---|
| 1.x或旧试验2.x需求现场 | 不读取为当前工作状态、不转换/补齐/续跑；既有输入检查明确拒绝、原目录保持，另建新需求 |
| 同一2.x新需求的完整早期轮次 | 按当前合同支持材料换版、人答沿用、update、重入与确权恢复；不反复从零覆盖本需求 |
| 当前生产记录缺必需问题/字段/来源 | 报不完整并限制依赖动作；修当前生产者，必要时从同一需求的可信原件恢复真实内容，不用默认值/新问题回填成旧事实 |
| 当前源完整，派生索引/阅读件因中断或损坏丢失 | 沿既有责任明确恢复/重算，并核原字节及生成关系；不是旧格式升级入口 |
| 字段完整且合法的unknown/未决或适用性待判断 | 保实际业务未知及来源，交原有语义判断；不混同必填字段缺失 |
| 新需求尚未产生的条件记录/产物 | 按当前合同表示未开始或合法空集合，不伪造人答、旧基准或完成；记录一旦产生就须满足必需字段 |
| 新输入工具派生路径/摘要/provenance | 沿真实原件正常生成，保身份；不为减少工具动作而重新要求作者手抄 |

不新增历史版本识别器、迁移器或对旧现场的格式恢复平台。原生代码里名为legacy/compat的共享函数不凭名称机械删除；仅按本版新需求的实际消费者保必要调用，Extension不为旧任务增加分支、参数或验收。安装机制更新、知识所有权和合法统计保持，不能顺带迁旧业务记录。

以正式1.9.9 b4fbf433为基线，保持根inbox、RR/prd.md、SR/design.md、AR/design.md及业务/过程目录、assets、.backups职责。普通导入后原件仍留inbox；明确替代/退役才保全旧原件并更新当前集合。撤回物理sources/、sources/inbox和sources/backups，也不将它们改名为另一套统一版本仓。唯一必要的共享图路径调整为根级ux-reference→既有assets/ux（真实原生标志冲突）；原根级施工阶段/契约归CU，blueprint新增。

AR/design.md保本单已取得原文/阅读稿，不再被complete/五段提取稿覆盖；本地补充仍沿AR/story-src/upstream。RR/SR等为人可读当前稿，不因不可变引用需要而另逼用户进入版本目录。来源说明沿原索引和Story材料附录，不新建sources/README替代入口。

`AR/story-src/materials.json`保持唯一来源/版本登记；D05已由schema3切schema4恢复原件留存，本轮D08目标为schema5（聚合历史与稳定引用，现源码仍schema4），明确拒绝旧试验现场，不做格式迁移。索引持久保source_id/kind/origin、版本、原件/阅读稿/图片真实路径和SHA256、当前材料关系、notes及派生files；文件位置不再用dir名称推断版本。当前素材和历史字节按真实文件核，历史登记不能由refresh按最新内容重算覆盖；索引坏按已有原子备份恢复，不丢历史新建。

| 对象 | 生产/保存 | 实际消费者 |
|---|---|---|
| 本地原件 | inbox相对路径作来源键；当前原件留存，变更与退役按既有职责 | 材料盘点、导入、update |

| 稳定版本 | 新增或真实变更时，在既有.backups/local内保必要原件/转换结果；同内容复用，不每轮全量复制 | 蓝图真实ref/片段/hash、旧采用版本与独审核源 |

稳定阅读文件沿来源角色与安全派生名/版本序号保存到`.backups/local/<角色>/<来源派生名>-v<N>.md`；原件沿已有`.backups/local/inbox/<原目录>/<主名>.<内容摘要><后缀>`保全。文件名不是原字节hash声明，完整hash记录实际内容。无转换/引用改写需要且已能唯一指认该版本的原件可直接作稳定阅读件；共用原件存储路径不能区分材料版本时，沿D08保必要的版本阅读地址，不通过最新匹配猜采用。人答可沿`AR/story-src/answers/`保真实导出的版本；不得恢复第二人答批准表。

每份聚合阅读稿明确关联其全部原件版本和图片，采用它时按该版本的真实组成展开，不从当前最新集合补旧证据；路径到来源不可假定一对一。真实原件、当前阅读和稳定副本有不同职责，原生引用使用已登记稳定字节，不靠作者手抄采用清单。

pending按当前原件字节、归类/引用关系与最后成功导入事实判断，文件仍在inbox不等于未导入；status不重转所有docx。更新直接改稿保现有比较责任，查询不自动覆盖或重新hash洗掉变动。目录与原件职责保持D05；聚合历史、别名解析、普通直接图换版和全部消费切换以[D08§2—4](../04-批次-能力保持与整版验收/08-稳定来源与测试提效集中返修.md#2-f1当前路径与稳定引用分开)为当前合同。files中reference标识当前输入别名，正式采用只消费稳定行；drafts保各版组成，人改当前稿不删历史。

### 2.2 有效人答：生效、适用性与送达（A05补正F1）

人答真源仍是已保存的真实流程记录，不是作者填的scope列表。新答复保存时保当时问题、选项/被选范围的完整语义、原话、时刻及原问题身份；从现有ask与scope上下文取，不能用以后变动的notes/选项重建成“当时问题”。当前新记录必须保存这些必要信息；缺失即本版数据不完整/生产缺陷，不能标作“历史缺上下文”后继续消费。修生产者并按可信原件恢复真实内容；旧需求或开发期旧记录不纳入回填/兼容。

**生效与导出顺序**：`cmd_decide`/`cmd_decide_update`先校验并保存真实答复，完成既有问法/侧车清理，再调用同一`registry.refresh`导出当前答复并刷新索引，最后用新结果给next。答复已保存而导出失败时明确“答复已生效、派生未完成、不要重答”；现有`round`可重试刷新，同材料不新开材料轮、不重复写人答。正常路径不要求消费模型额外补一次round。close/restore等改变上下文后同步派生结果，失败不伪称已经写盘的动作从未发生。

来源读取先核当前投影与真实记录一致：把有效记录规范化后取得期待的内容身份，与现有导出比较；未同步就报明确来源缺口并限制依赖它的来源/审查动作，不能仅WARN后继续消费旧answers。若导出文件已发布而索引落盘失败，重试复用已发布的同内容版本；保存、导出/索引与路由失败各报真实完成位置，不把路由错误说成答复未保存或导出失败。Python沿唯一answers读取职责；既有`story_flow.py status --materials`的只读材料投影带出`required_answers`（当前期待内容身份、实际导出路径/摘要及是否同步）和具体source_problems，正文不塞进普通status。跨语言作者/审查输入通过已有flow/client读取一次并在本次装配中共用，不各写一套有效性算法；Python内调用直接复用同一函数，不为每文件起进程。准备来源的写入口可以复用refresh完成必要派生，status/独审纯读取不暗中写人答。该结果在一次作者/审查输入装配中共用，不为每个局部判据重跑全流程。

**集合与适用性**：

| 原始记录 | 当前输入如何处理 |
|---|---|
| 起手/会议关卡 | 取真实human且accepted的记录，保ask_id/gate/round、问题/选项、chosen/reply/at及meeting/item；不是模型建议 |
| 范围及承载答复 | 同一新需求当前整体承载时，其早期split_carrier只保该需求历史；当前切分时，只认相同范围问题/轮次/份表的承载答复。复用round、scope_options、split.settled_round和问答上下文，不用相同选项编号推断相同范围；reopen未重答期间旧答不冒新授权 |
| 同一新需求的当前及历史update裁决 | 仅读取该需求按当前合同生成的open契约及updates/record.json中的真实决定，去重同一保存事件，保update id、item、issue、asked、当时问题/原话/时间。这里没有outcome字段，保存成功即有真实答复，不能套关卡accepted过滤 |
| 同议题的多份答复 | 同issue且同asked的问题版本可按后答替代前答；自由文字item不作稳定身份。asked变了不自动意味着旧业务决定被撤销；保各自适用上下文，让作者/原生质询按真实语义判断相关、替代或冲突，使用既有决定机制，不造第二张裁决表 |
| 本地update撤回 | restored表示文件处理结果，不表示用户业务决定被撤销。保真实原话及其版本；仅按明确撤回/替代或已失适用范围处理，不把整轮人的决定自动丢掉。问题上下文不再对应当前产物时标明出处/待核，不能称当前无条件有效 |

复用该新需求的update记录枚举和严格读取错误，不扫描1.x/旧试验2.x现场。以下需语义判断的记录前提是必需字段完整，不能把缺问句/缺身份的数据纳入“待核但可继续”的人答集合。确定当前的答复与需结合上下文判断的记录分组呈现；两组都进入本次必读阅读件和联合身份，不能把待核记录只藏在历史导航。已明确失效/被替代的原话保追溯，不强制每次重读全部历史，不以“最新”掩盖不同问题语义。

独立质询仍遵守原生先人读八问、后核源的顺序；必读人答放进其实际核源任务，不提前污染首读隔离载体。输入清单存在不代替实际读取。

当前有效人答阅读件是**独立必读上下文**：设计作者、原生独立质询、Story作者及其独审都取得实际路径/字节身份和问题上下文，不能取决于作者有没有把它写进scope或设计引用。原生质询通过本次正常请求/已有知识任务与材料入口送达，不私改Framework。Story审查对象始终含该阅读件；人答未变则复用版本，变化则参与本次来源输入身份和报告对象绑定。

`materials.digest`继续只表示取得材料变化，人答不进入它以避免答复反生补料轮。既有`story_basis.sources_sha256`改为“实际设计来源身份＋必读人答身份”的同一派生摘要，不新建answer_revision/readiness。材料digest相同不能遮住人答变化；人答变后是否改蓝图/正文按实际影响处理，允许有据保持，但旧审查不得自动冒充已看过新答复。

### 2.3 scope、设计依据、库存与采用（A05补正F3/F4）

| 对象 | 表达什么 | 不表达什么 |
|---|---|---|
| 原生current_scope_items | 本次真实requirement/goal/invariant/high_risk及其设计追溯 | 不是全部阅读文件的目录；不要求每个背景稿、图片或人答各造一项 |
| 实际设计依据 | 蓝图事实、设计对象、合同和真实决定所引的具体来源及用途 | 没有明确引用不自动等于“未采用/不适用”；工具只说未见引用，语义由作者/独审核 |
| 材料库存 | 全部已登记来源、版本、原件与阅读/图/纠偏角色，latest只表示最新取得 | 不决定设计采用、不因漏写scope删核源材料 |
| 采用版本集合 | 真实设计依据精确命中库存后派生的来源版本及其内容 | 不把库存最新自动替换旧采用，不保存另一份作者手写采用账 |
| 必读人答及冲突依据 | 当前有效人答独立送达；未裁决冲突的双方都可核 | 不是每条均自动已采用或每条均需造scope |

一个正常例子（仅说明关系，不新增案例业务）：需求稿v1中的真实目标形成scope项R；系统说明v1在设计fact的provenance被引用，属于支撑采用，不必造invariant；最新有效人答v3无论是否另成scope均是必读。库存后来取得系统说明v2时，输出仍区分“取得v2、设计引证v1”，由update判断新旧影响。人答内容若确实规定目标/边界，原生scope应反映该真实约束，但不是按人答文件数造条目。

**来源收集范围已定**：保原生`currentScopeItems`及其严格来源/hash/追溯检查；支撑依据取蓝图根与`discovery.facts`、原生`design_views`的nodes/runtime_data_flows、relations、contracts、decisions/gaps的真实provenance，以及原生合同实际operation、request/response DTO及字段、mappings、errors/idempotency/nfr中的source_ref。此范围对应原生provenance/contract校验承担的对象，不扫描叙述文本猜引用。

保引用所在对象/字段位置、原ref（含片段）和已有声明摘要。排除reader_guide.source_refs（它是canonical JSON Pointer）、内部design/verification/traceability地址，以及示例、说明或被否方案中的任意同名字段；discovery.conflicts.sources进入核源但不自动算双方都已采用。框架允许的非文件provenance继续按原契约处理，不能为了归一集合把所有原生来源强迫变成本地材料。

N1的`blueprintSourceRefFiles(projectRoot, blueprint)`可对**已选真实依据字段构成的只读视图**提供现存工程内文件依赖枚举，不把整个蓝图任意JSON递归结果当采用真值。它会省缺失文件且不保片段/hash，所以仍由既有`readSourceFiles/resolveCurrentScopeSource`承担适用来源校验；真实scope不得因枚举省略而免查。本需求登记材料的引用必须匹配真实已登记文件；声明当前需求文件却缺失/未登记要点名，不能静默过滤。合法代码/schema等非材料来源单独保原生身份，不伪造一个材料版本。

**统一登记读取**：从现有索引sources[].versions、drafts各版记录和实际文件派生工程相对路径→来源行集合；当前别名带reference，稳定行保真实source_id/version/kind/role/expected_sha，不能按路径最后一行覆盖来源身份。包括普通材料、图、人答及会议原件/raw/纠偏/阅读件，不扫描统一版本仓，不按目录名猜身份。去片段仅用于文件匹配，原引用交原生验证时保片段。读取合同固定为：registry在D08目标schema5材料索引内派生`files`视图，每行给`path/source_id/version/kind/role/sha256`及所属版本位置；它从索引保存的版本关系、真实文件和会议生产者推导，不由作者维护。各消费者读这一视图，不各自扫描目录/猜文件角色；新生产索引必须包含当前派生字段，缺失不能默用旧形状。只有同一新需求的完整来源登记及原件可核时，才沿既有恢复入口重算确属可再生的派生物；不借refresh为旧格式或缺必需源记录补字段。`files`只是现有库存的可重建视图，原件及其版本关系仍按真实登记/受控会议产物核；不新增独立台账。

`adoptedSources`保持纯派生职责：调用者明确给当前Story需求身份/原生蓝图身份和完整登记上下文；返回引用及所在对象、命中版本和展开文件、独立必读人答、冲突核源与具体问题。Story消费按已给的需求身份读取索引，不从某种来源目录名反推需求。普通原生设计读取未声明Story消费上下文时，不强造Story实例或要求不存在的材料索引。

对每个明确命中的版本只展开稳定原件、实际阅读件、图和必要纠偏链，排除当前输入别名；聚合按该版固定components展开，共享图仅作字节资源叶子，不反向采用其所有父版本。Markdown阅读投影引用的登记原图按实际目标加入来源对象，图版本从完整索引精确匹配，不能仅因它不在本Markdown的目录里漏掉；合法外部链接仍按原输入边界处理。审查输入合并“当前完整材料＋必读人答＋旧采用版本及冲突依据”，按角色/字节去重但不消掉来源关系。人读材料表可同一行写“取得v2、设计引证v1、原因/贡献”，不要求复制两张完整表。

**机械与语义边界**：工具验证路径/原字节/声明身份及集合当前性；作者和独审判断真实使用、适用性与漏义务。没引用的资料可以有据不用，也可能只是漏标依据，不能由脚本替模型定“不采用”。原生scope仍必须完整反映真实目标，不能利用支撑引用绕掉真正需求的追溯。

### 2.4 Markdown与会议阅读件的同源保护（A05补正F2/F3）

Markdown原件留inbox；设计引用的稳定保全副本仍保原字节。对有本地相对引用的正文，导入按**导入前原位置**解析引用，在本次已提供或已登记材料里定位真实文件；原件外另生成链接正确的阅读投影，用相对最终阅读稿的路径指向真实目标。图片保assets中的稳定内容身份，无需为每份Markdown/CU复制多份原图。对应关系从原件、阅读稿实际引用及材料索引派生，不新增作者填图关系表。

先为本次输入确定当前阅读位置与所需稳定版本文件，再生成并校验对应阅读投影后发布；不把先复制原件导致的断链留给作者修。外部URL/文内锚点不改；声明本地引用缺文件时一次列真实缺口，不改成不存在的路径、不静默丢图。沿本产品已有链接/图片形态处理，不建立通用文档抓取平台。无引用改写需要的合法Markdown可继续以原件作阅读稿。

相同原件与相同引用身份/转换结果重复导入复用版本；引用目标或转换结果确有变化时，按既有内容版本规则保存新阅读结果，旧版本不原地重写。只处理本次实际导入/更新的对象，不反向扫描重写全库旧Markdown，不为此建立依赖调度器。夹具可以预备下游状态，但导入能力回归必须用未改写的原始Markdown与图走真生产者。

会议原件和raw的固定身份按既有source元数据核；corrections/evidence是受控阅读派生，使用现有apply_corrections与evidence_stale等规则核对原文、纠偏及实际结果，再给当前摘要。不能直接对被篡改的阅读件重算SHA就认成新原话。会议可保在story-src/meetings，统一登记读取提供全部合法文件角色；正常来源补齐、原生质询和Story核源均能取得实际使用的原件/纠偏/阅读件。源读取只核不暗修，失败回已有meeting-refresh责任修，原始会议与人答不覆盖。

## 3. 直接设计交接及业务流程状态（A04）

### 3.1 无绑定仪式、无重复提交稿

需求标识是blueprint_id的路径键；component_id由原生component-design根据真实工程组件上下文确定，不能从需求号或案例默认猜。尚无完整canonical时允许正常设计起步，不要求先造空蓝图以满足Extension前置。

Extension交接内容是已有范围/兄弟单责任、完整来源索引和独立必读人答。scope仅含真实义务，支撑资料采用按§2.3处理，不为每份资料造scope。对外部取得的原件，作者将**一次形成的原生scope item语义**交原生来源物化；工具从索引填source_ref、真实source_sha256、provenance、authority及已确定的component/blueprint身份，生成原生所需信封。该语义不再另填design-input/adopted列表。来源信封是原生协议要求，不是另一份材料副本或新完成账本；支撑来源无需为了获得采用身份挤进信封items。

本地文件/直接人工来源由原生builder直接规范化到current_scope_items，不强制创建provider JSON。原件及人答已经在版本位置，不再freeze一次。外部来源信封如需落盘，放blueprint/内原生设计交接材料位置，仅含引用/必要原生字段，不复制原件正文；相同输入不重复写。正常设计编排调用现有导入/来源读取能力即可，不再发布`complete`或`bind-design`用户步骤。

原生源校验成功不等于设计完成；源失败直接返回具体缺口/责任，已有原件与旧设计不改。source identity字段由工具生成，语义范围与是否采用由作者基于已有有效决定判断，脚本不按关键词提取需求。

### 3.2 flow schema与派生状态

`story-chapters.json.flow.schema`由5升6；只用于当前2.x新初始化的需求，不接续旧任务。材料schema3为A03当时对象，schema4为D05已实现对象，当前schema5目标及全消费者切换见D08；全部直接读者一并更新；flow6在A04切换状态、命令与所有直接读者。旧/不受支持的schema仅说明本版不接续该现场，应另建新需求；不指派2.x替旧版收口，不清旧目录或偷偷改格式。

flow只保存业务轮次、材料/会议/范围关卡、有效授权/人答、Story登记及交付记录；`status`保`gathering`和`story_written`，退出`complete`值、`input.snapshot_*`、`design_binding`及`after_complete`的旧含义。已进入设计/已有成果的保护从真实原生对象与本地登记派生，不要求再写一个design_started账本。`next`仍由既有routing即时计算：

| 真实条件 | next与边界 |
|---|---|
| 缺必要原件/存在未处理来源变化/必要业务决定未得 | 对应导入、分析或真实关卡；不假报“材料为空/无变化” |
| 范围与必要输入可用，设计未开始 | component-design，给出实际原件/人答/范围；不等complete |
| 已有设计草稿 | 原生继续/查看/修订按请求；可写诚实业务草稿，不以草稿冒充准入 |
| 设计满足本次请求，Story尚未登记或已过期 | Story起稿/必要更新及独审；非业务相关纯身份调和先按原生等价规则核，不无条件全文重写 |
| Story当前且原权限允许 | 送审、指定设计交接或已授权后续；未指定终点才沿原一次性交付选择 |

成文登记保文件指纹、实际采用来源与独立必读人答的联合身份、原生蓝图精确ref、知识上下文身份及真实审查结果；不保冻结包引用。源集合按§2.3由原生实际依据和完整索引派生，当前人答不能由作者scope选择排除，不新增作者清单。旧`story_written_at`等计量事实仍按真实成功事件写，当前性更新不造历史成功。

## 4. CU实际需求与图片输入（B02）

CU接受、修订、ready set和Feature身份由原生consumer决定。不能直接写canonical change-unit.yaml；首次候选按原生路径接受，已接受只readiness，未完成修订使用原生精确ref/API。设计目标被引用即整体继承，公共/专属内容必须在蓝图对象划分正确，不能投影后按predicate隐藏误继承内容。

交给独立阶段或完整run的需求正文使用当前用户请求、已确认范围和真实来源引用，不以Story替代施工权威，也不复制第二份人工维护的需求稿。来源路径及可读原文作为当前调用输入；若原生`--requirement-file`使用已存在的有效正文，保持其真实字节；多来源或需携带共享图片时使用原生允许的`--requirement`正文，明确引用当前原文与图片/图片目录，不能同时给两者。该正文是原生调用请求，由正常作者在既有范围准备中形成，不新增需用户批准的技术文档。

图片消费分两条真实入口核：

- 图发现读取当前调用的requirement及requirementSourceFiles；完整run以正式manifest.requirement/requirement_source_files为准。它只合并显式引用图片/目录和source父目录一层图片，不能期待递归扫描每个材料目录，也不能假定蓝图source_ref自动写入manifest。
- Spec视觉交接的authoritative_refs指向这些共享原图的项目相对路径；实际读取和能力证据由原生链承担。来源原件、Story图片、CU图引用采用同一字节身份，不复制新图冒充读过。

所有原文/图在首次冻结原生范围之前送达；已有run后不能用新的--requirement覆盖它，变化沿原生范围/设计修订继续。普通未变请求恢复不重复写manifest。无图片的合法需求不编图/目录；图片不可用如实显示实际依赖，不能把路径存在当图像已读。

## 5. 知识最小扩展合同（B01）

原生有来源、facts、决定、对象和typed投影，没有本项目规约单元/模式角色语义；仅为这部分定义窄扩展，使用既有知识loader与lite-schema能力，不建新DSL/验证平台。

### 5.1 输入身份

在蓝图`discovery.inputs.knowledge_context`保存一次工具生成的`digest`和`entries:[{source_ref,kind,form,sha256}]`，清单从当前manifest激活结果派生，稳定排序/原字节计算，不由作者手抄。它只记录本次设计收到的知识输入身份，不能证明已经理解或正确应用；事实/义务不用逐条复制摘要全集。新知识增加、删除、变更可与该身份比较，模型判断影响，原生设计修订及既有当前性承担后续；不另建knowledge revision/readiness。

非CU的新Feature在原生`contracts.knowledge_context`使用同一形态和同一比较器；CU继续读蓝图，不重复复制。`entries`避开N1未知嵌套`files`的文件引用扫描；撤下非CU的`context:false`，错误指向实际载体。知识任务生产输入身份，获准设计阶段保存，下游只消费、变化回设计方；尚无契约的独立Spec不强造提前Plan。详细生产消费与原生验证见[C00§3](../03-批次-业务送审与变更交付/00-前批集中返修.md#3-r2r4知识职责一次接通)。本版新初始化合同一次切换，不保旧键双读。

该字段属于Extension扩展，不宣称Framework原生已理解它。原生开放inputs载体和原指纹仍照合同处理，Extension只在已有任务/检查中核其实际文件身份。

### 5.2 判断、义务和角色

| 对象 | 新形态/责任 |
|---|---|
| 项目事实 | 原生fact的value/provenance说明真实工程事实；源为具体知识/源码，不复制另一工程库存 |
| 规约适用事实 | 原生fact的provenance.source_ref指规约文件；value含`knowledge_kind:constraints`与理由。整域无关用`outcome:not_applicable`；相关域用`items:[{unit,outcome,rationale,target_refs}]`，两者互斥 |
| 相关域条目 | 覆盖该域实际声明条目；applied需真实目标，not_applicable给条件理由。真实争议/豁免/待定回原生decision/gap，pending同时引用已知受影响实体与真实decision/gap；仅有decision/gap时为归属未定公共缺口，不在此另授批准 |
| 实体义务 | `must:[{text,source_ref,verify}]`；source_ref指具体规约条目；text写此实体实际责任，verify沿既有ut/device/both/review等有效责任，不默认both |
| 模式角色 | `pattern_roles:[{pattern_ref,role}]`；pattern_ref指实际模式文件/单元，role来自该知识定义，实体本身是承担者 |
| 验收 | 原生AC/BD/NFR行为与结果，知识关联使用`knowledge_refs:[source_ref...]`扩展字段；保原生source_ref业务来源，不覆盖它，不依赖knowledge_decision_id |

每个规约文件本来即合法的一域；同域有命中项不能用整域无关省略，跨域混装仍回知识所有者。激活清单不是每模式必判的清单；模式只按真实业务信号形成候选。facts只存适用性/原因/目标，不存第二份义务正文；只有真正决定才进原生decisions。必要业务内容进正常设计位置，机器追溯不成为Story正文。

确定性检查核来源/上下文、域条目存在及不重复、真实地址、角色合法、引用和投影保真；独审核是否漏读/漏判相关域、理由错误、义务曲解或模式漏用。不能靠ID齐、词数或事实数量代语义。知识为空沿当前显式空清单语义；声明了但不可读仍报输入缺口。

B01一次同步所有旧knowledge_application、must.decision_id、knowledge_decision_id消费者和专用fixture；B02再深化阶段内容，不承担补救断链。原生通用decision/人工问题ID不删除。

## 6. 原生完成、Story审查与交付（B03/C02）

现有Framework访问桥增加只读当前事实入口，Python消费者只读返回，不复制状态判定：

- 当前实际Extension消费者是update跨CU的Feature聚合：各自feature+已有相关阶段构造CleanPassOptions，保持无run查询，读取原生当前事实。完整attended运行的run/scope/workflow由原生执行入口自身校验/续行；环境裸runId不得套给兄弟CU，不新增无消费者的run接口。
- 当前没有原生独立request消费者，不占位接入PreparedRequest。以后确有本次请求消费者时沿真实request_sha256/bindings/reportDir读取，不用阶段summary伪造请求。
- 原生readCurrentDispositionInput→resolveCurrentDisposition输出problems、completionBlocking、releaseBlocking、disclosed、completionEligible、releaseReady。透传真实owner/phase/action及证据路径，不新存永久裁决副本。缺能力/异常如实待核，只阻相关必要工作。

单位disposition独立于阶段列表：即使阶段均current，completion阻断、release阻断、disclosed或unknown仍在status/close披露。单位级phase=*不伪装成某阶段返工；只有阶段问题才给最早阶段续行，发布限制不撤销普通完成，施工未完不自动阻止update本身收口。详见C00§5。

Stage历史closed保留，当前能否完成/发布另列；状态查询不写入、不启动原生readiness等有副作用动作。usage原完成记录不因当前新问题抹掉，新工作按原真实起止记录；不能拿新读取的旧closed结算本轮未完成工作。

Story审查沿现有prepare/原报告/结果协议：有reviewer真实派审，无reviewer且无当前已知阻断时返回unreviewed与能力原因；声明可用却调用失败属于故障，不偷换成缺审。坏对象、过期、被改报告及已知FAIL按实际问题处理。未审贯通Story/Review机器区、登记、update/publish，并独立于原生普通完成/发布结果，不能记独审/DSH通过。

Story审查对象是实际业务稿＋有效来源＋设计参考，原件/图仍可回查；业务首读不重复全套蓝图技术论证。真正设计问题回原生owner，表达问题回Story作者，建议采纳或有据保留，无新增人批/waiver。

本地读原生评审投影作为设计参考；系统需附件时在交付边界从当前投影准备确定性附件，保版本/摘要及上传读回，不常驻第二设计真源、不要求副本再次独审。实际外部合同决定是否需设计附件，不能在未查接口时一概删去，也不强制无此要求的本地用户提供第三件。

## 2026-10-31 实际实现与来源版本的补正

本次材料包先在内存确定最终可读版本：原件未变不代表阅读关系未变；引用目标提升版本时，同包引用者按最终目标重算，稳定后原子写盘。每份输入最多提升一次，旧版本/未提交旧资料不改，流程见C00§2。

原生`diff-scope.implementationFiles`承担实际变更＋预测引用的观察集合，`implementationChangeContext`提供删除/改名原文。coding实体/探针/角色读者共用该集合；缺有效基线就披露相应未核，不把只读旧预测误报为完整扫描。预测文件/模块不是授权白名单，真实请求限制仍由原生承担，具体消费者见C00§4。

pending归属按实体地址，decision/gap只标解决责任；纯决定地址的未定归属要实际送达公共缺口，其他CU已知专属待定不广播。模式提取返回patternRef，review/coding等下游使用同一身份；不恢复must.rule/decision_id产物字段。

## 2026-10-31 C批复评的有效接口补正

具体工程步骤在[D00](../04-批次-能力保持与整版验收/00-前批返修与明确提效.md)，本节固定跨步含义，不重复制施工全文。

- **Story章组织**：默认合同保职责ID；现有写作设计派生本需求有效章表。展示标题/顺序与ID分离，不涉及章可省略；工具用既有ID的隐藏章锚点安全定位，有界提交/编号/附录/披露/独审同源。本轮不做任意新增职责或合并平台，不加工旧在途稿、金样和历史资料。
- **上游图承接**：来源与原图全集仍送达，作者映射是自选阅读定位；已选择位置核真实，未映射不由脚本判业务遗漏，也不要求全图不适用账。独审判断相关关系是否被完整表达。
- **自动未审**：同次宿主事实决定准备结果、载体与下一动作，缺审查员不要求派审；已知必修原件引用/摘要进入首读后的既有context，恢复审查有事实可核，不新增批准/发现台账。
- **交付选择**：fetch输出目标对接事实delivery_requirements.design_reference；原已有请求可由publish --with-design-reference承接，默认业务两件。发布准备唯一形成receipt.delivery，上传/读回/归档/终点消费同一实际集合；未选旧设计附件保持其真实历史版，不冒称已更新。
- **远程恢复**：fetch→restored --prepare（可用既有--reply处理真实冲突）→adapter restore→restored。准备单项放receipt.restore，复用B/L/E与publish_overrides；adapter核本地/远端未漂移，只改正文、同版跳写、读回不一致不报成功，最终登记核目标与准备时间。原件、人答、其它附件/原生CU不回滚。
- **性能接口**：本次动作共享ctx/未变来源对象，不跨写入复用；registration-check组合原三项检查，Python一次Node消费结构结果后才原子登记。单独check/review/basis的正常用途保持。夹具只构建一次目标蓝图，不减少原生职责。

restore不再使用无准备的contentOverride直写，也不以普通fetch冒充恢复成功；本地恢复与远程恢复仍分责。实际接口结果在实施时按对应离线/原生边界取证，本页静态定案不称运行通过。
