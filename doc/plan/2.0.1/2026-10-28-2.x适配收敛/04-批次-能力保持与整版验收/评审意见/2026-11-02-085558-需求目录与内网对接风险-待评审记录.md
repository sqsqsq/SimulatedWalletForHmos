## 3. 候选目录与职责（待评审）

建议方向：保稳定用户入口和备份所有权，内部来源按版本管理，蓝图/CU按原生身份组织。

```text
doc/features/<需求标识>/
├─ inbox/                      # 用户投递；系统取材按指定批次写入
├─ sources/
│  ├─ README.md                # 材料及版本阅读入口
│  └─ <材料名称>-v<N>/          # 原件、必要阅读稿、所属图片
├─ AR/
│  ├─ story.md
│  ├─ review.md
│  └─ story-src/                # 既有写作、来源索引、会议与审查工作记录
├─ .backups/
│  ├─ cloud/                   # adapter的系统正文覆盖前备份
│  ├─ local/                   # Extension本地更新/撤回备份
│  └─ published/               # 已交付版本比较依据
├─ blueprint/                 # 原生整体设计
└─ <change_unit_id>/           # 原生施工单位
   ├─ spec/
   ├─ plan/
   └─ ux-reference/            # 实际需要的CU专属视觉资料
```

目录按需要创建。用户只需知道根级inbox；sources是导入后的原件/阅读稿/图片版本区，不另设第二收件入口。共享原图通过真实路径送入蓝图/CU，不为默认目录复制多套图片。既有会议工作记录不因图示而再次搬迁。

`.backups/cloud/`为本仓候选默认约定。目标内网若有已确定的有效备份位置，adapter返回真实位置，核心登记和恢复消费该路径，不为形式统一强制迁移。取材按传入`--out`执行；材料版本管理归Extension，adapter不必维护内部版本目录。不新增通用路径配置平台、链接目录或旧新路径双读层。

## 4. 原生识别与内网风险待核

**根级inbox并非当前原生已无条件支持。** N1会检查工作区直接子目录是否含施工标志；inbox里直接放spec.md、contracts.yaml或某些施工目录时，仍可能被误识别为CU/孤儿Feature。正常流程先导入可以减少暴露，但不能保证其它Framework操作不受影响。后续须明确辅助收件目录的原生识别合同，不用Extension影子过滤或要求用户改原文件名掩盖问题；此项不是本记录新增的全局停工条件。

内网adapter尚未直接核查，不能宣称已损坏或已兼容。需要结合真实实现确认：

- fetch是否遵守`--out`，其来源/批次回执能否被当前导入器消费，是否仍硬编码旧目录。
- archive是否把实际备份路径交给核心；若仅返回旧式backupPath而未进入新发布记录，可能出现“备份在盘上但核心找不到恢复目标”。
- restore是否消费本次明确目标与摘要，还是自行选择某目录最新文件；写入和读回结果是否能被核心正确登记。
- 设计附件本地来源和交付集合是否仍固定旧AR副本/三件，造成正常发布断接。

目录不一致不必然导致故障：只要生产者报告真实路径、消费者按同一合同使用，原备份位置可以继续有效。真正风险是硬编码路径与新旧接口责任错位。目标adapters按所有权保留，机制升级不会自动证明目标对接已适配；外网替身通过也不能代签内网接口。
