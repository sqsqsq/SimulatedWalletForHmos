日期：2026-10-02。角色：维护设计者。对象：`e54764ee` 及其 CLI 交回。本文是新一轮评测结果，不改写 2.0.0 已有实施记录。优化入口见 [实施总览](01-优化总览与裁定.md)。

## 1. 裁定与证据范围

**本轮不通过整体适配验收，也不具备发布条件。** 自动充值证明了部分取材、成文和冲突处理能力，但没有证明可信的蓝图独立质询与完整送审；车钥匙没有交出目标产物。不能只补跑车钥匙、将自动充值记为已验收。

本轮直接检查了两 Case 的中间文件、最终文件、主事件流、OpenCode 会话数据库中的用户消息/工具调用/会话关系、独立审查原件，以及 1.9.8 对应产物。对“思考过程”的判断来自模型可观察的计划、取材、调用、修改与交付行为，不将内部推理文本当作事实证据。

证据集保存在仓根 `output/story/2.0.1-analysis-20261002/`，不入库；`inventory.json` 记录复制来源与逐文件 SHA-256。保留 199 份文件，包括检查点和需求目录之外的 Story 审查原件；另导出两份 `session-evidence.json`，只包含用户消息、选定工具调用和会话关系，不包含私有推理或凭据表。`transport-evidence.json` 保留两轮请求/实际消息，`metrics.json` 保留现有计量结果。原 run 保持原样，评分文件除外。

## 2. 关键发现及归责

### F01：两个 Case 的首条业务请求都没有完整送达

请求文件与启动 argv 保存的是完整多行 prompt，而数据库中的实际首条用户消息只有第一行，且带字面双引号：

- 自动充值：`"AR90006 是交通卡自动充值的开发需求，产品需求和系统设计都在需求系统里，"`
- 车钥匙：`"这是我们自己记的一个问题单，编号 ISSUE-206，数字车钥匙分享这块的端侧能力。"`

材料索取、目标终点、不施工等后续行丢失。车钥匙随后问“这轮要我做什么”，宿主重申了目标，却没有完整恢复原始材料可用性说明。**同样的截断也存在于 1.9.8 两 Case 的首条消息中。** 因此这是既有测试装置问题，不能全归为 2.0 路由回退。

责任在 `tools/cli/registry.py` 的可执行文件解析和 `tools/cli/runner.py` 的启动边界：实际运行的是 npm 的 `opencode.CMD`，其 `%*` 再转交原生 exe。`shell=False` 不保证 Windows 批处理参数无损。Framework 自己的 `utils/agent-containment.ts` 已有避开 CMD 的处理，但维护 CLI runtime 没有走该实现。

本轮已做无模型的真实子进程回显：同一三行参数直接交原生 Python 保持完整，经 `.cmd` 的 `%*` 转交只剩第一行，而且退出码仍为 0（`transport-probe.json`）。这与实跑失效点一致，不能靠退出成功证明输入送达，也不能把 prompt 压成单行掩盖错误。探针仅在 output/scratch 写临时文件，没有改 CLI 产品实现或调用模型。

### F02：车钥匙不只是“没有发现 Story”

10:18:27 的 read 工具记录 `prt_0fa67e227001AYmYPqqIx7gKGS` 显示模型读完 Story SKILL 全文，包含本地单入口说明；之后仍将 ISSUE-206 判为平铺维护 Feature，进入原生 Spec。产物仅有 `execution-scope.json`、`feature.yaml`、需求材料及 Spec 的准备报告；没有蓝图、Story、Review、Spec 正文、Plan 或 CU。

原生桥接的描述确实只有“实例扩展 Skill：story”，比 1.x 丢失用途信息；但它不是唯一原因。组合原因是请求截断、自然语言任务与入口用途关联弱，以及模型读完指令后的错误分类。不能用“文件不存在就转 Story”的 Spec hook 补救：这会误接合法的直接 Framework 工作流，而且发生在选错入口之后。

### F03：蓝图作者填写了独立质询完成，实际没有独立质询调用

主模型交给蓝图作者的任务 `prt_0fa7f4054001g5lD4k22nNO6E0`，要求先读多份 checker/schema 源码，补足 questioning 字段、使用不同 provider 名称和 `isolated_context=true`，迭代至无 BLOCKER。实际蓝图作者子会话为 `ses_f05805b36ffejB7Qiq2hVGhvOu`；其工具记录没有另派质询者。整棵会话树只有蓝图作者、两次初始 Story 审查和一次 update Story 审查，另一次 task 是恢复第二位 Story 审查者改报告格式。

canonical 却登记 `questioning.status=complete`、`provider_id=independent-blueprint-questioner`、`extraction_method=independent_questioning`。这不是独立审查证据。后来 Story 审查不替代先前设计质询。

同时，作者任务明确要求把当前会阻断的缺口放入 `slice-auto-topup-future`，使用 `headless_assumed` 降为 WARN，并从 checker 错误取得指纹。这表明执行目标偏向“使对象通过检查”，没有先确认当前设计实际成立。用户授权范围是 interactive，不支持借 headless 假定替代人工决定。

根因同时在设计和执行：交接没有把作者、独立质询者、处理意见者的实际动作落实为可检查交付；原生检查能验证字段，不能仅凭作者写出的“隔离/完成”证明独立性。Extension 没有真正送达质询要求；Framework 负责正常 component-design 的独立质询组织和结果消费。修正应回这两个责任位置，不能另造 Extension 设计审查框架。

### F04：推断被登记成 SE 权威；未决被形式上移出当前范围

新增 SR 明确了四个接口。会议新增的 `updateAutoTopupContract` 只给出接口意图及 contractNo、门限、面额，没有完整版本、类型、可空性和成功响应。模型生成第五个契约时补入版本 1.0、int/分等信息，却标为 `authoritative`、`se_transcription`；部分本地映射也用了同样权威标签。`source_ref` 指向自写转写文件，转写与 canonical 一致不证明与原始 SE 一致。

成功响应缺口 D7 保留了，但以空响应字段加 `drop` 映射处理；相关 gaps 的 `needed_by` 指向 future，当前契约仍被采用。T2/T7 等缺口也被推迟。保留未决是正确的；为了准入移动 `needed_by`，却不真正调整依赖它的当前设计或取得范围裁定，不正确。

设计决定可以基于推断，但必须与外部确认事实区分。未补齐时可交“含未决的评审草稿”，不能把它记为满足当前全部设计前提的准入结果。是否可缩小当前设计范围由用户/设计负责方决定，脚本和作者不能凭门禁结果改范围。

### F05：已知 Framework Markdown 引用缺陷本次确实触发

11:48:13 的任务 `prt_0fab87949001wfJglm1E6O5gus` 恢复第二位 Story 审查者，要求：改掉最终结论之前带“结论”的标题；在范围中列全 40 个文件；因原生引用检查不认 Markdown/YAML，在每条发现的涉及文件中加上 `decisions.json`。

`auto-topup/reports/f8bf4579a28773d7/review-original.md` 的六条 CR 均加了这个 JSON，即使问题是图的支付链路或正文重复。实际源码 `demo/framework/harness/scripts/check-review.ts:652` 的后缀过滤不含 md/yaml，尽管其他位置支持这些后缀。**交回中“4E 本次没有触发”与事实相反。** 这是运行中的补丁式规避，不是正确适配。

独立审查并非全无价值：首轮发现了 D8 缺依据、图线、配置遗漏及档位表述等，并促成修订。但最终报告通过不能证明审查接口已正确接通。报告格式义务应在派审前给出；文件引用与标题解析问题应由 Framework 修正。禁止用无关 JSON 引用或减少真实发现来换取 PASS。

### F06：Story 的精确设计与蓝图分离，知识链尚未成立

最终蓝图没有 `story_details`。Story 中却出现配置表、四条过程埋点等精确说明；规约决定引用 OBS 条目与设计节点，却没有形成对应的完整事件内容。脚本只能读已存在的 canonical 字段，当前指令对“蓝图没有”处理过宽，允许模型在 Story 另行补成设计。这与“设计先成立、Story 投影”目标不符。

知识已有实际作用：缓存、观测、兼容、页面角色等进入了讨论和节点，不能判为完全没读。问题是若干落点只写“须统计/按规范”，不足以证明应用完成；facts 中的知识来源以普通字符串承载，消费者只识别结构化知识值时也不能据此声称事实链完整。DFX-02 的“不新增资源所以不适用”还缺实际资源选择依据；不能仅凭新增源码就反过来断言该条必然适用，应在设计中确认资源/依赖事实。

本轮没有完成 CU，因此 CU 派生、must/模式角色进入 Spec/Plan、UT/Testing 的连续消费**未验证**；不能用原生 schema 通过或知识名称出现在表格代替。

### F07：update 能识别冲突，但“采用的新材料”与登记依据不一致

新版产品稿将日上限改为 300，模型询问后人选择 200，D9 与正文保持一致，这是有效能力。D10 补横幅重签位置，D11 保留发票后续处理，人工意见没有被简单删除。

但更新后的 Story 声称采用 v1.1，新输入和新决定没有形成新的冻结设计输入；`flow.input.snapshot_sha256` 与 `story_basis.input_sha256` 仍同为初版 `8dfd1905f00a1e75ffc90b353dc6318878295002670ffca3a5f030956df1932b`。初版和更新版蓝图原始字节 SHA-256 均为 `5803481100c43effe1f0500c7135af0c1169689807363d3e62523c73427cf198`，revision 1。

**蓝图未变本身不是错误。** 原版已经包含停用后可重签，D10 可以是表达澄清；如果要求新设一个特定横幅动作，则应由设计负责方确认其设计影响。当前缺的是：有效输入变化的真实登记、与既有设计相容的明确判断，以及审查对象取同一版本。不能规定所有 update 必升 revision，也不能只改 Story 的材料清单便称已同步。

### 3.2 自动充值 Story/Review

正确保留了服务端余额触发、端侧职责、同卡单签约、200 元上限、连续三次失败停用、开关不隐藏已签约入口、更新代替解约重签等核心内容；图片有来源，十章与 Review 的已定/未决基本可读。不能因此把整个结果判定为正确。

需要修正的实质问题：

1. Story §7.2 把“网络异常或接口失败”都写成“云侧没有签约记录”。响应丢失并不能证明云侧未建立签约，与当前重试有效性未决也不相容。需区分明确拒绝、尚未发送和结果未知。
2. §4.2 图把“触发判定与扣款”从卡云连向刷卡节点，未讲清支付部件扣款交互，与职责表不一致。不是美观建议，而是整体业务链表达问题。
3. 改档/关闭失败后的用户状态与恢复说明不足；附录列有失败统计不等于正文交代处置。对未知服务端结果不应自行许诺回滚或成功。
4. 接口附录逐契约展开所有映射、幂等和 NFR 对象，夹杂英文键和重复共性，掩盖业务差异；精确性与可读性未兼顾。
5. 配置、埋点等没有回到 canonical，已有知识义务的验收表达比 1.x 弱。不能靠给验收表补若干固定行号修复，须从有效设计义务派生。
6. Review 保留未决有价值，但其已定/待定依据仍受假定角色、未真实质询影响。不得以 report WARN 抵消正文或来源错误。

独立查看停用态 PNG 发现其呈现主要为无文字色块，不能据此验证按钮文案或交互位置。它可辅助页面区域说明，不能证明高保真还原；不得把图数量当视觉质量。

### 3.3 车钥匙

没有目标中间链和最终交付。当前 `doc/features/ISSUE-206-update` 后缀由回流命名产生，不表示真的执行了 update。本 Case 不能评价 Plan 质量、CU 知识承接或 Story 保持能力，全部记未验证；“gate_failed”是本轮失败终态，不是成功完成一次原生 Spec。

## 4. 可观察的模型工作过程

自动充值前半段有正常的取材、分歧提问和来源组织，更新时也确实停下问 200/300。偏离出现在设计交接：作者被要求学习 checker 内部结构、填完通过条件，假造独立质询，继而通过报告格式规避来收口。这种行为不能解释成正常工程探索。修正应让正式输入、作者合同和独立处理结果在动作前送达，工具承担可计算字段，语义判断由实际独立执行体完成。

车钥匙先因输入不完整询问任务，之后虽然读了 Story 仍错分维护入口，继而围绕原生 scope/report/术语反复准备，没有主动补齐本地需求材料。不能将其全部归为模型能力差，也不能假定加一句路由提示必然解决；修好输入和可发现性后应观察正常入口是否真正成立。

## 5. 相对 1.x 的差距

自动充值 Story 旧版约 17,828 字符，新版约 24,144；正文约 11,570→9,015，附录约 6,249→15,120，附录占比约 35%→63%。字符和图数只用于定位结构变化，不直接评分。阅读比较说明：增长主要是契约原始对象展开，核心业务异常与知识验证并未随之加强，属于超出预期的负向差距。

车钥匙从旧轮能够交付 Story/Spec/Plan 退到本轮无交付，是明确结果回退；但输入截断在两轮都存在，不能凭两次成败推断 2.0 设计必然不支持本地单。

应保留 1.x 的真实业务完整性、人读组织、图片与人工意见保护、知识义务传递；不恢复 Spec 依赖或旧阶段调度。旧版也有不应继承的推断，例如把降额无需再验证写得过于确定、缺来源的性能数值。优化以原始材料与当前决定为准，不追求复刻旧表格、字数和金样坐标。

## 6. Case 与宿主交互的整改

1. 自动充值业务请求是“定稿送审”，驱动器 `end_at: story` 却在成文登记/交付门通过时截停；宿主回答送审被检查点拒绝，随后按协议进入 update。因而本轮没有 archive，却投放“系统送审后反馈”。**Case 目标、终点与交互协议不一致**。先完成真实授权的送审，再投放送审反馈；本地单维持本地交付。
2. 交互脚本是业务答案库，不是必须逐行问完的剧本。模型合并提问时按实际问题答，未问事项不得宿主主动代做；但模型也不能把未问的人物权限、未定业务结论写成人签。采用“实际未决是否被正确处置”验收，避免为达预设步数制造重复确认。
3. 更新反馈“停用后没有重签去处”与初版已经写可重签不完全相符。可将正常反馈表述为“请明确从停用横幅直接进入”，保留改版冲突意图，不要求模型先接受错误前提。若新稿已满足，允许有据判定无需修改。
4. 宿主没有责任替消费模型修设计或报告。F03/F05 的操作来自被测主模型与其子代理，不是外层执行者注入。宿主应负责完整交付业务请求、真实答复、保留证据和报告异常。
5. 回流命名按实际发生的段落，不能因配置 `after_initial` 就把失败初轮命名 update；审查报告在 `doc/reports`，必须与需求/蓝图快照一起留存。
6. 模拟 SE 草案四个接口是有效的测试输入增强，应保留；不能为了让第五接口全绿，事后把模型推断补进原件。正常需求未决本就需要正确分流。

## 8. 对设计的反思

2.0.0 把“准入的 canonical、冻结输入、独立审查”定为权威方向是正确的，但实施合同过于依赖消费模型自觉填字段、手工调组件，以及 gate 是否返回成功。设计者此前以静态接线和离线证据确认了过多行为结论，这是设计验收缺口。

本轮不再追加针对报错的一行提示。下一轮按输入送达、真实设计责任、可读交付与业务终点四个完整环节收敛；保留既有脚本和权威对象，退出替代权威及绕行。上游明确缺陷单独交付，不让实施者边跑边猜接口；未验证的正常路径通过授权实跑补证，不优先扩建复杂异常框架。
