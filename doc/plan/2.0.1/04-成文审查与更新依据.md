# P3：人读审查、成文与更新依据

目标：Story 专属审查替换代码审查 request，保持零 CU 成文及有效输入一致。预算见总览。必读 core/story 的 review-object、independent-review、delivery、design-source、appendix-readers，reader-review-task、story-reader-rules，flow submission/update 与章节合同。

## 1. prepare / check

保留 story-build review --action prepare|check，复用 reviewObject/materialKey、现有任务和原件。

| 动作 | 输入 | 输出/副作用 |
|---|---|---|
| prepare | 定稿 Story/Review、有效输入/设计/决定、知识和判据 | 任务、全材料清单、material_key、原件位置；同材料有效通过可复用 |
| 宿主派审 | 任务、材料身份和位置 | 隔离 reviewer 回复，主执行者原样落盘并留调用事实 |
| check | 当前材料、准备记录、原始回复 | pass/warn/fail 或材料/报告缺口；不跑代码审查 harness |
| 登记/交付/状态 | 同一对象和报告 | 共用判定，不制造阶段 receipt |

材料集合只在 reviewObject 定义，materialKey 是本次 Story 身份。不另加 request_sha256、代码审查 summary 或工作副本绑定。时间/报告编号/登记不参与身份；任务不嵌入由自己内容算出的 key，避免循环。

报告仍在 doc/reports/story/<需求>/<材料键>/，历次回复保留；现有准备记录指当前原件，该引用不参与材料指纹。重新派审可产生新报告，不锁首份；正文、决定、设计、采用输入、知识或判据变化使旧报告失效。

## 2. 专属报告合同

现有 Story 判据与 reader-review-task 的报告说明维护唯一合同，派审前交付：

- 回显 material_key 和总体 pass/warn/fail。
- 逐项判据给结论与依据；不适用说明业务理由。
- 每项发现有编号、严重程度、问题、真实材料位置、依据及修正责任。
- 未解除 BLOCKER/MAJOR 为 fail；只有 MINOR/INFO 为 warn；无发现且核查完整为 pass。
- 不要求代码分类、Plan 模块表或无关源码；材料不足不能编造已核结论。

报告保持 Markdown，采用唯一的 `material_key: <64 位原始材料指纹>` 行、三个精确二级标题「判据核对」「发现」「总体结论」。判据表列为「判据 ID / 结果 / 依据」，ID 取 semantic_checks 的真实键且逐项唯一，结果为 pass/warn/fail/not_applicable，不适用必须有依据。发现表列为「编号 / 严重程度 / 判据 ID / 材料位置 / 问题与依据 / 修正责任」；无发现可空表。总体结论节只给一个 pass/warn/fail 及理由，不能靠标题包含“结论”进行模糊匹配。

prepare 输出 `material_key`、`task`、`rows`、`report_dir`、`report_file` 和 `reused`；check 输出沿用 `result/detail/advisories` 语义。报告以 review-original.<序号>.md 保存，同材料已有有效通过则返回原位置；缺报告复用待交位置；已有失败/坏报告的后续派审准备新位置，旧回复保留。现有 prepared.json 只存本次材料键与原件引用，不建立多份身份或首份结论锁。

check 缺准备/原件为 report_missing，格式/覆盖/引用/结论矛盾为 report_invalid，当前材料与准备/报告身份不符为 subject_stale，输入不可读为 input_invalid。有效报告才返回 pass/warn/fail；只读消费与显式 check 共用判定。报告显示 fail 或有未解除阻断时不能被机械检查改成 pass。

读取表格前核分隔行和列结构，无法完整读取返回 report_invalid，不丢弃未经确认的数据行。材料位置与本次文件集合精确匹配并支持定位片段，不用路径子串判断；总体结论按唯一首行读。当前材料的最近有效业务结论不因 prepare 创建新回复位置而撤销，真实后续复审可以更新结论，不建立首份结论锁。

脚本核格式/身份/覆盖/真实引用/结论一致性；遗漏、编造、图文、来源忠实和知识效果归独立语义判断。引用按真实材料集合，不用后缀排除 Markdown/YAML/图片。

作者不改原回复结论或补引用；格式错交 reviewer 重给并保留历史。格式合法不证明独立性，真实调用另留证。

退出 independent-review 的代码审查 request、工作副本、代码规则解析和多重绑定；framework-access 中仅服务此路径且无消费者的导出删除，其余原生消费者保留。不是新建通用 verifier。

## 3. 无能力与授权披露

核实实际宿主缺独立能力，说明事实，仅在明确人工授权后允许“未审查交付”。沿现有人签保存原话与授权对象，成文依据关联当前材料和披露；变化后核授权适用性。

坏报告、未派审、工具失败或实现未接通不归缺能力。不造 PASS；check 如实给未审查与授权事实，交付资格据此消费。状态随人读件和交回可见，不豁免蓝图准入/业务阻断。Case 不预置未审授权换通过。

先核实际能力、既有人签及尚未解除的业务阻断，再生成披露，最后绑定最终材料；理由/原话参数非空不能代替能力核实或真实授权来源。授权沿既有人签记录维护，准备记录引用它，不形成平行权威。仅重新准备或添加披露不能使已知阻断消失。

披露落在 Review 题头提示之后、议题章节之前的机器维护说明，并在 Story 的 09-rollout「交付与上线」章呈现“审查状态”，写清本版未审查、原因和范围；人工区不动。披露先进入文件再计算 material_key，后续重渲染/prepare 幂等，不在登记后改被审字节。只在控制台打印不算随交付件披露。

## 4. 成文

作者讲业务/角色/状态/正常与异常/结果未知/恢复/决定/验收，脚本投影成立的精确设计。退出任意对象递归摊平，按明确接口、字段、类型/含义/可空性、映射、错误、幂等、配置/事件等呈现。

不删事实或限字数；canonical 真有共享对象才共用引用，不按相似文本合并语义。内部核对路径留依据，外部人读引用可解析。适用义务缺设计回 P2，不写“不涉及”或另建 Story 权威。待施工细化明确责任。

按已支持 canonical 结构核投影覆盖，不以“原生评审投影未打印”判为非法字段。合法对象状态、错误条目及数据责任不能因类型是对象而被写成破折号；尚无明确人读映射的必要业务结构报投影缺口，由设计/作者在已有精确明细合同内处理。退出静默丢对象的断言，保留来源追溯信息与业务正文的职责分工。

## 5. update

1. 收齐变化与人签，明确采用及不采用。
2. 有效输入/决定变化，复用 complete 冻结新版本；历史不覆写。原件/转换稿按来源关系识别。
3. 模型判设计影响：表达/相容在 update-notes 给具体依据，revision 可不变；设计变化走原生反馈、接受与修订。
4. 材料清单、story_basis、审查对象取同一有效版本；材料变更做必要重审，同对象登记不自激。
5. close 共用 submission 的采用/冻结核对，核输入处置、人读同步、审查与人签；旧 flow.input 与旧 story_basis 自洽不足以收口。

上述核对针对完整有效输入，包括采用文件字节、scope_items、有效人签和提取稿，复用既有 selection/规范化逻辑。材料 digest 相等只是其中一项，不代表采用关系未变；不把整个工作区纳入摘要，也不强制未采用新材料成为设计依据。

资料请求不自动生成文档；文档更新不推施工授权。restore 按原所有权集合，保护人工意见、冻结输入、蓝图/CU、报告历史及发布记录。失败留旧有效登记与新候选。

## 6. 验收

迁移 test_story_build.py、test_story_inputs.py、test_story_update.py、test_review_modes.py、test_review_closure.py、test_review_golden.py 及现有报告协议测试：

Markdown-only 发现可读；阻断/建议/过期/坏报告/缺能力分别消费，无 JSON 绕行；同材料通过复用；新报告不因非首份被拒；新稿保持旧业务数值也登记新采用与实际裁定；未采用不假称采用；纯表达不强升 revision；未冻结的新采用阻止 close；精确投影完整、章节与人工区保护保持。
