# P3：成文、审查与更新依据

目标：解决 F05/F06/F07 与正文质量问题，保持零 CU 成文和章节/人工区保护。

必读：`skills/story/contracts/story-chapters.json`，`scripts/core/story/{sources,design-source,appendix-readers,appendix,independent-review,delivery}.mjs`，`scripts/core/flow/{submission,update}.py`，`phases/design.md`、`phases/update.md`。

## 1. 人读内容与精确投影

作者负责业务叙事：对象和状态、角色协作、正常流程、失败/未知结果与恢复、人工已定/未决、验收意图。脚本负责将已经成立的精确设计投影到附录。结构检查核来源、对象一致及章节保护，独立审查核遗漏、矛盾、编造与可读性。

调整 `appendix-readers.mjs`：退出通用 `describe()` 将任意对象递归摊进单元格的正文职责，按当前原生契约的明确字段投影。每个接口保留操作、方向、版本及其来源状态、请求/响应字段的类型/含义/可空性、映射与业务错误/幂等要求。共性按 canonical 的真实共享对象引用呈现；没有共享对象时不靠文本相似去合并不同语义。明确未决保留，未知字段不解释为必有。

保留完整精确内容；映射细节放同一接口的独立表，叙事正文只讲实际交互与失败语义。不用删字段、限字数或固定表行数缩短文档。仓内核对路径保留在成文依据/审查对象中，人读件使用可解析的业务来源标题和引用，不能为规避归档校验抹掉来源状态。

| 内容 | 取源 | 缺失行为 |
|---|---|---|
| 术语、范围 | 原生当前设计及有效需求/人工决定 | 缺确认时标未决，不用模型假定冒充人签 |
| 接口/数据/幂等 | canonical contracts / runtime_data_flows | 当前必须内容缺失回设计；未来细化明确说明 |
| 配置/事件/专项 | 已存在设计对象或 story_details | 有适用义务却无设计不能写“不涉及”；回 P2 补设计 |
| 知识判断 | facts/decisions 与承担对象 | 不另写第二份判断，展示理由与实际设计影响 |

正文新增或深化了设计结论时先回设计，不在 Story 人工区私自建立新权威；单纯表达改善不强制升蓝图 revision。独立审查至少关注“明确失败与结果未知”“角色与图线一致”“管理动作失败恢复”，这些是通用业务语义，不把本 Case 答案写入产品判据。

## 2. 独立审查

沿用现有独立产物 prepare/check，Extension 只提供 Story 判据与被审材料，U1 修复原生报告校验。prepare 产出的真实材料列表、报告格式、最终结论位置、文件引用规则必须在派审前给到 reviewer。

原始报告由实际 reviewer 写入原生报告目录。作者可按报告改业务产物；需要报告格式修正时仍由 reviewer 根据真实对象修改，不能由作者指定保留 PASS、添加无关引用或删掉发现。被审正文、有效决定、设计来源、采用输入、相关契约转写/映射变化均使旧报告失效；报告路径、时间戳和登记命令不改变业务对象。

交付结果继续按真实原生返回值消费：PASS 放行，非阻断 WARN 保留建议，阻断/报告无效/对象过期停在相应责任；能力缺失如实披露，只有现有已授权的未审查交付路径可使用，不能自动降为 PASS。U1 未交付前，不以旁路 checker 或无关 JSON 让正式验证全绿。

## 3. update 的有效输入

复用已有 `complete`、冻结集合和 `flow.input`，不加第二个输入版本中心。

1. update 收齐材料与人工意见后，模型明确本轮采用集合、采用范围、哪些意见只是表达澄清；当前有效材料与原始人签进现有设计输入登记。转换稿/原件用现有来源关系识别，不因复制路径不同便称未采用。
2. 本轮采用的需求版本或有效决定变化，调用现有 `complete` 生成/复用冻结版本；正文材料清单、审查任务与 `story_basis` 从这个版本派生。未采用新材料也明确记录其处置，不把它宣称为已采用。
3. 设计负责方判断新输入是否改变现有设计。改变时走原生反馈/修订，取得实际接受结果及当前设计；不改变时，在已有 update-notes 说明新输入与当前设计相容的具体依据，保留原 revision。不能仅凭 revision 没变推断相容。
4. 更新受影响正文/附录，按实际审查对象取得必要的新审查，重新登记 `story_basis`。同输入、同设计、同人读件重复调用保持幂等。
5. `update close` 核本轮输入处置已记录、当前采用集合与冻结输入一致、人读件/登记依据一致、必要审查成立和实际人签存在，才收口。施工未完不阻止文档更新，但如实交回原生状态。

确定性比较与完整性读取共用 submission 的现有来源/冻结逻辑，close 和 delivery 不各自重建摘要算法。脚本不判定“表达还是设计变化”的业务语义；这由模型作出，独立审查对照原件与具体落点复核。

失败时保留旧有效登记与新候选，不覆写历史冻结输入；restore 仍按既有可编辑集合恢复，不删除已被设计引用的输入、审查历史或 Framework 对象。新来源的权威处理不通过整树恢复撤销。

## 4. 验收

在 `test_story_build.py`、`test_story_inputs.py`、`test_story_update.py`、`test_review_modes.py`、`test_review_closure.py`、`test_review_golden.py` 中迁移相应覆盖：

- 普通领域合法契约的可空性、映射、错误和未决正确投影；中性复杂对象不以英文键递归摊平；人工区和其他章节不变。
- 新产品稿被采用：冻结摘要与 story_basis 更新；即使业务结论经人裁定保持原值，也保留新输入及覆盖决定。旧报告不能因 revision 相同而复用。
- 纯措辞修订：蓝图 revision 可不变，正文变更触发人读审查对象更新；再次登记不引发无意义审查。
- 新材料未采用：不写成已采用；当前有效冻结版本可保持，处置意见进入更新审查。
- 采用集合变了但未重新冻结：close 返回明确缺口，不谎报完整更新。
- Markdown-only 审查发现指向真实 Markdown；不需借 JSON，原生报告结论与实际对象吻合。

金样按有效设计重建，不把本轮错误原样固化。源文忠实与可读性通过独立语义审查，不能把“含某关键词”升级为语义证明。预算引用总览 P3。
