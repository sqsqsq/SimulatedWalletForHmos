## 2. R1 [P1] 报告解析会吞掉阻断发现，引用也未精确核对

位置：independent-review.mjs:117–180，table/judge。

table 不验证 Markdown 分隔行，直接丢弃第二行。反例：保留一条 MAJOR 发现，删除发现表的分隔行，将总体与判据写为 pass；检查直接返回 pass，MAJOR 被作为分隔行丢掉。这不是审查语义难题，是原始报告内容没有完整进入确定性判断。

材料位置使用 where.includes(path)，把实际文件路径加 .bak 的不存在文件也接受为 warn；没有完成“实际材料引用存在”的合同。总体结论使用多行搜索，也不等同于检查规定的第一行。

修正：先验证表头、分隔行、列数及数据行，再归类，无法完整读取时返回 report_invalid；不能静默丢行。材料位置解析成实际项目相对文件和可选定位，与本次材料集合精确匹配，不以子串命中证明存在。按合同读取唯一总体结论首行及理由。保持现有 Story 报告格式，不新增通用 Markdown 框架。

验收：缺分隔行、缺列的报告明确无效；MAJOR/BLOCKER 不因格式错误变 pass；真实 Markdown/YAML 路径可用，.bak 等不存在引用拒绝；正常 pass/warn/fail 保持。

## 3. R2 [P1] 未审查路径可绕过已知阻断，交付件也看不到披露

位置：independent-review.mjs:80–98、136–141；delivery、lifecycle 及人读件生产者。

authorizeUnreviewed 只要求 reason/reply 非空，没有核宿主实际能力或当前对象已有阻断。独立反例沿真实 prepare/check/register/deliver 调用：先得到 BLOCKER/fail → 相同材料重新 prepare → unreviewed 提供理由与原话 → 返回 unreviewed，登记和交付门均退出 0。重准备创建了没有回复的新位置，使仍未解除的业务阻断被“未审查”覆盖。

同一次交付中 Story 与 Review 均没有“未经独立审查”说明，仅控制台给出披露。收件人只拿到文件时无法知道此结果未经审查，不满足方案“状态随人读件和交回可见”。这是已知实现缺口，不必等 CLI 才定。

修正合同：

1. 核当前宿主实际能力事实和真实人工授权，按既有人签记录保留来源与适用范围；理由非空不能证明没有审查能力，prepared 不能成为另一份独立授权真源。
2. prepare 只是再次准备，不撤销同材料已有的实际业务阻断。沿现有报告历史读取当前材料最近的有效业务结论；未解除 fail 不能转为未审查交付。真实后续审查可以改变结论，不恢复“第一份报告锁定”账本。
3. 未审查状态、原因与适用范围写入 Review 题头提示之后、议题章节之前的机器说明，并在 Story 的 09-rollout「交付与上线」章呈现“审查状态”；人工区保持。披露属于交付内容，必须先进入最终文件，再计算材料键、绑定授权与登记。随后 prepare/渲染保持幂等，不在算完键后偷偷改文件。
4. 无能力、坏报告、没派审、工具失败分别处理。合法未审查授权不豁免蓝图准入和已知业务阻断。

验收覆盖有能力时不允许以缺能力降级、fail→prepare→未审查仍拒绝、真实无能力且有授权的披露随最终两件可见、材料变化旧授权失效、后续真正复审可替代旧报告。

## 4. R3 [P1] 定向投影变成了静默删设计内容

位置：appendix-readers.mjs:26–41、74–83、boundaryRows。

text_ 对任何对象返回空，数组过滤掉全部对象条目。反例中 development 节点的 current_state/target_state 为有实际说明的对象，原生 validateBlueprintViews 返回零问题，附录却显示“— → —”。另一个投影函数反例中 errors.items 的对象条目包含冲突码和恢复语义，输出“错误：—”。后者仅证明投影函数丢内容，不冒充整份蓝图准入测试。

“原生评审投影没打印”不能推出“不是合法 canonical 内容”。原生投影本身还展示 projections_and_caches 等字段，当前缩减也未完整对应。金样未依赖某项不能成为删除未知需求事实的依据。

修正：核已支持 canonical 字段的真实结构，明确读取必要业务内容，保留对象状态、错误/幂等/NFR 条目及数据责任；来源追溯字段可以留在核对面，业务事实不能以空值代替。没有明确人读映射的必要业务结构要给出投影缺口，交设计/作者在已有精确明细合同内处理，不能静默跳过。无需恢复任意递归摊平，也不增通用渲染器。

退出“嵌套对象只要不显示就算正确”的断言，改核实际信息保持及明确缺口。已适用的合法结构化输入和缺失输入分别验证，不只用标量金样证明。

## 5. R4 [P1] update 只比材料摘要，没有核当前有效设计输入

位置：flow/update.py:691–703；应复用 submission/frozen 的输入选择职责。

materials_digest 只描述材料字节，设计输入还包含采用集合、scope_items、人签及提取稿。新增比较没有覆盖这些内容，仍可能沿用旧冻结依据。

独立反例沿正常已登记需求开启 documents 更新：原材料不变，将 design-input.json 的一个当前条目 kind 从 requirement 改为 goal，更新说明记本轮已采用该分类；不重新 complete，再登记和 close。结果 close=closed，input 未变化。这证明输入声明变动未被检查，不是声称模型已经真实完成新的需求裁定。

修正：complete 与 close 共用对有效输入的规范化选择/比较，核采用文件内容、有效 scope_items、人签、提取稿与已登记冻结版本。差异尚未处理就指回 complete；不单独复制一套摘要算法，也不把整个工作区纳入哈希。

新材料未采用时，记录其处置并保持真实采用集合；不能机械强制所有文件变化都成为新设计来源。纯表达不升蓝图 revision。当前声明确实改变时，新版本由原生设计负责方判断相容或修订，随后同步人读及必要审查。

验收增加“材料字节未变但采用/条目/有效人签改变”“新材料不采用”“同输入重入”三类，保留已经通过的材料改版反例。
