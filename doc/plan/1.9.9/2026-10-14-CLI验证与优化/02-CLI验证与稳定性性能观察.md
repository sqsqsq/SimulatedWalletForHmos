## 2. 本次 CLI 必须记录的稳定性与性能观察项

2026-10-13用户明确要求：Extension稳定性与性能是本次测试的观察项，不能只看业务产物和末次门禁是否通过。以下是R7需求的实际观察清单，沿用 [TEST §6](../../../../test/TEST.md#6-评价) 的证据与评分协议，不新增评分表、固定通过阈值或通用评测工具。覆盖本轮获授权的两个Case初始阶段及update第二段，按Case、阶段分别记录，不将不同终点的耗时混在一起。

| 观察项 | 记录什么 | 如何判断 |
|---|---|---|
| 总成本与主要耗时 | 从init到本轮规定可交付终点的墙钟；作者、脚本、verifier、返修的耗时与可取得的token；人工等待、API/网络/环境故障另列；SVG重述/检查/恢复成本可区分 | 不把等待扣掉后隐去，也不把外部故障全归Extension；定位主要时间花在业务工作还是重复检查/读取/排障 |
| 同一对象重复派审 | 每次派审的subject、当时产物/材料变化、触发原因及报告落盘后的下一动作；首次收口与已闭环补审分别记录 | 真实业务变化需要重审是正常成本；只落报告或切换阅读形态导致无效新对象/重复审查，回机制根因，不靠删审查获得提速 |
| 一次成文与返修收敛 | 每个Case首份完整成文到首轮语义审查的结果、后续返修轮次、每轮根因；同根因是否再次出现 | 区分业务理解不足、规则未及时送达、检查误判、报告协议问题；两个Case只报告各自结果/计数，不据小样本宣称统计成文率提升 |
| 所有实际出现的harness/工具失败是否可理解 | 原始失败位置、事实、判据机制、恢复入口、模型随后采取的动作与恢复结果；前置缺失导致未执行的检查单列 | 模型是否能靠公开上下文和错误解释恢复；若必须读checker源码才知道判据，归最早信息生产者。Framework原生错误也登记，不能只写“上游问题”而漏证据 |
| 读源码及无效读取 | 每次读checker/Extension机制源码的文件、触发错误、目的和读后动作；重复查询、重复通读、大段重复注入一并定位 | 检查是否在研究业务，还是学习隐藏规则/迎合门禁；按TEST的调查口径判断，不把所有源码读取一概算错，也不因最终修好就忽略原因 |
| 告警与决定复用 | 同一WARN/建议已有去向后是否仍反复要求处置；已有数值/议题决定是否被重复询问或重新发明 | 真实新事实重新判断正常；没有事实变化却反复劳动是稳定性/效率问题。不能隐藏WARN或把open决定写死换通过 |
| 大输入与上下文成本 | 是否按当前标题路径读齐正文、附录与所需材料；遗漏/截断/跨段矛盾、重复阅读和输入版本混用；可取得的上下文/token增长 | 任务包变短不等于整体更省；审查范围和发现能力不能降低。未触发大输入场景即标未覆盖，不从小稿成功外推 |
| archive/update/视图的稳定性 | 切入Mermaid、比较/快照/上传/登记、恢复可用SVG的实际顺序；过期提示、失败后的已生效动作与恢复次数；是否重复上传或出现伪漂移 | 自动切换应减少手动步骤，错误不吞掉、不诱发重复副作用；功能正确与额外成本分别核。AR一键脚本属于人工工具，不让模型靠它补正常流程缺口 |
| 人工介入与终检 | 实际需求决定/澄清，与为机制故障作的救援操作分别计数；结束后才暴露的失败、终态及日志位置 | 正常人作业务决定不是机制失败；宿主不得为让测试通过透露checker解法、修改被测产物或伪续跑 |

**证据取得与交回**：运行宿主按TEST只观察、留存现有事件流/运行日志/工具调用与门禁产物，不在实跑中切换成维护角色教模型修机制。finalize后由维护评审按上表归因，引用 `output/story/<suite>/` 的原始位置；缺少计时/token等数据写“未取得”，没有触发的路径写“未覆盖”，不能填0充当表现良好。沿现有汇总能力取得数据，确需补采集能力时另指出缺口，本条不授权新增运行器。

本轮报告须同时交业务结果与稳定性/性能观察：哪些无效工作已消除、哪些仍发生、对应根因和修复责任、哪些无法验证。声称相对旧版“更快/更稳定”须有输入语义、模型设置、质量与终点可比的证据；无可比基线时只报告本轮实测，不为了补基线擅自增加CLI运行。一次成文、总成本与审查覆盖须结合判断，不以token单项下降或最终全绿代签优化成立。

本表没有扩大CLI启动授权；运行Case、终点和专项覆盖仍按本轮起跑安排确定。adapt移植及六类图/大输入专项未纳入某次实际运行时保留未覆盖，不能由两个常规Case的结果代替。
