# 1.9.9 需求评审与设计建议

2026-10-12，维护设计者。对象为本工作区 `doc/spec/1.9.9/` 当前稿（包括未提交内容），实现基线 `2fb4c304`。本稿回答需求是否成立、设计如何组织；不修改被审 spec、产品、Demo 与金样，不授权实施、真实 CLI 或发布。

## 1. 结论

六项需求的目标成立，适合在 1.x 独立演进。当前 spec 尚不能直接交实施：R1 的现状归因不准确，R4 对现有图片交付能力的前提不成立，R5 与较新的知识适配方法有冲突；R6 的旧仲裁规则与本版金样定位仍需同步。应保留目标，先收定下面的合同，再按独立需求拆实施包。

| 需求 | 判断 | 本轮应解决的实际问题 |
|---|---|---|
| R1 材料表与图文 | 成立，修正现状描述 | 已有作者贡献列表，但原件、转换稿与贡献的关系不够明确；统一为三列表并核完整性，保留机器身份与变化判定 |
| R2 子目录 | 成立 | 扫描和归类确实只认文件名；递归输入须贯通身份、转换、门禁与 update，冲突在写入前报告 |
| R3 页面交互 | 成立，定位为现有流程章的表达补全 | 读者能沿入口、页面、操作、结果与异常去向理解业务；不能把未知交互写成已确认事实 |
| R4 SVG | 成立，实际范围大于指导与检查器 | 派生图身份、审查覆盖、局部改图失效与本地完整交付都要接线；系统附件能力另核 |
| R5 adapt | 成立，基于当前方法做增量 | 定向升级、首跑知识覆盖、独立核对与只读状态视图；不恢复全量重盘点 |
| R6 金样 | 成立，先理清期望产物与测试状态的边界 | 完整、可信的期望产物和场景对照，生产检查确实执行；不能用金样自身证明业务正确 |

本轮仅核源码、合同与文档，并调用现有计量函数；未运行行为测试，未重做历史性能分析。2.x 的实现等价性尚未逐项复核，不能据本稿声称两线外部合同已经完全相同。

## 2. 必须先修正的依据与决定

### 2.1 R1 已有作者材料列表；机器登记不是可整体退出的旧机制

依据：[story-write.md](../../../../extensions/skills/story/phases/story-write.md) 已要求附录每行写来源、文件名、提供方与方式、内容贡献及原文链接；[sources.mjs](../../../../extensions/skills/story/scripts/core/story/sources.mjs) 的 `materialListTargets`、`materialListProblems` 已按 `materials.json` 核覆盖与链接。故“贡献关系不成文”“没有自己维护的材料表”须区分列表与表格形态，不能据此另造一条作者链。

[registry.py](../../../../extensions/skills/story/scripts/core/materials/registry.py) 的 `collect_materials`、`compute_digest`、`collect_sources` 同时负责材料身份、轮次摘要与待导入判定；[importer.py](../../../../extensions/skills/story/scripts/core/materials/importer.py) 明确不留导入回执，而是重新转换后比磁盘。因此 spec 的“导入登记”不能被当成现成的、完备的一对多溯源日志。

建议：作者表是“采用哪些材料、来源与贡献”的唯一语义正文；`materials.json` 保持唯一机器事实索引，不写贡献判断。二者责任不同，不是重复清单。退出旧列表语法和对应解析判据；不退出 digest、pending、图片说明/取舍与 update 消费能力。

“一份进入需求的材料一行”还须区分：原件、由多个原件组成的阅读稿、正文中引用的图片、会议版本与本轮生成件。当前 `materialListTargets` 会把文档落点与 inbox 原件一起列入，不能直接把现有集合换成三列表而保留重复要求。

### 2.2 R2 支持递归不等于允许全部同名输入

依据：`importer.scan_sources` 用 `iterdir`；`convert_sources` 按 `path.name` 归类、按 `stem` 组织正文标题和 `assets/<stem>`，UX 图写入平铺目标。`registry.collect_sources` 也以 `p.name` 建字典。递归扫描一处改完仍会覆盖或混淆。

现 spec 已明确要求跨目录同名报错，本稿保留这个范围。对外应准确表述为“保留输入子目录，冲突显式处理”，不能同时承诺任意目录不整理即可导入。正文标题可继续取主名，拼接顺序改为 POSIX 相对路径排序。落点冲突预检要同时考虑图片目标、抽图目录和正文标题；目标平台大小写碰撞也须被发现。

“assets 顶层平铺”不是当前准确事实：实际是 `assets/<源文档主名>/<图>`。保持其现有布局即可，不用为了对齐措辞改存储。

### 2.3 R3 是事实表达，仍然受已确认的业务决定约束

依据：[章节合同](../../../../extensions/skills/story/contracts/story-chapters.json) 已有业务流程章和“交互与界面”决策类别；写作页已有页面原图、页面状态及无页面业务的规则。缺口在沿流程组织页面信息和独立审查覆盖，而非从零增加 UX 体系。

建议采用流程章内小节与五列表。简单路径无需为满足验收额外画流转图，复杂分支才配图。已确认的页面操作和结果可以成为行为验收依据；“不按每页机械产生验收条目”不应被写成“交互描述不是验收依据”。材料冲突先按现有议题路径处理，不能以“有稿照录”为由跳过冲突判断。

### 2.4 R4 不能按“PNG 已有完整链，SVG 同权即可”实施

依据：[importer.py](../../../../extensions/skills/story/scripts/core/materials/importer.py) 的 `IMAGE_EXTS` 没有 SVG；[images.mjs](../../../../extensions/skills/story/scripts/core/story/images.mjs) 区分原材料图片和 Mermaid 图源承接；`registry.collect_materials` 枚举 `assets/` 后把其身份计入材料 digest。只加 SVG 后缀并存入 assets，会把作者画图当作上游材料变化，存在自己产出触发新材料轮次的风险。

[archive.js](../../../../extensions/skills/story/scripts/adapters/archive.js) 明确“只上传 md”，当前仅上传 story 正文和 review 附件；[state.py](../../../../extensions/skills/story/scripts/core/flow/state.py) 的 `STORY_REGISTERED` 也只有 story、决策登记、写作设计，不包含独立 SVG 文件。[lifecycle.py](../../../../extensions/skills/story/scripts/core/flow/lifecycle.py) 的 `archived` 只记时间。spec 不能假定已有资源上传、包摘要或资源版本回执。

包的路径也需修正：现有规格在 `spec/spec.md`，不是 `AR/spec.md`。保字节、保相对布局时应为 `<需求>/AR/story.md`、`<需求>/AR/review.md`、`<需求>/spec/spec.md`，再加允许的引用闭包。三件里的链接可能指向过程材料或工程源码；如何处理越界引用必须在生成包前报告，不能无限递归复制工程，也不能静默断链。

SVG 字符宽度近似只能提示风险，不能一概成为溢出 FAIL。字体、对齐、transform 与裁切会影响结果；确定性错误阻断，近似判断交实际渲染确认。否则合法图形会被机械门禁误拒。

### 2.5 R5 首装知识盘点必须服从当前准入规则

依据：[knowledge-adaptation.md](../../../../extensions/skills/story-adaptation/reference/knowledge-adaptation.md) 已有逐主题判断、首批每份最多三项、编码规范不进入知识、模式仅按演进主题与相同依赖适配等要求。旧 [03](../../../spec/1.9.9/03-知识范围定义.md) 的“完整覆盖”和从仓内惯用结构推导模式，不能直接覆盖这些决定。

建议：首跑集用于发现缺口，不要求填满四格；没有对应项目知识的决定允许有证据的不适用。遇到首跑确实必需、但当前起步规模或模式准入承接不了的内容，明确记录缺口和由目标维护者处理的动作，不能自动扩充或假报就绪。覆盖判断要含“适用且已覆盖 / 有据不适用 / 缺口”，不能只含“有文件 / 缺口”。

`--status` 还有一个事实边界：[adapt-scan.mjs](../../../../extensions/skills/story-adaptation/scripts/adapt-scan.mjs) 的 `INSTALLED` 在进程启动时读目标 version，升级中的 followUp 因而知道升级前版本；升级后另起 status 进程就丢失这个起点。只读视图不能把“当前版本之后没有在途条目”冒充“上次升级没有遗留在途事项”。建议输出当前事实与按当前游标可推导的建议；历史完成情况不可恢复时明确未知，并引用上次交回。若要完整恢复历史待办，须另定记录责任，本版不以新增状态文件补洞。

### 2.6 R6 要退出“金样永远正确”的仲裁规则

本版 [00 口径条款](../../../spec/1.9.9/00-版本范围.md) 已规定金样仅为经审核的期望产物。但 [02](../../../spec/1.9.9/02-金样优化.md)、[test_golden_sample.py](../../../../test/tests/test_golden_sample.py)、[golden_workspace.py](../../../../test/scripts/golden_workspace.py) 仍有“任何判据拦金样，错的是判据”。退出范围必须包括这些真实消费者，不能只用上层条款覆盖。

建议：金样正本存期望产物；上游原件、测试输入、流程准备由 fixture 与隔离工作区承担。真实人的决定与构造的测试表态分开，后者不能被当成该业务已经获准。遇到规则与金样冲突，回材料、有效决定和现行合同判断哪方错。已审核金样仍有回归保护作用，不能为让门禁通过任意改写。

旧 G2 提出的知识多落点冲突也不可由修金样偷偷改产品合同：当前 [validation.mjs](../../../../extensions/hooks/shared/knowledge-use/validation.mjs) 确实对单条落点作约束，但是否修改 schema 需要核完整作者—投影—plan 消费链，单列局部决定及预算。真实需求需要多落点时不能删掉有效义务来迁就金样。

## 3. 建议的职责与正常路径

### 3.1 材料输入、作者表与页面表达（R1、R2、R3）

1. 用户从既有系统入口或 inbox 交材料；导入器递归枚举，统一 POSIX 相对路径，模型读内容归类。全批转换前报告缺归类、非法路径和目标冲突。隐藏目录、控制件和 README 排除，目录链接不跟随到 inbox 之外。
2. registry 根据实际来源与转换落点生成机器事实；转换关系直接复用导入器的确定性映射。远端直接给定的文档是输入事实，不能因没有 inbox 原件而被判缺原件。模型转写的一对多来源需要显式说明，无法机械推导的真实性由独立审查核。
3. 作者在现有 Story 附录材料节维护唯一三列表，转换稿一行列全部采用原件；原件不再为满足计数重复作为独立贡献行。未采用材料保留去向与理由；原图继续走现有图片取舍，不要求在贡献表重复全部图片。
4. 表结构、来源覆盖、重复、缺文件与禁止纳入的过程件由脚本核；来源采用是否合理、贡献是否真实、遗漏业务内容由独立审查核。作者表不能反过来定义待检查的原件全集，否则漏写一行就能把原件排除在审查外。
5. 写作设计把已采用 UX 说明分配给对应业务流程；作者写页面流转表、引用已登记原图，未知操作形成议题。图前概括阅读目的，图后补图中没有的条件、责任和结果；信息已讲清时不凑三类空话。
6. update 仍由模型判断新料是否替代旧料；旧原件依相对路径留存、归类同步，再用同一转换算法重建。内容哈希改变才改变材料身份；只改作者贡献说明不制造上游新材料。

核心文件动作：修改 `materials/{importer,registry}.py`、`flow/update.py`、`story/{sources,language,images,writing-plan}.mjs` 中相关消费点，以及现有写作页、导入规则、inbox 模板、章节合同、作者任务与读审任务。依据实际职责替换，不新增第二套材料服务。R1 第一包即采用相对路径合同，R2 再开放递归能力，避免先写文件名键再重改消费者。

完成条件：平铺和多层输入都可处理；冲突失败不覆盖目标；同一转换关系供实际导入和 pending 判定；漏原件、伪造来源、重复行各有发现者；页面叙事能回答入口、操作、正常结果、受限及异常去向。无页面、无图、未决交互均有正常路径。

### 3.2 SVG 与完整交付（R4）

先在现有图片/图形职责内区分“输入原图”与“作者派生图”。原图沿材料 digest；派生图属于成文产物，来源指向当前材料或规格，不进入上游材料 digest。登记尽量复用现有图形身份与说明入口，扩充其来源类型和产物指纹；不新增 SVG 专属状态机。具体存放路径及共用登记字段须在 R4 实施分册中定案，不能仅把文件放进被 registry 全扫的目录。

派生图生成后先做 XML、viewBox、引用解析等结构检查，再渲染核裁切、遮挡与连线。读审同时取得正文与图像，核关系和条件。图字节改变应使现有成文/审查依据过期，回既有重审路径；上游输入未变时不重启材料范围判断。Mermaid 转为 SVG 后仍须保有上游关系的承接证据，不能被现有“只能围栏带图源”的规则拒绝。

本地打包是确定性 helper：输入为当前通过交付检查的三件及获准引用资源，输出 zip 与同批内容摘要；消费者是本地交付入口与后续 adapter。必要性在于自动解析依赖、保路径并核缺件，避免用户逐张拷图。更简单的只交 Markdown 无法满足离线资源完整性；本 helper 不承担写作、版本调度或审查判断。该新增能力须按项目约定确认后实施。

闭包以三件为起点，按链接解析到允许的来源与图片资源，原路径、原字节打包；不纳入整个 story-src、报告或工程。出现不允许的链接时报告引用位置，由作者修正文表达或明确交付边界后重验，打包器不改文案。外链保留并注明网络依赖，SVG 内部依赖也要解析。Markdown 资源解析应复用已有可用能力并扩展实际需要的语法，不能只以一个简单正则宣称支持全部 Markdown。

系统正文归档、图片展示、zip 附件上传分别报告。当前 adapter 不支持后二者；先核真实系统接口和回执能力，再由 adapter 维护方实现。无接口证据时只交本地包并列系统资源交付未完成，不能签完整系统 SVG 交付。

验证覆盖：只改图不改正文时旧审查失效；打包不改变材料轮次；同名不同路径不丢文件；缺资源和越界链接不产成功包；重复打包内容集合一致；失败保留上次有效包及人工意见。六类指导各有渲染和语义证据，优先选型逐场景给配对成本证据，不从一张好图外推。

### 3.3 adapt 增量（R5）

首装保留画像和知识范围的现有确认点，范围从当前升级主题与目标仓决定空间取得。盘点结论写在既有交回中，不造第二份知识台账；升级只处理新主题和加载异常，无变化不重做内容审查。

`--status` 复用 `knowledgeCheck`、版本比较、manifest 读取与 followUp 的纯计算部分，退出方法页内重复的手写检查脚本。不得调用含 `writeAdaptedFor` 的 `printFollowUp`。未安装、依赖缺失、坏 manifest/知识清单分别报告，不能误报“零知识且通过”；读前读后核文件集合和内容不变。

独立语义审查在本次知识产物完成、交回适配完成之前进行：输入是目标激活知识、已定范围、对应源码/规范和待验证的正常需求；不把作者自评当审查结论。核有据性、阶段决定支撑、项目级边界与不适用理由，失败回适配作者修相应知识。缺独立执行能力时明确未审，不能由同上下文自检代签。具体宿主调用入口要在实施前按 codex/opencode 可用能力核实，不复制阶段 verifier 调度框架。

T6 记录实际人工决策次数和首个 spec 闭环成本；现有两个计划确认点是流程设计，发生额外澄清或返修时照实计入，不能把“2 次”写成达标阈值。

### 3.4 金样与验证（R6）

先将 AR90004 的业务事实、未决与已有人的决定核清，整理贯通锚，再补 AR90006、无页面/本地单等对照。未确认的决策维持未决，不能为让 plan 闭环而示范代签。测试确需一个确定选择时放入明确标识的构造输入，验证该输入的机制效果，不冒充业务真实授权。

生产入口装配和状态准备放 `test/scripts/golden_workspace.py` 及 fixture；正本留 `test/golden/`。增加检查确实执行、预期缺陷确实被发现的验证，不能只查输出没有几个报错词。保留渲染器回归等仍有效的业务覆盖；机械形态与语义质量分别判断，不用表行数或章节数量替代完整性。

每份金样实质修改仍按 02 的用户确认要求交具体稿。旧路径引用、错误规则和人工表态来源同时修正；不在本轮直接动正本。

## 4. 实施组织与依赖建议

用一份版本总览加独立需求分册，每个需求 1–3 个可验收步骤；不把六项目标强塞成四个大提交。

| 分册 | 步骤 | 依赖与退出 |
|---|---|---|
| R1 | 定材料对象与三列表合同 → 改作者/检查/审查同源消费 | 身份先按相对路径；旧列表语法、重复覆盖规则退出 |
| R2 | 递归导入与冲突预检 → update/门禁/指引贯通 | 接 R1 身份；文件名作身份的旧路径退出 |
| R3 | 流程章与 UX 成文路由 → 页面/无页面语义复核 | 接 R1 图文口径；不必等待整套 R6 完成，可先用已核输入，最终回填金样 |
