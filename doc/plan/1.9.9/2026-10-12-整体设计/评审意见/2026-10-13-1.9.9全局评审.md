## 1. 对四个问题的结论

| 用户问题 | 结论 |
|---|---|
| 是否打补丁 | **局部存在只修报错入口、没有贯通同一职责的问题。** inbox 根联接只在 retire 拦，扫描/导入仍接受；I/O 失败说明套到了整批写入，但未覆盖图片目录内的部分写入。整体架构未见新增平行 Framework、双份身份库或通用补丁调度层，不支持“整版都是补丁”的判断 |
| 是否过拟合 | **存在验证对少量输入形态过窄的问题，已导致合法输入失败和合同未被测到。** 来源名用简单标点切分，测试只有简单名字；投影稳定性只测等行数替换；部分写入只测两个正文文件之间失败；根联接只测 retire。未发现本版新增机制按两个 Case 的单号、业务答案或金样行数分支。不能把没有 Case 专名等同于没有过拟合 |
| 是否偏离诉求、只求测试通过 | **部分实现结果偏离诉求，但没有证据判定实施者主观上为赶通过而作弊。** 当前回归全绿仍遗漏本报告四个反例；“失败能直接理解并恢复”和“减少无效审查身份变化”尚未完整成立。把 helper、文字规则和测试数量直接当效果完成，会造成事实上的偏离 |
| 所有设计点是否实现、符合期望 | **否。** 多数机制和交付指引已落地；P6 正本切换/旧消费者退出明确未做；P3/P4/P5/P7 多项效果证据未取得；另有本报告四项实现缺口。不能签“全部实现且符合期望”，也不能说“只差跑一下 CLI” |

综合结论：**先修四项局部缺口并补有区分力的回归，再按已定安排进入 CLI。** 不需要由此推翻七包设计或新建通用框架。CLI 验证准备可并行进行，验证改期不豁免当前已可确定复现的错误。

## 2. 新发现与复验要求

### G01：图片写入中途失败，已发生的删除和写入未进入错误事实（P1）

位置：[importer.py](../../../../../extensions/skills/story/scripts/core/materials/importer.py) 第 814、846–855 行，`cmd_import` 与 `_write_all`。

图片循环先删除旧 `assets/<stem>/`，逐图写入，全部写完后才追加 `written`。我用中性 docx 的两张图，在第二张 `write_bytes` 注入磁盘错误：旧图已经不存在、第一张新图已经写入，结果却报告“已写：无；覆盖前的旧版备份：无”，并要求“按备份把已写的目标恢复”。[实际结果](../../../../../output/story/1.9.9-global-review-20261013/import-partial.json)。

这不是要求新增跨文件事务；P2/P7 已明确接受中途失败，但必须如实说明落盘进度、受影响位置和真实恢复办法。当前统一错误包装没有覆盖图片目录内部进度，会使消费模型误判现场并走读源码。

**责任与修正结果**：实施者在实际删除/写入发生的位置记录受影响路径，区分已完成、部分写入/可能破坏与未执行；存在可恢复备份则指出，不存在则明确从仍在的原件重新导入，不声称有旧图备份。正文、图片复制、会议版本的同类分步写入一并核。局部修正即可，不建事务框架。

**复验**：正文之间失败、同一图片目录第二张失败、覆盖写入失败分别核磁盘事实和报错一致；正常重跑可恢复完整派生产物。既有 `test_a_write_failure_midway_says_what_was_written` 只测正文间失败，不足以代表全部写入面。

### G02：合法材料名被标点截断，模型照公开规则写仍无法通过（P2）

位置：[post_check.mjs](../../../../../extensions/hooks/spec/post_check.mjs) 第 143、152–179 行，`UPSTREAM_NAME_RE` / `upstreamNameProblems`。

P1 明确允许真实文件名含括号，P7 要求用已登记材料名定位。我向实际函数提供同结构的 origins，并分别使用 `规则(v2).md`、`规则（终版）.md`、`规则,定稿.md`：名称被截成 `规则(v2`、`规则（终版`、`规则` 后报不存在；简单的 `规则.md` 通过。[四个正例的对照](../../../../../output/story/1.9.9-global-review-20261013/source-names.json)。探针仅在隔离副本导出内部函数，函数正文未改。

根因是把普通标点当成名字的边界，没有与“真实已登记名字”合同接通；不是原件缺失或业务来源错误。作者照任务包填写也会被迫改写名称以迎合检查，偏离来源忠实目标。

**责任与修正结果**：实施者让名称取得方式支持合同允许的名字，并与作者写法同源；可按已登记名称精确匹配或采用明确且可表达完整名字的有界写法，不新增随样例累加的标点豁免。泛称与真实歧义仍应失败，不能通过取消定位检查解决。

**复验**：中文/英文括号、逗号、空格、完整相对路径、重名与无登记名；同时核真实的 spec 门禁与作者任务中的写法。现有来源名测试的正例仅简单合同名和路径。

### G03：同一个 inbox 根联接，导入接受、退原件拒绝（P2）

位置：[importer.py](../../../../../extensions/skills/story/scripts/core/materials/importer.py) 第 126–151 行 `scan_sources` 与第 533 行 `retire_source`。

扫描把 `inbox.resolve()` 直接当信任根，只有子项被检查；此前修复的根联接检查只在 retire。本次创建独立临时需求与同级 outside，把 inbox 联接到 outside：真实扫描和 `cmd_import` 成功，将外部原件写入 RR 阅读稿；同一路径的 retire 被拒，外部原件仍在。[结果](../../../../../output/story/1.9.9-global-review-20261013/root-inbox.json)。没有对用户真实材料作读写。

这违反 P2“遇到目录链接显式报错、不跟随到 inbox 外”的整体来源边界，也说明前轮根因处理只落在发现反例的一个入口。本报告不撤销 retire 自身已通过的结论，而是新增扫描/导入消费者缺口。

**责任与修正结果**：实施者在共用来源枚举/边界位置统一实际根检查，让导入、registry/pending、update 与 retire 遵守同一规则；不要继续各入口补一份不同判据。

**复验**：根联接、子目录联接、文件链接和普通多层目录分别通过真实调用链；拒绝发生在首次写入前，正常目录不受影响。

### G04：减载索引重新把投影区的行数带进审查对象（P2）

位置：[reader-review-task.mjs](../../../../../extensions/hooks/shared/reader-review-task.mjs) 第 227、347–367 行。摘要计算使用去掉机器区正文的 `authorZone(story)`，但阅读行数、段落末行和标题仍从完整 Story 取得，并进入生命周期片段。

我只在机器投影区追加一个空行，作者正文不变：作者区摘要保持 `1671fa42c90374a2`，任务中的总行数和末段范围由13改14，完整 reader task 改变。再以相同 context/checks 调用当前 Framework 的生产材料和 request 函数，只替换该片段，subject 确实变化。[范围对照](../../../../../output/story/1.9.9-global-review-20261013/projection-ranges.json)、[生产 helper 结果](../../../../../output/story/1.9.9-global-review-20261013/projection-subject.json)。这不是完整 CLI，不能据此宣称必然发生派审循环。

但它已经反证 P7 S3“投影刷新不变”的交付声明。既有稳定性测试只把一行中的短文字换成长文字，行数不变，所以全绿没有覆盖这一输入维度。不能把摘要不变等同于整个身份输入不变。

**责任与修正结果**：实施者与设计者核完整片段的稳定边界，使机器投影的纯排版刷新不会通过阅读坐标造成无效身份变化，同时保证实际阅读入口可定位、作者内容变化仍失效、机器区仍被审。优先复用稳定章节/区名入口，不复制 Framework 身份算法、不加第二套审查状态。若必须改变有效身份合同，由设计者明确调整并重新验收，不仅改测试预期。

**复验**：机器区等行数替换、增删空行、长度变化与作者区变化分开；用实际任务生成和 Framework 生产函数核身份，再在 CLI 中观察真正的派审次数。

## 3. 是否有架构性补丁与被替代机制残留

下列改动有明确的当前责任与消费者，接受其方向：

- 报告校验从审前 post_check 移到报告落盘后、交付门及 update close；旧保护迁移，未直接删除坏报告检查。
- origins 是既有材料清单中的派生关系，沿真实转换算法取得；未另建人工来源账本，digest 算法没有重复计入它。
- SVG 的正式入口共用 `figure-view`，Python 调同一 JS 入口；没有 zip、归一化指纹或平行 Framework 身份实现。
- adapt status 复用知识加载与跟进计算，未造升级历史状态库；同用途分组只是线索，未用相似度代替内容审查。
- 数值复用沿知识与现有 decisions；告警未靠抑制清单消失；大任务用当前审查任务的阅读顺序，未复活逐行裁决协议。

局部收敛仍不足的是 G01/G03：共同职责只在部分失败出口成立。G04 则是新减载机制与原身份边界没有一起验收。修复应回到对应生产者，不再叠一层“错误翻译”、特殊 Case 规则或运行次数限制。

**P6 的退出没有完成**：`test/scripts/golden_workspace.py`、`test/tests/test_golden_sample.py` 仍承担旧 AR90004 工作区/指纹逻辑，`test_review_golden.py` 仍读旧平铺 AR90006；新两组七件仍在候选目录。当前因用户未审定允许过渡，不将此解释为恶意留兼容；但在完整需求验收时，这就是未交付的旧机制退出项，不能以“实现问题已关闭”覆盖。

## 4. 过拟合与测试通过的边界

机制文本及主要新增实现未见按 auto-topup/car-key-sharing、Case 单号、额度答案或金样章节数作运行时分支。六类图、十章、三列表和命名表等是已确认的有界合同，不因为固定就判过拟合。知识中的目标仓专名按所有权属于样板事实，不计作机制泄露。

有根据的测试调整包括：旧列表夹具迁成三列表；报告校验测试迁到审后出口并保持反例；新版本测试按版本关系断言而不固定唯一旧版号；候选配图按已登记位置和真实引用与运行证据区分。没有发现靠屏蔽三项全量失败来写“全量通过”，它们一直明确披露。

需要纠正的是**证据外推**：G01–G04 均在498项相关测试通过时仍成立。测试分别锁住了正文间故障、简单材料名、retire根联接、等行数投影替换，却没有覆盖相同合同的其他合法/异常输入。过拟合检查应问“换一种合法输入或异常发生位置是否仍成立”，不能只搜专名。

O5 曾为“二次确认”排除二次的历史修补，当前已改为明确分工：歧义形式交独立语义审查，作者、overlay、计划一致。这个现行决定本身不等于降低需求，但只有语义执行证据证明“一次/二次”约束也能被审到，才能算目标成立；目前没有该证据。不能拿正则测试通过替代它。
