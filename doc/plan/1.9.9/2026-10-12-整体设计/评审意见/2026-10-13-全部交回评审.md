## 3. 必须返修的实现问题

### R01 [P1] 修改 Mermaid 真源后正式入口被挡住，恢复命令会覆盖新源

位置：[figure-view.mjs](../../../../../extensions/skills/story/scripts/core/story/figure-view.mjs) 第 134–151 行；[svg.md](../../../../../extensions/skills/story/reference/svg.md)“改图义改它，再跑 mermaid”的使用合同。

复演：prepare 后，Story 为 Mermaid 形态，将 `.mmd` 中 `A --> B` 改为 `A --> C`；`switchView(..., 'mermaid')` 报“块被手改过，或源改了还没切回”，零写入。按错误给出的 `prepare --id` 恢复，则将 `.mmd` 覆盖回旧的 `A --> B`。这不是坏输入：正式方法正是要求修改该真源。

影响：合法改图无法继续登记/审查/update；被推荐的恢复动作还会丢失新图义。现有用例只测了“当前是 SVG 时改源”，没有测正常的 Mermaid 作业期。

责任与结果：实施修正源更新与块损坏的处理；设计者也应收定二者在恢复入口上的区别。Mermaid 源必须保持权威，不能让正文管理块无条件反写源。复验覆盖两种当前形态下改源、损坏块、源缺失、显式重建，证明合法修改可继续且不会回退新源。

### R02 [P2] SVG 结构合同未完整执行，已显示的视图还能绕过复查

位置：[figure-check.py](../../../../../extensions/skills/story/scripts/core/story/figure-check.py) 第 30、37、44 行；[figure-view.mjs](../../../../../extensions/skills/story/scripts/core/story/figure-view.mjs) 第 174–182 行。

已复现三个结构错误返回空问题集：根为 `<notsvg>`，viewBox 为 `0 0 NaN Infinity`，CSS `url(missing.woff2)` 指向缺失字体。原因分别是后缀判断根名、未核数值有限性、只查 href 不查 CSS 引用。另在 Story 已为 SVG 形态时，将图改成宽度为零但 metadata 不变，再跑 svg，仍返回成功且保留显示，因为该分支根本不调用 viewGap。

要求：精确核 XML 元素及有限正视口，覆盖受支持 SVG 中实际会引用资源的形态；不支持的引用形式明确报告。已经显示的 SVG 也要经过同一结构前置；源快照相同不是结构/视觉通过。补上述反例及合法命名空间、合法 CSS 本地资源正例，不以禁掉全部 CSS 或 transform 代替合理支持。

### R03 [P2] IMAGES 原件被排除，材料贡献无法回到原文件

位置：[registry.py](../../../../../extensions/skills/story/scripts/core/materials/registry.py) 第 323–329 行；P1S1/P1S2 与 P6S2 的 IMAGES 取舍说明。

`collect_origins` 把“图片不用逐张进贡献表”扩大成“提供这些图片的原始文档也不进”。已采用的 IMAGES 文档只留下图的路径、摘要和说明；图片条目没有原文档版本/溯源关系。复演给已 ingested 的 IMAGES 原件及其有效图片，origins 返回空；auto-topup 候选也因此没有产品原稿这一来源。

要求：区分图片对象与承载图片的原件。原件已经对成文有贡献，就须在共同来源事实里保留其身份、版本和到图片的关系，并让作者/审查能说明贡献；不要求把每张图片重复列一行。这是 P1 目标缺口，不能交给用户以“能否接受材料表少一行”豁免。既有计划若对只抽图原件表达含糊，同步责任说明。

### R04 [P2] 同路径连续替代没有安全的旧版本留存约定

位置：[inbox_import.md](../../../../../extensions/skills/story/rules/inbox_import.md) 第 72 行；P2S2 §4。

规则把每次旧原件都移到 `.backups/local/inbox/<相对路径>`。同一输入路径被第二次替代时，目标已经存在；不同移动工具会覆盖或拒绝，规则没有保全旧版本的确定出口。交回以“由模型决定是否改名”留下了备份身份选择，但这项确定性工作已有保留旧版的明确要求。

要求：明确可重现且不覆盖历史原件的备份定位，继续保留原相对路径；冲突时不得覆盖。用同一路径三版内容做连续替代，核每版可回查、恢复及归类键同步。这里不要求新建事务框架。

### R05 [P2] 为“二次确认”排除了所有“二次”，漏掉真实次数约束

位置：[spec/post_check.mjs](../../../../../extensions/hooks/spec/post_check.mjs) 第 134–139 行；P7S2 §5 的后补修正。

生产 hook 复演：“连续失败二次后停用”不报来源缺失，“连续失败两次后停用”“连续失败 2 次后停用”会报。同一个合法业务约束因写法不同漏检。用金样出现的“二次确认”推导“所有二次都不是数值”，超出了该样例能支持的范围。

要求：修正数值检测的适用范围与表达规则；能确定的次数不能豁免，语义有歧义的交原有审查，不由单字排除替模型判断。补多种次数表达、序数和操作名称正反例，不只把这个新句子加入特例。

### R06 [P2] 阅读索引重叠，使“分段减载”变成重复通读

位置：[reader-review-task.mjs](../../../../../extensions/hooks/shared/reader-review-task.mjs) 第 347–355 行。

readingRows 同时列 H1、H2、H3，每段到下一个同级/上级标题才结束。9 行测试稿的有序入口为 L1–9、L3–6、L5–6、L7–9，共要求读 18 行。真实 Story 的 H1 首项覆盖整篇，后面又按章、节重复读，与“每段读完再往下”的指令冲突。

要求：阅读单元按实际原文区间不重叠、完整覆盖；目录父项与执行阅读项分开。保留当前内容变化使请求变化的职责，不能靠少读正文省 token。复验 H1 前言、嵌套标题、无 H3、围栏内标题、大附录等合法结构；语义上的跨段完整性另取实际审查证据。

### R07 [P2] summary 缺报告字段被误判为“宿主没有审查员”

位置：[verifier-report.mjs](../../../../../extensions/hooks/shared/verifier-report.mjs) 第 127 行及命令退出码映射。

当前只有 summary 不存在会报缺口；只要对象存在但没有 verifier_report，就返回 NOT_REVIEWED、命令退出 0，并断言 verifier 未启用。复演即使 summary 有当前 subject、宣称 enabled，仍是相同结果。字段缺失可能是坏/不完整 summary，不能据此推导宿主能力。

要求：由原生能力/请求状态确认“确实未启用”才进入未审路径；取不到这一事实时报告未知/前置不完整，并指向原生恢复入口。不能通过给构造 summary 新加一个自证字段修复。此处结论仅为该命令误报与错误出口，不声称已证明完整 check-receipt 可被绕过。

## 4. 金样与知识真源的问题

### R08 [P1] 自动充值时序图在验证取消后仍画了创建签约

位置：[auto-topup Story](../../金样候选/auto-topup/AR/story.md) 第 192–193 行。

支付返回写“协议号，或取消、未通过”，下一行无条件 `W->>C: 创建签约`。创建结果 alt 在这次调用之后，不能约束前面的授权条件。正文和 [原始 SR](../../../../../test/cases/auto-topup/system/SR90006/design.md) 明确未获授权不能创建；同稿流程图也有取消回签约页分支。

要求：图中明确授权成功才调用创建，取消/未通过终止或返回签约页。复核图与 Spec、异常和验收使用同一条件。Mermaid 能渲染只证明语法，不能签图文语义一致。

### R09 [P1] 本人钥匙详情的输入身份在 Plan 中断链

位置：[car-key Spec](../../金样候选/car-key-sharing/spec/spec.md) 第 150 行；[Plan](../../金样候选/car-key-sharing/plan/plan.md) 第 103、185、217 行。

Spec 要求“本人钥匙卡片点击进详情”。OwnerCarKey 只有 vehicleId/modelName，但唯一详情路由只收 shareId，且只经 getReceivedKey 取被分享人收到的分享。本人钥匙不是一条分享，拿不出这个 shareId；也没有本人详情的另一路数据取得合同。

要求：给已承诺的本人钥匙详情补完整的身份、路由、数据源和展示边界，与收到的钥匙区分，不能伪造分享 ID 或删除本人卡片能力过关。至少用本人钥匙和收到的钥匙两种合法输入走通。

### R10 [P1] 通信失败被写成确定的业务状态未变

位置：[car-key Spec](../../金样候选/car-key-sharing/spec/spec.md) 第 318 行 E10；[Plan](../../金样候选/car-key-sharing/plan/plan.md) 第 312、315 行；Story“撤销请求失败”对应表述。

Spec 将“车云返回失败或通信失败”合并为“不改变状态”；Plan 要求接受通信失败保持待接受、撤销通信失败保持生效。合法反例是云侧已经接受/撤销，响应丢失；此时端侧不能由通信异常证明远端状态未变。

要求：区分明确业务拒绝与结果未知，说明未知时展示、查询/对账和再次操作边界；不能把网络结果直接当业务结论。依据是当前云侧状态真源与接口合同，不要求凭空增加协议能力；真实接口缺口须显式交回。同步图、异常、统计描述和验收，特别检查“重试”是否可能再次执行已完成动作。

### R11 [P1] 满额前置挡住已到云侧的同一请求续办

位置：[car-key Spec](../../金样候选/car-key-sharing/spec/spec.md) 第 119、319、382 行；[Story](../../金样候选/car-key-sharing/AR/story.md) §5.2；[Plan](../../金样候选/car-key-sharing/plan/plan.md) 第 173 行。

反例：原有 4 条分享，创建第 5 条已成功但响应丢失，本地草稿仍在。回来查询配额已满，现稿无条件置灰、不发请求；同一幂等键原本应返回已建立的分享，却再无恢复出口。这同时违背续办与不重复创建的目标。

要求：区分新增分享的配额限制与确认既有尝试结果，补满额下的未知结果恢复。保留“草稿不绕过新建配额”，不能以删除配额检查解决；也不能给接口编造未存在字段。用“最后一个配额已被本次请求占用”与“确实被另一请求占满”两种输入区分。

### R12 [P1] 候选将 SEC-01 改成展示脱敏，未关闭知识合同冲突

位置：[安全隐私知识](../../../../../extensions/knowledge/constraints/security-privacy.md) 第 23、29 行；[car-key Spec](../../金样候选/car-key-sharing/spec/spec.md) 第 470–472 行；auto-topup Spec §7.3。

现行知识要求“任何出口都须先脱敏”且“采集处脱敏，输出端过滤不作为落实方式”。候选将其解释为组装展示内容时脱敏，同时明确业务接口传可识别身份、草稿保留 granteeId，并在生成的规约区声明已落实。这两份责任来源并不一致。

业务身份必须可用，G04 的修正方向应保留；不能机械要求把接口身份也不可逆脱敏。问题应回知识样板真源：定清必要业务身份处理、输出/展示/日志边界与相应保护方式，由有权来源裁定并同步消费者，再核知识应用。不得在金样内偷偷缩窄红线，也不能以“真实工具生成了规约区”证明应用正确。此项属确实影响两个 Case 的知识修复，不是扩建无关金样。

## 6. 对实施者请求裁定事项的意见

1. **P4 切换放核心入口**：从职责看是可接受的收敛方向，官方 `/story archive` 的①交付门→②上传→③登记若能保证始终上传 Mermaid、最后恢复 SVG，就能保持用户目标，且不让自备 adapter 依赖 core。旧测试本身不是拒绝已定方案的权限来源；此处判断依据是实际生产链。应同步方案中的调用位置，并补完整链及失败分支证据后签收；当前尚无该证据，不作无条件通过。
2. **只抽图原件不进来源集合**：不接受，按 R03 修。图片不重复成行与原件失踪不是一回事。
3. **备份不加版本区分**：不接受现有空白，按 R04 给确定、不覆盖的留存方式，不限定必须用某一种时间戳格式。
