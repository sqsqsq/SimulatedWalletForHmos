## 1. 现状核实与范围修正

| 输入假设 | 当前依据 | 决定 |
|---|---|---|
| 写报告必然换 subject | Framework `verifier-material.ts` 已排除 reports/回执；但 hook 片段与 check 状态仍参与哈希 | 不新增稳定 subject 旁路。使 Extension 审前检查只取业务输入/产物，把报告校验移到审后 |
| 所有场合改用 sync-closure | `phase-closure-finalizer.ts` 的已闭环分支复用旧绑定；现有 phases/spec.md 全部要求完整 harness | 按当前对象未闭环/已闭环区分动作；不得用 sync 冒充采纳已闭环后的新报告 |
| MINOR 修记录就可不再报 | 高频术语告警属于 Framework `check-spec.ts`，并无 Extension 抑制接口 | 底层事实保留；收敛的是重复修复请求，不篡改 WARN 为 PASS |
| 218 条裁决需建设分批机制 | 当前 pre_verifier 与 test_verifier_report_protocol 已明示该机制退场 | 不恢复旧裁决表；当前大输入以分节阅读与最后交叉检查减载 |
| 数值缺一个全新登记库 | author.md 已要求本工程设定登记议题，现有知识可承担项目级约束 | 用已有 decisions/知识及正常 update 复用，不建数字缓存或跨 run 自动学习 |
| 所有失败已讲清 | delivery.mjs 把 check-receipt 输出截为最后 12 行；guard 的异常有责任但部分环境错误无具体恢复动作 | 全链核失败事实是否送达；补原因、机制及恢复类别/入口，保留原诊断 |

源码调查后又调用当前 Framework 的 `buildVerifierMaterialView` 与 `buildVerifierRequest` 做局部复演，结果四项均成立：只新增报告文件不改材料摘要；检查状态改变会改材料摘要；hook 片段改变会改材料摘要；仅 prompt 字节改变不改 subject。运行证据在 [material-probe-result.json](../../../../output/story/1.9.9-design/material-probe-result.json)，临时脚本在 `output/scratch/1.9.9-design/material-probe.cjs`。该证据只证明这两个生产 helper 的关系，没有运行完整 harness/receipt 闭环或独立语义审查，不能当效率收益证据。

## 2. 所有失败的交付合同（本轮用户新增重点）

范围覆盖 Extension 登记的 spec/plan/coding/review/ut/testing 六个 post_check、其共用 helper，以及 Story 命令调用 harness/check-receipt、材料导入和状态命令的失败传递。Framework 原生检查也纳入消费模型最终收到的信息核查；责任修复按原始生产者区分。

每个失败给出四件事，同一问题内连贯表达，不把关键部分散到提示其他角落：

1. **事实与位置**：哪个文件/条目/阶段，实际读取到什么，缺什么；输入缺失与检查未执行分开。
2. **原因和机制**：依据哪个当前合同、如何取身份/集合/状态、什么事实违反哪条判据及为何不能通过。只陈述判定所依据的计算规则，不延伸到场景修法，不倾倒实现代码。
3. **恢复类别与入口**：说明属于作者真源修订、补材料、审查回复重取、环境恢复或维护者处理，给真实可执行入口/落点及责任。具体改哪些业务内容、怎样取舍由消费模型推导；脚本不按场景开处方，不让作者改审查报告或手改流程状态。
4. **恢复终点**：重跑哪个入口、应看到什么状态；已经写入成功但后续失败的明确哪些动作已生效，防止重复执行。

确定性检查一次返回全部可计算问题和因前置不足未执行项。不能机械扫描“四个字段齐全”就宣称报错可理解：维护者用缺陷输入只读错误和公开规则，验证能定位问题、理解判据、识别恢复类别/入口；修法是否正确及是否因解释不足而走读源码，交授权后的真实实跑观察。

复用 `hooks/shared/gate.mjs` 的聚合和 guard；具体原因仍写在实际判据生产处，不新增通用错误翻译服务、判据解释字典或会过期的场景处方模板库。已有满足合同的错误保持，不为统一文风重写全仓。

`story/delivery.mjs` 移除尾部 12 行截断和把多行压成一行的失真传递。原 stdout/stderr 完整保留可定位输出；面向模型先给失败类别和恢复入口，再给原问题清单。无权限、依赖缺失、子进程起不来、非零退出、输出为空分别报告，不能全归为“产物不合格”。`flow/client.mjs`、Python subprocess 调用和 CLI 顶层异常出口同样核信息损失。

环境依赖缺失时给目标 framework/harness 的依赖恢复入口；check-receipt 缺席时归 Framework 安装维护；报告解析失败归独立审查回复重取；门禁代码异常保留原始异常及未执行范围，归维护者处理。这些是恢复类别和入口，不根据场景生成源码修改或业务取舍处方。

Framework 原生错误已有 details/suggestion 的完整透传，不另写 Extension 判定。若原始信息本身不足，实施者在本分册交回中登记复现输入、原输出、缺少的机制解释、责任文件和所需上游修正；在没有上游发布件前明确未解决。不得违反 Framework 只读边界，或声称单靠 Extension 已满足所有原生错误的解释目标。

## 3. O1/O11：审前与审后分开，恢复路径明确

### 3.1 生产者与消费位置

`hooks/spec/post_check.mjs`、`hooks/plan/post_check.mjs` 退出 `reportProblems` 调用；仍核全部业务产物、知识、投影与流程。`pre_verifier.mjs` 不引入旧报告结论、路径或处置状态；warning 的数据只由当前输入/产物决定。

报告结构、overlay 条目完整性、同对象首份合规结论和处置检查保留在 `hooks/shared/verifier-report.mjs`，增加命令出口：`node <ext>/hooks/shared/verifier-report.mjs --feature <名> --phase <阶段>`。从当前 summary 定位报告；命令实际要校验报告时，缺 summary/缺报告明确失败，不能沿库原来的“尚未派审就跳过”行为返回成功。Framework 明确未启用 verifier 的情况单列未审，不伪作 PASS。

退出码 0 表示当前报告形态/处置核对通过，1 为可修的缺项或冲突，2 为参数/环境前置错误。命令复用现有函数和结论记录，不重新判断 verdict 的语义或伪造 framework 回执。审查身份、闭环仍由 check-receipt/原生 harness 校验。

报告命令的必要性：post_check 位于派审之前，把其自身报告带回这个位置会形成反向依赖；已有校验不能删除，只能移到报告产生之后。该命令只是现有模块的出口，不是第二套 verifier 或运行器。

调用方为 phases/spec.md 闭环步骤、plan 作者交回指引、`story/delivery.mjs` 与 `flow/update.py` 收口检查。交付门先核报告形态和处置，再调用原生回执；update 对受影响且需闭环的阶段核当前报告，不让绕过方法页的直接 close 跳过校验。语义确实沿用历史 PASS 时复用已有 `withoutCurrentReport` 路径并明示未独立重审，不向不存在的当前报告强加必需性。

### 3.2 动作表

| 当前事实 | 下一动作 | 不得混淆 |
|---|---|---|
| 当前请求首次审查完成、业务材料未变、阶段尚未闭环 | 原样落报告 → 报告校验 → check-receipt → sync-closure → 交付门 | 只落报告不再完整跑审前链制造新问题 |
| 报告格式/条目不完整 | 同一 request 交独立审查者修回复，原样落盘后再校验 | 作者不能自己改报告内容 |
| 有阻断或改业务/契约 | 回最早真源返修 → story 重新登记 → 完整 harness → 当前请求独立审查 | 不能以“不想重审”沿用旧结论 |
| PASS 后只改表达且符合当前 Framework revalidate 条件 | 现有 revalidate，并明示沿用范围 | 表达深化不能掩盖业务变化 |
| 阶段已经沿旧报告闭环，后来补了当前对象独立 PASS | 完整 harness 采纳，核 summary 当前 reviewed_subject 与 readiness | sync 的已闭环分支不会重写旧 evidence binding |
| advisory 不在本阶段做 | 现有 notes 写问题、理由、接手阶段/人 | 保留事实，不反复要求同一处理，也不当成已修 |

状态与恢复要求同源送入 phases/spec.md、phases/update.md、hooks/{spec,plan}/author.md 与 `flow/update.py` 报错。相关指引替换而非追加一份相反规则。测试必须证明 reportProblems 原有保护仍在新消费位置成立。

## 4. O2–O10：规则、数值与告警

| 项 | 本次定案 | 机械与语义边界 |
|---|---|---|
| O2 reopen | update 开着时沿原范围完成可独立修改、保留范围问题并 close，再 reopen；未获范围决定不先重写受限产物 | 对照 rounds.py/update.py 真实状态覆盖 close→reopen→complete→story；没有真实逻辑缺陷不加新状态 |
| O3 AC 承接 | 在现有验收条目的说明里写 `承接：<上游原始编号>`；不承接仍写编号、原因与范围依据 | 编号集合由脚本核，意义与完整性由读审核，不造一张重复验收表 |
| O3 指标粒度 | 一个独立业务指标一小节，先定义口径再列统计点；不定指标数量 | 指标是不是同一个由模型判断，脚本不靠点数/标题词判 |
| O3 统计列 | spec/plan 采用当前知识规定的阶段列集；机制只要求现有统计点身份列，允许必要补充列 | 单一真源在知识及扩展模板，不能把 Demo BI/Chart 专名写进通用列清单 |
| O3 术语表 | 按当前 profile spec 模板列序生成默认形态；按列名读取仍允许合法调整 | 不把列序偏好升级为业务阻断 |
| O3/O6 来源名 | `上游约束：<已登记材料名称>`，名称能在 P1 集合映射到唯一文件/采用版本；存在歧义用完整文件名 | 不要求跨文档章坐标；来源名存在不代表数值来源真实，仍独立回原文 |
| O4 数值真源 | 先查现行项目约束；本工程新设数值登记既有议题的量、单位、适用条件、理由及候选/决定，再由 Spec/Plan 承接 | 只把已确认值当约束；open 保持条件。跨独立运行没有共同决定时不强制同值 |
| O5 数值检测 | 机械层按已声明形态核阿拉伯数字配单位、汉字时长/金额和“两次”及以上次数；作者面送达可机械核的写法。“一次/二次”等歧义形式全部交独立数值判项，作次数约束同样必须有来源，操作名不强判 | 不以语境后缀词表猜含义；不声称机械覆盖了全部中文数量。版本号、编号、序数、代码中的数字不当业务阈值；语义覆盖另以 V02 取证 |
| O7 引用块 | 已知模板流程提示/占位残留由脚本按模板标记核；一般 blockquote 是否为业务引用由语义审查判断 | 不全面禁止合法引用块，也不以标点猜“说明性” |
| O8 H1 | Spec/Plan 采用当前 profile 模板的文档类型标题，功能名由当前需求给；单一 H1、无未替换占位 | 同业务名的合法表达不因不同于金样字串失败；模板解析失败明确报，不硬编码 hmos 名 |
| O9 告警处置 | facts 不变的提醒沿既有 notes 留去向；真正修复后底层不再报；新的对象或事实变化重新判断 | 不引入 WARN 抑制清单，不把宽松语义判定塞进脚本 |
| O10 失败解释 | 按 §2 全链盘点、补齐与完整传递 | 不靠批量加一句“请修复”冒充解释机制 |

O4 不新增专用数值登记 schema：既有决策原文已有唯一决定责任。机器可核材料标签及议题存在，单位换算、同义数值、是否真的沿用由独立审查核。确为项目级常量时由目标知识维护者按既有准入维护；单需求值不进入通用知识。这样避免将某次测试生成的 1s/1.5s/2s 固化成全部需求答案。

notes 的有据处置不以 `notes.includes(id)` 等于语义解决；机械只核引用存在、指向当前报告，独立审查/作者须解释处置。已有同 id 不代表新报告同问题自动豁免，不新增“已忽略”全局状态。

## 5. O12/O13：当前大任务与结束前可见性

`reader-review-task.mjs` 目前内联 Story 作者区与写作设计全文，再列会议与议题；本次改成有序阅读入口：文件、当前作者区内容摘要、按作者区标题路径派生的阅读清单与检查目标；每段读到清单中下一个标题之前，最后一段读至文件末尾，附录机器区也须通读。正式需求审查读取前由 P4 入口实际切为 Mermaid，原生harness/独立审查运行期间不提前恢复；Extension的归档/update/生成/检查/状态命令由自身机制在最外层结束时恢复可用SVG（P4 §3），实际正文由独立审查者分段读磁盘原件，不能只读索引；SVG 重述对照审单独完成，不把视图字节混入正式业务审查身份。输入摘要稳定进入 pre_verifier 片段，正文变化仍改变对象，不用仅路径替换正文而漏失效。

审查先沿业务流程逐段核，再集中核所有 open/settled 议题及跨件关系，最后一份现有报告汇总。读取失败明确哪些未审，材料变化后重取当前请求，禁止拼接不同输入版本的局部判断。批次是一次独立审查任务内的阅读顺序，不新增子任务调度、分批 JSON 或固定返修次数。保持每个开放决定的具体结论义务，减少复制不减少审查范围。

O13 先复用当前 `test/scripts/run_case.py` 的 run_gates、gate_diagnostics 和 closure 观测。核各正式检查能在模型结束前由正常产品入口运行；发现某条产品正确性判据仅在终检出现，应前移到它的真实生产门（若是已经退出的 review-disposition 旧规则则删失效检查）。宿主不能把隐藏判据解法作为业务回复教给模型。

测试域只增强诊断：未运行、执行失败、产物失败、已闭环只读复核分别可见；保留完整日志路径和终态原因。被测已结束后的失败如实交回，不自动重启、伪续跑或让宿主修改产物。是否新增一次真实验证按 TEST 授权，不在本包实现自动修复调度。
