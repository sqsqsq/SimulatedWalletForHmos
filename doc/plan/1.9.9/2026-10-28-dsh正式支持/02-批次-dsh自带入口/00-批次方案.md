## 2. 设计：`.dsh` 与 `.opencode` 同构

**用户 10-28 质疑，原话**：「我对你的方案有质疑，我期望.dsh跟.opencode一样的完整。framework也没支持opencode，是我单独给demo加的」。

第一版设计只把阶段技能和 story 放进 `.dsh/skills`，规则仍留在 `.agents/rules`，dsh adapter 也继续声明自己沿用共享的 `.agents` bundle。现改为按 opencode adapter 的形态：dsh 有一套自有、完整的目录，与 `.agents` 解耦。

| `.opencode` 现状 | `.dsh` 对应 | 生产者 | 说明 |
|---|---|---|---|
| `agent/verifier.md`（原生子代理） | `framework-verifier.patch.yml` | Framework 物化器（`commands.subagents`，批次 1 不变） | dsh 的审查员只能用配置层表达，启动与续跑都要 `--patch` |
| `skill/<阶段>/SKILL.md` ×11 | `skills/<阶段>/SKILL.md` ×11 | Framework 物化器（`skill_bridge.target_dir: .dsh/skills`） | 模板同为共享 `skills-bridge`，跳板深度相同，正文与 `.opencode/skill`、`.agents/skills` 逐字节一致。dsh 默认扫描该目录（rank 100），不需要 `--patch` |
| `rules/{framework.mdc, framework-agent-execution.mdc, interaction-renderer.md}` | `rules/` 同三份 | Framework 物化器（`rules.target_dir: .dsh/rules`） | 与 opencode 同性质：dsh 不自动加载规则目录，是被 AGENTS.md 与 skill 引用的被动文档 |
| `skill/story/SKILL.md` | `skills/story/SKILL.md` | Extension 安装函数（manifest `provides.bridges` 新增一条） | source 用 `bridges/agents-skill-story.md`：同层深度、同为标准 skill frontmatter，正文完全相同，不复制第二份。（更正：起草时误写“opencode 有自己的 bridge 文件是因为 frontmatter 不同”；实测 `opencode-skill-story.md` 与 `agents-skill-story.md` 逐字节相同，是既有的一份重复，本批不扩大它，也不顺手合并） |
| 没有 `story-adaptation` | 没有 | — | 与 opencode 一致。实例扩展跳板只由 Framework 按项目的 `agent_adapter` 生成。`/story adapt` 经 story 入口直接读 story-adaptation 正文 |
| 没有 hooks | 没有 | — | 与 opencode 一致 |
| 根 `AGENTS.md` | 根 `AGENTS.md`/`CLAUDE.md` | 不变 | 两个宿主都只从工程根读指令 |

- **demo 本地定制（只动 `framework/agents/dsh/` 与 dsh 自己的选项登记，上游和 Framework 逻辑不动）**：
  - `agents/dsh/adapter.yaml`：`skill_bridge.target_dir` 改为 `.dsh/skills`，`rules.target_dir` 改为 `.dsh/rules`；description 与 notes 改为“自有 `.dsh/` bundle（AGENTS.md 共享）”，写明 dsh 自动加载的只有 AGENTS.md/CLAUDE.md 与 `.dsh/skills`，规则目录是引用可达的被动文档。
  - `skills/reference/confirmation-registry.yaml`：dsh 选项的 label 与 notes 里的“dsh 用 `.agents` bundle”一句改为自有 `.dsh/` bundle。批次 1 之前它就为 dsh 做过本地定制。
- **`.agents/`**：generic、chrys 照常使用并保留，dsh 不再物化到这里。dsh 两个目录都扫，同名技能以 `.dsh/skills` 为准，不会出现两个同名 story。

### S6 中央 runtime 的 dsh 档位带权限档（实跑后新增）

**发现**：`story-suite-20261028-143352` 实跑中，`story-build` 与 `author.mjs` 用管道 `spawnSync` 调 python，在 dsh 沙箱里报 `spawnSync python EPERM`。dsh 文档写明这是已知边界：受限令牌下 libuv 的管道 stdio 会 EPERM，继承或文件句柄可用。

**归因**：
- 10-24 及以前的 dsh 会话首个事件是 `permission/preset: danger-full-access`，本轮是 `workspace-write`；
- dsh 的档位由环境变量 `DSH_PERMISSION_MODE` 决定，缺省为 `workspace-write`；
- 本仓与中央配置里都没有设这个变量，所以当时是临时设置，交回只写了“headless 配置已还原”。

这一项也属于测试装置对 dsh 的临时支持。用户决定「两头都修」。

**改动**：
- 中央 `clis.json` 的 dsh 档位加 profile `env`：`build` 设 `DSH_PERMISSION_MODE: danger-full-access`，`plan` 设 `read-only`，与 claude/codex/opencode 的 build 档“可写工作区并执行命令”对齐；
- 加中央测试；
- 提交、打标签、同步进本仓。

### S7 Extension 子进程不用管道收集输出（已撤回）

**撤回（2026-10-28）**：实施后未提交，用户质疑：
- 「我们究竟在干什么？为啥extension本身的机制，受agent影响？」
- 「agent适配本身不是已经有bridges层了吗」
- 「我期望的是正式支持dsh，与其他claude codex opencode一样啊」
- 「你要搞清楚，哪些是测试装置的问题，哪些是应该extension提供的能力」

**复核结论**：
- 管道 EPERM 是 dsh `workspace-write` 沙箱的宿主特性，与其它宿主的权限审批属同一类：交互时由人审批，无人值守用完全权限档；
- Extension 核心机制不应为某个宿主的执行限制改写；
- 宿主差异只收在 bridges 层，而 bridges 层也无须为它加专属说明。

**已全部还原**：代码、`child.mjs`、测试、demo 重装件、文档中的“默认沙箱也能跑”表述，预算回到 S5 读数。下面保留原写法，供追溯。

**原改动**：
- 新增一个共用函数：子进程的 stdin/stdout/stderr 经临时文件句柄传递，不用管道；返回值与 `spawnSync` 同形；
- 替换 Extension 里 4 处管道调用：`flow/client.mjs` 的 `runPython`、`story-build.mjs` 的 `child`、`story/delivery.mjs` 的 check-receipt、`story-adaptation/scripts/adapt-scan.mjs` 的 `git`；
- `figure-view.mjs` 生成的启动器本来就是 `stdio: 'inherit'`，不动；
- 加回归测试：一是这个函数的输出、输入、退出码、找不到命令四种行为；二是 `extensions/` 里不再出现默认走管道的子进程调用。

**目的**：使用者在 dsh 默认沙箱 `workspace-write` 下用 `/story` 也能跑。

**未覆盖**：Framework harness 自己起的子进程在沙箱里是否有同样问题，归 Framework，本批不改。测试按 S6 跑 full-access，所以覆盖不到 `workspace-write` 下的完整链。
