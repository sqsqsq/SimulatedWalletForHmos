### S2 中央 runtime 提供配置层装载能力，业务仓测试配置指定装载哪份

- **中央 runtime**（`C:/Users/kangz/.agents/tools/cli-runtime`）：
  - `tools/cli/models.py`：`CliRunRequest` 新增 `options: dict[str, list[str]]`，缺省为空；`to_dict`/`from_dict` 同步，工作进程经 `request.json` 拿到同样的值。
  - `tools/cli/config/clis.json` 的 dsh 条目：
    - 声明它支持的启动选项 `"options": {"patch": ["--patch", "{value}"]}`；
    - plan、build 两个档位的 `args` 与 `resume_args` 在 `--profile headless` 之后加一个整词占位 `{options}`；
    - 不新增档位，其他宿主的条目不变。
  - `tools/cli/registry.py`：
    - 校验：`{options}` 只能占整词，只许出现在声明了 `options` 的条目里；每个选项模板必须含 `{value}`。
    - `build`：请求里的每个值按选项模板展开，按请求顺序拼接，替换 `{options}`；没有选项时这个词去掉，与原命令完全相同。

## 3. 设计依据与取舍

- **不新增 dsh bridge**：实跑原件已证 dsh 从 `.agents/skills` 发现 `story`。新增文件没有新消费者，还可能出现同名技能。
- **审查员入册**：adapter-schema 的入册纪律要求实测观测，`verifier_subagent` 一直保持 false。现在有四轮 CLI 的实际调用作依据，但“写工具实际不可用”这一条未满足。用户明确接受这个差距后入册，差距写进 adapter 注释、维护操作和发布说明，不改称已满足。
- **中央仓提供能力，业务仓指定装载哪份**（用户 10-28 定）：
  - 原来按 suite 生成快照，等于测试装置在中央注册表之外另造一份 dsh 启动命令。
  - 现在由中央 dsh 条目声明 `patch` 选项、请求携带具体值。中央不出现任何项目路径；本仓只在测试配置里写装哪份，不再有 dsh 专属的启动处理。
  - 没有选项时命令与原来完全相同，共用中央配置的其他仓不受影响。
  - 被否定的方案：
    - 中央新增 `maison-build` 档位：把项目路径写进了中央仓；
    - 写进 DSH 用户 profile：人设在机器上另存一份，会和 demo 漂移；
    - 保留快照：与“去掉临时支持”的目标冲突。
- **配置层缺失时由 `run_case` 报错**：缺失检查按“配置指定的文件必须存在”通用处理，不再是 dsh 专属的起跑检查；同时由离线测试保证 demo 物化了配置层、template 也带上了。
- **本轮收口不要求真实 CLI**（用户 10-28 问“是否必须走cli测试”，以下是答复）：
  - 每项改动都有离线对照，覆盖到与上一轮实跑等价：
    - Extension 只改注释；
    - 审查员配置层与 `c2d8b72b` 之后 `story-suite-20261024-224427` 用的是同一份；
    - `verifier_subagent` 的值等于该轮在工作区临时设的值；
    - 启动命令与该轮 `run.json` 逐项比对相同。
  - 那一轮在这个组合下已有真实的 `skill` 与 `verifier` 调用。
  - 离线证明不了的部分：dsh 能否真的从新路径启动（Windows 批处理包装和含空格路径下的实际进程），以及“升级后直接跑”的端到端效果。这些列为未覆盖，不签行为通过。
  - 下一轮用户启动的正常 suite 就是首个真实验证，不需要为本轮另开专项诊断。
  - 用户想在收口前先证实时，可授权跑一次单 Case 的正常 suite，终点到 spec 闭环即可，核三点：dsh 带配置层能启动、会话里有 `verifier` 工具、阶段报告验真闭环。TEST §5.2 的 verifier smoke 物化的是 `.opencode/`，没接 dsh，不作此用。
- **verifier 改为 true 的新风险**：人工交互时没带配置层启动，会话里没有 verifier 工具。处理办法：给人看的启动说明，以及 adapter notes 里的“新开会话”恢复路径。不加启动脚本，不改 Framework 逻辑（用户未选）。

## 4. 讨论与修订依据

- **本方案第一版**：保留 suite 快照注入，只做审查员入册、模板同步与 Extension 登记。用户补充目标「去掉测试装置对dsh的临时支持，后续demo仓可以直接升级extension并完成cli测试」后，选定「dsh 启动配置固定带上」，第一版的快照保留被替代，新增 S2。原话与澄清经过见[需求 §4](../../../spec/1.9.9/2026-10-28-dsh正式支持/00-需求.md#4-讨论与修订依据)。
- **本方案第二版（2026-10-28）**：仓库里第一次提交的版本（`89d4dce3`）在中央新增 `maison-build` 档位，把 `--patch {cwd}/.dsh/framework-verifier.patch.yml` 写死在中央。用户指出（原话）：「关于中央cli的maison-build档位我有点困惑，中央仓dsh应该支持--patch功能，patch file本身由项目的cli测试装置持有」「中央仓提供能力，具体参与由业务仓的cli指定」。据此把 S2 改为中央声明 `patch` 选项、本仓测试配置指定路径；`maison-build` 档位被替代。路径取 Case 工作区里 demo 带来的物化件，而不是根目录的维护拷贝，因为这样测的是 demo 正式交付的那份。两者逐字节相同由 S1 的测试保证，用户如果更想由测试装置自带一份，只需改 `test.yaml` 的值。
- 「不改framework」按用户确认取“不改上游、demo 的 dsh 定制可改”，与 10-20 的[中央 runtime 与 dsh 审查员交回](../2026-10-20-dsh实跑回流与补充完善/实施反馈/2026-10-20-中央runtime与dsh审查员-实施交回.md)口径相同。
