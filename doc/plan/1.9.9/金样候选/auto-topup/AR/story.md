# AR90006 交通卡自动充值（钱包端）

## 1. 背景

交通卡余额用尽，用户往往在闸机前才发现，只能在人流中当场充值，这是交通卡用户最集中的投诉点。难点不在充值本身，而在时机：余额还有富余时，用户没有理由想起这件事。

本需求让用户对一张交通卡签约一次，之后余额低于自己设的门限时由系统自动充值，把「想起来充值」从用户身上移走。

成功标准来自产品需求，由服务端按全局口径统计：

- 签约用户的闸机余额不足发生率降到万分之五以下；
- 签约转化率不低于交通卡月活的 8%。

钱包端以入口露出和签约流程的顺畅支撑这两个目标，不直接承诺这两个线上数值。

整套方案分签约、触发、扣款、入账、停用五段，钱包端只承担用户看得见的那部分：

- 交通卡详情页上的自动充值入口；
- 签约：选触发门限与单笔面额、同意免密扣款协议、过一次免密验证；
- 签约后在同一入口查看充值记录、修改门限面额、关闭自动充值。

余额判定、扣款、入账与停用都在服务端完成，用户侧没有「发起自动充值」的动作。

## 2. 术语

| 术语 | 在本需求里的意思 |
|---|---|
| 自动充值 | 交通卡详情页上的一项功能：用户签约后，余额低于门限时由系统自动完成充值 |
| 签约 | 用户选好触发门限、单笔面额并同意免密扣款协议，通过一次免密验证后，由交通卡云建立的自动充值关系 |
| 触发门限 | 余额低于多少（5 / 10 / 20 / 30 元）时触发一次自动充值，签约时单选，之后可修改 |
| 单笔面额 | 每次自动充值充多少（20 / 50 / 100 元），签约时单选，之后可修改 |
| 免密扣款协议 | 用户授权系统在满足条件时自动扣款的协议；协议文案写明单笔上限与单日上限，协议号由支付部件返回 |
| 管理页 | 开启自动充值后，同一入口对应的页面：查看签约状态、充值记录、修改门限面额、关闭或处理停用 |
| 停用 | 扣款连续失败 3 次后，签约被服务端停用，管理页展示停用状态与原因，需重新签约才能恢复 |
| 签约状态未知 | 这次没有取到这张卡在云侧的签约状态；页面只显示未知或本地旧值，可以重新查询 |
| 恢复确认 | 签约、重新签约、改档或关闭之前，钱包端向对端确认这张卡有没有还没结束的操作、有没有授权后没建成的那次签约；本期由模拟数据提供 |

容易读混的几组说法：

| 说法 | 怎么分 |
|---|---|
| 触发门限 与 单笔面额 | 门限是余额低到多少就触发，面额是触发后充多少；方向相反，互不换算 |
| 授权 与 签约 | 免密验证通过只说明支付侧形成了授权；交通卡云用协议号建立签约关系后，才算签约成功 |
| 停用 与 关闭 | 停用由服务端在扣款连续失败 3 次后做出，用户只能重新签约；关闭是用户主动解约，之后想用要重新签约 |
| 单笔上限 与 单日上限 | 单笔上限随所选面额设置；单日上限本期 200 元，达到后当日不再触发 |
| 「看不到入口」与「可见并引导实名」 | 按澄清会，未实名用户的入口可见、点进去先实名；产品需求原验收句「看不到入口」是旧版遗留，不采用（D2） |
| 状态未知 与 未签约 | 未签约是云侧明确返回没有签约；本地没有副本、查询又失败时只是不知道，不能当成未签约去签约 |
| 签约关系的状态 与 操作是否已结束 | 未签约、生效、停用说的是现在的关系；一次签约、改档或关闭有没有结束是另一件事，关系已经是目标值，原请求也可能还没结束 |
| 本地没有记录 与 没有未结束的操作 | 退出登录或清除数据只清钱包端的记录；对端已受理的操作和已形成的授权还在，可能稍后生效，要以恢复确认为准 |

## 3. 范围

整套自动充值由五方共同完成，钱包端是本次交付：

| 参与方 | 在这项业务里负责什么 | 本期怎么承载 |
|---|---|---|
| 钱包端（本次交付） | 详情页自动充值入口、签约页（门限与面额选择、协议、拉起免密验证）、实名引导回跳、签约选择暂存、管理页（状态、记录、改档、关闭、停用重签），以及写操作前向对端取恢复确认 | 本需求交付。工程里还没有交通卡详情页，本需求新增一个来承载入口，从哪里进入由实现方案定 |
| 交通卡云 | 余额上报、门限判定、充值订单与写卡、连续失败停用；签约关系、门限面额与充值订单的唯一真源；保留已受理操作的终态，回答恢复确认 | 五个接口按定好的契约用模拟数据承载（D7）；更新接口的响应、请求终态、失败记录原因与「解约返回未解约」的含义由模拟数据源声明；恢复确认是本轮维护设计给模拟对端补的能力，随本稿待审定 |
| 支付部件 | 免密协议签订与协议号、单笔额度校验、免密验证界面与自动扣款；成功授权的事实供恢复确认使用 | 既有能力，只用不改；本期模拟拉起与返回结果（D7） |
| 账号能力 | 实名结果，以及卡云接口要用的账号标识 | 模拟数据源提供（D7），不从脱敏展示账号反推 |
| 运营管理台 | 下发自动充值功能开关、门限与面额档位 | 模拟配置，档位取现行值（D7）；配置页面与逻辑不在钱包端 |

钱包端在这份需求里不做：

- 不判断余额是否低于门限，不发起任何自动充值；
- 不保存支付凭据，免密协议号只透传；
- 不实现运营管理台的页面与配置逻辑；
- 不改变余额的判定口径：判定输入是服务端记录的余额，不是用户手机上显示的余额。

本期不做：

- 按日期或按行程预约充值、一张签约覆盖多张卡、家庭成员代充：都需要新的账户模型；
- 充值记录按月筛选：会上没定挂在哪张单，会后需求方确认不算这张单；导出本期不做（D6）；
- 交通卡余额提醒：另立需求单，与自动充值不共用门限档位。

范围确认时需求方定为整单承载、不拆分。

工程里还没有任何自动充值的实现，交通卡云与支付部件的接口在工程里接不上，账号能力也只给出登录态。本期交付是按定好的接口、用模拟数据验证过的钱包端签约与管理交互，验收不等真实云端；与卡云、支付的真实联调另行验收，本需求不算验过（D7）。各项能力正式向用户开放的条件见第 9 章。

## 4. 业务方案

签约关系、余额门限与充值订单的唯一真源是交通卡云。判定与扣款都在服务端：卡云按服务端记录的余额判断是否低于门限，生成订单，经支付部件按协议免密扣款，再写卡。钱包端负责让用户建立和管理这份关系，并如实展示卡云给出的结果。

签约是先授权、后建约的两步。卡云先判定这张卡可以签约，钱包端再拉起支付部件的免密验证；验证通过后支付返回协议号，钱包端带着它请卡云建立签约关系，协议号只透传、不保存。授权形成了不等于签约建成：卡云没有建成时不留半签约状态，这次授权之后怎样再次开启待 D4。

签约之后改门限或面额走更新接口，原关系不断。关闭是解约，之后想用要重新签约；扣款连续失败 3 次由卡云停用，停用后重新签约是一次新签约。

退出登录、换号或清除应用数据会清掉钱包端的记录，对端已受理的操作和已形成的授权却还在，可能稍后生效。所以每次写入之前，钱包端先向对端确认这张卡有没有未结束的操作、有没有授权后没建成的那次签约，再决定能不能写（规则见 7.2）。

几个关键取舍：

| 取舍 | 结论 | 没选的做法为什么不行 |
|---|---|---|
| 谁判定余额、发起扣款 | 卡云按服务端记录的余额判定并扣款，钱包端不参与 | 端侧监测余额直接扣款：用户离线刷卡后手机上显示的余额会长期不准，按它判定会扣出用户预期之外的钱 |
| 改门限或面额怎么改 | 走更新接口，原签约关系不断（D1） | 先解约再重签：中间有空窗，那几分钟余额掉下去不会充，还要再拉一次免密验证 |
| 入口怎么分流 | 先看这张卡在云侧的签约状态；未签约时再逐项看功能开关、支付能力、恢复确认、实名结果和卡云的可签约判断（D2、D5） | 把开关或实名折进可签约性：未实名（应可见并引导实名）与开关关闭（应隐藏入口）分不开；只看本地副本：副本缺失会被当成未签约，把已签约用户送去重复签约 |
| 不可签约怎么提示 | 按卡云的「能否签约」判断分流，原因文字只拿来显示，为空时给通用提示 | 按原因文字猜是不是未实名：文字没有分类编码，猜错会把用户引到错误的页面 |
| 档位从哪来 | 取策略接口返回的档位，运营调整即时生效 | 写死在端侧：签约页档位与运营下发不一致，运营想调调不动 |
| 同一张卡重复签约 | 卡云按「卡片 + 生效状态」判重，返回既有签约号，端侧转管理页 | 端侧自己判重：签约关系的真源在卡云，端侧判不全 |
| 改档、关闭结果不明时怎么解锁 | 只有拿到明确成功、明确拒绝，或对端确认原操作已终结才解除；查到目标状态只更新展示 | 查几次还是旧值就当失败放开：原请求可能稍后才生效，放开后用户再改会互相覆盖 |
| 退出登录或清除数据后能不能直接写 | 先向对端取恢复确认，没有未结束的操作、也没有授权后未建成才放开 | 本地没记录就放开：已发出的旧请求可能晚到，用户再签或再改会多出一份签约或互相覆盖；为此保留该清的个人数据：违背退出即清 |

改档的验证要求：

- 只改门限不涉及免密额度，不需要重新验证（澄清会已定），即时生效；
- 改面额（调高或调低）要不要重新免密验证，待支付侧与风控确认（D3），未定前改面额不开放。

签约与扣款按这几条规则取值：

| 规则项 | 取值 | 适用与来源 |
|---|---|---|
| 触发门限档位 | 5 / 10 / 20 / 30 元 | 策略接口返回的现行值，运营可调 |
| 单笔面额档位 | 20 / 50 / 100 元 | 策略接口返回的现行值，运营可调 |
| 免密单笔上限 | 等于所选面额 | 不设固定值：选 20 元面额却签出 100 元的免密额度说不过去，用户会质疑扣款 |
| 单日充值上限 | 200 元 | 产品需求；澄清会确认本期不动，协议文案写明 |
| 连续扣款失败停用 | 3 次 | 产品需求；单日达到上限不计入 |
| 单日达到上限 | 当日不再触发，次日零点恢复 | 产品需求与系统设计 |
| 跨上限的一笔 | 由卡云定 | 已充 180 元、面额 50 元这种情况材料没有说明；钱包端只展示卡云的结果，不拆额、不改面额 |

改面额是否要重新免密验证（D3）、授权后创建签约没有建成时怎样再次开启（D4）尚未对齐，依赖它们的行为只写两边都成立的共同要求，这两处在结论前不开放（见 7.3）。

## 5. 业务流程

用户在交通卡详情页的同一个自动充值入口签约一次（5.1）；之后每当余额低于门限，卡云自动完成充值，用户不做任何操作（5.2）；用户回到同一入口查看记录、修改门限面额或关闭，停用后在这里重新签约（5.3）。签约、重新签约、改档、关闭这几次写入之前，都先经过 7.2 的恢复确认。

### 5.1 签约与授权

签约时用户、钱包端、支付部件和交通卡云按下面的先后交接，必须先取得支付授权，卡云才建立签约：

- 授权之后没有建成，不留半签约状态；再次开启是复用协议号还是重新验证等 D4，结论前这一步不开放。这次未建成按账号加卡片记下来：离开签约页、从入口重进，甚至关掉应用再打开，进入这张卡时仍是「上次授权后没有开通、再次开启待定」，不会换一条路进来就重新拉起免密验证。
- 卡云按「卡片 + 生效状态」判重，已有生效签约时返回既有签约号，钱包端转管理页，不建第二份签约。

前置检查的完整组合如下，入口和点进去的去向都由它决定：

| 云侧签约状态 | 开关与支付能力 | 恢复确认 | 实名与卡云的可签约判断 | 入口 | 点进去 |
|---|---|---|---|---|---|
| 生效或停用 | 不看 | —— | —— | 始终可见 | 管理页；在那里写操作前再取恢复确认（5.3） |
| 状态未知 | —— | —— | —— | 可见，显示未知或本地旧值（标明未确认） | 只能重新查询；查清前不进签约页，也不开放管理操作 |
| 未签约 | 开关关、读不到，或支付能力不可用 | —— | —— | 不可见 | —— |
| 未签约 | 开关开、支付可用 | 有未结束的操作：签约、改档或关闭任一种 | —— | 可见 | 留在详情页，按那项操作显示开通、修改或关闭确认中，只能再次查询 |
| 未签约 | 同上 | 授权后未建成 | —— | 可见 | 说明上次没有开通、选择保留；再次开启待 D4，不拉起验证 |
| 未签约 | 同上 | 取不到恢复信息 | —— | 可见 | 留在详情页，提示重查 |
| 未签约 | 同上 | 允许继续 | 未实名或读不到 | 可见 | 引导实名，完成后再取一次可签约判断 |
| 未签约 | 同上 | 允许继续 | 已实名，卡云判定可签约 | 可见 | 签约页，按暂存回填此前的选择 |
| 未签约 | 同上 | 允许继续 | 已实名，卡云判定不可签约 | 可见 | 留在详情页显示原因，原因为空时显示「这张卡暂不能开通自动充值」 |
| 未签约 | 同上 | 允许继续 | 取可签约判断时查询失败 | 可见 | 留在详情页，提示稍后重试 |

- 「允许继续」指恢复确认明确返回没有未结束的操作，也没有待处理的授权。任一种未结束的操作都会挡住这次签约，包括关闭已让关系回到未签约、解约请求本身还没结束的情形；页面按返回的那项操作显示，不按云侧当前是未签约去推断。
- 停用后重新签约走的也是这条签约路径，要重新满足开关、支付能力、恢复确认、实名和可签约判断。授权后没建成同样记下来；这时云侧仍是原来的停用关系，它证明不了这次授权已经建成，不能当作解除的依据。
- 退出登录或清除应用数据会清掉本地的未建成记录，但支付那边的授权还在；再次点进来时由恢复确认把它找回来，仍按未建成显示。只有对端确认这次授权已经对应到建立的签约关系，这条记录才清除。
- 中途退出签约页、去实名、验证取消或没通过时，已选的门限与面额按账号加卡片暂存，下次进来回填；换一张卡不会带出这张卡的选择，退出登录清除（D2）。

### 5.2 签约后的自动充值

签约之后的每一次充值都在服务端发生，用户不做任何操作。一笔充值发不发生、钱从哪扣、卡怎样写入，按下面的责任分工依次决定，钱包端在最后展示结果：

<!-- story-figure:fig-55cee031:begin -->
```mermaid
%% 图源 spec §5.4 #1
flowchart TD
  A[卡云：收到卡片余额上报] --> B{卡云：低于门限？}
  B -->|否| Z[不触发]
  B -->|是| L{卡云：当日已达单日上限？}
  L -->|是| Z2[当日不再触发，次日零点恢复；不计入连续失败]
  L -->|否| O[卡云：创建充值订单]
  O --> P{支付部件：按协议免密扣款}
  P -->|成功| W{卡云：写卡}
  W -->|完成| OK[充值成功]
  W -->|未完成| ING[订单保持充值中，下次读卡补写]
  P -->|失败| F{卡云：连续失败满 3 次？}
  F -->|否| FR[本笔失败，记录带原因]
  F -->|是| DS[卡云停用签约]
  OK --> SH[钱包端：管理页展示记录与签约状态]
  ING --> SH
  FR --> SH
  DS --> SH
```
<!-- story-figure:fig-55cee031:end -->

- 触发真源是卡云记录的余额，不是手机上显示的余额；门限与面额按用户签约时选的档位。
- 单日达到上限是正常受限，不计入连续失败，也不算扣款失败；当日已充额度加本笔面额超过上限时怎样处理由卡云定，钱包端只展示结果。
- 写卡未完成时订单保持充值中，由卡云下次读卡补写；端侧不提供重试，也不重复下单。
- 连续失败满 3 次后签约停用，管理页顶部换成停用横幅和原因，用户可以从那里重新签约（5.3）。

### 5.3 查看与管理

签约关系只有三个云侧状态，停用由卡云做出，其余迁移由用户触发；用户在每个状态下能做的事不同：

<!-- story-figure:fig-22c28d5a:begin -->
```mermaid
%% 图源 SR §1 #2
%% 图源 spec §5.2 #1
stateDiagram-v2
  [*] --> 未签约
  未签约 --> 生效: 签约建立
  生效 --> 未签约: 用户关闭，卡云解约
  生效 --> 停用: 扣款连续失败 3 次
  停用 --> 生效: 重新签约建立
  note right of 生效: 改门限或面额在生效态内更新，关系不断
  note right of 停用: 可查看停用原因与记录
```
<!-- story-figure:fig-22c28d5a:end -->

每个云侧状态下能看什么、能做什么，操作前还要满足什么，结果去哪：

| 云侧状态 | 可以查看 | 可以做的操作 | 操作前还要满足 | 结果去向 |
|---|---|---|---|---|
| 生效 | 当前门限与面额、最近记录 | 改门限 | 云侧状态已确认，没有确认中的操作，恢复确认允许继续（7.2） | 卡云更新签约，不需要重新验证，新门限即时生效；明确拒绝时保持原状态并说明这次没有生效；没有明确回应显示修改确认中（7.2） |
| 生效 | 同上 | 改面额 | 同上，另待 D3 | D3 有结论前不开放 |
| 生效 | 同上 | 关闭自动充值 | 同上，并经二次确认 | 卡云解约，关系回到未签约，不再触发；不回滚进行中的订单，也不撤销已完成订单；回包说「未解约」时按关闭没有生效提示；没有明确回应显示关闭确认中（7.2） |
| 停用 | 停用原因与最近记录 | 重新签约 | 恢复确认允许继续，且开关、支付能力、实名与卡云的可签约判断都满足 | 走 5.1 签约；条件不满足时说明暂不能重新签约；上次重签授权后未建成时说明没有开通、停在 D4 边界，原有停用关系不解除这项限制 |
| 未签约 | —— | 签约 | 见 5.1 的前置组合 | 走 5.1 签约 |

- 云侧查询失败时不是第四种状态，只是这次不知道：有副本就显示副本旧值并标明「未能确认最新状态」，没有副本显示未知；两种情况都可以重新查询，改档、关闭、重新签约暂不可用，也不把缓存缺失当成未签约。
- 还没结束的操作同样不是第四种状态，它和关系状态并存，限制的是这张卡现在能不能写。任一种未结束的签约、改档或关闭都会挡住写入：停用后重新签约的创建还在处理时，关系仍是停用，管理页按恢复确认显示重新签约确认中，不能再次重签。怎样确认与解除见 7.2。
- 签约号、门限、面额、状态、确认中的操作与授权后未建成的记录，在端侧按账号加卡片存一份副本，用于先行展示、离线展示和恢复确认中。进入管理页先显示副本，同时向云侧确认一次，同一次页面内复用确认结果；服务端停用与新增的记录以这次确认为准。
- D5 只定了开关不影响已签约用户的入口与管理，没说停用用户在开关关闭时能否重新签约；这里按新签约处理，随评审确认。

## 6. 功能说明

钱包端在自动充值里提供六项能力：详情页入口、签约页、免密验证拉起、实名引导、签约选择暂存与管理页。

### 6.1 交通卡详情页入口

交通卡详情页在余额行之下、充值记录之上展示一整行「自动充值」入口，行内写着这张卡的状态：未开启、已开启及当前门限面额、已停用，或状态未知（有本地旧值时标明未确认）：

![图 1 · 交通卡详情页上的自动充值入口（整行入口，位于余额行之下、充值记录之上）](../ux-reference/detail-entry.png)

- 入口是否可见、点进去去哪，按 5.1 的前置组合；已签约（含停用）的卡不看开关，始终可见。
- 点进去时若有确认中的操作、上次授权后没有开通，或取不到恢复信息，留在详情页说明，不进签约页、不拉起验证。
- 卡云判定不可签约或开通条件取不到时，也留在详情页显示原因或「暂时无法开通，请稍后重试」。
- 入口防重入：连点只响应一次。

### 6.2 签约页

签约页让用户为这张卡建立自动充值关系：

- 触发门限单选：可选值来自策略接口返回的档位，现行值为 5 / 10 / 20 / 30 元；
- 单笔面额单选：可选值同样来自策略接口，现行值为 20 / 50 / 100 元；
- 协议勾选：协议文案写明单笔上限等于所选面额、单日最多充 200 元，勾选后「开启」按钮才可点击。

签约页一屏内完成选择与同意，视觉沿用钱包现有卡片页面样式，不新增控件类型：

![图 2 · 自动充值签约页：门限与面额均为单选，协议勾选后开启按钮才可点击](../ux-reference/signup-page.png)

- 点「开启」后处理中不重复提交；中途退出时已选值暂存，下次回填。
- 授权后没有建成时，页面说明「这次没有开通成功，已选的门限和面额已保留」，「开启」不可用，再次开启待 D4。
- 创建没有明确回应时显示「开通结果确认中」，不显示成功也不显示未签约。

### 6.3 免密验证拉起

点「开启」后拉起支付部件的免密验证，验证页说明单笔额度。

- 验证通过：返回协议号，钱包端带着它去创建签约；
- 用户取消或没通过：回到签约页，不建立任何签约关系，也不留下半签约状态；
- 验证页拉不起来：用户可以重试，已选门限面额保留；
- 验证通过后签约没有建成：回到签约页说明这次没有开通，选择保留；再次开启的方式等 D4。停用后重新签约时同样如此。

验证页由支付部件提供，说明这次授权的单笔额度：

![图 3 · 免密验证页：首次签约时说明单笔额度并请求用户确认](../ux-reference/verify-page.png)

### 6.4 实名引导

未实名用户的入口照常可见，点进去先完成实名认证；实名完成后再取一次卡云的可签约判断，可签约时回到签约页，此前选好的门限与面额都还在（D2）。实名没完成就返回，仍签不成，入口照旧可见。

### 6.5 签约选择暂存

用户中途退出签约页、去实名、验证取消或没通过时，已选的门限与面额暂存，下次从入口进来按暂存值回填。暂存按账号加卡片保存：同一账号的两张卡各存各的，换卡不会带出别的卡的选择；退出登录清除这个账号的全部暂存。它只覆盖「退出签约页后再进来」，应用关闭后不保留。授权之后没有建成的那一次不靠这份暂存，记在签约关系副本里，应用重启后也还在（5.1）。

### 6.6 管理页

开启自动充值后，入口点进去是管理页：顶部为当前签约状态，下方为最近的自动充值记录。

![图 4 · 自动充值管理页与记录列表：顶部为当前签约状态，下方为最近记录，失败记录展示失败原因](../ux-reference/manage-page.png)

管理页提供五件事，每件在什么状态下成立、结果去哪，按 5.3 的状态与操作表：

- 查看签约状态与门限面额；查询失败时显示副本旧值并标明未确认，可以重新查询；
- 查看最近记录：每条有时间、金额、结果；失败的记录展示失败原因，卡云没给原因时显示「原因暂不可用」，不拿停用原因代替；卡号取当前这张卡的卡号按现有规则脱敏，4 位及以下的卡号不展示，签约号不当卡号显示；
- 修改门限面额：走更新接口，原签约关系不断（D1）；改面额等 D3；
- 关闭自动充值：二次确认后解约，关闭后不再触发；
- 处理停用：扣款连续失败 3 次后签约被卡云停用，管理页顶部换成停用横幅并给出停用原因，用户可以从这里重新签约；上次重新签约授权后没建成时，横幅下说明这一点，重新签约暂不开放。

有还没结束的操作时，顶部按那项操作显示「修改确认中」「关闭确认中」「重新签约确认中」或「开通确认中」及目标值，可以再次查询，冲突的操作暂不可用；离开再进来仍从这项确认恢复。

停用时管理页顶部的样子：

![图 5 · 停用态：扣款连续失败停用后，管理页顶部换成停用横幅并给出失败原因](../ux-reference/disabled-state.png)

## 7. 异常与恢复

### 7.1 失败后的现场与责任

设计成的正常受限，用户都有去处：

| 场景 | 用户看到什么 | 接下来怎么走 | 责任人 |
|---|---|---|---|
| 免密验证取消或没通过 | 留在签约页，门限与面额仍在 | 可直接再试一次，不必重选 | 钱包端 |
| 未完成实名 | 提示先完成实名认证 | 引导去实名，回来后可签约时回签约页继续 | 钱包端、账号能力 |
| 卡云判定这张卡不可签约 | 详情页显示原因；没有原因时显示通用提示 | 不进签约页、不拉起验证 | 交通卡云判定、钱包端展示 |
| 同一张卡已有生效签约 | 不重复签约 | 直接进管理页，在那里改门限面额或关掉 | 交通卡云判重、钱包端分流 |
| 用户中途退出签约页 | —— | 下次从这张卡的入口进来，此前选的门限面额仍在 | 钱包端（签约选择暂存） |
| 单日达到充值上限 | 当日不再触发 | 次日零点恢复；不计入连续失败 | 交通卡云 |
| 扣款连续失败 3 次 | 管理页顶部停用横幅与停用原因 | 查看原因；开通条件满足时可重新签约 | 交通卡云停用、钱包端展示 |
| 扣款成功但写卡未完成 | 订单保持充值中 | 卡云下次读卡补写；端侧不重试、不重复下单 | 交通卡云 |
| 功能开关关闭 | 未签约用户看不到入口 | 已签约用户不受影响，照常自动充值；停用用户暂不能重新签约 | 运营管理台、钱包端 |

请求失败、结果不明或本地数据变化时，用户看到真实结果，不假装成功：

| 场景 | 用户看到什么 | 接下来怎么走 | 责任人 |
|---|---|---|---|
| 免密授权后创建签约明确失败 | 签约页说明这次没有开通，门限与面额仍在，不显示成功；离开后再进来仍是这个样子 | 不留半签约状态；按账号加卡片记下未建成，停用后重签同样记；再次开启等 D4 | 钱包端、交通卡云、支付部件 |
| 创建签约、改档或关闭没有明确回应 | 开通、重新签约、修改或关闭确认中，不显示成功也不显示失败 | 按 7.2 收口；离开再进来仍是确认中 | 钱包端、交通卡云 |
| 解约回包说未解约 | 关闭没有生效 | 保持原状态，可以稍后再试；具体原因要卡云说明 | 钱包端、交通卡云 |
| 云侧状态查询失败或回包无效 | 有副本时显示副本旧值并标明未确认；没有副本显示状态未知 | 可重新查询；不进签约页、不开放管理操作，不按本地缓存缺失推断未签约 | 钱包端 |
| 取开通条件时查询失败 | 留在详情页提示稍后重试 | 不进签约页 | 钱包端 |
| 失败记录没有原因 | 显示「原因暂不可用」 | 不用停用原因代替；卡云补齐原因字段后照实显示 | 钱包端、交通卡云 |
| 免密验证拉不起来 | 拉不起来验证页 | 用户可重试，已选门限面额保留 | 钱包端 |
| 写操作前取不到恢复信息 | 签约、重新签约、改档、关闭暂不可用，提示重查 | 不当作没有未结束的操作；查看照常，可以重查（7.2） | 钱包端、交通卡云、支付部件 |
| 清除应用数据，或本地副本缺失 | 签约关系以云侧查询为准恢复展示：生效、停用照云侧显示，云侧无签约才看开通条件，查询失败显示未知 | 可以重试；确认中的操作与授权后未建成在写操作前由恢复确认找回（7.2） | 钱包端 |
| 退出登录或换账号 | 这个账号所有卡片的副本与暂存清掉，换账号后读不到旧数据 | 清除只清钱包端，不撤销对端已受理的操作；旧账号的晚到回包不写进新账号的页面；同一账号再写入时按 7.2 | 钱包端 |

### 7.2 写操作前的共同恢复规则

钱包端的记录会随退出登录、换号和清除应用数据被清掉，对端已受理的操作和支付已形成的授权却不会跟着消失，本地没有记录证明不了旧请求不会再生效。所以首次签约点入、停用后重新签约、改档与关闭之前，钱包端先向对端取一次这张卡的恢复确认，同一次操作里复用结果。签约入口和管理页都按同一张表处理：

| 恢复结果 | 对端给出的事实 | 钱包端怎么做 | 什么时候解除 |
|---|---|---|---|
| 有未结束的操作 | 已受理的签约、改档或关闭还在处理，或判定不了终态；带操作对象、类型与目标 | 按返回的类型与目标显示开通、修改、重新签约或关闭确认中；只能查看与再次查询，不发冲突的新操作。不按云侧当前关系猜是哪种操作：关系是未签约也可能有未结束的关闭，关系是停用也可能有未结束的重新签约 | 拿到这次操作的明确结果，或恢复确认表明它已结束 |
| 授权后未建成 | 支付保留了成功授权，卡云这次授权的建约结果为未建成；原有停用关系不算建成 | 显示上次没有开通、选择保留；再次开启待 D4，不重新拉起验证 | 恢复确认表明这次授权已对应到建立的签约关系 |
| 没有未结束的操作与待处理授权 | 已受理的请求都已结束、晚到也不会生效，成功授权都已对应到签约关系，或从来没有这类操作 | 清掉本地对应的记录，按云侧状态与开通条件或管理规则正常继续 | —— |
| 取不到恢复信息 | 查询失败、缺字段，或结果对应不上当前账号与卡片 | 查看照常；签约、重新签约、改档、关闭都不开放，提示重查 | 重查取得前三种结果之一 |

钱包本地、交通卡云与支付部件各自持有哪些事实、清除只改了哪一份、关系为未签约或停用时为什么仍可能不能写，画在阅读图[事实持有与写入许可](figures/auto-topup-recovery-boundary.svg)里。

结果不明的操作这样收口：

- **创建签约没有明确回应**（超时，或回包缺签约号）：查询云侧签约状态。已生效按已开启展示；云侧无签约、或重新签约时仍是原来的停用关系，按授权后未建成处理（等 D4）；查询也失败就保持「结果待确认」，可以稍后再查。不当成没签成，也不重新验证。
- **改档或关闭没有明确回应**：页面显示确认中。查询能证明目标已经达到，却证明不了原请求已经终止：查到目标值时页面按目标值展示，解除确认中还要拿到明确结果，或恢复确认表明原操作已结束。连续查到原值、或查询失败，都保持确认中，不按查询次数或等待时长判失败，也不自动重发。用户可以离开，再进来仍从这项操作恢复；退出登录后由恢复确认找回。卡云补齐「原请求是否已终止」的查询之前，原值长期不变的情形没有安全的解锁方式，这是正式开放前要补的依赖（第 9 章）。

恢复确认本身的几条约束：

- 对端只在确认旧请求已经结束、或它晚到也会被拒绝时，才回答「没有未结束的操作」；请求已发出但还没到达，也算没结束。
- 模拟卡云受理创建、改档、解约时自己再核一遍，冲突就明确拒绝，钱包端随后重取恢复确认；页面之前查过一次绕不过这条限制。本次创建携带的协议号对应的正是这次要建约的授权，卡云照常受理；冲突只指别的未结束操作，或别的还没对应到签约关系的成功授权。
- 恢复确认按当前登录的账号取；旧账号的晚到回包不写进新账号的页面，也不把清掉的记录写回来。
- 在途的请求不二次提交；确认中、或恢复确认没放开之前，不能提交冲突的签约、改档或关闭。
- 这是本轮维护设计给模拟交付补的前提，随本稿待审定；真实卡云与支付还没有对应能力，正式开放前要补（第 9 章）。

### 7.3 未定的两条边界

这两件两端尚未对齐，候选选项在评审记录里等裁定。

**改面额是否要重新免密验证（D3）**

- 已定：只改门限不涉及额度，不用验证。
- 未定：面额与免密单笔额度绑定，调高会放大额度；调低会上只说「应该不用」，也要等风控确认，风控也可能要求调低同样验证。
- 影响：改面额在结论前不开放；改门限即时生效、关闭照常；验收只覆盖改门限路径与关闭路径。

**授权后创建签约没有建成时怎样再次开启（D4）**

- 已定：明确失败或确认云侧无签约时留在签约页、保留已选门限与面额、不留半签约状态；结果未知时以云侧签约状态为准，不把超时当成没签成。
- 未定：卡云说协议号十分钟内可复用；支付侧认为有效期可能随验证会话走、未必十分钟；能否复用要卡云和支付两边都成立，产品要求等两端对齐，不按十分钟写。
- 影响：结论前授权后的再次开启不开放，离开签约页、重进或应用重启后同样不开放，停用后重签也一样；退出登录或清除数据后由恢复确认找回这次未建成，同样不开放。验证取消或没通过后的重试照常。

两条边界解除前，受影响的行为都不能写成已定；解除后由本单评审回流更新。

- **签约尝试观测成功占比**：点「开启」的尝试里，本端在这次尝试中看到签约生效的占比，观察签约链路是否顺畅。它不是背景里的「签约转化率」（那一项按交通卡月活计，由服务端统计），也不是最终签约成功率。
- **管理操作观测成功占比**：确认改档与关闭的尝试里，本端在这次尝试中看到生效的占比。

## 9. 交付与上线

本期交付按定好的接口、用模拟数据验证过的钱包端交互与产物，验收不等真实云端（D7）。正式向用户开放按能力逐项判断：真实对端就绪、对应的待定事项有结论，那一项才开放；联调顺序是先签约（策略与创建），通过后状态查询、改门限与解约，最后运营下发档位并打开开关。

| 能力 | 本期怎么承载 | 正式开放还要什么 | 谁负责 | 缺了怎样 |
|---|---|---|---|---|
| 入口与开通条件 | 模拟的签约状态、开关、支付能力、实名结果与可签约判断（D7） | 卡云策略与状态接口联调；账号能力给出实名结果与账号标识；运营下发档位并打开开关 | 交通卡云、账号能力、运营管理台 | 开关关或读不到时未签约用户看不到入口；已签约用户照常管理 |
| 首次签约 | 模拟卡云、模拟支付与模拟恢复确认（D7） | 创建接口联调；支付免密能力可用；卡云与支付给出写操作前恢复确认的等价可核语义 | 交通卡云、支付部件 | 不开放新签约；支付能力不可用时隐藏新签约入口 |
| 停用后重新签约 | 同首次签约 | 同首次签约 | 同上 | 停用用户只能查看原因与记录 |
| 授权后未建成的再次开启 | 不开放 | D4 有结论：复用协议号还是重新验证 | 交通卡云、支付部件 | 一直显示「上次没有开通、再次开启待定」 |
| 状态查询与记录 | 模拟（D7） | 状态接口联调；失败记录的原因字段 | 交通卡云 | 失败记录显示「原因暂不可用」 |
| 改门限 | 模拟（D7） | 更新接口的成功与拒绝回包定稿；原请求是否已终止的查询或等价保证；恢复确认的等价语义 | 交通卡云 | 结果未知时没有安全的解锁方式，不能开放 |
| 改面额 | 不开放（D3） | D3 有结论，并满足改门限的全部前置 | 支付侧、风控、交通卡云 | 不开放 |
| 关闭自动充值 | 模拟（D7） | 解约接口联调；「解约返回未解约」的含义；原请求终态的查询或等价保证；恢复确认的等价语义 | 交通卡云 | 未解约只能按关闭没有生效提示；结果未知时同改门限 |
| 服务端自动充值 | 不在钱包端 | 卡云执行单日上限与跨上限一笔的规则 | 交通卡云 | 钱包端只展示卡云给出的结果，不拆额、不改面额 |

开关、能力不可用与回退时，进行中的业务这样处理：

- 功能开关关闭：未签约用户看不到入口，停用用户暂不能重新签约；已签约用户的入口、管理与自动充值照常（D5）。档位配置不可用按关闭处理。
- 支付能力不可用：隐藏新签约入口，已签约用户继续自动充值。
- 卡云接口异常：签约页、管理页走通用失败处理，服务端已签约的自动充值不受影响。
- 端侧版本回退：回退版本没有自动充值入口；云侧已有签约照常自动充值，不随端侧回退解除，再进入时以云侧查询为准。上线后如需回退，关闭功能开关即可让未签约用户不再看到入口。
- 用户关闭自动充值即解除签约，之后想用要重新签约；关闭不回滚进行中的订单，也不撤销已完成的订单。

### 10.3 埋点

<!-- story-build:begin 埋点 · 由spec 「宿主扩展治理项 › 埋点」生成，改它请改真源 · sha256:f0313008de9aad3a -->
本需求观察签约与管理两条流程在本端的结果，为失败定位与链路复盘提供口径。项目既有上报入口为公共能力模块导出的 Chart/VOC 上报封装（模板枚举当前仅 Wallet_COMMON），仓内目前无业务调用（建设差距）；本需求在既有封装之上新增流程级统计点，不另造上报通道，实现层的取值由 plan 落实。

统计边界：
- 一次尝试从用户点「开启」（签约）或确认改档、关闭（管理）开始；同一次尝试里的验证、创建与紧接着的状态确认都属于这一次，重新发起是新的一次。
- 每次尝试按本端实际观测到的结果结算一次：观测成功、明确拒绝或失败、验证取消、验证未通过、拉起异常、结果未知（当前确认链走完仍未知）、中断（用户退出当前操作）。结果未知单列，不叫失败；用户离开不能证明云侧没有执行。
- 进程被直接终止、没有结束事件的尝试不补造结果，不进已结算总数。
- 晚到的回调不重复结算。用户稍后再次查询得到的结果记为恢复观测，不改写前一次结算，也不算一次新的成功尝试。
- 进入签约页取档位、进入详情页或管理页取状态属于页面加载，失败只写定位记录、不进统计。
- 事件只带去标识账号、卡片类型、阶段与结果分类；上报失败不改变业务结果。

两项指标都是本端观测口径，不代表最终业务成功率，也不是全部用户点击的转化；背景里的签约转化率按交通卡月活计，由服务端统计。若以后要最终成功率，需要另行确认的对端关联机制，本需求不提供。

#### 10.3.2 管理操作观测成功占比

衡量用户在管理页确认的改档与关闭，本端在这次尝试里观测到生效的比例。怎么算：改档流程与关闭流程中结算为观测成功的尝试数 ÷ 两条流程已结算的尝试数；明确成功、结果未知后同一确认链查到目标状态，都算观测成功。每次结算随事件带操作类型（改门限 / 改面额 / 关闭）与结束分类（明确拒绝 / 结果未知 / 中断）；结果未知未解除时不能开始冲突的新操作，因而同一张卡不会同时有并行的管理尝试。
