# AR90006 交通卡自动充值（钱包端）

## 1. 背景

交通卡余额用尽，用户往往在闸机前才发现，只能在人流中当场充值，这是交通卡用户最集中的投诉点。难点不在充值本身，而在时机：余额还有富余时，用户没有理由想起这件事。

本需求让用户对一张交通卡签约一次，之后余额低于自己设的门限时由系统自动充值，把「想起来充值」从用户身上移走。

成功标准来自产品需求，由服务端按全局口径统计：

- 签约用户的闸机余额不足发生率降到万分之五以下；
- 签约转化率不低于交通卡月活的 8%。

钱包端以入口露出和签约流程的顺畅支撑这两个目标，不直接承诺这两个线上数值。

整套方案分签约、触发、扣款、入账、停用五段，钱包端只承担用户看得见的那部分：

- 交通卡详情页上的自动充值入口；
- 签约：选触发门限与单笔面额、同意免密扣款协议、过一次免密验证；
- 签约后在同一入口查看充值记录、修改门限面额、关闭自动充值。

余额判定、扣款、入账与停用都在服务端完成，用户侧没有「发起自动充值」的动作。

## 2. 术语

| 术语 | 在本需求里的意思 |
|---|---|
| 自动充值 | 交通卡详情页上的一项功能：用户签约后，余额低于门限时由系统自动完成充值 |
| 签约 | 用户在签约页选好触发门限、单笔面额并同意免密扣款协议，通过一次免密验证后建立的自动充值关系 |
| 触发门限 | 余额低于多少（5 / 10 / 20 / 30 元）时触发一次自动充值，签约时单选，之后可修改 |
| 单笔面额 | 每次自动充值充多少（20 / 50 / 100 元），签约时单选，之后可修改 |
| 免密扣款协议 | 用户授权系统在满足条件时自动扣款的协议；协议文案写明单笔上限与单日上限，协议号由支付部件返回 |
| 管理页 | 开启自动充值后，同一入口对应的页面：查看签约状态、充值记录、修改门限面额、关闭或处理停用 |
| 停用 | 扣款连续失败 3 次后，签约被服务端停用，管理页展示停用状态与原因，需重新签约才能恢复 |

容易读混的几组说法：

| 说法 | 怎么分 |
|---|---|
| 触发门限 与 单笔面额 | 门限是余额低到多少就触发，面额是触发后充多少；方向相反，互不换算 |
| 停用 与 关闭 | 停用由服务端在扣款连续失败 3 次后做出，用户只能重新签约；关闭是用户主动解约，之后想用要重新签约 |
| 单笔上限 与 单日上限 | 单笔上限随所选面额设置；单日上限本期 200 元，达到后当日不再触发 |
| 「看不到入口」与「可见并引导实名」 | 按澄清会，未实名用户的入口可见、点进去先实名；产品需求原验收句「看不到入口」是旧版遗留，不采用（D2） |

## 3. 范围

整套自动充值由五方共同完成：

| 参与方 | 做什么 | 在本需求里 |
|---|---|---|
| 钱包端（本次交付） | 详情页自动充值入口、签约页（门限/面额选择、协议、拉起免密验证）、管理页（状态、记录、改档、关闭、停用重签）、实名引导回跳、端侧暂存签约选择 | 本需求交付 |
| 交通卡云 | 余额上报、门限判定、自动扣款与入账、写卡；签约关系、门限面额与充值订单的唯一真源 | 接口对端，按定好的接口协作 |
| 支付部件 | 免密协议签订、协议号、单笔额度校验；拉起免密验证界面 | 既有能力，只用不改 |
| 账号能力 | 登录实名结果 | 既有能力，提供身份判定 |
| 运营管理台 | 下发自动充值功能开关、门限与面额档位 | 配置与本需求同版本上线；配置页面与逻辑不在钱包端 |

钱包端在这份需求里不做：

- 不判断余额是否低于门限，不发起任何自动充值；
- 不保存支付凭据，免密协议号只透传；
- 不实现运营管理台的页面与配置逻辑；
- 不改变余额的判定口径：判定输入是服务端记录的余额，不是用户手机上显示的余额。

本期不做：

- 按日期或按行程预约充值、一张签约覆盖多张卡、家庭成员代充：都需要新的账户模型；
- 充值记录按月筛选：会上没定挂在哪张单，会后需求方确认不算这张单；导出本期不做（D6）；
- 交通卡余额提醒：另立需求单，与自动充值不共用门限档位。

范围确认时需求方定为整单承载、不拆分。

工程里还没有任何自动充值的实现，也没有交通卡详情页；交通卡云与支付部件的接口在工程里接不上。本次按定好的接口用模拟数据验证钱包端的签约与管理交互；与卡云、支付的真实联调另行验收，本需求不算验过（D7）。

| 事 | 本期怎么承担 | 换成正式能力的条件 |
|---|---|---|
| 交通卡详情页 | 工程里没有，本需求新增一个交通卡详情页承载自动充值入口，从哪里进入由实现方案定 | —— |
| 交通卡云的五个接口 | 按定好的接口契约用模拟数据承载（D7） | 卡云接口就绪后换真实数据源，页面与状态语义不变 |
| 支付部件的免密验证 | 模拟拉起与返回结果（D7） | 支付部件能力在工程内可用 |
| 账号的实名结果 | 模拟实名结果（D7） | 账号能力暴露实名结果 |
| 运营下发的开关与档位 | 模拟配置，档位取现行值（D7） | 运营管理台配置随版本上线 |

依赖关系：

- 交通卡云是最外层依赖，签约、改档、关闭与状态展示都依赖它的接口；
- 支付部件能力不可用时，隐藏新签约入口，已签约用户照常自动充值。

## 4. 业务方案

签约关系、余额门限与充值订单的唯一真源是交通卡云，判定与扣款都在服务端；钱包端只负责签约入口、签约交互、状态展示与记录查看。

不采用「端侧监测余额并直接发起扣款」：用户离线刷卡后手机上显示的余额会长期不准，按它判定会扣出用户预期之外的钱。

钱包端调用交通卡云发起签约与查询，支付部件向用户拉起免密验证并返回协议号：

| 参与方 | 输入 | 输出 | 责任 | 失败时 |
|---|---|---|---|---|
| 钱包端 | 用户动作、卡片与云侧状态 | 签约请求、状态页与提示 | 收集确认、拉起签约、展示结果 | 不判断是否该扣款，不保存支付凭据 |
| 交通卡云 | 卡片、账号、余额上报、协议号 | 签约、触发、订单与扣款结果 | 门限判定、订单创建、失败停用 | 是签约与扣款结论的唯一真源 |
| 支付部件 | 协议号、订单和金额 | 签约与扣款结果 | 免密协议和扣款 | 不改变签约关系，不重复扣款 |
| 账号能力 | 登录实名请求 | 合格身份或失败结果 | 提供既有身份能力 | 未实名不允许签约 |
| 运营管理台 | 运营配置 | 开关、门限和面额档位 | 配置下发 | 配置不可用按关闭处理 |

几个关键取舍：

| 取舍 | 结论 | 没选的做法为什么不行 |
|---|---|---|
| 改门限或面额怎么改 | 走更新接口，原签约关系不断（D1） | 先解约再重签：中间有空窗，那几分钟余额掉下去不会充，还要再拉一次免密验证 |
| 入口可见性怎么判 | 按签约状态、功能开关与实名显式分四档（D2、D5） | 把开关折进可签约性：未实名（应可见并引导实名）与开关关闭（应隐藏入口）就分不开 |
| 档位从哪来 | 取策略接口返回的档位，运营调整即时生效 | 写死在端侧：运营想调调不动 |
| 同一张卡重复签约 | 卡云按「卡片 + 生效状态」判重，返回既有签约号，端侧转管理页 | 端侧自己判重：签约关系的真源在卡云，端侧判不全 |

改档的验证要求：

- 只改门限不涉及免密额度，不需要重新验证（澄清会已定），即时生效；
- 改面额（调高或调低）要不要重新免密验证，待支付侧与风控确认（D3），未定前不写死。

签约与扣款按这几条规则取值：

| 规则项 | 取值 | 适用与来源 |
|---|---|---|
| 触发门限档位 | 5 / 10 / 20 / 30 元 | 策略接口返回的现行值，运营可调 |
| 单笔面额档位 | 20 / 50 / 100 元 | 策略接口返回的现行值，运营可调 |
| 免密单笔上限 | 等于所选面额 | 不设固定值：选 20 元面额却签出 100 元的免密额度说不过去 |
| 单日充值上限 | 200 元 | 产品需求；澄清会确认本期不动，协议文案写明 |
| 连续扣款失败停用 | 3 次 | 产品需求；单日达到上限不计入 |
| 单日达到上限 | 当日不再触发，次日零点恢复 | 产品需求与系统设计 |

这套划分要防住五类风险：

| 风险 | 触发条件 | 影响 | 已有控制 |
|---|---|---|---|
| 判定扣错金额 | 按用户端显示余额判定 | 扣出用户预期之外的钱 | 判定输入是服务端记录余额，端侧不参与判定 |
| 免密额度与所选面额不符 | 面额与免密额度解绑 | 用户质疑扣款 | 单笔上限随所选面额设置 |
| 改档重建签约造成空窗 | 改档走解约重签 | 空窗期余额下降不自动充；重复拉验证 | 改档走更新接口，原关系不断 |
| 签约页档位与运营下发不一致 | 档位写死 | 运营想调调不动 | 档位取自策略接口 |
| 端云能力需本地承载 | 工程里没有自动充值实现，卡云与支付接口接不上 | 签约与管理链路没有真实数据源，验收只到本地模拟 | 按接口契约建模、数据源可替换，用模拟数据验证（D7）；真实联调另行验收 |

改面额是否要重新免密验证（D3）、授权后创建签约失败或结果未知时怎样再次尝试（D4）尚未对齐，依赖它们的行为只写两边都成立的共同要求。

## 5. 业务流程

钱包端参与两条路径，都从交通卡详情页的同一个自动充值入口进入：

- 签约路径：把这张卡的自动充值关系建立起来；
- 管理路径：建立之后的查看、修改、关闭与停用重签。

入口去向由入口可见性决定（D2、D5）：已签约的进管理页，未签约的再按功能开关与实名分流。签约之后的每一次充值在服务端完成，钱包端只展示结果。

### 5.1 签约路径

看这张图要看出：入口怎样分流，以及验证取消、明确失败、已有签约、结果未知各自回到哪里。

```mermaid
%% 图源 SR §1 #1
%% 图源 spec §5.1 #1
flowchart TD
  A[详情页入口] --> X{入口分流}
  X -->|已有生效签约| MG[管理页]
  X -->|未实名| RN[引导实名]
  RN -->|实名完成| B
  X -->|可签约| B[签约页选门限与面额]
  B --> C[免密验证]
  C -->|取消或未通过| B
  C -->|通过，返回协议号| D[卡云建签约关系]
  D -->|成功| E[详情页显示已开启]
  D -->|明确失败| B
  D -->|卡片已有生效签约| MG
  D -->|超时，结果未知| Q{查询云侧签约状态}
  Q -->|已生效| E
  Q -->|云侧无签约| B
  Q -->|查询也失败| U[提示结果待确认，可稍后再查]
```

- 回到签约页的几条分支，门限与面额都按暂存值保留，不必重选（D2）。
- 创建明确失败时不留半签约状态；再次尝试是复用协议号还是重新验证，等 D4 的结论。
- 超时的那一次，页面既不显示成功，也不当作没签成，以云侧签约状态为准。
- 中途退出签约页时，已选的门限与面额暂存，只在本账号本卡有效，退出登录清除。

看这张图要看出：只有免密验证通过拿到协议号才创建签约，协议号交给谁，以及超时后由谁确认结果。

```mermaid
sequenceDiagram
  actor U as 用户
  participant W as 钱包端
  participant P as 支付部件
  participant C as 交通卡云
  U->>W: 从入口进入签约
  W->>C: 取可签约性与门限面额档位
  C-->>W: 档位与单日上限，或不可签约的原因
  U->>W: 选门限与面额，同意协议，点开启
  W->>P: 拉起免密验证（单笔额度按所选面额）
  alt 验证通过
    P-->>W: 协议号
    W->>C: 创建签约（协议号只透传）
    alt 成功
      C-->>W: 签约号
    else 明确失败
      C-->>W: 失败原因
    else 超时
      W->>C: 查询签约状态
      C-->>W: 已生效、无签约，或查询失败
    end
  else 取消或未通过
    P-->>W: 没有协议号
    Note over W: 回签约页，已选门限面额保留，不创建签约
  end
```

- 协议号只透传给卡云，钱包端不保存。
- 实名结果来自账号能力（本期以模拟结果承载，D7）：未实名时钱包端引导实名，不拉起免密验证；策略接口的不可签约原因只用于提示，不作分流依据。
- 卡云按「卡片 + 生效状态」判重，已有生效签约时返回既有签约号，钱包端转管理页，不建第二份签约。

用户在签约路径上依次经过这几个页面：

| 页面 | 来路/入口 | 用户操作 | 正常结果 | 异常提示与去向 |
|---|---|---|---|---|
| 交通卡详情页 | 用户打开某张交通卡 | 点「自动充值」入口 | 未签约且可签约时进签约页；已签约时进管理页 | 未签约且开关关闭时不显示入口；未实名时进实名引导 |
| 实名引导 | 详情页入口（未实名） | 完成实名认证 | 回到签约页，此前选的门限面额回填 | 实名未完成就返回：仍签不成，入口照旧可见 |
| 签约页 | 详情页入口；实名回来；验证或创建失败回来 | 选门限与面额、勾选协议、点「开启」 | 拉起免密验证 | 协议没勾时「开启」不可点；中途退出暂存已选值，下次回填 |
| 免密验证页 | 签约页点「开启」 | 确认或取消 | 返回协议号，钱包端创建签约，成功后回详情页显示已开启 | 取消或没通过回签约页、选择保留；创建明确失败回签约页；超时显示结果确认中，查询失败提示结果待确认 |

### 5.2 管理路径

看这张图要看出：改档、关闭、停用重签都从管理页出发，以及改门限与改面额在验证要求上的区别。

```mermaid
%% 图源 SR §1 #2
%% 图源 spec §5.2 #1
flowchart TD
  M[管理页] --> N[改门限或面额]
  M --> O[关闭自动充值]
  M --> P[停用态查看失败原因]
  N -->|只改门限：不需验证| Q[卡云更新签约，原关系不断]
  N -->|改面额：是否重新验证待定 D3| Q
  O --> R[卡云解约，签约转为未签约]
  P --> S[重新签约，走签约路径]
```

- 改门限即时生效；改面额的交互在 D3 有结论前不写死（D1）。
- 解约不回滚正在进行中的订单，也不撤销已完成订单。
- 签约号、门限、面额和状态在端侧有副本，用于先行展示与离线展示：进入管理页先显示副本，同时向云侧确认一次，同一次页面内复用确认结果；服务端停用与新增的记录以这次确认为准。
- 云侧查询失败时：有副本就显示副本旧值并标明「未能确认最新状态」，旧值不当作当前生效；没有副本显示未知、可重试，不把缓存缺失当成未签约。
- 改档、关闭的请求响应丢失时页面显示确认中，向云侧确认：已到目标值或已解约按已生效；仍是原值或查询失败提示结果未确认，不判失败、不自动重发，确认后才可再次操作。

| 页面 | 来路/入口 | 用户操作 | 正常结果 | 异常提示与去向 |
|---|---|---|---|---|
| 管理页 | 详情页入口（已签约，含停用） | 查看状态与记录；改门限；关闭自动充值；停用时点重新签约 | 改门限按新值即时生效；关闭后入口回到未签约；重新签约进签约页 | 状态查询失败显示副本旧值并标明未确认，或显示未知、可重试；改面额的交互等 D3；改档或关闭明确失败留在管理页提示；响应丢失显示确认中，确认前不能再次操作 |


## 6. 功能说明

钱包端在自动充值里提供六项能力：详情页入口、签约、免密验证拉起、实名引导、端侧暂存与管理页。

### 6.1 交通卡详情页入口

交通卡详情页在余额行之下、充值记录之上展示一整行「自动充值」入口；是否可见、点进去去哪，由四档决定（D2、D5）。

入口在详情页上的位置如下：

![图 1 · 交通卡详情页上的自动充值入口（整行入口，位于余额行之下、充值记录之上）](../ux-reference/detail-entry.png)

| 用户状态 | 入口 | 点进去 |
|---|---|---|
| 未签约 + 开关开 + 可签约 | 可见 | 签约页 |
| 未签约 + 开关开 + 未实名 | 可见 | 引导实名 |
| 未签约 + 开关关 | 不可见 | —— |
| 已签约（含停用） | 始终可见 | 管理页 |

### 6.2 签约页

签约页让用户为这张卡建立自动充值关系：

- 触发门限单选：可选值来自策略接口返回的档位，现行值为 5 / 10 / 20 / 30 元；
- 单笔面额单选：可选值同样来自策略接口，现行值为 20 / 50 / 100 元；
- 协议勾选：协议文案写明单笔上限等于所选面额、单日最多充 200 元，勾选后「开启」按钮才可点击。

签约页一屏内完成选择与同意，视觉沿用钱包现有卡片页面样式，不新增控件类型：

![图 2 · 自动充值签约页：门限与面额均为单选，协议勾选后开启按钮才可点击](../ux-reference/signup-page.png)

### 6.3 免密验证拉起

点「开启」后拉起支付部件的免密验证，验证页说明单笔额度。

- 验证通过：返回协议号，钱包端带着它去创建签约；
- 用户取消或没通过：留在签约页，不建立任何签约关系，也不留下半签约状态。

验证页由支付部件提供，说明这次授权的单笔额度：

![图 3 · 免密验证页：首次签约时说明单笔额度并请求用户确认](../ux-reference/verify-page.png)

### 6.4 实名引导

未实名用户的入口照常可见，点进去先完成实名认证；实名完成后回到签约页，此前选好的门限与面额都还在（D2）。

### 6.5 端侧暂存

用户中途退出签约页、去实名、验证取消或没通过时，已选的门限与面额暂存，下次从入口进来按暂存值回填。暂存只在本账号本卡有效，退出登录即清除；它只覆盖「退出签约页后再进来」，应用关闭后不保留。

### 6.6 管理页

开启自动充值后，入口点进去是管理页：顶部为当前签约状态，下方为最近的自动充值记录。

![图 4 · 自动充值管理页与记录列表：顶部为当前签约状态，下方为最近记录，失败记录展示失败原因](../ux-reference/manage-page.png)

管理页提供五件事：

- 查看签约状态与门限面额；
- 查看最近记录：失败的记录展示失败原因，记录中的卡号按现有规则脱敏；
- 修改门限面额：走更新接口，原签约关系不断（D1）；
- 关闭自动充值：二次确认后解约，关闭后不再触发；
- 处理停用：扣款连续失败 3 次后签约被卡云停用，管理页顶部换成停用横幅并给出失败原因，用户可以从这里重新签约。

停用时管理页顶部的样子：

![图 5 · 停用态：扣款连续失败停用后，管理页顶部换成停用横幅并给出失败原因](../ux-reference/disabled-state.png)

每个操作只在对应的签约状态下成立：

| 操作 | 成立条件 | 结果 |
|---|---|---|
| 修改门限 | 签约生效中 | 卡云更新签约关系，不需要重新验证，新门限即时生效 |
| 修改面额 | 签约生效中 | 是否要重新免密验证待支付侧与风控确认（D3），结论前不写死改面额的交互 |
| 关闭自动充值 | 签约生效中 | 卡云解约，不再触发自动充值 |
| 查看失败原因 | 签约被停用 | 展示停用原因，并提供重新签约 |
| 重新签约 | 签约被停用 | 重新走一遍签约流程 |

## 7. 异常与恢复

异常分两类：设计内的正常受限结果，和没被设计接住的真正异常。

### 7.1 正常受限结果

这些场景在设计里各有去处，用户不会停在没有出路的页面上：

| 场景 | 用户看到什么 | 接下来怎么走 | 责任人 |
|---|---|---|---|
| 免密验证取消或没通过 | 留在签约页，门限与面额仍在 | 可直接再试一次，不必重选 | 钱包端 |
| 未完成实名 | 提示先完成实名认证 | 引导去实名，回来后回签约页继续 | 钱包端、账号能力 |
| 同一张卡已有生效签约 | 不重复签约 | 直接进管理页，在那里改门限面额或关掉 | 交通卡云判重、钱包端分流 |
| 用户中途退出签约页 | —— | 下次从入口进来时，此前选的门限面额仍在 | 钱包端（端侧暂存） |
| 单日达到充值上限 | 当日不再触发 | 当日不再充，次日零点恢复；不计入连续失败 | 交通卡云 |
| 扣款连续失败 3 次 | 管理页顶部停用横幅与失败原因 | 查看原因后重新签约 | 交通卡云停用、钱包端展示 |
| 扣款成功但写卡未完成 | 订单保持充值中 | 卡云下次读卡补写；端侧不重试、不重复下单 | 交通卡云 |
| 功能开关关闭 | 未签约用户看不到入口 | 已签约用户不受影响，照常自动充值 | 运营管理台、钱包端 |

### 7.2 真正异常

真正异常指设计上没有具体兜底、走通用逻辑的场景，用户要看到失败结果，而不是假装成功：

| 场景 | 可观察结果 | 恢复方式 | 责任人 |
|---|---|---|---|
| 免密授权后创建签约明确失败 | 留在签约页，门限与面额仍在，不显示成功 | 不留半签约状态；再次尝试的方式（复用协议号或重新验证）等 D4 结论 | 钱包端、交通卡云、支付部件 |
| 创建签约超时、结果未知 | 不显示成功，也不显示未签约 | 查询云侧签约状态：已生效按已开启展示；云侧无签约按本次未建成处理、留在签约页；查询失败保持待确认、可稍后再查 | 钱包端、交通卡云 |
| 云侧状态查询失败 | 有副本时显示副本旧值并标明未确认；没有副本显示状态未知 | 可重试；旧值不当作当前生效，不按本地缓存缺失推断未签约 | 钱包端 |
| 改档或关闭结果未知 | 页面显示确认中，不显示成功也不显示失败 | 查询云侧签约状态：已到目标值或已解约按已生效；仍是原值或查询失败提示结果未确认，不自动重发，确认后才可再次操作；更新接口的响应字段与并发判重待卡云定稿 | 钱包端、交通卡云 |
| 免密验证拉不起来 | 拉不起来验证页 | 用户可重试，已选门限面额保留 | 钱包端 |

### 7.3 未定的两条边界

这两件两端尚未对齐，已定与待定分开写。

**改面额是否要重新免密验证（D3）**

- 已定：只改门限不涉及额度，不用验证。
- 未定：面额与免密单笔额度绑定，调高会放大额度；调低会上只说「应该不用」，也要等风控确认。
- 本期写法：改面额的交互不写死，只写两种结论都成立的共同要求（改门限即时生效、管理页保留现场）；验收只覆盖改门限路径与关闭路径。

**授权后创建签约失败或结果未知时怎样再次尝试（D4）**

- 已定：明确失败时留在签约页、保留已选门限与面额、不留半签约状态；结果未知时以云侧签约状态为准，不把超时当成没签成。
- 未定：卡云说协议号十分钟内可复用；支付侧认为有效期可能随验证会话走、未必十分钟；产品要求等两端对齐，不按十分钟写。
- 本期写法：复用协议号还是重新验证，等结论再写。

两条边界解除前，受影响的行为都不能写成已定；解除后由本单评审回流更新。

### 7.4 恢复路径

- **清除数据或缓存缺失**：签约关系以云侧查询为准恢复。生效、停用照云侧显示，云侧无签约才进签约引导，查询失败显示未知、可重试。
- **签约过程被打断**：退出签约页时暂存已选的门限与面额，下次从入口进来回填；去实名回来同样回填（D2）。
- **防重复**：在途的创建请求不二次提交；卡云对已有生效签约的卡返回既有签约号，重复进入最终都收敛到管理页。

## 8. 验收

通过条件按澄清会修订后的口径，主责是谁来验：

| 分组 | 编号 | 验收点 | 可观察的通过条件 | 主责 |
|---|---|---|---|---|
| 入口与实名 | AC-R1 | 未实名用户 | 能看到自动充值入口，点进去被引导去实名，完成实名前无法签约（按澄清会修订，原「看不到入口」作废，D2） | 端侧 + 测试 |
| 入口与实名 | AC-R8 | 实名后续办 | 未实名用户被引导去实名，完成后回到签约页继续，此前的选择仍在 | 端侧 + 测试 |
| 入口与实名 | AC-R9 | 已签约再进入 | 已有生效签约的卡再点入口，进入的是管理页而不是重新签约 | 端侧 + 测试 |
| 签约 | AC-R7 | 验证取消后重试 | 用户在支付验证界面取消，回到签约页时刚才选的门限与面额仍在，可直接再次开启 | 端侧 + 测试 |
| 签约 | AC-R10 | 创建签约结果未知 | 免密验证通过后创建签约超时：页面不显示成功也不显示未签约；云侧已生效时按已开启展示，云侧无签约时留在签约页且门限面额仍在，查询失败时提示结果待确认 | 端侧 + 交通卡云测试 |
| 自动充值与停用 | AC-R2 | 签约后自动充值 | 余额低于门限时用户不做任何操作即可完成充值，并能在记录里看到这笔 | 端侧 + 交通卡云测试 |
| 自动充值与停用 | AC-R3 | 连续失败停用 | 扣款连续失败 3 次后自动停用，用户打开管理页能看到停用状态与失败原因，并可从停用横幅重新签约 | 端侧 + 交通卡云测试 |
| 管理 | AC-R6 | 修改与关闭 | 签约后可修改门限并按新值生效；关闭后不再触发自动充值。改门限不需要重新验证；改面额是否要重新免密验证待 D3，结论前只验改门限路径与关闭路径 | 端侧 + 交通卡云测试 |
| 管理 | —— | 修改与关闭结果未知 | 改门限、关闭的响应丢失时页面显示确认中；云侧已到目标值或已解约按已生效，仍是原值或查询失败提示结果未确认、不自动重发（本单按系统设计「失败与恢复」补，Spec AC-8b） | 端侧 + 交通卡云测试 |
| 管理 | AC-R5 | 记录展示 | 充值记录中的卡号按现有规则脱敏展示，失败记录展示失败原因 | 端侧 + 测试 |
| 开关 | AC-R4 | 功能开关关闭 | 未签约用户看不到入口；已签约用户入口不隐藏、直达管理页，自动充值照常发生（按澄清会：开关只管新签约，D5） | 端侧 + 运营测试 |
| 本地数据 | AC-R11 | 本地缓存缺失 | 清除应用数据后进入：云侧生效时显示已开启并进管理页，云侧停用时显示停用与原因，云侧无签约时进入签约引导，云侧查询失败时显示状态未知且可重试 | 端侧 + 测试 |

AC-R10、AC-R11 是本单按系统设计「失败与恢复」补的两条，沿用上游编号顺延。交通卡云与支付部件的接口在工程里接不上，以上结论只到本地模拟（D7）；与卡云、支付的真实联调另行验收。

上线后观察两项流程指标，由本需求设定，不作为验收判据；都以一次流程尝试计，重新发起算新的一次：

- **签约成功率**：用户点「开启」后这张卡最终签上的比例，观察签约链路是否顺畅；它不是背景里的「签约转化率」，那一项按交通卡月活计，是服务端全局指标。
- **管理操作成功率**：改档与关闭最终生效的比例。

## 9. 交付与上线

上线按系统设计的交付口径推进：先联调策略查询与创建签约，再开放状态查询与解约，最后由运营开启功能开关。

看这张图要看出：哪些前置就绪后才能开放下一段，以及最后一步由谁打开。

```mermaid
flowchart LR
  I[卡云发布五个接口] --> A[联调策略查询与创建签约]
  PAY[支付部件免密能力可用] --> A
  A --> B[开放状态查询与解约]
  B --> S[运营开启功能开关，未签约用户可见入口]
```

- 前置：交通卡云发布策略、创建、状态、更新与解约五个接口，支付部件免密能力可用。
- 接口就绪前，钱包端按定好的接口用模拟数据验证（D7），不等联调。

能单独开关的对象，以及开关时进行中的业务怎样：

| 对象 | 启用 | 停用 | 进行中的业务受什么影响 |
|---|---|---|---|
| 自动充值功能开关 | 运营管理台开启后，未签约用户可见签约入口 | 运营管理台关闭后，未签约用户看不到入口；已签约用户一律不受影响 | 已签约用户的自动充值照常发生，管理入口也不隐藏（D5） |
| 策略接口返回的档位 | 运营下发门限与面额档位 | 配置不可用时按关闭处理 | 新签约入口隐藏 |
| 支付部件能力 | 能力可用时拉起免密验证 | 能力不可用时隐藏新签约入口 | 已签约用户继续自动充值，不受影响 |
| 创建签约、状态查询等接口 | 与交通卡云联调完成后开放 | 接口异常时签约页、管理页走通用失败处理 | 已签约用户的服务端自动充值不受影响 |
| 端侧版本回退 | —— | 回退版本没有自动充值入口 | 云侧已有签约照常自动充值，不随端侧回退解除；再进入时以云侧查询为准 |

关闭与回退：

- 用户关闭自动充值即解除签约，之后想用要重新签约；关闭不回滚进行中的订单，也不撤销已完成的订单。
- 上线后如需回退，关闭功能开关即可让未签约用户不再看到入口；已签约用户继续由服务端执行自动充值。

### 10.3 埋点

<!-- story-build:begin 埋点 · 由spec 「宿主扩展治理项 › 埋点」生成，改它请改真源 · sha256:7add98be53b3bbdb -->
本需求观察签约与管理两条流程的结果，为失败定位与链路复盘提供口径。项目既有上报入口为公共能力模块导出的 Chart/VOC 上报封装（模板枚举当前仅 Wallet_COMMON），仓内目前无业务调用（建设差距）；本需求在既有封装之上新增流程级统计点，不另造上报通道，实现层的取值由 plan 落实。统计边界：一次尝试从流程开始到结果确定，重新发起是新的一次；进入签约页取档位、进入管理页取状态属于页面加载，失败只写定位记录、不进统计；事件只带去标识账号、卡片类型、阶段与结果分类，上报失败不改变业务结果。

#### 10.3.1 签约成功率

衡量用户点「开启」后这张卡最终签上自动充值的比例，观察签约链路是否顺畅；它不是背景里的「签约转化率」（那一项按交通卡月活计，由服务端统计）。怎么算：签约流程以「生效」结束的尝试 ÷ 签约流程的全部尝试；超时后查询确认已生效、卡云返回已有生效签约，都算生效。随事件带未生效时的结束原因（用户取消验证 / 验证未通过 / 创建明确失败 / 结果仍未知）。

| 统计点 | 业务动作 | 实际适用结果 | 本端获知时机 | 已有覆盖或新增 |
|---|---|---|---|---|
| 签约流程 / 免密验证 | 拉起支付部件的免密验证 | 通过 / 用户取消 / 未通过 | 验证回调 | 新增 |
| 签约流程 / 创建签约 | 带协议号请卡云建立签约 | 成功 / 已有生效签约 / 明确失败 / 超时 | createAutoTopupContract 返回或超时 | 新增 |
| 签约流程 / 状态确认 | 创建超时后查询云侧签约状态 | 已生效 / 无签约 / 查询失败 | getAutoTopupStatus 返回 | 新增 |
| 签约流程 / 全流程 | 一次签约尝试结束 | 生效 / 未生效（带结束原因） | 最后一个走到的步骤得知结果时 | 新增 |

#### 10.3.2 管理操作成功率

衡量用户在管理页确认的改档与关闭最终生效的比例。怎么算：改档流程与关闭流程以「生效」结束的尝试 ÷ 两条流程的全部尝试；结果未知后经状态确认已生效的算生效；随事件带操作类型（改门限 / 改面额 / 关闭）与未生效原因（明确拒绝 / 结果仍未知），结果未知不记成失败。

|---|---|---|---|---|
| 改档流程 / 更新签约 | 确认修改门限或面额，卡云更新签约 | 生效 / 明确拒绝 / 结果未知 | updateAutoTopupContract 返回或超时 | 新增 |
| 关闭流程 / 解约 | 确认关闭，卡云解约 | 生效 / 明确拒绝 / 结果未知 | cancelAutoTopupContract 返回或超时 | 新增 |
| 改档流程、关闭流程 / 状态确认 | 结果未知后查询云侧签约状态 | 已到目标 / 仍为原状态 / 查询失败 | getAutoTopupStatus 返回 | 新增 |
| 改档流程、关闭流程 / 全流程 | 一次操作尝试结束 | 生效 / 未生效（带原因） | 最后一个走到的步骤得知结果时 | 新增 |
