# auto-topup 金样（初始情景）

- **情景终点**：从需求系统单 AR90006 起手，规格定稿送审（`case.yaml` 的 `end_phase: spec`）。不含 update 情景（用户 2026-10-12 裁定金样不考虑 update）。
- **目标产物**：`AR/story.md`、`AR/review.md`、`spec/spec.md`、`ux-reference/` 五张界面图。只放目标产物；`decisions.json`、`knowledge-use.yaml`、`materials.json`、流程契约等中间产物不入金样。
- **输入**：`test/cases/auto-topup`（P6 S1 承接后的版本，摘要见 `test/EVOLUTION.md` 1.9.9 条）：需求系统快照 RR90006 `prd.md`、SR90006 `design.md`（`d8a0e00c`）、AR90006 `design.md`；补料《交通卡自动充值.docx》（产品原稿 v0.4，只取图）与《交通卡澄清会记录-0903.docx》（会议版本 `23fdc64d`）。目标工程事实取本线 demo，知识判断取本轮开发源 `extensions/knowledge/`。
- **有效宿主立场**（取自 `interaction-script.yaml` 与答案卷）：补料一次交齐；整单承载不拆；会后确认按月筛选不属本单（D6）；端云能力先用模拟数据验证、真实联调另算（D7）。会议里已定的：更新接口（D1）、未实名入口可见并引导实名（D2）、开关只管新签约（D5）、单日上限本期 200 元；会议未定、保持待定的：改面额是否重新验证（D3）、授权后建约没有建成时怎样再次开启（D4，卡云与支付共同定）。
- **设计选择**：
  - 入口先按本账号这张卡的云侧签约状态（未签约 / 生效 / 停用 / 未知）分流；未签约时再按功能开关、支付能力、实名结果、策略 `signable` 四项独立的开通条件判断；`unsignableReason` 只作提示文字。
  - 停用后能管理，重新签约要重查开通条件。
  - 授权之后没有建成的，停在 D4 待定的边界上。
  - 签约关系副本与签约暂存按账号加卡片绑定。副本含未确认的改档或关闭，落盘保护交 Plan。
  - 管理操作结果未知时，只按明确结果或查到目标状态解除。
  - 最近记录的卡号取当前卡片；失败原因缺值显示「原因暂不可用」。回包字段区分必需、按状态可空、待卡云补充。
  - 统计用本端单次尝试观测口径：结果未知与中断另列，稍后重查只记恢复观测。
  - 本期是模拟交付，正式开放另列条件。

  换一种合理的命名、表格切法不算错。
- **本轮设计前提**（2026-10-16 维护设计，随具体稿待用户审定）：
  - 账号标识、实名结果、开关与档位由 WalletMain 的模拟数据源提供；
  - 模拟卡云声明失败记录原因字段、更新接口的成功 / 拒绝 / 未知三种结果，以及 `cancelled=false` 按关闭没有生效处理；
  - 真实字段与请求终态的查询由卡云定稿，列为正式开放前的依赖。

  以上不是已有人签，也不改写原始 RR / SR / AR 或人工答复。
- **保留的真实未决**：D3、D4；停用用户在开关关闭时能否重新签约，D5 没有明确覆盖，规格按新签约处理并随评审确认。
