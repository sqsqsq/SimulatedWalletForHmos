## 3. 必须修正的局部问题

### F01 / P2：统计汇总代码量仍在跨需求去重

依据：V5 §6、usage 纠正方案 §4/5，明确混合提交每需求计整笔，退出代码量跨需求去重。

实际：`extensions/skills/story-stats/scripts/stats.py:124` 建立 `seen`，134 行按 SHA 去重，158—159 行用它产生汇总新增/删除量；模板也要求显示去重行数。逐需求算法正确，但汇总又保留了被替代的口径。复用真实隔离 Git 用例，逐需求新增之和为 75，summary.added 为 60，见 E/probes.json 的 mixed_totals。不是算术错误，而是没有按已定口径退出旧能力。

要求：汇总代码量按已确认的逐需求归属汇总，保持各需求的混合提交标记；同步模板与测试。人员去重不受影响，不把此修正扩大为禁止所有去重，也不新建第二套可选统计口径。复验一笔混合提交加一笔单需求提交，逐需求与汇总数字可按同一口径复算。

### F02 / P2：update 轮数依赖可丢失的运行态

依据：V5 §4.2/5.2/8、I3@2。运行态丢失允许损失未结算起点，已关闭轮次仍是完成事实；rounds 回答真正收口了几轮。

实际：`extensions/skills/story/scripts/core/usage.py:335` 的 tally_update 只有在 starts 中还保存该 update id 时才累加 rounds。隔离复验：open 已采集 → 本地 `.usage-state.json` 丢失 → 同一 record 以 opened_at=08:00、closed_at=08:05 正常关闭 → refresh。结果是 `"story update": {}`，统计端将 rounds_total 算为 0，而不是已收口 1 轮。两端时刻和 closed 记录都仍在。见 E/probes.json。

要求：已关闭 update 的轮数不得随本地运行态丢失；复用原生 update 记录，不增加事件账本或持久终态游标。可核耗时按已有真源与 V5 结算，不能编造缺失起点，不能抹掉已有累计。复验运行态丢失、重复刷新、第二轮收口和撤回不计，确保分别可判断；不是要求给任意损坏状态增加通用修复器。

### F03 / P2：会议同名分支仍有大小写身份不一致

依据：R2/A2，无需人工改名；会议属于正常支持的材料类别。交回 §7 已披露此问题，本轮确认它确实影响后续使用。

实际：Windows 下 `inbox/a/Review.docx` 与 `inbox/b/review.docx` 内容不同，正常 import 返回 0。`materials/meeting.py:54` 的版本目录使用 stem，60 行枚举按磁盘目录名建键，254 行读判断又按 source 的原始大小写建键。盘上两版都在 Review 目录；第二份 source 仍是 review.docx，按 source.json 正常填写判断后报“对不上任何会议版本”。见 E/meeting-probe.json。正文、docx 图片和 UX 的新派生路径没有这个问题。

要求：只统一会议版本生产者与消费者的身份解析，保留版本原件、内容摘要及原话引用；不能恢复“请改名”或增加用户确认。复验这两份正常导入→按 source.json 写判断→版本匹配，以及原有同名不同内容/重导/历史引用保持。无需重做整个会议机制或导入平台。
