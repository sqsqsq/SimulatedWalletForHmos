## 1. P1：能力裁定的读取位置

### 先核事实：Framework 把这两份写在哪

复核要求改用 `phaseReportsDir`。动手前，我用 Framework 自己的路径函数在四种配置下取了这两份文件的实际位置，记录在 `framework-path-probe.json`。探针脚本是 `output/scratch/s1-fix/framework-path-probe.ts`，直接 import `capabilitySnapshotPath`、`fidelityIntentSsotPath` 与 `featurePhaseReportsDir`。

| 配置 | Framework 写能力快照/保真意图的位置 | 阶段报告目录（`phaseReportsDir`） |
|---|---|---|
| 默认 | `doc/features/N/spec/reports/` | `doc/features/N/spec/reports` |
| `reports_dir_pattern: evidence/<feature>/<phase>` | `doc/features/N/spec/reports/` | `evidence/N/spec` |
| `features_dir: specs/features` | `specs/features/N/spec/reports/` | `doc/features/N/spec/reports` |
| 两者都自定义 | `specs/features/N/spec/reports/` | `evidence/N/spec` |

依据源码：
- `fidelity-shared.ts`：`capabilitySnapshotPath`、`fidelityIntentSsotPath` 都是 `featureFilePath(projectRoot, feature, path.join('spec', 'reports', …))`；
- `config.ts`：`featureFilePath` 走 `<features_dir>/<feature>`；
- `fidelity-intent-init.ts` 头注释：产物是 `<feature>/spec/reports/capability-snapshot.json + fidelity-intent.json`。

这两份是 spec 所有的裁定件，不随 `reports_dir_pattern` 走。只要两项配置中任一项是自定义的，`phaseReportsDir` 就指向 Framework 从不写这两份的目录：
- 改用它的话，自定义报告目录的工程永远读不到当前裁定，被误拦；
- 自定义需求目录时，会去读默认目录下的件。

这正是复核担心的两种误读。

**复核探针为何得出相反结论**：`output/scratch/s1-review/path-probe.mjs` 把「当前裁定」写在 `evidence/<feature>/<phase>`（Framework 不写的位置），又把 Framework 的真实位置当作「旧默认残留」。在当前代码上重跑，仍得 false、true，但两个结果都是正确行为：自定义报告目录里那份不是 Framework 的裁定；默认位置那份才是 Framework 当前的裁定。

### 实际做的

01 §3.1 写的是「用 phaseReportsDir 定位」。按上面的事实，我没有照这一句改，而是把同源落实为「在 Framework 写的位置读」。**这一处与方案文字不一致，请设计者裁定并同步 01。**

| 新承担者 | 内容 |
|---|---|
| `review-inputs.mjs::visualDeferral` 头注释 | 写明读取位置跟随 Framework `capabilitySnapshotPath` / `fidelityIntentSsotPath`，即 `<features_dir>/<需求>/spec/reports/`，不随 `reports_dir_pattern` |
| `review-inputs.mjs::reviewInputs` 开头 | `framework.config.json` 在而读不出时报一条缺口：需求目录判不了，必审集合按默认目录推导，不能当作这个工程的；并且不再计算视觉延期。复核说的是「解析失败如实交付缺口，不能回退读默认旧件」。我把缺口放在整份集合上而不是只放在视觉裁定上，因为整份必审集合都依赖 `features_dir` |
| 任务与报告校验 | 原本就都消费同一个 `reviewInputs` 投影，没改 |

缺件、strict、判项未核、业务阻断等检查保持不变。

### 新增测试（`TheVisualRulingIsReadWhereFrameworkWritesIt`，5 条）

- 默认、自定义报告目录、报告目录为空串、为 null：裁定都在 Framework 位置被读到，延期集合正确。
- Framework 位置的裁定是「看得了图」，自定义报告目录里另有一份「看不了」：不延期。
- 自定义需求目录：默认目录下的裁定被忽略；`specs/features/...` 下的被读到。
- 坏 JSON 配置：报「framework.config.json 读不出」缺口，不延期。
- 静态锚：Framework 源码里这两份仍由 `featureFilePath(…'spec','reports',…)` 写；Framework 改了写入位置时这条先红。
