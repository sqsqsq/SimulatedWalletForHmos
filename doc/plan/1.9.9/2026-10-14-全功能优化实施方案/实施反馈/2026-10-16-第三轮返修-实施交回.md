## 2. T01 阅读状态按产品输出合同判

位置：`test/scripts/run_case.py`。

**`reading_contract(work)`**：逐条列出不合的地方，空表才可信。
- **字段与类型**：
  - `applicable`、`complete` 是布尔；
  - `items`、`unmanaged`、`problems` 是列表；
  - `next` 是非空文字或 null；
  - 每张图有 `id`、`state`、`reason`，没就绪的图必须写原因；
  - `unmanaged` 是行号，`problems` 是非空文字。
- **相互关系**：
  - 不适用：没有任何待办、不说没完成、没有下一动作；
  - 已完成：没有待办，也没有下一动作；
  - 没完成：至少一处待办，且给了下一动作。

**`reading_facts(feature_root, story_required=...)`**：
- 子命令起不来、退出码非 0、不是 JSON、不合合同，都是 unknown，并写明原因。
- 没有 `AR/story.md` 时，只有本轮还没到成文才算不适用。业务已收口而 story 缺失（`closure_facts` 与 worker 按「起点是 story 且目标已闭环」传入）判 unknown。

**证据**：`test_reading_completion.py::TheReadingFactsKeepTheProductsContract`。11 个变体逐个走 `reading_facts` → `closure_facts.target_complete`，结论一致：
- 合法无图 → not_applicable；
- 全部就绪 → complete；
- 有待办 → pending，原因、未建源行号、结构问题、下一动作原样保留；
- 以下都判 unknown：读取失败、缺 applicable（复评复现的那份输出）、applicable 是文字、说完成却有问题、说不适用却有问题、没完成却没下一动作、没完成却没有待办、没就绪却没写原因；
- story 缺失：未到成文时不适用，业务已收口时 unknown，此时整体目标不成立。

## 3. T02 退出固定次数，判不了进展时交宿主

**退出**：`READING_ATTEMPTS`、`reading_followup`、`reading_watch`、`reading_stopped`。

**`reading_turn`**：业务收口（第一段，和第二段 update）时决定阅读的去向：

| 情形 | 去向 |
|---|---|
| 完成或不适用 | 不续 |
| 会话续不了（这轮没成功或没有 session） | 不续，阅读按事实记未完成 |
| 自动用例，产品给了下一动作，待办与上次转交时不同（第一次，或之后有可见变化） | 原样转交，同一段继续，不限次数 |
| 交互用例 | 交宿主（模型这一轮可能正在问人，不拿产品待办替人回答） |
| 状态判不了 | 交宿主 |
| 转交后没有可见变化 | 交宿主（看不出有没有进展） |

**交宿主**的做法：
- 走既有的 `wait_for_human_reply`，新增参数 `kind`，这里取 `local_reading`；
- 停等时带上模型本轮原话和阅读证据；
- 宿主回话就用它续同一段；宿主收工就记 `reading_handoff: host_concluded`，这一段照原逻辑结束或进检查点。

**没有改动的边界**：宿主主动收工、会话故障、系统级运行预算，仍按原有出口处理；不把它们当成阅读能力的判据。

**证据**：`test_reading_completion.py::TheWorkerFinishesTheReading`，用替身 CLI 驱动真实的 `foreground`。
- 正常工作需要 5 轮往返（每轮有可见进展），全部自动转交，没有交宿主，整体完成。
- 待办文字没变但仍在处理：第 2 轮后交宿主，停等里带模型原话；宿主回「接着画」后续同一段，做完整体完成。
- 能力明确缺失：模型说「看不了图片」，交宿主，宿主收工，记业务收口、阅读未完成，进程仍是 finished。
- 交互用例里模型正在问人：立刻交宿主，问题原样带上；宿主的回话作为续话。
- 状态读不出：交宿主，不当成不适用。
- 会话不可续：不续，也不交宿主，整体目标不成立。
- 宿主主动收工：不续，整体目标不成立。
- 第一检查点、第二检查点都在阅读完成后才停，且各自续的是同一段。

## 4. T03 报告目录按 framework 原生语义

依据：`demo/framework/harness/config.ts` 的 `normalizeConfig`（第 1048 行，`paths` 浅合并）与 `featurePhaseReportsDir`（第 1993–2016 行）；`repo-layout.ts::inferRepoLayout`。

**规则**（JS 的 `hooks/shared/paths.mjs::phaseReportsDir` 与 Python 的 `materials/importer.py::phase_reports_dir` 同一份）：

| 配置 | 报告目录 |
|---|---|
| `reports_dir_pattern` 字段缺失（含没有配置文件、`paths` 为 null） | framework 默认 `doc/features/<feature>/<phase>/reports`，不随 `features_dir` 变 |
| 非空字符串 | 按占位展开，相对工程根 |
| 显式空串、只有空白、null | `<框架根>/harness/reports/<feature>/<phase>`；框架根按原生规则认：`framework/` 下有 `skills` 或 `workflows` 取它，否则工程根自身有就取工程根 |

两种情况抛错，不退回默认位置：
- 要回退却认不出框架树；
- 配置不是合法 JSON。

**消费者**：
- `verifier-report.mjs::reportLocation` 接住错误，报「阶段报告目录判不了」；
- `routing.spec_closed`、`update._phase_facts` 由 story_flow 的既有出口报错。

**证据**：新增 `test_reports_dir_native.py`，用原生探针 `test/fixtures/native/reports-dir-probe.ts`（经 demo harness 的 ts-node 直接调 `featurePhaseReportsDir`，只读）。11 种配置下，原生、JS、Python 三方的目录（或同样报错）逐项一致：
- 没有配置文件；
- 空配置；
- 字段缺失且 `features_dir` 自定义；
- 非空自定义；
- 显式空串、显式 null、只有空白、`paths` 为 null；
- 空值且框架就是工程根；
- 空值且认不出框架树（三方都报错）；
- 配置不是合法 JSON（三方都报错）。

**未覆盖**：
- framework 的 `assertNoDeprecatedPaths`（废弃字段报错）；
- profile 级 `config-defaults.json` 改默认 pattern：本仓 profile 里没有这一项。
