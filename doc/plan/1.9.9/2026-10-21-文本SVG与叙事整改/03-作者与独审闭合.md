# S3：让作者与独审沿真实决定和业务关系工作

预算与推进按[00](00-执行总览与预算.md)，预计G50/X40。只处理本轮实际发现的未决变默认、问题未问、旅程不完整、状态/操作混淆及无增益复述。规则、数据和报告复用现有入口，不新增决策状态、主题台账、语义关键词门禁或模型轮次。

## 1. 当前责任与最小修正

现行story-write已有未决边界、图文关系与必要重现；reader overlay已有完整性要求。真实运行中作者仍把“协议号处理等待结论”写成可重试，车钥匙说稍后询问却进入Plan。因此不再新增一份完整写作规则，而把已有实际决定摆到当前动作之前，把审查从逐章看“有没有”改为优先核“是否与决定一致、整个旅程能否走完”。

决定只来自现有decisions.json、有效人答复、Spec及原件。模型判断其影响，不由脚本根据open数量、词语或模块名单推断业务是否可做。人已明确保持待定的，不反复问同一个问题；仅限制受影响行为，其他已定内容继续。

## 2. 作者输入与执行

| 文件 | 必须改变的行为 | 退出/保护 |
|---|---|---|
| `extensions/hooks/spec/author.mjs::currentDecisions/decisionSection` | 当前已按open/settled交付原文，保留该生产者，不重做列表。在现有决策段和写作起手之间明确先用当前open核受影响动作，再展开流程/异常/验收；已有已定共同部分继续写。只替换重复指引，不加第二份数据投影 | 不新建索引或复制完整Review；不添加作者要填的影响字段、证明表；已有决策数据形状保持 |
| `extensions/hooks/plan/author.mjs`、`author.md` | 在知识/契约选型前取得当前决定和Spec Scope。已有必读文件能直接交付的就复用；对现有decisions解析结果作简短open列表，提醒在设计受影响实体前判断是否需人裁定。未批的模块扩展与业务承载问题必须实际提问，不用mock/默认选项代批准 | 纯局部实现选型仍归实施设计者，明确不适用规则不造人工确认。没有Story决定文件的非Story需求保持原流程；文件存在但坏掉明确报输入缺口，不当空决定 |
| `phases/spec.md`、`phases/story-write.md`现有起手/成文/回看段 | 将当前原则转成一次按真实输入走读：决定允许什么→用户从哪里开始→操作→正常/失败/结果未知去哪里→哪些后续操作仍受限制。按现有写作设计组织，无需另写对照表 | 保留必要重现；不强制每页一表或每条分支一张图；删除重复的泛化提醒，避免新旧两份规则并存 |

具体语义边界：

- “保持待定”不能在流程表/异常表变成默认可重试、已开放或本期不做。写清现阶段确定的行为和待裁定部分；输入不足时不承诺新的恢复接口。
- 需要当前用户决定、且会改变验收/业务范围/批准模块的冲突，首次影响该动作时集中询问相关问题；在原件中已经明确由其他方后续裁定的，按待定边界交回，不催人编答案。缺决定只停对应依赖，不能拦住无关工作。
- 操作开始不等于业务状态迁移完成。图、表、文字共同说明触发事件、责任方、返回/未知与后续动作，不从本地草稿缺失推出远端请求没执行。
- 用户视角的交互体验是本项主体：人从哪里进入、看到哪个页面、怎样操作、得到什么反馈、完成或异常后去哪里。系统调用/业务状态图不能代替用户旅程，页面表也不是硬要求。无页面业务按参与方和数据生命周期讲。空泛“提示可重试”不足以替代实际条件，但不要求引入额外恢复能力来补齐。
- 依据中的量化业务规则保持；没有需求依据且无实际必要的数值不为了“可测”自行设定再增加审批。规则明确不适用的有理由即可，不单独造评审议题。

这些是消费行为要求，不把本轮Case业务名、D编号、金样恢复服务或具体阈值写进机制。修完旧测试产物不能当改进效果；真实新产物由后续授权运行取得。

## 3. 独立审查取得同一份事实，先核关系后核表现

`extensions/hooks/shared/reader-review-task.mjs::decisionRows`当前已经列open原文及settled来源，不新增同类投影。把该段移到必审输入之后、长篇逐章入口之前，先要求审查者从当前决定找与之冲突的实际动作/状态/验收，再做逐章完整性核查；删除后部重复的同类提示，报告仍用现有四键。每个实际冲突给具体位置，无冲突说明核过的受影响位置即可，不新建逐条裁决表。审查者不按作者“已经覆盖”的声明缩小范围。

`extensions/rules/spec-rules.overlay.yaml::story_reader_review`在现有描述内重排优先级，替换重复的泛化枚举：

1. 对每个实际未决/冲突，核相关正文有没有默认选边，以及当前范围内的人是否真正作过决定；“稍后问”但后续已当成前提使用属于未完成。
2. 沿原材料的每条主旅程核条件、角色交接、状态变化、结果未知和正常/失败去向。正文提到某概念，不等于该关系成立；状态边必须是状态改变条件，不是只画用户点击。
3. 看图文合起来是否讲清：能由表/正文承接的不要强制加图；重复流程如果没有新关系价值应收敛；材料中的关键关系未被任何载体承接才是遗漏。
4. 阅读图选择按当前正文是否缺少关系、SVG是否真补足判断，图数/颜色/标题不构成通过依据。必要重现不是重复。

按原报告details四键交回：实际错误及其影响进blocking_findings；表达偏好进advisories；未取得必要输入进unreviewed。不要求每条都生成裁决表、摘要副本或第二份报告。

Plan端复用现有 `plan-rules.overlay.yaml::knowledge_obligation_substance`的“按业务流程走一遍设计与契约”部分，明确核对从Spec继承的真实条件和批准范围：未批准的范围扩展、尚待业务决定却采用默认/mock的受影响实体，不得以技术上可实现签可交编码。`hooks/shared/review-inputs.mjs`中该判据现有必读集合核其能取得decisions/Review和Spec Scope；已有则不重复加表。若仅是缺某个非关键补充建议，沿原分级处理，不把全部open升级为阻断。

Framework原生PASS/closed含义与算法不在本包修改。产物通过既有机械门并不覆盖上述语义发现；语义FAIL按现有机制返修，没闭合的业务决定如实交回，不新增影子阶段门。

## 4. 有区分力的验收

复用author_task_package、reader_review、review_inputs、verifier_report、plan知识审查和writing/story_build相关现有用例，按实际文件名定位运行；不新建评测平台。确定性检查只核任务在动笔/派审前实际包含当前决定、协议正确及既有保持项。

用本轮已保存稿件定位错误，再用中性材料验证方法，不把Case原句变成机器匹配。语义验收由独立于作者的模型/人做，调用模型须用户授权：

| 输入差异 | 应判结果 |
|---|---|
| 人已选保持待定，正文却写可重试/默认开放 | 指出具体冲突及受影响动作，不能PASS |
| 同一未决仅影响一个分支，其余流程有确定依据 | 未决处明确限制，其余内容可继续，不整篇停工 |
| 用户明确授权了某个方案，表达与金样不同但关系完整 | 合法，不要求抄金样或再确认 |
| 图把点击操作当终态，或只有成功状态没有用户去向 | 指到具体边/去向及影响；不靠要求固定节点数修复 |
| 无SVG且文字/表/Mermaid足够；或有SVG但只重复近邻图表 | 前者合法，后者要求取消或改善增益；不能按图数判定 |
| Plan只作可替换局部选型；另一稿未经批准扩大业务/模块范围 | 前者可由Plan定，后者回需求方；明确不适用项不制造审批 |

同义改写、不同章节组织和不同图表选择至少复核一组，防止“只会修这两个Case”。不要求穷尽异常组合。交回区分结构已验、独立语义已验、真实消费效果待验；按00末尾统一准备实际CLI验证，不由维护者代写新Case答案。

设计证据边界：原任务已经交付了open条目，本次不能把上轮失败归为“没有提供决定”。已证问题是作者没有遵守、独审没有抓住；本步只做现有任务优先级和具体走读方法的局部修正。其效果必须由上述独立语义对照及后续真实运行验证，不能以新文本出现、报告字段齐或脚本全绿宣告解决。
