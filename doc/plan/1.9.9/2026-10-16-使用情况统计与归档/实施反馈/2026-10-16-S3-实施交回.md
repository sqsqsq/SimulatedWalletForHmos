## 2. 执行链

**collect**：
1. 先调 S1 记录器做 `reconcile`，有错就报「统计前对账没做成」并停下；
2. 读 `doc/usage.json` 完整字节，固定一次 `git rev-parse HEAD`；
3. `git log --no-merges --numstat <HEAD>` 取可达普通提交；正文里恰好一行 `[TicketNo:] AR…/DTS…` 才关联（两行编号的不关联，Description 里的编号不看）；二进制的 `-` 不计行数；author 邮箱小写去重；committer 带时区时间用于标题起止；
4. 聚合出表格（已格式化）与标题，写 `<features_dir>/.usage-stats/<id>/facts.json`；facts 里记 scope、HEAD、usage 摘要；
5. 在 `current.json` 的锁内建本次目录、写 facts、把 pending 设为本次 `{id, facts_sha256}`，published 不动。

建目录与写 facts 放进锁内，是自测时发现的：若在锁外，并发的 publish 清旧输出时可能删掉一份还没登记为 pending 的新 facts。

**publish**（全程持 `current.json` 锁）：
- 已发布的同一 id 再发：返回原结果并标 `already`；
- pending 不是本次：报「已被新统计请求替代」；
- facts 摘要与 pending 登记的不一致：报错；
- 候选报告核对：每张 facts 表须逐格原样出现、报告里所有表各行列数一致、每个标题原文出现；不符逐条列出；
- 通过后先把 `report.draft.md` 原子改名为 `report.md`，再原子写 `current.json` 为 `{pending: null, published: 本次}`，然后清理输出根下其它目录；
- 改名后、写索引前中断：重试时 draft 不在、`report.md` 在，就拿它核对后续完成。

## 3. 聚合

| 表 id | 内容 | 分母 |
|---|---|---|
| overview | 需求数、开发人数（去重）、关联提交数、新增 / 删除行数 | — |
| steps | 每步：使用需求数、使用占比、完成过的需求数、完成率 | 占比 / 范围内全部需求；完成率 / 使用过该步骤的需求；零分母 — |
| versions（仅全版本） | 每版本：需求数、开发人数、提交数、新增 / 删除行数；未知版本排最后 | 各版本人数各自去重，总览人数重新去重 |
| steps:<版本>（仅全版本） | 每个版本一张 steps | 本版本 |
| environments | 版本 / fw / ext / agent / model 组合编号 E1…，需求数 | — |
| durations | 步骤 × 环境组的平均分钟 | 已完成且 spent 为数值的需求；零秒有效，null 与未完成不当 0；无样本 — |

步骤顺序读共享合同 `contracts/usage.json`。标题：全版本「全版本总览（起—止）」，指定版本「业务版本 X（起—止）」，每个版本一个标题；没有关联提交的不写时间。`--version 未知` 筛 version=null；没有数据的版本给空范围，不退回全版本。

- **成文质量**：模型按模板写的报告是否只陈述表内事实、语气是否合适，结构检查证明不了，留 S4 与真实 CLI。
