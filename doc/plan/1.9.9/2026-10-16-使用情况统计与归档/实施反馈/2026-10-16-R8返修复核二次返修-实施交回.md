## 1. R02：原生毫秒时间使同一终态再次结算

**根因有两处**：
- 游标按整秒保存，带毫秒的原生闭环时刻永远比它晚；
- 采纳时没有排除同一事件 ID。

| 位置 | 改法 |
|---|---|
| `usage.py::iso` | 保留原值的小数秒，游标与原生事件同精度 |
| `usage.py::take_terminal` | 只采纳 ID 不同、且严格晚于游标的终态；同刻不同 ID 仍走原来的稳定未知边界 |
| `phase_facts.py::event` | 事件 ID 里的结束时刻先换算到 UTC，同一时刻换一种时区写法仍是同一事件 |
| `usage.py` begin 起点 | 取整秒（不晚于实际开始）|

**起点取整秒的原因**：update 记录的关闭时刻只到秒。起点若带微秒，同一秒内开轮再关轮时，关闭时刻会早于起点，这一轮就结算不了。改游标精度后，现有的两条 update 入口用例当场暴露了这个问题，起点取整秒后通过。

**复验**：
- 设计者复现脚本：起点 00:00:00、唯一终态 `00:01:00.500Z`，三次对账依次为 `changed` true / false / false；`spent` 保持 60；游标为 `00:01:00.500000Z`。
- 新用例 `test_a_native_millisecond_closure_settles_once_in_any_time_zone`：
  - Framework 写法（UTC、毫秒）的闭环结算一次，再对账两次零写入；
  - 同一时刻改写成东八区，零写入且字节不变；
  - 真正更晚的一轮（带毫秒）照常推进，累计 90 秒。
- 原同刻用例改用毫秒时刻：两个同刻不同 ID 的闭环首次结算后，连续三次零写入；更晚的闭环仍推进游标。
- 同刻追加只置一次未知的用例照旧通过。

## 2. R04：被隐藏的 Markdown 仍可发布

**根因**：解析时先 strip 丢了缩进，也没有排除 HTML 注释；报告头又是从全文扫描的，和正文不在同一个可见上下文里。

| 位置 | 改法 |
|---|---|
| `stats.py::outline` | 先把 HTML 注释替换成等量换行（保留行号）；围栏代码块按 0–3 格缩进识别；缩进 4 格或制表符起头的行是代码，不算标题或表。返回值另带一份可见行 |
| `stats.py::report_problems` | 报告头只在可见行里找 |

模板里的说明注释照旧不进正文。这次没有新建通用 Markdown 解析，也没有加依赖。

**复验**：
- 设计者可见性脚本：
  - 整篇放进注释：报 5 处不符，真实 publish 返回 `ok=false`；
  - 报告头保持可见、正文缩进 4 格：报「第 1 个标题应为……，报告里是（没有了）」；
  - 脚本内跑的 9 个统计用例全过。
- `test_usage_stats.py` 发布反例从 8 种增至 11 种，新增三种都被拒，旧 published 保持：
  - 整篇放进注释；
  - 正文缩进成代码块；
  - 报告头的「统计范围」放进注释。
- 正例照旧通过：
  - 全版本、指定版本、空范围三种按模板组织的报告都过核对；
  - 修好候选后重试、改名后中断重试、已发布 ID 幂等。
