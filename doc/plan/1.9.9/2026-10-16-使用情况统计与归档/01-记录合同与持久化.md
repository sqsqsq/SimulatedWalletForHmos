## 2. 持久结构

唯一文件 `<projectRoot>/doc/usage.json`。同仓同编号一个节点；原有本地编号仍可记录，Git统计仅按AR/DTS合同关联。

| 层级 | 字段 | 定义 |
|---|---|---|
| 根 | schema / requirements | 当前schema及需求映射 |
| 需求 | name / version | 首份初始化输入的名称、业务版本；版本未知为null |
| 需求 | fw / ext / agent / model | 首次观察时安装版本与可知的会话初始信息；之后不随切换更新 |
| 需求 | features | 实际观察到且已明确属于该需求的feature目录名，去重；用于定位原生证据，不是第二份需求身份 |
| 需求 | steps | 以story、story update、spec、plan、coding、review、ut、testing为键 |
| 步骤 | start / spent | 当前可信起点或null；已结束轮次累计秒数或null |
| 步骤 | verdict / completed | 当前已采纳结果或null；有过可信完成事实的布尔值 |
| 步骤 | last_result | 最近一次采纳的终态游标 `{id, ended_at}` 或null；id为稳定终态指纹，ended_at为该原生终态时刻。脚本生成，不由模型填写、不在报告显示 |

`last_result`只识别已经采纳的完成/明确终止事件，不随检查中的PASS/FAIL或文件存在性变化更新。id取稳定来源类型、真实路径、原生对象/轮次身份、终态类型与结束时刻；不含对账时刻、报告格式或未完成文件清单。它不是报告字节hash，也不保存逐轮事件流水。

### 初始化输入与一次性冻结

六阶段共用 `<features_dir>/<feature>/.usage-input.json`，由原任务中的模型写入语义信息，已有hook/命令自动读取；不要求直接Coding等调用Story init或Spec/Plan作者命令。必填键为requirement、name、version，name非空，version为明确字符串或显式null；缺version键表示尚未完成首份版本判断，不等同于已确认未知。agent/model可空，且只有第一次观察时提供才进入初始化环境。

name/version作为一组原子接收。detail.title可成为name候选，但不能单独将name写成非空并冻结version；版本判断未提交时保持name=null的待补状态。首次hook已有明确需求身份时先保存真实使用、features及机械环境；后续只允许在name仍为null时接收首份完整name/version。接收成功后清理本输入文件；usage已初始化时相同输入幂等，冲突输入报“初始化已固定”，不覆盖。

原post_check在六阶段都能指向同一输入位置与字段合同；可用框架上下文确定的编号不让模型重新猜。文件requirement与实际需求关系冲突时拒绝写入，不能把另一个任务的输入绑定进来。未知业务版本合法，不增加向人补齐版本的关卡；agent/model首次未知保持null，不以晚来的身份冒充第一次。

`.usage-input.json`是一次性语义输入，不是独立登记真源，适配时按精确路径忽略；名字、版本及步骤唯一持久记录仍是doc/usage.json。缺输入时保留已观察使用，不静默漏计，模型按原阶段诊断补文件后重跑原操作即可。

## 3. 内部操作合同

供正式入口内部调用，不在作者正常流程中要求额外运行usage命令。机器入口支持stdin JSON：`python <安装包>/skills/story/scripts/core/usage.py --project-root <根>`；stdout一个结果JSON、stderr诊断，输入不经shell拼接。

| 动作 | 输入 | 写入规则 |
|---|---|---|
| observe | requirement、feature、step、可用初始化输入 | 保证节点/步骤存在，登记已发生的使用与feature关联；不能由检查观测生成可信start |
| begin | 同上，且来自S2指定的真实工作入口 | 先对账旧结果，再开启可信工作区间；已有同轮start保持，不因重复读取重置 |
| reconcile | 已有requirement或全部已登记需求 | 读取已登记features/steps的现存证据，更新结果与计时，不创造未观察到的需求或步骤 |
| finish-own | Story/update实际生产者提供已落盘结果位置 | 从文件核结果，结算对应自有步骤，不接受调用者自报PASS或任意结束时刻 |
| abort-own | 现有update restore等明确结束动作 | 结算可核实跨度，不增加completed；无明确终止的进程中断不自动结算 |

首次初始化fw/ext由脚本取实际安装包/Framework版本；不读维护仓开发源代替。name/version输入语义优先级按spec；类型错误返回一次完整诊断，可空字段不因此向人新增确认。未知字段按合同处理，不增加旧schema兼容。

## 4. 来源与结算算法

共享reader按T03实际框架根和配置路径读summary，不从默认目录兜旧报告。读取结果区分“没有文件”“存在但坏了”“有效未闭环”“当前有效闭环”。原生六阶段只在PASS且原生关闭事实及时间合法时形成完成事件，按现有消费者的对象绑定规则读取；Story/update来源在S2定义。

每次对账先分离当前检查结果与终态事件，文件事务内按下面顺序处理：

1. 当前有效检查结果可以更新verdict；它不改变last_result、completed或spent，也不清start。文件暂缺/不可读不是新终态，游标保持。
2. 没有可信终态，结束本次结算。存在终态时，id与last_result.id相同则只保留既有结算，不再加spent、不清新start；完成A→中间FAIL→读回A仍是同一个A。
3. 不同id但结束时刻早于已采纳终态，视为旧快照，不回退游标或重算历史。相同时刻的不同身份、来源归属或先后关系无法证明时不算新的时间区间，明确保留未知边界，不仅按文件变化判新轮。
4. 可信的新完成事件使completed=true。有一致来源、合法start且结束不早于start时累加时间后清start；缺本轮起点则spent=null。真正新终态B可以推进游标，与重复A分开。
5. 明确终止事件不增加completed。存在start时结算已知区间；无start的重复restore等动作不把已结算spent改为未知。完成过的历史不被撤回操作抹掉。
6. 终态游标、completed、spent和start在同一原子事务更新；写失败全部保持旧值。新终态已落业务文件但usage写失败，下次原入口重试即可结算一次。

多feature读取不能把“当前所有文件hash集合”当成结算事件。各终态按真实时间和来源核身份；任何无法证明未曾结算/区间不重叠的多来源情况不累加时间，spent=null。只保留一个最近终态游标，不因此新增事件台账。

begin前先对账旧闭环，防止把上次结果算成本轮。仅仅再跑一次Harness或status不算新工作区间；没有可信begin却观测到新的闭环，只补完成事实、将完整累计标未知。已未知的历史累计不因后续一轮可算而恢复为假精确值。

工作入口范围：Spec/Plan作者任务包首次用于本轮任务，Story实际写作入口，以及update实际开轮。重复模板查询/读状态不begin；难以证明同轮/新轮时选择未知计时。开始时间表示可观察工作入口，不宣称覆盖此前未进入工具的思考时间。

多feature的步骤使用/完成按需求去重，有一次可信完成即“完成过该步骤”，不宣称全部feature交付。对账按已登记来源取得终态事件；来源归属或并行区间无法证明时spent=null，不相加重叠时间，不增加多feature调度与逐轮流水。

## 5. 单文件事务与错误

全文件读改写采用OS互斥，锁后重新读文件，只修改本次条目；同目录临时文件原子替换，失败保留原字节。锁和临时文件不入库，不持锁等待模型、执行Git或运行业务命令。

锁忙明确提示重试；坏JSON、冲突标记、不支持schema或权限错误拒绝覆盖。不要重置为空表。跨分支合并沿Git处理，不自动把相同需求spent相加。

S1返回 `{ok, changed, errors}` 等机器结果供S2接入。记录失败与原业务结果分别处理：业务成功不能被说成没执行；采集失败也不能被吞掉说完整。无新事实时零写入，统计调用本身不制造新的使用。

## 6. 自验

覆盖：初始化一次与待补名称、两个需求并发、同需求重复入口、两轮结算、同闭环重复对账、完成A→中间FAIL→读回A、新终态B与恢复旧快照、文件暂不可读再恢复、旧闭环早于新起点、新闭环缺起点、未知累计、跨时区、零秒、restore与中断区别、多feature不重复计数；坏文件与写入失败保留原内容。

用真实文件与子进程证明持久化，不仅mock写函数。退出私有reader时同时跑原update消费者回归。交回函数输入/输出、结果指纹防重证据及实际G/X；本步不声称生命周期采集已全部接通。
