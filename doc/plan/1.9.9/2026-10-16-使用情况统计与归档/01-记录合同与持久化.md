# S1：记录合同、事实读取与持久化

前置和预算见 [总览](00-实施总览与接续条件.md)。本步交付可被现有入口调用的一个记录器，不改变业务阶段。

## 2. 持久结构

唯一文件 `<projectRoot>/doc/usage.json`。同仓同编号一个节点；原有本地编号仍可记录，Git统计仅按AR/DTS合同关联。

| 层级 | 字段 | 定义 |
|---|---|---|
| 根 | schema / requirements | 当前schema及需求映射 |
| 需求 | name / version | 首份初始化输入的名称、业务版本；版本未知为null |
| 需求 | fw / ext / agent / model | 首次观察时安装版本与可知的会话初始信息；之后不随切换更新 |
| 需求 | features | 实际观察到且已明确属于该需求的feature目录名，去重；用于定位原生证据，不是第二份需求身份 |
| 需求 | steps | 以story、story update、spec、plan、coding、review、ut、testing为键 |
| 步骤 | start / spent | 当前可信起点或null；已结束轮次累计秒数或null |
| 步骤 | verdict / completed | 当前已采纳结果或null；有过可信完成事实的布尔值 |
| 步骤 | last_result | 最近一次采纳的结果集合指纹或null，仅防重复采纳；脚本生成，不由模型填写、不在报告显示 |

`last_result`是必要的防重游标：仅有start=null不能区分“同一闭环重复对账”和“漏掉起点的新闭环”。指纹取当前可用来源的类型、真实相对路径、原生对象/轮次身份及结果时刻，按固定顺序计算；不对usage整文件取hash，不新增逐轮事件台账。

### 初始化尚未补齐时

正常入口先收到完整语义输入再建档。若Framework hook先观察到明确需求身份但没有名称输入，也必须保留实际使用：name=null表示初始化语义尚待补齐，version暂为null，机械环境在首次观察时固定。已有post_check明确报告该项待补，模型通过原任务输入补齐name/version，成功后name为非空并固定；不另设初始化状态文件。

补齐不是更新跟踪：只允许name仍为null时接收首份name/version，之后不改；agent/model首次未知仍保留null，不能以后来的模型冒充首次环境。暂存节点也按用户口径计为已使用，报告不展开缺失分析。原始需求编号都无法取得时明确返回身份错误，不能编造节点或按目录子串匹配。

## 3. 内部操作合同

供正式入口内部调用，不在作者正常流程中要求额外运行usage命令。机器入口支持stdin JSON：`python <安装包>/skills/story/scripts/core/usage.py --project-root <根>`；stdout一个结果JSON、stderr诊断，输入不经shell拼接。

| 动作 | 输入 | 写入规则 |
|---|---|---|
| observe | requirement、feature、step、可用初始化输入 | 保证节点/步骤存在，登记已发生的使用与feature关联；不能由检查观测生成可信start |
| begin | 同上，且来自S2指定的真实工作入口 | 先对账旧结果，再开启可信工作区间；已有同轮start保持，不因重复读取重置 |
| reconcile | 已有requirement或全部已登记需求 | 读取已登记features/steps的现存证据，更新结果与计时，不创造未观察到的需求或步骤 |
| finish-own | Story/update实际生产者提供已落盘结果位置 | 从文件核结果，结算对应自有步骤，不接受调用者自报PASS或任意结束时刻 |
| abort-own | 现有update restore等明确结束动作 | 结算可核实跨度，不增加completed；无明确终止的进程中断不自动结算 |

首次初始化fw/ext由脚本取实际安装包/Framework版本；不读维护仓开发源代替。name/version输入语义优先级按spec；类型错误返回一次完整诊断，可空字段不因此向人新增确认。未知字段按合同处理，不增加旧schema兼容。

## 4. 来源与结算算法

共享reader按T03实际框架根和配置路径读summary，不从默认目录兜旧报告。读取结果区分“没有文件”“存在但坏了”“有效未闭环”“当前有效闭环”。原生六阶段只在PASS且原生关闭事实及时间合法时形成完成事件，按现有消费者的对象绑定规则读取；Story/update来源在S2定义。

每次对账在文件事务内比较last_result：

1. 无新结果或指纹相同：不重复加spent，不清正在等待新结果的start。
2. 新结果只表示检查状态：更新verdict，不能据此写completed或结束计时。
3. 有新完成事实：completed置true。若本轮start可信、来源归属一致且结束不早于start，增加结束−start并清空start；否则spent=null，不用0代替。
4. 采纳的新结果指纹与更新后的字段在同一次原子写入中保存；重试读到相同指纹即幂等。
5. completed只表达“完成过”。下一轮检查失败不能抹去历史完成，但当前verdict按实际事实更新。

begin前先对账旧闭环，防止把上次结果算成本轮。仅仅再跑一次Harness或status不算新工作区间；没有可信begin却观测到新的闭环，只补完成事实、将完整累计标未知。已未知的历史累计不因后续一轮可算而恢复为假精确值。

工作入口范围：Spec/Plan作者任务包首次用于本轮任务，Story实际写作入口，以及update实际开轮。重复模板查询/读状态不begin；难以证明同轮/新轮时选择未知计时。开始时间表示可观察工作入口，不宣称覆盖此前未进入工具的思考时间。

多feature的步骤使用/完成按需求去重，有一次可信完成即“完成过该步骤”，不宣称全部feature交付。对账读取已登记来源形成一个结果集合指纹；来源归属或并行区间无法证明时spent=null，不相加重叠时间，不增加多feature调度与逐轮流水。

## 5. 单文件事务与错误

全文件读改写采用OS互斥，锁后重新读文件，只修改本次条目；同目录临时文件原子替换，失败保留原字节。锁和临时文件不入库，不持锁等待模型、执行Git或运行业务命令。

锁忙明确提示重试；坏JSON、冲突标记、不支持schema或权限错误拒绝覆盖。不要重置为空表。跨分支合并沿Git处理，不自动把相同需求spent相加。

S1返回 `{ok, changed, errors}` 等机器结果供S2接入。记录失败与原业务结果分别处理：业务成功不能被说成没执行；采集失败也不能被吞掉说完整。无新事实时零写入，统计调用本身不制造新的使用。

## 6. 自验

覆盖：初始化一次与待补名称、两个需求并发、同需求重复入口、两轮结算、同闭环重复对账、旧闭环早于新起点、新闭环缺起点、未知累计、跨时区、零秒、restore与中断区别、多feature不重复计数；坏文件与写入失败保留原内容。

用真实文件与子进程证明持久化，不仅mock写函数。退出私有reader时同时跑原update消费者回归。交回函数输入/输出、结果指纹防重证据及实际G/X；本步不声称生命周期采集已全部接通。
