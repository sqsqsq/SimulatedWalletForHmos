## 2. 记录与CLI合同

持久结构以 [spec §2–3](../../../spec/1.9.9/11-使用情况统计与归档.md) 为准：唯一 `doc/usage.json`，编号键、初始化字段、steps的start/spent/verdict/completed。保留原业务支持的本地编号，但Git关联仅支持明确AR/DTS；不把测试用例名称作为解析规则。

提供以下内部操作（安装后从工程根调用 `python doc/extensions/skills/story/scripts/core/usage.py ...`）：

| 操作 | 输入 | 行为 |
|---|---|---|
| `init --requirement <编号> --from <json文件>` | name/version/agent/model；产品版本脚本读取 | 验证后原子建节点；存在则保留初始化内容，不因配置变化更新 |
| `start --requirement <编号> --step <步骤>` | 既有节点与真实新活动 | 没有start时记脚本当前UTC；已有start视为同轮恢复，不重置；保留历史completed/spent，清空新轮verdict |
| `sync --requirement <编号> --step <步骤> --feature <实际目录名>` | 真实产物，不收模型PASS/耗时值 | 更新结果；满足S2结束合同才结算并清空start，重复调用无二次累计 |
| `stop --requirement <编号> --step <步骤>` | 已明确停止这轮的执行动作 | 用当前UTC结算已知start；不增加completed，不把停止写成业务失败；只读status不得调用 |

共同参数 `--project-root` 为目标工程根；默认复用现有安装布局解析。结构化初始化走文件，不把整段JSON塞shell参数；输入文件是一次性工作输入，不新增长期身份件。stdout为单份JSON，日志stderr；错误必须说明路径/条件/恢复动作。init缺name或非法类型拒绝写入；version/agent/model允许null，框架/扩展版本读取失败属于真实环境错误，不编版本。

script只接收明确需求编号，feature用于定位证据，两者可以不同；绑定来源由当前任务的实际需求关系提供。不得从任意目录名或提交描述猜编号。普通Framework工作与Story使用同一接口。

## 3. 状态与时间推演

| 输入状态/事件 | 结果 |
|---|---|
| 首次使用 | 节点创建，步骤start=现在、spent=0、verdict=null、completed=false |
| 同轮start再次调用 | 保留原start；不多算一次使用 |
| 当前检查FAIL或PASS但未闭环 | 更新当前有效verdict，保留start和历史completed，不结算 |
| 当前轮有效结束 | ended-start加到spent，completed置true，start清空；只有当前对象的完成事实能触发 |
| 已结束后重复sync | 结果可复读，start为空则不累加 |
| 完成后再次真实工作 | 新start，completed仍true，spent保留；这是完成过而不是新轮已完成 |
| 有完成事实但没有起点 | completed可true，spent=null；不能把采集时刻当历史开始 |
| 旧闭环时间早于新start/来源不匹配 | 不接受为新轮完成，不清start，不加耗时 |
| 时间倒置、证据不足 | spent=null，错误或未知明确返回；不能用0替代 |

零开始时间与null含义不同，bool不得当数值秒数。时间以带时区UTC读写，比较真实时刻，显示时才转换。spent一旦因为不可核实历史成为null，不凭下一轮局部时间恢复为完整累计。明确停止后的继续由新start开下一轮；进程中断没有停止事实时恢复沿原start。

现行1.x以需求目录为常见执行边界。合法的多feature关联同一需求时，不新增逐feature统计表或轮次账：调用者要交本次真实来源；只有能由实际关系证明单一步骤活动区间时才结算。无法分清重叠区间时保留使用/完成事实、spent记null，不能反过来阻止业务并行或把两段相加冒充精确计时。此分支需中性离线反例验证，不用业务样例特判。

## 4. 持久化与失败

固定项目级路径在记录器唯一维护，由stats读取同一入口。无需新配置项。对整个读—合并—写过程使用OS文件互斥，取得后重新读最新内容；同目录临时文件原子替换。锁随进程关闭释放，临时文件和锁属于运行态，不入库；沿现有平台依赖处理Windows/POSIX，不引入分布式锁。

无法取锁时立即说明当前记录忙，稍后重试同一操作；不设置影响业务流程的自动重试次数。破损JSON、不支持schema、合并冲突拒绝更新，保留原字节；不重置空表。业务线程不持锁做模型或Git调用，减少占用。

S1库抛出明确UsageError，由S2调用方区分“业务已成功/采集未完成”；独立CLI错误退出非零。写入过程中异常必须保留原文件，不把旧文件删除再重建。

## 5. 验收

离线覆盖：不同合法编号、初始化不可覆盖、start重复、两轮累计、重复sync、旧闭环拒绝、缺起点、时区、零秒、显式停止与中断恢复；两个进程更新不同需求均保留；同需求重复动作不丢历史；损坏/权限/替换失败不覆写旧文件。

验证先读真实文件再断言，不仅mock写入函数。用真实子进程验证互斥和幂等；不要写与当前业务样例同名的特殊分支。交回记录S1实际G/X与总规模，进入S2前先保证库可被真正调用。
