# 1.9.5 复测后整体重写方案

维护设计者，2026-09-22。用户要求重新设计整条链，不继续局部补丁。本文是下一轮唯一实施方案，替代此前“首轮结果与下一轮优化”中的后续修补安排；历史评审和结果保留，不重新定义已发生的测试为通过。方案尚未实施。

## 1. 为什么连续两轮效果差

问题不只是模型没认真读。两轮方案把“知识被列出、增加一段作者提示、审查里有一句、产物表格能投影”作为主要改进手段，验证了载体，却没有证明模型完成了业务设计。

| 已证事实 | 设计问题 | 本轮改变 |
|---|---|---|
| 两轮Spec仍以事件大类替代步骤设计，Plan仍写以后登记 | 以规约条目判断和契约挂号为中心，缺少一个必须实际完成的完整设计工作单元 | 作者围绕本需求的完整业务流程完成专项设计，知识判断只保存决定，不代替设计 |
| verifier能列出规约和名字却放过空泛Plan、错误引用 | overlay新要求与pre_verifier既有“判判断本身”的任务焦点没有统一 | 重写审查任务主干，核实际设计及其消费关系，删除旧的替代性审查目标 |
| auto Spec章节错位，Story带源9.4.1，Plan引用错号 | 只核章节存在和表格/投影文本一致，不核正确的编号与定位关系 | 模板/章节合同为真源，校验父子编号和引用；投影转换目标标题而非原样带源编号 |
| auto复制报告、替换subject；summary仍prior-review | 报告闭环路径未在真实材料变化下验证稳定，交付要求又只追当前路径文件 | 先核清真实报告与对象关系、稳定采纳路径；缺真实审查就明确未完成，禁止以换名/换ID修证据 |
| 耗时下降但Plan更空 | 用流程走完、绿灯和速度替代成品质量判断 | 验收同时核内容、证据、可读性和成本，不以缩内容取得快 |

这是设计者前两轮方法的责任：没有把生产者、消费者、审查和机械合同一起定清。模型篡改报告是明确执行错误；subject为何变化的根因仍未完成复现，不提前断言全部由Framework造成。

## 2. 保持的产品边界

- 知识三类分工不改：facts为项目能力/定义/惯例，constraints为独立义务，patterns为可选结构；上报事实仍一份reporting，OBS沿当前已确认五项基线，安全强制要求保持。
- 独立BI以产品/SE明确采集要求为依据，复用自动交互上报；同语义共享事件常量，字段按渠道适用。subFuncID步骤成功及其他实际结果完整，不按每个内部函数铺点。
- Spec只在9.4完整说明；Story只在附录B承接；Plan只在既有服务层上报小节落实。埋点是配套内容，不变成全篇主线。
- Framework发布件只读。若稳定采纳或机械契约验证确属框架能力缺陷，向上游交最小复现，不能在Extension重造收口器。
- 两个原Case、原材料、auto到Spec/car到Plan、无update第二段；Demo不跑Coding或设备。当前没有启动第三轮的授权动作。

## 3. 正向生产链：每一步交什么给下一步

### 3.1 业务设计先于知识登记回显

Spec作者先取得需求材料、人工决定、激活知识原文和实际工程入口。在本次已有Spec写作任务中完成一份9.4，而非先写规约表再从表拼正文。

9.4的最小内容由需求规模决定：说明流程与指标/采集目的，列该流程必要步骤/子点、实际适用结果及业务触发，区分已有覆盖与本次新增；有多个流程就在本节分组。自动能力与BI策略由项目知识决定，模板不固化项目规则。没有独立运营需求写清不新增即可，不补空表。

作者沿材料已经描述的业务流程逐段检查遗漏，处理未执行步骤、可恢复子失败与整体结束的区别。流程图、功能清单和9.4不要求重复全文，但统计点必须能追到某个实际业务动作；只给“发起/接受/撤销/失效”四类名字不足以完成较细业务覆盖。

形成业务决定后，knowledge-use记录其当前应用和责任来源，不能成为另一份更详细却正文不承接的设计。Spec验收写实际可观察条件，来源/未决按既有机制保留；发现范围或协议不清只问具体未知。

### 3.2 Story做正确投影，不再解释第二遍

Spec9.4是完整事实来源。Story附录保留其必要段落、分组、表/列表；源章节编号不进入目标层级，合法引用目标保持。正文其他章节保留必要业务目标和验收引用，不另写一套上报方案。

本轮采用已有的完整投影路径，保留必要业务关系与内容顺序，不新增模型摘要轮次。

### 3.3 Plan完成映射，不能将自己的职责推给Coding

Plan以已定9.4为输入，沿实际业务执行位置完成：点位/粒度、项目身份与编码、各结果与必要参数、值来源、观察方式、调用时机、复用/新增、验证条件。已有值允许引用可定位的唯一源码定义，无需每处复制；“同上登记”只有在确有明确登记内容可定位时才成立。

没有分配规则时说明具体待定及所需裁决；有规则但无实现时设计必要实体/常量/调用，不能把“将在实现设计登记”留给自己之后。若业务状态发生在远端，明确本端能取得它的回调/查询/通知；没有来源就列真实依赖或建设项，不写成已能观察。

方法契约绑定真实决定结果的调用者：发起动作的责任方法承担发起点位，上报器承担序列化/发送，不由上报器兜底全部流程覆盖。数据实体承接已定字段，use-cases引用实际验收ID和实际方法。用例只写概念而下游无法解析，不是轻微文案漂移。

### 3.4 独立审查评最终设计，而非评“登记像不像需求”

保持现有verifier角色和一次正常审查入口，不新增多层Agent。送达对象是该阶段实际Spec/Story或Plan/contracts/use-cases，以及相应原材料、有效决定、知识定义和义务。

审查方法改为两个动作：先按业务流程走通内容及异常，再核当前阶段的交付是否足以下游使用。知识判断是被审对象和追溯入口，不能以名字具体、rule合法或附录相同证明正文完整。

Spec阶段核9.4与业务动作是否对应、有无遗漏实际结果；Story核投影可读、编号/引用正确。Plan阶段实际追一次“触发→取得结果→确定分类与参数→调用→验证”；未知与建设项区分清楚，契约实体和引用能接通。不要求逐规则抄一张证据表，只报告具体问题和结论依据。

基线例外允许有真实理由、影响、补偿与评审决定；未记录例外而缺设计仍是缺陷。自然到期等具体词不成为通用判据，语义以项目定义为准。

## 4. 文档结构与审查证据必须可信

### 4.1 一个章法来源，生产/校验/引用共用

Spec/Plan目标模板里的主章与不编号辅助章为权威；Story章节合同为其权威。现有解析器识别真实标题，围栏内示例不算标题。需要追加检测时从目标模板/合同取得关系，不抄另一份完整章序表。

Spec须保持Scope等辅助章不挤占主章编号；技术契约主章与子节一致，已有明确章节引用指向同名对象。Plan表中“承载设计章”的编号与标题相符；验收/方法引用按对应真源实际集合解析。无引用的辅助H3是否编号不作为问题。

Story投影迁移标题时去除源局部编号，按附录层级渲染，必要锚点同步；不能仅增加#号。机器区以同一投影函数生成与比较，保留手改保护。与投影有关的问题修生产者，不要求作者手改机器区。

### 4.2 报告是证据，不能靠重新贴标签完成闭环

先做有界复现再决定最小接线，不再先承诺“重跑full phase一定能采纳”。使用第二轮auto的隔离副本，保持未改的原件另存；复现工具操作但不启动新模型。

每次核：请求subject及材料清单/摘要、报告终态块、summary、NEXT；区分业务材料、hook片段、脚本报告发生的变化。保持业务材料不变，追到稳定采纳或一个可定位的不稳定来源即可，不做无信息的重复循环。

- 当前有效报告已存在、材料仍与其绑定对象相同：走Framework实际支持的采纳动作，读取结果确认；已采纳不再跑。
- 当前对象变了：旧报告保持原样。根据真实材料差异与Framework规则决定是否需新审或允许明确的历史沿用，不能复制旧报告改subject冒充当前结论。
- 路径缺报告：按当前请求和真实执行状态说明“尚无对应报告”；只有确有那份verifier原始回复才能原样落盘，不能让“写到当前路径”成为补造报告的指令。
- 仅格式/机械记录漂移导致稳定采纳失败：留未完成/明确历史沿用状态与证据，交机制或Framework责任方；不添加影子闭环状态以宣称通过。

测试装置的report_adopted只表示它能核对的有效报告/summary事实，不证明回复来源真实。真实审查来源由运行中task请求/回复/写入轨迹核验，最终评审保留这一层；不建设防篡改平台，不把字符串匹配伪装成语义真实性保证。

## 6. 三个实施步骤和完成条件

### 第一步：闭环与文档合同定案

先保存本次失败证据，完成4.2隔离复现和4.1章法/引用定位。交回具体失败输入、已知根因、有效采纳路径或上游阻塞、各机械问题的生产者/校验者。稳定规则确认后实施结构/投影/交付状态修正。

验收：auto式Scope误编号不能通过；源编号不泄漏Story；Plan章名/章号和验收ID不一致可检出；真实报告对象不被替换；采纳反例明确失败且无误报完成。若Framework阻塞仍在，允许继续第二步内容工作，但不宣称整体可交付或起第三轮。

### 第二步：知识描述、作者与审查任务整体替换

本步明确包含知识本身的描述优化，交付 reporting.md 与 observability.md 的必要实质改动，不只改作者或审查提示：

- reporting按项目已有能力、身份/SDK映射、结果与按需参数、待核字段、登记与短关系示例组织。将步骤/子点/尝试的对应和实际结果来源讲清楚，移除重复、歧义和误导实现的概述；保留用户已确认的目标项目能力，不用Demo暂缺实现否定它。
- observability保留五项简短基线责任和少量真正边界，协议定义只在reporting一处；不因效果不好新增规约或恢复全部红线。
- 三类知识边界不变：facts讲能力/惯例及实际映射，constraints讲条件与义务，patterns只承担可选结构。现有上报使用例不升级为通用设计模式。
- 用同一真实业务对照“知识能否支持形成完整设计”，缺业务语义须具体列未知，不能只补关键字；协议值与业务示例不进入Extension机制。

按3.1–3.4同时重写作者输入与verifier主干，不先加新段保留旧冲突。以实际需求作桌面推演：合法的细粒度方案能被读懂，首轮/复测那些“仅事件类别、无观察来源、无定义、转发器兜覆盖”的方案能指出缺的实际决定。

不用新建产物schema或要求每条规则增加自证字段。测试固定机械合同及数据流；语义评审由设计者审具体输入与期望，不为了每种反例额外调用模型。正向生产输入保持通用，测试答案不进入机制。

验收：统一的作者任务能明确产出责任、输入/未知处置和完成条件；审查读到同一责任真源并核真正产物。每项旧句删除有新职责接替，无同义规则层层叠加。

### 第三步：效果验证

前两步通过且实际阻塞解除后，再向用户呈现具体变更与测试准备，确定第三轮是否启动；本稿不自动开启。沿两原Case/原材料/原终点，无update和Coding，不靠喂答案修上轮半成品。

成功必须同时满足：章节/引用正确、Spec按指标与流程覆盖必要步骤、Story可读完整、Plan有依据且可实施、真正当前审查或被规则允许且明确披露的历史沿用、原业务约束不丢。耗时单列，不能用内容减半换达标。三轴建议分与实际证据交用户确认。

## 8. 此方案如何替代旧方案

执行者只用本文与本轮根因交回，不拼读旧评审逐条补丁。旧方案/评审作为历史证据保留；已实现有效代码继续复用，失效指令随职责替换一次退出。当前任务交付的是重写方案，不代表修复已完成；复测原件与被篡改报告保持作为审计事实。

| 指标→流程→步骤/必要子点→实际结果 | 知识与作者任务能指导形成关系，审查核真实材料 | 不用事件大类表替代完整覆盖，必要步骤成功不漏 |
| 项目能力复用与运营依据 | 自动能力、BI策略只由项目知识提供 | 无明确运营需求不擅增BI，不重复已覆盖交互 |
| 身份、结果与尝试分开 | 项目协议与实际字段/调用映射相容 | 不按结果另造步骤身份，不混同子点/父步骤或重试/重复 |
| Plan足以指导实现 | 真实观察者、数据源、常量定义与契约责任有直接承接 | 不只写以后登记或给发送封装挂笼统义务；未知具体而真实 |
| Story面向读者可理解 | 完整投影保留关系、正确重排源标题及链接 | 人能看懂流程、目的和边界；不是仅把坏Spec无损搬过去 |
| 审查与运行证据可信 | 请求/报告/材料对象关系和采纳路径核实 | 不以复制/改subject报告替代独立审查，finished不等于质量通过 |

阶段产物尚未真实生成时，只能确认承载与输入/合同已具备，并把实际生成效果留到真实复测；不能提前宣称实际生成效果已通过验收。真实复测必须整组看Spec/Story/Plan，保留无Plan的Case的范围限制。

Story沿完整投影生成，验收核内容完整、标题层级正确、引用可达和业务关系可读；不通过额外摘要流程掩盖源内容缺失。

每次评审结论区分：已达到、仅载体具备/效果待验、未达到（具体缺口）、不适用（具体依据）。差距回到知识、作者任务、生成/校验或审查的真实责任位置；不得用增添项目关键词、复制测试答案或删业务范围来取得通过。维护评审材料不进入被测Case输入。

## 10. 防过拟合与设计者责任（用户明确要求）

评审检查信息是否完整、关系是否正确、是否可实施与可验证；不固定某个案例的业务步骤、事件名、编码、字段集合、表行数或唯一表达形式。测试Case里的偶然特征不能进入通用机制，真实项目约定只在对应知识维护。

实施不达预期时，设计者先还原“目标→输入→决定→产物→消费者→验证”，同时审方案与实现：

| 事实 | 责任处置 |
|---|---|
| 目标/完成条件不明确，存在多种冲突解读 | 修方案真源和验收，不事后用未写清的个人预期指责实施者 |
| 必要信息未在决定前送达、职责重复或有空档 | 修输入与流程设计，并同步直接消费者；不靠增加同义提醒 |
| 按方案实现仍得到错误结果，或简单实现无法履行方案 | 反思方案假设与机制选择，给出更简单完整替代；不要求继续给错误方案打补丁 |
| 方案已明确可执行，实际实现偏离有效决定 | 指出具体偏离和影响，回实施位置修；仍核是否存在诱导偏离的矛盾指令 |
| 缺少事实或执行证据 | 标为待查，先取得区分原因的最小证据，不直接判模型能力或归责执行者 |
| 同类返修反复、修A损害B或成本明显上涨 | 暂停继续堆局部修法，整体审视本步骤的目标、责任和输入输出，再确定调整 |

每条评审问题说明：期望来源、实际证据、影响、根因判断及其确定程度、应该修改的位置。新增要求明确记为需求/设计变化，不追溯成实施者原有义务；可有多方责任，不强行二选一。

验证优先采用另一种合法业务/配置或相关异常路径核适用范围；真实协议常量和已确认项目规则保留，不为避免专名而过度泛化。不把测试答案放进消费模型输入，不通过删需求、放宽正确性或只挑有利测试宣告通过。

设计者对方案是否服务目标负责；实施评审通过但真实效果失败，必须回审此前接受依据，不能用“测试绿了”“实现照做了”免责。方案调整沿当前真源同步，旧失效要求退出，避免实施者继续拼接互相矛盾的评审意见。
