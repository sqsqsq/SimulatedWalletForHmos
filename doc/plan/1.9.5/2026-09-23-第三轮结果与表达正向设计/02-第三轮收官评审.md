## 3. Plan 埋点：与金样候选的差距、机制与知识的责任

### 3.1 差距

car Plan §6「埋点」（`plan/plan.md:339–350`）：一张四行表（发起 / 撤销 / 接受 / 失效），一段字段约束，一句「身份与内码按 reporting §5 首次使用登记位置与分配依据，新事件身份追加登记」。契约上 OBS-03 只挂在撤销方法 `revokeForManage`，发起方法 `createFromSetup` 只挂了 OBS-02（定位记录），没有统计义务；OBS-05/06 挂在仓储组件顶层。

金样候选 Plan（`test/story/golden/bank-card-opening-reporting-candidate/plan.md`）有五块：流程与实现责任（流程、funcID、指标、责任方）；事件身份表（模板 / 流程 / 步骤 / 完整身份）；内码与结果表（每个统计点的成功码、失败码及含义、取消码、分类映射、外码来源）；调用时机与责任表（责任位置、触发与取得、不上报与防重复边界，含去重键与耗时定义）；验证要点。

| 金样候选有的 | car Plan 有没有 |
|---|---|
| 指标 ↔ 流程 ↔ 责任方 | 没有指标；责任方只在契约里挂了一半 |
| 事件身份实际值或精确待决 | 「追加登记」，没有值，也没有说登记在哪个文件、按什么规则取值 |
| 每个结果的内码与分类 | 没有内码；分类只在 Spec 附注出现 |
| 外码来源与缺席 | 没有 |
| 去重键、尝试、耗时定义 | 一句「同一次尝试不重复」 |
| 验证要点 | 没有 |
| 远端结果的取得时机 | 有（列表回查）——这是本轮唯一比候选形态更贴近本需求的地方 |

### 3.2 为什么会这样：知识的问题

1. **知识把「分配」交还给了 Plan，却没给分配规则**。reporting §5 写「当前仓尚无业务流程、步骤和内码登记；首次使用时在实现设计中明确登记位置及分配依据」。Plan 就是实现设计，作者读到这句最省力的写法就是把这句话抄回去。候选金样能写出 `BankCard_001_002`、`1001020201`，是因为它自己定了模板名、流程号、步骤序、结果段含义；Demo 知识没有这一层，作者无从取值，也无从「精确待决」——待决要写清缺什么，可知识没说清到底缺哪一段由谁定。
2. **知识的关系示例只到 Spec 深度**。reporting §6 是「统计对象 / 结果与分类 / 本端从哪得知」，正是 Spec 9.4 要的三列；Plan 要的身份、内码、外码、责任方法、去重键、耗时起止，知识里只有字段清单（§3），没有一个把它们连起来的例子。
3. **observability 的处置列是「明确流程、点位、适用结果及触发条件」**，四行表逐字满足；「同点位同次尝试不重复」一句就满足。规约本身没有要求身份值、编码值和责任方法，作者与审查都按规约字面判。

### 3.3 为什么会这样：机制的问题

1. **Plan 没有作者任务包**。spec 阶段有 `hooks/spec/author.mjs` 把激活知识、规约原文入口、9.4 模板一次送到作者面前；plan 阶段只有 `hooks/plan/author.md` 一页，埋点是「② must 挂法」下的第四个圆点，作者要自己去 manifest 找 reporting 再打开。第三轮 car 在 plan 阶段的事件里没有打开 reporting.md 的记录；它对上报的认识停留在 spec 阶段读过的那一遍。
2. **Plan 模板没有埋点小节的形状**。`templates/plan-sections.md` 只有知识决策章骨架和契约挂法样例；Spec 有 9.4 模板，Plan 没有对应物。作者把 Spec 9.4 的四行搬到 Plan、换了两列，就是「有了埋点小节」。
3. **Plan 不能比 Spec 更细**。9.4 是四行事件大类，Plan 沿它逐点写，也只能是四行。上游没有步骤，下游没有可映射的对象。
4. **审查核的是「规约 ↔ must」对表，不是「统计点 ↔ 实现」**。`pre_verifier.mjs::obligationTable` 把每条规约原文与契约上的 must 并列，审查按这张表判「义务在实体上」；plan overlay 里「只写同上登记按没落地判」这一句没有配套材料——审查任务里没有并列 Spec 9.4 的统计点与 Plan 的落实行，审查没有对象可以逐点核。「按 reporting §5 首次使用登记」这种引用规则的句子在审查眼里是合规，不是推迟。
5. **审查任务没有带 reporting 的内容**。plan 的 verifier.material 里 reporting、observability 零命中；审查判 OBS-05/06「落 KeySharingRepository，均在设计章有承载」，是按 must 存在判的。

## 4. 交付门的重审循环

spec 阶段时间线：13:35 首审 PASS（3 WARN）→ 13:49 交付门说材料变了，读当前 request → 13:57 二审 PASS（5 WARN）→ 按 WARN 改 → 14:00 模型自述「只是 verifier 自己建议的修法，按协议仍须每个材料版本审一次」→ 14:07 三审 → 14:12 才闭环。plan 阶段：14:43 一审 → 按 FAIL/WARN 改 → 14:52 重跑 harness，直接 completed_with_prior_review 闭环。

两次读法都在现行文字允许范围内：`hooks/plan/author.md` §四写「派审之后又改了审查材料的，先重跑这条命令取新的请求再派」，CLAUDE.md §五写「材料变了但历史有 PASS 沿用并如实标」。前者是作者页，后者是 Framework 规则，作者页没有说什么时候走后者。spec 多出的两次审约 30 分钟。

更正（09-24，第二步实施者按 events 逐次核对后）：第二次派审（13:57）前的改动是用户裁定撤销时限改为 24 小时，spec、acceptance、story 的验收与异常章随之改，属于业务口径与验收条件的变化，按分流规则仍应重派；只有第三次（14:07）前的改动是按 WARN 修法，可走历史沿用。所以本样本上分流规则省的是一次派审（约 10 分钟），不是两次。

处置（01 第三步）：`hooks/plan/author.md` §四与 `phases/update.md` 采纳判据第 4 步改为一句明确的分流——当前报告 PASS 且此后改动只是它的 advisory 或 WARN 修法时，重跑 harness 走历史沿用并在 notes 记「按 <subject> 报告的建议修改，未独立重审」；改动触及业务口径、范围、验收或新增实体时才取新请求再派。不新增状态，不改 Framework。
