## 2. 收尾门禁：「没跑成」与「内容不通过」分开，同一份输入只跑一次

`test/story/scripts/run_case.py`：

| 改动 | 说明 |
|---|---|
| `_story_build_verdict` | 用户定的协议：退出 0 且有「`[story-build check] 通过`」= pass；退出 1 且有它自己的诊断 = fail；其余（别的退出码、无输出、启动异常）= 没跑成（None）。**认 `[story-build` 前缀**：起手预检的报错走 `fail()`，前缀是 `[story-build]` 而非 `[story-build check]`、退出码同为 1，报的也是产物内容问题（例如知识判断没填全）——只认后者会把这类内容失败错归成「没跑成」而掩盖 |
| `_post_check_verdict` | 其它门禁按自己的协议：post_check 读到带 `ok` 的 JSON 才算跑成，`ok: true` 且退出 0 为 pass |
| `_run_story_gates` | 没跑成的门禁**不写进结果**，只在 `gate_diagnostics.json` 该项记 `status: not_run`、原因与原始输出；缺席的门禁由现有逻辑判 `harness_incomplete`（退出码 2，装置的账），不新增状态字符串。跑完把结果与**输入摘要**（整个需求目录 + 扩展目录，复用 `_tree_digest`；检查器实现与知识都在扩展目录里）一起写进同一份 `gate_diagnostics.json` 的 `story_gates_cache`；下次调用摘要一致就复用、不起进程，任何变化就重跑 |
| 第二检查点 | 进入等待前先跑一次 story 门禁（事件 `story_gates_prerun`）。收工后 `run_gates` 调同一个函数，输入没变即复用。普通单终点没有预跑，照旧在收场时跑 |
| 诊断写入失败 | 记 `write_error`，缓存没落盘，下次照常重跑，不伪造「已检查」 |

下游核对：`expected_gate_names`、`build_phase_results`（按「在不在」取门禁）、终态判定（缺席 → `harness_incomplete`）都不需要改；provider 失败跳过门禁的分支不动。Framework 阶段 harness 的读法不变，没有前移或多跑。

TEST.md：终态段写明 story 门禁没跑成落 `harness_incomplete`、原因在 `gate_diagnostics.json`；§5.9 第 7 步注明门禁已在第二检查点前跑过。

用例（`test_update_checkpoints.py::StoryGatesTellNotRunFromFailed`，7 条）：输出协议逐项（含 `0xC0000142` 空输出、退出 1 无诊断、非 0 却无通过行）；没跑成的不进结果且落到缺席集合；真实内容失败仍是 fail；同一输入第二次不起进程（断言调用次数）；正文、侧车、检查器实现任一变化都重跑；没跑成那次的缓存不会被补成通过；第二检查点里门禁先于等待。

`0xC0000142` 只是离线注入的样本，没有被写成识别条件；真实机器资源问题没有被「根治」，只是不再被记成内容失败。

## 4. 给 framework 上游的交接（未发送，等授权）

**现象**：update 改完材料后跑 `harness-runner.ts --revalidate`，阶段在跑内按沿用历史 PASS 闭环；revalidate 的汇总表写 `| spec | PASS | closed | completed_with_prior_review | script_revalidated, semantic_not_reverified |`。之后写好当前 subject 的报告再跑 `--sync-closure --phase <阶段>`，输出「已闭环（check-receipt PASS）closure_commit: already_committed」，summary 不被改写，仍是 `completed_with_prior_review`。正式 T2 两个主 agent 都据这句「已闭环」报了「已确认无 semantic_not_reverified」。

**本仓已有的做法**：完整跑一次 `harness-runner.ts --phase <阶段>` 即采纳当前 subject 的报告（spec、plan 各实验一次，subject 稳定；错 subject 与 FAIL 回到 open，不借历史 PASS 变绿）；`/story update` 的方法页第 4 步与 `close` 守卫已按此改。

**建议**：`--sync-closure` 对已闭环阶段的输出点明「本次未采纳新报告，闭环方式仍为 completed_with_prior_review」；revalidate 的汇总里 `semantic_not_reverified` 同行提示「写好当前报告后跑完整 `--phase` 采纳」。

证据：`证据/报告采纳实验/spec/c5_step1.log`（revalidate 汇总）、`plan/1-revalidate.log`、`plan/3-phase-plan.log`、`plan/反例A-*.log`、`plan/反例B-*.log`；T2 现场 summary 见 1.9.4 《T2正式结果评审》§2。
