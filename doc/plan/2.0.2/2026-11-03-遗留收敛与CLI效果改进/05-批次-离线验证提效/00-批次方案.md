## 2. 已定设计

### 2.1 不变约束

- Framework与Extension一行不改，不加测试专用的导出或入口（用户11-04、R9）。产品命令内部的跨语言往返，例如`story_flow.py`为算身份起node、`story-build.mjs`问状态起Python，都是测试的既定成本，不在本批消除。
- 不新增runner、常驻宿主、缓存或调度框架。只用现有的`shared_state.shared_tree`/`copy_tree`、`prepared_copy`、`designed_copy`、C03的`variant`恢复办法，以及C02的直接调判据写法。
- 不删有效断言。每条被测职责都留一条真实链路的见证，覆盖CLI参数、退出码、输出合同、写入与身份。
- `FULL_WORKERS`等并发值保持不变。收益不靠扫并发，也不靠暖缓存：批首、批末的对照都在清空`%TEMP%/story-test-state`之后测。

### 2.2 三种做法与适用判据

逐条用例按下面的顺序判断，判据写进本步交回的逐类表：

1. **前态共享**：一组用例在执行被测动作之前，输入与命令序列完全相同，就把被测动作之前的那份状态用`shared_state.shared_tree`造一次，各例`copy_tree`后再`link_framework`。
   - 键至少包括：夹具、`shared_state.COMMON`、`framework_version()`、造前态的测试文件、变体名（同`prepared_copy`）。
   - 共享只覆盖到被测动作之前。被测动作，以及被测动作之前必须先由本例改动的那几步，仍在用例里真实执行。
   - 例：在story上改字后跑`check`，可以从“骨架已起”的共享态开始；先改材料再起骨架的，要从“设计已准入”开始，本例自己跑`init`、`round`、`skeleton`。
2. **局部规则直调**：断言只关心“某个输入状态下判据给出什么结论”，且同一职责的CLI外壳已有真实链见证，就改成直接调用Extension已导出的函数，每个类起一个node进程批量跑完本类各组输入。
   - 驱动写法同C02的`STORY_RULES`：一段内联ESM读参数，按组调用、输出JSON，Python侧逐条assert。
   - 所需ctx用已有导出组装，例如`requirementContext`；不新增导出。
   - 当前已核到的可用导出：
     - `independent-review.mjs`：`prepareReview`、`reviewResult`、`preparedRecord`、`reviewStatusBlock`、`discloseInStory`；
     - `knowledge-task.mjs`：`knowledgeTask`；
     - `knowledge-application.mjs`：`featureKnowledge`、`blueprintKnowledge`、`unitContext`；
     - `framework-access.mjs`：`readFeature`、`readBlueprint`、`featureIdentity`等；
     - story规则族：C02已用过的`scanLanguageRedline`、`appendixStructureProblems`、`chapterImageProblems`、`imageProblems`、`chapterStructureProblems`。
   - Python侧的局部规则直接import产品模块里的函数，已有测试这样做，不经`story_flow.py` CLI。
   - 需要的函数没导出，就不改产品，这条用例保留CLI，在交回里列出。
3. **同态只读复用**：同一状态上的只读查询（`status`、只读`check`、`readFeature`）在类内取一次，变体用`fresh`另读、不进缓存。这是C03 `probe`缓存的做法。

三种都不适用的，原样保留。

### 2.3 共享前态的固定

| 前态名（`shared_tree`的name） | 造法 | 使用者 |
|---|---|---|
| `skeleton-ready-<变体>` | `designed_copy`后`ensure_flow_state`，再跑`story-build skeleton` | StoryBuildCase、Step8Case、RealRunCase里“骨架之后才改”的用例；test_writing_plan同理 |
| `flow-complete-<变体>` | 按`flow_steps.walk_to_complete`走到范围已定 | test_design_handover、test_material_rounds里只测关卡之后行为的用例 |
| `adapt-target-<种类>` | 造目标仓（含git初始提交） | 两个adapt文件；需要“未提交改动”的例子在副本上改 |
| `kt-frozen` / `kt-candidate` | 已有`prepared_project`，进程内缓存 | 不变 |

变体按实际DESIGN、夹具、宿主声明区分；不同语义前态不合并（C03的约束）。已派审、已接收、已登记这类状态不做跨根共享（`test/tests/README.md`「用时预算」的既有规则）：每个根自己准备审查；现有的`update-registered`照旧，本批不新增同类共享态。共享态目录里只放工程内的相对路径，`framework`照旧是链接、复制时跳过。

### 2.4 度量口径

- **逐步**：本步改动的测试文件，用`STORY_TEST_TIMING_JSON=<文件> python test/scripts/verify.py affected <文件…>`各跑一次。子进程数是主口径，可以确定地比；类用时只作参考，它受负载影响。
- **批首与批末**：先清空`%TEMP%/story-test-state`，再跑`verify.py handback`，带上`STORY_TEST_TIMING_JSON`。冷态墙钟、full、各通道、子进程总数并排报告。本批只跑这两次全量，不为计时反复跑。
- 嵌套进程的复核可以用`probe/`下的探针（PYTHONPATH加NODE_OPTIONS，不改仓库），只作批末归因，不进验证门。

## 3. 步骤

同批连续执行。每步做完定向验证，写增量交回并提交；批末集中评审。

### E01 冷态基线

- **输入**：本页§1；当前HEAD（测试与D01固定对象相同）。
- **动作**：清空`%TEMP%/story-test-state`后跑一次`verify.py handback`，带`STORY_TEST_TIMING_JSON`。这是批首对照。不改代码。
- **完成**：交回列冷态墙钟、full、failure-modes、子进程总数和按文件分布，并与D01暖态结果（1093/1043 s）对照，冷热差单列。

### E02 成文前态（story_build、writing_plan、image_registration、figure_view）

- **决定**：按§2.2逐类判断。“骨架之后才改”的用例改从`skeleton-ready-<DESIGN变体>`起手：
  - `StoryBuildCase.run_build("skeleton")`在共享态里已经跑过，用例不再调；
  - `Step8Case.round_now`这类在本例改动后要重新登记的，保留真实`round`；
  - `RealRunCase`按它自己的夹具另成一个变体。
- **局部规则**：只判红线、编号、表单形式、标题一类的用例，改为批量直调已导出的story规则函数（2.2第2条）。
  - 每类真实链见证至少留一条：`check`经CLI的失败与通过各一条；`chapter`落盘的原子性与拒写；`skeleton`的预检拒绝。
  - 预检类（`SkeletonPreflightCase`）测的就是`skeleton`本身，保持从“设计已准入”起手。
- **退出**：用例里重复的`ensure_flow_state` + `skeleton`前缀。
- **完成**：affected全过。逐类表（类名、原子进程数、新子进程数、做法、留下的真实链）。预估story_build 989→≤450、writing_plan 286→≤140，实际偏离要说明。

### E03 独审协议（verifier_report_protocol、blueprint_case_closure）

- **决定**：报告合同的正反例覆盖缺节、表头、判据行、发现、覆盖声明、结论一致性、材料键、只读核对。前态仍从现有`prepared_copy`（准备审查之前）复制，每个用例一个根，每个根自己准备审查，不跨根共享已派审的状态。改的是调用方式：一个类里各变体的根合成两次批量node调用。
  1. 各根直调`prepareReview`准备；
  2. Python按变体写夹具回复或改回复；
  3. 各根再直调`prepareReview`接收，接着直调`reviewResult`取结论。
  
  这样每例三到四次CLI（各自加载Framework）变成每类两个进程。
- **保留真实CLI链**：
  - `TheStoryIsReviewedRegisteredAndDelivered`系列里正常链各一条：prepare → 回复 → prepare接收 → check → `story_flow story`登记 → `check --deliver`；
  - `format_repair`的完整新回复链；
  - 审查身份进派审载体；
  - 宿主无审查员时的未审披露；
  - 报告目录跟材料走；
  - 坏的准备记录算输入故障。
  
  被测的就是准备或接收本身时（身份、只读、材料变化带前轮报告），该例保持CLI。
- **完成**：affected全过；逐类表；预估408→≤220。

### E04 流程命令（design_handover、material_rounds、story_update、meeting_material、story_inputs）

- **决定**：
  - design_handover、material_rounds：只测关卡之后行为的用例改从`flow-complete-<变体>`起手；测关卡本身（`init`、`round`、`decide`的拒绝与写入）的保持真实链。
  - 同态的`status`读数类内只取一次（2.2第3条）。
  - Python局部规则直接import产品模块的函数。
  - story_update已有两份共享态，只核还在逐例重走的`update`前缀能否从已有共享态起手，不再新增update专用态。
- **完成**：affected全过；逐类表。预估design_handover 503→≤250、material_rounds 385→≤220、story_update 588→≤400。

### E05 知识、CU、adapt、usage（knowledge_task、knowledge_protocol、neutral_knowledge、cu_knowledge_chain、adapt_ownership、adapt_source_kinds、usage、usage_stats）

- **决定**：
  - knowledge_task里对同一前态的多次`knowledge-task.mjs`、`framework-access.mjs` CLI调用，在类内合成一个批量node进程，直调`knowledgeTask`、`readFeature`；作者任务“开始阶段”这类写使用记录的副作用，仍经CLI真实执行（`OnAFrozenScope`的两例）。

## 4. 预期与未达标的处置

估算：测试直接起的产品进程减少约45–50%，嵌套进程随之同比例下降，冷态handback预计落在约500–650 s。

120—180秒在“产品不改、真实链见证保留”的约束下预计到不了。剩下的主要是两部分：
- 产品命令的单次成本，即每次加载Framework，以及命令内部的跨语言往返；
- 每类真实链的必要执行。

批末如实报告这段距离和它的构成。要不要再动产品或改变真实链的保留范围，由用户另定，本批不自行扩大。

## 5. 风险与保护

| 风险 | 保护 |
|---|---|
| 共享态让本该在用例里执行的被测动作被缓存 | §2.2第1条“只覆盖到被测动作之前”；已派审、接收、登记态不跨根共享；逐类表写明被测动作，评审逐类核 |
| 直调绕过CLI外壳，入口回归漏掉 | 每职责一条真实链见证，清单进交回 |
| 共享态目录被用例写脏 | 只读共享根，用例一律先`copy_tree`（现有约定） |
| 变体合并掩盖语义差异 | 不同DESIGN、夹具、宿主声明各成变体；C03的“两个独立语义根”约束保持 |
| 冷热混比 | 批首、批末都冷态测，交回分列 |

## 7. 讨论与修订依据

**原意与来源**：见Spec §8“2026-11-04：离线提效未达标与测试方案本身”。用户原话：
- “你直接设计优化方案吧，放在2.0.2的优化范围里”；
- “测试优化的目的是提效，但不要因此依赖framework和Extension的改动。它们是按自己的需求目标实现，不能为了测试整改”。

**否定的方案**：

| 方案 | 取舍 |
|---|---|
| 每个worker一个常驻node宿主，在进程内调产品入口 | 收益最大，但违反R9“不新增runner/调度框架”；同时要求产品入口可作函数调用，违反用户的产品不改约束。不采用 |
| 减少产品内部跨语言往返（`feature-identity`身份查询2739次、状态查询1616次） | 会让真实使用也受益，但属产品整改，用户明确排除。成本照实记为测试的既定输入 |
| 调高handback里full的并发 | R9把“扫并发”排除在收益来源之外；32 worker的实测也证明整机已饱和。不采用 |

**设计者判断**：在上述约束下，到不了120—180秒的可能性高（§4）。这一判断已写明，交用户知悉；不作为降低本批去重要求的理由。

**实施中的设计更正（2026-11-04，本会话设计者据E03、E06交回）**：
- **E03的前提不成立**：方案设想用直调`prepareReview`代替CLI的准备与接收。`review --action prepare`在调`prepareReview`之前，还经过`story-build.mjs`私有的建源、重投、编号、渲染与结构检查，直调不等价；而准备、接收本身又是该文件多数用例的被测对象。E03因此不改，预估“408→≤220”作废（见[E03评估交回](实施反馈/2026-11-04-134000-独审协议评估-交回.md)）。
- **整体估算偏乐观**：方案估“直接产品进程减45–50%、冷态handback 500–650 s”，实际直接子进程7081→6396（−10%），冷态handback墙钟1082→784 s（−28%），full 1041→745 s。秒数降得比进程数多，原因是退出的都是重的准备链（流程、骨架、设计准备），整机争用也随之下降。剩下的大头是被测命令本身，以及产品命令的单次成本（见[E06交回](实施反馈/)）。
- 120—180秒在“产品不改、真实链保留”下仍然到不了，与§4的判断一致。进一步的候选列在E06交回，由用户决定是否再投入。
