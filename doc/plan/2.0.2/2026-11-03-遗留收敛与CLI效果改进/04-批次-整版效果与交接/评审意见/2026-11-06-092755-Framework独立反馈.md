## F1：闭包收取 gap，但 design_refs 无法合法表达 gap

### 正常触发

一个runtime flow通过`decisions_and_gaps`关联已经登记的gap。gap可以已经`not_applicable`，不应仅因“尚未解决”阻塞。CU精确引用该flow，原生补全应保留其必要关系，或者按明确语义排除无需成为独立施工引用的对象。

### 实现不一致

文件前缀为`framework/harness/`：

1. `scripts/utils/change-unit-design-gate.ts:24–31,74–89`：`DIRECT_REF_FIELDS`包含`decisions_and_gaps`，`linkedAddresses`收其地址。
2. 同文件`:105–158`：`deriveClosure`将稳定索引内的关联gap加入required。
3. 同文件`:222–231`：要求每个required地址出现在显式`design_refs`；缺少即`change_unit_design_closure_incomplete`。
4. 同文件`:168–173`：`completeChangeUnitDesignRefs`只补node/flow及`blueprint|view|relation|decision|contract`，没有gap。
5. `schemas/change-unit.schema.json:110–117`：target.kind枚举同样没有gap；原生地址转引用也返回null。

因此“应显式引用”与“可合法引用”冲突。不能用手补schema不支持的字段或删真实关联作为正常恢复。

### 最小反例和已观察结果

核心输入（用于选择/闭包边界；省略完整P1要求，与正式完整蓝图区分）：

```json
{
  "blueprint_id": "b",
  "design_views": [{
    "view_id": "runtime",
    "runtime_data_flows": [{
      "flow_id": "f",
      "decisions_and_gaps": ["gap:closed-gap"]
    }]
  }],
  "decisions_and_gaps": {
    "gaps": [{"gap_id": "closed-gap", "status": "not_applicable"}]
  }
}
```

CU初始design_refs只选`view:runtime/flow:f`。执行固定版本原函数，结果：

```text
stableAddressIndex: flow 和 gap 都存在
required closure: [view:runtime/flow:f, gap:closed-gap]
completed design_refs: [view:runtime/flow:f]
gap address -> native ref: null
validateChangeUnitDesign: blocked
issue: change_unit_design_closure_incomplete / BLOCKER
message: 当前 delta 闭包缺稳定地址 gap:closed-gap。
```

对照只移除flow里的gap关联，其他对象相同，窄门结果constructable。这是定位用对照，不是建议产品删关联。

反例用未改N1的gate/model/addressing和CU辅助函数；经现有resolver注入隔离P1文件/准入检查。无component索引、无contracts.components，未触发component资产选择支路。它证明这个精确闭包/种类不一致，不证明最小对象通过完整蓝图验收，也不推出所有gap/所有CU都会失败。

真实CLI中，作者先把gap改成not_applicable，仍被runtime view关联带回闭包，随后继续删除view的gap引用；见car runlog L20750—20908。该现象与源码/窄反例吻合，产生了真实返工和删除设计关联的压力。

### 请求的修正与验收

请由Framework确定gap是可选取的设计引用对象，还是只参与阻塞判定而不进入显式施工引用要求；生产者、补全器、schema、地址转换和校验须采用同一语义。这里不预先指定必须新增kind或必须排除gap。

验收至少覆盖本次正常反例，以及真正未决且影响当前CU的gap仍能阻断；解决/不适用的gap不得因不可表达的引用死锁。已存在的其他引用种类、真实依赖关系、来源与准入检查保留。无需扩成所有状态组合或引入兼容旁路。

## F2：人读主文与全量参考的渲染组织，造成浅正文与重复长文

### 实际效果与代码

11-05 car原生人读投影123,518字符，技术参考区112,881字符，约91.4%。正文有短导读，具体调用/恢复/验收大量留在后半。此比例只是定位载体成本，不是通过门或硬压缩目标。

`framework/harness/scripts/utils/blueprint-review-projection.ts`：

- `:627–645`采用reader_guide prose及关联图。
- `:646`在有guide时多数节不再用字段fallback，但decisions/questions仍追加fallback，已写导读也会再展开。
- `:295–308`收集稳定地址的typed内容；`:735–883`及相关renderer在参考区保留模型、契约、流、用例、来源、决定、质询等明细。

这使“作者写得短”与“参考完整展开”能够同时成立，正文质量不会随canonical变大自动提高；同一决定还可能guide与fallback重复。最新手写目标稿只作阅读效果参照，不要求原生复制其章节、图数或业务答案。

### 责任与请求

原生渲染选择确实放大单份人读稿的体量，值得改进；但作者没生成图、guide没讲清、把既定业务规则滥列为decision属于生产内容问题，不能全归renderer。实际canonical没登记图片来源，不能以素材在磁盘上就认定renderer漏图。

希望明确：业务/设计评审主文承担哪些关系解释，技术权威明细怎样按需查阅，guide与结构化内容如何避免重复而不丢依据。可优先使用既有投影/地址/引用能力收敛，不要求新增一套模板体系、第二份canonical或自动语义摘要器。不要单凭字数裁删源设计。

验收可固定同一canonical对比：主文可理解责任、调用、状态、恢复和取舍，完整明细仍可真实到达；重复段落的消减没有损失权威字段，也不要求把缺失设计自动生成出来。

## Q1：typed消费与authoritative来源，请确认推荐的正常生产合同

已核正常实现：`blueprint-skill-projection.ts:247–284`只合并CU design_refs精确选中对象自身的acceptance/contracts/use_cases；不自动从父view取，也不把根端云contracts变成flow的施工contracts。人读投影能扫描全蓝图显示它们，不代表某CU收到。窄反例已验证这一点。

真实作者提前把typed放在view，后段CU引flow时收不到，又搬结构/扩引用。公开工作流曾提示承载位置，故不报“原生漏传”bug；请确认面向作者的正常入口是否能足够直接区分两种contracts和两类消费结果，减少从checker倒推协议。

authoritative检查只针对选中的、实际带typed字段的对象。它没有要求所有ref都改authoritative，也没有要求source_ref指canonical自身。真实作者却批量改成blueprint_design自指，Extension再按材料来源拒收。

需要确认：授权范围内的设计作者形成typed内容时，合法设计authority如何表示；其来源provenance怎样同时保留外部事实/原材料依据；哪些对象允许指向已存在的设计本身。该问题是双方责任接缝，**不是要求Framework替Extension放宽材料核验，更不是已经证明自指一定合法或非法**。Extension对来源角色混用的责任会在本仓处理。

## Q2：interactive宿主只到Plan的正式入口

Extension希望在Story之后完成CU Spec/Plan，止于Plan。当前交接沿change-unit-progression进入attended run；本地dsh patch只支持interactive、不声明goal_capability。

实际`goal-mode-entry.ts:344–367`调用`routeGoalCapability(..., 'attended')`并要求in_session，故next拒绝。这符合当前代码，不能称为随机原生故障；attended也不能因目录叫goal-runs就等同headless。

原生存在独立Spec/Plan准备路径，但是否能承接本次所需的完整CU阶段、以及已建立run后如何按原生状态继续，不能仅凭命令存在推断。

请确认：对没有goal_capability、但有interactive模型及所需工具能力的宿主，官方支持的“从蓝图到CU Spec/Plan”入口及前置是什么；若确实不支持，正常入口应在哪里准确说明，而不是让作者在建run并多轮准备后才遭遇能力拒绝。**不请求为dsh增加goal/headless能力，不请求放宽能力门或构造影子runner。**本仓Extension路线选择和测试宿主把停下误当收尾的责任另行处理。

## 不向 Framework 转嫁的项目

- 空event投影被写成业务“不涉及”：Extension指令冲突与作者/独审处置问题。
- Story遗漏已给的业务条件、未知结果写成确定失败：现有作者与语义审查失效，不是要求原生按案例答案检查。
- 技术字段迁到参考但系统没交参考：Extension表达/对接合同接缝。
- 质询发现后整包延期、INFO错判、报告最终身份不一致和不完整返修：各自Extension/宿主执行责任。
- 最新金样中的Asset、额外恢复API、48小时人答、固定CU数：不是通用Framework要求。
