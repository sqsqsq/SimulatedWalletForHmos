# 两轮 runlog、最新目标稿与实际内容差距：实现归因补评

2026-11-06。维护设计者对 D02 实跑效果的进一步原因核查。只新增本报告及调查证据，不改产品、Spec、Plan、金样或旧评审，不启动新 CLI，不提交。不是版本完成签署，也不是新实施许可。

## 1. 结论

当前差距不是一个“模型写得太短”的问题。沿实际输入、作者决定、工具输出和最终消费者，已经能指认以下链条：

1. **Extension 明确把完整技术字段移出 Story，但业务关系也在模型重新组织时丢失。** 两者必须分开：前者是现行表达分工的结果；auto 的充值中状态、端侧不重试/不重复下单则是有效业务事实漏写，上一轮曾经正确写出。
2. **缺设计被当成了不适用。** car 作者知道统计上篇该在蓝图完成，仍以复杂度和后续施工为由登记 gap；Extension 又指示“蓝图没有类别就写不涉及”，最终形成“承诺四类事件＋埋点不涉及”的矛盾。
3. **有的返修只消除了局部冲突，没有把承诺闭合。** car 质询指出 AppStorage 与跨进程恢复矛盾后，作者改为会话内草稿，却继续保证进程重启后靠同一幂等标识防重复；原标识从哪里恢复没有设计。接受方数据来源、未知结果处理也有相同的生产消费缺口。
4. **蓝图的增长主要发生在结构化来源、设计视图和质询记录，不是 Story 所缺的业务解释。** 多处重复承载导致实际同步返工；人读渲染又出现短导读优先、明细大量附后的结果。不能用蓝图大或字段齐证明 Story 完整。
5. **原生“人读可见”和“CU 取得 typed 输入”是两条消费路径。** 模型提前写了可选施工片段，挂在 view 等位置；后续 CU 精确引用 flow 时收不到，再移动、补引用、改来源。该边界有原生函数反例与实跑交叉验证。
6. **审查真实纠错，但未守住设计完整性；部分成本来自不完整返修、协议返修与小项全量重审。** 新轮独审原件交接较旧轮明显改善，不能仍以旧轮摘要代写问题概括本轮；同样不能以最后 WARN 或结构通过宣布业务完整。

另已窄验证一项 Framework 原生缺陷：CU 闭包收取关联 gap 并要求显式引用，但补全器和 schema 都不支持 gap 引用种类（§3.9），造成正常关系无法闭合的返工压力。

最值得收敛的是现有作者、质询、Story 独审与原生投影之间的职责和退出条件，而不是继续增加核对字段、异常分支或独立平台。

## 3. 具体差距与因果链

### 3.1 业务条件在写作组织中丢失，不是来源没有

**例：auto 扣款成功、写卡未完成。** A1 `artifact/SR/design.md:135` 明定订单保持充值中、下次读卡由卡云补写、端侧不重试也不重复下单。此关系无需任何额外金样人答。

A0 独审指出后，作者在 L10053/L10321 回填 record-display、状态模型与恢复流程；旧 Story:238 已完整表达。A1 canonical 多处仍保留云补写字样，但写作规划与最终 Story 将重心缩成钱包签约/管理主线：L9308 的全篇规划未承接该结果，L9786/L9824 的业务方案/流程规划继续遗漏；最终 Story:111 只剩“写卡补写都在云侧”，管理与异常章节没有上述订单态和端侧义务。

`story-write.md:67–68` 本来要求完整业务过程与本端承担分开说，不能以“不由钱包实施”省略读者必须理解的结果。逐章输入 `drafts.mjs:102–105` 主要送章节问题、边界和本章设计；模型本轮按局部交互线成文，全文回看与独审没有发现遗漏。

**归因**：内容保持失败已证；模型范围收缩、独审漏核已证。没有确定性字数上限或脚本删除这段的证据，不把“未新增语义清单检查器”本身判作机制缺陷。修正应在已有业务写作与首读审查责任，验证来源中的关键关系在实际 Story 可直接理解。

### 3.2 “蓝图没有”被合法结构化成“不涉及”

C1 原 SR:146 明有四类事件，scope 答复包含事件上报。知识和 `hooks/blueprint/author.md:85–98` 已要求本阶段形成指标、分母/窗口/责任、统计点和获知时机；编号及具体方法才归 Plan。

C1 L7675—7703、L7848、L8324 连续记录：作者已知上述分工，因增加复杂度而选择登记“统计明细待 plan”、设远期切片，不写事件明细；最终蓝图 `story_details` 没有 event 项。Story:244 将指标定义、统计点、时机与内码一并下放，:309 写“不涉及”，:301 却继续承诺四类统计。

直接关联的现实现：

- `phases/design.md:82` 指示“蓝图里没有的类别……写不涉及”，混同了业务不适用与上游尚未完成。
- `appendix-readers.mjs:10–17` 无 event 返回空集合；这一步自身只是如实投影，并未删除设计。
- `appendix.mjs:202–210` 接受“不涉及”起头的机器节说明，故错误解释可以结构通过。
- 同页 design:84 又要求共同设计不能留给 CU 修，合同出口与职责要求未形成一致解释。

**归因**：作者主动延期＋质询处置放过＋Extension 不适用提示放大＋Story 独审漏挡，是闭合证据链。原生允许登记 gap 本身合理，但登记不是完成，更不能使当前已适用义务退出。最小收敛方向是修正现有缺类恢复说明、统计上篇责任与审查判断，不新增统计平台或强制给所有题材造 event。

### 3.3 局部收窄消掉矛盾，却留下无依据保证

C1 L7681—7687/L7730：独立质询发现内存 AppStorage 与跨进程恢复冲突，作者改成草稿只在会话内保留，把 process_recreation 设不适用；同一次处置仍保留“重启后重新发起、同一幂等不产生第二条”。最终 Story:148/206/289 如此表述。

SR:96—102 只保证**同一** idempotencyKey 防重；会话丢失后原 key/请求如何取得没有生产者。当前材料“退出或断网”是否含关闭进程并未明确，不能强令使用金样 Asset；但无论选哪种载体，都不能在来源缺失时保证恢复同一请求。这是日常中断与请求未知结果，不是为了极端异常加设计。

同类已证缺口还有：接受页需要车型、车主昵称、当前账号收到的分享，现有 accept 接口只给凭据/状态、车主清单按 vehicleId 查询，不能自行提供接受方加载；撤销失败又被写成保留原状态，没有区分明确拒绝和响应丢失。最新目标稿把请求身份/展示身份、失败/未知、本地空/远端未决分开，值得保持的是这些关系，不是其特定模拟 API。

**归因**：有源材料缺口，作者却写成确定能力；安全/环境 must 与知识名称存在未能证明生产消费闭合。已有 author、原生 App 运行流、独立质询均有承担此判断的位置，尚无证据证明需新增通用状态机制。由作者补合法设计或明确受影响缺口，审查者核承诺实际前提。

### 3.4 技术明细迁移是明确设计，实际交付却不总含参考

`design.md:78–82`、`story-write.md:104`、`story-chapters.json` 附录和 `story-inputs.mjs::designReferenceSection` 明确：Story 附录写接口/数据/规约业务摘要，完整字段、类型与映射在原生蓝图人读参考，不复制。A1 L10355 实际收到，L10359 按此组织附录。因而相对 1.x/最新候选完整技术表的减少，部分就是 Extension 现设计直接造成，不能都算模型漏写。

但移走不等于端到端交付：两轮 auto 取材回执 `delivery_requirements.design_reference=false`，实际归档仅 Story+Review。`publish.py:85–93` 只在系统要求或本单显式请求时加参考附件，忠实执行合同；不能把该分支叫实现故障，也不能擅改系统要求。

**设计接缝**：成文指导无条件将精确查阅转给本地参考，归档消费者不一定得到它。远端本次交付集合不能证明具备完整技术查阅能力。若业务必要条件也依赖该参考则直接违反 Story 独立阅读；纯技术字段需按实际接收者与既有合同确定交付位置。最小方向是使表达位置与实际交付集合一致，不恢复整份重复技术正文，也不强迫全部系统多收一个附件。

根端云 contracts 数仍为 auto5/car6、flow 均3；auto 根 contracts、reader_guide、story_details 反而缩小。不能归因为接口数量涨或专项设计太多。car 最终稿还包含 Story 交付后的 CU 修订，不能用终稿所有体量解释此前成文成本。

最新 2.x 候选 car 蓝图目标稿为15,141字符；实际人读投影为123,518字符，参考区112,881（91.4%）。这是同类**人读稿**比较，不拿机器 YAML 与手写正文直接比。实际导读约束下正文没有图，canonical `generated_graphs=[]`、13个 guide 的 graph_ids 为空；参考末尾虽有两张旅程图，整体/状态/关键调用的阅读效果未达到候选。图数本身不是判据，缺的是关系就地可读。

原生 `blueprint-review-projection.ts:627–646` 有效 guide prose 优先，除决策/质询等外不再走字段展开；`:295–308` 遍历稳定地址收集 typed，后半将大量明细列在参考。当前模型短 guide＋大量结构化明细，经此原生渲染得到“主文摘要、查阅庞大”。Extension 采用这份原生投影作为设计参考，并未另造人读 renderer；因此需要向 Framework 所有者反馈正常产物的阅读组织，不能在 Extension 叠第二套蓝图。

图片消费也已窄验：N1 `registeredImages` 从 canonical 的来源引用识别图片，对实际 car 返回空集合；在内存对象补入图片来源后即可识别。图片已导入磁盘不等于蓝图 renderer 已收到，不能误判原生完全不支持图片。这里需要作者正确提供展示依据，而不是再造图像平台。

来源转写也有真实成本：原 SR→`contracts/se-interfaces.yaml`/mappings→根 contracts 逐段引用/比对→投影。Framework 检查器真读这些结构化权威段；Extension 选择让模型完成转写，不能把它们当无消费者副本一删了之。应分别减少同义叙述维护和多次现场学习结构的成本，保留来源与契约核验。

### 3.6 “评审里能看到”不代表 CU 能消费

A1 L5247、C1 L5772—5914：作者知道 typed 内容可选、当前先做可评审设计不建 CU，仍为评审显示完整提前写 acceptance/contracts/use_cases。C1 还知道自己将内容放在 view、相同 AC 在多处重复，选择先通过 checker 再处理。

原生 `blueprint-skill-projection.ts:247–284` 只读 CU design_refs 精确选中的对象，既不递归找父 view，也不把根端云 contracts 自动转成目标内施工 contracts；人读 renderer 则能扫描更广。以 N1 未改函数执行的反例成立：flow 无typed、父view有用例→CU只引flow收不到；补view引用才取得用例；typed contracts放到flow才取得契约。反例只验证选择内核，不声称构造蓝图通过全量准入。

真实 C1 在 Story 交付后出现用例缺失、contracts形状不对、state_management移动。作者一度尝试为 flow 外的状态数据手填含自身hash的引用；原生已有 flow 内自动绑定 design_ref 的正常路径，后来才采用。不是 Framework 强制不可实现的自引用算法。

**归因**：原生两条消费路径与同名 contracts 容易被混读；作者实际误用、提早生产与错误承载造成返工。公开规则曾送达，不能简单说“未告知”。需要在已有 component-design→CU 交接中让生产位置、引用对象、实际投影对应；不以再多一份图/字段数代替消费验证，不建影子准备器。原生同名概念/可发现性问题由 Framework 处理。

### 3.7 来源与 authority 接缝仍需分责，旧阻塞已经改善

C0 L6257以后至收尾持续卡在 Extension 将派生契约 JSON Pointer 当登记材料/文本片段核验；原生合同接受而 Extension 拒收。C1 已成功质询、成文和过 Story 当时交付门，证明 2.0.2 确有改善。

C1 后续 CU 准备时，作者把“承载 typed 目标须 authoritative”扩大理解为每个 design_ref 都要升权威，并将6个node/flow及根的来源改为 canonical 自指。N1实际只检查**有选中 typed 字段**的承载目标，没有要求改成自引用。最终 Extension `framework-access.mjs:491–513,663–715` 又把各 provenance.source_ref 当材料 support 核，导致末端来源门失败。

**已证**：错误理解后的作者批改、原生机器准入与 Extension 材料消费拒收，以及原材料 source_index 仍保留。**未证**：所有自指都语义非法、原生明确推荐自指、或 Framework 自动把根加入每个 CU。不能仅凭作者“确诊”或PASS定责。关闭需按真实设计 authority 与原材料 provenance 的不同职责核同一正常链，不让模型靠导入蓝图/改路径迎合来源门。

### 3.8 独审与返工：发现问题后仍会选错退出路径

独审不是未发生。auto 抓住 D1 未决却选定演示、协议号生产者/消费者错位、正文已修但蓝图8处旧口径；car 抓住草稿恢复矛盾、48小时选边、图与状态错位、统计没展开。但处理出现三种问题：

- 一次修稿只改部分位置，例如 auto D1四处改三处、协议号先修图再修正文再修蓝图，引发逐轮复审。
- 设计缺口被登记为远期 gap，或主文与蓝图“彼此一致”就降低关注，未确认当前必需设计是否完成；统计和幂等恢复正是在此漏过。

### 3.9 Framework 闭包要求 gap 引用，引用协议却不能表达

这是进一步核出的原生契约不一致，不能混同作者误读。N1 `change-unit-design-gate.ts:24–31,74–89,105–158` 沿 `decisions_and_gaps` 等合法关系收闭包；`:222–231`要求闭包地址全部出现在CU显式design_refs。但自动补全`:168–173`的flat种类没有gap，`change-unit.schema.json:115`也没有gap种类。
