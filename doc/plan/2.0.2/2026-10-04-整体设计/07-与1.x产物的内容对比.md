# 与 1.x 产物的内容对比：Story 为什么变成接口手册

## 1. 对照对象与限制

1.x 形态样本取 `doc/features/archive/Story-Features-20261002-101455/{AR90006,ISSUE-206}/`，其中 Spec/Plan 的创建日期是 2026-09-28，Story 机器区明确从 Spec 与 `spec/knowledge-use.yaml` 投影。归档目录日期不是运行版本号，本稿不把它称为 10 月 2 日的 1.9.8 实跑。2.x 样本为 10 月 3 日 suite 回流的当前 `doc/features/`。

两 Case 的 RR/prd.md 逐字节相同；车钥匙 UX README 也相同。SR 不同：新自动充值增加 55 行接口明细，新车钥匙增加字段类型、必填/可空与错误约定。因此技术精度增加一部分来自测试输入补全，不能全部归为框架升级效果。

本次直接读了两版接口小节、业务正文、Review 议题、知识/埋点/数据附录、车钥匙 Spec 的术语与范围、Plan 的范围/文件与实体设计，并对照现行投影实现。不是只比较目录和文件长度。

## 2. 端云接口篇幅的实际变化

| 样本 | 1.x 接口小节 | 2.x 接口小节 | 非空白字符占 Story 全文 |
|---|---:|---:|---|
| 自动充值（5 个接口） | 12 行 / 514 字符 | 126 行 / 5549 字符 | 3.3% → 26.6% |
| 车钥匙（6 个接口） | 16 行 / 568 字符 | 128 行 / 5172 字符 | 4.1% → 25.6% |

统计含小节标题与机器区注释，用于定位内容重心，不作质量阈值。新 Story 的总行数反而由 541→494、590→513，表格把大量内容压进长单元格；“行数变少”掩盖不了接口内容占比和阅读负担增加。

1.x 一张表，列“接口 / 性质 / 输入→输出 / 错误码”。例如 queryGranteePermission：车辆标识、分享对象→可用权限档位，不可分享返回原因。读者能知道依赖谁、接口干什么。

2.x 同一接口展开请求和响应 DTO、逐字段类型/可空、逐项映射：`vehicleId`→`…vehicleId`，`shareable`→`…shareable`，`permissionLevels`→`…permissionLevels`，并逐接口重复查询幂等、错误与非功能说明。自动充值还把 create 失败后的协议号复用问题附在 getStatus、cancel、update 等接口的非功能说明中；这是源设计把同一段说明普遍复制，投影再全部展示，不是每个接口都有这项语义。

自动充值 `updated:boolean` 明明是未定响应占位，附录却作为响应表一行标“必有”，旁边再备注待卡云定稿。精确表格的外观强化了“契约已定”的印象，超过真实证据。

## 3. 原因：输入增加、设计扩大与机械投影叠加

1. 本轮 SR 补齐字段，蓝图可以合法保存更精确的对外契约。这部分应保留，不能为缩短 Story 删除源字段。
2. 蓝图又加入客户端 DTO 和 direct 映射等实现设计，技术内容超出原始输入本身。
3. `appendix-readers.mjs` 的 `contractRows()` 遍历全部 contracts，固定输出 operation、两类 DTO 字段、全部 mappings、errors/idempotency/nfr，没有区分“评审需要知道的契约”与“编码需要使用的映射”。`appendix.mjs` 又把这份全量结果作为投影与核对的共同标准。
4. 这不是实施者擅自多写：2.0.1 分册 04 §成文要求明确要求字段、映射等完整投影。维护设计者此前把“精确事实不能丢、权威必须可追溯”误扩大为“Story 必须逐项展开全部 canonical”。责任在方案边界，不能只改渲染排版。

蓝图成为设计权威，并不意味着 Story 成为蓝图数据库的展示页。当前实现保住了逐字一致，却没有保住每份产物面向谁、让人做什么决定。

## 4. 各产物的具体差异

| 产物 | 1.x 样本 | 2.x 样本 | 判断 |
|---|---|---|---|
| 原始输入与提取 | RR/SR/AR、会议、UX；AR 常承接提取稿 | 原件保留，提取稿与输入快照分开，人签与文件摘要冻结 | 版本追溯更强；当前 Story 清单旧摘要配新链接是消费缺陷，不应回退冻结能力 |
| 总体设计 | 整体技术取舍主要落需求级 Spec 与扩展章节 | 独立 blueprint 含事实、视图、关系、契约、知识决定、缺口与质询；新增 CU 分工 | 正确的职责前移；但当前把缺口标 future 取通过、以 pass 混同可施工是错误 |
| Story 正文 | 十章业务叙事，来源为需求与 Spec；车钥匙旧稿接受侧也已包含 | 仍是十章，零 CU 可先成文；正文来源转为需求、决定和蓝图 | 不应变成交付质量或业务颗粒度下降。新版不是所有正文都变差，也不能把接受侧完整归功于蓝图：此处可比的旧样本已有接受侧 |
| 接口附录 | 接口摘要表 | 全 DTO、映射、错误/幂等/NFR 展开 | 交付层级发生不必要扩大，造成约四分之一正文体量落在接口细节 |
| 数据附录 | 面向本地数据项、用途、存储/清理等约定 | 从 runtime flow 展开 authority/state_owner/recovery，出现 `view:runtime/node:…` 等原生地址 | 获得运行链追踪，但不等价于清晰的存储说明；两条 flow 重复同一缓存策略，业务读者更难辨职责 |
| 规约附录 | 来自 knowledge-use，域/编号/判定/本需求依据 | 来自蓝图 decisions，知识单元/判定/要求理由/target_refs | 权威迁移正确；地址不是解释。自动充值甚至 not_applicable 行也带“在下列对象落实规约”的统一尾句，语义矛盾来自蓝图内容，不只是表头 |
| 埋点附录 | 车钥匙四个统计点分别说明指标意义、分母/重试和结果；自动充值有策略、免密、创建、管理过程 | 车钥匙为一张四行点位表；自动充值主要是两项汇总指标与“实施阶段登记” | 不应把端云接口写细、统计业务设计反而写粗。哪些编码可留 Plan，哪些业务点位/结果/获知时机已应确定，要按知识与当前设计判，不能一律后移 |
| Review | 车钥匙 24/48 冲突保持多方案；另有自行设定 1.5 秒时延问题 | 仍同一人工区形态；24/48 推荐转为 SR48“物理约束”；增加本地模拟承载决策 | 结构能力保持，但推荐逻辑变化不是蓝图必需。旧自设时延也不理想，不以 1.x 全部正确为前提 |
| Spec | 需求级整篇规格，含较宽术语/Scope 与扩展技术章节 | CU-bound，继承 blueprint/design refs，327 行，对象约束更明确 | 正确方向是细化 CU 承担的义务，不重做总体决定。现有术语简化、范围限定需核事实；Phone 改动漏出 scope 不能算精简 |
| Plan | 需求级 478 行；Phone 扩展单列用户批准，文件规划含 domain service/gateway/统计登记 | CU 级 235 行草稿；Phone 明列“不修改”同时计划改路由；缺口由 checker 暴露 | 本轮未完稿，不能按短了一半宣称简化成功。旧路径“在 Plan 申请扩权”应由蓝图修订接替，而不是只删除出口后无处承接 |
| 机器契约与验收 | 车钥匙 contracts 505 行、acceptance 444 行；供 Coding/Review/UT 消费 | contracts 931 行、acceptance 546 行，加入 CU 映射、运行流与知识决定引用 | 新原生关联有必要，但行数不是完整性。末轮仍有 must.verify、运行映射/use-cases 错误，无 Coding/设备证据 |
| 审查证据 | Story 跟随 Spec 的阶段审查 | 蓝图独立质询＋Story 独立审查＋施工阶段审查 | 拆责任是必要的；同一材料重复整包读取、作者改原始报告不必要，且削弱证据独立性 |

## 5. 正向调整建议（本稿分析结论，未改产品）

Story 保持需求评审载体：正文解释端云协作、条件、失败、数据权威与待决；接口附录给读者足以核边界的摘要，保留影响业务决定的精确数值/枚举/约束及真实未决。比如 24/48 冲突、重复创建是否新建、取消是否回滚订单都不能被摘要藏掉。

完整 wire 字段、类型、可空、内部 DTO 与 direct 映射保留 canonical 及现有技术契约/原生设计投影，CU 仍按原生引用消费。完整设计交接时必须可取得这些材料；不能只留仓内链接给无法访问仓库的送审读者，也不为此立刻新增一套独立 API 文档生成器。先按现有归档/附件能力定可交付引用，未确定前不声称接口已可从 Story 删除。

判定标准不是“删到几行”或“最多几个字段”，而是这个细节是否改变读者要确认的业务边界、风险、依赖或验收。精确技术设计与 Story 摘要各有读者，唯一设计权威不变；摘要漏了关键影响由独立审查发现，不用全字段逐字一致替代语义正确。

同样审视数据、规约、埋点投影：数据说清持有/寿命/清除/恢复；规约说清本需求为何适用及具体落点；埋点保住点位/结果/获知时机，编码留应负责阶段。不能只修端云接口这一节，把同样的倾倒问题留在其他附录。

此前 2.0.2 P2 聚焦审查和来源，尚未完整纳入这次发现的“产物职责与展示粒度”问题；不能声称原方案已解决。后续完善应调整该包的附录合同、投影消费与验收，不回退为 Spec 驱动 Story，不删除蓝图精确事实，也不照抄 1.x 的错误选型。
