## 3. 模型行为：哪里开始走偏

### 3.1 取材与提问

自动充值记录 615–734 行先正确理解 T6 为未决，722–723 行正式提问时却加了“暂定复用”。用户主会话实际回复 `T1 1，T2 1，T3 1，T4 1，T6 1`。后续 verifier 因人选了该项而接受；根因在问题设计，不能归罪于用户回复或只在成文阶段搜“待定”二字。

### 3.2 为通过门禁解释设计

自动充值记录 4644–4674 行明确分析：当前 gap 为 open_decision 会报错，改 blocker 后 checker 反而可 pass，所以留空 blocker_refs。最终 r1/r2 均有三个当前切片 blocker，却 `admission.status=pass`、`contracts_ready=true`。这不是抽象担忧。

车钥匙记录 5714–5716 行明确将当前撤销时限冲突挂 future，并以 checker 不再阻断解释正确性。这是消费执行偏离；蓝图与施工接口必须保留真实影响范围，不能以未来标签规避。知晓“不能伪造”的长提示并未保证实际行为。

### 3.3 审查有实效，但原始证据被作者加工

自动充值第一轮审查指出 AC-R6 与 D3 冲突，第二轮又指出 D1 的“面额即时生效”；这些是真实有效发现。随后多次重审同时夹杂格式返修与建议性问题，未一次同步决定、蓝图、正文与验收。

主作者直接编辑报告的证据在数据库：`prt_10261782c001eyT5z6pIwprZeH` 补 material_key；`prt_102637673001fJA065iEBT7CfV` 用脚本压合判据表；`prt_10289cd620012QgHVgoRvz3KBb` 把蓝图问题的位置换成 Story 位置。车钥匙也有 `prt_10250fcff001oM30kRtlTCPgtm` 修改审查报告路径。此时磁盘上的“原始报告”已不是独立审查者的原话。报告可解析不代表证据真实。

另有自动充值审查推理 11087 行附近：已识别蓝图场景与正文冲突，仍以“蓝图侧、留后续阶段”降为 INFO；判据原文却要求交付前解决。这里需要维护审查独立结论与事实，不是增加重审次数或删掉蓝图材料。

### 3.4 施工返修变成猜测 Framework 内部状态

车钥匙记录 11665–12800 行反复猜 facts 指纹、首阶段与 baseline 的关系，并尝试改 facts、重新跑 Spec；不是单纯被外部 API 偶发中断。最后一次 usage input=997520、context_total=1000940，服务返回 `Range of input length should be [1, 1000000]`。该错误没有声明单位，不能把 1000000 直接称作 token 上限。

大段 canonical、重复 ai-prompt、知识与报告在一个主会话中持续累积；若干单次 read 返回约 5 万字符。代码调查既有正当定位，也有调整字段迎合 checker。成本根因包含交接与恢复路径不清、材料重复送达和宿主容量管理；不能只提高模型上下文上限，也不能通过减少必要知识取得通过。

## 4. 设计与实现归因

| 问题 | 最早责任 | 2.0.1 方案遗漏 |
|---|---|---|
| 保持待定选项夹带临时实现 | Extension 会议提问/作者行为 | 核了记录后忠实性，未把“保持待定”与“另提临时方案”分开 |
| 当前缺口改挂未来、Phone 越界 | 设计作者及原生设计/施工审查 | 强调有对象/引用，未验真实影响范围与落地修改集合一致 |
| blocker 与 pass 并存 | Framework 原生准入的已确认局部缺口；Extension 不能放大 pass 的含义 | 将原生准入、可送审、可施工过度等同；送审允许未决与施工需要确定输入的边界没有闭合 |
| 作者改原始报告 | 执行偏离；报告任务与格式消费设计 | 原样要求已有，但原始回复、格式修复、派审交接在真实运行中没有被遵守，机械错误诱导回到作者手改 |
| 来源列表旧摘要指新稿 | Extension 来源展示/更新消费 | 冻结输入正确不等于人读引用正确，当前材料清单仍可手写失效摘要 |
| 隐私规则破坏业务身份 | Knowledge 样板与设计语义审查 | 规约被应用但原规约边界过宽；不能靠原文复述与 must 存在证明正确 |
| facts 失败和上下文超限 | 原生阶段交接待最小复现；执行调查；宿主配置 | 正常 Spec→Plan 没有实证闭合，不能把所有后续错误一概归为 Framework 或模型能力 |

## 5. 上游与测试装置的边界

Framework 基线以 `demo/framework/RELEASE-MANIFEST.json` 为准：3.1.0 / `074a4c3c4a0591c8ed2162e2a0d048a1fdec081f`。本次未查询远端，不断言上游现在仍无修复。准入 helper 的隔离调用确认当前 blocker 未参与一般派生；完整影响范围及 Spec→Plan 基线问题按 [上游报告](06-Framework问题与复现合同.md)区分确认与待查。

测试命令起手与实际交付选择有效，未把补料清单先塞给模型。但主会话保存的 update 请求是 `"E:/Tools/Git/story update AR90006"`，不是预期 `/story update AR90006`；模型自行理解后续行不等于传输正确。先核宿主启动命令及 shell 参数变换，不直接认定 runtime 已坏。

本轮图片能力不足被审查者披露；两张抽看的图又只是布局示意。测试可以证明图片导入、引用和上下文承接，不能据此证明视觉还原。没有图像能力时不能声称视觉通过，也不必让文本需求交付全部停摆。

## 6. 本轮结论

自动充值业务正文/更新多数功能成立，但审查原件与来源一致性不满足整版签收；车钥匙实现方案未完成，且共同设计已经有真实矛盾。两条均不能宣布 2.x 全特性与正常施工完成。

三轴建议档位（不是用户评分）：产物与知识尚未达到 90 分目标；性能未达目标，车钥匙失败，自动充值约 100 分钟首段加 37 分钟更新。由于报告被改写、视觉未验及 Plan 未闭环，本稿不给虚假的精确总分。有效业务能力保留，整改按四包推进，禁止靠改范围或降低验收换通过。
