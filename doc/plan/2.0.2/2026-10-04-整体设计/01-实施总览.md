# Story 2.0.2 实施总览与产品合同

状态：2026-10-04 经用户确认重写的方案，供审核与分包实施。维护设计者负责方案与评审，维护实施者负责产品、装置及验证；当前没有实施产品、启动新 CLI 或发布 demo。01–06 是唯一现行实施方案；00、07、08 保留证据与归因，不作为平行实现指令。发生冲突以本总览和对应步骤合同为准。

## 1. 交付目标

2.x 由 Framework 蓝图承担整体设计权威和施工组织，Story Extension 使人能理解、评审、更新需求，并使项目知识影响真实设计与施工。2.0.2 要交付的是一条正常链：原始输入和真实决定一致地进入蓝图、Story/Review 与 CU；独立审查原文可信；按授权停在送审、设计交接、Plan 或实现终点。

保持 1.x 的材料导入、会议、图片、人签、逐章写入、人工区、update、归档与 restore，保持原有效 48 项特性。读取 `doc/spec/2.0.0/01-完整特性树.md` 和 2.0.1 的 07 核验表作继承基线，不修改历史版。不得以简化产物为由删掉有效业务、知识或验证义务。

## 2. 每份产物的职责

| 产物 | 使用者与完成判断 | 权威与表达边界 |
|---|---|---|
| 原始材料、会议原文、人签 | 设计/审查能回查原话、对象与权限 | 原件保留；模型解释不覆盖来源 |
| 冻结输入 | Framework 和后续审查取得同一有效版本 | 原始字节摘要、实际采用集合和真实人签；历史版本不覆写 |
| 蓝图 canonical | 设计负责方维护整体行为、契约、状态、责任、知识决定和未决；CU 引用 | 全部设计权威，不能按 gate 结果改变真实范围或来源 |
| Story | 产品/开发/测试读懂背景、范围、整体协作、流程、功能、异常、验收、上线与待决 | 十章职责保持；用业务语言组织。附录是评审需要的约定，不是 canonical 全字段转储 |
| Review | 有权的人决定真实争议，复核已有结论 | 议题、依据、选项后果、建议、责任方；人工区保持。实现细节由设计负责，不全部上交 |
| design-review.md | 技术读者取得完整蓝图评审内容、契约字段/映射与设计依据 | Framework 原生评审投影的逐字节副本，绑定同一 revision；只读附件，不新增设计权威 |
| CU | Framework 组织可独立施工的设计责任与依赖 | design_refs、touches、readiness 原生生成/消费，不在 Story 重建施工状态 |
| Spec/acceptance | 当前 CU 的行为义务和可判定验收 | 继承共同设计，细化自己承担的行为；原生许可复用时不强制新文档 |
| Plan/contracts/use-cases | 文件、实体、接口、状态、实施与验证责任可直接落实 | 不私自改共同协议或范围，知识落实到实际实体 |
| 独立报告 | 说明当前材料的发现、依据、责任及结论 | 原始回复保留；作者不能修饰成通过；格式、身份、语义和实际独立性分别验 |

接口摘要保留影响业务判断的精确约束；完整 wire/DTO/mapping 留原生投影与 canonical。数据说明持有、寿命、清理和恢复；规约说明真实适用理由和承担者；统计说明点位、业务结果、获知时机和去重边界，不能因接口写细而把统计设计留空。无实质设计内容时不凑空表，不按行数验收。

## 3. 协作与终点

| 当前请求 | 顺序与终点 |
|---|---|
| `/story init` | 取材/会议/范围 → 显式关联蓝图 → 冻结 → Framework 发现/设计/真实独立质询 → 取得可评审设计 → 写 Story/Review/设计附件 → 独立人读审查 → 登记与交付选择 |
| 送审（系统单） | 当前交付门 → 实际正文/附件上传及读回核对 → 发布记录；本地单无远端动作 |
| 完整设计交接 | 已成立设计经原生 CU 准备与 readiness 交回；不启动施工 |
| 实现方案 | 原生 CU 准备 → 原生范围候选（request，spec,plan）→ 适用阶段完成或合法复用；不进入 Coding |
| 完整实现 | 外层入口在已有授权内交 Framework 的 interactive/attended 路径；Extension 不增施工循环 |
| `/story update` | 取得变化及人意见 → 确认有效输入 → 判断决定/设计影响 → 必要原生修订 → 同步人读三件和必要审查 → close；不隐含新的实施授权 |
| 直接 `/component-design` 或原生阶段 | 经原生扩展资产/phase binding 取得知识；不创建 Story flow，不强制绕 `/story` |

已有明确授权直接使用；业务裁决和实施授权不是同一件事。缺决定就交实际责任人；真正独立的范围可经原生设计分解继续，不改 needed_by 伪装远期。

**可送审与可施工分开。** 有明确影响和责任的业务未决可以交人审，源损坏、未经实际独立质询、设计互相矛盾不能借“待决”放行。当前施工所需决定未成立时对应 CU 不可施工。该原生接缝有真实依赖，合同定于 06；不得临时用 draft 读取绕开 delivery gate。

### 连续实施与集中评审（用户 2026-10-04 确认）

本版共四步。执行者每步完成定向自验并在本目录 `实施反馈/` 写交回后，可连续进入满足依赖的下一步，不必等待维护设计者逐步评审；完成全部当前可执行范围后一次集中提交评审。交回状态写“自验完成，待集中评审”，不得写成设计者已签收。

关键设计冲突、必要上游未交付、超过本人权限的预算/授权事项，停止依赖该问题的工作并明确报告；可独立完成的其他工作继续，不绕过依赖、不私自选另一套设计。P4 未授权的真实 CLI 保留待验证，不为凑全步骤完成而启动。新 CLI、demo 发布、Git 提交/推送不因集中评审自动取得额外授权。

最终评审逐步核交回、实际 diff、旧职责退出和整体业务链；集中一次不降低任何验收要求。当前入口与续行状态见上一层 `99-执行者会话交接.md`。

## 6. 完成与必读

步骤签收只证明其实际范围；整版完成还须原生依赖到位、正常请求终点成立、未决/知识/人工内容未丢、旧消费者退出、用户确认行为评价。Coding/设备没有实证时单列未验证。发布另获用户决定。

实施必读：本总览、对应步骤、根 AGENTS、test/TEST，以及步骤列出的当前源码/原生入口。00/07/08 用于追查事实，不要求执行者靠拼历史补全产品决定。
