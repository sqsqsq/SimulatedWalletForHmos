## 4. §4 两项发现

### 4.1 `/story update` 变成 `E:/Tools/Git/story update`

- **出处**：`story-suite-20261003-215006` 自动充值那一轮的 CLI 记录 `cli-runtime/e1e621f9004e4c21/request.json`，`prompt` 已经是 `E:/Tools/Git/story update AR90006`，run.json 里的 argv 也一样。同一个 Case 的第一段请求 `/story init AR90006` 是从 case.yaml 读出来的，原样到达。
- **最早改写的位置**：在宿主（我）调用 `run_multi_case.py resume-update --text "/story update AR90006"` 的时候。Git Bash 把以 `/` 开头的命令行参数改写成了 Windows 路径。CLI 层用列表参数启动子进程、不经 shell，没有再改动它。产品和 runtime 都没有问题，也不需要在产品里识别这个前缀。
- **修正**：第二段请求改为从 case.yaml 读，与第一段同一条路；回话可以用文件传。

### 4.2 车钥匙那一轮上下文涨满之前没有压缩

- **证据**：车钥匙主会话共 467 步，part 表里没有一条 compaction。每一步的输入加缓存读取一路涨到 998,544；下一步服务端返回 `Range of input length should be [1, 1000000]`。
- **配置来源**：`run_case.py` 把 `OPENCODE_CONFIG` 指向用户的 `~/.config/opencode/opencode.jsonc`，隔离的 XDG 配置目录里没有模型配置。那份配置给 `bailian/deepseek-v4-flash-0731` 声明 `limit.context 1,048,576`、`output 131,072`（只读了这两个数，密钥没有读出）。
- **推断**：opencode 按声明的上下文判断何时压缩，声明值高于服务端实际接受的上限，所以压缩没有在服务端拒绝之前触发。服务端报错没写单位，这里把它和 opencode 统计的 token 数对照，属于推断。
- **处理**：按方案，用户的全局配置我不改、也不换模型。**请你决定**：
  - 把这个模型的 `limit.context` 声明调到服务端上限以内（例如 1,000,000 以下，留出输出余量）；
  - 或者由测试装置给运行单独指定一份模型容量声明。这需要新增配置合同，要另行确认。
- **本仓改动**：减少重复送达，即知识任务里 spec/plan 不再重复列整份蓝图判断。错误返回已经带文件、字段和责任，没有再加机制。

## 5. §2 FW-05：正常顺序的复现

在 `output/scratch/2.0.2/fw05/` 用中性夹具 CU（`wallet-balance-refresh/balance-refresh`），只走原生入口，脚本是 `output/scratch/2.0.2/fw05_repro.py`，每一步的状态存在 `states/`：

| 步骤 | 命令 | 结果 |
|---|---|---|
| 物化 | `prepare-blueprint-design.ts --feature C` | 写出 `acceptance.yaml`、`contracts.yaml` |
| 范围候选 | `goal-mode-entry.ts --prepare-scope --completion-target request --requested-phases spec,plan --requirement-file doc/requirements/…` | `phase_chain: []`：「本次无需执行任何阶段（现有结果已覆盖请求）」，验收与设计都由原生从蓝图派生 |
| 先候选后物化 | 同上 | 一样是 `phase_chain: []` |

在这个夹具上，正常路径走的是合法复用，不执行 Spec 和 Plan，所以 facts 基线没有被建立，也就无从承接，FW-05 在这里复现不出来。

车钥匙那一轮的原始记录（events，只读）：

- **调用**：seq 96 的范围候选用的是 `--requirement-file "doc/features/ISSUE-206/AR/story.md"`。这是 §1 说的错误调用：拿运行中会变的 Story 当需求输入，而不是冻结的提取稿。原生判 `phase_chain [spec, plan]`，因为 `acceptance-context:pending`，没有可解析的验收来源。
- **spec 阶段**：首次 runner 报 `context_exploration_facts_scope_coverage`：「当前目标未覆盖：doc/features/ISSUE-206/AR/story.md」。
- **plan 阶段**：首次 runner 在 seq 299，最先失败的是 `context_exploration_facts_run_match`：「建立事实必须绑定当前 feature 冻结范围指纹」。之后又有 `established_by_invalid` 和 `phase_delta: plan` 缺失。
- **facts.md 的来历**：由模型在 seq 178 手写，之后编辑了 9 次（186 到 513），中间去看过 `execution-scope.json` 的 revisions。

结论：

- 已查实的是错误调用，说明已修正。
- 「Spec 完成之后范围指纹变了、facts 绑不上」是原生的正常派生还是调用方造成的，**未确认**。最终现场被手改过，不能当证据。
- 要确认，需要一个蓝图里推不出验收、必须执行 Spec 的中性 CU，从头走 Spec 闭环再进 Plan。这要离线写出 Spec 产物和审查回复，工作量不小。**请设计者定**：在本仓先做这份复现，还是在 P4 授权实跑时按修正后的调用直接观察。不管哪种，FW-05 未确认之前施工路径都不签收。
