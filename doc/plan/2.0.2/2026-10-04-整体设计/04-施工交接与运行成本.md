# P3：原生 CU 施工承接、事实恢复与运行成本

预算 G70/X90。本包交付一个能按正常入口到达 Plan 的施工链；不新建 Extension selector、运行循环或事实状态修复器。

## 1. 身份与实际原生调用

需求目录标识 F 仅用于 Story；蓝图 B 和原生 CU Feature ID C 由 Framework identity/resolver 取得，不手拼 Base64 或路径。需求输入用本轮冻结提取稿的实际文件，文本在范围候选、首次阶段与后续 run 中一致，不能把运行中会变化的 Story 正文临时换作原始输入。

文件定位固定：读取 flow.input.snapshot_ref 对应快照，在 files 中取本轮 `role=extracted_analysis` 的提取稿行，路径为快照目录的 `files/<row.path>`，本轮实例为 `files/AR/story-src/design-draft.md`。不是按文件名搜索最新稿。缺失或不唯一属于冻结输入不完整，回 complete；其来源身份仍为派生分析，不宣称它替代原件权威，蓝图中的原始来源与人签保持可回查。若原生 requirement resolver 不接受此合法来源，按 FW-05 报具体接口不匹配，禁止静默换用 Story。

必读当前发布件：`skills/project/{component-design,change-unit-progression,goal-mode}/SKILL.md`、`skills/reference/goal-mode-operations.md`、`harness/scripts/{prepare-blueprint-design,goal-mode-entry}.ts`。本包只涉及 interactive：默认沿原生“不建 run 的交互阶段调用”完成 Plan；需要 run 级恢复/预算时才按已授权的 attended 路径，不能切 headless。

| 动作 | 调用者/实际入口 | 输入与结果 |
|---|---|---|
| CU 设计准备 | 主执行者请求 `/component-design B` 完整设计交接，原生 change-unit-progression 设计准备段 | 已准入设计，原生 consumer validator 接受候选并原子写 CU；重复已有 CU 用原生复用，不手写 canonical CU |
| 施工输入物化 | `npx ts-node scripts/prepare-blueprint-design.ts --feature C --project-root <根> --framework-root <根>/framework` | 原生 design refs → 本 CU 的设计输入，stdout 的 written 为实际写入列表 |
| 范围候选 | 下方 prepare-scope | 同一需求文件、request 终点、spec/plan 请求 → scope_candidate_prepared；只生成候选不冻结 |
| Spec/Plan 执行 | 已安装原生 `/spec`、`/plan` Skill 与 harness-runner | 首次真实调用冻结范围，阶段完成/合法复用由原生判，不因存在文件认为完成 |
| 结束 | 原生请求范围完成结果 | 请求上限为 Plan，无 Coding；设计阻塞或失败如实交回 |

在 `<工程根>/framework/harness` 执行：

```text
npx ts-node scripts/goal-mode-entry.ts --prepare-scope --feature C --completion-target request --requested-results "形成本施工单位的实现方案，止于 Plan" --requested-phases spec,plan --requirement-file <冻结输入中提取稿的工程相对路径> --project-root <工程根> --framework-root <工程根>/framework
npx ts-node harness-runner.ts --phase spec --feature C
npx ts-node harness-runner.ts --phase plan --feature C
```

后两条是阶段校验/闭环入口，不是用命令代替作者执行 Skill 的内容工作。候选打印的 phase_chain/复用/unresolved 由原生裁定；报未知输入不跳过。原生要求 impact 输入时给真实行为影响及已有来源路径，不能为通过选 false。

## 2. 事实基线正常建立与恢复

P3 开始先用现有隔离模板/中性 CU 测正常顺序：物化→范围候选→首阶段事实→Spec 完成证据→Plan 承接。保留每步实际调用、execution-scope、facts、resolvedInputs、证据 manifest；不以失败 Case 后期被手改的 facts 作基线。相同输入重入不增加设计 revision，合法阶段复用不重新作者整篇。

事实是否新鲜和首阶段资格由原生调用身份/依赖决定。消费者不写 frozen_scope_fingerprint、established_by 来配错误，不改 receipt。源真实变化按原生重验路径回建立责任，完成后再进 Plan；若已发布路径没有可执行恢复动作或干净路径仍坏，交 06 FW-05 最小复现。保持本地有效工作，不删除全部产物从头重来。

这是有输入/输出/预期的依赖验证，不是让实施者自选状态设计。FW-05 未确认时，交回写清哪一步首先失效、哪份输入由哪条命令产生；未证上游故障不先改 Framework，也不把所有事实问题归给消费模型。

## 3. 设计到实体的知识任务

`story-knowledge` 和 `hooks/shared/knowledge-task.mjs` 继续唯一提供当前 Feature 动作的任务：项目根、原生 C、action=spec|plan、audience=author；返回当前原生输入、CU 实际 design refs、适用知识决定/原文、缺口、作者要求。模块不推进阶段、不重判适用性。

修改任务组织：先交本动作必须履行的具体设计/验收与知识义务，再给对应完整条目/方法篇章；公共知识索引只列一次。不得按知识名猜适用或仅给摘要。继承同一有效决定，无改动不重新判一轮；相应知识变化回设计负责方。

Plan 作者先定实体与方法，再把已成立义务挂到实际承担者。`must.verify` 取值与知识执行体的确定性规则由现有 obligation/check 实现和作者任务共用，任务直接呈现该条允许的验证方式，避免模型再从长文推取。实例 text/落点由模型做语义设计，脚本不代填。当前 post_check 对错误 verify、缺实体、错 decision_id 的检查保留。

数据请求身份、显示数据、日志和统计值分开设计；原生 runtime 流的 state/mutation/publication/subscription/consumer/recovery 按原生设计引用物化与落实。`use-cases.yaml` 引用真实契约方法与实际 acceptance ID；缺映射回当前施工作者，共同设计错误回 blueprint，不复制原生算法。

文件动作：`hooks/{spec,plan}/author.md`、`hooks/shared/knowledge-task.mjs`、现有 obligations/契约消费者及相应任务生成；只对确实重复或错序的送达替换，保留 UT/Testing 和非 Story 直接入口。无新 Spec/Plan 的合法复用仍读当前契约，不依赖固定章节号。

## 4. 宿主与输入容量

从本轮 run 的实际启动参数/配置来源核 opencode 使用的模型容量声明与既有压缩机制，记录来源及生效证据；不打印凭据、不擅改用户全局配置、不换模型。不把服务错误中的 1000000 当已知 token 单位。

本仓只修可证错误的启动/配置传递，复用宿主已有压缩/恢复：保留需求身份、授权终点、当前文件/原生状态与未决。没有可用压缩能力就明确运行限制，交宿主责任方；不在 Extension 新建会话调度或自动重开假续行。

本轮 update 字符串变形先做无模型回显：对照主持人传入 `/story update F`、runtime argv/stdin 与消费会话 user part，定位最早变成 `E:/Tools/Git/...` 的位置。用现有原生进程调用传原值，首次/resume 同路；不用产品识别该特殊前缀。测试中文、多行、引号和斜杠，不只覆盖单行 Case。

减少上下文的是重复送达与无效修复：同一阶段不因 status/check 再读整份报告与 canonical；错误返回文件/字段/责任和完整问题集合，细节留原报告。没有证据的旧事实要读，已验证事实按原生基线用；不靠降低产物颗粒度、删知识或规定返修次数省成本。

## 5. 验收

定向 `verify.py affected`：`test_cu_knowledge_chain.py`、`test_knowledge_task.py`、`test_author_context_entry.py`、`tools/cli/tests/test_registry.py`、`test_lifecycle.py`，必要新增在同一测试组，禁止另造运行器。

正常输入、错误引用、同对象重入、来源真实变化、合法复用各有结果。正确 CU 应走到原生认可的 Plan；错误 scope/verify 应给真实责任且不写完成。提取稿输入在各阶段不漂移；断续恢复使用同一原生身份；实际修改文件集合与 touches 一致。
