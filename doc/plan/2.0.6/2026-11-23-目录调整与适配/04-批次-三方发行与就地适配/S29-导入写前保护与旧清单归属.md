# S29 导入写前保护与旧清单归属

承接[04 批二评 R1–R3](../评审意见/2026-11-25-042600-S25至S28复评与demo双次更新裁定.md)。返修估算 G32/X32（根登记及旧机制退出 G24/X27，适配完成条件及消费指令 G8/X5；打包导入的维护脚本按 §5 不计）。基于 567fa6a1，可与 S30 的 Framework 接入准备并行。

1. 在目标被替换前，复用既有写面和冲突检查，对实际 Git 工程中的已跟踪、未跟踪、受忽略保护的目标人工件及已有桥先取前像。新包先在隔离位置验证；目标 base 解包、旧项退场、合并清单都须在同一次导入的写前判断之后。普通冲突在首次写入前报具体路径，原文件与旧登记仍可用；写入中断按已发生事实恢复。外网导出到空发行目录和导入已有业务工程分清使用。复验本轮「脏 base + 同名他属桥」及无冲突导入，比较目标全写面，保住其他工程。对同名他属桥测实际 init 的 stdout、选中宿主产物及后续显式核对。即使 init 报成功，也要在产品入口明确哪个宿主缺桥及冲突来源，不能只检查退出码。
2. 旧版识别使用正式旧清单、已知旧包的机制 ID／路径／字节及对应阶段绑定。当旧 skill 已被新阶段入口接替时同步退出其六条旧引用；保本工程自有 hook、能力、动作等合法登记及文件，不能把整个 hooks/rules/skills 前缀视作包所有。未知归属保留并说明冲突。用原样 2.0.5、**当前 demo 的 1.9.8 原清单及桥的隔离副本**，分别做原位预置→第一次 framework-init→宿主 /story adapt；同时验证带业务 hook 的合法变体和保留对接、阶段输入。干净首装沿现有允许的最小根登记，不能预设尚未生成的 Framework 工程配置。
3. adapter 来源标记只决定离线替身或内网实例的验证口径；两个入口文件是否齐备应对各入口一致判定。stand-in 缺一、缺两件时 --check / --mark-adapted 及自动完成分支应给明确缺件，保游标和样例；完整替身时验证本地可用并照实记录。保住已通过的正常 token 迁移、业务冲突停止、样例和同名桥归属保护。
4. 从干净提交导出，保存旧/新根清单、实际桥、业务 hook 与对接前后内容、文件范围及原生命令结果；在统一候选交回。返回官方 G/X 和 G202、G60 待裁定项对应的新旧消费者。
