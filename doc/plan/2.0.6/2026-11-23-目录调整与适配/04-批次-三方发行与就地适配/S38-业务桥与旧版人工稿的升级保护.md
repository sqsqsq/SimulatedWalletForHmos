## 1. 先判桥的实际来源，再让原生物化器写

现行 `entries.mjs::isStorySource` 将旧根 `skills/` 整体认作本包。于是原生 loader 保留了 `business-receipts`，物化器仍能以 orphan 为由删除可调用的桥。**同一份归属判断供 entryPlan、entryCheck、initSkillBridgeHook、entryMaterialize 及其快照恢复共用**，以受管标记里的 sourceRel 与包拥有的具体 Skill 源对应。新源从包元数据和实际 base 取；旧源只取已核旧版中本包的具体 ID／源或旧版显式桥前像。目标 manifest 的业务 Skill 登记与已存在的业务桥用于识别他属来源。仅以目录或桥名相同不足以认领。

| 当前真实入口 | 实施结果 | 复评读取什么 |
|---|---|---|
| 本包旧桥，来源可核 | 刷新至 base 的唯一新源；已退本包 ID 才撤桥 | init 后实际打开的桥与源 |
| 已登记的业务 Skill，已有它自己的受管桥，和本包不同名 | 让原有业务桥可继续调用，前后同一路径、同一业务源、同一字节；原生清理触及该桥时复用已有保护逻辑 | 导入前、第一次正式 init 后、再独立跑 apply 后逐次打开业务桥；同时核 loader 登记和源文件 |
| 本包想占的同名目标已有他属桥或人工稿 | 首次写前报告冲突和双方来源，保原字节 | 冲突路径、返回、整个本次写面前后差异 |

## 2. 先核将被删除的实际文件，再替换 base

交付实现只有一套“这份文件可否随旧包退出”的规则。保留 Git 对未提交写面的保护；对旧 `base/examples/` **从目标磁盘枚举所有普通文件**，以旧包可信清单的路径及原内容核归属。原件来源可用 `7b117923:extensions/base/examples/.manifest.json` 核实（Git blob `aeafb234`）；不能拿待删目录里任意自报的清单给自身放行。清单未列、内容与已核旧件不符或无法核归属的，先报出原相对路径并保留整个写面。仅有可核、未改的旧包文件才允许整目录替换。新无样例发行不承接这份清单作为常规安装资产。

在实际目标或暂存区读源时分别明确根。**文件归属用相对于目标扩展根的路径；Git 输出先按工作树根还原，再投到本次业务项目。** 例如 Git 给出 `apps/pay/doc/extensions/base/examples/draft.md`，实体位于 `<git根>/apps/pay/doc/extensions/base/examples/draft.md`，只去一次工程前缀。已提交、未跟踪、被忽略均不能单独证明文件归包。检查失败或目录枚举不完整时，挂起这次覆盖并告知原因。退掉 Python `import_external_base` 与 JS `unownedIgnoredInBase` 各自从 porcelain 行猜所有权的分支。交付者可选最简复用位置，但公开业务导入及其写前预检必须得到同一结果；含跳过 init 准备的调用，若会替换已有 base，同样不能绕过文件保护。向全新发行目录打包沿现有路径。
