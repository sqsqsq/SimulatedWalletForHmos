# S09 核定宿主首装的正式接点

**设计裁定（2026-11-24）：通过，S10/S11 可采用，本接点无需上游修改。** 用户要求项目 `framework-init` 消费业务根 manifest 的登记，完成后宿主能从 base 发起 `/story adapt`。首装和升级均在未修改的正式 Framework 上触发了配置并生成了桥。上次只核了 `provides.skills` 的默认寻址和单独的 `/extension materialize`，漏查了 init 自身实际执行的全局阶段，因而错误地要求等待外部接纳。本页取代先前的 S09 停点。[本批安排](00-批次方案.md) · [总方案](../00-实施方案.md)

## 已实测的入口

1. 业务根清单位于 `doc/extensions/manifest.yaml`。正式 schema 1.1 的 `provides.hooks.docs.post_check` 接受相对该根的文件路径。项目级 CREATE 和 UPDATE 的 `run-global-phases` 在默认启用生命周期钩子时执行全局 docs 检查，harness 调用登记的 Extension 模块。触发依据是当前 init 的实际调度；单纯在 AGENTS.md 生成一句提示或把 Markdown 发给 verifier 均不足以说明初始化作者已经行动。
2. 接手该事件的模块从本项目配置取扩展根及实际选择的宿主，从包元数据取 Skill ID，复用正式分发自带的桥生成器 `emitInstanceSkillBridge`。调用时把**扫描 Skill 的目录**指向扩展根之下的 `base`，项目配置的 `paths.extension_dir` 和知识清单仍按原根解析。生成器由固定分发提供；其 TypeScript 导出随 Framework 版本复核。探针限定在 init 内的全局 docs 事件，普通 docs 检查不应写宿主文件。交付实现须以安装版本能识别的 init 上下文为准。
3. init 返回后从真实的 `.codex/skills/story/SKILL.md` 打开 `doc/extensions/base/skills/story/SKILL.md`，按该页的 adapt 路由打开同包 `../story-adaptation/SKILL.md`。两次运行均未在 init 后另调 materialize，未恢复旧根 Skill，也未加第二份运行时 manifest。模型按配置执行初始化即可取得 bridge；此路线把文件写入交给现有生成器，省去模型自行拼写宿主路径。

## S10、S11 采用的合同

**旧混装首升另做了一次对照。** 在 f894 上先用 2.0.5 源树 `2fa9e13f` 和旧清单建立原生 Codex 桥，核其确实指向旧源。再在隔离工程备好新布局、原位合并最小启动登记、保留 13 条项目知识登记；运行正式 UPDATE 退出 0，同一座 Story 桥改指 base，旧根源已不存在。这里的物料转换由夹具准备；正式安装器的迁移、全部 Feature 绑定与写前保护由 S10/S11 交付。[新旧桥及 UPDATE 记录](../../../../../output/evidence/2.0.6-s09-formal-init/legacy/result.json)

首装允许人工在原位根 manifest 合并以下机制登记。原有项目身份和 `provides.knowledge` 原样保留。这里是合并片段；探针用了等义的短路径 `base/bootstrap.mjs`，产品复用已有安装器的入口管理模块，由 S10/S11 把它交付到下列稳定位置。

```yaml
provides:
  hooks:
    docs:
      post_check:
        - base/skills/story-adaptation/scripts/entries.mjs
```

- **S10** 现在可在隔离候选完成布局、包元数据、初装清单和原生触发接线。投送的 Skill 源只在 `base/skills/`。区分宿主 bridge 清单与 Framework Feature 阶段自身的绑定；本次最小清单未验证完整的 Feature 作业链，不能把 base 路径塞进旧式 `provides.skills`，也不能为了让根 manifest 看起来正常而删掉实际阶段义务。S10 在真实完整 manifest 下核加载和受影响阶段作者入口。02/03 返修合流时迁入最终一份源。
- **S11** 现在可接宿主入口实施就地适配。复用现有入口选取、归属检查、写前保护与 Framework 渲染；按包的全部有效 ID 和实际选定宿主核新增、改源、退役。其他所有者的有效入口不得被批量清退；有人工冲突或 hook 被禁用时按真实状态说明。新版往后更新只替换发行目录，沿同一根登记触发。旧混装首次迁移在已定覆盖前检查期间读取旧 manifest 和入口归属，由安装流程在**同一路径**更新机制登记，保住项目知识和对接设置，使第一次 init 已能触发。无需用户每次重配。
- **真实边界** 已从生成桥沿 Story 路由发起当前 adapt 正文规定的第一条 `--apply`。最初取样漏拷 hooks，补齐包内相关目录后，两个候选均在旧安装器读取 `doc/extensions/skills/story/contracts/usage.json` 时退出 1。S10 修机制资源寻址，S11 从同一桥重跑至就地适配完成、样例清理、知识读回与版本落盘。用户真实 CLI 仍只在最终 S13 一次运行。S09 本身 G0/X0，S10/S11 沿本批批准额按实际交回。[固定 pin 实际调用](../../../../../output/evidence/2.0.6-s09-formal-init/900c508d/adapt-entry.json) · [集成分发实际调用](../../../../../output/evidence/2.0.6-s09-formal-init/f8946531/adapt-entry.json)
