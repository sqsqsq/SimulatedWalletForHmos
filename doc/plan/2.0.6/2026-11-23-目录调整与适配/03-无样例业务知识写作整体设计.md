# 无样例业务知识写作整体设计

**S33 的实施真源。** 执行者整体替换 adapt 的知识作业，从第一次选题到最后独审收回按本设计实施。发布安装、目录保护、宿主桥和真实对接沿各自现行合同。下面的 demo 文件、钱包名词及历史反例给维护者校准；交给消费模型的是通用方法和目标项目材料。[执行顺序与交回](04-批次-三方发行与就地适配/S33-无样例首装生成项目知识与受测版本发布.md)

## 2. 对照 example 与现行 adapt：13 份文件分别教会了什么

基线为 `7b117923:extensions/base/examples/knowledge/`，可在样例退场后用 Git 读回。13 份正文与该提交的 demo 正式知识相同（3 份事实、8 份规约、2 份模式）。现行[主题页](../../../../extensions/base/skills/story-adaptation/reference/knowledge-topics.md)已逐题给出六项提示，[方法页](../../../../extensions/base/skills/story-adaptation/reference/knowledge-adaptation.md)却仍让作者照四格样例写，且用样例的 depends_on 与底稿决定模式准入。下表逐份定清要接替的判断。**左列取具体成品供设计校准；右列是执行者重写对应主题时必须说清的取证、归纳和不成立分支。目标仓自己决定文件名和题目是否适用。**

| example 与实际内容 | 现行提示的不足 → 新的写作决定 |
|---|---|
| **component-profile**：部件称谓、边界、六类交互方；原件缺少部分交互方出处。 | 主题页说查架构和出口，但“交互最多”不能证明责任。取入口／注册、项目职责说明及一个跨边界协作；写谁发起、谁决定结果、本端交到哪一步。另有权威约定却暂无代码的协作单列“已约定”；无证据列缺口。不能把旧稿的六方名单带到新仓。[画像](../../../../demo/doc/extensions/knowledge/facts/component-profile.md) |
| **engineering-capabilities**：七个面，含导航、记录、脱敏和资源。其 §6 忽略了真正的共享主题色承担方。 | “找公共导出和常用封装”容易选中同名壳层资源。先从实际调用逆查 import、所属模块的依赖、实现的返回／限制；写出入口、用法、一个会选错的边界。只在单个页面出现的私有处理留源码；公开但未见采用须交代使用现状。见下节成文对照。 |
| **event-tracking**：上篇从指标推到流程、点位、结果和本端可见时机；下篇给事件身份、结果、内外码、描述的取值来源，区分项目已知与未登记。 | 只给“成功数/发起数”和字段名不能指导下游。查有效上报协议、封装及已有调用／登记，按一个业务结果推导：谁拥有分母、谁看到终态、重试是否新尝试；再写每项输入由哪个返回值／登记处给出，未知由谁确认。没有该项目方法、不需要多步推导时不造上下篇。示意流程号、事件号不能成为目标事实。[上报成品](../../../../demo/doc/extensions/knowledge/facts/event-tracking.md) |
| **observability**：OBS-02 定位、03 指标覆盖、05 字段来源、06 定义兼容、07 运营采集依据各自约束不同决定。 | 主题页短例只举“发起与结束要有记录”。从目标运维／上报规范归并同一义务的多处说法；是否需要留定位记录、是否允许另加运营点、登记是否兼容分别判。写具体命中、责任、漏做的后果和验法；API 用法放事实。 |
| **security-privacy**：SEC-01 把有权对端所需原始身份、展示／日志及持久化分开。 | 主题短例谈权限拒绝，不能代替数据去向判断。沿字段从输入追至协议对端、展示、记录或存储，取各自授权和约束。将同一保护义务合为一条，差异写边界；不把“日志脱敏”扩大成业务对端也只能接收脱敏值。没有协议则标缺口。[原条目与边界](../../../../demo/doc/extensions/knowledge/constraints/security-privacy.md) |
| **compatibility-checklist**：字段变更和错误码语义各自影响历史调用者。 | 对照真实新旧读写方、接口协议，取哪一方接受缺省／未知值、哪种变更破坏调用。列使规约命中的变化及可验证的兼容行为；不抄接口字段全集。 |
| **env-exceptions**：清数据后恢复、多入口重入；把环境、人为取消及普通业务失败分开。 | 查目标的环境测试依据、恢复责任和保留状态。只写跨需求复现的条件、恢复者和可观察结果；某页面专有超时报错留在本需求。缺依据不列一套设备异常大全。 |
| **dfx-baseline**：频次与引入体积两类评估，若干基线值实际上待补。 | 从目标性能协议、量测口径及责任方取指标；分清要评估的义务和已经批准的数值。没有阈值可写“须获取哪条基线、影响何种验收”，不得填演示数字。 |
| **ux-consistency**：RTL 镜像是面向用户的结果，探针只能找部分形态。 | 取产品多形态/方向要求与可验证现象。写触发条件、哪一类用户行为会错及模型／实机各能验什么；将语言写法、样式 lint 留已有编码规约。目标无 UI 时有据不适用。 |
| **resource-usage**：规定资源取用优先级；图大小阈值、字符串复用条件均属该项目。 | 分两份职责：事实写“入口在哪、怎样复用”，规约写“什么条件必须复用、哪种例外可新增、依据是什么”。相互引用；不把示范 10KB 或资源目录复制到目标。 |
| **deliverables**：翻译回稿、对外接口文档归档是协作交付。 | 从本项目发布／协作约定取触发条件、负责方、实物和确认方式。人工归档等按既有“评审动作”语义表达；不把非代码责任挂成实现方法。 |
| **decision-tree**：上篇讲分支多步失败时怎样选、线性流程何时不用；下篇有节点表、枚举、上下文和构建／启动责任。§9 的“本工程存量开卡就是反例”缺源码证明。 | 在目标实际使用的承载库查分支、状态和终止语义，从入口调用找各角色。写业务信号及反例，再写目标库真实保证、项目需自己维持的纪律、角色落点和行为验证。只有普通 if/else 而无对应承载依赖，交“不适用”；有依赖未见本业务采用时只说明候选，不写存量采用史。 |
| **page-interaction**：独立业务问题是用户操作与业务回执怎样驱动界面，示范角色为动作表、动作枚举、交互封装、上下文、页面。 | 与流程模式分别判断：查目标中由谁收用户输入、谁解释回执、谁使界面等待／完成、有无相应承载能力。简单独立按钮不构成准入理由。若两种模式确实组合，写清交接与失败收敛方；角色名称来自目标。[两类模式的原件目录](../../../../demo/doc/extensions/knowledge/design-patterns/) |

## 3. 整个知识作业怎样运行

本节是消费路径的定稿骨架。执行者可以适配已有命令选项与措辞长度；输入来源、动作顺序、分流、正文粒度及退回位置已定。只改原文件，模型语义判断继续由作者／现有独审承担。

**入口与分流。** `/story adapt` 完成机制写前核后，在作者产生第一份知识前，主 Skill 只把当前任务交给 `knowledge-adaptation.md` 相应分支、指明 protocol 与按需主题索引。--apply 人读下一步同时给出“本次为何从基线起／为何只看变更”“已有知识是否可读”“由谁取得哪些输入”。保持 --status 的完整版本与结构读数。首次从正常业务动作开始，历代迁移说明用来查漏；升级直接给晚于游标的主题及加载问题。安装输出、知识内容和达到适配完成条件分别汇报。

| 情景 | 作者从哪里开始 | 本次交付 |
|---|---|---|
| 首次，正式知识为空 | 从工程配置和产品入口识别部件；有真实需求用它，无需求取仓内一个有实际调用的常规业务动作。 | 起步画像；对该动作和项目跨模块决定具有实际用途的能力、规约及有据适用的方法／模式。对会卡住首需求的缺口说明影响。 |
| 有正式知识、缺已适配版本 | 从基线逐主题查已有知识和真实源；保留能用的原文、编号和条目引用。 | 只补漏项、纠错、消重复；在原位合并登记。作者不推测游标。 |
| 已适配、收到版本变更 | 读有效版本差异、目标现状和受影响知识。 | 有变化才定向写／审；无适用变化且可读时允许零新增。有坏登记先交清楚具体缺件。 |
| 无依据或资料相冲 | 先查代码能回答什么，再查有权文档或人能回答什么。 | 已实现行为、已定业务责任、尚待裁决分别陈述。已有通路的部分继续；关键缺口不冒充首装就绪。 |

**作者方法全文的作业顺序（重写原“输入—步骤—质量判据—四格—交回”，删除其中的照样例列）。**

1. **画清一笔业务的责任。** 读当前请求、架构和入口注册，选一个常用动作。沿调用到直接决定结果、状态或外部交接的一方；再查相邻模块或失败分支，核排除范围。只记后面写知识用得着的源位置。有权文档和可执行代码回答不同问题：约定谁负责，与今天谁已接入，分开写。
2. **在定范围前先试证。** 对首需求的部件归属、公共能力、强约束分别问：“没有这条项目知识，下游会选错什么？”查真实调用和规范；用演进主题扫一个动作可能漏掉的隐私、兼容、发布等项目级约束。单模块私有规则、命名格式/lint 与无助于决定的细节从候选中移出。需要多步推导才选方法型事实；模式只走本版已定主题与实际使用的承载依赖。不以分类数量或 demo 文件名决定范围。
3. **用原有的一次范围确认定起步集。** 按主题报“适用及拟写内容／有据不适用及查过何处／缺口、影响及找谁补”。首批按每份最多三项挑高影响内容，规约先按领域归纳再选。未入首批但会影响下游的重要义务明示；长期扩充交本仓维护者。不用拆成多份文件规避上限，不要求人重复回答工程可证的事实。
4. **按第 4 节起草。** 先写业务判断，再写项目依据和边界；给出的源码位置要能找到，且打开后确能支持该结论。多人／多端协作写清结果由谁决定。条目写完才在根 manifest 登记；有一处权威正文即可，跨主题只引用。用项目读者的语言写正文，适配过程与待办放现有交回。
5. **作者自己用一次，再由现有独审独立用一次。** 对正常需求和一个改变命中条件的邻近需求，读者应能选对接口、责任和验证去向；条件不成立时应停止套用。第 5 节规定反馈与重审。保留原 check/status、摘要、部分完成及最终 mark 的边界。

## 模型实际收到的第一段话

以下三段定执行顺序与结束条件，分别替换各入口原有的知识作业正文。后续只读相应分支和主题；不要把整份设计对照表送给消费模型。

**首次 /story adapt 作者。** “先核实安装脚本给出的游标、已有知识和加载问题。现在要为这个项目写起步知识。选一个项目确实处理的业务动作，从谁发起追到哪一方给出结果，找出做需求时会判断错的责任、能复用的公共能力和必须遵守的约定。每个候选先开原件：在使用方读调用和依赖，在提供方读接口和限制，约束另查正式规范或有权决定。用主题页核有没有漏掉项目级要求；用现有盘点说清拟写、可排除和缺什么，按一次范围确认接着写。写成别人能拿去圈范围、定设计和做验收的内容。拿刚才的业务动作和一个条件变化的动作走读后，把知识、目标原件与需求交独审。”

**已有知识的升级作者。** “从脚本给出的已适配版本继续，查看晚于该版本的条目和当前加载错误。先打开已有知识，判断哪个业务结论会改变，保留仍有效的原文、编号和人工决定。无适用变化时交回零新增；无游标但已有知识时从基线核覆盖，沿用已有结论。涉及新增义务而项目依据不足时，说明影响哪个决定、由谁补证。只重审受影响的知识，完成条件具备后按现有脚本记版本。”

**独立知识读者。** “拿本次正常需求，先从目标仓给出你的业务判断和源位置，然后用作者的知识再作一次判断。点出会选错的承担者、误用的能力、遗漏的条件和没有采用证据的模式。对错处给出所在文件、错误动作、可核依据和要修改的正文；对作者根本没写的关键项也给出影响。逐份复核粒度、用途、重复和编码边界，在现有报告里分别填结论与 blocking。已定范围正确、关键判断有据且读者能用时才接收。”

**交回时看见什么才叫照方案做了。** 在同一目标里，若模块 A 已声明对共享模块 B 的依赖、实际从 B 导入组件，而应用壳层 C 只有相似资源名，合格稿应写“该业务向 B 取公共能力；C 的同名资产限壳层”，并指明定义与调用；没有权限文件时，不能从这个调用推出“该业务有权把用户数据发送到 C”。这组对照只供维护者验读。若执行者交回的是增加一个“请务必核实”的通用句，或保留原来的列目录顺序让模型自己想内容，视为未实现本设计。

## 4. 四种成品的具体写法与拒收对照

继续使用现有 frontmatter（name、kind、form、applies_when）、章节、条目编号、结构检查与下游引用合同。本节控制**正文说什么**。下面的成稿片段是维护者对照，禁止原样注入通用产品。

**项目事实 · 分面。** 一个二级标题回答一类查找问题，每项用短句给出“有什么、项目位置、怎样用、何时不能用”。部件画像先给一句边界和上游别称，再列实际协作方、本端职责和交接结果；能力面只收跨需求可用的入口。能指到一个定义只能证明它存在；声称“本模块应复用／已在用”要有依赖或调用与适用条件。拿掉类内部调度过程。

- 退稿：“资源由 Phone 统一提供；先查 Phone。”依据只看见壳层有资源目录，不能推出其他模块的依赖。
- 可接受：“共享主题色从 CommUI 的 `resources/base/element/color.json` 查已有 `comm_*` 键。WalletMain 已依赖 CommUI，添卡页面通过该模块使用 SectionCard。页面私有资源仍查本模块，Phone 的壳层资源按壳层使用。”依据分别核架构职责、两端模块依赖、资源文件和真实调用。主题色与 SectionCard 是分别有据的两个事实，不由组件调用推断某个颜色键已经被该页面使用。[模块职责](../../../../demo/doc/architecture.md:94) · [真实调用](../../../../demo/02-Feature/WalletMain/src/main/ets/presentation/pages/AddCardEntryPage.ets:36)

**项目方法 · 上下篇。** 上篇从“解决哪个业务判断、何时不适用”开始，沿输入、选择、结果给出可重复的推导，结束处有下篇可接的结论。下篇逐项给值：项目调用入口、值从哪里来、何时能取得、责任人或合法缺值、怎样验。方法要能迁到另一笔业务。拒收“接埋点 SDK、填事件 ID、测成功率”这种目录式说明。合格的写法会解释：若本端只见已受理，其记录仅能支持受理结果；若另有权威完成回执，才可用该回执设计完成率，重试按项目口径计次数；未知编码指回登记者。用目标项目的真实字段展现此推导，下游能得出结果的来源；无方法依据时不编数字、渠道或下篇。

**项目规约 · 条目。** 先按同一决策与业务结果聚类，合并同一条件、同一责任、同一验法的规范片段；若权限、例外或验收主体不同会改变下游处置，应拆开。每项按 protocol 既有列写编号、约束、强制力、命中条件、处置、验证及适用时的探针。强制力来自规范或有权确认，已有做法仅用于核目前落实。落法附注只解释该条容易误读的例外。作者不得为凑上限把五项独立义务压成含糊的一句。
- 退稿：“手机号要脱敏；日志不许打手机号；UI 不许打手机号；所有请求也传掩码。”前几句按载体反复抄，末句改变了业务接口含义。
- 合格的**内容形态**：目标协议允许某受权对端用原始标识履约时，写明对端及授权用途；展示／日志进入渠道前另生成展示值或排除该字段。核调用方和实际输出两种流向；没有受权协议时就不能写允许传原值。脱敏封装的名称及调用位置放能力事实，只在规约引用。若义务只是人工归档，按已有评审动作交人工，不造代码义务。

**设计模式 · 上下篇。** 只评批准的流程编排和页面交互两个主题。先从目标实际依赖及使用处证明承载能力，再以业务信号判断本需求可否采用。流程编排上篇讲何种分支、失败与恢复值得采用，给线性单步的反例；页面交互上篇讲异步回执、等待/恢复与用户动作怎样交接，给独立按钮的反例。下篇用真实承载库的行为写角色职责、项目落点、最小协作顺序、接口约束和可观察完成条件；注明哪些是库保证，哪些是项目约定。保留协议要求的 roles、coordinator_role 及适用信号。已有使用、候选用法和本工程尚无实例分开写。仅有普通业务代码相似、声明了依赖但未证实际使用时，不能造“项目惯用模式”或从单个私有模块自动归纳第三种模式。

## 5. 独审与验收必须怎样区分好坏

**知识审查的整项任务。** 先把目标根、已定范围、原需求、激活知识和当前摘要交给原有独立读者。读者先在项目源中独立回答：谁承担关键结果；哪项能力可复用；哪个条件会改变允许的处理；有何证据或缺口。再逐份核四项历史判据：粒度是否归纳、事实能否指导用法、是否跨文件重复、是否误收编码规范；另查上述关键答案有没有在整套稿件中漏掉。举出具体错句／漏项、依据、造成的错误动作和需要返修的知识。错误公共依赖、虚构权限、无据采用模式、漏掉会改变验收的条件进入现有 blocking；对应文件用既有 FAIL 维度，整套缺项记 blocking 即可。仅措辞或非关键扩充建议才留 WARN。继续用既有证据块、独立角色、当前摘要与重审流程，不增加一个评分器或评审角色。

| 评测输入（仅维护域） | 必须看到的产物和下游区别 |
|---|---|
| 一个空知识的真实陌生工程，固定版本、业务输入和模型；优先非 ArkTS、非钱包，模型看不到 demo、历史成稿和校准答案。 | 评审先从仓内原件独立封存本题关键责任、公共能力、真实规约、可用／不适用的模式和外部未知。保留作者实际读面、范围、首稿、独审原文、改稿及用时；实际阶段读者按稿找对责任、入口与验法。 |
| 同一目标中改变一个有实际依据的条件，如观察性输出改成受权业务调用，或复杂交互改成单步。 | 作者／读者分别给出不同处置并能回到源证；只换名词仍照搬原方案算失败。用上节的四种历史坏稿及四条人工反思逐一检查；缺可用条件应有据不适用，不能因为某格没有文件扣分。 |
| 已有知识无游标、已适配且零有效差异、已适配且有新义务。 | 分别能保留并补判、零新增结束、只改受影响条目；文件变更后旧报告失效，实际下游读新版，游标由现有脚本最后落盘。 |
| 退场后的可复现发行。 | 从干净提交打包，外网与内网包均无成品 examples；正式入口、加载器、脚本输出和测试不引用已删文件。合法目标自己的 examples／人工 .gitignore 不受破坏。 |

**质量判定。** 对每个预先封存的关键判断逐个比“目标原件 → 作者首稿 → 独审纠正 → 最终知识 → 下游决定”。记录正确、错误、漏项、或有据缺口及实际影响。陈述首稿与终稿各自的问题。影响业务行动的错漏必须修至独立核验通过；不能只看 Markdown 格式、文件数、例子相似度或“审查通过”的自报。保持原定同目标对照，缺改前真实原件时据实记录，只判绝对质量、不报提升幅度。S12 能冻结用于测试的候选；正式认可 example 退场与发布，须有获准最终窗口的陌生仓首装行为证据。现有 demo 升级和手工构造稿仅证明各自局部行为。
