## 待维护设计者确认的三项问题

### Q1（S09 / S10–S11）：为什么 2.0.6 目录调整仍对 Framework 有依赖？未到件前 04 批怎么推进？

- **用户原话**：“怎么还对framework有依赖呢？请跟设计者确认”
- **已查原件与源码位置**：
  - [S09-核定宿主首装的正式接点.md](../04-批次-三方发行与就地适配/S09-核定宿主首装的正式接点.md#L19-L24)、[draft/2026-11-23-目录调整与就地适配.md](../../../spec/2.0.6/draft/2026-11-23-目录调整与就地适配.md#L59-L78)、[test/config/framework-under-test.json](../../../../test/config/framework-under-test.json)（当前 pin `900c508d`）。
  - 当前未改动的 Framework `900c508d` 存在两处硬限制：
    1. `extension-loader.ts` 读取 `doc/extensions/manifest.yaml` 的 `provides.skills` 时，只接受纯 ID 数组，并写死到扩展根下的 `skills/<id>/SKILL.md` 校验；把 Skill 搬进 `doc/extensions/base/skills/<id>/SKILL.md` 且撤掉旧 `doc/extensions/skills/` 后，加载器直接报 `skill_missing` 导致整包失效。
    2. 项目级 `framework-init`（CREATE/UPDATE）只渲染 `AGENTS.md` 等工程说明，不在收尾自动调用扩展 Skill 跳板物化器，因此干净工程跑完 `framework-init` 后宿主里还没有可调用的 `/story`（从而无法直接执行 `/story adapt`）。
  - S09 修订 2 已用隔离原型验证了需要 Framework 上游做的两处改动（支持 `base/skills/` 注册清单 + `init` 收尾自动物化跳板），但该改动尚未进入正式上游 Framework 发布件。
- **对实施的影响**：
  - 如果在主线 `story` 把 `extensions/` 迁移进 `extensions/base/` 而测试 pin 仍是未改 `900c508d`，`verify.py handback`、`failure-modes` 和模板装配中的原生加载器会直接报 `skill_missing`。
  - 同时 S10 的包元数据 `provides.skills` 登记写法、S11 的 `composeManifest` / `entries.mjs` 都直接依赖上游最终接纳的注册语法（原型用的是 `base/skills/registered.yaml`，尚未正式定案）。
- **请设计者确认**：
  1. 向用户明确说明：2.0.6 是否确定等上游 Framework 接入这两处正式能力（还是有不改 Framework 的替代方案，例如接受变更目标边界）？
  2. 在上游正式发布件与语法合同到件前，执行者的施工边界是否确认为：**01–03 批（S01–S08）在现有目录坐标上完成并合入 `story`；04 批仅先做 S10 物料盘点与 S11 独立的工程根/子工程 Git 脏检查，S10 目录搬迁及 S11 依赖正式注册语法的 manifest 合并/物化待上游到件后再合入**？

### Q2（S05）：`review-object.mjs` 中“蓝图未采用的库存原件与上游原始文档”是保留绑定还是移出？

- **已查原件与源码位置**：
  - 现行实现：[review-object.mjs](../../../../extensions/skills/story/scripts/core/story/review-object.mjs#L139-L142) 把材料清单里登记的全部原件与阅读稿（含蓝图未引用的材料）均标为 `required_read: true` 并纳入 `material_key` 摘要计算。
  - 2.0.6 方案：[S05-独立读稿及报告接收.md](../02-批次-蓝图裁决与独立成文/S05-独立读稿及报告接收.md#L7) 要求把 Story 独立审查从“第二轮通盘核材料取舍”收窄为“先读 Story，再核有效事实/蓝图/固定人答与必要依据”，并“区分材料身份绑定与必须逐份阅读”。
- **不同处理的影响**：
  - **方案 A（建议）**：蓝图未采用的库存原件与上游原始文档**保留在 `material_key` 绑定集合里，仅将 `required_read` 改为 `false`**（任务书里归为“按疑点回查索引”，不再要求独审逐份必读）。影响：既减轻独审通盘读料负担，又能保证如果上游补录/修改了某份原始材料，旧 Story 审查报告不会静默沿用 PASS。
  - **方案 B**：直接**移出 `material_key` 计算**（只绑定 Story、写作设计、蓝图、固定人答/改稿原件、更新笔记及蓝图实际采用版本）。影响：若上游更新了一版未被蓝图引用的材料，Story 审查对象的 `material_key` 不变、不触发重审（仅在蓝图改动后才失效）。
- **请设计者确认**：按方案 A 还是方案 B 实现？

### Q3（S06）：蓝图 `questioning` 动作的知识原文投送范围，以及 Schema 组排除 `units` 的 `target_refs` 形态

- **已查原件与源码位置**：
  - [knowledge-task.mjs](../../../../extensions/hooks/shared/knowledge-task.mjs#L39) 当前对 `discovery / design / questioning` 三个蓝图动作一律传 `related = null`（全送 13 份原文）。
  - [knowledge-application.mjs](../../../../extensions/hooks/shared/knowledge-application.mjs#L81-L87) 使用 Framework 原生 `lite-json-schema.ts` 的 `auditSchemaSupport` 校验 [knowledge-application.schema.json](../../../../extensions/skills/story/contracts/knowledge-application.schema.json#L20-L33)。
  - [S06-动作前知识与承担实体.md](../03-批次-知识与施工接续/S06-动作前知识与承担实体.md#L7-L9) 要求：`design` 承接 `discovery` 有效版本只展开新增/变化/争议；独立质询“仍按实际问题读原件”；schema 接受互斥的单项 `unit` 与组 `units`（组仅用于 `not_applicable`）。
- **不同处理的影响**：
  1. **`questioning` 动作送多少正文**：
     - **选项 A（建议）**：`questioning` 保持全送原文（或与 `discovery` 同等全送），保障独立质询能发现作者漏判的规约/模式；仅 `design` 按有效判断+新增/变化/争议收缩正文（保留全部索引行）。
     - **选项 B**：`questioning` 也与 `design` 一样只送相关/新增/变化/争议原文，其余由质询者看索引后自行按路径读原文。
  2. **Schema `units` 组排除分支的 `target_refs` 约束**：
     - 为兼容 `lite-json-schema`，拟用 `oneOf` 拆为“单项 `unit`”与“组 `units`（`minItems: 1`，`outcome: const not_applicable`）”两分支。
     - **选项 A（建议）**：`units` 分支允许省略 `target_refs`（与现有域级 `not_applicable` 形态一致，且禁止写非空 `target_refs`）。
     - **选项 B**：`units` 分支要求显式写 `target_refs: []`。
- **请设计者确认**：两处各选哪一项？
