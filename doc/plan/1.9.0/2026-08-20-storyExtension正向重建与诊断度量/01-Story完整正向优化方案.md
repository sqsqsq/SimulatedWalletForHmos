# Story 完整正向优化方案

> 状态：已实施并通过离线验证；Story CLI 行为与语义质量尚未实跑
> 本文件只定义 Story 的输入、目标结构、模型写作、装配、Review、迁移和验收。  
> 工程 Knowledge 与 ADAPTATION 见 [02-Knowledge与ADAPTATION正向重建方案.md](02-Knowledge与ADAPTATION正向重建方案.md)。

## 1. 根因和目标

当前致命错误不是 Story 要“面向人类”造成的，而是章节合同同时规定了两件不该绑在一起的事：输出章要回答什么，以及输入必须从哪个文件、哪个标题取得。测试 Case 的文件名、标题和内容分配方式因此变成生产协议，内网材料只要换一种正常写法就会被判缺失。

人读优化又暴露了另一条独立问题：把标题、表格和篇幅变少当成优化信号，会在去重复时删掉唯一事实；只追求内容齐全，又会把同一条业务路径在流程、功能、异常和验收中反复叙述。

本轮目标是同时成立四件事：

1. 输入宽容：全部实际需求材料进入作者上下文，不做脚本级语义分章；
2. 内容守恒：同一版本的每个有效事实和编号都有落点；
3. 叙述经济：每个事实只有一处完整主叙述；
4. 输出稳定：最终 Story 使用已确认结构，装配和 Review 的确定性能力不回退。

## 2. 三份产物的职责

| 产物 | 主要读者 | 唯一职责 |
|---|---|---|
| `spec/spec.md` | Plan、Coding、UT 等后续 AI | 无歧义地定义实现要求、技术契约和验收口径 |
| `AR/story.md` | 人类评审者 | 独立讲清完整需求、当前特性、方案、失败恢复、验收和交付 |
| `AR/review.md` | 人类评审者和开发团队 | 收拢需要表态的已定或开放决定，保留人工确认结果 |

Story 不是 Spec 摘要，也不是当前模块的局部实现说明。评审者不打开 RR、SR、AR 或 Spec，也应能理解完整需求和当前特性在其中的位置。Story 只重组和解释已有事实，不创造新需求。

Review 不重复需求正文。已确认取舍的完整理由在 Story 的业务对象处讲一次，Review 只保留决定标识、当前结论、依据摘要、责任人和表态位；开放问题只进入 Review，不生成“待确认事项”正文章。

## 3. 输入：全部读取，但不混版本

### 3.1 两个时点的输入

Story 流程有两个取材时点，不能混为一谈：

| 时点 | 实际输入 | 用途 |
|---|---|---|
| Story 初始化与范围收口 | 当前 feature 的 RR、SR、AR 现状、`AR/upstream.md`、UX 和经导入链规范落位的补充材料 | 判断材料是否齐全，形成当前 AR 范围和 `AR/design.md` |
| Spec 完成后的 Story 成文 | 同一轮上述材料、最终 `spec/spec.md`、`acceptance.yaml`、decisions v2 和 ids v1 | 形成完整 Story、Review 和机械追溯 |

Spec 可以提供本轮收口后的功能、异常和契约，但不能以自身证明内容完整。作者仍须回到同一轮 RR、SR、AR 和 UX 核对业务价值、全局方案、被否选择、无编号事实、图片和跨特性关系。

### 3.2 材料发现只做机械工作

复用现有 `import_sources.py`、feature 路径配置和共享路径解析。材料发现只负责：

1. 解析 `features_dir` 和当前 feature；
2. 枚举导入链已经支持的 RR、SR、AR、`AR/upstream.md`、UX 和补充材料；
3. 按安全路径、支持格式和稳定顺序返回实际存在的文件；
4. 检查本地图片存在且不越 feature 边界；remote/data 图片不联网；
5. 将实际路径交给模型，并继续使用 `context/facts.md > key_inputs_read` 记录读取事实。

材料发现不得：

- 根据文件名、标题、关键词或正文内容判断属于哪一章；
- 选择 primary/supporting source；
- 截掉它认为不重要的段落；
- 把历史 Story、旧成功产物、测试判据或 Extension Knowledge 当需求事实；
- 以“整篇 fallback”掩盖本应报告的真实缺料。

### 3.3 版本一致性

作者开始成文前必须确认本轮输入属于同一需求版本。不同轮次或不同版本的材料不取并集，也不自行选择“较完整”的一版。

同一轮 RR、SR、AR、Spec、Acceptance、UX 或已确认决定之间仍有互斥内容时，模型不得覆盖其中一方或自行解释成一致。应把双方来源位置、冲突内容和影响登记到现有 decisions v2，并渲染进 Review。未受影响的内容可以继续形成草稿，但 Story 不得定稿，归档检查不得通过；人给出结论后，先修正对应真源，再重新生成 Story/Review。这里复用现有决定与 Review，不新增冲突台账或生命周期状态。

历史 Story 只用于实施后发现退化，不进入正常作者输入。图片和原型同样受版本约束：与当前 RR、SR、AR、Spec 的范围或流程冲突时不能嵌入 Story。

本轮不新增 `story-sources.json`、`source-inventory.json` 或其他持久来源台账。来源事实已经由工作区、导入链和 `context/facts.md` 表达。

## 4. 输出：以目标结构为唯一依据

[06-Story目标结构.md](06-Story目标结构.md) 是最终 Story 结构的唯一方案依据。固定二级顺序为：

1. 背景；
2. 术语；
3. 范围；
4. 业务方案；
5. 业务流程；
6. 功能说明；
7. 异常与恢复；
8. 验收；
9. 交付与上线；
10. 附录。

### 4.1 原 14 章的内容归宿

新结构删除的是重复或割裂的独立叙事位置，不是内容类别。原 14 章中的有效内容按下表进入新 10 章：

| 原章节 | 新结构中的完整归宿 | 调整理由 |
|---|---|---|
| 背景与目标 | 背景；可验收的目标进入验收 | 先说明为什么做，再在验收中说明怎样证明目标达成 |
| 术语 | 术语 | 理解正文必需的概念仍独立保留，并固定在背景之后 |
| 完整用户旅程 | 业务流程；当前特性细节进入功能说明 | 完整路径只叙述一次，当前特性的页面和动作另行展开 |
| 全局方案与参与方 | 业务方案；特性责任进入范围 | 把“怎样协作”和“谁负责什么”分开，避免一张参与方表反复出现 |
| 范围、边界与依赖 | 范围；交付依赖进入交付与上线；精确模块边界进入附录/工程范围 | 正文保留评审边界，附录保留工程查询细节 |
| 场景与功能 | 功能说明；可观察结果进入验收 | 功能正文讲行为，验收只讲通过条件 |
| 页面、组件与状态 | 用户可见页面和状态进入功能说明；跨阶段状态变化进入业务流程；组件落点进入附录/工程范围 | 人读行为与工程落点分层，但两类事实都保留 |
| 业务流程与状态变化 | 业务流程；异常停点和恢复进入异常与恢复 | 合并与完整用户路径重复的叙述，保留状态变化和失败出口 |
| 方案取舍 | 随对象进入业务方案、功能说明或交付与上线 | 让“采用什么”和“为什么”相邻，不再把理由与方案拆开 |
| 技术与数据约定 | 接口、数据与配置、事件、工程范围等附录；影响业务判断的部分留在正文对象处 | 精确契约便于查询，业务影响仍能被评审者直接看到 |
| 异常、恢复与风险 | 异常与恢复；风险随业务方案、具体功能或交付归位；未决冲突进入 Review | 异常集中查找，风险紧邻其影响对象，不新增孤立风险章 |
| 影响面与合规 | 功能说明、验收中的整体质量、交付与上线及附录追溯 | 按“影响什么、怎样检查、怎样交付”分别落位，避免空泛汇总 |
| 质量与验收 | 验收；精确编号关系进入附录/追溯 | 保留产品、特性、跨特性和质量的不同责任与观察层次 |
| 上线与协同 | 范围中的相关特性；交付与上线 | 稳定责任关系归范围，真实联调、开放、观察和回退按时间归上线 |

因此，14→10 不能只靠标题对照验收。它还必须通过第 10.4 节的固定快照全量事实核对，才能证明某一轮实际内容没有丢失。

### 4.2 新结构的职责

这十个二级标题负责让读者定位，不是内容压缩指标。三级、四级标题由实际业务阶段、功能、分支和验收场景产生，不预设数量，不为了对称生成空节。

各章唯一职责如下：

| 章节 | 完整回答什么 | 不重复什么 |
|---|---|---|
| 背景 | 用户问题、业务价值、完整需求目标和当前特性所处位置 | 不提前展开范围表、页面和接口 |
| 术语 | 理解后文必需的业务词和易混概念 | 不放模块映射、置信度等机器列 |
| 范围 | 当前特性和相关特性的拆分原因、职责、交接、顺序、上下文生命周期和阻塞关系 | 不重复业务规则和系统协作方案 |
| 业务方案 | 怎样解决问题、参与方怎样配合、各自输入输出、失败影响、结果真源、重要规则、方案取舍和相关风险 | 不重复特性责任表或页面操作 |
| 业务流程 | 完整需求从开始到最终结果怎样推进、全部有效业务分支和特性交接点 | 不展开当前特性的每个页面字段和按钮 |
| 功能说明 | 当前特性负责的页面、场景、动作、状态、正常分支和直接相关风险 | 不重讲完整跨特性流程 |
| 异常与恢复 | 真正异常发生在哪里、用户看到什么、业务停在哪里和如何恢复 | 不把身份未完成、资格不符等正常业务分支再抄一遍 |
| 验收 | 按真实业务场景给出可观察通过条件，每个原始编号独立一行，质量要求标明上游来源或已确认工程设定 | 不重复正文中的原因和方案论证 |
| 交付与上线 | 真实依赖、联调、开放顺序、开关、观察、翻译、资料、回退和相关风险 | 不重列范围和完整验收 |
| 附录 | 接口、字段、错误码、数据、配置、事件、工程范围、追溯和来源 | 不建立第二份业务叙述 |

相关特性只在确实存在拆分时生成。单特性场景不保留空的“相关特性”内容；多特性场景必须让读者独立理解为什么拆、谁先谁后、交什么结果、共享状态何时建立和清理、谁阻塞联调或正式开放。

## 5. 模型怎样写

[05-Story面向人类写作与语义验收规则.md](05-Story面向人类写作与语义验收规则.md) 是运行期模型指令和语义评价的设计依据。模型按以下顺序成文：

1. 先读完同一版本的全部输入，不边读边写；
2. 在内部列出有效事实、编号、限定条件、否定条件和已确认决定；
3. 为每项指定一个主落点，并标出只需在验收或附录保留精确值的内容；
4. 按 06 建立标题树，二级标题固定，H3/H4 使用当前需求的真实业务名称；
5. 先写连续主叙述，再选择确实有助于理解的表格、流程图、状态图或时序图；
6. 将字段级和契约级细节完整放入附录，正文保留它们对用户和协作边界的影响；
7. 将开放问题登记到 decisions v2，由 Review 提供表态位；
8. 对照全部输入做内容守恒检查，再做跨章重复、标题自然度和叙述顺序检查。

内部事实清单只服务本次写作，不成为新文件、状态或注册表。生产指令不出现 AR90004 等演示编号、业务专属标题、接口名或历史事故叙述。

当前特性必须完整保留全部有效内容，包括页面、状态、规则、分支、异常、契约影响、质量和交付要求。兄弟特性只保留评审当前 Story 所需的拆分原因、职责、交接结果、依赖顺序、共享状态或上下文生命周期和阻塞关系；不复制兄弟特性内部的页面字段、接口实现和独立验收细节，除非它们直接改变当前特性的边界或交接结果。

## 6. 输出型章节合同

`story-chapters.json` 升级为纯输出合同。每个 chapter 只保留：

- 稳定 `id`；
- `title` 和顺序；
- `reader_question`；
- 内容 `boundary`；
- `expression_hint`。

目标 ID 与标题固定为：

| ID | 二级标题 |
|---|---|
| `01-background` | 背景 |
| `02-terms` | 术语 |
| `03-scope` | 范围 |
| `04-business-solution` | 业务方案 |
| `05-business-flow` | 业务流程 |
| `06-feature-details` | 功能说明 |
| `07-exception-recovery` | 异常与恢复 |
| `08-acceptance` | 验收 |
| `09-delivery-rollout` | 交付与上线 |
| `10-appendix` | 附录 |

删除 `sources`、`inputs`、exact/regex/heading path/whole selectors、primary/supporting、`already_explained` 和章节输入命中检查。`spec_shape` 也从章节合同删除；现有 Spec 编号和术语表解析迁入 Story 脚本内部的 `scripts/lib/spec-shape.mjs`，由 `story-build.mjs` 与 `merge-story.mjs` 共同调用。这个模块只集中既有解析代码，不提供新的外部配置、合同、台账或状态。

确定性脚本只检查章节、登记表、图片、编号、引用、重复决定投影、路径和发布安全。事实是否完整、标题是否自然、归章是否合理、是否存在重复叙述由独立 Verifier 判断。

## 7. Scaffold、Build 与 Review

### 7.1 Scaffold

保留现有命令入口。scaffold 在单次命令中：

1. 在 feature 内临时位置生成十个章节任务书、decisions v2 和 ids v1；
2. 每个任务书只写全局材料清单、读者问题、内容边界和表达提示，不分配章节输入；
3. 校验 schema、路径和必需文件；
4. 全部通过后发布到正式 `AR/story-src`；
5. 失败时保留原工作区，不留下会被后续当成有效工作区的半成品。

`story_flow.py` 已有侧车仍由原流程维护，scaffold 不整体替换其目录，也不新增 workspace ready 状态。

### 7.2 Build

build 只消费章节作者区、decisions v2、ids v1、当前 Spec/Acceptance 和已有 Review 人工响应：

1. 在内存中解析全部输入；
2. 渲染临时 Story 和 Review 机器区；
3. 检查章节顺序、决定唯一投影、原始验收编号、图片、Spec 标识和 Review 决定集合；
4. 两份临时产物都通过后才替换正式 Story/Review；
5. 替换失败时恢复命令开始前的两份文件。

build 不判断文章是否“像人写的”，不引入 build_id、workspace marker、第二套 receipt 或新的生命周期状态。

### 7.3 Review

Review 保持两类所有权：

- 机器区由 decisions v2 确定性生成；
- 人工响应按稳定 decision ID 归并并由人填写。

外部需求系统回稿先作为临时输入解析，解析成功后只更新人工字段；解析失败不覆盖 canonical Review。往返合同使用可见稳定标题和 decision ID，不把 HTML 注释作为唯一边界。

未归档且人明确把状态改回 draft 后可以重建；已归档继续遵守现有 archive/restore/review 语义，本轮不增加评审轮命令。Story 正文不出现“待确认事项”章节或要求某角色拍板的议程措辞。

## 8. 一次性迁移

v4 工作区迁到新输出合同时：

1. 完整备份原章节和登记表；
2. 只剥离已知生成任务书区域，作者正文逐字保留；
3. decisions v2、ids v1 直接保留；更老登记表只在无歧义时一次升级，冲突项交人处理；
4. 生成新章节任务书，将旧作者正文按语义归入新结构；
5. 用新 build 生成 Story/Review，并对照旧稿和当前来源做事实守恒检查；
6. 迁移成功后删除旧 schema 读取、selector 实现和“selector 失败即正确”的测试。

不长期双读 v4/v5，不用 fallback 保留错误机制。迁移报告只记录备份、hash、迁移结果和人工处置项，不成为运行时真源。

## 9. Story 与工程 Knowledge 隔离

Story 的正常执行只读需求材料和评审输入，不读 Project Facts、Constraints 或 Patterns。Story Skill、rules、reference 和 Spec Story 注入件中对 `component-profile.md`、`codebase-facts.md`、Knowledge README 或具体模式的静态直链全部退出 Story 路径。

工程知识从 Spec 阶段开始生效。若工程事实证明需求范围或验收必须变化，按 Framework 修正三问回到 Story/Spec 的责任层更新，不能在 Story 生成时暗中裁剪需求。

## 10. 验收

### 10.1 输入与反过拟合

- 同一业务事实使用不同文件名、标题、顺序和自然叙述时都进入作者上下文；
- 删除旧 Case 的任一 selector 标题但保留事实，不再因标题未命中失败；
- 未知补充文件经现有导入链规范落位后进入全量材料，不被静默忽略；
- 不读取 `test/story`、历史输出、Demo Knowledge 或旧 Story 来补需求事实；
- 同一轮素材冲突时登记现有 decisions v2 和 Review，Story 定稿与归档检查保持阻断，模型不自行拼接或选择版本。

这些机械变形测试直接看护生产合同。另按 04 构造覆盖 Story 功能的多场景需求 Case 和同事实叙述变体；当前执行者只用离线检查验证 Case 可独立装载，不执行任何 Story CLI 测试。

### 10.2 结构与确定性能力

- 最终二级结构和顺序与 06 一致；H3/H4 使用真实业务名称，无模板占位标题；
- decisions v2、ids v1、Review 人工区、图片和现有 CLI 能力通过；
- 每个原始验收编号独立保留；
- 缺材料、非法图片、登记冲突、重复投影和编号断链在发布前失败；
- scaffold/build/review 失败不破坏上一次有效产物或人工响应。

### 10.3 人读语义

按现有 Story 真值标准逐字评价：

- S1：不打开外部文档也能理解并评审；
- S2：编号事实和无编号事实都没有丢失或走样；
- S3：按“为什么、是什么、怎么做、哪里会失败、怎样验收”推进；
- S4：关键选择包含采用方案、被否方案和理由；
- S5：正文、表格和图各自用于适合的信息关系；
- S6：开放问题和人工议程只进入 Review；
- S7：同一事实只有一处完整主叙述，没有无价值段落或表行；
- R1～R4：Review 可用于开会、逐项可答、有人工作区且不是第二份 Story。

脚本只给机械结果；语义通过必须由独立评价者对照当轮 RR、SR、AR、UX、Spec、Acceptance 和 Story/Review 原文取证。

### 10.4 内容守恒的全量验收

正式验收先固定本轮 RR、SR、AR、UX、补充材料、Spec、Acceptance 和已确认决定的输入快照，再逐项核对全部有效事实，不再只抽查 8 条无编号事实。核对范围包括：

- 所有原始编号和表格行；
- 业务规则、限定条件和否定条件；
- 数值、默认值、清理条件和失败语义；
- 图片、图中有效信息和全部有效业务分支；
- 已确认取舍，以及被否方案和理由。

本轮交付报告为每项记录“来源位置、事实内容、Story 或 Review 的唯一主落点、最终产物证据”。已确认事实以 Story 为主落点，开放冲突以 Review 为主落点；登记表、验收和附录中的短引用或精确投影不算第二份主叙述。

任一有效事实缺失、语义走样、限定条件变化，或在多个位置出现完整主叙述，内容守恒均判失败。该核对表只属于本轮交付报告，不进入 feature 工作区，不新增运行时台账，也不成为下一轮写作输入。

## 11. 受影响范围与完成判据

实施时允许调整：

- `doc/extensions/skills/story/` 的章节合同、规则、脚本和任务书；
- `doc/extensions/hooks/spec/story/` 中 Story 成文和机械检查相关注入；
- `test/story` 中直接验证 Story 生产合同的现有测试和文档；
- 已有 Story 工作区的一次性迁移工具或报告。

不允许调整 `framework/`、产品业务代码或新的通用协议；不得为了让测试通过而删改 Case 的有效事实、预写期望 Story，或把 Case 答案写进生产规约。

本方案完成必须同时满足：

1. 旧 selector/primary/Spec 形态镜像和相反测试已删除，不存在双读；
2. 06 的结构、05 的写作规则和本文件的输入/装配合同一致；
3. Story 守恒能力、Review 人工所有权、图片和现有 CLI 无回退；
4. Story 不直接消费任何 Extension Knowledge；
5. 机械门禁与语义 Verifier 各守自己的边界；
6. 固定输入快照的全量内容守恒核对通过，交付报告能逐项给出来源、唯一落点和产物证据；
7. 04 规定的 Extension 回归、多场景 Case 静态验收和当前范围 Framework 凭证全部通过；全部 Story CLI 实跑已在 07 中交接。
