# Story 测试现场延迟清理与稳定观测

## 1. 目标

本轮测试结束后保留隔离 workspace 和 `output/story/<suite-id>`，让测试现场至少存续到下一轮起跑。
下一轮在迁移 `doc/features` 前统一验证并清理历史现场。120 秒 Goal/heartbeat 只在全部 Case 连续两轮
15 秒观测均稳定处于 Spec 自动状态后启动。

## 2. 生命周期

新 suite 先创建自己的 output 控制目录，再扫描 `%TEMP%/sw-story/*` 和 `output/story/*`。只处理由
合法 `suite.json` 或 Story suite 名称证明所有权的直接子目录。已知 suite 必须终态且 worker 不活动；
孤儿目录必须通过进程命令行检查。软链接、越界、活动进程、未知所有权或进程枚举失败均阻止清理。

整体预检通过后先删历史 workspace，再删对应历史 output，逐项写入新 suite 的
`previous-run-cleanup.json`。全部成功后才迁移当前 `doc/features` 和创建新 workspace。删除部分失败时
拒绝继续起跑。`finalize --cleanup` 停用，本轮 finalize 只回灌、写报告并把现场标为 retained。

## 3. 稳定观测

Case 首次可靠进入 Spec 时记录 `spec_entered_at`。每轮 15 秒完整观测后统一评价全部所选 Case：均已
进入 Spec、非终态 Case 当前仍在 spec+、无等待回复且读取成功，才累计一次确认。连续第二次确认后写
`automation_stability.ready_at` 并切换 120 秒。等待回复、阶段回退或读取失败会清零并恢复 15 秒。

## 4. 验收

- finalize 后 workspace/output 均存在，cleanup 参数明确失败。
- 下一轮能够成对清理安全的历史现场，孤儿现场只有在进程检查通过后删除。
- 清理失败发生在 feature 迁移之前，新 suite 不启动 worker。
- 单次 Spec 观测不切换；连续两次才进入 120 秒，异常后可降级并重新稳定。
