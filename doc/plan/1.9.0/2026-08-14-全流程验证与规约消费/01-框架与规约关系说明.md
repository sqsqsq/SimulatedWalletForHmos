# 框架与规约的关系说明

> **写给谁**：在新会话里审视规约（`doc/extensions/knowledge/constraints/`）内容准确性的人与模型。
> 本文自包含，不依赖任何历史对话。只陈述事实与边界，改法由审视者定。
> 所有引证格式为 `文件:行号`，行号以 2026-08-14 的工作区状态为准。

## 1. 规约是什么

**落点**：`doc/extensions/knowledge/constraints/`——README + 9 个域文件。
`README.md:3-4`：「本目录是工程级的常驻约束知识，**也是这些约束的权威所在**——不是某份外部
文档的抄本。条目一律平权：写在这里就是规则，要改走评审改这里。」

**规模**：9 域共 53 条。

| 域文件 | 前缀 | 条目数 | applies_when |
|---|---|---|---|
| ux-consistency.md | UX | 7 | 需求含新页面/UI 改版 |
| run-modes.md | MODE | 3 | always |
| security-privacy.md | SEC | 7 | always |
| app-lifecycle-config.md | APP | 6 | always |
| dfx-baseline.md | DFX | 5 | always |
| telemetry.md | TEL | 4（TEL-02 缺号，全仓无废止说明） | 需求含流程/页面/逻辑改动 |
| compatibility-checklist.md | COMPAT | 11 | always |
| env-exceptions.md | ENV | 5 | always |
| deliverables.md | DLV | 5 | always |

**条目三要素**（`README.md:69`：「新增条目须同时给出等级与判定方法——没有判定方法的条目没法执行」）：

1. **等级**，三档有真实后果（`README.md:51-57`）：
   **红线**=阻断（命中未处置即评审驳回/门禁拦截，不得「后续再补」）；
   **基线**=须给结论（可不做，但必须写明为什么不做及补偿措施）；
   **建议**=可不做（无需理由）。
2. **判定方法**：怎么判断本需求命中/符合这条。
3. **applies_when**（域级）：什么需求需要过这个域。

**`<待补充：…>` 的语义**（`README.md:59-63`）：真实的空缺登记。判定时写「基准待补充，
按条目语义定性评估」，**不得臆造数值**；补齐的办法是在本仓填上，不是去别处找。
「本部件适用性」标**不适用**的条目不参与命中判定，但保留不删。

**出身**：九域 356 行系 2026-08-11 提交 `0304fd2`（feat(story): story 需求评审叙事能力）
**一次性建成**，为 story/spec 阶段服务；其中面向 plan/coding/review/ut/testing 的部分
（见 §2 适用矩阵）是同一次写下的**设计意图，至今无实践验证**。

TEL 的埋点落实）才是真增量。

## 3. 内容与机制的边界（本文核心）

规约是**外挂**：单独维护、单独评审。两侧的改动归属如下，**设计不变量：改内容永远不需要动
任何 hook / overlay / skill 文件**。

| 改动 | 归属 | 由谁做 |
|---|---|---|
| 条目增删改、等级调整、判定方法补齐、`<待补充>` 填空、域文件增删 | **内容** | 规约维护者（即本次新会话） |
| 适用矩阵**格子里的维度文字**（某域在某阶段消费成什么） | **内容** | 规约维护者 |
| hook 挂载、overlay 门禁、README 里指向消费方的那几行、机械断言 | **机制** | skill/fram架侧（另行进行，见 §7） |
| 适用矩阵格子**有没有真实消费方落点** | **机制** | 同上（机械断言钉住） |

**边界的机械保障**：`test/story/tests/test_knowledge_purity.py` 断言知识文件里出现任何
消费方坐标（spec 章节号、`AR/story`、`AR/review` 路径、回显指引节等）即失败——
知识只答「约束是什么、怎么判断命中」，「哪个阶段怎么用」归消费方。
**审内容时请勿在域文件里加入消费方坐标**，会当场红。

## 4. 条目写作契约（改条目时的合格标准）

1. **等级 + 判定方法必填**（`README.md:69`）。整表缺列 = 该表不可执行（现状见 §5-1）。
2. **判定方法须可操作、可证伪**。
   正例：`app-lifecycle-config.md:15` APP-02 给出**反例判据**「只写『数据随账号同步』不算」
   ——把不可判的东西拉回可判；`app-lifecycle-config.md:19` APP-06 给出精确代码位置
   （`onCreate` / `onWindowStageCreate`（UI 内容加载在此，不在 onCreate）/ `aboutToAppear`）。
   反例：`dfx-baseline.md:28` DFX-03（红线）「后台禁止**不必要的**业务逻辑」——「不必要」
   无定义，判定方法只能判「有没有」，判不了「必不必要」。
3. **一问一 ID**。`compatibility-checklist.md:33` COMPAT-09 一条塞六个独立问题，
   输出却只有一个「命中/不命中」二值——六问一票，必然是最容易的那问决定结论。
   同病：COMPAT-01（4 问）、COMPAT-02（4 问）、COMPAT-07（5 问）。
4. **红线的门槛**：红线 = 门禁拦截。判定基准缺失的条目标红线，结果只有「阻塞一切」或
   「每次特批绕过」两种，后者顺带削弱其余红线的权威。**「红线 + `<待补充>` 判定方法」是
   最矛盾的组合**（现状 5 条，见 §5-2）。
5. **与 coding-standards 的分工**（见 §2.3）：已被它覆盖的不必在矩阵 coding 列重复。
6. **平台化**：条目价值与 HarmonyOS 贴合度强相关。写「布局用相对/栅格单位」不如写
   `GridRow`/`GridCol`、断点 `sm/md/lg`；写「以单调时钟为准」不如写
   `systemDateTime.getUptime(TimeType.STARTUP)`。
7. **事实与动作分列**：条目正文只写约束事实（「打点变更须说明改动点」），「通知谁确认、
   谁拍板」放独立列（协同动作/责任方）。混写会被消费方原样回显成议程措辞——
   消费方规则再多也只是事后拦截（实例见 §5-4-6）。

## 6. 一条现成的执行力证据

UX-01（红线）：色值走 `$r('app.color.*')`，同名 key 须在 base 与 dark 的 `color.json` 各配一份。
规则清楚、判定方法（比对两份 key 成对）有效。实测本仓（2026-08-14）：

| 模块 | base keys | dark keys |
|---|---|---|
| `01-Product/Phone` | 4 | **1** |
| `02-Feature/FinancialCard` | 7 | **无 dark 目录** |
| `02-Feature/WalletMain` | 25 | **无 dark 目录** |
| `05-SystemBase/CommUI` | 6 | **无 dark 目录** |

**42 个 key，41 个深色不生效。** 与此同时 AR90006 的 spec 与 story 都正确写着「base/dark 各一份」
（§2.2）。**规约的短板不在声明而在执行**——审内容时，优先保「判定方法可执行」，
措辞漂亮与否是次要的。

## 7. 机制侧正在做什么（避免两边撞车）

与内容审视并行，skill/framework 侧本轮（2026-08-14）在做：

1. **挂载**：一份 `hooks/constraint-application.md` 挂到 plan/coding/review/ut/testing 五阶段
   （manifest 五行指同一文件）；hook 正文零域名零维度，只指向适用矩阵；
2. **门禁**：`phase_rules_overlays.{plan,coding,review}` 各加一条指向矩阵的 semantic_checks；
3. **悬空修复**：`README.md:21` 指向已删除 hook 的那半句改为指向新 hook（**矩阵格子的维度文字一字不动**）；
4. **机械断言**：矩阵非「—」的格子必须有真实消费方落点，否则测试红；
5. story 侧：图片形态守恒、数值来源落笔冲突消解（与规约内容无关）。

**对内容审视的含义**：矩阵行列可以放心增删改（那是内容）；只要某格非「—」，机制侧的断言会
保证它有消费方。若审视结论是「某域某阶段不该消费」，把格子改成「—」即可，机制自动跟随。
