## 2. 用户拍板的三项决策

1. **叙事三层漏斗**:全局→本部件→本 AR。story 仍是本 AR 的评审叙事件,无拆分时第三层
   自动退化(本 AR=本部件全部),同一条规则不写分支——与既有「单 AR 时范围=全集」哲学一致;
2. **兄弟 AR 只结构化登记,不建产物**:兄弟各自走自己的 `/story init`;carrier 单号即未来
   跨 AR 协同的接口;
3. **本轮建 split 端到端 case**,正式跑与评测合并到规约内容落地后的复测。

## 3. 设计

### 3.1 契约 parts 结构化

```json
"split": {
  "decided": "split", "settled_round": 2,
  "scope_text": "挂失申请与状态展示(由脚本从 parts 推导,见下)",
  "parts": [
    {"seq": 1, "carrier": "AR90005", "scope": "挂失申请与状态展示(对照 SE §3-§5)", "depends_on": []},
    {"seq": 2, "carrier": "AR90004", "scope": "补卡链路与卡券恢复(对照 SE §6-§8)", "depends_on": [1]},
    {"seq": 3, "carrier": "待立项", "scope": "运营报表适配", "depends_on": [1]}
  ]
}
```

- `carrier`:本 feature 名 / 兄弟单号 / 「待立项」;**恰一个 = 本 feature 名**;
- `seq` = 建议执行顺序;`depends_on` = 硬依赖(须先交付),引用已存在 seq,禁自引、环检测;
- **`scope_text` 由脚本从 parts 推导**(取 carrier=本 AR 那份的 scope)——同一事实单一权威,
  消除「份表说 A、scope_text 说 B」;旧调用(`--scope-text` 无 parts)过渡期兼容;
- **输入走文件**(M4 纪律):模型定案后写 `AR/story-src/.split-parts.json`,
  `decide --chosen split` 读取→校验→写契约→**删侧车**(与导入回执同模式,一次性)。

### 3.2 初析第 5 节形态钉住(四段)

① 材料现状表(已有);② 缺口判断一句(已有);
③ **拆分信号逐条核对表** `| 信号 | 命中? | 依据一句 |`(三行:跨多业务模块/超长流程/
大颗粒分层——AR90004 那轮的好形态制度化);
④ 结论:「无需拆分」或 1–2 个候选;每个候选 = 拆分依据 + **份表**(序/承载建议/范围一句
对照 SR 章节/依赖)+ 推荐承载理由(依赖最少可先行,推导显式化)。
S3 关卡呈现的就是可直接定案的份表。

### 3.3 定案链与 §1.2 形态

S3 选拆分 → 子菜单呈候选份表 → 用户认可或修改 → 模型写 `.split-parts.json` → decide →
S4 按契约 parts 转写 design.md §1.2:

- 无拆分:「本 AR 承载全部需求,无拆分。」+ 范围句(现状不变);
- 拆分:「本需求拆分为 N 份,本 AR 承载第 k 份」+ 拆分表(序/承载/范围/依赖)+
  「本 AR 范围:…;范围外去向见上表」。

§1.2 定案后仍是唯一权威、契约转历史(现有机制不变)。post_check 对 §1.2 做**存在性**校验
(split 时含拆分表且每个 carrier 出现)——防漏不防抄错,抄错由 verifier 语义判,
不做脆弱的逐格文本比对。

### 3.4 三层叙事的章节落点(不加新章)

| 层 | 落点 | 现状 |
|---|---|---|
| 全局 | 04-global | 已有(rubric S3-3 在看) |
| 本部件 | 04-global 参与方/边界 | 已有 |
| **本 AR** | **05-scope** | 断链修复后由 §1.2 供给 |

- `rules.md` 第 9 条(独立可读)扩为:「…本部件只负责哪一段、**本 AR 承载其中哪部分
  (拆分时:兄弟 AR 各承载什么、先后与依赖)**、边界与风险在哪」;
- `story-chapters.json` 05-scope inputs 加 `{"doc":"DESIGN","section":["本 AR 范围与拆分说明","范围"]}`。

### 3.5 spec 一致性

- `hooks/spec/on_context_load.md`:「Scope 与功能清单的边界以 §1.2 为准:拆分表中归兄弟
  AR/待立项的功能**不入**本 AR 功能清单与验收;其涉及模块若须登记 out_of_scope,
  rationale 写明『归属 ARxxxx』」;
- `spec-rules.overlay.yaml` 新 semantic_check:「契约 split=split 时:spec 功能清单/Scope
  与 §1.2 拆分边界是否一致——归兄弟的功能未被纳入?范围外去向有归属?split=none 时 SKIP」。

### 3.6 决策六类与 rubric

- `rules.md` 决策扫描清单五类→六类,加「AR 拆分与承载」:**拆分与否都登记一条 settled**
  (question 固定形态「本 AR 是否需要拆分?各兄弟 AR 承载哪些部分?」——AR90006 的
  自觉实践制度化);rubric R1-4 同步六类;
- rubric 新观察点(split case 适用,无拆分 N/A):① 初析含逐信号核对;
  ② story 05 章兄弟清单+顺序+依赖齐备且与 §1.2 一致;③ review 含拆分 settled。

## 4. 兼容与明确不做

- 旧契约(split=none、无 parts)读取缺省 `[]`;post_check 仅 split=split 时要求 parts;
- 不建兄弟 feature 目录/产物;不做跨 AR spec 引用机制(carrier 单号即接口);
- 不做拆分历史/撤销(覆写语义保持);acceptance 不单独切分(spec 边界定了,验收自然只含本 AR)。
