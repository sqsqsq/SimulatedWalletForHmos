## 现状能力边界

- 测试驱动器（`test/story/scripts/run_case.py`）只驱动 story+spec：`:399-401` 三件套
  （spec/spec.md、AR/story.md、AR/review.md）一齐备立刻 break——**结构性阻断**，不是参数没开；
- `run_case.py:287` 门禁调用写死 `phase:'spec'`；`case.yaml` 无 phase 字段；
  `assert_story.py` 判据全部是 story/review/spec 三件套，无下游阶段判据；
- 实测成本：story+spec 单 case 37–40 分钟（AR90004 2369s/2 轮、AR90006 2231s/3 轮），
  单 case 工具调用 200+ 次、门禁往返 9 轮；全链保守估计 **4–8 小时/case**，
  超出现有 90 min 硬时钟（`config/test.yaml:22-23`）。

## 改造设计（重启时按此实施）

1. `case.yaml` 加 `end_phase`（缺省 `spec`，现有用例逐字节兼容）；
2. 终止条件按 end_phase 分段：spec 及以前沿用三件套；之后逐阶段以
   `check-receipt.ts --feature <f> --phase <p>` exit 0 为闭环判据（framework 钦定的跨会话判据，
   CLAUDE.md §五）；
3. 门禁调用按 phase 参数化，story 专属 mjs 仅 phase=spec 挂；
4. **源码复位**：起跑记录 HEAD 与 untracked 清单；复位 = tracked 走 git 恢复 +
   run 期间新增 untracked 按清单删除；现有 doc/features 守卫对 spec 用例不变；
5. **人工闸门自动应答**：GATE_REPLY 机制扩展至 B1/B3 等编号菜单；**报告须显式声明**
   此举掩盖「哪里真的需要人」的观测，逐次记录应答点；B4 visual needs_human 对
   vision none 用例按既有 visual-debt 登记路径走；
6. 时钟/轮次按阶段配置（coding 单独放宽）；
7. 编排（用户 2026-08-14 拍板）：用 **first-release（AR90003，首页快捷支付入口）**
   单用例跑全链，end_phase=review。选型依据：三用例中最简（单模块、无 docx 补料环节、
   mock 材料 104+138 行，约为 AR90006 的一半），且规约钩子齐全——UX（新入口/新页面）、
   TEL（`home_quick` 打点与报表口径）、MODE（未登录分支）、COMPAT（`SR-design.md:104`
   旧版本不解析 home_quick 来源）、DLV（新增文案）——story+规约的实际应用效果均可观测；
   附带收益：该用例当前无完整 run 记录，正好补上。AR90006 end_phase=review 作可选第二轮。
   逐阶段各写一份 `04-<phase>实测.md`，重点采集：
   - 该阶段 `ai-prompt.md` 是否含 `<!-- hook:on_context_load:extension:constraint-application.md -->`；
   - 产物中规约落笔是**增量还是复读**（对照 01 §2.2 的同句现象）；
   - 四件套闭环与人工闸门应答记录。

## 为什么遗留

规约消费效果的观测依赖：① 规约内容先经审视（用户新会话进行中）；② 消费机制先挂上（W3）。
两者未就绪时打通链路只能测出「悬空矩阵 + 未审内容」的效果，结论无效。W2/W3 与内容审视
完成后重启本项。
