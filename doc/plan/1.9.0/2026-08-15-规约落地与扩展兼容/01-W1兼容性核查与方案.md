# spec 阶段兼容性方案：让 story 扩展对非 story 场景完全隐形

> **性质**：方案，待评审。**未改任何文件。**
> **要解决的**：framework 已在真实代码仓被他人使用。老用法——口述一个需求或给一个文件，
> 直接跑 spec，无 `AR/design.md`、无 SR/RR、AR 目录结构不全——合入 story 扩展后会被硬阻断。
> **裁定**：非 story 场景下扩展应**完全隐形**，体验与扩展不存在时逐字相同。

## 1. 核查结论

### 1.1 framework 原生根本没有「三份产物」

| 项 | 原生 | 引证 |
|---|---|---|
| 产物 | **只有 `spec/spec.md` + `acceptance.yaml`**（UI 需求时加 ui-spec.yaml 等视觉件） | `framework/skills/feature/spec/SKILL.md:24-27`、`contract.yaml:13-18` |
| 输入 | **文字描述 / 界面截图 / 模块名**——正是老用法 | `SKILL.md:39`、`contract.yaml:7-9` |
| spec 章节 | 0–8 章 + 宿主扩展治理项 + 附录，**无 §9** | `framework/profiles/generic/skills/spec/templates/spec-template.md` |
| lifecycle hook | **零**——framework 与 profile 下都没有 `hooks/spec/` | 全仓 `post_check*` 唯一命中在扩展侧 |
| base 规则 | `applies_to` 只声明 spec.md；`story`/`AR/` 在 `framework/specs/phase-rules/` **0 命中** | `spec-rules.yaml:14` |

全仓 grep「三份产物/三份文档/产出三份」18 处命中，**framework/ 下 0 处**——该说法完全由
story 扩展引入。framework 自己的模板还写明流程性事项"不进 core 模板，由宿主叠加"
（`spec-template.md:257-261`），**即 framework 把这类东西定义为可选叠加层**。

### 1.2 三层的破坏力不同

| 层 | 无 story 场景的行为 | 强度 |
|---|---|---|
| `spec-rules.overlay.yaml` 6 条 | 4 条刷红（`spec_constraint_echo`、`spec_ext_conclusion_validity`、`story_reader_fitness`、`story_decision_substance`），2 条自带 SKIP | **MAJOR，只红不阻断** |
| `post_check.mjs` | 4 类检查中 3 类**无条件**命中 | **BLOCKER，硬阻断** |
| `on_context_load.md` | 无条件注入 121 行作业指令 | 引导性，但后果最重（见 1.4） |

overlay 层是**纯增量**：6 条 key 与 base 零冲突，不动 structure/traceability，
`profile-loader.ts:85-96` 的 spread 保证 base 40 余条一条不丢。**这一层不用大改。**

### 1.3 post_check 的四类检查，只有一类做了 gate

| # | 检查 | 位置 | 对老用户 |
|---|---|---|---|
| ① | 三份产物齐备（`AR/review.md`、`AR/story.md`） | `:191-204` + `:344-348` | **必然命中** |
| ② | story 流程契约 `AR/story-flow.json` | `:221-322` | **已 gate**——`:223` 文件不存在则 `return []`；`:213` 注释明写"没走 /story 的 feature 不受本检查影响" |
| ③ | §9 技术契约 + 五小节 | `:186-188` + `:353-373` | **必然命中**（core 模板本就没有 §9） |
| ④ | 术语表解释列 / 禁用词 / 禁文档坐标 / 数值来源 | `:386-469` | 部分必然命中——**老用户习惯写"见 §7.1"这类交叉引用会直接失败** |

**根因**：作者写 ② 时已经建立了正确的 gate 范式，并专门写注释解释为什么要 gate，
**但没把同一范式用到 ①③④ 上**。

**severity 的额外问题**：`post_check.mjs:474` 的 `severityOverride: 'BLOCKER'` 绕过了
framework 给 extension 层设的"只能 MAJOR"保险（`hooks-dispatcher.ts:48-50`），
把自己抬成硬拦截，宿主无处降级。

### 1.4 最危险的一环：脚本不崩，反而「成功」造空壳

`on_context_load.md:35-42` 有四条命令标着"AI 自跑，不得让用户手动跑"，模型读到就会执行。

而 `story-build.mjs` 的 `loadSourceDocs`（`:414`）对缺失源文档的处理是
`fs.existsSync(p) ? read : null`，随后只往 notes 记一句"源文档不存在，跳过该输入"
（`:439-442`）。**PRD/SE 全缺时 scaffold 照样成功退出**，在 `AR/story-src/chapters/` 下
建出整套空章节文件，再建 `decisions.json` 与 `ids.json`。

后果：模型面对空骨架，会把用户口述的一段话**硬摊成三份文档 + 一整套 AR/story-src/**。
用户要一份 spec，拿到一个需求评审套件，其中大部分内容是为填满章节骨架而生成的。
（唯一硬报错的是 feature 目录不存在：`:425` 的 `fail()` → `process.exit(1)`。）

### 1.5 一处语义冲突（不只是增量）

`on_context_load.md:120` 要求模型**自行补写并重排下一步**（必须以"人工评审 → 归档"为首选，
"进入 plan"只能作次选）；而原生 `SKILL.md:70` 与 `:99-101` 两处明确要求
**"只呈现 harness 的 NEXT_STEP 段落，不自行推导或补写跨阶段建议"**。这是直接冲突。

### 1.6 没有开关可关

framework 无任何扩展启用/禁用机制：manifest 无 `enabled`/`applies_when`
（schema `additionalProperties: false`）；`lifecycle_hooks_enabled` 是三层通杀且关不掉 overlay；
CLI 无 `--no-extension`；无环境变量；overlay 无删除语义；hook 返回值无 skip 语义。

**关键不对称**：`.mjs` 返回 `{ok:true}` 且不产 fragment = 事实上的 skip；
`.md` 走 `hooks-dispatcher.ts:162-166` **无条件读取注入**，没有判断余地。

framework 的设计前提是「**扩展不存在时零影响**」（`extension-loader.ts:5-6` 文件头注释），
不是「扩展存在但可被关闭」——story 扩展违反了这个前提。

## 2. 方案

**核心：不改 framework，让扩展自我限定。** 这与 framework 的设计意图一致。

### 2.1 场景探针

**判据：`AR/story-flow.json` 是否存在。** 它是 `/story` 流程创建的标记，
`post_check.mjs:213` 已确立此语义。

选它的理由是**探测用户意图而非模型产出**：用户走过 `/story` 流程就有这个文件，
那么即使模型偷懒没产出 story.md，门禁照常拦；用户从没走过，就直接放行。

⚠️ **实施前必须先验证**：`story-flow.json` 的创建时机是否早于 spec 阶段的
`on_context_load` 与 `post_check` 执行。若晚于，换探针——候选是 `AR/design.md` 存在，
或让 story skill 在 init 期落一个独立标记。**这个前提不成立则整个方案要改。**

### 2.2 四处改动

| # | 文件 | 改法 | 优先级 |
|---|---|---|---|
| 1 | `hooks/spec/on_context_load.md` → **改写为 `.mjs`** | `.md` 无法自我豁免。新 `.mjs` 探针未命中即 `{ok:true}` 静默让路；命中则读同一份 `.md` 正文注入。**正文内容零改动**，只加一层开关 | **最高**——它拦在最前面，不让模型去调 story 脚本，就不会产生空壳 |
| 2 | `hooks/spec/post_check.mjs` | 给 ①三份产物（`:344-348`）、③§9（`:353-373`）、④全文红线（`:437-469`）套上与 ② 同构的 gate | 高——这是硬阻断的来源 |
| 3 | `rules/spec-rules.overlay.yaml` | 4 条无 SKIP 的 check 补 SKIP 条件，写法照 `upstream_inputs_coverage:97` | 中——不阻断，但一堆红字会诱发软阻断 |
| 4 | `hooks/constraint-application.md` | 六阶段无条件注入，同样是 `.md`——**需单独裁决**，见 §4 | 待定 |

改动 1 的形态：

```js
// hooks/spec/on_context_load.mjs
const flowPath = path.join(featureRoot, 'AR', 'story-flow.json');
if (!fs.existsSync(flowPath)) return { ok: true };        // 非 story 场景，静默让路
return { ok: true, promptFragments: [fs.readFileSync(mdPath, 'utf8')] };
```

### 2.3 附带修掉语义冲突

`on_context_load.md:120` 的"重排下一步"与原生 `SKILL.md:70/99-101` 冲突，
应删除或改为仅在 story 场景生效——随 §2.2-1 的探针一并解决。

## 3. 验证

必须跑**两个方向**，缺一不可：

1. **老用法回归**：建一个只有 `spec/spec.md`、无 `AR/` 的 feature，
   跑 `harness --phase spec` → 应 **exit 0**，且 ai-prompt 中不出现任何 story 指令；
2. **story 场景不退化**：完整 story 流程跑一遍 → 三份产物检查、§9、全文红线**照常生效**
   ——**不能把门禁修没了**；
3. 两场景的 verifier 报告对比：纯 spec 场景不应出现 story 相关 MAJOR FAIL；
4. `pytest test/story` 全量绿（当前基线 331）；
5. 不提交 git。

## 4. 已裁决（原「需裁决」）

`constraint-application.md` 挂六阶段、是 `.md`、对所有人无条件注入——
**规约是否应适用于不用 story 的人？**

**裁决：是。** 规约与 story 功能不绑定，即使从 spec 出发也应正常生效
（用户裁决，见 `02-` 卷首裁决 1）。故 `constraint-application.md` **保持不动**。

合入说明须告知老用户"你们会多一层规约提示"（它只注入提示，不阻断）。

⚠️ **本节的 §2.2 改动 4「待定」随之关闭**——该项不做。

## 5. 与其它方案的关系

- `04-W3规约分层与生成方案.md` 的极小集入驻会减少规约条目，但**不影响本方案**——
  本方案治的是 hook 与门禁的场景适配，与规约内容多少无关；
- 若 §4 裁定"规约只适用 story 场景"，则 `11-` 的交付面也随之收窄，两方案需同步。
