# 06 · 实施顺序与验证

## 1. 批次

### A. Story

- 十章合同、全部材料可见、逐章成文和全文统稿。
- 成文后 `content-audit.md`。
- 不增加 Story 实现专用测试文件；使用临时输入做脚本烟测，并由现有四个隔离 Case 做语义验证。

### B. Knowledge

- 原位完善两份项目知识。
- 完整复制两个模式和 README。
- 增加三层可观测性规约。
- 最小修改现有 Manifest、Hook 和 Overlay。

### C. Adapt

- 生成 1.0/2.0 简单发布清单。
- 新增独立适配 Skill、脚本、安装记录模板和四类跳板路由。
- 用临时目标工程验证三种状态和失败恢复。

### D. 发布

- Manifest 与发布清单声明 2.0，并重算直接维护内容指纹；行为验证结论独立记录。
- 更新 EVOLUTION，只记录真实完成与未验证边界。

## 2. 禁止回归

- 不创建 `story-map.json`、`FACT-*`、`narrative_plan`、Active Knowledge 或新 contracts 知识命名空间。
- 不删除或摘要 `component-profile.md`、`codebase-facts.md` 和两个模式原件。
- 不新增测试关键词、标题硬匹配、固定 Markdown 数量或 invented schema 测试。
- 不同时修改全部子系统后再统一定位问题。

## 3. 验证

- `doc/extensions` 改动逐项对应本方案。
- 两个模式正文与原件进行内容对比。
- Demo 与 Tools 指纹保持不变；Demo 编译通过。
- Tools CLI 和现有四个 Story 并行 CLI 测试模块通过。
- 四个隔离 Case 完成事实、人读、图片/链接和 Knowledge 应用的独立语义评价。
- 临时目标工程覆盖 Framework 缺失、首装、升级、重适配和失败恢复。
