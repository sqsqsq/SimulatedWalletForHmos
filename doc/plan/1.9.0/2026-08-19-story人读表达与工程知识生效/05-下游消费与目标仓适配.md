# 步骤 5：下游消费与目标仓适配

> 前置：[Plan 工程知识生效设计](04-Plan工程知识生效设计.md)  
> 本步交付：Coding、Review、UT、Testing 对规约和设计模式形成连续、可追溯的真实消费，并能在内网绑定真实模式实现。

## 1. 全链消费原则

Plan 冻结一次，下游按职责消费，不重新选型：

每个下游阶段首先读取 `plan.md > 工程知识应用契约` 和 `contracts.yaml > project_knowledge`。前者提供候选处置、选型理由、零命中结论和设计语境，后者提供必须执行的结构化实例、义务与锚点。共享 hook 使用固定标题定位，不依赖模型自行搜索或猜测章节。

本文件中的 Review 指流水线代码审查阶段，其产物 `review/review-report.md` 面向 AI 消费；面向人的需求决策材料始终是 `AR/review.md`。

| 阶段 | 设计模式职责 | 规约职责 | 权威证据 |
|---|---|---|---|
| Coding | 按模式实例实现角色、结构、协作边界和可观察行为 | 将实现义务落到代码、资源、配置和清理逻辑 | 实际 diff、编译与 lint |
| Review | 对照模式使用约定和 Plan 锚点审查成型实现 | 对照实际命中规则审查 diff 落点 | `review/review-report.md` + diff |
| UT | 验证模式派生的业务可观察行为、停止/恢复/分支等契约 | 把验证义务写入场景、动作和断言 | 测试代码、DAG、mock plan、覆盖摘要 |
| Testing | 验证分配到真机层的模式行为与端到端交互 | 完成真机走查、测量、故障注入和交付核对 | test plan/report、截图、日志、数值 |

一个模式如果只改变内部结构、没有新增外部可观察行为，UT/Testing 对该实例给出有依据的不适用结论，不编造业务用例。一个规约域或具体规则没有命中时同样不生成伪实现、伪用例或“已通过”结论。

## 2. 共享设计模式消费协议

`hooks/shared/design-pattern-application.md` 扩展为五个阶段分支：

### 2.1 Plan

按路由表选择模式、建立实例、冻结结构和行为锚点。详细合同由步骤 4 定义。

### 2.2 Coding

读取 `plan.md > 工程知识应用契约` 与 `project_knowledge.pattern_applications`：

- 按 `contract_anchors` 定位应实现的文件、接口、组件、角色、状态和所有权；
- 按 `knowledge_ref` 的 SDK 行为事实与使用约定落码；
- 按 `behavior_anchors` 保持对外行为；
- 模式实例与规约实现义务共同落到真实 diff。

### 2.3 Review

以 Plan 冻结结果为审查基线：

- 从 `工程知识应用契约` 取得采用/拒绝理由、域级判断与设计语境；
- 每个模式实例逐项核对使用约定和 contract anchors；
- 每个约束义务逐项核对 implementation anchors；
- 区分实现偏差、Plan 设计错误和 Spec 契约错误，并给出对应 correction 层。

### 2.4 UT

读取 `工程知识应用契约`、模式 `behavior_anchors` 与规约 `verification_anchors`：

- 把可观察状态、动作、分支、停止、恢复、错误和幂等行为写入业务级测试；
- 内部节点名、类名和文件结构不进入业务断言；
- 需要外部依赖时，mock plan 与 contracts 的接口和错误语义一致；
- 纯结构型模式按 Plan 说明 SKIP，不用测试名冒充覆盖。

### 2.5 Testing

从 `工程知识应用契约` 确认阶段判断，再从 behavior/verification anchors 中选择 acceptance 已分配给 `device_focus` 的内容：

- 形成真实设备上的操作、环境、预期观察和证据；
- 验证端到端交互、生命周期、恢复、兼容、性能和故障表现；
- 条件不足时记录未验证及阻塞事实，不写成通过。

## 3. 共享规约消费协议

`hooks/shared/constraint-application.md` 保持“适用矩阵决定阶段消费面、需求事实决定具体命中”的模型，并对齐新的机器交接：

- Plan 形成 `constraint_obligations`；
- Coding/Review 以 `implementation_anchors` 为落地与审查入口；
- UT/Testing 以 `verification_anchors` 和 acceptance 分层为验证入口；
- 各阶段仍需读取本阶段矩阵非“—”域，防止 Plan 漏项被下游无条件继承；
- `rule_id` 只用于实际命中项追溯，域级判断不靠凑编号。

## 4. 阶段 overlay

### 4.1 Coding

沿用并对齐：

- `coding_pattern_invariants_held`：登记实例在实际 diff 中存在，模式使用约定和行为契约成立；
- `coding_constraint_landing`：每项约束实现义务在代码、资源或配置中有真实落点。

证据是实际 diff。文档里再次声明“已应用”不构成通过。

### 4.2 Review

沿用并对齐：

- `review_pattern_conformance`：逐实例审查模式约定、结构和行为实现；
- `review_constraint_audit`：逐义务审查规约落地，并识别上游登记与实现之间的缺口。

证据进入既有 `review/review-report.md`，不生成新的模式审查台账。

### 4.3 UT

保留 `ut_constraint_cases`，新增：

- `ut_pattern_behavior_cases`：对每个具有 `behavior_anchors` 的模式实例，验证对应业务场景的前置、动作、分支和断言；纯结构型实例按 Plan 证据 SKIP。

结果落在现有测试代码、DAG、mock plan 和覆盖摘要，不新建说明表。

### 4.4 Testing

保留 `testing_constraint_walkthrough`，新增：

- `testing_pattern_behavior_walkthrough`：对分配到 device 层的模式行为执行真机操作，记录观察结果和证据；没有 device 义务时按 acceptance 分层 SKIP。

结果落在现有 `testing/test-plan.md`、`testing/test-report.md` 及外部证据。

共享 `pre_verifier` 保证以上 check ID 与 framework 原生检查一起逐项进入对应阶段 verifier 报告。

## 5. 为什么不为每阶段新增 post-check

Plan 需要新的 post-check，是因为它创建了下游必须稳定解析的 `project_knowledge` 机器接口，候选覆盖、ID 和锚点关系可确定性判断。

Coding、Review、UT、Testing 的核心结论依赖代码语义、diff、断言和真机证据。它们由现有原生 gate 检查文件与基本结构，由 phase overlay 和 verifier 判断工程知识是否真正生效。新增关键词或表格 post-check 会形成平行台账，也无法证明语义正确。

这不是省略下游能力：每个阶段都有明确输入、动作、原生产物和语义 check；只把机械与语义职责放在能够真实判断它们的位置。

## 6. 目标仓模式适配

当前两份模式文档的叙述结构保留：识别适用问题、分解角色与动作、契约投影、SDK 行为事实、使用约定和验证。准确内容由内网按以下权威顺序校准：

```text
内网对应设计模式 Skill
        ↓
真实 SDK 类型声明与实现
        ↓
多个既有业务应用（主案例、边界案例、存在时的组合案例）
        ↓
demo 文档仅提供承载结构
```

`doc/extensions/ADAPTATION.md` 只需对齐：

- 新的 shared/spec/story/plan hook 路径；
- Plan 的两个固定 AI 消费区和 `project_knowledge` 结构；
- Coding、Review、UT、Testing 的阶段消费与证据；
- 正向命中、部分命中和零命中用例；
- 内网已有两个模式 Skill 的发现、SDK 复核和业务案例取证步骤。

模式文档准确性由内网完成后再标“已确认”。本仓 demo 只验证路由、投影和全链消费机制，不替代内网真实结论。

## 7. 内网验证交接

本轮外部正式 CLI 运行到 Coding 与 Review，用来验证冻结契约能够落到真实 diff 并被代码审查消费。交给内网继续 UT/Testing 时，输入必须包含：

- 已闭环的 Spec、Plan、contracts、acceptance/use-cases；
- 每个模式实例的结构与行为锚点；
- 每项命中规约的实现与验证锚点；
- 已适配的模式 Skill、SDK 证据和代表业务案例；
- Coding/Review/UT/Testing 各自应出现的 overlay check ID 与证据要求。

内网从本轮已经闭环的 Review 继续执行 UT → Testing，不需要重新跑 Story/Spec/Plan/Coding/Review，也不需要新增阶段 Skill；若内网适配真实模式知识后改变了 Plan 契约，则按最早责任层回到 Plan 并级联重验，而不是在测试阶段静默改写选型。

## 8. 完成条件

- Coding、Review、UT、Testing 均明确消费设计模式和规约；
- Coding 的证据是实际实现，Review 的证据是 diff 审查，UT/Testing 的证据是可执行验证；
- UT/Testing 能验证模式派生的可观察行为，同时不把内部结构写成业务断言；
- 纯结构模式、阶段不适用、部分命中和完全零命中都有合法路径；
- 六阶段所有扩展 check 都由共享 pre-verifier 纳入报告；
- 内网可按真实 Skill、SDK 和业务案例完成模式适配与后续验证；
- 不产生第二组选型、规约或验证真源。
