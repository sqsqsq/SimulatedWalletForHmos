# 步骤 1：Story 人读信息架构

> 前置：[总体方案](00-规格总览与执行顺序.md)  
> 本步交付：面向人类评审者的稳定阅读主线、合理子章节和内容表达体系。

## 1. 读者任务

Story 的第一读者是第一次接触需求的人类评审者。只读 `AR/story.md`，应能连续回答：

1. 为什么做，解决谁的什么问题；
2. 全局方案是什么，各参与方怎样协作；
3. 当前需求与本 AR 承担什么、不承担什么；
4. 场景、页面、流程、状态和异常怎样设计；
5. 系统怎样承载，接口、数据、配置和事件边界在哪里；
6. 当前有哪些问题、风险和依赖，采用什么处置；
7. 怎样验收、上线和协作。

Story 开篇直接进入需求。评审者需要表态的事项由 `AR/review.md` 组织，Story 只呈现理解和判断所需的完整上下文。

## 2. 稳定阅读主线

```text
# <需求名称>

## 1. 需求概览
## 2. 范围与协作边界
## 3. 整体方案
## 4. 场景与功能设计
## 5. 体验、流程与状态设计
## 6. 系统方案与实现边界
## 7. 问题、风险与当前处置
## 8. 验收、上线与协作

## 附录 A：术语表
## 附录 B：详细契约
## 附录 C：追溯关系
```

正文承担连续叙事，附录承担查询。术语第一次出现时在正文自然解释，附录 A 提供统一速查；因此术语表放在附录不会削弱独立可读性，也不会打断开篇叙事。

## 3. 章节合同的兼容更新

`contracts/story-chapters.json` 沿用 schema v4 和现有字段：`reader_question`、`inputs`、`already_explained`、`boundary`、`expression_hint`、`review_focus`。现有章节 ID 继续作为内部文件键，只调整数组顺序、可见标题、输入归属和任务描述；新增系统方案章时增加一个新 ID。

| 可见顺序 | 可见标题 | 内部章节 ID | 唯一叙述职责 |
|---|---|---|---|
| 1 | 需求概览 | `01-review-guide` | 背景、问题、用户价值、成功定义与本轮边界概览 |
| 2 | 范围与协作边界 | `03-scope` | 全局参与关系、本 AR 承载、物理修改范围、外部依赖和不做事项 |
| 3 | 整体方案 | `02-panorama` | 方案骨架、关键取舍、端到端主路径及核心数据/状态关系 |
| 4 | 场景与功能设计 | `04-scenarios` | 场景组、触发条件、业务规则、成功/拒绝/恢复结果 |
| 5 | 体验、流程与状态设计 | `05-experience-flow` | 页面、交互、流程分支、用户可见状态与异常恢复 |
| 6 | 系统方案与实现边界 | `06-system-boundary`（新增） | 模块协作、接口、事件、数据、配置和工程知识带来的设计影响 |
| 7 | 问题、风险与当前处置 | `06-exception-risk` | 已知问题、限制、影响、当前处置与外部依赖 |
| 8 | 验收、上线与协作 | `07-rollout` | 验收策略、兼容/开关、发布回退、协作行动和阻塞关系 |
| A | 术语表 | `08-appendix-terms` | 人读术语与易混项速查 |
| B | 详细契约 | `09-appendix-contract` | 完整接口、字段、存储、配置、事件与依赖约定 |
| C | 追溯关系 | `10-appendix-quality` | 质量、合规、验收、规约与需求编号映射 |

内部 ID 不进入最终 Story。保留既有 ID 可使已经生成的章节源继续被识别；新增章由 scaffold 明确创建，不把旧章静默当作新章。

## 4. 章内层级

| 层级 | 语义 | 典型对象 |
|---|---|---|
| H1 | 一份需求 | 需求名称 |
| H2 | 阅读主线中的一个大问题 | 范围、整体方案、体验、系统方案、风险 |
| H3 | 可以独立评审的主题 | 页面与交互、状态与恢复、接口与事件 |
| H4 | H3 下独立的业务或设计对象 | 某页面、某场景、某状态域、某接口组、某分支 |

作者先完成本章标题树，再写正文。标题树本身应能复述本章的讨论顺序。

- 一个 H2 下存在多个可以分别讨论和形成结论的主题时，拆为 H3；
- 一个 H3 下存在多个页面、场景、流程分支、状态域、接口组或依赖对象时，拆为 H4；
- 只包装一句说明的标题并回正文；
- H4 必须位于 H3 下，正文标题不跳级；
- 字段级明细使用表格或附录，不继续切碎标题。

章节数量不是质量指标。简单需求可以没有 H4，复杂需求则按真实对象自然展开。

## 5. Markdown 表达体系

作者先判断信息之间的关系，再选择最利于人阅读的形态。

| 信息关系 | 首选表达 | 使用边界 |
|---|---|---|
| 背景、原因、方案、取舍和影响 | 连贯段落 | 保持完整论证，不切成标签堆叠 |
| 无先后关系的同级事实 | 无序列表 | 每项同一粒度 |
| 简单线性步骤 | 编号列表 | 步骤存在明确顺序和完成点 |
| 父子分类 | 一层嵌套列表 | 只表达真实从属关系 |
| 多对象同字段比较 | 表格 | 列具备稳定重复字段；单条事实用正文 |
| 端到端路径、分支和汇合 | Mermaid `flowchart` | 图后补充关键分支含义 |
| 状态、事件、守卫和终态 | Mermaid `stateDiagram` | 区分内部状态与用户可见状态 |
| 多参与方调用先后 | Mermaid `sequenceDiagram` | 参与方和先后关系确有评审价值 |
| 页面或视觉依据 | 图片、替代文本和图注 | 图片必须能从最终 Story 路径解析 |
| 高影响结论、当前处置或风险 | 简短引用块 | 一块只强调一个结论，正文仍给上下文 |
| 扫读锚点 | 局部加粗 | 强调结论，不整段加粗 |
| 接口、字段、配置和状态名 | 行内代码 | 保持可按名回查 |
| 补充来源或次要说明 | 链接或脚注 | Story 正文仍须自包含，链接不是理解前置 |

关键信息保持直接可见。折叠区、脚注和附录只承载补充或查询材料，不隐藏范围、方案、风险和验收事实。

## 6. 单向叙述

每项事实只有一个完整叙述位置：

```text
正文主归属章完整解释事实、原因与影响
        ↓
后续正文用一句承接或内部链接
        ↓
附录保存字段、编号和映射明细
```

- 范围章完整解释参与方与边界；上线章只讲行动、时序和阻塞关系；
- 整体方案建立全局骨架；场景章展开业务分支；体验章展开页面、流程和状态；
- 系统方案章解释接口、数据和配置的业务意义；附录 B 保存完整签名与字段；
- 规约对用户或设计的影响进入对应正文；`rule_id` 与验收映射进入附录 C；
- 风险章说明当前处置和残余影响，不把内容写成会议问题或任务清单。

## 7. 实施落点

- `doc/extensions/skills/story/contracts/story-chapters.json`：调整章节顺序、标题、来源、边界和写作提示，保持 schema v4；
- `doc/extensions/skills/story/rules/rules.md`：定义标题树先行、H3/H4 拆分条件和表达选择；
- `doc/extensions/hooks/spec/story/instructions.md`：按章生成标题树并逐章成文；
- `doc/extensions/skills/story/scripts/story-build.mjs`：装配新顺序，检查 H4 归属、标题跳级、资产和章节守恒；
- `doc/extensions/skills/story/scripts/merge-story.mjs`：保持最终产物与章节源一致；
- `test/story/tests/test_story_build.py` 及相关合同测试：覆盖合法层级、非法跳级、旧章节 ID 兼容与新章创建。

机械检查只守标题层级、装配、引用和资产等确定性事实。子章节是否合理、表达形态是否恰当、读者能否顺畅理解，仍由独立语义评价逐字通读判断。

## 8. 完成条件

- 最终 Story 按八章正文与三个附录连续成文；
- 复杂页面、场景、状态或接口能自然形成 H3/H4，简单内容不被强制切碎；
- 表格、列表、图、图片、引用块和正文按信息关系使用；
- Story 中不存在独立“评审导读”或文首“待确认事项”；
- 术语在正文首次解释，附录 A 提供完整查询；
- 同一事实只有一个完整叙述位置；
- 现有章节源可兼容迁移，新系统方案章不会覆盖旧内容；
- 结构正反例通过，语义质量保持独立评价。
