# Story 人读表达与工程知识生效：总体方案

> 方案日期：2026-08-19  
> 证据基线：[09-Human-First-story-spec-plan正式实跑报告.md](../2026-08-18-story适配与设计模式重启/09-Human-First-story-spec-plan正式实跑报告.md)  
> 状态：运行能力已实施，离线回归已通过，待正式 CLI 实跑  
> 本目录是本轮优化的唯一方案真源。

## 1. 目标结果

本轮建立两项可以通过正式产物验证的能力：

1. `AR/story.md` 成为人类评审者可以独立阅读、理解并据此审查需求的完整文档；
2. 应用域规约和设计模式在需求事实实际命中时，进入设计选择、机器契约、实现、审查与验证，而不是只在上下文或回执中出现名称。

工程知识是否生效，以阶段原生产物发生相应变化为准。`pattern_id`、`rule_id` 和应用表只负责追溯，不能替代真实设计、契约、代码、审查或测试证据。每个需求按自身事实判断；模式零命中、某个规约域零命中或只命中少量规则都属于正常结果。

## 2. 正向能力模型

需求交付链的读者边界固定如下：

| 产物 | 目标读者 | 设计取向 |
|---|---|---|
| `AR/story.md` | 人 | 连续、完整、可独立理解的需求叙事 |
| `AR/review.md` | 人 | 可逐项审核、表态和记录结果的决策材料 |
| `spec.md`、`plan.md`、`contracts.yaml`、`acceptance.yaml`、`use-cases.yaml` | AI | 稳定结构、明确字段、受控 ID 与可解析锚点 |
| Coding、Review、UT、Testing 阶段产物 | AI | 支持下一阶段消费、门禁与 verifier 取证 |

`AR/review.md` 与流水线的 Review 阶段不是同一产物：前者面向人进行需求决策，后者的 `review/review-report.md` 面向 AI 流程进行代码审查。

```text
Story：把需求组织成人能连续理解的叙事
   ↓
Spec：把需要实现的要求写成无歧义规格，并登记模式候选信号
   ↓
Plan：对候选完成采用/不采用判断，把实际命中的规约和模式冻结为设计与机器契约
   ↓
Coding：按冻结契约实现
   ↓
Review：对实际 diff 审查契约遵从性
   ↓
UT / Testing：验证模式派生的可观察行为与实际命中的约束
```

Plan 是本链路的“选择与冻结”阶段，不是工程知识能力的终点。Coding、Review、UT、Testing 都必须继续消费 Plan 结果：Coding 落实模式结构与规约义务，Review 审查实际 diff，UT 验证模式派生的可观察行为与规约场景，Testing 验证真机与交付环境中的可观察结果。各阶段沿用自己的原生产物作为证据，并通过共享 hook 与 phase overlay 补齐消费任务和语义闭环。

## 3. 目标架构

| 层 | 权威职责 | 目标位置 |
|---|---|---|
| Story 生成能力 | 章节合同、逐章写作、装配与 Review 渲染 | `doc/extensions/skills/story/` |
| 工程知识 | 规约、模式、适用条件与内容 | `doc/extensions/knowledge/` |
| 共享消费协议 | 规约、模式与 verifier 的公共指针 | `doc/extensions/hooks/shared/` |
| Spec 扩展 | 保持现有 §9/§10 与 Story 条件编排 | `doc/extensions/hooks/spec/` |
| Plan 扩展 | 形成 AI 工程知识消费契约、机器交接与确定性闭环 | `doc/extensions/hooks/plan/` |
| 下游消费能力 | 在 Coding、Review、UT、Testing 中落实、审查和验证 Plan 冻结结果 | 共享 hook、各阶段 overlay 与阶段原生产物 |
| 阶段语义判据 | 判断工程知识是否真正改变阶段产物 | `doc/extensions/rules/*-rules.overlay.yaml` |
| 扩展注册 | 以 canonical phase/event 注册实际需要的 hook | `doc/extensions/manifest.yaml` |
| 目标仓适配 | 用内网模式 Skill、真实 SDK 和既有业务案例校准知识 | `doc/extensions/ADAPTATION.md` |
| 评测与演进 | 离线合同、CLI 实跑、语义评价与报告 | `test/story/` |

`framework/**` 保持当前字节内容不变。Story 继续使用现有 Story Skill；其它阶段继续使用 framework 原生 Skill 与实例扩展机制。本轮不新增 Plan、Coding、Review、UT 或 Testing Skill。

## 4. 关键设计决定

- Story 采用已确认的八章正文与三个附录；正文服务连续阅读，附录服务查询。
- Story 章节合同沿用 schema v4 和现有字段，只调整章节拓扑、输入归属与写作任务；不再复制一套内容轴 schema。
- `decisions.json` 沿用 schema v2。Story 锚点由决策占位位置确定，不新增 `story_anchor` 字段。
- Story 不生成“评审导读”或“待确认事项”；人工表态只在 `AR/review.md`。
- Spec 的 `spec-sections.md`、§9、§10、现有 `post_check` 和 overlay 保持职责不变，只随 hook 目录规范化更新引用。
- Plan 新增一份面向 AI 的自包含阶段合同和一个确定性 `post_check`；输出形态直接写在阶段合同中，不新增 `artifact_contract.md`。
- Coding、Review、UT、Testing 的共享 hook 和 overlay 按新的 Plan 交接结构更新：各阶段都获得明确的模式与规约消费任务，并在原生产物中形成证据；共享 `pre_verifier` 保证这些扩展 check 被逐项裁决。
- 设计模式文档与适配指南保留现有叙述骨架；本轮只对齐新的 Plan 交接结构、hook 路径和消费验证方式。
- 评测判据 SSOT 不因本轮实现而改变。机械检查只判断结构事实，Story 人读质量和知识是否真正生效继续由独立语义评价判断。

## 7. 诉求覆盖

| 原始诉求 | 方案落点 |
|---|---|
| Story 是给人看的完整需求，不是给 AI 的机器台账 | 步骤 1、2 |
| 除 Story/Review 外的需求交付链产物均按 AI 消费设计 | 步骤 3、4、5 |
| 子章节按真实对象合理拆分，充分使用 Markdown 表达能力 | 步骤 1 |
| Story 不出现待确认清单和评审导读；术语作为查询附录 | 步骤 1、2 |

| Spec 已有效的扩展能力保持稳定 | 步骤 3 |
| manifest 配置风格一致，但不追求阶段文件数量对称 | 步骤 3 |

## 8. 总体完成条件

- Story 可由第一次接触需求的人连续读懂，并能据此审查问题、范围、方案、场景、系统边界、风险和验收；
- Review 覆盖本需求实际存在的决策全景，并能回到 Story 的唯一上下文；
- Spec 既有扩展能力和正式闭环无回归；
- Plan 对每个 Spec 模式候选给出采用或不采用结论，对适用矩阵要求的每个 Plan 域给出需求化处置；
- 采用的模式和实际命中的规约改变真实设计，并进入最小 `project_knowledge` 机器交接；
- Coding、Review、UT、Testing 分别完成实现、审查、业务验证和真机验证，能够证明 Plan 冻结的规约与模式已生效；
- 正向命中和零命中均可闭环；
- 正式外部实跑完成 Story、Spec、Plan、Coding 与 Review，UT/Testing 未启动；
- 正式报告落盘后停止，后续修改由人另行决定。

## 9. 执行边界

实施只落在本方案声明的实例扩展与测试域；`framework/**` 保持实施前字节状态。
正式 CLI 按步骤 7 分三段推进至 Review，结束后只产出报告，不依据报告自动修改运行能力。
