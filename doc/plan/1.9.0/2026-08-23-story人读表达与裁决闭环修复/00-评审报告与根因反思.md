## 5. 根因反思:为什么上一轮目标实现后仍有这么大差距

差距由三个层次各担约三分之一,外加一个验收偏差——**"方案文件没写清楚"成立,但只是其一**:

1. **方案层缺失(≈1/3)**。上一轮 01 方案的写作契约本身不全:形式选择只写了 4 形态(被否档案里更全的「有序/无序/任务列表/强调/引用」说明没有回收);没有段落纪律;没有"story 应厚于 spec"的厚度基准;没有写作范例;没有设计"verifier 是否真的执行了判据"的验证环。实施者(同一会话)按方案做了——**方案缺什么,实现就缺什么**。这部分是方案文件的直接责任。
2. **判据措辞自拆台(≈1/3)**。方案写了"流程用图",配套判据的 hint 却同时写「不要因为它没有某个章节号或某张表而判 FAIL」——为防"形式配额"写的宽容句,被 verifier 当成了豁免一切形式要求的许可。删配额(冻结 C2)之后没有配非配额的观测(mermaid 不在 audit 统计)与硬语义判据(「过程压成箭头文字即 FAIL」),矫枉过正。
3. **执行链无机械闭环(≈1/3)**。所谓"执行模型对上下文理解缺失",不发生在"方案→实施模型"那一跳(同一会话,无传递损耗),而发生在 **"注入件→被测模型→verifier"**:注入件是被测模型唯一读到的"方案",它十条平铺、无优先级信号、无范例,模型抓不住重点;verifier 本该兜底,AR90006 0/8 没人拦。教训:**注入件要按"给模型的方案文件"来写(范例+负面清单+明确 FAIL 判据),裁决要加机械闭环**;往维护侧方案文件里堆更多字没有用。
4. **验收自证偏差**。上一轮行为验证判据由实现者自拟(V3 只看了表格占比与机器面),天然只验自己做过的事;首轮评审同样漏掉这四点,由用户指出。**下一轮验收清单必须从冻结需求文本独立重推**,并把"读者体感"类判据(图示形态、段落纪律、厚度)显式入列——见本轮 02 文档。
5. **就地取材污染机制层**(§5.1 专项检查后补)。实现时拿眼前的东西当材料——拿测试产物当示例(H1 示例写了测试 Case 业务名)、拿当期域清单当常量(4c 正则写死七个域前缀)、拿本仓 spec 实践当通用约定(编号形态固化)——测试特征与知识内容就这样渗进了机制层。缺一道"机制层零业务、零 Case 标识、零知识字面"的**提交前固定扫描**;本轮方案把它加为收口门禁。

## 6. 写作方法论调研结论(01 方案第②项的输入)

- **AI 味的可识别信号**:句长均一(窄带节律)、模板化结构复用、通用过渡词、华而无据的判断、hype 词。对策:变句长、换段形与过渡、立场明确;**给 2-5 个真实写作范例的效果远超抽象指令**。
- **段落纪律**:一段只讲一件事;段 5-10 行;句均 15-20 词、超 25 词拆句;节首先用一段说明"这节要讲什么"再展开;节间留白;标题引路(问句式标题有效)。
- **形式选择**:真实顺序→有序列表;并列相关→无序列表;紧凑对比/参考数据→表(能用列表就不用表);过程与分支→图;命令与配置→代码块;强调只在改变含义处用;避免深嵌套。
- 出处:George Kao《How To Write Without Sounding Like AI》、louisbouchard.ai《AI Editing》、BCcampus《Technical Writing Essentials》(Readability / Style Tips 两章)、OPM Plain Language、Google Markdown Style Guide、MarkdownMastery《Markdown for Documentation Best Practices》。
