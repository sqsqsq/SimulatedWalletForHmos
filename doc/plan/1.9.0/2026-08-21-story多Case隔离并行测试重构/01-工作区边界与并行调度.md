# 工作区边界与并行调度设计

## 1. 当前实现为何仍不够隔离

现有 `run_multi_case.py` 虽然已经支持 isolated workspace，但实现仍有三个结构性问题：

1. 先把主工程整仓复制，再用忽略列表排除目录；工作区边界由“复制后排除”决定，容易把不应进入模型视野的测试或历史状态带进去。
2. 工作区通过 Git template/clone 建立，并把 `.git` 作为源码事务和状态基础；这与“临时代码仓只保留被测工程范围”的要求冲突，也放大了 Windows 路径和只读对象问题。
3. suite 结果根与 case 控制指针分离，默认还保留 `output/story/runs` 这一层；用户查看一轮测试时无法从 `output/story/` 直接看到唯一的大目录。

## 2. 新的目录契约

### 2.1 主工程

主工程只负责运行控制和最终接收通过验收的结果：

```text
E:/Project/SimulatedWalletForHmos/
├─ test/story/                 # 测试定义与 runner，只在宿主侧使用
├─ tools/                      # CLI runtime，只在宿主侧使用
├─ output/story/               # 每轮唯一结果大目录
├─ doc/features/               # 起跑前迁移历史，结束后接收通过验收的产物
└─ 01-Product ... 05-SystemBase # 被测源码基线，不被并行 Case 直接修改
```

### 2.2 本轮结果目录

结果根固定为：

```text
output/story/<YYYYMMDD-HHMMSS>-<task-name>/
├─ suite.json
├─ authorization.json
├─ preflight.json
├─ backup/doc-features/         # 起跑前迁移的历史 feature
├─ cases/
│  ├─ split-two-ar/
│  │  ├─ case.json
│  │  ├─ runs/<run-id>/
│  │  ├─ observations/
│  │  └─ promotion-manifest.json
│  ├─ split-interactive/
│  ├─ source-conflict-review/
│  └─ pattern-image-review/
└─ suite-summary.json
```

不再新建 `output/story/runs/<suite>` 作为本轮用户入口；所有 Case 数据必须能从这一轮大目录追溯。

### 2.3 Case 临时工作区

每个 Case 一个独立目录，目录名不从长结果路径派生。工作区模板采用白名单复制：

```text
<short-temp-root>/<suite-short>/<case>/
├─ 01-Product/
├─ 02-Feature/
├─ 04-BusinessBase/
├─ 05-SystemBase/
├─ AppScope/                   # 存在时复制
├─ framework/                  # 被测 Skill/Framework 运行所需内容
├─ doc/extensions/             # 被测扩展
├─ doc/architecture.md
├─ doc/module-catalog.yaml
├─ doc/glossary.yaml
├─ 项目构建所需的根配置文件
└─ doc/features/<AR>/          # 仅由本 Case 输入和本轮产物组成
```

明确不复制：

- `output/`
- `test/`
- `tools/`
- 主工程历史 `doc/features/` 全目录
- `.git/`
- `scratch/`、`node_modules/`、`oh_modules/`、构建缓存和 IDE 缓存

Case 的测试材料从 `test/story/cases/<case>/workspace/` 单独铺入该 Case 的 `doc/features/<AR>/` 或约定材料目录，不以复制主工程 `doc/features/` 的方式提供。

## 3. 并行安全条件

只有同时满足以下条件，调度器才允许四个 Case 同时启动：

1. 四个 AR 唯一，四个 feature 目录唯一。
2. 四个工作区的绝对路径唯一，且工作区内的 `framework/harness/state`、CLI runtime 和输出目录唯一。
3. 被测进程的 cwd、临时目录、缓存目录和配置目录指向 Case 私有路径。
4. Coding Case 不写主工程；源码变更只发生在该 Case 工作区。
5. 构建命令禁用共享 daemon，或为每个工作区设置独立 daemon/cache 目录。
6. 调度器启动前完成四个工作区的写入和读取自检。

不再以“主工作区是否有另一个 Case 正在 Story/Spec/Plan”作为阻塞条件。共享 Story 阶段槽被工作区隔离消除；真正共享的系统资源若自检失败，才整体拒绝本轮启动。

## 4. Case 状态与调度

每个 Case 使用以下状态边界：

```text
prepared → starting → running
                     ├→ waiting_for_scripted_human → running
                     ├→ provider_rejected
                     ├→ worker_lost
                     └→ terminal
```

`pending` 只表示工作区尚未启动，不表示等待其他 Case 让出 Story 阶段槽。四个 Case 的首次 `start` 必须在同一个调度批次中发出，并在 `preflight.json` 中记录四个 worker pid/run-id。

停止时先发出 graceful stop，随后按实际进程树验证；进程查询失败不能直接判定“已停止”，必须结合 worker lease、停止回执和最终进程复核给出 `stopped` 或 `stop_failed`。

## 5. Coding 变更处理

Coding Case 不再对主工程建立 Git 源码事务，也不把长结果目录作为事务目录。工作区本身就是隔离的 baseline：

1. 启动前为受控源码目录生成文件清单和 SHA-256。
2. Coding/Review 结束后在短临时证据根生成 changed/new/deleted 清单和文件副本。
3. 结果目录只保存证据和哈希，不作为工作区源码事务的父目录。
4. 通过验收后由宿主执行回灌；回灌前再做主工程同名文件备份，回灌后逐文件校验。
