# 归档、回灌与实施验收

## 1. 起跑前门禁

调度器在启动任何 worker 前必须生成 `preflight.json`，并全部满足：

- [ ] 非沙箱授权已记录，范围为本轮四 Case CLI、观测、归档和通过验收后的回灌。
- [ ] 旧 suite 没有活跃 worker、CLI run 或未处理 lease。
- [ ] 主工程历史 `doc/features/` 已迁移到本轮 `backup/doc-features/`，迁移清单和哈希齐全。
- [ ] 四个 Case 的 AR 唯一：AR90005、AR90006、AR91004、AR90004。
- [ ] 每个 Case 的材料输入独立，工作区不含主工程历史 `doc/features/`。
- [ ] 工作区不含 `output/`、`test/`、`tools/`、`.git` 和构建缓存。
- [ ] 每个工作区的 Framework 状态、CLI runtime、缓存和运行目录独立。
- [ ] 结果路径与源码证据路径通过路径长度检查，源码证据路径使用短临时根。
- [ ] `reply` 不依赖不可靠的 `tasklist` 字符串判断；至少能在 worker 正常持有 lease 时入队并被消费。
- [ ] 四个 Case 都能在同一批次完成 `start`，不得出现“第 4 个等前 3 个释放共享槽”。

任一门禁失败，整轮不启动；先修 runner 或工作区准备问题。

## 2. 运行中验收

运行器必须实时保存：

- `suite.json`：任务、授权、四 Case 计划、调度策略和状态。
- 每个 Case 的 `case.json`：AR、工作区、run-id、交互脚本、阶段范围和状态。
- `events.jsonl`：启动、交互入队/消费、观测、错误、终态。
- `observations/`：每 120 秒的状态、模型新增内容、事件和产物摘要。
- `run/`：CLI 输出、report_data、phase trace、原始日志。

四个 Case 之间不得以共享的 latest 指针代替明确的 run-id；任何状态报告都必须写出 Case、AR、run-id 和结果目录。

## 3. 回灌规则

### 3.1 文档产物

通过目标阶段并通过语义验收的 Case，回灌其工作区中的 `doc/features/<AR>`。回灌前：

1. 若主工程出现同名目录，先移入本轮 backup。
2. 生成源文件清单和 SHA-256。
3. 复制后重新计算目标哈希。
4. 写入 `promotion-manifest.json`，记录 source、destination、hash、Case、AR 和时间。

### 3.2 Coding 新增代码

只回灌 Coding 工作区相对 baseline 的新增或修改文件，并限制在：

```text
01-Product/
02-Feature/
04-BusinessBase/
05-SystemBase/
```

不回灌 `test/`、`tools/`、`output/`、`framework/`、`doc/extensions/` 或构建缓存。删除文件必须单独列在清单中，未获明确验收不得执行删除。

### 3.3 失败与停止

`provider_rejected`、`workspace_prepare_failed`、`worker_lost`、`stopped` 和未通过质量验收的 Case：

- 只归档工作区产物和源码差异证据；
- 不把未闭环 `doc/features/` 或半成品源码回灌主工程；
- 证据固化后再删除临时工作区。

这里的“测试完”定义为 Case 已达到可验收终态；停止或基础设施失败不视为可回灌终态。

## 4. 实施顺序

### Step 1：先修目录与工作区

改造 suite 根目录、白名单复制、Case 输入铺设和短路径源码差异采集。完成条件：只做本地准备演练，不启动模型，也能生成四个独立工作区和 `preflight.json`。

### Step 2：再修交互与进程控制

移除运行器对业务 prompt 的长控制提示拼接；建立交互脚本、关卡指纹、reply accepted/consumed 和可靠 worker lease 判断。完成条件：不启动模型也能通过 harness 测试验证 reply 文件路由、消费回执和停止状态收敛。

### Step 3：执行四 Case 并行测试

仅在 Step 1、Step 2 的门禁通过后，以 `jobs=4` 一次启动 AR90005、AR90006、AR91004、AR90004。执行中不插入单 CLI 基线，不额外加入第 5 个 Case。

### Step 4：分析、回灌、清理

先完成四 Case 的机械报告和语义报告，再按回灌规则处理通过验收的产物，最后删除工作区并保留本轮结果大目录。

## 5. 最终验收

本轮方案实施完成后，必须能回答：

1. 四个 Case 是否同批次启动，是否都拥有独立 workspace 和 run-id？
2. 是否存在重复 AR、共享 feature 目录或共享 Framework 状态？
3. 每个交互回复是否在正确关卡被消费？
4. 120 秒观测是否从最后一次交互完成后才开始？
5. AR91004 的 provider 错误是否没有被误报为业务失败？
6. AR90004 是否不再因结果路径过长而在模型启动前失败？
7. 主工程是否只接收通过验收的文档和源码变更？
8. 本轮所有数据是否集中在 `output/story/<时间戳-任务名>/`？
