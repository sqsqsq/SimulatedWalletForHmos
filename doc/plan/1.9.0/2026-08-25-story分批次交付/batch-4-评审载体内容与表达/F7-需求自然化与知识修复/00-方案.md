## §1 A 线 · 需求自然化（两 case × 两模式，四个业务场景）

**设计原则**：每个场景必须有独立的产品理由（用户价值/风控理由），拿掉「测模式」这个动机
后它依然成立；材料只写业务，不写任何结构暗示。以下场景内容是**方案给执行者的底稿**，
执行者按各材料文体融入（PRD 的旅程与规则、SR 的时序与接口、docx 重生成），不逐字照搬。

### 1a auto-topup 补 page-interaction 信号：支付验证环节写实

现状：材料把签约写成「同意协议→开启」一步顺流。真实的免密代扣业务**本来就有**支付验证
环节——把它写实（产品理由：扣款授权必须经支付验证，这是支付合规常识，不写才是失真）：
用户同意协议后**拉起支付验证**（支付能力的验证界面），验证通过才建立签约；验证失败或
用户取消则留在签约页可重试。落点：RR 旅程与规则补这一环、SR 时序补「钱包⇄支付能力」
一跳与失败返回、验收意图补「验证取消后停留可重试」条目。
（这正是 page-interaction 知识文件开篇的场景原型——「确认之后拉起验证、验证通过要提交、
提交结果决定关闭还是留在原地」——但材料里**一个结构词都不写**，只写业务。）

### 1b auto-topup 补 decision-tree 信号：签约建立流程的分支写实

现状：端侧签约被写得太顺（云侧流程在云端，端侧确实没有多分支——F4 反证这半是对的）。
写实端侧签约的真实分支（产品理由：这些情形线上都会发生，材料不写、开发就不处理）：
①资格核验不过→引导去完成对应条件后返回续办；②已有生效签约→进入管理而不是重复建立；
③支付验证失败→保留选择可重试；④用户中途退出→再进入时恢复此前选择。每条分支有自己的
后续动作与去向——这在 PRD 用户旅程与 SR 失败恢复节按业务写全。

### 1c car-key-sharing 补 page-interaction 信号：对象决定权限档位

现状：三项独立单选、无结果驱动链。自然场景（产品理由：临时借车的人不应拿到全功能——
权限策略跟人走是真实产品的常识）：车主选定分享对象后，**系统按对象与车辆的关系返回
该对象可用的权限档位**（家庭成员可选全功能，其他联系人仅解闭锁），权限区按返回结果
呈现；更换对象则权限重新确定。落点：PRD 分享设置页描述与规则、SR 补「查询对象可用
权限」一跳（接口或并入配额查询）、验收意图补「更换对象后权限选项随之变化」。

### 1d car-key-sharing 的 decision-tree：材料不动，只列预期

发起/接受/撤销流程的多分支多步信号**材料里本来就有**（F4 同材料判命中是证据）——
本 case 此模式不改材料；F6 的翻转由 B 线修复判断链来回正。1c 的新增不得削弱既有流程叙述。

### 1e 配套

- docx 用 `make_case_assets.py` 重生成（图不必改——新场景不新增页面，只改选项呈现逻辑，
  文字稿承载即可；若执行判断需调整图内文字，同通道再生）；
- interaction-script 立场依据**尽量不加新关卡**：新场景写进材料即自洽，需求方无需新表态；
  若执行发现某场景必然引发模型提问（如权限档位的来源），给对应 planned_intent 补一条立场，
  登记差异栏；
- 材料过拟合自检（KM 口径三词表＋通读）：零机制词、零模式暗示、每场景产品理由在材料内成立。

## §2 B 线 · 知识与判断链修复（四条，全部对 F6 四环）

### 2a README 零命中行去模板化（对环 3「话术模板」）

现文（README 路由表第三行）：「单一线性流程、两三个分支且各自只有一两步、无跨步骤状态；
或页面只有几个彼此独立的按钮 → 零命中（正常结论，不是遗漏）」——具体描述被 F6 实证照搬
成反证话术（连「无跨步骤状态」这个与业务不符的断言也是抄来的）。
改法：判定标准保留语义但**改为举证要求**——「零命中同样要举证：反证必须指向本需求的
具体业务事实（哪段流程、有哪些分支、各自后续是什么、有没有贯穿多步的状态——逐一指到
材料），**不得复述本表的判定语言**；『正常结论不是遗漏』只在举证成立时成立。」
不加机器判据（措辞判会催生改写躲避），审查归 2c。

### 2b 输入源口径覆盖 spec 判断者（对环 4「读者面缺口」）

- README 上篇读者标注「读者：plan」改为「读者：spec 的候选判定与 plan 的选型」；
- 「信号来自业务流程本身，承载会换、业务不会」这句**同时落进 spec 模板**
  （`spec-sections.md` 的 §11 注释——spec 阶段判断者的实际输入面），与 README 同一段文字。

### 2c verifier 对 §11 的专项问（对环 2「防线缺席」——防线本体已由 F6 删子 agent 路恢复）

`phases/story-verify.md`（或 spec 阶段的裁决问句所在处，执行按现结构落）补一问：
「§11 的每条反证，与材料对得上吗——反证里每个可核对的业务断言逐条拿材料核；
断言与材料相反（材料明写存在的东西，反证说没有）即点名。」
语义问，不做正则；问句本身不携带任何具体断言样例（防止又造出一个可填空模板）。

### 2d DESIGN_HEADING_RE 结构化改判（对 F6 §七待决项，执行者建议采纳）

## §2′ C 线 · 工具辅助与产物卫生（F6 遗留三件，2026-09-01 用户裁定并入；
与 A/B 线同主题——模型缺官方辅助就野生自造，给辅助好过放任）

### 2e docx 只读预览（F6 遗留 #6）

`import_sources.py` 加 `--preview <docx>`：复用既有解析代码输出正文文本与图清单，
**只读不落盘、零新增依赖**。作业书归类步骤提一句「预览用它，不自写解析」。
自验：对两个 case 的现有 docx 各跑一次，输出与落盘版正文一致（抽段比对）。

### 2f audit 分布与明细输出（F6 遗留 #7）

`story-build.mjs` 的 `audit` 命令补打印：三态分布计数（at/covered_by/machine_facing/待分配）、
按落点章的分布、**待分配单元的逐条明细**（key＋首 30 字）——数据全在内存，只是没打印。
不改任何判定逻辑（diff 只在输出面，单测锁）。

### 2g 登记步清理中间件（F6 遗留 #8，冻结判据的姊妹动作）

story 登记时（写指纹之前）把 `AR/story-src/` 下**非机制五件**的文件清除——五件白名单
**引用机制内既有的产物清单常量**（D3 冻结指纹用的同一份），不在清理代码里另列一份文件名——F6 实测模型自造 21 个 `_chapter_*` / `_pool_*` /
`_map_*` 草稿混进归档目录。清除动作打印被清清单；只清 story-src/ 一层，不碰其它目录。
自验：夹具放两个 `_x.txt` 跑登记→被清且指纹只含五件；五件本体不受影响（回归）。
