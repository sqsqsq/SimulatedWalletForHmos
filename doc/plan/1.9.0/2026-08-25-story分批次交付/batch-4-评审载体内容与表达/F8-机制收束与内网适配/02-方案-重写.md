### 层三 · 枚举出来的图，写的时候没画（**这一层是 F8 的责任**）

`kind` 维度的单元数几乎没变（auto-topup image 3→3、diagram 3→2；car-key image 4→2、diagram 6→4），
但画出来的从 3/3、4/6 掉到 0/0、2/1。

三个成因叠加：

1. **图在守恒链上本来就只有半层网。** `source-units.mjs:274-283`：图片单元的 `tokens`
   **只有一个元素——文件 basename**，它只有在作者真写了 `![](…/x.png)` 时才命中；
   没画图 → `autoPlace` 返回 null → 落回 `old.at`、`by: 'author'`，记录看起来完好、
   `audit` 的「待你分配 0 条」照样绿。流程图更弱：中文 mermaid 节点名被
   `tokensOf` 的 `t.length >= 2` 过滤掉，tokens 近乎空数组，连参与守恒的资格都没有。
   **所以文字事实丢了会被整篇 token 守恒在任意位置捞回来，图丢了只有 `check` 末尾那一条形态判。**
2. **F8 把两层削成一层**：删掉「整篇形态数不降级」。
3. **作者面被改成自相矛盾**：F8 在 `story-write.md:72/76` 加了「图不必每张都进 story」
   「没有数量判据——引多引少都不判」，而 `:161` 原有的「**图片一张不少、一图一引**」还在。
   同一份文件里两句话打架，且新加的两句就在第一步分配表正下方，位置更显眼。

### 层三的邻接缺口 · 写作时没有逐章欠账清单

`story-write.md:137-146` 第二步声明每章的输入：

| 输入 | 拿它做什么 |
|---|---|
| **分给本章的那些单元正文** | 这一章要讲的全部事实。**只看这些，不回头翻材料** |

**这份清单没有任何东西产出它。** 全仓没有按章过滤 `audit.json` 的命令、没有逐章任务书、
没有任何在动笔前告诉作者「这一章分到了 3 张图」的输出。作者得自己把 367 个单元
按章 join 一遍，靠上下文记忆——5 张图在 367 条里自然掉出去。

历史原因：1.0 的 `scaffold()` 会给每章物化一份任务书（章文件头注）。
`ab3ab091` 把它整条删除，**删的理由是对的**——1.0 由合同按关键词把材料路由给章，
同一事实被四个章节合同各指一次，于是被强制写四遍。**但它连带删掉了「动笔前手边有本章清单」
这个载体。** 旧代码自己写过一句：

> 它必须出现在**写作动作发生的地方**（章文件头注），而不只在规则文件里：
> 规则隔着几十步，任务书就在眼前。

这句话正好描述现在的失效模式。**现在的落点是作者自己定的一对一分配，按构造不可能重复
——这正是 1.0 做不到、而现在可以做的。**

## §2 设计原则（这五条是对根因的直接回应，实施时逐条对照）

| # | 原则 | 怎么落到动作上 |
|---|---|---|
| **P1** | **放宽前先写命中面** | 每一处删除或弱化判据，方案里必须先写清「它防的是什么坏产物」，再写误伤面，然后指名**谁来接**。接不住就不删 |
| **P2** | **判据双向** | 每一处放宽配一条**反例夹具**：原来拦得住的坏产物，改完还得拦得住。只有正向夹具（好产物不被拦）不算验收完成 |
| **P3** | **先上游后下游** | 取材侧的静默失败先补。上游漏 34 个单元时，下游修得再好也是在残缺的守恒面上修 |
| **P4** | **判据前移，不是加判据** | 同一条判据能在更早时刻跑就前移；不在更晚的时刻叠新判据。前移不改变判定逻辑，只改变作者何时看见 |
| **P5** | **一次只动一层** | 批次之间设硬门：前一批的反例夹具全绿，才允许开下一批 |

### 批次 2 · 上游止血：声明的来源缺失要出声（层一）

**命中面（P1）**：防的是「合同声明了六个来源，实际只读到五个，守恒面缩掉一整类而无人知晓」。
实跑证据：UX 34→0、11→0，零信号。

**误伤面**：`AR/upstream.md` 是人工补录件，多数需求没有它；`ux-reference/README.md`
在没有界面的需求里也可能不存在。**所以不能一律报缺失**。

**谁来接**：合同声明每个来源的必备性，机器按声明判。

**改动**：

1. `contracts/story-chapters.json` 的 `sources`，每个来源由字符串/对象扩展为带 `required` 的对象：

   ```json
   "sources": {
     "PRD":      { "path": "RR/prd.md",            "required": true  },
     "SE":       { "path": "SR/design.md",         "required": true  },
     "SPEC":     { "path": "spec/spec.md",         "required": true,  "derived": true },
     "DESIGN":   { "path": "AR/design.md",         "required": true,  "derived": true },
     "UPSTREAM": { "path": "AR/upstream.md",       "required": false },
     "UX":       { "path": "ux-reference/README.md","required": false, "warn_if_siblings": "ux-reference" }
   }
   ```

   现有解析已支持「字符串或带 `path` 的对象」（`sourceDocs:299`），只需加读 `required`。
   **`derived` 字段的现有语义不动。**

2. `sourceDocs` 返回值增加缺失清单；`init` 与 `check` 各消费一次：
   - `required: true` 而文件不存在 → **BLOCKER**，报「合同声明的来源 X 不存在：`<路径>`」；
   - `required: false` 而文件不存在 → **记一笔**（`notes`，不拦）；
   - **`warn_if_siblings` 命中时升级为 BLOCKER**：`ux-reference/` 目录里有文件、
     却没有 `README.md`——这正是本轮的实况（2 张 png 在、README 不在）。
     图片在而索引不在，是「导入做了一半」，不是「本需求没有界面」。

3. `init` 的收尾输出加一行来源账：`来源：PRD 40、SE 28、UX 0（ux-reference/ 有 2 个文件但缺 README.md）`。

**不做**：不去改 `import_sources.py` 让它一定产出 README——那是取材侧的另一件事，
本轮只负责**让缺失可见**。（可见之后，是补导入还是补 README，由作者按报错处置。）

**验收**：KG8R-2，含 N8 转正。

### 批次 3 · 图的守恒：判据前移 + 逐章欠账清单（层三 + 邻接缺口）

**这一批是本轮的核心，也是上一版栽跟头的地方。顺序不可颠倒。**

#### 3a. 把 `check` 的形态判前移到 `audit`（P4）

**关键事实**：`check` 判「图片落在 X 章但那一章没有图片引用」所需的全部输入
——`kind`（在 `doc.units`）、`at`（在 `records`）、章内有没有 `![](`（在已渲染的 story.md）
——**在 `audit` 时刻就已经全在内存里**（`cmdAudit` 同时持有两者）。

**改动**：`cmdAudit` 在写完 `audit.json` 之后，对**已渲染的章**跑一遍与 `check ④` 完全相同的形态判，
把结果打印出来（**不写文件、不改退出码**）：

```
  形态欠账（已渲染章）：
    功能说明 —— 欠图片 2 张：PRD:35「签约页示意」、PRD:41「管理页示意」
    业务流程 —— 欠图 1 张：SPEC:205「签约状态流转」
```

**判定逻辑共用同一个函数**，不允许两处各写一份（这正是 D4 教训的推广）：
抽出 `formShortfall(units, records, sections, contract)`，`audit` 与 `check ④` 同调。

**为什么这不是新判据**：同一条判据、同一份代码，只是多在一个更早的时刻跑一次。
作者写完一章就能看见欠了什么，而不是全篇写完后被 `check` 一次性告知。

#### 3b. 逐章欠账清单：把第二步声明的输入真的产出来

**改动**：`cmdAudit` 输出「**下一个待写章欠什么**」，逐条列，不只给计数。
现有的「已分配按落点章：功能说明 37、…」只有章名和条数，
「功能说明 37」里含不含 3 张图看不出来。

新输出（接在现有分布行之后）：

```
  下一个待写章「业务流程」分到 21 条：
    图 2 张   SPEC:205「签约状态流转」、SPEC:225「失败恢复」
    图片 1 张 PRD:51「充值时序」
    表行 9 条、叙述 9 条
```

**只列下一个待写章**（`pending[0]`），不是全部十章——一次给全等于回到 1.0 的任务书体量。
断点续写时它自然指向正确的位置（`pending` 已有现成计算，`cmdAudit:864-871`）。

#### 3c. 作者面：消掉自相矛盾，补上「清单从哪来」

`story-write.md` 第二步的输入表第一行，把「分给本章的那些单元正文」补成可执行的：
**跑 `audit`，它会列出下一个待写章分到哪些单元、其中几张图几张表**。

**同时必须处理 `:161` 与新增文本的冲突**——这是上一版留下的雷：
- `:161` 现有「**图片一张不少、一图一引**」→ 保留，它对应的是「分了落点的图必须画」；
- **不写**「图不必每张都进」「引多引少都不判」这类无限定的许可句。
  要表达「可以不引」，只能连同它的条件一起写（见 3d）。

#### 3d. `material_only` 与数量判据：先证明接得住，再删（P1 的严格应用）

**内网问题 7 是真问题**：30+ 图的 PRD 上，「数量不降级」等价于逼人复刻 PRD。
上一版用 30 图夹具证过：删前 28 条逼引报错，删后 0 条。**这个方向是对的。**

**但上一版直接删了，没证明谁来接。** 这一版的顺序是：

1. **先做 3a + 3b**（前移判据 + 欠账清单）；
2. 用 30 图夹具证明：**分了落点却没画的图，在 `audit` 时刻就报得出来**（不必等到 check）；
3. **然后**才引入 `material_only` 作为第四态，并删除两条数量判据；
4. `material_only` 的形态判：只给图类（`kind ∈ {image, diagram}`）、理由非空。
   **不判理由的措辞**——上一版加过「理由必须点名承载者」，那是在措辞上加验证，属补丁，本版不做。

**放宽账（P1 表格，实施时抄进提交信息）**：

| 删/弱化 | 它防的是什么 | 误伤面 | 谁来接 |
|---|---|---|---|
| 删「整篇形态数不降级」×2 | 材料有图而 story 少画 | 30+ 图材料上逼人复刻 PRD | 3a 前移的逐单元形态判（`audit` + `check` 两个时刻）＋ 3b 的欠账清单让作者写前就知道 |
| diagram 落点判开 `material_only` 口 | 图连落点都没有 | 确实不必进正文的图无处安放 | `material_only` 的形态判 ＋ N4 反例夹具锁住「三态皆空仍报」 |

**验收**：KG8R-3，含 N1–N4 全绿、30 图夹具零逼引、demo 两 case 回灌不新增报错。

#### 4-6 · token 夹死的正向解法

**上一版做法**：标识符的守恒范围从「落点章」放大到**整个附录**。
**这是放宽**——附录是个大草垛，只要附录里任何位置出现过这个标识符就算核到，
与「这个单元的事实在附录有落点」不是一回事。

**这一版做法**：范围缩到**该单元在附录里的那一行**。

- 技术契约类单元本来就由 `appendixBound` 机器直接归附录，它们在附录表里各占一行；
- 含标识符的**叙事**单元：标识符去附录的对应行核，业务语义留在叙事落点章由裁决者核；
- 判定式与 `check ⑩` 共用一个（`IDENTIFIER_SHAPE`），两处一个真源；
- **作用域与 ⑩ 对齐**：⑩ 跳过围栏（`lint-rules.mjs` 的 `inFence`），守恒也跳过
  ——围栏里的图类型词（`flowchart` 这种）不该被赶去附录。

**P1 表格**：

| 弱化 | 它防的是什么 | 误伤面 | 谁来接 |
|---|---|---|---|
| 标识符不再要求出现在叙事落点章 | 标识符所属的事实整个丢失 | 与 ⑩「主叙事不出现工程标识」直接打架，作者无路可走（内网问题 6） | 附录**对应行**的逐行核 ＋ N5 反例夹具 |

#### 4-8b · 报错聚合要重新评估，不默认沿用

**上一版做法**：报错超过 40 条时按判据类聚合，每类打印 5 条样本，全量落 `check-detail.md`。
上一版把它归类为「只改输出形态，判定逻辑零变化」。

**这个归类可能是错的**：消费者是模型，**模型修它看得见的那些**。
实跑中 auto-topup 报 250 条、终端只显示约 45 条样本，其余要模型主动去读
`check-detail.md`——多一步，就多一次可能不做。

**这一版要求**：
1. 聚合**保留**（1000+ 条刷屏确实构成删台账的动力，内网问题 8 是实证）；
2. 但**必须验它对修复率的影响**：KG8R-4 要求在同一份坏产物上，对比「逐条输出」与
   「聚合输出」两种形态下，模型一轮修掉的条数。**这一条只能在 CLI 实跑里测**，
   离线测不出；
3. 若实跑显示聚合降低修复率，**改为「聚合摘要 + 全量逐条」并存**（摘要在前给全局，
   逐条在后不省略），而不是二选一。
