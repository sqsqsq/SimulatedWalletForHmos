## 2. 历史诉求原文（执行者必读，不得再概括）

### 2.1 用户 08-21 原始需求 §2「Story 面向人类叙述友好」（`../../2026-08-21-story全量需求与踩坑记录/00-全量原始需求记录.md` §2）

- Story 面向第一次接触需求的人类评审者，阅读者无需先读 Spec、产品需求、系统设计或代码。
- 文档按照人的理解顺序说明为什么做、涉及谁、怎样解决、业务如何推进、当前特性负责什么、哪里会失败、怎样验收和怎样交付。
- 先说明背景，再解释理解后文必需的术语。
- 标题使用真实业务名称，简短、自然并准确概括下文。
- 标题不能使用模板占位语、模型提问、机械分类词、解释性长句和明显的 AI 式表达。
- 三级、四级标题根据真实业务从属关系自然生成，不为了形式对称强制出现。
- 完整业务过程与当前特性功能分别说明：业务过程说明需求怎样推进和在哪里交接，功能说明展开当前特性承担的页面、动作、状态和分支。
- 正常受限结果与真正异常分开说明。
- 连贯的原因、方案、取舍和影响使用自然叙述；表格、流程图、状态图、时序图和图片按实际表达需要使用。
- 接口、字段、错误码、配置、事件和追溯信息必须保留，但不能打断面向人的主叙述。
- 验收按照真实业务场景或结果组织，每个原始验收编号独立保留，并提供可观察的通过条件。
- Story 只表达已经成立的需求和决定，未确认事项进入 Review，不在 Story 中生成"待确认事项"或"评审导读"。
- Story 保留以下骨架（§3.1），后续优化重点是让模型基于真实需求内容写出自然标题、连贯正文和合理层级，而不是继续更换骨架。
- 人读改写完成后必须再次核对全部事实，确保叙述优化没有造成内容丢失或重新引入重复。

### 2.2 冻结 01「内容守恒与去重」C1–C5（`test/story/spec/2026-08-21-story四项需求澄清/01-Story内容守恒与去重.md`）

- **C1 先完整盘点，再做减法**：不预先用「相关/无关」筛选事实；先完整盘点再识别重复；只有已证明为重复的表达才能删除；去重后仍对原始材料全部有效事实逐项反查。
- **C2 重复按「事实、问题和新增信息」共同判断**：两处谈到同一事实不自动构成重复；同一事实、回答同一个问题、后一处没有该位置独有的信息或判断时才是重复；同一事实为不同章节职责提供独有信息时可分别出现（如流程说阶段与顺序、验收说可观察条件）。
- **C3 按读者要回答的问题选择主叙述位置**：主叙述位置由事实主要帮助读者回答的问题决定，不按来源文件、标题、关键词或固定材料类型；背景回答为什么做及当前特性位置；术语在背景后、业务方案前；范围回答当前特性与相关特性各负责什么；业务方案回答各方怎样协作、采用什么方案和业务规则；业务流程回答怎样推进、在哪里分支和交接；功能说明回答页面、动作、状态和正常受限结果；异常与恢复回答真正失败后的用户表现、业务结果和恢复方式；验收回答怎样观察到做对；交付与上线回答怎样联调、开放、观察和回退；附录承载接口、数据、配置、事件、工程范围和追溯等机器细节；一事实多影响时只在主位置完整表述。
- **C4 完整逐项核对必须留下独立证据**：每项有效事实有可审查的核对记录（来源事实、是否进入、主叙述位置、其它位置独有信息、重复合并、处置）；记录不进正文不随归档；附录追溯只保留人类评审需要的信息。
- **C5 保留章节合同的安全回退**：候选词根匹配不到时回落读整篇；已回滚的「关键词硬匹配、匹配不到判失败」不得以任何形式回来；「标题未命中」与「源文件缺失」是两件事。

### 2.3 冻结 02「面向人类叙述」C1–C3（同目录 `02-Story面向人类叙述.md`）

- **C1**：需求 2 是需求 1 结果上的人读改写，不新增、删除或改变任何需求事实、取舍、边界和验收含义；改写后重新逐项核对，防止丢失、走样或重复回流。
- **C2**：在固定顶层骨架内重组——可调整事实顺序、跨段重组、合并或拆分三级四级章节、补必要承接；标题使用真实业务名称；正文、有序 / 无序列表、任务列表、强调、引用、表格、行内代码 / 代码块、流程图、状态图、时序图、图片和链接都按内容的实际关系自然使用；**不为了形式丰富设置每章必须使用的 Markdown 类型或数量配额**；脚本只检查结构和引用完整性，表达选择是否合理由语义评价判断；图片引用不强制集中到固定章节，也不能在改写中丢失图片承载的信息；链接保留说明文字与原始目标。
- **C3**：全局规划 → 逐章成文 → 全文统稿 → 全量复核；章节职责说明主要回答的问题，不能成为隐藏材料或提前删除事实的筛选器；每章能读全部同轮材料；每章完成后核对本章应回答的问题、图片和链接；统稿只处理承接、顺序、标题自然度、用词口径和跨章重复，不重写整篇、不压缩事实；核对记录只用于审计。

### 2.4 08-21 成文方案 §2「人读表达」（`../../2026-08-21-story四项需求实现方案/02-Story面向人类阅读成文方案.md`）

- 先说明本段要解决的问题或结论，再解释原因、参与者、条件、过程和结果。
- 标题使用真实业务名称，H3/H4 只反映真实从属关系。
- 连续因果使用正文；有真实顺序时用有序列表；并列内容用无序列表；横向比较才用表格。
- 强调、引用、代码、图、图片和链接只在能改善理解时使用。
- 接口、字段、错误码、配置和事件放在其影响的功能、异常、验收或附录中，不打断主叙述。

### 2.5 1.0 `rules.md` 第 2 条（`e96e90fc`）

> 表达形态与数量不得降级：源材料用流程图、状态机或表格表达的内容，对应章节必须保持同类形态，且图的数量不少于源。把流程图压成 `A → B → C` 箭头文字、把表格压成散文，都算降级。

### 2.6 批次 3 删掉、本批恢复的判据 `story_reader_fitness (3)`

> 表达贴合内容——能一句话说清的不建表；并列多项且需逐条比对的才建表；流程用图。通篇是表、叙述只在表间做连接词，即不达标。

### 2.7 外部风格指南（阈值来源）

- Google developer documentation style guide（Tables / Lists）：表只用于二维数据（每项 ≥3 个相关属性）；只有一列的表改列表；只有一行不成表。
- Microsoft writing style guide：短句短段；每段结论先行；步骤超过 12 步拆节；复杂段落换成列表或表格。

### 2.8 历史教训（为什么会反复）

| 轮次 | 代理指标 | writer 最省力解 | 畸形 |
|---|---|---|---|
| 1.0 | 合同按章路由材料 + 逐章必答 | 每章各抄一遍 | 同一事实四章重复；800K 上下文 |
| 2.0/2.1 十章 | 关键词硬匹配章节、形态判据管语义、装配器降级标题、附录复述规约原文 | 换皮通过 | 半途双轨、离线全绿掩盖行为未验（踩坑 #1–#26） |
| 批次 2 | 不进要写理由 | 写「不相关」 | 59% 单元不进 |
| 批次 3 | token 整篇出现且无附录 | 抄 spec 原句、类名、事件 ID | 工程细节泄漏、spec 腔；verifier 0 未讲清；术语成列表、流程图丢 |

**原则**：机器只守可核事实（数值 / 编号 / 读者认识的名字 / 图 / 表 / 结构 / 长度）；语义靠逐问逐单元裁决 + 对抗测试；不给 writer 任何能靠抄写通过的判据；阈值与形态规则是合同数据不是代码。

## 4. 附录与语言红线（M1）

- **附录是工程标识的唯一落点**：接口、字段、存储键、配置项、事件、错误码、工程范围、规约编号判定表只在附录成表；主叙事写中文业务名与中文规约名。守恒 token（接口名、键名、事件 ID、编号）在附录表里可核——`check ②` 不变，落点自然在附录。
- **语言红线**（lint，作用域 = 附录外主叙事）：仓内标识（类名 / 方法 / 事件 ID / 正则）、规约编号、检索措辞（「检索…零命中」）、来源括注「（本工程设定…）」「（上游约束…）」、文档坐标、模板占位标题、提问式 / 机械分类 / AI 腔标题。词表与形态在 `lint-rules.mjs` 作为数据；`kinds` 由合同 `language_redline` 声明。

## 5. 判据面（M2 / M3 / M4 / M5）

### 5.1 verifier（`phases/story-verify.md`，逐对 + 逐问 + 逐章）

- 逐单元（已有）：`by: author` 的单元 → 讲清 + 引文 / 未讲清 + 缺什么。
- **逐问**：每章每个 `questions[]` → 答了 + 引文 / 没答 + 缺什么。产物 `story-verdicts.md` 第二张表 `| 章 | 问题 | 裁决 | 引文 |`。
- **逐章可读**（13 条人读要求中语义性的）：业务过程与本特性功能是否分开；正常受限结果与真正异常是否分开；取舍有无被否方案与理由；标题是否真实业务名且从属自然；**表达贴合**（§2.6 原文）；第一次接触者读完能否答「为什么做 / 怎么做 / 哪里会坏 / 怎么算对」。产物第三张表 `| 章 | 维度 | 裁决 | 依据 |`。
- `check ⑥` 扩：三张表都要齐、引文 ≥12 字且在该章、非回声。

### 5.2 lint（机械；全部阈值来自合同 `readability` / `language_redline`）

- 章序与标题：十章顺序；术语在背景后；标题非占位（`{{`）、非提问（`？` 结尾）、非 AI 腔词表（「综上」「值得注意的是」等，数据）。
- 验收：`keep` 编号每个独立成行且在验收章。
- 未确认事项：正文不出现「待确认」「评审导读」段。
- **长文红线**：段落 > `paragraph_max_chars` FAIL；章 > `chapter_split_at_chars` 且无 H3 / 列表 / 表 FAIL；
  有序列表 > `ordered_steps_max` 项 FAIL。
  **不设句长红线**（用户 2026-08-29 裁定）：拆长段、拆长章一定更可读，拆句子不然——
  中文技术叙述里 45–60 字的完整复句很常见，逼着断句会写出半截话和断裂的指代，
  而 writer 最省力的做法正是在逗号处一刀切：形式过了、读起来更差。
  这与踩坑 #2「形态判据管语义 → 换皮四次」同形。句子啰嗦、该断不断归 verifier
  的「表达贴合」维度（§5.1）——**它是语义问题，机器判不了**。
- **重复**：规范化（去空白标点）后相同段落（≥20 字）= 0。
- **形态守恒**（M4）：`diagram` 单元落点章含围栏图；`image` 单元以图片引用落点；
  story 图数 ≥ 源图数、表数 ≥ 源表数；`list_item` 不约束。不设「每章必须有表/图」。
- `table_row` 的口径**与 M5 的「一行不成表」对齐**：该章分到 **≥2 个** `table_row` 单元时，
  要求该章有表且这些行 ≥1 格原文在表内；**只分到 1 个时不要求成表**，只要求该行原文
  在该章出现。理由与 M4 自己的立意一致——它防的是「把表压成散文」这种降级，
  而一行本来就不构成表（§2.7 Google 风格指南），不存在降级。
  不写明这一条，就会出现机器要求建表、verifier 判它不该建表的相斥判定。
- 现 `check ①③④⑤⑧⑨` 保留（① 改十章）。

### 5.3 作业书（`phases/story-write.md`）

- 分配 → 逐章渲染流程不变；每章输入 = 分配单元 + 本章 `questions` + 上一章结尾 + **选择规则表**（下表，§2.4 + §2.7 合成）+ 语言红线 + 长文阈值。

| 内容 | 形态 |
|---|---|
| 原因、方案、取舍、影响 | 正文，结论先行 |
| 有真实先后的步骤 | 有序列表（>12 步拆节） |
| 并列项 | 无序列表 |
| ≥3 个属性逐项比对 | 表（一列的改列表，一行的不成表） |
| 流程 / 状态流转 / 多方交互 | flowchart / 状态图 / 时序图 |
| 界面 | 图片 + 一句说明它画的是什么 |
| 关键结论、硬约束 | 强调 |
| 上游原话、裁定原话 | 引用 |
| 接口、字段、存储键、配置、事件 | 附录表 |
| 标题 | 短、真实业务名；H3/H4 只反映真实从属 |

- 13 条人读要求原文（§2.1）整段进作业书「读者是谁」之后。

## 6. 不丢 / 不重的验收口径（M3）

- **不丢**：内容基线 story 作为第五份材料枚举单元 → 对新 story 跑 `audit` → 每个基线单元有落点（机器或 verifier「讲清」）；缺失逐条点名；人核完整率 ≥ 90%（批次 3 KC-5 口径）。删事实对抗测试常驻（每 Case 删 5 个事实 → verifier ≥5 条未讲清）。
- **不重**：分配恰好一处（机器）；相同段落 = 0（lint）；verifier 逐问表里同一事实在两章都作为「答了」的引文 → 标「重复」。
- 只在测试域跑，不进生产链。
