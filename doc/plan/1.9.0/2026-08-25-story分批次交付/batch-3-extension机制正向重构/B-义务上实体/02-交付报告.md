## 五、实施中坐实的缺陷

| # | 缺陷 | 怎么暴露的 | 处置 |
|---|---|---|---|
| N1 | markdown 里 `\|` 是字面竖线，而表格解析按裸 `\|` 简单切——探针列必然用到正则的或运算符，切完后半格顶掉右边所有列 | UX-01 的探针解析出 `\b(left\` | `markdownTable` 改逐字符扫描、认 `\|` 转义 |
| N2 | **探针把注释里的提及当成真引用**——零调用的角色类判过了 | KB-4 第二半构造的最小场景 | 加 `blankComments`（保留行数列位以便报行号）。**这正是基线「不分声明/调用/注释」的形态，我第一版重蹈了** |
| N3 | 探针值被 markdown 强调清理吃掉 `*`，`\s*` 悄悄变成 `\s` | 解析结果比对原文 | 探针列只剥反引号，不剥 `*` |
| N4 | 经 Python 生成 JS 时 `\\\|` 被吃成 `\\`，`/\\\|/g` 里的 `\|` 成了正则或运算符，替换出 `\|a\|b\|s\|e...` | 派生结果乱码 | 坑 #36 的又一次。改用 Edit 直接写，不走转义链 |
| N5 | 机制层注释里写了 Case 编号举例 | 台账 M02 当场 FAIL | G7 红线，改中性表述 |
| N6 | A03 checker 把文件末尾换行算成内容行，每份 author.md 多 1 行 | `plan/author.md` 60 行被判 61 超标 | 口径修正（与子批 A 的「判据是**」同类） |
| N7 | `subprocess` 在 Windows 上 `text=True` 走 GBK，中文输出让 stdout 解码失败变成 None——「跑了没输出」与「判据没过」同形 | B01 两面都报「没有输出」 | 显式 utf-8 + `errors=replace` |
| N8 | **checker 按夹具名分支**，而 `label` 实际是目录名 `bad`/`good`，判定侥幸对、理由全反 | 看 PASS 的证据文案时发现 | 根因是把判定与期望写在同一处，两边一起错发现不了。改成如实判定，正反由框架 `self_check` 核对 |

N2、N4 是同一类：**基线记过的坑，实现时又踩了一遍**。坑册里写着「不分声明/调用/注释」和
「勿走转义链」，但写代码时没回头查。
