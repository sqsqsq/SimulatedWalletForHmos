# 子批 C · story 机制 · 方案

> 自足件。上位：[../03-实施切分.md](../03-实施切分.md) §3 批次 C（KC-1…KC-7）；设计 [../01-正向设计.md](../01-正向设计.md) §6。

## 0. 一句话

**删掉逐章生产线，story 由独立 writer 一份文档写成；守恒从「按章数数」改成「整篇事实级 token」。**

## 1. 现在为什么不行

`story-build.mjs` 1337 行是 **1.0 的逐章装配器**（`scaffold` 生成 14 份逐章任务书 → 各章分别写 →
`build` 装配）。它的守恒是「每章把取材节的每行表格/数值/反引号写全」——**同一个事实被四个章节
合同各指一次，于是被强制写四遍**（PIT-040/041）。

`story-chapters.json` 399 行里，每章带 `inputs`（取材路标）+ `must_answer`（逐章必答）+ `form`。
这三样正是逐章生产线的核心：它们把「读者要什么」偷换成了「这一章该从哪几节抄什么」。

而 story 在 **spec 会话末尾、540K 上下文里**写成——诊断实测该阶段上下文从 11K 单调涨到 818K、
零 compaction，story 是最后写的那一份。

## 2. 目标形态

### 2.1 位置：`/story` 链 S5

```
S1 取材 → S2 导入+初析 → S3 关卡 → S4 收口 AR/design.md → [framework spec 闭环]
→ S5 成文（writer 子 agent）→ S6 归档
```

- `story_flow.py` 增 mode `story`（登记成文态；前置：`story-build check` 通过）；`archived` 前置改为成文态。
- spec 阶段：`spec/post_check.mjs` **删除全部 story 判据**，只留 §9/§10/§11 与 story-flow 收口。

### 2.2 writer 子 agent

- 主 agent 在 S5 用 Task 启动子 agent（新鲜上下文），prompt = `phases/story-write.md` + feature 名。
- **输入包（固定清单）**：`templates/story-template.md`、`RR/prd.md`、`SR/design.md`、`AR/design.md`、
  `AR/upstream.md`（存在时）、`spec/spec.md`、`AR/story-src/decisions.json`、
  `AR/story-src/source-units.json`（`story-build init` 产）。
- 子 agent 内部循环：写 → `audit` → 对无落点单元补写或标 `covered_by` → `check` 通过才返回。
- 主 agent 只收结果，不重读材料。

### 2.3 来源单元枚举（新建）

- 单元类型：`paragraph` / `list_item` / `table_row` / `image` / `link` / `diagram`（mermaid、flowchart 围栏）
  / `blockquote` / `code`（yaml、json 围栏）。
- token 取**全部单元格**：反引号跨度、ASCII 标识符 `[A-Za-z_][A-Za-z0-9_.]{3,}`、带量纲数值、
  图片 basename、URL、合同声明的编号形态。
- 跨材料重复内容保留 `also_in`，透传进 audit。

**基线上没有这个文件**——`source-units` 全域零命中。它是**新建**，替代 `story-build.mjs` 里的
取材与逐章守恒函数（`extractOne` / `extractSection` / `findMissingFacts` / `findMissingIdentifiers`）。

### 2.4 `story-chapters.json` 从 0 重写

只留：`sources`（来源文档映射）+ 14 章的 `id`/`title`/`question`（这一章回答读者什么问题）
+ `machine_facing`（`unit_kinds` + `table_columns`）+ `id_shapes`（`keep`/`drop`）。

**删除** `inputs`（逐章取材路标）、`must_answer`（逐章必答）、`form`——它们是逐章生产线的核心。

### 2.5 `story-build.mjs` 从 0 重写，四命令

| 命令 | 做什么 |
|---|---|
| `init` | 枚举来源单元 → `AR/story-src/source-units.json`；建 `decisions.json` 骨架（六类 `scanned_categories`） |
| `audit` | 三态核对：`at`（机器按 token 命中定，或作者填）/ `covered_by`（作者填）/ `machine_facing`（只能机器打标） |
| `check` | 14 标题与顺序、整篇 token 守恒、编号形态、diagram 单元有落点、`scanned_categories` 齐、review 语法 |
| `build` | 由 `decisions.json` 渲染 `AR/review.md`（机器区重算、人工区逐字节保留） |

**删除**：`scaffold`、`assemble`、逐章守恒、`ids.json`、`knowledge.json` 与附录渲染
（`renderKnowledgeAppendix` / `renderPatternAppendix`）。

### 2.6 守恒判据（`check`，整篇）

1. 14 个 `## ` 标题与顺序 = 合同；空节恰为「本需求不涉及。」
2. **非机器面单元的每个 token，在 story 整篇或 `decisions.json` 里有落点**；缺哪个点名哪个
3. `id_shapes.drop` 形态出现即 FAIL；`keep` 形态的上游验收编号须在「质量与验收」章出现
4. 带量纲数值须上游或 decisions 有据（既有）
5. 图片可解析、全篇唯一；`diagram` 单元须有 `at` 或 `covered_by`
6. 归档件自包含四红线、术语表首列守恒（既有 `merge-story`）

### 2.7 三态核对（`audit.json`）

| 态 | 谁填 | 机器判 |
|---|---|---|
| `at: <标题>` | 机器（token 命中的节）或作者 | 标题在册；作者填的须该节含该单元 ≥1 token |
| `covered_by: <单元键>` | 作者 | 目标存在、目标 `at` 非空、目标 ≠ 自己、共享 ≥1 token 或同 `also_in` 组 |
| `machine_facing: true` | 机器 | 只能由枚举器打标，作者不得改 |

**三态之外 → FAIL**。基线的自由文本 `reason` 是逃生口：实测 161/272 单元「不进」、
理由去重后只有 2 种，而门禁只判非空。

### 2.8 `merge-story.mjs` 重写

只留归档件自包含四红线 + 术语表首列守恒。**删**技术契约首列守恒（被 §2.6 判据 2 覆盖）与编号守恒。

## 6. 风险

1. **`story-build.mjs` 1337 行里混着仍需保留的能力**：`decisions.json` 的机器区/人工区分界渲染
   （批次 2 验证过的自解释语法）、图片路径重算与引用完整性、CRLF 安全分行。重写前先列清单，
   逐条对照（同 KA-10 的做法）。
2. **`story-chapters.json` 的 `inputs` 一删，现有 AR90004 产物的校验会全变**——它是对照样本，
   不入回归目标集，但 KC-7 要求新 `check` 对它有区分力。
3. **本子批收口时 §0 ②③⑤ 首次全量成立**——A/B 移交的四项必须都做完，否则退场 grep 不会零命中。
