> 日期：2026-08-18

## 0. 结论先行

本轮已经证明两件不同的事：

1. **规约与设计模式确实能够作用于真实需求产物。** spec 正确登记了 `decision-tree` 与
   `page-interaction`；plan 进一步生成了设计模式应用表、应用域约束处置，并把模式投影进
   `contracts.yaml` 与 `use-cases.yaml`。因此，用户最初关心的“知识是否真的生效”已经得到
   正向实证，不需要为了观测而给 Story 增加逐条 `rule_id` 信号。
2. **最新 Story 还不是一份合格的人类评审材料。** 它的信息覆盖较完整，机械门禁也通过，
   但叙述重复、层级扁平、决策展开噪声、范围表述矛盾，评审者需要先自行整理，才能拿它开会。

本轮另有一个决定模式适配方案的重要前提：当前两份 design-pattern 知识基于 demo SDK 生成，
只承担本仓的机制验证与文档结构示范；内网目标仓已经具备这两个模式各自的真实 Skill、真实 SDK，
并存在真实业务应用场景。内网适配不是给 demo API 换名字，而是由目标仓模型读取真实 Skill，
再以 SDK 和既有代码完成事实校准，最终重写为本扩展可消费的项目知识。

所以，后续优化不再扩张知识路由，也不靠增加更多门禁“修”阅读体验；应当正向建立一套
**面向人的 Story 编辑与装配模型**，同时把实跑 harness 的阶段终态和进程生命周期做完整。

本方案完成后应形成以下稳定闭环：

```text
来源材料
  → 确定性取材
  → 章节编辑任务书（内部）
  → 面向人的完整需求叙事
  → 同文档内的可查询附录
  → 独立人类语义评审

适用知识
  → spec 中形成具体要求/模式信号
  → plan 中形成约束处置/模式应用
  → contracts 与 use-cases 承接实现契约
```

两条链路相互验证，但不能混写：Story 服务评审者；知识登记和阶段追踪服务开发流程。

## 2. 最新 Story 的人读审视

### 2.1 已经做对的部分

最新 `story.md` 的前部能交代业务背景、目标、完整旅程、主要参与方和范围。事实覆盖与结构素材
基本齐备，流程图、状态、接口、异常、合规和验收也都有落点。问题不是“没内容”，而是内容被
装配成了一份需要读者二次编辑的材料。

### 2.2 影响人类阅读的实质问题

1. **篇章层级形式化而非叙述化。** 全文 669 行，几乎每章都出现同名二级和三级标题，例如
   `## 背景与目标` 后立即跟 `### 背景与目标`。目录看似完整，但每章没有形成新的阅读问题，
   人必须在大量平级材料中自行判断主次。
2. **开篇存在直接破坏阅读的拼接句。** 第 35 行把“承载说明”“范围指引”“拆分决策”连续拼成
   一句，缺少标点和逻辑关系。这不是文案瑕疵，而是装配边界不清。
3. **决策引用遮蔽了业务含义。** 第 51 行等位置把正文、完整决策值、开放状态和编号嵌套展开，
   形成“结论套结论”的长括号。读者先看到登记机制，后看到真正结论。
4. **同一事实被不同章节重新讲述。** 参与方职责在全景、范围、上线协同重复；成功标准在开头和
   验收章重复；安全、性能与 UX 在合规总览、NFR、UX、验收中多轮重复。上线章与背景章还有
   4 行完全相同的表格行，全景与上线章共享 3 个长单元格。
5. **Story 与 Spec 的职责混杂。** “流程契约”“检索零命中”、完整规则编号、模拟实现依据等
   工程取证语汇直接进入主叙述。它们对实现有用，但让人类评审者不断切换到工具/代码视角。
6. **关键评审事项被埋在细节里。** “实名能力当前只是占位”“端云接口当前使用模拟数据”以及
   “1500 ms 是无上游依据的工程设定”都影响需求是否可交付，却散落在长表格和多重括号中，
   没有成为评审者一眼能看到的待确认事项。
7. **范围口径自相矛盾。** 正文声明 `in_scope_modules` 只有 `WalletMain`，同时又写 `Phone`
   需要登记新增页面导航。只要发生物理文件修改，模块就不能一边被声明为范围外、一边被安排修改；
   “业务归属”与“物理改动范围”被混成了一个概念。

### 2.3 指标只能说明趋势，不能代替人读结论

当前采集结果为 267 行表格、106 行正文、表格占比 0.72；旧方案中的 V1.3 与 V2.3 未达标，
V1.4、V2.4、V3.2、V5.2 达标。这些数据能帮助定位“哪里可能拥挤或重复”，但不能直接推出
Story 好或坏。表格比例、篇幅、相同单元格数今后都只作为诊断素材，不设为语义质量门禁。

### 3.1 实施前正向性审视

本方案按“产品定义 → 编辑合同 → 确定性装配 → 阶段消费 → 运行状态”的完整生成链设计，问题均落在
最早责任层，不依赖 AR90004、`Phone`、某个标题词或某个模式的特判。实施时按以下边界保持单一真源：

| 责任 | 唯一真源 | 消费者 |
|---|---|---|
| Story 阅读目标与撰写原则 | Story `rules.md` | 撰写模型、人类评审者 |
| 章节顺序、取材和编辑任务 | `story-chapters.json` | scaffold、build、check |
| 来源选择语义 | Story 装配器共享选择函数 | scaffold、build、check |
| 决策事实 | `AR/story-src/decisions.json` | Story 装配器与附录投影 |
| 目标仓模式绑定状态 | `ADAPTATION.md` 的“当前仓绑定记录” | 适配执行者、自检入口 |
| 运行期模式知识 | `knowledge/design-patterns/` | spec、plan、coding、review |
| 测试执行状态 | `test/story` 的 run / phase 状态文件 | start、poll、stop、resume、report |

由此确认三项实施约束：

1. 运行期模式 README 不承载 `confirmed`、SDK 指纹或适配进度，避免维护元数据污染 plan/coding；
2. Story 脚本只判断可确定的结构错误，人读质量仍由独立语义评价负责；
3. harness 只汇总适用阶段，不用进程退出状态覆盖已经固化的阶段质量。

以上边界闭合后，工作包之间是顺序承接关系，不需要通过末端补丁互相兜底，可以作为本轮实施基线。

## 4. Human-First Story 正向设计

### 4.1 Story 的唯一产品定义

`AR/story.md` 是给需求评审者直接阅读和开会使用的完整材料。合格的 Story 应让第一次接触需求的
评审者只读这一份文档就能回答：

- 为什么做，用户和业务得到什么；
- 本次做什么、不做什么，谁参与，边界在哪里；
- 用户从进入到完成经历什么，关键状态和异常如何变化；
- 方案为何这样设计，哪些结论已定，哪些必须由人确认；
- 有哪些实现、合规、兼容、上线和验收影响。

“完整”不等于“把所有上游表格再抄一遍”。主叙述负责建立理解；同一份 Story 的附录负责承载
需要查阅的完整接口、错误码、验收映射、约束编号与来源索引。

### 4.2 三层阅读结构

Story 采用三层阅读深度，而不是固定章数或固定表格数量：

1. **评审导读**：一屏内说明问题、目标、本次边界、主流程、最重要风险和待确认项。
2. **完整需求叙事**：按理解顺序展开业务全景、用户旅程、场景与状态、关键系统边界、异常恢复、
   交付影响和验收。每节必须回答一个新的读者问题，不能回到前文重新讲同一张全景。
3. **查询附录**：放完整接口签名、错误码、数据字段、全量验收映射、规约编号和来源索引。
   附录仍属于 Story，因此不破坏“只读一份即可评审”，但不会打断主线。

这是一种编辑原则，不是 7 章硬模板。简单需求可以合并章节，复杂需求可以拆分；唯一不变的是
阅读顺序从“理解需求”逐步收敛到“核对细节”。

### 4.3 章节合同改为编辑任务书

现有章节合同继续承担逐章装配和事实守恒，但从“素材清单”升级为内部编辑任务书。每章至少说明：

| 内部字段 | 作用 |
|---|---|
| `reader_question` | 读完本章，评审者应得到什么答案 |
| `primary_sources` | 本章拥有首次解释权的来源 |
| `supporting_sources` | 只供补充，不得整段复制的来源 |
| `already_explained` | 前文已经建立的事实，本章只引用其结论 |
| `expression_hint` | 根据内容建议使用段落、列表、表格或图；不是固定配额 |
| `review_focus` | 本章必须让人看到的风险、假设或开放决策 |

这些字段只存在于撰写和装配过程，不得渲染到 Story。不得在最终文档中出现 fact id、知识路由、
prompt 指令、来源选择器或“为了通过检查”等内部语义。

### 4.4 确定性来源选择

来源选择建立统一、通用的引用协议：

- 章节来源只能使用**精确标题路径**、锚定标题正则或显式 `whole: true`；不再使用宽泛子串命中。
- 一级标题不参与章节匹配；只有明确声明 `whole: true` 才能取整篇。
- 必需来源未命中立即失败，并报告期望标题与候选标题；可选来源未命中只记录 skip。
- 禁止“没找到章节就静默退化为整篇”。
- 同一选择器实现被 scaffold、build 和 check 共同调用，避免三个阶段各自解释。
- 规则保持业务无关：不为“协同”、`Phone` 或 AR90004 写特例。

这会从源头消除“一个模糊词命中上游 H1，整篇材料被灌入某章”的问题。

### 4.5 全文事实按自然归宿守恒

事实覆盖从“每章都带一份素材”改为“整份 Story 中每类事实有自然归宿”：

| 事实类型 | 主落点 |
|---|---|
| 问题、目标、用户价值 | 评审导读 / 背景 |
| 端到端旅程与参与关系 | 全景 / 用户旅程 |
| 本次范围、明确不做、物理修改范围 | 范围 |
| 页面、状态、异常和恢复 | 对应场景章节 |
| 已定取舍与理由 | 对应对象首次出现处 |
| 开放假设、工程设定、外部依赖 | 评审重点 / 风险 |
| 完整接口、错误码、字段、规则编号 | 查询附录 |
| 验收结论 | 验收章节；导读只概括成功定义 |

装配器只保证来源事实有合法落点、引用可解析和附录可查询，不把同一事实复制到每个可能相关的章节。

### 4.6 面向人的决策模型

决策数据明确拆成五种含义：

- `display_text`：正文首次出现时使用的自然结论；是可内联纯文本，不含列表、表格或二次引用；
- `rationale`：理由与取舍，只在需要解释的自然位置或评审记录中展开；
- `status`：已定 / 开放；
- `source`：结论来自哪里；
- `impact`：对范围、体验、实现或上线的影响。

渲染规则：

- 已定决策在正文像正常叙述一样出现，编号只在首次出现或附录提供轻量回查；
- 开放决策必须进入显眼的“待确认事项”，正文表达当前建议及不确认的影响；
- 同一处不得由作者先抄结论，再让渲染器展开同一结论；
- 不用嵌套括号承载状态、编号、理由和正文；
- 不按字符数机械截断决策，也不把“≤40 字”设为质量门禁。

脚本只拦截空投影、未解析占位符、嵌套引用、重复包裹和非法块级内容。是否简洁、是否像人话，由独立
语义评审判断。

### 4.7 重复信息的编辑策略

- 每项事实选择一个主叙述位置，后文需要时用自然短引述或章节指引，不再复制整行/整表。
- 安全、范围红线等确有必要的重复允许保留，但每次重复必须服务于不同决策场景。
- 精确重复、跨章共享长单元格和章长只作为评审线索；脚本不自动删除，也不因计数超阈值判 Story 失败。
- 相邻同名标题、完全相同的连续段落属于确定性装配错误，可以机械拦截。

### 4.8 Story 与 Spec 的清晰边界

| Story 主叙述 | Story 查询附录 / Spec |
|---|---|
| 用户行为、业务规则的含义与影响 | 完整接口签名与字段枚举 |
| 系统边界及参与方如何协同 | 全量错误码与映射表 |
| 关键状态、异常、恢复与体验 | 约束 `rule_id`、追踪矩阵 |
| 为什么选择该方案、还缺什么确认 | 机器消费的契约坐标与实现清单 |

Story 主叙述不再出现“检索零命中”“流程契约”等实现取证语言。确有评审意义时，应翻译成人类结论，
例如“当前工程尚无可复用的端云封装，因此本次先以同签名模拟层完成端侧闭环；真实联调仍是上线前置条件”。

### 4.9 范围表达使用现有 SSOT，不扩 framework

- `in_scope_modules` 包含所有会发生物理文件修改的模块。
- Story 另用自然语言区分“业务主责模块”和“宿主装配改动”；例如 WalletMain 承担业务，Phone 只做导航装配。
- `integration_points` 写清确切文件、符号和动作，不能用“仅消费”掩盖实际修改。
- `out_of_scope_modules` 不得包含本需求会修改的模块。
- plan 若发现新增物理改动模块，应按既有 correction 流程回到 spec 修正范围，而不是在 plan 中静默扩大。
- 检查落在扩展侧 spec/story 规则与测试，不新增 `framework/` 判据，也不硬编码某个模块名。

## 5. 规约与设计模式：保留有效链路，补齐验证而不污染 Story

### 5.1 生效的判定

“已生效”不是指所有规约、所有模式在每个需求中全部出现，而是：

1. 先根据需求判断是否适用；
2. 适用规约在 spec 形成具体、可执行要求；
3. 适用模式在 spec 留下正确 `pattern_id` 信号；
4. plan 对每项适用知识给出处置，并投影到 contracts / use-cases；
5. 不适用项保持无污染。

AR90004 已经正向证明前四步。后续不再给 Story 增加“规约命中台账”；人类回执只给整体结论，只有失败、
豁免或冲突时才展开具体 `rule_id`。

### 5.2 后续只补两类验证

- **正例保持**：AR90004 继续命中 `decision-tree` 与 `page-interaction`，plan 应用表、应用域约束处置、
  contracts 与 use-cases 投影不得回退。
- **负例无污染**：增加一个简单线性需求，允许模式信号为“无”，plan 不产生伪模式实例；规约也只消费
  实际适用项。

coding / review 的真实落地由用户在内网验证，本仓本轮到 plan 正式闭环即停止。

### 5.3 内网真实模式的四方校准

内网适配时，四类来源各有唯一职责，发生冲突时不得混为“都可参考”：

| 来源 | 权威范围 | 冲突处置 |
|---|---|---|
| 内网设计模式 Skill | 模式意图、适用/不适用边界、分解方法、设计风格与标准落法 | 设计语义以 Skill 为准，但其中 SDK 断言仍须由真实 SDK 复核 |
| 真实 SDK 类型声明与源码 | 包名、类型、方法、字段及运行时行为 | 运行时事实以 SDK 为准，不用 Skill 或旧代码覆盖 |
| 目标仓既有业务应用场景 | 架构落点、组合方式、生命周期、上下文所有权及已落地工程惯例 | 对比多个案例后提炼；单个历史写法不能自动升级为规则 |
| 当前 demo design-pattern 文档 | README 路由、上下篇分读者、契约投影、SDK 事实/使用约定分层等承载形式 | 只继承结构，不继承 demo API、示例代码或工程结论 |

目标仓模型必须先完整读取对应 Skill，再完成以下适配动作：

1. 定位真实 SDK 的包名、版本、依赖声明、导出类型和实现源码；确认哪些字段运行时读取、哪些只是声明。
2. 扫描全仓对该 SDK 的 import、Builder、Manager、节点/动作接口与 context 实现，列出已有业务实例。
3. 每个模式至少选一个规范主案例和一个复杂/边界案例；若存在两个模式组合使用的实例，必须单独取证。
4. 沿真实调用链读完入口、编排对象、context、节点/动作、页面或服务、测试及停止/恢复路径。
5. 将结论分为“SDK 保证”“工程约定”“单个案例偶然写法”；只有前两类进入模式知识。
6. 重新核对 README 的适用单元和路由信号；“上篇跨工程稳定”只能作为初始假设，不能跳过真实 Skill
   与业务场景复核。
7. 重写每份模式文档的契约投影、SDK 行为、角色落点、可编译骨架、使用约定和反模式；清除所有 demo 锚点。

若 Skill、SDK 源码或真实业务实例任一关键来源不可访问，相关模式保持 `未确认`，明确缺失证据并停止
发布该模式的目标仓编码指导，不得以 demo 内容或平台常识补空。

### 5.4 适配指南的自包含执行合同

ADAPTATION 保留现有“本仓适配 / 移植新工程”“逐项适配”“规约维护”“回灌”结构，只补齐以下执行合同：

1. **入口明确**：在模式适配步骤中明确要求读取目标仓已安装的设计模式 Skill；Skill 的实际标识或路径
   由目标仓能力目录发现，不把内网专有路径硬编码进可移植文档。
2. **证据明确**：每个模式形成目标仓绑定记录，至少含 `pattern_id`、Skill 引用、SDK 包名/版本、
   类型或源码指纹、代表性业务实例、确认状态与未决项。
3. **单一落点**：绑定记录集中放在 `ADAPTATION.md` 的“当前仓绑定记录”章；
   `confirmed` 与原“SDK 校验摘要”均以此为唯一真源，各模式正文和运行期 README 不重复维护。
4. **状态明确**：首次适配或 SDK/Skill/代表实例变化时退回 `未确认`；完成三方取证并由掌握目标仓的
   模型或人员复核后才能标 `已确认`。
5. **验证自包含**：目标仓适配必需的最小校验入口必须随 `doc/extensions/` 交付，或使用目标仓确定存在的
   标准命令；不得依赖明确排除在能力之外的 `test/story/`。`test/story/` 继续承担本仓能力评测。
6. **消费闭环**：适配自检不能停在 spec。至少以一个正向模式需求和一个零命中需求跑到 plan，确认应用表、
   契约投影和无污染；coding 编译与 review 遵从性在内网按用户安排完成。

绑定记录不复制 Skill 全文，也不复制业务源码；它只保存可回查引用、版本/指纹、代表实例和确认状态，
避免在项目知识与内网 Skill 之间形成两份会独立演化的模式定义。运行期 plan/coding/review 不读取
ADAPTATION，因此不会被维护元数据干扰。

## 6. `test/story` harness 正向状态模型

本轮出现的 worker 丢失、陈旧 running 状态和人工 stop 覆盖阶段结果，说明 harness 需要明确“进程状态”
与“阶段质量”是两条轴。

### 6.1 用例声明

每个用例显式声明：

- `start_phase`、`end_phase`；
- 本轮要验证的证据目标；
- 需要真人参与时声明 `interactive`。

适用 gate 不在 YAML 再抄一份，而是由 runner 从 `start_phase/end_phase` 唯一派生；`start_phase != story`
即表示复用已闭环上游，runner 在运行前后自动计算同一上游范围的内容指纹。这样声明与执行不会各自漂移，
同时仍会把派生后的 gate 清单和上游指纹写入报告供审计。

plan-only 用例到 plan 即正常截停，不启动 coding，也不以 coding skipped 判失败；同时不重新解释 Story
语义质量，只验证上游指纹未漂移。

### 6.2 运行与阶段结果分离

- 每个 phase 形成不可变结果：执行状态、gate 结果、语义/机械状态、凭证状态分别保存。
- case 总结只聚合适用 phase；后续 `stop`、worker 退出或无关 gate 不能覆盖已经形成的 plan PASS。
- “plan harness PASS、verifier/receipt 未完成”应表达为 `phase_quality=pass`、`closure=open`，而不是笼统成功。
- “worker 消失”使用明确终态 `worker_lost`，不能长期保留 `running`。

### 6.3 worker 生命周期

- worker 定期写 heartbeat 与 lease；控制端同时核验 PID/进程树和租约。
- PID 不存在且租约过期时，原子转为 `worker_lost`，记录最后阶段、最后事件和恢复建议。
- stop 负责整个子进程树的温和退出与必要善后；仍有残留则进入 `stop_failed` 并记录 `residual_pid`。
- resume 从最后一个完整 phase 继续，不重复已闭环阶段；恢复动作可重入。
- gate 日志统一记录命令、return code、stdout/stderr、耗时与异常，避免“fail 但日志为空”。

### 6.4 观测节奏

保持已经落地的 60 秒默认间隔：有新事件、状态变化、产物变化或等待用户回复时立即返回；普通静默期按
`next_poll_after_sec=60` 再观察。不得重新引入高频忙轮询。

所有这些修改只落在 `test/story/`，不触碰 framework 的全局 phase slot；测试侧继续使用既有的运行前快照、
终态还原策略。

3. 风险、假设、占位能力和工程设定是否在作决策前可见；
4. 是否可以不先编辑文档就直接主持评审会议。

任一问题为否，语义评审仍应 FAIL，即使所有机械测试全绿。

## 10. 明确不做

- 不修改或新增 `framework/` 文件。
- 不把 Story 改成 AI 读取的结构化台账，也不暴露内部 fact id、路由或 prompt。
- 不按固定篇幅、表格比例、关键词数量或重复次数机械裁定人读质量。
- 不机械截断决策，不用正则替人判断“理由是否充分”“叙述是否自然”。
- 不为“协同”、`Phone`、AR90004 或某个 pattern_id 写业务特例。
- 不要求所有规约或模式每轮全部命中；不适用就是正确结果。
- 不把 demo SDK、demo 代码骨架或单个内网历史实例当成目标仓模式真源。
- 不把内网 Skill 全文复制进项目知识；只登记引用并提炼经 SDK/业务场景验证的项目落法。
- 不把内网专有 Skill 路径、SDK 路径硬编码进可移植模板，由目标仓适配时发现并登记。
- 不重跑 spec 来伪造 plan 验证；实施后因被测件指纹变化需要正式复跑时，按新版本重新建立评价结果。
- 不在本仓继续 coding / review；由用户在内网完成。
- 未经用户批准，不执行本方案，不提交 git。

## 11. 最终完成定义

只有同时满足以下条件，才可宣布本轮优化完成：

1. 新 Story 可由人直接阅读并主持评审，无需先做结构整理或去除机器噪声；
2. Story 独立语义评价完成，`semantic_verdict` 不再 pending，且没有未处理的实质 `extra_findings`；
3. AR90004 的规约与两个设计模式仍在 spec → plan → contracts/use-cases 中真实生效；
4. 简单需求的零命中对照不受知识污染；
5. plan verifier 与 receipt 完成，正式闭环到 plan；
6. harness 能准确处理正常完成、worker 丢失、stop 与 resume，不遗留孤儿进程；
7. ADAPTATION 明确内网 Skill、真实 SDK、既有业务场景与 demo 模板的权威边界，且目标仓绑定记录、
   `confirmed`、SDK 身份/指纹和代表实例均有唯一落点；
8. 不携带 `test/story/` 时，目标仓仍可执行最小适配自检，并能将正例/零命中例验证到 plan；
9. `framework/` 完整性不变，本仓 coding / review 保持本轮明确跳过，内网验证凭证由用户侧完成。

这套完成定义同时守住两个目标：**Story 真正给人看**，以及**规约/设计模式在需要它们的需求中真正生效**。
