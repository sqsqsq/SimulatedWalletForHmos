# 新一轮优化 · 问题分析总结

> 背景：docx-supplement（AR90006）用例三次实跑（2026-08-12 19:02 / 19:30 / 19:46）暴露的
> 问题清单，与框架既有机制的对照调查。本文只回答「问题是什么、根因在哪」；

## 一、三轮实测暴露的问题

### P1 流程靠散文路由，动作没有钉死（根因级）

「导入上游材料」是一个**没有调用方的孤儿章节**：主流程链条（「初始化」章）写的是
`init → 生成design.md → 关卡`，导入章靠开头「何时用：需求系统没归档时…」等模型自己联想。

实测三轮两种行为：

| 轮 | 模型顺手执行的命令 | 结果 |
|---|---|---|
| 1（19:02） | `ls -R doc/features/AR90006/` | 撞见 docx → 导入发生（偶然） |
| 2（19:30） | `ls -R`（同上） | 同上（偶然） |
| 3（19:46） | `ls -la` 两个目录，未展开 inbox | **准确诊断出「PRD 缺料」后径直进 /spec**，人工补录的整份 PRD 凭空消失 |

第 3 轮最说明问题：模型专门检查了 `AR/upstream.md` 与 `ux-reference/`（因为它们**在
输入清单里写着**），唯独没查 inbox（不在任何清单里）。扫不扫收件箱取决于模型顺手用
哪条 ls——这是设计缺陷，不是模型缺陷。

### P2 关卡语义绝对化，授权没有落点（已修，保留）

SKILL.md 曾写「所有关卡都停等用户选择，AI 不得代答」（无条件绝对句）。用户 prompt 明写
「各确认关卡按你的判断取默认项，一路走到底」，模型仍停等——它执行得完全正确，是规约里
没有「授权」这个概念。而框架早有整套授权机制（`transition_policy`：`batch_authorized` /
`goal_mode`，解析 SSOT `phase-transition-policy.ts`），本 skill 自造了一个不接入它的孤儿关卡。

已修：关卡按 `transition_policy` 分档——`manual` 停等不得代答；授权态按推荐项决策继续，
报告一字不减并写明采用项与依据。**本条修复方向正确，新方案保留。**

### P3 视觉判据押注模型看图能力（已修，保留）

界面图识别曾以「AI 直接查看图片」为主判据。实测被测模型自述「不支持读图」，仅凭正文
上下文（「签约页效果如下」）就判对了三张图。已修：上下文为主判据（任何宿主可用），
看图降为可用时复核；登记改为当场执行（可逆复制）。**保留。**

### P4 交互产物即席化：报告与决策只活在对话流里

关卡报告（材料现状/缺口/拆分建议/草稿摘要）是即席生成的对话输出——会话一断就没了；
「谁在什么依据下选了什么」没有任何落盘记录。后果：

- 跨会话恢复时无从知道流程走到哪一步、哪些决策已做；
- AI 代答（授权态）的决策无审计落点，人事后无从复核推翻；
- 无法机械校验「前置决策是否完成」，跳步（P1 第 3 轮）不可拦截。

### P5 修复方式补丁化（本轮教训，方向性）

针对 P1 我先后打了两个补丁，方向都错：

- **「四源改五源」**：把 `inbox/` 塞进生成输入清单——概念错误。inbox 不是事实来源，
  是**汇入**权威文件的进料口（不变量：某类目标文件全文 = 该类 inbox 集合的转换结果）。
  当第五源读 = 同一份事实两个落点；
- **「报缺料必须同时报 inbox」**：提醒式负向措辞，治标不治本。

教训：P1 的病根是**流程没有结构**，在散文上继续加句子治不了结构病。

### P6 story 流程没有交付件检查确认机制（用户问题 3 的调查结论）

见下节对照表——框架的 spec/plan 每一步都有「落盘产物 + 机械校验 + 人工确认 + 决策记录」，
story init 链路一项都没有。

## 二、框架机制调查：spec/plan 的交付件检查确认机制

| 机制维度 | spec 阶段 | plan 阶段 | story init 链路现状 |
|---|---|---|---|
| **落盘交付件** | `spec.md` + `acceptance.yaml` + `ui-spec.yaml` | `plan.md` + `contracts.yaml`（机器契约真源） | **无**——init 与 design.md 之间零中间产物，分析只在对话里 |
| **机械校验** | `spec-rules.yaml`（required_chapters / required_columns，BLOCKER 级）由 harness 执行 | `plan-rules.yaml` + Step 13.1 | **无** |
| **人工确认点** | 术语映射表逐行 `[x]`、`spec.freeze`（`1=冻结可进 plan`）、`phase.next_step` | `plan.ok_to_code`（每次 plan 改动后 MUST）、`plan.scope_expansion`、`plan.split_table` | 关卡有（本轮新增），但**选项不由状态驱动**，靠模型即席组织 |
| **决策记录** | trace.json + receipt（四件套），授权须留用户原话 | 同左 | **无** |
| **跨会话恢复** | Resume Gate：`check-receipt.ts` exit 0 → 已闭环停等 | 同左 | **无**——重进会话只能靠模型重新推断走到哪了 |

框架的模式一句话：**落盘 → harness 机械校验 → 停等人审（registry 编号确认）→ 决策留痕
→ 凭产物恢复**。story init 作为 spec 的前置流程，恰恰是全链路里唯一没有这套结构的一段。

## 三、结论

P1/P4/P6 是同一个病的三个症状：**流程状态只存在于模型的注意力里**。
方向：把 story init 流程「契约化」——每步有落盘产物、有决策记录、可机械校验、可恢复，
与框架四重闭环同构。方案见 01。
