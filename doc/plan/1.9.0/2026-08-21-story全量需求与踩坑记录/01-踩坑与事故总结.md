# Story 相关踩坑与事故总结

> 日期：2026-08-21  
> 性质：只记录已经发生的错误、成因、影响和证据边界，不包含修复建议或设计方案。  

## 1. 总体事故链

从 2026-08-18 开始，Story 优化同时承载了适配、人读表达、设计模式、规约消费、运行闭环、测试基础设施和诊断度量等多个目标。改动逐渐从局部质量优化扩大为 Extension 多条链路重构。

主要事故链如下：

```text
正常版本可运行
→ 为提高 Story 结构和知识生效能力增加大量合同
→ 把单一 Demo 的标题和路径写成输入协议
→ 内网合法材料无法命中，Story 不能运行
→ 删除严格 selector，但保留分章成文等其它结构性假设
→ 离线测试通过，被表述为能力已完成
→ 真实四 Case 实跑再次出现内容缺失、重复和开放决定泄漏
→ 同时暴露 Knowledge 未闭环、truth 错误、并行缓存和归档协议问题
→ 多轮局部修改没有形成稳定目标
```

这次事故不是单一代码 Bug，而是需求、目标结构、运行合同、机械门禁和评价证据被混在一起演进。

## 2. 正常版本被误读为内容金标

### PIT-001 正常运行与内容正确被混为一谈

事实：

- `0c8ab1d` 在内网能够正常进入 Story 流程；
- 该版本包含按章节标题提取内容的逻辑；
- 标题没有命中时会回退整篇材料；
- 某一来源缺失时可以继续；
- 旧 Story 仍有重复、机械表达和无依据指标等内容问题。

误读：

- 一度把“旧版本有标题词”理解成“标题匹配没有风险”；
- 一度把“旧版本可以运行”理解成“旧章节和旧产物内容都应恢复”；
- 一度用旧 Story 的行数、表格和详细程度说明新 Story 丢失，却没有先剔除旧 Story 自身的错误内容。

影响：

- 输入容错的真正原因被忽略；
- 旧版本的有效运行行为和旧版本的内容缺陷没有分开；
- 后续讨论在“回旧版”与“保留新结构”之间反复摆动。

## 3. 单 Case 标题过拟合事故

### PIT-010 输出控制扩张为输入控制

事实：

- 章节合同原本用于规定最终 Story 写什么；
- 后续实现给每章增加 `heading`、`heading_regex`、`heading_path`、primary 和 supporting 等输入选择；
- 30 项来源被声明为必需；
- 31 项来源全部依赖标题或标题路径；
- 没有整篇材料作为无条件输入；
- 任一章缺少 primary 命中时 scaffold 整体失败。

成因：

- 为了让输出稳定，把输入格式也固定；
- 把模型负责的语义归章交给脚本；
- 从本地 RR、SR、AR、Spec Mock 的标题反推生产协议。

影响：

- H1-only、纯文本、自由标题、编号变化和层级变化全部可能失败；
- 内网材料内容有效，但标题不同，Story 不能开始；
- 测试验证的是 Mock 与合同完全一致，而不是通用能力。

### PIT-011 宽容 fallback 被主动改成 fail-closed

事实：

- 正常父版本标题落空时回退整篇；
- 故障版本把标题落空改成 missing；
- 测试明确断言“内容有效但标题无关”时必须失败；
- H1 永远不能匹配也被写成正确行为。

影响：

- 内网故障不是偶发解析问题，而是新合同按设计执行的结果；
- 简单恢复 fallback 与保留严格合同之间产生多轮争论；
- 后续“软指导”讨论持续围绕标题词，而没有立即回到完整成文目标。

### PIT-012 Scaffold 失败留下半工作区

事实：

- scaffold 先创建目录；
- 再逐个写章节文件；
- 最后才汇总 missing 并失败；
- decisions/ids 等文件的创建顺序在失败点之后；
- 失败后存在部分目录和部分章节。

影响：

- 后续流程可能把半成品当已初始化；
- 空 Story/Review 和残留工作区的来源难以判断；
- 同一 feature 重试时同时受到旧残留和新输入影响。

### PIT-013 空文件通过“存在性”门禁

事实：

- Spec lifecycle 一度只检查 `story.md`、`review.md` 是否存在；
- 两个空文件也可以满足存在性；
- Story scaffold 本身不负责创建最终两个空文件，空文件可能来自模型兜底、旧残留或其它路径。

影响：

- “文件存在”被误当“Story 完成”；
- 事故归因曾错误指向 scaffold；
- 门禁无法区分空文件、旧文件、当前构建和合法归档件。

## 4. 测试把 Mock 变成产品协议

### PIT-020 正例与生产合同同构

事实：

- 测试夹具使用与章节合同完全相同的标题；
- 文件名、章节名和组织顺序都来自少数本地样例；
- 正例只证明“完全按合同写的 Mock 能通过”；
- 标题变化被作为失败反例，而不是兼容性正例。

影响：

- 测试数量很多，但覆盖的输入世界非常窄；
- 内网输入变化第一次出现时直接失败；
- 离线全绿制造了通用能力已经成立的错觉。

### PIT-021 单一检查点对应大量 Case

事实：

- 正式 Case 一度扩张到约 15 个；
- 多个 Case 只改变文件名、标题、角色叙述或流程叙述；
- 每个 Case 都重复完整 Story/Spec 链路；
- 同一真实业务组合被拆成多个孤立场景。

影响：

- 运行成本高；
- 场景之间的组合效应没有被覆盖；
- 单一成功 Case 容易被误当整体能力成功；
- 测试维护量掩盖了 truth 与输入是否一致的问题。

### PIT-022 Case 输入与 truth 互斥

最新发现：

- `split-interactive` truth 曾写“门限、面额、单日上限均可修改”，真实 DOCX 只允许修改门限和面额，单日上限固定；
- truth 曾写“账号不进入事件”，SR 明确允许去标识账号等分类字段；
- 一些 truth 包含输入中不存在的接口、参与方、错误语义和隐私事实；
- 人工反馈事实没有进入 truth 声明的可执行来源；
- 修订后上述两项具体互斥得到纠正。

影响：

- 被测模型无法同时满足输入和 truth；
- 评价失败无法区分产物错误和答案错误；
- 为追求 truth 通过可能诱导模型写入不存在的事实。

### PIT-023 过程事实被当成 Story 事实

事实：

- `split-two-ar` truth 中存在材料库存、定位选项和选择结果等流程事实；
- `split-interactive` truth 中存在 DOCX 导入文件名和 Review 往返事实；
- rubric 的内容守恒项把 truth 当成 Story 必须覆盖的统一集合。

影响：

- 测试会要求人类 Story 写入工具维护信息；
- Story 的“只讲需求”与 truth 的“所有事实都进 Story”发生冲突；
- 机械内容守恒统计看似通过，但读者纯度受到污染。

## 5. Story 结构多轮变更事故

### PIT-030 章节数成为讨论中心

历史变化：

- 原结构约 14 章；
- 一轮收敛到 12 章；
- 后续变为 8 章正文加 3 个附录；
- 又变为十个二级章节；
- 多轮讨论围绕章节增删、合并和标题移动；
- 用户最终指出，问题核心是去重复和面向人类，不是章节数量。

影响：

- 结构变化被误当质量优化；
- 每次章节调整都带来内容迁移风险；
- 内容完整性没有先形成稳定基线；
- “精简”多次演变为事实删除。

### PIT-031 模拟稿越改越差

事实：

- 曾尝试通过 AR90004 完整模拟稿验证目标形态；
- 模拟稿先于稳定骨架反复修改；
- 标题被指出机械、解释性过强、AI 味明显；
- 模板缺少三级、四级标题；
- AR 拆分时兄弟特性关系不完整；
- 模拟稿出现待确认项；
- 相比已验证正常版本丢失大量内容；
- 用户最终放弃模拟稿，不再把它作为设计依据或验收前置。

影响：

- 模拟稿本身成为新的局部优化对象；
- 每轮为了看起来更短、更整齐而继续删内容；
- 模拟稿没有证明真实模型在不同输入上能稳定生成同等质量。

### PIT-032 模板语言进入标题

出现过的表达：

- “用户旅程”；
- “另一个业务场景或业务结果”；
- “业务阶段或主场景”；
- “目标与位置”；
- “方案成立的前提”；
- “端到端推进”；
- “当前特性负责的业务”。

问题：

- 有些是模板分类词；
- 有些把解释写进标题；
- 有些不是团队会自然使用的业务名称；
- 有些最终被模型原样输出。

影响：

- 标题树看起来完整，但人读仍有明显机器感；
- 模型把占位语言当内容模板；
- 评审者需要二次翻译标题含义。

### PIT-033 以篇幅下降判断优化

事实：

- 一度用标题数、表格行数、总行数和文档变短判断“更人读”；
- 旧 Story 很长，新 Story 较短，被当成去重证据；
- 后续逐项对照发现，短文档同时丢失接口、异常、状态、验收和上游事实。

影响：

- 内容删除与重复删除无法区分；
- 事实守恒落后于形式优化；
- 每次“更简洁”都可能造成新的信息缺口。

## 6. 分章成文导致的全局问题

### PIT-040 每章独立取材诱发重复

旧写作合同曾要求：

- 每章打开指定来源；
- 来源中的每个事实点都写进本章；
- 一次只写一章；
- 写完本章再写下一章。

当同一来源被多个章节引用时，同一事实天然进入多个章节。章节 must-answer 又存在交叠，进一步放大重复。

### PIT-041 删除 selector 后重复仍存在

后续实现：

- 每章获得全部材料；
- 加入 `reading_focus`；
- 写完十章后要求模型统一通读和去重。

最新实跑结果：

- `split-interactive` 的“关闭开关只隐藏新入口”在多个章节重复；
- `split-two-ar` 的 freeze ticket、生命周期和不收费规则遍布多个章节；
- `source-conflict-review` 的 `shareInProgress` 在方案、流程、功能、异常、验收和附录重复；
- `pattern-image-review` 的兄弟生命周期、云侧真源、恢复和开关行为重复。

结论事实：

- 删除 selector 解决了输入失败，不自动解决成文重复；
- “统一通读”作为提示没有稳定改变模型最终产物；
- S7 在四个 Case 中实质未达标。

### PIT-042 Reading focus 被误当完成证据

事实：

- `reading_focus` 恢复了旧版中有价值的来源职责提醒；
- 离线测试证明字段存在、十章不同、材料清单没有因提示变化；
- 没有 Story CLI 实跑时，这一轮被表述为“离线实施完成”；
- 最新实跑仍出现上游事实遗漏。

影响：

- “提示已经正确注入”被误当“模型已经正确取材”；
- 输入可见、输入已读和事实已进入 Story 三件事被混淆。

## 7. 内容守恒仍失败

### PIT-050 `split-interactive` 遗漏上游事实

最新产物缺少或没有完整保留：

- 连续三次扣款失败后的自动停用；
- 用户看到停用原因并需要重新签约；
- 扣款成功但写卡未完成时保持充值中；
- 下次读卡完成写入，不重扣、不重复订单；
- 定时充值、多卡共享签约和家庭成员充值等范围外内容；
- 管理页面相关信息；
- 通知失败事实。

同时 Review 中仍存在相关开放决定，Story 没有形成完整且正确的需求表达。

### PIT-051 `pattern-image-review` 遗漏和走样

最新产物问题：

- 上游 `AC-R1` 至 `AC-R10` 被替换为新的 `AC-1` 至 `AC-12`，原始编号没有独立保留；
- 精确事件 ID `loss_flow_start`、`loss_flow_result`、`loss_flow_recovery` 没有保留；
- RTL 被写成含糊的方向性要求；
- “支付中断从既有订单继续”被写成“不重复创建订单”，恢复语义不完整；
- 无上游依据的 `300ms` 再次进入验收。

机械 S2 同时报告“精确 ID 缺失为 0”，说明机械评价没有覆盖真实 truth 目标。

### PIT-052 Story 跟随不完整 Spec

多个 Case 中，Story 基本复述最终 Spec 已包含内容。RR/SR 中未进入 Spec 的事实也随之从 Story 消失。

影响：

- “Story 由全部同轮材料共同成文”没有在最终产物中成立；
- Spec 成为实际单一输入，即使文档规则声称不是；
- 上游内容守恒只能靠人工逐项阅读发现。

## 8. 开放决定泄漏事故

### PIT-060 只阻止 marker，没有阻止语义复述

实现曾检查：

- open 决定不能有 Story 占位；
- settled 决定需要投影；
- Review 由登记表渲染。

未覆盖：

- 模型不使用 marker，直接在章节正文中换句话写 open 建议；
- 同一建议被写成当前方案、验收条件或工程事实。

### PIT-061 四 Case 均出现泄漏

具体表现：

- `split-two-ar`：open 的 mock 数据方案进入 Story；
- `split-interactive`：open 的开关行为在 Story 多处成为正式规则；
- `source-conflict-review`：open 条目直接列入 Story 范围和附录；
- `pattern-image-review`：open 的模拟云适配和 `300ms` 指标进入 Story。

影响：

- Story 与 Review 职责没有真正分开；
- 人类评审者可能把建议当已确定需求；
- Review 中“不得进入 Story”的说明与最终 Story 原文互相矛盾。

### PIT-062 决定登记变成第二正文

历史表现：

- `conclusion` 或 `proposal` 写入完整长段论证；
- 同一决定在 Story 多次投影，每次展开长值；
- 作者先手写同义值，再附决定 token；
- 形成嵌套“X（X（决策））”；
- 决策引用遮住表格单元格真实答案。

影响：

- 决定单一真源没有减少重复，反而放大重复；
- Review 和 Story 都出现机器拼接感；
- 短 ID 追溯与人读正文纠缠。

## 9. 人类友好仍未达标

### PIT-070 结构顺序改善不等于自然表达

最新 Story 顶层顺序比旧版清晰，但仍出现：

- H1 固定为“ARxxxx — 需求说明”；
- “目标与位置”；
- “方案成立的前提”；
- “端到端推进（S1→S4）”；
- F1/F2 等机器编号主导标题；
- `carry_all`、流程契约、故事关卡等维护术语；
- 大量规则速查和追溯表进入主阅读路径。

影响：

- 读者能找到信息，但仍像模型生成的结构化报告；
- 文档无法直接作为自然需求评审材料；
- Human-First 的结构方向和语言结果被混为一谈。

### PIT-071 Verifier 对自然语言偏宽

历史正式实跑中：

- Story 出现“唯一业务锚”“原子检查点”等模型化措辞；
- 出现“卡云适配层按键交付”等错词；
- 规约原句和机器字段进入正文；
- Verifier 仍可给出整体 PASS 或未将其识别为阻断。

影响：

- 规则进入 verifier 上下文不代表实际被严格裁决；
- 结构完整和编号存在掩盖了语言质量。

## 10. 机械门禁与语义质量混淆

### PIT-080 离线全绿被表述为完成

事实：

- 多轮改动取得数百项离线测试通过；
- Extension Harness 通过；
- 独立代码复核给出 0 blocker/major；
- 当时明确没有执行 Story CLI；
- 文档仍多次出现“已实施”“离线完成”等积极结论；
- 最新真实 suite 证明模型产物未达标。

影响：

- 代码合同自洽被误当用户目标达成；
- 用户在真实测试后才发现结构性问题；
- 多轮“完成”状态需要重新撤销。

### PIT-081 机械 S2 不能证明内容守恒

事实：

- 机械检查主要覆盖 Spec ID、表行、数值、代码标识和图片数量；
- 自然语言事实、限定条件、恢复语义和近义走样无法可靠机械判定；
- `pattern-image-review` 原始 ID 和事件 ID 缺失时，机械结果仍可通过；
- 四 Case 的实质遗漏由人工完整阅读发现。

影响：

- “S2 pass”存在口径歧义；
- 脚本结果被拿来推翻产物原文；
- 内容守恒的语义层长期处于 pending 或没有真正执行。

### PIT-082 Verifier 固定清单漏掉 Extension check

历史 Plan 实跑中：

- 生成的 verifier prompt 包含 `plan_constraint_coverage` 和 `plan_pattern_selection_projected`；
- 实际 verifier report 只执行固定 14 项；
- 两个 Extension check 没有出现在输出；
- Plan 仍返回 PASS。

影响：

- 规则被注入但未执行；
- “知识已进入大上下文”被误当“知识已闭环”；
- Extension 与 Framework verifier 的责任边界长期不清。

## 11. Spec 生命周期问题

### PIT-090 Story 错误整体升级 Spec 提示

事实：

- post-check 同时返回普通 Spec 问题和 Story BLOCKER；
- 使用单一 `severityOverride=BLOCKER`；
- 普通提示被整体升级。

影响：

- 问题严重级别失真；
- 执行者无法区分 Story 不可用和普通 Spec 改进项；
- 修正范围被扩大。

### PIT-091 禁用词报错显示“undefined 路径”

事实：
