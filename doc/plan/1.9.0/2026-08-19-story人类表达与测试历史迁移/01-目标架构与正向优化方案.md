`2026-08-19-story人读表达与工程知识生效/` 目录用于保存上一版设计和实跑基线。

## 1. 目标

本轮形成五项完整能力：

1. `AR/story.md` 以专业需求文档的方式组织内容，供人直接阅读和主持评审；
2. Story 在提升表达质量的同时守住需求事实，并保持仓内本地图片链接有效；
3. 规约和设计模式从 Spec 信号进入 Plan 主体设计，冻结后由 Coding、Review、UT、Testing 按阶段职责持续消费；
4. 内网模型能够依据适配指南，用真实模式 Skill、SDK 和业务案例建立目标仓知识；
5. CLI 测试具备历史产物迁移、两分钟观测和一致的源码事务终态。

整体因果链为：

```text
原始需求与代码仓事实
  → Story 形成人读需求
  → Spec 形成实现规格、规约要求和模式候选事实
  → Plan 完成知识选择并改变主体设计
  → contracts 冻结设计义务
  → Coding 实现
  → Review 审查
  → UT / Testing 验证可观察行为
```

`framework/**` 在实施前后保持字节一致。Story 和需求 `review.md` 面向人；Spec、Plan、Coding、技术 Review、UT、Testing 的阶段产物面向 AI。

## 2. 能力结构

### 2.1 实例扩展分工

| 能力 | 权威职责 | 落点 |
|---|---|---|
| Story Skill | Story 初始化、逐章编辑、装配、归档、恢复和需求评审 | `doc/extensions/skills/story/` |
| 工程知识 | 描述应用域规约与设计模式本身 | `doc/extensions/knowledge/` |
| 生命周期 hook | 在阶段上下文中注入知识读取、应用和交接动作 | `doc/extensions/hooks/<phase>/` |
| phase overlay | 为对应 verifier 增加规约和模式的语义检查 | `doc/extensions/rules/` |
| manifest | 注册实际使用的 phase、event 与文件路径 | `doc/extensions/manifest.yaml` |
| 适配指南 | 指导内网模型建立真实模式知识与绑定证据 | `doc/extensions/ADAPTATION.md` |
| 测试控制器 | 编排 case、迁移历史产物、观察进程、保存证据和恢复源码 | `test/story/` |

`manifest.yaml` 的事件统一采用 framework 已支持的 canonical event 名：`on_context_load`、`post_check`、`pre_verifier`。阶段目录表达作用域，实际职责决定该阶段注册哪些事件。

Spec、Plan、Coding、Review、UT、Testing 沿用 framework 原生 Skills。实例扩展通过 hook、knowledge 和 overlay 进入这些阶段。

### 2.2 契约分工

framework 标准字段继续承载文件、组件、接口、资源、验收和用例等核心契约。`contracts.yaml > project_knowledge` 作为实例扩展命名空间，冻结本需求已经采用的模式实例和已经命中的规约义务，由实例 hook、overlay 与确定性检查消费。

两类契约保持一致：

- 标准 contracts、acceptance、use-cases 表达真实设计对象和可观察行为；
- `project_knowledge` 表达这些对象所遵循的模式实例、规约来源、实施锚点和验证锚点。

## 3. Story：面向人的专业需求文档

### 3.1 稳定主线与自然子章节

Story 保留八章正文和三个附录：

```text
# <需求名称>

## 1. 需求概览
## 2. 范围与协作边界
## 3. 整体方案
## 4. 场景与功能设计
## 5. 体验、流程与状态设计
## 6. 系统方案与实现边界
## 7. 问题、风险与当前处置
## 8. 验收、上线与协作

## 附录 A：术语表
## 附录 B：详细契约
## 附录 C：追溯关系
```

H2 提供稳定阅读主线，H3/H4 由当前需求的真实内容决定：

- 一个 H2 中包含多个可独立理解和评审的主题时拆为 H3；
- 一个主题中包含多个独立页面、场景、状态域、流程分支、接口组或参与方时拆为 H4；
- 短小事实并入正文，并列字段进入表格或附录；
- 标题树应能单独复述本章的内容顺序，层级数量本身不作为质量目标。

### 3.2 标题与正文

内部 `reader_question` 用于帮助模型理解读者关注点，最终标题使用专业、简洁、名词性的需求文档语言：

| 内部关注点 | 可见标题示例 |
|---|---|
| 为什么现在要做 | 需求背景 |
| 给谁带来价值 | 业务价值 / 用户价值 |
| 本轮怎样才算成功 | 需求目标 / 成功标准 |
| 本期承载什么 | 本期建设内容 |
| 改动落在哪里 | 系统影响范围 |
| 哪些条件影响上线 | 关键依赖 / 上线前置条件 |

该表表达写作原则，由模型结合业务语义选择准确标题。正文按照人的理解顺序说明背景、价值、范围、方案、场景、体验、系统边界、风险和验收。工程事实先解释业务或系统含义，内部 ID、字段映射和追溯编号集中到契约或附录。

### 3.3 Markdown 表达

| 信息关系 | 主要表达形式 |
|---|---|
| 背景、方案、取舍、影响 | 连贯段落 |
| 同粒度并列事实 | 列表 |
| 多对象共享稳定字段 | 表格 |
| 跨参与方调用顺序 | 时序图 |
| 流程分支与汇合 | 流程图 |
| 状态、事件和恢复 | 状态图 |
| 高影响结论或风险 | 简短引用块 |
| 字段、接口、配置名 | 行内代码 |

异常信息在场景和验收章节中自然呈现。需要集中比较时，使用“异常场景｜用户表现｜系统处理｜验收重点”的人读表格；机器追溯关系进入 `acceptance.yaml` 或附录 C。

### 3.4 内容守恒

Story 编辑采用以下流程：

1. 将本轮原始材料分配到唯一主归属章，并在现有 source block 中保留原文；
2. 为每章建立标题树，随后逐章成文；
3. Spec 定稿后，以最终 Spec 和已登记决策进行一次人读信息对账；
4. 装配后独立审视业务事实、参与关系、用户状态、恢复路径、决策和数值依据；
5. 缺失内容回到责任章节局部修订并重新装配。

当前原始材料、最终 Spec 和已登记决策共同构成内容真源。历史 Story 用于测试侧回归比较和退化诊断。语义重复可以归并，每项独有事实保留一个自然的人读落点。

Spec 中以下信息需要进入 Story 或需求 `review.md`：

- 用户行为、业务规则、范围和参与方边界；
- 页面、流程、状态、异常、失败恢复和兼容行为；
- 数据、接口、配置、隐私、DFX、上线和外部依赖对人产生的影响；
- 人能够据此判断需求是否正确的验收口径与风险。

脚本负责原始输入保留、章节装配和结构完整性；模型与独立语义评价负责事实等价、内容完整和叙述质量。

### 3.5 图片链接

本轮保障仓内最终 `AR/story.md` 的本地图片引用：

- 装配过程保留 Markdown 图片、替代文本和必要图注；
- 相对路径以最终 Story 所在目录为基准；
- 确定性检查验证链接语法、目标文件存在和路径位于该 feature 的允许资产范围；
- 人读评价检查图片与正文的关系。

### 3.6 Story 与需求 Review

- Story 提供完整、连续、可主持评审的需求上下文；
- `AR/review.md` 承载需要人工表态的审核对象、当前结论、依据、责任人和最终结果；
- 已确定且影响需求理解的结论在 Story 对应上下文中自然说明；
- 术语表位于附录 A，正文首次出现时同步给出自然解释。

## 4. Spec：实现规格与模式候选事实

### 4.1 规约生效

需求事实实际命中的规则进入对应的实现要求、技术契约、异常、非功能或验收语义，并携带可追溯 `rule_id`。有效证据是规格内容因规则形成了明确约束；`rule_id` 负责定位知识来源。

域相关但具体规则未命中时，Spec 记录本需求事实和判断依据。每轮仅处理本需求实际涉及的规则。

### 4.2 模式候选信号

Spec 枚举有明确起止的流程段、页面和关键组件。每个单元使用一个在当前 Spec 内唯一、可原样传给 Plan 的“适用单元”名称，并记录：

- 用户或业务目标；
- 分支、动作、状态、等待点、自动后继、失败和恢复事实；
- 由路由表得到的候选 `pattern_id`，或“无候选”；
- 对应需求与技术契约证据。

Spec 负责候选事实，Plan 负责最终选型。Spec post-check 校验章节、字段、单元唯一性、在册 ID 和证据字段；候选完整性与适用性由 Plan 和 verifier 继续判断。

## 5. Plan：知识选择、主体设计与冻结

### 5.1 设计顺序

Plan 按以下顺序工作：

1. 从 Spec、代码仓事实和系统边界独立重建适用单元与规约域；
2. 根据单元事实读取路由表，并读取候选模式文档的 Plan 部分；
3. 形成模式采用结论和规约设计义务；
4. 以这些结论设计文件、角色、接口、数据、状态、上下文所有权、等待点、失败收敛、SDK 依赖和验证行为；
5. 深入设计后复核新发现的单元、证据和反证；
6. 生成工程知识决策区与 `project_knowledge`，冻结已经进入主体设计的结果。

因此，工程知识决策表是主体设计的索引和下游交接，不是独立于设计的回显区。

### 5.2 工程知识决策区

```markdown
## 工程知识决策

### 设计模式选择
| 适用单元 | 关键事实 | 候选 pattern_id | 结论 | 理由/反证 | 主体设计与契约锚点 |

### 应用域约束
| 约束域 | 本需求事实 | 命中 rule_id | 设计义务 | 实现锚点 | 验证锚点 |
```

设计模式表覆盖 Spec 中每个适用单元，并纳入 Plan 深入设计发现的新单元：

- 单元具有多个候选时，每个“适用单元 + pattern_id”形成一行采用或拒绝结论；
- 单元没有可信候选时，以“无候选”记录该单元事实；
- 完全零命中由各真实单元的判断共同形成；
- verifier 从需求与设计事实独立判断单元完整性和结论合理性。

### 5.3 模式对主体设计的影响

采用模式至少形成以下设计结果：

- 唯一实例和职责边界；
- 上下文所有者及跨步骤传递的数据；
- 入口、动作或节点、自动后继、用户等待点和终点；
- 失败收敛、恢复或补偿；
- 与其它模式或系统的交接接口；
- SDK 依赖和计划文件；
- 内部结构锚点和外部可观察行为锚点。

`page-interaction` 根据业务结果驱动的后继动作、多个用户等待点和页面编排职责判断；`decision-tree` 根据真实多步业务分支、云调用、失败收敛、回滚、补偿或恢复判断。

### 5.4 规约对主体设计的影响

命中规约转化为需求化设计义务，并进入对应的接口、数据、资源、配置、异常、兼容、隐私、幂等、性能或验证设计。Plan 复核三组一致性：

1. 主体设计、工程知识决策区和 `project_knowledge`；
2. contracts 中的实现对象与 acceptance/use-cases 中的可观察对象；
3. 每项规约义务的实现锚点与验证锚点。

### 5.5 机器契约

`project_knowledge` 只保存已采用模式和实际命中规约。模式拒绝理由、无候选和域级判断保留在 `plan.md`。

标准机器契约同时满足 framework 既有口径：

- `prd_to_code_traceability.key_files` 使用项目根相对路径；
- 实现锚点指向 contracts 中真实规划的对象；
- 验证锚点指向 acceptance/use-cases 中真实对象；
- Plan 计划引用的既有资源定义文件进入 framework 现有扫描输入；
- 多模块 UI 工程通过实例配置明确唯一 `paths.ui_kit_target_dir`。

Plan 阶段检查当时已经可知的路径、锚点、已声明文件和实例配置；Coding Harness 检查最终代码、资源和构建结果。

### 5.6 机械检查与语义评价

Plan `post_check` 负责确定性事实：

- 受控 ID、表格和数组结构；
- Spec 显式单元与候选的结构化处置；
- 采用项与 `project_knowledge` 的一致性；
- 锚点解析、路径口径、已声明文件和实例配置。

Plan verifier 独立评价：

- 真实适用单元是否完整；
- 候选与选型是否合理；
- 采用项是否改变主体设计；
- 拒绝项是否具备与模式判据一致的反证；
- 规约是否形成实际设计义务；
- 主体、决策区、contracts、acceptance 和 use-cases 是否一致。

## 6. Coding、Review、UT 与 Testing：消费同一冻结结果

### 6.1 阶段职责

| 阶段 | 阶段动作 | 有效证据 |
|---|---|---|
| Coding | 读取采用模式的 Coding 部分和规约义务，按锚点落实到代码、资源与配置 | 真实 diff、逐文件诊断、编译结果 |
| Review | 读取同一模式的 Review 部分，逐实例、逐义务审查真实 diff | 技术审查报告中的结构、行为与反模式证据 |
| UT | 将可观察验证锚点转成测试场景和断言 | 测试代码、场景、断言与运行结果 |
| Testing | 验证分配到设备和环境层的行为 | 测试计划、日志、截图与测量证据 |

每个阶段的规约检查和模式检查都按 verifier 协议输出 `PASS`、`FAIL` 或 `SKIP`。合法零命中使用 `SKIP` 并引用 Plan 的逐单元事实；已冻结实例和义务进入该阶段的实际检查。

### 6.2 阶段纠错

当 Coding、Review、UT 或 Testing 的真实事实表明 Plan 的设计或冻结结果需要修正时：

1. 当前阶段对应语义检查输出 `FAIL`，证据定位 Plan 主体、冻结契约与阶段事实的矛盾；
2. 报告标记 `correction.layer=plan`；
3. 主流程使用 framework 既有 correction 流程完成修正三问和用户确认；
4. 修改 Plan 层真源并执行 `--correction-check`；
5. Plan 与已闭环下游通过重验后，按正常阶段授权继续流程。

### 6.3 Coding 逐文件闭环

正式 Coding case 使用已知具备 `ReadLints` 或等价单文件诊断能力的 CLI/profile。事件与 trace 需要证明“写一个文件 → 立即诊断 → 零 error → 下一个文件”的顺序。最终 Harness 继续承担全量构建、架构、scope、资源和契约验证。

## 7. 设计模式文档与内网适配

### 7.1 模式知识结构

每份运行期模式文档采用统一内容模型：

1. 解决的问题和适用单元；
2. `applies_when` 与 `not_applies_when`；
3. Plan 必须形成的设计投影；
4. Coding 所需的 SDK 行为事实与结构约定；
5. Review 检查项与反模式；
6. UT/Testing 可观察行为边界；
7. 正例、反例和组合边界。

模式文档保持纯粹的运行期知识。环境绑定、适配进度和核实证据统一记录在 `ADAPTATION.md`。

### 7.2 内网适配任务链

内网模型按以下权威顺序建立目标仓知识：

```text
内网现有的两个设计模式 Skill
  → 真实 SDK 类型声明与运行实现
  → 业务仓已有主案例、边界案例与组合案例
  → 目标仓模式文档与阶段指引
  → 正例、负例、组合例与编译验证
```

适配任务包括：

1. 建立模式 Skill 与目标仓模式 ID 的语义映射；
2. 核实构建器、上下文、返回值、停机、后继和错误行为；
3. 提取真实文件布局、职责边界和反模式；
4. 重建适用条件、Plan 投影、Coding 落地、Review 审查与验证清单；
5. 用可编译最小示例或真实代码片段验证；
6. 在 `ADAPTATION.md` 登记来源、证据、确认状态和知识引用；
7. 运行 `verify-adaptation.mjs --require-confirmed` 完成目标仓启用校验。

本仓 demo 用于验证机制和文档结构；内网目标仓使用完成核实后的 Skill、SDK 和业务案例事实。

## 8. CLI 测试基础设施

### 8.1 历史需求产物迁移

测试配置提供备份根目录 `E:\Project\bak`。case 既有 `start_phase` 表达链路边界：

- `start_phase == story`：启动全新链；
- `start_phase != story`：继续当前 feature 的阶段链。

新链启动顺序：

1. 解析并校验仓库根目录、feature 和 start phase；
2. 检查当前 case 对应的 `doc/features/<feature>`；
3. 目录存在时，在注入本轮输入前移动到 `E:\Project\bak\<feature>-<yyyyMMdd-HHmmss>`；
4. 目标重名时追加 run-id；
5. 新产物留在 `doc/features/<feature>` 供同链下游消费。

迁移记录写入 run 元数据。续跑阶段直接使用当前工作区的上游产物。

### 8.2 观测与运行方式

- 正式 CLI 使用非沙箱模式，并在 run 元数据记录启动参数；
- 外部观测间隔为 120 秒；
- worker 心跳、软超时和进程监测使用各自配置；
- 观察日志在新事件、状态变化和终态时记录摘要。

### 8.3 源码事务

源码事务采用单一 finalize 路径：

```text
capture → active → stopping → restoring → restored / restore_failed
                                           ↓
                              派生 run 最终状态
```

- worker 自然结束和外部 stop 都进入同一 finalize；
- restore 串行执行并具备幂等结果；
- finalize 完成 restore 后派生 execution、pipeline 和 run 顶层状态；
- `pre_digest`、`restored_digest` 和新增文件清单共同构成恢复证据；
- 恢复异常保存完整错误和人工重试入口。

## 9. 验证设计

### 9.1 离线验证

离线测试覆盖：

1. Story build、merge、import、review、路径、标题层级和图片链接；
2. Story 人读样例、内容守恒以及 Story 与最终 Spec 的人读信息对账；
3. Spec shape、规约命中、模式候选信号；
4. Plan 正例、负例、组合例、逐单元处置、契约锚点和 verifier 独立判断；
5. Coding、Review、UT、Testing 的 hook、overlay 与 `PASS/FAIL/SKIP` 输出；
6. design-pattern knowledge purity、适配指南和目标仓确认校验；
7. 历史迁移、两分钟观测、源码事务和 stop 收口；
8. 实例扩展完整性与 framework 指纹。

### 9.2 正式 CLI 验证

正式 CLI 使用一个信息丰富的主正例，从 Story 运行到 Review：

- 原始需求自然包含 `page-interaction` 和 `decision-tree` 的业务适用事实，输入中只描述用户目标、业务规则、外部行为、失败恢复和验收结果；
- 原始材料包含一张与需求有关的本地图片；
- Story 验证人读表达、内容守恒和最终图片链接；
- Spec 验证规约要求与模式候选事实；
- Plan 验证两个模式真实改变主体设计、contracts 和 use-cases，规约形成设计义务；
- Coding 验证冻结结果落码、逐文件诊断和构建；
- Review 验证同一模式实例和规约义务的实现质量与反模式。

另设一个自然负例运行到 Plan，验证简单线性流程和独立按钮能够形成合理的逐单元拒绝结论。UT/Testing 的知识消费在本轮完成离线合同验证，真实执行由内网后续测试承担。

每个 run 保存输入、版本指纹、事件流、阶段产物、Harness、verifier、receipt、源码事务和历史迁移证据。测试结束后形成正式报告，报告按“现象 → 证据 → 责任层 → 原始诉求达成情况 → 后续建议”组织，并停在报告交付处。

## 10. 完成标准

本轮优化完成时同时满足：

1. Story 标题、子章节、正文和 Markdown 表达符合专业需求文档习惯；
2. 当前原始材料、最终 Spec 和已登记决策中的人读事实均在 Story 或需求 Review 有自然落点；
3. 仓内最终 Story 的本地图片链接有效；
4. Story 与需求 Review 的职责清晰，术语表位于附录 A；
5. Spec 的规约要求和模式候选事实忠于需求；
6. Plan 独立选型，规约和模式真实改变主体设计并形成一致的机器契约；
7. Coding 与技术 Review 消费同一冻结结果，UT/Testing 具备同源消费合同；
8. 内网适配指南能够指导模型依据真实 Skill、SDK 和业务案例完成适配；
9. 新测试链将旧 feature 产物迁移到 `E:\Project\bak\<feature>-<timestamp>`，同链续跑连续；
10. 正式 CLI 采用非沙箱模式和两分钟观测，源码事务终态与磁盘恢复事实一致；
11. framework 指纹保持一致，应用工程无关功能和用户修改保持原状；
12. 正式测试报告落盘，测试结果与后续修改分开确认。
