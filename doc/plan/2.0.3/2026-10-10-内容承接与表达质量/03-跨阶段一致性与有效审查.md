# 步骤3：跨阶段一致性与有效审查

## 原生接缝与材料身份

继续用现有author phase bindings、knowledge-task、shared/pre_verifier和spec/plan overlay，不增Skill/phase/报告协议或Extension receipt。

已核源码：harness-runner在assembleAIPrompt与buildVerifierMaterialView中传同一lifecycleFragments；verifier-material包含lifecycle_sha256、extension_sha256和files摘要。本轮直接使用，不再列为接口未定。

额外采用片段及其确定性来源身份放进现有promptFragments。交路径时同时交实际读取内容摘要，不能内容变而片段字符串不变。采用部分Story时只绑定实际片段及其身份，不加入整篇Story的内容摘要/时间戳，不因无关段落或登记变化重审；原生蓝图版本有效性仍按原规则。

同一原文只装配一次；不同时在任务、规则和报告另抄全文。定向测试经过原生材料视图入口核相关片段变→material_sha变化、相同内容复用、无关Story段变不制造新审查。不是仅对自写hash函数作断言。

Story的reviewObject保持需求级对象集合，不把所有CU文档加进去。新增实际采用来源按原材料身份绑定。CU作者及verifier取得原生设计与当前范围、约束、实际引用表达；作者自报“同步完”不能代替审查。

## 跨阶段处理

| 发现 | 责任与结果 |
|---|---|
| 合法局部细化 | 留CU，不强迫Story改写 |
| CU与有效设计矛盾 | 修Spec/Plan，不改共同设计迁就误写 |
| Story与有效设计矛盾 | 回Story作者，CU不继承错稿 |
| 共同设计错误/用户可见承诺需变 | 影响当前CU行为或验收时FAIL，回component-design，经原生修订同步受影响交付 |
| 范围或依赖被偷偷缩减 | 阻断当前完整交付声明，回实际决定责任 |

在现有spec/plan overlay增加design_content_consistency语义判项，pre_verifier交相同来源，报告走原生阶段合同。post_check只核引用、图源和原生有效性，不用关键词判语义。

变化沿已有反馈、story_basis和原生CU失效机制；不新增双向自动同步器。纯表达不升设计revision；局部实现不强制全需求重写；共同承诺变更明确受影响对象与责任，未同步不称当前完整交付。

## 诊断问题正向处理

- 写作设计关系应兑现：已有形式检查核载体存在，独立审查核实际条件、分支、往返、状态和责任能否理解。不能凭文字出现或来源标记判完整；也不按参与方/分支数强制图。合法更好组织沿template-adjustments说明，不把旧安排升为不可改权威。
- Discovery/独立质询在决策前核材料承诺与工程事实；恢复路径核发起者、查询身份、对象、状态真源和消费者。正常新增代码不自动变成承载争议；已有能力不实、外部依赖/模拟影响验收才登记。
- 会议归属不明或改变范围必须问人；已有明确归属直接承接，不用作者“不属本单”标签替代决定。
- Review的settled仅用于实际需要裁决且已有原话的议题；材料事实不需重复人签，模型工程判断保持原生inferred来源。同步作者与审查解释，不重复加一套准入台账。
- 非阻断建议允许有理由不采纳，在交付摘要说明重要建议处理；采纳改变材料则沿原身份重审，无变化复用，不强求建议清零。
- 中性局部示例写进已有作者页，说明适用/不适用与选择理由，不引用Case答案或新建模板库。

主要责任位置：blueprint author/questioning要求页、story-write/meeting-read/design/update、reader-review-task/story-reader-rules、spec/plan author与overlays。已正确要求先核实际送达，只有当前缺口才修改，避免叠加重复话术。
