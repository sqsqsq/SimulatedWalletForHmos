## 3. 本轮最重要的三项发现

### 3.1 auto 自建 Goal，交互停等被绕过

**事实**：

- 范围拍板后，父会话 21:46 调用原生 `create_goal`，`max_goal_rounds=40`。依据只是模型自己的推理：“这是一个长任务，应该创建一个 goal 让会话跨轮次继续”（`events.jsonl` 第 551–553 行附近）。
- 此后 run `3ad0f50b` 从 21:41:59 连续跑到 23:02:39，是同一次 CLI 调用。
- 期间模型在 22:15 和 22:29 两次发出“请逐条确认术语映射”，Goal 都自动续了下一轮。宿主一次也没收到 `awaiting_reply`。
- 模型随后推理“现在处于 goal 自动继续模式（无人值守 headless）”，把 6 个术语记为 `headless_assumed`。直到交付选择那一问才把它们列为待人复核；宿主确认后蓝图从 r1 改到 r2，Story 又做了一次复核。证据在 `output/evidence/2.0.3-C02-prerun-review/20261109/auto-goal-*.txt`。
- car 没有创建 Goal。

**影响**：

- 本轮 auto 的设计、成文、首读和复核约 80 分钟，实际是在 Goal 语义下跑的。维护范围只覆盖 interactive（AGENTS §0），这段结果不能当作 interactive 正常链的效果证据。
- 这次只漏了术语确认，但同样的机制可以吞掉任何停等。

**责任**：

- dsh 测试配置在 interactive Case 里仍暴露 Goal 工具；适配声明却是不支持 goal（2.0.2 D02 记过 attended next 因此被拒）。两者自相矛盾，这是本地宿主定制和测试装置的问题。
- Story 的停等表没有说明 interactive 下不建 Goal。
- 驱动器和度量对 `create_goal` 没有任何提示。

这不是 Framework 缺陷，也不能只靠在提示里加一句来保证。

## 4. car 为什么停在 design_handoff

| 步 | 事实 | 证据 |
|---|---|---|
| 蓝图阶段问人 | 模型问 AC-K6 草稿是会话级还是跨进程，并说明“跨进程 → 新增持久化能力，成为新 blocker”；宿主按规划立场答跨进程 | car 第 3 问 |
| 知识的说法 | `engineering-capabilities.md:35`「工程里没有现成的受保护持久化封装：要跨重启存敏感字段时，保护方式按真实依据定，没有依据就写成缺口」；`security-privacy.md:37` SEC-01「保护能力……没有真实依据的，写成缺口与责任方」 | 知识原文 |
| 模型的判断 | 推理里提到“Preferences + 加密”，但按“没有依据写成缺口”登记 `gap-draft-persistence`，状态 blocker | `events.jsonl` |
| 原生拒绝 | `check-change-unit --accept-candidates` 两次 FAIL。第二次修好 owner/consumer/recovery predicate 后仍剩：`change_unit_design_closure_incomplete`（闭包缺 `gap:gap-draft-persistence` 稳定地址）与 `change_unit_current_design_unresolved`（该 gap 在当前 delta 是 blocker） | `car-cu-reject.txt` 第 1866、1877 条 |
| 宿主处置 | 模型给出 A（确认平台受保护存储）/ B（工程新增封装）/ C（暂停）三选一，宿主答“受保护持久化……是工程侧的方案，需求方这边定不了……在此之前不要为了过门硬编一个来源”，随后 conclude，理由写“受 F1 阻断” | car 第 5 问与 host_conclude |

**判断**：

- 第一条是 F1 形态（gap 进了闭包却没法引用）。第二条是 F1 修正要求里明确要保留的正常阻断：真实未决、又影响当前 CU 的 gap 仍然要拦。所以 F1 到件后，car 照样会停在这里，“受 F1 阻断”不成立。
- 根因在 Demo 知识样板。它把两件事混成了一件：一是工程里没有现成封装，这是本需求要设计并承担的实现工作，保护方式可以按平台能力的真实依据去选；二是平台或环境能力本身未知，这才应该写成缺口。金样当时用的设计前提是“API 12 具备 SystemCapability.Security.Asset”，与现在的知识版本对不上。
- Case 里也没有工程侧的立场，宿主作为需求方确实答不了 A 或 B，所以按 §0.3 停下是对的。但宿主的两句回话（“不要为了过门硬编一个来源”“不要为了凑齐硬编一个来源”）涉及门禁和做法，越出了需求方立场（§0.3），属于轻度污染。
- 归属：Demo 知识样板由本仓维护者负责（AGENTS §3.3）；Case 与金样前提一致性归测试域；结论标签归我在方案里的预设（§6）。

## 8a. 补充：Story 内容在 2.x 逐轮收缩（2026-11-09，用户提问后补查）

## 8b. 进一步优化 Extension 是否必须先等 Framework

不必。本轮的主要差距大多由 Extension、Demo 知识样板或测试域自己负责，可以直接动手：

| 差距 | 责任 | 是否要等 Framework |
|---|---|---|
| Story 内容收缩、规约验收漏接（§8a） | Extension 成文机制 | 不用 |
| 未知、待定、撤销语义复现（§3.2） | Extension 作者与独审 | 不用 |
| 统计空投影、按建议删承诺（§3.3） | Extension 设计页与 Story 回看 | 不用 |
| DFX-02、持久化封装与缺口混淆（§4） | Demo 知识样板 | 不用 |
| 质询 `task.md` 写成 UTF-16、首读原件没落盘 | Extension 确定性写入与接收 | 不用 |
| interactive 里模型建 Goal | 测试装置与 dsh 本地定制 | 不用 |
| car 到不了 Plan | Demo 知识与 Case 前提为主；F1 只是其中一条 | 修掉知识与 Case 后，只有闭包里确实挂着已解决 gap 的流程才会被 F1 卡住 |
| 读校验器源码学蓝图载体（F3） | Framework | 要，但只影响成本，不挡 Extension 的改动 |
| 设计参考的阅读组织（F2） | Framework | 要，只影响设计参考，不影响 Story 本身 |

需要注意一点：2.x 里 Story 处在 Framework 蓝图的下游，蓝图载体越重，留给 Story 的预算越少。Extension 不能删减 Framework 要求的蓝图字段；但 Story 怎么写、拿到哪些知识、验收写哪些、成文分多少工作，都是 Extension 自己能定的。
