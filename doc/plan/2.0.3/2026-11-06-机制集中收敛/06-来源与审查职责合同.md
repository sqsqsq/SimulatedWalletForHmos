# 来源、原生审查应用与最小证据接入

2026-11-07修订。来源§1—2与业务分责§3保持；§4—6取代bf7704bf的Standalone资格链设计。原方案、A03实现与A批评审保留可追溯。本页是A04的详细设计，B批阶段接续见05，知识输入见07；暂不实施。

## 1. 来源分类：先保信息，再判效力

### 1.1 首次归类与生产消费

1. 按现`import_sources.py --preview`（共用docx_to_markdown）读完整正文和图片清单；不另造预览器。
2. 需要承接正文的混合材料按主体归RR/SR/AR/UX，现convert已经同时保留全文和内嵌图，沿registry→稳定阅读稿→materialSet→Story/质询消费。版本早、粒度粗、父作者先问补图，都不能单独证明正文不应承接。
3. IMAGES仅用于有依据排除整份正文的材料：例如核对确认正文已被有效材料完整覆盖，或用户明确限定视觉输入且无其它须承接信息。理由落已有初析/采用说明，不增加分类批准表。文内“以此为准”只是一项来源主张，不自动覆盖人答或更高效力来源。
4. 有独有文字但效力不清，仍保正文，通过已有冲突/人答机制处理影响设计的差异；不为每份分类追加人工停等。保全文不等于照单采纳旧稿。

修改：inbox_import.md、templates/inbox-readme.md、初析/设计输入说明以及sources.mjs关于IMAGES的提示，同步改其适用边界。普通RR/SR/UX的转换与图链保持；不新增混合类、分段采用schema或自动语义分类器。

### 1.2 已导入后纠类与历史保护

当前source.class是来源级字段。真实函数反例已证：IMAGES v1加入RR v2时，旧DOCX会在records/files_view中被当成image；只保旧字节不够。

本版保持来源级类型语义，不改成逐版本类型：

- 尚未首次导入：直接改.classify.json。
- 已有版本而确需换类：先用已有`--retire <旧相对路径>`将旧件退到现备份，保旧source/class/versions及稳定引用；将同一原件以明确的新inbox相对路径放回，按新类导入为新source。在现有来源初析/采用说明注明纠类替换关系，后续设计显式采用新来源，旧材料库存与已引用旧件继续可查。
- `cmd_import`在validate后、meeting恢复/任何写盘之前，对同source_id且class不同的待导入件一次报出；不改盘、不隐式回写旧class。`registry.add_version`只在首次建立source时写class，后续版本退出现source.class覆盖赋值，不再加重复拒绝。其余真实调用是类型固定的direct/ANSWER生产者，无第二个合法换类入口。新来源/同类新版本/内容相同幂等不受影响。
- 该退役+新来源路径仅用于有依据的材料角色纠正，不能用于绕过合法契约Pointer、authority或本单范围检查；不能无理由挪输入求绿。不承诺或迁移已存在的错误历史分类，既有旧运行原件保持。

验证必须经真实preview/classify/import/derive消费：混合正文与图均进入正确读者；同来源换类在写前拒绝；走现退役/新路径后旧版本的class、role、sha和旧引用保持，新来源正文/图可读。不是只断旧字节未变。

## 2. 原件、协议转写、本地mapping与蓝图各自负责

上游契约事实由有效SR稳定版本或有权限的逐项确认支持；se-interfaces是其结构化转写，不因candidate写了而获得外部权威。mappings是本部件消费/转换设计，必须能指到上游字段及本地承担者，不能伪装成上游已确认协议。canonical是共同设计权威，不是上游原件的改写者。

遇authority mismatch只走以下顺序：

| 判断 | 正确修改者与动作 |
|---|---|
| 蓝图抄错转写，转写与原件吻合 | 改蓝图，原生逐段核验并重渲 |
| 转写不忠实原件/有效新决定 | 作者回读原始依据修转写，说明差异，再同步蓝图；已被旧revision引用的转写新建版本文件，旧件保留 |
| 原件没给类型/错误/幂等等外部保证 | 保来源未知/推断及真实缺口，交对应owner；不由同名字段批量补权威映射 |
| 本地mapping设计错误 | 在本地设计权限内修mapping与承担实体，核输入输出/失败；不改上游字段使它配合当前设计 |

独立蓝图质询负责原件→转写→设计真实性与知识实体落实；原生相等检查只证结构/引用和一致，不证转写忠实。原报告对候选的结论与作者修后处置分开；父可按原生结构登记真实回答，不把“建议补must/改名”登记成原独审已核修后对象。新候选影响设计时回原生复核，不靠自造非空fingerprint代内容绑定。

具体位置：evidence-rules.md §5、phases/design.md、hooks/blueprint/author.md/reviewer.md和questioning任务的职责说明；既有原件/稳定引用/转写版本和原生validator保留。不能再加一层Story全量技术质询来补蓝图失职，也不修改Framework算法来消报错。

## 3. 蓝图与Story审查分工

| 对象/职责 | 蓝图质询 | Story业务审查 |
|---|---|---|
| 原始目标、人答、范围、关键业务条件 | 形成共同设计前独立核效力与承担 | 独立核本稿未遗漏/改义/先行选边；上游PASS不豁免 |
| 外部契约转写、mapping、数据/状态/恢复设计 | 对原件和设计实体完整核实，指出外部缺口 | 影响业务行为、必要查阅或发现矛盾时回查；报发现回设计owner，不重新作整套技术设计 |
| 知识适用、实体must/roles、统计上篇 | 在共同设计阶段完成与复核 | 核读者应取得的义务/结果与实际落点；有疑点查原知识，不逐份无条件重审全部知识 |
| 技术schema/原生scope/准入/typed形状 | 原生确定性检查＋相应设计质询承担 | 消费当前状态/问题，不能以状态代业务正确；不再重复机器结构审查 |
| Story的完整叙事、页面旅程、图文、未决、验收与必要查阅 | 不预写Story，不代签成品效果 | 本职完整核；不是只核它是否复述蓝图 |
| 业务源共同漏项 | 回最早来源/设计责任修 | 即使两稿一致也必须报，不能以不归Story设计为理由放过 |

### 3.1 审查对象完整绑定，阅读按责任分层

reviewObject仍保完整库存、采用/冲突依据、有效人答、canonical、投影、权威转写、knowledge、manifest与报告任务，material_key仍按原字节算；不因阅读减量删对象或放松当前性。

`required_read`继续复用：Story、Review、有效业务原文/阅读稿、未采用但有冲突的业务来源、当前人答/决定、上游业务图和现判据为业务核查入口；写作设计是可被质疑的作者安排。canonical、完整原生技术参考、技术转写/映射、全部知识和工程说明为按问题回查材料，required_read=false；元数据/二进制原件仍按现身份/在场处理。人读投影按业务相关正文与关联对象核对，不要求把技术参考全读一遍。

reader-review-task在后读任务中复用现blueprintKnowledge结果，给知识适用/不适用结论、理由和承担对象引用作定位（沿story-inputs已有同类展示，不复制整份知识、不新登记）。这些仍是待核设计判断，审查者结合当前业务结果核影响，需要时回原条款；不能只露作者选中的义务而隐藏不适用判断。该定位替代无差别重读全部知识，不能把摘要当源。

对象表文字区分“核在场的metadata”和“按问题回查的text”，不把二者都说成不需审。具体判断需要的参考未取得时，是本次未核，不能利用false豁免。完整业务来源仍可反查作者未采用材料，不由作者scope/清单缩小。材料库存只有reviewObject/task这一份，不复制到prepared另建快照表。

### 3.2 首读输入的真实边界

- Story首次独立阅读先只给Story路径、通用问题、当前key及后读task/最近原报告路径；派审必须使用按本次真实工作生成的dispatch_text，父不预置旧结论、改法或摘要。真实调用工具与agentPreset/任务文本纳验证，不能仅查文件存在。
- 初审需要未见被审内容/前结论的新隔离会话；若复核决定重新做盲读，也用未见旧材料的执行体。已有上下文的同会话可做集中复核，不改称盲读；不要求每轮固定新会话或新增审查角色。
- 复核明确称复核，不强迫每轮假装全新首读。采用可信前轮报告是有据复核，不让它成为免除新问题的判据；需要新首读时先读Story再context，若旧上下文已经看过则如实标不是盲读。
- 蓝图八问保原生规则。questioning.mjs/knowledge-task根据同版本原生投影的`<a id="reference"></a>`及紧随的`## 技术与追溯参考`确定正文末行，在现首读载体给出1..end的读取范围，不复制正文/另造renderer。标记缺失/不唯一或与当前投影身份不符时明确无法生成可靠首读边界，由设计者核原生变更；不猜边界、不签盲读，正常技术质询可继续且披露首读未成立。读完八问才按原任务看参考与原件。
- YAML判据的description/ai_prompt_hint改保自然段换行，reader-review-task按段输出；退出把多页规则折成单物理行。验证实读传输而不是只看磁盘全文，不把2000字符宿主限制硬编码成所有宿主业务规则。

## 4. 原生方法与本地运输边界

原生component-design的独立质询仍负责共同设计。固定ff111909的app-component-blueprint-workflow末段规定：原质询者修后通读当前正文，复核旧发现与受影响要求，只定向核源，不重做完整八问或全源码，不增第二reader/轮次/回执。Extension按这个方式组织复核，不把Story结果写成蓝图derived_results，不借蓝图准入代业务阅读。

Story首次由未参与其生产的隔离只读执行体读成品，先Story后业务来源/人答/相关设计；复核优先交原读者，通读当前稿并核旧问题、变更涉及的行为与引用。新读者或没有可信上下文时补足业务核查，不能假称完成过盲读。作者不预置结论、不代定只需局部；读者可沿任务中的完整库存、知识判断定位回查。无变化且最近有效回复与当前key相同不再派审；身份变化不自动等于全量技术重审。

### 4.1 真实宿主接线及保留理由

原生阶段verifier只收harness签发的maison_verifier_request。当前DSH可用的隔离spawn是本地Preset maison-verifier/具名工具verifier，五宿主模板也有本地自足只读任务分支；它不是原生通用Story API。不能因为工具名字相同就把阶段规则应用到Story，也不能声称删文字后已存在另一通用入口。

**本版保留现有本地只读运输桥，收缩其职责。** Story及图面都是实际消费者；为替换工具名再新增具名Agent、调度层或权限平台没有必要。本地分支只接收自足任务、保持隔离/只读和完整最终返回，按本任务内容工作；不复制阶段结论规则、复核资格或闭环调度。阶段JSON分支保持原生协议，图面保持自身报告合同。adapt知识审查沿既有普通隔离/独立会话方法，不因此新增调用链。

hostReviewer的verifier_subagent只能说明可委派，不能单独证明接受自足任务。生产入口先按已装宿主的实际工具说明/任务合同选择现有可用隔离执行体；测试固定组合以受控patch和物化入口证明运输桥存在。无可用入口时沿诚实未审，不向仅接受阶段JSON的工具投文本，也不添加新能力注册表或靠模板字串猜能力。已经取得的当前有效回复不因换宿主就失效；旧已知必修仍须复核。

DSH现有spawn不继承父对话，但只读靠Preset及任务约束、不能宣称物理禁写；沿现有正常事件核未写业务件/回复来源，不为假设攻击新增沙箱。五宿主装配/模板核查和实际CLI能力分别结论。未来正式宿主同等只读入口具备且Story、图面两个消费者完成切换后才能撤运输桥；这是现有能力的有据保留，不作为本版外部等待或新增Framework诉求。

### 4.2 能力事实怎样送到prepare

为补齐现pendingDisclosure只认verifier_subagent的缺口，review --action prepare明确接收--reader task|unavailable；unavailable必须带--reader-reason说明实际缺工具/任务合同不接受/调用明确拒绝的事实。task表示主执行者已从实际工具说明或已物化的自足只读合同核可用，不是脚本替它认证，也不是可写任意角色名的新注册表。默认不再靠verifier_subagent推断，缺参数只报准备输入未给，不写业务件、不新增人工询问。命令帮助、所有派审/重收件调用点与夹具同步提供它。

prepared复用已有disclosure承载该不可用事实；task分支移除本轮旧未审披露再定稿，unavailable分支写真实未审披露再算key，check只读已定对象/原件/披露，不再独立探宿主另算结论。先只读核最近可消费pass/warn是否已绑定当前完整对象；成立则直接复用原回复，不因新宿主无能力去改正文或取消已有审查。否则按本次参数准备新对象，最近fail保护仍优先，不可由unavailable洗掉。提供task却工具拒绝时不循环重投阶段verifier，保返回证据，按unavailable+真实原因重新准备或交已有可用独立会话；不是waiver批准。

当前测试DSH/五宿主受控运输桥已具备时使用task；无同等实际入口的目标安装用unavailable。这个参数只补本次调用所缺的输入，不声明新宿主能力、不新增状态/配置平台、不把主模型声明当独立性证据；正常运行仍核实际调用、完成回复和保存字节。

### 4.3 原发现的处理

设计遗漏回蓝图owner，按原生修订/质询；表达遗漏回Story章稿。作者一次同步同根因的全部影响处，读者按当前对象复核，旧意见和修法分别保留。INFO/MINOR有据保留不强制清零；实际重大缺陷或必要未核仍不交成业务通过。缺两行元信息只请原读者补最终回复，不自动全业务重审。取消full/focused资格、format_repair状态、历史basis链、历史PASS回找；无历史稿不计算semantic diff、不建前稿冻结平台。

## 5. 最小证据接入：不再建立第二套审查流程

保留现story-build review的prepare/check/manual入口，改变其责任；manual的人工Review保护完全不动。prepare只定稿/结构核、组装输入、给本次原样回复位置及接收原件；check只读身份、原件与读者显式结论，不决定复核模式/资格、不从发现表推导语义结论、不调度子代理。登记/交付仍消费这一个检查结果。

### 5.1 输入与原样回复

review-object继续绑定完整材料库存、采用版本/冲突来源、有效人答、蓝图/投影、知识和静态任务原字节；task不嵌入自身算出的key，也不嵌入每轮前报告避免自激变化。派审载体在key算出后给key、Story路径、后读任务、最近原报告路径及本次最终回复位置。首次正文先读；已有读者复核直接说明是复核，不再通用写“像第一次”。

回复仍Markdown，仅固定开头两行：

~~~text
material_key: <本次64位key>
conclusion: pass|warn|fail
~~~

后文由独立读者简洁说明实际核验/前轮依据、发现与位置、修正责任、未核及结论理由。不强制标题、YAML、发现表、条目ID副本或库存清单；必要发现和未核必须如实写。业务规则中重大缺陷/必要未核应fail、非阻断建议可warn、无问题pass，由读者判断；脚本不扫正文严重度词替其推结论。不存在脚本签发的focused资格。

父等到实际完成回复后原样保存，保持当前原回复命名/目录习惯及原件不覆盖；中途消息和整理摘要不冒充最终回复。保存后重跑prepare收件；收件摘要只能证明此后未改，首次原样性仍由实际完成消息与保存字节交叉取证。错key/缺两行/原件被改分别报明确缺口，不能猜一个结论让格式通过。

### 5.2 最小记录与不丢已知必修

prepared只保当前请求（material_key/project_root/task/dispatch/report_file/report_dir及当前无能力披露）和最近一次可消费独立回复的引用last_received（material_key/report_file/report_sha256）。原件继续留在原目录；不存scope模式、review_contexts、各key报告目录索引、资格链或结论副本。结论从last_received所指原件读出，不另存result。新需求从新记录起步，旧格式明确不支持、保现场，不自动迁移旧需求。

prepare收当前回复时按两行/当前key核可消费性并记录原字节摘要；无效回复保留但不覆盖last_received。需要补正时给新空回复位置，不覆盖旧件。最近有效回复同key且pass/warn可复用；不搜更老PASS，A→B→A不自动找回历史A通过。当前待回复不被旧PASS冒充已审；报report_missing/subject_stale或当前接收错误。任务改变只影响当前性，不机器决定重新全读。

最近可消费回复为fail，在新可消费回复前保“已知必修未复核”，即使改稿、出现无效补正或换为无审查能力宿主也不能变unreviewed。这个旧fail不是对新对象作失败判断，而是尚未取得修后结论；新对象pass/warn只能来自实际独立读者。原件缺失/摘要变化报证据错误，不用历史有利结论替补。最近结论非fail、当前无可用入口且没有当前有效审查时，按现披露规则允许诚实未审送业务评审，不算独审通过。

本记录只追踪当前请求及一份必要前证，不维护审查资格或轮次状态机。连续接收过的旧原件不删除，未核缺口/发现和修正理解由模型沿原回复判断；不加递归、周期遍历、自动差量引擎或复杂异常恢复。

### 5.3 消费者与语义边界

reviewResult保现有pass/warn/fail/unreviewed及证据错误出口，detail指向原件；report_file/material_key仍给消费者。退出advisories表解析，warn交付提示链接原样报告并由主模型如实说明建议/保留理由，不重新生成建议清单。discloseInStory仍保护人工区并在对象定稿前完成，避免登记动作改被审件。

story-build registration-check、deliveryProblems、flow lifecycle/state/routing/update和context当前性恢复统一读最小结果，不再读取contexts、发现表或资格；登记后story_basis文件摘要、basisDriftProblems、归档读回/恢复继续保护交付对象。usage按真实工作完成事件保持，不以prepare/check当新完成事件。check两行绿不代表报告语义自洽；作者须核原答、必要修正回责任方，维护效果评审以真实缺陷与漏判取证，不能用新parser绿覆盖已知质量问题。
