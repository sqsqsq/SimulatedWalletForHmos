# 来源、审查职责与轻量报告合同

2026-11-06本轮集中修订的关键设计真源。承接十二会话补评与继承反思，取代初稿“所有实质变化完整核源、报告合同不改”的设计；B批原生接续仍见05。仅设计，不实施。实现者按本页完成接口与消费者，不另选报告形态、分级算法或来源状态模型。

## 1. 来源分类：先保信息，再判效力

### 1.1 首次归类与生产消费

1. 按现`import_sources.py --preview`（共用docx_to_markdown）读完整正文和图片清单；不另造预览器。
2. 需要承接正文的混合材料按主体归RR/SR/AR/UX，现convert已经同时保留全文和内嵌图，沿registry→稳定阅读稿→materialSet→Story/质询消费。版本早、粒度粗、父作者先问补图，都不能单独证明正文不应承接。
3. IMAGES仅用于有依据排除整份正文的材料：例如核对确认正文已被有效材料完整覆盖，或用户明确限定视觉输入且无其它须承接信息。理由落已有初析/采用说明，不增加分类批准表。文内“以此为准”只是一项来源主张，不自动覆盖人答或更高效力来源。
4. 有独有文字但效力不清，仍保正文，通过已有冲突/人答机制处理影响设计的差异；不为每份分类追加人工停等。保全文不等于照单采纳旧稿。

修改：inbox_import.md、templates/inbox-readme.md、初析/设计输入说明以及sources.mjs关于IMAGES的提示，同步改其适用边界。普通RR/SR/UX的转换与图链保持；不新增混合类、分段采用schema或自动语义分类器。

### 1.2 已导入后纠类与历史保护

当前source.class是来源级字段。真实函数反例已证：IMAGES v1加入RR v2时，旧DOCX会在records/files_view中被当成image；只保旧字节不够。

本版保持来源级类型语义，不改成逐版本类型：

- 尚未首次导入：直接改.classify.json。
- 已有版本而确需换类：先用已有`--retire <旧相对路径>`将旧件退到现备份，保旧source/class/versions及稳定引用；将同一原件以明确的新inbox相对路径放回，按新类导入为新source。在现有来源初析/采用说明注明纠类替换关系，后续设计显式采用新来源，旧材料库存与已引用旧件继续可查。
- `cmd_import`在validate后、meeting恢复/任何写盘之前，对同source_id且class不同的待导入件一次报出；不改盘、不隐式回写旧class。`registry.add_version`只在首次建立source时写class，后续版本退出现source.class覆盖赋值，不再加重复拒绝。其余真实调用是类型固定的direct/ANSWER生产者，无第二个合法换类入口。新来源/同类新版本/内容相同幂等不受影响。
- 该退役+新来源路径仅用于有依据的材料角色纠正，不能用于绕过合法契约Pointer、authority或本单范围检查；不能无理由挪输入求绿。不承诺或迁移已存在的错误历史分类，既有旧运行原件保持。

验证必须经真实preview/classify/import/derive消费：混合正文与图均进入正确读者；同来源换类在写前拒绝；走现退役/新路径后旧版本的class、role、sha和旧引用保持，新来源正文/图可读。不是只断旧字节未变。

## 2. 原件、协议转写、本地mapping与蓝图各自负责

上游契约事实由有效SR稳定版本或有权限的逐项确认支持；se-interfaces是其结构化转写，不因candidate写了而获得外部权威。mappings是本部件消费/转换设计，必须能指到上游字段及本地承担者，不能伪装成上游已确认协议。canonical是共同设计权威，不是上游原件的改写者。

遇authority mismatch只走以下顺序：

| 判断 | 正确修改者与动作 |
|---|---|
| 蓝图抄错转写，转写与原件吻合 | 改蓝图，原生逐段核验并重渲 |
| 转写不忠实原件/有效新决定 | 作者回读原始依据修转写，说明差异，再同步蓝图；已被旧revision引用的转写新建版本文件，旧件保留 |
| 原件没给类型/错误/幂等等外部保证 | 保来源未知/推断及真实缺口，交对应owner；不由同名字段批量补权威映射 |
| 本地mapping设计错误 | 在本地设计权限内修mapping与承担实体，核输入输出/失败；不改上游字段使它配合当前设计 |

独立蓝图质询负责原件→转写→设计真实性与知识实体落实；原生相等检查只证结构/引用和一致，不证转写忠实。原报告对候选的结论与作者修后处置分开；父可按原生结构登记真实回答，不把“建议补must/改名”登记成原独审已核修后对象。新候选影响设计时回原生复核，不靠自造非空fingerprint代内容绑定。

具体位置：evidence-rules.md §5、phases/design.md、hooks/blueprint/author.md/reviewer.md和questioning任务的职责说明；既有原件/稳定引用/转写版本和原生validator保留。不能再加一层Story全量技术质询来补蓝图失职，也不修改Framework算法来消报错。

## 3. 蓝图与Story审查分工

| 对象/职责 | 蓝图质询 | Story业务审查 |
|---|---|---|
| 原始目标、人答、范围、关键业务条件 | 形成共同设计前独立核效力与承担 | 独立核本稿未遗漏/改义/先行选边；上游PASS不豁免 |
| 外部契约转写、mapping、数据/状态/恢复设计 | 对原件和设计实体完整核实，指出外部缺口 | 影响业务行为、必要查阅或发现矛盾时回查；报发现回设计owner，不重新作整套技术设计 |
| 知识适用、实体must/roles、统计上篇 | 在共同设计阶段完成与复核 | 核读者应取得的义务/结果与实际落点；有疑点查原知识，不逐份无条件重审全部知识 |
| 技术schema/原生scope/准入/typed形状 | 原生确定性检查＋相应设计质询承担 | 消费当前状态/问题，不能以状态代业务正确；不再重复机器结构审查 |
| Story的完整叙事、页面旅程、图文、未决、验收与必要查阅 | 不预写Story，不代签成品效果 | 本职完整核；不是只核它是否复述蓝图 |
| 业务源共同漏项 | 回最早来源/设计责任修 | 即使两稿一致也必须报，不能以不归Story设计为理由放过 |

### 3.1 审查对象完整绑定，阅读按责任分层

reviewObject仍保完整库存、采用/冲突依据、有效人答、canonical、投影、权威转写、knowledge、manifest与报告任务，material_key仍按原字节算；不因阅读减量删对象或放松当前性。

`required_read`继续复用：Story、Review、有效业务原文/阅读稿、未采用但有冲突的业务来源、当前人答/决定、上游业务图和现判据为业务核查入口；写作设计是可被质疑的作者安排。canonical、完整原生技术参考、技术转写/映射、全部知识和工程说明为按问题回查材料，required_read=false；元数据/二进制原件仍按现身份/在场处理。人读投影按业务相关正文与关联对象核对，不要求把技术参考全读一遍。

reader-review-task在后读任务中复用现blueprintKnowledge结果，给知识适用/不适用结论、理由和承担对象引用作定位（沿story-inputs已有同类展示，不复制整份知识、不新登记）。这些仍是待核设计判断，审查者结合当前业务结果核影响，需要时回原条款；不能只露作者选中的义务而隐藏不适用判断。该定位替代无差别重读全部知识，不能把摘要当源。

对象表文字区分“核在场的metadata”和“按问题回查的text”，不把二者都说成不需审。具体判断需要的参考未取得时，是本次未核，不能利用false豁免。完整业务来源仍可反查作者未采用材料，不由作者scope/清单缩小。材料库存只有reviewObject/task这一份，不复制到prepared另建快照表。

### 3.2 首读输入的真实边界

- Story初审/fresh先只给Story路径、通用问题、当前key及后读task/context路径；派审必须使用原dispatch_text，父不预置旧结论、改法或摘要。真实调用工具与agentPreset/任务文本纳验证，不能仅查文件存在。
- fresh初审需要未见被审内容/前结论的新隔离会话；若复核决定重新做盲读，也用未见旧材料的执行体。已有上下文的同会话可做集中复核，不改称盲读；不要求每轮固定新会话或新增审查角色。
- 复核明确称复核，不强迫每轮假装全新首读。采用可信前轮报告是有据复核，不让它成为免除新问题的判据；需要新首读时先读Story再context，若旧上下文已经看过则如实标不是盲读。
- 蓝图八问保原生规则。questioning.mjs/knowledge-task根据同版本原生投影的`<a id="reference"></a>`及紧随的`## 技术与追溯参考`确定正文末行，在现首读载体给出1..end的读取范围，不复制正文/另造renderer。标记缺失/不唯一或与当前投影身份不符时明确无法生成可靠首读边界，由设计者核原生变更；不猜边界、不签盲读，正常技术质询可继续且披露首读未成立。读完八问才按原任务看参考与原件。
- YAML判据的description/ai_prompt_hint改保自然段换行，reader-review-task按段输出；退出把多页规则折成单物理行。验证实读传输而不是只看磁盘全文，不把2000字符宿主限制硬编码成所有宿主业务规则。

## 4. 按影响复核，但所有新键都有当前结论

现replyPlace、originals、received及context种类保持；现prepared的复核上下文改为按报告保留（§5.1），不新增模式状态机/semantic hash/自动差量判定器。复核范围由独立审查者依据真实变更判断，不能由作者一句“只改措辞”获得豁免。

| 现有情形 | 本次核查责任 | 接收边界 |
|---|---|---|
| 同key已有合规pass/warn | 复用同对象原报告，不派新审 | 原件未改、对象相同、现有check通过 |
| fresh/前轮缺席或损坏 | 完整业务初审：首读→有效业务源、人答、设计相关内容→全部Story业务职责 | 新报告；不得从更早有利报告替补 |
| recheck或prior_revision，业务来源/授权/范围/关键行为变化 | 核当前有效依据与所有受影响关系，通读当前Story/Review；重大或影响不清时完整业务审查 | 新key新报告，旧报告只作可回查依据，不继承判定 |
| 局部业务纠正 | 核原发现根因、所有受影响位置及关联行为，通读当前Story/Review查新增矛盾；发现外溢扩大范围 | 当前报告说明实际范围和前轮依据，不只核作者列点 |
| 纯表达/排版调整 | 有可信前稿/具体前轮依据可核时，核语义未变、当前稿整体可读与相关上下文；不重演全部技术核源 | 当前报告明确是集中复核、未重做盲读；无法证明影响界限则扩大业务核查 |
| format_repair，同对象 | 原判断与核验充分才只修报告形状；若缺读/缺依据补对应工作，不能把格式诊断当充分审查认证 | 原审查责任方重给完整原样回复；原件保留；报告如实说明本轮只补什么 |
| 作者已改变被审对象 | 先收齐本轮修改，新prepare后只审新对象；旧对象修复不继续伪装同轮 | 原件/中止事实保留；不并行做无意义旧报告补正 |

现prior_revision没有旧材料字节快照，**不能机器证明diff/“其它都没变”**。复用已有前报告具体依据、现有修订说明、正常留存或可取得的Git/原件前稿；没有可靠比较材料就做完整业务核查。这里的提效主要来自职责收缩、短报告和集中修正，不以新增冻结包、差量引擎或跨键PASS继承换收益。

## 5. 新Standalone Story报告合同（唯一形态）

只替换Standalone Story合同，不改原生Feature/蓝图质询/图面报告四键合同。不兼容旧Standalone报告或给旧现场补默认字段；新2.0.3需求从当前入口起步，旧报告和旧运行原样保留。

报告继续Markdown，第一行`material_key: <64位>`；三个二级节固定为“审查范围与依据”“发现”“总体结论”。退出逐判据表和逐章对账长文，发现只写一次。当前仅有story_reader_review这一业务判据，任务仍交完整判据，但报告不再重复抄ID到每一行。

“审查范围与依据”以自然段说明首次读者理解或复核实际工作、有效人答/仍开选择的依赖行为判断、核源依据和复用范围；每个当前open选择给简短有据结论，不能只写“均已核”。不要求重抄整份会议/材料/知识库存。其后恰好一个短YAML块：

```yaml
review_scope:
  kind: full                 # full | focused，报告承担的业务核查范围，不是流程状态
  basis_report: null         # focused的前轮依据；格式补正沿被修报告原scope
  unreviewed: []              # 当前职责确实未核的 {path或check, reason}
  additional_inputs: []      # 仅材料表之外实际回查的 {path, purpose}
```

- full表示本报告承担完整业务核查范围，完成与否由真实未核/总体结论说明；不表示所有技术参考逐字读完、也不表示格式补正这一次重读所有文件。首次/fresh必须full；format_repair可保留原核验责任，但自然段明确这次实际补正。
- focused初次选择只在recheck/prior_revision且存在可信、可读、未被改写的前轮合规语义报告时使用；basis_report必须等于该报告上下文给出的原报告并匹配其sha，不允许作者任指旧PASS。原报告缺覆盖/缺依据或不能支持边界时扩大full。format_repair若修的是focused报告，保持其原scope/basis，沿被修报告已有上下文核资格；不强迫写full假装已全面重审。原scope读不清/核验不足则回业务扩核，格式诊断本身不授权复用。
- unreviewed必须显式存在；它列当前判断需要却没核到的输入/业务职责，不把未使用的技术参考全列成缺陷。出现非图面延期的必要未核，当前结果不得pass/warn。图片按现原生storyReviewVisual裁定允许延期时最高warn；其它业务阻断仍fail。
- additional_inputs不顶替必要输入，不新增只准工程内文件的白名单/存在性门。若额外材料改变授权或设计依据，回正常导入/决定入口再准备新对象，不能以报告额外引用绕过当前性。

“发现”唯一表头：`编号 | 严重程度 | 材料位置 | 问题与依据 | 修正责任`；没有发现保表头/分隔行、不写空发现。严重度仍BLOCKER/MAJOR/MINOR/INFO；位置沿现locations解析，属于当前对象或明确额外取证，编号唯一、问题和责任非空。不要另写blocking_findings/advisories编号副本。

“总体结论”首行pass/warn/fail及理由。判定从一次发现解析和真实未核派生：BLOCKER/MAJOR或必要未核→fail；仅MINOR/INFO或合法图面延期→warn；其它→pass。声明与派生矛盾报report_invalid。必要未核已给明确理由时不强迫在发现表重复一遍；发现与未核都不能被coverage字段齐全代替。

### 5.1 解析/状态/交付如何闭合

`review-report-contract.mjs`维护新常量与一份报告说明；`independent-review.mjs::judge/coverageOf`替换旧逐判据表、旧四键coverage和重复ID比对，以本页三节/短scope/五列表/派生结论核当前报告。scope解析和context资格由该模块承担，judge取得被核报告自身的上下文，不使用最新另一轮context判历史资格。历史basis缺席时只核形状/原身份，不借当前文件伪补旧核验。

Standalone不再把“未列路径”派生成已经逐字读过：不生成examined_inputs的全库存假阅读声明；不再调用共享detailProblems执行旧四键全列表协议，必要的严重度、引用、未核/图面规则在本judge复用现inputs/alias/visual事实核。共享review-inputs::detailProblems本身及其它消费者保持原合同。

**复核依据存储的唯一调整**：退出prepared.review_context单槽，替换为同一prepared中的`review_contexts: {<report_file>: <原context对象或null>}`；null明确该报告fresh无前轮，缺条目是记录缺失，不默认fresh。原context的kind、前报告路径/hash、旧material_key与diagnostic仍沿已有含义。新回复位置第一次准备写入该项，同位置续等/接收/复用不覆盖；contextFor/dispatchFor/replyPlace/unresolvedFail及judge统一按record.report_file或所核报告文件读取，当前context.md只是这项的派生人读件。原单槽消费者和专测同步退出。

这是当前新报告声明basis_report的必要消费者：若只留最新单槽，同key reused清context及A→B→A都会丢掉已派审依据。选择现记录内索引，代价为每份报告一小段既有context；不保存业务前稿、不复制库存、不增加流程状态或第二资格真源。originals继续保护所引前报告；focused必须匹配该报告对应context的有效前报告/hash，format_repair沿被修报告的已存context承接原basis（不把待修格式的报告变成新的业务充分性依据）。缺项、自指或循环是记录无效，报input_invalid/report_invalid并保原件，不猜基线。

把judge中“解析旧报告形状/旧key/发现与结论/原件及对应context”与“核当前报告的引用、必要未核和当前visual”分开；materialConclusion/earlierConclusion/unresolvedFail的历史调用不得用当前object.rows/visual重新裁旧报告。A→B→A实际当前对象就是A时，仍按A的完整当前事实检查。不能证明历史资格时扩大业务核查，不拿当前文件补旧覆盖。

check对外仍返回现result/detail/advisories/report_file/material_key等；advisories由发现表派生，delivery/登记/status/update/usage不新增状态类型。prepared现有目录选择/originals/received/alteredReplies/unresolved_fail及同键复用保留，上述单槽仅由同职责按报告索引接替，报告最终正文仍由专用只读审查者产生、父原样保存。任务/规则改变自然使key变化，不把新报告与旧格式并行接收。
