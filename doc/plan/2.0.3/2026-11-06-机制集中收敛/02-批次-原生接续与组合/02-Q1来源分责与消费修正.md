# Q1合法来源契约与本地消费者修正

2026-11-07，设计者定案，基线cb5ff694/Framework ff111909。Q1不再泛称“等Framework确认设计authority”：正常原生能力已存在，剩余需修的是Extension把部分设计出处当导入材料的消费边界。本页是B02中不依赖F1的局部来源职责切片，不为所有自指或来源强度补签合法性；本轮只形成方案。

## 1. 原生真实合同与合法含义

| 对象 | 原生实际核什么 | 不能据此声称什么 |
|---|---|---|
| 当前scope需求条目 | 真实文件、原字节SHA、原文片段与来源强度 | 当前源存在不等于人已授权所有推断 |
| 精确选中且实际承载typed内容的target | provenance形状和authoritative强度；其余未承载target不一律要求升级 | 不要求所有design_refs/根都改强度或canonical自指；此局部校验甚至允许缺失源，故PASS不证明源存在/语义权威 |
| 根contracts各段的source_ref | 外部/结构化契约文件的YAML JSON Pointer、逐段内容相等及可达性 | 与转写相等不证明转写忠实原件；不能候选反填转写求绿 |
| 原生CU provenance | owner蓝图的特定原生归属合同 | 不能把CU例外推广成所有节点自证 |

正常默认路径：保留真实原材料/有效人答/工程证据的provenance.source_ref；仅对确在当前授权内形成并承载typed的设计对象声明对应设计authority。内部设计关系沿原生design_refs/fact_refs/关系与决定表达，不因为报authority缺口就批量改自指。外部协议未知仍回外部owner，不由本地authoritative声明变成已确认事实。

合法本地设计出处指当前授权内实际形成、可定位且与有效需求/决定相符的设计记录；文件位置、schema通过或自指本身都不证明该语义。指回canonical只能提供内部定位，不能作为“这项外部事实/人类批准真实存在”的依据。设计者与独立质询核原件→决定→设计关系，确定性脚本只验证引用、原件与当前性。

## 3. 窄范围生产/消费设计

复用framework-access的refsOf/sourcesOf（产source_index）/authorityOf和现source_index字段，不新加source_kind白名单、designFiles账本、导入canonical步骤或兼容格式。

### 3.1 来源分流顺序

1. current_scope_items始终沿原来源登记/稳定版本/原字节/强度检查；根provenance和discovery事实的原料身份保持现材料责任，不以本地设计目录豁免。
2. contracts各段权威引用继续优先走authorityRefs/authorityOf：精确段引用由原生JSON Pointer验证后进入authorityFiles，同权威文件未核段仍拒，不能降级为普通文件/substring定位。这个已成立能力不重写。
3. refsOf在当前已有字段枚举中区分设计实体provenance（节点、运行数据流、关系、决定/缺口、contract对象）与上述原料引用。内部分类用于当次分流，不新增持久schema，不用where字符串前缀猜业务、更不信source_kind枚举自报。
4. 所有真实材料索引命中仍优先走原pick/expand：稳定版本、别名、source_revision、多文件/图/冲突与人答全部保持。
5. 设计实体关联未命中材料时，若文件属于**当前原生蓝图canonicalPath所在设计目录**，按现原生工程相对路径/普通片段解析读真实原字节，进入现projectFiles（仍保use/where、SHA）。目录从原生解析的canonicalPath派生；readBlueprint将本次load/check取得的该路径随现核查上下文交给sourcesOf，其他真实调用沿同一原生loader取路径，不从需求名猜目录。不硬编码Case/蓝图名、canonical文件名或额外后缀清单；不把“任意需求目录内文件”都放行。其他需求目录内未登记原料继续报导入/身份缺口，inbox/RR等不会因换source_kind而免登记。
6. 需求目录外工程依据沿现projectFiles路径。对本次实际需要读取的设计/工程引用，缺文件/坏片段明确报来源缺口，不因原生typed局部不验源或现exists短路而静默跳过。scope与材料采用门仍要至少一个真实登记材料版本，设计自引/工程文件不能单独满足它。

第5项只解除本次已证明的同蓝图设计归属误判，不自动接受所有任意路径的“设计文件”。新支持诉求不由执行者猜；原工程文件路径能力保持。普通片段校验是原生原文片段语义，不假装它理解JSON Pointer；需要结构化契约Pointer的仍只走第2项。

### 3.2 下游同一事实与恢复

- framework-access::scopeConsumption沿source_index同次结果，原sources/requirements只承接真实材料版本，projectFiles提供设计/工程字节，authorityFiles提供已核契约段。不得让projectFiles计作采用了本需求材料。
- blueprintSources、knowledge-task与questioning从现projectFiles把实际出处送到作者/质询者；review-object继续绑定现有字节与可回查文件，设计依据仅按问题回查，不改Story独立首读顺序。
- design-source::sourcesOf/currentBasis及material_key消费同一来源身份；被引设计记录真实修订应使旧basis失效，恢复回owner及正常原生修订/同步，不指导把合法新设计恢复成旧“不可改材料”。adoptedSourceProblems中把projectFiles一律叫导入材料损坏的说明同步区分。
- 设计/工程字节只证明当前出处；业务效力与自指是否构成循环论证由作者/独立质询按原件、授权判断。保人工区、旧原件、契约对原件忠实和最终组合要求。

## 4. 验证与退出

在test_knowledge_task、test_requirement_source、test_contracts_single_source及已有Story来源用例扩同一切片：

1. 保真实材料引用、仅真实selected typed目标有据authoritative时，原生阶段准备与Extension公开读取都可消费；不批改根/其他target。
2. 同材料采用前提下，对当前原生设计目录内真实记录与canonical内部定位的对照，确认projectFiles保原SHA/位置、requirements版本不增；knowledge任务、review-object和Story basis实际消费。
3. 未登记scope原料、设计实体误指inbox/RR未登记件、材料别名/坏摘要、仅设计自引无材料采用仍拒；source_kind换名不改变结果。外部工程/本地设计缺文件或坏片段明确缺口，不静默丢来源。
4. 合法设计记录变更使旧basis/material_key失效，走owner修订/原生质询与新Story登记恢复；真实材料原件变化仍按材料保护恢复。无须新增独立状态。
5. 契约段合法Pointer/坏Pointer/同文件未核段继续分别通过或拒绝，不能因新projectFiles分支漏过。原始转写与候选一致性的语义审查仍在，不用结构绿代签。

退出“需求目录内所有provenance都属于materials”的目录推论，以及设计/工程来源错误时统一要求恢复导入材料的说明；原导入版本、source_revision、图链、人答、authority与来源完整性能力不退出。需更新蓝图author/reviewer及evidence-rules中target authority说明，具体写本页§1正常路径，不塞案例答案。
