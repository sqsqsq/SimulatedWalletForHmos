### 1.1 请求阶段与范围

主执行者从现有有效授权确定requested-phases，参数在当前请求第一次prepare-scope时写定。按原生实际phase_chain/obligations执行/复用，不因为用户点了Plan就手写必须跑哪些前置；合法缺失/前置由原生报告，遇确需扩大授权的动作如实交回，不自行把单阶段改双阶段。只写指引与现入口参数消费，不增加授权状态/选择器。

用户明确Spec或Plan时不再问一次同样的确认。普通“实现方案”沿既有spec,plan请求；所有原生身份由当前CU返回取得，不拼业务名。后续阶段用同一请求/需求原文件；候选differs按05恢复，不覆盖冻结。

### 1.2 接受、已有CU与就绪

原生check-change-unit输出accepted、inventory、readiness、ready_ids和status的含义分别消费：

1. 新候选只接受一次；保accepted返回的实际副作用。随后就绪失败时，不能当接受没发生而重复accept。
2. 已有CU或修复后用--readiness；accepted此时可为空，身份/规范路径从inventory取，原生解析的feature_id用于下阶段。inventory是清单，不是可施工许可，包含退役项时不据此推进。
3. 按原生ready_ids/readiness/busy与用户授权求本次可接续集合。未就绪沿原生缺口/竞争提示处理，只暂停相关CU；不要手工写ready字段或等价状态。
4. 文档物化失败和施工readiness分别处理：原生给rebuildCommand时用它恢复投影，不重复接受，也不把纯文档错误改成新的施工许可门。实际影响最终Story依据时仍按既有同步/复核/登记处理。

### 1.3 收口指令真源

以固定原生harness-runner.ts的buildPassGuidanceLines/buildNextLine与真实summary为依据，phase-closure中唯一维护动作表：

| 原生动作 | 调用方行为 |
|---|---|
| run_verifier_then_receipt / rerun_verifier_with_current_request | 取当次签发request交原生阶段verifier；最终完整回复原样写到summary给的report路径，运行check-receipt，不无条件再跑完整harness |
| fill_receipt_then_sync_closure | 当前证据按原生可消费；按NEXT跑check-receipt或harness --sync-closure收口，不重派独审 |
| fix_verifier_findings_then_rerun_harness或真实材料变更 | 按原统一处置修最早责任，按NEXT重跑对应检查/独审；不由旧报告结论或自述跳过 |
| 阶段已closed | 核本次负责阶段current disposition及输入新鲜度；已有授权覆盖后续阶段时按原生请求链继续，不凭目录/closed历史签整单完成 |

上表解释原生分支，不在Extension复制next_action判定实现。check-receipt/原生finalizer承担证据采纳与闭环，不手写summary、receipt、物证manifest。最后交付仍需当前处置无本职责必修/待核、原生阶段证据与Story当前依据一致；沿现disposition和check --deliver消费，不加第二个完成门。

## 2. 最小离线验证组合

复用现test_blueprint_case_closure.py、test_verifier_report_protocol.py与design_fixture/knowledge-chain夹具，不新增测试框架、业务Case或真实模型运行。原有Plan FAIL/open五例保留，成功路径补在同一正常生产入口，避免仅测试字串。

### 2.1 三个必要分支

- 授权参数：单Spec、单Plan、双阶段从公开提示/实际原生prepare-scope输入验证，断实际请求范围与原生派生结果；复用阶段由原生解释，不断言每例都必须生成两个阶段报告。
- 已有与未就绪：新接受→再readiness的accepted为空但inventory身份正确；接受已落而readiness不成立时保副作用、不给后续执行。以真实原生构造的普通缺口或既有fixture取状态，不手改准备记录伪造正确分支；不穷举异常矩阵。
- 当前收口：实际harness签发request后，报告到receipt/finalizer的链能产当前合法closed；报告缺失/对象不符不被认完成，真实需要返修的结果仍按原生未完成。缺设备或不可得外部执行不伪造。

### 2.2 同一工程里的成功链

选现有已带合法蓝图验收、原生允许Spec复用的一个最小CU，保单阶段必须执行时的参数对照，不把本次扩成全业务端到端测试。

1. 从现设计夹具的蓝图和来源开始，实际accept-candidates产生CU；真实prepare-scope产生request候选，按其链执行Plan，真实prepare-blueprint-design只导本阶段输入。
2. 夹具承担作者边界，按原生required_outputs补合法Plan产物：contracts中的change_unit sidecar（change_unit_ref及predicate/provide/design_ref mappings）、context exploration事实、knowledge_context/实体义务、适用use_cases与正文。取现design_fixture/knowledge-chain已有合法生产方式，不把这些“作者写的产物”说成系统自动生成，也不预造冻结/完成件。
3. 正式harness自己冻结并检查/签发本对象request。仅在审查外部边界使用明确标为测试替身的合规最终回复，回显这次真实request的subject，不伪称模型审过。原生trace等required证据由现有正常工具/入口产生；不能禁用policy求绿或手改readiness。
4. 由实际check-receipt/finalizer生成summary当前闭环、receipt及物证，observer/end_target消费同一真实输出确认phase:plan。这里测试确定性接口/身份/采纳，不测试替身的业务判断能力。
5. 在同工程按现有Story夹具正常prepare→独立回复边界替身→接收/登记→check --deliver，核CU/蓝图/最终Story引用同一当前对象。合法设计修订时沿原生修订/当前性与原读者复核路径；旧阶段物证/旧Story依据应失效，责任修复后再消费。已有两条失效回归可复用，不再构造多轮极端回滚。

成功组合里若原生正常输入仍遇明确契约阻断，保存输入/命令/输出给设计者，不退回手填closed或降低标准；这不同于真实模型CLI未授权。单纯缺合法fixture产物由执行者在已定作者边界补，不交用户设计。
