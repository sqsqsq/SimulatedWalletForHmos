## 2. 成功闭环组合：Plan 走到签发审查请求，审查必审输入阻断

按 01 §2.2 在同一最小工程上跑（夹具作者以外全部走原生入口）：

1. 知识链夹具蓝图（`test_cu_knowledge_chain.design`）→ 施工单位改为候选，经 `--accept-candidates` 接受 → `prepare-scope --requested-phases plan` 派生 `[plan]` → `prepare-blueprint-design --phase plan` 只写 `contracts.yaml`。
2. 夹具作者按原生 required_outputs 补：`contracts.change_unit`（change_unit_ref 按 canonical CU 原字节摘要，predicate/provide/design_ref 三组映射）；`context/facts.md` 用 schema 1.1，`established_by: plan`，`frozen_scope_fingerprint` 由原生 `executionScopeFingerprint` 算冻结范围；探索来源从 demo 复制 7 份真实文件。
3. 正式 harness 自行冻结，脚本检查 PASS（只剩 integration_points 的 SKIP），`next_action=run_verifier_then_receipt`，并签发本对象的 verifier request（subject `00fa6d1e…`）。

**阻断**：同一 request 的审查提示（Extension 钩子片段 4）把 `knowledge_obligation_substance` 的必审输入列成本单位目录下 `spec/spec.md`、`acceptance.yaml`、`plan/plan.md`、`contracts.yaml`、`use-cases.yaml` 五份，前四份以外都标「读不到：必审，缺了不能判 PASS」。原生在这条复用路径上的事实是：

- `readFeature(plan)`：`acceptance` 已 resolved（来自蓝图验收），`contracts` 已 resolved，status ok；
- 本单位 Spec 由原生复用、没有执行，没有 `spec/spec.md` 和本地 `acceptance.yaml`，`use_cases` 也不是这次 Plan 的输入；
- Extension 自己的 plan 门禁把没有 `plan.md` 当作「前置缺失、交独立审查核」，不判阻断。

所以一份合规的审查回复在这条路径上只能列 unreviewed 并判阻断，成功闭环走不通。产生这个集合的是 `extensions/hooks/shared/review-inputs.mjs:149-153`：五份写死为本地文件、`required` 默认真，没有按原生对本阶段输入的解析结果取。

我没有改它，也没有写替身 spec/验收来绕过：必审集合该按原生解析结果取（复用的验收指到蓝图来源）、`plan.md` 与 `use-cases.yaml` 什么时候是必审，属于 Plan 审查读法的设计，01/02 分册都没覆盖，交设计者定。现场（命令、原生输出、作者夹具、facts、契约、summary、request、必审输入节选、探针脚本）在 `output/evidence/2.0.3-B01-R01/20261108/success-chain/`。

受这一项影响、本次没做的：verifier 替身回复 → `check-receipt` 收口 → observer 认 phase:plan → 同工程最终 Story 依据（01 §2.2 第 3—5 步）；01 §2.1 的「接受已生效但就绪不成立」状态，我没找到正常原生构造方法，也没有做。
