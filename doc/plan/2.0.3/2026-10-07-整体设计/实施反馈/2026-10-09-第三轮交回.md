## 4. 术语漏问的调查结果

证据都在 `output/story/story-suite-20261003-215006/cases/car-key-sharing/20261003-215418-3560-9d94e32d/events.jsonl`，可以用 `output/scratch/2.0.3-p1/trace_terms.py` 复查。

| 环节 | 事实 |
|---|---|
| 规则送达 | 第 5 步读了 Story SKILL，其关卡表写明「术语确认（framework 的关卡）｜你问。蓝图设计里确认术语时，交互态下请人逐条确认｜人确认之后才登记为已确认」（`extensions/skills/story/SKILL.md:98`）。第 48 步读了 Framework 蓝图工作流：medium、low 置信度须当场确认，记 `user_confirmed`；headless 自动继续才记 `headless_assumed`（`demo/framework/skills/reference/app-component-blueprint-workflow.md:40`） |
| 作者的做法 | 第 206 步在蓝图生成器里直接把三条术语写成 `headless_assumed`，没有发起确认 |
| 门禁结果 | 第 231、252 步原生检查给出 3 条 WARN，0 条 BLOCKER |
| 作者的判断 | 第 254 步写下「Zero BLOCKER, only 3 WARN (headless terminology assumptions, expected for automated runs)」，把这次交互运行当成了自动化运行 |
| 原生门 | `blueprint-discovery.ts` 遇到 `headless_assumed` 一律只给 WARN（195 行），不区分运行模式，所以交互运行里不问也能准入 |

定位分两层：

1. **作者违反了已经送达的合同**。规则在设计之前就送到了，作者误判了运行模式。Extension 的术语关卡只写在 SKILL 的关卡表里，不像材料、范围关卡那样有 `story_flow` 的确定性停点，作者可以跳过而不被发现。
2. **原生门在交互态放行了 `headless_assumed`**。门禁本身不知道当前是不是交互运行。这一层是否算上游缺陷，取决于 Framework 是否本来就打算由门禁判断运行模式，现在不下结论。

可能的改法，按「改在最早拥有这项职责的位置」排列，都还没有实施：

- Extension 的维护范围只覆盖 interactive（AGENTS §0），所以成文前的设计消费检查（读蓝图状态的那一处）可以把 `headless_assumed` 的术语当成「术语未经人确认」报出来，挡在成文之前。这样不复制 Framework 的确认状态机，只是不消费未确认的术语。
- 或者把术语确认做成和范围关卡同样的确定性停点。
- 如果设计者判断门禁应当区分运行模式，就另列最小复现报给上游。

另外，auto-topup 的蓝图里**一条术语事实都没有**，原生检查也没报。这是不是当前范围本来就不需要术语事实，还要核，一并交给设计者。
