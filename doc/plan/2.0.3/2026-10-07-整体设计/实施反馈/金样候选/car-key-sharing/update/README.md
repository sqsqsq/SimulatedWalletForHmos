# car-key-sharing/update 候选：来源与语义差异

> 情景终点：承接评审人在 Review 人工区的表态。宽限窗那条意见与「车辆侧撤销即拒绝」冲突，按 update 规则登记为待确认议题 D7，停下问人。
> 状态：**维护构造的待裁定候选**。评审表态全部来自既有测试的预置输入，不是真实发生的回答（§2）。以 [reviewable 候选](../reviewable/README.md)为起点，蓝图未改动、仍未准入。这份候选不是正式金样。

## 1. 阅读入口

| 读什么 | 打开 |

## 2. 哪些是真实发生的，哪些是预置输入

| 内容 | 来源 | 能证明什么 |
|---|---|---|
| D1、D2、D6 人工区里的勾选与意见 | 既有测试预置输入 `test/cases/car-key-sharing/update-inputs/car-review-feedback.yaml`，由测试域的 `run_case._write_review_zones` 写入 | 只能证明在这组输入下 update 应当怎样呈现；**不证明**人真的这样表态、流程执行过、update 已闭环 |
| 材料关卡「不补」、D7 的立场 | 交互脚本里的预置台词，没有送出 | 都没有用。没有开流程轮次，也没有跑 `decide` |
| 10-03 实跑 | 只跑到 plan 阶段就因输入超过 1M token 终止，没有 update 段 | 这一段没有任何真实回答 |

生产入口的验证仍须真实走关卡（10-08 设计者裁定）。

## 3. 生成方式

| 步骤 | 做法 |
|---|---|
| 起点 | reviewable 候选的工作区 `ck-review`（D2 已拆分、术语已如实记录）复制为 `ck-update` |
| 评审表态 | 预置输入写进人工区：D1 需修改（36 小时那句）；D2、D6 暂缓。拆分之后，两条「暂缓」各自落到自己的议题上 |
| 修订 | `revise_ck_update.py`：登记 D7（open，选择题，建议按卡片收回期限理解）；业务方案与验收的撤销宽限处各补一句指向 D7。经 `chapter` 提交、`build` 渲染 Review、`number` 编号 |

## 4. 语义差异（相对 reviewable 候选）

| 项 | reviewable | update 候选 | 依据 |
|---|---|---|---|
| D1 人工区 | 空 | 需修改，预置原话照录 | 预置输入 |
| D2、D6 人工区 | 空 | 暂缓，预置原话照录 | 预置输入 |
| D7 | 无 | 新登记：36 小时指卡片收回期限，还是车辆侧仍认钥匙；两边来源并列 | 系统设计状态机一节、产品稿「失效前车辆侧就要拒绝」与意见原话冲突 |
| 正文 | 宽限待对齐 | 补一句：评审人提出 36 小时，含义待确认（D7），确认前不改方案 | 同上 |

保持不变的部分：D1 正文（评审人已对它表态，改了渲染会拦下）、D2–D6 正文、蓝图、状态机与车辆侧拒绝的口径。
