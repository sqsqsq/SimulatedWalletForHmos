# auto-topup/initial

- 情景终点：系统送审，零施工单位。
- 目标产物：`AR/story.md`、`AR/review.md`、`assets/` 配图（取自产品原稿《交通卡自动充值》抽出的界面图）。
- 输入：`test/cases/auto-topup`（基底 `15844e09`；交互脚本 10-10 补承载立场后为 `1c1c6561bda0443c`，答案卷 `999e5cc4b578744d`，记账见 `test/EVOLUTION.md` §7）。目标工程 demo 与知识取 `15844e09`。
- 有效宿主立场：会议各话题按 `meeting-*`（加更新接口；AC-R1 与开关按会上改；充值记录按月筛选不属本单；调高面额是否重验、授权后建约失败保持待定）；`no-real-interface`（卡云与支付接口接不上，先用模拟数据验证钱包端，真实联调另算，D7）；范围不拆；术语确认；送审。
- 设计选择：授权后创建失败分「明确失败」与「结果未知」，结果未知以状态查询确认、不当成没签成；面额调整（调高、调低）的验证待定，只改门限不验证已定；缓存缺失与查询失败不推断未签约；「创建签约成功率」与业务目标「签约转化率」分开。
- 相对旧稿的具体优化：按修订合同改正 G01、G02、G03、G08；对照 1.x 最佳形态补上目标来源与端侧承诺边界、易混说法表、范围不拆与按月筛选去向（D6）、工程承载现实与承载表（D7）、取舍三列表与业务规则表、恢复路径、验收分组与模拟口径、统计口径、版本回退与关闭不可逆；Review 去掉三条指不出人表态的已定议题（档位来源、入口矩阵、判重，属材料事实或由 D2、D5 推出），D2、D5 依据补会上原话；业务流程补签约分支图、签约时序、服务端充值链与签约状态图、开放顺序图；删去指着文档说话的句子；材料清单链接回 Case 原件。
- 可参考的表达位置：签约流程图与时序图的分工（分支去向一张、跨方交接一张）；服务端充值链里的单日上限与连续失败分支；取舍三列表的「没选的做法为什么不行」；未定边界已定与待定分开写；验收 AC-R10、AC-R11 的可观察条件。
- 这是期望结果：人的回答取自 Case 设计的宿主立场，是构造预期的输入，不是已发生的人签；它不证明产品已能产出这份结果。
