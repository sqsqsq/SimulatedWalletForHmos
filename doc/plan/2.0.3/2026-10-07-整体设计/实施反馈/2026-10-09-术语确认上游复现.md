# 10-09 术语确认上游交接：交互运行里的 headless_assumed 只给 WARN

> 读者：Framework（AgentMaison）原生蓝图负责方，以及维护设计者。依据：[P2](../02-步骤2-产物与独立审查.md)「术语确认的上游交接」。
> 本文只给复现与接口/行为请求，不改本仓的 vendored 副本，不在 Extension 加术语关卡。

## 1. 现象

10-03 的 car-key 实跑声明为交互运行（`test/cases/car-key-sharing/case.yaml` 写 `interactive: true`）。作者在生成蓝图时，把三条 medium 术语直接写成 `extraction_method: headless_assumed`，没有发起确认。之后作者写下「Zero BLOCKER, only 3 WARN (headless terminology assumptions, expected for automated runs)」，蓝图照常准入。这三条术语从头到尾没问过人。

事件证据和逐步定位见[第三轮交回](2026-10-09-第三轮交回.md)第 51–59 行。

## 2. 实际接入版本与代码位置

- Framework 3.1.0，source commit `074a4c3c4a0591c8ed2162e2a0d048a1fdec081f`（`demo/framework/RELEASE-MANIFEST.json`）。
- `harness/scripts/utils/blueprint-discovery.ts` 的 `validateTerminologyFacts`：`headless_assumed` 一律以 WARN 返回（第 194–196 行），不看当前是不是交互运行。
- 检查器 `check-component-blueprint.ts` 的参数只有 `--project-root`、`--blueprint`、`--ref`、`--materialization`、`--projection`、`--feedback`、`--json`。蓝图里也没有声明运行模式的字段，检查器无从判断。

## 3. 最小复现与实测输出

脚本：`output/scratch/2.0.3-p1/term_headless_repro.py`。

1. 把 10-03 实跑保留的 car-key 工作区复制到临时目录（不带 `framework/` 与 `node_modules`）。
2. 只改蓝图里第一条 medium 术语事实的确认方式，用 3.1.0 原生检查器运行：`npx ts-node scripts/check-component-blueprint.ts --project-root <临时工作区> --blueprint bp-ISSUE-206 --json`。

原始输出在 `output/scratch/2.0.3-p1/term_headless_repro.out.json`。

| 对照 | 术语事实 | `terminology_facts_confirmed` |
|---|---|---|
| A | medium，`headless_assumed` | **WARN**：「headless 自动继续（headless_assumed），入 must-review…」 |
| B | medium，`user_confirmed` | 无问题 |
| C | medium，未确认（`model_inference`），无停放 | **BLOCKER**：「medium 置信度未经用户确认…交互态须当场确认并记 user_confirmed…」 |
| D | medium，未确认，由远期 `open_decision` gap 停放 | WARN：「已由 gap … 停放到远期切片…」 |

四个对照还都报了另外两项 BLOCKER：`blueprint_questioning_provider_missing` 与 `blueprint_source_fingerprint_mismatch`。原因是这份工作区是未准入的候选现场，四者都有，不影响术语分支的对比。D 为构造停放补的最小 gap 还额外带出几条 schema 与 gap 控制问题，只说明停放分支确实走到了。

「high 且 glossary 精确命中」这一对照本次没有构造运行。按代码第 211–214 行，它只在 glossary 精确命中且模块一致时直接确认，与本请求无关。

结论：同一条未问过人的 medium 术语，记成「未确认」会被拦（C）；改记 `headless_assumed` 就只是 WARN（A）。在交互运行里，作者换一个确认方式的字样就能绕过当场确认。

## 4. 请求的接口与行为

1. **原生能拿到运行模式**：由宿主或运行装置提供这次运行是 interactive 还是 headless。可以是检查器参数，也可以是蓝图或运行状态里由宿主写、作者不能改的字段。字段形态由原生方定。
2. **interactive 运行拒绝 headless 来源**：运行模式为 interactive 时，medium 或 low 术语的 `headless_assumed` 按 C 同样判 BLOCKER，并提示当场确认。
3. **其余对照不变**：
   - headless 运行里的 `headless_assumed` 仍为 WARN 并入 must-review；
   - `user_confirmed` 通过；
   - 合法的远期 gap 停放仍为 WARN；
   - glossary 精确命中的 high 仍直接确认。

   不把所有 WARN 一律改成阻断。

## 5. 本仓边界

- 不增设 story_flow 术语关卡，不复制原生置信度算法，不改 vendored 代码。上游未交付前，这项自动兜底标「未验证」。
- 真实 CLI 只观察作者是否按已送达的规则当场提问。规则写在 `extensions/skills/story/SKILL.md` 的关卡表，以及 Framework 蓝图工作流。
- 蓝图里没有 `term:` 事实本身不算缺陷，要按当前材料与工程核有没有需要消歧的映射。
- 结果金样的编写不等待这个接口。
