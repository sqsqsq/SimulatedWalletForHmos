# 金样职责修正与执行合同

2026-10-09。用户要求将修正方案落盘，交维护实施者修改。维护设计者负责本合同与交回评审，不代改产品或测试。本文替代现行 spec/plan 中要求金样维护完整生产现场的条款；原有产品能力、P2/P3 有效改动、真实验证与发布边界保持。

## 1. 目标与责任

金样定义给定输入下期望的交付结果；专项回归验证确定性机制；真实 CLI 验证消费模型的实际过程与结果。三者共享需求依据，各自交证据，不互相冒充完成。

金样直接根据 Case 原始材料、目标工程事实和宿主立场编写。预置立场是构造预期的合法输入，不是已发生的人签。无需先制造准入蓝图、独立质询记录或阶段回执。金样内容仍须有据、完整、可读、可实施；不能因脱离生产装配而降低质量。

真实运行的蓝图、决定和流程状态仍须检查，必要时用它们定位错误，但不将其固定为效果金样。没有真实调用时不制造质询、审查或完成事实。

## 2. 唯一范围与落点

| 情景 | 目标金样 |
|---|---|
| auto-topup/initial、auto-topup/update | Story、Review、必要配图 |
| car-key-sharing/reviewable | Story、Review、必要配图 |
| car-key-sharing/plan-ready | Story、Review、必要施工单位的 Spec、Plan、必要配图 |
| car-key-sharing/update | 更新后的 Story、Review，以及本次变更影响的已有 Spec、Plan；必要配图 |

候选沿用 `实施反馈/金样候选/<case>/<情景>/`；正式正本在用户审定后进入 `test/golden/<case>/<情景>/`。Story/Review 放 AR 下，Spec/Plan 保留能明确所属施工单位的目录，但只保存目标 Markdown，不伴随运行状态。图片使用情景内相对链接。原始输入仍在 test/cases，不复制整套输入到金样。

每组只带简短 README：采用输入版本/摘要、情景终点、有效宿主立场、必要设计选择及配图来源。它是追溯说明，不是新的业务权威或数据库。

`design-review.md` 不设独立效果金样。产品仍生成并交付它：专项回归验证其与原生投影同源；真实审查核内容正确、引用可达及与 Story 无矛盾。不能以退出金样为由删除附件能力。

附录直接编写完整期望内容，不留下“未准入无法投影”的缺件，不为填写附录创建蓝图现场。金样不需要机器区摘要、准入标记或流程记录证明自身成立。需要验证这些机制时使用专项夹具。

## 3. P1：完成期望结果

1. 固定采用的 Case 输入与宿主立场，沿现有来源说明记录本轮输入变化；保留历史版本作证据。
2. 复用已有有效 Story/Review 修订，补齐各情景目标文档、附录和配图。G01–G09、签约与充值链、身份与脱敏、未决边界和跨件一致性继续核。
3. 通读每组产物：仅看 Story/Review 能理解整体需求与争议，Spec/Plan 能判断施工范围、实现落点及验证责任，多个产物对同一事实不矛盾。
4. 进行独立内容评价与用户效果审定。独立评价输入是原始依据、目标稿和效果判据，不要求派审前先造生产状态；模型调用沿既有授权边界。

车钥匙本人钥匙来源按本轮模拟承载立场处理：期望方案明确模拟的本人钥匙数据、车辆标识及分享关系，真实数据源与联调另列依赖。不得虚构已存在真实接口，也不为写金样修改 demo。具体数据结构由实施者按真实工程和已有接口设计，换一种合理实现不应判错。

P1 完成条件：所有目标文档完整可读、业务有据、跨件一致、无运行状态造成的内容空缺。证明的是期望结果已明确，不是产品已能产出它。plan-ready 不再因金样没有准入现场而只交缺口清单；真实业务未定事项仍如实表述。

## 4. P4：消费者迁移与机制回归

不新增框架、运行器或金样生成器。先登记实际消费者和有效覆盖，再迁移；不能只换名搬走整套旧装配。

| 当前对象 | 动作 | 必须保持 |
|---|---|---|
| golden_workspace.py、golden_design.py | 退出效果金样的整链装配、旧格式映射和重投；消费者迁完后删除失效实现 | 有效机制场景复用现有 design_fixture 等专项夹具；确需抽取 helper 时限于当前测试职责 |
| test_golden_sample.py | 检查目标文件、配图、链接、审定版本；退出要求金样拥有准入现场的断言 | 金样完整性；业务质量由语义评价核 |
| test_review_golden.py、test_review_modes.py | 采用小型明确输入与确定性预期，不从整份业务金样反推登记状态 | 编号、分组、人工区保护、重复渲染 |
| test_story_build.py、test_verifier_report_protocol.py | 使用既有专项夹具验证生产入口 | 章节写入、机器投影、附件同源、来源与审查对象绑定 |
| check_failure_modes.py | 将整份金样装配依赖迁为对应机制的正反例，同步台账引用 | 正常输入不误拒、错误能发现、判据实际执行 |
| README、指纹、枚举与唯一副本检查 | 消费新目标路径与职责；删除“拦金样必然是判据错”的说明 | 已审结果唯一、变化可追溯 |

字节比较只用于确定性渲染、审定文件保护和副本一致性。实跑产物与金样按语义与读者效果比对，允许合理的组织、图形、设计和 CU 划分差异；不要求内部状态或中间路径一致。

正式切换前用户审定目标金样、覆盖迁移通过；切换后仅新正本承担效果权威，方案候选退为审定证据，不继续双份编辑。真实 CLI 与性能验收仍是版本完成条件，但不再是编写期望稿的前置。

## 5. 文档与退出动作

执行者落实以下文件动作，按本合同正向改写，不在正文保留相反条款：

- 2.0.3 spec 的 R1、R4、版本总览：统一结果范围、Case 立场和完成条件。
- plan 的总览、P1、P4：撤下原生现场作为金样前置及五情景完整装配要求；P2/P3 仅同步依赖，不重写已成立机制。
- 历史评审保留事实，注明被本合同替代的金样状态要求；不继续以旧裁定阻塞结果编写。
- 候选中的蓝图、登记、章草稿、更新过程、设计反馈、指纹及质询状态退出日常维护；只为维护这些候选而存在的临时生成/重投/拼装脚本一起退出。
- 阅读副本不再携带金样中间件；目标 Markdown 与配图可直接阅读，不新增导出流程。

删除前核实际消费者与本轮在途修改；真实运行证据、原始材料、不可变历史基底、仍有效专项夹具保护。原始输入不因金样修订被静默更换。已有测试覆盖没有接替前不得先删。

这是一轮职责纠正，不新增版本或实施包。P1/P4 承担上述修改，其他已通过工作保持。

## 6. 验证、预算与交回

按 test/TEST.md 使用现有 verify.py：迁移时对实际改动跑 affected（golden_sample、review_golden、review_modes、story_build、verifier_report_protocol、run_measurement 及新增发现的消费者）；最终跑 handback。失效形态同时核台账引用。检查全仓旧 helper/夹具/旧格式映射引用，无消费者后退出。用户未授权时不启动新模型或 CLI。

交回包括：目标产物入口、内容改动及依据、实际消费者迁移表、保留/退出覆盖、验证日志、未验证范围、金样效果与真实行为证据的区别。逐包交回后集中评审，不为维护虚构中间状态再开返修轮。

本项预计产品运行机制 G/X=0，不需要新增运行功能。维护域 helper 与测试退场按真实清单核，不预设删行指标、不靠删覆盖省预算。已有 P2/P3 计量和逐轮累计保持，删除不冲销历史新增。若迁移暴露确需产品改动，先交最早责任与必要性评审，不扩建旁路。

最后分别签收：金样表达了正确期望；专项回归证明确定性机制；授权 CLI 证明真实过程、结果和成本。发布、推送、demo 更新不在本合同授权内。
