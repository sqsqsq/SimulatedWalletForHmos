# P4 综合验证、金样切换与完成

需求：[R4](../../../spec/2.0.3/04-综合验证与成本观测/需求.md)。本步承接 G1/G2/Q1、审查有效性和需求执行成本；安装与 SVG 增强不混入本轮变量。

## 验证顺序

1. 每包定向自验后核实际源版本，最终跑现有 `verify.py handback`，已知历史失败单列，不用全绿替代内容评审。
2. 按 R4 场景核 P1 候选与原始来源/真实决定，核正常与相关异常、不同合法输入。独立审查报告要对应当前对象，真实读过什么、谁写了原件可回查。
3. 获授权后跑正常系统/本地 Case，按实际索材与问题回答，自动充值按现有初段 submitted＋update，车钥匙按 plan 上限＋现有 update；金样和维护答案不进入消费工作区。不为覆盖强造同数量 CU，未决未裁定时正确停等不能算施工完成。
4. 依规格 R3 §3 的配对/非增长签收条件评价成本，不用报告数或失败运行耗时替代；用户按 TEST 三轴确认消费效果，Coding/设备/内网无证据的保留未验证。

## 正式金样切换

切换前检查所有实际消费者：`test_golden_sample.py`、`test_review_golden.py`、`test_review_modes.py`、`test_story_build.py`、`test_run_measurement.py`、golden_workspace 及装配/枚举/指纹/唯一副本逻辑。旧样本有效场景逐项指出新承接或保留为小型专项输入，不能随旧正本误删。

用户审定候选、对应生产验证和覆盖迁移都成立后，才把两 Case 正式效果正本一次切到 `test/golden/`，输入/知识快照仍在 `test/fixtures/golden/`。方案候选退为审定证据，不再被日常装配消费；旧错误机制及专用断言退出。历史参考原件不改，不留两份现行可编辑正文。

切换未获审定或验证失败时旧正式基线继续供既有回归，新候选只供审核。指出内容、Framework、机制、装配或授权缺口，由实际责任方处理，不抹掉原始失败。

## 完成报告

分别交内容效果、独立过程、知识传递、成本、原能力保持、旧职责退出和预算 G/X/净增。2.0.2 的正常阶段/发布恢复/依赖收口引用其最终评审，不由本步代签；上游未交付的对应能力不写完成。

本版机制发布、demo 更新、README/release 和推送另按授权。本轮版本重整只建立这些步骤，不执行产品修改、金样切换或新 CLI。

## 消费者切换清单

| 现行消费者 | 本步动作 | 保持的责任 |
|---|---|---|
| test/golden/README 与既有 story-金样-AR90004、review-金样-AR90006 等旧效果正本 | 用户审定后指向 P1 明确的新 case/情景路径；退出被取代正文的日常效果权威 | 旧独有合法场景保留为小型专项输入，不删覆盖 |
| golden_workspace.py / golden_design.py | 显式选择新 case/情景输入及知识快照，复用原生设计/生产检查；退出仅为旧格式搬运的映射分支 | 真实输入装配、来源身份和现行产物检查 |
| test_golden_sample / test_review_golden / test_review_modes | 指纹绑定审定的新正本；Review 用对应真实决定渲染 | 原话、人工区、结构与幂等 |
| test_story_build / test_run_measurement 及枚举/唯一副本检查 | 更新已确定新路径与消费者集合；不将现行设计附件当废弃中间件 | 来源、图片、命名/位置与效果正本唯一 |

先验证新装配，再在同一实施步骤切换以上消费者；失败时不宣告新正本，保留待审候选。原始历史证据不修改。自动扫描其它真实引用补入同一切换步骤，不创建另一个日常金样根。

同步退出旧 README/测试注释中“任何判据拦金样，错的一定是判据”的绝对说法。新合同为：审定金样与原始来源均为复核依据；失败先定位来源/样本/当前规则是否发生真实变化，再回责任方修，不能以金样名义豁免有效约束。指纹只保护已审字节，不证明业务永远正确。
