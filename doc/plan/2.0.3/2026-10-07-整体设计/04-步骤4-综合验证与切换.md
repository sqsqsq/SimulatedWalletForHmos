# P4 综合验证、金样切换与完成

需求：[R4](../../../spec/2.0.3/04-综合验证与成本观测/需求.md)。本步承接 G1/G2/Q1、审查有效性和需求执行成本；安装与 SVG 增强不混入本轮变量。

## 验证顺序

1. 每包定向自验后核实际源版本，最终跑现有 `verify.py handback`，已知历史失败单列，不用全绿替代内容评审。
2. 按 R4 场景核 P1 候选与原始来源/真实决定，核正常与相关异常、不同合法输入。独立审查报告要对应当前对象，真实读过什么、谁写了原件可回查。
3. 获授权后跑正常系统/本地 Case，按实际索材与问题回答，保留初段/update及实际施工上限；金样和维护答案不进入消费工作区。不为覆盖强造同数量 CU，未决未裁定时正确停等不能算施工完成。
4. 相同质量与终点后评成本；用户按 TEST 三轴确认消费效果，Coding/设备/内网无证据的保留未验证。

## 正式金样切换

切换前检查所有实际消费者：`test_golden_sample.py`、`test_review_golden.py`、`test_review_modes.py`、`test_story_build.py`、`test_run_measurement.py`、golden_workspace 及装配/枚举/指纹/唯一副本逻辑。旧样本有效场景逐项指出新承接或保留为小型专项输入，不能随旧正本误删。

用户审定候选、对应生产验证和覆盖迁移都成立后，才把两 Case 正式效果正本一次切到 `test/golden/`，输入/知识快照仍在 `test/fixtures/golden/`。方案候选退为审定证据，不再被日常装配消费；旧错误机制及专用断言退出。历史参考原件不改，不留两份现行可编辑正文。

切换未获审定或验证失败时旧正式基线继续供既有回归，新候选只供审核。指出内容、Framework、机制、装配或授权缺口，由实际责任方处理，不抹掉原始失败。
