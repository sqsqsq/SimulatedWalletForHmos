# P2 产物表达与独立审查效果

需求：[R2](../../../spec/2.0.3/02-产物内容与独立审查/需求.md)。输入为 P1 审定差异、当前实际机制与必要预算，不能凭历史样例错误预设产品仍有同一缺陷。

## 处理责任

| 真实差距 | 现有落点 | 应有结果 |
|---|---|---|
| 决定在不同产物变义 | Story 的 design/update 作者流程、蓝图实际决定与审查 | 回最早权威修完整影响面，不只把正文改绿 |
| 人读件难以评估 | story-chapters、story-write、作者写作设计/摘要 | Story 讲清业务全貌，Review 给可决定的争议，技术附件可查，CU 文档能判断局部实现 |
| 审查受作者结论影响 | 当前 reader-review-task / story-reader-rules 与既有 dispatch | 主执行者交真实材料/客观变化，独立审查自行判断；原始回复不由作者加工 |
| 知识只回显或实际链断 | 当前 knowledge 作者任务/决定/义务消费者 | 理由指具体事实，实体承担实际行为，不以 must 存在代替可执行 |

文件动作沿实际生产者/消费者修改；规则在一处维护，其余引用，不新增专属状态或报告协议。正常消费者必须继续用当前 prepare/check，不恢复旧代码审查 request、旧 Spec 知识真源或已退出资格工具。

## 具体文件动作与行为合同

1. 修改 `story-chapters.json` 的范围、业务方案、流程和附录 questions/boundary；`phases/story-write.md` 与 `writing-plan.mjs` 空壳从该合同取得读者目标。阅读主线明确“责任边界→整体协作/关键取舍→状态与分支→验收/待决”，允许作者按真实关系分节；不新增必填自证表、固定图数或全文模板。Story 自身回答整体问题，附件只作精确核对。
2. 修改 `phases/meeting-read.md`、`phases/design.md`、`phases/update.md` 的决定处置：在已有 doc-refresh/update-notes 中写本次决定、实际原话和受影响原生地址/人读位置，按真实权威先修设计再修派生；原文/人签不改。纯表达仅改章稿。有相反 canonical 主张时独立审查仍阻断，不因“属于蓝图侧”降为建议。这是模型语义任务，不建自动影响图或另一个状态表。
3. 修改 `story-reader-rules.yaml`，消除同一条一致性/图文/来源要求在多个段落的重复说明，保留一份可执行判据；`reader-review-task.mjs` 继续从原规则和章合同加载。本轮明确要求核两个不同层次：原始决定与设计是否一致、设计与人读件是否一致。未知结果、真实身份、缓存/云状态与入口接入按具体语义核，不把 G01–G09 名称或数值写进规则。
4. 保持 `review-report-contract.mjs`、prepare/dispatch/check、材料键与原件恢复规则；不换报告格式、不新增判据账本。复审输入沿当前 dispatch，不附作者“已全部关闭”的结论。坏报告按现行独立返修，不能作者手改原文。

变更只覆盖上述作者/判据/任务及对应测试。若 2.0.2 已实现完全相同的要求，核其消费者后不重复写一份；该条交回引用实际实现。若实际来源推翻设计则回蓝图负责方，未交付原生能力保持依赖，不由实施者选择新 API。

## 定向验收

`verify.py affected` 选择 test_story_build、test_writing_plan、test_verifier_report_protocol、test_knowledge_application、test_cu_knowledge_chain 的实际改动组。保留无 Spec/零 CU 成文、合法复用、章节字节保护、人工区、原始报告与当前对象绑定。

语义验收直接读候选：只看 Story/Review 可解释整体责任和主路径，技术附件无相反结论；同一决定变化覆盖其所有实际影响，不在另一件保留旧主张；段落/表/图的合法组织不因形式被误拒。用中性业务的同类输入核通用性，不对 Case 词条或字段个数加规则。

## 交回

每项给原缺口、最早责任、实际变更、旧消费者退出和独立内容结果。P1 的候选可同步修订，但本步不直接切正式金样。不新增 SVG 或安装流程；出现需要新原生能力的事实单列，设计者定合同后再实施，不能临场做旁路。
