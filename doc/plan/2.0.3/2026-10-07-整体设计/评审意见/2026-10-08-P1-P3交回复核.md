## 必须处理的问题

### R1：候选把签约与充值订单混为一谈（P1，重要）

`金样候选/auto-topup/initial/AR/story.md:111` 写“创建签约成功但写卡未完成：订单保持充值中”。原始 `test/cases/auto-topup/system/SR90006/design.md` §4 的条件是“扣款成功但写卡未完成”；签约接口只建立关系，并不因此产生充值订单。候选 §7.1 又按正确的扣款条件写，形成篇内矛盾。

修订应回到两类对象的生命周期：签约成功结束签约链；余额触发、扣款与补写属于后续充值链。保留后续链的整体说明，核蓝图、附件、正文和验收是否还有混用，不新增匹配这句话的产品检查。完成条件：读者能区分“已签约”和“有一笔充值订单”，同一补写分支在各件中的触发条件一致。

### R2：修改候选后仍保留旧质询完成与准入事实（P1，重要）

两份候选蓝图的 `review_summary.questioning.status` 仍为 `complete`；自动充值 `component-blueprint.yaml:17–27` 还标 `admission.status: pass`。README 明确承认修订后未重新质询。候选是维护构造稿、保留 revision=1，并不能使旧独立回复成为当前内容的审查证据；原生结构 PASS 也不能证明这一点。

保留旧报告作历史来源，当前候选不得把它登记为本版已完成质询。按原生合同保留未完成状态；若完整投影/准备入口要求已准入，先交明确未准入的设计草稿和可阅读候选，不为了过门保留假的通过。待授权的独立质询及实际处理后再生成当前准入事实。此项修候选和交回事实，不新增 Extension 准入旁路。

### R3：导出的候选不能直接阅读图片和核对来源（P1，重要）

实际检查两份候选 Story 的相对链接：自动充值 20/20、车钥匙 19/19 的本地链接目标不存在，包括正文图片和冻结来源。README 只说素材仍在底稿，没有给逐件可核的阅读映射；当前 Markdown 打开即缺图，不能以工作区里结构通过代替交回可读。

继续遵守原件与大件证据放 output 的约定，不把素材复制进 doc/plan。利用已有底稿/工作区，在 output 下保留与这次候选同字节的人读三件、相对布局及必要来源，在候选 README 给出准确可打开的阅读入口、来源与摘要，并核图片全部可达。doc/plan 仍是唯一可编辑候选，output 是可重建的阅读副本，不成为第二正本。临时工作区不能作为没有保留说明的唯一证据。无需新建打包器或运行状态。

### R4：Story 的议题引用在 Review 正常预览中无法定位（P2，中等）

候选大量引用 D3/D4/D5，但 `review.mjs:386` 只输出章节号和标题，D 编号在 HTML 注释中。执行者已经正确发现此问题，应在现有渲染职责直接修复。

裁定：Review 标题显示稳定的 decision ID，同时保留现有章节号、标题、HTML 机器锚和人工区保护。Story 继续引用稳定 ID，不让作者手工追随可变章节号。覆盖多个议题、分组/排序变化和重复 build，证明可见 ID 正确且人工区逐字节不变；不新增编号登记或同步机制。
