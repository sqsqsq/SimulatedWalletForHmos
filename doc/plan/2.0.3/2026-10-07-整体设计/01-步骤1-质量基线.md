# P1 两 Case 的有据质量基线

需求：[R1](../../../spec/2.0.3/01-两Case金样与质量基线/需求.md)及其 G01–G09 修订合同。本步不改生产机制或正式金样，先交可供人评估的正确候选。

## 输入与产出

读取 Case 当前原始材料、历史候选、真实用户问题/选项/回复、目标工程与知识。首先记录版本和实际文件来源，旧 factbase 仅为定位线索。候选放本计划 `实施反馈/金样候选/<case>/`，原始图片/运行日志与大件证据留 output/story；候选不是第二正式正本，不被日常测试装配读取。

每个 Case 交来源索引、语义差异说明及实际需要的 Story/Review、整体设计/技术附件和 CU Spec/Plan/契约。文档数量随真实设计，不为“七份”硬补 CU；缺原生能力的对象标待验证。原件不改，新增人签只取真实业务权威。

## 修订次序

1. 核 G01–G09 的原话与工程关系，逐项区分已定、冲突与未知；从原始输入纠正，不能以历史稿多数相同当依据。
2. 修决定、状态/数据与实际接入关系，再同步蓝图、人读、验收及施工。展示掩码不能代业务身份；超时不等于远端失败；缓存清除不改变云关系；入口/路由必须可达。
3. 形成待决与具备真实定案输入两种可评情景。没有授权就保留待决，不造人签让正例通过。人仅审效果并不代表批准 Case 全部业务建议。
4. 整体通读，核每份产物的读者问题；同一事实跨件不矛盾，图中关系有据，详细技术信息可回查而不倾倒入业务正文。

独立审查取得同版本原件、候选和本步判据，自行给内容结论。宿主任务按实际能力执行；涉及模型调用须授权，本轮文件工作不启动。用户审定具体修订稿与语义差异，而非仅审目录或字数。

## 交回与推进

给 G01–G09 及新增实际缺口的来源、修改位置、保持项和剩余决定，不逐条复制所有材料造新数据库。评审核内容；现有结构/引用/编号/渲染能力用于机械核验，不能自证语义。

产品开工前附差距→现有承担者→必要改动→退出项及预算，当前已解决项只核保持。缺来源、人签或原生接口时按责任保留缺口；维护域其他内容继续，不将候选切成 test/golden 正本。
