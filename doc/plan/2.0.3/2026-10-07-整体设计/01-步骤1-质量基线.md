# P1 两 Case 的有据质量基线

需求：[R1](../../../spec/2.0.3/01-两Case金样与质量基线/需求.md)及其 G01–G09 修订合同。本步不改生产机制或正式金样，先交可供人评估的正确候选。

## 输入与产出

读取 Case 当前原始材料、历史候选、真实用户问题/选项/回复、目标工程与知识。采用版本与 tree ID 固定见规格 R1 §2.1，首先记录实际文件摘要和原始人签来源，旧 factbase 仅为定位线索。候选放本计划 `实施反馈/金样候选/<case>/`，原始图片/运行日志与大件证据留 output/story；候选不是第二正式正本，不被日常测试装配读取。

候选目录固定为 `auto-topup/initial`、`auto-topup/update`、`car-key-sharing/reviewable`、`car-key-sharing/plan-ready`、`car-key-sharing/update`，分别按规格 R1 §2.1 的集合和终点交付。每份候选带来源索引与语义差异说明，Story/Review/设计附件位于 AR，蓝图/CU 按原生目录保存。文档数量随真实设计，不为“七份”硬补 CU；缺原生能力的对象标待验证。原件不改，新增人签只取真实业务权威。

## 修订次序

1. 核 G01–G09 的原话与工程关系，逐项区分已定、冲突与未知；从原始输入纠正，不能以历史稿多数相同当依据。
2. 修决定、状态/数据与实际接入关系，再同步蓝图、人读、验收及施工。展示掩码不能代业务身份；超时不等于远端失败；缓存清除不改变云关系；入口/路由必须可达。
3. 形成待决与具备真实定案输入两种可评情景。没有授权就保留待决，不造人签让正例通过。人仅审效果并不代表批准 Case 全部业务建议。
4. 整体通读，核每份产物的读者问题；同一事实跨件不矛盾，图中关系有据，详细技术信息可回查而不倾倒入业务正文。

独立审查取得同版本原件、候选和本步判据，自行给内容结论。宿主任务按实际能力执行；涉及模型调用须授权，本轮文件工作不启动。用户审定具体修订稿与语义差异，而非仅审目录或字数。

## 交回与推进

给 G01–G09 及新增实际缺口的来源、修改位置、保持项和剩余决定，不逐条复制所有材料造新数据库。评审核内容；现有结构/引用/编号/渲染能力用于机械核验，不能自证语义。

交回列差距→现有承担者→本计划 P2/P3 对应动作→退出项，预算按总览；没有新差距不新加产品改动。缺来源、人签或原生接口时按责任保留缺口；维护域其他内容继续，不将候选切成 test/golden 正本。

## 正本及装配的确定落点

未来正式正本按 `test/golden/<case>/<情景>/AR/{story,review,design-review}.md` 组织，必要施工 Markdown 放该情景的原生蓝图/CU 目录；`test/fixtures/golden/<case>/<情景>/` 保存配套原始输入、知识/工程定位与原生设计夹具，不保存第二份可编辑效果正文。候选阶段不创建这些正式文件。

生产验证复用 golden_workspace/golden_design，P4 将其从单一 AR90004 装配改为显式 case＋情景选择，仍走真实 bind/complete/设计/成文入口，不能绕生产 gate。缺必需来源或真实确认时停止该情景，不补假批准。未决样例与可施工样例的完成期待分别写入对应现有测试，不统一断言所有候选必须 Plan PASS。
