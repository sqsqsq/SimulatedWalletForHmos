## 1. 业务统计设计怎样形成

Spec 的思考对象是指标所观察的业务过程；Plan 的思考对象是每个业务结果怎样被代码产生并报告。知识告诉模型项目规则，两阶段作者要求告诉模型此时做什么。

### Spec / Story

修改 hooks/spec/author.md 中现有第4步和 templates/spec-sections.md 的 §9.4 指引，保留一个指标一个 H4 的已定组织形式。每个指标先用短段说明观察什么、对应哪个流程、哪些行为属于观察范围、与材料中的业务目标有什么关系，再列业务步骤/子点、实际结果、本端何时得知、已有覆盖与新增。表不是独立清单，须能沿流程解释为什么这些点足以支撑观察。

多指标共用同一步骤时说明复用同一事件事实，不把同一执行重复采集；不同流程同名步骤要带流程限定。指标关系是统计目的的关系，不代替业务执行身份。后台口径未定义时说明需要的数据，不自行决定成功率分母。

以中性的“资料提交”说明写法：关注提交完成率，过程含资料校验、提交、结果获取。校验结果是通过、条件不满足或校验失败；提交被受理不一定表示处理成功，最终结果从回调或查询取得。是否需要独立运营采集由需求和项目知识判断。示例不提供固定 SDK、编号或适用于所有项目的必报点。

Story 继续由 Spec §9.4 投影到现有附录技术约定，正文按业务主线解释必要目的。源 Spec 写出业务语义后，原投影负责保留它与指标的关系。

### Plan

修改 hooks/plan/author.md、author.mjs 的 QUESTIONS 与 templates/plan-sections.md 中现有埋点小节，保留“服务层接口定义”章下单处设计。任务包先给上游指标与全部点位，再要求作者执行：查真实接口与知识 → 为每点枚举适用业务结果 → 确认值的来源 → 决定调用位置与时机 → 形成契约和验证。

沿用现有表头可识别的“统计点”“责任方法”，每点允许多行结果；新增叙述或列按信息需要组织，不靠铺满大表。共同身份/公共维度可在同节先定义，再让结果行引用，避免重复。

每个实际结果能追到：接口.方法及分支或回调；结果取得依据；事件身份及必要字段的实际值或具体候选；内外部结果与参数来源；同次尝试的边界；重复回调、重试和取消后的处理；有耗时要求时的起止；预期原始事件。字段取舍来自知识，通用提示不列封闭的 SDK 字段清单。

“待登记”只表示值已经设计、尚未写入常量文件；“缺项目分配依据”列出精确缺口及影响，不能把整个点位留作编码后再定。若关键映射不能完成，相关设计不具备交付条件。建设新封装属于设计动作，给接口与责任，不伪称已有实现。

contracts 仍用已有 data_models 字段、interfaces 方法、files 和 must 结构：方法落实报告义务，参数或常量的类型/含义在实体说明中引用本节唯一取值表；文件登记承载未来实现位置。已选交互模式需要的用户动作/业务状态落到 use-cases，照模式与 Framework 现行合同写。

写入 Plan author.md，替换原埋点段及模板中“缺哪一段”的笼统待登记说明：

> 读取 Spec 已定的指标、点位与业务结果。对每个结果，先定位能够确定它的接口返回、回调或用户动作，再在该责任方法中决定上报时机。查项目知识与已有定义，形成身份、结果及必要参数的具体取值或取值表达式，并说明来源。共同定义集中写在本节，结果行引用定义。结合一次实际执行说明去重、重试、取消和耗时边界。将方法、参数模型、返回类型与需要实现的文件写入契约，再列每种适用结果对应的原始事件验证。给定规则能产生具体候选时，本阶段给出候选；尚缺依据时点明缺失项与受影响的设计，提交相应裁决。

作者完成一行后能回答“实现者应在哪个分支、取哪些值、调用什么、看到怎样的事件”，再处理下一结果。公共封装的复用不代替业务方法承担调用责任。

### 贯穿示例：资料提交的业务语义与实现

以下是独立中性示意。假设该目标仓已有 SubmitService.submit 返回 accepted/rejected、抛出 TransportError；Reporter.emit 支持事件名、流程、节点、结果和自定义字段。协议规定流程申请号由需求设计提出，结果使用 accepted/rejected/transport_error。示例的 API、值与路径只在这个假设目标中成立，交付指令教模型从实际输入取得相应事实。

Spec §9.4 的 H4“提交成功率（资料提交流程）”正文：用户通过资料校验后发起一次提交，观察本次提交是否被服务受理；这里的成功仅表示受理，不代表后续审核通过。输入校验用于定位未能发起提交的原因，不当作提交失败；用户发起前退出没有产生一次提交。运营采集没有明确需求，本次不新增独立运营点位。

| 统计点 | 实际业务结果 | 本端获知时机 | 覆盖与关系 |
|---|---|---|---|
| 资料提交/校验 | 通过、资料不完整 | 校验完成 | 既有页面点击记录不能表达校验结果；本次补充 |
| 资料提交/请求 | 已受理、业务拒绝、通信失败 | 提交响应或请求失败 | 三者都属于已发起提交的结果；需要区分 |

Story 对同一内容的表达留在现有附录；业务读者能看懂为何记录校验与请求结果，以及“已受理”的边界。

Plan 在既有埋点小节定义本次新增候选：事件 form_submit，流程 application，节点 validate/request。字段 attemptId 来自本次方法执行创建的尝试标识；业务幂等键保持独立。示例协议允许这些候选名称，编码前登记并核同语义/冲突。

| 统计点 | 业务结果与协议值 | 责任方法 | 确定结果与发送时机 | 参数来源与缺席 | 同次边界及验证 |
|---|---|---|---|---|---|
| 资料提交/校验 | 通过→valid；资料不完整→invalid | SubmitFlow.validate | 本地校验完成后记录一次 | node=validate；字段名集合只含协议允许的非敏感类别 | 每次校验调用一条；不报原始用户输入 |
| 资料提交/请求 | 已受理→accepted | SubmitFlow.submit | Service 返回 accepted 后发事件，再推进页面状态 | node=request；requestId 取响应；attemptId 取本次上下文 | 同次执行只有一个终态；预期一条 accepted |
| 资料提交/请求 | 业务拒绝→rejected | SubmitFlow.submit | Service 返回 rejected 分支 | reasonCode 取拒绝响应；不带 requestId（本例拒绝响应无此字段） | 预期一条 rejected，原因码来自响应 |
| 资料提交/请求 | 通信失败→transport_error | SubmitFlow.submit | 捕获已定义 TransportError 时 | errorCode 取错误对象；没有则缺席 | 预期一条 transport_error；重试创建新 attemptId |

本例请求是单次 Promise 返回，既有控制流即可确保只进入一个终态，不额外实现全局去重器。若真实接口采用重复回调，则在对应执行上下文使用一次结算状态保护。页面退出后已发送请求仍按其结果结算，本例接口没有主动取消契约，因此不虚构取消请求的能力。

契约承接示意（字段形状沿当前 contracts，具体类型按目标画像）：

```yaml
data_models:
  - name: SubmitResult
    description: 受理结果；accepted 与 rejected 两种状态
    fields:
      - {name: status, type: string, required: true}
      - {name: requestId, type: string, required: false, description: accepted 时提供}
      - {name: reasonCode, type: string, required: false, description: rejected 时提供}
  - name: SubmitAttempt
    fields:
      - {name: attemptId, type: string, required: true}
interfaces:
  - name: SubmitFlow
    methods:
      - name: submit
        return: Promise<SubmitResult>
        description: 调用已有 SubmitService；各结果按 Plan 埋点本节定义发送，随后更新交互状态
```

这是展示交接的片段；实际方案还要按真实接口写输入参数、异常类型及文件清单。采用页面交互模式时，把“用户点击提交→调用 SubmitFlow.submit→显示受理/拒绝/通信失败状态”写入 use-cases 的 user_actions.calls、user_sequence 与 state_model，不另创结果模型。类型已在目标仓存在时引用实际定义，新增时在本次契约给出完整字段。

示例让实施者看清交接的完整链条；消费模板保留方法与形状，目标协议值来自当前需求与知识。

模板示例同步上述尝试边界：每次实际执行用尝试上下文控制一次结算，业务幂等键独立负责服务端避免重复创建；重试形成新尝试。取消示例明确发生在发起前，已发请求按实际取消契约或响应结算。原模板的“同一幂等键只记一次”“取消后不再发成功或失败”由这些明确条件替换。

### 统计点多行的确定性交接

现行 pre_verifier.statPointTable 用 Map<pointKey,row>，同点后一个结果行覆盖前一个。将其改为 Map<pointKey,row[]>，渲染时完整显示该点全部 Plan 行。用 consumedKeys 集合标识已匹配键，所有 Spec 指标遍历完再显示未匹配 Plan 点；匹配时保持 map 原内容，确保多个指标共用同一统计点时均可看到同一组实现行。

stat-points.specStatPoints 按表头“统计点”定位该列，仅收该类表；其他表保持在 text 全文中供模型阅读。groups 的 title/points/rows 保留现有接口，point 顺序来自原表。若统计点列不在第一列，标准化 rows 为统计点在首列、其余单元保持原相对顺序，以维持现有消费者约定。planStatRows 保留每一行及 cells，不按名字去重。

沿现有 /story 适用边界判断输出义务：走 /story 且要求 §9.4 时，Spec 缺少 §9.4、存在但没有指标点表、明确不涉及是三个事实。直接 Spec 的原有范围没有要求该扩展小节时，缺席只报告“本阶段未提供统计设计”，按已有阶段要求继续，不扩大强制范围。plan 作者和审查分别提示补上游、补齐结构、核不适用依据；现行“没有点就不适用”的分支改为如实缺失提示。多指标是否真共用一点、结果是否齐全仍由模型按正文判断。

### 分配规则的闭合方法

现文“各特性文件顺序下一个编号”不能保证相同模板跨特性唯一。身份和内码的命名空间在 reporting 的登记一节分别说清：身份按模板→流程→步骤分配；内码按项目业务模块→模块内流程→节点→子节点→具体结果分配，两种流程段长度不同，不做字符串机械截取。

采用人工维护的项目登记约定，不新增分配服务：先扫描真实模板/常量及调用，按业务语义复用已有值；新值从对应父范围的未用编号提出具体候选。同一模板跨特性先核全部已有定义；首用父范围尚无登记时，Plan 同时列父范围与子项的具体候选及依据，由该项目现有设计评审确认，不把候选称作既有分配。若真实项目有外部统一分配，使用其结果；拿不到时列精确待决，不自行占号。

Demo 无外部分配事实时，将上述局部设计约定标为本仓拟定规范，不冒充现有代码事实；首次候选按升序可用号提出，从 01 / 001 开始，00 保留用于未细分节点；项目已有定义优先。保留已定结果段成功00、取消10；失败使用其余未用号，避免“01起”覆盖10。编码登记前重新核冲突，有冲突回 Plan 调整同一设计，不自动换号。候选/确认状态在正常设计材料表示，不建全局分配脚本或锁服务。

模型取到足够项目依据才可以设计具体值；本设计给方法和 Demo 新规范，不替任一业务提前分配实际编号。

## 3. 决策和材料链

R04：现行 decisions.json 的 status/review_mode 保留。spec/author.mjs 的 decisionSection 从只接收章节合同，改为接收 projectRoot、feature 和 contract；用 featureRoot 找到 AR/story-src/decisions.json，复用 core/story/review.mjs 的 decisionList 读取顶层数组或 decisions 数组。原 DECISION_FIELDS 继续负责字段说明。

任务包在字段说明后原样列每项 id、status、title、decider、clarification；按 open/settled 分组，完整保留澄清正文中的依据和选项。脚本没有结构化的“影响段落”数据，不从自然语言推断。作者依据这些原文，将影响写回正常功能、流程和验收处：确定的共同要求直接写，依赖裁决的差异写条件及关联的议题编号。关联属于业务写作，使用现有决策和正文，不新增 impacts JSON。

决策文件不存在时标“本次尚无登记”，作者照正常流程识别新议题；存在而 JSON 损坏或 decisionList 返回 null 时，报具体文件与格式问题，不能当成零议题。作者任务取到后新增/修改的议题，以成文时当前文件为准回查一次。

reader-review-task.mjs 的现有决策检查任务要求审查者读取当前 decisions.json 与 Spec、Story、acceptance，逐个 open 事项检查受影响的行为。审查依据是选项的实际后果，而非正文是否出现“待定”二字。具体发现进入已有读者审查判据；不增加一份平行报告。

例如“超时后是否自动重试”仍 open，共同要求为保留当前提交信息、告知结果尚未确定；自动重试的触发次数与相应验收暂不写成确定承诺。用户选择后，作者沿既有 update 同步行为、异常和验收。settled 依据须指向真实表态，选择改变时仍由现行更新流程处理。

决策字段完整性继续由原脚本检查；“正文是否偷选”由 reviewer 将 open 事项与功能、流程、异常和验收相对照。无需给每条正文建立新状态或用关键词判断“待定”是否足够。

## 4. Plan 契约和审查

改 hooks/shared/pre_verifier.mjs 现有任务片段、rules/spec-rules.overlay.yaml 和 plan-rules.overlay.yaml 的相关语义条目，替换原泛化要求，不追加平行清单：

- Spec：源材料与已定决定是否支持关键结论，open 选择是否进入无条件验收；业务统计语义是否完整。
- Plan：按结果走通接口输入/输出、状态与调用；返回类型在本次契约定义或可定位的现有类型中存在；选中模式的必要投影实际存在。
- 上报：并列上游结果和本阶段映射，核每个已定结果是否已有责任与参数；候选未登记与根本没值分别判。
- 把缺失影响交给实际规则判：下游需要重新决定接口结构、核心业务行为或必要值的，相关条目 FAIL；措辞和局部优化才可 advisory/WARN。不因文字概述够长而放行。

复用 knowledge.mjs 与 stat-points 的现有数据。Spec/Plan 同名点对齐仍按稳定业务名，若不同流程同名有歧义，作者补流程限定；脚本只报告歧义，不猜语义。pre_verifier 应给已有知识全文入口及所需章节条件，不把所有知识无差别内联。一般返回类型检查的 Framework 缺陷交上游，Extension 只落实自身知识义务的作者和审查要求。

审查报告仍走现行真实 verifier 与回执；历史报告沿用按宿主协议如实记录，不手工篡改摘要或强造二次报告。维护验收读最终产物与变更，不以 closed 替代实际复核。
