# B02 CU按原生阶段取得并落实自身设计

> 本步已实施交回；当前修订以参考01及[C00](../03-批次-业务送审与变更交付/00-前批集中返修.md)为准。知识身份统一entries、pending按实体归属、实际实现使用N1入口；update为无run的Feature聚合，无request消费者时不占位接入。原交回保留。


本步以B01完整新合同和前批同根身份为输入；B01的所有旧字段直接消费者必须已切换。本页深化各阶段正常职责，不接受半迁移兼容层。当前仍只是方案，实施与真实运行另依总方案授权。

## 1. 已定接口和准备时机

新main的`framework/harness/scripts/prepare-blueprint-design.ts`提供`--feature <canonical CU feature id> --phase spec|plan`，调用`blueprint-skill-projection.ts`的`materializeBlueprintSkillInputs`。独立Spec按`--phase spec`只准备本阶段acceptance；独立Plan按`--phase plan`只准备contracts及适用use-cases，保同一新需求内原生允许的不冲突阶段补充，不用Plan覆盖Spec或反向补造共同设计。

原生runtime已准备的输入直接消费，不再次调用准备器；只有独立阶段入口缺少本阶段准备时才沿该命令。是否已准备依原生身份和当前投影事实，不靠文件名存在猜测，也不建Extension准备状态机。阶段冲突回实际Spec/Plan或蓝图责任，不能静默覆盖已有合法产物。

CU职责按`design_refs`选真实设计对象及关联公共对象，再使用原生typed投影。`must={text,source_ref,verify}`、`pattern_roles={pattern_ref,role}`、原生acceptance/calls等结构沿统一解析保持类型与有序调用；不从旧decision清单、Story段落或预测文件推导另一套设计。共同设计改变先回蓝图并处理原生当前性，不能只改CU稿后称一致。

## 2. 正常各阶段行为

Spec读已准备acceptance和本单位对象，写本单位行为、边界、异常、可观察结果与验证责任。知识任务提供相关原文、facts判断与承担对象，Spec解释技术约定、规约和模式作用，不搬整份蓝图、不要求全量重判。已由原生满足的合法Spec可复用；机器接受/readiness不是新增人工审批。

Plan读本阶段contracts/use-cases和有效Spec，落实体、方法、存储、依赖调用、选中角色、必要配置/统计点及验证责任。已有能力与拟建/模拟明确区分，真实缺口不得造外部接口。义务随真实承担实体落实；普通文件/模块预测调整按实际义务、公共契约、原授权和架构判断，不因预测未列就强求人批，也不取消用户硬边界。

Coding读Plan实体及相关知识下篇，形成真实调用和义务实现；Review核实际diff与来源、公共契约、模式角色和硬边界；UT/testing从验收条件与`verify`承担场景/设备责任。尚未获准Coding或设备执行时，只核相应消费者可承接与离线合同，不自动推进阶段、不把未跑报告成通过。

## 3. 具体动作与退场

在B01已改合同基础上深化`hooks/shared/knowledge-task.mjs`的Feature各动作输入和作者/reviewer分工，`framework-access.mjs`的原生Feature/冻结输入访问及`skills/story/scripts/core/story/design-source.mjs`的CU来源取得。使用上游原生prepare及typed解析导出，不复制归一化、calls解析、投影器或新状态登记。

同步`hooks/spec`、`hooks/plan`作者页和post_check、`hooks/coding`、`hooks/review`、`hooks/ut`、`hooks/testing`及`hooks/shared/pre_verifier.mjs`阶段说明和缺口归属，校验各阶段只要求本阶段合法输入。核`story-knowledge`、宿主扩展规则和阶段入口的实际调用；独立入口补phase参数，runtime链不加重复prepare。文件级预测仅作定位和规划信息的消费假设同步退出。

B01已删除的旧知识decision桥接不得重引入。退出Extension隐含“每阶段全量准备”“所有阶段重判全知识”“文件清单就是授权”的要求与对应测试；保原生身份、来源、冻结范围、真实业务限制、实体义务与有效Spec增量。无legacy调用时只登记已核无调用，不虚构删除工作。

## 4. 验证预期与交回

复用`test_cu_knowledge_chain.py`、`test_knowledge_task.py`、`test_blueprint_case_closure.py`和阶段相关离线回归，fixture从真实上游投影生产路径进入。Spec-only不要求尚未准备的Plan contracts；Plan-only不重写合法acceptance；runtime已准备时不得发生第二次prepare写入；错阶段/坏身份由原生报明，不静默降级。

合法calls结构及顺序完整投影；共享对象相关CU均承接，专属对象不串入；真实实体移动仍在授权和契约内时可通过，实际越业务/架构硬边界应被原责任发现；未落实实体义务、漏模式角色或验收失去可观察条件不能因typed合法就通过。独审核Spec/Plan各自内容足够且不重复决定，后续代码义务证明保留为获准阶段取证。

交回包含独立Spec、独立Plan、runtime三条入口的实际准备/消费证据，真实typed对象到实体/验收的链、预测调整与真越界对照、未跑后续范围、预算及本步提交。前提齐备连续B03。拟议G360/X480，见[预算](../参考/03-预算与计量.md)；不得重算B01新增或以本步深化掩盖上步断链。

原生prepare的合法absent可能保留已有文件并返回空写集，不能把未写文件直接判为准备失败；是否缺本阶段必需输入按原生解析/required_outputs处理，不造占位件。
