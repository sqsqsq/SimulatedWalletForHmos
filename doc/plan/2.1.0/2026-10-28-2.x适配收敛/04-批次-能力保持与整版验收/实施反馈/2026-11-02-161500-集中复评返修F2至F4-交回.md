## 2. F4 同进程：实测与停下的理由

复评说的没错，`createContext`、`cmdBuild`、`discloseInStory`、`storyCheck`、`prepareReview`、`reviewResult` 都已导出。D06 交回说它们没导出，这个说法是错的，在此更正。

按复评的方向，我在同一私有根上，每个动作新建 ctx，直接调已导出的函数，实测如下。探针在 `output/scratch/2.1.0-F/`，不提交：

| 方式 | 每个动作用时 |
|---|---|
| CLI `review prepare`（含投影、编号、渲染、检查） | 2.8—2.9 秒 |
| CLI `review check` | 2.6 秒 |
| 单独 node 进程、新 ctx 调 `reviewResult` / `prepareReview` | 2.6 秒 |
| 同一个 node 进程里第 2、3 个动作（每个动作新 ctx） | 8—11 毫秒 |

可见开销集中在每个进程第一次读原生蓝图与采用来源（P2 的进程内复用只对同一进程后面的动作生效），编排本身几乎不花时间。所以每个动作各开一个进程、调导出函数，几乎省不下时间。要省，就要让一个进程连续执行多个动作。这个类里的动作之间穿插着 Python 侧的写入（夹具审查者按 `prepared.json` 写回复、改 Story），只有两种做法：

1. 测试侧加一个常驻 node 进程，由测试逐条发动作（就是 runner）；
2. 产品加同进程多动作入口。

复评 F4 写明「停止新增未证实的通用缓存、runner 或多动作产品入口」，两条都不在授权里，所以我没做。这个类单跑 35 秒（6 条在同一个 worker 上串行）。要不要按上面的实测授权其中一种，由设计者定。
