## 3. R2—R4：知识职责一次接通

### 3.1 模式和条目身份

`patternRolesFromContracts`的`patternRef`为当前实际返回身份；review门禁按它核已选模式及复核表，coding报错也用同一字段。coding/ut/testing作者输入改为实际`must.source_ref`，不再指导模型写`must.rule`。保内部派生的显示编号`rule`供原表定位，但不能反向当新产物字段。由契约实体→角色提取→review门禁验证缺模式行会被发现，真实模式协作是否充分仍由语义审查承担。

### 3.2 pending的归属与效力

继续用`items[].target_refs`，不新增字段：

- 已知受影响实体时，同一pending同时引用真实decision/gap与实体地址。CU按**实体责任范围**接收，decision/gap仅说明由谁解决；不因另一个CU引用同一决定就串入不属于它的实体责任。
- 只有decision/gap地址时，表示实体归属尚未确定。`unitContext.common`将其列为“归属待核的公共知识缺口”，作者/独审实际取得原因及原生引用，不能静默丢掉。已知属于其他CU的pending不广播。
- 平铺新Feature没有CU划分，全部属于当前Feature。`unitDuties`仍只产生applied/selected的施工义务，pending不变成已生效must，不据“有引用”推定获得豁免。

蓝图作者页、`unitContext/unitLines`、pre_verifier和宿主扩展说明同步；真实地址校验保持。无需每个pending都加人工批准：已有决定按其效力使用，确实影响当前动作的未决沿原生责任处理，无关工作继续。

红线以真实知识正文与授权为准。登记豁免不等于可豁免，独审核适用边界、有效权限、理由和补偿；原规约不允许的，不能以pending/decision洗成已批准。保持语义责任，不恢复通用“所有知识必须先填决定账本”的机械规则。

### 3.3 蓝图和非CU新Feature共用知识输入身份

统一形态改为`knowledge_context = {digest, entries:[{source_ref,kind,form,sha256}]}`。只将既有清单键`files`改为`entries`，排序/摘要计算与每项字段保持；不新增sidecar、第二摘要、revision或readiness。

载体：蓝图仍为`discovery.inputs.knowledge_context`；非CU新Feature为原生`contracts.knowledge_context`。CU继续从蓝图读取，不在每个CU重复抄清单。两种载体都走`knowledgeContext/contextProblems/checkFacts`，撤下非CU的`context:false`。空激活清单保持现行显式零项行为；有知识但无当前身份、原文变化或清单增删均给实际责任位置及影响，不补默认值冒充已读。

静态依据为固定N1的contracts schema `additionalProperties:true`与`contract-reference-closure.ts`未知字段扫描：`files`命中文件引用键名规则，`entries/source_ref`不命中；原生投影保合法未知扩展。实际原生解析/冻结消费者在实施定向验证中确认，不声称已经运行通过。

生产者为现有知识任务：蓝图设计任务给蓝图载体；独立非CU的设计/Plan输入给契约载体，作者沿当前阶段有权写的设计产物保存。下游coding/review只消费，不自动改写旧设计身份；发现知识变化回设计责任方。非CU尚无契约的独立Spec可读取原文并说明后续Plan承接，不能为它强造提前的Plan契约；一旦有承载判断的契约，就须核其身份。真正无可用判断的下游不得以新摘要替旧决定自动通过。

同步schema、任务文字、错误位置、Feature加载、门禁、独审、Story引用及已有fixture。本版仅新需求初始化，不保files/entries双读兼容；当前开发夹具按新生产者更新，旧历史运行数据不迁移。`digest`仍是唯一当前性摘要，不给每条fact追加一份知识全集。

## 4. R5：使用原生实际实现定位，不把预测当授权

固定N1 `diff-scope.ts::implementationFiles(projectRoot,feature,contracts,runId?)`已经合并原契约预测与有效基线实际源码变更，按实现域和路径规则取现存文件；`implementationChangeContext`提供删除/改名的基线原文及变更事实。**直接复用这两个原生能力**，不重新写Git枚举、全仓扫描或作者文件台账。预测不是写授权，依据N1 contracts.schema和coding Skill，不能读demo旧版说明得出相反结论。

coding post_check的实体存在、知识探针、角色调用观察使用同一批实际实现文件；角色地址与义务来源继续从原生契约取。当前阶段已有run上下文时，使用该阶段已验证的feature与原生harness注入的`MAISON_GOAL_RUN_ID`向上述原生helper传runId（已有显式阶段上下文优先）；它只用于当前被检查的Feature，不复用到update遍历的其他CU；独立Feature按原生无run基线读取，不能挑最近run。删除/改名的旧文本交语义review，不假装旧路径仍存在。

`implementationFiles`在基线不可得时可能只保可读预测引用。因此同一真实输入的`resolveEffectiveDiffBaseline`结果也须可见：能核的显式实体继续核；依赖完整实际diff的缺实体/无调用结论若缺基线，应报告该组未执行/证据缺口，不能仅凭旧预测未找到就报未实现，也不能冒充全组通过。真正读取得到的违规按既有责任处理，原生diff/身份检查仍承担其结果。

作者页、Plan门禁注释与coding报错一起取消“授权文件清单”。实际需求限制、公共契约、架构和只读所有权继续由原生负责，普通预测位置变化不增加人批。验证在现有coding/review离线链内做“保持实体/调用、从预测A改到实际B”和“实际义务缺失”的对照；不启动模型Coding、设备或全仓探针。

## 5. R6及B03答疑：聚合查询与运行接续分责

当前`update._unit_facts`遍历同一蓝图所有CU，是Feature级只读聚合，不是某个run的执行/接续。保持现有`currentDisposition`无run查询，**不新增未被消费的run参数或PreparedRequest接口**。`MAISON_GOAL_RUN_ID`是裸ID，不含所属Feature，不能把环境ID套给兄弟CU。

完整attended运行由原生harness校验feature/run/attempt/owner后自行加载scope/workflow与运行事实，Extension不另建运行完成裁决。若未来出现明确的run专项消费者，必须从该调用的feature+runId取得原生绑定，再沿原生manifest/effective scope/workflow读取；当前没有这个消费者，不占位实现、不找最近run。上轮评审“运行组合待核”据此细化为：本步验证聚合职责不冒充运行裁决，真实宿主续行效果留获准CLI。

单位输出继续携带原生`disposition`：completion_eligible、release_ready、completion_blocking、release_blocking、disclosed及owner/phase/action/detail；不用新增持久状态。

- `_current`保明确阶段/owner匹配；单位级`phase='*'`不硬塞某个阶段，也不抹各阶段历史closed。
- `stale_units/stale_text`及status/close直接消费者同时查看单位disposition，不能只按阶段current决定是否披露。无阶段过期但单位完成受阻、处置unknown、仅发布阻断或有披露事项，都有明确输出；阶段列表与三类问题分列。
- 只有确有阶段问题才建议从最早受影响阶段续行；单位问题按原生owner/action处理，不编造`from`。仅发布阻断不改普通完成，披露不变成缺陷；update记录/收口本身不因施工未完成而禁止，既有真实终点条件保持。

使用小型直接消费例核四种返回：阶段新鲜＋单位完成阻断、阶段新鲜＋仅发布阻断、普通完成＋披露、unknown。另保一个真实N1读取→update状态链；不为每种返回都重建完整工程或伪造模型报告。
