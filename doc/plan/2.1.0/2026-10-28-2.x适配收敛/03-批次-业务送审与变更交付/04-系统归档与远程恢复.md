# 步骤04：系统归档与远程恢复

本步将当前合格业务稿交到真实需求系统，保逐件冲突检查、上传读回、部分成功续接与远程正文恢复。归档是业务交付，不是Extension版本发布。当前仅方案，未调用远端。

## 1. 输入与最小交付集合

必读[批次方案](00-批次方案.md)、[共享接口](../参考/01-目标接口与状态.md)、步骤01—03及主Spec R1/R6—R10、AC6—AC11。输入为系统需求身份、已有送审/归档授权、当前Story/Review登记及审查事实、当前原生蓝图人读稿、最近fetch回执、逐件发布基线、远端当前内容和必要备份。本地需求不进入远端，不为本地交付生成上传准备状态。

最小业务交付为Story系统正文及Review附件。设计参考能力保持：需交设计参考时直接取当前原生蓝图人读稿，作为确定性交付附件，正文标识其设计参考用途；不让作者再维护一份不同设计。沿既有系统`design-review.md`附件接口提供此能力，附件内容、蓝图版本和摘要可回到原生源。该附件是否交付按D00§4具体入口：fetch回执delivery_requirements.design_reference表示目标对接要求，或已有请求由publish --with-design-reference承接；无两者则两件，不新增批准。不把“每单必有AR/design-review.md且再独审”作为业务资格。原生投影缺必要内容是上游/设计缺口，如实列影响，不手改副本伪造。

集合仅在本轮发布准备处形成一次，`flow/publish.py`与数据适配器消费同一份明确的交付项及本地/原生来源摘要；复用现有publish结果和fetched回执扩展字段，不新增通用交付状态平台。既有远端设计附件若本轮未更新，保其外部当前版并说明，不静默删除或伪称三件同版。fetch核外部已有附件不等于新增强制上传义务。

## 2. 逐件发布与状态顺序

1. `scripts/core/flow/publish.py`的`cmd_publish`先调用步骤02交付门，展示真实差异、未决、未审及未验证范围。`ITEMS`、`_baselines`、`_external`改为消费本轮明确交付集合；`publication_record`记录实际项、来源/设计引用、字节摘要和读回，不按固定三件存在推完成。原送审授权持续有效，不以进入归档新问一次批准。
2. `scripts/adapters/dirs.js`的`cloudBackupDir`及使用者切换`sources/backups/`；`archive.js`的`backupBody`把覆盖前真实系统正文保存到该根，原件/外部意见备份不可被更新流程覆盖。此前fetch取得的系统原正文也保真实来源身份，首次发布基线从来源索引/回执取，不依赖旧`AR/design.md`固定副本。
3. `archive.js`的`archiveOne`先逐件重读取远端：与预检回执不同则一件不写；当前远端已等于本地目标则标同版，只读回不再上传；与允许基线相等才写。远端由他人修改时展示差异交人决定合并或确认覆盖，授权只绑定本项当次外部/本地摘要；有效人答与外部意见保原文，不能拿普通送审授权代替覆盖他人意见。
4. 上传按正文→Review→本轮实际设计参考顺序，逐件成功后立即读回并记录摘要/时间。设计参考附件从当前原生投影生成的交付副本只在需要时准备，上传前核源未漂移，归档登记保引用。任一项失败停止后续，保已成功项；重新fetch、publish后远端等于目标的成功项跳过上传，仅补缺失/失败项。不得在重试时撤销真实成功或重复覆盖正文/制造重复备份。
5. `publish.py`的`readbacks`、`cmd_archived`按本轮实际集合逐件核当前目标、读回时间和摘要。远端上传成功但归档登记或下一步读取故障时，明确“远端已成功，登记/续接待处理”，修故障后补登记；不得要求从头上传。`flow/routing.py`、`state.py`和`usage.py`读取实际归档/业务结果，不用设计附件缺省、旧closed或自动未审伪造当前完成/发布资格。归档后Review人工区所有权与更新保护保持。

以上路径前缀为`extensions/skills/story/`。`scripts/adapters/fetch.js`、`story.js`命令入口、`flow/publish.py`的`RECEIPT`、`phases/design.md`、`phases/update.md`、SKILL归档/恢复说明和`reference/phase-closure.md`是直接消费者，须同步交付项、路径和重试语义，不能仅改archive实现。

## 3. 远程恢复

`scripts/adapters/restore.js`的`restoreOne`从`sources/backups/`取得实际归档前正文，按D00§4.2的fetch→restored --prepare→adapter restore→restored顺序，准备时展示目标/当前差异并复用现有覆盖决定；`archive.js`的`putBodyOnly`只写正文并读回，不动附件/本地业务稿/原生蓝图CU/有效人答，不产生空备份或重复备份。若远端自上次登记后有他人改动，沿同一冲突保护先取得当次覆盖决定，不因“恢复”跳过所有权。

`flow/publish.py`的`cmd_restored`更新外部正文真实基线，保两个附件各自实际版本与历史归档记录，并报告远端/本地差异；恢复没有回滚本地设计、审查或原生阶段。读回失败即恢复未确认，保原错误和实际已发生副作用；再次取材核现状后续接，不能把本地日志存在算远端成功。若远端本已是恢复目标，只读回核实而不重复写。没有真实归档前正文时明确不能恢复，不挑任意旧来源代替。

## 4. 退出、验证和批末交回

退出固定“三件缺任一即失败”的资格判断、固定本地设计副本必审/必存在、旧`.backups/cloud`新写入路径、旧`AR/design.md`首次基线读取及重复批准文字；本轮不迁旧在途或备份历史，历史原件继续保护。新承担者分别是明确交付集合、原生设计投影、同根来源备份和逐件摘要/回执。设计参考上传能力、真正外部冲突确认、逐件读回和局部恢复保持，不因本批简化删除安全责任。

后续实施在`test/tests/test_story_update.py`既有归档/恢复回归及`test_update_dispatch.py`核：本地单零远端；最小业务集合与实际需要设计附件两种合法交付；原生投影源漂移拒绝冒签；预检后远端改动一件不写；第二项失败后第一项保成功，重试不再上传；上传全成而登记故障只补登记；未审披露仍真实、已知FAIL不归档；Review人工意见冲突不覆盖；远程恢复只动正文并更新其真实基线。用实际适配器/回执入口构造独立期望，不预造“已归档”字段代替写入与读回。

独立语义检查系统读者是否取得完整业务Story、真实Review裁决与必要设计参考，未审/未验证/多版本状态能否正确理解。真实系统上传/恢复需另按TEST授权和正常DSH入口取得远端原件、回执及读回证据；替身仅证明确定性接口与恢复，不冒充真实系统接入，缺权限/宿主能力单列责任和取证动作。

预计G160/X220，按[共享预算](../参考/03-预算与计量.md)和AGENTS§5累计。完成本步后写增量交回、提交，交回同时汇总四步、实际交付组合、来源/对象身份、预算、旧路径退出、独立语义及真实行为未覆盖，集中送审后等待；不自动进入新批次、运行Coding、更新demo或发布。

原ITEMS固定三件及其readbacks/publication_record/archived/end_target消费者一起退到本次实际delivery集合；保未选旧附件及其已确认基线。restore单项准备与实际读回保在既有fetch回执，adapter不读core契约，核心登记只消费晚于准备且等于目标的真实结果。具体字段/错误/重试及源头接口唯一设计见D00§4，不再保本页原“只说按需但无判定入口”的空白。
