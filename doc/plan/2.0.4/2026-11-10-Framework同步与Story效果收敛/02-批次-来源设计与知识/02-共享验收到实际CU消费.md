## 2. 唯一新helper合同

在knowledge-application.mjs中定义（不新增模块、CLI或状态）：
```
knowledgeAcceptanceProblems({ knowledge, active, judged, acceptance }) -> string[]
```
- knowledge：调用方已取的activeKnowledge结果；active：调用方已有activation(projectRoot, knowledge)的Map；judged：该Feature/CU的featureKnowledge结果；acceptance：phaseArtifacts给出的当前原生规范值。
- 调用前四项必须已取得。缺源/知识加载失败由现调用方groups及原生issues/skipped处理；helper不补默认、不自己读YAML/文件、不调用activeKnowledge/activation或重判适用性。
- **核查纠正**：activation会readFileSync知识原件取摘要，原四参数projectRoot方案却写“helper不读文件”不成立。改为传现Map；Plan已生成active直接复用，Spec在现位置生成一次后传入，不增加第二次扫描。

算法固定：
1. `unitDuties(judged).applied`取得本单位适用条目；`knowledgeCriteria(acceptance)`解析criteria/boundaries的所有knowledge_refs，并先保全部既有形状/旧字段问题。
2. 每条applied若byRef无其完整source_ref，报告该单位、条目/来源及缺验收承接；不以裸编号合并不同文件。
3. 每条byRef以现knowledgeSource(active, ref)及entryOf(knowledge, ...)核激活；不在激活内报错，已激活但不在本单位applied集合报错，给关联AC ID及实际ref。
4. 汇总返回问题数组，不改输入/文件。行为是否真的落实由独审核，helper不做字串语义评分。

错误恢复文字随对象保持：CU共同验收缺项回蓝图承担对象，合法局部规格细化交Spec，Plan不另造验收求绿；非CU维护Feature按原Spec生产责任处理。不要把所有缺项统一提示为“在当前阶段写一条criteria”。

## 3. 两个实际消费者的接法

Spec post_check：保native输入问题、design问题、正文对齐/编号/宿主章/报告检查。原知识桥内联段替为helper调用；需要activation时在调用方取得一次。无acceptance且有适用义务仍按原why记skipped，不把[]当全阶段通过。去掉不再使用的entryOf/knowledgeSource/knowledgeCriteria导入，保实际其他用途。

Plan post_check：复用本来已有knowledge、active、judged；具体插入在现`const active`及`unitDuties`取值之后，向现reference组追加helper问题，组名改为“验收的知识归属与用例引用”。仅knowledge/judged/acceptance都取得时调用；缺知识沿现加载问题，缺acceptance且有applied时记对应skipped及inputs.why。保原位置的acceptanceRefProblems及linked_acceptance ID检查，不把helper放进“有useCases”或“有本地contracts”分支，否则Spec复用或暂缺用例时会漏核真实验收。must/pattern实体验证不动；不回填本地假文件，不新增完成字段。

knowledge-task蓝图作者动作先要求共同验收/义务/真实事件在质询前形成；质询检查它是否与真实来源一致，Story-only也不能把应有业务验收交给不会到的Spec。carriedDuties(spec)对CU改为复用实际已选条目与合法深化，非CU保原验收生产；共同取舍变更回owner。消息不带业务专名/阈值。

Plan作者/pre_verifier/reviewInputs沿当前完整binding和实际knowledgeTaskData读取，不新造inliner/cache/必审集合。统计沿designStatPoints→Plan表/责任方法/验收，Story沿appendix-readers/projectAppendix。相关空投影是需查设计的缺项，不自动“不涉及”。
