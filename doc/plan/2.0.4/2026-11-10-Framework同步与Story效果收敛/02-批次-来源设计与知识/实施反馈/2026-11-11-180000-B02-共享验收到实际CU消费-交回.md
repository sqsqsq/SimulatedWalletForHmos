## 完成

**唯一新 helper**：`extensions/hooks/shared/knowledge-application.mjs`

```
knowledgeAcceptanceProblems({ knowledge, active, judged, acceptance }) -> string[]
```

- 四项输入都由调用方取得：`knowledge` 来自 `activeKnowledge`，`active` 是调用方已有的 `activation` Map，`judged` 来自 `featureKnowledge`，`acceptance` 是 `phaseArtifacts` 给出的原生本阶段验收。helper 不读文件，不调用 `activation`/`activeKnowledge`，不重判适用性。
- 算法按方案：
  1. 用 `knowledgeCriteria(acceptance)` 取得旧字段与形状问题以及 `byRef`；
  2. `unitDuties(judged).applied` 里每一条不在 `byRef` 中的，报缺验收承接；
  3. `byRef` 的每个引用用 `knowledgeSource` 加 `entryOf` 核：不在激活规约里的报错，已激活但不是本单位承接的也报错，带关联 AC 编号；
  4. 返回问题数组，不改输入。
- 恢复提示按对象区分：
  - CU（`judged.scope` 非空）：「验收由蓝图承担对象给出的，交设计负责方在那个设计对象上补一条；蓝图没有验收投影、由 spec 产出的，在 acceptance.yaml 补一条 criteria；两种都在 knowledge_refs 列 <ref>，plan 不另造验收」。
  - 非 CU 维护 Feature：保持原来的「写一条 criteria，knowledge_refs 列 <ref>；下游 ut / testing 按它找要覆盖的场景」。
- 导入 `contracts.mjs::knowledgeCriteria`，没有循环依赖（`contracts.mjs` 只导入 `framework-access.mjs`）。

## 方案外决定

- **CU 的恢复提示写明两种去向**：方案写的是「CU 共同验收缺项回蓝图承担对象」。但现有用例 `ASpecWithoutAnAcceptanceProjectionWritesItsOwn` 说明，CU 的设计对象不带验收时，原生投影为 absent，由 spec 自己产出 `acceptance.yaml` 是合法的。helper 只拿四项输入，分辨不出验收来自蓝图还是本阶段产物，所以提示里把两种去向都写出来。职责没变，请设计者确认。
- **夹具补共同验收**：新的 Plan 检查拦下了 `chain.design` 夹具：它给 OBS-02 写了适用判断和 `must`，但承担对象上的验收没有用 `knowledge_refs` 承接（两个用例因此失败）。按「夹具是合法设计、不删义务」，在 `chain.design` 里给模块节点加一条承接 OBS-02 的 AC-002（`BRIDGED_CRITERION`，与 AC-001 同形），并加 `bridged` 开关供反向用例使用。`test_cu_knowledge_chain.py:832` 原本断言 CU 场景下的「写一条 criteria」，按新提示更新。
- 新增测试：
  - `ThePlanChecksTheSelectedAcceptanceWhenTheSpecIsReused`：蓝图带验收但不承接，本地没有 `acceptance.yaml`，`inputs.acceptance` 为 resolved，Plan 门禁在新组里点名缺承接与恢复去向。
  - `TheAcceptanceOwnershipIsCheckedPerReference`：真实工程的激活知识与判断，分别核非激活引用、别的施工单位的条目（`AC-4、AC-5` 两条全保留）、两条验收同承接一条不报，以及缺承接的提示；另做静态核：helper 函数体里没有文件读取或 `activation`、`activeKnowledge`、`readFeature`、`phaseArtifacts` 调用，`hooks/` 下调用方正好是 spec、plan 两个门禁。
