## 2. 交付选择到原生动作的确定映射

| 真实请求 | 本层动作 | 结果/边界 |
|---|---|---|
| 送审/暂不施工 | 按现业务交付门、系统合同登记/上传或本地交付 | 不生成CU/Spec文件求齐套，不从Case end_at追加阶段请求 |
| 完整设计交接 | 原生设计准备，当前未分解才接受候选；已有CU只readiness | 输出真实身份、可就绪项和问题，停在施工选择前 |
| 实现方案到Plan | 对ready且获准CU生成request，requested_phases为真实授权spec,plan | 依原生phase_chain/obligations执行或复用，结果仍按实际闭环 |
| 真实独立Spec/Plan | 沿现request填写实际阶段，保授权边界 | 原生若返回超权限工作，如实报本请求限制；不扩大授权，不把专项实验设为两例前置 |
| 完整实现 | 引用Framework当前完成协调器/正式入口，以真实请求接续 | 本步不新增受管初始化、运行器或Coding实跑；未支持/未验证的组合如实给边界，不编造支持 |

产品文案表达：已有请求直接使用，没有明确后续目标才沿现交付选择问一次；原生普通完成、业务送审和发布资格分开。不要新增“范围门先问终点”的固定步骤，也不再出现旧batch授权话术。

## 3. 请求与返回合同

1. 首次分解文件按原生`[{providerId, artifact}]`。design_refs只写CU实际承担目标及采用的必需决定，整批覆盖义务，依赖闭包交原生。调用`check:change-unit --accept-candidates <工程相对路径> --json`；成功后按原生命令处理候选清理，不重复接受；失败保候选不写canonical。
2. 已有CU用`--readiness --json`。accepted仅表示本次接受，inventory给完整feature_id/canonical_path，ready_ids才是可推进集合。身份不从业务名拼，不将accepted为空当失败；busy等原生可重试事实按其返回恢复。
3. 对获准ready_ids调用现`goal-mode-entry --prepare-scope --completion-target request --requested-results <真实结果> --requested-phases <实际阶段> --requirement-file <真实需求源>`。需要人读Plan/Spec时按原合同另列plan.md/spec.md；这来自业务要求，不从测试元数据推导。需求源取蓝图requirement来源文件去片段，不另存一份权威需求。
4. 按原生需要在冻结前`prepare-blueprint-design --phase P`，Spec只物化本阶段验收，Plan只备本阶段契约/用例；已合法内容保留，absent由该阶段作者产出，invalid/共同设计冲突回owner。已冻结/runtime已准备不再覆盖。
5. 作者→harness→真实verifier request→原件保存→receipt/check-receipt→原生当前事实→observer。NEXT控制恢复，主模型不手填closed/绑定/完工；依赖未满足不越过。

失败恢复：真实当前blocker按原生拒绝施工；已解决问题形成设计/决定并保历史，不写不存在的gap.status=resolved。不因报告是PASS忽略当前scope或输入过期；不以Spec输入存在当该阶段产物已交。非依赖故障不冻结全部独立工作。
