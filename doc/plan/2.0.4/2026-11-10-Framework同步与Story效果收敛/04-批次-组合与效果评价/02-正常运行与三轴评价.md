# 步骤D02：正常运行与三轴评价

完整结果：在D01固定组合上取得正常业务全过程及独立语义证据，评价结果、性能、Knowledge三轴和原能力保持。产品G0/X0。前置为D01成立、受影响实现问题已复评、用户明确授权本轮两例CLI；本方案和当前文档修订不构成启动许可。

## 1. 执行者与评审者输入

实跑宿主读D01候选/测试计划、TEST§0.3/§2—§4及Case交互条件；消费模型只取得业务请求、真实材料、人答和已装机制/知识。金样、维护方案、失败答案和checker源码不投送。维护设计者从原件、最终产物和实际会话做效果评审；不以被测系统PASS替代判断。

## 2. 获准后的实际动作

仓根用现入口，不另写驱动、不直接调用run_case.py。示例suite-id须替为本轮真实唯一身份，不覆盖历史：
```
python test/scripts/run_multi_case.py start auto-topup car-key-sharing --jobs 2 --suite-id <本轮suite-id> --authorize-non-sandbox
python test/scripts/run_multi_case.py poll --suite-id <本轮suite-id> --wait-sec 0
```
start使用D01已核Case终点，不追加统一--end-at，也不追加Spec-only请求。宿主按工具实际返回的next_action/interval继续poll及TEST规定的观测安排；status只诊断，不能代poll。需要回复时使用现reply和原条件材料，记录planned/answered/neutral/improvised及对应问答，不提前选出未被询问的答案。测试宿主不通过业务回复规定模型必须生成哪些内部文件或固定审查轮数。

正常收工由现end_target和conclude核真实事实；失败/未到目标如实记录，不降低目标。基础设施重试、配置切换、内存中止和人工介入按TEST已有分类处理，保所有attempt，不为内容未达标无限重跑。组合变化则重新标身份和受影响范围，不能继续沿旧候选评分。

全部Case终态后按TEST§4.5核回灌前置，再用现`finalize --suite-id <本轮suite-id> --promote`保留材料及原生父子会话；逐项核manifest的not_captured/problems，缺失标证据限制。本轮不跑Coding，若出现预期外业务源码改动或与在途demo冲突，先保两方原件并处理冲突，不以回灌授权扩大产品源码变更。运行证据在output/story永留，长期引用不只指向会被下轮清理的workspace。

## 4. 逐项评审与性能归因

读两例完整Story/Review、相关原件/实际人答、蓝图正文及关键canonical、实际CU产物、父子会话原件/可读日志和报告，不只读末轮摘要。图面须实际查看；缺图/首次报告/父子会话时列明确限制。每个金样差距写目标效果、实际位置、来源与人答差异、作者实际信息/决定、独审反应和最终结果，再归机制/执行/装置/合理变体/证据不足；追至实际生产者和消费者，不从一次模型错误直接增机制。

并列1.9.9、2.0.3和本轮的输入/模型/授权/终点/产出差异；按取材、共同设计/质询、成文/独审、登记交付、实际CU分段比较。总墙钟、人工等待、工具重探、正常设计、审查/返工、上下文及未知区间分别列。1.x Spec共同职责映射到2.x蓝图/Story及实际CU，不能把不同业务范围总时长直接相减。C02同命令节省只作局部事实，不能替全链收益；不另建性能计量平台。
