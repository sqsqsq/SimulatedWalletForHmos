# Case 与宿主交互专项评审

> 本文保留调查/评审证据；现行执行规则以[实施总览及四份步骤](../00-实施总览.md)为准，不与方案正文并行下发。

维护设计者，2026-10-11。按用户要求复核测试输入和实际宿主反馈；本次不修改 Case、装置、产品和历史运行证据，不启动测试。证据包括两 Case 的 case.yaml、interaction-script.yaml、RR/SR/AR 正文、四份补料 docx 的正文、update 回稿、TEST §0–§3、装置源码和本轮 observations/events/初段快照。此次未作 docx 配图视觉评审，图片本身的质量单列未验证。

## 1. 总体结论

两个 Case 有合理覆盖：系统单与本地单、补料和图文导入、会议/冲突、人签、设计、交付、Plan 上限与 update。真实材料有冲突并不使 Case 无效；不应删去冲突换取通过。但它们属于组合验收，不能把全部历时称为简单正常需求性能，也不能以尚未发送的宿主立场判模型缺失。

本轮存在确切的宿主反馈偏移，以及固定回稿对实际产物作不实预设的问题。测试链本身不是中性的，产品归因需要修正。没有发现本轮回复直接告诉模型该改哪个脚本或门禁的证据；不能据此认定宿主没有影响业务结论。

## 2. 已成立的问题

### C1 固定评审回稿预设了并不存在的整体缺失

`test/cases/auto-topup/update-inputs/review-feedback.md` 第 3 条预设“管理页只写了停用原因，没有给用户下一步”，要求重新签约去处。

实际初段快照 `output/story/story-suite-20261011-093025/cases/auto-topup/20261011-093445-23368-49cb86ea/checkpoints/initial/AR/story.md` 第 251–254 行已经写停用横幅和“用户可从这里重新签约”；第 155–169 行也有管理页重新签约路径。尚可要求把动作明确落在横幅及补独立验收，但不能声称整个下一步缺失。14:52:49 的模型提问又沿用了固定回稿的缺失断言，说明测试输入已影响 update 的变化判断。

修正方向：保留稳定业务立场，反馈按实际送审件分成“已满足予以确认”和“具体差异要求修改”；不在每轮无条件投同一句缺陷断言。仍用既有回稿路径，不增加评测平台。确需保证 update 有变化时应使用真实的新业务决定，而不是制造当前稿缺陷。不得回改本轮反馈来美化证据。

### C2 反馈定位依赖合法标题的特定写法

`test/scripts/run_case.py::_write_review_zones` 按 `####` 标题及 `match` 词匹配；车钥匙宽限、转分享、强制下线回稿只在唯一匹配时写入，零或多匹配则跳过并记 note。合理同义标题可能使意见未投递，不等于产品没有承接意见。当前车钥匙未进入 update，这一风险未在本轮触发。

修正方向：宿主依据真实 Review 语义选中实际议题，写入仍由现有人工区工具完成；未投递单列为测试准备问题，不算产品能力失败。保留唯一目标与人工区保护，不向产品强加测试标题，也不扩大关键词列表凑覆盖。

### H1 编号选择批准了 Case 之外的业务结论

09:41:42 自动充值 T6：Case 的立场是“授权后建约失败怎么处理，保持待定”；会议原文 14:24–14:25 也让端侧处理等待结论。模型选项 1 却将保持待定与“用户可直接重走验证”合并，宿主回复 `T6 1`，并把理由记成保持待定。

RR 允许直接再试对应的是支付验证未通过/取消，不是验证已成功、create 失败或超时。初段 Story 第 97、120、129、277 行随后把直接重走验证写入共同处理口径。最早偏移在模型拟选项，宿主未核选项全部含义又将其批准；不能把后续结论只算成文编造，也不能把本次批准当成符合测试立场的人签。

TEST §3.2 “有编号只回编号”与“按真实立场回答”的优先关系必须明确：没有等价选项时，以一句业务话纠正，例如“建约失败后的处理保持待定，暂不确认可以直接重新验证”。这不是教实现，不应记作随意发挥；不要机械批准夹带的新事实或方案。

### H2 术语确认立场过于无条件

两 Case 都预设“术语按你列的确认”，本轮问题还含业务名词到 WalletMain 的权威模块映射。宿主确认不应自动证明工程映射正确，也不应顺带批准同段提到的设计修改。需区分能由需求方确认的业务含义与由工程事实负责的映射；当前证据未证明本轮映射错误，故这是确认范围缺陷，不将其升级为已发生的业务错误。

### H3 明确的宿主延迟放大总耗时

自动充值上传确认在 13:07:45 已被装置检出，14:45:05 才回复，间隔 **97 分 20 秒**。TEST 要求本次唤醒内回复；此次协调没有满足。重复提问本身回 Extension，长时间未回复回宿主，两者分开归因。不能用这一时段证明模型或 Extension 计算慢。

### H4 异常输出被当作普通推进续行

车钥匙 12:13:52、12:30:35、12:44:05 三次回复“继续”，reason 已明确记录大量重复输出。它们没有注入实现答案，但不再是普通无提问推进；续行延长了异常会话，不能与正常执行成本混计。

TEST 当前同时允许 neutral 续行、规定 stop/retry 只响应用户要求，不能倒推宿主本应擅自停测。应完善异常上报与继续权限边界：观察到无业务进展的异常生成时向用户报告，按既有权限决定停止/恢复；不把异常默认为正常推进，不新增基于本次重复词或固定次数的检测器。

### H5 装置给出的“匹配立场”不足以证明语义匹配

`run_multi_case.py::plan_matches` 只比等待 kind/phase；request_host_reply 用当前脚本游标给 planned_intent，并把 question 截为 1200 字符（model_prompt 留原文）。同阶段的不同问题不能由这个结果判为同一业务关卡，长问题也不能据截断文本作决定。本轮宿主确有按实际话题跨条回复，不能说所有回复都被游标驱动；T6 漏核证明最终语义责任仍未可靠履行。

修正方向：保留装置的机械候选提示，完整问题可取得，宿主先核全部选项与实际立场再回答。合并问题按实际回答登记已覆盖条目，未问的条目保留未发生；不新建自动语义应答器。

## 3. 材料合理性与评价边界

- 自动充值 docx 标“v0.4 草稿、先以本文档为准”，系统 RR 是 v1.0 归档版；Case 注释认 RR 为准。模拟旧稿残留可以成立，但维护答案不能代替被测可见的版本与权威证据。原 RR 中指往产品原稿的“触发与扣款流程图”，补料又将流程图指向 SR，需在材料整体验收核其实际来源闭合，不能把无法取得的引用都算模型遗漏。
- 车钥匙同时包含产品假设能力已上线而工程不存在、24/48 小时冲突、接受侧补料、缺补拉契约及外部联调限制。可以测发现与裁决，但范围不拆不等于这些问题已决定，术语确认也不能覆盖它们。
- 本轮车钥匙未问宽限、卡片范围、模拟接口、草稿细化与指标责任等预设事项，宿主未提前补答案，这一点符合协议。评价时必须按实际输入，不能以 interaction-script 或金样中尚未送达的 48 小时、完整卡片范围、指标口径当已定要求。是否必须问、能否局部设计或应停在准备，由实际业务依赖判断。
- 固定复杂组合 Case 可以保留，但性能比较只在相同输入、实际决定、目标终点与质量下成立。本轮人工等待、异常续行、业务裁决、正常作者与审查成本分别记，不推出全流程已提效或全由产品导致超时的结论。

## 4. 纳入 2.0.4 的处理边界
