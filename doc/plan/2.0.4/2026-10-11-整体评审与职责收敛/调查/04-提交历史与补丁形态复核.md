## 3. 确实发生的职责迁移，不应统称补丁

`43035b62` 的 manifest diff 删除 `provides.bridges` 六宿主登记、`adapters/adapted_for`，增加原生物化说明；framework-access 初版仅 `loadNative`，用目标仓 harness 注册 ts-node。结合新增 entries.mjs 与删除 bridges 文件，这是宿主入口所有权替换，不是换名。

`d5950962` 的 lifecycle diff新增由路由派生的等待设计、可成文、需同步状态；`dc7fd36c` 新增 design-source，以已准入蓝图提供成文来源。当前 `design-source.mjs` 仍读 `design_binding`、冻结 snapshot、原生 `readBlueprint(...,'delivery',snapshot_ref)`，并核消费本次输入。保留需求取材、人签与人读件登记，是 Extension 的有效业务能力；新增蓝图关联不是单凭“旧 flow 仍在”就能判为旧职责保留。

`d452bd44` 的 spec/post_check 实际删除 Story/Review 成文、旧 knowledge-use 读写投影、章节模板校验、数值格式红线等大段职责，改取原生设计中的判断并核当前 CU 验收承接。其文件开头明确把真实性归独立审查。此证据反驳“1.x 完整原样留着，再加蓝图包装”的判断。它不证明后来宿主扩展章、图源、知识任务没有再增错职责，后增内容需另审。

`5da9a975 → ba472897 → 9eecfe81` 的 readFeature 从自己派生 acceptance/contracts，改按原生 `resolveCapabilityResolutionEntryInput → resolveCapabilityInputs → SpecLoader`，再补需求来源恢复。第二、三版主要是补齐真实原生入口前置，属于必要接入修正；其频繁返修反映最初真实契约核得不完整，不能据次数把所有代码判成绕框架。

`9a2f21e0` 的 blueprintGraph 调原生 `resolveComponentBlueprintRef`，从这一版 `generated_graphs` 查 graph_id。图源是 document 或 blueprint、复用比图体的具体合同属于来源证明职责；是否有图、表达是否充分仍归作者与独立审查，不能再用固定图数补偿。

## 4. 当前仍需责任核验的接缝

framework-access 当前 558 行，承担 native 加载、蓝图准入/投影、冻结输入消费、CU 身份、运行需求恢复、阶段输入解析、宿主审查能力、反馈资格与关联、图源、关联 Story 定位。这里有大量真实原生调用，不等于“复制了 Framework”；但 native loader 与 Extension 业务定位混在同一文件，所有权必须逐函数说明，不应只以“唯一入口”概括合理性。

当前仍有 `MAISON_GOAL_RUN_ID` 分支和相关运行需求恢复，见 framework-access.mjs:406、418、463。项目维护范围仅 interactive；这些字段可能是原生交互入口仍使用的实际上下文，也可能超出本仓承诺范围。本次没有读取上游调用证据，不能直接宣布违规或建议删除，需按真实消费者核实。

Story 的成文登记、材料身份、审查回复与 CU 人读片段各有不同用途。当前 relatedStories 已不自判当前性是正向收敛；仍须核当前性是否全链使用同一结果、错误是否被消费者丢弃、材料键是否绑定应审范围。旧 `story_digests` 等名字退出并不能回答这些问题。

当前修复后到底提升了未知消费模型质量与成本，历史 diff 无法单独证明。本次未运行 CLI，不宣称行为通过。

## 5. 历史初稿应收敛的结论

初稿 §6 的“声明的退出全部真实落地”“改向不是旧机制残留”超出 grep 所能证明的范围。应改成：点名符号未检出；已核职责链确有撤回；其他旧职责及新增同义职责由实际消费者核验。这不会推翻已核删除事实，但撤去笼统免责结论。

“49 返修标题”“上百提交”只说明协作与变更密度，不能量化补丁占比。应以本表具体错误判定、撤回及残留为依据。预算端点净增小也不能掩盖已撤回中间实现成本；Git 行数与预算累计 G/X 分开。

本次无需据历史单独重写现行方案。若现行方案仍以“旧名已退，所以只做表达优化和 CLI”作为实施前提，需要先改这一关键事实：核清职责边界和真实消费链后才能确定范围。具体调整理由应由整体评审结合另外三份调查定案，而不是把所有新增统一删除或按版本重来。
