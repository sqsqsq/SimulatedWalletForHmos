# 步骤4：测试可信性、效果、退场与版本收口

本步承担 F2–F5、R08–R10、E01、V01/V02 的总验收和所有历史问题去向核对。TEST是命令、状态和评分协议的唯一来源，本页明确本轮输入与完成条件，不另建运行器或评测平台。

## 1. Case 与宿主决定

两个复杂Case保留命令起手、实际索材时补料、初段加update。自动充值当前Story/Review实际送审；车钥匙原生认可的适用Spec/Plan或合法复用，止Plan、不编码。初始消息不透露补料清单、会议和测试答案。

自动充值回稿使用稳定业务要求；当前稿已满足则保持、部分不足才指具体缺口，不预制“现稿没有下一步”的错误评价。车钥匙静态意见保留真实主体、三态和立场，不用标题关键词定位。两份Case的业务难点和冲突不删除换绿；输入改动登记版本，不能与旧轮冒称同输入成本对比。

宿主取得完整model_prompt；question只是展示摘要。候选条目不是业务问题已识别。整个选项与立场等价才回答编号；含额外结论就用简短业务话限定决定。术语确认不批准工程映射；未问到的立场不主动注入；没有真实议题承接意见不伪造D身份。完整问题、实际回复及来源保留在原观测中。

## 2. 成功回复重入（F2）

在 `test/scripts/run_multi_case.py::command_reply` 保留已实现run_id/turn和多step接口，改顺序：纯参数形态检查后，先查目标run/turn的已有成功记录；文本、deliver和covered_steps与成功请求相同则返回原结果，不再核当前阶段或补料是否仍存在。不相同拒绝，不能把旧回复发给新问题。

无成功记录的新发送才核当前等待对象、phase/kind、phase_ready及补料。下层run_case实际发信前再核run/turn。失败不消费step；发送结果未知先核原事件，不自动重试，不做跨崩溃exactly-once系统。answered_steps为实际成功覆盖集合，interaction_index只由首个未答位置派生。历史suite不重放迁移。

必要反例是回复成功后已进另一阶段的同请求重试；只测阶段不变的重试不足。

## 3. 完整投递计划与人工区（F3–F5）

沿既有 `resume-update --review-feedback-file`、deliver_update_inputs、_write_review_zones修复，不新增事务平台。

输入YAML每项 `{source_item, decision_id, verdict, opinion}`：source_item完整唯一覆盖静态意见，目标D唯一且属于当前initial稿；verdict/opinion保持对应业务立场。宿主按当前Review语义选择D，不靠机器词匹配。若无真实对应议题，停在未投递意见，交设计者裁定正常承接，不把反馈塞进相似议题。

所有update_inputs和额外deliver先形成完整动作集合，解析实际目标后一起预检：不同内容写同目标整批拒绝，无写入、无update请求；同字节同目标可合并一次并保留来源明细。不能仅核来源存在。

人工区的三态各恰好一行、意见行恰好一行，重复或缺失写前拒绝；空白区可首次写，完全相同意见幂等，已有不同意见保留冲突。机器区与初段身份核对，换行和其他内容保持。脚本不替人删除额外勾选行。

执行期IO失败分三类：delivered是完成项；failed是当前失败且可能部分写入，报告目标/错误和可读时实际存在、大小、摘要，读不到为unknown；not_delivered仅尚未执行项。失败不启动模型、不伪称零写入、不自动覆盖恢复。重试沿现有同字节和冲突规则。

## 4. 环境与上游的起跑条件

E01由维护实施者取得：CLI二进制版本、实际请求模型及生效配置路径、输入/上下文/输出limits、当前压缩算法及触发条件、服务限制的单位与依据。只记脱敏字段，不记录密钥。1048576和报错1000000的单位未统一前不能作大小推断。

据事实提出最小配置修正和离线阈值核验；用户配置修改仍按授权。若服务口径拿不到，明确起跑风险与受影响终点，不能声称已修、不能盲目扩大context或重跑。异常无业务进展时保留事件并报告，stop/retry按TEST既有授权，不机械多次“继续”。等待在当前唤醒中及时处理；宿主延迟单列成本。

U01未就绪不签CU准备/Plan完成；U02没有强生产者绑定保证时只按实际调用证据评价原件；FW-04/05与interactive术语确认按总览逐项状态。已经能独立做的离线验证继续，不笼统等待Framework全部能力。

## 5. 完整验证矩阵

| 验证对象 | 具体输入/动作 | 成功与失败如何区分 |
|---|---|---|
| 来源→设计 | 原件包含有效条件、无AC、候选漏对象；另给真实范围外项 | 独立内容评价指出前者缺口，后者有真实排除依据；不按关键词判 |
| 设计→首稿 | 结果未知、待决验收、完整恢复路径及纯背景章 | 首稿保留条件和边界；不能只看修后终稿或要求同一组织 |
| CU承接 | 直接入口、单/多CU、common/undetermined、合法复用、关联漏登记 | 原生责任及实际知识/Story输入一致；无机器关联不冒称无业务责任 |
| 审查→交付 | 格式错、实质缺判据、真实修订、可保留warn | 原件保留、结论对当前对象、真实缺陷回真源、偏好不强制循环 |
| update/restore | 真open/导入/complete/restore；closed后新轮重新采用旧原件 | needs_sync真实，人工/冻结/蓝图/发布记录受保护；不手改origins |
| 材料与图 | 材料图引用逐个定位，原样/细化/新绘，合法不同图型 | 实际目标可读，业务关系正确；未看图像不能签视觉质量 |
| 装置 | 阶段变化重试、混合来源同目标、重复人工行、写部分后报错 | 不重复发送、不误写、不伪称未投，原件保留 |
| 通用性 | 预约/协作等中性业务，无云/无模式/无待决，合法CU划分 | 不强制不存在内容，不依赖Case名称、固定数值或形式 |

机械夹具只证明协议与副作用；语义反例由维护设计者直接读内容或获授权的独立模型评价。新模型评价和CLI不因本方案自动获授权。语义失败必须给实际输入、首稿、审查和修复位置，回最早责任，不能追加Case专用判门。

### 共享替换的必要反例

同一文件及声明分别经蓝图任务、Story图源、CU图源/表达取得：字节正确时都能消费，坏摘要/文件缺失得到一致缺口，坏fragment不能因先去片段而漏掉；特别覆盖“冻结包files均正确，但候选声明的fragment或sha错误”，此时蓝图任务必须报错，不得以包校验成功或draft状态ok继续。原生直接来源没有Story登记仍成立。候选旧版与flow新版并存时分别取各自指定版本；快照坏JSON不得成为空成功。检查adoptedInputs/unitSources已无自有read/hash循环，并逐个核reader-review-task、story-inputs、images、storyCurrency、storyExpression的实际返回。

basisSections同一结果包含原文、空refs和稳定章/节位置；nextSteps取得背景文字，storyExpression不把它送给全部CU。有地址仍走原生scope及区间去重，坏地址仍报原缺口。测试核这两个实际消费者，不只断言新增字段存在。前置图源/当前性原有失败结果及原件无写入保持。

## 6. 离线命令与证据交回

F2–F5复用 `test_multi_case_cli.py`、`test_host_driver.py`、`test_material_delivery.py`；保持 `test_cli_config_failover.py`、`test_run_measurement.py`、`test_multi_scenario_cases.py` 的有效覆盖。各产品步骤先跑所列定向检查，最后一次必要收口：

```powershell
python test/scripts/verify.py affected test/tests/test_multi_case_cli.py test/tests/test_host_driver.py test/tests/test_material_delivery.py test/tests/test_cli_config_failover.py test/tests/test_run_measurement.py test/tests/test_multi_scenario_cases.py
python test/scripts/verify.py cases
python test/scripts/verify.py handback
```

新修改、失败或新证据才重复相关检查。保留首败，产品/环境/资源分别归因。图引用、完整恢复入口链、当前任务内容走查可以离线完成，不以没有CLI授权跳过。

正式运行读取实际安装身份、输入与宿主答复、原事件/runlog、模型可用执行记录、子代理原件、候选/首稿/修复稿、蓝图/CU、最终Story/Review/Spec/Plan及归档/更新证据。不存在的产物标未生成；模型自报、文件数量和门禁PASS不补证据。模型执行记录只用于行为分析，不捏造不可取得的内部过程。

## 7. 金样、成本与正常链的签收

沿现有五个结果金样情景，直接比较背景范围、协作与分流、恢复、验收及CU可实施性。只因图数、H3或章节编号不同不判退化；遗漏业务条件、错来源、入口/状态/调用接不上须判不合格。金样不重建运行现场，不将隐藏立场投给被测模型。金样正式切换仍须用户审定，本方案不代签。

成本按同输入版本、同质量、同终点比较；记录首次主体产出、真实业务修复、格式返修、无信息增量读取、建议改稿、审查和人等。现有measure_run/events承载，不建新账本。失败旧轮只能证明问题存在或能力恢复，不能作提效分母；扣等待不是纯推理时间，多Case历时不相加冒充suite历时。质量先成立，没有可比样本就写未证明收益。

## 8. 退场审计与版本结论

按总览退出台账逐项核生产者、消费者、指令、状态、配置、注释和专用测试。旧错误断言退出，有效反例覆盖迁移；纯注释、测试、升级记录不计产品X但仍记录工作量。对历史点名的导出消费者做静态引用后追实际入口，名称被搜索到不等于可达；没有具体孤儿证据不预删，发现新职责问题回设计者定案，不自行扩大架构。

31处readJson审计的既有结论保持：只处理已证实坏prepared问题，不把合法空值全部改抛错。已退knowledge-use/bridge/旧Spec编排不再计X；2.x未发布升级条目保持退出，现役安装、1.x历史和知识保护保留。

每步交实际输入输出、消费者、替换/保护、失败结果、定向证据和G/X，集中评审。最终分别判：产品合同与实现正确、内容达到目标、真实交互成立、成本有同条件证据、旧职责确退。只完成离线不能宣布整个2.x适配完成；未完成项仍在本版列明，不靠移版关闭。

本步产品预估G/X为0，测试域估G120–200/X25–60，用于F2–F5真实反例及完整入口链、退出错误分支和充分性断言；这是维护工作估算，不计产品账。发现需要新的产品修复先交最早失败证据与最小方案，不设隐藏产品预留额度。
