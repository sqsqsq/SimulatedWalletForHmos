## 2. R2：「怎么读」入口先分情形

`reader-review-task.mjs::reading` 改成：开头一段先按派审载体的情形定范围。

- 首审、fail 复审、带上一版参考的审查：按 1–4 条完整读。
- 格式返修：原回复的实质判断与判据覆盖充分就照用，只回材料核诊断点到的那部分。
- 诊断是缺判据、引用找不到、依据不足、结论矛盾，或者看不出原审查是否完整时：同样完整读。

退出了末尾追加的第 5 条例外。1–4 条的完整阅读顺序与同字节投影只读一次保持不变。

全文核查：生成任务里其余「完整审查 / 逐项核」都在 recheck、prior_revision、fresh_review 与首审载体中，属于完整审查的情形，不冲突。

## 3. R3：已登记 Story 的真实恢复链

V01 的入口步骤抽成 mixin `SameNamedOriginalSteps`，未登记与已登记两种起点共用，原两条用例改用它，保持通过。

新增 `ARegisteredStoryGoesThroughTheRealEntries`，起点是：

1. v1 原件经材料关卡导入、complete；
2. 设计同步（`design_kit.install_blueprint`，与既有登记用例同一个夹具入口）；
3. 作者把材料清单改列原件；
4. prepare 加夹具通过报告，真实 `story` 登记，close。

第 3 步不是测试补丁：不改列原件，prepare 的结构检查就会照实拦下「RR/prd.md 是 inbox/甲需求.md 的转换稿——列原件」。

**场景一：同名换版后撤回。**

- 新一轮导入 v2 并 complete 后，契约状态从 `story_written` 变成 `complete`，路由是 `design_blueprint`。
- restore 先列冲突，人按开轮版本定回后得到 `restored`。
- 撤回后：
  - 状态仍是 `complete` 加 `design_blueprint`，旧登记不被当成现在的；
  - `needs_sync` 为空，因为 update.py 只在 `story_written` 时算漂移，这里断言实际路由而不是空列表本身；
  - 交付门 `check --deliver` 拒绝。
- 冻结输入登记、v1 与 v2 包、蓝图字节、关卡记录（含人的原话 `reply`）、归档标记都没被回写。

**场景二：保持登记状态的表达修改后撤回。**

- 已登记后开一轮，改「背景」，审查后重新登记（这是完成点），再 restore。
- 结果：
  - Story 退回开轮时那一版；
  - `needs_sync = ["AR/story.md"]`，状态仍是 `story_written`，路由 `register_story`；
  - 交付门拒绝，原因含「登记之后改过」；
  - 轮次已关；
  - 上面那组受保护项都不变。

报告由夹具提供，这里证明的是确定性的登记与恢复，不是语义评价。

## 5. R5：容量说明与启动配置

`tools/cli/README.md` 那一节改写，只写 opencode 1.18.32 已核的内容：

- `reserved` 取配置或 min(20000, 输出上限)；
- 输出上限是 min(limit.output, 32000)，可被环境变量改；
- `compaction.auto` 的前提。

未核项单列：服务单位、其他提供商的限额。去掉了「各模型统一 1000000」和「低于服务拒收线」的普适说法。

用户 10-12 进一步要求「固化为 opencode 的 CLI 启动配置，不靠读文档改配置」，据此把上限放进 Case 驱动的配置组：

| 位置 | 改动 |
|---|---|
| `test/config/test.yaml` | 只给观察到服务限额的 `bailian-deepseek` 声明 `limit: {context: 1048576, input: 1000000, output: 131072}`，注释写算法、来源报错、单位未核与适用范围 |
| `cli_config_group.load_cli_group` | 校验 `limit` 只给 opencode、三项正整数、input 不大于 context |
| `run_case.build_cli_env` | 有 `limit` 时设 `OPENCODE_CONFIG_CONTENT = {"provider": {<p>: {"models": {<m>: {"limit": …}}}}}`；没有就不带 |
| 测试 | `test_cli_config_failover`（配置组上限与三种拒绝）、`test_harness`（环境变量形状、未声明不带） |

opencode 端的实际合并已探过（`e01_merge_probe.py`，只读 limit 字段、不调用模型）：

- 内联配置按层独立校验，只给 `input` 会报 context、output 缺失，所以三项都要给；
- 给全后 `debug config` 里这个模型的 input 被内联值覆盖，其他模型不受影响。

用户全局 `opencode.jsonc` 之前已按授权给 5 个模型加了 `input: 1000000`（备份 `opencode.jsonc.bak-20261012072249`），这次没有回滚。Case 运行现在不依赖它。其他 4 个模型的限额依据仍未知，要不要恢复备份由用户决定。
