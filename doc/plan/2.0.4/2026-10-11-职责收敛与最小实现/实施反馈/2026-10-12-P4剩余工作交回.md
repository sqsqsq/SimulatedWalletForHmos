## B1. E01 容量依据

| 问题 | 事实与来源 |
|---|---|
| 被拒的是哪次请求 | `story-suite-20261011-093025` 车钥匙，运行 `548d7338c6e240b9`，`bailian/deepseek-v4-flash-0731`（events 中 providerID bailian 9269 次、modelID 7544 次） |
| 服务的计量单位 | **token**：阿里云百炼官方错误码页对 `Range of input length should be [1, xxx]（InternalError.Algo.InvalidParameter）` 的解决办法写的是「messages 数组的总 token 数不超过模型的最大输入 token 限额」 |
| 是不是这个端点 / 模型的值 | 方括号里的上限随模型与端点变化（其他端点报过 30720、196608、169984 等）；这里的 1,000,000 来自本配置这一个端点与模型的实际报错，不外推到其他提供商 |
| 运行证据与单位一致吗 | 一致。被拒前最后一个成功步骤服务自报：input 908 + cache.read 998,400 = **999,308** 输入 token 被接受，加输出 755 合计 1,000,063；下一次请求在此基础上加上输出与工具结果即被拒。1,000,063 低于旧压缩线 1,016,576，所以没压缩 |
| 当前配置的触发窗口 | `limit.input` 1,000,000 − reserved 20,000 = **980,000** |
| 下一请求的余量够不够 | **不够**。统计近期各轮 3,370 个相邻步骤的输入增长：中位 851、p90 4,132、p99 14,440、**最大 32,906**（接近单轮输出上限 32,000 加工具结果）。压缩判断用的是上一步的用量：若某步结束时在 980,000 以下（不触发），下一请求再加 33k，就会越过 1,000,000 |

**起跑判断：当前配置不足以支持长会话的目标测试。**

建议的调整（**需设计者或用户定，未改**）：只改 `test/config/test.yaml` 这一组的 `limit.input`，取 **960000**，触发窗口变为 940,000，余量 60,000，约为已观测最大单步增长的 1.8 倍。

- 压缩请求本身发送约 94 万 token 的历史，也在服务上限内。
- 等价做法是保持 input、加 `compaction.reserved`，但那会作用于整轮运行的全部模型，不如按模型的 input 精确。
- 工具单次结果没有硬上限，超大读文件仍可能跨过余量。这是剩余风险，属于宿主层面，不在 Extension 里补。

**已知 / 未知**：单位与端点已知；opencode 1.18.32 的触发算法与内联合并已知；单步增长的分布已从 10 月各 suite 的运行事件实测取得（3,370 个相邻步骤）。未知的是其他三个 opencode 模型的服务限额，它们在本仓配置里没有声明。用户全局配置里那 4 个模型的 `input: 1000000` 没动，要不要恢复备份由用户定。
