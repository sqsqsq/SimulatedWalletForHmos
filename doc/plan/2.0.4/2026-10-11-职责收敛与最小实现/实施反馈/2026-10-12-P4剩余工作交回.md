## B1. E01 容量依据

| 问题 | 事实与来源 |
|---|---|
| 被拒的是哪次请求 | `story-suite-20261011-093025` 车钥匙，运行 `548d7338c6e240b9`，`bailian/deepseek-v4-flash-0731`（events 中 providerID bailian 9269 次、modelID 7544 次） |
| 服务的计量单位 | **token**：阿里云百炼官方错误码页对 `Range of input length should be [1, xxx]（InternalError.Algo.InvalidParameter）` 的解决办法写的是「messages 数组的总 token 数不超过模型的最大输入 token 限额」 |
| 是不是这个端点 / 模型的值 | 方括号里的上限随模型与端点变化（其他端点报过 30720、196608、169984 等）；这里的 1,000,000 来自本配置这一个端点与模型的实际报错，不外推到其他提供商 |
| 运行证据与单位一致吗 | 一致。被拒前最后一个成功步骤服务自报：input 908 + cache.read 998,400 = **999,308** 输入 token 被接受，加输出 755 合计 1,000,063；下一次请求在此基础上加上输出与工具结果即被拒。1,000,063 低于旧压缩线 1,016,576，所以没压缩 |
| 余量统计的口径 | opencode 判断压缩用的是**上一步总用量**（已含上一步输出）；下一请求超出这个量的部分，才是两次判断之间新增的输入。统计脚本 `output/scratch/2.0.4/e01_margin.py`，结果 `e01_margin.out`：10 月 suite 里 `request.json` 模型为 bailian/deepseek-v4-flash-0731 的 41 个运行，同一 raw.jsonl、同一 sessionID 内相邻两条 step_finish 配对，共 **2426 对**（负差 0）；增长 = 下一步 input+cache.read+cache.write − 上一步 tokens.total |
| 统计结果 | 中位 244.5、p90 2,672、p99 9,543、**最大 19,935**（`story-suite-20261003-215006` 车钥匙运行 `50d506c539024e0a`，raw.jsonl 第 30→34 行）。与评审独立复核一致；p90、p99 的个位差来自分位数取法 |
| 原交回的错误 | 原写「3,370 对、最大 32,906，20k 必然不够」是**输入对输入**口径，把上一步 32,000 输出当成了新增，又混入了其他模型；最大样本（自动充值 `c5473201b4834078` 第 394→398 行）按正确口径只增长 906。「不够已证实」的结论撤回 |
| 原配置的余量 | 触发窗口 1,000,000 − 20,000 = 980,000，余量 20,000，只比已观测最大值多 65：没有被证明必然超限，但没有稳健余量 |

**按评审裁定已改**：`test/config/test.yaml` 中 `bailian-deepseek` 的 `limit.input` 由 1000000 改为 **960000**，依据注释同步；context、output 与其他配置组不变，用户全局配置不动。`test_cli_config_failover` 断言该组配置值的那一处同步（通用结构测试不绑定数值）。

生效核对（`output/scratch/2.0.4/e01_effective.py`，结果 `e01_effective.out`）：用驱动真实的 `build_cli_env` 加配置组装配环境，启动原生 `opencode debug config`，只读 limit 与 compaction 字段，不调用模型。

- 这个模型生效为 `{context 1048576, input 960000, output 131072}`；
- `compaction.auto` 与 `reserved` 都未配置，reserved 取默认 min(20000, 32000)=20000；
- 实际压缩窗口 **940,000**，相对服务输入上限留 **60,000**；
- 其他四个模型仍是用户配置的值，没有被这组覆盖。

**起跑判断**：这组的容量配置有已核依据和 60,000 余量。这不是永不超限的保证：单次工具结果没有上限，历史最大值不代表未来上限，剩余风险留在宿主层，不在 Extension 加截断、循环或容量状态。
