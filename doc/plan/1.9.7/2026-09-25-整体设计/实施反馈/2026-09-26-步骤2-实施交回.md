# 步骤 2 实施交回：审查与闭环

2026-09-26，维护实施者。依据 [04](../04-步骤2-审查与闭环.md)。不含评审结论，四步做完后统一评审。

## 1. 做了什么

### 判据全量下发（C01）

- `verifier-report.mjs` 新增 `overlayChecks`：按阶段读 overlay 的 `semantic_checks`，审查请求与报告核对共用。
- `pre_verifier.mjs` 先注入「本阶段全部判据（逐条出结论）」：每条判据一行（id、级别、描述首句），并写明报告结构——汇总表每条一行四格、非 PASS 出 YAML 明细、恰好一个终态块。原来按前缀挑选的 `overlayCheckIds` 退出。

### 一处定义的处置规则（C02–C05、C19）

- `phases/spec.md` 新「闭环」一节是唯一的处置表：有阻断项 / PASS 只改表达 / PASS 改业务 / PASS 建议不在本阶段修，各写你做什么与闭环方式。`phases/update.md`、`hooks/spec/author.md`、`hooks/plan/author.md` 只引用它；路由在步骤 1 已改为指向这一节。
- `withoutCurrentReport` 去掉「update 进行中一律要求重审」一支，交付门不再读流程契约（`deliveryRunFacts` 退出）。update 里改了业务的阶段改由 update-notes 声明「业务改动的阶段：…」，`update --action close` 核这些阶段有当前对象的 PASS 报告。
- 读者审查判 WARN 且没有阻断项时交付门放行，建议项进 notes；有阻断项时提示逐条指到那几条。
- `SKILL.md` 失败出口改为：门禁反复报同一问题而作者判断改不动时，停下说明卡在哪、缺什么、需要谁提供。「连续三次运行」的机械条件退出。

### 审查对象按业务内容计（C06、C07）

- `reader-review-task.mjs` 嵌入 story 时，附录机器区换成一行区名（「附录机器区：<区名>」），片段最前面加一行注释形态的「审查对象标识（非审查内容）：story 作者区 sha256:…」。机器区重投不改片段，作者区改了片段随之变。这是过渡路径（04 §3.3），上游反馈已在 02 §4。
- `story-build project` 在登记之后也能跑，只重投机器区；作者区要改才 reopen。

### 报告与定级（C08、C09、C15、C17、C18）

- `reportProblems`（spec、plan 门禁都调）：格式不合（终态块不是恰好一个或没有汇总表）的回复移到 `reports/rejected/`，报被拒、不计结论；缺判据逐条点名「缺判据：<id>」；同一审查对象记在 `reports/verifier.conclusions.json`，已有合规结论后被覆盖就报；报告里 WARN、FAIL 的判据要在 `<阶段>/notes.md` 里有处置记录。
- overlay：spec 的 `knowledge_spec_exit_substance`、`spec_ext_conclusion_validity` 与 plan 的 `knowledge_obligation_substance` 改为 BLOCKER，描述里写明哪些缺陷类让下游必须重新决定；spec 新增 `judgement_change_basis`（审查之后改判断要有新依据）。
- `hooks/plan/author.md` 写明事实回改：发现 spec 的现状结论与仓不符，走修正入口改 spec 并登记议题，再继续 plan。

### 机械核前移（C10–C14）

- 合同 `id_shapes.acceptance` 是验收编号形态的唯一定义；`hooks/shared/contracts.mjs` 的 `acceptanceIdRe`、`keptIdRe` 读它，ut、testing 门禁改用它（两处写死的正则退出）。
- spec 门禁 `acceptanceAlignment`：§8 每个编号在 acceptance.yaml 里有、关联功能与 `prd_function` 一致、同号同义；走 /story 的需求另核上游原始验收编号在 §8 或 acceptance.yaml 里有对应行，或写「不承接：<编号> <理由>」。
- 图源标记：`sourceMarkProblems` 只核引用——指向的图在直接上游里存在、不指向 story 自己；围栏外的标记只报一处「写在了围栏外」，同一行不再按文档坐标再报一次。
- 归档件大标题：`skeleton` 从需求详情取名称写「编号 名称」；check 对只有编号的标题报「大标题缺需求名」。

### 门禁提示（C13、G06、G09）

- spec 门禁的数值来源、禁用词、文档坐标全部列全，数值来源合成一条逐处列出；序数（第 N 次）不当数值。story check 的语言红线同样列全。
- 示例换中性名：overlay 的 `createBusinessOrder`、`last_business_context`、`feature_entry_enabled`，spec 门禁提示里的「管理台功能开关」，`phases/spec.md` 的「管理台排期、打点归档、翻译回稿」。
- 合同说明的重复一句已在步骤 1 去掉（G09）。
