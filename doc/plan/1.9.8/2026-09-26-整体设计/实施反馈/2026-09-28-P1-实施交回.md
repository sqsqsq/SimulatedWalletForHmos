## 5. 与方案的出入

1. **开发源原地跑不起来。** 扩展的 YAML 读取器按设计从自身位置向上找消费工程的 harness；开发源 `extensions/` 不在任何消费工程里，所以原地执行扩展脚本的测试和检查器一律失败（首轮全量 243 条）。分册 02 只写了「静态源码扫描或取源键才指 extensions」，没有覆盖「执行」这一类。我按 02 第 9 项「开发版集成检查给 template」的同一原则处理：检查器的执行器取 `--project-root` 里装的扩展；测试由 `ext_workspace.DEV_EXT` 在每个进程里把开发源逐字拷进一个临时消费工程再执行。P2 的 `install_extension` 落地后，`DEV_EXT` 是否改为调用它，请设计者在 P2 定，避免两份安装实现。
2. **adapt 用目标的 yaml 包读包的 manifest**（同一原因：包可能是开发源）。原来「目标没有 harness」只提示、继续复制，现在直接停。
3. **adapt 的 git 前置改为「目标的 `framework.config.json` 被所在仓跟踪」。** 只判「在工作区里」会放过本机的情况：用户目录本身是个忽略全部文件的 git 仓，临时目标的改动从未存档，脏检查也看不见。demo 这类子目录照常通过。
4. **演进记录加了空的 `## 1.9.8` 节。** 版本号检查要求本版有节；本版对目标没有属于「知识 / 对接层 / 在途单」的适配动作（入口映射与取源方式由 adapt 自己处理），写成条目会让升级无谓地停下来问人。是否要写条目、写在哪一块，请设计者定。
5. **本地需求系统与替身默认目录。** 替身对接层 `mcp.js` 默认读「消费工程根/test/story/requirement-system」，原来靠「消费根就是维护仓根」与 bootstrap 对上；现在消费根是 demo，而 demo 顶层放维护目录属于结构漂移。bootstrap 改为把单据装在维护域 `test/requirement-system`，回执与日志给出 `STORY_REQUIREMENT_SYSTEM_DIR`；「与 mcp.js 回落值一字不差」的核对随之退出。`mcp.js` 是产品机制、不在 AC02 允许面，未改；它的回落值在新布局下落空，是否调整请设计者定。
6. **夹具重排。** A02 的 `package/` 改为扩展根形态，检查器把真实 adapt 脚本放进包、目标同版本也带一份，并给目标接 yaml；A05 夹具的入口文件与扩展段放在同一层，夹具根就是工程根，检查器不再「从扩展目录向上找三级」。
7. **验证资产词表**：检查器 G02 与 `test_narrative_variants` 的 `"test/story"` 改为 `"test/"`（维护域现在的根）；当前扩展里零命中。
8. **局部选择**：`.cursor/plans/*`（43 份历史计划）随宿主目录进 demo；`run_multi_case` 的 git 快照仍记维护仓，套件里的「主工作区」记 demo。
