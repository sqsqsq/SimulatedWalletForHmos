## 4. README 阅读顺序重新裁定

接受用户确定的三类读者与四部分顺序；不机械搬动六节，按动作深度分配：

- **快速上手**：开头用三行讲清已安装前提、`/story init <编号>`、送审或后续阶段选择。然后一张简短命令表（命令/何时用），一条需求主线，一张简化参与表（何时问/你如何答）。系统单与本地单差异必须在起手可见。init/archive/update写主线，adapt在命令表只链接移植节。材料格式与会议的长触发列表不塞进大表。
- **FAQ**：固定覆盖token、补料格式、会议转写、中断继续、范围调整、改Story、update撤回与线上restore区别、后续阶段授权、无审查员。每题先给用户现在能做的一两句话，再链接机制规则；不是把长说明藏到链接后让用户仍不知道怎么做。
- **移植**：保留当前安装节的来源工程→目标工程、所有权、首装确认、升级跟进、脏覆盖处理与宿主入口，修R2。业务维护者只读此节即可取得前置、执行动作和失败责任，适配方式不依赖先读正常需求流程。
- **机制与说明**：产物表、三类知识及六阶段承接、成文和投影、审查与授权、update影响范围与恢复、已知局限。这里承载机制依据；不重复命令表或用户步骤。修R1，四项当前效果边界保留。

先前“命令只在动作旁”“FAQ必须拆散”的结构决定撤回；它们没有比用户的阅读目标更高的权威。也不把“每个名词只出现一次”当验收：入口短提醒与机制解释可合理分层，同一规则的完整定义只维护一处。沿用已核实的事实修正，禁止恢复“两处参与/三个保证/永远一致”等过度承诺。
