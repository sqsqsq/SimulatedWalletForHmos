## 3. 真实 CLI 怎么跑（照这个走，别自己发明）

**唯一入口**是 `test/story/scripts/run_multi_case.py`，四步：`plan` → `start` → 循环 `poll`/`reply`
→ `finalize --promote`。即使只跑一个 Case 也不直接调 `run_case.py`。

```powershell
python test/story/scripts/run_multi_case.py plan auto-topup --jobs 1          # 只读，先看清选了什么
python test/story/scripts/run_multi_case.py start auto-topup --jobs 1 `
  --suite-id story-suite-<YYYYMMDD-HHMMSS> --authorize-non-sandbox
# 循环：poll → 读 adaptive_reply_requests → 以需求方身份回话 → 再 poll
python test/story/scripts/run_multi_case.py finalize --suite-id <同上> --promote
```

- `--authorize-non-sandbox` 是**长期授权**（TEST §0），每轮不必再问；沙箱里起不动子进程。
- **起跑即清场**：`start` 会把主仓 `doc/features/*` 整体归档到 `E:\Project\bak\Story-Features-<ts>`，
  并删掉所有历史 suite 的 workspace/output。这不是可选步骤，是它的一部分。
- 终点由 `case.yaml` 的 `end_phase` 一行定（当前 `spec`）。**prompt 里不写阶段链**，
  阶段推进是驱动器的职责。要跑到归档就改那一行，别动 prompt。

### 3.1 heartbeat 我用的代跑脚本

15 秒（进 spec 后 120 秒）的 heartbeat 我没法靠定时唤醒做到，用了一个代跑脚本，
它严格照 TEST §3.1 的两条：`next_action` 一旦不是 `poll_after_interval` 就**立刻退出并把
「等宿主」写进日志**，判断全留在驱动器里。脚本留在本目录
`hb-heartbeat代跑.py`（一次性工具，方案目录在 .gitignore 里，不进仓）：

```powershell
python test/story/plan/2026-09-11-Extension旧机制退场与新机制替换/13-实现质量替换/hb-heartbeat代跑.py <suite-id> <预算秒数>
```

它自己读 `next_interval_sec` 切 15→120 秒。放后台跑，它退出时你会收到通知。

**只能有一个 poller。** `poll` 是会**消费事件**的事务，不是只读查询——两个 poller 并发，
事件被其中一个吃掉，另一个看到空的。我自己犯过一次：后台 hb 还活着时又手工 `poll` 了一次
（这一跑没看出损伤，但那是运气）。要看状态就等 hb 那一轮的输出，或先停掉它。

### 3.2 回话口径（错一次就污染整轮观测）

- 模型给编号选项 → **只回编号**（`"1"`、`"2"`），不回选项内容、不解释为什么；
- 要投料 → 先 `--deliver <文件名>`（文件先落进收件箱，那句话才排队），再回一句或编号；
- **`--reply-kind` 与 `--step` 是记账**：`planned` 要带 `--step <规划条目 id>`，规划指针才前进；
  规划外但需求方答得上的用 `answered`；模型没提问只是在推进用 `neutral`（一句不含事实的「继续」）；
  自己的话用 `improvised`——尽量别用，评测时要单独拎出来。
- **一次回话不超过一句**。不点命令、文件、字段、关卡名——说出解法那一刻，
  测的就不是「它能不能自己走通」，而是「宿主知不知道答案」。

### 3.3 并行两遍同一个 Case：不行，硬障碍是**结果回写**

用户问过，查清了，省得下一个人再查一遍：

| 门 | 在哪 | 规则还是物理 |
|---|---|---|
| 同 suite 重复 case id | `select_cases` | **物理**：workspace 目录就是 `workspace_root/<case-id>`，`create_case_workspace` 见已存在即拒绝 |
| 同 suite 重复 AR（`same_feature_parallelism: 0`） | `select_cases` + `start_block_reason` | 跑时是规则，代价在最后一步兑现 ↓ |
| **`finalize --promote` 的落点是 `doc/features/<AR>`** | `promote_case_workspace` | **物理**：一个 AR 一个落点，第二份只能记 `feature_destination_conflict` 不回灌 |
| 两个 suite 并行 | `start` 的清理预检 | 直接 `SystemExit`：起跑要删所有历史 suite 的 workspace/output，另一个还活着就是「要删的里有活的」 |

**隔离本身没问题**（每 Case 独立临时 workspace + 独立需求系统快照 `sw-sys/<suite>-<hash>/<case>/`，
跑的时候不会互相写坏）。真要并行两遍同一业务材料，只能给第二份一个自己的 AR 号
（复制 Case 目录 + system 快照改号），那是**新增测试数据，要用户点头**。

## 8. 环境坑（都真实踩过）

- **两个 poller 不能并存**（§3.1）：`poll` 会消费事件。
- **heredoc 会把 `\\` 折成 `\`——连带引号的 `<<'PY'` 也照折**（反直觉，这一轮踩了三次）：
  Python 源里的 `"\n"` 变成真换行，于是 JS 里 `'\n'` 断成两行字符串字面量，`node --check`
  报 `Invalid or unexpected token`。要么用 `chr(92)` 拼，要么写完**回读确认**——
  我有一次替换因此静默没命中，`withMethod` 根本没接上。
- **Windows 控制台是 GBK**：`print` 中文或 `⑫` 会抛 `UnicodeEncodeError`，脚本前加
  `PYTHONIOENCODING=utf-8`。它只影响输出，**文件写入照常**——见过「print 炸了但改动已落盘」。
- **夹具正文别写机制自己的忌语**：写「夹具」会被 ⑩ 的 harness 术语判据抓住，
  写「S4」会被仓内工作编号判据抓住。夹具文案也要用业务话。
- 失效形态夹具改动后必跑 `check_failure_modes.py`：`bad` 夹具要保持它的缺陷，
  **不能拿 `project` 把缺陷洗掉**（评审明令：那是造必绿证据）。
