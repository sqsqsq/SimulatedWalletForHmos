## 1. 现状：根下有什么、谁写的

一次真实跑完的产物（`doc/features/AR90006/AR/`），按**写它的人**分开看——这一列决定了哪些动得了：

| 根下的东西 | 是什么 | 写它的 | 归属 |
|---|---|---|---|
| `design.md` | **交付文档** | `story.js:204` | 对接层 |
| `story.md` | **交付文档** | `story-build chapter` / `project` | 公共 |
| `review.md` | **交付文档** | `review.js:55` | 对接层 |
| `detail.json` | 单据元信息（单号、类型、父单号） | `story.js:206` | 对接层 |
| `.review-backup/` | 回稿前的备份目录 | `review.js:44-46` | 对接层 |
| `init-analysis.md` | 材料盘点与需求分析的支撑件 | `story_flow.py`（`ANALYSIS`，`:67`） | **公共** |
| `story-flow.json` | 流程契约（轮次、关卡、决策） | `story_flow.py` | **公共** |
| `upstream.md` | 导入落点产物 | `import_sources.py:645` | **公共** |

**`story.js` / `review.js` / `token.js` 三个是内网自己实现的对接层**（用户 2026-09-07 明确：只有这三个是内网的，其余全公共）。改它们的写入路径等于改内网合同，而内网那份不会跟着改——本仓改了就当场断链。

**所以本步只动公共侧写的那三个**：`init-analysis.md`、`story-flow.json`、`upstream.md`。

## 2. 目标布局

```
AR/
├─ design.md          交付（对接层写）
├─ story.md           交付
├─ review.md          交付（对接层写）
├─ detail.json        单据元信息（对接层写，不动）
├─ .review-backup/    对接层的备份目录（不动）
└─ story-src/         辅助（沿用现有目录，不改名）
   ├─ story-flow.json     ← 从根下移入；登记后仍由 story_flow.py 续写（archived / reopen），留、不冻结
   ├─ init-analysis.md    ← 从根下移入；指纹已记在契约（analysis_sha），留、不冻结
   ├─ upstream.md         ← 从根下移入；导入落点，round 重算，留、不冻结
   ├─ materials.json      （原位）留、不冻结
   ├─ decisions.json      （原位）随稿冻结
   ├─ copyedit.md         （原位）随稿冻结
   ├─ drafts/             （原位）登记成功后删
   └─ .*.json             一次性侧车（原位）
```

**目标一句话**：公共机制不再往 `AR/` 根下写任何辅助文件。根下剩的四个文件里三个是交付文档、一个是对接层写的单据身份，都不是本步能动或该动的。

**沿用 `story-src` 不改名**：它已经是辅助材料的既有落点，需求分册说「优先利用现有子目录，按用途采用简单布局」。

**`story-src/` 里的每一件都有一个「登记时怎么处置」**：成文登记（`story_flow.py story`）会把这个目录扫一遍，不在保留集里的文件与目录一律删掉（`sweep_story_src`，`story_flow.py:88`），保留集 = 随稿冻结的两件（`STORY_SRC_FROZEN`）+ `materials.json` + `drafts/`。移入的三件各归一类，上面的树写明了：三件都是「留、不冻结」——契约在登记之后还要写，导入落点与分析件随材料演化，与 `materials.json` 同一性质。这一条是 R4。

**根下不再新增文件**：后续任何公共侧的新辅助件（含会议转写的证据与确认记录，见步骤 4）一律进子目录。

## 3. 改什么

### R1 · 路径常量改值

三个路径各有一个模块常量，改值即可：

| 文件 | 现在 | 改成 |
|---|---|---|
| `story_flow.py:66` | `CONTRACT = ("AR", "story-flow.json")` | `("AR", "story-src", "story-flow.json")` |

`RR/detail.json` 与 `SR/detail.json`（`story.js` 也写）不动——那两个目录下没有交付文档，不在本需求范围内。

### R2 · 消费者跟上

四类分开处理：

- **脚本读取**：`story_flow.py`（含 `:515` 写进契约的字面 `"AR/init-analysis.md"`，改成从 `ANALYSIS` 拼）、`flow-check.mjs`、`story-build.mjs`、`hooks/spec/post_check.mjs`、`hooks/shared/reader-review-task.mjs`、`materials.py:41`（`SOURCE_DOCS` 里的 `AR/upstream.md` 改成从 `import_sources.DOC_TARGET["AR"]` 取，材料指纹算它）。`story-build.mjs` 已有 `srcDir` 派生，契约路径挂到它下面即可。
- **合同与规则数据**：`contracts/story-chapters.json:32`（材料清单章允许的来源 `AR/upstream.md`）；`rules/spec-rules.overlay.yaml` 五处（第 49、84、91、99、105 行）——这是 framework verifier 按路径读契约的地方，第 49 行写明「无 `AR/story-flow.json` 本检查 SKIP」，路径不跟上，拆分边界一致性与读者审查的输入就静默跳过，四件套照样绿。**这一类离线测试不报，逐处改、逐处核。**
- **文档指路**：`SKILL.md`（含 `:251` 产物定位表）、`rules/init_analysis.md`、`rules/scope_gate.md`、`rules/ar_design_init.md`、`rules/inbox_import.md`、`hooks/spec/author.md`。作者照它去写文件，指错一层他会写到根下。**这一类测试不会报，要人工核。**
- **测试域**：`test/story/scripts/`（`check_failure_modes.py`、`run_multi_case.py`、`run_review_qualification.py`）与 `test/story/tests/` 下七份用例。

引用点规模（`grep` HEAD，不含历史方案）：`story-flow.json` 约 30 处在扩展内、18 处在测试域；`init-analysis.md` 9 处；`upstream.md` 8 处。其中相当一部分在注释与文档里——改不改不影响运行，但影响作者照着走。

### R4 · 清扫与冻结认得新住户

`sweep_story_src`（`story_flow.py:88`）的保留集加三个名字：`CONTRACT[-1]`、`ANALYSIS[-1]`、`materials.UPSTREAM.name`（`materials.py` 新增 `UPSTREAM = import_sources.DOC_TARGET["AR"]`，`SOURCE_DOCS` 也从它取；`story_flow.py` 只 import `materials`，不直接 import `import_sources`），与 `materials.MANIFEST[-1]` 并列——四件都是「留、不冻结」，名字从各自的常量取，不另抄一份字面。`STORY_SRC_FROZEN` 不变，仍是 `decisions.json` 与 `copyedit.md`。`story-build.mjs:182` 的注释说冻结文件名的真源在 `STORY_SRC_FROZEN`，保留集扩了之后那句照旧成立，不用动。

登记之后契约还要写 `story_written_at`、`story_src_digests`、`archived`，`reopen` 还要撤销它们——契约留在保留集里，这些路径才走得通。

### R3 · 根下的文件白名单

`story-build check` 加一条：登记成文时，`AR/` 根下的**独立文件**只有白名单里那四个。

**用白名单不用黑名单**：黑名单挡不住「以后又有人往根下写一个新文件」，而需求分册的完成条件第 2 条正是「相关流程不会重新向根目录写出辅助文件」——那是个持续成立的性质。

**只判文件，目录一律放过**：`story-src/`、`.review-backup/`、`assets/` 都是正当的子目录，限制它们没有意义。

报错要点名多出来的那个文件并给动作（挪进 `story-src/`）。白名单里 `detail.json` 要注明归属（对接层写的），否则下一个维护者会以为它漏收了。

**只在这一处守就够**：登记之前往根下写的只有公共侧（本步已全部挪走）；登记之后往根下写的只有对接层（`review.js:44` 建 `.review-backup/`，是目录，放过），归档后不再有公共侧写入。

## 4. 不做的事

- **不动对接层写的四样**（`design.md`、`review.md`、`detail.json`、`.review-backup/`）：改它们等于改内网合同，而内网那份是他们自己维护的。
- **不迁移已有产物**：`doc/features/` 下现有的 AR 目录保持原样。
- **不做历史兼容**：脚本不再从根下找那三个文件，找不到就按现有的缺件路径报错。
- **不改 `story-src` 的名字**，不新增第二层目录，不为收纳建通用的文件管理机制。
- **不动 `RR/`、`SR/`、`ux-reference/`、`assets/`、`inbox/`** 的布局。
- **不动交付文档的正文**：三份文档里的相对链接与图片引用与本次移动无关；`review.md` 的人工区一个字节不动。

## 5. 验收

| # | 判据 | 怎么验 |
|---|---|---|
| 1 | 跑完一轮，`AR/` 根下的独立文件只有白名单那四个 | 实跑后 `ls`；或夹具走完 init→round→关卡→complete→成文登记 |
| 2 | 三个移入的文件被原消费者正常找到 | 离线全量绿——脚本读取的引用点都在测试覆盖里 |
| 3 | 登记之后三件仍在 `story-src/`，契约续写得下去 | 夹具：成文登记 → `status` 读到 `story_written` → `archived` → `reopen`，每一步契约都在；登记日志里「清理中间件」不含这三个名字 |
| 4 | verifier 规则找得到契约 | 人工核 `spec-rules.overlay.yaml` 五处路径；用十跑产物挪好布局后跑一次 `check --deliver`，读者审查的输入清单里契约路径可读，拆分检查不报 SKIP |
| 5 | 往根下写第五个文件会被拦 | 夹具：在根下造一个 `notes.md`，`check` 点名它并给出挪去哪 |
| 6 | 对接层写的那四样不受影响 | 夹具：`review.md` 填过「审核结果：」之后重跑 `build`，那几句仍在；`detail.json` 仍在根下且可读 |
| 7 | 四道门 | 离线全量、失效形态 FAIL 0、`adapt-scan --check`、`framework/` 零改动 |

判据 1、3、5 是核心：挪对了、登记不把它们清掉、以后不会再散。
