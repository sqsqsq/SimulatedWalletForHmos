## 2. 安装与保护合同

维护安装与对外 adapt 的所有权保持不同：维护安装器整体复制本仓开发包（含本仓样板/替身），用于 demo/template；对外 adapt 保留目标知识、身份和按来源归属的对接。两个入口共用已核的原生物化能力，不把维护全包复制用于目标业务仓。

### 2.1 安装顺序

1. 读全源及目标配置，核实际 3.1 能力、active workflow、materialized_adapters、源完整性和覆盖面。输入缺失/损坏、明确冲突在写前集中报告。
2. 对外 adapt 合成候选 manifest：机制登记来自包，身份及知识登记来自目标；新装知识为空。归位实际目标 adaptation 数据。维护安装使用源包事实。
3. 按目标旧 manifest 的 target/source 核旧入口归属：目标与旧发布源相同才撤下；人工改写或缺归属依据报告冲突。旧 story-ext 段唯一成对且与旧 section 对应时可退出，区外保持。
4. 通过已核 buildAgentsTemplateVars/renderAgentsTemplate、inspectInstanceSkillBridgeArtifacts 及现有安装预检检查拟生成面，安全条件成立后按所有权写机制和元数据，退出已确认旧入口，调用实际 materialize。
5. 原生 verify、入口可达及所有权核对通过后返回 installed。原生检查报告需要写盘时在安装后的验证阶段执行，dry-run 保持只读。

D 核对还未闭合的人工覆盖操作必须停在冲突处；不静默覆盖、不用“安装成功后恢复”代替保护。已有安全目标上的机制复制、身份/清单解析及确定性测试可继续，不以缺某个预设计划函数名冻结全部适配。

维护 API 为 `install_extension(source, target, *, dry_run=False)`，移除 bridge_files 参数，CLI 保留 --source/--target/--dry-run。结果沿 InstallResult 的 status/version/target/planned/completed/failed/problems；0=planned/installed，2=前置失败且安装面零写入，1=写入中失败并给实际完成面。原生结果映射在 D 核对后由设计者写入本节；实施者不自造上游返回值。

对外 adapt 保留 --apply/--check、显式 --target 和既有 --package 语义，从已安装发布副本执行。--check 核机制、保留项和原生入口；缺口不能报整体成功。跟进由模型向人交回，部分完成/跳过不把 adapted_for 更新为全部完成。

### 2.2 元数据与失败

adaptation.yaml 为可读映射，adapters/adapted_for 为可选字符串。新装真实目标为 {}；stand-in 为替身，缺 adapters 沿既有业务来源语义；缺 adapted_for 表示未完成跟进，版本比较起点为 0。

升级一次性从目标旧 manifest 迁实际两值；新文件已有时读新文件，两处值冲突写前报告。运行只读新位置。知识路径/顺序/summary/audience 保留，坏登记报错，包的样板清单不覆盖目标。

template 写入失败即作废重建；正式 demo 失败停下，实施者按 Git 查看并恢复指定面再预检；对外失败列实际结果和原始错误，按目标版本管理处理。保持 1.9.8 简洁恢复纪律，不新增安装事务、运行日志或强制覆盖分支。

## 3. 知识入口与 manifest

knowledge-task 参数：`--project-root`、`--action`、`--audience` 必填；`--blueprint` 与 `--feature` 恰好一个。蓝图 action=discovery/design/questioning，Feature action 来自当前 workflow 的 spec/plan/coding/review/ut/testing；audience=author/reviewer。

```text
node doc/extensions/hooks/shared/knowledge-task.mjs --project-root <root> --blueprint <id> --action discovery --audience author
node doc/extensions/hooks/shared/knowledge-task.mjs --project-root <root> --blueprint <id> --action questioning --audience reviewer
node doc/extensions/hooks/shared/knowledge-task.mjs --project-root <root> --feature <native-id> --action plan --audience author
```

输出 Markdown 六块：当前动作与对象、激活知识及原文、有效事实与决定、当前契约与义务、本次完成条件、缺口与责任。discovery 可在蓝图不存在时取得知识；questioning 读取合法草稿，不要求依赖本次质询的准入已通过。Feature 按本阶段实际输入要求取原生结果，不一律要求后继契约。

退出 0 为完整任务；2 为参数/依赖错误；1 为坏身份、坏登记、所需来源缺失或引用失效。失败 stdout 不交半份任务，stderr 给对象、缺口、责任；所有动作只读。空清单合法且明示零项；未登记知识不读；已登记缺文件、坏 frontmatter 或非法形态集中报错。

原文按激活顺序完整提供，方法上下篇都可取并标明本动作用途；模型结合任务判断适用性。facts×halves 以知识文件为使用单位，保留 H2 锚点回查，不为每个方法小节强造事实决定。阶段间已成立判断随原生结果承接，不重复猜选型。

```yaml
schema_version: "1.1"
name: sample-extension
version: "2.0.0"
description: 需求与知识协作
provides:
  skills: [story, story-adaptation, story-knowledge]
  knowledge: []
  hooks:
    spec:
      post_check: [hooks/spec/post_check.mjs]
      pre_verifier: [hooks/shared/pre_verifier.mjs]
    plan:
      post_check: [hooks/plan/post_check.mjs]
      pre_verifier: [hooks/shared/pre_verifier.mjs]
    coding:
      post_check: [hooks/coding/post_check.mjs]
      pre_verifier: [hooks/shared/pre_verifier.mjs]
    review:
      post_check: [hooks/review/post_check.mjs]
      pre_verifier: [hooks/shared/pre_verifier.mjs]
    ut:
      post_check: [hooks/ut/post_check.mjs]
      pre_verifier: [hooks/shared/pre_verifier.mjs]
    testing:
      post_check: [hooks/testing/post_check.mjs]
      pre_verifier: [hooks/shared/pre_verifier.mjs]
  phase_rules_overlays:
    spec: rules/spec-rules.overlay.yaml
    plan: rules/plan-rules.overlay.yaml
    coding: rules/coding-rules.overlay.yaml
    review: rules/review-rules.overlay.yaml
    ut: rules/ut-rules.overlay.yaml
    testing: rules/testing-rules.overlay.yaml
phase_bindings:
  spec: &author_knowledge
    before_phase_work:
      - {kind: skill, ref: story-knowledge}
  plan: *author_knowledge
  coding: *author_knowledge
  review: *author_knowledge
  ut: *author_knowledge
  testing: *author_knowledge
```

该片段是已核 manifest 1.1 的基础登记示例，实际 name/description/knowledge 按所有权合成。A 的设计资产登记由基线核对后的真实消费入口决定，设计者在本节补入核实的资产键/路径或其他原生接线后，才能认定设计知识入口完成。不能仅登记原先建议的两键就宣称已送达。knowledge 字符串表示全 Feature phase；对象登记必须遵守原生 path/summary/audience 结构，不能丢 summary/audience 后仍称语义保留。

story-knowledge 从当前 phase 上下文取得原生身份，调用 author 任务。pre_verifier 使用同一加载器生成 reviewer 材料并经真实审前输入交给独立执行者；不再追加第二份 before_phase_verify Skill 导致重复材料。Blueprint 的要求页沿 A 核定的原生输入位置送达，blueprint id 明确来自本次设计请求。A 尚未核定时可完成纯加载器/身份/任务内容的定向验证，设计者不能把直接设计路径验收标为通过。
