## 1. 测试装配与终点观测

复用 run_multi_case/run_case、现有 Case、checkpoint/finalize 及回流机制。Framework 先按步骤 1/分册 06 接入 main 并同步 story/demo；测试只复制这个已核 Framework 基线，再把开发 Extension 装入隔离 template。不在每轮测试另换 Framework，不在 demo 上安装开发 Extension，不新增 runner。

在现有 Case 配置将 end_phase 迁为 `end_at`，形态固定为 `{kind: story|blueprint|design_handoff|phase, phase?: <原生phase>}`。phase 仅 kind=phase 时必填，其他 kind 禁止携带；旧 Case 配置一次迁移，不保留两份终点真源。CLI 的 `--end-phase` 迁为 `--end-at`（story/blueprint/design_handoff 或 phase:<phase>），一次覆盖在 suite 记录 requested/effective 两值，记录配置原值。所有 Case、帮助、交互规划、tests 及 config 消费者随同迁移。

| 终点 | 观测依据 |
|---|---|
| story | 对当前需求运行只读 delivery 检查；原生设计有效、basis 当前且审查可消费，不能用三文件存在代替 |
| blueprint | 显式 blueprint_id 的原生准入及当前有效投影；不创建 Story 或要求 CU |
| design_handoff | 原生设计准备结果：admitted、真实 CU/design_refs/readiness；不要求施工 |
| phase | 需求绑定下各实际 CU 的原生当前范围/输入及请求终点结果；必要 phase receipt 当前有效，合法复用按原生证据判断 |

Case 的业务需求标识继续用于材料与回流；直接 Framework Case 明确 blueprint_id 或原生 feature 身份，驱动器不靠目录名称猜。phase scope 中尚未形成必要 CU 时列设计准备缺口；多 CU 逐个显示身份、当前阶段及缺口，不能把其中一个 Plan PASS 当整单终点。没有新 Spec/Plan 但原生有效输入满足请求时合法闭合；资格判断读取原生结果，不复制 scope 推理或创建假回执。

状态观察增加 blueprint/需求交付摘要及 CU 列表；退出“目录出现即已进入 Spec”和固定三件套 artifacts_ready。保留原始观测，不把模型“完成”当原生闭合。conclude 仍是用户/宿主声明本轮观察结束，缺证据时记录未闭合，不冒充 target_reached。

回流按实际需求关联复制需求目录与被引用的蓝图/CU 工作区；不同名蓝图也带上源文件，保持项目内相对关系。回流目标仍为维护仓 doc/features，冲突沿既有逐文件/目录内容比较，不写 demo/doc/features。需求和蓝图同名时只复制一次。双检查点产物另名只用于维护归档展示，保留原始身份及来源关系，不改 Framework 文件内部引用。

### CLI 的阻塞判定与观察记录

按总览 §1.3，在正常业务中记录以下观察，不预写 PASS：设计作者及质询者是否在决定前读到必要知识；Story 独立审查是否由独立执行者完成且报告对应当前材料；CU 是否取得真实验收/契约与知识义务；交互续行是否在已有授权内沿正确对象继续。

每项记录触发请求、实际调用/输入、预期、实际、原始证据、对本轮终点的影响及最早失效处。失败先排查 Extension 接线和配置；属于本仓则修本仓，合法调用仍失败才形成 Framework 阻塞结论。只有不可继续的路径停止，独立路径继续；未覆盖项标未验证，未审查披露不等于独立审查能力通过。

不为等待 CLI 重复撞已知的非法字段或不存在的接口；这些先通过确定性检查定位。CLI 用于核实际信息送达、理解、应用和整体协作。本版结论止于实际 Plan 上限，后段能力不外推。

### 4.1 两个既有 Case 的 2.0 迁移

当前文件事实：auto-topup（系统单 AR90006）为 start_phase=story、end_phase=spec；car-key-sharing（本地单 ISSUE-206）为 start_phase=story、end_phase=plan。两个 case.yaml 都已有 after_initial=update；1.9.8 那次实跑没有执行 update，不代表 update 场景被删除。

按原业务验证目的迁移，不把“旧 spec”机械改成“新 CU spec”：旧第一个终点主要证明可送审的需求文档，第二个继续证明施工设计承接。

| Case | 2.0 初始终点 | 第一段过程与必查结果 | update 第二段 |
|---|---|---|---|
| auto-topup | `end_at: {kind: story}` | 系统取材、补图/会议、人工范围→冻结来源→蓝图准入→Story/Review→B 审查→按授权送审；在新需求零 CU 场景完成，不要求 Spec/Plan 或其 receipt | 保留新版需求与系统评审回稿，处理原口径冲突；真实裁定进入对应来源/蓝图，Story/Review 和审查同步，update close 成立；不自动施工 |
| car-key-sharing | `end_at: {kind: phase, phase: plan}` | 本地取材、范围/冲突→蓝图及人读交付→CU 准备→验收/施工输入补齐或原生复用；检查全部相关 CU 在本次 Plan 上限内的有效契约、知识义务及证据，保留一套 Story/Review | 保留 Review 人工区意见及安全口径冲突；更新需求/设计与受影响的已有施工设计，在 Plan 上限内恢复当前依据及必要审查；不运行 Coding/设备测试 |

两个 Case 的材料、图、会议、人工立场和冲突探针保留，需求编号只存在测试域；产品机制不依赖其名称。分解成几个 CU 由实际设计决定，不在 Case 答案里预填，不为证明多 CU 强制拆分。

prompt 用业务终点表达：自动充值维持“需求说明定稿送审，不开展施工”；车钥匙维持“需求说明定稿后继续完成可交开发的实现方案，到方案为止”。实施者须去掉车钥匙旧 prompt 中“产品源码按方案该改就改”的越出本轮上限表述，同步旧 test/story 路径说明；不在业务 prompt 点具体 Skill、脚本、字段或修法。

两条仍使用既有 initial→快照/评测/回流→同会话 resume-update→update 检查点链。initial 对第一条表示人读交付，对第二条表示 Plan 请求结果，不再统一解释为 Spec 三件套。两条 update 都需要实际关闭记录、当前交付资格和真实原话，模型说“更新完成”不代替检查。

第二条到 Plan 时，逐 CU 列出：身份与有效蓝图引用、验收/契约来源、实际执行或复用的职责、所需当前证据和缺口。有一个 CU 未满足本次请求即不报整单达到终点。没有新 spec.md/plan.md 时，仅当原生有效输入和请求结果已经满足才计合法复用；没有文件本身不能判成功或失败。既有 Story 设计事实与后续 CU 设计不一致时，先按步骤 3 §2.4 处理，再交回当前结果。

### 4.2 必要补充安排及证据边界

主 Case 保持两条业务主线，以下是补充安排，不把它们硬塞成每条主线必须出现的行为。真实执行仍待用户里程碑授权。

| 安排 | 输入与动作 | 证明及不能外推的部分 |
|---|---|---|
| 直接 Framework 设计 | 独立隔离工程，目标激活知识，从真实来源直接请求 component-design，终点 blueprint | A 在无 Story 流程时送达且影响设计；不生成 Story 记录，不证明 B |
| 无新 Spec/Plan 的复用 | 使用原生已校验、带完整来源的蓝图/CU/验收与契约，显式请求本次设计结果；输入过期时沿原生责任处理 | 有效输入能被实际执行者和知识任务消费，避免补空文档；预置有效产物只能证明复用，不能冒充该轮模型生成质量 |
| 多 CU | 使用实际设计确有多个施工单位的正常需求，检查共同设计、各 CU 知识及一套人读交付 | 验证需求级交付与施工拆分解耦；若两条主 Case 自然满足即可复用证据，否则设计者另给业务场景供用户确认，不由实施者制造分解答案 |
| 阶段与失败反例 | 结构夹具覆盖过期引用、少一个 CU、缺 must/角色、坏审查、恢复冲突 | 证明确定性消费者会拒绝错误，不证明模型理解或完整 Coding/Testing 能力 |

Coding/Review/UT/Testing 的扩展接线用对应离线合同验证保持；没有真实后段执行时继续标未验证，不因本版截止 Plan 而删除这些阶段职责。跨版比较按“人读交付质量”和“施工设计承接”分别比较，记录增加蓝图/独立审查的工作量，不能把新旧名称不同的阶段耗时直接当效率提升或下降。
