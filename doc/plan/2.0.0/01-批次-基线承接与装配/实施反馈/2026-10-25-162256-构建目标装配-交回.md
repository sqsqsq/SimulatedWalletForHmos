## 3. 实施中取得的事实与局部选择

1. **补丁工具的环境**
   - 用户主目录 `C:/Users/kangz` 本身是 Git 仓，`%TEMP%` 下的 template 会被它认领，`git apply` 会把补丁路径当作仓内子目录而跳过。
   - 全局 `core.autocrlf=true` 会让 `git apply`、`git archive` 把文件转成 CRLF。
   - 处理：装配时设 `GIT_CEILING_DIRECTORIES` 为 template 上级目录，并加 `-c core.autocrlf=false`；发布树改由 `git cat-file --batch` 原样写入。
2. **旧 Framework 的清理口径**
   - demo/framework 里有发布清单之外的旧本地定制（opencode `verifier.md`），只按旧清单删会残留，导致补丁新建失败。
   - 处理：除运行态（`harness/node_modules`、`package-lock.json`、`reports`、`state`）外全部移除，旧清单之外被移除的文件记入 `removed_outside_release`。
3. **物化清单的纳入方式**
   - smart-auto UPDATE 要求磁盘配置清单与命令行清单完全一致（`validateMaterializedAdapterSetsCrossCheck`），直接传 `dsh` 会在预检被拒。
   - 处理：按参考14“在消费 template 的 materialized_adapters 纳入 DSH，再原生物化”，只改 template 配置这一项（追加 dsh），再用同一清单 UPDATE。demo 的 7 个 adapter 保留。
4. **原生 UPDATE 的进程环境**
   - 测试进程带 `NODE_OPTIONS=--require …/ts_transpile_cache.cjs`。N 的 catalog 门禁把它判为进程注入（integrity BLOCKER），并要求清除后在干净环境重跑。
   - 处理：调用原生 UPDATE 时去掉 `NODE_OPTIONS`。
5. **旧扩展段**
   - N 的 UPDATE 把 AGENTS.md/CLAUDE.md 里 demo 已装 1.9.8 的 `story-ext` 段渲染掉了；6 个已登记 bridge 入口未被改动。
   - 随后开发源安装的写前核（O `entries.mjs`）通过，并按新渲染写回扩展段，所以不需要恢复旧文件。把旧文件恢复反而会让“去掉扩展段后与 Framework 渲染逐字相同”的核验失败。
6. **自查纠正**：第一次混跑出现 7 failed、18 errors，原因是本步两处实现错误。一是新反例类插在旧测试方法之前，把两个旧方法归到了它名下；二是原生 UPDATE 继承了 `NODE_OPTIONS`（即第 4 项）。两处修正后才有上面的读数。
7. **依赖**
   - N 与 demo 的 harness `package.json` 依赖声明相同，只多一条 scripts 项，沿用 template 带的 `node_modules`。
   - 依赖声明不同或缺依赖目录时，装配停下，不现装依赖。
