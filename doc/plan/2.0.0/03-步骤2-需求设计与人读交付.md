## 2. flow 身份、字段和命令

所有持久化仍由 flow.state/load/save 写入；schema 5 是新单合同，旧单报版本不支持并指向 1.x 收口或 init 重起。

| 字段 | 内容、生产者和有效性 |
|---|---|
| design_binding | `{component_id,blueprint_id}`；bind-design 首次写入，重复同值字节不变，其他值冲突 |
| input | `{snapshot_ref,snapshot_sha256,materials_digest,candidate_sha256}`；complete 全部成功后写，指完整冻结输入 |
| story_basis | `{blueprint_ref,input_sha256,knowledge_sha256,files}`；story 登记实际设计、输入及被审材料路径→完整原始 SHA-256；集合按 §5，含 Review 人工区和稳定决定投影 |

原生完整 blueprint_ref 包含 artifact/component_id/blueprint_id/revision/source_fingerprint/artifact_sha256/target；target 为整蓝图对象。不得只记录 revision 数字。snapshot_ref 为项目相对 snapshot.json 路径；snapshot_sha256 是该文件原始字节的 64 位 hex，candidate_sha256 是候选稿原始字节的 64 位 hex，materials_digest 保持现有比较口径。input_sha256 等于实际引用 input.snapshot_sha256；knowledge_sha256 为有序激活登记及知识字节摘要的确定性 JSON 摘要。files 排除登记与审查历史等非对象记录，集合见 §5。

```text
python doc/extensions/skills/story/scripts/core/story_flow.py bind-design --project-root <root> --feature <需求> --component <组件> --blueprint <蓝图>
python doc/extensions/skills/story/scripts/core/story_flow.py complete --project-root <root> --feature <需求> --from AR/story-src/design-draft.md --input AR/story-src/design-input.json
python doc/extensions/skills/story/scripts/core/story_flow.py status --project-root <root> --feature <需求>
```

命令中的 --feature 只指需求目录。bind-design 需要 init 后的 flow；标识调原生安全段检查。需求材料目录与蓝图工作区使用不同的身份和目录；新需求建议 blueprint_id=`bp-<需求标识>`，调用者必须显式传值并按原生安全段校验。已有蓝图须核实际 component/blueprint 及目录分离，不按名称扫描。无蓝图允许绑定明确的新对象，后续读到归属不匹配立即失败。bind-design 写入前拒绝需求与蓝图使用同一目录，保留需求的 ux-reference 材料位置；身份冲突交调用者选择，不自动改绑或搬 Framework 文件。绑定后不自动改绑，错误绑定通过重新起单处理。

complete 不覆盖 AR/design.md，候选提取稿保留 extracted_analysis 来源；覆盖上游原文的旧 overwrite/backup 专用路径退出。同一候选、采用集合及人签版本复用 input；材料内容变化需在 update 或 reopen 后重确认，不允许悄悄换输入。

命令成功退出 0、stdout 沿现有 JSON；参数错误 2；前置/身份/来源冲突 1。失败保持原 input/basis，status 全程只读。

## 3. 状态与合法动作

flow 不保存 Framework 准入、当前 revision、CU 或施工状态副本。每次通过总览薄读取器取得真实结果，按下表由上到下派生；工具故障单独报读取失败，不推定“尚未设计”。

| 派生状态 | 条件 | 合法下一动作 |
|---|---|---|
| gathering | 当前轮材料未确认 | round/decide；complete/story 拒绝 |
| scope_pending | 材料已确认，必要范围/会议决定未定 | analysis/decide；complete/story 拒绝 |
| input_ready | 当前确认完成，无对应有效 input | bind-design（若缺）→ complete |
| waiting_for_design | input 有效，蓝图不存在或尚未 admitted | component-design 继续；story 拒绝 |
| ready_to_write | 原生准入和投影有效，无历史 basis | skeleton/chapter/check/review → story |
| needs_sync | 有 basis 但输入、正文、人签、设计引用或知识不匹配 | 当前返修或 update；重新审查并登记 |
| registered | 所有依据及人读件与 basis 匹配，当前审查可消费 | 交付选择；重复 story/status 不换对象 |

update 活动优先显示 update_inputs/update_open/restore_conflicted，并同时给出上述主状态。错误输入和读取故障高于状态推断，不自动回退旧来源。

reopen 的职责是重开本轮需求范围决定，在初始和 update 中都合法；保留蓝图绑定、冻结输入、人签历史及旧 basis，明确旧 basis 暂不可交付。reopen 不自动关闭 update，也不要求调用者先伪造一次 close。重新确认后 complete 生成新输入，设计负责人处理实际影响。

registered 重复 complete：同输入幂等；不同输入拒绝直到开启合法更新/重开。needs_sync 可返修后再次 story；story 失败不改旧 basis。跨会话读取当前文件、flow 和原生对象续行，不能凭聊天记忆重设状态。update close/restore 的条件唯一在步骤 3。

## 4. 采用输入、冻结与物化

### 4.1 候选输入

模型基于本轮 materials.json 和真实确认写 `AR/story-src/design-input.json`：

```json
{
  "adopted": ["RR/prd.md", "AR/design.md", "assets/flow.svg"],
  "human_decision_ids": ["scope-confirmation"],
  "scope_items": [
    {"item_id":"request-main","kind":"requirement","source_path":"RR/prd.md","authority":{"owner":"需求负责人","formality":"formal_requirement"}},
    {"item_id":"scope-ruling","kind":"invariant","source_path":"AR/story-src/human-decisions.json","authority":{"owner":"需求负责人","formality":"formal_requirement"}}
  ]
}
```

adopted 每项必须属于本轮确认版本且仍为相同字节；不采用项在提取分析说明理由，完整性由设计/人读审查判断。human_decision_ids 解析到真实 ask/gate 记录；脚本导出原话、所选项、身份和原位置到冻结集合内的 human-decisions.json，不让模型手填。该路径是冻结导出名，不覆盖工作区原件。

scope_items 的语义身份、类别、正式性及 owner 来自原始材料或实际人签；只有路径/摘要等机械字段由脚本生成。来源不足保持 unspecified/缺口按原生规则处理；本地文件经 builder 规范化，系统来源生成原生 materialization。

### 4.2 唯一冻结模块

`materials/frozen.py` 定义选集、路径、摘要和复用。选集=adopted+候选提取稿+真实人签导出；原件的本地相对图/链接必须闭合在选集内，缺引用报告具体路径，不自动搜同名图片。外部链接保留实际地址及可用性事实，不作为本地文件复制。

目录为 `AR/story-src/inputs/<64位hex>/`，内部 `files/<需求相对路径>` 按原始字节保存。snapshot.json 含排序的 `{path,sha256,role,provenance}` 文件行、scope_items、human_decision_ids、observed_at。role=original/image/human_record/extracted_analysis。provenance 来自实际材料登记或真实人签导出，随摘要参与版本身份。

ID=除 observed_at 之外完整 snapshot 内容的 UTF-8、键排序、无多余空白 JSON 的 SHA-256；文件原始 SHA 与现有材料归一化/短摘要分别命名，不混用。原生字段要求 `sha256:<hex>` 时由统一序列化加前缀；目录名仅 hex。读取冻结版本时共用 frozen.py 的只读核验，逐文件复核边界、存在性和字节，不只核 snapshot.json。

先在 inputs 下临时目录完整写入、复核文件与引用，生成完整 snapshot，再改名为最终 ID；现有相同 ID 核全部内容后复用，损坏报错。系统单在完整冻结目录内生成 materialization，source_ref 指已落盘的最终 files 路径，然后执行原生来源检查；本地单核同样的来源闭包。只有检查成功才写 flow.input 并输出可交设计的入口。目录存在仅表示候选字节完整，调用者只消费 flow.input 登记的有效版本。校验失败保留候选与诊断，旧 input 不变；重试先复核完整字节再重验。临时目录或未登记的失败候选均不作为有效输入。

本地输入请求交给 builder 的是最终文件位置及源清单，builder 形成原生 currentScopeItem；不另外造 provider manifest。已被设计引用的版本不覆写、不删除；更新采用新版本。

### 4.3 原生字段来源

| 字段 | 来源 |
|---|---|
| artifact | 原生 requirement-source-materialization@1 |
| component_id/blueprint_id | 已校验的 design_binding |
| item_id/kind | 模型从采用依据提取的稳定语义身份及原生类别 |
| source_ref、source_sha256 | 冻结文件项目相对 POSIX 路径、原始字节 SHA |
| provenance.source_kind/extraction_method | 实际来源与转换；人签=recorded_user_reply，派生稿=extracted_analysis |
| provenance.source_ref | 与顶层实际冻结文件一致 |
| observed_at/source_revision | 保留可核的来源观察时间/版本；仅能证明冻结时读取时明确标本次文件观察，不冒充原取得时间。各人签保留原 at。重复导出复用，缺可选版本省略 |
| evidence_strength/authority | 来源事实与实际权限；文件读取可标 observed，分析为 inferred，authoritative 须有实际权威依据。不得按 original/image 类别升级权威；source_evidence 与有效人签规则见本轮评审 R3 |

多材料验收：正文 RR/prd.md 引 `../assets/flow.svg`，人工范围另有一条真实决定；冻结保留原目录结构及两类身份。改正文字节触发 hash 失败，删图片触发闭包失败，伪人签 ID 被拒；图片作为正文资源，不伪造成独立 requirement。

## 5. 成文来源、审查与登记

### 附录替换

章节合同以具名读取器替换固定 from 章号，生成与校验共用读取器。先原生校验完整蓝图及 admission，核 discovery.inputs.current_scope_items 已消费本次冻结 scope_items 的身份、路径与原始摘要，再核投影对应相同字节和 revision；投影过期由设计职责重新生成，Extension 不手改 derived_from。

| 旧来源 | 新来源 | 渲染与缺失行为 |
|---|---|---|
| Spec 术语 | discovery.facts 的 term: 事实及 provenance | 术语章；缺真实解释回来源，不用模块名代替 |
| Spec scope/9.1.5 | development 节点/module、architecture_impact 决定及需求侧业务范围 | 改动边界；明确未改项保留有据说明 |
| Spec 9.1.1 接口 | canonical contracts 的实际 operation、DTO、mapping、errors、idempotency、nfr 内容 | 接口附录；已触发但缺设计的交设计责任 |
| Spec 9.1.2 数据 | runtime flows 的 data_domain_refs/source_of_truth/state_owner/failure_recovery 及实际契约 | 数据附录；已有隔离/有效期/清理设计保留 |
| Spec 配置、事件、专项 | 对应原生对象的实际字段，原生未承载的明细使用 story_details | 配置/事件附录和专项正文；尚未形成施工值明确后续责任 |
| Spec 知识表 | knowledge_application decisions | 按真实判断渲染理由与落点，缺判断明确缺口 |
| 材料清单 | snapshot 与 materials 来源记录 | 分别展示原件、派生稿和实际采用版本 |

`story_details` 只用于原生 node/flow/contract 已形成而原生字段未表达的精确内容，形态为 `{id,kind,title,body,evidence_refs}` 数组，kind=data_policy/configuration/event/special_design。由蓝图设计作者写入 canonical 并经原生修订；Extension 不另写设计文件。body 为完整 Markdown，渲染逐字比对；该对象地址与 evidence_refs 必须可查。已有原生字段不重复搬入 body。不存在条目不由脚本推断不适用，由语义审查核需求完整性。

### 独立审查

`rules/story-reader-rules.yaml` 为 Story 判据唯一位置；reader-review-task.mjs 为唯一任务生成器。章级、议题、会议、人签、图片、来源、知识及整体叙事要求保留。Spec overlay/pre_verifier 退出 Story 专属判据，只负责当前阶段。

Extension 内部入口为 `story-build review --feature <需求> --project-root <root> --action prepare|check`；真实原生接线、报告目录和结果消费唯一见 §5.1。prepare 前先完成 project/number/build 并作结构检查，使被审对象成为最终人读版本；登记阶段只读核对后一次保存 basis。接线错误属于 input_invalid/tool_error，只有实际宿主能力缺失才可为 reviewer_unavailable。

对象材料：Story、Review 当前机器区和人工区、有效决定的稳定内容、写作设计、采用 snapshot 及图片、当前 canonical/投影、知识原文及激活登记、章节合同、读者判据、稳定结构检查结果、实际读者任务。决定/任务生成时排除历史报告路径、运行日志和时间字段，防止回显上一报告改变新对象。

排除：审查目录历史、flow 自身、登记/归档时间、调用次数、报告 ledger 和本轮状态记录。含这些字段的混合文件先由既有责任模块生成稳定内容投影，投影与原记录可回查；不能整份 hash 后声称时间不影响对象。

| Extension 对实际原生结果的归一语义 | 交付动作 |
|---|---|
| pass，结构通过 | 可登记交付 |
| warn，blocking_findings 为空 | 带 advisories 交付，不因建议无限重审 |
| fail 或有 blocking_findings | 阻断，回作者/设计等实际责任 |
| report_missing/invalid/subject_stale | 保留原回复，重新准备或修真实输入，作者不改审查结论 |
| reviewer_unavailable | 明示未审，消费既有明确授权；无授权时请用户选择，不自称 PASS |
| input_invalid/tool_error | 阻断并报告实际工具/来源缺口 |

story 登记前重核所有源及当前 check 对象，成功才更新 basis；失败保留旧 basis 并派生待同步。登记自身不重投附录、编号或重渲染 Review，不产生新的 subject。正文、人签、设计、知识或判据变后重验，只有报告/登记时间变化保持对象。改章不损伤其他章，Review 人工区按既有保护处理。

### 5.1 B 的实际调用合同（Framework 3.1.0）

核对发布件 source_commit=074a4c3c4a0591c8ed2162e2a0d048a1fdec081f。必读原生材料：`framework/docs/operations/request-harness.md`、`harness/scripts/utils/{capability-resolution-entry-input,request-phase,context-facts,report-generator,markdown-parser}.ts` 与 `harness/scripts/check-review.ts`。本节选用已有无 Feature review request，不使用 Feature verifier 短 request，不新增通用审查调度或验真框架。独立执行与语义有效性留给真实宿主验证，不能把准备接口可调用写成已审查。

**职责和落点**

- `reader-review-task.mjs` 生成 Story 专属任务，提供 §5 的全体材料及原文路径。任务明确区分待审 Story/Review 与只读对照来源，包含采用版本的实际图片、知识激活集合与知识原文；不能只列当前 RR/SR 而遗漏设计采用的冻结版本。
- Extension 的 `prepare` 完成最终渲染、稳定材料投影、结构检查，并生成原生 request JSON；不代写 Research facts 或审查结论。混合台账的稳定投影由所属模块生成，保留有效人签/决定及原记录定位，排除登记时间和历史报告。正文与 Review 人工区直接计原始字节。
- 请求文件留在需求侧 `AR/story-src/review/request.json`，任务在同目录 `task.md`。以 §5 对象的排序路径与完整 SHA-256 列表计算材料键，用于选择本次报告目录和重入；材料键不是原生 request 身份。任务正文不包含本次报告目录/材料键，避免摘要循环。
- 默认报告目录 `doc/reports/story/<需求标识>/<材料键>/`。可用 `--report-dir <项目相对路径>` 明确替代；两者都经原生路径保护，若与自定义 features_dir 等保护面重叠，prepare 报错要求显式合法目录，不静默搬家。原生 `request_sha256` 由 prepare 输出取得，Extension 不重实现算法。
- 请求的报告目录、路径与原生准备输出记在 `AR/story-src/review/prepared.json`，这是本次原生调用结果的记录，不参与被审对象。重入先重算材料，再按记录重新运行原生 prepare 核 request_sha256；不能只看 prepared 文件存在。

**原生请求和命令**

```json
{
  "schema_version":"1.0",
  "phase":"review",
  "requested_result":"按任务文件独立审查当前 Story/Review 的业务完整性、来源、人签及知识应用",
  "targets":{"files":["<Story>","<Review>","<task.md>","<其余实际对象材料与稳定投影>"],"tests":[]},
  "baseline":{"head":"WORKTREE"},
  "inputs":{"review_report":"<报告目录>/review-report.md"},
  "allowed_test_writes":[]
}
```

files 实际展开为去重排序的项目相对路径，包含全部被审与对照材料，不把占位字符串落盘；无 Spec/Plan 就不设 contracts/acceptance 输入。原生对文件原始字节绑定，图片同样进入 targets（独立执行者通过宿主看图能力读取，不用 UTF-8 解码代替看图）。不传 Feature/Goal 参数，baseline 不用 HEAD，防止无关提交改变对象。

在 `<root>/framework/harness` 执行：

```text
npm run check -- --project-root <root> --phase review --request-file <需求路径>/AR/story-src/review/request.json --report-dir <报告目录> --prepare-request
npm run check -- --project-root <root> --phase review --request-file <同上> --report-dir <同上>
```

Extension 可从共享薄访问器直接调用同一发布件 `request-phase.ts:runExplicitRequest({projectRoot,frameworkRoot,args})`，参数键与上述 CLI 相同；统一一条调用路径，不能复制其校验。prepare 输出含 request_sha256、bindings、baseline、factsPath、inputs、gaps。退出 0 仅表示请求已解析：首次缺 facts/review_report 是预期的待产物；目标缺失、保护目录冲突、能力禁用等必须分类报出。不得把所有 gaps 一概当审查者不可用。

**独立执行与原始报告**

宿主主模型按自身已有的独立上下文委派能力，将任务文件、原生准备输出和完整材料入口交给与作者隔离的审查执行者。沿原生 request-harness 的 Research/报告协议工作：执行者实际读取材料，按原生 P1 形成 `<报告目录>/context/facts.md`（schema_version=1.1、request_sha256=本次输出、established_by=review，不写 feature/run_id），报告采用原生 review 章节、问题表和结论声明格式，并回答 Story 判据。不投递到仅接受 Feature verifier 短 JSON 的专用入口，不要求作者手造 Feature 身份。

宿主保留实际委派/返回证据，将回复原样落为 `<报告目录>/review-original.md`；原生检查用的 `review-report.md` 由该原文逐字复制。理由：原生 check-review 的统计修复可改写工作报告，原始回复必须保留；original 是唯一原回复，工作报告只是检查副本，两者都不让作者改写结论。缺独立执行能力时报告宿主实际缺口，已有明确未审授权才进入降级；尚未实现适配器不能使用这条降级。

**check 与结果消费**

1. 重新核 §5 对象及原生 prepare 的 request_sha256；与派审时不同先报 subject_stale，保留旧报告，重新 prepare 使用新材料目录。只有登记/报告时间改变不改变对象。
2. 原始回复或工作报告缺失为 report_missing，不能写 reviewer_unavailable。运行原生正式 request 检查；读取本次 stdout 及 `summary.json`、`script-report.json`，核 subject=request、completion_target=request、phase=review、request_sha256 相等和 summary.evidence.script_report_sha256。报告的实际 binding 从 input_bindings 取得，以原生 readBoundInput/解析器验证，不能只相信一条自述 PASS。
3. 原生 CLI 输出 `{subject,request_sha256,verdict,report}`，PASS 退出 0，其他 verdict 退出 1；解析/路径异常可能没有 summary。缺当前合法 summary 属 tool_error/input_invalid，不能沿用旧文件。
4. 原生检查通过后，使用原生 markdown-parser 的 getSectionContent、extractDeclaredVerdict、extractTables 读取实际工作报告：结论“通过”且无阻断为 pass；“有条件通过”且原生检查允许、无未关闭阻断/MAJOR，或只有非阻断建议为 warn；“不通过”或有阻断为 fail。原生 negative_verdict_closure/conditional_pass_closure 的失败是业务阻断；报告章节/计数/引用/格式失败为 report_invalid；来源/材料变化优先 subject_stale。遇到未识别失败保留原生 checks 并阻断，不能把所有退出 1 都说成业务失败或能力缺失。原生 verdict=FAIL 或未声明 not_applicable 的阻断 SKIP 不能经检查 ID 白名单被改判为 pass/warn；当前 issue_to_file 不识别 Markdown 的局部缺口按专项 Framework 反馈处理，不在 Extension 豁免。
5. 交付门只消费当前对象的这些结果。原生 summary PASS 证明结构/绑定，不证明审查独立或业务无遗漏；后者以实际委派事件、阅读和报告内容在 CLI 核实。同对象且报告和 binding 有效则复用，重新登记不派新审。

同一材料目录的原生机器报告不被人工覆盖；材料变化走新目录，报告历史保留。本路径不创建 receipt、不改变 CU/Feature 状态，不追加下一阶段。
