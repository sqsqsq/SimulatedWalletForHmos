## 2. 1.9.9继承与新增能力保持

下表规定最低盘点面与保持结果，是本版能力保持清单的责任来源。每行可按实际职责拆项，须登记：固定提交/合同及实际符号、当前实现状态、测试/真实运行/用户审定/发布证据分别到哪、原缺陷或限制、应保持的可观察结果、待定新承担者、对应验收。今天可核固定开发源，尚未逐项完成的标未盘点；正式发布后核差额。不得将本表存在或spec承诺等同于能力已实现。

| 能力面 | 必须保持和独立检查的结果 |
|---|---|
| 取材与本地单 | 系统材料拉取、查无此单及本地材料入口分别有效，来源身份、需求范围和缺料恢复不丢失 |
| 关卡与授权 | 材料确认、会议逐议题裁决、范围/承载、术语及推进边界、归档/恢复授权按适用条件执行，不重复问或跳过人签 |
| 收件箱与材料清单（R1/R2） | 相对路径身份、同名不同目录、递归导入、冲突预检、原件集合与贡献说明贯通update |
| 完整叙事与页面交互（R3） | 独立读者能沿业务及页面/操作理解条件、异常、恢复、验收与交付，技术查阅有出口 |
| 图文与SVG（R1/R4） | 原图来源、表/图承接、选型、阅读切换及资源交付按最终发布合同保持；金样先改的期望单独标记 |
| 三类知识及六阶段 | 项目事实、规约、模式在动作前送达，知识影响设计实体及适用的spec/plan/coding/review/ut/testing产物；改入口不丢作者任务与审查输入 |
| Review与独审 | 人工区不代填，意见/事实/建议/裁决分开；稳定对象、原件、格式恢复、warn及视觉限制均有处理 |
| archive/restore | 正文/附件、授权、覆盖与恢复一致；二进制资源的真实发布支持边界明确，不冒称系统完整上传 |
| update、续接与撤回 | 新材料、反馈、人新决定、直接改稿、会话中断、同名换版与新轮次可恢复，人工区/历史身份保持 |
| 后续开发闭环 | plan至testing的阶段责任、知识义务及验证保持；只验Story不能签全部生命周期 |
| adapt（R5） | 首装/升级所有权、知识适配、盘点/独审、状态/ignore保护及成本按发布实态保持，不自动扩入三目录分发 |
| usage/stats（R8） | 初始化元信息、阶段自动采集、补采/对账、Git关联、并发与成文均有消费者；新蓝图/多CU不重复计同一需求或漏阶段 |
| 稳定性与快速恢复（R7及后续轮次） | 帮助/公开命令、参数写前检查、完整诊断与未执行判据、登记顺序、部分成功与恢复入口不退化 |
| 金样与宿主装置（R6及公共能力） | 新正本、来源/模拟前提与未决保持；宿主忠实投递、幂等、冲突写前拒绝和部分写入恢复有效 |
| 安装与宿主发现 | Story、adapt、stats及实际需要的知识Skill由支持宿主正常发现和调用，原生物化接替bridge须验实际入口 |

状态至少区分：已发布且须保持、发布前待核、已有缺陷、目标架构待定、明确后续范围。已发布能力不得静默删除；发布前承诺与缺陷记录须有去向，跨版本迁入或改变范围由用户确定，不自动扩大2.0.0。

来源核对要从发布README/SKILL/manifest、有效规格及最新交回/测试两向检查；1.9.9的旧spec头部可能落后于后续提交，不能让旧摘要盖掉已发生事实。已核例子：`f5972a82:extensions/manifest.yaml`登记story-stats与story-view/usage阶段hook，故统计与阅读视图不能只按正文功能处理。
