- 没有可核发布件：立即交回查到的实际 main/清单、缺少的具体发布输入及其取得情况。设计者负责核实版本交付来源并形成接入决定；实施者不自行用源码目录充当发布件、不改 version 冒充升级。此时只阻止实际复制/安装，仍可核对来源与阅读原生合同。

本轮实际取得的是 main 接入提交及其中发布清单，1225 个文件均已核对；不再索取额外 zip 作为重复前置。后续接入若 main 尚无目标发布件，再按上述分支取得真实输入。历史源码观察的本地 zip 描述不替代交付证据。

## 2. 将 3.1 接入本仓 main

在 main 的隔离工作区执行，先核工作区归属与干净状态；保留 story 当前未提交的方案，不切换它去覆盖工作区。复用合适的已有工作区，必要时按宿主的工作区工具创建。main 的旧 Extension 清理已经放弃，本任务不恢复该清理。

输入必须具备：真实包位置与摘要、version/source_commit/built_at、清单及 MIGRATION；清单版本须为实际 3.1 系列。核包摘要与交付清单，记录选用身份。

接入顺序：替换 main 的 framework 发布面 → 按该发布件 framework-init UPDATE 更新必要配置及宿主生成物 → 检查实际 diff → 原生 Framework 测试及相关接入检查 → 提交 main 的接入结果。推送按用户对该任务的授权执行，不强推分支。

所有权：只改发布件目录、MIGRATION 所需配置字段及宿主生成入口；不复制包外业务代码、不覆盖目标知识、不删除 main 的旧 Extension 源。UPDATE 与旧扩展入口发生冲突时保留人工现场、报告实际文件和责任；不能通过清空知识或关闭门禁得到成功。

原生 Framework 校验与旧 Extension 兼容性分别报告。UPDATE 若因旧扩展 manifest/入口合同停住，保留原错误及当前入口，把受影响的扩展物化列为后续适配项；不得伪报 UPDATE 全部成功，也不得清空旧包来换绿。已正确装入且核验通过的原生发布件可以独立交回；未完成的入口不作为可调用前提。真正的框架输入损坏、发布件校验失败或必需配置缺失须先解决，不能提交为框架接入完成。

输出：main 的明确接入提交、发布清单身份、必要配置/入口差异、原生验证及旧扩展兼容性观察。不得把整个分支合入 story 作为替代。

## 3. 从 main 同步到 story 的 demo

固定 §2 完成的 main 提交 M。若远端后来变化，本轮仍用记录的 M，更新来源需另记差异。开始前 demo 的非忽略改动为空；story 的方案修改保持。

| main 来源 | story 目标 | 操作 |
|---|---|---|
| M:framework/ 中的已交付发布内容及清单 | demo/framework/ | 按发布清单替换；清除被新发布件退出的旧框架文件，不携带依赖/缓存/运行状态 |
| 新发布件的 MIGRATION 和 UPDATE 指令 | demo/framework.config.json 及实际宿主生成面 | 用 demo 自己的配置/业务事实执行 UPDATE，按必要字段更新，不整份复制 main 工程配置 |
| 原有两处 OpenCode 装置定制 | 新发布件对应文件及 demo/.opencode/agent/verifier.md | 按根 AGENTS §2/6 在新文件上重加；除这两处不保留旧框架补丁 |
| demo 中物化后的 verifier 装置 | 根 .opencode/agent/verifier.md | 按现有维护协议逐字节同步 |

保留 demo 的业务内容、知识与已安装 Extension 1.9.8 的版本身份。同步后 demo 的 Framework 已是 3.1，Extension 尚在适配：明确标为“框架接入基线，组合尚未验收”，不能对外推荐为已发布的 Story 2.0。可用的 1.x 产品线由 story-1.0 保留；不为了保持 1.9.8 组合而继续让 story/demo 停在 3.0。

保护旧扩展入口：先按它实际 manifest 与生成来源识别归属，框架 UPDATE 引起的冲突按根协议逐项处理，不批量重装开发扩展、不清理未知入口。旧扩展造成的物化未完成与原生框架配置缺失分开交回；后续新包安装接替旧入口时由步骤 1 的安装合同完成对应物化。实际缺失的入口不能在核对报告中标为可用。

核对每个发布文件与 M 的清单对应；两处定制单列，其他差异须有发布说明依据。`check_framework_drift.py` 只比较版本及展示来源，不足以证明文件一致，另保留清单逐文件比较结果。失败保留现场，由实施者按 Git 对指定接入面恢复，不能影响其他任务。

输出：main 同步基点 M、story 接入提交、demo 前后身份、清单核对、两处定制与生成入口差异、验证结果及组合边界。Framework 基线达到这一交回即可评审，不等 A/B/C/D 全部定案。

## 4. 基于已同步 3.1 的能力核对

只读实际 demo/framework 的公开文档和代码，在隔离 template 做必要定向验证。源码检索与纯确定性例证可以执行；真实 CLI 仍按 TEST 里程碑授权。不能因目录里有文档就判模型实际送达。

| 项 | 首先核已有能力 | 交回正常/异常事实 |
|---|---|---|
| 基础蓝图 | component-design、来源物化、投影/反馈、identity/resolver、施工派生、component-closure | 实际命令/函数存在且输入可解析；坏身份、过期引用按原生结果失败 |
| A | skill_assets、设计发现入口、独立质询材料装配 | 作者和质询的真实输入位置；直接入口与 Story 路径；未登记和登记缺文件 |
| B | 原生 verifier、无 Feature request、任务/材料装配、报告验真及复用 | 能否审人读件而不制造 Feature；实际身份、状态/退出码；内容变化、报告坏/缺失、能力缺失 |
| C | 原生契约实体、文件授权和扩展字段、derive/物化/复用 | 哪些真实义务/角色可直接承载；哪些会被丢弃或拒绝；相关完整链及错误路径 |
| D | extension inspect/materialize、renderer、ownership 及安装器现有预检 | 无变更/正常生成/人工内容/冲突/部分失败；是否已有可复用的只读计算和保护 |
| interactive | 无 run 的 prepare-scope、阶段执行、CU 完成与整体结果消费 | Skill 指令与真实调用是否一致；不以创建 Goal 或私有循环绕过差异 |

交回放到当前 plan 的实施反馈目录；日志/材料放 output/story/2.0.0/<实际任务>/，临时副本在 output/scratch/。报告逐项写：输入和实际发布身份→原生生产者→结果→消费者→相关失败→证据；“已有可用”“缺 Extension 接线”“确有 Framework 缺口”分别标明，不只列缺文件名。

## 5. 设计者裁定及后继实施

收到 §4 交回后，维护设计者在总览/对应分册直接锁定实际命令、字段与失败映射，删掉已被现成能力替代的提案。实施者不自行选择知识权威、审查协议、文件职责载体或覆盖政策。

已有能力足够：按真实接口接线并实施相应 Extension 功能。需要 Extension 自有调整：由设计者补齐消费者合同，保留普通局部编码选择。确有原生能力缺口：给实际反例、必要性、最小改动与验收，并精确圈定待完成部分；Framework 维护者在自身责任域交付，随后经 main→story 同一路径更新。其他已闭合部分继续。

首个允许交回的成果是 3.1 基线取得/接入，不是四项上游“接受表”。只有当前仍缺真实发布件时，实际安装暂不能进行；报告这一项即可，不能再以所有新增接口未交付为全版开工门。
