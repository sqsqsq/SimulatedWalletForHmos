## 1. usage 并发「四条只剩三条」：查清与处理

先把用例改成保留每次调用的退出码、stdout、stderr 与最终记录，再用同样做法压测（`output/evidence/2.0.0-rewrite/batch3-03/`）：

| 取证 | 结果 |
|---|---|
| `usage-stress-1.json`：40 轮 × 4 个需求同时 begin，12 个 CPU 负载进程 | 1 轮 2 次调用报错 |
| `usage-stress-2.json`：200 轮，24 个负载进程 | 8 次调用报错 |
| 报错内容（全部） | `os.replace` 把临时文件换成 `doc/features/.usage-state.json` 时被系统拒绝（`WinError 5`）；调用照实返回 `ok: false` 与「重跑原操作即可补记」，进程没有崩 |
| 记录完整性 | 所有异常轮里成功的调用的记录都在，没有出现成功写入被别人覆盖 |
| `replace-probe.json`：单进程、无并发，照 `write_json` 的做法反复「写临时文件 → `os.replace`」3000 次 | 14 次被拒（`PermissionError 13`）；同目录「临时目录 → rename」3000 次 0 次 |

结论：这不是调用失败、锁等待或并发覆盖。本机有我们之外的进程短暂占着刚写过的目标文件，替换被拒；原因进程没认出来（杀软或索引只是推测）。冻结 `staging.rename` 的 `WinError 5` 是同一类「替换刚写过的东西被拒」，单进程探针这次没复现改名。

压测之外，循环跑改过的用例暴露了一个**真实产品缺陷**：被拒发生在记录已写进 `usage.json`、清运行态那一步时，这次调用在写身份件（`.usage-id`）之前就返回了；重跑认不出已有节点，另起一个同编号节点，又因「同编号旧节点是否已提交判不了」报错。旧用例只数最后的条数，看不出这件事。

**修复**（`skills/story/scripts/core/usage.py::record`，最早责任处）：身份件与已接收输入的写入、删除挪到 `usage.json` 落盘之后立即做，在清运行态之前；`changed` 同时置真。清运行态再失败时待写行留在运行态，下一次按它赋值不重复累加（原有语义）。没有加重试或锁。

用例：

- `WriteProtection.test_two_requirements_written_at_once_both_survive` 改为核契约：每次调用都给出结果；报成功的必在记录里；报失败的错误照实、重跑补上；最后四个需求各一个节点。修复前循环 12 次失败 2 次（都是上面的重复节点），修复后循环 15 次 0 失败。
- 新增 `test_a_refused_state_cleanup_after_the_record_keeps_the_same_node`：确定性注入「第二次写运行态被拒」，第一次报失败、记录已写，重跑成功且仍只有一个节点。修复前失败、修复后通过。
