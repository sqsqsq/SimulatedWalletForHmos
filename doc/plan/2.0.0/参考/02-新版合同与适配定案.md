# 新版合同与产品适配定案

来源约定：B为44cba622正式1.9.9完整源，O为19d26cad旧2.x，N为24ea6aeb的Framework发布树。下文 `core/` 是 `extensions/skills/story/scripts/core/`，`hooks/`从extensions起。真实接口和调查位置见[11](11-最新输入与调查依据.md)。本页定案实现职责，验证与预算另见12、13。

## 1. 正常链与唯一真源

系统单/本地材料 → 有权决定与采用材料 → 原字节冻结 → 原生component-design（含设计前知识、独立首读质询）→ 原生蓝图人读稿 → 独立Story写作设计与逐章成文 → Story独审 → 登记/送审/读回归档。进入施工时：蓝图 → 初次CU接受/原生readiness → CU Spec → CU Plan。update沿同一条链修订，不另起平行设计。

| 对象 | 真源、生产者与消费者 |
|---|---|
| 材料/人的决定 | 原件与既有流程关卡记录；冻结版本保存原字节与真实人签导出；作者、质询和Story核源读取。提取稿只作索引/分析，不替代原件 |
| 整体设计 | canonical component-blueprint；Framework作者及原生修订流程生产；原生renderer、Story和CU消费。同一决定不在Story另行维护 |
| 原生人读稿/reader_guide | Framework物化，Extension只通过真实publication接口校验/复制参考附件；guide引用存在不证明叙述忠实，交独审核语义 |
| Story与Review | Story作者持有全文写作设计与叙事；decisions.json持有Story澄清议题，Review由其渲染并保护人工区。它不是第二份设计决策：影响业务的有权裁决先回canonical |
| 知识 | `provides.knowledge`唯一激活清单，文件frontmatter持类型；canonical knowledge_application记录判断及落点；CU Spec/Plan落实义务和角色 |
| CU内容与Feature路径 | 原生CU工件和精确ref；创建/修订/调和由Framework负责，物理路径由原生解析器返回；Extension不拼编码ID目录 |
| 使用事实 | B的usage schema 1与Git；Story共同工作一次，CU各自阶段各记一次；不创建额外父子计时系统 |

## 4. 设计知识、质询与CU传递

保留O `knowledge-task.mjs`、`knowledge-application.mjs`、`story-knowledge/SKILL.md`及唯一schema。设计前先调用discovery/design任务再做决定；直接component-design从新原生knowledge资产读取同一方法，不能只有/story链送达。

- facts写 `discovery.facts[].value.knowledge`，由真实项目来源核事实。
- 规约/模式判断写 `decisions_and_gaps.decisions[]` 的 `kind: knowledge_application`；`knowledge.{kind,form,unit,source_sha256,outcome,target_refs}` 保持唯一合同。适用规约给requirement，模式roles给role/target_ref；有权豁免用waiver的reason/compensation/authority_ref。脚本核形状、来源、落点，模型判断适用性和内容充分性。
- CU按 `design_refs`承接实际承担对象：`featureKnowledge/unitScope/unitDuties/unitContext/rolesOf`继续区分共同依据、当前义务、未定归属；pending不分摊为全CU义务。Spec `acceptance.yaml`用 `knowledge_rule/knowledge_decision_id`，Plan实体用 `must:[{rule,decision_id,text,verify}]`、`pattern_roles:[{pattern,role,decision_id}]`。不把must塞进路径字符串files。
- 将B `indicatorShape`及指标定义/层次、口径/条件/结果获知时机/责任方法要求迁到canonical event作者输入、审查及必要结构核对；O `designStatPoints`单独不能保持B全部埋点能力。原始依据交作者可逐字引用，成品Story不因此逐字照抄。
- 后续coding/review/ut/testing保留知识义务及实现证据/不适用关系；本版真实终点到Plan，后段只签实际离线覆盖。

独立蓝图质询使用**同一个隔离执行体，先首读再核源**：作者先以现有knowledge-task生成questioning任务文件，保存到 `questioningRound()` 返回的candidate/reply同目录（如task.md），保留候选原字节；派发只给当前人读稿路径、原生八问、阅读规则和核源任务路径，不内联任务内容。子级答完正文八问后再read任务、canonical、原件和有效人签核required scopes；只读子级不负责运行脚本生成任务。不把作者摘要、知识决定表或YAML预先塞给首读者；退出的是O提前交付完整上下文的顺序，不禁止预生成文件。保留原生questioning结果及原报告，不新加reader角色、状态或固定轮数。DSH实际调用见14。

## 5. Story全文与独立审查

保留B写作设计、章草稿、chapter原子写入、来源贡献、图文/页面/异常叙事、Review人工区、同图可选SVG；事实输入改为O `story/design-source.mjs`、`story-inputs.mjs`的冻结来源+canonical+知识判断。退出B从需求级Spec提取设计的专用链与 `knowledge-use.yaml`，CU Spec不再是Story成文前置。

`designSource`、`review-object`、`routing.design_gate/story_stage_step`改成原生draft读取：保留输入完整、归属、消费记录、投影当前性校验，原生issues和admitted原样进入作者/独审/交付说明。**草稿可阅读不等于准入通过**；当前业务待决可送审，缺来源、坏身份、无当前稿或未有效独审不能因“允许draft”被忽略。不新增review_ready，不复制原生issue白名单。

成文保留现有章节合同作为组织起点；依据读者目标允许已有小节扩展与重排，不把十章或字数当业务完整性的上限，不新造模板引擎。O `story_details.body`逐字呈现规则及 `appendix.specialDesignProblems`全文匹配退出；N已有quality_attributes/data_domains/DTO/acceptance等字段优先承担设计，尚无等价字段的精确事件/配置等按现有canonical扩展保存，不另设设计文件。精确业务值、引用和来源可机械核，全文关系完整性由独审判断。

原生 `component-blueprint.review.md`仍只由Framework写；`AR/design-review.md`沿 `attachDesignReview`只复制当前原生投影并保护未知人工改动，随交付附上，业务评审者可选读。附件仍在既有审查/归档对象集合中，不因可选读变成可以缺件。Story正文须自行讲清业务，不能用“详见蓝图”补关键条件。纯guide改动按原生摘要处理，不等于Story语义已校验。

### 审查与原件

复用O `story/independent-review.mjs`、`review-object.mjs`、`review-report-contract.mjs`、`story-reader-rules.yaml`；合入B最新Reader语义、有效人签和必审覆盖判据。Story仍用material_key、三节Markdown、三列判据表和六列发现表；CU原生阶段继续用Feature汇总/明细合同，不能把Feature四列表套进Story六列消费者。

保B `review-inputs.mjs::detailProblems`的必审覆盖、缺件、未审及视觉能力边界：在Story现有“判据核对”节表后增加唯一YAML明细块，固定四键 `blocking_findings/advisories/examined_inputs/unreviewed`。前两者只引用六列发现表中的编号（分别为BLOCKER/MAJOR与MINOR/INFO），不重复写事实；examined_inputs列实际读过的路径，unreviewed沿B的 `{path|check,reason}`。report-contract一处定义，reader任务和judge共同消费；judge核编号与严重度一致，并把当前reviewObject必审集合/缺件/合法别名及下述独立Story视觉裁定作为basis调用detailProblems，保额外取证允许、缺件不能PASS的语义。新增块是现有独立报告的输入覆盖声明，不产生第二份报告或结论真源。

必须同时修改 `hooks/shared/reader-review-task.mjs::reading/readerReviewTask`、`independent-review.mjs::dispatchFor` 和story-build的prepare输出。dispatch只含Story路径、通用首读问题、材料键及后续task路径；现有 `AR/story-src/review/task.md`承载判据、作者回看、来源/人签/图源及返修诊断，首读完成后才读取。不能一开始内联这些内容，再靠一句“先读Story”声称独立首读。复审与格式修复沿已有分支按必要范围核，不添加第二reader。蓝图质询与Story独审是不同阅读任务。

保留 `material_key/report_dirs/originals/review_context` 的既有含义：当前材料绑定当前结果；前版本报告只参考；无效报告带原诊断交独立审查者，在新编号处返回完整修正版；重试不反复产生无意义编号；改过的原件不再取结论，恢复或新独审明确处理。源1.9.9的Feature报告核对继续用于CU，不混用Story材料键与原生subject。

DSH子级只返回最终报告，父调用方按完成通知原样保存，随后立即用已有check核并记录；同步修改reportFormat、reader任务和派审载体“审查者写文件”的文字，避免与DSH只读角色冲突。首次消费前的生产者真实性不由hash自证：正式证据须保留子级最终回复并与保存原件对照。脚本已有原件保护负责消费后的改动识别，不声称OS级防篡改，也不增旁路审计平台。

WARN非阻断建议有去向即可，不要求全部消告警。业务变化回canonical再成文；表达变化不新增业务批准，但实际稿字节变化所需的当前对象核对不能借旧PASS冒充。来源不足/视觉工具未用明确未覆盖，不要求制作无阅读收益SVG。

### 独立Story的视觉裁定：复用原生纯函数，不建立Spec阶段

N已有两层可用接口：`multimodal-probe.ts::resolveContextAdapterImageInput(projectRoot,frameworkRoot,adapter,identity?)`解析当前图像输入能力；`fidelity-shared.ts::resolveFidelityRoutingDecision(input)`在内存中计算保真路由。后者不读盘、不探测、不写Spec，返回inferred/selected/effective/strictness/defer/decision等字段，允许调用方提供真实执行身份。`effective-vision-context.ts::resolveEffectiveVisionContext`可保留能力来源/unknown说明，但仅有能力轴不构成best_effort裁定。**不调用**固定写spec/reports的fidelity-intent-init或initializeFidelityRouting，也不需要上游新增入口。

只在既有 `framework-access.mjs` 增加只读 `--action story-review-visual --feature <逻辑需求ID>`，与其现有原生模块加载方式一致；由Story prepare调用，现有task和check消费，正常链如下：

1. 本次必审图片集合为空时沿现有无图片路径，不启动视觉准备。需要裁定时，桥从当前flow读取已绑定蓝图和 `input.snapshot_ref`，经现有readFrozenInputs核来源；不接受作者传入一个自行选择的best_effort值。
2. `requirementText`由已采用且冻结的需求阅读原文（original角色中的有效文本/已登记原件转换稿）和human_record中的有效人签组成。复用现有材料阅读稿及其来源关系，不直接拼二进制原件；排除extracted_analysis、Story正文、写作设计和维护提示。无法取得必要原文时说明来源不足，不用作者摘要补成可降级裁定。
3. `requirementSha`使用现有冻结输入摘要；`executionIdentity`使用 `story:<逻辑需求ID>:<blueprint_id>:<revision>:<artifact_sha256>`。它是本次Story对象身份，不冒充 `phase:<主需求>:spec`，不写第二个需求或能力账本。
4. adapter来自原生当前工程/个人配置；modelPin仅在已有实际执行身份可取得时传入，不从业务文档猜。14的DSH专用verifier不设agentOptions、派发也不覆写provider/model，按已核DSH协议继承父路由，因此此配置下使用同一执行能力；空上下文不等于模型不同。若实际调用另选模型而现有配置无法对应，标unknown，不借父能力放行，也不为这种少见情况搭子代理能力平台。没有modelPin时沿原生interactive无pin解析，并保留adapter_declared等证据强度；工具名存在不证明模型能看图。
5. 取原生图像能力，OCR就绪只复用 `loadResolvedProfile(...).profileDir` 和 `resolveOcrAvailableForRun` 的既有环境检查，不调模型、OCR识别或新探针。调用纯routing时传 `{requirementText,requirementSha,executionIdentity,capability:{hasVision,ocrAvailable,reviewVision}}`；当前固定同模型reader的reviewVision等于已确认的该执行能力，不凭“配置了verifier”置true，不传虚构的manifestFidelity覆盖需求。
6. 返回蓝图ref、snapshot_ref/摘要、adapter/已知modelPin、能力来源及原生routing结果。prepare把这段派生事实写入已有 `AR/story-src/review/task.md` 的核源部分，生成后才计算material_key；不在首读载体内联来源结论。无新视觉文件、数据库或状态机。check沿同一只读函数核该来源/身份/裁定仍对应当前输入，变化走已有subject_stale→prepare，旧报告保持不变。

`basis.visual`只在**明确无视觉、原生effective=semantic_layout、strictness=best_effort且defer=false**时提供允许延期的已存在图片集合；其他情况为空。图面未核最高WARN，文字或其他必审内容未完、图片不存在仍失败。native `defer=true`（如hard像素要求被能力钳制）如实交需求/设计责任者处理，不能强写best_effort、换无关CU裁定或删除图片来放行；reference_only也不擅自扩大为原B的semantic_layout豁免。

修改落点限既有framework-access、reader-review-task、review-inputs和independent-review/check的定向接线；删除B visualDeferral对主需求Spec两份JSON的读取，CU自己的Feature阶段仍按原生Spec裁定，互不代签。当前是同一既有规则更换生产者和对象绑定，不增加用户确认关卡、第二审查者或视觉服务。

## 6. CU初建、调和与修订

| 动作 | 唯一生产接口与结果 |
|---|---|
| 初次接受 | 原生 `check:change-unit --project-root <root> --blueprint <id> --accept-candidates <file> --json`，文件是数组 `[{providerId,artifact}]`。provenance.extraction_method含真实providerId；空数组不是一次接受，无CU设计无需强行接受 |
| 接受后恢复/等价指针刷新 | `check:change-unit ... --readiness --json`或已有桥的显式readiness动作；会调和指针和物化，不能标只读。accepted已经成功后只恢复readiness/rebuildCommand，不再accept |
| 业务内容改变 | `reviseChangeUnitContent(root,blueprintId,[{expectedRef,candidate:{providerId,artifact}}])`；expectedRef完整保留artifact、component_id、blueprint_id、change_unit_id、revision、artifact_sha256；薄桥不手写revision或canonical |
| 已完成CU的新增工作 | 原生新CU/后继语义，不删除completion、run或改回未完成；无关CU保持原身份，受影响消费者一起修订 |

同ID修订保持component/CU/supersedes身份，完成/退役CU拒绝；active run非调用方锁返回busy，Extension不传伪造run/锁身份。provide承诺变化需同批显式修消费者，依赖缺失/循环拒绝，写失败由原生整批回滚。revision冲突先重读当前对象和变化，不能盲重投旧候选。原生accepted/ref更新已成功但文档失败，结果明确“已写与未完成”，不能以exit非零误判全没写。

施工准备消费原生readiness与实际设计缺口，业务送审不自动授权施工。CU到Plan沿正常无run interactive能力链；Spec→Plan事实增量问题见§8，不转Goal避开。

## 7. update、归档、usage/stats与adapt

update复用B的权限判定和O的设计绑定：核变化来源→保留原件→prepare记录→冻结新输入→设计所有者修canonical→按§6更新受影响CU→原生投影→Story/Review/独审→登记→上传/读回/回执→close。人尚未定范围时处理不依赖它的工作，保留剩余事项；意见不因更晚时间自动成为裁决。

CU内容修订不自动更新既有Spec/Plan。修订后由phase-evidence读当前新鲜度，而不是仅看旧summary.closed/PASS：若本轮已授权到Plan，回最早stale/missing阶段重新取得原生输入、落实变更并闭环到Plan后才称该范围同步完成；只授权业务文档更新时，可关闭该文档轮次，但必须列受影响CU、过期阶段和接手动作，不能称全部可继续旧Plan。该披露进入现有update记录/交回，不另建状态账。同步改 `phases/update.md`旧“不自动改、不重跑”绝对表述；`flow/update.py::_phase_facts`、`phase_facts`与usage.closed_at共同消费当前fresh结果，历史closure仍保留但不结算为本轮新完成。

反馈通过 `validateBlueprintReviewFeedback` 只说明候选形状/资格，authoritative_ruling还须精确source_revision、owner/role及真实decision。作者不得自造人签。表达调整只改表达；story_basis的蓝图ref、快照SHA、知识SHA及审查材料绑定照实际变化更新。原生identityNeutralDigest只处理其支持的CU/Feature，不拿整份蓝图做自造等价证明。

`flow/update.py`保持prepare/checkpoint/restore/close及人工区保护。restore只恢复其确权的Story/材料工作件；若canonical/CU已由原生提交，不能文件级倒退整个Framework树，恢复业务决定须走新的原生修订，成功完成CU也不倒退。报告目录统一原生解析。重新打开已closed轮次产生新轮，不把旧记录涂成当前。

归档沿B `story-build archive`：交付门→正式Mermaid→上传→读回→核回执→登记；回读不一致不登记，远端成功本地失败只补登记。原件/未知附件写前保护，任何失败列已完成与未执行，退出2/工具缺失不提示作者改业务稿。正式动作结束恢复有效本地SVG；SVG不成为系统二进制上传承诺。

usage保持B schema 1：

- `/story`确定需求身份后、取材/读取业务原件前显式begin story；更新在读取变化材料前begin story update。Skill入口及正常command下一动作同步，不以init/目录预置时刻补起点。无可核起点仍null；已有最早begin保留。
- `story-knowledge`的**作者入口**在读知识和业务工作前begin CU阶段；通用knowledgeTask及reviewer调用保持只读，不能误开作者计时。退出旧spec/plan author.mjs时同包接替其begin副作用。
- 主需求记录共同Story/设计和共同update一次；每个CU逻辑Feature只记自己的Spec/Plan等阶段，不复制共同耗时。所有identity、open_update、state key和路径消费者核逻辑ID/物理目录区别，不只改一个feature_dir函数。
- Story成功登记的真实时间回调结束Story，update真实close结束该轮，Feature只有原生有效closure才finalize；readiness、测试观察或上传开始都不等于工作完成。pending恢复按B覆盖/清理语义，不重复相加。
- stats仍只读usage与Git，报告写系统临时目录，不扫描业务目录补事实；自报模型/工具与未知时长照实披露。CU若展示名称仅解析已有身份，不引入强制业务索引。

adapt保持B首装/升级定向知识与对接层、独立知识审查、usage写前核/合法记录保护；新入口由entries原生物化。升级演进记录明确2.0.0知识落点/对接层变化及旧需求在旧版收口或重新init；不恢复“在途单”扫描/迁移。真实目标仓自己的Framework与DSH等宿主由其所有者接入，本扩展不复制本仓本地adapter。
