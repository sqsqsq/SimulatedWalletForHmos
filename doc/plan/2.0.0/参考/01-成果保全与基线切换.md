## 4. merge操作及提交次序

**第一批不执行产品merge。** 它可独立提交来源/保全/文档接续、标准/预算工具和N/DSH装配；安装核验对象仍为O，结果只证明装配层。产品B的完整承接在第二批01，与主链及共享合同适配同一步发生。

```powershell
git status --short
git rev-parse HEAD
git fetch output/story/2.0.0-rewrite/20261025-152853/git/story-1.0-local-9c865bfb.bundle refs/heads/story-1.0   # 批次一保全的B′对象，前置为B
git rev-parse FETCH_HEAD   # 必须是 9c865bfb242ce0c64da4aafd49507c96731f56a2

git merge --no-ff --no-commit 9c865bfb242ce0c64da4aafd49507c96731f56a2
git diff --name-only --diff-filter=U
```

保持本步合并事务，按§3逐路径处理完整包及已归档历史；源提交不得把第一批已移出的1.x版本重新留为活跃入口。保当前分批Plan和project。路径恢复用 `git restore --source=<T或B或O> --staged --worktree -- <经核明确路径>`，不全仓选一方、不执行占位符。

第二批01同时完成参考02的首链必要设计与共享协议，使用O canonical update骨架并合B适用修复，所有保留入口的imports/路径/状态/副作用一致。第三批仍要完成完整更新/恢复等语义；它不是为第二批保留断接口或旧Spec运行链兜底。首链定向检查和安装组合成立、预算权限满足后，在**同一步末尾**显式stage并提交真实merge M：

```powershell
git diff --cached --check
git diff --cached --name-status
git commit -F <本步交付材料中的提交说明文件>
git merge-base --is-ancestor <T完整SHA> HEAD
git merge-base --is-ancestor 9c865bfb242ce0c64da4aafd49507c96731f56a2 HEAD
git show -s --format="%H %P" HEAD
```

M必须有T/B两条祖先和真实双亲，不能merge -s ours只登记来源。M后第二批02及第三批每个实施/返修步骤正常交回并提交；不把MERGE_HEAD跨到下一步，不等全版完工才固定首个产品对象。若本步首链或共享合同失败，保过程diff、暂停受影响工作并交设计者；不以批次拆分放宽首包要求。
