### 1.3 用户裁定：继续适配，以真实 CLI 判断行为阻塞

2026-09-29 用户确认的推进口径，后续实施与评审均以本节为准：**先按现有原生能力推进适配，未验证的行为疑点列入正常 CLI 观察项，不因这些疑点整体停工；用实际结果判定是否阻塞产品目标。**

1. 实施使用真实、合法的原生入口与数据合同。遇到已经确定复现的接口错误、信息丢失或破坏性覆盖，及时定位处理，不把已知硬错误留到最后耗费 CLI 运行。
2. 设计知识送达、独立人读审查、CU 承接与无 run 续行等尚未验证的行为，保留为测试观察项；不以上游全部回复、四项新增 API 或这些行为事先通过为适配开工条件。
3. 准备进入 CLI 时，区分“实现及必要离线检查已通过、可实跑”和“行为已被 CLI 验收”。不能要求同一行为先通过验收，才允许启动用于验证它的测试。真实 CLI 仍由用户在既有里程碑启动，本条不自动启动测试。
4. 测试出现问题先核 Extension 调用、输入、信息送达、原生配置与对象身份。修正本仓接线后再验证；只有合法调用仍无法满足目标，才判 Framework 的实际阻塞并给出复现、最小修正诉求和影响范围。已确定的原生缺陷可先反馈，其他独立适配继续。
5. 不伪造报告/回执，不调用不存在的接口，不绕过检查或降低目标取得通过。测试发现真正必经能力缺失时，保留失败事实并只暂停受影响路径，不要求把不可实现部分冒充“全部适配完”。
6. CLI 上限仍为 Plan，结论只覆盖实际执行的路径和范围；Coding、设备与整体施工未跑时继续标未验证。正式发布仍须满足本版目标及对应验收，疑点未证实不等于能力已成立。

问题反馈报告与既有源码观察继续有效，但“发现风险”“可继续实现/实跑”“目标验收通过”分别记录。后续不得再次将未验证疑点直接写成全部适配的前置阻塞。

### 1.4 用户裁定：先跑通正常流程（2026-09-30）

首要目标是完成 Framework 3.1 适配，让正常需求从材料、设计、人读交付到已授权的 CU 阶段跑起来。实施与评审优先选择最简单、完整、正确的接线；正常路径成立且实现符合目标就继续推进。异常处理按实际 CLI 暴露的问题逐步补齐，不把预设的全部异常矩阵作为下一步或首次 CLI 的门槛。

- 当前必须处理：正常使用必经的输入输出、实际来源与权限、审查接线、当前对象一致性，以及会干扰正常流程的失效旧职责。确定错误采用局部修正，复用已有原生校验，不能靠伪造结果或降低要求跑通。
- 可后补：人为损坏冻结件、多重中断、历史记录异常组合、低概率并发等防御与恢复。记在本需求现有评审或 CLI 观察项中，写清触发条件、影响和现有处置；无需新建异常管理系统。
- 原生错误可先原样报告并停止当前动作，复杂自动恢复、穷尽分类和跨文件事务不作为本轮默认建设。已能简单修正的写前校验、成功后登记仍直接完成。
- 离线验证先覆盖真实正常链和本次修正直接涉及的少量反例；正常 CLI 的结果决定后续加固顺序。明确未验证不等于必须停工，也不等于已验收。CLI 仍按用户授权启动。

本裁定约束四个步骤，优先于各分册中把全部异常验收列为当前推进门槛的表述。步骤 2 的具体分流见本轮评审 §5；版本目标、角色边界和真实结果要求保持。

## 3. 适配接缝 A/B/C/D 的核对与裁定

A/B/C/D 现在表示**四项适配接缝**，不是 Framework 3.1 缺失蓝图功能的证明，也不是四项必须先开发的新 API。先以实际接入的 main 提交核已有入口；保留旧源码发现作为核对线索，不预先把解决方案固定为上游改造。

### A：设计作者和独立质询的知识输入

结果要求：当前激活知识及作者/质询要求在设计决定前送达；直接 component-design 和 Story 转入均成立。

先核已接入 manifest 的 skill_assets、component-design 资产读取及独立质询装配。已有机制可达即直接登记 Extension 要求页；作者页、质询页及 knowledge-task 是 Extension 自身职责。`extension_author_requirements`、`extension_review_requirements` 仅是原方案建议的资产键，未核实消费语义前不得称已接通。

如果现成的原生公开输入方式已经能完整送达，采用该方式并删除多余的键；只有缺少直接入口或独立质询的通用输入消费时才提最小 Framework 修正。只有 Story 包装入口生效不满足直接入口目标。未接通部分限制相关送达验收，不限制基线同步和其他确定性适配。

### B：不依赖 Spec 的人读审查

结果要求：独立执行者审当前 Story/Review，复用有效审查，识别过期/非法报告，能力缺失如实披露；不制造 Feature 或阶段 receipt。

先核实际发布件的独立审查、无 Feature request 入口、可传任务与材料的公共调用面及对象验真。不能因为没有名为 artifact-review.ts 的文件就判缺能力；也不能因为存在 code-review 请求就声称它支持任意人读产物。设计者按输入、对象身份、判据、报告及消费者逐项核适用性。

原方案拟定的 artifact-review.ts 和 prepare/check CLI 退出既定接口地位。Extension 内部仍提供步骤 2 的 prepare/check 业务动作，原生实际命令及状态映射在基线核对后由设计者写入其调用合同。按 §1.3 使用现有合法调用推进适配与验证；只有确认必经通用能力确实缺失时，才交 Framework 最小补齐并限制对应正式交付。独立审查目标保持，不以“待回复”阻止其他适配。

### C：施工输入中的知识职责

已核实体级 must、验收 knowledge_rule/knowledge_decision_id、knowledge_applications 可经过派生/物化/部分阶段 resolver；真实组件的 pattern_roles 已有同类证据。接口/数据模型的角色经独立 SpecLoader/原生文件引用核对保留，完整派生及 phase 检查在实施时补齐。具体格式唯一在步骤 3。

## 4. 原生读取与交互开发的共同调用

步骤 1 新增一个薄 `hooks/shared/framework-access.mjs`，只调用已交付的原生模块并转交 JSON/错误。它用 createRequire 绑定 `<root>/framework/harness/package.json`，加载该发布件安装的 ts-node 并注册其 tsconfig，随后 require 原生 TypeScript 公共函数；不复制框架实现、不另装全局运行器。Python 调用同一 Node CLI。

```text
node <ext>/hooks/shared/framework-access.mjs --project-root <root> --action blueprint --blueprint <id> --purpose draft|delivery
node <ext>/hooks/shared/framework-access.mjs --project-root <root> --action feature --feature <native-id> --phase <phase>
```

运行时从显式 root 的 framework 加载模块，不从维护源码或固定全局安装位置导入。调用者使用参数数组，保持空格路径；依赖缺失明确报工具缺口。

blueprint 动作使用 loadCanonicalBlueprint、checkCanonicalComponentBlueprint、evaluateDesignPreparationEntry。draft 可返回未准入草稿与原生 issues；delivery 必须 blueprintAdmitted=true。输出 `{status,canonical_path,blueprint,blueprint_ref,admitted,issues}`；blueprint_ref 为原生完整引用，target={kind:blueprint,id:blueprint_id}。先后读取发生摘要变化报 stale，不消费混合对象。

feature 动作先 classifyFeatureId/featureRelativePath。CU 调 loadCanonicalChangeUnit、resolveComponentBlueprintRef，并调用原生有效输入解析；派生路径使用 deriveBlueprintSkillInput，已有材料经当前 phase 的 resolveCapabilityInputs/SpecLoader 读取。只返回本动作需要的输入，discovery/设计准备不能要求后继 contracts 已存在。输出 `{status,identity,feature_path,blueprint_ref,design_refs,inputs,issues}`；inputs 含 acceptance/contracts/use_cases 的实际值及原生 binding，原生 absent/invalid 区分。合法非 CU 维护 Feature 用相同原生 phase resolver，不创建蓝图。

普通成功退出 0；对象缺失、坏来源、过期或未准入退出 1并返回原生 issues；参数/依赖错误退出 2。所有动作只读，调用者按当前目的决定缺输入是否阻止该动作，不能把全部 phase 都硬要求完整施工契约。原生 resolveCapabilityInputs 的输入为 `{frameworkRoot,projectRoot,feature,phase,track,inputContext?,requirement?,requirementSourceFiles?}`，读取返回 report/inputs；无 run 的 spec 还必须沿原生 featureRequirementBinding/resolveRequirementInput/readBoundInput 恢复并验证真实需求，把 requirement/requirementSourceFiles 交入；不能只调用后半段 resolver。track 和 scope 从原生当前 Feature/request 上下文取得，不写死 full。当前阶段 hook 已有原生 resolvedInputs 时直接消费，不再启动第二次解析。命令行 feature 动作必须带 phase，沿该阶段原生 artifact/derive 优先级和有效性判定取输入；不得绕过已存在但 invalid/stale 的本地契约，直接派生另一份结果覆盖错误。只读 resolver 与冻结 scope 是不同动作。脚本只读调用解析器前先核当前 scope 可读，缺 scope 返回待原生入口准备，不由知识任务冻结 scope。

无 run 交互路径在实际 3.1 基线上单独核对：此前源码观察发现部分 Skill 强制 Goal 文案与实现不一致。若接入件仍有差异，设计者根据实际调用和证据裁定影响，只暂停受影响的交互推进接线；不阻止 Framework 基线同步，也不让 Extension 自建推进循环。

首阶段准备由已经获得该阶段授权的主模型承担：prepare-scope 生成真实候选后，委托原生 ensureFeatureExecutionScopeFrozen 完成范围准备，frozen/reused 后重新取得知识任务再动笔；已冻结直接读取。知识读取器只读，未冻结输出是预览，不作为完整阶段输入。不得为冻结提前运行整个阶段 harness，也不新增私有循环；调用合同和顺序验收见本轮返修评审 §4。

交互开发沿 project-entry 的原生 prepare-scope → 首阶段范围冻结 → 适用阶段 → component-closure；范围、下一责任和结果读取原生输出。Story 外层交接授权终点及真实来源，不写 execution-scope.json、CU 回执或私有阶段循环。用户只要 Plan 时停在实际设计义务上限，不自动进入 Coding。
