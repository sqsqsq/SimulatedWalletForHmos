## 3. 适配接缝 A/B/C/D 的核对与裁定

A/B/C/D 现在表示**四项适配接缝**，不是 Framework 3.1 缺失蓝图功能的证明，也不是四项必须先开发的新 API。先以实际接入的 main 提交核已有入口；保留旧源码发现作为核对线索，不预先把解决方案固定为上游改造。

### A：设计作者和独立质询的知识输入

结果要求：当前激活知识及作者/质询要求在设计决定前送达；直接 component-design 和 Story 转入均成立。

先核已接入 manifest 的 skill_assets、component-design 资产读取及独立质询装配。已有机制可达即直接登记 Extension 要求页；作者页、质询页及 knowledge-task 是 Extension 自身职责。`extension_author_requirements`、`extension_review_requirements` 仅是原方案建议的资产键，未核实消费语义前不得称已接通。

如果现成的原生公开输入方式已经能完整送达，采用该方式并删除多余的键；只有缺少直接入口或独立质询的通用输入消费时才提最小 Framework 修正。只有 Story 包装入口生效不满足直接入口目标。未接通部分限制相关送达验收，不限制基线同步和其他确定性适配。

### B：不依赖 Spec 的人读审查

结果要求：独立执行者审当前 Story/Review，复用有效审查，识别过期/非法报告，能力缺失如实披露；不制造 Feature 或阶段 receipt。

先核实际发布件的独立审查、无 Feature request 入口、可传任务与材料的公共调用面及对象验真。不能因为没有名为 artifact-review.ts 的文件就判缺能力；也不能因为存在 code-review 请求就声称它支持任意人读产物。设计者按输入、对象身份、判据、报告及消费者逐项核适用性。

原方案拟定的 artifact-review.ts 和 prepare/check CLI 退出既定接口地位。Extension 内部仍提供步骤 2 的 prepare/check 业务动作，原生实际命令及状态映射在基线核对后由设计者写入其调用合同。确有通用缺口才交 Framework 最小补齐；该缺口阻断正式人读审查/交付，不阻断取材、冻结、蓝图读取及草稿成文。

### C：施工输入中的知识职责

结果要求：规约义务、模式角色及验收责任经过蓝图/CU 派生、物化、复用后仍可被当前执行者读取；原生文件授权不放宽。

先核真实 contracts/acceptance 的实体扩展能力与原生解析链，优先在本来承担该职责的实体上保留知识信息。此前已证明：7753c18f 的 files 为 string[]；把知识职责硬塞进 files 对象会丢失；自拟 knowledge_files 也会被未知文件字段检查拒绝。这证明旧方案的两个写法不成立，不证明蓝图版整体无法适配。

knowledge_files 退出既定实施字段。设计者对原生现有实体和允许的扩展位置作真实链核对：已有合法位置足够时直接使用并同步消费者；确无合适载体且必须保留文件职责时，才提出原生 schema/resolver 的窄补充。禁止改字段名绕过检查，禁止用无业务职责的假组件装文件路径。核对结论只阻断受影响的文件职责接线及完整链验收。

### D：安装入口物化及目标人工保护

结果要求：使用原生宿主生成能力，同时保留目标知识、对接、身份和人工入口内容；前置冲突明确，部分失败不报整体成功。

先核实际 extension inspect/materialize、bridge ownership、入口 renderer 与现有安装器的预检能力。对外适配的所有权判断继续由 Extension 安装职责承担；不因旧提案没有“只读计划 API”就要求新建通用计划机制。

此前观察到的整文件 AGENTS/CLAUDE 覆盖必须用实际输入验证。可通过已存在的原生渲染/保护接口及现有安装预检安全处理，就直接组合；如生成者确实不能识别/保护必要人工区域，才提出最小修正。原方案 planExtensionMaterialization API 退出既定合同。受影响的目标覆盖操作在保护成立前暂停；不因此阻止 Framework 基线读取、身份适配或其他无覆盖动作。

### 核对结果与局部缺口的责任

[分册 06](06-Framework基线接入与能力核对.md)规定首次交回。每项必须给：实际 main 提交与发布身份、原生入口/参数/返回、正常与相关失败证据、直接消费者、现成能力是否足够。实施者负责取证；设计者负责选方案、锁定真实调用和修正文档，不能把协议选择推给实施者。

只有明确无法满足必要目标的差异才成为 Framework 修改需求，包含实际反例、最小修正、影响范围、验收和回执要求。Framework 维护者在其责任域实现并发布，再按同一路径进入 main 和 story；本仓不修改 vendored 副本。上游接受、实现、发布和本仓接入分别记录。

当前：实际 main 仍为 3.0.0，尚未产生“本仓 3.1 已接入后的接缝核对结果”。四项都未被批准为必须新增 API；此前源码例证保留其事实意义，不扩大为总体阻塞结论。

## 4. 原生读取与交互开发的共同调用

步骤 1 新增一个薄 `hooks/shared/framework-access.mjs`，只调用已交付的原生模块并转交 JSON/错误。它用 createRequire 绑定 `<root>/framework/harness/package.json`，加载该发布件安装的 ts-node 并注册其 tsconfig，随后 require 原生 TypeScript 公共函数；不复制框架实现、不另装全局运行器。Python 调用同一 Node CLI。

```text
node <ext>/hooks/shared/framework-access.mjs --project-root <root> --action blueprint --blueprint <id> --purpose draft|delivery
node <ext>/hooks/shared/framework-access.mjs --project-root <root> --action feature --feature <native-id> --phase <phase>
```

运行时从显式 root 的 framework 加载模块，不从维护源码或固定全局安装位置导入。调用者使用参数数组，保持空格路径；依赖缺失明确报工具缺口。

blueprint 动作使用 loadCanonicalBlueprint、checkCanonicalComponentBlueprint、evaluateDesignPreparationEntry。draft 可返回未准入草稿与原生 issues；delivery 必须 blueprintAdmitted=true。输出 `{status,canonical_path,blueprint,blueprint_ref,admitted,issues}`；blueprint_ref 为原生完整引用，target={kind:blueprint,id:blueprint_id}。先后读取发生摘要变化报 stale，不消费混合对象。

feature 动作先 classifyFeatureId/featureRelativePath。CU 调 loadCanonicalChangeUnit、resolveComponentBlueprintRef，并调用原生有效输入解析；派生路径使用 deriveBlueprintSkillInput，已有材料经当前 phase 的 resolveCapabilityInputs/SpecLoader 读取。只返回本动作需要的输入，discovery/设计准备不能要求后继 contracts 已存在。输出 `{status,identity,feature_path,blueprint_ref,design_refs,inputs,issues}`；inputs 含 acceptance/contracts/use_cases 的实际值及原生 binding，原生 absent/invalid 区分。合法非 CU 维护 Feature 用相同原生 phase resolver，不创建蓝图。

普通成功退出 0；对象缺失、坏来源、过期或未准入退出 1并返回原生 issues；参数/依赖错误退出 2。所有动作只读，调用者按当前目的决定缺输入是否阻止该动作，不能把全部 phase 都硬要求完整施工契约。原生 resolveCapabilityInputs 的输入为 `{frameworkRoot,projectRoot,feature,phase,track,inputContext?,requirement?,requirementSourceFiles?}`，读取返回 report/inputs；track 和 scope 从原生当前 Feature/request 上下文取得，不写死 full。当前阶段 hook 已有原生 resolvedInputs 时直接消费，不再启动第二次解析。脚本只读调用解析器前先核当前 scope 可读，缺 scope 返回待原生入口准备，不由知识任务冻结 scope。

无 run 交互路径在实际 3.1 基线上单独核对：此前源码观察发现部分 Skill 强制 Goal 文案与实现不一致。若接入件仍有差异，设计者根据实际调用和证据裁定影响，只暂停受影响的交互推进接线；不阻止 Framework 基线同步，也不让 Extension 自建推进循环。

交互开发沿 project-entry 的原生 prepare-scope → 首阶段范围冻结 → 适用阶段 → component-closure；范围、下一责任和结果读取原生输出。Story 外层交接授权终点及真实来源，不写 execution-scope.json、CU 回执或私有阶段循环。用户只要 Plan 时停在实际设计义务上限，不自动进入 Coding。

## 5. 预算与交回

唯一范围按根 AGENTS §5：extensions 的交付实现与指令，排除知识、业务对接和安装器升级记录；安装器计入，维护和测试不计。用现有 measure() 复测，1.9.8 基线 B=13993。版本更名不重置初始额度。
