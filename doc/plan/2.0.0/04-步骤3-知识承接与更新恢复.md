# 步骤 3：施工知识、反馈、更新与恢复

先读[总览](01-实施总览与协作合同.md) §2–4、步骤 2 的 flow/输入/审查合同，以及根 AGENTS §3/5。本步以实际 3.1 基线及相关人读/原生输入合同成立为前置，将设计知识与变化处理接入真实下游。C 的合法实体与角色载体已按本轮评审确定，接口/模型角色尚需补完整派生与 phase 验证；无实体的具体文件义务由设计者另核，不影响已闭合的事实/决定读取、反馈及自有恢复。

接口身份及本仓实施已通过[收口评审](评审意见/2026-10-01-步骤3接口身份评审.md)，进入步骤 4；真实行为、已知上游缺口及版本发布保持各自验收边界。正常链优先，后补异常边界保持。

## 2. 知识应用数据合同

### 2.1 蓝图事实与决定

| 对象 | 最小内容与责任 |
|---|---|
| discovery.facts[] | 原生 fact_id/subject/value/provenance；value.knowledge={unit,form,source_sha256}，value.observation 记录实际事实及用途 |
| decisions_and_gaps.decisions[] | 原生 decision_id/kind/status/owner/provenance/verification_refs/rationale；kind=knowledge_application；knowledge 如下 |
| 施工实体 | 保留各合法实体位置的 must；验收 knowledge_rule；文件级实体在 §2.2 定义其待核载体与接入规则 |
| 非 CU 的合法维护 Feature | 当前原生 contracts.knowledge_applications[] 使用同一决定行；真实来源保留，不创建需求蓝图或 Story |

knowledge 为 `{kind,form,unit,source_sha256,outcome,target_refs}`；kind=constraints/patterns，form=entries/halves；unit 来自激活 parser；来源路径只放 provenance.source_ref。目标使用原生稳定地址，由 blueprint-addressing 验证；同单元按来源路径+unit 区分，不能因不同文件重号而合并。旧的全仓编号唯一限制及裸 entryById 消费退出，must/验收通过 decision_id 定位来源，再按 file+unit 查条目。source_sha256 为 `sha256:<64hex>`。

- constraints：outcome=applied/not_applicable/waived/pending。applied 有 requirement、理由和非空 target_refs；waived 有 waiver={reason,compensation,authority_ref} 指真实授权，知识声明的不可豁免要求不接受 waiver；not_applicable 说明本需求条件，target_refs 可空。
- patterns：outcome=selected/rejected/adjusted/pending。selected/adjusted 有理由、target_refs 和 roles=[{role,target_ref}]；role 取实际知识角色。rejected 说明反证；pending 对应原生 gap，带 owner/needed_by/unlock_condition。
- 模型有据判断为 answered_with_evidence；明确不适用用 not_applicable；实际被接受的人工裁决才用 decided_with_authority 并引用原话/权限；未决按原生 open_decision/blocker 处理。
- 规约逐条判断，facts 只记录实际使用单元，模式候选及选择理由保持。共同设计约束在设计前成立，尚属后续执行阶段的具体义务保留责任与验证位置，不凭清单补齐虚构设计。
- facts×halves 按文件作为方法单位，H2 是回查锚点；facts×facets、constraints 条目及 patterns 单元由现有 parser 定义。相关原文完整可取。

正常及不适用的维护例子（用于两个不同需求；摘要须对实际知识文件计算）：

```json
{
  "decision_id":"retention-choice",
  "kind":"knowledge_application",
  "status":"answered_with_evidence",
  "owner":"design-author",
  "provenance":{"source_kind":"knowledge","source_ref":"doc/extensions/knowledge/constraints/retention.md","observed_at":"2026-09-29T00:00:00Z","evidence_strength":"inferred","extraction_method":"read_and_apply"},
  "verification_refs":["view:logical/node:record-store"],
  "rationale":"本需求保存临时记录，处理完成后须清除内容。",
  "knowledge":{"kind":"constraints","form":"entries","unit":"R-1","source_sha256":"sha256:1c9c9c69682f9a43b276e0484b5e4cc51ef43c602231ec346fd1aacbce78e1d4","outcome":"applied","requirement":"完成后清除临时内容","target_refs":["view:logical/node:record-store"]}
}
```

不适用例子使用同形对象，将 status=not_applicable、outcome=not_applicable、target_refs=[]，rationale="本需求仅读取已有记录，不创建或缓存记录"，移除 requirement，verification_refs 指真实需求来源。示例知识原始 UTF-8/LF 文本为 `# Retention\n\nR-1: Remove temporary records after completion.\n`；实施测试先计算摘要再提交原生完整对象校验。样例身份和结论不得复制到产品任务。

原生整体 closure 对 decided_with_authority 还要求 knowledge_refs 精确指向 discovery.inputs.knowledge_assets 中存在的文件及 #conclusion-id（component-closure-knowledge.ts）。设计作者在作出权威决定时就要取得这项归位要求，并由真实设计/知识责任方形成有据落点；该原生资产集合不直接等同于 Extension 的全局激活清单。本轮业务决定不能自动变成全局规约，也不能为过门把真实人工裁决改为模型推断。缺归位时保留实际责任及缺口，整体完成不可误报；阶段消费者与最终验收需覆盖该链。

### 2.2 文件授权与知识实体

原生 contracts.files 保持实际发布件定义的授权形态。此前已核源码为 string[]，因此旧 files[].must/pattern/role 对象读取必须替换。设计者依据 C 的实际核对结果锁定合法实体位置，不先让上游支持一个自拟字段。

优先使用本来承担业务职责的原生契约实体。保留现行合法 must 位置的能力：data_models[].fields[]、interfaces[].methods[]、components[]、components[].state[]、resource_keys 条目；实际解析/物化后仍保留是验收条件，不能只看 schema 允许未知键。state_management 顶层等现行未允许位置仍须报告越位。文件级要求及角色必须有真实授权文件和承担者，不通过虚构组件或改字段名躲过原生文件检查。

must 的业务内容固定为 rule/text/verify 及稳定 decision_id；verify=ut/device/both/review，与知识实际执行责任相符。共同设计中的 knowledge decision 是唯一判断来源；canonical 内保存稳定 ID，不内嵌含自身摘要的完整引用。CU 消费者先核原生蓝图身份，再按该 ID 调原生 resolver；非 CU 维护 Feature 按其身份引用自身原生契约中的决定，不以缺蓝图触发 fallback。

验收 criteria/boundaries 的 knowledge_rule 保持字符串编号，并以 knowledge_decision_id 明确来源决定；knowledgeCriteria 按决定定位知识来源，再核到实际 must 和验证责任，避免不同文件同编号混合。模式角色同样指回有效选型决定及真正承担角色的施工实体。

本轮已核后采用实体角色 `pattern_roles: [{pattern,role,decision_id}]`：只放在真实承担职责的 components、interfaces 或 data_models 对象上，以其原生 name/class 定位，以原生 file 取得实现文件；角色行不重复写文件路径。实体地址统一按原生类型：接口用 interfaces[].class，方法用 methods[].name，data_models/components 用各自 name；义务、角色、引用解析、plan 方法表和审查输出共用现有 contracts 模块的命名职责，不让接口 name-only 旧样例形成兼容分支。共享模式的整体角色在蓝图核完整性，每个 CU 只核角色 target_ref 落在其有效设计责任内的部分，不能因承担其中一个角色而要求复制其他 CU 的角色；角色名同时核实际模式声明。探针及复核结果的分组/去重使用决定身份或来源文件+单元，不能按裸编号把不同来源、强制力的结果合并。真实组件的派生/物化/部分 resolver 保留已有证据，接口/模型已核 SpecLoader/引用检查，实施须补齐完整派生与 phase 验收。patternRolesFromContracts 及其调用者同步从真实实体取得角色、实现路径和决定，不再读 files 对象。

五处实体 must 和验收桥的接线可开始；没有承担实体的文件级要求，由作者交出真实要求、目标文件和设计落点，设计者定位后再补合同，不能用假组件或未知嵌套 file 键蒙混。现阶段不增加 knowledge_files，也不据“缺这种自拟字段”向 Framework 要求扩展。

完整承接验证覆盖原生 deriveBlueprintSkillInput → SpecLoader/文件引用闭环 → materializeBlueprintSkillInputs → 当前 phase resolver → Extension 消费。模型知识判断的 inferred provenance 与已准入设计对象的 provenance 各按真实来源，不改成人工权威来通过派生。已有物化结果和当前有效设计冲突时回原生责任，不自动覆盖。尚未定位的具体文件职责只影响它自身，已明确的事实/决定读取、合法实体及恢复逻辑继续。

| 消费者 | 实际读取 | 失败/缺口 |
|---|---|---|
| Story 附录 | 当前蓝图 facts/knowledge_application，按激活单元展示理由、来源及目标 | 缺判断、知识 hash 已变或设计过期报告待同步 |
| CU 设计准备 | 原生 design_refs 对应实体及决定 | 跨身份/旧 revision/未承担对象回设计负责方 |

| post_check | 扩展 schema、单位、来源、稳定地址、实体 must、核定的文件职责载体、验收桥 | 集中报告坏结构、失效引用、未授权文件和角色缺口 |
| pre_verifier | 条目原文、判断理由、设计对象和当前施工实体 | 独立核语义、遗漏和偏离；字段存在不算应用 |
| Coding/Review | 有效契约文件职责及实现证据 | 形态探针只是线索；真实语义由作者/审查核 |

非 CU 维护 Feature 通过原生身份明确分派，使用当前有效原生产物；没有蓝图不触发 fallback 去猜 Story 或平铺 Spec。合法空知识通过，已声明义务在派生中丢失必须失败。

### 2.4 CU 各阶段产物、模板与扩展作用

Story/Review 是需求级人读交付，CU 的 spec/plan/code/review/test 是施工职责产物，二者各有读者与权威。每个 CU 不再复制一套 Story/Review，也不重新裁决已经成立的共同设计。以下是实施者修改阶段作者页、overlay 和 checker 的交接表。

| 阶段 | 主要有效输入与产物 | Extension 2.0 对它的作用 | 从 1.x 退出的职责 |
|---|---|---|---|
| Spec | CU 及其设计引用、原始需求、已有 acceptance；补清本 CU 行为/边界/验收，按请求形成 spec.md | 交付相关原文与已成立蓝图判断，核本 CU 验收是否承接适用规约及验证责任 | 全需求知识判断真源、模式候选唯一入口、Spec 内生成 Story/Review、Spec 必须有人读交付登记 |
| Plan | 有效验收、蓝图设计、当前施工对象；形成精确 contracts/use_cases，按请求形成 plan.md | 将决定落实到 must、实际核定的文件职责实体、角色和验收桥；核源码职责、专项设计及验证安排 | 重做整体选型、固定 Spec 章节读取、以 files 对象存知识职责 |
| Coding | 原生有效契约、验收、授权写集；源码及真实编译/检查结果 | 作者在实现前取得义务和模式角色；保留有依据的结构探针，审查实际落地 | 通过平铺路径或旧知识文件重猜适用规则，靠回显名称宣称应用 |
| Code Review | 当前代码、设计和验收；原生代码审查报告 | 核规约行为、角色协作、专项实现及偏离；真实问题回设计或实现责任处 | 重复审需求级 Story，读取旧 Spec 判断表作为当前权威 |
| UT | 验收 ID、实现及 unit/both 责任；测试代码和执行/覆盖证据 | 通过 knowledge_decision_id 和实际 must 对应本 CU 必须验证的业务行为 | 仅按同名编号或 Spec 表格找用例，字段出现即算覆盖 |
| Testing | 有效 device/both 等责任、应用及环境；测试计划和实际证据 | 核设备、人工和组合责任是否落实，缺证据如实表达 | UT 通过替代设备证据、无义务也造测试、靠旧阶段文件存在判断完成 |

模板分三层处理：

1. **Framework 原生模板和输入协议**由实际发布件维护，Extension 不复制或修改 vendored 模板。是否必须生成 spec.md/plan.md 由本次原生 required_outputs 决定；已有合法 typed 输入可复用。复用省去的是重复文档生产，验收、契约及后续证据责任仍须成立。
2. **Extension 阶段作者要求、hooks 和 overlays**保持承担专项知识质量的能力，按本表更换输入源、身份及检查位置；因此机制不与 1.x 原样相同。各阶段在动作前读知识任务，post_check 核确定事实，pre_verifier 给独立审查者实际材料。
3. **Story 章节合同及人读判据**继续由 Extension 维护，只在需求级成文/交付使用。其设计来源改蓝图，人读审查走 B，退出 Spec overlay 中的旧捆绑。

没有新 spec.md/plan.md 时，作者与 checker 消费原生有效输入，不补空文档让旧读取器继续工作。蓝图承接到 CU 的角色与义务由 C 的实际接线及本节共同核对；直接 Framework 阶段入口也适用，不需要先创建 Story。

CU 后续细化的影响按责任处理：仅补文件、类型或局部实现细节且没有改变蓝图或已交付人读事实时，保留 Story 原稿；改变共同边界、外部契约或设计取舍时回 component-design 修订；使 Story 的已陈述内容不再准确时按步骤 2/本步 update 同步并重新判断审查有效性。不能让 CU 自行改写共同设计，也不因每次 Coding 提交重生成 Story。

### 2.5 正常路径的专项送达裁定

无 plan.md 时，埋点落实由当前有效原生 contracts.interfaces[].methods[].description 与相关验收条目承载，说明真实统计点、适用结果及验证方式。有 plan.md 的逐点表继续作为人读表达。作者/审查任务并列提供蓝图 event 的完整 body、实际契约方法说明与相关验收完整条目及验证字段，不只列统计点名称或任选一个验收字段；保留设计身份与地址，独立审查逐点核落实；脚本只核可确定的引用。缺 Markdown 表可以报告该表的一致性检查不适用，不能跳过整个埋点义务。不新增平行统计点文件、虚构 must 决定或强制补 plan.md。

现有 evidence-rules.md 调整为设计发现/当前事实核对的共同取证页，blueprint author 在发现前送达，spec author 只在本 CU 新增事实时引用。意图来自本次需求/决定及有效原生输入，不以 spec.md 为必备真源；取证结果写入各动作的原生事实对象。

## 3. 反馈、更新与交互开发

更新保留来源获取、材料关卡、范围决定和人工意见保护。脚本比较未变/变化/缺基准/故障；用户请求本身也可开启轮次，文件相同不能吞掉明确更新意图。

Review 的设计议题记录被评完整蓝图 ref 和真实 target_ref。候选反馈使用原生 opinion/fact_supplement/suggestion/authoritative_ruling；人的原话留在既有决定记录。无蓝图目标的业务意见留需求侧。原生 checker 只判资格，实际接受或拒绝由蓝图负责方处理；若尚无可读处理结果，报告“待处理”，不得自报接受。候选资格在被评 revision 下记录；当前处理观察另读当前设计。决定的完整 provenance.source_ref 精确指向本轮反馈文件与 feedback_id 时，只显示相关决定及其原生状态，不按 #D3 等片段推导已处理。负责方实际回复原文记录在既有 update-notes.md，模型结合当前蓝图判结果；没有明确结果保持待确认，不增加自有处理结果登记中心。

| 变化 | 动作及完成依据 |
|---|---|
| 表达 | 自有稿修订、结构和人读审查；原设计 ref 不变 |
| 需求/范围 | update 内 reopen→真实确认→complete 新冻结版本→设计处理 |
| 设计反馈 | 合格候选交原生负责方；接受后取新 ref 和下游有效性 |
| 原生设计已变 | 读取当前 canonical/投影，同步受影响人读件 |
| 人直接编辑 | 先保存、理解，再送来源责任处；不把派生文档升级为整体权威 |

完整实现使用总览的交互路径；update 不隐含施工授权。已有施工结果仅查询并说明后续责任，不自动修改 CU 或重跑已完成阶段。

本轮 requested_result 从实际请求记录为 materials 或 documents：仅取材/澄清且无已有人读件受影响为 materials，其余为 documents。改变终点由实际用户请求或需同步的已有结果决定，模型不能为了 close 降级为 materials；已有 Story 受影响一律 documents。它是本轮请求记录，不复制 Framework 运行状态。

### 4.2 恢复真值表

| before / after / current | 动作 |
|---|---|
| current == before | 保持原状 |
| after 已登记、current == after、before 有文件 | 恢复 before；例如本轮已登记修改的 Story |
| after 已登记、current == after、before=null | 删除本轮新增且未被后来改的草稿 |
| current 不同于 after，或无 after 且不同于 before | 保留 current，列冲突及可比较版本；例如后来人工修改或中断稿 |
| protected | 原字节保持；例如被蓝图引用的新冻结件、原始报告 |

Review 的人工区单独保护：以上文件级恢复表只作用于 Extension 所有的内容，不能整文件回拷或删除已有人填写的 Review。复用现有渲染/人工区处理；无法确认旧议题与当前表态适配时保留当前 Review 并报告冲突，不靠历史副本代替当前人工内容保护。

有冲突设 restore_conflicted，活动轮次保持；重复恢复只处理满足明确条件的文件。无冲突设 restored 并关闭活动指针。binding、input、人签、轮次历史和发布记录保持；story_basis 重新核有效性，不伪造旧 PASS。恢复表达不能撤销已接受设计，新设计不一致显示 needs_sync。

### 4.3 close

共同条件：本轮输入已处理或有据不采用、人签原话已归入 record、无未处理恢复冲突。materials 终点在这些条件成立时可收口，明确尚未设计/成文。

documents 另需：当前有效设计与 Story basis 一致；所有受影响人读件同步、结构通过、实际独立审查结果按步骤 2 可消费。纯表达可以复用设计；新设计已接受而稿未同步不可 close。失败给完整缺口并保持 open。Framework 施工是否完成只读报告，不阻止符合本轮文档请求的 close。

## 5. 外部发布和验收

归档资格改用当前人读交付门；先展示差异、未决和未验证项，再按授权发布。失败保留本地结果，重试比较外部当前内容与上次实际基线，外部新增意见冲突交人，不直接覆盖。远程 restore 保留后续人工意见，报告内外版本差异；本地单无远端动作。

S3-01 原生完整派生/物化/复用保持实体与角色；S3-02 无新 Spec/Plan、直接阶段及共享义务持续送达；S3-03 四类反馈、缺权威、旧版本与无目标意见分别处理；S3-04 表达/范围/设计/未变请求正确分派；S3-05 四类恢复文件、人签、冲突重入和保护字节；S3-06 归档失败/外部新修改/本地单；S3-07 材料终点、update 内 reopen 及跨会话 close 不死锁。
