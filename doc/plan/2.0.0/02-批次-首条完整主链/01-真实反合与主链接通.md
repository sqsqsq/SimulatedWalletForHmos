# 01 真实反合与首条主链接通

输入：第一批最后一次评审及必要修正后的实际HEAD（T），固定B/N，全部当前参考合同。**本步开始真实merge，本步结束提交merge，不将MERGE_HEAD带入下一步或第三批。** 是完整新协议产品切换，不是只登记祖先。

## 实施与消费者

1. 按参考01写前检查，记录真实T并接入已授权台账，启动 `git merge --no-ff --no-commit <B完整SHA>`；完整产品、测试和相关资料逐路径按来源处置，保当前Plan、归档与project在途资料。manifest在本次首个产品提交为2.0.0。
2. 安装/入口用B能力加O原生entries；新schema/skills/knowledge资产、phase_bindings及正式Mermaid钩子共同成立。新版DSH模板和原生提示由第一批可重建输入取得，不写demo发布版。
3. 采用O冻结输入、原生路径桥与知识/CU链，合B最终知识/指标/来源语义，按参考02修publication签名、Feature identity、CU接受/readiness/修订薄调用。材料关卡的真实授权、知识先于决定、下游实体义务同一真源。
4. B写作/图文/Review/可选SVG和可靠性为底，接O蓝图输入、原生人读参考、独立Story原件与恢复。首读后核源、Story视觉纯函数、报告合同生产消费、登记和上传读回按参考02实现，主链不再经过需求级Spec成文。
5. 首链所需usage begin/完成、CU逻辑身份与物理目录、阶段freshness读取，以及安装器合法usage保护同时迁入。所有被声明入口的imports/共享常量/状态/原生API引用一起核，不只让新建路径可调用。
6. 对update选取O已有canonical骨架（PRODUCTS为STORY/REVIEW），按新共享接口改接并吸收B已经适用的可靠修复；不复制B以主需求spec/spec.md、plan/plan.md为更新对象的旧骨架。第三批再落实完整变化/撤回/多轮保持语义。所有受本次退出影响的消费者必须同步，残余正确性待验和显见旧协议错配分开。

本步内部可分段检查/记录，但只有一个增量交回与产品merge提交。不得为保存中间进度使用假merge、把旧1.x桥与新入口并挂，或新增临时禁用开关代替正确接线。发生核心设计不成立先保diff和现有证据，暂停受影响工作，不能用允许分批作为交付错配树的理由。

## 定向验收与提交M

用第一批公共template验证manifest全引用/入口所有权/安装同源/各保留入口可加载，并用真实公共脚本和中性合法工件验证材料冻结、蓝图读取、Story任务/章提交/报告/归档以及CU Spec/Plan输入与闭环的组合。环境/外部系统仅沿既有边界替身，不替消费生产者预先写好关键结果；静态/离线闭合不代签未知需求叙事效果。

共享接口一致、首链职责可验证、适用定向检查通过且预算符合后，显式stage获批路径，提交真实双亲对象M；核T/B都是M祖先、M有两父、最终文件来源和未完成保持项明确。**不等第三批update全部语义验完才提交M，但有已知不可加载、旧协议写错对象或首链前置失效时不提交。**
