## 1. 对象与判断方式

P=正式1.9.9 b4fbf433；O=旧2.x 19d26cad；N=实际采用Framework24ea6aeb/source226fee6f；本轮读取当前HEAD155efc55。原生要求按N固定源码/Skill核，不能只因Extension写“Framework要求”就算数。

必须分开：
- **人工决策/批准**：正常工作为取得一个人答而停，是本次重点。
- **自动审查/校验**：AI或脚本完成，不应再问“要不要继续/要不要修”。
- **真实新事实**：来源冲突、范围改变、外部被别人改过等，需要沿既有权限处理，不能借“零新增”自动替人决定。
- **环境/工具失败**：没有审查能力、不能保存原件、所有权不明等，应准确报故障，不能改称新的业务授权；也不能把“不是审批”当作没有新增人工恢复负担。

1.x已有点不因迁移重新询问；Framework例外仅指原生真实触发条件，不是对一切新增询问的豁免。

## 2. Story审查：能力旧有，当前独立流程是新增编排

P的phases/spec.md要求同一Spec阶段产出Spec/Story/Review，再由Framework harness的NEXT派verifier；spec-rules.overlay.yaml已有story_reader_review。其闭环明确：没有审查员就进入后续核对并披露未审。不存在当前story-build review prepare/check加逐版免审授权的独立链。

O把Story从主需求Spec阶段分离后，增加独立prepare/派审/接收/check，再成文登记。当前沿用。审查Story的能力不是新需求；重新接线有理由，但每个新状态、报告步骤和人审批都不能借“原来有独审”自动取得保留依据。

特别是当前design.md:103–106、flow/lifecycle.py:236–254要求无审查员时提供人的--reply，写review_waiver；材料变了重新授权。这是确定的Extension新增人工审批，不是N蓝图独立质询，也不是1.x原样迁移。

**建议退出该新增人工豁免审批，保审查结果诚实披露。** 缺少Story审查能力时究竟沿P允许的后续继续，还是仅保稿并报告未完成，属于接下来需明确的结果边界；不能自动冒称已审/通过。本版DSH效果验收必须有真实独审证据，未审绝不能算通过。N本身强制的蓝图质询不受Story例外替代。

## 4. 新机制到底干什么、为什么加、怎样取舍

| 机制 | 普通解释与增加原因 | 建议结果 |
|---|---|---|
| 蓝图关联 | 旧Spec换成蓝图后，记住这张需求消费哪份设计 | 保自动关系；不要求用户选机器ID；不同目录及重起单不是关系本身必需 |
| 冻结输入 | 保存“这一版设计依据的是哪版原件及人答”，以后材料变了也能核 | 保一次可信快照；不用用户批准每个技术文件，沿1.x已确认采用范围 |
| 原生来源物化/分类 | 把真实需求来源按Framework可读取的合同交进去 | 保来源真实性；现有权威信息直接承接，只有原生确需而缺失的信息问人 |
| 知识决定/实体义务 | 把1.x知识使用结论放进蓝图，并让CU知道自己承担哪部分 | 保有效判断及落点；不加人逐条批准适用/不适用，也不把每项展示成空取舍 |
| Story独立审查链 | 不再有主需求Spec阶段，需为Story接上原有阅读审查能力 | 保AI审查；检查重复流程是否必要；新增免审人批退出 |
| 报告对象/原件绑定 | 防止审旧稿、改审查结论、拿别轮PASS凑当前结果 | 保对象真实与原件，不让用户处理报告格式或逐版批准技术状态 |
| 设计附件 | 送审时读者能取得对应版本的蓝图参考 | 保必要交付快照，不成为第二设计真源或第二批准动作 |
| CU/freshness同步 | 设计变了后，知道哪些施工内容过期，避免沿旧结果继续 | 按已有授权修受影响部分，未授权部分说明；不每个同步动作都问 |
| 发布基线/恢复保护 | 避免覆盖外部已改内容，重复动作不重复上传/丢原文 | 保真实冲突识别；退出同范围已授权情况下的重复确认 |

新增机器机制不必然是过度设计，但必须有真实消费者；原“已有代码/已有测试”不是保留理由。对绑定恢复、安装冲突等还需要核心工程事实的项，保持待设计，不用一句“自动处理”掩盖风险，也不要求用户理解机器协议后替我们设计。
