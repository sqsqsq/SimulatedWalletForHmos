# 简化目标产物方案与2.x金样建设依据

本页为用户审定候选，不是实现指令或已批准金样。保持独立Story、送审A、原生设计真源及必要追溯，优先简化默认阅读和重复决定。

## 1. 三类读者的默认入口

| 读者任务 | 默认读什么 | 不需要先读什么 |
|---|---|---|
| 业务评审/测试：这件事要怎样工作、还缺什么决定 | Story完整正文；Review中需要自己裁决的事项 | canonical、规则编号、知识清单、冻结哈希、完整接口签名/追溯索引 |
| 开发负责人：方案是否成立、谁负责、有哪些施工依赖 | 原生蓝图人读稿的设计主体，按需展开技术参考；需业务脉络时读Story | 重新拼装所有机器字段才能理解整体方案 |
| 实施者：当前授权的工作怎样落实 | 蓝图共享事实＋所属CU及原生实际需要的Spec/Plan | 再做一遍全需求知识判断或复制整份Story/蓝图 |

目标不是“只剩两个文件”，而是主阅读入口清楚、必要信息在其责任位置完整，不靠来回翻多份才能确认业务。

## 2. 产物合同

### Story：完整业务正文

覆盖真实输入与已定范围、角色/入口条件、正常流程、各条件/异常/未知结果、用户可见状态及动作、恢复边界、未决及验收。图与文字同节按场景互补，重要路径不能仅在技术附件出现。标题以业务主题为主，不把实现模块表当用户旅程；不限定固定字数、图数或十章即合格。

只讲影响业务理解的接口语义和知识效果。例如身份保护写成谁能看/改哪份数据、结果未知写成等待/查询/再次操作条件，不展开完整schema、所有知识ID和被否技术方案。已有原生事实可以按业务语言重述，但不能在这里另作相反决定。

### Review：真正需要决定的事

由现有决定真源形成，保人工区和真实原话；区分已决定、待决定、建议与仅供参考。每项写影响、选项/取舍、决定权及下一步；不要把每条规约、每个INFO或已授权交付目标变成用户必须再回答一次的问题。不存在真实缺口时可没有待裁决项，不造固定条数。

### 蓝图：完整设计真源和原生人读参考

canonical仍负责真实设计与关系；人读稿正确投影，不手工维护第二真源。设计主体应可理解整体方案、职责、必要接口/状态/恢复与关键取舍；技术参考按需查精确字段、来源和稳定地址，不能把它作为业务单读前置。

知识呈现推荐值：
- 机器侧按1.9.9的域和实际业务单元判断：整域不命中保真实理由，命中域内保逐项覆盖；适用义务挂承担实体，模式角色落实际对象，同一判断一次定案。
- 人读稿展开真正改变方案的适用决定、豁免、争议和待决；不适用登记保依据但不逐条生成“选了什么—/被否方案未记录”的决策卡。
- Story只表达这些决定造成的业务效果，CU只落实自身义务，不再复制判断过程和知识正文。
- 原生renderer当前不能正确呈现的部分需其所有者支持或修复约定映射；Extension不得后处理裁剪带签名投影、改canonical凑格式或新造简版blueprint.md。

技术参考虽可按需阅读，当前原生导出的完整内容仍保留。若要物理折叠/拆分/减少默认输出，先取得Framework公共能力，不能在金样中伪造一个现接口不能生成的合格附件。

### CU：按获准的设计交接或实施目标产生

纯业务送审时零CU合法，送审不自动授权CU准备或施工。用户可以只授权完整设计交接：准备CU而不启动施工；也可授权实现方案到Plan或后续实施。按本轮目标经原生ID/路径接受与修订；已满足义务合法复用，不强制再写Spec。Plan只细化当前CU的结构、落点及验证；共享事实引用蓝图，不把每个CU做成一套全需求规格。

### 材料、附件与过程件

原件、人答、采用/未采用理由、图资源、冻结快照、独审原回复和回执仍按消费者保留。原生人读稿发布为AR/design-review.md时是一份绑定当前版本的参考快照，不能独立编辑或重新决定。日常无需多处反复复制/解释同一内容。

金样主件不塞运行日志、哈希表、完整门禁输出或使用计量；它们在证据域有可追溯位置。正式Mermaid及实际资源保持，可选SVG须有阅读收益和原有审查绑定，不强迫制作。缺输入不靠占位件掩盖。

## 3. 目录：已定单需求根，不保双目录目标

用户已明确按1.x思路统一物理需求目录。目标及正常路径消费者以[闭合表§2–3](04-三项核查闭合与适配处置.md#2-统一目录目标与准确的原生边界)为准：

```text
doc/features/<需求ID>/
  RR/ SR/ inbox/ assets/ ux-reference/
  AR/                   原件、Story、Review、设计参考及必需过程件
  blueprint/            原生设计
  <CU-ID>/              获准设计交接或实施目标实际需要的CU
```

不再另选bp-ID或执行独立bind-design。需求身份确定蓝图工作区，组件归属和精确ref仍依原生合同。当前N会把根ux-reference与blueprint共存判为歧义，所核接口没有辅助目录豁免参数；需要原生公共能力承接，不能让用户重新接受双根。AR/story.md本身不在N施工标志中。

旧双目录只描述待替换的现有实现，不再作为金样推荐基线；原生支持未取得前，目录目标可审定但不伪称已可执行，不移动测试现场，不另造兼容或改绑恢复机制。

## 4. 门禁与人机协作的简化目标

| 层 | 保留 | 收回的过强行为 |
|---|---|---|
| 结构/身份 | 原件不改、来源真实、必需输入、指针/报告身份、文件/引用与输出可消费 | 用字段存在判语义充分；给坏稿补占位再判通过 |
| 设计/施工 | 原生真实依赖和当前blocker限制相应施工；来源未知明确保留 | optional资产未证明依赖就停所有工作；把未来实现缺口挡成文/业务送审 |
| Story业务送审 | 真实未决披露、完整业务、核源、有效独审及交付协议 | 仅因蓝图未施工准入一律不让评审业务草稿 |
| 独审 | 蓝图核设计成立，Story核单读完整/忠实；每个对象独立语义责任和必审输入保持 | 两次不分职责全文重做、为INFO固定再审、同对象未变反复生成证据 |
| 人的决定 | 范围/权限/真实业务取舍必要时问；interactive只记录真实人答 | 重问已有有效授权、建议当批准、headless_assumed当真实人签 |

共同来源中哪些核对可复用，要以同输入同职责为证，保每个独审发现各自对象遗漏的能力；不先删除必审材料、不共享一份PASS代替两个对象、不增加固定审查轮数。机器失败按真实前置/工具问题处理，不让作者修改被测Extension绕过。

## 5. 金样建设的明确范围

拟沿现有test/golden与TEST审定流程，不新建评价平台。本次不写入金样正本；未来候选先放维护评审材料，用户审定后才晋升。

| 目标情景 | 拟展示的完整目标 | 不移签的前提 |
|---|---|---|
| auto初段 | 系统材料→设计参考→完整Story/Review→正式资源与送审/归档对应关系；无施工时不强造CU | 旧金样200元、恢复查询/模拟能力等逐项核本次材料/已授权人答，不能把旧模拟前提藏进新输入 |
| car初段 | 本地材料→设计/Story→真实授权后的合法CU到Plan，图文与接口责任一致 | 48小时、待接受撤回、转分享、断网下线、模拟工程前提分清已答/建议/未答，不由金样替用户答 |
| update补充情景 | 在初段固定对象上，明确谁改变哪份材料/决定、授权终点、受影响设计/CU/Story及保持的原件/人签 | 旧两组明确不含update；新增目标需单独明示场景与输入，不由旧金样自动外推 |

先推荐确认新初段目标包；update目标单独列清并审定，不能将本版update能力排除，也不擅自扩大旧金样审定范围。无关临界故障和设备矩阵不加入金样正文。

每个候选包用既有README说明输入身份、人答、模拟前提、维护设计细化与未决；附目标Story/Review、原生完整蓝图组、实际需要的CU阶段产物、图资源与必要来源。金样是效果参照，结构化工件只作为其一致性配套，不把所有过程状态都封为黄金格式。

## 6. 审定清单

- 单读Story能回答范围、流程、异常/未知、权限、恢复及验收；不需要技术附件补业务缺口。
- 蓝图主体能说明设计，技术参考中的接口/验收/用例确实有效；没有空取舍卡或不明意义的重复声明。
- 同一决定在Story、Review、canonical和CU一致；合法表达不同不算错，未决不被写成确定事实。
- 知识对实际承担对象有可指认影响，Story表达业务效果、CU落实义务；不以名称/数量/覆盖表自证应用。
- 不把材料效力、金样模拟前提与真实人答混淆；图、表/文字、叙述、知识及成本并排看。
- 前次复核快照中的两条CLI样本均未完成目标且auto曾改执行件，其产物可供诊断，不能直接作为审定正本。
- 目标稿的静态/语义审定与真实DSH效果分别取证；没有真实运行就不写“送审/归档/独审已验证”，用户审定分数与发布另行决定。

## 7. 明确不采用的简化

不合并掉用户已选择的独立Story；不让Story成为蓝图碎片；不删有效知识、原件保护和恢复；不为减体积删必要契约/异常语义；不靠字数比例验收；不改原生生成稿；不把运行态哈希目录数量当金样评分；不新增第三份可见总览文档或第二真源。简化的目标是责任与阅读清楚，不是文件越少越好。
