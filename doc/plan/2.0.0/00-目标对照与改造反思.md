# 2.0.0 改造依据与裁定

2026-09-29，维护设计者。当前方案以[总览](01-实施总览与协作合同.md)及四步分册为准。本轮按用户单独确认，以本仓 main→story 的 Framework 3.1 接入为首项工作重整；本页保留真实改造依据，历史论证由 Git 保留。

## 1. 整体判断

需求材料、人工保护、章节写作、知识解析、实体义务和对接能力继续承担有效业务责任。替换对象是需求与单一 Feature 的路径耦合、Spec 附属成文与交付、固定阶段知识判断、整树恢复以及自有入口分发。

框架采用蓝图并不要求 Extension 成为 CU 管理器。需求侧保留完整理解和一套人读交付，Framework 保有设计及施工权威。主模型在原生 interactive 路径完成已有授权的工作，Extension 不创建 Goal run。

## 4. 方案自身必须纠正的点

1. 先接入 main 的真实 Framework 3.1 并同步 story，再适配 Extension。1.9.7/1.9.8 已交付；Framework 版本号相同不能当作构建相同。
2. 文件角色不能从旧 files 对象照搬；C 先核原生合法实体和完整派生链，再裁定是否必须增登记，不预设改 Framework。
3. 原生整文件物化的观察说明必须核保护，不足以直接裁定新增计划 API；D 先组合真实原生能力与现有安装预检，仅对必要缺口提出修正。
4. phase binding 是模型指令入口；独立审查还要经 pre_verifier 的实际输入送达，不能把绑定登记当执行。
5. `reopen` 必须能在 update 内完成新范围确认；输入和原话保留，不能出现方法页允许而状态机拒绝的死路。
6. update 允许止于材料请求；没有 Story 的资料更新不能被 close 强制要求完整设计。
7. canonical 内的施工义务只存稳定决定 ID，完整版本身份由外部 CU 引用提供；退出会让蓝图摘要引用自身的完整内嵌引用设计。
8. 已完成旧版报告保持历史意义；新的 source/schema 例证只能证明局部合同，不能冒充完整产品接入。

[1.9.9 分析报告](../../spec/1.9.9/04-稳定性与性能分析/01-分析报告.md)提供审查对象自激和 reopen 冲突等风险信号。本版分别由 B 的稳定审查对象和步骤 2/3 的状态合同覆盖；金额/单位、写法选择等其他优化仍在其原需求，不纳入本版范围。

## 5. 最小实现与必要上游成本

复用现有 flow、章节合同、知识 parser、实体访问器、安装器及测试装置。新增冻结模块处理历史引用不可变性；薄 native adapter 统一跨 Python/Node 的原生读取；story-knowledge 提供当前动作任务。它们分别替换旧提交、路径/来源解析和作者材料装配，不引入通用状态、调度或插件框架。

A/B/C/D 为设计知识、人读审查、施工承接和安装保护四项核对。直接使用实际 3.1 的已有能力；设计者在明确证据后提出必要差异，局部停止范围也由其明确。本轮不批准四项上游新增，也不估算一组尚未确定的 Framework 改造工作量。
