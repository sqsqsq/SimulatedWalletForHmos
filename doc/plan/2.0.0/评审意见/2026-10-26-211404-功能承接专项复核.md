# 功能承接专项复核

2026-10-26，维护设计者。用户在历史归档专项分析之后追问“除了文档，功能方面还有此类问题？”本轮按能力而非文件数量复核 `647ee702`，对照正式1.9.9/B′ `9c865bfb`、O `19d26cad`、固定Framework N `24ea6aeb`以及有效2.0.0 Spec/Plan和标准@19。

**结论：有，至少发现两处现存的承接缺口：独审完整材料覆盖没有接全，以及CU文档编号/引用自洽保障退出后没有明确承担者。** 前者是当前主链的正确性缺口；后者同时暴露迁移设计映射错误。它们不能仅标成第三批“尚未验证”，也不等于所有1.9.9功能都已退化。

三个gpt-6.1-sol只读调查分别核退场与测试、材料/独审/归档、usage/stats/adapt；主评审核实际代码和最小函数探针。不修改产品/方案，不跑模型CLI，不改在途2.1.0与diagnosis资料。此前R1–R4的具体修正保持关闭，本报告增加它们未覆盖的功能迁移判断。

## 1. F1：独审覆盖对象缩窄，任务与检查器使用了不同集合

### 原能力及当前缺口

B′ `extensions/hooks/shared/review-inputs.mjs::reviewInputs()`按材料清单枚举阅读稿、每个图片对象及会议corrections.json；只取图的原件另核存在。它不是强迫审查者直接全文阅读所有二进制文件，而是让作者的采用选择不能缩小完整核源责任。标准A3/A4/A6及独审输入覆盖保持这一目标。

当前 `extensions/skills/story/scripts/core/story/review-object.mjs:40–111` 枚举Story/Review/设计附件、写作设计、决定、部分会议材料、冻结快照中的files、蓝图与知识。其中`:82`后的来源主体是作者adopted集合及选择的人签所形成的冻结文件；没有从materials.origins.readable_paths、未采用图片及会议纠偏留痕补齐完整审查集合。

与此同时，`extensions/hooks/shared/reader-review-task.mjs:335`仍列完整来源并要求核“没采纳的新值或冲突版本”的依据，`:340–350`要求查看raw.md、corrections.json、evidence.md，后续图片段也列作者登记不用的图片。这说明业务审查职责没有被有效裁定取消，材料也不能笼统说完全没送达。

实际断点在消费者：`independent-review.mjs:458–470`的coverageBasis只把reviewObject.rows作为必审集合，且alias为空；`:513–519`只允许发现定位引用这个集合里的路径。结果是：

- 作者未采用的冲突阅读稿或图片若不在该集合，审查报告漏读它也不会触发必审缺项；不能由此证明作者排除材料的依据已经核过。
- 审查者依任务读取这些文件、发现问题并引用真实路径，反而可能被报告结构门判为“不是这一次审查材料里的文件”。
- 冻结采用版本与原始阅读稿的路径关系也需统一，不能让任务给一种有效路径、发现定位只接受另一种而没有合法对应关系。

这是正常材料冲突/取舍、会议纠偏路径上的问题，不需要极端故障构造。当前源码的集合生成及成员判断足以确认合同错配；本轮未运行真实模型，不声称已经在某份实跑产物中造成漏判。

### 最小修正方向

在现有reviewObject责任处承接完整审查输入，复用已有材料/图片/会议枚举能力，供任务、材料键、覆盖声明及发现定位共同消费。采用的设计依据继续读取其冻结版本；核“为何未采用”的材料保留真实身份和必要阅读入口，不把当前活跃材料静默替换成冻结依据。允许有身份依据的额外取证与路径对应，仍不得用额外材料顶替必审项。

验证只需现有报告/材料用例中的两个结果：未采用但必须核源的阅读稿或图片不能静默漏审；对它的合法发现引用可被接收，并仍拒绝虚构或无效引用。会议纠偏沿相同集合规则覆盖。不要删除完整核源判据、强制采用全部材料或新建第二审查服务来求通过。

## 2. F2：CU文档引用/编号保障未承接，迁移表还把职责分错

B的 `hooks/shared/chapters.mjs`包含chapterRefProblems、chapterNumberProblems等确定性检查。它们有一部分保护的是“表格写2.架构，而实际第1章才是架构”“子节号与所属父节号冲突”等内部自洽性，不是要求Story只能有固定十章，也不因主需求Spec改成蓝图而自然失效。

该模块和test_chapter_numbers.py已删除。当前 `hooks/shared/host-chapter.mjs:28–58`承接的是锚点存在、所需小节、规约/验收引用和埋点表位置；真实消费者仍为spec/post_check:128及plan/post_check:212。N的check-spec/check-plan必需章节检查只核章节名存在，未接替上述编号引用关系。

对现有公共hostChapterProblems的纯函数探针中，错父子节号、错误带号章节引用均返回空问题列表。证据：[chapter-check.json](../../../../output/evidence/2.0.0-capability-audit/chapter-check.json)。此结果只证明替代函数没有该职责，不冒称整条原生流水线或独立语义审查一定放行。

迁移表也有明确缺口：参考15第8行仍将test_chapter_numbers列为二-01保留有效行为；第32行把test_host_extension_anchor归为“安装与宿主”，参考12用loader/entries一组承接。后者实际测Spec/Plan文档锚点，并不是宿主Skill入口安装。这是设计者按名称归类造成的职责错配，不能仅要求执行者补回同名文件。

**修正边界**：先保留仍有效的内部编号与引用准确性，按新模板及职责决定放在Framework还是现有扩展检查；不得直接恢复旧固定章号或整套旧模板约束。N当前Spec模板的宿主扩展章在258行且无号，Plan模板160行同样无号；没有充分依据把B的“宿主章之后只能附录”直接提升成N硬规则。首次调查将锚点位置/附录尾序一并归入退化，进一步核N后收窄本结论：位置要求属于待确认设计变化，不能为此先加门禁。

本项的完成应是当前有效自洽保障有实际承担者和对应回归，或者对不再适用的旧检查明确退出依据；不是把测试清单改成“已退出”就算关闭。

## 4. 为什么此前检查没有识别

共同问题与archive相似：文件存在、函数有调用、模块清单和通过数量，证明的是局部迁入；它们没有证明“原能力的输入范围、错误发现和下游消费”完整承接。

- F1复用了O独审对象与B完整核源任务，二者各自成立，组合时却没有统一必审全集。R3保护了报告原件，也不会自动发现报告究竟漏审哪些输入。
- F2把旧Spec运行机制与仍有效的文档自洽保障一起退出，又把文档锚点测试误映射为安装入口测试；新测试数量增加不能冲销这项保障。
- 参考15仍是设计时清单，部分条目目标文件已不存在但状态仍not_run。其本身是交接记录不足，不单独证明全部能力丢失；本轮通过真实消费者核出上面两项。

设计与评审应承担这次漏核责任，不能归因成执行者没有机械复制全部1.9.9文件。历史已知限制也不能误作所有回归均被接受；1.9.9按限制发布，不等于本轮可新增遗漏。

## 5. 对后续的影响

F1应作为当前主链的一项集中修正，先于依赖这套独审证据的真实里程碑及第三批完成结论；F2纳入同一轮能力承接核对并修正迁移映射。可以与第三批已有工作合并交回，但要点名结果、承担者和对应证据，不能写成笼统“第三批最后检查”。不重新merge、不恢复所有旧实现、不重建测试平台，也不立即增加真实CLI运行。

下一次能力保持核对至少串起：旧使用效果及有效依据→当前生产/消费路径→退出或替代说明→必要正反例→真实未覆盖。沿现有标准和迁移表补齐，不另造一套总评测框架。此前R1–R4已关闭的局部结论不撤回，但不能将其解释为第二批所有功能都已完整保持。

本次仅新增分析与定向函数证据，未修改源码、Plan、标准或历史原件，未提交/推送，未启动真实CLI。以上是本轮查实的两项，不宣称剩余全部能力已经穷尽审计。
