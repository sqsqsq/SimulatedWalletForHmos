## 2. 必须修正

### R1（P1）：本次冻结输入与蓝图没有消费关系校验

位置：story/design-source.mjs:designSource、flow/routing.py:design_stage_step。当前只分别验证 snapshot.json 与蓝图准入/投影，并比较 component_id。蓝图的 discovery.inputs.current_scope_items 是否引用本次交付来源没有检查。

独立反例：正常完成材料/范围确认与 complete，关联 wallet-main/AR90001；放入同组件且改成该蓝图标识的余额刷新准入夹具，它的来源仍是 doc/requirements/wallet-balance-refresh.md，不是本次冻结输入。designSource 返回 problems=[]。现有 design_fixture.hand_to_design 也先放这份无关蓝图再 complete，因而一批绿色用例没有证明需求被当前设计消费。

修正：按步骤 2 §4 的 scope_items 生成本次预期的原生来源条目，用原生 currentScopeItems/来源解析结果核 item_id、kind、源路径与原始摘要，authority/provenance 不得与交给设计的事实冲突。允许既有蓝图包含其他有据条目，不要求全蓝图条目集合相等；本次条目须被消费，缺失或仍引用旧版就停在等待设计同步。源路径按原生 resolver 规范化，锚点与文件摘要遵从原生规则。status、skeleton、basis、登记和交付共用这项结果。

正例夹具必须把本次真实冻结来源交给蓝图、按原生要求生成有效关联与投影；保留旧版蓝图/另一需求蓝图作为反例，不只替换 blueprint_id。需求内容是否真正被设计落实仍由独立语义审查判断，脚本只核显式消费关系。

### R2（P1）：冻结文件损坏在成文入口不被发现

位置：story/design-source.mjs:readSnapshot。它只核 snapshot.json 自身的摘要，没有核 snapshot.files 指向的文件。独立反例在上述工作区改坏冻结提取稿，snapshot 与 flow 不变；再次 designSource 仍 problems=[]。即便蓝图原生 checker 核了范围条目的来源，也不会替 Extension 核未作为 scope_item 的图片、提取稿等全体输入。

修正：共用冻结模块的只读校验，核目录版本身份、snapshot 摘要及每个文件的存在、边界与原始 SHA-256。后续消费者不能仅因登记曾成功就相信当前磁盘；只读校验不改冻结件。缺图、改提取稿、改人签导出均须在成文/审查前报具体文件，保留旧 input/basis。把这一职责接到现有 frozen.py 的 verify（经薄调用或共享确定性实现），不要再维护一份不同的快照规则。

### R3（P1）：文件类别被脚本升级成权威来源

位置：materials/frozen.py:PROVENANCE、selection、materialization。original/image 一律 authoritative/as_confirmed；材料关卡确认“材料齐了”不能证明其中每句话都是正式授权结论。只按文件类别赋值也丢失实际来源/转换依据。human_records 扫全部轮次的 accepted 记录，未区分历史接受与当前有效，旧 ask_id 仍可重新导出为当前人签。

修正：角色只决定 original/image/extracted_analysis 等用途；source_kind、evidence_strength、extraction_method 从实际材料来源或本次有据判断取得。design-input 可为采用项登记 source_evidence（以需求相对路径为键，含 provenance 与 evidence_refs），核指向采用材料或真实人签，保留实际登记中的取得/转换关系。无权威依据的文件读取最多标 observed，派生判断为 inferred；authoritative 必须有实际权威依据，由设计及审查核语义，不由文件后缀推断。人签从当前有效关卡（含现有合法承接规则）导出，历史记录保留但已被 reopen/新决定替代的拒绝作为有效输入。

observed_at 裁定：能取得原始来源时刻则保留；只能证明本次冻结时读到文件时，可使用冻结观察时刻，但 extraction_method 明确为本次文件观察，不冒充原取得时间。snapshot.observed_at 表示冻结动作。合并人签文件可记导出观察时刻，每条原话仍保留各自 at，不把所有裁决说成 max(at) 时作出。原生要求 owner/formality 而事实不足时按原生缺口处理，不填一个虚构权威人。

### R4（P1）：登记失败删除旧依据；登记对象也不完整

位置：flow/lifecycle.py:cmd_story（123–127 行）、flow/state.py:STORY_REGISTERED/ledger_digest。重复登记起手即删除 story_basis/story_written_at 并保存 complete。独立反例：已有登记，Story 文件缺失导致失败，旧 basis 已消失。与方案“story 失败不改旧 basis”直接冲突。

另有两个共同责任问题：files 只含 Story/decisions/template，漏 Review 人工区等已声明审查材料；仍使用换行归一化的 16 位摘要，不是方案的原始完整 SHA-256。project/number/build 在审查之后的登记动作里仍可改变被审对象；没有最终对象比较，不能保证审的是实际交付那份。

修正：project/number/build 放到审查准备之前，把最终 Story/Review 及稳定决定投影纳入同一对象。登记只读校验最终对象和审查结果，通过后一次写新 basis；失败保留旧 basis，派生为待同步而非继续交付。相同对象重复登记不变更对象身份。按方案列全材料，混合台账由所属模块导出排除时间/历史报告的稳定投影，哈希用完整原始 SHA-256；Review 人工正文有变化必须失效。旧 ledger_digest 可保留给原有材料比较消费者，不能冒充新审查摘要。

### R5（P1，含设计缺口）：接线未完成被伪装成审查能力缺失

位置：story-build.mjs:cmdReview、story/delivery.mjs:deliveryProblems、phases/design.md。check 固定报 reviewer_unavailable 且退出成功；交付门返回 problems=[]。缺原生调用实现与实际宿主不能独立派审是两件事。此行为违反 S2-07，并把开发占位分支放进正常交付路径。

修正按步骤 2 §5.1 接真实 request 能力。接线/输入/工具故障阻断并返回责任；只有宿主实际能力判定不可用才走已有未审授权。检查不接受作者自写的 PASS 取代报告。Story 判据、任务与 gate 用一份材料集合；读取 Review、有效人工决定、采用版本原文和激活知识，不能只在判据里提到知识却不给原文入口。原生 request 没有自动派 verifier 的行为，宿主负责真实独立审查；不得把 Feature verifier 的身份塞进去。
