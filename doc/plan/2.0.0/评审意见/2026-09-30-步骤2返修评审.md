## 2. F1：按检查 ID 跳过原生失败（P1）

位置：`extensions/skills/story/scripts/core/story/independent-review.mjs` 的 failing 过滤，`c.id !== 'issue_to_file'`。

独立复跑现有 advice 正常夹具：Extension 返回 warn、允许交付；同次原生 summary.verdict=FAIL，issue_to_file=SKIP/BLOCKER，原因是 Markdown 不在其文件后缀枚举中。这不是已声明 not_applicable，Extension 也没有完成同责任的合法原生核验；按报错 ID 排除后继续，属于绕过原生门禁的局部补丁。不能以“Markdown 是合法输入”推出“该检查永远可以丢掉”，否则不存在的 Markdown 引用也不会由这一项发现。

裁定：删除此豁免。原生 FAIL、未声明不适用的阻断 SKIP 如实交回，不能归成 pass/warn；无阻断建议可交付这一产品目标保持，由 Framework 修正 request 的文件引用识别实现。已形成[Framework 专项反馈](2026-09-30-Framework3.1专项审查文件引用问题.md)，不用本仓改 vendored 副本、不引入第二份通用引用检查、不伪造源码后缀或无关代码引用来过门。

这是当前已复现的上游局部缺口，影响“问题表只引用 Markdown 的独立审查”；无问题报告及其他独立适配工作仍可继续。本轮不宣告 Framework 整体不可用，也不把这一已知失败留到付费 CLI 重复发现。

## 3. F2：正常 UI 需求与蓝图共目录（P1，设计责任）

既有方案令 blueprint_id 默认等于需求标识，而导入器正常把参考图放到需求的 ux-reference。原生 FEATURE_MARKER_DIRS 包含 ux-reference，enumerateFeatures 对同目录同时有 blueprint/ 与平铺 Feature 标志明确拒绝。实施者没有擅自绕过，交回正确。

独立验证：同目录失败；在隔离副本仅把蓝图工作区分离到另一目录、保留需求 ux-reference 后，原生 enumerateFeatures 成功。此探针只证明目录枚举，改后的完整设计/审查链仍由实施者验证。

裁定：**保留需求材料目录；蓝图工作区使用不同的显式身份。** 新单建议 blueprint_id=`bp-<需求标识>`，调用者仍显式传 `--blueprint`，按原生安全段校验。需求目录与蓝图根目录必须不同；已有设计按指定的原生身份接续，也须满足分离。标识冲突明确报出，由调用者选择实际对象，不自动搜索、改绑或循环换名。错误新单按既有规则重起，Extension 不移动已成立的 Framework 工作区。

这比搬迁所有 UX 材料与视觉链路、或放宽原生身份规则更简单。实现同步 bind-design、作者指引、status/帮助、设计夹具与回流映射；不要新增“有 ux-reference 才换名”的条件分支。测试正例用真实异名关联且保留参考图，从冻结、蓝图消费到 review prepare 完成。CU 始终使用 Framework 身份，不把需求目录当 CU。
