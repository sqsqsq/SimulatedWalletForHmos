## 2. R1 尚未闭合：spec 缺原生需求恢复与校验步骤（P1）

位置：extensions/hooks/shared/framework-access.mjs:readFeature 中 resolveCapabilityResolutionEntryInput/resolveCapabilityInputs 的参数组装。

原生 harness-runner.ts:990–1023 在无 run 的 spec 路径先做：featureRequirementBinding → resolveRequirementInput（显式来源或绑定来源文件）→ readBoundInput 核原绑定，再把 requirement/requirementSourceFiles 交给入口组装与阶段 resolver。Extension 只做了后半段，两个字段都未传。

独立复现：使用 test_knowledge_task 的真实夹具与原生 prepare-scope/ensureFeatureExecutionScopeFrozen，保持同一冻结对象、来源文件和当前契约。只读执行原生 spec 的需求恢复及绑定核验后：

```json
{
  "native": {"assurance":"full","requirement":"resolved","blocked":[]},
  "extension": {"status":"invalid","assurance":"blocked","issues":[{"code":"capability_blocked","message":"capability_spec_requirement 被原生判为缺必需输入（requirement=absent）"}]}
}
```

这是 Extension 少传参数，不是 Framework 无法取得该需求，也不能归到 coding 的 F6 观察项。没有运行完整 spec checker，本对照只证明同一原生输入解析在完整参数下成功。

修正合同：适配层沿原生当前阶段完整的输入组装/校验责任恢复需求，复用 featureRequirementBinding、resolveRequirementInput、readBoundInput 等现有函数；必要时把调用者已有的显式 requirement/requirement-file 交入薄入口。文件绑定按原路径和摘要恢复；inline/无可恢复来源时要求调用者提供实际原文并核绑定，不能用 requested_results、蓝图摘要或 README 猜正文。已冻结输入不以其他来源回退顶替，读取仍不写 scope/receipt/report。

验收至少补：文件来源的冻结 spec 与原生同结果；来源字节变化报原生 stale；inline 来源不足明确缺口、给正确原文才可继续；知识任务和 pre_verifier 在同一合法 spec 对象上不再误报缺需求。plan/review 的已通过来源选择和过期反例保持。

## 4. 首阶段范围冻结时序裁定

责任分开：知识读取器始终只读；开始已授权阶段工作的主模型负责调用 Framework 的阶段准备能力。

1. 没有有效候选时，主模型先走原生 prepare-scope，用真实需求与影响依据生成候选。单纯查看知识不因此获得阶段执行授权。
2. 本次已经授权开始该阶段、候选可用而 scope 尚未冻结时，由主模型委托已存在的原生 `feature-execution-scope.ts:ensureFeatureExecutionScopeFrozen({projectRoot,frameworkRoot,feature})` 完成首阶段范围准备；该函数承担原生校验/写入，Extension 不复制逻辑或手写冻结记录。
3. 返回 frozen/reused 后重取当前阶段知识任务，确认原生输入及相应知识义务后才形成受其约束的产物。已冻结则直接取当前有效任务；原生失败照实交回责任，不绕过。
4. 不为冻结提前跑完整阶段 harness，避免在产物未形成时额外触发编译/测试/审查。知识任务本身不调用冻结函数、不启动后续阶段，不新增私有推进循环。

当前 scope=not_frozen 的成功输出只能作为知识预览。实施者在 story-knowledge 入口及缺口指引中把“先原生准备、再重取、再动笔”写清，并补一个用现有原生函数完成准备后能取得真实输入的顺序用例；模型实际是否遵循仍由 CLI 观察。此裁定补齐方案时序，不要求 Framework 新增接口。
