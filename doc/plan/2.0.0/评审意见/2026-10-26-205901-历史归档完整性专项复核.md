# 历史归档完整性专项复核

2026-10-26，维护设计者。对象为 `647ee702` 下的归档及历史承接，关联O `19d26cad`、B `44cba622`、完整反合源B′ `9c865bfb`、反合前T `a05a3634`和merge `61a1446e`。用户连续指出：story-1.0还有大量文件未同步；archive处理使story自身历史不够完整；问题不止目录和链接。本报告复核这些纠正，不重写历史原件或执行目录迁移。

**结论：选定快照的字节保全基本成立，历史作为一个可阅读、可核证、可辨认有效性的整体，尚未成立。** 缺口涉及选取范围、证据依赖、金样身份、分支叙述、历史决定有效性和导航，而不是只需换一个archive目录名。没有证据支持“所有旧历史已经丢失”；同样不能继续以manifest全匹配、Git可恢复或真实merge成立，推导“历史已完整承接”。

## 2. 实际问题

### A. 保全范围按版本目录选择，没有覆盖历史结论所依赖的材料

归档保存了评审正文，但评审中的关键反例和测量不一定跟着进入story。已抽到三件：

| 历史结论引用 | 依赖原件 | 当前情况 |
|---|---|---|
| B 2026-10-13全局评审，部分写入反例 | `output/evidence/1.9.9-global-review-20261013/import-partial.json` | 仅story-1.0本机目录存在；不在B Git、不在当前story、不在external manifest |
| B 2026-10-16整版功能与预算复核 | `output/evidence/1.9.9-budget-20261016/measurement.json` | 同上 |
| B 2026-10-12整体设计08-R7，原生材料/请求关系局部复演 | `output/evidence/1.9.9-design/material-probe-result.json` | 同上 |

三件并未在源仓丢失，但当前story归档无法仅靠自己核实这些结论。`doc/archive/story-1.0/44cba622/README.md`将未复制output概括为按 `44cba622:<原路径>` 或批次一保全包取得，适用范围写得过宽：Git忽略的原件无法用该SHA取出，选定保全包也没有这三件。原交回本来已披露排除其它历轮suite/evidence，归档导航却未准确承接这一限制。

**修正方向**：先按仍要追溯的评审引用补齐必要原件及其输入/结果绑定；未取得的列出确切缺件和影响，不复制所有缓存或无限扩展所有运行记录。Git内对象与Git外证据分别给真实取得位置。

### B. 旧story金样的历史身份没有成套承接

当前B的27件金样已完整同步，这不能替代旧O金样的历史保全。O的16件test/golden对象中，当前doc/archive只找到5张图片的相同blob；另外11件没有同blob归档副本，包括旧Story/Review正本、说明、银行卡候选组及image1/image2。原Git对象仍可恢复。

旧2.0.3的五组候选及其图片确实保存且可读，但历史金样状态报告明确它们尚未转正。不能因为“archive里也有一个Story和相同图片”，就拿候选或新版金样替代历史评审当时的正本。

**修正方向**：从固定O恢复成套旧金样及原README/候选身份，保持当时正式/候选状态；给历史评审一个能直接到达该组原件的入口。当前test/golden继续使用B已审定版本，不把历史正本恢复成现行判据。

### C. 证据仍依赖可清理的scratch，与长期历史定位不匹配

旧2.0.4宿主接缝定案引用 `output/scratch/2.0.4/dispatch-contract/source.json`；四步骤交回评审引用 `review-product-delivery/result.json`及驱动脚本，历史预算也有scratch中的measurement/churn。抽查对象尚在，不应判已遗失；但按当前TEST它们可随时清理、且被Git忽略。

**修正方向**：把被历史结论实际依赖的原件按原字节保全到持久证据位置，保留旧路径/来源身份及新的取得入口；历史报告原件不重签。不要把整座scratch永久化，也不要声称普通checkout自带运行证据。

### D. 去重保持了字节，却拆散了story自己的阅读上下文

story-before-rewrite只有3件差异文件，其余904件需通过JSON映射到story-1.0归档。一个具体例子是story自己的1.9.8发布说明：上版发布说明、需求与方案链接在该快照里不能直接打开；旧1.9.9导航又跨到legacy-2.x的旧2.1。读者需要理解来源提交和映射规则才能复原当时版本。

不能简单认为“去重本身就是错误”：同blob共享存储可以成立。实际缺的是一个完整的story历史阅读视图和确定的引用解析；仅补一份总README，或把907份都复制一遍，也无法自动解决外部证据和旧金样问题。

筛查中，已绑定源提交的167处缺失相对文件目标在原提交存在（B归档145、重写前快照15、story差异快照7）。其中有设计上允许回Git读取的源码，不能把167全部当必须复制的文件；但需求、方案、发布说明、审定依据之间的核心链不应只留一句“请查Git”。另有迁移前已缺引用，保持原缺失身份，不归责这次迁移。

### E. 演进记录合并了两个分支，缺少事件发生在哪条线的说明

`test/EVOLUTION.md:30`与`:36`重复记录同一个d19b26f7发布；`:8`是story-1.0的1.9.9发布，`:34`是story的Framework3.1+Story1.9.8 demo接入。这些事件各自真实，不能拼成同一消费工程的线性升级史。当前入口另有7处指向已移走的1.x发布/评审资料。

该文件`:16–24`的“不承接施工单位终点”等属于当时1.9.9吸收2.x Case改进的边界；`:120–132`仍有旧方案“当前设计/实施”“当前实现以……为准”“只以……台账为准”等强权威措辞。文件顶端有历史提示，但正文的时点和效力不够清楚。

对比T/B′确认，O独有Framework接入事件和B′维护事件都还在，未发现merge整段抹除。问题是事实合并后叙述未调和，不应通过删除其中一条分支的历史来去重。

**修正方向**：事件注明分支、当时版本/消费工程、固定提交；共同事件只保一个清晰叙述并列来源差异。历史“当前”限定为当时时点，保持原决定原意；新的有效依据单列，不反改旧结论。

### F. “归档”“被替代”“未完成”不是同一种状态

当前Spec已明确旧2.1待承接内容不因重写取消，七组1.9.9遗留进入本轮2.x，原1.10评价系统已完成且复用。这些是正确保护，不能在整理时把所有archive统一标为废弃。

同时存在story-1.0旧2.0.1、story旧2.0.1，以及重写后新2.0.0、新2.1.0等同号轮次。仅按版本号归并会把不同目标混为一件事。当前若干README已有局部区分，但缺少全局演进关系及未完成项的当前去向入口。

**修正方向**：保留来源线和轮次身份，区分已完成历史、被新职责接替、仍作为现行依据、未承接遗留；已经有Spec/Plan承接的引用它，不再另造平行需求台账。旧2.x从1.9.8分出，不应描述成1.9.9之后发生的一轮升级。

### G. 项目决定的正文保住了，摘要却可能让人以为没有确认

本项是整体历史承接的关联问题，不是archive搬文件直接造成。doc/project与T相比没有被merge删除，但根README将Maison共建整体概括为“尚未定案”，子README仍说已确认动作仅建目录和复制文件；03的逐轮记录已确认交付链原则，05又明确沿用外网开发→demo→内网真实验证及交付边界。具体组织方案和人员资源未定，不等于这些原则也未确认。

**修正方向**：只更新当前摘要的决定层级和来源，不把旧讨论重新写成一致答案。验证历史承接应同时看“文件在不在”和“读入口是否会误解已经确认的内容”。

### H. 原字节身份有一处较小但确切的说明错误

重写前14份快照中，01-成果保全与基线切换.md的manifest写“unchanged from 19d26cad”。实际O为10001字节，快照为10060字节：59处LF变CRLF，归一化后正文完全相同。快照自己的SHA256是对的，但不能称它是该Git blob的原字节。

这不构成业务内容遗失，也不应与证据缺件同等严重。保留已被引用快照，注明工作区行尾身份与Git原件关系即可，不为了修标注覆盖原快照。

## 3. 对此前判断的纠正

之前把1331件或4266件逐项校验通过，概括为历史完整，这是把“所选集合保全正确”扩大成了“选择集合充分”。B保全完整与旧O金样成套保全是两项；Git可恢复与普通读者可沿文档核证也是两项。真实merge保留祖先，并不会自动修正文档链接、补齐Git外证据或厘清历史效力。

本轮纠正的是设计与评审范围：归档以目录快照和去重为主，没有同时验收历史关系及证据依赖。已按方案完成的原件复制，不应全部归责执行者漏做；但当前入口断链和分支拼接需要按实际责任补齐。

上一答复建议“story完整视图”方向仍有价值，但不足以独自解决A/B/C；不能只新增导航后再次宣布完整。本轮也明确收回可能把行尾差异读成正文改写的表述。

本报告不推翻R1–R4产品修正已关闭的结论，但**不再认可把归档/完整历史承接视为已完成的隐含前提**。第三批的历史与文档总核必须补入这些已证问题，不能因先前批次通过而跳过。

## 4. 建议的最小调整次序

1. **先保当前仍可取得的必要原件**：被历史评审引用而仅在源仓或scratch的材料，以及O旧金样完整组。每项记录原路径/身份、目标和适用历史结论；不改产品、不跑业务CLI、不搬全部运行缓存。
2. **再明确历史主线与效力**：共同1.x历史、分支后的两条演进、新2.0合流各自说清；固定同号不同轮次的入口；现行依据/已完成/待承接分开。
3. **最后修阅读与引用**：从版本入口连到Spec→Plan→交回→评审→发布→必要原件；来源分支去重不能要求读者手工查JSON。选择完整阅读副本或明确跨快照引用时以简单可用为准，不新建文档平台、生成器或多层索引。
4. **按实际历史任务验收**：能从story1.9.8发布找到当时方案和差异；能从旧2.0.4评审找到当时金样及证据；能从1.9.9结项找到发布遗留及2.x承担者；能区分旧新2.1而不误取消要求。既有摘要核验继续保留，但不再作为唯一完成条件。

是否将共同1.x资料恢复原目录，或在archive内提供完整阅读入口，是随后需定的组织选择；本次证据不足以支持立即把全部资料搬回活跃目录。用户要求新重写从2.0.0开始与保存完整历史可以同时满足，关键是有效施工入口与历史阅读入口清楚，而非历史目录里不能出现旧版本。

本次分析只产本报告及核查证据，未修改源码、有效Plan、archive原件、历史评分或运行记录，未提交、推送或运行模型。未遍历所有Git修订和全部历史输出；三件源仓证据是已证实的例子，不是宣称仅有三件缺口。
