## 3. 接口身份裁定（P1，本步修正）

### 原生事实与影响

实际发布件 `framework/harness/scripts/utils/types.ts` 的 ContractsSpec.interfaces 定义 class/file/methods，方法定义 name；`blueprint-skill-projection.ts:checkTypedConstructionContent` 明确检查接口 class/file/methods；`contract-reference-closure.ts` 的接口字段集合也使用 class。这不是某份夹具的偶然形态。

独立用合法 class=Store、method.name=save 的契约调用当前消费者：

- obligationsFromContracts 生成 `interfaces..save`；
- resolveEntityRef 能正确解析 `interfaces.Store.save`；
- statDelivery 展示 `interfaces.Store.save`。

同一个对象已有三种消费者口径。plan/post_check 的 declared 集合还按 i.name 生成方法名，真实 `Store.save` 会被当作未声明。patternRolesFromContracts 也复用漏读 class 的 name()，接口角色实体名同样为空。该问题会影响正常 plan 逐点表、义务/角色展示和 review 对照，不能留给 CLI 碰撞报错才补规则。

### 具体修改合同

1. 在现有 contracts.mjs 的实体命名职责内统一按**实体种类**读取原生身份：interfaces 用 class；data_models/components 与方法/字段/状态用各自原生 name；resource_keys 保留已成立的专属定位。不新增通用注册中心。
2. obligationsFromContracts、patternRolesFromContracts、resolveEntityRef、plan declared 方法集合、statDelivery 及作者/审查地址输出共用该规则。接口地址固定 `interfaces.<class>.<method.name>`，人读逐点表仍为 `<class>.<method.name>`。
3. 不将 `name ?? class` 的宽泛字段尝试推广为接口协议，不补造 name、不把 name-only 旧夹具当作合法接口。可保留其他实体类型真实需要的既有字段读取；兼容旧接口格式不属于本版目标。缺原生身份保持原生问题，不生成双点空地址。
4. 同步接口 YAML 示例和专用夹具的 class 字段；保留本来验证其他实体 name 的测试。删除因接口全用 name 而锁住错误行为的断言，避免一边改产品一边留旧正例。
5. 用同一份原生派生/物化契约核义务地址、接口角色地址、plan 责任方法和审查复核行均认同一接口。至少一条真实 CU 的合法 `<class>.<method>` 通过逐点引用核对，错方法仍拒绝；不用再新造一套大夹具。

这是适配接口的集中小修正，不需改蓝图身份、知识决定或重做更新恢复。上次已核 R1–R4 和本轮 F1–F3 结论保持。
