## 1. spec 的原生需求参数链（评审 §2）

`framework-access.mjs` 的 `readFeature` 在范围冻结后、组装入口之前，照原生 harness（`harness-runner.ts:990–1023`）的无 run spec 路径恢复并核对需求。条件与原生相同：没有 run、阶段是 spec、workflow 是 1.2。

1. `featureRequirementBinding` 取冻结候选的需求绑定，`inferLegacyProjectRoot` 推旧根；
2. 调用方给了 `--requirement` 或 `--requirement-file` 时，用 `resolveRequirementInput` 读它；否则取绑定里唯一存在的来源文件（`resolveDependencyPath` 重定位）读回；来源不是恰好一份（inline 或旧候选）就报 `requirement_text_needed`，要调用方给原文；
3. `readBoundInput` 按冻结绑定核一遍，不一致报 `requirement_stale`（原生的 `input binding stale` 原文保留）；
4. 把 `requirement`、`requirementSourceFiles` 交入 `resolveCapabilityResolutionEntryInput`，再跑阶段解析。

同时按原生把 `MAISON_GOAL_RUN_ID` 交给范围来源选择与入口组装：有 run 时范围与需求以 run 为准，调用方再给需求就报 `requirement_override`（原生同样拒绝这两个覆盖参数）。

入口：`framework-access.mjs` 与 `knowledge-task.mjs` 的 feature 动作都新增可选 `--requirement-file <文件> | --requirement <原文>`，只在无 run 的 spec 使用。知识任务对两种新缺口分别写责任：给原文的是调用方；来源在冻结后变了的交回范围负责方，不换一份需求顶上。

pre_verifier 走同一次读取。原生 hook 的 ctx 不带需求正文，所以来源文件可恢复的 spec 能取到任务；inline 候选下它照实给「知识任务（取不到）」与缺口。

测试（`test_knowledge_task.py::SpecRecoversTheRequirementLikeTheNativeHarness`）。对照脚本 `NATIVE_SPEC` 照 harness-runner 那一段原样调用原生函数：

| 用例 | 结果 |
|---|---|
| 文件来源的冻结 spec | 原生 full / requirement resolved / 无 blocked；Extension 退出 0、assurance 相同，知识任务退出 0、不是预览 |
| 冻结后改需求来源 | 退出 1、`requirement_stale`，知识任务 stdout 为空。来源用一份只给这次请求的文件：夹具需求同时是蓝图来源，改它原生会先判蓝图失效 |
| inline 候选 | 不给原文：`requirement_text_needed`，知识任务退出 1 并指明 `--requirement-file`；给错原文：`requirement_stale`；给同一原文（`--requirement` 或同内容的 `--requirement-file`）：退出 0，assurance 与原生相同 |
| pre_verifier 在同一文件来源 spec 上 | 给出「知识任务：spec（审查者）」，不再报取不到 |

plan/review 的来源选择与过期反例、无 run coding 的 blocked 用例保持原样通过。

## 2. 首阶段准备顺序（评审 §4）

- **知识任务**：范围未冻结时标题带「——预览，执行范围未冻结」；第 4 块写明不作为动笔依据；第 6 块写顺序：已获准的主模型先原生准备，frozen 或 reused 后重取，原生失败按报错交回。读取器本身不冻结。
- **story-knowledge Skill** 新增「范围未冻结时」三步：
  1. 没有候选时，按 Framework 的 `goal-mode-operations.md` 走 `goal-mode-entry --prepare-scope`；
  2. 候选可用后，在 `framework/harness` 下执行一行命令，直接调用原生 `ensureFeatureExecutionScopeFrozen`；
  3. 返回 frozen 或 reused 后重取再动笔，其他状态按 `checks` 交回。

  同时写明：只查看知识不算获准开始阶段，也不为冻结提前跑整个阶段 harness。另新增「spec 的需求正文」一段。原首句「Framework 按 phase_bindings 调用本 Skill」按上次措辞更正改为「登记在阶段之前」。
- **顺序用例** `test_the_first_phase_is_prepared_natively_before_the_task_is_used`：
  - 只生成候选时，spec 任务是预览；
  - 从装好的 SKILL.md 取出那行命令原样执行，返回 frozen；
  - 重取后 spec 与 plan 都是 frozen、非预览，plan 写「契约来自 derive」。

  这证明 Skill 给的命令本身可用；模型实际是否照做留给 CLI 观察。

SKILL 的命令围栏起初标了 `bash`，被失效形态 M21（围栏写死 shell）拦下，已去掉标注。

## 4. 预算记录更正（评审 §5）

差额的来源是 `output/scratch/s1/budget_delta.py`。它对改动文件先按全部非空行做差分（注释行也在内），再乘以「有效行 / 非空行」比例四舍五入折算，所以新增减退出不等于规模差。现改为 `budget_delta2.py`：逐文件用台账 `code_lines` 同一剥法取出有效行本身，直接在有效行上做差分。这样新增减退出恒等于两端规模差，基线与计量口径不变。
