## 1. F1 原生 FAIL 不再归成通过

**改动**（`independent-review.mjs`）：删掉按检查 ID 放过 `issue_to_file` SKIP 的过滤。

**现在的判法**

| 原生结果 | Extension 归类 |
|---|---|
| 判 FAIL 的检查项 | 按类别归 fail、subject_stale 或 report_invalid |
| 没声明不适用的阻断 SKIP | 不归 pass/warn；无法归到其他类时记 tool_error，原样列出原生检查 |

**只有 Markdown 建议的报告**：原生 verdict 是 FAIL，Extension 给 tool_error 并点名 `issue_to_file`，登记拒绝。
- 用例：`test_a_native_failure_is_not_turned_into_a_pass`，同时核同次原生 summary 的 verdict。
- 「只有非阻断建议的报告可以交付」这一产品目标保留为 `test_advisories_are_delivered_with_the_story`，用 `expectedFailure` 标未满足，docstring 指向 Framework 专项反馈。上游修好后它会变成意外通过，届时去掉标记，用同一输入复验。

## 2. F2 需求目录与蓝图工作区分开

**产品**

- **bind-design**：蓝图标识与需求标识相同时拒绝，报错建议 `--blueprint bp-<需求>`。已有设计给出实际标识，不自动搜索或改名。
- **指引与提示**：`phases/design.md` 第二节第 1 步、`routing` 的 `run_complete` 提示同步。
- **读取**：产品代码本来就只按关联的蓝图身份读取，没有从需求名推蓝图位置的地方。

**夹具与回流**

- **夹具**：`design_fixture.blueprint_of`（有关联用关联，没有用 `bp-<需求>`）；`install_blueprint`、`change_blueprint`、`hand_to_design`、`hand_over_state` 都按它放蓝图。
- **回流**：
  - `run_layout.linked_blueprint` 只按流程契约的 `design_binding` 找异名的蓝图工作区，没有契约、同名或盘上不存在都返回空；
  - 检查点：`run_case.cmd_checkpoint` 用 `_freeze_tree` 同时固定需求目录和 `<point>.blueprint`；
  - 回流动作：`promote-checkpoint` 与终态回流用 `_promote_tree`，按蓝图自己的身份带回，双检查点终态同样另名。

**正例**：`ARequirementWithUiReferenceGoesThrough`，带 `ux-reference/home.png`、异名蓝图 `bp-REQ-DEMO`，依次走通：
1. 冻结；
2. 蓝图消费；
3. 照检查提示的原样命令登记不用理由；
4. 原生 review 准备，请求目标里有参考图和异名蓝图；
5. 夹具审查通过、登记、交付门通过。

**顺带修正**：`images.mjs` 在「图没去处」的提示里给的是需求相对路径，而 `import_sources.py --caption-image` 要的是工程相对路径，照抄会失败。现在给工程相对路径，正例测试就是照抄那条命令执行的。

回流用例：
- `test_the_linked_blueprint_flows_back_under_its_own_name`：终态与检查点两条路径；
- `test_a_requirement_without_a_separate_blueprint_links_nothing`。
