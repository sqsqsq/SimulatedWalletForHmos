# 步骤 3 返修交回

> 读者：2.0.0 方案设计者。时机：复核[步骤 3 实施评审](../评审意见/2026-09-30-步骤3实施评审.md)的返修之前。
> 起点：评审入库 `c8414a7c`。

## 1. 逐项处置

### R1 阶段消费者改用原生有效输入

- `framework-access.readFeature` 交出原生检查器看到的同一份规格 `spec`（`SpecLoader.loadFeatureSpec`）：冻结时是解析器选定的输入加
  本阶段自己的产出（产出按产出核），没冻结时是原生按本地文件读出的规格；同一次任务里同一 Feature、同一阶段只解析一次。
- `contracts.mjs` 的 `readContracts` / `readAcceptance` 退出，换成 `phaseArtifacts(root, feature, phase)`：交出原生身份给的目录、
  契约 / 验收 / 用例，以及原生对本阶段输入报的问题。spec、plan、coding、review、ut、testing 门禁与审查任务、知识任务都改读它；
  原生报的问题在门禁里单列一组原样报出。
- 退路退出：`featureDir` 不再自拼 `doc/features`；`featureKnowledge` 在原生身份不成立时原样交回问题（不当成平铺 Feature）；
  设计引用解析失败报出来，不静默少一个承接地址。
- 原生规格已报「集合不是列表、条目不是映射」（`feature_spec_shape`），`knowledgeCriteria` 里重复的这两段形状检查退出。

### R2 知识身份与多 CU 角色

- `knowledge.mjs` 的「激活规约编号全仓唯一」与 `entryById` 退出；`knowledge-application.entryOf` 先由义务的 `decision_id` 找到判断，
  再按判断的来源文件与单元找条目。plan（verify、探针落点）、coding（探针）、review（强制力）、审查任务的并列表都改用它。
- 承接范围 `scope` 改为按原生目标关系判：地址是设计引用指向的对象、在其中或包含它（对象包含关系，不按字符串前缀）。
- 模式角色：`rolesOf` 只取落点在本单位设计责任内的角色；plan 只要求这些角色有实体承担，实体认领别的单位的角色也点名；
  知识应用决定里的角色名核模式知识的声明（`roles` / `optionalRoles`）。
- 知识协议补一句：编号在本文件内不复用，不同文件可以同编号，判断与义务按「来源文件 + 编号」认。

### R3 Review 人工区不随撤回退掉

- `restore` 在评审记录与开轮时不同、且现在这一份里有人写过字（议题人工区或自由意见区）时，一律保留为冲突，不整文件退回或删除。
- 「有没有人写过字」用渲染侧同一份判据：`story-build review --action manual`（`review.mjs` 的 `manualContent`，复用 `hasHumanWords`）；
  读不出按有人写过处理。只有机器内容的 Review 照恢复真值表处理。

### R4 反馈处理不再推断

- `framework-access` 的 `feedback` 只判候选资格；新增 `feedback-related`，只列当前蓝图里 `provenance.source_ref` 恰好是
  「反馈文件工程相对路径#feedback_id」的决定及其原生状态。按片段推导「已处理」退出。
- `update --action feedback` 分开记两件事：提交时的候选资格（按被评版本记，文件没改不重判、新 revision 不改投）与当前相关决定；
  状态一律「待确认」，接受与否由模型读负责方回复（记在本轮 update-notes）与当前设计判断。close 只列待确认，不代表接受、不取得施工授权。

### §6.1 没有 plan.md 的埋点落实

- `stat-points.statDelivery` 并列蓝图埋点明细、契约方法说明（`interfaces[].methods[].description`）与验收条目；知识任务（施工阶段作者）
  与 plan 审查任务在没有 plan.md 时送这一份，审查逐点核。plan 门禁只把「plan.md 逐点表一致性」记为不适用，不再跳过整个埋点义务。

### §6.2 取证页

- `evidence-rules.md` 改为「取证规则」：读者是蓝图来源发现与设计的作者、本单位有新增事实的 spec 作者；意图来自本次需求、有效决定与原生
  当前输入（spec.md 不再必备）；检索范围取工程配置与实际模块；结果写进各动作的原生事实对象。蓝图作者页在发现前指向它，
  spec 作者页只在本单位有新增事实时指向。

### §7 其他退出

- `upgrade-changes.md` 2.0.0 的在途单改回已定边界：旧单在 1.x 收口，或在 2.0.0 用 init 重新起单。
- `test_yaml_reader` 不再从历史运行件找 knowledge-use 样本，改用夹具里的当前契约样本（知识应用决定、实体 must 与 pattern_roles）；
  `test_update_checkpoints` 的预检报错样例换成当前真实的台账缺失报错。

## 2. 新增与迁移的用例

| 用例 | 核什么 |
|---|---|
| `test_cu_knowledge_chain.py` `TheDerivedContractCarriesTheObligations` | 真实 CU 冻结后原生从蓝图派生契约：实体上的 `must`/`decision_id`/`pattern_roles` 原样到 plan 门禁与审查任务；别的单位的角色不要求本单位承担；关掉测试转译缓存钩子重跑，结果一致 |
| 同上 `AMissingOwnRoleIsNamed` | 本单位角色没有实体承担时只点名它，不点名别的单位的角色 |
| 同上 `TheMaterializedContractIsReused` | 先物化本地契约再冻结，复用本地产物时义务与角色照样被读到 |
| `test_neutral_knowledge.TheSameIdFromTwoFiles` | 两份规约同编号照常激活；两条 must 各按自己来源条目的执行体核 verify |
| `test_story_update.RestoreKeepsTheReviewersWords` | 新建与既有 Review 填了人工意见后撤回都保留为冲突；只有机器内容的照真值表退回 |
| `test_story_update.DesignFeedbackGoesToTheBlueprintOwner` | 候选资格不等于接受；精确引用列为相关决定且仍待确认；别的文件同锚点不命中 |

已有的过期输入拒绝（`test_knowledge_task`）保留。

## 3. 验证

- 全量：1397 通过、1 xfail；失败 6 条，其中 4 条既有（金样 3、`test_run_measurement` 1），另 2 条是 `test_contracts_single_source` 仍调已退出的读取函数，
  迁到 `phaseArtifacts` 后单独复跑 4 条通过。
- 失效形态：FAIL 1（G01，既有）。
- 测试用时：本轮全量 169 秒，超出 120 秒目标；新增的 CU 链路三类各冻结一份工程，是这次增加的主要来源。
- 设计者探针复现的两处（CU 派生契约被当成缺契约、Review 撤回被删）在新用例里各有对应断言。
