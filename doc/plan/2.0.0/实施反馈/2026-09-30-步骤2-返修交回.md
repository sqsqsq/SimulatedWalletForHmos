## 2. 各项修正

### R1 蓝图消费本次输入

**核对（`hooks/shared/framework-access.mjs`）**
- 带冻结快照读蓝图时返回 `consumption`。
- 预期条目由快照推出：`item_id`、`kind`、`<版本>/files/<路径>` 与原始字节 `sha256:`。
- 用原生 `currentScopeItems` 逐条核：
  - 同一 `item_id` 存在；
  - `kind` 一致；
  - 来源路径一致（经原生 `validateProjectRelativePath` 规范化，锚点不计）；
  - 摘要一致；
  - 蓝图声明的证据强度不高于交给设计时。
- 蓝图另有其他条目不算问题。

**共用这项结果的地方**
- `routing.py` 拆出 `design_gate`，它同时服务两处：
  - status 的设计关口；
  - update 内重新登记前的检查。

  没消费时停在 `design_blueprint`，提示设计职责同步。
- `design-source.mjs` 把同一结果写进 problems，因此 skeleton、basis、check、交付门都会停下。

**夹具**
- `design_fixture` 改为真实顺序：先 bind 和 complete，再放消费这次输入的准入蓝图（条目换成冻结输入推出的原生条目，来源指纹按原生算法重算）。
- `hand_over_state` 同理。
- update 用例在换输入之后加一步「设计同步」。

**反例**（`test_design_handover.py::TheDesignConsumesThisInput`）

### R3 来源性质与人签

**来源性质**（`materials/frozen.py`）

| 角色 | evidence_strength | extraction_method |
|---|---|---|
| 原件、图片 | observed | `frozen_file_observation` |
| 人签 | authoritative | `recorded_user_reply` |
| 提取稿 | inferred | — |

**时刻**
- 物化件里各行的 `observed_at` 统一取冻结观察时刻，并标明是本次文件观察。
- 人签合并文件记导出时刻，每条原话保留自己的 `at`。
- 快照去掉 `human_decided_at`（即旧的 max(at)）。

**人签**
- 只导出当前有效的：同一关卡（会议按话题分）取最后一条人给出、已生效的记录。
- 被 reopen 或重问替代的旧编号，报「已被之后同一关卡的人签替代」。
- 测试：
  - `test_a_file_only_proves_it_was_observed_and_the_person_is_the_authority`；
  - `test_a_decision_replaced_by_a_later_answer_is_not_current`。
- 两条依赖旧行为的用例改为使用当前人签：
  - 损坏版本复用：改成直接重提同一输入；
  - 换输入：改为核旧版本仍在，不再数版本个数。

**未做**：`design-input.json` 的 `source_evidence`。评审定为可选，当前没有比文件观察更强、可证的来源记录可接。

### R4 登记

**定稿挪到审查之前**：定稿（project → number → build → 全篇 check）由 `story-build review --action prepare` 完成。

**登记改为只读**（`lifecycle.cmd_story`），依次核：
1. `story-build check --registering`：结构检查，不核「登记之后改过没有」，因为要替换的正是旧登记；
2. `story-build review --action check` 的结果是 pass 或 warn；
3. `story-build basis`。

三项都成立才一次写入新依据：
- 失败时，状态与旧依据原样保留；
- 依据与已登记的相同时不改，返回 `registered: false`。

**登记指纹**
- 改为原始字节的完整 SHA-256（`file_sha256`，JS 侧的 `digestOf` 同口径）。
- `STORY_REGISTERED` 加入 `AR/review.md`，人工区改了也会失效。
- 旧的 `ledger_digest` 没有其他消费者，已退出。

**测试**
- 登记失败保留旧依据，交付门拦下：`test_a_failed_registration_keeps_the_old_basis`。
- 同一对象重复登记不变：正常链用例的最后一段。
- 源码顺序：
  - `cmdReview` 按 project → number → build → check → prepareReview；
  - `cmd_story` 不再有 project、number、build 调用。

### R5 独立审查接线（按 §5.1）

**审查对象**：`story/review-object.mjs` 是唯一定义。

| 类别 | 内容 |
|---|---|
| 待审 | Story、Review |
| 只读对照 | 审查任务、写作设计、决策登记、会议记录与原文、冻结输入快照与全部文件、已准入蓝图与评审投影、激活清单与知识原文、章节合同、判据 |

审查任务列它，请求目标用它，材料键由它算，三处共用这一份。

**prepare**
1. 定稿并过结构检查；
2. 写 `task.md`；
3. 生成 `AR/story-src/review/request.json`：`phase: review`、`baseline.head: WORKTREE`、不带 Feature/Goal，`inputs.review_report` 指向报告目录；
4. 调原生 prepare：`framework-access.explicitRequest` 在进程内调 `request-phase.ts:runExplicitRequest`，参数键与 `npm run check` 相同；
5. 除事实记录与报告两个待产物之外，其他 gaps 都作为输入错误停下；
6. 记下 `prepared.json`（材料键、报告目录、request_sha256）；
7. 输出派审要带的东西。

报告目录默认 `doc/reports/story/<需求>/<材料键前 16 位>/`，可用 `--report-dir` 替代。

**check**
1. 材料键与准备时不同，报 `subject_stale`；
2. `review-original.md` 不在，报 `report_missing`；
3. 每次把原回复逐字复制成工作报告 `review-report.md`，原生可以回写它，原回复不动；
4. 重跑原生 prepare 核 `request_sha256`；
5. 跑原生正式检查，核 summary 的 `subject`、`completion_target`、`phase`、`request_sha256` 与 `script_report_sha256`，缺当前合法 summary 报 `tool_error`；
6. 按原生检查项归类：

| 原生检查项 | 归类 |
|---|---|
| `negative_verdict_closure` / `conditional_pass_closure` | fail |
| 输入变更与绑定过期 | subject_stale |
| 章节、表格、统计、结论、范围、事实记录、`issue_to_file` FAIL | report_invalid |
| 其余认不出的 | tool_error，原样列出 |
| 都没有 | 问题清单有行为 warn（列出建议），否则 pass |

**交付门**：`deliveryProblems` 改为异步，消费当前对象的这一结果。

**判据与任务**
- `story-reader-rules.yaml` 的输出契约改为原生 review 报告：
  - blocking_findings 进 BLOCKER / MAJOR；
  - advisories 进 MINOR / INFO；
  - 逐章证据、open 议题结论和会议去向写在「审查方法」；
  - 没有问题写「无问题。」。
- `reader-review-task.mjs` 新增「本次审查的材料」（待审与只读对照分列）和「报告怎么写」（事实记录 frontmatter、章节、表头、`CR-` 编号、分类取值、结论行）。
- `request_sha256` 不写进任务，由 prepare 输出交给宿主，避免摘要循环。

**退出**：固定 `reviewer_unavailable` 占位及其文案退出。`phases/design.md`「五」改为：定稿准备 → 派审 → 核结果（结果与动作一张表）→ 登记 → 交付门。

**夹具审查者**：`design_fixture.write_review` 按原生格式写事实记录与报告，只验证协议。

**测试**（`test_verifier_report_protocol.py::TheStoryIsReviewedRegisteredAndDelivered`）

| 用例 | 结论 |
|---|---|
| 正常链 | 请求目标含 Story、Review、任务、判据、冻结输入与蓝图，基线 WORKTREE；pass → 登记 → 交付门通过、给出选项；原回复字节不变；重复登记不变 |
| 建议 | warn，交付门放行并照录 CR-001 |
| 阻断（BLOCKER / 未关闭 MAJOR） | fail，登记拒绝 |
| 缺回复 | report_missing |
| 对象已变 | subject_stale |
| 登记失败 | 保留旧依据 |
| 蓝图修订之后 | 交付门拦下 |
| 结构检查没过 | 不准备；任务里有判据、报告格式与材料分列 |

在旧实现上 12 条中 9 条失败。另 3 条（普通 check、未登记、蓝图修订）是不受本次改动影响的既有行为。

## 4. 新发现，需要设计者处理

1. **`ux-reference/` 与原生 Feature 标志冲突**
   - 原生 `enumerateFeatures` 把 `ux-reference`、`context`、`spec` 等目录当作平铺 Feature 产物的标志（`framework/harness/config.ts` 的 `FEATURE_MARKER_DIRS`）。
   - 目录同时有 `blueprint/` 时，它按歧义 fail-closed。新需求默认 `blueprint_id` 等于需求标识，蓝图工作区和需求目录是同一个目录；而 Story 的界面参考图按材料约定放在 `ux-reference/`。
   - 实测：同一工程没有 `ux-reference/` 时 prepare 成功；加一张参考图后，原生 prepare 报「歧义：REQ-DEMO 同时含 blueprint/ 工作区与平铺 Feature 产物，fail-closed」。证据在 `output/story/2.0.0/step2-rework/ux-reference-probe.json`。
   - 影响：凡是带 UI 参考图的需求，审查接线在正常链上走不通。其他会枚举 Feature 的原生动作，理论上受同一规则影响，未逐一验证。
   - 可选方向：改 Extension 的参考图目录、改默认蓝图标识，或反馈 Framework。实施者不自选。
   - 1.x 夹具里留在需求目录的 `spec/` 同样会触发。测试已按 2.0 形态删掉它；step 3 的 update 与 spec 相关用例仍可能碰到。
2. **原生 `issue_to_file` 只认代码后缀**
   - 它只认 ets、ts、js、json、py 等代码后缀。问题只指向 `.md` 的报告会得到 SKIP BLOCKER，原生 verdict 因此是 FAIL，即使只有 MINOR 建议。
   - Extension 把这一项 SKIP 排除在「报告问题」之外（依据同上）。它 FAIL（引用了不存在的文件）时仍按报告无效处理。
   - 是否作为 Framework 缺口反馈，请设计者定。
3. **宿主没有独立执行能力时**：这一版没有未审交付通道，交付门不放行，design.md 写明照实告诉人缺什么。§5.1 提到的「已有明确未审授权才进入降级」没有实现，留待 CLI 暴露后再定。
