2026-09-30，维护实施者。步骤 2 正在实施（2A 已提交 `d5950962`、`447e9b18`、`6f2f1658`；2B 成文来源改造进行中）。以下两件需要设计者裁定或补齐。用户同日选择「交设计者裁定，2B 其余照做」。

## 1. 金样 AR90004 与 2.0 成文来源冲突

**事实**

- 金样正本 `test/golden/story-金样-AR90004.md` 按 1.x 写成：
  - 正文里的图带 `%% 图源 spec §5.1 #1` 这类标记，承接的是 Spec 里的图；
  - 附录七处机器区（端云接口、数据存储、配置项、依赖变更、规约、埋点、改动边界）由金样工作区从 `fixtures/golden/AR90004/spec` 投影。
- 步骤 2 §5 规定：Story 退出 Spec 固定章号来源，附录按已准入蓝图的具名读取器投影。上游带图文档只剩系统设计（`sources.SPEC` 已从章节合同退出）。
- 因此 2.0 判据拦住金样，共三处：
  1. `图源 spec` 标记被判为「指向的不是直接上游」；
  2. 金样工作区没有设计关联和冻结输入，也没有准入蓝图，附录机器区无从投影；
  3. 失效形态 G01 与 `test_golden_sample.py` 的 3 条用例因此失败。
- `test/golden/README.md` 的规则是「单向否决锚：任何判据拦金样即判据错，改判据不改金样」。这与 2.0 取消 Spec 上游正面冲突：改回判据等于恢复已退出的 Spec 来源；改金样又违反锚定规则。实施者不自行选择。

**可选做法（供裁定，不预设）**

- **A**：金样只改随 Spec 退出的元数据。正文、图和附录作者区一字不改；指向 spec 的图源标记去掉（或改指蓝图对象）；附录机器区由金样工作区的准入蓝图重投。金样工作区需要一份表达同样设计内容的准入蓝图：接口、数据、配置、埋点用 `contracts`、运行数据流与 `story_details`。其中 `contracts` 要过原生的权威比对，需要备齐对应的来源文件。
- **B**：保留 AR90004 作为 1.x 锚，另定 2.0 金样，由步骤 4 的 Case 迁移产出后定稿。在此之前 2.0 判据不以 AR90004 否决。
- **C**：其他。

**当前处理**：金样 3 条用例和 G01 如实保持失败，交回时列明。不跳过，不改金样，也不放宽判据。

## 2. 独立审查（接缝 B）的原生调用记录

步骤 2 §5「独立审查」要求设计者补齐 B 的接入记录：

- 实际入口及版本；
- 输入字段与材料集合的映射；
- 报告路径及落盘者；
- 对象身份的取得方式；
- 原生状态/退出码到交付动作表的映射。

能力核对评审目前只写到「由设计者及时核定调用」。缺这份记录时，实施者按分册只停在审查接线，取材、冻结和成文照做。`story-build review --action prepare|check` 的业务动作等记录到位后再接。
