# 步骤 4 实施者意见：金样装配迁移的三处映射

> 读者：2.0.0 方案设计者。时机：步骤 4 实施中（4A 已提交 `7825d7c1`），金样装配迁移（4B）动手前。
> 依据：[步骤 2 实施评审](../评审意见/2026-09-30-步骤2实施评审.md) §3 的金样裁定——保留正本、迁移测试装配；在隔离副本里用同一真实设计事实建立原生蓝图、补真实来源绑定，
> 旧图源定位映射到确有对应的蓝图/来源对象，机器附录由当前 renderer 派生；逐项列「旧事实 → 蓝图对象 → 新输出」，无事实丢失、无新决定；未知映射报错。

按裁定逐项核金样（`test/golden/story-金样-AR90004.md`）的旧元数据，有三处找不到「确有对应」的 2.0 承载对象。实施者不自行补来源或挪内容，请设计者定。
其余部分能照裁定做，见 §4。

## 1. 端云接口缺可比对的权威来源

**事实**

- 2.0 附录「端云接口」读蓝图顶层 `contracts`（`extensions/skills/story/scripts/core/story/appendix-readers.mjs:38-58`）。
- 原生准入对每个契约的 `operation`、`request_dto`、`response_dto` 做权威比对：`source_ref` 必须是工程内相对路径的 YAML/JSON 文件加 JSON Pointer，
  指到的内容与蓝图里声明的逐字段相等（`demo/framework/harness/scripts/utils/blueprint-contracts.ts:43-104`）。
- AR90004 的三个接口（`queryLossEligibility`、`createOrReuseLossApplication`、`queryFreezeResult`）只写在 SR 的 Markdown 设计文档 §4 与 1.x spec 的技术契约表里。
  金样输入夹具里没有任何机器可读的接口定义，SR 的 Markdown 解析不成 JSON Pointer 的目标。

**选项**

- **A**：金样输入夹具随 SR 增加一份接口定义附件（例如 `SR/api/traffic-card-loss.yaml`），内容逐项转录 SR §4 的字段、语义与错误约定，作为契约的权威来源。
  这是给输入加一份文件，转录本身不产生新事实，但它是新的输入件。
- **B**：金样工作区不建顶层 `contracts`，「端云接口」机器区在迁移副本里为空；接口事实改由其他对象承载。
  这样附录·端云接口的事实会从机器区消失，按裁定属于事实丢失。

**建议**：A。转录范围只限 SR §4 已写明的字段与约定；1.x spec 表里有、SR 里没有的内容（如「性质：新增 WalletMain 卡云适配接口」）
放在契约的 `nfr` 或 `errors` 等语义字段，并在映射表里逐项标出处。

## 2. 「依赖变更」在 2.0 没有机器区

**事实**

- 金样附录有 `技术契约·依赖变更` 机器区（§10.1.4）：「不涉及新增或升级外部依赖：复用 `AccountManager`、`CommUI`、`CommFunc` 的已有出口；卡云适配层由 `WalletMain` 自有代码承载。」
- 2.0 章节合同的附录投影只有六个机器区：端云接口、数据存储、配置项、规约、埋点、改动边界（`extensions/skills/story/contracts/story-chapters.json` chapters[9].projection），没有依赖变更。
- 改动边界读开发视图节点与带 `change` 的架构影响决定（`appendix-readers.mjs:88-104`），能表达「AccountManager / CommUI / CommFunc 不改」，
  但「不新增外部依赖、卡云适配层由 WalletMain 自有代码承载」这句没有对应字段。

**选项**

- **A**：这句事实落到开发视图的架构影响决定上（`module`、`change: 不改`、`rationale: 复用已有出口，不新增外部依赖`），由改动边界机器区呈现；
  §10.1.4 的机器区在迁移副本里退出，小节标题随之去掉。正本不动，但迁移副本的附录少一节。
- **B**：§10.1.4 的机器区在迁移副本里改为作者区原文保留（去掉机器区标记，文字不动）。事实不丢，但作者区里出现了原本由机器生成的文字。

**建议**：A。事实在改动边界里仍逐项可查；附录少一节属于章节结构随机器区退出，不改正文语义。若设计者认为附录结构变化需要用户确认，按裁定另交用户。

## 3. `spec §5.1 #1` 这张图在 2.0 的上游里没有对应

**事实**

- 金样 §5 的时序图同时标了 `%% 图源 SR §3 #1` 与 `%% 图源 spec §5.1 #1`。
- 两张上游图不是同一张：SR §3 是端到端时序图（`sequenceDiagram`），spec §5.1 是端侧主流程图（`flowchart`，含账号恢复、既有请求、风险确认、结果分支与重试先查）。
  金样把两张合成了一张时序图。
- 2.0 的图源标记只认直接上游，而直接上游只有系统设计（`extensions/skills/story/scripts/core/story/sources.mjs:168-177`，标签 `SR`）。
  spec 退出之后，spec §5.1 那张流程图的内容在 2.0 由蓝图的运行视图（运行数据流、失败恢复）与场景视图承载，但蓝图对象不是图源标记能指向的上游文档。
- 所以 `spec §5.1 #1` 没有「确有对应」的 2.0 上游图；按裁定，未知映射应报错，不能通用删除标记。

**选项**

- **A**：映射表把 `spec §5.1 #1` 登记为「承接对象已不是上游图：内容由蓝图运行视图 `<flow_id…>` 与场景视图承载」，迁移副本删去这一行标记，
  保留 `SR §3 #1`。映射表逐项列出流程图里每条分支在蓝图里的对象，缺一个就报错。
- **B**：保留这一行标记，接受迁移副本在图源检查上失败——金样测试与 G01 继续失败。

**建议**：A。删的是一行已无上游的来源元数据，承接内容逐条挂到蓝图对象上可查，不是通用删除。

## 4. 不受上面影响、能照裁定做的部分

| 旧元数据 | 2.0 承载 | 新输出 |
|---|---|---|
| 规约表（19 行，`spec/knowledge-use.yaml` 投影） | 蓝图知识应用决定，来源为金样知识快照 `test/fixtures/golden/knowledge/`，按「来源文件 + 单元」认；落点指向蓝图对象 | 附录·规约机器区（列变为「单元 / 判定 / 要求与理由 / 落点」，规约域由来源文件确定） |
| 数据存储（`loss_report_recovery_context`） | 运行视图的数据流（权威来源、状态归属、失败恢复）+ `story_details` 的 data_policy 明细（介质、值结构、有效期、用途原文） | 附录·数据存储机器区 |
| 配置项（`traffic_card_emergency_loss_enabled`） | `story_details` 的 configuration 明细（默认值与行为原文） | 附录·配置项机器区 |
| 埋点（两个指标、三个统计点） | `story_details` 的 event 明细（正文与两张统计点表原文） | 附录·埋点机器区 |
| 改动边界（WalletMain 改，其余四个不改） | 开发视图节点（WalletMain 当前 → 目标）+ 架构影响决定（四个模块不改） | 附录·改动边界机器区 |
| 需求输入 | 用真实流程命令走材料、范围关卡与冻结，设计关联到这份蓝图，蓝图消费冻结输入 | 成文依据与交付门 |

实施方式：迁移脚本在隔离副本里建蓝图与来源绑定，再用当前 renderer 重投机器区；映射表逐项写「旧事实 → 蓝图对象 → 新输出里的位置」，
脚本逐项核新输出里能找到旧事实的原文，映射不到或找不到就报错。正本 `test/golden/story-金样-AR90004.md` 不改，不维护第二份可编辑金样。
