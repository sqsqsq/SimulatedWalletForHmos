## 1. 四项返修

### R1：CU 输入改走当前阶段的原生解析

- **命令行**：`framework-access.mjs --action feature` 现在必须带 `--phase`。
- **范围已冻结时**，按原生阶段调用的顺序取输入：
  - 先由 `resolveCapabilityResolutionEntryInput` 组装入口；
  - 再用 `resolveFeatureTrack(loadFeatureTrackDecl(...))` 取得 track；
  - 然后调 `resolveCapabilityInputs`，把结果交给 `SpecLoader.loadFeatureSpec(feature, inputs)` 规范化。

  选用哪份输入、是否复用、是否过期或 invalid、是否 blocked，都采用原生的结论。每份输入附上原生 binding：`derive` 或 `artifact contracts@1`。
- **范围未冻结时**：不调用解析器，不代为冻结，只报 `scope: not_frozen`。Extension 不再自己从蓝图派生契约来补位。
- **pre_verifier**：原生传给 hook 的上下文里没有已解析的输入（只有工程根、阶段和 Feature），所以它也走同一次只读解析。它运行时 harness 已经冻结了范围。

实测结果（`test_knowledge_task` 的 `PhaseInputsComeFromTheNativeResolver`）：

| 场景 | 原生结果 | Extension 结果 |
|---|---|---|
| 冻结后尚无本地输入 | plan 为 full，binding 是 derive | 知识任务写明「契约来自 derive」 |
| 先物化本地输入，再冻结 | binding 是 artifact contracts@1 | 同左 |
| 物化并冻结后，改动本地契约的语义 | plan 为 blocked，review 报 `input binding stale` | framework-access 报 invalid；知识任务退出 1，stdout 为空；读取前后需求目录与 harness 状态目录的字节都不变 |
| 无 run 的 coding | blocked，`requirement=absent` | 按原生结论失败 |
| 自定义 `features_dir` 并冻结 | 解析成功 | 同左 |

说明：原生在交互（无 run）路径上只给 spec 阶段传需求正文，所以 coding 的上下文能力被判为 blocked；原生 harness 在这一步同样会被挡住。这属于已上报 F6 的无 run 续行范围，Extension 只是照原生结论报告。

### R2：必需输入缺失或损坏时不给半份任务

knowledge-task 在以下情况退出 1，stdout 为空，stderr 写明对象、缺口与责任方：

- Feature 不存在（`feature_missing`）；
- 本地契约形状错误（`feature_spec_shape`，例如 `files: wrong-shape`）。范围未冻结时也用 SpecLoader 只读核对本地文件的形状，只收集形状错误，不把这些文件当作本阶段输入；
- 输入为 invalid；
- 原生 assurance 为 blocked；
- CU 引用过期。

以下正常路径仍然成功：合法的空知识或空义务、蓝图建立前的 discovery、范围未冻结的阶段。范围未冻结时，第 4 块写「本阶段的原生输入还没有确定」，第 6 块写明由原生入口的首次阶段调用来冻结。

pre_verifier 读不到任务时，给出「知识任务（取不到）」、缺口原文，以及「依赖知识的判断写未验证」，不会展示成有效知识（测试 `test_the_reviewer_is_told_when_its_task_cannot_be_read`）。

### R3：替换前用原生加载器校验待装 manifest

`entries.mjs` 新增 `candidateProblems`，做法如下：

- 把待装内容放进一个临时工程，里面带上目标的 `framework.config.json`，这样阶段名会按目标自己的 workflow 核对；
- 用目标 Framework 的 `loadInstanceExtensions` 校验 manifest 以及其中登记的 Skill、钩子、规则覆盖、资产、知识和阶段绑定的引用。

两个安装入口放进临时工程的内容不同：

- **维护安装**：放整个源包，由 `_plan` 通过 `--candidate` 传入；
- **对外 adapt**：放包的机制面、合成后的 manifest 和目标自己的知识。包里的 Demo 知识不会放进去，也不读知识正文。

adapt 的检查顺序是：先核待装登记，再核入口。登记坏了时入口渲染也会跟着变，所以先报根本原因。

测试覆盖：

- 源包登记了不存在的知识、绑定了不存在的阶段：dry-run 和 apply 都返回 `preflight_failed`，目标字节不变；
- adapt 时目标自己登记了不存在的知识：退出 2，报 `knowledge_missing`，零写入；
- 未提交的合法源文件仍会进入安装（原有测试）。

### R4：原生物化中途失败时如实报告

`entryMaterialize` 在调用原生之前，先记下本次覆盖面的字节，范围包括入口文件、所有已声明 Skill 的入口（含 orphan）和要撤下的旧入口。即使原生抛错，也照样对比前后字节，报告真实的 written 和 removed，并保留原始错误（「原生物化失败：…」）。命令行退出码为 1，同时照常输出结构化结果。

维护安装器的完成项改为「写入路径」加「remove 路径」。

测试做法：源包新增一个合法的 extra Skill，同时把目标的 `CLAUDE.md` 设为只读。断言有两条：

- 目标上真实改动的宿主入口，与完成项的集合逐一相等，其中包含 `.claude/commands/extra.md`；
- 被删除的入口与 `remove` 项相等。

## 4. 待设计者确认

- **范围冻结的时序**：`before_phase_work` 发生在作者动笔前，而原生在首次阶段调用（harness）时才冻结范围，所以第一个阶段取知识任务时范围通常尚未冻结。当前做法是：照常给出知识原文与蓝图判断，并写明本阶段输入由首次阶段调用确定。是否需要 Story 或作者页在动笔前先完成一次原生阶段调用，请设计者裁定。
- **无 run 的 coding 缺需求正文**：见 §1 R1 的说明，这是原生行为，已记入 F6 观察。
