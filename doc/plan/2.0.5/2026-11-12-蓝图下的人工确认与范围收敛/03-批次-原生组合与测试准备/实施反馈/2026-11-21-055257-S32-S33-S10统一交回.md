原始诊断证据归档于 [output/evidence/2.0.5-03-S10/20261121-s32-s33/finding-c-diag/](../../../../../../output/evidence/2.0.5-03-S10/20261121-s32-s33/finding-c-diag/)：

1. **`.git` 指针删除 `[WinError 32]`（`test_multi_case_cli.py:2057`）**：
   - **定位证据**：`RmGetList` 返回 `count=0`（无用户态持有者），A/B 对照（80 轮 xdist，[git-ab-events.jsonl](../../../../../../output/evidence/2.0.5-03-S10/20261121-s32-s33/finding-c-diag/git-ab-events.jsonl)）证实：

     - `plain_no_git_init`（父仓无 `git init`，写 `.git`）：**0 / 20** 命中；
     - `write_only`（父仓有 `git init`，写 `.git` 后**不调** `ensure_case_git` / `_verify_workspace_boundary` 直接 `unlink`）：**3 / 20** 命中，10.9–69.5 ms 后自动释放；
     - `with_boundary`：**8 / 20** 命中，10.6–12.8 ms 后自动释放；
     - 宿主进程核查见 `TGitCache.exe`（TortoiseGit 图标缓存）与 `MsMpEng`（Windows Defender），前者在父仓 `git init` 后对子树新建 `.git` 文件做 ~10–70 ms 只读扫描。
   - **归因与处置**：`ensure_case_git` 与 `_verify_workspace_boundary` 无句柄泄漏，属宿主外壳缓存瞬态只读扫描。在 `test_a_git_pointer_or_nested_repo_is_still_refused` 仅对清理假 `.git` 指针的 `unlink()` 加有界重试（40×25 ms），**未改产品/脚本代码与任何工作区 Git/指针/嵌套目录判据**。处置后 `verify.py handback` 并行 `full` **首次即 2213 passed / 0 failed**。
2. **`cli-tests` `burst` 超时（`test_lifecycle.py` 两条 `burst` 用例）**：
   - **定位证据**：[s10-diag-result.json](../../../../../../output/evidence/2.0.5-03-S10/20261121-s32-s33/finding-c-diag/s10-diag-result.json) 实测：`tools/cli/run_store.py::append_event` 为防混合快照对每条事件原子更新 `run.json`（`atomic_json`），507 条事件在**空闲机器**上单次即耗时 **3641–4265 ms**（`cli-tests-idle.log` 亦显示两条 `burst` 用例空闲耗时 **6.60s** / **3.93s**）。而 `test_lifecycle.py` 虽将外层等待设为 15–20s，却未覆盖 `burst` 请求的 `soft_timeout_sec/hard_timeout_sec`，使其继承默认 `soft_sec=2 / hard_sec=4`；Windows 4 KB 匿名管道背压使 `fake_cli.py` 在 `runner.py:278` 超过 4s 时被正常硬超时终止。
