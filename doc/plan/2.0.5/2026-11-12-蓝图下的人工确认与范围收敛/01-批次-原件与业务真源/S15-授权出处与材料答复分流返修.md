## R2　哪些原件能支持有权裁决

**修前与接口。** `flow/update.py::_original_kind` 把除质询目录三个文件外的可读文件都返回为 human。复评只引作者的 story-template.md，公开 feedback 已返回 eligible=true。保留 S14 的首次 `--questioning-candidate`、第 7 块同轮核验、update 对已登记稿的版本绑定、四类反馈、原生资格和 owner 采纳合同。只替换权威裁决的出处判断与对应的作者提示。普通意见、建议、事实补充继续走各自合同。

| 输入 | 运输层如何认原件 | 作者、owner 和独审者怎样判效力 |
|---|---|---|
| 设计问答原话 | 从当前需求 materials registry 的 source/version 取 kind=answer 的 answer_record 或 answer，校路径与实际字节 SHA。JSON 和阅读稿沿用 answers.export 的登记；历史版本保留原身份。 | 从具体题、完整 reply、时间和上下文判断谁批准哪一项。材料门选项只证明补料选择。历史原话的可追溯性不能自动赋予当前版本效力。 |
| 直接批注、改稿、追加及会话转述 | 取本轮 prepare 固定的 review_inputs，以 before 原件和该行的路径/完整 SHA 为据；系统件同时核实际批次回执。可接受对应的当前路径或快照引用，须定位到同一版本。尚未开 update 的 init 仅用本次实际取得、来源可核的原件；本地意见和会话原话依已有评审输入取得路径保全。 | 原件保留说话人、原话与所针对的稿。评审人建议、转述者推断、仅仅改了系统正文都不能自行定案。转述能追到有权人明确说法才支持相应裁决；只有意见时按 opinion/suggestion，真正阻断且本人可定才问。 |
| 正式决定、会议中有权人的话 | 复用 `materials/registry.py::files_view` 的来源身份、稳定版本行和原件摘要。可变别名按 reference 落到稳定版本；会议阅读稿沿已有同源关系回到 raw/原件。聚合稿须追到相应 components 的实际原件。具备正式来源的批注附件按上一行取证。 | 找出具体签发主体或会议发言人、决定对象、适用期和原文位置。材料里明确有权人在本范围作出的决定可直接复用；一般需求描述、会议上他人的主张或作者的整理只支持其实际事实。 |
| 质询回复、蓝图、Story、写作计划、update-notes、机器报告和工程文件 | 文件可读仅证明引用在场。可作技术/上下文佐证；作者稿不会因目录名像 answers、复制进收件箱或出现在技术任务中就变成人签。只有原件被人实际批注/改写的部分可按评审输入回查。 | 单用这些内容时不给授权裁决候选。模型不能再把自己的总结写成“用户同意”；可保留为建议、事实或 gap，并交还原责任人。 |

**执行决定。** 在 `cmd_update_feedback` 一次为本次反馈取得现有材料索引和本操作的评审输入，归一需求相对/工程相对引用，按同一实际路径、版本和摘要查证；片段留给读者定位，技术地址依原生解析。缺出处、越出本需求来源集合、摘要漂移、读不出或只有技术证据时给出原因与可修位置，整个无资格结果不返回可提交候选。多条引用允许人的原件和技术佐证并存。保留可读、有身份的普通材料作为**可能载有人签的来源**，具体话是否支持反馈中的 owner、target、revision、期限和承诺，由 owner 对原件核定。脚本不猜说话人、不做子串授权、不建“已授权”文件表。对同字节反馈的失败重试沿既有再核分支；历史提交资格与实际采纳分开。

**关键指令。** 在安装后的 `phases/update.md` 反馈段定义：“先指出谁在原件的哪一处，对哪个对象、哪个版本、什么期限作了什么决定。没有这句话就保留意见或缺口；有这句话再随反馈交给蓝图负责方核权。”init 的 `phases/design.md` 在取得本轮候选和答复后指向该段。feedback 的失败 action 应点出实际问题，例如“这个引用是作者稿；请引用已取得的人答或含决定的来源原件，或按实际性质提交意见”。不要求重新签已有裁决。

**复验。** 从真实 status→decide 导出一条有范围限定的答复；同一候选、同一 feedback body，依次换为真实导出、真实取得的人工批注、可查正式决定、只有质询回复、只有作者稿、伪同名未登记件、已变字节。核 init 和 update 的完整结果、action 与 owner 取得的原件。对“本轮同意”和“建议以后做”作独立语义对照。不得手写人工答复导出或开轮记录来证明该生产路径。

**正式依据的边界。** 使用原有正式决定时，先定位实际签发/会议原话所在的段或条目，连同能够核对说话人职责与该次决定的材料交 owner；设计事实已有原生来源引用时沿引用回到登记原件。归入 PRD、上传者身份、材料清单的一行、模型自填的 authority.owner/role，都不能独立证明其中某项承诺已经获准。归属或是否明确拍板取不到时按待核来源处理，保留原件；能直接用已有有效决定解决的也不要求补填一份新表。对稳定的旧人答仍可回查旧版本；是否适用本次目标要另核，不能把它重标为当前人答。

## R3　材料答复按整句分流

**唯一材料门合同。** 收到人的完整回复时，先由主作者区分“在明确选择”“在询问/附条件”“只是补充材料事实”。工具只为完整、无歧义的选择落盘。保留原文用于本次 ask；模型不能截出“选2”、删掉问号或把选项改写成用户的话去调用 decide。

| 整条回复的情形 | 工具动作与人的下一步 |
|---|---|
| 整句裸编号、完整的“第 n 项／选 n”、完整选项标签 | 验当前 ask 与编号/标签，记录人的整句；沿既有 supplied/confirm_scope 分流。只去首尾空白和确定的陈述结束符，完整标签按合同标点比较。 |
| 明确选择并重述**同一**选项，或已经支持的简短枚举确认“1）就这样” | 按完整表达匹配，保留原话。枚举后的文字仅在可完整验证为同一选项标签或既有明确确认格式时自动承接；任意业务附言不能凭编号前缀放行。“不选 1，选 2”各分句均为完整选择表达且唯一肯定，保留；仅否定、矛盾或多个肯定不落 accepted。 |
| 疑问、反问、条件、保留意见、尚未决定、正文中引用别人的选择，或编号后带其它自由附言 | 材料门不前进。先保留原文、处理能直接处理的补料/问题；还需要判定材料选择时，只澄清这一个选择。即使附言看起来无害，只要工具不能按整句协议验证，就不从附言推授权。独立提供的业务事实继续按原职责使用。 |
| 业务设计问答的自由答复 | 仍经设计问答 ask/item 逐字保存，“仅本轮”“暂缓”“只同意其中一项”按 R2 回原件判断；材料门的限定语法不扩到这里。 |

**替换与提示。** 在 `flow/asks.py::pick_explicit` 用全输入覆盖代替“先丢标点→拆分→忽略不认识的分句→累计肯定项”。先识别完整合同标签；对编号选择和受支持的复合选择用全句语法核，有问号（含中英文）、引用语境、额外未消费文字或不能确认的词句时走澄清。标点清洗不得把“选2？”等同“选2”。既有“1）就这样”是发布接口已测的显式例形，不能据此扩出自由附言或同义词猜测。材料 SKILL 只维护一次使用说明：“可以直接回编号或完整选项。若你在问这个选项的含义，我先回答；若还要补材料，我先保留缺口。”工具报错指回本次真实问法。保留材料未到时的磁盘检查、错误原因、原 ask 和重入。

**实际入口验法。** 从一次真实 material_scope 的 status 取同一问法，为每个输入使用独立前态。成对跑“选2／选2？”、“1）就这样／1）要等材料到了才这样”、完整标签/同标签后带质疑、“不选 1，选 2／选 1，选 2”、编号作业务数量和“选2？我还没有决定，材料还没齐。”。核退出码、gates 前后、next 和展示给人的回复；允许补料而签认选项的正例须准备该选项所需的实际材料。既有 `test_material_rounds`、`test_rework_guards` 的有效正例和不扩大选择的负例继续成立。

## R4　只修展示，不改问法状态

本项对应复评发现 3。保留对人可读的题号；若操作用的 item_id 含原生地址或路径，展示层按本组原顺序给人读序号，部分答复后保原序。记录时主作者从结构化 items 取原 item_id，不把展示序号当成新的绑定身份。

保留 `pending_view`、完整磁盘 ask、ask_id 算法、操作身份与答完续行。设计问答 `asks.block` 只展示题号、业务问题、候选、必要的建议/业务理由。source_ref、机器路径及供作者核验的定位留在结构字段和导出；作者写给人的 question/reason 用可理解的来源说明，不把路径改贴到理由里。接口采用当前形状：status 或显式重试读 `ask.block`；部分答复后的 decide 读 `ask_block`，其 `ask` 继续返回 ID。分别修 `decisions.py` 的 nextAction 和设计阶段页的接手续句，不增字段或第二个渲染器。

关键句：“status 把本次要问的内容放在 ask.block；刚记下部分答复时，直接展示 decide 返回的 ask_block。有几题待答就展示几题。”同一轮两道本人可答的问题，另一道第三方问题留 gap。答一题后同时核普通 status、显式重试和 decide，展示文本应逐字同义同形，只有余题且不含内部路径；系统侧原问法和已答证据仍能查回原 source_ref。零待答不展示空问卷。

## R7　用一次真实职责交接补证（产品 G0/X0）

复用现已正确的三稿说明、首读派发、原件任务、蓝图原生质询和 `chapter` 提交。只补证；本项发现新的产品差距须回报设计者，不在该项顺手改门禁或作者协议。

1. **固定来源与对照。** 使用合法 AR 号、正式安装的当前机制和隔离需求系统，沿此前 `archive-ar` 的无前缀放行路线。由归档与读回产生 B0；本地未发布的有效修改为 L1；评审人从 B0 作 E1。系统 fetch、inputs、prepare 产生 E1 身份、原件和 before。由输入提供者给出一处异段独有改动和一处同段冲突；业务输入中应有真实影响的限定（例如期限或适用对象）。预期只用于维护评审，不送给作者作为答案。
2. **原话→候选。** 需要本次用户作决定时展示实际 ask，保存用户消息、decide 返回、导出的版本/摘要与相应 item。主动改稿/意见走评审原件路径。对冲突处理必须能从真实回执的 saved 或本轮 before 找到 E1。notes 引用实际原件位置及人的完整限定；同名文件、测试脚本里的常量无取证效力。
3. **候选→蓝图。** 已有 Story 的 update 采用该稿登记的 blueprint_ref；首次设计的合法对照沿 R2 第 7 块。执行原生 feedback 资格校验后，由承担 component-design 的作者在原生调和步骤读输入并实际判断。若采纳，保旧候选、反馈文件及 feedback_id、owner 的处置理由、新 revision、决定/受影响对象的 provenance 与重新生成的投影；让原质询者核修订后的目标和限定。结合 `feedback-related` 的精确来源关联与实际蓝图内容核，单独返回候选或“待确认”均不能证明已采纳。拒绝或缺权时保 gap/理由，不把它写成已实施。
4. **蓝图→Story→下游。** 将实际原件与新投影交给负责写章的作者，由作者独立写受影响草稿，沿安装件 `story-build ... chapter --from ...` 的正常用法提交。保留章节提交输出、最终 Story、真实 notes 和位置。设计者从最终段落反查“谁、什么条件、有效多久、异常去向”，再核 L1 与 E1 的独有信息各有去向。若写了“5 分钟”却少“仅本轮”，即使 notes 中提到也判失败。首次 prepare 时取首读 dispatch，接收前保存后读 task，接收后区分复用载体。沿登记、close、发布比较、归档读回及 restore 验保护。纯表达分支保当前蓝图身份，独立于需设计修订的主链。
5. **谁写、能证明什么。** 外部服务、需要投放的人答和传输可用隔离替身；采用、蓝图 revision、报告身份、真实章提交和最终成稿从相应职责的实际工作取得。可由维护者在隔离工程按作者职责读材料、做判断和写章，标明实际写者，结论限于这次离线交接。程序不得替 owner 预填接受、按预期字符串拼 final 或直接覆盖 AR/story.md；读者替身只证明运输。交回一条从最终业务段回溯到反馈、原话及原件版本的完整实例，以及纯表达不升 revision 的对照。没有完成的环节照实列未覆盖，不用真实 CLI 越权补齐。
