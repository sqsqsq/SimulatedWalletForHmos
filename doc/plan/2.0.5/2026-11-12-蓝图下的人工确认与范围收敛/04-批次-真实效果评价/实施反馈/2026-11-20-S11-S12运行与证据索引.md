## 3. 两例运行顺序（初始 + auto 一次 update）

### 3.1 总顺序

```powershell
# 1) 只读计划（起跑前）
python test/scripts/run_multi_case.py plan --all --jobs 2

# 2) 起跑（两例严格顺序启动，之后并行；每轮只在用户授权后执行）
python test/scripts/run_multi_case.py start --all --jobs 2 `
  --suite-id story-suite-<YYYYMMDD-HHMMSS> --authorize-non-sandbox

# 3) 观测与作答（heartbeat 或 watch 二选一）
python test/scripts/run_multi_case.py watch --suite-id <suite> --interval 60
#    有定时唤醒时用 heartbeat，每次唤醒只 poll 一次：
python test/scripts/run_multi_case.py poll --suite-id <suite> --wait-sec 0
```

- `start` 返回 `next_action=poll_after_interval`、`next_interval_sec=15`；宿主随即建立绑定 suite-id 的 heartbeat（或 `watch`）。
- 每关三步（TEST §3.2）：读 `adaptive_reply_requests[]` 的完整 `model_prompt`（`question_truncated` 为真时读全文）→ 判断属于哪种 `--reply-kind` 并作答 → 同一回合立即再 poll。
- `--run-id` 与 `--turn` 原样带回；**回复只落到宿主看到的那一问**。回话多行/带引号/以 `/` 开头时写 UTF-8 文件用 `--text-file`。
- 不设时限、不设轮次上限；`awaiting_reply` 在出现的那次唤醒内回完，延迟记入观测记录。
- 同一句回复：`observations.jsonl` 的 `interaction_reply`（含 `at`、`delivered`、`covered_steps`、`reply_kind`、`reason`）。宿主的实际回话原文另存 `output/story/<suite>/host/replies/<case>-<turn>.md`（便于 S12 核"人答是否注入"）。

### 3.2 auto-topup：第一段（到 `story:submitted`）

1. 模型在材料关卡停下时：`--deliver 交通卡自动充值.docx`、`--deliver 交通卡澄清会记录-0903.docx`，回"已放入"（`--reply-kind planned --step hand-over-the-ui-doc`）。
2. 后续按实际问到作答（问到才用，未问到不预送）：`no-real-interface`（模拟数据承载）、`terms-confirmed`（术语表确认；宿主先核表再答）。
3. 交付关卡：回答"送审"（`--reply-kind planned --step deliver-for-review`）。这是**第一段的交付授权**；模型须真实归档/送审（发布记录 + 已发布副本 + 需求系统正文与评审记录附件逐字为当前 Story/Review）。
4. 模型做完被授权动作后停到**第一检查点**（`awaiting_kind: initial_checkpoint`）。若最后那一问就是交付选择，按第 3 步答完再等它停；若本段没有待办，才允许 `conclude`。
5. 到目标但拿不到 session → 终态 `cli_session_lost`，不报完成、不另起 run。

### 3.3 auto-topup：检查点 → 回流 → update（顺序固定，TEST §4.4）

```powershell
# 6) 固定第一段快照（停着、无写入者时复制）
python test/scripts/run_multi_case.py checkpoint --suite-id <suite> --case auto-topup --point initial
# 7) 只读评测第一段快照（评分结论不在这一步公布给模型）
# 8) 回流到维护仓 doc/features/AR90006
python test/scripts/run_multi_case.py promote-checkpoint --suite-id <suite> --case auto-topup --point initial
# 9) 投第二段：case.yaml 的 update_request + update_inputs（本 Case 无 review_human_zone，不需要 --review-feedback-file）
python test/scripts/run_multi_case.py resume-update --suite-id <suite> --case auto-topup
# 10) 第二段材料关卡：按 update-material 回"本次没有其他材料"
# 11) 第二段停在第二检查点（stop_reason: update_checkpoint）
python test/scripts/run_multi_case.py checkpoint --suite-id <suite> --case auto-topup --point update
# 12) 只读后评 → 收工
python test/scripts/run_multi_case.py conclude --suite-id <suite> --case auto-topup --reason "update 已关闭，第二段无其他待办"
```

- 第 9 步会先投 `update_inputs` 再排 `/story update AR90006`：`交通卡自动充值-v2.docx` → 需求目录 `inbox/`；`review-feedback.md` → 需求系统 `<sys>/AR90006/review-feedback.md`。写前核不成立时一项不写、不发请求。
- 若模型问到单日上限变化，按 `update-daily-limit-conflict` 答"这版产品需求已经把本期单日上限调整为 300 元，协议文案也按 300 元更新"；**不问而有据按 300 更新同样合法**。
- 第二段到终点后必须 `checkpoint --point update` 再 `conclude`；不发 `conclude` 会一直等、最后只能被外部停掉（终态成 `worker_lost`）。

### 3.4 car-key-sharing：第一段（到 `phase:plan`）

1. 材料关卡：`--deliver 数字车钥匙分享.docx`、`--deliver 车钥匙接受侧界面说明.docx`，回"已放入"（`--step hand-over-the-product-doc`）。
2. 之后按实际问到作答（问到才用）：`materials-complete`、`grace-window-initial`（48h 收回 + 车辆侧即拒）、`car-key-card-scope`、`no-real-interface`、`draft-resume-boundary`、`acceptance-ratio-owner`、`terms-confirmed`。
3. 交付关卡：回"实现方案"（`--step implementation-plan`）。模型继续走 design_handoff 与各施工单位 spec/plan，直到 `end_at: phase:plan` 的判据成立。
4. 到目标后停在第一检查点；若最后的待办是"要不要编码"之类，明确"本轮停在方案，不进入编码"；无待办则 `conclude` 后 `finalize`。
5. **本版不追加第二次 update**：`car-review-feedback.yaml`、`update_request: /story update ISSUE-206` 与 update 备料一律不投；若装置/宿主误投，按原样留证并报设计者。

```powershell
python test/scripts/run_multi_case.py checkpoint --suite-id <suite> --case car-key-sharing --point initial
# 只读评测第一段快照
python test/scripts/run_multi_case.py conclude --suite-id <suite> --case car-key-sharing --reason "实现方案已到终点，无第二段"
```

### 3.5 收尾

```powershell
python test/scripts/run_multi_case.py finalize --suite-id <suite> --promote
python test/scripts/measure_run.py output/story/<suite>/cases/<case>/<run>
```

- `finalize --promote`：回流 `doc/features/<编号>`；实际续跑过第二段的 auto 落到 `AR90006-update`，第一段那份不被覆盖；car 按实际段落（本版不跑第二段）回原编号。两例都应取到 dsh 原生会话（缺失记 `not_captured`，不代造）。
- `measure_run.py` 只报数：段、耗时、人工等待、工具/审查区间、门禁与返修、上下文增长；未知不记 0。
- 收工后核 `promotion-manifest.json` 的 `segment`/`partial` 与终态 `artifact`、`terminal`。

## 4. 投放时刻、等待与中断恢复（取证要求）

### 4.1 投放/收到分开记

| 输入 | 投放记录 | 收到记录 |
|---|---|---|
| 第一段补料（`supplements/`） | `observations.jsonl` 的 `interaction_reply.at` + `delivered`；`inbox/` 副本字节 = 源件 SHA（见 `01-两例计划与固定输入.md`） | `materials.json` 的 `inbox_path` / `original.sha256` / `acquired_at`（会议件另看 `meetings/<键>/source.json`） |
| auto update 的 `local_material` | `update-delivery.json` 逐件 `delivered_at` / `sha256` / `bytes`；`queued_at` + `request` | `materials.json` 的导入记录（同一件按 `inbox_path`/SHA 对） |
| auto update 的 `system` 件 | 同上（`kind: system`，`destination`） | 本次取材回执 `AR/story-src/fetched.json` 的 `status`/`sha256`/`bytes`/`fetchedAt` 与批次 `.receipt.json` |
| 人工区意见（本版不投） | —（car 不投第二段） | 无 |

- **投放 ≠ 收到**：不得把 `delivered_at` 或 `fetchedAt` 互相当作对方；`reconcile_update_receipts` 在终态回填 `received`/`not_received`/`ordered_only`/`unknown`。
- 报告完整性、逐件收件归账的判定以 S26/S28/S29 最终实现为准；修前 counts 只作历史对照，不作 S11 度量依据。

### 4.2 人工等待

- 模型停在 `awaiting_reply` 会一直等，每 5 分钟发 `awaiting_reply_stale`；回话即继续。
- 记录实际等待（`waited_sec`、`human_wait_sec`），不把事件空档叫推理耗时；宿主自己的思考/操作时间如实单列。
- 同一件事连续没有业务进展时，不机械连发"继续"；按故障报用户。

### 4.3 中断恢复

| 情形 | 处置 |
|---|---|
| `watch` 被内存回收/终端关闭 | 先零等待 `poll` 补回漏掉的回话，再以 `--interval 60` 重起；在回复里说明是回收后重启（用户已长期授权） |
| 模型无业务进展的循环/卡死 | 保留原话与事件，报用户；`retry` 只在用户同意后执行（干净基线 attempt+1），`stop` 同理 |
| 内容审查 400 / 401 | 按 TEST §2.1 配置组处理（装置自动重跑/熔断切换），宿主不手工作答；换配置即换被测对象，结论按 `cli_config_id` 记 |
| 测试被宿主中止（内存等） | 用户已授权直接重起；期间不改被测源码、不提交；保留被中止的那次与重跑结果 |
| 到目标拿不到 session | 终态 `cli_session_lost`，不另起 run |
| 运行中出现真实违规/失败 | 按 TEST 处理并保边界；诊断与正式效果分开，不自行豁免旧规则、不重跑到绿 |

## 5. S12 证据索引与缺证项（58 项标准、评分/用户确认边界）

### 5.1 每 run 必须保全（S12 逐条回指）

```text
output/story/<suite>/
├─ suite.json / workspace-boundary.json / cli-registry.json / previous-run-cleanup.json
├─ controls/<case>/{active.json,latest.json}
└─ cases/<case>/
   ├─ observations.jsonl / observation-record.md / promotion-manifest.json / source-diff/
   └─ <run>/
      ├─ state.json / live.jsonl / events.jsonl / runlog.md / worker.log
      ├─ gate_*.log / gate_diagnostics.json / phase-results/
      ├─ cli-runtime/<runtime-id>/{request.json,run.json,raw.jsonl,events.jsonl}
      ├─ usage/{initial,update,final}/usage.json
      ├─ native-sessions/<session-id>/（manifest 记来源与摘要）
      ├─ checkpoints/{initial[,update]}/ + .reports/ + .dependencies/
      └─ artifact/ + artifact.dependencies/
```

- 每次独立调用保完整父/子会话与 final、读者写入的报告原件、接收/登记/改稿事件；含 fail、格式补正、未完成轮。
- 检查点与终态按同一刻 `source_index` 固定根外依赖；读不到/摘要不符标 `incomplete`。
- 宿主回复原文、`update-delivery.json`、`fetched.json` 与投放前 `materials.json` 一并列入索引。
