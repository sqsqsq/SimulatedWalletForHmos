## 已核定的生产者、消费者和缺口

1. Extension 的 `skills/story/SKILL.md` 已有 frontmatter `description`。这就是可复用的发现说明。f894 的 `extension-loader.ts` 对 manifest 1.1 的 `provides.skills` 只接收 Skill ID 字符串；`instance-skill-bridge.ts::formatExtensionSkillSectionMarkdown` 生成根入口表时只输出 ID 与路径。跳板的 description 固定为“实例扩展 Skill：story”。单纯换正文或 metadata 都晚于普通前门选路。
2. 在 S24 的实际 f894 包上，保持 manifest、宿主和包不变，只在隔离源里给 Story description 增加 AR 规则，重新走正式安装与物化。两组均 installed、entries check=0；已装 Story 源字节改变，AGENTS、CLAUDE、共享 Skill 跳板与通用 project-entry 四份字节全部相同。这是对公开入口的直接反例。阶段钩子只覆盖已选阶段，特别简单可以不经设计；知识索引、编译定制与历史已撤的 AGENTS.section 不承担此职责。
3. **定案**：普通请求的主作者在首次选路前取得已安装 Skill 的适用说明；Story 的 AR 语义写一次，归原 Skill 的 description。首选让 Framework 的现有根入口渲染与 Skill 跳板消费同一份已有 description；也可由上游给出在微型、短设计与仅方案路径上同样早送达的正式机制。框架只负责投送实例说明；身份来自用户原话的需求编号。无需建第二套分档、路由服务或状态。已给 [Framework 所有者的两个核实问题](../Framework对接-普通入口与原请求恢复.md)。当前 f894 无此已证能力，不能把在晚到的页面加提醒签作普通 AR 已修。

**关键句。** “本次需求编号以 AR 开头时，须在本单形成或更新 AR/story.md。只看方案止于设计，开发按已有授权继续，归档按该单送审授权。非 AR 微型、小型已授权普通开发可直接交改动与适用验证；小型先形成同请求短蓝图。”执行者在源描述中保留原有 init、update、archive、restore 的用途。正向产品改写限该来源的一行替换 G1/X1，已由设计者条件批准：有正式可用的前门消费方式时随同接入和复验；未到件前只在隔离候选试验，不能把单独的说明改写记为已接线。其他实施选择改变所有权或需更多产品代码时，交实际差异由设计者定。
