## 3. 发现

### R1 退出载体的三项附带能力没有承接者（前置）

- **有效依据**：AGENTS §3.2「替换旧机制完整退出……有效能力与回归保留」；用户「删除载体不能删除对应能力」（修订 2 版本范围第 11 行同样写了）。
- **实际位置**：
  - `extensions/skills/story/phases/meeting-read.md` 第 95 行：会议关卡一轮里「参会人角色：你判出的角色一行，请人确认」。auto 交互脚本 `meeting-roles` 就是这一问。修订 2 的 R02 要求「按原话和发言者权限理解」，但角色从哪里确认没有着落：R01 的三种问人条件都是业务决定，覆盖不到「谁是产品、谁是支付」这类身份事实。
  - `phases/design.md` 第五节第 3 步：没有可用独审时，「prepare 已把未审披露写进 Story 交付章与 Review 题头」。
  - `SKILL.md`「归档」：「成功后输出这次带着送审的未决议题与未验证项：向人展示」。现在的来源是 Review。
- **影响**：第一项会直接削弱 R02——发言者权限判断没有确认过的输入，模型可能把非决定人的话当拍板，正是 D02 R1 那类错误。后两项是用户可见的提示，退出后会静默消失。
- **责任**：Spec 修订 2（保护表与 R10 没有逐项列出四类载体的附带能力）。
- **要求的结果**：在 R01 或 R02 写明参会人角色这类身份事实的确认方式（例如在材料关卡或同一次集中提问里一并确认，确认的是事实，不是业务裁决）；在保护表补「未审披露」「归档时展示待定与未验证项」两行，来源改为蓝图 open gap 和 Story。
- **复验**：保护表逐行对照 §2.3。
- **调度**：前置。Plan 的变化台账要逐项给被替换物的接替者，读的就是这张保护表。

### R2 规格层有几条按 D02 个案写成的规则（前置）

- **有效依据**：AGENTS §3.2「机制层零测试特征……换合法题材/表达仍成立」；修订 2 自己在依据层第 70 行写了「具体测试业务、接口名、Case 数字不成为通用产品规则」；项目记忆「示例形状压过规则文字」（被测模型照示例不照规则）。
- **实际位置**：
  - R05 第 1 段：「不以『没有图片/SDK』忽略新增文案资源、不把有真实依赖的交互说成独立按钮、不拿非持久化当本地状态不存在」——分别对应 car 的 DFX 误判、auto 的 page-interaction 拒选理由、auto 的 agreementNo 判断；
  - R03 第 3 段：「缓存/无缓存等真实条件不相互矛盾」「不得以类型目录……冒充实际页面」——分别对应 auto 管理页与 car 的 c4 目录。
- **影响**：Plan 很可能把这些句子原样转进作者页或审查任务，成为针对两个 Case 的特征规则；换一个题材，这些句子既不适用，也无助于发现同类错误。
- **要求的结果**：规格层只写通则——「适用、不适用、不选用的理由必须与当前需求的真实依赖和设计一致」「页面与数据的承担者必须是实际存在或本期设计的对象」；个案保留在依据层 A12 作为样本，验收 AC15、AC19 用样本取证。
- **复验**：换一个题材（例如「会议室预约」）读 R03、R05，每句仍成立、仍有判断力。
- **调度**：前置。Plan 会依据它写模型指令。

### R3 测试与宿主需求混在产品需求和验收里（前置）

- **有效依据**：maintain spec 第 1 步「测试条件……写进依据层的测试条件清单」；AGENTS §2 所有权表把「测试域」与「Extension 机制」分开；用户本次要求「确认没有把测试条件混入产品需求」。
- **实际位置**：
  - R09「维护验证与输出运输（测试/宿主责任）」排在 R01—R10 产品需求中间；US22（测试运行者）、AC22（大输出与 spill 进入测试）排在产品用户故事和验收里。
  - AC21 把产品行为（Extension `usage.py` 记录的身份与完成，标准 I4）和测试计量口径（measure_run 把对象目录当审查次数、父 usage 当 API 次数）写成同一条验收。
  - 修订 2 的标注本身是准确的（R09 标题写明测试/宿主责任，§9 写「R09 归装置/宿主，不混入 Extension 通用机制」），问题在于版面位置：Plan 按 AC 列表分配步骤与预算时会把它们当作产品验收。
- **影响**：测试装置和 DSH 的改动可能被计入 Extension 产品预算（AGENTS §5 计量只算 `extensions/`），或产品验收被测试装置的进度卡住。
- **要求的结果**：把 R09、US22、AC22 和 AC21 中的计量口径部分移到独立一节「测试域与宿主需求」，自带编号与验收，仍属 2.0.5 范围；AC21 只保留产品侧（usage 记录真实身份、未知不填、退出 Review 不制造虚假阶段）。
- **复验**：产品 AC 列表中每条的承担者都在 `extensions/` 内或原生合同内。
- **调度**：前置。Plan 的验证计划和预算按 AC 分层。

### R4 FR1 有一条原生内备选路径未核，上游诉求发出前需用户确认（前置，只限 R06 的恢复部分）

- **有效依据**：用户 11-12「对最新的蓝图有新能力诉求……尽可能避免，如果从机制上是更优和必须的，可以提……是否阻塞」；AGENTS §2「缺 Framework 能力回其所有者」；D02 原生反馈文件头「未对外发送……供用户与相应维护者核合同」。
- **实际位置**：
  - 机制结论「Framework 恢复的确定性结论」第 3、4 条：修订**前**以 `prepare-run attended` 创建状态成功；run 内 `reviseCurrentScope` 有真实消费者；「未执行创建后的 next/execute」。也就是说，「实现方案请求一开始就以原生 attended 载体承接、修订时走 run 内修订」这条路径既没有被证伪，也没有被验证。
  - Spec R06 第 3 段写「按下节 FR1 取得上游能力」，U2 写「Framework 维护者交明确入口/修复」，都默认这条诉求会发出。
- **判断**：修订 2 把 FR1 限定在受影响链、不作全版前置，这个依赖边界是准确的。但在用户「尽量避免新能力诉求」的前提下，应先核这条原生已有路径：它是否真能消费修订、是否在本仓 interactive 维护范围内（AGENTS §0 只覆盖 interactive；attended 是否算 Goal 范围要判）。核不通再提 FR1。
- **要求的结果**：U2 改为两步：① 设计者在 Plan 前段用隔离探针核「实现方案以 attended 载体承接并经 run 内修订恢复」，同时判它是否在维护范围内；② 不通或超出范围时，FR1 经用户确认后再发给 Framework。R06 的措辞相应改为「取得合法恢复路径（原生已有或上游提供）」。
- **复验**：U2 的两步各有取证位置；R06 不再预设上游一定要提供。
- **调度**：前置，只影响 R06 恢复部分的 Plan，其余范围照常。

### R7 修订 2 收紧了用户已确认的 Q13 答复登记口径，需用户知悉（随批，随修订 3 一并确认）
