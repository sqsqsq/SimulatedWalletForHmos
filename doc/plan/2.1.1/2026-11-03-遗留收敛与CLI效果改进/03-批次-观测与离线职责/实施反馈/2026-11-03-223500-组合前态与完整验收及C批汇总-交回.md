**同参数三类合为一个状态组。** 原来的`TheDerivedContractCarriesTheObligations`、`ThePlanTableNamesTheClassMethod`、`TheHostChapterExplainsTheUnit`三类参数相同（WITH_ROLES=True、PATTERN=selected、ELSEWHERE/FACTS/PENDING=False、STEPS=(freeze,)），合成`TheDerivedUnitWithItsRole`，只做一次make_project/design/freeze：

保留了一正一反的实际post_check：

## 2. V1：两条正常路径的真实证据

两条都补了最小的真实原生准备，分别经阶段写入与实际消费者验证。用例放在`test_cu_knowledge_chain.py`，复用`design()`改夹具蓝图的同一入口，新加两个开关：`acceptance=False`、`use_cases=True`。

| 路径 | 前态（原生真实准备，冻结后） | 阶段写入与实际消费者 | 用例 |
|---|---|---|---|
| Spec验收投影absent → 本阶段写验收 → Spec检查 | 设计对象不带验收也不带契约。spec阶段原生解析ok，验收为absent；plan被原生挡在`acceptance=absent` | spec写`acceptance.yaml`：不带`knowledge_refs`时，spec门禁点名OBS-02“没有验收条目承接”；带上后门禁放行，plan阶段验收改由`artifact acceptance@1`解析，plan解析ok | `ASpecWithoutAnAcceptanceProjectionWritesItsOwn` |
| contracts absent但有use-cases权威 | 设计对象带一段`use_cases`、不带契约。原生contracts投影为absent，artifacts仍含`use-cases@1` | 原生权威对齐（`authoritativeContentDrift`，与原生plan检查同一函数）：只写契约时判`use_cases:$`漂移；照权威写`use-cases.yaml`后aligned，plan门禁放行；分支改引AC-999时原生判`use_cases:refreshed.linked_acceptance`漂移，plan门禁点名“use-cases.yaml 引了验收 AC-999” | `APlanUnderAUseCaseAuthority` |

B01交回里“方案点名的两条生产路径都已覆盖”，收窄为下面已取得的具体路径：
- ① resolved：原生物化或冻结取得的契约，由plan门禁消费；
- ② Plan contracts absent：`APlanWithoutAProjectionWritesItsOwnContract`；
- ③ Spec acceptance absent：以上第一行；
- ④ contracts absent带use-cases权威：以上第二行。

invalid交owner仍沿原有`readFeature`停下的路径，本批没有单测。

**实测中看到、本批不处理的两点（交设计者判断）：**
1. 只去掉验收、保留契约（acceptance absent + contracts resolved）时，冻结后原生在spec阶段把`codebase`判为`input binding stale; return to scope owner`。所以第一条路径改用验收与契约都不带的前态。原因在原生绑定比对里，本批没有授权追查，也没有改原生；记录为未归因的原生观察。
2. use-cases权威下，plan作者任务只给通用的“设计已有的权威内容照它写”，没有点名用例权威及其位置。约束本身由原生对齐守住（上表），作者从哪里得知要写use-cases属于作者面送达。这次没有改产品。
