# 裁定：update 缺补料环节（2026-09-21）

来源：用户在 T2 测试中反馈「update 是否支持非 AR 需求？非 AR 的资料来源于 inbox，AR 也可能补 inbox，update 应有一步跟 init 一样的补充材料环节」。核实后成立，且影响正在跑的 auto Case。

## 1. 事实

| 项 | 位置 | 现状 |
|---|---|---|
| prepare 的检测集合 | `core/flow/update.py::cmd_update_prepare` | 只比监视集合、`AR/story-src/incoming/`、`--request`；不读 inbox，不调 `material_state` |
| 现成的材料事实 | `core/flow/routing.py:60-78 material_state` | `pending`＝收件箱里未并入正文的原件；`changed`＝材料指纹与本轮登记对不上。init 的材料关卡靠它 |
| 方法页 | `phases/update.md` | 只写「采用的料放 inbox 跑 round 登记」，没有「先盘点手上与该取的料」 |
| 本地单 | `story.js fetch` 明确拒绝本地单 | 唯一料源是 inbox，而 inbox 不在检测集合里 |
| T2 auto 刺激 | `cases/auto-topup/update_inputs` kind=local_material → inbox | 第二段起跑后 prepare 会报 `unchanged` |

## 2. 设计：update 的输入阶段就是 init 的第一级关卡（定稿，替代前两版）

用户 2026-09-21 定的入口记为 D21，设计者补进 spec 00 §2：**AR 单先触发上游系统更新检查并报告上游材料更新情况，同时问用户要不要补料；用户答了，再决定最终的材料变化。非 AR 没有上游，直接进入补料问询。** 用户同日进一步要求：init 与 update 大量重合，同一功能不实现两遍，尽量复用。

核过 init 第一级（`routing.py::scope_step`、`material_gate_state`、`material_options`、SKILL 真值表「材料关卡第一轮必停」、`rules/init_analysis.md` S2a）之后的定法：

**update = 开新轮 + 第一级关卡照走 + 范围沿用上一轮 + 产物对上次已处理版本比较 + 修订与审查。**

### 2.1 复用映射

| update 要做的事 | 复用什么 | 差异 |
|---|---|---|
| 取上游新正文与评审回稿 | `story.js` 的读系统 helper；材料链的 inbox 导入 | `fetch` 落点改为 **inbox**（不再另设 incoming）；评审回稿作为一份材料进 inbox |
| 报告上游与本地材料变化 | `routing.py::material_state`（pending、changed，磁盘逐字比） | 无 |
| 材料盘点、缺口判断、问料停等、交料、登记 | 第一级关卡 `material_scope`：选项侧车、清单、缺口判断、`decide` 人签、`round` 登记；`init_analysis.md` S2a 含 B1 补的那句 | 无；一次 update 开一轮，按真值表必停一次，这就是 D21 |
| 新会议 | 会议关卡 | 无 |
| 范围 | 范围关卡 | update 上下文**沿用上一轮结论不停**；范围要变见 2.4 |
| 上次已处理版本比较、镜像、恢复、收口、修订清单、派审 | 无对应物 | update 独有，保留 C1–C3 已实现的 prepare/close/restore、update-notes、派审五步 |

### 2.2 顺序

1. `/story update <编号>`：AR 单先 `fetch` 到 inbox；本地单跳过。
2. 开新轮（复用「材料再变会开出新一轮」的现有语义，`update.open` 记轮 id）→ 第一级关卡：材料盘点按 S2a，报告上游哪几份变了、没变、取不到，本地已有什么，问补料，**停等**。
3. 用户放料或答不补 → `decide` 记人签 → `round` 登记。
4. `prepare`：只做产物与真源对上次已处理版本的比较与镜像；材料事实来自本轮登记。四类都空且比较完整 → `unchanged` 快速退出，什么都不建。
5. 会议关卡按现有条件；范围关卡沿用上一轮结论不停；进修订清单 → 动作一至六 → 派审 → close。

**顺序硬规则（预跑实证）**：新料一律先 `round` 登记到本轮，再 `reopen` 撤销成文登记。预跑里增量没有退回关卡，靠的正是这个顺序（本轮关卡已全部 accepted、材料指纹已登记）；反过来先 reopen 再登记，路由会按「材料变了」送回材料与范围关卡。写进 `update.md` 与路由 `update_in_progress` 的 action。

**镜像范围**：`_mirror` 排除 `*/reports/`、`.backup/`、`revalidation.json`——它们不是业务内容（03 §7.2），且 64 位哈希文件名套进检查点目录会超 Windows 路径上限（预跑 auto 的 `checkpoint --point update` 第一次因此失败）。

### 2.2a 退出项

- C1 的 `AR/story-src/incoming/`、prepare 复制暂存区、close 清空暂存区、`update.md`「暂存区怎么用完」一段：退出，inbox 是唯一入料口。
- 前两版裁定的 `check` / `inputs` 动作与新停等：不做。

### 2.2b 落点、用例、预算

| 落点 | 改什么 |
|---|---|
| `03-统一update.md` §2、§8.1、§4.4；`spec/1.9.4/00` §2 | 输入阶段＝第一级关卡；D21；范围变化路径 |
| `story.js fetch`、`scripts/README.md`、`story-adaptation/SKILL.md` | 落点 inbox；评审回稿作为材料 |
| `routing.py` | update 上下文：第一级照走、范围沿用、先提 pending |
| `update.py` | 去掉 incoming 相关；prepare 的 unchanged 条件加材料事实 |
| `phases/update.md`、`SKILL.md` 真值表 | 「零、开新轮走材料关卡」，真值表材料一行注明 update 同样必停 |
| `test_story_update` | AR 单 fetch 落 inbox 且 pending 列出；本地单不调 fetch；不补且无变化 → unchanged；范围变化 → 尚未完成并 close 保留项（+4 条）；incoming 相关用例退出 |

预算：退 incoming 相关约 −25，加路由与落点改约 +30～45，机制侧净 +5～20；scripts_py 在途 2800 够，实际按交回核。

### 2.2c 变化判定的文件范围（用户 09-21 裁定；修正 C1 评审 §4 第 1 条）

判定范围只有**人和上游会动的输入与交付件**：`RR/prd.md`、`SR/design.md`、`AR/design.md`、`inbox/`、`AR/story.md`、`AR/review.md`、`spec/spec.md`、`plan/plan.md`。inbox 不按文件哈希比，用现成的 `material_state`（未并入的原件、材料指纹变没变）。

`decisions.json`、`story-template.md`、`knowledge-use.yaml`、`acceptance.yaml`、`contracts.yaml`、`use-cases.yaml` 是模型写的中间真源，只随交付件的修订而变，是结果不是原因，**不进判定**；进了只会让报告多出对用户无意义的行。C1 评审 §4 第 1 条把它们加进来是划宽了，C1 返修加的这六项退掉，`after/` 基准与差异同样只留八项；镜像与 restore 仍是整个目录。人的决定经 `decide` 记原话、评审人的话进 review.md 人工区、产品改稿进 inbox 或上游系统，八项已覆盖全部入口。

边界：acceptance.yaml、contracts.yaml、use-cases.yaml 是 framework 的强契约真源，framework 修正入口里人可能直接改；那是 correction 不是 update，按修正三问走，不由 update 判定。

用例：「手改 plan.md 被检出」保留；「手改 decisions.json 被检出」删除。

### 2.3 场景矩阵

| 场景 | 承接 | 现状 |
|---|---|---|
| 系统上游正文变 / 评审回稿 / 系统 AR 正文其实是自己归档的 story | 输入阶段 fetch 三态；来源角色由模型判（03 §7.3） | 已有 |
| inbox 新原件、新会议、图片与界面参考 | 输入阶段 pending；会议走现有 late 分支进会议关卡 | 本次补 |
| 手改产物、决策登记、写作设计、Plan 契约 | 监视集合 | C1 返修已补 |
| 人的口头要求、无字节变化 | `--request` | 已有 |
| 上一轮未完成 | resume | 已有 |
| 无变化 | 输入定了之后的快速退出 | 位置本次改 |
| 本地单 | 无上游，直接补料问询 | 本次补 |
| 只有材料 / spec 后 / plan 在途 / plan 闭环 / 已归档 / 已到代码 | update.md 进展表 | 已有 |
| 系统不可达、token 缺、基准缺席、读不到、镜像失败、写一半、外部改过 | incomplete、镜像先存、restore 留双方 | 已有 |
| 冲突、改已定结论、大幅重组、回写确认 | 问人四类 | 已有 |
| 人写过意见的议题变义或被删 | review 两条判据 | 已有 |
| 改动阶段的独立审查 | 派审五步 | 已有 |
| **范围要变** | 见 2.4 | **缺口** |

### 2.4 范围变化不在 update 内做

update 里判定范围要扩或缩时，03 只说「按权限问人」，没说答了怎么落；范围由 story-flow 的关卡定，而 update 上下文刻意不进关卡。定法：update 报「尚未完成：范围需重新拍板」并 close 保留项；用户走现有 `reopen` 进范围关卡重拍；范围定了再起一轮 update 更新产物。两条路各管一件事：update 更新产物，reopen 重拍范围。写进 update.md 动作四与 03 §4.4。

### 2.5 落点、用例、预算

| 落点 | 改什么 |
|---|---|
| `03-统一update.md` §2、§4.4 | 输入阶段定义、范围变化路径 |
| `spec/1.9.4/00` §2 | D21 |
| `update.py` | 收集函数（fetch 结果比对、material_state、监视集合、request）、`inputs` 动作、prepare 改为「定输入」 |
| `phases/update.md`、`SKILL.md` 真值表 | 「零、输入阶段」、材料那一停加 update 一行、范围变化路径 |
| `routing.py` | `update_in_progress` 先提 pending |
| `test_story_update` | AR 单 inputs 报上游与 pending；本地单不调 fetch；不补且无变化 → unchanged；放料后 changed 且 pending 列出；范围变化 → 尚未完成并 close 保留项（+5 条） |

不做：不另建材料台账；close 不清 inbox；不改 init 关卡；不写第二份比较代码。预算机制侧约 +80～110，scripts_py 在途签 2800，总 12270 够；target 在 T2 收口时按实测改签。

## 3. 对正在跑的 T2

入口流程变了，正式 T2 要在最终流程上跑。处置：

- 这一批两 Case 作为**预跑**：car 照跑到底、finalize，它的第二段观察「变化理解与关联修订」与派审接线仍有效，证据留存；auto 停在第一检查点，初评与回流做完后 conclude。
- 修复提交等这批 suite finalize 之后再进仓，避免 `harness_contaminated`。执行者先在工作区改与离线验证。
- 修复后**两 Case 重新起一批**作为正式 T2。这一批的成本按 04 §2.1 记故障成本，原因写明：入口流程缺补料环节，由用户在测试中指出。

## 4. 责任归属

设计缺口在 03 §2：它把「变化」定义为文件差异与暂存区，漏了材料关卡已有的两个事实；04 §2.3 的隔离投递把它暴露出来。记入 1.9.4 发布说明的「本版发现并修复」。
