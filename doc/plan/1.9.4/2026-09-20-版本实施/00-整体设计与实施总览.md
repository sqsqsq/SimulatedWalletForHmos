# 1.9.4 整体设计与实施总览

状态：按用户“重写整个 design，把逻辑、步骤、方案讲清楚”的指令重写。本文及链接分册为当前唯一设计，旧稿退出。需求依据为 [版本需求与结论](../../../spec/1.9.4/00-版本需求与结论.md)；用户决定不重做，技术取舍由维护设计者负责。本轮是设计交付，未实施产品或启动真实 Case。

## 1. 版本由哪些需求组成

| 需求 | 结果 | 设计与执行步骤 |
|---|---|---|
| A：Story 表达优化 | 长文减少混装、层级自然、表达具体；图表文帮助理解且内容完整 | [需求 A](01-Story表达优化.md)，A1 |
| B：关键缺陷修复 | 规约边界、评审状态、图关系、材料索取与返修路径正确 | [需求 B](02-关键缺陷修复.md)，B1 |
| C：统一 update | 模型判断有效依据与变化影响，使已有相关产物一致且可继续工作；可恢复、确认回写，替换独立 review | [需求 C](03-统一update.md)，C1/C2/C3 |
| 共同支撑：测试与发布 | 两 Case 同会话初次/更新后评测，分别回流；有证据发布 | [测试与发布](04-测试与发布.md)，T1/T2 |

Story 表达优化只是需求 A，不用整个版本名称、预算或状态代替它。S-CLEAN 按实际替换发生的位置处理，不设全仓清理需求或独立重构阶段。

## 2. 为什么这样做

现有成文链已经支持父子层级、多形式、来源标记、人工区保留，主要缺口在组织方法、送达及冲突指令。因此 A 复用结构能力，明确怎样生成可读成品；B 修正最早责任位置，不继续叠关键词门禁。

C 先用轻量脚本快速检查变化；完整无变化且无续办/新修订请求时报告并清理本次临时副本，有需要才由模型还原依据、解释变化、推演关系、处理裁决、修订和核对。现有 review 只改 Spec，不能覆盖用户手改、多源变化、旧版意见和既有 Plan；C 以模型工作方法承接，复用文件与流程能力，不把复杂场景展开成脚本分支或语义表单。

现有 worker 在首次目标处终止，finalize 只回流终态原名。T1 在已有等待与回流机制上增加两个检查点，满足用户明确的测试形态；T2 仍只有两个 Case，不把各需求都变成一轮新实跑。

## 3. 实施顺序：7 个可交回步骤

多个独立需求分别拆步，每个需求不超过三步；不把全部工作强行塞进四个大包。顺序保持用户“表达与缺陷先交付，update 随后”的决定。

| 顺序 | 步骤 | 输入 | 可检查交回 | 推进条件 |
|---|---|---|---|---|
| 1 | A1 成文组织与送达 | S-EXP、现有骨架/草稿/来源链 | 作者方法、源图规则、实际离线成文链、原功能保护 | 设计者按成品目标与实际 diff 评审 |
| 2 | B1 关键缺陷 | S-FIX、已确认两条知识定义、A1 | 五类责任修复及结构证据，不复制 A1 的图规则 | 对应缺陷有发现与恢复路径 |
| 3 | C1 识别变化与推演影响 | 当前请求、材料、决定、产物进展 | 模型方法和场景走查；真实输入送达、只读取材与完整保留 | 语义职责完整，取材/保留离线成立 |
| 4 | C2 关联修订与结果核对 | C1 解释、有效决定与保留项 | 相关真源/叙事/Plan 同步，未决与可继续范围明确；恢复可用 | 场景有修订与保持证据，旧能力不退化 |
| 5 | C3 统一入口与退场 | C2、四桥接、归档与适配边界 | update 可用；旧 review 全链退出；发布确认与失败重试 | 消费者、适配、回归与退出核对通过 |
| 5b | C4 update 输入阶段与预跑修正 | D21–D23、预跑评审 §4 | 输入阶段复用第一级关卡、判定范围八项、镜像排除报告、方法页三处 | 设计评审通过即启动正式 T2；见 [05-C4](05-C4-update输入阶段与预跑修正.md) |
| 7b | C5 发布前必改两项 | T2 正式结果评审 §5/§7 | 派审闭环实验与按结论改法、取代旧原件的措辞与提示、两句加强 | 交回评审通过即进发布；见 [06-C5](06-C5-发布前必改两项.md) |
| 6 | T1 双检查点装置 | C 的操作结束事实与模型结果说明、现有 runner | 同 session 续行、两份固定快照和另名回流的伪运行 | 不终止/不覆写/隔离及普通 Case 行为成立 |
| 7 | T2 两 Case 验收与发布 | 前六步交回、实际配置与预登记刺激 | 两初评、两后评、两组回流、用户审视和发布核对 | 用户启动测试；用户按结果裁定发布 |

一次实施当前步骤，交回实际输入生产者、处理位置、消费者、失败路径、diff 与离线结果，维护设计者复核后推进。A1/B1 可独立交回，不因此多跑一次真实 CLI。T1 代码可在 C 合同稳定后准备，但 T2 必须在前六步完成后开始。

## 4. 职责和权威来源

| 对象 | 拥有什么 | 不代替什么 |
|---|---|---|
| 用户与目标知识所有者 | 业务范围、冲突裁决、有效人签、回写确认、最终成品评价 | 不替实施者猜函数和代码行数 |
| 消费模型 | 来源理解、影响判断、表达、修改真源、解释依据 | 不将推荐或空框当人签 |
| Story 脚本 | 文件获取/比较/保留、结构、路由和操作事实 | 不按关键词/数量判内容完整 |
| Framework | 阶段、原生修正/重验、既有 verifier 调度与回执 | 不由 Extension 再造影子阶段状态 |
| 测试装置与维护者 | 隔离输入、快照、观测、离线回归和效果评测 | 不把测试答案或实现修法传给消费模型 |

需求事实维护在 spec；作者方法在 story-write；章节职责在合同；知识定义在知识文件；update 方法在 phases/update.md，脚本只管理文件操作合同；测试协议在 TEST。设计只说明改动与交接，实施时生产消费者都取得其真实输入，不把维护设计稿当运行时依赖。

## 5. 已核事实与边界

- 成文 H3/H4、多形式与正文不设骨架上限来自 writing-plan.mjs、chapter-contract.mjs；七项相关现有测试通过。它们只证明结构能力。
- review 专用旧流程见 rules/review_reflow.md，真实退出动作在 C3。历史文件可保留作原件，活跃消费者与双写路径退出。
- reopen/complete/story 的状态与冻结逻辑见 core/flow，C 在同一入口内增加更新上下文，不另开阶段引擎。
- Framework revalidate 按已有 summary 选已跑阶段，没有结束阶段参数；它不自动派审，但会生成适用的当前请求。C3 让主动 update 对实际改动阶段使用既有 verifier 审当前材料，再原生闭环；普通 correction 保持原路径。历史 PASS 复用不等于新稿已审，越出文档范围仍明确交接。
- runner 的 target_reached 后退出、finalize 终态限制与固定回流名已读源码；T1 先实施才能满足测试安排。
- 目标需求系统渲染和内网 adapter 未实测。沿已知 Markdown/图引用能力工作，增强载体先核目标；不新增默认 HTML/图片生成依赖。
- GitHub 技能正文、模板与公开示例已查，公开图片/HTML 的视觉核验尚未完成。见 [调查证据](参考/04-GitHub同类技能调查.md)，不得当成效果复现证明。

## 6. 新旧交接与预算

统一查看 [交接与预算](参考/03-职责交接与预算依据.md)。每项新增有消费者，被替换者同需求交付时退出；不能只搜旧名字，也不能因重复读同一文件就判存在多个真源。

预算按已核基线、具体工作单元、预计新增/退出与不确定项管理；初始额度在开工准备的有界检查后由设计评审核定。区间不是批准额度，过程峰值不是完成目标。按 test/story/AGENTS.md §5 处理超差，不靠削功能或逐包改分母换绿。

本任务开始已有两份 design-patterns、EVOLUTION 和 manifest 在途修改，保留。Framework 只读，目标已有知识/业务 adapters 的所有权保持。当前 manifest=1.9.3 是上版遗漏修复，T2 发布本版时才升 1.9.4。

## 7. 完成证据与交付边界

结构证据说明文件/协议/状态正确；语义结论来自真实来源与产物核对；行为效果来自两 Case 的实际过程和用户审视。链接检查、状态 completed、报告 PASS、示范好看都不能单独证明整个需求完成。

A/B/C 分别记录需求完成度，共同问题回其所有者，不拿总分相互抵消。T2 以“初次不终止、回流一次、同会话 update、后评再终止并 -update 回流”执行；异常分支主要由离线覆盖。

交付实施时当前设计只保留本文及四分册。参考目录保留同源示范、交接预算和调查证据；它们各承担明确用途，不再有另一份表达合同与正文互相补丁。
