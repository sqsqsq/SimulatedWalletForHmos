# S5：用户级要求补充与 maintenance-agent 实施

## 结果与输入

交付一个人工可直接调用的维护入口：理解当前 Agent 项目的目标与现状，审视用户级和项目级要求是否支持实际维护，定位设计、实现及维护材料中的问题，并形成完整修复计划。S1–S4 提供实际规则与项目入口。

调用只需 `$maintenance-agent`，无需先给问题描述。用户可补充关注点。交付结果是有证据的诊断和可实施计划；规则、代码和配置的修复由后续任务执行。

## 诊断能力与产出

以下能力共同完成一次维护诊断。每次调用都完整检查当前维护范围，不复用上次诊断结论。

| 诊断内容 | 依据与检查 | 应得到的结果 |
|---|---|---|
| 产品目标与当前方向 | 项目定位、现行能力、当前需求/方案及必要实现；比较目标、在建和已验证状态 | 项目正在解决什么，各项建设是否服务该目标；偏离或未知有具体依据 |
| 角色、职责与信息 | 用户和项目规约、消费入口、计划及可得行为记录 | 维护设计、实施、消费边界是否清楚；必要事实和约束是否在动作前可得 |
| 维护材料的内容归属与时效 | AGENTS/CLAUDE、项目说明、现行合同、TEST、STATUS 及直接引用；区分适用对象、读者和读取时机 | 确定责任来源及保留/修正位置；提出删除时核原句、相同适用对象的完整等义承接和读者在动作前可读到的路径，不能按同义概括上移 |
| 设计与实现的一致性 | 当前设计、相关实现、生产者/消费者、已有验证证据 | 职责与正常路径是否合理；是否有补偿分支、重复机制、未退出旧职责或未同步材料 |
| 交付和验证的充分性 | 有效计划、实施记录、验收方法与实际结果 | 计划能否直接实施，现有证据是否支撑完成结论，缺口在哪一层 |
| 整体修复设计 | 综合上述发现，比较原职责修正与必要替换 | 围绕目标组织的改动、保留和退出安排，具有依赖、输入输出及验收 |

用户级检查核实共同要求是否清楚、适用且与项目正确衔接；项目级检查保留领域事实和特殊边界。不能把“文件存在”或“内容一致”当作能力成立，也不能从材料推断不可观察的模型内心。

实施时读本步，创建时读 skill-creator 及 writing-for-agents。运行时读取用户级 AGENTS.md/CLAUDE.md 与实际项目入口，不读本实施计划或历史审计作为答案。

写入的语义如下，实施者可在不改变含义的前提下与原句合并：

- **交付规模**：需求方案通常拆为 1–4 个可独立验收的步骤。超过时先按交付目标审视边界，优先拆成范围清楚、依赖明确的多个需求；确实无法独立拆分时说明必要性，不为凑步数合并过大步骤或遗漏内容。多个独立目标用简短总览与步骤文档，交付前仍按输入、决定、动作和验收推演。
- **完整退场**：修复或实现需求时同时明确新增、保留、替换和删除。被替代或失效的旧机制及其专用测试随完整需求交付一并退出，包含相关入口、兼容分支、配置和文档引用；仍有效的业务能力及回归覆盖保留或迁移。分步实施中确需保留的过渡路径有明确消费者和退出条件，完成验收同时核新行为成立与旧路径退出。
- **适用性**：实施者依据真实契约及适用范围实现，样例、测试夹具和单次报错用于理解问题，不直接成为通用逻辑。特殊分支须有实际业务或协议依据；评审者检查实现及测试是否依赖样例名称、固定值或单一场景，并用适用范围内的其他合法输入或相关异常路径核实。有效协议常量、已确认业务规则及有界场景差异可保留，不为消除过拟合而过度泛化。

新增需求拆分的目标和范围变化按既有用户授权办理，不由实施者自行拆成用户未确认的新目标。1–4 步是以后制定方案的默认建议，不反向拆散本计划已完成的 S1–S4；后续仍只推进 S5、S6。没有替换对象的新增能力不制造删除项，正常回归测试也不因“旧”而全部删除。

## SKILL.md 的执行步骤

### 1. 确定当前对象，无需参数

调用后识别当前项目和用户级来源，明确这次诊断的对象及边界。用户附加的关注点优先调查，但不替代其余基础诊断。调用只授权相关读取和诊断产物写入，不授权修复、提交或正式 Case。

从 cwd 用 Git 找当前项目根；从已加载用户规则定位用户根。读项目入口、定位、当前状态和相关目录约定，确定维护对象与输出位置。项目初始材料包括用户共同要求、本项目目标与规约、现行设计和状态、相关验证入口。

根是应用入口而存在 Agent 子系统时，沿已有扩展/维护指针查找；缺少直接指针时，仅枚举当前根及 test、doc、docs 下的 AGENTS 候选，排除 fixtures/reports/归档，读标题与开头确定对象，再读选中入口。不要进入产品 Skill 的消费管线。

沿项目正常维护指针寻找资料和方案目录，不要求专用配置。没有唯一对象时先完成用户级可做的调查，只询问目标歧义；已有对象和目录时不追问角色、模式或问题描述。

明确不在 Git 仓时以 cwd 为项目根，Git 信息记为不适用；权限、信任或工具错误记为未取得及原因，不能据此判断没有仓库。完成本步须确定诊断对象、两级材料位置与输出路径，并记录可得的 Git 根和 HEAD 或缺失原因。没有目录约定时按用户规则提出具体路径并确认，其他调查可继续。

### 2. 取得本次诊断依据

先取得项目目标、正常使用过程、维护职责和当前工作状态的材料，再沿引用读取相关设计和实现。

每次完整检查维护范围：用户级规约、项目维护入口及其引用的规约、方案、状态和验证入口。对项目声明的交付目录，使用现有文件工具或结合 Git 已跟踪、未跟踪清单取得当前工作区文件清单，并补读本次相关的被忽略材料；按项目约定排除依赖缓存和生成物。仅列已跟踪文件不能代表当前交付内容；按职责和引用读取相关证据，不新增清单脚本或状态机制。

每个适用诊断内容都有本次结论；缺材料的项写明未知及所需证据。

### 3. 判断问题及修复方向

按上表完成适用判断，区分事实、推断与未知。每个问题给出具体证据、对目标的影响及最早责任位置；同一原因产生的多处表现合并分析。无可靠问题则说明检查范围和结论，不为凑修复项创造新机制。

将发现放回产品目标与维护过程判断：需要修正哪项责任或输入，各项调整如何共同改善结果，哪些现有能力仍应保持。用户例子用于解释原因，不直接生成永久规则。是否需要工具、状态或新抽象，依据当前真实缺口决定。

判断文档与实现漂移时，读取实际生产者、消费者和必要验证证据；不能只检查文档之间互相一致。取证材料写入计划证据。正式 Case 或需额外授权的验证先列明缺口，不由诊断调用自动运行。

每项删改建议注明原内容、适用对象和读者、具体承接位置及完整等义依据。用户级已有概括句不能替代项目产品合同，另一个文件出现相似文字也不能替代实际加载路径核查；承接不成立则保留原项目内容。

### 4. 形成后续实施安排

按项目已有约定建立或覆盖本地 `plan.md` 当前稿；多个独立实施结果使用 `steps/NN-主题.md`。设计文档不归档、不提交，不创建版本副本。

plan.md 先解释当前目标、实际问题和整体修复结果，再写决定、步骤及验收。开头写明检查范围、两级来源可得的 Git 根与 HEAD；非 Git 来源记为不适用，无法取得的版本信息注明原因，不猜测版本。诊断维度给简短结论和证据。

plan.md 的组织固定为“目标与事实 / 诊断结论及整体处理 / 实施步骤 / 验收与待决事项”。诊断结论包含各项能力的适用性、实际结论及证据；没有资料的项写清缺口。步骤表列结果、依赖、文件或分册及当前是否可实施。简单任务直接在本文件写步骤，不为四个标题另建四份材料。

计划把同一职责的修改和退出组织为完整步骤，不输出需要实施者再设计的建议清单。无修复项只保存简短结论。

每步提供必要背景、有效决定、文件动作、输入输出、依赖、保留/删除及验收。在步骤表用日常语言注明可实施或具体待决项，不设置 ready 字段。可实施不等于已获用户实施授权。

生成计划时遵循用户级交付规模与完整退场要求；诊断实现时核特殊分支的业务依据和适用范围，发现样例依赖需给具体代码/材料证据及受影响的其他合法情形。没有证据不能仅因实现具体就判过拟合。

若真实信息不足，能完成的步骤照常定案；受阻步骤标明缺口、决定者和影响。整体重写既有已采用方案时，遵守用户重写确认。

### 5. 检查和交付

核对引用、证据和计划是否可实施，写明尚待解决事项。

最终回复只给计划链接、重要发现和必要限制。诊断完成不等于实施完成。
