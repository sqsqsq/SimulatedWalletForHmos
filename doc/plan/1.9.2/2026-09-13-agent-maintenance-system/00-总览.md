# Agent 项目维护体系实施计划

## 实施目标

建立一套日常可用的维护方式：维护模型理解产品要解决的问题，依据清楚的职责和事实作出设计与改动；产品演进后，规约、实现和使用说明仍保持一致。本轮交付用户级工作要求、三个项目的维护依据，以及供人工调用的维护诊断能力。

这套方式服务于三个 Agent 产品的持续演进。评价结果是维护工作是否准确、完整、便于接续，及其是否改善产品使用效果；文件、工具和记录承担对应职责。

| 层次 | 提供什么 | 日常如何使用 |
|---|---|---|
| 用户级 | 跨项目的角色认知、判断方法、工作和交付要求 | 共同要求直接写入 AGENTS.md/CLAUDE.md；项目材料按任务读取 |
| 项目级 | 产品目标、当前能力、职责、事实来源、项目约束和维护入口 | 按当前任务取得相关依据，随对应改动同步 |
| 维护诊断 | 审视目标、维护依据与实际工作，定位问题并形成完整修复计划 | 调用 maintenance-agent；每次完整诊断 |

## 接手与交付

本计划覆盖需求背景、有效决定和实施安排。执行会话先取得用户的实施授权，再从 STATUS 的首个未完成步骤开始；不从本轮聊天或反思记录重新推导需求。

1. 以当前步骤声明的 Git 根为工作目录。跨仓命令显式用 `git -C <该根>`，相对路径均相对于该根，不能沿用方案存放仓的 cwd。
2. 只读本页、STATUS、当前步骤及该步骤具名材料；共享材料仍有效则复用。历史和其他项目按疑问再取。
3. 对照当前文件核实输入；保留已发生的新产品决定和其他任务修改。章节号是定位线索，实际以标题及职责匹配，不照旧行号删除。
4. 完成具名文件动作与本步验证，将结果写入 STATUS 对应步骤：实际改动、验证/未验证、剩余事项和证据路径；已有通过证据可引用，不再另写重复报告。
5. 前置结果满足才进入依赖步骤。若关键设计受新事实影响，明确受阻决定及影响；局部措辞、排版和不改变职责的实现选择由执行者完成。

S1–S5 的完成是各自交付物和本步检查完成；S6 汇总复用这些证据并补真实使用评价。设计已定与实施授权、部署完成与行为通过分别记录。

## 产物与所有权

| 产物 | 责任 |
|---|---|
| 用户级 AGENTS.md、CLAUDE.md | 直接承载通用工作和维护要求；AGENTS 的两个既有落点同步，不增加独立维护文件 |
| 三个项目原有规约、说明和状态文件 | 各自产品的事实、差异要求与当前维护依据 |
| `.agents/skills/maintenance-agent/SKILL.md` | 维护诊断与修复计划的工作步骤（Skill 主体）；Claude 只在 `.claude/skills/maintenance-agent/SKILL.md` 放跳板文件，经用户仓 `.gitignore` 白名单跟踪 |

用户级约束维护者如何工作，项目级完整说明产品、使用者和测试的实际合同。内容按责任来源维护，各入口按读者和使用时机提供必要要求；同义措辞不等于同一合同。摘要和视图可以保留，修改时核对来源一致性。

只有同一读者在对应动作前可取得完整等义内容，才删除该入口的重复句。不能用用户级的一条概括替代项目的消费输入、产品机制或验收义务。

## 长期规范与本次任务

AGENTS、CLAUDE、PROJECT 等长期规范说明产品目标、角色、事实来源与工作方法，不指定某次优化为所有会话的“当前轮次”，也不记录该轮的暂存材料和将来搬迁动作。具体需求、方案和实施状态由用户本次任务提供；未明确时根据任务目标定位已有材料，不按日期选最新方案。

现有状态页和任务索引可以记录工作现状，但不取得给所有新任务指定方案的权力。协议主清单、资产清单等持续维护的事实源可继续引用，不能因路径在 task 下就误删。迁移条件或架构取舍若仍有效，提炼为项目事实；单轮编号、进度与过程叙事留在对应工作记录，不能简单把绑定换一个文件藏起来。

用户级确定三类工作角色的边界，项目级分别说明这三类角色在本项目负责什么。“维护者”只作维护设计者和维护实施者的合称，不能替代逐角色分工。产品内部 author/verifier 等是消费系统能力，不另建一套与用户级冲突的项目角色数量定义。

本计划是特定任务的实施材料，可以给出准确文件、历史依据和在途基线；这些任务信息不复制进长期项目规范。

三层的交接关系是：用户级提供共同工作要求，项目级给出该任务的实际依据，maintenance-agent 使用这两层及相关证据生成新的实施安排。项目正常维护不以安装该 Skill 为前置，Skill 也不承担维护规约的唯一送达渠道。

## 实施范围

维护设计者、维护实施者和消费模型各有职责；会话协作工具与机制由用户选择，不纳入本计划。

Story 在 test/story 下原位修改项目级文件及 S4 具名的说明注释，根入口、工程结构、Framework、测试逻辑和预算数值保持。当前工作区变更作为实施输入保留，无需先提交。三个项目的有效产品约束、测试隔离和冻结事实均需保护。

用户级仓库为 `C:/Users/kangz`，三个项目各有 Git 根。各仓改动分别核对。maintenance-agent 零参数完整检查当前项目与用户级并生成方案，不执行修复、不做增量复用、不保存状态记录，不新增辅助脚本。实施、提交和正式测试按任务授权办理。
