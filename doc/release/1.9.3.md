# Story Extension 1.9.3 发布说明

> 2026-09-20 收口，机制版本 `1af7fdf7`。上一版见 [1.9.2](1.9.2.md)，本版在它之上做增量。
> 收口时两 Case 三轴分仍未达 90（建议分见文末），未闭的效果问题移交 1.9.4。

## 本版新增与优化

### 1. 会议是需求材料的一种，不再单独走一遍关卡

问料 → 交料（可以夹着会议转写）→ AI 读会与分析 → **只有会议里有要人定的话题时才停一次**，逐话题给推荐与选项 → 范围确认。
交料之后不再回头问一遍「材料是不是全部」。没有会议、或会上的事都定了，这一处就不出现。

### 2. 整条链只在一张表里停

停等点收在 `SKILL.md` 的一张真值表里：材料关卡（第一轮必停）、会议裁决（有待人定的话题才停）、范围关卡（含拆分追问）三处是本扩展新增的；交付门之后的选择、init 查无此单、归档与恢复是各自既有的确认点。门禁报错要不要修、下一步做什么，不是停等点。

### 3. verifier 回复之后不回头

verifier 判了阻断项才返修；没有阻断项就走完回执与交付门。闭环之后发现的真实问题走 framework 的修正入口（`--correction-init` 定责任层 → 改真源 → `--revalidate` 只重跑脚本门禁），**不重跑闭环链、不手动再派 verifier**；纯表达类提醒记进 `<phase>/notes.md`，交评审回流或下一轮。1.9.2 的「改完重新绑定审查对象」这句措辞随之退出——它被读成了「换一版再审一遍」，一份没怎么变的产物因此被审过五六遍。

### 4. 判断的那一刻拿到原义

知识判断骨架按命中条件、处置、附注分行给；评审动作类的条目落到评审议题（写 `decision: <议题 id>`）；verifier 的任务书把规约原文、契约义务、会议话题四栏、上游图与承接图并排摆出来，不再只给路径；决策登记要写「这件事该谁定」，选方案类的议题必须有建议段与理由。

### 5. 读法与门禁收成一处

扩展读 YAML 与 framework 同一个解析器；`resource_keys` 按「模块 → 分类 → 资源」两层合同读；各阶段 post_check 按组一次把能判的全判完，不再洋葱式一层层报；成文侧的围栏、标题、表与文档坐标只有一份解析；契约的流程常量（schema、关卡名、整体承载键）与语言红线词表都登记在章节合同里，脚本两侧都从它读。

### 6. 提示层按读者、时机、动作重排

20 份提示文件每份开头写明读者与时机；成文作业书按「起手输入 → 写给谁 → 写作设计 → 写一章 → 决策登记 → 回看 → 登记」的写章时机排，逐章重复的组织说明退场（那些问题与边界在章节合同里，草稿开头已经铺好）；写作单位从「一章」改成「一条完整的业务关系」——把它讲完整的那一章和需要重现它的章一起写或改；改章只有两条路：登记前在草稿上改、重提那一章，登记后先 `reopen`。

## 修复

- 章节合同里 19 个零读者说明键迁进 `contracts/README.md`，合同只留数据。
- 待写记号、上游文档路径、评审记录的表单腔词表由脚本字面改为读合同。
- hooks 侧自带的第二份找标题、切节、切列与围栏识别收进成文侧的同一份解析；plan 的设计模式选型表改为按列名读，不再按位置。
- spec / UT / 真机测试三处读验收桥接的集合名统一为 `criteria + boundaries`。
- 冻结之后重提章的报错说出唯一的出口 `reopen`。
- 度量脚本 `measure_run.py` 的「读判据源码」改为读取动词直接作用于该路径才计（执行脚本后管道截取不再误计），输出带算法版本与未分类数。

## 退出项

上游图承接判据独立成类、一图一行；离线「标题首词像编号」分支、图前承接句判据、verifier 报告「逐单元表」判据退出（交读者审查）；流程契约里 8 个零读者字段与常量（本轮并入名单、材料路径、范围来源、选项推荐标记、收口后变更记录、reopen 留痕、`--scope-text` 兜底、旧会议话题索引检测）退出；JS 侧与 Python 重复的 7 条契约判据退出；六个台账已退役的失效形态检查函数删除；14 个未使用的导入与几处孤立注释清理。

## 本版验证结果

四次真实 CLI 实跑（两次检查点、两次补跑/步骤 8 正式轮），最终版本 `1af7fdf7` 上跑了三次。

| | 第一轮（20260918-140014） | 第二轮（20260918-175714） |
|---|---|---|
| auto-topup（到 spec） | 自然闭环 | 90 / 72 / 86 |
| car-key-sharing（到 plan） | 宿主叫停于 plan 收尾前 | 84 / 80 / 80 |

三轴为产物结果 / 性能 / 知识应用，为建议分，用户人工审视为准。对照 1.9.2 第二轮（88/75/86、83/70/85）：产物与性能持平或略升，知识持平，仍无一轴稳定过 90。

按验收的六类比较单元两两比过两轮产物：
- **业务未决四次实跑零次被写成已定**（1.9.2 的首要缺陷，两轮各出现一次），其中一次是 verifier 抓到「撤销时限被写死」的阻断后返修改回未决；
- 决策集合两轮一一对应，规约适用判断 17 条里 14 条一致，图关系 4 组里 3 组一致；
- 会议交互合一两轮都成立；停等次数与真值表逐次一致；扩展脚本零崩溃、门禁零循环。

**没有达成的**：verifier 的审查补述要求逐话题各写一行，两轮都没照做（0/2）；「需求方明说手上有的材料要索取」五次里生效两次；「闭环后不回头」四次里一次没遵守（模型在 verifier 判通过后又去改两条提醒，多花约 18 分钟与两次审查）。上下文终值 474K–562K、单次实跑 59–85 分钟，与 1.9.2 持平，本版未以此为目标。

## 移交 1.9.4 的已知缺口

1. **规约命中条件的措辞**：`DLV-02`「对外开放页面或接口」、`COMPAT-02`「改动错误码」没有定义边界，两轮判断摇摆（这是知识内容问题，不是送达机制问题）。
2. **评审动作类议题被写成已定**：登记了 `decision` 之后，状态仍可由模型写成 settled，审查没拦。
3. **会议逐话题一行未生效**：任务书与输出要求都在，verifier 就是不按那个形态写。
4. 观察项：需求方材料索取不稳；闭环后回头改一次；承接图改画后丢了参与者与失败责任而审查判为完整；spec 章节编号重复（归 framework）；上下文与耗时未降；framework 七条缺口未变。

代码侧的残留清点（章节合同访问器、hooks 自研定位、待写记号双写等六项）见 `test/story/spec/1.9.4/2026-09-20-Extension残留清点与正向性复查/`；本文 1–3 与它不重叠，一并进 1.9.4。

## 规模

收口实测 11536 有效行（Python 2342 / MJS 3380 / hooks 3367 / prompts 1683 / data 764），相对 1.9.2 收口的 11878 净减 342。

完成目标在本版内被重签三次（10600 → 10860 → 11500 → 11536）：方案估算按原始行数与「一套一份」推，估净减 1015，实际只减 342；送达一侧估 +70、实际 +200 多。预算在 1.9.3 没有起到约束作用，责任在设计侧——应在步骤 1 交回时按现行计数口径重估，而不是逐步改签。这一条如实记在这里，供下一版定预算时参考。
