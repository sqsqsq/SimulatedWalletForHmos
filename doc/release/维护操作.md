# 维护操作

本页只维护 Framework 本地定制的实际文件、接入后的恢复与退出条件；维护环境准备、Framework 接入与 Extension 安装发布的步骤在
[根契约](../../AGENTS.md) §1、§6、§7。设计或评审本地宿主 / verifier 定制、接入 Framework 发布件时读本页；普通讨论、方案与实现评审无需加载。
测试、评分与过程取证只在 [TEST](../../test/TEST.md) 维护，本页不替代实跑或发布授权。

## 2. Framework 本地定制

- `demo/framework/` 是 AgentMaison 发布件；版本与 source_commit 读取 `demo/framework/RELEASE-MANIFEST.json`。正式交付落在上游，经 framework-init UPDATE
  进入消费仓；本仓副本只在用户明确授权的单步验证中临时修改，交付时保留上游基线、可复现补丁和临时放行的失效条件。
- 本仓对 framework 有三组本地定制，都不含逻辑改动，以一份补丁维护：[`test/fixtures/framework-local/3.1.0-dsh.patch`](../../test/fixtures/framework-local/3.1.0-dsh.patch)，
  相对 [`test/config/framework-under-test.json`](../../test/config/framework-under-test.json) 登记的固定发布树（Framework 3.1.0，main `900c508d`，tree `5a20d305`，source_commit `bd06421c`）。补丁共 19 个文件，按下面三组逐一列出。
  测试 template 装配时应用它，单测接的被测 Framework 也带它。demo 仍是上一发布版：它的 `framework/` 不含 dsh adapter，
  正式接入这一发布件时按根契约 §6 用同一补丁加回，不另维护第二份。
  - opencode：`agents/opencode/adapter.yaml` 的 `verifier_subagent: true` 与 `templates/agents/verifier.md` 子代理模板（物化为工程的 `.opencode/agent/verifier.md`；
    根 `.opencode/agent/verifier.md` 是维护装置的拷贝）。
  - dsh：整个 `agents/dsh/` adapter（含 `templates/rules/interaction-renderer.md`），加上 `skills/reference/confirmation-registry.yaml` 里的 dsh 选项。
    审查员模板 `templates/agents/framework-verifier.patch.yml` 物化为工程的 `.dsh/framework-verifier.patch.yml`，dsh 启动与续跑须带 `--patch` 装载它；
    同一配置层顶层关掉 DSH 的 goal 工具插件（`tool-goal`），维护范围只承接 interactive，Framework 名称里带 goal 的原生命令不受影响。
    `verifier_subagent` 设为 true 供原生派审，依据是已有的专用工具、空上下文与原运行证据，不等于这一组合已经验收；审查员 Preset 以 N 的
    Claude verifier 语义为底，保留物理 Feature 路径规则与合法产品 FAIL 诊断例外。
  - verifier 调用文字：本地定制涉及的调用指引统一为「调用当前宿主登记的专用 verifier 角色（Task 宿主显式选 verifier，原生 verifier 工具直接调用），
    不用通用研究/开发子 agent 顶替」。审查员入口分两种调用：阶段 request 照原生合同，扩展给的自足只读审查任务（Story 派审载体、阅读图验收）照任务回复，
    两种都只读、回复由调用方原样存盘。这组文字在 `agents/claude/templates/agents/verifier.md`（Codeagent 复用它）、`agents/opencode/templates/agents/verifier.md`
    与 dsh 的 `framework-verifier.patch.yml`；`agents/codex/templates/agents/verifier.toml` 是原生 `npm run sync:codex-agents` 按 Claude 源生成的结果，
    随补丁一起保存，改 Claude 源后重新生成、不手改，再跑一次 sync 应无差异。工具集合、权限与生成器不在这组定制里。补丁触及 `skills/reference/agents-entry-detail.md`、
    `skills/feature/{coding,plan,spec}/SKILL.md`、`skills/reference/{code-review,device-testing}-workflow-detail.md`、
    `harness-runner.ts` 与 `verifier-evidence.ts` 的调用提示、回执 `receipt-scaffold.ts` 与 `phase-completion-receipt.md` 的 `host_verifier_role`、
    `docs/operations/harness-runbook.md`。上游已提供同义指引时去掉这组差异：`900c508d` 起共享规则 `framework-agent-execution.mdc` §2 与
    `skills/reference/business-ut-workflow-detail.md` Step 8.2 改由共同协调器按实际签发的 request 运输独立审查，这两份保持上游原字节、不再带本地差异；原生 UT 方法页第 291 行仍有上游的 Task 传输措辞，属上游原文，不归这组定制。

  上游 `deepseek-harness` adapter（`ff111909` 起）声明 goal 能力、不声明专用 verifier、不物化独立审查员配置层，不能替代 `dsh`；三组定制照常保留（2.0.1 A02 重基，新增选项与 dsh 选项在确认登记表中并列）。
  它们不交上游，接入新发布件时按根契约 §6 重新加回。不随 story-adaptation 进目标仓：目标仓的宿主入口由它自己的 Framework 按扩展 manifest 物化。
- `demo/.opencode/` 是 OpenCode 测试装置，Case工作区按TEST从demo装配；当前宿主/模型组合以[测试配置](../../test/config/test.yaml)、[TEST §2.1](../../test/TEST.md#21-cli-配置组与单-case-故障重跑)及本轮授权命令为准，不从目录存在推断实际运行宿主。目标仓宿主由其实际配置决定。
