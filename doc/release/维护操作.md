# 维护操作

本页维护环境准备、Framework 接入与本地定制、Extension 安装发布的操作步骤；授权、所有权和预算以[根契约](../../AGENTS.md)为准。命令除显式切目录外从仓根执行。

| 当前任务 | 行动前读取 |
|---|---|
| 首次恢复维护环境 | §1，再按 TEST 选择实际需要的装置 |
| 设计或评审本地宿主/verifier定制 | §2；涉及接入顺序再读§3 |
| 接入 Framework 发布件 | §2—§3；版本和构建身份从发布件读取 |
| 安装测试模板 / 正式发布 Extension | §4；测试装配读 TEST，发布须已有用户决定 |

不涉及上述操作或定制的普通讨论、方案和实现评审无需加载本页；涉及哪项就读对应章节。测试、评分与过程取证仍只在[TEST](../../test/TEST.md)维护；本页不替代实跑/发布授权。

## 1. 维护环境准备

依赖目录不入库。新checkout先核本次任务缺什么，按下表恢复需要的部分，不因准备环境默认安装全部宿主或鸿蒙工具（PowerShell，从仓根执行）：

| 本次用途 | 所需依赖 |
|---|---|
| 维护Python脚本与测试 | pytest、pytest-xdist、pyyaml |
| Framework harness门禁、渲染及相关测试 | demo/framework/harness 的npm依赖 |
| OpenCode宿主实跑 | demo/.opencode 的插件 |
| demo鸿蒙模块依赖、构建或设备验证 | DevEco自带node/ohpm及模块依赖 |

```powershell
python -m pip install pytest pytest-xdist pyyaml                     # Python维护需要时
cd demo/framework/harness; npm install; cd ../../..                  # harness需要时
cd demo/.opencode; npm install @opencode-ai/plugin@1.18.26; cd ../..  # OpenCode需要时；package.json由它生成、不入库
# 以下仅用于鸿蒙模块依赖、构建或设备验证：
$env:OHPM_EXE = "<DevEco>\tools\ohpm\bin\ohpm.bat"                    # 鸿蒙依赖用本机 DevEco 自带的 ohpm 与 node
$env:DEVECO_NODE = "<DevEco>\tools\node\node.exe"
demo/scripts/build-dependence.ps1                                     # 重建 demo 各模块的 oh_modules
```

`package-lock.json` 不入库，harness 的依赖会解析到各自版本范围内的最新补丁版。人手试用 `/story` 还要装本地需求系统，见 TEST §1.3。

## 2. Framework 本地定制

- `demo/framework/` 是 AgentMaison 发布件；版本与 source_commit 读取 `demo/framework/RELEASE-MANIFEST.json`。正式交付落在上游，经 framework-init UPDATE
  进入消费仓；本仓副本只在用户明确授权的单步验证中临时修改，交付时保留上游基线、可复现补丁和临时放行的失效条件。
- 本仓对 framework 有三组本地定制，都不含逻辑改动：
  - opencode：`demo/framework/agents/opencode/adapter.yaml` 的 `verifier_subagent` 登记与 `templates/agents/verifier.md` 子代理模板
    （物化为 `demo/.opencode/agent/verifier.md`，根 `.opencode/agent/verifier.md` 是维护装置的拷贝）。
  - dsh：`demo/framework/agents/dsh/` 整个 adapter，加上 `skills/reference/confirmation-registry.yaml` 里的 dsh 选项。
    审查员模板 `templates/agents/framework-verifier.patch.yml` 由 opencode 子代理正文生成，物化为 `demo/.dsh/framework-verifier.patch.yml`，
    dsh 启动与续跑须带 `--patch` 装载它。能力声明以当前 adapter 为准；未取得对应宿主实跑证据前，`verifier_subagent` 保持 false，不因文档声明签可用。
  - verifier 调用文字：作者读到的调用指引统一为「调用当前宿主登记的专用 verifier 角色（Task 宿主显式选 verifier，原生 verifier 工具直接调用），不用通用研究/开发子 agent 顶替」。涉及 `templates/AGENTS.md.template`（及渲染出的 demo `AGENTS.md`、`CLAUDE.md`）、`skills/reference/agents-entry-detail.md`、共享规则 `framework-agent-execution.mdc`（及 `.agents/.codex/.cursor/.opencode` 下的已装副本）、六个阶段 SKILL 的 AI Harness 段、`harness-runner.ts` 与 `verifier-evidence.ts` 的调用提示、回执的静态 `invoked_via`。上游已提供同义指引时去掉这组差异。

  它们不交上游，接入新发布件时按本文§3 重新加回；不随 story-adaptation 进目标仓，进目标仓的只有 manifest `provides.bridges` 登记的入口。
- `demo/.opencode/` 是 OpenCode 测试装置，Case工作区按TEST从demo装配；当前宿主/模型组合以[测试配置](../../test/config/test.yaml)、[TEST §2.1](../../test/TEST.md#21-cli-配置组与单-case-故障重跑)及本轮授权命令为准，不从目录存在推断实际运行宿主。目标仓宿主由其实际配置决定。

## 3. Framework 接入

输入是 Maison 的已验证发布件（zip），版本与构建身份看其中 `framework/RELEASE-MANIFEST.json`。
`python test/scripts/check_framework_drift.py` 比较 main 与 demo 接入的版本：退出 0 相同，1 不同，2 读取失败。

1. demo 先干净：`git status --porcelain -- demo` 为空。
2. 把发布件解压到 demo 根，替换 `demo/framework/`；用 `git diff --stat -- demo/framework` 核改动面与发布件的 `MIGRATION.md` 相符。
3. 三组本地定制（本文§2）被发布件覆盖时，在新文件上重新加回定制内容，不整文件回退到旧版；上游已带同义内容的那组不再加回。
4. 在 demo 根按 [framework-init](../../demo/framework/skills/project/framework-init/SKILL.md) 做 UPDATE（S1–S4），物化清单按本轮实际选择。
5. 用 demo 已装版本的 manifest 判断 diff 里的入口是否属于 Extension；已登记入口或 AGENTS/CLAUDE 的 story-ext 扩展段被换成通用内容时，
   只把该文件恢复为已装版本的内容，不重装 Extension（方案 1.9.8 分册 03 §2.2）。
6. 装置同步：根 `.opencode/agent/verifier.md` 逐字节复制自 `demo/.opencode/agent/verifier.md`。
7. 验证：demo 下 `cd framework/harness && npm test`；`check_framework_drift.py` 结果与本次接入一致；按 [TEST §5](../../test/TEST.md) 跑与改动相关的离线回归。
8. 提交 demo，并在 [test/EVOLUTION.md](../../test/EVOLUTION.md) 登记发布件版本、source_commit、定制处理与验证结果。

失败时用 git 核对并仅还原本次 demo 改动，保护其他在途内容；framework 自身的缺陷报回上游。

## 4. Extension 安装与发布

同一个安装函数 `test/scripts/publish_to_demo.py` 服务两种目标，顺序固定：整体替换目标 `doc/extensions` → 按 manifest `provides.bridges`
的「目标位置 / 来源」对写宿主入口 → 更新 AGENTS.md / CLAUDE.md 的 story-ext 扩展段（区外不动）。

- **测试**：只装一次性 template，由 `run_multi_case.py` 按 TEST §1.2 装配，离线检查用的 template 按 TEST §5 现建。测试不写 demo；
  需求产物回流到维护仓 `doc/features/`。
- **版本号**：新版本第一次改动 `extensions/` 的提交就把 `manifest.yaml` 的 `version` 升到新版本号。
- **正式发布**：前置是用户已决定发布本版本、demo 干净。

  ```powershell
  python test/scripts/publish_to_demo.py --source extensions --target demo --dry-run   # 看计划
  python test/scripts/publish_to_demo.py --source extensions --target demo             # 退出 0 = 已安装
  ```

  验证 `git status -- demo` 的改动只在 `demo/doc/extensions/`、manifest 登记的入口和两份入口文件的扩展段，再核 demo 扩展与开发源同源（打印 `True`）：

  ```powershell
  python -c @"
  import sys
  from pathlib import Path
  sys.path.insert(0, 'test/scripts')
  import publish_to_demo as p
  src, dst = Path('extensions'), Path('demo/doc/extensions')
  files = p.enumerate_source(src)
  print(files == p.enumerate_source(dst) and all((src / f).read_bytes() == (dst / f).read_bytes() for f in files))
  "@
  ```

  然后跑 `python test/scripts/check_failure_modes.py`（缺省检查 demo）。发布提交带上 demo、`doc/release/<版本>.md` 与更新后的
  [README](../../README.md)，并在 EVOLUTION 登记。提交前核：本版增量里使用者可见的每项变化都已反映在 README 的当前描述里
  （命令、能力、产物、入口、安装），与发布版本一致；README 只写当前状态，版本变化只写在本版发布说明。
- **失败**：退出 2 是输入读取或 git 前置不成立，目标没写；退出 1 是写入中途失败，结果 JSON 列出实际完成项。用 git 核对并仅还原本次 demo 改动，
  修好后从同一源重装。
- **对外升级**：其他仓的安装与升级用 demo 里已装的发布版 adapt（`demo/doc/extensions/skills/story-adaptation/`）。
