## 1. 用户反馈与问题

用户指出，当前蓝图缺少完整、人可读的需求级 `blueprint.md`；用户已向蓝图开发者反馈，开发者此前遗漏，正在修改。进一步讨论中，开发者表示新版将吸收现有 `story.md` 的很多成文内容，使蓝图同时服务机器和人阅读。

以上是用户转述的上游变更方向。新版产物、结构、权威及扩展合同尚未取得，不能据此认定能力已经交付。当前仓内确有 `component-blueprint.review.md` 的确定性评审投影；已有 Markdown 投影不等于用户所要求的完整需求级文档。现行接口见 [component-design 的评审投影与反馈](../../../demo/framework/skills/project/component-design/SKILL.md)。

用户关心三项问题：

1. 1.x 中 Spec 面向需求和消费模型，Story 面向人；Extension 有独立叙述逻辑，将知识带入 Spec/Plan，并将 Spec 内容投影到 Story。总体上是在 Framework 输出基础上增强。新版是否会将 Extension 收窄为 Framework 的材料提供方？
2. 蓝图吸收 Story 的部分功能是有价值的，但两者应合并，还是保持各自的阅读职责？
3. 如果扩展主要按宿主扩展块进入 `blueprint.md`，现有能力与后续优化是否难以实现，或破坏整篇人读叙事的自洽性？

用户同时指出：1.x Spec/Story 确有重复，主要用于解决人和机器阅读方式不同的问题；不能仅为维持历史结构而拒绝蓝图吸收通用能力。

## 2. 已核现状与解释边界

当前讨论时仓内 Framework 发布件为 3.1.0，身份见 [RELEASE-MANIFEST](../../../demo/framework/RELEASE-MANIFEST.json)；它不是待取得的新版 `blueprint.md` 发布件。

Extension 当前已经参与蓝图设计输入：知识要求在设计前送达，知识判断及精确专项内容进入蓝图；Story 随后依据已准入蓝图独立完成写作设计、逐章表达、审查和交付。因此当前关系也包含 Extension 向 Framework 提供设计要求，不能只概括为单向下游增强。依据见 [蓝图作者要求](../../../extensions/hooks/blueprint/author.md)与 [设计、成文及交付流程](../../../extensions/skills/story/phases/design.md)。

Story 的现行读者是第一次接触需求的产品、开发负责人和测试人员；他们不看代码、不翻仓库，单凭成品判断业务是否想清楚、能否开工及怎样验收。其表达合同要求按人的理解顺序组织，不能仅搬运规格章节和表格。依据见 [Story 成文合同](../../../extensions/skills/story/phases/story-write.md)。

本次没有取得新版合同，没有验证新版人读效果，也没有做同输入、同模型的合并与独立成文对照。以下为待后续验证的设计建议。

## 3. 讨论建议：按阅读任务划职责

维护设计者建议支持蓝图补齐人读设计，但现阶段保留 Story 独立交付职责；取得新版后按实际能力决定是否合并。用户本次授权记录讨论，尚未单独确认这项建议为最终架构。

蓝图人读说明首先应支持整体设计评审：方案是什么、为何这样设计、对象和责任怎样划分、契约及约束是什么、哪些决定尚未成立。Story 则支持业务评审者沿完整业务和用户过程理解行为、限制、异常、验收与交付。两者都可给人读，但阅读任务未必相同。

同一事实在不同视图重复呈现可以有必要；重复作决定、维护相互独立的事实才是主要风险。不能仅按文件数量、文字重叠或“人/机器”二分法判断合并。

例如提交后结果未知：设计说明需讲清状态、结果权威、查询及重试责任与未决约束；业务叙事需讲清用户看到什么、能做什么、怎样获得结果及哪些结果不能承诺。具体内容来自同一有效设计，表达顺序由阅读任务决定。

待比较的职责安排为：蓝图负责完整需求级设计与设计说明；Story 负责面向其目标读者的完整叙事和交付；CU Spec/Plan 负责共同设计下的施工细化。蓝图不能把必要的整体设计缺口留给 Story，Story 不能自行改变共同设计来补缺。

成文发现遗漏或矛盾时，由拥有设计职责的位置修订真源并同步下游；仅调整叙述顺序、图表和措辞时，由成文职责处理。文字解释的深化与业务决定变化必须区分。

## 4. Extension 可扩展性的关键风险

Extension 位于上游或下游不是主要判据。关键在于它对所承担结果是否拥有必要的组织权，以及 Framework 是否有明确承担者整合全文。

如果 Framework 决定整体叙事，Extension 只能向固定章节填内容，却仍承担人读质量责任，就形成责任与控制范围不匹配。各扩展块分别正确，整篇仍可能重复、顺序混乱、术语不一致或遗漏跨章节关系。

“支持宿主扩展”或“允许插入 Markdown”不足以证明完整叙事能力成立。须核扩展能否影响整体写作设计、章节关系与读者目标；最终由谁组织全文，审查是否覆盖整合后的完整产物。具体实现机制待新版合同核实，不预设必须增加新的扩展平台。

| 能力 | 新版适配须解决的问题 |
|---|---|
| 知识应用、接口与精确约束 | 内容是否进入有效设计、绑定承担对象并传给 CU，还是仅出现在说明文字里 |
| 页面交互、复杂异常与恢复叙事 | 是否能按业务重组分节及讲述顺序，完整连接前置、行为与结果 |
| SVG、材料图与资源交付 | 选型、正文引用、视觉审查、资源附件及归档是否形成完整链 |
| Review 与人工裁决 | 意见、事实、建议和授权决定如何区分并回灌，谁负责决定 |
| update、原件保护与审查收敛 | 版本身份、历史保持、影响面同步及独立审查如何持续有效 |

上述是能力保持和接口评估问题，不表示 2.1.0 的对应新增需求已在本版获实施授权。

## 5. 合并条件与权威关系

合并可作为实际能力接替后的结果，不先定为减少文件的目标。若新版 `blueprint.md` 能完整支持 Story 的目标读者，并承接知识效果、图形资源、验收、Review、归档与更新职责，合并可能减少重复成文及一致性维护。

合并时必须明确职责交给谁，旧 Story 的生产、检查、状态和专用入口如何退出；有效业务能力与回归覆盖保留或迁移。只搬部分章节，同时保留两套完整写作与审查路径，可能增加成本。保留独立 Story 时也须说明它新增的阅读价值及同步成本，不以历史存在为理由。

新版须定案结构化蓝图与 `blueprint.md` 的关系：哪些内容在哪里编辑；哪份载体对什么事实有权威；人读稿发现错误回哪里修；表达修改是否改变设计 revision；修订后机器与人读视图怎样保持一致。单一真源不要求一份文件，但同一决定不能有两份可独立变更的权威。

建议向蓝图开发者说明的合作目标是：补齐可独立评审的需求级整体设计，吸收通用表达能力；同时明确整体叙事责任、扩展控制范围及既有交付职责的接替。在实际接替得到验证前，保留有效的 Story 交付能力。

## 6. 后续设计与验收要求

取得正式发布件后，先核以下关键未知，再定合并或独立方案：

- 新版 `blueprint.md` 的目标读者、覆盖范围、写作及审查责任。
- YAML/Markdown 的内容权威、修订、引用和下游消费合同。
- Extension 输入在设计及成文之前如何送达，是否能支持整篇叙事的组织要求。
- 已有知识、Review、归档、update、图片及资源能力的真实接替位置。
- 直接 Framework 入口与 Story 入口是否同样消费必要要求，失败和能力不足如何恢复。

验收分别核以下结果，不由一个格式检查或最终 pass 代签：

| 验收对象 | 可检查结果 |
|---|---|
| 需求级设计 | 真实来源与知识形成完整设计决定、关系、约束及未决边界，必要共同决定不推给 CU |
| 人读效果 | 未参与设计的目标评审者只读拟交付文档，能理解完整业务、识别未决条件并制定验收 |
| 机器消费 | 同版本有效设计进入 CU，准确承接共同义务与角色，Spec/Plan 能据此完成施工细化 |
| 扩展整合 | 合法的不同需求及新增内容进入后，整篇仍保持顺序、术语和业务关系一致，不局限于固定样例 |
| 独立审查与恢复 | 核实际输入、派审、原件、发现与修复；能力不足明确处理，有效 warn 的处置不演化为无收益循环 |
| 生命周期与退出 | 变更、裁决、更新、归档及恢复保持一致；被接替职责的旧消费者、状态与入口真实退出 |
| 成本 | 在可比输入与运行条件下核成文、读取、审查和维护成本；未取得证据时不宣称合并提效 |

结构检查证明文件、引用与合同可读；模型语义审查及实际使用证据证明理解和行为。方案比较可以先做，但真实 CLI、金样正式切换与发布仍按项目授权执行。最终架构及版本承接由用户依据核实后的方案确认。
