## 1. 产品目标与实施主线

Extension 服务需求材料、澄清、人签、知识、完整人读交付、反馈和更新；Framework 承担蓝图设计权威、CU 施工单位、阶段及整体闭环。Story 仍是一项需求的一套说明，知识仍须完成看到、理解、应用、传递。

产品主路径：材料/范围确认 → component-design 到蓝图准入 → Story/Review 与独立人读审查 → 按已有授权继续完整设计交接或实现。默认送审允许零 CU，不要求先产生 Spec/Plan；多个 CU 不增加业务建单或重复 Story。

维护实施顺序与上述用户流程不同：

1. 确认并接入 Framework 3.1 到本仓 main，核实际发布身份与原生能力。
2. 将这个明确 main 提交的 Framework 同步到 story/demo，完成该消费工程的配置与入口更新。
3. 依据实际接入件适配根 extensions；优先使用已有能力，真实局部缺口由设计者裁定最小修正及其影响范围。
4. 复制 demo、安装开发 Extension 做隔离验证，验收后将 Extension 2.0.0 发布安装进 demo。

范围承接 1.9.8 有效业务能力，含系统/本地单、图片/会议、人工 Review、三类知识、更新/归档/恢复、续行及跨仓适配。运行选择 interactive，不创建 Goal run；跨部件自动协调和新增 Demo 业务不在本版。实际 3.1 的 design lens 支持范围需核对，现有源码观察仅有 hmos-app。

## 4. 词义及边界

| 对象 | 含义 |
|---|---|
| 需求 | 业务目标、范围及交付责任的单位 |
| 需求依据 | 原件、采用版本及真实人工决定；派生分析保留其派生身份 |
| 蓝图 | 部件一次演进的权威设计，有自身身份、revision 和准入结果 |
| CU | Framework 的施工单位，引用其承担的设计对象 |
| Story / Review | 完整人读说明 / 真实人工议题与表态 |
| 交付 | 分别说明人读文档、设计交接、实施、外部发布的完成状态 |
| 恢复 | 明确恢复自有工作件、外部发布或设计意图，各走所属责任 |

需求与蓝图允许显式不同名，一项需求关联一个部件的一次蓝图演进；本版不建设任意多对多登记平台。知识归目标工程维护；适配脚本按目录所有权安装，知识内容由模型依据目标事实适配。

## 5. 接缝、审核与完成

A/B/C/D 分别指设计知识送达、独立人读审查、施工知识承接和安装保护四项接缝。它们是需要证明的协作结果，不是四项已经批准的 Framework 新功能。先核实际 3.1 已有能力，必要时只修其真实缺口；任何一项未闭合都不能被虚报通过，但也不阻止不依赖它的工作。

四步计划分段交回，Framework 基线同步可先独立验收。设计者负责基于实际接入件锁定接口及必要修正，实施者按闭合合同执行；真实 CLI 按用户里程碑授权，上限仍为 Plan。Coding、设备、内网及整体施工没有真实证据时单列未验证。

版本完成须实现对应产品能力、保留目标知识与人工工作、退出旧机制、完成授权验证并准确发布。main 已升级、源码可读、文档可链接或局部 schema 通过，都不单独构成 Story 2.0 完成。
