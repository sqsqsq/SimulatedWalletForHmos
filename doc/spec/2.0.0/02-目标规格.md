# Story 2.0.0 目标规格

依据[完整特性树](01-完整特性树.md)。本页定义接入 Framework 3.1 后的产品行为；先按本仓 main→story 路径完成实际版本接入，字段、脚本入口和接缝核对见[实施总览](../../plan/2.0.0/01-实施总览与协作合同.md)。

## 1. 职责和两种入口

Extension 对真实需求输入、人工决定、人读表达、知识应用要求和外部交付负责；Framework 对蓝图、CU、施工输入、阶段与整体完成负责。模型分析语义、适用性和影响，脚本执行路径解析、获取、摘要、校验和确定性投影。

需求入口组织材料、设计、Story/Review 及后续更新。直接 Framework 入口只取得当前动作所需知识，不创建 Story 记录。两条路径使用同一目标激活清单、知识原文和应用判据。

| 信息 | 权威及消费者 |
|---|---|
| 原始需求与图片 | 实际来源及采用版本；理解者、设计者、成文者和审查者读取 |
| 范围、人签和评审原话 | 实际有权决定的人及原记录；双方按对象与版本消费 |
| 知识 | 目标工程维护的事实、规约、模式；当前执行者在有关决定前读取 |
| 整体设计 | Framework 的有效蓝图；Story 展示、CU 引用 |
| 施工细化和完成证据 | 原生契约、验收与阶段结果；Extension 只读解释 |
| Story 表达 | Extension 的人读工作件；设计事实保持蓝图来源 |
| 外部发布 | 远端实际结果及本地发布记录；重试和恢复核对 |

## 2. 材料、设计和交付终点

模型盘点正文、表格、图、会议及补料，保留原件和转换关系；缺席、读取失败、无法比较分别报告。每轮均完成材料关卡；必要会议待决请人裁决；业务范围由人确认，CU 拆分不改变业务分单。

模型提出本轮采用集合及提取分析，脚本核对确认版本，导出真实人签并冻结本次设计引用的文件和必要图片。原始 AR/design.md 保持，提取稿标为派生分析。系统来源走原生 materialization，本地来源交冻结的项目内文件；两者均保留来源、原始字节摘要和真实权威。缺权威回实际责任人，不由脚本猜测。

Framework 在收到来源后完成发现、设计、独立质询和准入。知识在相关决定前到达作者和质询方；当前设计的必要事实与权限缺口在准入前解决。仅查看、重入或表达修改不产生设计 revision。

| 请求 | 完成条件及停止点 |
|---|---|
| 取材、状态、局部解释 | 完成本次明确请求，不自动创建设计或施工 |
| 默认 Story / 送审 | 蓝图已准入、有效投影、一套 Story/Review、结构检查及适用独立审查；零 CU 合法 |
| 完整设计交接 | 上述人读结果，加原生 CU、design_refs 与 readiness；不启动施工 |
| 完整实现 | 已授权范围内完成设计准备、交互式原生开发与必要整体闭环 |
| update | 同步本轮受影响的已有结果及必要审查，说明后续责任；不推断新施工授权 |

交付选择为送审、完整设计交接、完整实现或暂不推进。系统单可按授权归档或先归档再继续，本地单只有本地交付。已有适用授权直接使用；业务审批与普通实施授权分开。

完整实现由 Framework 原生交互路径承担。主模型交付请求终点、请求结果、明确动作及有来源的影响判断，由原生 prepare-scope 解析并在首个阶段调用时冻结范围；按有效输入及原生结果继续，不强制新跑可复用的 Spec/Plan。Extension 不创建 Goal run，不维护 next-phase 表或 CU 调度状态。需要人的事实、范围和权限时停在对应决定。

## 3. 人读表达与人工评审

Story 结合原始需求、有效人工决定和指定 revision 的蓝图，讲清背景、术语、边界、参与方、场景、流程、异常、取舍、非功能、验收、交付及精确依据。沿用十章职责和可靠章节提交，允许有据分节、深化关系和专项说明。

技术附录从已校验的 canonical 对象派生；原生投影保持原样，正文由模型组织。已形成的接口、数据策略、配置、事件和知识要求不得在改写中丢失；尚待施工形成的细节明确交给相应阶段。Story 不依赖 Plan，退出 Spec 固定章号来源。

Review 呈现真正有后果的议题、依据、选项和人的填写位。人工区保护、原话、版本和议题含义共同决定表态是否仍适用；编号相同不代表可以沿用。模型建议、会议讨论和默认推荐不写成人签。

结构检查核来源、对象和精确投影；独立审查核遗漏、矛盾、编造、表达及知识效果。报告必须对应当前被审对象；无审查能力沿既有授权如实披露，坏报告和缺报告不得伪装成无能力。非阻断建议记录后交付，真实阻断回最早责任处修正；不以固定返修次数代替结果。

## 4. 知识链

目标激活清单保持唯一，四种形态维持 facts×facets、facts×halves、constraints×entries、patterns×halves。明确空集合合法，登记损坏报错；知识单位来自解析结果，不按名称猜适用性。方法型事实按整篇知识单位登记使用依据，上下篇在相关决定前完整可取，章节锚点只用于回查。

项目事实的使用依据进入蓝图 discovery facts；约束判断与模式选择进入 decisions。模型有据判断、人的权威裁决和未决使用各自真实原生状态。规约逐条判断，模式按需求提出候选与选择理由；阶段性要求在相应动作前落实，不为追求全表已定而提前杜撰施工细节。

适用要求必须改变真实设计对象、角色、契约实体或验证责任。CU 引用实际承担的对象和决定，共享义务由共同设计承载，组合责任经原生关系、流和闭环证据表达。文件授权仍用原生字符串清单，文件级知识职责使用实际原生合法实体承载，具体位置由设计者按接入件核定，协议见步骤 3；同一决定只在蓝图成立一次。

后续作者和审查者取得有效决定、必要原文及本次施工契约。复用输入、不新生成 Spec/Plan、没有 Story 的直接入口均须保持知识承接。Coding、Review、UT、Testing 分别提供行为、角色与证据；缺设备或组合证据如实保留缺口。

## 5. 更新、反馈与恢复

用户请求或实际材料、人工决定、知识、设计变化均可引发 update。脚本给出比较事实，模型理解影响；无变化、缺比较依据、已有更新待续和来源故障分别处理。

| 变化 | 责任动作 |
|---|---|
| 表达 | 改自有人读件并检查，保持设计 revision |
| 需求或范围 | 人确认新的有效输入，形成新设计输入版本 |
| 设计意见 | 按原生四类反馈交候选，资格与接受分别读取 |
| 设计已修订 | 读取当前设计及下游有效性，同步人读件 |
| 人直接改派生内容 | 先保护、理解意图，再交有权修改的来源 |

设计反馈绑定真实 revision 和目标；无技术目标的业务意见留在需求侧。旧反馈由裁决方确认新版本适用性，不能只换 revision 重投。Extension 不批量改 CU、回执或完成事实。

本地恢复只覆盖声明的自有可编辑集合，逐文件比较开轮前、最后已完成写入及当前字节；后来人工修改与不明中间稿保留并报告冲突。原始材料、真实人签历史、已引用冻结输入、审查历史、发布记录及 Framework 文件受保护。恢复表达后若设计已变，显示待同步；撤销设计意图走原生修订。

close 在本轮输入已处理、人读件已同步、必要审查成立、人签已留存且无恢复冲突时成立。仅资料更新且尚未形成 Story 时可在该明确终点收口，不为关记录强制补设计和人读件。施工结果只读说明，不作为文档收口的额外条件。

归档发布前展示当前版本、差异、未决及验证缺口；失败保留本地结果，重试核远端新修改。远程恢复只处理授权外部对象，不代表撤销本地设计或代码。本地单不调用远端。

## 6. 安装与验收

开发源、发布 demo、隔离 template 沿用 1.9.8 所有权。对外 adapt 从已发布的消费副本执行，保留目标知识、身份及按来源归属的对接层。机制升级按新格式运行，旧在途单在 1.x 收口或在 2.0.0 重起；知识形态及内容由 adapt 的模型步骤处理。

宿主入口交 Framework 原生物化。完整入口的覆盖保护须成立，不能因机制安装而抹去工程人工内容；实际接入件的原生能力不足时，由设计者提出最小修正并只标明受影响操作。清晰的预检失败保持零写入，写入失败列完成面和未完成面，维护发布按 Git 恢复，template 重建。

验收逐项覆盖完整特性树及合法异常，包含单/多 CU、零 CU、直接入口和输入复用。静态及结构证据只证明确定事实；实际信息送达、业务完整性及知识应用由正常需求的独立语义审查和授权实跑判断。
