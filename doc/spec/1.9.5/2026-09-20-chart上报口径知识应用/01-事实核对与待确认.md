1.9.4 最新 T1 返修/T2 准备评审记录为 T1 收口、待用户启动 T2；工作区仍有预算/运行器/度量脚本修改。1.9.5 可以澄清，但模板和知识消费的实现基线应以 1.9.4 最终交付为准；“与 1.9.4/2.0.1 并行不冲突”未得到验证或授权。

## 3. 原稿中不直接采纳的判断

- G1 的“直接根因”改为已发现的内容缺口；完整归因需要真实失败产物及其输入/送达证据。
- “四要素都进 facts”需按事实/规范区分：真实 API、类型和登记位置属工程事实；应如何设计统计、何时必须上报、哪些结果计入统计属项目规则。具体文件组织由设计负责，不让用户选知识分类。
- “新增场景/分支就必须扩错误码”过强：先核是否新增了需要区分的语义，能否复用有效编码，避免为每个代码分支造新码。
- “独立子章节=新增通用固定槽位”是实现推断。用户需要的可读效果与具体生成方式要分开，钱包规则保持在知识层。
- Q8“OBS-01/02/03 全保留”是 GLM 意见；不能用一次评分或缺少对照实验否决用户对规约必要性的讨论，也不因模型会打日志就直接删除项目特有义务。
- Q2/Q7 未回答时按 GLM 默认，不成立。未确认的选择继续待决，不视为用户同意。
- Q6“排版”措辞不准确，其实是版本归属和排期；排期不属于本轮自动获得的授权。

## 4. 本轮澄清主题及后续设计边界

核心业务选择已在 §5 收齐并进入需求正文 D01–D14。下表说明本次澄清解决什么，以及剩余哪些内容由设计取证细化，不表示用户还需逐项重答。

| 主题 | 要确定什么 | 为什么需要 |
|---|---|---|
| 核心交付 | 正确指标方案→文档→实现→验证，还是只做其中一段 | 避免“知识补了”就算业务结果完成 |
| 权威来源 | 真实钱包规范、本仓实现，或先以用户规则为准再核对应 | 避免拿 Demo 现状冒充目标要求 |
| 文档效果 | 涉及需求有独立小节，还是每个需求固定留位；各文档读者的内容分工 | 确认效果，不替用户批准模板机制 |
| 指标适用 | 哪些需求必须评估成功率/性能/占比；已有统计受影响是否同等覆盖 | “新业务大概率涉及”不是可判断的边界 |
| 内码 | 十位五段是否准确，最后段结果与四类结果枚举的关系；编码分配/登记责任 | 避免独立字段被误合成，避免擅自创建编码 |
| 成功率 | 已确认计算属于数据使用层；代码侧保证各场景事件正确完整，仍需明确重试/多步骤的事件产生时机与识别信息 | 不把数据计算规则强塞到代码侧，也不为计算公式过滤原始事件 |
| 性能与占比 | 采集起止、耗时单位及必要业务维度在设计中明确；不制定汇总公式和统计分母 | 保证原始数据足够、正确，不越入数据使用层 |
| 外码与扩展参数 | 无外码/嵌套错误如何取值，哪些公共维度必填、哪些按业务定义、隐私边界 | 当前 SDK 字段不能代替目标协议 |
| 通道边界 | Chart 运维统计、VOC 问题定位、BI 运营打点；二选一仅限 VOC/Chart | 防止把不同目的混成同一上报，或将二选一误扩为三选一 |
| 规约必要性 | 日志/VOC/Chart 哪些特有义务需要明确，哪些只是模型通用能力 | 保留必要要求，避免无根据全保留或全删除 |
| 验收范围 | 验设计与代码，还要看实际事件内容、次数、时机及统计能否成立；是否需真实平台 | 定义“应用得好”的证据，单次调用出现不够 |

## 5. 本轮确认记录

2026-09-21 用户已确认核心交付：**涉及指标或影响既有上报的需求，模型能设计正确统计方案、实现并验证；相关知识与文档一起完善。**

用户先选择“以当前 Demo 代码为准，在本仓定义并落实新规范”，随后进一步明确：**“demo给样例，内网按样例根据真实代码适配就行，这样才能做到迁移到其他代码仓时，也能适配”。** 以后者澄清为准：Demo 是本轮样例的实现与验证环境，不是所有目标仓的固定业务协议；目标仓参考样例的表达与使用方法，按自身真实代码/规则适配。类名、字段、取值、编码表和具体统计口径均不得固化进通用机制。

本轮不以取得内网规范为前置；Demo 代码已有字段不自动补齐尚未定义的统计含义。需要确保样例提供足够的可适配说明与知识结构，但不据此授权升级覆盖目标已有知识，也不把样例代码作为目标事实。首次适配/已有知识如何承接的具体方式留设计核实，产品目标是可迁移、能按真实工程使用。

用户已确认文档效果：**涉及 Chart 时，Story、Spec、Plan 三份文档各有独立可定位的小节，内容按各自用途组织。** 不据此默认所有需求固定留位，也不等于批准新增通用槽位/检查器；实现方式由设计核实已有能力后决定。

用户已确认 Demo 内码：**10 位数字字符串，5 段各 2 位，依次为业务模块、业务流程、节点/事件、子节点/子事件、结果。** 内码末段与 WalletFuncResult 是不同维度：**前者表示具体结果，后者表示统计分类。** 这不是为所有目标仓固化同一编码取值。

用户已确认结果分类：**STEP_ERROR_BY_USER 仅表示主动取消；拒绝授权等归普通失败。** 不根据枚举名字把全部“用户原因”扩大归类为取消。

用户已纠正统计责任：**“这是属于数据使用层的事，代码实现层要保证所有场景的打点都正确上报，不要遗漏”。** 因此本轮方案聚焦事件覆盖、上报时机、结果分类、编码和参数正确；分子/分母及计算规则不作为代码侧需求，不为了统计公式删减原始事件。最初“正确统计方案”的宽泛表述以后续这条澄清限定。

用户已确认参数范围为公共字段加按业务需要定义的额外维度，并补充：事件自身的 eventId、funcID、subFuncID、walletEventDesc，以及 channel、source、issueID、issueName、operationType、orderNumber、srcPassType 等。需要按场景说明含义、类型、单位、来源及隐私处理；不是要求每次上报填满所有字段，也不能用“四要素”穷尽上报设计。代码命名/字段映射按目标工程实际接口适配。

用户已确认节点覆盖：**需求设计识别需要统计的业务节点，并完整覆盖这些节点的成功、失败、取消等适用结果**，不是要求每个内部函数或所有业务步骤都固定上报。

用户已确认编码变更：**相同节点和具体结果可复用；新增需要区分的含义才扩展编码，并检查冲突**，不为每个新增代码分支机械分配新码。

用户已确认通道目的：**VOC 用于问题定位，Chart 用于运维统计，运营埋点另有用途。** 随后补充真实代码仓的命名：**运营打点叫 BI 上报，三个封装分别为 VocBuilder、ChartBuilder、BIBuilder。** GLM 的 VOC=运营 对应不成立。此处真实仓名称以用户陈述为依据，不伪称已读取内网实现；Demo 是否具备对应接口仍按本仓源码确认。
