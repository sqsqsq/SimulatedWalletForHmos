## 1. 问题、使用者与产品目标

2.0.0已将需求级Spec的整体设计职责迁向Framework蓝图/CU，本版初始调查发现双目录绑定、重复输入登记、全激活知识取舍、人工免审批准等旧路径；当前已实施/未闭合情况见Plan，不把初始问题当作全部仍存在。已有实现、离线验证或合并完成不证明产品形态满足用户预期；人工金样改善也不证明正常入口能生成同样结果。

**2.0.1目标**：保持1.9.9的使用能力和业务阅读体验，通过Framework原生蓝图/CU承接设计与施工；Extension继续负责需求流程、知识应用和独立Story表达，收回无依据的额外步骤、重复内容和人工介入，并验证完整使用链及原能力保持。

### 新需求起步与数据边界

本版支持对象是经当前2.x初始化的新需求。1.x及旧试验2.x已存在的flow、材料索引、蓝图绑定、阶段/run、审查回执和批准状态不作为可接续输入；不设计自动或手工转换、字段补默认、从当前上下文回填旧问题、旧目录回退或旧现场恢复成功路径。遇到旧现场或不受支持格式，明确拒绝并保护原目录，另建新需求；不自动清空、改写或迁移旧现场，也不为识别每个历史版本新增平台。当前新需求的数据缺损按下文完整性与可信恢复边界处理，不一概要求重起。

“从新需求开始”不等于每次命令清空该需求：同一2.x新需求内的有效早期材料/人答/已完成阶段和update记录仍需按当前合同重入、比较、复用或恢复。新记录应由当前生产者完整生成；缺必需问题/字段/来源是数据不完整，不是可用历史默认值填平的兼容情形。完整记录的业务适用性待判断、以及合同明示允许的unknown/空值，与缺必填字段分开。

现有工程代码、项目知识、安装所有权、合法usage/Git统计和维护历史保持；它们不构成继承旧需求的状态/授权。旧原件/运行证据可留作维护追溯，不被自动认作新需求的已执行结果。必要的当前来源路径/摘要/provenance由工具依真实输入派生，属于正常生产，不是旧数据回填。

## 3. 完整正常使用场景

### R1 单需求目录与源头一致性

同一需求的原始材料、Story/Review、蓝图和实际需要的CU位于同一物理需求目录，不能只用导航链接包装两个根。需求身份直接定位其蓝图工作区，不另选一份独立蓝图编号、填对应表或执行额外绑定仪式；原生组件归属、CU身份与版本引用仍真实一致。

**目录和使用行为以正式1.9.9为默认，只有原生蓝图/CU约束或已确认功能确需变化时才改。** 根级inbox、RR/prd.md、SR/design.md、AR业务/过程文件、assets及原备份职责保持；撤回sources统一目录、sources/inbox和sources/backups，不以“整理更统一”改变用户入口或目标adapter路径。

普通原件导入后仍留inbox；有新字节或明确退役按原取材/替代职责处理，已并入的原样件不因仍存在就重复导入。当前阅读稿沿RR/SR/AR，原件身份、转换关系、实际采用版本及历史字节可回查；必要稳定版本在已有.backups/local保全，由材料索引唯一登记，不另建统一材料仓或作者自证账。

必须变化的目录限于：新增blueprint，实际CU承接原根级Spec/Plan/契约和后续阶段；根级ux-reference与蓝图工作区存在确定标志冲突，共享UX移入已有assets/ux，CU专属视觉目录按原生需要。AR/design.md仍可保存本单取得原文，但不再由重复提取/complete覆盖。没有必要理由的其它路径保持1.9.9。

内网adapter可保持已定备份位置，返回真实路径，核心按记录消费；目录回调不等于省去必要的来源回执/交付/恢复合同适配。用户材料、有效人答和已确认范围不因技术记录换名而重批。不增加影子Feature或改写原生枚举。验证围绕真实PRD/系统设计/会议/图片输入，不以假设inbox/spec.md要求上游先修。

| 正常场景 | 应得行为 | 完成边界 |
|---|---|---|
| 系统或本地起单 | 按原权限取得关联原件、图片和需求，盘点真实缺口，形成有效范围及来源版本 | 本地零远端；缺件不伪报充分，可选且未依赖的缺件不扩大阻断 |
| 材料/会议澄清 | 区分事实、建议、人答与未决，关键输入先于决定送达；新材料不自动覆盖仍有效裁决 | 只问影响当前工作的真实取舍，保护原话和人工区 |
| 共同设计与业务成文 | 项目事实/规约/模式参与蓝图设计，Story独立组织全文，Review整理真实裁决 | 诚实业务草稿与施工准入分开，不能靠Story补造设计决定 |
| 纯业务送审 | 在已有授权和原流程允许范围交完整Story/Review | 可零CU，不为文件齐全强造施工产物；强制原生质询不豁免 |

| update与续行 | 先取得变化，区分无变化/待续/不可比较/变化，修真源后同步受影响的既有产物 | 已有同范围授权持续有效；过期CU阶段如实处理，不冒用旧Plan或推进未授权阶段 |

## 4. 五类产物和跨阶段知识职责

### R2 延续1.x的设计协作关系

Extension在整体设计前提供相关知识、规约、模式与扩展信息，蓝图接替旧需求级Spec的整体设计职责；canonical是设计真源，原生人读稿是参考视图，Story保自主叙事。共同决定变更回真源，不能在下游另立答案。

| 产物/阶段 | 消费的依据与应交结果 | 保护边界 |
|---|---|---|
| 蓝图及原生人读稿 | 原材料、人答和工程事实形成接口/状态/数据/流程/角色/质量设计；知识有实际落点，必要配置/指标与外部缺口有承担者 | 原生投影由Framework产生；不靠手改签名稿、同义字段或第二设计真源补显示 |
| Story | 自主讲完整业务、用户页面体验、正常/受限/失败/未知、未决、验收和必要技术摘要 | 评审者无需拼读蓝图或代码，必要重述可保，不能扩大承诺 |
| Review | 真实待决、选项后果、有效答复和人工区 | 不是独审报告；知识判断、INFO、格式修正与已授权目标不变成新议题 |
| CU Spec | 本单位行为、边界、可观察结果与验收；宿主扩展解释技术约定、规约、模式承担及项目事实复用 | 不重判共同设计、不搬整份蓝图，不只列知识/验收编号 |
| CU Plan | 本单位实体、方法、存储、调用、角色、复用、统计点和验证责任；宿主扩展与契约同义 | 拟建/模拟不能冒充已有能力，不补造外部接口；共同取舍变更回蓝图 |
| Coding及后续 | 实际消费实体义务、选中模式与相关知识，代码存在且真实调用，按适用责任验证 | 阶段通过、字段存在不等于义务落实；本版不据此默认授权后续实跑 |

Framework原生职责、业务材料/有效决定、Extension知识影响三类来源应可区分；金样中的Asset、恢复接口、具体类名/目录名等案例选择不升级为通用要求。当前知识承载字段是实现选择，不固定为永久需求。

新版原生独立阶段按职责准备：Spec承接acceptance，Plan承接contracts及适用use-cases，沿原生入口取得合法投影并保同一新需求内不冲突的阶段补充；冲突交对应阶段或设计责任方，不跨阶段覆盖、不另建Extension影子准备器。统一解析的合法calls等结构沿原生消费，不能复制另一套归一化或漏掉有序调用及知识义务。

Plan中的文件/模块清单及部分实现位置属于预测，不直接构成用户授权白名单。普通位置调整仍须满足实际义务、公共契约与架构约束；用户明确限制和真实业务范围继续有效，不能因原生放宽预测就取消硬约束，也不能仅因文件未列预测就新增人工批准。

### R3 Story完整阅读与重复内容边界

保持1.9.9独立业务送审及必要技术摘要：接口业务语义、状态与恢复、规约、配置和埋点摘要可读可查，不因蓝图已有就删。关系、条件、责任和结果不能通过摘要化或藏进链接丢失；必要重述与重复决定分开。

用户视角页面交互保入口→页面→操作→可见反馈→去向（跳转或留页），系统协作图不能替代。表达优先级为图＞表格＞列表＞章节＞文字；按角色/场景分组，复杂分支优先页面图，表补完整细节。自制业务关系图保图前短说明→图→图后补充列表，图文共同完整，不凑项、不逐箭头复述、不机械紧邻；原界面图不一律套同类任务，SVG按收益可零张。

标题应像人写文章，简洁准确提炼业务或常规文档主题，审全部层级及加粗小标题；长文、图文、全文逻辑和章节职责按[阅读R1—R7及AC1—AC8](../2026-10-25-Story阅读与写作质量提升/00-需求.md)评价。保持有界落盘、续写、局部替换及人工内容；不把本案例恢复十章/§9变成通用固定章数，不设字数/图数/关键词/相似度质量门。

### R4 知识应用保持与登记收敛

| 环节 | 必须得到的结果 |
|---|---|
| 看到 | 相关知识原文、适用条件和工程事实在受影响决定前实际进入正确执行体，不以文件/清单存在代签 |
| 理解 | 按本需求事实判适用、不适用、冲突或待定，理由可核；项目事实错误回知识真源 |
| 应用 | 适用知识改变具体设计对象的行为、保护、边界或协作，有非自指落点，不能只回显名字 |
| 传递 | CU及后续获准阶段取得并履行自身义务、角色和验证责任，不全量重判，不因桥接ID正确就认语义成立 |

规约可整域不适用并集中说明真实理由；域内有命中时保必要逐项判断。模式按实际业务单元和候选信号/反证选择，不因在激活清单就要求每个无关模式造取舍。相关义务不可漏，来源和知识当前性继续可核。

常规知识义务不要求先登记成通用知识取舍，再凭决定ID才能落实。适用判断、具体义务和真实取舍各有承担位置；保持看到—理解—应用—传递，不保旧knowledge_application账本或其强制桥接。

有效共同判断只维护一次，Story解释业务效果，CU落实本单位责任；常规义务不强套“被否方案”，不适用记录不默认展开正文。适用且改变设计、争议、豁免与待决按阅读用途呈现；真实豁免仍须有合法依据，验证执行体为人工不等于增加人工批准。不能通过减少展示量削弱实际读取与理解。具体实现位置可在真实约束内调整，知识义务须在实际承担实体上可指认并被验证，不能把预测文件路径固化成唯一合法实现。

| DSH与测试证据 | 被测构建、宿主配置、父子原报告、失败/截断/终点及干预可追 | 临时改执行件或诊断辅助不冒称正常产品能力；替身不冒充真实外部接入 |
| 历史与发布 | 正常1.x接新2.x、旧轮次资料可追；历史运行记录不清理 | 按既定发布后迁移决定，不把合并、目录或局部绿测当发布完成 |

已有正确路径优先复用。比如无变化更新、归档读回后补登记、计量起止分责和独立stats，不因统一目录或改知识承载而另造系统。保持责任须有验证对象，不能只以“沿用旧能力”关闭验收。

## 6. 必需适配、简化与退场

### R5 保可信来源，收回重复交接仪式

原件、实际采用版本、真实人答、备份、人工区及必要不可变证据继续可取得；正常换版不能以新原件冒充旧设计依据，分析稿不替代原件或授权。原件全集不由作者摘要或漏写表行缩小。

退出多份作者手抄采用清单、人答标识和语义条目再相互对账的要求；已有稳定版本足够时不无条件复制全部材料/分析。原生来源合同仍满足，必要版本保护先有承担者。固定标题、哈希目录、登记数量、complete动作本身不是业务要求；具体替代对象与消费者由Plan设计，不能只删冻结生产端。

### R6 不新增Extension人工介入点

相对正式1.9.9，除Framework原生真实条件外不新增人工介入。材料、会议、范围和真实外部覆盖/恢复的权限保持；已有有效人答和同范围授权持续使用，不因蓝图/CU、技术状态或版本记录变化再问。

机器ID、转换、冻结、CU接受/readiness、报告核对/格式修复、已授权同步由Agent/工具承担；原生分类/术语/视觉等确认按真实触发条件，不包装成普遍审批。授权内可确定的安装/环境处置不一律交给人；未知归属、受保护内容、业务冲突、范围或权限变化仍按原边界处理，不以自动化代人裁决。

实现预测调整不等于业务授权扩大，判断依据是原请求、有效人答、公共契约与实际架构影响。原生会话交接的机器调用沿可信原授权执行，不把每次领取/上报变成新人工确认；日志、默认权限配置和Agent自写记录本身不构成授权。

工具或环境故障须如实报告并交其责任位置；不把新增人工免责、手工搬运报告或批准绕过变成标准产品流程。已有明确授权内可确定的工作正常处理，未知归属和受保护内容仍不擅动。

### R7 两种自动审查各负其责

蓝图质询核设计成立，Story审查核业务完整可读及与有效设计一致，必要回查原件，不重复完整技术论证。设计问题回真源；有效核对结果只在真实范围内复用，不能一份PASS代替另一对象审查。保独立执行、当前对象绑定、原始报告及完整必审依据，不用字段/合规表或作者自述代签。

没有Story审查员时沿1.9.9明确未审，按既有授权继续原流程允许的后续；不增加免审批准或逐版重批，未审不能计独审/DSH通过。Framework原生强制蓝图质询不豁免。未审语义须贯通登记、update和交付，不能只去掉页面问句却保下游waiver依赖。

新增原生DSH adapter不自动等价于已有本地审查员组合。独立审查、原始报告、图像输入等按实际声明与调用能力判断；没有Story审查员仍按本节处理，不能借原生软降级或普通完成规则记为独审/DSH验收通过。

### R8 缺陷、建议与门禁各按真实责任处理

事实错误、关键遗漏、设计矛盾及影响当前目标的阻断问题应修；非阻断建议由作者采纳或有据保留，不默认停交付或求批准。不能只按INFO/WARN标签忽略真实严重缺陷。对象变化后的必要复核保留，不固定轮数、不为表达建议默认重走全链；报告格式由原审查责任修正，作者不改独审原文。

结构/身份/来源可消费性、业务送审和施工准入分别判断。施工未准入不自动阻止诚实业务草稿成文/送审，真实承诺缺口仍保留；可选或未来缺件只限制实际依赖它的工作，不增加通用豁免、白名单或新门禁平台。

历史闭环事实、当前必修/待核/交接/披露、当前完成资格、发布资格分别报告。旧PASS、closed或旧有效回执不能遮住当前真实必修或待核；建议也不因MAJOR标签自动升级。沿原生共同处置决定责任与必要复核，不增加第二套处置/补核/恢复平台。

普通完成可以与需披露的软视觉/资源债务并存，发布资格仍可阻断，原轴不改签PASS；真实hard要求、必需文本/审查/执行证据、当前有效断言失败等不能借披露放行。原生检查异常或未执行如实保未知及原必需性，必要结论缺失限制相关工作，独立且已授权工作按真实依赖继续；不一律转成作者返修，也不假报成功。修复后复用仍有效结果、核受影响对象，原报告和累计消耗保持。

### 8.2 Framework依赖与推进顺序

统一需求根及正确人读结果保持。此前先把根级ux-reference冲突扩大为必须等Framework，又将全部材料改到sources，随后用假设文件名推上游前置，均缺少对实际使用及最小变化的区分。2026-11-02用户明确撤回这些扩张：inbox等保持1.9.9，只有真实根级UX标志冲突作局部调整；原生图输入接实际原文/图路径。静态可行不冒称正常链已验证。

蓝图renderer、guide和workflow在本次上游对比中哈希未变，但常规知识并不必须装进decision：旧Extension全量知识决定包装是重复显示的重要来源，先按原生facts/实际对象和真实取舍分责适配。目标稿不以当前呈现能力为前置；2.0.1获准实测后再据实际剩余差异决定是否向Framework反馈，不预设必须改renderer。

实现时使用固定发布件真实入口、schema与消费者。确有不可完成的公共合同缺口才以实际证据交其责任方，只限制相关路径；不私改vendored逻辑、不建影子平台、不把未验证写成已支持，也不因保旧字段/目录人为制造外部前置。

CLI配置中的headless等名称不是Extension产品模式承诺；产品范围仍为interactive。真实业务/装置/宿主问题按所有者处理，不全部升成Extension新增需求，也不因归外部而丢验证责任。
