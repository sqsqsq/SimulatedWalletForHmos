## 样例随 base 分发，适配成功后清理

下文涉及的宿主入口须先可用。首装顺序与实测见[首次取得 Story 入口](#首次取得-story-入口)。

本轮用户决定将原草案中与 `base/` 同级的 `examples/` 移入 `base/`。发行包显式包含 `extensions/base/examples/knowledge/` 及 `extensions/base/.gitignore`。解包后，业务工程中的 `doc/extensions/base/.gitignore` 含一行 `/examples/`，只忽略该目录下的临时样例。正式 `knowledge/`、`adapters/` 仍与 `base/` 同级。

`/story adapt` 从 `base/examples/knowledge/` 参考写法，依据目标工程事实生成或更新正式知识，并在现有 manifest 的 `provides.knowledge` 中更新项目实际激活的正式知识路径。样例不登记。适配成功并确认正式知识可加载后，由脚本删除业务工程里本次解包的 `base/examples/`，保留 `base/.gitignore`。适配中断时保留样例供续做，发行压缩包保留完整原件。

验收分两个时点：打开实际发行包，核对样例文件和 `.gitignore` 均已入包；完成适配后，核对临时样例已清理、忽略规则仍在，再从实际 Story 入口读取项目已激活的正式知识。安装校验将这次清理识别为预期结果。

## 现状成因与验收锚点

旧 adapt 从来源工程向目标工程复制文件，要求目标根等于 Git 顶层，以便用同一套路径检查未提交改动。隔离实验中，目标设为 `repo/apps/pay/`，Git 可找到外层仓库，但旧 `--apply` 返回 2；把来源和目标设为同一工程，也返回 2。仓内子工程的 Git 状态路径带 `apps/pay/` 前缀，因此仅删除根目录相等判断会留下覆盖检查漏判的风险。[原始命令结果](../../../../output/evidence/2.0.6-design-review/adapt-roots.json)

| 场景 | 用户应当看到的结果 |
|---|---|
| 在 `repo/apps/pay/` 装好机制后执行 adapt | 从已安装的 adapt 找到 pay 工程的配置、Framework 和扩展。用户无需指定目标仓；同仓兄弟工程保持原样。 |
| 替换本工程的 base 和 adapters 后升级 | adapt 读取业务侧已适配版本，核两目录为本次发行内容、知识与登记针对本项目，完成后记录版本。同版再次执行时不重复派发已完成事项。 |
| 替换动作会覆盖未保存的目标改动 | 在实际替换前指出受影响文件。保护责任随写入动作归属；事后执行的 adapt 无法补救已被覆盖的内容。 |

## 首次取得 Story 入口

**用户纠正：安装后的 Story 源文件只有 `doc/extensions/base/skills/story/SKILL.md`。** 根 manifest 仍在 `doc/extensions/manifest.yaml`。旧的 `doc/extensions/skills/story/SKILL.md` 随旧布局退出。上一稿为迁就 900c 而增加的短入口、包内 `base/install/skills/`、复制步骤和依赖它的升级顺序均已撤回。宿主自己的命令入口（例如 Codex 的 `.codex/skills/story/SKILL.md`）归 Framework 物化，应直接指向 base 中的真实源。业务知识清单仍相对扩展根解析。

**init 具体消费什么。** 对照正式 900c 的项目级 init，`materialize-entry-file` 在渲染宿主工程说明时调用 `loadInstanceExtensions` 读取根 manifest。`provides.skills` 给出 Skill ID 清单，渲染成工程说明中的技能名和源文件链接；`provides.knowledge` 形成知识路径、受众和读取时机，`phase_bindings.<phase>.before_phase_work` 形成阶段前动作指引。manifest 1.1 还接受 `provides.hooks`、`capabilities`、`skill_assets`、`phase_rules_overlays`、`mcp_actions`，各由对应的阶段或功能消费。1.1 的合法字段中没有 `provides.bridges`，也未发现项目 init 在收尾消费的 bridge 更新配置。哪些宿主要生成跳板由 `framework.config.json` 的 `materialized_adapters` 提供。上述工程说明的渲染与原生扩展物化器把跳板写入宿主目录是两个动作。[原生首装结果](../../../../output/evidence/2.0.6-knowledge-and-first-entry/probe-_qpyrdlq/first-install.json)

**目标体验。** 人在原位 manifest 首次做最小声明；首装、更新各跑一次 `framework-init`，由它按有效 Skill 声明与所选宿主复用现有桥生成器，返回时 `/story` 可用，再运行 `/story adapt`。目前尚无可填入现版 manifest、即可同时实现 init 收尾自动写桥与 base 源文件寻址的公开配置。保留这项使用者要求，不把未来扩展字段写成现有用法，也不新增旧地址转发件。

**为什么旧地址曾出现在方案里。** 在现行 900c 的 manifest 1.1 中，`provides.skills: [story]` 登记的是 ID。公开的 `/extension materialize` 先调用原生加载器按扩展根的 `skills/<id>/SKILL.md` 验证；清单有效后才生成宿主跳板。当前布局下把 ID 写成 `base/skills/story` 也不是合法路径登记。上一次能工作的短文件是我提出的变通，并非产品需求。[根 manifest、Skill 直接放入 base 的实际结果](../../../../output/evidence/2.0.6-layout-probe/layout-7gbipkjf/pin-parent-with-examples-entry.txt) · [把路径填进 ID 的实际结果](../../../../output/evidence/2.0.6-layout-probe/layout-7gbipkjf/parent-skill-paths-load.json)

**设计边界。** 目标仍是首装允许一次根 manifest 最小配置，然后由宿主入口进入真正的 `/story adapt`；升级替换 base 和 adapters 后继续使用同一命令。必须让加载器认可 `story` 的 base 源地址，并让宿主跳板引用同一份文件。仅改变底层桥生成器的扫描目录，无法满足根 manifest 装载及阶段绑定校验。使用既有公开命令且不改 Framework 的方案，在这些约束下目前没有成立的接法。若后续选择扩展 Framework，所需讨论只涉及 Skill 源路径解析及其物化，知识注册沿现行合同。该选项未获实施授权。手工直读包内 adapt 可以执行适配，但不能据此宣称宿主已有可调用的 `/story`。
