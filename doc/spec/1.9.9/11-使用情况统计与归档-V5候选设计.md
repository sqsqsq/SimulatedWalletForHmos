## 1. 目标与统计问题

背景：Framework+Extension 被装到各业务仓后，维护侧感知不到谁在用、用了哪些需求与功能、用得怎么样，只能人工问询，跨项目问询不可持续。本设计让 Extension 按需求留下机器可读的使用记录、随代码仓归档，统计时只用「记录文件 + git 历史」拼出全部信息。

统计必须回答的问题（用户裁定）：

1. 哪些需求在用；
2. 哪些人在用（git 提交人）；
3. 用了框架的哪些功能：`story`／`story update`／`spec`／`plan`／`coding`／`review`／`ut`（单元测试）／`testing`（真机）；
4. 每个功能花了多少时间；
5. 这个需求用的什么 agent 和什么模型；
6. 用的 framework 和 extension 是什么版本。

口径：**只看结果**——文件只收完成态与耗时；不收质量判定（verdict）、不收归档步骤、不收过程叙事与备注；语义内容（如需求名称）不入文件；统计以节点编号与启动身份识别需求，不要求取得需求名称。

## 2. 总体结构

| 项 | 决定 |
|---|---|
| 文件 | 仓库级单一 `doc/usage.json`（2026-10-21 用户裁定，与现行实现对齐）；随需求正常提交进仓 |
| 结构 | 一个需求一个节点；功能统一挂 `steps` 子节点（§3 示例、§4 字段说明） |
| 写入者 | Extension 机制层的更新器脚本，**唯一写入者**；模型与人不直接写本文件 |
| 身份真源 | 执行现场的需求目录持一次性身份件；记录器将身份映射进usage。需求目录和身份件不作为独立stats的输入 |
| 统计端 | `/story stats` 分两层：仅凭已归档usage与Git提交记录产事实，模型按模板成文（§6）；doc/features及其中任何文件均非归档依赖 |

## 3. 独立示例

```json
{
  "schema": 1,
  "requirements": {
    "AR90006-202610150930": {
      "ext": "1.9.9",
      "fw": "3.0.0",
      "agent": "opencode",
      "model": "glm-4.6",
      "steps": {
        "story":        { "spent": 3600 },
        "spec":         { "spent": 2085 },
        "plan":         { "spent": 1942 },
        "coding":       { "spent": 4942 },
        "review":       { "spent": 2247 },
        "ut":           { "spent": 1722 },
        "testing":      { "spent": 13735 },
        "story update": { "spent": 1683, "rounds": 2 }
      }
    },
    "AR90006-202610180900": {
      "ext": "1.9.9",
      "fw": "3.0.0",
      "agent": "codex",
      "model": "gpt-5.2",
      "steps": {
        "story": { "spent": 2940 },
        "spec":  { "spent": 1560 }
      }
    },
    "ISSUE-88-202610161100": {
      "ext": "1.9.9",
      "fw": "3.0.0",
      "agent": null,
      "model": null,
      "steps": {}
    }
  }
}
```

**逐节点解读**：

- **节点一**：完整走完一次生命周期。八个步骤全部做完过；`testing` 的 13735 秒含真机未过重试再跑的各段之和（累计、不存逐轮）；`story update` 收口 2 轮。
- **节点二**：**同编号、另一次启动**——时刻不同、键不同，两个节点天然共存（不同人提交相同编号不做特殊处理）。只做完过 `story` 和 `spec`；后续步骤没做完过所以没有行，coding 即使正在进行也看不出。
- **节点三**：首次阶段活动建了节点、尚无完成步骤（`steps` 空）；纯框架使用没有模型写入时机，`agent`/`model` 如实 `null`（统计呈现「身份未知」）。

## 4. 字段功能设计说明（schema 1）

时间戳统一 ISO 8601 带时区；耗时单位为秒（整数）；唯一写入者是更新器脚本。

### 4.1 文件与节点级

| 字段 | 功能与统计问题 | 值来源 | 写入时机与语义 | 缺失/降级语义 |
|---|---|---|---|---|
| `schema` | 使用文件合同版本；消费方按它解析 | 更新器随写入携带 | 合同变更时随首次写入更新 | 版本未知即报错，不猜格式、不做旧格式兼容 |
| 节点键 `<编号>-<时刻>` | 需求唯一标识，回答「这是哪一次需求使用」 | 编号 = 需求目录名；时刻 = 需求目录身份件（真源，见 §5.1），usage 只映射 | 建节点时写一次，此后需求怎么开发、usage 怎么重派生，id 都不变 | 身份件缺失不建节点，更新器报缺失并指明写法 |
| `ext` | 该节点最后刷新时的 Extension 版本，回答「用的哪版扩展」 | `doc/extensions/manifest.yaml > version` | 每次刷新替换为当前值（最后活动版本为准） | 读不到 manifest 报缺失，不填占位值 |
| `fw` | 同上，Framework 版本 | `gate_fingerprint` 前缀（framework `package.json > version`），随 summary 落盘 | 同 `ext` | 无任何阶段 summary 时缺失，如实不填 |
| `agent` / `model` | 模型自报的宿主与模型，回答「用什么 agent/模型跑的」；按「自报身份」口径呈现 | init/建节点任务包让模型提供两个短字段，脚本校验非空字符串后写入 | 最早的写入时机填入，一次后不再改（重启建新节点另算） | 无模型写入时机（纯框架使用）= `null`，统计呈现「身份未知」 |
| `steps` | 功能完成态集合，回答「用完过哪些功能、各花了多少时间」 | 更新器从时间真源计算（§5.2） | 只记完成态：完成一次出现一行，重试/重进累加 `spent` | 空 = 有活动但尚无完成步骤 |

### 4.2 steps 行级

步骤键即功能名：`story`（init 与成文合并为一个步骤）／`story update`／`spec`／`plan`／`coding`／`review`／`ut`／`testing`；前两个对应 story 命令，其余六个对应 framework 阶段。

| 字段 | 功能与统计问题 | 值来源与写入时机 | 缺失/边界语义 | 适用范围 |
|---|---|---|---|---|
| `spent` | 该功能累计耗时（秒），回答「花了多少时间」；**存在 = 做完过（至少一次）** | Σ(完成时刻 − 该轮起点)，各轮求和；真源见 §5.2 | 重试/重进的各段全部计入；轮内含等待与中断（日历跨度）；进行中的这轮不出现、不占 `spent`；缺起点的完成轮不计耗时；各步骤可重叠，**不相加成需求总耗时** | 全部步骤 |
| `rounds` | update 收口轮数，回答「改了几轮」 | update 收口计数，每次收口 +1 | — | 仅 `story update` |
| （行不存在） | 没做完过该步骤 | — | 进行中与未开始都表现为无行；「做到哪了」由最后完成的步骤推断 | — |

## 5. 记录器：写入机制

### 5.1 身份与节点创建

- **身份件**：`doc/features/<编号>/.usage-id`，内容为时刻戳（如 `202610150930`）。story 需求由 init 写入，纯框架使用由更新器在首次阶段活动时写入；一次性，之后永不改。节点键 = `<编号>-<身份件值>`——需求怎么开发，id 不变；本地各种操作不因重新生成时刻产生重复节点。
- **建节点**：首次阶段活动即建节点（含没用 `/story` 的纯框架需求），不等步骤完成或代码提交。
- **同人本地重启**：init（或建节点）时发现同编号、**未提交**的旧节点（`git show HEAD:doc/usage.json` 里没有它）→ 删除旧节点、写新节点——视为人在本地重启该需求，旧尝试数据丢弃。
- **不同人同编号**：时刻不可能相同，复合键天然不同，两个节点自然共存，不做任何处理。

### 5.2 时间采集与结算

全部取机器真源，不用模型自报时间：

| 事件 | 起点真源 | 完成真源 |
|---|---|---|
| framework 六阶段 | 首轮：`<phase>/reports/trace.json > started_at`（框架写入、已有不覆盖）；重试轮：该轮 pre_phase 触发时刻 | 任一后续刷新点读到该阶段有效闭环：`summary.json` 的 `closure_status=="closed"` 与 `closure_commit.committed_at` |
| `story` | init 时刻（身份件值） | 成文登记（`story-flow.json > story_written_at`，缺则登记动作时刻） |
| `story update` | 该轮 `record.json > opened_at` | 同记录 `closed_at`，随收口 `rounds` +1 |

**结算规则（防重复累计的关键）**：

1. 首次阶段起点直接取trace，首次结算形成步骤行；已有行不重复用trace结算。Story按身份时刻到首次成文形成一行，之后重登不重复计。
2. 阶段重试仅保留尚未结算的轮次起点；完成不早于起点时累加并清起点，同轮重复进入不换起点，同闭环重复收尾不再加。不需要持久终态游标。
3. update按原生各轮record直接派生已完成轮数与已知起止区间，不维护第二份update起点；baseline排除，已收口再撤回仍保留曾完成事实。
4. 缺可靠起点：完成事实仍成立（行出现），不编耗时、不抹已有累计。进程中断无完成证据不结算，已有重试起点保持。
5. 只有本次结算涉及跨文件失败恢复时保留必要的待写步骤目标值；不复制全部完成历史，成功后清除。纯init和空slot不制造临时账。

重试轮的pre_phase起点尚无可替代的原生逐轮历史，由记录器在执行现场保存最小运行态；它不归档、不被stats读取。首次trace、Story和update已有真源不重复保存。运行态丢失不抹已累计spent，不能借减量改变多轮累计含义。

### 5.3 刷新点

- story 命令成功路径：init（建节点 + 身份件 + agent/model）、成文登记、update 收口；
- 每阶段 pre_phase 钩子：登记/刷新本轮起点，并顺带对账既有闭环（补结算）；
- stats不是采集或补结算触点；记录器必须在需求执行及使用记录归档前完成必要结算。

不建后台轮询或影子阶段系统，不依赖Framework修改。最后阶段由消费模型按Extension阶段作业，在原生闭环成功后、交付/代码归档前执行现有记录器的finalize收尾，脚本读取真实完成事实、幂等结算并核落盘；Story交付门直接复用同一动作。失败由消费模型重试收尾，不要求用户补账，不在stats补救。原phase_closed上游通知方案撤销。完整时序与验收见[统一接续](../../plan/1.9.9/2026-10-22-CLI后整改统一接续.md)。

### 5.4 文件写入保护

- 单文件互斥；读-改-写**原子替换**（同目录临时文件 + 替换）；写失败保留旧文件并报错，不以空表覆盖；
- 重复操作幂等；坏 JSON / 合并冲突标记明确报错，不静默重生成；
- 分支合并沿正常 git 冲突处理，不自动合并 `spent`。

### 5.5 落库与降级

- adapt 幂等追加 `.gitignore` 白名单行 `!doc/usage.json`（只加行，不改写目标仓已有 ignore 规则，不靠 `git add -f`）；
- adapt 检查时以 `git check-ignore` 核实文件可随正常 `git add` 入库；命中目标仓已有排除规则时如实给出命中的规则与记录位置——文件仅存本地，统计报告标注「文件未入库」，不改写已有规则、不人工介入。

## 6. 统计端：/story stats 两层

| 层 | 职责 |
|---|---|
| **脚本（确定性）** | 读 `usage.json` + git log/numstat → 事实数据 JSON：逐需求行（节点键、提交人、各步骤 `spent`、agent/模型、ext/fw、关联提交变更量）+ 汇总；需求以usage节点编号与启动身份展示；不读取工作区或Git中的doc/features正文取名称；**每个数字可复算** |
| **模型（表达）** | 按 skill 要求核对事实数据、按报告模板组织成文；事实数据是报告数字的**唯一来源**：缺数据如实标注（文件未入库/无提交/身份未知），不得改数、不得推断补数、不得引入事实数据之外的数字 |

**git 归属**：diff 中携带某需求记录行的提交 = 该需求的提交，作者即提交人、numstat 即变更量；一笔提交携带多个需求的记录行时每个需求都计入并标注「混合提交」，代码量不去重；无关联提交的需求如实呈现，不虚构开发人。

报告写运行输出目录，不入库；本期只做本仓报告，跨仓汇总后置另立。独立统计可在完全没有doc/features、Framework运行态和需求产物的代码仓执行，Git历史也无需含需求目录；stats不修改usage。

## 7. 与现行实现的对照（分歧与理由）

现行实现（另一会话，2026-10-16 起的口径）与本文的差异逐项如下；更正时按下表右移左。文件位置已按用户 2026-10-21 裁定对齐为 `doc/usage.json`，不再是分歧项。

| 维度 | V5（本文，用户裁定） | 现行实现 | V5 的理由 |
|---|---|---|---|
| 节点键 | `<编号>-<时刻>` 复合键 | 编号直作键 | 同编号的不同人/不同次启动要能区分共存；同人本地重启由替换规则处理 |
| 身份 | 需求目录身份件真源，usage 只映射 | 无身份件 | id 生成权在需求目录，usage 重派生不漂移、不产生重复 |
| 语义字段 | 不收 `name`/`version`/`features` | 初始化收语义字段、按业务版本分组统计 | 文件只放统计必需最小集；独立统计按编号/身份展示，不依赖未归档名称；模型编写的语义字段不可核验 |
| 步骤行 | `{spent[, rounds]}` | `{start, spent, verdict, completed, last_result}` | 只看结果；「做完过」由 spent 存在单一判定；防重由「结算即清起点」结构性达成，不需要游标与多状态字段 |
| `verdict` | 不记 | 记 PASS/FAIL 并进步骤行 | 用户裁定质量判定不进使用文件，耗时与完成即「结果」 |
| git 归属 | 携带记录行的提交（混合提交双计+标注） | 提交信息 `[TicketNo:]` 解析 | 归属依据与记录同源（文件随提交入库），不依赖提交信息书写约定 |
| 统计端 | 两层：脚本事实数据 + 模型按模板成文 | 脚本直接组装报告，模型只概括 | 用户裁定分两层；事实与表达分责，数字可溯源到事实数据 |
| 报告粒度 | 逐需求明细 + 汇总 | 只汇总、不展示逐需求 | 原始诉求要回答「哪些需求、哪些人」，逐需求是必要输出 |
| 业务版本维度 | 不在本期字段合同 | 业务版本分组、版本开发周期 | 未在 V5 澄清中确立；如需应另立决策，不混入本合同 |

## 8. 完成条件（验收）

| 能力 | 必须具备的证据 |
|---|---|
| 身份与建节点 | init/首次活动建节点且身份件一次性写入；重派生 usage 后节点键不变；同人本地重启替换未提交旧节点；不同人同编号共存 |
| 完成态记录 | 步骤完成后出现行，`spent` 与真源时间差一致；重试/重进后正确累加；同一完成事实反复刷新不重复累加（无游标字段而防重成立）；缺起点的完成轮行出现、耗时缺失；未完成步骤无行 |
| 身份与版本 | `agent`/`model` 自填写入与 `null` 降级；`ext`/`fw` 与实际安装版本一致 |
| 落库与降级 | adapt 幂等追加白名单行且目标 `git add` 可入库；被已有规则排除时报告标注「文件未入库」；不改写目标仓已有 ignore 行 |
| 写入保护 | 并发/重复写幂等；写失败保留旧文件；坏 JSON 与冲突标记报错不覆盖 |
| 统计报告 | 事实数据含提交人、需求编号/启动身份、各步骤耗时、agent/模型、变更量，混合提交双计+标注；报告由模型按模板成文且每个数字可溯源到事实数据；报告不入库 |
| 原能力保持 | 现有流程、门禁、测试全量与失效形态清单不因本设计新增失败 |
