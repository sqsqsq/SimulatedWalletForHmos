# R8 使用情况统计与归档

2026-10-15，按用户逐项确认的结论修订。原始诉求是了解不同项目中 Framework + Extension 的使用情况；本期交付使用事实采集与本仓统计。跨仓汇总和效果评分后置，不为它们增加平台、接口或预留字段。

本页确认业务口径与最小设计，尚未实施。[2026-10-16 实施方案](../../plan/1.9.9/2026-10-16-使用情况统计与归档/00-实施总览与接续条件.md)已形成：在当前 T01–T03 返修及计量修正完成、R8 新增预算确认后接续四步。累计预算沿根 [AGENTS §5](../../../AGENTS.md)，不因方案存在取得真实 CLI、发布或推送授权。

## 1. 本期要回答的问题

默认 `/story stats` 先给当前仓库全版本总体统计，再按业务版本分组；`/story stats --version <业务版本>` 只查看指定版本。报告包含关键指标、占比和各功能步骤的汇总统计，不展示逐需求统计信息。usage 仍按需求保存原始统计事实。

- 各业务版本有多少需求使用了 AI 框架进行编码。
- 有多少需求、多少位需求开发人，以及关联提交的增加行数、删除行数。
- 各业务版本关联 Git 提交覆盖的开发周期。
- 各功能步骤的使用与完成情况；在业务版本的初始化环境分组中，按步骤展示每需求平均耗时，不展开逐需求明细。
- 按业务版本汇总需求初始化时的 Framework、Extension、agent 与模型组合及对应需求数，不展示需求维度。

**使用口径由用户明确裁定：只要 usage 中有该需求，就计为使用了 AI 框架进行编码的需求。** 不要求先出现 coding 完成证据。steps 表达使用框架的程度，不据此声明整项需求已交付，也不折算为质量分或认定步骤越多越好。

只统计取得的数据和可计算的指标。不引入业务版本总需求数、全员人数、整体采用率或缺失数据分析；不要求补齐这些数据才能出报告。下文明确要求的未知业务版本、未知计时仍如实保留。

## 2. 已确认的数据口径

### 2.1 需求身份与初始化

同一仓库内，相同 AR / DTS 编号就是同一个需求，节点直接以需求编号为键。多人接力、换会话、重新执行、update 均复用节点；不追加时间戳，不新增 `.usage-id`，不因节点未提交而删除历史。原有其他本地编号的开发流程保持；本期提交关联按实际内网 AR / DTS 合同实现，不扩充其它编号协议。

首次实际使用 Framework / Extension 时创建记录，不等步骤完成或代码提交。模型在开始业务工作前从当前任务取得编号及下面的初始化信息，由脚本写入；直接使用 Framework 阶段、没有先运行 `/story` 的场景同样覆盖。

| 信息 | 获取与维护规则 |
|---|---|
| 需求名称 | 初始化时取需求明确名称；没有明确名称时，模型按需求功能编写，随记录保存，不等统计时再读 detail.json 或 Story |
| 业务版本 | 需求明确指定的版本优先；没有再取目标工程的 AppVersion 等版本配置；冲突以需求为准，找不到记未知。模型查真实材料与配置，不猜值 |
| Framework / Extension 版本 | 初始化时由脚本读实际安装版本；Framework 读实际 framework 根下 package.json，Extension 读已安装 manifest，不能读维护仓开发源代替 |
| agent / model | 初始化时记录一次，模型从当前会话可知信息提供，不能可靠取得时为 null。是初始化信息，不宣称为运行时验真身份 |

以上信息只在建节点时记录，后续不追踪宿主、模型或产品版本的切换。业务版本与 Framework / Extension 自身版本分开。统计命令不重新读取工程当前版本覆盖旧需求。

### 2.2 开发人与提交关联

按用户确认的内网业务约定：Git 提交人就是需求开发人；一笔提交只对应一个 AR / DTS 编号。提交信息为：

```text
[TicketNo:] ARXXXX或DTSXXX
[Description:] XXX
[Binary Source:] NA
```

脚本只解析 `[TicketNo:]` 行中的唯一编号，与 usage 的需求键精确关联，不从描述、文件名或“本次提交修改了 usage”推断需求归属。需求代码可以与 usage 在不同提交中落库。

以当前分支 HEAD 可达历史为统计范围。开发人取 Git author 的姓名和邮箱，按邮箱去重、姓名用于展示；不增加账号映射服务。一个需求有多个提交人时保留全部，全版本人数按同一规则跨版本去重，不把分组人数相加。

代码量取关联普通提交的 numstat 增加/删除行数，按提交 SHA 去重；merge commit 不重复计入已可达的父分支提交。二进制 numstat 不转换为行数。指标称为“关联提交变更量”，不称为 AI 生成量。提交格式无法解析或没有对应 usage 节点的提交不参与本次需求统计，不制造需求记录；未提交需求仍参与 usage 需求与步骤统计。

### 2.3 版本开发周期

按业务版本筛选 usage 需求，再通过 TicketNo 取得关联提交。取这些提交最早、最晚的 Git committer 时间（`%cI`，带时区）作为周期起止，使用与代码量相同的可达历史和提交去重集合。按真实时间比较先后，再统一转换到报告时区展示。

周期直接写在对应业务版本标题上，格式为“业务版本（开始时间—结束时间）”，不另列周期表，不换算为几天几小时。默认报告的全版本总览标题展示全部 usage 需求关联提交的最早—最晚时间，各版本分组标题展示各自起止时间；指定版本报告写在报告标题上。正文标明统一时区，统计时间跨度与报告生成时间分别展示。

这是关联提交覆盖的时间范围，不是实际 AI 工作时长、正式立项至发布周期或已发布证明。只有一笔关联提交时起止时间相同；没有关联提交的版本只写版本标题，不猜起止时间。业务版本来自 usage 初始化信息，Git 不再推断版本归属。

起止时间由统计脚本读 Git 取得，不向 usage 增加时间字段，不接入 tag、发布系统或立项时间。`spent` 继续独立展示各步骤已结算的日历跨度。

### 2.4 步骤使用与结果

统计步骤为 `story`、`story update`、`spec`、`plan`、`coding`、`review`、`ut`、`testing`。它们是当前产品功能，不另立流程引擎。

- 步骤首次实际使用即进入 steps；没有该步骤节点表示没有采集到其使用。
- verdict 原样消费该步骤当前有效结果；没有结果为 null，不推断成 FAIL。Framework PASS 不自动等于正式闭环。
- completed 表示该步骤有过可信的完成事实；重新进入时保留这个历史事实，同时 start 表示本轮尚未结束。报告区分“完成过”与“当前仍在执行”，不把历史完成替代当前轮次结果。
- Framework 完成以原生 summary 的有效闭环为准；Story 成文使用当前登记及交付检查；update 使用实际 closed 的轮次记录。脚本读原生事实，不接受模型自填 PASS。
- 重复采样不增加使用需求数；每个需求每个步骤最多贡献一次使用计数、一次完成计数。

### 2.5 时间

用户确认采用可核实的**日历跨度**，包含同一轮内等待和中断，不宣称 AI 活动工作时间。使用 `start` 记当前轮起点，`spent` 累计已结束轮次的跨度，不新增逐轮明细账。

1. 开始操作时，脚本写 start；同轮重复开始或恢复不覆盖它。
2. 完成时读取该轮真实结束事实，累计结束减 start，然后清空 start；重复刷新时 start 已空，不再次累加。同一步骤确实新开一轮后才写新 start。
3. 明确终止一轮时，在终止动作发生时结算；进程失联没有终止证据时不猜结束时间，不自动清空 start。恢复同轮仍沿用 start。
4. `spent: 0` 表示起点已知、尚无已结束跨度；起止缺证据、时间倒置或归属不明时为 null，报告按用户确认显示未知。已有累计出现不可核实区间时，不把部分可知值包装成完整累计，也不另造缺失覆盖率指标。
5. verdict 与 completed 不决定耗时是否为零；有完成结果但缺开始证据时，完成可成立，耗时仍未知。
6. 各步骤可能重叠，Story 在 Spec 内成文，update 也会涉及多个阶段；不把步骤 spent 相加成需求总耗时或全仓总执行时间。

## 3. 最小记录与报告

预期阅读效果见 [统计报告样例](11-使用情况统计与归档-预期统计报告样例.md)。样例使用模拟数据，展示全版本、业务版本与功能步骤汇总；不作为真实使用证据或固定业务模板。

目标工程唯一记录为 **`<projectRoot>/doc/usage.json`**，归目标工程所有，不在 Extension 安装替换范围内。该位置与 `paths.features_dir` 无关，避免需求过程目录整体被忽略导致记录不能入库；读取阶段产物仍必须使用真实配置路径。

记录示意（中性编号，仅说明结构；不是业务匹配规则）：

```json
{
  "schema": 1,
  "requirements": {
    "AR12345": {
      "name": "通知订阅设置",
      "version": "4.2.0",
      "ext": "1.9.9",
      "fw": "3.0.0",
      "agent": "opencode",
      "model": null,
      "steps": {
        "spec": {"start": null, "spent": 1800, "verdict": "PASS", "completed": true},
        "coding": {"start": "2026-10-15T03:00:00Z", "spent": 0, "verdict": null, "completed": false}
      }
    },
    "DTS67890": {
      "name": "通知状态修正",
      "version": null,
      "ext": "1.9.9",
      "fw": "3.0.0",
      "agent": null,
      "model": null,
      "steps": {}
    }
  }
}
```

version 为 null 的需求归“未知版本”组，可用 `--version 未知` 查看；未知是显示/筛选值，不写成虚构版本。schema 校验与不支持格式的明确错误由记录脚本承担，不增加旧格式兼容分支。

统计脚本产生事实 JSON，模型按 Story stats 的说明组织 Markdown 报告，报告数字只能取事实 JSON。两份产物写 `<features_dir>/.usage-stats/` 运行目录，安装时确认该目录不入库；不上传、不自动提交。`/story stats` 作为现有 Story 命令分支，不新建第二个统计 Skill 或调度层。

| 报告部分 | 口径 |
|---|---|
| 默认总览 | 标题展示全版本关联提交起止时间；全版本 usage 需求数、关联提交开发人数、关联提交数及变更行数；各步骤使用数、完成数和占比 |
| 版本分组 | 相同指标按业务版本分组；使用占比分母为该版本 usage 需求数，步骤完成率分母为该版本使用过该步骤的需求数；在版本标题标明 Git 关联提交覆盖的起止时间 |
| 版本开发周期 | 对应版本标题写“开始时间—结束时间”；不另列周期表或天/小时差值；没有关联提交时不添加时间范围 |
| 指定版本 | 只筛选对应版本，展示该版本汇总、各功能步骤汇总及初始化环境组合统计 |
| 初始化环境 | 按业务版本 + 初始化 Framework/Extension 版本 + agent/model 组合分组，统计各组合的需求数及分步骤的每需求平均耗时；同一版本可有多行，不选取最后一次环境代表全版本，不展示需求编号 |
| 步骤平均耗时 | 在“业务版本 + 初始化环境组合”内逐步骤计算：已完成该步骤且 spent 数值可核实的需求，其 spent 合计 / 对应需求数；不是除以该版本或环境组全部需求数，也不是按执行轮次平均。未使用、未完成、spent 未知不作为零值参与；没有样本显示 —。报告单位为分钟/需求，不在功能使用表展示累计耗时，不跨步骤求和 |
| 步骤占比 | 使用率 = 有该 steps 节点的需求数 / 本统计范围 usage 需求数；步骤完成率 = 该步骤 completed 为 true 的需求数 / 使用过该步骤的需求数。对应分母为零不计算百分比，显示 — |

默认同时有全版本统计和分版本统计。不同版本的开发人可重叠，全版本去重重算；提交按唯一 TicketNo 归属。没有关联提交时不虚构开发人或代码量，仅展示取得的数据；不扩展缺失数据分析章节。

## 4. 核实后的采集设计

### 4.1 已有能力与限制

- [harness-runner.ts](../../../demo/framework/harness/harness-runner.ts) 的 `recordStartCommit` 在检查执行时调用，已有 trace.start_commit 时不覆盖。trace.started_at 不是作者开始工作的可靠替代，不能拿它重建各轮开始。
- 同文件在生成本次检查报告前触发 post_phase；[hooks-dispatcher.ts](../../../demo/framework/harness/hooks-dispatcher.ts) 当前没有正式闭环后事件。仅登记 post_phase 不能保证最后一步完成被记录。
- [phase-closure-finalizer.ts](../../../demo/framework/harness/scripts/utils/phase-closure-finalizer.ts) 维护真实 closure_commit；[check-receipt.ts](../../../demo/framework/harness/scripts/check-receipt.ts) 和 sync-closure 可独立闭环，不经过 Extension 阶段钩子。
- [AGENTS.section.md](../../../extensions/skills/story/AGENTS.section.md) 已在作者动笔前指向六阶段作者页，由 [adapt-scan.mjs](../../../extensions/skills/story-adaptation/scripts/adapt-scan.mjs) 与 [publish_to_demo.py](../../../test/scripts/publish_to_demo.py) 按所有权分发。
- [lifecycle.py](../../../extensions/skills/story/scripts/core/flow/lifecycle.py) 有 Story 成文登记；[update.py](../../../extensions/skills/story/scripts/core/flow/update.py) 有实际 opened_at/closed_at 和轮次状态，可作为自有步骤生产者。
- 当前根及 demo 的 ignore 都排除 doc/features；本次只读检查中 doc/usage.json 与 demo/doc/usage.json 均未被忽略。这只证明本仓现状，不代表所有目标工程。

### 4.2 一套记录操作，复用现有入口

新增薄记录脚本统一承担初始化、步骤开始、结果刷新和计时结算，供现有 Story 流程及作者操作调用。它只计算统计事实，不控制业务阶段、不替 Framework 判定闭环。内部命令参数和语言复用实现时的公共模块，不在 spec 新建独立状态框架。

| 时机 | 负责方与动作 |
|---|---|
| 需求第一次实际使用 | 模型读取需求与工程，提供编号、名称、业务版本及会话初始化信息；脚本读取已安装产品版本并一次建节点 |
| 作者开始某阶段业务工作前 | AGENTS 扩展段及六阶段作者页提前送达记录动作；脚本登记该步骤 start。普通 Framework 入口同样执行，不强迫先运行 Story |
| Story / update 开始、登记、收口 | 在其现有命令成功路径调用同一记录脚本；有效原生时刻可复用，不从统计调用时刻冒充历史开始 |
| Framework 检查与正式闭环后 | 作者在原生操作返回后调用结果刷新；脚本读当前对象对应的 summary/closure 事实。没有闭环不填 completed；只刷新 verdict 时不结束仍在返修的轮次 |
| 正常交付或提交前 | 现有交付指引要求同步本需求结果、确认 usage 变更可正常提交；补采已完成但漏刷的结果时使用真实结束时间，缺开始则耗时未知 |
| `/story stats` | 只消费已归档 usage 与 Git，不需要本地原始材料、报告、身份件；不依据当前工程状态改写历史记录 |

作者指引不是执行保证。本期不增加 watcher、后台进程、Git hook 或 Framework 影子闭环。采集链是否实际送达并执行，需要隔离消费验证；普通 Framework 入口、最后阶段独立闭环后不再运行 Story 的场景均须验证。接线未证明前不宣称自动采集已成立。

重新执行 start 前，先核该需求/步骤是否确有新活动；旧 summary 不可结束新轮。结果消费须匹配当前阶段对象及轮次起止关系，复用已收敛的报告读取能力，不能只看旧 PASS 的存在。多 feature 对应同一需求时由当前任务的真实需求编号归并，不能从 feature 目录名猜出 AR/DTS；同一步骤同时处于多个 feature 活动时先核现有操作是否能归并为一个活跃区间，未证明前不得分别相加造成重复计时，不为此新增多层调度。

### 4.3 入库与并发写入

- adapt 保留已有 doc/usage.json；首装及检查核 `git check-ignore --no-index`，须能随正常 git add 入库。不能只追加一条无效白名单，也不能以“仅留本地”验收通过。
- 被目标自有规则排除时明确给出命中的规则和唯一记录位置，沿现有适配确认方式完成必要的针对性调整后重查；不取消其它过程目录的忽略，不自动提交或推送，不靠每次 git add -f 使用。
- 每次修改按单文件互斥、重新读取、仅合并本次需求/步骤、同目录临时文件替换的顺序完成。临时文件与锁不入库；无法取得锁或写失败明确报错，旧文件保留，不以空表覆盖。这里是必要的文件读改写保护，不建设通用锁服务。
- 同需求的初始化只创建一次，已存在则保留初值；重复刷新及同轮重复 start 幂等。不同需求的并发更新均须保留。
- 分支合并沿正常 Git 冲突处理，不自动把同需求 spent 相加，不覆盖其它需求。统计时遇坏 JSON 或冲突标记明确报错，不生成似乎完整的报告。

## 5. 实施范围与保持项

| 对象 | 必要动作与保持能力 |
|---|---|
| Story 现有命令入口及脚本 | 增加 stats 路由、统一使用记录操作；保持 init/update/归档/恢复原语义，统计不构成业务交付裁决 |
| AGENTS.section 与六阶段作者页 | 送达首次信息取得、操作前开始记录、原生结束后刷新；不修改 Framework 发布件 |
| Story lifecycle / update | 调用公共记录器，保留既有状态、原件和回执，不重实现业务判定 |
| 已有路径与报告读取器 | 按真实 frameworkRoot、features_dir 和报告配置消费现行事实；承接 T03 修复，不复制新的路径回退分支 |

## 6. 完成条件

| 检查对象 | 必须观察到的结果 |
|---|---|
| 需求身份 | 同仓相同编号只一个节点；多人接力、重进与未提交续行不删历史；不同编号互不覆盖 |
| 初始化信息 | 明确名称直接取用、无名称按功能编写；需求版本优先、冲突以需求为准、无版本归未知；初始化后的配置或模型变化不改记录 |
| 使用与完成 | 开始即出现步骤；没有结果不填 FAIL；有 PASS 未闭环不能 completed；完成后再执行保留历史完成且显示当前活动 |
| 计时 | 两轮正确累计，同轮重复开始/刷新不重复计数；漏起点为未知；等待与中断包含在同轮日历跨度中；不同步骤不加成总耗时 |
| Git 合同 | AR 与 DTS 两种合法 TicketNo 均关联；需求代码和 usage 分开提交仍关联；开发人去重；每笔提交只计一次，不按 usage diff 归属；版本标题的周期取关联提交 committer 时间的最小值/最大值，核跨时区及单提交起止相同，不显示时长差值 |
| 统计报告 | 默认全版本总览与逐版本分组齐全，全版本及各版本标题的起止时间与对应关联提交一致；指定版本含汇总、步骤与初始化环境组合统计，各版本环境组合需求数与版本需求数一致，报告不展开逐需求数据；使用占比与步骤完成率分别采用已定义分母，零使用步骤的完成率显示 —；步骤平均耗时按业务版本和初始化环境组合正确分组、分母仅含该步骤已完成且 spent 可核实的需求；跨版本人数重新去重；仅有 usage 和 Git 的新克隆可出报告 |
| 入库 | 目标正常 git add 可纳入 usage；忽略冲突没有被假报完成；adapt 升级保留已有记录，运行输出不入库 |
| 文件更新 | 两需求并发写均保留；重复操作幂等；写入失败保留原文件；坏 JSON/合并冲突不被覆盖或吞掉 |
| 实际采集 | 从 Story 起手和直接 Framework 起手均取得记录；最后阶段独立闭环后没有下一次 Story 命令也能刷新结果；用真实执行证据核作者送达与行为 |
| 原能力保持 | 沿 [TEST](../../../test/TEST.md) 对实际改动跑相关离线回归和规定检查；本需求不修改业务结果、原生闭环或授权边界 |
