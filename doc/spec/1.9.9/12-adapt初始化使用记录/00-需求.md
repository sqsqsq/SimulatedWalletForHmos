# 1.9.9适配时建立使用记录文件

2026-10-19新增，来源为用户明确要求：“1.9.9升级时，adapt应生成初始版本的usage.json，以让业务仓将其与1.9.9升级内容一起归档”。空表创建能力已实施；本轮按用户最新V5字段合同保持doc/usage.json路径并同步合法性与入库降级，不把旧记录合同视为仍有效。

## 目标

`/story adapt`把业务仓升级到1.9.9机制时，即使业务仓尚未用框架处理任何需求，也应得到可随普通Git提交入库的`doc/usage.json`。创建动作由适配脚本触发，模型不需要额外建文件；不是上传需求系统，也不由工具替用户提交Git。

初始数据沿用现行合同，无业务使用事实时为：

```json
{
  "schema": 1,
  "requirements": {}
}
```

schema取现行usage合同，不在安装器再硬编码一套。升级本身不是业务需求，不新增AR/DTS节点、步骤、耗时、使用者或环境伪记录；真实需求的初始化版本/模型等仍在原使用入口记录。

## 已有文件与失败边界

- 目标文件已存在且合法：逐字节保留，既有数据不重置、不重排、不补造历史；重复adapt幂等。
- 文件缺失：成功适配必须建立空表，后续记录器继续向同一文件记录。
- 文件坏格式/冲突/旧schema：报错并保留原文件，不能当空表覆盖。
- 文件被既有ignore规则阻挡：按V5精确放行并复查；仍受父目录排除等规则影响时只标“文件未入库”，本地记录保留，不新增人工中断。目录不可写或写入失败则如实报告初始化未完成，已完成的机制写入单列。
- `--status`、`--check`只读，不能用检查命令悄悄补建。正常`--apply`负责建立，`--check`确认存在、合法并如实报告可否入库。

已有首装与升级共用apply，首装到本版同样建立；同版本重跑且文件缺失也补建。这不是新适配模式，不改变目标知识、对接层与业务产物所有权。

本次实现和验收以[usage V5纠正方案](../../../plan/1.9.9/2026-10-21-usage按V5纠正/00-实施方案.md)为准；旧适配初始化方案仅留作已实施记录。
