# R2 收件箱子目录导入

> 2026-10-21用户更正：子目录同名文件是合法输入，不因文件名或派生落点冲突新增人工中断。来源身份是完整相对路径，命名处理由脚本完成。实施以[同名材料方案](../../plan/1.9.9/2026-10-21-子目录同名材料/00-实施方案.md)为准，下文历史现状不是当前实现声明。

2026-10-12 立项，与 2.1.0 R4 同诉求（2026-10-10 用户提出）。收件箱是人工补料的唯一入料口，补料常以整目录形态出现：一批会议记录、一套界面稿、一组逐日日志。当前机制只认收件箱顶层的文件，模型只好把目录里的文件复制平铺到 inbox 顶层再归类导入——一次没有信息增量的复制，还破坏「原文件留在收件箱存档」的原样。本诉求让导入链按目录原样收料：子目录里的文件按相对路径识别、归类、转换与登记。实施排在 [R1 材料清单](05-材料清单与图文合同.md) 表结构落地之后（共享「清单按相对路径列原件」的口径），接线由 `doc/plan/1.9.9/2026-10-12-整体设计/` 承接；本页定现状、目标行为、边界与完成条件。现状已按本分支源码逐条核实。

## 1. 现状：平铺假设贯穿整条导入链（1.x 已核）

| 环节 | 现状 | 位置 |
|---|---|---|
| 收件扫描 | 只扫一层，目录整体不可见；注释明说「只扫一层：inbox 是声明，不是搜索起点。递归会把子目录里的无关文件卷进来」 | [importer.py `scan_sources`](../../../extensions/skills/story/scripts/core/materials/importer.py#L119-L126) |
| 归类件 | `.classify.json` 键是平铺文件名（`{"<文件名>":"RR|SR|AR|UX|IMAGES|MEETING", ...}`），写不下子目录里的文件 | [inbox_import.md 归类落盘](../../../extensions/skills/story/rules/inbox_import.md#L54-L61)、importer.py `read_classify` |
| 材料门禁 | 「料到了没有」经材料事实判定，子目录里的新料不算「到了」，人放了料被请「再放一次」 | [decisions.py 材料关卡](../../../extensions/skills/story/scripts/core/flow/decisions.py#L138-L143) |
| 材料清单 | 原件按文件名登记，跨目录同名会互相顶替 | [registry.py `collect_sources`](../../../extensions/skills/story/scripts/core/materials/registry.py#L238-L256)（条目键为 `p.name`） |
| update | 旧原件按文件名匹配、导入前移备份；归类件校验同口径只认平铺文件名 | [update.py](../../../extensions/skills/story/scripts/core/flow/update.py)（行号实施时按现源码定位） |
| 用户指引 | 收件箱 README 与导入规则只说「放进本目录」；UX 类明确「图片进 `ux-reference/` 顶层」 | [inbox-readme.md](../../../extensions/skills/story/templates/inbox-readme.md)、[inbox_import.md](../../../extensions/skills/story/rules/inbox_import.md#L29) |

结果：放进 inbox 的目录对脚本完全不可见，只有靠模型把文件复制平铺，导入链才能继续；复制产生的副本与原目录并存，清单、门禁与「原文件留档」约定失去统一基准。

## 2. 目标行为

- 用户把整目录放进 inbox（任意深度），告知后导入照常走通：子目录里的文件按**相对 inbox 的路径**出现在材料盘点、归类件与导入结果里。
- 归类仍由模型按内容判断六类之一，写进归类件；路径只是事实的定位，不参与归类判断。
- 材料门禁把子目录里的新料算作「到了」；材料清单按相对路径登记原件，跨目录同名分别保留，完整相对路径指认来源；派生标题与资源命名自动区分，不要求人改名。
- update 的比较、旧原件替换与备份沿用既有规则，落点从文件名换成相对路径。
- 收件箱 README 与导入规则写清子目录用法；「章节标题取自文件名」在子目录下的取法由实施在 plan 定，保持「同类多份的拼接顺序确定、重跑幂等」不变。正文来源标题以完整相对路径区分，拼接按相对路径排序；不再以相同主名拒收。
- 对外表述为「**目录原样放入，按完整路径识别来源；同名自动区分**」。同名不构成业务歧义，不增加改名、选择或确认关卡。

## 3. 设计决定

- **键与身份用相对路径**：归类件、清单条目、门禁计数、update 匹配统一以 inbox 内相对路径为键；平铺文件名天然是它自己的相对路径，现有平铺用法无迁移成本。
- **枚举递归、排序确定**：递归枚举后按相对路径排序；排除规则沿用（点文件与控制件不收、README 不收、空目录不产生条目）。
- **同名由派生落点自动区分**：完整相对路径是唯一来源身份；正文分节按来源路径可定位，资源目标从来源路径确定性派生。不同目录同文件名、不同后缀同主名以及目标平台大小写折叠都不合并、不覆盖，不要求人改名。真实不可读或不能转换的材料如实报告具体原因，不能假报已导入；这不是新增命名审批。
- **会议材料不受影响**：会议版本按原件内容指纹留存（registry.py 经 `meeting.saved` 判定，与来源路径无关）；子目录支持后，多目录下的会议材料自动获得同一留存能力。
- **路径口径唯一**：登记用 POSIX 风格相对路径；非法字符、超长路径等按现有失败口径报错，不做静默降级。

## 4. 边界与非目标

- 不解压压缩包：zip 等归档是否自动展开另行按真实需求立项，不在本诉求内。
- 保留 `ux-reference/` 顶层可扫描布局；顶层派生文件名自动区分来源。assets仍按原件分组，但分组键不再用裸文件主名。Framework扫描能力不改。
- 不按目录名自动归类、不引入目录级归类配置；归类判断仍在模型。
- 不做新旧双轨：归类件、清单与门禁只有一套相对路径口径。
