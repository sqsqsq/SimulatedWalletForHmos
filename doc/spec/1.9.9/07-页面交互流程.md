# R3 页面交互流程

2026-10-12 立项，与 2.1.0 R5 同诉求（2026-10-10 用户与测试同学提出）。动机：开卡这类业务，评审人想知道要经过哪些页面、每页做什么操作、正常与异常各怎样走完。当前 Story 的流程说明以业务与系统视角为主，页面级的人读交互没有专门的位置与判据。本诉求给 Story 增加面向人的页面交互流程说明，与现有各章分工清楚、不重复描述。实施排在 [R1 材料清单](05-材料清单与图文合同.md)（同改写作页与章节合同，不并行改同一文件）与 [R6 金样](02-金样优化.md) 贯通锚可用之后，接线由 `doc/plan/1.9.9/2026-10-12-整体设计/` 承接；本页定目标、分工、表达形态与完成条件。开卡仅记录动机，机制与指导使用中性题材。

## 1. 现状与缺口（1.x 已核）

| 已有 | 内容 | 位置 |
|---|---|---|
| 业务流程章 | 从触发到终态的完整过程、跨方协作、状态与分支去向——业务与系统视角 | [章节合同](../../../extensions/skills/story/contracts/story-chapters.json) 业务流程章（行号实施时按现源码定位） |
| UX 材料链 | UX 图进 `ux-reference/` 顶层并带一句说明；交互说明文档并入参考图目录说明、按材料登记 | [inbox_import.md UX 类](../../../extensions/skills/story/rules/inbox_import.md#L29-L31) |
| 决策维度 | 「交互与界面」类别：新入口、页面、参考图、没有稿的部分 | [章节合同 decision_categories](../../../extensions/skills/story/contracts/story-chapters.json#L222-L228) |
| 页面表达规则 | 写作页已有页面原图、页面状态与无页面业务的规则（评审 §2.3 核实）；缺口在沿流程组织页面信息与独立审查覆盖，不是从零增加 UX 体系 | [story-write.md](../../../extensions/skills/story/phases/story-write.md) |

缺口：评审人只能把页面信息从材料与图里自行拼出来——沿一条业务流程走一遍「从哪进入、到哪个页面、做什么操作、看到什么结果」的叙事在正文里没有归属位置、没有写法、没有审查判据；UX 交互说明文档落进参考图目录后，没有面向流程章的成文路由。

## 2. 目标

第一次接触需求的评审人，不翻仓库与原型工具，能沿一条业务流程读出完整的人机交互：从哪个入口进入、依次经过哪些页面、每页做什么操作、正常完成看到什么、受限与异常时看到什么、被引导去哪里。交互流程依附业务流程成立，不另起一套业务事实。

## 3. 与现有各章的分工（不重复描述）

| 章 | 回答什么 | 与页面交互流程的关系 |
|---|---|---|
| 业务流程 | 业务与系统怎么走：触发、跨方协作、状态、分支去向、交接点 | 提供被沿走的流程骨架；交互流程按流程小节组织，引用其分支不重述规则 |
| 功能说明 | 能力内部规则：输入、条件、数据与状态变化 | 页面上的操作写「做什么」，规则留在能力章 |
| 异常与恢复 | 异常分类、影响、恢复方式 | 交互流程写异常时人看到什么、能做什么，分类与恢复不重述 |
| 验收 | 可观察的通过条件 | 已确认的页面操作与结果可以成为行为验收依据；不按每页机械产生验收条目 |

去重规则沿用章节合同既有判据「同一件事只在一处完整表述」：业务规则、分支条件与状态只在规则所在章成文；页面、操作与页面间的引导是交互流程的独有信息，规则章不因交互流程出现而补写页面。两章互相用业务名指认，不复制内容；互补（表讲属性、文字讲理由、图讲关系）不算重复。

## 4. 交互流程怎么写

- **位置**：业务流程章内按流程小节组织——每条有人机交互的业务流程配一节页面交互，页面数量多时按入口或角色分组；小节切法由写作设计按需求定，十章合同与章数不变。
- **主载体**：页面流转表——`页面 | 来路/入口 | 用户操作 | 正常结果 | 异常提示与去向`；页面分支复杂时配页面流转图（Mermaid；SVG 成立后按 [R4](08-SVG表达与交付.md) 的自然选型处理，不双版试画）。
- **原图**：关键页面引用 `ux-reference/` 的登记原图，按既有图三件套落盘（图前一句说明、图后写图上没有的信息，口径与 [R1](05-材料清单与图文合同.md) 图文合同一致）；不复制图片、不新开目录。
- **素材边界**：只写材料里有的页面与操作——UX 稿、交互说明、产品需求、会议结论；材料没给的交互细节登记议题（决策登记「交互与界面」类），不替人补设计。材料冲突先按现有议题路径处理，不以「有稿照录」跳过冲突判断。
- **显式不适用**：没有页面的业务（后台作业、服务端流程）按现有规则写调用方与数据生命周期，显式写明无页面交互，不硬造页面。

## 5. 方案方向（实施前由用户确认）

1. 交互流程作为业务流程章内的小节（提议），不新增第十一章——章数变化牵动模板、审查与全部金样，收益不成比例；
2. 交互判断先按「材料有稿照录 + 缺口登记议题」处理，不为它扩展规格职责；实跑若发现页面序列需要共同设计权威，再按最早责任回设计立项（1.x 的设计权威是经确认的范围与规格）；
3. 验收不强制按页面出条目；页面交互是理解辅助，验收仍按行为判。

## 6. 机制落点（实施输入）

[story-chapters.json](../../../extensions/skills/story/contracts/story-chapters.json)（业务流程章的问题与结构、去重判据增加交互维度）、[story-write.md](../../../extensions/skills/story/phases/story-write.md)（章表、表达选择补页面交互行、骨架写法）、UX 文档归类落点（交互说明作为流程章的成文来源，或维持材料登记由写作设计引用，实施在 plan 定）、审查判据（页面与登记原图一致、与规则章去重）、金样（在 [R6](02-金样优化.md) 贯通锚基线上加交互内容）。

## 7. 完成条件

| 能力 | 必须具备的证据 |
|---|---|
| 有稿需求的交互叙事 | 中性示例展示页面流转表 + 原图引用 + 页面流转图的完整形态，经渲染与语义复核 |
| 与规则章不重复 | 同一需求里规则与交互各自一处成文、互相指认，审查判据能区分重复与互补 |
| 无页面业务 | 显式不适用路径成立，不硬造页面 |
| 原能力保持 | 十章结构、图三件套、UX 登记链、决策登记类别全部照旧成立 |
