# DSH 正式支持（1.9.9 发布后补充，版本号不变）

2026-10-28，来源：用户在 1.9.9 结项后提出 1.9.9 没有完成对 dsh 的正式支持，要求重开 1.9.9 补上。实施入口为[实施方案](../../../plan/1.9.9/2026-10-28-dsh正式支持/00-实施方案.md)，判法采用 extension-acceptance@17（保持，见[本版标准变更](../评价标准变更.md)末节）。

## 1. 目标

不改上游 Framework，Extension 与 demo 正式支持 dsh；测试装置对 dsh 的临时支持退出。之后 demo 用正常发布入口升级 Extension，就能按默认测试配置直接完成 dsh 的 CLI 测试，不需要任何手工临时改动。

1. dsh 会话在 demo 里经现有入口取得 Framework 各阶段与 `/story`：工程根 `AGENTS.md`/`CLAUDE.md` 与 `.agents/skills/*`。Extension 不为 dsh 新增入口文件，正式登记共用的 `.agents/skills/story/SKILL.md` 服务 dsh。
2. demo 的 dsh 独立审查员正式启用：带审查员配置层启动的 dsh 会话里，Framework 按“有审查员”生成 request、作者调用 `verifier` 工具，报告按原协议验真闭环。不再在测试工作区临时改声明。
3. demo 的 dsh adapter 模板与已物化的配置层是同一份，Framework UPDATE 重新物化不会把可用的配置层换成 DSH 0.2.1 无法加载的旧写法。
4. 审查员配置层由 dsh 的启动配置固定装载，启动与续跑都带；测试装置不再按 suite 生成注入快照，也不再有 dsh 专属的起跑检查。dsh 原生会话采集是取证，保留。
5. 使用者能从 README、发布说明知道：dsh 用哪个入口，审查员从哪里来，怎样启动和续跑，目标仓没有 dsh adapter 时是什么结果。

## 2. 不做

- 不改上游 agent-maison，不改 Framework 的调度、request、验真或闭环逻辑；demo 里只动 `framework/agents/dsh/` 这组本地定制。
- 不新增 dsh 专属 bridge 文件，不升 Extension 版本号，不改 Extension 的流程与产物合同。
- 不提供启动脚本，不接 dsh 阶段钩子（Stop 闭环检查、framework 写保护）。
- 不处理测试隔离问题（见 §4 第 4 项），留作后续。
- 不运行新的真实 CLI；最终行为验证由用户另行授权起 suite。

## 3. 验收

- demo 的 `framework/agents/dsh/adapter.yaml` 声明有审查员；adapter 模板、demo 物化件和根目录维护拷贝逐字节相同；Framework 的 adapter 目录一致性检查与物化探针通过。
- `test.yaml` 默认 dsh 配置在任一 Case 工程 cwd 下解析出的启动与续跑命令各带一次该工程的配置层；测试装置里注入快照、`cli-registry.json` 与对应环境变量零残留，专用测试随之退出。
- demo 按 `publish_to_demo.py` 以 1.9.9 原号重装后与开发源同源，改动只在扩展目录、登记入口与扩展段；失效形态 FAIL 0。
- 从 demo 现建的一次性 template 带上配置层与“有审查员”的声明，即“升级后直接 CLI”的离线证据。
- Extension 预算有效行 G/X 不变（仍为 G3866/X948）。
- 未覆盖如实列出：新一轮真实 CLI、dsh tui/web 交互形态、子级只读的工具级保证。

## 4. 讨论与修订依据

1. **原始诉求**（用户原话）：「我发现1.9.9有个问题，没有完成对dsh的正式支持。我希望重开1.9.9，增加对dsh的支持和适配。1）demo的.dsh实现framework+extension的完整功能入口 2）bridge 增加对dsh的支持 3）将新的1.9.9在demo进行安装 4）当前dsh似乎一直是在cli测试装置里实现的是吗？一直没有正式应用？」
2. **第 4 问的调查结论**（执行者只读核对，2026-10-28）：
   - 测试装置完整接入了 dsh：中央 runtime 有 `DshAdapter`，suite 快照会注入 `--patch`，`test.yaml` 默认配置就是 dsh。
   - demo 的 dsh adapter 是 10-20 起的本地定制，上游没有。`verifier_subagent` 一直是 false，四轮 CLI（10-21 到 10-24）都是在测试工作区里临时改成 true 才跑的。adapter 模板还是 DSH 0.2.0 写法，与 `c2d8b72b` 物化的 0.2.1 配置层不一致。
   - Extension 没有 dsh 专属内容。实跑原件证明 dsh 从 `.agents/skills` 发现了 story/spec/plan，会话里调用过 `skill` 与 `verifier`（`output/story/story-suite-20261024-224427/cases/auto-topup/20261024-224503-27060-d418f976/native-sessions/`）。
   - 结论：dsh 一直只在测试装置里完整可用，正式交付面没有登记。
3. **范围澄清**：执行者问了四个选择，用户原答如下。
   - 角色：「本轮授权我兼写方案」。
   - 版本：「沿用 1.9.9 原号重装」。执行者提示过的后果：已装目标与使用记录分不清新旧内容。沿用 1.9.8「发布后补充，版本号不变」的先例 `2e872e7d`。
   - bridge：「正式登记共用 .agents 入口」，不选新增专属入口。dsh 是否扫描工程 `.dsh/skills` 未核，新增可能出现两个同名 story。
   - 入口范围：只选「审查员正式启用」。选项里写明的已知差距由用户接受：子级仍看得见写工具，只读只靠人设约束。未选交互启动脚本、dsh 阶段钩子和测试隔离修正。
4. **执行者顺带发现，未纳入本次**：dsh 实跑时，用户级 `~/.agents/AGENTS.md` 与用户级维护技能（maintenance-designer/executor 等）进入了消费模型上下文，违反“消费模型不接触维护方案”。用户未选修正，记为已知问题。
5. **目标修订**（用户在方案起草中补充，原话）：「我的目标是，不改framework，但extension和demo正式支持dsh，去掉测试装置对dsh的临时支持，后续demo仓可以直接升级extension并完成cli测试」。随后确认两点：
   - 「不改framework」的边界：「不改上游，demo 的 dsh 定制可改」，与 10-20 口径相同。
   - 配置层装载：「dsh 启动配置固定带上」，suite 快照注入退出。
   - 由此新增 §1 第 4 项；第一版方案里保留注入快照的写法被替代。
