# R3 需求执行效率

承接原 2.1.0 R3 §5 中需求生成、局部修复、重复输入和派审的有效目标。安装升级、知识适配增量与图形试错效率仍归 2.1.0 R2/R3。

## 1. 优化责任

| 目标 | 在现有流程中做什么 | 观察什么 |
|---|---|---|
| 首次成文质量 | 动笔前取得有效决定、事实、表达要求与完成条件；复用已交付的确定性辅助 | 首轮漏条件、误权威和无依据结论减少 |
| 同根因一次处理 | 按实际决定及影响面修真源/派生/人读件，完整报已发现问题和责任 | 不在已知其他位置重复发现同一矛盾 |
| 减少重复查询与输入 | 同一动作一次提供必要结果与下一责任，读取当前有效版本，规则单一来源 | 无信息增量调用、重复全文和无效上下文减少 |
| 减少无效派审 | 沿现有对象绑定/有效报告复用；格式修复与语义变更按真实性质处理 | 不因报告时刻/登记动作重新成文或重审 |
| 上下文与恢复 | 核实际宿主容量和压缩/续行，按原生当前范围与状态恢复 | 不靠读 checker 反复猜状态，不因装置配置错误中断正常链 |

已在 2.0.2 成立的能力只核保持。本版不重建 dispatch、材料指纹、原生事实基线或运行状态；不新增模型配置系统，不改用户全局设置、不擅自换模型。发现配置风险先查单位、实际生效来源和触发证据，不能将无单位错误消息当精确 token 上限。

## 2. 成本计算边界

必须在相同质量、输入版本、授权终点与环境可比后比较。单位是一项实际请求：Story 首段、update、蓝图、设计交接、CU 施工分别列，不能用一个 CU 代整单；人工等待、外部失败与模型有效工作分开。统计未知保留未知，墙钟不冒充模型净耗时，报告数不等于返修次数。

独立执行者仍需要自己的完整必要输入，不能为省 token 复用作者上下文或删除知识。减少派审不能放宽真实内容变化的重审。维护对照不变成消费模型每次必须做的双版本试写，不以硬编码返修次数/长度阈值取得成本目标。

## 3. 可检查的完成条件

质量门先成立：按 TEST 三轴中的产物/知识评价达到 90 分档并经用户确认，且无未解除的业务阻断；不能通过减少事实或独立审查达到成本目标。

同一 Case/材料字节/实际人决定/终点/宿主模型设置的基线与候选各完成一次作为最小配对；已有同条件合格基线可复用，不为轮次数重复付费。模型调用另获授权。初段与 update 分开，所含主/子任务全部计入；总 token 用现有归一化 usage（输入、输出、缓存分别披露），处理时间剔除可证人工等待与基础设施停顿，未能剔除则记不可比。

本版效率签收：两个正常 Case 达各自授权终点，至少一组同质同终点配对具有效率证据；总 token、有效处理时间均不增加，至少一项严格下降，必需人工操作不增加。同一配对若一升一降，只记局部收益，不签“整体提效”；需要用户另行调整目标才可改变此条件。单次差值只证明该配对观察，不宣称统计显著或普遍收益。

基线失败或质量不合格的组可证明能力恢复，不能用失败耗时比较成本。无可比配对、事件缺失或环境不可比时效率仍未验证；不以计数推测补足。旧范围/用量缺口继续保留原记录。
