# R2 产物内容、表达与独立审查

从原 2.1.0 R3 §1、§5 的首次成文与局部修复内容迁入，消费本版 R1 质量基线。2.0.2 的确定性返修与身份/原件保护继续归原版本，本版不另建闭环。

## 1. 应有结果

| 对象 | 读者要完成的判断 |
|---|---|
| Story | 独立理解背景、范围、整体协作、正常/异常/未知结果、恢复、验收、上线及待决；不能靠字段齐或复制蓝图全文代替 |
| Review | 真正需要决定的事项、冲突双方、可选后果、建议及权威明确；已定/未定与正文一致，人工区受保护 |
| 整体设计与技术附件 | 共同责任、状态、契约和取舍可回查；不能把结构化投影称作已经达到旧 Spec/Plan 的阅读效果 |
| CU Spec/Plan | 该单位承担的行为、文件/实体、输入输出、状态和验证可评估；局部设计不改共同范围，也不缩水为一组 YAML 链接 |
| 图与文 | 合起来讲清关系、条件、参与方、返回结果及失败责任；载体不固定，不要求用 SVG |

同类信息有清晰组织，允许有依据的表达差异；不以固定行数、节点数、句式、字数或 Case 答案限制作者。接口细节放在正确读者需要的位置，关键精确业务约束不得被摘要藏掉。统计指标的分母/时间范围/来源不因重新表述改变。

### 1.1 整体视角的固定承担者

人只读 Story 与 Review，即应知道需求为何做、整体分工、主流程及关键状态、失败/未知结果、影响验收的约束、待谁决定什么。Story 范围章说明责任边界，业务方案章说明协作与取舍，流程章把调用、返回、分支和终态连起来；图型由关系决定，不强制固定图数。原生设计附件供技术核对，不能把正文应讲的关系全部移进去。

生成时点保持蓝图设计之后、CU 施工之前；不新增“整体设计.md”或自建 renderer。CU Spec/Plan 要回答本单位行为和实现责任，在当前 required_outputs 允许复用时给实际引用及覆盖说明，不补空篇。全需求解释不依赖一个或多个 CU 文档拼接。

验收为内容问答：不打开 YAML、工具日志和维护材料，读者能从 Story/Review 找到以上答案；打开技术附件能核到接口/状态/决定来源，不能发现相反结论。找不到关键答案即未达质量目标，不按字数或字段覆盖百分比放行。

## 2. 最早责任处修正

来源与决定在作者行动前送达；模型负责理解、选择与叙事，确定性脚本负责身份、来源绑定、结构、投影及渲染辅助。设计关系错误回蓝图，真实业务未决回实际负责人，表达错误回作者。一次语义发现按同一决定检查受影响对象，不逐个文件碰运气返修。

沿现有章节合同、作者页、写作设计和独立审查判据维护一份要求，其余按来源消费。当前机制是否仍有金样同类缺陷须以实际输入/输出查证；不把历史候选错误直接转成产品规则。新页面、业务身份、恢复与跨端数据须有实际生产者和消费者，不能仅列类名或接口名。

### 2.1 从实际缺口到机制改动

每项改动说明：什么信息在何时缺失，谁需要它，哪个现有入口承担，期望改善什么实际输出。先核已有规则的送达与消费，不因候选有错就追加相同提示。

信息缺失修任务装配；已送达但被误解修最早作者要求或示例；共同设计错误回蓝图负责方。Spec/Plan从本CU原生设计与验收取得行为、条件、恢复及验证义务，不从Story重新推导设计。已经正确成立的机制只核保持。

确定性检查只承担结构、路径、引用、身份、材料变化、人工区及投影；独立审查承担来源忠实、完整性、可读性和可实施性。双方共享同一内容合同，使用前送达；检查一次给全当前能判断的问题，前置缺失导致未执行的检查明确列出，沿用现有返回协议。

## 3. 独立审查有效性

使用 2.0.2 的 dispatch/材料身份/原始报告合同。独立执行者取得完整必要输入，自行判断，不将作者“已经修好”或前轮结论当本轮标准。检查实际读取范围、报告原话和真实缺陷是否对应；格式 PASS 或隔离 task 存在不单独证明审查有效。

坏格式返回独立执行者，原件保持；材料变化按现有身份重审，同材料有效结果复用。机器不得按语义关键词把结论改成通过。有效建议不强迫无意义返修，业务矛盾也不因属于蓝图侧而降级。能力不足如实说明，授权规则沿既有合同，不伪造已验。

## 4. 验收与边界

用 R1 修订稿和真实运行材料对照每类读者问题，核完整性、准确性、跨产物一致及可执行性。独立语义审查和用户效果审定均需有具体内容。不同合法名称、分组与关系规模用于判断通用性；不把金样注入消费模型。

本版不新增 SVG 通道、不修改分发结构、不申请通用文档审查框架。出现 Framework 原生表达/数据缺口时交其责任方并标明影响，不能本仓复制设计真源。对应成本由 R3/R4 统一核。
