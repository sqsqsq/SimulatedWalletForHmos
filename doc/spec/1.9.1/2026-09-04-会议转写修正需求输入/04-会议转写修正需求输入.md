# 会议转写修正需求输入

> 状态：已冻结（2026-09-04 修订一处：议题即需求，见 D11；2026-09-07 修订一处：解析脚本归公共，见 D4）

> 本版为重写版。首版按机制拆成十六条结论，混入了方案层细节，且没有完整写出执行者的任务；
> 经用户确认后重组为下面五节。首版中属于方案层的内容不在本文保留，留给 design 轮次重新提出。

## 原始诉求

现有流程中，story init 依赖需求系统或 inbox 补齐需求材料。这些材料依赖人或 AI 保证准确和完整。
现实中 SE 和产品在首轮提供材料后，后续变化不一定刷新这些材料。

新增一种输入：需求澄清会议的语音转文字文档。用户希望有一套可靠机制，用它对需求文档做修正和增强，
不引入问题，不乱猜乱编。

转写文档的已知局限：

1. 大量错别字或语义转化异常，局部描述可能因转写质量出错，原意并非如此。
2. 会议是人的讨论，存在来回修正、重复说明、前后矛盾、跳跃式思维。
3. 内容可能与需求文档冲突：增强、修正、裁剪、错谬、矛盾。

## 1. 问题与目标

需求文档在首轮提供之后可能不再刷新。此后需求的变化只留在澄清会议里，而会议只有一份语音转写。

目标有两个：

- 后续 spec 建立在会议达成的最新共识上，而不是过期的文档上；
- 人能看出文档哪里已经过期，好把刷新的责任交回给 SE 和产品。

「可靠、不乱猜乱编」在行为上的含义：执行者报出的每一处改变都能指回会上的原话；会上没说的它不写；
会上没收敛的它不替人定；它漏掉的由独立审查找出来。

## 2. 执行者的任务定义

这一节沿维护契约 §2 的行为链写，是本需求的核心。执行者在接触转写之前必须已经得到这一节的内容。

**材料是什么。** 一场围绕本需求的讨论记录。它比需求文档新，是需求变化的唯一记录。但它是讨论态：
有转写错误，有说了又改的话，有没收敛的分歧，有跳跃。会议按议题组织，一个议题对应一个需求，一场会通常覆盖多个需求；
议题之内没有可用的结构。它是证据，不是定论。

**用它做什么。** 找出会议对本需求输入的实际改变，写成一份会议结论，让改变进入 spec 的输入。
会议结论按话题记：会上定了什么、原话依据、对文档的影响（增强、修正或裁剪，落在哪一段）、
状态（已定、未收敛、转写存疑）。与本需求无关的话题只记不消费。不是复述或整理会议，
不是替 SE 和产品改他们的文档。同时把「文档哪里过期了」交给人。

**怎么做。** 先从已有材料建立对本需求的理解；纠正转写里的字面错误，让讨论可读；按议题判断哪些属于当前需求，
判得准的直接取，判不准的在关卡上问人，不属于的只记不消费；带着对需求的理解通读整场讨论，
形成对每个话题「最后定了什么、中间怎么变、哪里没收敛」的整体判断；再对照文档，定位每一处改变落在哪份文档的哪一段，
以及它是增强、修正还是裁剪。整体判断先于逐条对照，不是逐句扫描。

**做到什么程度。** 三个尺度：

- 解释尺度：会上明确收口的，执行者自己定为结论，不问人；判据是转写里有收口的那句话，能引出来。
  没有收口那句话的一律记为开放问题，不替人定。说话人自己改口的按后说的算，记轨迹。
  文档与会议冲突时以会议为准写进结论，但它属于修正类，要在关卡上请人过目。
- 产物尺度：落到 design.md 的输入为止。不改 RR 与 SR，不直接改 spec；spec 仍从 design.md 来。
- 处理深度：每条发言都读，按话题记录，不逐句登记。完整的判据是每个话题都有去向：结论、开放或不消费；
  转写里有而结论里没有去向的话题就是漏。

人只介入一次：材料关卡那一轮，执行者摆出结论摘要，只把值得问的拿来问，即议题是否属于本需求判不准的、
未收敛的、影响结论的转写存疑、改动范围或接口的高影响修正，每条带推荐。人读一遍结论、一轮答完；没有异议的条目随这一轮的确认一起生效。

以下是用户在澄清过程中做出的决定，方案必须遵守，不再重新讨论。

|---|---|---|
| D1 | 转写不并入 RR/SR/AR/UX 任何正文。它是证据源；执行者从它得出改变，改变经人确认后才成为需求输入。原始 RR/SR 本地正文不改。 | 用户确认 |
| D2 | 裁决人是使用流程的开发者本人，通常参加过那场会。 | 用户确认 |
| D3 | 转写件以原始 docx 进入。docx 含会议信息与参会人姓名，正文按议题分节，议题内逐条为「姓名 时间：发言」，没有角色标签。发言人角色由模型提出、人确认。 | 用户确认 |
| D4 | 机制自带 docx 解析与语义纠偏。解析是独立具名的**公共脚本**，随升级正常更新，内网不另实现；输出合同写在脚本自身。纠偏提示词随机制交付。 | 用户明确要求；2026-09-07 按 01 分册 A11（对接脚本只有三个）把解析归公共 |
| D5 | 纠偏只改字面：人名、术语、拼音、错别字。依据只来自已知事实：参会人名单、本需求材料、目标仓项目事实、术语表。源外拿不准的不改。不删发言、不合并、不摘要、不消解矛盾、不调顺序。纠偏后的文本是证据，原始 docx 存档溯源。纠偏不单独停等。 | 用户确认 |
| D6 | 不在裁决前把转写重写成自洽文档。执行者的整体理解体现在它报出的改变与开放问题里，不另落一份文件。 | 用户确认不做 |
| D7 | 人的介入并入材料关卡那一轮，不新增停等点。改变按影响排序，互不牵制的一轮摆完，每条带推荐与理由，人整轮回答；记录仍逐条，只认人签，依据记人的原话。人的时间只花在影响大的地方。 | 用户提出并确认 |
| D8 | 人确认的改变作为独立来源进入 design.md 提取；与原文冲突时以它为准，因为它更晚且经人确认。由它派生一份文档刷新清单交给人。 | 用户确认 |
| D9 | 一场会一轮。后一场推翻前一场已确认的改变时须再经人裁决，不自动覆盖；旧结论保留可查。 | 用户确认 |
| D10 | 本轮范围到 spec 输入为止；spec 定稿后再来的会议另立需求。只覆盖 interactive。 | 用户确认 |
| D11 | 一个议题对应一个需求，一场会覆盖多个需求。执行者按议题内容自动匹配当前需求：判得准的直接取，判不准的在材料关卡那一轮问人，不属于本需求的议题只记不消费。 | 用户 2026-09-04 修正并确认 |

## 4. 验收的行为判据

验收对象是执行者的行为，不是文件或字段。三层各证明一件事：

- **确定性部分**：解析、纠偏产出与人工裁决记录的结构由脚本自检，用构造件覆盖它们各自的失败语义。构造件只用于脚本自检，不用来证明模型判断力。
- **语义部分**：独立 verifier 判断执行者有没有漏掉会上说了的改变、有没有写出会上没说的、有没有替人定没收敛的事、纠偏有没有改了意思。
- **行为部分**：用用户真实开过的会议 docx 跑真实 CLI。用户按评分协议判：用户自己知道的那几处变化它报没报；它有没有编；它问人的问题是不是值得问。

规模按维护契约 §7.5 在方案里登记峰值与上限；脚本里的语义代理标识零新增。

## 5. 范围外

- 刷新清单怎么送回需求系统。
- spec 定稿后的会议处理。
- headless / goal 模式。
- 会议之外的其它澄清载体（聊天记录、邮件）。机制对它们是否成立由 design 轮次判断，本轮不承诺。
