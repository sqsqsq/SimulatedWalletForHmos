# Review 决策发现与表达

> 状态：**已冻结**（用户 2026-09-07 确认）。R1–R9 覆盖发现方法、表达与验收尺度；
> 本文为该需求的基线，方案在 design 轮次另立。

## 用户明确提出的问题

同一个需求多次生成 review.md，结果不够稳定。用户认为缺少指导模型发现决策点的方法论。这里记录的是用户的实际使用反馈，本次尚未进行同输入重复测试，也不据此断言所有差异都来自提示词。

决策点的表达没有充分讲清问题、背景与依据、建议与理由。可以借鉴 grill-me 的部分优点。用户已退出 grill-me 访谈模式，后续按普通需求讨论推进。

分类本身没有问题，但分类应发生在发现问题之后。不能把分类清单当成发现决策点的方法，也不能用每类凑出一条来表现覆盖充分。

用户进一步明确：grill-me 追问人，Review 的分析要求追问模型，交给人的是一份相对可靠的输出。模型应先用可获得的证据检验自己的判断，整理结论、理由与仍需确认的事项，避免让人承担模型本可完成的分析。这里定义的是行为能力，不预先指定额外 Agent 或多轮调用。

用户提出将这项能力与会议转写的澄清环节结合。两处都需要发现问题、核查依据、检验结论和提出有理由的建议。

## 当前实现提供了什么，缺口在哪里

当前 `doc/extensions/skills/story/phases/story-write.md` 已有决策准入要求、十一类议题扫描，以及已定、待定事项的三段式表达要求。因此问题不是完全没有规则，而是缺少从具体事实推导关键判断的清晰过程；分类提醒和格式要求不足以保证发现、论证的质量。

当前待定事项要求“要定的事／可选的做法／建议”，未像已定事项一样显式组织依据。即使补上标题，也仍需说明事实如何支持选项与推荐，否则只是形式完整。

`review-render.mjs` 展示作者写入的 clarification，保留人类审核区。决策发现和论证属于作者的语义工作；渲染器增加字段或段落不能替代它。

## 期望结果

1. 在需求材料、确认范围、已有决定和相关工程事实相同的条件下，关键决策的覆盖与判断依据应基本一致。允许措辞、顺序和合理合并方式变化；稳定性不要求条数、标题或全文完全相同。
2. 每条事项让评审人读懂：需要决定什么，为什么会出现这个问题，已知事实和不确定之处是什么，建议怎样处理，理由和影响是什么。
3. 有真实取舍时讲清可行选择的主要差异；事实已能确定的事项先查证，不把可查事实包装成人类选择，也不虚构备选方案。
4. 已确认的决定保留确认依据和影响；需要人确认的事项明确尚待决定的部分。不得将已有结论无故重新开放。
5. 改善应来自更有效的发现与表达方法，结合整体简化诉求替换低效要求；不默认增加脚本、字段、门禁、交互轮次或长篇说明。

## 已明确的需求

| 编号 | 决定 | 来源 |
|---|---|---|
| R1 | 发现分三层，各司其职：**遍历**定看的顺序，**撞法**定每一处往哪些方向查，**分类**只在发现之后归档。当前把十一类当遍历顺序（「找议题时对着这十一类过一遍」）是顺序错位 | 用户「分类应发生在发现问题之后」 |
| R2 | 遍历对象是 **story 十章 + spec 逐处，以及它们各自用到的材料内容**，不是只沿业务流程走。作者对需求做过的全部澄清都在这个范围里 | 用户「不是只按业务流程走，而是整体 story+spec 所进行的对需求的澄清内容，都要去看」 |
| R3 | 决策点有**两支**：① 材料没给而产物给了（缺口）；② 材料给了但材料本身靠不住——不是最新、不是最合适、不是最准确 | 用户「材料里有的可能也是一个决策点，因为材料不能保证一定是最新的、最合适的、最准确的」 |
| R4 | 第二支靠**撞**来识别，不靠单读材料：更晚的输入（SR 晚于 RR、界面稿、会议转写）、材料之间交叉、工程事实、规约、材料自己声明的目标。十一类那张表的第三列就是撞法，它编码的是「哪些维度上材料最容易出问题」，这份经验保留 | 用户「这也是之前定分类的原因，给了一些找的维度」 |
| R5 | 「不合适」只认**撞得出来的四种**：工程里没有这个能力（要新建 / 近似 / 模拟）、与既有实现冲突、撞规约、材料自己声明的目标与它给的做法对不上。四条都有可指的对照物；纯主观的「我觉得有更好的设计」不进——那是设计意见，会制造无价值议题 | 用户对 Q2 选择「只认撞得出来的四种」 |
| R6 | 待定事项**每个可选做法各带一句后果**：选它之后范围 / 行为 / 验收 / 交付哪一项会变。建议的理由就是「哪个后果更可接受」。不加「依据」标题——补标题容易被填成「根据材料和工程现状」这类空话；后果写不出差别，说明这不是真取舍，那条不该占评审人的表态位 | 用户对 Q3 选择「每个选项各写『选它会怎样』」 |
| R7 | 每条议题的正文里**指出它是在哪儿撞出来的**：story 哪一章 / spec 哪一节，与哪份材料或哪条工程事实撞的。不新增字段——那句话本来就是评审人要的背景（这条为什么冒出来）。稳定性据此对比**撞点集合**，措辞、顺序、合并方式不同不影响；写不出来源，就是没走 R2 的遍历 | 用户对 Q4 选择「比撞点集合」 |
| R8 | 撞的材料范围 = **已确认特性范围内、且产物实际用到的那些内容**。范围外的材料不撞（它不影响本单产物）；范围内而产物完全没接的，那是内容丢失，由既有的守恒判据管，不由决策发现兜 | 用户「按产物用到的（特性范围内）」 |
| R9 | 撞法的落点是**写完 story + spec 之后回看一遍**，不逐章就地做。回看时对照对象已经完整——跨章的矛盾、spec 与 story 的不一致，只有整篇在手才看得见；逐章做会把它们切断，还要反复进出上下文 | 用户对 Q6 选择「前者」 |

**顺带的一个出口**：第一支的对照（材料没有 + 产物有）同时分出第三种结果——**材料没有、也说不出依据**。那不是决策点，是编造，该删。发现与查编造是同一次对照的两个出口，不另建机制。

**为什么这样改能改善稳定性**：遍历骨架从「清单」换成「产物」。同一需求写出的 story 结构由合同定死，回看的对象每次一致；而对着清单想例子，注意力落点每次不同，命中哪几类靠运气。这直接对上用户「同一个需求多次生成 review.md，结果不够稳定」的反馈。

**范围与守恒的分工**（R8 的直接后果）：决策发现只管「产物用到的地方有没有判断」，不管「范围内的材料有没有被用上」。后者是内容守恒的事，既有判据已经在管。两件事分开之后，决策发现的成本与产物规模成正比，不随材料总量涨。

## 与会议转写澄清的关系

共同目标是模型先审视自己的理解：结论由什么证据支持，是否遗漏相关条件或冲突，哪些事实可以继续查明，哪些选择确实需要人裁决。最终向人交付可核查的结论与必要问题，不交付逐轮自问自答记录。具体实现方式留待设计，能力相同不等于必须新增通用模块或合并两份产物。

Review 面向当前需求与方案，发现影响范围、行为、验收和交付的决策，解释已定事项及待定取舍。会议转写面向会议证据，辨清讨论演变、最终共识、未收敛分歧和对原需求文档的改变。

会议侧继续遵守 [04 分册](../04-会议转写修正需求输入.md) 的冻结边界：字面纠偏不消解矛盾；结论须有会议收口依据；会上没收敛的不能因模型认为某方案更合理就写成会议共识。模型建议与会上已定必须明确区分。

会议侧的人类确认仍并入原有材料关卡的一轮，摆出摘要及确需裁决的事项，每条带推荐与理由；本次关联不增加停等点，也不改变原始文档、确认来源和输入优先级的约定。会议已确认的决定进入后续 Review 时沿用其依据，只有新证据或新冲突才产生新的待确认事项。

## 后续验收需要能判断

- 相同输入下，重要决策是否反复遗漏、出现无依据的新议题，或给出相互矛盾的推荐；输入发生变化时，能否解释对应的决定为何变化。
- 评审人能否仅通过事项正文及必要引用理解并表态，无需再次追问“为什么要问”“根据什么推荐”“不同意会怎样”。
- 分类和段落齐全、字数增长、事项数量一致，均不能单独证明上述目标达到。
- 改善覆盖与表达时，是否减少无价值事项及重复说明，并保持合理的生成和阅读成本。
- 模型是否先完成能够依靠材料和工程事实解决的核查；会议侧是否清楚区分会议结论、模型建议与未定事项，避免把合理推断当成参会人的共识。

## 逐项澄清记录

### Q1：发现决策点用什么方法，替代「对着十一类过一遍」

推荐：沿业务流程走，十一类只做事后归类。

用户结论：**方向对但骨架太窄**——不是只按业务流程走，而是整体 story + spec 所进行的对需求的澄清内容都要看；而且材料里有的也可能是决策点，因为材料不保证最新、最合适、最准确。用户同时指出这一支难在如何识别，并说明当初定分类正是为了给出「找的维度」。

据此重写为 R1–R4：遍历对象扩到 story 十章 + spec 逐处；决策点分两支；十一类的第三列回到「撞法」的位置，不再充当遍历顺序。

### Q2：「材料说了但不合适」这一支，边界划在哪

推荐：只认撞得出来的四种（工程没这能力 / 与既有实现冲突 / 撞规约 / 材料自身目标与做法对不上）。

用户确认：**只认撞得出来的四种。** 已写入 R5。

### Q5：撞的材料范围

推荐：只撞产物实际用到的。

用户结论：**按产物用到的，且限定在特性范围内。** 已写入 R8。范围外的材料不撞；范围内而产物没接的归内容守恒管，不由决策发现兜。

### Q6：撞法放在什么时候做

推荐：写完 story + spec 之后回看一遍。

用户确认：**前者。** 已写入 R9。

### Q4：稳定性拿什么对比

分册已排除比条数、比长度、比分类齐全；而措辞、顺序、合理合并都允许变，所以要另找可比较的东西。

推荐：每条正文里指出来源（哪一章 / 哪一节与哪份材料撞的），两次跑对比撞点集合。

用户确认：**比撞点集合。** 已写入 R7。

### Q3：待定事项的表达，怎么要才逼得出真依据

问题不在缺「依据」标题，在「可选的做法」与「建议」之间断了一环：列了甲乙两种，然后说建议甲，中间「凭什么」没有落点。补一个标题多半被填成「根据材料和工程现状」这种什么也没说的话。

推荐：每个可选做法各写一句「选它会怎样」，依据自然落在后果里。

用户确认：**每个选项各写「选它会怎样」。** 已写入 R6。
