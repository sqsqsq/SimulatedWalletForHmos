## 1. 前提：评估目标是 Extension，不是 Framework

- **Framework 的行为可以作为分析和评估的一个数据**——阶段闭环、宿主调度、模板、门禁时机这些是证据底座、对照基准、归因输入；**但它不是评估目标。评估目标是 Extension**：它的功能、特性能力，以及这些能力按合同应产生的效果。
- 这条边界适用于全部维度（本文生效即约束全部梳理与后续方案）：
  - **过程维**（梳理三/04 引用的 S1–S9 各阶段）：Framework 的阶段行为是 Extension 功能运行的数据底座，各阶段的评估目标是该阶段 **Extension 的功能面**；
  - **产物维**（梳理五已按此重排）：spec/plan 的 Framework 主模板与阶段设计质量是数据，评估目标是 Extension 的扩展面（扩展章、知识投影、义务挂载、埋点、承接、报告协议）；story/review 是 Extension 产物合同，整体是评估目标；
  - **度量维**：Framework 自身门禁/调度产生的信号（如 subject 寻址、阶段报告）是分析数据，不是 Extension 的扣分项或达标项——1.9.9 分析已确立「模型不稳定不是主要矛盾，体系才是」的同类区分（04-稳定性与性能分析/01-分析报告.md C2）。
- 契约依据：AGENTS §2 职责表（Framework 管通用阶段/上下文装配/宿主能力/verifier 调度/阶段闭环；Extension 管需求流程/作者任务/阶段扩展/知识路由/产物合同/确定性辅助能力）；「问题修在最早拥有该职责的位置」。

## 2. 1.10.0 的目标（一句话与展开）

**一句话：1.10.0 构建一个可靠的、覆盖 Extension 全维度特性能力的「目标—效果—评判」评估体系能力，使后续需求开发拥有标准的度量验收手段。**

展开为四个构成：

1. **覆盖对象——全维度特性能力**：过程维（流程主干 S1–S9 ＋ 横切功能域 C1–C6）× 产物维（spec/story/plan/review 的 Extension 面）× 证据层次（结构/语义/真实行为）；粒度到每个特性的「目标（为什么存在）、效果（应达到什么）、评判（怎么判、由谁判）」三元组（→梳理二/三/四/五的行）。
2. **产出形态——体系能力，不是一轮评估**：交付的是可重复使用的评估体系（标准真源、评判手段、判定规则、证据要求、报告形态），后续每轮需求开发与发布**复用同一套**体系验收，不是一次性测试报告或金样翻新。
3. **可靠性标准**：判定可复算或可复核、证据对应当前对象与版本、未覆盖如实披露、不同判定主体（脚本/独审/用户）的权责分明（承接 TEST §6.2 证据分层与 1.9.9 S4 的状态分离纪律：「进程结束、门禁、业务正确、阅读完成和发布就绪分别判断」）。
4. **用途——标准的度量验收手段**：维护链路上的每一次「实现完了吗、设计符合吗、这版能不能收」都有章可循；跨版本可比（历史对比三层级）、稳定性可证（同条件独立重复）。

## 3. 1.10.0 不做什么

- **不直接构建 Extension 的交付功能**：不新增面向消费模型的业务机制特性，不改变使用者看到的行为面（评估体系自身需要的最小载体，由方案阶段论证）。
- 不评估、不改造 Framework 本体（Framework 行为只是数据，见 §1）。
- 不把评估体系做成一次性动作：单轮金样翻新、一次 CLI 复测、一份打样档案都只是体系的组成部分，不构成完成。

## 4. 评估体系服务的角色（目标表述）

| 角色 | 1.10.0 之后他得到什么 |
|---|---|
| **维护执行者** | 知道**如何实现才是对的**：每个特性有目标/效果合同与可执行的验收手段；实现完能自证「符合哪些、未覆盖哪些」，不再靠门禁全绿或一次 Case 成功自证 |
| **维护设计者** | 知道**应该怎么设计**：设计有目标与效果合同可依（三元组先于实现）；知道**设计者实现的是否符合要求**：评审用同一套标准度量，区分「符合设计 / 偏离设计 / 未覆盖」，不以 impressions 判收；知道**应该怎么改**：缺口定位到特性、维度与证据层次，指向责任位置与改法，而不是按最新反例打补丁（1.9.1 P4 问题的体系化解法） |
| 用户（验收方） | 有标准的度量验收手段：跨版本可比、稳定性可证、评分链不再中断（三轴分 1.9.4 起未评、基线未建立的历史不再重复） |

## 6. 目标自身的效果判据（方向性，1.10.0 spec 细化）

以下保留目标效果方向；当前定案的标准结构、证据判法、版本演进和完成边界以[标准变更](评价标准变更.md)、[TEST §6.5](../../../test/TEST.md#65-维护标准与评审)及实施方案00—03为准：

1. 全量特性的每个条目在体系中都有「目标、效果、评判」三元组落位，分母可数、来源可查；
2. 每层证据（结构/语义/真实行为）的判定手段存在且可执行；没有手段的条目**如实标「无手段/未覆盖」**，不填 0、不标不适用掩盖（承接 S4 证据记录格式，04 分册:19）；
3. 体系产出能区分「符合 / 偏离 / 未覆盖」，缺口归位到特性＋层次＋责任位置；
4. 同条件重复与跨版本历史对比有既定章法（承接 S4 三层级与 TEST §6.4 跨轮比较条件）；
5. 评分链闭合：建议分→用户确认→基线建立→跨轮可比（TEST §6.4 既有协议的启用或修订）。

## 7. 与在途工作的关系

1.10.0独立建立全量标准与维护流程，不等待1.9.9收口，不修改Extension产品。1.9.9已有装置与运行记录是首次应用的证据来源，当前需求效力以[统一接续](../../plan/1.9.9/2026-10-21-需求确认与执行接续.md)为准；缺真实运行、目标仓或设备的效果仍未覆盖，不恢复旧强制视觉前置。

本次S1—S3交回沿[实施反馈](../../plan/1.10.0/实施反馈/)读取。标准/流程建立、方法走读、独立使用证据和产品行为分别报告；自查不称独立评审，不能把维护体系建立写成所有Extension能力已通过。
