## 2. spec 的评估标准（Extension 功能面）

**职责边界**：spec 主模板（头部块、§0 术语、§1–§8 业务章，模板在 `demo/framework/profiles/hmos-app/skills/spec/templates/spec-template.md`，B5:17）与术语确认、阶段闭环属 **Framework spec 阶段职责，不进本评估标准**；Extension 拥有并应被评估的是：扩展章 9.1–9.4（技术契约/规约/设计模式/埋点）、知识命中判断与投影、数值来源形态（evidence-rules）、上游 AC 承接写法、拆分边界一致性、判断改动留痕、材料三列表（story 侧，见 §3）。Extension 判据可以**以业务章为证据底座走查**（核知识是否落进设计），但不评估业务章内容质量本身——那归 Framework 阶段。

**目标表述（Extension 功能面）**：overlay 开宗明义「spec 要能交给 plan 去设计：业务关系走得通，**规约的适用判断落在真实的设计上**」（spec-rules:8）——这句就是 Extension 在 spec 上的功能目标：把项目知识落进设计。2.0.3 R1 的 Spec 行（需求.md:70「本施工单位行为、边界……明确｜不合格：抄 Story、只列功能名称……」）评的是 Framework 阶段的 spec 主件质量，**仅作读者背景，不进本标准**。

**评估维度（overlay 现行判据）**：

## 3. story 的评估标准

**目标表述**：「归档叙事件的独立审查：读者拿这一份能不能读懂这个需求」（spec-rules:119）；读者=第一次接触需求的评审人（与 R3 同源，07:18）；树 B 组组合结果「读者无需拼接施工单元，就能理解整项需求、有效设计、风险与交付要求，并追查精确依据」（树:24）。每章读者问题与章级质量维度在章节合同，「按那份合同审，不另立标准」（spec-rules:126-128）。

**评估维度（story_reader_review，现行最完整的产物判据，spec-rules:117-239）**：

- **审查姿态**：「**从原件反查成果**，不只在作者登记过的集合里找错」（:122）——直接对应本轮 C02 反例的根因。
- **十个方面**：背景、范围、方案、流程、功能、异常、验收、交付、图与文配合（每张图三问：图前目的／图后补条件责任结果／图种合不合）、判断与事实分开（:124-126）。
- **跨章八问**：同一条件四处（流程/功能/异常/验收）一致吗；图里每条路径有后续吗；材料打架怎么处理的；附录落点是不是实际对象；上游图每条路径讲到了吗；业务流程章端到端讲清了吗（「判的是总览与局部加起来」）；回看清单逐条核去向；议题依据指得出撞点吗（:199-222）。
- **open 议题逐条判后果**：「各选项（含保持待定）都会有的行为才是共同要求，只属于某一选项的做法或数值出现在正文与验收里，就是替人选了一边。判的是后果，不是有没有『待定』二字」（:131-133）——对应 A02 反例。
- **伪定案判据**：「登记成 settled 的条目拿不出人的表态……要人表态才成立的事，依据指不出那个人在哪说过就是伪定案，它本该是 open。decider 有名字只说明该谁定；转述、计划与作者自己的推荐都不是表态」（:170-174）。
- **会议逐话题核**：「按『话题 → 原话 → 人选的那一项 → 最终结论』逐条核……会议不因为更新就压过文档：没有人的裁决而改了已定口径的，算问题」（:158-163）。
- **页面交互按流程逐页核**（R3 落地判据）：「入口、操作、正常结果、异常提示与去向回界面原图、交互说明与已登记判断看；编了材料与判断都没有的页面……漏了异常去向，或几份材料冲突时替人选了一边，都写进结论」（:152-154）。
- **材料表逐行核**：「每行的贡献是不是那几份原件真给的、采用的是不是当前版本……错版、编造贡献、漏掉的业务内容都由你发现」（:155-157）。
- **blocking/advisory 分界——判内容不判形态**：blocking 清单含「关键业务事实缺失或写反、核心章只剩空泛短句、编造、替人选边、结果未知写成确定、越权改约束、伪定案、义务挂错实体、前后矛盾、超漏范围、验收无法判定、AC 关联不一致、图声称承接却丢关系、实现选型进待确认区、依据只回显条目名称」（:165-189）；advisory 只有「不影响正确、完整与可执行的表达建议……正文里指着文档说话的句子与章开场白」（:191）；「同一件事写成表还是写成段、标题怎么起、几个小节，都不构成 finding；反过来，十章齐全、字数不少而某一章只有空泛短句，是 blocking」（:192-193）。
- **报告契约**：四键明细（blocking_findings/advisories/examined_inputs/unreviewed）**无论结论都写**；「必审输入没读完不能判 PASS 或 WARN」；「零 blocking 时说明你逐章都过了什么，不要只写一句『未发现问题』——那与没审同形」（:227-239）。

**经验基准**：story 侧无 B5 打样（B5 只做 spec，B5:3）；R6 五情景效果定义 Story 行（需求.md:66）「背景/范围说明问题与责任；业务方案解释协作与取舍；流程连起条件、交接、分支和终态；功能说明补局部规则；异常、验收、上线完整；附录供精确查阅｜不合格：正文被接口清单占据、只列参与方无协作、关键行为藏附录、重复堆表」；02 分册 story 问题表（02:46-58：背景缺「本特性在完整需求里承担哪一段」、范围缺「整个需求不做什么」、全篇小节号引用、open 议题替人选边、上线后观察三种写法不一致等）。

**由谁评**：reader review（独审）→ 金样对照（评价域）→ 用户三轴（**产物结果分的对象正是 story+review 组**，TEST.md:524-528）。

## 4. plan 的评估标准（Extension 功能面）

**职责边界**：plan 设计主体——设计章的业务方案、contracts/use-cases 的接口与数据设计、「数据来源、状态持有者、接口、页面接入、调用/返回、清理恢复、文件动作及验证责任相互接得上」（2.0.3 R1 Plan 行，需求.md:71）——属 **Framework plan 阶段职责，不进本评估标准**（该行仅作产物读者背景）。Extension 拥有并应被评估的是：冻结义务（must）挂载到真实实体、模式选型判据、埋点统计点落实（扩展章 9.4）、复用优先判断、评审表态可见、报告协议。

**目标表述（Extension 功能面）**：overlay 的功能目标——「本文件只问『冻结的义务是不是本需求的设计』」（plan-rules:4）；「plan 要能交给编码去实现与验证」的落点在 Extension 面即：知识命中的每条义务在编码里真的有承载、埋点每个统计点真的可兑现。

**评估维度（plan overlay 现行判据）**：

| 维度 | 判据要点 | 级别 |
|---|---|---|
| 义务实体化与可实施 | 「挂着义务的实体在本需求里真的做这件事吗（借挂、夹带普通业务规则都点名），同样适用它的其它步骤有没有漏挂；义务挂在决定结果的业务实体上，不全压在公共封装上」；埋点「spec 的每种适用结果都有结果行，每行指到决定它的分支或回调……以引用规则代替给值……按没落地判」；use-cases「要能追到 contracts 的声明、已核的外部接口与 acceptance 的实际 id；找不到合法绑定按实现断链判，不按措辞问题降级」；「从 spec 与原件反查，不只核作者登记过的实体」；「业务缺口没回 spec 而在 plan 里悄悄定……都是 FAIL」；「缺口按对编码的影响定级：编码要重新决定接口结构、核心业务行为或必要取值的，FAIL」（plan-rules:11-33） | BLOCKER |
| 复用优先 | 「任一类新增能力既没复用登记的入口、也没写为什么不复用，即 FAIL」；「把项目知识文件的原文复制一遍不算依据」（plan-rules:45-57） | MAJOR |
| 评审表态可见 | 每议题人工区须有人表态，「还空着就进入 plan 时判 WARN」；「**归档件与当前产物不一致本身不是缺陷**，记录下来并送到了下游就是合法状态；同一版产物内部自相矛盾才是」（plan-rules:59-68） | MINOR |
| 机械层形态（Extension 面） | 必须设计项五值（事件 ID/内码/结果分类/描述带来源/外码来源——1.9.7 J4 定义，承载在埋点知识＋扩展章 9.4＋plan 门禁）；统计点表列集；义务落点可解析 | 门禁 |

> 边界说明：义务实体化判据「按业务流程走一遍设计章」是 **Extension 检查的方法**（以 Framework 设计为证据底座去核知识义务与埋点是否落地），不是对 Framework 设计质量本身的评估——设计章业务内容的好坏归 Framework 阶段门禁与审阅。

**经验基准**：**plan 无金样、B5 未打样 plan**（02:68-69「全仓没有 plan 金样；银行卡候选样稿只覆盖埋点，与现行五项取值、渠道规则不符」）；J4 判值在 1.9.7 四轮重跑中逐轮波动（→00§5 条目 25）；本轮 K01 反例（AC 错挂传下游）说明「对象都存在，问题是义务的语义绑定；再加编号存在性检查不能解决」（CLI对照:186）。

**由谁评**：机械门（plan post_check）→ 独审（①层 3 判据）→ 用户：**三轴不含 plan 的产物分（缺口，§8.1）**。

## 5. review.md 的评估标准

**目标表述**：「上线要定什么、评审定了什么（**人的决策**，AI 不得覆盖）；与 spec 并列交付，前者 AI 写、后者人写」（SKILL:202）——机器区 AI 渲染、人工区归评审人。

**评估维度（分散在四层）**：

- **议题发现质量**（1.9.1 R1–R9）：「发现分遍历/撞法/分类三层」；每条议题指出撞出来的位置，「只有『根据材料』一类没有指向的话，算没写依据」（与 story_reader_review :221-222 同口径）；「材料没有、也说不出依据。那不是决策点，是编造，该删」；「稳定性不要求条数、标题或全文完全相同」——比撞点集合（→02§2）。
- **选项与建议表达**（1.9.1 R6 + R6 问题表 02:62-64）：待定事项每个选项各写「选它会怎样」；建议段要有方案名与理由（「建议段只写『选择方案 N』」是已登记缺陷）。
- **人工区形态**（1.9.7）：只留「同意 / 需修改 / 暂缓」三态＋修改意见；「填写位不预选任何一项，议题里的建议不等于已选」（README:85）；归档后归人所有、再渲染逐字保留（README:193）。
- **已定/未定与正文一致**（2.0.3 Review 行，需求.md:69）：「每项独立可决定，依据、选项后果、推荐理由和决定责任明确；已定/待定与正文一致，更新保留原话和当前处置｜不合格：合并不同决定、只有选项号、工程选型都推给人、待定处暗选答案」。
- **从未演示的形态**（R6 摸底，02:64）：人工区三态已填、修改意见、评审人原话定案、沿用上一版表态、其他意见区有内容、无待决时的 review、「数据与隐私」「质量指标」两个决策类别——这些是 review.md 评估时「形态是否成立」的已登记对照缺口。

**由谁评**：渲染与人工区保护（脚本）→ story_reader_review 对 open 议题逐条判、伪定案阻断 → plan 阶段 review_gate_acknowledged（MINOR，要「谁还没表态」被看见）→ 评审人表态、用户审定。

## 8. 缺口（事实，供 1.10.0 澄清）
