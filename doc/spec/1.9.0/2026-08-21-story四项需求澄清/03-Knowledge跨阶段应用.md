# Knowledge 跨阶段应用

> 状态：已冻结  
> 需求来源：[全量原始需求记录 §3](../../../plan/1.9.0/2026-08-21-story全量需求与踩坑记录/00-全量原始需求记录.md#3-knowledge-能力重构并在各阶段有效应用)

## 目标

把 Extension Knowledge 收敛为职责清楚且不重叠的规约、设计模式和项目知识，并使相关知识从 Spec
识别、Plan 决定和冻结，稳定传递到 Coding、Review、UT 与 Testing 的真实实现和行为验证。

## 原始需求中已经明确、不重复提问的内容

- 三类知识分别是规约、设计模式和项目知识，职责不能重叠。
- `project_facts` 与 `codebase_facts` 不再形成两套项目事实体系。
- 项目知识必须来自目标工程真实源码、依赖、配置、工具链或明确核实。
- Story 不直接读取三类工程知识。
- Spec 只识别规约影响和设计模式候选，不把候选当成最终选择。
- Plan 作出选择并把结果稳定传递给后续阶段。
- Coding、Review、UT 和 Testing 分别按真实实现与行为消费和验证知识结果。
- 读取、识别、选择、传递和实际应用是不同状态，前一步不能证明后一步。
- 目标工程允许零模式、一个模式、多个现有模式或其它模式，不强制采用。
- README、使用说明、示例、测试夹具和正式运行知识必须明确区分。
- Knowledge 保留原始需求指定的目录结构。

## 已确认结论

### C1：三类知识使用各自的生命周期

- 项目知识：核实 → 启用 → 被相关阶段引用 → 对设计或实现产生影响。项目知识描述工程事实，不存在
  “选用或不选用”。
- 规约：启用 → 判断是否适用 → 落实 → 验证。规约一旦适用于当前需求就必须落实，不能作为可选方案。
- 设计模式：启用 → 识别为候选 → Plan 选择或不选择 → 冻结选择结果 → 实现 → 验证。允许没有候选，
  也允许存在候选但最终一个都不采用。
- 三类知识不能共用“候选、选择、采用”等状态，避免把工程事实和强制规约错误地变成可选项。

确认结果：用户确认。

### C2：三类知识是当前版本的封闭集合

- 当前 Extension Knowledge 只包含项目知识、规约和设计模式三种语义类型。
- 三类分别覆盖工程事实、强制方案和可选方案，在当前需求范围内形成完整划分。
- README、教程、示例、测试夹具、证据和阶段决策属于说明、验证、取证或阶段产物，不形成新的知识类型。
- 当前只允许在三类内部增加领域和知识项，不建设泛化的可插拔知识类型机制，也不设置“其它”类型。
- 将来出现确实无法归入三类的新语义时，必须作为新需求修改分类和版本，不能静默增加类型或勉强归类。

确认结果：用户确认。

### C3：规约不携带目标工程专属实现事实

- 规约只保留目标工程必须满足的要求、适用条件和验证要求。
- 目标工程当前使用的工具、API、SDK、配置、代码位置和既有实现全部归项目知识，并且必须经过目标工程核实。
- 规约需要实现依据时只引用已核实的项目知识，不能复制项目事实，也不能因规约启用而默认目标工程具备
  当前工程的实现能力。

确认结果：用户确认。

### C4：Knowledge 不维护阶段消费路由

- Knowledge 只定义知识内容、适用范围和验证语义，不负责调度各阶段怎样消费。
- Manifest 只声明目标工程正式启用了哪些知识。
- Spec、Plan、Coding、Review、UT 和 Testing 各自在消费规则中定义本阶段怎样处理知识。
- Plan 针对当前需求形成冻结结果后，下游阶段只消费冻结结果中的义务，不回到 Knowledge 重新选择或解释。
- Knowledge README 只作为知识索引和类别说明，不维护阶段消费矩阵。

确认结果：用户确认。

### C5：Plan 冻结结果是下游唯一知识入口

- Manifest 确定性声明目标工程正式启用的知识；阶段不能扫描目录或读取未启用文件补充知识。
- Spec 根据激活清单识别本需求适用的规约影响和设计模式候选，不在 Spec 作最终模式选择。
- Plan 结合 Spec 识别结果和已核实的项目知识完成初步工程方案设计，再从已经进入方案的决定中形成冻结
  结果，明确规约落实方式、项目事实影响、模式采用或不采用的决定，以及实现、Review、UT 和 Testing
  的具体义务，不能只记录知识名称。
- Coding、Review、UT 和 Testing 的阶段入口确定性获得 Plan 冻结结果；结果缺失或不可解析时阻断，
  不允许下游重新扫描 Knowledge、重新选择或静默改变决定。
- Coding 用真实代码证明落实；Review 用真实 diff 复核；UT 和 Testing 用各自层次的实际用例、步骤和
  结果验证行为，不能用知识名称出现代替应用证据。
- 下游发现项目事实变化或冻结决定无法实现时，返回 Plan 更新冻结结果。

确认结果：用户确认。

### C6：Plan 必须在方案设计中实际应用知识

- Plan 不是知识清单或转发层，必须让适用知识实际影响初步工程方案。
- 项目知识必须影响复用、依赖、能力边界或缺失能力的处理；只引用事实名称不算应用。
- 适用规约必须落实为具体设计约束、处理方式和验证义务；只列“已命中”不算应用。
- 被采用的设计模式必须改变方案中的结构、流程、状态、接口或协作方式；只写模式名称不算应用。
- 未采用的候选模式须记录不采用的理由，但不强制为了展示知识而采用模式。
- 冻结结果必须能指回方案中的实际落点；没有设计落点的知识不能标记为已应用。

确认结果：用户确认。

### C7：恢复日志、VOC 和 Chart 三层可观测性知识

- 三层渠道共用业务 `flow_id` 和 `step_id`：日志用于本地调测和完整流程还原，VOC 用于无本地日志时
  远程定位，Chart 用于成功率、时延和终态结果统计。
- 信息与触发密度遵循“日志 > VOC > Chart”，不用固定数量配额判断覆盖质量。
- Spec 只说明业务上需要定位和统计什么，不规划具体日志调用点。
- Plan 按业务流程和步骤设计日志检查点、VOC 关键路径事件和 Chart 业务步骤终态事件，把三层知识实际
  应用到主体方案和可观测性合同，再冻结实现、Review、UT 和 Testing 义务。
- Coding 真实落实三层观测；Review 根据真实代码检查覆盖、密度、字段和失败隔离；UT 与 Testing 验证
  各自层次的业务结果、事件终态唯一性、实际字段、触发时机和时延。
- Debug 可以承载必要调测信息，但所有渠道均排除凭据、访问令牌、会话秘密和密钥；Info、Error、VOC、
  Chart 对受保护业务字段省略或脱敏。
- 日志或上报失败不能改变业务流程、结果、分支或重试。
- 三层覆盖、密度、数据保护和失败隔离属于规约；Demo 已有 Logger、VOC、Chart API 及代码位置属于
  经核实的项目知识，不形成第四类知识。

当前 Demo 事实：`Logger.debug/info/error`、`WalletHAManager`、`WalletHAReportForVOCBuilder`、
`WalletHAReportForChartCBuilder` 已存在并从 CommFunc 公开出口导出；两类 Reporter 采用非阻塞写入，
失败只记录 `Logger.error`，不向业务调用方传播。

确认结果：用户确认恢复完整三层合同。

### C8：恢复两个指定的设计模式

- Story Extension 2.0 必须恢复 `decision-tree` 和 `page-interaction` 两个设计模式；模式原型分别取自
  `E:\Project\AIDefectHelpler\docs\archive\需求开发\extensions\knowledge\design-patterns\decision-tree.md`
  和同目录的 `page-interaction.md`。
- `decision-tree` 负责复杂业务分支编排；`page-interaction` 负责由业务结果驱动的页面交互编排。
  两者是不同适用单元上的可选方案，允许单独采用、组合采用或都不采用。
- 原型目录的 `README.md` 只承载两个模式的索引、适用单元和组合边界，不算第三个模式，也不负责阶段调度。
- 两个模式的名称、适用与不适用条件、方案结构、契约投影和验证要求作为 2.0 的模式基线保留。
  其中具体 SDK、依赖、API、代码位置和既有案例必须按项目知识核实，不能因模式文档存在而假定目标工程具备。
- 两个模式进入目标工程的正式激活清单后只代表可被识别为候选；当前需求是否采用，仍由 Plan 结合适用单元
  和项目事实决定并冻结。

确认结果：用户指定恢复并采用这两个模式原型。
