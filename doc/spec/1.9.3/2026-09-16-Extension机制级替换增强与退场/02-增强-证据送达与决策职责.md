# 02 局部增强：证据送达与决策职责

原则：脚本只把已经有身份的对象（规约编号、图源标记、会议话题与人工 gate、决策 id）在模型做判断的那一刻并列送到；语义仍由模型判。全部是当次装配，不落新的持久文件，不加 Agent 轮次。

## E1 知识判断骨架：命中条件与处置分行送达

**现状**：`hooks/shared/knowledge-use/document.mjs:138-139` 渲出的注释是 `# 强制力 · 约束 · 命中：<when> · 验法：<executors>`，处置列（`handling`）不在其中；`when` 为「同上」时原样渲出。作者判 `applicable` 时既没看到「命中后要给出什么」，也没有被要求写命中条件对应的事实。历史比较：DFX-01 以处置结果（低频）否定命中；DFX-02、RES-01、COMPAT-02 在轮间 T/F 摇摆且理由类别不同。

**动作**：骨架每条注释保留原条目完整含义并分行：`# <强制力> · <约束原文>`、`# 命中条件：<when>`、`# 命中后要给出：<handling>`、`# 验法：<executors>`；条目所在文件有落法附注时加一行 `# 附注：<该条目的附注>`。切分规则：`knowledge.mjs:254-255` 现把「落法附注」整节存为一段文本，改为按列表项切：以 `- **<编号>**` 开头的一项为一条，到下一条同形项或节末为止，多行合并成一行；编号不在册的项报错；条目没有对应项时不渲附注行。不删原来送达的任何一项，只补处置与附注；`reason` 的填法说明改为「写命中条件里哪个事实在本需求成立或不成立」。`validation.mjs::isEmptyReason` 不变（不设字数）。`spec/author.md` 知识判断节同步为同一说法，删掉重复的六条填法里与骨架注释重叠的部分。

**验收**：夹具知识两条（一条命中条件与处置边界清楚、一条 reviewAction）渲出四到五行且约束原文与强制力仍在；`grep "命中：" document.mjs` 零命中；spec verifier 判据 `knowledge_spec_exit_substance` 的 hint 改为「判 reason 说的事实是否属于命中条件而非处置结果」（overlay 一处）。

## E2 评审动作类规约的落点

**现状**：`validation.mjs:206-213` 落点二选一 contract / impact；处置以「（评审动作）」开头的条目（现有 DLV-02）不产生 must，`projection.mjs:65` 只把它渲进「评审动作」清单。两 Case 作者都在 reason 写「已登记进评审」而 `review.md` 无对应议题。`decisions.json` 议题有 id，可被引用。

**动作**：`knowledge-use.yaml` 的 `constraints[]` 落点改为三选一：`contract`、`impact`、`decision`；`decision` 只对 reviewAction 条目合法，值为 `decisions.json` 里的议题 id。`spec/post_check.mjs` 在 acceptance 桥同组核：命中的 reviewAction 条目其 `decision` 在 `decisions.json` 中存在。**只对走 /story 链的需求生效**（`isStoryFeature` 为真时才有 `decisions.json`）；不走 story 的需求，reviewAction 条目仍用 `impact`，但 `impact` 必须写出人工动作的对象与承接位置（谁、在哪份产物表态），不接受「已进评审」一类自证句，语义归 verifier。`renderZones` 的评审动作清单带上议题 id。骨架对 reviewAction 条目的两行填法说明改为这一条。

**填写时机**：`decisions.json` 与 `knowledge-use.yaml` 同在 spec 阶段产出，但成文登记后议题冻结（`refuseIfFrozen`）。顺序定为：作者写 knowledge-use 判到 reviewAction 命中时，先在 `decisions.json` 登记该议题再填 `decision`；登记之后才判到的，走 `reopen` 补议题，不允许为凑 id 提前造空议题。骨架注释与 spec 作者页各写一句这个顺序。

**替代**：作者用 reason 自证「已进评审」的写法；verifier 追查不到的依据。

**验收**：夹具 reviewAction 命中且 `decision` 指向不存在 id 时报错点名；不命中时不要求；非 reviewAction 条目写 `decision` 被拒。

## E3 verifier 输入并列原义与当前判断

### E3a 知识（`hooks/shared/pre_verifier.mjs`）

**现状**：`:103` 写「它是唯一真源，读哪个都行」；fragment 用长段方法说明。`plan/post_check` 只核挂位，verifier `knowledge_obligation_substance` 两轮 PASS 而六态与步骤终态混淆持续。

**动作**：spec 阶段 fragment 改为数据表：每条激活规约一行，列「编号 / 强制力 / 约束原文 / 命中条件 / 命中后要给出 / 附注 / 作者判断（applicable 与 reason）/ 落点」，包含不命中与豁免；plan 阶段每条命中规约一行，列「编号 / 约束原文 / 命中后要给出 / 附注 / 全部 must（entityPath、text、verify）」，复用 `obligationsFromContracts`。原要求本身必须在表里，审查才判得出「步骤终态」有没有被写成「对象状态」这类原义偏离。措辞改为「原知识与仓内事实是审查依据，use 与契约是被审判断」。coding/review/ut/testing 的 `SOURCE_OF_TRUTH` 各自写对（现 `:73` 全部 fallback 到 plan 文案）。

### E3b 会议（`hooks/shared/reader-review-task.mjs:135-146`）

**现状**：只给三个路径。第二轮实跑人选 defer 的话题，结果段仍采用了未选选项的行为，审查未报。

**动作**：逐话题渲染四栏：`notes.finding`、原话（按 evidence 行范围从 `raw.md` 取，同范围只取一次）、人工 gate 的 `options/chosen/basis`（无记录写「未裁决」）、`doc-refresh.md` 对应话题段（按已有版本/话题 id 定位）。审查动作三句：原话哪些确定、人选了什么与没选什么、当前结果的每个确定行为有没有依据。不用相似度，不恢复 effect。

**步骤 4 检查点后补（2026-09-18）**：实跑里四栏送到了但审查没写会议结论，原因是 overlay `story_reader_review` 的输出契约只要求「证据格写逐章过了什么」。步骤 5 在输出契约段加一句：任务书里有「会议材料：逐话题并列」一节时，补述里逐话题各一行（话题 id → 人选了什么 → 当前结果里的确定行为有没有依据），没有这些行与没审同形。不加机械判据。

### E3c 图（`hooks/spec/author.mjs::diagramSection`、reader-review-task）

**现状**：作者页 `:276` 让作者「按行号去读」；审查只拿标记。car 模板在总览处选流程图，跨云返回与回滚关系在最终 story 丢失，审查 PASS。

**动作**：作者页与审查任务书都直接给源围栏内容（`diagramsOf` 已有 `lines`），并把每张源图与 story 里带同一图源标记的图并排；多源合一时列全来源。审查判据写在 overlay `story_reader_review` 一处：参与者、请求与返回、条件分支、结果所有者、失败责任是否保持；图种可换，声称等价承接却丢关系才 blocking。

**体积决定**：接受任务书增长；主上界是**整份任务书**（ai-prompt 原件 + 扩展片段）的字符数：步骤 3 开工前用两 Case 第二轮产物副本各装配一次记下基线（spec 与 plan 各一份），改后同一副本装配的整份字符数不超过基线的 1.5 倍（步骤 3 评审明确：不按扩展片段单独算，plan 阶段片段基线只有 786 字，按片段算任何并列表都过线）。步骤 3 实测 1.16 / 1.08 / 1.07 倍。耗时只作辅助观察（第二轮 auto spec 6.3 分、car spec 与 plan 合计 25.4 分），机器与网络造成的慢跑不触发裁剪。超过时由设计者决定裁剪对象，顺序固定：先把源围栏内容改为「标记 + 首行 + 行数」、再把不命中且非豁免的规约行并成一行清单、最后把会议原话改为行范围引用；实施者不自行截断，也不为达标裁掉命中条目与人工裁决。

**验收（E3 合并）**：用真实产物副本跑 `author.mjs` 与 pre_verifier 装配，输出里三类对象都能看到原义与当前判断并排；源缺失时写「未取得，未验证」而非空对象；记录任务书字符数与本轮对比，不截断材料换绿。

## E4 决策登记的「谁定」与 choice 必要段

**演进史**：8d9d649f（09-14）用户定 Review 按 choice/confirm 分填写位、正文标签「决策点」「依据」、「建议先写选哪项再写理由」；`review.mjs:431` 注释记的五段就是那次定的形态。本条只是把已定形态里「建议」段的存在核起来，不改形态。

**现状**：`story-write.md:209-231` 议题准入只说「表态有后果才占位」；`review.mjs:272-304` 对 choice 只核「可选的做法」是有序列表且每项带 `——`；`:431` 注释写 choice 有「决策点 / 依据 / 可选的做法 / 建议 / 理由」五段但只核一段。car：实现选型（存储介质）进评审待确认，plan 已定；「已定事项」整节为空。auto：choice 无建议与理由。

**动作**：
1. 准入判据加一条「谁定」：改变业务口径或对外承诺的进评审载体；换实现方案结论就变、且不改对外承诺的是实现选型，**不登记为评审议题**——已定的写在 spec §9 技术契约对应行，未定的在 §9 对应行写「由 plan 定」并成为 plan 输入，plan 定案后由 plan 承担。`decider` 字段语义不变（仍是「请谁确认」），不用它记「谁已经定了」。判不准时按「评审人不表态这件事能不能上线」。
2. `review.mjs` 对 `review_mode: choice` 增加一条形状判据：段首为「建议」的段存在且非空（与 `choiceListProblems` 同一定位方式，用 `SEGMENT_HEAD`）。段名常量与渲染标签仍同在 `review.mjs` 一处，沿步骤 1 评审「decision_form 不进合同」的裁定，不搬动。
3. 「已定事项」不造议题填满：已定 = 来源已定或人已裁且有取舍位置；空着时提示写一句为什么本轮没有已定事项，不判错。

**验收**：choice 议题缺「建议」段被点名，confirm 议题不要求；overlay `story_reader_review` 新增一句「实现选型出现在待确认区，或 §9 未定项没有写明由 plan 定」为 finding 的判据（语义归审查）。

## E7 `must.verify` 与执行体映射（评审后撤回，改为不做）

**现状**：`obligations.mjs:22-26` `VERIFY_KINDS = ut / device / both / review`；`VERIFY_BY_EXECUTOR` 只约束「实机 → ut/device/both」。知识执行体是模型 / 构建 / 实机 / 人工，可以多段并列（`constraints/README.md:18`「各段都要」）。

**评审意见与核实**：原方案写「实机 → testing/both；构建 → ut/both；模型 → review；人工 → review」——`testing` 不是合法取值；「构建」是编译与 CodeLinter 证据，不是单测；执行体是并列关系，逐一映射成互斥的 verify 会误拦「模型＋实机」这类正常契约。现有实现已经表达了唯一可机械核的约束（要实机证据的不能只标 review），其余执行体没有对应的 verify 种类。

**决定**：不做。verify 与执行体的语义对应保持现状；知识作者页与 plan-sections 里对 verify 的说明不改。

## E8 归档后的下一步与 status 瘦身（不新增状态）

**现状**：`lifecycle.py::cmd_archived` 只写 `archived:{at}`，`status` 保持 `story_written`；`routing.py:278-296` 归档后 next 恒为 `run_archived`。`status === 'story_written'` 是冻结判据（`context.mjs:179`）、成文登记只一次（`lifecycle.py:89`）、归档前置（`:172`）与 `check.mjs::reached` 的共同依据。

**评审意见与核实**：新增 `archived` 状态会让上述四处消费者各自需要改判，漏一处即已归档件失去冻结保护；而 `archived` 记录本身已在契约里。

**动作**：**不新增状态值**。`routing.next_step` 在 `status == story_written` 且 `contract.archived` 存在时返回 `next: done` 与一句「本轮已归档送审；评审回流走 /story review，补料或改稿先 reopen」；`reopen` 对已归档件的行为保持现状（撤销登记、`archived` 记录保留为留痕）。`status` 输出只在 `next` 落在 spec 阶段那一步时带一行授权声明短句，其余不带；`meetings` 枚举与 `sidecar` 形状只在相应 `next` 下输出。

**验收**：归档后 `status.next == done`；冻结、只登记一次、归档前置、`reached` 四处行为不变（现有用例全绿）；`status` 单次输出字符数记录对比。

## E9 知识内容修正（不改机制，换知识不改代码）

**验收**：`knowledge.mjs::activeKnowledge` 与 `selfCheck` 全绿；`grep -n "同上" knowledge/constraints` 零命中；`knowledge-use.yaml` 的 `manifest_digest` 变化按现有机制提示重判。

## E11 会议交互合一（用户 2026-09-18 裁定，步骤 4 补跑后纳入）

**用户期望**：会议是需求材料的一种，没有单独的会议步骤。问料 → 人交料（可能含会议）→ AI 分析全部材料；有需要人定的会议话题才确认一次，否则按原流程进范围确认。

**现状**（84229f31）：`routing.py:339-367` 把 `await_gate:meeting` 排在第一级材料关卡之前；`scope_step:400-414` 在第一级已定后因 `unconfirmed`（会议判断未经人确认）再摆一次第一级；`decisions.py:52-58` 为此开了「例外里的例外」；第一级 accepted 记录带 `meetings` 版本。实跑里轮①② 模型把两问合成一问，补跑分成两问，行为随模型。

**动作**：
1. `routing.next_step` 顺序：`await_gate:material_scope`（第一轮无条件）→ `import_materials` → 读会链（`fix_meeting` / `refresh_meeting` / `read_meeting`）→ **`await_gate:meeting`，仅当 `pending_asks` 非空**，一次停等把全部话题列出（要问的带选项与推荐，不问的一句摘要说明按会议采纳）→ `read_meeting`（写 `doc-refresh.md`）→ `run_analysis` → `await_gate:scope_decision`。
2. 退出：`scope_step` 的 `fresh`/`unconfirmed` 重摆；`decisions.py:52-58` 例外里的例外；`decisions.py:136-141` 第一级记录的 `meetings` 字段；`meetings.py::unconfirmed`；SKILL/规则页里「会议判断与第一级同一轮摆」的说法。
3. `decide --gate meeting --item` 逐话题不变；同一次停等内多次 decide。
