# lite 轻量开发

2026-10-27，维护设计者。版本记录为 2.5.0，来源是本次会话用户诉求及 clarify Q1、Q3、Q4、Q6、Q8 的明确答复。主要需求已确认；本文件不决定具体实现和开工时间。

## 1. 问题与目标

完整 Framework + Extension 用于小需求时，必需输入、设计与过程产物、交互及验证组织可能使成本超过实际改动需要。直接 vibecoding 又难以稳定获得必要方案设计、UT、真机测试和代码检视。

lite 面向希望集中处理一个小需求或问题的开发者，降低从提出到可交付结果的单任务闭环时间与人工投入，同时保持与改动相称的质量保障。效率收益应在一个任务上可获得，不要求开发者并行管理多个任务。

用户举过发布前要求一小时、完整处理可能三小时的例子，随后明确“一小时只是举例，不要设成固定时限”。本需求不设一小时或其他统一时限，也不以减少文档数、工具次数或阶段数单独证明成功。

## 2. 已确认需求

### L1 适用任务与起点

覆盖从零开始的小功能新增、局部行为调整和明确缺陷修复。判断依据是需求是否清楚、影响是否可界定、验证是否可完成；不只按文件数或是否跨模块判断。尚未给出机械复杂度阈值，本 Spec 不代拟固定清单。

初期不考虑从外部接手已有开发进度的复杂场景。正常 lite 工作中已完成的调查、有效结果及受阻现场应保留，不能把恢复本次任务等同于被排除的中途接手产品能力。

### L2 必要设计与输入

保留指导实现所必需的简短方案和验收说明，项目事实、知识和有效业务约束仍须应用。缺少影响业务承诺、实现正确性或验收的决定时，先澄清缺口，不能以轻量名义猜测。

减少无必要的输入准备、重复读取、重复确认、过程产物及维护负担。具体资料组织和机器内部表示留待设计，不预先指定一个模板、文件数量或新的状态系统。

### L3 默认交付范围

默认不要求完整 Story／Review 业务送审资料；有明确送审要求时，再承担相应交付。这里的 Review 指需求送审的人工议题载体，不表示免除代码检视。

正常交付包含可理解的必要方案与验收说明、代码改动、适用的测试和检视结果，以及仍未完成的事项或风险。已有有效依据可以复用，不为满足流程名称重复生产材料。

### L4 必要质量保障

代码检视作为常规要求。UT、真机测试按改动影响确定必要范围：纯计算逻辑与页面交互可有不同验证重点，不机械要求每次执行完全相同的检查。

不适用要说明原因；适用但未执行明确为未验证。设备、工具或输入不足不能被解释为业务检查已通过，不能以“lite”降低本次必要验证要求。发现问题后按实际授权处理，修复后的结论对应修改后的结果。

### L5 范围扩大与受阻处理

调查发现新的关键业务决定、验收冲突或明显扩大影响时，保留已有调查与有效结果，说明新增复杂性及影响，由用户选择缩小本次范围或转完整开发。不能静默降低验证，也不能未经决定扩大为完整项目。

必要验证尚未完成时，可以交回现有代码与证据，但结果保持待验证，不称 lite 已闭环。已授权内的普通执行问题按既有恢复责任处理，不为每个普通步骤重新询问。

### L6 闭环终点

闭环到形成可供审核合入的结果：问题或需求已完成，必要的编译、UT、真机验证和检视按适用范围完成，发现的问题已处理，剩余风险与未验证项清楚，代码与简短交付说明可供审核。适用且必要的验证没有完成时，不满足该终点。

committer 审核、合入、发布和对应等待由团队既有安排承担，与 lite 自身的处理时间分别说明。生成代码、某一项检查通过或模型宣布完成均不能独立代表闭环。

## 3. 使用场景与完成判断

| 场景 | 预期行为与结果 |
|---|---|
| 明确预期的普通缺陷 | 取得必要依据，形成相称的修复思路，完成修复和必要回归；不为此补造完整需求送审资料 |
| 边界明确的小功能或局部交互 | 将预期、影响和验收讲清，完成必要设计、实现与验证，形成可审查结果 |
| 影响涉及局部跨模块 | 不因跨模块本身自动拒绝，核依赖和验证是否仍可界定；必要知识和责任保持 |
| 发布前单一阻塞问题 | 用户专注该问题即可获得效率收益；不要求同时启动其他任务来解释“更快”，不设固定一小时承诺 |
| 发现新的业务争议或影响扩大 | 交代现有结论与新增事项，用户决定缩范围或转完整路径，已取得的有效工作不丢失 |
| 必要设备验证受阻 | 如实交回受阻项和已有结果，不能签完整交付；不适用与未执行分开 |

## 4. 验收与保持

| 条目 | 前置与触发 | 应取得的结果与证据 |
|---|---|---|
| LA1 单任务收益 | 同一类且输入、目标、环境与必要质量要求可比较的小任务 | 比较闭环时间、人工实际工作、交互与返工；说明节省在哪里。等待与执行分开，不以并行任务数量代替收益，不预设比例 |
| LA2 最小必要交付 | 从零新增或修复，用户未要求业务送审 | 必要方案、代码与适用证据足够审核合入，不要求完整 Story/Review；减负没有丢弃有效约束和设计依据 |
| LA3 质量适用性 | 不同改动需要不同验证 | 适用、不适用、失败、未验证可区分；必要验证完成才闭环，真实执行证据可回查 |
| LA4 范围变化 | 实际影响超出轻量预期 | 新增影响说清，有效成果保留，由用户作范围选择；没有静默扩权或降要求 |
| LA5 完成边界 | 任务交回 | 代码和检视对应当前修改，必要问题及验证已处理；committer/发布等待单列，不用阶段状态代签效果 |
| LA6 平台与原能力 | 在已具备平台条件的组合中使用 | 平台结果与未覆盖范围真实表达，知识、授权、安全落盘、恢复及正式交付义务保持；未就绪平台不假签 |

能力事实与真实缺口见[共同调查](../01-现有能力与讨论依据.md)。已有按义务选择阶段、独立 UT/设备验证等能力优先复用；本版不要求恢复已退役的 change-lite，不要求另建轻量框架。正式接口、记录形式和执行顺序由后续 Plan 在固定基线上定案。

本轮未运行产品验证。人工推演只能支持目标可理解，不能证明实际提速或质量保持；实际内网交付须验证，标准绑定按[本版标准准备](../评价标准变更.md)。

## 5. 讨论与修订依据

### 原始诉求与已有共识

早期用户提出完整能力用于小需求代价太大，希望取得“必要的最小化的方案设计、UT和真机测试、代码检视”，相比全量更快、相比 vibecoding 更可靠。[共建记录](../../../project/2026-10-20-Maison共建讨论/03-逐轮确认记录.md)已确认减少执行时间、输入、产物与维护负担，初期从零开始，三平台为共同目标。

本轮用户要求先核 Framework/Extension 已有能力再澄清，纠正了把独立能力假定为完全缺失的风险。调查显示现有维护路径、独立测试与动态义务可复用，但不能据此称从零轻量交付已成立；实现取舍没有在需求阶段预定。

### Q1、Q3、Q4、Q6 的明确答复

用户同意：lite 默认不要求完整 Story／Review 业务送审资料；覆盖小功能新增、局部行为调整和明确修复；检视常规执行，UT/真机按适用范围；影响扩大时保留成果并由用户选择缩范围或转完整开发。L1—L5 承接，具体流程机制仍未选择。

### 并行与单任务时延的争论

用户提出两种声音：一方认为应并行运行多个需求提高效率，另一方指出普通开发者上下文切换负担高，发布阻塞问题需要自身快速闭环。助手区分多任务吞吐量、单任务闭环时间、人工投入和质量；这些解释不能替代真实成本证据。

用户随后明确：“1小时只是举例，不要设成固定时限。lite重点是降低单个需求或问题的闭环时间和人工投入，同时保留必要的质量保障，不能靠要求开发者并行管理多个任务来替代。”该决定落实为目标、L4 和 LA1，不将并行调度纳入本版解决方案。

### Q8 的终点确认

用户同意闭环到可供审核合入的代码与说明，必要验证和检视完成；适用且必要的验证缺失时仅为待验证；committer 审核、合入和发布等待单列。L6 和 LA5 是有效终点，不将人工合入耗时算作已由 lite 自动解决。
