# review 增强与优秀 Skill 能力吸收

2026-10-27，维护设计者。版本记录为 2.2.0。本文承接开发者检视、三层职责及内网能力吸收的讨论；已确认使用要求、用户提出的方向和候选架构分别标明，不将示例子命令写成已定接口。

## 1. 问题与两个使用者

代码可能来自完整 Framework 开发、vibecoding、人工或其他工具。开发者需要统一的检视入口，对实际变更应用通用能力和业务要求，完成授权范围内的问题处理，交给 committer 可核实的结果。

内网另有优秀检视工具或 Skill，不同业务有不同规则诉求；用户无法提供这些原件到外网。业务或扩展维护者需要在内网直接利用模型分析和吸收其长处，并持续维护增强能力。不能将反馈吸收的必要前置设为人先总结全部方法、再向外网提供原件。

两类任务分别是当前代码的运行态检视，以及检视能力自身的维护态诊断与改进。二者可以协作，但对象、授权和完成结果不同。

## 2. 已确认的运行态需求

### R1 统一入口与开发来源无关

从 Framework 提供的统一 review 入口受理实际 diff、提交或指定代码范围，结合必要业务说明、接口、调用者和项目规则检视。已有 Spec/Plan 等依据可复用，缺少时不强制补建完整开发流程，也不从实现反推需求。

已承担正式交付义务的任务保留其适用义务，不能借独立入口绕过。用户明确要求的覆盖范围、实际已读范围和无法判断的部分须说清。

### R2 检视深度与人工责任

AI 应检查根据代码、需求与有效规则能够判断的问题，包含适用的业务逻辑、异常、并发、恢复、安全、性能等 DFX。不能将深层问题整体留给 committer，只检查表面规范。

发现给具体触发、影响、位置与依据。需要业务背景、架构取舍或实际运行才能确认的部分，明确依据缺口和人工关注点。committer 聚焦需人工审查、权衡和合入裁决的内容；AI 的“通过”不能代替这些责任。

### R3 只审与授权修复的终点

用户说“检视这次改动”，默认只审不改，交付发现、建议和未验证部分。用户明确要求“检视并修复”时，在授权范围内修复并复核，给出已处理、未处理、残留风险和验证结果；普通问题不逐项重复确认。

修复改变业务承诺、扩大范围或遇关键决定缺失时请有权人决定。复核对应修改后的实际代码，不能沿用修改前结论。未执行的编译、设备或其他检查保持未验证。

### R4 面向开发者与 committer 的交付

保留可交给 committer 的简短结论，说明审查对象与范围、有效发现和依据、已处理与未处理问题、残留风险及未验证项。具体文件和格式由后续设计决定，不强制补做 Spec/Plan 或套完整正式阶段报告。

结论帮助开发者处理问题、帮助 committer 集中判断，不以报告存在、问题数量或工具 PASS 数量单独证明有效。已有单独审查和报告入口见[共同调查](../01-现有能力与讨论依据.md)，不重复建设。

### R5 业务规则及指定能力的扩展

业务团队独立维护本业务规则、有效事实与范例，日常更新不要求修改或重新发布 Framework，公共产品升级保留这些内容。统一入口能够使用适用业务规则，而不是只接受 Framework 开发时形成的契约义务。

首批已确认目标为独立检视与业务规则消费；其他检视 Skill、静态工具先选具体对象验证接入，不承诺任意工具都能自动加载。新增能力吸收方向见 §4，其是否与首批同批交付仍待定。

同一规则保留权威来源，复用现有工程惯例或知识位置；通用代码规范、业务知识与专项方法按其实际所有权归属，不为 review 另复制一套同义规则。具体承载和消费接口由 Plan 核实。

## 3. 三层职责：已纳入需求的边界

用户“基本认可”三层分析，并明确要求将三层职责和优秀 Skill 反馈吸收纳入需求。下表是逻辑职责，不是已定物理目录、仓库或多层加载协议。

| 部分 | 负责的结果 | 边界 |
|---|---|---|
| Framework | 统一 review 入口、通用检视方法与执行协作、授权边界和整体结论 | 平台工具链沿既有 Profile 职责；不内置各业务规则，不以扩展自报通过代替整体结果 |
| Extension 能力层 | 可复用专项方法、既有 Skill/工具的接入及知识应用 | 当前 Story Extension 是实际产品之一，但独立 review 不应被强制绑定完整 Story 流程；不复制影子 Framework |
| 业务定制 | 当前业务事实、规则、适用条件、项目范例、能力选择与内部依赖 | 由业务维护，不通过重抄整份公共 review Skill 承担日常定制 |

能力从哪里发布与逻辑职责不同。方法适用于多个业务，并不意味着必须进入外网 Framework；能通过公开扩展职责承担的内容，可以形成内网共享能力。该方向来自用户随后提出的内网独立吸收场景，具体交付组织仍待设计。

## 4. 内网诊断与吸收诉求：方向及待定边界

### 4.1 用户提出的两个输入场景

| 场景 | 期望分析对象与结果 | 当前确认程度 |
|---|---|---|
| 当前会话中人对检视意见有反馈 | 模型结合原发现、代码/依据及人的反馈，反思漏检、误报或不实用意见，指出当前 review 能力的问题 | 用户明确提出的场景，需纳入需求讨论；不是收到反馈就自动认定人说法正确 |
| 指定一个优秀 Skill | 模型在内网直接读取它，比较与当前能力的重叠、长处、依赖和限制，判断可用于自身优化的部分 | 用户明确提出的场景，外网无需取得内部原件；具体读取范围和输出终点待定 |

用户以“review 诊断子命令”及“doctor”举例，并明说“不一定是最终目标”。需求保存场景与目的，不批准命令名、子命令拆分或一个新的通用诊断平台，也不等同调用维护 Skill 的现有 doctor 命令。

### 4.2 模型直接分析与内网持续增强

用户提出独立能力入口，由模型直接分析内部优秀检视 Skill，可作为内网 Extension 或业务知识集成，让外网正常演进、无需感知每次内部更新。本轮按该方向记录：维护者提供目标、材料位置和必要决定，模型承担具体阅读与比较，不依赖人工先提炼 Skill 精华再转述外网。

可能吸收的价值包括可直接调用的执行能力、可跨业务使用的专项方法、业务规则或项目事实。能够直接利用的能力不必全文复制；只有有明确收益和适用依据的内容才考虑提炼。具体内部 Skill 尚未核读，不能预置其先进性或承诺所有对象都能接入。

内网原件、内部实现与派生成果留在内网。通用问题可沿已允许的人工分析与转述方式反馈外网，但这不成为每次内网能力增强的必经路径，也不被解释为允许原始代码、日志、文档或内部设计外传。

### 4.3 诊断与应用的责任界限仍须定案

方向是形成可用的增强能力，而非只积累诊断报告。一次诊断具体停在建议、候选改动，还是在显式授权下继续本地修订与验证，用户尚未最终选定。不能把助手建议的“首阶段先给建议”当作用户已接受，也不能反过来默认诊断授权包含修改或发布。

一次正常 review 的授权不自动成为更改下一次 review 使用规则的授权。反馈涉及新的业务决定、多个规则冲突或公共接口不足时，应明确责任与影响；未确认的推荐不能静默变成对所有业务生效的规则。

## 5. 架构建议与取舍记录（候选，尚非 Plan）

| 候选建议 | 必要性与预期收益 | 成本、替代及当前效力 |
|---|---|---|
| 来源与运行依赖分开 | 外网能力、内网共享能力和业务规则都可以服务一次 review，避免使用者理解四层继承 | 需明确选用、重复和冲突的责任；相较逐级覆盖链可减少升级耦合。用户已提出复杂度顾虑，尚未明确批准具体组合方式 |
| 诊断面向本工程有效 review 整体 | 发现规则未读、专项能力未用或业务依据缺失时，能改到正确位置，不把所有反馈追加到一个 SKILL.md | 需要识别当前实际启用内容及来源；先复用已有维护和扩展能力，不预设新注册表或状态系统 |
| 直接调用与方法提炼分开 | 工具已能执行就复用结果，方法有价值再提炼，降低复制与同步成本 | 调用、适配和方法有效性需分别验证；不能承诺任意格式、宿主或工具无成本接入 |
| 同一职责有明确承担者 | 补充与接替分别说明，减少多个 Skill 对同一对象重复检视或结论互相覆盖 | 不将配置加载顺序等同业务约束优先级；具体冲突裁决和覆盖能力尚未定案 |
| 结果综合与验证 | 合并重复发现、保留来源，解释冲突和未执行项；增强价值由有效发现、误报、人工工作和成本综合判断 | 不能把多个 PASS 拼成整体通过；也不为每个来源额外制造一套报告。汇总与验证方式待设计 |

以上候选不要求新增四个产品层、独立仓或包管理平台。Framework 的扩展点不足时先形成准确缺口，不默认通过修改内网 Framework 发布件另开核心分支。

诊断实例的候选判法：人反馈“这是本工程要求，不是重复实现”时，先核有效约定。约定已存在但未读到，调查读取与应用；确属业务已定而未记录，建议回业务真源；方法错误，回对应方法；依据不足则保留争议。不能把一句否定变成永久豁免。

## 6. 场景、验收及证据边界

| 条目 | 前置/场景 | 应得到的结果与证据 |
|---|---|---|
| RA1 独立检视 | 无完整 Framework 开发资料的真实改动 | 按实际范围和必要依据检视，缺资料如实披露；不补造 Spec/Plan，不缩成只读 diff 摘要 |
| RA2 深度与业务规则 | 有适用业务规则、异常或 DFX 关注 | 判断能回查代码和规则，发现触发与后果具体；缺证据的人工关注点清楚，不因工具通过宣称全范围正确 |
| RA3 修复授权与复核 | 只审，或明确授权审查并修复 | 前者不擅改；后者在范围内处理并按修改后的代码复核；扩大业务承诺时取得决定 |
| RA4 committer 交接 | 检视结束 | 有可保留的简短结果，能理解审查对象、问题处理、风险和未验证范围；不靠报告存在签效果 |
| RA5 业务维护与扩展 | 业务更新规则或启用具体专项能力 | 业务内容保持唯一来源，公共升级保留；规则在正常入口实际影响判断，未执行或受阻可见，不只验证声明登记 |
| RA6 三层边界 | 通用、专项与业务内容共同参与 | 不强迫走完整 Story 才能独立 review，公共与业务责任可说明；未将同一职责无依据复制到多个位置 |
| RA7 反馈诊断方向 | 内网当前会话有反馈且对应原对象可取得 | 模型按原结论、反馈和依据分析，区分规则缺失、未取得、方法不足、执行偏差与未知；不要求人先完成诊断，不把反馈自动判真 |
| RA8 指定 Skill 吸收方向 | 内网可读取指定 Skill 或工具说明 | 给出可复用价值、适用前提、已有重叠及归属；不适用或证据不足可成立。若届时授权范围含修订，须经正常 review 入口证明实际使用效果，不能以读过或登记过代替 |

RA7/RA8 的完整交付终点、首次支持对象和是否同批实现，依 §8 定案后固定；本表不预先批准自动写入。测试既看有效发现也看误报、重复和成本；不以发现更多问题或增加更多规则单独验收。

三平台支持可分批验证。使用模型名称只表达内网环境水平，不增加逐型号门槛。后续须在内网真实使用验证；本次只有源码/合同调查，没有新增运行证据。标准与角色边界见[本版标准准备](../评价标准变更.md)。

## 7. 讨论与修订依据

### 7.1 原始 review 诉求及基础能力校正

用户早期希望利用业务仓已接入的 Maison review，覆盖完整框架与 vibecoding 开发，由开发者本地检视，让 committer 专注方案、业务隐患和 DFX；进一步支持其他检视 Skill/静态工具与业务规则。已有共建记录见[共同依据](../01-现有能力与讨论依据.md) §4。

本轮用户要求先查已有能力再 clarify。调查确认固定发布件已经有无 Feature 的 review、项目惯例和独立报告路径；不能把这些描述为全新缺口。当前重点转为实际使用闭环、知识与规则消费、交接和效果，具体错配留待设计核实。

### 7.2 Q2、Q5、Q7 的明确答复

Q2 用户同意保留可交给 committer 的简短结论；Q5 同意 AI 也检查有据可判断的业务逻辑和 DFX，人工处理需要背景与权衡的部分；Q7 同意只审与授权修复分开，复核对应修改后的代码。R2—R4 承接，不产生自动提交或发布权限。

### 7.3 从接入清单纠正为三层职责与反馈吸收

用户补充内网有不同工具/Skill、业务有不同规则，希望统一入口并汲取优秀 Skill 长处，但无法提供原件。助手起初追问必查清单，用户纠正“其实是讨论关于review。framework extension 业务定制这3部分的架构设计问题。以及如何实现对优秀skill的反馈吸收能力”。随后用户基本认可三层分析，并要求纳入需求。

处理为 §3 的逻辑职责与两个使用者场景。Framework 负责统一执行及结论，扩展提供专项能力和知识应用，业务维护自身事实与规则；具体物理分层与流程没有因此定案。此前关于业务指定必查项的提问没有得到单独答复，其决定权与受阻处置仍在 §8 保留。

### 7.4 从人工转述改进转向内网模型直接吸收

助手曾建议先由人工反馈形成改进建议，用户提出：“不要靠人工反馈，而是由一个独立的能力入口，直接让模型进行分析，并可以作为内网的extension部分来集成，这样外网不用感知，正常演进，内网extension或者业务知识持续扩展增强”。

这里用户改变的是获取和吸收方法的方式，不是取消人的目标与授权责任。§4 保存模型直接读取内部材料、内网持续增强的方向；人工转述只继续服务确有必要的外网通用问题，不作为每次吸收的前置。通用方法有价值也不强制迁入外网核心。

### 7.5 诊断子命令示例与四层复杂度顾虑

用户明确“举个例子，不一定是最终目标”，提出 review 诊断子命令从当前会话获取人对检视意见的反馈，反思当前技能；或指定一个 Skill 分析哪些可用于自身优化。用户同时担心形成“framework层 外网extension+规则层 内网extension+规则层 业务extension+规则层”后依赖复杂。

助手建议区分来源/维护归属与运行依赖，让多个来源服务目标工程的一次 review，避免自动成为四层逐级继承；诊断面向当前有效能力整体，按问题归属形成改进。该简化建议尚未得到单独确认，保存在 §5，不将四层链或组合方案写成已定实现。

### 7.6 本次成文

用户调用 spec，明确要求将 lite 和 review 的相关诉求、讨论与方案记录在 2.2.0。本次承接已确认目标并保留候选建议和未决，没有进一步访谈、修改产品、运行真实检视或提交 Git。文档自查不能代替独立评审或内网效果验证。

## 8. 未决及其影响

| 未决 | 当前边界与取得方式 |
|---|---|
| 诊断入口及任务形态 | review doctor 只是用户例子；设计者按两种输入场景和既有能力提出最简单方案，不预先确定命令或新平台 |
| 自动应用、候选修改与发布 | 用户希望可集成为内网扩展，但尚未规定一次诊断默认是否写入。设计者需明确建议、候选、应用/验证各自授权和完成结果，涉及用户承诺时继续澄清 |
| 多来源内容的补充、接替和冲突 | 三层职责已纳入，四层继承复杂度已提出；具体组合与优先级尚未定案，不用加载顺序默判业务冲突 |
| 业务必查项的决定权 | 先前提问未获明确答复；不得将强制清单、失败阻断或任意跳过写成已确认制度 |
| 首批吸收对象和交付批次 | 原已确认首批为独立检视与业务规则；新增维护态方向未确定是否同批。内网维护者在允许环境选择实际对象和材料，外网不要求原件 |
| 实际效果与依赖 | 某 Skill 的价值、工具可用性、规则更新及框架升级影响均待真实证据；模型输出新规则不等于有效增强 |

这些未决限制维护态吸收和组合架构的具体 Plan，不抹掉运行态已确认需求，也不妨碍本次完整记录讨论。
