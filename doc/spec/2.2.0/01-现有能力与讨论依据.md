## 2. lite 的已有能力与缺口

| 方面 | 已核事实 | 对需求的影响 |
|---|---|---|
| 按义务选择工作 | P: `workflows/obligation-driven.workflow.yaml`、`docs/concepts/skill-contracts.md`、`harness/scripts/utils/execution-scope.ts` 按终点、有效输入和未满足义务确定范围，允许复用已有设计/验收 | 不必把所有请求固定跑完整阶段；但“已有设计可以复用”不证明从零小需求已轻量化 |
| 维护与新设计 | P: `templates/AGENTS.md.template` 先查已有依据；恢复明确预期的普通 bug 按维护处理，新增或改变预期与设计决定承担设计职责 | 小功能新增不能仅套用已有 bug 维护结论；本版需取得从零小任务的实际效果 |
| Plan 与 Coding | 已有正式设计、契约与编码路径；P: `skills/feature/plan/contract.yaml`、`SKILL.md` 仍有验收前置和较完整产物要求 | 不能从可裁剪阶段推定必需输入与过程产物已达到用户期望 |
| 独立 UT | P: `skills/feature/business-ut/SKILL.md` 支持只设计用例、运行既有测试及新增/修改测试；简单函数不强制制造完整复杂流程资料 | 能力可复用，实际执行、预期来源、失败处理和授权边界仍须保持 |
| 独立设备验证 | P: `skills/feature/device-testing/SKILL.md` 支持即席操作、观察、验证修复和正式阶段；`request-phase.ts` 核执行与证据 | 导航成功或截图存在不等于业务通过；缺设备或 provider 不可伪报已验 |
| 平台 | 所核发布树和上游快照内有 hmos-app、generic；hmos 有相关编译、UT 和设备执行支持，generic 禁用部分执行阶段 | 未见已交付 Android/Web 执行 provider，不能将目标平台写成已支持 |
| Extension | [Story 入口](../../../extensions/skills/story/SKILL.md)服务材料、范围、蓝图、成文与送审；[知识入口](../../../extensions/skills/story-knowledge/SKILL.md)按蓝图或 Feature 取得任务 | 需要保持知识应用效果；尚不能认定省掉某些产物后整条轻量知识链自然成立 |

历史 change-lite 是单模块 `change → coding → exit`、单份 change.md、出口编译/lint/范围/条件 UT，没有覆盖本轮所需的完整检视和适用设备验证。U 的 `8a523b70` 已删除旧 change/exit checker 和专用 Skill/schema，旧 track 不再决定新流程；`a32ad1d0` 又统一新完整交付的 run 内核，会话 next/report 与无人值守是不同使用方式。这些是上游未接入差异，不等于本版要扩大到 headless/goal，也不作为恢复旧 lite 的依据。

## 3. review 的已有能力与缺口

| 方面 | 已核事实 | 对需求的影响 |
|---|---|---|
| 独立入口 | P: `skills/feature/code-review/SKILL.md` 已支持 diff、提交、指定文件且无需 Feature；普通审查不要求 Spec/Plan、request/facts 或完整报告。该入口与所核上游版本一致 | 无 Spec/Plan 检视不是全新能力，不能重复立项 |
| 审查方法 | P: `skills/reference/code-review-workflow-detail.md` 要求确认基线、读代码和调用链、追数据与异常、报告具体触发和后果 | 方法存在不证明真实漏检/误报效果；仍需业务材料与实际证据 |
| 项目惯例 | P: `docs/concepts/conventions.md`、`check-review.ts` 已消费业务仓维护的 conventions 和适用范例，机器 request 也有覆盖检查 | 可复用入口；工程惯例不是所有业务规则的唯一容器，不能无判断地搬入其他权威内容 |
| 授权与报告 | 默认只审，明确授权可修复；已有无 Feature 的持久机器报告路径，目标变化需对应新对象 | 需要明确开发者到 committer 的简短交付结果，旧结论不能替代修改后的复核 |
| 模板残留 | 所核 `review-report-template.md` 仍预设 Plan、contracts.files 等；generic review 补充也有正式契约范围文字 | 独立审查入口与部分报告指导存在需核的错配；不是所有使用场景都被阻塞 |
| Extension 知识 | [review 作者要求](../../../extensions/hooks/review/author.md)、[post_check](../../../extensions/hooks/review/post_check.mjs)以契约 must/pattern_roles 为依据；当前独立知识任务以 Feature/蓝图身份进入 | 尚未证实无完整开发资料的 review 可以获得同等业务知识应用，不能让使用者为此补走整个 Story |
| 扩展能力 | [Framework 扩展说明](E:/Project/agent-maison/skills/project/extension/SKILL.md)支持 Skill、knowledge、hook、capability、overlay、asset、MCP action 等；phase binding 针对 Feature phases | 声明可用不等于已调度或有有效结果；不能推定普通 review 会自动执行所有扩展，也不能承诺任意 Skill 无成本接入 |

P 中 request/checker 有真实消费者；U 中 request 与 conventions 测试覆盖输入身份、范围、活跃 Feature 保护及规则读取等分支。本次只读测试源码，没有执行，所以不登记通过数或产品效果。

## 4. 共同边界与旧讨论效力

早期原始诉求见[共建现状](../../project/2026-10-20-Maison共建讨论/01-现状诉求与问题.md)，已有确认见[逐轮记录](../../project/2026-10-20-Maison共建讨论/03-逐轮确认记录.md)第四至六轮：lite 从零开始；review 不补完整开发流程；三平台共同目标；首批独立检视与业务规则消费，其他 Skill/工具按具体对象接入；业务规则由业务方独立维护。

此前共建协作方案中的人员、仓库和发布安排属于候选，不作为本版功能实施的授权。2026-10-27 用户明确开始讨论 lite/review 功能诉求，后续有效决定由两份需求正文保存；共建阶段“只谈协作”的当时边界不阻止本轮需求澄清，也不授权直接实施。

本轮仍按源职责修正：Framework 的通用能力缺口交 Framework；Extension 提供的专项能力与知识应用交对应扩展；业务事实和规则由目标业务维护。内网成果不能回传，允许人工分析后转述通用问题，但优秀 Skill 的具体阅读、比较和本地吸收不应以外网取得内部原件为前提。

本文件不决定新调度层、状态机制、通用加载平台、目录协议或工具 API。后续设计复用已有效的能力，先核实际缺口，再讨论必要新增。
