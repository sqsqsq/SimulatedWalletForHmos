# 一个Case看清Extension对五类产物的影响

2026-10-28。选用1.9.9已审定的car-key-sharing/ISSUE-206情景。本文是解释性示范，不是正式金样、不新增业务决定、不要求固定章节/句式/文件数；未运行模型、未生成合法原生CU或蓝图签名。最新CLI中间稿的状态及缺口仍按原评审，不用本文替代。

目的：具体说明整个Extension如何影响蓝图人读稿、CU Spec、CU Plan、Story、Review，而不只讨论知识登记。以下先说**当前实现要求**，再展示**沿已确认2.1.0目标的具体内容**；示范稿不等于现有renderer现在就能输出该呈现。

## 0. 共同输入，不能算成Extension新发明

来源为[test/golden/car-key-sharing/README.md](../../../../../test/golden/car-key-sharing/README.md)及其Story、Spec、Plan、Review。
- 已定：补料、不拆需求；钱包端含卡包钥匙卡片与入口；车辆侧撤销即拒绝，对方设备上的卡片最长48小时收回；退出页面/断网/关闭应用可续办，发出成功/退出登录/切账号清草稿。
- 已定情景：先用公开模拟能力验证，真实接口联调另验；钱包只记录发起、接受、撤销三个流程，分享被接受比例归车云。
- 保持未决：再转第三人、极端断网强制下线、待接受分享能否撤回。
- 旧金样公开的模拟前提：稳定账号身份、可用Asset能力及草稿大小约束；模拟云端有创建恢复/幂等能力，钱包进程退出后仍保存。真实六个车云接口没有完整创建恢复能力，不得写成已存在的正式接口。

为说明CU职责，假设获准的设计交接把这批钱包端工作交给“车钥匙分享端侧”CU；这只是解释范围，不强制实际CU数量/名称。原生已满足Spec义务时可复用，不为本示范强造Spec文件。

## 1. 总体作用：先影响设计，再分别影响表达与落实

| 对象 | Extension实际要求增加或保证的内容 | 不是Extension可以自行决定的东西 |
|---|---|---|
| 蓝图人读稿/其canonical | 真材料与人答、工程现状、知识应用及实体落点、接口转写/来源、恢复职责、配置/埋点等必要专项、独立质询核源 | 48小时等业务值、未决裁决、虚构接口、原生渲染布局 |
| CU Spec | 本CU的行为/边界/验收承接知识义务；必要技术约定及知识解释 | 重新决定整个需求、改变原有未决、复制整份蓝图 |
| CU Plan | 将义务与模式角色落实到实体/方法/存储及验证；统计点有实际负责人 | 凭空声明工程已有封装；偷偷改变共同设计 |
| Story | 作者按业务完整自主成文，图文、条件/异常、验收及技术摘要；资源、当前设计参考、可靠落盘和读者审查 | 为讲顺而填掉未决；要求读者先拼读蓝图才能理解 |
| Review | 从真实议题生成澄清内容与人工填写位，保已有决定与原话、未决和变更关系 | 自动替人填意见；把每条知识/INFO变成新人工批准 |

当前没有做“完全不安装Extension”的A/B实跑。这里确认的是指令/生产/消费责任，不声称这些内容没有Extension就绝不会由Framework作者写出。

## 2. blueprint人读稿：共同设计到底怎样成立

### 当前实现怎样影响它

Extension在component-design前提供原件/人答、项目事实、规约、模式与任务；要求判断写入canonical，应用落到设计对象。原生renderer再把canonical/reader_guide生成component-blueprint.review.md。Extension不直接把人读稿当可编辑真源。

当前“每激活知识一条决定”使知识应用进入decisions；原生渲染器统一展开选择/理由/被否方案，未正确读取knowledge.requirement/outcome时形成空结论，参考区又重复列出。这是已经查明的现状，下面示范的是它应表达的实际设计内容，不是继续扩张这套表。

### 目标内容示范：分享草稿及创建结果

> 分享设置保存在当前账号、当前车辆的草稿中。离开页面、断网或关闭应用后，再次进入可继续填写；发出成功、退出登录或切换账号后不再恢复旧草稿。
>
> 草稿包含接收方账号与发起请求，属于受保护数据。设计将其保存与清理职责交给草稿存储，将发送及创建结果确认交给分享仓储。页面只拿可显示的昵称和打码信息；真实账号仍用于请求，不能用打码值替代请求身份。
>
> 发送结果未知时，保留原请求和幂等身份，由创建恢复职责查询旧请求去向；结果未明确前不再次创建。此能力来自本情景公开的模拟云端前提，真实车云接口尚缺该能力，列为正式开放前依赖，不伪称已对接。

这里包含了设计对象、身份、存储、恢复与外部依赖。不是再写“已阅读隐私规约”。

| 知识/来源要求 | 蓝图中实际改变的对象 | 人读稿应该解释的结果 |
|---|---|---|
| 隐私与隔离 | 草稿存储、显示转换、事件出口 | 敏感草稿受保护，账号隔离，日志/事件不泄漏原账号 |
| 页面交互模式 | 设置页、动作表、交互封装、上下文 | 选联系人后重新取可用权限；页面动作与状态变化有统一协作 |
| 统计要求 | 发起、接受、撤销的尝试与结果责任 | 钱包只报可观察的本端流程；总体接受比例归云端，不在端侧凑分母 |
| 原需求及人答 | 撤销流程、车辆/设备双云责任 | 车辆立即拒绝与设备卡片延迟收回是两种结果，不能用一个“48小时后失效”混写 |

蓝图还须包含完整需求主线、对象关系、契约及验收，不是只写上面这段。接口原始参数、返回和错误依据由必要原生契约及来源转写承载；无依据处保缺口。Story读取的是这一共同设计，不再自行创造另一套方案。

## 3. CU Spec：本单位要实现、验收什么

### 当前实现怎样影响它

知识任务给本CU承接的决定、相关Story表达和知识原文。spec/author要求把应用后的行为写入acceptance，关联知识规则/决定；生成spec.md时，“宿主扩展治理项”解释技术约定、规约、模式和工程事实。本CU不重新判断蓝图共同取舍。

当前实现可能把每项判断又写一遍，2.1.0应保“本单位怎样履行”的内容，退出无信息增量的重复表；实际已满足的原生Spec可不重写。

### 目标内容示范：草稿与撤销验收

> 本CU承担钱包端草稿、发起、接受、管理、撤销及卡包入口。车云决定分享关系状态，车厂云执行车辆钥匙撤销；钱包不自行推算云端成功。
>
> 重新进入设置页时，只恢复当前账号和当前车辆的草稿。创建结果未知时显示确认中并保护原请求，不能把超时作为创建失败后立即重新发送。
>
> 撤销请求生效后，车辆侧立即拒绝该钥匙；对方离线时设备卡片最长48小时收回。“撤销中”不能被解释为仍可使用车辆。

| 验收场景 | 可观察结果 | 与知识/设计的关系 |
|---|---|---|
| 设置中退出页面或关闭应用后重开 | 恢复同账号同车辆的已保存设置 | 续办承诺与受保护持久化 |
| 切换账号后进入同一车辆设置 | 不出现上一账号草稿及敏感信息 | 隔离与清理义务 |
| 发出后结果未知 | 保持确认中；不重复创建；明确结果后按结果推进 | 请求身份与恢复责任 |
| 对方离线时撤销 | 车辆立即拒绝；设备端按48小时边界收回，界面区分两者 | 原业务决定，非Extension自行设值 |
| 查看页面、日志及事件 | 显示按既定脱敏口径；观察性出口没有对方完整账号 | 隐私规约落实 |
| 待接受状态请求撤回 | 不把未决D8写成已支持或已禁止的承诺 | 保留真实未决 |

这些内容回答“要做对什么”。它不应详细列Asset别名算法、每个类方法和所有埋点调用位置；那些归Plan。机器验收条目要可追到相同义务，编号本身不证明验收有效。

## 4. CU Plan：哪个实体具体承担，怎么验证

### 当前实现怎样影响它

plan/author要求适用义务挂到实际契约实体的must，选中模式角色挂pattern_roles；正文说明实际复用、实体承担和验证。埋点进一步落实到统计点与责任方法。缺失实体或只列知识名，后续编码/审查无法取得实际义务。

### 目标内容示范：落实到旧金样已有的设计角色

以下名称来自1.9.9金样Plan的拟实现设计，不表示当前工程已经存在这些类。

| 实体/角色 | 本CU具体落实 | 验证 |
|---|---|---|
| ShareDraftStore | 每账号每车辆一份受保护草稿；保存完整发起请求；按情景约束清理；读取区分不存在、有草稿、不可访问、损坏 | 账号/车辆隔离、关闭应用后重开、清理、读取结果；平台能力另按公开前提验证 |
| KeySharingRepository | 串行处理同账号同车辆的发起与创建恢复；回调核当前账号/会话；结果未知不结算成失败或重发 | 正常、拒绝、未知及恢复链；旧请求不会变成第二条分享 |
| ShareSetupPageInteraction / Operates / Context | 分别承担交互封装、动作表、上下文；联系人变化后刷新权限选项，提交参数来自当前有效上下文 | 模式角色实际协作，非只在文件表写“采用page-interaction” |
| KeySharingErrorMapper | 将错误码转成可显示的安全说明，不直接回显原始message | 已知码及未识别码不泄漏服务端敏感原文 |
| SimulatedKeySharingSource | 按已公开前提提供模拟状态及创建恢复；与真实六个车云接口的缺口分别标明 | 证明模拟情景，不声称真实接口联调通过 |

埋点在Plan中还需明确三个流程的尝试起点、观察到的结果、实际责任方法及去重/结算；创建结果未知与已确认失败分开。统计点由承担该流程的真实方法消费，不能只在附录列名。

这一步回答“怎样履行Spec及共同设计”。若发现真实接口没有创建恢复，不能在Plan偷偷补一个云接口当已存在；保模拟前提和正式开放依赖，设计变化回蓝图。

## 5. Story：给第一次接触需求的人讲完整业务

### 当前实现怎样影响它

Extension自主组织正文、图文、章节及Review议题；配置/埋点等可从设计投影，接口/存储/规约写成业务摘要，完整技术设计随原生参考附件提供。逐章落盘、当前性/资源/原件检查及独立读者审查服务可靠交付，不应把这些过程写进业务正文。

### 目标内容示范：离开设置页后怎样继续

> 车主选择分享对象、权限和有效期后，可以暂时离开设置页。网络中断或关闭应用不会使已保存的设置消失；下次用同一账号为同一车辆发起分享时，可以接着填写。
>
> 发出成功后，这份草稿结束。退出登录或切换账号也会清除本地草稿，新的账号看不到前一个账号填写的信息。
>
> 如果点击发出后没有取得明确结果，页面显示“确认中”。再次进入时先确认上一次请求的去向，不直接再发一份；确认已经创建则展示原分享，确认旧请求已终结且未创建，才允许重新发起。该恢复能力在本情景中由模拟服务提供，正式开放仍依赖真实服务提供等价能力。

### 目标内容示范：撤销为什么仍显示“撤销中”

> 对生效的分享发起撤销后，车辆侧立即拒绝该钥匙。对方设备离线时，设备里的卡片可能暂时还在，但这不表示还能用它开车；卡片最长48小时内收回。管理页以“撤销中”区分车辆已拒绝与设备卡片尚未收回。
>
> 待接受的分享能否撤回尚未确定，不能把这条生效分享的撤销规则直接套过去。

正文不塞ShareDraftStore、must、decision_id；必要接口语义、配置、规约效果和三个流程的统计口径仍可在Story附录查阅。技术摘要不因蓝图已有而删除，但也不复制整套类方法表。

完整Story还要覆盖分享入口、可分享对象/权限/配额、接受、管理、六态、卡包、正常受限、失败/未知、验收和交付边界。上述两段只是展示同一设计如何转成叙事，不能代替全文。

## 6. Review：保留真实需要人决定的事情

**Review不是独审报告。** 它是用户/评审者的议题与决定载体；独审原报告另存，不让作者改写成用户意见。

### 目标内容示范：初段仍待定的议题

| 议题 | 已知边界 | 尚需谁决定什么 |
|---|---|---|
| D2 再转第三人 | 本期原材料明确不作结论 | 需求方后续明确是否支持及权限范围；不能写成“本期禁止”作为既定事实 |
| D5 极端断网强制下线 | 常规撤销和48小时卡片收回已有含义 | 需求方/车厂明确极端长期离线的额外处置，不凭作者补一个强制下线方案 |
| D8 待接受分享撤回 | 当前系统接口只明确生效分享撤销，与产品“随时撤销”存在待对齐处 | 需求方与车云决定是否支持及能力边界 |

本例已定的48小时含义、续办/清理、模拟交付、卡包范围和统计责任，应带原有依据作为已定事项展示，不因2.x换载体再问一次。人工填写位保持由人填写；本文不伪造新运行的人签。

隐私规约、模式角色、报告格式修复和INFO建议不是自动新增Review议题。只有真实业务决定或原生条件要求才问；非阻断建议由作者有据处置。

## 7. 用一条知识串起五份产物

```text
知识原文：敏感数据需要保护与隔离
  ↓ 蓝图：确定哪些数据敏感、谁存、谁清、谁能用
  ↓ CU Spec：本单位必须表现出的隔离/清理行为及验收
  ↓ CU Plan：存储与调用实体实际承担，方法/角色/验证明确
  ↘ Story：用户看得见的续办、切号清理、未知结果和限制
  ↘ Review：只有保护要求与真实业务取舍冲突且需要裁决时形成议题
```

“看到”是动作前拿到真实知识；“理解”是按本需求判断；“应用”是设计对象发生实质变化；“传递”是CU乃至实现取得并履行义务。五处不是五次判断，也不是五份相同规约表。

## 8. Extension其余能力如何影响产物

- 来源导入、会议与人答决定共同输入的效力，不能把产品草稿升格成正式权威或将推荐当人签。
- 稳定来源版本和设计引用使这些产物对应同一版事实；作用是可信，不是让人读正文理解哈希。
- update按实际有权变化修真源和受影响视图，未改内容/人工区保留；本例不构造update金样。
- archive把当前Story、Review、设计参考及正式资源交付并读回核对；不会把“门禁通过”当已经送审。
- usage/stats记录真实开始/完成和成本，不应变成业务文档中的计量章节。
- adapt/install/DSH接线确保真实消费者能取得这些能力，不额外决定本Case业务，也不增加人工批准。
- 自动门禁只证明确定性身份/结构/引用与合同；蓝图质询与Story审查分别核设计和表达；未审、不适用、未验证、通过不可互换。

## 9. 依据和效力

业务前提来自1.9.9已审定金样README及其正文；上表展示类名来自同组plan/plan.md。当前责任依据为extensions/hooks/blueprint/author.md与reviewer.md、hooks/spec/author.md、hooks/plan/author.md、skills/story/phases/design.md和story-write.md，以及实际知识任务/义务消费者。

本文区分三件事：当前机制要求、1.9.9金样情景、2.1.0目标呈现。当前机制中的全激活逐项登记、空取舍展开、不同目录及新增免审批准等，不因本示范被追认；仍按2.1.0 Spec处置。本页没有写入test/golden、没有修改实现，也没有运行模型或生成正式原生工件。
