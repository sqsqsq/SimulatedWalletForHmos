# 两 Case 金样：审核问题与修订合同

2026-09-30，独立审核。对象是历史参考中的 AR90006 三份、ISSUE-206 四份产物及两份 factbase；依据为有效材料、真实决定和选定工程事实。当前结论：不能原样替换正式金样。下列为已核问题，不声称穷尽所有缺陷，也不声称已完成渲染、门禁或实跑验证。

原始文件保持不变，本页规定后续修订责任和复核条件。具体审核结果与本轮规格定案不同：发现错误已经成立，修订后的金样尚未形成或签收。

## 1. AR90006

### G01 面额下调验证被同时写成已定与待定

证据：[Story](../历史参考/原1.9.9/04-稳定性与性能分析/data/golden/AR90006/story.md) 第 139、284、338、376 行；[Spec](../历史参考/原1.9.9/04-稳定性与性能分析/data/golden/AR90006/spec.md) 的 E13、AC-7；[会议原文](../../../../doc/features/archive/Story-Features-20260927-004631/AR90006-update/AR/story-src/meetings/交通卡澄清会记录-0903/23fdc64d/raw.md) 14:07–14:08 与 14:16。

已核矛盾：Story 功能说明说面额下调同样待口径，风险、未决说明及验收却说下调不验证、已经确定。会议原话是“往下调应该不用，这个我回去跟风控确认”，不能仅凭这句升为确定规则；“只改门限不用验证”另有明确原话。

修订：由金样修订者核真实后续决定，取得明确确认才写已定；没有则面额变化分支保持待决，只保留只改门限的已知结论。factbase、蓝图、图文、Review 和验收同步，不以历史稿多数相同推定正确。

复核：任一待决分支不能在别处出现无条件通过标准；每个已定分支有对应真实依据。职责：业务权威决定，金样作者承接，独立审查核一致性。

### G02 创建超时被当成云侧肯定没有签约

证据：[Story](../历史参考/原1.9.9/04-稳定性与性能分析/data/golden/AR90006/story.md) 第 325 行；[Review](../历史参考/原1.9.9/04-稳定性与性能分析/data/golden/AR90006/review.md) D7；[上游 SR](../../../../test/cases/auto-topup/system/SR90006/design.md) §3/4。

已核问题：异常表把创建失败/超时的影响写成“云侧无签约记录”，并写重走验证；上游“没有任何签约记录”的条件是用户未取得授权、尚未创建。请求超时不能证明远端没完成，D7 的协议号复用和重试策略又仍待两端对齐。

修订：分开未获授权、明确业务失败、请求结果未知。未知结果保留待确认状态与当前可证明事实；协议号/重试策略按真实决定承接，不能由作者替业务选择重新验证。沿已定接口明确结果查询/幂等恢复义务，协议未定则登记具体缺口，不凭空新增接口保证。

复核：结果未知不会被显示成确定未签约，也不会因金样固定重试方式引入错误恢复承诺；相关图、异常表、Review 和验收一致。

### G03 清除缓存被解释为云侧未签约

证据：[Story](../历史参考/原1.9.9/04-稳定性与性能分析/data/golden/AR90006/story.md) 第 303 行及异常表；[Spec](../历史参考/原1.9.9/04-稳定性与性能分析/data/golden/AR90006/spec.md) AC-12；[上游 SR](../../../../test/cases/auto-topup/system/SR90006/design.md) §3 的缓存边界。

已核问题：上游说缓存仅用于免网展示、缺失以云侧查询为准；金样却把清数据后的恢复写成未签约展示并重新走签约页。当地缓存消失不改变云侧签约关系。

修订：以真实云侧结果恢复显示，查询未完成/失败时明确未知或不可用，不能推断未签约；仅云侧确认未签约时进入相应流程。同步缓存命中、失效和重新查询的边界，避免陈旧缓存永久遮住云侧停用等变化。

复核：至少核云侧仍生效、已停用、确无签约及查询失败四种输入；“不崩溃”不能代替业务状态正确。

### G08 签约目标与转化率说明使用不同分母

证据：[Story](../历史参考/原1.9.9/04-稳定性与性能分析/data/golden/AR90006/story.md) 第 25 行；[采用版本产品提取稿](../../../../doc/features/archive/Story-Features-20260927-004631/AR90006-update/RR/prd.md) “背景与目标”。

已核问题：“不低于交通卡月活的 8%”被解释成看到入口的用户中完成签约的比例，二者分母不同。相同标题和数值并不证明指标相同。

修订：按材料保留业务目标的总体与分母；入口曝光转化如有真实需求则另立指标和来源，不能共用 8% 目标。流程成功率、业务转化率与端侧统计采样分别说明，不用一组事件自动宣称能算全部指标。

复核：指标名称、分子分母、时间范围、数据来源和责任一致；正文、验收与埋点不存在口径偷换。

## 2. ISSUE-206

### G04 展示脱敏值不能承担接口业务身份

证据：[Plan](../历史参考/原1.9.9/04-稳定性与性能分析/data/golden/ISSUE-206/plan.md) 第 150–167 行的数据模型和 §6 的 selectGrantee/queryGranteePermission/createKeySharing；[上游 SR](../../../../test/cases/car-key-sharing/workspace/SR/design.md) §4.1b/4.2；[MaskUtil](../../../../demo/05-SystemBase/CommFunc/src/main/ets/shared/utils/MaskUtil.ets) 的 maskAccount。

已核问题：选择对象和草稿模型只有不可逆脱敏的账号；下游查询权限/创建分享又需要可识别的对方账号，契约没有保留可用身份或定义换取身份的路径。隐私要求针对页面、日志和事件输出，不能把业务请求所需身份一起丢掉。

修订：把必要业务身份与显示值分开建模，沿输入→查询→草稿→创建说明传递、保留时长和清理；日志/事件/显示继续脱敏。若采用不透明标识，须有真实协议支持，不自行假设存在映射服务。Spec、Plan 和附录同源同步。

复核：合法但显示脱敏值相同的两个账号仍能被正确区分；接口拿到正确对象，输出出口不泄漏敏感标识；不得靠测试只用一个账号隐藏断链。

### G05 草稿、模拟承载的决定状态跨产物不一致

证据：[Spec](../历史参考/原1.9.9/04-稳定性与性能分析/data/golden/ISSUE-206/spec.md) 第 308 行画“草稿落盘”；[Plan](../历史参考/原1.9.9/04-稳定性与性能分析/data/golden/ISSUE-206/plan.md) 第 257 行写内存、杀进程丢失；[Review](../历史参考/原1.9.9/04-稳定性与性能分析/data/golden/ISSUE-206/review.md) D4/D5；[Story](../历史参考/原1.9.9/04-稳定性与性能分析/data/golden/ISSUE-206/story.md) §3.3/6.10。

已核问题：草稿介质同时出现落盘、内存和待定。模拟接口与模拟卡片也已进入“本期承担”及部分验收解释，相关决定仍 open。建议可以提出，但“本工程无现成封装”不能代替允许降低交付范围的真实决定。

修订：将已确认共同要求、候选方案和待决影响明确分开；材料无真实结论时不让下游把一个选项当硬义务。定案情景由真实确认输入决定存储和承载范围。模拟验证与真实联调的完成声明分开，不能从前者推出后者通过。

复核：图、数据模型、生命周期、验收和交付边界一致；原生准入/施工对受影响缺口按真实合同处理；不补虚构人签让正例通过。

### G06 卡片入口组件没有实际接入位置

证据：[Plan](../历史参考/原1.9.9/04-稳定性与性能分析/data/golden/ISSUE-206/plan.md) §2/4.4/7/8；[CardPackPage](../../../../demo/02-Feature/WalletMain/src/main/ets/presentation/pages/CardPackPage.ets) 的现有 build。文件表创建 KeySharingOuterCard 并要求嵌入现有 CardPackPage，却没有列 CardPackPage 的修改；已核页面没有自动加载该新增组件的入口。

修订：在实际核定的 CardPackPage 接入处安排修改，进入文件授权与验收；补清车主入口、接受后卡片和详情的生产者/消费者。若选定基线变化，按实际代码重新核接入，不凭文件命名推断已有连接。

复核：入口由真实消费页面引用并可达；新增路由、builder 导出与主页面接入各有承担者。文件列表与真实需要修改的对象一致，不能只存在新组件文件。

### G07 总览增加待接受撤销，和状态机不一致

证据：[Story](../历史参考/原1.9.9/04-稳定性与性能分析/data/golden/ISSUE-206/story.md) 第 165 行及 §5.3；[上游 SR](../../../../test/cases/car-key-sharing/workspace/SR/design.md) §3。总览从待接受节点连向撤销，局部状态机及上游仅从生效态撤销，管理页又未在所有描述中限定允许动作。

修订：按当前有据状态机从生效态连接撤销，同步每状态的按钮可用性、流程图和验收。若要增加待接受撤销，必须有真实业务决定及相应协议，不作为排版调整顺手加入。

复核：图中每条边、页面动作和验收均能在同一有效状态定义找到依据；终态和待接受态不会意外获得未定义动作。

### G09 示范人工回填容易被当成真实批准

证据：[Review](../历史参考/原1.9.9/04-稳定性与性能分析/data/golden/ISSUE-206/review.md) 第 198/219/242 行写“复核通过（角色 2026-09-29）”；其 HTML 头注和[MANIFEST](../历史参考/原1.9.9/04-稳定性与性能分析/data/golden/MANIFEST.md) 已说明这是形态示范。正常 Markdown 渲染不显示这段 HTML 注释。

修订：正式效果稿使用真实可追溯的回填；仅演示写法的片段在读者可见位置注明示范、与实际决策分开，不计入 Case 已确认事项或生产门的权威输入。不得以用户认可金样形式替代 Case 业务批准。

复核：读者在正常预览下能区分示范与真实回复；正向生产输入不依赖示范日期/角色/勾选。

## 3. 修订次序与交回

先锁采用材料和工程基线，再修有效决定与数据/状态关系，再同步 Story/Review 及必要施工产物，最后核表达与图形。G01–G09 的根因定位不能被“机械字段一致”替代；修正一份后逐个核同一事实的其他消费者。

交回按每项给：采用依据、改动的真实结论、受影响产物位置、保留的有效内容、独立复核及仍缺输入。未决事项保留真实状态，用户只审具体修订结果，不让用户代替维护者做所有技术取舍。

## 4. 与 2.x 迁移和产品改进的区别

旧知识登记、固定 Spec/Plan 章号、contracts.files 上的旧义务/角色、假机器投影标记和缺少实际契约输入是另一类迁移工作；按 R1 的 2.x 来源和消费者合同重建，不把这些机械迁移当作已修 G01–G09。

上述金样错误不自动证明当前产品也会犯相同错误。R3 须结合实际作者输入、职责和验证查当前缺口，再决定是否修产品；已被 2.0 承接的问题只核保持。历史探索仍可提供好的表达片段，但每片段必须在当前事实和决定下成立。
