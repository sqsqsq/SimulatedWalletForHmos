# 1.9.9 升级分发链路问题登记

2026-09-29，维护设计者。用户当日提出 extension 升级/新安装链路繁琐的问题（外网优化 → GitHub 传递 → 内网内源 demo 仓 → 各业务仓），本页**登记问题与方向，不构成实施授权**；方案细化与取舍另立 plan，开放问题（§5）在 plan 中逐项裁定后才进入实施。

## 1. 环境与拓扑现状（用户 2026-09-29 陈述的结构化）

- extension 优化在外网 + 钱包 demo（当前维护仓环境）进行；
- 优化结果上传 GitHub，内网从 GitHub 下载；
- 内网 demo 工程执行 adapt，升级内网钱包代码仓；
- 为让其他业务也能用（其他人无法访问外网 demo），内网另建**内源 demo 仓**：存放 demo/ 下所有内容，其中 `adapters/` 已替换为内网真实脚本；
- 每次发布，内网要执行：1）从外网拉取最新代码；2）在内源 demo 仓用模型执行 adapt 升级；3）再操作一次 adapt 升级钱包仓。

结构性事实（实测）：

- **adapters 双态**：外网包 `adaptation.yaml` 写 `adapters: stand-in`（替身，本地目录模拟需求系统）；内源 demo 仓已替换为内网真实现。外网包永远不能直接用于新业务仓首装（会装出无对接层的仓）；
- **知识绑定业务代码仓**：知识归目标维护、不可跨仓复制（所有权红线）；镜像仓的知识与外网 demo 同源，业务仓的知识各自从自己的代码出发；
- **adapt-scan 的所有权规则已内建**：`--apply` 写入面不含 `knowledge/` 与 `adapters/`，manifest 身份与 `adaptation.yaml` 归目标；机制面安装本身是脱离模型的确定性命令（`node adapt-scan.mjs --apply --target <目标> --package <包>`）；
- 外网发布基线的适配状态：demo 的 manifest 顶层 `adapters: stand-in`、`adapted_for: "1.9.7"`（1.x 形态），包侧 `adaptation.yaml` 同值。

## 2. 升级场景 × 问题矩阵

> 本节与 §3 登记的是 **v2 方向前（现状链路）的问题**，作为 v2（§4）的依据保留；方向落地后场景 1 整体消解、场景 2/4 部分消解，逐项对应见 §4/§5。

### 场景 1：内源 demo 仓自身升级（外网新版 → 内源 demo 仓）

| 问题 | 性质 |
|---|---|
| 唯一可用的工具是为业务目标设计的「模型 adapt」，而内源仓是镜像/分发源，不是业务目标 | 工具语义错位 |
| 它的知识镜像自外网 demo（外网发布时已适配新版），模型在内源仓做知识条目 = 重做外网已做的事 | 重复劳动 |
| 自复制那一刻起与上游分叉（adapters 换真），之后没有工具定义「哪些跟上游、哪些保持本地」的同步边界——adapt 所有权规则正是这个边界，但未被工具化为镜像同步流程 | 边界靠人 |
| 适配状态对齐（`adapted_for` 应与外网包携带的适配状态一致）无自动化 | 待定（§5） |

### 场景 2：内网钱包仓升级（内源 demo 仓 → 钱包仓）

| 问题 | 性质 |
|---|---|
| 模型 adapt 合法（知识绑定钱包代码仓、演进条目驱动），但**演进条目为空（纯机制面版本）时仍要开一次模型会话**，此时模型价值为零 | 流程未分层 |
| 升级包源是内源 demo 仓，它是内网所有仓的版本上界：外网 → 内源仓 → 钱包仓串行，内源仓卡则全卡 | 单点 + 串行 |

### 场景 3：新业务仓首次安装（只能从内源 demo 仓）

| 问题 | 性质 |
|---|---|
| 外网包不能直接用于新装（替身 adapters）——内源 demo 仓是新装的唯一入口 | 单点（拓扑必然，内源仓存在是必要的，问题在其自身升级方式） |
| 首装知识生产是完整一遍（T2/T3 在优化准确性，成本合法但存在） | 已有优化方向（T2/T3），非本页新问题 |

### 场景 4：内网其他业务仓的安装与升级（内源 demo 仓初衷）

| 问题 | 性质 |
|---|---|
| 同场景 2/3；附加：各业务仓的需求系统对接可能有差异——从内源仓复刻 adapters 后仍需按实际运行校准，这部分模型工作不可省但**未被文档区分为独立环节** | 流程缺一层 |

### 场景 5：外网侧发布（开发源 → 外网 demo 基线）

| 问题 | 性质 |
|---|---|
| 已工具化（publish_to_demo）；问题只在发布物形态：产出的是仓库代码而非「包」——内网要自己识别哪部分可分发，adapters 双态使外网包永远「不完整」，各环境自行组装，边界靠人 | 发布物无跨环境形态 |

## 3. 结构性问题归纳

1. **发布物没有跨环境形态**：机制面可分发、adapters 环境绑定、知识仓绑定——但「包」没有按这个边界成形；
2. **镜像仓没有自己的升级语义**：把分发源当业务目标跑模型 adapt；
3. **模型会话是所有流程的唯一入口**：机制面安装是确定性命令，但镜像同步 / 纯机制面升级 / 有条目升级三种流程没有分层，全部从模型会话进；
4. **内源 demo 仓单点 + 串行依赖**：它是新装唯一入口与版本上界，其自身升级方式（模型 adapt）放大了每次发布的开销。

## 4. 方向 v2：发布包三分结构（2026-09-29 用户提出，替代同日早前的「镜像同步」方向）

核心判断：**内源 demo 仓退役**。分发物从「demo 镜像仓」改为「三分结构的发布包」，所有权三分法直接编码进目录与流程：

| 组成 | 内容 | 归属 | 分发方式 |
|---|---|---|---|
| 机制面发布包 | skills/hooks/rules/manifest/bridges + 演进记录 + adaptation 标记（stand-in）+ 校验清单 | extension 维护方（外网） | 外网发布 → GitHub |
| 真实 adapters | 内网需求系统对接实现 | 内网（独立注入源） | 内网发布管理者在分发前注入组装包，`adapters: stand-in` 改为真实现标记 |
| knowledge | 各业务仓自产的激活知识 | 各业务代码仓 | **包永不携带**；目标仓由模型按方法页从自己的代码写 |

### 内网 adapt 职责定义（发布包场景下只有两件事）

| 职责 | 承载 |
|---|---|
| **agent 桥阶层更新**：撤下旧入口、按新 manifest 重新物化宿主入口、bridges 对齐校验 | `adapt-scan --apply` 的后半段——确定性命令，一条完成 |
| **知识维护**：演进记录里晚于目标 `adapted_for` 的 `[知识]` 条目与 `[在途单]` | `--apply` 末尾「按版本跟进」打印 → 模型按方法页逐条做 |

- 机制面文件本身由发布包直装承载（`node adapt-scan.mjs --apply --package <组装包> --target <业务仓>`，一条命令：删退场/复制/manifest 合成/桥物化/自检），**不手工删换**——手工替换会绕过退场清理、入口物化与防脏工作区保护；
- **对接层不作为独立条目块**：组装包统一携带真 adapters（内网一套对接实现），各业务仓复刻后与统一实现的差异校准并入实际运行验证，不逐仓单列——该简化的前提是「内网统一 adapters」成立；
- 演进条目为空（纯机制面版本）时，直装命令即完成全部，不进模型流程。

### 目标拓扑

```
外网维护仓：开发 + 发布（发布包 = 纯机制面）
   ▼ GitHub
内网：注入真 adapters → 组装包（唯一分发物）
   ├── 各业务仓直装 --apply + adapt（桥阶层更新 + 知识维护）
   └── 新业务仓首装：同路径（复刻真 adapters + 知识空清单，首装求准确按 T2）
```

原内源 demo 仓的两个职责各有所归：分发源 → 组装包；真 adapters 存放 → 独立注入源。镜像同步、适配状态对齐、demo 业务/framework 低频同步四类工作随仓退役整体消失。

## 5. 开放问题与遗留裁定（实施前定，不得先写实现）

原五项开放问题在 v2 方向下重新核定：

| 原 # | 问题 | 状态 |
|---|---|---|
| 1 | 镜像仓 knowledge 同步策略 | **消解**——镜像仓退役 |
| 2 | adapted_for 对齐自动化 | **消解**——包的 adaptation.yaml 即适配状态真源，目标经 `--apply` 的适配状态写入对齐 |
| 3 | 升级包是否带知识正文 | **已裁定**——不带（knowledge 归各业务仓，包永不携带） |
| 4 | framework/demo 业务低频同步 | **消解**——业务仓不背 demo 的任何部分 |
| 5 | 各业务仓与统一 adapters 的差异校准 | **保留**——并入实际运行验证，不单列条目块（前提：内网统一 adapters 成立，见 §4 职责定义） |

遗留裁定项（进入 plan 前确认）：

1. **adapters 注入源形态**：内网独立目录/小仓（建议名 `story-adapters-internal/`），只装 adapters 与真实现标记——内源 demo 仓退役后它的真源归属；
2. **knowledge 拆分实施时机**：建议 T9 分两步——先跑通组装包流程（打包时排除 knowledge 即可，不动现有目录），后做 demo/extension 的目录迁移（`doc/extension/{knowledge, 机制面}` 结构）——后者牵动 1.9.8 刚落地的结构、demo manifest 的 provides.knowledge 路径、adapt-scan 常量与测试装配，需单独评估成本与排期；
3. **1.9.8 结构再迁移的成本评估**：随裁定项 2 的第二步进行；
4. 组装动作的执行者与频率登记（内网发布管理者，每次发布一次）。

## 6. 与本版其他部分的关系

- T6 移植成本观测可把本链路的模型会话次数纳入口径（组装包直装前后的对比是天然观测点）；
