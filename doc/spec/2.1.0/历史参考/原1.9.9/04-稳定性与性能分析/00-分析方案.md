# 稳定性与性能全量分析：方案

2026-09-29，维护设计者。用户提出「extension 的稳定性与性能优化」分析诉求，授权用历史数据（产物备份 + suite 运行证据）叠加代码演进记录做全量分析。本文是分析方案（过程稿）：记录诉求、登记已核实材料事实、定义分析问题与执行方式。**本任务只产出分析报告，不产出优化方案；优化是否立项、如何立项，待报告交用户裁定。**

## 1. 诉求记录（用户 2026-09-29）

### 性能

- P1 一次需求的性能波动很大：一方面受模型不确定性影响；另一方面一次成文质量不达标，模型花大量时间修复问题。
- P2 从历史 runlog.md 等文件分析：执行模型实施时究竟遇到哪些问题；其中哪些可通过正向优化避免触犯，哪些要通过异常提示、后置 harness 防护等方式提高修复效率。
- P3 期望：模型最好不犯错；若犯错，要能快速知道发生了什么、应该如何解决，且不重复犯错，不出现「一个问题只修了局部然后再次报错」。

### 稳定性

- S1 历史测试产物（spec、review、plan、story）内容不够稳定；模型有不确定性，但要正向提高产物的确定性程度。
- S2 从 2 个 Case 的全部历史产物中挑选最好部分拼装「理想最佳形态」（类似金样效果）。
- S3 从最佳形态反推不稳定性成因；优化思路与性能一致：正向提升为主，异常提示或 harness 兜底为辅。

### 边界

- 不是要 plan，而是先记录诉求、做全量分析、给出报告；不轻易给出优化方案。
- 分析对象是巨量历史文档（几十次测试的产物 + 执行模型运行时思考数据），分析方案先行设计。

## 3. 分析问题清单

### A. 性能与一次成文质量（数据源：suite 运行证据 + db）

| # | 问题 | 提取口径 |
|---|---|---|
| A1 | 量化基线：一次需求到底花多少时间、波动多大 | 每 run 总时长（state/runlog）、各阶段时长、等待人时长、轮次数、token 用量（session 表） |
| A2 | 一次成文率：多少比例的阶段一次通过 | gate_*.log / reports/script-report.json 的失败条目数；verifier.report 份数（1=一次过，N=返修 N-1 次）；merged-report 结论 |
| A3 | 模型遇到的问题清单：什么问题、在哪个阶段、频次 | gate/script-report/verifier 失败条目逐条抽取，借 failure-modes clause 框架归类，按频次排序 |
| A4 | 重复犯错与「只修局部再报错」：同一错误修了几次 | 单 run 内同一 clause 错误的出现次数（连续轮演化）；跨 run 同类错误重复率 |
| A5 | 报错质量：犯了错之后能否快速知道发生了什么、怎么修 | 抽检失败条目文案是否含「未满足的条件 + 回到正确路径的方法」；统计需人工/宿主转译才能修的比例 |
| A6 | 模型为什么绕弯：典型修复段落的推理链 | 从 db reasoning 抽样典型返修段落，归纳卡点（理解错报错/找不到来源/规则理解偏差/反复试错） |

### B. 产物稳定性（数据源：59 份产物快照，同 Case 跨 run 对比）

| # | 问题 | 提取口径 |
|---|---|---|
| B1 | 结构差异：章节、顺序、标题写法漂移 | 同 Case 多份 spec/story/review/plan 的章节树机械提取与 diff（缺失/多出/顺序/编号写法） |
| B2 | 字段差异：表格表头、列数、必填字段 | 表头行提取对比（验收点、主责、来源标注、埋点定义段等现行必填项） |
| B3 | 内容差异：同一信息的表达漂移 | 数值来源标注方式、上游 AC 承接写法、知识 used_for 与实际设计、open 议题「待定」写法 |
| B4 | 门禁盲区：全过但形态漂移的点 | B1–B3 差异中「门禁全绿仍发生」的部分 = 判据未覆盖的自由度清单 |
| B5 | 理想最佳形态：逐章拼装 | 判据 = 现行合同/写作页规则 + 门禁全过 + TEST §6 三轴口径 + 用户已裁规则；逐章从历史版本挑最优，形成「最佳形态档案」，标注每章最优来源与最差版本差距 |

### C. 归因（叠加代码演进）

| # | 问题 | 提取口径 |
|---|---|---|
| C1 | 问题的时间分布：已修还是仍在 | 每类问题首次/末次出现 → git log/EVOLUTION 映射 extension 版本区间 → 标注「后续版本已处理 / 现状仍存在 / 未处理」 |
| C2 | 责任位置 | 信息未送达（任务包/模板/知识缺失或歧义）/ 判据缺失 / 报错质量不足 / 模型自由度过大 / 环境与基础设施 |
| C3 | 处置层分类（只分类，不出方案） | 正向预防（信息先于决策）/ 更早发现与修复指引（异常提示、报错文案）/ harness 兜底（确定性检查、verifier）；每类问题给出分类判断与依据 |

## 4. 执行方式

| 阶段 | 内容 | 产物 |
|---|---|---|
| Phase 0 索引 | 脚本遍历 bak 与 output/story：suite × case × run × 终态 × 时长清单；Story-Features 配对（含置信度）；db 覆盖登记；suite 时间戳 → extension 版本映射 | `index.json` / `index.md` |
| Phase 1 机械提取 | 脚本抽取：A1 耗时与 token 表、A2 一次成文率、A3 失败条目表（clause 归类）、B1 章节树、B2 表头对比 | `extract/*.json` + 汇总表 |
| Phase 2 语义分批 | 模型精读，子代理并行分批：A5/A6 报错质量与推理链抽样；B3 内容差异；B4 门禁盲区逐项确认；B5 逐章评审选优 | 分批结论 JSON/MD |
| Phase 3 归因与报告 | 叠加演进时间线（C1–C3），汇总 A/B 结论，写报告 | 分析报告 |

- 脚本与中间产物：脚本在 `output/scratch/2026-09-29-stability-performance/`（临时，不入库）；提取的数据与报告经用户 2026-09-29 指定放 `doc/spec/1.9.9/04-稳定性与性能分析/`（`data/` 放探索数据，报告与方案同层）。
- 语义分批每批给定：输入文件清单、提取问题、输出格式、证据路径要求；结论必须可回溯到具体文件与行。

## 5. 边界与证据分级

- **只读分析**：不改任何产物、不重跑测试、不改产品文件；候选「最佳形态」只登记来源与内容，不回写产品。
- **结论分级**：机械统计（可复算）与语义结论（模型判断）分开标注；每条结论给证据路径；未验证项单列。
- **历史局限**：观察对象是历史版本 extension；报告区分「当时问题」与「现状仍存在」（以现行 extensions/ 源与最新 suite 为准）；思考数据只覆盖保留 opencode.db 的 run，覆盖面 Phase 0 登记。
- **样本边界**：样本只覆盖测试 Case 的两个业务域（auto-topup、car-key-sharing）与早期 Case；外推到任意业务域需谨慎标注。
