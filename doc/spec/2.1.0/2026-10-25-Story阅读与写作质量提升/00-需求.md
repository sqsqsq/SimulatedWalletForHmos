# Story 阅读与写作质量提升

2026-10-25，维护设计者。需求共识来源为本次会话的用户反馈与 `maintenance-designer clarify` 答复；讨论及纠正见 §7。版本为新 2.1.0，实施时机等 2.0.x 发布后再由用户决定。

## 1. 问题与目标

Story 是面向产品、开发负责人和测试人员的完整业务送审正文。首次接触需求的人只读 Story，便应理解为什么做、整体如何运转、本次范围和协作边界、行为与结果、异常恢复、有效决定和未决、验收及交付责任。读者据此可以同意、要求修改或明确当前尚不能承诺的部分；准确识别缺口也是有效结果，不以一律“可以开工”为目标。

用户人工指出五类持续差距：人类阅读友好与写作效果不足；很多章节名不符合人的写作习惯；长文组织不足；丰富图文表达不稳定；全文逻辑、自洽与通畅、冗余重复及章节定位仍有较大提升空间。本需求同时检查实际生成稿与既有金样，不能只要求生成稿追平一个不再审视的样本。

目标是在业务事实、约束和评审能力保持的前提下，降低理解与查阅负担，提高文章自然程度、组织质量与图文解释效果。更短、更多图或形式齐备都不单独代表改善。

## 2. 使用场景与可观察结果

| 场景 | 应得到的结果 |
|---|---|
| 评审者首次阅读 | 沿文章形成整体业务理解，知道本次改变、参与方与边界，不依赖代码、仓库或蓝图补齐关键解释 |
| 评审者深入一条业务 | 从入口、前提、动作、交接走到正常、受限、失败或结果未知的去向；必要条件在当前阅读位置可理解，不靠跨章拼接才能成立 |
| 读者定位一项规则或责任 | 标题准确概括内容，层级与同级划分清楚，能找到相应行为、条件、恢复和验收，不误入含义重叠的小节 |
| 复杂需求形成长篇 Story | 能先掌握整体，再深入局部和查阅精确依据；完整性与阅读负担分别判断，不通过摘要化、隐藏条件或移走事实取得简短 |
| 存在多角色、状态或条件关系 | 选择适合解释关系的图、表、列表与文字，彼此补充；普通线性说明也可直接成立，不为丰富而增加装饰 |
| 阅读发现矛盾、缺口或未决 | 明确其影响和决定责任；设计问题回设计真源，表达问题修叙事，不在正文里私补业务决定 |
| 更新或局部返修后再阅读 | 新旧有效决定和关系一致，未改内容及人工意见受保护；局部改善不能破坏全文主线或制造重复 |

## 3. 需求要求

### R1 自然、准确的业务写作

正文以业务中的人、系统、对象、规则和结果为主语，表达清楚、连贯。写作指引、模板占位和完成任务的过程不应成为业务正文。普通衔接与解释按其阅读作用判断，不以禁词清单裁定自然程度。

段落围绕明确的业务主张组织，必要条件、因果和责任能读懂。并列条目、表格和叙述各有用途，不能仅把散文改成项目列表就宣称改善。范围、功能、流程、异常和验收对同一情形的含义一致，且共同忠实于有效来源。

### R2 所有层级的标题可评估调整

标题准确概括实际内容，采用读者能识别的业务或常规文档用语；避免空泛标签、维护术语、杂项收纳及直接照搬写作任务。问句或名词短语均按语境判断，不统一套句式。

本轮范围包括固定大章名和业务小节名。必要内容职责保持，但不将现有十个章名或章数预先视为不可调整；也不以改名或重排本身作为改善。标题、正文边界和相关引用须一致，改名不能破坏安全定位、局部更新与查阅。

### R3 长文的层次、详略与阅读路线

整篇能建立整体认识，局部能深入解释，精确内容可查。章节与小节按实际理解依赖、业务对象和内容职责组织；重要关系得到充分解释，简单内容不被不必要的层级或多次总结打断。

不以固定字数、段数、篇幅比例或预设深度为效果判据。不可通过删事实、压缩表格列、将关键条件藏进链接或附录、要求读者追问才交完整内容来缩短文章。篇幅较长可以合理，但每处保留与展开须有阅读或评审用途。

### R4 图文形式的适用性与配合

按需要解释的关系选形式：旅程、跨方调用、状态、条件组合、边界、页面和精确属性可以采用不同表达；不以图种数量或视觉装饰判断丰富性。总览与局部可以共同承担完整关系，局部结果应能接回主线。

源材料和设计中的有效关系、条件与失败责任在改写后保持。图前说明、图后补充、表格与文字各增加必要信息，不逐箭头或逐表行机械复述，也不为满足形态凑说明。材料原图保留真实身份与使用语境。

正式图与可选 SVG 阅读增强分别判断。零 SVG 可以成立；制作增强稿不能改变业务事实，未制作不能仅因数量被判失败。不能回到每图必做或另造补图义务。

### R5 全文自洽、通畅、去冗余与章节分工

写作组织和成稿都应解释每处内容的独有用途。同一事实可以为不同阅读任务必要重现，例如验收独立判断所需条件；不设“同一事实只能出现一次”的硬限制。完整复述而没有新用途的内容应合并或改为必要承接。

分别检查在写作设计中已经重复分配、成文时重复展开，以及分类或先后本身不合理的情形。流程推进、局部规则、失败恢复和验收互相支持；不能因各章分别完整，就要求读者自己补齐章节之间的关系。

全文一致性不能替代正确性。业务未决不因标注存在就允许在其他位置默认选边；结果未知不擅自变成失败可重试；设计缺口不能以叙事顺畅掩盖。属于现有 2.0.x 责任的缺陷继续由原需求闭合，本版核后续表达改动没有重新引入。

### R6 生成差距、目标改善与责任归因

对每个实际差距区分：设计或机制缺失/冲突、实现偏离有效合同、模型实际执行未达效果、合法表达差异及证据不足。产物有错不直接证明方案有错，提示存在也不证明已送达或实际有效。不能以少量样本把反复缺口归为模型随机性。

修改落在最早拥有该职责的位置。已有正确要求未落实时先核执行与送达；设计本身不足时修设计；确定性错误修实现。普通风格偏好与影响理解、判断的质量问题分别说明，不为每个实例追加字段、状态、门禁或固定返修轮数。

### R7 以现有金样为起点，同时审视目标效果

1.0 分支两组已审定金样为本版效果起点：自动充值至 Spec，车钥匙至 Plan。保留其有效事实、阅读组织和审定价值；不新建平行金样，不要求生成稿同标题、同字数、同句式或同图数。

分别判断生成稿未达到金样的差距，以及金样本身可改善的标题、组织、长文和图文效果。两组存在各自有效决定、设计选择及模拟前提，不能把金样新增前提当作其他运行已经取得的授权或能力。比较时先对齐这些条件，不靠替换业务事实制造表达改善。

金样及真实运行原件保留。若后续需要实质修订金样，给出前后差异、保留事实、理由与受影响消费者，重新交用户审定；被接受的表达改进不自动成为新的业务裁决。维护样本和答案不进入消费模型上下文。

## 4. 必须保持的能力与范围

保留独立 Story 送审、有效设计事实单一真源、材料与图片追溯、Review 人工区、独立语义审查、正式归档、update 与恢复等现有有效能力。设计遗漏回设计责任位置处理，Story 可重组和深化表达，不自建第二套事实。

历史已证明有价值的有界落盘、中断续写、局部替换与保护未改内容继续成立。可以调整表达结构及其实现，但须证明新组织仍保持这些结果；不把“更自由写作”作为回到一次性全文输出的理由。

本版不重做 Framework 蓝图或 CU 体系，不扩展 headless/goal，不改变业务审批权限，不建设新编辑平台或通用评测系统。具体作者、脚本和审查如何协作由后续 Plan 定；本 Spec 不指定新增流程或工具。

## 5. 验收与证据

| 条目 | 前置或触发 | 应检查的结果与证据 |
|---|---|---|
| AC1 首读理解 | 独立读者未先取得作者解释，阅读当前完整 Story | 能形成范围、整体关系、主要行为、责任、限制与验收的准确理解；记录具体理解及问题，再核有效来源。格式通过不能替代 |
| AC2 标题 | 对照整篇标题与对应正文 | 标题准确自然、层级及同级划分清楚，读者可定位所需内容；逐处给判断依据，不能由标题黑名单或字符串相似度替代 |
| AC3 长文组织 | 完整内容不减少，对比当前稿与效果参照 | 整体认识、局部深入和精确查阅能成立，必要前提可理解；说明合并、迁移、保留及详略变化的作用，不以更短签通过 |
| AC4 图文效果 | 使用当前需求实际存在的关系、图和页面素材 | 所选形式适用且互补，角色、条件、返回和去向保全；未选或零 SVG 按实际阅读作用判，不固定图数或强制照抄金样 |
| AC5 全文逻辑与重复 | 顺主旅程及相关章节阅读，含正常、受限、失败、未知及未决 | 含义与依据一致、章节衔接成立，无无增益完整复述；验收和独立理解所需重现保留。图表与文字均属于核对范围 |
| AC6 金样处理 | 比较两组已有金样与实际生成稿 | 生成差距和目标改善分开结论，前提差异披露；旧原件可取，实质修订有用户审定，不以某样本名称或固定值建立通用规则 |
| AC7 机制与执行归因 | 发现未达效果或修订作者/脚本/审查 | 目标、设计、实际送达与执行、产物和独审证据对应；归因有依据，未知明示，修正覆盖真实消费者且被替代旧路径退出 |
| AC8 保持与更新 | 表达改动涉及结构、标题、图或局部返修 | 追溯、精确值、人工区、局部安全落盘、归档及更新仍成立；确定性检查核其机械职责，独立审查与正常 CLI 分别证明语义和实际行为 |

实施前按 [TEST §6.5](../../../../test/TEST.md#65-维护标准与评审)更新并固定本版评价标准；[本版变更记录](../评价标准变更.md)只维护版本采用、映射和状态，不复制完整标准。现行 B1/B2/B3/B6/B7/B8、G3/G4/G5 等为初步关联，启动时按实际发布版重新核对。

本次只形成需求与历史调查结论。未对新 2.1.0 执行结构、独立语义或正常 CLI 验收，不预置通过、成本收益或稳定成功率。后续效果须从正常产品入口取得；人工改稿只支持目标讨论，不能证明消费模型会自动生成。实跑、发布及金样变更各依实际授权。

## 7. 讨论与修订依据

### 7.1 原始诉求及初次分析的不足

来源为本次会话。用户先要求理解当前仓历次 CLI Story、1.0 本地数据及 Extension 实现方案，再问 Story 的问题与目标。助手起初将成文规则、十章及逐章写作可能造成的负担作了整体性批评，缺少与其替代失败路径的比较。

用户纠正：“很多决策是踩坑之后逐步形成的”，要求寻找原质疑不成立或当前实现更可行的历史依据。反查得到 §6 所列证据，收回“现有机制整体过重”的推断，保留有具体证据的效果问题。历史价值不等于无须改进，当前缺陷也不直接证明原架构错误；本 Spec 以 R6 和保护项落实这一区分。

### 7.2 用户明确的五类问题

用户原意：“面向人类阅读友好和写作效果待提升”“很多章节名不符合人写作的命名习惯”“长文内容没有很好解决”“丰富图文形态表达方式不够稳定”，以及“整个文章的逻辑自洽、通畅；冗余、重复；各章节的定位依然有很大的提升空间”。同时要求区分机制缺陷、实现偏差和模型执行效果，有据改进且不重复踩坑。正文 R1—R6 承接，不将助手提出的具体代码或流程改法当作已批准方案。

### 7.3 clarify 的有效决定

用户对 Q1 明确“作为2.1.0版本，等2.0.x发布后再决策什么时候做”；对 Q2 同意所有层级标题可评估，保留必要职责而不预先锁死固定章名；对 Q3 指出“1.0分支有金样”，因此沿用已有正本，不另建目标基线。

随后 Q4 区分“生成稿未达到金样”与“金样本身还可改善”，建议以现有金样起步、保留有效内容、具体修改另审定。用户回复“同意”。R7 同时承接两条改进路径；不是修改金样原件的执行授权。

### 7.4 本次落实与尚未证明

用户调用 `maintenance-designer spec` 后，形成本文、版本入口和评价标准变更记录，均为本地需求材料。当前 2.0.0 Plan、产品、CLI 产物、金样和全量标准正文未因本次成文改变。需求整理自查与文档链接检查不证明写作效果改善，也不构成独立评审、设计开工或实施批准。
