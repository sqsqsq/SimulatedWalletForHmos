# 需求：知识能力适配

版本归属 1.9.6。维护设计者 2026-09-24 起草，同日按用户裁定与[需求审查意见](01-需求审查意见.md) K01–K07 重写（用户确认重写，并要求 adapt 轻脚本、重点构建模型的理解与执行能力）。本文是当前需求正文，替换此前各稿；已确认的决定见 §10。

## 1. 问题

Extension 每一版机制都假定目标仓有某些知识：1.9.2 规约表加了强制力、执行体、探针三列；1.9.5 新增上报事实，Plan 要靠它写出协议字段的值。这些假定只写在机制代码与当次手写的内网适配指南里。

| 事实 | 依据 |
|---|---|
| adapt 不认识知识：升级时 `knowledge/` 不读不写，`--check` 只回答机制面装没装对 | `skills/story-adaptation/SKILL.md` |
| 新知识能力靠一次性指南送达；跳版本升级或之后才接入的仓，没有东西告诉它这项能力存在 | `release/内网适配指南-1.9.3升级1.9.5.md` 第二节 |
| 知识缺了，阶段不说；知识送到了，也不等于能力具备 | 机制按「项目知识若有」运行，缺失无提示；1.9.5 第四步作者读过上报事实，Plan 仍只给占位，部分原因是首次分配规则不闭合（归[遗留问题收口](../2026-09-24-遗留问题收口/00-需求.md) R03） |
| 知识的读写规则放错了地方 | `knowledge/` 下四份 README 写的全是机制规则（三类知识的用法、事实写法、规约表列义与值域、模式候选登记）。首装复制进目标仓后不再更新；协议版本校验挂在它们的 `kind: index` 分支上（`hooks/shared/knowledge.mjs`） |

目标仓的情况各不相同：第一次接入；旧版本接入、知识有内容但没有任何能力登记；部分接入；判过不适用；编程语言与业务类型与 Demo 完全不同；有 Demo 没有的知识。

## 2. 目标

目标仓的维护模型在安装或升级后，能理解这一版机制需要什么知识、看清本仓知识的实际状况、说清差在哪；人决定这次适配哪些之后，模型依据目标仓的真实代码与业务依据完成适配，并如实交回。阶段消费模型据此取得有效知识，知识不足时知道缺什么、影响什么。

实施前置：先完成 1.9.5 遗留问题收口并通过独立评审，再实施本需求。以该收口版本的知识和阶段消费行为为基线，不与遗留修复并行改动同一职责；具体收口条件见[版本范围](../00-版本范围.md)。

## 3. 模型与脚本的分工（轻脚本）

适配的难点是理解：这个仓的知识覆盖了什么、对不对、哪些适用。这由模型完成，本需求的主要交付是让模型做好这件事的输入与方法。脚本只做确定的事，不新增判断型脚本。

| 由脚本做 | 由模型做 |
|---|---|
| 按目录所有权安装机制面（现行 `adapt-scan`，写入范围不变） | 读台账与适配方法，理解这一版要求什么 |
| 知识加载时按机制侧规则核格式：文件读不到、列与值域不合、编号重复、读写协议不兼容，一次报全（现行加载器承接） | 读目标已有知识与代码，识别覆盖了哪些能力、哪些面、是否正确 |
| 列出事实：激活清单里有哪些文件、各自声明承担什么 | 形成差异、给人决定用的说明，按人定的范围取证、改写、登记、走查 |

读写协议兼容性与能力要求版本分别表达。能力要求版本落后、或旧知识尚无能力登记，只是待识别或复核的事实；模型结合内容和本次需求判断影响，不按版本差异整体阻断。包发布版本变化也不自动要求知识更新。

不新增：差异计算脚本、自动分配或生成知识的脚本、安装状态记录、文件指纹、历史版本推断。

## 4. 包提供什么

### 4.1 知识能力台账

写给模型读的说明，一项能力一条，按三层组织：

| 层 | 含义 | 例子 |
|---|---|---|
| 通用读写规则 | 所有目标都要遵守的写法与读法 | 事实按面写与 `confirmed`；规约表列义与值域；模式的上下篇结构 |
| 业务相关能力 | 需求涉及相应业务时才需要 | 部件画像（固定必做）、通用工程事实、各规约域、上报事实 |
| 可选模式 | 由目标按自身代码结构选择，可以一个不用 | Demo 的两个设计模式（依赖特定编排 SDK） |

每条写清：它回答什么问题；哪些阶段消费、要从中得到什么；适用条件；缺失或不适用时阶段会怎样；要回答的面，每面到目标仓哪类代码结构或业务依据取证（按结构写，如「身份常量的定义」「一条正常和一条失败的实际调用」，不写 ArkTS 类名或 Demo 路径）；怎样走查算完成；当前完整要求、要求版本及必要变化说明（新增、变更、拆分、合并、迁移，迁移写明从哪到哪）；Demo 样例文件，只作组织参考。

跨版本升级的模型须能取得从目标旧登记到当前要求的有效迁移依据；不能只提供相对上一版的增量，导致旧能力更名或拆分后无法关联。材料组织由 design 确定，不引入安装历史推断或每版完整快照。

1.9.5 之前已有的能力全部补登。台账全登记不等于目标都要接入：业务相关能力按适用条件判，可选模式按目标选择，Demo 的文件拆分、域数量、具体模式都不是完整性标准。上报事实一条以遗留问题收口 R01–R03 定下的要求为准（见[版本范围](../00-版本范围.md)「两项需求怎样衔接」）。

### 4.2 适配方法

一份给维护模型的方法页，承接现行 adapt Skill 的「写部件画像」一节并扩展到全部能力：怎样识别现状、形成差异、向人说明、取证、写与登记、走查、交回（§5）。它是本需求的核心交付，按 writing-for-agents 的要求写：在动作前给目标、输入、步骤、完成条件与失败处置，附一段中性题材的完整示例（一项能力从识别到交回），不堆规则。

### 4.3 读写规则归机制

`knowledge/` 下各类 README 的规则搬进机制面，与台账同处，随 adapt 升级。模式 README 的「模式清单」退出，由激活的模式文件派生；模式依赖写回各模式文件。首装不再复制 README，`knowledge/` 从空开始，第一份是部件画像。阶段作者任务包与审查任务在用到某类知识时给出对应规则的位置。

## 5. 一次适配的过程

### 5.1 识别现状

模型读目标的激活清单、各知识文件与相关代码，逐项能力判断现状。三种起点都走同一个方法：

| 起点 | 模型怎么做 |
|---|---|
| 新仓，`knowledge/` 为空 | 部件画像必做；其余能力全部进差异 |
| 已有能力登记 | 按登记与台账的要求版本找出变化，再读内容确认实际状况 |
| 旧仓：有知识内容，没有能力登记 | 读已有内容识别它覆盖了哪些能力与面，不凭文件名推定；只补登记与真实缺口，保留原文与目标扩展，不重建整份 |

一份文件可以承担多项能力，一项能力也可以由几份文件共同承担；登记写在知识文件的 frontmatter（承担的能力、按哪版要求写），不另建第二份清单。

登记只证明状态，不证明内容正确。版本一致也要读内容：关键定义缺失、与代码冲突的，照样算差异。

### 5.2 形成差异，交人决定

| 差异 | 说明给人的内容 |
|---|---|
| 新能力，或旧仓尚未覆盖的能力 | 它回答什么、谁消费、本仓看起来适不适用 |
| 要求变了（新增面、拆分、合并、迁移） | 变了什么、本仓哪一处要动 |
| 已登记但内容有缺口或与代码冲突 | 缺什么、冲突在哪、证据位置 |
| 原判不适用，但相关条件变了 | 哪一面受影响；未变的原决定照旧，不全量重问；整项不适用与部分面不适用互不覆盖 |
| 目标自有、台账里没有 | 列为目标自有，照常消费，不当作错误；与 Demo 同名同号时以目标为准 |
| 加载器报出的格式或文件错误 | 具体错误与修法，必须修，不走「不适用」 |

人决定这次适配哪几项、哪几项判不适用（写明依据与所针对的能力或面）、哪几项留待以后。

### 5.3 自动适配

安装脚本只写机制。知识由模型在人选定的范围内直接修改，不再逐项确认成品：按台账取证、写或补齐知识、登记能力、更新激活清单与相关引用，逐项走查。遇到新的业务决定、材料或代码互相冲突、超出已选范围时，停下问人。

取证来源分开：当前实现由代码证明；业务语义由协议、需求或负责人证明；已确定但尚未实现的能力按依据写成「已定规范」，不写成已存在，也不因代码里还没有就判不适用；查不到的标「未确认」，不编。能力迁移时，按台账写明的迁移关系搬内容、保持一处来源、旧入口退出。

适配中断后再执行，从当前真实文件重新识别：已完成的保留，未完成的不登记成完成。

### 5.4 交回

分别报告：机制面安装结果；每项已适配能力写了什么、证据在哪、走查结果、未确认项；判不适用的依据；留待以后的及其影响到哪些阶段。机制面装好、知识只完成一部分时，如实分开写，不笼统称升级完成。

## 6. README 退出

目标里的 README 可能被改过，模型先区分通用规则与项目说明：通用规则已由机制面接替，项目说明迁到合适的知识文件，修正激活清单与引用后，旧 README 退出。格式校验不随 README 删除而消失：加载器改按机制侧规则检查格式与读写协议兼容性；知识文件声明的能力要求版本交模型结合内容识别差异；不为兼容保留两套索引规则。

## 7. 目标仓与 Demo 不同

| 差异 | 要求 |
|---|---|
| 编程语言不同 | 台账按问题与代码结构写；Demo 知识只示范组织方式，内容一字不搬 |
| 业务类型差异大 | 适用与否由模型据目标业务判断、人确认；可按能力或按面判 |
| 部分适用、部分不适用、部分新增 | 按 §5.2 处理；目标自有的规约域、事实面与设计模式照三类知识的写法写，机制照常消费 |
| Demo 模式依赖特定 SDK | 目标没有这个 SDK 或换了语言时判不适用，不因此判知识不完整 |

机制里与语言绑定的部分（契约样例的类型写法、资源键结构）来自 Framework 的工程画像，本需求不改；不匹配时在交回里列为未适配，交 Framework 侧。

## 8. 阶段消费时

| 情况 | 阶段怎么做 |
|---|---|
| 能力对本需求不适用 | 按登记的依据正常继续 |
| 本需求需要，但目标未接入 | 按任务从代码与材料取证；仍缺依据时写明影响哪些设计与验证，列为未决 |
| 激活文件缺失或格式错误 | 加载器报出具体错误，先修，不悄悄忽略 |
| 知识可解析，但能力要求版本落后或尚无登记 | 模型核内容及本需求影响；无关能力的待办不阻断本需求，当前必需而欠缺的内容准确列为未决 |
| 关键业务决定尚未形成 | 保留准确的未决，不编值，不声明相关设计已完整 |

说明写内容，不写文档本身。没有任何知识的仓能正常进入流程、识别需求与缺口，不等于任何需求都能无条件完成；已有依据却没做完的设计，不能拿缺失说明放行。

## 9. 新增知识类型

三类知识目前是封闭集合，新增类型作为独立需求。将来的新类型沿同一条路交付：机制支持、读写规则、台账条目同版发布；模型在适配时按「新能力」识别，目标决定接不接。

## 10. 已确认的决定

| 事项 | 决定（用户 09-24） |
|---|---|
| 读写规则 | 搬进机制，与台账同处；`knowledge/` 下 README 退出，只放目标内容 |
| 接入登记 | 不另建记录；知识文件 frontmatter 写承担的能力与按哪版要求写；不适用写明依据与针对的能力或面 |
| 台账范围 | 1.9.5 之前已有的能力全部补登；分通用规则、业务相关能力、可选模式三层 |
| 适配方式 | 识别差异，人定范围，模型按真实代码自动适配并交回；遇新决定、冲突、超范围再问人 |
| 分工 | 轻脚本，重模型的理解与执行 |
| 实施顺序 | 先收口 1.9.5 遗留问题并通过独立评审，再实施知识能力适配 |
| 具体位置与字段形态 | 台账、规则、方法页的路径，frontmatter 字段，差异说明的排版，由 design 定；需写清生产者、消费者与错误处理 |

## 11. 验收

脚本的离线正反例只证明安装、格式校验与错误报告；模型的识别与适配效果由模型演练或真实交回证明，离线测试通过不代表模型能力。模型演练使用正常适配任务中的真实知识、代码与材料；真实冲突可复核，未出现的情形如实列为未观测。人为构造的缺陷仅用于确定性脚本自检或事后诊断，不证明模型判断力。具体演练范围由 design 定。

| ID | 可检查的完成条件 | 证据 |
|---|---|---|
| AC01 | 台账覆盖机制消费的全部知识能力，分三层；每条有问题、消费者、适用条件、缺失影响、取证位置类型、走查条件、版本变化 | 台账与机制消费点逐一对照 |
| AC02 | 适配方法页在动作前给出目标、输入、步骤、完成条件、失败处置与一段完整中性示例 | 方法页与 writing-for-agents 要求对照 |
| AC03 | 新仓：部件画像完成，其余能力进差异；机制面写入范围与现行相同，脚本不写知识 | Demo 首装到中性空仓的演练 |
| AC04 | 旧仓有知识无登记：识别并复用已有内容，只补登记与真实缺口，目标扩展不丢 | 构造旧形态目标的演练 |
| AC05 | 部分接入与跨版本：已接入且内容正确的不再报出；要求变化、内容缺口、条件变化的不适用项各自报出，未变的不重问 | 登记与解析的离线正反例；正常适配任务的实际交回 |
| AC06 | 走查以真实定义、调用及业务依据判断内容，不以登记或版本一致替代；实际发现缺口或冲突时准确说明并处置 | 正常适配任务的取证与交回；既有真实冲突的复核，未观测项单列，不人为造错取得通过 |
| AC07 | 能力拆分、合并或迁移：激活清单、能力登记、下游引用同步，旧入口退出 | 迁移场景演练，包含跳过中间版本后旧能力已更名或拆分的关联 |
| AC08 | 适配中断后再执行：从当前文件识别，已完成保留、未完成不记完成 | 中断重跑演练 |
| AC09 | README 退出：目标自定义说明迁移不丢、引用不悬空、格式校验照常生效；不并存两套索引规则 | 扫描与加载器正反例 |
| AC10 | 阶段消费各情况分别按 §8 表现；格式错误不被当作不适用，可解析的旧要求知识不因无关能力待补而阻断当前需求 | 任务包、审查任务与加载器输出 |
| AC11 | 非 ArkTS、非钱包的中性目标：台账可照着取证，Demo 内容未被搬入，不采用 Demo 模式不判不完整，目标自有规约域与模式被消费 | 中性目标仓演练 |
| AC12 | 交回分开报告机制面、各项知识、不适用与待办，说明剩余动作 | 演练与内网交回 |
| AC13 | 机制层零专名；无任何知识的仓正常进入流程 | 扫描与既有测试 |
| AC14 | 内网适配指南只写本版变化并引用台账；1.9.5 指南第二节的内容在台账中有同等条目 | 文档对照 |
| AC15 | 内网真实仓的适配由内网维护模型按本方法完成并交回走查记录 | 内网交回；本仓不代替 |

## 12. 交付与依据

交付：知识能力台账；适配方法页（含中性示例）；机制侧读写规则与 README 退出说明；知识文件的能力登记写法；加载器按新规则校验；阶段任务包与审查任务的缺失说明；adapt Skill 与使用文档同步；1.9.6 内网适配指南；离线校验与模型演练记录。

依据：`skills/story-adaptation/SKILL.md` 与 `scripts/adapt-scan.mjs`（现行所有权与写入面）；`knowledge/*/README.md` 与 `hooks/shared/knowledge.mjs`（现行规则位置、索引件解析与格式校验）；`manifest.yaml`（激活清单）；`release/内网适配指南-1.9.3升级1.9.5.md`（能力交接的现行写法）；`EVOLUTION.md` 中 2.0 适配设计与 1.9.0 起「不做历史兼容」的退场；[需求审查意见](01-需求审查意见.md)。
