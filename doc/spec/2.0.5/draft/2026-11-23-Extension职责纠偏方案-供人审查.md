# Extension 职责纠偏方案（供人审查）

> 历史人审稿。下文保留提请审查时的建议；版本排期和人审结果以[2.0.6 职责纠偏与基线承接](../../2.0.6/draft/2026-11-23-职责纠偏与2.0.5基线承接.md)为准。

**审阅状态：待用户审查。** 设计对象是当前 2.0.5 开发树 `2fa9e13f`。正式 1.9.9 是能力基线。下文是我作为维护设计者提出的取舍，供决定修订范围和版本安排。人的原话、历史提交、已复现问题与尚无实跑证据的判断保存在[调查及 ask 记录](2026-11-23-Story审稿边界与2.x机制偏差.md)。

## 我在设计和评审上做错了什么

1. **把设计缺陷交给了下游兜底。** 蓝图和 Story 曾共同漏过内容。我接受了“让 Story 审查员再核一次原始决定到蓝图”的方案，评审时查了它能否发现漏项，却没查这个动作是否应该还在 Story 这一侧。即使执行者逐字照做，也会把审稿变成第二轮设计核查。责任在我的方案。
2. **把维护样例写成了产品规则。** 为保历史埋点表不会误收，我接受了按表头附注词语排除整表的实现。测试覆盖了历史反例，没用含义相同、换一种合法表达的正常稿检验门禁和审查提示。已有有效数据因此被报成缺行。
3. **把一次验法扩大成了产品和发布前置。** 为了在普通开发入口做“只换编号”的测试，我要求上游 Framework 加接点。为了解释中央模拟 CLI 的超时，我又要求中央接纳修改。这两项都超出了原要求。它们后来撤回，部分交接材料还在让执行者等待。
4. **把充分留证推成了重复劳动。** 原件、防截断、人工改稿和恢复确有价值。我多次把“再留一份、再验证一种损坏”视作天然收益，缺少对实际读取者、真实损失和边际成本的判断。下列第 2、8、9 项只建议退出有等价承接或确定无人使用的部分。

今后在本次修订的每项取舍中，我负责说清楚谁提出了目标、谁本来负责、哪位使用者会受益，以及失败时由哪里修。只在维护验收中有用的检查留在测试域；执行者照原方案也会出错时，由我改方案。以上是本次设计和评审的做法，项目长期规约另由人决定。

## 我建议怎样处理一张真实需求

**材料和人的授权 → 主 agent 完成蓝图 → Framework 质询共同设计 → 主 agent 依据有效设计写 Story → 审最终稿的业务内容和写作 → 按已有授权交付。**

蓝图作者负责发现原材料的矛盾、真实待决和知识义务，在问询处解决需要解决的问题。Story 作者负责让业务读者看懂谁在什么条件下做什么、失败有何结果、怎样验收。**我建议沿用当前已有的独立读稿调用，收窄它的任务**。理由是蓝图质询完成时最终稿还不存在，作者也容易因熟悉自己的设计而读过一个真实漏句。代价是生成 Story 的正常路径仍有一次读稿成本。只换提示词却保留旧的必读、报告和阻断条件，不能完成这项修订。你已确认两种审查的职责；是否保留这次独立调用，是我提交你审查的设计建议。

例如蓝图已定“失败可人工受理”。最终稿写成“自动拒绝”，由 Story 作者改正文和验收；同一事实都写对却让人读不出谁受理，由作者改行文。读稿时若正好看到蓝图内两条有效结论互相冲突，指出具体冲突和受影响的承诺，交蓝图负责人处理；未获裁定前保留真实待定，不能发布一项虚假的确定承诺。这三种情况都不需要让读者通盘重新选择材料或重问已经回答过的问题。

## 逐项处理意见

下列编号用于这份人审稿；括号中的 A、B、L、F 可追到[历版调查清单](../../../project/2026-11-23-历版功能来源与待裁定清单.md)。表中验法是采用建议后应取得的证据。

| 项目与现状 | 正向设计及旧做法退场 | 如何判断做对 |
|---|---|---|
| **1　蓝图质询与 Story 审稿。** 实际派审同时核“来源到蓝图”和“蓝图到 Story”，任一层都能导致 Story 审查失败。 | 蓝图写作与原生质询承担第一层。复用现有问询，把以前由下游抓到的设计漏项用作蓝图验收反例。Story 首先独立读最终稿，再对照有效设计、明确的人答和需要的原件，核内容、权限、叙述、图文与验收。退出常规重判未采用材料及“两层任一失败”的任务。同步改作者回看、读者规则、实际派审材料、报告接收条件、发布标准中要求双层核源的判法。 | 同一装配从实际蓝图问询入口和 `story-build review --action prepare` 取完整任务。用上面三个场景核谁发现、谁修改、是否重新问人。业务稿把未定写成承诺仍须拦；具体依据冲突能交回源头。无 Story 的已授权路径不派 Story 读者。[实际任务](../../../../extensions/hooks/shared/reader-review-task.mjs) · [读者判据](../../../../extensions/rules/story-reader-rules.yaml) |
| **2　首读、复核和报告交接（B1、B2、B9）。** 原设计防作者代写、截断误收，也增加重复投送和长报告补交的成本。 | 保留首次读最终稿时看不到作者答案的条件。纯表达修正沿原报告复查改处及其关联段落；材料或设计改变按真实影响扩大，旧报告不可用时重新读当前对象。原生蓝图质询沿原协议。报告唯一作者仍是读者；已有宿主若能将本轮调用完成和指定的完整原件可靠关联，最终回复只需指向原件。当前接收器自身不读宿主会话，证实这个条件以前沿用现有双全文保护。 | 一份完整原件且有同次完成依据可收；只有文件、错误轮次、已结束但报告缺失、旧协议下回复截断都不能冒作完成。局部改一处时查实际派审内容和核回范围。报告补交与发现业务问题分开记。[接收器](../../../../extensions/skills/story/scripts/core/story/independent-review.mjs) |
| **3　按当前决定传知识（B3、B4）。** 逐项留去向能防漏，到了下游仍可能反复接收相同原文、填写相同排除理由。 | 蓝图决定适用性，落到对象、义务和共同验收。下游执行已定决定时给这些内容与来源；确实需要解释、选型或解决冲突时给相关原文。保留各阶段实际需要的知识入口。相关条目可列为一组，由作者写一次共同理由，已有逐项身份继续承接覆盖；需按条消费的视图由同一判断派生。例外和待定单列。 | 取蓝图、Plan 实际作者输入和最终落点。三条同因排除能查回三条；将其中一条改为适用时，它单独产生责任和验收。未处理的第四条能被发现。仅登记来源不能证明义务已落实。[蓝图知识合同](../../../../extensions/hooks/blueprint/author.md) |
| **4　埋点表误拒（B6，已复现）。** 方法列的附注提到“统计点”就使合法数据消失，门禁和审查员都被告知缺行。 | 两个消费者复用同一解析器。按本期职责段、各列主要含义及不同列位置取行，保住方法引用核对；去掉因附注含另一列词语或样例词就排除的做法。真缺行才报缺行，形状无法识别应说明是哪一处。 | 同一行只改责任方法列的附注，三种已有写法都取到同一统计点。历史段的表、把两种职责塞在一列、方法不存在分别得到符合其真实原因的结果，同时核 Plan 门与独审输入。[生产入口反例](../../../plan/2.0.6/2026-11-23-目录调整与适配/评审意见/2026-11-23-2.0.5现状审视.md) |
| **5　目标侧收到维护用的反过拟合指令（1.x 遗留）。** 适配者被要求避开维护仓的测试题材，而它通常看不到这些材料。 | 建议交付面只说明按目标工程事实写简短、具有代表性的例子，注明假设和适用条件；删除与维护 Case 或样稿比题材的要求。例子够说明用法即可，退出“只能一个”的硬上限。防过拟合由维护评审用不同题材抽查。 | 从目标工程的 adapt 入口读实际指令。只给目标材料也能完成知识适配；换题材仍说得通。这个数字与“每份知识最多三个起步条目”（L5）是两条不同规则，后者此次保留。[实际知识协议](../../../../extensions/skills/story/reference/knowledge/protocol.md) |
| **6　结果未知被默认导向查询。** 已证通用蓝图文字过窄；尚未证实现行模型因此编造接口。 | 蓝图作者依据真实协议说明结果由谁确认、凭什么身份、能何时继续；查询、等回调、以原幂等身份重送都以目标已有能力为前提。没有相应能力就说明未知和后果。清除作者及审查提示中无条件要求查询的文字。 | 给支持查询与只支持原请求重送的两份契约，两份设计都能成立；没有任何结果确认能力时保持未知。已知失败、未知、获准新建的请求仍区分。[蓝图作者入口](../../../../extensions/hooks/blueprint/author.md) |
| **7　版本与交接指引还会让人等已撤的上游（A1、A2）。** 当前入口并列 @33 和旧状态。 | 设计者在版本规划、执行者首屏、运行索引及引用旧结论的草稿上标清时点。有效入口只指向 @33、本仓正式 900c 与当前 S10 清单。保留带原候选身份的复评、隔离补丁证据与两条中央夹具超时原件。 | 让接手人只读当前入口：能说清 AR 成文的有效范围、真实 CLI 采用对象、谁冻结和谁启动，不会去催普通入口桥接或中央改生产底座。[有效运行口径](../../../plan/2.0.5/2026-11-12-蓝图下的人工确认与范围收敛/03-执行者下一范围-S27-S28与S10.md) |

## 提请审查的决定

| 请审的取舍 | 我的建议 |
|---|---|
| 成文后由谁看最终稿 | 第 1、2 项采用已有独立读稿，只审最终业务稿；蓝图侧先承担设计完整性。取消这次调用会减少成本，但会失去一位未参与写作的读者。现有读稿成本和纠错收益在最终 CLI 原件中分别核。 |
| 什么进入本版修订 | 建议第 1、3—7 项中已有明确职责偏差、确认口径或可复现误拒的部分，在最终 CLI 前一起修。第 2 项随第 1 项调整首读与复核范围；报告收件方式只在现有宿主能提供可信完成依据时切换。 |
| 缺证的优化怎样结束 | 建议接受第 8、9 项的保留与退出条件。有明确重复才动；没有证据就保留，不成为 2.0.5 等待项。 |

若人认可本稿，设计者再将获准项写入正式方案、评价标准变更、具体退出位置与预算，按强化档交接。评审从同一候选的真实入口核提示、工具返回、下游和原件；离线只签其能证明的部分。真实 CLI 沿原安排在全部批次完成、S10 冻结并由用户启动后，以 DSH + 百炼 `deepseek-v4.1-flash-1017` 集中跑两例及一次 update。本稿的复核限于设计者自查，人审结论待填。
