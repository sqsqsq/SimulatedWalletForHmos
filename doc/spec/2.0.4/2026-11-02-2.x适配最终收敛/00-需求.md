## 1. 问题与预期结果

2.x以Framework原生蓝图和施工单位（CU）接替旧需求级Spec的整体设计与施工承接。在适配过程中，需求理解、上游合同、方案和实现多次调整，形成来源冻结/绑定、知识登记、章节组织、审查与交付、恢复、安装、计量及测试准备等多轮替换与返修。已有方案和测试通过不能证明这些职责已在当前组合中完整收敛。

用户需要从最终产品出发，得到一套能够直接理解和使用的2.x适配：消费者按正常入口完成未知需求，维护者按有效方案理解职责和接口，评审者按一致的金样和评测标准判断结果。正常运行无需解释历轮补丁为何存在，维护历史仍可追溯。

本版解决的是历轮修补积累造成的职责、结构、语义与验证问题。已有修复中必要且正确的能力应保留；历史变更次数、文件名、行数和新增分支本身不证明实现有问题。是否替换须回到最终职责、真实接口和实际消费者判断。

## 3. 使用场景

| 场景 | 最终应得到的行为 |
|---|---|
| 新系统单或本地需求 | 原件、图片、会议和有效人答进入正确执行体；范围由有权人决定；无需额外登记同义信息或重新批准已有决定 |
| 业务送审或继续施工 | 蓝图持设计真源，Story独立讲清业务，Review供真实裁决；按目标需要零个或多个CU，不强造施工产物，也不擅自编码 |
| 知识影响设计与实现 | 在决定前读到相关知识，结合需求判断适用，将义务和角色落到真实设计与施工实体，下游取得并落实 |
| 补料、评审回流或直接改稿 | 比较真实变化，保有效旧决定，改正确真源并传播；局部表达调整不扩大为业务重批，无变化不无条件全链重做 |
| 中断、局部失败与重试 | 可说明实际已经发生的动作、当前缺口和正确恢复；来源、人答、人工内容、外部意见及已发生副作用不会因刷新或重试丢失 |
| 安装、升级与统计 | 机制、知识和对接按所有权处理；正常使用可记录和复算，未知与未执行不伪装成功 |
| 维护者接手最终适配 | 阅读当前有效方案即可理解完整正常链及必要异常，不必拼接多份返修意见才能知道怎么实现或验证 |
| 评价消费结果 | 同一有效需求下，方案、实现、金样和评测标准含义一致；正确、错误、合法差异与未覆盖可区分 |

## 4. 收敛要求

### R1 全部适配问题有基于最终事实的处置

2.1收工后，核对最终代码/配置/标准身份、离线交回、CLI原事件与产物、人工干预、未达终点及未覆盖分支。与历轮已知问题、需求纠正、设计取舍、已退和未退内容一起分析，给出保留、修正、替换、退出、已关闭或有依据的外部依赖处置。

已关闭事项核保持，不重新算成待开发功能；历史问题不能仅因后来有PASS而消失，候选问题也不能仅因旧评审列过就默认仍存在。全部指可取得有效依据中的适配范围，不承诺消灭所有未知缺陷，不以故意破坏或无契约依据的极端组合扩成无限整改。

### R2 最终方案从职责和正常路径正向设计

后续有效Plan须说明目标、所有者、真实接口、完整输入输出、数据和状态、正常使用、关键变化与恢复、下游消费者及验证。逐项证明为什么需要当前承担者、是否可复用原生或现有能力，并明确被替换内容与保持能力。

正常路径是设计主体，已证异常在其责任处恢复；不能把历轮“禁止某旧行为、加一层登记、再核一遍”的顺序作为最终架构。合法未知题材与正常业务差异应成立，不带Case答案、专名依赖或样例特判。

完整方案不等于全仓重写、所有函数合并或删除全部防护。有效且简单的实现可沿用，复杂性须有真实职责依据。方案若需要新增通用框架、状态/缓存/兼容机制等，仍按项目规则先说明必要性、成本和更简单替代，不能由本需求预批。

### R3 实现与所有实际消费者一起收敛

实现应与最终方案一一对应。替换时一起核生产者、消费者、状态/配置、提示与入口、导出、模板、错误/恢复、安装、专用断言及下游终点；同一职责不保留新旧并行路径、无消费者导出或长期临时分支。

不能只改文档或生产者便认定收敛，也不能机械删除带旧名的合法能力。结构上清楚、语义上正确与正常入口行为成立分别验证。每个保留的额外步骤、防护或重复读取须能说明承担的独有职责；单有调用者不证明设计必要。

### R4 信息、事实与授权在完整链保持一致

来源库存、实际采用、人答效力、业务范围、设计状态、审查结果、当前完成与发布资格各按真实所有者解释。派生视图从真源取得，不另造可独立修改的同义账本。

材料、知识、人的决定和失败上下文在需要它的动作前送达；存在于磁盘或打印了路径不能代替实际消费。刷新、重入和重试保护原件、采用版本、人工内容和已经发生的副作用，受影响下游能发现不一致并恢复。技术载体变化不使既有有效授权失效。

### R5 审查与人工交互承担必要职责

蓝图设计质询、Story业务阅读、结构检查和后续阶段审查各有明确对象、输入、独立性与恢复。模型判断语义，确定性工具核其真实结构与身份；报告合规不代替实际审查，缺审如实披露，已知必修不能借未审放行。

保持已有业务决定和授权边界，不新增Extension层面无业务必要的人工停点。不把非阻断建议、纯表达调整、内部状态切换或已有授权重新变成批准请求；Framework原生确需条件独立核实。独立首读不提前得到作者答案，后续核源不遗漏有效材料和人答。

### R6 金样体现最终目标且与真实证据分开

以既有两组业务及有效原材料、人答、未决和已定效果为起点，形成覆盖整体设计、Story、Review、CU Spec/Plan及必要关联图文的最终目标金样。具体适用产物按系统/本地与目标阶段区分，不为形式齐套强造CU或设计附件。

金样应共同证明业务完整、阅读自然、页面交互可理解、异常/未知不失真、知识有实际落点、跨稿一致及必要技术摘要可查。不能把当前生成稿原样转正、补入未经决定的业务，或通过删内容和降要求使其适配实现。业务阅读质量与技术正确性分别核。

目标稿与正式运行产物分开。目标稿经独立语义核对，正本晋升沿既有用户审定规则；原金样与原依据保留。金样不进入消费模型上下文，不因本版改名改变旧运行评分或报告。

### R7 评测标准表达最终行为并可辨正误

复用现行全量能力及三轴评价方法，先根据最终需求核全部适用条件、保持项及变化项，再在唯一标准正文实施必要修订。本版记录采用身份和映射，不复制另一套完整标准、不另造评分或评测平台。

标准以使用结果描述要求，退出绑定旧机制的判据；不得随着当前错误产物或实现降低要求。正例、真实缺陷反例与合法差异须能区分；词数、文件数、字段存在、专名零命中或固定章数不独立证明效果。

方案、实现、目标金样和评测判据相互核对，但各自不能为自身正确作证。全量能力覆盖、独立语义、真实行为及成本均有对象和证据边界，不以局部绿测、平均分或运行终态代签整版。

### R8 验证投入与职责相称

确定性局部规则用相称输入验证，生产消费和恢复转折用真实链验证，装配用独立可重建对象验证，模型使用效果由获准正常CLI取得。不因所有测试重复全链而把简单改动变重，也不以删除有效断言、使用暖缓存或绕过真实消费者取得速度。

记录必要准备、执行、等待、返工与人工介入的实际成本，条件不同只作有边界比较。180秒沿现有决定仅作优化目标；本需求不设新硬时限、行数指标或固定返修轮数。预算按后续Plan及官方工具确定，不借版本切换抹去2.0/2.1投入和问题历史。
