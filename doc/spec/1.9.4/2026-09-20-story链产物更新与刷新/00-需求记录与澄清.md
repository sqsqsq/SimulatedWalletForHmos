# S-UPD：需求变更后的统一更新

状态：入口、范围、权限和验收已确认。有效决定见 [版本总览 D08–D15、D18](../00-版本需求与结论.md)。实现合同见 [需求 C · C1–C3](../../../plan/1.9.4/2026-09-20-版本实施/03-统一update.md)。

## 1. 入口与结果

`/story update <需求编号>` 的目标是：结合最新有效输入、既有决定和当前需求进展，判断哪些内容仍然成立、哪些需要修订，使受影响的已有产物成为一致、可继续工作的依据，并明确未决或尚未验证的部分。

更新主要依靠模型识别和理解，用户无需先列出修改文件。字节差异帮助找到线索，不等于业务变化；无新差异也不能掩盖上次未同步内容。脚本辅助取材、保留、差异与确定性检查，不替模型判断影响、意见效力或内容一致性。真正需要裁决的冲突、含糊意见、大幅重组及外部回写才停等；当前用户已有明确有效决定时引用，不重复询问。

用户进一步明确：实现越轻量越好，脚本快速判断有没有变化和具体文件差异，模型负责理解。快速检查完整、无变化、无未完成更新且无新的重查/修订请求时，直接报告并删除本次临时镜像/暂存，不进入模型的完整分析与成文，不写业务产物或重验。普通业务未决没有新信息时保持未决，不因此重复催问。

update 完整替换独立 review 入口与流程。评审意见是更新输入的一种，`review.md` 继续作为评审交付件；原先“只修 Spec、Story 永远停在送审时点”的现行工作方式退出。历史送审版本通过备份保留，当前工作版本同步反映有效结论。

## 2. 输入及判定责任

| 输入 | 获取范围 | 判定 |
|---|---|---|
| 需求系统 | 当前单及其关联上游材料、评审反馈；本地单明确不适用 | 脚本取得版本/字节变化，模型判断语义与影响 |
| 本地材料 | 已登记材料、约定 inbox 与界面参考目录；包括新增/修订会议 | 按现有导入、会议原文与人工裁决链处理 |
| 直接编辑产物 | 当前已有 Spec/Story/Review/Plan 及其契约和验收真源 | 视为待理解的修改输入；不自动把任意直接修改认作新业务决定 |
| 人工评审 | 远端回稿、本地人工区及明确提供的意见 | 保留原文，区分采纳、建议、暂缓、未评审与冲突 |

输入变更不等于批准改变业务。模型依据有效材料和历史决定判断；新内容与已定结论冲突时给人原依据、新依据及影响，集中询问。脚本不按“更新更晚”自动判新事实优先。

任何来源不可达、无权限、内容损坏或缺少比较基线，都须区别于无变化。自己刚归档的 Story 出现在系统 AR 正文中，不能再次当作上游新需求输入。

### 2.1 场景完整性

模型至少能够处理：新增或修订要求、删除/挪位但含义未明、新会议里的讨论与决定、针对旧版的评审意见、用户已经手改部分产物、多源冲突、未决得到答案、规则改变引起隐含关联、Plan 在途或已闭环、无新差异但仍未同步、已经进入代码/测试、纯表达变化、来源不全及中断续行。

每种情形需要说明变化含义、有效依据、相关内容、保留项、待裁决与下游影响；这些不是脚本的业务分类枚举。模型按真实关系处理没有预列的合法情形，不能用固定模板的行数证明场景已覆盖。具体推演与执行见设计 §2–§4。

## 3. 按当前进展更新

| 当前已有产物 | 本次动作 |
|---|---|
| 只有材料/初析/提取稿 | 更新受影响的已有内容，留下后续影响；不生成 Spec |
| 已有 Spec、Story、Review | 同步受影响的需求、验收、决策与叙事，不重复询问未变的范围 |
| 已有 Plan（含在途） | 同步受影响设计、契约、用例及知识承接；不自动开始 coding |
| 已进入代码/测试 | 文档更新到已有 Plan，明确列出代码与测试影响，交既有修正流程；本命令不自动实施代码与测试修改 |
| 已归档 | 保留历史送审版本，更新本地工作版本；展示差异并取得确认后才回写 |

模型同时确认当前意图、已有产物、在途内容、已闭环结果与历史送审版本，再决定本次修订和可继续范围。产物存在性与真实回执提供事实；不能只按“有这个文件”确定其有效性，也不能把写完文件当作可以继续全部下游工作。

## 4. 修改、人工决定与恢复

默认修改局部及必要的关联内容。整篇大幅重组需先说明原因、范围和保持项，再请用户确认。整篇表达优化只有用户明确触发才执行。

已经明确采纳、没有冲突的意见自动落实；空框、推荐项、含糊的“通过”和纯模型推断不冒充人的决定。决定的有效范围发生变化时，保留旧意见及其上下文，新的问题保持待决。

每次实际更新前保留完整本地结果，更新后提供变更摘要与逐文件差异。失败时可恢复到本次更新前；在失败现场已有人进一步改动的情况下，先保护其改动，不盲目覆盖。无变化不重写业务产物，不重跑完整阶段。

本次启动镜像用于恢复，保持完整旧内容；新内容正常存入原需求目录。识别启动前手改使用上次已处理版本，不能只将启动镜像与当前目录相比。优先复用已有版本，必要时保存只读比较内容；无比较依据或来源失败不当作无变化。只有本次临时无变化副本清理，历史有效备份不随之删除。

部分产物修改成功不代表整次更新完成。来源缺口、尚未完成的同步、验收失败和外部回写失败分开报告。外部系统失败不会把已完成的本地更新伪报为丢失，也不能报为已发布。

## 5. 用户看到的结果

结果说明包含当前采用的有效依据、变化解释、关联修订、保留项、人签/未决、核对及其证据边界、恢复方式和下游影响。

模型区分“已同步可继续当前工作”“已同步但仍有明确保留项”“尚未完成”“核对后无需修订”。外部发布另报；脚本操作结束不能代替上述语义判断。第一次缺历史基线时，不声称历史无变化；资料不足时说明可确定与不能确定的范围，不一律全停或全报完成。

展示结果后确认是否回写需求系统；确认绑定当前产物版本，确认后又发生变化须重新展示。本地单没有回写动作。没有变化时直接给出检查结果，不人为制造确认或新一轮。

对实际修订的适用阶段，主模型在原生重验后使用当前请求派既有 verifier，报告原样回写并同步闭环；当前材料已有 PASS 复用，无变化/未修订/纯过程记录不额外派审。普通局部 correction 的原有不自动重审路径保持；具体触发、失败返修和无审查能力边界见设计 §8.2。

## 6. 验收

对应版本 AC05–AC12。两个 Case 分别在 Spec、Plan 后继续同一会话执行 update，前后结果分别评测和回流。异常、恢复、无变化、不同输入形态及安全路径由离线测试覆盖；不为每一分支增加真实模型运行。

性能比较区分首次生成与增量更新，记录改动量及实际验证范围。新输入确实影响多处时允许必要同步；无变化和局部变化不默认触发整套 init→六阶段重做。
