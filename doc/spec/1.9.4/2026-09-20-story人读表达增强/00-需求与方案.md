# S-EXP：Story 与 Review 人读表达

状态：需求已确认，实施未开始。有效决定见 [版本总览 D04–D07](../00-版本需求与结论.md)。本文描述效果与边界；文件动作见 [需求 A · A1](../../../plan/1.9.4/2026-09-20-版本实施/01-Story表达优化.md)。

## 1. 读者要得到什么

Story 帮评审者理解为什么做、谁参与、怎样完成、在什么条件下失败、哪些事项仍待决定，以及怎样验收。Review 帮评审者定位真正需要他决定的事，理解选项后果、建议依据与既有结论，填写意见后能被准确承接。

减少读者在长段叙述中寻找关系的负担，改善章节层级单薄和表达生硬。图形、表格、简洁说明、自然的三级/四级小节是手段；关系不适合图示时保留准确的文字。既不以“图更多”判好，也不通过删事实让文档变短。

设计必须给出整篇阅读组织、分节条件、形式选择、图文互补及自然表达的动作和示范，并落实到已有骨架/草稿/回看/审查消费者。[成品表达合同](../../../plan/1.9.4/2026-09-20-版本实施/01-Story表达优化.md)及[同源示范](../../../plan/1.9.4/2026-09-20-版本实施/参考/02-同源成品示范与保持核对.md)用于实施者对齐；不以再增加一句“图讲关系、文字讲理由”作为交付。

## 2. 使用场景与范围

| 场景 | 要求 |
|---|---|
| 首次生成 | 在来源理解和写作设计中考虑阅读主线，直接产出改善后的 Story/Review |
| 局部业务更新 | 只优化受影响内容及必须共同说明的关联部分；相关业务关系完整表达 |
| 用户要求整篇表达优化 | 可以整理已有 Story/Review；业务结论不变，提供前后比对；涉及章结构或大幅重组时先给具体方案确认 |
| 既有 Spec/Plan | 仅同步业务或契约变化，不作为本版全面排版优化对象 |

保留 Story 十章职责，章内可以重组或增加必要小节。写作设计保存当前表达安排，不是正文内容上限；成文中发现更好的表达可以调整，沿现有记录说明依据，不为每处形态选择增加用户确认。

## 3. 内容保持

改画流程、时序或状态图时，保留原材料的参与者、调用方向、前置、成功与失败分支、返回、补偿责任和状态迁移条件。图可以分拆，解释可以移到相邻文字，但读者必须能明确对应；不能用“整体失败/整体回滚”替代已知的责任归属。

未决事项保持未决；推荐、工程假设和人的决定清楚区分。表达优化发现原始材料冲突时交回需求或决策真源处理，不在叙事中暗自裁决。

Review 保留人工区、自由意见及其所属议题。仅当人的表态明确覆盖当前议题含义时才能沿用其结论；文字保留不等于旧表态对变化后的方案继续有效。

## 4. 表达与归档环境

维护实施者先核可取得的需求系统渲染说明或正常预览证据。当前 Demo 对接只证实传输 Markdown，不能证明真实平台支持 Mermaid、HTML 或折叠。

环境未验证时，核心结论由普通 Markdown 文字与表格完整承载，图与必要说明互补；不把未验证的图形语法作为唯一承载。增强语法启用依据写入目标对接说明。参考目录仅供维护者比较效果，不注入消费模型作为答案，不要求同图数、同节数或同句式。

## 5. 验收

- 对应版本 AC01/AC02：评审者能理解主线，重要条件与责任不因压缩或换图丢失；真实来源对照证明内容保持。
- 对应 AC03/AC08：待决清楚，原人工意见保存并且语境正确；Review 能实际支持作决定。
- 指引在选形态、写章和独立审查之前送达；离线装配仅证明送达载体，不证明模型应用。
- 影响正确性、完整性或可执行性的遗漏作为阻断；纯风格偏好不阻断，不以重开全链强制修到“更漂亮”。
- 真实验证复用版本规定的两个 Case 初始与 update 后成品，不新增表达专项实跑。
