# 共建可行性分析框架与遗留问题

2026-10-20，按用户要求记录本轮分析成果。本文确定分析范围与方法，不预先选择主线位置、仓库组织、发布形态或人员任命。

> 当前范围纠正：本任务分析共建协作与分工，不分析具体功能开发。下文涉及实现接口和代码调查的条目仅保留为先前分析记录，不作为本轮下一步工作或前置条件。当前应比较工作组织、贡献路径、责任划分、集成交付和维护方式，不启动 lite、review 或 Profile 的实现调查。

## 1. 已成立的基线

Framework 和 Extension 已采用外网开发、外网 demo 验证、内网真实验证和交付。此次讨论要解决新增人员和能力如何进入或扩展这条链，不是重新建设已有交付流程。

内网开发成果不能回传外网。开发模型与运行模型分别判断：用户说明当前 Framework 和 Extension 开发需要最新模型，GLM 5.3 不足；运行态要求 GLM 5.2 和 DeepSeek V4，并必须在内网验证通过。

人员可以长期参与，允许按难度分担实现，但每项能力须有负责人保证在整体框架中运行并达成效果。局部设计决定可在授权范围内下放，公共接口和跨产品影响集中协调。

第三轮进一步确认：Framework 只在内网使用，外网只承担开发和 demo 验证，通常完成主要功能场景验证。内网问题先人工分析，再人工转述到外网反馈模型优化，不将内网文档、日志或代码传到外网分析。先根据功能和限制设计协作，再推导人员与环境要求；当前无固定时间要求，有投入意愿、目标和计划即可。

## 2. 十项分析因素

前五项由用户明确提出，后五项由助手补充；均纳入分析，具体结论待事实与取舍支撑。

| 因素 | 必须回答的问题 | 对方案的影响 |
|---|---|---|
| 1. 网络限制与模型条件 | 内外网允许传递什么；开发、评审、运行各需要什么模型；成员能否获得相应条件 | 决定工作地点、任务承接和修复闭环，不能用运行模型能力推断开发能力 |
| 2. 交付形态 | 完整包、随包组件、独立安装内容分别是什么；使用者拿到什么组合 | 决定安装、依赖、升级和交付成本，不从目录结构直接推定 |
| 3. 代码仓与分支 | 权威源码在哪里；同仓或分仓；单向下发或独立演进；改动合到哪里 | 决定贡献能否进入产品以及长期分叉风险 |
| 4. 人员分工与协作 | 目标、设计、实现、集成、验收、维护分别由谁负责；投入、经验、环境是否匹配 | 决定实际产能，负责人不必独自执行全部工作 |
| 5. 产品开发与交付流程 | 需求入口、接口协调、评审合入、候选构建、内网验收和正式交付如何连接 | 决定多人工作能否成为可用版本 |
| 6. 产品与架构边界 | 各特性哪些部分属于核心、平台或业务；现有接口能否支持独立演进 | 决定可拆分工作包和必要公共改动 |
| 7. 版本依赖与生命周期 | 支持哪些组合；谁适配升级；如何通知和验收；旧版维护多久 | 独立开发、独立发布和独立升级不等同 |
| 8. 质量验收与支持范围 | 平台、宿主、模型上的承诺是什么；需要什么证据；谁签收 | 区分局部、demo、真实工程证据，防止将未验证组合视为可用 |
| 9. 问题反馈与持续修复 | 内网问题能反馈什么；谁定位；修在哪里；怎样进入下次交付 | 决定单向交付之外是否有可持续的维护闭环 |
| 10. 现有资产、迁移成本和资源容量 | 哪些直接保留、适配或重做；增加多少评审、集成和维护工作 | 避免理想终态脱离既有 Web、Android 实现及人员容量 |

这些因素须联动比较。源码位置影响贡献路径，模型条件影响可承担改动，交付形态影响集成，集成又影响人员责任和持续成本。

## 3. 三个位置分别记录

- 开发地点：某项工作在哪里完成。
- 源码归属：成果长期由哪个权威仓维护。
- 发布来源：使用者取得的版本由哪里构建和确认。

三者可以不同，但每次跨越都要有可行路径。人员在内网负责不自动意味着源码必须在内网；外网统一发布也不意味着内网成果能回流。

## 4. 可行性分析顺序

1. 固定硬约束与现有事实：网络、模型、人员条件、既有代码和已运行交付链。
2. 核能力边界与依赖：分别检查 Framework、Extension、Web、Android、lite 和 review，不按名称推定难度或解耦程度。
3. 比较完整组织方案：每个候选同时写明仓库、人员、模型、构建、验收与修复路径，明确收益、成本和不可行条件。
4. 用实际场景检验：新增能力、公共接口变化、内网独有故障、框架升级、负责人交接。
5. 形成分阶段建议：长期形态、现有成果承接、过渡责任和成本均明确后，再决定具体分工。

最终产物应为共建可行性分析和组织方案，不是先给人员分派功能再补理由。本轮仅记录分析框架，未授权产品实施。
