## 1. 总体组织与责任

本方案作为 07 的完整修订稿，保留已有确认与讨论依据，补齐发布仓中转、下游同步与反合、仓内维护、并行分支、合入验证和发行验证。

采用已确认的**按部件边界同步和回交**方式：

- 外网维护 Framework、Extension 公共产品。
- 内网 Web、Android 仓维护各自 Profile 源码。
- 内网发布仓接收上游发布内容，接纳平台源码成果，形成可运行组合，承担合入验证、发行验证和完整发布。
- 业务项目安装已发布产品，维护自身代码、知识、配置和对接。
- Framework、Extension 的公共能力缺口统一向外网维护者提出，内网不修改公共副本。
- 发布负责人按版本轮值。每个候选、维护线和正式版本都有明确负责人。

### 1.1 仓库关系

```text
外网 Maison 源码仓
    │ Framework 发布件
    ├──────────→ 外网 Demo main
    │                  │ 固定接入基线
    │                  ↓
    │            Story 开发／维护分支
    │                  │ Extension 正式发布载体
    ↓                  ↓
        内网 maison-distribution
        接入、同步、合入验证、发行验证、发布
           ↑↓                    ↑↓
     maison-web             maison-android
     平台开发与修复          平台开发与修复
                  │
                  ↓ 完整发行包
             各业务消费工程
```

三种关系各有含义：

| 关系 | 内容 | 操作 |
|---|---|---|
| 外网 → 发布仓 | Framework 正式包、Extension 正式载体 | 固定身份导入，不合并外网整仓历史 |
| 发布仓 ↔ 平台仓 | 公共依赖、已接纳的平台基线、平台源码变更 | 按部件路径同步和回交，不做整仓 Git merge |
| 发布仓 → 业务工程 | 经验证的完整发行包 | 原生安装、初始化、适配和业务验收 |

## 2. 仓库真实结构、源码归属与版本

### 2.1 外网保持现有发布与适配链

Framework 作者从固定源码构建一次 ZIP：

1. 将其解包接入 Demo main，完成必要初始化／更新。
2. 将同一 ZIP、清单和说明交给内网发布仓。
3. 记录 Framework 构建身份和 Demo 接入提交，二者不混用。

Story 根据固定 Demo main 基线分析适配，在自身开发线完成新版本。`story-1.0` 继续承担已知 Framework 3.0 对应稳定线的维护；后续稳定线按实际发布对象建立。

Framework 可以先发布；Story 可以复用已验证兼容的旧版。内网完整发行必须采用明确兼容的组合。

### 2.2 平台仓：开发源码真源

两个平台仓采用相同职责布局：

```text
maison-web/ 或 maison-android/
├─ profile/                 本平台正式源码
├─ tests/                   部件开发测试
├─ examples/                可运行的代表性业务工程基础
├─ dependencies.json        当前开发分支的公共依赖与同步基线
├─ docs/                    需求、设计、开发说明、回交记录
└─ .work/                   本地验证工程与依赖副本，不入库
```

平台仓不保存第二套可独立修改的 Framework、Extension。

`profile/` 是平台源码真源。发布仓中的平台目录是**已接纳的发行快照**，通过平台仓成果更新，不在发布仓直接开发平台需求。

### 2.3 发布仓：中转、集成、验证和发布真源

```text
maison-distribution/
├─ inputs/
│  ├─ framework/<输入身份>/
│  │  ├─ framework-<版本>.zip
│  │  ├─ framework-<版本>.manifest.json
│  │  └─ 来源及升级说明
│  └─ story/<输入身份>/
│     ├─ 来源及适配说明
│     └─ demo/                      正式发布 Demo 的目录快照
├─ components/
│  ├─ web/profile/                  已接纳的 Web 正式源码快照
│  └─ android/profile/              已接纳的 Android 正式源码快照
├─ release.lock.json                当前分支选择的完整组合
├─ assembly/                        发行装配与校验入口
├─ test/
│  ├─ projects/                     三平台代表性验证工程基础
│  ├─ cases/                        发行验收场景和预期
│  └─ scripts/                      现场准备、执行与结果收集
├─ docs/
│  ├─ requests/                     跨仓需求协调
│  └─ releases/                     版本、候选、验收、维护与交接
├─ .work/                           隔离装配和验证现场，不入库
└─ dist/                            最终输出，经发布渠道留存
```

各区域的更新规则：

| 区域 | 谁提供变更 | 维护规则 |
|---|---|---|
| `inputs/` | 外网维护者 | 固定输入导入，已归档输入不原位修改 |
| `components/` | 平台维护者反合 | 只接纳本平台正式文件；记录对应平台源码提交 |
| `release.lock.json` | 当值负责人组织更新 | 指定公共输入及平台快照来源，不使用浮动分支 |
| `assembly/` | 发行维护者 | 只处理发行职责；公共机制缺口交外网 |
| `test/` | 团队共同维护 | 发布仓拥有发行验收场景，平台维护者贡献工程和测试 |
| `dist/` | 固定候选构建产生 | 不手工修改，不作为开发源码提交 |

Framework ZIP 是输入真源，不再维护一份可修改的解包输入。Story 首版保留现有正式 Demo 载体，不擅自裁成未经验证的新包。

### 2.4 组合身份与源码追踪

一个发行对象固定：

- Framework 发布输入。
- Extension 发布输入及兼容关系。
- Web、Android 源码提交及接纳的文件内容。
- 发布仓中的装配、测试和组合记录。
- 实际发行包的校验信息。

平台回交至少说明：

- 目标发行版本线。
- 从发布仓哪个提交／版本开始开发。
- 当时该平台已接纳的源码基线。
- 本次回交的平台源码提交。
- 公共依赖要求、改动范围及测试结果。

这些信息进入既有回交和合并记录，不另建全局状态系统。

### 2.5 分支和版本

| 仓 | 分支 | 用途 |
|---|---|---|
| 平台仓 | `main` | 下一平台开发基线 |
| 平台仓 | `feature/<需求>`、`fix/<问题>` | 多人并行开发 |
| 平台仓 | `upgrade/<目标基线>` | 公共依赖升级 |
| 平台仓 | `maint/<维护线>` | 旧发行线所需平台修复 |
| 发布仓 | `main` | 当前下一发行线的已接纳组合 |
| 发布仓 | `intake/<输入>` | 接收上游输入 |
| 发布仓 | `integrate/<需求>` | 接收平台反合或发行变更 |
| 发布仓 | `upgrade/<目标>` | 尚未具备替换主线条件的大版本升级组合 |
| 发布仓 | `release/<版本线>` | 候选冻结、正式发布和稳定补丁 |

短期分支名称可以沿团队习惯，不强制每次使用所有分支。

Framework、Extension 保留外网版本；平台成果以固定提交为主，内部里程碑可打 tag。内网完整 Maison 独立编号。正式 tag 不移动，发布包不覆盖。

`main`、升级分支和稳定维护线各有自己的组合，不能用一个全局“最新版”替代它们。

## 3. 各仓日常维护与双向同步

### 3.1 发布仓接受上游更新

当值负责人按以下步骤接收：

1. 取得固定发布件／载体、来源和升级说明。
2. 在 `intake/*` 导入新身份，检查内容与来源一致。
3. 将输入归档提交与“本轮采用它”的组合修改分开。
4. 不需要立即采用时，仅完成输入接收。
5. 需要采用时，在本轮集成或升级分支修改组合，并通知受影响维护者。

输入已到达，不代表完整产品已经升级。稳定线继续使用原输入。

针对稳定线的上游补丁，独立导入该补丁输入，不为取一个包合并整个开发主线。

### 3.2 平台仓从发布仓同步

平台开发者先确定目标：

- 为当前开发发行线做功能，选该发行线的固定提交。
- 为稳定版修复，选稳定版本 tag／维护线固定提交。
- 为新框架适配，选指定升级分支的固定提交。

同步过程：

1. 获取指定发布仓提交。
2. 读取公共输入、已接纳的平台源码基线和装配方法。
3. 核对平台本地分支与该基线的关系。
4. 在本仓同步／升级分支更新依赖，必要时补入已接纳的平台变更。
5. 解决与本地工作冲突，保留本仓未交付的功能。
6. 重建本地消费验证工程，按正常入口安装并验证。
7. 提交同步结果，再开展或继续任务。

平台仓仍维护自己的源代码。同步不会把完整发布仓合入平台仓，也不会用发行快照强行覆盖开发分支。

日常开发使用平台依赖记录；发行验收使用候选组合。二者不同需要明确记录，不能静默切换。

### 3.3 平台开发完成后反合发布仓

反合对象是指定部件路径的源码变更及其来源，不是整仓文件，也不只是一个口头版本号。

1. 开发者完成本仓评审和必要测试。
2. 选择可交付的固定提交，确认没有夹带无关未完成能力。
3. 向发布仓目标版本线发起回交，说明共同基线和变更范围。
4. 在发布仓 `integrate/*` 中比较：
   - 回交所依据的已接纳平台基线；
   - 发布仓当前已接纳平台内容；
   - 本次平台回交内容。
5. 接纳新增、修改和删除，禁止将测试工程、依赖副本或公共产品改动混入平台目录。
6. 运行合入验证。
7. 通过后合入目标发行线，并把接纳提交反馈平台仓和需求负责人。

**发生冲突时，平台维护者负责在平台源码中完成协调。**发布仓不直接形成一份无法对应平台源码的修复结果。

如果发布仓已经接纳另一项同平台变更，平台维护者先吸收该成果、形成兼容的新回交提交；不能用旧整目录快照覆盖它。

### 3.4 多人和多分支并行

- 同一平台多人开发，使用同一平台仓的独立任务分支。
- 不同任务可以基于不同稳定或升级基线，回交时必须指定目标发行线。
- 本仓 `main` 含有无关在研内容时，从相应可交付基线整理交付分支，避免把所有最新源码一起反合。
- Web、Android 可以并行回交，分别接纳到所属路径。
- 共用依赖变化时，发布仓核最终组合；不能把两个旧组合下的通过结果直接相加。
- 已发布的平台修复应检查所有受影响活跃分支，包含升级分支；在原任务中记录已同步或不适用原因。
- 开发者不因发布仓出现新提交就必须同步，只有任务需要、公共影响或准备回交时才更新。

### 3.5 仓内维护与下游反馈

每个源码仓维护自己的需求、设计、回归和分支。平台维护者对源码与长期维护负责；轮值负责人对发布仓当前发行工作负责。

单仓需求在所属仓维护。跨仓需求在发布仓记录总目标、依赖及验收，各仓维护子任务。

内网反馈由人员分析后向外网转述。外网维护者在自己的仓中形成问题或需求，修复后重新发布；内网不上传原始业务代码、日志或内部资料。

## 4. 从需求到发行的操作场景

### 4.1 一次普通 Web 需求

假设稳定版 `M1 = F1＋E1＋W1＋A1`。

| 人 | 仓与分支 | 操作 | 形成的结果 |
|---|---|---|---|
| Web 开发者 | Web `feature/N` | 从 M1 对应依赖和平台基线开始开发 | 平台变更 W2 |
| Web 维护者 | Web 仓 | 评审、测试、固定回交提交 | 可回交 W2 |
| 当值负责人 | 发布仓 `integrate/N` | 接收 Web 路径变更，保持 F1/E1/A1 | 新组合候选 |
| 平台及发行测试执行者 | 发布仓规定的测试现场 | 合入验证及受影响功能验证 | 绑定候选的结果 |
| 当值负责人 | 发布仓目标发行线 | 接纳、汇总发行验收、发布 | 新完整版本 M2 |

Web 仓取得发布仓接纳位置，需求负责人据真实验收关闭任务。Android 无需无故产生新提交。

### 4.2 一次同时涉及 Framework、Extension 和平台的需求

1. 需求负责人明确总目标和子任务；公共能力诉求交外网维护者。
2. Framework 作者在 Maison 完成实现和验证，发布 F2。
3. 同一个 F2 接入 Demo main，并导入内网发布仓。
4. Story 固定 Demo 基线，适配并发布 E2；旧版兼容时明确复用。
5. Web、Android 分别从发布仓升级组合取得固定输入，开发和验证平台改动。
6. 平台成果按部件边界反合升级分支。
7. 发布仓完成最终组合的合入和发行验证，达到目标后成为新的发行线。
8. 原稳定线继续接受补丁，不被升级分支覆盖。

可使用外网维护者提供的固定候选构建提前联合验证，但候选与正式身份必须区分。正式发布输入发生变化后，复核受影响结果。

### 4.3 升级过程中插入稳定版补丁

假设开发线正在使用 F2，而稳定版仍为 M1：

1. 对应平台从 W1 或 A1 建维护修复分支，使用 F1/E1。
2. 发布仓从 M1 接续 `release/*`，只接收必要修复。
3. 完成补丁验收，发布 M1 的补丁版。
4. 平台修复同步到受影响的开发与升级分支。
5. 发行脚本的修复同样检查其他活跃发行线。

Framework、Extension 缺陷由外网旧线交付补丁；不要求 Demo main 回退，也不允许内网改公共副本。

如果上游不再支持该旧线，当值负责人与需求方明确升级或支持调整，不能承诺无法兑现的修复。

### 4.4 两个任务相互冲突或依赖未到位

- 同平台源码冲突：回平台仓解决，重新提交可追溯成果。
- 公共输入不兼容：保留旧组合，阻止受影响任务进入正式候选。
- 平台完成、公共能力未发布：可保留开发成果，不能标记完整需求已交付。
- 一个任务延迟：无依赖的成熟任务可以发布；不能把未验证平台继续列为已支持。
- 未定位问题：先在固定候选中定位，不靠修改公共副本绕过。
- 发布负责人换人：按候选、版本线、待合入事项及失败结果交接，不能重新选一套输入“从头再试”。

## 5. 发布仓的验证能力与业务安装

### 5.1 发布仓承担两级验证

**合入验证**针对每次上游采用、平台反合或发行变更：

- 来源、基线、路径归属和依赖一致。
- 删除项正确退出，没有覆盖另一项已接纳成果。
- 能够从固定输入组装。
- 运行相关确定性检查及代表性场景。
- 结果对应待合入内容。

**发行验证**针对固定完整候选：

- 从实际候选包完成三平台首次安装。
- 从承诺支持的旧版本完成升级。
- 验证 Framework、Profile、Extension 的必要功能及交互。
- 验证真实宿主、工具链、设备和必要的内网业务对接。
- 核目标知识、配置和对接的保留与适配。
- 核本版承诺的恢复、续行和旧需求边界。
- 核完整包和发布说明对应实际验证结果。

平台开发仓测试、合入验证和发行验证各有对象。有效证据可复用，但不能用部件自测替代完整候选验收。

### 5.2 发行测试工程

发布仓维护 HarmonyOS、Web、Android 的代表性工程基础、测试场景和执行说明。平台维护者贡献并修复相关测试内容，发行仓对验收覆盖负责。

验证工程必须：

- 有实际业务代码和正确平台工具链。
- 有独立 Git 根及明确基线。
- 从指定候选安装产品。
- 按原生入口初始化与适配。
- 保留必要的原始结果和候选身份。

首次安装从未接入工程开始；日常功能测试可以复用已适配的固定基础；升级测试从明确旧版本工程开始。

测试可分布在不同机器，统一使用发布仓确定的候选、场景和预期。当值负责人负责完整结果，不能仅收几份不对应同一候选的报告。

### 5.3 实际发行形态

装配现场：

```text
.work/<候选>/
├─ framework/                 上游 Framework＋内网 Profile
├─ story-source/              原样保留的正式 Story 分发载体
├─ 完整发行身份与来源清单
└─ 安装、升级及限制说明
```

`dist/` 输出该目录的发行 ZIP 及校验信息。它不是源码修改位置。正式包进入团队现有发布存储，保存下载位置与校验值，不仅保留在当值电脑。

Story 载体中的 Framework 属于其原始上下文；根下 `framework/` 才是实际装到业务工程的组合。后续精简载体必须由 Extension 维护者验证交付。

### 5.4 各业务工程实际安装

1. 取得确定的完整版本，核平台和升级起点。
2. 在业务工程的接入分支或独立验证副本中接入组合 Framework。
3. 按该版要求准备 Harness 依赖。
4. 执行原生 framework-init：扫描、确定计划、执行、读取结果，生成或更新项目配置及宿主入口。
5. 从发行包指定 Story 来源对目标工程执行正常 adapt。
6. 完成目标知识、需求系统对接和个人工具链设置。
7. 执行该工程约定的接入验收，再合入业务工程。

发行包不能预先替所有目标生成项目配置、个人路径或项目知识。

当前已核对的初始化菜单只列出 generic、hmos-app。Web、Android 的原生选择、配置及更新路径必须由 Framework 维护者确认或补齐，不能靠内网直接改公共菜单绕过。

2.x 不接续旧需求现场的边界保持。软件升级与旧需求迁移分开处理；必要时旧需求继续留在旧版工程，新需求进入新版。

### 6.2 必须通过的协作场景

首轮除产品功能验收外，完成以下操作验证：

1. 外网新 Framework 输入进入发布仓，平台仓能取得固定版本而不改变稳定线。
2. 平台从固定基线开发，回交新增、修改和删除，发布仓准确接纳。
3. 两个开发者修改同一平台，第二次回交不覆盖第一次已接纳成果。
4. Web、Android 并行回交，最终组合经过统一验证。
5. 升级进行中仍能发布稳定补丁，并将适用修复带入后续开发线。
6. 从实际发行包完成三平台正常安装与承诺的升级路径。
7. 更换当值负责人后，能够重建候选、继续处理合入和完成发布。

### 6.3 简化原则与默认安排

- 三仓保持，不新增同步中心、版本管理平台或独立 Profile 安装产品。
- 同步与反合采用路径边界和固定基线，不做跨仓整分支合并。
- 发布仓保存已接纳源码快照，平台仓保存开发源码；快照只由可追溯回交更新。
- 公共输入、平台开发依赖、完整发行组合分别承担不同职责，不维护重复的完整进度台账。
- 验证当前候选和承诺维护的版本线，不穷举所有版本组合。
- 默认维护当前稳定线及确有需要的上一条线。
- 公开接口、初始化、更新和发行支持的不足由外网维护者处理；内网发行脚本只执行已确定的装配职责。
