# 当前共建协作方案

2026-10-20。基于用户已确认的信息制定，供本轮共建执行安排使用。已确认原则见 [03](03-逐轮确认记录.md)，分析因素见 [04](04-可行性分析框架与遗留问题.md)。本文给出具体建议，不表示人员任命、环境资源或仓库创建已经执行。

## 1. 本轮决定与适用范围

沿用已运行的外网开发、外网 demo 主要场景验证、内网真实验证与交付链。Framework 只在内网使用；不建立面向外网用户的另一套正式交付。

本轮采用两条贡献路径：

1. Framework 主体、lite、review 通用增强、Android Profile 在外网贡献到 Maison 主线；Story Extension 在外网独立仓线开发与发布。
2. 已在内网开发的 Web Profile 保留内网权威源码，在内网与指定 Framework 构建组合验证和交付，不要求回流外网。

Web 采用第二条路径是承接已有成果与不可回传约束，不把 lite、review 等新公共能力继续放到内网形成另一套主体。本轮不搬迁核心主线、不重写 Web、不另造内网 Framework 分支、不建设通用包管理平台。

共建方式按工作需要确定，再配置人员环境。不能因某位成员目前只有内网环境，就把公共能力改成内网开发；也不能把所有公共实现退回盛强、王义康。

本轮不增设委员会、轮值或第二负责人制度。

## 3. 内外网工作安排

| 位置 | 本轮承担工作 | 交接内容 |
|---|---|---|
| 外网 | 公共源码开发、评审、集成；除内网 Web 外的主要功能场景 demo 验证；构建候选发布件 | 固定源码身份的包、版本与依赖说明、验证结果、已知问题及内网验收范围 |
| 内网 | 真实工程验证、交付使用；Web Profile 开发与验证；业务规则和内部适配维护 | 内网保留原始证据；外网仅接收人员分析后的文字转述，不接收内网文档、代码或日志 |

外网 demo 完成主要场景验证后再交内网，不把内网当作发现基础功能缺陷的主要场所。Web 已有源码不能外传，因此其开发验证保留内网，这是本轮明确例外。

内网发现问题时，由对应任务负责人组织内网分析：

- 属于业务规则、内部配置或 Web 自身的问题，在内网权威来源修复并重新验证。
- 属于公共 Framework、Android 或通用 Extension 的问题，通过人员转述反馈；外网负责人据此修改外网源码，重新产出候选件，再进入内网验证。
- 问题尚未定位时保留“待定位”，不先在内网改公共副本形成正式版本。

不以“脱敏”为由上传内部原件，也不将人员转述等同于允许搬运内部设计。沿用当前已运行的人工反馈方式。

## 4. 代码仓与贡献路径

| 对象 | 权威源码与组织方式 | 合入和维护 |
|---|---|---|
| Framework、lite、review、Android Profile | 外网 `agent-maison`；按任务开分支，不为每项功能另建仓 | 任务负责人提交改动；盛强核公共影响并合入共同主线；相互依赖改动明确先后提交 |
| Story Extension | 外网 `SimulatedWalletForHmos` 的既有 Story 开发线 | 王义康按现有版本安排维护；本轮共建不改变 story-1.0、新 2.0.0 的既有基线与切换决定 |
| Web Profile | 保留现有内网源码位置为唯一权威来源；如果尚无可共同维护的独立版本记录，先在内网建立专用 Git 仓 | 高云云维护并交付固定版本；不往外网复制，也不再建立第二份独立开发的 Web 源码 |
| 内网业务检视规则、知识和内部适配 | 所属业务仓 | 业务方负责内容，升级公共产品时保留 |
| 内网业务仓的 Framework 发布件 | 消费副本，记录采用的外网构建身份 | 不作为公共源码开发主线；修复走外网源码后重新交付 |

是否新建 Web 仓仅取决于现有内网位置能否唯一追踪和维护源码；本方案不要求为目录形式而搬迁已有成果。

贡献者可以修改任务必需的公共部分，不能将所有这类修改转交盛强编码。提交时说明目的、影响、依赖、验证和未完成事项，维护者负责评审与合入。无需在本轮建立新的评审系统，使用仓库现有提交与评审方式。

## 5. 交付形态

### Framework

继续通过 Maison 构建的 Framework 发布件交付。lite、review 属于该产品的共同源码成果，不作为本轮另立的独立产品包。Android Profile 达到集成与验证条件后随 Framework 包交付。

一个候选件不必同时包含所有在研能力。成熟工作合入并验证后即可形成候选；未完成的工作留在任务分支，不阻塞无依赖的交付。

### Story Extension

继续独立发布，明确采用的 Framework 构建，不仅记录同名版本号。由王义康维护组合验证与交付说明，不强制与 Framework 同日发版。

### 内网 Web 组合

Web Profile 保留内网版本，与固定的外网 Framework 发布件在内网形成完整可用组合。由高云云完成装配、验证和交付，使用者不自行寻找兼容版本。

这是独立维护源码、集中形成使用组合，不要求立即建设独立插件安装协议。装配与更新沿已有可用方式执行；若现有方式不能形成完整可用组合，则该项不能宣告完成，由负责人提出最小必要接入工作，不把缺口交给使用者解决。

### 对使用方的共同交付要求

交付说明写明目标工程类型、所含产品与构建身份、已验证范围、接入与升级步骤、已知限制及责任人。复用现有发布说明承载，不新建复杂发布登记系统。

同包、分包是维护方内部组织方式。业务方得到的是可按说明接入的已验证组合。

## 6. 人员与环境的当前要求

### 外网公共贡献者

盛强、王义康、钟玉生以及承担 review、lite 的人员，需要具备：

- 能访问对应权威仓、提交分支和参加评审的外网开发环境。
- 胜任公共产品开发与评审的强模型条件，不将内网运行模型水平当作开发条件。
- 可运行对应 demo 与相关检查的工具环境；内网业务原件不作为外网开发必需输入。
- 进入内网验证或组织内网验证的协作条件。

强模型配置按现有 Framework 开发经验提供，不以本轮开展模型横向评测为前置。平台局部工作的模型成本可以在执行中优化，不据此改变源码归属。

### 内网 Web 贡献者

高云云需要现有 Web 源码、内网代码仓、实际工具链与业务验证条件，以及指定 Framework 发布件。内网模型能否支撑现有 Web 任务，不在本轮作未经证据的保证；遇到明确能力不足时登记实际受阻工作与可用条件，不默认其成果可以搬到外网接手。

### 当前资源缺口及开工条件

黄志强、潘雨晨此前描述的主要条件是内网。要让两人增加公共产品开发产能，需要给本轮任务配置外网开发与强模型条件。这是本方案明确的资源要求，不把它隐藏为盛强、王义康的额外代写工作。

如果当前无法配置，两人可先承接任务澄清、内网使用场景与验收，但相应公共实现必须另有具备条件的明确承担者；否则任务保持未开工，不能登记成两项已并行开发，也不能为了开工就在内网另写一套公共实现。

本轮没有固定期限，各任务按实际投入制定简短计划。计划至少明确本次交付、负责人、协作依赖、开发位置、合入位置和验收终点，不要求先给全员设投入比例。

## 7. 立即执行顺序

1. 确认本轮任务负责人和上述环境需求，review/lite 先落实实际外网实现承担者；具备条件的任务可以直接开始，不等待全部人员环境齐备。
2. 每位负责人登记一页当前任务安排：交付结果、参与者与责任、开发环境和仓库、依赖、demo 交回、内网验收与交付位置。已有计划可直接补齐这些项，不重复立文档。
3. 贡献进入指定任务分支。跨责任改动由任务负责人协调维护者评审，明确依赖后集成；各负责人保持自己任务的状态，不让用户代为拼接进度。
4. 外网主要场景通过后，按成熟范围形成候选件并进入内网。Web 在内网完成对应组合验证。问题按第 3 节返回正确源码来源修正。
5. 内网验证通过后由对应交付负责人发布已验证组合，记录实际范围，不等待无关在研项。

本轮完成标志是各项当前工作有实际承担者、可用开发条件、唯一代码来源、可执行贡献路径和明确内网交付终点，并已有成熟成果通过该路径交付。这里只制定协作安排，不代替具体功能验收，不启动发布或环境变更。
