## 1. 产品边界

建议按能力划分负责人，以一个 Framework 主线集成；成熟 Profile 随框架发布，Extension 保持独立发布。开发可以分布在内外网，但源码来源与合入责任统一。

| 对象 | 建议职责与归属 |
|---|---|
| Framework 主体 | 通用阶段选择、上下文、授权、执行、审查、证据和恢复，归 Maison |
| lite | 小需求的轻量执行路径，优先复用 Framework 已有能力 |
| review 增强 | 面向实际代码变更的通用检视，支持不同开发来源和扩展规则，归 Framework |
| Web / Android Profile | 平台工具链、编译、UT、设备或浏览器测试、平台规则 |
| Story Extension | 取材、范围与决定、项目知识、业务评审、更新和送审，独立产品与发布 |
| 业务自定义检视规则 | 由业务仓维护，通过框架接口消费 |

本次读取 Maison `profiles/README.md`，已有能力声明、平台补充说明、规则覆盖和 provider 接口。建议先核现有能力能否满足需求，再决定必要的公共接口改动，不为 lite 和 review 各建一套调度、状态或检查机制。

## 3. 开发与发布形态

建议先采用一个 Maison 源码主线，包含主体和成熟 Profile，统一构建 Framework 发布件；Story Extension 保持独立版本和依赖声明。

- lite、review、Web、Android 通过短期特性分支推进，达到约定条件后进入主线。
- 未成熟 Profile 留在开发分支或明确的试验构建中；文件合入不等于正式支持。
- Profile 首次正式交付须有平台工具链及真实消费证据，以后按改动影响回归。
- Extension 发布固定已验证的 Framework 版本及构建身份，同版本号也区分不同构建。
- 内网使用组合记录 Framework 构建、Profile、Extension、宿主、模型及已验证范围。

暂不建议每个 Profile 独立发包。当前加载位置在 `framework/profiles/`，同包交付能减少安装、依赖与版本组合成本。只有出现明确的独立更新需求，才评估独立包及兼容、安装协议。

不建议长期维护内网版和外网版两套 Framework 产品逻辑。环境配置允许不同，公共修正回到统一主线。权威仓具体部署位置尚未决定。

## 4. 内外网协作

不建议固定为“外网两人开发，内网其他人验证”。这种方式可能使实现工作集中到少数人，内网发现问题后仍须等待转交。

| 工作 | 建议安排 |
|---|---|
| 通用流程和复杂公共机制 | 优先使用模型与工具条件较好的环境 |
| 平台适配 | 在能取得真实工具链、工程和设备的环境开发 |
| 业务规则与真实需求验证 | 在对应业务环境开展 |
| 面向内网的交付验收 | 使用内网实际模型和宿主验证可靠性 |
| 通用发布件 | 从统一、已评审的源码身份构建 |

跨网交接至少带基线提交、改动补丁或提交集合、验证结果和未解决问题。接收方先核基线再集成，避免目录复制后无法说明来源。

内网同事承担完整开发责任。允许转出的通用代码和脱敏案例回到权威主线；受限制的材料留在内网，通过获准的复现与验证结论协作。跨网方式须遵守已有规定，尚未确定具体工具和操作协议。

## 5. lite 与 review 的推进建议

建议 review 先形成最小可用结果，lite 同时澄清与试点，随后复用 review 能力。

### review

最小目标：无论代码来自 Framework 还是 vibecoding，开发者都能指定实际改动范围，完成有效检视、问题处理，并交给 committer 可复核的结果。

输入以 diff、相关代码、业务要求和项目规则为基础。已有设计和测试产物作为可用输入；缺少时补齐影响判断的必要信息，不强制补做完整开发流程。未运行和无法判断的部分明确记录。

先验证已有 review 对两类来源均有效，再逐步接入其他检查 Skill、静态工具和业务规则。committer 保留方案、业务逻辑、DFX 和合入裁决责任，AI 的“通过”不能替代这些责任。

### lite

最小目标：对边界清楚的小需求，以简短方案组织改动，完成适用的 UT、真机或浏览器测试及代码检视，以较低成本得到可靠结果。

轻量主要来自减少无用文档、重复读取、重复规划和不相关阶段。设备行为改动仍需设备证据；不涉及运行行为的改动不机械要求真机测试。

两项诉求都须明确适用输入与风险、必需能力、不适用条件，以及范围扩大、设计不清或验证失败时如何转入已有完整能力。验收比较耗时、人工介入和遗漏，不只看命令退出或模型自述。
