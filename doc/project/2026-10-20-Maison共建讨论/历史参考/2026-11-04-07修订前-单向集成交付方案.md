# Maison 内外网共建协作方案

2026-11-04。当前有效协作方案，按用户本轮完整确认的方案落盘。

本文接替 [06 三仓建议稿](06-内网三仓协作与完整版本发布方案.md)，保留原件供追溯。旧稿固定对象为本仓提交 `7a5cd5ce` 中的同路径文件。后续讨论、自查及确认依据见 §7；本次实际落实状态见 §6.1。文档完成不代表内网建仓、公共能力实现或真实发布完成。

## 1. 目标、产品关系与责任

覆盖各仓维护、内外网需求开发、依赖升级、完整发布和稳定版修复。

- Framework、Extension 在外网开发和独立发布。
- Web、Android Profile 在内网独立开发，向内网发布仓交付固定成果，随 Framework 主体一起交付使用者。
- 内网发布仓负责接收、组装、验证和发布完整 Maison，承担发行维护职责。
- Profile 或发行工作需要公共能力时，向外网 Framework、Extension 维护者提出诉求；内网不直接修改其公共产品内容。
- 每个完整版本指定一名当值发布负责人，团队成员可以轮值。部件维护责任保持连续，不随发布负责人轮换。

### 1.1 产品与交付关系

```text
外网 Maison 源码仓
    │ 发布一次 Framework
    ├─ 接入外网 Demo main
    │       └─ Story 分析变化、适配、正式发布 Extension
    └─ 将同一 Framework 发布件交入内网
                         │
内网 Web 源码仓 ─────────┤
内网 Android 源码仓 ─────┤
外网 Story 正式发布载体 ─┤
                         ↓
                 内网发布仓固定组合
                         ↓
             Framework＋Web＋Android
                         ＋
                 兼容的 Extension
                         ↓
                Maison 内网完整版本
```

Framework 发布不必等待 Extension 适配。Profile 可以提前验证新 Framework；完整 Maison 发布必须使用已明确兼容并完成内网验证的组合。

### 1.2 分工

| 角色 | 当前对应人员或安排 | 责任与交付终点 |
|---|---|---|
| Framework 维护者 | 盛强 | 公共需求判断、设计实现、评审合入、版本维护、发布及 Demo main 接入；提供升级影响和必要的内网组合发布支持 |
| Extension 维护者 | 王义康 | 根据 Demo main 的变化完成 Story 适配；独立发布，明确所依赖的 Framework 构建、适配说明和旧线维护安排 |
| Web 维护者 | 高云云 | Web 需求、源码、平台测试、公共能力诉求、依赖适配及固定成果交付；负责最终候选中的 Web 效果 |
| Android 维护者 | 钟玉生 | 同上，负责 Android |
| 当值发布负责人 | 每轮由团队指定，可轮值 | 发布仓日常变更组织、本轮范围和组合、依赖协调、候选验证、正式发布及本轮交接 |
| 跨仓需求负责人 | 每项跨仓需求指定一人 | 管理总目标、依赖、子任务和业务验收，推动整体结果，不替各仓维护者合入代码 |
| 业务验收人 | 对应需求方或实际使用团队 | 提供真实场景，确认需求效果和已知限制 |

发布负责人轮换时，交接当前完整版本、维护线、进行中的候选、未完成需求、已知问题和下一动作。记录放在发布仓，不依赖个人会话。

公共版本取舍由当值负责人组织相关维护者决定；涉及需求降级、取消已承诺能力或改变支持范围时，由需求方裁定。

## 2. 代码仓结构与自身维护

### 2.1 外网保持现有仓库与分支关系

**Maison 源码仓**继续使用自身已有开发和发布流程。Framework 作者从同一固定源码构建发布件：

1. 将该发布件接入 Demo main。
2. 将同一发布件及说明提供给内网。
3. 两处分别完成接入，不分别生成内容不同却同名的 Framework。

**Demo／Story 仓**保持现有职责：

| 分支 | 用途 |
|---|---|
| Demo `main` | Framework 正式版本在消费工程中的接入基线 |
| `story` | Story 后续版本的开发与适配 |
| `story-1.0` | 对应 Framework 3.0 的既有稳定维护线 |
| 其他必要维护分支 | 从实际发布对象建立，承接仍被使用的旧版本修复 |

Demo main 的提交身份与其中 Framework 的发布身份分别记录。Story 适配依据固定 Demo 基线分析，不要求将结构不同的 main 整分支合并进 story。

### 2.2 内网三仓

```text
Maison 内网项目
├─ maison-web
├─ maison-android
└─ maison-distribution
```

Web、Android 仓采用相同职责结构：

```text
profile/                 本平台正式源码
tests/                   部件测试
examples/                验证工程基础
dependencies.json        日常开发使用的固定依赖
docs/                    开发说明、需求与发布记录
.work/                   本地装配与运行现场，不入库
```

发布仓：

```text
inputs/                  外网正式输入及来源记录
release.lock.json        当前分支选用的完整组合
assembly/                发行装配入口及发行自身配置
docs/requests/           跨仓需求的协调记录
docs/releases/           候选、正式发布、维护范围及交接
validation/              组合场景、结果摘要和原始证据位置
.work/                   装配与验证现场，不入库
dist/                    输出包，通过发布渠道留存
```

目录名称为本方案采用的默认。已有符合职责的目录原位承接，不为统一名称搬迁历史。

### 2.3 各仓维护规则

| 仓库 | 可以修改 | 维护者合入前检查 | 交给下游 |
|---|---|---|---|
| Framework | 公共源码、公共接口、原生工具与发布能力 | 需求符合、公共影响、必要回归、迁移说明 | 固定发布件、构建身份、变化和支持说明 |
| Extension | Story 机制及所属适配能力 | 对应 Framework 合同、Story 能力、安装适配及必要回归 | 正式分发载体、对应 Framework、适配说明 |
| Web／Android | 本平台 Profile、测试及开发资料 | 平台效果、依赖身份、是否越入公共职责 | 固定源码提交、发布文件范围、验证结果 |
| 发布仓 | 输入登记、组合选择、发行装配、验证及发布资料 | 输入真实、组合成立、装配正确、升级边界清楚 | 完整包、完整版本、安装升级说明 |

各仓采用短期任务分支评审合入。维护者负责审查和合入，作者提供改动、依据及验证。跨仓接口变更由生产者与消费者共同核对。

公共缺陷回公共源码修复，Profile 缺陷回对应仓修复。发布仓不得通过修改装配副本完成产品修复。

### 2.4 需求与状态的真源

- 单仓需求保存在所属仓现有需求入口。
- 跨仓需求在发布仓保存总目标、负责人、子任务关系及整体验收；各仓保存自己的实施子任务。
- 总需求记录整体状态，子任务记录本仓实施状态，避免复制多份完整进度。
- 外网自行发起的需求仍沿外网入口推进；影响内网时，由发布仓建立对应接入事项。
- 内网原始代码、日志、文档和 Skill 保留内网。跨网协作沿用人员分析后文字转述；外网维护者据此建立自己的需求记录，互记可追踪标识，不自动同步内部原件。

## 3. 输入、依赖、分支与版本

### 3.1 发布输入与源码管理

内网以**正式发布内容**作为 Framework、Extension 输入。发布内容中包含可读源码，并不意味着内网取得公共源码修改权。

- Framework 接收原始发布件、清单及升级说明。
- Extension 接收其正式 adapt 所需分发载体和上下文，首轮沿用现有正式 Demo 形态，不自行发明精简包。
- 输入记录外网产品版本、固定源码／发布提交、构建身份、来源路径及校验信息。
- 发布仓可纳入解包后的发布快照便于比较，原包按发布输入归档。两者由同一输入生成，不能分别维护。
- 外网完整开发仓只在确有调查需要时作为只读参考，不作为内网第二条公共开发主线。

Story 载体附带的 Framework 保留其来源身份。正式组合默认采用 Story 发布已确认的 Framework 配对；不同配对须先由外网维护者明确兼容，再进入内网验证。

### 3.2 Profile 怎样开发和验证

Profile 仓的依赖记录固定：

- 可取得输入的发布仓提交和位置。
- Framework、Extension 的实际发布身份。
- 所用发行装配能力的版本。

日常开发按该记录重建本地验证工程，装入当前 Profile 工作分支。代码始终在 Profile 源码目录修改。

完整候选验证则使用发布仓锁定的组合：

- **日常开发依赖**由 Profile 仓决定。
- **完整验证与发行依赖**由候选组合决定。
- 实际运行记录写明最终使用的输入。
- 旧 Profile 在新 Framework 上无需改代码即可通过时，直接复用旧提交；兼容证据保存在该完整候选中。

从开发源码导出 Profile 发布内容时，只包含所属正式文件，排除测试现场和依赖副本。下游选用固定提交，不读取浮动分支头。

### 3.3 分支

| 仓库 | 主线 | 短期分支 | 长期维护线 |
|---|---|---|---|
| 外网 Framework／Extension | 沿现有安排 | 功能、修复、适配分支 | 对仍需支持的正式版本维护 |
| Web／Android | `main` | `feature/*`、`fix/*`、`upgrade/*` | `maint/<版本线>`，确需修旧版时建立 |
| 发布仓 | `main`，下一完整版本 | 输入接入、部件集成、组合升级分支 | `release/<版本线>`，承担候选冻结及后续补丁 |

短期分支按实际任务使用，不要求每次经过所有分支种类。

稳定补丁从对应发布对象起步，不整体合并最新开发主线。修复向开发线同步时，只带适用修复，不把旧依赖记录覆盖到新线。

### 3.4 版本与支持

- Framework、Extension 沿用外网产品版本及构建身份。
- Web、Android 使用固定提交，内部里程碑可打 tag；不建设面向业务方的独立安装发布流程。
- 内网 Maison 使用独立完整版本号。兼容新增能力升次版本，修复升补丁，不兼容使用或升级变化升主版本。
- 完整版本固定四项输入及发行装配版本，不强制所有部件同时升版。
- 正式 tag 和已发布内容不覆盖；修订必须产生新候选或新版本。
- 默认维护当前稳定版本及确有使用需求的上一条版本线。停止维护前说明承接版本及在途工作安排。
- 声明支持旧完整版本前，必须确认其 Framework、Extension 上游仍有可行维护路径，不能承诺内网无法完成的公共修复。

## 4. 一项需求从提出到交付的完整流程

### 4.1 接收、归属与安排

| 步骤 | 负责人 | 输入与动作 | 产出／完成条件 |
|---|---|---|---|
| 需求提出 | 需求方、发现者 | 说明场景、目标、现象和使用版本 | 可判断的需求或问题 |
| 初步归属 | 相关部件维护者；跨仓由当值负责人协调 | 判断是平台、Framework、Extension、发行还是目标工程内容 | 明确承担仓；未知则先定位 |
| 跨仓拆分 | 需求负责人 | 写明共同目标、子任务、依赖、保持项和验收场景 | 每个子任务有人承接，依赖顺序明确 |
| 版本安排 | 当值负责人及各维护者 | 按实际投入决定进入哪个候选；成熟无依赖项可先交付 | 本轮范围和延期项可见 |

只有平台内部改动的需求直接在内网开发。公共能力诉求由相应外网维护者接收，确认解决方式和交付版本；平台负责人可以完成不依赖该能力的部分。

### 4.2 外网公共开发

**Framework 维护者：**

1. 接收公共需求，核实通用性、现有能力与影响。
2. 在 Maison 自身流程中完成设计、开发、评审和外网 demo 验证。
3. 提前说明影响 Profile、Extension 的接口或行为变化。
4. 从固定源码产出一次正式发布件。
5. 将该发布件接入 Demo main，并提供固定 Demo 接入提交。
6. 将同一发布件和说明交入内网，处理后续真实反馈。

**Extension 维护者：**

1. 固定需要跟进的 Demo main 基线。
2. 分析 Framework 变化，明确 Story 需要修改的部分。
3. 在适用开发线完成实现、评审和验证。
4. 通过现有 Story 发布流程形成正式分发载体。
5. 交付对应 Framework 身份、适配说明、已知限制和旧需求边界。
6. 旧 Extension 经验证兼容时可以复用，不为跟随版本机械改版。

公共产品的局部开发验证完成，不代替内网平台与完整使用结果。

### 4.3 内网平台开发

Web、Android 各自执行：

1. 固定当前开发依赖，从本仓建立任务或升级分支。
2. 用固定输入装配本地平台验证工程。
3. 在本仓实现平台能力，完成对应工具链和实际场景验证。
4. 发现公共能力缺口时，形成文字诉求交外网；不改公共副本，不交付旁路实现。
5. 取得新公共输入后继续验证；涉及 Story 的流程等待确定的 Extension 输入。
6. 经本仓评审后固定候选提交，交给发布仓。
7. 交回实际依赖、变更、验证结果、已知问题，以及是否改变平台接入方式。
8. 参与最终组合验证并处理所属缺陷。

不要求 Web、Android 同时更新。旧部件经新组合验证可继续使用。

### 4.4 集成、候选与反馈

当值发布负责人执行：

1. 接收并核对公共输入；导入与采用分开。
2. 接收 Profile 固定成果，更新本轮组合。
3. 从干净现场装配完整候选。
4. 将该候选交相关负责人验证，记录实际对象。
5. 对问题按所有权分派，更新固定输入后形成下一候选。
6. 合入期间若依赖或关联部件变化，重核受影响结果；其余证据复用。
7. 达到完整发布条件后冻结版本并发布。

两个分支无 Git 冲突不代表组合成立；不同组合下的局部通过不能直接拼成整体通过。

内网问题由人员分析后转述外网。外网修复重新进入原发布链；内网保留真实证据并完成复验。

## 5. 组合发布、补丁与验收

### 5.1 明确内网发行的输入输出

内网采用**已发布内容组装**：

```text
输入：Framework 正式包＋固定 Profile 成果＋Extension 正式载体
处理：组装、校验、平台与完整链验证
输出：一个具有独立身份的 Maison 完整发行包
```

完整发行包包含：

- 已纳入 Web、Android 的 Framework 分发内容。
- 兼容的 Extension 分发载体。
- 组合和来源清单。
- 安装升级入口及说明。
- 已验证范围、限制与恢复安排。

使用者选择工程类型，不自行寻找和拼接四个部件。Extension 保留独立适配入口，依赖方向仍为 Extension → Framework。

### 5.2 首轮必须交付的公共发行支持

当前不能把“Profile 独立维护后可直接组成正式 Framework 包”当成已经实现的能力。将它作为首轮明确任务，由 Framework 维护者承接：

- 接收固定 Framework 发布件和指定 Profile 成果。
- 保持公共运行内容不被内网修改，限定 Profile 的归属位置。
- 输出可验证的组合分发内容，保留上游身份并表达内网组合身份。
- 支持原生初始化、更新和必要的旧 Profile 文件退出。
- 与现有发布校验衔接，不让内网自行篡改清单冒充原包。

Extension 维护者负责确认正式载体在内网组合中的正常 adapt 使用方式；需要修改公共适配机制时，在外网完成。

发行仓只维护组合选择、调用和发行自身内容。首轮不建设通用包管理平台，也不替代 Framework 初始化与 Story adapt。

### 5.3 发布验收

| 验收对象 | 责任人 | 必须得到的结果 |
|---|---|---|
| 输入与组合 | 当值负责人 | 输入可取得，身份固定，产品配对符合上游结论 |
| 平台能力 | 各平台维护者 | 承诺的平台场景实际成立 |
| Story 链路 | Extension 维护者配合平台维护者 | 平台上的承诺流程成立；公共与平台问题分别归因 |
| 安装／升级 | 当值负责人组织 | 从明确起点完成接入，保留目标知识、对接和有效配置 |
| 在途需求 | 需求负责人及相关维护者 | 明确哪些可继续、哪些留在旧现场完成 |
| 实际使用 | 业务验收人 | 需求效果符合约定，限制可接受 |

2.x 不接续旧需求现场的既有边界保持。产品升级不等于历史需求迁移；旧需求需要时留在旧版工作区继续，新需求进入新版。

正式发布使用实际验证的内容。重打包改变内容时重新核验，不用候选通过为不同内容背书。

### 5.4 三类变更的运行方式

| 场景 | 处理 |
|---|---|
| 普通平台功能 | 平台仓基于固定依赖开发；发行仓只更新该平台，完成受影响验证后发布 |
| Framework 升级 | 新包先接入 Demo main 和内网；Story 与 Profile 分别适配；确定组合后完成整体候选验证；稳定线继续维护 |
| 稳定版补丁 | 从稳定版本对象修复，只更新必要输入；在对应发行维护线验证发布，并向后续开发线同步适用修复 |

Framework、Extension 稳定补丁由外网对应维护线交付，使用固定发布对象进入内网，不要求 Demo main 回退。

发行装配自身的修复可以只提高完整发行版本，四个产品输入保持不变。

## 6. 首轮执行与交接

首轮按以下顺序完成，前一步的产出直接作为后一步输入：

| 顺序 | 工作 | 责任与完成条件 |
|---|---|---|
| 1 | 指定当值负责人，登记当前实际版本和使用范围 | 当值负责人形成首轮范围及责任表 |

首轮验收还应实际推演三项协作操作：

1. 一个 Profile 更新、另一个保持不变，能够形成完整版本。
2. 新 Framework 适配进行中，旧稳定线仍能正常修复。
3. 发布负责人更换后，能够取得固定输入、重建验证现场并定位未完成任务。

本方案中的人员对应沿既有分工；当值责任按每轮指定。仓名、目录名、分支命名及“当前稳定线加必要上一条维护线”为默认安排。具体实现使用现有工具和入口，新增公共能力统一由外网维护者交付，内网按本方案承担平台开发与完整发行。
