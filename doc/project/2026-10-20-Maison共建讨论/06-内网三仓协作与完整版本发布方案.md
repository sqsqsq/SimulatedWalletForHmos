# 内网三仓协作与完整版本发布方案

2026-11-03。维护设计者根据本轮共建讨论整理，按用户要求保存于共建目录。

状态：协作方案建议稿。用户已要求按三仓方案展开并保存；本文不表示全部细节已批准，也不授权创建仓库、实施装配工具或发布。已确认事实与建议安排分别列出。本文是本轮内网协作与发布讨论入口；05 保留为此前建议原件，其中 Android 外网开发的安排已被本轮事实更新。

## 1. 已确认事实与讨论依据

用户本轮明确：

- Framework、Extension 继续在外网独立开发发布，再同步内网；Android、Web Profile 在内网开发。
- 内网需要完整版本发布，覆盖 Framework、Extension 及承诺的平台能力；各部件开发尽量互不干扰，减少上游升级带来的重复适配。
- Maison 主仓有自己的分支和版本演进节奏。Framework 作者把发布版本推送到 Demo main；Story 根据 main 的变化分析适配方案，完成新版本开发与发布。
- `story-1.0` 对应 Framework 3.0，是稳定维护线；`story` 已基于 Demo main 改造，承接后续适配。
- 内网成果不能回传外网、内网问题由人员分析转述、外网 demo 与内网真实验证各负其责等既有约束保持，来源见 [03](03-逐轮确认记录.md)。

本轮只读核对：本地 `story-1.0:demo/framework/RELEASE-MANIFEST.json` 为 Framework 3.0.0，source_commit 为 `0143e21ecacf679fcb021d36243ab0372b71a305`；同分支已装 Extension manifest 为 1.9.9。Demo main 的 Framework 为 3.1.0，source_commit 为 `879f1e8b2b398bd6e178f1e1abcbfe2e94958042`。这是身份核对，不证明内网平台组合已验证。

讨论与修订依据：助手最初建议四个部件仓加一个集成仓，后根据 Framework/Extension 内网主要承担发布输入、尚无独立开发职责，改为两个 Profile 开发仓加一个集成仓。用户要求重点讨论共建协作而非三种 Git 形态的比较，随后要求按三仓展开日常开发、升级和补丁流程。用户补充外网实际适配链后，方案改为沿 Demo main → Story 适配发布取得正式组合，不把任意 Framework 与 Extension 版本拼合视为有效发布输入。

## 2. 总体链路与责任

```text
Maison 独立开发发布 Framework
  → Framework 作者更新 Demo main
  → Story 分析变化、适配、正式发布
  → 内网取得确定的 Framework＋Extension 输入
  → Web、Android 适配与组合验证
  → Maison 内网完整版本发布
```

新 Framework 到达 Demo main 后，内网可以提前开展平台适配；此时不认定 Story 已兼容。Story 正式发布后才形成可进入完整集成验证的上游组合。旧 Extension 经确认兼容时可以复用，不要求每次随 Framework 升版。

| 责任 | 建议承担者与交付终点 |
|---|---|
| Framework | 盛强：外网公共能力、评审与发布，提供固定输入和升级影响 |
| Extension | 王义康：沿 Demo main 适配发布，明确 Framework 构建和 Demo 基线 |
| Web | 高云云：内网平台开发、适配、实际效果与固定部件交付 |
| Android | 钟玉生：内网平台开发、适配、实际效果与固定部件交付 |
| 内网集成 | 人选待明确，可兼任；负责组合选择、验证组织、完整发布及稳定线维护 |
| 跨部件任务 | 每项明确一位任务负责人，推动依赖与整体结果；所属维护者负责各自改动及合入 |

人员安排沿此前讨论提出，不代表本轮已核实任命或投入。集成负责人不包办部件修复，不新增管理层级。

## 3. 三仓与目录

内网一个项目组，建立 `maison-web`、`maison-android`、`maison-distribution` 三仓。仓名为建议。

### 3.1 Profile 开发仓

两个仓采用相同职责布局：

```text
maison-web/ 或 maison-android/
├─ profile/                 正式 Profile 源码
├─ tests/                   部件测试
├─ examples/                可重建的验证工程基础
├─ dependencies.json        本分支固定开发依赖
├─ docs/development.md      开发与验证入口
├─ docs/releases/           部件发布说明
└─ .work/                   依赖副本与验证现场，不入库
```

`profile/` 对应最终 `framework/profiles/<profile-id>/`。平台维护资料不混入发布内容。公共 Framework 修改须逐项确定归属，不能把完整 Framework 副本作为两个 Profile 的长期源码。

依赖记录包含：集成仓地址与固定提交、Framework 和 Extension 输入身份及路径/校验信息、装配方法的固定位置。固定提交用于取得内容，实际部件身份用于判断依赖是否相同。不引用浮动 main 或“最新版”。Web、Android 无实际继承关系时不互相依赖。

开发者按记录取得输入，在 `.work/` 内装配消费验证工程，再装入本分支 Profile。代码修改回 `profile/`，不提交依赖副本。开发现场与正式发布复用同一套装配规则。

### 3.2 集成发布仓

```text
maison-distribution/
├─ imports/framework/<输入身份>/   Framework 发布内容与来源记录
├─ imports/story/<输入身份>/       Story 正式分发载体与来源记录
├─ composition.lock.json           本分支完整组合
├─ assembly/                       最小装配、安装与升级实现
├─ validation/scenarios/           组合验收场景
├─ validation/results/             结果摘要及原始证据位置
├─ docs/releases/                  完整发布说明
├─ .work/                          验证现场，不入库
└─ dist/                           输出包，不作为源码维护
```

输入记录保留外网仓、固定提交、来源路径、产品版本、构建身份、校验信息；Story 输入另外说明对应 Framework 和 Demo 基线。已导入输入不原位修改，同名版本不同构建使用不同输入身份。原始发布件沿现有存储方式留存，不为此新建制品平台。

Story 暂保正式 adapt 所需完整载体和上下文，不假定单独提取 `doc/extensions/` 即可安装。载体业务代码不直接装入目标；附带 Framework 不得默默覆盖组合明确选中的版本。

组合清单只维护本版选择：完整版本、Framework/Extension 输入身份、Web/Android 仓库与固定提交及版本。导入新输入不等于采用它。Profile 开发依赖与组合清单各有用途，不互为第二份发布台账。

### 3.3 跨仓“合入”的含义

- 外网到内网：导入固定发布内容形成提交，不合并 Maison、Demo main、Story 的整条分支。
- Profile 到集成仓：选固定提交或版本，取得发布内容并更新组合，不合并 Profile 仓历史。
- 同一仓内：任务分支经评审合入主线或维护线。

目录差异通过明确的发布输入和装配映射解决。Framework 使用 Maison 已构建发布件；Extension 使用指定正式 Story 发布源，不取开发分支最新 `extensions/` 冒充发布版。

## 4. 分支与版本

| 仓 | 分支/标签 | 用途 |
|---|---|---|
| Profile | main | 下一部件版本共同开发线 |
| Profile | feature/<任务>、fix/<问题> | 普通开发与修复 |
| Profile | upgrade/<上游基线> | 依赖升级适配 |
| Profile | maint/<版本线> | 主线前进后仍需修复的旧版，按需建立 |
| Profile | v1.1.0 等 tag | 固定部件版本 |
| 集成 | main | 下一完整版本集成线 |
| 集成 | import/<输入> | 导入发布输入，核对后合入 |
| 集成 | integrate/<任务> | 更新部件选择或装配 |
| 集成 | upgrade/<上游基线> | 新组合整体升级 |
| 集成 | release/1.0 等 | 候选冻结及该版本线补丁维护 |
| 集成 | maison/v1.0.0-rc.1、maison/v1.0.0 | 固定候选与正式版本 |

不按部件设长期分支，不为每个补丁建长期分支。正式 tag 不移动覆盖，实际发布包与校验信息留存。

Framework、Extension 沿外网版本；Profile 各自独立编号；内网完整 Maison 使用独立主/次/补丁号。不兼容的使用、安装升级或支持变化升主版本，兼容新增能力升次版本，修复升补丁版本。Framework 版本变化不机械决定完整产品版本级别。无代码变化的部件不为完整发版而升版。

兼容声明帮助选择输入，正式结论仍绑定实际验证组合；“都是3.x”不等于兼容。建议初期维护当前稳定版及确有业务需要的上一条版本线，不默认无限维护历史版本。

## 5. 三种工作场景

以下编号仅作流程示例，不表示版本已经存在。初始完整版为 `Maison 1.0.0 = F0 + E0 + Web 1.0.0 + Android 1.0.0`。

### 5.1 日常 Web 功能开发

1. Web 从 main 建 feature 分支，沿用固定 F0/E0，在自己的消费验证工程开发测试。
2. 评审合入 Web main，固定候选提交，交回依赖和结果。
3. 集成仓建 integrate 分支，只更新 Web 选择，重新装配并验证相关组合与升级路径。
4. 缺陷回所属仓修复；集成仓只修自己的装配问题。通过后固定部件版本，合入并发布完整候选。
5. 最终可形成 `Maison 1.1.0 = F0 + E0 + Web 1.1.0 + Android 1.0.0`。Android 不需要无故改代码或升版，按实际影响参与验证。

Web 依赖已有 F0/E0，集成仓接收其新成果；不要求先发布包含新 Web 的完整版本，Web 才能开发，避免循环依赖。

### 5.2 Framework 升级

1. 外网 Framework 发布 F1 并更新 Demo main；内网导入 F1，保持稳定组合不变。
2. 两个 Profile 可提前建立 upgrade 分支验证平台能力，此时不声称完整 Story 链成立。
3. 外网 Story 验证旧 E0；必要时适配发布 E1，并明确对应 F1。旧版兼容则复用，不强制升版。
4. 集成仓导入确定 Story 输入，建立 upgrade 分支固定 F1/E1 候选，供 Profile 仓更新依赖。
5. Profile 各自验证，必要时改代码，交回固定提交。集成仓选入并完成完整组合、新装和升级验证。
6. 冻结候选，发布新完整版本；旧稳定线继续维护。旧 Android 经验证兼容时可沿用，否则完整升级尚未完成。

F1 已导入、Story 已适配、Profile 已通过、完整版本已发布分别记录。各仓无依赖的工作可以并行，不强制所有人同步升级。

### 5.3 稳定版补丁

假设 Maison 1.1.0 在用，而主线正在升级 F1：

1. Web 从 v1.1.0 建 maint/1.1，在 F0/E0 下修复并固定补丁候选。
2. 集成仓从 maison/v1.1.0 接续 release/1.1，只替换 Web，其他输入保持。
3. 完成问题、受影响组合及升级验证，发布 Web 1.1.1 与 Maison 1.1.1。
4. 检查 Web main 和升级线是否仍有该缺陷，按各线实现同步修复，不把旧依赖记录覆盖到新线。

稳定线不通过合并最新开发主线取得修复。若缺陷属于 Framework/Extension，先由外网所属产品修出正式补丁，再导入稳定组合。不得修改上游快照后沿用原身份。

## 6. 装配与完整发布

完整包采用外层产品包，包含 Framework 原始发布件、Extension 正式分发内容、两个 Profile 固定发布内容、装配与安装升级入口、组合清单、校验和发布说明。用户取得一个产品，按目标选择适用 Profile，不自行寻找兼容部件。

安装责任顺序：核目标现场与组合适用条件 → 接入指定 Framework 并装入所选 Profile → 原生初始化/更新 → 对应版 Story adapt → 必要知识与对接适配 → 结果检查。细节服从所选版本真实入口；Profile 必须在初始化选择它之前可用。

文件所有权：公共 Framework 来自外网发布；Profile 来自内网对应仓；Extension 机制来自正式发布源；业务知识、对接及有效目标配置归目标工程。开发侧整体安装 demo 的 `publish_to_demo.py` 不直接用于覆盖业务目标的 Extension。

当前已知实施前提：Profile 位于 `framework/profiles/`，Framework 发布件有文件清单和哈希。内网需保留上游原始身份，并记录附加 Profile 和最终装配身份。若现有安装更新/身份检查不能处理，应由所属所有者补最小接入能力；不篡改上游清单后冒充原包，不另造旁路。

需要的最小新增维护内容是固定输入获取与统一装配，解决手工复制、依赖漂移和遗漏；各仓各自复制是更简单但易漂移的替代。本文提出统一装配建议，尚未授权实现，不建设通用包管理系统。

发布完成条件：输入和装配固定；承诺平台及能力有对应证据；新装、受支持升级和实际可行恢复有结果；交付实际验证的包，重打包改变内容须重新核；保护目标知识、对接和配置。构建/离线通过不代替真实内网行为通过。回退须考虑配置和需求现场，不以切 Git tag 代替业务恢复。

## 7. 协作交接与落地顺序

外网发布由部件负责人交固定输入、变化和升级影响；Profile 交回固定提交、依赖、验证和已知问题；跨部件任务负责人协调动作与先后；集成负责人选择组合、组织候选验证和完整发布。使用现有任务、评审和发布记录，不新建管理平台。

落地顺序：

1. 核 Web/Android 实际边界，识别公共改动及现有源码历史，明确责任位置。
2. 明确集成负责人，建立三仓并保护已有历史；实际人员与环境尚待落实。
3. 导入已知正式 Framework 3.0.0＋Extension 1.9.9 输入；不能据此假定内网 Profile 已适用。
4. 核并补齐最小装配、身份、升级及恢复能力，形成首个经过真实内网验证的完整基线。
5. 从该基线分别推进普通开发、上游升级和稳定补丁。

待核实项集中为：Profile 是否已有公共 Framework 分叉、正式 Story 载体的最小可分发边界、内网源码/权限与负责人、Profile 组合对现有安装更新和发布校验的影响。它们影响实施设计，本文不把建议目录或流程当作已经实现的功能。
