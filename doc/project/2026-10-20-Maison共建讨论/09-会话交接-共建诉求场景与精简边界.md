## 2. 用户真正要求解决什么

用户多次把焦点从 Git 形态拉回协作本身：

> “你的重点不是对3种方案进行对比分析，而是基于这些信息，给出实现maision共建的协作方案”

> “这是一个复杂的问题，你想的太片面，请整合目前的文档和分析结果，给出完善的共建文档，讲清楚人+仓库+版本 3者之间的关系和场景”

完整目标包括：各部件维护者能独立推进；公共依赖有明确来源；多人并行修改不会相互覆盖或把在研功能带进稳定版；使用者拿到确定、验证过的组合；失败能找到责任人、回正确源码修复，并进入下一次可用版本。

“简单”与“完整”的共同判据是：接手人能从一项需求或一个问题开始，知道谁在哪个仓、基于哪个版本操作、交什么给谁、怎样确认完成。少写目录或少建仓可以是简化；删掉依赖、冲突、验证和旧版修复的处理不能直接算简化。

## 4. 讨论中的关键纠正：原问题、为何返工、最终保留什么

### 4.1 三仓并不是原始目的

用户最初给出分支、submodule、多仓三种候选，要求解决并行、多版本、补丁、release 等关系。助手先推荐五仓，后因 Framework／Extension 内网主要是输入来源，收敛为两个平台仓加一个发布仓。用户随后要求“按三仓方案”展开并完整确认了方案。

因此三仓是本会话当时采纳的方案，不是脱离场景的永恒约束。另一个会话若获准改成单仓，可以减少跨仓同步；但还必须处理任务分支、部件边界、选择交付范围、候选验证和稳定线维护。不能以“同仓不用反合”推导这些问题全部消失。

### 4.2 “谁任职”不是需要长期纠缠的问题

用户对集成负责人选的原话：

> “这个不是关键，理论上共建团队的任何人都可以轮值负责”

本会话据此在方案中采用每版明确当值、可轮换、交接资料留仓。核心是责任可确定、接手不丢状态；用户不是要求另建排班制度。固定一人可作为后来选择，但不能把“轮值必然很重”当作已经证明，更不能因此删掉负责人更替的交接场景。

### 4.3 发布仓必须有功能验证能力，不能只是中转目录

用户明确指出：

> “完整的maison发布仓，应该包含发布前的必要功能验证能力啊，否则谁为组合发布的结果负责呢？”

助手早期只写“组织平台验证、汇总结果”，用户认为不足。后来方案补入发布仓的代表工程、场景、执行入口和两级验证：合入看本次变更及相关连接；发行看最终确定组合的承诺能力。

**要求是发行对象有真实验收能力和责任，不是每个补丁都从零重跑所有平台所有测试。**07明确允许按影响复验、复用未受影响证据，不穷举版本组合。平台作者可执行测试，但应使用同一候选、发行场景和预期；“作者本地通过”与“组合发行通过”仍是两件事。

### 4.4 用户反复追问真实文件与真实安装

用户原话包括：

> “请把发布仓的中的inputs/dist的真实形态讲清楚”

> “各项目要如何集成，是否了解清楚了现有framework和Extension的真实具体安装步骤”

此前助手只讲版本和架构，没有完整核安装，是确实存在的缺口，不应因其后补充细节较长就全部删回抽象口号。后来形成的区分是：Framework 原包、Story 正式消费载体、开发源码、安装后工程、组装现场、实际交付物各有用途；“发布包里有源码”不等于“内网重建公共开发主线”。

07采用原包和来源快照、已接纳平台源码、组装现场和输出分离，是一种实现。目录名、清单格式、是否生成外层 ZIP均可重新评估；但维护者和业务方仍要知道实际取什么、安装什么、哪些文件不可覆盖、结果绑定哪个版本。

### 4.5 发布仓与平台开发之间必须有闭环

用户明确指出：

> “发布代码仓不会直接开发需求，但是它是一个核心的中转和发布点。web和android要从发布仓同步。开发完还要反合到发布仓”

> “发布仓要解决接受上游更新、下游反合、合入验证、发布验证”

在具体选择中，用户选择了“按部件边界回交（推荐）”。在当时三仓方案下，这意味着只回交平台路径及对应源码，不混入平台工程、测试现场和公共副本，不要求整仓共享 Git 历史。

简化为单仓后，物理跨仓回交可由任务分支合入替代；仍需要说明每项任务的共同基线、目标版本线、依赖、删除项、冲突承担者、验收对象及接纳结果。不是把整个 main 当“所有部件随时都能发”的承诺。

## 5. 接手者必须推演的问题场景

以下是判断简化是否保住能力的场景清单，不要求新增十五套工具或自动化测试。用现有分支、清单和真实工程即可回答；不能处理的须标明限制及处置。

| 场景 | 接手方案至少回答什么 | 遗漏后的典型后果 |
|---|---|---|
| 外网 Framework 已到，Story 尚未适配 | 谁保存新输入，平台能提前测什么，稳定组合是否变化 | 收到新包就被当成可完整升级 |
| 同名 Framework 版本存在不同构建 | 用什么固定对象辨认，Demo接入提交与源码/发布身份如何对应 | 只写3.x版本号而拿错实际内容 |
| 仅 Web 做普通功能 | Web 从哪个基线起步，哪些成果被选入本版，其他部件如何保持 | 无关平台或公共依赖被顺带升级 |
| 两人并行修改同一平台 | 共同基线、冲突解决位置、第二项如何包含第一项成果 | 旧目录快照覆盖已接纳修改 |
| Web 可发，Android main 已含未完成新功能 | 如何形成只含已成熟范围的候选与 tag | 记录写旧 Android，tag实际包含新 Android |
| 平台基于 F0 开发，集成期间改为 F1 | 验证结论绑定哪个组合，何时重核受影响场景 | 无Git冲突就把旧结果移签新组合 |
| 平台尚需公共能力 | 向谁提诉求，谁开发，等待期间做什么，何时算完成 | 内网直接改核心或用旁路交付 |
| Framework升级期间稳定版报错 | 旧线怎么取输入、修哪里、如何发布补丁 | 为取一个修复整体合入新主线 |
| 一个修复影响多个活跃分支 | main、升级线、旧维护线分别是否要带修复 | 补丁修好了，下一版又复发 |
| 发行装配或安装说明自身出错 | 部件不变时谁修发行内容、怎样形成新发行身份 | 没有部件发版就无法修发行问题 |
| Profile源码未变，公共Framework变了 | 对实际受影响调用和运行行为怎样复验 | “平台没改”被错误等同于“不受影响” |
| 目标首次安装 | 从实际交付物进入原生 init/adapt，平台选择和真实工程是否可用 | 只在已装好的作者工程上验过 |
| 旧工程升级且有知识、规则、对接和人工改动 | 哪些保留，哪些适配，未完成对接如何标明 | 简单覆盖让业务内容丢失或功能假通过 |
| 1.x在途需求遇到2.x安装升级 | 软件升级和需求现场续行如何区分 | 把“已装新版”当成旧需求可直接续做 |
| 发布人换人、已有候选验证失败 | 后继者如何取得同一候选、继续失败处理 | 重选一套版本，丢掉失败对象和结论 |
| 业务问题尚未定位或上游不修旧线 | 何种现场可以恢复、是否可升级、由谁接受取舍 | “退回上一版”成为无条件承诺 |
| 一个平台暂不能进入新版 | 该版支持范围、旧线、使用者选择如何明确 | 三平台完整支持口径与实际能力不符 |

上述场景同时适用于“一个仓＋目录”和“三仓＋回交”。需要的是可执行回答，不是预先认定只能用 07 的工具和结构。
